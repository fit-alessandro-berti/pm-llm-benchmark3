# 1. Delay-decomposition definitions

For a case *c* and branch *i*  {A, B, C}, let timestamps be expressed in minutes from midnight on 2026-05-19.

| Symbol | Definition | Formula (from log) |
|---|---|---|
| `arrival_c` | Entry to process | given |
| `fork_c` | Earliest time all branches permitted to begin | given |
| `start_i,c` | Branch *i* begin | given |
| `end_i,c` | Branch *i* complete | given |
| `f_s,c` | Final activity **F** begin | given |
| `f_e,c` | Final activity **F** end | given |

**Computed quantities**

- **Upstream elapsed (before fork)**  
  `U_c = fork_c  arrival_c`

- **Branch queue (own-branch delay after fork)**  
  `Q_i,c = start_i,c  fork_c`  
  *(Assumption: a branch never starts before `fork_release`; if it did, queue would be 0 and we would revise. All cases satisfy `start  fork`.)*

- **Branch active service**  
  `S_i,c = end_i,c  start_i,c`

- **Join ready (unobserved max-completion)**  
  `J_c = max(end_A,c, end_B,c, end_C,c)`

- **Critical branch** (deterministic tie-break A > B > C)  
  `crit_c = argmax_i end_i,c` with lexical tie resolution.

- **Branch synchronization waiting** (post-completion idle until all done)  
  `W_i,c = max(0, J_c  end_i,c)`  
  For the critical branch `W_crit,c = 0` unless a tie occurs.

- **Elapsed fork-join stage** (parallel stage duration; **not** summed across branches)  
  `P_c = J_c  fork_c`

- **Downstream queueing before F**  
  `D_c = f_s,c  J_c`  
  *(Assumption: the rule `final_start  join_ready` holds; if it failed, `D_c` would be negative, signaling a data/model inconsistency. All cases are non-negative.)*

- **Final service**  
  `F_s = f_e,c  f_s,c` (observed constant 20 min).

- **Total case flow time**  
  `T_c = f_e,c  arrival_c`

**Why summing all `W_i,c` double-counts elapsed clock time**

For any branch *i* that starts at or after `fork_c` and ends at or before `J_c`:

`Q_i,c + S_i,c + W_i,c = (startfork) + (endstart) + (Jend) = J_c  fork_c = P_c`

Thus each branch individually spans the full parallel interval `P_c`. Summing over three branches gives `3·P_c`, triple-counting the same wall-clock period. The decomposition avoids double counting by assigning the parallel interval to the **critical branch only** (`P_c = Q_crit + S_crit`) and treating non-critical synchronization as **resource-idle overlap**, not additive flow time.

**Additive identity (no double counting)**

`T_c = U_c + P_c + D_c + F_s`  
`P_c = Q_crit,c + S_crit,c`

All other branch metrics (`Q_i`, `S_i`, `W_i` for `i  crit`) are diagnostic of resource contention, not additional flow-time terms.

    delta2 = r['join_ready_min'] - J2
    saved2 = max(0, delta2 - r['downstream_queue']) if delta2 > r['downstream_queue'] else 0

    # CF3: eliminate downstream queue

    cf_rows.append({
        "case": r['case'],
        "CF1_delta_join": delta1,
        "CF2_delta_join": delta2,
        "CF3_downstream": saved3,
        "CF1_est_saved_masked": saved1,
        "CF2_est_saved_masked": saved2,
        "CF3_est_saved": saved3
    })

cf_df = pd.DataFrame(cf_rows)

# 7. Limits of inference

**What cannot be identified from these timestamps alone:**

- **Causality / mechanism**: We observe that B’s start is 5–30 min after `fork_release`, but we do not know whether this is due to resource unavailability, prioritization, or preparatory sub-tasks within B. Correlation is not resource-causation.
- **Branch resource capacity & identity**: The log does not state how many technicians/machines serve A, B, or C. If A and B share a pool, reducing B queue might steal capacity from A, altering dynamics not shown.
- **Work preemption / interruption**: Timestamps are complete-event; a branch could have been interrupted and resumed, making `S_i` an overestimate of continuous active time.
- **True final-station queue vs. release policy**: `D_c = final_start  join_ready` measures elapsed wait, but we cannot distinguish (a) the case waiting because F1/F2 are busy, (b) a batching/release policy that intentionally defers start, or (c) upstream notification delays. Changing capacity may or may not reduce `D_c` if the cause is policy.
- **Branch interaction / resource contention across cases**: The table is case-level; multi-case queues at branches A/B/C are implied by start lags but not explicitly modeled. We assume independence of branch queues, which may not hold if branches share staff.
- **Pre-fork preparation variability**: `U_c = fork  arrival` varies (15–20 min). We cannot tell whether this is fixed overhead or variable upstream work.
- **Accuracy beyond one minute**: All values are minute-precise by statement; sub-minute dynamics (e.g., 09:00 vs 09:00:30) are unrecoverable.

**Defensible assumptions made:**
1. `start  fork` for all branches; queue is `start  fork`.
2. `final_start  join_ready`; `D_c` is non-negative wait, not negative.
3. Tie-break for critical branch is lexical A > B > C when ends are exactly equal (no tie occurs, but rule is explicit).
4. Branch service is continuous over the `start  end` interval; no hidden pauses.
