# 3. Consequences for performance analysis

- **G1 (genuine simultaneous batch).** If treated as 4 independent sequential tasks, waiting time is *overstated* (queue_arrival-to-start gap is real, but "service time" of 09:00–09:03 is correctly a batch-cycle time, not 4×3 min). Utilization of RBT-7 is correctly high; bottleneck detection should attribute capacity to the fixture, not the individual item — mislabeling as 4 separate services would *understate* effective throughput per cycle and could hide that true capacity is "4 items/3 min," not "1 item/3 min."

- **G2 (start batching / sequential completion).** If the shared 10:00 start is used as each item's true start, service time for the first-finishing item is overstated relative to later ones and waiting time is understated (queue_arrival10:00 gap looks short and uniform, hiding that some items sat longer before the group even began). Utilization of T-B appears continuous 10:00–10:27, but the true service pattern (serial after a shared trigger) suggests the *station*, not the *screen event*, is the bottleneck.

- **G3 (end batching).** Using 11:30 as each case's completion collapses all service times to the (start11:30) interval, which *inflates* apparent service time for early starters (E01: 28 min) and deflates it for late starters (E04: 6 min) — a pure artifact of bulk submission, not differential effort. Waiting time (queue_arrivalstart) is comparatively trustworthy since starts are distinct. Bottleneck analysis risks blaming "slow review" on E01 when the real driver is submission timing.

- **G4 (sequential, high fidelity).** This is the case where naive metrics are *least* biased: adjacency directly gives service time (4 min per item) and zero idle time between items, so utilization 100% in this window and throughput 1 item/4 min. Main residual risk is only the (unlikely but non-zero) chance that start is copied from previous complete rather than measured.

- **G5 (shared account).** Overlapping intervals under a single resource ID will make utilization *appear* > 100% relative to a single worker (impossible for one person, i.e., a data-quality red flag) or will make PM4Py batch/concurrency discovery *falsely* attribute multitasking capability to one worker, biasing resource-capacity and workload-balancing conclusions. Waiting time and service time per case are individually plausible; only the *resource attribution* layer is corrupted.

- **G6 (bulk closure).** This is the textbook case for **simultaneously inflated waiting and near-zero service**: queue_arrival spans 14:05–16:25 (up to ~3 h before close), so waiting time (arrivalstart=17:00) is large and heterogeneous — but because start=complete=17:00 exactly, computed service time is 0 for every case. A process-mining tool would report a "fast" activity with "long queues," which is a logging artifact (bulk button press), not evidence that closing is instantaneous or that the queue truly sat idle for hours (some of that queue time may include real background work never separately timestamped). Any bottleneck/SLA analysis based on this activity's "service time" will be meaningless; the waiting-time signal is directionally plausible (a backlog existed) but its magnitude is unverifiable because we don't know when real work, if any, started.

- **G7 (coarse rounding).** All service times round to a fixed 15-min block (14:0014:15) regardless of true duration, *compressing variance to zero* and making every case look identical — this will erase any real difference between cases and can make throughput look artificially uniform (5 items "in the same 15-min slot"), inflating apparent batch size and biasing cycle-time distributions toward the rounding grid. Recording lag (recorded_atcomplete) increasing by 1 minute per row is the only real signal of sequential separation and should not be confused with duration.

- **G8 (queue accumulation, capacity loss).** Naively computed waiting time (queue_arrivalstart  30–38 min) is *real* and should be attributed to the safety-check stoppage, not to worker unavailability — mislabeling it as "resource idle/slow" would incorrectly flag T-H as a bottleneck when the true cause is an upstream capacity loss. Once processing resumes, service times are trustworthy (adjacent, 1sec precision), so post-recovery throughput estimates are fine; only the pre-recovery waiting-time attribution is at risk, compounded by the clock-mismatch caveat.

# 5. Robustness and alternative explanations

**Resource ID trusted vs. shared-account:**
- G5 is the clearest case: if `analyst_pool` is trusted as one worker, the overlapping intervals imply an impossible >100%-utilized single resource and would likely be discovered by PM4Py as "concurrent batching," feeding a false conclusion that one analyst can genuinely work 4 cases at once. If treated as shared (as documented), the same intervals become ordinary concurrent work by up to 3 different people, and utilization/service-time metrics must be computed at the *pool* level, not the individual level — cycle time per case remains usable, but "analyst productivity" cannot be computed.
- G1/G4/G7/G8 resources (RBT-7, T-D, T-G, T-H) are stated as normal (non-shared) IDs; trusting them is low-risk given single-purpose automated/manual stations, but nothing in the data proves it — this is an assumption of convenience, not evidence.

**Timestamps exact vs. interval-censored by stated precision:**
- G7 (15min precision) is the extreme case: treating 14:00/14:15 as exact makes every item's duration exactly 15 min with zero variance — almost certainly false. Treating them as interval-censored (true start  [13:45,14:00) or [14:00,14:15) depending on rounding direction, true complete similarly) turns a single point estimate into a duration bound of roughly 0–30 min, which materially changes any SLA or bottleneck conclusion.
- G2/G3/G5/G6 (1min precision) have smaller but non-trivial censoring windows; e.g., G3's zero apparent variance in "time to submit" could hide up to ±30–60 s of real differences given adjacent rows recorded at :31.
- G1/G4/G8 (1sec precision) are least affected by coarsening, so their adjacency/simultaneity findings are comparatively more trustworthy *as timestamps*, even though the physical interpretation (batch vs. serial vs. queue) remains separately uncertain.

**At least three cases where the same temporal pattern supports multiple physical explanations:**
1. **G1** — identical start & complete across 4 cases is consistent with (a) genuine one-fixture simultaneous batch (favored, given context) **or** (b) a cycle-level PLC event stamped identically onto 4 sub-items regardless of any internal sequencing invisible to the log (i.e., coarse *event modeling*, not coarse *clock* resolution).
2. **G6** — start=complete=17:00 with spread queue_arrival is consistent with (a) true end-of-shift bulk data entry after real, unlogged work during the day **or** (b) genuine queue accumulation with zero work until 17:00 (capacity loss). Both produce identical zero-duration, backlog-shaped signatures; only operational validation (e.g., interviewing T-F or checking a separate work log) can distinguish them.
3. **G7** — identical rounded start/complete for 5 items is consistent with (a) true simultaneous batch measurement rounded onto the same grid, (b) true sequential measurements that happen to fall in the same 15min bucket, or (c) true concurrent multitasking likewise bucketed — the rounding destroys the distinguishing signal, and only the incidental 1minute-spaced `recorded_at` values weakly favor sequential entry.
4. (Bonus) **G2** — identical start with staggered completion is consistent with (a) start-batching + strictly sequential single-worker completion, or (b) start-batching + concurrent multitasking with independently-timed but coincidentally monotonic completions; the evenly-spaced ~6 min gaps are suggestive but not conclusive of pure serial work.

# 6. Data-collection redesign

Priority-ordered recommendations:

1. **Separate execution timestamps from logging/recording timestamps for every activity**, especially bulk-entry sources (G6) and folder-based review tools (G3): capture the actual moment of decision/finish *and* the moment of database submission as two distinct fields.
2. **Document and, where possible, eliminate timestamp rounding rules** (G7's legacy MES): record raw sub-15-min values internally even if the UI displays rounded values, and publish the rounding convention (floor/ceiling/nearest) so analysts can back-correct.
3. **Restore individual identity for shared/pooled accounts** (G5's `analyst_pool`): require badge-in per session or per case; without this, no utilization or workload-balancing claim about individuals is defensible.
4. **Synchronize all source clocks to one reference time**, explicitly for cases where two systems both timestamp the same physical station (G8's safety-check vs. queue clock): log clock-offset metadata per source, or better, route all events through one NTP-synced logger.
5. **Introduce explicit group/batch identifiers** wherever a physical batch is plausible (G1's fixture, G2's "begin group" button): a `batch_id`/`fixture_id` field removes the need to infer batching from coincident timestamps at all.
6. **Record workstation/resource capacity metadata** (e.g., "RBT-7 holds 4 items/cycle," "T-B screen supports N concurrent open items") so batch-vs-serial inference has a mechanical prior instead of relying purely on timestamp coincidence.
7. **Log pause/resume and downtime events explicitly** on the same clock as production (G8's safety stoppage, G6's possible idle backlog): an explicit `station_down`/`station_up` event pair would convert a currently ambiguous "gap" into a directly measurable, attributable downtime interval.
8. **Attach precision/accuracy metadata to every timestamp field at write time** (not just documented separately as in this dataset): a `precision` and, ideally, a `measured vs. rounded` flag per timestamp would let downstream tools automatically decide whether to interval-censor rather than requiring after-the-fact reconstruction as done here.

- **G4** — genuine sequential single-resource work; adjacency and 1sec precision make waiting/service-time estimates directly usable, modulo the residual "timestamp inheritance" caveat.
- **G3** — end-batching is well supported by explicit domain context and staggered starts; waiting time (queue_arrivalstart) is usable, but service/completion time must be treated as bulk-submission-derived, not literal.

**Should be excluded or interval-censored before any queue/service-time conclusion:**
- **G6** — zero-duration "service time" is a logging artifact; exclude this activity from service-time and bottleneck analysis entirely, and treat waiting time only as a lower bound on real backlog, not an exact value.
- **G7** — 15minute rounding destroys duration variance; either exclude from fine-grained cycle-time analysis or interval-censor every timestamp to the documented (but unverified) rounding rule before use.
- **G2** — start-batching plus 1min precision means per-item service time should be interval-censored (±30–60 s) rather than taken as exact; do not treat the shared 10:00 start as each item's individual true start.

**Require operational validation before any performance conclusion:**
- **G1** — plausible and well-supported by context, but should be confirmed with fixture/cycle documentation before asserting "4 simultaneous completions" rather than "1 cycle event logged 4×."
- **G5** — cannot be used for individual utilization/workload analysis until badge-level identity is restored or the number of concurrent analysts per session is confirmed; case-level durations may still be usable if only aggregate (pool-level) capacity is of interest.
- **G8** — the queue-accumulation narrative is plausible but rests on comparing two clocks explicitly flagged as unsynchronized; do not attribute the 15:00–15:38 gap to the safety stoppage (or to worker unavailability) until the clocks are reconciled or an independent downtime log is obtained.
