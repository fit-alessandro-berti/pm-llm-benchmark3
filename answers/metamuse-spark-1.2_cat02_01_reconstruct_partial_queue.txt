# 1. Assumptions and notation

**Notation**  
`a` = `arrival_s1` (rounded). `s1s,s1e,s2s,s2e` = reported start/end. `W1 = s1s-a` , `S1 = s1e-s1s`, `J1 = W1+S1 = s1e-a` (S1 station sojourn). `qe2 = s1e` is entry to S2 queue. `W2 = s2s - s1e`, `S2 = s2e-s2s`, `J2 = W2+S2 = s2e-s1e`. For censored intervals `S2_elapsed(t)= min(t,14:00)-s2s`. Total sojourn for complete path `J = J1+J2 = s2e-a`. For cases not yet in S2 `J` is undefined. WIP and queue lengths are interval-dependent.

**Assumptions - labelled**

* **A1 Event-order convention for simultaneous rounded times.** For count processes we apply: arrivals inclusive at `t`, completions inclusive, departures from queue on start inclusive. If `sXe = sYe = t` and `sYe_next = t`, we order `end before start` to avoid artificial negative waits and to respect FCFS and `no resource overlap`; i.e. `[e,t) ` and `[t, e')` are treated as non-overlapping. For WIP curves we state `WIP(t) = arrivals(t) - departures_S2(t)` right-continuous, counting a case that both arrives and departs at `t` as `0.5` or explicitly noted. Choice shifts L by 1.

* **A2 Rounding.** Reported `t` implies true time `t*  [t-2.5min, t+2.5min)` intersect `[08:00,14:00]`. Differences of two rounded times have ±5 min rectangular uncertainty. Sums over n activities have ±5n worst-case but ~`sqrt(n)*` smaller random. Bounds reported below include this. We do **not** de-round to a point.

* **A3 Capacity.** S1: two single-task servers I1,I2 continuously available 08:00-14:00. S2: C1 continuously, C2 unavailable `10:55-11:10` inclusive (so no service can cover that interval; 15 min capacity loss =345 min available for C2 vs 360 for others). Reported `resource` is taken as true server; undocumented help is hypothesis not fact.

* **A4 Apparent resource conflict.** If two intervals on same resource overlap after rounding, we treat as rounding / logging artefact, not as proof of extra capacity, unless overlap >5 min after de-rounding which would trigger hypothesis of assistance/missing timestamp.

* **A5 MISSING start.** Activity is known to have occurred, end and resource known, start unrecorded. Constraints: `s*  max(qe, prev_end_same_resource)` and `s*  e` and `s*  next_start_same_resource` and `S*=e-s* 0` (strictly >0 in reality). For **bounds** we allow `S*(0, e - lower_bound_on_s*]` giving maximal W interval, minimal S. For **optimistic/pessimistic** scenarios see §6. No silent single-value imputation.

* **A6 OPEN.** Activity started, not completed by 14:00. `elapsed = 14:00 - s` (rounded ±5). Final `S* > elapsed`, unknown. `W` is known if both ends known, else bounded as in A5.

* **A7 Blank S2.** Case completed S1 (or OPEN) but no S2 timestamps  waiting for S2 at 14:00. `W2_elapsed = 14:00 - s1e` is lower bound on final W2. Similarly blank S1  waiting for S1 at 14:00.

* **A8 No bypass/reneging.** FCFS is expected but not assumed for inference; out-of-order starts would be noted as anomaly.

* **A9 Little's Law validity.** `L =  W` requires (i) long-run average, (ii) stable system, (iii) W measured as time in that system, (iv) no censoring truncation bias. Only intervals with approximately stable WIP and with censoring <10% are considered defensible.

* **A10 PM4Py semantics.** `insert_case_service_waiting_time` and `insert_case_arrival_finish_rate` are **case-level** (inter-case arrival of cases to log and case sojourn from first start to last end). They are **not** station-level queue metrics and must not be read as S1 vs S2 waits.

# 2. Reconstruction method and formulas

**Waiting / service / sojourn**  
Nominal (reported) values computed directly where both timestamps present. Interval bounds:

```
W1  [ (s1s-2.5)-(a+2.5) , (s1s+2.5)-(a-2.5)] = nominal W1 ±5  if both present
S1  nominal S1 ±5
If s1s = MISSING: let Lb = max(a, prev_s1e_same_resource+) ; Ub = s1e - 
  where  = minimal plausible service (0 for absolute bound, 5-10 min for realistic,
  25-40 min for central imputation based on own resource median)
  then W1  [Lb-a , Ub-a] ±5 , S1  [s1e-Ub , s1e-Lb] ±5
W2 analog with Lb2 = max(s1e, prev_s2e_same_resource), Ub2 = s2e-
If s2s=MISSING else W2 = s2s-s1e ±5 , S2 = s2e-s2s ±5
If OPEN: S_elapsed = 14:00-s ±5, S_final  (S_elapsed , )
          W_elapsed known, W_final = W_elapsed if completed, else lower bound.
J = J1+J2; J1=s1e-a, J2=s2e-s1e; censored J lower bounded by 14:00-a.
Total sojourn for completed cases only: J = s2e-a ±5.
```

**Rates**  
`_arr(I) = N_arr(I)/|I|` , `_dep(I)= N_dep(I)/|I|` counting rounded times falling in interval (`(t1,t2]`). Arrival rate uses `a`. S1 departure rate uses `s1e`, S2 departure rate uses `s2e`. Throughput `X` is departures of that station.

**WIP / Queue length (pandas, not log-level PM4Py)**  
For each minute grid we evaluate:
```
WIP_total(t) = #{c: a  t < s2e}  (if s2e missing/open  count until 14:00)
WIP_S1q(t)   = #{c: a  t < s1s}  (if s1s missing estimate range; if blank t<14:00)
WIP_S1srv(t) = #{c: s1s  t < s1e}
WIP_S2q(t)   = #{c: s1e  t < s2s}
WIP_S2srv(t) = #{c: s2s  t < s2e}  (OPEN  till 14:00)
```
For bounds, missing `s` contributes 0 or 1 depending on scenario. Peak = max_t WIP, mean = WIP dt / |I|.

PM4Py `convert_log_to_time_intervals` returns occupancy of **log cases** as intervals `first_start..last_end`, which conflates S1+queue+S2 and ignores intermediate queue structure and censoring. Direct station-specific pandas calculation is safer for §4; we demonstrate the PM4Py call but label it case-level only.

**Utilization**  
`Busy_r =  S_r` (sum of service times on that resource, elapsed for OPEN).  
`U_r = Busy_r / Available_r` . Range from absolute bounds on missing/OPEN (0 vs full remaining) ± rounding. System utilization `U_S1 = (Busy_I1+Busy_I2)/(2*360)`, `U_S2 = (Busy_C1+Busy_C2)/(360+345)`. Completed-only utilization is lower bound; true utilization includes elapsed open work.

**Little's Law check**  
Only applied per station per interval where |WIP change| small and censoring negligible. Compute `L_bar` (time-average WIP in interval), `_bar` (arrival to that station), `W_bar` (average sojourn in that station for cases departing in interval and fully observed). Compare `L_bar` vs `_bar*W_bar` within bounds.

**Three imputation scenarios**  
*Central*: impute missing S as median service of same resource among fully observed (`I1 median 27.5, C1 40, C2 40`).  
*Optimistic* (short service / low congestion): minimal plausible service 10 min (S1) / 15 min (S2)  maximal waits, minimal busy time.  
*Pessimistic* (long service / high load): maximal feasible service given resource constraints (`e - Lb`)  minimal waits, maximal busy time. Rounding interval added on top.

# 5. Bottleneck and temporal interpretation

**Evidence vs hypothesis**

*Evidence:* S1 queue wait grows almost monotonic from 5 min to >100 min; S1 service times stable ~25-30 min; departures S1 (20 in 5h20 elapsed from first end 08:25 to last 13:45 = 320 min  3.75/h) roughly match arrivals (22 in 250 min =5.28/h early, then 4/h). Arrival > departure throughout, so S1 backlog accumulates. WIP_S1 queue peaks 6-7. Utilization S1 system ~70-75% looks not saturated but *subperiod* utilization in M and L is 83-88% with two servers — near saturation given variability and rounding; S1 clearly cannot keep up after ~09:00.

S2 queue wait also grows (5 65) and mean jumps from 9 min (E) to 35 min (M) to 55 min (L). Service times longer and more variable (40-50 min) than S1, so nominal capacity per server lower (1.5/h vs 2/h). C1 and C2 busy times similar but C2 loses 15 min. In E, S2 is lightly loaded (Q20.3). By M, queue forms.

**Interpretation: time-varying combined bottleneck, S1 dominating.**

- **08:00-09:30: Balanced / slight S1 build.** Both stations process in order, small waits (5-20). S1 slightly ahead of demand, S2 idle between jobs.
- **09:30-11:15: S1 primary bottleneck, S2 secondary but masked.** S1 backlog accelerates (waits 35-75). S2 still drains but starts to see larger inter-arrival burst from S1. Maintenance `10:55-11:10` **did not cause direct loss** (no job scheduled covering it; gap 10:50-11:15 exists). *Hypothesis:* Without outage C2 could have taken P08 ~10:55 instead of 11:15, reducing P08 wait by ~20 min and slightly lowering downstream M peak, but effect limited (<1 job). No evidence of jobs delayed *by* outage; it merely created 15 min forced idle that was already idle due to S1 starvation.
- **11:15-14:00: Dual bottleneck, S1 remains primary.** S1 queue stays 4-6. S2 queue now persistent: P08 wait 55, P10 50, P12 45, P13 50, P14 65, P15 75, P17 65. S2 arrivals in L (8-9) exceed S2 departures (5-6) even with both servers busy ~86%. So S2 would be bottleneck *if S1 flow continued*, but observed S2 backlog is *driven by upstream S1 output bunching* — cases arrive to S2 faster in L because S1 finally releases them. In a counterfactual with more S1 capacity, S2 would have been primary bottleneck sooner.

**Contrast:** If S2 were primary from start, we would expect S1 waits small and S2 queue building early with S1 servers idle — not observed. S1 idle gaps are minimal (5 min between jobs). Therefore S1 is the limiting process for system throughput over the window. Toward end, system is *bottleneck-shifting* to S2 if S1 capacity increased.

**Maintenance effect hypotheses:**
1. *Null (evidence-consistent):* Outage caused no job delay; it coincided with natural starvation.
2. *Max impact hypothesis:* If a job would have started at 10:55 on C2, delay =15 min propagated to all subsequent C2 jobs (P08, P11, P13, P15) adding up to 15 min to their waits. Upper bound on extra W2 =15, not 20-30 observed increase, so outage explains at most ~25% of S2 wait growth.
3. *Indirect:* Outage forced scheduler to keep C1 busy (P09 11:00) while C2 idle, creating imbalance that later caused P10 to use C1 (unusual) and P11 to be short.

We keep (1) as evidence, (2-3) as hypotheses.

**What is stable across scenarios?**

- **Stable:** S1 wait growth 5100, S2 wait growth 565, monotonic increase, queue lengths and WIP growth, peak WIP 9-10, S1 departures < arrivals, bottleneck S1 primary (and time-varying), C2 outage not explaining main growth, total throughput ~3.5-4/h per station, mean S1 service ~28-30 vs S2 ~38-42. Little's law mismatch over whole window (see below) remains.
- **Unstable / sensitive:** Exact mean wait for S2 (shifts 15-20 min depending on P05/P11), exact service-time mean (shifts 3-5 min), exact utilization (±5-8 points), exact W2 for P05/P11 (±15), total sojourn for P05/P07/P11 (±15-30), and latency of P15/P17/P21 final services (censored). Utilization conclusion (70% vs 78%) changes whether system appears moderately vs heavily loaded, but subperiod >80% in M/L is stable.

**Censoring sensitivity:** Excluding censored cases underestimates wait and WIP. Including them as lower bounds (elapsed) underestimates final wait by unknown but at least +15 min for waiting S2 queue, +30 min for open S1. Completes-only analysis would report mean system WIP ~4 vs true 5-6, and would hide 6 cases in backlog that represent ~2-3 hours future work.

**Rounding sensitivity:** ±5 min per difference means any single wait is uncertain by ±5, but mean over 14-20 cases is ± ~2 min (averaging). Utilization range from rounding is ±3% system-wide, smaller than imputation range. Simultaneous events ambiguity adds ±1 to WIP counts; does not change bottleneck conclusion.

**Bounds summary:** For any defensible imputation, `W1` interval for affected cases spans ~20-25 min, `S1` spans ~25 min, `W2` spans ~30 min, but aggregate trends move together.

# 2. parse status-aware timestamps (distinguish MISSING/OPEN/blank)
base = datetime(2026,5,12)
def parse(t):
    if t in ("", "MISSING", "OPEN", None):
        return pd.NaT, t  # keep flag
    return pd.Timestamp(base.replace(hour=int(t[:2]), minute=int(t[3:]))), "REPORTED"

for c in ["arrival_s1","s1_start","s1_end","s2_start","s2_end"]:

# WIP via minute grid (station-specific, safer than log-level)
grid = pd.date_range(base.replace(hour=8,minute=0), base.replace(hour=14,minute=0), freq="5T")
def wip_at(t, scenario="central"):
    # scenario handling for missing starts is simplified to central for demo
    # missing P07 s1s = 09:25, P15=11:45, P05 s2s=09:45, P11=12:00 (central)
    imputed = {"P07_s1s": base.replace(hour=9,minute=25),
               "P15_s1s": base.replace(hour=11,minute=45),
               "P05_s2s": base.replace(hour=9,minute=45),
               "P11_s2s": base.replace(hour=12,minute=0)}
    c=0
    for _,r in df.iterrows():
        a=r["arrival_s1_ts"]
        if pd.isNaT(a) or t<a: continue
        # determine s1s
        if r["case"]=="P07": s1s=imputed["P07_s1s"]
        elif r["case"]=="P15": s1s=imputed["P15_s1s"]
        else: s1s=r["s1_start_ts"]
        s1e=r["s1_end_ts"]
        s2s = r["s2_start_ts"] if r["case"] not in ["P05","P11"] else imputed[r["case"]+"_s2s"]
        s2e=r["s2_end_ts"]
        # not yet arrived to S2 system? count if t < s2e (or no s2e yet)
        if pd.isNaT(s2e) or t < s2e:
            # if t < a -> not counted already filtered; else counted as WIP_total
            # but need to exclude completed S2 (t >= s2e)
            # OPEN cases: s2e is NaT -> counted till 14:00
            if pd.isNaT(s2e) or r["s2_end_flag"]=="OPEN" or pd.isNaT(s2s):
                # waiting or open -> still in system at 14:00
                c+=1
            else:
                if t < s2e:
                    c+=1
        # also need to handle cases completed fully: t >= s2e not counted
    return c
