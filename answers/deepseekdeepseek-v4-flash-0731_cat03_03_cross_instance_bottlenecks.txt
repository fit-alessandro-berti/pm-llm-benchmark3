## 4. What flattening misses

### Job flattening

A Job flattening makes the standard release -> component -> machine -> inspect -> pack -> dispatch chain visible. It hides interactions that are not directly linked to the job object, such as batch synchronization, tool blocking, lot quarantine, and shipment consolidation. It can also duplicate the single `Batch Cure` event across J1, J2, and J3, making one batch cure look like three separate job-level activities. The misleading conclusion is that `Pack -> Dispatch` median 1.1 h is normal, while J1 actually waits 5 h 55 min between packing and S1 dispatch.

### Machine flattening

A Machine flattening makes utilization, activity sequences, and idle gaps visible. It hides why a machine is idle. For example, OVEN-1 is idle from 12:55 to 14:50, which looks like spare capacity, but B2 does not start until 14:50 because RACK-7 is cleaning/quarantined until 14:35 and J5 is not ready until 14:40. The misleading conclusion is that low machine utilization means no flow problem.

### Batch flattening

A Batch flattening makes batch cure events visible and links them to machines and tools. It hides the per-job ready times and synchronization wait. B1 appears as a single cure event at 12:05, with no indication that J1 was ready at 08:10 and waited 3 h 55 min. The misleading conclusion is that batching is efficient because the batch itself is one compact activity.

### Tool flattening

A Tool flattening makes FIX-A acquire/release, RACK-7 cleaning, and CAL-3 recalibration visible. It hides which jobs are blocked, because there is no explicit `Wait for Tool` activity. The misleading conclusion is that tools are not bottlenecks because no wait event was recorded; in fact, J4 cannot start until FIX-A is released at 11:40, despite CNC-2 being idle earlier.

### ComponentLot flattening

A ComponentLot flattening makes L7 containing C2 and C5 visible, plus quarantine and release events. It hides the inconsistent job links: the quarantine event can be related to J2 and J5 only through an alternative pipeline, while J2 bypasses the hold via supervisor override. The misleading conclusion is that L7’s quarantine equally blocks all jobs in the lot, or that the lot has no job impact because the default flattening omits it.

### Shipment flattening

A Shipment flattening makes `Create Shipment -> Load -> Dispatch` visible. It hides how long packed jobs wait for shipment partners. S1 dispatches at 19:25, which looks quick after load, but J1 was packed at 13:30. The misleading conclusion is that dispatch is fast because `Load -> Dispatch` median is 0.3 h, while the real delay happens before loading.

Low machine utilization can coexist with long job waiting because utilization measures machine occupancy, while job waiting measures the time a job spends blocked by batches, tools, lot holds, and shipment policies. Machines can be idle while jobs wait for non-machine objects.

- **Policy constraints**: B1 batches J1, J2, and J3; S1 consolidates J1 and J4.
- **Causal speculation**: If B1 had not waited for all three jobs and S1 had not waited for J4, J1 would probably have left much earlier. This is plausible but not proven, because OVEN-1 availability and dispatch schedules are not fully specified.

- **Policy constraints**: L7 is quarantined; J2 is overridden into B1 while J5 is not; CAL-3 recalibration appears to be a required policy; S3 consolidates J5 and J6.
- **Causal speculation**: The lot hold did not delay B2 on this day because release occurred before J5’s readiness. CAL-3 recalibration delayed J6 by 50 min. J2 and J5 share L7, but their actual coupling is asymmetric because of the override.

## 8. Falsification and additional data

Observations that would weaken the top-ranked batch-synchronization explanation:

1. A time-stamped event log showing OVEN-1 was occupied by another batch from 08:10 to 12:05.
2. A material-kitting log showing C1/C2/C3 were not physically staged until 11:50, so J1/J2 were not truly ready at 08:10/08:25.
3. A batch recipe specification requiring exactly three jobs and a fixed 12:05 cure window.
4. Evidence that J3 actually arrived at 08:30, and the 11:55 timestamp was a delayed data-entry event.
5. Records showing RACK-7 was unavailable until 12:05 because of cleaning, not only at 14:35.
6. Job-level status flags showing J1/J2 were still in another operation between 08:10 and 11:55, meaning “ready for batch” did not mean “ready to wait idle.”

Additional fields and event types that would discriminate among the hypotheses:

1. Explicit `WaitForBatch` events with start/end timestamps and job IDs.
2. Explicit `WaitForTool` or `ToolRequest` events.
3. Batch recipe metadata: minimum/maximum batch size, required setup time, valid cure start windows.
4. Lot status transitions with override actor, reason, and effective time.
5. Machine and tool calendar data, including cleaning and recalibration schedules.
6. Shipment route/carrier/cutoff times and the cost function for extra shipments.
7. Event qualifiers distinguishing `involved`, `blocked_by`, `uses`, and `releases`.
8. Operator-entered “ready” timestamps and job priority flags, independent of system-generated event times.
