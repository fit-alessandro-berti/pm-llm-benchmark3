## 1. Modeling assumptions

The object types are exactly `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment` (capitalized as shown). Event IDs `e01`–`e17` identify events, while business IDs identify objects. Payment amounts are event attributes in monetary units; the invoice face amount and allocation of payments between Orders are unspecified.

E2O qualifiers describe the object's role in an event: `created_order`, `receiving_order`, `added_item`, `stock_reserved_for_order`, `reserved_item`, `packed_for_order`, `packed_item`, `packed_package`, `dispatched_package`, `dispatch_delivery`, `billed_order`, `issued_invoice`, `recorded_payment`, `invoice_receiving_payment`, `confirmed_delivery`, and `closed_order`. Each event–object pair has one role here.

O2O edges are directed as `Order → Item` (`contains`), `Package → Item` (`packs`), `Delivery → Package` (`carries`), `Invoice → Order` (`bills`), and `Payment → Invoice` (`partially_settles`). Both payments use `partially_settles`: the narrative does not establish that M2 clears the invoice balance.

The E2O policy records direct involvement stated for each event. Reserve Stock involves I1, I3, O100, and O200; Pack P1 involves P1, I1, I3, O100, and O200. Pack P2 involves P2 and I2, with no inferred Order E2O link. Dispatch involves the named Package and Delivery; confirmation involves the Delivery. Invoice issuance directly involves V1 and both Orders. Payment recording involves its Payment and V1, with no direct Order or Item link. Thus logistics and financial events link to Orders only where stated; they do not automatically inherit every reachable Order or Item. The O2O graph retains the other business relationships. Any optional reachability-based expansion should be kept in a separate, provenance-labeled analytical table, rather than silently inserted into these source E2O rows.

The code assumes a PM4Py version exposing the named high-level discovery functions and accepting `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`. If its OCEL constructor signature differs, adapt the single constructor line to that version's equivalent, preserving the four tables and their semantics. It also assumes `ocel_flattening` returns a log accepted by `discover_dfg` and `discover_log_skeleton`.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL


# All timestamps are UTC. Amount is an event attribute, not an object.
event_spec = [
    ("e01", "Create Order",      "2026-04-06 08:00", None),
    ("e02", "Add Item",          "2026-04-06 08:05", None),
    ("e03", "Add Item",          "2026-04-06 08:06", None),
    ("e04", "Create Order",      "2026-04-06 08:10", None),
    ("e05", "Add Item",          "2026-04-06 08:12", None),
    ("e06", "Reserve Stock",     "2026-04-06 08:30", None),
    ("e07", "Pack Package",      "2026-04-06 09:00", None),
    ("e08", "Pack Package",      "2026-04-06 09:05", None),
    ("e09", "Dispatch Package",  "2026-04-06 10:00", None),
    ("e10", "Dispatch Package",  "2026-04-06 10:15", None),
    ("e11", "Issue Invoice",     "2026-04-06 11:00", None),
    ("e12", "Record Payment",    "2026-04-06 11:30", 100.0),
    ("e13", "Confirm Delivery",  "2026-04-06 13:00", None),
    ("e14", "Confirm Delivery",  "2026-04-07 09:00", None),
    ("e15", "Record Payment",    "2026-04-07 10:00", 150.0),
    ("e16", "Close Order",       "2026-04-07 10:30", None),
    ("e17", "Close Order",       "2026-04-07 10:35", None),
]
events = pd.DataFrame(
    [
        {
            "ocel:eid": eid,
            "ocel:activity": activity,
            "ocel:timestamp": pd.Timestamp(when, tz="UTC"),
            "payment_amount": amount,
        }
        for eid, activity, when, amount in event_spec
    ]
)

objects_by_type = {
    "Order": ["O100", "O200"],
    "Item": ["I1", "I2", "I3"],
    "Package": ["P1", "P2"],
    "Delivery": ["D1", "D2"],
    "Invoice": ["V1"],
    "Payment": ["M1", "M2"],
}
objects = pd.DataFrame(
    [(oid, object_type) for object_type, ids in objects_by_type.items()
     for oid in ids],
    columns=["ocel:oid", "ocel:type"],
)

# Only directly stated event involvement goes into this E2O specification.
# The tuples are (object ID, role of that object in the event).
e2o_spec = {
    "e01": [("O100", "created_order")],
    "e02": [("O100", "receiving_order"), ("I1", "added_item")],
    "e03": [("O100", "receiving_order"), ("I2", "added_item")],
    "e04": [("O200", "created_order")],
    "e05": [("O200", "receiving_order"), ("I3", "added_item")],
    "e06": [("O100", "stock_reserved_for_order"),
            ("O200", "stock_reserved_for_order"),
            ("I1", "reserved_item"), ("I3", "reserved_item")],
    "e07": [("P1", "packed_package"),
            ("I1", "packed_item"), ("I3", "packed_item"),
            ("O100", "packed_for_order"), ("O200", "packed_for_order")],
    "e08": [("P2", "packed_package"), ("I2", "packed_item")],
    "e09": [("P1", "dispatched_package"), ("D1", "dispatch_delivery")],
    "e10": [("P2", "dispatched_package"), ("D2", "dispatch_delivery")],
    "e11": [("V1", "issued_invoice"),
            ("O100", "billed_order"), ("O200", "billed_order")],
    "e12": [("M1", "recorded_payment"),
            ("V1", "invoice_receiving_payment")],
    "e13": [("D1", "confirmed_delivery")],
    "e14": [("D2", "confirmed_delivery")],
    "e15": [("M2", "recorded_payment"),
            ("V1", "invoice_receiving_payment")],
    "e16": [("O200", "closed_order")],
    "e17": [("O100", "closed_order")],
}

# Copy the activity and timestamp from the event table, and the type from
# the object table, so that the three OCEL tables cannot disagree silently.
event_lookup = events.set_index("ocel:eid")
object_lookup = objects.set_index("ocel:oid")
relations = pd.DataFrame(
    [
        {
            "ocel:eid": eid,
            "ocel:activity": event_lookup.at[eid, "ocel:activity"],
            "ocel:timestamp": event_lookup.at[eid, "ocel:timestamp"],
            "ocel:oid": oid,
            "ocel:type": object_lookup.at[oid, "ocel:type"],
            "ocel:qualifier": qualifier,
        }
        for eid, links in e2o_spec.items()
        for oid, qualifier in links
    ],
    columns=["ocel:eid", "ocel:activity", "ocel:timestamp",
             "ocel:oid", "ocel:type", "ocel:qualifier"],
)

# Direction: left object --qualifier--> right object.
o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"),
        ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"),
        ("P1", "I3", "packs"),
        ("P2", "I2", "packs"),
        ("D1", "P1", "carries"),
        ("D2", "P2", "carries"),
        ("V1", "O100", "bills"),
        ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"),
        ("M2", "V1", "partially_settles"),
    ],
    columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"],
)

# Structural and referential-integrity checks.
event_ids = set(events["ocel:eid"])
object_ids = set(objects["ocel:oid"])
assert len(events) == 17 and events["ocel:eid"].is_unique
assert len(objects) == 12 and objects["ocel:oid"].is_unique
assert set(e2o_spec) == event_ids
assert set(relations["ocel:eid"]) == event_ids
assert set(relations["ocel:eid"]).issubset(event_ids)
assert set(relations["ocel:oid"]).issubset(object_ids)
assert (set(o2o["ocel:oid"]) | set(o2o["ocel:oid_2"])).issubset(object_ids)
assert not relations.duplicated().any()
assert not relations.duplicated(["ocel:eid", "ocel:oid"]).any()
assert not o2o.duplicated().any()
assert not o2o["ocel:oid"].eq(o2o["ocel:oid_2"]).any()
assert events["ocel:timestamp"].dt.tz is not None
assert relations["ocel:timestamp"].dt.tz is not None

checked = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
    on="ocel:eid", suffixes=("", "_event"), validate="many_to_one"
).merge(
    objects, on="ocel:oid", suffixes=("", "_object"),
    validate="many_to_one"
)
assert checked["ocel:activity"].eq(checked["ocel:activity_event"]).all()
assert checked["ocel:timestamp"].eq(checked["ocel:timestamp_event"]).all()
assert checked["ocel:type"].eq(checked["ocel:type_object"]).all()

# If a PM4Py release has a different constructor signature, adapt this line.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)
print(ocel)
print("Activity frequencies:")
print(events["ocel:activity"].value_counts())
print("Object-type frequencies:")
print(objects["ocel:type"].value_counts())
print("OCEL object types:", pm4py.ocel_get_object_types(ocel))
print("Activities by object type:", pm4py.ocel_object_type_activities(ocel))

flattened = {}
dfgs = {}
skeletons = {}
for object_type in ("Order", "Package", "Delivery", "Invoice"):
    flattened[object_type] = pm4py.ocel_flattening(ocel, object_type)
    dfgs[object_type] = pm4py.discover_dfg(flattened[object_type])
    skeletons[object_type] = pm4py.discover_log_skeleton(
        flattened[object_type]
    )

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Optional visual inspection, where the installed PM4Py release exposes
# these convenience viewers:
# pm4py.view_ocdfg(ocdfg)
# pm4py.view_ocpn(ocpn)
```

The 17 events yield 34 E2O rows and 12 O2O rows. Event `e06` is one reservation shared by two Items and two Orders, and `e07` is one packing event shared by P1, I1, I3, O100, and O200. They create cross-order convergence. Event `e11` converges the two Orders on V1; `e12` and `e15` then diverge into distinct Payment objects attached to that same Invoice. Treating any of these shared events as separate physical occurrences would change the story.

## 4. Expected flattened behavior

| Case object | Approximate traces | Copied shared events, omissions, and likely DFG edges |
|---|---|---|
| Order | O100: Create → Add I1 → Add I2 → Reserve → Pack P1 → Issue Invoice → Close. O200: Create → Add I3 → Reserve → Pack P1 → Issue Invoice → Close. | `e06`, `e07`, and `e11` occur once in each Order trace: each is still only one OCEL event. Likely edges include Create→Add, Add→Add (O100), Add→Reserve, Reserve→Pack, Pack→Issue, Issue→Close. Pack P2, both dispatches, both confirmations, and both payments are absent because they lack direct Order E2O links. The Issue→Close edge can misleadingly suggest nothing relevant happened between billing and closure. |
| Package | P1 and P2 each have Pack → Dispatch. | Likely DFG edge: Pack→Dispatch. P1's Pack event is shared with two Orders and two Items but appears once in the P1 case; no Package event is copied between the P1 and P2 cases. Confirm Delivery and invoice/payment activity disappear. The identical two-step traces conceal that P1 spans two Orders while P2 does not. |
| Delivery | D1 and D2 each have Dispatch → Confirm. | Likely DFG edge: Dispatch→Confirm. Each dispatch event is also seen in its Package view, but no event is shared between the two Delivery cases. Packing, Order, and financial histories disappear. The traces alone cannot show which Items or Orders were delivered. |
| Invoice | V1 has Issue → Record M1 → Record M2. | Likely edges: Issue Invoice→Record Payment and Record Payment→Record Payment (a repeated activity, not the same payment event). `e11` also appears in both Order traces; `e12` and `e15` each appear in their Payment object's view. Logistics, Order closure, and the per-Order allocation of 100 and 150 are absent. One Invoice case gives especially weak evidence for general log-skeleton constraints. |

Flattening on Payment would produce one `Record Payment` event for M1 and one for M2. There is no within-Payment transition to discover, and the Invoice-level sequence and shared V1 are lost. DFGs and skeletons from these one-event cases would be nearly uninformative.

## 5. Expected object-centric structures

The OC-DFG retains object-type-specific succession: Items show Add→Reserve→Pack for I1 and I3, while I2 shows Add→Pack; Packages show Pack→Dispatch; Deliveries show Dispatch→Confirm; Invoice V1 shows Issue→Record→Record. The Order projection has Reserve→Pack→Issue for both O100 and O200. These are different directly-following relations over one event set, so `e07` remains one P1 packing operation even when it participates in both Order paths. A discovered edge is succession in a chosen object perspective, not proof of a physical handoff or payment allocation.

The OTG should expose the type-level connectivity supported by direct E2O co-occurrence: Order–Item at adding/reserving/packing, Order–Package and Item–Package at packing, Package–Delivery at dispatch, Order–Invoice at issue, and Invoice–Payment at recording. The O2O edges additionally explain that P1 packs I1 from O100 and I3 from O200, and that V1 bills both Orders. No direct Delivery–Order or Payment–Order event link was asserted; a graph implementation that includes O2O or derived reachability may display additional paths, which must be labeled by their source.

The ET–OT graph should match the activity/type audit table: for example, `Pack Package` touches Package, Item, and (via P1) Order; `Record Payment` touches Payment and Invoice; `Confirm Delivery` touches Delivery only. It summarizes involvement, not event order or cardinality.

An object-centric Petri net may show synchronization around the shared reservation of I1/I3 and O100/O200, the P1 packing, and V1's issue for both Orders. It may show two payment occurrences along V1's flow, with M1 and M2 as distinct objects. Its mined places, arcs, and token interpretation depend on algorithm settings and this tiny log; no uniquely determined net, invoice-balance rule, or cross-order payment allocation follows from the data.

An object-interactions summary based on shared events should associate O100 and O200 through `e06`, `e07`, and `e11`; P1 with I1, I3, and both Orders through `e07`; V1 with both Orders through `e11`; and V1 separately with M1 and M2 through `e12` and `e15`. M1 and M2 do not share an event with each other. Depending on the PM4Py summary's definition, explicit O2O edges may be reported separately from event co-occurrences. In particular, an inferred O100–M1 path through V1 is not a direct interaction event.

## 6. Modeling alternatives

| E2O policy | Defensible change and analytical effect |
|---|---|
| Source-minimal, as implemented | Link only participants explicitly given for each event. Order traces omit P2 packing, dispatch, confirmation, and payment; those facts remain traversable through O2O. This keeps event co-occurrence close to the stated observations. |
| Full operational involvement | Directly link P2 packing to O100, and link dispatch and confirmation to the Orders and Items implicated by each Package/Delivery; one could also link payment events to both billed Orders if the business process records that involvement. Order and Item traces become longer, and the OTG/interactions summary becomes denser. These links need a declared operational rule, since they are not all directly stated event associations. |
| O2O-propagated analytical relations | Preserve the source `relations`, then create a separate derived table by traversing `contains`, `packs`, `carries`, `bills`, and `partially_settles` with explicit path, rule, and provenance columns. Discovery on that derived view makes Order traces include downstream logistics and finance, but can multiply associations and turn indirect reachability into apparent synchronizations if provenance is ignored. |
| Strict actor-only events | Attach an event to only its primary object (for example, payment to M1/M2 and dispatch to D1/D2), relying on O2O for the rest. This is compact but erases direct joint participation: Order flattening would lose the shared reservation, P1 pack, and invoice issue unless those are explicitly retained as exceptions. |

These policies change E2O projections and therefore discovery results, while the same 17 occurrences and 12 business objects can still describe the same underlying process. The chosen policy must accompany any reported DFG or net.

## 7. Failure modes

1. **Relation inflation:** attaching every reachable Order and Item to each downstream event makes an inferred association look like direct participation and creates dense, potentially spurious DFG/OTG structure.
2. **Missing direct E2O links:** omitting O100 or O200 from `e06`, `e07`, or `e11` loses explicitly shared operational events in Order traces.
3. **Propagation mistaken for observation:** adding O2O-reached links to the source `relations` without provenance prevents a reviewer from separating stated facts from analytical inference.
4. **Duplicate shared events after flattening:** counting each copy of `e06`, `e07`, or `e11` as a new physical event overstates work and can corrupt duration or frequency calculations.
5. **Ambiguous payment allocation:** V1 bills two Orders, while M1=100 and M2=150 settle V1; neither amount is assigned to an individual Order, nor is V1's face amount supplied.
6. **Overly short Payment traces:** M1 and M2 each have one event, so a Payment DFG or skeleton cannot recover the two-installment Invoice lifecycle.
7. **Constructor/API version mismatch:** PM4Py releases may differ in OCEL constructor arguments or convenience function availability. Change the adapter/API call for that installation, not the event/object semantics.
8. **False total order for same-time events:** sorting tied timestamps by event ID would invent causality. This dataset has no timestamp ties, but a reusable pipeline should retain concurrency or use a justified tie-breaker when ties arise.
9. **Wrong O2O direction or qualifier:** reversing `V1 → O100` or saying M2 `completes_settlement` without balance evidence changes the meaning of the graph.
10. **Broken denormalized relation fields:** manually retyping an activity, timestamp, or object type into E2O can disagree with its event/object row; the construction and checks prevent this.
11. **Assuming absent links mean absent business actions:** the missing Order E2O link on `e08` does not mean O100's I2 was never packed; P2→I2 and O100→I2 establish that business relationship.

## 8. Final semantic checks

1. There are exactly 17 distinct event IDs, in the stated UTC time order, and exactly the 12 named objects with the six capitalized types.
2. O100 contains I1 and I2; O200 contains I3; P1 packs I1 and I3, crossing the two Orders; P2 packs I2.
3. `e06` is a *single* Reserve Stock event related to I1, I3, O100, and O200, and it has no relation to I2.
4. `e07` is a *single* Pack Package event related to P1, I1, I3, O100, and O200; `e08` relates to P2 and I2. The O100–P2 association is available through O2O, not fabricated as a direct `e08` E2O row.
5. D1 carries P1 and D2 carries P2. `e09` relates to D1/P1, `e10` to D2/P2, and confirmations `e13`/`e14` relate to D1/D2 respectively.
6. V1 bills both O100 and O200, and the one issuance event `e11` relates to V1 and both Orders.
7. `e12` relates M1 to V1 and has `payment_amount == 100.0`; `e15` relates M2 to V1 and has `payment_amount == 150.0`. Both Payment→Invoice O2O edges say `partially_settles`.
8. O200 closes at `e16` (10:30 UTC) and O100 at `e17` (10:35 UTC) on 2026-04-07; payment allocation and final invoice balance remain unspecified.
9. Every relation references existing event and object IDs, repeats that event's activity and timestamp and that object's type, and no event–object pair appears twice.
