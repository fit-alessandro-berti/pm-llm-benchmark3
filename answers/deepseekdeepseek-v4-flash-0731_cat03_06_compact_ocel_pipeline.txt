## 1. Modeling assumptions

- **Object types and capitalization**: The object types are exactly as described: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. Capitalization is preserved.
- **E2O qualifier vocabulary**: We use the following qualifiers, each describing the role of the object in the event:
  - `created` – for a `Create Order` event acting on an `Order`.
  - `added` – for an `Add Item` event acting on an `Order` or an `Item`.
  - `reserved` – for a `Reserve Stock` event acting on an `Order` or an `Item`.
  - `packed` – for a `Pack Package` event acting on a `Package`, an `Item`, or an `Order`.
  - `dispatched` – for a `Dispatch Package` event acting on a `Package` or a `Delivery`.
  - `issued` – for an `Issue Invoice` event acting on an `Invoice` or an `Order`.
  - `paid` – for a `Record Payment` event acting on a `Payment` or an `Invoice`.
  - `confirmed` – for a `Confirm Delivery` event acting on a `Delivery`.
  - `closed` – for a `Close Order` event acting on an `Order`.
- **O2O direction conventions**: All O2O relations are directed from the source object to the target object, with the qualifier expressing the relationship. For example, `Order contains Item` is represented as `(Order, Item, "contains")`. `Payment` to `Invoice` uses `"partially_settles"` or `"completes_settlement"` depending on whether the payment fully settles the invoice.
- **Direct vs. propagated relations**: Only **source-system facts** are represented as E2O relations. That is, an event is linked to an object only if the event description explicitly mentions that object. For example, `Confirm Delivery D1` is linked only to `D1`, not to `P1` or any `Order`. Similarly, `Record Payment M1` is linked only to `M1` and `V1`, not to `O100`/`O200`. This avoids mixing analytical propagation with observed facts. The O2O relations provide the analytical connectivity, but they are not used to create additional E2O rows.
- **Prevention of confusion**: We do **not** add E2O rows that are derived from O2O relationships. The O2O table is kept separate and is used only for objectinteraction analysis and optional propagation by the analyst. The `relations` table contains only direct observations.
- **Version-dependent PM4Py assumption**: The constructor `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is assumed to be available. In some PM4Py versions, the import path might be `from pm4py.objects.ocel.ocel import OCEL`; if that fails, one can use `from pm4py.objects.ocel.ocel import OCEL` as fallback. The data semantics are unchanged.

## 4. Expected flattened behavior

- **Order flattening**: For `O100`, trace  `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Dispatch Package  Dispatch Package  Issue Invoice  Record Payment  Confirm Delivery  Record Payment  Close Order`. For `O200`, trace  `Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Record Payment  Confirm Delivery  Record Payment  Close Order`. The shared events `Reserve Stock`, `Pack Package` (for P1), `Issue Invoice`, `Record Payment` (both), and `Confirm Delivery` (for D1) appear **in both traces** because they are directly related to both orders. This duplication is expected but can distort metrics like waiting times if not handled carefully.
- **Package flattening**: For `P1`, trace  `Pack Package  Dispatch Package  Confirm Delivery`. For `P2`, trace  `Pack Package  Dispatch Package  Confirm Delivery`. The `Pack Package` event for P1 also relates to items and orders, but flattening to Package only includes events that directly touch the package. Thus `Reserve Stock` and `Issue Invoice` are omitted, losing the link to the order lifecycle.
- **Delivery flattening**: For `D1`, trace  `Dispatch Package  Confirm Delivery`. For `D2`, trace  `Dispatch Package  Confirm Delivery`. The `Pack Package` event is omitted because it is not directly linked to the delivery; only the dispatch is. This hides the preparation step.
- **Invoice flattening**: For `V1`, trace  `Issue Invoice  Record Payment  Record Payment`. The `Record Payment` events appear twice (once for each payment). The `Close Order` events are omitted because they are not directly related to the invoice. This trace is very short and does not show the order fulfillment that led to the invoice.
- **Payment flattening**: Flattening on `Payment` yields two traces of length 1 (`Record Payment` for M1 and M2). This is extremely weak because there is no context about the invoice, orders, or deliveries. It gives no insight into the process beyond the payment events themselves.

## 5. Expected object-centric structures

- **OC-DFG**: The graph will show activities as nodes and edges representing the temporal order of activities that share at least one object. Example edges: `Create Order  Add Item`, `Add Item  Reserve Stock`, `Reserve Stock  Pack Package`, `Pack Package  Dispatch Package`, `Dispatch Package  Confirm Delivery`, `Issue Invoice  Record Payment`, `Record Payment  Close Order`. The edge `Reserve Stock  Pack Package` will be seen for both orders and items, and `Pack Package  Dispatch Package` for both packages and items. The presence of `P1` and `P2` creates parallel paths, while `V1` and the two payments create a separate financial subprocess.
- **OTG**: The objecttype graph will show relationships between object types based on their cooccurrence in events. It will connect `Order`–`Item`, `Order`–`Package`, `Item`–`Package`, `Package`–`Delivery`, `Invoice`–`Order`, `Payment`–`Invoice`. The node `Order` will have high degree because it participates in many activities.
- **ET–OT**: The eventtypeobjecttype graph will show for each activity which object types it touches. It will visually highlight that `Reserve Stock` and `Pack Package` touch multiple object types, while `Confirm Delivery` touches only `Delivery`. This helps identify activities that are true objectcentric synchronisation points.
- **Object-centric Petri net**: The discovered net will likely consist of a single process with multiple places for `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment` tokens. The transitions will be the activities. The net will show that tokens for `O100` and `O200` flow through `Reserve Stock` and `Pack Package` (P1) together, while `P2` carries only `O100`’s item. The `Invoice` and `Payments` form a separate but connected subnet. The net is not uniquely determined; multiple Petri nets can explain the same behaviour.
- **Object-interactions summary**: This will show the number of times pairs of objects cooccur in events. For example, `O100` and `I1` appear together in `Add Item`, `Reserve Stock`, and `Pack Package`; `O200` and `I3` appear in `Reserve Stock` and `Pack Package`; `V1` and `O100`/`O200` appear in `Issue Invoice`; `M1` and `M2` appear with `V1` in `Record Payment`. The summary will highlight that `P1` connects `O100` and `O200` through the items `I1` and `I3`.

## 6. Modeling alternatives

- **Sourceminimal relations** (chosen): only objects explicitly mentioned in the event description are linked. This keeps the data clean but may underrepresent the analytical reach of events (e.g., `Confirm Delivery` does not link to `Package` or `Order`).
- **Full operational involvement**: every event that is operationally relevant to an object is linked, even if not explicitly named. For example, `Confirm Delivery D1` would also link to `P1` and both `O100`/`O200` because the delivery carries their package. This enriches the flattening but risks duplicating events and may introduce bias if the source system does not record those links.
- **O2Opropagated analytical relations**: add E2O rows for every object that is reachable via O2O at the time of the event. For instance, `Confirm Delivery D1` would link to `O100` and `O200` because `D1` carries `P1` which contains items from both orders. This makes the objectcentric log more complete but creates a large number of artificial relations that are not directly observed, potentially distorting discovery.

## 7. Failure modes

- **Relation inflation**: Adding too many E2O rows (e.g., propagating all O2O relations) makes the log dense and may cause activities to appear in traces they were never part of, distorting DFG and Petri net discovery.
- **Missing direct E2O links**: If we omit `Reserve Stock` from `O200` (because it is not explicitly mentioned), the order trace for `O200` would miss a critical step, breaking the intended process.
- **Treating O2O propagation as observation**: Using O2O to infer E2O relations without a clear policy can mix facts with analysis, leading to false confidence in discovered models.
- **Duplicate shared events after flattening**: When flattening to `Order`, the same `Reserve Stock` event appears in both `O100` and `O200` traces. If not handled, the flattened log may contain duplicate events that are not truly independent observations.
- **Ambiguous payment allocation**: The two payments `M1` and `M2` are both linked to `V1`, but the amounts are different. Without a clear allocation rule, the invoice may be considered settled only after `M2`. If the model treats each payment as an independent event, it may miss the settlement condition.
- **Overly short Payment traces**: Flattening on `Payment` yields traces of length 1, which are too short for meaningful process discovery (e.g., DFG or skeleton).
- **Constructor/API version mismatch**: The `OCEL` class may not accept `o2o` in some PM4Py versions, or the import path may differ. This would cause the code to fail even though the data is correct.
- **False total order for same-time events**: Although this example has no timestamp ties, a real dataset could have events with identical timestamps. Without a tiebreaking rule, the ordering of such events is arbitrary, affecting any discovered ordering relations.
