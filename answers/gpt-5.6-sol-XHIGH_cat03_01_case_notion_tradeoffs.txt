## 1. Analytical assumptions

- **Case notion.** Flattening on type \(T\) creates one case per object of type \(T\). A case contains only events directly related to that object in the supplied E2O relations, ordered by timestamp and then event ID. I do not treat O2O reachability as an implicit E2O relation.
- **Convergence.** An event converges multiple objects of the selected type when it is directly related to more than one of them and is therefore copied across cases. Examples are e16 in the Order flattening, where one dispatch appears in O1, O2, and O3, and e16 in the Package flattening, where it appears in P2 and P3.
- **Divergence.** One selected object diverges into multiple operational branches or related objects, causing repeated activities and serializing work that may actually concern separate branches. O1, for example, receives two Pack Package, Dispatch, and Confirm Delivery occurrences because it is split over P1 and P2.
- **Copied events are both evidence and duplication.** The copy of e16 in three order cases is valid evidence that three orders were affected. It is not evidence that three dispatch executions occurred. Thus case-incidence frequency and execution frequency must be reported separately.
- **Permitted transformations.** The direct-E2O log is the baseline. I would permit:
  1. event-ID deduplication or weights of \(1/k\), where \(k\) is the number of selected objects related to an event, for execution-oriented statistics;
  2. bounded, typed O2O propagation as an explicitly labelled alternative, retaining the propagation path and direct/inferred flag;
  3. enrichment with O2O qualifiers, especially `partially_settles` and `completes_settlement`;
  4. grouping copied rows by original event ID for equivalent-execution analysis.

Unrestricted propagation is inappropriate: propagating every V2 event to both M2 and M3, for example, could make e22 appear in the future M3 lifecycle merely because both payments relate to V2.

## 3. Concrete distortion analysis

1. **Order flattening — split O1 creates false serial dependence.**  
   O1 contains e11/e12, e15/e16, and e23/e24 for P1 and P2. Its DFG includes Pack PackagePack Package, DispatchDispatch, and Confirm DeliveryConfirm Delivery. These edges serialize separate package branches rather than demonstrating rework. They are harmful for control-flow interpretation but informative that O1 required two fulfilment branches.

2. **Order flattening — cross-order package P3 inflates execution counts.**  
   E13 is copied to O2 and O3 because P3 packs I21 and I31. One physical Pack Package execution therefore contributes two case occurrences and two surrounding order-level paths. This is valid order-impact evidence, but harmful if Pack Package frequency is interpreted as warehouse workload.

3. **Order flattening — cross-order package P4 compounds convergence and divergence.**  
   E14, e17, and e27 appear in both O3 and O4 because P4 contains I32 and I41. For O3 these follow its earlier P3/D2 branch, creating another Pack Package and Dispatch; for O4 they are its only logistics branch. The resulting O3 variant looks substantially more complex even though part of that complexity is shared with O4. This is context-dependent: useful for order complexity, misleading for execution counts.

4. **Package flattening — cross-order composition becomes invisible.**  
   P3 and P4 have the same PackDispatchConfirm variant as single-order P1 and P2. The activity sequence alone does not reveal that P3 spans O2/O3 or P4 spans O3/O4. This is harmful when studying consolidation policy, although it is harmless for a narrow package-stage conformance check.

5. **Item flattening — apparent perfect standardization masks consolidation.**  
   All six items follow Add ItemPack PackageDispatchConfirm Delivery. E13 is copied across I21/I31, e14 across I32/I41, and e16/e24 across I12/I21/I31. Consequently the DFG reports six item transitions through each stage, despite only four packing events and three delivery executions. The regularity is informative for item exposure but harmful as an operational execution model.

6. **Package and Item flattenings — consolidated delivery D2 is overweighted.**  
   The e16e24 interval is represented in P2 and P3 package cases and in I12, I21, and I31 item cases. Thus one 4-hour-55-minute delivery interval receives weight two or three, respectively. Delivery flattening represents it once as D2. The difference is not an error if the estimand is packages or items delivered, but it biases carrier execution performance.

7. **Order flattening — consolidated invoice V2 is copied as if order-specific.**  
   E19, e22, and e25 each occur in both O2 and O3. An order-level frequency report therefore contains two Issue Invoice incidences and four Record Payment incidences for one invoice and two payment executions. This is informative about the two affected orders but harmful for invoice and payment workload measurement.

8. **Invoice versus Order flattening — instalment structure changes with interleaving.**  
   In V2, e19e22e25 yields Record PaymentRecord Payment. In O2 and O3, e24 occurs between e22 and e25, so the direct payment self-loop disappears and becomes Record PaymentConfirm DeliveryRecord Payment. Neither DFG alone captures the full semantics: the invoice view emphasizes instalments, while the order view emphasizes temporal interleaving.

9. **Payment flattening — partial settlement is fragmented into singletons.**  
   M2 contains only e22 and M3 only e25. The 20-hour-20-minute interval between the two V2 payments is lost, as is their order as instalments. Conversely, Invoice flattening preserves the sequence but needs the O2O qualifiers `partially_settles` and `completes_settlement` to avoid labelling the second payment as rework. The payment flattening is harmful for settlement-process analysis but useful as an atomic audit population.

10. **Delivery flattening — near-singleton lifecycle invites overclaiming.**  
    D1–D3 contain only Dispatch and Confirm Delivery. The DFG’s sole edge is operationally meaningful, but a short and highly conforming model does not establish end-to-end process simplicity. It excludes e11–e14 packing, e18–e26 finance, and e28–e31 closure. This is safe for delivery SLA measurement and harmful if generalized to fulfilment.

11. **Strict direct-E2O flattening causes legitimate scope truncation.**  
    Item cases begin at Add Item rather than e01–e04 and end at delivery rather than e28–e31. Package and Delivery cases begin even later; Invoice cases omit all logistics. These are not missing data under the stated E2O semantics. They become a trap only if analysts silently describe the resulting durations as total order lead time.

## 4. Traditional versus object-centric analysis portfolio

I would create all six flattened logs as **diagnostic projections**, but not treat them as interchangeable:

- **Order:** per-order exposure, create-to-close lead time, and the number of logistical or financial touchpoints affecting each order. Shared-event counts must be labelled as order incidences.
- **Item:** item-stage conformance and item-level waiting times from Add Item to delivery.
- **Package:** pack-to-delivery handling and package impact of delivery consolidation.
- **Delivery:** carrier dispatch-to-confirmation durations, with D2 counted once.
- **Invoice:** issue-to-first-payment and issue-to-complete-settlement performance, after adding settlement qualifiers.
- **Payment:** record completeness and timestamp/attribute auditing, not DFG-based process discovery.

An **OC-DFG** is required to compare execution frequency with object impact without forcing one denominator. The **ET–OT graph** should verify direct scope—for example, Create/Close relate only to Order, while Record Payment relates to Order, Invoice, and Payment. The **OTG** shows that the process has several coupled object-type lifecycles rather than a simple hierarchy. An **object interaction summary** is needed to expose concrete structures such as D2–P2/P3–O1/O2/O3 and V2–O2/O3–M2/M3.

Equivalent-execution clustering can identify repeated item or package execution patterns, such as the common item activity sequence, but should be run separately by candidate object type. A global cluster would risk equating business-distinct units merely because their activity labels match.

Contradictory results should be reconciled by stating the denominator. “Dispatch occurred three times” is an event-execution statement about e15–e17; “six order-dispatch incidences” counts O1 once at e15, O1/O2/O3 at e16, and O3/O4 at e17. Both are valid. Original event IDs, object identities, and qualifiers should be retained so that every flattened statistic can be mapped back to its object-centric explanation.

## 5. Lead-object decision

**C. Reject a single lead object for this process.**

**Decision criteria**

1. Coverage of commercial, logistics, financial, and closure stages.
2. Stability of the selected unit across splits and consolidations.
3. Ability to distinguish execution counts from affected-object counts.
4. Meaningful lifecycle duration and DFG semantics.
5. Preservation of actionable units such as deliveries and invoices.

**Strongest supporting evidence**

No object type satisfies all five criteria. Order has broad direct coverage, but O1 splits across P1/P2, O3 spans P3/P4, D2 combines three orders, and V2 combines two orders and two instalments. Package, Delivery, and Invoice are more stable execution units within their domains, but their lifecycles are deliberately truncated. Payment is a singleton rather than a process case.

The many-to-many structures are also orthogonal: choosing Order does not resolve delivery consolidation, while choosing Delivery does not resolve consolidated invoicing. One lead would privilege a particular stakeholder’s denominator rather than recover a neutral end-to-end unit.

**Strongest counterargument**

Order is the only type directly related to every activity family and the only one with explicit creation and closure. If “end-to-end” means customer-order accountability, an Order projection is highly defensible: copying e16 into O1/O2/O3 correctly records that all three orders were affected.

**Residual risk**

Rejecting one lead object makes conformance reporting and ownership more complex. Stakeholders may still demand one variant count or one SLA denominator, and a portfolio can produce apparently contradictory frequencies unless metric semantics are governed carefully.

**Conditions for changing the decision**

I would adopt Order as a primary lead if the process owner explicitly defined the contractual unit as an order, shared-operation costs were allocated to orders, and all frequencies were labelled as order impacts rather than executions. For a carrier-only scope I would select Delivery; for receivables I would select Invoice with settlement qualifiers. Those would be scoped analyses, not a universal end-to-end lead.

## 6. PM4Py analysis outline

```python
import pandas as pd
import pm4py

# The OCEL is assumed to have already been loaded.
print(ocel)

EVENT_ID = "ocel:eid"
ACTIVITY = "ocel:activity"
OBJECT_ID = "ocel:oid"
OBJECT_TYPE = "ocel:type"

events_df = ocel.events.copy()
objects_df = ocel.objects.copy()
relations_df = ocel.relations.copy()

# Execution frequencies: one row per original event.
activity_frequencies = (
    events_df[ACTIVITY]
    .value_counts(dropna=False)
    .rename_axis("activity")
    .rename("unique_event_frequency")
)
print(activity_frequencies)

# Inventory frequencies: one row per object.
object_type_frequencies = (
    objects_df[OBJECT_TYPE]
    .value_counts(dropna=False)
    .rename_axis("object_type")
    .rename("object_count")
)
print(object_type_frequencies)

# Direct E2O incidence profile. "relation_rows" exposes how flattening can
# create more case-event incidences than unique original events.
relation_profile = (
    relations_df.groupby(OBJECT_TYPE)
    .agg(
        relation_rows=(EVENT_ID, "size"),
        unique_related_events=(EVENT_ID, "nunique"),
        unique_objects=(OBJECT_ID, "nunique"),
    )
    .sort_index()
)
relation_profile["copies_above_unique_events"] = (
    relation_profile["relation_rows"] -
    relation_profile["unique_related_events"]
)
print(relation_profile)

# Activity-by-object-type incidence, explicitly based on direct E2O.
relation_activity_df = relations_df[
    [EVENT_ID, OBJECT_ID, OBJECT_TYPE]
].merge(
    events_df[[EVENT_ID, ACTIVITY]],
    on=EVENT_ID,
    how="left",
    validate="many_to_one",
)
activity_object_type_incidences = pd.crosstab(
    relation_activity_df[ACTIVITY],
    relation_activity_df[OBJECT_TYPE],
)
print(activity_object_type_incidences)

candidate_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

flattened_logs = {}
flattened_dfg_results = {}
flattened_log_skeletons = {}

for object_type in candidate_types:
    flattened_log = pm4py.ocel_flattening(ocel, object_type)
    flattened_logs[object_type] = flattened_log

    # These models are projections. Their frequencies must later be
    # interpreted as incidences of the selected object type.
    flattened_dfg_results[object_type] = pm4py.discover_dfg(flattened_log)
    flattened_log_skeletons[object_type] = (
        pm4py.discover_log_skeleton(flattened_log)
    )

# Object-centric structures retain the multiple object-type perspectives.
ocdfg_model = pm4py.discover_ocdfg(ocel)
object_type_graph = pm4py.discover_otg(ocel)
event_type_object_type_graph = pm4py.discover_etot(ocel)
object_interaction_summary = (
    pm4py.ocel_objects_interactions_summary(ocel)
)

print("OC-DFG discovered:", type(ocdfg_model))
print("OTG discovered:", type(object_type_graph))
print("ET-OT graph discovered:", type(event_type_object_type_graph))
print(object_interaction_summary)

# No pm4py.cluster_equivalent_ocel call is made here because the decision
# rejects a single lead type. Clustering should only be run after selecting
# an explicit type-specific question and validating its equivalence criteria.

analysis_semantics = {
    "execution_frequency": "count distinct original event IDs",
    "object_impact_frequency": "count direct E2O incidences by object type",
    "propagation": "disabled in this baseline",
    "interpretation_note":
        "Models do not by themselves determine the appropriate business unit.",
}
print(analysis_semantics)
```

## 7. Sensitivity and validation plan

1. **Copied-event weighting.** Recompute flattened DFG frequencies using ordinary case incidences, one representative per original event ID, and weights \(1/k\) for an event copied to \(k\) selected objects. In the Order log, e16 and e24 would have total execution weight one rather than three. Compare both frequency rankings and performance averages; do not remove copies from per-order impact reporting.

2. **Direct versus propagated relations.** Maintain the supplied direct-E2O OCEL as the baseline and create a separately named, provenance-preserving propagated variant. Test bounded paths such as ItemOrder for creation/closure context and PaymentInvoice for invoice issuance. Validate that propagation does not incorrectly make e22 part of M3 merely because M3 and M2 both settle V2.

3. **Change the candidate lead.** Compare Order create-to-close results with Item fulfilment, Delivery SLA, and Invoice settlement results. In particular, compare D2’s e16e24 duration when counted for three orders, three items, two packages, and one delivery. A conclusion that reverses solely because the denominator changed must be reported as scope-dependent.

4. **OC-DFG frequency semantics.** Compare event frequency, unique-object frequency, and total-object frequency. For Dispatch, event frequency is three—e15, e16, e17—while Order unique-object frequency is four and total Order incidences are six because O1 and O3 appear in two dispatches. Package total incidence is four and Delivery incidence is three. These measures answer different questions and should not be substituted for one another.

5. **Payment-completion definition.** For V2, compare issue-to-first-payment using e19e22 with issue-to-complete-settlement using e19e25. Enrich the latter with the `partially_settles` and `completes_settlement` qualifiers. Check whether any performance conclusion changes when repeated Record Payment is treated as planned instalment rather than rework.

6. **Interaction-preservation validation.** For every flattened variant or discovered cluster, map representative cases back to original event IDs and interaction structures. Required checks include P3 linking O2/O3, P4 linking O3/O4, D2 linking P2/P3 and three orders, and V2 linking O2/O3 and M2/M3. Any projection that cannot recover these structures should not support consolidation-related conclusions.
