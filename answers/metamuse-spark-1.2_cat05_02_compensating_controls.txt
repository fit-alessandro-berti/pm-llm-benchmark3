## 1. Control-Objective Decomposition

FEP-1 is not a syntactic rule about different user IDs. Its objective is to ensure no single compromised, mistaken, or dishonest actor can unilaterally cause irrevocable outflow. Decomposed:

**O1 - Single-actor initiation + authorization fraud/error**
*Threat:* One person creates a fictitious invoice, inflates amount, or substitutes payee and then authorizes it. System or colluding manager is bypassed.
*Requires:* Independent human authorization before funds leave control. 
*AV-2:* **Cannot prevent** - only checks data patterns, not who controls account or intent, does not detect collusion. Can block duplicates/limits but overrideable. *Fails to address* core if overridden.
*MG-4:* **Prevents if before release/settlement and independent**; **Detects if after release but before settlement** (hybrid). Fails if rubber-stamp, conflicted, or after irrevocable settlement.
*RA-7:* **Detective only**; **Corrective only within ~24h recall window**, otherwise no correction. Fails to prevent loss.
*ED-1:* Permission structure, not a control itself; makes O1 tolerable only if all 7 conditions substitute independence with constrained risk.

**O2 - Duplicate / erroneous payment and operator-limit breach**
*Threat:* Mistaken resubmission, fat-finger amount, operator exceeds delegated authority.
*AV-2:* **Preventive** (block) or **Preventive-warning** (overrideable). Strong coverage for duplicates, limits, PO match. Clean pass is strong evidence *only* for those checks.
*MG-4:* **Preventive/detective** if manager reviews amount vs. limit and duplicate status. Weak if no review.
*RA-7:* **Detective**, correctable if before settlement/recall.
*ED-1:* Requires AV-2 fully operational and passed without override + amount <100k + no override. Directly addresses O2.

**O3 - Bank-account hijack / business-email compromise / sanctions breach**
*Threat:* Vendor master data changed, funds diverted to attacker-controlled account, sanctioned entity.
*AV-2:* **Preventive** for bank change in last 7 days, sanctions list, account ownership. **Fails if unavailable, unsigned manual checklist, or overridden**. Does not prove ownership if service down.
*MG-4:* **Preventive/detective** if manager independently verifies bank details against source documents. Fails if manager relies solely on AV-2 pass.
*RA-7:* **Detective**; after 24h recovery uncertain, so not corrective.
*ED-1:* Explicitly forbids hijack case: vendor >180 days AND no bank change 7 days AND AV-2 passed without override.

**O4 - No commercial substance / fictitious goods & services, unreasonable price**
*Threat:* Payment for not-received goods/services, fabricated receipt, kickback, price not commercially reasonable.
*AV-2:* **Explicitly fails to address** per definition. Basic PO match is not proof of receipt or reasonableness.
*MG-4:* **Preventive** only if manager reviews receipt/service report/invoice and commercial reasonableness. Rubber stamp = fail.
*RA-7:* **Detective** - audit can sample receipt evidence, but after settlement often too late for recovery.
*ED-1:* Does not address O4 alone; depends on MG-4 review quality.

**O5 - Collusion and independence failure (same workstation, repeated pairing, shared credentials)**
*Threat:* Two persons act as one, manager shares override credential, preparer = releaser via service account.
*AV-2:* **Fails** - does not detect collusion or credential sharing, cannot establish who controlled account.
*MG-4:* **Fails if conflicted** (e.g., direct supervisor rating subordinate, L <3, or credential shared). Unresolved credential-sharing remains independence failure.
*RA-7:* **Detective** via pattern mining (same pair 37x/30d, same workstation, same-user rate). Not preventive.
*ED-1:* Requires independent MG-4 (not preparer/releaser, L3+, no unresolved conflict). Not satisfied if m09 = credential owner + rater.

**O6 - Irrevocability / recoverability failure**
*Threat:* Defect discovered after bank settlement when recall no longer reliable.
*AV-2 & MG-4:* Value depends on **timing vs. settlement**. Before Release = preventive. After Release but before Settlement = hybrid - can still stop settlement/recall. After Settlement = purely detective, no corrective capacity, even if exceptional legal recovery theoretically possible.
*RA-7:* **Corrective capacity** exists only if audit within 1 business day AND within 24h of release. After that, becomes documentation, not correction.
*ED-1:* Mandates MG-4 before settlement AND RA-7 within 1 business day to preserve corrective window.

**O7 - Accountability and non-repudiation**
*Threat:* Action cannot be attributed, token time forged, logging delay obscures precondition.
*AV-2 / MG-4 / RA-7:* All fail if evidence quality poor (missing review artifacts, no bank-ownership evidence at release time, late token without audit trail, manual checklist unsigned).
*ED-1:* Requires token active *before* Prepare_Payment. Logging delay = precondition failure unless proven otherwise.

## 2. Equivalence and Sufficiency Test

A package is not equivalent because it exists; it must replicate the *risk-reduction properties* of independent second releaser.

**Test Steps - T.I.C.O.R.E.C.:**

1.  **Timing (Preventive vs Detective):** Was independent check *before* Release_Payment (fully preventive), *between Release and Settlement* (hybrid - preventive if it can block settlement/recall, detective otherwise), or *after Settlement* (purely detective)? Hybrid is downgraded vs. true four-eyes unless there is evidence the manager actually held settlement.
2.  **Independence:** Manager L3+? Not preparer/releaser? No unresolved conflict (rater, relative, shared workstation, shared credential)? Same-user workstation sharing undermines even distinct IDs. Credential-sharing = independence failure until resolved.
3.  **Coverage:** What checks were actually performed? AV-2 only covers duplicate, sanctions, ownership, 7-day bank change, limit, PO match. It does NOT cover receipt, collusion, reasonableness, or account-control compromise. MG-4 coverage depends on artifacts reviewed (invoice + bank details + receipt). Clean AV-2 pass  proof of no defect.
4.  **Overrideability:** Was AV-2 block vs warning? Was warning overridden with proper independent credential vs. self-override with borrowed credential? Override with assigned manager credential destroys both AV-2 and MG-4.
5.  **Recoverability:** Could defect still be stopped/recalled? Within 24h and before settlement = correctable. After settlement + 24h = unrecoverable for control purposes. RA-7 within 1 business day is required for ED-1 to be partly corrective.
6.  **Evidence Quality:** Are reviews documented (service report seen?), is bank-ownership evidence contemporaneous with release time? Is token timestamp trustworthy? Missing evidence = cannot assume coverage.
7.  **Collusion Resistance:** Does package resist two actors acting as one? Repeated pairing, same workstation, high same-user rate require organizational design evidence. Distinct IDs alone are insufficient.

**Graduated Verdict:**

*   **Fully Equivalent:** All ED-1 conditions met OR independent MG-4 before Release with verified coverage on O1-O4 + timely RA-7 + no independence/coverage gaps. Residual risk comparable to true four-eyes.
*   **Partially Equivalent (Tolerable Deviation):** Core independence before *settlement* with good coverage, AV-2 passed without override, low-risk vendor/amount, but a non-material ED-1 timing or evidence gap (e.g., manager 24 min after release but before settlement with full review). Technically nonconforming but control objective substantially met. Requires monitoring, not sanction.
*   **Merely Mitigating:** Some controls present but material gap remains: manager after settlement, conflicted manager, AV-2 overridden or unavailable, late audit outside recall window, high-risk bank change. Risk reduced vs. naked single-user but not to four-eyes level.
*   **Ineffective:** Controls absent, overridden by same actor, or post-settlement ratification with no corrective capacity + high exposure (new vendor, bank change, large amount). Objective failed.

**Why "same expected loss" alone is insufficient:**

Expected loss = probability × amount averages away distinct control objectives. Two cases with same expected loss can have unacceptable differences: 
(a) **Tail-risk and irrevocability:** A €900k unrecoverable payment has existential and regulatory impact beyond its probability-weighted value.
(b) **Threat coverage:** AV-2 may lower expected duplicate-payment loss but leaves O4/O5 (fictitious receipt, collusion) untouched - same mean hides uncovered scenarios.
(c) **Precedent and moral hazard:** Tolerating convenience same-user for low amounts normalizes violation, increasing future probability of high-risk violation.
(d) **Auditability and legal defensibility:** Regulator requires demonstrable segregation, not statistical equivalence. A detective-only package that relies on uncertain recall does not satisfy ex-ante control design principles even if ex-post loss was zero.
(e) **Knightian uncertainty:** Fraud with collusion cannot be assigned a stable probability; control must demonstrate resistance, not just low historical frequency.

**Semantics chosen for "manager before settlement but after Release_Payment":**

We classify it as **Hybrid (Preventive-Detective)**, not purely detective, with rationale: `pm4py` and process-mining literature often label any post-Release activity as detective because the log event Release_Payment has occurred. Control-objectively, bank settlement is the irrevocability point. A manager action at 08:30 that prevents a 10:00 settlement is functionally preventive even though log-order is detective. Our table therefore uses:

*   **Preventive** = before Release_Payment
*   **Hybrid** = after Release_Payment but before Bank_Settlement and within recall window - counts toward preventive capacity but downgraded one level vs. before-release because (a) release already triggered downstream workflows, (b) relies on settlement hold process working, (c) shorter time to review.
*   **Detective** = after settlement or outside recall.

Thus AP-201 (08:30 ratify before 10:00 settlement) and AP-207 (14:40 before 16:00) are hybrid - materially mitigating but not fully equivalent to `Prepare  Release`. AP-203 and AP-206 manager *before* release are fully preventive and stronger. AP-208 manager *after* settlement is purely detective.

## 5. Counterfactual and Residual-Risk Analysis

*All numerical ranges are illustrative and labeled as such; qualitative labels are primary.*

**AP-201 - Low-value convenience violation (€1,800, no bank change):**
*Most plausible loss mechanism:* Same-user error (wrong amount/vendor) or small opportunistic fraud hidden as office supply. AV-2 would catch duplicate/limit but not fictitious receipt; without manager, error would settle.
*Which control breaks chain:* Hybrid MG-4 before settlement (m04 independent) + AV-2 pass. Manager could have blocked settlement if amount/vendor wrong.
*What remains exposed:* Recall window missed by audit (25h). If manager review had been rubber-stamp without looking at receipt, O4 would remain uncovered. Residual risk **Low** - single low-value exposure, but precedent risk remains.
*With truly independent second releaser:* Second person would have to independently retrieve PO/receipt before authorizing release, eliminating convenience bypass. Expected change: violation disappears; residual risk moves from Low (hybrid) to **Negligible**. No material difference in loss amount but restores discipline.

**AP-202 - Override-driven fraud (€480k, bank change 2h, override with manager credential):**
*Loss mechanism:* New vendor + immediate bank change = classic hijack; operator limit breach + credential sharing indicates intentional bypass. Funds diverted to employee-relative account.
*Breaks chain:* **None** effectively - AV-2 emitted warning but was overridden by same actor using m09 credential, destroying AV-2 and MG-4. Late conflicted manager ratification after funds gone cannot break chain.
*Remaining exposed:* Everything - O1, O3, O5 all failed, unrecoverable after 24h.
*Counterfactual second releaser:* Independent u*  u23 would have received AV-2 warning, would not have override credential, and would be required to verify new bank account out-of-band. *Illustrative:* Probability of release would drop from ~90% (override available) to **Low (5-15%)**; exposure would be €0 blocked vs. €480k lost. True four-eyes is the only control that would have reliably stopped this.

**AP-204 - Nominal pass but fabricated receipt (€220k, u12/u13 pair):**
*Loss mechanism:* Colluding or non-independent pair fabricates service receipt for consulting; AV-2 cannot detect (O4 not covered), nominal four-eyes gives false assurance, settlement occurs.
*Breaks chain:* RA-7 audit detected fabrication but 4 days later - too late for recall  detective only, not corrective.
*Remaining exposed:* Collusion resistance, O4 coverage. Even timely audit next day might not verify receipt authenticity without fieldwork.
*Counterfactual second releaser:* Truly independent releaser from different team/workstation with mandatory receipt verification (site visit, timesheet) would have questioned receipt before release. *Illustrative:* Detection before release rises from **Low (~10% with current AV-2)** to **Moderate-High (60-80% with independent verification)**. Repeated-pair monitoring + job rotation would be needed to keep pair from acting as one.

**AP-206 - Token timing gap (€95k, production outage, manager before release):**
*Loss mechanism:* If outage claim false, same-user could push emergency payment without proper authorization. Token after Prepare suggests permission may have been retrospective. If manager review weak, fictitious emergency could pass.
*Breaks chain:* Strong package: AV-2 pass, manager m11 before release with presumably full review, audit within recall. Even if ED-1 precondition fails on 2-min gap, preventive controls replicate four-eyes substance.
*Remaining exposed:* Evidentiary / accountability risk (O7) - if token gap is not logging delay, then permission was invalid and sets precedent for unauthorized emergency use. Residual risk **Low** for loss, **Medium** for compliance precedent.
*Counterfactual:* With second releaser, token timing irrelevant - no emergency needed. With proven logging delay, residual risk becomes **Low** and classification would move from INDETERMINATE to OBJECTIVE_MET. Without proof, must remain INDETERMINATE and require log forensics.

**AP-208 - AV outage high-value (€900k, bank change 3d, settlement before manager):**
*Loss mechanism:* Bank account changed 3 days prior - possible hijack that AV-2 would have flagged as "bank change 7 days". With AV unavailable and manual checklist unsigned, manager after settlement cannot verify ownership at release time. Even legitimate payment had no assurance; attacker could reuse same path.
*Breaks chain:* None before irrevocability - no AV coverage, no preventive manager, audit 4 days later.
*Remaining exposed:* O3 completely uncovered, O6 irrevocable, tail risk extreme. Legitimate outcome was luck, not control. *Illustrative* residual exposure at release time: **High (70-90% chance that a hijacked payment would have cleared)**.
*Counterfactual second releaser:* Even without AV, independent releaser would be forced to perform manual bank-ownership verification (call-back, Letter to vendor) before release, and high-value €900k > limits would require extra approval. Payment would have been **held pending AV restoration** under proper policy, reducing residual risk to **Low**. Rule: AV outage should equal payment block for >€100k.

**AP-209 - Repeated pair without proven defect (€42k, u12/u13 again):**
*Loss mechanism:* Same as AP-204 but not realized in this case - shared workstation + tight pairing could hide collusion or simply reflect efficient cell design. O5 is the threat.
*Breaks chain:* AV-2 pass + timely audit within recall (found no defect). However, audit cannot prove independence of pair.
*Remaining exposed:* Medium collusion risk carried forward; future high-value payment by same pair could replicate AP-204. Single-case audit clean does not clear systemic pattern.
*Counterfactual:* Independent releaser rotation (require 3-person pool, random assignment, prohibited shared workstation for release) would break repeated-pair dominance. Detection of anomalous pairing would trigger **Preventive - payment queued for different releaser**. Without organizational docs, we cannot distinguish misconduct from design, hence INDETERMINATE.

## 6. Evidence and Monitoring Recommendations

**Evidence to collect to close gaps (case-specific):**

*   Token forensics: request/approval vs. creation timestamps, system clock sync logs for AP-206; emergency justification call/ticket for AP-203/206/207/208.
*   Manager review artifacts: screenshot/checklist that m04/m02/m11/m15 reviewed invoice + bank master data + receipt/service report (not just ratify button). Level confirmation L3+.
*   Bank-ownership contemporaneous evidence: vendor bank letter, out-of-band verification log for AP-202/208 at release time, not after.
*   Credential-sharing investigation AP-202: SIEM logs showing m09 credential use by u23 IP/workstation, HR conflict documentation.
*   Workstation/assignment for AP-204/209: Are u12/u13 formally assigned as two-person payment cell? If so, provide charter, rotation, segregation waiver; if not, treat as collusion red flag. Require distinct physical logins, not shared workstation.
*   AV-2 outage AP-208: Why was payment not blocked? Collect manual checklist policy and exception approval.

**Continuous monitoring rules - Alert  Proof:**

| Monitor | Alert Rule | Why | Alert  Proof - Required Triage |
|---|---|---|---|
| **Same-user rate** | % completed payments where Prepare = Release > 5% weekly or >2% daily | Detects convenience drift (AP-201) | Alert triggers review; emergency-permitted cases with full ED-1 are excluded from numerator after verification |
| **Override rate** | AV-2 warning overridden >0% or block bypass attempt | AP-202 pattern | Each override requires independent second-person override credential + documented business reason; self-override is automatic violation |
| **Late manager approval** | Manager approve/ratify timestamp > Release or > Settlement or >24h | Hybrid vs detective distinction | Before-settlement hybrid allowed only if manager evidence shows hold; after-settlement always flagged as detective lapse even if legitimate |
| **Audit-before-recall** | RA-7 not within 1 business day OR >24h after Release for emergencies | Loss of corrective capacity | Late audit is control failure even if payment was legitimate; track % audits within recall window |
| **Repeated resource pairs** | Same Prepare+Release pair 10 joint payments /30d or Jaccard >0.7 | Collusion / independence erosion (AP-204/209) | Could be legitimate cell - requires organizational design doc to whitelist; otherwise rotate pairs |
| **Shared workstations** | Same workstation/host for Prepare and Release of same case or pair | Undermines independence despite distinct IDs | Could be hot-desking - verify via badge/logon data before alleging misconduct |
| **Bank-change proximity** | Payment within 7 days of vendor bank change | O3 hijack risk (AP-202/208) | New vendor legitimate change still requires enhanced verification; block until verification documented |
| **AV-2 outage** | Validation_Service_Unavailable or AV not operational flag | Zero coverage period - should block high-value payments | Outage alone not misconduct; failure to block payment during outage is control breach (AP-208) |
| **Amount vs limit/outage** | Payment >€100k during emergency or >operator limit or AV unavailable | ED-1 amount condition, limit breach | Large legitimate emergencies may exist - requires pre-approved exception board, not single manager ratify post-settlement |

**Distinguish alert from proof:** Every rule above generates an *alert for investigation*, not a misconduct conclusion. Example: repeated u12/u13 pairing is *suspicious pattern* but could be authorized cell; only after missing design docs + fabricated receipt does it become failure. Similarly, AV-2 clean pass is *evidence of limited checks*, not proof goods received. Monitoring should use case-mix risk scoring (amount × vendor age × bank change × pair frequency) rather than raw same-user count.

**Process design recommendations:**

*   Enforce system block: if AV-2 unavailable, block Prepare/Release for payments >€50k or with bank change <7d.
*   Enforce override segregation: warning override requires *different* manager credential than ratifier, with MFA.
*   Require manager approval **before Release** for >€50k; allow after-Release-before-Settlement hybrid only for ED-1 with documented hold.
*   Mandate random releaser assignment from pool of 3 for high-value consulting payments.

**PM4Py behavior you cannot guarantee across versions:**

*   `pm4py.filter_four_eyes_principle` - In some versions returns conforming cases, in others violating cases, and parameter order (`activity_1`, `activity_2`) may be strict. The code computes violating via set-difference against `Release_Payment` cases to be version-robust, with manual fallback if the function is absent.
*   `pm4py.format_dataframe` - Requires `case_id`, `activity_key`, `timestamp_key` naming; older versions ignore `org:resource` for four-eyes and require `org:resource` column explicitly named; we keep it as `org:resource` which is standard but some forks expect `org:resource` to be renamed.
*   UTC handling - PM4Py may convert to local timezone or drop tzinfo; we parse with `utc=True` and treat settlement/recall windows in raw hours, not business-day calendars (weekends not modeled).
*   Cases without `Release_Payment` (AP-205 `Attempt_Release`) are correctly excluded from four-eyes check; PM4Py will not count them as violation, so we flag them separately as `LOSS_PREVENTED_BEFORE_COMPLETION`.
*   No external file I/O or service calls are used; all data is in-memory.
