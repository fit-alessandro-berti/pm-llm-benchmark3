## 1. Modeling assumptions

- **Object types (singular PascalCase):** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. Identifiers stay as given (`O100`, `I1`, `P1`, `D1`, `V1`, `M1`, …).
- **E2O qualifier vocabulary** (event-to-object role, not a second object type):
  - `creates` — Create Order → Order
  - `adds` / `receives` — Add Item → Item / Order
  - `reserves` / `stock_reserved_for` — Reserve Stock → Item / Order
  - `packs` / `packed` — Pack Package → Package / Item
  - `dispatches` / `dispatched_as` — Dispatch Package → Package / Delivery
  - `confirms` / `confirmed_package` — Confirm Delivery → Delivery / Package
  - `issues` / `bills` — Issue Invoice → Invoice / Order
  - `records` / `settles` — Record Payment → Payment / Invoice
  - `closes` — Close Order → Order
  - `related_order` — logistics milestone that operationally involves an Order because the event moves that order’s items (Pack, Dispatch, Confirm)
- **O2O direction:** `ocel:oid` is the subject (container, bill, settler); `ocel:oid_2` is the target. Qualifiers: Order `contains` Item; Package `packs` Item; Delivery `carries` Package; Invoice `bills` Order; Payment `partially_settles` or `completes_settlement` Invoice. M1 is the first installment (`partially_settles`); M2 is modeled as the completing installment (`completes_settlement`). That completion is an assumption: the narrative does not state the invoice total.
- **Downstream E2O richness:** logistics events are related directly to their native objects (Package, Item, Delivery) **and** to the Orders whose items they move. Financial events: Issue Invoice touches `V1` and both Orders; Record Payment touches only the Payment and `V1`. Payments are **not** allocated to Orders or Items. Items are **not** attached to Dispatch, Confirm, invoice, payment, or close events.
- **Source facts vs. analytical propagation:** E2O rows are the only observed event involvements. O2O rows are structural master data. Transitive reachability (Confirm D1 ↝ I1 via D1→P1→I1) is **not** materialized as E2O. The qualifier `related_order` is an explicit operational-involvement policy, distinct from `creates`/`closes` and from O2O `contains`. Discovery therefore cannot treat a derived path as if a source system logged it.
- **PM4Py assumption:** constructor `OCEL(events=..., objects=..., relations=..., o2o=...)` and the high-level `pm4py.ocel_*` / `pm4py.discover_*` names used below (≈ 2.7+). If a build rejects `o2o=` or lacks `discover_otg` / `discover_etot`, keep the four DataFrames unchanged and only swap the isolated constructor/API line (commented in the pipeline). Flattening may return a DataFrame; the pipeline converts to an EventLog when the skeleton miner requires it.

**Trade-off (direct source vs. propagated relations).** Source-minimal E2O (only objects named in the sentence) preserves provenance but starves Order flattening of Dispatch/Confirm, so order DFGs look as if fulfillment ended at pack/invoice. Full O2O-propagated E2O (every reachable Item/Order on every downstream event) makes traces look complete but inflates convergence, copies shared events into still more cases, and makes discovery treat inference as observation. The hybrid used here puts Orders on logistics milestones that actually move their items, keeps Items on create/reserve/pack only, and keeps payments on the invoice — enough for order-level fulfillment views without pretending the source allocated cash or confirmed individual SKUs.

**Consequential relation sets (convergence / divergence)**

- **e07 Pack P1** is the logistics hinge: one event, two Items (I1, I3) from two Orders (O100, O200), plus P1. Flattening on Order or Item **copies** this event into both cases (convergence). It is also why P1 is not “an O100 package.”
- **e06 Reserve Stock** is the earlier shared operational event on I1/I3 and O100/O200; same copy-on-flatten effect, before any package exists.
- **e11 Issue Invoice** is the financial hinge: one V1, two Orders. Flattening on Order duplicates invoicing; flattening on Invoice does not.
- **O100** is the main divergence object: two Add Item, two Pack, two Dispatch, two Confirm (P1/D1 *and* P2/D2). A flattened DFG will draw repeat-edges that look like rework rather than two parallel parcels.
- **V1** diverges on Record Payment (M1 then M2) without allocating either payment to an order.

## 4. Expected flattened behavior

**Order (2 cases).**  
O100 ≈ Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Pack Package → Dispatch Package → Dispatch Package → Issue Invoice → Confirm Delivery → Confirm Delivery → Close Order.  
O200 ≈ Create Order → Add Item → Reserve Stock → Pack Package → Dispatch Package → Issue Invoice → Confirm Delivery → Close Order.  
**Copied shared events:** e06, e07, e09, e11, e13 appear in *both* cases.  
**Omitted:** both payments (unallocated), the other order’s create/add/close, and O200’s exclusive P2/D2 path.  
**Likely DFG edges:** Create→Add; Add→Add (only O100) and Add→Reserve; Reserve→Pack; Pack→Pack (O100) and Pack→Dispatch; Dispatch→Dispatch (O100) and Dispatch→Issue Invoice; Issue Invoice→Confirm; Confirm→Confirm (O100) and Confirm→Close.  
**Misleading:** shared events look executed twice; O100’s double Pack/Dispatch/Confirm looks like a loop/rework rather than two packages; each order looks separately invoiced; frequencies of Reserve/Pack(P1)/Issue Invoice are inflated to 2.

**Package (2 cases).**  
P1 ≈ Pack Package → Dispatch Package → Confirm Delivery.  
P2 ≈ the same shape.  
**Copied shared events:** none between P1 and P2 under this E2O policy.  
**Omitted:** order creation, line-item adds, stock reserve, invoice, payments, close; and the fact that P1 mixes two orders.  
**Likely DFG:** Pack→Dispatch→Confirm, each edge frequency 2.  
**Misleading:** two identical independent package processes; P1’s batching across O100/O200 is invisible.

**Delivery (2 cases).**  
D1 ≈ Dispatch Package → Confirm Delivery; D2 ≈ the same.  
**Copied shared events:** none.  
**Omitted:** everything before dispatch, all finance, item identity.  
**Likely DFG:** Dispatch→Confirm (freq 2).  
**Misleading:** deliveries look interchangeable; D1’s mixed-order cargo is hidden.

**Invoice (1 case).**  
V1 ≈ Issue Invoice → Record Payment(100) → Record Payment(150).  
**Copied shared events:** none (single invoice object).  
**Omitted:** entire logistics and both Close Order events.  
**Likely DFG:** Issue Invoice→Record Payment and Record Payment→Record Payment (or a self-loop).  
**Misleading:** a tidy two-installment invoice for “one customer bill,” with no view that V1 covers two orders and no allocation of M1/M2.

**Why Payment flattening is particularly weak.** Each of M1 and M2 participates in exactly one event. The flattened log is two singleton traces `[Record Payment]`. There are no DFG edges, no skeleton constraints beyond “this activity occurs once,” and the settlement story (partial then complete against V1, covering O100 and O200) lives only in E2O/O2O to the invoice. Amounts are attributes, not control-flow. Flattening on Payment therefore discards the only relations that make payments meaningful.

## 5. Expected object-centric structures

**OC-DFG.** Per-type directly-follows graphs plus cross-type coupling at shared events. Order: create–add–reserve–pack–dispatch–invoice–confirm–close, with extra pack/dispatch/confirm repeats from O100. Item: Add→Reserve→Pack (I2 skips Reserve). Package: Pack→Dispatch→Confirm. Delivery: Dispatch→Confirm. Invoice: Issue→Record Payment→Record Payment. Payment: a single activity, no edge. The OC-DFG should show **P1** as the place where O100 and O200 meet (e07), and **V1** as the place where both orders meet financially (e11) while **M1**/**M2** only extend the Invoice stream.

**OTG.** A small typed graph from O2O only: Order→Item (`contains`), Package→Item (`packs`), Delivery→Package (`carries`), Invoice→Order (`bills`), Payment→Invoice (`partially_settles` / `completes_settlement`). Item is a sink. There is **no** O2O edge Package–Order; the P1–O100/O200 coupling is event-level, not master-data. V1 is the financial hub; M1 and M2 only touch V1.

**ET–OT.** Create/Close touch only Order. Add Item and Reserve Stock touch Order+Item. Pack touches Order+Item+Package. Dispatch touches Order+Package+Delivery. Confirm touches Order+Package+Delivery. Issue Invoice touches Order+Invoice. Record Payment touches Payment+Invoice only. That last cell is the deliberate non-allocation of M1/M2 to O100/O200.

**Object-centric Petri net.** Expect typed places and synchronizing transitions at e06 (I1∧I3 / O100∧O200), e07 (P1 created while both orders and both items participate), and e11 (V1 issued for both orders). M1 then M2 are successive invoice transitions; Close is per-order. O100’s path needs both delivery confirmations; O200 only needs D1. **This net is not unique:** miner variant, silent transitions, and how shared events are fused vs. duplicated all change the wiring. Read it as one plausible synchronization hypothesis, not *the* model.

**Object-interactions summary.** O100 interacts (via events) with I1, I2, P1, P2, D1, D2, V1. O200 interacts with I3, P1, D1, V1. **P1** is the cross-order logistics hub (I1, I3, O100, O200, D1). **V1** is the cross-order financial hub (O100, O200, M1, M2). M1 and M2 interact with V1, not with each other and not with a single order. P2/D2 stay inside O100.

## 6. Modeling alternatives

1. **Source-minimal E2O.** Relate an event only to objects named in its sentence: Dispatch → {P, D}; Confirm → {D}; Pack P2 → {P2, I2} without O100; payments unchanged; Reserve/Pack P1/Issue Invoice still include the orders the text names. *Effect:* Order DFGs lose dispatch/confirm (or confirm), so fulfillment looks finished at pack/invoice. Convergence at e07/e11 remains. Provenance is cleaner; lifecycle completeness on Order is worse. Business story unchanged.

2. **Full operational involvement.** Also attach every O2O-reachable Item and Order to Dispatch, Confirm, Issue Invoice, and both payments (e.g. e13 → D1, P1, I1, I3, O100, O200; e12 → M1, V1, O100, O200). *Effect:* Order traces gain M1/M2 (still unallocated, now duplicated); Item traces gain dispatch/confirm; OC-DFG frequencies and OC-net synchronization explode. Discovery treats inferred involvement as observed. Same story, noisier models.

3. **O2O-propagated analytical relations (derived view).** Keep stored E2O source-minimal; at analysis time walk O2O and add rows qualified `derived:related_order` / `derived:contains`. *Effect:* raw OC-DFG/OTG stay honest; a second, labeled derived OCEL reproduces alternative 2. Failure mode is loading the derived table back as if it were the system of record. The narrative does not change; only which graph you claim is “the log.”

Other defensible tweaks: drop `related_order` on Confirm but keep it on Dispatch; treat both M1 and M2 as `partially_settles` if you refuse to assume V1 is fully paid; omit Package from Confirm. Each moves a milestone between object-type DFGs without rewriting who bought what or who paid V1.

## 7. Failure modes

1. **Relation inflation.** Attaching every reachable object to every event (especially Items on payments, or both Orders on M1/M2) makes every flattening look like the same long trace and fabricates frequencies.
2. **Missing direct E2O links.** If Pack P1 is not related to O200, or Issue Invoice is not related to both Orders, object-centric discovery never sees the batch/bill coupling that *is* in the narrative.
3. **Treating O2O propagation as observation.** Walking D1→P1→I1 and inserting Confirm→I1 into `relations` silently converts master data into an event fact. Qualifiers and the E2O/O2O split exist to prevent that.
4. **Duplicate shared events after flattening.** e06, e07, e09, e11, e13 are one happening each. Order/Item flattening copies them. Throughput, resource, and “how often did we reserve stock?” questions asked on a flattened Order log will double-count.
5. **Ambiguous payment allocation.** Linking M1 or M2 to O100 or O200 invents a split the process does not give. Amounts stay on events; settlement is via V1 only.
6. **Overly short Payment traces.** Flattening on Payment yields two length-1 cases. A DFG/skeleton/Petri net on that view cannot express partial-then-complete settlement.
7. **Constructor / API version mismatch.** Passing `o2o=` into an old `OCEL(...)`, or calling `discover_etot` where the build only has a namespaced algo, raises TypeError/AttributeError. Fix the isolated call; do not drop O2O or split into six classic logs.
8. **False total order for same-time events.** This log has unique timestamps, so DFG order is safe. If two events shared a timestamp, flattening and DFG would still impose an arbitrary order (DataFrame order / eid sort). Do not read “directly follows” as physical sequence when times tie.
9. **Qualifier collisions.** Reusing `packs` for both E2O (event packs package) and O2O (package packs item) is readable but easy to mis-join. Always filter by table.
10. **OC Petri net over-interpretation.** Multiple nets fit 17 events. A silent transition around O100’s second confirm is a miner artifact until you test it against the narrative.
