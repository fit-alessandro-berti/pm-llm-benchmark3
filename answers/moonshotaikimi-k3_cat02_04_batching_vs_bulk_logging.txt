**Why G6-like data creates both inflated waiting and near-zero service (mechanism).** The form captures one timestamp pair at the moment of data entry and writes it to both lifecycle fields, while `queue_arrival` comes from a real upstream system. Waiting = entry_time  arrival therefore measures the clerk's *reporting delay* (hours), not queueing for the closing task — inflating waiting. Service = complete  start = 0 because both fields are the same entry instant — collapsing service. The two biases are *coupled through the same artifact*: every hour added to waiting is an hour removed from visible work. Downstream: utilization reads 0% all afternoon; throughput becomes a delta spike at 17:00 (seven completions in one minute  near-infinite instantaneous rate); flow-time and SLA metrics shift to 17:00 regardless of when tickets were actually resolved; conformance tools may drop zero-duration events or discover false parallelism; and bottleneck analysis concludes Close ticket has infinite capacity and zero cost, pushing all apparent delay onto upstream steps — exactly backwards from reality, since the afternoon's actual closing work is invisible.

# ---------- (5) independent pandas diagnostics ----------
def strict_overlap_rate(s, e):
    n, ov, tot = len(s), 0, 0
    for i in range(n):
        for j in range(i + 1, n):
            tot += 1
            ov += bool(s[j] < e[i])          # strict: touching is NOT overlap
    return ov / tot if tot else np.nan

def max_depth(s, e):
    pts = [(t, 1) for t in s] + [(t, -1) for t in e]
    pts.sort(key=lambda p: (p[0], p[1]))     # ends before starts => strict depth
    cur = best = 0
    for _, d in pts:
        cur += d; best = max(best, cur)
    return best

def max_backlog(arr, comp):
    pts = [(t, 1) for t in arr] + [(t, -1) for t in comp]
    pts.sort(key=lambda p: (p[0], -p[1]))    # arrivals before completions
    cur = best = 0
    for _, d in pts:
        cur += d; best = max(best, cur)
    return best

def diag(g):
    g = g.sort_values(["start_timestamp", "sequence_no"])
    s = g["start_timestamp"].to_numpy(); e = g["time:timestamp"].to_numpy()
    adj = np.mean([s[j] == e[j-1] for j in range(1, len(g))]) if len(g) > 1 else np.nan
    zero_dur = g[g["start_timestamp"] == g["time:timestamp"]]
    inst = zero_dur.groupby("start_timestamp").size().max() if len(zero_dur) else 0
    return pd.Series({
        "n": len(g),
        "uniq_starts": g["start_timestamp"].nunique(),
        "uniq_ends": g["time:timestamp"].nunique(),
        "max_start_grp": g.groupby("start_timestamp").size().max(),
        "max_end_grp": g.groupby("time:timestamp").size().max(),
        "overlap_rate": round(strict_overlap_rate(s, e), 2),
        "max_depth": max(max_depth(s, e), inst),   # inst handles G6 zero-duration
        "adjacency_rate": round(adj, 2),
        "med_rec_lag_s": (g["recorded_at"] - g["time:timestamp"]).dt.total_seconds().median(),
        "single_recording": g["recorded_at"].nunique() == 1,
        "neg_waits": int((g["start_timestamp"] < g["queue_arrival"]).sum()),

                              .dt.total_seconds().median() / 60, 1),

        "arr_before_1st_start": int((g["queue_arrival"] < g["start_timestamp"].min()).sum()),
        # granularity indicators: lifecycle fields at :00s vs recorded_at seconds
        "lifecycle_sec0": float(((g["start_timestamp"].dt.second == 0)
                                 & (g["time:timestamp"].dt.second == 0)).mean()),
        "recorded_has_sec": float((g["recorded_at"].dt.second != 0).mean()),

# 5. Robustness and alternative explanations

**Toggle 1 — resource IDs trusted vs. treated as shared accounts.**

| cluster | if resource ID trusted | if treated as shared account |
|---|---|---|
| G1 | Machine ID; batch conclusion unchanged | N/A (machine); unchanged |
| G2 | One inspector: serial-after-setup favored | Two inspectors sharing T-B: common start + parallel pairs becomes possible; completion pairing unresolvable |
| G3 | One reviewer; bulk submission favored | Multiple submitters could each bulk-submit at 11:30 — but the *single* recorded_at (11:31) argues against it |
| G4 | Serial single server; unchanged | Sharing would break exact adjacency — adjacency itself evidences one actor |
| G5 | One analyst multitasking 4 cases, depth 4 for 8 min — strained but not impossible | 2–3 analysts concurrent — natural; depth-4 window still requires 4 sessions or one person on two cases |
| G6 | One clerk's end-of-shift entry | Several clerks entering at 17:00–17:01 — still bulk entry; diagnosis stable |
| G7 | One operator, order unknown | Sharing irrelevant; rounding dominates |
| G8 | One technician; unchanged | Sharing would break adjacency; unchanged |

Net effect: only G5's *headline* explanation flips with the identity assumption; G2/G3 shift in degree. No cluster's *artifact* diagnoses (G6, G7) depend on identity.

**Toggle 2 — timestamps exact vs. interval-censored at stated precision.**
- 1-sec sources (G1, G4, G8): censoring ±1 s leaves equalities and adjacency intact  conclusions stable.
- 1-min sources (G2, G3, G5, G6): equalities survive ±30–60 s censoring; G5's four-way overlap window (8 min) is robust even though boundary overlaps are not; G6's bulk-entry diagnosis is unaffected.
- 15-min source (G7): censoring is decisive — the entire quarter-hour cell is one equivalence class. Simultaneous, serial, and interleaved execution are *all* consistent with the lifecycle fields; only the arrivals and the 1-min-stepped recorded_at (14:1614:20) carry ordering information. Exact-timestamp analysis of G7 is simply invalid; bounds must be reported instead.

**Same pattern, multiple physical explanations (five exhibits):**
1. **G2 (common start, staggered ends):** (a) genuine group setup then serial work; (b) "begin group" button artifact over serial work; (c) interleaved multitasking completed in arrival order. All three produce byte-identical logs.
2. **G3 (staggered starts, common end):** (a) folder bulk submission; (b) a hard 11:30 deadline forcing synchronized stop with immediate entry; (c) genuinely concurrent reviews finishing together. The identical recorded_at favors (a) but (b)+fast-typing is observationally close.
3. **G7 (grid-aligned identical bounds):** (a) rounded serial work (~3 min/item); (b) rounded simultaneous session; (c) post-hoc entry against shift defaults. The stepped recorded_at weakly favors sequential handling but cannot prove it.
4. **G4/G8 (exact adjacency):** (a) engineered sequential batching; (b) natural single-server queue drain; (c) scanner coupling (one scan writes item *i*'s end and item *i+1*'s start). Same timestamps; only (c) is distinguishable, and only via scanner documentation.
5. **G1 (identical start and complete):** (a) physical fixture batch; (b) one PLC cycle stamp written to all four items — a logging batch isomorphic to the physical batch. Both imply the same capacity model but different event semantics (per-item vs per-cycle truth).

# 6. Data-collection redesign

Prioritized by how directly each item kills an observed failure mode:

- **P0 — Per-item execution timestamps at the workpoint.** Capture start/complete from sensors, scans, or per-item buttons at the moment of work, never derived from form submission. (Kills G6's zero-duration bulk entry and G3's submission-as-completion.) Retain `recorded_at` *and* add `start_recorded_at` so retro-entry is detectable via lag asymmetry.
- **P0 — Resource/badge identity.** Prohibit shared logins on executed work, or attach badge/session IDs to every event. (Kills G5's attribution failure.)
- **P0 — Store raw, unrounded values.** Persist the pre-rounding timestamp alongside any rounded display value. (Kills G7; the undocumented round-down/up rule must be documented in metadata.)
- **P1 — First-class group/batch identifiers.** Fixture load ID (G1), begin-group ID (G2), folder/submission ID (G3) generated at execution time, so operational batches are explicit data rather than inference targets.
- **P1 — Workstation capacity metadata.** Machine-readable capacity per workstation (e.g., RBT-7 = 4) so utilization can be computed as union-of-busy with correct capacity denominators.
- **P1 — Block/unblock and pause/resume events.** Safety checks, changeovers, and downtime as activities on the resource timeline. (Converts G8's inferred capacity loss into data; enables waiting decomposition into blocked vs. queued.)
- **P2 — Clock synchronization.** NTP across PLC, MES, tablets, and safety systems, with measured offsets logged per source. (G8's cross-clock join is currently unverifiable.)
- **P2 — Precision/accuracy metadata per field**, including rounding rule and true accuracy, plus automated data-quality monitors: negative-wait alarms, equality-cluster alarms (many identical starts/ends), and zero-duration alarms. These three monitors would have flagged G6 and G7 on the day they were produced.

# 7. Final adjudication

**Interpretable with high confidence (usable, with stated caveats):**
- **G1** — genuine simultaneous machine batch (fixture capacity 4 matches batch size; near-real-time PLC recording). Caveat: confirm second-level stamps. Model as one resource, capacity 4, 3-min cycle.
- **G4** — trustworthy serial single-server processing of an accumulated queue; the PM4Py "sequential batching" label is a detection, not an engineering finding. Only open item: the 7-min lead gap before 12:05.
- **G6** — high confidence *as an artifact*: end-of-shift bulk entry. Confident diagnosis, unusable performance data.
- **G7** — high confidence *as an artifact*: quarter-hour rounding, proven by negative waits. Confident diagnosis, unusable point timestamps.

**Exclude or interval-censor in queue/service analysis:**
- **G7** — interval-censor to [14:00, 14:15) / (14:00, 14:15]; report bounds only; never the apparent 15-min service.
- **G6** — exclude lifecycle fields entirely; retain recorded_at (17:01) as a right-censoring bound on true completions.
- **G3** — treat 11:30 as submission time; true completions right-censored in [start, 11:30]; starts usable only with a recall-uncertainty caveat.
- **G2** — treat 10:00 as group-level start; per-item starts censored in [10:00, own completion]; apparent durations are upper bounds.

**Require operational validation before any performance conclusion:**
- **G5** — obtain badge/session data; until then, report pool-level union utilization (30 min busy, average concurrency 2.33) and flag the unexplained depth-4 window.
- **G8** — measure the clock offset between safety and repair systems; only then decompose waiting into blocked vs. queued and confirm the 15:3515:38 alignment.
- **G2** — observe inspection practice (serial vs. interleaved) to choose between the second-ranked explanations.
- **G1** — verify whether the PLC writes per-item or per-cycle timestamps; affects event semantics, not the capacity conclusion.

The through-line: PM4Py's batch labels and the physical explanations coincide for G1–G5 and G8 only after independent evidence (recording lag, negative waits, capacity, identity, external events) is brought to bear; for G6 and G7 the *same label* ("batching at all lifecycle") is a pure recording artifact. Identical timestamps are evidence about the *logging process* first, and about the *work process* only after the logging process is understood.
