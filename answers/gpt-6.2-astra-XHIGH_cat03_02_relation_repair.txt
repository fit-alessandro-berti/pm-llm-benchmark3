## 1. Consistency rules and evidence model

- **Hard invariants.** Preserve all observed events, objects and relations. Each added E2O must join an existing event to an existing object. Each added O2O must have existing endpoints in the correct roles and direction. Store a qualified relation once. Two events with the same timestamp retain their separate IDs.
- **Strong defaults.** Expect one Order per creation, one Order and one Item per addition, and one Item and one Package per packing scan. Expect one Package and one Delivery per dispatch, allowing bulk dispatch. An invoice issue needs one Invoice and at least one Order. A payment record needs one Payment and usually one Invoice. Confirmation has no single-Delivery requirement. Use the observed sequences from addition through packing and dispatch, and from invoice issue through payment, to check each candidate.
- **Weak heuristics.** Identifier fragments gain weight when another event demonstrates how the identifier is used. In particular, ev07 pairs `PK8-1` with PK-8, which makes the next scan `PK8-2` quite specific. A common route, customer or timestamp has little power to distinguish candidates here. Amounts gain weight when the object roles, timing and an observed transaction also fit. There are no item weights or manifest totals against which to reconcile gross weights.
- **Evidence against a repair.** A second assignment that conflicts with a more specific scan, an unsupported reversal of an O2O qualifier, or an allocation based only on a shared customer weighs against insertion. The portal permits an order-only receipt, an invoice may include adjustments, and cash may be unapplied. These explanations have different implications from a missing relation and remain available even if a proposed repair fits.

I use existing E2O/O2O pairs as examples of how this log records participation and persistent relationships. For a new pair I ask separately whether an event involved the object and whether a particular business relationship held. Neither a transitive path nor two proposed rows derived from the same clue supply a second observation.

## 3. Alternative repair bundles

**Bundle A — conservative/minimum-change repair.** Insert P01, P02, P11 and P12. The packing inference has a neighboring scan with a known package. The payment inference has an identified invoice, an earlier documented payment against it and an exact residual half an hour later. I use `settles` for an applied payment, as in the observed PAY-1 row. PK-8 now contains items from two orders. Its dispatch on ev10 is observed, but its delivery identity stays open between Y, the better textual match, and X, a possible shared departure. Keep ev11 on ORD-A alone. Keep INV-44 billed to the observed ORD-A and defer the possible ORD-B allocation. Applying PAY-2 to an invoice requires no decision about which orders that invoice covers. The unexplained difference between A's declared value and the invoice total remains visible.

**Bundle B — two shipments, joint acknowledgment and consolidated billing.** Insert P01–P04 and P07–P12. PK-8 takes IT-B1 alongside IT-A2. Interpret the question mark at ev10 as uncertainty about an otherwise matching N-421 and assign PK-8 to Y. X carries the observed PK-7. Each shipment now carries an item from A, so ev11 can be one acknowledgment by A covering both X and Y. Keep B off the receipt. Let ev12 issue INV-44 for both orders and let the two payments apply to that invoice. The orders share logistics and billing, while their observed item additions remain distinct. Nothing allocates an individual payment to an individual order. The joint receipt is the least certain step. The same two dispatches could lead to a receipt for X alone, Y alone, or an order-only acknowledgment even if the billing interpretation is correct.

## 6. Downstream process-mining effects

Direct object projections give the following changes. An O2O path can explain an event without placing that event in every trace along the path.

| Flattening | Unrepaired → A → B |
|---|---|
| Order | A's trace stays ev01, ev03, ev04, ev11, ev12 throughout. B's order trace stays ev02, ev05 under Bundle A, then gains ev12 under Bundle B. Flattening B's consolidated invoice issue across orders yields two case rows for one event. |
| Package | PK-7 keeps ev06, ev09. PK-8 changes from ev07, ev10 to ev07, ev08, ev10 in A and B. |
| Delivery | Initially and in A, only X yields a row, ev09. Under B, X has ev09, ev11 and Y has ev10, ev11. Both traces include the same receipt. |
| Invoice | INV-44 changes from ev12, ev13 to ev12, ev13, ev14 in A and B. Billing two orders in B still gives one issue row in this invoice case. |
| Payment | PAY-1 has ev13 and PAY-2 has ev14 in all three logs. Applying PAY-2 changes the invoice trace while leaving both Payment cases singletons. |

**OC-DFG.** In A the Package graph gains Pack Item → Pack Item. On PK-8 the event pair ev08 → ev10 replaces ev07 → ev10, so Pack Item → Dispatch Package keeps its activity-level frequency of two across packages. The Invoice graph gains Record Payment → Record Payment. B keeps these changes and adds Dispatch Package → Confirm Delivery on two Delivery traces. It also adds Add Item → Issue Invoice for ORD-B. The simultaneous dispatches themselves supply no directly-follows order in either bundle.

**OTG.** For a type graph based on stored O2O, count qualified directed edges. Package `packs` Item grows from two instances to three in A, and Payment `settles` Invoice from one to two. B additionally raises Delivery `carries` Package and Invoice `bills` Order from one to two each. These type pairs already exist. For an OTG based on event co-participation, A likewise strengthens existing type pairs. B introduces Order–Delivery at ev11. Both deliveries co-occur there and both orders co-occur at ev12, visible as same-type interactions if the graph retains them. Report the construction and weight convention, since a co-participation edge has no `carries` or `bills` semantics.

**ET–OT graph and frequencies.** All logs have 14 distinct events, including three Pack Item events and one Confirm Delivery. A increases the Pack Item–Package incidence count from two to three, but the number of unique packages packed stays two. For Record Payment–Invoice the incidence count rises from one to two while the unique invoice count stays one. B introduces Confirm Delivery–Delivery with one contributing event, two unique deliveries and two incidences. Issue Invoice–Order grows from one to two unique orders on one event. Across all activities the total E2O incidence counts are 22, 24 and 28 for raw, A and B. Thus event frequency, number of participating objects counted distinctly, and total object participations answer different questions.

**Equivalent executions around Order.** In the raw interaction graph the two order neighborhoods are disconnected. A joins them through IT-B1 and PK-8, and brings PAY-2 into the invoice neighborhood. B adds a shared invoice issue and connects the receipt to both shipments. A leading-Order extraction can consequently include shared events in both executions, depending on its traversal and stopping rules. Whole-component extraction can return one connected execution covering both roots after A. Rooted, type- and activity-preserving equivalence can still distinguish them by item count and direct confirmation. A shared component or common customer alone does not justify merging the order cases or predicting an exact cluster count.

## 7. PM4Py-oriented validation outline

The block assumes standard OCEL column names. It supplies the event and object metadata used in PM4Py's denormalized E2O table. Confidence and justification stay in the repair record above.

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

eid, oid, oid2 = "ocel:eid", "ocel:oid", "ocel:oid_2"
act, ts, typ, qual = "ocel:activity", "ocel:timestamp", "ocel:type", "ocel:qualifier"
original = tuple(df.copy(deep=True) for df in (events, objects, relations, o2o))
ev, ob, rel, links = (df.copy(deep=True) for df in original)

for df, key in ((ev, eid), (ob, oid)):
    assert df[key].notna().all() and df[key].is_unique, key
ev[ts] = pd.to_datetime(ev[ts], utc=True, errors="raise")
assert ev[[act, ts]].notna().all().all() and ob[typ].notna().all()

new_rel = pd.DataFrame(
    [("ev08", "PK-8", "package"), ("ev14", "INV-44", "invoice")],
    columns=[eid, oid, qual],
)
new_links = pd.DataFrame(
    [("PK-8", "IT-B1", "packs"), ("PAY-2", "INV-44", "settles")],
    columns=[oid, oid2, qual],
)
# These proposals add missing participants, never a second role for an existing pair.
assert rel.merge(new_rel[[eid, oid]], on=[eid, oid]).empty
rel = pd.concat([rel, new_rel], ignore_index=True)
links = pd.concat([links, new_links], ignore_index=True)

assert rel[eid].isin(ev[eid]).all() and rel[oid].isin(ob[oid]).all()
assert links[oid].isin(ob[oid]).all() and links[oid2].isin(ob[oid]).all()
assert not rel.duplicated([eid, oid, qual]).any()
assert not links.duplicated([oid, oid2, qual]).any()

event_index = ev.set_index(eid)
for col in (act, ts):
    rel[col] = rel[eid].map(event_index[col])
rel[typ] = rel[oid].map(ob.set_index(oid)[typ])
ev = ev.sort_values([ts, eid]).reset_index(drop=True)
rel = rel.sort_values([ts, eid, oid]).reset_index(drop=True)

# Version-dependent constructor and import path. Use the installed release's
# OCEL signature for events, objects, denormalized relations and qualified O2O.
ocel = OCEL(events=ev, objects=ob, relations=rel, o2o=links)
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
order_flat = pm4py.ocel_flattening(ocel, "Order")
delivery_flat = pm4py.ocel_flattening(ocel, "Delivery")
assert len(order_flat) == 7 and len(delivery_flat) == 1
```

## 8. Over-repair warnings

- Assigning ev10 to X solely by the 10:00 timestamp could give X two dispatches and create a tie-dependent Dispatch Package → Dispatch Package edge.
- Adding PK-8 to ev09 under the bulk exception could double-count its departure alongside ev10.
- Resolving the wildcard on ev11 to every northern delivery could turn one portal action into two apparent carrier confirmations.
- Propagating A's receipt through PK-8 to ORD-B could add Confirm Delivery to an order trace without a portal acknowledgment for that order.
- Splitting INV-44, or inventing individual invoice issues for each order, would inflate billing frequency. A genuine consolidated issue uses a single event ID.
- Allocating PAY-1 to B and PAY-2 to A on amount alone could create fictitious order-level settlement histories, even if both payments truly applied to INV-44.
- Automatically converting co-participation into persistent O2O could make the two jointly acknowledged deliveries look commercially related to one another. The receipt supports participation in that event only.
