def discover_batches(df, merge_distance_min, min_batch_size):
    md = pd.Timedelta(minutes=merge_distance_min)

        ("merge_distance", dict(merge_distance=merge_distance_min, min_batch_size=min_batch_size)),
        ("max_interval_interleaved", dict(max_interval_interleaved=md, min_batch_size=min_batch_size)),

        ("min_batch_only", dict(min_batch_size=min_batch_size)),
        ("bare", dict()),
    ]
    for name, kw in attempts:

            return pm4py.discover_batches(df, **kw), name, kw
        except TypeError:
            continue
        except Exception as ex:

def normalise_batches(res):
    """Return tidy df with columns: case:concept:name, batch_id (may be NaN)."""
    if res is None:
        return pd.DataFrame({"case:concept:name": [], "batch_id": []})
    if isinstance(res, pd.DataFrame):
        cols = [c for c in res.columns if "batch" in str(c).lower()]
        bcol = cols[0] if cols else None
        casecol = "case:concept:name" if "case:concept:name" in res.columns else None
        if bcol and casecol:
            out = res[[casecol, bcol]].rename(columns={bcol: "batch_id"})
        elif casecol:
            # log returned unchanged -> no batch annotation found
            out = res[[casecol]].copy(); out["batch_id"] = pd.NA
        else:
            out = pd.DataFrame({"case:concept:name": [], "batch_id": []})
        return out
    if isinstance(res, (list, tuple, set)):
        rows = []
        for k, item in enumerate(res):
            bid = f"B{k}"
            if isinstance(item, dict):
                ids = item.get("cases") or item.get("case_ids") or item.get("case:concept:name") or item.get("batch") or []
                if isinstance(ids, str): ids = [ids]
                for c in ids: rows.append((c, bid))
            elif isinstance(item, str):
                rows.append((item, bid))
            else:
                try:
                    for c in list(item): rows.append((c, bid))
                except TypeError:
                    pass
        return pd.DataFrame(rows, columns=["case:concept:name","batch_id"])
    return pd.DataFrame({"case:concept:name": [], "batch_id": []})

- waiting = arrivalT  upper bound on true waiting (true waiting = arrivaltrue start  T), inflated by the deferred-submission delay;
- service = 0  lower bound (0), deflated to the floor;
- utilization   service  0  the resource looks idle all day;
- throughput  1/service  infinite at T;
- bottleneck rankings by waiting vs by utilization give opposite answers for the same activity;
- conformance: zero-duration activities often violate minimum-duration rules, and their identical timestamps are flagged as batches;
- conformance/throughput counts at 17:00 create a 7-per-minute spike;
- mean cycle time is roughly preserved (arrivalT  true cycle time if the work truly happened at submission), so aggregate KPIs look fine while the decomposition is maximally wrong — the most dangerous case, because the totals validate while the split does not.

# 3. Consequences for performance analysis

Notation: *wait* = `start  queue_arrival`, *service* = `complete  start`, *naive utilisation* =  service ÷ (max complete  min start).

## 3.1 Per-cluster bias

**G1 (simultaneous fixture batch).** Waiting (6/5/4/2 min) is roughly trustworthy *if* the fixture-fill policy is the real gate, but items 2–4 may have been held upstream, so per-item waiting can be understated. Service is the real distortion: 3 min is **one cycle shared by four items**, so  service = 12 machine-minutes inside a 3-minute window  naive utilisation = **400 %**, while true machine utilisation is 100 %. Throughput (80 items/h) is correct for the cell, but any per-item cycle-time model either flags the cell as an impossible bottleneck (>100 %) or, if overlap is silently permitted, understates its capacity 4× and shifts the bottleneck wrongly downstream. Conformance: four identical traces on one resource violate one-resource-at-a-time assumptions  spurious deviations unless a batch activity/attribute is modelled.

**G2 (start batching).** Using the shared start 10:00 moves time from waiting into service: recorded waiting (18/14/11/6 min) is **understated** for items 2–4 (their true starts are later, e.g. 10:21 for item 4  true wait 27 min vs recorded 6), while service is **inflated** (8/14/21/27 min, mean 17.5, versus a serial ceiling of 27 min of work in a 27-min window  mean  6.75 min; inflation  2.6×). Utilisation = 70 ÷ 27 = **259 %** on one inspector  either an impossible resource load or an invented second inspector. The monotone rise 827 min is a *stamping* artefact that can be misread as a learning-curve reversal. Throughput from completions (4 per 27 min) stays valid. Bottleneck detection over-flags inspection; headcount-based capacity planning is wrong in both directions.

**G3 (end batching).** Waiting from staggered starts (22/18/19/19 min) is roughly right, so waiting-based rankings are only mildly affected. Service is inflated for the *early* items (28/20/13/6 min) and produces a fake "later items are faster" trend, plus a fake convergence of sojourn time (50/38/32/25 min). Utilisation = 67 ÷ 28 = **239 %** on one reviewer. Throughput is fine, but downstream the four items genuinely arrive together at 11:30 — so *downstream* waiting must use 11:30 as the release instant, while *upstream* cycle-time work must not use these ends. Conformance: minimum-duration rules pass spuriously for the last item and fail for the first.

**G4 (sequential run).** The one cluster where waiting is trustworthy: 7/10/13/16/19 min with a strict +3 min step is exactly FIFO behaviour when arrivals (1/min) exceed service (0.25/min); backlog peaks at 5. Service has **zero variance** (all 4 min), which collapses the tail: P95 = mean = 4 min, so SLA risk is invisible, and if the stamps are standard rather than measured the whole service distribution is uninformative. Utilisation = 100 % with no idle gap  almost certainly **overstated**, because setup/idle between items is not recorded. Bottleneck detection correctly identifies packing, but the unexplained 11:5812:05 gap is a hidden capacity-loss or unlogged-prior-task that, if ignored, misattributes the queue's origin.

**G5 (shared account).** Waiting (~15 min, flat) is valid at *pool* level and meaningless at *person* level. Service (25/15/20/10 min) includes whatever idle time the open window contained  overstated if windows are open-state. Utilisation is entirely a resource-definition choice: as one lane, 70 ÷ 30 = **233 %** (invalid); as a 3-analyst pool, 70 ÷ 90 = **78 %** (plausible) — yet 4 concurrent open windows still exceed 3 analysts. Throughput at pool level is fine; per-analyst productivity is not identifiable at all. Conformance: overlapping activities for a single resource generate spurious alignment deviations.

**G6 (bulk stamp).** Covered in detail in §3.2.

**G7 (coarsened).** Waiting is *invalid*: 4 of 5 values are negative (1/4/7/9 min). A naive pipeline either drops them — silently deleting the four latest-arriving items and leaving a mean wait of 2 min from M01 only, a severe downward bias — or clamps them to 0, also downward. Service is exactly one quantum (15 min): variance destroyed. Under round-down/round-down with a 15-min quantum, true service per item  [recorded  15, recorded + 15] = **[0, 30] min** — 100 % relative uncertainty. Utilisation = 75 ÷ 15 = **500 %**, unusable; under censoring, true utilisation for one operator is bounded above by 100 % and below by nothing useful  **non-identifiable**. Coarsening also erases micro-idle and micro-queue, so bottleneck severity is understated and no sub-15-min claim is supportable.

**G8 (capacity loss + serial run).** Waiting (3858 min, mean 48) is inflated by ~30–35 min of stop time. Unless the stop is decomposed out, improvement work will blame staffing or demand instead of the capacity loss. Service (7 min × 5, variance 0) has the same tail-collapse problem as G4. Utilisation is 100 % from 15:38–16:13; including the safety check it is (35+35)÷73 = **96 %** — but this number depends on clock alignment between two systems, so it carries an unknown minutes-level error. Bottleneck: after the stop the station is genuinely the constraint (arrival 0.63/min vs service 0.14/min), but the *initial* 38-min wait is a stop, not a queue.

## 3.2 Why G6-like data creates both inflated waiting and near-zero service

A single bulk transaction writes *N* rows with `start = complete = T` (here T = 17:00, N = 7, `recorded_at` = 17:01, source `manual_bulk_form`). Total residence time (arrival  T) is **conserved**, but it is decomposed maximally:

1. **Waiting** becomes arrival  T: an upper bound on true waiting, inflated by exactly the deferred-submission delay (mean 103 min, max 175 min, monotone decreasing 17535 — the signature of everyone being pulled to one stamp).
2. **Service** becomes `complete  start` = 0: a lower bound pinned to the floor of the scale.
3. **Utilisation** (  service)  **0 %**, so the resource looks idle all day.
4. **Throughput** ( 1/service)  formally *infinite*, or 7 events per minute at 17:00 — an instantaneous spike no physical step can produce.
5. **Bottleneck ranking splits**: by waiting, "Close ticket" is the worst queue in the dataset; by utilisation/cycle time, it is the *best* step (zero service, infinite capacity). The same cluster therefore appears simultaneously as the top queue and as a non-bottleneck — the contradiction is manufactured by the waiting/service split, not by the process.
6. **Conformance** breaks in both directions: zero-duration activities violate any minimum-duration rule, while their identical timestamps fire batch detectors.
7. Most dangerously, **aggregate KPIs still look right**: arrival  17:00  true cycle time if the work really happened at submission, so totals validate while the decomposition does not.

If instead the substantive work was done earlier in the day and only *submitted* at 17:00, waiting is inflated **and** service is understated simultaneously; if the work genuinely happened at 17:00 in a burst, waiting is largely real but still contaminated by the deferred start stamp. Under both readings the waiting/service split is unusable — only the sojourn time survives.

def pair_stats(g):
    g = g.sort_values("sequence_no")
    s, e = g["start"].to_numpy(), g["complete"].to_numpy()
    n, pairs, se, ee, ov = len(g), 0, 0, 0, 0
    for i in range(n):
        for j in range(i+1, n):
            if pd.isna(s[i]) or pd.isna(s[j]): continue
            pairs += 1
            if s[i] == s[j]: se += 1
            if e[i] == e[j]: ee += 1
            if max(s[i], s[j]) < min(e[i], e[j]): ov += 1

              if pd.notna(e[i]) and pd.notna(s[i+1]) and e[i] == s[i+1])
    return dict(start_equal_rate=se/max(pairs,1), end_equal_rate=ee/max(pairs,1),

def max_open_concurrency(g):
    ts = pd.Series(sorted(set(g["start"].dropna()) | set(g["complete"].dropna())))
    best, when = 0, None
    for t in ts:
        c = int(((g["start"] <= t) & (t < g["complete"])).sum())
        if c > best: best, when = c, t
    return best, when

                wait_monotone_inc=bool(w.is_monotonic_increasing),
                wait_monotone_dec=bool(w.is_monotonic_decreasing),

def granularity(g, col):
    v = g[col].dropna()
    if v.empty: return np.nan, np.nan
    nonzero_sec = int((v.dt.second != 0).sum())
    gaps = v.sort_values().diff().dt.total_seconds().dropna()
    return nonzero_sec, (gaps.min() if len(gaps) else np.nan)

def categorise(d):
    if d.neg_waits > 0 and d.precision_s >= 900: return "coarsened (impossible ordering)"
    if d.zero_dur == 1 and d.end_equal == 1:     return "zero-duration bulk stamp"
    if d.start_equal == 1 and d.end_equal == 1:  return "start+end equality (simultaneous OR single stamp)"
    if d.start_equal == 1:                       return "start-side batch (common setup)"
    if d.end_equal == 1:                         return "end-side batch (common completion)"
    if d.adj == 1 and d.overlap == 0:            return "sequential back-to-back (no overlap)"
    if d.overlap > 0 and d.shared:               return "overlap under shared account"
    if d.overlap > 0:                            return "overlap (concurrency or inflated windows)"
    return "no batch pattern"

def temporal_claim(spread_s, prec):
    if pd.isna(spread_s): return "n/a"
    if spread_s == 0:     return "equal within precision" if prec <= 60 else "NOT identifiable (precision > 60 s)"
    return "distinct" if spread_s > prec else "NOT identifiable (spread <= precision)"

# 5. Robustness and alternative explanations

## 5.1 Resource IDs trusted vs treated as shared accounts

| cluster | if IDs are trusted (one actor per ID) | if IDs are treated as shared / multi-actor | what actually changes |
|---|---|---|---|
| G1 | One machine  the 4 equal windows *must* be a machine-level batch (a single lane cannot run 4 tasks) | If RBT-7 were a station tag covering several cells, 4-way equality could come from 4 cells finishing together | Identity barely matters; **capacity metadata** (fixture positions) decides the interpretation |
| G2 | 4 overlapping windows on one inspector are impossible  the common start *must* be a stamping artefact | A multi-inspector account makes 4-way simultaneous inspection physically possible  "genuine simultaneous batch" becomes defensible | Changes whether service times are repaired (interval-censored) or accepted; changes headcount-based capacity |
| G3 | Overlap impossible on one reviewer  end stamping confirmed | Concurrent reviews with a shared release milestone becomes possible | Changes whether 11:30 is treated as a data artefact or as a real release event downstream |
| G4 | One packer  adjacency is genuine serial work; utilisation is that person's utilisation | A shared station tag  two packers at one scanner; the perfect adjacency becomes coincidence, and true utilisation 50 % | Changes utilisation and bottleneck severity, not waiting |
| G5 | **Impossible**: 4 open windows  1 analyst  data error | Pool-level metrics only: utilisation 70 ÷ 90 = 78 % of 3 analysts; per-analyst values unidentifiable; 4 > 3 still requires multitasking or open-idle | Changes everything about resource performance; waiting stays valid at pool level |
| G6 | 7 simultaneous closures on T-F  bulk artefact | Still a bulk artefact (all stamped 17:00) | **Identity-invariant**: the conclusion does not depend on identity |
| G7 | 5 simultaneous manual measures by one operator  coarsening | Simultaneity would be possible, but the 4 negative waits still prove coarsening/clock trouble | **Identity-invariant**: coarsening stands |
| G8 | One triage lane  serial, and no triage during the safety check | Several lanes at one station  triage could have run *during* 15:00–15:35, wiping out the capacity-loss explanation | Changes whether G8's top explanation survives |

Overall: the conclusion flips for **G2, G3, G4, G8**; it is refined (not flipped) for **G1, G5**; and it is identity-invariant for **G6, G7**. Resource-identity reliability therefore ranks: PLC/scanner  desktop/tablet  `shared_VDI`.

|---|---|---|---|

## 5.3 Three-plus cases where one temporal pattern supports several physical explanations

1. **All-equal start and end (G1, G6, G7).** (a) genuine simultaneous batch — a 4-position fixture processed in one cycle; (b) bulk submission — one human action stamping seven rows; (c) quantization — five serial events collapsed into one 15-min window. *Discriminating evidence:* declared precision (1 s vs 1 min vs 15 min), the `recorded_at` pattern (G1: 2–3 s lag in two ticks; G6: one minute-level value; **G7: a 60300 s lag gradient against a flat complete — the fingerprint of serial work hidden by rounding**), logical ordering (only G7 violates it), and operational metadata (fixture capacity, form type, rounding rule).
2. **Common start, staggered end (G2).** (a) start batching via a "begin group" button; (b) rounding of four different starts into one minute; (c) a genuine scheduled group start (a route/shift starting at 10:00); (d) a genuine simultaneous batch with staggered releases. *Discriminating evidence:* per-row `recorded_at` (present, distinct  the ends were written individually), end spread  precision (6–7 min gaps  60 s), and whether other groups also start exactly at 10:00 (cross-cluster check not available in the supplied fragment).
3. **Staggered start, common end (G3).** (a) bulk submission after finishing a folder; (b) a real shared completion milestone (folder release); (c) rounding of four ends into one minute. *Discriminating evidence:* the monotone duration collapse (28/20/13/6), the half-hour boundary, the operator's statement, and whether other activities also end at 11:30. 4. **Overlap on a single resource (G2, G3, G5).** (a) true concurrency behind one account; (b) shared-account artefact; (c) open-but-paused windows (no pause/resume events recorded); (d) inflated windows produced by batching at one or both ends. *Discriminating evidence:* badge identity, documented pool capacity (G5 fails it: 4 > 3), and pause events (absent everywhere).

# 6. Data-collection redesign

**P0 — without these, waiting, service and concurrency are not identifiable**

1. **Execution timestamps per item, from the controller/source.** True per-item `exec_start`/`exec_end` for the automated cell (G1: per item on the fixture, not per cycle), per item rather than per group for inspection (G2), per review rather than per folder for release (G3), and per ticket for closure (G6). Never let a form default write `start` from a submission action.
2. **Group / batch identifiers as first-class data.** `fixture_id`, `group_id`, `folder_id`, `submission_id`, `batch_id`, plus `batch_size` and `batch_type` (physical / operational / logging). Batches must be *declared objects*, not inferred from equal timestamps — this single field resolves G1, G2, G3 and G6 at once.
3. **Resource and actor identity separated.** Store `account_id` and `actor_id` (badge/NFC) in different columns, never a shared login as the sole key; publish a pool-membership table with capacity over time (G5). Scanner/tablet users must badge in per event.
4. **Source-clock discipline.** One time base (NTP/PTP) or a per-source `clock_offset_ms` recorded *with each event*, plus the source clock ID; retain both source and server timestamps. This is the only way to decide whether G8's 15:3515:38 gap is real.
5. **Timestamp precision metadata that is machine-readable.** `precision`, `resolution`, `rounding_rule` (down / up / nearest / floor-to-bucket), `timezone`, `derived_flag` — per field, not per source. G7 is uninterpretable without the rule; G1/G4/G8 need it because declared 1 s conflicts with observed whole-minute lifecycle values.

**P1 — needed for trustworthy queue and utilisation analysis**

6. **Recording timestamps with transaction identity.** Keep `recorded_at`, add `insert_txn_id` so a bulk write is provably one transaction (this would settle the A1 ambiguity in G3/G6) and add `recorded_by_service`.
7. **Pause / resume / interrupt events with reason codes**, including planned stops (safety check, maintenance, break) and their begin/end — the only way to separate *capacity-loss waiting* (G8) from *queue waiting*, and to split open windows from busy time (G5).
8. **Workstation capacity as versioned configuration**: parallel positions per station, fixture capacity, pool size, number of active lanes. Utilisation cannot be interpreted without a denominator.
9. **Queue lifecycle events**: `arrive`, `dispatch`, `blocked(reason)`, `start`, `end`, so waiting can be decomposed into *waiting-for-capacity*, *waiting-for-setup* and *waiting-for-material* instead of one number (G4's unexplained 11:5812:05 gap).

**P2 — hygiene and auditability**

10. **Never substitute a default for an unavailable lifecycle field.** Blank start must stay blank with an explicit `start_unavailable` flag rather than being filled with the submission time.
11. **Retain raw and derived values side by side** (`start_raw`, `start_rounded`, `rounding_applied`), keep `sequence_no`, and log bulk edits with actor, timestamp and before/after values.
12. **Continuous data-quality checks in the pipeline**: negative waiting, `start < queue_arrival`, zero durations, overlap on a single-lane resource, declared-vs-observed resolution mismatch, and lag gradients — all eight clusters here would have been caught automatically.

# 7. Final adjudication

**High confidence (interpretable now, with the stated caveat)**

- **G6 — 95.** High confidence *as a logging artefact*: zero durations, a single stamp, a source literally named `manual_bulk_form`, and monotone decreasing waits toward one instant. Its *physical* meaning (was there work at all, and when?) remains unknown, but no performance metric should be built from its service field.
- **G7 — 90.** Coarsening is proven by the impossible ordering (4 negative waits) and by the `recorded_at` lag gradient (60300 s) against a flat complete value. Under a round-down rule the rows reduce to defensible intervals; without the rule they remain intervals of ±15 min.
- **G1 — 85** *at fixture level*: simultaneous execution of four items on one fixture is consistent with every observation. The residual uncertainty is provenance (one cycle stamp copied to four rows) and the whole-minute alignment under a declared 1-second precision.
- **G4 and G8 (structure) — 80 / 75.** Waiting-time *shape* is trustworthy: FIFO growth in G4 (+3 min per item), and a capacity-loss gap followed by an overloaded serial run in G8. Exact durations (all 4 min, all 7 min, zero variance) are not trustworthy until provenance is confirmed.

**Exclude from, or interval-censor in, queue analysis**

- **G6:** exclude entirely from service-time, utilisation and cycle-time-per-step statistics; represent `start` as the interval [queue_arrival, 17:00] and keep only sojourn time as a point estimate.
- **G7:** exclude from any waiting-time statistic (4 of 5 values are impossible) and from all simultaneity claims; interval-censor both lifecycle fields by the 15-min quantum and intersect with the logical constraint `start  queue_arrival`.
- **G3:** censor `complete` to an upper bound; use 11:30 as the *release* instant for downstream analysis, never as per-item service end.
- **G2:** censor `start` to a group-open marker; compute service only from completion-to-completion differences.
- **G5:** keep at pool level only; exclude from per-analyst utilisation, per-worker productivity and any one-resource-at-a-time conformance rule.

**Requires operational validation before any performance conclusion**

- **G1:** confirm whether the PLC writes one timestamp pair per *cycle* or per *item*, and confirm fixture capacity — this decides between "genuine simultaneous batch" and "single observation replicated four times", and therefore whether machine utilisation is 100 % or 400 %.
- **G2:** confirm the semantics of the "begin group" button (does it stamp an execution start or open a group?) and how many inspectors share T-B.
- **G3:** confirm whether 11:30 is a genuine folder-release milestone or a submission instant; this decides whether the step's service time is 6–28 min or ~unknown.
- **G4 and G8:** confirm whether the constant 4-min / 7-min durations are measured or standard values (auto-stamp hypothesis), and obtain the setup/idle record between items.
- **G5:** obtain badge-level identity and a pool-capacity history; also determine whether recorded windows are busy-state or open-state — required to reconcile 4 open windows with a 3-analyst pool.
- **G8:** obtain clock offsets between the safety system and the repair queue before asserting either overlap or gap around 15:35–15:38; annotate the stop with a reason code so waiting can be decomposed.

**Bottom line:** identical timestamps are a *measurement* fact, not an execution fact. G1, G6 and G7 produce byte-identical equality patterns for three entirely different physical reasons; only G4 and G8 support waiting-time analysis as-is; and every cluster except G4/G8 must be interval-censored or operationally validated before any bottleneck, utilisation or service-time conclusion is published.
