## 1. Temporal Data Semantics

**State Reconstruction:**
*   **Forward-Filling:** Attributes (`amount`, `risk_level`, `jurisdiction`, `customer_type`, `exemption_id`) are reconstructed per case by forward-filling the latest non-blank value observed up to the current event. Blank cells in the CSV denote "no update at this event," not nullification.
*   **Event Ordering:** Events are ordered primarily by `time:timestamp` (UTC) and secondarily by `event_index` for ties. When `event_index` differs at the same timestamp, the lower index occurs first.
*   **Material Changes:** An update to `amount`, `risk_level`, `jurisdiction`, or `customer_type` constitutes a material data change. The change is effective at the event timestamp unless the note explicitly states a different effective time (none found in this log).
*   **Final Attributes:** The final state of a case is **not** projected backward. Obligations at `Release_Funds` are evaluated against the state known at that specific timestamp. Post-release events (e.g., `Settlement_Confirmed`, `Record_Exemption` inserts) do not retroactively validate or invalidate pre-release obligations unless they provide evidence of a state that existed earlier (see Exemption Evidence).
*   **Time Distinctions:**
    *   *Event Time:* When the event occurred in the system.
    *   *Effective Time:* When a value became active (usually Event Time).
    *   *Record Time:* When data was logged (e.g., `Record_Exemption` at 11:00).
    *   *Evidence Time:* Timestamps from signatures, certificates, or notes used to infer historical state (e.g., signature timestamp 09:05 vs. DB insert 11:00).

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **R1** | `Release_Funds` AND `jurisdiction != DE` AND `amount >= 100,000` | `Enhanced_Review` | `latest_material_change < Enhanced_Review < Release_Funds` | State at `Release_Funds` | Valid Exemption (waives R1) | If amount missing, INDETERMINATE | Exemption scope, approval time, expiry |
| **R2** | `Release_Funds` AND (`risk_level == HIGH` OR `customer_type == PEP`) | `Enhanced_Review`, `Compliance_Approve` | `latest_material_change < Enhanced_Review < Compliance_Approve < Release_Funds` | State at `Release_Funds` | None | If risk/cust missing, INDETERMINATE | N/A |
| **R3** | `Sanctions_List_Update` adds jurisdiction `J` | `Sanctions_Screen` | `Sanctions_List_Update < Sanctions_Screen < Release_Funds` | State at `Release_Funds` | None | N/A | N/A |
| **R4** | `Update_Amount` increases amount by > 20% vs. pre-change amount | Invalidates prior `Standard_Review`/`Enhanced_Review` | N/A (Effect is invalidation) | State at `Update_Amount` | None | Increase from unknown is INDETERMINATE | N/A |
| **R5** | Exemption claim at `Release_Funds` | Exemption record in register | `effective_from <= Release_Funds` AND `expiry > Release_Funds` | State at `Release_Funds` | N/A | N/A | Approval by Head_Compliance, evidence of approval existence at trigger time |
| **R6** | Missing decisive attribute | N/A | N/A | State at event | N/A | Classify INDETERMINATE if trigger cannot be established/excluded | N/A |
| **R7** | General evaluation | N/A | N/A | Latest known value at event | N/A | N/A | N/A |

**Formal Pseudo-Logic:**

```datalog
% R1: Foreign high-value enhanced review
r1_violation(C) :-
    release(C, T),
    jurisdiction(C, T) != 'DE',
    amount(C, T) >= 100000,
    not valid_exemption_waives_r1(C, T),
    not enhanced_review_after_material_change(C, T).

enhanced_review_after_material_change(C, T) :-
    enhanced_review(C, T_rev),
    latest_material_change(C, T_mat),
    T_mat < T_rev,
    T_rev < T.

% R2: High-risk or PEP approval
r2_violation(C) :-
    release(C, T),
    (risk_level(C, T) == 'HIGH'; customer_type(C, T) == 'PEP'),
    not (enhanced_review(C, T_e) ; compliance_approve(C, T_c)),
    not (T_e < T_c).

% R3: Sanctions-list update
r3_violation(C) :-
    sanctions_list_update(C, T_u, J),
    jurisdiction(C, T_u) == J,
    release(C, T),
    T_u < T,
    not sanctions_screen_after_update(C, T_u, T).

sanctions_screen_after_update(C, T_u, T) :-
    sanctions_screen(C, T_s),
    T_u < T_s,
    T_s < T.

% R4: Material amount change
invalidates_review(C, T_inv) :-
    update_amount(C, T_u),
    amount(C, T_prev) > 0,
    amount(C, T_u) > amount(C, T_prev) * 1.2,
    T_inv = T_u. % Marks reviews before T_u as invalid for amount obligations

% R5: Exemption validity
valid_exemption(C, T_rel, EID) :-
    exemption_record(EID, scope_j, scope_ct, scope_amt, effective_from, expiry),
    jurisdiction(C, T_rel) == scope_j,
    customer_type(C, T_rel) == scope_ct,
    amount(C, T_rel) <= scope_amt,
    effective_from <= T_rel,
    expiry > T_rel,
    approved_by_head_compliance(EID),
    evidence_of_approval_at(EID, T_rel).

% R6: Missing data handling
indeterminate(C, Rule) :-
    release(C, T),
    missing_attribute(C, T, attr),
    rule_requires_attr(Rule, attr),
    not other_evidence_resolves(C, attr).
```

## 4. Ambiguities and Alternative Readings

*   **TX-302 (JUSTIFIED_EXCEPTION):** If the documented outage were not verifiable, the late DB insert would cast doubt on the exemption's existence at release. However, the qualified digital signature timestamp (09:05) provides independent evidence of approval prior to release, resolving the ambiguity.
*   **TX-305 (INDETERMINATE):** If business policy allows `Settlement_Confirmed` amount to serve as a proxy for `Release_Funds` amount, the case could be re-evaluated. With amount=150k, R1 would trigger. However, R6 prohibits copying final states backward, and the settlement event is distinct. The classification remains INDETERMINATE unless release payloads are recovered.
*   **TX-310 (NONCOMPLIANT):** The exemption evidence is contradictory. The PDF shows approval at 08:50, but the certificate was created at 10:30. If the certificate creation time reflects when the key was generated but the signature was applied earlier (e.g., offline signing), the exemption might be valid. However, the witness is the transaction requester, which is a conflict of interest. If an independent witness confirmed oral approval by Head_Compliance, the case could shift to JUSTIFIED_EXCEPTION.
*   **TX-311 (COMPLIANT):** Event index 3 (Ench_Review) precedes index 4 (Update_Jurisdiction to DE). If index 4 preceded index 3, the jurisdiction would be DE at the time of the review. Since R1 is waived by DE jurisdiction, the ordering does not affect the outcome. The case is robustly COMPLIANT.
*   **TX-306 (COMPLIANT):** R1 requires Enhanced_Review "after the latest material data change." The amount update at 12:30 is a material change. The Enhanced_Review is at 12:15. Strictly, the review is before the change. However, R4 states increases >20% invalidate reviews. The increase is 4.5%. The interaction suggests R4 defines the threshold for "materiality" that breaks a review. Since the change is below threshold, the review is deemed sufficient, and R1's temporal constraint is satisfied by the review's continued validity.

**Why Control-Flow-Only Conformance Is Insufficient:**
The code above demonstrates that while control-flow checks can verify event ordering, they fail to capture the substantive compliance rules. For example, a case could have perfect control flow (Create -> Review -> Release) but still violate R1 if the review is before an amount update, or violate R2 if the risk is PEP but only a standard review exists. Control-flow conformance cannot evaluate attribute thresholds, temporal constraints relative to data changes, or exemption validity.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1.  **Final-State Leakage:** Control-flow tools often assume attributes are static. They may incorrectly validate a case using the final jurisdiction (e.g., TX-311 DE) to check a rule that should have been evaluated at an earlier timestamp when the jurisdiction was different.
2.  **Post-Hoc Exemptions:** A case might have a valid exemption recorded after release. Control-flow conformance might flag the absence of an exemption event before release as non-compliant, missing the nuance that the exemption was effective earlier (as in TX-302).
3.  **Material Changes After Review:** Control-flow sees `Update_Amount` and `Enhanced_Review` as independent events. It cannot detect that the review occurred before the update and is therefore stale for amount-dependent obligations (TX-301, TX-309).
4.  **Conditional Activation:** Rules like R1 and R2 depend on attribute values (amount, risk). Control-flow cannot evaluate `amount >= 100000` or `risk == HIGH`. A case with low risk might be flagged as needing enhanced review if the model doesn't account for conditions.
5.  **Missing Data:** Control-flow cannot handle missing amounts. It might assume a default or fail to trigger rules, leading to false positives or negatives. R6 requires INDETERMINATE classification, which control-flow conformance cannot produce.
6.  **Same-Timestamp Ordering:** Rules depend on `event_index` for ties (e.g., TX-311). Control-flow tools may randomize order or ignore indices, potentially reversing the jurisdiction update and the review, altering the outcome.

## 7. Recommended Logging and Control Improvements

*   **Immutable Release Payloads:** Capture the exact amount, risk, jurisdiction, and customer type at `Release_Funds` in an immutable log entry. This prevents ambiguity about the state at release.
*   **Effective/Record/Signature Timestamps:** Log separate fields for `effective_time`, `record_time`, and `signature_timestamp`. This distinguishes when a value changed, when it was logged, and when evidence was generated.
*   **Rule Versioning:** Include `rule_version` in exemption records and review events to handle policy changes over time.
*   **Exemption Scope Granularity:** Store exemption scopes as structured data (JSON) with explicit fields for `waives_rules`, `max_amount`, `jurisdictions`, etc., to enable automated matching.
*   **Change Provenance:** Log `updated_by` and `reason` for attribute updates. Include a `previous_value` field in updates to facilitate R4 calculations without forward-filling ambiguity.
*   **Stable Event Ordering:** Enforce unique, monotonically increasing sequence numbers for all events across the system, not just within cases, to resolve cross-case or system-level ordering issues.
