Events with identical timestamps without an index are **infeasible to order automatically**; the suite marks them as "ambiguous" and requires manual resolution or index availability before use.

2. **Prefix-time availability check** (feature-level)  
   - For each feature, define its "defining timestamp": the latest event time required to compute the feature value (e.g., `total_case_duration_hours` needs closure time; `num_requests_up_to_t0` needs max request timestamp  t0).  
   - Validate: `defining timestamp  t0`? If no, reject feature for prefix prediction.  
   - Example: `queue_length_at_t0` passes if snapshot timestamp  t0; otherwise use prior snapshot. `prior_claim_count_before_t0` passes only if `claim_created_at < t0_timestamp`.

3. **Activity-order feasibility check** (prefix-level)  
   - At t0 (immediately after `Coverage Check Completed`), the **enabled** events are:  
     - Must have: `Claim Registered`, `Coverage Check Completed`.  
     - May have (could have occurred  t0): `Damage Assessment Completed` (in fast track), `Documents Requested`/`Documents Received`/`Documents Validated` (in progress), `Fraud Investigation Opened` (if trigger met).  
     - **Impossible** at t0: `Settlement Decision Recorded` (step 5), `Appeal` (step 7), `Claim Closed` (step 8).  
     - Future-possible: `Appeal` or `Second Settlement Decision` may occur later, but **cannot be claimed as occurred or imminent at t0** in explanations.  
   - Check local/sequence explanations:  
     - Flag if they state an impossible event occurred at t0 (e.g., "final_decision = Partial", "Claim Closed  DM pattern").  
     - Flag if pattern nodes include impossible events (e.g., `Claim Closed` in pattern).  
     - Allow pattern nodes only if both events’ timestamps  t0 (e.g., `Damage Assessment Completed  Settlement Decision Recorded` only if `Damage Assessment Completed`  t0).

4. **Same-timestamp ambiguity handling**  
   - If two events have identical timestamps (e.g., `Claim Closed` and `Damage Assessment Completed`) and no sequence index is present, **do not infer order**. Mark the case as "ambiguous for pattern validation".  
   - Validations:  
     - Reject patterns using such pairs (e.g., `Claim Closed  DM`) for automatic validation at t0.  
     - In explanations, avoid claiming order (e.g., do not say "Claim Closed happened before DM"; say "both occurred around the same time if data allows, but order unknown").  
   - Limitation: Process may logically constrain order (e.g., DM must precede Settlement), but without index, validation cannot resolve; require index in data pipeline for pattern use.

5. **Complete-trace feature detection**  
   - For each global/local feature, check if its definition depends on events after t0 (e.g., `full_trace_variant_id`, `total_case_duration`). The suite has a rule-based detector: if feature name contains "total", "variant", "snapshot" (without timestamp qualifier), or lineage note says "calculated after closure", flag as potential leakage. Cross-check with defining timestamp check.

6. **Repeated Settlement Decision validation**  
   - Only the **first** `Settlement Decision Recorded` (step 5) can occur  t0. The **second** `Settlement Decision Recorded` (after appeal) must occur after `Appeal` and thus after t0 (since appeal  step 7 > step 2).  
   - In explanations:  
     - Allow "appeal possible" or "appeal may trigger reconsideration" (future-possible, not certain).  
     - Never say "appeal causes breach" or "appeal  decision will be X" at t0.  
     - Sequence pattern `Appeal  Settlement Decision Recorded` is invalid at t0 if it refers to the second decision; only allow `Damage Assessment Completed  Settlement Decision Recorded` (first decision) if Damage Completed  t0.

7. **Execution workflow**  
   - On prediction request for a case:  
     1. Extract prefix (events  t0) using sequence index; flag missing index for same-timestamp pairs.  
     2. Run availability check (defining timestamp  t0).  
     3. Run activity feasibility check: list enabled/impossible events; reject explanations mentioning impossible events.  
     4. Run pattern check: allow pattern only if both nodes  t0 and no impossible nodes (e.g., no `Claim Closed`).  
     5. Output: "valid prefix", "flagged ambiguities" (e.g., missing index), "invalid features/patterns", and "safe explanation rules" (no causal claims about future).  
   - Limitation: The suite checks consistency with the **normative process** (steps 1–8), not all possible organizational nuances (e.g., "fraud runs parallel" may allow early Fraud Opened). It does not validate fairness; that is separate (see Section 5). It is lightweight (SQL/Python rules), testable per case, and auditable.

> **Why this works**: It directly enforces "only information available at or before t0" via defining timestamps, checks logical process feasibility (no Settlement Recorded at t0), handles same-timestamp uncertainty without over-constraining (flags ambiguity), and validates pattern usage node-by-node. It avoids assuming causal rules (e.g., "queue causes delay"); it only checks if the pattern/feature could plausibly exist in the prefix per steps 1–8.

> **Boundary rules for explanations**:  
> - Always use "may", "typically", "often", "based on historical patterns" for predictive associations. Avoid "causes", "guarantees", "because", "due to [protected/social factor]".  
> - Never say an event "will" or "must" happen at t0 (e.g., "appeal will cause breach"; correct: "appeal may trigger a second settlement decision later").  
> - Operational actionability: explanations can note "high queue may reduce capacity" for awareness; they cannot say "assign X staff now" as a model recommendation (actionability requires domain-specific policy; model only predicts breach risk).  
> - Fairness: proxies (region, week) are kept for prediction if useful, but explanations must not imply discriminatory causation. Fairness review (Section 5) checks for disparate impact post-prediction.

## 5. Recommendations for explanation validation

Prioritized, actionable plan (implement in order; monitor continuously):

1. **Feature store hardening (Week 1–2)**  
   - Require every feature to store `feat_min_time` (earliest event needed) and `feat_max_time` (latest event needed) with timestamps. For mutable features (e.g., risk score), require `feat_snapshot_time`  prediction time when used, and store version ID.  
   - Add automated check at ingestion: `feat_max_time  t0` must hold for prefix queries. Reject or flag features where `feat_max_time` depends on closure/appeal (e.g., `total_case_duration`).  
   - For "total"/"variant"/"snapshot" features, require a prefix counterpart (e.g., `total_case_duration`  `prefix_max_duration_estimate` computed from prefix only; document uncertainty).

2. **Prefix-only feature pipeline (Week 1–3)**  
   - Build a dedicated "prefix feature job" that, given `t0` (from first `Coverage Check Completed`), computes all features using only events  t0 and `feat_min_time`/`feat_max_time` checks. Do not join complete-trace fields (e.g., `full_trace_variant_id`).  
   - Test with "what-if" cases: inject same-timestamp events without index; pipeline should flag ambiguity or use safe defaults (e.g., `Documents Requested` before `Documents Received`).  
   - Integrate this pipeline into the prediction service; never use full-trace features at t0 prediction time.

3. **Process-conformance validation suite (Week 2–4, automated)**  
   - Deploy the consistency checks from Section 2 as a lightweight API/unit test per case:  
     - Extract prefix; validate `feat_max_time  t0`.  
     - Check enabled/impossible events (no Settlement Recorded/Appeal at t0 in prefix).  
     - Validate patterns: both nodes  t0 and no impossible nodes.  
     - Flag missing sequence index for same-timestamp pairs.  
   - Run this suite on 100% of predictions; fail prediction explanation generation if it references an impossible event or uses a leaked feature.  
   - Log "ambiguous" cases (missing index) for manual review; require index availability in data pipeline for pattern use.

4. **Explanation template & language guardrails (Week 2)**  
   - Create a short internal style guide for local/global explanations:  
     -  Use: "typically requires", "may indicate", "may reduce capacity", "based on historical patterns", "observed at t0".  
     -  Avoid: "causes", "guarantees", "because [social/policy factor]", "will happen", "must occur", "due to X".  
     -  For proxies (region/week): "may vary by region based on historical patterns; monitor for fairness impact".  
     -  For uncertainty: "at t0 we observe X; Y may contribute because of typical process needs".  
   - Add a lint step in explanation generation that scans for forbidden phrases (e.g., "causes", "will") and suggests safe wording. Train model team on examples (e.g., replace "appeal causes breach"  "appeal may trigger a second settlement decision later").

5. **Fairness & proxy review (ongoing, start Week 3)**  
   - For every proxy feature (`calendar_week`, `claimant_region`, `queue_length` if correlated), run a monthly fairness check:  
     - Compute breach prediction distribution by protected attributes (e.g., region subgroup vs majority).  
     - Check for demographic parity lift (>10% difference) or disparate impact (>80% of majority rate).  
     - If lift > threshold, investigate: is proxy correlated with policy change (e.g., week 52 holiday)? If yes, note in metadata; if no, consider removing or adjusting feature weight.  
   - Use process-aware fairness: e.g., if region R4 has higher breach rate only during holiday weeks, the proxy is legitimate for week; but if region bias persists across weeks, flag for review.  
   - Do not remove proxies automatically; review evidence (process docs + data). Fairness review is separate from leakage audit (leakage is temporal; fairness is attribute-based).

6. **Pattern validation refinement (Week 3–4)**  
   - Only allow sequence patterns where both nodes have timestamps  t0 (e.g., `Damage Assessment Completed  Settlement Decision Recorded` if Damage Completed  t0).  
   - Do not store or use patterns that include `Claim Closed`, `Appeal`, or other post-t0 nodes.  
   - For same-timestamp pairs (e.g., Claim Closed & DM), require a sequence index in event ingestion. If index missing, do not use the pattern in explanations; instead, describe generically (e.g., "both events occurred around the same time; order unknown").

7. **Monitoring & drift detection (ongoing)**  
   - Track these metrics weekly:  
     - % of predictions flagged by validation suite (should be 0 for valid cases).  
     - # of missing sequence indices for same-timestamp pairs.  
     - Proxy fairness lift (region/week vs majority).  
     - % of features using `feat_max_time > t0` (should be 0).  
   - Alert if >5% of cases have missing index or fairness lift >10%.  
   - When process changes occur (e.g., new policy, holiday schedule), re-run fairness review for affected proxies and update pattern rules (e.g., if Appeals may open earlier, adjust pattern allowlist).

8. **Team training & documentation (Week 1–ongoing)**  
   - Run a 60-minute workshop: "Predictive vs causal vs actionable in explanations" with examples (e.g., "queue may indicate load"  vs "queue causes delay" ). Use real case snippets from X/Y/Z.  
   - Publish a one-page "Explanation checklist" (see style guide) and attach it to model cards. Model cards must list:  
     - Features used at t0 (with `feat_max_time  t0` confirmation),  
     - Proxies present (e.g., `calendar_week`),  
     - Fairness check date and result,  
     - Pattern rules (both nodes  t0),  
     - Uncertainty note template for cases with missing index.  
   - Encourage "explainability reviews" during model iteration: before releasing explanations, run the validation suite + lint check.

> **Why this works**: It addresses all task requirements without over-removing correlated features. It keeps legitimate congestion signals (`queue_length` when valid, `elapsed`), uses precise language to separate predictive association ("may indicate") from causal claims ("causes"), and handles mutable lineage via snapshot timestamps. Fairness review is practical (monthly check + evidence-based), not automatic removal. Monitoring catches drift (policy changes, index missingness). The plan is prioritized: hardening the feature store first prevents leakage at ingestion; validation suite catches issues at prediction time; language guardrails ensure consistent credible explanations. This balances rigor with usability—model team keeps useful signals but learns concrete phrasing rules.

> **Credibility note**: This audit distinguishes clearly:  
> - *Temporal leakage*: `total_case_duration`, `appeal_seen`, `full_trace`, `same_day doc snapshot` — unusable at t0.  
> - *Process impossibility*: `final_decision=Partial` at t0, `Claim Closed` pattern — impossible per steps 1–8; explanations must not claim they occurred.  
> - *Mutable lineage*: `risk_score`, `last_role` — may change post-t0; use snapshot at t0 if available.  
> - *Correlated proxies*: `region`, `week` — predictive but need fairness review; language uses "may vary"/"based on historical patterns".  
> - *Legitimate signals*: `initial_complexity`, `queue` (if valid), `elapsed` — descriptive, "may" language, no causation.  
> No feature is deleted outright without repair option (e.g., `queue_length` is usable if snapshot  t0); explanations are revised to be process-aware and temporally consistent. The JSON revisions for X/Y avoid causal claims and use only t0-available features. Uncertainty for Z is clearly stated without over-interpreting. Recommendations are actionable, measurable, and phased.
