```python
def perturb(log, p_missing=0.05, p_duplicate=0.05, seed=0):
    rng = random.Random(seed)
    new = EventLog()
    for case in log:
        t = Trace()
        for e in case:

            if r < p_missing: continue
            t.append(e)
            if rng.random() < p_duplicate: t.append(copy.deepcopy(e))
```

Post-hoc checker:

```python
def posthoc_policy_check(trace, sourcing=None, affected=None):
    """trace: list[str] of activity names, in order. Returns list of findings."""
    findings = []
    checks = ["Credit Check", "Technical Review"]
    # P7: repeated mandatory check without preceding correction
    last_cd = -1
    count = {c: 0 for c in checks}
    for i, a in enumerate(trace):
        if a == "Correct Dossier":
            last_cd = i
        elif a in count:
            count[a] += 1
            if count[a] > 1 and last_cd == -1:
                findings.append(f"P7 suspicious: {a} repeated at #{i} with no preceding Correct Dossier")
    # P3 (only checkable if attribute exists)
    if sourcing is not None:
        has_sr = "Supplier Review" in trace
        if sourcing == "external" and not has_sr:
            findings.append("P3 violation: external order without Supplier Review")
        if sourcing == "internal" and has_sr:
            findings.append("P3 finding: internal order with Supplier Review (waste?)")
    else:
        findings.append("P3 UNVERIFIABLE: sourcing attribute missing")
    # P6 completeness (only checkable if attribute exists)
    if affected is None and "Correct Dossier" in trace:
        findings.append("P6 PARTIALLY VERIFIABLE: affected_checks attribute missing; recheck correctness not provable")
    return findings
```

| Simulation / capacity planning | Generate realistic traces | Needs data attributes (sourcing, urgency) that this log lacks; neither submitted model is adequate |

# 3. Adversarial Review of Model S

**Strongest case for S.** It achieves 0.981 holdout fitness with 0.018 s alignments, 0.918 simplicity, 4.4 comprehension, and 0.907 token generalization. As a *capability map* — "these activities exist, roughly between registration and release" — it is genuinely useful, robust to the missing Supplier Review events reported in F4, and legible to business users. F7's defense (exploration, not enforcement) is coherent *if* consumers are warned.

**Strongest case against S.** Its high scores are purchased by encoding mandatory controls as optional. Precision 0.584 means a large share of model-enabled behavior was never observed — and because precision was measured only against observed positives (F5), 0.584 *understates* the policy problem. Worse, S cannot express Correct Dossier at all: it is not merely permissive, it is **incomplete** on P6/P7. If corrections occur in the training log with any frequency, 0.992 training fitness is implausible under standard alignment costs — either corrections are rare in the log, or the cost settings quietly absorbed them. Both possibilities demand disclosure.

**Concrete undesirable/policy-ambiguous admissions (5):**

1. `Register Dossier, Manager Approval, Release Order` (B3) — approval with **no checks at all** (all four branches take tau). Forbidden; a credit-control breach.
2. `Register Dossier, Auto Approval, Release Order` — *automatic* approval with zero checks. Arguably worse than B3.
3. `Register Dossier, Credit Check, Manager Approval, Release Order` — Technical Review skipped. Violates P2.
4. `Register Dossier, Technical Review, Auto Approval, Release Order` — Credit Check skipped. Violates P2.
5. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` (B4) — expedite *before* the checks it must follow. Violates P4.
6. `Register Dossier, Supplier Review, Manager Approval, Release Order` — an optional conditional activity substitutes for mandatory controls.
7. `Register Dossier, Supplier Review, Expedite Review, Auto Approval, Release Order` — only optionals, then auto-approval.

**Intentional noise tolerance vs. accidental semantic flaws.** Defensible/intended: tau on Supplier Review (the conditioning attribute is missing from the log — optionality is the only log-only encoding available, shared by every model here); tau on Expedite Review (P4 says optional); unordered Credit Check / Technical Review (P2 allows either order). **Accidental semantic flaws:** tau on Credit Check and Technical Review (P2 says *mandatory* — this is the decisive error); absence of any ordering edge forcing Expedite Review after the checks (P4); total absence of correction behavior (P6/P7). The discovery team's "robust to missing events" is operationally indistinguishable from "blind to skipped mandatory controls": in alignment diagnostics, a missing Credit Check routes through tau at zero cost and the dashboard shows green while a control was bypassed.

# 4. Adversarial Review of Model C

**Strongest case for C.** Under F8's quarantine doctrine — unseen behavior is noncompliant until approved — a whitelist is a legitimate, auditable operating pattern. C rejects every dangerous probe (B3, B4, B8), contains no silent transitions (so every alignment deviation is a visible, explainable log/model move), and its 0.941 training precision shows it rarely enables unobserved behavior. For a regulator, "the model is exactly the list of approved variants" is an easy story to tell.

**Strongest case against C.** The whitelist is *incomplete even against already-approved policy*, so it fails its own doctrine:

- **Enumeration gap, quantified.** Without corrections, the declared-valid space is: check order (2) × approval (2) × supplier/expedite placement (no SR with/without ER; SR alone; ER before SR; ER after SR = 5) = **20 combinations**. C lists **7** of them (35%). It therefore rejects B2 (TR-first + Auto Approval) and B5 (TR-first + SR + ER + AA) — both declared valid/plausible. In the correction space (unbounded cycles × recheck subsets × orders × approvals) C covers exactly **one** point.
- **Correction handling.** C7 repeats *both* checks and exists only in CC-first order with Manager Approval. B6 (recheck Technical Review alone) — explicitly contemplated by the process owner (F6) — is rejected. Multiple corrections are impossible.
- **Holdout degradation is ambiguous evidence.** The 0.744 mixes valid-novel combinations, possibly-missing Supplier Review events (F4), and genuinely suspicious traces. C's advocates (F8) and critics (F2) are both partially right; the metric cannot arbitrate without per-case diagnostics.
- **Precision as memorization artifact.** Enumerating branches from training variants and then measuring precision against the training log is close to circular; token generalization 0.412 (single-use branches) confirms the model memorizes rather than abstracts.
- **Duplicate labels and maintainability.** 48 transitions for 9 labels; the reported "33" duplicates is irreproducible under any standard definition. Every activity's control logic is smeared across up to 9 transitions — exactly F3's ownership/impact-analysis problem — and adding one approved variant means editing and re-validating the whole net (F2).
- **Secondary costs.** Simplicity 0.281, comprehension 1.9, ~24× alignment runtime.

C is neither a correct whitelist (too incomplete) nor a generalizing model (too rigid). Its remaining value is as a *catalog of historically frequent variants*.

"Accepts?" = the model can generate exactly this trace (perfectly fitting alignment under standard costs). Model C's language is the 8 listed sequences — membership is exact, no loop/silent ambiguity. Model S's answers assume standard process-tree semantics (`+` = interleaving, `X(·, tau)` = optional); under those semantics there is no residual uncertainty.

# 6. Likely Metric Pathologies

Ranked by likely decision impact (most dangerous first):

1. **Fitness rewarded by optionalizing mandatory behavior.** S's 0.992/0.981 is bought by tau branches on Credit Check and Technical Review. In the limit, a flower model scores fitness 1.0. This pathology can cause the board to select a model that approves orders without credit checks — the highest-stakes error available.
2. **Split sensitivity / leakage / distribution shift.** No seeds, no case lists. F4 documents that the holdout contains systematically novel combinations (and possibly missing events), so train/holdout are not exchangeable; conversely, near-duplicate variants split across train/holdout would *inflate* C. Either direction is possible; the 0.981 vs 0.744 gap could move substantially with a different seed. Nothing should be decided until the split is reproduced.
3. **Positive-log-only precision (F5).** Precision against observed positives cannot penalize S for admitting unobserved-but-forbidden B3, and cannot credit C for rejecting it. S's 0.584 understates its policy-imprecision; C's 0.941 overstates its policy-precision (memorization circularity).
4. **Missing-event bias.** S's tau branches absorb missing Supplier Review events at zero cost; C pays a model move for every absent expected activity. "Robust to missing events" and "unable to detect skipped controls" are the same mechanism described with opposite spin.
5. **Generalization rewarded by excessive permissiveness.** S's 0.907 reflects reusable parallel structure, not correctness of the generalized behavior. Reading it as evidence S is "better" double-counts pathology 1.
6. **Duplicate-label effects.** C's 48 transitions / 9 labels: alignment results become ambiguous (which "Credit Check" fired?), generalization is structurally depressed, ownership is obscured (F3), and the reported count of 33 is irreproducible (natural definitions give 39 or 25) — itself a governance red flag.
7. **Silent-transition effects.** Tau paths let alignments erase deviations invisibly; conformance diagnostics show no move where a control was skipped. Any model using tau (including my proposal in §7) must publish which tau corresponds to which policy decision.
8. **Alignment-cost sensitivity.** Costs unpublished. C's holdout fitness rises if model moves are cheapened (missing-event regime); S's rises if log moves are cheapened. Rankings can flip across a plausible cost grid — must be tested, not assumed.
9. **Runtime confounding by model size.** 0.018 s vs 0.440 s measures search-space size and trace deviation, not model quality. Operationally relevant at scale; evidentially irrelevant to correctness.
10. **Stakeholder-score methodology.** Informal 1–5, no protocol, unknown raters. Treat 4.4/1.9 as a hypothesis to re-test under a documented protocol, not as evidence.

Interactions matter: (1)×(4) jointly explain S's fitness; (3)×(6) jointly explain C's precision/generalization split.

# 7. Third Alternative

**Strategy: a balanced POWL backbone that encodes P1–P5 and the *structure* of P6/P7 procedurally, plus a small declarative layer carrying exactly the two rules that the missing attributes make unenforceable (P3's condition, P6's affected-check matching).** Nothing is silently optionalized: the only optional activities are the two the policy itself declares optional/conditional, and each silent path corresponds to a named, documented policy decision.

**1. Compact formal description.**

`model_third = StrictPartialOrder(N, )` with nodes `N = {R, CHECKS, CORR, SR, ER, AP, RO}` and precedence
` = {(R,CHECKS), (R,SR), (CHECKS,CORR), (CHECKS,ER), (CORR,AP), (ER,AP), (SR,AP), (AP,RO)}` (plus transitive closure), where:

- `CHECKS = StrictPartialOrder({Credit Check, Technical Review}, )` — both mandatory, either order.
- `CORR = XOR(, LOOP(do: Correct Dossier  RECHECK, redo: ))` — zero or more correction cycles.
- `RECHECK = StrictPartialOrder({XOR(Credit Check, ), XOR(Technical Review, )}, )` — after a correction, recheck either, both, or neither check (bounded duplicate labels: each check appears at most twice in the whole model, in distinct roles).
- `SR = XOR(Supplier Review, )`; `ER = XOR(Expedite Review, )`; `AP = XOR(Manager Approval, Auto Approval)`.

**2. Self-contained PM4Py code.**

```python
import pm4py
from pm4py.objects.powl.obj import (
    Transition, SilentTransition, OperatorPOWL, StrictPartialOrder,
)
from pm4py.objects.process_tree.obj import Operator

# --- atomic activities ---------------------------------------------------
R  = Transition("Register Dossier")
CC = Transition("Credit Check")
TR = Transition("Technical Review")
CD = Transition("Correct Dossier")
RO = Transition("Release Order")

# --- P2: both mandatory checks, either order ------------------------------
CHECKS = StrictPartialOrder(nodes=[CC, TR])          # no edge => unordered, both required

# --- P6/P7: zero or more cycles of (Correct Dossier -> recheck subset) ----
CC_re = Transition("Credit Check")      # bounded duplicate: 'recheck' role only
TR_re = Transition("Technical Review")  # bounded duplicate: 'recheck' role only
RECHECK = StrictPartialOrder(nodes=[
    OperatorPOWL(Operator.XOR, [CC_re, SilentTransition()]),
    OperatorPOWL(Operator.XOR, [TR_re, SilentTransition()]),
])
CYCLE = StrictPartialOrder(nodes=[CD, RECHECK])
CYCLE.order.add_edge(CD, RECHECK)                    # recheck only after correction
CORR = OperatorPOWL(Operator.XOR, [
    SilentTransition(),                                  # zero corrections
    OperatorPOWL(Operator.LOOP, [CYCLE, SilentTransition()]),  # 1..n cycles
])
# Fallback if the installed PM4Py cannot convert POWL LOOP:
# replace CORR by XOR(tau, CYCLE, CYCLE;CYCLE) as a bounded unrolling and
# monitor for >2 cycles operationally.

# --- P3/P4/P5 -------------------------------------------------------------
SR = OperatorPOWL(Operator.XOR, [Transition("Supplier Review"), SilentTransition()])
ER = OperatorPOWL(Operator.XOR, [Transition("Expedite Review"), SilentTransition()])
AP = OperatorPOWL(Operator.XOR, [Transition("Manager Approval"),
                                 Transition("Auto Approval")])

# --- global partial order --------------------------------------------------
model_third = StrictPartialOrder(nodes=[R, CHECKS, CORR, SR, ER, AP, RO])
model_third.order.add_edge(R, CHECKS)
model_third.order.add_edge(R, SR)
model_third.order.add_edge(CHECKS, CORR)
model_third.order.add_edge(CHECKS, ER)      # expedite after BOTH checks (P4)
model_third.order.add_edge(CORR, AP)
model_third.order.add_edge(ER, AP)          # expedite before approval (P4)
model_third.order.add_edge(SR, AP)
model_third.order.add_edge(AP, RO)          # release last (P1)

net_third, im_third, fm_third = pm4py.convert_to_petri_net(model_third)
pm4py.check_soundness(net_third, im_third, fm_third, print_diagnostics=True)
```

**3. Declarative layer and external checks.**

```python
DECLARATIVE_RULES = {
    "D1_supplier_condition": {
        "kind": "data_condition",
        "rule": "'Supplier Review' present  <=>  case.sourcing == 'external'",
        "status": "BLOCKED - 'sourcing' attribute absent from discovery log",
        "interim": "report SR presence/absence rates; sample-audit suspected external cases",
    },
    "D2_recheck_requires_correction": {
        "kind": "precedence",
        "rule": "k-th occurrence (k>1) of Credit/Technical Check is preceded by "
                "Correct Dossier after the (k-1)-th occurrence",
        "status": "ENFORCED procedurally; post-hoc double-check below",
    },
    "D3_affected_check_repeated": {
        "kind": "response",
        "rule": "after Correct Dossier, every check in event.affected_checks "
                "recurs before approval; no unaffected check recurs",
        "status": "BLOCKED - 'affected_checks' attribute absent",
        "interim": "random audit sampling of correction cases",
    },
    "D4_exactly_one_approval": {"kind": "cardinality", "status": "ENFORCED procedurally"},
    "D5_expedite_window":    {"kind": "precedence",   "status": "ENFORCED procedurally"},
}

def posthoc_policy_check(trace, sourcing=None, affected=None):
    """trace: list of activity names in order. Returns findings (P6/P7 + data rules)."""
    findings, last_cd = [], -1
    count = {"Credit Check": 0, "Technical Review": 0}
    for i, a in enumerate(trace):
        if a == "Correct Dossier":
            last_cd = i
        elif a in count:
            count[a] += 1
            if count[a] > 1 and last_cd == -1:
                findings.append(f"P7 suspicious: {a} repeated at position {i} "
                                "without preceding Correct Dossier")
    if sourcing is None:
        findings.append("P3 UNVERIFIABLE: sourcing attribute missing")
    elif sourcing == "external" and "Supplier Review" not in trace:
        findings.append("P3 violation: external order without Supplier Review")
    elif sourcing == "internal" and "Supplier Review" in trace:
        findings.append("P3 finding: internal order with Supplier Review (waste?)")
    if "Correct Dossier" in trace and affected is None:
        findings.append("P6 PARTIALLY VERIFIABLE: affected_checks missing; "
                        "recheck correctness not provable")
    return findings
```

**4. Explicit semantics.**

- **Mandatory checks (P2):** `CHECKS` is a partial order with no edge — Credit Check and Technical Review each occur exactly once, in either order, and both are ancestors of approval.
- **Optional Supplier Review (P3):** exactly one activity is optional; its *condition* lives in D1, blocked until the sourcing attribute exists. We do **not** fix missing data by optionalizing anything else.
- **Expedite ordering (P4):** `CHECKS  ER  AP`; no edge between ER and SR, so expedite may precede or follow Supplier Review, as written in P4.
- **Exactly-one approval (P5):** single XOR node; structurally impossible to take both or neither.
- **Correction/recheck (P6/P7):** any repeated mandatory check is *structurally impossible* without an intervening Correct Dossier (P7 by construction, with the post-hoc checker as a second line that downgrades to "suspicious" in exploration mode). After a correction, any subset of {Credit Check, Technical Review} may recur — including neither (plausible for clerical corrections) — and cycles may repeat.

**5. Limitations from missing attributes.** (a) P3 cannot be enforced: external orders without SR and internal orders with SR both fit; only monitoring + sampling is possible until `sourcing` is logged. (b) P6's *correctness* of rechecks is unprovable: a correction affecting Credit Check followed by a Technical Review recheck fits the model; only D3 (blocked) or audit sampling catches it. (c) Whether a correction invalidates a completed Supplier Review is unresolved stakeholder detail; the model permits the interleaving and flags it. Migration path once attributes exist: either enforce D1/D3 as data-aware guards, or split into an attribute-conditioned family (`model_external`: SR mandatory; `model_internal`: SR removed) selected per case.

```python
import copy, random
def perturb(log, p_missing=0.0, p_duplicate=0.0, seed=0):
    rng = random.Random(seed); new = EventLog()
    for case in log:
        t = Trace(attributes=dict(case.attributes))
        for e in case:
            if rng.random() < p_missing:
                continue
            t.append(e)
            if rng.random() < p_duplicate:

        new.append(t)
    return new
```

**9.9 Stakeholder comprehension protocol.** 12 raters across compliance, operations, IT; models anonymized and rendered in identical style; order counterbalanced. Tasks: (a) judge validity of B1–B8, (b) trap question ("can an order be approved without Credit Check?"), (c) modify-the-model scenario. Record accuracy, time, confidence; Likert items with written anchors; report median/IQR and Fleiss' kappa; pre-register the analysis.

**9.10 Rejection rule (hard vetoes, immune to aggregates).** A model is rejected for enforcement **regardless of any average** if: V1 any negative-suite trace (B3/B4/B8/N1/N2/N4 class) is perfectly fitting; V2 soundness fails or any required label is unreachable; V3 zero-cost acceptance of the declared-valid unseen-combination suite < 95%; V4 results are irreproducible (missing seeds/configs). If the board insists on a composite score, weights must be fixed ex ante per use case and may not override vetoes.

# 10. Governance Recommendation

- **Exploration/communication:** Model S may be used *provisionally*, watermarked "not policy-complete: admits approval without mandatory checks; cannot represent corrections," and only until the third alternative passes the comprehension protocol — at which point **S is retired**, because a simple model that teaches a wrong control structure is a communication hazard, not a neutral sketch. F7's defense is accepted only under that labeling condition.
- **Compliance/enforcement:** **Neither S nor C.** S fails veto V1 (B3, B4). C fails veto V3 (B2, B5, B6-class) — F8's quarantine doctrine is defensible in principle, but C is the wrong artifact for it, because a whitelist must at minimum contain all *already-approved* valid behavior; C covers 7 of 20 declared-valid no-correction combinations and one correction pattern of an unbounded family. Retain C solely as a **catalog of historically frequent variants** (documentation), not as a gate.
- **Retirement:** Retire S and C as decision artifacts; archive both with their metrics, seeds (once reproduced), and configs for the audit trail.
- **Conditions for deploying the third alternative:** (1) `sourcing` and `affected_checks` attributes added to the event log, unblocking D1/D3; (2) all hard vetoes passed, including 100% negative-suite rejection on mandatory-safety items; (3) stratified holdout and unseen-combination fitness at agreed thresholds across 20 seeds; (4) soundness and label-reachability verified; (5) documented comprehension protocol showing parity with S (or a justified gap); (6) shadow-mode dual run against current manual review for an agreed period; (7) version-controlled ownership with a change board including compliance and operations; (8) drift monitoring on variant distribution, correction-cycle rates, and SR presence once sourcing exists.

# 11. Dissenting View

Deploy Model C as the enforcement gate now and treat the third model as a research track. My recommendation depends on a validation program and two event attributes that do not yet exist; until they exist, the third model's safety case is structural argument, not measurement. Its correction region deliberately admits behavior no stakeholder has approved — correction without any recheck, supplier review before the checks — and its bounded duplicate labels reintroduce in miniature the very pathology I criticized in Model C. POWL loop tooling is less battle-tested than a plain enumerated net, and the hybrid's post-hoc checks are, operationally, an audit queue nobody has staffed. Model C's 0.744 holdout fitness is ugly but honest under a quarantine doctrine: in a credit-regulated process, an unrecognized variant *should* stop the line. C rejects every dangerous probe (B3, B4, B8) while Model S waves them through, and a whitelist plus a fast variant-approval workflow is a known, auditable operating pattern. High training precision at least proves C rarely invents behavior; the third model's generality is only a promise that its flexibility will be exercised responsibly. Shipping governance this quarter may matter more than elegance next year.

**What would change my decision:** (1) evidence that a quarantine/variant-approval workflow is actually sustainable — measured approval SLA and quarantine volume low enough that rejecting B2/B5-class cases costs little; (2) the attribute roadmap slipping beyond the audit deadline, making D1/D3 permanently unenforceable; (3) the third model failing soundness/LOOP conversion or showing, on the perturbation grid, that its fitness advantage over C vanishes under standard costs; (4) playout-based policy-precision revealing that the third model's flexibility is exercised as policy-gray behavior at a non-trivial rate; (5) shadow-mode data showing C's false rejections are rarer in production than the probe analysis predicts. Any two of these would move me to "C-with-change-control now, third model when the data catches up."
