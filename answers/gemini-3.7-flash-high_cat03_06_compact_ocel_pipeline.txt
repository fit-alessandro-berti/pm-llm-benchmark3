## 1. Modeling assumptions

### Object Types and Capitalization
The data model uses six object types formatted in standard PascalCase:
- `Order`: Commercial purchasing agreements between the customer and retailer (`O100`, `O200`).
- `Item`: Discrete physical or catalog line items belonging to orders (`I1`, `I2`, `I3`).
- `Package`: Physical packaging containers into which items are consolidated for shipping (`P1`, `P2`).
- `Delivery`: Freight transport shipments dispatched to fulfill packages (`D1`, `D2`).
- `Invoice`: Financial billing instrument consolidating charges for orders (`V1`).
- `Payment`: Financial settlement transactions clearing invoice balances (`M1`, `M2`).

### E2O Qualifier Vocabulary
Event-to-Object (E2O) relations in the `relations` DataFrame capture the exact operational role an object plays in an event:
- `created`: The event instantiates the object's lifecycle (e.g., `Create Order` $\to$ `Order`).
- `target`: The object acts as the receiving parent container/aggregate for an addition (e.g., `Add Item` $\to$ `Order`).
- `added`: The object is newly associated or inserted into an aggregate (e.g., `Add Item` $\to$ `Item`).
- `reserved`: Inventory is allocated specifically for the object (e.g., `Reserve Stock` $\to$ `Item`).
- `operational_context`: The object provides the broader business/commercial context for an execution event (e.g., `Reserve Stock` $\to$ `Order`, `Pack Package` $\to$ `Order`).
- `packed`: The physical freight container being assembled (e.g., `Pack Package` $\to$ `Package`).
- `content`: The item placed inside a container (e.g., `Pack Package` $\to$ `Item`).
- `dispatched_in`: The shipment vehicle/consignment executing the transport (e.g., `Dispatch Package` $\to$ `Delivery`).
- `dispatched`: The container unit loaded and released for transport (e.g., `Dispatch Package` $\to$ `Package`).
- `issued`: The financial billing document generated (e.g., `Issue Invoice` $\to$ `Invoice`).
- `billed`: The commercial order covered by the invoice (e.g., `Issue Invoice` $\to$ `Order`).
- `recorded`: The payment transaction registered in the ledger (e.g., `Record Payment` $\to$ `Payment`).
- `settled`: The target invoice receiving the remittance (e.g., `Record Payment` $\to$ `Invoice`).
- `confirmed`: The shipment confirmed as delivered at the destination (e.g., `Confirm Delivery` $\to$ `Delivery`).
- `closed`: The commercial entity whose fulfillment and accounting lifecycle is terminated (e.g., `Close Order` $\to$ `Order`).

### O2O Direction Conventions
Object-to-Object (O2O) relations in the `o2o` DataFrame represent structural, topological, or master-data associations oriented from the active/containing entity (`ocel:oid`) to the referenced/contained entity (`ocel:oid_2`):
- `Order` $\xrightarrow{\text{contains}}$ `Item` (1:N structural breakdown: `O100` contains `I1`, `I2`; `O200` contains `I3`).
- `Package` $\xrightarrow{\text{packs}}$ `Item` (1:N / N:M physical packing: `P1` packs `I1`, `I3`; `P2` packs `I2`).
- `Delivery` $\xrightarrow{\text{carries}}$ `Package` (1:1 / 1:N logistics assignment: `D1` carries `P1`; `D2` carries `P2`).
- `Invoice` $\xrightarrow{\text{bills}}$ `Order` (1:N consolidated commercial billing: `V1` bills `O100`, `O200`).
- `Payment` $\xrightarrow{\text{partially_settles}}$ `Invoice` (N:1 settlement step: `M1` settles `V1`).
- `Payment` $\xrightarrow{\text{completes_settlement}}$ `Invoice` (N:1 final settlement step: `M2` settles `V1`).

### Direct vs. Mediated Logistics and Financial Relations
- **Logistics Events (`Dispatch Package`, `Confirm Delivery`)**: Directly linked in E2O to `Delivery` and `Package` objects because physical freight handling occurs at the container and shipment levels. They are not directly linked to individual `Item` or `Order` objects in the primary event stream, maintaining alignment with source WMS/carrier tracking logs.
- **Financial Settlement Events (`Record Payment`)**: Directly linked in E2O to `Payment` and `Invoice` (`V1`). Because `V1` is a consolidated invoice covering both orders without an explicit itemized ledger split at the moment of payment, payments are not artificially split or linked directly to `Order` or `Item` objects.
- **Packaging and Reservation Events (`Reserve Stock`, `Pack Package`)**: Directly linked to `Item`, `Package`, and `Order` objects because warehouse management systems execute stock reservations and packing tasks against specific line items while tracking the active commercial order context.

### Preventing Analytical Propagation Confusion
To avoid conflating raw source observations with inferred analytical connections:
1. **Source Fidelity in Base Tables**: The `relations` DataFrame records only direct operational interactions captured by operational systems at runtime.
2. **Explicit Qualifier Typing**: When operational context is captured (e.g., orders involved in packing), it is explicitly qualified as `operational_context` rather than `target` or `packed`.
3. **Graph-Derived Propagation**: Any downstream analytical closure (e.g., associating delivery confirmation back to an order via $D1 \to P1 \to I1 \to O100$) is computed dynamically via O2O graph traversal rather than injected into the primary E2O log.

### PM4Py Version-Dependent Assumptions
- Assumes the PM4Py 2.x relational OCEL representation where the `OCEL` object is instantiated via `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` with standard `ocel:` prefixed columns.
- Timestamps are pandas timezone-aware UTC datetime objects (`datetime64[ns, UTC]`).
- Flattening (`pm4py.ocel_flattening`) projects the multi-object log onto traditional single-case logs (`case:concept:name`, `concept:name`, `time:timestamp`), duplicating shared events across participating object lifecycles.

## 6. Modeling alternatives

| Modeling Policy | Core E2O Strategy | Primary Advantages | Impact on Process Discovery |
| :--- | :--- | :--- | :--- |
| **1. Source-Minimal (Strict Locality-First)** | Events link *only* to the immediate physical/transactional objects directly manipulated (e.g., `Reserve Stock` $\to$ only `Item`; `Pack Package` $\to$ `Package`, `Item`; `Issue Invoice` $\to$ `Invoice`). Orders and Invoices are never linked to downstream logistics or payments. | Maximizes source-system fidelity; eliminates event duplication in flattened logs; zero artificial E2O overhead. | Order-flattened logs truncate at `Add Item` and `Close Order`; cross-domain causal connections rely entirely on O2O graph joins; OC-DFG has fewer shared synchronization nodes. |
| **2. Full Operational Context (Implemented Policy)** | Events link to immediate physical objects *plus* the active commercial context objects directly referenced in the execution transaction (e.g., attaching `Order` to `Reserve Stock`, `Pack Package`, and `Issue Invoice`). | Reflects true ERP/WMS operational execution context; produces rich end-to-end Order lifecycles while maintaining strict logistics/financial boundaries. | Order traces include packaging and billing milestones; OC-DFG and ET-OT explicitly show multi-order bundling at `Pack Package` and `Issue Invoice`; flattened Order logs duplicate shared batch events. |
| **3. O2O-Propagated Analytical Closure (Transitive Closure)** | Pre-processes the log by computing the transitive closure over O2O relationships ($D \to P \to I \to O$, $M \to V \to O$), linking every downstream event to all ancestor objects. | Allows single-case flattening on `Order` to display the entire timeline from creation to payment and carrier delivery. | Massive relation inflation; creates artificial concurrency and spurious directly-follows edges; destroys distinction between direct observation and indirect causality. |

## 7. Failure modes

1. **Relation Inflation (Combinatorial Overspecification)**:
   Transitively linking every downstream event to every ancestor object (e.g., attaching `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `V1` to `Confirm Delivery D1`) causes exponential growth in the `relations` table, rendering OC-DFG discovery unreadable and computationally intractable.
2. **Missing Direct E2O Links (Underspecification)**:
   Omitting direct operational participants (e.g., linking `Pack Package` only to `Package` and omitting `Item`) severs the lifecycle link between items and packages, causing process discovery algorithms to treat item packing as an unconnected, unobserved step.
3. **Treating O2O Propagation as Observation**:
   Conflating static master-data associations in `o2o` with runtime execution in `relations` assumes relationships existed prior to their actual instantiation, destroying the temporal validity of the event log.
4. **Duplicate Shared Events After Flattening**:
   When an event relates to $k$ objects of the flattening type (e.g., `Issue Invoice` related to `O100` and `O200`), flattening duplicates the event across $k$ case traces. This leads to double-counting in throughput times, cost allocations, and frequency statistics.
5. **Ambiguous Payment Allocation**:
   Remittances `M1` (100) and `M2` (150) settle consolidated invoice `V1` (total 250) without line-item or order-specific remittance advice. Forcing direct E2O links from `Payment` to `Order` requires arbitrary heuristic splitting (e.g., FIFO or pro-rata), introducing false domain assumptions into the log.
6. **Overly Short Payment Traces**:
   Defining transactional records (`Payment`) as process object types produces single-event traces of length 1. This leads to empty DFGs, undefined process paths, and uninformative conformance checking.
7. **Constructor and API Version Mismatches**:
   Attempting to pass relational OCEL 2.0 tables (`relations`, `o2o`) to legacy OCEL 1.0 parsers (which expect a flat table with list-valued object columns) results in runtime schema rejection, missing object-type assignments, or unhandled attribute exceptions.
8. **False Total Order for Same-Time Events**:
   When concurrent events share identical timestamps (e.g., if `e2` and `e3` had identical timestamps), sorting by timestamp arbitrarily imposes a deterministic sequential order ($e2 \to e3$ instead of $e2 \parallel e3$), inducing spurious directly-follows edges and misleading log skeleton invariants.
