## 1. Modeling assumptions

- **Object types and capitalization**
  - `Order`
  - `Item`
  - `Package`
  - `Delivery`
  - `Invoice`
  - `Payment`

- **E2O qualifier vocabulary**
  - All event-to-object rows in the constructed `relations` table are treated as **source/operational observations** and are prefixed with `src:`.
  - Qualifiers used:
    - `src:order_created`
    - `src:order_updated`
    - `src:item_added`
    - `src:item_reserved`
    - `src:order_reserved`
    - `src:package_packed`
    - `src:item_packed`
    - `src:order_packed`
    - `src:package_dispatched`
    - `src:delivery_used`
    - `src:invoice_issued`
    - `src:order_billed`
    - `src:payment_created`
    - `src:invoice_partially_settled`
    - `src:invoice_settlement_completed`
    - `src:delivery_confirmed`
    - `src:order_closed`
  - If analytical propagation were added later, it would use a separate `derived:` qualifier prefix, or a separate derived relations table, so that inferred links are not confused with source-system facts. This pipeline intentionally stores only `src:` E2O relations.

- **O2O direction conventions**
  - O2O rows are written as **subject  object**, matching the natural-language verb:
    - `Order contains Item`
    - `Package packs Item`
    - `Delivery carries Package`
    - `Invoice bills Order`
    - `Payment partially_settles Invoice`
    - `Payment completes_settlement Invoice`
  - Therefore:
    - `ocel:oid` is the subject/source/parent.
    - `ocel:oid_2` is the object/target/child.

- **Directness policy for logistics and financial events**
  - **Orders and Items** are directly related to:
    - order creation,
    - item addition,
    - joint stock reservation,
    - packing where order involvement is explicit or unambiguous.
  - **Packages and Deliveries** are directly related to dispatch and delivery confirmation.
  - **Invoices and Orders** are directly related when the invoice is issued.
  - **Payments** are directly related only to the payment object and the invoice. They are not allocated directly to orders because the narrative gives only invoice-level settlement, not order-level allocation.
  - Dispatch and delivery confirmation are kept package/delivery-centric. They could be propagated to orders/items through O2O links, but doing so as direct E2O facts would overstate what the operational event explicitly records.

- **Separation of source facts from propagated analysis**
  - The `relations` table contains source-style E2O facts only.
  - The `o2o` table contains structural/business relationships that can be used for analytical traversal or enrichment.
  - This keeps provenance clean: if a later analysis wants to infer, for example, that dispatching `P1` indirectly affects `O100` and `O200`, that inference should be marked as derived rather than inserted as another `src:` observation.

- **Version-dependent PM4Py assumption**
  - The pipeline assumes a PM4Py-style OCEL container accepting:
    - `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`
  - If a PM4Py release requires positional arguments, or exposes an `OCEL2` container, only the import/construction line should be adjusted. The DataFrame semantics remain unchanged.

| Activity | Event IDs | Object types touched |
|---|---|---|

| `Close Order` | `E16`, `E17` | `Order` |

### Especially consequential relation sets

- **`E06 Reserve Stock`**
  - Links `I1`, `I3`, `O100`, and `O200`.
  - This is the first major cross-order convergence point.
  - In an Order flattening, this single event will be copied into both order cases.

- **`E07 Pack Package` for `P1`**
  - Links `P1`, `I1`, `I3`, `O100`, and `O200`.
  - This is the strongest operational convergence point because one package combines items from two orders.

- **`E08 Pack Package` for `P2`**
  - Links `P2`, `I2`, and `O100`.
  - This introduces divergence between `O100` and `O200`: `O100` has an additional packaging event.

- **`E11 Issue Invoice`**
  - Links `V1`, `O100`, and `O200`.
  - This is the main financial convergence point.

- **`E12` and `E15 Record Payment`**
  - Link payments only to `V1`, not to orders.
  - They preserve invoice-level settlement but deliberately leave order-level payment allocation ambiguous.

## 4. Expected flattened behavior

### Flattening on `Order`

Expected cases:

- Case `O100`:
  1. `Create Order`
  2. `Add Item`
  3. `Add Item`
  4. `Reserve Stock`
  5. `Pack Package`
  6. `Pack Package`
  7. `Issue Invoice`
  8. `Close Order`

- Case `O200`:
  1. `Create Order`
  2. `Add Item`
  3. `Reserve Stock`
  4. `Pack Package`
  5. `Issue Invoice`
  6. `Close Order`

Shared events copied into both order cases:

- `E06 Reserve Stock`
- `E07 Pack Package` for `P1`
- `E11 Issue Invoice`

Likely DFG edges:

- `Create Order -> Add Item`
- `Add Item -> Add Item`
- `Add Item -> Reserve Stock`
- `Reserve Stock -> Pack Package`
- `Pack Package -> Pack Package`
- `Pack Package -> Issue Invoice`
- `Issue Invoice -> Close Order`

Omitted lifecycle aspects:

- Dispatching `P1` and `P2` is not directly visible in the Order view.
- Delivery confirmation is not directly visible in the Order view.
- Payments are not directly visible in the Order view because they are linked only to `V1`.

Misleading interpretations:

- The shared `Reserve Stock`, `Pack Package`, and `Issue Invoice` events may make the two orders appear more synchronized than they are.
- The `Pack Package -> Pack Package` edge for `O100` could be misread as rework, whereas it actually represents two distinct packages, `P1` and `P2`.
- Because payments are absent from the Order flattening, one might incorrectly infer that orders are closed without payment settlement.

### Flattening on `Package`

Expected cases:

- Case `P1`:
  1. `Pack Package`
  2. `Dispatch Package`

- Case `P2`:
  1. `Pack Package`
  2. `Dispatch Package`

Copied shared events:

- None between `P1` and `P2`; they only share the same activity names.

Likely DFG edge:

- `Pack Package -> Dispatch Package`

Omitted lifecycle aspects:

- Item and order context is not visible in the flattened Package log.
- Delivery confirmation is not directly linked to packages, so it is omitted.
- Invoice and payment lifecycle are omitted.

Misleading interpretations:

- `P1` may appear to have the same simple lifecycle as `P2`, hiding the fact that `P1` combines items from two different orders.
- The Package view may suggest that packages are complete after dispatch, even though delivery confirmation happens later at the Delivery level.

### Flattening on `Delivery`

Expected cases:

- Case `D1`:
  1. `Dispatch Package`
  2. `Confirm Delivery`

- Case `D2`:
  1. `Dispatch Package`
  2. `Confirm Delivery`

Copied shared events:

- None between `D1` and `D2`; they share activity names only.

Likely DFG edge:

- `Dispatch Package -> Confirm Delivery`

Omitted lifecycle aspects:

- Package contents are not visible.
- Order and item involvement are not visible.
- Invoice and payment lifecycle are not visible.

Misleading interpretations:

- The Delivery view may suggest two independent, identical delivery processes.
- It hides that `D1` carries `P1`, which is cross-order, while `D2` carries `P2`, which belongs to `O100` only.
- It hides the long gap between dispatching `D2` and confirming it on the next day.

### Flattening on `Invoice`

Expected case:

- Case `V1`:
  1. `Issue Invoice`
  2. `Record Payment`
  3. `Record Payment`

Copied shared events:

- There is only one invoice case, so no cross-case copying occurs.
- Both payment events are collected into the same invoice case.

Likely DFG edges:

- `Issue Invoice -> Record Payment`
- `Record Payment -> Record Payment`

Omitted lifecycle aspects:

- Order creation and item addition are omitted.
- Packaging and delivery are omitted.
- The fact that `V1` bills two orders is not visible from the flattened event sequence alone unless object attributes or the original O2O relations are inspected.

Misleading interpretations:

- The Invoice view may look like a simple single-case payment process.
- It may hide that the invoice covers two separate orders, `O100` and `O200`.
- Without the `ocel:amount` attribute, the two `Record Payment` events appear indistinguishable.

### Why flattening on `Payment` would be weak here

Flattening on `Payment` would produce two extremely short cases:

- Case `M1`:
  1. `Record Payment`

- Case `M2`:
  1. `Record Payment`

This is analytically weak because:

- Each payment trace has only one event.
- There are no directly-follows edges inside each payment case.
- The relationship between `M1` and `M2` exists only through the shared invoice `V1`, which is lost if one insists on treating each payment as an independent case.
- Payment allocation to orders is intentionally not modeled, so a Payment flattening cannot answer order-level settlement questions.

## 6. Modeling alternatives

### Alternative 1: Source-minimal E2O relations

Policy:

- Relate events only to objects explicitly named in the event description.
- For example, `Pack Package P2 with I2` would relate only to `P2` and `I2`, not to `O100`.
- Dispatch and confirmation would remain package/delivery-centric.
- Payments would remain invoice-centric.

Effect on discovery:

- Order flattening would be sparser.
- `O100` might miss packaging of `P2` unless analytical propagation is performed.
- Object-centric graphs would be cleaner and closer to raw event observations.
- Less relation inflation, but weaker flattened order completeness.

### Alternative 2: Full operational involvement

Policy:

- Add direct E2O links from logistics events to all orders and items affected.
- For example:
  - dispatching `P1` would directly relate to `O100`, `O200`, `I1`, and `I3`;
  - confirming `D1` would directly relate to `P1`, and possibly to the orders/items inside it;
  - payments might be allocated to orders using some business rule.

Effect on discovery:

- Order flattening would show a more complete end-to-end order lifecycle.
- DFGs would contain more edges between order-centric activities and logistics activities.
- However, this can cause relation inflation and make shared events appear more directly synchronized than the source system actually recorded.
- Payment allocation could become arbitrary unless the source provides explicit allocation rules.

### Alternative 3: O2O-propagated analytical relations

Policy:

- Keep source E2O relations minimal and provenance-clean.
- Use O2O relations such as `Order contains Item`, `Package packs Item`, and `Delivery carries Package` to propagate analytical relations.
- Store propagated E2O rows separately or with `derived:` qualifiers, for example:
  - `derived:order_dispatched`
  - `derived:order_delivered`
  - `derived:order_paid`

Effect on discovery:

- Flattened views can be enriched without pretending that inferred links were directly observed.
- Analysts can compare source-only and source-plus-derived discoveries.
- If derived relations are not filtered or labeled properly, they can be mistaken for source facts.
- This alternative gives the best provenance control but requires more disciplined pipeline design.

## 7. Failure modes

1. **Relation inflation**
   - Adding every possible indirect link as a direct E2O relation can make every event appear related to every object.
   - Example: linking `Confirm Delivery D1` directly to `O100`, `O200`, `I1`, and `I3` may be analytically derivable, but it overstates the direct operational observation.

2. **Missing direct E2O links**
   - If an event should be visible in a flattened view but lacks a direct relation, the flattened log will omit it.
   - Example: if `Pack Package P2` were not linked to `O100`, the Order flattening for `O100` would miss that packaging step.

3. **Treating O2O propagation as observation**
   - O2O links such as `P1 packs I1` are structural facts.
   - If they are copied into E2O relations without a derived qualifier, downstream discovery may treat them as event observations.
   - This damages provenance and can distort frequency-based discovery.

4. **Duplicate shared events after flattening**
   - Shared events such as `Reserve Stock`, `Pack Package P1`, and `Issue Invoice V1` are copied into multiple object cases.
   - In an Order flattening, this inflates their frequencies and can make separate orders look artificially synchronized.

5. **Ambiguous payment allocation**
   - `M1` and `M2` settle `V1`, not directly `O100` or `O200`.
   - If an analysis forces payment allocation to orders without a business rule, it may produce misleading order-level payment behavior.

6. **Overly short Payment traces**
   - Flattening on `Payment` gives one-event cases for `M1` and `M2`.
   - DFG discovery becomes uninformative.
   - The meaningful payment process appears only when flattening on `Invoice` or using object-centric discovery.

7. **Constructor/API version mismatch**
   - PM4Py OCEL APIs can differ by version.
   - The constructor may require positional arguments, or the class may be named `OCEL2`.
   - Discovery functions may return tuples or objects.
   - The pipeline isolates this risk by keeping the DataFrame semantics stable and commenting the version-dependent construction line.

8. **False total order for same-time events**
   - Flattening often imposes a total order by timestamp and event identifier.
   - This dataset has no timestamp ties, but in general, same-time events could be falsely interpreted as strictly sequential.
   - This is especially dangerous for shared events or batch operations.

9. **Qualifier drift**
   - Inconsistent qualifiers such as `packed`, `packs`, `packed_item`, and `item_packed` can fragment analysis.
   - The controlled `src:` vocabulary reduces this risk.

10. **Timezone-naive timestamps**
   - If timestamps lose timezone information, cross-system ordering can become ambiguous.
   - The pipeline explicitly uses UTC-aware timestamps.
