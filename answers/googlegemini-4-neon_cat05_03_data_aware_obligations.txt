## 1. Temporal Data Semantics

To evaluate compliance faithfully without introducing anachronisms, we define the event log as a finite set of events $E$, where each event $e \in E$ belongs to a case $c(e)$, has an activity $\text{act}(e)$, a UTC event timestamp $t_{\text{evt}}(e)$, a source-system tie-break integer $\text{idx}(e)$, and a partial map of attribute updates $\Delta(e)$ over $A = \{\text{amount}, \text{risk\_level}, \text{jurisdiction}, \text{customer\_type}, \text{exemption\_id}\}$.

1. **Total Event Ordering and Same-Timestamp Tie-Breaking (R7)**
   Within each case $c$, events are totally ordered by the lexicographic key $k(e) = (t_{\text{evt}}(e), \text{idx}(e))$:
   $$e_1 \prec e_2 \iff c(e_1) = c(e_2) \land \big(t_{\text{evt}}(e_1) < t_{\text{evt}}(e_2) \lor (t_{\text{evt}}(e_1) = t_{\text{evt}}(e_2) \land \text{idx}(e_1) < \text{idx}(e_2))\big).$$
   Using `event_index` resolves equal-timestamp ties deterministically. For example, in `TX-311`, `Enhanced_Review` at `16:20:00Z` (`event_index=3`) strictly precedes `Update_Jurisdiction` to `DE` at `16:20:00Z` (`event_index=4`), meaning the review evaluated `US` while the subsequent release at `16:30:00Z` occurred under `DE`.

2. **State Reconstruction and Blank-Cell Semantics**
   Blank cells represent *no update at this event* ($\bot_{\text{no-op}}$), not deletion or assignment of null/low-risk defaults. For any attribute $a \in A$, the reconstructed state at event $e$, written $S(e)[a]$, is obtained strictly via forward-fill over events $e' \preceq e$:
   $$S(e)[a] = \begin{cases} \Delta(e)[a] & \text{if } \Delta(e)[a] \text{ is non-blank}, \\ S(e_{\text{prev}})[a] & \text{if } \Delta(e)[a] \text{ is blank and } e_{\text{prev}} \text{ immediately precedes } e, \\ \text{UNKNOWN} & \text{if } a \text{ has never been populated at or before } e. \end{cases}$$
   If $S(e)[a] = \text{UNKNOWN}$ and $a$ is decisive for a rule trigger or invalidation check, three-valued logic ($\text{TRUE}, \text{FALSE}, \text{UNKNOWN}$) propagates to `INDETERMINATE` under R6 rather than defaulting to a benign value.

3. **Prohibition of Final-Attribute Backward Leakage (R7)**
   Case-level final values—and any attribute recorded at events $e_{\text{post}} \succ e_{\text{rel}}$ (such as `Settlement_Confirmed` in `TX-305` or `Record_Exemption` in `TX-302`/`TX-310`)—are never copied backward into $S(e_{\text{rel}})$. Post-release events may inform *evidential investigation* (e.g., corroborating an outage-delayed database insert or signaling a reconciliation discrepancy), but they do not retroactively populate event-time decision state unless independent contemporaneous proof establishes the value at $e_{\text{rel}}$.

4. **Material Data Changes (R1, R4)**
   A data update $e_u$ occurring after a review $e_r$ ($e_r \prec e_u \prec e_{\text{rel}}$) is **material** with respect to $e_r$ if:
   - **Amount increase > 20% (R4):** Both $S(e_r)[\text{amount}]$ and $S(e_u)[\text{amount}]$ are known and $\frac{S(e_u)[\text{amount}] - S(e_r)[\text{amount}]}{S(e_r)[\text{amount}]} > 0.20$. An amount decrease ($S(e_u)[\text{amount}] < S(e_r)[\text{amount}]$) does *not* by itself invalidate $e_r$. If either amount is `UNKNOWN`, materiality is `UNKNOWN` (not safely classifiable without additional evidence).
   - **Risk/KYC/Jurisdiction escalation:** An upward risk reclassification (e.g., to `HIGH`), customer-type escalation (to `PEP`), or a jurisdiction change into a foreign/sanctioned scope after $e_r$ renders a prior review stale for rules whose triggers depend on those attributes. (Conversely, if a jurisdiction change moves the transaction *out* of R1's scope—e.g., `US -> DE` before release—R1 itself is no longer triggered at release.)

5. **Four Distinct Temporal Dimensions**
   - **Event time ($t_{\text{evt}}$):** When the operational activity occurred in the source system (`time:timestamp`, refined by `event_index`). Governs obligation triggers and activity ordering.
   - **Effective time ($t_{\text{eff}}$):** When a policy instrument or attribute update takes legal/rule effect (defaults to $t_{\text{evt}}$ unless an authoritative instrument establishes otherwise, such as an exemption's `effective_from`). Must satisfy $t_{\text{eff}} \le t_{\text{evt}}(e_{\text{rel}})$ and $t_{\text{evt}}(e_{\text{rel}}) \le t_{\text{exp}}$.
   - **Record time ($t_{\text{rec}}$):** When the fact is persisted in the compliance/logging database (e.g., `Record_Exemption` at `11:00:00Z`). Late $t_{\text{rec}}$ does not automatically void an exemption if $t_{\text{evid}}$ proves timely approval.
   - **Evidence time ($t_{\text{evid}}$):** When independent, tamper-evident proof of an authorization was generated (e.g., a qualified digital signature timestamp: `09:05` for `EX-77` vs. `10:30` for `EX-88`). Under R5, $t_{\text{evid}}$ outweighs a self-declared/displayed backdated date on a PDF when assessing whether approval actually existed before release.

### Formal Pseudo-Logic (R1–R7)

**Temporal Relations and Notation:**
- $e_1 \prec e_2$ means event $e_1$ strictly precedes $e_2$ in the same case under lexicographic order $(t_{\text{evt}}, \text{idx})$ (R7).
- $e_1 \preceq e_2 \iff (e_1 \prec e_2) \lor (e_1 = e_2)$.
- $t_1 \le t_2$ is standard UTC wall-clock comparison (`t_1` on or before `t_2`).
- $\text{val}(e, a) \in D_a \cup \{\bot\}$ denotes the forward-filled state $S(e)[a]$ computed exclusively from $\{e' \mid e' \preceq e\}$ (R7; no backward projection).
- Three-valued Kleene logic is used over $\{\top, \bot_{\text{F}}, \text{U}\}$ so unknown decisive predicates yield $\text{U}$ (`INDETERMINATE`, R6).

```text
-- R7: Event-time order & forward-only state reconstruction
e1  e2  :<=>  case(e1) = case(e2)  ( t_evt(e1) < t_evt(e2)
                 (t_evt(e1) = t_evt(e2)  idx(e1) < idx(e2)) )

S(e)[a]  :=  last non-blank (e')[a] over { e' | e'  e }, else UNKNOWN.

-- R4: Material amount invalidation of a review e_r before e_rel
AmountInvalidated(e_r, e_rel) :=
  IF S(e_r)[amount] = UNKNOWN  S(e_rel)[amount] = UNKNOWN THEN UNKNOWN
  ELSE  e_u : act(e_u) = Update_Amount  e_r  e_u  e_rel
                S(e_u)[amount] > 1.20 * S(e_r)[amount].
  (Note: S(e_u)[amount]  S(e_r)[amount] never sets AmountInvalidated := TRUE.)

MaterialChangeAfter(e_r, e_rel) :=
  AmountInvalidated(e_r, e_rel)
    e_u : e_r  e_u  e_rel  (
       (act(e_u) = Risk_Reclassify  S(e_u)[risk_level] = HIGH  S(e_r)[risk_level]  HIGH)
      (act(e_u) = Update_Customer_Type  S(e_u)[customer_type] = PEP  S(e_r)[customer_type]  PEP)
      (act(e_u) = Update_Jurisdiction  S(e_u)[jurisdiction]  S(e_r)[jurisdiction]
         S(e_u)[jurisdiction]  DE)
    ).

-- R5: Defeasible exemption validity for rule R at release e_rel
ValidExemption(x, R, e_rel) :=
  approved_by(x) = Head_Compliance
   R  waived_rules(x)
   t_eff(x)  t_evt(e_rel)  t_exp(x)
   ScopeMatch(x, S(e_rel))
   CrediblePreReleaseEvidence(x, e_rel)
  where:
    ScopeMatch(x, s) := s[jurisdiction]  jur_scope(x)
                       s[customer_type]  cust_scope(x)
                       s[amount]  UNKNOWN  s[amount]  max_amount(x)
    CrediblePreReleaseEvidence(x, e_rel) :=
      (t_evid(x)  t_evt(e_rel)  independent_verifiable(x))
      -- Displayed backdated date alone or uncorroborated conflicted witness fails this clause.

-- R1: Foreign high-value enhanced review
Trigger_R1(e_rel) := (S(e_rel)[jurisdiction]  DE)  (S(e_rel)[amount]  100000).
Satisfied_R1(e_rel) :=
  ( e_er : act(e_er) = Enhanced_Review  e_er  e_rel  ¬MaterialChangeAfter(e_er, e_rel))
   ( x : x = S(e_rel)[exemption_id]  ValidExemption(x, R1, e_rel)).
Rule_R1(e_rel) := Trigger_R1(e_rel)  Satisfied_R1(e_rel).

-- R2: High-risk or PEP approval
Trigger_R2(e_rel) := (S(e_rel)[risk_level] = HIGH)  (S(e_rel)[customer_type] = PEP).
Satisfied_R2(e_rel) :=
   e_er, e_ca :
    act(e_er) = Enhanced_Review  act(e_ca) = Compliance_Approve
     e_er  e_ca  e_rel
     ¬MaterialChangeAfter(e_er, e_rel)
     approves_enhanced_packet(e_ca, e_er).
Rule_R2(e_rel) := Trigger_R2(e_rel)  Satisfied_R2(e_rel).

-- R3: Sanctions-list update re-screening
Trigger_R3(e_rel) :=
   e_lu : act(e_lu) = Sanctions_List_Update
            (e_lu)[jurisdiction] = S(e_rel)[jurisdiction]
            e_lu  e_rel.
Satisfied_R3(e_rel) :=
   e_lu : (act(e_lu) = Sanctions_List_Update  (e_lu)[jurisdiction] = S(e_rel)[jurisdiction]  e_lu  e_rel)
            ( e_ss : act(e_ss) = Sanctions_Screen  e_lu  e_ss  e_rel).
Rule_R3(e_rel) := Trigger_R3(e_rel)  Satisfied_R3(e_rel).

-- R6: Case verdict aggregation (3-valued)
Verdict(c) :=
  IF  R  {R1, R2, R3} : Rule_R(e_rel) = FALSE THEN NONCOMPLIANT
  ELSE IF  R  {R1, R2, R3} : Rule_R(e_rel) = UNKNOWN THEN INDETERMINATE
  ELSE IF R1 satisfied ONLY via ValidExemption(x, R1, e_rel) THEN JUSTIFIED_EXCEPTION
  ELSE COMPLIANT.
```

## 4. Ambiguities and Alternative Readings

### 1. TX-305 (`INDETERMINATE` — Missing Pre-Release Amount)
- **Why indeterminate:** The amount was unavailable at creation, omitted from the `Enhanced_Review` document (`11:15Z`), and omitted from the `Release_Funds` message (`11:30Z`). Under R6 and R7, next-day `Settlement_Confirmed` (`150,000`) cannot be projected backward without an immutable release payload, and R4 prohibits classifying an increase from an unknown reviewed amount as non-material.
- **Evidence that changes the result:**
  - *To `NONCOMPLIANT`:* Payment-gateway logs, SWIFT/SEPA wire instructions, or bank-submission payloads proving the released amount was $\ge \text{EUR } 100{,}000$ (e.g., `150,000`) while `Enhanced_Review` genuinely had no amount (making the review substantively deficient for an amount-dependent obligation) or reviewed a lower amount that increased by $>20\%$.
  - *To `COMPLIANT`:* Authoritative release-time payload proving the released amount was $< \text{EUR } 100{,}000$ (e.g., a bundled or FX-adjusted settlement caused the `150,000` figure, so R1 never triggered), **or** both an immutable release payload of `150,000` and contemporaneous reviewer workpapers proving the reviewer actually evaluated `150,000` (with $\le 20\%$ variance).

### 2. TX-310 (`NONCOMPLIANT` under fail-closed R5 vs. `INDETERMINATE` / `JUSTIFIED_EXCEPTION` — Contradictory Exemption Evidence)
- **Why ambiguous:** R1 is unequivocally triggered (`AE`, `200,000`) and no `Enhanced_Review` occurred. The case turns entirely on `EX-88`. On one hand, `Release_Funds` at `10:00Z` already referenced `EX-88`, and a witness asserts `Head_Compliance` gave oral approval at `08:45Z`. On the other hand, the qualified signing certificate was created at `10:30Z` (30 minutes *after* release), the DB insert was at `11:00Z`, R5 states a displayed backdated date (`08:50`) alone is not conclusive, and the witness is the conflicted transaction requester.
- **Alternative reading (`INDETERMINATE`):** Under a forensic-hold posture rather than a fail-closed evidentiary burden, TX-310 is classified `INDETERMINATE` because the `10:00Z` log reference to `EX-88` prevents conclusively ruling out prior oral approval without interviewing `Head_Compliance` and inspecting ID-generation logs.
- **Evidence that changes the result:**
  - *To `JUSTIFIED_EXCEPTION`:* Independent, tamper-evident pre-release proof—such as a timestamped email/Teams message/recorded phone call from `Head_Compliance` at `08:45Z`, paired with an audit log showing `EX-88` was generated by Compliance (not self-reserved by the requester) before `10:00Z`, confirming oral approval was policy-permissible and merely formalized via e-signature at `10:30Z`.
  - *To `NONCOMPLIANT` (High confidence):* Audit logs showing `EX-88` was drafted/approved only at `10:25–10:30Z` (or `Head_Compliance` denying pre-release approval), proving retroactive backdating.

### 3. TX-302 (`COMPLIANT` vs. `JUSTIFIED_EXCEPTION` — Redundant Review + Late-Recorded Valid Exemption)
- **Why nuanced:** TX-302 contains *both* a timely `Enhanced_Review` (`09:20Z`, with no subsequent material change before `09:40Z` release) *and* a referenced exemption `EX-77` recorded late in the database (`11:00Z`) due to a documented outage, but backed by a valid qualified digital signature at `09:05Z` (effective `09:00Z`).
- **Alternative readings:**
  - *Primary reading (`COMPLIANT`):* Because `Enhanced_Review` completed before release after all data updates, R1's primary control was directly satisfied; no exception was actually needed to avoid a violation.
  - *Alternative reading (`JUSTIFIED_EXCEPTION`):* If governance records treat the release as having relied on `EX-77` (or if quality assurance later found the `09:20Z` `Enhanced_Review` incomplete), TX-302 would be classified `JUSTIFIED_EXCEPTION` because `EX-77` satisfies every clause of R5 despite its `11:00Z` record time.
  - *Evidence that would change to `NONCOMPLIANT`:* Proof that the `09:20Z` `Enhanced_Review` was invalid **and** that the `09:05Z` signature certificate was compromised or outside scope.

### 4. TX-311 (`COMPLIANT` vs. `NONCOMPLIANT` / `INDETERMINATE` — Same-Timestamp Jurisdiction Change to `DE`)
- **Why nuanced:** By R7 (`event_index 3 < 4` at `16:20:00Z`), `Enhanced_Review` evaluated `US` (`115,000`), and immediately afterward `Update_Jurisdiction` changed the jurisdiction to `DE`. Evaluating R1 on the event-time state at `Release_Funds` (`16:30Z`) yields `jurisdiction = DE`, so R1 does not trigger (`COMPLIANT`).
- **Alternative readings and counterfactuals:**
  - *Counterfactual direction (`DE -> US`):* Had `event_index 4` changed jurisdiction from `DE` to `US` (or another foreign jurisdiction), the `event_index` tie-break would flip compliance: `Update_Jurisdiction` after `Enhanced_Review` would render the review stale under R1 (`NONCOMPLIANT`), whereas `idx=4` preceding `idx=3` would have been `COMPLIANT`.
  - *Anti-evasion / data-integrity reading:* If compliance policy treats *any* post-review jurisdiction change on a transaction previously flagged for foreign high-value review as a material change requiring reviewer confirmation (to prevent jurisdiction-shopping / domestic re-coding to bypass controls), TX-311 would become `NONCOMPLIANT`—or `INDETERMINATE` if evidence is needed to verify that `DE` was a genuine correction rather than an unverified override.

### 5. TX-306 (`COMPLIANT` vs. Stricter R2 Interpretation — Post-Approval Non-Material Amount Increase)
- **Why worth noting:** `Update_Amount` (`220k -> 230k`, `+4.55%`) occurred at `12:30Z`, *after* both `Enhanced_Review` (`12:15Z`) and `Compliance_Approve` (`12:25Z`). Under R4, `+4.55% <= 20%` does not invalidate `Enhanced_Review`, so TX-306 is `COMPLIANT`.
- **Alternative interpretation:** If an institution's internal R2 sign-off standard treated `Compliance_Approve` as binding strictly to an immutable approved amount (with zero tolerance for post-approval increases on `HIGH`/`PEP` transactions, regardless of R4's 20% threshold), TX-306 would shift to `NONCOMPLIANT`.

### 6. TX-307 (`NONCOMPLIANT` — Packet-Scope Semantics of `Compliance_Approve`)
- **Alternative interpretation:** Under the stated rules and semantic facts, `Standard_Review` is not `Enhanced_Review`, and `Compliance_Approve` over a standard packet does not cure R2 (`NONCOMPLIANT`). Only if documentary evidence proved that `rev07` actually performed all substantive enhanced-due-diligence checks and mislabeled the activity code as `Standard_Review` (a logging defect rather than a control failure) would the substantive finding shift toward `COMPLIANT` (with a logging-control deficiency).

## 6. Why Control-Flow-Only Conformance Is Insufficient

Pure control-flow conformance (Petri nets, alignments, BPMN replay, or activity-only DECLARE constraints) evaluates only the sequence of activity labels $\langle \text{act}(e_1), \dots, \text{act}(e_n) \rangle$. In data- and time-sensitive compliance logs, it suffers from at least seven distinct failure modes:

1. **Final-State Leakage (Retroactive Projection):**
   Even when analysts augment control-flow models with *case-level* attributes (a common shortcut in process mining), case attributes typically store the final state. Copying `Settlement_Confirmed`'s `150,000` backward in `TX-305` fabricates a release-time amount that was unknown at decision time; copying `Record_Exemption` backward in `TX-310` erases the distinction between pre-release approval and post-hoc recording.

2. **Post-Hoc Exemptions and Evidential Asymmetry:**
   Control-flow traces cannot distinguish `EX-77` (`TX-302`) from `EX-88` (`TX-310`) on exemption timing: both cases have `Release_Funds` followed by `Record_Exemption` at `11:00Z`. Determining compliance requires comparing four separate timestamps ($t_{\text{evt}}, t_{\text{eff}}, t_{\text{rec}}, t_{\text{evid}}$), verifying scope bounds (`jurisdiction`, `customer_type`, `max_amount`), and weighing independent cryptographic signatures against conflicted witness claims.

3. **Material vs. Non-Material Data Changes After Review (R4):**
   `TX-306`, `TX-308`, and `TX-309` all exhibit the exact activity pattern `Enhanced_Review -> Update_Amount -> Release_Funds`. Control-flow conformance must either reject all three or accept all three; it cannot compute the relative delta (`+4.55%` vs. `-28.57%` vs. `+22.88%`) to enforce R4's asymmetric `> 20%` upward invalidation rule.

4. **Conditional Activation of Obligations:**
   R1, R2, and R3 are dormant unless specific attribute predicates hold at `Release_Funds` (`jurisdiction != DE  amount >= 100k`; `risk = HIGH  customer_type = PEP`; `Sanctions_List_Update` matching the case's *current* jurisdiction). A static control-flow requirement for `Enhanced_Review` or `Compliance_Approve` produces false positives on low-risk domestic cases and false negatives when mid-case updates (`Risk_Reclassify` in `TX-303`, `Update_Customer_Type` in `TX-307`, `Update_Amount` in `TX-301`) dynamically activate obligations mid-flight.

5. **Missing and Unknown Data Semantics (R6):**
   Control-flow replay has no representation of three-valued uncertainty. In `TX-305`, the activity sequence `Create_Transaction -> Enhanced_Review -> Release_Funds -> Settlement_Confirmed` appears completely well-formed, masking the fatal fact that `amount` was missing throughout the entire review and release lifecycle.

6. **Same-Timestamp Ordering and Nondeterministic Ties (R7):**
   Standard process-mining tools that sort strictly on `time:timestamp` treat equal-timestamp events (`TX-311` at `16:20:00Z`) as unordered or arbitrarily ordered. Without deterministic tie-breaking via `event_index`, the tool cannot establish whether `Enhanced_Review` evaluated `US` or `DE`, nor whether `Update_Jurisdiction` occurred before or after review.

7. **Artifact / Packet Provenance and Cross-Event Semantic Binding:**
   In `TX-307`, the sequence `Standard_Review -> Compliance_Approve -> Release_Funds` satisfies any coarse `Review -> Approve -> Release` constraint, yet violates R2 because `Compliance_Approve` reviewed a *standard* packet rather than an *enhanced* packet. Similarly, in `TX-304`, R3 is not merely `Sanctions_List_Update -> Sanctions_Screen`; it binds the updated jurisdiction (`XZ`) to the transaction's active jurisdiction at release.

## 7. Recommended Logging and Control Improvements

To eliminate indeterminacy, prevent post-hoc disputes, and shift from detective forensics to deterministic pre-release enforcement, the platform should implement the following logging and control upgrades:

1. **Immutable Release Payloads (Solves TX-305):**
   Emit a tamper-evident, schema-validated JSON snapshot (with SHA-256 hash) on every `Release_Funds` event capturing the exact effective `amount`, `currency`, `risk_level`, `jurisdiction`, `customer_type`, `exemption_id`, and the `event_id`s of the reviews/approvals/screens relied upon. Add a **preventive circuit breaker** that blocks `Release_Funds` (or forces manual escalation) whenever a decisive attribute such as `amount` is `UNKNOWN` due to an upstream feed outage.

2. **Explicit Multi-Temporal Timestamps and RFC 3161 Timestamping (Solves TX-302, TX-310):**
   Replace single-timestamp logging with four explicit UTC fields on compliance artifacts and exemptions: `event_time`, `effective_time`, `record_time`, and `signature_time` (backed by a qualified Trust Service Provider / RFC 3161 timestamp authority). Use a durable local write-ahead queue/outbox so database outages do not delay exemption issuance metadata, and prohibit referencing an `exemption_id` at `Release_Funds` unless a signed token (JWT/X.509) is presented and verified inline at release time.

3. **Policy and Rule Versioning:**
   Log `policy_version` (e.g., `TX-POL-2026.04`) and the pre-release policy engine's evaluation output (`triggered_rules`, `satisfied_rules`, `waived_rules`, `decision_id`) at every `Release_Funds` event so audits are reproducible even after thresholds (such as the `EUR 100,000` or `20%` rules) evolve.

4. **Structured Exemption Scope and Authority Registry:**
   Store exemptions as machine-checkable policy objects containing `exemption_id`, `issuer_role`, `issuer_id`, `issued_at`, `effective_from`, `expires_at`, `allowed_jurisdictions`, `allowed_customer_types`, `max_amount`, `waived_rules` (explicitly enforcing that R1 waivers cannot waive R2/R3), `approval_channel`, and `cryptographic_signature`. Disallow undocumented oral exemptions—or require an emergency dual-control ticket created by `Head_Compliance` *before* release.

5. **Change Provenance and Review-to-State Lineage (Solves TX-301, TX-306, TX-307, TX-309):**
   - Attach a `reviewed_state_hash` and `reviewed_amount` to every `Standard_Review` and `Enhanced_Review`, and require `Compliance_Approve` to reference a foreign key `approved_review_id` (enforcing `review_type == ENHANCED` whenever R2 is active).
   - Log `previous_value`, `new_value`, `pct_delta`, `change_reason`, and `change_actor` on all `Update_*` and `Risk_Reclassify` events, automatically invalidating open review tokens whenever a material threshold (`>20%` amount increase, risk escalation to `HIGH`, customer upgrade to `PEP`, or jurisdiction shift) is crossed.
   - Flag post-review jurisdiction changes from foreign to domestic (`US -> DE`, as in `TX-311`) with a `jurisdiction_downgrade_reason` and optional secondary check to mitigate control-bypass risk.

6. **Stable Monotonic Event Ordering and Explicit Null Semantics (Solves TX-311, TX-305):**
   Persist microsecond/nanosecond UTC timestamps alongside a strictly monotonic case-level `sequence_no` (not just per-timestamp `event_index`) in all XES/OCEL exports so downstream process-mining tools preserve exact causality. Distinguish `NO_CHANGE` (field omitted in delta event) from `UNKNOWN_FEED_ERROR` and explicit `NULL` so analytics pipelines never confuse blank log cells with missing upstream data.
