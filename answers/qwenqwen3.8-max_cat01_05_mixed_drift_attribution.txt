## 2. Raw-versus-normalized interpretation

The raw/mapped fitness gap shows that much of the March conformance collapse is an identifier and provenance problem, not necessarily a business-process rupture. Raw fitness falls from about 0.93 to 0.55, while mapped fitness remains near 0.90 because `Eligibility Screen` is reconciled and duplicated `Open Case` events are removed. This implies that the old normative model became incompatible with new log labels, but it does not imply that eligibility work itself was unchanged; mapping restores token replayability while leaving semantics, data quality, and responsibility boundaries unverified. Duplicated technical events inflate case starts, create artificial loops, and bias conformance, variant counts, and throughput estimates. Missing resource identifiers mainly undermine resource, handoff, and queue analyses; they can also hide team-specific bottlenecks without changing activity order. After May, however, logging drift alone is insufficient. Even after mapping, rework variants, `Assess -> Request Info -> Collect Documents` rates, supplier-Z exposure, and cycle-time quantiles rise together and only partially reverse when Supplier Z recovers. The normalized DFG distance remains materially above baseline, and queue waiting, not just `Assess` service time, increases. Thus, March is best treated primarily as semantic drift, while May onward reflects real control-flow, population, and capacity changes.

def _require_pm4py():
    try:
        import pm4py
        return pm4py
    except ImportError as exc:
        raise ImportError("PM4Py is required for Part B event-level functions.") from exc


def format_event_log(
    df: pd.DataFrame,
    case_id: str = "case:concept:name",
    activity_key: str = "concept:name",
    timestamp_key: str = "time:timestamp"
):
    """Format an event dataframe using PM4Py standard column semantics."""
    pm4py = _require_pm4py()
    return pm4py.format_dataframe(
        df,
        case_id=case_id,
        activity_key=activity_key,
        timestamp_key=timestamp_key
    )


def slice_window(log, start, end, **kwargs):
    """Slice a log by time range without mutating the input object."""
    pm4py = _require_pm4py()
    return pm4py.filter_time_range(log, start, end, **kwargs)


def compute_monthly_dfgs(
    df: pd.DataFrame,
    month_col: str = "month",
    case_id: str = "case:concept:name",
    activity_key: str = "concept:name",
    timestamp_key: str = "time:timestamp",
    min_cases: int = 30
) -> Dict[Any, Dict[str, Any]]:
    """Compute monthly DFGs, skipping months with insufficient support."""
    pm4py = _require_pm4py()
    results = {}

    for month, group in df.groupby(month_col):
        if group[case_id].nunique() < min_cases:
            continue

        log = pm4py.format_dataframe(
            group,
            case_id=case_id,
            activity_key=activity_key,
            timestamp_key=timestamp_key
        )
        dfg, start_activities, end_activities = pm4py.discover_dfg(log)
        results[month] = {
            "dfg": dfg,
            "start_activities": start_activities,
            "end_activities": end_activities,
            "case_count": group[case_id].nunique()
        }

    return results


def compute_variants(log):
    """Compute case variants from a formatted PM4Py log."""
    pm4py = _require_pm4py()
    return pm4py.get_variants(log)


def compute_temporal_profile(log):
    """Compute temporal profile from a formatted PM4Py log."""
    pm4py = _require_pm4py()
    return pm4py.discover_temporal_profile(log)


def discover_log_skeleton_safe(log, noise_threshold: float = 0.1):
    """Optionally discover a log skeleton if available in the PM4Py version."""
    pm4py = _require_pm4py()
    try:
        return pm4py.discover_log_skeleton(log, noise_threshold=noise_threshold)
    except AttributeError:
        return None


def discover_declare_safe(log, noise_threshold: float = 0.1):
    """Optionally discover a DECLARE model if available in the PM4Py version."""
    pm4py = _require_pm4py()
    try:
        return pm4py.discover_declare(log, noise_threshold=noise_threshold)
    except AttributeError:
        try:
            from pm4py.algo.discovery.declare import algorithm as declare_algorithm
            return declare_algorithm.apply(log)
        except Exception:
            return None


def normalize_label_mapping(
    df: pd.DataFrame,
    activity_key: str = "concept:name",
    label_mapping: Optional[Mapping[str, str]] = None,
    duplicate_technical_activity: Optional[str] = "Open Case",
    case_id: str = "case:concept:name",
    timestamp_key: str = "time:timestamp"
) -> pd.DataFrame:
    """
    Create a normalized copy of the event dataframe.

    - Preserves original activity in original_activity.
    - Applies label mapping, e.g. Eligibility Screen -> Validate Eligibility.
    - Removes duplicated technical Open Case events, keeping the first per case.
    """
    normalized = df.copy()
    normalized["original_activity"] = normalized[activity_key]

    if label_mapping:
        normalized[activity_key] = normalized[activity_key].replace(label_mapping)

    if duplicate_technical_activity:
        is_technical = normalized[activity_key] == duplicate_technical_activity
        duplicated_technical = normalized.duplicated(
            subset=[case_id, activity_key],
            keep="first"
        )
        normalized = normalized[~(is_technical & duplicated_technical)]

    return normalized


def compare_raw_and_normalized(
    df: pd.DataFrame,
    label_mapping: Optional[Mapping[str, str]] = None,
    duplicate_technical_activity: Optional[str] = "Open Case",
    case_id: str = "case:concept:name",
    activity_key: str = "concept:name",
    timestamp_key: str = "time:timestamp"
) -> Dict[str, Any]:
    """
    Compare raw and normalized logs without overwriting the original dataframe.
    Returns DFGs and variants for both representations.
    """
    pm4py = _require_pm4py()

    raw_log = format_event_log(
        df,
        case_id=case_id,
        activity_key=activity_key,
        timestamp_key=timestamp_key
    )

    normalized_df = normalize_label_mapping(
        df,
        activity_key=activity_key,
        label_mapping=label_mapping,
        duplicate_technical_activity=duplicate_technical_activity,
        case_id=case_id,
        timestamp_key=timestamp_key
    )

    normalized_log = format_event_log(
        normalized_df,
        case_id=case_id,
        activity_key=activity_key,
        timestamp_key=timestamp_key
    )

    raw_dfg, raw_start, raw_end = pm4py.discover_dfg(raw_log)
    norm_dfg, norm_start, norm_end = pm4py.discover_dfg(normalized_log)

    return {
        "raw_dfg": raw_dfg,
        "raw_start_activities": raw_start,
        "raw_end_activities": raw_end,
        "normalized_dfg": norm_dfg,
        "normalized_start_activities": norm_start,
        "normalized_end_activities": norm_end,
        "raw_variants": pm4py.get_variants(raw_log),
        "normalized_variants": pm4py.get_variants(normalized_log),
        "normalized_dataframe": normalized_df
    }

## 9. Provisional attribution

The strongest attribution is the March migration as a logging/semantic and provenance change. The sudden raw-fitness collapse, new label count, duplicated `Open Case` events, and missing resource identifiers, together with near-normal mapped DFG and mapped fitness, support this at high confidence. It is not evidence of a major business-process break. The next strongest conclusion is that Supplier Z’s May disruption caused real control-flow rework: supplier exposure jumps, `Request Info` and rework variants rise sharply, and September recovery partially reverses the pattern. This is high-to-moderate confidence, tempered by Supplier Z’s non-random customer mix and pre-existing complexity. Staffing cuts likely caused queueing degradation from mid-June onward; the fact that `Assess` service time rose only modestly while waiting before `Assess` and p90 cycle time increased is consistent with capacity loss. This is moderate confidence because rework and priority changes also increase queue load and the aggregates lack assessor-level utilization. The October-November deterioration is best attributed to seasonal renewal case mix, with high-complexity share, volume, and `Senior Assessment` rates rising; confidence in the mix change is high, but its performance impact is confounded by residual staffing constraints and priority routing. The July priority rule plausibly redistributed waiting from high-complexity to standard cases, but the evidence is only plausible, not strong, because class-specific waiting is absent. December improvement cannot be cleanly assigned to overtime/campaigns; supplier recovery, lower seasonal load, and backlog decay mediate the improvement. Interaction is substantial: supplier rework increased assess workload, staffing loss amplified waiting, priority changed who bore delay, and seasonality changed the population. I would revise the account if mapped, supplier-stratified logs showed rework rising before May, if standard-case waiting did not worsen after July, or if complexity-standardized cycle times remained flat in October.

## 10. Monitoring decision rules

1. IF raw model fitness drops sharply while mapped fitness remains stable and label/duplicate anomalies increase, THEN treat the incident as logging/schema drift and repair mapping before operational escalation, BECAUSE conformance loss is driven by semantic/provenance drift rather than actual control-flow change.

2. IF mapped fitness or normalized DFG distance remains degraded after label mapping and deduplication, THEN investigate real behavioral drift, BECAUSE residual deviation after normalization indicates changed process behavior, not merely renamed events.

3. IF `Assess -> Request Info -> Collect Documents` rates rise first in Supplier Z cases, THEN trigger supplier document-quality escalation and bundle-completeness checks, BECAUSE incomplete supplier bundles cause repeated document collection and assessment loops.

4. IF queue waiting before `Assess` rises much faster than `Assess` service time, especially in p90, THEN review assessor capacity and backlog, BECAUSE staffing loss creates queueing degradation rather than longer individual assessment work.

5. IF high-complexity waiting falls while standard-complexity waiting rises after the priority rule, THEN evaluate priority-rule fairness and capacity tradeoffs, BECAUSE prioritization redistributes delay across case classes instead of removing total delay.

6. IF high-complexity share, volume, and `Senior Assessment` rates rise during renewal season, THEN switch to seasonal baselines and pre-planned staffing rules, BECAUSE recurring population drift changes expected performance and should not be treated as a novel fault.

7. IF December-like improvement coincides with interventions, lower seasonal load, and supplier recovery, THEN use interrupted time series and segmented controls before declaring intervention success, BECAUSE seasonality and external recovery can mediate apparent improvement.
