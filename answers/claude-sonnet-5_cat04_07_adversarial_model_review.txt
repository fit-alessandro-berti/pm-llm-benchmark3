# 1. Review Scope and Assumptions

Before scoring either model I fix **what the model is for**, because the acceptable fitness/precision trade-off is not fixed across uses.

- **Exploration / discovery communication** (business workshops, "what does the process roughly look like"): high recall of variants, tolerance for some over-generalization, low cost of false negatives. Precision can be low; comprehension matters most.
- **Conformance enforcement / compliance gatekeeping** (deciding whether a *specific* case may proceed to release): false negatives (accepting forbidden behavior, e.g., skipping Credit Check) are costly and possibly regulatory violations. Here precision and **negative-behavior rejection** dominate; raw fitness on a positive-only log is close to irrelevant.
- **Simulation / capacity planning**: needs realistic branching probabilities, not just admissible language — neither model as given carries frequencies, so neither is directly usable here without re-attaching statistics.
- **Audit / after-the-fact review**: needs faithful replay of *actually occurred* variants including corrections, with clear diagnostics of deviations — favors precision and clear semantics of duplicate/looping behavior, not sheer permissiveness.

Because P3 and P6 depend on attributes (`external`, `affected_check`) that are **absent from the discovery log**, no purely control-flow model — however fitted — can be judged as compliance-complete. Any claim of "audit-ready" or "compliance enforcement" made about Model S or Model C is therefore already suspect on data-availability grounds alone, independent of the metrics.

I treat the reported numbers as **evidence about model shape**, not as proof of fitness-for-purpose. Both models were computed under an unverified, non-reproducible pipeline (no seeds, no alignment-cost spec, no shared holdout cases), which further limits how much weight any single number should carry.

# 3. Adversarial Review of Model S

**Strongest case for S:** it is a compact, human-readable skeleton that never fails to parse an event it doesn't recognize into a catastrophic mismatch, tolerates missing/reordered events gracefully, and is cheap to align. For early-stage discovery and stakeholder communication (Section 1's first use case) this is a legitimate advantage, and F7's defense ("not intended for enforcement") is coherent *if actually enforced organizationally.*

**Strongest case against it:** the `+` (concurrent) operator over four `X(activity, tau)` leaves removes essentially all control-flow *constraints* — order, mandatoriness, and precedence are all discarded simultaneously. This is not "noise tolerance," it is a **semantic flaw**: noise tolerance would mean occasionally accepting a slightly perturbed valid trace; Model S instead makes the *entire language* permissive by construction, so it cannot express P2, P4, P5's necessity, or P6/P7 at all.

Concrete undesirable/policy-ambiguous behaviors admitted by Model S:

1. `Register Dossier, Manager Approval, Release Order` — skips both mandatory checks (violates P2). [= B3]
2. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` — Expedite Review before either mandatory check (violates P4). [= B4]
3. `Register Dossier, Supplier Review, Manager Approval, Release Order` — Supplier Review with no checks at all, and no way to know if it was even required (P3 unrepresented, P2 broken).
4. `Register Dossier, Auto Approval, Release Order` — auto-approves with zero checks, arguably worse than #1 for an audit trail.
5. `Register Dossier, Manager Approval, Auto Approval, Release Order` — **exactly-one is not enforced**: `X('Manager Approval','Auto Approval')` is itself an exclusive choice, so this specific sequence is *not* admitted — but note the entire block is only reachable via the top-level `->`, and nothing prevents constructing a log where a tool interprets missing precedence loosely; more importantly, since P5 is only enforced by the single `X`, any log or replay tooling that treats the four-way `+` block as reentrant (e.g., during simulation with playout) can still generate degenerate short traces like #1–#4 as first-class "conforming" behavior, not edge cases.
6. Model S has **no representation of `Correct Dossier` at all** — the label is absent from its alphabet. This means it structurally cannot conform to *any* trace with a legitimate correction (P6), and because it also has no loop operator, it equally cannot represent a genuinely suspicious repeat (P7). Its apparent "robustness to missing events" is therefore actually **brittleness to repeated/corrected events**, the opposite of what F1/discovery-team framing implies for the parts of the policy that matter most for compliance.

Distinguishing intentional vs. accidental permissiveness: skipping SR is *intentional and correct* tolerance for the external/internal ambiguity (P3). Skipping CC/TR and admitting ER-before-checks is *accidental*, arising from using `+` where a `->` with a mandatory sub-block was required — this is a modeling defect, not a deliberate abstraction.

# 4. Adversarial Review of Model C

**Strongest case for C:** each disjunct is a plausible, checkable variant; for a fixed, closed population of process instances that never deviates from the eight known shapes, C gives high precision and an auditable enumeration — useful as **documentation** of currently-observed behavior.

**Strongest case against it:** C is a **memorized training-set encoding**, not a generalizable model, and this is visible in concrete gaps:

- **Branch enumeration brittleness.** Model C has *no* variant combining `Auto Approval` with `Supplier Review`, `Expedite Review`, or the swapped `Technical Review  Credit Check` order. Since P2 states check order is free "in either order" *regardless of which approval follows*, and P4/P3 do not exclude Auto Approval, this is an arbitrary asymmetry baked in from whatever cases happened to appear in training — exactly what F2 and F4 report.
- **Duplicate labels.** `Credit Check` and `Technical Review` each appear in most branches, plus twice more in the correction branch. This is not "noise" but a direct structural cost: duplicate labels break the one-to-one labeltransition mapping that token-replay and alignment-precision algorithms assume, inflating apparent precision (an "unseen" trace using a *different* occurrence of the same label than the training-aligned one can be silently misjudged) and making ownership/impact analysis (F3) genuinely hard — which of the two `Credit Check` transitions "owns" a defect fix?
- **Correction handling is a single hard-coded case.** Only "both CC and TR repeat" is representable (P6 explicitly allows CC-only or TR-only repeats). This directly produces the false rejection in F6/B6.
- **Holdout degradation (0.744) is not surprising, it is diagnostic**: it is the direct, mechanical consequence of enumerating training variants rather than the underlying constraints. This is strong evidence that the reported 0.941 training precision is at least partly an artifact of memorization rather than a genuinely tight but correct model (F5's point sharpened): a model built by directly transcribing frequent variants from the same log that is later used to compute precision is close to circular reasoning.
- **Maintainability.** Every new legitimate combination (new SR/ER/approval interaction) requires adding a new top-level disjunct, and every such addition risks yet more duplicate labels — the model does not scale with legitimate process variability, only with enumerated memory of the past.

F8's defense ("unseen behavior should be non-compliant until approved") is a legitimate **policy stance**, but it is not what C's *structure* implements — C rejects even behaviors that are policy-legitimate combinations of already-approved constructs (B2, B5), which is stricter than the stated policy, not merely conservative.

**Precise uncertainty note:** for B6/B8 against Model S, "accepts?" is not simply No — under the reminded PM4Py alignment machinery, a trace with a label absent from the model's alphabet (`Correct Dossier`) or a disallowed repetition is still *aligned* with nonzero cost (log-moves), not hard-rejected as in the Model C parses. I distinguish **language membership (No)** from **partial alignment (nonzero-cost, "graded No")** rather than reporting a single boolean, because this distinction is exactly what the reported fitness numbers obscure.

# 6. Likely Metric Pathologies

Ranked by likely impact on the governance decision:

1. **Fitness rewarded by optionalizing mandatory behavior (highest impact).** Model S's high fitness (train and holdout) is substantially explained by making everything optional — a flower-adjacent model. This is the single biggest reason the raw fitness numbers must not drive the decision.
2. **Positive-log-only precision (F5).** Neither precision number reflects rejection of known-bad behavior; C's 0.941 in particular could co-exist with 100% acceptance of forbidden traces the log never happened to contain.
3. **Generalization rewarded by excessive permissiveness.** S's 0.907 token-based generalization is inflated by the same structural permissiveness that produces B3/B4 — "generalizes well" here partly means "constrains almost nothing."
4. **Duplicated-label effects on C.** Duplicate transitions distort both alignment search (multiple zero/low-cost paths for the same label) and precision estimates, and they compromise the reliability of any per-model diagnostics used for audit (F3).
5. **Missing-event bias / split sensitivity.** F4 notes some Supplier Review events may be missing from holdout cases; if so, C's low holdout fitness is partly a data-quality artifact rather than a pure model-quality signal, and neither team published the split, so this cannot be checked.
6. **Silent-transition effects.** Every `tau` in Model S is a "free" way to satisfy the model without doing anything; this silently helps its fitness/generalization scores and is invisible in the aggregate numbers.
7. **Alignment-cost sensitivity.** Neither team disclosed move costs; a small change in the cost of log-moves vs. model-moves could substantially shift both fitness and precision, especially for C's duplicate-label branches.
8. **Runtime confounded by model size, not quality.** The 24x runtime gap mostly reflects net size/branching, not correctness; using it as evidence for either model is a category error.
9. **Stakeholder-score methodology.** No blinding, no sample size, no rubric — a 4.4 vs. 1.9 gap could easily reflect "which diagram is shorter" rather than "which diagram is correct."
10. **Train/holdout leakage risk.** Because Model C's variants look hand-derived from "frequent variants," and no seed/held-out case list was shared, we cannot rule out that some "holdout" cases informed the variant enumeration.

# 7. Third Alternative

## 7.1 Strategy chosen
A **block-structured procedural backbone** (mandatory concurrency for Credit Check / Technical Review, an explicit bounded correction-and-recheck loop, and a constrained optional-review block) **plus an external declarative/data-aware check layer** for the two attributes the log does not contain (`external`, `affected_check`) and for the P7 suspicion rule. This directly targets the failure modes found in Sections 3–5: unlike Model S it keeps CC/TR/approval genuinely mandatory and orders ER correctly; unlike Model C it does not enumerate variants and supports arbitrary legitimate correction patterns without branch explosion or duplicate-label sprawl beyond the one principled loop.

## 7.2 Compact formal description

```
RD
· (CC  TR)                              -- mandatory, either order (P2)
· [ (CD · choice{CC, TR, CCTR}) ]*      -- 0..n correction cycles; every repeat
                                            of CC/TR is causally preceded by CD (P6, P7)
· (SR?  ER?)                            -- both optional, unordered relative to
                                            each other, but only reachable AFTER
                                            the checks/correction block (P4, P3)
· XOR(MA, AA)                            -- exactly one (P5)
· RO
```

External layer (evaluated on the aligned/replayed log, not baked into the Petri net):

- `SR-conditional(case)`: if `case.external == True` then `Supplier Review  case`, else no requirement. If `external` is missing  tag `SR_COMPLIANCE = UNVERIFIED` (never silently "compliant").
- `Suspicious-repeat(case)`: if CC or TR occurs more than once and is **not** preceded by a `Correct Dossier` in the model's own semantics, this cannot happen by construction (the loop guarantees it) — the check becomes a **regression test** on real logs to catch cases the model would refuse to replay, surfacing them as alignment deviations rather than silently accepting them as Model S does.
- `Affected-check-audit(case)`: if `affected_check` attribute exists, verify it matches which of CC/TR actually repeated after each CD; if absent, tag `CORRECTION_SCOPE = UNVERIFIED`.

## 7.4 External declarative / data-aware checks (required companion, not optional)

```python
DECLARE_STYLE_RULES = {
    "SR_conditional_existence": {
        "description": "If case attribute 'external' is True, Supplier Review must occur.",
        "requires_attribute": "external",
        "on_missing_attribute": "flag SR_COMPLIANCE = UNVERIFIED",
    },
    "correction_scope_audit": {
        "description": "The specific check(s) repeated after Correct Dossier should match "
                        "case attribute 'affected_check' when available.",
        "requires_attribute": "affected_check",
        "on_missing_attribute": "flag CORRECTION_SCOPE = UNVERIFIED",
    },
    "exactly_one_approval": {
        "description": "Manager Approval XOR Auto Approval before Release Order.",
        "enforced_in_control_flow": True,
    },
}

def post_hoc_case_flags(trace, case_attributes):
    flags = {}
    if "external" not in case_attributes:
        flags["SR_COMPLIANCE"] = "UNVERIFIED"
    elif case_attributes["external"] and not any(e["concept:name"] == "Supplier Review" for e in trace):
        flags["SR_COMPLIANCE"] = "VIOLATION"

    if "affected_check" not in case_attributes:
        flags["CORRECTION_SCOPE"] = "UNVERIFIED"
    return flags
```

## 7.5 Explicit semantics

- **Mandatory checks:** `+('Credit Check','Technical Review')` — both must occur, order free; unlike Model S, neither is wrapped in `X(_, tau)`.
- **Optional Supplier Review:** structurally optional (control-flow cannot encode the missing `external` attribute), but *never silently declared compliant* — compensated by `SR_conditional_existence` and explicit `UNVERIFIED` tagging.
- **Expedite Review ordering:** placed in the `+()` block that is sequentially *after* the mandatory-checks-and-correction block, guaranteeing it cannot precede CC/TR (fixes B4), while remaining unordered relative to Supplier Review (satisfies P4's "before or after Supplier Review").
- **Exactly-one approval:** enforced with a genuine `X('Manager Approval','Auto Approval')`, reachable from every path, so B2/B5-style variants with Auto Approval are not artificially excluded (fixes Model C's asymmetry).
- **Correction/recheck:** the loop `*(tau, ->(CD, X(CC,TR,CCTR)))` permits zero or more correction cycles, each independently choosing to recheck CC only, TR only, or both — covering all three legitimate P6 patterns, and making any repeat of CC/TR **causally require** a preceding `Correct Dossier`, which operationalizes P7 as a structural guarantee rather than an after-the-fact label.

## 7.6 Limitations from missing attributes

- Without `external`, the model **cannot** make Supplier Review conditionally mandatory in the control-flow; this is compensated, not solved, by the external check, and any deployment must report `SR_COMPLIANCE = UNVERIFIED` rates to governance, not hide them.
- Without `affected_check`, the model cannot verify that the *specific* check recorded as repeated in a real case matches the correction's intended scope; it can only confirm that *some* legitimate recheck pattern occurred.
- The correction loop assumes rechecks are always immediately preceded by `Correct Dossier` and immediately followed by the next block; if real corrections can be batched or delayed across other activities, the backbone would need revision — this should be checked empirically (Section 9).

**Three adversarial traces designed to further separate the models:**

1. `RD, TR, CC, ER, SR, AA, RO` — swapped check order, ER before SR, Auto Approval. S: accepts (as usual, too permissive to be informative). C: rejects (no AA+SR+ER branch, again). Third: accepts (CCTR any order  correction skip  ERSR any order  AA). This isolates C's approval/optional-review blind spot cleanly.
2. `RD, CC, TR, CD, CC, TR, CD, TR, MA, RO` — two correction cycles, first re-checking both, second re-checking TR only. S: cannot replay (no CD, no loop). C: cannot replay (only one fixed correction shape). Third: accepts (loop iterates twice, second time choosing TR-only). This stresses the *multiplicity* of P6 that neither original model attempts.
3. `RD, CC, TR, CC, TR, MA, RO` — a full repeat of both checks with **no** Correct Dossier in between (a pure P7 violation with no textual "excuse"). S: cannot replay (no loop) — accidentally correct rejection. C: cannot replay (not enumerated) — accidentally correct rejection. Third: cannot replay because the loop requires `CD` before any repeat — **principled** rejection. This trace is where all three models agree on the verdict but only Third's rejection generalizes to the *reason* rather than coincidence.

Additional protocol elements (not code, but required):

- **Stakeholder comprehension**: blind A/B diagram review, 15 raters per stakeholder group (compliance, ops, IT, audit), fixed rubric ("can you identify whether trace X is compliant using only this diagram?"), report inter-rater agreement (e.g., Krippendorff's ), not just a mean score.
- **Decision rule for rejection despite good aggregate metrics:** reject any candidate model that (a) accepts **any** trace from the curated negative suite, regardless of aggregate fitness/precision; or (b) shows holdout fitness dropping more than a pre-registered threshold (e.g., >10 points) versus training without an approved explanation tied to data quality, not model quality; or (c) cannot pass `check_soundness`.

# 10. Governance Recommendation

- **Model S**: retain only for early-stage exploration and stakeholder communication, with a mandatory disclaimer that it must never gate release decisions. It fails the compliance-critical probes (B3, B4) and cannot represent correction/suspicion (P6/P7) at all.
- **Model C**: retain only as a *documentation snapshot* of currently-known frequent variants (e.g., for audit narrative), not as an automated gate — it wrongly rejects legitimate variants (B2, B5) and cannot express partial corrections (B6), and its duplicate-label structure undermines the very audit-traceability it's credited with.
- **Neither original model should be used for automated conformance enforcement today.**
- **Third alternative**: adopt as the candidate enforcement backbone, contingent on:
  1. Passing the full validation program in Section 9, especially the curated negative suite and soundness check, with results published (not just claimed).
  2. Logging enhancement to capture `external` and `affected_check` attributes within a defined timeframe; until then, all SR- and correction-scope-related decisions must carry an explicit `UNVERIFIED` flag routed to human review — never silently approved.
  3. Independent, reproducible re-computation of fitness/precision/generalization/simplicity with published seeds and alignment-cost settings before any go-live comparison claim is made against S or C.

# 11. Dissenting View

*"This recommendation replaces two already-built, already-scored models with a third model that has **no reported metrics at all** — only structural argument. That is a governance regression, not an improvement. Model C, whatever its brittleness, was built directly from observed frequent behavior and has a human-checkable enumeration; deploying it with a lightweight manual-override queue for rejected-but-plausible cases (as operations already does informally per F2) costs far less than building, validating, and maintaining a dual-layer system (process tree + external declarative checker) whose two attribute dependencies (`external`, `affected_check`) may never be reliably logged. Meanwhile Model S, bolted onto a strict post-hoc negative-trace filter, would be cheaper to fix than a ground-up redesign. The third alternative's clean performance on B1–B8 is unsurprising: those probes were used to *design* it, which is the same overfitting critique leveled at Model C's holdout collapse. Until the third alternative is tested on genuinely independent holdout data with the same rigor demanded of S and C, preferring it is an act of faith in architecture over evidence."*

**What would change my mind:** (1) validation results (Section 9) showing the third alternative's holdout fitness/precision degrade similarly to Model C's when tested on truly independent, attribute-stratified data — this would suggest its apparent superiority is also probe-derived overfitting; (2) evidence that the external declarative layer produces so many `UNVERIFIED` flags in practice that it paralyzes operations rather than informing them; (3) a stakeholder comprehension study (properly blinded) showing the loop-based correction semantics are harder for business users to reason about than C's explicit enumeration, undermining the maintainability argument. Any of these would shift me toward a hardened Model C (fixing the AA/order asymmetry and adding a partial-correction branch) with a human-review gate, rather than the proposed third alternative.
