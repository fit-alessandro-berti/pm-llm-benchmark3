## 3. Consequences for performance analysis

**G1 (Apply label):**
- Waiting time: Underestimated (true waiting starts at queue arrival, not 09:00)
- Service time: Accurate (physical batch processing)
- Utilization: Overestimated (appears as 100% during batch)
- Bottleneck: May appear as constraint when it's actually efficient batching

**G2 (Surface inspection):**
- Waiting time: Overestimated (start time is when group begins, not individual processing)
- Service time: Overestimated (includes setup time for entire group)
- Utilization: Overestimated (appears as continuous work)
- Bottleneck: May appear as constraint due to apparent long service times

**G3 (Release review):**
- Waiting time: Overestimated (reviews performed throughout but logged at end)
- Service time: Underestimated (only final submission time recorded)
- Utilization: Underestimated (actual work spread over time)
- Bottleneck: May be missed due to compressed timing

**G4 (Pack item):**
- Waiting time: Accurate (sequential processing)
- Service time: Accurate
- Utilization: Accurate
- Bottleneck: Accurate detection

**G5 (Root-cause analysis):**
- Waiting time: Unreliable (shared account obscures individual patterns)
- Service time: Unreliable (may represent multiple analysts)
- Utilization: Overestimated (appears as single resource)
- Bottleneck: May be missed or falsely detected

**G6 (Close ticket):**
- Waiting time: Severely overestimated (appears as 2-3 hours when actual processing may be near-instant)
- Service time: Severely underestimated (appears as 0 minutes)
- Utilization: Overestimated (appears as continuous work)
- Bottleneck: False positive (appears as constraint when none exists)
- *Mechanism*: Bulk submission creates artificial waiting time (time from queue arrival to 17:00) and zero service time (17:00 to 17:00)

**G7 (Manual measure):**
- Waiting time: Unreliable (coarse timestamps obscure true timing)
- Service time: Overestimated (15-minute blocks appear as service time)
- Utilization: Overestimated (appears as continuous work)
- Bottleneck: May be falsely detected due to apparent long service times

**G8 (Repair triage):**
- Waiting time: Overestimated (includes safety check period)
- Service time: Accurate
- Utilization: Underestimated (safety check not accounted for)
- Bottleneck: May be missed if safety check isn't considered

3. **G3 (T-C reviews):**
   - Trusted: Appears as single resource with batch completion
   - Distrusted: Still appears as single resource (T-C is individual)
   - Same temporal pattern (end equality) supports both end batching and concurrent work

**Impact of exact vs. interval-censored timestamps:**
1. **G7 (Manual measure):**
   - Exact: Appears as perfectly simultaneous batches
   - Interval-censored: Reveals true timing uncertainty (15-minute windows)
   - Same temporal pattern supports both timestamp coarsening and genuine simultaneous batch

2. **G6 (Close ticket):**
   - Exact: Creates artificial waiting time and zero service time
   - Interval-censored: Would show true processing time is unknown (between queue arrival and 17:00)
   - Same temporal pattern supports both end batching and queue accumulation

3. **G1 (Apply label):**
   - Exact: Appears as perfect batch processing
   - Interval-censored: Would show true processing time is within 1-second window
   - Same temporal pattern supports both genuine simultaneous batch and timestamp coarsening

**Cases where same pattern supports multiple explanations:**
1. **Start equality (G2, G5):**
   - Start batching (G2)
   - Shared-account artifact (G5)
   - Timestamp coarsening (if precision were coarser)

2. **End equality (G3, G6):**
   - End batching (G3)
   - Queue accumulation (G6)
   - Bulk submission artifact (both)

3. **Sequential adjacency (G4, G8):**
   - Sequential batching (G4)
   - Queue accumulation after capacity loss (G8)
   - Resource constraint (both)

## 6. Data-collection redesign

**Prioritized recommendations:**

1. **Execution timestamps:**
   - Add explicit batch/group identifiers to distinguish physical batches from logging artifacts
   - Capture actual start/end times at the workstation level, not just submission times
   - Implement pause/resume events for activities that may be interrupted

2. **Resource identity:**
   - Replace shared accounts with individual badges or login credentials
   - For automated systems (like RBT-7), record fixture capacity and actual occupancy
   - Capture team composition when multiple resources work together

3. **Timestamp precision:**
   - Standardize precision to at least 1 second across all systems
   - Document the true accuracy (not just precision) of each timestamp source
   - For legacy systems, implement timestamp correction algorithms

4. **Recording timestamps:**
   - Separate the timestamp of physical completion from database recording
   - Implement real-time logging where possible to reduce recording lag
   - For bulk submissions, record the actual processing time of each case

5. **Source clocks:**
   - Synchronize all system clocks to a common time source
   - Document clock drift and implement correction factors
   - For systems with different clocks (like G8 safety check), implement clock synchronization events

6. **Workstation capacity:**
   - Record the physical capacity of each workstation (number of items that can be processed simultaneously)
   - Capture queue length at each workstation over time
   - Implement events for workstation downtime and capacity changes

7. **Metadata:**
   - Document the semantics of each timestamp field (when it's generated, what it represents)
   - Capture the business rules for timestamp rounding/coarsening
   - Record the data collection method (automated vs. manual entry)

8. **Validation:**
   - Implement operational validation of critical timestamps
   - Conduct periodic time studies to verify timestamp accuracy
   - Create feedback loops for workers to report timestamp issues

- **G4 (Pack item):** Sequential batching with accurate timing
- **G8 (Repair triage):** Sequential processing with queue accumulation

**Clusters requiring interval-censoring in queue analysis:**

**Clusters to exclude from performance analysis:**
