# 1. Policy Interpretation and Conflict Resolution

## Assumptions
1. **R5 (Legal Dept.)**: `Obtain Legal Opinion` must **always** precede `Activate Vendor` if `Sanctions Escalation` occurs.
2. **R6 (Operations Dept.)**: Emergency activation (not logged as an attribute) may bypass R5, but `Obtain Legal Opinion` must follow within 24 hours.
3. **Conflict**: R5 and R6 are **incompatible** because R5 is absolute, while R6 allows conditional bypass.
4. **Missing Attributes**: The log lacks `emergency` flags or joint authorization data, making R6 **unverifiable from activity traces alone**.

## Resolutions for R5/R6 Conflict
### Option 1: **Strict Compliance (R5 Wins)**
- **Model**: Enforce `Obtain Legal Opinion` **before** `Activate Vendor` in all cases.
- **Risk**: Operations may violate this in emergencies, but the model flags it as a **hard violation**.
- **Implementation**: Use DECLARE `precedence(Sanctions Escalation, Obtain Legal Opinion)` + `precedence(Obtain Legal Opinion, Activate Vendor)`.

### Option 2: **Conditional Compliance (R6 Wins)**
- **Model**: Allow `Activate Vendor` before `Obtain Legal Opinion` **only if** `Sanctions Escalation` occurred, but require `Obtain Legal Opinion` within 24 hours.
- **Risk**: Without `emergency` attributes, this **cannot be enforced** in activity-only models. Requires external data.
- **Implementation**: Use a **temporal profile** to flag late `Obtain Legal Opinion` (warning) + a **resource/data check** to verify emergency authorization (if available).

### **Chosen Resolution**: **Option 1 (Strict Compliance)**
- **Justification**: R5 is a **legal requirement**, while R6 is an operational exception. Without verifiable attributes, we default to the stricter rule.
- **Compliance Risk**: False positives if emergencies occur but are not logged. Mitigated by **manual review** of flagged cases.

# 3. Procedural Backbone

## 1. Formal Description (Process Tree)
```
(Receive Onboarding Request,
  (Capture Master Data, Run Sanctions Screening, Verify Bank Account),
  Classify Risk,
  X(
    Reject Vendor,
    (Manager Approval, Activate Vendor),
    (Enhanced Due Diligence, Compliance Approval, Activate Vendor)
  ),
  X(
    Close Onboarding,
    (Release First Payment, Close Onboarding)
  )
)
```
- **Concurrency**: `` for parallel checks.
- **Choice**: `X` for rejection vs. approval routes.
- **Loops**: **Not included** (clarification loops are cross-cutting; handled in DECLARE).
- **Post-Activation**: **Not included** (R11 is a separate constraint).

## 2. PM4Py Process Tree Code
```python

procedural_model = ProcessTree(

## 3. Explanation
- **Concurrency**: `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` run in parallel (``).
- **Choices**: After `Classify Risk`, the process branches into:
  - Rejection (`Reject Vendor`).
  - Low-risk route (`Manager Approval  Activate Vendor`).
  - High-risk route (`Enhanced Due Diligence  Compliance Approval  Activate Vendor`).
- **Terminal Outcomes**: `Close Onboarding` follows either `Reject Vendor` or `Release First Payment`.
- **Limitations**:
  - **Clarification loops (R3)** are not in the backbone (handled in DECLARE).
  - **Post-activation changes (R11)** are excluded (require separate modeling).

## Overlaps and Disagreements
- **With DECLARE**:
  - `always_before`/`always_after` overlap with DECLARE `precedence`/`response`.

- **Limitations**:

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),  # 48h mean, 24h std
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),    # 12h mean, 6h std

}
```

## Explanation
- ** = 2.0**: Deviations beyond `mean ± 2*std` are flagged as **warnings**.
- **Why Warnings?**:
  - Temporal constraints (R12) are **normative but not absolute** (per compliance).
  - Hard enforcement would reject valid cases with minor delays (e.g., 96h for `Activate  Release` is within `72 ± 72`).
  - **Resource/data checks** (e.g., emergency flags) may justify deviations.

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
from pm4py.filtering import filter_four_eyes_principle

def check_resource_constraints(log: pd.DataFrame) -> pd.DataFrame:
    """
    Checks R9 (segregation of duties) and R6 (emergency policy).
    Assumes log has columns: 'case:concept:name', 'time:timestamp', 'org:resource'.
    """
    violations = pd.DataFrame(columns=["case_id", "violation", "details"])

    # R9: Verify Bank Account  Approval resource
    for case_id, case in log.groupby("case:concept:name"):
        case_log = case.sort_values("time:timestamp")
        verify_resources = case_log[case_log["concept:name"] == "Verify Bank Account"]["org:resource"].tolist()
        approval_activities = ["Manager Approval", "Compliance Approval"]
        approval_resources = case_log[case_log["concept:name"].isin(approval_activities)]["org:resource"].tolist()

        for vr in verify_resources:
            for ar in approval_resources:
                if vr == ar:
                    violations.loc[len(violations)] = {
                        "case_id": case_id,
                        "violation": "R9_Verify_Approval_Conflict",
                        "details": f"Verify Bank Account by {vr} and Approval by {ar}"
                    }

        # R9: Capture Master Data  Activate Vendor resource
        capture_resources = case_log[case_log["concept:name"] == "Capture Master Data"]["org:resource"].tolist()
        activate_resources = case_log[case_log["concept:name"] == "Activate Vendor"]["org:resource"].tolist()

        for cr in capture_resources:
            for ar in activate_resources:
                if cr == ar:
                    violations.loc[len(violations)] = {
                        "case_id": case_id,
                        "violation": "R9_Capture_Activate_Conflict",
                        "details": f"Capture Master Data by {cr} and Activate Vendor by {ar}"
                    }

    # R6: Emergency policy (if Sanctions Escalation occurs)
    for case_id, case in log.groupby("case:concept:name"):
        case_log = case.sort_values("time:timestamp")
        if "Sanctions Escalation" in case_log["concept:name"].values:
            escalation_time = case_log[case_log["concept:name"] == "Sanctions Escalation"]["time:timestamp"].iloc[0]
            activate_time = case_log[case_log["concept:name"] == "Activate Vendor"]["time:timestamp"]
            legal_time = case_log[case_log["concept:name"] == "Obtain Legal Opinion"]["time:timestamp"]

            if not activate_time.empty and not legal_time.empty:
                activate_ts = activate_time.iloc[0]
                legal_ts = legal_time.iloc[0]
                if activate_ts < legal_ts:  # Activate before Legal
                    time_diff = (legal_ts - activate_ts).total_seconds()
                    if time_diff > 24 * 3600:  # >24h
                        violations.loc[len(violations)] = {
                            "case_id": case_id,
                            "violation": "R6_Emergency_Late_Legal",
                            "details": f"Activate Vendor at {activate_ts}, Obtain Legal Opinion at {legal_ts} (>24h later)"
                        }
            elif not activate_time.empty and legal_time.empty:
                violations.loc[len(violations)] = {
                    "case_id": case_id,
                    "violation": "R6_Missing_Legal_Opinion",
                    "details": "Sanctions Escalation occurred but no Obtain Legal Opinion"
                }

    return violations

# Alternative: Use PM4Py's built-in four-eyes check
def check_four_eyes(log: pd.DataFrame) -> pd.DataFrame:
    """Checks R9 using PM4Py's filter_four_eyes_principle."""
    violations = []
    for case_id, case in log.groupby("case:concept:name"):
        # Verify Bank Account vs. Approvals
        four_eyes_violation = filter_four_eyes_principle(
            case,
            activity1="Verify Bank Account",
            activity2=["Manager Approval", "Compliance Approval"]
        )
        if not four_eyes_violation.empty:
            violations.append((case_id, "R9_Verify_Approval_Conflict", "Four-eyes violation"))

        # Capture Master Data vs. Activate Vendor
        four_eyes_violation = filter_four_eyes_principle(
            case,
            activity1="Capture Master Data",
            activity2="Activate Vendor"
        )
        if not four_eyes_violation.empty:
            violations.append((case_id, "R9_Capture_Activate_Conflict", "Four-eyes violation"))

    return pd.DataFrame(violations, columns=["case_id", "violation", "details"])

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated Enforcement
- **R1 (Reject/Activate mutual exclusion)**: Enforced in **Log Skeleton (`never_together`)** and **DECLARE (`noncoexistence`)**.
- **R8 (Approval mutual exclusion)**: Enforced in **Log Skeleton** and **DECLARE**.
- **R10 (At-most-once)**: Enforced in **Log Skeleton (`activ_freq`)** and **DECLARE (`exactly_one`)**.

## Inconsistencies Under Loops/Post-Activation
- **R3 (Clarification Loops)**: DECLARE `chainresponse` allows infinite loops, but Log Skeleton `activ_freq` limits `Request Clarification` to 3. **Conflict**: DECLARE permits more loops than Log Skeleton.
- **R11 (Post-Activation)**: Procedural model **excludes** post-activation changes; DECLARE/Log Skeleton **include** them. **Risk**: Cases with `Change Bank Details` would fail procedural conformance but pass DECLARE/Log Skeleton.

## Vacuity in Declarative Rules
- **R2 (`exactly_one` approvals)**: Vacuous if neither approval occurs (e.g., rejected case). Mitigated by `altprecedence(Reject, Approval)`.
- **R4 (`response(Sanctions, Legal)`)**: Vacuous if `Sanctions Escalation` never occurs.

## Missing Case Attributes
- **R6 (Emergency Policy)**: Cannot verify without `emergency` flag or joint authorization data. **Blind spot**: Model assumes no emergencies (strict R5).
- **R9 (Four-Eyes)**: Requires `org:resource`; missing data  **conservative failure**.

## Timestamp-Only Limitations
- **Temporal Profile**: Assumes timestamps are accurate and in the same timezone. **Blind spot**: Clock skew or missing timestamps break checks.
- **R6**: Cannot distinguish between "emergency activation" and "violation" without metadata.

## Support/Confidence Metadata
- **Risk**: Treating `support=1.0, confidence=1.0` as normative may **over-constrain** real logs (e.g., rare edge cases).
- **Mitigation**: Use confidence < 1.0 for rules with known exceptions (e.g., R6).

# 10. Deployment Recommendation

## Canonical Representation
- **Procedural Backbone**: Use the **Process Tree** (Section 3) as the **primary control-flow model**.
- **Authoritative Policy Layer**: **DECLARE** (Section 4) for cross-cutting constraints (R1–R5, R7–R8, R10–R11).
  - **Justification**: DECLARE handles conditional and temporal constraints better than Log Skeletons or Process Trees.

## Conformance Checking Order
1. **Procedural Model**: Check basic control-flow (e.g., `Receive Onboarding Request` first, `Classify Risk` after checks).
2. **Log Skeleton**: Quick filtering for hard constraints (R1, R8, R10).
3. **DECLARE**: Detailed cross-cutting constraints (R2–R5, R7, R11).
4. **Temporal Profile**: Flag deviations (R12) as **warnings**.
5. **Resource/Data Layer**: Final validation for R6, R9.

## Handling Contradictions
- **Priority Order**:
  1. **Hard Violations** (R1, R2, R4, R5, R7–R11): Fail the case.
  2. **Warnings** (R12, R6 under emergency): Escalate to compliance team.
  3. **Missing Data**: Fail if critical (e.g., R9 resources missing); warn if non-critical (e.g., R6 emergency flag).
- **User Feedback**:
  - **Dashboard**: Show **layered results** (e.g., "Procedural: Pass | DECLARE: Fail (R3) | Temporal: Warning (R12)").
  - **Explainability**: Highlight the **earliest decisive violation** (e.g., T5 fails at R3 before R10).

## Tooling Integration
- Use `pm4py.conformance_declare()` for DECLARE.
- Use `pm4py.conformance_log_skeleton()` for Log Skeleton.
- Use `pm4py.conformance_temporal_profile()` for temporal checks.
- Use custom code (Section 7) for resource/data checks.
```
