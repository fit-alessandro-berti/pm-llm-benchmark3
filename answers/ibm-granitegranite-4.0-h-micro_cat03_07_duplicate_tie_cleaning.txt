## 1. Duplicate-handling decision tree

### Decision Tree for Duplicate Handling

1. **Exact Technical Duplicate**
   - **Condition**: Same `source_event_key` and `source_seq`.
   - **Decision**: Drop one of the duplicates. 
   - **Reason**: Identical source identifiers imply identical content. Preserving one maintains provenance while dropping the redundant copy.

2. **Same Physical Event Observed by Multiple Systems**
   - **Condition**: Same `related objects` and `payload_hash` but different `source`.
   - **Decision**: Merge attributes and relations, retain one canonical `eid`.
   - **Reason**: These events represent the same business occurrence but captured by distinct systems. Merging preserves context while consolidating.

3. **Summary Event Derived from a Detailed Event**
   - **Condition**: One event is a higher-level summary (e.g., ERP summary) of a detailed event (e.g., WMS packing).
   - **Decision**: Retain both, but introduce qualifiers to distinguish levels (e.g., “summary” vs. “detailed”).
   - **Reason**: Both events are valuable; the summary provides a high-level view, while the detailed event offers granular insight. Qualifiers prevent semantic loss.

4. **Harmonization Collision Between Semantically Distinct Source Activities**
   - **Condition**: Events share objects but have different meanings (e.g., `Dispatch Package` vs. `Dispatch Package` as carrier acceptance).
   - **Decision**: Create harmonized labels or retain both with distinct qualifiers.
   - **Reason**: Harmonization is beneficial for consistency, but semantically distinct events require clear differentiation to avoid conflating meanings.

5. **Concurrent Same-Label Events Involving Different Objects**
   - **Condition**: Events have identical labels but involve different objects (e.g., e11/e16 for invoice issuance).
   - **Decision**: Merge attributes and relations, retain canonical `eid`.
   - **Reason**: The underlying business action is the same; the distinction lies in the object, which can be handled by merging without losing context.

6. **Unresolved Candidate**
   - **Condition**: No clear pattern identified.
   - **Decision**: Quarantine for review.
   - **Reason**: Unresolved candidates may contain nuanced business logic that automated rules cannot capture. Review ensures no critical data is lost.

### Timestamp-Tie Ordering Rules

1. **Domain Constraints**: Prioritize business-level constraints over timestamps. For example, the financial lifecycle (invoice  payment) should always precede the logistics lifecycle (dispatch  delivery).

2. **Within-Source Sequence**: Use the `source_seq` to maintain order within each system. This ensures that events from the same system are processed in the order they were generated.

3. **Lifecycle Constraints on Shared Objects**: Events involving the same business object (e.g., Order `O1`) should be ordered based on their lifecycle stages (Create  Validate  Pick  Pack  Dispatch  Delivery).

4. **Source-Specific Semantics**: Some systems may have unique semantics for timestamps (e.g., ERP might record system clock time, while WMS records physical processing time). Adjust timestamps to a unified business time reference (UTC) when ordering.

5. **Ingestion Time**: Use `ingested_at` as a deterministic fallback when timestamps conflict. This ensures that the most recent ingestion reflects the latest business activity.

6. **Stable Fallback Order**: If all else fails, use a stable fallback order based on the order of appearance in the dataset. This ensures reproducibility without introducing bias.

## 3. Timestamp-tie ordering rules

### Rules

1. **Semantic Rules**:
   - **Domain Constraints**: Ensure business logic flow is maintained (e.g., invoice before payment).
   - **Object Lifecycle**: Preserve the sequence of events involving shared objects.

2. **Deterministic Rules**:
   - **Within-Source Sequence**: Use `source_seq` to maintain order within each system.
   - **Ingestion Time**: Use `ingested_at` as a tiebreaker when timestamps are identical.
   - **Stable Fallback Order**: Use the order of appearance in the dataset as a last resort.

### Microseconds Consideration

Adding microseconds can introduce false stories if not carefully justified. Timestamps at the millisecond level are sufficient for most business processes. Adding microseconds can imply unnecessary precision, leading to incorrect assumptions about the exact timing of events. It is crucial to only add microseconds when the business context demands such precision, as it can obscure the true business process flow.

## 4. Conservative cleaning pipeline

### Pipeline Steps

1. **Duplicate Detection**: Identify exact technical duplicates using `source_event_key` and `source_seq`.
2. **Merge Duplicates**: For same physical events observed by multiple systems, merge attributes and relations, retaining one canonical `eid`.
3. **Preserve Abstraction Levels**: Keep detailed events separate from summary events, using qualifiers to distinguish levels.
4. **Retain Original Identifiers**: Store original `source_event_key`, `source_seq`, and `ingested_at` to maintain provenance.
5. **Introduce Deterministic Ordering**: Apply the timestamp-tie ordering rules to establish a deterministic total order.
6. **Store Provenance Information**: Record all merge decisions, original identifiers, and merge policies in a structured audit trail.

### Expected Retained Event Count

The conservative pipeline is expected to retain around 80% of the original events, balancing data reduction with the preservation of critical business context.

## 5. Aggressive alternatives

### Scenario 1: Evidence-Based Semantic Merging

- **Description**: Merge events based on semantic similarity, using domain knowledge to decide which attributes to retain. For example, e13 and e14 could be merged into a single payment event with qualifiers for each stage.
- **Expected Retained Event Count**: Approximately 70% of original events.
- **Semantic Damage**: Potential loss of detailed payment breakdowns, but gains a more streamlined view of the payment lifecycle.

### Scenario 2: Mechanically Aggressive PM4Py Merging

- **Description**: Use PM4Py's `ocel_merge_duplicates` to aggressively merge events based on high-confidence matches, without retaining original identifiers or qualifiers.
- **Expected Retained Event Count**: Approximately 60% of original events.
- **Semantic Damage**: High risk of losing critical business context and introducing unintended conflations between events.

### Justification for Not Using Ingestion Time

Using ingestion time as the primary business order can lead to incorrect ordering if ingestion times are not synchronized across systems. Timestamps provide a more reliable reference for the actual business events, ensuring that the pipeline reflects the true chronological order of operations.
