# 1. Objectives and constraints

The proposed policy is a **constrained scoring policy**, not a claim that one routing rule is universally optimal. It deliberately trades some immediate speed for lower rework, better SLA control, fairer load, and auditability.

**Primary objectives**

1. **SLA protection:** prioritize urgent/high-priority cases and cases where remaining SLA is small relative to complexity and likely handover delay.
2. **Safe and correct execution:** respect skill rules, especially for Security Review and Final Approval.
3. **Workload fairness and sustainability:** avoid consuming already overloaded or high-overtime-risk resources.
4. **Continuity of case ownership:** avoid unnecessary handovers, especially when reassignment count is already high or complexity is high.
5. **Skill development:** use normal/low-priority work for documented training where SLA risk is acceptable.
6. **Resilience:** avoid creating bottlenecks around scarce specialists and preserve surge capacity for urgent work.
7. **Explainability and auditability:** every assignment should have a short, valid reason that can be checked from event-log data.

**Hard safety/compliance constraints**

- Skill score `0` means not allowed.
- High-priority cases must not be assigned below skill `2` unless there is explicit supervision.
- Security Review must be done by skill `3`, or by skill `1–2` only under explicit supervision by R7_Gita or R8_Hugo.
- Final Approval must be finalized by skill `2–3`; skill `1` may prepare but not finalize.
- No resource receives more than **4 new assignments** in this decision batch.
- High-overtime-risk resources are not assigned additional work unless the case is urgent and no safer alternative exists.
- Quality Check batching is allowed only for normal/low priority with SLA remaining greater than 24h.
- At least 20% of normal/low-priority assignments should support documented training priorities when SLA risk remains acceptable.
- Deviations must be logged in `assignment_reason`.

**Preference trade-offs, not absolute rules**

- A specialist assignment may reduce immediate errors but increase handover delay and specialist queues.
- Keeping the current owner preserves context but may increase service time if skill is weak.
- Training improves resilience but can slow a case and requires supervision.
- Batching improves efficiency but must not create SLA blind spots.
- Fairness may mean not giving a case to the technically “best” resource if that resource is already a bottleneck.

# 2. Assignment policy

The policy first filters candidates by hard constraints, then scores feasible candidates.

```text
INPUT:
  queue of cases
  resource skill matrix
  current workload and hours remaining
  historical evidence: handover cost, reassignment_count, rework/appeal rates
  team, overtime risk, training priorities

STATE:
  assignments_received[resource] = 0

For each case, process in descending urgency order:
  1. Build eligible performer/supervisor options.
  2. Apply hard safety, skill, capacity, SLA, and overtime constraints.
  3. Score each feasible option.
  4. Choose highest-scoring feasible option.
  5. Update workload counters.
  6. Write an explainable assignment_reason.
```

**Eligibility filtering**

```text
candidate is eligible only if:

  skill_score(resource, required_skill) > 0

  AND hours_remaining(resource) > expected handling time

  AND assignments_received[resource] < 4

  AND if resource.overtime_risk == high:
        case.priority == urgent AND no safe alternative exists

  AND if required_skill == Security:
        skill_score == 3
        OR skill_score in {1,2} with supervisor in {R7_Gita, R8_Hugo}

  AND if required_skill == Approval:
        skill_score >= 2 for finalization
        skill_score == 1 only as preparation under a skill >= 2 finalizer

  AND if case.priority in {urgent, high}:
        skill_score >= 2
        OR explicit supervisor with sufficient skill is assigned

  AND if required_skill == Quality and batching is proposed:
        case.priority in {normal, low}
        AND sla_remaining > 24h
```

**SLA urgency scoring**

```text
priority_weight:
  urgent = 4
  high   = 3
  normal = 2
  low    = 1

sla_pressure = 1 + min(2, 8 / (sla_remaining_hours + 1))
complexity_factor = 1 + 0.5 * case_complexity

urgency_score =
  priority_weight * sla_pressure * complexity_factor
```

A case gets an additional SLA-risk penalty if:

```text
sla_remaining < expected_service_time
                + expected_handover_delay
                + safety_buffer
```

When this happens, SLA weight increases and training/batching scores are reduced.

**Skill-match scoring**

```text
base_skill_score:
  skill 3 = 1.00
  skill 2 = 0.75
  skill 1 = 0.30
  skill 0 = inadmissible

penalties:
  high-priority case with skill < 2, even supervised: -0.30
  Security Review without skill 3 and without approved supervisor: inadmissible
  Final Approval with skill 1 as finalizer: inadmissible
```

Specialist assignment is rewarded, but not so strongly that it overrides urgent SLA risk, handover cost, or overtime constraints.

**Continuity and handover-cost scoring**

```text
continuity_score =
  +0.80 if candidate == current_owner

  -0.10 if handover_cost_band == low
  -0.25 if handover_cost_band == medium
  -0.45 if handover_cost_band == high

  -0.15 * reassignment_count
  -0.35 if reassignment_count > 2

  +0.50 if case_complexity >= 0.70
         AND handover_cost_band in {medium, high}
         AND candidate == current_owner
```

Continuity is preferred for high-complexity, high-handover cases unless the current owner lacks required skill or SLA risk makes keeping the owner unsafe.

**Workload and overtime fairness scoring**

```text
workload_penalty =
  -0.30 * (current_open_cases / reasonable_open_case_capacity)
  -0.30 * (1 - hours_remaining / standard_shift_hours)

overtime_penalty =
  -0.60 if overtime_risk == high and case is not urgent
```

If the resource is the only feasible specialist for an urgent case, the overtime penalty may be overridden, but the override must be logged.

**Training and development scoring**

```text
training_bonus =
  +0.25 if case.priority in {normal, low}
         AND resource.training_priority == required_skill
         AND SLA risk is acceptable
         AND supervisor exists if needed

  +0.10 if resource is a documented shadow/trainee
         and does not become accountable final owner
```

Training never overrides safety constraints.

**Resilience and bottleneck avoidance**

```text
resilience_penalty =
  -0.35 if assigning a scarce skill-3 resource to a low-priority task
         while a competent skill-2 resource is available

  -0.20 if the assignment creates high concentration in one team
         or consumes scarce Security/Approval capacity needed later

  +0.15 if the option preserves qualified backup capacity
         for urgent Security or Approval work
```

**Total score**

```text
total_score =
    w_sla       * urgency_score
  + w_skill     * skill_score
  + w_continuity* continuity_score
  + w_fairness  * workload_score
  + w_training  * training_bonus
  + w_resilience* resilience_score
  - hard_constraint_penalties
```

Example weights:

```text
Urgent cases:
  SLA 0.35, skill 0.20, continuity 0.15,
  fairness 0.10, training 0.00, resilience 0.20

Normal/low cases:
  SLA 0.18, skill 0.20, continuity 0.18,
  fairness 0.18, training 0.16, resilience 0.10
```

**Tie-breaking**

If scores are close:

1. Lower SLA risk.
2. Higher skill score.
3. Lower overtime risk.
4. Lower current open-case count.
5. Better continuity.
6. Lower reassignment increase.
7. Stable resource ID as final deterministic tie-break.

**Exception handling**

- If no eligible performer exists, create a supervised pair.
- If a high-priority case would otherwise go to a trainee, require a named supervisor.
- If an overtime-risk override is needed, require `assignment_reason = urgent_override_no_safe_alternative`.
- If a high-complexity case is removed from its current owner, require `assignment_reason` to mention SLA/skill/compliance reason.
- All exceptions are auditable from the event log.

# 4. Comparison with baseline policies

| Dimension | First-available routing | Specialist-only routing | Proposed dynamic policy |
|---|---|---|---|
| Expected throughput | Can look fast in the short term because it uses low-open-case resources quickly | Lower throughput when specialists become queues, especially Security, Approval, and Diagnosis | Balanced throughput: not always fastest, but avoids rework and bottleneck collapse |
| SLA risk | High risk for urgent cases because skill mismatch can cause service delays and rework; e.g. urgent negotiation or security may go to low-skill resources | Mixed: good where specialist already owns the case; poor where handover on complex cases adds waiting | Lower risk for urgent cases because SLA and complexity drive ordering and routing; some normal cases accept slower handling |
| Error/rework risk | Highest risk: first-available ignores specialization except skill 0 | Lowest immediate error risk, but handovers can increase rework and appeals | Moderate-low risk: safety rules plus continuity scoring reduce both mismatch and avoidable handover |
| Workload fairness | Superficially fair because it equalizes open cases, but ignores overtime risk and skill burden | Often unfair: scarce specialists and low-open experts absorb many cases; high-overtime-risk staff may be underused or suddenly overloaded | Fairer: explicit cap, overtime penalties, hours remaining, and team/resilience checks |
| Skill development | Incidental; training happens by accident | Poor; specialists do the work and trainees are rarely used | Deliberate: documented training on suitable normal/low cases with supervision |
| Continuity of case ownership | Weak; handovers are common | Weak; specialists often take cases from current owners | Strong; continuity is scored and preserved unless SLA/skill rules justify handover |
| Resilience to absence or bottlenecks | Poor: first-available may create hidden skill mismatches and repeated reassignment loops | Poor: creates dependency on scarce specialists | Better: protects scarce capacity, uses supervised alternatives, avoids overloading high-risk staff |
| Explainability | Simple but weak: “lowest open cases” is easy to explain but not defensible for SLA/skill exceptions | Simple: “highest skill wins,” but ignores context | More explainable: each assignment has a reason tied to SLA, skill, continuity, fairness, training, or resilience |

First-available routing may outperform the proposed policy on raw initial waiting time when work is easy and low risk. Specialist-only routing may outperform it on immediate correctness when SLA slack is large and handover costs are low. The proposed policy is preferable when the process must also satisfy auditability, fairness, training, and resilience requirements. It accepts slightly more complex decisions in exchange for fewer hidden failures.

# 5. Explanation to workers

Assignments are not meant to reward or punish anyone. They are meant to protect customers, keep work safe, and share work fairly.

For each case, we look at five things:

1. **How urgent is it?** Urgent cases with little time left are handled first.
2. **Who has the right skill?** Some activities, especially Security Review and Final Approval, have strict rules.
3. **Who already owns the case?** If the current owner can safely do the work, we usually keep the case there because context matters.
4. **Who already has too much work?** We avoid adding work to people who are already overloaded or at high overtime risk.
5. **Can this case help someone learn safely?** Normal or low-priority cases may be used for training when there is enough time and a supervisor is available.

If a case moves away from its current owner, it is not because the previous owner did badly. It may be because the SLA is too tight, the activity requires a specialist, or the owner already has too much work.

If a case stays with the same owner, it is because continuity helps avoid repeated handovers and rework.

If a trainee is assigned with supervision, the supervisor is there to support the work and protect quality. Trainees will not be made solely responsible for work that the rules say must be finalized by a competent or specialist resource.

Any exception will be recorded in plain language, such as “urgent SLA, no safe alternative” or “security rule required specialist.”

# 6. Process-mining audit indicators

| Indicator | Event-log definition | Audit use |
|---|---|---|
| Handover frequency | Percentage of cases where `org:resource` changes between consecutive activities; can be visualized with `pm4py.discover_handover_of_work_network` | Detect excessive handovers and identify risky transition pairs |
| Reassignment count | Average and maximum `reassignment_count`; share of cases with `reassignment_count > 2` | Historical evidence says more than 2 reassignments increases rework and appeals |
| Skill mismatch | Share of events where the resource skill for `required_skill` is below required level; separate high-priority and supervised cases | Check compliance with high-priority, Security, and Approval rules |
| Workload distribution | Number of active cases per `org:resource` per time window; compare with `workload_snapshot` | Detect overload, underuse, and violations of the 4-assignment batch cap |
| Overtime risk exposure | Count/share of assignments to resources with `overtime_risk = high`, split by priority and exception reason | Verify that high-overtime-risk resources are used only when justified |
| SLA misses | Cases where completion time exceeds `sla_deadline`; also track near misses within a buffer | Measure whether the policy protects urgent and high-priority work |
| Rework/appeal after assignment | Rate of `Rework Correction` or appeal events after a handover, skill mismatch, or reassignment | Test whether routing choices create downstream quality problems |
| Training assignment share | Share of normal/low assignments where `assignment_reason` indicates training and `training_priority` matches `required_skill` | Verify the 20% training target and supervisor presence |
| Specialist bottleneck indicators | Waiting time and queue length by required skill/resource role; concentration of assignments among R7/R8/R6/R3; use role discovery and performance DFGs | Detect whether specialist-only tendencies are forming |
| Deviations from assignment policy | Events with `assignment_reason` containing override, missing reason, or violating hard constraints | Support audit, explanation, and policy refinement |

Additional network indicators:

- `discover_working_together_network` can show whether planned supervision pairs actually work together.
- `discover_activity_based_resource_similarity` can show whether resources assigned to similar activities have plausible skill profiles.
- `discover_organizational_roles` can validate whether Security and Approval roles remain distinct and staffed.
- `discover_batches` can verify that Quality Check batching is real and not just stated in `assignment_reason`.

# ------------------------------------------------------------
# 5. Assignment scoring sketch
# ------------------------------------------------------------

PRIORITY_WEIGHT = {
    "urgent": 4,
    "high": 3,
    "normal": 2,
    "low": 1
}

SKILL_SCORE = {
    3: 1.00,
    2: 0.75,
    1: 0.30,
    0: float("-inf")
}

def urgency_score(case):
    sla = max(case["sla_remaining_hours"], 0)
    priority = PRIORITY_WEIGHT[case["case_priority"]]
    sla_pressure = 1 + min(2, 8 / (sla + 1))
    complexity_factor = 1 + 0.5 * case["case_complexity"]
    return priority * sla_pressure * complexity_factor

def continuity_score(case, resource_id):
    score = 0.0

    if case["current_owner"] == resource_id:
        score += 0.80

    handover = case["handover_cost_band"]
    score += {
        "none": 0.00,
        "low": -0.10,
        "medium": -0.25,
        "high": -0.45
    }.get(handover, 0.0)

    score -= 0.15 * case["reassignment_count"]

    if case["reassignment_count"] > 2:
        score -= 0.35

    if (case["case_complexity"] >= 0.70
            and handover in {"medium", "high"}
            and case["current_owner"] == resource_id):
        score += 0.50

    return score

def is_eligible(case, resource, state, supervisor=None):
    required = case["required_skill"]
    skill = resource[f"{required}_skill"]
    priority = case["case_priority"]

    if skill <= 0:
        return False

    if state["assigned_count"][resource["org:resource"]] >= 4:
        return False

    if resource["hours_remaining"] <= 0:
        return False

    if resource["overtime_risk"] == "high" and priority != "urgent":
        return False

    if required == "Security":
        if skill < 3 and supervisor not in {"R7_Gita", "R8_Hugo"}:
            return False

    if required == "Approval":
        if skill < 2:
            return False

    if priority in {"urgent", "high"} and skill < 2 and supervisor is None:
        return False

    return True

def score_assignment(case, resource, state, supervisor=None):
    required = case["required_skill"]
    skill = resource[f"{required}_skill"]

    if not is_eligible(case, resource, state, supervisor):
        return float("-inf"), "inadmissible"

    s_skill = SKILL_SCORE[skill]
    s_urgency = urgency_score(case)
    s_continuity = continuity_score(case, resource["org:resource"])

    s_fairness = (
        -0.30 * resource["current_open_cases"] / 15.0
        -0.30 * (1 - resource["hours_remaining"] / 8.0)
    )

    s_overtime = -0.60 if resource["overtime_risk"] == "high" else 0.0

    s_training = 0.0
    if (case["case_priority"] in {"normal", "low"}
            and resource["training_priority"] == required):
        s_training = 0.25

    s_resilience = 0.0
    if skill == 3 and case["case_priority"] == "low":
        s_resilience = -0.35

    weights = {
        "urgent": {
            "urgency": 0.35, "skill": 0.20, "continuity": 0.15,
            "fairness": 0.10, "training": 0.00, "resilience": 0.20
        },
        "high": {
            "urgency": 0.30, "skill": 0.22, "continuity": 0.18,
            "fairness": 0.12, "training": 0.03, "resilience": 0.15
        },
        "normal": {
            "urgency": 0.18, "skill": 0.20, "continuity": 0.18,
            "fairness": 0.18, "training": 0.16, "resilience": 0.10
        },
        "low": {
            "urgency": 0.15, "skill": 0.18, "continuity": 0.15,
            "fairness": 0.20, "training": 0.20, "resilience": 0.12
        }
    }[case["case_priority"]]

    total = (
        weights["urgency"] * s_urgency
        + weights["skill"] * s_skill
        + weights["continuity"] * s_continuity
        + weights["fairness"] * s_fairness
        + weights["training"] * s_training
        + weights["resilience"] * s_resilience
        + s_overtime
    )

    reason_parts = [
        f"priority={case['case_priority']}",
        f"sla={case['sla_remaining_hours']}h",
        f"skill={skill}",
        f"handover={case['handover_cost_band']}"
    ]

    if resource["training_priority"] == required:
        reason_parts.append("documented_training")

    if resource["overtime_risk"] == "high":
        reason_parts.append("overtime_override_required")

    return total, "; ".join(reason_parts)
