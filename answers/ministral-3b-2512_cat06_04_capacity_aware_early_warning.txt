### **1. Decision Rule**
**Eligibility Criteria:**
- **Stage:** Only intervene if the case is in **Triage** or **Diagnosis Started** (excluded if `Diagnosis Complete`).
- **Alert Persistence:** Require **20% increase in `p_now` from `p_prev`** (absolute threshold) **or 10% relative increase** if `p_prev` is already >0.5. This prevents false alarms from model refreshes (e.g., I-05) unless new evidence emerges.
- **Segment Adjustments:**
  - **Public Sector/SME:** Adjust `p_now` upward by **+0.05** (to account for underprediction).
  - **Strategic Enterprise:** Adjust `p_now` downward by **-0.05** (to account for overprediction).
  - **Non-Native-Language Support:** Use **minimum `p_now` of 0.6** (due to sparse calibration).
- **Value Threshold:** Only intervene if **value of avoiding breach > €5,000** (to avoid low-value cases consuming slots).
- **False-Alarm Burden:** If `p_now` is 0.7 and `p_prev` is unchanged, **suppress further alerts** unless new evidence (e.g., I-07’s log upload) justifies a new swarm.
- **Priority Tiers:**
  1. **Highest:** Cases with **new evidence** (e.g., I-07) or **high value + high risk** (e.g., I-02).
  2. **Medium:** Cases with **repeated alerts but no new evidence** (e.g., I-05) or **moderate value/risk** (e.g., I-04).
  3. **Lowest:** Cases with **low `p_now`** or **high false-alarm burden** (e.g., I-01).

**Intervention Effect Estimation:**
- Use **midpoint of absolute risk reduction range** for base case, but:
  - **Upper bound** if `p_now` is near the high end of the range.
  - **Lower bound** if `p_now` is near the low end or if the case’s alert history suggests model miscalibration.
- **Spillover:** Assume **0.02 per slot** for base case; scale up/down based on congestion (e.g., if queue length >5, multiply spillover by 1.5).

### **4. Repeated Alerts and Temporal Policy**
**I-05 vs. I-07:**
- **I-05:** Repeated alert with **no new evidence**  **suppress further alerts** unless `p_now` rises by 30% from prior peak.
- **I-07:** Repeated alert with **new log upload**  **intervene immediately** if `p_now` rises by 15% from prior peak.

**Cool-Down:**
- After a swarm, **no new alerts** for 24 hours unless `p_now` exceeds prior peak by 25%.

**Suppression:**
- If `p_now` is 0.7 and `p_prev` is unchanged for 3 consecutive refreshes  **automatically suppress** unless new evidence (e.g., I-07).

**Escalation:**
- If a case’s `p_now` rises by 40% from prior peak **and** value > €20k  **prioritize for swarm** even if not in queue.

**Re-entry:**
- If a case is suppressed, re-enter if `p_now` exceeds prior peak by 20% and value > €10k.

### **5. Fairness and Feedback-Loop Risks**
**Potential Issues:**
1. **Value-Based Starvation:**
   - Low-value cases (e.g., I-01, I-10) may be ignored despite high `p_now`. **Mitigation:** Set a **minimum value threshold of €5k** for intervention.
2. **Segment Calibration:**
   - Public Sector/SME underpredict; Strategic Enterprise overpredicts. **Mitigation:** Adjust `p_now` as described in the rule.
3. **Non-Native-Language Support:**
   - High uncertainty in effect estimates. **Mitigation:** Only intervene if `p_now` 0.6 **and** value > €15k.
4. **Feedback Loops:**
   - Selective intervention may **mislabel cases** in training data. **Mitigation:**
     - Log **all interventions** (success/failure) and **retrain model quarterly** with post-intervention labels.
     - Use **blind validation** (e.g., hold out cases where swarms failed to reduce breach risk).
5. **Spillover Harms:**
   - Untreated cases may bear spillover risk. **Mitigation:**
     - Monitor **queue length** and **breach rates** in untreated diagnosis-stage cases.
     - If spillover exceeds 0.05 per slot, **reduce slot allocation by 20%**.

### **6. Monitoring and Recalibration Plan**
**Operational Monitoring:**
- **Daily:**
  - Track **slots used vs. reserved**.
  - Log **false alarms** (e.g., I-05) and **missed breaches** (e.g., I-03).
- **Weekly:**
  - Compare **actual breach rates** in intervened vs. untreated cases.
  - Check **queue congestion** and **spillover spillover** (e.g., if 6 untreated cases each have 0.03 spillover).

**Predictive Monitoring:**
- **Monthly:**
  - Recalibrate `p_now` adjustments for segments (e.g., if Public Sector underpredicts by 0.06 instead of 0.05).
  - Test **new evidence thresholds** (e.g., does 20% `p_now` increase suffice for I-07?).

**Causal-Effect Monitoring:**
- **Quarterly:**
  - Run **ab-abs analysis** (before/after swarms) to estimate **true effect size**.
  - Compare **intervened vs. untreated breach rates** in high-value cases.

**Capacity Monitoring:**
- If **spillover exceeds 0.05 per slot**, reduce allocation by 20% and **expand queue capacity**.
- If **false-alarm rate > 10%**, adjust suppression thresholds.

**Fairness Monitoring:**
- **Annually:**
  - Audit **value distribution** among intervened cases (e.g., is I-08’s €100k case overrepresented?).
  - Check **segment representation** in interventions (e.g., are Strategic Enterprise cases underrepresented?).

**Policy Change Trigger:**
- If **net-impact is consistently negative** (e.g., Adverse scenario dominates), **increase minimum `p_now` by 0.05** or **reduce slot allocation by 30%**.
- If **spillover harms are systematic** (e.g., Public Sector cases bear most spillover), **allocate slots preferentially to Strategic Enterprise**.
