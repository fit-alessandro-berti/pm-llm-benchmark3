# 1. Delay-decomposition definitions

Let case index be \(c\) and branch index be \(i \in \{A,B,C\}\).

Observed timestamps:

- \(t^{arr}_c\): `arrival`
- \(t^{fork}_c\): `fork_release`
- \(s_{c,i}\): branch start (`A_start`, `B_start`, `C_start`)
- \(e_{c,i}\): branch completion (`A_end`, `B_end`, `C_end`)
- \(t^{F,s}_c\): `final_start`
- \(t^{F,e}_c\): `final_end`

Derived decomposition components:

1. **Upstream elapsed time before fork release**

\[
U_c = t^{fork}_c - t^{arr}_c
\]

2. **Branch-specific queue waiting**

Assumption: a branch cannot start before `fork_release`; any later start is branch-specific waiting.

\[
Q_{c,i} = \max(0, s_{c,i} - t^{fork}_c)
\]

In the supplied data all branch starts are at or after `fork_release`, so the max operator does not change the values.

3. **Branch active service**

\[
P_{c,i} = e_{c,i} - s_{c,i}
\]

4. **Join readiness**

The problem states that `F` may start only after all three branches have completed. Therefore:

\[
J_c = \max_i(e_{c,i})
\]

`join_ready` is not logged directly; it is inferred as the latest branch completion.

5. **Branch-specific synchronization waiting after completion**

\[
W_{c,i} = J_c - e_{c,i}
\]

This is the time a completed branch waits for the other branches.

6. **Elapsed fork-join stage time**

\[
E_c = J_c - t^{fork}_c
\]

This is the actual calendar time spent in the parallel fork-join stage.

7. **Downstream queueing before F**

Assumption: if the model rule holds, any time between `join_ready` and `final_start` is downstream waiting.

\[
D_c = \max(0, t^{F,s}_c - J_c)
\]

8. **Final service**

\[
S_c = t^{F,e}_c - t^{F,s}_c
\]

9. **Total case flow time**

\[
T_c = t^{F,e}_c - t^{arr}_c
\]

With the definitions above, the non-double-counting identity is:

\[
T_c = U_c + E_c + D_c + S_c
\]

The critical branch is:

\[
i^*_c = \arg\max_i(e_{c,i})
\]

For deterministic tie handling, I use the ordering \(A \succ B \succ C\): if two or more branches complete at the same latest time, A is selected before B, and B before C. The baseline data contain no ties.

## Why summing all branch synchronization waits double counts elapsed time

For each branch:

\[
Q_{c,i} + P_{c,i} + W_{c,i}
=
(s_{c,i} - t^{fork}_c) + (e_{c,i} - s_{c,i}) + (J_c - e_{c,i})
=
J_c - t^{fork}_c
=
E_c
\]

So every branch’s queue-plus-service-plus-synchronization duration equals the same elapsed fork-join stage duration \(E_c\). Therefore:

\[
\sum_i (Q_{c,i} + P_{c,i} + W_{c,i}) = 3E_c
\]

If one computed total flow time as:

\[
U_c + \sum_i(Q_{c,i}+P_{c,i}+W_{c,i}) + D_c + S_c
\]

the result would be:

\[
U_c + 3E_c + D_c + S_c
\]

which overstates elapsed time by \(2E_c\).

The same issue applies specifically to synchronization waiting:

\[
\sum_i W_{c,i} = \sum_i (J_c - e_{c,i})
\]

This counts the same calendar interval multiple times because completed branches wait concurrently. For example, in F07, A waits 25 minutes and C waits 52 minutes after completion, but the fork-join stage elapsed time is only 75 minutes. The synchronization waits overlap; they are diagnostic, not additive in the case-level elapsed-time equation.

# 4. Counterfactual redesign analysis

## Assumptions used for counterfactuals

I label the assumptions because the log does not identify causal mechanisms.

- **Assumption CF-1:** Upstream `fork_release` times and final service durations remain unchanged in branch counterfactuals.
- **Assumption CF-2:** For branch counterfactuals, the direct potential case-duration saving is measured as the reduction in `join_ready`. If the final station can start earlier by the same amount and downstream queueing is unchanged, this equals total flow-time saving.
- **Assumption CF-3:** A conservative lower bound on realized flow-time saving is zero if `final_start` is fixed by a release policy or by final-station congestion. Therefore, branch improvements can be masked downstream.
- **Assumption CF-4:** Fractional minutes are allowed in counterfactual estimates because a 50% queue reduction can produce half-minute values. The input timestamps are one-minute accurate, but the counterfactuals are estimates, not observed events.
- **Assumption CF-5:** For final-station counterfactuals, the upper-bound saving from removing downstream queueing is the observed `downstream_queue`. A more conservative capacity-only estimate is the part of downstream waiting that can be explained by the previous observed final job on the same final resource.

- F01, F04, F08, and F11 have zero potential saving because another branch remains latest even after B is accelerated.

Partial benefit cases:

- F05 and F10 do not capture the full half-queue reduction because A becomes critical before the full B reduction is realized.
- F02 and F06 tie with A after reduction; the full queue reduction is captured in `join_ready`, but the identity of the critical branch changes.

Downstream masking:

- Several B-critical cases also have nontrivial downstream queueing. If final-station capacity or release policy prevents earlier `final_start`, the realized total flow-time saving will be less than the potential `join_ready` saving.
- For example, F09 has a potential 12.5-minute join-ready saving, but its observed final start is already constrained by the F1 sequence. If preceding final work does not move, some or all of the benefit may be absorbed as additional downstream waiting.

Secondary effects:

- Reducing B queue can shift criticality to A in some cases, especially F05 and F10.
- It can reduce synchronization waiting for A and C.
- It may move cases earlier into the final station, potentially increasing final-station queueing unless final capacity or release scheduling is also improved.

## Counterfactual 3: add final-station capacity or otherwise reduce downstream queueing

Observed downstream queueing is:

| case | downstream_queue, minutes | upper-bound saving if downstream queue removed | resource-conflict subset estimate |
|---|---:|---:|---:|
| F01 | 8 | 8 | 0 |
| F02 | 15 | 15 | 0 |
| F03 | 15 | 15 | 0 |
| F04 | 18 | 18 | 8 |
| F05 | 10 | 10 | 10 |
| F06 | 15 | 15 | 0 |
| F07 | 15 | 15 | 0 |
| F08 | 15 | 15 | 15 |
| F09 | 15 | 15 | 15 |
| F10 | 20 | 20 | 5 |
| F11 | 20 | 20 | 20 |
| F12 | 10 | 10 | 0 |
| **Aggregate** | **176** | **176** | **73** |
| **Mean** | **14.67** | **14.67** | **6.08** |

Upper-bound interpretation:

- If “otherwise reducing downstream queueing” means all observed `final_start - join_ready` waiting is removed, the potential aggregate saving is 176 minutes, mean 14.67 minutes per case.
- This is the largest single counterfactual saving among the three evaluated.

Resource-conflict subset:

- Using only the observed final-resource sequence, 73 minutes of the 176 minutes can be associated with the previous final job on the same resource still being active when the case is ready.
- The remaining 103 minutes may be due to release policy, batching, unobserved final-station tasks, resource availability not captured by `final_resource`, or data granularity.
- Therefore, adding physical capacity alone may not capture the full 176 minutes unless the unexplained waiting is also caused by capacity contention.

Cases with zero resource-conflict benefit:

- Under the conservative resource-conflict estimate, F01, F02, F03, F06, F07, and F12 have zero saving because no same-resource predecessor explains their downstream wait.
- This does not mean their waits are unimportant; it means the log does not prove they are caused by the two observed final resources being busy.

Secondary effects:

- If downstream queueing is reduced, branch delays become more visible. Total flow time may then be controlled even more strongly by B.
- If final capacity is increased without changing branch performance, final resources may experience more idle time because the fork-join stage remains the dominant elapsed-time block.
- If final release policy is changed rather than capacity added, the improvement may be cheaper but depends on identifying why `final_start` lags `join_ready`.

## Combined view

The three counterfactuals are not strictly additive because changing `join_ready` can change final-station queueing, and changing final-station queueing can change the realized value of branch improvements. Still, the directional conclusion is clear:

- B queue delay is the strongest branch-side lever.
- Downstream final-station waiting is the largest single observed elapsed-time lever after the fork-join stage.
- A service reduction has limited effect unless combined with B improvements.
- Final-station congestion can mask branch-side improvements, so branch and final-station redesigns should be evaluated together.

# 5. Recommended redesigns and risks

## Redesign 1: Reduce B queue delay

Recommended action:

- Increase effective Machine Stress Test capacity or reduce B queueing through scheduling, setup reduction, parallel testing, or priority rules for cases nearing branch completion.

Why this is recommended:

- B is the last-completing branch in 8 of 12 cases.
- B has the highest mean queue-plus-service duration from fork release.
- B controls the tail of the fork-join stage, including the two 75-minute fork-join cases.
- The 50% B-queue counterfactual produces 92.5 minutes of potential aggregate saving, far more than the A-service counterfactual.

Throughput:

- If B queueing is caused by limited stress-test capacity, reducing B queueing can increase throughput by preventing cases from stalling before the join.
- If B queueing is caused by batching or scheduling policy, throughput may improve without new capital investment.

Flow-time tail:

- This redesign directly attacks the worst fork-join delays. F07 and F12 both have 75-minute fork-join elapsed times and B-critical completion.

Resource utilization:

- B resource utilization may remain high if demand is unchanged. If queueing is reduced by adding capacity, utilization may fall unless throughput increases.
- A and C synchronization waiting should decrease because cases will reach the join more evenly.

Possible new bottlenecks:

- A may become critical more often. In the 50% B-queue counterfactual, A becomes binding or co-binding in cases such as F05 and F10.
- The final station may receive cases earlier, increasing downstream queueing if final capacity or release policy is unchanged.

Synchronization effects:

- Reducing B delay reduces the time completed A and C branches wait at the join.
- It may also make final arrivals more clustered, which can stress the final station unless release scheduling is smoothed.

What to pilot or measure first:

- Pilot a small B-capacity increase or scheduling change.
- Measure before and after:
  - `B_queue`
  - `B_end - fork_release`
  - critical-branch frequency
  - `join_ready - fork_release`
  - `final_start - join_ready`
  - total flow time
- Monitor whether A or final station waiting increases after B improvement.

## Redesign 2: Redesign final-station release policy or final-station capacity flexibility

Recommended action:

- Investigate and reduce the observed downstream queue between `join_ready` and `final_start`.
- This could be done by:
  - making F1 and F2 fully interchangeable if they are not already;
  - reducing administrative release delays;
  - allowing release decisions to start as soon as `join_ready` occurs;
  - adding a third final station only if resource-conflict waiting is confirmed by further measurement.

Why this is recommended:

- Downstream queueing averages 14.67 minutes per case.
- It is the largest single non-branch elapsed-time component after the fork-join stage.
- Some downstream waits are directly explainable by same-resource final jobs, for example F05, F08, F09, and F11.
- Other downstream waits occur even when the named final resource appears free, suggesting a release-policy or unobserved constraint that may be cheaper to fix than adding capacity.

Throughput:

- If the current final station is delayed by policy rather than capacity, smoothing release can increase effective throughput without adding resources.
- If resource conflicts are real, cross-training F1 and F2 or adding capacity can reduce blocking.

Flow-time tail:

- Cases F04, F10, and F11 have downstream queues of 18–20 minutes. Reducing these would directly reduce the upper tail of total flow time.

Resource utilization:

- If final resources currently have idle gaps but cases still wait, utilization measurement may reveal that the problem is scheduling rather than capacity.
- Adding a third final resource could reduce resource-conflict waiting but may have low utilization if the underlying issue is release policy.

Possible new bottlenecks:

- If final processing becomes faster, the fork-join stage, especially B, becomes the dominant constraint.
- If final releases are pulled earlier without branch improvements, final resources may spend more time waiting for branches.

Synchronization effects:

- Faster final release reduces synchronization-like waiting after the join.
- However, if final starts become earlier and more variable, final-station load may become less predictable.

What to pilot or measure first:

- Measure:
  - `final_start - join_ready`
  - final-resource idle time
  - final-resource conflicts based on predecessor final jobs
  - whether final starts are delayed by policy, approvals, batching, or resource absence
- Pilot flexible assignment between F1 and F2 before adding a third resource.
- If a third resource is considered, first simulate using observed `join_ready` and final service times.

# 7. Limits of inference

Several important things cannot be identified from the supplied timestamps alone.

## Causality

The decomposition identifies where time is spent, not why it is spent there. For example, B queue delay may be caused by limited machine capacity, batching, priority rules, maintenance, operator availability, or upstream sequencing. The data show that B starts late relative to `fork_release`, but they do not prove the cause.

## Branch resource capacity

No resource information is supplied for branches A, B, or C. We can observe that A starts immediately at `fork_release` in every case, but we cannot tell whether that is because A has ample capacity, because A work is scheduled first, or because the log omits hidden A-side waiting before `fork_release`. Similarly, B queue delay could reflect a true capacity constraint or merely a scheduling policy.

## Work preemption and interruptions

The timestamps give only start and end times for each branch. They do not show whether work was continuous, interrupted, preempted, or subject to rework. The “service time” calculated here is elapsed active duration from start to end, not necessarily hands-on processing time.

## Final-station waiting: queue or release policy?

The interval `final_start - join_ready` is treated as downstream queueing under the stated model assumptions. However, the log cannot prove that this interval is a pure queue. It could include:

- a deliberate release delay;
- administrative approval or documentation checking;
- batching of release decisions;
- final-resource unavailability not captured by `final_resource`;
- setup or transition time;
- policy buffers.

Some final waits occur even when the same final resource appears free based on the previous observed final job. That suggests either unobserved resource constraints or a release policy.

## Final-resource assignment rules

The log shows F1 and F2 assignments, but not whether assignments are fixed, flexible, priority-based, or opportunistic. Counterfactual capacity estimates therefore depend on assumptions about how cases would be assigned to existing or added final resources.

## Small sample and timestamp granularity

There are only 12 cases, all on one day. The observed patterns may not represent long-run behavior. Timestamps are accurate to one minute, so fractional counterfactual savings such as 12.5 minutes should be interpreted as model estimates, not observed minute-level events.

## Counterfactual uncertainty

The counterfactual savings are conditional on assumptions. Branch-side savings are measured as reductions in `join_ready`. Realized total flow-time savings depend on whether the final station can start earlier. If final-station congestion or release policy fixes `final_start`, branch-side improvements may be masked. Conversely, if final-station scheduling is improved, branch-side savings may become more visible.

## Process-mining limitation

Standard directly-follows performance analysis can show activity durations and observed transitions, but it does not by itself recover fork-join synchronization semantics. The unlogged `join_ready` must be reconstructed from the max of branch completions, and synchronization waiting must be computed explicitly. This is why the core decomposition relies on custom pandas calculations, with PM4Py used mainly for interval-event representation and activity service-time validation.
