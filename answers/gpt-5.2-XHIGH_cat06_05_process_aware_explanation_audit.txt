## 2. Process-model consistency checks

Build a validation suite that treats “admissible at `t0`” as a first-class contract and separately checks conformance to the normative process.

- **A. Prefix-time availability (feature-store “as-of” contracts)**  
  - For every feature, store metadata: `feature_time` (the latest time of any data used), `generated_at`, `source_tables`, and an `as_of_cutoff` (must be \(\le t0\)).  
  - Automated test per case: recompute features from raw sources using only records with timestamps \(\le t0\); compare to production feature values. Any feature with `feature_time > t0` fails the build (critical).  
  - Static lineage checks for “complete-trace” patterns: feature SQL that aggregates “total”, “final”, “anywhere”, or uses tables keyed by case closure without as-of constraints is flagged for manual review.

- **B. Activity-order feasibility (normative constraints vs empirical edges)**  
  - Encode the normative process as a simple Petri net/BPMN (or declarative constraints):  
    - `Claim Registered` precedes `Coverage Check Completed`.  
    - `Claim Closed` must occur after a final decision or withdrawal.  
    - `Appeal` only after a `Settlement Decision Recorded` with outcome Partial or Deny; and then a second `Settlement Decision Recorded` is allowed.  
    - Evidence cycle `Documents Requested -> Documents Received -> Documents Validated` may repeat; damage assessment follows evidence completion on that path.  
  - Run **alignment / token-based replay** to detect impossible orderings and missing/extra events. Use it to *diagnose data quality and feasibility*, not to “prove” causality.
  - Complement with **footprint/prefix checks**: verify forbidden relations (e.g., `Claim Closed` before `Damage Assessment Completed`) and required precedences.
  - Important limitation: a frequent **DFG** edge is not a normative rule; it is only a statistical summary and can be distorted by timestamp ties and label coarsening.

- **C. Same-timestamp ambiguity handling**  
  - Detect cases with equal timestamps and missing `sequence_index`. Treat ordering among tied events as **unknown (partial order)**.  
  - For conformance and pattern mining, either (i) exclude tie-dependent relations, or (ii) impute order only with reliable tie-breakers (event IDs, lifecycle transitions) and mark imputed edges.  
  - Block any explanation that relies on an ordering that is not identifiable (e.g., `Claim Closed -> Damage Assessment Completed` when both share a timestamp and no index exists).

- **D. Complete-trace dependence checks for explainers**  
  - For SHAP-like explainers: enforce that explanations are computed from the **same admissible feature vector** used for prediction at `t0`.  
  - For sequence/pattern explainers: enforce that any “pattern present = 1” references only events in the observed prefix (\(\le t0\)). If the explainer wants to mention future-reachable steps, it must do so as **process-enabled possibilities** (“next enabled activities include …”), not as observed facts.

- **E. Enabled / impossible / future-possible explanation gating**  
  - Given the process state at `t0` (immediately after first `Coverage Check Completed`), categorize any activity mentioned in an explanation as:  
    - **Observed** (in prefix),  
    - **Enabled-next** (can occur next),  
    - **Future-possible** (reachable later but not enabled now),  
    - **Impossible** (violates normative model).  
  - At `t0`, activities like `Claim Closed`, `Appeal`, and `Settlement Decision Recorded` are not observed; `Claim Closed` is effectively impossible as an immediate next step; `Appeal` is future-possible only after an initial decision; `Documents Requested` and `Damage Assessment Completed` are enabled-next depending on the branch; `Fraud Investigation Opened` is enabled-next only if triggers exist. Explanations must respect these categories.

- **F. Repeated `Settlement Decision Recorded` semantics**  
  - Add a `decision_round` (1, 2, …) and/or an explicit link to a preceding appeal. Validate: round 2 exists only if an appeal exists, and appeal preconditions (Partial/Deny) hold.  
  - Ensure sequence explanations distinguish “decision after appeal” from “initial decision” to avoid semantic errors.

## 3. Alternative feature interpretations

Below are process-aware classes for the surviving or repairable signals, and what may/may not be claimed in each.

- **Defensible predictive signal (case attributes / early assessments)**  
  - **Examples**: `initial_damage_complexity`, `initial_reserve` (if stored as-of `t0`), `prior_claim_count_before_t0` (after SQL fix), `risk_score_at_t0` (after timestamping).  
  - **May claim**: these attributes are *associated* with higher/lower breach risk in out-of-sample evaluation when computed strictly as-of `t0`.  
  - **May not claim**: changing these fields (or the claimant) would causally change breach; many are descriptive, partially subjective, or proxies for latent factors.

- **Process-state or congestion signal (system context at `t0`)**  
  - **Examples**: `queue_length_at_t0` (with `snapshot_time <= t0`), `elapsed_since_registration_at_t0` (slack/age), `handler_team_at_t0` + team workload (after lineage repair).  
  - **May claim**: the model is using *current workload/state* and *remaining slack* indicators that historically correlate with misses.  
  - **May not claim**: congestion is the sole cause for a specific case, or that simply “moving a case” will reduce breach without testing; these are portfolio-level levers and can induce spillovers.

- **Proxy requiring fairness/robustness review (risk of discriminatory or unstable explanations)**  
  - **Examples**: `claimant_region`, `claimant_channel`, and potentially `handler_team_at_t0` if assignment correlates with claimant attributes.  
  - **May claim**: they improve predictive accuracy under strict governance and do not introduce unacceptable disparities (to be demonstrated).  
  - **May not claim**: “region causes delay” or “broker causes breach.” Explanations shown to end users should avoid attributing outcomes to protected/proxy attributes; use them, if at all, as internal risk stratifiers with fairness controls.

- **Drift/calendar proxy (regime detection rather than mechanism)**  
  - **Examples**: `calendar_week` (aligned with policy changes/holidays).  
  - **May claim**: captures regime effects (staffing, holidays, policy changes) that affect throughput and may improve calibration within known regimes.  
  - **May not claim**: week number is a mechanistic cause. It can degrade generalization; requires monitoring and potentially being replaced by explicit regime features.

- **Unusable until lineage is repaired (must not appear in `t0` explanations)**  
  - **Examples**: `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, `last_resource_role`, `same_day_document_count_snapshot` (until as-of), `final_handler_team` (until as-of), `risk_score_current` (until timestamped), sequence patterns referencing future/end-of-case events.  
  - **May claim**: nothing at `t0`; their current definitions violate the admissibility contract.  
  - **Required**: redesign feature definitions with explicit timestamps and prefix-only computation; then re-evaluate predictive value and recalibrate.

## 5. Recommendations for explanation validation

- **1) Enforce an “as-of `t0`” feature-store contract (highest priority)**  
  - Add `feature_time`/`as_of_cutoff` to every feature and block any feature where `feature_time > t0`.  
  - Use SCD2/as-of joins for mutable dimensions (handler team, employee experience, roles, risk scores, reserves).  
  - Prohibit “final/total/anywhere/last” fields in early-prediction feature views unless explicitly defined as prefix-only.

- **2) Rebuild training data with prefix-only recomputation**  
  - Re-extract training examples exactly at `t0` and compute features strictly from data \(\le t0\).  
  - Remove leaked features/patterns, retrain, and **recalibrate** probabilities (Platt/isotonic) because removal of leakage typically reduces apparent confidence.

- **3) Add conformance and temporal-leakage tests to CI/CD**  
  - Unit tests for known pitfalls: `claim_created_at < t0` (not extraction date), `snapshot_time <= t0`, and “no closure-stage fields at `t0`.”  
  - Process feasibility checks via alignments/footprints and declarative constraints; fail builds when impossible orderings appear above a threshold, and quarantine cases with missing sequence indices.

- **4) Redesign explainers to be process-aware at the right time**  
  - SHAP-like explainers must operate on the exact admissible feature vector used at inference.  
  - Sequence explainers must be **prefix-only** at `t0`; if you want to communicate future-reachable steps, present them as *enabled possibilities* (with uncertainty), not observed patterns.  
  - Gate explanation content by process state (observed vs enabled-next vs future-possible vs impossible).

- **5) Validate explanation stability and sensitivity**  
  - Track explanation drift over time and across retrains (e.g., stability of top drivers, SHAP variance).  
  - Run ablations: remove calendar/region/channel and quantify performance, calibration, and explanation shifts to detect overreliance on proxies/regime effects.

- **6) Proxy/fairness and robustness analysis before surfacing reasons**  
  - For `claimant_region`/`claimant_channel` (and any similar proxies), evaluate group-wise calibration, false positive/negative rates, and counterfactual robustness.  
  - Decide governance: allow for internal triage with monitoring vs exclude from user-facing explanations (or replace with operational mediators).

- **7) Monitor process/schema drift and data-quality signals**  
  - Detect changes in event ordering quality (rise in same-timestamp ties, missing sequence index), process variants, and policy/holiday regimes.  
  - Alert on shifts in feature missingness, as-of violations, and conformance deviations; retrain/recalibrate when regimes change.
