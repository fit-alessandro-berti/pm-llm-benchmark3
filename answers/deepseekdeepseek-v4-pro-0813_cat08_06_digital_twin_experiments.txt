def case_arrival_stats(df):
    df = df.copy()
    df['time:timestamp'] = pd.to_datetime(df['time:timestamp'])
    first_ts = df.groupby('case:concept:name')['time:timestamp'].min().sort_values()
    interarrival = first_ts.diff().dropna()
    avg_seconds = interarrival.mean().total_seconds()
    avg_days = avg_seconds / 86400.0
    print(f"Average interarrival: {avg_days:.4f} days; average daily arrivals: {1/avg_days:.2f}")

## 1. Model scope and state variables

**Digital twin boundary**

- Includes the municipal permit process from **Submit application** through **Issue permit** or **Reject application**.
- Includes municipal service activities, applicant/third-party response delays, resource calendars, queues, rework, and cross-case dependencies.
- Includes case-level interactions that can affect multiple permits: same-architect submission bursts, neighborhood objections, and district-batched inspections.
- Excludes construction after permit, post-issuance court appeals, and non-permit work of environmental reviewers outside the modeled share.

**Level of detail**

- Discrete-event simulation in continuous time.
- Activity-level events, not sub-activity task decomposition, except inspection travel time can be separated from on-site inspection service time.
- Municipal service times are sampled from fitted distributions by activity, case type, district, resource pool, and rework status.
- Applicant and third-party times are modeled as exogenous stochastic durations with heavy tails.
- Process tree is used as nominal control-flow prior, but executable routing uses attribute-based rules and estimated probabilities.

**Entities**

- **Case**: permit application with case attributes: `case_type`, `district`, `architect_id`, `application_value`, flags for fire, environment, public notice, prior violations, rework counts, and current process state.
- **Applicant/architect**: source of submissions, document responses, and missing-doc loops. Top architects can submit multiple related applications.
- **Third party/objector**: latent process affecting public-notice extension and possibly related cases.
- **Resource**: clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, and system resources.
- **Queue**: activity queues with priority rules for aging cases, batching groups, and district.
- **Inspection bundle**: group of cases in the same district that can be scheduled together to reduce travel time.

**State variables**

- `case_status`: current activity, queue, or completed/rejected.
- `waiting_time`: time spent in queue before current activity.
- `service_time`: sampled or actual municipal service duration.
- `rework_count`: number of rework loops by activity.
- `missing_doc_loop_count`: number of missing-document cycles.
- `objection_status`: latent object; observed only through public-notice extension.
- `resource_available`: available capacity for each resource pool.
- `queue_state`: current cases waiting, priorities, district, and batching eligibility.
- `calendar_state`: date, time, public holiday, council meeting week, weekday.
- `global_policy_state`: activated interventions and any conditional routing rules.

**Queues, calendars, and cross-case dependencies**

- Shared queues create dependency through resource contention.
- Planners, clerks, fire reviewers, environmental reviewers, inspectors, and legal officers use HR calendars.
- Inspectors can batch field visits by district.
- Legal officers are unavailable during council meeting weeks except urgent cases.
- Fire reviewers are available only Tuesday-Thursday.
- Environmental reviewers have 40% non-permit duty.
- Public-notice periods are handled as system/calendar-constrained durations with latent objection extensions.
- Architect bursts create correlated arrivals.
- Objections can affect multiple cases in a district or neighborhood window.
- District-batched inspections reduce travel time but may increase waiting for the first case in a batch.

## 2. Parameter-estimation plan

**2.1 PM4Py log/model handling**

- Use `pandas.read_csv` to load event logs.
- Do **not** use a nonexistent `pm4py.read_csv`.
- Convert to a PM4Py event log with:

```python
pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)
```

- Use `pm4py.get_variants` to compute variant frequencies.
- Use `pm4py.discover_dfg` for control-flow summary.
- Use `pm4py.discover_performance_dfg` only as a first-pass throughput diagnosis.
- Use `pm4py.parse_process_tree` to parse or import the simplified process tree as a structural prior.
- **Important:** performance DFG duration is not a service-time estimate. It is the observed throughput duration between activity completions.

**2.2 Arrival estimation**

- Use first event per case as the arrival timestamp.
- Fit a time-varying Poisson or negative binomial model for daily arrivals with:
  - month factors;
  - day-of-week factors;
  - seasonal peak factors;
  - holiday effects;
  - top-architect burst effects.
- Estimate the known factors from the log:
  - Monday: ~2.2× Wednesday;
  - March-May and September-November: ~1.7× January-February.
- For top-20 architects, estimate a burst process:
  - probability that an application from a top architect occurs within 7 days of a prior application by the same architect;
  - size distribution of related application clusters.
- Use covariates to avoid treating the burst as purely random independent Poisson arrivals.

**2.3 Service-time and waiting-time estimation**

- For cases with start and completion timestamps:
  - `service_time = completion - start`;
  - `waiting_before = start - previous_completion`.
- For cases with missing start timestamps:
  - treat observed `completion - previous_completion` as an interval-censored sum of waiting plus service;
  - do **not** collapse waiting and service into one service-time distribution;
  - use Bayesian latent variable models or survival/deconvolution approaches to separate waiting and service distributions.
- Fit positive heavy-tailed distributions:
  - lognormal;
  - gamma;
  - Weibull.
- Use case attributes and queue covariates when estimating waiting-time distributions.
- Model inspection travel time separately from on-site service time.

**2.4 Branching and routing probabilities**

- Estimate routing probabilities from variant shares and case attributes.
- Use logistic regression or probabilistic decision trees for:
  - fire review required;
  - environmental review required;
  - public notice required;
  - legal check required;
  - inspection required;
  - final issue/reject.
- For missing thresholds or incomplete sensitivity data:
  - use multiple imputation;
  - retain uncertainty around expected routing probabilities.
- Estimate rework probabilities from repeated activity episodes:
  - planning rework;
  - inspection rework;
  - legal rework;
  - appeal-related rework.
- Use unstructured rework reason text only as a supplementary latent classifier, not as ground truth.

**2.5 Resource calendars and availability**

- Use HR calendars as prior calendars.
- Validate with event-log timestamps:
  - fire reviewers should not complete tasks outside Tuesday-Thursday;
  - legal officers should not complete non-urgent work in council meeting weeks;
  - inspectors should not perform field visits on Mondays.
- Estimate effective availability factors for environmental reviewers, clerks, and legal officers.
- Use timestamped resource activity to estimate workload and validation metrics.

**2.6 Dependencies and missing data**

- **Architect bursts**: estimate top-architect clustering from `architect_id` and submission timestamps.
- **Objections**: treat objections as a latent mixture process. Public notice above the 14-day fixed minimum is a proxy. Fit a zero-inflated or two-component duration model:
  - `notice_duration = 14d fixed + objection_extension` when latent objection occurs.
- **Inspection batching**: estimate the current degree of district batching from case timestamps and inspector IDs.
- **Missing starts**: modeled as censored, not observed.
- **Missing objection events**: modeled as latent, not as observed none.
- **Missing rare emergency decisions**: noted as removed; they are excluded from normal policy comparison inference and reported as coverage limitation.

## 3. Assumptions

**Arrivals**

- Nonstationary Poisson-like demand with monthly and weekday factors.
- Monday arrivals substantially higher than Wednesday, as given in the data summary.
- Arrival bursts for top architects are not independent; a top architect can generate multiple related applications in the same week.
- Policies D1 and D7 can affect applicant submission behavior and/or timing.

**Service times**

- Municipal service times are independent conditional on activity, case type, district, resource pool, rework status, and batching.
- Human service times are positive and heavy-tailed; lognormal/gamma/Weibull are candidates.
- System tasks are effectively unlimited capacity, but date-based constraints can still affect calendar-driven states such as public-notice period.
- Inspection time is decomposed into on-site service time plus district-dependent travel time.
- Missing start timestamps imply service/waiting split is uncertain; the model does not assume throughput duration equals service time.

**Routing**

- Routing follows estimated probabilities and explicit case attributes.
- The given process tree is a useful nominal control-flow prior but not a fully executable BPMN model.
- Fire and environmental requirements are partly imputed because some thresholds and sensitivity data are missing.
- Public notice is required for Complex variance and some New residential cases; objections can extend it.
- Decision drafting waits for all applicable reviews and inspection results.

**Resources/calendars**

- Resource calendars are reconstructed HR calendars and are treated as priors, not fixed truth.
- Human resources are capacity-constrained by working hours and part-time availability.
- Tasks can pause across non-working hours, except field inspections which are scheduled as site visits.
- Legal officers are mostly unavailable in council meeting weeks except urgent cases.
- System tasks do not contend with human resource capacity.

**Rework**

- Rework occurs after Planning review, Inspection, Legal check, or applicant appeal.
- Rework probability depends on case type, district, value, prior rework, and whether required reviews are missing or incomplete.
- Rework duration combines service time and waiting time with the same resource calendars.
- Rework reason is modeled as a latent categorical factor, not a fully reliable text-coded field.

**Applicant/third-party response**

- Missing-document response time is applicant-driven and heavy-tailed.
- Applicants can request missing documents more than once, but probability decreases with each loop unless policy D1 changes it.
- Third-party consultant and objector responses are partially observed through downstream duration.
- Applicant/third-party response is not treated as municipal service time.

**Cross-case dependencies**

- Same-architect submissions can be correlated in timing and case attributes.
- Neighborhood objections are latent and can affect several related active cases.
- Inspection scheduling can be batched by district.
- Resource queues create indirect case-to-case interactions.

**Non-stationary demand**

- Seasonal and day-of-week demand effects are deterministic multipliers around a baseline arrival rate.
- Architect bursts are stochastic but nonstationary.
- Policy changes can alter future arrival timing or case mix.
- No assumption of perfectly stationary waiting or service conditions.

**Missing data**

- Start timestamps are missing for many human activities; these are inferred.
- Objection events are missing; they are modeled as latent.
- Rework reasons are not reliably coded; they are modeled only as noisy latent categories.
- HR calendars are not assumed to be perfectly reflected in logs.
- Rare emergency decisions removed from the log are not modeled as ordinary cases.

## 5. Warm-up, replications, and uncertainty treatment

**Warm-up**

- Use a 12-month warm-up period covering a full seasonal cycle.
- Initialize queues, partial cases, and inspection bundles using the observed distribution of end-of-warm-up backlog.
- Discard all warm-up KPIs before analysis.
- After warm-up, run the operational evaluation period.

**Run length**

- Use a 48-month evaluation period after warm-up.
- A shorter run of at least 24 months is acceptable only for early exploratory runs.
- 48 months allows multiple seasonal peak cycles and enough tail-event observations.

**Replications**

- Use 50 replications for initial mean, median, and utilization comparisons.
- Use 100-200 replications for tail metrics such as p90 and p95 because quantile variance is high.
- Use common random numbers for intervention comparisons to reduce variance.

**Random seeds and streams**

- Use one master `numpy.random.SeedSequence`.
- Create independent child random streams for:
  - arrivals;
  - case attributes;
  - service times;
  - waiting times;
  - applicant/third-party response;
  - objection events;
  - rework;
  - resource scheduling.
- Keep policy comparisons paired by seed where possible.

**Confidence and credible intervals**

- For means and utilizations: use replication mean ± t-based confidence interval or batch-means interval.
- For quartiles and p90/p95: use ordered-statistic bootstrap or percentile bootstrap over replicate summary statistics.
- For parameter uncertainty: draw multiple model parameter sets by bootstrap or Bayesian posterior sampling from the event log.
- Combine parameter uncertainty and simulation uncertainty into two-level intervals:
  - draw M parameter sets;
  - run N simulation replications per parameter set;
  - report overall 95% intervals.
- Avoid interpreting small overlapping differences as meaningful.

**Heavy-tailed durations**

- Fit heavy-tailed distributions explicitly.
- Report median, p90, p95, and perhaps p99.
- Do not use the Gaussian distribution for duration.
- Inspect QQ plots and tail behavior.
- For very rare extremes, note that simulation may underestimate the maximum possible duration even with many replications.

  - missing-doc response time;
  - rework counts.
- Use QQ plots, Hellinger distance, or maximum mean discrepancy, not only means.
- Do not validate only against the historical mean.

**Resource-utilization validation**

- Compare simulated weekly and monthly utilization by resource pool against log-derived workload.
- Validate special calendar constraints:
  - fire review only Tuesday-Thursday;
  - legal low activity in council meeting weeks;
  - inspector field visits Tuesday-Friday.
- Check that queues form at the correct bottlenecks: Planning review, Inspection scheduling, Legal check, and Environmental review.

**Bottleneck validation**

- Calculate simulated mean waiting and utilization by activity.
- Compare with observed waiting summaries and known bottlenecks.
- If simulated bottleneck ranks do not match observed bottleneck ranks, recalibrate service/wait decomposition or routing probabilities.

**Out-of-sample validation**

- Hold out the last 3 months of the 18-month event log.
- Calibrate on the first 15 months.
- Simulate the hold-out period using actual arrival timestamps or a separate arrival model.
- Compare simulated and observed KPIs, especially median duration and p90 duration.
- Use rolling-origin validation if data volume allows.
- Do not claim an intervention is optimal unless out-of-sample validation shows stable model behavior.

---

## 7. Decision criteria

Use these metrics and ranges. All criteria should be evaluated with uncertainty intervals, not by a single replication.

**Duration metrics**

- Overall median duration:
  - Improvement relative to baseline;
  - Not allowed to worsen by more than 5% for any common case type.
- Tail duration:
  - p90 overall and by case type;
  - p95/p99 for Complex variance and Commercial;
  - Tail should not degrade by more than 10% from baseline.
- Case-type target ranges:
  - Simple renovation: median  15 days, p90  40 days;
  - New residential: median  55 days, p90  100 days;
  - Commercial: median  75 days, p90  150 days;
  - Complex variance: median  160 days, p90  280 days.

**SLA compliance**

- Simple renovation: 80% decided within 30 days.
- New residential: 80% decided within 100 days.
- Commercial: 80% decided within 150 days.
- Complex variance: 70% decided within 300 days.
- Evaluate SLA compliance by case type, not only overall.

**Fairness across districts and architects**

- District duration ratio:
  - highest district p90 / lowest district p90  1.5.
- No district should have p90 worsen by more than 10% while overall duration improves.
- Top-20 architect cases should not be systematically favored or heavily delayed compared with smaller architects.

**Resource utilization**

- Planners: target 70-85% active municipal capacity.
- Inspectors: target 70-85% active field capacity.
- Legal officers: target 70-80% available capacity.
- Fire reviewers: target 50-70% available capacity.
- Environmental reviewers: target 55-75% municipal permit-related capacity.
- Sustained pool utilization above 90% for four weeks is a warning threshold.

**Rework and backlog**

- Rework rate should not increase by more than 5 percentage points.
- Missing-doc loops should decline under D1.
- Backlog measured as number of cases waiting > 10 business days should not increase by more than 10% under normal demand.
- During stress scenarios, backlog may increase but should return within two months after the stress peak.

**Robustness**

- A candidate intervention is preferred if its benefits remain under stress scenarios.
- Compute probability that an intervention beats baseline on median and p90 across parameter uncertainty.
- Use a Pareto-style comparison:
  - duration tail;
  - fairness;
  - resource utilization;
  - backlog;
  - implementation complexity.
- A policy is selected only if its credible or confidence intervals show meaningful improvement and no severe fairness/tail degradation.

def sanitize_process_tree_string(tree_str: str) -> str:
    """
    PM4Py process tree labels normally use identifiers, not quoted strings.
    Replace 'Submit application' with Submit_application etc.
    """
    def replace_quoted_label(match: re.Match) -> str:
        label = match.group(1)
        label_id = re.sub(r"[^A-Za-z0-9]+", "_", label).strip("_")
        return label_id or "activity"

    return re.sub(r"'([^']+)'", replace_quoted_label, tree_str)


def parse_tree(tree_str: str = PROCESS_TREE_SIMPLIFIED):
    """
    Attempt to parse the process tree. If the quotated form fails, parse the
    sanitized identifier form. The parsed tree is used only as a process
    model prior, not as a full executable simulation engine.
    """
    candidates = [tree_str, sanitize_process_tree_string(tree_str)]
    for cand in candidates:
        if parse_process_tree is not None:
            try:
                pt = parse_process_tree(cand)

                return pt

    return None

def pm4py_log_summary(df: pd.DataFrame) -> Tuple:
    """
    Convert to PM4Py event log and compute variants, DFG, and performance DFG.
    """
    df = df.copy()
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])

    event_log = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp"
    )

    variants = pm4py.get_variants(event_log)
    dfg, start_activities, end_activities = pm4py.discover_dfg(event_log)
    performance_dfg, perf_start_activities, perf_end_activities = pm4py.discover_performance_dfg(event_log)

    print("Number of variants:", len(variants))
    print("Number of DFG edges:", len(dfg))
    print("Number of performance DFG edges:", len(performance_dfg))

    return event_log, variants, dfg, performance_dfg


def case_arrival_stats(df: pd.DataFrame) -> Tuple[pd.Series, pd.Series, float]:
    """
    Estimate case arrival average from first timestamp per case.
    """
    df = df.copy()
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])
    first_timestamps = (
        df.groupby("case:concept:name")["time:timestamp"]
        .min()
        .sort_values()
    )

    interarrival = first_timestamps.diff().dropna()
    avg_interarrival_days = (
        interarrival.mean().total_seconds() / 86400.0
        if not interarrival.empty
        else np.nan
    )

    print(f"Average interarrival: {avg_interarrival_days:.4f} days")
    if not np.isnan(avg_interarrival_days) and avg_interarrival_days > 0:
        print(f"Average daily arrivals: {1.0 / avg_interarrival_days:.4f}")
    else:
        print("Average daily arrivals: unavailable for this excerpt")

    return first_timestamps, interarrival, avg_interarrival_days


def compute_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Create service and waiting time columns if start timestamps exist.

    This excerpt does not contain start_timestamp. Therefore service time is
    NaN. The observed throughput-time-from-previous-completion is NOT the same
    as service time.
    """
    df = df.copy()
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])

    has_start = "start_timestamp" in df.columns

    if has_start:
        df["start_timestamp"] = pd.to_datetime(df["start_timestamp"])
        df["service_time_hours"] = (
            (df["time:timestamp"] - df["start_timestamp"]).dt.total_seconds() / 3600.0
        )
    else:
        df["start_timestamp"] = pd.NaT
        df["service_time_hours"] = np.nan

    df = df.sort_values(["case:concept:name", "time:timestamp"])
    df["previous_completion"] = df.groupby("case:concept:name")["time:timestamp"].shift(1)
    df["throughput_time_from_prev_hours"] = (
        (df["time:timestamp"] - df["previous_completion"]).dt.total_seconds() / 3600.0
    )

    if has_start:
        df["waiting_before_hours"] = (
            (df["start_timestamp"] - df["previous_completion"]).dt.total_seconds() / 3600.0
        )
    else:
        df["waiting_before_hours"] = np.nan

    return df
