       """
       events: list of dicts, each with 'timestamp', 'activity', 'object_ids' (dict: object_type -> list of ids)
       notes: string or dict of O2O qualifiers (optional)
       returns: tuple suitable for clustering, invariant to local ID renaming.

       seq = tuple(evt['activity'] for evt in events)
       
       # 2. Object type participation counts per activity
       # We count, for each (activity, object_type), how many events mention that type.
       # This is invariant to how many IDs of that type are in one event? 
       # To capture multiplicities, we could count total ID occurrences, but let's count event occurrences 
       # and also track total ID counts separately. I'll do both: 
       # - event_based: count of events with that type in that activity
       # - id_based: total number of object IDs of that type mentioned across events of that activity
       # I'll use id_based for "object multiplicities".
       from collections import Counter
       type_participation = Counter()  # (activity, object_type) -> total ID count
       for evt in events:
           label = evt['activity']
           for obj_type, ids in evt['object_ids'].items():
               type_participation[(label, obj_type)] += len(ids)
       
       # 3. External object types
       external_types = set()
       for evt in events:
           for obj_type, ids in evt['object_ids'].items():
               if any(obj_id.startswith('EXT') for obj_id in ids):
                   external_types.add(obj_type)
       external_fs = frozenset(external_types)
       
       # 4. O2O qualifiers
       qualifiers = set()
       if notes:
           # parse notes; for this exercise, we'll assume notes contain qualifier keywords
           # I'll add a simple extraction: look for known qualifiers
           known = ['removed_before_dispatch', 'partial_settlement', 'completes_settlement',

           for q in known:

           seq,

       )

   ### 1.1 Activity-sequence equivalence (AS-eq)
   **Definition:** Two executions $E, E'$ are AS-equivalent iff the sequences of their activity labels, extracted in timestamp order and with all object identifiers, O2O metadata, and multiplicity details removed, are identical. Formally, let $\lambda(E) = (l_1, l_2, \dots, l_n)$ be the tuple of activity labels in event timestamp order. Then $E \approx_{AS} E' \iff \lambda(E) = \lambda(E')$.
   **Invariants:** Ordered list of activity labels (a string multiset with order).
   **Discarded:** All object IDs, object types, external-object flags, O2O qualifiers, payment multiplicities, and any event-specific details beyond the label.
   **Reflexivity/symmetry/transitivity:** Holds because equality of tuples is an equivalence relation.
   **Concurrency:** Executions are provided with timestamp-ordered events; if concurrent events existed, we would project to a partial order and require order-isomorphism of the causal net. Here, total order is assumed.

   ### 1.2 Typed structural equivalence (TS-eq) under identifier renaming
   **Definition:** Two executions $E, E'$ are TS-equivalent iff there exists a bijection $\phi$ between their object identifiers such that:
   - $\phi$ preserves object types (i.e., if $obj$ has type $T$, $\phi(obj)$ has type $T$).
   - $\phi$ preserves the EXT prefix: $obj$ starts with `EXT` iff $\phi(obj)$ starts with `EXT`.
   - For every event $e$ in timestamp order, the multiset of $(object\_type, is\_EXT)$ pairs participating in $e$ is identical in $E$ and $\phi(e)$ in $E'$.
   - The total order of events is preserved.
   **Invariants:** Object type distribution per event, EXT-flag alignment, event-ordered incidence structure.
   **Discarded:** Specific identifier values, but retained is which types interact in which event and in what order.
   **Reflexivity/symmetry/transitivity:** Yes; isomorphism of typed, ordered event structures is an equivalence relation.
   **Concurrency:** Same as AS-eq; total order assumed.

   ```python
   def compute_canonical_signature(events, notes=""):
       """
       Compute a canonical signature for an object-centric execution,
       invariant to local identifier renaming but preserving:
       - object types
       - object multiplicities (total ID counts per type per activity)
       - external-object flags
       - event order (total order of labels)
       - E2O incidence (via type participations)
       - O2O qualifiers
       - repeated activities
       
       events: list of dicts, each with 'activity' (str) and 
               'object_ids' (dict: str -> list of str, where keys are object types)
       notes: string containing O2O qualifier keywords (from the execution's O2O notes)
       
       returns: tuple (seq, type_part, external_set, qualifiers_fs, act_counts)
       """
       from collections import Counter
       
       # 1. Activity label sequence in timestamp order (already assumed sorted)
       seq = tuple(evt['activity'] for evt in events)
       
       # 2. Object type participation: total number of object IDs mentioned
       #    per (activity, object_type) across all events.
       type_part = Counter()  # (activity, obj_type) -> int
       for evt in events:
           label = evt['activity']
           for obj_type, ids in evt['object_ids'].items():
               type_part[(label, obj_type)] += len(ids)
       
       # 3. External object types: any object ID starting with 'EXT'
       external_types = set()
       for evt in events:
           for obj_type, ids in evt['object_ids'].items():
               if any(obj_id.startswith('EXT') for obj_id in ids):
                   external_types.add(obj_type)
       external_fs = frozenset(external_types)
       
       # 4. O2O qualifiers: extract known keywords from notes
       known_qualifiers = [
           'removed_before_dispatch',
           'partial_settlement',
           'completes_settlement',
           'replaces',
           'cross_order',
           'shared'
       ]
       found_qualifiers = set()
       notes_lower = notes.lower()
       for q in known_qualifiers:
           if q in notes_lower:
               found_qualifiers.add(q)
       qualifiers_fs = frozenset(found_qualifiers)
       
       # 5. Repeated activity counts (derivable from seq, but included explicitly)
       act_counts = Counter(seq)
       act_counts_fs = frozenset(act_counts.items())
       
       # 6. Build signature tuple
       # We use frozenset of items for type_part and act_counts to make it hashable/order-independent in clustering,
       # but the seq tuple preserves order.
       signature = (
           seq,  # activity label sequence (order preserved)
           frozenset(type_part.items()),  # renaming-invariant type participations
           external_fs,
           qualifiers_fs,
           act_counts_fs
       )
       return signature
   ```

## 1. Equivalence design space

### 1.1 Activity-sequence equivalence (AS-eq)
**Definition:** Two executions \(E, E'\) are AS-equivalent iff the sequences of their activity labels, extracted in timestamp order and with all object identifiers, O2O metadata, and multiplicity details removed, are identical. Formally, let \(\lambda(E) = (l_1, l_2, \dots, l_n)\) be the tuple of activity labels in event timestamp order. Then \(E \approx_{AS} E' \iff \lambda(E) = \lambda(E')\).

**Invariants:** Ordered list of activity labels (a string tuple with preserved order).

**Discarded:** All object IDs, object types, externalobject flags, O2O qualifiers, payment multiplicities, and any eventspecific details beyond the label.

**Reflexivity/symmetry/transitivity:** Holds because equality of tuples is an equivalence relation.

**Concurrency handling:** Executions are provided with timestampordered events; we assume a total order. If concurrent events were present, we would project to the causal partial order and require orderisomorphism of the causal net. Here, the total order is the default.

---

### 1.2 Typed structural equivalence (TS-eq) under identifier renaming
**Definition:** Two executions \(E, E'\) are TS-equivalent iff there exists a bijection \(\phi\) between their object identifiers such that:
- \(\phi\) preserves object types (if \(obj\) has type \(T\), \(\phi(obj)\) has type \(T\)).
- \(\phi\) preserves the EXT prefix: \(obj\) starts with `EXT` iff \(\phi(obj)\) starts with `EXT`.
- For every event \(e\) in timestamp order, the multiset of \((object\_type, is\_EXT)\) pairs participating in \(e\) is identical in \(E\) and \(\phi(e)\) in \(E'\).
- The total order of events is preserved.

**Invariants:** Object type distribution per event, EXTflag alignment, eventordered incidence structure.

**Discarded:** Specific identifier values, but retained is which types interact in which event and in what order.

**Reflexivity/symmetry/transitivity:** Yes; isomorphism of typed, ordered event structures is an equivalence relation.

**Concurrency handling:** Same as AS-eq; total order assumed.

---

### 1.3 Business-semantic equivalence (BS-eq)
**Definition:** Two executions are BS-equivalent iff they yield identical canonical signatures \(\sigma(E) = \sigma(E')\), where \(\sigma\) is the signature function defined in Section 2. This relation aggregates type participations, externalobject flags, O2O qualifiers, and repeatedactivity counts into a businessoperationabstraction that identifies executions modeling the same operational variant, tolerating structural rearrangements that do not change the core business meaning.

**Invariants:** Canonical signature components (activity sequence, type participations, external flags, qualifiers, repeatedactivity counts).

**Discarded:** Exact object IDs, minor event orderings that do not alter the core business meaning, purely cosmetic renames.

**Reflexivity/symmetry/transitivity:** Holds because signature equality is an equivalence relation.

**Concurrency handling:** Signature preserves event order; if partial order were used, the signature would incorporate partialorder isomorphism, but here total order is used.

## 2. Canonical signatures

The following Pythonlike function produces a signature invariant to local identifier renaming while preserving the specified structural dimensions. It is designed for the “preferred semantic cluster” (BS-eq) but can be adapted.

```python
from collections import Counter

def compute_canonical_signature(events, notes=""):
    """
    Compute a canonical signature for an object-centric execution.
    
    events: list of dicts, each with 'activity' (str) and 
            'object_ids' (dict: str -> list of str, keys are object type names).
    notes: string containing O2O qualifier keywords from the execution's O2O notes.
    
    returns: tuple (seq, type_part_fs, external_fs, qualifiers_fs, act_counts_fs)
    """
    # 1. Activity label sequence in timestamp order (already sorted)
    seq = tuple(evt['activity'] for evt in events)
    
    # 2. Object type participation: total number of object IDs mentioned
    #    per (activity, object_type) across all events. This captures
    #    multiplicities renaming-invariantly.
    type_part = Counter()  # (activity, obj_type) -> int
    for evt in events:
        label = evt['activity']
        for obj_type, ids in evt['object_ids'].items():
            type_part[(label, obj_type)] += len(ids)
    type_part_fs = frozenset(type_part.items())
    
    # 3. External object types: any object ID starting with 'EXT'
    external_types = set()
    for evt in events:
        for obj_type, ids in evt['object_ids'].items():
            if any(obj_id.startswith('EXT') for obj_id in ids):
                external_types.add(obj_type)
    external_fs = frozenset(external_types)
    
    # 4. O2O qualifiers: extract known keywords from notes
    known_qualifiers = [
        'removed_before_dispatch',
        'partial_settlement',
        'completes_settlement',
        'replaces',
        'cross_order',
        'shared'
    ]
    found_qualifiers = set()
    notes_lower = notes.lower()
    for q in known_qualifiers:
        if q in notes_lower:
            found_qualifiers.add(q)
    qualifiers_fs = frozenset(found_qualifiers)
    
    # 5. Repeated activity counts (derivable from seq, included explicitly)
    act_counts = Counter(seq)
    act_counts_fs = frozenset(act_counts.items())
    
    # 6. Build signature tuple
    # seq preserves order; the frozensets make the hashable parts renaming-invariant.
    signature = (
        seq,
        type_part_fs,
        external_fs,
        qualifiers_fs,
        act_counts_fs
    )
    return signature
```

The signature tuple components are:
- `seq`: activity label sequence (total order preserved).
- `type_part_fs`: renaminginvariant participation counts per (activity, object type).
- `external_fs`: set of object types that have at least one EXTprefixed instance.
- `qualifiers_fs`: set of O2O qualifier keywords detected in the execution’s notes.
- `act_counts_fs`: frequency of each activity label across the execution.

This scheme makes every execution comparable without depending on local IDs, while surfacelevel business features (external sharing, replacement, return) are explicitly encoded.

**Business behavior:** Logistics follow the X1 pattern (single package, single delivery), but the invoice V61 and payment M61 bill both the lead order O6 **and** an external party EXTOB. Settlement occurs without orderlevel allocation, indicating shared cost/revenue.  
**Operational risks/opportunities:** Risks: cost allocation disputes, revenuerecognition timing issues, and compliance challenges if the external party’s contribution is not documented. Opportunities: sharedservice billing, consortiumlevel reporting.  
**Traditional flattening poor representation:** Flattening would show a single Invoice/Payment line, erasing the sharedparty semantics and potentially misallocating financial responsibility.  
**Stability:** Similar to BS4; the cluster holds when external flags are preserved. Ignoring external objects (Section 7 perturbation) collapses X6 into BS1, underscoring the clause’s fragility without the externality dimension.

### BS6 – Item replacement before dispatch (X7)
**Signature:** Seq:CO,AII,P,D,Inv,Pay; Part:Pk:1,It:2,Dsp:1,Item:1(in Dsp),Inv:1,Pay:1; Ext:no; Qual=removed_before_dispatch.  
**Business behavior:** Items I71 and I72 are added; Pack P71 contains both, but a `removed_before_dispatch` qualifier links P71 to I71, implying substitution or removal. Dispatch explicitly references Item I72, and the process proceeds with the replacement item. Models product substitution, warranty swap, or defectdriven replacement.  
**Operational risks/opportunities:** Risks: inventory mismatch, customer dissatisfaction if replacement is uncommunicated, and regulatory compliance if the removed item is safetycritical. Opportunities: flexible product Offerings, efficient defect handling.  
**Traditional flattening poor representation:** Flattening would show a single Dispatch with one Item, erasing the substitution mechanism and the qualified relation that explains *why* one item is absent.  
**Stability:** Stable under ID renaming, but sensitive to qualifier retention. If O2O qualifiers are stripped (Section 7 perturbation), X7’s typeparticipation signature approaches X1’s, risking misclustering under a coarse equivalence.

### BS7 – Return and repack (X8)
**Signature:** Seq:CO,AII,P,D,Rtn,InsPck,Dsp2,Inv,Pay; Part:Pk:2,It:2,Dsp:2,Rtn:1,Ins:1,Inv:1,Pay:1; Ext:no; Qual=replaces.  
**Business behavior:** After initial dispatch (P81, D81), item I82 is returned via the same delivery, inspected, repacked into P82, and redispatched via D82. The replacement package P82 replaces P81 for I82. Encodes reverselogistics flow: return, quality check, repack, and redelivery.  
**Operational risks/opportunities:** Risks: returnprocessing delays, repack quality erosion, and increased cycle time. Opportunities: warranty/claim resolution, recycling, and secondarymarket redistribution.  
**Traditional flattening poor representation:** A caseflattened log would collapse the return loop into a single forwarddispatch event, completely losing the reverselogistics motif and the repack/redispatch sequence.  
**Stability:** Stable under ID renaming; however, if the Return/Inspect events are collapsed or relabeled as “Dispatch,” the signature would merge with BS3 or BS1, losing the reverselogistics semantics.

- **TS-eq verdict:** Equivalent (isomorphic after renaming I11I21, I12I22; the opposite additem order does not affect typeparticipation counts).  
- **BS-eq verdict:** Equivalent (identical canonical signature).  
- **Defensible disagreement:** If one adopts “exact structural equivalence” that preserves object identifiers, X1 and X2 would be distinct. The tension lies between IDsensitive exact equivalence (too fine for most objectcentric purposes) and the renamingtolerant notions defined here. Under our definitions, they agree, but the border is whether identifier renaming is viewed as a transformation (preserving meaning) or a distinction (preserving exact provenance).

BSeq preserves the externality dimension, correctly identifying a different operational variant. A defender of ASeq might argue that for highlevel activity compliance monitoring, the flow is identical; a defender of BSeq would counter that the financial/logistics topology changes risk profiles and thus the cluster. ## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py function `pm4py.cluster_equivalent_ocel` groups OCEL cases based on a key structure that typically hashencodes activity labels, object types, and **raw object identifiers**. This has immediate implications for the clusterings above.

- **What the PM4Py key preserves:** For each case (here, each Order execution), the key is a function of the multiset of activity labels, the set of object types involved, and the exact string values of object IDs. If two executions have the same activity sequence and same object-type participation but different ID strings (e.g., `O1` vs `O2`), PM4Py assigns different keys, placing them in separate clusters even though the structural pattern is identical.

- **Why raw object identifiers make exact clusters too fine:** In our executions, X1 and X2 differ only in identifier names (O1O2, I11I22/I21). A rawID PM4Py clustering would separate them, producing 8 singleton clusters rather than the meaningful partitions we defined. This defeats the purpose of objectcentric clustering, which should abstract away local identifiers to reveal process variants.

- **Canonicalization/postprocessing:** To obtain coarser, businessrelevant clusters from PM4Py output, one would:
  1. Run `pm4py.cluster_equivalent_ocel(ocel, parameters={"activity_key":"concept:name", "id_key":"..."})`.
  2. For each returned cluster, extract the events and run a custom canonicalization step (e.g., the `compute_canonical_signature` function from Section 2), normalizing object IDs by stripping `EXT` prefixes, mapping nonEXT IDs to their type+occurrence index, and collapsing the signature tuple.
  3. Merge PM4Py clusters that yield identical canonical signatures, thereby discarding identifier noise while preserving typeparticipation, externalflag, and qualifier information.
  This postprocessing step effectively upgrades PM4Py’s finegrained exact equivalence to a coarser, semanticsaware clustering.

- **When exact equivalence is preferable to coarser business clustering:** Exact equivalence (PM4Py’s rawID clusters) is preferable when provenance tracking is critical—e.g., auditing a specific order’s lifecycle, legal compliance requiring exact eventID traces, or debugging where a single identifier discrepancy signals a dataquality issue. In descriptive reporting or operational segmentation, however, coarser business clustering (as defined here) is more informative because it groups executions by operational pattern rather than cosmetic ID differences.

- **Effect of `max_objs` or large connected executions:** PM4Py’s `max_objs` parameter limits the number of distinct objects considered in the key; setting it low can artificially merge executions that differ in object count, producing overly coarse clusters. For large connected executions (many Orders sharing external objects), the connected component size can blow up the key space, making rawID clusters sparse. Canonicalization that aggregates object types and EXT flags (as in our signature) mitigates this by focusing on structural patterns rather than cardinality of distinct IDs. In practice, for executions with dozens of Orders, one would first partition by leadobject type (`Order`), then apply the canonical signature within each partition, ensuring that the clustering remains tractable and semantically meaningful.

## 7. Robustness analysis

How do cluster assignments change under the following perturbations? Each analysis assumes the same canonical signature framework, with the indicated modification.

### 7.1 Ignore all O2O qualifiers
- **Effect:** `qualifiers_fs` becomes empty for all executions. X7’s `removed_before_dispatch` and X8’s `replaces` are lost.  
- **Cluster shifts:** X7 moves closer to X1/X2 in TSeq (its typeparticipation signature now approaches X1’s, as the DispatchItem participation still differs but qualifiers are gone). In BSeq, X7 may merge with BS1 or BS6 depending on whether the `(Dispatch,Item):1` count alone is enough to keep it distinct; likely X7 joins BS6 (item replacement) if the count is retained, or BS1 if typeparticipation is also smoothed. X8 loses `replaces`, potentially merging with BS3 or BS1 if external flags are also ignored.  
- **Overall:** Qualifieragnostic equivalence collapses the replacement and returnrepack motifs, reducing the number of BS clusters from 7 to roughly 5 (BS1, BS2, BS3, a merged BS4/BS5, and a collapsed BS6/BS7).

### 7.2 Ignore external objects
- **Effect:** `external_fs` set to `` for all executions; `type_participations` lose all `(·,External)` entries.  
- **Cluster shifts:** X5 and X6 lose their external flags. Their `type_part_fs` becomes identical to X1’s (same Pack/Dispatch/Invoice counts). In TSeq, X5 and X6 merge with TS1 (X1X2). In BSeq, X5 and X6 merge with BS1 (standard order), eliminating BS4 and BS5. The total number of BS clusters drops to 5 (BS1–BS3, BS6, BS7).  
- **Overall:** Externalobject ignorance flattens crossorder sharing executions into the baseline, demonstrating that BS4 and BS5 are entirely contingent on the externality dimension.

### 7.3 Collapse repeated samelabel events
- **Effect:** Activities appearing multiple times are merged into a single occurrence (e.g., X4’s two RecordPayment events become one; X8’s two Pack/Dispatch events become one each).  
- **Cluster shifts:** X4’s signature changes from `(Pay:2)` to `(Pay:1)`, making its typeparticipation closer to X3’s; X4 may shift from BS3 toward BS2 (split packages, consolidated delivery) if the payment split is the only differentiator. X8’s two Pack and two Dispatch events collapse to one each, reducing its event count; X8 may merge with BS3 or BS1, losing the reverselogistics distinctiveness.  
- **Overall:** Collapsing repeats tends to merge clusters that differ only in multiplicity of the same activity, highlighting that multiplicity is a meaningful differentiator in BSeq. The number of ASeq clusters is unaffected (labels remain, just counts change), but TSeq and BSeq lose granularity.

### 7.4 Treat Pack and Dispatch event order as a partial order
- **Effect:** The totalorder constraint in ASeq and TSeq is relaxed; two executions are equivalent if their event structures are isomorphic under some topological sort that respects causality.  
- **Cluster shifts:** X3 and X4, which differ only in the interleaving of Pack and Dispatch, could become TSequivalent or BSequivalent under a partialorder view, as both realize the same incidence graph (two packages, two items, one order, each package linked to one item and one dispatch). X3’s “two Packs before Dispatch” and X4’s “Pack, Dispatch, Pack, Dispatch” would be seen as different linearizations of the same partial order. X1/X2, X5/X6, X7, X8 are largely unaffected because their causal structures are total or have unique orderings.  
- **Overall:** Partialorder equivalence expands the TSeq and BSeq clusters, potentially reducing the total number of TS clusters from 7 to 5 (TS1: X1,X2,X3,X4; TS2: X5; TS3: X6; TS4: X7; TS5: X8) and similarly for BS. This shows that eventorder perception is a key differentiator.

### 7.5 Treat payment multiplicity as an amount attribute (optional)
- **Effect:** Instead of counting RecordPayment events, the signature includes a numeric `amount` field summed per invoice. X4 has two payments M41, M42 that may total the invoice amount; X8 has a single payment M81.  
- **Cluster shifts:** If amounts are preserved, X4’s BS signature now contains `Pay:2; amount:total`, while X8 has `Pay:1; amount:single`. The clusters BS3 (split payment) and BS7 (return/repack) remain distinct because the event sequences differ. However, if amounts are **ignored** (only count matters), X4 and X8 could potentially be compared on payment count alone, but the activity sequences still differ (Return/Inspect vs. Pay split).  
- **Overall:** Introducing amounts adds a quantitative dimension that can refine BSeq segmentation (e.g., distinguishing “partial payment of 50%” from “full payment”), but it does not fundamentally alter the activitybased cluster boundaries defined by event labels and types.

## 8. Limitations and recommendation

### Recommendation by purpose

| Purpose | Recommended equivalence level | Why |
|---------|------------------------------|-----|
| **Compliance monitoring** | **Activitysequence equivalence (ASeq)** | ASeq is robust to identifier renaming and focuses on whether the required activity flow (create  add  pack  dispatch  invoice  pay) was executed. It tolerates minor structural variations (item order, ID changes) while flagging missing or extra events, which is essential for audit trails and SLA checks. |
| **Operational segmentation** | **Businesssemantic equivalence (BSeq)** | BSeq captures the intentional business variants (split delivery, crossorder sharing, replacement, return) that drive different operational pathways, staffing, and KPIs. It segments the log into meaningful process families (e.g., “standard fulfilment” vs. “reverse logistics”) enabling targeted performance analysis. |
| **Rootcause analysis** | **Typed structural equivalence (TSeq)** | TSeq preserves the exact typed eventobject incidence and qualifier relations, making it ideal for pinpointing where a deviation occurred (e.g., a missing `removed_before_dispatch` qualifier, an unexpected external object in a package, a splitdelivery pattern). The structural detail helps trace the precise mechanism of a process failure. |
| **Descriptive reporting** | **Businesssemantic equivalence (BSeq)** | For highlevel reporting (dashboards, executive summaries), BSeq provides a concise taxonomy of process variants that is intuitive to business stakeholders (“we have three kinds of orders: standard, splitdelivery, and returndriven”). It balances granularity and readability, unlike the toofine TSeq or the toocoarse ASeq. |

### Why no single equivalence notion is best for all four purposes

- **ASeq** is too coarse: it discards all objectlevel and qualifier information, so it cannot distinguish operational variants that share the same activity labels but differ in logistics (e.g., X3 vs X1, or X5 vs X1). It would incorrectly group fundamentally different business processes under one “compliant” label, misleading segmentation and rootcause work.
- **TSeq** is too fine: it is sensitive to local identifier naming and exact eventorder prescriptions. Small dataquality differences (a renamed ID, a timestamp swap) can fracture clusters that should belong together, inflating the number of segments and obscuring macrolevel patterns. For compliance monitoring, this granularity is often unnecessary and increases manual overhead.
- **BSeq** sits in the middle but depends on the canonical signature design. Its partitions are meaningful for segmentation and reporting, yet the signature must be carefully defined to include the right dimensions (external flags, qualifiers, multiplicity). If the signature omits a relevant feature (e.g., treating EXT flags as irrelevant), BSeq collapses into ASeq; if it overfits, it becomes indistinguishable from TSeq. The “best” equivalence is thus contextdependent and signaturedependent.

**Bottom line:** A layered approach is advisable—use ASeq for quick compliance checks, TSeq for forensic rootcause digging, and BSeq for operational segmentation and reporting. The clusterings presented here demonstrate that meaningful partitions emerge only when the equivalence notion is aligned with the analytical goal, and that “objectcentric” must involve more than just activity labels; it requires disciplined treatment of types, multiplicities, external objects, and qualifiers.
