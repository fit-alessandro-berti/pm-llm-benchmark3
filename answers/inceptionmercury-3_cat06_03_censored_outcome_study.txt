## 1. Target definition

The primary prediction target is a **multi-state / competing-outcome target**, not a single binary label applied to every application. I define the event of interest as:

> The application is eventually **activated** and then experiences a **default within 90 days after activation**, before any other terminal disposition.

More formally, let \(X_i(\tau_i)\) be the information available at the prediction time \(\tau_i\), where \(\tau_i\) is defined from the first few events of application \(i\). Let:

- \(A_i\) = time from application start to Account Activated;
- \(D_i\) = time from Account Activated to default;
- \(C_i\) = time to the earliest competing terminal event before activation: Rejected, Withdrawn, or Transferred.

The primary estimand is:

\[
F_1(90 \mid x) = P\big(A_i < \infty,\; D_i \le 90,\; C_i > A_i \mid X_i(\tau_i)=x\big)
\]

This is a **cause-specific cumulative incidence of activation followed by 90-day default**. Rejected, withdrawn, transferred, and still-open applications are not labeled as “non-default.” Instead, they contribute to the multi-state likelihood as competing terminal states or as right-censored observations.

**Prediction time.** For the primary early-warning model, the prefix is truncated before the first decision/activation event: Accepted, Rejected, Withdrawn, Transferred, Contract Signed, or Account Activated. The prediction time is the time of the last event in that pre-decision prefix.

**Horizon.** 90 days after Account Activated.

**Unit of analysis.** One credit application.

**Population.** All 48,000 applications started between 1 January 2024 and 31 December 2025, as recorded in the event log.

**Alternative target.** A simpler but different estimand is:

\[
P(D_i \le 90 \mid A_i < \infty,\; X_i(\tau_i))
\]

That is the **default probability among accounts that are eventually activated**. It is useful after approval, but it conditions on a future event and is not a default probability for every application. A counterfactual target such as “default if every application had been activated” would require strong policy assumptions and is not identified from these observational data.

## 2. Cohort construction

The primary cohort is the **full event log**, not the exported 21,600 labeled rows. The exported labeled set is only one source of outcome information.

**Inclusion rules**
- Any application with a valid `Application Started` event between 1 January 2024 and 31 December 2025.
- No case is excluded solely because it was rejected, withdrawn, transferred, open, or not yet mature.

**Exclusion rules**
- Cases with invalid case IDs, missing start timestamps, or corrupted event ordering are excluded after data-quality review.
- Exact duplicate events introduced by the 15 October 2025 migration are removed before analysis.

**As-of rules**
- All data are as of the extraction date 15 February 2026.
- A default label is considered available only when `default_90d` is non-missing.
- Activated accounts with no available label by the extraction date are treated as censored or permanently missing, not as non-default.

### Cohort flow table

| Cohort stratum | Count | Role in primary analysis |
|---|---:|---|
| Total applications started | 48,000 | Study population |
| Activated, default by 90 days | 2,700 | Event of interest |
| Activated, no default by 90 days | 18,900 | Absorbing non-default state after 90 days |
| Activated, outcome not yet mature / feed missing | 3,600 | Right-censored or missing label |
| Rejected | 9,100 | Competing terminal event before activation |
| Withdrawn | 5,700 | Competing terminal event before activation |
| Transferred | 2,900 | Competing terminal event for the original process; linkage available for 60% |
| Still open at extraction | 5,100 | Right-censored |

The 21,600 exported labels correspond to the first two rows: 18,900 non-default plus 2,700 default. The other groups are not ignored and are not coded as non-default.

## 3. Censoring and missing-label strategy

I distinguish several mechanisms that must not be conflated.

### Mechanisms

- **Ordinary right censoring**: the event has not yet occurred by the extraction date. This applies to still-open applications and to activated accounts that are fewer than 90 days past activation at extraction.
- **Delayed labels**: the external outcome feed arrives 7–35 days after the 90-day horizon. A case may be activated and even past 90 days, but its label is not yet available at extraction. These cases are censored until `label_available_at`.
- **Selection through activation**: default is observable only after activation. Rejected, withdrawn, and transferred applications are not exposed to credit, so their default outcome is undefined under the observed policy.
- **Transfer as a competing event or missing follow-up**: transfer closes the original application process. For the primary analysis, transfer is a competing terminal event. In sensitivity analysis, linked partner-platform outcomes are used for the 60% of transfers with a linkage.
- **Permanently missing outcome feeds**: some activated accounts, especially partner-originated ones, may never receive an outcome label. This is a potentially informative missingness mechanism.

### Primary analysis strategy

Use a **multi-state survival framework** with cause-specific hazards.

1. Fit a pre-activation model for transitions into Account Activated versus Rejected, Withdrawn, and Transferred.
2. Fit a post-activation model for default within 90 days after activation, with 90-day non-default as an absorbing competing state.
3. Combine the hazards to estimate the primary cumulative incidence \(F_1(90 \mid x)\).

All cases, including censored and competing-event cases, contribute to the likelihood. The analysis is thus not limited to the 21,600 complete labels.

### Sensitivity analyses

1. **Activation-gated complete-case analysis**: train only on the 21,600 mature activated accounts and estimate \(P(\text{default} \mid \text{activated})\). This is a conditional target and is used only as a comparison.
2. **Transfer treatment**: treat transfer as censored instead of competing, or use linked downstream outcomes with inverse probability of linkage weights.
3. **Permanent missing outcomes**: perform tipping-point analyses in which the missing defaults are varied from 0% to 100%, stratified by `source_system`.
4. **Policy/migration stability**: fit on pre-policy data and evaluate on post-policy and post-migration data.

### Testability

- **Partially testable**: whether missing labels are predicted by observed features; whether linked transfers differ from unlinked transfers; whether delayed labels arrive within the expected 7–35-day delay.
- **Fundamentally untestable**: the counterfactual default outcome of rejected, withdrawn, or transferred applications under a hypothetical activation policy.

## 4. Prefix extraction

The prefix must be constructed without looking into the future.

### Fixed event-count prefixes

For a fixed length \(K\), default \(K=5\):

1. Sort events by case, timestamp, and original row order.
2. Truncate before the first decision/activation event: Accepted, Rejected, Withdrawn, Transferred, Contract Signed, or Account Activated.
3. Take the first \(K\) events from the remaining pre-decision event sequence.
4. The prediction time is the timestamp of the last event in that prefix.
5. If a case has fewer than \(K\) pre-decision events, use all available pre-decision events.

This prevents the Reject/Accept/Activation event itself from being used as a predictor.

### Elapsed-time prefixes

For an elapsed-time prefix of \(d\) days, default \(d=7\):

1. Use only events with `time:timestamp < start_time + d days`.
2. Apply the same pre-decision truncation rule.
3. The prediction time is `start_time + d days`.

### Short cases

Short cases are retained. They are not padded with synthetic events. The number of events in the prefix is itself a useful feature.

### Repeated document loops

Loops are not collapsed. Repeated `Request Documents` / `Credit Review` alternations are kept as events and later summarized as rework counts and durations.

### Activity renaming and duplicates

After 15 October 2025, activities are mapped to canonical names, e.g. `Credit Review v2`  `Credit Review`, `Request Docs`  `Request Documents`. Exact duplicate events are removed using case ID, activity, timestamp, and resource.

## 5. Process-aware features

All features are computed from the truncated pre-decision prefix.

### Static case attributes

- `case:channel`
- `case:region`
- `case:requested_amount`
- `source_system`
- Application start hour, weekday, month, and policy/migration epoch

### Prefix-derived features

- Number of events in the prefix
- Counts of each canonical activity
- Presence/absence indicators for key activities
- Number of Credit Review  Request Documents loops
- Number of returns to Credit Review
- Total requested documents
- Number of distinct resources
- Total elapsed time from application start to prediction time
- Average and standard deviation of inter-event times
- Time since the most recent event
- Directly-follows edge counts obtained from the prefix log
- Top process variants encoded from the prefix

### Cohort/calendar features

- Whether the case started before or after 1 July 2025 policy change
- Whether the case started before or after 15 October 2025 migration
- Calendar month and day-of-week effects

### Features requiring historical reference data

- Resource experience at the event time, if an HR snapshot is available
- Rolling historical default/activation rates by channel, region, amount band, or risk score, computed from the training period only

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated after the final credit decision; encodes decision/selection | Only if the decision event occurs before the prediction time; otherwise missing | Drop for early-warning prediction; conditional keep for post-decision models | It is not known from the first few pre-decision events |
| `decision_reason` | Populated at or after Accept/Reject; can reveal terminal state | Only if event timestamp is before prediction time | Drop for early-warning prediction | It leaks the decision outcome |
| `collection_status` | Updated after activation; directly reveals default/collections | Never available before activation | Drop | This is an outcome-related field, not a predictor at the prefix time |
| Future events: Contract Signed, Account Activated, Collections Contact, Default Recorded | Post-prefix events define the outcome or selection | Exclude all events after the prefix cutoff | Drop from features; use for label construction only | Otherwise the model sees the future |
| `documents_total` | Nightly snapshot can include documents uploaded later on the same calendar day | Use document upload timestamps before prediction; otherwise use previous-day lag | Repair with lag or drop | Same-day snapshot creates lookahead |
| Updated `risk_score` | The warehouse may store the latest value rather than the as-of value | Use the last risk score at an event before the prediction time | Repair: construct `risk_score_asof` | Prevents post-prefix updates from entering features |
| Resource experience | Stored at extraction time, not event time | Requires an event-time HR snapshot | Drop unless event-time snapshot is available | Future experience is not available at the time of the event |
| `label_available_at` / `default_90d` | Outcome labels; using them as features is fatal leakage | Never as predictors | Keep only as target/censoring columns | They define the outcome |
| `data_extract_time` | Constant metadata; no predictive value | Never a feature | Drop | Not informative |

## 7. Validation design

A random case split would be misleading because:

- Applications started at different times are subject to different policies and system behavior.
- Label maturity is correlated with start time; random splits can leak outcome information.
- The July 2025 policy change and October 2025 migration create time-dependent distribution shifts.

### Primary temporal split

- **Train**: applications started before 1 July 2025.
- **Validation**: applications started from 1 July 2025 through 14 October 2025.
- **Test**: applications started on or after 15 October 2025.

This places the policy change between training and validation, and the migration at the start of the test period. The test set is evaluated with censoring-aware metrics because not all test outcomes will be mature by 15 February 2026.

### Rolling-origin backtest

In addition, I recommend a rolling-origin backtest with quarterly origins: train on all earlier starts, validate on the next quarter, and test on the following quarter. This gives multiple evaluations across policy and migration boundaries.

### Metrics

For the primary multi-state target:

- Time-dependent AUC with inverse probability of censoring weights.
- Brier score with IPCW at 90 days after activation.
- Calibration plots of predicted cumulative incidence versus Aalen–Johansen estimates.
- Calibration slope and intercept.
- Subgroup performance by channel, region, amount band, policy epoch, migration epoch, and `source_system`.

For the activation-gated alternative:

- ROC AUC and precision-recall AUC.
- Brier score.
- Calibration curves.

The primary validation implementation remains temporal. `pm4py.split_train_test` may be used as a convenience baseline, but it is not the main evaluation design.

## 8. Limitations and decision-use boundary

### What the study can claim

- The model estimates the probability of the observed process outcome: activation followed by default within 90 days, under the historical policy and data-generating process.
- The model can rank applications by composite early-warning risk.
- The model explicitly accounts for competing dispositions and censoring.

### What the study cannot claim

- It does not estimate a causal effect of the model or of credit policy.
- It does not estimate counterfactual default risk for rejected, withdrawn, transferred, or open applications.
- It does not claim that missing outcome feeds are missing at random.
- It does not claim that the activation-gated default model can be used to change activation policy without recalibration.

### Deployment changes that could alter the data-generating process

1. If the model is used to reject or reroute applications, the composition of activated accounts changes, and the activation-gated part of the model becomes miscalibrated.
2. Credit policy threshold changes can alter approval rates, activation timing, and the relationship between prefix features and default.
3. System or activity-name changes alter the event log representation; without remapping or retraining, the features degrade.
4. Applicants and staff may respond strategically to being flagged, changing event durations, withdrawals, and transfers.
5. Partner transfer linkage coverage and outcome-feed completeness may change over time, affecting censoring and missing-data patterns.

## 9. PM4Py-oriented Python implementation skeleton

```python
# -*- coding: utf-8 -*-
"""PM4Py-oriented implementation skeleton for the multi-state early-warning study."""
import pandas as pd
import numpy as np
import pm4py

CSV_PATH = "applications_events.csv"
EXTRACT_DATE = pd.Timestamp("2026-02-15")
POLICY_CHANGE_DATE = pd.Timestamp("2025-07-01")
MIGRATION_DATE = pd.Timestamp("2025-10-15")
PREFIX_LENGTH = 5

events = pd.read_csv(CSV_PATH, parse_dates=["time:timestamp","label_available_at","data_extract_time"])
events = pm4py.format_dataframe(events, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")
events["concept:name"] = events["concept:name"].replace({"Credit Review v2":"Credit Review","Request Docs":"Request Documents"})
events = events.drop_duplicates(subset=["case:concept:name","concept:name","time:timestamp","org:resource"])
events = events.sort_values(["case:concept:name","time:timestamp","org:resource"])

def build_case_table(events, extract_date):
    starts = events[events["concept:name"]=="Application Started"].groupby("case:concept:name")["time:timestamp"].min()
    activations = events[events["concept:name"]=="Account Activated"].groupby("case:concept:name")["time:timestamp"].min()
    cases = pd.DataFrame(index=starts.index)
    cases["start_time"] = starts
    cases["activation_time"] = activations
    cases["terminal"] = ""
    for act, st in {"Rejected":"Rejected","Withdrawn":"Withdrawn","Transferred":"Transferred"}.items():
        hit = events[events["concept:name"]==act].groupby("case:concept:name")["time:timestamp"].idxmin()
        cases.loc[hit.index, "terminal"] = st
    cases["default"] = events[events["default_90d"].notna()].groupby("case:concept:name")["default_90d"].max()
    cases["label_available_at"] = events[events["label_available_at"].notna()].groupby("case:concept:name")["label_available_at"].max()

    def outcome(r):
        if r["default"] == 1:
            return "Default"
        if r["default"] == 0:
            return "NonDefaultActivated"
        if r["terminal"] != "":
            return r["terminal"]
        return "Censored"

    cases["outcome"] = cases.apply(outcome, axis=1)
    cases["is_activated"] = cases["activation_time"].notna()
    cases["permanent_missing"] = (
        cases["is_activated"]
        & cases["default"].isna()
        & cases["label_available_at"].notna()
        & (cases["label_available_at"] <= extract_date)
    )
    return cases

cases = build_case_table(events, EXTRACT_DATE)
print(cases["outcome"].value_counts())

cases["split"] = "train"
cases.loc[(cases["start_time"] >= POLICY_CHANGE_DATE) & (cases["start_time"] < MIGRATION_DATE), "split"] = "validation"
cases.loc[cases["start_time"] >= MIGRATION_DATE, "split"] = "test"

# Pre-decision prefix cutoff.
decision_activities = ["Accepted","Rejected","Withdrawn","Transferred","Contract Signed","Account Activated"]
decision_times = events[events["concept:name"].isin(decision_activities)].groupby("case:concept:name")["time:timestamp"].min()
events["decision_time"] = events["case:concept:name"].map(decision_times)
pre_decision_events = events[events["decision_time"].isna() | (events["time:timestamp"] < events["decision_time"])]

event_log = pm4py.convert_to_event_log(pm4py.format_dataframe(events, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp"))
try:
    pm4py.get_prefixes_from_log(event_log, length=PREFIX_LENGTH)
except Exception:
    pass

prefix_events = pre_decision_events.groupby("case:concept:name").head(PREFIX_LENGTH)
leaky_cols = [
    "default_90d","label_available_at","collection_status","final_limit",
    "decision_reason","data_extract_time","documents_total","decision_time",
]
prefix_events = prefix_events.drop(columns=leaky_cols, errors="ignore")

static_attrs = events.groupby("case:concept:name").agg(
    channel=("case:channel", "first"),
    region=("case:region", "first"),
    requested_amount=("case:requested_amount", "first"),
    source_system=("source_system", "first"),
)
cases = cases.join(static_attrs)

def build_prefix_features(prefix_events, cases):
    rows = []
    for case, g in prefix_events.groupby("case:concept:name"):
        g = g.sort_values("time:timestamp")
        n = len(g)
        last_time = g["time:timestamp"].iloc[-1] if n else cases.loc[case, "start_time"]
        risk = g["risk_score"].dropna()
        rows.append({
            "case:concept:name": case,
            "n_events": n,
            "n_credit_review": int((g["concept:name"] == "Credit Review").sum()),
            "n_docs_requested": int((g["concept:name"] == "Request Documents").sum()),
            "n_kyc": int((g["concept:name"] == "Identity/KYC Check").sum()),
            "n_distinct_resources": int(g["org:resource"].nunique()),
            "total_duration_s": (last_time - cases.loc[case, "start_time"]).total_seconds(),
            "avg_interevent_s": g["time:timestamp"].diff().mean().total_seconds() if n > 1 else 0.0,
            "risk_score_asof": float(risk.iloc[-1]) if len(risk) else np.nan,
            "channel": cases.loc[case, "channel"],
            "region": cases.loc[case, "region"],
            "requested_amount": cases.loc[case, "requested_amount"],
            "source_system": cases.loc[case, "source_system"],
            "policy_epoch": int(cases.loc[case, "start_time"] >= POLICY_CHANGE_DATE),
            "migration_epoch": int(cases.loc[case, "start_time"] >= MIGRATION_DATE),
        })
    return pd.DataFrame(rows).set_index("case:concept:name")

features = build_prefix_features(prefix_events, cases)
for col in ["default_90d","collection_status","final_limit","decision_reason","documents_total"]:
    assert col not in features.columns, f"Leakage: {col}"

X, y = features, cases["outcome"]
train_idx = cases.index[cases["split"] == "train"]
val_idx = cases.index[cases["split"] == "validation"]
test_idx = cases.index[cases["split"] == "test"]
X_train, y_train = X.loc[train_idx], y.loc[train_idx]
X_val, y_val = X.loc[val_idx], y.loc[val_idx]
X_test, y_test = X.loc[test_idx], y.loc[test_idx]

print(cases.groupby(["split","outcome"]).size().unstack(fill_value=0))

for split in ["train","validation","test"]:
    ids = cases.index[cases["split"] == split]
    split_events = prefix_events[prefix_events["case:concept:name"].isin(ids)]
    if split_events.empty:
        continue
    split_log = pm4py.convert_to_event_log(
        pm4py.format_dataframe(split_events, case_id="case:concept:name",
                               activity_key="concept:name", timestamp_key="time:timestamp")
    )
    dfg = pm4py.discover_dfg(split_log)
    variants = pm4py.get_variants(split_log)
    print(split, "DFG nodes:", len(dfg[0]), "variants:", len(variants))

# Next stage: create a person-period table from cases and the original event log.
# For each day from the prediction time until activation/competing event, then
# for up to 90 days after activation, emit one row. Fit a discrete-time
# cause-specific hazard model for default. Combine hazard estimates to compute
# the cumulative incidence function for the primary estimand.
```
