## 1. Temporal Data Semantics  
• Case timeline = list of events ordered by `(time:timestamp, event_index)`.  
• A row shows only the attributes that change; a blank cell means “keep last known value”.  
• Forward-fill attribute values within a case (never copy a later value backwards).  
• The “current state” of any obligation is the latest known value *strictly before or at* the
  evaluation instant.  
• Four different times are tracked per fact  
  – event_time  = when the business action happened (log timestamp)  
  – record_time = when the row was written (not available here)  
  – effective_time = explicit “effective_from” field on an exemption, or as established by evidence  
  – evidence_time = signing / hash / certificate time that proves existence of a fact  
• “Material data change” =  
  - amount  >20 % (R4)orrisk_level, jurisdiction, customer_type change  
• Same-timestamp tie-break = lower event_index happens first (R7).  
• Final case attributes are *not* projected backwards; each obligation is decided with the
  snapshot that exists at its own trigger event.

## 4. Ambiguities and Alternative Readings

TX-302  
• If one insists that the late database insert (11 :00) is the *only* reliable record, EX-77
  would not have been in force at 09 :40, but rule satisfaction does not depend on it.
  Outcome remains COMPLIANT.  

TX-305  
• A signed settlement file (150 k) appears after release, but we cannot prove that the same
  amount applied at 11 :30.  
• If an immutable release payload or front-office ticket showed 150 k, R1 would trigger
  and be satisfied because an ER exists  COMPLIANT.  
• If the real amount were <100 k, R1 would not trigger  COMPLIANT.  

TX-310  
• Accepting the witness statement as strong evidence would make EX-88 valid, turning the
  result into JUSTIFIED_EXCEPTION.  
• A time-stamped qualified signature  10 :00 would also cure the breach.  

TX-311  
• Some policies treat “domestic vs. foreign” as the jurisdiction at *review* time, not
  release time; under that reading R1 would still trigger (US), but ER already covered it,
  so still COMPLIANT.  
• If the order of event_index were mis-recorded, the jurisdiction could be DE during ER,
  removing the foreign aspect earlier as well.

Other general ambiguities  
• Whether a 20 % amount increase is “material” for R1: we followed R4 and treated it as
  non-material; a stricter policy would require a fresh ER and would mark TX-306
  NONCOMPLIANT.

## 5. PM4Py and pandas Checking Code
```python
import io, pandas as pd, pm4py
from datetime import timedelta

csv_data = """case:concept:name,event_index,concept:name,time:timestamp,org:resource,amount,risk_level,jurisdiction,customer_type,exemption_id,note
<PASTE THE WHOLE CSV FROM THE PROMPT HERE>"""

# 1. Read
df = pd.read_csv(io.StringIO(csv_data))
df['time:timestamp'] = pd.to_datetime(df['time:timestamp'], utc=True)

# 2. Order rows
df = df.sort_values(['case:concept:name', 'time:timestamp', 'event_index'])

# 3. Forward-fill attributes inside each case
state_cols = ['amount', 'risk_level', 'jurisdiction', 'customer_type']
df[state_cols] = df.groupby('case:concept:name')[state_cols].ffill()

# 4. Helper views for latest reviews, approvals, etc.
def latest_before(df_case, event_time, col_name):
    occured = df_case[(df_case['concept:name'] == col_name) &
                      (df_case['time:timestamp'] < event_time)]
    return occured['time:timestamp'].max()

records = []

for case, g in df.groupby('case:concept:name'):
    g = g.reset_index(drop=True)
    rf = g[g['concept:name'] == 'Release_Funds']
    if rf.empty:
        continue
    rf_row = rf.iloc[0]      # one release per case here
    snap = rf_row[state_cols].to_dict()
    amount = snap['amount']
    juris  = snap['jurisdiction']
    risk   = snap['risk_level']
    ctype  = snap['customer_type']
    rf_time = rf_row['time:timestamp']

    # find latest reviews
    er_time = latest_before(g, rf_time, 'Enhanced_Review')
    sr_time = latest_before(g, rf_time, 'Standard_Review')
    ca_time = latest_before(g, rf_time, 'Compliance_Approve')

    # material change after ER/SR ?
    mat_after_er = False
    if pd.notna(er_time):
        after_er = g[(g['time:timestamp'] > er_time) &
                     (g['time:timestamp'] < rf_time)]
        if not after_er.empty:
            last_row_before_rf = g[g['time:timestamp'] < rf_time].iloc[-1]
            # simple amount logic
            er_amount = g.loc[g['time:timestamp'] == er_time, 'amount'].iloc[0]
            inc = (amount - er_amount)/er_amount if pd.notna(er_amount) and pd.notna(amount) else None
            if inc and inc > 0.20:
                mat_after_er = True
            # any change in other attributes
            attrs = ['jurisdiction', 'risk_level', 'customer_type']
            er_state = g.loc[g['time:timestamp'] == er_time, attrs].iloc[0].to_dict()
            for a in attrs:
                if er_state[a] != snap[a]:
                    mat_after_er = True

    # --- Coarse rule flags
    trigger_r1 = pd.notna(amount) and amount >= 100000 and juris != 'DE'
    r1_ok = bool(er_time) and not mat_after_er
    trigger_r2 = (risk == 'HIGH') or (ctype == 'PEP')
    r2_ok = bool(er_time) and bool(ca_time) and er_time < ca_time < rf_time

    records.append(dict(case=case, amount=amount, juris=juris,
                        r1_trigger=trigger_r1, r1_ok=r1_ok,
                        r2_trigger=trigger_r2, r2_ok=r2_ok,
                        er_time=er_time, ca_time=ca_time,
                        unknown_amt=pd.isna(amount)))

diag = pd.DataFrame(records)
print(diag)

                             activity_key='concept:name',
                             timestamp_key='time:timestamp')
res = declare_conformance.apply(log, decl)
print("Pure control-flow conformance:", res['fulfillments'][:3], "... (truncated)")

print("\nNOTE: Declare sees TX-309 as conformant because an Enhanced_Review precedes "
      "Release_Funds, but the amount increased by 22 % afterwards – a data condition "
      "the control-flow template cannot detect.")
```

## 6. Why Control-Flow-Only Conformance Is Insufficient  

1. Final-state leakage: replay tools silently use the last snapshot; they would miss that
   USDE jurisdiction change in TX-311 happens *after* the review.  
2. Post-hoc exemptions: TX-302 and TX-310 both reference late database inserts; control-flow
   cannot evaluate evidential timing or signature quality.  
3. Material amount changes: TX-309 passes the “ER before Release” template but violates
   R4 because of a >20 % increase afterwards.  
4. Conditional activation: R1 fires only when amount  100 k *and* foreign jurisdiction.
   Declare or Petri-net models with only activities cannot express those data guards.  
5. Missing data: TX-305 has no amount at release; control-flow would mark it compliant
   despite the uncertainty.  
6. Same-timestamp ordering: TX-311 needs event_index to know ER happened just before the
   DE update. Pure timestamp replay would treat them as unordered and might create a
   false breach.  
7. Evidence quality: Rule R5 demands cryptographic proof of timely approval; this lies
   completely outside the event structure.  
8. Multi-source time semantics: R3 needs to compare list-update time with the last
   screening; again invisible in a plain control-flow model.

## 7. Recommended Logging and Control Improvements  

1. Persist an immutable “release payload” including amount, currency, jurisdiction,
   risk_level, customer_type, and hash it in the transaction record.  
2. Store `event_time`, `record_time`, and, when signed, `signature_time` explicitly on
   every row.  
3. Include `effective_from` and `expires_at` on all updates, not only exemptions.  
4. Emit a “review_version” identifier so a later change can reference exactly which
   review instance it relied on.  
5. Record material-change events automatically when monitored attributes cross policy
   thresholds (e.g., amount 100 k, 20 %).  
6. Carry the rule version that was applied to each decision for future audits.  
7. Require Head_Compliance digital signatures to be captured *before* an exemption can
   be referenced, and link the signature hash in the log row.  
8. Persist `ordering_token` per event to remove ambiguity when multiple updates share
   a timestamp.  
9. Attach provenance (“manual entry”, “system feed”, “oracle API”) to each attribute
   change to help decide evidential reliability.
