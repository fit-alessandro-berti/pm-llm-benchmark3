### 6. Failure modes and displaced bottlenecks
*(Per redesign; at least 2 failure modes + 1 likely bottleneck migration)*

- **Redesign A**:  
  - Failure mode 1: Auto-screen rules updated too strictly, causing >35% manual inflow increase (e.g., many low-risk claims flagged as "evidence incomplete" due to portal prompt misinterpretation), pushing Manual review utilization >82%, creating bottleneck (current peak >82%); complaint rate may not drop if portal abandonment >5% (e.g., low-literacy customers abandon after first portal request).  
  - Failure mode 2: Portal confirmation not consistently reliable (e.g., photo verification error for accessories), leading to occasional Fast approval for incomplete evidence, reverting to Rule R2 violation and complaint; Manual review catches it later but reopen rate may briefly spike.  
  - Displaced bottleneck: Quality inspectors see higher usage from repair path (since gate not added), but underuse decreases; Manual review bottleneck may be mitigated if portal reduces Request evidence loops (reduces Manual inflow from Request evidence), so bottleneck shifts from Manual peak >82% to potentially Quality if repair volume rises, but less likely due to existing underuse. *Mitigation:* Pilot with rule thresholds (e.g., "portal complete" only if 2 evidence items uploaded or tech confirms via 1-min check), monitor manual queue <75% after rule update.

- **Redesign B**:  
  - Failure mode 1: Portal mandatory check causes higher abandonment for low digital literacy (e.g., >8% abandonment in pilot), especially if phone-in option is clunky; this increases Request evidence loops, potentially re-entering Manual bottleneck (e.g., Manual inflow rises if abandonment >5%), counteracting rework reduction.  
  - Failure mode 2: Repair quote path delay if part-price confirmation takes >24h for high-value (common bottleneck), causing cycle time >72h for Standard high-value, violating tolerance; customers perceive slowness despite lower complaints.  
  - Displaced bottleneck: Fraud review bottleneck (Mon/campaign spikes) may decrease because Fast approval for devices is eliminated (no FastFraud flows), reducing Fraud inflow on Mondays; Manual review bottleneck may increase slightly for evidence cases but stay <82% if portal reduces repeats; repair quote delay (part price) remains but is independent of Manual/Fraud. *Mitigation:* Pilot portal with one-click upload + SMS reminder; integrate part-price API check at Repair quote creation to reduce confirmation time; monitor abandonment <5% and part-price confirmation <12h in pilot.

- **Redesign C**:  
  - Failure mode 1: Gate not parallelized effectively (e.g., gate techs busy with other tasks), causing gate decision delay >12h for low-risk Fast candidates, pushing dispatch beyond 24h for Premium low-risk, triggering service-credit exposure (CX failure); high-value device gate not needed (devices go Repair quote), so gate only affects low-risk, but if gate adds >8h for Premium low-risk, CX suffers.  
  - Failure mode 2: Gate rule misclassification (e.g., gate says "request part" for a correct low-risk part due to model confusion), causing unnecessary repair quote loop for low-risk accessories, increasing cycle time and rework chance; Manual review then handles reopen, adding steps.  
  - Displaced bottleneck: Quality inspectors now used for gate (vs underused before), so gate utilization may rise but likely stays <80% if gate handles ~43% of cases; Manual review bottleneck may decrease because FastRequest loops are reduced (gate approves dispatch only if part correct, avoiding FastDispatchComplaint loops); Fraud review bottleneck may decrease slightly (no FastFraud for devices). However, if gate staff are overallocated, gate could become a new bottleneck; but parallel prep (dispatch logistics runs alongside gate check) helps avoid this. *Mitigation:* Pilot gate with max 10h turnaround for low-risk (track actual gate time); use 1 tech for gate + dispatch coordinator to overlap checks; monitor gate time <10h for >80% of low-risk candidates in pilot.

### 7. Recommended experiment sequence
- **Goal**: Validate trade-offs segment-wise with minimal disruption; measure real downstream effects (not just path frequency); avoid shifting complaints downstream.
- **First pilot (Redesign A on Premium high-value only; 200 cases, 2 weeks)**:  
  - Scope: Only Premium high-value devices (14% of total; ~70 cases) and Premium low-risk accessories (18% ~90 cases), but apply Redesign A rules strictly: Auto screen  portal check; if portal "complete" for low-risk  Fast approval pending dispatch (no gate); if portal "incomplete" or high-value  Repair quote; Manual only for evidence/risk; instant credit 24h for complaints; no Escalation board for standard complaints. Portal includes optional SMS upload (1-sentence prompt: "Send photo of damaged part").  
  - Metrics to monitor (track per segment, per path):  
    - Primary: Complaint/reopen rate (target <15% vs current 22% for Premium high-value); Median cycle time (target <48h for Premium high-value, <24h for Premium low-risk); Reopen duration (mean <24h); Rework % for high-value repairs (target <8%); Manual review utilization (max <80%); Portal abandonment rate (<5%).  
    - Secondary: Cost proxy (track number of service credits issued + dispatch rework cases; compare to current for same segment); Customer satisfaction score from post-resolution survey (focus on clarity of status visibility); Manual queue wait time (hours). *Do not use average cycle time alone; use median and p90 to capture tail.*  
    - Compliance check: % of dispatches for high-value devices (should be 0 in pilot since high-value always goes Repair quote); % of low-risk Fast approvals with portal "complete" confirmation (target 100%); Rule R2 violations (should be 0).  
  - Stop/go thresholds (qualitative, based on pilot data only; no extrapolation):  
    - **Stop** if: (a) Complaint rate 20% for Premium high-value; (b) Median cycle time for Premium high-value 60h; (c) Portal abandonment 7% (indicating poor UX for low-literacy); (d) Manual utilization consistently >85% (bottleneck risk). *Reason: Complaints >20% fails CX target; cycle >60h exceeds practical tolerance; abandonment >7% suggests portal issue needs redesign; manual >85% risks bottleneck.*
