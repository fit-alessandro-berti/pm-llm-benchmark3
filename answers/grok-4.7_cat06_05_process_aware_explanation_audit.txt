## 1. Leakage and temporal-consistency findings

Prediction time `t0` is immediately after the first `Coverage Check Completed`. For the three local cases the prefix is only `Claim Registered -> Coverage Check Completed`. A feature is admissible only if its value is fixed by that prefix or by a snapshot whose valid time is at or before `t0`. Importance in the published ranking is not evidence that a feature is an early signal.

## 2. Process-model consistency checks

Run this suite on every training row and on every local explanation before a SHAP value is shown. The normative model is the audit reference. A frequent directly-follows edge is an observation about the log, not a rule.

**Prefix-time availability.** Define `t0` as the timestamp of the first `Coverage Check Completed`, with a stored sequence index as the tie break. For every feature, require `valid_time <= t0` and `knowledge_time <= t0`. Recompute the feature on the prefix alone and on the full trace. Any change means the published column uses suffix information. This test catches `total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id`, `num_document_requests_total`, `final_decision`, and `last_resource_role` immediately. Apply the same test to snapshot joins: queue snapshot time, document-count refresh time, risk-score calculation time, and employee effective time must all be at or before `t0`.

**Activity-order feasibility.** Align each full trace to a model that encodes registration, coverage check, an optional document loop (`Documents Requested -> Documents Received -> Documents Validated`, with a repeat request allowed), damage assessment on both the fast track and the evidence track, optional parallel fraud investigation, one settlement decision, an appeal only after Partial or Deny, a second settlement decision only after that appeal, and closure as the terminal event. Alignment classifies log moves that violate that model. Use it to reject `Claim Closed -> Damage Assessment Completed` as a conformance violation, and to accept `Appeal -> Settlement Decision Recorded` only when the first decision was Partial or Deny. Alignment cost can hide a violation by preferring a cheap model move, so pair it with hard constraints for the successions below. Conformance of the suffix is a data-quality result. It must not be written back into a `t0` feature.

**Same-timestamp ambiguity.** If two events share a timestamp and the ingestion sequence index is null, mark the pair unordered. Do not train a directly-follows indicator on that pair, and do not explain it. Case Z fails this check for `Claim Closed` and `Damage Assessment Completed`. A reliable sequence index can restore order. It cannot make either event admissible at `t0`, because both are still in the future.

**Complete-trace features.** Maintain an allow-list of feature expressions that may read only `hd(trace, t0)` plus dimensional rows with valid time at or before `t0`. Block expressions that scan to closure, use `extraction_date` as the cutoff, take `last_value` over the case, or join a variant table built from whole traces. `final_handler_team` fails even when it often equals the `t0` team, because equality on 65% of rows is not a historical timestamp.

**Enabled, impossible, or future-possible.** Replay the prefix on the model and label every activity cited by an explanation:

- Observed at `t0` for these cases: `Claim Registered`, `Coverage Check Completed`.
- Enabled next: `Documents Requested`, fast-track `Damage Assessment Completed`, and `Fraud Investigation Opened` when a trigger is present. Enabled means the marking allows a firing. It does not mean the firing has happened. The fraud pattern fails here because the explanation treats an unfired edge as observed.
- Future-possible but not enabled: `Documents Received`, `Documents Validated`, `Settlement Decision Recorded`, `Claim Closed`. Receipt requires a request; a decision requires assessment.
- Impossible in this marking: `Appeal`, a second settlement decision, and any activity after `Claim Closed`. Case X’s appeal flag cites an impossible activity.

**Repeated settlement decisions.** Count `Settlement Decision Recorded`. One decision is the ordinary case. Two decisions are legitimate only when an `Appeal` sits between them and the first outcome was Partial or Deny. A second decision without an appeal, or an appeal after Approve or Withdrawn, is non-conforming and must not be explained as a normal variant effect. Case Y’s variant shape can satisfy this rule on the finished trace and still be illegal as a `t0` input, because none of those events has occurred.

**Roles and limits of the other checks.** A prefix footprint or prefix DFG shows which pairs have actually occurred by `t0`; here that set is only registration followed by coverage check. A full-trace DFG is useful to discover the artifactual closure-to-assessment edge and to see parallel interleaving from fraud investigation, which creates spurious direct successions. DFG support does not authorize an edge. Declarative checks are the right home for hard rules: precedence of Partial or Deny before appeal, a second decision only after appeal, and absence of any activity after closure. Declarative rules do not check feature-store clocks. Prefix alignment does not notice a nightly snapshot that was attached from outside the event log.

## 3. Alternative feature interpretations

Four standards apply separately. Predictive validity asks whether a point-in-time feature improves out-of-time discrimination. Causal interpretation asks whether changing the feature would change breach probability; a SHAP value does not answer that. Operational actionability asks whether a handler can know the fact at `t0` and has a permissible lever. Fairness review asks whether the feature, or something it stands for, tracks socioeconomic or other sensitive characteristics and whether use is proportionate. A feature can pass the first standard and fail the other three. Correlated features stay in the audit under those standards; they are not dropped merely because they are correlated, and they are not promoted to causes because they rank highly.

**Defensible predictive signal.** `initial_damage_complexity`, and `initial_reserve` once its opening value is confirmed frozen, describe claim severity already recorded at registration. `claimant_channel` is in the same family if the registration record is immutable, with the proxy limits below. After the SQL repair, `prior_claim_count` can describe earlier claim history. A repaired, time-stamped `risk_score` can be a summary of information that existed at `t0`. What may be claimed is a historical association under the current recording policy. What must be withheld is any statement that editing the complexity code, the reserve, the channel, or the score would change the physical duration of the claim. Prefix control-flow adds nothing at this horizon: X, Y, and Z share one prefix variant.

**Process-state or congestion signal.** `queue_length_at_t0` is the workload visible around coverage completion. `elapsed_since_registration_at_t0` is consumed slack against the 10-day target. A handler-team-at-`t0` field, after history is restored, is assignment context; the closure team is not. What may be claimed is that the case faces a given queue and has a given remainder of the settlement window. Elapsed time has a definitional link to the target, because the clock has already moved. Queue length supports triage and capacity discussion. It becomes a causal claim only under an explicit intervention evaluation. Document-request and same-day document counts become process-state signals only after they are recomputed on the prefix; on conforming prefixes at this `t0` they are zero and cannot explain why one case scores higher than another.

**Proxy requiring fairness or robustness review.** `claimant_region` remains available and may be predictive, and it is a bundle of repair-network coverage, language, channel, and socioeconomic context. Channel and a repaired prior-claim count need the same review: history and broker mix can stand in for customer circumstances rather than for handling effort. What may be claimed is a monitored association with a stated purpose, plus group error rates. The fair operational substitute, where the business mechanism is real, is a direct measure such as repair-network coverage or language support. Region is a weak and sensitive lever for routing or prioritization. These features are not deleted by default, and they are not described as delay drivers.

**Drift or calendar proxy.** `calendar_week` is knowable at `t0` and can predict well inside one regime. Week 52 coincides with holidays, and the notes tie some weeks to an operating-policy change. What may be claimed is a seasonal or regime association for the period used in training. The more stable encodings are a holiday calendar and a policy-regime flag. After those are included, any leftover week effect has to be re-estimated on a later period. A week coefficient is not an explanation that operations in that week are worse, and it will not travel across the policy change.

**Unusable until lineage is repaired.** Permanently unusable at this decision point: `total_case_duration_hours`, `appeal_seen_anywhere`, `final_decision`, `full_trace_variant_id`, `last_resource_role` as currently defined, and all five published sequence patterns. Repairable into one of the classes above, and unusable as currently built: `final_handler_team` (substitute team at `t0`), `num_document_requests_total` and `same_day_document_count_snapshot` (prefix counts; degenerate here), `prior_claim_count_before_t0` (cutoff `< t0`), `risk_score_current` (version at `t0`), `initial_reserve` if it is overwritten, employee experience (join at event time), and `queue_length_at_t0` only to the extent a snapshot falls after `t0`. `Claim Closed -> Damage Assessment Completed` is a data-quality defect, not a repairable predictor. `Appeal -> Settlement Decision Recorded` is the opposite kind of object: a legal later succession that is simply not knowable at coverage check.

Published magnitudes cannot be reused feature by feature. SHAP in a model that already sees the outcome redistributes credit among leaked fields and their correlates. Directions on `queue_length_at_t0`, complexity, and elapsed time are hypotheses to re-estimate after the refit.

## 5. Recommendations for explanation validation

1. **Point-in-time feature store first.** Give every feature a valid time and a knowledge time. Ban joins on `extraction_date` and ban `last_value` over the case for any model scored at coverage check. Rebuild the training row as of the first `Coverage Check Completed` before any new importance ranking.

2. **Historical timestamps and sequence indexes.** Require an ingestion sequence index on every event. Persist handler team, reserve, risk score, queue snapshots, document counts, and employee attributes as versioned rows. Make a null feature time a failed publish, not a silent current-state join.

3. **Prefix-only recomputation.** Retrain without the permanent exclusions in section 3, using repaired substitutes where they still have variance. On a time-based holdout, compare discrimination and calibration with and without the leaked columns so the inflation in the current 0.82 / 0.71 / 0.64 scores is measured. Recompute local explanations only on that refit.

4. **Process-conformance gate in the explainer.** Before an explanation is released, replay the prefix, run the declarative checks for appeal and repeated decisions, and reject any cited activity that is not observed. Quarantine unordered timestamp ties. Keep full-trace conformance as a separate data-quality dashboard so suffix violations never re-enter the feature matrix.

5. **Calibration after removal.** Leakage removal will move probabilities, not only explanations. Recalibrate on a later period and publish reliability by queue band, complexity, and week regime. Retire the current local probabilities until that calibration exists.

6. **Explanation stability.** On a suffix-masking test, attributions for admissible features should stay put when the future trace is deleted, and attributions for leaked features should go to zero. Add bootstrap or time-split stability checks, and suppress explanations whose sign flips across nearby snapshots of the same prefix.

7. **Proxy and fairness analysis, without blanket deletion.** For region, channel, and repaired prior-claim count, report error rates and score gaps, then test whether repair-network coverage, language support, and portfolio mix absorb the gap. Keep a feature that represents a documented operational constraint. Restrict automated routing uses when the residual is a socioeconomic proxy. Record that predictive lift is a different decision from deployment.

8. **Drift monitoring.** Monitor schema changes, null feature timestamps, conformance rates, the share of tied events, holiday and policy-regime mix, and calibration by week. Alert when importance shifts toward any feature whose valid time is after `t0`, or when a new activity appears in the log that the normative model does not enable. Revisit calendar features at the policy-change boundary rather than treating week importance as a stable finding.
