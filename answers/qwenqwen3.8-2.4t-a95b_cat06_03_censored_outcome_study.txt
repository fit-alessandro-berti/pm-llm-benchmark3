## 1. Target definition

**Primary target: observed-process cumulative incidence of 90-day post-activation default from application start.**

- **Unit of analysis:** one credit application case (`case:concept:name`).
- **Population:** all applications started between 1 January 2024 and 31 December 2025, not only activated accounts.
- **Prediction time:** a pre-decision “early prefix” time, defined as the earlier of:
  - completion of the first `k = 3` pre-decision events, e.g. `Application Started`, `Identity/KYC Check`, first `Credit Review`; or
  - `start_time + 7 days`.
  
  The prediction time is truncated to occur strictly before the first decision or post-decision event (`Accepted`, `Rejected`, `Withdrawn`, `Transferred`, `Contract Signed`, `Account Activated`). If a case decides or terminates before the nominal prefix time, the prediction time is moved to just before that first decision/terminal event and the prefix is flagged as short.

- **Horizon:** because `default_90d` is defined only after activation, the primary target uses an explicit bounded pathway:
  1. activation must occur within an operational fulfillment window, e.g. **180 days from application start**; and
  2. if activated, default must occur within **90 days after `Account Activated`**.

  The 180-day activation window is a design assumption. It makes the all-application estimand bounded and testable. Sensitivity analyses should vary this window.

- **Estimand:** the cumulative incidence, under the observed historical process, that a started application leads to an activated account and a default within 90 days of activation, before competing non-activation outcomes or administrative censoring. Formally, for prefix `x` and observed regime `r`:

  \[
  \theta(x, r) = P(\text{activation within 180d and default within 90d post-activation} \mid \text{prefix}=x, \text{regime}=r)
  \]

  estimated with competing risks and right censoring.

This target is **not** “rejected/withdrawn/open equals non-default.” Rejected and withdrawn applications are not exposed to credit under the observed process, so default is not observed and is not meaningfully zero. They are competing outcomes or undefined-under-activation states, depending on the formulation.

**Why this primary target is defensible:**  
It answers an operational early-warning question across the full application funnel while respecting the fact that default is only observable after activation. It allows the lender to estimate which early application prefixes are associated with downstream default under the current observed acceptance, funding, and servicing process. It also supports decomposition into activation transition risk and post-activation default risk.

**Credible alternative target: activation-conditional 90-day default.**  
This target is:

\[
P(\text{default within 90d of activation} \mid \text{eventually activated}, \text{prefix}=x)
\]

This answers a different question: among accounts that eventually become activated, which early prefixes predict default? It is statistically cleaner because the outcome is defined, but it conditions on a post-prefix event, activation. If used for every application, it requires an activation model, inverse-probability-of-activation weighting, or strong counterfactual assumptions. It does not by itself answer what happens to rejected, withdrawn, transferred, or still-open applications.

Another alternative is a **policy-specific counterfactual target**, such as “probability of default within 90 days if this application were accepted and activated under policy version `p`.” That target may be closest to a lending decision, but it requires strong causal assumptions, an explicit activation policy, and usually additional data or experiments. It should be labeled as counterfactual, not as an directly observed outcome.

## 2. Cohort construction

### Inclusion rules

Include:

1. All cases with a valid `Application Started` event between 2024-01-01 and 2025-12-31.
2. All cases present in the event log, regardless of whether they appear in the current labeled ML export.
3. All cases with a usable pre-decision prefix. Cases that terminate before the desired prefix length are retained with a short-prefix flag for the primary analysis; a sensitivity analysis may exclude them if the business requires exactly `k` events.

### Exclusion rules

Exclude only for data-quality reasons, not because outcomes are missing:

1. Cases with missing or invalid start timestamps.
2. Duplicate synthetic cases created by migration, after deduplication.
3. Cases whose first event occurs after the analysis as-of cutoff.
4. Cases with corrupted case identifiers that cannot be linked to events.

Do **not** exclude rejected, withdrawn, transferred, still-open, or immature activated cases from the cohort. They must be represented with correct censoring or competing-state labels.

### As-of rules

Use a configurable analysis cutoff, for example:

- `AS_OF = 2026-01-31`, slightly before the 2026-02-15 extraction date to allow validation freeze.
- Only events with `time:timestamp <= AS_OF` are used for features and outcomes.
- Only labels with `label_available_at <= AS_OF`, or otherwise known by `AS_OF`, are treated as observed.
- A matured activated account requires:

  \[
  \text{activation time} + 90 \text{ days} + \text{maximum feed delay} \le AS_OF
  \]

  with maximum feed delay set conservatively to 35 days.

### Transfer linkage rule

Transferred cases should be joined to the linkage table before final outcome assignment.

- Linked transfers: follow the new identifier if it reappears and becomes activated/matured.
- Unlinked transfers: treated in the primary analysis as a competing/missing-follow-up state, with sensitivity analyses described in Section 3.

## 3. Censoring and missing-label strategy

The data contain several distinct missingness and censoring mechanisms. They must not be collapsed into “non-default.”

### 3.1 Ordinary right censoring

Examples:

- Still-open applications at `AS_OF`.
- Activated accounts whose 90-day window has not finished.
- Activated accounts whose window finished but whose delayed outcome feed has not arrived.
- Linked transferred cases that are still unresolved by `AS_OF`.

These cases are not known non-defaults. They are censored at the earlier of:

- `AS_OF`;
- the end of the target window, e.g. `start_time + 180 days` for activation and `activation_time + 90 days` for default;
- last reliable contact or event time, if follow-up is otherwise incomplete.

### 3.2 Delayed labels

The external outcome feed can arrive 7–35 days after the 90-day horizon. Therefore:

- A default label is usable only if `label_available_at <= AS_OF` or the default event is otherwise known by `AS_OF`.
- A non-default label for an activated account is usable only after the 90-day horizon plus the maximum plausible feed delay has passed.
- If the feed has not matured, the case is censored or delayed, not set to zero.

### 3.3 Selection through activation

Default is observed only if the case reaches `Account Activated`. Activation is a post-prefix intermediate event, not a harmless sampling condition.

For the primary all-application target, activation is modeled as part of the process:

- application prefix influences probability of activation;
- activation influences whether default can be observed;
- default is an absorbing state after activation.

For an activation-conditional alternative target, selection through activation must be addressed using methods such as inverse-probability-of-activation weighting, outcome regression with selection adjustment, or explicit modeling of the activation transition. This requires assumptions that are at best partially testable.

### 3.4 Transfer as competing event or missing follow-up

Transferred cases are ambiguous:

- If linked to a new identifier and the new case activates and matures, the outcome can be recovered.
- If linked but still unresolved, treat as censored or unresolved transfer.
- If unlinked, the local system cannot observe the outcome.

Primary analysis: treat unlinked transfers as a competing outcome or missing-follow-up state, not as non-default.

Sensitivity analyses:

1. Treat unlinked transfers as censored.
2. Treat unlinked transfers as competing events.
3. Impute worst-case and best-case default rates.
4. Impute default rates equal to linked transfers with similar prefixes.
5. Use partner-origin indicators and historical feed-completeness rates to bound the outcome.

### 3.5 Permanently missing outcome feeds

Partner-originated activated accounts have elevated probability of permanently missing outcomes. This is not ordinary random missingness.

Primary strategy:

- Include partner/source indicators.
- Estimate feed-completeness rates from historical linked cases.
- Use censoring-aware models rather than complete-case deletion.
- Report bounds for default incidence under plausible missing-feed scenarios.

Sensitivity strategy:

- Pattern-mixture bounds.
- Multiple imputation under missing-at-random assumptions using prefix, channel, region, risk score, and partner history.
- Inverse-probability-of-observation weighting for outcome feed availability.
- Extreme-case bounds: all missing partner feeds default versus none default.

### Primary analysis strategy

Use a **multi-state or competing-risk framework**:

States:

1. Application open / pre-activation.
2. Activated.
3. Default within 90 days post-activation.
4. Activated, no default within 90 days.
5. Rejected.
6. Withdrawn.
7. Transferred unresolved.
8. Administratively censored.

Possible transitions:

- Open  Activated.
- Open  Rejected / Withdrawn / Transferred unresolved.
- Open  Censored.
- Activated  Default.
- Activated  No default within 90 days, once matured.
- Activated  Censored if immature or feed delayed.

This can be implemented with cause-specific hazard models, Fine-Gray subdistribution models, discrete-time transition models, or Aalen-Johansen estimation, depending on modeling choice. The implementation skeleton in Section 9 prepares the cohort but does not fabricate a survival-model API.

### Assumption testability

| Assumption | Testability |
|---|---|
| Label maturity rule and delayed-feed timing | Testable using `label_available_at` and historical feed arrival. |
| Duplicate and activity-renaming rules | Testable using migration logs and duplicate patterns. |
| Transfer linkage coverage | Partially testable using the 60% linked subset. |
| Outcome distribution of linked transfers | Testable within linked subset, but may not generalize to unlinked transfers. |
| Independent censoring for still-open cases | Partially testable if later extracts become available. |
| Missing outcome feed independent conditional on observed features | Partially testable, but likely fragile for partner-originated accounts. |
| Default outcomes for rejected/withdrawn cases if they had been activated | Fundamentally untestable from these data. |
| Counterfactual default under an all-accept or changed-accept policy | Fundamentally untestable without stronger causal assumptions or experimental data. |

## 4. Prefix extraction

Prefix extraction must preserve an as-of perspective. No event, field, or derived value after the prediction time may enter the feature table.

### 4.1 Canonical activity mapping

Because the 15 October 2025 migration renamed activities:

1. Map old and new activity names to canonical names.
2. Store both original and canonical activity names for audit.
3. Add a `post_migration` flag based on timestamp.
4. Remove duplicate events created by migration where the same case, canonical activity, timestamp, resource, and source system appear more than once.

### 4.2 Pre-decision activity set

For the early-warning model, only pre-decision activities are allowed in prefixes:

- `Application Started`
- `Identity/KYC Check`
- `Credit Review`
- `Request Documents`

The following are excluded from prefix features:

- `Accepted`
- `Rejected`
- `Withdrawn`
- `Transferred`
- `Contract Signed`
- `Account Activated`
- `Collections Contact`
- `Default Recorded`

These excluded events are used only for target construction, censoring, and cohort definition.

### 4.3 Fixed event-count prefixes

Fixed prefix rule:

- Count only pre-decision events.
- Prediction time is the timestamp of the `k`-th pre-decision event, e.g. `k = 3`.
- If fewer than `k` pre-decision events occur before the first decision/terminal event, use the available shorter prefix and record `prefix_length`.
- If the business requires exactly `k` events, run a sensitivity analysis excluding short prefixes.

### 4.4 Elapsed-time prefixes

Elapsed-time rule:

- Prediction time is `start_time + `, e.g. ` = 7 days`.
- Include only pre-decision events with `time:timestamp <= prediction_time`.
- If a decision or terminal event occurs before ``, move prediction time to immediately before that event.
- Record whether the prefix was truncated by decision, termination, or insufficient events.

### 4.5 Short cases

Short cases are retained in the primary cohort with explicit flags:

- `prefix_length`
- `prefix_truncated_by_decision`
- `prefix_truncated_by_time`
- `prefix_contains_document_loop`
- `prefix_contains_kyc_repeat`

This avoids silently selecting only easy, long-running cases.

### 4.6 Repeated document loops

Document loops are process information, not leakage, if they occur before the prediction time.

- Count `Request Documents` events before prediction time.
- Count returns to `Credit Review` after document requests.
- Do not include document events after prediction time.
- Do not use same-day nightly snapshot totals unless the snapshot can be reconstructed as of the exact prediction timestamp.

### 4.7 Activity renaming and duplicates

For migration:

- Use canonical activity names before variant discovery or prefix extraction.
- Keep a `migration_period` flag.
- Deduplicate exact duplicates.
- If duplicate events are uncertain, keep one version and run a sensitivity analysis including/excluding suspected duplicates.

## 7. Validation design

A random case split is misleading here because it mixes:

- pre- and post-policy-change cases;
- pre- and post-migration cases;
- matured and immature labels;
- different activation rates and outcome observation probabilities;
- cases whose future events may leak into features if preprocessing is not strictly as-of.

The primary validation must be temporal.

### Temporal split by application start time

Using `AS_OF = 2026-01-31`:

| Split | Case start window | Purpose | Label maturity |
|---|---|---|---|
| Train | 2024-01-01 to 2024-12-31 | Learn baseline process/outcome relationships. | Mostly matured, except late activations with delayed feeds. |
| Validation | 2025-01-01 to 2025-06-30 | Tune models before policy change. | Mostly matured by `AS_OF` for reasonable activation times. |
| Test A: policy shift | 2025-07-01 to 2025-09-30 | Evaluate robustness after 1 July 2025 credit-policy change and before migration. | Partially matured; use censoring-aware metrics and restrict binary metrics to matured cases. |
| Test B: migration shift | 2025-10-15 to 2025-12-31 | Evaluate activity renaming, duplicates, prefix stability, and short-term transitions. | Mostly immature for 90-day post-activation default by `AS_OF`; use for monitoring and censored likelihoods, not final default metrics until later extracts. |

### Rolling backtest

Use monthly or quarterly origin cohorts:

1. Train on cases started before training cutoff.
2. Freeze model.
3. Score cases in the next month using only prefix information available at prediction time.
4. Evaluate only after the cohort’s labels have matured.
5. Repeat with rolling origin.

This simulates deployment more honestly than a random split.

### Handling policy change and migration

- Include policy-period and migration-period indicators.
- Report separate performance before/after 1 July 2025 and before/after 15 October 2025.
- Test calibration drift across policy periods.
- Compare prefix variant distributions before/after migration.
- Consider period-stratified models or interaction terms if drift is large.

### Metrics for the primary target

Because the target includes censoring and competing events, use survival/competing-risk metrics:

- Cumulative incidence function calibration: predicted default CIF versus Aalen-Johansen or nonparametric CIF by risk decile.
- Time-dependent AUROC for default incidence.
- IPCW Brier score.
- Calibration slope and intercept for predicted cumulative incidence.
- Ranked probability score for multi-state probabilities, if multi-state probabilities are produced.
- Decision-curve analysis adapted to competing risks.
- Cumulative/dynamic AUC at the target horizon.

For the subset of matured activated accounts, also report:

- AUROC.
- AUPRC, because default is minority class.
- Brier score.
- Calibration plot, calibration slope, intercept.
- Precision-recall by risk decile.

### Subgroup evaluation

Evaluate performance by:

- policy period;
- migration period;
- channel;
- region;
- partner/source system;
- risk-score band;
- prefix length;
- short-prefix versus full-prefix cases;
- linked versus unlinked transfers;
- activated-only versus full cohort.

### Distribution-shift monitoring

Track:

- PSI/KL divergence for key features.
- Activation rate by prefix and period.
- Rejection/withdrawal/transfer rates.
- Outcome-feed completeness.
- Default rate among matured activated accounts.
- Prefix variant distribution.
- Duplicate and renamed-activity rates.

`pm4py.split_train_test` may be used as a convenience baseline, but it is not the primary validation design because it does not respect policy change, migration, or label maturity.

## 8. Limitations and decision-use boundary

### What the study can claim

The study can claim:

1. **Predictive association under the observed process.**  
   Early prefixes are associated with the probability of later activation and, conditional on activation, observed 90-day default.

2. **Censoring-aware risk estimation.**  
   The study can estimate cumulative incidence of default among started applications while treating open, immature, transferred, rejected, and withdrawn cases honestly.

3. **Process monitoring.**  
   The study can detect changes in process behavior, activation rates, document loops, migration effects, and policy-period drift.

4. **Decision support under the current observed funnel.**  
   The model can prioritize applications for review, document collection, or monitoring based on expected downstream default under the historical process.

### What the study cannot claim

The study cannot claim:

1. **Counterfactual default risk for rejected or withdrawn applications.**  
   A rejected application has no observed default outcome under activation. Treating it as non-default is not valid.

2. **Default risk under a new acceptance policy without causal assumptions.**  
   If the lender wants to know what would happen if a currently rejected applicant were accepted, that is a policy-specific counterfactual target.

3. **Unbiased all-application default probability if activation is changed by deployment.**  
   Activation is selected and influenced by policy, applicant behavior, and operational capacity.

4. **Complete outcome observability for unlinked transfers.**  
   Unlinked transfers are missing follow-up, not confirmed non-defaults.

5. **Stable performance across policy regimes without revalidation.**  
   The 1 July 2025 policy change means the same prefix may have different selection probability and outcome relationship.

### Predictive association, selection effects, and counterfactual risk

The observed default rate among activated accounts is conditional on acceptance and activation. If high-risk prefixes are more likely to be rejected, the activated population is selected. A model trained only on activated matured accounts may learn associations that do not generalize to all applications. Counterfactual default risk under an alternative acceptance policy requires assumptions such as no unmeasured confounding, correct activation modeling, or experimental variation.

### Deployment can change the data-generating process

At least three deployment feedback loops are likely:

1. **Acceptance-policy feedback.**  
   If the model changes accept/reject decisions, the activated population changes, changing the observed default base rate.

2. **Operational-intervention feedback.**  
   If high-risk cases receive more document requests, closer monitoring, or different collections treatment, the process and default recording change.

3. **Routing and missingness feedback.**  
   If the model changes transfer routing to partners, the proportion of unlinked or missing outcome feeds may change, altering label observability.

Additional possible changes include applicant behavior after repeated document requests, credit-policy threshold changes, and macroeconomic shifts.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import numpy as np
import pm4py

# Assumptions: as-of cutoff, 90d horizon, 35d delayed feed, 180d activation window, prefix rule.
CASE_ID, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
AS_OF = pd.Timestamp("2026-01-31")
HORIZON = pd.Timedelta(days=90)
MAX_FEED_DELAY = pd.Timedelta(days=35)
ACTIVATION_WINDOW = pd.Timedelta(days=180)
PREFIX_EVENT_COUNT, PREFIX_ELAPSED_DAYS = 3, 7

df = pd.read_csv("applications_events.csv", parse_dates=[TS, "label_available_at", "data_extract_time"])
df = pm4py.format_dataframe(df, case_id=CASE_ID, activity_key=ACT, timestamp_key=TS)

# Canonicalize migration renames and drop exact duplicate rows created by migration.
rename_map = {"Identity Check": "Identity/KYC Check", "KYC": "Identity/KYC Check",
              "Credit Decision - Accept": "Accepted", "Credit Decision - Reject": "Rejected",
              "Applicant Withdrawal": "Withdrawn", "Partner Transfer": "Transferred",
              "Activated Account": "Account Activated", "Default": "Default Recorded"}
df[ACT] = df[ACT].replace(rename_map)
df = df.sort_values([CASE_ID, TS, ACT])
df = df[~df.duplicated(subset=[CASE_ID, TS, ACT, "org:resource", "source_system"], keep="first")]

PRE_DECISION = {"Application Started", "Identity/KYC Check", "Credit Review", "Request Documents"}
DECISION = {"Accepted", "Rejected", "Withdrawn", "Transferred"}
FORBIDDEN = {"final_limit", "decision_reason", "collection_status", "default_90d",
             "label_available_at", "data_extract_time"}
events = df[df[TS] <= AS_OF].copy()

case = events.groupby(CASE_ID).agg(start_time=(TS, "min"), last_event_time=(TS, "max")).reset_index()
def first_time(acts):
    return events.loc[events[ACT].isin(acts)].groupby(CASE_ID)[TS].min()
case = case.merge(first_time({"Account Activated"}).rename("activation_time"), on=CASE_ID, how="left")
case = case.merge(first_time({"Default Recorded"}).rename("default_event_time"), on=CASE_ID, how="left")
case = case.merge(first_time(DECISION).rename("first_decision_time"), on=CASE_ID, how="left")
case = case.merge(first_time({"Rejected"}).rename("rejected_time"), on=CASE_ID, how="left")
case = case.merge(first_time({"Withdrawn"}).rename("withdrawn_time"), on=CASE_ID, how="left")
case = case.merge(first_time({"Transferred"}).rename("transferred_time"), on=CASE_ID, how="left")

# Labels are usable only if the delayed feed was available by AS_OF.
known_labels = events[events["default_90d"].notna() &
                      ((events["label_available_at"].isna()) | (events["label_available_at"] <= AS_OF))]
label_last = known_labels.groupby(CASE_ID).agg(default_90d_last=("default_90d", "max"),
                                               label_available_max=("label_available_at", "max"))
case = case.merge(label_last, on=CASE_ID, how="left")
known_default = case["default_90d_last"] == 1
proxy = case["label_available_max"].fillna(AS_OF)
mask = known_default & case["default_event_time"].isna()
case.loc[mask, "default_event_time"] = proxy[mask]

case["activation_plus_90"] = case["activation_time"] + HORIZON
case["outcome_matured"] = (case["activation_time"].notna() & case["default_90d_last"].notna() &
                           ((case["activation_plus_90"] + MAX_FEED_DELAY) <= AS_OF))
case["default_within_90"] = (case["activation_time"].notna() &
                             (known_default | (case["default_event_time"] <= case["activation_plus_90"])))

def cohort_status(r):
    if pd.notna(r.activation_time):
        if r.outcome_matured:
            return "activated_matured_default" if r.default_within_90 else "activated_matured_nodefault"
        return "activated_immature_or_delayed"
    if pd.notna(r.rejected_time): return "rejected_competing"
    if pd.notna(r.withdrawn_time): return "withdrawn_competing"
    if pd.notna(r.transferred_time): return "transferred_unresolved_missing_followup"  # join linkage later
    return "open_censored"
case["cohort_status"] = case.apply(cohort_status, axis=1)

# Prediction time from first k pre-decision events or elapsed days, truncated before decision.
pre = events[events[ACT].isin(PRE_DECISION)].copy()
pre["pre_seq"] = pre.groupby(CASE_ID).cumcount() + 1
kth = pre.loc[pre["pre_seq"] == PREFIX_EVENT_COUNT].groupby(CASE_ID)[TS].min()
case = case.merge(kth.rename("kth_time"), on=CASE_ID, how="left")
case["elapsed_pred_time"] = case["start_time"] + pd.Timedelta(days=PREFIX_ELAPSED_DAYS)
case["pred_time"] = case[["kth_time", "elapsed_pred_time"]].min(axis=1)
eps = pd.Timedelta(seconds=1)
too_late = case["first_decision_time"].notna() & (case["pred_time"] >= case["first_decision_time"])
case.loc[too_late, "pred_time"] = case.loc[too_late, "first_decision_time"] - eps
case["pred_time"] = case["pred_time"].clip(lower=case["start_time"])

pre_before = pre.merge(case[[CASE_ID, "pred_time"]], on=CASE_ID, how="inner")
pre_before = pre_before[pre_before[TS] <= pre_before["pred_time"]]
case = case.merge(pre_before.groupby(CASE_ID)["pre_seq"].max().rename("prefix_length"), on=CASE_ID, how="left")
case["prefix_length"] = case["prefix_length"].fillna(0).astype(int)

# Leakage-safe prefix log and fixed-length prefixes.
prefix_log = events.merge(case[[CASE_ID, "pred_time"]], on=CASE_ID, how="inner")
prefix_log = prefix_log[(prefix_log[TS] <= prefix_log["pred_time"]) &
                        (prefix_log[ACT].isin(PRE_DECISION))].copy()
prefix_log = pm4py.format_dataframe(prefix_log, case_id=CASE_ID, activity_key=ACT, timestamp_key=TS)
prefixes_fixed = pm4py.get_prefixes_from_log(prefix_log, PREFIX_EVENT_COUNT)

# Feature table using only pre-prefix/static values. Post-decision columns are forbidden.
static_cols = ["case:channel", "case:region", "case:requested_amount"]
first_static = prefix_log.sort_values(TS).groupby(CASE_ID)[static_cols].first()
risk_last = prefix_log.sort_values(TS).groupby(CASE_ID)["risk_score"].last()
feature_df = case[[CASE_ID, "start_time", "pred_time", "prefix_length", "cohort_status"]].set_index(CASE_ID)
feature_df = feature_df.join(first_static).join(risk_last.rename("risk_score_latest_prefix"))

# Process-aware summaries only on leakage-safe prefix log.
variants = pm4py.get_variants(prefix_log)
dfg, dfg_start, dfg_end = pm4py.discover_dfg(prefix_log)
# temporal = pm4py.extract_temporal_features_dataframe(prefix_log)  # use only with true event timestamps.

# Temporal split by case start; random split is not primary.
s = feature_df["start_time"]
feature_df["split"] = np.select(
    [s < pd.Timestamp("2025-04-01"),
     s.between(pd.Timestamp("2025-04-01"), pd.Timestamp("2025-06-30")),
     s.between(pd.Timestamp("2025-07-01"), pd.Timestamp("2025-09-30")),
     s >= pd.Timestamp("2025-10-15")],
    ["train", "validation_pre_policy", "test_post_policy_pre_migration", "monitor_post_migration_immature"],
    default="other")

# Cohort counts and leakage audit.
cohort_counts = case["cohort_status"].value_counts()
leaked = sorted(FORBIDDEN.intersection(feature_df.columns))
post_prefix = prefix_log[prefix_log[TS] > prefix_log["pred_time"]]
assert not leaked, "Forbidden post-decision/outcome columns in feature table"
assert post_prefix.empty, "Post-prefix events leaked into prefix log"

# Connect to survival/competing-risk modeling downstream:
# event times: default_time, rejected/withdrawn/transferred_time, activation+90 for matured non-defaults;
# censored at min(AS_OF, start+ACTIVATION_WINDOW, last_event_time). No survival model is fabricated here.
case["analysis_end_time"] = (case["start_time"] + ACTIVATION_WINDOW).clip(upper=AS_OF)
# pm4py.split_train_test(prefix_log, train_percentage=0.8) is only a non-temporal convenience baseline.
```
