# 3. Consequences for performance analysis

**General mechanisms:** Waiting time = `start - queue_arrival` (or `first available - arrival`). Service time = `complete - start`. Utilization = busy time / available time per resource. Throughput = completions per time unit. Conformance: temporal order vs model. Any equality/interval artifact directly injects bias.

*G1 - Genuine simultaneous batch (parallel machine):*
- Waiting: if measured `start - arrival` = 2-6 min correct (queue before fixture loaded). If analyst expands 4×3-min services sequentially, waiting inflated for later items in fixture misinterpreted as queue.
- Service: Naive sum 4×3=12 min overcounts capacity; correct is 3 min joint service, throughput 4 per 3 min. Treating as concurrent human tasks underestimates utilization divisor.
- Utilization: Robot busy 3 min not 12; conflating scans simultaneous would suggest >100% utilization.
- Bottleneck: appears as batch resource; correct bottleneck is loading/unloading fixture, not processing rate.

*G2 - Start batching artifact + sequential execution:*
- Waiting: `10:00 - arrival` 6-18 min understates for S02-S04 whose true start was 10:08,10:14,10:21. True waiting longer by ~8-21 min; apparent waiting artificially compressed.
- Service: If using logged start, S02 service 14 min (10:00-10:14) double counts S01 busy period, overlapping services sum > clock time, inflating utilization >100% and depressing throughput (appears 4 concurrent). True service = 8,6,7,6 min sequential.
- Utilization: Concurrent view suggests operator 4× busy during 10:00-10:27 (27 min clock, 52 min summed), >100% utilization  false multitasking alarm.
- Bottleneck: spurious parallelism hides sequential bottleneck.

*G3 - End batching / bulk submission:*
- Waiting: For E01 `11:02-10:40`=22 min correct, but for E04 `11:24-11:05`=19 min correct; however if waiting defined to bulk completion `11:30`, waiting inflated to 50,38,32,25 min (early items appear to wait while actually being processed).
- Service: Logged durations 28,20,13,6 min decreasing trend artifactually; true durations unknown but likely ~7-8 min each sequential. Bulk end deflates last item service and inflates first.
- Utilization: Sum 67 min busy in 28 min window  239% utilization artifact.
- Bottleneck: early arrivals appear to queue for bulk step, mis-identified as release review bottleneck when bottleneck is form submission process.

*G4 - Faithful sequential:*
- Unbiased baseline. Waiting 7,10,13,16,19 min reflects real queue build at ~1/min arrival vs 4-min service slightly slower. Service ~4 min stable, utilization 20/20 =100% during 12:05-12:25 busy, idle otherwise. No correction. Use to calibrate expectation.

*G5 - Shared-account artifact:*
- Waiting: Pool-level waiting correct; per-worker waiting indeterminate without split.
- Service: Apparent overlapping services per “resource” double count time  utilization may exceed 300% if 3 analysts busy, falsely alarming as multitasking violation. If analyst assumes single worker, service time appears concurrent and conformance flags impossible overlap as violation.
- Throughput: Pool throughput sum of workers, not individual productivity; cannot rank analysts.
- Bottleneck: obscures whether bottleneck is insufficient analysts or slow analysis; requires badge granularity.

*G6 - Bulk submission (extreme end batching) - why both biases coexist:*
- Mechanism: Execution occurred earlier throughout 14:05-17:00 but `start=complete=17:00` records only the logging event. So
  - **Waiting inflated:** `waiting = 17:00 - queue_arrival` = 35 to 175 min, includes both real waiting + processing + deferred logging delay. True waiting likely far smaller; queue appears to explode at 17:00.
  - **Service near-zero:** `service = complete - start = 0` for all 7. Real service >0 but unobserved; naive average service ~0, throughput appears as 7 instant completions at 17:00  infinite instantaneous throughput, then zero elsewhere, destroying capacity planning.
  - Both simultaneously because start is pulled **forward** to logging time (inflating waiting) and complete is also pulled to same time (collapsing service). Valid analyses must exclude G6 from service distribution and interval-censor waiting to [arrival, 17:01] unknown.
  - Utilization: 0 min busy  0% utilization despite real work preceding bulk.
  - Conformance: trace appears as 7 parallel zero-duration activities violating duration constraints; alignments fail.

*G7 - Timestamp coarsening 15-min:*
- Waiting: Any arrival inside [14:00,14:15) after apparent start 14:00 yields negative waiting (e.g., M05 arrival 14:11 - start 14:00 = -11 min)  paradoxical “started before queued”. Signals censoring.
- Service: All 15 min, but true durations likely <15 and sequential; service overestimated, throughput underestimated (5 completions at 14:15 instant vs spread).
- Utilization: 5×15 =75 min busy in 15 min window  500% overstatement if interpreted as concurrent.
- Bottleneck: coarse grid hides sequencing, masks true bottleneck granularity.

*G8 - Queue accumulation after capacity loss:*
- Waiting: `15:38 -15:00 =38 min` for Q01 includes 35 min blocking (safety check) +3 min true queue. Without annotating `unavailable` calendar, waiting attributed to congestion, inflating queueing delay and mis-identifying repair as bottleneck.
- Service: 7 min each correct during drain, unbiased if blocking separated.
- Utilization: During 15:00-15:35 utilization should be 0% unavailable, not 0% idle/available; naively appears as starvation. Drain phase shows 100% utilization which is recovery, not overload.
- Bottleneck: Downtime queue appears as process bottleneck; corrective action is capacity restoration, not added repair staff.

```python
    neg_wait = (wait < 0).any()
    diagnostics.append([cl, len(g), g["resource"].iloc[0], g["source"].iloc[0], g["precision"].iloc[0],
                        start_eq, end_eq, start_groups, end_groups, round(adj,2), round(ov,2),
                        round(lag.min()/60,2), round(lag.max()/60,2), round(sec_zero_start,2), round(sec_zero_end,2),
                        round(wait.min(),1), round(wait.max(),1), neg_wait])

diag_cols = ["cluster","n","resource","source","precision","all_start_eq","all_end_eq","max_start_tie","max_end_tie","adjacency","overlap_rate","lag_min_m","lag_max_m","sec0_start","sec0_end","wait_min","wait_max","neg_wait"]
diag_df = pd.DataFrame(diagnostics, columns=diag_cols).sort_values("cluster")
print("\n=== CLUSTER-LEVEL DIAGNOSTIC TABLE ===")
print(diag_df.to_string(index=False))
# compare with PM4Py categories
print("\nComparison: PM4Py batch categories are purely temporal (simultaneous vs sequential vs concurrent) and will label G1,G6,G7 as 'simultaneous' at 60s, G2 as simultaneous-start/ sequential-end, G3 as simultaneous-end, G4/G8 as sequential - but semantics differ (physical vs logging vs coarse). See G5 shared-account false positives.")
print(diag_df)
```


The code preserves all clusters even where `start` or `complete` suspect; diagnostics flag `neg_wait`, `sec0` granularity and `lag` to distinguish logging batches from execution batches rather than dropping them.

# 5. Robustness and alternative explanations

**Sensitivity 1: Resource identity trusted vs shared-account treated as unreliable**

| assumption | G5 interpretation shift | other clusters shift |
|---|---|---|
| Trusted: `analyst_pool` = one worker | Overlap = proof of illegal multitasking / 100% overlap  utilization >100% flagged as violation, bottleneck mis-located | No change: G1-G4/G6-G8 resource IDs assumed reliable |
| Shared: up to 3 analysts (documentation) | Overlap = expected pooling of 2-3 parallel workers; apparent concurrent batch disappears after disaggregation; pool throughput valid, individual idle invalid | If G2/G3/G4 also shared (hypothesis absent evidence), could falsely explain start/end equality as parallel workers, but source context and single-resource screens make that less parsimonious |

Robustness: G5 confidence drops from 45 to <20 if forced to trust ID; recommendation to exclude G5 from per-resource metrics is robust under shared assumption but reverses if trust is enforced. All other clusters’ top explanation stable under either assumption except G6 where shared account could mimic 7 parallel closers but bulk-form context refutes.

**Sensitivity 2: Timestamps exact points vs interval-censored by stated precision**

Assume point-exact: G7 equality at 14:00/14:15 taken as evidence of simultaneous 15-min service; G2 start equality at 10:00 taken as true simultaneous start; G3 end equality as true simultaneous finish.

Assume interval-censored ([t, t+precision)) or rounding to grid: G7’s 5 intervals collapse to grid points; true order inside 15-min bin unknown, negative waiting (-11 min) becomes valid (arrival inside interval). G2’s starts lie inside [10:00,10:01), so could be sequential within minute; adjacency of G4 (±0 sec) robust only at 1-sec precision—if 1-sec logs were coarse, adjacency would be hidden. G6 with 1-min granularity interval-censoring still zero-duration remains zero (both stamps same minute) even if censored.

Result: Under exact assumption, PM4Py `merge_distance=60` labels G2,G3,G7 as high-confidence batches; under interval-censored assumption confidence falls 30-50 points and requires reporting service as interval [0, precision] or excluding G6/G7 from point-based waiting/service.

**Three cases where identical temporal pattern supports multiple physical explanations:**

1. **All starts equal + all ends equal (G1 pattern)**: Could be (a) genuine simultaneous batch on parallel fixture (G1 truth), (b) start/end batching logging artifact where sequential work logged as common stamps (if PLC logged group vs per-item), (c) timestamp coarsening where 15-min rounding forces equality even for sequential work (G7 mimics G1). Without source metadata and capacity knowledge, pattern insufficient; distinguishes only via precision test (G1 retains equality at 1-sec, G7 only at 15-min) and capacity documentation.

2. **All starts equal, ends staggered (G2 pattern)**: Could be (a) start-batched sequential campaign (G2 truth), (b) concurrent multitasking where worker time-slices across cases (would also start “together” then overlap but G2 has no overlap, so alternative requires multitasking with blocking), (c) shared-account artifact where X workers each start at 10:00 on same account but complete independently (if G2 had been `analyst_pool`, overlap would appear concurrently, but G2 sequential completions would then be mis-read as one worker’s sequence). Same start equality supports both logging and sharing hypotheses.

3. **All ends equal, starts staggered (G3 pattern) vs bulk entry (G6 pattern)**: Both show fan-in to common end; could be (a) end-batch physical synchronization (e.g., oven batch, G1-like but at end), (b) bulk form submission logging batch (G3/G6 truth), (c) queue accumulation + simultaneous release (e.g., gate opens). G3 (starts spread, ends equal, small `recorded_at` lag) vs G6 (both start/end equal) are ends of continuum; gradual shift in `merge_distance` merges them both as “simultaneous-end batch” in PM4Py, yet operational response differs completely (approve batch vs fix data-entry workflow).

General robustness lesson: PM4Py batch discovery is **threshold-dependent**. Example: `merge_distance=0` sec: G4/G8 sequential remain sequential, G1 simultaneous persists, but G2 start equality at 1-min precision appears as 4 starts identical to the second (still batch). `merge_distance=60` sec absorbs 1-min tablet/desktop_form quantization into batch labels; `merge_distance=900` sec absorbs G7’s 15-min grid making every cluster look simultaneous. Comparison of at least two distances is required to separate precision artifact from true simultaneity.

# 6. Data-collection redesign

Prioritized by impact on queue/service/bottleneck validity:

1. **Separate execution timestamps from recording timestamps (highest priority).** Store `actual_start` and `actual_complete` (event time) distinct from `recorded_at` / `logged_at` (DB insert) and `submitted_at` (form commit). Implement transactional logging: tablet/desktop_form should auto-save start on case open, complete on per-case button, not folder submit. Fixes G2/G3/G6. Add `recorded_at` always with 1-sec or ms precision independent of display precision.

2. **Resource / badge identity with share detection.** Replace `analyst_pool` shared login with SSO badge swipe, or log `os_user` + `session_id` + `workstation_id` alongside pool account; enforce concurrent session limit logging. For robot cells, log `fixture_id` and `slot_id` and capacity (`fixture_capacity`). Fixes G5 attribution and confirms G1 parallelism (4 slots).

3. **Group / batch identifiers.** Add `batch_id`, `group_id`, `parent_case`, `is_batch_start`, `is_batch_end` fields. PLC should emit `batch_id=RBT-7-20260526-0900` with child `slot` records. Tablet “begin group” should create `group_id` linking 4 inspections but preserving individual start triggers. Allows PM4Py to discover logical batches not just temporal proximity.

4. **Availability / capacity calendar and pause/resume events.** Log `resource_unavailable` intervals (safety check, breaks, downtime) with synchronized clock (NTP) separate from production queue. Log `queue_arrival` from upstream consistently (already present) and `resource_state` (idle/busy/blocked). Fixes G8 queue accumulation misattribution. Sync clocks between safety system and scanner; store `clock_source` and `ntp_offset`.

5. **Timestamp precision metadata as first-class data.** Store raw sensor timestamp at source resolution plus `precision` and `rounding_rule` (floor/ceil/nearest) and `original_timestamp_utc`. Never overwrite raw value with rounded display value. For legacy MES, retain milliseconds internally then derive 15-min bucket; expose both. Add validation flag `is_rounded` if seconds=0 and precision >1 sec. Enables interval-censored analysis for G7.

6. **Source clocks and sequencing integrity.** Enforce NTP across PLC, tablet, desktop, scanner, VDI, MES; log `source_clock` and `ingest_latency`. Preserve `sequence_no` strictly monotonic per source and include it in log; add `event_id` UUID. Use this to order events when timestamps tie (already available for G1/G6 but should be generic).

7. **Workstation capacity and concurrency constraints.** Maintain master data `resource_capacity` and `allowed_concurrency` (RBT-7=4 parallel, T-B=1, etc.) and validate against log: alert if overlap > capacity. This turns physiological impossibility into data-quality rule.

8. **Process-model enrichment.** Log `activity_lifecycle` transition (`start`, `suspend`, `resume`, `complete`, `abort`) per IEEE XES, plus per-item duration vs batch duration. Enables correct service time for batch (batch duration vs sum). Implement PM4Py `start_timestamp` population for all sources (currently missing for G7 if undocumented).

Implementation order: 1  2  3 can be done with application changes without hardware; 4  5  6 require platform/infra; 7-8 are governance.

# 7. Final adjudication

**High confidence interpretation, may use for performance (with noted correction):**

- **G1 – usable as parallel batch:** High confidence genuine simultaneous batch. Use batch-aware analysis: throughput 4/3 min, service per item = batch duration, resource utilization fixture-level. Retain.
- **G4 – usable as faithful sequential:** Highest confidence. Use as-is for waiting/service/bottleneck baseline. Retain without correction.
- **G8 – usable after masking downtime:** High confidence sequential drain after capacity loss. Usable if unavailable calendar 15:00-15:35 annotated; otherwise waiting inflated. Retain with annotation; service times valid.

**Interval-censored / limited use, exclude from point-estimate queue analysis:**

- **G2 – censored start:** Start times invalid; end times valid sequential. Use only `complete` chain for ordering; do not compute per-case waiting on start or concurrent utilization. Requires operational validation that group button indeed logs single start, but evidence strong enough to censor.
- **G3 – censored end:** End (submission) invalid for service; start spread likely valid. Use interval [start, 11:31] for service upper bound. Exclude from bottleneck ranking until per-case submit separated.
- **G7 – fully interval-censored:** Both start/complete quantized to 15-min grid. Exclude from point waiting/service; report only interval bounds. Must validate MES rounding rule before any conclusion.

**Exclude from quantitative performance until redesign or validation:**

- **G6 – exclude:** No execution times captured; bulk logging only. Exclude entirely from waiting/service/utilization; count only as throughput at submission date with flag `logging_batch`. If included, must label waiting as `upper bound` and service as `unknown`.
- **G5 – exclude from individual resource metrics:** Pool-level counts allowed, but per-worker utilization/queue analysis invalid without badge split. Exclude from per-resource bottleneck. Requires operational audit to assign sessions to analysts.

**Requires operational validation before any performance conclusion:** G5 (shared-account truth), G7 (true concurrency vs coarse rounding - need raw MES logs), G2/G3 (confirm button semantics via screen recording or audit). G1 benefits from fixture sensor confirmation but already strong; G8 requires clock sync verification between safety and repair logs.

**Overall guidance:** Do not aggregate G1-G8 into single performance model. Stratify by source and precision. Treat PM4Py `discover_batches` output as screening, then apply `overlap_rate`, `lag`, `sec0` and arrival-gap diagnostics to classify operational vs logging vs coarse batches. Report waiting and service with uncertainty intervals where timestamps are censored, and annotate “capacity loss queue” vs “process queue” to avoid misdirected improvement actions.
