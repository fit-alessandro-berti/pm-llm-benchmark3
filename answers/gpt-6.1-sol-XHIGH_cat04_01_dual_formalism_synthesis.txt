# 1. Assumptions and Interpretation

1. **Comparison domain.** I compare finite, complete, single-case traces of activity completions. Register Deviation is first and Archive Case is last. Containment, analysis, planning, design, release, and archiving are mandatory and occur once. A trace is allowed if some consistent assignment of the omitted case data and inspection outcomes realizes it; known case data would restrict the alternatives externally.
2. **Risk route.** After Analyze Root Cause, an exclusive choice selects either Supervisor Review or a concurrent pair consisting of Quality Review and Regulatory Review. The selected route is fixed for the case. Both high-risk reviews are mandatory, each occurs once, and neither orders the other. No trace may execute both risk alternatives.
3. **Supplier consultation.** A separate exclusive choice selects either a silent skip or one Consult Supplier. Its visible activity can start only after root-cause analysis. This choice is outside the trial loop, so consultation cannot recur with each trial. Release waits for the selected alternative to finish.
4. **Inspection outcomes and termination.** A trial body is Execute Trial followed by Inspect Trial. Choosing the redo branch means that inspection failed: Adjust Parameters is then mandatory before the next trial body. Choosing loop exit means that inspection passed. Thus the last inspection in a completed case is the passing one. Outcomes are not inferred from additional event labels or tested against data. Any finite number of failures is allowed, including zero. Ordinary unbounded loops also admit an infinite succession of failures; eventual passing is an environmental assumption, not a liveness guarantee supplied by either model.
5. **Duplicate labels.** Duplicate visible labels would be permitted syntactically, but I use none: each named activity has one structural leaf/transition in each model. Repeated executions of Execute Trial, Inspect Trial, and Adjust Parameters revisit loop nodes; they are not duplicated nodes. Distinct silent nodes are permitted.
6. **Process-tree approximation.** I use a conservative under-approximation: both Contain Material and Analyze Root Cause must finish before planning, design, approvals, or selected supplier consultation starts. This explicit barrier preserves every required prerequisite but excludes some legal interleavings. POWL retains the original cross-branch dependencies directly.
7. **Concurrency and timing.** “May overlap” means structurally independent branches with no ordering between the relevant activities, subject to their own prerequisites. It permits actual overlap and all compatible completion orders; it does not require simultaneous execution. “As soon as” means enabled once prerequisites finish, without urgency or a resource assumption. Completion-only traces cannot establish actual start times or prove that intervals overlapped; the models specify prerequisite-based enabling rather than timestamp validation.

Notation used below: `RD` = Register Deviation; `CM` = Contain Material; `RC` = Analyze Root Cause; `PV` = Plan Verification; `DC` = Design Corrective Action; `SR` = Supervisor Review; `QR` = Quality Review; `RR` = Regulatory Review; `CS` = Consult Supplier; `ET` = Execute Trial; `IT` = Inspect Trial; `AP` = Adjust Parameters; `RM` = Release Material; `AC` = Archive Case. `B` denotes the approval submodel, `U` the optional supplier submodel, `T` the trial loop, and `τ` a silent action.

# 2. Intended Dependency Specification

Precedence means the source must finish before the target can start. For composite nodes, it relates completion of the source submodel to activation of the target submodel. The table describes the intended behavior before any tree approximation.

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D01 | Case entry / Archive Case | Register Deviation / case completion | Boundary and uniqueness | Register is the first visible activity; Archive is the final visible activity of a complete case. |
| D02 | Register Deviation | Contain Material and Analyze Root Cause | Precedence and parallel fork | Both initial obligations follow registration. |
| D03 | Contain Material | Analyze Root Cause | Concurrency | Neither initial work stream waits for the other. |
| D04 | Contain Material | Plan Verification | Precedence | Planning needs completed containment. |
| D05 | Analyze Root Cause | Design Corrective Action | Precedence | Design needs completed analysis. |
| D06 | Analyze Root Cause | Approval submodel B | Precedence | The risk route is selected after analysis. |
| D07 | Approval submodel B | Supervisor Review OR {Quality Review, Regulatory Review} | Exclusive choice; concurrency inside the high-risk alternative | Exactly one route is selected; both high-risk reviews must complete in either order. |
| D08 | Analyze Root Cause | Optional supplier submodel U | Precedence | Consultation cannot start before analysis. |
| D09 | Optional supplier submodel U | Silent skip OR Consult Supplier | Exclusive optionality, at most once | Case data selects absence or one consultation. |
| D10 | Analyze Root Cause / Contain Material | Plan Verification / Design Corrective Action, B, U | No additional cross-stream precedence | Planning need not wait for analysis; root-cause-dependent work need not wait for containment. |
| D11 | {Plan Verification, Design Corrective Action} | Trial loop T | AND synchronization | The first trial requires both work products. |
| D12 | Execute Trial | Inspect Trial | Sequence within every iteration | Each execution is inspected before the next loop decision. |
| D13 | Failed inspection | Adjust Parameters, then the next Execute Trial–Inspect Trial body | Loop redo | Every failure triggers adjustment and another full trial. |
| D14 | Passing inspection | Trial-loop completion | Loop exit | There is no adjustment or further trial after the passing inspection. |
| D15 | Approval submodel B | Trial loop T | Concurrency | Approvals do not gate trial entry and may finish during or after trial work. |
| D16 | Optional supplier submodel U | Design, planning, B, and T | Concurrency subject to existing prerequisites | Selected consultation may overlap any of these obligations. |
| D17 | {Completed T, completed B, completed U} | Release Material | AND synchronization | Loop completion represents a pass; the chosen approval and supplier obligations must also be discharged. |
| D18 | Release Material | Archive Case | Precedence | Archiving follows successful release. |

# 3. PM4Py Process-Tree Model

Here `SEQ`, `AND`, and `XOR` mean sequence, parallel, and exclusive choice. I use a two-child `LOOP(do, redo)`: the do child executes once, followed by zero or more redo–do repetitions, with implicit silent exit after a do execution. Its visible language is `do (redo do)*`. The notation is explanatory; the Python code constructs the objects directly.

```text
SEQ(
  RD,
  AND(CM, RC),
  AND(
    SEQ(AND(PV, DC), LOOP(SEQ(ET, IT), AP)),
    XOR(SR, AND(QR, RR)),
    XOR(τ, CS)
  ),
  RM,
  AC
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    # label=None creates a silent leaf.
    return ProcessTree(label=label)


def branch(operator, *children):
    parent = ProcessTree(operator=operator)
    for child in children:
        parent.children.append(child)
        child.parent = parent
    return parent


approvals_tree = branch(
    Operator.XOR,
    leaf("Supervisor Review"),
    branch(
        Operator.PARALLEL,
        leaf("Quality Review"),
        leaf("Regulatory Review"),
    ),
)

supplier_tree = branch(
    Operator.XOR,
    leaf(None),
    leaf("Consult Supplier"),
)

trial_tree = branch(
    Operator.LOOP,
    branch(
        Operator.SEQUENCE,
        leaf("Execute Trial"),
        leaf("Inspect Trial"),
    ),
    leaf("Adjust Parameters"),
)

work_tree = branch(
    Operator.SEQUENCE,
    branch(
        Operator.PARALLEL,
        leaf("Plan Verification"),
        leaf("Design Corrective Action"),
    ),
    trial_tree,
)

tree = branch(
    Operator.SEQUENCE,
    leaf("Register Deviation"),
    branch(
        Operator.PARALLEL,
        leaf("Contain Material"),
        leaf("Analyze Root Cause"),
    ),
    branch(
        Operator.PARALLEL,
        work_tree,
        approvals_tree,
        supplier_tree,
    ),
    leaf("Release Material"),
    leaf("Archive Case"),
)
tree.parent = None
```

Each child is attached once, with both its parent's child list and its own parent pointer set explicitly. The loop has exactly two children; its silent exit is implicit. Appending a silent redo alternative could admit repetitions without adjustment, so the redo child is only Adjust Parameters. The third parallel block allows approvals and consultation to overlap planning, design, and any number of trial iterations. Its join prevents release until all three branches finish.

The representational loss is precisely the initial barrier: it adds `RC < PV`, `CM < DC`, `CM < B`, and `CM < U`, including their transitive consequences. Thus planning cannot progress while analysis remains unfinished, and design, either approval route, and selected consultation cannot progress while containment remains unfinished. The supplier-skip decision is also delayed, though that delay is invisible when consultation is absent. These restrictions approximate the independence in requirements 3–6. Trial entry still does not wait for approvals or consultation, and the route choices, consultation count, loop structure, and release join are preserved exactly under the stated abstraction. Every complete tree trace satisfies the intended abstract prerequisites; some intended traces are excluded.

This policy favors a compact model with one node per visible label. The cross-branch pattern does not admit a straightforward nesting of independent stream blocks and joins without extra ordering. I do not claim that every conceivable duplicated or enumerated tree is impossible; such constructions would trade this explicit timing loss for duplicated labels and greater analytical complexity.

# 4. PM4Py POWL Model

`PO(nodes; edges)` denotes a strict partial order. Edges to or from a composite node apply to the entire submodel. The POWL two-child loop has the visible language `do (redo do)*`, with an implicit silent exit after a do execution.

```text
B = XOR(SR, PO({QR, RR}; no edges))
U = XOR(τ, CS)
T = LOOP(PO({ET, IT}; ET < IT), AP)

powl = PO(
  {RD, CM, RC, PV, DC, B, U, T, RM, AC};
  RD < CM, RD < RC,
  CM < PV,
  RC < DC, RC < B, RC < U,
  PV < T, DC < T,
  T < RM, B < RM, U < RM,
  RM < AC
)
Include all transitive consequences of these edges.
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")
supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")
consult = Transition(label="Consult Supplier")
execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
adjust = Transition(label="Adjust Parameters")
release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

# Empty order: both high-risk reviews are required but unordered.
high_route = StrictPartialOrder([quality, regulatory])
approvals = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor, high_route],
)

supplier = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), consult],
)

trial_body = StrictPartialOrder([execute, inspect])
trial_body.order.add_edge(execute, inspect)
trial = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, adjust],
)

nodes = [
    register, contain, analyze, plan, design,
    approvals, supplier, trial, release, archive,
]
powl = StrictPartialOrder(nodes)

required_edges = [
    (register, contain),
    (register, analyze),
    (contain, plan),
    (analyze, design),
    (analyze, approvals),
    (analyze, supplier),
    (plan, trial),
    (design, trial),
    (trial, release),
    (approvals, release),
    (supplier, release),
    (release, archive),
]
for source_node, target_node in required_edges:
    powl.order.add_edge(source_node, target_node)

# Materialize the strict transitive closure instead of assuming that
# add_edge automatically inserts every implied relation.
positions = {id(node): index for index, node in enumerate(nodes)}
size = len(nodes)
reach = [[False] * size for _ in range(size)]
direct_pairs = set()

for source_node, target_node in required_edges:
    i = positions[id(source_node)]
    j = positions[id(target_node)]
    reach[i][j] = True
    direct_pairs.add((i, j))

for k in range(size):
    for i in range(size):
        for j in range(size):
            reach[i][j] = reach[i][j] or (reach[i][k] and reach[k][j])

for i in range(size):
    if reach[i][i]:
        raise ValueError("Cyclic precedence specification")
    for j in range(size):
        if reach[i][j] and (i, j) not in direct_pairs:
            powl.order.add_edge(nodes[i], nodes[j])
```

The high-risk submodel has no edges because either review may execute first or overlap the other. The trial body has its required Execute-to-Inspect edge. At the root, planning and design independently enable the composite trial node; approval and consultation completion are required only at release. The supplier node must complete even when its selected child is silent, which discharges the absent-consultation obligation without adding a visible event.

The intentionally incomparable root-node pairs are exactly: `CM || RC`; `CM || DC, B, U`; `RC || PV`; `PV || DC, B, U`; `DC || B, U`; `B || U, T`; and `U || T`. Each pair belongs to independently progressing obligations and has no narrative prerequisite between its members. Shared prerequisites may delay both members without ordering them against each other. Inside the high-risk route, `QR || RR` is similarly intentional. All other root pairs are ordered directly or transitively. Absence of an edge between XOR alternatives does not make them concurrent: only one alternative executes. The LOOP operator itself sequences its body and redo child.

# 5. Behavioral Witnesses

These are complete visible traces; silent steps are omitted. An unannotated final `IT` represents passing via loop exit. In A3, the first `IT` fails and the second passes. Verdicts use the data abstraction in section 1.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|---|---|---|---|---|---|
| A1 | `RD CM RC PV DC SR ET IT RM AC` | Allowed, low risk | Allowed | Allowed | One passing trial; supervisor approval completes before release; supplier is absent. |
| A2 | `RD RC CM DC PV ET RR IT QR RM AC` | Allowed, high risk | Allowed | Allowed | Trial execution completes before either review completes; Regulatory finishes before Quality, and release waits for both. |
| A3 | `RD CM RC DC PV ET IT AP SR ET CS IT RM AC` | Allowed, low risk with supplier | Allowed | Allowed | Two trial bodies are separated by adjustment. Supervisor review and consultation finish during the trial process; all obligations finish before release. |
| A4 | `RD CM PV RC DC QR RR ET IT RM AC` | Allowed, high risk | Forbidden | Allowed | Planning at event 3 has completed containment as its prerequisite. The tree rejects it at that event because its extra analysis barrier has not finished. This also shows Quality before Regulatory. |
| A5 | `RD RC DC SR CS CM PV ET IT RM AC` | Allowed, low risk with supplier | Forbidden | Allowed | Root-cause-dependent design, review, and consultation finish before containment. The tree first rejects DC at event 3 because of its extra containment barrier. |
| F1 | `RD RC PV CM DC SR ET IT RM AC` | Forbidden | Forbidden | Forbidden | Earliest violation: PV at event 3 precedes completed CM. This violates a cross-branch prerequisite, despite valid case boundaries. |
| F2 | `RD CM RC PV DC QR ET IT RM RR AC` | Forbidden | Forbidden | Forbidden | Earliest violation: RM at event 9 occurs before required RR completes. QR selects the high-risk alternative; one review is insufficient. |
| F3 | `RD CM RC PV DC SR ET IT CS RM AP AC` | Forbidden | Forbidden | Forbidden | Earliest violation: AP at event 11 occurs after release. Release establishes that the preceding inspection passed and the loop exited; adjustment can no longer execute. |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Case boundaries | Register first; Archive follows Release and ends every completed case | Preserved | Preserved | None for complete traces; infinite retries need the stated liveness assumption | No completed case bypasses registration or release. |
| Two initial work streams | Containment and root-cause analysis are independent after registration | Parallel initial block | Unordered CM and RC, each preceded by RD | No loss in their mutual concurrency | Either initial stream may finish first. |
| Split dependencies into planning/design | PV depends only on CM; DC depends only on RC | Both initial activities gate both work products | Separate CM-to-PV and RC-to-DC edges | Tree adds RC-to-PV and CM-to-DC | Legitimate early planning or design is rejected and expected waiting time may be exaggerated. |
| Risk route | After RC, low risk requires SR; high risk requires both unordered QR and RR | Correct XOR and parallel high-risk branch, delayed until CM also finishes | XOR with an unordered high-risk partial order, gated only by RC | Tree adds CM-to-selected-approval ordering; neither model checks risk data | Correct review cardinality is enforced, but the tree delays independent approvals. |
| Approval and trial overlap | Approvals do not gate trials; they gate release | Separate concurrent branches after the barrier | B and T are incomparable | No direct approval-to-trial constraint in either model | Trial work can proceed while approval remains outstanding. |
| Optional supplier consultation | Zero or one CS, after RC; can overlap other work; must finish before release when selected | XOR skip/CS outside loop, concurrent with work and approvals | XOR skip/CS outside loop, with RC-to-U and U-to-RM edges | Tree adds CM-to-CS; supplier-selection data is external in both | No consultation repeats with retries or remains outstanding at release, but the tree delays some valid consultations. |
| Trial prerequisites | Both PV and DC must finish before trial entry | Join of PV and DC before loop | PV-to-T and DC-to-T edges | Correct join; the tree's earlier barrier may indirectly delay readiness | Neither model permits trials without both work products. |
| Repeat-until behavior | ET then IT; every failure gives AP then another body; pass exits | Two-child loop with implicit exit | Two-child loop with implicit exit | Exact finite structural abstraction; neither tests actual outcomes or guarantees eventual exit | Adjustment is excluded after passing exit; data-aware correctness and universal termination need further assumptions. |
| Release synchronization | Passing loop completion, selected approvals, and selected supplier obligation must all finish | Join of the three parallel branches | T, B, and U all precede RM | No missing control-flow release prerequisite | Incomplete high-risk review or consultation cannot be bypassed on a completed trace. |
| Duplicate-label risk | Labels should identify activities without obscuring alternatives | One visible leaf per label | One visible transition per label | No structural duplication in these constructions | Counts and conformance are not confounded by multiple same-labelled nodes; loop executions still legitimately repeat labels. |
| Completion versus interval semantics | Successor starts must follow prerequisite completion; actual overlap is optional | Prerequisite-based abstract enabling | Prerequisite-based abstract enabling | Completion logs alone cannot verify actual start times in either representation | Auditing real start-time violations requires lifecycle events or reliable interval records. |

# 7. Preferred Representation and Validation Plan

POWL is the canonical representation because its root partial order expresses the independent prerequisite and release joins without the process tree's initial barrier. The tree is suitable only as a documented conservative simplification, not as an exact conformance baseline. Under the assumptions above, the claimed language relation is:

`L(tree) ⊊ L(powl) = L(intended finite completion-trace abstraction)`.

A4 and A5 witness the strict inclusion. The equality for POWL follows from the matching prerequisite relations, exclusive route and supplier choices, trial language, and final synchronization; soundness or eight successful trace tests alone would not prove that equality.

The concrete validation plan is:

1. **Convert both models to accepting Petri nets.** Use `pm4py.convert_to_petri_net(model)` to obtain `net, im, fm` where supported. Record the PM4Py version and conversion route. If a release does not support POWL conversion through this interface, use its supported POWL converter or explicitly report that the conversion check is unavailable; do not treat API failure as a behavioral verdict.
2. **Check net soundness.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`. Inspect option to complete, proper completion, and absence of dead transitions. For these small nets, independently enumerate reachable markings and check that every reachable marking can reach the final marking, that reaching the final token placement leaves no additional tokens, and that every transition can occur. This also avoids relying exclusively on numerical invariant calculations. Soundness establishes completion availability, not guaranteed eventual passing.
3. **Bounded and sampled playout.** Enumerate or sample both risk routes, both supplier choices, and one, two, and three trial iterations. With at most two failures, the longest complete trace has 18 visible events. Use `pm4py.play_out` with appropriate local-version parameters for additional sampled runs, while bounding both visible events and internal steps. Check each generated complete trace against an independent oracle: mandatory counts, exactly one approval alternative, at most one CS, the projected trial language `ET IT (AP ET IT)*`, all prerequisite inequalities, and the release join. Bound incomplete runs explicitly instead of silently calling them complete.
4. **Exact positive and negative tests.** Test all eight witnesses against both converted nets. Explore states of the form `(marking, trace position)`: a matching visible transition consumes one event; a silent transition consumes none. Accept only when the entire trace is consumed and the exact final marking is reached, allowing any necessary silent steps. This is an acceptance test, rather than a repaired alignment that can hide violations through model or log moves. Add prerequisite-order mutations and release-before-obligation mutations. Specifically reject consecutive trial bodies without intervening Adjust Parameters, to detect an unintended silent redo path. Expect the tree's deliberately excluded positive cases to fail only its own acceptance test.
5. **Silent behavior and label identity.** Explore silent closures and check for reachable silent-only cycles that could cause internal divergence. Confirm the skip branch discharges U without CS, while the selected consultation branch cannot be skipped at release. Count visible leaves/transitions by label in both source models and converted nets: each should have exactly one node per activity. Verify that repeated trial firing does not repeat consultation or approvals, and that silent choices cannot combine low- and high-risk routes.
6. **Limits of validation.** Bounds and sampling do not establish behavior for arbitrarily many failures. Exhaustive net reachability can establish finite-state net properties but does not establish fidelity to omitted data, real activity intervals, or universal termination of an unbounded failure sequence. Successful construction and conversion establish executable syntax, not correspondence to the narrative. Changes to the PM4Py version require rerunning the checks.

Local verification of the displayed constructions successfully converted both models, and PM4Py's soundness checker reported true for both. Independent exhaustive reachable-marking audits found 91 states for the tree net and 114 for the POWL net. Both were 1-safe, had proper terminal completion, allowed completion from every reachable marking, had no dead transitions, and had no reachable silent-only cycles. This independently corroborated the checker despite a numerical invariant-solver warning. Silent-aware exact replay matched all eight verdicts and rejected unadjusted repetition. Each net had exactly one visible transition for each of the fourteen activity labels.

In 1,000 bounded random walks per net, using an 18-visible-event and 200-internal-step limit, 866 tree runs and 849 POWL runs completed; every completed run satisfied the independent intended-behavior oracle. Both samples covered all twelve combinations of risk route, supplier presence, and one to three trials. The remaining walks were explicitly recorded as incomplete at the bound, not accepted as completed cases.

# 8. Final Self-Critique

1. The outcome abstraction can accept a structurally passing exit even when an actual recorded inspection failed; it also permits endless failure runs. Explicit outcome data and a separate eventual-success assumption are needed for stronger semantics.
2. Completion-only traces preserve permitted orders but cannot demonstrate actual overlap or audit whether an activity started before its prerequisite finished. Lifecycle or interval information is needed for that purpose.
3. The process tree deliberately loses valid early progress. Its conservative language can therefore produce false conformance failures and distorted waiting-time conclusions even if its implementation and converted net pass every structural check.
