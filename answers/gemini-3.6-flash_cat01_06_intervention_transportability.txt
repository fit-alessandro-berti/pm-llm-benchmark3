### Causal Mechanism and Transportability Analysis
The structural causal model reveals that while the core mechanism—`treatment_parallelization` driving `true_overlap` to reduce `waiting_before_assessment` and overall `cycle_time`—is nominally shared, the causal path is strongly mediated and moderated by site-specific context variables. 

At Site A, `true_overlap` was enabled by high `digital_documents` (90%), multi-user IT infrastructure, cross-trained staff, and co-interventions (`API_latency` reduction and `queue_huddles`). At Site B, selection nodes ($S\_*$) introduce severe structural shifts:
1. **Site-specific mechanisms**: `originals_required` (62%) introduces an exogenous postal delay (median 18h) that physically blocks `Document Check` activation. Furthermore, fixed `role_specialization` and an `IT_case_lock` prevent distinct reviewers from working a case simultaneously without operational workarounds.
2. **Effect modifiers**: `digital_documents`, `IT_case_lock`, `assessment_capacity`, and `originals_required` act as critical effect modifiers. If `IT_case_lock` is active, `treatment_parallelization` produces zero `true_overlap` and merely splits logging events. If `originals_required` is true, parallel task creation cannot start `Document Check` early.
3. **Control-flow fallacy**: A identical target Petri net or control-flow diagram (`+ (Identity, Document)`) guarantees only logical possibility, not operational concurrency. Control-flow models abstract away resource assignment locks, physical document availability, queuing delays, and capacity bottlenecks. Without structural transportability of these underlying mechanisms, control-flow equivalence does not translate to cycle-time reduction.

### Scenario Derivation and Reasoning
- **Scenario 1 (Naive Copy)**: Enforcing parallel task creation without fixing IT locks forces workers into manual workarounds. The 62% physical cases cannot start document checks anyway. Tasks sit open, inflating system WIP and confusing queue priority, worsening P90.
- **Scenario 2 (Segmented Optimistic)**: By isolating digital claims (38%) for full parallelization and running `Identity Check` during the 18h `Originals Receipt` window for physical claims (62%), Site B recovers 5–8 hours of median wait time without violating statutory rules.
- **Scenario 3 (Digital Only)**: Zero risk to physical workflows. The 38% digital cases experience a drop from 44h to ~35h median cycle time, translating to an aggregate 3h median reduction across all cases.
- **Scenario 4 (Bottleneck Shift - Tail Worsening)**: Parallelizing front-end verification accelerates case arrival at `Assessment`. However, Site B has only 3 Assessors and 2 Legal Reviewers. Batched arrivals saturate the Assessment pool. While median pre-assessment wait drops, queueing *at* Assessment and Legal Review explodes, causing P90 to worsen by +8h to +18h.
- **Scenario 5 (Workaround Failure)**: Manual post-logging to bypass IT locks creates batch entries, hidden inventory, and missed verification errors, driving rework up to 20% and stretching the tail.

## 6. Candidate Site B intervention

### Process Specification
1. **Eligibility Rules**:
   - **Segment D (Digital)**: `originals_required == False` (38% of cases).
   - **Segment P (Physical)**: `originals_required == True` (62% of cases).
2. **Concurrent Task Execution**:
   - **Segment D**: Upon `Register`, system automatically creates both `Identity Check` and `Document Check` tasks concurrently.
   - **Segment P**: Upon `Register`, system creates `Identity Check` and `Originals Receipt` tasks concurrently. `Document Check` task is created ONLY upon logging of `Originals Receipt`.
3. **Statutory Prerequisites**:
   - `Document Check` MUST NOT start before `Originals Receipt` event for Segment P cases.
   - `Assessment` MUST NOT start until BOTH `Identity Check` and `Document Check` reach `Complete` state.
4. **Queue and WIP Controls**:
   - Max open verification WIP per reviewer pool: 5 active tasks per FTE.
   - Dynamic queue balancing: If `Assessment` queue exceeds 15 open cases, pause parallel task dispatch and revert temporarily to FIFO single-task dispatch.
5. **Resource Responsibilities**:
   - `Identity Check` $\rightarrow$ Identity Reviewers (4 FTE).
   - `Document Check` $\rightarrow$ Document Reviewers (7 FTE).
   - `Assessment` $\rightarrow$ Assessors (3 FTE).
   - `Legal Review` $\rightarrow$ Legal Reviewers (2 FTE).
6. **Legal Review and Supplement Loops**:
   - If `Legal Review` issues `Request Supplement`: Re-open ONLY `Document Check` (and `Originals Receipt` if new physical evidence required). Do NOT re-open `Identity Check` unless legal explicitly flags identity discrepancy.
7. **Logging Requirements**:
   - System patch required to support multi-user task-level locking (eliminating single-user case lock).
   - Mandatory real-time transition logging (`start`, `complete`, `suspend`) enforced via UI.

### Textual POWL Process Structure
```text
PartialOrder(
  Nodes: {
    Register,
    Choice_Branch(
      Digital: PartialOrder({Identity_Check, Document_Check}),
      Physical: PartialOrder({Identity_Check, Sequence(Originals_Receipt -> Document_Check)})
    ),
    Assessment,
    Choice_Post_Assess(
      Standard: Choice(Approve, Reject),
      Legal_Path: Sequence(
        Legal_Review,
        Loop(
          Body: Choice(Approve, Reject),
          Redo: Sequence(Request_Supplement, Document_Check, Assessment, Legal_Review)
        )
      )
    ),
    Notify
  },
  Edges: {
    Register -> Choice_Branch,
    Choice_Branch -> Assessment,
    Assessment -> Choice_Post_Assess,
    Choice_Post_Assess -> Notify
  }
)
```

### Mechanism vs. Implementation Failure Analysis
The pilot structure explicitly decouples mechanism failure from implementation failure through granular logging and stratified controls. 

An **implementation failure** occurs when the intended process design is not executed correctly in practice—for example, if legacy IT locks force workers to complete tasks sequentially offline and post-enter timestamps, or if reviewers ignore open concurrent tasks. This is directly detected via conformance checking and timestamp analysis: if process mining shows `cases with overlapping verification intervals %` remains near baseline (6%) in the treatment arm despite workflow configuration changes, the failure is purely operational/implementation.

A **mechanism failure** occurs when the treatment is implemented perfectly (conformance is high, true overlap reaches $>70\%$, and front-end wait drops by 6 hours), but overall `cycle_time` fails to improve or overall quality degrades. This happens if the time saved at verification simply shifts cases into a congested downstream queue at `Assessment` or `Legal Review`, or if parallel execution deprives reviewers of contextual checks, causing `rework` to spike. By measuring intermediate duration markers (`waiting_before_assessment`, `assessment_queue_time`) alongside downstream error metrics, the pilot proves whether the underlying causal mechanism validly produces net organizational value.

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

def construct_and_validate_models():
    # -------------------------------------------------------------------------
    # 1. Site A Process Trees (Before and After)
    # -------------------------------------------------------------------------
    # Site A Before: Sequential Register -> Identity -> Document -> Assessment -> Choice -> Notify
    tree_a_before = pm4py.parse_process_tree(
        "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
    )
    
    # Site A After: Parallel verification via AND (+ operator)
    tree_a_after = pm4py.parse_process_tree(
        "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
    )

    # -------------------------------------------------------------------------
    # 2. Convert Site A Trees to Accepting Petri Nets
    # -------------------------------------------------------------------------
    net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(tree_a_before)
    net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(tree_a_after)

    # -------------------------------------------------------------------------
    # 3. Construct Site B Candidate Model using POWL
    # -------------------------------------------------------------------------
    # Define POWL Transitions
    t_reg = Transition(label="Register")
    t_id = Transition(label="Identity Check")
    t_orig = Transition(label="Originals Receipt")
    t_doc = Transition(label="Document Check")
    t_assess = Transition(label="Assessment")
    t_app = Transition(label="Approve")
    t_rej = Transition(label="Reject")
    t_legal = Transition(label="Legal Review")
    t_supp = Transition(label="Request Supplement")
    t_notify = Transition(label="Notify")
    tau = SilentTransition()

    # Front-end Verification Partial Order (Site B Segmented / Parallel logic):
    # Register runs first. Identity Check and Originals Receipt start in parallel.
    # Document Check MUST wait for Originals Receipt.
    # Assessment MUST wait for both Identity Check and Document Check.
    front_nodes = [t_reg, t_id, t_orig, t_doc, t_assess]
    po_front = StrictPartialOrder(nodes=front_nodes)
    
    # Explicit order edges
    po_front.add_edge(t_reg, t_id)
    po_front.add_edge(t_reg, t_orig)
    po_front.add_edge(t_orig, t_doc)
    
    # CRITICAL STRUCTURAL CONSTRAINT: Assessment waits for BOTH Identity Check and Document Check
    po_front.add_edge(t_id, t_assess)
    po_front.add_edge(t_doc, t_assess)

    # Outcome Decision Choice (Approve / Reject)
    choice_decision = OperatorPOWL(Operator.XOR, [t_app, t_rej])

    # Legal Review Branch with Supplement Loop:
    # Loop body: Decision; Redo: Request Supplement -> Document Check -> Assessment -> Legal Review
    # Sub-POWL for Redo path
    redo_nodes = [t_supp, t_doc, t_assess, t_legal]
    po_redo = StrictPartialOrder(nodes=redo_nodes)
    po_redo.add_edge(t_supp, t_doc)
    po_redo.add_edge(t_doc, t_assess)
    po_redo.add_edge(t_assess, t_legal)

    # Legal Loop: Operator.LOOP (Children: [Body, Redo])
    legal_loop = OperatorPOWL(Operator.LOOP, [choice_decision, po_redo])
    
    # Legal Path: Legal Review -> Legal Loop
    po_legal_path = StrictPartialOrder(nodes=[t_legal, legal_loop])
    po_legal_path.add_edge(t_legal, legal_loop)

    # Decision Path Choice: Standard Choice vs Legal Path Choice
    choice_post_assess = OperatorPOWL(Operator.XOR, [choice_decision, po_legal_path])

    # Top-level POWL Partial Order for Site B
    site_b_powl = StrictPartialOrder(nodes=[po_front, choice_post_assess, t_notify])
    site_b_powl.add_edge(po_front, choice_post_assess)
    site_b_powl.add_edge(choice_post_assess, t_notify)

    # -------------------------------------------------------------------------
    # 4 & 5. Convert POWL Model to Accepting Petri Net
    # -------------------------------------------------------------------------
    net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b_powl)

    # -------------------------------------------------------------------------
    # 6. Check Soundness and Workflow Net Properties
    # -------------------------------------------------------------------------
    is_wfnet_a_before = pm4py.check_is_workflow_net(net_a_before)
    is_wfnet_a_after = pm4py.check_is_workflow_net(net_a_after)
    is_wfnet_b = pm4py.check_is_workflow_net(net_b)

    soundness_a_before = pm4py.check_soundness(net_a_before, im_a_before, fm_a_before)
    soundness_a_after = pm4py.check_soundness(net_a_after, im_a_after, fm_a_after)
    soundness_b = pm4py.check_soundness(net_b, im_b, fm_b)

    print(f"Site A Before - Is WF-Net: {is_wfnet_a_before}, Sound: {soundness_a_before}")
    print(f"Site A After  - Is WF-Net: {is_wfnet_a_after}, Sound: {soundness_a_after}")
    print(f"Site B Model  - Is WF-Net: {is_wfnet_b}, Sound: {soundness_b}")

    # -------------------------------------------------------------------------
    # 7. Playout Sample Traces
    # -------------------------------------------------------------------------
    sim_traces_b = pm4py.play_out(net_b, im_b, fm_b, no_traces=5)
    print("\nSample Simulated Traces from Site B POWL Petri Net:")
    for i, trace in enumerate(sim_traces_b):
        events = [e["concept:name"] for e in trace]
        print(f" Trace {i+1}: {' -> '.join(events)}")

    # -------------------------------------------------------------------------
    # 8. Operational & Modeling Limitations Comments
    # -------------------------------------------------------------------------
    """
    MODELING LIMITATIONS COMMENTARY:
    What this Petri net / POWL control-flow model CANNOT encode:
    1. Data-Dependent Branching: The 62% physical vs 38% digital split and 40% legal requirement
       depend on case attributes (data payload), which pure control-flow nets ignore.
    2. Resource Capacity & Role Allocation: The net allows transitions to fire whenever tokens
       are present, ignoring fixed FTE bounds (4 Identity, 7 Document, 3 Assessors, 2 Legal).
    3. IT Case Locks: The model cannot represent single-user software mutex constraints or UI locks.
    4. Queuing Delays & Durations: Transit times (18h mail wait, service touch times) are non-temporal
       in standard Petri nets; tokens move instantaneously upon transition firing.
```

## 9. Recommendation

`conditional go`

### Operational Justification & Implementation Strategy
A unsegmented, naive direct transfer (`go`) of Site A’s process intervention to Site B will fail due to severe structural incompatibility. Site B operates under strict statutory constraints (62% of claims require physical document originals before inspection), specialized resource pooling (siloed teams), and legacy IT case-locking mechanisms. Blindly opening `Document Check` tasks simultaneously at `Register` across all cases will create phantom queues, administrative bypasses, distorted process metrics, and downstream bottleneck congestion at `Assessment` (3 FTEs) and `Legal Review` (2 FTEs).

However, a total rejection (`no-go`) would needlessly forfeit achievable cycle-time reductions. We recommend a **conditional go**, transferring *only* the structural concurrency mechanism under strict segmentation, workflow modifications, and IT safeguards.

#### What Should Be Transferred
- Concurrent execution of `Identity Check` and `Document Check` **exclusively** for Segment D (38% purely digital claims).
- Concurrent execution of `Identity Check` alongside `Originals Receipt` mail waiting for Segment P (62% physical claims), allowing identity verification to complete while awaiting physical mail.

#### What Should NOT Be Copied
- Unconditional creation of `Document Check` at `Register` for physical claims.
- Cross-trained flexible task grabbing (Site B staff must remain in role-specific pools until cross-training is formally conducted).
- Uncapped open task limits per worker.

#### Initial Subgroup Entry & Rollout Phasing
Phase 1 must enter exclusively with **Segment D (Digital Claims without Legal Review required)**. This represents low-risk, high-yield volume where the causal mechanism directly mirrors Site A without statutory impediment.

#### Expected Benefits & Operational Risks
- **Expected Benefits**: 5 to 8-hour median cycle-time reduction on digital cases (aggregate 2.5 to 4-hour median reduction across total volume); reduction of pre-assessment wait from 20h to ~14h.
- **Operational Risks**: Queue shifting to the small Assessor pool (3 FTEs); IT post-logging workarounds degrading event log integrity; potential minor increase in rework if reviewers lose cross-verification context.

#### Evidence Triggers for Expansion, Modification, or Abandonment
- **Trigger for Expansion (Phase 2 - Segment P)**: Pilot demonstrates $\ge 70\%$ true log overlap in Segment D with zero increase in 90-day appeals and $<2\%$ increase in rework.
- **Trigger for Modification**: Assessment queue wait increases by $>20\%$. *Action*: Implement dynamic WIP caps on front-end parallel task dispatching.
- **Trigger for Abandonment**: IT system lock cannot be patched, resulting in $<20\%$ genuine task overlap and continuous manual timestamp back-entry workarounds; OR rework rate exceeds 20%.

## 10. Assumption register

1. **Statutory Document Prerequisite Rigidity** — The requirement that original physical documents must be received prior to `Document Check` for 62% of claims is a hard statutory rule that cannot be legally bypassed or deferred. — Test via audit of legal compliance guidelines and regulatory frameworks at Site B. — If false, `Document Check` could begin provisionally on digital copies for physical cases, increasing parallelization yield.

2. **IT Case-Lock Patchability** — The legacy case management software can be patched or configured via middleware to allow two distinct users to hold active task locks on separate sub-tasks of the same Case ID concurrently. — Test via IT sandbox simulation of dual-user concurrent editing. — If false, true parallel execution by specialized pools is impossible; tasks will be executed sequentially offline, rendering metrics invalid.

3. **Resource Pool Non-Flexibility** — Staff in Identity, Document, Assessment, and Legal pools cannot be cross-assigned on demand without formal labor agreements and retraining. — Test via operational HR resource allocation logs and cross-training matrix. — If false, management can dynamically flex capacity to clear emerging Assessment bottlenecks.

4. **Digital Segment Data Integrity** — The metadata flag `originals_required` is accurately populated in the case management system at `Register` with 100% reliability. — Test via process mining conformance checks comparing system flags against physical mail arrival logs. — If false, physical cases will be misrouted into parallel document checking, causing compliance breaches.

5. **Assessor Pool Capacity Threshold** — The 3 Assessor FTEs currently operate near capacity and will experience queue inflation if upstream verification completions arrive in batched parallel bursts rather than a steady sequential stream. — Test via baseline queueing theory models ($M/M/c$) driven by arrival rate distribution analysis. — If false, downstream bottleneck shifting will not occur, allowing larger median cycle time gains.

6. **Independence of Verification Checks** — `Identity Check` and `Document Check` rely on independent data sources such that performing them concurrently does not degrade verification accuracy or increase error rates. — Test via retrospective regression analysis of historical error logs comparing sequential error overlap against independent error rates. — If false, rework and appeal rates will spike significantly under parallel execution.

7. **Timestamp Logging Fidelity Post-Patch** — Once the IT lock is patched, task start and completion event timestamps captured in the log will reflect true human work execution rather than delayed batch entry. — Test via random observational time studies cross-referenced against event log timestamps during pilot burn-in. — If false, process mining metrics cannot be trusted for causal inference.

8. **Exogenous Arrival Mix Stability** — The incoming ratio of complex cases (48%), physical document claims (62%), and legal review requirements (40%) will remain stationary during the pilot period. — Test via weekly statistical process control (SPC) charts on incoming claim attributes. — If false, cycle time changes during the pilot may be confounded by exogenous mix shifts rather than the intervention.
