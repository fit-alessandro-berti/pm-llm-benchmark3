- Freeze all retraining pipelines. Add a feature-pipeline health gate: any month with `Unknown activity share > 5%` or `Missing queue feature > 5%` is automatically quarantined from training.

**Stage 2 — Short-term recalibration (after pipeline repair, ~2 weeks).**
- After (3b) confirms Apr/May features are clean, recompute. If metrics return to baseline, only a recalibration (isotonic regression per variant) is needed for Apr–Jun.
- For Jul, a mild recalibration may suffice if V3 breach rise is captured by the existing V3-relevant features.
- Use **only Jan–Jun data** for recalibration; do not include Jul+ yet because the concept drift signature is unclear until Aug–Sep maturity.

**Stage 3 — Feature repair and segment-specific modeling (1–2 months).**
- Add `Order Part  Part Received` rolling median and `rural_distance` and `device_age` as first-class features.
- Train a **segment-specific model for V3** (and a second one for Partner Z) using Jul–Sep data **with at least 90-day label vintage**. Justification: V3 dynamics changed most, and Partner Z has features the original model never saw.
- Keep a global model for V1/V2 (their breach rates are stable).

**Stage 4 — Full retraining (only after Oct maturity).**
- Do not use Jul–Oct data naively. Only after the Oct cohort reaches 90% maturity can Oct be included.
- A complete retrain is justified only if Stage 3 segment-specific models still show global ECE deterioration.

**Training-safety verdict by month.**
- **Safe:** Jan, Feb, Mar (fully mature, clean pipeline).
- **Safe after repair:** May, Jun (after pipeline + duplicate cleanup; Jun is a process-mix month, so apply variant reweighting).
- **Use with stratification and reweighting:** Jul, Aug, Sep.
- **Unsafe until vintage  90 days:** Oct.
- **Do not use:** Apr (pipeline), or any month with unknown-activity share > 5%.

**Segment-specific model justification:** Yes. V3 breach moved from 0.30 to 0.61–0.64 within three months; Partner Z cases have features (rural distance, device age) that the original model never ingested; the global ECE is dominated by V3. A V3-specific (and Partner-Z-specific) model is justified on both statistical (heteroscedastic outcomes) and operational (interpretability for routing) grounds.

## 5. Monitoring architecture

The monitoring system has eight monitors with explicit alert dependencies to prevent cascading false alarms.

1. **Predictive performance monitor** — weekly AUROC, Brier, PR-AUC, on a rolling 4-week window, stratified by variant and source.
2. **Calibration monitor** — ECE per segment, reliability diagrams; alert when ECE |.| > 0.05 for two consecutive weeks **and** label maturity > 85%.
3. **Label-maturity monitor** — % of cases with outcome label older than N days; median label delay. **Routes to:** data-engineering alert and a *soft* recalibration trigger; **does not** trigger retraining by itself.
4. **Data-quality monitor** — unknown activity share, missing queue feature rate, duplicate-event count, lineage checksum for the diagnosis-prefix feature.
5. **Process-variant monitor** — V1/V2/V3 distribution; alert at 3 shift. Outputs both case-start-cohort and event-calendar-cohort views (these are **not** the same).
6. **Performance-DFG monitor** — median and 90th-percentile edge times for `Order Part  Part Received`, `Triage  Initial Diagnosis`, `Dispatch  Repair`. Alert when median > 2× baseline.
7. **Population monitor** — Partner Z share, source mix, PSI on every input feature, missingness rate per feature.
8. **Intervention/deployment monitor** — model version in production, prediction volume, fraction of flagged "untrusted" predictions, A/B holdout.

**Alert dependency graph.**
- `data-quality alarm`  **suppress** calibration/concept-drift alarms (a pipeline bug mimics drift).
- `label-maturity alarm`  route only to **recalibration** path; **block** retraining until maturity  85%.
- `process-variant alarm`  trigger **stratified re-evaluation**; do not retrain by itself.
- `performance-DFG alarm + label-maturity alarm` together  escalate to retraining review.
- `population alarm` (PSI > 0.2)  trigger **reweighting check** and Partner-Z-specific evaluation.

import pandas as pd
import pm4py

# --- 1. Read and format ---
df = pd.read_csv(
    "field_service_events.csv",
    dtype={"case_id": str, "activity": str, "resource": str},
)
df["timestamp"] = pd.to_datetime(df["timestamp"], utc=True)
df = pm4py.format_dataframe(
    df,
    case_id="case_id",
    activity_key="activity",
    timestamp_key="timestamp",
)

# --- 2. Normalize the renamed diagnosis label ---
DIAGNOSIS_ALIASES = {
    "Initial Diagnosis Completed",
    "Diagnostic Assessment Completed",
    "Diagnosis Completed",
}
df["concept:name"] = df["concept:name"].apply(
    lambda x: "DIAGNOSIS_COMPLETED" if x in DIAGNOSIS_ALIASES else x
)

# --- 3. Duplicate-handling strategy ---
# (a) audit: how many duplicates per (case, activity, timestamp)?
dup_mask = df.duplicated(subset=["case:concept:name", "concept:name", "time:timestamp"], keep=False)
df["is_duplicate"] = dup_mask
# (b) keep first occurrence; flag the rest for the data-quality monitor
df = df.sort_values(["case:concept:name", "time:timestamp"])
df = df.drop_duplicates(
    subset=["case:concept:name", "concept:name", "time:timestamp"], keep="first"
)
# (c) keep UNKNOWN_ACTIVITY visible for monitoring but exclude from DFG
unknown_mask = df["concept:name"] == "UNKNOWN_ACTIVITY"
df_clean = df[~unknown_mask].copy()

# --- 4. Two cohort views (NOT interchangeable) ---
# Event-calendar cohort: any case with activity in the month
# -> good for throughput / activity-volume monitors.
def event_calendar_cohort(log, start, end):
    return pm4py.filter_time_range(log, start, end, mode="events")

# Case-start cohort: cases whose first event is in the month
# -> matches how the prediction model is invoked (Case Created -> ...).
def case_start_cohort(log, start, end):
    return pm4py.filter_time_range(log, start, end, mode="traces")

# --- 5. Monthly auditable summaries ---
def monthly_summary(month_log, label):
    n_cases = month_log["case:concept:name"].nunique()
    dfg, start_acts, end_acts = pm4py.discover_dfg(month_log)
    perf_dfg = pm4py.discover_performance_dfg(month_log)
    variants = pm4py.get_variants(month_log)
    top_variant = max(variants.values()) / n_cases if variants else 0.0
    # Variant share as % of cases (auditable, not just model output)
    variant_share = {v: c / n_cases for v, c in variants.items()} if variants else {}
    return {
        "month": label,
        "n_cases": n_cases,
        "n_activities": len(month_log),
        "n_variants": len(variants),
        "top_variant_share": top_variant,
        "variant_share": variant_share,
        "dfg_edges": len(dfg),
        "perf_dfg_edges": len(perf_dfg),
    }

# --- 6. Prediction-point features (just after diagnosis) ---
def prediction_point_features(case_log):
    diag_cases = case_log[case_log["concept:name"] == "DIAGNOSIS_COMPLETED"]
    return pm4py.extract_temporal_features_dataframe(diag_cases, granularity="1h")

# --- 7. Drive the audit ---
MONTHS = [(f"2026-{m:02d}-01", f"2026-{m:02d}-28") for m in range(1, 11)]
audit_rows = []
for start, end in MONTHS:
    start_cohort = case_start_cohort(df_clean, start, end)
    audit_rows.append(monthly_summary(start_cohort, start[:7]))
audit_df = pd.DataFrame(audit_rows)

# Note: we deliberately do NOT invent a pm4py drift detector.
# We rely on month-over-month diffs on:
#   - variant_share
#   - perf_dfg edge times (read from perf_dfg dicts)
#   - data-quality flags (dup counts, unknown share)
# downstream (e.g., PSI, control charts, fixed-vintage backtests).

## 6. Risks of acting on the wrong diagnosis

**Risk 1: Retraining on October's immature labels.**
Acting on October's observed breach rate (0.16) would push the model toward *lower* predicted risk, exactly opposite to the supplier-driven reality (V3 breach  0.60). The model would become dangerously under-confident on the highest-risk path precisely when V3 share is rising.
- *Mitigation:* block Oct from training until 90-day vintage; route any "Oct alarm" through the label-maturity monitor first; require a fixed-vintage backtest before accepting any Oct-sourced weights.

**Risk 2: Calibrating around April's pipeline bug.**
Treating April's miscalibration as the new normal and running isotonic regression on it would lock in a calibration curve that compensates for missing/unknown features rather than for real risk shift. After May's patch, the calibration would be wrong twice — first for the bug, then for the overcorrection.
- *Mitigation:* quarantine Apr from training entirely; the data-quality alarm must suppress calibration signals; rebuild features and verify Apr metrics against Jan–Mar before allowing Apr to enter any training set.

**Risk 3: Ignoring genuine supplier-driven concept drift in August–September.**
If we attribute August–September deterioration entirely to Partner Z population shift, we will miss that V3 cases *across all sources* now breach at 0.60+. A model that only fixes Partner Z will remain dangerously miscalibrated on the V3 majority. The under-confidence (mean pred 0.19 vs obs 0.28) is the opposite signature from April's over-confidence; conflating them produces a confused remediation.
- *Mitigation:* require both (a) same-path conditional breach-rate comparison and (b) stratified calibration per variant *before* accepting any population-shift hypothesis; ship a V3-specific recalibration independent of Partner-Z actions.

**Risk 4: Attributing Partner Z's population shift to "unfair" model behavior without stratified evidence.**
Partner Z's 0.45 vs 0.27 breach gap looks like bias, but Partner Z labels mature more slowly and Partner Z is concentrated in the most-drifted variant (V3). Without stratification, "fairness remediation" (e.g., reweighting) could mask supplier-driven risk and delay needed supplier interventions.
- *Mitigation:* require three pieces of evidence before any fairness action — (i) Partner Z vs others at matched OrderPart times, (ii) Partner Z vs others at fixed 90-day vintage, (iii) whether adding `rural_distance` and `device_age` closes the gap. Only after stratified evidence should a segment-specific model or reweighting be deployed.

**Risk 5 (additional): Conflating process drift with concept drift.**
June's V2 mix-up is process drift that the global model can absorb. Treating it as concept drift and retraining would cause overfitting to a transient policy change. Conversely, August's V3 mix-up is partly process drift *and* partly concept drift; treating only the variant-share change without recognizing the same-path breach-rate shift would under-correct.
- *Mitigation:* keep process-variant and performance-DFG monitors separate from calibration monitors; require both to fire before retraining is approved; default action for variant-mix alarms is stratified re-evaluation, not retraining.

**Risk 6 (additional): Acting on Partner Z's Sep breach gap before rural/age features exist.**
Any decision (reweighting, threshold change, segment model) that uses Partner Z data without the rural-distance and device-age features will misattribute the breach gap to model unfairness rather than to genuine covariate mismatch.
- *Mitigation:* instrument the missing features first; do not file Partner Z as a model-bias incident until those features are live and stratified evidence is in hand.
