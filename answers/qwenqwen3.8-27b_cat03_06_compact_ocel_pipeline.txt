def validate_ocel_frames(events, objects, relations, o2o):
    assert events[EID].is_unique, "event IDs are not unique"
    assert objects[OID].is_unique, "object IDs are not unique"
    assert not relations[EID].isna().any(), "relations contain missing event IDs"
    assert set(relations[EID]).issubset(set(events[EID])), "orphan event IDs in relations"
    assert set(relations[OID]).issubset(set(objects[OID])), "orphan object IDs in relations"
    assert set(o2o[OID]).issubset(set(objects[OID])), "orphan source object IDs in O2O"
    assert set(o2o[OID2]).issubset(set(objects[OID])), "orphan target object IDs in O2O"
    merged = relations.merge(events[[EID, ACT, TS]], on=EID, how="left", suffixes=("_rel", "_evt"), validate="many_to_one")
    assert (merged[ACT + "_rel"] == merged[ACT + "_evt"]).all(), "activity mismatch between events and relations"
    assert (pd.to_datetime(merged[TS + "_rel"], utc=True) == pd.to_datetime(merged[TS + "_evt"], utc=True)).all(), "timestamp mismatch"
    assert not relations.duplicated().any(), "duplicate relation rows"
    assert not relations.duplicated(subset=[EID, OID, QUAL]).any(), "duplicate event-object-qualifier relations"
    type_map = objects.set_index(OID)[TYPE]
    assert (relations[TYPE] == relations[OID].map(type_map)).all(), "object type mismatch in relations"
    print("Validation passed: unique IDs, referential integrity, consistency, no duplicate relations.")

## 1. Modeling assumptions

- **Object types and capitalization:**  
  `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.

- **E2O qualifier vocabulary:**  
  The event-to-object qualifiers use object-role names, with an `affected_` prefix for operationally affected downstream objects:
  - `order`: explicit order participant, e.g., create order, add item, issue invoice, record payment, close order.
  - `affected_order`: order operationally affected through a package or delivery, e.g., dispatching or confirming a package that contains items from that order.
  - `item`: explicit item participant, e.g., add item, reserve stock, pack package.
  - `affected_item`: item operationally affected through a package or delivery, e.g., dispatch or confirmation of a package containing the item.
  - `package`: explicit package participant, e.g., pack package, dispatch package.
  - `affected_package`: package operationally affected through a delivery, e.g., confirm delivery of a delivery that carries the package.
  - `delivery`: explicit delivery participant, e.g., dispatch package, confirm delivery.
  - `invoice`: explicit invoice participant, e.g., issue invoice, record payment.
  - `payment`: explicit payment participant, e.g., record payment.

- **O2O direction conventions:**  
  `ocel:oid` is the source/owner object, and `ocel:oid_2` is the target/dependent object.  
  Qualifiers are:
  - `contains`: Order contains Item.
  - `packs`: Package packs Item.
  - `carries`: Delivery carries Package.
  - `bills`: Invoice bills Order.
  - `partially_settles`: Payment partially_settles Invoice.

- **Logistics and financial event relations:**  
  - Logistics events (`Pack Package`, `Dispatch Package`, `Confirm Delivery`) relate to Orders and Items. `Pack Package P1` explicitly relates to both Orders. Downstream logistics events use `affected_order`, `affected_item`, and `affected_package` where the object is not the primary named event object but is operationally involved.
  - Financial events (`Issue Invoice`, `Record Payment`) relate to Orders, Invoice, and Payment, but not directly to Items. This avoids inflating every item with invoice/payment events. Item-level financial state can be derived analytically through `Order contains Item` if needed.
  - Payment amounts are stored as event attributes in `events.ocel:amount`, not as separate objects.

- **Preventing analytical propagation from being confused with source facts:**  
  The `relations` frame contains only the explicit E2O modeling decisions made above. It does not contain rows generated by automatically traversing O2O relations. If an analyst later derives additional links, for example `Dispatch Package P1 -> O100` through `P1 packs I1` and `O100 contains I1`, those derived links should be stored in a separate derived frame or marked with distinct `derived_*` qualifiers. In this construction, downstream logistics links are explicit modeling assertions and are visibly marked with `affected_*` qualifiers.

- **Version-dependent PM4Py assumption:**  
  The pipeline assumes an OCEL constructor of the form:

  ```text
  OCEL(events=events, objects=objects, relations=relations, o2o=o2o)
  ```

  and the PM4Py OCEL analysis functions named in the task. The OCEL construction line is isolated in the code. If a PM4Py release exposes the class or functions differently, only the import/constructor or function-call layer should be adjusted; the four DataFrames remain the semantic contract.

## 4. Expected flattened behavior

**Order flattening**

- **Approximate trace shape:**
  - O100: 14 events: Create Order, Add Item, Add Item, Reserve Stock, Pack Package, Pack Package, Dispatch Package, Dispatch Package, Issue Invoice, Record Payment, Confirm Delivery, Confirm Delivery, Record Payment, Close Order.
  - O200: 10 events: Create Order, Add Item, Reserve Stock, Pack Package, Dispatch Package, Issue Invoice, Record Payment, Confirm Delivery, Record Payment, Close Order.
- **Copied shared events:** E006, E007, E009, E011, E012, E013, and E015 appear in both O100 and O200 flattened logs.
- **Omitted lifecycle aspects:** the flattened Order log loses explicit object identities unless they are carried as event attributes. It does not show the O2O structure, for example which item is in which package or which package is in which delivery.
- **Likely DFG edges:**
  - Create Order  Add Item
  - Add Item  Add Item, due to O100 having I1 then I2
  - Add Item  Reserve Stock
  - Reserve Stock  Pack Package
  - Pack Package  Pack Package, due to O100 having P1 then P2
  - Pack Package  Dispatch Package
  - Dispatch Package  Dispatch Package, due to O100 having P1 then P2
  - Dispatch Package  Issue Invoice
  - Issue Invoice  Record Payment
  - Record Payment  Confirm Delivery
  - Confirm Delivery  Record Payment
  - Confirm Delivery  Confirm Delivery, due to O100 having D1 then D2
  - Confirm Delivery  Close Order, mainly from O200
  - Record Payment  Close Order
- **Misleading interpretations:** self-loops such as Add Item  Add Item, Pack Package  Pack Package, Dispatch Package  Dispatch Package, and Confirm Delivery  Confirm Delivery are caused by O100 having multiple items/packages/deliveries, not by a general repeated lifecycle. The cycle Record Payment  Confirm Delivery reflects interleaving of M1, D1 confirmation, and M2, not necessarily causal dependency.

**Package flattening**

- **Approximate trace shape:**
  - P1: Pack Package, Dispatch Package, Confirm Delivery.
  - P2: Pack Package, Dispatch Package, Confirm Delivery.
- **Copied shared events:** P1 events are also present in O100 and O200 logs; P2 events are also present in O100.
- **Omitted lifecycle aspects:** no order creation, item addition, invoice issuance, payment recording, or order closing.
- **Likely DFG edges:** Pack Package  Dispatch Package  Confirm Delivery.
- **Misleading interpretations:** P1 appears as a simple independent package lifecycle. The fact that P1 combines items from O100 and O200 is not visible in the flattened Package log itself.

**Delivery flattening**

- **Approximate trace shape:**
  - D1: Dispatch Package, Confirm Delivery.
  - D2: Dispatch Package, Confirm Delivery.
- **Copied shared events:** D1 events are also present in P1, O100, and O200 logs; D2 events are also present in P2 and O100 logs.
- **Omitted lifecycle aspects:** no package packing, item reservation, order creation, invoice, payment, or order closing.
- **Likely DFG edges:** Dispatch Package  Confirm Delivery.
- **Misleading interpretations:** the delivery lifecycle appears to begin at dispatch. Upstream package and order context is absent.

**Invoice flattening**

- **Approximate trace shape:** V1: Issue Invoice, Record Payment, Record Payment.
- **Copied shared events:** all three invoice events are also present in O100 and O200 logs.
- **Omitted lifecycle aspects:** no logistics events, no order closing, and no explicit allocation of payments to individual orders.
- **Likely DFG edges:** Issue Invoice  Record Payment, Record Payment  Record Payment.
- **Misleading interpretations:** the Record Payment  Record Payment edge may suggest that payments are strictly sequential lifecycle steps of the invoice. In reality, M1 and M2 are partial settlements of the same invoice, and the flattened log does not show how much of each order is settled by each payment.

**Why Payment flattening is particularly weak here**

Flattening on `Payment` produces M1 and M2 as single-event traces. Each payment has only one activity, `Record Payment`. A DFG over such traces is trivial: one activity per case, no meaningful direct-follow structure, and no lifecycle progression. Payment flattening cannot show partial settlement behavior, settlement order, or allocation to O100/O200. Those insights require object-centric views or O2O traversal.

## 5. Expected object-centric structures

**OC-DFG**

The OC-DFG should reveal cross-object activity transitions rather than a single object-type log. Expected insights include:

- O100 has a richer logistics branch than O200 because O100 contains both I1 and I2, leading to P1 and P2, then D1 and D2.
- O200 has only I3, so its logistics branch goes through P1 and D1 only.
- P1 is a convergence object: it connects I1 and I3, and therefore O100 and O200, through Pack Package, Dispatch Package, and Confirm Delivery.
- V1 is a financial convergence object: it connects O100 and O200 through Issue Invoice, M1, and M2.
- M1 and M2 appear as sequential Payment objects under V1, with M1 before M2.
- The financial branch and logistics branch interleave: Issue Invoice and Record Payment occur between dispatch and delivery confirmation.

**OTG**

The object-type graph should show the core O2O structure:

- Order  Item via `contains`.
- Package  Item via `packs`.
- Delivery  Package via `carries`.
- Invoice  Order via `bills`.
- Payment  Invoice via `partially_settles`.

Depending on implementation, event-induced OTG edges may also appear, for example:

- Order  Package through Pack/Dispatch/Confirm events.
- Order  Delivery through Dispatch/Confirm events.
- Item  Package through Pack/Dispatch/Confirm events.
- Package  Delivery through Dispatch/Confirm events.

Instance-level reading: P1 sits between I1/I3 and D1; V1 sits between O100/O200 and M1/M2.

**ET–OT graph**

The event-type-to-object-type graph should show which activities are integration points:

- Create Order touches Order only.
- Add Item touches Order and Item.
- Reserve Stock touches Order and Item.
- Pack Package touches Order, Package, and Item.
- Dispatch Package touches Order, Package, Delivery, and Item.
- Issue Invoice touches Invoice and Order.
- Record Payment touches Payment, Invoice, and Order.
- Confirm Delivery touches Order, Package, Delivery, and Item.
- Close Order touches Order only.

This reveals that Pack, Dispatch, Confirm Delivery, and Record Payment are the most object-crossing activities.

**Object-centric Petri net**

A plausible object-centric Petri net would show:

- Order creation for O100 and O200.
- Item addition branches: O100 adds I1 and I2; O200 adds I3.
- A shared Reserve Stock synchronization for I1 and I3.
- Parallel or interleaved package branches:
  - P1 branch for I1 and I3.
  - P2 branch for I2, relevant only to O100.
- P1 synchronizes O100 and O200 logistics through D1.
- P2 provides an additional O100 logistics branch through D2.
- A financial branch through V1, with M1 and M2 as payment transitions.
- Order closing after delivery confirmations and final payment.

This net does not have one uniquely determined interpretation. For example, M1 and M2 could be modeled as strictly sequential, as parallel with observed timestamp order, or as two alternative partial settlements. P1 and P2 could be modeled as parallel branches or as sequential package processing. The data constrains the net but does not force a single net.

**Object-interactions summary**

The interaction summary should show elevated interactions between:

- Order and Item, from Add Item, Reserve Stock, Pack, Dispatch, and Confirm Delivery.
- Order and Package, from Pack, Dispatch, and Confirm Delivery.
- Order and Delivery, from Dispatch and Confirm Delivery.
- Order and Invoice, from Issue Invoice and Record Payment.
- Order and Payment, from Record Payment.
- Package and Item, from Pack, Dispatch, and Confirm Delivery.
- Package and Delivery, from Dispatch and Confirm Delivery.
- Invoice and Payment, from Record Payment.

Instance-level highlights:

- P1 interacts with O100, O200, I1, I3, and D1.
- P2 interacts with O100, I2, and D2.
- V1 interacts with O100, O200, M1, and M2.
- M1 and M2 each interact with V1, O100, and O200.

## 6. Modeling alternatives

| Alternative policy | E2O modeling choice | Effect on discovery results |
|---|---|---|
| Source-minimal explicit objects | Relate events only to objects explicitly named in the event text. For example, Dispatch Package P1 relates only to P1 and D1; Confirm Delivery D1 relates only to D1. | Order and Item flattened logs become sparser. Order logs may miss dispatch and confirmation events. Package logs may miss confirmation events. OC-DFG and ET–OT show fewer cross-object integration points. O2O propagation becomes necessary to recover the full operational story. |
| Full operational involvement, used here | Include explicit and operationally affected objects. Logistics events relate to affected Orders, Items, Packages, and Deliveries. Financial events relate to Orders, Invoice, and Payment but not Items. | Order, Package, Delivery, and Invoice flattened logs are richer. DFGs show more edges, including self-loops and interleaving cycles. Object-interaction summaries are denser. The risk is relation inflation and misleading sequential dependencies. |
| O2O-propagated analytical relations | Store only source-minimal E2O facts, then compute derived E2O rows by traversing O2O relations before analysis. For example, Dispatch P1 is propagated to I1/I3 through `packs`, then to O100/O200 through `contains`. | Discovery can resemble full operational involvement, but derived links can be kept separate from source facts. This preserves provenance. The risk is over-propagation, for example propagating Invoice or Payment events to Items through Order contains Item, and duplicate events if direct and derived links are both used. |

A fourth defensible variant would extend financial events to Items, for example relating Record Payment to I1, I2, and I3. That would make Item logs include financial completion, but it would also inflate item-level payment activity and may misrepresent item-specific settlement.

## 7. Failure modes

1. **Relation inflation:** Adding every downstream Order, Item, Package, and Delivery to every logistics event can make shared events appear many times across object views and create noisy DFG edges.

2. **Missing direct E2O links:** If Dispatch or Confirm Delivery are not related to Orders, the flattened Order log may miss important fulfillment events, making the Order DFG incomplete.

3. **Treating O2O propagation as observation:** Derived links, such as Dispatch P1  O100 through P1 packs I1 and O100 contains I1, can be mistaken for directly observed source-system facts if not explicitly labeled as derived.

4. **Duplicate shared events after flattening:** If flattening uses both direct E2O links and O2O propagation, the same event may be copied twice into the same object log, creating artificial duplicate transitions.

5. **Ambiguous payment allocation:** M1 and M2 settle V1, and V1 bills both O100 and O200. Without explicit allocation, it is not possible to determine how much of O100 or O200 is settled by M1 versus M2.

6. **Overly short Payment traces:** M1 and M2 each have only one event. Payment flattening therefore produces trivial DFGs and cannot reveal settlement lifecycle behavior.

7. **Constructor/API version mismatch:** Different PM4Py releases may expose OCEL classes, flattening functions, or OC discovery functions under different names or with different parameter expectations. This can break the pipeline even when the data semantics are correct.

8. **False total order for same-time events:** This example has no timestamp ties, but if two events shared the same timestamp, DFG discovery might infer an order based on row order or arbitrary tie-breaking, producing a false sequential dependency.

9. **Object ID/type collisions or case sensitivity:** If object types are inconsistently capitalized, for example `order` versus `Order`, or if object IDs collide across types, flattening and object-type discovery may fail or produce incorrect views.

10. **Naive timestamps or activity/timestamp mismatch:** Mixing naive and timezone-aware timestamps, or allowing relation timestamps to drift from event timestamps, can corrupt ordering and invalidate DFG interpretation.
