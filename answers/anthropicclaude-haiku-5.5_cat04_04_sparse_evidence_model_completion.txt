# 1. Evidence Ledger

Legend for all sections: RO = Register Order, CC = Credit Check, ER = Engineering Review, SC = Supplier Confirmation, EX = Expedite Review, AP = Approve Configuration, RP = Release Production, AR = Archive Case,  = skip (silent).

Before using the DFG, I checked all 16 edge counts against the 7 variants. Every count reproduces exactly (for example, CCSC = 7 from the ER-first variant plus 2 from the CCSCER variant = 9; ERAP = 4 + 2 = 6). The DFG therefore adds no information beyond the variants. **Why both DFG directions do not prove concurrency.** A DFG counts adjacent pairs in completion order. Mutual edges CCER (17 and 11) show that neither order is universal. They are compatible with at least four explanations: (1) concurrency with overlapping execution; (2) sequence with a varying order chosen per case (for example, by staff availability); (3) an XOR choice of order, which is a different hypothesis with the same completion language for this pair; (4) logging artifacts, because completion-only logs with ingestion-index tie-breaking (S7) can reorder truly sequential or truly overlapping events. A loop (ERCCER) would show repeats, and none occur. Concurrency needs start or lifecycle evidence showing overlap; the completion DFG cannot provide it.

# 2. Shared Assumptions

1. **Completion semantics.** Each observed event is an activity completion. A precedence in a model constrains completion order only. "Concurrent" in a model means both completion orders are admitted; it makes no claim about overlapping execution. "Sequence" means one completion order is required.
2. **Start and end.** Every trace starts with RO and ends with AR (D1). Every observed case has RP after AP and AR last.
3. **No repetition.** Each activity occurs at most once per case. No repeated activities appear in the data, and D6 restricts EX to at most once. No model contains a loop.
4. **Missing Supplier Confirmation.** SC absence is a legitimate outcome in all three models. The model cannot distinguish stocked-skip (S4) from lost events (S5). This is a structural absorption of missingness: SC-free traces are not treated as violations, and the model does not estimate a missingness probability.
5. **Absent external/stocked attribute.** Without the attribute, SC is optional for every case. No model routes cases by sourcing type. Any model that is later refined with the attribute should make SC mandatory for external components.
6. **Optionality.** Optional activities are encoded as XOR with a silent transition () (for SC and EX). The three candidates use XOR-with- or a structural alternative, never a probability.
7. **Silent transitions** are invisible in logs and conformance checks.
8. **Duplicate labels.** The POWL model has no duplicate labels. The process trees contain the same label in several leaves, but each XOR ensures that at most one branch fires per case, so an activity still occurs at most once. The consequences for scalability are discussed in Section 3.
9. **Admission rule.** An unobserved combination is admitted only if it follows from the stated domain rules (D1–D6, S6) or from data-supported interleaving. Each admission is justified in Section 6.
10. **Sample.** The 30 cases are treated as a sample of unknown representativeness. No model is claimed to be the true process.

# 3. Conservative Candidate

**Inductive-bias statement.** This candidate is the closed-world hypothesis: it admits exactly the observed behavior and nothing else. Its bias is maximal reliance on the observed variant set. It has zero generalization beyond the 7 variants and is therefore the most overfit of the three. Its strengths are that every admitted trace is directly witnessed, every excluded trace is explicitly rejected, and fitness on the 30 cases is 1.0. Its weakness is that it treats the 7 variants as the population: any legitimate combination not yet seen (for example, expedite without SC) is rejected.

**Formal expression** (RO · [XOR of 7 middles] · AP · RP · AR):

M_C = RO · ( CC·ER·SC + ER·CC·SC + CC·ER + ER·CC + CC·SC·ER + CC·ER·SC·EX + ER·CC·EX·SC ) · AP · RP · AR

**PM4Py code:**

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO = "Register Order"; CC = "Credit Check"; ER = "Engineering Review"
SC = "Supplier Confirmation"; EX = "Expedite Review"; AP = "Approve Configuration"
RP = "Release Production"; AR = "Archive Case"

def _node(op, *children):
    n = ProcessTree(operator=op, children=[])
    for c in children:
        c.parent = n
        n.children.append(c)
    return n

def leaf(label=None):          # label=None -> silent (tau)
    return ProcessTree(label=label)

def seq(*c): return _node(Operator.SEQUENCE, *c)
def xor(*c): return _node(Operator.XOR, *c)

# Exact XOR enumeration of the 7 observed middle segments.
# Each leaf label appears in several branches (duplicate labels); XOR guarantees one branch per case.
CONSERVATIVE_MIDDLES = [
    (CC, ER, SC), (ER, CC, SC), (CC, ER), (ER, CC),
    (CC, SC, ER), (CC, ER, SC, EX), (ER, CC, EX, SC),
]

def build_conservative():
    branches = [seq(*[leaf(a) for a in mid]) for mid in CONSERVATIVE_MIDDLES]
    return seq(leaf(RO), xor(*branches), leaf(AP), leaf(RP), leaf(AR))

model_conservative = build_conservative()
```

**Behavior deliberately excluded**

- Any trace with EX but no SC (CC,ER,EX and ER,CC,EX), even though S4/S5 make SC-absence plausible.
- Any interleaving not observed, including CCSCER with EX, or ERSCCC.
- Any combination of SC placement not witnessed (for example, SC after AP is excluded by D4 in every model).
- All traces with SC before both CC and ER (D5).

**Known underfitting risks** (the conservative model is primarily overfitting, but it also underfits in the sense of rejecting plausible behavior):

- Rejects the 5 balanced-admissible traces and the 7 permissive-admissible traces (Section 6). Any of these appearing in production would be reported as nonconforming.
- If SC was lost in an EX-containing case (for example, F or G without SC), the trace is rejected, so the model will flag integration-missing cases as violations.
- Cannot represent SC-after-ER-only (D5), so it cannot test D5 at all.
- Scalability: the XOR grows linearly in the number of variants. With n independently orderable activities, possible orders grow factorially; the enumeration would require a number of branches close to n! before it captured the full concurrent behavior. Duplicate labels (CC appears 7 times, ER 7 times, SC 5 times in this tree) make the tree larger but do not change language semantics. Alignment-based metrics still work, but the tree is harder to read, and any change to one activity requires editing several leaves.

# 4. Balanced Candidate

**Inductive-bias statement.** This candidate is the most plausible generalization that uses the strongest evidence and keeps uncertain decisions explicit. It uses only edges that are either domain-required (D1–D4, D6) or empirically invariant in all 23 SC traces (CC precedes SC). It leaves unordered those pairs where both orders are observed and no rule orders them (CC/ER, ER/SC, EX/SC). It introduces optionality for SC and EX. Its bias is a moderate preference for generalization across orderings while still encoding the one precedence that the data supports completely. It is stricter than D5 on purpose: D5 allows SC after ER alone, which is never observed.

**Formal expression** (POWL partial order over nodes V = {RO, CC, ER, SC?, EX?, AP, RP, AR}, where X? = X  ):

M_B = (V, ), with the transitively closed set of edges:
ROCC, ROER, CCSC?, CCEX?, EREX?, CCAP, ERAP, SC?AP, EX?AP, APRPAR.

Its visible language consists of 12 middle segments (the 7 observed plus 5 unobserved), hand-enumerated; the validation script in Section 8 checks this count.

**Decision procedure for each pair** (this is how I chose between sequence, concurrency, and partial order):

- **CC vs ER: unordered (concurrency in the POWL sense).** Both orders are observed (19 CC-first, 11 ER-first). No domain rule orders them. S2 supports parallel; S1 is refuted by data. A sequence would have to pick one direction and would refute 11 or 19 observed cases. An XOR of two orders would reproduce the pair's completion behavior but would not generalize to interleavings with SC (V-E), which is observed. Partial order without an edge is therefore the only choice that is both consistent with data and general enough.
- **CC vs SC: edge CCSC.** All 23 SC-bearing traces have CC completed before SC. This is the only precedence that the data supports without exception. D5 would allow SC after ER alone, but it is never observed; balanced therefore encodes CC as the gating predecessor. This is a deliberate decision that disagrees with D5, and Section 10 treats it as uncertain.
- **ER vs SC: unordered.** ER precedes SC in 21 traces and follows it in 2. Both orders are observed, and no rule orders them.
- **EX vs CC and ER: edges CCEX and EREX.** D6 requires both checks to be completed first; both EX traces satisfy this.
- **EX vs SC: unordered.** F has SC before EX; G has EX before SC. S6 explicitly allows either order.
- **SC and EX vs AP: edges into AP.** D4 and D6 require them before approval.
- **Optionality:** SC? and EX? are XOR-with- nodes. SC? represents both stocked-skip and missing events (disclosed abstraction). EX? is optional by D6.
- **Why not a single sequence or a fully parallel block.** A sequence would be overfit to the observed order. A fully parallel block {CC, ER, SC?, EX?} would admit SC before CC, which violates the 23/23 invariant and D5's "after either."

**PM4Py code:**

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

RO = "Register Order"; CC = "Credit Check"; ER = "Engineering Review"
SC = "Supplier Confirmation"; EX = "Expedite Review"; AP = "Approve Configuration"
RP = "Release Production"; AR = "Archive Case"

def _transitive_closure(edges):
    closure = list(edges)
    changed = True
    while changed:
        changed = False
        for (a, b) in list(closure):
            for (c, d) in list(closure):
                if b is c and not any(x is a and y is d for (x, y) in closure):
                    closure.append((a, d))
                    changed = True
    return closure

def build_balanced():
    ro = Transition(label=RO)
    cc = Transition(label=CC)
    er = Transition(label=ER)
    sc = OperatorPOWL(operator=Operator.XOR, children=[Transition(label=SC), SilentTransition()])
    ex = OperatorPOWL(operator=Operator.XOR, children=[Transition(label=EX), SilentTransition()])
    ap = Transition(label=AP)
    rp = Transition(label=RP)
    ar = Transition(label=AR)
    po = StrictPartialOrder(nodes=[ro, cc, er, sc, ex, ap, rp, ar])
    edges = [(ro, cc), (ro, er),
             (cc, sc), (cc, ex), (er, ex),
             (cc, ap), (er, ap), (sc, ap), (ex, ap),
             (ap, rp), (rp, ar)]
    for a, b in _transitive_closure(edges):
        po.order.add_edge(a, b)
    return po

model_balanced = build_balanced()
```

**Behavior deliberately excluded**

- SC completing before CC completes (for example, RO,ER,SC,CC,AP). This is the CCSC invariant; it is stronger than D5.
- Traces with SC before both CC and ER (D5).
- Any EX before both CC and ER, or EX after AP (D6).
- Any EX repeated, or any activity after AR.

**Known underfitting risks**

- If SC really can follow ER alone (D5), balanced rejects those traces as violations. Its exclusion of ERSCCC is the largest single assumption.
- The completion-order model cannot represent overlap, so it cannot test whether the CC/ER pair actually ran concurrently.
- Cannot represent a rule like "SC is required for external components" because the attribute is absent; SC is optional for all cases.
- If the actual SC-free rate is driven by systematic loss in one order (for example, only when CC is slow), balanced cannot detect that; it treats SC-free as normal.

# 5. Permissive Candidate

**Inductive-bias statement.** This candidate generalizes broadly within what the domain rules allow. It admits all interleavings of CC, ER, SC, and EX that satisfy D1–D6 and S6, including SC after either CC or ER (D5), and all SC/EX optionality (S4, S5, S6). Its bias is a strong preference for coverage of the rule-consistent behavior space and a weak preference for precision. It is the least overfit and the most at risk of admitting behavior that is rule-compatible but operationally unlikely.

**Formal expression** (RO · M · AP · RP · AR, where M = (CCER)·EX? + CC·((ER·EX?)  SC?) + ER·((CC·EX?)  SC?)):

M_P = RO · [ (CC  ER)·EX? + CC·((ER·EX?)  SC?) + ER·((CC·EX?)  SC?) ] · AP · RP · AR

It admits 14 visible middle segments: the 7 observed, 5 also admitted by balanced, and 2 more (ER,SC,CC and ER,SC,CC,EX), which are exactly the D5-only traces.

**Boundary: reasonable generalization versus forbidden behavior.**

- *Reasonable:* any order of CC and ER; SC after CC or after ER (D5); SC optional (S4/S5); EX optional, after both checks, before or after SC (S6).
- *Forbidden:* SC before both CC and ER (D5); EX before both checks or repeated (D6); AP before CC, ER, or a present SC/EX (D3, D4, D6); RP before AP or AR before RP (D2); any missing RO or AR (D1); any repetition or new activity.

**PM4Py code:**

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO = "Register Order"; CC = "Credit Check"; ER = "Engineering Review"
SC = "Supplier Confirmation"; EX = "Expedite Review"; AP = "Approve Configuration"
RP = "Release Production"; AR = "Archive Case"

def _node(op, *children):
    n = ProcessTree(operator=op, children=[])
    for c in children:
        c.parent = n
        n.children.append(c)
    return n

def leaf(label=None):          # label=None -> silent (tau)
    return ProcessTree(label=label)

def seq(*c): return _node(Operator.SEQUENCE, *c)
def xor(*c): return _node(Operator.XOR, *c)
def par(*c): return _node(Operator.PARALLEL, *c)
def opt(x):  return xor(x, leaf(None))

def build_permissive():
    # Three mutually exclusive phases; exactly one fires per case, so each label fires at most once.
    phase = xor(
        seq(par(leaf(CC), leaf(ER)), opt(leaf(EX))),                                  # no SC
        seq(leaf(CC), par(seq(leaf(ER), opt(leaf(EX))), opt(leaf(SC)))),              # CC first
        seq(leaf(ER), par(seq(leaf(CC), opt(leaf(EX))), opt(leaf(SC)))),              # ER first (D5: SC after ER)
    )
    return seq(leaf(RO), phase, leaf(AP), leaf(RP), leaf(AR))

model_permissive = build_permissive()
```
