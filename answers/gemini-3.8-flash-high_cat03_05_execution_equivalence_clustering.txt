## 1. Equivalence design space

Object-centric event logs (OCEL) model processes as multi-relational graphs of interacting objects, dynamic event participation (Event-to-Object, E2O), and evolving structural relations (Object-to-Object, O2O). Executions can be abstracted at different granularities. We define three foundational equivalence relations and one qualified refinement.

### 1. Activity-Sequence Equivalence ($\equiv_{\text{seq}}$)
- **Definition:** For execution $X = (E, O, \mathcal{E}_{\text{E2O}}, \lambda_E, \le_E)$ with lead order $o_{\text{lead}} \in O$, trace $\sigma_{\text{lead}}(X)$ is the timestamp-ordered sequence of activity labels $\langle \lambda_E(e_1), \dots, \lambda_E(e_k) \rangle$ for events where $(e_i, o_{\text{lead}}) \in \mathcal{E}_{\text{E2O}}$. $X \equiv_{\text{seq}} X'$ iff $\sigma_{\text{lead}}(X) = \sigma_{\text{lead}}(X')$.
- **Invariants Preserved:** Total sequence order and frequency of activities directly referencing the lead order.
- **Information Discarded:** Non-lead object types, multiplicities, E2O interaction arities, external boundary crossings (`EXT-*`), and all O2O relations/qualifiers.
- **Properties:** Reflexive, symmetric, transitive (string equality in $\Sigma^*$).
- **Concurrency / Same-Time Events:** Arbitrary timestamp interleavings create spurious variants; resolved via Mazurkiewicz traces (commuting independent activities: $a \cdot b \sim b \cdot a$) or step multisets.

### 2. Typed Structural Equivalence Under Identifier Renaming ($\equiv_{\text{struct}}$)
- **Definition:** An execution graph is $G(X) = (E, O, \mathcal{E}_{\text{E2O}}, \mathcal{E}_{\text{O2O}}, \lambda_E, \tau_O, \text{ext}_O, \le_E)$. $X \equiv_{\text{struct}} X'$ iff there exist bijections $f_E: E \to E'$ and $f_O: O \to O'$ preserving: (1) event ordering ($e_1 \le_E e_2 \iff f_E(e_1) \le_{E'} f_E(e_2)$); (2) activity labels ($\lambda_{E'}(f_E(e)) = \lambda_E(e)$); (3) object types and external flags ($\tau_{O'}(f_O(o)) = \tau_O(o), \text{ext}_{O'}(f_O(o)) = \text{ext}_O(o)$); (4) E2O incidence ($(e, o) \in \mathcal{E}_{\text{E2O}} \iff (f_E(e), f_O(o)) \in \mathcal{E'}_{\text{E2O}}$); and (5) base O2O edges ($(o_1, o_2, r) \in \mathcal{E}_{\text{O2O}} \iff (f_O(o_1), f_O(o_2), r) \in \mathcal{E'}_{\text{O2O}}$). *(Preserving qualifiers $q \in \mathcal{Q}$ yields Qualified Structural Equivalence $\equiv_{\text{qual}}$.)*
- **Invariants Preserved:** Object counts per type, E2O incidence degrees, base O2O topology, external flags, and event ordering.
- **Information Discarded:** Concrete local object IDs; fine-grained O2O semantic qualifiers (`partially_settles`, `removed_before_dispatch`).
- **Properties:** Reflexive, symmetric, transitive (typed graph isomorphism preserving event order).
- **Concurrency / Same-Time Events:** Strict order $\le_E$ over-differentiates parallel actions; resolved by causal partial order $\prec_E$, where $e_1 \prec_E e_2$ iff $\exists o \in O: (e_1, o), (e_2, o) \in \mathcal{E}_{\text{E2O}}$ and $t(e_1) < t(e_2)$.

### 3. Business-Semantic Equivalence ($\equiv_{\text{sem}}$) — Preferred Relation
- **Definition:** Partitions executions by operational feature tuple $M(X) = \langle \Phi_{\text{bound}}, \Phi_{\text{pack}}, \Phi_{\text{ship}}, \Phi_{\text{bill}}, \Phi_{\text{life}} \rangle$:
  - $\Phi_{\text{bound}} \in \{\text{Isolated}, \text{SharedLogistics}, \text{SharedBilling}\}$ (boundary autonomy).
  - $\Phi_{\text{pack}} \in \{\text{SinglePackage}, \text{SplitPackages}\}$ (packaging cardinality).
  - $\Phi_{\text{ship}} \in \{\text{SingleConsolidated}, \text{SplitStaged}\}$ (dispatch coupling).
  - $\Phi_{\text{bill}} \in \{\text{SingleFull}, \text{InstallmentSettlement}, \text{SharedUnallocated}\}$ (financial settlement).
  - $\Phi_{\text{life}} \in \{\text{LinearSTP}, \text{PreDispatchMutation}, \text{ReverseLogisticsRework}\}$ (lifecycle integrity).
  $X \equiv_{\text{sem}} X'$ iff $M(X) = M(X')$.
- **Invariants Preserved:** Fulfillment pattern, freight coupling, financial exposure, boundary crossings, and rework loops.
- **Information Discarded:** Arbitrary local IDs, exact item count when packing topology is invariant, non-causal event interleavings, and local timestamp noise.
- **Properties:** Reflexive, symmetric, transitive (kernel equivalence induced by projection $M$).
- **Concurrency / Same-Time Events:** Invariant to concurrency because motifs evaluate graph topology, cardinality ratios, and causal state changes rather than serialized linear logs.

## 2. Canonical signatures

The Python script below computes a deterministic canonical signature for $\equiv_{\text{sem}}$ and an isomorphism hash for $\equiv_{\text{struct}}$. It abstracts local IDs into normalized roles, detects external boundaries, evaluates E2O/O2O multiplicities and qualifiers, and generates reproducible signatures.

```python
"""
Canonical Signature Generation for Object-Centric Executions.
Transforms an execution into reproducible semantic and structural signatures.
"""

from collections import defaultdict
from typing import Dict, List, Tuple, Any

def compute_canonical_signature(execution: Dict[str, Any]) -> Tuple[str, str]:
    events = execution['events']
    o2o = execution.get('o2o', [])
    lead_order = execution['lead_order']
    
    # 1. Map object types and external references
    objects_by_type = defaultdict(set)
    for ev in events:
        for otype, oids in ev['omap'].items():
            for oid in oids:
                objects_by_type[otype].add(oid)
                    
    num_pkgs = len(objects_by_type['Package'])
    num_delivs = len(objects_by_type['Delivery'])
    
    # 2. Classify Boundary Scope (Phi_bound)
    ext_in_logistics = any(
        oid.startswith("EXT-") 
        for ev in events if ev['activity'] in {'Pack Package', 'Dispatch'}
        for oids in ev['omap'].values() for oid in oids
    )
    ext_in_finance = any(
        oid.startswith("EXT-") 
        for ev in events if ev['activity'] in {'Issue Invoice', 'Record Payment'}
        for oids in ev['omap'].values() for oid in oids
    )
    
    if ext_in_logistics and not ext_in_finance:
        phi_bound = "SHARED_LOGISTICS"
    elif ext_in_finance and not ext_in_logistics:
        phi_bound = "SHARED_BILLING"
    else:
        phi_bound = "ISOLATED"
        
    # 3. Classify Packaging & Shipping (Phi_pack, Phi_ship)
    pack_events = [ev for ev in events if ev['activity'] == 'Pack Package']
    phi_pack = "SPLIT_PACKAGES" if (num_pkgs > 1 and len(pack_events) > 1) else "SINGLE_PACKAGE"

    dispatch_events = [ev for ev in events if ev['activity'] == 'Dispatch']
    if num_delivs == 1 and num_pkgs > 1:
        multi_pkg = any(len(ev['omap'].get('Package', [])) > 1 for ev in dispatch_events)
        phi_ship = "CONSOLIDATED_DELIVERY" if multi_pkg else "SINGLE_DELIVERY"
    elif num_delivs > 1:
        phi_ship = "SPLIT_STAGED_DELIVERIES"
    else:
        phi_ship = "SINGLE_DELIVERY"

    # 4. Classify Billing & Lifecycle (Phi_bill, Phi_life)
    payment_events = [ev for ev in events if ev['activity'] == 'Record Payment']
    has_partial = any(rel.get('qualifier') == 'partially_settles' for rel in o2o)
    if phi_bound == "SHARED_BILLING":
        phi_bill = "SHARED_UNALLOCATED"
    elif has_partial or len(payment_events) > 1:
        phi_bill = "INSTALLMENT_SETTLEMENT"
    else:
        phi_bill = "SINGLE_FULL_SETTLEMENT"

    has_removal = any(rel.get('qualifier') == 'removed_before_dispatch' for rel in o2o)
    has_replace = any(rel.get('relation') == 'replaces' or rel.get('qualifier') == 'replaces' for rel in o2o)
    has_return = any(ev['activity'] in {'Return Item', 'Inspect Return'} for ev in events)
    
    if has_return:
        phi_life = "REVERSE_LOGISTICS_REWORK"
    elif has_removal or (has_replace and not has_return):
        phi_life = "PRE_DISPATCH_MUTATION"
    else:
        phi_life = "LINEAR_STP"

    semantic_sig = f"SEM[Bound:{phi_bound}|Pack:{phi_pack}|Ship:{phi_ship}|Bill:{phi_bill}|Life:{phi_life}]"

    # 5. Structural Canonical Hash (Isomorphism Certificate)
    canonical_id = {lead_order: "Order_1"}
    type_counts = defaultdict(int, {'Order': 1})
    
    def get_c_id(oid: str, otype: str) -> str:
        if oid not in canonical_id:
            prefix = "EXT_" if oid.startswith("EXT-") else ""
            type_counts[otype] += 1
            canonical_id[oid] = f"{prefix}{otype}_{type_counts[otype]}"
        return canonical_id[oid]

    ev_tokens = []
    for ev in events:
        omap_str = []
        for otype in sorted(ev['omap'].keys()):
            c_ids = sorted([get_c_id(oid, otype) for oid in ev['omap'][otype]])
            omap_str.append(f"{otype}:({','.join(c_ids)})")
        ev_tokens.append(f"{ev['activity']}{{{';'.join(omap_str)}}}")

    o2o_tokens = []
    for rel in sorted(o2o, key=lambda x: (x['relation'], x.get('qualifier') or '', x['source'], x['target'])):
        s_t = next((t for t, objs in objects_by_type.items() if rel['source'] in objs), "Obj")
        t_t = next((t for t, objs in objects_by_type.items() if rel['target'] in objs), "Obj")
        s_c, t_c = get_c_id(rel['source'], s_t), get_c_id(rel['target'], t_t)
        q_str = f":{rel['qualifier']}" if rel.get('qualifier') else ""
        o2o_tokens.append(f"{rel['relation']}{q_str}({s_c}->{t_c})")

    struct_sig = f"STRUCT[EV={' -> '.join(ev_tokens)} | O2O={'; '.join(sorted(o2o_tokens))}]"
    return semantic_sig, struct_sig
```

## 4. Cluster interpretations

### Cluster 1: `Sem-Standard` (Executions X1, X2)
- **Signature:** `[Bound:ISOLATED | Pack:1P | Ship:1D | Bill:SingleFull | Life:STP]`
- **Behavior:** Straight-through processing (STP); items ship in one box and delivery, billed once, and settled in full.
- **Risks/Opportunities:** Lowest handling cost benchmark; prime target for automation.
- **Traditional Flattening:** Flattening to `Item` duplicates Delivery, Invoice, and Payment rows, falsely implying multiple transactions.
- **Data-Repair Stability:** Stable; impervious to scan ordering and timestamp jitter.

### Cluster 2: `Sem-ConsolidatedDelivery` (Execution X3)
- **Signature:** `[Bound:ISOLATED | Pack:2P | Ship:1D-Consol | Bill:SingleFull | Life:STP]`
- **Behavior:** Multi-package packing with consolidated dispatch; items split across cartons but ship together on one truck.
- **Risks/Opportunities:** Higher packing costs but freight is minimized; staging bottleneck risk if one box lags.
- **Traditional Flattening:** Flattening to `Package` duplicates delivery and invoice; flattening to `Delivery` masks split packaging costs.
- **Data-Repair Stability:** Vulnerable if warehouse ETL merges carton IDs into a virtual single container.

### Cluster 3: `Sem-SplitStagedFulfillment` (Execution X4)
- **Signature:** `[Bound:ISOLATED | Pack:2P | Ship:2D-Split | Bill:Installments | Life:STP]`
- **Behavior:** Staged partial delivery and installment settlement; items ship asynchronously across dispatches, settling in partial payments.
- **Risks/Opportunities:** Duplicate carrier freight charges and credit exposure between installments.
- **Traditional Flattening:** Flattening to `Order` creates 1:N fan-out on delivery and payment; flattening to `Delivery` breaks order-payment links.
- **Data-Repair Stability:** Sensitive; merging partial bank deposits collapses X4 into single settlement.

### Cluster 4: `Sem-CrossOrderLogistics` (Execution X5)
- **Signature:** `[Bound:SHARED_LOGISTICS | Pack:1P | Ship:1D | Bill:SingleFull | Life:STP]`
- **Behavior:** Collaborative freight co-loading; items from separate orders (`O5` and `EXT-OA`) share a package and truck, with isolated billing.
- **Risks/Opportunities:** Maximizes cube utilization. High compliance risk: cargo cross-contamination, customs discrepancies, and privacy breaches.
- **Traditional Flattening:** Filtering on `Order=O5` strips external objects, misclassifying X5 as baseline fulfillment (identical to X1).
- **Data-Repair Stability:** Fragile; single-tenant extraction severs external links, erasing shared logistics visibility.

### Cluster 5: `Sem-CrossOrderBilling` (Execution X6)
- **Signature:** `[Bound:SHARED_BILLING | Pack:1P | Ship:1D | Bill:Unallocated | Life:STP]`
- **Behavior:** Centralized multi-order invoicing; logistics is isolated, but billing is combined with `EXT-OB` into joint invoice `V61` and unallocated payment `M61`.
- **Risks/Opportunities:** Streamlines corporate billing. Major audit risk: unallocated payments prevent line-item cash reconciliation.
- **Traditional Flattening:** Flattening to `Order` duplicates invoice totals; flattening to `Invoice` conflates independent physical warehouse flows.
- **Data-Repair Stability:** Fragile; single-order ETL extracts leave `V61` and `M61` unanchored, creating phantom unpaid balances.

### Cluster 6: `Sem-PreDispatchMutation` (Execution X7)
- **Signature:** `[Bound:ISOLATED | Pack:1P | Ship:1D | Bill:SingleFull | Life:PreDispatchRemoved]`
- **Behavior:** Warehouse picking correction; items `I71` and `I72` were packed, but `I71` was removed before dispatch and replaced by `I72`. Only `I72` ships.
- **Risks/Opportunities:** Captures picking errors or bench damage. Unrecorded removals cause phantom inventory and invoice disputes.
- **Traditional Flattening:** Invisible in control flow, which mirrors X1. Flattening to `Item` shows `I71` vanishing after packing without explanation.
- **Data-Repair Stability:** Highly fragile; dropping qualifiers (`removed_before_dispatch`) merges X7 into X1.

### Cluster 7: `Sem-ReverseLogisticsRework` (Execution X8)
- **Signature:** `[Bound:ISOLATED | Pack:2P | Ship:2D-Rework | Bill:SingleFull | Life:ReturnRework]`
- **Behavior:** Post-delivery reverse logistics and warranty replacement; item `I82` is returned, inspected, repacked into box `P82`, and redelivered via `D82`.
- **Risks/Opportunities:** Incurs return freight and warranty reserve depletion, but inspection logs offer critical QA feedback.
- **Traditional Flattening:** Flattening to `Order` creates a tangled loop; flattening to `Item` splits the order into an STP item and a looping item.
- **Data-Repair Stability:** Highly stable; dedicated activity labels (`Return Item`, `Inspect Return`) preserve the cluster even without qualifiers.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Preserved Information and Aggregation Mechanics
The function `pm4py.cluster_equivalent_ocel` partitions an OCEL by computing canonical hash keys for connected components. The key structure preserves:
1. The ordered sequence of activity labels.
2. The multiset of object types participating in each event.
3. The transition graph of object types across sequential events.
4. The bipartite graph topology connecting anonymous event nodes to anonymous object nodes.

### Granularity and Practical Challenges
- **Raw Identifier Leakage:** Retaining raw IDs (`O1`, `I11`) forces every case into a singleton cluster. Unconstrained stripping allows shared objects (`EXT-OA`, `EXT-OB`) to merge hundreds of orders into massive connected components.
- **Post-Processing Pipeline:** Raw clusters must be post-processed by: (1) scoping ego-networks to lead object `Order`; (2) canonically relabeling local objects (`Order_1`, `Item_1`); (3) injecting O2O qualifiers (`removed_before_dispatch`, `partially_settles`); and (4) projecting graph hashes into business motif vectors $M(X)$.
- **Exact vs. Coarse Use Cases:** Exact structural equivalence is vital for RPA verification and audit conformance. Coarse semantic clustering is superior for process discovery and executive KPI dashboards.
- **Graph Explosion & `max_objs`:** In enterprise logs, shared pallets or bulk invoices cause dense object coupling (the "object hairball"). Setting `max_objs` prunes traversal depth to prevent memory exhaustion, but risks truncating execution boundaries into artificial fragments.

### Executable Python Pipeline

```python
"""
Executable Python pipeline illustrating object-centric clustering using PM4Py,
custom canonicalization, and semantic motif aggregation centered on 'Order'.
"""

import pm4py
from collections import defaultdict
from typing import Dict, Any

def run_object_centric_clustering(ocel: pm4py.OCEL) -> Dict[str, Any]:
    lead_type = "Order"
    
    # 1. Scope lead objects
    objects_df = pm4py.ocel_get_objects(ocel)
    lead_orders = objects_df[objects_df['ocel:type'] == lead_type]['ocel:oid'].tolist()
    
    # 2. Extract structural variants using PM4Py bounded by max_objs
    raw_clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=50)
    
    # 3. Custom canonicalization and semantic post-processing
    final_clusters = defaultdict(list)
    cluster_metadata = {}
    
    for cluster_id, cluster_ocel in enumerate(raw_clusters):
        c_objs = pm4py.ocel_get_objects(cluster_ocel)
        c_orders = c_objs[c_objs['ocel:type'] == lead_type]['ocel:oid'].tolist()
        c_events = pm4py.ocel_get_events(cluster_ocel)
        activities = c_events['ocel:activity'].tolist()
        
        num_pkgs = len(c_objs[c_objs['ocel:type'] == 'Package'])
        num_delivs = len(c_objs[c_objs['ocel:type'] == 'Delivery'])
        has_ext = any(str(oid).startswith("EXT-") for oid in c_objs['ocel:oid'])
        has_returns = any(act in {'Return Item', 'Inspect Return'} for act in activities)
        
        # Classify into preferred business semantic cluster
        if has_returns:
            sem_label = "Sem-ReverseLogisticsRework"
        elif has_ext:
            sem_label = "Sem-CrossOrderShared"
        elif num_pkgs > 1 and num_delivs == 1:
            sem_label = "Sem-ConsolidatedDelivery"
        elif num_pkgs > 1 and num_delivs > 1:
            sem_label = "Sem-SplitStagedFulfillment"
        else:
            sem_label = "Sem-Standard"
            
        for oid in c_orders:
            final_clusters[sem_label].append(oid)
            
        cluster_metadata[sem_label] = {
            "order_count": len(final_clusters[sem_label]),
            "activities_profile": list(dict.fromkeys(activities))
        }
        
    return {
        "assignments": dict(final_clusters),
        "metadata": cluster_metadata
    }

if __name__ == "__main__":
    pass
```

## 7. Robustness analysis

We assess cluster assignment stability under five structural and semantic perturbations.

### 1. Ignore all O2O qualifiers
Qualifiers like `removed_before_dispatch`, `replaces`, `partially_settles`, and `completes_settlement` are discarded. Consequently, **X7 collapses into X1** (except for item participation in Dispatch). In **X4**, installment payment semantics disappear, reducing to two unannotated payment events. In **X8**, the replacement link $P_{82} \to P_{81}$ is lost, though explicit activity labels (`Return Item`) keep X8 distinct from normal fulfillments.

### 2. Ignore external objects
External objects (`EXT-OA`, `EXT-IA`, `EXT-OB`) and their incident edges are filtered out. In **X5**, removing `EXT-OA` and `EXT-IA` leaves Pack Package and Dispatch referencing only local objects; **X5 collapses into X1**. In **X6**, removing `EXT-OB` leaves invoice and payment referencing only $O_6$; **X6 collapses into X1**. Traditional order-isolated filtering thus masks critical compliance and logistics anomalies.

### 3. Collapse repeated same-label events
Consecutive occurrences of identical activity labels are deduplicated (`Add Item+ -> Add Item`, `Pack Package+ -> Pack Package`). In **X3**, the two `Pack Package` events collapse into one; its control flow becomes identical to **X1**, merging into the baseline if object counts are ignored. In **X4**, the two `Record Payment` events collapse to one, but the alternating sequence `Pack -> Dispatch -> Pack -> Dispatch` remains uncollapsed unless set-based reduction is applied. In **X8**, return/repack iteration counts are erased.

### 4. Treat Pack and Dispatch event order as a partial order rather than a total order
Total ordering $\le_E$ is relaxed to a causal dependency order $\prec_E$ induced by shared object lifecycles. In **X4**, the chains $\text{Item } I_{41} \to P_{41} \to D_{41}$ and $\text{Item } I_{42} \to P_{42} \to D_{42}$ share no objects other than the lead order. Under partial ordering, any warehouse interleaving (e.g., packing both before dispatching vs packing and dispatching sequentially) maps to the exact same concurrent execution graph. Cluster assignment becomes robust against physical staging jitter.

### 5. Treat payment multiplicity as an amount attribute rather than structure
Multiple `Record Payment` events and distinct Payment objects are abstracted into state updates on Invoice ($V_{41}.\text{paid\_amount} \mathrel{+}= \text{amount}$). In **X4**, financial settlement ceases to generate multiple structural nodes. Structural topology simplifies to split logistics with a single updated invoice, cleanly decoupling financial milestone accounting from physical logistics flows.

## 8. Limitations and recommendation

### 1. Compliance Monitoring: Qualified Structural Equivalence ($\equiv_{\text{qual}}$)
- **Recommendation:** Strict typed graph isomorphism preserving O2O qualifiers and external object boundaries.
- **Rationale:** Auditing and fraud detection cannot tolerate abstraction. In customs, **X5** represents co-mingled cargo violating origin declarations. In financial audits (SOX), **X6** represents unallocated cross-entity revenue sharing. In inventory control, **X7** represents unauthorized substitution or phantom scrap. Only $\equiv_{\text{qual}}$ flags these violations.

### 2. Operational Segmentation: Business-Semantic Motif Equivalence ($\equiv_{\text{sem}}$)
- **Recommendation:** Feature-vector motif equivalence ($M(X)$).
- **Rationale:** Operations managers require clusters reflecting physical handling procedures and freight costs. They must distinguish consolidated shipments (**X3**) from staged split deliveries (**X4**), while ignoring trivial item scan ordering (**X1 vs X2**). $\equiv_{\text{sem}}$ provides optimal operational granularity.

### 3. Root-Cause Analysis (RCA): Causal Partial-Order Structural Equivalence ($\equiv_{\text{causal-qual}}$)
- **Recommendation:** Partially ordered graph isomorphism enriched with O2O qualifiers.
- **Rationale:** When diagnosing delays, analysts must trace true causal dependencies. RCA must distinguish intentional split fulfillment (**X4**) from defect-driven reverse logistics (**X8**); conflating them blames warehouse staging for product defects. Evaluating causal DAGs isolates true bottlenecks without timestamp noise.

### 4. Descriptive Reporting: Coarse Semantic / Lead-Projected Equivalence
- **Recommendation:** Coarse semantic clustering or lead-projected sequence equivalence with cardinality flags.
- **Rationale:** Executive dashboards require concise summaries of business volume (e.g., "90% Standard STP, 5% Split Shipments, 3% Returns, 2% Shared Invoicing"). Exposing hundreds of micro-variants overwhelms executive decision-makers.

### Why No Single Equivalence Notion Suffices
The design space of object-centric process mining exhibits an unavoidable trade-off between **precision**, **robustness**, and **interpretability**:
- Strict relations ($\equiv_{\text{qual}}$) create thousands of singleton clusters in enterprise logs, overwhelming executive reporting.
- Coarse sequence relations ($\equiv_{\text{seq}}$) suffer from catastrophic blindness: grouping baseline execution **X1**, co-loading **X5**, shared billing **X6**, and item removal **X7** into the same cluster, masking critical compliance breaches.
- Operational segmentation requires cardinality invariants, whereas root-cause analysis requires causal DAGs.

A robust OCEL architecture must therefore support a multi-tiered hierarchy of equivalence relations tailored to the analytical objective.
