

## 1. Interaction-graph description

The system manifests a multi-typed interaction graph where Jobs interact through shared Resources, Policy Constraints, and Logistics Chains. Important node types include Job (J1–J6), Machine (CNC-2, OVEN-1, TEST-1), Tool (FIX-A, RACK-7, CAL-3), Batch (B1, B2), ComponentLot (L7, L8), and Shipment (S1–S3).

Edge types connect these nodes via direct resource consumption (requires, contains, batches) or synchronization (consolidates, quarantine, release). Qualifiers distinguish ownership versus state. For example, `requires` links J1 to C1, while `batches` groups J1, J2, and J3 into B1.

Higher-order motifs reveal dependency structures:
1.  **Batch Synchronization Motif:** Jobs (J1, J2, J3) connect to Batch (B1), which connects to Machine (OVEN-1). This creates a "wait for all" pattern where faster jobs must idle for the slowest.
2.  **Resource Chain Motif:** Job (J4) connects to Tool (FIX-A), which connects to Machine (CNC-2). Holding one object blocks the next activity on the other.
3.  **Lot-Coupling Motif:** Jobs (J2, J5) share ComponentLot (L7), which connects to a quarantine event. A policy state on the Lot affects distinct Jobs independently of their individual process times.

Direct observations appear as event logs (e.g., `Batch Cure`, `Release Lot`). Inferred edges represent waiting times derived from gaps between ready timestamps and start timestamps (e.g., J1 ready 08:10, Batch Start 12:05).

**Compact Adjacency List:**

- J3: [requires C3, batches B1, consolidates S2]

## 2. Quantitative delay decomposition

**1. Avoidable waiting for J1 in B1**
*   **Observation:** J1 ready at 08:10. Batch B1 starts at 12:05.
*   **Calculation:** 12:05 minus 08:10 = 3 hours, 55 minutes.
*   **Counterfactual:** If B1 had no size constraint, J1 could enter OVEN-1 immediately at 08:10. This delay is synchronization-induced, not processing time.

**2. Avoidable waiting for J2 in B1**
*   **Observation:** J2 ready at 08:25. Batch B1 starts at 12:05.
*   **Calculation:** 12:05 minus 08:25 = 3 hours, 40 minutes.
*   **Counterfactual:** Similar to J1, J2 is held by the batch policy. The 15-minute gap between J1 and J2 readiness is negligible compared to the batch synchronization delay.

**3. Delay plausibly associated with FIX-A for J4**
*   **Observation:** J3 releases FIX-A at 11:40. J4 uses CNC-2 at 11:45. CNC-2 is idle 10:05–10:47.
*   **Calculation:** The 42-minute machine idle gap (10:47 to 11:29) suggests J4 arrived early but waited for the tool. Assuming J4 ready at 09:50 and FIX-A held by J3 until 11:40, the direct block is roughly 11:40–11:45, but the upstream impact created machine waste.
*   **Counterfactual:** If FIX-A were available earlier or shared, CNC-2 utilization could improve without additional capacity.

**4. Delay imposed on J1 by S1 consolidation**
*   **Observation:** J1 packed at 13:30. Shipment S1 dispatches at 19:25.
*   **Calculation:** 19:25 minus 13:30 = 5 hours, 55 minutes.
*   **Counterfactual:** If S1 shipped per-job, J1 could leave at 13:30. The consolidation policy adds nearly 6 hours to lead time regardless of logistics speed.

**5. Delay plausibly associated with CAL-3 for J6**
*   **Observation:** J6 ready at 16:05. J5 tests 16:10–16:35. CAL-3 recalibrated 16:35–17:20. J6 tests 17:25.
*   **Calculation:** 17:25 minus 16:05 = 1 hour, 20 minutes.
*   **Counterfactual:** If CAL-3 calibration occurred during a setup phase or was parallelized, J6 could have tested immediately after J5.

## 4. What flattening misses

**Job-flattened View:**
*   **Visible:** Sequence of stages (Release -> Process -> Inspect).
*   **Hidden:** Shared resource locks (Tool, Batch) and policy constraints (Lot release).
*   **Misleading Conclusion:** Because individual job durations are within 1.8 SD, the process appears stable. This hides that jobs are delayed by external coordination, not internal inefficiency.

**Machine-flattened View:**
*   **Visible:** Utilization rates (44–58%) and activity sequences.
*   **Hidden:** Waiting time caused by missing tools or incomplete batches.
*   **Misleading Conclusion:** Low utilization suggests no bottleneck. In reality, the machine waits for policy triggers (Batch Start) rather than physical capacity limits.

**Batch-flattened View (if available):**
*   **Visible:** Batch start/end times.
*   **Hidden:** Why batches wait for specific jobs or why machines wait for batches.
*   **Misleading Conclusion:** Batch duration may look normal, masking the long waits prior to batch initiation.

**Shipment-flattened View:**
*   **Visible:** Shipment creation to dispatch times.
*   **Hidden:** Time packed jobs wait for partners.
*   **Misleading Conclusion:** Short `Load -> Dispatch` time (0.3h) implies fast logistics, ignoring the 6h wait for J1.

**Tool-flattened View:**
*   **Visible:** Tool usage counts.
*   **Hidden:** Tool release times that block downstream machines.
*   **Misleading Conclusion:** Tools seem underutilized, yet their availability gates critical path jobs.

**ComponentLot-flattened View:**
*   **Visible:** Lot events (Quarantine, Release).
*   **Hidden:** Link to Jobs not logged in same system.
*   **Misleading Conclusion:** Lot events appear isolated incidents rather than systemic blocking events.

**Why Low Utilization Coexists with Long Job Waiting:**
Utilization measures active processing time divided by total available time. If machines wait for policy triggers (Batch Start) or tools (FIX-A), they register as idle. This creates a paradox: the system is not "busy" (low utilization), but Jobs are stuck (high waiting). Traditional flattening attributes waiting to machine capacity, but object-centric evidence reveals the waiting is driven by synchronization and tool availability.

## 5. Object-lifecycle evidence

**Narrative 1: Batch-Coupled Delay (J1, J2, B1, OVEN-1, S1)**
*   **Temporal Precedence:** J1 (08:10), J2 (08:25) ready before B1 (12:05) start. J1 packed (13:30) before S1 (19:25) dispatch.
*   **Resource Feasibility:** OVEN-1 capable of single-job processing, but policy requires B1. S1 capable of immediate dispatch, but policy waits for J4.
*   **Policy Constraints:** Batch size limits; Shipment consolidation rules.
*   **Causal Speculation:** Delays stem from inventory policy rather than equipment capacity.

**Narrative 2: Tool-Induced Stalls (J3, J4, FIX-A, CNC-2)**
*   **Temporal Precedence:** J3 holds FIX-A (09:00–11:40). J4 arrives CNC-2 (09:50) but starts process (11:45).
*   **Resource Feasibility:** CNC-2 idle 10:05–10:47 implies readiness but missing fixture.
*   **Policy Constraints:** One fixture per job; manual release logic.
*   **Causal Speculation:** Fixture availability creates artificial idle periods not captured by machine logs.

**Narrative 3: Lot and Calibration Blocking (J5, J6, L7, CAL-3, TEST-1)**
*   **Temporal Precedence:** L7 quarantined (10:20) then released (13:50). J5 tests (16:10–16:35) then CAL-3 recalibrated (16:35–17:20) before J6 tests (17:25).
*   **Resource Feasibility:** TEST-1 available; CAL-3 exclusive requirement per test event.
*   **Policy Constraints:** Calibration maintenance schedule or manual reconfiguration.
*   **Causal Speculation:** Calibration policy serializes parallel test readiness, creating downstream waiting.

## 6. Intervention portfolio and spillovers

**1. Allow Partial Batch Release**
*   **Target:** Batch Synchronization.
*   **Benefit:** Reduce J1/J2 waiting from ~4h to minutes.
*   **Helped:** J1, J2.
*   **Harmed:** OVEN-1 (more changeovers).
*   **Risk:** Reduced quality consistency if batch logic is mandatory.
*   **Metric:** On-time delivery vs. Oven changeover rate.
*   **Evaluation:** Compare wait time in simulation with partial batch logic.

**2. Add a Second CAL-3 Tool**
*   **Target:** Shared-Tool Contention.
*   **Benefit:** Eliminate J6's 1h20m wait for calibration.
*   **Helped:** J6, subsequent high-volume jobs.
*   **Harmed:** Budget/Inventory management.
*   **Risk:** Calibration maintenance costs increase.
*   **Metric:** Calibration idle time vs. Test utilization.
*   **Evaluation:** Track test queue depth before and after tool addition.

**3. Decouple Shipment Dispatch**
*   **Target:** Shipment Consolidation.
*   **Benefit:** J1 can leave immediately after packing.
*   **Helped:** J1, J4.
*   **Harmed:** Logistics/Transport (smaller loads).
*   **Risk:** Shipping costs per unit increase.
*   **Metric:** Average lead time vs. Cost per unit shipped.
*   **Evaluation:** A/B test consolidated vs. immediate shipping on similar SKUs.

**4. Integrate Lot Events to Job Logs**
*   **Target:** Data-Integration Artifacts.
*   **Benefit:** Accurate root-cause visibility for J2/J5 delays.
*   **Helped:** All jobs requiring L7/L8.
*   **Harmed:** IT/Integration team time.
*   **Risk:** Data quality issues during migration.
*   **Metric:** Event linking completeness.
*   **Evaluation:** Verify if Lot events now appear in Job-centric pipelines.

**5. Align Calibration with Maintenance**
*   **Target:** Maintenance Policy.
*   **Benefit:** Move CAL-3 calibration to non-peak hours.
*   **Helped:** J6, TEST-1.
*   **Harmed:** Maintenance team (shift changes).
*   **Risk:** Tool availability may decrease during peak if not monitored.
*   **Metric:** Calibration time outside production hours.
*   **Evaluation:** Monitor if peak test times are free of calibration events.

## 8. Falsification and additional data

**Observations Weakening Top Explanation (Batch Synchronization):**
1.  If J1, J2, J3 were ready at 11:55, batch wait would disappear.
2.  If OVEN-1 had capacity for 4 jobs and B1 had 3, wait should be minimal.
3.  If Batch Start times matched Earliest Job Ready times consistently.
4.  If B2 start time matched J4 ready time without OVEN idle gaps.
5.  If J3 did not hold FIX-A until after J4 arrival.
6.  If Calibration of CAL-3 was logged before test queues built up.

**Additional Fields Required to Discriminate Hypotheses:**
1.  `batch_ready_time`: Timestamp when batch policy is satisfied.
2.  `tool_availability_time`: Timestamp when tool released and free.
3.  `lot_link_id`: Explicit link field between Lot Events and Job IDs.
4.  `consolidation_reason`: Policy rule ID causing shipment hold.
5.  `setup_duration`: Time spent preparing machine before `Machine Process`.
6.  `maintenance_schedule`: Scheduled maintenance window vs. actual.

To refine hypothesis ranking, we must distinguish coordination delays from physical capacity limits. The current data shows machines are physically idle (capacity exists) while Jobs wait for policy gates (batch, lot, shipment). Thus, the primary constraint is not machine volume but synchronization logic.
