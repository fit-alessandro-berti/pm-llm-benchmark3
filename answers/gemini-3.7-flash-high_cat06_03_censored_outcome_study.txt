# Uncertainty-Aware Predictive Process Monitoring Study: Credit Application Default Under Censoring, Selection, and Process Shift

## 1. Target definition

### Primary Prediction Target Formulation
The primary target is formulated within a **Multi-State Competing Risks and Cause-Specific Survival Framework** at an early process milestone. 

- **Unit of Analysis**: An individual credit application prefix $\mathcal{E}_{\le t}(i)$, capturing the sequence of events and contextual attributes from application initiation up to the early prediction cutoff.
- **Target Population**: All initiated credit applications ($\mathcal{U} = \{1, \dots, N\}$, $N = 48,000$) within the observation window, avoiding upfront truncation to only approved accounts.
- **Prediction Time ($t_{\text{pred}}$)**: Evaluated at a standardized early operational milestone: specifically, the timestamp immediately upon completion of the initial `Identity/KYC Check` and first entry into `Credit Review` (or alternatively, a fixed event prefix $k = 3$).
- **Outcome Horizon**: $H = 90\text{ calendar days}$ post-account activation ($t_{\text{activation}} + 90\text{ days}$).
- **Primary Estimand**: The joint cumulative incidence of transition into the terminal states $\mathcal{S} = \{\text{Activated-Default}_{\le 90d}, \text{Activated-NonDefault}_{> 90d}, \text{Rejected}, \text{Withdrawn}, \text{Transferred}\}$, combined with the cause-specific hazard of 90-day default conditional on policy activation:
  $$\lambda_{\text{default}}(t \mid X_{\le t_{\text{pred}}}) = \lim_{\Delta t \to 0} \frac{P(t \le T_{\text{def}} < t + \Delta t, \text{State}=\text{Default} \mid T \ge t, X_{\le t_{\text{pred}}})}{\Delta t}$$
  For binary operational decision-support (e.g., triage prioritization), the primary estimand decomposes as:
  $$P(\text{Default}_{\le 90d}, \text{Activated} = 1 \mid X_{\le t_{\text{pred}}}) = P(\text{Default}_{\le 90d} \mid \text{Activated} = 1, X_{\le t_{\text{pred}}}) \cdot P(\text{Activated} = 1 \mid X_{\le t_{\text{pred}}})$$

### The Fallacy of Treating Rejections as Non-Default
The business request informally treats rejected applications as "non-default." This is a severe semantic and statistical fallacy:
1. **Counterfactual Missingness vs. True Solvency**: An applicant who is rejected is never exposed to credit. Their default outcome under activation $Y(1)$ is unobserved (counterfactually missing), not zero. Setting $Y=0$ for rejected cases equates credit denial with perfect solvency.
2. **Pathological Distortion of Underwriting Signals**: If high-risk applicants are rejected by policy, labeling them as "non-defaulters" forces the machine learning model to associate high-risk prefix features (e.g., low initial risk scores, high requested amounts, repeated KYC issues) with successful loan repayment. In deployment, the model would actively recommend approving the very applicants the existing policy rejected.

### Credible Alternative Target Formulations
1. **Pure Conditional Post-Activation Survival ($S(t \mid \text{Activated}=1, X_{\le t_{\text{pred}}})$)**:
   - *Question Answered*: "Given that an application meets current underwriting criteria and is activated, what is the probability of surviving 90 days without default?"
   - *Trade-off*: Statistically clean for portfolio loss provisioning and risk-based loan pricing under the *status quo* policy, but completely uninformative for borderline applications that would be rejected under current rules.
2. **Counterfactual Potential Outcome Target ($E[Y(a=1) \mid X_{\le t_{\text{pred}}}]$)**:
   - *Question Answered*: "What would be the 90-day default rate if the lender unilaterally approved and activated every applicant at intake?"
   - *Trade-off*: Addresses the true underwriting optimization problem, but requires untestable causal assumptions (strong conditional ignorability $Y(1) \perp A \mid X$ and positivity $0 < P(A=1 \mid X) < 1$). Because credit policies enforce deterministic cutoff boundaries, positivity is strictly violated in historical data for severely subprime applicants.

### Primary Selection Justification
The **Multi-State Competing Risks Framework** is chosen as primary because it is statistically honest and operationally actionable: it treats rejection, withdrawal, and transfer as explicit competing endpoints rather than pretending they are mature solvent accounts or dropping them via selection bias.

## 2. Cohort construction

### Inclusion, Exclusion, and As-Of Rules
- **Inclusion Rules**: Every application initiated between `2024-01-01 00:00:00` and `2025-12-31 23:59:59` ($N = 48,000$) is included in the master intake cohort.
- **Exclusion Rules**: No cases are excluded at the intake level. For sub-models analyzing post-activation survival trajectories, non-activated cases are explicitly accounted for via Inverse Probability of Selection Weighting (IPW) rather than naive filtering.
- **As-Of Timeline Rules**: 
  - Extraction Date ($t_{\text{extract}}$): `2026-02-15`.
  - Horizon + Delayed Feed Maturity Buffer: $90\text{ days (horizon)} + 35\text{ days (maximum feed lag)} = 125\text{ days}$.
  - Maturity Threshold Date: `2026-02-15 - 125 days = 2025-10-13`. Any account activated after `2025-10-13` cannot be verified as a mature non-default and is classified as right-censored/immature.

## 3. Censoring and missing-label strategy

### Taxonomy of Censoring and Missingness Mechanisms

```
48,000 Total Intake Applications
├── In-Flight / Open (5,100) ───────────────> Administrative Process Right-Censoring
├── Terminated Pre-Activation
│   ├── Rejected (9,100) ───────────────────> Selective Non-Observation (Missing Counterfactual)
│   ├── Withdrawn (5,700) ──────────────────> Competing Terminal Risk (Funnel Drop-out)
│   └── Transferred (2,900)
│       ├── Linked (1,740 [60%]) ───────────> Partial External Follow-Up
│       └── Unlinked (1,160 [40%]) ─────────> Informative Missing Follow-Up / Competing Event
└── Activated Accounts (25,200)
    ├── Fully Mature Matured (21,600)
    │   ├── Default <= 90d (2,700) ─────────> Fully Observed Event
    │   └── Non-Default > 90d (18,900) ─────> Fully Observed Survival
    ├── Immature / Feed Pending (3,600) ────> Ordinary Right-Censoring (Maturation Horizon Lag)
    └── Partner Permanently Missing ────────> Informative Attrition / Missing Not at Random (MNAR)
```

1. **Ordinary Right-Censoring**: Activated accounts that have not experienced a default but have been observed for fewer than 90 days as of extraction date $t_{\text{extract}}$, or open applications still in review. Standard non-informative right-censoring assumes independent event times conditional on covariates $X_{\le t}$.
2. **Delayed Labels (Feed Maturation Lag)**: External bureau outcome feeds exhibit a 7–35 day transmission delay post 90-day horizon. A case activated at day $t_{\text{act}}$ cannot be confirmed as a non-defaulter until $t_{\text{act}} + 90\text{d} + 35\text{d}$. Cases observed between 90 and 125 days without a default feed are right-censored at $t_{\text{last\_feed\_sync}}$, preventing false "non-default" labeling.
3. **Selection Through Activation**: Conditioning analysis solely on activated cases creates severe selection bias (conditioning on a post-treatment collider/decision). The 9,100 rejected cases represent selective counterfactual missingness driven by the historical underwriting policy $\pi_0$.
4. **Transfer as Competing Risk vs. Missing Follow-Up**: Transferred cases (2,900) leave the internal system. The 60% linked subset allows tracking on partner platforms; the 40% unlinked subset represents informative loss to follow-up, correlated with partner platform capabilities and applicant risk tiers.
5. **Permanently Missing Outcome Feeds**: Partner-originated activated accounts suffer from elevated rates of permanently unreturned outcome feeds. This is Missing Not at Random (MNAR) if missingness correlates with partner underwriting quality or loan distress.

### Primary Analysis Strategy
The primary strategy applies an **Aalen-Johansen Multi-State Estimator / Cause-Specific Cox Hazard Model with Inverse Probability of Censoring Weighting (IPCW)**:
- Competing outcomes (Activation + Default, Activation + Survival, Rejection, Withdrawal, Transfer) are modeled jointly using cause-specific hazard functions.
- For post-activation survival models, time-dependent weights $W_i(t) = \frac{1}{\hat{G}(t \mid X_i)}$ are computed using a censoring survival model $\hat{G}(t)$ to unbias estimates against maturation lag and observable dropout.
- A selection propensity model $\hat{e}(X_{\le t_{\text{pred}}}) = P(\text{Activated} = 1 \mid X_{\le t_{\text{pred}}})$ is estimated to weight activated instances ($w_i = 1/\hat{e}(X_i)$), adjusting the conditional default risk back to the intake population distribution where positivity holds.

### Sensitivity Analyses
1. **Manski Non-Parametric Worst/Best-Case Bounds**:
   - Compute sharp worst-case default rate bounds by setting all 9,100 rejected and 1,160 unlinked transferred cases first to $Y=0$ (lower bound), then to $Y=1$ (upper bound).
   - Evaluate whether model rankings and feature importances remain stable across intermediate plausible default assumptions (e.g., rejected cases experiencing $2\times$ to $4\times$ the baseline activated default rate).
2. **Pattern-Mixture / Tipping Point Analysis for Missing Partner Feeds**:
   - Model the probability of missing outcome feeds as a function of channel and risk score. Introduce a sensitivity parameter $\delta \in [1.0, 3.5]$ representing the odds ratio of default among missing feeds versus observed feeds within the same partner tier, identifying the tipping point where model calibration fails.
3. **Bivariate Probit / Heckman Selection Model**:
   - Jointly estimate the selection equation ($\text{Activated}$) and outcome equation ($\text{Default}_{90d}$) under varying correlation parameters $\rho \in [-0.5, 0.8]$ between the error terms to test sensitivity to unmeasured underwriter discretion.

### Testability Classification of Assumptions

| Assumption | Testability Status | Verification / Refutation Method |
| :--- | :--- | :--- |
| **Proportional Hazards of Default Post-Activation** | **Testable** | Schoenfeld residual tests and log-cumulative hazard plots on the 21,600 mature activated accounts. |
| **Missing at Random (MAR) of Delayed Outcome Feeds** | **Testable** | Compare prefix feature distributions and default rates across cases with 7-day vs. 35-day reporting lags. |
| **Linkage Balance in Transferred Cohort (60% vs 40%)** | **Partially Testable** | Test whether observed prefix features ($X_{\le t}$) differ between linked and unlinked transfers via Kolmogorov-Smirnov and SMD tests. Untestable for post-transfer unobserved events. |
| **Ignorability of Partner Feed Missingness** | **Partially Testable** | Test dependence on observed intake channel, loan amount, and initial score. Untestable regarding partner-side operational breakdowns vs applicant distress. |
| **Unconfoundedness of Rejection ($Y(1) \perp A \mid X_{\le t}$)** | **Fundamentally Untestable** | Counterfactual default outcomes for rejected applicants can never be observed under the current policy regime without randomized credit trials. |

## 4. Prefix extraction

### Prefix Generation Methodology
To support early warning decision-making without future leakage, prefixes are extracted using two complementary temporal parameterizations:

1. **Fixed Event-Count Prefixes ($k \in \{1, 2, 3, 5\}$)**:
   - Primary operational benchmark set at $k = 3$ (typically: `Application Started` $\to$ `Identity/KYC Check` $\to$ `Credit Review`).
   - For every case $i$, the prefix log contains strictly events $\{e_{i, 1}, \dots, e_{i, \min(k, n_i)}\}$, where $n_i$ is the total event count.
2. **Elapsed-Time Window Prefixes ($\Delta t \in \{24\text{h}, 72\text{h}, 7\text{d}\}$ from $t_0$)**:
   - Captures case state at a fixed operational time horizon regardless of execution velocity. Slices event log to include only events where $\text{timestamp}(e_{i, j}) \le \text{timestamp}(e_{i, 1}) + \Delta t$.

### Edge Cases and Data Anomaly Handling
- **Short Cases ($n_i < k$)**: Cases that terminate prior to index $k$ (e.g., automated KYC failure rejected at $k=2$) must **never be discarded**, as dropping them introduces severe survivorship bias. They are retained as completed short prefixes with an absorbing termination indicator and zero-padded transition vectors.
- **Repeated Document Loops (`Credit Review` $\leftrightarrow$ `Request Documents`)**: 
  - Iterative document loops are tracked dynamically. The prefix at event index $j$ computes cumulative loop counts $\sum \mathbb{I}(\text{activity} = \text{'Request Documents'})$, time elapsed in document pending state, and delta between consecutive review iterations.
  - No future loop iterations beyond event index $j$ are aggregated.
- **System Migration and Activity Renaming (15 October 2025)**:
  - An explicit pre-prefix ontology mapping table standardizes legacy activity names (pre-Oct 15) and modernized names (post-Oct 15) to a canonical schema prior to trace splitting.
  - Migration-induced duplicate events with identical timestamps ($\Delta t = 0$) and identical activity/resource payloads are deduplicated deterministically by retaining the first occurrence.
- **Strict Timestamp Filtering**:
  - The prefix generation pipeline enforces a strict temporal barrier: for any evaluated cutoff $t_{\text{cut}}$, all events with $\text{time:timestamp} > t_{\text{cut}}$ are masked out before computing state, graph, or statistical aggregations.

## 5. Process-aware features

All features are constructed strictly from the observed event trace prior to or at prediction time $t_{\text{pred}}$.

```
Prefix Event Sequence (t <= t_pred)
├── Control-Flow: Activity n-grams, DFG transition probabilities, execution variant ID
├── Temporal/Velocity: Case age, inter-event duration, KYC duration, off-hours flag
├── Resource/Queue: Assigned underwriter ID, queue depth at t_pred, resource historical velocity
├── Rework/Friction: Document request count, KYC resubmission count, reviewer reassignments
└── Static Case Context: Intake channel, requested amount, region, initial risk score (t=0)
```

### Taxonomy of Process-Aware Features

1. **Control-Flow & Sequence Features**:
   - *Activity N-grams & Transitions*: Frequency of direct transitions (e.g., `KYC Check` $\to$ `Request Documents`) within the prefix.
   - *Process Variant Identifier*: Categorical encoding of the exact control-flow sequence up to $t_{\text{pred}}$, mapped against historical training variants.
   - *Current Execution State*: One-hot encoding of the latest executed activity and predecessor activity.
2. **Timing, Queueing, and Velocity Features**:
   - *Case Age ($t_{\text{pred}} - t_0$)*: Total elapsed wall-clock time from application start.
   - *Stage-Specific Durations*: Precise time spent inside `Identity/KYC Check` and initial queue time prior to `Credit Review`.
   - *Temporal Arrival Context*: Day of week, hour of day, and business-hours vs. weekend/night application submission indicator.
   - *Process Acceleration / Deceleration*: Ratio of second-event duration to first-event duration ($\frac{t_2 - t_1}{t_1 - t_0}$).
3. **Resource & Congestion Features**:
   - *Resource Anonymized ID*: Categorical identifier of the handling officer for KYC and Credit Review.
   - *Point-in-Time Queue Congestion*: Number of active, unresolved cases in the specific resource's or department's queue at timestamp $t_{\text{pred}}$ (computed via historical replay).
   - *Resource Handover Count*: Number of distinct `org:resource` transitions observed across the prefix.
4. **Rework, Friction, and Anomaly Features**:
   - *Document Request Count*: Number of explicit document request cycles triggered prior to $t_{\text{pred}}$.
   - *KYC Resubmission Flag*: Indicator whether identity verification required multiple attempts.
   - *Process Deviation Metric*: Conformance fitness score of the observed prefix against the standard normative process model.
5. **Static Context & Historical Reference Features**:
   - *Static Case Attributes*: `case:requested_amount`, `case:channel` (Direct Web, Mobile, Broker, Partner), `case:region`.
   - *Point-in-Time Baseline Score*: Initial `risk_score` established at `Application Started`.
   - *Historical Resource Risk Rate*: Rolling 60-day historical approval default rate for the assigned underwriter, computed strictly on matured accounts resolved prior to $t_{\text{pred}}$.
   - *Policy Regime Indicator*: Binary flag $\mathbb{I}(t_{\text{start}} \ge \text{2025-07-01})$ representing the macroeconomic and credit policy environment.

## 6. Leakage audit

| Feature or Data Element | Leakage or Bias Risk | Valid Availability Rule | Keep / Repair / Drop | Rationale |
| :--- | :--- | :--- | :--- | :--- |
| `final_limit` | **Severe Target & Decision Leakage** | Populated only at final credit approval/contract issuance. | **DROP** | Absent on rejected/withdrawn cases; perfectly separates acceptance from rejection and reflects post-review limit sizing. |
| `decision_reason` | **Direct Post-Decision Leakage** | Generated at or after final `Accept` or `Reject` event. | **DROP** | Unobserved at early prefix; contains underwriter's final post-review determination. |
| `collection_status` | **Direct Target Proxy Leakage** | Updated weeks/months post-activation during default collection workflows. | **DROP** | Directly reveals the default target $Y=1$; causes 100% artificial target leakage. |
| `Future Events` (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | **Temporal Lookahead Leakage** | Occur strictly downstream of early prediction point $t_{\text{pred}}$. | **DROP (from features)** | Downstream execution events; must be masked during prefix feature extraction and used solely to establish ground truth labels. |
| `documents_total` | **Nightly Snapshot Aggregation Leakage** | Computed via end-of-day batch ETL; includes documents uploaded later on the same day after $t_{\text{pred}}$. | **REPAIR** | End-of-day aggregation leaks future intraday events. Repair by replacing with an event-driven running count `documents_count_asof_t` computed strictly from timestamps $\le t_{\text{pred}}$. |
| `updated risk_score` | **Post-Prefix Update Leakage** | Re-computed dynamically during subsequent underwriting stages or post-activation checks. | **REPAIR** | Score updates after $t_{\text{pred}}$ incorporate downstream underwriter inquiries. Repair by extracting strictly the point-in-time `risk_score` recorded at or before $t_{\text{pred}}$. |
| `resource experience` | **Extraction-Time Lookahead Bias** | Computed as employee tenure at extraction date (`2026-02-15`), not at event occurrence time. | **REPAIR** | A reviewer handling a case in Jan 2024 has 2 years of artificial experience added if using extraction-time data. Repair by calculating tenure at event time: $\text{timestamp}(e) - \text{employee\_hire\_date}$. If hire date is absent, drop feature. |
| `label_available_at` & `default_90d` | **Direct Ground Truth Leakage** | External feed timestamps and maturity flags. | **DROP (from features)** | Primary target labels; must be isolated completely from the feature matrix and referenced only for loss computation and cohort partitioning. |

## 7. Validation design

### Temporal Validation and Backtesting Scheme
To replicate real-world operational deployment, the validation architecture strictly uses **out-of-time (OOT) rolling temporal splits** based on `case:start_time`.

```
Observation Timeline (Jan 1, 2024 - Dec 31, 2025)                      Extraction (Feb 15, 2026)
├──────────────────────────────────────┼──────────────┼──────────────┼──────────────┤
│ Train Set (18 Months)                │ Policy Drift │ Test 1       │ Immature     │
│ Jan 1, 2024 - Jun 30, 2025           │ Validation   │ System Shift │ Masked       │
│                                      │ Jul 1 - Sep  │ Oct 1 - Oct  │ Oct 14, 2025 │
│ (Pre-Policy Shift, Fully Matured)    │ 30, 2025     │ 13, 2025     │ - Dec 31     │
└──────────────────────────────────────┴──────────────┴──────────────┴──────────────┘
                                                                     ▲
                                                  Maturity Cutoff (Oct 13, 2025)
                                                  (Extraction - 90d horizon - 35d feed lag)
```

1. **Training Cohort (`2024-01-01` to `2025-06-30`, 18 Months)**:
   - Established under original credit policy rules.
   - 100% of activated accounts have surpassed the $90\text{d} + 35\text{d} = 125\text{d}$ maturation threshold, providing stable ground truth.
2. **Validation Cohort 1: Policy Shift Stress-Test (`2025-07-01` to `2025-09-30`, 3 Months)**:
   - Evaluates model stability across the **1 July 2025 credit policy change**.
   - Fully matured by extraction date (`2026-02-15`).
   - Assesses out-of-distribution generalization when approval thresholds and applicant selection probabilities shift.
3. **Validation Cohort 2: System Migration & Schema Shift (`2025-10-01` to `2025-10-13`, ~2 Weeks)**:
   - Evaluates the impact of the **15 October 2025 system migration** (activity renaming, event duplication).
   - Serves as the final fully-matured evaluation test block (activated $\le \text{2025-10-13}$).
4. **Immature / Censored Holdout (`2025-10-14` to `2025-12-31`)**:
   - Retained exclusively for right-censored survival model evaluation (C-index, Brier score under IPCW) and funnel progression validation; excluded from fixed-horizon binary evaluation tables.

### Why Random Case Splits Are Fatal in this Setting
- **Temporal Information Leakage**: Random splits leak future macro-economic conditions, interest rate environments, and seasonal applicant quality across folds.
- **Concealment of Policy and System Drift**: A random split samples pre- and post-July 1 policy cases into both train and test sets, artificially inflating cross-validation performance while concealing the fact that the model fails under policy regime changes.
- **Label Maturation Contamination**: Random splitting mixes immature cases with mature cases, causing models to treat recent right-censored non-defaults as confirmed solvent accounts.

### Evaluation Metrics
1. **Inverse Probability of Censoring Weighted (IPCW) Brier Score**:
   $$\text{BS}^{\text{IPCW}}(t) = \frac{1}{N} \sum_{i=1}^N \left[ \frac{\hat{P}(T_i \le t \mid X_i)^2 \cdot \mathbb{I}(T_i > t)}{\hat{G}(t)} + \frac{(1 - \hat{P}(T_i \le t \mid X_i))^2 \cdot \mathbb{I}(T_i \le t, \Delta_i = 1)}{\hat{G}(T_i^-)} \right]$$
2. **Time-Dependent Cumulative/Dynamic AUC ($AUC^{\text{IPCW}}(t)$)**: Evaluates discrimination capacity at the 90-day horizon accounting for maturation censoring.
3. **Uno’s Concordance Index ($C$-index)**: Evaluates global ranking of default risk without requiring proportional hazards assumptions.
4. **Integrated Calibration Index (ICI) and Calibration Intercept/Slope**: Measures whether predicted default probabilities match empirical default rates across risk deciles.
5. **Subgroup Disparity Metrics**: Tracking AUC and Brier score disparities across intake channels (Partner vs. Direct Web) and regional cohorts to detect channel-specific degradation.

## 8. Limitations and decision-use boundary

### What the Study Can and Cannot Claim
- **Can Claim**: The study provides a statistically consistent estimator of default risk **conditional on the applicant being approved and activated under the historical underwriting policy $\pi_0$**: $P(\text{Default}_{90d} \mid \text{Activated}=1, X_{\le t_{\text{pred}}})$.
- **Cannot Claim**: The model **cannot** estimate the counterfactual default risk of currently rejected applicants if policy were relaxed ($P(Y(1) = 1 \mid \text{Rejected}, X_{\le t_{\text{pred}}})$).
- **Cannot Claim**: The model does not establish causal mechanisms between process friction (e.g., document request delays) and credit default; process delays may be symptoms of applicant unreliability rather than causal drivers.

### Performative Prediction and Feedback Loops in Deployment

```
Model Deployment Feedback Mechanisms
├── 1. Automated Gatekeeping ───> Rejects high-risk prefixes ───> Eliminates ground truth labels (Self-Fulfilling)
├── 2. Applicant Attrition ────> Extended document checks ──────> Solvent applicants withdraw (Adverse Selection)
├── 3. Underwriter Deskilling ──> Over-reliance on model score ──> Perfunctory document reviews (Process Drift)
└── 4. Partner Gaming ─────────> Brokers repackage traces ──────> Evades early-warning rules (Adversarial Adaptation)
```

1. **Automated Gatekeeping and Outcome Elimination (The Selection Feedback Loop)**:
   - If the model is deployed to auto-reject applications with high early default probabilities, these applicants are never activated.
   - Consequently, no future ground-truth default labels can ever be collected in that region of feature space. The model's historical belief that these applicants are high-risk becomes self-reinforcing and untestable, permanently blinding the lender to shifts in applicant quality.
2. **Adverse Selection Induced by Process Friction**:
   - If the early warning system routes flagged applications into intensive, repetitive document review loops, creditworthy applicants with alternative financing options will withdraw ($Withdrawn$).
   - Desperate, credit-impaired applicants are more willing to endure prolonged operational friction, worsening the unobserved default propensity of the remaining active cohort.
3. **Underwriter Behavioral Drift & Automation Complacency**:
   - Human credit reviewers exposed to early model risk scores may exhibit confirmation bias, performing perfunctory reviews on "low-risk" flagged applications and hyper-scrutinizing "high-risk" flags.
   - This alters the distribution of `org:resource`, review durations, and document requests, degrading the predictive validity of process-aware features over time.
4. **Strategic Manipulation by Originating Partners**:
   - External broker and partner platforms incentivize volume. Once partners learn the features driving early warnings (e.g., specific document submission sequences or initial loan amounts), they will coach applicants to alter initial submissions, inducing adversarial data shift.

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Uncertainty-Aware Predictive Process Monitoring & Audit Pipeline
Demonstrates cohort flow, leakage auditing, temporal splitting, and prefix generation.
"""

import numpy as np
import pandas as pd
import pm4py
from pm4py.objects.log.util import dataframe_utils


def run_pipeline(csv_path: str = "applications_events.csv") -> dict:
    # -------------------------------------------------------------------------
    # 1. Ingestion & Point-in-Time Schema Normalization
    # -------------------------------------------------------------------------
    df_raw = pd.read_csv(csv_path)

    # Parse timestamps strictly
    df_raw["time:timestamp"] = pd.to_datetime(
        df_raw["time:timestamp"], utc=True
    )
    df_raw["label_available_at"] = pd.to_datetime(
        df_raw["label_available_at"], utc=True
    )
    df_raw["data_extract_time"] = pd.to_datetime(
        df_raw["data_extract_time"], utc=True
    )

    t_extract = df_raw["data_extract_time"].max()
    HORIZON_DAYS = 90
    MAX_FEED_LAG_DAYS = 35
    t_maturity_cutoff = t_extract - pd.Timedelta(
        days=HORIZON_DAYS + MAX_FEED_LAG_DAYS
    )

    # Resolve Oct 15, 2025 System Migration: Canonical Activity Mapping & Deduplication
    ACTIVITY_SYNONYMS = {
        "Doc_Req_Legacy": "Request Documents",
        "KYC_Initial_v1": "Identity/KYC Check",
        "Review_Credit_L1": "Credit Review",
    }
    df_raw["concept:name"] = df_raw["concept:name"].replace(ACTIVITY_SYNONYMS)
    df_raw = df_raw.drop_duplicates(
        subset=["case:concept:name", "concept:name", "time:timestamp"]
    )

    # -------------------------------------------------------------------------
    # 2. Case-Level State, Milestone, and Label Maturity Construction
    # -------------------------------------------------------------------------
    def derive_case_metadata(trace: pd.DataFrame) -> pd.Series:
        acts = trace["concept:name"].tolist()
        t_start = trace["time:timestamp"].min()

        is_activated = "Account Activated" in acts
        is_rejected = "Rejected" in acts or any(
            "Reject" in a for a in acts
        )
        is_withdrawn = "Withdrawn" in acts
        is_transferred = "Transferred" in acts

        t_act = (
            trace.loc[
                trace["concept:name"] == "Account Activated", "time:timestamp"
            ].min()
            if is_activated
            else pd.NaT
        )

        # Classify terminal state
        if is_activated:
            if pd.notna(t_act) and t_act <= t_maturity_cutoff:
                # Fully mature window
                default_val = trace["default_90d"].dropna().iloc[-1] if (
                    trace["default_90d"].dropna().shape[0] > 0
                ) else 0.0
                state = (
                    "Activated_Default"
                    if default_val == 1.0
                    else "Activated_NonDefault"
                )
                mature_flag = True
            else:
                state = "Activated_Immature"
                mature_flag = False
        elif is_rejected:
            state = "Rejected"
            mature_flag = True
        elif is_withdrawn:
            state = "Withdrawn"
            mature_flag = True
        elif is_transferred:
            state = "Transferred"
            mature_flag = True
        else:
            state = "Still_Open"
            mature_flag = False

        return pd.Series(
            {
                "case_start_time": t_start,
                "activation_time": t_act,
                "terminal_state": state,
                "is_mature": mature_flag,
                "initial_score": trace["risk_score"].dropna().iloc[0]
                if trace["risk_score"].dropna().shape[0] > 0
                else np.nan,
            }
        )

    case_meta = (
        df_raw.groupby("case:concept:name")
        .apply(derive_case_metadata)
        .reset_index()
    )
    cohort_summary = case_meta["terminal_state"].value_counts().to_dict()

    # -------------------------------------------------------------------------
    # 3. Strict Temporal Train / Validation / Test Splitting
    # -------------------------------------------------------------------------
    # Train: 2024-01-01 to 2025-06-30 (Pre-policy change)
    # Val: 2025-07-01 to 2025-09-30 (Policy shift stress test)
    # Test: 2025-10-01 to 2025-10-13 (Migration shift & mature test)
    train_cases = case_meta.loc[
        case_meta["case_start_time"] < "2025-07-01", "case:concept:name"
    ]
    val_cases = case_meta.loc[
        (case_meta["case_start_time"] >= "2025-07-01")
        & (case_meta["case_start_time"] < "2025-10-01"),
        "case:concept:name",
    ]
    test_cases = case_meta.loc[
        (case_meta["case_start_time"] >= "2025-10-01")
        & (case_meta["case_start_time"] <= t_maturity_cutoff),
        "case:concept:name",
    ]

    # -------------------------------------------------------------------------
    # 4. Leakage-Free Prefix Extraction & Feature Engineering
    # -------------------------------------------------------------------------
    PREFIX_K = 3
    LEAKAGE_COLS = [
        "final_limit",
        "decision_reason",
        "collection_status",
        "default_90d",
        "label_available_at",
    ]

    # Mask leakage columns from raw event stream
    df_sanitized = df_raw.drop(columns=LEAKAGE_COLS, errors="ignore").copy()
    df_sanitized = dataframe_utils.convert_timestamp_columns_in_df(df_sanitized)
    df_sanitized = df_sanitized.sort_values(
        ["case:concept:name", "time:timestamp"]
    )

    # Format dataframe for PM4Py
    event_log = pm4py.format_dataframe(
        df_sanitized,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )

    # Extract event-count prefixes k=3
    prefixes_df = pm4py.get_prefixes_from_log(
        event_log, length=PREFIX_K
    ) if hasattr(pm4py, "get_prefixes_from_log") else (
        df_sanitized.groupby("case:concept:name").head(PREFIX_K)
    )

    # Feature Extractor per prefix
    def extract_prefix_features(prefix: pd.DataFrame) -> pd.Series:
        events = prefix["concept:name"].tolist()
        t0 = prefix["time:timestamp"].min()
        tk = prefix["time:timestamp"].max()

        duration_sec = (tk - t0).total_seconds()
        doc_requests = events.count("Request Documents")

        # Point-in-time risk score (latest available at or before tk)
        pt_risk = prefix["risk_score"].dropna().iloc[-1] if (
            prefix["risk_score"].dropna().shape[0] > 0
        ) else np.nan

        return pd.Series(
            {
                "prefix_len": len(events),
                "duration_to_prefix_hours": duration_sec / 3600.0,
                "doc_request_count": doc_requests,
                "point_in_time_risk_score": pt_risk,
                "current_activity": events[-1],
                "lead_channel": prefix["case:channel"].iloc[0]
                if "case:channel" in prefix.columns
                else "Unknown",
                "requested_amount": prefix["case:requested_amount"].iloc[0]
                if "case:requested_amount" in prefix.columns
                else np.nan,
            }
        )

    features_df = (
        prefixes_df.groupby("case:concept:name")
        .apply(extract_prefix_features)
        .reset_index()
    )
    dataset = features_df.merge(
        case_meta[
            [
                "case:concept:name",
                "terminal_state",
                "is_mature",
                "case_start_time",
            ]
        ],
        on="case:concept:name",
    )

    # -------------------------------------------------------------------------
    # 5. Automated Leakage Audit Assertions
    # -------------------------------------------------------------------------
    for col in LEAKAGE_COLS:
        assert (
            col not in dataset.columns
        ), f"CRITICAL LEAKAGE DETECTED: {col} present in feature set!"
    assert (
        dataset["point_in_time_risk_score"].isna().sum() < len(dataset)
    ), "Risk score tracking failed."

    # Note: Connect dataset here to downstream Cause-Specific Cox / Fine-Gray
    # Competing Risk or IPCW-weighted Survival models using `terminal_state` & `duration`

    return {
        "cohort_summary": cohort_summary,
        "train_size": len(train_cases),
        "val_size": len(val_cases),
        "test_size": len(test_cases),
        "features_shape": dataset.shape,
    }
```
