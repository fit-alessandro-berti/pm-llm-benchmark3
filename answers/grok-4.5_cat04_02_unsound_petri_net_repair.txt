# 1. Executive Verdict

The net is a workflow net (unique source, unique sink, every node lies on a source-to-sink path). It should **not** be expected to be sound. The principal defect is that `t_join_waived` has only one input (`p_waived`) and never synchronizes with analysis completion, while `t_join_normal` correctly waits for both `p_analysis_done` and `p_review_done`. Business consequence: on the waiver route, authorization can fire before analysis finishes (or without it ever finishing), and a token remains forever in `p_analysis` or `p_analysis_done`, so the exact final marking `fm` is unreachable after a waiver. The standard-review route completes properly; the waiver route violates mandatory analysis and proper completion.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source` / `im` | Single entry; one token starts the case | Unique source with `im[source]=1` | OK as WF-net entry |
| `t_register`  `p_ready`  `t_split` | Register then AND-split into analysis  review | Silent split correctly produces one token in `p_analysis` and one in `p_review` | Parallelism starts as intended |
| Analysis branch `p_analysis`  `t_analyze`  `p_analysis_done` | Mandatory analysis | Branch is well-formed but only consumed by `t_join_normal` | Token orphaned when waiver join is used |
| XOR review: `t_standard_review` vs `t_waive_review` | Choose standard review or recorded waiver | Free choice from `p_review`; mutually exclusive outcomes `p_review_done` / `p_waived` | Choice itself is fine |
| `t_join_normal` | AND-join: analysis done  standard review done | Two inputs; correctly implements AND for the standard path | Standard path can complete |
| `t_join_waived` | AND-join: analysis done  waiver recorded | **Only one input** (`p_waived`); no arc from `p_analysis_done` | Authorization without analysis; leftover analysis token |
| `p_decision`  `t_authorize`  `sink` / `fm` | Authorize only after both sides done; unique exit | Reachable from either join; `fm[sink]=1` | Token in `sink`  proper completion if other places still marked |
| Source-to-sink coverage | Every node on a path sourcesink | Graph-theoretically satisfied (including `p_waived`, both joins, analysis places) | WF-net check can pass while soundness fails |
| Silent `t_split`, `t_join_*` | Pure routing | Fine if wiring is correct; waiver join wiring is not | Invisible bypass of the analysis conjunct |

# 3. Marking-Based Counterexample

Legal firing sequence exposing the defect (waiver route, analysis still pending):

`t_register`  `t_split`  `t_waive_review`  `t_join_waived`  `t_authorize`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---|---|---|---|---|
| 0 | — | `{source:1}` | `t_register` | Start at `im` |
| 1 | `t_register` | `{p_ready:1}` | `t_split` | Case registered |
| 2 | `t_split` | `{p_analysis:1, p_review:1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | Both parallel branches marked |
| 3 | `t_waive_review` | `{p_analysis:1, p_waived:1}` | `t_analyze`, `t_join_waived` | Waiver taken; analysis token still in `p_analysis` |
| 4 | `t_join_waived` | `{p_analysis:1, p_decision:1}` | `t_analyze`, `t_authorize` | **Join did not wait for analysis** |
| 5 | `t_authorize` | `{p_analysis:1, sink:1}` | `t_analyze` | Token in `sink`, but marking  `fm` |
| 6 | `t_analyze` | `{p_analysis_done:1, sink:1}` | — (none that can clear the leftover) | Leftover in `p_analysis_done`; `t_join_normal` needs `p_review_done`, which will never appear |

So: (i) `t_authorize` can occur **before** `t_analyze`; (ii) a token in `sink` is **not** the exact final marking `fm`; (iii) the leftover cannot be consumed because the only consumer of `p_analysis_done` is `t_join_normal`, which also requires `p_review_done`.

**Second counterexample** (analysis completes before the broken join; still improper completion):

`t_register`  `t_split`  `t_analyze`  `t_waive_review`  `t_join_waived`  `t_authorize`

Final nonzero marking `{p_analysis_done:1, sink:1}`  `fm`. Same stuck token; option-to-complete fails on every waiver trace.

(The standard path `t_register, t_split, t_analyze, t_standard_review, t_join_normal, t_authorize` does reach `fm`; the defect is path-specific.)

# 4. Minimal-Repair Alternatives

Edit-cost model: each added or removed arc = 1; each added or removed place = 1; each added or removed transition = 1. Label-only changes = 0. No weight for comments or variable names.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---|---|---|---|
| **A. Sync waiver join** | Add arc `p_analysis_done  t_join_waived` | **1** | Yes: analysis mandatory on both review outcomes; waiver vs standard still distinct; auth after both complete | Waiver path now blocks until analysis done | None material; both joins compete for `p_analysis_done` but XOR review makes only one join enabled |
| **B. Unify review outcomes** | Remove arc `waive_review  p_waived`; add arc `waive_review  p_review_done`; remove arcs `p_waived  join_waived`, `join_waived  p_decision`; remove transition `t_join_waived`; remove place `p_waived` | **6** | Yes: analysis still mandatory; one AND-join | Single join for both outcomes; `p_waived` gone as observable place | Slightly less explicit “waiver committed” place for monitors; dead-code removal must be complete |
| **C. Policy change: skip analysis on waiver** | Add arc `p_analysis  t_join_waived` (cancel unstarted analysis when waiver joins) | **1** | **No** — analysis no longer mandatory under waiver (policy change must be stated) | Waiver may complete without `t_analyze` if analysis not yet started | Race: if `t_analyze` already fired, token sits in `p_analysis_done`, `t_join_waived` stuck needing `p_analysis`, deadlock |

**Minimality justification.** Under the edit-cost model, A and C both cost 1 and are minimal cardinality repairs. They are behaviorally opposite: A enforces the stated business rule; C deliberately weakens it and still leaves a deadlock race unless further edits handle `p_analysis_done` (so a *correct* optional-analysis repair would cost more than 1). B preserves intent like A but costs 6; it is attractive for structural simplicity (one join), not for edit distance. A and C tie on cost; A wins on fidelity to the given intent, so A is the primary minimal repair that keeps mandatory analysis on the waiver path. B is the distinct structural alternative that also keeps mandatory analysis.

import pm4py
from pm4py.objects.petri_net.obj import PetriNet, Marking
from pm4py.objects.petri_net.utils import petri_utils


def fire_named(net, marking, transition_name):
    """Fire one transition by name if enabled; print and return the new marking."""
    enabled = pm4py.get_enabled_transitions(net, marking)
    by_name = {t.name: t for t in enabled}
    if transition_name not in by_name:
        raise RuntimeError(
            f"Transition {transition_name!r} not enabled at {dict(marking)}; "
            f"enabled={sorted(by_name)}"
        )
    t = by_name[transition_name]
    # manual fire using preset/postset
    new_marking = Marking(marking)
    for arc in t.in_arcs:
        new_marking[arc.source] -= arc.weight
        if new_marking[arc.source] <= 0:
            del new_marking[arc.source]
    for arc in t.out_arcs:
        new_marking[arc.target] = new_marking.get(arc.target, 0) + arc.weight
    print(f"fired {transition_name}: {dict(new_marking)}")
    return new_marking

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of waiver vs standard review.** Repair A keeps both `t_waive_review` / `p_waived` and `t_standard_review` / `p_review_done`, so logs and the net still distinguish the outcomes. Repair B keeps distinct visible transitions but drops `p_waived` as a place. Repair C keeps names but changes the meaning of waiver (skips analysis).

- **Silent transitions.** `t_split`, `t_join_normal`, and `t_join_waived` remain silent. That is appropriate for routing. Repair A does not add new silent duplicates; the two joins are alternative AND-synchronizers, not duplicate activities. Confusion risk is low if monitors key off visible labels (`Perform Analysis`, `Record Review Waiver`, `Authorize Case`).

- **Soundness vs business alignment.** Soundness of Repair A shows option to complete, proper completion, and no dead transitions (assuming the usual WF-net soundness notion). It does **not** by itself prove that every organizational rule is captured (e.g., who may waive, SLAs, or that waiver must be formally recorded in an external system). Alignment still needs trace-level acceptance tests.

- **Regression traces.**  
  - **Positive:**  
    - `Register  Analyze  StandardReview  Authorize` (any interleaving of the parallel pair).  
    - `Register  Analyze  WaiveReview  Authorize` (any interleaving; authorize only after both).  
  - **Negative:**  
    - Any trace where `Authorize` occurs with analysis never started or not finished while waiver was chosen.  
    - Traces that take both standard review and waiver (should be impossible).  
    - Completion with tokens left in `p_analysis` / `p_analysis_done`.

- **Detecting accidental bypass of mandatory analysis.** Check that every accepting trace contains `t_analyze` (or label “Perform Analysis”). In the net, assert there is no path from the post-waiver place to `t_authorize` that avoids consuming `p_analysis_done`. In diagnostics, after repair, `t_join_waived` must never be enabled unless `p_analysis_done` is marked. Log-based LTL/alignments: activity `Authorize Case` only after `Perform Analysis` on all cases, including waived ones.

# 8. Final Recommendation

**Deploy Repair A** (add `p_analysis_done  t_join_waived`). It is the unique cost-1 edit that restores the stated policy: analysis remains mandatory on the waiver path, waiver and standard review stay distinguishable, and proper completion to `fm` is restored without removing structure or renaming work. The dual-join shape matches the business narrative (“whichever review outcome was selected” still AND-synced with analysis).

**Fallback: Repair B** (route waiver into `p_review_done` and delete the dead waiver-join place/transition). Use B if toolchains or reviewers prefer a single synchronization transition and a smaller net, or if an extra place `p_waived` complicates downstream mining. B preserves the same visible mandatory-analysis behavior at higher edit cost.

Do not deploy Repair C unless product owners explicitly redefine the policy so that a recorded waiver cancels analysis; even then C as a one-arc patch is unsafe because of the analyze/join race and would need a fuller cancel-or-join design.

After deployment, run the Section 6 diagnostics, replay both positive parallel interleavings, and assert that the short waiver-without-analysis counterexample is impossible on the repaired net.
