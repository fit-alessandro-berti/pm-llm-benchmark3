# 1. Policy Interpretation and Conflict Resolution

The requirements, activity labels, temporal profile values, and eight test cases are taken from the uploaded task text. 

**Material assumptions**

1. **Case start and close.** `Receive Onboarding Request` is the unique first event. `Close Onboarding` is the administrative close after either rejection or first payment.
2. **Accepted vs rejected.** A case is treated as **accepted** if `Activate Vendor` occurs and `Reject Vendor` does not. It is treated as **rejected** if `Reject Vendor` occurs and `Activate Vendor` does not. If both occur, the case is contradictory and fails before any risk-route interpretation.
3. **Risk route is not data-observable.** The log has no explicit low-risk/high-risk attribute in the supplied test cases. Therefore, the procedural model enforces the low-risk route as `Manager Approval` and the high-risk route as `Enhanced Due Diligence -> Compliance Approval`, but it cannot verify whether the chosen route matches the true risk classification without a data attribute.
4. **Procedural backbone is checked on projection.** The procedural ProcessTree below is intentionally scoped to the stable onboarding backbone. Cross-cutting events such as `Request Clarification`, `Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, and `Suspend Vendor` are evaluated by declarative and stateful validation layers. Procedural conformance should therefore be run on a projection to the backbone activities.
5. **Clarification final outcome.** For R3, “before any final outcome” means before `Reject Vendor` or `Activate Vendor`. `Close Onboarding` should also not occur with an unresolved clarification, but the decisive business violation happens earlier at rejection or activation.
6. **R6 24-hour clock.** I interpret the emergency opinion deadline as 24 hours after the emergency `Activate Vendor`. In T6, the opinion is also within 24 hours of `Sanctions Escalation`, so the T6 conclusion is unchanged under either clock.
7. **Timestamps define order.** Events appear in timestamp order. If real logs contain equal timestamps, a deterministic secondary ordering policy is needed.
8. **Resource attribute.** `org:resource` is required for segregation-of-duties checks. Missing resource values are not interpreted as compliance with four-eyes rules.
9. **Temporal profile deviations are warnings.** R12 says these expectations are “normative enough to flag but not automatically reject,” so temporal deviations produce warnings unless another hard rule fails.
10. **Support and confidence are modeling metadata.** The `support` and `confidence` values in the DECLARE dictionary are manually assigned policy metadata, not empirical discovery results from the eight test cases.

**Two defensible R5/R6 resolutions**

**Resolution A — strict legal precedence, chosen for the implemented model.**
R5 is treated as authoritative: after `Sanctions Escalation`, `Obtain Legal Opinion` must occur before `Activate Vendor` under all circumstances. R6 is not ignored, but because the supplied event log does not contain an emergency flag or joint authorization, the override cannot be proven from the activity sequence. Under this resolution, an activation before legal opinion fails unless the policy and log schema are changed to record the exception explicitly.

Compliance risk of this choice: it may falsely fail genuinely authorized emergency activations, creating operational friction. Its advantage is that it avoids silently accepting an exception that Legal explicitly described as forbidden “under all circumstances.”

**Resolution B — operations emergency override.**
R6 is treated as a controlled exception to R5: `Activate Vendor` may precede `Obtain Legal Opinion` only when there is out-of-log joint authorization and the opinion arrives within 24 hours. Because the test log has no emergency attribute, a log-only audit can only return `policy-dependent` unless the external authorization record is joined into the case data.

Compliance risk of this choice: it weakens the Legal rule unless the external authorization record is complete, immutable, and auditable. It also risks legitimizing emergency behavior after the fact if the authorization timestamp is not reliable.

**Implemented choice.**
I implement Resolution A as the default hard compliance model. I still show how T6 changes under Resolution B in the verdict matrix.

# 3. Procedural Backbone

**Compact formal description**

The procedural backbone is:

```text
->(
  "Receive Onboarding Request",
  +(
    "Capture Master Data",
    "Run Sanctions Screening",
    "Verify Bank Account"
  ),
  "Classify Risk",
  X(
    "Reject Vendor",
    ->(
      X(
        "Manager Approval",
        ->("Enhanced Due Diligence", "Compliance Approval")
      ),
      "Activate Vendor",
      "Release First Payment"
    )
  ),
  "Close Onboarding"
)
```

Here `->` is sequence, `+` is parallel/concurrent execution, and `X` is exclusive choice.

**Self-contained PM4Py-style code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.conversion.process_tree import converter as pt_converter

def leaf(label: str) -> ProcessTree:
    return ProcessTree(label=label)

def node(operator: Operator, *children: ProcessTree) -> ProcessTree:
    n = ProcessTree(operator=operator)
    n.children = list(children)
    for c in n.children:
        c.parent = n
    return n

BACKBONE_ACTIVITIES = {
    "Receive Onboarding Request",
    "Capture Master Data",
    "Run Sanctions Screening",
    "Verify Bank Account",
    "Classify Risk",
    "Enhanced Due Diligence",
    "Manager Approval",
    "Compliance Approval",
    "Reject Vendor",
    "Activate Vendor",
    "Release First Payment",
    "Close Onboarding",
}

checks = node(
    Operator.PARALLEL,
    leaf("Capture Master Data"),
    leaf("Run Sanctions Screening"),
    leaf("Verify Bank Account"),
)

high_risk_route = node(
    Operator.SEQUENCE,
    leaf("Enhanced Due Diligence"),
    leaf("Compliance Approval"),
)

approval_choice = node(
    Operator.XOR,
    leaf("Manager Approval"),
    high_risk_route,
)

accepted_route = node(
    Operator.SEQUENCE,
    approval_choice,
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
)

primary_outcome = node(
    Operator.XOR,
    leaf("Reject Vendor"),
    accepted_route,
)

procedural_tree = node(
    Operator.SEQUENCE,
    leaf("Receive Onboarding Request"),
    checks,
    leaf("Classify Risk"),
    primary_outcome,
    leaf("Close Onboarding"),
)

net, initial_marking, final_marking = pt_converter.apply(procedural_tree)

# The accepting Petri net representation used by downstream PM4Py conformance.
procedural_model = (net, initial_marking, final_marking)

# In deployment, replay this model on a projection of the event log:
# log_backbone = pm4py.filter_event_attribute_values(
#     log,
#     "concept:name",
#     BACKBONE_ACTIVITIES,
#     retain=True
# )
```

**Modeling explanation**

The parallel block allows `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` in any order after `Receive Onboarding Request`, while still requiring all three before `Classify Risk`.

The outcome is an XOR: either `Reject Vendor`, or an accepted route. The accepted route is itself an XOR between the low-risk route, represented by `Manager Approval`, and the high-risk route, represented by `Enhanced Due Diligence -> Compliance Approval`. Both accepted routes then continue with `Activate Vendor -> Release First Payment -> Close Onboarding`.

I deliberately exclude clarification, sanctions escalation, legal opinion, bank-detail changes, and suspension from this ProcessTree. They are cross-cutting obligations whose correct semantics are conditional, resource-aware, or time-aware. Including them naively in a block-structured ProcessTree would either over-constrain legal cases or allow behavior that violates the policy.

I do **not** encode R5 as `precedence[("Obtain Legal Opinion", "Activate Vendor")]`, because that would require a legal opinion before every activation, even when there was no sanctions escalation. I also do **not** encode R5 as `nonsuccession[("Sanctions Escalation", "Activate Vendor")]`, because that would forbid activation after escalation even when the legal opinion was properly obtained first.

# 5. Log-Skeleton Model

I use this orientation:

* `("A", "B")` in `always_before` means: whenever `A` occurs, `B` must have occurred earlier.
* `("A", "B")` in `always_after` means: whenever `A` occurs, `B` must occur later.
* `("A", "B")` in `never_together` means: `A` and `B` must not co-occur in the same case.

```python
log_skeleton = {
    "equivalence": set(),

    "always_before": {
        ("Capture Master Data", "Receive Onboarding Request"),
        ("Run Sanctions Screening", "Receive Onboarding Request"),
        ("Verify Bank Account", "Receive Onboarding Request"),

        ("Classify Risk", "Capture Master Data"),
        ("Classify Risk", "Run Sanctions Screening"),
        ("Classify Risk", "Verify Bank Account"),

        ("Enhanced Due Diligence", "Classify Risk"),
        ("Manager Approval", "Classify Risk"),
        ("Compliance Approval", "Enhanced Due Diligence"),
        ("Compliance Approval", "Classify Risk"),

        ("Sanctions Escalation", "Run Sanctions Screening"),

        ("Activate Vendor", "Classify Risk"),
        ("Reject Vendor", "Classify Risk"),
        ("Release First Payment", "Activate Vendor"),
        ("Close Onboarding", "Receive Onboarding Request"),
    },

    "always_after": {
        ("Receive Onboarding Request", "Close Onboarding"),

        ("Request Clarification", "Receive Clarification"),
        ("Sanctions Escalation", "Obtain Legal Opinion"),

        ("Enhanced Due Diligence", "Compliance Approval"),
        ("Manager Approval", "Activate Vendor"),
        ("Compliance Approval", "Activate Vendor"),

        ("Activate Vendor", "Release First Payment"),
        ("Reject Vendor", "Close Onboarding"),
        ("Release First Payment", "Close Onboarding"),
    },

    "never_together": {
        ("Reject Vendor", "Activate Vendor"),
        ("Enhanced Due Diligence", "Manager Approval"),
        ("Compliance Approval", "Manager Approval"),
        ("Reject Vendor", "Manager Approval"),
        ("Reject Vendor", "Compliance Approval"),
    },

    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1},
        "Close Onboarding": {1},
    },

    "directly_follows": set(),
}
```

I leave `equivalence` empty. Although `Activate Vendor` and `Release First Payment` normally co-occur in the backbone, R11 introduces post-activation bank-detail changes and suspension behavior, so a hard equivalence would be too brittle.

I leave `directly_follows` empty because the model explicitly allows concurrency and interleavings. For example, the three checks after `Receive Onboarding Request` need not appear in a fixed directly-follows order.

There is intentional overlap with the procedural and DECLARE layers: terminal noncoexistence, approval separation, and payment-after-activation are duplicated because they are central controls. There is also intentional non-coverage: R5/R6 and the “another verification” part of R11 are not encoded in the Log Skeleton because they require conditional state.

| Pair                                             | Mean | Standard deviation | Warning if elapsed is outside |
| ------------------------------------------------ | ---: | -----------------: | ----------------------------: |
| `Request Clarification -> Receive Clarification` |  48h |                24h |                     0h to 96h |

# 7. Resource- and Data-Aware Checks

Required event attributes:

| Check                            | Required attributes                                                                                                                              | Missing-attribute handling                                                                                                                                                |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Event ordering and elapsed times | `case:concept:name`, `concept:name`, `time:timestamp`                                                                                            | Cannot evaluate; fail-closed for operational gating, `not evaluated` for retrospective analytics.                                                                         |
| Four-eyes checks                 | `org:resource` on `Verify Bank Account`, approval events, `Capture Master Data`, and `Activate Vendor`                                           | Missing resource means the rule cannot be proven. Use manual review or fail-closed before activation/payment.                                                             |
| R6 emergency override            | Case/event attribute such as `emergency_authorized`, external authorization ID, authorization timestamp, and at least two authorizing identities | Under strict model, missing override data does not matter because override is not accepted. Under operations override, missing data gives `policy-dependent`, not `pass`. |
| R11 post-activation bank change  | Event timestamps for `Activate Vendor`, `Change Bank Details`, `Suspend Vendor`, `Verify Bank Account`, `Release First Payment`                  | Missing timestamps make “after,” “later,” and “before” impossible to verify.                                                                                              |

Executable-style validation:

```python
import pandas as pd

FINAL_OUTCOMES = {"Reject Vendor", "Activate Vendor"}

def _events(case_df, activity):
    return case_df[case_df["concept:name"] == activity].sort_values("time:timestamp")

def _first_time(case_df, activity):
    ev = _events(case_df, activity)
    if ev.empty:
        return None
    return ev.iloc[0]["time:timestamp"]

def _resources(case_df, activity):
    ev = _events(case_df, activity)
    if ev.empty:
        return set()
    if "org:resource" not in ev.columns or ev["org:resource"].isna().any():
        return None
    return set(ev["org:resource"])

def validate_vendor_case(case_df, emergency_policy="strict_legal"):
    """
    emergency_policy:
      - "strict_legal": implements R5 as hard precedence.
      - "operations_override": permits R6 only with auditable external authorization.
    Returns a list of findings. Empty list means pass for this layer.
    """
    findings = []

    required_cols = {"concept:name", "time:timestamp"}
    missing = required_cols - set(case_df.columns)
    if missing:
        return [{
            "requirement": "schema",
            "status": "fail",
            "message": f"Missing required columns: {sorted(missing)}",
        }]

    case_df = case_df.sort_values("time:timestamp").reset_index(drop=True)

    # R2 and R1 branch consistency.
    n_activate = (case_df["concept:name"] == "Activate Vendor").sum()
    n_reject = (case_df["concept:name"] == "Reject Vendor").sum()
    n_manager = (case_df["concept:name"] == "Manager Approval").sum()
    n_compliance = (case_df["concept:name"] == "Compliance Approval").sum()

    if n_activate and n_reject:
        findings.append({
            "requirement": "R1/R2",
            "status": "fail",
            "message": "Case contains both Activate Vendor and Reject Vendor.",
        })

    if n_activate and not n_reject:
        if n_manager + n_compliance != 1:
            findings.append({
                "requirement": "R2",
                "status": "fail",
                "message": "Accepted case must contain exactly one applicable approval.",
            })

    if n_reject and not n_activate:
        if n_manager or n_compliance:
            findings.append({
                "requirement": "R2",
                "status": "fail",
                "message": "Rejected case must not contain Manager Approval or Compliance Approval.",
            })

    # R3 clarification state machine.
    pending_clarification = False
    for _, row in case_df.iterrows():
        act = row["concept:name"]

        if act == "Request Clarification":
            if pending_clarification:
                findings.append({
                    "requirement": "R3",
                    "status": "fail",
                    "message": "New Request Clarification occurred before Receive Clarification.",
                    "time": row["time:timestamp"],
                })
            pending_clarification = True

        elif act == "Receive Clarification":
            pending_clarification = False

        elif act in FINAL_OUTCOMES and pending_clarification:
            findings.append({
                "requirement": "R3",
                "status": "fail",
                "message": f"{act} occurred while clarification was pending.",
                "time": row["time:timestamp"],
            })

    if pending_clarification:
        findings.append({
            "requirement": "R3",
            "status": "fail",
            "message": "Trace ended with unresolved clarification request.",
        })

    # R7: escalation only after screening.
    first_screening = _first_time(case_df, "Run Sanctions Screening")
    for _, esc in _events(case_df, "Sanctions Escalation").iterrows():
        if first_screening is None or first_screening >= esc["time:timestamp"]:
            findings.append({
                "requirement": "R7",
                "status": "fail",
                "message": "Sanctions Escalation occurred before Run Sanctions Screening.",
                "time": esc["time:timestamp"],
            })

    # R5/R6: legal opinion before activation after escalation.
    escalation_times = list(_events(case_df, "Sanctions Escalation")["time:timestamp"])
    opinion_times = list(_events(case_df, "Obtain Legal Opinion")["time:timestamp"])

    for _, activation in _events(case_df, "Activate Vendor").iterrows():
        t_a = activation["time:timestamp"]

        relevant_escalations = [t_s for t_s in escalation_times if t_s < t_a]
        if not relevant_escalations:
            continue

        latest_relevant_escalation = max(relevant_escalations)
        prior_opinions = [
            t_o for t_o in opinion_times
            if latest_relevant_escalation < t_o < t_a
        ]

        if prior_opinions:
            continue

        if emergency_policy == "strict_legal":
            findings.append({
                "requirement": "R5",
                "status": "fail",
                "message": "Activate Vendor occurred after Sanctions Escalation but before Obtain Legal Opinion.",
                "time": t_a,
            })

        elif emergency_policy == "operations_override":
            has_flag = (
                "emergency_authorized" in case_df.columns
                and bool(case_df["emergency_authorized"].fillna(False).any())
            )
            has_joint_auth = (
                "joint_authorization_id" in case_df.columns
                and case_df["joint_authorization_id"].notna().any()
            )

            later_opinions = [t_o for t_o in opinion_times if t_o > t_a]
            opinion_within_24h = any(
                t_o <= t_a + pd.Timedelta(hours=24)
                for t_o in later_opinions
            )

            if not has_flag or not has_joint_auth:
                findings.append({
                    "requirement": "R6",
                    "status": "policy-dependent",
                    "message": "Emergency activation cannot be proven from the event log.",
                    "time": t_a,
                })
            elif not opinion_within_24h:
                findings.append({
                    "requirement": "R6",
                    "status": "fail",
                    "message": "Emergency activation lacks legal opinion within 24 hours.",
                    "time": t_a,
                })

    # R9: four-eyes resource checks.
    if "org:resource" not in case_df.columns:
        findings.append({
            "requirement": "R9",
            "status": "fail",
            "message": "Missing org:resource; four-eyes rules cannot be verified.",
        })
    else:
        verify_resources = _resources(case_df, "Verify Bank Account")
        capture_resources = _resources(case_df, "Capture Master Data")

        for approval in ["Manager Approval", "Compliance Approval"]:
            approval_resources = _resources(case_df, approval)
            if approval_resources is None or verify_resources is None:
                if not _events(case_df, approval).empty:
                    findings.append({
                        "requirement": "R9",
                        "status": "fail",
                        "message": f"Missing resource for Verify Bank Account or {approval}.",
                    })
            elif verify_resources & approval_resources:
                findings.append({
                    "requirement": "R9",
                    "status": "fail",
                    "message": f"Same resource performed Verify Bank Account and {approval}.",
                    "resources": sorted(verify_resources & approval_resources),
                })

        activate_resources = _resources(case_df, "Activate Vendor")
        if activate_resources is None or capture_resources is None:
            if not _events(case_df, "Activate Vendor").empty:
                findings.append({
                    "requirement": "R9",
                    "status": "fail",
                    "message": "Missing resource for Capture Master Data or Activate Vendor.",
                })
        elif capture_resources & activate_resources:
            findings.append({
                "requirement": "R9",
                "status": "fail",
                "message": "Same resource performed Capture Master Data and Activate Vendor.",
                "resources": sorted(capture_resources & activate_resources),
            })

    # R10: at-most-once rules.
    for activity in ["Activate Vendor", "Reject Vendor", "Release First Payment"]:
        count = (case_df["concept:name"] == activity).sum()
        if count > 1:
            findings.append({
                "requirement": "R10",
                "status": "fail",
                "message": f"{activity} occurred {count} times.",
            })

    # R11: post-activation bank-detail change.
    activation_time = _first_time(case_df, "Activate Vendor")
    if activation_time is not None:
        changes = _events(case_df, "Change Bank Details")
        suspends = _events(case_df, "Suspend Vendor")
        verifications = _events(case_df, "Verify Bank Account")
        releases = _events(case_df, "Release First Payment")

        for _, change in changes.iterrows():
            t_c = change["time:timestamp"]
            if t_c <= activation_time:
                continue

            later_suspends = suspends[suspends["time:timestamp"] > t_c]
            if later_suspends.empty:
                findings.append({
                    "requirement": "R11",
                    "status": "fail",
                    "message": "Change Bank Details after activation was not followed by Suspend Vendor.",
                    "time": t_c,
                })

            later_releases = releases[releases["time:timestamp"] > t_c]
            for _, rel in later_releases.iterrows():
                t_r = rel["time:timestamp"]
                intervening_verify = verifications[
                    (verifications["time:timestamp"] > t_c)
                    & (verifications["time:timestamp"] < t_r)
                ]
                if intervening_verify.empty:
                    findings.append({
                        "requirement": "R11",
                        "status": "fail",
                        "message": "Later Release First Payment lacked a new Verify Bank Account after bank-detail change.",
                        "change_time": t_c,
                        "release_time": t_r,
                    })

    return findings
```

# 9. Contradictions, Redundancies, and Blind Spots

**Duplicated enforcement across layers.**
Several rules appear in more than one layer. `Reject Vendor`/`Activate Vendor` exclusivity is enforced by the ProcessTree XOR, DECLARE `noncoexistence`, and Log Skeleton `never_together`. Approval separation is enforced structurally by the ProcessTree and declaratively by noncoexistence rules. This redundancy is intentional for critical controls, but deployment should nominate one authoritative source per finding to avoid duplicate tickets.

**R5/R6 contradiction.**
R5 says legal opinion must precede activation under all circumstances after escalation. R6 says emergency activation before legal opinion may be allowed with external authorization. These cannot be silently merged into one activity-only rule. They require either a strict policy or an explicit exception model with auditable emergency attributes.

**Loops and conditional constraints.**
Clarification cycles make simple frequency or equivalence rules unsafe. A case may have several `Request Clarification` and `Receive Clarification` events, so a Log Skeleton equivalence or exactly-one rule would be wrong. `altresponse` is better than ordinary `response`, but still needs a stateful check for “before final outcome.”

**Post-activation changes can conflict with simple backbone assumptions.**
R11 implies that after activation, a bank-detail change can introduce `Suspend Vendor` and another `Verify Bank Account` before any later `Release First Payment`. Therefore, a naive activation-frequency rule for `Verify Bank Account` would be inconsistent with R11. I intentionally do not set `Verify Bank Account` to exactly once.

**Vacuity in DECLARE rules.**
`response[("Sanctions Escalation", "Obtain Legal Opinion")]` passes every case with no escalation. `response[("Change Bank Details", "Suspend Vendor")]` passes every case with no bank-detail change. `noncoexistence` passes if neither activity occurs. Vacuous satisfaction is normal in DECLARE, but dashboards should not present it as evidence that the control was actively exercised.

**Missing case attributes.**
The supplied traces do not contain risk class, emergency authorization, authorization timestamp, or joint authorizers. Therefore, route correctness and R6 exception validity cannot be inferred from activity labels alone.

**Resource visibility.**
R9 depends on `org:resource`. If resources are missing, pseudonymized inconsistently, or recorded at team rather than person level, four-eyes validation may be impossible. Passing the activity sequence is not evidence of segregation of duties.

**Timestamp-only limitations.**
The traces provide event timestamps, not start/end intervals. The apparent concurrency of the three checks is modeled procedurally, but timestamp order alone does not prove that work was truly parallel. The temporal profile also cannot distinguish waiting time from service time, supplier delay, system delay, or weekend effects.

**Support and confidence are not normative truth.**
In the DECLARE dictionary, `support` and `confidence` are required metadata. They should not be interpreted as discovered empirical reliability from the eight test cases. A rule with `confidence: 0.95` can still be mandatory if the policy owner declares it mandatory; conversely, a high empirical confidence would not make an unsupported rule legally binding.

# 10. Deployment Recommendation

Use the **ProcessTree converted to an accepting Petri net** as the canonical procedural representation for the stable onboarding backbone. Run it on a projection to the backbone activities so that cross-cutting events do not create false procedural failures.

Use an explicit **policy validation layer** as the authoritative source for conditional, resource-aware, and data-aware obligations: R2 conditional approval counts, R3 pending clarification before final outcome, R5/R6 legal-emergency handling, R9 segregation of duties, and R11 post-activation bank-detail changes.

Recommended conformance order:

1. **Schema validation.** Confirm required columns: case ID, activity, timestamp, resource, and any external authorization attributes if R6 override mode is enabled.
2. **Basic event-order validation.** Sort events, detect duplicate timestamps if they affect rule interpretation, and verify unique start/close assumptions.
3. **Procedural replay on the backbone projection.** Identify violations of the core onboarding path.
4. **Hard declarative and Log Skeleton checks.** Apply noncoexistence, precedence, response, activation-frequency, and case-level ordering constraints.
5. **Stateful resource/data-aware checks.** Evaluate unresolved clarifications, four-eyes rules, legal-opinion-before-activation, emergency override evidence, and post-activation bank-detail changes.
6. **Temporal profile warnings.** Add warnings for timing outliers after hard conformance results are known.

Contradictory findings should be surfaced explicitly by requirement ID, layer, timestamp, and resource. For example, T6 should not be labeled simply “pass” or “fail” without context. The system should show: “R5 strict legal model: fail at `Activate Vendor@13`; R6 operations override: potentially allowed only with external joint authorization; authorization not present in event log.” This prevents an activity-only conformance score from hiding a real policy conflict.
