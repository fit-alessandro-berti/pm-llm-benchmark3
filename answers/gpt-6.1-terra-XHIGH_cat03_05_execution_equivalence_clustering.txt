## 1. Equivalence design space

Treat each execution as the supplied ordered events, their event-to-object (E2O) incidences, and the explicitly supplied object-to-object (O2O) relations. The lead Order and the local/external status of each object are distinguished. IDs themselves are arbitrary. An unmentioned O2O relation is unknown, not an assertion that the relation is absent. For reproducibility, the comparisons below operate on the stated records; they do not fill in omitted relations from business assumptions.

**Activity-sequence equivalence.** Two executions are equivalent if their ordered lists of activity labels are identical, including repetitions. It preserves the labels and their order and count; it discards all object information, relations, attributes, and elapsed times. If events have the same timestamp, represent each timestamp as a sorted multiset of labels and compare the resulting ordered list of multisets. Thus simultaneous events are not ordered by arbitrary IDs. The supplied sequences are already ordered and need no tie resolution.

**Typed structural equivalence.** Two executions are equivalent when there is a bijection between their objects preserving type, local/external status, and the distinguished lead, such that it preserves every position's activity and E2O incidence, and every explicitly recorded directed O2O edge with its relation label. The timestamp values and all other attributes are ignored. This preserves object counts, repeated events, sharing, topology, and relation qualifiers. It discards the actual object and event IDs and elapsed times. For equal timestamps, allow a bijection between the events in the same timestamp block, preserving activity and incidence; unequal timestamps retain their block order. “Typed structural” here is deliberately qualifier-sensitive; an alternative that drops O2O labels is also defensible.

**Preferred business-semantic equivalence.** Project each execution to the tuple `(D, M, L, F, R, S, P)` defined in section 2, and equate executions exactly when the tuples match. This preserves the number of dispatch and payment events, external sharing at logistics and financial events, return activity, replacement/removal qualifiers, and partial-settlement qualifiers. It deliberately discards package count, most E2O and O2O topology, add/pack counts, timing, and event order. In particular, splitting an order into two packages for one delivery does not by itself change the business cluster. All events in the supplied execution count; there is no implied completion, value, allocation, or causal relation beyond what is recorded. Equal-time and concurrent events need no tie-breaking because this projection is order-independent.

Each definition is equality of a deterministic representation, or isomorphism of finite labeled structures, so it is reflexive, symmetric, and transitive. These properties depend on a fixed vocabulary and normalization policy. A fuzzy similarity threshold would not necessarily be transitive and is not the relation used here.

## 2. Canonical signatures

For the preferred relation, use the following exact projection. First normalize activity and qualifier spellings using a fixed, versioned vocabulary; do not infer a missing qualifier. `external(o)` means the supplied external flag, not a property of the identifier except that `EXT` is the flag in this example. The logistics activities are `Pack Package` and `Dispatch`; the financial activities are `Issue Invoice` and `Record Payment`.

```python
def semantic_key(execution):
    events = execution.events  # supplied events of this lead execution
    labels = [e.activity for e in events]
    qualifiers = {edge.qualifier for edge in execution.o2o}

    def shared_at(activities):
        return any(external(o)
                   for e in events if e.activity in activities
                   for o in e.objects)

    return (
        labels.count("Dispatch"),                     # D
        labels.count("Record Payment"),               # M
        shared_at({"Pack Package", "Dispatch"}),       # L
        shared_at({"Issue Invoice", "Record Payment"}),# F
        "Return Item" in labels,                      # R
        bool(qualifiers & {"replaces", "removed_before_dispatch"}), # S
        "partially_settles" in qualifiers,            # P
    )
```

The tuple is canonical because it contains no object or event identifiers and uses counts and set membership. A replacement edge involving packages in X8 and one involving items in X7 both set `S`; the separate return and dispatch features distinguish those executions. `P` records explicit partial-settlement evidence, not an inferred outstanding balance. This deliberately small signature is a business projection, not a canonical encoding of the entire typed graph. In other datasets the external flag and qualifiers must be supplied or derived by a documented policy; absence of a recorded fact is not proof it did not happen.

## 4. Cluster interpretations

- **S0 — `(1,1,0,0,0,0,0)`:** One dispatch and one recorded payment, with no recorded sharing, return, replacement, or partial settlement. X3 shows that this class can include consolidated delivery of separately packed items. Consolidation may save delivery cost, but package-level workload differs within the cluster. A single Order trace hides that difference and package-to-item associations. The class is stable to ID repair and package-count corrections that preserve the defining features; it is sensitive to discovery of omitted sharing or exceptions.
- **S1 — `(2,2,0,0,0,0,1)`:** Split fulfillment with explicitly partial then completed settlement. Multiple deliveries and payments create coordination and reconciliation work, but can support early shipment or flexible payment. An Order trace with deduplicated labels hides both repetitions; an Invoice trace alone misses the delivery pattern. It is sensitive to payment-event deduplication and settlement-qualifier repair, though losing only the qualifier leaves its dispatch and payment counts distinct in this sample.
- **S2 — `(1,1,1,0,0,0,0)`:** Logistics are shared with another order, while the stated invoice bills only the lead order. Consolidation may reduce shipping costs; cross-order packing makes attribution and privacy-sensitive handling harder. Flattening by Order duplicates the shared pack and dispatch across cases or obscures that another order participated. The class depends on correctly identifying external participation and is sensitive to execution-boundary repair.
- **S3 — `(1,1,0,1,0,0,0)`:** Logistics are local, but invoicing and settlement are shared. Consolidated billing may simplify collection; the recorded payment does not establish how much is allocated to O6. Flattening by Order can misleadingly associate the entire payment with each order. The classification is sensitive to external-order identification and invoice-link repair; adding allocation evidence improves interpretation but does not change this signature.
- **S4 — `(1,1,0,0,0,1,0)`:** An item replacement and removal are recorded before dispatch. This may reflect a substitution or correction; the reason and commercial acceptability are not supplied. An activity-only Order trace hides these qualified relations, while an Item trace loses the order-wide context. This class is sensitive to qualifier normalization or removal and to corrections of the replacement link.
- **S5 — `(2,1,0,0,1,1,0)`:** A dispatched item is returned, inspected, repacked, and dispatched again. Rework creates delay and handling cost and may reveal a quality issue; its cause is not established. An Invoice trace misses the return loop, while a simple Order trace cannot express which item and package were involved. The class is sensitive to missing return events or repair of replacement links, but not to local ID renaming.

Stability statements are conditional on the supplied data. In particular, an unrecorded return or missing cross-order edge can move an execution even if its actual business behavior never changed.

## 5. Borderline cases

**X1 versus X2.** Literal comparison of IDs or of the strings `I11` and `I22` separates them. Typed isomorphism maps the first added item to the first added item and the second to the second, so it merges them; their identical activity labels also give the same sequence. The apparent reversal is only an identifier convention.

**X1 versus X5.** Activity sequences agree, and a lead-only projection that removes external objects can merge them. The preferred relation and full typed structure separate them because logistics events include external participants. The latter preserves the fact that a package is shared even though the invoice is local.

**X1 versus X6.** Activity sequences and a projection counting only local objects agree. The preferred relation separates shared financial execution from local financial execution; a typed graph also retains the extra order in invoice and payment incidence. The shared payment provides no order-level allocation, so it cannot be treated as payment in full for O6 on the supplied evidence.

**X1 versus X7.** Activity sequences agree. The preferred relation separates explicit replacement/removal, while typed structure also sees the extra Item incidence at dispatch and the O2O edges. A coarser definition that ignores item-level incidence and replacement qualifiers merges them, but loses evidence about the dispatched contents.

**X3 versus X4.** A broad class such as “multiple packages for one order” merges them. Sequence, typed structure, and the preferred signature separate them: X3 consolidates two packages into one delivery and has one payment; X4 has two deliveries, two payments, and a partial-settlement qualifier. Split packing alone does not imply split delivery.

**X4 versus X8.** A logistics projection counting two dispatches merges them. The preferred relation separates X4's two payments and partial settlement from X8's return and replacement. Typed structure and activity sequences also separate them. Two dispatches can represent parallel fulfillment or rework, with different operational meanings.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

In the locally installed PM4Py 2.7.23.4 implementation, the function splits around objects of the requested type using an ancestors/descendants object-interaction graph, renames objects, and constructs a `VARIANT2` description without timestamp values. The key is a pair: an ordered tuple of event tuples `(activity, related object IDs...)`, and a tuple of `(object ID, object type)` pairs. Thus it retains event activity, repetition, sorted event order, E2O incidence, object IDs after renaming, types, and multiplicity. Timestamps still influence sorting and renaming, even though their values are omitted from the key. Event IDs break some sort ties but are not themselves in the key. O2O edges and qualifiers, E2O qualifiers, attributes, and explicit external flags are not included in that description. The split may also differ from the compact execution boundaries in the question.

The default renamer replaces IDs per object type using lifecycle start/end and lexicographic ID as a tie-breaker. Therefore it reduces raw-ID sensitivity but is not a general graph-isomorphism canonicalizer: ties can still cause structurally equivalent executions to receive different renamed keys. If a type is excluded from renaming, its raw IDs directly make keys finer. Conversely, distinct executions can have the same PM4Py key if they differ only in omitted qualifiers or O2O edges. Never recover semantic features from the key alone; inspect every returned execution, including members of the same exact-key group.

The following outline implements the projection above for this question's `EXT` convention. It selects events incident to the central Order and O2O edges between their incident objects. A production importer must supply reliable external flags, execution boundaries, normalized qualifiers, and missing-data handling; the splitter's larger connected slice alone does not establish those facts.

```python
from collections import defaultdict
import pm4py

LOGISTICS = {"Pack Package", "Dispatch"}
FINANCE = {"Issue Invoice", "Record Payment"}

def key_for_order(oc, lead):
    eid, oid = oc.event_id_column, oc.object_id_column
    activity, qual = oc.event_activity, oc.qualifier

    # Restrict to events directly incident to this lead Order.
    lead_events = set(oc.relations.loc[oc.relations[oid] == lead, eid])
    ev = oc.events[oc.events[eid].isin(lead_events)]
    rel = oc.relations[oc.relations[eid].isin(lead_events)]
    labels = list(ev[activity])
    activity_by_event = dict(zip(ev[eid], ev[activity]))

    def shared_at(activities):
        return any(activity_by_event.get(row[eid]) in activities
                   and str(row[oid]).startswith("EXT")
                   for _, row in rel.iterrows())

    incident = set(rel[oid])
    edges = oc.o2o
    if edges is None or edges.empty:
        qualifiers = set()
    else:
        edges = edges[edges[oid].isin(incident) &
                      edges[oid + "_2"].isin(incident)]
        qualifiers = set(edges[qual].dropna())

    return (labels.count("Dispatch"), labels.count("Record Payment"),
            shared_at(LOGISTICS), shared_at(FINANCE),
            "Return Item" in labels,
            bool(qualifiers & {"replaces", "removed_before_dispatch"}),
            "partially_settles" in qualifiers)

exact_groups = pm4py.cluster_equivalent_ocel(
    ocel, object_type="Order", max_objs=10000
)
semantic_groups = defaultdict(list)
for exact_key, executions in exact_groups.items():
    for execution in executions:
        lead = execution.parameters["@@central_object"]
        semantic_groups[key_for_order(execution, lead)].append(execution)
```

An exact description is useful for debugging ingestion, finding repeated recorded variants, or auditing precisely the fields it preserves. For full qualifier-sensitive structural equivalence, construct and canonically label a typed graph from each returned execution, rather than assuming the PM4Py key is that graph. A post-processing pass can merge returned groups under a coarser projection, as above, or subdivide a returned group using information omitted from the key.

In the inspected version, `max_objs` limits how many lead-type objects are processed, not the size of each resulting execution; the first `max_objs` in the internal object order are selected. A finite limit therefore yields a potentially biased subset, not a complete clustering. Large connected executions can make graph construction, transitive closure, filtering, and canonical graph comparisons expensive; sharing can also pull in more context than the intended business case. Inspect coverage and boundary choices before interpreting frequencies.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** Under the preferred signature, `S` and `P` become false. X7 joins S0 because its only retained semantic distinction was replacement/removal. X8 retains a return and two dispatches; X4 retains two dispatches and two payments, so neither joins S0. This is loss of recorded semantics, not proof those actions did not occur. A qualifier-insensitive typed graph can still distinguish X7 through its extra dispatch incidence and unlabelled edges.
- **Ignore external objects:** Remove them from event incidence and recompute sharing flags. X5 and X6 join S0; their cross-order logistics and financial risks are no longer visible. Do not retain a hidden sharing flag while claiming external information was discarded.
- **Collapse consecutive runs of identical labels:** Replace each maximal adjacent run with one event, union its incidences, and retain all O2O edges and qualifiers. X3's two consecutive packs and X4's consecutive payments collapse; the latter's signature becomes `(2,1,0,0,0,0,1)`. No preferred clusters merge in this sample. Collapsing all occurrences of a label regardless of position would additionally erase X4's and X8's second dispatch, and can conceal a return/rework loop.
- **Use a partial order for packing and dispatch:** Preserve known precedence such as a package's pack before its dispatch, but do not impose an ordering on independent package operations solely from timestamps. This can merge typed variants with different interleavings of the same independent work. It does not merge X3 with X4: their delivery incidence, dispatch count, and payment behavior differ. The preferred signatures already discard event order, so their assignments do not change.
- **Represent payment multiplicity as an amount instead:** Drop `M` only if reliable comparable amounts and an allocation policy exist. X4 remains distinct here because it has two dispatches and partial-settlement evidence, but other executions with one versus several payments could merge. No amounts are supplied, so equal total value or settlement status cannot be assumed for these examples.

## 8. Limitations and recommendation

For **compliance monitoring**, use qualifier-sensitive typed structure augmented with the attributes, policies, timestamps, and allocation evidence required by the specific control. Fine-grained distinctions matter, but recorded absence and actual absence must not be conflated.

For **operational segmentation**, use the preferred semantic projection as a starting point: it separates sharing, split dispatch, partial settlement, and rework while grouping X3 with the routine single-delivery cases. Add package count if staffing or packing cost is the decision of interest.

For **root-cause analysis**, retain the full typed graph, qualifiers, timing, and relevant attributes, then compare related variants and their context. A cluster alone cannot establish why a return, substitution, or partial payment occurred.

For **descriptive reporting**, use a documented coarser projection and report both its coverage and the dimensions it suppresses. Activity sequences may be appropriate for a high-level overview, but cannot substantiate claims about sharing or item-level behavior.

These purposes need different resolutions: a coarse class is easier to summarize, while an investigation or control may depend on distinctions that class intentionally discards. The proposed signatures describe the supplied records, not guaranteed real-world completion, amounts, causes, or missing links.
