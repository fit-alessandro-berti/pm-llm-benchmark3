## 1. Equivalence design space

To effectively cluster object-centric executions, we must establish rigorous equivalence relations that dictate when two executions are considered identical. We define three primary equivalence relations below, spanning from coarse behavioral patterns to fine-grained semantic topologies.

### 1. Activity-sequence equivalence (ASE)
- **Formal definition:** Two executions are equivalent if and only if their chronologically ordered sequence of event activity labels is identical. Let an execution $E$ be a sequence of events $(e_1, e_2, \dots, e_n)$. ASE maps $E$ to a tuple of labels $(L(e_1), L(e_2), \dots, L(e_n))$. Two executions $E$ and $E'$ are equivalent if their tuples are identical.
- **Invariants preserved:** The strict temporal order and exact occurrence of business activities.
- **Information discarded:** All object-centric information is ignored. This includes object types, local and external object identifiers, object multiplicities per event, Event-to-Object (E2O) incidence, and Object-to-Object (O2O) qualifiers. 
- **Properties:** The relation is strictly reflexive, symmetric, and transitive, as it relies on exact string-tuple equality.
- **Concurrency handling:** If events occur at the exact same timestamp, a deterministic tie-breaking mechanism (such as lexicographical sorting by activity label) must be applied to ensure reproducible tuples. Otherwise, concurrent events would randomly permute the sequence, fracturing otherwise equivalent clusters.

### 2. Typed structural equivalence under identifier renaming (TSE)
- **Formal definition:** Two executions are equivalent if there exists a bijective mapping between their local object identifiers such that substituting the identifiers makes the executions perfectly identical in their E2O structure. Operationally, each event is represented by its activity label and the multiset of object types involved. $E$ and $E'$ are equivalent if their sequence of tuples $(L(e_i), M(e_i))$ is identical, where $M(e_i)$ is a frequency map of object types (e.g., `{Order: 1, Item: 2, Package: 1}`).
- **Invariants preserved:** Temporal order of activities, types of objects interacting at each step, and the exact count (multiplicity) of objects of each type per event. 
- **Information discarded:** The specific, raw string values of local object identifiers (which are typically auto-generated UUIDs). Any explicit differentiation between local and external objects is lost unless the type itself encodes it. Complex O2O edge attributes are similarly ignored.
- **Properties:** The relation is reflexive, symmetric, and transitive. It mathematically defines an isomorphism over the typed bipartite E2O execution graphs.
- **Concurrency handling:** Concurrent events require graph isomorphism checks rather than simple string matching, as the events can form unordered subgraphs. Topological sorting based on E2O incidence can serialize concurrent events deterministically.

### 3. Business-semantic equivalence (BSE)
- **Formal definition:** Two executions are equivalent if their canonical lifecycle signatures match. This signature abstracts away raw local identifiers but explicitly preserves the topological footprint of the execution: object types, multiplicities, the specific distinction between local and external objects (`EXT-` prefixes), and enriched O2O qualifiers (like `removed_before_dispatch`). 
- **Invariants preserved:** The core business outcome, logistic and financial topologies (e.g., shared vs. isolated boundaries), exception motifs (e.g., substitutions and removals), and the structural interplay of multiple items.
- **Information discarded:** Irrelevant variations in initial object naming, chronological permutations of strictly independent concurrent events (e.g., adding two independent items to a cart in different orders), and meaningless identifier hashes.
- **Properties:** Reflexive, symmetric, and transitive, achieved by mapping the execution to a deterministic, order-invariant canonical string representation before equality testing.
- **Concurrency handling:** Concurrent events are grouped into order-agnostic itemsets or sorted topologically. If `Add Item` operations happen simultaneously, they are canonically sorted by their mapped local aliases, preventing concurrency from fracturing semantic clusters.

## 2. Canonical signatures

To implement Business-Semantic Equivalence (BSE), we require a reproducible canonical signature scheme. The following Python-like pseudocode deterministically canonicalizes an execution graph into a string signature. It preserves E2O incidence, external flags, O2O qualifiers, and multiplicities while remaining strictly invariant to local identifier renaming.

```python
def generate_bse_signature(execution):
    """
    Generates a canonical signature for an object-centric execution.
    Assumes execution.events is a list of events ordered by timestamp.
    """
    alias_map = {}
    type_counters = {}
    canonical_events = []
    
    for event in execution.events:
        canonical_objects = []
        
        # Iterate over object types and their associated raw IDs in the event
        for obj_type, raw_ids in event.objects.items():
            for raw_id in sorted(raw_ids):
                # Preserve external object semantics explicitly
                if raw_id.startswith("EXT"):
                    canonical_objects.append(f"EXT_{obj_type}")
                else:
                    # Assign a deterministic local alias based on first appearance
                    if raw_id not in alias_map:
                        type_counters[obj_type] = type_counters.get(obj_type, 0) + 1
                        alias_map[raw_id] = f"{obj_type}_{type_counters[obj_type]}"
                    canonical_objects.append(alias_map[raw_id])
                    
        # Sort the mapped objects to ensure stable E2O representation per event
        canonical_objects.sort()
        obj_string = ",".join(canonical_objects)
        canonical_events.append(f"{event.activity}[{obj_string}]")
        
    # Serialize events. (Concurrency handling: sort adjacent same-timestamp events here if needed)
    events_signature = " -> ".join(canonical_events)
    
    # Process O2O qualifiers
    qualifiers = []
    for qual in execution.o2o_qualifiers:
        src = alias_map.get(qual.source, qual.source)
        tgt = alias_map.get(qual.target, qual.target)
        qualifiers.append(f"({src})-[{qual.label}]->({tgt})")
        
    qualifiers_signature = " | ".join(sorted(qualifiers))
    
    return f"EVENTS: {events_signature} || O2O: {qualifiers_signature}"
```

## 4. Cluster interpretations

### Standard-Isolated (X1, X2)
- **Concise signature:** 1 Order : 2 Items : 1 Package : 1 Delivery : 1 Invoice : 1 Payment (No EXT).
- **Business behavior:** The idealized happy-path fulfillment flow. All requested items are sourced together, packed into a single box, dispatched in a single vehicle, and paid off in a single transaction.
- **Operational risks/opportunities:** Represents the baseline for operational excellence. Opportunities lie in maximizing the percentage of orders falling into this cluster to ensure predictable margins.
- **Traditional flattening:** Case-centric flattening handles this flawlessly. Because all multiplicities collapse cleanly to 1:1 at the package/delivery/invoice level, tabular data models accurately reflect the truth.
- **Stability under repair:** Highly stable. Standard data quality scrubbing or imputation algorithms rarely distort this simple topology.

### Logistics-Consolidated (X3)
- **Concise signature:** N Packs -> 1 Dispatch.
- **Business behavior:** Items are handled independently during warehouse packing (e.g., arriving from different warehouse zones or requiring different packaging types), but are ultimately consolidated onto a single delivery truck.
- **Operational risks/opportunities:** Risk of bottlenecks where one package waits on the loading dock for the other. Opportunity to analyze warehouse zoning to see why items weren't picked and packed together originally.
- **Traditional flattening:** If flattened to the Order level, the distinction of multiple packages is lost. If flattened to the Item level, the consolidated delivery is duplicated, making freight costs appear artificially high.
- **Stability under repair:** Moderately stable. Aggressive aggregation scripts might mistakenly collapse the two `Pack Package` events into one, converting this cluster into a Standard-Isolated signature.

### Logistics-Split (X4)
- **Concise signature:** N Packs -> N Dispatches -> N Payments.
- **Business behavior:** Complete operational divergence. The items are packed separately, shipped in completely different deliveries, and paid for via separate, partial payments. 
- **Operational risks/opportunities:** Exponentially higher cost-to-serve. Requires double shipping fees and complex financial reconciliation to ensure the sum of partial payments equals the invoice total.
- **Traditional flattening:** Fails catastrophically. Cartesian products emerge if flattened by Item and Payment simultaneously, causing catastrophic duplication of revenue and costs in BI tools.
- **Stability under repair:** Vulnerable. Financial reconciliation scripts often aggregate partial payments (`Record Payment`) into a single daily lump sum, artificially mutating the signature.

### Shared-Logistics (X5)
- **Concise signature:** `EXT_Order` and `EXT_Item` present in logistics events.
- **Business behavior:** Cross-order batching. The warehouse logistics team placed items from multiple different orders into the same physical package to optimize shipping costs.
- **Operational risks/opportunities:** Major cost-saving opportunity for B2B shipments. However, it risks SLA violations if one order is delayed to wait for items from an external order.
- **Traditional flattening:** Results in phantom data. Extracting Order O5 into a flat table will either silently drop the `EXT_IA` item or inject an item into O5 that the customer never actually ordered, ruining downstream data integrity.
- **Stability under repair:** Highly fragile. ETL pipelines usually enforce strict containment (Order -> Items) and frequently prune external identifiers, converting X5 into a false Standard-Isolated execution.

### Shared-Finance (X6)
- **Concise signature:** `EXT_Order` present in financial events.
- **Business behavior:** Consolidated billing. Items are shipped separately, but the accounting department issues a single master invoice covering multiple orders for the same customer.
- **Operational risks/opportunities:** Improves client relationships by reducing invoice fatigue. However, if a dispute arises on one order, the customer may withhold payment for the entire master invoice, impacting cash flow.
- **Traditional flattening:** Extremely problematic. The total value of Invoice V61 will be duplicated across all participating orders, artificially inflating revenue reporting unless complex allocation logic is applied.
- **Stability under repair:** Stable, but frequently flagged as an "error" by naive data quality monitors that assume 1 Order = 1 Invoice, leading to manual interventions that sever the shared invoice edge.

### Replaced-Item (X7)
- **Concise signature:** Presence of O2O qualifier `removed_before_dispatch`.
- **Business behavior:** An item was picked and packed, but before the package left the facility, an exception occurred (e.g., quality failure, customer last-minute swap) requiring the item to be removed and replaced.
- **Operational risks/opportunities:** Represents hidden rework. The warehouse spent labor packing an item that did not generate revenue. If not tracked, inventory counts will drift because the initial item was never physically dispatched.
- **Traditional flattening:** Invisible. Tabular structures typically overwrite the item ID with the "final" state or ignore O2O qualifiers entirely, erasing the substitution history.
- **Stability under repair:** Very fragile. O2O qualifiers are advanced OCEL features that are frequently dropped when logs are converted into standard event streams or legacy formats.

### Return-Rework (X8)
- **Concise signature:** Cyclic repetition of logistics milestones (`Return`, `Inspect`, `Pack`, `Dispatch`).
- **Business behavior:** A physical delivery failed or was rejected. The goods were returned to the facility, inspected by quality assurance, repacked, and shipped a second time.
- **Operational risks/opportunities:** A massive margin killer. Requires urgent root-cause analysis into why the initial delivery failed to prevent systemic logistics hemorrhaging.
- **Traditional flattening:** Creates cyclic data paths. Analysts must resort to renaming columns (`Dispatch_1`, `Dispatch_2`), which breaks strict database schemas and complicates temporal querying.
- **Stability under repair:** Stable. Because the anomaly is encoded directly in new activity labels (`Return Item`, `Inspect Return`), it survives almost all standard data transformations.

## 5. Borderline cases

- **X1 versus X2:**
  - *Disagreement:* Exact structural equivalence (matching exact string identifiers) splits these into two clusters because `I11` != `I22`. Conversely, Typed-structural equivalence (TSE) and Business-semantic equivalence (BSE) group them because the ID swap is a meaningless artifact of UUID generation.
  - *Defense:* Grouping them is logically superior unless the local identifiers encode latent meaning (e.g., `I11` means Warehouse 1, `I22` means Warehouse 2), in which case exact ID equivalence is defensible.

- **X1 versus X5:**
  - *Disagreement:* Activity-sequence equivalence (ASE) groups these together because both exhibit the exact same `C, A, A, P, D, I, R` sequence. BSE strictly separates them due to the external objects in X5.
  - *Defense:* If the analyst's sole goal is tracking milestone completion rates (Did the order ship?), ASE is sufficient. If the goal is cost-accounting and logistics optimization, BSE is required to expose the batching.

- **X1 versus X6:**
  - *Disagreement:* Similar to above, ASE groups them, while BSE splits them based on external financial objects.
  - *Defense:* A warehouse logistics manager views X1 and X6 as identical because the physical handling is the same. An accounts-receivable clerk views them as fundamentally different because X6 involves complex liability and cross-account settlement.

- **X1 versus X7:**
  - *Disagreement:* ASE and standard TSE group them because the activity labels and general multiplicities match the happy path. BSE splits them by reading the `removed_before_dispatch` O2O qualifier.
  - *Defense:* Process mining based purely on event labels will blindly group these, underreporting rework. Object-centric mining equipped with O2O property awareness correctly isolates the anomaly.

- **X3 versus X4:**
  - *Disagreement:* Both ASE and BSE separate these due to differing activity lengths. However, a coarse "Multi-package order" business heuristic might group them.
  - *Defense:* Grouping them is defensible if a packaging supplier is only measuring how many boxes they need to procure. Separating them is critical for the logistics provider who has to route two separate trucks in X4.

- **X4 versus X8:**
  - *Disagreement:* A naive structural clustering might group them under "High Touch / Repetitive Volume" because both feature multiple `Pack` and `Dispatch` events. 
  - *Defense:* BSE heavily splits them because the *reason* for repetition matters. X4 is a planned operational split (parallel execution), whereas X8 contains explicit `Return` and `Inspect` events, denoting an unplanned failure (rework loop).

## 6. Relation to `pm4py.cluster_equivalent_ocel`

- **Information preserved by PM4Py's key structure:** The built-in `pm4py.cluster_equivalent_ocel` function generally groups executions by hashing their exact graph structure. It preserves activity labels, exact object types, exact object identifiers, and the strict mathematical incidence (E2O edges) between them.
- **Why raw object identifiers make exact clusters too fine:** If an algorithm uses raw identifiers (e.g., `ord-992`, `item-441`) in its hashing mechanism without checking for graph isomorphism, every single order will hash to a completely unique signature. This results in $N$ clusters for $N$ orders, defeating the purpose of clustering.
- **Canonicalization/post-processing:** To utilize `pm4py`, the OCEL must be pre-processed. Raw identifiers must be overwritten with canonical aliases (e.g., `Order_1`, `Item_1`, `Item_2`) determined by a deterministic traversal of the execution graph (like breadth-first search starting from the lead object). 
- **When exact equivalence is preferable:** Exact graph equivalence is highly useful during IT system migrations, ETL debugging, or fraud detection, where the analyst is looking for literal data duplication, malformed data loads, or specific rogue identifiers.
- **Effects of `max_objs` and large components:** Object-centric logs often form massive, intertwined connected components due to shared logistics (X5) or finance (X6). Using heuristic parameters like `max_objs` forcefully truncates these graphs to prevent memory exhaustion. However, this practically severs the `EXT` edges, degrading X5 and X6 into standard X1 executions and blinding the analysis to cross-order behavior.

### Python implementation outline

```python
import pm4py
import pandas as pd
from pm4py.objects.ocel.obj import OCEL

def cluster_order_executions(ocel: OCEL):
    # 1. Isolate executions centered on the lead object
    # (Assuming a helper that filters the OCEL to subgraphs per Order)
    order_subgraphs = extract_lead_object_subgraphs(ocel, lead_type="Order")
    
    canonical_data = []
    
    # 2. Custom Canonicalization step
    for subgraph_ocel in order_subgraphs:
        alias_map = {}
        type_counts = {}
        
        # Iterate over E2O dataframe to rename objects based on appearance order
        for idx, row in subgraph_ocel.relations.iterrows():
            raw_id = row['ocel:oid']
            obj_type = row['ocel:type']
            
            # Preserve external markers if present in ID
            if "EXT" in raw_id:
                canonical_id = f"EXT_{obj_type}"
            else:
                if raw_id not in alias_map:
                    type_counts[obj_type] = type_counts.get(obj_type, 0) + 1
                    alias_map[raw_id] = f"{obj_type}_{type_counts[obj_type]}"
                canonical_id = alias_map[raw_id]
                
            # Update the dataframe with the canonical alias
            subgraph_ocel.relations.at[idx, 'ocel:oid'] = canonical_id
            
        canonical_data.append(subgraph_ocel)
        
    # 3. Combine canonicalized subgraphs back into a single OCEL
    # This prepares the data for PM4Py's structural clustering
    merged_canonical_ocel = merge_ocels(canonical_data)
    
    # 4. Use PM4Py to cluster the now-canonicalized exact graphs
    # Because IDs are aliased, structurally identical graphs will hash together
    clusters = pm4py.cluster_equivalent_ocel(merged_canonical_ocel)
    
    return clusters
```

## 7. Robustness analysis

The cluster assignments are highly sensitive to how data is modeled and pre-processed. Here is how assignments mutate under various structural perturbations:

1. **Ignore all O2O qualifiers:** If semantic links like `removed_before_dispatch` are discarded, execution **X7 merges entirely into X1**. The execution simply looks like an order where two items were packed, but only one was shipped, mimicking a benign partial shipment rather than explicitly signaling a late-stage physical replacement.
2. **Ignore external objects:** Dropping external object tracking forces **X5 and X6 to merge into X1**. For X5, the logistics steps appear perfectly normal, hiding the cost-saving cross-order batching. For X6, the invoice appears isolated, completely masking the B2B master-billing complexity.
3. **Collapse repeated same-label events:** If multiple occurrences of the same activity are deduplicated (e.g., `Pack`, `Pack` becomes a single `Pack`), **X3 degrades into X1**. More drastically, **X4 collapses into a sequence heavily resembling X1** (`C, A, P, D, I, R`), destroying all visibility into the split shipments and partial payments that define its operational cost.
4. **Treat Pack and Dispatch event order as a partial order:** If we relax the strict sequence requirement and treat logistics events as a partially ordered set (poset), minor warehouse timing variations are absorbed. For example, a sequence of `Pack, Dispatch, Pack, Dispatch` (X4) becomes equivalent to `Pack, Pack, Dispatch, Dispatch` if causal links between specific packages are omitted. This aggregates minor warehouse worker variations into a single cohesive "Split-Execution" cluster.
5. **Treat payment multiplicity as an amount attribute:** If the object-centric financial events (`M41`, `M42` in X4) are modeled simply as a fluctuating `amount_paid` attribute on the Invoice object, the structural distinctiveness of the payments disappears. **X4's signature simplifies**, effectively merging its financial behavior with X3, hiding the manual effort required by the accounting team to reconcile partial payments.

## 8. Limitations and recommendation

Because object-centric executions contain multiple dimensions of complexity (chronological, structural, relational, and cross-boundary), no single equivalence relation can satisfy all analytical needs. The choice of equivalence must be strictly tailored to the stakeholder's objective.

- **Compliance monitoring:** We recommend **Business-semantic equivalence (BSE)** or exact structural equivalence. Compliance and auditing require hyper-precise partitions. An auditor needs to know if a payment was cross-applied (X6) or if an item was swapped without proper documentation (X7). Coarser clusters dangerously mask these violations as "standard" behavior.
- **Operational segmentation:** We recommend **Activity-sequence equivalence (ASE)** or partial-order ASE. Warehouse and shift managers primarily care about macro-flows and throughput. Whether an invoice is shared (X6) or isolated (X1) has zero impact on the forklift driver. ASE provides a clean, noise-free view of physical operations.
- **Root-cause analysis:** We recommend **Typed structural equivalence (TSE)**. When diagnosing why specific orders suffer from SLA breaches, analysts need to know the volumetric complexity (e.g., "This order had 5 items and 3 packages"). TSE preserves this structural multiplicity without burdening the analyst with raw UUIDs or financial edge cases.
- **Descriptive reporting:** We recommend **Hierarchical Business-semantic equivalence**. Executive dashboards require roll-ups. Executions should be grouped into primary buckets (Standard, Split, Rework) using coarse rules, but allow drill-down into BSE to explain cost variances caused by external batching or hidden replacements.

**Conclusion:** Forcing a single equivalence notion across an organization ensures failure. Using ASE for accounting obscures master-billing liabilities, while using BSE for warehouse operations creates unmanageable dashboard fragmentation. Object-centric process mining is uniquely powerful precisely because it allows analysts to dynamically shift the equivalence lens based on the specific dimension (logistics vs. finance) they are optimizing.
