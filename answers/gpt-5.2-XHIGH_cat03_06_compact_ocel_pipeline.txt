## 1. Modeling assumptions

- **Object types (capitalization)**: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.

- **E2O qualifier vocabulary (consistent roles)**:
  - **Order lifecycle**: `created`, `closed`
  - **Order–Item composition (event-level)**: `receives_item` (Order role), `added` (Item role)
  - **Shared stock operation**: `reservation_scope` (Order role), `reserved` (Item role)
  - **Packing operation**: `packed` (Package role), `packed_item` (Item role), `fulfilled_for` (Order role)
  - **Dispatch & confirmation**: `dispatch` / `confirmed` (Delivery role), `dispatched` / `delivered` (Package role)
  - **Invoicing**: `issued` (Invoice role), `billed_order` (Order role)
  - **Payments**: `recorded` (Payment role), `settlement_target` (Invoice role)

- **O2O direction conventions (`ocel:oid` → `ocel:oid_2`)**:
  - **Container/actor → contained/target**: `Order` → `Item` (`contains`), `Package` → `Item` (`packs`), `Delivery` → `Package` (`carries`).
  - **Financial**: `Invoice` → `Order` (`bills`), `Payment` → `Invoice` (`partially_settles` / `completes_settlement`).

- **Direct links for logistics & finance (source-faithful, compact)**:
  - **Logistics events** (`Dispatch Package`, `Confirm Delivery`) relate directly to `Delivery` and `Package` only (not directly to `Order`/`Item`).
  - **Finance events**: `Issue Invoice` relates to `Invoice` and both `Order`s; each `Record Payment` relates to `Payment` and `Invoice` only (not directly to `Order`s).
  - **Operational shared events explicitly stated as cross-order** (`Reserve Stock` for I1+I3; `Pack Package P1` with I1+I3) are linked to both `Order`s and the affected `Item`s because the narrative states joint operational sharing.

- **Preventing confusion between source facts and propagated analytics**:
  - The `relations` table below is treated as **source/system facts**.
  - If an analyst wants order-level traces that “include delivery/payment milestones”, they should compute a **separate derived relations table** (e.g., `relations_derived`) with qualifiers prefixed `derived:` (or an extra column like `rel_origin = source|derived`) and build a separate OCEL view explicitly. This avoids silently turning propagated inferences into “observations”.

- **PM4Py version-dependent assumption**:
  - The code assumes an `OCEL(events=..., objects=..., relations=..., o2o=...)` constructor is available. If your PM4Py exposes `OCEL` under a different import path (or expects a different signature), only adapt the import/constructor line; keep the DataFrame semantics identical.

## 3. Data-model audit

### Object inventory

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

### O2O qualifiers and cardinalities

| O2O qualifier | Count | Examples |
|---|---:|---|
| contains | 3 | O100→I1, O100→I2, O200→I3 |
| packs | 3 | P1→I1, P1→I3, P2→I2 |
| carries | 2 | D1→P1, D2→P2 |
| bills | 2 | V1→O100, V1→O200 |
| partially_settles | 1 | M1→V1 |
| completes_settlement | 1 | M2→V1 |

### Activities and the object types they touch (via E2O)

| Activity | Touched object types |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Order, Item, Package |
| Dispatch Package | Delivery, Package |
| Confirm Delivery | Delivery, Package |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Close Order | Order |

### Relation-set “pivot” events

- **E07 — Pack Package (P1)**: it binds **P1** to **I1+I3** and to **both O100 and O200**, making it the main convergence point between the two orders at the operational/logistics layer.
- **E06 — Reserve Stock** and **E11 — Issue Invoice (V1)** are also consequential: E06 operationally couples O100/O200 early; E11 couples them again in the financial layer via **V1**.

## 4. Expected flattened behavior

### Order flattening

- **Approximate trace shapes**:
  - **O100**: Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Pack Package → Issue Invoice → Close Order
  - **O200**: Create Order → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order
- **Copied shared events (duplicated across cases)**:
  - **Reserve Stock (E06)** appears in both O100 and O200 traces (one joint event copied into two cases).
  - **Pack Package P1 (E07)** appears in both order traces.
  - **Issue Invoice V1 (E11)** appears in both order traces.
- **Omitted lifecycle aspects (by the compact/source-faithful policy)**:
  - No `Dispatch Package` / `Confirm Delivery` milestones in order traces (those are tracked at `Delivery`/`Package` level).
  - No `Record Payment` events in order traces (payments are linked to `Invoice`/`Payment` only).
- **Likely DFG edges** (high probability):
  - Create Order → Add Item
  - Add Item → Add Item (visible for O100 due to two line items)
  - Add Item → Reserve Stock
  - Reserve Stock → Pack Package
  - Pack Package → Pack Package (visible for O100 because it has P1 then P2 packing)
  - Pack Package → Issue Invoice
  - Issue Invoice → Close Order
- **Misleading interpretations**:
  - Frequency inflation: the single shared reservation (E06) may look like “two reservations” when counted per order-case.
  - The absence of delivery and payment steps can make it look like orders close right after invoicing, hiding “fulfilled” vs “closed” distinctions.
  - Cross-order coupling (via P1) may be misread as a normal order lifecycle step rather than a packaging consolidation decision.

### Package flattening

- **Approximate trace shapes**:
  - **P1**: Pack Package → Dispatch Package → Confirm Delivery
  - **P2**: Pack Package → Dispatch Package → Confirm Delivery
- **Copied shared events**: none expected at package level (each package has its own dispatch/confirm events).
- **Omitted lifecycle aspects**:
  - No explicit `Create Order` / `Add Item` history; upstream order composition is only visible via object-centric views (and O2O).
  - Finance (`Issue Invoice`, payments) is absent.
- **Likely DFG edges**:
  - Pack Package → Dispatch Package → Confirm Delivery
- **Misleading interpretations**:
  - P1’s special role (combining two orders) is not obvious from the flattened package trace alone; it shows a clean 3-step logistics lifecycle that hides cross-order consolidation.

### Delivery flattening

- **Approximate trace shapes**:
  - **D1**: Dispatch Package → Confirm Delivery
  - **D2**: Dispatch Package → Confirm Delivery
- **Copied shared events**: none expected.
- **Omitted lifecycle aspects**:
  - Packing steps are absent (pack events were linked to packages and orders/items, not to deliveries).
  - Upstream order context and finance are absent.
- **Likely DFG edges**:
  - Dispatch Package → Confirm Delivery
- **Misleading interpretations**:
  - If one assumes “delivery case = customer order”, D1 might be mistaken as serving a single order, while it actually carries P1 with items from **O100 and O200**.

### Invoice flattening

- **Approximate trace shape (single case V1)**:
  - Issue Invoice → Record Payment → Record Payment
- **Copied shared events**:
  - Payment events are “shared” across multiple perspectives (Invoice and Payment), but within invoice flattening they are simply sequential events on V1.
- **Omitted lifecycle aspects**:
  - Fulfillment steps are absent; invoice lifecycle is financial, not logistics.
  - Order closure events are absent (closure is an order lifecycle decision).
- **Likely DFG edges**:
  - Issue Invoice → Record Payment
  - Record Payment → Record Payment (because V1 has two partial payments)
- **Misleading interpretations**:
  - Without explicit allocation rules, one might incorrectly interpret each payment as “for O100” or “for O200”; the log only supports “against V1”.

### Why flattening on Payment is particularly weak

- Each `Payment` object (M1, M2) has essentially **one event** (`Record Payment`), yielding **single-event traces** that provide little to no structure for DFG/skeleton discovery.
- The business meaning (partial settlement of a shared invoice V1 billing both orders) lives in **object relations (Payment→Invoice, Invoice→Orders)**; a payment-centric flattening discards that multi-object context unless you propagate relations.

## 5. Expected object-centric structures

- **OC-DFG (`discover_ocdfg`)**:
  - Should reveal two intertwined “subsystems”:
    - **Order/Item/Package operational path**: Create Order → Add Item → Reserve Stock → Pack Package (for Items and Orders; Pack also progresses Packages).
    - **Logistics path**: Pack Package → Dispatch Package → Confirm Delivery (for Packages/Deliveries).
    - **Finance path**: Issue Invoice → Record Payment → Record Payment (for Invoice/Payments).
  - The OC-DFG will highlight cross-order coupling through **P1**: the packing event for **P1** connects **O100** and **O200** (shared E07) and also relates to both items **I1** and **I3**.

- **OTG (`discover_otg`)**:
  - Expected dominant type-level connections:
    - `Order`—`Item` (via both O2O `contains` and shared events like Add Item / Reserve Stock)
    - `Package`—`Item` (O2O `packs`)
    - `Delivery`—`Package` (O2O `carries` and events Dispatch/Confirm)
    - `Invoice`—`Order` (O2O `bills` and Issue Invoice event)
    - `Payment`—`Invoice` (O2O settlement qualifiers and Record Payment events)
  - P1’s consolidation effect is not “an extra node” but manifests as stronger multi-type interactions around `Package` with `Order` and `Item`.

- **ET–OT graph (`discover_etot`)**:
  - Will show that:
    - `Pack Package` touches three types (`Order`, `Item`, `Package`),
    - `Reserve Stock` couples (`Order`, `Item`),
    - `Issue Invoice` couples (`Invoice`, `Order`),
    - `Record Payment` couples (`Payment`, `Invoice`),
    - `Dispatch Package` and `Confirm Delivery` couple (`Delivery`, `Package`).
  - This immediately explains why different flattenings emphasize different parts of the process.

- **Object-centric Petri net (`discover_oc_petri_net`)**:
  - Expect transitions corresponding to the main activities with multi-type synchronization where events touch multiple object types.
  - Particularly, `Pack Package` and `Issue Invoice` are likely to appear as “synchronizing” transitions because they involve multiple object types; **P1** being tied to both **O100** and **O200** can cause the discovered net to encode coupling patterns (not a unique interpretation, but a learned structure reflecting shared events).
  - `Record Payment` transitions should be tied to `Invoice` and `Payment` types, showing how **M1** and **M2** progress settlement of **V1** without directly progressing order states.

- **Object-interactions summary (`ocel_objects_interactions_summary`)**:
  - Should rank interactions that reflect the narrative’s “bridges”:
    - **P1** interacts with **O100** and **O200** (via the shared packing event) and with **D1** (via dispatch/confirm plus `carries`).
    - **V1** interacts with **O100** and **O200** (bills both) and with **M1** and **M2** (payments settling the invoice).
  - It may also show same-type interactions (Order–Order) because **O100 and O200 co-occur in E06 and E07 and E11**, indicating genuine operational coupling (shared stock reservation and consolidated packing, plus shared invoice).

## 6. Modeling alternatives

- **Alternative A — Source-minimal E2O (even more compact than above)**:
  - Policy: Link each event only to the object that “owns” the event in the source system (e.g., `Pack Package` only to `Package`; `Reserve Stock` only to `Item`s; `Issue Invoice` only to `Invoice`; payments only to `Payment`).
  - Effect on discovery: Flattened `Order` traces become very short (mostly Create/Close only unless you keep Add Item), and object-centric discovery shifts most structure to `Package`/`Invoice` lifecycles. Cross-order coupling via P1 becomes visible mainly through O2O (packs/contains) rather than shared events.

- **Alternative B — Full operational involvement (maximal direct E2O)**:
  - Policy: For each downstream event (dispatch/confirm/payments), also directly link all impacted `Order`s and `Item`s (e.g., dispatch D1 also links to O100/O200 and I1/I3).
  - Effect on discovery: `Order` flattening becomes “end-to-end” (includes dispatch/confirm/payment), but produces **relation inflation**, heavy duplication of shared events, and can falsely suggest that every order explicitly participated in every logistics/finance event rather than being related via packages/invoices.

- **Alternative C — O2O-propagated analytical relations (two-layer approach)**:
  - Policy: Keep `relations` source-faithful; compute `relations_derived` by propagating along O2O (e.g., Delivery→Package→Item and Order→Item) to attach dispatch/confirm events to orders/items for analysis only.
  - Effect on discovery: Lets you obtain “order end-to-end traces” while keeping provenance: object-centric models on the source layer remain clean; the derived layer supports richer flattenings but can be switched off to avoid counting derived edges as observations.

- **Alternative D — Finance-to-order hybrid (allocation-free enrichment)**:
  - Policy: Link `Record Payment` events directly to both orders billed by V1 (without allocating amounts), using a qualifier like `invoice_related_payment`.
  - Effect on discovery: `Order` flattening includes payment milestones (improving lead-time analyses from order to payment) but risks misinterpretation (“O100 got paid 100”) unless the qualifier clearly signals “related via shared invoice, not allocated”.

## 7. Failure modes

- **Relation inflation**: connecting dispatch/confirm/payment events to every related order/item without provenance, making every case look identical and distorting frequencies.
- **Missing direct E2O links**: e.g., forgetting to relate `Record Payment` events to `V1` causes invoice flattening to miss payments entirely.
- **Treating O2O propagation as observation**: mixing derived links into `relations` without tagging leads analysts to believe the source system recorded those relationships.
- **Duplicate shared events after flattening**: joint events like E06/E07/E11 appear in multiple cases; naive counts can double-count “operations performed”.
- **Ambiguous payment allocation**: V1 bills both O100 and O200; payments M1/M2 settle V1 but are not attributable per order without an explicit allocation rule.
- **Overly short Payment traces**: payment-centric flattening yields one-event traces, making discovered DFG/skeleton trivial and often misleading (“nothing happens”).
- **Constructor/API version mismatch**: OCEL constructor signature/import path or function names (e.g., OCEL discovery/visualization utilities) vary across PM4Py releases.
- **False total order for same-time events**: even though there are no timestamp ties here, real datasets often have ties; sorting without tie-break rationale can introduce artificial precedence in DFG/skeleton.
- **Activity/timestamp inconsistency between `events` and `relations`**: if relations are manually typed, it’s easy to drift from the events table; object-centric discovery can silently use inconsistent timestamps.
- **Type drift / wrong `ocel:type` in relations**: mis-typing `P1` as `Item` breaks OTG/ET–OT and can make object-centric models nonsensical.
