## 2. Process-model consistency checks
A validation suite must run on every feature and explanation:

- Prefix-time availability: for each feature, assert that its computation timestamp  t0 using stored event timestamps; reject any feature whose value changes after t0.
- Activity-order feasibility: use a declarative model (Declare or DFG with negative constraints) to verify that any pattern or variant used in an explanation is enabled by the prefix at t0; flag “Claim Closed before Damage Assessment” as impossible.
- Same-timestamp ambiguity: when two events share a timestamp, require a reliable sequence index; if absent, treat the pair as unordered and disallow any ordering-dependent pattern.
- Complete-trace detection: compute each feature twice—once on the full trace and once on the prefix up to t0—and reject features whose values differ.
- Enabled vs. future-possible: for any activity referenced in an explanation, check whether it is reachable from the observed prefix without future events; flag any explanation that presupposes an Appeal or second Settlement Decision.
- Repeated Settlement Decision legitimacy: allow a second Settlement Decision Recorded only when an Appeal event is present in the trace; otherwise treat it as a data-quality error.

Alignment checks verify trace fitness against the normative model; footprint and DFG checks detect frequent but non-normative edges; prefix and declarative checks enforce temporal and ordering constraints. None of these checks alone proves causality.

## 3. Alternative feature interpretations
- Defensible predictive signal: queue_length_at_t0, elapsed_since_registration_at_t0, initial_damage_complexity, Documents Requested  Documents Received (prefix-restricted), Coverage Check Completed  Fraud Investigation Opened. These may be claimed only as “statistically associated with breach risk given the observed prefix”; no operational delay-reduction claim is warranted.
- Process-state or congestion signal: queue_length_at_t0 and elapsed_since_registration_at_t0. May be described as “current workload or age at prediction time correlates with outcome”; actionability requires separate causal study.
- Proxy requiring fairness/robustness review: claimant_region, calendar_week. Predictive use is permissible after disparate-impact testing; causal language (“region drives delay”) is disallowed.
- Drift/calendar proxy: calendar_week. May be retained for short-term prediction but must be monitored for policy/holiday shifts; never presented as a stable operational lever.
- Unusable until lineage is repaired: total_case_duration_hours, appeal_seen_anywhere, final_handler_team, num_document_requests_total, full_trace_variant_id, same_day_document_count_snapshot, prior_claim_count_before_t0 (current SQL), risk_score_current, last_resource_role, final_decision, and all impossible sequence patterns.

## 5. Recommendations for explanation validation
1. Implement a feature store that stores every feature with its computation timestamp and recomputes all top-12 features on the prefix only.
2. Add historical event timestamps and sequence indices to every table; enforce prefix-only materialization before model training.
3. Run automated conformance checks (Declare rules + DFG negative constraints) on every explanation before deployment.
4. After removing leaked features, retrain and recalibrate; verify that explanation stability (rank correlation) remains above a pre-defined threshold.
5. Conduct proxy/fairness analysis on claimant_region and calendar_week with disparate-impact metrics; document acceptable use.
6. Establish drift monitoring on queue_length distribution, calendar_week effects, and process variant frequencies; trigger re-audit on detected shifts.
