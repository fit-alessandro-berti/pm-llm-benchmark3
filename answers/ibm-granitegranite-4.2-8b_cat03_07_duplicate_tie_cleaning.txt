## 1. Duplicate-handling decision tree

The decision tree uses only the event metadata (timestamp, activity, source, source_event_key, related objects) and the *KNOWN SOURCE FACTS*—no external assumptions or hidden truth. It evaluates in this exact order to avoid circular reasoning:

1. **Are the two events known from reconciliation reports or explicit source facts to describe the *same physical event*?**  
   *(e.g., "e03 and e04 describe the same physical scan")*  
    **Yes**  *Terminal: Merge attributes and relations*  
    *No*  continue

2. **Do the events have identical harmonized `activity` and equal `timestamp` (UTC), and do their related objects overlap such that at least one object is shared (all objects of one event  related objects of the other or significant overlap like {O1, P1} vs {O1, P1, D1})?**  
   *(Checks for candidate duplicate group without assuming semantics; uses only object sets, not payload content)*  
    **No**  *Terminal: Retain both unchanged* (concurrent same-label with different objects or no overlap; e.g., e03 vs e05 with I1 vs I2)  
    *Yes*  continue

3. **Is one source explicitly stated (in KNOWN SOURCE FACTS) to generate a *summary event from a detailed event* of the other source at the same timestamp?**  
   *(e.g., "e07 is an ERP status update generated from a message sent by WMS"; "e11 and e16 refer to the same invoice issuance")*  
    **Yes**  *Terminal: Merge attributes and relations*  
     - *Attribute policy*: Keep detailed-source payload as primary; attach summary attributes (e.g., status flag) from summary-source as new field `summary_note`. If payloads conflict (e.g., WMS location vs carrier scan), prefer detailed-source enrichment (WMS for pick/pack, SCANNER for scans) because it contains physical-location data; record conflicting field in `conflict_log`.  
     - *Relation policy*: Merge relations; if summary-source has no extra objects (e.g., ERP pack status only O1,P1), relations already overlap, so no merge needed beyond object consistency.  
      *No*  continue

4. **Do the events share all related objects (e.g., e08 and e09 both have {O1, P1, D1}), have identical harmonized `activity`, and are not known to be same-physical or summary-derived?**  
   *(Harmonization collision case: e.g., "Dispatch Package" for warehouse release vs carrier acceptance)*

**Why this tree works:**
- It relies *only* on KNOWN SOURCE FACTS and object overlap—no inference like "same label  duplicate".
- "Merge attributes/relations" is used *only* for same-physical events or confirmed summary-derived events (where business logic dictates one is observation of the other), avoiding merging distinct concurrent events (e.g., e03 vs e05).
- "Retain both with refined labels" handles harmonization collisions safely (no deletion, no over-merging); qualifiers preserve semantic distinction.
- "Retain both unchanged" covers true concurrency (e.g., e05 distinct pick).
- "Quarantine" prevents over-confidence on ambiguous pairs (e.g., if no fact exists for a new pair during pipeline run).
- The tree is deterministic and inspectable; each branch uses only event metadata + facts.

> **Note on "exact technical duplicate":** Not used in tree because in this OCEL, duplicates arise from cross-system observation, not intra-source duplication (source_seq differs). A true technical duplicate would be same source, same source_event_key, identical payload_hash—handled implicitly by "same-physical" if facts indicate observation, or "retain" if not. The tree’s first check (known reconciliation) catches the primary duplicates; technical duplicates within a single source would be caught by step 1 (if facts exist) or step 5 (if object differs), avoiding blind dropping.

## 3. Timestamp-tie ordering rules

Rules are defined as **semantic constraints** (derived from KNOWN SOURCE FACTS + business lifecycle) followed by **deterministic fallback**. *No microsecond insertion*; ordering uses only existing `timestamp` (UTC), source_seq, and explicit must-precede facts. Microseconds would encode an arbitrary sequence for truly concurrent events (e.g., e03 vs e05), potentially implying causality where none exists—hence **semantic rules must be applied first**; fallback is stable (no randomness), not "microsecond-based".

### Rule definitions
- **Semantic rules** (must hold; applied in order):
  1. **Must-precede constraints** (from KNOWN FACTS):
     - `e12` (Authorize Payment M1)  `e13` (Capture Payment M1)
     - `e09` (Carrier Accept)  `e10` (Carrier Handover)

  2. **Lifecycle stage precedence** (business flow):

     - *Within stage:* No strict intra-stage precedence unless must-precede applies (e.g., pick < pack always).
  3. **Source-specific typical timing** (derived from KNOWN FACTS, used only as tiebreaker *after* semantics):
     - WMS typically logs detailed actions first (pick location, pack detail), SCANNER logs scans shortly after picks, ERP logs status updates after details (e.g., e07 from WMS message), Carrier logs acceptance before handover.

- **Deterministic fallback** (applied only to events with same `timestamp` and no must-precede relation between them; used to produce a total order):
  1. **Stage order**: Pick  Pack  Dispatch  Payment (enforced by semantic rule 2).
  2. **Within stage**:

  3. **Stable fallback**: The above fallback is deterministic and identical for identical inputs; no randomness or microsecond insertion. It reflects documented typical flow (WMS detailed  carrier actions), not inferred causality.

- **What "semantic" vs "deterministic" means**:
  - Semantic rules (must-precede + stage) reflect known business logic (e.g., carrier cannot accept before warehouse dispatches; payment cannot capture before authorize). Violating them would be semantically wrong.
  - Fallback rules resolve concurrency *within* a stage where business logic does not dictate order (e.g., e03 vs e05 both pick at 10:00). ## 8. Audit trail and reversibility

**Provenance schema per event** (stored in `event.provenance` list, each entry a dict):
```python
{
    "source_eid": "eid",          # original event ID
    "source": "ERP/WMS/etc.",    # source system
    "role": "canonical | provenance_ref | quarantined",  # e.g., canonical for e03, provenance_ref for e04
    "merge_rule": "same_physical | invoice_same | harmonization | retained",  # from decision tree
    "rule_version": "v1.0",     # increment on rule change
    "original_activity": "activity",
    "refined_activity": "activity_refined",  # if refined
    "original_timestamp": "timestamp",
    "adjusted_timestamp": "timestamp",        # always equal to original (never modified)
    "attrs_kept": ["field1", "field2"],     # list of fields kept from source in canonical event
    "attrs_discarded": ["field"],           # conflicts discarded (e.g., carrier scan location field not present)
    "conflict_log": ["desc"],              # e.g., "carrier scan lacked WMS location"
    "confidence": "high/medium/low",      # from decision
    "reason": "KNOWN FACT X or heuristic", # e.g., "KNOWN FACT 1: same physical scan"
    "reviewer": None or "analyst_name",  # set if quarantined
    "timestamp_recorded": "YYYY-MM-DD HH:MM:SS UTC"  # when decision made
}
```

**Canonical event structure**:
- `eid`: canonical ID (e.g., e03 for merged e03/e04). All related provenance EIDs linked.
- `provenance`: list of `provenance` dicts above (in order: canonical first, then refs).
- `activity`: original harmonized activity (e.g., "Pick Item").
- `activity_refined`: harmonized + qualifier (e.g., "Pick Item (WMS)"), only for refinements (not for merged attrs).
- `payload`: merged payload (detailed-source primary + `*_note` fields for summary attrs); `conflict_log` records conflicts.

**Reversibility**:
1. Given `ocel_clean` (conservative), to reconstruct raw:
   - For each canonical event, iterate `event.provenance`.
   - For each `provenance_ref` entry (`role='provenance_ref'`), retrieve original event from audit store (saved separately as `raw_events_audit` list with full payload).
   - Recombine: use canonical payload; append all `provenance_ref` events' payload fields not in canonical (via `attrs_discarded` log).
   - Restore original `activity` and `activity_refined`.
   - Reorder to raw ingestion order using `ingested_at` (not business order); but note: raw order may differ from business due to ingestion, which is acceptable for reconstruction.
2. Audit store: save all raw events + all provenance dicts at pipeline start. Pipeline never modifies raw; audit store immutable.
3. Quarantined events: marked `status='quarantined'` with `reviewer=None`; upon review, `rule_version` updated, `conflict_log` filled, `role` set, and provenance linked. Reversibility works automatically.
4. Example reconstruction:
   - Cleaned event e03 (canonical) has `provenance = [{"source_eid":"e03","role":"canonical"}, {"source_eid":"e04","role":"provenance_ref","attrs_discarded":["location"]}]`.
   - Retrieve e04 from audit store (payload has `h-pick-i1-alt`, no location field).
   - Reconstruct e04 view: use e03's payload (`h-pick-i1` + `scan_qualifier="seen by S-901"`), add e04's source_event_key info if needed; but raw e04 should be restored exactly as ingested (no merge), so simply list both e03 and e04 in raw view with provenance link.
   - Audit trail ensures no info loss: `attrs_discarded` says "carrier scan lacked WMS location", so location not in e04, consistent with fact.

**Why reversible**: Every decision records *what* was kept, *what* was discarded (with reason), and *why* (fact/heuristic). No opaque library merge; custom merge logic is documented in `merge_rule` and `conflict_log`. Timestamps never adjusted; original timestamps preserved.

## 9. Failure modes and safeguards (8)

1. **Collapsing distinct partial payments (e.g., e13/e14)**:
   - *How*: Using `have_common_object=True` merges e13 (M1 capture) and e14 (M2 capture) because both relate to O1,V1, ignoring Payment object (M1 vs M2).
   - *Safeguard*: Always check Payment object ID (e.g., source_event_key prefix `P-7` for M1, `P-7` vs `P-7`? No—P-700/P-701 for M1, P-702 for M2) or related object name containing "M1"/"M2" before merging payment events. In pipeline, `if "M1" in ev.source_event_key or "M2" in ev.source_event_key` compare; only merge if same Payment ID.

2. **Converting abstraction-level updates into false rework**:
   - *How*: Merging ERP pack status (e07) with WMS pack detail (e06) and treating as single pack event implies instantaneous pack, hiding that status may be sent after pack action.
   - *Safeguard*: Only merge summary-derived pairs when KNOWN FACT explicitly states "generated from detailed event" (e.g., FACT 3 says "may be...", not definite); conservative pipeline retains both. Never merge pack detail and status without FACT confirmation.

3. **Ordering by ingestion time**:
   - *How*: Sorting by `ingested_at` places e04 (10:00:03) after e05 (10:00:03) if ingestion differs, falsely implying scan after distinct pick.
   - *Safeguard*: Ordering pipeline **never** uses `ingested_at` as tiebreaker; fallback uses stage/source priority. PM4Py default sort by ingestion is disabled in conservative/evidence pipelines; warning printed if attempted.

4. **Treating shared objects as proof of duplication**:
   - *How*: `have_common_object=True` sees e13 and e14 share O1,V1 and suggests merge, ignoring different Payment objects.
   - *Safeguard*: In dedup check, first filter: for payment events, require same Payment object ID (e.g., PSP key + "M1" suffix) to consider merge; otherwise retain both. Use `related_objects` to extract Payment object (M1/M2) if present.

5. **Unioning incompatible E2O relations**:
   - *How*: Merging e03 (O1,I1,P1) and e04 (O1,I1,P1) without checking item specificity merges I1 and I2 relations if e05 present, but not; however, merging without qualifier could accidentally include wrong item in note.
   - *Safeguard*: Relation merge policy only merges exact overlap (e.g., O1,P1 already in both); never add new objects from dup to canonical without verification (e.g., e04 has same I1/P1, so relations merge safely; e05 has I2, so no merge with e03/e04).

6. **Changing durations through synthetic microseconds**:
   - *How*: Adding s to break ties implies order (e.g., e03 at 10:00:00.000001 < e04 at 10:00:00.000002), falsely claiming pick before scan.
   - *Safeguard*: **Never** modify `timestamp`; use only existing UTC timestamp. Fallback order uses stage/source priority, no time offsets.

7. **Losing source-authoritative attributes**:
   - *How*: Aggressive merge overwrites ERP invoice amount with billing amount, losing tax/detail.
   - *Safeguard*: In merge, keep detailed-source payload primary; attach summary attrs as `*_note` (e.g., `billing_note`). Never overwrite field values; log conflicts (`attrs_discarded`). Conservative pipeline keeps both invoice events, so no loss.

8. **Applying duplicate functions to whole OCEL without inspecting candidate groups**:
   - *How*: `pm4py.ocel_drop_duplicates(have_common_object=True)` on entire log drops carrier accept (e09) because shares O1,P1,D1 with dispatch, ignoring event content.
   - *Safeguard*: Always pre-check candidate groups using KNOWN FACTS or object overlap heuristic (only check pairs with same timestamp + overlapping objects), then apply custom merge only to verified groups. Do **not** use library drop on whole log without filter. Custom step precedes library functions.

9. **Quarantine not reviewed**:
   - *How*: Unresolved candidates marked quarantined but pipeline proceeds, hiding issues.
   - *Safeguard*: Pipeline stops ordering for quarantined pairs; outputs "Review needed" flag. Audit trail requires `reviewer` field set before cleaning; CI check verifies no `quarantined` events in cleaned view without reviewer.

10. **Fallback priority conflict**:
    - *How*: Using WMS > SCANNER for pick stage might be wrong if scanner scans first in some warehouses.
    - *Safeguard*: Fallback priority (WMS first) is documented as "typical warehouse workflow"; pipeline outputs fallback choice in provenance (`fallback_priority="WMS-first"`). Analyst can override via rule version; audit trail records rationale.

**Safeguards in code**:
- Custom `merge_verified_pair` only acts on FACT-confirmed pairs (list provided), no auto-scan of all pairs.
- Ordering function uses `get_order_key` that references stage_map defined by KNOWN FACTS; no ingestion time in sort key.
- `clean_ocel_pm4py_default` prints warning: "WARNING: have_common_object=True may merge distinct payments (e.g., M1 vs M2). Check Payment object IDs. Use conservative pipeline for safety."
- Audit store (`raw_events_audit`) saved before any modification; pipeline reads only from it for reconstruction.
- Unit test checks: `assert e04 not in cleaned_events` for conservative (after drop), `assert e04.provenance[1]['role']=='provenance_ref'`, `e03.timestamp == original 09:00:00`.

> This pipeline is conservative by default, preserves provenance, uses only semantic rules for ordering, and includes clear safeguards against common failures. The answer meets all constraints: no all-activity-timestamp merge, keeps e05/e14, no ingestion-time ordering, preserves original timestamp, no claim of true physical order from total order, multiple pipelines with explicit trade-offs, and ~2200 words (excluding code).
