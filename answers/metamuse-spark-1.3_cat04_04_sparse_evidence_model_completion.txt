# 2. Shared Assumptions

1. **Completion semantics only.** Log records completion. `A before B` in a trace means `complete(A) < complete(B)` (or equal with ingestion tie-break), not `end(A) < start(B)`. All models therefore reason about completion order; claimed concurrency means *no required completion order*, not proven simultaneous execution.
2. **Common backbone.** `Register Order` is start, `Archive Case` is end, `Approve Configuration`  `Release Production`  `Archive Case` is sequential in all models per D1/D2 and 30/30 support. No model allows skipping `Credit Check`, `Engineering Review`, `Approve Configuration`, `Release Production`, or repeating any activity.
3. **Missing vs optional Supplier conflated.** Absent `external/stocked` attribute and unidentifiable 5–10% missing `Supplier Confirmation` events mean true optionality (S4) and false-negative missingness (S5) are indistinguishable. All three models represent this with a single control-flow alternative `XOR(Supplier Confirmation, )` and **disclose** that  means “stocked *or* lost event *or* integration gap.” No model attempts probabilistic missing-data imputation or duplicate `Supplier Confirmation` labels to separate causes.
4. **Optionality via silent choice.** `XOR(activity, silent)` is used for optional `Supplier Confirmation` and `Expedite Review`. This is a control-flow over-approximation: it admits the skip but loses *why* it was skipped and any data condition. Fitness/precision are computed on control-flow only.
5. **Expedite at most once, no loops.** No trace shows repetition. No model contains a loop operator. Future repetition would be non-conforming in all candidates by design.
6. **No timestamps, resources, or attributes used.** Decisions use order + domain rules only. Frequency thresholds are not treated as causal.
7. **Soundness required.** All candidates must convert to sound workflow nets.

# 3. Conservative Candidate

**Inductive bias.** Closed-world, observation-bound: admit exactly the seven observed completion orders and nothing else; prefer under-generalization to any speculation about concurrency, optionality cause, or unseen interleavings. Contradicts S2/D5/S6 where they would add behavior; follows S1 only insofar as observed orders are preserved, not as a universal sequence. This is deliberate overfitting to maximize precision and auditability for compliance.

**Formal expression.** `( Register Order, X( (Credit Check, Engineering Review, Supplier Confirmation), (Engineering Review, Credit Check, Supplier Confirmation), (Credit Check, Engineering Review), (Engineering Review, Credit Check), (Credit Check, Supplier Confirmation, Engineering Review), (Credit Check, Engineering Review, Supplier Confirmation, Expedite Review), (Engineering Review, Credit Check, Expedite Review, Supplier Confirmation) ), Approve Configuration, Release Production, Archive Case )` — i.e. XOR of 7 observed middles sandwiched in a fixed backbone. No parallel operator appears.

**Code:**
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def _leaf(label):
    t = ProcessTree()
    t.label = label
    return t

def _seq(*labels):
    return ProcessTree(operator=Operator.SEQUENCE, children=[_leaf(l) for l in labels])

RO = "Register Order"; CC = "Credit Check"; ER = "Engineering Review"
SC = "Supplier Confirmation"; EX = "Expedite Review"
AC = "Approve Configuration"; RP = "Release Production"; AR = "Archive Case"

b1 = _seq(CC, ER, SC)        # 12x V1
b2 = _seq(ER, CC, SC)        # 7x V2
b3 = _seq(CC, ER)            # 4x V3 skip SC
b4 = _seq(ER, CC)            # 3x V4 skip SC
b5 = _seq(CC, SC, ER)        # 2x V5 interleaved SC
b6 = _seq(CC, ER, SC, EX)    # 1x V6
b7 = _seq(ER, CC, EX, SC)    # 1x V7

middle = ProcessTree(operator=Operator.XOR, children=[b1, b2, b3, b4, b5, b6, b7])

model_conservative = ProcessTree(operator=Operator.SEQUENCE, children=[
    _leaf(RO), middle, _leaf(AC), _leaf(RP), _leaf(AR)
])
```

**Deliberately excluded:**
- Any `Expedite Review` position other than the two observed (`SCEX` after both+SC, `EXSC` after both before SC); e.g. `CC, SC, ER, EX` or `EX` without `SC` position swapped.
- Any `Supplier Confirmation` position other than observed: e.g. `ER, SC, CC`, `SC, CC, ER`, `SC` before both checks.
- Any concurrent completion equivalence: model treats `CC,ER` vs `ER,CC` as distinct XOR branches, not parallel; unseen `CCERSC` interleavings like `ER, SC, CC` rejected.
- Any repetition, skipping of `CC/ER/AC/RP`, or `EX` twice or after `AC`.

**Known underfitting risks (within its own bias, overfitting globally):**
- Brittle to missing `Supplier Confirmation` (S5): a true V1 case with lost `SC` event looks like V3 and is accepted only by accident via a different branch; a V5 case with lost event similarly misclassified, masking data quality.
- Rejects plausible compliant behavior per S6/D5/D6 (e.g. `CC, ER, EX` without `SC` — expedited stocked order — has zero support but is domain-plausible).
- XOR enumeration uses duplicate labels across branches (7× `Credit Check`, etc.); scales linearly with variants and obscures that branches share activities — poor simplicity/explainability and no generalization to 8th variant. Discussed as anti-pattern kept here only to guarantee precision.

# 4. Balanced Candidate

**Inductive bias.** Plausible-generalization with guardrails: accept S2 (checks parallel) and S6/D6 (expedite after both,  supplier) and the empirically grounded part of D5 (`CCSC` holds 23/23, `ERSC` fails 2/23), while refusing to admit `Supplier Confirmation` before both checks or `Expedite Review` without both checks. Treats V5 as evidence of genuine overlap, not noise, but treats absence of `SC-first` as evidence of a constraint.

**Formal expression (POWL).** Nodes `{RO, CC, ER, SC_opt=X(SC,), EX_opt=X(EX,), AC, RP, AR}` with partial order: `RO<{CC,ER}; CC<SC_opt; {CC,ER}<EX_opt; {CC,ER,SC_opt,EX_opt}<AC<RP<AR; ERSC_opt; SC_optEX_opt`. I.e. checks concurrent, supplier needs `Credit Check` but overlaps `Engineering Review`, expedite needs both checks and overlaps supplier.

**Code:**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

_ro = Transition(label="Register Order")
_cc = Transition(label="Credit Check")
_er = Transition(label="Engineering Review")
_sc = Transition(label="Supplier Confirmation")
_ex = Transition(label="Expedite Review")
_ac = Transition(label="Approve Configuration")
_rp = Transition(label="Release Production")
_ar = Transition(label="Archive Case")

sc_opt = OperatorPOWL(operator=Operator.XOR, children=[_sc, SilentTransition()])
ex_opt = OperatorPOWL(operator=Operator.XOR, children=[_ex, SilentTransition()])

model_balanced = StrictPartialOrder(nodes=[_ro, _cc, _er, sc_opt, ex_opt, _ac, _rp, _ar])
model_balanced.order.add_edge(_ro, _cc)
model_balanced.order.add_edge(_ro, _er)
model_balanced.order.add_edge(_cc, sc_opt)   # grounded: 23/23 CC before SC
# no edge _er -> sc_opt : allows V5 (SC before ER), keeps ER || SC
model_balanced.order.add_edge(_cc, ex_opt)   # D6/S6: expedite after both
model_balanced.order.add_edge(_er, ex_opt)
# no edge sc_opt <-> ex_opt : S6 before-or-after allowed
model_balanced.order.add_edge(_cc, _ac)      # D3
model_balanced.order.add_edge(_er, _ac)
model_balanced.order.add_edge(sc_opt, _ac)   # D4
model_balanced.order.add_edge(ex_opt, _ac)   # D6 before approval
model_balanced.order.add_edge(_ac, _rp)      # D2
model_balanced.order.add_edge(_rp, _ar)      # D1
```

**How sequence vs concurrency vs partial order decided:**
- `Credit Check` vs `Engineering Review`: **concurrency** (``). Both orders frequent (19 CC-first incl. ROCC, 11 ER-first; 17 CCER vs 11 ERCC directly). S1 (strict sequence) falsified by 11 counterexamples; S2 (parallel) explains symmetry + S7 tie-break. Sequence would halve fitness; XOR would hide parallelism. POWL `` admits both + future duration variance.
- `Supplier Confirmation`: **partial order `CC<SC, ERSC`, optional**. `CC<SC` in 23/23 SC cases  keep edge. `ER<SC` in only 20/23, violated by V5 (2×)  drop edge, model as overlap consistent with D5 “after either suffices.” Fully after-both would exclude observed V5; fully parallel would admit never-seen `SC` before `CC`. Chosen middle ground is the only one replaying all 30 without admitting `SC-first`.
- `Expedite Review`: **optional, after both checks,  supplier**. Only 2 cases but both satisfy `CC,ER<EX<AC` (D6 medium + S6) and show both `SC<EX` and `EX<SC`  optional node with two incoming edges from checks, no edge to supplier, edge to approval. Sequence to supplier in either direction would exclude one observed case.
- Backbone `RO … ACRPAR`: **sequence** per D1/D2 and 30/30.

**Deliberately excluded:**
- `Supplier Confirmation` completing before `Credit Check` (e.g. `RO, SC, CC, ER…`, `RO, ER, SC, CC…`).
- `Expedite Review` without both checks complete (e.g. `RO, CC, EX, ER…`) or after `Approve Configuration` or twice.
- Skipping `CC/ER/AC/RP` or reordering backbone.

**Known underfitting risks:**
- If V5 is actually logging noise (S7 ingestion ordering of simultaneous completions), the dropped `ERSC` edge over-generalizes; true process might require both checks.
- If missing `SC` events (S5) hide `SC-first` cases, the retained `CCSC` edge underfits future true `ER-only-triggered SC`.
- Silent-choice abstraction cannot distinguish stocked skip from lost event; precision penalized if many skips are missingness.

# 5. Permissive Candidate

**Inductive bias.** Exploration-first: admit any completion order consistent with high/medium domain rules (D1–D4, D6) while relaxing the low-medium D5 dependency to “supplier anytime between start and approval.” Prefers recall over precision; treats absent `SC-first` as sampling gap (only 30 cases, integration loss) rather than prohibition. Still forbids what no rule permits.

**Formal expression (POWL).** Nodes as balanced, but order: `RO<{CC,ER,SC_opt}; {CC,ER}<EX_opt; {CC,ER,SC_opt,EX_opt}<AC<RP<AR; CCERSC_opt; SC_optEX_opt`. Supplier fully parallel with checks; expedite still gated by both checks.

**Code:**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

_ro2 = Transition(label="Register Order")
_cc2 = Transition(label="Credit Check")
_er2 = Transition(label="Engineering Review")
_sc2 = Transition(label="Supplier Confirmation")
_ex2 = Transition(label="Expedite Review")
_ac2 = Transition(label="Approve Configuration")
_rp2 = Transition(label="Release Production")
_ar2 = Transition(label="Archive Case")

sc_opt2 = OperatorPOWL(operator=Operator.XOR, children=[_sc2, SilentTransition()])
ex_opt2 = OperatorPOWL(operator=Operator.XOR, children=[_ex2, SilentTransition()])

model_permissive = StrictPartialOrder(nodes=[_ro2, _cc2, _er2, sc_opt2, ex_opt2, _ac2, _rp2, _ar2])
model_permissive.order.add_edge(_ro2, _cc2)
model_permissive.order.add_edge(_ro2, _er2)
model_permissive.order.add_edge(_ro2, sc_opt2)  # relaxed: SC needs only RO, not CC
# no edge _cc2 -> sc_opt2, no edge _er2 -> sc_opt2 : SC || CC, SC || ER
model_permissive.order.add_edge(_cc2, ex_opt2)
model_permissive.order.add_edge(_er2, ex_opt2)
model_permissive.order.add_edge(_cc2, _ac2)
model_permissive.order.add_edge(_er2, _ac2)
model_permissive.order.add_edge(sc_opt2, _ac2)
model_permissive.order.add_edge(ex_opt2, _ac2)
model_permissive.order.add_edge(_ac2, _rp2)
model_permissive.order.add_edge(_rp2, _ar2)
```

**Deliberately excluded (boundary of reasonable generalization):**
- *Forbidden retained:* skip/duplicate/reorder of `CC, ER, AC, RP, AR`; `AC` not before `RP`; `EX` without both `CC+ER`, `EX` after `AC` or twice; `SC` after `AC`; start not with `RO` or end not with `AR`.
- *Admitted as reasonable though unobserved:* `SC` before one or both checks (e.g. `RO, SC, CC, ER…`), `EX` without `SC` (`RO, CC, ER, EX…`), `EXSC` in any order with/without `SC`.
- *Still forbidden though syntactically possible:* `SC` concurrent with `AC/RP`, loops, partial `CC` without `ER`.

**Known underfitting risks (here under-precision / over-generalization):**
- Admits `SC-first` which has zero support and contradicts 23/23 `CC<SC`; if D5 truly requires a check first, this is risky generalization.
- Masks data-quality signal: robustness to missing `SC` comes at cost of inability to detect anomalous early `SC`.
- Lower precision may trigger false-positive compliance passes for expedited paths.

| Robustness to missing Supplier events | Brittle (missing SC maps to wrong branch or, if pattern unseen e.g. `ER,CC,EX`+lost SC, fails; masks S5) | Moderate (silent choice absorbs skip regardless of cause; `CCSC` still requires order when present) | Most robust (any position/absence accepted; best under 5–10% loss, worst for detecting loss) |
| Handling of unseen interleavings | Rejects all (including compliant `EX`-without-`SC`, mirror `EX/SC` orders) | Accepts compliant recombinations, rejects `SC-first` and `EX-without-both` | Accepts all D1–D4/D6-compliant interleavings including `SC-first` |
| Suitability for compliance vs exploration | Best for compliance/enforcement, audit, regression testing | Best for operations/decision support, balanced KPI analysis | Best for exploration, simulation, sensitivity/what-if; unsuitable as normative control |

Qualitative only; exact numbers require running §8 on the Petri-net conversions and depend on alignment costs.

# 9. Recommendation and Data-Collection Plan

**Recommend for immediate use: Balanced (POWL).** It replays all 30 cases, respects all high-confidence rules, encodes the best-supported reading of medium rules (`CCSC`, `CC,EREX`, `SCEX`, `CCER`), remains sound and compact without duplicate labels, and separates plausible generalization (expedited stocked orders, mirrored `EX/SC` orders, `SC`-between-checks) from risky generalization (`SC-first`). Conservative is too brittle for operations (any new compliant variant breaks); permissive is too lax for control.

**Recommend for sensitivity analysis: run Conservative vs Permissive as bounds.** Use conservative as lower-bound (precision/compliance oracle: any trace it rejects but balanced accepts is a generalization assumption to review) and permissive as upper-bound (recall/robustness oracle under missingness). Report KPIs under all three; flag cases where verdicts diverge (especially `SC-first` or `EX-without-SC`) for manual review.

**Concrete data-collection plan to resolve XOR vs sequence vs concurrency vs optionality:**

1. **Lifecycle timestamps:** collect `start` + `end` (or `schedule/start/complete`) for `Credit Check`, `Engineering Review`, `Supplier Confirmation`, `Expedite Review`. Concurrency test: overlapping `[start,end]` intervals + both completion orders  parallel; consistent `end(A)<start(B)`  sequence; `SC.start` after `CC.end` but before `ER.end`  overlap explanation of V5.
2. **Attributes:** export `external/stocked` flag, `expediteRequested/approvedBy`, `supplierId`, resource/role, order value. Join to traces to test S3/S4: is skip perfectly predicted by `stocked`? If yes, replace silent choice with data-aware gateway.
3. **Fix integration loss (S5):** add supplier-system acknowledgement ID, reconcile 5–10% gap, mark `isMissing` vs `isSkipped`; re-mine with repair.
4. **Preserve fine timestamps + ingestion index:** keep millisecond completion + ingestion order separately (S7) to avoid tie-break artefacts.
5. **Maximally informative future traces:** (a) `RO, ER, SC, CC…` vs `RO, SC, CC, ER…` — distinguishes “after CC” vs “after either” vs “fully parallel”; (b) `RO, CC, ER, EX…` without `SC` — tests expedited stocked path and D6 without SC; (c) `RO, CC, ER, SC…` with measured overlap of `CC/ER` — distinguishes AND vs XOR; (d) any `EX` before a check or `SC` after `AC` — would falsify D4/D6 and force redesign; (e) stocked order with `SC` present (over-processing) or external order without `SC` and without loss (violation).
6. **Experiments:** if possible, controlled variation of check durations / resource allocation to see if `CC/ER` order flips (supports S2 parallelism); targeted audit of the 7 skip cases for stocked vs lost.

# 10. Uncertainty Statement

- **Backbone `RO…ACRPAR`:** ~95% confident. 30/30 + D1/D2 high. Alternative (hidden post-approval steps) unlikely to change recommendation.
- **`CCER` (vs two opposite sequences):** ~70% concurrent/overlap, ~25% XOR-sequences, ~5% S1-style single sequence with logging error. Completion-only data cannot decide; S2 + symmetry favors concurrency but duration variance could mimic it. If start timestamps showed strict non-overlap, recommendation would shift toward conservative XOR or a LOOP-free choice.
- **`CCSC` with `ERSC` (balanced core):** ~60% confident. 23/23 supports `CCSC`; V5 (2×) breaks `ERSC`. Alternative: V5 is ingestion noise (S7) and true rule is “after both” (~25%)  conservative/balanced would need tightening; or `SCboth` is true and `CC-first` is sampling luck (~15%)  permissive would be correct. A single reliable `ER,SC,CC` or `SC-first` observation would flip this to permissive.
- **`EX after both,  SC, 1`:** ~65% confident. Only n=2, but corroborated by S6/D6 medium. Alternative: expedite needs only one check or is position-free; more cases could relax to permissive or tighten to single position (conservative).
- **Skip = stocked (S4) vs missing (S5):** ~60% mostly stocked (23% skip rate >> 5–10% loss), ~30% mixed, ~10% mostly missing. Without attribute, silent-choice abstraction is calibrated but hides cause; discovering that most skips are losses would favor permissive robustness and urgent pipeline fix over stocked-gateway design.
- **Most material alternative interpretation:** that V5 + 17/11 asymmetry are artefacts of completion-only logging with simultaneous completions ordered by ingestion (S7), and the true process is `CCER  SC  (optional EX)  AC` (strict after-both). Under that world the balanced `ERSC` edge is over-generalization, permissive `SC-first` is clearly undesirable, and a tightened balanced variant (`CC,ERSC`) plus conservative bound would be preferable. Collecting start timestamps is the single highest-value step to test this.
