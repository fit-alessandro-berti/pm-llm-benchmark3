# 1. Model scope and state variables

## Boundary and level of detail

Use a **calendar-aware, discrete-event simulation (DES)** from attempted portal submission through permit issuance, rejection, or appeal closure. Include:

- Municipal processing and queues.
- Applicant and consultant response delays.
- Public-notice and objection-related delays.
- Resource calendars, holidays, council weeks, and peak staffing.
- Rework loops and applicable parallel reviews.
- Dependencies among related applications.
- Inspection travel, batching, and no-shows.

Pre-submission effort under D1 is represented explicitly, even though it occurs before the current log boundary. Post-decision construction and enforcement are outside scope, except that prior-violation status affects D2 eligibility.

The supplied process tree is a starting control-flow model, not the simulator itself. In particular, the simulator must enforce the synchronization rule that Decision drafting waits for every applicable review, notice, and inspection outcome. Appeals and some rework also need extensions because they are not fully represented by the tree.

## Entities

| Entity | Important attributes |
|---|---|
| Application case | Case type, district, architect, value, submission time, risk, required reviews, public-notice requirement, prior violations, age, due date, rework history, current state |
| Architect | Architect ID, size/group, burst propensity, appointment-slot behavior, related-case batches |
| Related-case group | Architect, district, submission window, project/neighborhood linkage, shared objection and inspection-bundle state |
| Work item | Activity, release time, priority, required skill, estimated effort, eligible resources |
| Resource | Skill/pool, calendar, district eligibility, current assignment, utilization |
| Inspection trip | District, cases included, route/travel time, visit capacity |
| Objection episode | Latent occurrence, affected neighborhood/group, duration/severity |
| Policy regime | Effective date and active interventions |
| External responder | Applicant, consultant, objector, council-calendar process |

## Case and system state

Per-case state includes:

- Enabled, active, completed, and failed activities.
- Applicable Planning, Fire, Environmental, Public-notice, Inspection, and Legal branches.
- Arrival cohort, case age, SLA clock, and queue-enter times.
- Work consumed versus remaining service.
- Missing-document count and applicant-response clock.
- Inspection readiness, no-show status, bundle membership, and travel class.
- Rework count and cause category, including an “unknown” category.
- Public-notice minimum end date and latent objection state.
- Appeal status and final outcome.
- Decision dependencies and synchronization tokens.

System state includes:

- Time-varying queues by activity, skill, district, priority, and aging band.
- Resource availability and calendar state.
- Backlog, work in process, and completed cases.
- Architect submission burst state.
- Open related-case groups and neighborhood objection episodes.
- Inspection batches awaiting release.
- Time-varying policy and staffing state.

## Resources, queues, and calendars

Model the following pools:

- **Clerks:** five FTE, Monday–Friday 08:00–16:00; on Mondays one clerk is unavailable for permit work due to portal support.
- **Planners:** eight FTE, Monday–Friday 09:00–17:00; two restricted to Simple renovation.
- **Fire reviewers:** two FTE-equivalent, Tuesday–Thursday only.
- **Environmental reviewers:** three FTE, with only 60% permit capacity. Represent reservation through blocked calendar intervals or effective availability, not by shortening observed work.
- **Schedulers:** estimate staffing/calendar from HR and assignments; treat as uncertain because it is not fully specified.
- **Inspectors:** four FTE; site visits Tuesday–Friday, with district-specific travel and trip capacity.
- **Legal officers:** two FTE; closed during council-meeting weeks except explicitly classified urgent cases.
- **System tasks:** unlimited capacity, but retain configured processing/notification delays.
- **External responders:** delay generators rather than municipal resources.

Queues should permit skill restrictions, FIFO as a default, and configurable priority rules. D6 introduces an aging-priority allocation without assuming that all planner work becomes preemptive. Work crossing calendar closure is paused and resumed unless the activity is empirically non-preemptive.

Public-notice duration is a calendar timer, not 14 days of resource service. Its legal interpretation—calendar versus business days—must be confirmed.

## Cross-case dependencies

The model must not simulate cases independently:

1. **Correlated submissions:** architect-level cluster processes create same-week bursts, while seasonal and weekday effects determine the background intensity.
2. **Inspection bundles:** eligible cases from the same district, and especially the same architect/district group, may wait for a batching cutoff. Bundling reduces trip travel per case but increases the first case’s waiting time.
3. **Neighborhood objections:** latent neighborhood/group-level objection episodes may affect several related public notices. These are inferred, not treated as observed events.
4. **Shared-resource congestion:** all cases interact through finite queues and calendars.
5. **Policy-induced spillovers:** skipping inspections may help other case types; aging priority may delay younger cases; legal pre-check may shift work earlier rather than eliminate it.
6. **Optional shared applicant capacity:** sensitivity scenarios can model a large architect’s limited capacity to answer several missing-document requests simultaneously.

# 2. Parameter-estimation plan

## Log preparation and process-mining role

Use pandas to parse and quality-check the CSV, then `pm4py.format_dataframe` with:

- `case_id="case:concept:name"`
- `activity_key="concept:name"`
- `timestamp_key="time:timestamp"`

Use PM4Py for:

- Variant extraction and frequency analysis.
- Directly-follows and performance DFGs.
- Case-arrival statistics.
- Process-tree/Petri-net handling and conformance diagnostics.
- Token replay or alignment-based identification of deviations.
- Discovery of empirical routing and rework patterns.

Do **not** use a process-mining model as a substitute for resource queues or a calibrated DES. PM4Py establishes empirical control flow and diagnostics; a separate simulation engine handles clocks, capacities, calendars, dependencies, and policies.

The tree notation should be parsed only after normalization to PM4Py-supported syntax. If the exact installed PM4Py parser rejects the multiline simplified notation, store it as a specification, convert it manually to a Petri net/BPMN structure, and validate traces against that model.

## Arrivals

Estimate arrivals from case start events, not all event timestamps.

A suitable hierarchical count model is:

\[
N_{d,a,k}\sim \text{NegBin}(\lambda_{d,a,k},\phi)
\]

where intensity varies by:

- Date and hour.
- Month/season.
- Day of week.
- Case type.
- Architect segment.
- District.
- Holidays and policy regime.

Use a non-homogeneous Poisson model only if overdispersion tests support it. Otherwise use negative-binomial daily counts or a Cox/cluster process. Top architects should receive explicit burst models, such as a weekly architect activation followed by a cluster-size distribution and intra-week submission times. The remaining demand can use a background process.

Estimate case mix conditionally by season, architect segment, and district rather than fixing it to 45/28/17/10 in every scenario. Preserve Monday’s approximately 2.2-to-1 ratio relative to Wednesday during calibration.

## Service and waiting times

For activities with starts and completions:

- Service = completion minus start, intersected with the working calendar if work pauses overnight.
- Waiting = start minus enablement time.
- Enablement must respect joins and applicable branches.

For completion-only activities, elapsed gaps mix queueing, service, calendars, and external delays. Do not fit them directly as service time. Instead:

1. Reconstruct enablement using the process model and case attributes.
2. Infer feasible service distributions from complete records, staffing observations, task samples, and the provided medians/p90s.
3. Let simulated queues generate waiting endogenously.
4. Calibrate latent service parameters so simulated start/completion gaps and utilization match observations.
5. Propagate uncertainty by drawing alternative service/wait decompositions.

Use stratified lognormal, gamma, or Weibull models where appropriate. For long tails, compare lognormal, generalized gamma, and mixture models using censored likelihood and posterior predictive checks. Include case type, district, application value, rework number, and review flags when supported by sample size.

Applicant response, consultant reports, public notice, and travel must be modeled separately from municipal service.

## Branching and routing

Fit probabilistic models for:

- Missing-document request.
- Fire and Environmental review when flags are incomplete.
- Public notice.
- Legal check.
- Rejection and appeal.
- Rework after Planning, Inspection, and Legal.

Use known rules as deterministic constraints and estimate only unresolved portions. For example, `requires_fire=yes` always routes to Fire; cases with `no` may still route there because area is unavailable. A regularized logistic or Bayesian hierarchical model can estimate this residual risk by case type, value, district, architect segment, and observed route.

Audit routing labels against actual traces. Avoid leakage by not using downstream duration or outcome to make an earlier simulated decision.

## Rework

Identify repeated activities and alignment deviations, then construct loop episodes rather than counting every duplicate event mechanically. Estimate:

- Probability of each rework type.
- Number of loop repetitions.
- Activities invalidated by rework.
- New municipal work and external response delay.
- Transition from rework to rejection/appeal.

Stratify by case type and stage. Since reasons are unstructured, use a broad unknown-cause category. NLP-based reason coding can be exploratory but must not be treated as ground truth without manual validation.

## Calendars and allocation

Start with HR calendars and compare them to empirical activity-time heat maps. Estimate:

- Absence and effective-capacity factors.
- Activity eligibility by resource.
- Interruptibility.
- Actual assignment discipline: pooled, district-based, case ownership, or mixed.
- Council-week and holiday shutdown effects.

Resource assignment logs should be used to validate, not automatically overwrite, HR calendars because completion-only timestamps obscure actual work periods.

## Cross-case dependencies

- Detect architect bursts from within-architect interarrival distributions and weekly counts.
- Define candidate related groups using architect, district, close submission times, address/project identifiers if later available, and shared neighborhood.
- Estimate current inspection bundling from same-inspector, same-day, same-district sequences. Fit batch-size, maximum wait, and travel-saving functions.
- Estimate district travel distributions from route data if available; otherwise calibrate D3/D5 multipliers against inspection-day productivity.
- Infer objection prevalence and excess duration as a latent mixture:
  - no objection: statutory minimum plus administrative delay;
  - objection: heavy-tailed extension;
  - group-level random effect for related notices.

Because objection identity is not observed, estimate ranges and report partial identification rather than a single precise coefficient.

## Policy parameterization

Each intervention requires an explicit causal input, not just a shorter fitted duration:

- **D1:** missing-document odds ratio, number of loops, pre-submission effort, possible abandonment, and residual selection.
- **D2:** eligible share based on value, type, and prior violations; violation data must be supplied or imputed under scenarios.
- **D3:** batching window, maximum first-case delay, trip capacity, and travel reduction.
- **D4:** one inspector’s exact calendar and onboarding productivity.
- **D5:** fraction of legal work that can be done early, rework caused by changing files, and final-check effort remaining.
- **D6:** age threshold, daily reserved capacity, and release rule if no old case is waiting.
- **D7:** slot capacity, uptake, no-show/spillover behavior, and whether submissions are delayed or merely shifted.
- **D8:** triage sensitivity/specificity, review effort saved, and false-negative safeguards.
- **D9:** warning model performance, intervention uptake, and reduction in objection extension—not elimination of lawful notice.
- **D10:** compose D1–D4 at the mechanism level so that shared benefits are not double-counted.

# 3. Assumptions

## Arrivals

- Submission is the case-arrival event.
- Background demand and top-architect bursts are generated separately.
- Case mix may vary by month, district, and architect.
- D1 and D7 may change submission timing; D1 may also cause pre-submission abandonment, modeled only in sensitivity analysis unless measured.
- Emergency cases omitted from the log remain outside the primary baseline and are added as a stress scenario.

## Service times

- Service effort is distinct from elapsed time and queue waiting.
- Service distributions are conditional on activity and relevant case attributes.
- Human work pauses outside calendars unless evidence supports continuous or non-preemptive work.
- Portal and system activities have negligible capacity demand but may have short processing delays.
- Correlated task difficulty within a case is represented by a latent complexity multiplier to avoid unrealistically independent service draws.

## Routing

- Logged positive review flags deterministically require that review.
- Missing area, environmental sensitivity, and prior-violation attributes require probabilistic imputation or scenario bounds.
- Applicable reviews may execute in parallel.
- Decision drafting starts only after every applicable review, notice, and inspection dependency is complete.
- Policy rules apply by effective date and do not retroactively reroute in-progress cases unless specifically configured.

## Resources/calendars

- HR calendars are the baseline availability source.
- Environmental permit capacity is 60% of three FTE, with sensitivity around how reserved work is scheduled.
- Monday clerical permit capacity is four FTE.
- Fire review occurs only Tuesday–Thursday.
- Inspectors perform field visits Tuesday–Friday; administrative work requires a separately specified allocation.
- Legal work stops during council weeks except urgent cases.
- Overtime, absenteeism, and productivity variability are calibrated or included as uncertainty factors.
- Scheduler staffing is unknown and must be obtained or varied over a plausible range.

## Rework

- Stage-specific loops are modeled separately.
- A loop creates both additional service and possible external delay.
- Rework reasons not reliably coded remain latent.
- Rework counts are capped only for computational safety; the cap must be above observed extremes and tested for influence.
- Appeals are modeled as an extension to the supplied tree, particularly for Complex variance cases.

## Applicant/third-party response

- Missing-document response is heavy-tailed and differs by architect segment and case type.
- Consultant-report delay is distinct from Environmental reviewer effort.
- Public notice has a statutory minimum and a latent objection extension.
- Applicant readiness and no-shows affect inspection timing.
- External delays do not consume municipal capacity unless follow-up work is explicitly modeled.

## Cross-case dependencies

- Architect bursts induce correlated arrivals.
- Related cases are grouped probabilistically where definitive project/neighborhood identifiers are absent.
- Objection episodes may be shared within a neighborhood/time window.
- Inspection bundling saves travel but may hold early cases.
- Shared municipal queues create indirect interactions among all applications.

## Non-stationary demand

- Seasonal and weekday intensity is modeled explicitly.
- Baseline forecasting initially repeats or extrapolates the calibrated seasonal pattern, with trend uncertainty.
- March–May and September–November intensity is approximately 1.7 times January–February before finer estimation.
- Stress scenarios alter volume, mix, calendar availability, and burst concentration rather than scaling all durations directly.

## Missing data

- Missing starts are latent and are not replaced by arbitrary zero service times.
- Objections are unobserved latent events; long public-notice duration is only a proxy.
- Incomplete risk/routing covariates are multiply imputed.
- Rare removed emergency decisions create selection bias and are excluded from primary claims.
- Flattening may miss relationships, so cross-case parameters are sensitivity ranges until linked identifiers are available.
- Results are conditional estimates with calibration uncertainty, not claims of exact policy optimality.

# 4. Experiment matrix

All interventions should first be run singly, then in selected combinations. Use common random numbers across policies within each parameter draw.

| ID | Experiment | Key factor levels | Expected benefit | Main trade-off/risk |

| D3 | District batching | Batch window 0/1/2/3 days; max batch 2/4/6; travel saving 10/25/40% | Higher inspection productivity | First-case delay; district fairness |

For screening, use fractional factorial or Latin hypercube designs over uncertain effectiveness parameters. For finalists, run full paired replications at low, central, and high policy effectiveness. Compare D10 both with B0 and with its individual components to quantify interaction effects.

# 5. Warm-up, replications, and uncertainty treatment

## Initialization and warm-up

Use two complementary designs:

1. **Operational steady-season comparison:** simulate 12–18 months of warm-up using historical seasonality, discard warm-up outputs, then evaluate 36 months. Start sufficiently far before January so the evaluation begins with realistic aged backlog.
2. **Policy-transition comparison:** initialize from an actual snapshot of open cases, including stage, age, queue, and remaining work, then activate policy on a specified date. Do not discard the transition, because implementation effects are decision-relevant.

A Welch plot of weekly backlog, throughput, waiting, and utilization should determine whether 12–18 months is adequate. A non-stationary seasonal system should not be judged by convergence to a constant mean; compare repeated annual cycles and year-end backlog.

If offered demand exceeds sustainable capacity and backlog grows without bound, report instability rather than forcing a warm-up rule.

## Run length and replications

- Primary evaluation horizon: 36 months after warm-up.
- Transition horizon: at least 24 months, with monthly trajectories.
- Begin with 30 paired replications.
- Increase to 60–100 for finalists or until the 95% confidence-interval half-width is below:
  - 2 percentage points for SLA compliance;
  - 5% of the estimated policy effect for mean backlog;
  - 3 days for p90 duration where feasible.

Tail quantiles may require more replications or pooled quantile methods.

## Random seeds and pairing

Create a master seed sequence and separate random streams for:

- Background arrivals.
- Architect bursts.
- Case attributes.
- Routing.
- Service effort.
- External response.
- Rework.
- Objections.
- No-shows/travel.
- Resource absence.

Use common random numbers so corresponding baseline and intervention runs share exogenous demand and latent case difficulty. Policy-specific randomness should use separate derived streams. Preserve the seed registry for reproducibility.

## Interval estimates

Report:

- Paired 95% confidence intervals for intervention-minus-baseline effects.
- Bootstrap or batch/replication-based intervals for medians and p90/p95.
- Probability of improvement and probability of meeting each target.
- If Bayesian parameter models are used, posterior predictive credible intervals that integrate parameter and process uncertainty.

Distinguish:

1. Monte Carlo uncertainty.
2. Parameter-estimation uncertainty.
3. Structural uncertainty, such as objection and dependency models.
4. Policy-effect uncertainty.

## Heavy tails and censoring

- Retain right-censored open cases in estimation through survival methods.
- Avoid deleting long durations as outliers unless they are confirmed errors.
- Fit mixture or survival models to applicant response, objections, appeals, and consultant delays.
- Report median, p75, p90, p95, conditional tail mean, and probability of exceeding SLA.
- Apply a documented administrative simulation horizon; unfinished cases count as censored and contribute to backlog, not as completed zero-duration cases.
- Test tail caps or truncation only as sensitivity analyses.

## Sensitivity and uncertainty propagation

For each replication block, draw a calibrated parameter set via bootstrap, Bayesian posterior, or multiple imputation. Global sensitivity should vary:

- Arrival growth and seasonal multipliers.
- Service/wait decomposition.
- Absence and effective capacity.
- Rework probabilities.
- External-response tail parameters.
- Objection prevalence and correlation.
- Related-case grouping.
- D2 eligibility.
- D3 travel saving and hold time.
- Intervention uptake/effectiveness.

Use Latin hypercube sampling and summarize standardized effects, rank correlations, or Sobol indices where computationally feasible.

# 6. Validation strategy

## Face validation

Conduct structured walkthroughs with clerks, planners, reviewers, inspectors, legal officers, portal staff, applicants, and policy owners. Validate:

- Routing and synchronization.
- Queue disciplines and informal priorities.
- Real calendars, meeting weeks, and work interruption.
- Rework semantics.
- Inspection batching behavior.
- Plausibility of objection and applicant-response mechanisms.
- Intervention implementation details.

Use case animations and weekly queue/resource dashboards, not only aggregate averages.

## Event-log replay validation

Replay historical cases through the process model using PM4Py token replay or alignments to identify:

- Missing activities.
- Duplicate/rework behavior.
- Ordering deviations.
- Fitness and precision issues.
- Cases not represented by the supplied tree.

Replay validates control flow; it does not establish service-time or capacity validity. Extend the model for appeals and recurring completeness checks where required.

For simulation replay, feed historical arrivals and observed case attributes into the calibrated simulator, while allowing queues and durations to be generated. Compare simulated event sequences and timestamps with the log.

## Distributional validation

Compare observed and simulated distributions by case type, district, month, and variant group:

- Throughput and arrivals.
- End-to-end duration.
- Activity-to-activity elapsed times.
- Queue lengths and case ages where snapshots exist.
- Rework counts.
- Route shares and outcomes.
- Public-notice duration.
- Inspection batch size and same-district sequencing.

Use ECDFs, quantile–quantile plots, Wasserstein distance, calibration bands, and coverage of observed median/p90 values. Do not rely on mean absolute error alone.

## Resource-utilization validation

Compare simulated and operational evidence for:

- Activity completions by resource and week.
- Busy hours and idle/calendar-blocked hours.
- Queue lengths before Fire, Environmental, Inspection, and Legal.
- Tuesday–Thursday Fire throughput.
- Inspector visits per day and district travel mix.
- Legal throughput around council weeks.
- Monday clerk backlog.

Where start times are absent, validate utilization against staffing studies, work sampling, timesheets, or supervisor estimates rather than inferring exact utilization from completion timestamps.

## Bottleneck validation

The simulator should reproduce known qualitative and quantitative bottlenecks:

- Post-Monday Completeness queues.
- Fire constraints from part-time calendars.
- Environmental variability and consultant effects.
- Longer D3/D5 inspection cycles.
- Council-week Legal pauses.
- Long public-notice tails and Complex variance aging.
- Spillover effects when inspector or legal capacity is reduced.

Perform controlled perturbation tests: adding a small amount of capacity to a true bottleneck should change the appropriate queues and not implausibly reduce unrelated service effort.

## Out-of-sample validation

Use rolling temporal splits, for example:

- Train/calibrate on months 1–12.
- Validate on months 13–18.

Alternatively use several rolling-origin folds to include both peak and low seasons. Hold out some top architects or districts to test hierarchical generalization. Freeze parameters before evaluating the holdout.

Compare:

- Weekly arrivals and completions.
- Monthly backlog.
- Case-type median/p90.
- SLA compliance.
- Route and rework rates.
- Resource throughput and seasonal peaks.

A model that matches aggregate duration but fails district tails, council-week behavior, or Monday queues is not sufficiently validated for policy comparison.

# 7. Decision criteria

Targets should be approved by the municipality before results are viewed. The following are useful screening ranges rather than asserted legal standards.

| Dimension | Suggested selection criterion |
|---|---|
| Median duration | At least 10% reduction overall or in the targeted case type, with no material deterioration elsewhere |
| Tail duration | At least 10–15% reduction in p90 for targeted types; report p95 and conditional tail mean |
| SLA compliance | At least +5 percentage points for targeted case types, or 90% if that is the adopted SLA; no type worsens by more than 2 points |
| Backlog | No positive year-over-year growth under baseline demand; 10% lower average aged backlog for finalists |
| Aging cases | Fewer cases above 60/90/180-day thresholds; D6 should reduce old cases without excessive young-case harm |
| Resource utilization | Sustainable target generally 70–85%; flag persistent >90% monthly utilization or excessive idle capacity |
| Rework | 15% reduction for D1 or relevant quality interventions; no increase in late-stage rework |
| District fairness | Worst-district SLA gap no more than 5 percentage points larger than baseline; ideally narrow the D3/D5 gap |
| Architect fairness | Compare large versus small architects and appointment users/non-users; no subgroup loses >5 SLA points without justified mitigation |
| Applicant burden | D1/D7 pre-submission effort and delays explicitly reported; assess abandonment and digital-access effects |
| Inspection access | D3 must not increase median first-case bundle waiting by more than 2 days unless tail/throughput gains justify it |
| Robustness | Benefit remains positive in at least 80% of parameter draws and all but explicitly extreme stress scenarios |
| Cost effectiveness | Report cost per SLA-compliant additional case, backlog-day avoided, and temporary/permanent FTE need |
| Stability | Reject configurations whose backlog has a persistent positive trend under central demand |
| Safety/legal guardrails | D2/D8 cannot be selected solely on cycle time; require external safety, compliance, audit, and false-negative thresholds |

Report all metrics by case type and district, and where sample sizes allow by architect-size segment. For very small architect groups, use privacy-preserving aggregation or hierarchical estimates.

A policy is a candidate for implementation if it:

1. Meets legal and safety guardrails.
2. Improves targeted median and tail measures with paired uncertainty intervals.
3. Does not create unacceptable district, architect, or case-type disparities.
4. Remains operationally stable under at least the +20% demand and capacity-shock scenarios.
5. Has a feasible implementation cost and calendar.
6. Has monitorable leading indicators and a rollback rule.

Use a Pareto frontier across duration, fairness, risk, and cost rather than a single unvalidated weighted score. Simulation ranks are conditional on the calibrated model; they do not establish exact optimality.

def load_log(path: Optional[str] = None) -> pd.DataFrame:
    if path is None:
        raw = pd.read_csv(StringIO(LOG_EXCERPT))
    else:
        raw = pd.read_csv(path)

    raw["time:timestamp"] = pd.to_datetime(
        raw["time:timestamp"], errors="raise"
    )

    # If real start timestamps exist, parse them too. They are absent here.
    if "start_timestamp" in raw.columns:
        raw["start_timestamp"] = pd.to_datetime(
            raw["start_timestamp"], errors="coerce"
        )

    formatted = pm4py.format_dataframe(
        raw,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    return formatted.sort_values(
        ["case:concept:name", "time:timestamp"]
    ).reset_index(drop=True)

TREE_SPEC = """
->(
  'Submit application',
  *(
    ->(
      'Completeness check',
      X(
        tau,
        ->('Request missing documents','Receive missing documents')
      )
    ),
    'Completeness rework'
  ),
  +(
    'Planning review',
    X(tau,'Fire-safety review'),
    X(tau,'Environmental review')
  ),
  X(tau,'Public-notice period'),
  *(
    ->('Inspection scheduling','Site inspection'),
    'Inspection rework'
  ),
  'Decision drafting',
  X(tau,'Legal check'),
  X('Issue permit','Reject application')
)
"""


def parse_tree_spec(tree_text: str):
    """
    PM4Py process-tree parsing is version-sensitive regarding whitespace and
    accepted textual syntax. Try the public pm4py.parse_process_tree API after
    normalizing whitespace.

    If this simplified specification is rejected, the correct response is to
    translate it deliberately to a PM4Py process tree/Petri net, not silently
    alter its semantics. Appeals and the all-applicable-results synchronization
    also require simulator-side/model extensions.
    """
    normalized = re.sub(r"\s+", " ", tree_text).strip()
    try:
        return pm4py.parse_process_tree(normalized)
    except Exception as exc:
        print("Process tree was not parsed:", exc)
        print(
            "Treat TREE_SPEC as a control-flow specification and build/validate "
            "an equivalent PM4Py tree, Petri net, or BPMN model explicitly."
        )
        return None

def pm4py_descriptives(df: pd.DataFrame) -> dict[str, Any]:
    # Current PM4Py versions expose these convenience APIs.
    variants = pm4py.get_variants_as_tuples(df)
    dfg = pm4py.discover_dfg(df)
    performance_dfg = pm4py.discover_performance_dfg(df)

    try:
        arrival_average_seconds = pm4py.get_case_arrival_average(df)
    except AttributeError:
        # Transparent fallback for versions without the convenience function:
        # average difference between consecutive case-start timestamps.
        starts = (
            df.groupby("case:concept:name")["time:timestamp"]
              .min()
              .sort_values()
        )
        arrival_average_seconds = (
            starts.diff().dropna().dt.total_seconds().mean()
        )

    return {
        "variants": variants,
        "dfg": dfg,
        "performance_dfg": performance_dfg,
        "case_arrival_average_seconds": arrival_average_seconds,
    }

def add_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Adds observable elapsed-gap columns and, only where starts are present,
    service/wait columns.

    prev_completion_to_completion_seconds is NOT service time. With a
    completion-only log it combines enablement error, waiting, service,
    calendar closure, and possibly external delay.
    """
    x = df.sort_values(
        ["case:concept:name", "time:timestamp"]
    ).copy()

    x["previous_completion"] = (
        x.groupby("case:concept:name")["time:timestamp"].shift(1)
    )
    x["prev_completion_to_completion_seconds"] = (
        x["time:timestamp"] - x["previous_completion"]
    ).dt.total_seconds()

    # A real implementation should calculate enabled_timestamp from replay of
    # the process model, including joins and applicable branches.
    if "enabled_timestamp" not in x.columns:
        x["enabled_timestamp"] = pd.NaT

    if "start_timestamp" in x.columns:
        x["service_seconds_raw"] = (
            x["time:timestamp"] - x["start_timestamp"]
        ).dt.total_seconds()

        x["waiting_seconds_raw"] = (
            x["start_timestamp"] - x["enabled_timestamp"]
        ).dt.total_seconds()

        # Calendar-adjusted work effort must be computed by the calendar module;
        # raw elapsed service can include nights/weekends.
        x["service_seconds_calendar_adjusted"] = np.nan
    else:
        # Explicitly unknown rather than incorrectly assigning the whole gap.
        x["service_seconds_raw"] = np.nan
        x["waiting_seconds_raw"] = np.nan
        x["service_seconds_calendar_adjusted"] = np.nan

    return x


def case_level_arrivals(df: pd.DataFrame) -> pd.DataFrame:
    starts = (
        df.groupby("case:concept:name", as_index=False)
          .agg(
              arrival=("time:timestamp", "min"),
              case_type=("case_type", "first"),
              district=("district", "first"),
              architect_id=("architect_id", "first"),
          )
          .sort_values("arrival")
    )
    starts["month"] = starts["arrival"].dt.month
    starts["weekday"] = starts["arrival"].dt.dayofweek
    starts["week"] = starts["arrival"].dt.to_period("W").astype(str)
    return starts

@dataclass(frozen=True)
class WeeklyCalendar:
    name: str
    # day-of-week -> list of [start_hour, end_hour) intervals
    intervals: Mapping[int, tuple[tuple[float, float], ...]]
    holidays: frozenset[pd.Timestamp] = frozenset()
    blocked_weeks: frozenset[str] = frozenset()

    def is_open(self, timestamp: pd.Timestamp) -> bool:
        day = timestamp.normalize()
        if day in self.holidays:
            return False
        if timestamp.to_period("W").start_time.strftime("%Y-%m-%d") in self.blocked_weeks:
            return False
        hour = timestamp.hour + timestamp.minute / 60.0
        return any(
            start <= hour < end
            for start, end in self.intervals.get(timestamp.dayofweek, ())
        )

    def add_work_time(
        self, start: pd.Timestamp, work_seconds: float
    ) -> pd.Timestamp:
        """
        Placeholder: production code should advance only through open calendar
        intervals and support pauses, absences, and council-week exceptions.
        """
        raise NotImplementedError

class RoutingModel:
    def __init__(
        self,
        parameters: Mapping[str, Any],
        policy: PolicyConfig,
        rng: np.random.Generator,
    ):
        self.p = parameters
        self.policy = policy
        self.rng = rng

    def required_reviews(self, case: CaseState) -> set[str]:
        reviews = {"Planning review"}

        # Logged positive flags are deterministic; unresolved missing attributes
        # are handled by calibrated residual probabilities.
        if case.requires_fire:
            reviews.add("Fire-safety review")
        elif self.rng.random() < self.p.get("residual_fire_probability", 0.0):
            reviews.add("Fire-safety review")

        if case.requires_environment:
            reviews.add("Environmental review")
        elif self.rng.random() < self.p.get(
            "residual_environment_probability", 0.0
        ):
            reviews.add("Environmental review")

        return reviews

    def skip_inspection(self, case: CaseState) -> bool:
        return bool(
            self.policy.simple_skip_inspection
            and case.case_type == "Simple renovation"
            and case.application_value < 50_000
            and case.prior_violation is False
        )

    def decision_dependencies(self, case: CaseState) -> set[str]:
        deps = set(self.required_reviews(case))
        if case.requires_public_notice:
            deps.add("Public-notice period")
        if not self.skip_inspection(case):
            deps.add("Site inspection")
        return deps


class DependencyManager:
    """
    Maintains cross-case state:
      * architect burst groups,
      * architect/district inspection bundles,
      * neighborhood-level objection episodes.
    """

    def __init__(self, rng: np.random.Generator):
        self.rng = rng
        self.open_inspection_batches: dict[str, list[CaseState]] = {}
        self.objection_episodes: dict[str, dict[str, Any]] = {}

    def inspection_group_key(self, case: CaseState) -> str:
        return f"{case.district}:{case.architect_id}"

    def add_to_inspection_batch(self, case: CaseState) -> None:
        key = self.inspection_group_key(case)
        self.open_inspection_batches.setdefault(key, []).append(case)

    def latent_objection_extension_days(self, case: CaseState) -> float:
        # Must be calibrated as a latent correlated mixture, not interpreted as
        # an observed objection event.
        raise NotImplementedError


class SimulationEngine:
    """
    Minimal event-list shell. A production implementation could instead use
    SimPy, salabim, or a custom calendar-aware DES, but PM4Py remains separate.
    """

    def __init__(
        self,
        resources: Mapping[str, ResourcePool],
        routing: RoutingModel,
        dependencies: DependencyManager,
        rng: np.random.Generator,
    ):
        self.resources = resources
        self.routing = routing
        self.dependencies = dependencies
        self.rng = rng
        self.event_queue: list[tuple[pd.Timestamp, int, Callable, tuple]] = []
        self.counter = 0
        self.metrics: list[dict[str, Any]] = []

    def schedule(
        self, when: pd.Timestamp, callback: Callable, *args: Any
    ) -> None:
        self.counter += 1
        heapq.heappush(
            self.event_queue, (when, self.counter, callback, args)
        )

    def run(self, until: pd.Timestamp) -> pd.DataFrame:
        while self.event_queue and self.event_queue[0][0] <= until:
            now, _, callback, args = heapq.heappop(self.event_queue)
            callback(now, *args)
        return pd.DataFrame(self.metrics)

def weekday_intervals(
    days: Iterable[int], start: float, end: float
) -> dict[int, tuple[tuple[float, float], ...]]:
    result = {d: tuple() for d in range(7)}
    for d in days:
        result[d] = ((start, end),)
    return result

def make_seed_streams(master_seed: int) -> dict[str, np.random.Generator]:
    names = [
        "arrivals", "attributes", "routing", "service", "external",
        "rework", "objections", "travel", "absence"
    ]
    children = np.random.SeedSequence(master_seed).spawn(len(names))
    return {
        name: np.random.default_rng(child)
        for name, child in zip(names, children)
    }


def run_experiment(
    policy: PolicyConfig,
    calibrated_parameters: Mapping[str, Any],
    start: pd.Timestamp,
    end: pd.Timestamp,
    seed: int,
) -> pd.DataFrame:
    streams = make_seed_streams(seed)

    arrivals = ArrivalGenerator(
        calibrated_parameters["arrivals"], streams["arrivals"]
    )
    routing = RoutingModel(
        calibrated_parameters["routing"], policy, streams["routing"]
    )
    dependencies = DependencyManager(streams["objections"])
    resources = build_resources(policy)

    engine = SimulationEngine(
        resources=resources,
        routing=routing,
        dependencies=dependencies,
        rng=streams["service"],
    )

    # Production code:
    # 1. generate arrivals, including correlated architect clusters;
    # 2. create CaseState objects and schedule submission events;
    # 3. enqueue enabled activities into calendar-aware finite resource pools;
    # 4. schedule external response and public-notice timers separately;
    # 5. synchronize all applicable dependencies before Decision drafting;
    # 6. implement inspection batches and stage-specific rework;
    # 7. collect case, queue, utilization, fairness, and backlog metrics.
    for arrival_record in arrivals.generate(start, end):
        pass

    return engine.run(until=end)


def compare_policies(
    policies: Iterable[PolicyConfig],
    parameters: Mapping[str, Any],
    start: pd.Timestamp,
    end: pd.Timestamp,
    seeds: Iterable[int],
) -> pd.DataFrame:
    outputs = []
    for seed in seeds:
        # The same seed creates common exogenous streams across policies.
        for policy in policies:
            result = run_experiment(
                policy, parameters, start, end, seed
            )
            result["policy"] = policy.name
            result["seed"] = seed
            outputs.append(result)

    return pd.concat(outputs, ignore_index=True) if outputs else pd.DataFrame()
