## 1. Interaction-graph description

The object graph has **seven important node types**: Job, Component, ComponentLot, Batch, Machine, Tool, and Shipment. Edges are typed by the qualifier in the O2O relations, plus event-derived edges read from object-centric events.

Compact edge-list representation (only important relations; all jobs/components are listed):

```
requires:        J1-C1, J2-C2, J3-C3, J4-C4, J5-C5, J6-C6
contains:        L7-C2, L7-C5, L8-C1, L8-C3
batches:         B1-J1/J2/J3, B2-J4/J5
consolidates:    S1-J1/J4, S2-J2/J3, S3-J5/J6

event-derived:
J3 --holds--> FIX-A            (09:00-11:40)
J4 --uses--> FIX-A on CNC-2    (11:45 process event)
B1 --runs_on--> OVEN-1         (12:05 cure event)
B1 --uses--> RACK-7            (12:05 cure event)
L7 --quarantine/release--> J2/J5 (10:20/13:50)
J5,J6 --uses--> CAL-3 on TEST-1 (16:10/17:25)
```

The relation edges `requires`, `contains`, `batches`, and `consolidates` are **direct observations** from the supplied O2O relations. The edges involving machines, tools, and lot events are **direct event co-occurrences** with one qualification: tool holding is inferred from acquire/release timestamps, and the lot release event is inconsistently linked to jobs in the source logs. The graph is a projection of event hyperedges: for example, the 12:05 `Batch Cure` event participates in B1, OVEN-1, RACK-7, J1, J2, J3, C1, C2, and C3, so it creates a clique among those objects.

Higher-order motifs involving more than two object types:

- **Full-batch synchronization motif**: B1 batches J1/J2/J3; each job requires C1/C2/C3; B1 runs on OVEN-1 using RACK-7. This is a four-type motif in which the batch start is controlled by the latest ready job.
- **Tool-mediated chain motif**: J3 holds FIX-A until 11:40; J4 arrives at CNC-2 at 09:50; J4’s process event at 11:45 includes FIX-A. Thus J4 is coupled to J3 through a tool, even with no direct Job-Job edge.
- **Shared component-lot motif**: J2 requires C2 and J5 requires C5; both belong to L7. The quarantine/release event connects L7, J2, and J5, coupling two jobs that appear independent in job flattening.
- **Shipment consolidation motif**: S1 consolidates J1 and J4; J1 is packed at 13:30 but J4 is packed at 19:10, so the shipment edge connects an early job to a late job.

## 2. Quantitative delay decomposition

Each calculation is a counterfactual decomposition, not causal proof. The observed times are taken from the object-centric timing evidence.

1. **J1 delay in B1 synchronization**  
   - Ready for batch: 08:10.  
   - Batch start: 12:05.  
   - Wait = 3 h 55 min.  
   - Counterfactual: if J1 could process immediately when ready, without waiting for J3, it would save 235 minutes. This assumes the 08:10 readiness timestamp is true and OVEN-1/RACK-7 were otherwise available.

2. **J2 delay in B1 synchronization**  
   - Ready for batch: 08:25.  
   - Batch start: 12:05.  
   - Wait = 3 h 40 min.  
   - Counterfactual: same as J1; saving 220 minutes if no full-batch wait existed.

3. **B2 waiting for J4 and RACK-7**  
   - J4 ready: 13:10.  
   - B2 start: 14:50.  
   - Total wait = 1 h 40 min.  
   - RACK-7 is unavailable until 14:35. Counterfactual A: if J4 could start when ready and RACK-7 was already available, save 100 minutes. Counterfactual B: if RACK-7 was the only constraint, J4 would still wait until 14:35, so only the final 15 minutes appear to be batch/setup delay after J5 became ready at 14:40. The split is illustrative, not definitive.

4. **FIX-A-related delay for J4**  
   - J4 reaches CNC-2: 09:50.  
   - J3 releases FIX-A: 11:40.  
   - J4 `Machine Process` starts: 11:45.  
   - Delay plausibly associated with FIX-A = 1 h 50 min, plus 5 minutes of setup.  
   - Counterfactual: if FIX-A had been free and CNC-2 available at 09:50, J4 could have started at 09:50. This ignores any unrecorded work J4 may have performed.

5. **Shipment consolidation delay for J1**  
   - J1 packed: 13:30.  
   - S1 dispatch: 19:25.  
   - Packed-to-dispatch wait = 5 h 55 min.  
   - S2/S3 dispatch 25/35 minutes after their last packed job. Counterfactual: if J1 were dispatched soon after packing under a similar policy, it would save roughly 5 h 30 min. If S1 follows a fixed truck schedule, this is a policy choice rather than a production bottleneck.

6. **CAL-3-related delay for J6**  
   - J6 ready for final test: 16:05.  
   - J6 test start: 17:25.  
   - Wait = 1 h 20 min.  
   - CAL-3 is recalibrated from 16:35 to 17:20; TEST-1 is idle during that time. Counterfactual A: no J5 test and no recalibration, save 80 minutes. Counterfactual B: J5 still tests but recalibration is not needed, J6 could start at 16:35, saving 50 minutes. The idle TEST-1 window shows the constraint is CAL-3, not TEST-1.

## 4. What flattening misses

### Job flattening
- **Visible**: each job’s path from Release to Stage, Machine Process, Inspect, Pack, and Dispatch; rework loops; individual total durations.
- **Hides/duplicates**: waits that are not activities, such as waiting for a batch partner, tool, lot release, or shipment partner. It also hides the lot release events for J2/J5.
- **Misleading DFG conclusion**: the Job-flattened DFG looks broadly normal, but J1’s `Pack -> Dispatch` edge is really 5 h 55 min. The median of 1.1 h hides the long tail caused by S1 consolidation.

### Machine flattening
- **Visible**: utilization, typical activity sequence, and gaps between machine events.
- **Hides/duplicates**: why a machine is idle. OVEN-1 is idle from 12:55 to 14:50 partly because RACK-7 is quarantined and J5 is not ready. TEST-1 is idle from 16:35 to 17:25 because CAL-3 is being recalibrated.
- **Misleading conclusion**: 44–58% utilization suggests no machine bottleneck, but the bottleneck may be elsewhere; a machine gap is not proof that the machine was available to a waiting job.

### Batch flattening
- **Visible**: if a batch object is used, synchronization and batch cycle time become visible.
- **Hides/duplicates**: flattening the batch event to jobs makes J1, J2, and J3 appear as if they all experienced the 12:05 cure at once; it does not show that J1/J2 were ready hours earlier.
- **Misleading conclusion**: the batch event at 12:05 looks like a single start time, but the relevant delay is the gap between readiness and batch start.

### Tool flattening
- **Visible**: acquire/release intervals, cleaning, and recalibration, if the Tool object type is retained.
- **Hides/duplicates**: because there is no explicit `Wait for Tool` activity, J4’s 09:50 arrival at CNC-2 and 11:45 process start look like a long machine delay rather than a tool wait.
- **Misleading conclusion**: absence of a wait activity is not evidence that no wait occurred; it is evidence that waiting is not captured.

### ComponentLot flattening
- **Visible**: quarantine and release events for L7/L8.
- **Hides/duplicates**: the link from lot events to jobs is inconsistent. The Job flattening does not show the 10:20 quarantine or the 13:50 release because the extraction used only job-related events. J2’s override before release creates an apparent temporal contradiction.
- **Misleading conclusion**: it may appear that component availability is irrelevant, while in fact J5 reports being blocked until lot release.

### Shipment flattening
- **Visible**: `Create Shipment -> Load -> Dispatch` edges and shipment durations.
- **Hides/duplicates**: how long an already packed job waits for shipment partners. J1 packs at 13:30 and dispatches at 19:25; the shipment flattening only sees the short load/dispatch segment.
- **Misleading conclusion**: shipment consolidation looks efficient because loading and dispatch are short, but the packed-job dwell time is invisible.

Low machine utilization can coexist with long job waiting because the waiting is not in the machine queue. Jobs wait for batch synchronization, tool release, lot release, or shipment consolidation. Machines can be idle while jobs are blocked elsewhere, and jobs can be waiting while the machine is idle because the missing object is not the machine.

## 5. Object-lifecycle evidence

### Narrative 1: FIX-A  CNC-2  S1  J1

Objects: J3, FIX-A, J4, CNC-2, J1, S1.

- **Temporal precedence**: J3 acquires FIX-A at 09:00, releases at 11:40. J4 reaches CNC-2 at 09:50. J4’s `Machine Process` starts at 11:45. J4 packs at 19:10. S1 dispatches at 19:25.
- **Resource feasibility**: FIX-A is a single tool; J3 and J4 cannot hold it simultaneously. CNC-2 is idle from 10:05 to 10:47, so the machine is not the reason J4 cannot start during that interval.
- **Policy constraints**: S1 consolidates J1 and J4. J1 is packed at 13:30 but cannot leave until S1 dispatches.
- **Causal speculation**: J4 likely waits for FIX-A until 11:40, which pushes J4’s completion to 19:10, which delays S1 and forces J1 to wait. This is plausible but not proven because J4 may have had unlogged work and S1 may have a fixed departure schedule.

### Narrative 2: L7 quarantine  B2  TEST-1/CAL-3  S3

Objects: L7, C2, C5, J2, J5, B2, OVEN-1, RACK-7, CAL-3, TEST-1, J6, S3.

- **Temporal precedence**: L7 is quarantined at 10:20 and released at 13:50. J2 enters B1 at 12:05 through a supervisor override. J5 becomes ready for B2 at 14:40; B2 starts at 14:50. J5 tests 16:10-16:35; CAL-3 recalibrates until 17:20; J6 tests 17:25-17:50.
- **Resource feasibility**: B2 needs OVEN-1 and RACK-7; RACK-7 is cleaning/quarantined until 14:35. Final test requires both TEST-1 and CAL-3.
- **Policy constraints**: lot quarantine applies to C2 and C5; J2 bypasses it, while J5 does not. Batch policy holds B2 until J5 is ready.
- **Causal speculation**: the quarantine delays J5 until 13:50, and J5 readiness at 14:40 sets B2’s start. J5’s later test occupies CAL-3, delaying J6. Again, temporal order supports this but does not prove it.

### Narrative 3: B1 synchronization and shared rack/oven

Objects: J1, J2, J3, B1, OVEN-1, RACK-7, C1, C2, C3.

- **Temporal precedence**: J1 ready at 08:10; J2 ready at 08:25; J3 ready at 11:55; B1 starts at 12:05. OVEN-1 is idle from 12:55 to 14:50; RACK-7 is quarantined until 14:35.
- **Resource feasibility**: B1 cannot start before all three jobs are ready if the full-batch policy is enforced. OVEN-1 and RACK-7 are both needed for the cure event.
- **Policy constraints**: full-batch synchronization causes J1/J2 waiting. After B1, RACK-7 cleaning/quarantine imposes a minimum gap before B2.
- **Causal speculation**: J3’s late readiness directly creates J1/J2 waits. B1’s end and RACK-7 cleaning delay B2. J3’s late readiness itself may stem from upstream work, so batch synchronization is a proximate mechanism rather than the deepest root cause.

## 6. Intervention portfolio and spillovers

### Intervention 1: Decouple batch synchronization with a release cutoff

- **Target mechanism**: batch synchronization.
- **Expected benefit**: reduce J1/J2/J4 waits; lower WIP; smoother flow.
- **Jobs/objects helped**: J1, J2, J4; downstream shipments may improve.
- **Jobs/objects potentially harmed**: J3 and J5 may wait more if the oven is occupied by partial batches; more oven cycles could hurt efficiency.
- **New cost/risk**: extra oven energy, thermal variability, more setups, lower batch fill rates.
- **Perverse incentive**: “time from first-ready to batch start” could encourage starting nearly empty batches too early.
- **Object-centric evaluation**: compare ready-to-cure intervals and batch size distributions before/after using OCEL; track energy and number of oven cycles per job, not just cycle time.

### Intervention 2: Make tools schedulable and visible

- **Target mechanism**: shared-tool contention.
- **Expected benefit**: reduce J4’s FIX-A wait and J6’s CAL-3 wait.
- **Jobs/objects helped**: J4, J6, and possibly S1/S3 if completions advance.
- **Jobs/objects potentially harmed**: J3/J5 if priority rules change; maintenance risk if recalibration is deferred.
- **New cost/risk**: duplicate tools, extra calibration/cleaning capacity, operator training, tool-maintenance cost.
- **Perverse incentive**: “tool idle time” could encourage unnecessary recalibration or holding tools to appear busy.
- **Object-centric evaluation**: build a Tool-Job-Machine interaction graph, measure J4/J6 waiting percentiles before/after, and compare tool conflict counts rather than machine utilization.

### Intervention 3: Rework shipment consolidation policy

- **Target mechanism**: shipment consolidation.
- **Expected benefit**: cut J1’s 5 h 55 min packed wait; improve delivery responsiveness.
- **Jobs/objects helped**: J1 and customers expecting earlier delivery.
- **Jobs/objects potentially harmed**: J4 may bear higher freight if shipped alone; logistics cost increases.
- **New cost/risk**: more shipments, lower load factors, higher carrier costs, possible environment trade-offs.
- **Perverse incentive**: “packed-to-dispatch time” could lead to dispatching incomplete shipments just to hit the metric.
- **Object-centric evaluation**: compare packed-to-dispatch time, load factor, freight cost per job, and dispatch variability using Job and Shipment objects in OCEL.

### Intervention 4: Integrate lot release with job execution

- **Target mechanism**: component-lot release coupling and inconsistent lot job linkage.
- **Expected benefit**: make quarantine visible; prevent J5-type hidden waits; reduce supervisor overrides.
- **Jobs/objects helped**: J5, J2, planners.
- **Jobs/objects potentially harmed**: urgent jobs may lose flexibility if overrides are restricted.
- **New cost/risk**: system integration, governance overhead, more administrative work.
- **Perverse incentive**: reducing “override count” could cause people to hide overrides or stop making necessary exceptions.
- **Object-centric evaluation**: track lot quarantine/release events and job release events jointly; compare J5’s release-to-ready interval and conformance before/after; audit override events as cases, not delete them.

### Intervention 5: Add explicit wait-state logging

- **Target mechanism**: data-integration artifacts and invisible waiting.
- **Expected benefit**: managers see waiting caused by tools, batches, lots, and shipments; enable corrective action.
- **Jobs/objects helped**: all jobs through improved planning.
- **Jobs/objects potentially harmed**: no operational jobs, but data entry overhead and system migration risk.
- **New cost/risk**: event schema changes, training, duplicate or inaccurate wait events.
- **Perverse incentive**: “number of wait events” could become an operational target, encouraging event inflation or reclassification.
- **Object-centric evaluation**: run PM4Py OCEL discovery before/after; compare flattened DFGs with object-centric graphs and validate wait-event timestamps against physical records.

### Intervention 6: Release work only when component lot, tool, and batch are aligned

- **Target mechanism**: lot release, tool contention, and batch synchronization together.
- **Expected benefit**: reduce forced waiting, overrides, and cascading shipment delays.
- **Jobs/objects helped**: J5, J4, J6; S1/S3 could improve.
- **Jobs/objects potentially harmed**: J1/J2 may be released later under stricter gating; initial throughput may drop.
- **New cost/risk**: lower WIP could starve machines; planning complexity increases.
- **Perverse incentive**: “WIP level” as a target could discourage necessary work release.
- **Object-centric evaluation**: use a controlled rollout with the discovered object graph; measure end-to-end cycle time, waiting by cause category, utilization, and shipment adherence.

## 7. PM4Py analysis outline

The code below assumes an OCEL variable named `ocel`. It compares two object-centric frequency metrics and intentionally does not infer waiting from machine-event gaps.

```python
import pm4py
import pandas as pd

# 1. Object interaction frequencies: metric A
interactions = pm4py.ocel_objects_interactions_summary(ocel)
freq_by_type = interactions.groupby(["source_type", "target_type"])["count"].sum().sort_values(ascending=False)
print("Metric A - object type pair frequencies:")
print(freq_by_type.head(10))

# 2. Discover object graph and object-type graph
objects_graph = pm4py.discover_objects_graph(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)

# 3. Object-centric DFG: metric B
ocdfg_freq, ocdfg_perf = pm4py.discover_ocdfg(ocel, property_filter="frequency")
print("Object-centric DFG frequency edges:", len(ocdfg_freq))
print("Object-centric DFG performance edges:", len(ocdfg_perf))

# 4. Flatten to a job perspective for traditional comparison
flat_job = pm4py.ocel_flattening(ocel, object_type="job", flattening="performance")
job_perf_dfg = pm4py.discover_performance_dfg(flat_job)
job_freq_dfg = pm4py.discover_performance_dfg(flat_job)  # frequency counterpart if needed

# 5. Extract object-centric features
features = pm4py.extract_ocel_features(ocel)

# 6. Compare metric A and metric B
metric_A = freq_by_type
metric_B = pd.Series(ocdfg_freq).value_counts(normalize=True)
comparison = pd.DataFrame({
    "interaction_freq": metric_A,
    "ocdfg_event_freq": metric_B.reindex(metric_A.index).fillna(0)
})
print(comparison.sort_values("interaction_freq", ascending=False).head(10))

# 7. Optional networkx conversion for connected-component analysis
if hasattr(pm4py, "convert_ocel_to_networkx"):
    G = pm4py.convert_ocel_to_networkx(ocel)
    print("NetworkX graph nodes:", G.number_of_nodes(), "edges:", G.number_of_edges())

# 8. Waiting should be computed from Ready events, not machine gaps.
# Suppose the OCEL has an activity named "ReadyForBatch" and an event timestamp.
# If a ready event exists, compare it with the actual activity start time.
if "ocel:events" in ocel:
    events = ocel["ocel:events"]
    if "ready_time" in events.columns:
        wait_times = events["actual_start"] - events["ready_time"]
        print(wait_times.describe())
    else:
        print("No ready_time column available; do NOT infer waiting from machine gaps.")
```

## 8. Falsification and additional data

Observations that would weaken the top-ranked batch-synchronization explanation:

1. If physical tracking showed J1/J2 were not actually at the oven until 12:00, the 08:10/08:25 readiness timestamps are unreliable.
2. If OVEN-1 was undergoing setup until 12:05, the wait would be machine-caused rather than batch-caused.
3. If J3 was deliberately held to meet a thermal batch-size requirement, the wait is a process constraint, not a scheduling inefficiency.
4. If J4’s FIX-A wait was actually caused by operator lunch or preventive maintenance, tool contention would be less important.
5. If S1 had a scheduled departure at 19:25 regardless of J4, J1’s wait is due to a fixed route, not consolidation.
6. If L7’s release event was a paperwork transaction and J5 was physically free to proceed earlier, the lot-release coupling would be overstated.
7. If J2’s override actually moved C2 from a separate non-quarantined lot, then J2 and J5 do not share a blocking material constraint.
8. If the 12:05 `Batch Cure` event is an electronic approval timestamp rather than the physical cure start, the synchronization delay is mis-measured.

Additional fields or event types that would discriminate among hypotheses:

- `ReadyForActivity` events with source and confidence, e.g., sensor versus operator entry.
- Explicit `WaitForToolStart` and `WaitForToolEnd` events.
- Explicit `WaitForBatchStart` and `WaitForBatchEnd` events.
- Explicit `WaitForLotReleaseStart` and `WaitForLotReleaseEnd` events.
- Tool state events: `FixtureAcquire`, `FixtureRelease`, `CalibrateStart`, `CalibrateEnd`, `CleanStart`, `CleanEnd`, with quantity and reason.
- Batch policy events: `BatchFormed`, `BatchCutoff`, `BatchStarted`, `BatchCompleted`, with the policy reason.
- Lot status events: `QuarantineStart`, `InspectionResult`, `ReleaseApproved`, `OverrideAuthorized`, with actor and reason.
- Shipment events: `PackedAt`, `LoadedAt`, `ScheduledDeparture`, `ActualDeparture`, `CustomerDeliveryWindow`.
- Resource availability events: `OperatorShiftStart`, `OperatorShiftEnd`, `PreventiveMaintenance`, `SetupTime`.
- Component movement events with serial numbers: `MaterialMovedFromStoreToMachine`, `MaterialConsumed`, `QuantityRemaining`.
- Process sensor data: oven temperature profile, test parameters, and calibration drift values.
- A simulation log from any planned intervention, so intervention effects can be compared against baseline OCEL objects.
