### 1. Delay-decomposition definitions

Let $c$ represent the case index and $i \in \{A, B, C\}$ represent the branch index. 

**Component Definitions:**
- **Upstream Elapsed Time:** The time from case arrival to when the parallel branches are allowed to begin. 
  $\text{Upstream}_c = \text{fork\_release}_c - \text{arrival}_c$
- **Branch Queue Waiting ($i_{queue}$):** The time a specific branch waits at the fork before its work actually begins.
  $i_{queue, c} = i_{start, c} - \text{fork\_release}_c$
- **Branch Active Service ($i_{service}$):** The actual processing time for branch $i$.
  $i_{service, c} = i_{end, c} - i_{start, c}$
- **Join Ready:** The earliest time the final step $F$ is allowed to start. Under the stated rules, this is when the *last* branch completes.
  $\text{join\_ready}_c = \max(A_{end, c}, B_{end, c}, C_{end, c})$
- **Critical Branch:** The branch that determines the join-ready time. Deterministically, ties are broken alphabetically ($A > B > C$).
  $\text{critical\_branch}_c = \text{ArgMax}_{i \in \{A, B, C\}} (i_{end, c})$
- **Branch Synchronization Waiting ($i_{sync}$):** The time a completed branch $i$ waits for the other branches to finish.
  $i_{sync, c} = \text{join\_ready}_c - i_{end, c}$
- **Downstream Queue Waiting:** The time the case waits between all branches finishing and the final station starting.
  $\text{downstream\_queue}_c = \text{final\_start}_c - \text{join\_ready}_c$
- **Final Service:** The active processing time at the final station.
  $\text{final\_service}_c = \text{final\_end}_c - \text{final\_start}_c$
- **Total Case Flow Time:** The end-to-end elapsed time.
  $\text{total\_flow}_c = \text{final\_end}_c - \text{arrival}_c$

**Why summing all branch synchronization waits double counts elapsed time:**
If we were to sum $A_{sync} + B_{sync} + C_{sync}$ for a case, we would be adding overlapping segments of time. For instance, if Branch C finishes first, followed by Branch A, and finally Branch B (the critical branch), the physical elapsed time spent waiting for synchronization is exactly $\text{join\_ready} - C_{end}$. However, summing the waits would count this span once for Branch C, and a portion of it again for Branch A. Therefore, elapsed synchronization time is represented solely by the synchronization wait of the non-critical branches, but physically, the total elapsed time in the parallel stage is entirely driven by the $(queue + service)$ of the **critical branch**.

    *   C: start 10:45, end 11:03 $\rightarrow$ Queue=5, Service=18.
    *   Join Ready: $\max(11:30, 11:20, 11:03) = 11:30$ (50 min elapsed from fork_release). Critical Branch = A.
    *   Downstream Queue: 11:50 - 11:30 = 20 min.
    *   Final Service: 12:10 - 11:50 = 20 min.
    *   Total Flow: 12:10 - 10:20 = 110 min.

### 3. Aggregate critical-path analysis

**Branch Comparison Table:**
| Metric | Branch A | Branch B | Branch C |
|---|---|---|---|
| **Mean Service Time (min)** | 50.0 | 37.5 | 20.3 |
| **Mean Queue Delay (min)** | 0.0 | 19.2 | 10.0 |
| **Mean Queue + Service (min)** | 50.0 | 56.7 | 30.3 |
| **Critical-Branch Frequency** | 2 / 12 (16.7%) | 8 / 12 (66.7%) | 2 / 12 (16.7%) |
| **Mean Synchronization Wait (min)**| 16.3 | 0.0 | 33.1 |

**Reasoned Influence Ranking:**
1.  **Branch B (Strongest Influence):** Although Branch A has the longest active service time, Branch B has the highest critical-path frequency (66.7%). This is driven by Branch B's high queue delay and service time variance. Branch B's queue+service average (56.7 mins) consistently dominates Branch A's flat 50 minutes.
2.  **Downstream Queueing (Masking Influence):** The downstream queue averages ~15.8 minutes across all cases. Even if we optimize Branch B, this downstream congestion acts as a buffer. It limits the observable flow-time benefit of branch improvements because cases will still queue at the final station. 
3.  **Branch A (Secondary Influence):** With a consistent 50-minute service and zero queue time, Branch A is reliably the second-longest branch. It is the critical branch only when Branch B avoids long queues. 
4.  **Branch C (Minor Influence):** Primarily administrative and fast (20 mins average service). It only dictates the critical path when queues on A and B are minimized and its own queue is abnormally high (like F04).

### 4. Counterfactual redesign analysis

**Counterfactual 1: Reducing Branch A service time by 20%**
*   *Direct Benefit:* Branch A service drops to 40 minutes. 
*   *Affected Cases:* F01 and F11 see their `join_ready` time decrease by 10 minutes, directly shortening total flow time (assuming downstream queue doesn't expand).
*   *Zero-Benefit Cases:* For the 8 cases where Branch B is critical, and the 2 where Branch C is critical, Branch A's reduction provides exactly zero benefit. It only increases A's synchronization wait.

**Counterfactual 2: Reducing Branch B queue delay by 50%**
*   *Direct Benefit:* Branch B's average queue drops from 19.2 to 9.6 minutes. 
*   *Affected Cases:* For the 8 cases where B is critical, `join_ready` occurs earlier. For example, F07's flow time would drop by 15 minutes (queue reduced from 30 to 15), and F12 by 17.5 minutes. This directly attacks the primary bottleneck.
*   *Secondary Effects:* If B finishes earlier, it might change the critical branch for cases like F01 or F11, forcing A to become the sole critical path more frequently.

**Counterfactual 3: Adding Final-Station Capacity (Eliminating Downstream Queue)**
*   *Direct Benefit:* If F1 and F2 can absorb work instantly (reducing downstream queue to 0), *all 12 cases* would see an immediate, direct reduction in total flow time (averaging ~15.8 mins per case).
*   *Zero-Benefit Cases:* None. Every case currently experiences downstream queueing. 
*   *Secondary Effects:* By removing the downstream buffer, upstream synchronization delays (B's queue and service) become the absolute dominant factor in total flow time visibility.

### 5. Recommended redesigns and risks

**Redesign 1: Downstream Workload Balancing / Final Station Capacity Expansion**
*   *Recommendation:* Add a third resource (F3) to the final station or cross-train upstream branch workers to assist with F when backlogs occur.
*   *Throughput & Tail:* Throughput will increase as the "exit valve" of the process widens. The flow-time tail (currently 140 mins in F12) will sharply decrease. 
*   *Risks & Measurements:* You risk over-staffing the F station if upstream branches experience delays (leaving F workers idle). Pilot this by measuring F-resource utilization rate vs. `downstream_queue` length. If F is idle 40% of the time while a downstream queue exists, the bottleneck is release-policy based, not capacity based.

**Redesign 2: Dedicated Scheduling for Branch B (B Queue Elimination)**
*   *Recommendation:* Introduce a dedicated queue-priority or reserved resource window for Branch B immediately at `fork_release` to eliminate its 19.2-minute average queue delay.
*   *Throughput & Tail:* Because B dictates 66.7% of the critical path, this will aggressively reduce the upstream-to-join time. Flow time tail will improve significantly.
*   *New Bottlenecks & Risks:* If Branch B begins processing immediately at `fork_release` (0 queue), Branch A (with its 50-minute static duration) will become the new critical path for a significant number of cases. The bottleneck will cleanly shift from B's queue to A's active service time. Measure if solving B's queue causes unintended resource contention for the physical machines used in Branch A.

### 7. Limits of inference

While the data is highly granular (accurate to the minute), there are critical structural limitations to what can be inferred:
1.  **Causality of Delays:** We can observe that Branch B has high queue delays, but we cannot infer *why*. Is Branch B waiting for a shared upstream preparation resource, a specific skilled technician, or machine availability? 
2.  **Branch Resource Capacity:** We do not know if Branches A, B, and C have single or multiple parallel resources. If Branch B has a queue but Branch A does not, it could imply Branch B has a capacity of 1, while Branch A might have multiple machines running simultaneously (which would explain why A never queues).
3.  **Work Preemption:** The timestamps show start and end times. If a machine broke down in Branch B, we cannot distinguish if the 45-minute service time was active work or included an equipment downtime pause that wasn't logged.
4.  **Final-Station Waiting Semantics:** The downstream queue averages 15-20 minutes. We cannot prove this is purely a capacity bottleneck (F1/F2 being busy). It could be a *release policy* (e.g., a rule that states "F batches cases and only reviews them on the hour"), which would look identical in timestamp data but behave completely differently under redesign.
