 ## 9. Failure modes and safeguards

 We list at least eight failure modes:

  1. Collapsing distinct partial payments (e13 and e14) into one event because they share the same activity, timestamp, and some objects (O1, V1). Safeguard: check the payment objects (M1 and M2) and do not merge if they are different.

  4. Treating shared objects as proof of duplication (e.g., e03 and e05 share O1 and P1, but they are different items). Safeguard: check all objects and their types.

  5. Unioning incompatible E2O relations (e.g., e06 has I1 and I2, e07 only O1 and P1; if we merge, we might lose the item-level detail). Safeguard: when merging, combine the relations (e.g., keep all objects from both events).

## 1. Duplicate-handling Decision Tree

**Root Decision:** Examine candidate pair(s)

### Exact Technical Duplicate
- **Criteria:** Same `source`, `source_event_key`, `timestamp`, `activity`, `payload_hash`, and identical `related_objects`.  
- **Action:** Drop one instance.  
- **Provenance:** Record dropped ID with reference to retained instance.

### Same Physical Event (Multiple Observations)
- **Criteria:** Different sources, same `timestamp`, same `activity`, same core objects, and domain evidence (e.g., reconciliation report, later correction) confirms a single real-world occurrence.  
- **Action:** Merge attributes and relations. Keep the event with richest attributes as canonical; absorb others.  
- **Provenance:** Record all source IDs and attribute origins.

### Summary Event Derived from Detailed Event
- **Criteria:** Different sources, one is a high-level status update triggered by the other (e.g., ERP “Pack Package” from WMS message), fewer objects, fewer attributes.  
- **Action – Conservative:** Retain both; mark summary with qualifier (e.g., `activity = "Pack Package (Summary)"`).  
- **Action – Aggressive:** Drop summary if detailed event exists.  
- **Provenance:** Record derivation link.

### Harmonization Collision (Semantically Distinct Activities)
- **Criteria:** Same harmonized `activity` label, different `source` meanings (e.g., “Dispatch Package” in WMS vs. carrier acceptance).  
- **Action:** Retain both; refine label with source qualifier (e.g., `activity = "Dispatch Package (WMS)"`).  
- **Provenance:** Store original source activity.

### Concurrent Same-Label Events Involving Different Objects
- **Criteria:** Same `activity`, same `timestamp`, but distinct object sets (e.g., picking item I1 vs. I2).  
- **Action:** Retain both unchanged.  
- **Provenance:** Record independence.

### Unresolved Candidate
- **Criteria:** None of the above, ambiguous evidence.  
- **Action:** Quarantine for review.  
- **Provenance:** Flag with confidence score and reason.

## 3. Timestamp-tie Ordering Rules

**Deterministic Total Order Policy (for ties only):**

1. **Domain constraints** (semantic): Enforce known business sequences (e.g., authorization before capture, acceptance before handover).
2. **Within-source sequence** (semantic): For events from the same source, use `source_seq` (e.g., e12e13e14 from PSP).
3. **Lifecycle constraints on shared objects** (semantic): Order by object state progression (e.g., pick before pack, dispatch before handover).
4. **Source-specific semantics** (semantic): Source hierarchy (WMS before ERP for same business transition; carrier events after warehouse events).
5. **Ingestion time** (deterministic): Use `ingested_at` only if above rules fail. This is not business time.
6. **Stable fallback order** (deterministic): Break remaining ties by sorting on `(source, source_event_key, eid)`.

**Why synthetic microseconds are dangerous:** Adding microsecond offsets to timestamps encodes a false narrative of sequence and duration, potentially violating domain constraints (e.g., making a summary appear after a detailed event by microseconds) and creating artificial rework loops in process mining.

## 9. Failure Modes and Safeguards

1. **Collapsing distinct partial payments:** Merging e13 and e14 because they share O1, V1. *Safeguard:* Check for distinct Payment objects (M1, M2); require object-level identity, not just common objects.

2. **Converting abstraction updates into false rework:** Keeping e15 as a separate step creates InvoicePaymentSummaryInvoice loop. *Safeguard:* Qualify summary activities; optionally remove from main DFG.

3. **Ordering by ingestion time:** Using `ingested_at` as primary order may reverse business sequence (e09 ingested after e10 but occurs before). *Safeguard:* Domain constraints first; ingestion time only as last resort.

4. **Treating shared objects as duplication proof:** e03 and e05 share O1, P1 but are distinct picks. *Safeguard:* Require identical object sets, not just common subsets.

5. **Unioning incompatible E2O relations:** Merging e06 (O1,I1,I2,P1) and e07 (O1,P1) may incorrectly add items to ERP summary. *Safeguard:* Keep relations separate; mark source of each relation.

6. **Changing durations via synthetic microseconds:** Adding 0.001s to e08 and 0.002s to e09 creates false 0.001s duration. *Safeguard:* Never modify original timestamps; use deterministic order column.

7. **Losing source-authoritative attributes:** Discarding WMS location from e04 during merge. *Safeguard:* Keep all attributes with provenance; use attribute flags.

8. **Applying duplicate functions to whole OCEL:** `pm4py.ocel_merge_duplicates` on raw OCEL would merge e03/e05, e13/e14. *Safeguard:* Always inspect candidate groups first; use custom merge logic for verified pairs only.

**General Safeguard:** Implement a two-phase process: (1) Candidate group identification with human-in-the-loop for ambiguous cases; (2) Application of scenario-specific rules with full provenance logging.
