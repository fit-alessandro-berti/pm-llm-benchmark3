# 1. Mechanism map

| Restructuring action | Causal mechanism | Expected process-mining effect | Primary PM observables |
|---|---|---|---|
| Merge N/S/E Tech into Technical Shared Service | Removes local specialist loops; creates single inbound queue | **Nominal handover reduction** in local tech loops; **central queue formation** on shared tech | `discover_handover_of_work_network`:  local caseworkerembedded tech edges;  edges into shared tech pool;  median wait on those edges |
| Route all high-complexity + specialty cases to shared queues | Concentrates hard work centrally; increases specialist load breadth | **Specialist utilization** ; wait time variance ; possible hidden multitasking | Resource occupancy / busy time; `get_service_time`; waiting time after handover to shared queues |
| Shared advice pull-back to local caseworkers | Replaces synchronous local loops with async queue returns | More “subcontracting” pattern; longer caseworker idle-on-case waits | `discover_subcontracting_network`; `insert_case_service_waiting_time` |
| Shared approval queue; remove one local supervisor | Standardizes gates; thins local authority | **Role clarity**  (ownership ambiguity); approval batching; possible ping-pong | Role discovery instability;  reassignment_count; handover reason = “approval/escalation” |
| Keep intake & simple eligibility local | Preserves front-door locality | Stable early path; divergence after eligibility | DFG prefix stability; variant split after eligibility |
| Broader legal/risk detection rules | More cases enter scarce queues already at ~90%+ util | Queue explosion on Legal/Risk; **rework** if rushed or incomplete advice | Filter `required_specialty`; wait tails; rework_flag after specialist return |
| Loss of embedded tech presence | Less informal pre-triage; weaker regional conventions | **Local expertise loss**  more avoidable referrals; notes quality drift; **learning** atrophy |  referral rate from locals;  rework on complex/local-convention cases;  `local_expertise_flag` correlation with good outcomes |
| Cross-team cover formally reduced but central pool is “everyone’s” | Single queue is resilient to one person absent but fragile to pool overload | **Resilience to absence**: better for single-resource failure, worse for correlated demand spikes | Working-together network density; absence-period cycle-time sensitivity |
| Uniform routing rules across North/South/East | East unloaded; North/South lose advantage | **Fairness across teams/segments**: East cycle times may improve; North/South and language/regional segments may worsen | Segmented cycle time, SLA miss, satisfaction proxy by `team`, `customer_segment`, `location` |

**Mechanism chains (condensed):**

1. **Nominal handover   wait **  
   Local bidirectional tech loops (caseworkerN/S/E_Tech) shrink, but each remaining specialist edge lands on a deeper central queue  median/p90 wait after specialist handover can rise even if edge count falls.

2. **Utilization   multiskill congestion**  
   Shared tech also absorbs legal/risk triage and hard QC  utilization target (+15%) collides with already-high Legal/Risk util  priority inversion and complexity-based delay.

3. **Expertise depreciation  rework lag**  
   Early informal advice disappears  more cases enter specialist path incorrectly or incompletely  rework and repeat specialist visits appear weeks later, not in week-1 averages.

4. **Standardization  accountability diffusion**  
   Shared approval and shared tech mean `org:resource` on key decisions rotates  role discovery shows blurred roles; `handover_reason` and `reassignment_count` rise when ownership is unclear.

5. **Heterogeneous team baselines**  
   East (overloaded E_Tech, worse tails) has more headroom to benefit; North/South risk net loss of local speed and knowledge. Fairness is a cross-team and cross-segment distributional effect, not a global mean.

# 4. Risks invisible in average cycle time

1. **Tail latency (p90/p95) inflation**  
   Averages improve because high-volume simple cases go through a thinner local path, while a minority sits in Tech SS + Legal/Risk + approval convoys. Global mean/median can fall while the worst decile doubles.

2. **High-complexity case regression**  
   Routing “all high-complexity to SS” increases queue time exactly where local embedded tech previously retained context (table: local tech wait 3.2h with knowledge retained). Complexity-stratified DFG performance worsens while aggregate improves.

3. **Local knowledge loss and silent quality decay**  
   Regional conventions (especially North/South strength) are not columns that move average CT quickly. Rework and outcome degrade with lag as `local_expertise_flag` cases lose the people who understood them. Notes inconsistency (already a cross-team failure mode) becomes the default interface to SS.

4. **Fairness across teams and customer segments**  
   East may show large CT gains (E_Tech was at 82% util), pulling the portfolio average down, while North/South and language/regional segments absorb more handovers and lower satisfaction. Segment gaps are orthogonal to the mean.

5. **Learning and skill atrophy**  
   Locals stop seeing hard technical work  long-term capacity shrinks  future over-dependence on SS. Not visible in CT until SS capacity shocks. Activity-based resource similarity would show locals drifting away from tech-like profiles.

6. **Accountability and role diffusion**  
   Shared approval + shared tech  unclear owner during waits. Customers experience silence; internally `reassignment_count` and ping-pong rise. Average CT unchanged if work eventually completes, but experience and auditability worsen.

7. **Exception and absence fragility (false resilience)**  
   Cross-team ad hoc handovers drop (looks good), yet the central pool is a single point of congestion. Correlated absence, tooling outage, or demand spike stalls many teams at once—worse systemic risk than localized East overload.

8. **Priority inversion and “measured utilization” gaming**  
   +15% specialist utilization can mean specialists are busier on triage/QC/admin, not higher-value deep work. Utilization  with worse outcomes is invisible if leadership only watches CT and util dashboards.

9. **Rework displaced in time and location**  
   Defects introduced in central decisions surface at Implementation/QC/Rework or after Close. Attribution to the restructuring is missed if only end-to-end average CT is reported in the first month.

# 5. Pilot design

**Pilot scope**  
- Phase A (6–8 weeks): Centralize **Technical Shared Service** for **East + 50% of South** high-complexity and specialty-routed cases only. North remains embedded (control-like). Shared approval **not** fully live—or live only for medium-value East cases.  
- Phase B (only if guardrails pass): Extend Tech SS to North; then pilot shared approval queue; only then broaden legal/risk detection rules.

**Comparison group**  
- **Control:** North embedded model (as-is).  
- **Partial treatment:** South half-volume or stratified random case routing if ethically/operationally feasible.  
- **Full treatment in pilot:** East (expected beneficiary).  
- Compare difference-in-differences: East vs North, treated South vs North, controlling for `case_complexity`, `customer_segment`, `priority`, volume seasonality.

**Pre/post observation window**  
- **Pre:** 8–12 weeks stable baseline (same seasonality window if possible).  
- **Post pilot Phase A:** 6–8 weeks steady state after 2-week transition (exclude transition from primary stats but analyze separately).  
- Match calendar effects; freeze unrelated process changes.

**Segmentation**  
Always report metrics cut by:  
- `team` (North/South/East)  
- `case_complexity`  
- `required_specialty`  
- `customer_segment` and `location`  
- `priority`  
- `local_expertise_flag`  

**Guardrail metrics (hard)**  
- p90 wait after handover to Tech SS  agreed cap (e.g., 1.25× management 4.0h median target implies explicit p90 budget, not only median).  
- p90 cycle time for high-complexity cases not worse than baseline by >X% (pre-set).  
- Rework_flag rate post-SS return not  >Y pp.  
- SLA miss gap across teams/segments not widen beyond threshold.  
- Legal/Risk util not sustained >92–95%.  
- reassignment_count and wrong-queue handovers bounded.  
- No decline beyond threshold in outcome/CSAT for regional segments.

**Staff feedback collection**  
- Weekly 5-question pulse: ownership clarity, time-to-informal-help, queue transparency, skill use, customer awkwardness.  
- Shadowing sample of complex cases (qual notes linked to case IDs).  
- Specialist workload diary (tech vs triage vs QC share).

**Rollback / adjustment triggers**  
- Two consecutive weeks breach on any hard guardrail.  
- Single-week extreme: SS p95 wait or systemic stall under normal volume.  
- Fairness trigger: North/South or named customer_segment SLA/CSAT gap widens beyond bound.  
- Adjustment before full rollback: tighten routing (only true high-complexity), add tier-0 local tech office hours, cap Legal/Risk auto-detect, name case owner during SS wait, staff SS up, delay shared approval merger.  
- Full rollback: restore embedded tech to North/South (and East if adverse) if adjustments fail within 2 weeks.

# 6. Recommendation

**Pilot first (phased), do not full-rollout; modify the design before Phase B.**

**Why not reject:** East’s overload (E_Tech 82%, worse CT/rework/SLA) is a real structural problem; scarce Legal/Risk and inconsistent cross-team cover are real. Centralization can help **East** and scarce-specialty consistency if capacity and ownership are designed explicitly.

**Why not proceed as proposed:** The plan simultaneously (a) merges all local tech, (b) loads SS with QC and triage, (c) broadens legal/risk intake, (d) removes a supervisor into a shared approval queue. That stacks **central queue formation**, **role ambiguity**, and **expertise depreciation** on top of already saturated Legal/Risk. Management’s table shows higher waits on almost every specialist/approval edge while advertising “fewer handovers” and “+15% util”—a classic nominal-handover vs. real-delay confusion. North/South start from positions of strength; portfolio averages will hide their losses if East improves.

**Required modifications before/during pilot:**  
1. Staff the shared pool for **queue tails**, not mean utilization targets; treat 15% util  as a risk indicator near saturation, not a success KPI.  
2. Preserve **named case owner** and local customer contact during SS waits; do not remove supervisor capacity until approval queue SLAs are proven.  
3. Keep **tier-0 local technical access** (office hours / rotating embed) to protect informal triage and learning.  
4. Stage **legal/risk detection broadening** only after Tech SS stabilizes.  
5. Publish **segmented** dashboards (complexity × team × segment), not portfolio CT.  
6. Explicit knowledge artifacts (templates, local convention checklists) as entry criteria to SS.

**What management should *not* infer from early averages:**  
- Falling average/median cycle time  success (easy-case mix or East relief can dominate).  
- Fewer local handover edges  less waiting or better coordination.  
- Higher specialist utilization  healthy capacity (may be QC/triage congestion).  
- Lower cross-team handover count  higher resilience.  
- Short-window stable rework  preserved local expertise or fair outcomes.  
Early “green” means only: proceed to the next pilot gate if **guardrails on tails, segments, rework-after-SS, ownership, and Legal/Risk util** are also green.

    }

# Difference-in-differences style: East (treatment) vs North (control)
east = compare_segment(team=["East"])

# Fairness snapshot: p90 cycle and rework by team x customer_segment pre vs post
# Resilience: filter periods with known absence of SS staff; recompute hw and cycle tails
# Learning: over months, activity footprint of local caseworkers on technical activities
#            via discover_activity_based_resource_similarity on rolling windows

# Guardrail evaluation pseudocode
def guardrails(kpi_pre, kpi_post, hw_post, ss_names, thresholds):
    p90_high_pre = kpi_pre.query("case_complexity == 'high'")["cycle_days"].quantile(0.9)
    p90_high_post = kpi_post.query("case_complexity == 'high'")["cycle_days"].quantile(0.9)
    ss_waits = hw_post[hw_post["to_res"].isin(ss_names)]["wait_h"]
    checks = {
        "high_complexity_p90_regression": p90_high_post <= p90_high_pre * thresholds["max_p90_ratio"],
        "ss_wait_p90": ss_waits.quantile(0.9) <= thresholds["ss_p90_h"],
        "rework_delta": (
            kpi_post["rework_flag"].mean() - kpi_pre["rework_flag"].mean()
        ) <= thresholds["max_rework_pp"],
        # add segmented SLA gap checks...
    }
    return checks

**How to read the sketch in governance terms**  
- Use **handover / subcontracting networks** for nominal vs real centralization.  
- Use **handover wait p50/p90 by edge and segment** for queue formation.  
- Use **roles + resource similarity + reassignment_count** for role clarity and learning.  
- Use **variant/DFG performance stratified by East vs North/South and complexity** for fairness and tail risk.  
- Use **rework-after-SS and outcomes** as lagging quality.
