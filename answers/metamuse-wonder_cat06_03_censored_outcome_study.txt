## 1. Target definition

**Primary target: multi-state competing outcome for all applications still in process at an early prediction landmark.**

- **Unit of analysis:** One application-case at one prediction landmark; one row per case for the primary analysis.
- **Prediction time, $t_{pred}$:** Timestamp of the first completed `Credit Review` event, provided this is within the first five events and the case has not already reached `Accepted`, `Rejected`, `Withdrawn`, or `Transferred`. This is operationally early — documents may have been requested, but no final decision, contract, or activation has occurred — and is more process-meaningful than an arbitrary wall-clock point alone. Sensitivity landmarks are defined in Section 4.
- **Population:** All applications started 1 Jan 2024–31 Dec 2025 that reach $t_{pred}$ still open, regardless of eventual disposition. This is the population the lender actually wants to score.
- **Follow-up and horizon:** From $t_{pred}$ until the earliest of: (i) a terminal non-activation outcome (`Rejected`, `Withdrawn`, `Transferred`); (ii) `Account Activated` + 90 days, plus up to 35 days for the outcome feed to arrive; (iii) data extraction, 15 Feb 2026 (censoring). Because activation time varies, the default component is anchored to activation, not to application start.
- **Outcome $Y$ (mutually exclusive states):**
  1. `not_activated_rejected`
  2. `not_activated_withdrawn`
  3. `transferred` (treated as a competing state in the primary analysis; see Section 3)
  4. `activated_default_90d` — activated and default within 90 days of activation
  5. `activated_no_default_90d` — activated and no default within 90 days of activation
  6. `censored` — still open, or activated but horizon/feed not yet mature at extraction (not a class to predict; handled by censoring machinery)
- **Estimand:** $P(Y = j \mid X(t_{pred}), \text{still open at } t_{pred}, \text{observed policy regime})$, for each state $j$, where $X(t_{pred})$ uses only information available at $t_{pred}$. Two derived quantities are reported: the **joint** early-warning probability $P(\text{activated and default} \mid X(t_{pred}))$, which is defined for every scored application, and the **conditional** $P(\text{default} \mid \text{activated}, X(t_{pred})) = P(\text{activated\_default}) / [P(\text{activated\_default}) + P(\text{activated\_no\_default})]$, clearly labelled as conditional on an event (activation) that occurs after prediction.

**Why this is defensible.** It never requires inventing a default outcome for a rejected or withdrawn applicant who was never exposed to credit. Every scored case has a well-defined observable (or censorable) outcome under the policy actually in force. It also decomposes the lender's question honestly: a low joint default probability can arise because default risk is low *or because activation is unlikely* — conflating the two is exactly the error in the informal request.

**Alternative targets answering different questions.**

- *Conditional default among activated accounts* ($P(\text{default}_{90d} \mid \text{activated}, X)$): appropriate for provisioning and pricing *of the activated book*, and as a secondary model trained on the 21,600 mature activated cases. It cannot be applied to "every application" without the activation model, and it is subject to selection (collider) bias if interpreted as applicant risk.
- *Time-to-default after activation with right censoring:* a survival target landmarked at activation. Statistically efficient for the activated portfolio, but the landmark is after the early-warning point, so it does not answer the business question.
- *Policy-specific counterfactual* $P(\text{default}_{90d} \text{ if activated under policy } \pi)$: this is what "default for every application" literally asks for. It requires untestable assumptions (Section 3) and is reported, if at all, only as a clearly-flagged sensitivity quantity, never as the headline.

## 2. Cohort construction

**Inclusion rules (all as of extraction, 15 Feb 2026):**

- Application started between 1 Jan 2024 and 31 Dec 2025, with a valid case ID and at least `Application Started`, `Identity/KYC Check`, and a first `Credit Review` event.
- Case reaches $t_{pred}$ still open (no terminal event at or before $t_{pred}$).
- Events deduplicated and activity names harmonised (Section 4) before eligibility is assessed.

**Exclusion / handling rules:**

- Cases terminating before $t_{pred}$ (e.g., rejected at first review before the landmark is defined, immediate withdrawals) are **not scored** by this model; they are counted and reported, since silently dropping them would bias the scored population toward longer cases. If the business needs a score for them, a separate earlier landmark (e.g., after KYC) is required.
- Cases with impossible timestamps (events after `data_extract_time`, negative durations) are quarantined and counted, not silently repaired.
- A label is only assigned when **mature**: activation date + 90 days + 35 days (maximum feed delay)  15 Feb 2026, i.e. activation on or before approximately 13 Oct 2025, *and* `label_available_at`  extraction. Activated cases failing this are censored, not negative.
- Transferred cases with a linkage-table match (~60%) are followed on the receiving platform where the outcome is observable; unlinked transfers remain a competing state / missing-follow-up category, never non-default.

**Cohort flow (all 48,000 applications started):**

| Category | n | Status in primary analysis |
|---|---:|---|
| Activated, 90-day outcome mature: non-default | 18,900 | Labelled `activated_no_default_90d` |
| Activated, 90-day outcome mature: default | 2,700 | Labelled `activated_default_90d` |
| **Subtotal: current labelled ML export** | **21,600** | Labelled |
| Rejected | 9,100 | Competing outcome (not non-default) |
| Withdrawn | 5,700 | Competing outcome (not non-default) |
| Transferred | 2,900 | Competing outcome; ~60% linkable for follow-up sensitivity |
| Still open at extraction | 5,100 | Right-censored at 15 Feb 2026 |
| Activated, outcome/feed not yet mature | 3,600 | Censored (delayed label), not negative |
| **Total** | **48,000** | |

Within each row, the landmark-eligibility filter (reached first `Credit Review` still open) and the pre-/post-1 Jul 2025 policy split are applied and reported as sub-counts by the pipeline; these sub-counts are computed from data, not assumed. Note the labelled export prevalence of default (2,700/21,600 = 12.5%) is a prevalence *among mature activated accounts only* and must never be quoted as application-level default risk.

## 3. Censoring and missing-label strategy

**Distinct mechanisms:**

- **Ordinary right censoring:** Still-open cases (5,100) and cases whose post-prediction follow-up is cut by extraction. Censoring time is known; the outcome would eventually be observable in principle.
- **Delayed labels:** The 3,600 activated-but-immature accounts, plus mature-window cases whose feed (7–35 days late) has not arrived. These are censored at extraction with a known maturity date; treating them as non-default would bias risk downward, increasingly so near the extraction date and after the policy change.
- **Selection through activation:** `default_90d` exists only conditional on activation, which depends on the same prefix features used for prediction. This is not ordinary censoring: for rejected/withdrawn cases the outcome is *undefined under the observed policy*, not merely unobserved. No reweighting of the 21,600 can fix this without counterfactual assumptions.
- **Transfer:** A competing event that removes the case from observation; for ~40% without linkage it is also a missing-follow-up mechanism, plausibly informative (transfers may be systematically riskier or safer).
- **Permanently missing outcome feeds:** Especially partner-originated activated accounts. If feed missingness depends on the outcome itself (MNAR), no observed-data method identifies the risk without extra assumptions.

**Primary strategy:** Fit a discrete-time competing-risk / multi-state model (equivalently a multinomial landmark model with inverse-probability-of-censoring weights for still-open and immature cases), estimating state probabilities as in Section 1. Censoring weights are modelled on observed covariates (start date, channel, region, source system, prefix features). Transferred cases are a competing state in the primary analysis. The conditional activated-only default model on the 21,600 mature cases is fitted as a clearly-labelled secondary analysis.

**Sensitivity analyses (at least):**

1. **Linked-transfer follow-up:** Re-run including the ~60% linked transfers with their downstream outcomes; compare state probabilities. Follow with a tipping-point / pattern-mixture analysis for unlinked transfers, varying their assumed default rate from 0.5× to 2× the activated rate.
2. **Missing-feed bounds:** For partner-originated accounts with permanently missing feeds, report best/worst-case bounds and a delta-adjustment sensitivity rather than a single point estimate.
3. **IPCW vs. complete-case** comparison for delayed labels, and a pre/post-policy-change refit.

**Testability of assumptions:**

- *Partially testable:* whether censoring/feed-missingness depends on **observed** covariates (compare covariate distributions by maturity, feed presence, source system); overlap/positivity for censoring weights; linkage-match rates by subgroup.
- *Testable in aggregate:* calibration of predicted vs. Aalen–Johansen non-parametric state probabilities within strata.
- *Fundamentally untestable from these data:* default risk of never-activated applicants (the counterfactual); independence of censoring given **unobserved** factors; MNAR feed missingness depending on the unseen outcome. Any claim requiring these must be presented as assumption-dependent.

## 4. Prefix extraction

- **Fixed event-count prefixes:** $k \in \{2, 3, 5\}$ events, plus the process landmark "first `Credit Review` completed" as primary. A case contributes a prefix only if its $k$-th event exists and no terminal event occurs at or before it; the prefix timestamp is the timestamp of the $k$-th event, and only events with timestamp  $t_{pred}$ are used.
- **Elapsed-time prefixes:** 24h, 72h, and 7 days after `Application Started`, including all events with timestamp  start + horizon, requiring the case to still be open at that time (landmark condition). Cases already terminal are excluded from that landmark's risk set and counted.
- **Short cases:** Cases ending before a given prefix length are not padded, truncated-and-labelled, or carried forward; they are simply out of scope for that landmark. Prefix-length-specific cohorts and counts are reported so the changing risk set is transparent.
- **Repeated document loops:** Loops are retained, not collapsed. Loop count, number of document requests, and time per loop become features (Section 5); prefixes are cut by event position, so a case mid-loop at $k$ events is represented faithfully.
- **Activity renaming (15 Oct 2025 migration):** A documented, version-controlled mapping from post-migration names to the pre-migration canonical vocabulary is applied *before* prefixing, validated with process owners, and the mapping table is stored with the run. Unmapped activities are flagged and counted, never silently dropped.
- **Duplicates:** Exact duplicates on (case, activity, timestamp, resource, source system) created by the migration are removed with an audit count; near-duplicates (same case/activity, timestamps within seconds) are flagged for manual review rather than auto-deleted, since legitimate rapid repeats exist in document loops.
- **No future leakage in construction:** Prefix logs are physically truncated event logs; feature extraction code receives only the prefix log, never the full log (enforced in Section 9).

## 5. Process-aware features

**Static case attributes (known at start, valid at $t_{pred}$):** `case:channel`, `case:region`, `case:requested_amount`, source system, partner-originated flag, application start month.

**Prefix-derived features (computed only from events  $t_{pred}$):**

- *Control-flow:* prefix variant / last activity; whether document request occurred; number of distinct activities; direct-follows indicators from the prefix (e.g., `Credit Review -> Documents Requested`); position of first `Credit Review`.
- *Timing:* elapsed time start  $t_{pred}$; inter-event durations; waiting vs. service time within the prefix; time spent in document loops; calendar features of $t_{pred}$ (hour, weekday) and policy-regime indicator (pre/post 1 Jul 2025) — regime is known at prediction time and must be a feature, not a nuisance.
- *Resource/queue:* handler's case load *at $t_{pred}$* (count of concurrently open cases for that resource, computed point-in-time); number of distinct resources so far; handover count.
- *Rework:* document-request loop count, repeated KYC events, repeated `risk_score` revisions within prefix.

**Features requiring historical reference data (must be built point-in-time):** resource experience **as of the event time** (reconstructed from HR/history tables, not the extraction-time snapshot); historical approval and default rates by channel/region computed on a trailing window ending before $t_{pred}$; queue-length benchmarks by week. Each such feature needs an "as-of" join keyed on $t_{pred}$; if the as-of version cannot be reconstructed, the feature is dropped rather than approximated with extraction-time values.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision; encodes the decision the model precedes | Available only at/after decision | **Drop** | Post-prediction information; would leak acceptance |
| `decision_reason` | Recorded at/after Accept/Reject; directly reveals disposition | At/after decision event | **Drop** | Target-adjacent; unavailable at $t_{pred}$ by construction |
| `collection_status` | Updated after activation; may directly reveal default | Never before activation + collections activity | **Drop** | Essentially a proxy for the label |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`, terminal events) | Define or reveal the outcome path | Only events  $t_{pred}$ may enter features | **Drop (from features)** | Used only to construct the outcome, never as predictors |
| `documents_total` (nightly snapshot) | Includes documents uploaded later the same calendar day than $t_{pred}$ | Rebuild as cumulative count of document events with timestamp  $t_{pred}$ from the event log | **Repair** | Same-day look-ahead; event-log reconstruction is exactly available at $t_{pred}$ |
| `risk_score` (updated at several events) | Later updates incorporate post-prediction assessment | Use last value with event timestamp  $t_{pred}$; also count of updates within prefix | **Repair** | Point-in-time value is legitimate; final value leaks |
| Resource experience | Stored at extraction time, not event time; seniority accrues and staff churn | Reconstruct experience as of event time from dated records; otherwise drop | **Repair or drop** | Extraction-time value is future information for early cases |
| Label availability (`default_90d`, `label_available_at`) | Label fields on event rows can bleed into feature frames; immature cases masquerade as negatives | Labels joined only after feature freeze, only if activation+90d+35d  extraction and `label_available_at`  extraction; immature = censored | **Repair** | Prevents both direct leakage and delayed-label bias |
| Case attributes repeated on every event row (`case:channel` etc.) | Post-decision overwriting in some source systems could alter "static" fields | Verify stability within case; take value as of first event | **Repair** | Guard against silent restatement |

## 7. Validation design

**Temporal scheme (primary):** Split by **case start time**. Train: starts Jan–Dec 2024. Validation: Jan–Jun 2025 (pre-policy-change, used for tuning and calibration). Test: Jul–Dec 2025 starts (post-policy-change regime), with outcome evaluation restricted to cases whose full follow-up (terminal event, or activation + 90 days + 35 days) is observable by 15 Feb 2026; immature test cases contribute only to censored metrics. This deliberately makes the test set a *regime-shift* test, matching deployment. A second stress slice isolates cases spanning the 15 Oct 2025 migration. Rolling-origin monthly backtests within the training period supplement the single split.

**Why a random case split is misleading:** It mixes pre- and post-policy-change cases in train and test, so the model can learn regime-specific selection patterns and be tested on the same regime — overstating performance after 1 Jul 2025. It places near-identical prefixes from the same calendar period, queue conditions, and migration artefacts on both sides, leaking temporal context. And it ignores that labels for recent cases are systematically immature, so a random split hides the delayed-label bias that dominates real scoring.

**Metrics (matched to the competing-risk target):** Per-state and overall multiclass Brier score and log loss; IPCW-adjusted Brier score at the outcome horizon to handle censoring; calibration plots and calibration-in-the-large/slope per state and for the derived joint default probability, benchmarked against Aalen–Johansen estimates; AUPRC and sensitivity at fixed alert rates for the `activated_default_90d` state (prevalence-sensitive metrics reported with the activated-conditional prevalence stated); decision-curve / net-benefit analysis at lender-relevant alert thresholds. Discrimination alone (AUROC) is reported but never headlined.

**Subgroup and shift diagnostics:** Performance and calibration by channel, region, partner-originated vs. direct, source system, prefix length, and policy regime; population-stability indices on key features and on variant distributions across the migration; explicit reporting of the linkage rate and missing-feed rate per subgroup, since differential missingness can manufacture apparent subgroup gaps.

## 8. Limitations and decision-use boundary

**What the study can claim:** Calibrated probabilities, under the policy regime(s) represented in training, of each observable disposition for applications still open at the landmark, and a decomposition of default risk into activation probability and conditional default-given-activation. It can rank activated accounts by conditional default risk for provisioning support, with uncertainty that widens post-policy-change and post-migration.

**What it cannot claim:** It cannot estimate what a rejected or withdrawn applicant "would have" defaulted at — that quantity is undefined under the observed policy and unidentified without counterfactual assumptions (e.g., selection-on-observables for the activation decision plus positivity, which fails for hard policy cut-offs). Apparent feature effects are predictive associations entangled with selection: e.g., document requests may predict default partly because reviewers request documents from cases they already judge risky. Scores must not be used to auto-reject applicants as "would-be defaulters," nor quoted with the 12.5% activated-book prevalence as if it were application-level risk.

**How deployment changes the data-generating process (at least three):**

1. **Selective-label feedback:** If scores influence acceptance, future labels are generated only for cases the model lets through, entrenching its own selection and making retraining data progressively less representative.
2. **Behavioural adaptation:** Applicants and brokers learn which early signals trigger alerts and adapt document timing or channel choice (Goodhart effects), shifting prefix distributions.
3. **Operational feedback:** Alerts change reviewer behaviour — more document requests, faster escalation — altering loop counts and timings that are themselves features, so the process the model observes is partly created by the model.
4. **Policy interaction:** Threshold or routing changes in response to model output (e.g., transferring high-score cases to partners) change both the competing-event rates and the transfer-linkage missingness the model relies on.

Deployment therefore requires shadow-mode evaluation first, periodic recalibration against matured outcomes, and monitoring of the mechanisms above.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py

# ---- Config: all cutoffs explicit; assumptions marked ASSUMPTION ----
EXTRACT = pd.Timestamp("2026-02-15")
POLICY_CHANGE = pd.Timestamp("2025-07-01")
HORIZON_D, FEED_LAG_D = 90, 35          # ASSUMPTION: 35d = max feed delay
PREFIX_K = 3                            # primary landmark ~= first Credit Review
FORBIDDEN = ["final_limit", "decision_reason", "collection_status",
             "default_90d", "label_available_at"]  # leakage-audit drops

ACT_MAP = {  # ASSUMPTION: validate with process owners (15-Oct-2025 migration)
    "KYC Verification": "Identity/KYC Check", "Credit Assessment": "Credit Review",
    "Doc Request": "Documents Requested", "Sign Contract": "Contract Signed"}

df = pd.read_csv("applications_events.csv",
                 parse_dates=["time:timestamp", "label_available_at",
                              "data_extract_time"])
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)
EXTRACT = EXTRACT.tz_localize("UTC")

# Dedup migration artefacts (audit count kept); harmonise activity names
n_raw = len(df)
df = df.drop_duplicates(subset=["case:concept:name", "concept:name",
                                "time:timestamp", "org:resource", "source_system"])
print(f"duplicates removed: {n_raw - len(df)}")
df["concept:name"] = df["concept:name"].replace(ACT_MAP)
df = df[df["time:timestamp"] <= df["data_extract_time"]]  # nothing post-extract

log = pm4py.format_dataframe(df, case_id="case:concept:name",
                             activity_key="concept:name",
                             timestamp_key="time:timestamp")

# ---- Case-level as-of table: start / activation / terminal / maturity ----
def case_summary(g):
    acts = g["concept:name"]
    ts = g["time:timestamp"]
    act_time = ts[acts == "Account Activated"].min()
    term = g[acts.isin(["Rejected", "Withdrawn", "Transferred"])]
    return pd.Series({
        "start": ts.min(),
        "activation": act_time,
        "terminal_act": term["concept:name"].iloc[0] if len(term) else None,
        "terminal_time": term["time:timestamp"].min() if len(term) else pd.NaT,
        "label_avail": g["label_available_at"].max(),
        "default_90d": g["default_90d"].max()})

cases = df.groupby("case:concept:name").apply(case_summary, include_groups=False)
cases["mature_by"] = cases["activation"] + pd.Timedelta(days=HORIZON_D + FEED_LAG_D)
cases["label_mature"] = (cases["mature_by"] <= EXTRACT) & \
                        (cases["label_avail"] <= EXTRACT)

def outcome(r):  # competing states; censored != non-default
    if pd.notna(r["activation"]):
        if not r["label_mature"]:
            return "censored_immature"
        return "activated_default" if r["default_90d"] == 1 else "activated_no_default"
    if r["terminal_act"] in ("Rejected", "Withdrawn", "Transferred"):
        return r["terminal_act"].lower()
    return "censored_open"

cases["outcome"] = cases.apply(outcome, axis=1)
print(cases["outcome"].value_counts(dropna=False))  # cohort-flow audit (target 48k)

# ---- Temporal split by case START (primary; random split only as baseline) ----
cases["split"] = pd.cut(cases["start"],
    bins=[pd.Timestamp("2024-01-01", tz="UTC"), pd.Timestamp("2025-01-01", tz="UTC"),
          POLICY_CHANGE.tz_localize("UTC"), pd.Timestamp("2026-01-01", tz="UTC")],
    labels=["train", "validation", "test"])  # test = post-policy-change regime
# NOTE: pm4py.split_train_test(log, 0.8) exists but is random -> baseline only.

# ---- Prefixes: truncated logs only; post-prefix data never reaches features ----
prefix_log = pm4py.get_prefixes_from_log(log, PREFIX_K)
# Retain only cases still open at prefix end (no terminal event inside prefix)
term_in_prefix = {(e["case:concept:name"]) for t in prefix_log for e in t
                  if e["concept:name"] in
                  ("Rejected", "Withdrawn", "Transferred", "Account Activated")}
keep_ids = [t.attributes["concept:name"] for t in prefix_log
            if t.attributes["concept:name"] not in term_in_prefix]
prefix_log = pm4py.filter_log(lambda t: t.attributes["concept:name"] in keep_ids,
                              prefix_log) if False else prefix_log  # placeholder guard

# Descriptive structure on PREFIX log only (justified: no future events present)
dfg, sa, ea = pm4py.discover_dfg(prefix_log)
print("prefix variants (top):", list(pm4py.get_variants(prefix_log))[:5])
temp_feats = pm4py.extract_temporal_features_dataframe(prefix_log)

feat_rows = []
for trace in prefix_log:
    cid, ev = trace.attributes["concept:name"], list(trace)
    t_pred = ev[-1]["time:timestamp"]
    row = {"case_id": cid, "t_pred": t_pred,
           "n_events": len(ev),
           "n_doc_loops": sum(e["concept:name"] == "Documents Requested" for e in ev),
           "elapsed_h": (t_pred - ev[0]["time:timestamp"]).total_seconds() / 3600,
           "last_activity": ev[-1]["concept:name"],
           "risk_score_at_pred": [e.get("risk_score") for e in ev
                                  if pd.notna(e.get("risk_score"))][-1:],
           "post_policy": t_pred >= POLICY_CHANGE.tz_localize("UTC")}
    assert not (set(row) & set(FORBIDDEN))          # leakage-audit check
    assert max(e["time:timestamp"] for e in ev) <= t_pred
    feat_rows.append(row)

X = pd.DataFrame(feat_rows).set_index("case_id")
data = X.join(cases[["outcome", "split", "start"]], how="inner")
assert not (set(data.columns) & set(FORBIDDEN))
print(data.groupby(["split", "outcome"]).size().unstack(fill_value=0))

# NEXT (not in PM4Py): fit discrete-time competing-risk / IPCW multinomial model
# on train, calibrate on validation, evaluate IPCW-Brier + calibration vs
# Aalen-Johansen on test; sensitivity: linked transfers, missing-feed bounds.
```
