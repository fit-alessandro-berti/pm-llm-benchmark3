# 1. Model scope and state variables

## Digital twin boundary and level of detail
The digital twin is modeled as a **hybrid Discrete-Event Simulation (DES) with coupled cluster/spatial interaction rules** operating at the individual activity-instance level.
- **System boundary**: Begins at applicant submission readiness (capturing pre-submission document checking for D1 and appointment scheduling for D7) and ends at `Issue permit`, `Reject application`, or resolution of post-decision appeal rework. Downstream construction execution and municipal HR hiring pipelines are exogenous.
- **Why pure independent-case DES is insufficient**: Cases compete for shared calendar-constrained staff, arrive in correlated architect bursts, trigger district-level inspection batching, and experience spatially correlated Public-notice delays when neighborhood objections occur.

## Entities
- **Primary entity (`PermitCase`)**: Represents an individual application (`Simple renovation`, `New residential`, `Commercial`, `Complex variance`).
- **Coupling entities**:
  - `ArchitectCluster`: Aggregates applications submitted by the same `architect_id` (especially top-20 architects accounting for 31% of volume) to model submission bursts, shared document quality, and multi-permit inspection bundling.
  - `ObjectionShock`: A latent district-week event representing neighborhood opposition that simultaneously extends `Public-notice period` for co-located active cases.
  - `InspectionBatch`: A temporary container grouping `Site inspection` tasks within the same `district` (and optionally `architect_id`) under D3.

## State variables
- **Case-level state**:
  - `active_tokens`: Set of currently executing or queued parallel branches (`Planning`, `Fire`, `Environmental`, `Public_notice`, `Inspection`).
  - `completed_branches`: Bitmask/set used by the synchronization join before `Decision drafting`.
  - `rework_counts`: Dictionary tracking loops at `Completeness`, `Planning`, `Inspection`, and `Legal/Appeal`.
  - `missing_doc_flag`, `latent_objection_flag`, `latent_env_sensitive`, `latent_area_exceeds_fire_threshold`, `prior_violations`.
  - `aging_days`: Elapsed active time since submission (used for D6 priority escalation).
  - `bundle_hold_until`: Timestamp cap for holding a case in `Inspection scheduling` while awaiting a peer case (D3).
- **System-level state**:
  - `sim_clock`: Current simulation timestamp (UTC/local municipal time).
  - `calendar_regime`: Current seasonal multiplier (Mar–May / Sep–Nov vs. baseline), day-of-week, public holiday flag, and council-meeting week flag.
  - `district_wip[d]`: Active case count and active `Public-notice` density per district $d \in \{D1,\dots,D5\}$.

## Resources, queues, calendars, and cross-case dependencies
| Role | Capacity (FTE) | Calendar & Availability Rules | Queue Discipline |
| :--- | :--- | :--- | :--- |
| **Clerks** | 5 FTE | Mon–Fri 08:00–16:00; 1 FTE dedicated to portal support on Mondays (leaving 4 FTE for checks on Mon). | FIFO (or aging-weighted for D6). |
| **Planners** | 8 FTE | Mon–Fri 09:00–17:00; 2 FTE restricted strictly to `Simple renovation`; 6 FTE generalist. | FIFO per pool; D6 reserves 1 generalist/day for aging cases. |
| **Fire reviewers** | 2 FTE equiv. | Tue–Thu only (09:00–17:00); zero capacity Mon/Fri. | FIFO. |
| **Env. reviewers** | 3 FTE | Mon–Fri, 40% of capacity diverted to non-permit duties. | FIFO; D8 routes low-risk cases to fast-track. |
| **Inspectors** | 4 FTE | Tue–Fri field visits; travel time depends on `district` (D3, D5 longer); +1 temp FTE in peak months (D4). | District-batched (D3) or FIFO by district. |
| **Legal officers** | 2 FTE | Mon–Fri, **paused during council-meeting weeks** except `is_urgent=True`. | Priority (urgent > aging > FIFO). |
| **System** | $\infty$ | 24/7 instantaneous/automated execution (`Submit`, `Receive`, `Issue`). | None. |

**Cross-case dependencies**:
1. **Architect bursts**: Top-20 architects generate temporally clustered arrivals with correlated completeness-check failure probabilities.
2. **Spatial objection contagion**: A latent objection event in district $d$ extends `Public-notice period` across all overlapping `New residential` and `Complex variance` cases in $d$.
3. **Geographic inspection bundling**: Under D3, cases in the same district/architect group wait up to a threshold window $\Delta_{\text{wait}}$ to share one inspector trip, cutting per-case travel time at the cost of bundle-waiting time.

# 2. Parameter-estimation plan

## PM4Py log and model handling
1. **Log ingestion and standardization**: Load tabular exports with `pandas`, convert timestamps, and standardize schema using `pm4py.format_dataframe(df, case_id='case:concept:name', activity_key='concept:name', timestamp_key='time:timestamp')`.
2. **Structural and variant extraction**:
   - Use `pm4py.get_variants(df)` to verify empirical variant shares against the 7 variant groups (e.g., 26% Simple clean, 19% Simple missing docs, 18% New residential w/ fire + notice).
   - Use `pm4py.discover_dfg(df)` and `pm4py.discover_performance_dfg(df)` to extract observed directly-follows transitions and empirical **sojourn times** (note: with completion-only timestamps, performance DFG edge times represent waiting + calendar block + service time, not pure service time).
   - Parse the baseline tree via `pm4py.parse_process_tree` as a structural reference, then refine it into a colored/synchronized Petri net or custom DES graph to incorporate the missing rework loops (Planning, Legal, Appeal) and the synchronization barrier before `Decision drafting`.
3. **Arrival baseline**: Compute baseline inter-arrival averages via `pm4py.get_case_arrival_average(df)` stratified by month and weekday before fitting non-stationary intensities.

## Estimation of arrivals, timings, routing, calendars, and dependencies
- **Non-stationary and clustered arrivals**:
  - Fit a **Non-Homogeneous Poisson Process (NHPP)** rate $\lambda(t, c, d) = \lambda_0 \cdot m_{\text{season}}(t) \cdot m_{\text{dow}}(t) \cdot p(c, d \mid t)$, reproducing the 1.7x spring/autumn surge and 2.2x Monday-vs-Wednesday peak.
  - Separate top-20 `architect_id` cases (31% of volume) and fit a **compound/Hawkes cluster process**: parent arrival triggers a batch size $B \sim \text{DiscreteDist}$ (mean $>1$) spread over $[0, 5]$ days.
- **Separating service time from waiting time (deconvolution)**:
  - Because start timestamps are missing for many human tasks, **never equate `time:timestamp[i] - time:timestamp[i-1]` to service time**.
  - Estimate pure service-time distributions $S_a$ (Lognormal or Weibull) via **calendar-aware maximum likelihood / EM deconvolution**:
    1. Subtract known non-working periods (nights, weekends, council weeks, Tue–Thu Fire windows) from raw sojourn times.
    2. For activities/clerks where portal or subset start timestamps *are* logged, estimate $S_a$ directly and anchor median/p90 ratios.
    3. For completion-only activities, condition on estimated queue length $N_q(t)$ at arrival-to-activity time and HR FTE count $c_r(t)$ so queueing delay $W_a(N_q, c_r)$ is separated from $S_a$, calibrated until simulated p50/p90 waiting and service times match the empirical table (e.g., Planning review median 3.5h service vs. 6d waiting).
- **Branching probabilities and latent attributes**:
  - Fit multinomial/logistic models predicting `requires_fire`, `requires_environment`, `requires_public_notice`, and `Legal check` necessity from `case_type`, `district`, and `application_value`.
  - Calibrate unobserved thresholds (`building_area`, `env_sensitivity`) as latent conditional probabilities $P(\text{trigger} \mid \text{case\_type}, \text{district})$ matched to the variant summary shares.
- **Rework and external response times**:
  - Estimate loop probabilities from repeated activity occurrences per case in the event log (e.g., `Completeness check` counts $>1$, `Site inspection` counts $>1$ matching the 9% inspection rework share).
  - Fit `Receive missing documents` waiting time directly from `time(Receive) - time(Request)` (heavy-tailed, median 5d), decoupled from municipal resource queues.
- **Resource calendars and dependencies**:
  - Encode HR schedules directly; model Environmental reviewers' 40% non-permit load as an exogenous Poisson stream of preemptive/competing blocks or stochastic capacity scaling ($0.6\times$ effective FTE) validated against the 8d median waiting time.
  - Estimate district travel penalties (D3, D5) by regressing inter-inspection gaps and inspection sojourn times on `district` and same-day inspector route density.
  - Infer latent `ObjectionShock` frequency and duration uplift by fitting a two-component mixture to `Public-notice period` durations (point mass/narrow component at 14d fixed minimum vs. heavy-tailed 30–90d component) and measuring temporal clustering of long notices within the same district.

# 3. Assumptions

- **Arrivals**:
  - Portal submissions are timestamped instantaneously without server queuing.
  - Seasonal (Mar–May, Sep–Nov = 1.7x) and weekday (Mon = 2.2x Wed) profiles are stationary year-over-year in the baseline; top-20 architects maintain a 31% share unless altered by D7.
- **Service times**:
  - Human tasks pause cleanly across off-shift hours, weekends, and council-meeting weeks (work-conserving resume) without substantial restart penalties, except where rework occurs.
  - Service times follow right-skewed parametric distributions (Lognormal/Gamma) independent of current backlog size (no unmodeled "cutting corners under load").
- **Routing**:
  - The simplified process tree is structurally augmented so `Decision drafting` acts as an AND-join barrier over all required reviews (`Planning`, `Fire`, `Environmental`, `Public-notice`, and `Site inspection` when scheduled prior to drafting), reflecting the domain routing rule rather than strict sequential execution after Public-notice.
  - Rare removed emergency cases ($<1\%$) do not materially distort routine queue capacities.
- **Resources/calendars**:
  - HR calendars reflect true baseline shifts; Clerk Monday portal support removes exactly 1 FTE from `Completeness check` on Mondays.
  - Environmental reviewers' 40% non-permit workload occurs uniformly across weekdays as competing background tasks rather than multi-week total blocks.
  - Legal officers strictly defer non-urgent permit work during council-meeting weeks.
- **Rework**:
  - Because rework reasons are uncoded text, rework probabilities depend on `case_type`, `architect_id` tier, and policy flags (D1, D2), while rework service duration is modeled as a scaled draw ($0.6\times$–$0.8\times$) of first-pass service time.
  - A maximum rework cap (e.g., 3 loops before mandatory rejection/escalation) prevents infinite simulated cycles.
- **Applicant/third-party response**:
  - `Receive missing documents` turnaround and external environmental consultant delays are exogenous to municipal staffing.
  - Under D1 (pre-submission checker), reduced missing-doc loops are assumed to trade off against increased pre-submission preparation effort (modeled via a slight shift/delay in submission timing or small applicant abandonment rate tested in sensitivity analysis).
- **Cross-case dependencies**:
  - Architect bursts share a correlated missing-document propensity.
  - Neighborhood objections act as district-level shocks affecting concurrent `Public-notice` cases in the same district, rather than cross-district contagion.
  - District inspection batching (D3) reduces travel time per site visit within a batch while strictly enforcing a maximum wait cap so singletons do not starve.
- **Non-stationary demand**:
  - Demand seasonality is continuous across year boundaries; transient queues built in Mar–May and Sep–Nov carry into summer/winter recovery periods.
- **Missing data**:
  - Missing start timestamps are treated as unobserved latent states estimated via calendar-aware deconvolution rather than collapsed into zero waiting time.
  - Missing objection events are modeled as latent binary/intensity mixtures calibrated to `Public-notice` p50 (14d) and p90 (60d), never treated as directly observed timestamps.

# 5. Warm-up, replications, and uncertainty treatment

- **Warm-up approach**: Because demand is strongly seasonal (1.7x spring/autumn) and weekly (Monday 2.2x), the system is **non-stationary periodic** rather than strictly steady-state. Initialize the twin with a **180-day (6-month) warm-up period** spanning an off-peak-to-peak transition so initial empty queues populate realistic in-flight WIP (especially long-horizon Complex variance cases with p90 = 260d). Verify stabilization of rolling 30-day WIP and queue lengths via **Welch's graphical procedure** averaged across pilot replications.
- **Run length and replications**: Collect statistics over **24 months (730 days)** post-warm-up to observe two complete seasonal cycles and multiple council-meeting calendars. Execute **$R = 40$ independent replications** per experiment (increasing to $R = 60$ if p95 CI half-widths exceed 5% of the estimate).
- **Random seeds and variance reduction**: Assign orthogonal Mersenne-Twister / PCG64 sub-streams per replication $r \in \{1,\dots,R\}$ for `(arrivals, case_attributes, service_times, rework_shocks, objection_shocks)`. Apply **Common Random Numbers (CRN)** across B0 and D1–D11 so policy contrasts are evaluated on identical arrival and shock realizations.
- **Confidence / credible intervals**: Because durations are heavily skewed, report **non-parametric bootstrap 95% confidence intervals** (2,000 BCa resamples across replication-level medians, p90, and p95) alongside paired-$t$ CIs for CRN mean differences.
- **Handling heavy-tailed durations**:
  - Never rely solely on sample means or symmetric standard deviations.
  - Track **median, p90, p95, and Conditional Value-at-Risk ($\text{CVaR}_{95}$)** of lead time.
  - Account for **right-censoring** at the 24-month horizon: use Kaplan-Meier survival estimates for cases still in WIP at $t_{\text{end}}$ (especially Complex variance) and track end-of-horizon WIP age to detect hidden backlog accumulation.
- **Sensitivity analysis**: Perform Latin Hypercube Sampling (LHS) / Morris screening over key unidentifiable parameters: (i) waiting-vs-service deconvolution split ($\pm 20\%$ shift in service time variance), (ii) Environmental non-permit diversion ($30\%$–$50\%$), (iii) latent objection prevalence, and (iv) D1 applicant abandonment / D2 risk leakage rates.

# 6. Validation strategy

1. **Face validation**: Review animated/trace outputs, queue rules, Monday clerk splits, Fire Tue–Thu windows, Legal council-week pauses, and Environmental 40% diversion with municipal domain leads to confirm behavioral realism.
2. **Event-log replay validation (trace-driven)**: Feed exact historical arrival timestamps, `case_type`, `district`, `architect_id`, and known routing flags from the log into the twin. Verify that token synchronization at `Decision drafting`, rework loops, and resource calendar blocks produce structurally valid traces matching PM4Py conformance metrics (fitness $\ge 0.95$ against the augmented model).
3. **Distributional validation**: Compare simulated vs. empirical end-to-end duration distributions across all 7 variant groups (e.g., Simple clean p50=12d/p90=24d; Commercial p50=68d/p90=130d; Complex variance p50=140d/p90=260d) using **two-sample Kolmogorov-Smirnov tests**, **Wasserstein-1 distance**, and quantile-quantile alignment at p10, p50, p90, and p95.
4. **Resource-utilization validation**: Compare simulated active FTE utilization against HR expectations—verifying high pressure on Environmental reviewers (due to 40% non-permit diversion), mid-week utilization spikes for Fire reviewers, Monday completeness backlogs for Clerks, and zero Legal throughput during council weeks.
5. **Bottleneck validation**: Verify rank-order correlation (Spearman $\rho \ge 0.85$) between simulated and empirical median activity waiting times (Site inspection 8d, Environmental 8d, Legal 7d, Planning 6d, Decision drafting 5d, Fire 4d) and confirm seasonal backlog surges in Mar–May and Sep–Nov.
6. **Out-of-sample temporal validation**: Split the 18-month event log into **Months 1–12 (calibration)** and **Months 13–18 (holdout test)**. Freeze all fitted parameters and check whether 95% prediction intervals from the twin cover observed holdout monthly throughput, WIP, and p90 duration by case type. *Note: Interventions lacking historical precedent (D1, D2, D9) remain uncalibrated counterfactuals and must not be claimed as exact optima prior to pilot testing.*

| **Lead-time (Median & Tail)** | p50 and p90 duration by `case_type` | Simple p90 $\le 18\text{d}$ (from 24–45d); New res p90 $\le 70\text{d}$; Commercial p90 $\le 95\text{d}$; Complex p90 $\le 200\text{d}$; no increase in $\text{CVaR}_{95}$. |
| **SLA Compliance** | % cases completed within municipal SLA | $\ge 90\%$ Simple ($\le 21\text{d}$), $\ge 85\%$ New res ($\le 60\text{d}$), $\ge 80\%$ Commercial ($\le 90\text{d}$), $\ge 75\%$ Complex ($\le 180\text{d}$). |
| **District & Architect Fairness** | Max-to-min district p50 ratio; Top-20 vs. other architect wait ratio | District p50 ratio $\le 1.25$ (ensuring D3/D5 aren't penalized by D3 batching); Architect wait ratio $\in [0.90, 1.15]$ (small applicants not crowded out by D7). |

| **Robustness** | Minimax regret across stress scenarios (S1–S3) | Selected policy maintains positive SLA and p90 gains over Baseline across all three stress scenarios. |

def load_and_format_log(csv_text_or_path: str, is_raw_csv_text: bool = True) -> pd.DataFrame:

def extract_pm4py_diagnostics(df: pd.DataFrame) -> Dict[str, Any]:
    """
    Extract control-flow and timing diagnostics using PM4Py conventions.
    Note: Because start timestamps are absent in the excerpt, performance DFG
    and consecutive timestamp diffs measure SOJOURN time (waiting + service),
    not pure service time.
    """
    # Parse simplified process tree.
    # Limitations of SIMPLIFIED_PROCESS_TREE_STR:
    # 1. Omits rework loops after Planning review, Legal check, and appeals.
    # 2. Places Public-notice and Inspection sequentially before Decision drafting,
    #    whereas domain rules synchronize Planning/Fire/Env/Notice/Inspection at Decision drafting.
    # 3. Lacks attribute-based routing guards and cross-case coupling.
    process_tree = pm4py.parse_process_tree(SIMPLIFIED_PROCESS_TREE_STR)

    variants = pm4py.get_variants(df)
    dfg, start_activities, end_activities = pm4py.discover_dfg(df)
    perf_dfg, perf_sa, perf_ea = pm4py.discover_performance_dfg(df)
    case_arrival_avg_sec = pm4py.get_case_arrival_average(df)

    # Compute sojourn / waiting / service time columns explicitly
    df_sorted = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    df_sorted["sojourn_hours"] = (
        df_sorted.groupby("case:concept:name")["time:timestamp"]
        .diff()
        .dt.total_seconds()
        .div(3600.0)
    )

    if "start_timestamp" in df_sorted.columns:
        df_sorted["start_timestamp"] = pd.to_datetime(df_sorted["start_timestamp"], utc=True)
        prev_end = df_sorted.groupby("case:concept:name")["time:timestamp"].shift(1)
        df_sorted["service_hours"] = (
            (df_sorted["time:timestamp"] - df_sorted["start_timestamp"])
            .dt.total_seconds()
            .div(3600.0)
        )
        df_sorted["waiting_hours"] = (
            (df_sorted["start_timestamp"] - prev_end).dt.total_seconds().div(3600.0)
        )
    else:
        # Explicitly flag missing start timestamps rather than collapsing wait & service
        df_sorted["service_hours"] = pd.NA
        df_sorted["waiting_hours"] = pd.NA

    return {
        "process_tree": process_tree,
        "variants": variants,
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": perf_dfg,
        "case_arrival_avg_sec": case_arrival_avg_sec,
        "annotated_df": df_sorted,
    }

class NonStationaryArrivalGenerator:
    """NHPP arrival generator with seasonal/weekday multipliers and architect bursts."""

    def __init__(self, base_rate_per_hour: float, rng: random.Random, policy: Dict[str, Any]):
        self.base_rate = base_rate_per_hour
        self.rng = rng
        self.policy = policy

    def seasonal_multiplier(self, hour_of_year: float) -> float:
        day_of_year = (hour_of_year / 24.0) % 365
        # Peak in Mar-May (days 60..151) and Sep-Nov (days 244..334)
        if (60 <= day_of_year <= 151) or (244 <= day_of_year <= 334):
            return 1.7 * self.policy.get("demand_surge_mult", 1.0)
        return 1.0 * self.policy.get("demand_surge_mult", 1.0)

class RoutingAndDependencyModel:
    """Handles attribute routing, synchronization joins, rework, and objection shocks."""

    def __init__(self, rng: random.Random, policy: Dict[str, Any]):
        self.rng = rng
        self.policy = policy

    def determine_required_branches(self, case: PermitCase) -> set:
        branches = {"Planning review"}
        if case.requires_fire:
            branches.add("Fire-safety review")
        if case.requires_environment:
            branches.add("Environmental review")
        if case.requires_public_notice:
            branches.add("Public-notice period")
        # D2: Skip site inspection for low-risk Simple renovation
        skip_insp = (
            self.policy.get("D2_skip_simple_inspection", False)
            and case.case_type == "Simple renovation"
            and case.application_value < 50_000
            and not case.prior_violations
        )
        if not skip_insp:
            branches.add("Site inspection")
        return branches

    def sample_rework(self, stage: str, case: PermitCase) -> bool:
        """Return True if rework triggers; scaled down under D1 pre-sub checker."""
        base_prob = {"Completeness check": 0.25, "Site inspection": 0.09}.get(stage, 0.05)
        if stage == "Completeness check" and self.policy.get("D1_precheck", False):
            base_prob *= 0.40
        return self.rng.random() < base_prob


class PermitDigitalTwinSim:
    """Discrete-event simulation engine decoupling execution from PM4Py extraction."""

    def __init__(self, policy: Dict[str, Any], seed: int, warmup_hours: float, run_hours: float):
        self.policy = policy
        self.rng = random.Random(seed)
        self.warmup_hours = warmup_hours
        self.run_hours = run_hours
        self.event_queue: List[Tuple[float, int, Callable[..., Any]]] = []
        self.arrivals = NonStationaryArrivalGenerator(base_rate_per_hour=2.4, rng=self.rng, policy=policy)
        self.resources = ResourceCalendarManager(policy=policy)
        self.routing = RoutingAndDependencyModel(rng=self.rng, policy=policy)
        self.completed_cases: List[Dict[str, Any]] = []

    def run(self) -> Dict[str, Any]:
        cases = self.arrivals.generate_arrivals(self.warmup_hours + self.run_hours)
        # TODO: Schedule arrival events into self.event_queue, process heapq loop,

        _ = cases

        return {"policy": self.policy, "n_completed": len(self.completed_cases)}


class ExperimentRunner:
    """Runs baseline, interventions (D1-D10), and stress scenarios with CRN seeds."""

    def __init__(self, n_replications: int = 40, base_seed: int = 2026):
        self.n_replications = n_replications
        self.base_seed = base_seed

    def run_matrix(self, scenarios: Dict[str, Dict[str, Any]]) -> pd.DataFrame:
        rows = []
        for name, policy in scenarios.items():
            for rep in range(self.n_replications):
                seed = self.base_seed + rep  # Common Random Numbers across scenarios
                sim = PermitDigitalTwinSim(
                    policy=policy,
                    seed=seed,
                    warmup_hours=180 * 24,
                    run_hours=730 * 24,
                )
                metrics = sim.run()
                rows.append({"scenario": name, "rep": rep, **metrics})
        return pd.DataFrame(rows)
