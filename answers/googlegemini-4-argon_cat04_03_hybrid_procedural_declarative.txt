# 1. Policy Interpretation and Conflict Resolution

### Material Assumptions
1. **Clarification Window (R3):** Because test case T2 places `Request Clarification` and `Receive Clarification` *before* `Classify Risk` while the backbone states `Classify Risk` requires the three initial checks, we assume clarification cycles may occur during the pre-classification verification phase (concurrently with or immediately following the three checks, prior to `Classify Risk`) or during the post-classification review phase, provided every request is closed by a response before any terminal outcome (`Reject Vendor` or `Activate Vendor`).
2. **Sanctions Escalation Placement (R4, R7):** `Sanctions Escalation` is an optional ad-hoc event triggered after `Run Sanctions Screening`. As demonstrated in T6 and T7, it can occur after `Classify Risk` and runs in parallel with the high-risk `Enhanced Due Diligence` / `Compliance Approval` track.
3. **Post-Activation Bank Changes (R11):** `Change Bank Details` and `Suspend Vendor` occur only after `Activate Vendor`. Because `Verify Bank Account` must occur *both* before `Classify Risk` (Backbone) and after `Change Bank Details` prior to `Release First Payment` (R11), `Verify Bank Account` is permitted to execute a second time in cases where bank details change post-activation.
4. **Atomic Timestamps:** Event timestamps represent completion times in hours relative to case start.

### The R5 vs. R6 Policy Conflict
Requirement **R5** (Legal) states that when `Sanctions Escalation` occurs, `Obtain Legal Opinion` must precede `Activate Vendor` *under all circumstances*. Requirement **R6** (Operations) states that `Activate Vendor` may precede `Obtain Legal Opinion` in emergencies if jointly authorized outside the event log, provided the opinion arrives within 24 hours of escalation/activation. Furthermore, the event log lacks both the `emergency` flag and the `joint_authorization` record.

#### Resolution Option A: Strict Legal-First Policy (Conservative / Zero-Trust Log)
* **Mechanism:** Enforce R5 strictly in the control-flow layer (`nonsuccession(Activate Vendor, Obtain Legal Opinion)` in DECLARE and ordering in the procedural/skeleton layers). Any trace where `Activate Vendor` precedes `Obtain Legal Opinion` (such as T6) is marked as a **fail** in control-flow conformance.
* **Compliance Risk:** High operational friction and false-positive compliance violations. Legitimate emergency activations approved out-of-band by executives will fail automated conformance checks, requiring manual audit overrides. However, regulatory risk is zero because unverified emergency claims cannot slip through.

#### Resolution Option B: Deferred Data-Layer Verification (Permissive Control-Flow + Strict External Audit)
* **Mechanism:** Relax the control-flow constraint in DECLARE to mere `response(Sanctions Escalation, Obtain Legal Opinion)` (R4) so that either ordering between `Activate Vendor` and `Obtain Legal Opinion` passes activity-only control-flow. Delegate the R5/R6 check entirely to the **Resource/Data-Aware Validation Layer**, which inspects whether `Activate Vendor` preceded `Obtain Legal Opinion`. If it did, the layer checks external/case attributes for `joint_authorization == True` and checks `time(Obtain Legal Opinion) - time(Sanctions Escalation) <= 24h`. If the attribute is missing from the log, the data layer flags a violation or `policy-dependent` exception.
* **Compliance Risk:** If the external data check is bypassed or decoupled from the control-flow model, unauthorized early activations will silently pass process mining audits.

### Chosen Resolution for Implementation
We adopt **Resolution Option A (Strict Legal-First Policy)** as the baseline for the DECLARE control-flow layer to ensure that activity-only audits do not silently pass undocumented exceptions, while explicitly building the **Resolution Option B** validator in the Resource/Data-Aware layer (`# 7`) and showing both outcomes in the Test-Case Verdict Matrix (`# 8`).

# 3. Procedural Backbone

### 1. Compact Formal Description
The procedural backbone is modeled as a **Partially Ordered Workflow Language (POWL)** model (convertible to an accepting Petri net in PM4Py). It captures the structured happy path and structured clarification/post-activation loops:
$$\text{Seq}\Big(\text{Receive},\; \text{Loop}\big(\text{Par}(\text{Capture}, \text{Screening}, \text{Verify}), \text{Seq}(\text{ReqClar}, \text{RecClar})\big),\; \text{Classify},\; \text{XOR}\big(\text{Reject},\; \text{Seq}(\text{XOR}(\text{MgrApp}, \text{Seq}(\text{EDD}, \text{CompApp})), \text{Activate}, \text{Loop}(\tau, \text{Seq}(\text{ChangeBank}, \text{Suspend}, \text{Verify})), \text{Payment})\big),\; \text{Close}\Big)$$

*Note on POWL representation:* To keep `Verify Bank Account` labels unique or cleanly handled in PM4Py's POWL builder, the code below constructs the core acyclic backbone plus the clarification loop and optional sanctions escalation branch using `pm4py.objects.powl.obj`.

### 2. Self-Contained PM4Py Python Code (`procedural_model`)

```python
import pm4py
from pm4py.objects.powl.obj import (
    OperatorPOWL,
    StrictPartialOrder,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def build_procedural_backbone():
    # 1. Define visible activity transitions
    rec_req = Transition(label="Receive Onboarding Request")
    cap_md = Transition(label="Capture Master Data")
    run_ss = Transition(label="Run Sanctions Screening")
    ver_ba = Transition(label="Verify Bank Account")

    req_clar = Transition(label="Request Clarification")
    rec_clar = Transition(label="Receive Clarification")

    class_risk = Transition(label="Classify Risk")

    sanc_esc = Transition(label="Sanctions Escalation")
    obt_leg = Transition(label="Obtain Legal Opinion")

    mgr_app = Transition(label="Manager Approval")
    edd = Transition(label="Enhanced Due Diligence")
    comp_app = Transition(label="Compliance Approval")
    rej_ven = Transition(label="Reject Vendor")

    act_ven = Transition(label="Activate Vendor")
    rel_pay = Transition(label="Release First Payment")
    close_onb = Transition(label="Close Onboarding")

    # 2. Optional Clarification Loop (0 or more cycles of Request -> Receive)
    clar_cycle = StrictPartialOrder(nodes=[req_clar, rec_clar])
    clar_cycle.order.add_edge(req_clar, rec_clar)
    clar_loop = OperatorPOWL(
        operator=Operator.LOOP, children=[SilentTransition(), clar_cycle]
    )

    # 3. Pre-classification concurrent block: 3 mandatory checks + optional clarification loop
    pre_check_po = StrictPartialOrder(
        nodes=[cap_md, run_ss, ver_ba, clar_loop, class_risk]
    )
    pre_check_po.order.add_edge(cap_md, class_risk)
    pre_check_po.order.add_edge(run_ss, class_risk)
    pre_check_po.order.add_edge(ver_ba, class_risk)
    pre_check_po.order.add_edge(clar_loop, class_risk)

    # 4. Optional Sanctions Escalation -> Obtain Legal Opinion sub-branch (R4, R5)
    esc_seq = StrictPartialOrder(nodes=[sanc_esc, obt_leg])
    esc_seq.order.add_edge(sanc_esc, obt_leg)
    opt_esc = OperatorPOWL(
        operator=Operator.XOR, children=[SilentTransition(), esc_seq]
    )

    # 5. Approval Routes
    # Low-risk route: Manager Approval
    low_risk_branch = mgr_app

    # High-risk route: EDD and optional Escalation/Legal Opinion before Activation
    edd_comp_po = StrictPartialOrder(nodes=[edd, opt_esc, comp_app])
    edd_comp_po.order.add_edge(edd, comp_app)
    # Legal opinion must precede Activate Vendor (enforced at activation join below)
    high_risk_branch = edd_comp_po

    approval_xor = OperatorPOWL(
        operator=Operator.XOR, children=[low_risk_branch, high_risk_branch]
    )

    # Accepted path: Approval -> Activate Vendor -> Release First Payment
    accepted_po = StrictPartialOrder(nodes=[approval_xor, act_ven, rel_pay])
    accepted_po.order.add_edge(approval_xor, act_ven)
    accepted_po.order.add_edge(act_ven, rel_pay)

    # 6. Primary Outcome XOR: Reject Vendor vs Accepted Path
    outcome_xor = OperatorPOWL(
        operator=Operator.XOR, children=[rej_ven, accepted_po]
    )

    # 7. Top-level Partial Order
    root_po = StrictPartialOrder(
        nodes=[rec_req, pre_check_po, outcome_xor, close_onb]
    )
    root_po.order.add_edge(rec_req, pre_check_po)
    root_po.order.add_edge(pre_check_po, outcome_xor)
    root_po.order.add_edge(outcome_xor, close_onb)

    return root_po


procedural_model = build_procedural_backbone()
# Can be converted to an accepting Petri net for token/alignment conformance via:
# net, im, fm = pm4py.convert_to_petri_net(procedural_model)
```

### 3. Explanation of Structural Choices and Approximations
* **Concurrency:** `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` are nodes in `pre_check_po` with no edges between them, allowing full concurrency after `Receive Onboarding Request`. All three have explicit precedence edges into `Classify Risk`.
* **Clarification Loops:** Modeled as a `LOOP(SilentTransition(), Seq(Request Clarification, Receive Clarification))` concurrent with the three initial checks before `Classify Risk` (matching T2). If a clarification occurs *after* `Classify Risk`, the procedural model treats it as a move-on-log deviation unless we duplicate the loop node; therefore, **DECLARE (`# 4`) and Log Skeleton (`# 5`) serve as the authoritative layers for R3 across the entire trace lifecycle**.
* **Choices & Terminal Outcomes:** `outcome_xor` enforces an exclusive choice between `Reject Vendor` and the `accepted_po` sub-model. Within `accepted_po`, `approval_xor` forces an exclusive choice between `Manager Approval` (low-risk) and `Enhanced Due Diligence -> Compliance Approval` (high-risk). Both branches of `outcome_xor` join before `Close Onboarding`.
* **Post-Activation Exclusion (Deliberate Modeling Choice):** `Change Bank Details` and `Suspend Vendor` (R11) are deliberately excluded from `procedural_model` and handled in DECLARE and the Data-Aware layer. Including a second `Verify Bank Account` transition inside a post-activation loop creates duplicate transition labels in the Petri net, which degrades alignment precision and obscures whether a `Verify Bank Account` token belongs to pre-classification or post-bank-change verification.

### Semantics and Direction of Encoded Rules

| Template | Key `(A, B)` or `A` | Formal Semantics & Direction | Distinction from Related Templates |
|---|---|---|---|
| `init` | `A` | Every trace must start with `Receive Onboarding Request`. | Stronger than `existence`; fixes index 0. |
| `existence` | `A` | Activity `A` occurs at least once in the trace. | Does not cap maximum occurrences (unlike `exactly_one`). |
| `precedence` | `(A, B)` | **Target-activated (`B` activates):** If `B` occurs, `A` must have occurred before `B`. `A` can occur without `B` (e.g., `Run Sanctions Screening` occurs in T1 without `Sanctions Escalation`). | Unlike `response(A, B)`, `A` does not force `B` to occur. |
| `response` | `(A, B)` | **Source-activated (`A` activates):** Whenever `A` occurs, `B` must eventually occur after `A`. | Unlike `precedence(A, B)`, `B` can occur without `A` unless paired as `succession`. Unlike `altresponse`, multiple `A`s can be satisfied by a single later `B`. |
| `altresponse` | `(Req, Rec)` | Whenever `Request Clarification` occurs, `Receive Clarification` must eventually follow, and another `Request Clarification` cannot occur in between. | Stronger than `response` (forbids `Req -> Req -> Rec`), but weaker than `chainresponse` (which requires `Rec` to *immediately* follow `Req` with zero intervening events—too strict if `Capture Master Data` finishes while waiting for clarification). |
| `altprecedence` | `(Req, Rec)` | Whenever `Receive Clarification` occurs, it must be preceded by `Request Clarification`, without an intervening `Receive Clarification`. | Paired with `altresponse`, forms `altsuccession`, guaranteeing strict 1-to-1 alternation (`Req -> ... -> Rec -> ... -> Req -> ... -> Rec`). |
| `noncoexistence` | `(A, B)` | `A` and `B` can never both appear in the same trace (symmetric). | Stronger than `nonsuccession(A, B)`, which allows `B` before `A` in the same trace. |
| `nonsuccession` | `(A, B)` | `B` cannot occur after `A`. If both occur, `B` must precede `A`. | Used for R5: `nonsuccession('Activate Vendor', 'Obtain Legal Opinion')` allows `Obtain Legal Opinion` only *before* `Activate Vendor`, whereas `noncoexistence` would falsely forbid `Obtain Legal Opinion` in accepted cases. |

# 5. Log-Skeleton Model

### PM4Py Log-Skeleton Dictionary (`log_skeleton`)

*Note on `always_after` for `("Receive Clarification", "Activate Vendor")`:* If a case requests clarification and is subsequently *rejected*, `Activate Vendor` will not occur, which would violate `("Receive Clarification", "Activate Vendor")` in rejected traces. Because T1–T8 only test clarification in accepted cases (T2, T5), this holds on the test suite, but in production where rejected cases may also have clarifications, `("Receive Clarification", "Activate Vendor")` should be omitted from `log_skeleton["always_after"]` in favor of DECLARE's `nonsuccession("Activate Vendor", "Receive Clarification")` and `nonsuccession("Reject Vendor", "Receive Clarification")`, which only forbid clarification *after* the terminal decision without forcing `Activate Vendor` to exist.

### Orientation and Layer Comparison
* **Orientation in PM4Py Log Skeleton:**
  * `(A, B) in always_after`: Whenever `A` occurs, `B` must occur at some point *after* `A` (equivalent to DECLARE `response(A, B)`).
  * `(A, B) in always_before`: Whenever `A` occurs, `B` must have occurred at some point *before* `A` (equivalent to DECLARE `precedence(B, A)`—note the reversed tuple order compared to DECLARE `precedence`!).
* **Complementarity with DECLARE:** `log_skeleton["equivalence"]` enforces exact count equality (`count(Request Clarification) == count(Receive Clarification)`), which immediately catches **T5** (1 request, 0 responses) and **R10** (`activ_freq` $\le 1$). Conversely, Log Skeleton cannot express alternating sequences without `altresponse`/`altprecedence` if counts are equal (e.g., `Req -> Req -> Rec -> Rec` has equal counts of 2 and satisfies `always_after`/`always_before`, so DECLARE's `altresponse` is still required).

# 6. Temporal Profile

### PM4Py Temporal Profile Dictionary (`temporal_profile`)

Converting R12 from hours to seconds ($1\text{ hour} = 3600\text{ seconds}$):
* `Request Clarification` $\to$ `Receive Clarification`: $\mu = 48 \times 3600 = 172800\text{ s}$, $\sigma = 24 \times 3600 = 86400\text{ s}$
* `Sanctions Escalation` $\to$ `Obtain Legal Opinion`: $\mu = 12 \times 3600 = 43200\text{ s}$, $\sigma = 6 \times 3600 = 21600\text{ s}$
* `Activate Vendor` $\to$ `Release First Payment`: $\mu = 72 \times 3600 = 259200\text{ s}$, $\sigma = 36 \times 3600 = 129600\text{ s}$

```python
zeta = 2.0

temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800.0, 86400.0),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200.0, 21600.0),
    ("Activate Vendor", "Release First Payment"): (259200.0, 129600.0),
}

# Conformance invocation:
# temporal_deviations = pm4py.conformance_temporal_profile(log, temporal_profile, zeta=zeta)
```

### Threshold Mathematics ($\zeta = 2.0$)
For any pair $(A, B)$ with elapsed time $\Delta t$, PM4Py computes $z = \frac{|\Delta t - \mu|}{\sigma}$ and flags a deviation when $z > \zeta = 2.0$:
1. `Request Clarification` $\to$ `Receive Clarification`: Allowed interval $[0\text{ h},\; 48 + 2(24) = 96\text{ h}]$.
2. `Sanctions Escalation` $\to$ `Obtain Legal Opinion`: Allowed interval $[0\text{ h},\; 12 + 2(6) = 24\text{ h}]$.
3. `Activate Vendor` $\to$ `Release First Payment`: Allowed interval $[0\text{ h},\; 72 + 2(36) = 144\text{ h}]$.

### Why Temporal Deviations Are Warnings Rather Than Control-Flow Violations
1. **External Dependencies:** Waiting on a vendor to reply (`Receive Clarification`) or external counsel to finish research (`Obtain Legal Opinion`) is an SLA/performance concern, not a structural corruption of the onboarding state machine.
2. **Retroactive Unenforceability:** Once `Obtain Legal Opinion` arrives at hour 40 ($\Delta t = 34\text{ h} > 24\text{ h}$ in T7) and is valid, rejecting the vendor solely because Legal took 34 hours instead of 24 hours is operationally counterproductive. Separating the Temporal Profile from DECLARE allows compliance dashboards to route T7 to SLA bottleneck reporting (`warning`) while confirming that all legal gates were respected (`pass` on control flow).

# 7. Resource- and Data-Aware Checks

Activity-only formalisms (Petri nets, DECLARE, Log Skeleton) only see `concept:name` sequences. They cannot evaluate:
1. **R9 (Segregation of Duties / Four-Eyes Principle):** Requires comparing `org:resource` across event pairs (`Verify Bank Account` vs. `Manager Approval`/`Compliance Approval`, and `Capture Master Data` vs. `Activate Vendor`).
2. **R6 (Emergency Activation Policy):** Requires comparing timestamps (`Activate Vendor` before `Obtain Legal Opinion`), checking the 24-hour SLA window, and inspecting external/case-level authorization attributes (`case:emergency_authorized`).
3. **R11 (Post-Activation Re-Verification):** Requires verifying that a *new* `Verify Bank Account` event occurs specifically inside the time window `[t(Change Bank Details), t(Release First Payment)]`.

### Executable-Style Python Validation Layer

```python
from typing import Any, Dict, List
import pandas as pd
import pm4py


def validate_resource_and_data_rules(
    df: pd.DataFrame,
    case_id_col: str = "case:concept:name",
    activity_col: str = "concept:name",
    timestamp_col: str = "time:timestamp",
    resource_col: str = "org:resource",
    emergency_auth_col: str = "case:joint_authorization",
    allow_r6_emergency_override: bool = False,
) -> Dict[str, Dict[str, Any]]:
    """Evaluates R6, R9, and stateful R11 constraints per case.

    Required attributes:
      - org:resource (event-level): if missing or NaN on target events, status -> 'fail' (fail-closed).
      - case:joint_authorization (case/event-level boolean): required only if Activate precedes Legal Opinion.
        If missing when needed, status -> 'policy-dependent' (or 'fail' under strict zero-trust).
    """
    # Optional PM4Py built-in four-eyes filter demonstration (returns violating cases):
    # viol_mgr = pm4py.filter_four_eyes_principle(df, "Verify Bank Account", "Manager Approval")
    # viol_cmp = pm4py.filter_four_eyes_principle(df, "Verify Bank Account", "Compliance Approval")
    # viol_act = pm4py.filter_four_eyes_principle(df, "Capture Master Data", "Activate Vendor")

    results = {}
    df_sorted = df.sort_values(by=[case_id_col, timestamp_col])

    for case_id, group in df_sorted.groupby(case_id_col, sort=False):
        issues: List[str] = []
        policy_flags: List[str] = []

        # Helper to extract events of a given activity
        def get_events(act_name: str) -> pd.DataFrame:
            return group[group[activity_col] == act_name]

        # --- R9: Four-Eyes Principle Check ---
        if resource_col not in group.columns:
            issues.append(
                f"R9 Error: Missing required attribute '{resource_col}'."
            )
        else:
            # Rule 9a: Verify Bank Account resource != Applicable Approval resource
            ver_events = get_events("Verify Bank Account")
            app_events = group[
                group[activity_col].isin(
                    ["Manager Approval", "Compliance Approval"]
                )
            ]
            if not ver_events.empty and not app_events.empty:
                ver_res = set(ver_events[resource_col].dropna())
                app_res = set(app_events[resource_col].dropna())
                if ver_Events_missing := ver_events[resource_col].isna().any():
                    issues.append(
                        "R9 Violation: Missing resource on Verify Bank Account."
                    )
                if app_events[resource_col].isna().any():
                    issues.append(
                        "R9 Violation: Missing resource on Approval event."
                    )
                overlap_9a = ver_res.intersection(app_res)
                if overlap_9a:
                    issues.append(
                        f"R9 Four-Eyes Violation (Verify Bank vs Approval) by resource(s): {overlap_9a}"
                    )

            # Rule 9b: Capture Master Data resource != Activate Vendor resource
            cap_events = get_events("Capture Master Data")
            act_events = get_events("Activate Vendor")
            if not cap_events.empty and not act_events.empty:
                cap_res = set(cap_events[resource_col].dropna())
                act_res = set(act_events[resource_col].dropna())
                if (
                    cap_events[resource_col].isna().any()
                    or act_events[resource_col].isna().any()
                ):
                    issues.append(
                        "R9 Violation: Missing resource on Capture Master Data or Activate Vendor."
                    )
                overlap_9b = cap_res.intersection(act_res)
                if overlap_9b:
                    issues.append(
                        f"R9 Four-Eyes Violation (Capture Master Data vs Activate Vendor) by resource(s): {overlap_9b}"
                    )

        # --- R5 / R6: Emergency Activation vs. Legal Opinion ---
        esc_events = get_events("Sanctions Escalation")
        leg_events = get_events("Obtain Legal Opinion")
        act_events = get_events("Activate Vendor")

        if not esc_events.empty and not act_events.empty:
            t_esc = esc_events.iloc[0][timestamp_col]
            t_act = act_events.iloc[0][timestamp_col]
            if leg_events.empty:
                issues.append(
                    "R4/R5 Violation: Sanctions Escalation occurred without Obtain Legal Opinion."
                )
            else:
                t_leg = leg_events.iloc[0][timestamp_col]
                if t_act < t_leg:
                    # Activation preceded Legal Opinion -> Check R6 conditions
                    delta_hours = (t_leg - t_act).total_seconds() / 3600.0
                    esc_to_leg_hours = (t_leg - t_esc).total_seconds() / 3600.0

                    has_auth_col = emergency_auth_col in group.columns
                    is_authorized = (
                        bool(group[emergency_auth_col].iloc[0])
                        if has_auth_col
                        and pd.notna(group[emergency_auth_col].iloc[0])
                        else None
                    )

                    if not allow_r6_emergency_override:
                        issues.append(
                            "R5 Violation (Strict Legal Policy): Activate Vendor preceded Obtain Legal Opinion."
                        )
                    else:
                        if esc_to_leg_hours > 24.0 or delta_hours > 24.0:
                            issues.append(
                                f"R6 Violation: Emergency Legal Opinion arrived too late ({esc_to_leg_hours:.1f}h > 24h)."
                            )
                        elif is_authorized is True:
                            pass  # Valid R6 emergency override
                        elif is_authorized is False:
                            issues.append(
                                "R6 Violation: Emergency activation explicitly lacked joint authorization."
                            )
                        else:
                            policy_flags.append(
                                "R5/R6 Policy-Dependent: Activate Vendor preceded Obtain Legal Opinion within 24h "
                                f"(dt={esc_to_leg_hours:.1f}h), but '{emergency_auth_col}' is missing from the log."
                            )

        # --- R11: Stateful Post-Activation Bank Change Re-Verification ---
        chg_events = get_events("Change Bank Details")
        if not chg_events.empty:
            t_chg = chg_events.iloc[-1][timestamp_col]
            sus_after = get_events("Suspend Vendor")
            sus_after = sus_after[sus_after[timestamp_col] > t_chg]
            if sus_after.empty:
                issues.append(
                    "R11 Violation: Change Bank Details not followed by Suspend Vendor."
                )

            pay_after = get_events("Release First Payment")
            pay_after = pay_after[pay_after[timestamp_col] > t_chg]
            if not pay_after.empty:
                t_pay = pay_after.iloc[0][timestamp_col]
                ver_between = get_events("Verify Bank Account")
                ver_between = ver_between[
                    (ver_between[timestamp_col] > t_chg)
                    & (ver_between[timestamp_col] < t_pay)
                ]
                if ver_between.empty:
                    issues.append(
                        "R11 Violation: No second Verify Bank Account between Change Bank Details and Release First Payment."
                    )

        # Determine final layer verdict
        if issues:
            verdict = "fail"
        elif policy_flags:
            verdict = "policy-dependent"
        else:
            verdict = "pass"

        results[case_id] = {
            "verdict": verdict,
            "issues": issues,
            "policy_flags": policy_flags,
        }

    return results
```

# 9. Contradictions, Redundancies, and Blind Spots

1. **Duplicated Enforcement Across Layers:**
   * Mutual exclusions (R1, R2, R8) are encoded in three places: the POWL `XOR` structure, DECLARE `noncoexistence`, and Log Skeleton `never_together`. While redundant on conforming logs, this redundancy is intentional for diagnostics: if a trace fails the POWL alignment (like T8), the POWL alignment only reports non-specific "move on log / move on model" steps, whereas DECLARE and Log Skeleton immediately pinpoint the exact violated business rule (`noncoexistence(Activate Vendor, Reject Vendor)`).
2. **Constraints That Become Inconsistent Under Loops or Post-Activation Changes (R11 Blind Spot):**
   * `Verify Bank Account` is required before `Classify Risk` (Backbone) AND after `Change Bank Details` before `Release First Payment` (R11).
   * In DECLARE, `precedence("Verify Bank Account", "Release First Payment")` is **blind** to R11 violations because the *first* `Verify Bank Account` (at hour 2–3) already satisfies `precedence` for `Release First Payment`! Even if a bank change happens at hour 20 and no second verification occurs, DECLARE `precedence` will falsely report `pass`.
   * Conversely, if we added `always_before("Verify Bank Account", "Classify Risk")` in a naïve way that required *every* instance of `Verify Bank Account` to precede `Classify Risk`, a legitimate post-activation re-verification (R11) would falsely fail the model. Our Python data-aware check in `# 7` solves this by slicing the event sequence specifically on `t > t(Change Bank Details)`.
3. **Vacuity in Declarative Rules:**
   * Conditional DECLARE constraints (`response`, `precedence`, `altresponse`) are **vacuously satisfied** when their activation activity does not occur. In T3 (rejected case), `response("Activate Vendor", "Release First Payment")` passes with `1.0` fitness simply because `Activate Vendor` never occurred. Similarly, in T5, the Temporal Profile for `("Request Clarification", "Receive Clarification")` passes vacuously because `Receive Clarification` never occurred! Without pairing the Temporal Profile with DECLARE/Log Skeleton, an unanswered request (infinite delay) looks like a perfect temporal pass.
4. **Missing Case Attributes (The R6 Blind Spot):**
   * R6 relies on an out-of-band `joint_authorization` and `emergency` state not recorded in the event log. Any automated conformance checker operating solely on the event log cannot distinguish an authorized emergency override from an unauthorized compliance breach (T6).
5. **Timestamp-Only Limitations:**
   * The log provides only single completion timestamps (`@hour`), not `(start_timestamp, complete_timestamp)` intervals. Consequently, true parallel execution vs. rapid sequential execution cannot be distinguished, and R12 durations measure lead time between completions rather than actual task processing time.
6. **The Risk of Treating Support/Confidence Metadata as Normative Truth:**
   * In PM4Py's DECLARE discovery/conformance format, `support` and `confidence` are statistical frequency metrics derived from historical logs. Setting `"support": 1.0, "confidence": 1.0` in a normative model is a technical requirement of the API, **not** empirical evidence that the rule holds frequently. Conversely, if a modeler discovers a DECLARE model from a noisy log using `support >= 0.8`, rare but mandatory compliance events (such as `Sanctions Escalation` $\to$ `Obtain Legal Opinion` or `Change Bank Details` $\to$ `Suspend Vendor`) will have low support ($< 0.1$) and be dropped entirely, creating severe regulatory blind spots.

# 10. Deployment Recommendation

### 1. Canonical Procedural Representation & Authoritative Policy Layer
* **Canonical Procedural Model:** Deploy the **POWL model (`procedural_model` converted to an Accepting Petri Net)** as the visual backbone for process owners and alignment-based bottleneck analysis.
* **Authoritative Compliance Layer:** Treat the **Combined Rule Engine (DECLARE + Log Skeleton + Python Resource/Data Validator)** as the authoritative compliance gate. Each sub-layer owns a distinct orthogonal concern:
  * **Log Skeleton:** Authoritative for occurrence bounds (`activ_freq` for R10), count equivalence (`equivalence` for R3), and mutual exclusion (`never_together` for R1, R8).
  * **DECLARE:** Authoritative for reactive/alternating obligations (`altresponse`/`altprecedence` for R3, `response`/`precedence`/`nonsuccession` for R4, R5, R7).
  * **Resource/Data Python Layer:** Authoritative for Four-Eyes Segregation of Duties (R9), R5/R6 emergency authorization checks, and time-windowed re-verification after bank changes (R11).

### 2. Execution Order for Conformance Pipeline
Run conformance checks in fast-fail, increasing-cost order:
1. **Stage 1 — Schema & Resource/Data Validation (`validate_resource_and_data_rules`):** Fast $O(N)$ DataFrame scan. Verifies presence of `org:resource`, checks R9 Four-Eyes, checks R11 post-activation windowing, and evaluates R5/R6 emergency flags.
2. **Stage 2 — Log Skeleton & DECLARE Conformance (`pm4py.conformance_log_skeleton`, `pm4py.conformance_declare`):** Fast rule-based evaluation to catch structural mutual exclusions (T8), unanswered clarifications (T5), and out-of-order escalations (T6) with rule-level explainability.
3. **Stage 3 — Procedural Alignments (`pm4py.conformance_diagnostics_alignments`):** Run only on traces where root-cause state-machine visualization is needed, as optimal alignments are computationally heavier.
4. **Stage 4 — Temporal Profile Monitoring (`pm4py.conformance_temporal_profile` with $\zeta = 2.0$):** Run on control-flow-valid traces (or all traces) to generate non-blocking SLA `warning` alerts (T7).

### 3. Surfacing Contradictory Findings to Users
When layers disagree (e.g., **T4** passing control-flow but failing Resource/Data, **T6** passing Temporal SLA but failing R5 control-flow, or **T7** passing control-flow but failing Temporal SLA), the UI must **never collapse the result into a single opaque boolean**:
* Surface a **Multi-Dimensional Compliance Badge** per case: `[Control-Flow: PASS/FAIL] | [Resource/SoD: PASS/FAIL] | [SLA Timing: OK/WARNING]`.
* For **T6 (R5 vs. R6 conflict)**, route the case to an **"Exception Review Queue — Missing External Authorization"** rather than grouping it with structural errors like T8, prompting a compliance officer to attach the out-of-band joint authorization artifact to transition the case from `policy-dependent` to `pass`.
