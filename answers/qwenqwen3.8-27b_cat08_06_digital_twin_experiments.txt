# 1. Model scope and state variables

The digital twin should be a **counterfactual, discrete-event, multi-resource simulation** of the building-permit process, not merely a replay engine. It must support “what-if” comparison of interventions under non-stationary demand, resource calendars, rework, cross-case dependencies, and incomplete data.

## Boundary

**Included:**

- Application submission through portal or appointment.
- Completeness checking and missing-document loops.
- Planning, fire-safety, environmental, and public-notice reviews.
- Inspection scheduling, site inspection, and district batching.
- Decision drafting, legal check, permit issue, and rejection.
- Rework after completeness, planning, inspection, legal check, and appeal-related rework where modeled.
- Applicant and third-party response times.
- Municipal resource calendars, holidays, council-meeting weeks, and part-time capacity.
- Cross-case dependencies: architect bursts, related cases, neighborhood objections, district batching, and shared resource constraints.

**Excluded or abstracted:**

- Construction phase after permit issue.
- Detailed legal litigation unless modeled as appeal/rework.
- Full geographic routing; district-level travel times are sufficient.
- Full objection event stream because objections are not fully captured; objections are modeled as a latent process.

## Level of detail

- **Time resolution:** 15-minute steps for human service activities; daily resolution for public-notice periods and applicant response where appropriate.
- **Case level:** each permit application is a case entity with attributes and state.
- **Resource level:** pooled resources with calendars and FTE capacity, not individual employee behavior unless needed for fairness analysis.
- **Dependency level:** cases are not independent; related cases can share bundles, objection risk, and resource contention.

## Entities and state variables

| Entity | Key state variables |
|---|---|
| Case | `case_id`, `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `current_activity`, `status`, `arrival_time`, `submission_time`, `completion_time`, `rework_count`, `missing_docs_requested`, `missing_docs_received`, `inspection_bundle_id`, `priority`, `aging_days`, `outcome` |
| Applicant / architect | `architect_id`, `case_count`, `related_case_ids`, `prior_violations`, `burst_propensity`, `response_speed_profile` |
| District | `district_id`, `travel_time_factor`, `environmental_sensitivity_proxy`, `objection_propensity`, `inspection_batching_eligibility` |
| Resource pool | `pool_id`, `resource_type`, `FTE`, `work_windows`, `holidays`, `council_weeks`, `part_time_fraction`, `current_workload`, `utilization` |
| Inspection bundle | `bundle_id`, `district`, `case_ids`, `release_time`, `travel_time_saving`, `first_case_waiting_penalty` |
| Calendar | `date`, `holiday_flag`, `council_meeting_week`, `peak_month_flag`, `available_capacity_by_pool` |
| Policy / intervention | `intervention_id`, `active_flag`, `parameters`, `affected_case_types`, `affected_resources`, `effective_date` |

## Queues

Model explicit queues for:

- Completeness check.
- Missing-document request preparation.
- Applicant missing-document response.
- Planning review.
- Fire-safety review.
- Environmental review.
- Public-notice waiting and objection handling.
- Inspection scheduling.
- Site inspection.
- Decision drafting.
- Legal check.
- Permit issue / rejection.

Applicant and third-party response should be modeled as **external queues or external timers**, not as municipal service queues.

## Resources and calendars

| Resource pool | Calendar / capacity notes |
|---|---|
| Clerks | 5 FTE, Mon–Fri 08:00–16:00; one clerk reserved for portal support on Mondays |
| Planners | 8 FTE, Mon–Fri 09:00–17:00; two planners restricted to Simple renovation |
| Fire reviewers | 2 FTE equivalent, Tue–Thu only |
| Environmental reviewers | 3 FTE, Mon–Fri, 40% reserved for non-permit duties |
| Inspectors | 4 FTE, field visits Tue–Fri; district-dependent travel; batching possible |
| Legal officers | 2 FTE, unavailable during council-meeting weeks except urgent cases |
| System tasks | Unlimited capacity, e.g., portal receipt, permit issue automation |
| Applicant / third party | Not municipal FTE; modeled with response-time distributions |

## Cross-case dependencies

The twin must explicitly represent:

1. **Architect bursts:** top architects submit multiple related applications in the same week.
2. **Related-case bundling:** same architect and district cases may be bundled for inspection scheduling.
3. **Neighborhood objections:** latent objection events can affect multiple related or nearby cases during public notice.
4. **Geographic batching:** district batching reduces travel time but may increase waiting for the first case in the bundle.
5. **Shared resource contention:** all cases compete for planners, fire reviewers, environmental reviewers, inspectors, and legal officers.
6. **Policy coupling:** interventions can change arrival timing, routing, resource demand, and cross-case bundling simultaneously.

# 2. Parameter-estimation plan

The estimation plan should separate **PM4Py log/model handling** from **simulation parameter estimation**. PM4Py is used to prepare the event log, discover variants, build DFG and performance DFG, and optionally parse or compare the process tree. The simulation engine consumes calibrated statistical parameters and policy rules.

## PM4Py log/model handling

Use PM4Py for:

- Formatting the pandas DataFrame into an event log.
- Extracting case starts and case attributes.
- Discovering variants.
- Building the Directly-Follows Graph, DFG.
- Building the performance DFG.
- Optionally parsing the simplified process tree string.
- Conformance or alignment checks between discovered behavior and the nominal model, where feasible.

Important PM4Py convention:

- Use `pm4py.format_dataframe` with `case:concept:name`, `concept:name`, and `time:timestamp`.
- Do not use a nonexistent `pm4py.read_csv`; use pandas to load CSV data first.
- Treat PM4Py performance DFG durations as **elapsed durations between activities**, not necessarily pure service times.

## Arrival estimation

1. Extract case start time as the minimum timestamp per case.
2. Estimate a nonhomogeneous arrival intensity:

\[
\lambda(t) = \lambda_0 \times S(month) \times D(day\text{-}of\text{-}week) \times B(architect\ burst) \times P(policy)
\]

where:

- \(S(month)\) captures March–May and September–November peaks, approximately 1.7× baseline.
- \(D(day)\) captures Monday portal peaks, approximately 2.2× Wednesday.
- \(B(architect\ burst)\) captures top-architect burst behavior.
- \(P(policy)\) captures appointment slots or pre-submission effects.

3. Estimate baseline daily or hourly rates from the 18-month log.
4. Fit day-of-week and monthly multipliers using aggregated counts.
5. For top architects, estimate:
   - probability of a burst week,
   - burst size distribution,
   - correlation of case type and district within a burst,
   - inter-arrival time within a burst.
6. Validate arrival model using:
   - daily/weekly count comparison,
   - chi-square or likelihood-ratio tests for Poisson/NHPP assumptions,
   - day-of-week and seasonal pattern plots,
   - out-of-sample holdout.

## Service-time estimation

Because many human activities have only completion timestamps, service time and waiting time cannot always be directly observed.

If start timestamps are available:

\[
service = end - start
\]

\[
waiting = start - previous\_completion
\]

If start timestamps are missing:

- The observed gap between previous activity completion and current activity completion is:

\[
elapsed = waiting + service + possible\ idle\ or\ administrative\ delay
\]

- Do not silently treat elapsed time as service time.
- Estimate service and waiting jointly using:
  - resource calendars,
  - known FTE capacity,
  - queueing assumptions,
  - Bayesian hierarchical models,
  - interval-censored likelihoods,
  - simulation calibration.

For each activity, estimate distributions conditional on:

- case type,
- district,
- resource pool,
- day of week,
- season,
- rework flag,
- case value,
- review flags.

Candidate distributions:

- Lognormal for service times.
- Weibull or gamma for waiting times.
- Log-logistic or Pareto mixture for applicant response and public-notice objection tails.
- Zero-inflated or mixture distributions for rare rework and objections.

Use empirical medians and p90 values as constraints or priors.

## Waiting-time estimation

Waiting time should be estimated separately from service time where possible.

Approaches:

1. **Direct estimation** where start timestamps exist.
2. **Queueing-model inference** using resource capacity, arrival rates, and observed queue lengths.
3. **Performance DFG decomposition:** PM4Py performance DFG gives elapsed activity-to-activity durations; use these to calibrate waiting + service jointly.
4. **Resource-calendar backfilling:** infer likely waiting from unavailable calendar periods and resource workload.
5. **Simulation calibration:** tune waiting parameters until simulated resource utilization and queue ages match observed summaries.

Key waiting-time dependencies:

- Completeness check waiting spikes after Monday submissions.
- Planning review waiting depends on district and case type.
- Environmental review waiting is highly variable.
- Legal check waiting is affected by council-meeting weeks and holidays.
- Inspection waiting depends on inspector availability, travel, and batching.

## Branching probability estimation

Estimate from:

- PM4Py variants.
- PM4Py DFG.
- Attribute columns: `case_type`, `district`, `requires_fire`, `requires_environment`, `requires_public_notice`, `application_value`, `architect_id`.
- Repeated activity counts per case.

Estimate:

- Probability of missing documents by case type and architect history.
- Probability of fire-safety review by case type, district, and building attributes.
- Probability of environmental review by case type, district, and sensitivity proxy.
- Probability of public notice by case type and district.
- Probability of planning rework.
- Probability of inspection rework.
- Probability of legal rework.
- Probability of appeal-related rework.
- Probability of permit issue versus rejection.

Where attributes are incomplete, use:

- case-type priors,
- district proxies,
- imputation with uncertainty,
- latent variables for environmental sensitivity or objection risk.

## Rework estimation

Use PM4Py to detect repeated activities:

- Count occurrences of `Completeness check` per case.
- Count occurrences of `Planning review`, `Site inspection`, and `Legal check`.
- Identify variants with repeated activities.
- Estimate rework probability and rework count distribution.

Because rework reasons are unstructured text:

- Use NLP only as auxiliary evidence.
- Do not assume reliable reason coding.
- Model rework as stochastic with reason categories if needed for policy analysis.
- Use maximum rework loops to avoid infinite simulation loops.

## Resource-calendar estimation

Resource calendars were reconstructed from HR data, not event logs. Therefore:

- Treat HR calendars as structural assumptions.
- Validate them against observed resource activity timestamps where available.
- Estimate effective FTE by comparing observed throughput with calendar capacity.
- Estimate part-time fractions and reserved capacity, e.g., environmental reviewers’ 40% non-permit duty.
- Estimate council-meeting week effects on legal check.
- Estimate holiday effects on public notice and legal check.
- Calibrate resource counts so simulated utilization is plausible, not artificially low or high.

## Dependency estimation

### Architect and related-case dependencies

Group cases by:

- `architect_id`,
- `district`,
- submission week,
- case type,
- application value range.

Estimate:

- burst probability,
- burst size,
- probability that related cases share district,
- probability of inspection bundling,
- travel-time saving from bundling,
- waiting penalty for first case in bundle.

### Neighborhood objection dependencies

Objections are not fully captured. Do not treat public-notice duration as direct observation of objection events.

Instead:

- Model objection as a latent state.
- Use public-notice duration as a censored proxy.
- Estimate objection probability from long public-notice durations.
- Estimate objection extension distribution conditional on case type, district, and related-case cluster.
- Allow one objection event to affect multiple related cases with correlation.

## PM4Py usage summary

PM4Py should be used for:

- `format_dataframe`
- variant discovery
- DFG discovery
- performance DFG discovery
- process-tree parsing or comparison
- conformance checks where meaningful
- log filtering and attribute extraction

PM4Py should **not** be used as the simulation engine. The simulation engine should be a separate modular component that consumes calibrated distributions, calendars, routing rules, and intervention parameters.

# 3. Assumptions

## Arrivals

- Arrivals follow a nonhomogeneous Poisson or renewal process with time-varying intensity.
- Seasonal peaks in March–May and September–November are multiplicative.
- Monday submissions are higher than Wednesday submissions.
- Top architects generate bursty arrivals, not merely independent Poisson cases.
- Related cases from the same architect may arrive in the same week.
- Appointment-slot interventions shift arrival timing but do not eliminate demand.

## Service times

- Service times are positive, right-skewed, and heavy-tailed for some activities.
- Service time is conditional on activity, case type, district, resource pool, and calendar.
- Where start timestamps are missing, observed elapsed time is not assumed to equal service time.
- Service and waiting are modeled separately when identifiable; otherwise they are jointly calibrated.
- System tasks have negligible or deterministic service time.
- Rework service times may be longer than first-pass service times.

## Routing

- Routing is primarily determined by case attributes and review flags.
- Fire-safety review is required when `requires_fire=yes` or when missing building-area thresholds imply fire review.
- Environmental review is required when `requires_environment=yes` or district sensitivity proxy implies review.
- Public notice is required for Complex variance and some New residential cases.
- Decision drafting waits for all applicable upstream reviews and inspection results.
- Missing data in routing attributes is handled with probabilistic rules, not deterministic imputation.
- The simplified process tree is a nominal skeleton; the simulation routing must encode conditional branches and rework loops more explicitly.

## Resources/calendars

- HR-derived calendars are treated as the best available structural assumptions.
- Resources are pooled within role categories.
- FTE represents available capacity, not exact individual behavior.
- Holidays, council-meeting weeks, and part-time calendars reduce effective capacity.
- Legal officers are unavailable during council-meeting weeks except for urgent cases.
- Fire reviewers are available only Tuesday–Thursday.
- Inspectors perform field visits Tuesday–Friday.
- District travel time affects inspection scheduling and site inspection duration.
- Resource queues use FCFS by default, with priority or aging rules only when an intervention specifies them.

## Rework

- Rework is stochastic and may occur after completeness, planning, inspection, legal check, or appeal.
- Rework probability depends on case type, district, prior rework count, and resource quality proxies.
- Rework reasons are not fully coded; the simulation uses probabilistic rework categories.
- Maximum rework loops are imposed to keep simulation stable.
- Rework increases duration and resource consumption.
- Appeals are modeled as rare rework or post-decision events, depending on the chosen boundary.

## Applicant/third-party response

- Applicant response times are external to municipal capacity.
- Missing-document response times are heavy-tailed.
- Applicant effort is not the same as municipal service time.
- Pre-submission document checker reduces missing-document probability but may increase pre-submission applicant effort.
- Third-party consultant reports affect environmental review duration.
- Applicant no-shows or unreadiness can cause inspection rework.

## Cross-case dependencies

- Cases from the same architect and district are not independent.
- Related cases may be bundled for inspection scheduling.
- Bundling reduces travel time but can increase waiting for the first case in the bundle.
- Neighborhood objections can affect multiple related or nearby cases.
- Objection effects are latent and correlated, not directly observed.
- Cross-case dependencies are modeled at the level of architect, district, neighborhood proxy, and inspection bundle.

## Non-stationary demand

- Demand is not stationary over the year.
- Monthly and day-of-week effects are included.
- Peak months and Monday peaks are explicit factors.
- Interventions may change the arrival process, not only service times.
- Stress scenarios test robustness under higher demand, resource loss, or objection surge.

## Missing data

- Missing start timestamps mean waiting/service split is partly inferred.
- Missing objection events mean public-notice duration is a proxy, not a complete objection log.
- Unstructured rework text is not treated as reliable categorical data.
- Removed emergency decisions introduce selection bias; the model should state this limitation.
- Incomplete environmental sensitivity and building-area data require probabilistic routing.
- Flattened case logs may underrepresent dependencies between related applications; dependencies are reconstructed from attributes and clustering.

# 5. Warm-up, replications, and uncertainty treatment

## Warm-up

Because the system has queues, resource calendars, and non-stationary demand, a warm-up phase is required.

Recommended approach:

- Simulate at least one full annual cycle.
- Discard the first annual cycle or the first 3 months, whichever is longer.
- Alternatively, use a stability criterion:
  - queue lengths stable over 4 consecutive weeks,
  - resource utilization stable over 4 consecutive weeks,
  - case backlog not trending upward.
- For non-stationary demand, warm-up should include both peak and off-peak periods.

## Run length

- Minimum run length: 12 months per replication.
- Recommended run length: 3 annual cycles, collecting metrics from the last 12 months.
- For rare case types, e.g., Complex variance, use longer runs or more replications.
- For stress scenarios, run at least 12 months under stressed conditions.

## Replications

- Baseline and major interventions: at least 20 independent replications.
- Tail-sensitive metrics, p90/p95, and rare case types: 50 replications.
- Small-effect interventions: 100 replications if computationally feasible.
- Use independent random seeds for each replication.

## Random seeds

- Use a fixed seed list for reproducibility.
- Use common random numbers across interventions when comparing paired scenarios.
- Report seed range or seed list in the simulation documentation.

Example:

```text
seeds = [1000, 1001, ..., 1019] for 20 replications
```

## Confidence intervals

For each metric and experiment:

- Compute mean, median, p90, p95, and SLA compliance per replication.
- Use 95% confidence intervals.
- For means, use t-based intervals if normality is reasonable.
- For medians and quantiles, use bootstrap confidence intervals.
- For paired intervention comparisons, use paired differences and paired bootstrap or t intervals.
- If Bayesian parameter uncertainty is used, report credible intervals from posterior parameter samples propagated through simulation.

## Sensitivity analysis

Perform sensitivity analysis on high-impact parameters:

- Missing-document response time.
- Public-notice objection probability and extension duration.
- Inspection travel time and batching saving.
- Legal availability during council weeks.
- Environmental review service time.
- Planner capacity and simple-renovation planner restriction.
- Monday arrival multiplier.
- Architect burst size.

Methods:

- One-at-a-time sensitivity for interpretation.
- Morris method for screening.
- Sobol indices for variance decomposition where computationally feasible.
- Scenario-based stress tests for robustness.

## Heavy-tailed durations

Heavy tails require special care:

- Fit tail distributions separately, e.g., log-logistic, Weibull, or Pareto mixture.
- Use quantile matching at p50, p90, and p99 where data allow.
- Truncate extreme values only with explicit justification, e.g., p99.9 cap.
- Use longer simulation runs for p90/p95 metrics.
- Use batch means or replications to assess convergence of tail estimates.
- Consider importance sampling for rare long-duration events if direct simulation is unstable.
- Report tail metrics with wider uncertainty intervals.
- Do not claim exact tail optimality from a finite number of replications.

# 6. Validation strategy

Validation should be layered. The goal is not to prove exact optimality, but to establish that the twin is plausible, calibrated, and robust enough for intervention comparison.

## Face validation

Validate with process owners:

- Process sequence matches operational understanding.
- Resource roles and calendars are realistic.
- Review requirements are correct.
- Rework paths are plausible.
- Cross-case dependencies are operationally meaningful.
- Intervention mechanisms are represented correctly.

## Event-log replay validation

Replay historical cases through the calibrated simulation:

- Compare activity sequences.
- Compare case completion times.
- Compare resource assignments where observable.
- Compare variant frequencies.
- Compare rework occurrences.
- Compare case-type completion distributions.

Use PM4Py to compare discovered variants and DFGs from historical log and simulated log.

## Distributional validation

Compare simulated and observed distributions for:

- Interarrival times.
- Activity elapsed durations.
- Service times where start timestamps exist.
- Waiting times where identifiable.
- End-to-end case duration by case type.
- Missing-document response time.
- Public-notice duration.
- Inspection scheduling and site inspection duration.

Use:

- KS tests where assumptions are reasonable,
- Anderson–Darling tests,
- Wasserstein distance,
- quantile comparison,
- Q–Q plots,
- histogram and ECDF comparison.

For heavy-tailed variables, emphasize p90/p95/p99 validation.

## Resource-utilization validation

Compare simulated and observed:

- Clerk utilization.
- Planner utilization.
- Fire reviewer utilization.
- Environmental reviewer utilization.
- Inspector utilization.
- Legal officer utilization.
- Queue lengths by resource pool.
- Daily workload curves.

Where observed utilization is not directly available, validate indirectly through:

- throughput,
- waiting times,
- calendar capacity,
- known resource constraints.

## Bottleneck validation

Check whether the simulation reproduces known bottlenecks:

- Monday completeness-check queue spikes.
- Planning review waiting by district and case type.
- Environmental review variability.
- Legal check delays during council-meeting weeks.
- Inspection delays in D3 and D5.
- Public-notice tail when objections occur.

A valid model should not only match average duration but also identify the correct bottleneck queues.

## Out-of-sample validation

Use temporal or case-based holdout:

- Calibrate on first 12 months, validate on last 6 months.
- Or calibrate on 80% of cases, validate on 20%.
- Compare:
  - arrival rates,
  - case mix,
  - variant frequencies,
  - duration distributions,
  - resource utilization,
  - SLA compliance.

For interventions, out-of-sample validation cannot prove counterfactual truth, but it supports confidence that the model responds plausibly to parameter changes.

## Missing-data validation

Because objections and start timestamps are incomplete:

- Validate public-notice duration distribution using latent objection model.
- Do not validate objection event counts directly if events are not observed.
- Validate waiting/service split using cases with start timestamps as a subset.
- Perform missing-data sensitivity analysis.
- Report uncertainty due to inferred waiting times and latent objections.

# 7. Decision criteria

Decision criteria should support ranking and selection of interventions. They should not be interpreted as proof of exact optimality.

## Primary duration criteria

| Case type | Baseline median target | Baseline p90 target | Intervention selection rule |
|---|---:|---:|---|
| Simple renovation |  12 days |  24 days | Select if median reduces  5% and p90 reduces  10% without harming other types |
| New residential |  48 days |  95 days | Select if median reduces  5% or p90 reduces  10% |
| Commercial |  68 days |  130 days | Select if median reduces  5% or p90 reduces  10% |
| Complex variance |  140 days |  260 days | Select if p90 reduces  10% or tail SLA improves materially |

Overall:

- Median end-to-end duration should improve or remain stable.
- p90 duration should improve for the targeted case type.
- p95 duration should not worsen by more than 5%.

## SLA compliance

Define SLA compliance as the share of cases completing within a case-type target. For example:

- Simple renovation: within 24 days.
- New residential: within 95 days.
- Commercial: within 130 days.
- Complex variance: within 260 days.

Selection thresholds:

- Overall SLA compliance  85% is desirable.
- Case-type SLA compliance  80% is desirable.
- No case type should drop by more than 2 percentage points relative to baseline.
- For targeted interventions, the affected case type should improve by at least 3 percentage points.

## Fairness criteria

Fairness should be measured across districts and architects.

District fairness:

- Maximum district median duration gap  20% of city median.
- Maximum district p90 duration / minimum district p90 duration  1.5.
- D3 and D5 should not be systematically worse after batching or travel-time policies.

Architect fairness:

- Difference between 90th and 10th percentile architect-level median duration  20%.
- Large architects should not experience worse median duration due to bundling or appointment policies.
- Small architects should not be disadvantaged by batch release rules.

## Resource-utilization criteria

Target utilization ranges:

| Resource pool | Target utilization | Guardrail |
|---|---:|---|
| Clerks | 65%–85% | Avoid > 90% for more than 10% of business days |
| Planners | 65%–85% | Avoid > 90% for more than 10% of business days |
| Fire reviewers | 60%–85% | Avoid > 90% during Tue–Thu |
| Environmental reviewers | 60%–85% | Account for 40% non-permit reservation |
| Inspectors | 65%–85% | Avoid > 90% during Tue–Fri |
| Legal officers | 60%–85% | Avoid > 90% outside council weeks |

For temporary inspector D4:

- Peak-month utilization of temporary inspector  50% is desirable.
- If utilization is too low, the intervention is not cost-effective.

## Rework criteria

Interventions should reduce or stabilize rework:

- Missing-document loops: reduce by  10% if D1 is evaluated.
- Inspection rework: reduce by  5% if D2 or D3 is evaluated.
- Legal rework: should not increase by more than 2 percentage points.
- Planning rework: should not increase by more than 2 percentage points.
- Appeal-related rework: should remain stable or decrease.

## Backlog criteria

Backlog and aging should be monitored:

- Maximum queue length by activity.
- Number of cases aging above threshold:
  - Simple renovation: > 30 days.
  - New residential: > 60 days.
  - Commercial: > 90 days.
  - Complex variance: > 180 days.
- End-of-peak backlog should not increase by more than 5% relative to baseline.
- Aging-case reservation D6 should reduce aged cases by  20% without creating a new bottleneck.

## Robustness criteria

An intervention should be robust under stress scenarios:

- Under peak surge S1:
  - median duration increase  15% relative to baseline under same stress,
  - p90 duration increase  25%,
  - SLA drop  5 percentage points.
- Under resource constraint S2:
  - no resource pool exceeds 95% utilization for more than 15% of business days,
  - legal and inspection tails remain bounded.
- Under objection surge S3:
  - Complex variance p90 increase  25%,
  - New residential p90 increase  20%,
  - district fairness guardrails remain satisfied.

A combined policy should be preferred if it improves primary metrics in normal operation and remains acceptable in at least two of three stress scenarios.

## Cost and risk guardrails

Although not fully quantified here, decisions should consider:

- Administrative cost.
- Applicant effort.
- Missed-defect risk for D2.
- False-positive cost for D9.
- Implementation complexity.
- Data requirements.
- Staff training and calendar changes.

An intervention should not be selected solely on duration improvement if it creates unacceptable risk, fairness loss, or resource overload.

def format_log(df: pd.DataFrame):
    """
    Format a pandas DataFrame into a PM4Py event log.

    Uses PM4Py conventions:
    - case:concept:name
    - concept:name
    - time:timestamp
    - org:resource, if available
    """
    required = {"case:concept:name", "concept:name", "time:timestamp"}
    missing = required - set(df.columns)
    if missing:
        raise ValueError(f"Missing required columns: {missing}")

    try:
        log = pm4py.format_dataframe(
            df,
            case_id="case:concept:name",
            activity="concept:name",
            timestamp="time:timestamp",
            resource="org:resource",
        )
    except TypeError:
        # Fallback for PM4Py versions where resource keyword is not accepted.
        log = pm4py.format_dataframe(
            df,
            case_id="case:concept:name",
            activity="concept:name",
            timestamp="time:timestamp",
        )

    return log

def parse_process_tree_safe(process_tree_string: str):
    """
    Attempt to parse the simplified process tree string.

    Limitations:
    - The simplified string is not a complete executable model.
    - It omits attribute-based routing, rework after legal/appeal, and cross-case dependencies.

        return None
    except Exception as exc:
        print(f"Process tree parsing failed: {exc}")
        print("This is expected if the simplified string is not fully PM4Py-compatible.")
        print("The simulation engine should use explicit routing rules rather than relying solely on this string.")
        return None

def _flatten_dfg(dfg_graph: Dict) -> pd.DataFrame:
    rows = []
    for src, targets in dfg_graph.items():
        for dst, count in targets.items():
            rows.append((src, dst, count))
    return pd.DataFrame(rows, columns=["from_activity", "to_activity", "count"])


def _flatten_performance_dfg(perf_dfg: Dict) -> pd.DataFrame:
    rows = []
    for src, targets in perf_dfg.items():
        for dst, stats in targets.items():
            if isinstance(stats, dict):
                rows.append(
                    (
                        src,
                        dst,
                        stats.get("mean"),
                        stats.get("std"),
                        stats.get("count"),
                    )
                )
            elif isinstance(stats, (list, tuple)):
                stats = list(stats)
                count = stats[0] if len(stats) > 0 else None
                mean = stats[1] if len(stats) > 1 else None
                std = stats[2] if len(stats) > 2 else None
                rows.append((src, dst, mean, std, count))
            else:
                rows.append((src, dst, stats, None, None))

    return pd.DataFrame(
        rows,
        columns=["from_activity", "to_activity", "mean_duration", "std_duration", "count"],
    )


def compute_log_metrics(df: pd.DataFrame, log) -> Dict:
    """
    Compute basic PM4Py-based log metrics and activity duration columns.

    Important:
    - If start timestamps are not present, elapsed time between events is not pure service time.
    - It represents waiting + service + possible administrative delay.
    """
    metrics: Dict = {}

    # Case arrival average.
    case_starts = (
        df.groupby("case:concept:name")["time:timestamp"]
        .min()
        .reset_index(name="case_start")
        .sort_values("case_start")
    )
    case_starts["interarrival_days"] = (
        case_starts["case_start"].diff().dt.total_seconds() / 86400.0
    )
    metrics["n_cases"] = len(case_starts)
    metrics["case_arrival_average_days"] = (
        case_starts["interarrival_days"].dropna().mean()
    )

    # Variants.
    try:
        variant_counts = pm4_variants.get_variants(log)
        if isinstance(variant_counts, dict):
            variant_df = pd.DataFrame(
                list(variant_counts.items()),
                columns=["variant", "count"],
            )
        else:
            variant_df = pd.DataFrame(variant_counts, columns=["variant", "count"])
    except Exception as exc:
        print(f"Variant discovery failed: {exc}")
        variant_df = pd.DataFrame(columns=["variant", "count"])
    metrics["variants"] = variant_df

    # DFG.
    try:
        dfg_graph = pm4_dfg.get_dfg(log)
        dfg_df = _flatten_dfg(dfg_graph)
    except Exception as exc:
        print(f"DFG discovery failed: {exc}")
        dfg_df = pd.DataFrame(columns=["from_activity", "to_activity", "count"])
    metrics["dfg"] = dfg_df

    # Performance DFG.
    try:
        perf_dfg = pm4_perf_dfg.get_performance_dfg(log)
        perf_dfg_df = _flatten_performance_dfg(perf_dfg)
    except Exception as exc:
        print(f"Performance DFG discovery failed: {exc}")
        perf_dfg_df = pd.DataFrame(
            columns=[
                "from_activity",
                "to_activity",
                "mean_duration",
                "std_duration",
                "count",
            ]
        )
    metrics["performance_dfg"] = perf_dfg_df

    # Activity duration columns.
    df2 = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    df2["prev_timestamp"] = df2.groupby("case:concept:name")["time:timestamp"].shift(1)
    df2["elapsed_since_prev_hours"] = (
        (df2["time:timestamp"] - df2["prev_timestamp"]).dt.total_seconds() / 3600.0
    )

    if "time:start" in df2.columns:
        df2["time:start"] = pd.to_datetime(df2["time:start"])
        df2["service_time_hours"] = (
            (df2["time:timestamp"] - df2["time:start"]).dt.total_seconds() / 3600.0
        )
        df2["waiting_time_hours"] = (
            (df2["time:start"] - df2["prev_timestamp"]).dt.total_seconds() / 3600.0
        )
    else:
        # Without start timestamps, we cannot cleanly separate waiting and service.
        df2["service_time_hours"] = np.nan
        df2["waiting_time_hours"] = np.nan
        df2["elapsed_since_prev_hours_is_total_wait_plus_service"] = True

    metrics["activity_durations"] = df2
    return metrics

@dataclass
class PermitTwinConfig:
    scenario: str = "normal"
    interventions: Tuple[str, ...] = ()
    seed: int = 123
    horizon_start: str = "2026-01-01"
    horizon_days: int = 365
    warmup_days: int = 90

    # Approximate baseline: 31,200 cases over 18 months.
    base_daily_rate: float = 31200.0 / (18 * 30.44)

    # March-May and September-November peaks.
    season_multipliers: Dict[int, float] = field(
        default_factory=lambda: {
            3: 1.7,
            4: 1.7,
            5: 1.7,
            9: 1.7,
            10: 1.7,
            11: 1.7,
        }
    )

    # Monday submissions are 2.2x Wednesday.
    # weekday: Monday=0, Tuesday=1, ..., Sunday=6.
    dow_multipliers: Dict[int, float] = field(
        default_factory=lambda: {
            0: 2.2,
            1: 1.2,
            2: 1.0,
            3: 1.0,
            4: 1.1,
            5: 0.2,
            6: 0.1,
        }
    )

    # Top-architect burst behavior.
    architect_burst_prob: float = 0.08
    architect_burst_mean_size: float = 2.5

class ArrivalGenerator:
    """
    Placeholder arrival generator.

    A production version should use calibrated NHPP or renewal parameters
    estimated from the event log.
    """

    def __init__(self, config: PermitTwinConfig, rng: Optional[np.random.Generator] = None):
        self.config = config
        self.rng = rng if rng is not None else np.random.default_rng(config.seed)

    def daily_rate(self, date: pd.Timestamp) -> float:
        rate = self.config.base_daily_rate
        rate *= self.config.season_multipliers.get(date.month, 1.0)
        rate *= self.config.dow_multipliers.get(date.weekday(), 1.0)

        if self.config.scenario == "S1_peak_surge":
            rate *= 1.2

        return rate

    def sample_case(
        self,
        date: pd.Timestamp,
        idx: int,
        architect_id: Optional[str] = None,
        district: Optional[str] = None,
    ) -> Dict:
        case_id = f"C{date.strftime('%Y%m%d')}_{idx:06d}"

        case_type = self.rng.choice(
            ["Simple renovation", "New residential", "Commercial", "Complex variance"],
            p=[0.45, 0.28, 0.17, 0.10],
        )

        if district is None:
            district = self.rng.choice(["D1", "D2", "D3", "D4", "D5"])

        if architect_id is None:
            architect_id = f"A{self.rng.integers(1, 100):02d}"

        application_value = float(self.rng.lognormal(mean=10.5, sigma=1.2))

        fire_prob = {
            "Simple renovation": 0.05,
            "New residential": 0.70,
            "Commercial": 0.80,
            "Complex variance": 0.60,
        }[case_type]

        env_prob = {
            "Simple renovation": 0.05,
            "New residential": 0.20,
            "Commercial": 0.60,
            "Complex variance": 0.50,
        }[case_type]

        notice_prob = {
            "Simple renovation": 0.00,
            "New residential": 0.50,
            "Commercial": 0.20,
            "Complex variance": 1.00,
        }[case_type]

        requires_fire = "yes" if self.rng.random() < fire_prob else "no"
        requires_environment = "yes" if self.rng.random() < env_prob else "no"
        requires_public_notice = "yes" if self.rng.random() < notice_prob else "no"

        prior_violations = bool(self.rng.random() < 0.05)

        # Placeholder arrival time within the day.
        arrival_time = date + pd.Timedelta(minutes=int(self.rng.integers(0, 480)))

        return {
            "case:concept:name": case_id,
            "arrival_time": arrival_time,
            "case_type": case_type,
            "district": district,
            "architect_id": architect_id,
            "application_value": application_value,
            "requires_fire": requires_fire,
            "requires_environment": requires_environment,
            "requires_public_notice": requires_public_notice,
            "prior_violations": prior_violations,
        }

    def generate(self) -> pd.DataFrame:
        cases: List[Dict] = []
        start = pd.Timestamp(self.config.horizon_start)

        for day in range(self.config.horizon_days):
            date = start + pd.Timedelta(days=day)
            n_base = int(self.rng.poisson(self.daily_rate(date)))

            for i in range(n_base):
                cases.append(self.sample_case(date, i))

            # Architect burst: top architects submit multiple related cases in same week.
            if self.rng.random() < self.config.architect_burst_prob:
                architect_id = f"A{self.rng.integers(1, 21):02d}"
                district = self.rng.choice(["D1", "D2", "D3", "D4", "D5"])
                batch_size = int(self.rng.poisson(self.config.architect_burst_mean_size))

                for j in range(batch_size):
                    cases.append(
                        self.sample_case(
                            date,
                            n_base + j,
                            architect_id=architect_id,
                            district=district,
                        )
                    )

        return pd.DataFrame(cases)

class RoutingPolicy:
    """
    Placeholder routing policy.

    A production engine would use a full state machine or process-tree interpreter
    with attribute-based conditions, parallel joins, and rework loops.
    """

    def __init__(self, config: PermitTwinConfig):
        self.config = config
        self.interventions = set(config.interventions)

    @staticmethod
    def _is_yes(value) -> bool:
        return str(value).lower() == "yes"

    def required_reviews(self, case: Dict) -> Dict[str, bool]:
        return {
            "fire": self._is_yes(case.get("requires_fire", "no")),
            "environment": self._is_yes(case.get("requires_environment", "no")),
            "public_notice": self._is_yes(case.get("requires_public_notice", "no")),
        }

    def skip_site_inspection(self, case: Dict) -> bool:
        """
        D2: Simple renovation no-inspection rule.
        """
        if "D2" not in self.interventions:
            return False

        if case.get("case_type") != "Simple renovation":
            return False

        if float(case.get("application_value", 1e9)) >= 50000:
            return False

        if case.get("prior_violations", False):
            return False

        return True

    def next_activity(self, state: Dict) -> str:
        """
        Placeholder next-activity function.

        This is intentionally simplified. A full implementation should:
        - run fire/environment/public-notice tasks in parallel where required,
        - join all required review results before decision drafting,
        - model rework loops explicitly,
        - handle D5 parallel legal pre-check,
        - handle D3 inspection bundling.
        """
        current = state.get("current_activity")

        if current == "Submit application":
            return "Completeness check"

        if current == "Completeness check":
            if state.get("missing_docs_requested", False) and not state.get(
                "missing_docs_received", False
            ):
                return "Request missing documents"
            return "Planning review"

        if current == "Request missing documents":
            return "Receive missing documents"

        if current == "Receive missing documents":
            state["missing_docs_received"] = True
            return "Completeness check"

        if current == "Planning review":
            # Placeholder: in production, required reviews may be parallel.
            if state.get("skip_site_inspection", False):
                return "Decision drafting"
            return "Inspection scheduling"

        if current == "Inspection scheduling":
            return "Site inspection"

        if current == "Site inspection":
            return "Decision drafting"

        if current == "Decision drafting":
            if state.get("requires_legal", False):
                return "Legal check"
            return "Issue permit"

        if current == "Legal check":
            return "Issue permit"

        return "Issue permit"

    A production version should support:
    - FTE capacity,
    - multiple work windows,
    - holidays,
    - council-meeting weeks,
    - part-time fractions,
    - district travel time,
    - queue scheduling.
    """

    def __init__(
        self,
        pool: str,
        fte: float,
        work_windows: List[Tuple[int, int, int]],
        holidays: Optional[set] = None,
        council_weeks: Optional[set] = None,
        part_time_fraction: float = 1.0,
    ):
        self.pool = pool
        self.fte = fte
        self.work_windows = work_windows
        self.holidays = holidays or set()
        self.council_weeks = council_weeks or set()
        self.part_time_fraction = part_time_fraction

    def is_available(self, ts: pd.Timestamp) -> bool:
        if self.pool == "system":
            return True

        if ts.dayofweek in (5, 6):
            return False

        if ts.date() in self.holidays:
            return False

        if self.pool == "legal" and ts.isocalendar()[1] in self.council_weeks:
            return False

        current_hour = ts.hour + ts.minute / 60.0
        for dow, start_hour, end_hour in self.work_windows:
            if ts.dayofweek == dow and start_hour <= current_hour < end_hour:
                return True

        return False

    def next_available(self, ts: pd.Timestamp, service_hours: float) -> pd.Timestamp:
        """
        Placeholder: advance time in 15-minute increments until service_hours
        of available time have elapsed.
        """
        t = ts
        remaining = float(service_hours)

        while remaining > 0:
            if self.is_available(t):
                step = min(0.25, remaining)
                t = t + pd.Timedelta(hours=step)
                remaining -= step
            else:
                t = t + pd.Timedelta(minutes=15)

        return t


def build_calendars(config: PermitTwinConfig) -> Dict[str, ResourceCalendar]:
    holidays = {
        pd.Timestamp("2026-01-01").date(),
        pd.Timestamp("2026-05-01").date(),
        pd.Timestamp("2026-12-25").date(),
    }

    council_weeks = {5, 10, 15, 20, 25, 30}

    clerk_windows = [(d, 8, 16) for d in range(5)]
    planner_windows = [(d, 9, 17) for d in range(5)]
    fire_windows = [(1, 9, 17), (2, 9, 17), (3, 9, 17)]
    env_windows = [(d, 9, 17) for d in range(5)]
    inspector_windows = [(1, 8, 16), (2, 8, 16), (3, 8, 16), (4, 8, 16)]
    legal_windows = [(d, 9, 17) for d in range(5)]
    system_windows = [(d, 0, 24) for d in range(7)]

    inspector_fte = 4.0
    if "D4" in config.interventions:
        # Placeholder: full engine should add temporary inspector only in peak months.
        inspector_fte = 5.0

    return {
        "clerk": ResourceCalendar("clerk", 5.0, clerk_windows, holidays=holidays),
        "planner_simple": ResourceCalendar(
            "planner_simple", 2.0, planner_windows, holidays=holidays
        ),
        "planner_general": ResourceCalendar(
            "planner_general", 6.0, planner_windows, holidays=holidays
        ),
        "fire": ResourceCalendar("fire", 2.0, fire_windows, holidays=holidays),
        "environment": ResourceCalendar(
            "environment",
            3.0,
            env_windows,
            holidays=holidays,
            part_time_fraction=0.6,
        ),
        "inspector": ResourceCalendar(
            "inspector",
            inspector_fte,
            inspector_windows,
            holidays=holidays,
        ),
        "legal": ResourceCalendar(
            "legal",
            2.0,
            legal_windows,
            holidays=holidays,
            council_weeks=council_weeks,
        ),
        "system": ResourceCalendar("system", np.inf, system_windows),
    }

class BundleManager:
    """
    Placeholder for district-batched inspection scheduling, D3.
    """

    def __init__(self, max_bundle_size: int = 3, travel_saving: float = 0.2):
        self.max_bundle_size = max_bundle_size
        self.travel_saving = travel_saving

    def can_bundle(self, case: Dict, pending_cases: List[Dict]) -> bool:
        if "D3" not in case.get("interventions", set()):
            return False

        for other in pending_cases:
            if (
                other["district"] == case["district"]
                and other["case_type"] == case["case_type"]
                and other["architect_id"] == case["architect_id"]
            ):
                return True

        return False

    def release_bundle(self, cases: List[Dict]) -> Dict:
        """
        Placeholder: return bundle metadata.
        A full engine would adjust travel time and waiting penalties.
        """
        return {
            "district": cases[0]["district"],
            "case_ids": [c["case:concept:name"] for c in cases],
            "travel_saving": self.travel_saving,
        }

def run_experiment(
    name: str,
    interventions: Tuple[str, ...] = (),
    scenario: str = "normal",
    n_reps: int = 20,
    seeds: Optional[List[int]] = None,
) -> pd.DataFrame:
    """
    Run multiple replications of an experiment.

    Uses common random numbers across replications by assigning one seed per replication.
    """
    if seeds is None:
        seeds = list(range(1000, 1000 + n_reps))
    else:
        seeds = list(seeds)

    rows = []

    for seed in seeds:
        config = PermitTwinConfig(
            scenario=scenario,
            interventions=tuple(interventions),
            seed=seed,
        )

        rng = np.random.default_rng(seed)

        arrivals = ArrivalGenerator(config, rng=rng).generate()
        routing = RoutingPolicy(config)
        calendars = build_calendars(config)

        engine = SimulationEngine(
            config=config,
            arrivals=arrivals,
            routing=routing,
            calendars=calendars,
            rng=rng,
        )

        metrics = engine.run()
        metrics["experiment"] = name
        metrics["scenario"] = scenario
        metrics["interventions"] = ",".join(interventions)
        metrics["seed"] = seed

        rows.append(metrics)

    return pd.DataFrame(rows)
