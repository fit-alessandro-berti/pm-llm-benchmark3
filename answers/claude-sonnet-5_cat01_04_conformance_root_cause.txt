## 3. Causal-abductive explanation

```text
UI_release -> recorded_labels
UI_release -> alignment_moves [via unmapped label mismatch]
ETL_change -> recorded_order
ETL_change -> alignment_moves [via reversed Decision/Notify]
ETL_change -> missing_resource_field [side effect of pipeline change]
policy_change -> true_process [adds required Supervisor Sign-off for high-value cases]
policy_change -> normative_model [should have triggered update; did not]
normative_model -> alignment_moves [outdated model flags legitimate sign-off as deviation]
reviewer_behavior -> true_process [Manual Override used as workaround, small volume]
reviewer_behavior -> recorded_labels [interacts with 2026-08-12 override logging change]
technical_event_gateway -> recorded_labels [Queue Routed inserted, partial coverage]
technical_event_gateway -> alignment_moves
high_value_flag (hidden) -> true_process [determines whether sign-off is truly required]
high_value_flag (hidden) -> normative_model_gap [unobserved in alignment report]
true_process -> recorded_labels
true_process -> recorded_order
true_process -> business_outcomes
recorded_labels -> alignment_moves
recorded_order -> alignment_moves
alignment_moves -> measured_fitness
missing_resource_field -> measured_fitness [confidence/attribution degradation]
measured_fitness -> conclusions_about_true_process (hidden inferential step, potentially biased)
business_outcomes -> compliance_reported_incidents (hidden, admitted incomplete)
```

Multiple independent mechanisms are stacked in time and can jointly inflate a conformance metric without any real deterioration in claims handling. A UI rename (label drift) and a new technical event (Queue Routed) both alter `recorded_labels` without touching `true_process`; an ETL timestamp switch corrupts `recorded_order` for a subset of cases; and an unrelated regulatory change silently invalidates `normative_model` by adding a legitimate new activity the model cannot recognize. All four converge onto `alignment_moves`, which the initial (raw) conformance job could not distinguish from genuine deviations, producing a large, alarming `measured_fitness` drop. Stable `business_outcomes` do not prove the data is at fault, because approval and appeal rates are outcome-level metrics insensitive to procedural violations (e.g., a missed compliance check that does not change the final decision), and compliance itself admits detection is incomplete. Conversely, stable outcomes do not rule out noncompliance either, since silent bypasses (Manual Override, missing Compliance Check/Sign-off) could persist below the detection threshold of appeal-driven incident reporting. The correct inference discipline is to first strip out label/technical/order artifacts and update the model, then examine whatever conformance gap remains as the *candidate* real signal — which is exactly what the staged alignment results already show happening.

## 6. PM4Py reproduction and model-comparison code

```python
import pm4py
import pandas as pd

# ---------------------------------------------------------------------
# 1. Normative process tree
# ---------------------------------------------------------------------
normative_tree_str = (
    "-> ( 'Receive', 'Classify', "
    "X ( * ( 'Standard Review', 'Request Info' ), "
    "-> ( 'Enhanced Review', 'Compliance Check' ) ), "
    "'Decision', 'Notify' )"
)
normative_tree = pm4py.parse_process_tree(normative_tree_str)

# ---------------------------------------------------------------------
# 2. Convert to accepting Petri net
# ---------------------------------------------------------------------
net, im, fm = pm4py.convert_to_petri_net(normative_tree)

# ---------------------------------------------------------------------
# 3. Expand variant-frequency tables into event logs
#    (pm4py.parse_event_log_string accepts a list/iterable of
#    comma-separated trace strings and synthesizes case ids/timestamps)
# ---------------------------------------------------------------------
apr_may_variants = {
    "Receive,Classify,Standard Review,Decision,Notify": 380,
    "Receive,Classify,Enhanced Review,Compliance Check,Decision,Notify": 180,
    "Receive,Classify,Standard Review,Request Info,Standard Review,Decision,Notify": 40,
}

jun_jul_variants = {
    "Receive,Risk Screen,Queue Routed,Standard Review,Decision,Notify": 270,
    "Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Decision,Notify": 145,
    "Receive,Risk Screen,Queue Routed,Standard Review,Notify,Decision": 70,
    "Receive,Risk Screen,Standard Review,Decision,Notify": 90,
    "Receive,Classify,Queue Routed,Standard Review,Decision,Notify": 30,
    "Receive,Risk Screen,Queue Routed,Enhanced Review,Decision,Notify": 25,
    "Receive,Risk Screen,Queue Routed,Manual Override,Standard Review,Decision,Notify": 20,
}

aug_sep_variants = {
    "Receive,Risk Screen,Queue Routed,Standard Review,Decision,Notify": 210,
    "Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Supervisor Sign-off,Decision,Notify": 150,
    "Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Decision,Notify": 90,
    "Receive,Risk Screen,Queue Routed,Standard Review,Supervisor Sign-off,Decision,Notify": 60,
    "Receive,Risk Screen,Queue Routed,Standard Review,Notify,Decision": 45,
    "Receive,Risk Screen,Queue Routed,Enhanced Review,Decision,Notify": 30,
    "Receive,Risk Screen,Queue Routed,Manual Override,Standard Review,Decision,Notify": 35,
}

def expand_variants(variant_dict):
    traces = []
    for variant, count in variant_dict.items():
        traces.extend([variant] * count)
    return traces

apr_may_log = pm4py.parse_event_log_string(expand_variants(apr_may_variants), sep=",")
jun_jul_log = pm4py.parse_event_log_string(expand_variants(jun_jul_variants), sep=",")
aug_sep_log = pm4py.parse_event_log_string(expand_variants(aug_sep_variants), sep=",")

# ---------------------------------------------------------------------
# 4. Discover DFGs (frequency)
# ---------------------------------------------------------------------
dfg_am, sa_am, ea_am = pm4py.discover_dfg(apr_may_log)
dfg_jj, sa_jj, ea_jj = pm4py.discover_dfg(jun_jul_log)
dfg_as, sa_as, ea_as = pm4py.discover_dfg(aug_sep_log)

print("Jun-Jul DFG edges (sample):", list(dfg_jj.items())[:5])

# ---------------------------------------------------------------------
# 5. Alignment-based fitness against the RAW normative model
# ---------------------------------------------------------------------
def fitness_and_precision(log, net, im, fm):
    fitness = pm4py.fitness_alignments(log, net, im, fm)
    precision = pm4py.precision_alignments(log, net, im, fm)
    return fitness, precision

raw_fit_jj, raw_prec_jj = fitness_and_precision(jun_jul_log, net, im, fm)
raw_fit_as, raw_prec_as = fitness_and_precision(aug_sep_log, net, im, fm)

print("RAW Jun-Jul fitness:", raw_fit_jj)
print("RAW Aug-Sep fitness:", raw_fit_as)

# ---------------------------------------------------------------------
# 6. Transparent normalization pipeline:
#    map Risk Screen -> Classify, optionally strip Queue Routed

def normalize_log(log, remove_technical_events=True):
    normalized = log.copy(deep=True)
    normalized["concept:name"] = normalized["concept:name"].replace(
        {"Risk Screen": "Classify"}
    )
    if remove_technical_events:

    return normalized

jun_jul_norm = normalize_log(jun_jul_log, remove_technical_events=True)
aug_sep_norm = normalize_log(aug_sep_log, remove_technical_events=True)

norm_fit_jj, norm_prec_jj = fitness_and_precision(jun_jul_norm, net, im, fm)
norm_fit_as, norm_prec_as = fitness_and_precision(aug_sep_norm, net, im, fm)

# ---------------------------------------------------------------------
# 7. Compare raw vs normalized results
# ---------------------------------------------------------------------
comparison = pd.DataFrame({
    "period_condition": ["Jun-Jul raw", "Jun-Jul normalized",
                          "Aug-Sep raw", "Aug-Sep normalized"],
    "avg_trace_fitness": [
        raw_fit_jj.get("average_trace_fitness"),
        norm_fit_jj.get("average_trace_fitness"),
        raw_fit_as.get("average_trace_fitness"),
        norm_fit_as.get("average_trace_fitness"),
    ],
    "precision": [
        raw_prec_jj, norm_prec_jj, raw_prec_as, norm_prec_as
    ],

print(comparison)

# ---------------------------------------------------------------------

candidate_tree_str = (

    "X ( * ( 'Standard Review', 'Request Info' ), "
    "-> ( 'Enhanced Review', 'Compliance Check' ) ), "
    "X ( 'Supervisor Sign-off', tau ), "
    "'Decision', 'Notify' )"

candidate_tree = pm4py.parse_process_tree(candidate_tree_str)

# ---------------------------------------------------------------------
# 9. Caveats

print("""
CAVEATS:
- The candidate model treats 'Supervisor Sign-off' as an unconstrained optional
  activity (X( Supervisor Sign-off, tau )). Process trees / plain Petri nets encode

  claims above EUR 50,000, because claim value is a data attribute, not a control-flow

- A fitness increase under the candidate model must be read jointly with precision.
  If precision drops sharply, the model has become overgeneralized: it now silently
```

## 7. Provisional conclusion

**Primary explanation for the measured conformance collapse:** the bulk of the fitting-trace collapse (93%32% in Jun-Jul, remaining depressed through Aug-Sep) is best explained by a *stack of data and model artifacts*, not by a change in real work practice. The UI rename of `Classify``Risk Screen` (confirmed by a 40-case audit), the partial rollout of the technical `Queue Routed` event, an ETL timestamp change that silently reordered `Decision`/`Notify` for a subset of cases, and an unrelated regulatory change (`Supervisor Sign-off` >€50k) that was never reflected in the normative model together account for the overwhelming majority of the fitness loss — demonstrated directly by the staged alignment recovery (32%58%81%89% in Jun-Jul; 66%86% in Aug-Sep). **Confidence: high (85%)** that these four mechanisms are the dominant driver of the *measured* drop.

**Separate assessment of a real compliance problem:** even after all corrections, an unresolved residual remains — 25–30 Enhanced Review traces per period lack a Compliance Check, and Manual Override use, while small, is admitted by reviewers. Stable approval/appeal rates are reassuring but not dispositive, since compliance itself states incident detection is incomplete, and outcome-level KPIs are insensitive to procedural bypass unless it changes the ultimate decision. **Confidence: low-to-moderate (30–40%)** that a genuine, non-trivial compliance issue exists; it is neither confirmed nor ruled out by current evidence.

**Immediate actions:**
- *IT*: freeze further silent schema/label changes; expose source-sequence numbers to the conformance pipeline; document the `Queue Routed` and `Manual Override` event semantics formally.
- *Process owners*: submit a formal, versioned normative-model update reflecting the `Supervisor Sign-off` rule, ideally as a data-aware model.
- *Compliance*: commission the manual audit of the 25–30 missing-check traces and stratify by claim value and reviewer before drawing conclusions.

**What must not be claimed yet:** that employees have become noncompliant; that the process has materially changed; or, conversely, that the data problems fully explain away all deviations. All three claims are premature pending Phase 3–4 diagnostics.

## 8. Model-governance recommendation

1. **Model versioning**: Every normative process-tree deployment must carry a version identifier, effective-date range, and change log; conformance jobs must record which model version was used, and policy/regulatory changes must trigger a mandatory model-review ticket before go-live.
2. **Event-semantic contracts**: UI and label changes affecting `concept:name` values must be accompanied by a machine-readable activity-mapping contract (old label  new label  semantic equivalence claim), reviewed and signed off by process owners, not just release notes.
3. **Technical-event policy**: All non-user-initiated (gateway/system) events must be tagged with an explicit `event:type` (technical vs. business) at emission time, with a standing rule that conformance checking excludes or separately reports technical events by default.
4. **Timestamp provenance**: Any ETL change to timestamp source (e.g., ingestion time vs. source-system time) must preserve and propagate an authoritative ordering key (sequence number), and conformance pipelines must default to source-order when ingestion-time and sequence-number diverge.
5. **Data-aware constraints**: Amount-, risk-, or threshold-triggered obligations (e.g., mandatory sign-off above a monetary limit) must be modeled as guarded/data-aware conditions (e.g., Data Petri Nets) rather than relying on a control-flow-only tree, and the relevant case attributes must always be included in conformance extracts.
6. **Post-release validation**: Every UI, ETL, or policy release with potential process-mining impact must trigger an automatic before/after DFG and alignment-fitness comparison plus a small mandatory manual audit within the first reporting cycle, with sign-off required before the new baseline is accepted as "normal."
