### Why Directly-Follows Graph (DFG) Bidirectionality Does Not Prove Concurrency

In the derived DFG, we observe:
- `("Credit Check", "Engineering Review"): 17`
- `("Engineering Review", "Credit Check"): 11`

In process mining, observing bidirectional directly-follows arcs between two activities $A$ and $B$ (i.e., both $A \rightarrow B$ and $B \rightarrow A$ have non-zero counts across cases) is a *necessary* condition for interleaved completion under concurrency, but it is **not sufficient** to prove true concurrency. Specifically, four distinct phenomena produce identical bidirectional DFG patterns:

1. **Mutually Exclusive Sequential Execution (XOR-Sequence Branches):** The underlying business process may have two mutually exclusive case types. For example, standard commercial orders may execute $A$ then $B$ strictly sequentially because credit must clear before engineering begins work, whereas emergency custom orders execute $B$ then $A$ strictly sequentially because technical feasibility must be established before running credit. In neither case are $A$ and $B$ ever active concurrently. A DFG aggregates across cases, projecting two mutually exclusive sequential paths into a bidirectional cycle.
2. **Short Loops and Rework:** If an activity can repeat (e.g., $A \rightarrow B \rightarrow A$), a DFG exhibits bidirectional edges even though the execution within each case is strictly sequential.
3. **Discrete Completion Granularity and Arbitrary Ingestion:** Under completion-only logging (D7, S7), if two independent tasks run during overlapping intervals, whichever worker submits their form first is logged first. Conversely, if work is strictly batched by external schedules, completion timestamps may alternate without physical overlap.
4. **True Parallelism (AND-Concurrency):** Both activities are enabled simultaneously upon order registration, and independent workers process them in parallel.

Because the DFG projects multi-case event data into a first-order Markovian abstraction, it completely loses case-level execution state and cannot distinguish an AND-split/join from an XOR-split over opposing sequences. Concurrency can only be defended when supported by domain corroboration (statement S2 from the Engineering Lead) and causal invariant analysis (absence of data dependencies preventing parallel execution).

# 2. Shared Assumptions

The three candidate models share the following foundational modeling assumptions:

1. **Completion-Only Event Semantics (D7, S7):** All event log timestamps represent the moment an activity was completed and ingested. The process models represent transactional lifecycle completion order. The absence of start timestamps prevents measuring activity durations or physical temporal overlap directly from event data.
2. **Control-Flow Abstraction for Missing Data and Integration Loss (S3, S4, S5):** The dataset omits the case-level attribute distinguishing external components from stocked components. Furthermore, an estimated 5–10% of `Supplier Confirmation` events were dropped due to an upstream ETL integration bug. Because data-aware guards cannot be evaluated from the log, all models abstract both legitimate business skips (stocked orders) and data-pipeline dropouts (lost events) into a single non-deterministic control-flow routing: an exclusive choice between executing `Supplier Confirmation` and executing a silent transition ($\tau$ skip).
3. **Optionality Representation:** Both `Supplier Confirmation` and `Expedite Review` are optional within the process. Optionality is uniformly formalized as an XOR choice between the concrete activity transition and an unobservable silent transition ($\tau$).
4. **Strict Boundary Precedence (D1, D2):** Every case strictly begins with `Register Order` and strictly terminates with `Archive Case`. Furthermore, `Release Production` is unconditionally gated by `Approve Configuration`, followed immediately by `Archive Case`. The post-approval sequence is invariant: $\text{Approve Configuration} \rightarrow \text{Release Production} \rightarrow \text{Archive Case}$.
5. **No Rework or Looping (Acyclicity):** No activity is observed more than once within any single trace in the 30-case log. In accordance with domain rules D1–D6, the workflow is assumed to be an acyclic workflow net where each activity executes at most once per case instance.

# 3. Conservative Candidate

### Inductive-Bias Statement
The conservative candidate adopts an extreme empirical bias: it prioritizes precision over generalization, hypothesizing that the observed event log captures all allowable operational execution paths. It explicitly assumes that unobserved activity interleavings are either operationally forbidden or non-compliant. To avoid asserting concurrency where only completion-order sequences were recorded, it represents the intermediate phase between `Register Order` and `Approve Configuration` as an exclusive choice ($\text{XOR}$) among the 7 observed sequence variants.

### Compact Formal Expression
Let $\mathcal{A}$ be the set of activity labels. The conservative model is formulated as a block-structured Process Tree $M_{\text{cons}}$:

$$M_{\text{cons}} = \rightarrow\Big(\text{RO},\, \times(v_1, v_2, v_3, v_4, v_5, v_6, v_7),\, \text{AC},\, \text{RP},\, \text{ArC}\Big)$$

where:
- $\text{RO} = \text{Register Order}$, $\text{AC} = \text{Approve Configuration}$, $\text{RP} = \text{Release Production}$, $\text{ArC} = \text{Archive Case}$
- $v_1 = \rightarrow(\text{CC}, \text{ER}, \text{SC})$
- $v_2 = \rightarrow(\text{ER}, \text{CC}, \text{SC})$
- $v_3 = \rightarrow(\text{CC}, \text{ER})$
- $v_4 = \rightarrow(\text{ER}, \text{CC})$
- $v_5 = \rightarrow(\text{CC}, \text{SC}, \text{ER})$
- $v_6 = \rightarrow(\text{CC}, \text{ER}, \text{SC}, \text{XR})$
- $v_7 = \rightarrow(\text{ER}, \text{CC}, \text{XR}, \text{SC})$
with $\text{CC} = \text{Credit Check}$, $\text{ER} = \text{Engineering Review}$, $\text{SC} = \text{Supplier Confirmation}$, $\text{XR} = \text{Expedite Review}$.

### Self-Contained PM4Py Code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def create_conservative_model() -> ProcessTree:
    """
    Constructs model_conservative: an XOR enumeration of the 7 observed variants
    bounded by the invariant prefix (Register Order) and suffix (Approval -> Release -> Archive).
    """
    def make_seq(labels):
        st = ProcessTree(operator=Operator.SEQUENCE)
        for lbl in labels:
            st.children.append(ProcessTree(label=lbl, parent=st))
        return st

    middle_variants = [
        ['Credit Check', 'Engineering Review', 'Supplier Confirmation'],
        ['Engineering Review', 'Credit Check', 'Supplier Confirmation'],
        ['Credit Check', 'Engineering Review'],
        ['Engineering Review', 'Credit Check'],
        ['Credit Check', 'Supplier Confirmation', 'Engineering Review'],
        ['Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review'],
        ['Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation']
    ]

    root = ProcessTree(operator=Operator.SEQUENCE)
    root.children.append(ProcessTree(label='Register Order', parent=root))

    xor_mid = ProcessTree(operator=Operator.XOR, parent=root)
    for variant in middle_variants:
        child_seq = make_seq(variant)
        child_seq.parent = xor_mid
        xor_mid.children.append(child_seq)
    root.children.append(xor_mid)

    root.children.append(ProcessTree(label='Approve Configuration', parent=root))
    root.children.append(ProcessTree(label='Release Production', parent=root))
    root.children.append(ProcessTree(label='Archive Case', parent=root))

    return root

model_conservative = create_conservative_model()
```

### List of Behavior Deliberately Excluded
1. **Unobserved Expedite Review Interleavings:** Deliberately excludes an expedite review on a stocked item where `Supplier Confirmation` is skipped (`RO` $\rightarrow$ `CC` $\rightarrow$ `ER` $\rightarrow$ `XR` $\rightarrow$ `AC` $\rightarrow$ `RP` $\rightarrow$ `ArC`), despite being fully compliant with D6 and S6.
2. **Symmetric Expedite Interleaving:** Deliberately excludes `RO` $\rightarrow$ `CC` $\rightarrow$ `ER` $\rightarrow$ `XR` $\rightarrow$ `SC` $\rightarrow$ `AC` $\rightarrow$ `RP` $\rightarrow$ `ArC` (the mirror of V7 where `Credit Check` completes before `Engineering Review`).
3. **Expedite Review following V5:** Deliberately excludes `RO` $\rightarrow$ `CC` $\rightarrow$ `SC` $\rightarrow$ `ER` $\rightarrow$ `XR` $\rightarrow$ `AC` $\rightarrow$ `RP` $\rightarrow$ `ArC`.
4. **Engineering-Led Supplier Inquiries:** Deliberately excludes any trace where `Supplier Confirmation` completes before `Credit Check` (e.g., `ER` $\rightarrow$ `SC` $\rightarrow$ `CC`).

### List of Known Underfitting Risks and Scalability Limitations
- **Empirical Overfitting / Domain Underfitting (False Rejection):** By treating the 30-case log as an exhaustive census of all valid behaviors, the model severely underfits the real-world process dynamics. For example, if a custom order with stocked parts requests expedited handling, the real process would legitimately execute `XR` without `SC`, but `model_conservative` would classify this trace as non-compliant.
- **Duplicate Label Explosion:** In the converted Petri net, `Credit Check` appears 7 times, `Engineering Review` 7 times, `Supplier Confirmation` 5 times, and `Expedite Review` 2 times. Label duplication obscures the underlying causality and prevents standard token-replay diagnostics from uniquely identifying transition firing sequences without complex alignment search.
- **Maintenance and Ingestion Scalability:** The model size scales linearly with the number of observed variants ($O(|\mathcal{V}| \cdot L)$ transitions). In production environments with 15+ concurrent or optional activities, the variant count grows combinatorially ($>10^4$), causing the model structure to explode and rendering visual inspection and governance intractable.

# 4. Balanced Candidate

### Inductive-Bias Statement
The balanced candidate adopts a structured, partially ordered inductive bias: it reconciles observed variant frequencies with high-confidence domain rules by modeling true concurrency where supported by stakeholder evidence (S2) and ordering dependencies where substantiated by data. Specifically, it infers that `Credit Check` and `Engineering Review` are concurrent; `Supplier Confirmation` causally depends on `Credit Check` but runs concurrently with `Engineering Review`; and `Expedite Review` strictly requires the completion of both `Credit Check` and `Engineering Review`. Because this dependency structure forms a non-series-parallel partial order (an N-structure), it is encoded as a Partially Ordered Workflow Language (POWL) model.

### Compact Formal Expression
The balanced model is defined as a Strict Partial Order POWL model $M_{\text{bal}} = (N, \prec)$:

$$N = \{\text{ro}, \text{cc}, \text{er}, \text{sc}_{\text{choice}}, \text{xr}_{\text{choice}}, \text{ac}, \text{rp}, \text{arc}\}$$

where:
- $\text{ro} = \text{Transition}(\text{"Register Order"})$
- $\text{cc} = \text{Transition}(\text{"Credit Check"})$
- $\text{er} = \text{Transition}(\text{"Engineering Review"})$
- $\text{sc}_{\text{choice}} = \times_{\text{powl}}\big(\text{Transition}(\text{"Supplier Confirmation"}),\, \tau\big)$
- $\text{xr}_{\text{choice}} = \times_{\text{powl}}\big(\text{Transition}(\text{"Expedite Review"}),\, \tau\big)$
- $\text{ac} = \text{Transition}(\text{"Approve Configuration"})$
- $\text{rp} = \text{Transition}(\text{"Release Production"})$
- $\text{arc} = \text{Transition}(\text{"Archive Case"})$

The strict partial order relation $\prec$ is defined by the transitive closure of the following direct precedence edges:
$$\begin{aligned}
\text{ro} &\prec \text{cc}, \quad \text{ro} \prec \text{er} \\
\text{cc} &\prec \text{sc}_{\text{choice}} \\
\text{cc} &\prec \text{xr}_{\text{choice}}, \quad \text{er} \prec \text{xr}_{\text{choice}} \\
\text{sc}_{\text{choice}} &\prec \text{ac}, \quad \text{xr}_{\text{choice}} \prec \text{ac} \\
\text{ac} &\prec \text{rp} \prec \text{arc}
\end{aligned}$$

### Decision Rationale: Sequence, Concurrency, and Partial Order
1. **Credit Check vs. Engineering Review (Concurrency):** Finance (S1) claimed `Credit Check` must finish before `Engineering Review` starts. However, 11 of 30 cases (36.7%) exhibit `Engineering Review` finishing first. The Engineering Lead (S2) clarified that both checks are initiated in parallel upon registration, and completion timestamps reflect processing duration variance. Modeling `Credit Check` and `Engineering Review` as concurrent ($\text{cc} \parallel \text{er}$) explains both the 19 $\text{CC}\rightarrow\text{ER}$ and 11 $\text{ER}\rightarrow\text{CC}$ completions without asserting spurious cyclic rework.
2. **Supplier Confirmation Dependencies (Partial Order with CC, Concurrency with ER):** In all 23 traces containing `Supplier Confirmation`, `Credit Check` completed before `Supplier Confirmation`. However, in V5 (2 cases), `Supplier Confirmation` completed *before* `Engineering Review` ($\text{CC} \rightarrow \text{SC} \rightarrow \text{ER}$). If `Supplier Confirmation` required both checks, V5 would be impossible. If `Supplier Confirmation` was completely concurrent with both, we would expect to observe `SC` before `CC`, which never occurs. Therefore, `Supplier Confirmation` causally requires `Credit Check` (finance clears credit before commitments are sought from suppliers), but operates concurrently with `Engineering Review` ($\text{cc} \prec \text{sc}$, $\text{sc} \parallel \text{er}$).
3. **Expedite Review Dependencies (Joint Synchronization):** D6 and S6 mandate that `Expedite Review` requires completion of *both* principal checks. In the log, both V6 and V7 occur only after both `Credit Check` and `Engineering Review` are complete. Thus, $\text{cc} \prec \text{xr}$ and $\text{er} \prec \text{xr}$.
4. **Supplier Confirmation vs. Expedite Review (Mutual Concurrency):** In V6, `Supplier Confirmation` completes before `Expedite Review` ($\text{SC} \rightarrow \text{XR}$). In V7, `Expedite Review` completes before `Supplier Confirmation` ($\text{XR} \rightarrow \text{SC}$). S6 explicitly confirms that expedite reviews may occur before or after supplier confirmations. Thus, $\text{sc}_{\text{choice}} \parallel \text{xr}_{\text{choice}}$.
5. **Why POWL is Strictly Necessary (The N-Structure Theorem):**
   Consider the sub-poset over $\{\text{cc}, \text{er}, \text{sc}, \text{xr}\}$:
   - $\text{er} \prec \text{xr}$
   - $\text{cc} \prec \text{xr}$
   - $\text{cc} \prec \text{sc}$
   - $\text{er} \not\prec \text{sc}$ and $\text{sc} \not\prec \text{er}$ ($\text{er} \parallel \text{sc}$)
   - $\text{sc} \not\prec \text{xr}$ and $\text{xr} \not\prec \text{sc}$ ($\text{sc} \parallel \text{xr}$)

   In order theory (Valdes, Tarjan, and Lawler, 1979), a finite poset is series-parallel (and therefore representable as a standard Process Tree without duplicate transition labels) if and only if its Hasse diagram does not contain the four-element crown/fence poset known as the **$N$-structure**:
   $$\text{er} \longrightarrow \text{xr} \longleftarrow \text{cc} \longrightarrow \text{sc}$$
   Because $\text{er}$ connects to $\text{xr}$, $\text{cc}$ connects to both $\text{xr}$ and $\text{sc}$, but $\text{er}$ has no order relation to $\text{sc}$, this sub-graph is topologically an $N$-structure. A standard Process Tree cannot enforce that $\text{xr}$ waits for $\text{er}$ while $\text{sc}$ does not wait for $\text{er}$, while simultaneously allowing $\text{sc}$ and $\text{xr}$ to interleave in either order. POWL resolves this limitation by allowing general strict partial orders.

### Self-Contained PM4Py Code

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def create_balanced_model() -> StrictPartialOrder:
    """
    Constructs model_balanced: a POWL StrictPartialOrder capturing the N-structure:
    - CC and ER are concurrent after RO.
    - SC (optional) causally requires CC, but is concurrent with ER.
    - XR (optional) causally requires both CC and ER.
    - SC and XR are mutually concurrent.
    - AC synchronizes all completed checks before RP and ArC.
    """
    ro = Transition(label="Register Order")
    cc = Transition(label="Credit Check")
    er = Transition(label="Engineering Review")
    ac = Transition(label="Approve Configuration")
    rp = Transition(label="Release Production")
    arc = Transition(label="Archive Case")

    # Optionality modeled as XOR between activity transition and silent bypass
    sc_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label="Supplier Confirmation"), SilentTransition()]
    )
    xr_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label="Expedite Review"), SilentTransition()]
    )

    nodes = [ro, cc, er, sc_choice, xr_choice, ac, rp, arc]
    po = StrictPartialOrder(nodes=nodes)

    # Prefix
    po.order.add_edge(ro, cc)
    po.order.add_edge(ro, er)

    # Causal dependencies for SC and XR
    po.order.add_edge(cc, sc_choice)
    po.order.add_edge(cc, xr_choice)
    po.order.add_edge(er, xr_choice)

    # Suffix synchronization
    po.order.add_edge(sc_choice, ac)
    po.order.add_edge(xr_choice, ac)
    po.order.add_edge(ac, rp)
    po.order.add_edge(rp, arc)

    return po

model_balanced = create_balanced_model()
```

### List of Behavior Deliberately Excluded
1. **Pre-Credit Supplier Inquiries:** Deliberately excludes any execution where `Supplier Confirmation` occurs before `Credit Check` (e.g., `RO` $\rightarrow$ `SC` $\rightarrow$ `CC` $\rightarrow$ `ER` $\dots$ or `RO` $\rightarrow$ `ER` $\rightarrow$ `SC` $\rightarrow$ `CC` $\dots$).
2. **Premature Expedite Reviews:** Deliberately excludes any execution where `Expedite Review` occurs before either `Credit Check` or `Engineering Review` has completed (e.g., `RO` $\rightarrow$ `CC` $\rightarrow$ `XR` $\rightarrow$ `ER` $\dots$).
3. **Post-Approval Audits:** Excludes any execution of `Credit Check`, `Engineering Review`, `Supplier Confirmation`, or `Expedite Review` after `Approve Configuration`.
4. **Multiple Invocations:** Excludes looping or repeated executions of any activity.

### List of Known Underfitting Risks and Uncertainty Trade-offs
- **D5 Generalization Risk (ER-Initiated Supplier Inquiries):** Domain rule D5 states that `Supplier Confirmation` may begin after *either* `Credit Check` or `Engineering Review`. The balanced candidate enforces `cc` $\prec$ `sc_choice` because in all 23 empirical instances, `Credit Check` preceded `Supplier Confirmation`. If future orders allow engineering specifications to trigger supplier confirmation before credit is cleared (e.g., for specialized engineered-to-order parts), `model_balanced` will falsely reject those valid traces.
- **Sample Size Vulnerability (Sparse 30-case log):** With only 2 traces containing `Expedite Review` and 2 traces containing the `CC` $\rightarrow$ `SC` $\rightarrow$ `ER` interleaving, the model's structural edges rely heavily on low-frequency variants.

# 5. Permissive Candidate

### Inductive-Bias Statement
The permissive candidate adopts a maximally liberal, block-structured inductive bias: it prioritizes recall and operational flexibility over precision, postulating that all intermediate review, confirmation, and expedite activities are operationally decoupled. It admits that any intermediate activity may run concurrently once the order is registered, provided that all initiated checks complete before configuration approval. Structurally, it reflects the model discovered by block-structured mining algorithms (e.g., standard Inductive Miner without label duplication) that must generalize across non-series-parallel interleavings by wrapping all four intermediate tasks into a single parallel block.

### Compact Formal Expression
The permissive model is formulated as a Process Tree $M_{\text{perm}}$:

$$M_{\text{perm}} = \rightarrow\Big(\text{RO},\, +\big(\text{CC},\, \text{ER},\, \times(\text{SC}, \tau),\, \times(\text{XR}, \tau)\big),\, \text{AC},\, \text{RP},\, \text{ArC}\Big)$$

where:
- $+$ denotes the parallel (AND) operator;
- $\times(\cdot, \tau)$ denotes the exclusive choice (XOR) with a silent transition $\tau$.

### Definition of Boundary Between "Reasonable Generalization" and Forbidden Behavior
- **Admitted Reasonable Generalization:**
  1. *Complete Concurrency of SC:* `Supplier Confirmation` may precede `Credit Check`, interleave between `Credit Check` and `Engineering Review`, or succeed `Engineering Review`. This fully satisfies domain rule D5 in its most permissive interpretation (allowing supplier engagement to begin purely upon order registration).
  2. *Expedite Permissiveness:* `Expedite Review` may occur at any position prior to `Approve Configuration`, including in parallel with the principal checks.
  3. *Independent Omission:* Either or both of `Supplier Confirmation` and `Expedite Review` may be omitted independently.
- **Strictly Forbidden Behavior (Inviolable Boundaries):**
  1. *Lifecycle Boundaries (D1, D2):* `Register Order` must always be the first activity; `Archive Case` must always be the final activity.
  2. *Mandatory Configuration Gate (D2, D3, D4, D6):* `Approve Configuration` cannot execute until all active intermediate tasks have completed. Under no circumstances can `Credit Check`, `Engineering Review`, `Supplier Confirmation`, or `Expedite Review` occur after `Approve Configuration`.
  3. *Production Chain Invariance (D2):* `Release Production` can only execute directly after `Approve Configuration`, and `Archive Case` can only execute directly after `Release Production`.
  4. *Absence of Rework:* No activity can execute more than once per case.
  5. *Mandatory Principal Checks (D3):* `Credit Check` and `Engineering Review` cannot be bypassed; both must occur in every case.

### Self-Contained PM4Py Code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree

def create_permissive_model() -> ProcessTree:
    """
    Constructs model_permissive: a block-structured Process Tree where
    Credit Check, Engineering Review, optional Supplier Confirmation, and
    optional Expedite Review execute in parallel between Register Order
    and Approve Configuration -> Release Production -> Archive Case.
    """
    tree_string = (
        "->( 'Register Order', "
        "+( 'Credit Check', 'Engineering Review', "
        "X( 'Supplier Confirmation', tau ), X( 'Expedite Review', tau ) ), "
        "'Approve Configuration', 'Release Production', 'Archive Case' )"
    )
    return pm4py.parse_process_tree(tree_string)

model_permissive = create_permissive_model()
```

### List of Behavior Deliberately Excluded
1. **Omission of Principal Checks:** Excludes any trace skipping `Credit Check` or `Engineering Review` (e.g., `RO` $\rightarrow$ `SC` $\rightarrow$ `AC` $\rightarrow$ `RP` $\rightarrow$ `ArC`).
2. **Premature Production Release:** Excludes releasing production before approval (`RO` $\dots$ $\rightarrow$ `RP` $\rightarrow$ `AC` $\rightarrow$ `ArC`), upholding D2.
3. **Post-Approval Processing:** Excludes performing any check after configuration approval (e.g., `RO` $\rightarrow$ `CC` $\rightarrow$ `ER` $\rightarrow$ `AC` $\rightarrow$ `SC` $\rightarrow$ `RP` $\rightarrow$ `ArC`).
4. **Out-of-Order Lifecycle:** Excludes starting with any task other than `Register Order` or finishing with any task other than `Archive Case`.

### List of Known Underfitting Risks and Precision Penalties
- **Underfitting Constraints / Severe Precision Degradation:** By placing `Expedite Review` in parallel with `Credit Check` and `Engineering Review`, the model admits traces where an expedite review is performed before the order has been checked for credit or engineering feasibility. This directly violates compliance rule S6 and domain rule D6.
- **Uncontrolled Supplier Commitments:** Admits traces where external suppliers are contacted before establishing whether the customer is creditworthy or whether the design is technically feasible, introducing substantial commercial and legal exposure.

# 8. Validation Code

The self-contained Python script below:
1. Reconstructs the 30-case log from the variant frequencies using `pm4py.parse_event_log_string`;
2. Instantiates all three models and converts them into accepting Petri nets;
3. Runs soundness checks;
4. Computes alignment-based fitness, alignment-based precision, time-based replay generalization, and Petri net simplicity;
5. Executes bounded playout simulations;
6. Evaluates a comprehensive test suite of positive, plausible-unobserved, and negative (violating) traces.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from collections import Counter

# Part 1: LOG RECONSTRUCTION

def reconstruct_event_log():
    """
    Reconstructs the 30-case log from the observed variant frequencies.

        ("Register Order,Engineering Review,Credit Check,Expedite Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case", 1),

def build_conservative_model() -> ProcessTree:
    """Model 1: Conservative (Process Tree XOR of 7 variants)"""
    def make_seq(labels):
        st = ProcessTree(operator=Operator.SEQUENCE)
        for l in labels:
            st.children.append(ProcessTree(label=l, parent=st))
        return st

    middle_variants = [
        ['Credit Check', 'Engineering Review', 'Supplier Confirmation'],
        ['Engineering Review', 'Credit Check', 'Supplier Confirmation'],
        ['Credit Check', 'Engineering Review'],
        ['Engineering Review', 'Credit Check'],
        ['Credit Check', 'Supplier Confirmation', 'Engineering Review'],
        ['Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review'],
        ['Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation']
    ]

    root = ProcessTree(operator=Operator.SEQUENCE)
    root.children.append(ProcessTree(label='Register Order', parent=root))
    
    xor_mid = ProcessTree(operator=Operator.XOR, parent=root)
    for var in middle_variants:
        child = make_seq(var)
        child.parent = xor_mid
        xor_mid.children.append(child)
    root.children.append(xor_mid)

    root.children.append(ProcessTree(label='Approve Configuration', parent=root))
    root.children.append(ProcessTree(label='Release Production', parent=root))
    root.children.append(ProcessTree(label='Archive Case', parent=root))
    return root

def build_balanced_model() -> StrictPartialOrder:
    """Model 2: Balanced (POWL StrictPartialOrder encoding N-structure)"""
    ro = Transition(label='Register Order')
    cc = Transition(label='Credit Check')
    er = Transition(label='Engineering Review')
    ac = Transition(label='Approve Configuration')
    rp = Transition(label='Release Production')
    arc = Transition(label='Archive Case')

    sc_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label='Supplier Confirmation'), SilentTransition()]
    )
    xr_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label='Expedite Review'), SilentTransition()]
    )

    nodes = [ro, cc, er, sc_choice, xr_choice, ac, rp, arc]
    po = StrictPartialOrder(nodes=nodes)

    po.order.add_edge(ro, cc)
    po.order.add_edge(ro, er)
    po.order.add_edge(cc, sc_choice)
    po.order.add_edge(cc, xr_choice)
    po.order.add_edge(er, xr_choice)
    po.order.add_edge(sc_choice, ac)
    po.order.add_edge(xr_choice, ac)
    po.order.add_edge(ac, rp)
    po.order.add_edge(rp, arc)
    return po

def build_permissive_model() -> ProcessTree:
    """Model 3: Permissive (Process Tree parallel block)"""
    tree_string = (
        "->( 'Register Order', "
        "+( 'Credit Check', 'Engineering Review', "
        "X( 'Supplier Confirmation', tau ), X( 'Expedite Review', tau ) ), "
        "'Approve Configuration', 'Release Production', 'Archive Case' )"
    )
    return pm4py.parse_process_tree(tree_string)

        print(f"[{name}] Sound: {sound} | Places: {len(net.places)}, Transitions: {len(net.transitions)}, Arcs: {len(net.arcs)}")

    print("\n--- 2. Conformance & Structural Quality Metrics ---")
```

### Model Recommendations
- **Recommended for Immediate Operational Deployment: `model_balanced`**
  `model_balanced` provides the optimal trade-off between fitness, precision, and domain fidelity. It achieves $100\%$ fitness on the observed log while retaining high precision ($0.9189$), avoiding the severe underfitting of `model_conservative` (which cannot handle an expedited order on stocked parts) and the regulatory hazards of `model_permissive` (which permits illegal pre-check expedite reviews). ### Materially Disruptive Alternative Interpretation
**The "Rogue Expedited Procurement" Hypothesis:**
A plausible alternative interpretation is that `Credit Check` must finish before `Engineering Review` *starts* (S1 was correct as a mandatory financial control policy), and `Supplier Confirmation` must be preceded by *both* checks. Under this interpretation, the 11 cases where `Engineering Review` completed before `Credit Check` (V2, V4, V7) and the 2 cases where `Supplier Confirmation` completed before `Engineering Review` (V5) do **not** represent benign concurrency. Instead, they represent **severe compliance breaches**: engineering personnel started work on orders before financial clearance, and procurement committed inquiries to external vendors on high-risk accounts.

If this alternative hypothesis is true, our inductive discovery models commit a classic normative fallacy: **they confuse observed non-compliance with intended process flexibility**.
