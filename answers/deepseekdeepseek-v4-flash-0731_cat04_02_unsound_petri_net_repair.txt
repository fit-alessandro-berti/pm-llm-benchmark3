```
def get_transition(net, name):
    for t in net.transitions:
        if t.name == name:
            return t
    raise KeyError(name)

def fire_transition(net, marking, name):
    t = get_transition(net, name)
    enabled = pm4py.get_enabled_transitions(net, marking)
    if t not in enabled:
        raise ValueError(f"{name} is not enabled at {marking}")
    for arc in t.in_arcs:
        src = arc.source
        marking[src] -= arc.weight
        if marking[src] == 0:
            del marking[src]
    for arc in t.out_arcs:
        tgt = arc.target
        marking[tgt] = marking.get(tgt, 0) + arc.weight
    return marking
```

# 1. Executive Verdict

This net is a workflow net: it has a unique source place, unique sink place, and every node lies on a source-to-sink path. It should not be expected to be sound. The principal defect is that `t_join_waived` is not actually a synchronization: it consumes only `p_waived` and produces `p_decision`, so a waiver alone can enable `t_authorize` while `p_analysis` or `p_analysis_done` is still present. The business consequence is that a case can be authorized without completing the always-mandatory analysis, and any waiver-path completion can leave an unconsumable token, so the exact final marking is not reached. The standard-review path is correctly synchronized, but the waiver path violates the intent.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `t_split` | AND-split after registration | Consumes `p_ready`; produces one token in `p_analysis` and one in `p_review` | None; the parallel start works |
| `t_standard_review` + `p_review_done` | Standard review completion | Produces `p_review_done`; feeds `t_join_normal` | None on this branch |
| `t_waive_review` + `p_waived` | Waiver outcome | Produces `p_waived`; feeds `t_join_waived`; has no connection to `p_analysis_done` | Waiver path appears complete before analysis is done |
| `t_join_normal` | Synchronize analysis and standard review | Requires both `p_analysis_done` and `p_review_done`, then produces `p_decision` | Correct, but only usable for standard review |
| `t_join_waived` | Intended synchronization of analysis and waiver | Acts as a single-input pass-through from `p_waived` to `p_decision` | `p_decision` can be produced without analysis completion |
| Initial/final markings | Unique source and sink with clean final state | `source` and `sink` are unique; `im` and `fm` are well-formed | Workflow-net check passes |
| Source-to-sink path condition | Every node should be on a source-to-sink path | All nodes do lie on such paths | Workflow-net check passes, but soundness still fails |

# 3. Marking-Based Counterexample

Start from `im = {source: 1}` and follow the waiver route:

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---|---|---|---|---|
| 0 | — | `{source: 1}` | `t_register` | Initial marking |
| 1 | `t_register` | `{p_ready: 1}` | `t_split` | Registration done |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | Parallel branches started |
| 3 | `t_waive_review` | `{p_analysis: 1, p_waived: 1}` | `t_analyze`, `t_join_waived` | Waiver recorded; analysis not done |
| 4 | `t_join_waived` | `{p_analysis: 1, p_decision: 1}` | `t_analyze`, `t_authorize` | Waiver alone created a decision token |
| 5 | `t_authorize` | `{p_analysis: 1, sink: 1}` | `t_analyze` | A token exists in `sink`, but `fm` has not been reached |
| 6 | `t_analyze` | `{p_analysis_done: 1, sink: 1}` | — | Exact `fm` is never reached; leftover token is dead |

The leftover `p_analysis_done` cannot be consumed. Its only outgoing arc in the original net is to `t_join_normal`, but `t_join_normal` also requires `p_review_done`. The `p_review` token was already consumed by `t_waive_review`, and no transition can create `p_review_done` afterward. There is no arc from `p_analysis_done` to `t_join_waived`, so `t_join_waived` cannot consume it either.

So even if `t_authorize` fires after `t_analyze`, the final marking still contains an unconsumable `p_analysis_done` token.

# 4. Minimal-Repair Alternatives

Edit-cost model: adding or removing one arc, place, or transition costs 1. Relabeling is not an edit. A repair is minimal if no cheaper valid repair exists.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---|---|---|---|
| A: True waiver join | Add arc `p_analysis_done -> t_join_waived` | 1 | Fully preserves mandatory analysis and clean final marking | `t_join_waived` becomes a real two-input AND join; waiver can still be recorded before analysis, but the decision token waits for analysis completion | Less immediate waiver-to-decision flow; this is the intended synchronization |
| B: Gate waiver recording on analysis | Add arc `p_analysis_done -> t_waive_review` | 1 | Fully preserves mandatory analysis and clean final marking | Waiver cannot be recorded until analysis is complete; the review work is still started in parallel, but waiver recording is serialized after analysis | Reduces concurrency on the waiver path; changes the allowed ordering of `t_analyze` and `t_waive_review` |
| C: Optional analysis when waived | Add arc `p_analysis -> t_waive_review` | 1 | Changes business policy: analysis is no longer mandatory if waiver is selected; standard review still requires analysis | Choosing waiver consumes the analysis branch without performing `t_analyze`, so authorization can happen after waiver only | Compliance violation relative to the stated “analysis is always mandatory” rule |

Minimality justification: the original net is already defective, so any valid repair needs at least one edit. Deleting an existing arc cannot create the missing synchronization; it would only make behavior more permissive or disconnect nodes. Therefore a valid one-edit repair is globally minimal. Repairs A, B, and C are all one-arc additions, so they all have cost 1. A and B tie at cost 1 while preserving the mandatory-analysis rule. They are behaviorally distinct: A delays the waiver join until `p_analysis_done` exists, while B delays the waiver recording itself until `p_analysis_done` exists. C is also cost 1 but requires a deliberate policy change.

# 7. Repair Trade-Offs and Residual Risks

Waiver and standard review remain distinguishable in Repair A: the standard review path produces `p_review_done`, while the waiver path produces `p_waived`. They feed different silent transitions, `t_join_normal` and `t_join_waived`. After either join produces `p_decision`, the marking alone no longer reveals which review outcome occurred, but the transition history and labels still distinguish the paths.

Repair A does not introduce duplicate concurrent behavior. The two silent joins are mutually exclusive because they require different review-outcome places. However, two silent transitions both leading to `p_decision` can be confusing in process mining or in a diagram: an observer seeing only `p_decision` cannot tell whether the review was standard or waived. This is a readability/auditability concern, not a control-flow deadlock.

Soundness alone does not prove alignment with the business rule. A sound net could still make analysis optional, as in Repair C, while satisfying proper completion. The repaired net is sound and, because of the added arc, structurally enforces the rule: `t_join_waived` cannot produce a decision token unless `p_analysis_done` exists. But soundness is only a necessary condition, not a substitute for checking the intended business traces.

# 8. Final Recommendation

Deploy Repair A: add arc `p_analysis_done -> t_join_waived`. It is a cost-1 repair, fully preserves the stated business intent, keeps analysis mandatory, and directly fixes the root cause by making the waiver join a genuine two-input synchronization. It also preserves the intended parallelism better than Repair B, because waiver recording may still happen before analysis; only the authorization decision is forced to wait.

Use Repair B as the fallback: add arc `p_analysis_done -> t_waive_review`. It is also cost-1 and preserves mandatory analysis, but it imposes a stricter ordering: waiver recording cannot occur until analysis is complete. If the business accepts that stronger ordering, Repair B is still sound and easy to implement. Repair C should not be deployed under the original policy, because it changes the rule to make analysis optional on the waiver path. Between A and B, Repair A is the better fit for the stated intent because it keeps the review and analysis branches as concurrent as possible.
