## 1. Consistency rules and evidence model

**Rules used**

| Rule | Classification |
|---|---|
| No new objects/events may be invented. | hard invariant |
| Relation endpoints must exist in objects/events. | hard invariant |
| Object types must be compatible with activity semantics. | hard invariant |
| `Create Order` normally relates to one Order; `Add Item` normally relates to one Order and one Item. | strong default |
| `Pack Item` normally relates to one Item and one Package; scanner outages can create item-only rows. | strong default |
| `Dispatch Package` normally relates to one Package and one Delivery; bulk dispatches can cover multiple packages. | strong default |
| `Issue Invoice` normally relates to one Invoice and one or more Orders. | strong default |
| `Record Payment` normally relates to one Payment and normally one Invoice; unapplied cash is possible. | strong default |
| Identifier prefixes such as `PK8-`, `N-42*`, `B-77x` are informative. | weak heuristic |
| Arithmetic equality of order declared values, invoice totals, or payment sums is informative but not decisive. | weak heuristic |
| Same customer, route, or timestamp increases plausibility but does not identify a unique relation. | weak heuristic |
| A proposed edge that would create an incompatible cardinality or break lifecycle order counts against the repair. | evidence against a repair |

I combine evidence as follows:

- Identifier similarity has the greatest weight when an otherwise unused object matches the prefix in an event attribute: `ev10` with `external_ref=N-421?` points to `DEL-Y`, whose `carrier_ref=N-421`.
- Route and customer confirmations are supporting evidence, not unique identifiers.
- Amount equality is treated as a weak heuristic because fees, discounts, partial payments, and unapplied cash are plausible.
- Existing O2O edges constrain lifecycles: because `DEL-X carries PK-7` already exists, adding `ev10 -> DEL-X` would make `DEL-X` carry two packages at the same dispatch time while `DEL-Y` remains unused; that is possible but less likely than `ev10 -> DEL-Y`.
- I do **not** treat an O2O edge inferred from an E2O edge as independent confirmation of the same relation.
- Some ambiguous edges are left unresolved rather than forcing complete lifecycles.

## 3. Alternative repair bundles

### Bundle A — conservative/minimum-change repair

- **ev08 and PK-8**: Add `ev08 -> PK-8` and `PK-8 packs IT-B1` provisionally. This is the most direct reading of `scanner_ref=PK8-2`, but confidence is not high because a scanner outage is possible.
- **ev10 and DEL-X/DEL-Y**: Add `ev10 -> DEL-Y` and `DEL-Y carries PK-8`. The identifier match is strong enough to accept, while leaving open the small possibility that ev10 was meant for DEL-X.
- **ev11 and delivery objects**: Leave `ev11` unresolved with respect to DEL-X/DEL-Y. Keep only the observed `ev11 -> ORD-A`.
- **INV-44 and ORD-B**: Add `ev12 -> ORD-B` and `INV-44 bills ORD-B` provisionally. The amount/customer match is suggestive, not decisive.
- **PAY-2 and INV-44**: Add `ev14 -> INV-44` and `PAY-2 settles INV-44` provisionally.

This bundle keeps changes minimal but still creates a more coherent graph: ORD-B is invoiced, PK-8 is a two-item package, and DEL-Y is not an orphan.

### Bundle B — plausible alternative: group confirmation, but no cross-order package

- **ev08 and PK-8**: Do **not** add `ev08 -> PK-8` or `PK-8 packs IT-B1`. Interpret ev08 as an item-only scanner-outage row; IT-B1 remains unpacked because no later reconciliation event exists.
- **ev10 and DEL-X/DEL-Y**: Same as Bundle A: add `ev10 -> DEL-Y` and `DEL-Y carries PK-8`.
- **ev11 and delivery objects**: Tentatively add `ev11 -> DEL-X` and `ev11 -> DEL-Y` as a multi-delivery confirmation. ORD-A is represented in both DEL-X and DEL-Y through IT-A1 and IT-A2, so a portal confirmation keyed to ORD-A may cover both deliveries. This is over-repair if the portal only meant one delivery, but it yields complete delivery lifecycles.
- **INV-44 and ORD-B**: Same as Bundle A: add `ev12 -> ORD-B` and `INV-44 bills ORD-B`.
- **PAY-2 and INV-44**: Same as Bundle A: add `ev14 -> INV-44` and `PAY-2 settles INV-44`.

Bundle B is less conservative: it adds a speculative delivery confirmation but avoids forcing IT-B1 into PK-8. It produces incomplete fulfilment for ORD-B but more complete confirmation for deliveries.

## 5. Lifecycle and cardinality audit

For **Bundle A**:

- **Order**: ORD-A has Create Order, Add Item, Pack Item via PK-7/PK-8, Dispatch via DEL-X/DEL-Y, Confirm Delivery as observed, and Invoice via INV-44. ORD-B has Create Order, Add Item, Pack Item via PK-8, Dispatch via DEL-Y, and Invoice via INV-44. ORD-B has no delivery confirmation; this is acceptable because the confirmation event is unresolved.
- **Item**: IT-A1 and IT-A2 are packed and delivered. IT-B1 is packed into PK-8 only because of P2; if P2 is wrong, IT-B1 becomes an orphan. This is the weakest part of Bundle A.
- **Package**: PK-7 contains IT-A1 and is carried by DEL-X. PK-8 contains IT-A2 and IT-B1 and is carried by DEL-Y. PK-8 is a suspicious cross-order package because it mixes ORD-A and ORD-B items, but packing different orders together is not impossible.
- **Delivery**: DEL-X carries PK-7 and is dispatched at ev09. DEL-Y carries PK-8 and is dispatched at ev10. Neither delivery is explicitly confirmed because ev11 is left unresolved in Bundle A; this is incomplete but faithful.
- **Invoice**: INV-44 bills ORD-A and ORD-B. Both orders have `Issue Invoice` relations via ev12, so the invoice lifecycle is coherent if P3 is right.
- **Payment**: PAY-1 and PAY-2 both settle INV-44 in Bundle A. The invoice total equals the sum of payments, but this is still only evidence, not proof.

**Independence issue**: The O2O additions `DEL-Y carries PK-8`, `PK-8 packs IT-B1`, `INV-44 bills ORD-B`, and `PAY-2 settles INV-44` are not independent confirmations; they are derived from the corresponding E2O additions. I do not use them as independent support. The only independent double support in the log is for existing edges such as `ORD-A contains IT-A1`, supported by both ev03 and an O2O row.

## 6. Downstream process-mining effects

### Unrepaired log

- `ev08` relates only to IT-B1; `Pack Item` appears as an event with a dangling item.
- `ev10` relates to PK-8 but not to a Delivery, so `DEL-Y` never appears in the event log.
- `ev14` relates only to PAY-2, so `Record Payment` is disconnected from the invoice graph.
- `INV-44` is connected only to ORD-A, not ORD-B.
- Flattening on **Order** makes ORD-B artificially short: only Create Order, Add Item, and Pack Item.
- The **OTG** misses ItemPackage for IT-B1, PackageDelivery for PK-8, InvoiceOrder for ORD-B, and PaymentInvoice for PAY-2.

### Bundle A

- `PK-8` now has two `packs` edges, so the OTG contains a many-to-one fragment `IT-A2 -> PK-8 <- IT-B1`.
- `DEL-Y` now appears with a dispatch event, so the delivery flattening includes a complete dispatch for DEL-Y.
- ORD-B is connected to Invoice and Delivery, but also shares PK-8 with ORD-A. Order flattening therefore contains a cross-order object dependency: `ORD-A` and `ORD-B` both touch `PK-8`, which may duplicate package events in both order cases.
- Invoice flattening now includes both ORD-A and ORD-B creation and item activities because INV-44 bills both orders.
- Payment flattening now shows PAY-2 after `Record Payment`, connected to the invoice, so `Record Payment` can appear after `Issue Invoice` in the invoice case.

### Bundle B

- `ev08` remains item-only, so IT-B1 is not in any package; ORD-B flattening lacks delivery and package events.
- PK-8 remains single-order with respect to items: only IT-A2; no cross-order package is created.
- `ev11` is connected to both DEL-X and DEL-Y, so delivery flattening has a `Confirm Delivery` event after dispatch for both deliveries.
- The **OC-DFG** may show a confirmation edge from dispatch to confirm delivery only in Bundle B, not in Bundle A.
- Equivalent-execution clustering on Order will differ: Bundle A gives ORD-B and ORD-A a shared package and invoice fragment, but Bundle B keeps ORD-B separated from ORD-A at the package level while still sharing an invoice.

## 8. Over-repair warnings

1. **Uniquely assigning `ev11` to DEL-X or DEL-Y** would fabricate a delivery confirmation and make delivery flattening look more certain than the data allow. The wildcard `N-42*` is ambiguous.
2. **Treating `ev10` as a bulk dispatch to DEL-X** because of route and time would create a false many-to-one DeliveryPackage relationship while leaving DEL-Y unused.
3. **Adding `INV-44 bills ORD-B` solely from arithmetic equality** would ignore fees, discounts, taxes, and the possibility that the invoice includes amounts not represented as object attributes.
4. **Adding `PAY-2 settles INV-44` solely from payment-sum equality** would hide the possibility of unapplied cash and create a false fully-paid invoice state.
5. **Forcing `ev08 -> PK-8` to make IT-B1 delivered** would create a cross-order package that may not exist; a scanner outage is a valid alternative and should remain unresolved in one bundle.
6. **Inferring transitive O2O edges such as `DEL-Y carries ORD-B`** from package/item relationships would overstate direct event-object links and distort flattening.
7. **Using `pm4py.ocel_o2o_enrichment` as semantic validation** would multiply inferred edges without business-warranted qualifiers; it should only be used as graph enrichment, not as proof of actual order/delivery/invoice relations.
