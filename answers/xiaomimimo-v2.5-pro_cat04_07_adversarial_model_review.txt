A score of 4.4 vs. 1.9 might reflect evaluators' comfort with simple diagrams rather than their ability to correctly judge model behavior.

# 7. Third Alternative

## Design Rationale

The third model uses a **procedural backbone with a loop-based correction mechanism and declarative post-hoc constraints**. The design principles are:

1. **Mandatory checks are structurally non-skippable** (addresses S's permissive flaw)
2. **Check order is unconstrained** (addresses C's rigid ordering)
3. **Supplier Review is optional but post-hoc checkable** (acknowledges missing attribute)
4. **Expedite Review follows both checks** (enforces P4)
5. **Correction/recheck uses a loop with choice** (generalizes C's single correction branch)
6. **No branch enumeration** (addresses C's scalability problem)

## Formal Description

```
model_third =
  Register Dossier 
    LOOP(
      concurrent(Credit Check, Technical Review),      -- mandatory, either order
      Correct Dossier  XOR(                            -- correction step
        concurrent(Credit Check, Technical Review),     -- recheck both
        Credit Check,                                    -- recheck CC only
        Technical Review                                 -- recheck TR only
      )
    ) 
    concurrent(
      XOR(Supplier Review, ),                          -- optional
      XOR(Expedite Review, )                           -- optional
    ) 
    XOR(Manager Approval, Auto Approval) 
    Release Order
```

**LOOP(A, B) semantics:** Execute A, then either exit or execute B and repeat.

**Trace language pattern:**
```
Register,
[CC, TR in any order],
[CD  (CC|TR|CC,TR)]*,
[SR]?, [ER]?,
[MA|AA],
Release
```

The correction loop generates zero or more (CD  recheck) cycles. Each cycle requires at least one mandatory check to re-execute, enforcing the invariant that a correction always leads to a recheck.

## PM4Py Code

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
)

#  Activity transitions 
register = Transition(label='Register Dossier')
cc       = Transition(label='Credit Check')
tr       = Transition(label='Technical Review')
sr       = Transition(label='Supplier Review')
er       = Transition(label='Expedite Review')
cd       = Transition(label='Correct Dossier')
ma       = Transition(label='Manager Approval')
aa       = Transition(label='Auto Approval')
ro       = Transition(label='Release Order')

#  Mandatory checks: concurrent, either order 
checks = StrictPartialOrder(nodes=[cc, tr])
# No edges  fully concurrent

#  Recheck options (XOR: both, CC-only, TR-only) 
cc_r   = Transition(label='Credit Check')
tr_r   = Transition(label='Technical Review')
both_r = StrictPartialOrder(
    nodes=[Transition(label='Credit Check'),
           Transition(label='Technical Review')]
)

recheck = OperatorPOWL(
    operator=OperatorPOWL.XOR,
    children=[both_r, cc_r, tr_r]
)

#  Correction step: CD  recheck 
correction = StrictPartialOrder(nodes=[cd, recheck])
correction.order.add_edge(cd, recheck)

#  Correction loop: zero or more corrections 
tau_loop    = SilentTransition()
corr_loop   = OperatorPOWL(
    operator=OperatorPOWL.LOOP,
    children=[tau_loop, correction]
)

#  Checks phase: mandatory  optional corrections 
checks_phase = StrictPartialOrder(nodes=[checks, corr_loop])
checks_phase.order.add_edge(checks, corr_loop)

#  Optional reviews: concurrent, each optional 
tau_sr  = SilentTransition()
tau_er  = SilentTransition()

sup_opt = OperatorPOWL(operator=OperatorPOWL.XOR, children=[sr, tau_sr])
exp_opt = OperatorPOWL(operator=OperatorPOWL.XOR, children=[er, tau_er])

reviews = StrictPartialOrder(nodes=[sup_opt, exp_opt])
# No edges  concurrent

#  Approval: exactly one 
approval = OperatorPOWL(
    operator=OperatorPOWL.XOR,
    children=[ma, aa]
)

#  Main flow 
model_third = StrictPartialOrder(
    nodes=[register, checks_phase, reviews, approval, ro]
)
model_third.order.add_edge(register, checks_phase)
model_third.order.add_edge(checks_phase, reviews)
model_third.order.add_edge(reviews, approval)
model_third.order.add_edge(approval, ro)
```

## Explicit Semantics

| Requirement | How model_third handles it |
|---|---|
| **P1: Register first, Release last** | Structural edges enforce register  …  ro |
| **P2: Both mandatory checks, either order** | `StrictPartialOrder(nodes=[cc, tr])` with no edges = concurrent, both must fire |
| **P3: Supplier Review only for external** | `XOR(SR, )` makes it optional; DC1 activates when `source` attribute is available |
| **P4: Expedite after both checks, before approval** | Structural: `checks_phase  reviews  approval`; ER in `reviews` block |
| **P5: Exactly one approval** | `XOR(MA, AA)` |
| **P6: Correction  affected recheck** | Loop allows CD  {CC, TR, or both}; DC2 activates when `affected_check` attribute is available |
| **P7: Recheck without correction is suspicious** | Loop structure requires CD before any recheck; bare recheck incurs positive alignment cost |

## Limitations

1. **Correction always allows any recheck combination.** Without the `affected_check` attribute, the model cannot enforce that only the affected check repeats. The XOR in the correction body allows CC-only, TR-only, or both, which is a superset of the correct behavior. DC2 is the mitigation.

2. **Supplier Review is unconditionally optional.** Without the `source` attribute, external orders and internal orders are treated identically. DC1 is the mitigation, but it requires attribute availability.

3. **Duplicate labels remain (count: 4).** The correction body requires fresh transition objects with the same labels ("Credit Check" and "Technical Review") as the mandatory check phase. This is inherent to the POWL formalism for loop-based re-execution and is far fewer than Model C's 33.

4. **Loop generates infinite language.** The correction loop allows arbitrarily many correction cycles. While real processes rarely exceed 2–3 corrections, the model technically accepts unlimited corrections. Alignment algorithms handle this correctly, but playout will produce some implausibly long traces.

5. **No intra-review ordering constraint.** The model allows SR and ER concurrently (any order). If policy requires one before the other in specific cases, this would need DC constraints.

## 9.4 Perturbation Tests

```python
def perturb_remove(trace, fraction=0.15, seed=42):
    """Remove random non-structural events from a trace."""
    rng = np.random.RandomState(seed)
    protected = {'Register Dossier', 'Manager Approval', 'Auto Approval', 'Release Order'}
    removable = [i for i, e in enumerate(trace) if e['concept:name'] not in protected]
    n_remove = max(1, int(len(removable) * fraction))
    to_remove = set(rng.choice(removable, min(n_remove, len(removable)), replace=False))
    return Trace([e for i, e in enumerate(trace) if i not in to_remove])

def perturb_duplicate(trace, n_add=1, seed=42):
    """Add random duplicate events."""
    rng = np.random.RandomState(seed)
    result = Trace(list(trace))
    for _ in range(n_add):
        idx = rng.randint(0, len(trace))
        result.append(Event(dict(trace[idx])))
    return result

# Apply perturbations to holdout
holdout_remove = EventLog([perturb_remove(t, seed=i) for i, t in enumerate(holdout_log)])
holdout_duplicate = EventLog([perturb_duplicate(t, seed=i) for i, t in enumerate(holdout_log)])

for model, label in [(model_s, "S"), (model_c, "C"), (model_third, "Third")]:
    net, im, fm = pm4py.convert_to_petri_net(model)
    f_orig = pm4py.fitness_alignments(holdout_log, net, im, fm)['log_fitness']
    f_rem  = pm4py.fitness_alignments(holdout_remove, net, im, fm)['log_fitness']
    f_dup  = pm4py.fitness_alignments(holdout_duplicate, net, im, fm)['log_fitness']
    print(f"{label}: orig={f_orig:.3f}, remove={f_rem:.3f}, duplicate={f_dup:.3f}")
    print(f"  Sensitivity to removal:  {f_orig - f_rem:+.3f}")
    print(f"  Sensitivity to duplication: {f_orig - f_dup:+.3f}")
```

## 9.9 Decision Rule for Model Rejection

A model is **rejected despite good aggregate metrics** if ANY of the following hold:

1. **Safety violation:** The model accepts any trace in the curated negative suite (rejection rate < 100%).
2. **Behavioral probe failure:** The model rejects any probe marked "valid" (B1, B2, B5, B7) or accepts any probe marked "forbidden" (B3, B4, B8).
3. **Holdout fitness collapse:** Holdout fitness < 0.80, indicating the model cannot accommodate a significant fraction of observed behavior.
4. **Perturbation fragility:** Fitness drops by >0.15 when 15% of non-structural events are removed, indicating the model depends on data artifacts.
5. **Soundness failure:** The Petri net is not sound (proper completion not guaranteed, dead transitions exist).
6. **Comprehension failure:** Stakeholder comprehension < 3.0/5.0 with structured protocol.

# 11. Dissenting View

## Rebuttal (210 words)

The third model's loop-based correction mechanism is elegant in theory but potentially problematic in practice. By using `LOOP(tau, correction_step)`, the model generates an *infinite* language of correction sequences—arbitrarily many correction cycles, each with three recheck options. While alignment algorithms can handle this mathematically, the model provides no guidance on *how many* corrections are plausible or *which* recheck option is appropriate in a given context. A model that accepts a trace with ten consecutive corrections is not meaningfully more correct than one that accepts zero.

Furthermore, the mandatory-checks-first, then-corrections, then-reviews sequential structure imposes an ordering constraint that may not reflect reality. In practice, Supplier Review might be initiated before corrections are finalized—perhaps as a parallel workstream. The third model's rigid phasic structure would reject such traces, potentially penalizing efficient process execution.

The heavy reliance on inactive declarative constraints (DC1, DC2) is also concerning. These constraints are essentially placeholders—they provide no current enforcement value. Deploying the model without them means the same Supplier Review gap that exists in Model S persists in the third model, dressed up in more sophisticated notation.

Finally, the four duplicate labels—though fewer than Model C's 33—still introduce alignment ambiguity. A Petri-net-native representation with explicit place labels would be cleaner.

## Evidence That Would Change My Decision

I would revise my recommendation if:

1. **Stakeholder interviews** reveal that the phasic structure (checks  corrections  reviews  approval) does not reflect how work actually flows, and that reviews frequently overlap with correction cycles. This would require restructuring the model to allow concurrent correction and review.

2. **The holdout set** contains a significant proportion (>15%) of traces where Supplier Review precedes the final correction, suggesting the sequential ordering is empirically wrong.

3. **A simpler model** (e.g., a Declare/constraint-based model without procedural backbone) achieves comparable negative-trace rejection while scoring higher on stakeholder comprehension. The procedural backbone's value depends on stakeholder preference for explicit flow vs. implicit rules.

4. **Alignment experiments** show that the LOOP(tau, correction) pattern causes numerical instability or excessive runtime on long traces, making the model impractical for the deployment context.

5. **The negative trace suite** reveals that the third model accepts a forbidden behavior I haven't anticipated, indicating a structural flaw in the backbone rather than a missing constraint.
