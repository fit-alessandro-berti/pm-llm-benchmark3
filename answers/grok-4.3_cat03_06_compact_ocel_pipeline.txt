**## 1. Modeling assumptions**

- Object types (capitalized exactly): Order, Item, Package, Delivery, Invoice, Payment.
- E2O qualifier vocabulary (consistent, meaningful): contains, packs, carries, bills, settles, confirms, issues.
- O2O direction conventions: source  target (Order contains Item; Package packs Item; Delivery carries Package; Invoice bills Order; Payment settles Invoice).
- Logistics events (Pack, Dispatch, Confirm Delivery) receive direct E2O to the primary operational objects (Package, Delivery, and the Orders/Items they involve). Financial events (Issue Invoice, Record Payment) receive direct E2O to Invoice and the Orders they affect. Item-level relations are kept only where the event is explicitly operational on the Item (e.g., Add Item, Pack). Shared events (Reserve Stock, Pack P1) receive multiple E2O rows.
- Analytical relation propagation is prevented from being confused with source facts by (a) recording only direct, source-system relations in the E2O table and (b) letting downstream algorithms (flattening, OC-DFG) compute derived involvement via O2O. No “analytical” rows are inserted into relations.
- Version-dependent PM4Py assumption: the constructor `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available (PM4Py  2.7). If an older version is used, replace with `pm4py.ocel_import_sample()` style or the `OCEL` class from `pm4py.objects.ocel.obj`.

**## 3. Data-model audit**

Object types & instances: Order (O100, O200), Item (I1–I3), Package (P1, P2), Delivery (D1, D2), Invoice (V1), Payment (M1, M2).

O2O qualifiers & cardinality: contains (OrderItem, 1:N), packs (PackageItem, 1:N), carries (DeliveryPackage, 1:1), bills (InvoiceOrder, 1:N), settles (PaymentInvoice, N:1).

Activities vs. touched object types (selected):
- Create Order / Close Order  Order
- Add Item  Order, Item
- Reserve Stock / Pack Package  Order, Item, Package
- Dispatch Package  Package, Delivery
- Issue Invoice  Invoice, Order
- Record Payment  Invoice, Payment
- Confirm Delivery  Delivery

Consequential event: e7 (Pack Package P1) – touches both O100 and O200 simultaneously, creating convergence.

**## 4. Expected flattened behavior**

Order flattening yields two traces (O100, O200) that duplicate e6, e7, e11. Shared events appear in both traces; DFG edges include “Reserve Stock  Pack Package” twice. Lifecycle aspects after the last Order-specific event are omitted.

Package flattening produces two short traces (P1, P2) that copy the downstream Confirm Delivery events. DFG edges are “Pack Package  Dispatch Package  Confirm Delivery”. Misleading interpretation: Payments appear unrelated.

Delivery flattening yields two traces ending with Confirm Delivery; Invoice events are dropped.

Invoice flattening produces a single trace that merges both Orders’ lifecycle and both payments. Duplicate shared events are visible; payment allocation remains ambiguous.

Payment flattening is weak: each Payment object has only two events (Record Payment + implicit settlement), losing all upstream process context.

**## 5. Expected object-centric structures**

OC-DFG shows P1 as a convergence point linking O100 and O200; V1 as a synchronization point for M1/M2. OTG highlights Order–Item–Package–Delivery chain and the separate financial Invoice–Payment subgraph. ET–OT graph marks “Pack Package” and “Issue Invoice” as high-degree activities. The object-centric Petri net contains two parallel subnets (logistics vs. finance) joined at V1. Object-interactions summary explicitly lists the P1–O100/O200 and V1–M1/M2 interactions.

**## 6. Modeling alternatives**

- Source-minimal relations: only the minimal E2O rows that created each object. Discovery loses shared-event visibility; OC-DFG becomes disconnected.
- Full operational involvement: every downstream event receives E2O rows to all involved Orders/Items. Relation table inflates; flattening duplicates explode.
- O2O-propagated analytical relations: insert derived E2O rows via O2O traversal. Source facts become indistinguishable from computed facts; object-centric Petri net gains spurious arcs.

**## 7. Failure modes**

- Relation inflation from shared events (e6, e7).
- Missing direct E2O links for Confirm Delivery  Order.
- Treating O2O propagation as observation (false “M1 contains I1”).
- Duplicate shared events after flattening (e7 appears twice in Order log).
- Ambiguous payment allocation (M1/M2 amounts not linked to specific Orders).
- Overly short Payment traces (only two events).
- Constructor/API version mismatch (OCEL keyword arguments).
- False total order for same-time events (none present, but risk remains).

**## 8. Final semantic checks**

- e7 has three relations (P1, O100, O200) with correct qualifiers.
- V1 appears in exactly two O2O “bills” rows.
- M1 and M2 both have “settles” qualifier to V1.
- No relation row references a non-existent eid/oid.
- All timestamps in relations match the events table.
- O100–I3 link exists only via P1 (O2O), never directly in E2O.
