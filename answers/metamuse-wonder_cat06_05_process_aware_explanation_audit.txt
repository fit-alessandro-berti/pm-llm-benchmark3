## 1. Leakage and temporal-consistency findings

Finding types distinguish: **Unavailable-at-`t0`** = temporal leakage; **Process-inconsistent** = cannot occur as ordered in the normative process; **Point-in-time incorrect** = mutable / as-of-date lineage defect; **Valid at `t0` - non-causal** = may predict but must not be narrated as cause/action lever; **Legitimate prefix signal** = derivable from `Claim Registered -> Coverage Check Completed` and timestamps at `t0`.

## 2. Process-model consistency checks

Build a validation suite that runs over (a) raw events, (b) feature-generation code, and (c) every generated explanation, with failure severities matching Section 1.

**1. Prefix-time availability (point-in-time audit)**
- Reconstruct for each case the event prefix up to and including the first `Coverage Check Completed`, using timestamp **plus** reliable sequence index. Freeze this as the only admissible input at `t0`.
- For every feature, require metadata: `event_time`, `recorded_at / available_at`, transformation window, and as-of join keys. Automated test: recompute the feature from the truncated prefix and assert equality with the production value. Any mismatch = leakage or lineage bug. This test catches `total_case_duration_hours`, `appeal_seen_anywhere`, totals, full-trace variant, nightly snapshots and extraction-date joins.
- Adversarial unit tests: append synthetic future events (appeal, extra document request, later prior claim, document uploaded at 22:00) and assert `t0` features do not change. Shift extraction date and assert no change.
- Check mutable fields (`risk_score`, reserve, handler team, employee experience) for historical/effective-dated versions; absence of an as-of timestamp is itself a failure.

**2. Activity-order feasibility against the normative model**
- Encode normative rules, e.g.: `Claim Closed` only after a final `Settlement Decision Recorded` or Withdrawn; a second Damage/Decision ordering as per steps 3-6; `Documents Received` only after an outstanding `Documents Requested`; `Documents Validated` only after Received; `Appeal` only after Partial/Deny; `Settlement Decision` only after Damage Assessment.
- Use **declarative constraints** (Declare-style response/precedence/not-coexistence rules) for normative prohibitions, **alignment-based conformance** against a normative Petri net / BPMN model to locate insertions, skips and swapped events in traces, and a **footprint / directly-follows check** as a screening tool. Role and limits: a DFG is descriptive - a frequent DFG edge is *not* automatically a normative rule (it may encode the same timestamp bug at scale), and an infrequent edge is not automatically invalid (appeal paths are rare but legal). Alignments show *where* a trace deviates but not whether the cause is process violation, logging order, or a wrong normative model; deviations need triage, not automatic deletion.
- Apply to explanations as well as data: any explanation pattern violating a precedence rule is rejected outright, e.g. `Claim Closed -> Damage Assessment Completed`.

**3. Same-timestamp ambiguity**
- Detect event groups with identical timestamps within a case. If a reliable sequence index exists, use it and log provenance; if missing (Case Z), mark the group **unordered**: exclude directly-follows patterns spanning the tie, flag affected features, and run sensitivity analysis over permissible orderings. Never let ingestion order silently become process order.
- Report tie rate by activity pair and source system as a data-quality metric; pairs like Closed/Damage with high tie rates indicate clock granularity or batch-loading problems.

**4. Complete-trace information detection**
- Static lineage scan: flag feature SQL/code referencing whole-case aggregates (`total`, `anywhere`, `final`, `last`, `full_trace`, `MAX/MIN over case`, windows without `<= t0` bounds).
- Dynamic test: the prefix-recomputation and future-appending tests above. A feature that changes when the future changes fails, regardless of how plausible its name sounds. This also catches subtle cases such as `prior_claim_count` using extraction date.

**5. Enabled / impossible / future-possible classification at `t0`**
For each activity referenced by a feature or pattern, classify relative to the normative model given prefix `Registered -> Coverage Check Completed`:
- **Enabled now**: Damage Assessment Completed (fast track), Documents Requested (evidence track), possibly Fraud Investigation Opened if a trigger condition is documented at/before `t0`.
- **Future-possible but not yet enabled/known**: further document cycles, Fraud Investigation (absent trigger yet), Settlement Decision, Appeal (conditional on a future Partial/Deny), second Settlement Decision, Claim Closed. These may appear in scenario discussion but never as observed drivers at `t0`.
- **Impossible as ordered / not enabled in any continuation from this state as a next step**: Appeal before any Partial/Deny, Claim Closed before a final decision, Documents Received/Validated before Requested, Settlement Decision before Damage Assessment, and `Claim Closed -> Damage Assessment Completed` in any order-compliant trace.
Gate: explanations may only cite observed prefix facts and `t0` context. Future-possible activities can be mentioned only as unobserved possibilities with uncertainty, not contributions.

**6. Repeated Settlement Decision semantics**
- Validate by decision *values*, not just the coarse label: a second `Settlement Decision Recorded` is legitimate **only if** preceded by an Appeal which itself follows a Partial or Deny decision. Count of decisions >1 without that chain = conformance exception; count =1 after appeal with no new decision may be an incomplete trace.
- Feature engineering must keep decision ordinal and value (`decision_1_value`, `post_appeal_decision_value`) rather than collapsing to "decision seen", which would falsely make legitimate and impossible repetitions indistinguishable.
- In conformance testing, expect appeal-reconsideration traces to align without penalty; do not let a simplistic "each activity once" assumption flag them.

**7. Explanation-level gates**
- Every local/global explanation passes: all cited features prefix-recomputable; all cited patterns order-feasible; no cited activity classified impossible; causal verbs ("causes", "determines", "driver", "reduces uncertainty") blocked unless a separate causal study supports them.

## 3. Alternative feature interpretations

**Defensible predictive signals** - e.g. frozen `initial_damage_complexity`, `elapsed_since_registration_at_t0` (prefix age / consumed slack), `initial_reserve_at_registration` once its as-of lineage is verified, and `claimant_channel` once verified as recorded at registration.
- *May claim*: associated with higher/lower predicted breach risk at `t0` in this model and population; useful for triage/prioritisation under monitoring.
- *May not claim*: that intervening on the recorded value (e.g. relabelling complexity, changing reserve) reduces breach risk; SHAP magnitude is model reliance, not effect size.

**Process-state or congestion signals** - e.g. `queue_length_at_t0` (snapshot-verified), and legitimately, prefix state at `t0`: fast-track vs evidence-track eligibility if determined by `t0`, time already elapsed.
- *May claim*: claims arriving into a congested system state carry higher predicted risk; this supports operational hypotheses about resourcing and queue management to be tested operationally.
- *May not claim*: that this claimant's queue position caused their outcome, or quote a per-case causal effect. Congestion effects need queue-level / natural-experiment evidence; individual attribution from SHAP is an ecological fallacy risk.

**Proxies requiring fairness/robustness review** - e.g. `claimant_region`, `claimant_channel` (Broker), and possibly reserve/complexity if they encode socioeconomic or regional factors.
- *May claim*: predictive association survives (or not) specified robustness checks; retention is a governed decision weighing accuracy, legality, fairness metrics across groups, and availability of direct operational alternatives (repair-network capacity, language-support need, document completeness at `t0`).
- *May not claim*: "region is a delay driver" or any causal/essentialist story; nor use for adverse individual action without fairness review. Correlation alone is not grounds for automatic deletion - deleting a proxy while correlated features remain may hide rather than remove disparity - but it shifts the burden to documented review and monitoring.

**Drift/calendar proxies** - e.g. `calendar_week`, especially weeks aligned with policy change and holidays.
- *May claim*: risk differed in those regimes in training data; signal may help short-term forecasting while the regime persists.
- *May not claim*: a stable seasonal law or actionable "bad week" explanation. Require time-based validation, explicit regime/holiday covariates known at `t0`, and drift monitoring; expect degradation after policy change.

**Unusable until lineage is repaired** - e.g. current `prior_claim_count_before_t0` (extraction-date SQL), `same_day_document_count_snapshot` (nightly intraday leak), `final_handler_team` (no as-of history), `risk_score_current` (no computed-at timestamp), extraction-date employee experience, `initial_reserve` if only a current value exists.
- *May claim*: nothing from current values/contributions, in either direction.
- *May not claim*: that repair will preserve sign or importance; after point-in-time repair each must be revalidated, retrained and re-explained from scratch.

Explicitly **not surviving in any class** at `t0`: total duration, appeal anywhere, total document requests, full-trace variant, final decision, last resource role, and all complete-trace sequence patterns.

Four different standards apply throughout: **predictive validity** (prefix-available, stable out-of-time association), **causal interpretation** (requires design/assumptions beyond SHAP: confounding control, temporal order, no post-treatment variables), **operational actionability** (a lever someone can pull at `t0`, e.g. queue resourcing - not relabelling region/complexity), and **fairness review** (disparate impact and proxy legality even for predictively valid features). Passing one standard does not imply passing the others.

## 5. Recommendations for explanation validation

**Priority 0 - stop the leak (immediate)**
1. Withdraw the current global ranking, the 0.82/0.71/0.64 explanations, and any stakeholder material using causal verbs for them. Declare the model "not valid at `t0`" until rescored.
2. Freeze a prefix-only feature set for the Coverage-Check prediction time; blacklist complete-trace patterns (`total`, `final`, `last`, `anywhere`, `full_trace`, closure-derived) in feature review.

**Priority 1 - feature-store and point-in-time design**
3. Event-sourced feature store: every feature carries `event_time`, `recorded_at/available_at`, entity, transformation version, sequence-index provenance, and as-of join semantics. Late-arriving and corrected data are handled by `available_at`, not extraction date.
4. Historical feature timestamps for all mutable fields: risk scores (with model version), reserves, handler team, employee experience, queue snapshots. Point-in-time joins enforced as `available_at <= t0` in code, not convention.
5. Prefix-only recomputation harness in CI: truncate traces at each supported prediction time (starting with post-Coverage Check), recompute features, and diff against production; add the future-appending and extraction-date-shift adversarial tests from Section 2. Build pre-merge on feature SQL.

**Priority 2 - process conformance in the loop**
6. Implement the Section 2 suite: declarative normative constraints, alignment checks for diagnosis, DFG only as descriptive screening, same-timestamp tie reporting, and the enabled/impossible/future-possible gate applied to features *and* generated explanation text. Handle repeat Settlement Decisions by decision value and appeal precondition so legitimate reconsiderations pass.
7. Explanation linter: reject explanations citing impossible patterns, future activities as observed facts, or banned causal phrasing without a linked causal study.

**Priority 3 - revalidation after removal**
8. Calibration after feature removal: retrain leakage-free, then re-evaluate on **time-based** splits - discrimination, calibration curves/intercept/slope, and decision-curve impact at the operating threshold. Expect performance to drop; report the honest drop rather than tuning to recover leaked performance. Recheck SHAP on the new model only.
9. Explanation stability: bootstrap and seed-stability of rankings, stability under the ±5-minute queue tolerance and under permissible same-timestamp orderings, and agreement between explanation methods. Unstable local narratives are reported with uncertainty or suppressed.

**Priority 4 - proxy, fairness and drift governance**
10. Proxy/fairness analysis for region, channel, reserve and complexity: performance and calibration by group, disparate-impact assessment, comparison against models using direct operational variables, documented retention/removal decision with legal review. Predictive validity alone does not settle retention.
11. Monitoring for schema and process drift: schema changes in warehouse fields (e.g. handler team semantics), tie-rate and conformance-violation rate, variant distribution, policy-regime/holiday calendar effects, feature freshness, and population drift. Alert when a feature's `available_at` distribution shifts or new activity labels/paths appear; re-run the full leakage and conformance suite on any schema, policy, or process change, with sign-off recorded in a model/explanation changelog.
