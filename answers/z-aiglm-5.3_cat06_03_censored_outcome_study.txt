**## 1. Target definition**

Primary:
- Unit: one application case (case:concept:name).
- Prediction time : landmark — completion timestamp of the case's first Credit Review event (all applications pass it); input = event prefix strictly at/before . Two sanctioned variants for robustness: fixed-count (first 5 events) and elapsed-time (72h after Application Started); primary = landmark because it aligns the information set across cases to the same process stage and is robust to doc loops that inflate event counts.
- Population (estimation): applications started in 2024-01-01..2025-12-31 that reached , activated on the home platform, and whose 90-day label was available by the extraction date. (Inference/deployment population: in-flight applications that will be activated.)
- Horizon: default within 90 days after Account Activated (stored default_90d definition).
- Estimand: (x) = P(Default90 = 1 | X() = x, Activated = 1, label observed) — a conditional-on-activation (post-selection) estimand. Explicit semantics: it is the early-warning risk of the account that this application becomes, given that it does get activated under the current policy; NOT the marginal risk that an arbitrary applicant defaults, and not a counterfactual under a different approval policy. Because activation happens after , the score is used (i) inside the credit workflow as a warning to reviewers of to-be-funded accounts and (ii) as stage 2 of a cascade behind an activation/approval model; any single-number "portfolio default risk" requires combining with P(activated | prefix).

Alternative targets:
- A. Multi-state / competing-outcome target for all applications reaching : predict the distribution over terminal states {Activateddefault, Activatedno-default (or censored), Rejected, Withdrawn, Transferred, Open}. Answers a different question ("what will happen to this application" — funnel/ops planning, workload forecasting, withdraw-intervention), well-defined for every case, but mixes credit-policy effects with borrower risk and cannot be read as default risk.
- B. Time-to-default after activation with right censoring: discrete-time hazard within 90 days; answers "when, and with what probability, given partial follow-up," uses the 3,600 censored accounts instead of discarding them; recommended as the sensitivity/robustness layer (and eventually the production form).
- C. Policy-counterfactual ("default risk if approved") for all applicants incl. rejected/withdrawn: requires consistency, positivity, activation selection on observables, no interference — mostly untestable here; excluded as primary; only scenario analysis under explicit assumptions.

Why primary defensible: label is well-defined and observed on the estimation population without fabricating outcomes; attaches to the actual loss event (funded account default); matured-label restriction makes estimand = estimable quantity; conditioning is declared rather than hidden; rejects naive "everyone non-default" framing.

## 1. Target definition

**Primary target (selected).**

- **Unit of analysis:** one application case (`case:concept:name`).
- **Prediction time :** a *landmark* — the completion timestamp of the case's first `Credit Review` event. The model input is the event prefix strictly at or before  (typically `Application Started`, `Identity/KYC Check`, possibly document requests, first `Credit Review`). Two sanctioned variants for robustness: fixed event-count prefixes (first 5 events) and elapsed-time prefixes (72 h after case start); the landmark is primary because it aligns the information set across cases to the same process stage and is robust to document loops that inflate event counts.
- **Horizon:** default within 90 days after `Account Activated` (the stored `default_90d` definition).
- **Population (estimation):** applications started 2024-01-01…2025-12-31 that reached , were activated on the home platform, and whose label was available by the extraction date. Deployment/inference population: in-flight applications that will be activated.
- **Estimand:** (x) = P(Default = 1 | X() = x, Activated = 1, label observed). This is explicitly a **conditional-on-activation (post-selection) estimand**: the early-warning risk of the account this application *becomes*, given that it is funded under the current policy. It is **not** the marginal risk that an arbitrary applicant defaults, and **not** a counterfactual under a different approval policy. Because activation occurs after , the score must be used either (i) inside the review/monitoring workflow as a warning on to-be-funded accounts, or (ii) as stage 2 of a cascade behind a stage-1 activation/approval model; any portfolio-level default number requires multiplying by P(activated | prefix).

**Why this is defensible:** the label is well-defined and actually observed on the estimation population (no fabricated outcomes); the loss event attaches to funded accounts, matching the business use; the matured-label restriction makes the estimand equal to the estimable quantity; and the conditioning is *declared* rather than hidden.

**Credible alternatives (different questions):**

- **A. Multi-state / competing-outcome target for all applications reaching :** predict the distribution over {Activated  default, Activated  non-default, Rejected, Withdrawn, Transferred, Open}. Well-defined for every case; answers "what will happen to this application" (funnel forecasting, withdrawal intervention, workload planning) — but it mixes credit-policy effects with borrower risk and must not be read as default risk.
- **B. Time-to-default with right censoring (post-activation):** discrete-time hazard within 90 days; uses the 3,600 censored activated accounts instead of discarding them; answers "when, and with what probability, given partial follow-up." Recommended as the robustness layer (S1 below) and eventually the production form.
- **C. Policy-counterfactual "default risk if approved" for all applicants:** requires consistency, positivity, activation-selection-on-observables, and no interference — largely untestable here. Excluded as primary; only scenario analysis under explicit assumptions.

**Explicitly rejected:** the informal framing that rejected/withdrawn/open applications are "non-default." Rejected applicants were never exposed to credit; their outcome is *undefined under the observed policy*, not zero. Labeling them non-default would dilute the base rate (2,700/48,000  5.6%) and — worse — teach the model the approval policy rather than default risk.

## 3. Censoring and missing-label strategy

**Mechanisms, kept distinct:**

1. **Ordinary right censoring.** (a) *Process censoring:* the 5,100 open cases, censored mid-process at extraction. (b) *Horizon censoring:* activated cases with `horizon_end >` extraction. Administrative to the extent censoring depends only on calendar; checkable: open-status should track start date with no residual association with prefix features within start-month strata.
2. **Delayed labels.** Horizon matured but the feed arrives 7–35 days later; this is *not* censoring of the outcome but of the *observation* of the outcome. Testable from the distribution of (`label_available_at  horizon_end`) on labeled rows; determines the guaranteed-maturity threshold; also check delay-vs-outcome independence within labeled data.
3. **Selection through activation.** The 22,800 never-activated cases are not "labels missing at random"; the outcome is undefined for them under the observed policy. The primary estimand *conditions* on activation instead of pretending to marginalize. Any all-application statement needs P(activated|X) reweighting under selection-on-observables — an untestable assumption.
4. **Transfer as competing event / missing follow-up.** Pre-activation transfer is a clean competing outcome for the primary target. Cross-platform default follow-up exists only via the ~60% linkage table, and linkage is plausibly non-random (partner, region, amount)  informative missingness. Partially testable: compare linked vs unlinked transfers on pre-transfer features.
5. **Permanently missing outcome feed (partner-originated).** Missingness depends on platform, plausibly on the outcome itself  MNAR. Not directly testable; the stratum is at least *observable* via `source_system`, enabling pattern-mixture sensitivity.

**Primary analysis strategy.** Landmark complete-case analysis on **guaranteed-matured, labeled, activated** accounts with **temporal (out-of-time) validation**, and the conditional estimand declared on every report. Censoring and feed delay are handled by the guaranteed-maturity exclusion rule (valid for the conditional estimand when maturity depends only on activation date — administrative; verified via the delay model), not by imputation. Selection is not "corrected"; it is conditioned upon and made explicit. Calibration is a first-class output, monitored per policy period and per subgroup.

**Sensitivity analyses.**
- **S1 (censoring):** discrete-time hazard / survival model on all activated cases, right-censoring at extraction; IPCW Brier, time-dependent AUC at 30/60/90 d; check that the 90-day cumulative-incidence calibration agrees with the binary model.
- **S2 (MNAR feed):** delta-adjustment / tipping-point on the `activated_feed_missing` stratum (impute default at 0.5×, 1×, 2× the observed partner-originated rate); report ranking and calibration stability.
- **S3 (selection):** IPW projection to the reached- population via a P(activated|X) model — labeled a *policy projection*, not a validated fact.
- **S4 (transfer):** re-run including outcomes of linked transferred cases; assess stability.
- **S5 (maturity threshold):** repeat with 7/14/35-day feed-delay assumptions.

**Assumption audit.**
- *Testable:* feed-delay distribution and its outcome-independence; duplicate/renaming artifacts; covariate and DFG drift across the policy date; open-case rate vs calendar; reconciliation with the warehouse export; internal consistency (default  `Default Recorded` within horizon).
- *Partially testable:* MAR of the missing feed given `source_system` and covariates (dependence on observables detectable; dependence on the unobserved outcome not); representativeness of linked transfers; censoring ignorability within start-month strata.
- *Fundamentally untestable:* MNAR feed missingness; activation-selection ignorability (unobserved creditworthiness drives both decision and default); counterfactual outcomes of rejected/withdrawn applicants; SUTVA/no interference for any policy extrapolation.

## 4. Prefix extraction

- **Primary (landmark):** prefix = all events with `time:timestamp  ` ( = first `Credit Review` completion). Events sharing 's timestamp are included; deterministic tie-breaking via stable sort on (timestamp, activity). Hard rule, enforced in code: no event with timestamp >  can enter features; post- fields live only in the outcome table.
- **Fixed event-count variant (k = 5, sensitivity k  {3,5,7}):** first k events, demonstrated with `pm4py.get_prefixes_from_log`. **Short cases** (terminal or  reached with < k events — mostly rejected/withdrawn, i.e., the multi-state alternative's population) are kept with a `prefix_len` flag, never padded and never extended with post- events; the flag itself is a feature. Where the helper drops short traces, the landmark table retains them — the discrepancy is reported.
- **Elapsed-time variant ( = 72 h):** all events  `case_start + `, with a minimum-process condition ( 1 `Credit Review`); otherwise **prediction is deferred and the deferral rate is reported** — deferral correlates with workload and is itself a censoring mechanism on decisions.
- **Document loops:** never deduplicated — rework is signal. Counts (`n_doc_requests`, returns to `Credit Review`), loop durations, and time-in-loop are features. Under fixed-k prefixes, loops consume the event budget; therefore `prefix_len` and variant are included and landmark vs fixed-k conclusions are compared.
- **Renaming and duplicates (migration, 2025-10-15):** a canonical activity mapping from the migration runbook is applied *before* any prefix/variant/DFG computation, verified by the activity-frequency discontinuity at the migration date. Duplicates: exact-duplicate removal on (case, activity, timestamp, resource), plus a near-duplicate rule (same case/activity/resource within 60 s, applied especially post-migration); counts removed are reported.

## 5. Process-aware features

| Class | Features (all as-of ) |
|---|---|
| **Static case attributes** | `case:channel`, `case:region`, `case:requested_amount`, initial `risk_score` (value at first event). `source_system` retained as subgroup/audit variable only (indexes the MNAR feed mechanism). |
| **Prefix-derived — control flow** | activity counts (KYC, Credit Review, Request Documents), distinct activities, last activity, variant label (via `get_variants` on the *prefix* log), `prefix_len`, presence of doc loop |
| **Prefix-derived — timing** | time startKYC, KYCCredit Review, cumulative prefix duration, mean/max inter-event gap; waiting-time from `insert_case_service_waiting_time` on the prefix log (caveat: with instantaneous events, service time degenerates to ~0 and is dropped; queueing/waiting time is interpretable) |
| **Prefix-derived — resource/queue** | distinct resources, handoff count, queue wait before Credit Review |
| **Prefix-derived — rework** | document-request loop count, returns to Credit Review, self-loop edge frequencies from the prefix DFG, repeated-activity ratio |
| **Prefix-derived — as-of dynamics** | `risk_score` at last event  ,  vs first value, number of updates within prefix |
| **Cohort / calendar** | start month/weekday, policy-period flag and days-since-policy-change, holiday proximity — known calendar facts, not leakage |
| **Historical reference (as-of valid: computed from *other* cases' events  )** | resource's open-case load at ; resource experience **repaired** as cumulative cases completed by that resource up to  (replacing extraction-time experience); regional application volume in trailing 7/28 days; median activity durations from cases closed before ; frequency of the prefix's DFG edges under the training reference DFG |

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final credit decision; post- and reveals the accept decision (a mediator of the estimand) | Only in a post-decision model; never at  | **Drop** (early warning) | Lets the model read the decision, collapsing the conditional estimand into decision leakage |
| `decision_reason` | At/after Accept/Reject; encodes the terminal path | Never before the terminal event | **Drop** at  | Direct outcome-path proxy |
| `collection_status` | Updated post-activation; directly reveals default | Never as a feature | **Drop everywhere** | Label proxy; pure leakage |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | Post- events define or mediate the outcome; activation is the selection event itself | Event timestamp   | **Prevent** via hard truncation + assertion | Classic prefix-leakage; must not enter stage-2 features |
| `documents_total` (nightly snapshot) | Same-day uploads *after*  are included | Recompute as the count of document events with event timestamp   | **Repair** (event-sourced count) | Snapshot semantics violate point-in-time; the event stream is authoritative |
| Updated `risk_score` | Later revisions may embed decision/outcome information | Last non-null value at an event   (plus first value and update count within prefix) | **Repair** (as-of value) | Preserves the informative dynamics without future revisions |
| Resource experience (at extraction) | Computed 2026-02 for 2024–25 events: future information at event time; also encodes calendar position (policy/migration period) | Cumulative cases completed by the resource with completion time   | **Repair** (as-of cumulative count); else drop | Attribute-time inconsistency, not label leakage, but biasing |
| `default_90d`, `label_available_at`, `data_extract_time` | The label and its plumbing | Label only in the outcome table, gated by `label_available_at ` extraction and the maturity rule | **Keep as gated label/metadata only** | Label leakage and maturity bias |
| Variants / DFG / temporal features on the **full** log | Full-case durations and control flow include post- events | Compute only on the truncated prefix log | **Repair** | The most common PPM leakage; explicitly guarded in the skeleton |
| `source_system` | Correlates with feed missingness (MNAR) and platform policy | Known at case start | **Keep as subgroup/audit variable; exclude from primary features** | Prevents learning missingness artifacts; needed to stratify S2/S3 |
| Post-migration duplicate events | Bias (not leakage): inflates counts, corrupts variants, shifts fixed-k prefixes | Dedup (exact + 60 s near-duplicate) before prefixing | **Repair** | Otherwise prefix features change meaning after 2025-10-15 |
| Terminal outcome used to form the activated cohort | Selection, not feature leakage — but it silently changes the estimand | Explicit conditional-estimand declaration + stage-1 activation model | **Keep with declaration** | The conditioning must be visible in every report |

## 7. Validation design

**Temporal split by case start time (never random):**

| Split | Case start window | Notes |
|---|---|---|
| Train | 2024-01-01 – 2025-03-31 | Fully matured labels; includes pre-policy regime |
| Validation (tuning, thresholds, calibration fit) | 2025-04-01 – 2025-06-30 | Pre-policy, fully matured (activation by ~Jul, feed by ~Nov  extraction) |
| Test A (post-policy) | 2025-07-01 – 2025-10-14 | Evaluate on guaranteed-mature rows (activation  2025-10-13); report coverage; censoring-adjusted (IPCW) metrics for the remainder |
| Test B (post-migration) | 2025-10-15 – 2025-12-31 | Labels mostly immature  partial, censoring-adjusted evaluation only; model in *shadow mode*; full re-evaluation on a ~May 2026 re-extract |

**Why a random split misleads:** (1) it mixes policy regimes, so the model interpolates across the 2025-07-01 change and drift the business will actually face is hidden; (2) post-migration near-duplicate cases can straddle train/test; (3) label availability correlates with start date, so random splitting makes maturity bias invisible and lets seasonal/regime confounders be memorized; (4) calibration claims across periods require out-of-time evidence by construction. `pm4py.split_train_test(log, 0.8)` is acknowledged as a convenience baseline only — never for reporting.

**Metrics.**
- *Ranking:* AUROC, AUPRC (base rate 12.5%).
- *Probability quality:* Brier, ECE, reliability diagrams — overall and **per subgroup** (region, channel, amount band, `source_system`, policy period, pre/post migration). Post-policy calibration degradation is the headline acceptance criterion; recalibrate (Platt/isotonic fit on the validation window only) before deployment.
- *Decision metrics:* recall at a fixed alert budget / precision@k, matching reviewer capacity.
- *Censoring-aware (S1):* IPCW Brier, time-dependent AUC at 30/60/90 d, concordance; for the multi-state alternative, Brier/calibration of state-occupation probabilities (Aalen–Johansen reference).
- *Drift monitoring:* PSI/KS on features and on model scores traintest; DFG edge-distribution distance between periods (`discover_dfg`); variant-frequency shift; label-delay and missing-feed-rate dashboards.

## 8. Limitations and decision-use boundary

**Can claim:** conditional *predictive association* — among home-platform-activated accounts with matured labels, prefix features at  rank and quantify 90-day default risk, calibrated within deployment-similar periods. That is an early-warning signal, not a causal quantity.

**Cannot claim:** (i) causal effects of process handling (document loops, resources) on default — risk_score at  feeds the accept decision, so process features are entangled with policy; (ii) counterfactual default risk of rejected/withdrawn applicants — undefined under the observed policy, estimable only under untestable selection assumptions (S3); (iii) partner-platform default risk (MNAR feed); (iv) performance on post-migration cohorts until labels mature; (v) comparability of scores across strata with different activation or feed-missingness mechanisms. **Association  selection  counterfactual:** the score is association conditional on selection; portfolio-level or policy-level statements require the stage-1 model and additional assumptions.

**Ways deployment changes the data-generating process (3):**
1. **Score-gated approvals:** officers reject high-score applications  activation becomes conditioned on the model's own features  training distribution drifts and the conditional estimand shifts (collider/feedback loop).
2. **Alert-triggered interventions:** extra document requests, manual review, collections outreach change outcomes  labels become outcomes *of the interventions* (self-defeating prophecy); interventions must be logged and analyzed as treatments.
3. **Applicant adaptation:** applicants respond to scrutiny (faster uploads, withdrawal under pressure, channel switching), altering prefix distributions.
4. **Policy revisions informed by the model** change selection and outcome relationships (a second, endogenous "policy change").
5. **Pipeline churn:** migrations (renames, duplicates) and monitoring-induced events (reviewer notes, collections contacts in the log) corrupt feature semantics and future prefixes.

**Decision-use boundary:** use only as early warning within the review/monitoring workflow for applications expected to activate; never as adverse-action justification for never-activated applicants; human-in-the-loop required; drift alarms and scheduled recalibration; freeze-and-rescore protocol after any policy or system change.

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Uncertainty-aware early-warning study: 90-day default after Account Activated.
Discipline enforced below: features come only from events at or before a
case-specific prediction time (landmark); labels are used only if they were
available by the extract time.  Survival / competing-risk estimators are NOT
implemented here -- attachment points are marked HOOK.  pm4py.split_train_test
(a random split) is a convenience baseline only, never used for reporting.
"""
import numpy as np
import pandas as pd
import pm4py

# ---- 0. Study constants: single point of configuration (as-of discipline) -------
EXTRACT_TS = pd.Timestamp("2026-02-15 23:59:59")  # warehouse extract = cutoff
POLICY_TS  = pd.Timestamp("2025-07-01")           # credit-policy change
MIGRATION  = pd.Timestamp("2025-10-15")           # system migration
HORIZON_D, FEED_DELAY_D = 90, 35                  # 35d = documented max feed delay
PREFIX_LEN, ELAPSED_H   = 5, 72                   # prefix variants (sensitivity)
PRED_ACT = "Credit Review"                        # landmark activity
CASE = "case:concept:name"
LEAKY = ["final_limit", "decision_reason", "collection_status", "default_90d",
         "label_available_at", "data_extract_time", "documents_total"]

# ---- 1. Load, standardise, repair -------------------------------------------------
df = pd.read_csv("applications_events.csv")
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])
df = pm4py.format_dataframe(df, case_id=CASE, activity_key="concept:name",
                            timestamp_key="time:timestamp")
df = df[df["time:timestamp"] <= EXTRACT_TS]       # nothing after the extract exists
NEW2CANON = {"Credit Assessment": "Credit Review",      # audited migration renames
             "Document Request": "Request Documents"}   # verify: frequency jump at MIGRATION
df["concept:name"] = df["concept:name"].replace(NEW2CANON)
n0 = len(df)
df = df.drop_duplicates(subset=[CASE, "concept:name", "time:timestamp", "org:resource"])
df = df.sort_values("time:timestamp")
gap = df.groupby([CASE, "concept:name", "org:resource"])["time:timestamp"].diff()
df = df[~(gap.dt.total_seconds().lt(60) & (df["time:timestamp"] >= MIGRATION)).fillna(False)]
print(f"[repair] removed {n0 - len(df)} duplicate event rows")

# ---- 2. Case-level state machine as of EXTRACT_TS ---------------------------------
df = df.sort_values([CASE, "time:timestamp"])
case = df.groupby(CASE).agg(case_start=("time:timestamp", "min"))
term = (df[df["concept:name"].isin(["Account Activated", "Rejected",
                                    "Withdrawn", "Transferred"])]
        .groupby(CASE).head(1).set_index(CASE))
case["terminal_act"] = term["concept:name"]
case["activated_at"] = (df[df["concept:name"].eq("Account Activated")]
                        .groupby(CASE)["time:timestamp"].min())
lab = (df.dropna(subset=["default_90d"]).groupby(CASE)
       .agg(default_90d=("default_90d", "max"),
            label_available_at=("label_available_at", "min")))
case = case.join(lab)
case["horizon_end"]   = case["activated_at"] + pd.Timedelta(days=HORIZON_D)
case["has_label"]     = case["default_90d"].notna() & (case["label_available_at"] <= EXTRACT_TS)
case["label_matured"] = case["horizon_end"] + pd.Timedelta(days=FEED_DELAY_D) <= EXTRACT_TS

def classify(r):
    if r.terminal_act == "Account Activated":
        if r.has_label:     return "activated_labeled"       # expect 21,600
        if r.label_matured: return "activated_feed_missing"  # matured, no feed: MNAR suspect
        return "activated_censored"                          # ordinary right-censoring
    return {"Rejected": "rejected", "Withdrawn": "withdrawn",
            "Transferred": "transferred"}.get(r.terminal_act, "open")

case["cohort"] = case.apply(classify, axis=1)
print("[cohort flow]\n", case["cohort"].value_counts())
# AUDIT GATE: reconcile with the 48,000 snapshot (labeled 21,600; rejected 9,100;
# withdrawn 5,700; transferred 2,900; open 5,100; activated-unlabeled 3,600).
# Mismatch blocks the study (e.g., labels leaking into rejected rows).

# ---- 3. Prediction time (landmark) and temporal split by CASE START ---------------
case["pred_ts"] = (df[df["concept:name"].eq(PRED_ACT)]
                   .groupby(CASE)["time:timestamp"].min())
# elapsed-time variant: case["pred_ts"] = case["case_start"] + pd.Timedelta(hours=ELAPSED_H)
case["policy_period"] = np.where(case["case_start"] < POLICY_TS, "pre", "post")

def split_of(ts):                        # never a random split
    if ts < pd.Timestamp("2025-04-01"): return "train"
    if ts < pd.Timestamp("2025-07-01"): return "valid"        # pre-policy, matured
    if ts < MIGRATION:                  return "test_policy"   # post-policy regime
    return "test_migration"                                   # labels mostly immature

case["split"] = case["case_start"].map(split_of)

# ---- 4. Prefixes: hard as-of truncation; post-decision columns banned -------------
m = df.merge(case[["pred_ts"]], left_on=CASE, right_index=True)
dfp = m[m["time:timestamp"] <= m["pred_ts"]]            # no event after pred_ts, ever
dfp = dfp.drop(columns=[c for c in LEAKY if c in dfp.columns])
print("[prefix] cases reaching the landmark:", dfp[CASE].nunique())

log_all = pm4py.convert_to_event_log(dfp[[CASE, "concept:name", "time:timestamp"]])
pref = pm4py.get_prefixes_from_log(log_all, PREFIX_LEN)  # fixed event-count variant
log_pref = pref[-1] if isinstance(pref, list) else pref  # version-dependent return
pref_df = pm4py.convert_to_dataframe(log_pref)           # may drop traces shorter than k
print("[prefix] cases with a full", PREFIX_LEN, "event prefix:", pref_df[CASE].nunique())

# ---- 5. Feature table built from the truncated prefix ONLY --------------------------
feat = case[["case_start", "policy_period", "split", "cohort"]].copy()
for c in ["case:channel", "case:region", "case:requested_amount"]:    # static attributes
    feat[c] = df.groupby(CASE)[c].first()
feat["risk_score_asof"] = (dfp.sort_values("time:timestamp")
                           .groupby(CASE)["risk_score"].last())  # as-of, not the latest
feat["prefix_len"] = dfp.groupby(CASE).size()
acts = pd.crosstab(dfp[CASE], dfp["concept:name"])
for a, nm in [("Request Documents", "n_doc_requests"), (PRED_ACT, "n_credit_reviews")]:
    if a in acts.columns: feat[nm] = acts[a]
feat["doc_loop"] = (feat["n_doc_requests"].fillna(0) > 1).astype(int)  # rework signal
feat["n_resources"] = dfp.groupby(CASE)["org:resource"].nunique()
feat["hours_to_landmark"] = (case["pred_ts"] - case["case_start"]).dt.total_seconds() / 3600
feat["variant"] = (dfp.sort_values("time:timestamp").groupby(CASE)["concept:name"]
                   .apply(lambda s: ">".join(s)).astype("category"))

# PM4Py descriptors on the truncated prefix ONLY (on the full log they would
# leak post-prediction durations):
dfp = pm4py.insert_case_service_waiting_time(dfp.sort_values("time:timestamp"))
swc = [c for c in dfp.columns if c.startswith(("@@case_service", "@@case_waiting"))]
feat = feat.join(dfp.groupby(CASE)[swc].first())  # caveat: instantaneous events -> service ~ 0
tmp = pm4py.extract_temporal_features_dataframe(dfp)
if CASE in tmp.columns: tmp = tmp.set_index(CASE)
feat = feat.join(tmp, rsuffix="_tmp")             # prefix timing descriptors
_ = pm4py.get_variants(log_all)                   # variant census (drift-audit input)

# ---- 6. Labels, modeling cohort, censoring bookkeeping -------------------------------
feat["y_default90"] = case["default_90d"]          # defined ONLY for activated_labeled
feat["horizon_end"] = case["horizon_end"]
model = feat[(feat["cohort"] == "activated_labeled") & (feat["prefix_len"] >= 2)].copy()
print("[model] n =", len(model), "| base rate =", round(model["y_default90"].mean(), 3))
print(model.groupby("split")["y_default90"].agg(["size", "mean"]))
# HOOK (survival): add cohort == activated_censored rows with
#   (activated_at, min(horizon_end, EXTRACT_TS), event = has_label & y_default90)
#   into a discrete-time hazard model; the 90-day binary target is a special case.
# HOOK (competing risks): for ALL cases reaching the landmark, Aalen-Johansen over
#   states {in-process, activated, default, rejected, withdrawn, transferred}.
# HOOK (transfer): left-join the ~60% transfer-linkage table for sensitivity runs.
# HOOK (MNAR feed): delta-adjust activated_feed_missing outcomes by source_system.

# ---- 7. Process-drift audit across the policy change (DFG distance) ------------------
def dfg_dist(frame):
    dfg, _, _ = pm4py.discover_dfg(pm4py.convert_to_event_log(
        frame[[CASE, "concept:name", "time:timestamp"]]))
    s = pd.Series(dfg, dtype=float)
    return s / s.sum()
pre  = dfg_dist(dfp[dfp[CASE].isin(case.index[case.policy_period == "pre"])])
post = dfg_dist(dfp[dfp[CASE].isin(case.index[case.policy_period == "post"])])
print("[drift] top DFG shifts pre->post policy:\n",
      post.sub(pre, fill_value=0).abs().sort_values(ascending=False).head())

# ---- 8. Leakage audit ------------------------------------------------------------------
meta = {"y_default90", "horizon_end", "cohort", "split", "case_start", "policy_period"}
leaks = [c for c in feat.columns if c in LEAKY and c not in meta]
assert not leaks, f"leaky columns entered the feature table: {leaks}"
ev_max = dfp.groupby(CASE)["time:timestamp"].max()
assert (ev_max <= case["pred_ts"].reindex(ev_max.index)).all(), "post-landmark events leaked"
dflt = (df[df["concept:name"].eq("Default Recorded")]
        .groupby(CASE)["time:timestamp"].min().reindex(case.index))
bad = case[case["has_label"] & case["default_90d"].eq(1)
           & (dflt.isna() | (dflt > case["horizon_end"]))]
print(f"[audit] labeled defaults without in-horizon Default Recorded event: {len(bad)}")
print("[audit] leakage checks passed")
```

Notes on the skeleton: the state machine and cohort counts re-derive (rather than trust) the warehouse export; `EXTRACT_TS` is the configurable as-of cutoff for the whole study; the split is by case start with the post-migration window deliberately flagged as partially evaluable; `get_prefixes_from_log` demonstrates the fixed-count variant while the landmark table is the primary, keeping short prefixes; and the four PM4Py descriptors (`discover_dfg`, `get_variants`, `extract_temporal_features_dataframe`, `insert_case_service_waiting_time`) are applied only to the time-safe prefix log, with the service-time degeneracy caveat stated where relevant.
