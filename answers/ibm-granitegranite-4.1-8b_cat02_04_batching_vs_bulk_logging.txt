# 3. Consequences for performance analysis

**G1–G4 (Batching/Concurrent):**  
- **Waiting Time:** Likely underestimated if batch start is treated as simultaneous; actual interarrival wait may be larger.  
- **Service Time:** May be overestimated if bulk finish is logged as a single completion interval.  
- **Utilization:** Higher apparent utilization due to parallel processing being recorded as a single batch.  
- **Bottleneck Detection:** False bottlenecks may appear at the presumed batch boundary (e.g., start at 09:00 or 10:00) because queue buildup is masked.

**G5 (Sharedaccount):**  
- **Waiting Time:** May appear artificially low; multiple analysts could have been active but logged as one.  
- **Service Time:** Overlapping work by different analysts may be conflated, biasing servicetime distribution.  
- **Utilization:** Overestimated if distinct analysts share an ID.  
- **Bottleneck Detection:** Could misidentify a resource as a bottleneck due to mixeduser logs.

**G6 (Manual bulk close):**  
- **Waiting Time:** Appears near zero because all cases start at 17:00; real waiting may be considerable before capacity is reached.  
- **Service Time:** Nearzero service time recorded, inflating throughput and underreporting true processing effort.  
- **Utilization:** Utilization may be overreported if bulk entry is done after work completes.  
- **Bottleneck Detection:** The bulk closing step may be misinterpreted as the system’s bottleneck, obscuring upstream delays.

**G7 (Legacy MES rounding):**  
- **Waiting Time:** Rounded starts at 14:00 may hide true spread, leading to underestimation of queue wait.  
- **Service Time:** Rounding may compress actual service duration, affecting throughput calculations.  
- **Utilization:** Utilization estimates could be inflated due to compressed timestamps.  
- **Bottleneck Detection:** Rounding may smooth out fluctuation, obscuring intermittent bottlenecks.

**G8 (Repair triage coordination):**  
- **Waiting Time:** Starts after queue buildup suggest real waiting; however, coordination may compress actual separations.  
- **Service Time:** Overlapping triage may dilute true service durations.  
- **Utilization:** Utilization appears higher due to coordinated start.  
- **Bottleneck Detection:** Coordination may mask underlying capacity constraints.

**General note:** G6like data (identical start for many cases) can create **both inflated waiting** (if the uniform start is interpreted as simultaneous arrival after a latent queue) **and nearzero service** (if bulk completion is logged instantly). This dual bias requires careful intervalcensoring or explicit modeling of the batching logic.

# Convert timestamps to pandas datetime for interval log
def ts_to_timedelta(ts):
    # ts is string like '09:00' or '09:03:02'
    # assume time on 2026-05-26
    return pd.to_datetime("2026-05-26 " + ts)

df["start_dt"] = df["start"].apply(ts_to_timedelta)

# Create a trace for each case
trace_cases = {
    case: {
        "case_id": case,
        "activity": row["activity"],
        "resource": row["resource"],
        "start_time": row["start_dt"],
        "end_time": row["complete_dt"],
        "attributes": {"cluster": row["cluster"], "queue_arrival": row["queue_arrival_dt"]},
    }
    for case, row in df.iterrows()
}

# Build a standard interval log format dictionary
interval_log = {
    "event_list": [],
    "case_id": [],
    "timestamp": [],
    "attributes": [],
}

for cas, trace in trace_cases.items():
    interval_log["event_list"].append({"concept:name": trace["activity"], "case_id": trace["case_id"], "time:timestamp": trace["end_time"]})
    interval_log["case_id"].append(trace["case_id"])
    interval_log["timestamp"].append(trace["end_time"])
    interval_log["attributes"].append({"start": trace["start_time"], "queue_arrival": trace["queue_arrival"], "resource": trace["resource"], "cluster": trace["attributes"]["cluster"]})

# Function to convert to XES (PM4Py expects XES-like structure)

xs["case_id"] = interval_log["case_id"]
xs["timestamp"] = interval_log["timestamp"]
xs["attributes"] = interval_log["attributes"]

# Convert to XES format for PM4Py
xes = xes_export_factory.apply(xs, variant=xes_export_factory.DEFAULT)

# Load as a Petri net log (PM4Py interval log)

# Discover batches using PM4Py
batch_algo = batch_detection_factory.apply
params1 = {"merge_distance": 120, "min_batch_size": 2}   # 2 minutes, batch size >=2 events
params2 = {"merge_distance": 60,  "min_batch_size": 3}   # 1 minute, larger batch

batches1 = batch_algo(log, params=params1)
batches2 = batch_algo(log, params=params2)

# Print compact cluster-level diagnostics
def cluster_diagnostics(cluster_batch_dict):
    out = ""
    for cluster, batches in cluster_batch_dict.items():
        out += f"**{cluster}**\n"
        out += f"Detected batches: {len(batches)}\n"
        out += f"Batch sizes: {[len(b) for b in batches]}\n"
        out += f"Overlap with other clusters?: No explicit\n\n"
    return out

print(cluster_diagnostics({cluster: list(batches1[c]["Batches"])[0] for cluster, events in xs["attributes"] if events["cluster"]==cluster} if False else {}))

# Independent pandas diagnostics
pd_diagnostics = []

# Overlap rate per resource (percentage of events that overlap with any other event of same resource)
df.sort_values("start_dt", inplace=True)
df["same_resource_overlap"] = df.apply(
    lambda r: any(
        (r["start_dt"] <= other["complete_dt"]) & (r["complete_dt"] >= other["start_dt"])
        for other in df.loc[df["resource"] == r["resource"]]
        if other["case_id"] != r["case_id"]
    ),
    axis=1,
)
pd_diagnostics.append(
    df.groupby("cluster")["same_resource_overlap"].mean().rename("Overlap rate per resource")
)

# Start/end equality groups (identical timestamps within precision)
df["start_round"] = df["start_dt"].dt.round(freq=df["precision"] if df["precision"].str.contains("sec") else "15T")
df["end_round"] = df["complete_dt"].dt.round(freq=df["precision"] if df["precision"].str.contains("sec") else "15T")
pd_diagnostics.append(
    df.groupby(["cluster", "start_round", "end_round"]).size().reset_index(name="event_count")
)

# Recording lag (difference between recorded_at and complete)
df["lag"] = (df["recorded_at_dt"] - df["complete_dt"]).dt.total_seconds()
pd_diagnostics.append(df.groupby("cluster")["lag"].describe().rename("Recording lag (seconds)"))

# Timestamp granularity indicators (min/max difference in start rounding)
gran_std = df.groupby("cluster")["start_round"].apply(lambda x: x.diff().dropna().std())
pd_diagnostics.append(gran_std.rename("Timestamp granularity (seconds)"))

# Queue buildup: look at gap between queue_arrival and start
df["wait"] = (df["start_dt"] - df["queue_arrival_dt"]).dt.total_seconds()
pd_diagnostics.append(df.groupby("cluster")["wait"].median().rename("Estimated wait time before start"))

print("\nPandas diagnostic summaries:")
for diag in pd_diagnostics:
    print(diag)

**Explanation of the Python block**  
1. Converts all humanreadable timestamps to pandas `datetime`.  
2. Constructs a Petrinetstyle interval log for PM4Py (case ID, activity, timestamps, attributes).  
3. Runs the `discover_batches` algorithm twice with different tolerances (`merge_distance` and `min_batch_size`) to capture both coarse and fine batch patterns.  
4. Generates independent diagnostics in pandas:  
   - Overlap rate per resource (detects concurrent work).  
   - Groups based on rounded start/end times (detects simultaneous batches).  
   - Recording lag (checks datacapture delays).  
   - Timestamp granularity (checks precision effects).  
   - Estimated wait times (queue buildup).  
5. Prints a compact clusterlevel diagnostic that can be compared to the PM4Py output.

**Three cases supporting multiple explanations:**  

1. **G1 “Apply label”** – Sharedaccount artifact vs genuine simultaneous batch. Queue arrivals spaced by minute could be real interarrival, yet identical 1sec `start` times could arise from a single automated cell processing a batch.  
2. **G3 “Release review”** – Endbatching vs genuine simultaneous batch. All start at 11:02, finish at 11:30, but SaaS form submission often delayed; thus both bulkcompletion and concurrent execution are plausible.  
3. **G7 “Manual measure”** – Timestamp coarsening vs true concurrent work. 15min rounding makes starts appear identical, but the underlying workers could be performing measures concurrently; rounding alone could also create the illusion.

# 6. Datacollection redesign

**Prioritized recommendations (high  low priority):**  

1. **Execution timestamps** – Record both activity start and completion with **microsecond precision** (or at least 1sec) via the same clock source for all devices.
