# **Equivalence Criteria and Clustering of Eight Order-Centric Executions**

This analysis defines equivalence relations for order-centric executions, clusters the given executions, and interprets the business semantics of resulting clusters. The goal is to balance structural fidelity with business meaning while accounting for intentional variations in execution design.

---

## **1. Equivalence Design Space**

### **1.1 Activity-Sequence Equivalence**
**Definition:**
Two executions are *activity-sequence equivalent* if their sequences of event labels (ignoring object identifiers) are identical, including repeated activities (e.g., `Pack Package` appearing twice).

**Invariants Preserved:**
- Event order (total order).
- Repeated activities (e.g., partial payments, repacking).
- Local object multiplicities (e.g., number of items, packages, deliveries).

**Information Discarded:**
- Object identifiers (local or external).
- O2O qualifiers (e.g., `removed_before_dispatch`).
- External object dependencies.

**Properties:**
- **Reflexive:** Yes (a sequence is equivalent to itself).
- **Symmetric:** Yes (if A  B, then B  A).
- **Transitive:** Yes (if A  B and B  C, then A  C).
- **Concurrency Handling:** Treats same-time events as ordered by timestamp (no parallelism).

**Example:**
- **X1** and **X2** are activity-sequence equivalent because their event labels are identical.
- **X7** is equivalent to **X1** at this level, despite the `removed_before_dispatch` qualifier.

---

### **1.2 Typed Structural Equivalence Under Identifier Renaming**
**Definition:**
Two executions are *structurally equivalent* if:
1. The set of event types matches (e.g., `Add Item`, `Pack Package`).
2. The **multiplicities** of local objects (e.g., `Order`, `Item`, `Package`) are preserved under renaming.
3. The **external object dependencies** (denoted by `EXT-`) are preserved in type but not in identifier.
4. The **O2O relationships** (e.g., `Packs`, `Carries`) are isomorphic under renaming.

**Invariants Preserved:**
- Object types (`Order`, `Item`, `Package`, etc.).
- Local multiplicities (e.g., `Order:O1`  `Order:O2`).
- External object flags (e.g., `EXT-OA`).
- E2O (Event-to-Object) incidence (e.g., `Dispatch` carrying `Package`).
- O2O qualifiers (e.g., `removed_before_dispatch` in **X7**).

**Information Discarded:**
- Object identifiers (local and external).
- Event order (only multiplicities and types matter).

**Properties:**
- **Reflexive:** Yes.
- **Symmetric:** Yes.
- **Transitive:** Yes.
- **Concurrency Handling:** Ignores event ordering; only considers object relationships.

**Example:**
- **X1** and **X2** are structurally equivalent (same multiplicities, same O2O topology).
- **X5** and **X1** are not structurally equivalent because **X5** involves an external object (`EXT-IA`) that is not present in **X1**.

---

### **1.3 Business-Semantic Equivalence**
**Definition:**
Two executions are *business-semantically equivalent* if they represent the **same core business process** despite differences in:
- **Logistics granularity** (e.g., split packages vs. consolidated).
- **Financial allocation** (e.g., shared invoices, partial payments).
- **Item lifecycle** (e.g., replacements, returns).
- **External dependencies** (e.g., cross-order sharing).

**Invariants Preserved:**
- **Order-level behavior** (e.g., billing, payment settlement).
- **Item-level transformations** (e.g., additions, removals, returns).
- **External object sharing** (e.g., cross-order invoices).
- **Qualified O2O relationships** (e.g., `removed_before_dispatch` in **X7**).

**Information Discarded:**
- Exact object identifiers.
- Event ordering (only business motifs matter).
- Minor deviations in logistics (e.g., split vs. consolidated packages).

**Properties:**
- **Reflexive:** Yes.
- **Symmetric:** Yes.
- **Transitive:** Yes (if A  B and B  C, then A  C).
- **Concurrency Handling:** Treats parallel logistics (e.g., split deliveries) as equivalent.

**Example:**
- **X3** and **X4** are semantically equivalent because both represent:
  - Items added  split into packages  dispatched separately  invoiced  paid.
- **X6** and **X1** differ semantically because **X6** shares an invoice with an external order.

---

### **1.4 Fourth Relation: Partial-Order Semantics**
**Definition:**
Two executions are *partial-order equivalent* if their **event order is preserved up to concurrency** (e.g., two `Pack Package` events can be reordered as long as dependencies are maintained).

**Invariants Preserved:**
- Event types and multiplicities.
- O2O dependencies (e.g., `Pack` must precede `Dispatch`).
- External object sharing.

**Information Discarded:**
- Exact event ordering (only dependencies matter).

**Properties:**
- **Reflexive:** Yes.
- **Symmetric:** Yes.
- **Transitive:** Yes.
- **Use Case:** Useful for parallelizable logistics (e.g., independent package dispatch).

## **2. Canonical Signatures**
To make clustering reproducible, we define a **canonical signature** for business-semantic equivalence. The signature is invariant to local identifier renaming but preserves:

```python
def canonical_signature(execution):
    # Step 1: Extract event types and multiplicities
    event_types = sorted(set(event.label for event in execution.events))

    # Step 2: Extract object multiplicities (local + external)
    object_counts = {
        "Order": len([e for e in execution.events if "Order:" in e.object_ids]),
        "Item": len([e for e in execution.events if "Item:" in e.object_ids]),
        "Package": len([e for e in execution.events if "Package:" in e.object_ids]),
        "Delivery": len([e for e in execution.events if "Delivery:" in e.object_ids]),
        "Invoice": len([e for e in execution.events if "Invoice:" in e.object_ids]),
        "Payment": len([e for e in execution.events if "Payment:" in e.object_ids]),
    }

    # Step 3: Extract external object flags
    external_objects = {
        "EXT-OA": any("EXT-OA" in e.object_ids for e in execution.events),
        "EXT-OB": any("EXT-OB" in e.object_ids for e in execution.events),
        "EXT-IA": any("EXT-IA" in e.object_ids for e in execution.events),
    }

    # Step 4: Extract O2O qualifiers (simplified)
    qualifiers = {
        "removed_before_dispatch": any("removed_before_dispatch" in e.object_ids for e in execution.events),
    }

    # Step 5: Extract business motifs (e.g., split packages, shared invoices)
    motifs = {
        "split_packages": any("Pack Package" in e.label and len(e.object_ids.split(",")) > 1 for e in execution.events),
        "shared_invoice": any("Invoice:" in e.object_ids and "EXT-OB" in e.object_ids for e in execution.events),
        "return_item": any("Return Item" in e.label for e in execution.events),
    }

    return {
        "event_types": event_types,
        "object_counts": object_counts,
        "external_objects": external_objects,
        "qualifiers": qualifiers,
        "motifs": motifs,
    }
```

**Example:**
- **X1** and **X2** have identical signatures because they are structurally equivalent.
- **X5** differs because it includes `EXT-IA` and `EXT-OA`.

## **4. Cluster Interpretations**

### **Semantic Cluster A: Single-Order, Single-Package Flow**
**Signature:**
- No split packages.
- No external object sharing.
- No item replacements/returns.

**Business Behavior:**
- Classic order-to-cash (OTC) workflow:
  1. Order created.
  2. Items added.
  3. Single package packed.
  4. Delivered.
  5. Invoice issued.
  6. Payment recorded.

**Operational Risks:**
- **Logistics inefficiency:** Single package may be over/under-packaged.
- **Compliance risk:** No audit trail for item-level changes.

**Traditional Flattening:**
- Would treat as a single execution, losing granularity.

**Stability:**
- Robust under minor identifier changes.

---

### **Semantic Cluster B: Split-Package Logistics**
**Signature:**
- Multiple packages per order.
- Deliveries may be split.
- Partial payments possible.

**Business Behavior:**
- Items are split into multiple packages for efficiency.
- Deliveries are tracked separately.
- Payments may be partial (e.g., partial settlement).

**Operational Risks:**
- **Complexity:** Harder to track item-level allocations.
- **Cost:** Higher logistics overhead.

**Traditional Flattening:**
- Would merge into a single execution, losing split-delivery semantics.

**Stability:**
- Stable under minor logistics adjustments.

---

### **Semantic Cluster C: Cross-Order Dependencies**
**Signature:**
- External object sharing (e.g., `EXT-OA`, `EXT-IA`).
- No item-level replacements.

**Business Behavior:**
- Packages or invoices are shared across orders.
- Example: A package contains an external item (`EXT-IA`) from another order.

**Operational Risks:**
- **Data integrity:** Harder to track ownership.
- **Compliance:** May violate contract terms.

**Traditional Flattening:**
- Would treat as a single execution, losing cross-order semantics.

**Stability:**
- Fragile under external object removal.

---

### **Semantic Cluster D: Shared Invoices**
**Signature:**
- Invoice shared with an external order (`EXT-OB`).
- No item replacements.

**Business Behavior:**
- An order’s invoice is billed to another order (e.g., bulk discounts).
- Payment is allocated without item-level tracking.

**Operational Risks:**
- **Misallocation:** Payments may not match expected item values.
- **Audit complexity:** Harder to reconcile.

**Traditional Flattening:**
- Would merge into a single execution, losing financial tracking.

**Stability:**
- Stable under minor invoice adjustments.

---

### **Semantic Cluster E: Item Replacements/Returns**
**Signature:**
- Item is replaced (`removed_before_dispatch`).
- Return and repacking.

**Business Behavior:**
- An item is removed before dispatch and replaced later.
- Example: A defective item is returned and repacked.

**Operational Risks:**
- **Logistics delays:** Return and repacking may disrupt flow.
- **Cost:** Extra handling fees.

**Traditional Flattening:**
- Would treat as a single execution, losing item lifecycle tracking.

**Stability:**
- Fragile under minor return policies.

## **6. Relation to `pm4py.cluster_equivalent_ocel`**

### **What `pm4py` Preserves:**
- **Exact object-centric equivalence** (identifiers matter).
- **Event order and object relationships** (e.g., `Pack`  `Dispatch`).
- **No aggregation** (treats each execution as unique).

### **Why Raw Identifiers Are Problematic:**
- **Over-fine granularity:** Two executions with identical business flow but different identifiers are treated as distinct.
- **No business semantics:** Ignores item replacements, shared invoices, etc.

### **Canonicalization Approach:**
```python
def canonicalize_ocel(execution):
    # Step 1: Aggregate repeated events (e.g., multiple Pack Package  one)
    unique_events = []
    seen = set()
    for event in execution.events:
        event_key = (event.label, tuple(sorted(event.object_ids)))
        if event_key not in seen:
            seen.add(event_key)
            unique_events.append(event)

    # Step 2: Extract object multiplicities and motifs
    signature = canonical_signature(unique_events)

    return signature
```

### **When Exact Equivalence is Useful:**
- **Compliance audits:** Need to track exact object relationships.
- **Traceability:** Need to map events to specific objects.

### **When Business Clustering is Better:**
- **Operational segmentation:** Group executions by business flow.
- **Root-cause analysis:** Focus on business motifs, not identifiers.

## **7. Robustness Analysis**

### **Perturbation 1: Ignore O2O Qualifiers**
- **Effect:** **X7** and **X1** would no longer be equivalent.
- **Reason:** The `removed_before_dispatch` qualifier is lost.

### **Perturbation 2: Ignore External Objects**
- **Effect:** **X5** and **X6** would merge with **X1**.
- **Reason:** Cross-order dependencies are removed.

### **Perturbation 3: Collapse Repeated Same-Label Events**
- **Effect:** **X4** and **X8** would merge (both have `Record Payment`).
- **Reason:** Repeated payments are aggregated.

### **Perturbation 4: Treat Pack/Dispatch as Partial Order**
- **Effect:** **X3** and **X4** would merge (split packages are treated as independent).
- **Reason:** Event ordering is relaxed.

### **Perturbation 5: Treat Payment Multiplicity as Amount**
- **Effect:** **X4** and **X8** would merge if payments are treated as amounts.
- **Reason:** Partial payments are normalized.

## **8. Limitations and Recommendations**

### **Recommended Equivalence Level: Business-Semantic Equivalence**
| Purpose               | Equivalence Level | Why? |
|-----------------------|-------------------|------|
| **Compliance Monitoring** | Exact (OCEL) | Needs exact object tracking. |
| **Operational Segmentation** | Business-Semantic | Groups by core workflow. |
| **Root-Cause Analysis** | Business-Semantic | Focuses on business motifs. |
| **Descriptive Reporting** | Activity-Sequence | Simple and interpretable. |

### **Why No Single Equivalence is Best:**
- **Exact equivalence** is too fine-grained for business analysis.
- **Activity-sequence equivalence** ignores object relationships.
- **Structural equivalence** misses business semantics (e.g., shared invoices).
- **Business-semantic equivalence** is a trade-off between fidelity and meaning.

### **Final Recommendation:**
Use **business-semantic equivalence** for most business analysis, with **exact equivalence** reserved for compliance. For operational segmentation, aggregate by business motifs (e.g., single-package vs. multi-package flows).
