# 2. Shared Assumptions

The following assumptions define the observation boundary of all three candidates.

1. **Completion-event semantics.** Every listed activity is interpreted as a completion event. The trace is a total order produced from completion timestamps and, for ties, ingestion index. The models do not reconstruct unobserved start times.

2. **Visible-trace models, not timing models.** The candidates specify permitted visible activity sequences. They do not encode durations, resources, overlaps, component counts, probabilities, or timestamp precision.

3. **Notation.** Let:

   * `R` = Register Order
   * `C` = Credit Check
   * `E` = Engineering Review
   * `S` = Supplier Confirmation
   * `X` = Expedite Review
   * `A` = Approve Configuration
   * `L` = Release Production
   * `Z` = Archive Case
   * `Y? = XOR(Y, τ)` for an optional activity
   * `PO(N, <)` for a strict partial order over nodes `N`

4. **Fixed case boundary and suffix.** All models enforce `R` as the visible start, `A < L < Z`, and `Z` as the visible end.

5. **Principal checks.** Both `C` and `E` occur exactly once before `A`. This is a modeling decision based on D3 and unanimous observed support. There is no supplied evidence that either principal-check event is missing.

6. **Expedite optionality.** `X` is modeled as a true optional activity, occurs at most once, follows both `C` and `E`, and precedes `A`.

7. **Supplier absence is observationally ambiguous.** A trace without `S` can represent either:

   * a legitimate stocked-component route; or
   * an external-component route whose Supplier Confirmation event was lost.

   The model cannot distinguish those causes because the external/stocked attribute and event-level missingness indicators are absent.

8. **Unguarded optionality is an abstraction.** `S?` or an XOR branch without `S` does not assert that every order may freely skip supplier work. It stands in for an unavailable data condition and possible logging failure.

9. **No probabilities.** The XOR alternatives are unweighted. The 5–10% missingness estimate and observed branch frequencies are not converted into routing probabilities.

10. **At most one aggregate Supplier Confirmation.** The models treat `S` as a case-level aggregate milestone occurring at most once. If an order can contain several independently confirmed external components, all three candidates underfit that object-level behavior.

11. **No unsupported exceptional behavior.** Rework, repeated checks, cancellation, approval withdrawal, release reversal, incomplete cases, and alternative terminal activities are outside all three languages.

# 3. Conservative Candidate

**Inductive bias.** The conservative candidate applies a near-closed-world bias to the supplied completed traces: it factors out the unanimous start and suffix but admits only the seven observed preapproval sequences. This maximizes sample precision and minimizes unsupported behavior, but it treats a 30-case sample—especially only two expedite cases—as if it were behaviorally complete. It represents different recorded completion orders as XOR alternatives rather than inferring concurrency.

**Compact formal expression**

[
\begin{aligned}
M_c = \rightarrow(&R,\ \times(\
&\rightarrow(C,E,S),\
&\rightarrow(E,C,S),\
&\rightarrow(C,E),\
&\rightarrow(E,C),\
&\rightarrow(C,S,E),\
&\rightarrow(C,E,S,X),\
&\rightarrow(E,C,X,S)),\
&A,L,Z)
\end{aligned}
]

**Self-contained PM4Py code**

```python
import pm4py

model_conservative = pm4py.parse_process_tree(
    """
    ->(
      'Register Order',
      X(
        ->('Credit Check',
           'Engineering Review',
           'Supplier Confirmation'),

        ->('Engineering Review',
           'Credit Check',
           'Supplier Confirmation'),

        ->('Credit Check',
           'Engineering Review'),

        ->('Engineering Review',
           'Credit Check'),

        ->('Credit Check',
           'Supplier Confirmation',
           'Engineering Review'),

        ->('Credit Check',
           'Engineering Review',
           'Supplier Confirmation',
           'Expedite Review'),

        ->('Engineering Review',
           'Credit Check',
           'Expedite Review',
           'Supplier Confirmation')
      ),
      'Approve Configuration',
      'Release Production',
      'Archive Case'
    )
    """
)
```

The XOR enumeration duplicates visible labels across branches. After Petri-net conversion, several distinct transitions may therefore have the same label. That is legal but can make alignment explanations and transition-level diagnostics ambiguous: a synchronous `Credit Check` move may correspond to several internal branches. The representation also scales poorly. Adding optional activities or additional interleavings can multiply the number of branches rather than adding a small number of constraints.

**Behavior deliberately excluded**

* Every complete trace not among the seven observed variants.
* `E → S → C`, despite being a plausible symmetric counterpart to observed `C → S → E`.
* Expedite Review in a no-Supplier trace.
* `C → E → X → S` and `E → C → S → X` unless exactly observed.
* Any true concurrency representation for Credit Check and Engineering Review.
* Repeated, missing, or reordered principal checks.
* Supplier Confirmation after approval or any change to `A → L → Z`.

**Known underfitting risks**

* It treats rare-variant absence as prohibition; only two Expedite Review cases were observed.
* It cannot absorb missing Supplier Confirmation in an otherwise legitimate expedite case.
* It rejects plausible stocked-component expedite traces.
* It rejects future linearizations of concurrent or overlapping activities.
* It cannot generalize to `E → S → C`, although D5 is symmetric between the two principal checks.
* Its case-level single-Supplier abstraction can reject legitimate multi-component confirmation behavior.

# 4. Balanced Candidate

**Inductive bias.** The balanced candidate applies constrained abductive generalization. It preserves the high-confidence case boundary, approval/release relation, both-check approval prerequisite, and Expedite Review controls. It treats Credit Check and Engineering Review as incomparable in a partial order—not because the DFG proves concurrency, but because both recorded orders, S2, D7, and completion-only logging make a universal sequence unjustified. Supplier Confirmation is either absent or present with at least one completed principal check as a predecessor. Expedite Review follows both principal checks and remains unordered relative to Supplier Confirmation whenever both orders are feasible.

**Compact formal expression**

[
M_b = \rightarrow(R,\ \times(B_{\varnothing},B_C,B_E),\ A,L,Z)
]

where:

[
\begin{aligned}
B_{\varnothing}
&= PO({C,E,X?},{C<X?,E<X?})\
B_C
&= PO({C,E,S,X?},{C<S,C<X?,E<X?})\
B_E
&= PO({C,E,S,X?},{E<S,C<X?,E<X?})
\end{aligned}
]

The union of `B_C` and `B_E` implements the disjunctive supplier condition:

[
(C<S)\ \lor\ (E<S)
]

There is deliberately no edge between `S` and `X?`.

**Choice between sequence, concurrency, and partial order**

* **Credit Check versus Engineering Review:** A fixed `C → E` sequence would conflict with 11 recorded Engineering-first completions unless those cases were declared erroneous. A fixed `E → C` sequence would conflict with 19 Credit-first starts. An XOR between two sequences would reproduce completion orders but would assert that each case belongs to one sequential mode. The balanced candidate instead uses incomparable POWL nodes as a hypothesis of operational independence or overlap.
* **Supplier Confirmation:** The two branches with Supplier Confirmation encode “after Credit” or “after Engineering.” This admits `C,E,S`, `E,C,S`, `C,S,E`, and the unobserved but plausible `E,S,C`. It does not permit Supplier Confirmation to complete before both principal-check completions.
* **Expedite Review:** Edges from both `C` and `E` to `X?` enforce D6/S6. No `S–X` edge permits either order after the principal checks, while still respecting the fact that an early Supplier Confirmation can occur before the second principal check.
* **Approval:** Approval follows completion of the entire selected preapproval submodel, so both principal checks, any selected Supplier Confirmation, and any selected Expedite Review must be complete.

In PM4Py’s POWL representation, a strict-partial-order edge is a completion precedence and unconnected nodes are treated as concurrent. Here, incomparability is therefore an explicit modeling hypothesis, not something mechanically established by the DFG. ([GitHub][1])

**Self-contained PM4Py code**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def strict_sequence(nodes):
    """
    Encode a sequence as a transitively closed strict partial order.
    Every earlier node precedes every later node.
    """
    nodes = list(nodes)
    po = StrictPartialOrder(nodes=nodes)

    for i, source in enumerate(nodes):
        for target in nodes[i + 1:]:
            po.order.add_edge(source, target)

    po.validate_partial_orders()
    return po


def optional_activity(label):
    return OperatorPOWL(
        operator=Operator.XOR,
        children=[
            Transition(label=label),
            SilentTransition(),
        ],
    )


def balanced_branch(supplier_predecessor=None):
    credit = Transition(label="Credit Check")
    engineering = Transition(label="Engineering Review")
    expedite_optional = optional_activity("Expedite Review")

    nodes = [credit, engineering, expedite_optional]
    supplier = None

    if supplier_predecessor is not None:
        supplier = Transition(label="Supplier Confirmation")
        nodes.insert(2, supplier)

    branch = StrictPartialOrder(nodes=nodes)

    # Expedite Review, when selected, follows both principal checks.
    branch.order.add_edge(credit, expedite_optional)
    branch.order.add_edge(engineering, expedite_optional)

    # Supplier Confirmation follows at least one principal check.
    if supplier_predecessor == "credit":
        branch.order.add_edge(credit, supplier)
    elif supplier_predecessor == "engineering":
        branch.order.add_edge(engineering, supplier)
    elif supplier_predecessor is not None:
        raise ValueError(
            "supplier_predecessor must be None, "
            "'credit', or 'engineering'"
        )

    branch.validate_partial_orders()
    return branch


preapproval_balanced = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        balanced_branch(None),             # stocked or missing S
        balanced_branch("credit"),         # C < S
        balanced_branch("engineering"),    # E < S
    ],
)

model_balanced = strict_sequence(
    [
        Transition(label="Register Order"),
        preapproval_balanced,
        Transition(label="Approve Configuration"),
        Transition(label="Release Production"),
        Transition(label="Archive Case"),
    ]
)
```

The two Supplier-present branches introduce some duplicate labels and duplicate derivations of traces such as `C,E,S`. That is the cost of expressing an OR-predecessor condition using an XOR of strict partial orders. It is still substantially more compact and general than enumerating every complete linearization.

**Behavior deliberately excluded**

* Supplier Confirmation completing before both principal-check completions.
* Expedite Review before either principal check has completed.
* Approval before both principal checks.
* Approval before a selected Supplier Confirmation or Expedite Review.
* Supplier Confirmation or Expedite Review after approval.
* More than one occurrence of any preapproval activity.
* Rework, cancellation, missing principal checks, or alternative release/archive orders.

**Known underfitting risks**

* D5 concerns when Supplier Confirmation may **begin**, not necessarily when it may complete. If supplier work can begin from provisional information and finish before both checks complete, this model is too restrictive.
* Equal-timestamp ingestion ordering could record an otherwise legal Expedite Review before one principal-check completion.
* It assumes principal-check events are never missing.
* It assumes one aggregate Supplier Confirmation rather than component-level confirmations.
* It has no guards for external versus stocked cases and cannot distinguish legitimate skips from integration loss.

# 5. Permissive Candidate

**Inductive bias.** The permissive candidate defines a bounded exploratory envelope rather than a compliance-ready norm. It preserves the strongest boundary and approval rules but relaxes Supplier Confirmation’s completion-order relationship with the principal checks. This reflects the distinction between D5’s start-level information dependency and the log’s completion-only observations: supplier work might receive enough information while a check is still running and complete before either check’s logged completion. Supplier Confirmation is therefore optional and incomparable with both checks and Expedite Review, while Expedite Review remains strictly after both principal checks.

**Compact formal expression**

[
M_p =
\rightarrow\left(
R,
PO(
{C,E,S?,X?},
{C<X?,E<X?}
),
A,L,Z
\right)
]

The absence of supplier edges allows `S` to complete before, between, or after `C` and `E`, but always before approval because the whole partial-order block precedes `A`.

**Boundary between reasonable generalization and forbidden behavior**

Reasonable generalization includes:

* either completion order of Credit Check and Engineering Review;
* overlap or independence between the principal checks;
* true or observational absence of Supplier Confirmation;
* any Supplier Confirmation completion position before approval;
* Expedite Review with or without Supplier Confirmation;
* either order of Supplier Confirmation and Expedite Review, subject to Expedite Review following both principal checks.

Behavior remains forbidden when it violates the strongest shared rules:

* either principal check is absent;
* Expedite Review occurs before both principal checks are complete;
* approval occurs before the selected preapproval activities complete;
* Release Production precedes approval;
* activities repeat;
* Supplier Confirmation or Expedite Review occurs after approval;
* the start or terminal sequence changes.

**Self-contained PM4Py code**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def strict_sequence(nodes):
    nodes = list(nodes)
    po = StrictPartialOrder(nodes=nodes)

    for i, source in enumerate(nodes):
        for target in nodes[i + 1:]:
            po.order.add_edge(source, target)

    po.validate_partial_orders()
    return po


def optional_activity(label):
    return OperatorPOWL(
        operator=Operator.XOR,
        children=[
            Transition(label=label),
            SilentTransition(),
        ],
    )


credit = Transition(label="Credit Check")
engineering = Transition(label="Engineering Review")
supplier_optional = optional_activity("Supplier Confirmation")
expedite_optional = optional_activity("Expedite Review")

preapproval_permissive = StrictPartialOrder(
    nodes=[
        credit,
        engineering,
        supplier_optional,
        expedite_optional,
    ]
)

# Expedite Review still requires both principal checks.
preapproval_permissive.order.add_edge(
    credit,
    expedite_optional,
)
preapproval_permissive.order.add_edge(
    engineering,
    expedite_optional,
)

# No supplier edges: Supplier Confirmation's completion order
# is left open, while the outer sequence keeps it before approval.
preapproval_permissive.validate_partial_orders()

model_permissive = strict_sequence(
    [
        Transition(label="Register Order"),
        preapproval_permissive,
        Transition(label="Approve Configuration"),
        Transition(label="Release Production"),
        Transition(label="Archive Case"),
    ]
)
```

**Behavior deliberately excluded**

* Expedite Review before completion of Credit Check or Engineering Review.
* Approval without both principal checks.
* Release Production before approval.
* Supplier Confirmation or Expedite Review after approval.
* Repeated checks, repeated expedite reviews, and repeated supplier confirmations.
* Missing registration, missing archive, cancellation, rework, and alternative terminal outcomes.

**Known underfitting risks**

* It still cannot represent repeated component-level Supplier Confirmations.
* It cannot represent rechecks or approval rework.
* It assumes principal-check completion events are complete and reliable.
* It excludes same-timestamp traces whose ingestion order places Expedite Review before a principal-check event.
* It cannot model a legitimate case where approval is provisional or release is later withdrawn.
* Although permissive relative to the supplied alternatives, it remains a finite one-pass process.

* Conservative: **7** complete visible traces.
* Balanced: **14** complete visible traces.

# 8. Validation Code

The code below uses the current PM4Py interfaces for parsing trace strings and process trees, constructing POWL strict partial orders, converting ProcessTree or POWL models to accepting Petri nets, evaluating conformance metrics, checking soundness, and running bounded random playout. The sequence helper adds every earlier-to-later edge because a `StrictPartialOrder` is represented as a transitive relation rather than only a transitive reduction. ([GitHub][2])

The requested alignment fitness and precision, token-replay generalization, simplicity, and soundness functions are exposed by PM4Py; the playout parameter names used below are `noTraces`, `maxTraceLength`, and `add_only_if_fm_is_reached`. ([GitHub][3])

def strict_sequence(nodes: Sequence):
    """
    Encode a sequence as a transitively closed StrictPartialOrder.

    Adding only adjacent edges would describe a transitive reduction,
    not the complete strict partial-order relation expected by POWL's
    validation method.
    """
    nodes = list(nodes)
    po = StrictPartialOrder(nodes=nodes)

    for i, source in enumerate(nodes):
        for target in nodes[i + 1:]:
            po.order.add_edge(source, target)

    po.validate_partial_orders()
    return po


def optional_activity(label: str):
    """Exactly zero or one visible occurrence."""
    return OperatorPOWL(
        operator=Operator.XOR,
        children=[
            Transition(label=label),
            SilentTransition(),
        ],
    )

               'Supplier Confirmation',

def balanced_branch(supplier_predecessor: str | None):
    credit = Transition(label=CREDIT)
    engineering = Transition(label=ENG)
    expedite_optional = optional_activity(EXP)

    nodes = [credit, engineering, expedite_optional]
    supplier = None

    if supplier_predecessor is not None:
        supplier = Transition(label=SUP)
        nodes.insert(2, supplier)

    branch = StrictPartialOrder(nodes=nodes)

    # Expedite Review waits for both principal checks.
    branch.order.add_edge(credit, expedite_optional)
    branch.order.add_edge(engineering, expedite_optional)

    # Supplier Confirmation waits for at least one principal check.
    if supplier_predecessor == "credit":
        branch.order.add_edge(credit, supplier)
    elif supplier_predecessor == "engineering":
        branch.order.add_edge(engineering, supplier)
    elif supplier_predecessor is not None:
        raise ValueError(
            "supplier_predecessor must be None, "
            "'credit', or 'engineering'"
        )

    branch.validate_partial_orders()
    return branch


def build_balanced():
    preapproval = OperatorPOWL(
        operator=Operator.XOR,
        children=[
            balanced_branch(None),
            balanced_branch("credit"),
            balanced_branch("engineering"),
        ],
    )

    return strict_sequence(
        [
            Transition(label=REG),
            preapproval,
            Transition(label=APP),
            Transition(label=REL),
            Transition(label=ARC),
        ]
    )


# ---------------------------------------------------------------------
# Candidate 3: permissive POWL
# ---------------------------------------------------------------------

def build_permissive():
    credit = Transition(label=CREDIT)
    engineering = Transition(label=ENG)
    supplier_optional = optional_activity(SUP)
    expedite_optional = optional_activity(EXP)

    preapproval = StrictPartialOrder(
        nodes=[
            credit,
            engineering,
            supplier_optional,
            expedite_optional,
        ]
    )

    # Only Expedite Review has explicit principal-check predecessors.
    preapproval.order.add_edge(credit, expedite_optional)
    preapproval.order.add_edge(engineering, expedite_optional)
    preapproval.validate_partial_orders()

    return strict_sequence(
        [
            Transition(label=REG),
            preapproval,
            Transition(label=APP),
            Transition(label=REL),
            Transition(label=ARC),
        ]
    )

def fitting_percentage(result: Dict) -> float:
    """
    Normalize common PM4Py alignment-fitness result keys.
    """
    for key in (
        "percentage_of_fitting_traces",
        "perc_fit_traces",
    ):
        if key in result:
            return float(result[key])

    if "average_trace_fitness" in result:
        return (
            100.0
            * float(result["average_trace_fitness"])
        )

    raise KeyError(
        "Unrecognized fitness result keys: "
        f"{sorted(result)}"
    )


def alignment_accepts(
    labels: Iterable[str],
    net,
    im,
    fm,
    tolerance: float = 1e-9,
) -> bool:
    single_trace_log = pm4py.parse_event_log_string(
        [",".join(labels)]
    )

    result = pm4py.fitness_alignments(
        single_trace_log,
        net,
        im,
        fm,
        multi_processing=False,
    )

    return (
        abs(
            fitting_percentage(result)
            - 100.0
        )
        <= tolerance
    )

The sampled playout is intentionally bounded. Even when every sampled trace fits the manually expected boundary, sampling does not establish that no other trace exists. Conversely, failure to sample a valid rare trace does not establish exclusion. These three models are finite, so a dedicated exhaustive state-space or language enumeration could be added, but generic exhaustive comparison is not available for arbitrary models with loops or unbounded behavior. Fitness, precision, generalization, and simplicity are also descriptive quality indicators; none identifies the true causal process from this log.

# 9. Recommendation and Data-Collection Plan

**Immediate-use recommendation: `model_balanced`.**

It is the best compromise between empirical fit, domain controls, and controlled generalization. It admits every observed trace, preserves the high-confidence suffix and the both-check Expedite prerequisite, and introduces only interpretable unseen behavior. In particular, `E → S → C`, Expedite Review without Supplier Confirmation, and both Supplier/Expedite orders are direct consequences of stated domain hypotheses rather than arbitrary flower-model behavior.

The balanced model should not by itself classify every no-Supplier trace as compliant. Conformance should produce two separate outputs:

1. **Control-flow result:** whether the recorded visible sequence fits `model_balanced`.
2. **Data-quality/eligibility result:** whether Supplier Confirmation was legitimately unnecessary, verified through the external/stocked attribute or source-system reconciliation.

**Sensitivity-analysis recommendation: `model_permissive`.**

Use it to measure how many future cases differ from the balanced candidate only because Supplier Confirmation completes before both principal-check completion events. Those cases are the most informative observations for deciding whether the balanced supplier-precedence interpretation is too strong. The permissive model should not be the sole compliance gate because its Supplier-first traces may conceal genuine violations.

The conservative candidate remains valuable as a regression baseline: every trace accepted by it was literally observed. The gap between conservative and balanced quantifies controlled generalization; the gap between balanced and permissive quantifies start/completion uncertainty.

**Concrete data-collection plan**

| Main ambiguity                                            | Data to collect                                                                                                                                                   | How it resolves the ambiguity                                                                                                                                          |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sequential versus overlapping Credit and Engineering work | `lifecycle:start` and `lifecycle:complete` for both activities; activity instance ID; assigned resource; pause/resume timestamps where available                  | `C_complete ≤ E_start` consistently supports S1. Overlapping intervals support S2. Alternating non-overlapping orders support a case-type XOR rather than concurrency. |
| Timestamp ties and ingestion artifacts                    | Original source timestamp with maximum precision, ingestion timestamp, ingestion index, source event UUID, update/version number                                  | Separates genuine completion order from arbitrary ordering of equal-time events.                                                                                       |
| True Supplier optionality versus missing events           | `component_source ∈ {stocked, external}`, `supplier_required`, component IDs, supplier IDs, source-system event count, extraction status, integration-error code  | Allows a data-guarded branch and identifies external cases where missing `S` is a log-quality defect.                                                                  |
| Supplier dependency on Credit versus Engineering          | Supplier activity start time plus a `supplier_trigger_source` field such as `credit`, `engineering`, `both`, or `manual`; optionally an “information ready” event | Tests whether supplier work actually starts after one completed check, after an intermediate signal, or independently.                                                 |
| Expedite legality                                         | Expedite start and completion times, trigger reason, authorizing role, and a snapshot of the completion state of Credit and Engineering at Expedite start         | Directly tests D6/S6 rather than inferring eligibility from total completion order.                                                                                    |
| Supplier/Expedite relative order                          | Lifecycle intervals for both activities                                                                                                                           | Distinguishes true sequence from overlap with variable completion order.                                                                                               |
| One versus multiple Supplier Confirmations                | Component-to-event linkage or an object-centric log connecting Order, Component, Supplier Request, and Confirmation objects                                       | Determines whether repeated `S` is legitimate component-level behavior rather than rework or duplication.                                                              |
| Policy versus actual behavior                             | Policy version, order type, market, customer segment, risk band, and exception authorization                                                                      | Tests whether S1 and S2 apply to different scopes rather than being globally contradictory.                                                                            |

**Maximally informative future traces and observations**

* `R,E,S,C,A,L,Z` with accurate lifecycle timestamps. This distinguishes conservative enumeration from the balanced symmetric supplier hypothesis.
* `R,S,C,E,A,L,Z` or `R,S,E,C,A,L,Z`. These distinguish balanced from permissive, but only start timestamps can determine whether D5 was actually respected.
* `R,C,E,X,A,L,Z` on a confirmed stocked-component case. This tests whether Expedite Review is independent of Supplier Confirmation.
* An external-component case with no logged `S`, accompanied by successful source-system reconciliation. This would challenge S3/D4; the same trace accompanied by an integration failure would support a missing-event interpretation instead.
* Cases where Credit and Engineering share a completion timestamp but have distinct source times. These quantify how much observed bidirectionality is generated by ingestion ordering.
* A sufficient number of cases with `S < X` and `X < S` under comparable order types. This tests whether the relationship is genuine incomparability or condition-dependent routing.
* Orders with several external components and more than one Supplier Confirmation. These test the current aggregate single-occurrence abstraction.
* A case with Expedite Review starting before one principal check completes. If authorized and legitimate, it would directly falsify D6 as currently modeled; if unauthorized, it becomes a valuable negative compliance example.

# 10. Uncertainty Statement

A material alternative interpretation is that **S1 is the actual hard process rule**: Credit Check completes before Engineering Review starts, while Engineering-first traces result from incorrect timestamps, label semantics, or ingestion defects. Under that interpretation, the balanced partial-order model would admit prohibited behavior. The preferred model would instead contain `C → E`, and the 11 Engineering-first traces would be investigated as data-quality or conformance deviations rather than used to infer independence.

A second material alternative is that **Supplier Confirmation is mandatory in all 30 cases and every no-Supplier trace is an integration omission**. In that case, both balanced and permissive unguarded Supplier optionality are too lenient for compliance. The normative model should require `S`, while conformance checking should use missing-event-aware alignments or a separate observation model to explain absent log events.
