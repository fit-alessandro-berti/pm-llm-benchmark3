## 1. Modeling assumptions

- **Object types and capitalization:** singular, capitalized type labels: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.
- **E2O qualifier vocabulary:**  
  `created`, `receiving_order`, `added_item`, `reserved_for_order`, `reserved_item`, `packed_package`, `packed_item`, `packing_order`, `dispatched_package`, `dispatch_delivery`, `dispatch_order`, `issued_invoice`, `billed_order`, `recorded_payment`, `payment_target_invoice`, `confirmed_delivery`, `confirmed_package`, `confirmed_order`, `closed_order`.
- **O2O direction convention:** source `ocel:oid`  target `ocel:oid_2`:
  - `Order contains Item`
  - `Package packs Item`
  - `Delivery carries Package`
  - `Invoice bills Order`
  - `Payment partially_settles Invoice`  
  Both `M1` and `M2` use `partially_settles`, since the narrative says they are partial payments and gives no invoice total to prove completion.
- **Direct logistics/financial E2O policy:**  
  Logistics events directly relate to the physically involved Package/Delivery/Item objects and, for packing/dispatch/confirmation, also to the affected `Order` objects using explicit order-fulfillment qualifiers. Items are linked only where they are added, reserved, or packed. Financial events link `Record Payment` directly to `Payment` and `Invoice`; they do **not** link directly to Orders. `Issue Invoice` directly links the `Invoice` and the billed Orders.
- **Propagation distinction:** O2O remains structural (`contains`, `packs`, `carries`, `bills`, `partially_settles`). E2O qualifiers such as `dispatch_order` or `confirmed_order` mean “operationally affects this order,” not “this order is the same object as the package/delivery.” Payment-to-Order effects are intentionally only reachable via `Payment -> Invoice -> Order` O2O propagation; if materialized analytically, they should be kept separate or tagged as derived.
- **PM4Py version assumption:** the code assumes the stated constructor `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` exists. If a PM4Py version differs, isolate that constructor line and replace it with the version-specific OCEL factory while keeping the four DataFrames and their semantics unchanged.

## 3. Data-model audit

### Object types and objects

| Object type | Objects |
|---|---|
| `Order` | `O100`, `O200` |
| `Item` | `I1`, `I2`, `I3` |
| `Package` | `P1`, `P2` |
| `Delivery` | `D1`, `D2` |
| `Invoice` | `V1` |
| `Payment` | `M1`, `M2` |

### O2O qualifiers and cardinality

Direction is always source `ocel:oid`  target `ocel:oid_2`.

| Qualifier | Direction | Cardinality in data | Rows |
|---|---|---|---|
| `contains` | `Order`  `Item` | 1:N from order to items; each item has one order here | `O100-I1`, `O100-I2`, `O200-I3` |
| `packs` | `Package`  `Item` | 1:N from package to items; each item is in one package here | `P1-I1`, `P1-I3`, `P2-I2` |
| `carries` | `Delivery`  `Package` | 1:1 in this data | `D1-P1`, `D2-P2` |
| `bills` | `Invoice`  `Order` | 1:N; `V1` bills both orders | `V1-O100`, `V1-O200` |
| `partially_settles` | `Payment`  `Invoice` | N:1; two payments to one invoice | `M1-V1`, `M2-V1` |

### Activity-to-object-type audit

| Activity | Object types touched by E2O relations |
|---|---|
| `Create Order` | `Order` |
| `Add Item` | `Order`, `Item` |
| `Reserve Stock` | `Order`, `Item` |
| `Pack Package` | `Package`, `Item`, `Order` |
| `Dispatch Package` | `Package`, `Delivery`, `Order` |
| `Issue Invoice` | `Invoice`, `Order` |
| `Record Payment` | `Payment`, `Invoice` |
| `Confirm Delivery` | `Delivery`, `Package`, `Order` |
| `Close Order` | `Order` |

The most consequential E2O relations are in `e07` (`Pack Package P1`), `e11` (`Issue Invoice V1`), and `e13` (`Confirm Delivery D1`). `e07` synchronizes `I1` and `I3` into one package and links that package to both `O100` and `O200`. `e11` synchronizes both orders into the same invoice `V1`. `e13` confirms the shared package `P1` for both orders, creating strong convergence in object-centric views and duplicated shared events in flattened Order traces.

## 4. Expected flattened behavior

### Order flattening

- Approximate `O100` trace: `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Dispatch Package  Dispatch Package  Issue Invoice  Confirm Delivery  Confirm Delivery  Close Order`.
- Approximate `O200` trace: `Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order`.
- Copied shared events: `e06 Reserve Stock`, `e07 Pack Package P1`, `e09 Dispatch Package P1`, `e11 Issue Invoice V1`, and `e13 Confirm Delivery D1` appear in both order traces.
- Omitted lifecycle aspects: payment recording and settlement amounts are not directly attached to Orders; item/package identity and O2O composition are lost; `V1` identity and payment allocation are not visible in a plain flattened activity trace.
- Likely DFG edges: `Create Order  Add Item`; `Add Item  Add Item` for `O100`; `Add Item  Reserve Stock`; `Reserve Stock  Pack Package`; `Pack Package  Pack Package` for `O100`; `Pack Package  Dispatch Package`; `Dispatch Package  Dispatch Package` for `O100`; `Dispatch Package  Issue Invoice`; `Issue Invoice  Confirm Delivery`; `Confirm Delivery  Confirm Delivery` for `O100`; `Confirm Delivery  Close Order`.
- Misleading interpretations: shared `P1` activities appear as though each order independently packed, dispatched, and confirmed the same package. Counting events across traces double-counts shared physical work. The flattened Order view also hides that `P1` combines items from different orders and that `V1` bills both orders.

### Package flattening

- Approximate `P1` trace: `Pack Package  Dispatch Package  Confirm Delivery`.
- Approximate `P2` trace: `Pack Package  Dispatch Package  Confirm Delivery`.
- Copied shared events: the pack/dispatch/confirm events are shared with orders/items/deliveries, but each package trace contains its own single occurrence. The flattening loses the multiplicity of items and orders attached to `P1`.
- Omitted lifecycle aspects: item composition of packages, order membership, invoice/payment events, and order closure.
- Likely DFG edges: `Pack Package  Dispatch Package  Confirm Delivery`.
- Misleading interpretations: both packages look like identical three-step lifecycles. This hides that `P1` is a cross-order consolidation of `I1` and `I3`, while `P2` only contains `I2` for `O100`. The next-day confirmation of `D2`/`P2` is also compressed to the same activity sequence.

### Delivery flattening

- Approximate `D1` trace: `Dispatch Package  Confirm Delivery`.
- Approximate `D2` trace: `Dispatch Package  Confirm Delivery`.
- Copied shared events: `e09/e13` are shared with `P1` and Orders; `e10/e14` are shared with `P2` and `O100`. In Delivery flattening each appears once per delivery.
- Omitted lifecycle aspects: package contents, affected orders, invoice/payment activity, and order closure.
- Likely DFG edges: `Dispatch Package  Confirm Delivery`.
- Misleading interpretations: the delivery process looks trivially simple and independent. It hides that `D1` carries a package containing items from two orders, and that confirmation timing differs between `D1` and `D2`.

### Invoice flattening

- Approximate `V1` trace: `Issue Invoice  Record Payment  Record Payment`.
- Copied shared events: `e11 Issue Invoice` is shared with `O100` and `O200`, but appears once in the invoice trace. `e12` and `e15` are payment events directly linked to `V1`.
- Omitted lifecycle aspects: which orders are billed, package/item/delivery context, order closure, and any explicit allocation of payment amounts to `O100` versus `O200`.
- Likely DFG edges: `Issue Invoice  Record Payment`; `Record Payment  Record Payment`.
- Misleading interpretations: the two payment events have the same activity label, so the trace can look like a loop or repeated action. Without the invoice total, one cannot prove that `M2` completes settlement; the narrative only supports partial settlement.

Flattening on `Payment` would be particularly weak because `M1` and `M2` each occur in a single event. Each Payment case would be a one-event trace (`Record Payment`), giving no meaningful internal sequence and no context unless joined to `V1` or Orders via O2O.

## 5. Expected object-centric structures

- **OC-DFG:** Per-object directly-follows paths should show `Order` paths containing create/add/reserve/pack/dispatch/invoice/confirm/close, with `O100` additionally having `P2`-related pack/dispatch/confirm events. `P1` is the key convergence point: `I1` and `I3` both flow into `Pack Package`, and `O100`/`O200` both connect to the same `P1` pack/dispatch/confirm activities. `V1` creates financial convergence: `O100` and `O200` both connect to `Issue Invoice`, and `M1`/`M2` both connect to later payment events on `V1`.
- **OTG:** At object-type level, expect edges between `Order-Item`, `Order-Package`, `Order-Delivery`, `Package-Item`, `Package-Delivery`, `Invoice-Order`, and `Invoice-Payment`. The graph will not show that `P1` specifically combines `O100`/`O200`, but it will reveal that Package and Delivery are not isolated from Orders due to packing, dispatch, and confirmation relations.
- **ET–OT graph:** Event types touching multiple object types will stand out: `Pack Package` touches `Package`, `Item`, and `Order`; `Dispatch Package` and `Confirm Delivery` touch `Package`, `Delivery`, and `Order`; `Issue Invoice` touches `Invoice` and `Order`; `Record Payment` touches `Payment` and `Invoice`. This graph highlights why flattening on any single type loses part of the story.
- **Object-centric Petri net:** Expect places/tokens per object type and transitions for activities, with strong synchronization at `Pack Package P1` over `P1`, `I1`, `I3`, `O100`, and `O200`; at `Issue Invoice V1` over `V1`, `O100`, and `O200`; and at payment recording over `M1`/`M2` and `V1`. The net should not be interpreted as uniquely determined; variable arcs or multiple-token behavior for `P1`, `V1`, and the partial payments may be represented differently across PM4Py versions.
- **Object-interactions summary:** Expect high interaction counts for `Order-Item` from add/reserve/pack, `Package-Item` from pack, `Delivery-Package` from dispatch/confirm, `Invoice-Order` from invoice issue, and `Payment-Invoice` from payment recording. Because of the stated rich E2O policy, the summary will also show `Order-Package` and `Order-Delivery` interactions. `P1` connects `O100` and `O200`; `V1` connects `O100`, `O200`, `M1`, and `M2`; `M1` and `M2` both interact with the same invoice.

## 6. Modeling alternatives

1. **Source-minimal E2O relations:** Link only objects explicitly named in the event text. For example, `Dispatch Package P1 in Delivery D1` would link `P1` and `D1` but not Orders; `Confirm Delivery D1` would link only `D1`; `Record Payment M1` would link only `M1` and `V1`. This yields sparser OTG/ET-OT graphs and shorter flattenings: Delivery traces still show dispatch/confirm, but Order traces omit dispatch/confirm unless O2O propagation is applied analytically. It reduces relation inflation but may underrepresent operational Order fulfillment.
2. **Full operational involvement:** Propagate E2O links to every object plausibly affected: dispatch/confirm `P1` would link `O100`, `O200`, `I1`, and `I3`; invoice issue might link all contained items; payments might link Orders through `V1`. This produces much denser object-centric graphs, longer flattened Order/Item traces, more shared-event duplication, and a more connected Petri net. It is useful for Order-level KPIs but risks overcounting and confusing inference with observation.
3. **O2O-propagated analytical relations:** Keep the source OCEL source-minimal, then derive enriched per-object projections using `contains`, `packs`, `carries`, `bills`, and `partially_settles`. Discovery on the source OCEL stays faithful to observed E2O facts, while analytical Order views can include delivery confirmation or payment effects via `P1`/`V1`. The trade-off is that these derived relations should be materialized separately or qualified as derived, not silently mixed with source E2O observations.
4. **Qualifier-stratified modeling:** Keep the same rows but enforce a clear qualifier taxonomy such as `observed_on`, `fulfills`, `affects`, and `derived_from`. This does not change the business story, but it lets analyses filter direct observations from operational involvement and propagation, reducing semantic ambiguity.

## 7. Failure modes

1. **Relation inflation:** Linking every downstream event to every reachable Order or Item through O2O creates many extra E2O rows. Shared events such as `Pack Package P1`, `Dispatch Package P1`, `Issue Invoice V1`, and `Confirm Delivery D1` would be counted repeatedly, inflating frequencies and creating artificial convergence.
2. **Missing direct E2O links:** If `Pack Package P1` is linked only to `P1` but not to `I1`, `I3`, `O100`, and `O200`, the OCEL cannot directly show that `P1` combines two orders. Flattening on Order/Item then omits a central business fact.
3. **Treating O2O propagation as observation:** Inferring that a payment was directly recorded against `O100` or `O200` from `M1 -> V1 -> Order` is an analytical propagation. If reported as a source E2O fact, it overstates what the source system observed.
4. **Duplicate shared events after flattening:** `e07`, `e09`, `e11`, and `e13` appear in both `O100` and `O200` Order projections. Treating these copies as independent work double-counts physical packages, dispatches, invoices, and confirmations.
5. **Ambiguous payment allocation:** `M1` and `M2` both partially settle `V1`, but no amount is assigned to `O100` or `O200`. Any order-level payment allocation is an assumption, not a derived fact.
6. **Overly short Payment traces:** Flattening on `Payment` gives one event per payment, so `M1` and `M2` produce length-one traces. No payment-internal process can be discovered without returning to the Invoice or Order context.
7. **Constructor/API version mismatch:** PM4Py versions may differ in `OCEL(...)` arguments or function names. Changing the DataFrames to force a different constructor can silently alter semantics; isolate the constructor and adapt only that line.
8. **False total order for same-time events:** This example has no timestamp ties, but a robust pipeline should sort by timestamp plus a stable tie-breaker such as `ocel:eid`. Sorting only by timestamp can create arbitrary DFG edges if ties are introduced later.
9. **Orphan or duplicate relations:** Typos in `ocel:eid`/`ocel:oid`, duplicate relation rows, or activity/timestamp mismatches break referential integrity and distort discovery. The validation assertions guard against this.
10. **Overinterpreting the object-centric Petri net:** The discovered net, especially around multi-object transitions such as `Pack Package P1` and `Issue Invoice V1`, may have multiple defensible representations. It should not be presented as a uniquely determined process model.
