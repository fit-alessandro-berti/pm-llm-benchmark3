## 1. Temporal Data Semantics

**State reconstruction.** For every case, events are ordered by `(time:timestamp, event_index)` ascending — timestamp first, `event_index` as tie-breaker (R7). For each attribute (amount, risk_level, jurisdiction, customer_type, exemption_id), the *state at time t* is the value written by the **latest event with timestamp  t** (using the tie-break order for equal timestamps) whose cell for that attribute is non-blank. This is a per-attribute, per-case forward-fill — never a global/final-value copy.

**Blanks.** A blank cell means "no update at this event." It must never be coerced to `0`, `""`, `False`, `LOW`, or any other default. Blanks are simply skipped when computing the last-known value; if no prior event ever set the attribute, the value is `UNKNOWN`, not a default.

**Equal timestamps.** When two events share a timestamp, `event_index` fixes the order; an event with a lower `event_index` is treated as strictly prior for state-update purposes. This matters directly in TX-311 (Enhanced_Review = index 3, Update_Jurisdiction = index 4, both 16:20  the jurisdiction change is *after* the review).

**Material change identification.** A change is "material" for R4 only if it is an amount **increase** exceeding 20% relative to the amount known at the time of the review being tested. Decreases are never material for invalidation. An increase computed *from an unknown base* is not safely classifiable and must be flagged, not silently ignored or silently treated as material.

**Final attributes vs. governing attributes.** The last row of a case is not automatically what governed an earlier obligation. Every obligation is evaluated using the state *as of the triggering event's timestamp* (event-time semantics), never the case's terminal values (R7). This is why TX-301's Release_Funds must use the amount as of 08:25 (125,000), not some later value, and why TX-311's Release_Funds must use jurisdiction as of 16:30 (DE) rather than the value at the time Enhanced_Review ran (US).

**Four distinct time axes:**
- **Event time** — the row's `time:timestamp` (when the system recorded the fact).
- **Effective time** — when a fact/approval is asserted to hold (e.g., exemption `effective_from`); may differ from event time.
- **Record time** — when a database write occurred (`Record_Exemption` insert time); may lag true approval (outage) or may be the *only* trustworthy anchor if no independent signature exists.
- **Evidence time** — when independently verifiable proof (qualified signature, hash, screening log) was created; this is what actually adjudicates disputes between effective time and record time (R5). EX-77 and EX-88 are distinguished entirely by evidence time vs. displayed effective time.

## 4. Ambiguities and Alternative Readings

**TX-302 (exemption / late record).** Result hinges on treating the qualified digital signature (09:05) as the operative evidence time, with the 11:00 DB insert explained by a documented outage (R5's explicit allowance that late records can evidence earlier approval). *Alternative reading:* if the signature's binding to EX-77's specific terms (scope/amount ceiling) were doubted, or if the "outage" explanation were unverified, the exemption could be deemed unproven — but the case would *still* be COMPLIANT because Enhanced_Review independently satisfies R1. The only way to flip this case to NONCOMPLIANT is if evidence emerged that Enhanced_Review@09:20 did not reflect current (180k, GB) data, e.g., a hidden intervening amount jump before Release that the review didn't see.

**TX-305 (missing amount).** The finding treats the underlying amount as genuinely INDETERMINATE at the fact level, but argues the *compliance outcome* is invariant across both possible branches (amount<100k  R1 not triggered; amount100k  Enhanced_Review satisfies R1), yielding COMPLIANT. *Alternative reading:* if one holds that Settlement_Confirmed (150,000, next day) is strong retroactive evidence that the release-time amount was already 100k, that only reinforces the same conclusion (Enhanced_Review present). *But* if evidence surfaced that the settlement amount reflects a *different* transaction leg (e.g., fees added post-release) or that no reliable link exists between release-time and settlement-time amounts (as the note itself warns: "no immutable release payload"), the safest position is to keep the underlying amount INDETERMINATE while still reporting the *decision* as COMPLIANT — precisely the "resolved indeterminacy" case requested. If instead an auditor believed Enhanced_Review might not have addressed the true current amount at all (e.g., if it were shown to be a template review with no real diligence), the classification would properly regress to INDETERMINATE.

**TX-310 (conflicting exemption evidence).** Classified NONCOMPLIANT because the only independently verifiable timestamp (signing certificate, 10:30) postdates release (10:00), and the sole earlier-approval testimony comes from an interested party (the requester), which R5 treats as insufficient standing alone. *Alternative reading:* if an unbiased, contemporaneous record (e.g., an email or system log independent of the requester, timestamped 10:00) surfaced corroborating the 08:45 oral approval, EX-88 could become valid and the case would move to JUSTIFIED_EXCEPTION. Absent that, treating this as INDETERMINATE rather than NONCOMPLIANT is defensible if one holds that "insufficient evidence of exemption" is different from "insufficient evidence of the underlying trigger" — but per R5 the burden is on demonstrating exemption validity, and unmet burden means the R1 obligation stands unsatisfied, which is more precisely NONCOMPLIANT than INDETERMINATE.

**TX-311 (same-timestamp reordering).** The result depends entirely on the explicit tie-break: Enhanced_Review (idx 3) before Update_Jurisdiction (idx 4). *Alternative reading:* if the source system's `event_index` were not trustworthy (e.g., batch-inserted out of true order), or if the jurisdiction change were later shown to be a data-entry correction reflecting a jurisdiction that was *actually* true all along (not a new fact), then the "review under US, then flip to DE" pattern would look like evasion rather than a legitimate correction, and a human reviewer might reasonably require a fresh Enhanced_Review under confirmed DE jurisdiction before trusting the release. Absent such evidence, the literal rule (current-state evaluation at release) yields COMPLIANT, but this is flagged rather than closed.

**Two further cases:**
- **TX-306:** If the post-approval Update_Amount (+4.5%) had instead been 20%, both R1 and R2's amount-dependent basis would be invalidated, flipping this to NONCOMPLIANT despite the earlier Enhanced_Review/Compliance_Approve sequence — illustrating how close the non-materiality threshold is to changing the outcome.
- **TX-308:** If the "decrease" note were wrong and Update_Amount actually represented a later *increase* misrecorded, R4's decrease-exception would not apply, and the case would need re-evaluation for whether the amount at review time (140,000) vs. release time (100,000) changes the review's currency — a reminder that classification is only as good as the correctness of the note-level metadata.

# ---------- 1. Load ----------
df = pd.read_csv(io.StringIO(CSV))
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)

# Preserve source order strictly as (timestamp, event_index) -- R7 tie-break
df = df.sort_values(["case:concept:name", "time:timestamp", "event_index"]).reset_index(drop=True)

if HAVE_PM4PY:
    df = pm4py.format_dataframe(
        df, case_id="case:concept:name",
        activity_key="concept:name", timestamp_key="time:timestamp"
    )

# ---------- 2. Forward-fill without leaking future values backward ----------
ATTRS = ["amount", "risk_level", "jurisdiction", "customer_type", "exemption_id"]

def ffill_within_case(group):
    group = group.sort_values(["time:timestamp", "event_index"])
    for a in ATTRS:
        group[a] = group[a].ffill()  # forward only: never uses a later row's value
    return group

df = df.groupby("case:concept:name", group_keys=False).apply(ffill_within_case)

# Flag rows where an attribute has NEVER been set yet (true unknown, not "defaulted")
for a in ATTRS:
    df[f"{a}_unknown"] = df.groupby("case:concept:name")[a].transform(
        lambda s: s.isna()
    )

# ---------- 3. Track latest review/screen/approval/change events per case ----------
REVIEW_ACTS = {
    "Standard_Review": "last_standard_review",
    "Enhanced_Review": "last_enhanced_review",
    "Compliance_Approve": "last_compliance_approve",
    "Sanctions_Screen": "last_sanctions_screen",
    "Sanctions_List_Update": "last_sanctions_list_update",
}

def compute_latest_events(case_df):
    case_df = case_df.sort_values(["time:timestamp", "event_index"]).copy()
    trackers = {v: pd.NaT for v in REVIEW_ACTS.values()}
    tracker_idx = {v: None for v in REVIEW_ACTS.values()}
    out_rows = []
    prev_amount = None
    last_material_change_ts = pd.NaT
    for _, row in case_df.iterrows():
        act = row["concept:name"]
        # material amount-increase detection (R4): compare against last known amount
        cur_amount = row["amount"]
        if act == "Update_Amount" and pd.notna(cur_amount):
            if prev_amount is not None and pd.notna(prev_amount) and prev_amount > 0:
                pct = (cur_amount - prev_amount) / prev_amount
                if pct > 0.20:
                    last_material_change_ts = row["time:timestamp"]
            elif prev_amount is None:
                row["amount_increase_from_unknown"] = True
            prev_amount = cur_amount
        elif pd.notna(cur_amount):
            prev_amount = cur_amount

        snap = dict(row)
        for act_name, field in REVIEW_ACTS.items():
            snap[field] = trackers[field]
        snap["last_material_change_ts"] = last_material_change_ts
        out_rows.append(snap)

        if act in REVIEW_ACTS:
            trackers[REVIEW_ACTS[act]] = row["time:timestamp"]
    return pd.DataFrame(out_rows)

df = df.groupby("case:concept:name", group_keys=False).apply(compute_latest_events)

# ---------- 4. Extract state at Release_Funds ----------

    """R4: is a review invalidated by a >20% increase strictly after review_ts?"""
    if pd.isna(review_ts):
        return None  # no review exists at all
    lm = release_row["last_material_change_ts"]
    if pd.isna(lm):
        return False
    return lm > review_ts

    lambda j: (pd.notna(j)) and (j != "DE")
)
releases["r1_triggered"] = releases["r1_amount_ge_100k"] & releases["r1_jurisdiction_foreign"]
releases["r1_enhanced_review_present"] = releases["last_enhanced_review"].notna()
releases["r1_enhanced_review_after_material_change"] = releases.apply(
    lambda r: (pd.notna(r["last_enhanced_review"]) and
               (pd.isna(r["last_material_change_ts"]) or
                r["last_enhanced_review"] >= r["last_material_change_ts"]) and
               r["last_enhanced_review"] < r["time:timestamp"]),
    axis=1
)

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A conformance checker that reads a case's *last* attribute values (e.g., pandas `groupby().last()`) would judge TX-301's Release_Funds using amount=125,000 correctly by luck, but would judge TX-311 using DE for *every* event, wrongly implying the Enhanced_Review was evaluated against a DE-context trigger it never saw, and would misjudge TX-308's earlier Enhanced_Review as covering a 100,000 amount it may not have addressed as a decrease.

2. **Post-hoc exemptions.** A trace-only check sees "Release_Funds" followed later by "Record_Exemption" (TX-302, TX-310) and cannot distinguish a *timely* approval evidenced by an out-of-band signature (EX-77, valid) from a *backdated* approval whose only proof postdates release (EX-88, invalid). Control-flow ordering of the *logged* Record_Exemption event is actively misleading in both directions.

3. **Material changes after review.** Whether an Update_Amount invalidates a preceding review depends on a *percentage threshold* computed over data values, not on activity adjacency. Control-flow conformance sees "Review  Update_Amount  Release" in TX-308 and TX-309 identically, yet one is compliant (decrease) and the other is not (two compounding >20% increases).

4. **Conditional activation.** R1/R2/R3 obligations are *conditionally* triggered by data (jurisdictionDE, amount100k, risk=HIGH/PEP, sanctions-list state). A control-flow model would either always require Enhanced_Review (over-constraining domestic low-value cases like TX-307's R1 aspect) or never require it (under-constraining TX-301), because Petri nets/DECLARE constraints have no native notion of a numeric or categorical guard evaluated at a specific instant.

5. **Missing data.** Trace conformance typically treats an absent attribute as either an automatic pass or an automatic fail depending on encoding choices; neither matches the required behavior (explicit INDETERMINATE classification, as in TX-305) unless the model is augmented with a third truth value that most DECLARE/Petri-net formalisms don't natively support.

6. **Same-timestamp ordering.** Standard log-based conformance tools that sort only by timestamp (not `event_index`) would nondeterministically order Enhanced_Review and Update_Jurisdiction in TX-311, sometimes concluding the review reflects the DE state and sometimes the US state — producing an unstable, non-reproducible verdict for the same log.

*(Additional, non-exhaustive: control-flow checkers cannot express "N% of a numeric field," cannot express scope-matching between two independent records (exemption register vs. case), and cannot weigh conflicting evidence quality — all of which are decisive in this case set.)*

## 7. Recommended Logging and Control Improvements

- **Immutable release payload:** At `Release_Funds`, snapshot and hash the full attribute state (amount, jurisdiction, risk, customer_type, exemption_id) actually used for the decision, stored append-only, so later disputes (TX-305) don't depend on inferring release-time values from unrelated downstream events.
- **Separate effective / record / signature timestamps:** Every exemption and review record should carry three distinct timestamps — `effective_from` (business claim), `record_time` (DB write), `evidence_time` (cryptographic signature/witness creation) — with the evidence_time always treated as authoritative over the displayed effective time (directly resolving the EX-77 vs. EX-88 ambiguity class).
- **Rule/policy version tag:** Stamp each obligation check with the policy version (R1–R7 version id) in force at event time, so rule changes don't retroactively alter historical verdicts.
- **Explicit exemption scope object:** Store exemption scope as structured fields (jurisdiction list, customer-type list, amount ceiling, waived-rule ids, expiry) rather than free text, machine-joinable against case state at the exact trigger timestamp.
- **Change provenance:** Every `Update_*` event should log *why* (reason code, source system, requester vs. independent verifier) and *who authorized* the change, so amount/jurisdiction edits occurring suspiciously adjacent to reviews (TX-311) can be automatically flagged for human confirmation rather than silently accepted.
- **Stable, monotonic event ordering key:** Replace/augment `event_index` with a globally unique, monotonic sequence (e.g., a Lamport/HLC timestamp) generated at ingestion, eliminating any ambiguity about same-wallclock-timestamp ordering across distributed source systems.
- **Mandatory non-null sentinel for "unknown":** Represent truly unknown attributes with an explicit `UNKNOWN` sentinel distinct from "no update," so pipelines cannot accidentally conflate "no change" with "no data" during forward-fill.
- **First-class INDETERMINATE outcome in tooling:** Extend whatever conformance/DECLARE tooling is used to natively support a three-valued (True/False/Indeterminate) evaluation so coarse automated flags stop collapsing missing-data cases into false positives or false negatives.
