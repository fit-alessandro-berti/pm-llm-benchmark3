## 1. Control-Objective Decomposition

Nominal rule **FEP-1** (`Prepare_Payment` human $\neq$ `Release_Payment` human) is a structural mechanism, not an end in itself. Its underlying purpose—preventing a single actor from initiating and authorizing an erroneous or fraudulent transfer—decomposes into six distinct threat scenarios and sub-objectives:

| Sub-Objective / Threat Scenario | AV-2 (Automated Validation) | MG-4 (Independent Manager Approval) | RA-7 (Retrospective Audit & Recall) | ED-1 (Emergency Single-Operator Rule) |
|---|---|---|---|---|
| **1. Unintentional clerical or duplicate-payment error** (wrong amount, duplicate invoice, wrong PO reference) | **Preventive (Strong):** Blocks or warns on duplicate invoices, operator limits, and PO mismatches before release (e.g., AP-205). | **Preventive / Hybrid (Moderate):** Detects discrepancies if invoice and PO are substantively checked pre-settlement; fails if rubber-stamped. | **Detective / Partly Corrective:** Detects errors post-release; corrective only if caught within the ~24h bank recall window. | **Preventive Gate:** Caps exposure (< EUR 100k) and mandates un-overridden AV-2 pass before single-user release. |
| **2. Unauthorized payee or bank-account diversion** (vendor master tampering, Business Email Compromise, employee self-diversion) | **Preventive (Moderate–Strong):** Checks bank-account ownership, sanctions, and 7-day bank changes; vulnerable if overridden (AP-202) or offline (AP-208). | **Preventive / Hybrid (Moderate):** Effective only if independent manager verifies bank change authenticity against out-of-band evidence prior to settlement. | **Detective (Weak Corrective):** Fraudsters sweep diverted funds rapidly; bank recall even inside 24h often fails for intentional fraud, and >24h fails almost certainly (AP-202). | **Preventive Gate:** Prohibits use on new vendors (<180d) or recent bank changes (<7d), filtering out classic diversion vectors. |
| **3. Fictitious billing or unreceived goods/services** (fabricated receipts, shell consulting, overbilling) | **Fails to Address:** Cannot verify physical delivery, service performance, or commercial substance (e.g., AP-204 passed AV-2 cleanly). | **Preventive / Hybrid (Strong if substantive):** Independent L3+ review of service receipts and commercial purpose prevents release/settlement; fails if cursory. | **Detective:** Substantive audit catches fabricated receipts (AP-204), though often too late for bank recall if executed days later. | **Indirect Mitigation:** Restricts vendor age ($\ge 180\text{d}$) and value, blocking shell-vendor creation, but relies entirely on MG-4 and RA-7 for receipt verification. |
| **4. | **6. Commercial unreasonableness and authority-limit circumvention** (splitting or pushing excessive emergency transfers without economic justification) | **Preventive (Narrow):** Enforces static operator amount limits and basic PO match, but cannot judge commercial necessity or pricing fairness. | **Preventive / Hybrid:** L3+ business judgment evaluates operational urgency and commercial terms before irrevocable settlement. | **Detective:** Evaluates emergency token justification and commercial validity post-hoc. | **Preventive Gate:** Hard-caps single-user exposure at EUR 100,000 and requires an active pre-preparation emergency token. |

## 2. Equivalence and Sufficiency Test

A compensating-control package is evaluated across seven structural dimensions rather than raw activity counts:
1. **Timing relative to irrevocability:** Does the control act *before* `Release_Payment`, *between* `Release_Payment` and irrevocable `Bank_Settlement` (and if so, is settlement system-gated or merely delayed?), within the `<24h` revocable recall window, or post-settlement?
2. **Actor and session independence:** Are reviewers organizationally independent (no direct performance-rating COI like m09/u23), operating on distinct authenticated sessions/endpoints (unlike u12/u13's shared workstation), and free from shared override credentials?
3. **Threat coverage completeness:** Does the combined package cover master-data integrity, payment accuracy, *and* physical/service receipt validity (closing AV-2's blind spots)?
4. **Overrideability and fail-safe posture:** Does a control failure or warning fail *closed* (blocking release as in AP-205) or fail *open* (allowing unvalidated release during an outage as in AP-208, or permitting self-override via borrowed credentials as in AP-202)?
5. **Recoverability:** Given vendor profile, payment rail, and elapsed time, can an identified defect realistically be stopped or recalled before funds dissipate?
6. **Evidence quality:** Is review backed by verifiable artifacts (signed checklists, service reports, token timestamps, bank-ownership proofs) rather than bare log timestamps?
7. **Collusion resistance:** Does the control architecture resist two-person cliques or routine habituation (e.g., 37 repeated pairings in 30 days)?

### Four-Tier Sufficiency Standard

*   **Tier 1 — Fully Equivalent (`OBJECTIVE_MET`):** Pre-settlement risk reduction matches or exceeds nominal FEP-1 across all relevant threat vectors. Requires un-overridden AV-2 coverage, substantive independent MG-4 review *prior to irrevocable settlement* (ideally pre-release, or pre-settlement with deterministic settlement hold), verified emergency eligibility (ED-1 preconditions met), and timely RA-7 verification within the recall window.
*   **Tier 2 — Partially Equivalent (`OBJECTIVE_PARTIALLY_MET`):** Core threat vectors (payee authenticity, amount accuracy, receipt validity) are substantively checked before irrevocable loss by independent actors/systems, but governance preconditions, sequencing rules, or secondary timing windows suffer technical breaches (e.g., convenience bypass without an emergency token in low-risk AP-201, or minor token/validation sequence inversion in AP-206). Tolerable as an isolated control exception, unacceptable as routine practice.
*   **Tier 3 — Merely Mitigating (Insufficient for high risk; maps to `OBJECTIVE_FAILED` or `INDETERMINATE` depending on exposure/evidence):** Some controls executed (e.g., AV-2 passed, or late audit occurred), leaving critical threat dimensions—such as service receipt authenticity (AP-204) or human/session independence (AP-209)—unverified prior to irrevocable settlement.
*   **Tier 4 — Ineffective (`OBJECTIVE_FAILED`):** Preventive barriers were bypassed, unavailable, or conflicted; detective/corrective controls arrived after irrevocable settlement and outside the recall window (AP-202, AP-208).

### Why "Same Expected Loss" Is Not the Only Standard
Equating control sufficiency solely with $\mathbb{E}[\text{Loss}] = p \times L$ is flawed for four reasons:
1. **Tail-risk and variance aversion:** An unvalidated EUR 900,000 release during a validation outage (AP-208) with a 2% fraud/error probability has the same EUR 18,000 expected loss as ten EUR 1,800 payments with certainty of loss, yet threatens liquidity, material financial misstatement, and catastrophic single-event exposure.
2. **Deterrence and control-culture erosion:** Permitting convenience bypasses on small amounts (AP-201) because $\mathbb{E}[\text{Loss}]$ is tiny normalizes rule-breaking, teaching operators that controls are optional and creating behavioural pathways later exploited in high-value fraud.
3. **Epistemic and audit assurance:** Internal controls must produce *demonstrable proof* of authorization integrity for external auditors and regulators. "No money was stolen by luck" (AP-208) provides zero assurance that the process is under control.
4. **Fiduciary and regulatory non-linearity:** Sanctions breaches (checked by AV-2) or related-party embezzlement (AP-202) carry criminal, regulatory, and reputational penalties orders of magnitude larger than the face transfer amount.

## 4. Preventive–Detective–Corrective Comparison

| Control Mechanism | Primary Classification | Point of Action in Payment Lifecycle | Coverage Strengths | Structural Blind Spots & Failure Modes |
|---|---|---|---|---|
| **FEP-1 (Nominal Four-Eyes)** | **Preventive** | At `Release_Payment` (blocks single-ID execution) | Forces dual-actor participation across master/invoice check and release authorization. | Defeated by shared workstations/credentials (AP-204/209), collusion, or rubber-stamping without underlying document review. |
| **AV-2 (Automated Validation)** | **Preventive** | Pre-`Release_Payment` | Deterministic, 100% population check on duplicates (AP-205), sanctions, operator limits, PO match, and 7-day bank changes. | Blind to fabricated receipts (AP-204), collusion, and session control; defeated if overridable via shared credentials (AP-202) or configured fail-open during outages (AP-208). |
| **MG-4 (Pre-Release: AP-203, AP-206)** | **Preventive** | Before `Release_Payment` | Supplies human judgment on commercial reasonableness and service receipt validity before release authorization occurs. | Weak if cursory/rubber-stamped, conflicted (AP-202), or executed before AV-2 completes (AP-206 sequence gap). |
| **MG-4 (Post-Release, Pre-Settlement: AP-201, AP-207)** | **Hybrid (Workflow-Detective / Loss-Preventive)** | Between `Release_Payment` and `Bank_Settlement` | Catches unauthorized or defective releases inside the treasury pipeline before external funds movement becomes irrevocable. | Depends critically on settlement-hold mechanics (see below); narrow time buffer creates race-condition risk if batch settlement runs automatically. |
| **MG-4 (Post-Settlement: AP-202, AP-208)** | **Detective (Weak)** | After `Bank_Settlement` | Establishes late accountability or triggers belated investigation. | Zero preventive value; if delayed >24h post-settlement, loses even bank-recall corrective leverage. |
| **RA-7 (Retrospective Audit & Recall)** | **Detective (Conditionally Corrective)** | Post-`Release_Payment` (target: $\le 1$ business day / $<24\text{h}$) | Independent line-of-defense (`axx`) capable of uncovering fabricated receipts (AP-204) and cross-case pairing anomalies. | Purely detective after ~24h (AP-202, AP-204, AP-208); bank recall within 24h is best-effort and unreliable against agile fraudsters. |
| **ED-1 (Emergency Permission Framework)** | **Preventive Meta-Control (Risk-Bounding)** | Pre-`Prepare_Payment` through +1 business day | Restricts single-operator blast radius (< EUR 100k, established vendor, static bank) while mandating AV-2, MG-4, and RA-7. | Ineffective if ERP does not technically enforce its preconditions (allowing single-user release without token in AP-201/202, or >100k during AV outage in AP-208). |

### Semantics of Post-Release, Pre-Settlement Manager Action (`Manager_Ratify`)
A manager review executed *after* `Release_Payment` but *before* `Bank_Settlement` (as in AP-201 at `08:30` before `10:00`, and AP-207 at `14:40` before `16:00`) is **semantically hybrid**, and its classification depends on the boundary of reference:
1. **Relative to the internal ERP payment-release workflow, it is detective (and potentially internal-corrective):** The unauthorized or unreviewed `Release_Payment` state transition has already occurred; the manager detects an improper release event and must actively trigger an internal cancellation/abort before the payment file is transmitted or settled.
2. **Relative to the enterprise control objective (preventing irrevocable external fund outflow), it functions as loss-preventive—*if and only if* coupled with an architectural gate or actionable abort capability:**
   * **Hard-gated settlement (Strong Loss-Preventive):** If the treasury interface holds released emergency payments in a staging queue until `Manager_Ratify` is logged, ratification is genuinely preventive against external loss.
   * **Time-buffered batch window (Fragile Hybrid):** If `Bank_Settlement` simply occurs on a periodic sweep (e.g., every two hours at `10:00`, `12:00`, `16:00`) whether or not the manager acts, then ratification is a *detective race against the settlement clock*. Had `m15` been in a two-hour meeting in AP-207, `16:00` settlement would have executed unreviewed, degrading the control to post-settlement detection (exactly what happened to `m21` in AP-208). Treating both architectures as identically "preventive" overstates control reliability when settlement holds are unverified.

## 5. Counterfactual and Residual-Risk Analysis

Qualitative residual-risk bands used below: *Negligible, Low, Moderate, High, Critical*.

### 1. AP-202 (Realized Fraud / Related-Party Diversion — EUR 480,000)
*   **Most plausible loss mechanism:** Insider diversion (`u23` routing EUR 480k to a relative's account disguised as a new vendor, altering bank details 2h before release, and bypassing AV-2 warnings using supervisor `m09`'s credential—either via credential theft, careless sharing, or supervisor collusion).
*   **Control breaking the causal chain:** *None.* Every layer failed: ERP permitted same-user release without an ED-1 token, AV-2 override accepted `m09`'s credential within `u23`'s workflow without independent session/COI blocking, and `m09`/`a03` acted days past irrevocable settlement.
*   **What remains exposed:** Total principal loss (EUR 480k) plus unresolved insider/supervisory integrity compromise across any other payments touched by `u23` or `m09`.
*   **Counterfactual under a truly independent second releaser:** Residual risk drops from **Critical** to **Low–Moderate**. An unconflicted human releaser on a separate session would confront a brand-new vendor, a 2-hour-old bank change, an active AV-2 warning, and *zero receipt confirmation* for EUR 480k, halting release unless deceived by sophisticated forged documentation *and* an authorized manager override.

### 2. AP-203 (Authorized Emergency Repair — EUR 75,000)
*   **Most plausible loss mechanism:** Overbilling, erroneous duplicate dispatch during operational panic, or phantom emergency invoice during a machine breakdown.
*   **Control breaking the causal chain:** Dual preventive barrier—AV-2 verified 4-year vendor history, static bank ownership, and PO match (`10:02`), while independent manager `m02` substantively verified the invoice, bank account, and physical service report *prior to release* (`10:04`), backed by +5h audit (`15:00`).
*   **What remains exposed:** **Low** residual risk—limited to high-effort three-party collusion (`u31` + `m02` + vendor) or sophisticated forgery of the service report that fools both `m02` and `a02`.
*   **Counterfactual under a truly independent second releaser:** Risk remains **Low** (virtually unchanged, shifting only from Low to Negligible–Low). In fact, substantive pre-release review by an independent L3+ manager (`m02`) plus mandatory 5-hour audit arguably provides *stronger* scrutiny of commercial/receipt validity than a routine peer AP clerk releasing in a standard two-person queue.

### 3. AP-204 (Fabricated Consulting Receipt — EUR 220,000)
*   **Most plausible loss mechanism:** Internal-external fraud or two-person collusion (`u12` and `u13` submitting/approving a fabricated consulting receipt for an established vendor, or one operator controlling both logins on their shared workstation) to extract EUR 220k.
*   **Control breaking the causal chain:** Pre-settlement chain was *not* broken; AV-2 cannot inspect receipt authenticity, and `u13` failed to challenge it. `a07` broke concealment at +4 days (detective), exposing the scheme and stopping *future* iterations, though too late for standard 24h bank recall.
*   **What remains exposed:** **Critical** recovery risk on the EUR 220k consulting transfer (dependent on vendor clawback/litigation) and systemic exposure across the 36 other `u12`/`u13` paired payments in the prior 30 days.
*   **Counterfactual under a truly independent second releaser:** Residual risk drops from **Critical** to **Moderate**. A genuinely independent releaser on a separate workstation (rotated randomly rather than paired 37 times) breaks single-workstation credential abuse and casual two-person collusion; however, if the fabricated consulting receipt was visually convincing and matched a valid PO, a clerk without domain knowledge of the consulting engagement could still be deceived unless L3+ budget-owner receipt sign-off (MG-4) is required for high-value intangibles.

### 4. AP-206 (Production Outage with Late Emergency Token — EUR 95,000)
*   **Most plausible loss mechanism:** Post-hoc rationalization of an unauthorized rush payment, or approval of an unvalidated payment because `m11` approved at `13:04`—one minute *before* AV-2 ran at `13:05`.
*   **Control breaking the causal chain:** AV-2 (`13:05`) still gated `Release_Payment` (`13:08`) on a 3-year static vendor, `m11` reviewed independently before release, and `a05` audited within 19 hours (inside the recall window).
*   **What remains exposed:** **Low–Moderate** governance/process risk: if ERP architecture allows emergency tokens to be minted *after* `Prepare_Payment` (`13:02` vs `13:00`) and lets managers approve prior to automated validation results, an approver may rely on assumed system checks that have not yet run.
*   **Counterfactual under a truly independent second releaser:** Residual governance risk drops from **Low–Moderate** to **Low**, eliminating ED-1 token-timing ambiguity, though operational downtime cost during the `12:40` production outage could increase if no second operator was available.

### 5. AP-208 (EUR 900,000 Release During Validation Outage)
*   **Most plausible loss mechanism:** Opportunistic BEC / vendor bank-account hijacking (exploiting the 3-day-old bank change during an AV-2 outage, or intentional DoS/timing exploitation when validation is down) resulting in an irreversible EUR 900k wire.
*   **Control breaking the causal chain:** *None.* AV-2 failed open (`15:01`), the manual fallback checklist went unsigned, single-user release bypassed the EUR 100k ED-1 limit by 9x (`15:04`), `Bank_Settlement` locked in irrevocability in 56 minutes (`16:00`), and `m21`/`a08` arrived days too late. Only external fortune (the 3-day-old bank change happened to be legitimate) averted a EUR 900k loss.
*   **What remains exposed:** **Critical** structural process risk—the payment platform demonstrably permits single-user, sub-hour, million-euro settlements with recent bank changes when validation microservices go offline.
*   **Counterfactual under a truly independent second releaser:** Residual risk drops from **Critical** to **Moderate–High** (not Low!). Without AV-2 bank-ownership verification, even a conscientious second human releaser lacks automated sanctions/ownership telemetry; unless that second releaser strictly enforces the unsigned manual out-of-band bank callback checklist, two humans can still jointly release a sophisticated BEC invoice during a system outage.

### 6. AP-209 (Repeated Pair on Shared Workstation — EUR 42,000)
*   **Most plausible loss mechanism:** Latent single-actor control masquerading as dual control (`u12` using `u13`'s unlocked session on the shared terminal, or habitual mutual rubber-stamping within an isolated two-person cell).
*   **Control breaking the causal chain:** AV-2 (`16:02`) protected vendor/bank/PO baselines and `a07` (`+18h`) verified transaction legitimacy within the 24h recall window.
*   **What remains exposed:** **Moderate** structural vulnerability—if `u12`/`u13` independence is illusory, any non-PO or service-based invoice routed through them (like AP-204) bypasses human segregation of duties.
*   **Counterfactual under a truly independent second releaser:** Residual risk drops from **Moderate** to **Low**, restoring genuine dual-human scrutiny and eliminating shared-endpoint ambiguity.

## 6. Evidence and Monitoring Recommendations

### Evidence Collection & Logging Enhancements
1. **Mandatory Event-Log Capture of `Bank_Settlement` and Token Lifecycle:** Record `Emergency_Token_Created`, `Emergency_Token_Expired`, and `Bank_Settlement` natively in the event log for *all* cases (eliminating side-channel reliance seen in AP-201 through AP-204).
2. **Cryptographic Session & Endpoint Telemetry:** Log `session_id`, `workstation_id`, `ip_address`, and authentication method (MFA/SSO token subject) on every human event—especially `Override_Warning`, which must bind to the *authorizing manager's* authenticated session rather than allowing credential entry inside the operator's session (closing the AP-202 vulnerability).
3. **Hard System Gates (Fail-Closed Architecture):**
   * Block `Release_Payment` when `Prepare_Payment` user == `Release_Payment` user *unless* a valid pre-prep emergency token exists, amount $<$ EUR 100,000, and AV-2 returned a clean pass (preventing AP-201, AP-202, AP-208).
   * Hold `Bank_Settlement` in treasury staging on all ED-1 cases until an independent L3+ manager (`hr_supervisor != True`) logs `Manager_Approve` or `Manager_Ratify` with mandatory artifact-view attestation.

### Continuous Monitoring Rules

| Metric / Rule | Detection Logic & Threshold | Risk Targeted | Investigative Action |
|---|---|---|---|
| **1. ### Distinguishing an Alert from Proof of Misconduct
Monitoring indicators generate **probabilistic risk signals requiring corroboration, not verdicts of guilt**:
* **Repeated pairing and shared workstations (`u12`/`u13` in AP-204/AP-209)** may stem from an undocumented shift schedule, a dedicated regional payment desk, or a shared kiosk floor terminal rather than a kickback conspiracy. Even with AP-204's fabricated receipt, forensic evidence must distinguish *joint collusion* from *unilateral deception* (e.g., `u12` fabricating the receipt to trick an overworked `u13`, or `u12` using `u13`'s unattended terminal without `u13`'s knowledge).
* **Timestamp inversions (`13:02` token vs `13:00` prep in AP-206)** can result from asynchronous microservice logging, NTP clock skew between ticketing and ERP servers, or parallel crisis triage during a `12:40` plant outage rather than dishonest backdating.
* **Control outages (AP-208)** prove severe *control-design and compliance failure*, not fraud—`u72` may have acted under intense operational pressure to pay a legitimate EUR 900k vendor while unaware of the 3-day-old bank-change exposure. Disciplinary, legal, and remediation responses must match proven root causes.

## 7. PM4Py and pandas Checking Code

### Cross-Version PM4Py Behavioral Caveats
Before relying on `pm4py.filter_four_eyes_principle(log, "Prepare_Payment", "Release_Payment")`, reviewers must account for three version-dependent behaviors in PM4Py (`2.x` family):
1. **Default `positive` polarity (`positive=False` by default):** In PM4Py's LTL checker (`pm4py.algo.filtering.pandas.ltl.ltl_checker.four_eyes_principle`), the four-eyes rule asserts that `activity1` and `activity2` are performed by *different* resources. With default `positive=False`, many PM4Py 2.x releases return traces where same-resource execution *does not occur* (i.e., nominal *conforming* plus *incomplete* cases like `AP-204, AP-205, AP-209`), whereas passing `positive=True` returns the *violating* same-resource cases (`AP-201, AP-202, AP-203, AP-206, AP-207, AP-208`). Because polarity conventions have shifted across minor releases, production code should explicitly inspect whether the returned cases have matching or distinct resources on completed payments and normalize accordingly.
2. **Incomplete traces lacking the second activity:** Cases like `AP-205` (which has `Prepare_Payment` and `Attempt_Release`, but no `Release_Payment`) have no violating `(Prepare_Payment, Release_Payment)` pair. When `filter_four_eyes_principle` returns non-violating traces, `AP-205` is bundled alongside genuinely two-user completed payments (`AP-204`, `AP-209`) unless completed payments are explicitly filtered first.
3. **Repeated activity occurrences within a trace:** If a payment were reworked (multiple `Prepare_Payment` events by different clerks before one `Release_Payment`), PM4Py joins all `(A, B)` pairs within the case and flags any matching pair, which may differ from checking only the *final* effective preparer against the releaser.

        return (
            acts.loc[act_name, "org:resource"]
            if act_name in acts.index
            else None
        )

    mgr_act = (
        "Manager_Approve"
        if "Manager_Approve" in acts.index
        else ("Manager_Ratify" if "Manager_Ratify" in acts.index else None)
    )
    av_acts = [
        a
        for a in [
            "Automated_Validate",
            "Automated_Validate_Warning",
            "Automated_Validate_Block",
            "Validation_Service_Unavailable",
        ]
        if a in acts.index
    ]

    return pd.Series({
        "prep_user": get_res("Prepare_Payment"),
        "prep_time": get_time("Prepare_Payment"),
        "rel_user": get_res("Release_Payment"),
        "rel_time": get_time("Release_Payment"),
        "av_event": av_acts[0] if av_acts else "NONE",
        "av_overridden": "Override_Warning" in acts.index,
        "mgr_event": mgr_act or "NONE",
        "mgr_user": get_res(mgr_act) if mgr_act else None,
        "mgr_time": get_time(mgr_act) if mgr_act else pd.NaT,
        "log_settlement_time": get_time("Bank_Settlement"),
        "audit_time": get_time("Audit_Review"),
    })


event_summary = (
    log.groupby("case:concept:name", sort=True)
    .apply(summarize_case_events, include_groups=False)
    .reset_index()
)
evidence_df = pd.merge(event_summary, case_facts, on="case:concept:name")

# Resolve effective settlement time (event log first, fallback to case facts)
evidence_df["effective_settlement"] = evidence_df["log_settlement_time"].fillna(
    evidence_df["known_settlement_utc"]
)

# Detect repeated distinct-user pairs within this log + historical facts
pair_keys = evidence_df.apply(
    lambda r: f"{r['prep_user']}->{r['rel_user']}"
    if pd.notna(r["rel_user"]) and r["prep_user"] != r["rel_user"]
    else None,
    axis=1,
)
log_pair_counts = pair_keys.value_counts()

# Flag 1: Nominal status
evidence_df["flag_nominal_status"] = evidence_df["case:concept:name"].apply(
    lambda c: "BLOCKED_PRE_RELEASE"
    if c in attempted_but_blocked
    else (
        "SAME_USER_VIOLATION"
        if c in nominal_violating_completed
        else "DISTINCT_USERS"
    )
)

# Flag 2: AV-2 coverage
evidence_df["flag_av2_coverage"] = evidence_df.apply(
    lambda r: "CLEAN_PASS"
    if r["av_event"] == "Automated_Validate" and not r["av_overridden"]
    else (
        "BLOCKED_DUPLICATE"
        if r["av_event"] == "Automated_Validate_Block"
        else (
            "WARN_OVERRIDDEN"
            if r["av_overridden"]
            else (
                "OUTAGE_UNVALIDATED"
                if r["av_event"] == "Validation_Service_Unavailable"
                else "OTHER"
            )
        )
    ),
    axis=1,
)


# Flag 3: Manager timing & independence
def classify_mgr_timing(r):
    if pd.isna(r["mgr_time"]):
        return "NO_MGR_REVIEW"
    indep_tag = (
        "INDEP"
        if r["manager_independent"] is True
        else (
            "CONFLICTED" if r["manager_independent"] is False else "UNVERIFIED"
        )
    )
    if pd.notna(r["rel_time"]) and r["mgr_time"] < r["rel_time"]:
        return f"PRE_RELEASE_{indep_tag}"
    if (
        pd.notna(r["effective_settlement"])
        and r["mgr_time"] < r["effective_settlement"]
    ):
        return f"POST_REL_PRE_SETTLE_{indep_tag}"
    return f"POST_SETTLE_OR_UNKNOWN_{indep_tag}"


evidence_df["flag_mgr_timing"] = evidence_df.apply(classify_mgr_timing, axis=1)


# Flag 4: Audit timing relative to 24h recall window
def classify_audit_timing(r):
    if pd.isna(r["rel_time"]):
        return "N/A_NO_RELEASE"
    if pd.isna(r["audit_time"]):
        return "MISSING_AUDIT"
    hrs = (r["audit_time"] - r["rel_time"]).total_seconds() / 3600.0
    if hrs <= 24.0:
        return f"WITHIN_24H ({hrs:.1f}h)"
    if hrs <= 30.0:
        return f"BORDERLINE_1BD_PAST_24H ({hrs:.1f}h)"
    return f"LATE_POST_RECALL ({hrs:.1f}h)"


evidence_df["flag_audit_timing"] = evidence_df.apply(
    classify_audit_timing, axis=1
)

# Flag 5: Bank-change proximity
evidence_df["flag_bank_change"] = evidence_df["bank_change_7d"].map(
    {True: "RECENT_BANK_CHANGE_<7D", False: "STATIC_BANK"}
)


# Flag 6: Emergency ED-1 strict eligibility check (for same-user cases)
def check_ed1_eligibility(r):
    if r["flag_nominal_status"] != "SAME_USER_VIOLATION":
        return "N/A_NOT_SAME_USER"
    fails = []
    if not r["has_emergency_token"]:
        fails.append("no_token")
    elif pd.notna(r["token_time_utc"]) and r["token_time_utc"] > r["prep_time"]:
        fails.append("token_after_prep")
    if r["amount_eur"] >= 100000:
        fails.append("amt>=100k")
    if r["vendor_days"] < 180:
        fails.append("vendor<180d")
    if r["bank_change_7d"]:
        fails.append("bank_chg<7d")
    if r["flag_av2_coverage"] != "CLEAN_PASS":
        fails.append("av2_not_clean")
    if not r["flag_mgr_timing"].endswith("_INDEP") or r[
        "flag_mgr_timing"
    ].startswith("POST_SETTLE"):
        fails.append("mgr_not_indep_pre_settle")
    if not r["flag_audit_timing"].startswith("WITHIN_24H"):
        fails.append("audit>24h")
    return "ED1_ALL_7_MET" if not fails else "ED1_FAIL:" + ",".join(fails)


evidence_df["flag_ed1_check"] = evidence_df.apply(check_ed1_eligibility, axis=1)


# Flag 7: Repeated pairs & shared workstation risk
def check_pair_risk(r):
    pk = (
        f"{r['prep_user']}->{r['rel_user']}"
        if pd.notna(r["rel_user"]) and r["prep_user"] != r["rel_user"]
        else None
    )
    in_log_repeats = log_pair_counts.get(pk, 0) if pk else 0
    if in_log_repeats > 1 or r["historical_pair_30d"] > 5 or r["shared_workstation"]:
        return (
            f"REPEATED_PAIR(log={in_log_repeats},30d={r['historical_pair_30d']},"
            f"shared_ws={r['shared_workstation']})"
        )
    return "NONE"


evidence_df["flag_pair_independence"] = evidence_df.apply(
    check_pair_risk, axis=1
)
