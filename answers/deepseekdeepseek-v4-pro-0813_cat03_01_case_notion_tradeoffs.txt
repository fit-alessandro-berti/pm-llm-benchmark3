- Convergence: multiple objects of same type or different converge onto same event or object? We can say:
- Case notion = selected object identity that determines trace boundaries in traditional event log. Flattening projects event log onto selected object type, retaining only events directly or via propagation related to that object.
- Convergence risk = a single case trace pulls in events whose execution is actually driven by multiple objects, artificially merging distinct lifecycles and making it seem like one end-to-end process (e.g. Order O1 trace with D2 shared event merges O2/O3 fulfillment into O1).
- Divergence risk = a single real-world object's lifecycle is fragmented across multiple case IDs, or an object participates only in a slice, producing many short/incomplete traces, over-splitting variants and hiding dependencies that cross objects.

## 1. Analytical assumptions

**Case notion.** I treat a case notion as the object identity used to group events into one trace. For a flattened log on object type O, an event is included in a case for object o only if o is directly present in the event’s `Related objects` set. Events are ordered by timestamp within a trace.

**Convergence.** I define convergence as multiple objects or object types participating in the same event, or being pulled into the same case when flattening. In a flattened log, convergence often appears as a shared event copied into several traces. That is evidence that the case object participated in the event, but it is also duplication if the same physical event is counted once per case.

**Divergence.** I define divergence as one real-world object lifecycle being fragmented across multiple flattened cases, or being truncated because the chosen object participates only in a small slice of the process. For example, `P3` is one package but contains items from `O2` and `O3`; flattening on `Order` splits that one package event across two order traces. Conversely, flattening on `Package` hides order, invoice, and payment events.

**Copied shared events.** I treat copied shared events as both evidence and duplication. They are evidence that the selected object genuinely participated in the shared activity. They become distortion when they are interpreted as a distinct activity occurrence per case, inflating frequencies and creating spurious DFG edges or loops.

**Permitted transformations.** By default, I use the direct E2O relation set exactly as supplied. I do not silently propagate O2O relations. Propagation through O2O links, such as `Package  Item  Order`, is allowed only as an explicit sensitivity analysis, because it changes the semantics and can introduce indirect case participation.

## 3. Concrete distortion analysis

### 3.1 Cross-order package duplication in Order flattening — `P3`

- **Affected flattening:** `Order`
- **Specific events/objects:** `e13 Pack Package` with `O2,O3,I21,I31,P3`
- **Distortion:** One physical packing event is copied into the traces of `O2` and `O3`. If `Pack Package` frequency is read from the flattened order log, it appears twice for what is actually one package. The DFG edge `Add Item  Pack Package` is also duplicated.
- **Effect:** Harmful for operational workload or packaging cost if order-level counts are used. Informative for order status because both orders genuinely needed that packing event. Context-dependent.

### 3.2 Cross-order package duplication in Item flattening — `P3` and `P4`

- **Affected flattening:** `Item`
- **Specific events/objects:** `e13` for `I21,I31,P3`; `e14` for `I32,I41,P4`
- **Distortion:** `I21` and `I31` both show an identical `Pack Package` event. Without attributes, they look like two independent item packing events. The fact that both items are packed in the same physical package `P3`—and that `P3` crosses orders `O2` and `O3`—is hidden. The same problem affects `I32` and `I41` in `P4`.
- **Effect:** Context-dependent. It may be informative for item traceability, but it inflates packing frequency and hides cross-order consolidation.

### 3.3 Consolidated delivery split in Order flattening — `D2`

- **Affected flattening:** `Order`
- **Specific events/objects:** `e16 Dispatch` and `e24 Confirm Delivery` with `O1,O2,O3,I12,I21,I31,P2,P3,D2`
- **Distortion:** One physical dispatch and one physical confirmation are copied into three order traces. The event count for `Dispatch` and `Confirm Delivery` is inflated 3×. In `O2` and `O3`, the trace places `e16` and `e24` around invoice and payment events, so DFG may show `Dispatch  Issue Invoice` or `Record Payment  Confirm Delivery` rather than a clean transport edge.
- **Effect:** Misleading if used for delivery frequency or transport performance. Useful for order status if the analyst accepts duplication. Context-dependent but mainly harmful for delivery-level analysis.

### 3.4 Consolidated invoicing split in Order flattening — `V2`

- **Affected flattening:** `Order`
- **Specific events/objects:** `e19 Issue Invoice` with `O2,O3,V2`; `e22 Record Payment` and `e25 Record Payment` also with `O2,O3,V2`
- **Distortion:** One invoice `V2` for `O2` and `O3` is copied into both order traces. A revenue analyst reading the order-flattened log may infer two invoices. The partial settlement of `V2` by `M2` and `M3` is also split across two order cases.
- **Effect:** Harmful for invoice count and payment settlement analysis. It is informative only if the analyst explicitly knows that `V2` is shared.

### 3.5 Partial payments create an artificial loop in Order flattening

- **Affected flattening:** `Order`
- **Specific events/objects:** `O2`/`O3` traces around `e22`, `e24`, `e25`
- **Distortion:** The `O2` trace contains `e19 Issue Invoice  e22 Record Payment  e24 Confirm Delivery  e25 Record Payment  e29 Close Order`. This creates DFG edges `Record Payment  Confirm Delivery` and `Confirm Delivery  Record Payment`, suggesting a loop. In reality, `V2` is paid in two instalments: `M2` before delivery confirmation and `M3` after it. The invoice-level view `V2` shows the cleaner sequence `Issue Invoice  Record Payment  Record Payment`.
- **Effect:** Context-dependent. It can be informative if modeled as a two-instalment settlement, but it is harmful if discovered as a generic process loop without payment semantics.

### 3.6 Payment flattening near-singleton lifecycle

- **Affected flattening:** `Payment`
- **Specific events/objects:** `M1 e21`, `M2 e22`, `M3 e25`, `M4 e26`
- **Distortion:** Each payment object appears in exactly one event. The flattened log consists entirely of length-1 traces. There are no DFG edges and no lifecycle to analyze. The relation `M2 partially_settles V2` and `M3 completes_settlement V2` is not visible unless attributes are kept.
- **Effect:** Harmful for process discovery. Possibly useful only for auditing when payment events occurred.

### 3.7 Delivery flattening two-event truncation

- **Affected flattening:** `Delivery`
- **Specific events/objects:** `D1 e15,e23`; `D2 e16,e24`; `D3 e17,e27`
- **Distortion:** Delivery traces contain only `Dispatch  Confirm Delivery`. They omit packing, item, order, invoice, and payment events. Case duration equals transport time, not fulfillment time. This is a severe lifecycle truncation relative to `Order`.
- **Effect:** Harmful for end-to-end analysis, but informative for last-mile delivery performance. Context-dependent.

### 3.8 Package flattening hides pre-pack waiting and Add Item events

- **Affected flattening:** `Package`
- **Specific events/objects:** `P1 e11,e15,e23`; `P2 e12,e16,e24`; `P3 e13,e16,e24`; `P4 e14,e17,e27`
- **Distortion:** Package traces start at `Pack Package`. They omit the earlier `Add Item` events `e05–e10` and order creation. For `P3`, the trace does not show that `I21` and `I31` were added at `e07`/`e08` and belong to `O2`/`O3`. If an analyst measures cycle time from `Add Item` to `Pack Package`, package flattening cannot provide it.
- **Effect:** Downward-biased pre-pack waiting time and lost order context. Useful for package handling, but not for order availability.

### 3.9 Multiple items create artificial self-loops in Order flattening

- **Affected flattening:** `Order`
- **Specific events/objects:** `O1` with `e11,e12`; `e15,e16`; `e23,e24`
- **Distortion:** `O1` has two items and two packages, so the same activity appears consecutively. DFG may show `Pack Package  Pack Package`, `Dispatch  Dispatch`, and `Confirm Delivery  Confirm Delivery`. These self-loops are not rework but parallel/multiple-item execution.
- **Effect:** Context-dependent. They may be incorrectly interpreted as loops or repeated work.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs that should still be created, with safe questions:**

- **Order log:** Create for order-status analysis, customer order variants, and end-to-end order cycle time. Safe questions: “How long does an order take from creation to close?” and “What is the activity sequence for `O1` versus `O3`?” Unsafe questions: package count, invoice count, delivery trip count, or payment workload.
- **Item log:** Create for item-level logistics. Safe questions: “How long does each item take from `Add Item` to `Confirm Delivery`?” and “Do items in multi-item packages share the same timestamps?” Unsafe questions: order revenue or invoice settlement.
- **Package log:** Create for package handling and cross-order package diagnosis. Safe questions: “Which packages consolidate items from multiple orders?” For example, `P3` shows `e13,e16,e24` as one package. Unsafe questions: order-level financials or pre-pack waiting.
- **Delivery log:** Create for last-mile transport. Safe questions: “How long does `D2` take from dispatch to delivery confirmation?” and “Which delivery trips consolidate multiple packages?” Unsafe questions: fulfillment end-to-end.
- **Invoice log:** Create for accounts receivable. Safe questions: “How is `V2` settled by `M2` and `M3`?” and “What is the invoice settlement duration?” Unsafe questions: physical delivery or order fulfillment.
- **Payment log:** Probably only as an event audit table, not as a process-discovery log.

**Questions requiring object-centric views:**

- **OC-DFG:** Needed to avoid double counting shared events such as `e16` and `e24`. It shows one `Dispatch` event connected to multiple object types and objects rather than three order-level dispatch events.
- **OTG:** Needed to see structural relations such as `Order contains Item`, `Package packs Item`, `Delivery carries Package`, `Invoice bills Order`, and `Payment settles Invoice`. This clarifies why `D2` involves `P2,P3` and therefore `O1,O2,O3`.
- **ET-OT graph:** Needed to see which activities involve which object types. For example, `Record Payment` involves `Order`, `Invoice`, and `Payment`; `Close Order` involves only `Order`.
- **Object interaction summary:** Needed to identify interactions such as `P3` interacting with `I21,I31,O2,O3`, `D2` with `P2,P3`, and `V2` with `O2,O3,M2,M3`.
- **Equivalent-execution clustering:** Useful as a supplementary check on whether order-based traces form stable clusters or whether cross-order consolidation dominates.

**Reconciling contradictory findings.** If the order-flattened DFG shows `Record Payment  Confirm Delivery`, while the invoice-flattened DFG shows `Issue Invoice  Record Payment  Record Payment`, the contradiction is resolved by recognizing that they are different lifecycles. The order trace interleaves two payments (`M2`, `M3`) with delivery confirmation `e24`. The invoice trace correctly groups both payments under `V2`. Frequency contradictions should be resolved by comparing unique event counts from the OC-DFG against per-case copy counts from flattened logs.

## 5. Lead-object decision

**Position: B. Use a primary lead object plus explicitly secondary lifecycles.**

**Decision criteria.** The lead object should maximize end-to-end lifecycle coverage, preserve the main commercial unit, minimize lifecycle truncation, and not require the fewest duplicated events alone. It must be supplemented because many important events are inherently shared across objects.

**Choice.** `Order` is the primary lead object. `Item`, `Package`, `Delivery`, `Invoice`, and `Payment` are explicit secondary lifecycles.

**Strongest supporting evidence.** `Order` is the only object type that touches every activity in the process, from `Create Order` to `Close Order`. `O1` has a 12-event trace, `O2` has 9 events, `O3` has 13, and `O4` has 8. It directly includes add-item, packing, dispatch, delivery confirmation, invoicing, payment, and closing events. Its event-copy duplication ratio is moderate, around 42/31 = 1.35, much lower than the severe truncation of `Payment`, `Delivery`, `Invoice`, or `Package` logs. The commercial question “How does an order progress?” is the most natural end-to-end frame for an order-fulfilment process.

**Strongest counterargument.** The supplied process deliberately contains cross-order consolidations: `P3` packs `O2`/`O3`, `P4` packs `O3`/`O4`, `D2` consolidates `P2`/`P3` and involves `O1`/`O2`/`O3`, and `V2` consolidates `O2`/`O3`. A single-order case cannot correctly represent those one-to-many and many-to-many relations without copying shared events. Order flattening duplicates `e16`/`e24` three times and `e13,e14,e17,e19,e22,e25,e27` twice. It also creates artificial loops around partial payments and hides the physical unity of `P3`, `P4`, `D2`, and `V2`.

**Residual risk.** Even with the stated secondary lifecycles, users may treat the order-flattened log as dominant and ignore duplication. This risk must be controlled by always reporting shared-event frequency through the OC-DFG or object interaction summary, and by using domain logs for domain questions.

**Conditions for changing the decision.** If cross-order packages, consolidated deliveries, or consolidated invoices become the norm rather than the exception, I would reject a single lead object and move to position **C**. If the process became more order-homogeneous, with few shared objects, I would move to position **A** and rely primarily on `Order`. If the analysis were exclusively about transportation or accounts receivable, `Delivery` or `Invoice` would become the primary lead for that study.
