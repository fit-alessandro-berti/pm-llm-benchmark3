## 1. Duplicate-handling decision tree

The following decision tree classifies candidate relationships based on evidence, object overlap, and source semantics. It prioritizes provenance preservation and semantic fidelity over aggressive reduction.

1.  **Is there an exact technical duplicate?**
    *   *Criteria:* Identical `timestamp`, `activity`, `source`, `source_event_key`, and `payload_hash`.
    *   *Action:* **Drop** the redundant row. Retain the instance with the earliest `ingested_at` as canonical.
    *   *Reasoning:* Pure technical noise; no semantic value added.

2.  **Is this a "Same Physical Event" observed by multiple systems?**
    *   *Criteria:* Different `source` and `source_event_key`, but identical `timestamp` (within tolerance), overlapping `related_objects`, and reconciliations or object constraints indicating a single business occurrence. Payloads differ only in enrichment (e.g., location vs. raw scan).
    *   *Action:* **Merge attributes and relations**.
    *   *Procedure:* Create a canonical event retaining the original timestamp. Union `related_objects`. Merge attributes with a priority schema (e.g., WMS location > Scanner, ERP invoice number > Billing reference). Store all `source_event_key` and `payload_hash` values in a provenance list.
    *   *Confidence:* High if object overlap is complete and timestamps match exactly.

3.  **Is this a "Summary Event" derived from a "Detailed Event"?**
    *   *Criteria:* One event references a subset of objects of another, shares activity/timestamp, and source metadata indicates derivation (e.g., "status update from WMS message", "ERP summary after payment messages").
    *   *Action:* **Retain both**.
    *   *Refinement:* Optionally refine labels to indicate abstraction level (e.g., "Pack Package [Detail]", "Pack Package [Summary]").
    *   *Reasoning:* Merging loses the distinction between granular execution and high-level status. Dropping the summary loses the authoritative business state update.

4.  **Is this a "Harmonization Collision"?**
    *   *Criteria:* Same harmonized `activity` and `timestamp`, but sources have distinct semantic meanings (e.g., Carrier "Acceptance" mapped to "Dispatch" vs. WMS "Release" mapped to "Dispatch"). Object overlap exists but does not prove identity.
    *   *Action:* **Retain both with refined labels**.
    *   *Procedure:* Restore source-specific semantics in the label (e.g., "WMS Release", "Carrier Acceptance"). Keep harmonized label in a metadata column for backward compatibility.
    *   *Reasoning:* Harmonization collapsed distinct lifecycle stages. Restoring labels enables correct process mining.

5.  **Are these "Concurrent Same-Label Events" involving different objects?**
    *   *Criteria:* Same `timestamp` and `activity`, but `related_objects` differ in a way that implies distinct instances (e.g., different Items, different Payment IDs).
    *   *Action:* **Retain both unchanged**.
    *   *Reasoning:* These represent true concurrency. Merging would corrupt the object-centric view.

6.  **Unresolved Candidate?**
    *   *Criteria:* Ambiguous overlap, conflicting timestamps, or insufficient evidence.
    *   *Action:* **Quarantine for review**.
    *   *Reasoning:* Prevents automated semantic damage.

## 3. Timestamp-tie ordering rules

To enable deterministic processing in PM4Py while respecting concurrency, we define a weighted policy. **Semantic rules** determine business order; **deterministic rules** break ties only when semantics are silent, and must never imply false precision.

### Ordering Policy
1.  **Domain Constraints (Semantic):** Hard lifecycle rules (e.g., Auth before Capture, Pick before Pack).
2.  **Lifecycle Constraints on Shared Objects (Semantic):** If objects enforce order (e.g., Payment M1 Auth before Capture M1), enforce that.
3.  **Source-Specific Semantics (Semantic):** If sources have known relative timing (e.g., WMS release before Carrier acceptance), use this.
4.  **Within-Source Sequence (Deterministic):** `source_seq` is valid only within a source. Use to order events from the same source.
5.  **Ingestion Time (Deterministic):** `ingested_at`. Fallback only. **Never primary.**
6.  **Stable Fallback (Deterministic):** Lexicographic `eid`.

### Microseconds Warning
Adding microseconds to break ties creates a **false total order**. If two events are truly concurrent (e.g., e13 Capture M1 and e14 Capture M2), assigning `10:00:00.001` to one and `10:00:00.002` to the other encodes a story that the first caused the second. PM4Py DFGs will interpret this as a sequence, masking true concurrency and potentially creating artificial loops or rework patterns. Microseconds should only be added if a deterministic tie-breaker is absolutely required for a tool that cannot handle ties, and the analyst must be warned that the order is arbitrary.

### Intended Orders

*   **10:00 Block (e03–e07):**
    *   *Semantic:* Pick events (e03, e04, e05) must precede Pack events (e06, e07).
    *   *Order:* `{e03, e04, e05}`  `{e06, e07}`.
    *   *Tie-breaking:* Within Picks, e03/e04 are merged. e05 is distinct. No source-seq cross-comparison. Use stable fallback: `e03` (merged) before `e05`. Within Packs, e06 (WMS detail) before e07 (ERP summary) is plausible, but retain concurrency. Order: `e03_merged`, `e05`, `e06`, `e07`.

*   **10:15 Block (e08–e10):**
    *   *Semantic:* e08 (WMS Release)  e09 (Carrier Accept)  e10 (Handover). Fact 5 confirms e10 after e09. Domain confirms Release before Accept.
    *   *Order:* `e08`  `e09`  `e10`.

*   **12:00 Block (e11–e16 after merge):**
    *   *Merge:* e11/e16  `e11_merged`.
    *   *Semantic:* Invoice (`e11_merged`)  Auth (`e12`)  Capture (`e13`, `e14`). Fact 7: e12 before e13. Fact 8: e15 (Summary) after payments.
    *   *Concurrency:* e13 and e14 are distinct payments; retain concurrency.
    *   *Order:* `e11_merged`  `e12`  `{e13, e14}`  `e15`.

def merge_verified_pair(ocel, eid_a, eid_b, merge_policy='union_objects'):
    """
    Merges two events based on verified reconciliation.
    Retains provenance and preserves original timestamp.
    """
    # Deep copy not needed here as we modify ocel_conservative
    evt_a = ocel.events.loc[eid_a]
    evt_b = ocel.events.loc[eid_b]
    
    # Create canonical event
    canonical_eid = eid_a
    new_row = evt_a.copy()
    
    # Provenance
    provenance = [evt_a['source_event_key'], evt_b['source_event_key']]
    new_row['provenance_sources'] = provenance
    new_row['original_activity'] = evt_b['activity'] # Store merged activity if refined
    new_row['original_timestamp'] = evt_b['timestamp']
    
    # Attribute merge policy
    if merge_policy == 'union_objects':
        objs_a = set(evt_a['related_objects']) if isinstance(evt_a['related_objects'], list) else {evt_a['related_objects']}
        objs_b = set(evt_b['related_objects']) if isinstance(evt_b['related_objects'], list) else {evt_b['related_objects']}
        new_row['related_objects'] = list(objs_a | objs_b)
        
    # Update row
    ocel.events.loc[canonical_eid] = new_row
    
    # Drop merged event
    ocel.events = ocel.events.drop(eid_b)
    # Update E2O relations: remove relations from dropped event, add to canonical
    ocel.e2o = ocel.e2o[ocel.e2o['event_id'] != eid_b]
    # Re-link objects from dropped event to canonical
    ocel.e2o.loc[ocel.e2o['event_id'] == eid_b, 'event_id'] = canonical_eid 
    # Note: In real implementation, need to handle OT2O and ensure no duplicates in E2O
    
    return ocel

## 8. Audit trail and reversibility

### Provenance Schema
Store a metadata table `event_provenance`:

| Field | Description |
| :--- | :--- |
| `canonical_eid` | ID in cleaned log. |
| `source_eids` | List of original EIDs contributing to canonical. |
| `merge_rule` | Rule ID or description (e.g., "verified_scan_merge"). |
| `reviewer` | "Automated" or "Analyst_ID". |
| `original_activity` | List of harmonized activities merged. |
| `refined_activity` | Final activity label. |
| `original_timestamp` | Earliest/Canonical timestamp. |
| `adjusted_timestamp` | Timestamp after tie-breaking (if any). |
| `attrs_retained` | JSON of merged attributes. |
| `discarded_conflicts` | JSON of conflicting attributes dropped. |
| `confidence` | 0.0–1.0 score. |
| `reason` | Text justification. |

### Reversibility
An analyst can reconstruct the raw view by:
1.  Joining `event_provenance` with `ocel.events` on `canonical_eid`.
2.  Expanding `source_eids` to find original rows.
3.  Restoring `original_activity` and `original_timestamp` from provenance.
4.  Reinstating dropped rows if `merge_rule` was "drop".
5.  Splitting merged attributes back to sources using `attrs_retained` metadata.

## 9. Failure modes and safeguards

1.  **Collapsing distinct partial payments:** Merging e13/e14 loses M1/M2 distinction. *Safeguard:* Check `related_objects` for Payment IDs before merging captures.
2.  **Converting abstraction-level updates into false rework:** Merging e06/e07 or ordering e07 before e06 creates loops. *Safeguard:* Detect abstraction levels via source metadata or payload structure; retain both.
3.  **Ordering by ingestion time:** Using `ingested_at` as primary order encodes IT artifacts as business logic. *Safeguard:* Use ingestion only as last-resort tie-breaker.
4.  **Treating shared objects as proof of duplication:** e13/e14 share O1/V1 but are distinct payments. *Safeguard:* Require object overlap to be specific to the entity type (e.g., same Payment ID) or use reconciliation evidence.
5.  **Unioning incompatible E2O relations:** Merging events may create E2O relations that never existed (e.g., linking e03 to I2 if e05 had I2 and e05 was merged). *Safeguard:* Validate E2O consistency; only union objects if semantically compatible.
6.  **Changing durations through synthetic microseconds:** Adding microseconds alters duration metrics. *Safeguard:* Document synthetic timestamps; use them only for sorting, not duration calculation.
7.  **Losing source-authoritative attributes:** Merging may overwrite ERP balance with PSP data or vice versa. *Safeguard:* Define attribute priority schemas per source authority.
8.  **Applying duplicate functions without inspection:** Blindly calling `ocel_merge_duplicates` collapses e08/e09/e10. *Safeguard:* Always inspect candidate groups before applying bulk merge functions.

This pipeline ensures semantic integrity, preserves provenance, and provides a robust foundation for process mining while allowing controlled aggression when justified.
