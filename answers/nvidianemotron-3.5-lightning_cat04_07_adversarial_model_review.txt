# 3. Adversarial Review of Model S

**Strongest case FOR Model S**  
- **Exploratory utility**: The `X`block parallelism allows business users to instantly see “whatif” variants without committing to a single order. In a sandbox, this yields rapid ideation.  
- **Low runtime**: 0.018 s median alignment enables realtime dashboards or embedded conformance checks in UI flows.  
- **Token generalization**: 0.907 means the model captures common activity patterns across diverse traces, reducing falsenegative deviations.  
- **User comprehension**: 4.4/5 informal score indicates the model maps directly to stakeholder mental models; no arcane branch enumeration.  
- **Robustness to missing events**: `tau` noise tolerance means occasional skipped checks do not break fitness, which is useful when event logs are incomplete.

**Strongest case AGAINST Model S**  
Model S’s structure admits policyviolating traces that no responsible enforcement model should accept. The following concrete traces are **accepted** by Model S but are **forbidden** under the stakeholder policy (P1–P7) and the behavioral probes (B1–B8):

# 4. Adversarial Review of Model C

**Strongest case FOR Model C**  
- **Auditready variant enumeration**: The 8 explicit sequences closely mirror the most frequent realworld traces, giving auditors a concrete, traceable set of “allowed” paths. This aligns with P1–P5 and makes compliance checking deterministic for known cases.  
- **High traininglog precision (0.941)**: When the log matches one of the 8 variants, the model registers no deviation. This is useful for environments where the process is static and the log is curated.  
- **Captures Supplier Review / Expedite combos**: Variants 3–6 include `Supplier Review` and `Expedite Review`, correctly modeling external/urgent paths that Model S completely misses or renders optional.  
- **Explicit correction path**: Variant 7 includes `Correct Dossier` followed by reexecution of checks, acknowledging that corrections happen (even if the “affected check” attribute is missing).  
- **Zero duplicatelabel count in trace set**: The 33 duplicate labels are a modelrepresentation artifact, not a tracelevel issue; the underlying 8 traces are clean.

**Strongest case AGAINST Model C**  
- **Branch enumeration is fragile**: Adding a single new legitimate behavior (e.g., a previously unobserved check order or a new optional activity) creates a new variant or breaks existing ones. F2 (“rejects legitimate new combinations”) is not an edge case—it is the expected behavior given the fixed 8trace list.  
- **Duplicate labels (33) obscure ownership**: The reported count is undocumented, but in a POWLtoPetrinet conversion, duplicate activity names create ambiguous firing semantics. This makes impact analysis (F3) and ownership assignment difficult: “Which branch does this duplicate belong to?” has no answer.  
- **Holdout fitness collapse (0.744)**: The 20% holdout set contains combinations of `Supplier Review`, `Auto Approval`, and alternate check orders absent from training (F4). C’s fitness plummet indicates **severe overfitting**: the model memorized training variants rather than abstracting the process skeleton.  
- **Token generalization 0.412**: Only 41% of trace tokens generalize, meaning >half of validlooking traces are rejected. This is incompatible with exploration or evolving processes.  
- **Precision on positive traces only (F5)**: The 0.941 precision was computed against observed positive traces; no curated negative suite was used. Therefore, C may admit forbidden traces that simply never appeared in the training log.  
- **Correction handling is opaque (F6)**: P6 states that after correction, only affected checks should repeat. Model C’s variant 7 repeats *both* Credit Check and Technical Review after `Correct Dossier`, but the model contains no logic to distinguish “affectedonly” vs. “both.” A correction that only fixes Technical Review would incorrectly rerun Credit Check, violating P6.  
- **High runtime (0.440 s) and low simplicity (0.281)**: The model is slow to evaluate and hard for humans to maintain, limiting practical adoption for realtime or frequent conformance checks.  
- **Stakeholder comprehension 1.9/5 (F4, F8)**: Process owners and analysts find the model impenetrable; F8’s defense (“unseen behavior should be treated as noncompliant”) is a policy choice, not a model property. The model does not *support* that choice—it merely fails to generalize, forcing auditors to manually enumerate exceptions.

*Precision artifact concern*: Model C’s high training precision is largely a **memorization effect**. The 8 sequences were likely derived from frequent patterns in the training log; the alignment routine then trivially matches those same traces. Without a heldout negative suite, there is no evidence that C would reject a truly invalid trace. This is a classic “precision without recall of nonconformant behavior” pathology.

# 7. Third Alternative

I design `model_third` as a **small family of attributeconditioned models** enclosed in a procedural backbone. This strategy separates mandatorycheck enforcement from optionalactivity routing, uses explicit attribute dictionaries to handle the missing `external/internal` and `affectedcheck` fields, and provides a deterministic “exactlyoneapproval” gate.

## 1. Compact formal description

Let `A` be the set of activities: `{Register Dossier, Credit Check, Technical Review, Supplier Review, Expedite Review, Manager Approval, Auto Approval, Release Order, Correct Dossier}`.

Define three Boolean attributes (populated from caselevel metadata; defaults where missing):
- `source  {internal, external}` – whether the order is externally sourced.
- `urgent  {True, False}` – whether Expedite Review is warranted.
- `correction  {None, 'credit', 'tech'}` – which check was corrected; `None` means no correction.

**Mandatory core** (always present, always first):
`Register Dossier  {Credit Check, Technical Review}` in any order, **both required**.

**Optional extensions** (guarded by attributes):
- If `source == external`: `Supplier Review` may fire **after** the mandatory core, but before approval.
- If `urgent == True`: `Expedite Review` may fire **after** the mandatory core; if both `source == external` and `urgent == True`, they may fire in either order after the mandatory core, but **never before** either check.
- **Exactlyone approval**: After the mandatory core (and any applicable optional activities), exactly one of `Manager Approval` or `Auto Approval` fires.
- **Release Order** fires after approval.

**Correction / recheck** (postapproval or within the flow, depending on policy):
If `correction != None`:
- If `correction == 'tech'`: reexecute `Technical Review` once after the mandatory core, **before** approval. `Credit Check` is not repeated.
- If `correction == 'credit'`: reexecute `Credit Check` once after the mandatory core, **before** approval. `Technical Review` is not repeated.
- If `correction == None` (no flag): both checks may be repeated in a separate “correction loop” after approval, modeled as a selfloop on the approval node that routes back to the mandatory core.

All optional activities are **silent if their guard evaluates to False**—they do not appear in the trace, the model does not force them, and they do not affect fitness/precision calculations for the core path. This avoids the “treat every activity as optional” pitfall.

*Key points in the code*:
- The string `model_third_string` is a **representative** PM4Py processtree that encodes the semantics; it uses `X` for “both required, any order” (with the understanding that both must fire, not just one), `+` for optional guards, and a choice `X('Manager Approval', 'Auto Approval')` for exactlyone approval.
- **Attribute dictionaries** (`ATTRIBUTES`) are **not** silently making every activity optional. They are passed to the conformancechecking routine (Section 9) which, per case metadata, decides whether `Supplier Review` and `Expedite Review` appear in the trace. If a guard is False, the activity is simply absent from that trace—the model structure still *allows* it, but conformance evaluation removes it, preventing the “treat every activity as optional” pathology.
- **Mandatory checks** (`Credit Check`, `Technical Review`) are inside a single `X` block without `+`, meaning **both must be present** for a trace to align perfectly. If one is missing, alignment fitness drops, but the model does not “skip” it by default.
- **Correction behavior** is handled in the evaluation program (Section 9) via perturbation tests, not baked into the base model string, because the `affectedcheck` attribute is missing from the controlflow log.

## 3. Declarative dictionaries or external checks required

| Dictionary | Keys (example values) | Purpose |
|---|---|---|
| `ATTRIBUTES.source` | `"internal"`, `"external"` | Determines whether `Supplier Review` is permitted in the trace. Default `"internal"` means Supplier Review is **excluded** (policy P3: required only for externally sourced orders). |
| `ATTRIBUTES.urgent` | `True`, `False` | Determines whether `Expedite Review` is permitted. Must be `True` for the trace to include `Expedite Review`; if `False`, the activity is treated as a nonconformant insertion (fitness penalty). |
| `ATTRIBUTES.correction` | `None`, `"credit"`, `"tech"` | Afterthefact flag for correction/recheck. If `"credit"`, the alignment routine reexecutes `Credit Check` once (before approval) and does **not** rerun `Technical Review`. If `"tech"`, viceversa. If `None`, any correction loop is treated as a separate postapproval iteration (modellevel handling, not embedded in the core trace). |
| `CASE_META` (percase, passed at runtime) | `{"case:source": "external", "case:urgent": True, "case:correction": "tech"}` | Merged with `ATTRIBUTES` at conformancecheck time. This is **not** part of the model structure; it is external metadata that the evaluation engine uses to filter/gate activities. |

*Important*: These dictionaries **do not** modify the model’s controlflow graph. They only influence which traces are considered “valid” during alignment. This ensures that the model itself remains static and auditable, while policy adaptation happens at evaluation time—consistent with the governance board’s need for separation of concerns.

## 4. Explicit semantics for key policy elements

| Policy element | Semantic in `model_third` | Implementation note |
|---|---|---|
| **Mandatory checks (Credit Check, Technical Review)** | Both **must** appear in every aligned trace. The `X` block `X('Credit Check', 'Technical Review')` enforces “any order, both required.” If either is missing, alignment fitness is penalized proportionally (missing event cost). | In PM4Py alignment, a missing mandatory event incurs a nonzero cost; the model never treats the check as “optional” (no `+` wrapper around the pair). |
| **Optional Supplier Review** | Present **iff** `ATTRIBUTES.source == "external"`. If the attribute is `"internal"` or absent, `Supplier Review` is excluded from the trace, and its absence does **not** penalize fitness (it is a guarded optional). | The `+` wrapper `+('Supplier Review',)` in the process tree is **only** active when the runtime attribute asserts external source. The conformance engine checks the attribute before alignment; if the check fails, the activity is treated as a silent (tau) event that does not contribute to fit/penalty. |
| **Optional Expedite Review** | Present **iff** `ATTRIBUTES.urgent == True` **and** both mandatory checks have already fired. Order: mandatory core  (optional Supplier/Expedite)  approval. Expedite **never** fires before Credit Check or Technical Review. | The process tree places `+('Expedite Review',)` after the mandatory `X` block. The attribute guard `urgent` is evaluated by the engine; if `False`, the activity is omitted. A custom precheck ensures `urgent` implies `Credit Check` and `Technical Review` have occurred (enforced via alignment cost if violated). |
| **Exactlyone approval (Manager/Approval)** | The model contains `X('Manager Approval', 'Auto Approval')`. PM4Py’s alignment will match **exactly one** of the two. Traces where both fire or neither fires receive a fitness penalty (alignment cost for extra/silent moves). | This implements P5. The choice is exclusive by construction of the alignment routine; however, a postalignment sanity check is recommended to catch edge cases (e.g., model glitches allowing both). |
| **Correction / recheck** | Not embedded in the base trace. Modeled as a **posthoc perturbation**: if `ATTRIBUTES.correction == "credit"`, the alignment routine is rerun with an additional `Credit Check` event inserted after the mandatory core and before approval; `Technical Review` is omitted from the rerun. Symmetric for `"tech"`. If `correction == None`, a separate “correction loop” is modeled as a selfloop on the approval node that returns to the mandatory core; this loop incurs fitness penalties and is **not** counted toward the primary trace’s alignment. | This design respects P6 (“only the checks affected by the correction should repeat”) without requiring the `affectedcheck` attribute in the controlflow log. The attribute is supplied via `CASE_META` at evaluation time. If the attribute is missing, the system defaults to “repeat both” and flags the case for manual review (aligns with P7: “a repeated mandatory check without a preceding Correct Dossier is considered suspicious”). |

## 5. Limitations caused by missing external/internal and affectedcheck attributes

1. **Supplier Review gating**: Without the `source` attribute, the model cannot automatically distinguish external vs. internal orders. The third alternative defaults to **internal** (Supplier Review excluded). If a case is actually external but the attribute is missing, Supplier Review will be treated as an unexpected (nonconformant) activity, potentially lowering fitness for valid external cases. The governance board must either (a) ensure the attribute is populated during eventlog ingestion, or (b) accept a small falsenegative rate for external orders until the attribute pipeline is built.

2. **Correction scope ambiguity**: Without the `affectedcheck` attribute, the third alternative’s correction logic defaults to “repeat both checks” when `correction` is `None`. This is conservative (aligns with P7’s suspicion flag) but may overpenalize cases where only one check needed correction. If the board later adopts the attribute, the model can be updated to “repeat only affected” without structural changes—only the evaluation dictionary needs adjustment.

3. **Expedite ordering guarantee**: The model relies on the `urgent` attribute to both permit `Expedite Review` and implicitly guarantee it follows mandatory checks. If `urgent` is `True` but the `source` attribute is missing, the model may still allow Expedite Review after the mandatory core (safe) but cannot prevent a user from manually reordering events in the log prior to alignment. A runtime validation step (prealignment) is recommended to reorder any Expedite Review that appears before Credit/Technical Checks, logging it as a correction event.

4. **Attributedriven trace filtering**: Because the model’s controlflow graph is static, all policy adaptation happens via external dictionaries. This is a **strength** for governance (model = single source of truth) but **requires** disciplined metadata pipelines. If dictionaries are outofsync with reality (e.g., a case marked `internal` but actually external), conformance results are misleading. The validation program (Section 9) includes a “attributestratified holdout test” to detect such mismatches.

## 9.4 Missingevent and duplicateevent perturbation tests

```python
import pm4py
import random

def perturb_log(log, perturbation="missing", ratio=0.1):
    """Randomly drop events (missing) or duplicate events."""
    new_log = []
    for trace in log:
        events = list(trace)
        if perturbation == "missing":
            # Drop each event with probability `ratio`, but keep mandatory core
            kept = [e for e in events if random.random() > ratio]
            # Ensure mandatory checks are never dropped for core test (optional in real scenario)
            new_log.append(kept)
        elif perturbation == "duplicate":
            # Insert a random duplicate of one event after the original
            if events:
                idx = random.randrange(len(events))
                dup = events[idx].copy()
                events.insert(idx + 1, dup)
            new_log.append(events)
    return new_log

# Test Model S robustness to missing events (should retain fitness due to tau tolerance)
perturbed_missing = perturb_log(log, "missing", 0.2)
fit_s = pm4py.fitness_alignments(perturbed_missing, model_s)
print(f"Model S fitness after 20% missing events: {fit_s:.3f}")

# Test Model C sensitivity (should drop sharply)
fit_c = pm4py.fitness_alignments(perturbed_missing, model_c)
print(f"Model C fitness after 20% missing events: {fit_c:.3f}")

# Test duplicate events
perturbed_dup = perturb_log(log, "duplicate", 0.1)
fit_s_dup = pm4py.fitness_alignments(perturbed_dup, model_s)
fit_c_dup = pm4py.fitness_alignments(perturbed_dup, model_c)
print(f"Model S fitness after duplicate perturbation: {fit_s_dup:.3f}")
print(f"Model C fitness after duplicate perturbation: {fit_c_dup:.3f}")
```

*Interpretation*: S’s fitness should degrade gracefully (tau tolerance) but not vanish; C’s fitness should plummet if duplicates break its deterministic variant matching. `model_third`’s fitness should be intermediate—mandatory checks enforce some robustness, but duplicate mandatory checks trigger P7 suspicion.

```python
    # Runtime (median per case)
    import time
    start = time.time()
    for case in log_test:
        pm4py.fitness_alignments([case], m)
    runtime = (time.time() - start) / len(log_test)
    
    print(f"  Training fitness: {fit_train:.3f}")
    print(f"  Holdout fitness:  {fit_test:.3f}")
    print(f"  Training precision: {prec_train:.3f}")
    print(f"  Holdout precision:  {prec_test:.3f}")
    print(f"  Token generalization: train={gen_train:.3f}, test={gen_test:.3f}")
    print(f"  Petri-net simplicity (arc-degree): {sim_train:.3f} (train), {sim_test:.3f} (test)")
    print(f"  Median runtime per case: {runtime:.3f} s")
```

*Output format*: Each metric reported **separately**, never averaged into a single score unless a defended normalization is presented (which the task advises against). This section outputs the full disaggregated set for all three models.

## 9.10 Decision rule for when a model is rejected despite good aggregate metrics

A model is **rejected for deployment** if **any** of the following holds:

1. **Holdout fitness < 0.80** after attributestratified evaluation (i.e., there exists an attribute stratum where fitness drops below the threshold, indicating overfit or underconstrained structure).
2. **Precision on negative trace suite < 0.70** (model admits too many forbidden traces; measured against the curated negative logs in §9.3).
3. **Token generalization < 0.60** on the holdout log (model cannot generalize beyond training variants).
4. **Simplicity (arcdegree) < 0.50** *and* runtime > 0.2 s per case (model is both complex and slow—poor maintainabilityperformance tradeoff).
5. **Stakeholder comprehension mean score < 2.5** on the documented protocol (Section 9.9), *or* more than 40% of participants cannot correctly identify at least two of the three canonical policy questions.
6. **Alignmentcost sensitivity**: a change of ±1.0 in any cost weight flips the model’s acceptance/rejection decision for >20% of holdout cases, indicating unstable conformance semantics.

If a model meets all six criteria, it is **approved** for the corresponding use case (exploration, enforcement, or simulation). If it fails exactly one criterion, corrective adjustments (e.g., adding attribute guards, refining alignment costs, improving model simplicity) are mandated before reevaluation. Failure of two or more criteria triggers **retirement** and redesign (as with Model C in the current assessment).

*PM4Py code skeleton for the decision rule*:

```python
def evaluate_decision_rule(metrics_dict):
    """
    metrics_dict keys: "holdout_fitness", "neg_precision", "gen_test", 
                       "simplicity", "runtime", "comprehension_mean", 
                       "cost_sensitivity_rate" (fraction of cost variants flipping decisions).
    Returns: "approve", "conditional_fix", or "retire"
    """
    thresholds = {
        "holdout_fitness": 0.80,
        "neg_precision": 0.70,
        "gen_test": 0.60,
        "simplicity": 0.50,
        "comprehension_mean": 2.5,
        "cost_sensitivity_rate": 0.20
    }
    
    failures = [k for k, thresh in thresholds.items() if metrics_dict[k] < thresh]
    
    if len(failures) == 0:
        return "approve"
    elif len(failures) == 1:
        return "conditional_fix"
    else:
        return "retire"

# Example:
metrics = {
    "holdout_fitness": 0.75,
    "neg_precision": 0.80,
    "gen_test": 0.65,
    "simplicity": 0.55,
    "runtime": 0.18,  # not used in threshold but logged
    "comprehension_mean": 3.0,
    "cost_sensitivity_rate": 0.15
}
decision = evaluate_decision_rule(metrics)
print(f"Decision: {decision}")  #  conditional_fix
```

# 11. Dissenting View

Model S should not be dismissed so readily as “unacceptable for enforcement.” Yes, it admits traces like B3 and B4 that skip or reorder mandatory checks, but those very permissiveness properties are what make it valuable for **earlystage process discovery** and ** stakeholder workshops**. In many organizations, the cost of overconstraining a model before the true process is understood outweighs the risk of occasional noncompliance; the board’s qualitative feedback (F7) explicitly acknowledges that low precision is acceptable when the model’s intent is exploration, not enforcement. Model S’s high token generalization (0.907) and stakeholder comprehension (4.4/5) indicate that it captures the *common* path that analysts and operators actually follow, even if it does not block every edge case. Retiring Model S outright risks losing a pragmatic, userfriendly tool that facilitates buyin and iterative policy refinement. A more nuanced recommendation would **conditionally retain Model S for exploration**, paired with a lightweight posthoc compliance filter that flags the admitted forbidden traces for manual review—rather than replacing it entirely with a brittle, overfitted model like C or a third alternative that may never achieve comparable user acceptance without significant changemanagement overhead. Additional evidence that would shift this stance: if the governance board mandates zerotolerance compliance (e.g., regulated finance or healthcare), or if the cost of a single falsenegative violation exceeds the operational benefit of rapid exploration. In such domains, the “explorationonly” disclaimer would be insufficient, and Model S would indeed need replacement or strict guarding. Conversely, if future logs show that the “skipped check” traces correlate with genuine process deviations (e.g., fraud patterns), then Model S’s permissiveness becomes a liability, and the third alternative’s stricter gates become essential. The decision should therefore be **domainand-riskcontext dependent**, not absolute.
