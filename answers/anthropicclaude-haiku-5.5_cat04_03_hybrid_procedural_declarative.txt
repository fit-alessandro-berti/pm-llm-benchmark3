# 1. Policy Interpretation and Conflict Resolution

### Material assumptions

| ID | Assumption | Consequence if wrong |
|---|---|---|
| A1 | Traces are complete cases that end with `Close Onboarding`. Prefix monitoring is out of scope. | Open cases are reported as incomplete, not as violations. |
| A2 | An accepted case is `Activate Vendor` then `Release First Payment` then `Close Onboarding`. A rejected case is `Reject Vendor` then `Close Onboarding`. | Accepted cases without payment would fail the procedural layer. |
| A3 | `Receive Onboarding Request`, `Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account`, and `Classify Risk` occur once per case. Rework is not modelled. | Rework would need loop or count-based extensions. |
| A4 | The low-risk or high-risk route is a classifier output, not visible in activity labels. The procedural model accepts either approval route. Route consistency is a data-layer check that requires a `risk_level` attribute. | Route violations are invisible to activity-only layers. |
| A5 | "Final outcome" in R3 means `Reject Vendor` or `Activate Vendor`. Clarification may run during classification but must be closed before the outcome. | A stricter reading would also forbid overlap with `Classify Risk`. |
| A6 | `Sanctions Escalation` (SE) is allowed only after `Run Sanctions Screening` (R7). In the procedural model it is allowed only on the accepted path and must complete before `Activate Vendor`. Escalation on a rejected path is a deliberate approximation (see §3). | Rejected cases with escalation are flagged procedurally. This is conservative, and policy must decide. |
| A7 | `Obtain Legal Opinion` (LO) is required when SE occurs (R4). It is at most once per escalation. | Repeated opinions would need count-based extensions. |
| A8 | Post-activation maintenance (`Change Bank Details`, `Suspend Vendor`, re-verification) is outside the procedural backbone. It is covered by DECLARE, the log skeleton, and the data layer. Pre-activation Change Bank Details is a deviation. | Procedural traces containing these labels are reported as `not evaluated`. |
| A9 | Authorization for an R6 emergency exists only outside the log, in an external register keyed by case ID. The log contains no emergency attribute. | Without the register, R6 cannot be verified. |
| A10 | Timestamps are hours from case start, converted to seconds. Clocks are consistent across resources. | Ties and clock skew affect order-based checks. |
| A11 | Temporal profile values come only from R12. PM4Py temporal conformance measures all occurrences of a pair, not only directly adjacent ones. | Repeated clarification cycles inflate measured intervals. |
| A12 | Declared rules have `support = 1.0` and `confidence = 1.0`. These values mean normative, not mined. | Mined metadata would not be normative truth (see §9). |
| A13 | "Applicable approval" means whichever of Manager or Compliance Approval occurs in the case. If both occur, both are checked. | Restricts the four-eyes check to a single approver role. |
| A14 | Clarification responses have no segregation-of-duties requirement. | None. |

### Policy conflict: R5 versus R6

- **R5 (Legal):** after SE, LO must precede `Activate Vendor` "under all circumstances".
- **R6 (Operations):** emergency activation may precede LO if jointly authorized outside the log. The opinion must then arrive within 24 hours.

These cannot both be true for an emergency activation that occurs before LO. R5 forbids the case outright, while R6 permits it under an external condition.

**Resolution A: Legal precedence is hard (fail-closed).** R5 is authoritative. An activation before LO after SE is a control-flow violation. R6 is recorded as an off-log exception workflow. A waiver may open a review ticket, but it does not change the conformance verdict.
- *Compliance risk:* false positives for genuine emergencies. Process owners may be pressured to relabel activations or to ask for exceptions outside the system. The 24-hour R6 obligation is not verified in the authoritative verdict.

**Resolution B: Emergency exception overrides.** R6 is authoritative for cases with an external authorization. Activation may precede LO if the register holds a matching authorization and LO arrives within 24 hours of activation. Otherwise R5 applies.
- *Compliance risk:* the log cannot verify the authorization. If the register is stale, missing, or spoofed, unauthorized activations pass. The verdict depends on an external system that is not audited by the event log. Legal's "under all circumstances" wording is violated by design.

**Resolution C: Shadow reporting.** Evaluate under A and B in parallel and report both.
- *Compliance risk:* two verdicts create ambiguity about which one gates release. Users may pick the favourable verdict. This option is acceptable only if one verdict is declared authoritative.

**Chosen for the implemented model: Resolution A.** R5 uses the stronger normative wording. The conflicting permission in R6 depends on evidence that the event log cannot contain. A fail-closed verdict is safer than a pass based on an unverifiable claim. Policy B is still implemented as a separate, switchable function in §7 and is used only for the T6 sensitivity analysis in §8. The two policies are never merged in one verdict.

# 2. Requirement-to-Formalism Mapping

Authority is marked with **[A]** for the authoritative layer. Other layers are redundant or diagnostic.

| Requirement | Primary formalism | Exact encoding | Why this formalism | Redundancy or limitation |
|---|---|---|---|---|
| R1 Reject and Activate never co-occur | **[A] POWL** (terminal XOR) | `outcome = XOR(reject, accepted)`; `activate` exists only inside `accepted` | Hard exclusivity is native control flow | DECLARE `noncoexistence(Reject, Activate)`; log skeleton `never_together`. Intentional redundancy. |
| R2 Exactly one of Manager or Compliance approval in accepted cases; neither in rejected | **[A] POWL** for the accepted route; DECLARE and log skeleton for pairwise exclusion | `approval = XOR(manager, SPO[EDDCompliance])` inside `accepted`; `noncoexistence(MA,CA)`, `noncoexistence(RJ,MA)`, `noncoexistence(RJ,CA)`; `never_together` | The "at least one" part is a disjunctive existence that POWL can express through XOR | DECLARE cannot express "at least one of A or B" with binary templates. Route correctness depends on risk level, which is data. |
| R3 Clarification requests get answers before the next request and before the outcome | **[A] POWL** loop node for pending state; DECLARE for per-cycle pairing | `clarification = LOOP(tau, RequestReceive)`; `clarificationoutcome`; DECLARE `succession(Req,Recv)`, `altresponse(Req,Recv)`; log skeleton `always_after(Req,Recv)` | The loop must finish before the outcome, which requires a pending state. DECLARE expresses "before the next request" through `altresponse`. | "Before final outcome" is not a pairwise DECLARE template. POWL carries it. |
| R4 SE implies eventual LO | **[A] DECLARE** `response(SE,LO)`; POWL also orders them on the accepted path | `response(SE, LO)`; `escalation` block `SELO` | Eventual obligation is a response constraint | POWL orders SE before LO only on the accepted path. Rejected cases with SE are a deliberate gap (see §3). |
| R5 After SE, LO precedes Activate (Resolution A) | **[A] POWL** edge `escalation  activate` | `accepted.order.add_edge(escalation, activate)` with `escalation = XOR(tau, SELO)` | Conditional precedence ("if SE then LO before AV") is a POWL pattern through an optional block that gates activation. DECLARE cannot do this. | DECLARE `precedence(LO,AV)` would fail every low-risk case, so it is not used. Log skeleton `always_before(LO,AV)` has the same flaw. The data layer `check_emergency_policy` cross-checks. |
| R6 Emergency activation before LO under joint authorization, opinion within 24h | **Data layer** with external authorization register. Not encoded in control flow under Resolution A. | `check_emergency_policy(df, waivers, policy="B")` (sensitivity only) | Authorization is off-log. Only the data layer can join an external register. | No emergency attribute exists. The 24-hour bound is an AVLO interval, not the R12 SELO profile. |
| R7 SE only after screening | **[A] DECLARE** `precedence(Screen, SE)`; POWL implicit (escalation is inside the post-classify branch) | `precedence(("Run Sanctions Screening","Sanctions Escalation"))` | Pairwise precedence | Redundant with POWL ordering. |
| R8 EDD and Manager not together; Compliance and Manager not together | **[A] POWL** XOR for MA vs EDDCA; DECLARE and log skeleton for pairwise rules | `approval = XOR(manager, EDDCA)`; `noncoexistence(MA,EDD)`, `noncoexistence(MA,CA)`; `never_together` | R8 uses "should", but POWL enforces it hard. This is a disclosed strengthening. | EDD and Compliance together is allowed, as required by the high-risk route. |
| R9 Four-eyes: Verify  applicable approver; Capture  Activate | **Data/resource layer** | `check_sod_verify_vs_approval`, `check_sod_capture_vs_activate` on `org:resource` | Resources are not activities. Activity-only models cannot see them. | `pm4py.filter_four_eyes_principle` is symmetric and cannot implement the "applicable approval" disjunction. Missing resources yield `unverifiable`. |
| R10 Activate and Reject at most once; Release at most once | **[A] POWL** (each label occurs once, no loop covers these labels); log skeleton `activ_freq` | `activ_freq` = `{0,1}` for Activate, Reject, Release | DECLARE has no `absence2` template in the given list, so `activ_freq` is the right fit | Log skeleton counts are only meaningful for complete traces. Conflicts with R11 when post-activation release is re-tried (see §9). |
| R11 Post-activation bank change requires Suspend and re-verification before later release | **DECLARE** `response(CBD,SUS)`, `precedence(AV,CBD)`; **data layer** for "verify between CBD and next release" | DECLARE above; `check_post_activation_bank_change` | DECLARE can express Suspend follows CBD. "Verify lies between CBD and a later release" is a windowed ordering that DECLARE cannot express conditionally. | Post-activation is excluded from POWL. `response(CBD,VER)` is rejected because it would over-constrain cases that end without release. |
| R12 Temporal expectations (warnings) | **Temporal profile** | `temporal_profile` with `zeta = 2.0` | Real-valued durations are not an activity-level property | Warnings only. PM4Py measures all occurrences, not only adjacent ones. |

# 3. Procedural Backbone

### 3.1 Compact formal description

Let the top-level partial order be `P = (N, )` with nodes `N = {Recv, Cap, Scr, Ver, Clar, Cls, Out, Close}`.

- `Clar = LOOP(, Req  Rcv)`: zero or more request/response cycles, each ending with a receive.
- `Out = XOR(Rej, Acc)`.
- `Acc = SPO({Appr, Esc, Act, Rel}, {ApprAct, EscAct, ActRel})`, where:
  - `Appr = XOR(Mgr, EDD  Comp)`;
  - `Esc = XOR(, SE  LO)`.
- Top-level edges:
  - `Recv  Cap`, `Recv  Scr`, `Recv  Ver`, `Recv  Clar`;
  - `Cap  Cls`, `Scr  Cls`, `Ver  Cls`;
  - `Cls  Out`, `Clar  Out`, `Out  Close`.

**Excluded:** `Change Bank Details`, `Suspend Vendor`, and any second `Verify Bank Account`.

**Approximation:** the escalation block is only on the accepted path. A rejected case with `Sanctions Escalation` is a procedural deviation. This is conservative. The rejected-with-escalation policy requires a decision, and an entry should be added to the DECLARE layer for R4.

### 3.2 PM4Py code

```python
from pm4py.objects.powl.obj import (
    Transition, SilentTransition, StrictPartialOrder, OperatorPOWL, Operator
)

# ---- Leaf transitions (labels exactly as in the scenario) ----------------
receive    = Transition("Receive Onboarding Request")
capture    = Transition("Capture Master Data")
screen     = Transition("Run Sanctions Screening")
verify     = Transition("Verify Bank Account")
req_clar   = Transition("Request Clarification")
recv_clar  = Transition("Receive Clarification")
classify   = Transition("Classify Risk")
esc        = Transition("Sanctions Escalation")
legal      = Transition("Obtain Legal Opinion")
edd        = Transition("Enhanced Due Diligence")
manager    = Transition("Manager Approval")
compliance = Transition("Compliance Approval")
reject     = Transition("Reject Vendor")
activate   = Transition("Activate Vendor")
release    = Transition("Release First Payment")
close      = Transition("Close Onboarding")

# ---- Clarification cycle: tau (Request -> Receive)*  ---------------------
clar_cycle = StrictPartialOrder(nodes=[req_clar, recv_clar])
clar_cycle.order.add_edge(req_clar, recv_clar)
clarification = OperatorPOWL(
    operator=Operator.LOOP,
    children=[SilentTransition(), clar_cycle],
)

# ---- Approval route (exactly one): Manager OR (EDD -> Compliance) --------
high_risk_chain = StrictPartialOrder(nodes=[edd, compliance])
high_risk_chain.order.add_edge(edd, compliance)
approval = OperatorPOWL(
    operator=Operator.XOR,
    children=[manager, high_risk_chain],
)

# ---- Optional escalation block: tau XOR (SE -> LO) -----------------------
esc_chain = StrictPartialOrder(nodes=[esc, legal])
esc_chain.order.add_edge(esc, legal)
escalation = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), esc_chain],
)

# ---- Accepted branch ------------------------------------------------------
accepted = StrictPartialOrder(nodes=[approval, escalation, activate, release])
accepted.order.add_edge(approval, activate)     # approval before activation
accepted.order.add_edge(escalation, activate)   # R5 (Resolution A): LO before activation
accepted.order.add_edge(activate, release)      # payment after activation

# ---- Terminal choice: reject XOR accepted --------------------------------
outcome = OperatorPOWL(operator=Operator.XOR, children=[reject, accepted])

# ---- Top-level partial order with every precedence edge explicit ---------
procedural_model = StrictPartialOrder(
    nodes=[receive, capture, screen, verify, clarification, classify, outcome, close]
)
for src, dst in [
    (receive, capture),
    (receive, screen),
    (receive, verify),
    (receive, clarification),
    (capture, classify),
    (screen, classify),
    (verify, classify),
    (classify, outcome),
    (clarification, outcome),
    (outcome, close),
]:
    procedural_model.order.add_edge(src, dst)

# Optional: convert to an accepting Petri net for alignments.
# The conversion API differs across PM4Py versions; check your installed release.
# net, im, fm = pm4py.convert_to_petri_net(procedural_model)
```

### 3.3 Explanation

- **Concurrency:** `Capture`, `Screen`, `Verify`, and `Clar` are unordered after `Recv`. `Classify` waits for the three checks. The clarification loop is not gated by `Classify`, so a request may be open while classification runs (R3 literal reading).
- **Choices:** `Outcome` is an XOR between reject and accept (R1). Approval is an XOR between the low-risk and high-risk routes (R2 and R8). Escalation is an optional block (`` or SELO).
- **Clarification loop:** `LOOP(, ReqRcv)` permits zero or more complete cycles. Each cycle ends in a receive, and the loop must complete before the outcome. An unanswered request blocks the outcome.
- **Terminal outcomes:** reject and accept are exclusive. Accept ends with release, and both paths feed `Close`.
- **R5 encoding:** the edge `escalation  activate` makes `Activate` wait for the whole escalation block. If SE occurred, LO must have occurred. If SE did not occur, `` completes immediately.
- **Post-activation:** `Change Bank Details`, `Suspend Vendor`, and re-verification are excluded. Traces with these labels are `not evaluated` procedurally.
- **R10:** each leaf appears once, and no loop covers activation or release, so both are at most once.
