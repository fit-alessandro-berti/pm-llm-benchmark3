## 1. Equivalence design space

### 1.1 Activity-sequence equivalence

For execution \(X\), let

\[
A(X)=\langle a(e_1),\ldots,a(e_n)\rangle
\]

be its timestamp-ordered activity-label sequence. Define \(X\equiv_A Y\) iff \(A(X)=A(Y)\).

This preserves event count, activity labels, repetition, and total order. It discards object identifiers and types, event-to-object (E2O) incidence, object-to-object (O2O) relations, multiplicities, externality, and qualifiers.

As defined, it is reflexive, symmetric, and transitive.

For equal timestamps, I use a partial-order variant: each timestamp is an unordered multiset of labels, and timestamp blocks remain ordered. Thus arbitrary storage order does not split clusters. If reliable lifecycle precedence is available, it may refine this partial order.

Result:

- \(A1=\{X1,X2,X5,X6,X7\}\)
- \(A2=\{X3\}\)
- \(A3=\{X4\}\)
- \(A4=\{X8\}\)

This is useful as a control partition, but it is not object-centric.

### 1.2 Typed structural equivalence under identifier renaming

Represent an execution as a typed, attributed incidence structure:

- event vertices, labeled by activity and ordered by time;
- object vertices, labeled by object type and local/external flag;
- E2O edges between events and objects;
- O2O edges labeled by relation/qualifier;
- optional lead-object marker.

Define \(X\equiv_T Y\) iff there are bijections between their event and object vertices such that:

1. event activities and temporal order are preserved;
2. object types, lead status, and external flags are preserved;
3. E2O incidence is preserved;
4. O2O edge labels and qualifiers are preserved.

Raw identifiers are not preserved. Event bijection is needed only among same-label, same-time events; otherwise order fixes the event mapping.

This relation preserves exact typed multiplicities, shared-object incidence, repeated events, external participation, and qualified topology. It discards local identifier spelling and non-modeled attributes such as amounts.

It is reflexive, symmetric, and transitive because it is labeled-graph isomorphism.

For concurrency, temporal structure is a precedence relation rather than an arbitrary total order: the isomorphism must preserve \(e_i<e_j\), while concurrent events may be permuted.

Under this strict definition, X1 and X2 are equivalent; all other examples are structurally distinct. In particular, X7 differs from X1 because Dispatch explicitly references I72 and because qualified replacement/removal relations are present.

### 1.3 Business-semantic equivalence

Exact isomorphism is often too fine. I define a preferred semantic signature

\[
S(X)=(L,F,R)
\]

with three components:

- **Logistics motif \(L\):** number of active items, packages, and deliveries; item-to-package and package-to-delivery cardinality patterns; return/repack motif; replacement/removal motif; and whether logistics objects are shared externally.
- **Finance motif \(F\):** invoice count, payment-event multiplicity, partial/completed settlement motif, and whether an invoice/payment scope spans an external order.
- **Resolution flags \(R\):** isolated/shared, normal/replacement/return, and settled once/settled in parts.

Two executions are equivalent iff these normalized components are equal. Local identifiers, the order of interchangeable Add Item events, and non-essential exact item-to-package assignments are discarded. Repeated events are retained when they carry business meaning, such as two payments or two dispatches.

This preserves business-relevant multiplicities, external sharing, qualifiers such as `removed_before_dispatch`, and lifecycle motifs such as return–inspect–repack. It discards identifier spelling and harmless permutations. It is reflexive, symmetric, and transitive because equality of deterministic signatures is an equivalence relation.

Concurrent events are interpreted through causal constraints inferred from object lifecycles: Add precedes Pack for the same item, Pack precedes Dispatch for the same package, and Return precedes repack. Independent branches may be permuted.

### 1.4 Optional projection equivalence

For a selected concern \(C\), such as logistics or finance, project the preferred signature to \(S_C\). This is useful because X1 and X6 are logistics-equivalent but not finance-equivalent, while X1 and X5 have similar finance but different logistics isolation.

Projection equality is also reflexive, symmetric, and transitive. It deliberately discards all information outside the selected concern.

## 2. Canonical signatures

The preferred signature can be generated reproducibly after identifier-invariant graph canonicalization. The following outline assumes each event has `activity`, `time`, and typed object references; each O2O edge has `source`, `target`, `relation`, and qualifiers.

```python
from collections import Counter, defaultdict

def preferred_signature(execution):
    events = execution.events
    objects = execution.objects
    o2o = execution.o2o

    def objs(type_, external=None):
        out = [o for o in objects if o.type == type_]
        if external is not None:
            out = [o for o in out if o.is_external == external]
        return out

    def count_events(label):
        return sum(e.activity == label for e in events)

    # Identifier-free E2O cardinality profiles.
    event_profiles = []
    for e in events:
        counts = Counter((o.type, bool(o.is_external))
                         for o in e.objects)
        event_profiles.append((
            e.activity,
            tuple(sorted((typ, ext, n)
                         for (typ, ext), n in counts.items()))
        ))

    # Preserve order only modulo concurrent blocks.
    time_blocks = defaultdict(list)
    for e, profile in zip(events, event_profiles):
        time_blocks[e.time].append(profile)
    ordered_event_blocks = tuple(
        tuple(sorted(time_blocks[t]))
        for t in sorted(time_blocks)
    )

    # Canonical qualified O2O edge profile.
    o2o_profile = Counter()
    for r in o2o:
        q = tuple(sorted(r.qualifiers))  # empty tuple if none
        o2o_profile[(r.source.type, bool(r.source.is_external),
                     r.relation, q,
                     r.target.type, bool(r.target.is_external))] += 1

    # Degree/cardinality profiles preserve split/consolidation patterns.
    typed_degrees = []
    for o in objects:
        incident = Counter()
        for r in o2o:
            if r.source == o:
                incident[("out", r.relation, r.target.type)] += 1
            if r.target == o:
                incident[("in", r.relation, r.source.type)] += 1
        typed_degrees.append((
            o.type, bool(o.is_external),
            tuple(sorted(incident.items()))
        ))

    external_logistics = any(
        o.is_external and o.type in {"Order", "Item", "Package", "Delivery"}
        for o in objects
    )
    external_finance = any(
        o.is_external and o.type == "Order" and
        any(e.activity in {"Issue Invoice", "Record Payment"} and o in e.objects
            for e in events)
        for o in objects
    )

    qualifiers = {
        q for r in o2o for q in r.qualifiers
    }
    replacement = (
        "removed_before_dispatch" in qualifiers or
        any(r.relation == "replaces" for r in o2o)
    )
    return_repack = (
        count_events("Return Item") > 0 and
        count_events("Inspect Return") > 0 and
        count_events("Pack Package") > 1
    )

    logistics = (
        len(objs("Item", False)),
        len(objs("Package", False)),
        len(objs("Delivery", False)),
        count_events("Pack Package"),
        count_events("Dispatch"),
        external_logistics,
        replacement,
        return_repack,
        tuple(sorted(typed_degrees)),
    )

    finance = (
        len(objs("Invoice", False)),
        len(objs("Payment", False)),
        count_events("Record Payment"),
        external_finance,
        any("partially_settles" in r.qualifiers for r in o2o),
        any("completes_settlement" in r.qualifiers for r in o2o),
    )

    # Full canonical evidence can be retained for audit.
    return (
        logistics,
        finance,
        tuple(sorted(o2o_profile.items())),
        ordered_event_blocks,
    )
```

For the semantic clustering below, the final two evidence components are normalized into motifs rather than requiring literal equality. For example, item identities within two interchangeable single-item packages are ignored, but package and delivery cardinalities are retained. A production implementation could use Weisfeiler–Lehman refinement followed by a graph-isomorphism check to avoid relying solely on degree profiles.

## 4. Cluster interpretations

### S1 — Isolated consolidated straight-through fulfillment

**Signature:** `2 items  1 package  1 delivery; one invoice; one payment; no external sharing or exception motif`.

This is normal straight-through processing. Opportunities include automation and use as a baseline for service-level benchmarking; risks are mainly hidden data omissions if an apparently simple trace lacks recorded relations.

Order-only case flattening represents it reasonably, although it loses package/item topology. The cluster is stable under identifier repair, Add-event reordering, and completion of redundant unqualified relations. It is unstable if repair introduces genuine sharing or replacement qualifiers.

### S2 — Split packing with consolidated delivery

**Signature:** `2 items  2 packages  1 delivery; single settlement`.

Items are packed separately but shipped together. This can reflect handling constraints or warehouse zones. Risks include consolidation delays and package omission; opportunities include optimizing the consolidation point.

Order-level flattening poorly represents the two parallel package branches. Package-level flattening also duplicates the shared delivery. The cluster is stable if missing item–package links can be unambiguously repaired, but package deduplication would incorrectly merge it with S1.

### S3 — Split fulfillment with staged settlement

**Signature:** `2 items  2 packages  2 deliveries; one invoice  two qualified payments`.

The order is fulfilled in separate shipments and financially settled in installments. Risks include shipment coordination, higher handling costs, confusing partial-balance status, and premature closure after the first payment. It offers flexibility for backorders or customer cash flow.

Order-case flattening obscures branch correspondence; invoice-case flattening captures payment staging but not logistics. Stability is moderate: if payment amounts show that one event is a technical duplicate, the finance motif may change. Without such evidence, multiplicity and qualifiers should be retained.

### S4 — Cross-order shared logistics

**Signature:** `local items plus external item share package/delivery; invoice remains local`.

This is logistics consolidation across orders. Opportunities are lower shipping cost and better capacity use. Risks include ownership ambiguity, privacy leakage, package-level cancellation complexity, and cascading delay across orders.

Flattening by Order duplicates the shared package and delivery and may falsely treat each as isolated. Flattening by Package loses the distinction between lead and external orders. The cluster is stable only if external references are reliable; resolving `EXT-OA` as an accidental linkage would move X5 to S1.

### S5 — Cross-order shared finance

**Signature:** `baseline logistics; invoice and payment span lead and external order; no allocation`.

The physical flow is isolated, but billing is consolidated across orders. Risks include inability to attribute payment, incorrect receivables closure, refund ambiguity, and audit problems. The opportunity is efficient consolidated billing.

Order flattening duplicates one invoice/payment into multiple cases or arbitrarily assigns it. Invoice flattening preserves the financial object but loses order-level allocations. The cluster is stable if shared billing is intentional; adding an allocation does not necessarily remove sharing, but it creates a more precise semantic subtype.

### S6 — Replacement/removal before dispatch

**Signature:** `one package and delivery; one item marked removed/replaced before dispatch; single settlement`.

The apparent straight-through flow includes item substitution or removal. Risks include billing an unshipped item, inventory inconsistency, and customer dissatisfaction. Opportunities include measuring substitution effectiveness.

Activity-only and ordinary order flattening represent it poorly because the exception lives in E2O/O2O qualifiers, not a distinct activity. Stability is comparatively low: if `removed_before_dispatch` is missing or inferred unreliably, X7 collapses toward S1. Dispatch’s direct I72 incidence provides supporting evidence, however.

### S7 — Return, inspection, repack, and redispatch

**Signature:** `initial shipment  item return  inspection  repack  second shipment`.

This is a reverse-logistics recovery loop, potentially replacement, repair, or redelivery. Risks include repeated shipping cost, long resolution time, fraud, and inventory-state errors. Opportunities include improving first-time-right fulfillment and recovery speed.

Order flattening shows the labels but poorly represents that only I82 traverses the loop. Delivery flattening separates the original and replacement legs; item flattening duplicates shared initial packaging. The cluster is stable because several explicit events support it, though ambiguous meanings of `replaces` may alter its subtype.

## 5. Borderline cases

### X1 versus X2

They are equivalent under activity-sequence, typed-isomorphism, and preferred semantic definitions. Local identifier names and the order in which interchangeable Add events mention I11/I12 versus I22/I21 are ignored.

A strict serialized-log equivalence that includes complete event payload strings would separate them. That is defensible for replay integrity or forensic comparison, but not for behavioral clustering.

### X1 versus X5

Activity-sequence equivalence groups them because their labels and repetition coincide. A lead-order projection that deletes all external objects may also group them.

Typed structural and preferred semantic equivalence separate them: X5’s package and delivery participate in a cross-order connected component. This changes cancellation, ownership, and delay propagation semantics.

### X1 versus X6

They are activity-sequence equivalent and logistics-projection equivalent. Both have two local items, one package, and one delivery.

Full semantic equivalence separates them because V61 and M61 span O6 and `EXT-OB` without allocation. A reporting scheme concerned only with warehouse execution can defensibly group them; finance or compliance cannot.

### X1 versus X7

They are activity-sequence equivalent. A weak unqualified topology abstraction might also group them after ignoring direct Dispatch–Item incidence and all qualifiers.

Qualified structural and semantic definitions separate them. X7 states replacement/removal and identifies I72 at Dispatch. Thus equal package count does not imply equal fulfillment meaning.

### X3 versus X4

A packing-strategy equivalence groups both as “two items packed into two separate packages.” That is useful for warehouse analysis.

Full lifecycle semantics separates them: X3 consolidates both packages into one delivery and has one payment; X4 has two delivery legs and partial/completing payments. Even logistics-only equivalence separates them if delivery multiplicity is preserved.

### X4 versus X8

A coarse “multiple packs or deliveries / exception-heavy fulfillment” segmentation may group them as non-straight-through executions with two deliveries and increased handling.

Lifecycle-motif equivalence separates them sharply. X4 has two forward branches for distinct items; X8 has an initial shared shipment followed by return, inspection, and repeat handling of I82. X4 also has staged payment, while X8 does not.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` groups lead-object-centered executions using an exact key derived from each execution’s event/object structure. In practical use, the key preserves the selected lead-object scope, event activities/order as represented, object types and object participation, and object identifiers appearing in the extracted execution. Depending on OCEL version and conversion path, relation-level attributes or O2O qualifiers may require explicit verification rather than being assumed to participate in the key.

Raw identifiers make exact clusters too fine: X1 and X2 can receive different keys even though a type-preserving renaming maps one to the other. Shared identifiers can also be operationally important, so canonicalization must rename local objects while retaining type, externality, and cross-execution identity where required.

A practical pattern is: obtain exact PM4Py clusters, compute an identifier-invariant semantic signature for every member, and aggregate exact clusters sharing that signature.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# API return shape can vary by PM4Py version; consult that version's docs.
exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD_TYPE,
    max_objs=10000
)

def canonicalize_execution(exec_ocel, lead_order_id):
    # Build a lead-centered representation from exec_ocel.
    # Rename local objects by typed structural role, not raw ID:
    # Order:L0, Item:L0/L1, Package:L0..., while retaining external=True.
    execution = to_internal_execution(
        exec_ocel,
        lead_type=LEAD_TYPE,
        lead_id=lead_order_id,
        preserve_o2o=True,
        preserve_qualifiers=True,
        mark_external=True
    )
    return preferred_signature(execution)

semantic_clusters = defaultdict(list)

for exact_key, members in exact_clusters.items():
    # "members" may be IDs or sub-OCELs depending on version/wrapper.
    for member in members:
        lead_id, exec_ocel = materialize_member(ocel, member, LEAD_TYPE)
        sig = canonicalize_execution(exec_ocel, lead_id)
        semantic_clusters[sig].append(lead_id)

# Optional reporting aggregation.
summary = {
    sig: {
        "count": len(order_ids),
        "orders": order_ids
    }
    for sig, order_ids in semantic_clusters.items()
}
```

Exact equivalence is preferable for regression tests, duplicate detection, audit replay, and validating an extraction algorithm. Coarser clustering is preferable for operational segmentation and interpretable reporting.

`max_objs` protects against very large connected executions. Shared packages, invoices, or hub objects can connect many orders, causing memory growth and making “one execution” semantically unhelpful. A low threshold can truncate or exclude precisely the shared cases of interest; a high threshold can cause combinatorial and performance problems. Threshold hits should therefore be reported as their own category, not silently treated as ordinary executions.

## 7. Robustness analysis

### Ignore all O2O qualifiers

X7 becomes much closer to X1. It still differs under the strict typed structure because Dispatch directly references I72, but a semantic scheme using only package–delivery topology may merge S6 into S1. X4 loses explicit partial/completing meaning, yet two payment objects/events remain. X8 retains its return and inspection events, so it remains distinct.

### Ignore external objects

X5 may collapse into S1 if external E2O references and external item/package relations are removed. X6 likewise collapses into S1 after removal of `EXT-OB`. This demonstrates that externality is not incidental metadata: it distinguishes isolation from shared execution.

### Collapse repeated same-label events

X4’s two Pack, Dispatch, and Payment events may collapse, potentially making it resemble X1 or X3 despite different objects. X8’s repeated Pack and Dispatch events may also collapse, but Return and Inspect still distinguish it. Such collapsing is unsafe unless repetition is known to be logging duplication rather than lifecycle multiplicity.

### Treat Pack and Dispatch order as a partial order

X1 and X2 remain equivalent. X4’s independent item/package branches can be permuted without changing its cluster: `Pack P41, Dispatch P41, Pack P42, Dispatch P42` is equivalent to packing both before either dispatch, provided each package’s Pack precedes its Dispatch. This improves robustness to timestamp interleavings. It does not merge X3 and X4 because their delivery topology differs.

### Treat payment multiplicity as an amount attribute

If two payment events are normalized to one aggregate settlement object with attributes such as `installment_count=2`, X4 remains distinct only if that attribute is preserved in the semantic signature. If only total paid amount is retained, its finance motif may collapse to “fully settled once,” weakening separation from split-logistics cases with a single payment.

## 8. Limitations and recommendation

The preferred signatures depend on relation quality. Missing qualifiers can hide replacement; incomplete external references can make shared execution appear isolated; duplicate events can inflate multiplicities. The examples also omit amounts, quantities, cancellation states, actors, and durations. Consequently, signatures should retain provenance and confidence indicators rather than presenting inferred motifs as certain facts.

For **compliance monitoring**, use typed structural equivalence or a rule-refined semantic relation that preserves external sharing, qualified relations, payment multiplicity, and exact lifecycle order. False merging can conceal unauthorized consolidated billing or shipment substitution.

For **operational segmentation**, use the preferred business-semantic equivalence. It ignores harmless renaming and branch permutation while retaining package/delivery multiplicities, sharing, installments, replacement, and return motifs.

For **root-cause analysis**, begin with semantic clusters and drill down to exact typed structures, attributes, resources, and timing. Pure exact equivalence fragments the population; pure semantic equivalence may hide the decisive low-level difference.

For **descriptive reporting**, use concern-specific projections—logistics, finance, and returns—with explicit counts for shared executions. This produces understandable categories without pretending that one partition serves every audience.

No single notion is best because the objectives conflict: compliance values sensitivity, operations values stable actionable categories, root-cause analysis needs both aggregation and detail, and reporting values interpretability. A layered hierarchy from activity sequence, through typed isomorphism, to semantic motifs is therefore preferable to one universal clustering.
