## 1. Modeling assumptions

- The six case-sensitive types are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. One event ID denotes one business occurrence, including when several objects participate.
- E2O qualifiers describe the object's role in that occurrence. Creation and closure use `created_order` and `closed_order`. Addition uses `owning_order` and `added_item`. Reservation uses `affected_order` and `reserved_item`. Packing uses `packed_package`, `packed_item`, and, for explicitly involved Orders, `affected_order`. Dispatch uses `dispatched_package` and `carrier_delivery`. Confirmation uses `confirmed_delivery`. Invoice issue uses `issued_invoice` and `billed_order`. Payment recording uses `recorded_payment` and `credited_invoice`.
- Each O2O row reads as a sentence from `ocel:oid` through its qualifier to `ocel:oid_2`. An Order contains an Item, a Package packs an Item, a Delivery carries a Package, an Invoice bills an Order, and a Payment partially settles or completes settlement of an Invoice. M2 is the final installment. Its amount of 150 and M1's amount of 100 are event attributes.
- Direct E2O links follow the participants named in each event description. Both Orders participate in the joint reservation and in packing P1. Packing P2 names P2 and I2, so O100's connection to that event is available through I2. Dispatch links Package and Delivery, and confirmation links Delivery alone. Invoice issue includes both Orders. Each payment includes its Payment and V1. No financial event identifies an Item or allocates money to an Order.
- This preserves the distinction between “participated in the recorded event” and “can be reached through business relationships.” For example, O100's packing history in a direct flattening omits P2. For an enriched analysis I would keep a separate relation table with a derivation rule and supporting O2O path for each added link. The pipeline below uses the direct table throughout.
- The code uses the standard OCEL column names and the high-level PM4Py APIs in 2.7.23.4. The constructor is isolated on one line. On a release with different parameter names, adapt that call to pass the same four frames through its OCEL 2.0 interface, preserving both O2O endpoints and the qualifiers.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

EID, ACT, TS = "ocel:eid", "ocel:activity", "ocel:timestamp"
OID, OT, OID2, Q = "ocel:oid", "ocel:type", "ocel:oid_2", "ocel:qualifier"

ids_by_type = {
    "Order": ["O100", "O200"],
    "Item": ["I1", "I2", "I3"],
    "Package": ["P1", "P2"],
    "Delivery": ["D1", "D2"],
    "Invoice": ["V1"],
    "Payment": ["M1", "M2"],
}
objects = pd.DataFrame(
    [(oid, ot) for ot, ids in ids_by_type.items() for oid in ids],
    columns=[OID, OT],
)

event_rows = []
participant_rows = []

def add_event(eid, when, activity, *participants, amount=None):
    event_rows.append((eid, activity, when, amount))
    participant_rows.extend((eid, oid, role) for oid, role in participants)

add_event("E01", "2026-04-06T08:00Z", "Create Order", ("O100", "created_order"))
add_event("E02", "2026-04-06T08:05Z", "Add Item",
          ("O100", "owning_order"), ("I1", "added_item"))
add_event("E03", "2026-04-06T08:06Z", "Add Item",
          ("O100", "owning_order"), ("I2", "added_item"))
add_event("E04", "2026-04-06T08:10Z", "Create Order", ("O200", "created_order"))
add_event("E05", "2026-04-06T08:12Z", "Add Item",
          ("O200", "owning_order"), ("I3", "added_item"))
add_event("E06", "2026-04-06T08:30Z", "Reserve Stock",
          ("I1", "reserved_item"), ("I3", "reserved_item"),
          ("O100", "affected_order"), ("O200", "affected_order"))
add_event("E07", "2026-04-06T09:00Z", "Pack Package",
          ("P1", "packed_package"), ("I1", "packed_item"), ("I3", "packed_item"),
          ("O100", "affected_order"), ("O200", "affected_order"))
add_event("E08", "2026-04-06T09:05Z", "Pack Package",
          ("P2", "packed_package"), ("I2", "packed_item"))
add_event("E09", "2026-04-06T10:00Z", "Dispatch Package",
          ("P1", "dispatched_package"), ("D1", "carrier_delivery"))
add_event("E10", "2026-04-06T10:15Z", "Dispatch Package",
          ("P2", "dispatched_package"), ("D2", "carrier_delivery"))
add_event("E11", "2026-04-06T11:00Z", "Issue Invoice",
          ("V1", "issued_invoice"), ("O100", "billed_order"), ("O200", "billed_order"))
add_event("E12", "2026-04-06T11:30Z", "Record Payment",
          ("M1", "recorded_payment"), ("V1", "credited_invoice"), amount=100)
add_event("E13", "2026-04-06T13:00Z", "Confirm Delivery", ("D1", "confirmed_delivery"))
add_event("E14", "2026-04-07T09:00Z", "Confirm Delivery", ("D2", "confirmed_delivery"))
add_event("E15", "2026-04-07T10:00Z", "Record Payment",
          ("M2", "recorded_payment"), ("V1", "credited_invoice"), amount=150)
add_event("E16", "2026-04-07T10:30Z", "Close Order", ("O200", "closed_order"))
add_event("E17", "2026-04-07T10:35Z", "Close Order", ("O100", "closed_order"))

events = pd.DataFrame(event_rows, columns=[EID, ACT, TS, "amount"])
events[TS] = pd.to_datetime(events[TS], utc=True)
events["amount"] = events["amount"].astype("Int64")
events = events.sort_values([TS, EID]).reset_index(drop=True)

o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"), ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"), ("P1", "I3", "packs"), ("P2", "I2", "packs"),
        ("D1", "P1", "carries"), ("D2", "P2", "carries"),
        ("V1", "O100", "bills"), ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"), ("M2", "V1", "completes_settlement"),
    ],
    columns=[OID, OID2, Q],
)

assert len(events) == 17 and events[EID].is_unique
assert len(objects) == 12 and objects[OID].is_unique
assert events[[EID, ACT, TS]].notna().all().all()
assert objects[[OID, OT]].notna().all().all()
assert str(events[TS].dt.tz) == "UTC"

participants = pd.DataFrame(participant_rows, columns=[EID, OID, Q])
# Start with the submitted links so that a bad reference cannot vanish in a join.
relations = (
    participants.merge(events[[EID, ACT, TS]], on=EID, how="left", validate="many_to_one")
    .merge(objects, on=OID, how="left", validate="many_to_one")
    .loc[:, [EID, ACT, TS, OID, OT, Q]]
)
assert len(relations) == 34 and relations.notna().all().all()
assert set(relations[EID]) == set(events[EID])
assert set(relations[OID]) == set(objects[OID])
assert (set(o2o[OID]) | set(o2o[OID2])) <= set(objects[OID])
assert not relations.duplicated([EID, OID, Q]).any()
assert not relations.duplicated([EID, OID]).any()  # one role per participant here
assert len(o2o) == 12 and o2o.notna().all().all() and not o2o.duplicated().any()

event_by_id = events.set_index(EID)
type_by_id = objects.set_index(OID)[OT]
for col in (ACT, TS):
    assert relations[col].eq(relations[EID].map(event_by_id[col])).all()
assert relations[OT].eq(relations[OID].map(type_by_id)).all()
end_types = {
    "contains": ("Order", "Item"), "packs": ("Package", "Item"),
    "carries": ("Delivery", "Package"), "bills": ("Invoice", "Order"),
    "partially_settles": ("Payment", "Invoice"),
    "completes_settlement": ("Payment", "Invoice"),
}
for src, dst, role in o2o[[OID, OID2, Q]].itertuples(index=False, name=None):
    assert (type_by_id[src], type_by_id[dst]) == end_types[role]

# Constructor adapter point for the installed PM4Py release.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)
print(ocel)
print("Activity frequencies (events):", events[ACT].value_counts().to_dict())
print("Object-type frequencies (objects):", objects[OT].value_counts().to_dict())
print("Object types:", pm4py.ocel_get_object_types(ocel))
print("Activities per object type:", pm4py.ocel_object_type_activities(ocel))

flat_logs, dfgs, skeletons = {}, {}, {}
for ot in ("Order", "Package", "Delivery", "Invoice"):
    flat = pm4py.ocel_flattening(ocel, ot)
    flat_logs[ot] = flat
    dfgs[ot] = pm4py.discover_dfg(flat)  # (edge frequencies, starts, ends)
    skeletons[ot] = pm4py.discover_log_skeleton(flat, noise_threshold=0.0)

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# pm4py.view_ocdfg(ocdfg)
# pm4py.view_ocpn(ocpn)
```

## 3. Data-model audit

| Object type | Object IDs | Count |
|---|---|---:|

| Item | I1, I2, I3 | 3 |
| Package | P1, P2 | 2 |
| Delivery | D1, D2 | 2 |
| Invoice | V1 | 1 |
| Payment | M1, M2 | 2 |

| O2O qualifier | Directed endpoints | Edges | Observed cardinality |
|---|---|---:|---|
| contains | Order → Item | 3 | O100 has two Items and O200 has one. Each Item has one owner. |

| carries | Delivery → Package | 2 | One Package per Delivery and one Delivery per Package. |

|---|---:|---|
| Create Order | 2 | Order (2) |
| Add Item | 3 | Order (3), Item (3) |

E07 is the clearest **convergence** example. Packing P1 is one event with five participants. Flattening on Order copies it into two cases, and flattening on Item copies it into two item cases. E06 and E11 likewise converge on both Orders. **Divergence** appears in the other direction. O100 gathers additions for two different Items into one trace, and V1 gathers recordings for two different Payments. Both produce a repeated activity label along a single case.

## 4. Expected flattened behavior

A case contains the events directly linked to its object ID, in timestamp order. The edge counts below count adjacent occurrences within those cases.

| Flattening | Cases in event order | Activity DFG with frequencies |
|---|---|---|
| Order | O100: E01 → E02 → E03 → E06 → E07 → E11 → E17<br>O200: E04 → E05 → E06 → E07 → E11 → E16 | Create Order → Add Item (2), Add Item → Add Item (1), Add Item → Reserve Stock (2), Reserve Stock → Pack Package (2), Pack Package → Issue Invoice (2), Issue Invoice → Close Order (2) |
| Package | P1: E07 → E09<br>P2: E08 → E10 | Pack Package → Dispatch Package (2) |
| Delivery | D1: E09 → E13<br>D2: E10 → E14 | Dispatch Package → Confirm Delivery (2) |
| Invoice | V1: E11 → E12 → E15 | Issue Invoice → Record Payment (1), Record Payment → Record Payment (1) |

- **Order.** The 13 case rows represent ten distinct event IDs. E06, E07, and E11 each appear in both cases. In particular, the two Reserve Stock → Pack Package edges refer to the same pair of events. E02 → E03 records two separate item additions. The trace omits P2's packing, both dispatches, both confirmations, and both payments. The Issue Invoice → Close Order edge therefore gives no evidence of immediate closure or of payment being optional.
- **Package.** Each pack or dispatch belongs to one Package, so there are no copies across Package cases. E07 also figures in the Order and Item views, and E09/E10 also figure in the Delivery view. The two Package activity sequences look identical despite P1 combining two Orders. The case ends at dispatch. A package transit time or delivery outcome requires following its Delivery.
- **Delivery.** Each dispatch and confirmation belongs to one Delivery. The dispatch events are shared with their Packages and occur once each within this flattening. Packing, order composition, and billing are absent. Identical activity sequences conceal the difference between D1's 3 hours in transit and D2's 22 hours 45 minutes.
- **Invoice.** There is one case, so E11 occurs once even though it bills two Orders. E12 and E15 each occur once and are shared with different Payment objects. Their self-loop at the activity level represents two installments, 100 and 150. Treating it as a retry of M1 or as two payments per Order would misread the data. The view omits order creation and closure, logistics, and any split of the 250 between Orders.
- **Payment.** M1 has only E12 and M2 has only E15. Each case starts and ends with Record Payment, yielding an empty within-case DFG. The Invoice ID is what connects the two installments into a settlement history.

At zero noise, the Order log skeleton can reflect one creation and one closure per case and observed Add Item counts of one or two. The Package and Delivery skeletons each see a fixed two-step pattern. Two payment recordings per Invoice describe the single V1 trace. These sample sizes provide little support for universal cardinality or precedence rules.

## 5. Expected object-centric structures

- **OC-DFG.** Edges follow individual objects and retain the object type. Pack Package → Dispatch Package is a Package edge, and Dispatch Package → Confirm Delivery is a Delivery edge. Items I1 and I3 follow Add Item → Reserve Stock → Pack Package, while I2 goes directly from Add Item to Pack Package. The E06 → E07 pair supports two Order traversals and two Item traversals, all from one distinct pair of event IDs. V1 supplies the Invoice self-loop at Record Payment. M1 and M2 each supply a singleton Payment lifecycle. Edge frequencies depend on whether one counts distinct event pairs or traversals by objects.
- **OTG (object-type graph).** In the interaction part, Order–Package is supported by O100–P1 and O200–P1, Order–Invoice by the two billed Orders and V1, and Invoice–Payment by V1 with M1 and M2. O100–O200 contributes one distinct interacting pair of type Order–Order across three shared events. PM4Py also reports lifecycle-derived type relationships. For example, Dispatch Package is the last observed event of P1 and the first of D1, supporting Package → Delivery inheritance in the discovered graph. These labels describe observed lifecycles. The business statement “D1 carries P1” has its own directed O2O row.
- **ET–OT (event-type/object-type graph).** The activity table in section 3 gives its 16 distinct activity–type edges and their E2O weights. The Issue Invoice–Order edge has weight two from one invoice issue. The Pack Package–Order edge also has weight two, entirely from packing P1. A type-level edge means at least one occurrence involved the type. Record Payment connects to Invoice and Payment only.
- **Object-centric Petri net.** A discovered net can express shared activity transitions with type-specific places or arcs. Packing P1 brings Item, Package, and Order histories together, dispatch links the Package and Delivery histories, and recording M1 and M2 links successive steps for V1 with separate Payment objects. Variable multiplicity matters at packing, where E07 has two Items and E08 has one. The exact places, arcs, and optional behavior depend on discovery settings and the sample. A shared Issue Invoice transition alone cannot establish a rule that every invoice requires exactly two Orders, or determine how either Order is paid.
- **Object-interactions summary.** At event level, O100 and O200 co-occur in E06, E07, and E11. P1 co-occurs with both Orders and both packed Items in E07, then with D1 in E09. V1 co-occurs with O100 and O200 in E11, with M1 in E12, and with M2 in E15. M1 and M2 share an Invoice across events but never share an event with each other. PM4Py 2.7.23.4 emits both orientations of each pair, giving 54 rows here. Counting once per event and unordered pair gives 27. In particular, O100 co-occurring with I3 at E07 implies joint handling, while the `contains` rows assign I3 to O200.

## 6. Modeling alternatives

| E2O policy | Effect on this dataset and its discovery results |
|---|---|
| Explicit participants, as in the pipeline | Preserve every named participant, including the two Orders at E06 and E07. An Order case can identify a shared pack and invoice. Dispatch and confirmation require the Package or Delivery view. |
| Manifest-level confirmation | If proof of delivery records the manifest, attach P1 to E13 and P2 to E14. Package traces gain Dispatch Package → Confirm Delivery and ET–OT gains Confirm Delivery–Package. Order and Item traces keep their current shape. |
| Full operational logistics involvement | With an event record that identifies the full handling scope, include the owner at each pack and the Package, contained Items, and owning Orders at dispatch and confirmation. O100 then sees two dispatches and two confirmations, while O200 sees one of each. The Order DFG interleaves shipments, and the Item DFG extends through delivery. Such links require operational evidence to count as direct facts. |
| Path-limited analytical propagation | For an Order reporting view, derive beneficiary Orders using Package → Item ← Order, optionally prefixed by Delivery → Package. For payments use Payment → Invoice → billed Order. Keep inferred links and their paths separately. In the enriched Order view, both M1 and M2 appear under both Orders. Record Payment gains an Order edge in ET–OT, and the Order DFG gains payment steps. The invoice total stays 250 and order-level allocations remain unknown. |

## 7. Failure modes

1. **Relation inflation.** Taking the whole O2O connected component as each event's participants would spread D2's confirmation to O200 through unrelated paths. This creates spurious interactions and edges in the Order DFG.
2. **Missing direct E2O links.** Dropping O200 from E06 loses its explicitly stated participation. The `contains` edge to I3 does not make PM4Py include E06 in O200's case.
3. **Treating propagation as observation.** An inferred association from M1 through V1 to O100 shows billing context. Storing it as a source posting to O100 changes the financial meaning and makes the two interpretations hard to audit.
4. **Counting flattened copies as new events.** Counting Order rows reports two invoice issues for E11. Count distinct EIDs for global workload and keep the EID on every projected occurrence.
5. **Ambiguous payment allocation.** Assigning 250 to each billed Order would report 500. Even a 125/125 split needs evidence. Both amounts are recorded once against V1.
6. **Overly short Payment traces.** Mining only Payment cannot recover the ordering of installments or distinguish first from final settlement by activity sequence. V1 and the qualified O2O edges supply that context.
7. **Constructor or API mismatch.** A constructor that drops O2O or changes qualifier columns can leave enough E2O data for plausible flattenings. Check the constructed OCEL's O2O endpoints and roles when adapting the API.
8. **False total order at tied timestamps.** This log has no ties. In another log, a stable sort by EID can make output reproducible, yet an edge induced by that tie-break has no observed temporal precedence. Retain the tie and seek sequence or causal evidence before interpreting the edge.
9. **Counting join artifacts.** Duplicate E2O rows can multiply flattened occurrences. Inconsistent copies of an event's activity or timestamp can place a shared occurrence at different steps in different views. The validated joins and identity checks guard against both.
10. **Confusing co-occurrence with ownership.** The E07 interaction pairs include O100–I3 and O200–I1. Using these pairs to infer line ownership would contradict both Orders' `contains` rows.

## 8. Final semantic checks

- There are 17 distinct EIDs, 12 distinct OIDs, 34 direct E2O rows, and 12 qualified O2O rows. Every relation endpoint resolves to exactly one entity.
- Following `contains` gives O100 → {I1, I2} and O200 → {I3}. Following `packs` gives P1 → {I1, I3} and P2 → {I2}. P1 is therefore the cross-order Package.
- E06 is a single Reserve Stock occurrence at 08:30 UTC with exactly {O100, O200, I1, I3}. E07 has exactly that set plus P1. E08 has exactly {P2, I2}.
- E09 pairs P1 with D1 and E10 pairs P2 with D2, agreeing with both `carries` edges. E13 confirms D1 on April 6 and E14 confirms D2 on April 7.
- E11 has exactly {V1, O100, O200}, and V1 has exactly two outgoing `bills` edges. Both Order traces reference the same E11.
- E12 records 100 for {M1, V1} and E15 records 150 for {M2, V1}. Only those two event rows have an amount. M1 partially settles V1 and M2 completes its settlement.
- E16 closes only O200 at 10:30 UTC on April 7 and E17 closes only O100 five minutes later. Both closures follow the second payment in wall-clock time.
- Looking up any relation by EID gives the same activity and UTC timestamp as its event row. Looking up its OID gives the same type. Shared events differ across their relation rows by participant and role while keeping their event identity.
