# 1. Assumptions and Interpretation

1. **Abbreviations used in traces and discussion.**  
   I use the following abbreviations in the witness table and compact model descriptions:
   - `R` = Register Deviation
   - `C` = Contain Material
   - `A` = Analyze Root Cause
   - `PV` = Plan Verification
   - `DCA` = Design Corrective Action
   - `SR` = Supervisor Review
   - `QR` = Quality Review
   - `RR` = Regulatory Review
   - `CS` = Consult Supplier
   - `ET` = Execute Trial
   - `IT` = Inspect Trial
   - `AP` = Adjust Parameters
   - `RM` = Release Material
   - `AC` = Archive Case

2. **Activities are recorded at completion time.**  
   The traces are sequences of activity completions. “Overlap” therefore means that the completion events of two activities may interleave in either order, not necessarily that their executions start at the same instant.

3. **Representation of low-risk/high-risk choice.**  
   The risk route is represented as an exclusive control-flow choice after `Analyze Root Cause`:
   - low-risk branch: `Supervisor Review`;
   - high-risk branch: concurrent `Quality Review` and `Regulatory Review`, in either completion order.  
   No data attribute such as “risk level” is encoded. The choice is structural.

4. **Representation of optional supplier consultation.**  
   `Consult Supplier` is represented as an exclusive choice between performing `Consult Supplier` once and taking a silent skip transition. This makes the activity optional and at most once, without encoding the case-data condition that selects it.

5. **Abstraction of passing/failing inspection.**  
   The trial repetition is represented by a loop. The loop body is `Execute Trial` followed by `Inspect Trial`. The loop redo child is `Adjust Parameters`. Under the assumed PM4Py loop semantics, this yields:
   ```text
   ET IT (AP ET IT)*
   ```
   Thus an `Adjust Parameters` event occurs only between trial cycles and never after the final passing `Inspect Trial`. The pass/fail result itself is not an event label.

6. **Duplicate visible labels.**  
   Duplicate visible labels are **not permitted** in the selected models, except for intended behavioral repetitions caused by the trial loop: `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` may appear multiple times in a trace because the trial cycle may repeat. I deliberately avoid duplicating activities such as `Analyze Root Cause` or `Design Corrective Action` as separate model leaves, because that would create artificial duplicate events in traces or ambiguous model moves during conformance checking.

7. **Process-tree approximation policy.**  
   The process tree uses a **conservative under-approximation** policy. It preserves the hard prerequisites and the final release safety conditions, but it excludes some intended behavior: it forces the selected approval route and the optional supplier consultation, when selected, to complete before the trial loop starts. This excludes legally allowed overlap of approvals or supplier consultation with trial execution, but it avoids admitting unsafe behavior such as release before approvals or supplier consultation are complete.  
   The reason for this policy is that a block-structured process tree cannot directly express the required non-block synchronization: trial must wait for `Plan Verification` and `Design Corrective Action`, while approvals and optional supplier consultation may bypass that synchronization and join only at `Release Material`.

8. **Interpretation of “may overlap.”**  
   “May overlap” is interpreted as **absence of an order constraint**, not as a requirement for true simultaneous execution. In the process tree, parallelism is represented by the parallel operator and is usually interpreted through interleavings. In the POWL model, concurrency is represented by missing partial-order edges.

9. **Assumed loop semantics.**  
   I assume PM4Py’s `LOOP` operator has the common process-tree semantics:
   ```text
   loop(body, redo) = body (redo body)*
   ```
   Therefore, `loop(sequence(ET, IT), AP)` admits one or more trial cycles and places `AP` only between cycles. If a particular PM4Py version uses a different convention, the child order would need to be checked or swapped.

# 3. PM4Py Process-Tree Model

**Compact process-tree expression**

```text
sequence(
  'Register Deviation',
  parallel(
    sequence('Contain Material', 'Plan Verification'),
    sequence(
      'Analyze Root Cause',
      parallel(
        'Design Corrective Action',
        xor(
          'Supervisor Review',
          parallel('Quality Review', 'Regulatory Review')
        ),
        xor('Consult Supplier', tau)
      )
    )
  ),
  loop(
    sequence('Execute Trial', 'Inspect Trial'),
    'Adjust Parameters'
  ),
  'Release Material',
  'Archive Case'
)
```

Here, `tau` denotes a silent skip for the optional supplier consultation.

**Self-contained Python construction**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def add_child(parent, child):
    if parent.children is None:
        parent.children = []
    parent.children.append(child)
    child.parent = parent
    return child


def leaf(label=None):
    return ProcessTree(label=label)


# Root sequence
root = ProcessTree(operator=Operator.SEQUENCE)

# 1. Register Deviation
add_child(root, leaf("Register Deviation"))

# 2. Initial parallel work streams:
#    - Contain Material -> Plan Verification
#    - Analyze Root Cause -> post-analysis parallel work
initial_parallel = ProcessTree(operator=Operator.PARALLEL)
add_child(root, initial_parallel)

# Containment / verification-planning branch
contain_branch = ProcessTree(operator=Operator.SEQUENCE)
add_child(initial_parallel, contain_branch)
add_child(contain_branch, leaf("Contain Material"))
add_child(contain_branch, leaf("Plan Verification"))

# Root-cause / corrective-action / approval / supplier branch
analysis_branch = ProcessTree(operator=Operator.SEQUENCE)
add_child(initial_parallel, analysis_branch)
add_child(analysis_branch, leaf("Analyze Root Cause"))

post_analysis_parallel = ProcessTree(operator=Operator.PARALLEL)
add_child(analysis_branch, post_analysis_parallel)

# Design Corrective Action
add_child(post_analysis_parallel, leaf("Design Corrective Action"))

# Risk route: low-risk XOR high-risk
risk_xor = ProcessTree(operator=Operator.XOR)
add_child(post_analysis_parallel, risk_xor)

# Low-risk branch
add_child(risk_xor, leaf("Supervisor Review"))

# High-risk branch: Quality Review and Regulatory Review concurrent
high_risk_parallel = ProcessTree(operator=Operator.PARALLEL)
add_child(risk_xor, high_risk_parallel)
add_child(high_risk_parallel, leaf("Quality Review"))
add_child(high_risk_parallel, leaf("Regulatory Review"))

# Optional supplier consultation: Consult Supplier XOR silent skip
supplier_xor = ProcessTree(operator=Operator.XOR)
add_child(post_analysis_parallel, supplier_xor)
add_child(supplier_xor, leaf("Consult Supplier"))
add_child(supplier_xor, leaf(None))  # silent skip / tau

# 3. Trial loop: ET IT (AP ET IT)*
trial_loop = ProcessTree(operator=Operator.LOOP)
add_child(root, trial_loop)

trial_cycle = ProcessTree(operator=Operator.SEQUENCE)
add_child(trial_loop, trial_cycle)
add_child(trial_cycle, leaf("Execute Trial"))
add_child(trial_cycle, leaf("Inspect Trial"))

add_child(trial_loop, leaf("Adjust Parameters"))

# 4. Release and archive
add_child(root, leaf("Release Material"))
add_child(root, leaf("Archive Case"))

tree = root
```

**Approximation and representational loss**

The process tree is not an exact representation of the intended semantics. The principal loss concerns the non-block synchronization around trial and release. In the intended behavior, the selected approval route and optional supplier consultation may overlap the trial cycle and need only complete before `Release Material`. The tree above instead places the approval route and supplier choice inside the pre-trial parallel block. Consequently, the parallel join forces those obligations to complete before the trial loop can start. This is a conservative overconstraint: it excludes allowed traces such as a high-risk `Quality Review` completing after `Execute Trial` but before `Release Material`, while still preventing unsafe release before approvals or supplier consultation. The tree also represents risk level and supplier involvement as structural choices rather than data conditions, as required by the task. The pass/fail inspection result is not encoded as a label; it is abstracted by the loop’s exit versus redo behavior. Finally, the tree avoids duplicate visible labels, which preserves clean trace semantics but prevents a more permissive duplication-based encoding of approval/supplier overlap with trial.

# 4. PM4Py POWL Model

**Compact POWL description**

```text
StrictPartialOrder(
  nodes = [
    R, C, A, PV, DCA,
    ApprovalRoute,
    SupplierChoice,
    TrialLoop,
    RM, AC
  ],
  edges = [
    R -> C,
    R -> A,
    C -> PV,
    A -> DCA,
    A -> ApprovalRoute,
    A -> SupplierChoice,
    PV -> TrialLoop,
    DCA -> TrialLoop,
    TrialLoop -> RM,
    ApprovalRoute -> RM,
    SupplierChoice -> RM,
    RM -> AC
  ],

  ApprovalRoute = XOR(
    SR,
    SPO(QR, RR)   // no QR -> RR edge, so concurrent
  ),

  SupplierChoice = XOR(
    tau,
    CS
  ),

  TrialLoop = LOOP(
    SPO(ET -> IT),
    AP
  )
)
```

**Self-contained Python construction**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Visible transitions
R = Transition(label="Register Deviation")
C = Transition(label="Contain Material")
A = Transition(label="Analyze Root Cause")
PV = Transition(label="Plan Verification")
DCA = Transition(label="Design Corrective Action")
SR = Transition(label="Supervisor Review")
QR = Transition(label="Quality Review")
RR = Transition(label="Regulatory Review")
CS = Transition(label="Consult Supplier")
ET = Transition(label="Execute Trial")
IT = Transition(label="Inspect Trial")
AP = Transition(label="Adjust Parameters")
RM = Transition(label="Release Material")
AC = Transition(label="Archive Case")

# High-risk route: QR and RR concurrent.
# Concurrency is expressed by having no order edge between QR and RR.
high_risk = StrictPartialOrder(nodes=[QR, RR])

# Risk route: low-risk SR XOR high-risk concurrent QR/RR.
approval_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[SR, high_risk]
)

# Optional supplier consultation: silent skip XOR Consult Supplier.
supplier_skip = SilentTransition()
supplier_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[supplier_skip, CS]
)

# One trial cycle: Execute Trial -> Inspect Trial.
trial_cycle = StrictPartialOrder(nodes=[ET, IT])
trial_cycle.order.add_edge(ET, IT)

# Trial loop: ET IT (AP ET IT)*
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_cycle, AP]
)

# Top-level partial order.
powl = StrictPartialOrder(
    nodes=[
        R,
        C,
        A,
        PV,
        DCA,
        approval_route,
        supplier_choice,
        trial_loop,
        RM,
        AC
    ]
)

# Initial work streams
powl.order.add_edge(R, C)
powl.order.add_edge(R, A)

# Split dependencies
powl.order.add_edge(C, PV)
powl.order.add_edge(A, DCA)

# Post-analysis optional / approval obligations
powl.order.add_edge(A, approval_route)
powl.order.add_edge(A, supplier_choice)

# Trial prerequisites
powl.order.add_edge(PV, trial_loop)
powl.order.add_edge(DCA, trial_loop)

# Release synchronization
powl.order.add_edge(trial_loop, RM)
powl.order.add_edge(approval_route, RM)
powl.order.add_edge(supplier_choice, RM)

# End
powl.order.add_edge(RM, AC)
```

**Why intentionally unconnected nodes may remain concurrent**

The POWL model intentionally omits several order edges:

- `C` and `A` are unconnected after `R`, so containment and root-cause analysis may overlap.
- `PV` and `DCA` are unconnected, so verification planning and corrective-action design may overlap once their own prerequisites are satisfied.
- `approval_route` and `trial_loop` are unconnected except that both precede `RM`. Therefore approvals may occur before, during, or after trial cycles, but release waits for both.
- `supplier_choice` and `trial_loop` are unconnected except that both precede `RM`. Therefore supplier consultation may overlap trial work, but release waits for supplier completion if selected.
- `approval_route` and `supplier_choice` are unconnected, so approvals and supplier consultation may overlap.
- Inside the high-risk route, `QR` and `RR` are unconnected, so they may complete in either order.
- `approval_route` and `supplier_choice` are not ordered relative to `PV` or `DCA`, except through their shared dependency on `A` and shared successor `RM`. Thus they may occur while planning/design are ongoing, subject to their own prerequisites and release synchronization.

These missing edges are deliberate. They encode “may overlap” as absence of ordering, while the explicit edges preserve the mandatory dependencies.

# 7. Preferred Representation and Validation Plan

**Preferred canonical representation**

I prefer the **POWL model** as the canonical semantic representation for this process. The reason is that the narrative is fundamentally a partial-order specification: some activities are concurrent, some dependencies cross branches, and release is a synchronization point over independently progressing obligations. POWL can express these dependencies directly without forcing an artificial block structure. The process tree is useful for compatibility with tree-based tooling, but its conservative approximation hides the key approval/trial and supplier/trial overlap behavior.

For validation and execution, however, I would use an **accepting Petri net** as the canonical interchange representation where PM4Py conversion is supported. Petri nets provide an executable semantics and allow soundness checking, playout, and trace replay.

**Validation plan**

1. **Conversion to accepting Petri nets**

   Convert both models to accepting Petri nets where supported:

   ```python
   import pm4py

   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   ```

   If POWL-to-Petri-net conversion is not supported in a given PM4Py version, the POWL model should first be validated through available POWL-specific playout or serialization tools, and then manually translated into an equivalent accepting Petri net for analysis.

2. **Soundness checking**

   Check that the converted nets are structurally sound:

   ```python
   pm4py.check_soundness(tree_net, tree_im, tree_fm, print_diagnostics=True)
   pm4py.check_soundness(powl_net, powl_im, powl_fm, print_diagnostics=True)
   ```

   Expected outcome:
   - both nets should reach their final markings without deadlocks;
   - no required activity should be skipped unintentionally;
   - silent skip for supplier should not create unsafe bypass of release conditions.

3. **Bounded or sampled playout**

   Because the trial loop is unbounded, playout must be bounded or sampled. For example, using PM4Py’s playout facilities with version-appropriate bounding parameters:

   ```python
   sample_log_from_tree = pm4py.play_out(
       tree,
       parameters={"max_traces": 200, "max_trace_length": 40}
   )

   sample_log_from_powl = pm4py.play_out(
       powl,
       parameters={"max_traces": 200, "max_trace_length": 40}
   )
   ```

   If those exact parameter names are unavailable, use the installed PM4Py version’s equivalent bounded playout options, or perform bounded token-game exploration of the converted Petri nets.

4. **Explicit positive and negative trace tests**

   Use the eight witnesses from Section 5.

   Expected results:

   - POWL:
     - accept: T1, T2, T3, T4, T5;
     - reject: T6, T7, T8.
   - Process tree:
     - accept: T1, T3, T4, T5;
     - reject: T2, T6, T7, T8.

   The rejection of T2 by the process tree is expected and demonstrates the conservative approximation. The rejection of T6, T7, and T8 by both models demonstrates preservation of key safety dependencies.

5. **Silent-behavior and duplicate-label check**

   For sampled traces, project away silent transitions and check label properties:

   - `Register Deviation`, `Contain Material`, `Analyze Root Cause`, `Plan Verification`, `Design Corrective Action`, `Release Material`, and `Archive Case` should appear at most once per trace.
   - `Consult Supplier` should appear zero or one time.
   - Either `Supervisor Review` appears, or both `Quality Review` and `Regulatory Review` appear, but not a mixture of low-risk and high-risk reviews.
   - `Execute Trial` and `Inspect Trial` may repeat, but every `Adjust Parameters` must be followed by another `Execute Trial` before release.
   - No `Adjust Parameters` may occur after the final `Inspect Trial`.
   - Silent transitions should not appear in the visible projection.

   Conceptual checks:

   ```python
   non_repeatable = [
       "Register Deviation",
       "Contain Material",
       "Analyze Root Cause",
       "Plan Verification",
       "Design Corrective Action",
       "Supervisor Review",
       "Quality Review",
       "Regulatory Review",
       "Consult Supplier",
       "Release Material",
       "Archive Case",
   ]

   for trace in visible_traces:
       for label in non_repeatable:
           assert trace.count(label) <= 1
   ```

6. **Limitations of the validation plan**

   - Successful conversion and soundness checking do not prove semantic fidelity to the business narrative; they only show structural executability.
   - Sampled playout cannot exhaustively validate an unbounded loop or all partial-order interleavings.
   - The POWL model assumes that concurrency with a compound node such as the trial loop allows interleaving with the compound node’s internal transitions. This should be checked empirically in the installed PM4Py version.
   - Silent transitions for optional supplier skip may create invisible paths that affect conformance checking and alignment costs.
   - Risk level and supplier selection are free control-flow choices in both models, so validation cannot detect cases where the wrong branch is chosen relative to external case data.

# 8. Final Self-Critique

1. **Semantic uncertainty around hierarchical POWL concurrency.**  
   The POWL model assumes that a compound node such as `TrialLoop` can be concurrent with `ApprovalRoute` and `SupplierChoice` in a way that permits visible interleavings like `ET, QR, IT, RR`. If PM4Py’s POWL execution or Petri-net conversion treats compound operator nodes more atomically, some intended traces such as T2 may not be accepted. This is a semantic issue, not merely a Python syntax issue, and it requires empirical validation in the target PM4Py version.

2. **Control-flow choices abstract away case-data validity.**  
   The low-risk/high-risk choice and the optional supplier choice are represented as free structural choices. This satisfies the task’s instruction not to encode data conditions, but it means the models admit cases where the selected branch may be inconsistent with the actual case data. Therefore, the models are semantically underconstrained with respect to the real business decision logic.

3. **Process-tree approximation is safe but potentially too conservative.**  
   The chosen process tree excludes all approval/supplier overlap with the trial cycle. This preserves release safety and avoids duplicate visible labels, but it may be too restrictive for operational analysis, especially cycle-time analysis. A duplication-based process tree might recover some of that overlap, but at the cost of duplicated model leaves, more complex conformance alignment, and possible analytical artifacts. The answer does not provide a formal proof that the chosen approximation is the least restrictive safe tree approximation.
