# 1. Policy Interpretation and Conflict Resolution

## Material Assumptions
1. **R5/R6 Conflict**: The legal department's strict policy (R5) and operations' emergency policy (R6) are incompatible in the event log. We assume:
   - No explicit "emergency" attribute exists in logs.
   - Joint authorization is not recorded in event logs (only visible to external systems).
   - The 24-hour window for legal opinion is a hard constraint for compliance.

2. **Resource Segregation (R9)**: Resources are uniquely identifiable in event logs via the `resource` attribute. Missing resources default to "unknown" and trigger warnings.

3. **Temporal Deviations (R12)**: These are treated as warnings (not violations) to avoid false positives in high-pressure scenarios.

## Conflict Resolution Options
| Option | Description | Compliance Risk |
|--------|-------------|-----------------|
| **Strict Legal Priority** | Always enforce R5 (legal opinion before activation). Emergency activations are rejected. | Low (fully compliant), but may delay critical operations. |
| **Emergency Override** | Allow activation before legal opinion if within 24 hours (R6). Log a compliance warning. | Medium (requires manual review of exceptions). |
| **Hybrid Approach** | Use R5 as default, but allow R6 if an external system flags "emergency_override=True" (not in logs). | High (relies on external coordination). |

**Chosen Resolution**: **Emergency Override with Warning**
- **Implementation**: Enforce R5 in the procedural model but add a resource/data check (Section 7) to validate R6 conditions (24-hour window + implicit authorization).
- **Compliance Risk**: Acceptable if warnings trigger manual review. The risk is mitigated by treating R6 as a policy exception rather than a rule.

# 3. Procedural Backbone

## Compact Formal Description
The procedural model is a **ProcessTree** with:
1. **Concurrent start**: `Receive Onboarding Request`  `{Capture Master Data, Run Sanctions Screening, Verify Bank Account}`.
2. **Synchronization**: All three checks must complete before `Classify Risk`.
3. **Branching**:
   - `Classify Risk`  `Reject Vendor` (terminal).
   - `Classify Risk`  `Manager Approval` (low-risk).
   - `Classify Risk`  `Enhanced Due Diligence`  `Compliance Approval` (high-risk).
4. **Clarification loop**: `Request Clarification`  `Receive Clarification` (repeatable) before any terminal outcome.
5. **Sanctions escalation**: `Run Sanctions Screening`  `Sanctions Escalation`  `Obtain Legal Opinion` (mandatory if escalated).
6. **Terminal outcomes**:
   - `Reject Vendor`  `Close Onboarding`.
   - `Activate Vendor`  `Release First Payment`  `Close Onboarding`.
7. **Post-activation**: `Change Bank Details`  `Suspend Vendor`  `Verify Bank Account`  `Release First Payment`.

## PM4Py ProcessTree Code
```python

from pm4py.objects.process_tree.obj import Event

# Build the tree

start = Event("Receive Onboarding Request")
tree.root = start

# Concurrent checks
concurrent = Operator(Operator.CONCURRENT)
capture = Event("Capture Master Data")
sanctions = Event("Run Sanctions Screening")
verify = Event("Verify Bank Account")
concurrent.add_child(capture)
concurrent.add_child(sanctions)
concurrent.add_child(verify)
start.add_child(concurrent)

# Synchronization to Classify Risk
classify = Event("Classify Risk")
tree.add_sequence(concurrent, classify)

# Branching
reject = Event("Reject Vendor")
manager = Event("Manager Approval")
edd = Event("Enhanced Due Diligence")
compliance = Event("Compliance Approval")

# Low-risk path
low_risk = Operator(Operator.SEQUENCE)
low_risk.add_child(manager)
low_risk.add_child(Event("Activate Vendor"))
tree.add_choice(classify, reject, low_risk)

# High-risk path
high_risk = Operator(Operator.SEQUENCE)
high_risk.add_child(edd)
high_risk.add_child(compliance)
high_risk.add_child(Event("Activate Vendor"))
tree.add_choice(classify, reject, high_risk)

## Explanation
- **Concurrency**: The three checks (`Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account`) run in parallel after `Receive Onboarding Request`.
- **Choices**: After `Classify Risk`, the process branches into reject, low-risk, or high-risk paths.
- **Clarification Loops**: Not fully modeled in ProcessTree (see DECLARE for `chainresponse`).
- **Terminal Outcomes**: `Reject Vendor` and `Activate Vendor` are mutually exclusive (enforced by DECLARE).
- **Post-Activation**: `Change Bank Details`  `Suspend Vendor`  `Verify Bank Account` is modeled as a separate subpath (not shown in full tree for brevity).

## Rule Semantics Table

| Rule Type | Source  Target | Semantics | Direction |
|-----------|-----------------|-----------|-----------|
| `exactly_one` | `Manager Approval`, `Compliance Approval` | Exactly one of these must occur in accepted cases. | Mutual exclusion |
| `chainresponse` | `Request Clarification`  `Receive Clarification` | Every `Request Clarification` must eventually be followed by `Receive Clarification`. | Response chain |
| `nonchainsuccession` | `Request Clarification`  `Reject Vendor`/`Activate Vendor` | No terminal outcome before all clarifications are answered. | Non-succession |
| `precedence` | `Sanctions Escalation`  `Obtain Legal Opinion` | `Obtain Legal Opinion` must follow `Sanctions Escalation`. | Precedence |
| `precedence` | `Run Sanctions Screening`  `Sanctions Escalation` | `Sanctions Escalation` cannot occur before screening. | Precedence |
| `noncoexistence` | `Enhanced Due Diligence`  `Manager Approval` | These cannot occur in the same case. | Mutual exclusion |
| `exactly_one` | `Reject Vendor`, `Activate Vendor`, `Release First Payment` | Each occurs at most once. | Cardinality |

        ("Manager Approval", "Activate Vendor"),

        ("Reject Vendor", "Close Onboarding"),
    },

## Overlap/Disagreement Notes
- **Procedural vs. DECLARE**:
  - `always_before` in log skeleton mirrors `precedence` in DECLARE (e.g., `Sanctions Escalation`  `Obtain Legal Opinion`).
  - `never_together` in log skeleton mirrors `noncoexistence` in DECLARE (e.g., approvals).
- **Log Skeleton Limitations**:
  - Cannot express "eventually" (e.g., `Obtain Legal Opinion` must eventually follow `Sanctions Escalation`).
  - Cannot model loops (e.g., clarification cycles).
- **Orientation**:
  - `always_before` is stricter than DECLARE `precedence` (requires direct succession).
  - `directly_follows` is more permissive than procedural sequences.

## Why Warnings?
Temporal deviations are treated as warnings because:
1. **Business Flexibility**: Operations may need to adjust timelines (e.g., `Release First Payment` delayed due to payment processing).
2. **False Positives**: Strict enforcement could reject valid cases (e.g., `Obtain Legal Opinion` delayed by external legal teams).
3. **Manual Review**: Compliance (R12) expects humans to investigate deviations, not automate rejections.

# 7. Resource- and Data-Aware Checks
```python
import pandas as pd
from datetime import datetime, timedelta

def check_resource_segregation(log_df):
    """Check R9: Verify Bank Account  approval resource, Capture Master Data  Activate Vendor resource."""
    violations = []
    for _, case in log_df.groupby("case:concept:name"):
        verify_bank = case[case["concept:name"] == "Verify Bank Account"]["resource"].values
        approvals = case[case["concept:name"].isin(["Manager Approval", "Compliance Approval"])]["resource"].values
        if len(verify_bank) > 0 and len(approvals) > 0 and any(verify_bank == approvals):
            violations.append(f"Case {case.name}: Verify Bank Account and approval by same resource.")

        capture_master = case[case["concept:name"] == "Capture Master Data"]["resource"].values
        activate_vendor = case[case["concept:name"] == "Activate Vendor"]["resource"].values
        if len(capture_master) > 0 and len(activate_vendor) > 0 and any(capture_master == activate_vendor):
            violations.append(f"Case {case.name}: Capture Master Data and Activate Vendor by same resource.")
    return violations

def check_emergency_policy(log_df):
    """Check R6: Activate Vendor before Obtain Legal Opinion must have opinion within 24h."""
    violations = []
    for _, case in log_df.groupby("case:concept:name"):
        activate_events = case[case["concept:name"] == "Activate Vendor"]
        legal_events = case[case["concept:name"] == "Obtain Legal Opinion"]
        if not activate_events.empty and not legal_events.empty:
            activate_time = activate_events["time:timestamp"].iloc[0]
            legal_time = legal_events["time:timestamp"].iloc[0]
            if activate_time < legal_time:
                delta = (legal_time - activate_time).total_seconds() / 3600
                if delta > 24:
                    violations.append(f"Case {case.name}: Activate Vendor at {activate_time} but Obtain Legal Opinion at {legal_time} (>24h later).")
    return violations

def check_four_eyes(log_df):
    """Check R9: Verify Bank Account  approval resource (using pm4py helper)."""
    violations = []
    for _, case in log_df.groupby("case:concept:name"):
        verify_bank = case[case["concept:name"] == "Verify Bank Account"]
        approvals = case[case["concept:name"].isin(["Manager Approval", "Compliance Approval"])]
        if not verify_bank.empty and not approvals.empty:
            for _, vb_row in verify_bank.iterrows():
                for _, a_row in approvals.iterrows():
                    if vb_row["resource"] == a_row["resource"]:
                        violations.append(f"Case {case.name}: Four-eyes violation between Verify Bank Account and {a_row['concept:name']} by {vb_row['resource']}.")
    return violations
```

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated Enforcement
- **R2**: Enforced by:
  - Procedural (mutually exclusive paths).
  - DECLARE (`exactly_one` and `noncoexistence`).
  - Log Skeleton (`never_together`).
  - **Redundancy**: DECLARE and log skeleton are authoritative; procedural is declarative.
- **R4/R7**: Enforced by:
  - Procedural (`Sanctions Escalation`  `Obtain Legal Opinion`).
  - DECLARE (`precedence`).
  - Log Skeleton (`always_before`).
  - **Redundancy**: DECLARE is authoritative; procedural/log skeleton are cross-validations.

## Inconsistent Constraints
- **Post-Activation Changes (R11)**:
  - Procedural models `Change Bank Details`  `Suspend Vendor`  `Verify Bank Account`  `Release First Payment`.
  - DECLARE enforces `precedence` but cannot express "eventually" (e.g., `Suspend Vendor` must eventually follow `Change Bank Details`).
  - **Blind Spot**: If `Suspend Vendor` is skipped, the model cannot detect it without temporal checks.
- **Clarification Loops (R3)**:
  - DECLARE uses `chainresponse` but cannot enforce that all clarifications are answered before terminal outcomes in loops.
  - **Blind Spot**: A case could have `Request Clarification`  `Classify Risk`  `Activate Vendor` without `Receive Clarification`.

## Vacuity in Declarative Rules
- **`noncoexistence` (R8)**:
  - If `Enhanced Due Diligence` and `Manager Approval` never co-occur in logs, the rule is vacuously true.
  - **Risk**: False positives if the rule is misapplied to new data.
- **Temporal Profile (R12)**:
  - If no `Sanctions Escalation` occurs, the `Obtain Legal Opinion` rule is never triggered.
  - **Risk**: Overfitting to observed behavior.

## Missing Attributes
- **Emergency Policy (R6)**:
  - Requires `time:timestamp` and implicit "joint authorization" (not in logs).
  - **Workaround**: Use timestamp delta as a proxy (Section 7).
- **Resource Segregation (R9)**:
  - Missing `resource` attribute defaults to "unknown," which may bypass checks.
  - **Workaround**: Flag as warning and escalate.

## Timestamp Limitations
- **Temporal Profile**:
  - Cannot distinguish between:
    - `Obtain Legal Opinion` delayed due to backlog (valid).
    - `Obtain Legal Opinion` delayed due to fraud (invalid).
  - **Risk**: False negatives for malicious delays.

## Support/Confidence Metadata
- **Assumption**: `support=1.0` and high `confidence` are treated as normative.
- **Risk**: If the model is trained on incomplete logs (e.g., missing `Sanctions Escalation` cases), rules may be overconfident.
- **Mitigation**: Use domain knowledge to set conservative thresholds (e.g., `confidence=0.9` for critical rules).

# 10. Deployment Recommendation

## Canonical Representation
1. **Procedural Model (ProcessTree)**:
   - Authoritative for control-flow (R1, R4, R7, R11).
   - Defines the "happy path" and terminal outcomes.
2. **DECLARE Model**:
   - Authoritative for declarative constraints (R2, R3, R8, R10).
   - Catches violations not expressible in procedural models (e.g., loops, coexistence).
3. **Log Skeleton**:
   - Used for lightweight validation (e.g., cardinality, direct succession).
   - Less authoritative than DECLARE but faster to compute.
4. **Temporal Profile**:
   - Generates warnings, not violations.
   - Used for compliance monitoring (R12).
5. **Resource/Data Layer**:
   - Authoritative for segregation-of-duties (R9) and emergency policy (R6).
   - Requires event attributes (`resource`, `time:timestamp`).

## Check Order
1. **Procedural Conformance**: Fast rejection of obviously invalid traces.
2. **DECLARE Conformance**: Catch declarative violations (e.g., loops, coexistence).
3. **Log Skeleton**: Validate cardinality and direct succession.
4. **Temporal Profile**: Flag deviations for manual review.
5. **Resource/Data Checks**: Enforce segregation-of-duties and emergency policy.

## Contradictory Findings
- **Procedural vs. DECLARE**:
  - If a trace passes procedural but fails DECLARE (e.g., `Request Clarification` without `Receive Clarification`), prioritize DECLARE.
- **DECLARE vs. Resource Checks**:
  - If a trace passes DECLARE but fails resource segregation (e.g., `Verify Bank Account` and `Manager Approval` by same resource), escalate as a **critical violation**.
- **Temporal Warnings**:
  - Treat as **low-priority alerts** unless combined with other violations (e.g., late `Obtain Legal Opinion` + `Sanctions Escalation` flagged in logs).

## Surface to Users
- **Dashboard**:
  - **Critical Violations**: Procedural fails, DECLARE fails, or resource/data fails.
  - **Warnings**: Temporal deviations, missing attributes, or low-confidence DECLARE rules.
- **Alerts**:
  - **Blockers**: `Reject Vendor` and `Activate Vendor` in same case (R1).
  - **Escalations**: Four-eyes violations (R9), unanswered clarifications (R3), or emergency policy conflicts (R6).
- **Audit Trail**:
  - Log which checks were performed and why a trace was accepted/rejected.

## Example Workflow
1. **Case T4** (Four-Eyes Violation):
   - Procedural: Passes (control-flow is valid).
   - DECLARE: Passes (no declarative violations).
   - Resource Check: Fails (`Verify Bank Account` and `Manager Approval` by `Cora`).
   - **Action**: Block activation; notify compliance.
2. **Case T6** (Emergency Policy Conflict):
   - Procedural: Fails (no `Obtain Legal Opinion` before `Activate Vendor`).
   - Resource Check: If `Obtain Legal Opinion` arrives within 24h, flag as **warning** (R6 override).
   - **Action**: Manual review; document exception if R6 applies.
