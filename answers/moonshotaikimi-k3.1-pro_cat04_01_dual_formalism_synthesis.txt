# 1. Assumptions and Interpretation

1. **Activity and event abstraction.** Each visible activity occurrence is an atomic event recorded at completion. A precedence `X  Y` is the usual activity-level abstraction of “Y may start only after X completes.” Without start events and durations, completion traces alone cannot verify that stronger temporal statement. Activities occur once per case unless they are trial-loop activities or the optional consultation.

2. **Risk choice.** The risk data itself is not modeled. `RiskRoute` is an XOR between:
   - low risk: `Supervisor Review`;
   - high risk: a partial order/parallel block containing both `Quality Review` and `Regulatory Review`, with no edge between them.  
   The selected alternative is identifiable from the visible review activities, not from a separate risk event.

3. **Optional supplier consultation.** `SupplierOption` is `XOR(, Consult Supplier)`, where `` is silent. Thus consultation is skipped or occurs exactly once. In POWL, the whole option is after root-cause analysis and before release; in the process tree its placement is deliberately more restrictive.

4. **Inspection outcome.** No pass/fail event is introduced. The binary loop is interpreted as `do (redo do)*`. With `do = Execute Trial  Inspect Trial` and `redo = Adjust Parameters`, its visible projection is:
   ```text
   T I (J T I)*
   ```
   Loop-back abstracts a failed inspection; loop exit abstracts a pass on the last inspection. Consequently, `J` cannot occur after the loop’s passing exit.

5. **Duplicate labels.** No static duplicate visible labels are used in either model. Repeated `T`, `I`, and `J` events in traces are loop unfoldings, not duplicated model nodes. A duplication-based process-tree encoding is not used.

6. **Process-tree approximation policy.** The process tree is a **conservative under-approximation**: every visible trace it admits is intended to be legal, but some intended interleavings are excluded. It does not admit unsafe early trials or releases in exchange for broader coverage. The POWL model is exact relative to the stated activity-level abstraction.

7. **Meaning of “may overlap.”** This means **absence of an order constraint**, not compulsory physical overlap or simultaneous completion. Sequential execution in either order remains allowed unless a precedence says otherwise.

8. **Compact notation.** The abbreviations are: `R` Register Deviation, `C` Contain Material, `A` Analyze Root Cause, `P` Plan Verification, `D` Design Corrective Action, `S` Supervisor Review, `Q` Quality Review, `G` Regulatory Review, `U` Consult Supplier, `T` Execute Trial, `I` Inspect Trial, `J` Adjust Parameters, `L` Release Material, and `Z` Archive Case. Silent `` never appears in a visible trace.

# 3. PM4Py Process-Tree Model

The compact expression is:

```text
->(
  R,
  +(
    ->(C, P),
    ->(A, D)
  ),
  +(
    *(->(T, I), J),
    X(S, +(Q, G)),
    X(, U)
  ),
  L,
  Z
)
```

Here `->` is sequence, `+` is parallel/interleaving, `X` is XOR, and `*(do, redo)` means `do (redo do)*`. The first parallel block preserves all interleavings of the two precedence chains `C < P` and `A < D`. The second parallel block lets the trial, approval route, and supplier option overlap, and its completion synchronizes them before `L`.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def activity(label):
    return ProcessTree(label=label)


def compose(operator, children):
    node = ProcessTree(operator=operator)
    for child in children:
        # Explicitly maintain both sides of the parent/child relationship.
        node.children.append(child)
        child.parent = node
    return node


trial_loop = compose(
    Operator.LOOP,
    [
        compose(
            Operator.SEQUENCE,
            [activity("Execute Trial"), activity("Inspect Trial")]
        ),
        activity("Adjust Parameters")
    ]
)

risk_route = compose(
    Operator.XOR,
    [
        activity("Supervisor Review"),
        compose(
            Operator.PARALLEL,
            [activity("Quality Review"), activity("Regulatory Review")]
        )
    ]
)

supplier_option = compose(
    Operator.XOR,
    [
        ProcessTree(),  # silent tau: supplier consultation not selected
        activity("Consult Supplier")
    ]
)

tree = compose(
    Operator.SEQUENCE,
    [
        activity("Register Deviation"),
        compose(
            Operator.PARALLEL,
            [
                compose(
                    Operator.SEQUENCE,
                    [activity("Contain Material"), activity("Plan Verification")]
                ),
                compose(
                    Operator.SEQUENCE,
                    [
                        activity("Analyze Root Cause"),
                        activity("Design Corrective Action")
                    ]
                )
            ]
        ),
        compose(
            Operator.PARALLEL,
            [trial_loop, risk_route, supplier_option]
        ),
        activity("Release Material"),
        activity("Archive Case")
    ]
)
```

**Fidelity and approximation.** The tree preserves start/end behavior, the `C < P` and `A < D` chains, all interleavings among those four activities, the risk alternatives, high-review concurrency, the repeat-until loop, optional consultation, and release synchronization. Its loss is that `risk_route` and `supplier_option` both wait for the complete initial join—hence for `C`, `P`, `A`, and `D`—although the intended model requires only `A` before them. It therefore excludes early reviews or consultation and their overlap with design, containment/planning, or other pre-trial work. Placing these submodels instead inside the analysis branch would preserve earlier starts but force them to complete before the trial, sacrificing the explicitly required approval/trial overlap. The chosen placement retains that overlap and keeps release safe. Thus the loss is deliberate under-approximation, not a claim that the displayed tree is exact; no duplicated-label construction is being used to conceal the non-block structure.

# 4. PM4Py POWL Model

```text
HIGH   = StrictPartialOrder(Q, G)          # deliberately no Q/G edge
ROUTE  = XOR(S, HIGH)
SUP    = XOR(, U)
CYCLE  = StrictPartialOrder(T -> I)
TRIAL  = LOOP(do=CYCLE, redo=J)            # CYCLE (J CYCLE)*

ROOT nodes = {R, C, A, P, D, ROUTE, SUP, TRIAL, L, Z}

ROOT edges, and no others:
  R -> C
  R -> A
  C -> P
  A -> D
  A -> ROUTE
  A -> SUP
  P -> TRIAL
  D -> TRIAL
  TRIAL -> L
  ROUTE -> L
  SUP -> L
  L -> Z
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

R = Transition("Register Deviation")
C = Transition("Contain Material")
A = Transition("Analyze Root Cause")
P = Transition("Plan Verification")
D = Transition("Design Corrective Action")
S = Transition("Supervisor Review")
Q = Transition("Quality Review")
G = Transition("Regulatory Review")
U = Transition("Consult Supplier")
T = Transition("Execute Trial")
I = Transition("Inspect Trial")
J = Transition("Adjust Parameters")
L = Transition("Release Material")
Z = Transition("Archive Case")

# High-risk reviews are both mandatory but intentionally unordered.
high = StrictPartialOrder([Q, G])
route = OperatorPOWL(
    operator=Operator.XOR,
    children=[S, high]
)

# The silent alternative implements absence of supplier consultation.
supplier = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), U]
)

cycle = StrictPartialOrder([T, I])
cycle.order.add_edge(T, I)

# Binary LOOP semantics: cycle (J cycle)*.
trial = OperatorPOWL(
    operator=Operator.LOOP,
    children=[cycle, J]
)

powl = StrictPartialOrder(
    [R, C, A, P, D, route, supplier, trial, L, Z]
)

# Initial independent work and split dependencies.
powl.order.add_edge(R, C)
powl.order.add_edge(R, A)
powl.order.add_edge(C, P)
powl.order.add_edge(A, D)

# Analysis-dependent obligations.
powl.order.add_edge(A, route)
powl.order.add_edge(A, supplier)

# Trial joins planning and design, but not approvals or consultation.
powl.order.add_edge(P, trial)
powl.order.add_edge(D, trial)

# Release synchronizes the three independently progressing obligations.
powl.order.add_edge(trial, L)
powl.order.add_edge(route, L)
powl.order.add_edge(supplier, L)

powl.order.add_edge(L, Z)
```

At the stated abstraction, these edges directly encode the intended dependencies. Taking transitive ordering into account, the unordered root pairs are exactly:

- `{C,A}`, `{C,D}`, `{C,route}`, `{C,supplier}`, and `{A,P}`: the containment/planning stream is independent of analysis-derived work until a real dependency applies.
- `{P,D}`, `{P,route}`, `{P,supplier}`, `{D,route}`, `{D,supplier}`, and `{route,supplier}`: planning, design, reviews, and consultation have no additional ordering beyond their stated prerequisites and later joins.
- `{route,trial}` and `{supplier,trial}`: approvals and consultation may overlap the trial cycle.

Within `high`, `Q` and `G` are intentionally unordered. `S` and the high-risk submodel are XOR alternatives, not concurrent obligations. All remaining pairs are either transitively ordered or belong to the explicitly defined sequence/loop structure; in particular, the absence of `route  trial` does not weaken `P,D  trial`, and none of the unordered work can bypass the three incoming release dependencies.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | After `R`, `C` and `A` are independent; subsequent obligations follow their own prerequisites. | Parallel `CP` and `AD` chains preserve all interleavings of those four visible activities. | `R` branches to `C` and `A`, with no `C/A` edge and only the specified downstream edges. | No loss for `C/A/P/D` themselves; loss begins when analysis-derived route/supplier work is placed after the tree’s join. | The POWL better represents independent work and potential elapsed-time reduction. |
| Split dependencies into planning/design | `C<P`, `A<D`, and trial waits for both `P` and `D`, not for approvals. | The initial join precedes the trial block. Since `P` and `D` imply completion of their predecessors, trial gating itself is correct. | Direct `CP`, `AD`, `Ptrial`, and `Dtrial` edges. | No additional trial prerequisite in either model. | Neither model permits an unsafe trial lacking a work product. |
| Risk route | After `A`, choose `S` or mandatory unordered `Q,G`. | Correct XOR/high-parallel structure, but route execution waits for `C,P,A,D`. | `Aroute`; high route has no `Q/G` edge. | Tree overconstrains early review behavior. POWL is exact at this abstraction. | Tree-based conformance can falsely reject early reviews; tree-based simulation can overstate review waiting time. |
| Approval/trial overlap | No route-to-trial precedence; release, not trial, synchronizes approvals. | Route and trial are parallel after the initial join, so their overlap is retained, but only from that later point. | `route` and `trial` are unordered and separately precede `L`. | Partial tree overconstraint; no unsafe trial underconstraint. | The tree covers important trial/review overlap but misses cases where reviewing began before planning or design finished. |
| Optional supplier consultation | Skip or one `U`; after `A`; independent of design, planning, approvals, and trial; before `L` if selected. | `XOR(,U)` is correct and can overlap approvals/trial, but is delayed until after the initial join. | `AsupplierL`, with no edges to design, planning, route, or trial. | Tree excludes legitimate early consultation and its overlap with design/planning. | W3 would be falsely nonconforming under the tree; potential supplier lead-time advantages are absent from tree-only simulation. |
| Repeat-until behavior | One or more `TI` cycles; exactly one `J` between failed cycle and next cycle; no `J` after passing exit. | Binary loop gives `T I (J T I)*`. | Same loop, nested as a partial-order node. | Exact visible control-flow abstraction in both. Neither encodes inspection data or a guaranteed number of failures. | Both prevent structurally unsafe adjustment/release sequences; actual failure reasons and probabilities require event data. |
| Release synchronization | `L` waits for passing trial exit, complete selected route, and selected consultation. | The post-join parallel block completes before `L`. | Three explicit incoming edges to `L`. | No release underconstraint; tree safety is conservative. | Both prevent release with missing approvals, incomplete consultation, or an unfinished redo loop. |
| Duplicate-label risk | Trial activities may repeat visibly, but static duplication should not silently create different activity identities. | One visible leaf per activity; loop produces repeated `T/I/J`. | One transition per activity; loop produces repeated occurrences. | No duplication-based approximation is hidden. A different duplicated tree could fragment variants or distort activity frequencies. | Loop-aware counting remains necessary, but repeated trials are not mistaken for extra static model activities. |

For visible traces, the intended relationship is therefore `language(tree)  language(powl)`, with W3 demonstrating strictness.

# 7. Preferred Representation and Validation Plan

**The POWL model should be canonical.** Its partial-order edges express the non-block-structured joins and independent release obligations directly, without delaying reviews or consultation. The process tree remains useful for algorithms that require a tree, but it should be documented as a conservative view and should not be the sole conformance oracle.

1. **Perform structural smoke tests before conversion.**
   - Check every process-tree child’s `parent` pointer and every operator’s expected child count.
   - Check that the POWL root has exactly the listed nodes and edges and that its order is acyclic.
   - Verify transitive requirements such as `R` before every node, `P,D` before `trial`, and every non-`Z` obligation before `L`.
   - Verify the trial-only visible expression `T I (J T I)*`, the two risk alternatives, and the supplier XOR.

2. **Convert to accepting Petri nets where the installed PM4Py version supports it.**
   ```python
   net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)
   pm4py.check_soundness(net_t, im_t, fm_t, print_diagnostics=True)

   net_p, im_p, fm_p = pm4py.convert_to_petri_net(powl)
   pm4py.check_soundness(net_p, im_p, fm_p, print_diagnostics=True)
   ```
   Inspect the converted nets, initial/final markings, silent transitions, and diagnostics. If direct POWL conversion is unsupported, report that limitation and use an available semantics-preserving POWL conversion or direct POWL enumeration; do not silently substitute the approximate tree and claim that it validates the POWL. Soundness would check proper completion and absence of structural deadlocks, not fidelity to the narrative.

3. **Combine bounded reference enumeration with sampled playout.**
   - Enumerate loop unfoldings through three trial cycles and partial-order linearizations for both risk routes and both supplier choices.
   - Check bounded traces against an independently implemented dependency checker based on Section 2, including the regular expression for the `{T,I,J}` projection.
   - Use `pm4py.play_out` on supported models or converted nets, drawing a substantial sample—for example, 10,000 traces per model—while separately ensuring coverage of `QG` and `GQ`, supplier skip/selection, zero/one/two adjustments, early consultation, and reviews before/during/after trial work.
   - Test bounded inclusion of tree behavior in POWL/reference behavior and retain W3 as evidence that equality is not expected.

4. **Run explicit positive and negative tests.**
   - Require the exact verdicts in Section 5, especially POWL acceptance/tree rejection of W3 and rejection of F1 at the trial join.
   - Add negatives for trial before `D`, consultation before `A`, a second consultation, release before a selected `U`, low/high review mixtures, release with only one high-risk review, archiving before release, and a loop redo without a following cycle.
   - Use replay or alignment that correctly handles silent transitions; a visible-event-only checker should independently confirm why each trace is accepted or rejected.

5. **Inspect silent behavior and label duplication specifically.**
   - Confirm that supplier-skip `` never becomes a visible `"tau"`/`None` activity and that skipping consultation does not skip the trial or approval route.
   - Confirm that both supplier alternatives reach the same proper final marking without leaving tokens behind.
   - Count static model nodes, rather than edge references, and verify that there are no duplicate visible activity nodes. Check that repeated `T/I/J` events arise only from loop unfolding.
   - Inspect conversion-introduced silent transitions to ensure they cannot enable `L` before all three release predecessors have completed.

6. **Recognize the limits of these checks.**
   Bounded enumeration and playout cannot prove properties of the unbounded loop or of all interleavings. Conversion success and soundness do not establish semantic fidelity. The independent checker can also share an interpretation mistake. Finally, none of these completion-trace tests can prove actual start-after-complete behavior, physical overlap, risk-data correctness, or the real inspection outcome without richer events and case data.

# 8. Final Self-Critique

1. **The process tree is not proved optimal.** I have not proved that it is a maximal no-duplication under-approximation, nor formally proved that every possible duplication-based exact tree is impossible or unreasonable. It is a defended design choice, not an optimality result.

2. **The semantic abstraction remains weaker than the real scheduling statement.** Ordering completion events does not itself prove that an activity started only after its predecessor completed, and unordered completion events do not prove physical overlap. Risk selection, supplier-selection rationale, and inspection outcomes also remain outside the control-flow model.

3. **The validation plan is not exhaustive evidence.** Unbounded looping, conversion support, silent-transition behavior, and the very large interleaving space require runtime inspection and, ideally, independent review. A sound converted net could still faithfully implement the wrong interpretation, while the tree can remain safe yet reject legitimate cases such as W3.
