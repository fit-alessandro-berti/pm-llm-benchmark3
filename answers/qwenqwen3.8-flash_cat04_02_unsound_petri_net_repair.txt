# 1. Executive Verdict

The net is a workflow net: it has a unique source and sink, and every place/transition lies on some source-to-sink path. It should not be expected to be sound. The principal defect is the waiver synchronization: `t_join_waived` consumes only `p_waived` and does not consume `p_analysis_done`. Consequently `t_authorize` can fire after a waiver before `t_analyze`, and if `t_analyze` does fire, its token remains in `p_analysis_done` with no consuming transition on the waiver path. Business consequence: cases can be authorized without mandatory analysis, or can show a sink token while analysis is incomplete, so exact final marking and proper completion fail.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `sink`, `im`, `fm` | Unique start and unique end; final marking should be exactly one token in `sink`. | Unique source and sink are present. `im = {source:1}`, `fm = {sink:1}`. | A marking containing `sink:1` plus other tokens is not `fm`, even though a token is in the sink. |
| `t_register`, `p_ready` | Start the case and make it ready for parallel branching. | Correct local sequence: `source -> t_register -> p_ready`. | No defect here. |
| `t_split` | AND-split: start analysis and review in parallel. | One token in `p_ready` produces one token in `p_analysis` and one in `p_review`. | If one branch’s completion is not consumed by the selected join, a token can remain stranded. |
| `t_analyze`, `p_analysis`, `p_analysis_done` | Mandatory analysis branch. | `p_analysis` is consumed by `t_analyze`, producing `p_analysis_done`. | On the waiver route, `p_analysis_done` has no consuming transition unless `t_join_normal` is also enabled. |
| `t_standard_review`, `p_review`, `p_review_done` | Standard review alternative. | `p_review` is consumed by `t_standard_review`, producing `p_review_done`. | Works with `t_join_normal`, which requires `p_analysis_done` and `p_review_done`. |
| `t_waive_review`, `p_waived` | Waiver alternative. | `p_review` is consumed by `t_waive_review`, producing `p_waived`. | The waiver token is structurally separated from the normal review completion token. |
| `t_join_normal` | AND-join for analysis plus standard review. | Inputs: `p_analysis_done` and `p_review_done`; output: `p_decision`. | Correct for the standard-review path. |
| `t_join_waived` | Intended AND-join for analysis plus waiver. | Actual inputs: only `p_waived`; output: `p_decision`. It is a unary relay, not a join. | `p_decision` can be produced before analysis is complete. |
| `t_authorize`, `p_decision`, `sink` | Authorize after synchronization and finish. | Consumes `p_decision` and produces `sink`. It does not itself require `p_analysis_done`. | If `p_decision` is produced by the waiver relay, authorization can occur without analysis. |
| Source-to-sink path condition | Every node should be on some source-to-sink path. | True structurally: both `t_join_normal` and `t_join_waived` have paths to `sink`. | The workflow-net check can pass even though some reachable markings cannot reach `fm`. |
| Complete firing behavior | Standard and waiver paths should both reach `fm` with no leftovers. | Standard path can reach `fm`; waiver path cannot reach `fm` without leaving `p_analysis` or `p_analysis_done`. | Soundness failure: proper completion fails, and waiver transitions may be dead in the sense of not participating in any complete trace. |

# 3. Marking-Based Counterexample

A legal firing sequence that exposes the defect is:

```text
t_register, t_split, t_waive_review, t_join_waived, t_authorize, t_analyze
```

This sequence follows the waiver route and lets `t_authorize` fire before `t_analyze`.

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `source:1` | `t_register` | Start from `im`. |
| 1 | `t_register` | `p_ready:1` | `t_split` | Case registered. |
| 2 | `t_split` | `p_analysis:1`, `p_review:1` | `t_analyze`, `t_standard_review`, `t_waive_review` | AND-split creates tokens in both parallel branches. |
| 3 | `t_waive_review` | `p_analysis:1`, `p_waived:1` | `t_analyze`, `t_join_waived` | Waiver selected. `p_review` is consumed, but `p_analysis` remains. |
| 4 | `t_join_waived` | `p_analysis:1`, `p_decision:1` | `t_analyze`, `t_authorize` | `t_join_waived` consumes only `p_waived`; it does not wait for `p_analysis_done`. Therefore `t_authorize` is enabled before `t_analyze`. |
| 5 | `t_authorize` | `p_analysis:1`, `sink:1` | `t_analyze` | A token exists in `sink`, but the exact final marking `fm = {sink:1}` has not been reached because `p_analysis` remains. |
| 6 | `t_analyze` | `p_analysis_done:1`, `sink:1` | none | `t_analyze` consumes `p_analysis`, but produces `p_analysis_done`. On the waiver path, no transition consumes `p_analysis_done`: `t_join_normal` needs `p_review_done`, which is absent, and original `t_join_waived` does not have `p_analysis_done` as input. The marking is not `fm` and is dead. |

The same defect also appears if analysis is performed before authorization:

```text
t_register, t_split, t_waive_review, t_join_waived, t_analyze, t_authorize
```

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `source:1` | `t_register` | Start from `im`. |
| 1 | `t_register` | `p_ready:1` | `t_split` | Registered. |
| 2 | `t_split` | `p_analysis:1`, `p_review:1` | `t_analyze`, `t_standard_review`, `t_waive_review` | Parallel branches created. |
| 3 | `t_waive_review` | `p_analysis:1`, `p_waived:1` | `t_analyze`, `t_join_waived` | Waiver chosen. |
| 4 | `t_join_waived` | `p_analysis:1`, `p_decision:1` | `t_analyze`, `t_authorize` | Waiver relay fires without analysis. |
| 5 | `t_analyze` | `p_analysis_done:1`, `p_decision:1` | `t_authorize` | Analysis completes, but `p_analysis_done` is still not consumed by the waiver synchronization. |
| 6 | `t_authorize` | `p_analysis_done:1`, `sink:1` | none | A sink token exists, but the final marking is not `fm`; `p_analysis_done` is stranded. |

Thus the original net can produce a token in `sink` without reaching the exact final marking. The leftover token cannot be consumed on the waiver path because `t_join_normal` requires `p_review_done`, which is absent when the waiver route is taken, and original `t_join_waived` lacks `p_analysis_done` as an input.

# 4. Minimal-Repair Alternatives

I use the following explicit edit-cost model:

- Add an arc: cost `1`.
- Remove an arc: cost `1`.
- Redirect an existing arc: cost `1`. A redirect is treated as one minimal structural edit because it changes the target/source of an existing synchronization constraint without changing the total number of arcs.
- Add or remove a place: cost `2`.
- Add or remove a transition: cost `3`.

Under a stricter model that counts remove and add separately, the second repair would cost `2` and the first would be the unique global minimum. I state that trade-off explicitly below.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| R1: Make the waiver join a true AND-join | Add arc `p_analysis_done -> t_join_waived`. | `1` arc addition | Analysis remains mandatory. The waiver route now reaches `p_decision` only after both `p_analysis_done` and `p_waived` are present. Standard path is unchanged. Authorization still consumes only `p_decision`. | `t_join_waived` becomes a two-input join. On the waiver path, `t_authorize` cannot be enabled before `t_analyze` has completed. | If future changes make `p_analysis_done` and `p_waived` unable to coexist, `t_join_waived` can become dead. Silent joins still require event-log invariants to verify ordering. |
| R2: Move synchronization to `t_authorize` | Redirect arc `p_analysis_done -> t_join_normal` to `p_analysis_done -> t_authorize`. Equivalently: remove `p_analysis_done -> t_join_normal`, add `p_analysis_done -> t_authorize`. | `1` arc redirection under the chosen model; `2` if remove/add are counted separately. | Analysis remains mandatory for authorization because `t_authorize` now requires `p_analysis_done`. Review choice remains standard vs waiver. No leftover tokens are required for completion. | `t_join_normal` becomes review-only rather than analysis-plus-review. `p_decision` can be produced before analysis. Synchronization is moved from the joins to the authorization transition. | A `p_decision` token may be misread as a completed decision even though analysis is not yet complete. If any downstream logic consumes `p_decision` directly, mandatory analysis could be bypassed. The semantic role of `t_join_normal` is weakened. |

Minimality justification under the chosen cost model:

- No repair can have cost `0`, because the original net is not sound.
- R1 uses exactly one arc addition, which is the smallest possible edit that directly supplies the missing input to the waiver synchronization.
- R2 uses exactly one arc redirection, which is the smallest possible edit that moves the missing analysis constraint to the authorization gate.
- Therefore R1 and R2 tie at cost `1` under the chosen model. They are behaviorally distinct: R1 repairs the waiver join itself; R2 changes where the analysis constraint is enforced.
- If the cost model counts arc removal and arc addition separately, R1 remains cost `1`, while R2 becomes cost `2`. In that stricter model, R1 is the unique global minimum, and R2 is still a valid minimal repair within the family of repairs that synchronize at `t_authorize`.

import pm4py
from pm4py.objects.petri_net.obj import Marking


def _normalize_arc_weights(collection):
    """
    Return a dict place -> weight for transition.pre or transition.post.

    PM4Py may represent pre/post as dict-like or iterable collections.
    """
    if collection is None:
        return {}
    if isinstance(collection, dict):
        return collection

    weights = {}
    for place in collection:
        weights[place] = weights.get(place, 0) + 1
    return weights


def print_marking(label, marking):
    items = sorted(marking.items(), key=lambda kv: kv[0].name)
    print(label, {place.name: count for place, count in items})


def enabled_names(net, marking):
    return sorted(t.name for t in pm4py.get_enabled_transitions(net, marking))


def fire_named_transition(net, marking, transition_name):
    """
    Fire a transition by name, but only if it is enabled.
    Raises instead of silently moving tokens.
    """
    target = next((t for t in net.transitions if t.name == transition_name), None)
    if target is None:
        raise KeyError(f"Transition {transition_name!r} not found")

    enabled = pm4py.get_enabled_transitions(net, marking)
    if target not in enabled:
        raise RuntimeError(
            f"Transition {transition_name!r} is not enabled in marking "
            f"{ {p.name: c for p, c in marking.items()} }"
        )

    pre = _normalize_arc_weights(target.pre)
    post = _normalize_arc_weights(target.post)

    new_marking = Marking(marking)

    for place, weight in pre.items():
        if new_marking.get(place, 0) < weight:
            raise RuntimeError(
                f"Internal inconsistency: {transition_name!r} was reported enabled "
                f"but lacks {weight} tokens in {place.name!r}"
            )
        new_marking[place] = new_marking.get(place, 0) - weight
        if new_marking[place] == 0:
            del new_marking[place]

    for place, weight in post.items():
        new_marking[place] = new_marking.get(place, 0) + weight

    return new_marking

# 7. Repair Trade-Offs and Residual Risks

- Waiver and standard review remain distinguishable in both repairs because `t_standard_review` and `t_waive_review` have distinct visible labels and produce distinct intermediate places, `p_review_done` and `p_waived`. After synchronization, both paths produce `p_decision`, so downstream structure alone may not distinguish the review outcome unless transition names or event-log attributes are preserved.

- Silent transitions can create confusion. In R1, `t_join_waived` is silent and now consumes two tokens. If logs hide silent transitions, the visible trace may show only `t_register`, `t_analyze`, `t_waive_review`, and `t_authorize`, with the join order inferred rather than observed. This is acceptable but requires invariant checking. In R2, silent `t_join_normal` can fire before analysis, producing `p_decision` early. If any monitoring or downstream logic treats `p_decision` as “review and analysis complete,” R2 introduces a dangerous misinterpretation.

- Duplicate behavior is possible in the intended sense of parallelism: analysis and review can fire in either order. That should not be collapsed into a single total order unless the business requires sequencing. However, duplicate visible traces can arise if silent transitions are omitted and different interleavings produce the same visible label sequence.

- Soundness alone does not prove alignment with the business rule. A sound net can still allow an undesired ordering if the ordering constraint is not encoded in the net. For example, soundness does not by itself prove that every `t_authorize` occurrence is preceded by `t_analyze`; that must be checked as an invariant or by replaying event logs.

- Positive regression traces should include:
  - `t_register`, `t_split`, `t_analyze`, `t_standard_review`, `t_join_normal`, `t_authorize`
  - `t_register`, `t_split`, `t_standard_review`, `t_analyze`, `t_join_normal`, `t_authorize`
  - `t_register`, `t_split`, `t_analyze`, `t_waive_review`, `t_join_waived`, `t_authorize`
  - `t_register`, `t_split`, `t_waive_review`, `t_analyze`, `t_join_waived`, `t_authorize`

- Negative regression traces should include:
  - `t_authorize` without `t_analyze`
  - `t_authorize` without either `t_standard_review` or `t_waive_review`
  - both `t_standard_review` and `t_waive_review` in the same case
  - a marking with `sink:1` and any other token
  - a final marking that is not exactly `{sink:1}`

- To detect accidental bypass of mandatory analysis:
  - Check the reachability graph for any marking where `t_authorize` is enabled while `p_analysis_done` is absent.
  - In event logs, enforce the invariant that every trace containing `Authorize Case` must contain `Perform Analysis` before `Authorize Case`.
  - For R1, additionally check that `t_join_waived` is never enabled unless both `p_waived` and `p_analysis_done` are present.
  - For R2, check not only `t_authorize` enabledness but also whether any transition other than `t_authorize` consumes `p_decision`, because `p_decision` may exist before analysis.

# 8. Final Recommendation

Deploy R1. It is the smallest edit under the chosen model, directly repairs the faulty waiver join, and keeps the intended separation of concerns: `t_join_normal` synchronizes analysis with standard review, `t_join_waived` synchronizes analysis with waiver, and `t_authorize` only consumes `p_decision`. It preserves mandatory analysis on the waiver path and leaves the visible review choice intact. The main risk is that silent joins remain unlogged, so monitoring should use transition names or event-log invariants.

Fallback R2. It also preserves mandatory analysis for authorization, but it moves synchronization into `t_authorize`. This may be preferable if the waiver join cannot be changed or if the modeler wants authorize to be the single gate. However, it permits `p_decision` to exist before analysis, which can be misread by downstream logic or reporting as a completed decision. It also weakens the semantic role of `t_join_normal`. Therefore use R2 only if the decision token is never consumed except by `t_authorize` and if the business accepts an intermediate decision state before analysis.
