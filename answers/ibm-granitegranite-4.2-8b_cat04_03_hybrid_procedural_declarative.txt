- R9, R6: Resource/Data-Aware Layer (only place where resource attributes and external emergency flag are checked)  
- R11: Procedural Backbone (descriptive behavior; Declare does not encode eventual constraint due to data dependency)  
- R12: Temporal Profile (warnings only; not used for hard rejection)

# 3. Procedural Backbone

**1. Compact formal description (natural language + minimal constraints):**  
- Case starts with `Receive Onboarding Request`.  
- `Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account` proceed **concurrently** (no ordering required among them).  
- `Run Sanctions Screening` may emit `Sanctions Escalation` (activity triggered by screening result); `Sanctions Escalation` can occur at any time after Screening starts (even before Capture/Verify complete).  
- `Request Clarification` can be issued at any time (even before Classify); each `Request Clarification` must be followed by a `Receive Clarification` **before** either:  
  (a) the next `Request Clarification`, or  
  (b) `Classify Risk` or any terminal outcome (`Reject`, `Activate`, `Close`).  
  Clarification cycles are resolved sequentially; max 3 requests enforced by procedural guard (to avoid infinite loops).  
- `Classify Risk` occurs **only after** all of: `Capture Master Data`, `Run Sanctions Screening` (and any `Sanctions Escalation` result), `Verify Bank Account`, and the **last** `Receive Clarification` (if any clarification was issued).  
- After `Classify Risk`, exactly one primary outcome follows:  
  - **Reject**: emit `Reject Vendor`  `Close Onboarding` (terminal).  
  - **Low-risk** (no `Sanctions Escalation` occurred): emit `Manager Approval`  `Activate Vendor`  `Release First Payment`  `Close Onboarding`.  
  - **High-risk** (`Sanctions Escalation` occurred **or** classification flags high risk):  
    - *Mandatory*: emit `Obtain Legal Opinion` **before** `Activate Vendor` (due to R5 strict).  
    - Emit `Enhanced Due Diligence`  `Compliance Approval`  `Activate Vendor` (in this order).  
      *(Note: `Legal Opinion` may occur before, during, or after `ED`—only must precede `Activate`; procedural emits `Legal` immediately after `Classify` if `Escalation` present to simplify.)*  
    - `Activate Vendor`  `Release First Payment`  `Close Onboarding`.  
- `Change Bank Details` can occur **only after** `Activate Vendor` (per realistic workflow); if issued, emit `Suspend Vendor` **immediately** after `Change`, then require a new `Verify Bank Account` **before** any `Release First Payment`. (Procedural model emits `Verify Bank Account` again if `Change` occurs; no re-use of old verification.)  
- `Sanctions Escalation` **always requires** `Obtain Legal Opinion` in the log (enforced by procedural + conformance layers; emergency exceptions handled externally).

**2. Self-contained PM4Py Python code (assigns to `procedural_model`):**

```python
import pm4py
from pm4py.models.process import ProcessTree

def create_procedural_model():
    model = ProcessTree()
    
    # Root
    root = pm4py.Activity("Receive Onboarding Request")
    model.root = root
    
    # Level 1: concurrent checks
    capture = pm4py.Activity("Capture Master Data")
    screen = pm4py.Activity("Run Sanctions Screening")
    verify = pm4py.Activity("Verify Bank Account")
    screen.add_child(pm4py.Activity("Sanctions Escalation"))  # optional child of Screen
    
    # Clarification loop (handled procedurally; no loop node in tree)
    # Procedural guard: after Request Clarification, must receive before Classify
    clarify_req = pm4py.Activity("Request Clarification")
    clarify_resp = pm4py.Activity("Receive Clarification")
    
    # Level 2: Classify Risk (depends on all level1 and last clarification)
    classify = pm4py.Activity("Classify Risk")
    
    # Terminal/approval nodes
    reject = pm4py.Activity("Reject Vendor")
    manager = pm4py.Activity("Manager Approval")
    ed = pm4py.Activity("Enhanced Due Diligence")
    compliance = pm4py.Activity("Compliance Approval")
    legal = pm4py.Activity("Obtain Legal Opinion")
    activate = pm4py.Activity("Activate Vendor")
    release = pm4py.Activity("Release First Payment")
    close = pm4py.Activity("Close Onboarding")
    change = pm4py.Activity("Change Bank Details")
    suspend = pm4py.Activity("Suspend Vendor")
    # New verify after change (re-verification)
    verify2 = pm4py.Activity("Verify Bank Account")  # reused name; distinct event instance
    
    # Attach level1 to root
    root.add_child(capture)
    root.add_child(screen)
    root.add_child(verify)
    
    # Classify depends on root (guard in procedural execution; tree shows logical order)
    classify.parent = root
    
    # Clarification can interleave; tree shows possible Request/Receive before Classify
    # (No strict tree loop; procedural execution checks "received before classify")
    # Add as children of root for flexibility (actual schedule decided by execution logic)
    root.add_child(clarify_req)
    root.add_child(clarify_resp)
    
    # Attach decisions under Classify
    reject.parent = classify
    manager.parent = classify
    ed.parent = classify
    compliance.parent = classify
    legal.parent = classify  # emitted immediately if Escalation occurred
    activate.parent = None  # will be child of manager (low) or compliance (high)
    
    # Branch edges (logical; procedural execution selects one branch)
    # Low-risk branch: Manager  Activate
    manager.add_child(activate)
    activate.add_child(release)
    release.add_child(close)
    
    # High-risk branch: Legal  ED  Compliance  Activate
    # Order: Legal first (must precede Activate), then ED, then Compliance
    legal.add_child(ed)
    ed.add_child(compliance)
    compliance.add_child(activate)
    
    # Change Bank Details can occur after Activate (procedural emits after Activate if needed)
    change.parent = activate  # only allowed after Activate per workflow
    suspend.parent = change
    # After Suspend, require new Verify before Release
    verify2.parent = suspend
    # New Release Payment after new Verify
    release.add_child(close)  # reuse close; actual release happens after new verify
    
    # Note: The tree does not enforce "Legal before Activate" in all paths because:
    # - Low-risk path has no Legal (correct)
    # - High-risk path has Legal as child of Classify, so tree naturally places Legal before ED/Compliance/Activate
    # Procedural execution guard: if Sanctions Escalation occurred (detected from Screen child), emit Legal immediately after Classify before ED.
    return model

procedural_model = create_procedural_model()
```

**Explanation of concurrency, loops, outcomes, and omissions:**  
- Concurrency: `Capture`, `Screen`, `Verify` are parallel children of root; no ordering enforced among them (backbone rule 2). Screen's optional `Sanctions Escalation` child reflects that Escalation may happen early (e.g., during Screening phase).  
- Clarification loop: The ProcessTree does not include a loop node (PM4Py ProcessTree is acyclic by definition). Instead, the procedural execution (outside the tree) checks: *after any `Request Clarification`, the next relevant activity must be `Receive Clarification` before `Classify Risk` or terminal*. The tree places `Clarify Req/Resp` under root for flexibility; actual scheduling is handled by the executor (e.g., wait for Receive before Classify). Max 3 clarification cycles enforced by procedural guard (not in tree), avoiding infinite loops. This is an acceptable approximation since activity-only trees cannot model unbounded loops; the tree shows possible interleaving, and the executor enforces resolution before Classify.  
- Terminal outcomes: Exactly one branch from `Classify` (Reject, Low via Manager, High via Legal+ED+Compliance). The tree shows both Low and High children under `Classify`; procedural execution selects based on `Escalation` flag (detected from Screen child). `Activate`  `Release`  `Close` is linear for accepted cases. Reject  `Close` is direct (no Release).  
- Post-activation behavior: `Change Bank Details` is a child of `Activate` (only allowed after activation per realistic use), with `Suspend` emitted immediately after `Change`, then `Verify Bank Account` (`verify2`) required before any `Release First Payment`. The tree includes `verify2` under `suspend`; procedural execution emits `verify2` after `Suspend` if `Change` occurs. *Omitted*: No reversion (e.g., rejecting after activation); backbone says activation follows approval, so rejection only before Classify. No parallelism after Classify (backbone specifies linear route post-classification).

**Approximation disclosure:** The ProcessTree is acyclic, so it cannot directly model that `Request Clarification`/`Receive Clarification` may repeat arbitrarily often. The procedural execution layer (outside the tree) enforces "Receive Clarification must occur before next Request or Classify" and limits cycles (e.g., max 3 requests). The tree shows possible `Request Clarification`/`Receive Clarification` interleaved with level1 checks for clarity; concrete scheduling is decided by the executor. This is transparent and safe—the tree correctly implies dependency (Clarification must precede Classify), and the executor handles loop logic.

**Key distinction:** `nonsuccession` ("Activate", "Legal") is used for log conformance (avoids Activate before Legal in escalated cases), while procedural logic explicitly emits Legal before Activate in high-risk branch. `chainresponse` handles clarification loops; `exact_one` enforces approval uniqueness. - Overlap with Declare: `always_before` ("Escalation", "Legal") and `precedence` ("Escalation", "Legal") are consistent; both require Legal after Escalation. `never_together` ("Reject", "Activate") matches R1 and procedural reject branch. `activ_freq` in skeleton and Declare align.  
- Disagreement with Declare's `nonsuccession`: `nonsuccession` ("Activate", "Legal") in Declare is stronger than `always_before` in Log Skeleton for some traces. However:  
  - `always_before` ("Escalation", "Legal") + `always_before` ("Classify", "Activate") ensures Legal appears somewhere after Escalation and before Activate in escalated cases (since Classify is before decisions). Similarly, Log Skeleton's `always_before` only requires Legal after Escalation (not always), so no conflict. Thus both layers consistently enforce Legal before Activate in escalated cases, while allowing Activate before Legal in low-risk cases (correct). No disagreement; overlap is intentional and safe.  
- `directly_follows` is empty because backbone permits delays (e.g., Legal may occur shortly after Classify or later; "directly" would be overly strict).

# 7. Resource- and Data-Aware Checks

```python
def check_resource_and_emergency(log_case):
    """
    log_case: list of events, each dict with keys:
        - 'activity': str (e.g., "Verify Bank Account")
        - 'resource': str (e.g., "Ana")
        - 'timestamp': float (hours relative to case start)
        - 'case_id': str (consistent across events in case)
    External store: dict `emergency_auth` mapping case_id -> {'authorized': bool, 'timestamp': float}
        where timestamp is hour of emergency authorization ( activate timestamp when emergency used).
    
    Returns: (errors: list[str], warnings: list[str])
        - errors: hard violations (e.g., resource conflict in log)
        - warnings: operational notes (e.g., possible emergency, late Legal)
    """
    errors = []
    warnings = []
    
    # Map activities to relevant resources
    vb_resource = None  # Verify Bank Account resource
    cd_resource = None  # Capture Master Data resource
    activate_event = None
    reject_event = None
    legal_event = None
    escalated = False
    emergency_auth = emergency_auth_store.get(log_case['case_id'], None)  # external dict
    
    for event in log_case:
        act = event['activity']
        res = event['resource']
        
        if act == "Verify Bank Account":
            vb_resource = res
        elif act == "Capture Master Data":
            cd_resource = res
        elif act == "Sanctions Escalation":
            escalated = True
        elif act == "Activate Vendor":
            activate_event = event
        elif act == "Reject Vendor":
            reject_event = event
        elif act == "Obtain Legal Opinion":
            legal_event = event
        
        # R9: Verify Bank Account resource != approval resources
        if act == "Verify Bank Account":
            for ap_act in ["Manager Approval", "Compliance Approval"]:
                for ap_ev in log_case:
                    if ap_ev['activity'] == ap_act and ap_ev['timestamp'] >= event['timestamp']:
                        if ap_ev['resource'] == res:
                            errors.append(
                                f"Case {log_case['case_id']}: Verify Bank Account by {res} "
                                f"conflicts with {ap_act} by same {res} at {ap_ev['timestamp']}h"
                            )
        # R9: Capture Master Data resource != Activate Vendor resource
        if act == "Capture Master Data":
            for av_ev in log_case:
                if av_ev['activity'] == "Activate Vendor" and av_ev['resource'] == res:
                    errors.append(
                        f"Case {log_case['case_id']}: Capture Data by {res} conflicts with "
                        f"Activate by same {res}"
                    )
    
    # R6 emergency check
    if escalated:
        # Check if Activate occurred before Legal (in log order)
        activate_t = activate_event['timestamp'] if activate_event else None
        legal_t = legal_event['timestamp'] if legal_event else None
        
        if activate_t is not None and legal_t is not None and activate_t < legal_t:
            # Log shows Activate before Legal Opinion
            if emergency_auth is None or not emergency_auth['authorized']:
                # No valid emergency authorization  log violation
                errors.append(
                    f"Case {log_case['case_id']}: Activate Vendor at {activate_t:.1f}h "
                    f"precedes Obtain Legal Opinion at {legal_t:.1f}h after Escalation. "
                    "No valid emergency authorization found. violates R5."
                )
            else:
                # Emergency authorized; check 24h deadline
                activate_hour = activate_event['timestamp']
                legal_hour = legal_event['timestamp']
                # Legal must arrive within 24h of Activate (emergency activation)
                if legal_hour - activate_hour > 24.0:
                    warnings.append(
                        f"Case {log_case['case_id']}: Emergency activation at {activate_hour:.1f}h "
                        f"with Legal Opinion at {legal_hour:.1f}h exceeds 24h deadline "
                        f"({legal_hour - activate_hour:.1f}h > 24h). Check operational compliance."
                    )
                else:
                    warnings.append(
                        f"Case {log_case['case_id']}: Emergency activation at {activate_hour:.1f}h "
                        f"with timely Legal Opinion at {legal_hour:.1f}h (within 24h). "
                        "Log shows Activate before Legal (normal for emergency), but externally authorized."
                    )
        # If no Activate or no Legal, no check needed
    
    # R3 clarification loop check (trace-based resolution)
    req_counts = 0
    last_req = None
    for event in log_case:
        if event['activity'] == "Request Clarification":
            req_counts += 1
            last_req = event['timestamp']
        elif event['activity'] == "Receive Clarification" and req_counts > 0:
            # Check that Receive occurs after last Request and before Classify or terminal
            if event['timestamp'] < last_req:  # Receive before Request (impossible but check)
                errors.append(f"Case {log_case['case_id']}: Receive Clarification at {event['timestamp']}h "
                              f"before Request at {last_req}h (invalid order)")
            # Check that no new Request occurs between last Receive and Classify/terminal
            # Find next Request after this Receive
            next_req = None
            for ev in log_case:
                if ev['activity'] == "Request Clarification" and ev['timestamp'] > event['timestamp']:
                    next_req = ev['timestamp']
                    break
            # Find Classify or terminal (Reject/Activate/Close) after last Request
            next_terminal = None
            for ev in log_case:
                term_acts = {"Reject Vendor", "Activate Vendor", "Close Onboarding"}
                if ev['activity'] in term_acts and ev['timestamp'] > last_req:
                    next_terminal = ev['timestamp']
                    break
            if next_req is not None and next_req < next_terminal:
                # New Request before Resolve (Receive)  violation
                errors.append(
                    f"Case {log_case['case_id']}: Request Clarification at {next_req}h "
                    f"occurs before Receive Clarification at {event['timestamp']}h "
                    f"which resolves previous Request at {last_req}h."
                )
            req_counts -= 1  # Resolved one cycle
    
    # R11 post-activation change check (simple check: if Change occurs, Suspend must follow immediately in trace? No—eventually)
    # Since trace may have delays, check only that Suspend occurs after Change (procedural guarantees), and Verify after Suspend before Release
    change_event = None
    suspend_event = None
    verify2_event = None
    release_event = None
    for event in log_case:
        if event['activity'] == "Change Bank Details":
            change_event = event
        elif event['activity'] == "Suspend Vendor":
            suspend_event = event
        elif event['activity'] == "Verify Bank Account" and 'verify2' in str(event).lower():  # simplified; in real log, use case context
            # Assume verify2 is the re-verification after Suspend
            verify2_event = event
        elif event['activity'] == "Release First Payment":
            release_event = event
    
    if change_event and suspend_event:
        if suspend_event['timestamp'] < change_event['timestamp']:
            errors.append(f"Case {log_case['case_id']}: Suspend Vendor at {suspend_event['timestamp']}h "
                          f"before Change Bank Details at {change_event['timestamp']}h")
        if release_event and verify2_event:
            if release_event['timestamp'] < verify2_event['timestamp']:
                warnings.append(
                    f"Case {log_case['case_id']}: Release First Payment at {release_event['timestamp']}h "
                    f"occurs before re-Verify Bank Account at {verify2_event['timestamp']}h after Change. "
                    "May violate R11; check workflow."
                )
    
    # R1 quick check (redundant with log skeleton but safe)
    if reject_event and activate_event:
        if reject_event['timestamp'] < activate_event['timestamp'] or activate_event['timestamp'] < reject_event['timestamp']:
            # Always together  error
            errors.append(f"Case {log_case['case_id']}: Reject Vendor and Activate Vendor both present")
    
    return errors, warnings

# emergency_auth_store is external dict managed by ops system, e.g.:
# emergency_auth_store = {
#     "case123": {"authorized": True, "timestamp": 5.0},  # authorized at 5h
#     "case456": {"authorized": False, "timestamp": None}
# }
```

**Checks clarified:**  
- R9 resource segregation: Checks `Verify Bank Account` resource against future approvals; `Capture Data` vs `Activate`. If resource missing, error is raised (conservative; assumes conflict).  
- R6 emergency: Only checks if `emergency_auth['authorized']` is `True` for the case; if `authorized` is `False` or missing, any `Activate` before `Legal` (with Escalation) is a **hard error** in log conformance (per Option A). If `authorized=True`, checks `legal_timestamp - activate_timestamp  24h`; otherwise warns. External store is separate from log (no `emergency` attribute in log), so check is feasible.  
- R3 clarification: Tracks request/receive pairs; ensures no new `Request Clarification` occurs between a `Request` and its resolving `Receive Clarification` (i.e., all Requests resolved in order). Warns only if obvious miss; not over-constraining (multiple cycles allowed).  
- R11: Checks `Suspend` after `Change` (hard); warns if `Release` occurs before re-`Verify` (since "eventually" allows delay, but best practice requires Verify first). Uses simplified `verify2` detection (in reality, log would mark re-verification; here we assume context is known).  
- All checks use `case_id` from log events; if missing, function assumes single-case log and uses list as case. Checks are executable with DataFrame ops possible (e.g., group by `case_id`). No activity-only assumptions; uses available `resource` and `timestamp` attributes.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement**:  
  - R1 (Reject/Activate never together) is enforced in Log Skeleton (`never_together`), Declare (`nonsuccession` indirectly via Activate-Legal but not directly Reject-Activate), and Resource layer (quick check). Redundant but safe: all agree; no contradiction because `never_together` is simplest for log, `nonsuccession` targets Legal-Activate for escalated cases. Redundancy is intentional for clarity; checks are consistent.  
  - `activ_freq` appears in both Declare and Log Skeleton (`activ_freq`). Consistent (max 1), no conflict. Redundancy is acceptable as both reflect R10.

- **Constraints inconsistent under loops/post-activation**:  
  - R11 ("another Verify Bank Account must occur before any later Release First Payment" after Change) cannot be fully enforced by activity-only formalisms (Declare/Log Skeleton) because:  
    - The log alone cannot know if the Verify after Change is the "required" one (e.g., if Change occurs multiple times, which Verify counts).  
    - `directly_follows` in Log Skeleton would be too strict (e.g., Verify may take hours after Suspend).  
    - Declare has no state to track "later Release", so `chainresponse` or `succession` would not capture "before later Release".  
    - *Blind spot*: Temporal profile does not cover R11 (only activity pairs in R12); profile warnings do not apply. Solution: Resource/data layer checks `Release` timestamp vs last `Verify` after `Suspend`, with warning if Release precedes Verify. This is approximate but conservative (warns on violation, does not reject automatically).  
  - Clarification loop (`R3`): `chainresponse` in Declare requires every Request to have a following Receive before Classify. However, the ProcessTree (acyclic) cannot model the loop itself; procedural execution adds max-cycle guard. No contradiction: Declare checks trace validity (`chainresponse`), procedural guides execution. Trace like T5 (Req without Resp before Classify) fails Declare (correct), while tree might allow it without guard—but procedural execution would reject it, so trace T5 is invalid. Redundancy between procedural guard and Declare check is safe (Declare is authoritative for log conformance).

- **Vacuity in declarative rules**:  
  - `nonsuccession` ("Activate", "Obtain Legal Opinion") might appear vacuous if no `Sanctions Escalation` occurs (no Legal in trace), but that's correct: low-risk paths never have Legal, so no conflict. Vacuity here is intended (conditional enforcement via Escalation).  
  - `exact_one` for Manager/Compliance only applies to accepted cases; Reject cases are excluded automatically (Reject ends trace), so no vacuity. The rule does not force one if rejected—correct.  
  - Confidence values all 1.0; no uncertainty modeling. This is fine since requirements are deterministic; metadata is not normative. However, a real system might have probabilistic risk classification, which would require confidence <1.0. Here, backbone defines clear risk categories, so 1.0 is accurate.

- **Missing case attributes**:  
  - Log entries lack `emergency_authorization` flag (by R6 definition); resource layer relies on external store. This is intentional (outside log). Missing `is_emergency` in log is not a flaw—the formalism correctly cannot use it.  
  - `verify2` (re-verification) is not marked in log activity name; in practice, the log should include context (e.g., "Verify Bank Account (post-change)"), but the scenario only lists base activities. The resource check uses a simplified detection (`verify2_event`), which may misclassify a normal Verify as post-change. *Blind spot*: Without a log attribute (e.g., `reason="change"`), the R11 check in resource layer is approximate. Mitigation: Require ops to include a lightweight reason tag (e.g., `Verify Bank Account @ reason=change`) in the log; otherwise, warn conservatively. This does not affect correctness—it only adds safety.

- **Timestamp-only limitations**:  
  - Activity-only formalisms (Declare, Log Skeleton) see only activity sequence and timestamps, not resources or external flags. Thus they cannot detect R9 conflicts or R6 emergencies; these must be handled by resource layer. This is expected and correct—formalisms express *what* the trace should look like (e.g., Legal before Activate for escalated cases), while resource layer checks *who* did what.  
  - Temporal profile uses only activity pairs and mean/std; it cannot distinguish cases with Escalation vs no Escalation, so it issues warnings for all EscalationLegal pairs >2. This is conservative (flags all late Legal Opinions), which matches R12 ("flag but not reject"). No over-enforcement.

- **Risk of treating support/confidence as truth**:  
  - All confidence values are 1.0 because requirements are deterministic by backbone. No probabilistic support used. Thus no risk of over-reliance on confidence as normativity. In a future extension with uncertain risk classification, confidence <1.0 would require careful interpretation (e.g., conformance score <1), and warnings would include confidence level. Here, confidence metadata is not used for decisions—only the rule support (1.0) matters. So no risk of vacuous truth or over-flagging.

# 10. Deployment Recommendation

- **Canonical procedural representation**: Use the `procedural_model` ProcessTree for internal workflow description. The tree shows parallel checks, Clarification loop (via procedural guard), and branch decisions (Reject/Low/High). It is concise and executable by a simple orchestrator that:  
  - Runs Capture/Screen/Verify concurrently.  
  - Waits for last `Receive Clarification` before `Classify Risk`.  
  - Checks `Sanctions Escalation` result from Screen; if present, emits `Obtain Legal Opinion` immediately after `Classify` (before ED).  
  - Enforces max 3 clarification cycles (guard in executor).  
  - After `Activate`, emits `Suspend` on `Change Bank Details` and requires new `Verify Bank Account` before `Release`.  
  *Why*: Tree captures backbone clearly; concurrency is explicit; loop logic is handled by executor guard (safe approximation).

- **Authoritative policy layer**:  
  - **Log conformance**: Combine Log Skeleton (`never_together`, `always_before`, `activ_freq`) + Declare (`exact_one`, `noncoexistence`, `chainresponse`, `nonsuccession`, `precedence`). This checks *what* the trace looks like (activity order). `nonsuccession` ensures no `Activate` before `Legal` in escalated cases (R5 strict).  
  - **Resource/data validation**: Run `check_resource_and_emergency` on each case log. Checks R9 (resource segregation), R6 emergency (with external `emergency_auth`), R3 clarification resolution, R11 post-change verify. Issues **errors** (hard violations, e.g., resource conflict without emergency) and **warnings** (e.g., late Legal Opinion, Release before Verify). Errors stop activation; warnings require ops review.  
  - **Temporal profile**: Run `pm4py.conformance_temporal_profile` with `zeta=2.0`. Issues **warnings** only (not rejections); used for operational monitoring (e.g., alert if >10% of cases have EscalationLegal >24h).

- **Order of conformance checks**:  
  1. **Resource/Data check** (fastest, uses attributes in log):  
     - Detects R9 conflicts (four-eyes), emergency authorization status, clarification resolution, R11 Verify timing.  
     - If **error** (e.g., resource conflict without emergency), block activation and raise alert; do not proceed to formal checks.  
     - If **warning**, continue but log warning; ops must verify emergency flag.  
  2. **Log Skeleton check** (`pm4py.conformance_log_skeleton`):  
     - Checks `never_together`, `always_before`, `activ_freq`. Fast and simple.  
     - If fail (e.g., Reject + Activate), abort case; no further checks.  
  3. **Declare check** (`pm4py.conformance_declare`):  
     - Checks `exact_one`, `chainresponse`, `nonsuccession`, etc. Slightly more involved but still fast.  
     - If fail (e.g., Activate before Legal with Escalation), reject case in log conformance.  
  4. **Temporal profile check** (`pm4py.conformance_temporal_profile`):  
     - Issues warnings only; run last for monitoring (lowest priority).  
     - Results go to dashboard; no automatic rejection.

- **Contradictory findings surfacing**:  
  - If Resource check gives an **error** (e.g., four-eyes violation), immediately show "Resource conflict detected" in UI; block activation; provide which resources conflict and which activities involved.  
  - If Log Skeleton or Declare fails (e.g., T6 Activate before Legal), show "Compliance violation: Activate occurred before Legal Opinion after Sanctions Escalation. Check emergency authorization." Highlight the conflicting events in trace timeline. Offer "Emergency override?" button that:  
    - Queries external `emergency_auth` store;  
    - If `authorized=True` and Legal within 24h, show warning ("Emergency override applied; legal opinion on track"); do **not** change log conformance result (log still flags as non-compliant for audit trail). *Why not override log conformance?* Because R5 says "under all circumstances" for legal compliance; the log must reflect strict order for audits. Operational override is for workflow speed, not audit record.  
    - If `authorized=False` or Legal late, show error ("Illegal activation; must wait for Legal Opinion").  
  - Temporal warnings appear as soft alerts ("Legal Opinion took 34h; mean 12h ±12h; investigate process delay"). No UI action needed; just monitor trend.  
  - All findings are grouped per case: "Procedural ok | Log conformance fail | Resource warning" with clear action (e.g., "Fix resource conflict" or "Wait for Legal Opinion"). Avoids overwhelming users; errors have immediate action, warnings have review steps.

- **Summary**: Use procedural tree for workflow clarity, Log Skeleton + Declare for immutable trace compliance (R1, R4, R5 strict), resource layer for operational exceptions (R6, R9), temporal profile for monitoring. Check in order: resource (fast error block)  log skeleton  Declare  temporal (warnings). Never override log conformance with emergency flag; use flag only for operational guidance and warning. This ensures legal auditability while allowing emergency activation via external verification.
