# 1. Delay-decomposition definitions

## Core Definitions

For case $c$ and branch $i \in \{A, B, C\}$:

| Component | Formula | Interpretation |
|-----------|---------|----------------|
| `upstream_elapsed_c` | `fork_release_c - arrival_c` | Time from process entry until branches may begin |
| `branch_queue_{c,i}` | `start_{c,i} - fork_release_c` | Queue waiting before branch service begins |
| `branch_service_{c,i}` | `end_{c,i} - start_{c,i}` | Active processing time for branch |
| `branch_completion_{c,i}` | `end_{c,i}` | When branch finishes work |
| `join_ready_c` | `max(A_end_c, B_end_c, C_end_c)` | Latest branch completion (when all ready to join) |
| `sync_wait_{c,i}` | `join_ready_c - end_{c,i}` | Synchronization wait after branch completes |
| `downstream_queue_c` | `final_start_c - join_ready_c` | Wait at final station before F begins |
| `final_service_c` | `final_end_c - final_start_c` | Processing time at final station |
| `total_flow_c` | `final_end_c - arrival_c` | End-to-end case duration |

## Critical Branch Identification

```
critical_branch_c = argmax_{i{A,B,C}} (end_{c,i})
```

Tie-breaking rule: alphabetical order (A < B < C) for deterministic results.

## Why Summing Sync Waits Double-Counts

The synchronization wait measures *idle time after completion*. If we sum across branches:

$$\sum_i \text{sync\_wait}_{c,i} = \sum_i (\text{join\_ready}_c - \text{end}_{c,i}) = 3 \cdot \text{join\_ready}_c - \sum_i \text{end}_{c,i}$$

This counts the gap between the first-completing branch and the last-completing branch **multiple times**. Specifically, if branches finish at times $t_1 < t_2 < t_3$, then:

- Branch 1 waits: $(t_3 - t_1)$
- Branch 2 waits: $(t_3 - t_2)$  
- Branch 3 waits: $0$
- Sum: $2t_3 - t_1 - t_2$

But the actual elapsed synchronization time is only $(t_3 - t_1)$ — the span from first to last completion. The intermediate branch's wait is already embedded in the first branch's wait. Therefore, sync waits must be treated as **per-branch metrics**, not aggregated into total case time.

## Complete Flow-Time Decomposition (No Double-Counting)

$$\begin{aligned}
\text{total\_flow}_c &= \underbrace{\text{upstream\_elapsed}_c}_{\text{before fork}} \\
&+ \underbrace{\max_i(\text{queue}_{c,i} + \text{service}_{c,i})}_{\text{parallel stage: longest path}} \\
&+ \underbrace{\text{downstream\_queue}_c}_{\text{final station wait}} \\
&+ \underbrace{\text{final\_service}_c}_{\text{final processing}}
\end{aligned}$$

Note: $\max_i(\text{queue}_{c,i} + \text{service}_{c,i}) = \text{join\_ready}_c - \text{fork\_release}_c$. This captures the effective parallel stage duration without counting sync waits.

# 5. Recommended redesigns and risks

## Recommendation 1: Implement B Branch Priority Queuing

**Description**: Assign higher priority to B tasks in their queue, potentially dedicating a portion of B resource capacity exclusively to incoming cases.

**Expected Benefits**:
- **Throughput**: Reduce B queue delays by 40-60%, cutting 8/12 cases' flow time
- **Flow-time tail**: Eliminate worst-case B completions (F07, F06, F12)
- **Resource utilization**: May increase B resource utilization during peak periods
- **Synchronization**: Reduce sync wait for A and C branches

**Risks**:
- **New bottleneck**: A may become critical more frequently once B accelerates
- **Starvation risk**: Lower-priority B tasks could accumulate if demand spikes
- **Measurement needed**: Track B queue length distribution pre/post intervention

**Pilot Plan**:
1. Measure current B queue arrivals and departures over 2 weeks
2. Implement priority queuing for 50% of B capacity
3. Monitor F02, F03, F05, F06, F07, F09, F10, F12 (current B-critical cases)
4. Track if A becomes critical in 3 additional cases

## Recommendation 2: Decouple Final Station from Join-Ready Constraint

**Description**: Allow final station to begin preliminary work (e.g., document review, resource allocation) before all branches complete, using staged decision-making.

**Expected Benefits**:
- **Throughput**: Eliminate downstream queue entirely for many cases
- **Flow-time tail**: Reduce worst-case flows (F07, F03, F06, F12)
- **Resource utilization**: Better spread F1/F2 workload
- **Synchronization**: Convert sync wait into productive work

**Risks**:
- **Quality risk**: Partial decisions may require rework if branch outcomes change
- **Complexity**: Requires workflow changes and staff training
- **Masking effect**: Upstream branch delays may worsen if perceived as less critical
- **Measurement needed**: Track rework rates and decision accuracy

**Pilot Plan**:
1. Identify which final-station activities can safely start early
2. Implement partial-start protocol for 20% of cases
3. Measure downstream queue reduction vs. rework incidence
4. Scale if rework rate < 5%

# 7. Limits of inference

## What Cannot Be Identified from These Timestamps

### 1. Causality Between Events
While we observe temporal ordering, we cannot determine:
- Whether B queue delays are caused by resource contention or policy decisions
- Whether final-station waiting reflects true queueing or release coordination policies
- Whether upstream preparation step timing influenced fork_release scheduling

### 2. Branch Resource Capacity
We observe:
- A never queues (suggests dedicated or always-available resource)
- B queues significantly (suggests shared or constrained resource)
- C queues moderately (suggests variable administrative availability)

But we cannot identify:
- Number of physical resources per branch
- Resource shift patterns or breaks
- Whether queueing reflects batch processing policies

### 3. Work Preemption
Timestamps show start/end times but not:
- Whether any branch work was interrupted and resumed
- Whether partial progress was lost or preserved
- Whether apparent service times include rework cycles

### 4. Final-Station Waiting Nature
We measure `final_start - join_ready` as "downstream queue," but this conflates:
- True queueing (waiting for available F1/F2)
- Release policies (deliberate delay before final processing)
- Setup or handover time not captured in timestamps
- Quality checks occurring between join and final start

### 5. Unobserved Variability Sources
We cannot distinguish:
- Demand variability vs. resource variability causing B queues
- External dependencies affecting branch execution
- Case complexity differences beyond what timestamps capture

### 6. Synchronization Policy Details
We infer join_ready from max completion, but cannot determine:
- Whether synchronization is automatic or requires manual confirmation
- Whether partial joins are permitted (some branches waiting for others)
- Whether timeout mechanisms exist for straggler branches

## Implications for Recommendations

Given these limits:
1. **Prioritize measurement**: Before implementing redesigns, instrument processes to capture resource counts, queue discipline, and handover protocols
2. **Validate assumptions**: Test whether B queue reduction actually improves flow time by running controlled pilots
3. **Monitor secondary effects**: Watch for A becoming critical once B improves, and for quality impacts of decoupling final station
4. **Accept uncertainty**: Present recommendations as hypotheses requiring validation rather than certain solutions
