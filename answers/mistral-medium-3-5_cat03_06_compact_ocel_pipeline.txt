## 4. Expected flattened behavior

### Order
- **Trace shape**: `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Record Payment  Record Payment  Confirm Delivery  Close Order`
  - **Copied shared events**: `Reserve Stock` (E6) and `Pack Package` (E7) appear in **both** O100 and O200 traces because they relate to both Orders.
  - **Omitted lifecycle aspects**: The fact that P1 combines items from both Orders is lost; each Order's trace treats packing as independent.
  - **Likely DFG edges**:
    - `Create Order  Add Item` (strong)
    - `Add Item  Reserve Stock` (strong)
    - `Reserve Stock  Pack Package` (strong)
    - `Pack Package  Dispatch Package` (strong)
    - `Dispatch Package  Confirm Delivery` (strong)
    - `Issue Invoice  Record Payment` (strong)
  - **Misleading interpretations**:
    - The flattened view suggests O100 and O200 have identical packing steps, hiding that P1 is shared.
    - Payments (M1, M2) appear in both Order traces, implying direct payment-to-Order links, though they are actually tied to V1.

### Package
- **Trace shape**: `Pack Package  Dispatch Package  Confirm Delivery`
  - **Copied shared events**: None (each Package is unique to its trace).
  - **Omitted lifecycle aspects**: The **origin Orders** (O100 for P2, O100+O200 for P1) and **Items** are lost.
  - **Likely DFG edges**:
    - `Pack Package  Dispatch Package` (strong)
    - `Dispatch Package  Confirm Delivery` (strong)
  - **Misleading interpretations**:
    - P1's trace cannot show that it combines items from two Orders, so the cross-order dependency is invisible.

### Delivery
- **Trace shape**: `Dispatch Package  Confirm Delivery`
  - **Copied shared events**: None.
  - **Omitted lifecycle aspects**: The **Packages** (P1, P2) and their **Items/Orders** are lost.
  - **Likely DFG edges**:
    - `Dispatch Package  Confirm Delivery` (strong)
  - **Misleading interpretations**:
    - Deliveries appear as isolated logistics steps with no link to Orders or Items.

### Invoice
- **Trace shape**: `Issue Invoice  Record Payment  Record Payment`
  - **Copied shared events**: `Record Payment` (E12, E15) appears once per Payment, but the trace cannot show that both Payments settle the same Invoice.
  - **Omitted lifecycle aspects**: The **Orders** (O100, O200) billed by V1 are lost.
  - **Likely DFG edges**:
    - `Issue Invoice  Record Payment` (strong)
  - **Misleading interpretations**:
    - The trace suggests Payments are sequential, but they are **partial settlements** of the same Invoice. The flattened view cannot represent partial vs. full settlement.

### Why Payment Flattening is Weak
- **Trace shape**: `Record Payment` (single event per Payment).
  - **Problem**: Each Payment (M1, M2) has **only one event**, so the flattened log for `Payment` would consist of two traces, each with a single `Record Payment` event. This provides **no process structure** (no edges in DFG) and **no temporal context** (e.g., when payments occur relative to Orders or Invoices).
  - **Omitted**: The **Invoice** (V1) and its **Orders** are lost, so the payment's purpose is invisible.
  - **Misleading**: The flattened view cannot distinguish between partial and full payments or relate them to the billed Orders.

## 6. Modeling alternatives

### 1. Source-Minimal Relations
- **Policy**: Only include E2O relations for **directly observed** object involvement. For example:
  - `Reserve Stock` (E6) only relates to I1 and I3 (not O100/O200).
  - `Pack Package` (E7) only relates to P1, I1, I3 (not O100/O200).
- **Impact on Discovery**:
  - **OC-DFG**: Loses edges between Orders and shared events (E6, E7), so O100 and O200 appear **independent** in packing.
  - **OTG**: No `Order  Package` transitions; P1 is only linked to Items.
  - **Petri Net**: No synchronization between Orders in P1; P1 is only a consumer of Items.
- **Trade-off**: More **faithful to raw data** but **hides cross-order dependencies**.

### 2. Full Operational Involvement
- **Policy**: Include **all possible** E2O relations that can be inferred from O2O and event context. For example:
  - `Pack Package` (E7) relates to P1, I1, I3, O100, O200 (since O100 contains I1 and O200 contains I3).
  - `Dispatch Package` (E9) relates to P1, D1, I1, I3, O100, O200.
- **Impact on Discovery**:
  - **OC-DFG**: Overly dense; every logistics event relates to **all upstream Orders/Items**.
  - **OTG**: Spurious transitions (e.g., `Delivery  Order`) appear due to propagated relations.
  - **Petri Net**: Over-synchronized; P1 would require tokens from **all Orders**, which is not true (P1 only needs I1 and I3).
- **Trade-off**: **Rich connectivity** but **inflates relations** beyond source observations.

### 3. O2O-Propagated Analytical Relations
- **Policy**: Use O2O relations to **dynamically propagate** E2O relations during analysis (not in the raw data). For example:
  - If `P1 packs I1` and `O100 contains I1`, then **analytically** `P1` is related to `O100`.
- **Impact on Discovery**:
  - **OC-DFG**: Same as "Full Operational Involvement" but **computed at query time**.
  - **OTG**: Same as above.
  - **Petri Net**: Same as above.
- **Trade-off**: **Flexible** (can toggle propagation) but **blurs the line** between observed and inferred relations. Risks **false dependencies** if O2O relations are not carefully designed.

## 7. Failure modes

1. **Relation Inflation**
   - **Cause**: Adding E2O relations for every possible inferred link (e.g., `Dispatch Package` relates to all Orders).
   - **Effect**: OC-DFG becomes a **complete graph**, hiding true dependencies. OTG shows **spurious transitions**.

2. **Missing Direct E2O Links**
   - **Cause**: Omitting relations for shared events (e.g., `Reserve Stock` not linked to O100/O200).
   - **Effect**: Cross-order dependencies (e.g., P1 combining I1 and I3) are **invisible** in OC-DFG and Petri Net.

3. **Treating O2O Propagation as Observation**
   - **Cause**: Using O2O relations to **automatically add E2O relations** in the raw data.
   - **Effect**: **False synchronization** in Petri Net (e.g., P1 requiring O100 and O200 tokens simultaneously).

4. **Duplicate Shared Events After Flattening**
   - **Cause**: Flattening on `Order` copies shared events (e.g., `Reserve Stock`) into multiple traces.
   - **Effect**: **Artificial concurrency** in DFG (e.g., `Reserve Stock` appears to happen in parallel for O100 and O200).

5. **Ambiguous Payment Allocation**
   - **Cause**: Payments (M1, M2) are only linked to V1, not to Orders.
   - **Effect**: Flattened `Order` traces **incorrectly include** both Payments, suggesting direct payment-to-Order links.

6. **Overly Short Payment Traces**
   - **Cause**: Each Payment has only one event (`Record Payment`).
   - **Effect**: Flattened `Payment` log has **no process structure** (no edges in DFG).

7. **Constructor/API Version Mismatch**
   - **Cause**: Using `OCEL` constructor with column names that don’t match the expected schema (e.g., `eid` vs. `ocel:eid`).
   - **Effect**: **Silent failures** or errors in discovery algorithms.

8. **False Total Order for Same-Time Events**
   - **Cause**: Assuming events with the same timestamp have a **deterministic order** (not an issue here, but a general risk).
   - **Effect**: **Incorrect DFG edges** or **race conditions** in Petri Net.

A reviewer should verify the following in the generated tables:

1. **Event-Object Consistency**:
   - Every `ocel:eid` in `relations` exists in `events`.
   - Every `ocel:oid` in `relations` exists in `objects`.

2. **Shared Event Relations**:
   - Event 6 (`Reserve Stock`) has relations to **both I1 and I3** (Items) and **both O100 and O200** (Orders).
   - Event 7 (`Pack Package`) has relations to **P1, I1, I3, O100, O200**.

3. **O2O Completeness**:
   - `P1 packs I1` and `P1 packs I3` exist in `o2o`.
   - `V1 bills O100` and `V1 bills O200` exist in `o2o`.

4. **Payment-Invoice Links**:
   - `M1 partially_settles V1` and `M2 partially_settles V1` exist in `o2o`.

6. **Timestamp-Activity Alignment**:
