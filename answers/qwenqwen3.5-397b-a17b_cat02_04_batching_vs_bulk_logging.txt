```python
        if '15 min' in row['precision']: return 'G7_Coarsening'
        return 'G1_Simultaneous'
    if row['start_unique'] == 1 and row['complete_unique'] > 1:
        return 'G2_Start_Batch'
    if row['start_unique'] > 1 and row['complete_unique'] == 1:
        return 'G3_End_Batch'
    if row['overlap_count'] > 0:
        return 'G5_Shared_Overlap'
    if row['complete_unique'] == 1 and row['initial_wait_sec'] > 3600:
        return 'G6_Bulk_Submission'
    if row['start_unique'] == row['count']: # All starts unique
        return 'Sequential'
    return 'Unknown'

diagnostics['inferred_type'] = diagnostics.apply(infer_batch_type, axis=1)
print("\nInferred Batch Types")
print(diagnostics[['cluster', 'inferred_type']].to_string(index=False))
```

# 5. Robustness and alternative explanations

**Resource ID Trust:**
*   **Trusted (G5):** If `analyst_pool` is treated as a single resource, utilization is calculated as the union of all intervals. Overlaps suggest >100% utilization (impossible for one human), flagging a data quality issue.
*   **Shared Account:** If treated as 3 potential resources, the overlaps become valid parallel work. The "resource" dimension becomes noisy, making individual performance tracking impossible.
*   **Impact:** Treating G5 as a single resource inflates utilization metrics (potentially >100%) and hides individual bottlenecks.

**Timestamp Precision (Exact vs. Interval-Censored):**
*   **Exact (G4, G8):** Sequential logic holds. `Start_N == Complete_N-1` implies immediate handover.
*   **Interval-Censored (G7):** With 15-min precision, a recorded `14:00` start could be `13:52` to `14:00`. A recorded `14:15` complete could be `14:15` to `14:29`.
    *   **Alternative:** The "simultaneous" start in G7 might be an artifact of rounding. Items could have started sequentially within the 14:00-14:14 window.
    *   **Impact:** Service time variance is artificially zero. Analysis must treat G7 service times as intervals `[15m, 30m)` or similar, not point values.

**Three Cases of Ambiguity:**
1.  **G1 vs. G7:** Both show identical start/complete times. G1 is likely physical batching (1s precision, fixture context). G7 is likely coarsening (15m precision, legacy system). Without precision metadata, they look identical.
2.  **G3 vs. G6:** Both show identical completion times. G3 varies starts (work done throughout). G6 varies starts but compresses them to shift-end (data entry). Without `recorded_at` or shift context, G3 could be mistaken for G6-style bulk submission.
3.  **G5 vs. Multitasking:** Overlaps in G5 could be 3 analysts (parallel) or 1 analyst switching tasks rapidly (multitasking) with imprecise logging. Shared account metadata is required to distinguish.

# 6. Data-collection redesign

**Prioritized Recommendations:**

1.  **Execution Timestamps (Critical):** Decouple `work_start` and `work_complete` from `data_entry_time`. G6 and G3 failures stem from logging completion at submission time.
    *   *Action:* Implement event listeners on workstation actions (e.g., scanner trigger, form field focus) rather than form submit.
2.  **Resource/Badge Identity (High):** Eliminate shared accounts like `analyst_pool`.
    *   *Action:* Enforce badge swipes or SSO per session. If pooling is necessary, log `session_id` and map to users via roster.
3.  **Timestamp Precision Metadata (High):** Store the actual resolution of the source system.
    *   *Action:* Add `timestamp_precision` column (as done in this data) to all logs to enable interval censoring analysis.
4.  **Group/Batch Identifiers (Medium):** Explicitly log batch IDs where physical batching occurs (e.g., RBT-7 Fixture ID).
    *   *Action:* Add `batch_id` field to event schema for G1-like processes.
5.  **Source Clock Synchronization (Medium):** Ensure safety systems and repair queues (G8) share a time source.
    *   *Action:* NTP synchronization across PLC, MES, and Safety PLCs.
6.  **Pause/Resume Events (Low):** Capture interruptions (e.g., safety checks).
    *   *Action:* Log `system_pause` events to exclude downtime from service time calculations (critical for G8).

# 7. Final adjudication

**High Confidence Interpretations:**
*   **G1 (Physical Batch):** Evidence (fixture capacity, 1s precision) is strong. Can be used for throughput analysis if batch size is accounted for.
*   **G6 (Bulk Submission):** Evidence (shift-end timestamp, 0 service time) is definitive. **Exclude** from service time analysis; use only for arrival rate analysis.
*   **G7 (Coarsening):** Evidence (15m precision) is definitive. **Interval-censor** in analysis; do not treat as point timestamps.

**Exclude or Interval-Censor:**
*   **G5 (Shared Account):** Cannot attribute work to individuals. Analyze only at pool level.
*   **G7 (Coarsening):** As above.

**Require Operational Validation:**
*   **G2 & G3 (Start/End Batching):** Validate if "group" buttons or "folder" submissions accurately reflect work boundaries. Imputation of intermediate timestamps may be needed for accurate service time distribution.
*   **G8 (Queue Accumulation):** Validate the safety check duration. If the 15:00-15:35 gap is system downtime, it must be subtracted from waiting time to avoid penalizing resource T-H.

**Conclusion:**
Clusters G1, G6, and G7 have distinct data quality signatures that allow definitive diagnosis. G6 and G7 must be corrected or excluded from standard performance mining to avoid severe bias (zero service time, artificial synchronization). G5 requires resource schema changes. G2, G3, G4, and G8 are usable but require context-aware interpretation of batching and downtime.
