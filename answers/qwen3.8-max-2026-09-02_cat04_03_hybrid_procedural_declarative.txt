# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**

1. **Case and outcome semantics**
   - A case is *accepted* iff it contains `Activate Vendor`.
   - A case is *rejected* iff it contains `Reject Vendor`.
   - R1 makes these mutually exclusive.
   - `Close Onboarding` is the terminal event and should occur exactly once.

2. **“Final outcome” for clarification obligations**
   - I interpret R3’s “final outcome” as `Reject Vendor` or `Activate Vendor`, not `Close Onboarding`.
   - Therefore, an open `Request Clarification` must be answered before either rejection or activation.

3. **Clarification pairing**
   - There is at most one outstanding clarification request.
   - `Request Clarification` and `Receive Clarification` can repeat as paired cycles, but nested/unanswered requests are not allowed.

4. **Sanctions escalation timing**
   - R7 says `Sanctions Escalation` may occur only after `Run Sanctions Screening`.
   - In the implemented procedural net, I conservatively place escalation after `Classify Risk`, because all test escalations occur there. This is stricter than R7 and is disclosed as an approximation.

5. **Legal opinion obligation**
   - If `Sanctions Escalation` occurs, `Obtain Legal Opinion` is mandatory eventually (R4).
   - If activation occurs after escalation, strict legal interpretation requires the opinion before activation (R5), unless an explicit emergency exception is recognized.

6. **Emergency data is outside the event log**
   - R6 depends on an external joint authorization and a 24-hour deadline.
   - The event log alone cannot prove that an emergency activation was authorized.

7. **Temporal conformance is advisory**
   - R12 says deviations are normative enough to flag but not automatically reject.
   - Therefore temporal-profile violations are treated as warnings, not hard failures.

8. **Resource/data rules are not activity-only**
   - R9 and R6 require attributes beyond `concept:name`.
   - Missing required attributes produce inconclusive/warning findings, not silent passes.

---

**R5/R6 conflict: at least two resolutions**

1. **Strict legal-precedence resolution**
   - R5 overrides R6 for event-log conformance.
   - Any case with `Sanctions Escalation` followed by `Activate Vendor` before `Obtain Legal Opinion` is a violation.
   - Emergency authorizations are handled outside conformance as manual exceptions.

2. **Controlled emergency-exception resolution**
   - R6 is treated as a narrow exception to R5.
   - `Activate Vendor` may precede `Obtain Legal Opinion` only if:
     - an external joint-authorization record exists, and
     - `Obtain Legal Opinion` occurs within 24 hours of `Sanctions Escalation`.
   - Without external authorization, the case remains a violation.

**Chosen resolution for the implemented model**

I choose **Resolution 1: strict legal-precedence** for the executable procedural model.

**Why**

- The event log has no emergency attribute.
- Activity-only conformance cannot distinguish lawful emergency activation from unlawful precedence violation.
- A conservative compliance posture should fail the trace and require an explicit external exception.

**Compliance risk of this choice**

- **False positives / operational friction:** genuinely authorized emergency activations will fail conformance unless an exception workflow is maintained.
- **Workaround risk:** operations may avoid logging escalations or may pressure teams to delay recording activations.
- **Audit benefit:** the strict model minimizes the risk of silently accepting unauthorized activations.

The alternative emergency-aware policy is not silently merged into the procedural model. It is represented as a separate external check in Section 7.

```python
arc(t_a, can_clarify)

t_b = trans("t_b", "Capture Master Data")
arc(b_in, t_b)
arc(t_b, b_done)

t_c = trans("t_c", "Run Sanctions Screening")
arc(c_in, t_c)
arc(t_c, c_done)

t_d = trans("t_d", "Verify Bank Account")
arc(d_in, t_d)
arc(t_d, d_done)

# Classification synchronizes all three checks
t_e = trans("t_e", "Classify Risk")
arc(b_done, t_e)
arc(c_done, t_e)
arc(d_done, t_e)
arc(t_e, choose)

# Clarification loop: one outstanding request only
t_f = trans("t_f", "Request Clarification")
arc(can_clarify, t_f)
arc(t_f, pending_clar)

t_g = trans("t_g", "Receive Clarification")
arc(pending_clar, t_g)
arc(t_g, can_clarify)

# Outcome 1: normal rejection
t_m = trans("t_m", "Reject Vendor")
arc(choose, t_m)
arc(can_clarify, t_m)
arc(t_m, close_ready)

# Outcome 2: escalated rejection, legal opinion required before rejection
t_h_rej = trans("t_h_rej", "Sanctions Escalation")
arc(choose, t_h_rej)
arc(t_h_rej, rej_i_in)

t_i_rej = trans("t_i_rej", "Obtain Legal Opinion")
arc(rej_i_in, t_i_rej)
arc(t_i_rej, rej_ready)

t_m_esc = trans("t_m_esc", "Reject Vendor")
arc(rej_ready, t_m_esc)
arc(can_clarify, t_m_esc)
arc(t_m_esc, close_ready)

# Outcome 3: low-risk normal acceptance
t_k = trans("t_k", "Manager Approval")
arc(choose, t_k)
arc(t_k, low_k_done)

t_n_low = trans("t_n_low", "Activate Vendor")
arc(low_k_done, t_n_low)
arc(can_clarify, t_n_low)
arc(t_n_low, activated)

# Outcome 4: low-risk escalated acceptance
t_h_low = trans("t_h_low", "Sanctions Escalation")
arc(choose, t_h_low)
arc(t_h_low, lowesc_k_in)
arc(t_h_low, lowesc_i_in)

t_k_lowesc = trans("t_k_lowesc", "Manager Approval")
arc(lowesc_k_in, t_k_lowesc)
arc(t_k_lowesc, lowesc_k_done)

t_i_lowesc = trans("t_i_lowesc", "Obtain Legal Opinion")
arc(lowesc_i_in, t_i_lowesc)
arc(t_i_lowesc, lowesc_i_done)

t_n_lowesc = trans("t_n_lowesc", "Activate Vendor")
arc(lowesc_k_done, t_n_lowesc)
arc(lowesc_i_done, t_n_lowesc)
arc(can_clarify, t_n_lowesc)
arc(t_n_lowesc, activated)

# Outcome 5: high-risk normal acceptance
t_j = trans("t_j", "Enhanced Due Diligence")
arc(choose, t_j)
arc(t_j, high_l_in)

t_l = trans("t_l", "Compliance Approval")
arc(high_l_in, t_l)
arc(t_l, high_l_done)

t_n_high = trans("t_n_high", "Activate Vendor")
arc(high_l_done, t_n_high)
arc(can_clarify, t_n_high)
arc(t_n_high, activated)

# Outcome 6: high-risk escalated acceptance
t_h_high = trans("t_h_high", "Sanctions Escalation")
arc(choose, t_h_high)
arc(t_h_high, highesc_j_in)

t_j_highesc = trans("t_j_highesc", "Enhanced Due Diligence")
arc(highesc_j_in, t_j_highesc)
arc(t_j_highesc, highesc_i_in)
arc(t_j_highesc, highesc_l_in)

t_i_highesc = trans("t_i_highesc", "Obtain Legal Opinion")
arc(highesc_i_in, t_i_highesc)
arc(t_i_highesc, highesc_i_done)

t_l_highesc = trans("t_l_highesc", "Compliance Approval")
arc(highesc_l_in, t_l_highesc)
arc(t_l_highesc, highesc_l_done)

t_n_highesc = trans("t_n_highesc", "Activate Vendor")
arc(highesc_i_done, t_n_highesc)
arc(highesc_l_done, t_n_highesc)
arc(can_clarify, t_n_highesc)
arc(t_n_highesc, activated)

# Payment and closure
t_q = trans("t_q", "Release First Payment")
arc(activated, t_q)
arc(t_q, close_ready)

t_r = trans("t_r", "Close Onboarding")
arc(close_ready, t_r)
arc(t_r, end)

initial_marking = PetriNet.Marking({start: 1})
final_marking = PetriNet.Marking({end: 1})

procedural_model = (net, initial_marking, final_marking)
```

**Explanation**

- **Concurrency:** `Receive Onboarding Request` produces tokens for `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account`. `Classify Risk` consumes all three completion tokens, enforcing the join.
- **Choices:** after `Classify Risk`, one token enters an exclusive outcome choice. This enforces R1 and the primary-outcome structure.
- **Clarification loops:** the place `can_clarify` allows repeated `Request Clarification` / `Receive Clarification` cycles, but only one request can be outstanding. `Reject Vendor` and `Activate Vendor` require the `can_clarify` token, so they cannot occur while a clarification is unanswered.
- **Terminal outcomes:** rejection closes through `Reject Vendor  Close Onboarding`; acceptance closes through `Activate Vendor  Release First Payment  Close Onboarding`.
- **Escalation:** every `Sanctions Escalation` branch contains `Obtain Legal Opinion`. In acceptance branches, activation transitions require the legal-opinion token, implementing strict R5.
- **Post-activation behavior:** `Change Bank Details` and `Suspend Vendor` are deliberately excluded from the canonical onboarding net. R11 is handled in the external data-aware layer because it is post-activation and conditional. If such events are expected inside the same case type, the net should be extended with a separate post-activation subnet.
- **Disclosed approximation:** the procedural net places `Sanctions Escalation` after `Classify Risk`. R7 only requires it after `Run Sanctions Screening`. This is a conservative modeling choice and matches all provided test cases.

# 4. DECLARE Model

```python
def _rule(confidence=1.0):
    return {"support": 1.0, "confidence": confidence}

declare_model = {
    "init": {
        "Receive Onboarding Request": _rule()
    },

    "exactly_one": {
        "Receive Onboarding Request": _rule(),
        "Close Onboarding": _rule(),
    },

    "response": {
        ("Request Clarification", "Receive Clarification"): _rule(),
        ("Sanctions Escalation", "Obtain Legal Opinion"): _rule(),
        ("Activate Vendor", "Release First Payment"): _rule(),
        ("Reject Vendor", "Close Onboarding"): _rule(),
        ("Release First Payment", "Close Onboarding"): _rule(),
    },

    "precedence": {
        ("Capture Master Data", "Classify Risk"): _rule(),
        ("Run Sanctions Screening", "Classify Risk"): _rule(),
        ("Verify Bank Account", "Classify Risk"): _rule(),

        ("Classify Risk", "Reject Vendor"): _rule(),
        ("Classify Risk", "Manager Approval"): _rule(),
        ("Classify Risk", "Compliance Approval"): _rule(),
        ("Classify Risk", "Enhanced Due Diligence"): _rule(),

        ("Run Sanctions Screening", "Sanctions Escalation"): _rule(),
        ("Enhanced Due Diligence", "Compliance Approval"): _rule(),
        ("Activate Vendor", "Release First Payment"): _rule(),
    },

    "noncoexistence": {
        ("Reject Vendor", "Activate Vendor"): _rule(),
        ("Manager Approval", "Compliance Approval"): _rule(),
        ("Enhanced Due Diligence", "Manager Approval"): _rule(),
        ("Reject Vendor", "Manager Approval"): _rule(),
        ("Reject Vendor", "Compliance Approval"): _rule(),
        ("Reject Vendor", "Release First Payment"): _rule(),
    },
}
```

**Rule semantics**

| Template / key | Direction and meaning |
|---|---|
| `init: Receive Onboarding Request` | The first event of every case must be `Receive Onboarding Request`. |
| `exactly_one: Receive Onboarding Request` | The case must contain exactly one onboarding request. |
| `exactly_one: Close Onboarding` | The case must contain exactly one closure. |
| `response: (Request Clarification, Receive Clarification)` | Every clarification request must eventually be followed by some clarification response. This is weaker than full pairing; the Petri net is authoritative for one-outstanding semantics. |
| `response: (Sanctions Escalation, Obtain Legal Opinion)` | If escalation occurs, legal opinion must eventually occur. |
| `response: (Activate Vendor, Release First Payment)` | If activation occurs, first payment must eventually occur. |
| `response: (Reject Vendor, Close Onboarding)` | If rejection occurs, closure must eventually occur. |
| `response: (Release First Payment, Close Onboarding)` | If payment occurs, closure must eventually occur. |
| `precedence: (Capture Master Data, Classify Risk)` | If `Classify Risk` occurs, `Capture Master Data` must have occurred before it. |
| `precedence: (Run Sanctions Screening, Classify Risk)` | If `Classify Risk` occurs, sanctions screening must have occurred before it. |
| `precedence: (Verify Bank Account, Classify Risk)` | If `Classify Risk` occurs, bank verification must have occurred before it. |
| `precedence: (Classify Risk, Reject Vendor)` | Rejection is allowed only after classification. |
| `precedence: (Classify Risk, Manager Approval)` | Manager approval is allowed only after classification. |
| `precedence: (Classify Risk, Compliance Approval)` | Compliance approval is allowed only after classification. |
| `precedence: (Classify Risk, Enhanced Due Diligence)` | Enhanced due diligence is allowed only after classification. |
| `precedence: (Run Sanctions Screening, Sanctions Escalation)` | Escalation requires prior sanctions screening. |
| `precedence: (Enhanced Due Diligence, Compliance Approval)` | Compliance approval, if present, must be preceded by enhanced due diligence. |
| `precedence: (Activate Vendor, Release First Payment)` | Payment, if present, must be preceded by activation. |
| `noncoexistence: (Reject Vendor, Activate Vendor)` | R1: rejection and activation cannot both occur. |
| `noncoexistence: (Manager Approval, Compliance Approval)` | R2/R8: the two approvals should not co-occur. |
| `noncoexistence: (Enhanced Due Diligence, Manager Approval)` | R8: EDD and manager approval should not co-occur. |
| `noncoexistence: (Reject Vendor, Manager Approval)` | Rejected cases should not contain manager approval. |
| `noncoexistence: (Reject Vendor, Compliance Approval)` | Rejected cases should not contain compliance approval. |
| `noncoexistence: (Reject Vendor, Release First Payment)` | Rejected cases should not contain first payment. |

**Important DECLARE limitations**

- I do **not** encode a global `precedence("Obtain Legal Opinion", "Activate Vendor")` because it would fail legitimate low-risk accepted cases without escalation.
- I do **not** use `altresponse` or `chainresponse` for clarification because the requirement is paired obligation, not necessarily immediate succession. The Petri-net token is the authoritative pairing mechanism.
- `response` is weaker than R3’s “before the next clarification request.” DECLARE alone cannot fully express one-outstanding clarification semantics.
- `noncoexistence` is order-independent mutual exclusion. It is stronger than a directed `nonsuccession` rule, which would only forbid one order.

# 5. Log-Skeleton Model

```python
_labels = [
    "Receive Onboarding Request",
    "Capture Master Data",
    "Run Sanctions Screening",
    "Verify Bank Account",
    "Classify Risk",
    "Request Clarification",
    "Receive Clarification",
    "Sanctions Escalation",

    "Change Bank Details",

    "Release First Payment",
    "Close Onboarding",
]

A = "Receive Onboarding Request"

log_skeleton = {
    "equivalence": set(),

    "always_before": {
        (A, x) for x in _labels if x != A
    } | {
        ("Capture Master Data", "Classify Risk"),
        ("Run Sanctions Screening", "Classify Risk"),
        ("Verify Bank Account", "Classify Risk"),

        ("Classify Risk", "Reject Vendor"),

        ("Classify Risk", "Compliance Approval"),

        ("Enhanced Due Diligence", "Compliance Approval"),
        ("Activate Vendor", "Release First Payment"),
    },

    "always_after": {
        ("Request Clarification", "Receive Clarification"),
        ("Sanctions Escalation", "Obtain Legal Opinion"),

        ("Manager Approval", "Activate Vendor"),
        ("Compliance Approval", "Activate Vendor"),

        ("Reject Vendor", "Close Onboarding"),
        ("Activate Vendor", "Release First Payment"),
        ("Release First Payment", "Close Onboarding"),
    },

    "never_together": {
        ("Reject Vendor", "Activate Vendor"),
        ("Manager Approval", "Compliance Approval"),
        ("Enhanced Due Diligence", "Manager Approval"),
        ("Reject Vendor", "Manager Approval"),
        ("Reject Vendor", "Compliance Approval"),
        ("Reject Vendor", "Release First Payment"),
    },

    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Close Onboarding": {1},

        "Capture Master Data": {1},
        "Run Sanctions Screening": {1},
        "Classify Risk": {1},

        "Reject Vendor": {0, 1},
        "Activate Vendor": {0, 1},
        "Release First Payment": {0, 1},

        "Manager Approval": {0, 1},
        "Compliance Approval": {0, 1},
        "Enhanced Due Diligence": {0, 1},
        "Sanctions Escalation": {0, 1},
        "Obtain Legal Opinion": {0, 1},
    },

    "directly_follows": set(),
}
```

**Orientation and semantics**

- `always_before: (x, y)` means that if `y` occurs, `x` must have occurred earlier in the same case.
- `always_after: (x, y)` means that if `x` occurs, `y` must occur later in the same case.
- `never_together: (x, y)` means that `x` and `y` must not both occur in the same case; order is irrelevant.
- `activ_freq` gives allowed occurrence counts.
- `directly_follows` is left empty because the process contains optional interleavings, clarification cycles, and possible escalated legal opinions between activation and payment. For example, T6 has `Obtain Legal Opinion` between `Activate Vendor` and `Release First Payment`, so a direct-follows constraint from activation to payment would be too strict.

**Overlap and deliberate disagreement**

- `always_before` duplicates some procedural and DECLARE precedence constraints, such as the three checks before `Classify Risk`.
- `always_after` duplicates some DECLARE response constraints, such as clarification response and activation-to-payment.
- The Log Skeleton requires only `Run Sanctions Screening` before `Sanctions Escalation`, not `Classify Risk` before `Sanctions Escalation`. The procedural net is stricter because it places escalation after classification. This is intentional: the Log Skeleton remains closer to the minimal policy, while the procedural model encodes the conservative implemented path.
- `never_together` overlaps with DECLARE noncoexistence and with the Petri-net branch structure.
- `activ_freq` encodes R10 for the activities explicitly mentioned in R10, plus a few stable one-time backbone activities. I deliberately do not constrain `Verify Bank Account` frequency because R11 allows re-verification.

If a PM4Py version expects `never_together` as frozensets rather than tuples, the logical content can be converted mechanically, e.g. `{frozenset(pair) for pair in log_skeleton["never_together"]}`.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800, 86400),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200, 21600),
    ("Activate Vendor", "Release First Payment"): (259200, 129600),
}

zeta = 2.0
```

The values are converted from hours to seconds:

- 48 hours = `172800` seconds; 24 hours = `86400` seconds.
- 12 hours = `43200` seconds; 6 hours = `21600` seconds.
- 72 hours = `259200` seconds; 36 hours = `129600` seconds.

A temporal deviation is treated as:

```text
abs(observed_elapsed_seconds - mean_seconds) > zeta * standard_deviation_seconds
```

With `zeta = 2.0`, the acceptable band is plus or minus two standard deviations around the mean.

**Why temporal deviations are warnings**

R12 explicitly says these temporal expectations are normative enough to flag but not automatically reject. Therefore:

- temporal violations do not by themselves make a case non-compliant;
- they are operational or monitoring signals;
- they may indicate delays, missing external responses, or data-quality problems;
- they should be surfaced as warnings and routed for review, not used as hard control-flow failures.

# 7. Resource- and Data-Aware Checks

**Required event attributes**

- `case:concept:name`: case identifier.
- `concept:name`: activity label.
- `org:resource`: resource or user performing the activity.
- `time:timestamp`: event timestamp.

**Required external emergency attributes**

For the emergency-aware resolution of R6, an external table should contain at least:

- `case:concept:name`
- `escalation_time`
- `joint_authorization`
- optionally `authorizers` and `authorization_time`

**Missing attribute policy**

- If required columns are missing, return a data-quality warning and do not silently pass dependent checks.
- If an event exists but `org:resource` is missing, segregation-of-duties checks are inconclusive; mark warning/manual review.
- If timestamps are missing, temporal-order and deadline checks are inconclusive; mark warning/manual review.
- If emergency authorization data is missing under the emergency-exception policy, treat the emergency as unauthorized unless local policy says to hold the case.

```python
import pandas as pd
import pm4py

CASE = "case:concept:name"
ACT = "concept:name"
RES = "org:resource"
TIME = "time:timestamp"

def _missing_columns(df, cols):
    return [c for c in cols if c not in df.columns]

def _case_df(df, case):
    return df[df[CASE] == case]

def _times(df, case, activity):
    sub = df[(df[CASE] == case) & (df[ACT] == activity)]
    return sorted(sub[TIME].dropna().tolist())

def _first_time(df, case, activity):
    ts = _times(df, case, activity)
    return ts[0] if ts else None

def _resources(df, case, activity):
    sub = df[(df[CASE] == case) & (df[ACT] == activity)]
    if sub.empty:
        return set(), False

    missing = sub[RES].isna().any()
    return set(sub[RES].dropna()), bool(missing)

def check_segregation_of_duties(log):
    """
    R9:
    - Verify Bank Account resource must differ from applicable approval resource.
    - Capture Master Data resource must differ from Activate Vendor resource.

    Optional PM4Py shortcut:
      pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
      pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Compliance Approval")
      pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")

    The dataframe logic below defines the authoritative pass/fail semantics.
    """
    df = pm4py.convert_to_dataframe(log)
    findings = []

    missing = _missing_columns(df, [CASE, ACT, RES])
    if missing:
        return [{
            "check": "segregation_of_duties",
            "severity": "warning",
            "message": f"Missing attributes: {missing}. Cannot certify SoD."
        }]

    for case in df[CASE].unique():
        verify_res, verify_missing = _resources(df, case, "Verify Bank Account")
        capture_res, capture_missing = _resources(df, case, "Capture Master Data")
        activate_res, activate_missing = _resources(df, case, "Activate Vendor")

        # Verify Bank Account vs applicable approval
        for approval in ["Manager Approval", "Compliance Approval"]:
            app_res, app_missing = _resources(df, case, approval)

            if app_res and verify_res:
                overlap = verify_res & app_res
                if overlap:
                    findings.append({
                        "check": "segregation_of_duties",
                        "case": case,
                        "severity": "fail",
                        "rule": "R9",
                        "message": f"Same resource performed Verify Bank Account and {approval}: {sorted(overlap)}"
                    })

            if (app_res and app_missing) or (verify_res and verify_missing):
                findings.append({
                    "check": "segregation_of_duties",
                    "case": case,
                    "severity": "warning",
                    "rule": "R9",
                    "message": "Missing resource data prevents full SoD verification."
                })

        # Capture Master Data vs Activate Vendor
        if capture_res and activate_res:
            overlap = capture_res & activate_res
            if overlap:
                findings.append({
                    "check": "segregation_of_duties",
                    "case": case,
                    "severity": "fail",
                    "rule": "R9",
                    "message": f"Same resource performed Capture Master Data and Activate Vendor: {sorted(overlap)}"
                })

        if (capture_res and capture_missing) or (activate_res and activate_missing):
            findings.append({
                "check": "segregation_of_duties",
                "case": case,
                "severity": "warning",
                "rule": "R9",
                "message": "Missing resource data prevents full Capture/Activate SoD verification."
            })

    return findings


def check_outcome_and_approvals(log):
    """
    R1/R2 conditional outcome check:
    - Reject Vendor and Activate Vendor cannot both occur.
    - Accepted case: exactly one of Manager Approval and Compliance Approval.
    - Rejected case: neither approval.
    """
    df = pm4py.convert_to_dataframe(log)
    findings = []

    missing = _missing_columns(df, [CASE, ACT])
    if missing:
        return [{
            "check": "outcome_and_approvals",
            "severity": "warning",
            "message": f"Missing attributes: {missing}. Cannot certify outcome rules."
        }]

    for case in df[CASE].unique():
        acts = set(_case_df(df, case)[ACT])

        has_m = "Reject Vendor" in acts
        has_n = "Activate Vendor" in acts
        has_k = "Manager Approval" in acts
        has_l = "Compliance Approval" in acts

        if has_m and has_n:
            findings.append({
                "check": "outcome_and_approvals",
                "case": case,
                "severity": "fail",
                "rule": "R1",
                "message": "Both Reject Vendor and Activate Vendor occurred."
            })

        if has_n:
            if not (has_k ^ has_l):
                findings.append({
                    "check": "outcome_and_approvals",
                    "case": case,
                    "severity": "fail",
                    "rule": "R2",
                    "message": "Accepted case must contain exactly one of Manager Approval or Compliance Approval."
                })

        if has_m:
            if has_k or has_l:
                findings.append({
                    "check": "outcome_and_approvals",
                    "case": case,
                    "severity": "fail",
                    "rule": "R2",
                    "message": "Rejected case must contain neither Manager Approval nor Compliance Approval."
                })

        if not has_m and not has_n:
            findings.append({
                "check": "outcome_and_approvals",
                "case": case,
                "severity": "warning",
                "rule": "backbone",
                "message": "Case has no terminal outcome event."
            })

    return findings


def check_sanctions_emergency_policy(log, external_auth_df=None, mode="strict"):
    """
    R4/R5/R6:
    mode='strict':
      Any Activate Vendor before Obtain Legal Opinion after Sanctions Escalation fails.

    mode='emergency_allowed':
      Activate Vendor before Obtain Legal Opinion is allowed only if:
        - external joint authorization exists, and
        - Obtain Legal Opinion occurs within 24 hours of Sanctions Escalation.
    """
    df = pm4py.convert_to_dataframe(log)
    findings = []

    missing = _missing_columns(df, [CASE, ACT, TIME])
    if missing:
        return [{
            "check": "sanctions_emergency_policy",
            "severity": "warning",
            "message": f"Missing attributes: {missing}. Cannot certify escalation rules."
        }]

    if mode not in {"strict", "emergency_allowed"}:
        raise ValueError("mode must be 'strict' or 'emergency_allowed'")

    for case in df[CASE].unique():
        h_time = _first_time(df, case, "Sanctions Escalation")
        i_time = _first_time(df, case, "Obtain Legal Opinion")
        n_time = _first_time(df, case, "Activate Vendor")

        if h_time is None:
            continue

        if i_time is None:
            findings.append({
                "check": "sanctions_emergency_policy",
                "case": case,
                "severity": "fail",
                "rule": "R4",
                "message": "Sanctions Escalation occurred without Obtain Legal Opinion."
            })
            continue

        if n_time is not None and n_time < i_time:
            if mode == "strict":
                findings.append({
                    "check": "sanctions_emergency_policy",
                    "case": case,
                    "severity": "fail",
                    "rule": "R5",
                    "message": "Activate Vendor occurred before Obtain Legal Opinion after Sanctions Escalation."
                })
            else:
                authorized = False

                if external_auth_df is not None:
                    auth_missing = _missing_columns(
                        external_auth_df,
                        [CASE, "escalation_time", "joint_authorization"]
                    )
                    if auth_missing:
                        findings.append({
                            "check": "sanctions_emergency_policy",
                            "case": case,
                            "severity": "warning",
                            "rule": "R6",
                            "message": f"External authorization table missing columns: {auth_missing}."
                        })
                    else:
                        auth_rows = external_auth_df[
                            (external_auth_df[CASE] == case) &
                            (external_auth_df["escalation_time"] == h_time) &
                            (external_auth_df["joint_authorization"] == True)
                        ]
                        authorized = not auth_rows.empty

                if not authorized:
                    findings.append({
                        "check": "sanctions_emergency_policy",
                        "case": case,
                        "severity": "fail",
                        "rule": "R6",
                        "message": "Emergency activation before legal opinion lacks external joint authorization."
                    })
                elif i_time - h_time > pd.Timedelta(hours=24):
                    findings.append({
                        "check": "sanctions_emergency_policy",
                        "case": case,
                        "severity": "fail",
                        "rule": "R6",
                        "message": "Emergency legal opinion did not arrive within 24 hours."
                    })
                else:
                    findings.append({
                        "check": "sanctions_emergency_policy",
                        "case": case,
                        "severity": "warning",
                        "rule": "R6",
                        "message": "Authorized emergency activation before legal opinion; opinion arrived within 24 hours."
                    })

    return findings


def check_post_activation_bank_changes(log):
    """
    R11:
    If Change Bank Details occurs after activation:
      - Suspend Vendor must eventually follow it.
      - If a later Release First Payment occurs, another Verify Bank Account
        must occur between Change Bank Details and that Release First Payment.
    """
    df = pm4py.convert_to_dataframe(log)
    findings = []

    missing = _missing_columns(df, [CASE, ACT, TIME])
    if missing:
        return [{
            "check": "post_activation_bank_changes",
            "severity": "warning",
            "message": f"Missing attributes: {missing}. Cannot certify bank-change rules."
        }]

    for case in df[CASE].unique():
        n_time = _first_time(df, case, "Activate Vendor")
        q_time = _first_time(df, case, "Release First Payment")

        o_times = _times(df, case, "Change Bank Details")
        p_times = _times(df, case, "Suspend Vendor")
        d_times = _times(df, case, "Verify Bank Account")

        for o_time in o_times:
            if n_time is None or o_time < n_time:
                findings.append({
                    "check": "post_activation_bank_changes",
                    "case": case,
                    "severity": "warning",
                    "rule": "R11",
                    "message": "Change Bank Details occurred before activation; rule applies only after activation."
                })
                continue

            if not any(p_time > o_time for p_time in p_times):
                findings.append({
                    "check": "post_activation_bank_changes",
                    "case": case,
                    "severity": "fail",
                    "rule": "R11",
                    "message": "Change Bank Details after activation was not followed by Suspend Vendor."
                })

            if q_time is not None and q_time > o_time:
                if not any(o_time < d_time < q_time for d_time in d_times):
                    findings.append({
                        "check": "post_activation_bank_changes",
                        "case": case,
                        "severity": "fail",
                        "rule": "R11",
                        "message": "Later Release First Payment occurred without re-verification after Change Bank Details."
                    })

    return findings
```

# 9. Contradictions, Redundancies, and Blind Spots

**Duplicated enforcement across layers**

- R1 appears in the procedural net, DECLARE noncoexistence, and Log Skeleton `never_together`.
- R3 appears in the procedural clarification token, DECLARE response, and Log Skeleton `always_after`.
- R7 appears in the procedural net, DECLARE precedence, and Log Skeleton `always_before`.
- R8 appears in the procedural branch structure, DECLARE noncoexistence, and Log Skeleton `never_together`.

This redundancy is useful for defense in depth, but it creates a governance problem: layers can disagree in severity or strictness. Therefore one layer must be authoritative for each requirement.

**Constraints that become inconsistent under loops or post-activation changes**

- R11 allows or requires another `Verify Bank Account` after activation. If a model naively enforced `Verify Bank Account` exactly once, it would conflict with R11. I avoided this by not constraining `Verify Bank Account` frequency in the Log Skeleton and by handling R11 externally.
- The procedural net deliberately excludes `Change Bank Details` and `Suspend Vendor`. If those events occur inside the same case, the procedural model will fail them unless a post-activation subnet is added.
- Clarification semantics depend on what counts as final. I treated `Activate Vendor` and `Reject Vendor` as final outcomes for R3. If the business instead treats only `Close Onboarding` as final, clarification after activation but before payment might become ambiguous.

**Vacuity in declarative rules**

- DECLARE `response` rules are vacuously satisfied when the source activity does not occur. For example, low-risk cases pass `Sanctions Escalation  Obtain Legal Opinion` because there is no escalation.
- DECLARE `precedence` rules are vacuously satisfied when the target activity does not occur.
- Temporal-profile checks are vacuous when the relevant pair does not occur. T8, for example, can pass temporal checks despite contradictory terminal outcomes because temporal profiling does not detect missing required events.
- Log Skeleton `always_before` constraints often only apply when the target occurs. They cannot express all conditional obligations.

**Missing case attributes**

- The log lacks an explicit risk class. The route is inferred from approvals and EDD.
- The log lacks emergency authorization data. R6 cannot be validated from the event log alone.
- The log may lack complete resource data. If `org:resource` is missing, R9 cannot be certified.
- The log lacks vendor master-data identifiers, which may be needed for real-world data-aware validation.

**Timestamp-only limitations**

- Temporal profiles measure elapsed time but do not prove causal relationships.
- Timestamps alone cannot detect missing authorization, missing risk classification, or missing resource identity.
- If timestamps are missing, out of order, or coarse-grained, temporal and ordering checks become unreliable.
- The test cases use relative hours; real logs need consistent time zones and clock synchronization.

**Risk of treating support/confidence metadata as normative truth**

- In the DECLARE model, `support` and `confidence` are set to `1.0` to express intended policy strength.
- In discovered models, support and confidence describe historical frequency, not legal obligation.
- A rule with high support can still be violated by a rare but serious exception.
- A rule with low support may still be legally mandatory.
- Therefore support/confidence should inform monitoring and prioritization, not replace explicit policy semantics.

# 10. Deployment Recommendation

**Canonical procedural representation**

Use the **accepting Petri net** as the canonical procedural representation for the stable onboarding backbone. It is preferred over a pure process tree here because it can express:

- concurrent checks with a synchronization join;
- exclusive outcome branches;
- one-outstanding clarification tokens;
- escalated branches with conditional legal-opinion obligations;
- duplicate visible labels on alternative internal paths.

**Authoritative policy layer**

No single formalism should be authoritative for all requirements.

Recommended authority assignment:

- **Procedural Petri net:** authoritative for stable control-flow backbone, terminal outcomes, clarification blocking, and strict R5 in the default policy.
- **External resource/data layer:** authoritative for R9, R11, conditional R2, and R6 emergency exceptions.
- **DECLARE and Log Skeleton:** secondary redundancy and anomaly detection. They should catch violations and support explanation, but they should not silently override the procedural or external authoritative checks.
- **Temporal profile:** advisory warning layer only.

**Recommended conformance-check order**

1. **Data-quality validation**
   - Check required attributes: case id, activity, timestamp, resource.
   - Check external emergency-authorization availability if emergency policy is enabled.

2. **Event normalization**
   - Sort events by timestamp.
   - Validate activity labels.
   - Separate or flag post-activation events if needed.

3. **Procedural conformance**
   - Run alignment or replay against the accepting Petri net.
   - Treat backbone violations as hard failures unless an approved exception exists.

4. **DECLARE conformance**
   - Run as a secondary declarative check.
   - Use violations to explain policy breaches and detect activity-level anomalies.

5. **Log Skeleton conformance**
   - Run as a lightweight redundancy check.
   - Use it for count, ordering, and mutual-exclusion anomalies.

6. **Temporal profile conformance**
   - Run with `zeta = 2.0`.
   - Produce warnings, not automatic failures.

7. **Resource/data/emergency checks**
   - Run segregation-of-duties checks.
   - Run conditional approval/outcome checks.
   - Run emergency-policy checks against external authorization data.
   - Run post-activation bank-change checks.

8. **Aggregation and exception handling**
   - Aggregate findings by requirement, layer, severity, and event index.
   - A hard failure in an authoritative layer should fail the case.
   - Temporal warnings should not fail the case alone.
   - Emergency exceptions should be surfaced as policy-dependent findings requiring explicit approval.

**Surfacing contradictory findings**

Contradictions should not be hidden. For example, T6 should be displayed as:

- Legal/strict view: `Activate Vendor` before `Obtain Legal Opinion` after escalation violates R5.
- Operational/emergency view: the opinion arrived within 24 hours, but authorization is missing or external.
- Recommended user action: require an emergency authorization record, then re-evaluate.

The UI or conformance report should show both the strict violation and the possible exception path. The system should not silently convert a strict legal failure into a pass unless the external authorization evidence is present, complete, and auditable.
