# 5. PM4Py role-discovery and similarity code

The code is illustrative. PM4Py's return types differ slightly between versions, so the helpers are written defensively. `case_complexity` is assumed to be a numeric score in [0, 1] and `temporary_substitution` a boolean-like flag. The complexity bands are assumptions and should be replaced with the organisation's definitions.

```python
import numpy as np
import pandas as pd
import networkx as nx
import pm4py
from scipy.stats import entropy

CASE, ACT, TS, RES = "case:concept:name", "concept:name", "time:timestamp", "org:resource"
KW = dict(activity_key=ACT, timestamp_key=TS, case_id_key=CASE, resource_key=RES)

# ---------------------------------------------------------------
# 1. Load and format
# ---------------------------------------------------------------
raw = pd.read_csv("service_events.csv")
df = pm4py.format_dataframe(raw, case_id=CASE, activity_key=ACT,
                            timestamp_key=TS, timest_format=None)
df = df.sort_values([CASE, TS]).reset_index(drop=True)
df["temporary_substitution"] = (df["temporary_substitution"].astype(str)
                                .str.lower().isin(["true", "1", "yes", "y"]))
df["complexity_band"] = pd.cut(df["case_complexity"], [-0.01, 0.33, 0.66, 0.85, 1.0],
                               labels=["low", "medium", "high", "critical"])

# ---------------------------------------------------------------
# 2. Role discovery, run on several views so we can check stability
# ---------------------------------------------------------------
def mine_roles(d, label):
    roles = pm4py.discover_organizational_roles(
        d, activity_key=ACT, timestamp_key=TS, resource_key=RES, case_id_key=CASE)
    rows = []
    for i, r in enumerate(roles):
        for res, imp in r.originator_importance.items():
            rows.append(dict(view=label, mined_role=f"{label}_role{i}",
                             resource=res, importance=imp,
                             role_activities="|".join(sorted(r.activities))))
    return pd.DataFrame(rows)

views = {
    "all":            df,
    "no_bot":         df[df[RES] != "R14_Nora"],
    "no_substitution": df[~df["temporary_substitution"]],
    "high_critical":  df[df["complexity_band"].isin(["high", "critical"])],
    "low_medium":     df[df["complexity_band"].isin(["low", "medium"])],

def to_graph(sna, directed=True):

    for (a, b), w in sna.connections.items():
        if a != b:
```

# 6. Operational interpretation

**Staffing**
- Treat the structure as a capacity map. Front-office (R-B) and temp capacity (R-C) are interchangeable only for low-complexity cases. Complex and critical work depends on a small number of people (Erik, Mateo, Hana, Chen), so keep protected capacity for them, and do not staff them on volume.
- Plan explicit cover for each single-person function: pricing (Fatima), security (Erik), approval (Hana). Give Giorgio a defined and capacity-limited cover role, so it stays an intentional bench and not an accidental one.
- Use temps for low-complexity work only, and pair them with Amira or Ben for review.

**Training**
- Temps: a mandatory checklist for Validate Entitlement notes, addressing the 17 reopens in weeks 8–10, and a routing rule for anything that looks like A3 or A8.
- Dina: a structured development path towards Chen's complexity tier, and Chen to mentor and to be trained as a security triage backup.
- Giorgio and Mateo: formal pricing-review training and documented triage criteria (including security referral filtering and approval limits), so shadow work is repeatable rather than person-dependent.
- Ivan and Julia: KB entries on recurring reopen causes.

**Risk control**
- Define and audit delegation: what Mateo may approve or filter, and what must go to Hana or Erik.
- Add an SLA and alert for security-flagged critical cases waiting more than a set time (the two critical cases that waited more than two days in weeks 7–8 show why).
- Check segregation of duties where Ivan or Julia both fix (A5/A10) and check (A11) the same case.
- Add a Coordinate activity to the event log so that broker work is visible.

**Resilience**
- Cross-train in pairs (Chen/Dina, Ivan/Julia, Amira/Ben) and reduce single dependency on Erik, Fatima, Hana and Mateo.
- Use the handover and working-together networks to test for fragility: if removing Mateo disconnects specialists from the rest of the process, treat it as a design risk.

**Cautions about changing staffing based only on mined roles**
1. **Frequency and similarity are not authority or risk exposure.** Chen and Dina are 0.94 similar but carry very different critical-case loads. Erik's low volume conceals the fact that he is the only security-certified resource. Removing or "rebalancing" people on the basis of similarity or low counts could remove critical coverage.
2. **Substitution episodes are not proof of permanent competence, or incompetence.** Giorgio's pricing duration doubling and Mateo's rechecked approvals were affected by workload, case mix and unfamiliar queues. Formalizing them as permanent replacements, or penalising them, would misread these episodes. Test with complexity-adjusted comparisons over a longer window.
3. **Ten weeks of data include seasonality and routing policy.** Case allocation rules, shift patterns (Chen and Ivan on late shift) and seasonal temp deployment all shape the profiles. Confirm with routing rules and a longer horizon before reorganising.
4. **Removing "shadow" work can remove resilience.** Mateo's filtering reduced false escalations, and Giorgio's cover kept pricing running. Formalise, monitor and bound these roles instead of eliminating them, and do not assume they are improper.
