## 1. Consistency rules and evidence model

**Hard invariant** (violation  `reject`, no confidence bargaining):

- **HI1 Referential integrity.** Every added `ocel:eid` exists in `events`; every `ocel:oid` exists in `objects`. No new objects or events may be created (so the "missing package" behind `ev08` cannot be invented).
- **HI2 Directionality.** O2O qualifiers are directional (rule 8). `DEL-X carries PK-7` may never be stored as `PK-7 carries DEL-X`, and no qualifier outside the observed vocabulary (`contains, packs, carries, bills, settles`) is introduced, since a new qualifier silently changes OTG/ETOT semantics.
- **HI3 Event inheritance.** An E2O addition takes its timestamp from the existing event; an object's *first* event must be typeappropriate (an Order's first event is `Create Order`, a Delivery's is `Dispatch Package`, an Invoice's is `Issue Invoice`, a Payment's is `Record Payment`). This alone forbids many tempting links.
- **HI4 Activity/type compatibility.** `Record Payment` rows point at Payments/Invoices, `Pack Item` at Items/Packages, etc., following the observed type pattern.

**Strong default** (high prior, defeasible):

- **SD1** Rule 4: one `Dispatch Package`  one Package + one Delivery, unless a bulk flag exists.
- **SD2** Rule 3: one `Pack Item`  one Item + one Package; itemonly rows are outage artifacts to be reconciled *later*.
- **SD3** Rule 7: one `Record Payment`  exactly one Payment, normally one Invoice.
- **SD4** Rule 2 / Rule 1: `Add Item`  one Order + one Item; `Create Order`  one Order.
- **SD5** Lifecycle monotonicity: Create  Add  Pack  Dispatch  Confirm  Issue Invoice  Record Payment as a *partial* order, used only to detect impossible placements (e.g., invoicing before packing).

**Weak heuristic** (±0.10–0.25 on a score):

- **WH1** Identifier similarity (`N-421` vs `N-421?`, `N-42*`).
- **WH2** Timestamp coincidence (ev09/ev10 both 10:00; 14:00 < 15:00 < 16:00).
- **WH3** Attribute agreement: `customer=C17`, `route=NORTH`.
- **WH4** Amounts (230 vs 130+100; 100; 130) — informative only.
- **WH5** Scanner sequence (`PK8-1`, `PK8-2`).
- **WH6** Orphanness: an object with **zero** events is evidence that a relation is missing (DELY, in the unrepaired log).
- **WH7** Intraactivity symmetry: ev13 has an invoice, ev14 does not.
- **WH8** Existing O2O rows as priors on what the writing process normally emits.

**Evidence against a repair:**

- **EA1** Arithmetic equality used as proof (rule 6 forbids this).
- **EA2** Degraded identifiers: a wildcard `N-42*` is evidence for *"several or none"*, not for one delivery.
- **EA3** An O2O row written for `PK-8 packs IT-A2` but absent for `IT-B1`, although the same process wrote it — suggests the row is genuinely absent, not lost.
- **EA4** No domain rule authorises crossorder consolidation.
- **EA5** Rule 7 explicitly permits unapplied cash.
- **EA6** Duplicating an alreadyobserved edge.
- **EA7** Direction mirrors (HI2).

**Combination.** Hard invariants filter the candidate set; strong defaults set a prior (0.6–0.7 for a normal link, 0.4 when a stated exception branch is available); weak heuristics accumulate as coarse likelihood ratios; each `EA-*` subtracts. Thresholds: 0.80 `accept`; 0.55–0.79 `provisional` (written, flagged); 0.30–0.54 `unresolved` (candidate recorded, **not** written); 0.29 `reject`. ## 5. Lifecycle and cardinality audit

**Order.** ORDA: plausible in all bundles (Create  Add ×2  Pack (via its items, if O2O is propagated)  Dispatch  Confirm  Invoice). ORDB: truncated in A/C (Create  Add), extended in B (…  Invoice). No orphan orders. *Suspicion:* under B, `ev12  ORD-B` makes one event relate to two Orders — allowed by rule 6 ("one or more Orders"), but it is one event, not two independent ones.

**Item.** ITA1/ITA2 fully supported in all bundles. ITB1 is the orphanish case: it participates in a `Pack Item` event (ev08) while the event's `scanner_ref` points to a package that is **not** linked — a dangling attribute, not a dangling object. Resolved only in B.

**Package.** PK7: Pack  Dispatch in all bundles; independently supported by E2O (ev09) and O2O (`DEL-X carries PK-7`) — though note both traces back to one event write; the genuinely independent strand is the attribute `carrier_ref=N-420`. PK8: Pack  Dispatch after P01; in B it packs two items from two orders, producing a **manytomany OrderPackage** mapping. That is the single most suspicious cardinality in any bundle.

**Delivery.** DELX and DELY both terminate at Dispatch unless ev11 is linked; **no** bundle gives a Delivery its own arrival event. In the unrepaired log DELY has **zero** events (orphan object); P01 removes that orphan but only *provisionally*. Under B, one `Confirm Delivery` event fans out to 2 Deliveries + 1 Order — permitted by rule 5, but a 1event/3object fanout that will show up as duplicated confirmation influence.

**Invoice.** INV44 bills 1 (A/C: ORDA; B: ORDA + ORDB) orders; each Order has 1 invoice — no suspicious cardinality. **Payment.** PAY1 settles INV44 (observed); PAY2 is either unapplied (A) or settles INV44 (B/C). No payment ever relates to two invoices (rule 7 preserved).

**Independent dual support.** `PAY-2 settles INV-44`, `INV-44 bills ORD-B`, `PK-8 packs IT-B1` and `DEL-Y carries PK-8` are each supported by an E2O row **and** an O2O row — but each pair is a *single hypothesis written twice*. Treating them as two confirmations is circular. The same applies to P07P08: deciding INV44 bills ORDB and then "confirming" it with an added `ev12ORD-B` row is exactly the double count to avoid. Independent strands are only: (i) `carrier_ref`/`external_ref` string equality, (ii) bank_ref sequence, (iii) route/customer agreement, (iv) totals — and (iv) is explicitly barred as proof.

**Orphan events.** ev08 (package attribute without package object), ev10 (`N-421?` without a Delivery in the unrepaired log), ev11 (`N-42*` without any Delivery), ev14 (Payment without Invoice in A).

## 6. Downstream process-mining effects

**OCDFG.** Unrepaired: the node conditioned on Delivery exists only for `Dispatch Package` (weight 1); `Confirm Delivery  Delivery` is absent; `Record Payment  Invoice` has weight 1. Bundle A changes only weights (`Dispatch  Delivery`  2). Bundle B additionally creates `Confirm Delivery  Delivery` (2), raises `Record Payment  Invoice`  2, and raises `Issue Invoice  Order` from 1 to 2 objects. Edges such as `Confirm Delivery  Issue Invoice` conditioned on Order already exist; B makes the same edge visible on the Delivery slice. If someone overrepairs by adding Order links to pack/dispatch/payment events, a spurious chain `Create Order  Add Item  Pack Item  Dispatch Package  Confirm Delivery  Issue Invoice  Record Payment` appears on Orders — a fabricated endtoend process.

**OTG.** Unrepaired the OTG is a *path*: Order–Item–Package–Delivery plus Order–Invoice–Payment, with **no** Order–Delivery and **no** Order–Package edge. Bundle A leaves the topology untouched (only the Package–Delivery weight 12). Bundle B **closes a cycle**: ev11 linking Order + Deliveries creates Order–Delivery, and Order–Invoice weight 12, Invoice–Payment 12. A cyclic OTG vs an acyclic one is a large, easily overinterpreted structural difference.

**ET–OT graph.** Unrepaired: `Pack Item–Package` = 2 of 3 pack events (ev08 lacks a package); `Dispatch Package–Delivery` = 1; `Record Payment–Invoice` = 1; `Confirm Delivery–Delivery` absent; `Issue Invoice–Order` = 1. A: only `Dispatch Package–Delivery`  2. B: `Pack Item–Package`  3/3, `Record Payment–Invoice`  2, `Issue Invoice–Order`  2, plus the new `Confirm Delivery–Delivery` arc.

**Flattenings** (PM4Py's `ocel_flattening` builds perobject traces from E2O; verify whether your version propagates O2O — this changes ORDB below).
- *Order:* ORDA = `[Create, Add, Add, Confirm, Issue Invoice]` in every bundle (packs/dispatches/payments never touch an Order's E2O trace). ORDB = `[Create, Add]` in A/C, `[Create, Add, Issue Invoice]` in B. Accepting P11 (rejected) would make the two variants nearly identical.
- *Delivery:* unrepaired DELY = `[]` — an **empty case** that PM4Py may drop, biasing all percase statistics; A gives `[Dispatch]`; B gives `[Dispatch, Confirm]` for both.
- *Package:* PK8 = `[Pack, Dispatch]` (A/C) vs `[Pack, Pack, Dispatch]` (B) — a new selfloop `PackPack` and a longer mean trace.
- *Invoice:* `[Issue, Record Payment]` (unrepaired/A) vs `[Issue, Record Payment, Record Payment]` (B) — a new `PaymentPayment` selfloop.
- *Payment:* unchanged in all bundles — PAY2's own trace is `[Record Payment]` regardless; P09 affects the **Invoice** case only. A useful reminder that repairs move evidence between case notions.

**Activity frequencies.** Raw event counts are invariant (14 events). What changes is *object participation*: deliveries appearing in 1 event goes 1/2  2/2 after P01; invoices receiving payments 1  2 (B); payments with an invoice link 1  2 (B/C). Metrics using **total** objects as denominator will still count DELY as an idle delivery if P01 is withheld — a false availability signal.

**Equivalentexecution clustering around Order.** Unrepaired/A: two wellseparated clusters (long ORDA, short ORDB). B: ORDB gains `Issue Invoice`, moving it closer to ORDA but still distinguishable (ORDA keeps Confirm + two Adds). If P11 were also accepted, ORDA `[C,A,A,Confirm,Inv]` and ORDB `[C,A,Confirm,Inv]` become nearequivalent, and with O2O propagation both share Invoice/Payment suffixes — clustering would merge the very orders whose delivery histories differ, hiding the real behavioural difference.

## 8. Over-repair warnings

1. **Assigning ev11 to exactly one delivery (P17).** DELX would gain a proofofdelivery it may not have, while PK8/DELY looks permanently undelivered — a phantom SLA bottleneck and a false `Confirm Delivery` predecessor/successor structure on one branch only.
2. **Propagating O2O reachability into E2O** (adding Order links to `Pack Item`, `Dispatch Package`, `Record Payment`). This fabricates `CreateAddPackDispatchConfirmInvoicePay` as a *direct* Orderlevel process, inflates OCDFG edge weights, and makes every order look endtoend observable when payments never touch an order in the source data.
3. **Forcing `INV-44 bills ORD-B` from 130+100=230** and then "confirming" it with the added `ev12ORDB` row — one hypothesis counted twice. The result teaches consolidationbydefault from a single customer, and rulelearning models will happily generalise it to all C17style customers.
4. **Forcing `PAY-2 settles INV-44`.** It erases the unappliedcash class that rule 7 explicitly allows; a conformance checker trained on the repaired log would then flag *genuine* unapplied cash as a deviation, and the Invoice case gains a `PaymentPayment` selfloop that did not occur.
5. **Accepting `PK-8 packs IT-B1`.** It creates an OrderPackage manytomany mapping that the log never states; models may learn that items from different orders routinely merge, and ORDB inherits dispatch/confirmation influence through PK8 even though its own delivery was never confirmed.
6. **Treating the repaired DELY as certain.** The `?` in `N-421?` may mean "unassigned". A wrong P01 turns an empty case into a singleevent case, shifting mean trace length and start/end activity distributions for Delivery.
7. **Mirroring qualifiers** (`IT-A1 carries DEL-X`) or minting new qualifiers (`ORD-A delivers DEL-X`): direction errors corrupt OTG/ETOT arcs and make repaired and original graphs incomparable.
8. **Repairing until every object has a full lifecycle.** That goal, not the evidence, would drive the answer: PAY2, DELY and ITB1 are allowed to remain incomplete, and their incompleteness is itself signal (a genuinely missing application, a genuinely idle delivery, a genuinely broken scan).

I would treat Bundle B as a hypothesis for sensitivity analysis rather than as the log's repaired truth; Bundle A remains the defensible default if any downstream claim depends on the delivery or billing edges.
