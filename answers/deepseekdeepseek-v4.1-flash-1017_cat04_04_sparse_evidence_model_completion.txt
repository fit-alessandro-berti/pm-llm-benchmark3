# 2. Shared Assumptions

- Events are activity completion events at case level; start timestamps, resource timestamps, and overlapping intervals are unavailable.
- Same-timestamp order is ingestion order and is not causal. It is not used to infer parallelism.
- A and H are intended start/end; G requires F; F requires B and C in all candidates.
- If D occurs, it must be before F. D is represented as optional/silent-skippable in all candidates except that the conservative model admits only the exact D absence/presence patterns observed.
- D absence is an abstraction combining true stocked-component skips and missing D events. The absent external/stocked attribute means we cannot conditionally enforce S3.
- E, when present, is optional, occurs at most once, requires B and C to be complete, and occurs before F.
- No loops, rework, cancellations, multiple D, or multiple E are represented. Optionality is represented by XOR alternatives, not by arbitrary repetition.
- ProcessTree parallel operators and POWL partial orders represent possible interleavings, not proof that activities actually overlapped in the source process.

# 3. Conservative Candidate

It does not infer concurrency, generalized optionality, or new D/E interleavings beyond what was observed. It therefore has very high precision on the sample but weak generalization and poor robustness to legitimate new missing-D or concurrent-check cases.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model generalizes the high/medium-confidence rules while explicitly managing low-confidence uncertainty. It treats B and C as concurrent/interleavable because the DFG has both directions and S2 supports parallel checks, but it does not require true simultaneity. D is optional due to S4/S5; when present it must occur before F and after at least one of B or C per D5. E is optional, after both B and C, before F, and unordered with D per D6/S6. Optionality is represented by XOR scenario branches; D/E placements and B/C orders are enumerated only to the extent needed for these constraints.

A  X(

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model is an exploratory hypothesis. It keeps the high/medium rules—A start, H end, B/C before F, E only after both B and C and before F, D before F—but relaxes the low-confidence D5 prerequisite so that D may occur anywhere after A and before F. It uses POWL partial orders inside XOR scenarios for optional D/E, making it compact and suitable for sensitivity analysis rather than compliance enforcement.

**Compact formal expression.**  
`A  X(PO00, PO10, PO01, PO11)` where POxy is a partial order with optional D/E presence as indicated. In every PO:
- A precedes all activities.
- B and C are unordered and both precede F.
- F precedes G, and G precedes H.
- If D is present: D occurs after A and before F; no prerequisite from B/C is enforced in this permissive relaxation.
- If E is present: E occurs after B and C and before F.
- D and E are unordered relative to each other, except both must precede F.
- D and E occur at most once via XOR scenario choice.

**PM4Py POWL code assigning `model_permissive`.**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition
from pm4py.objects.process_tree.obj import Operator

def _add_powl_node(po, node):
    if hasattr(po, "add_node"):
        po.add_node(node)
    elif hasattr(po, "children"):
        try:
            po.children.add(node)
        except AttributeError:
            po.children.append(node)
    else:
        raise AttributeError("Cannot add node to StrictPartialOrder")

def _add_powl_edge(po, source, target):
    po.order.add_edge(source, target)

def build_permissive_po(include_D, include_E):
    labels = [
        "Register Order", "Credit Check", "Engineering Review",
        "Approve Configuration", "Release Production", "Archive Case"
    ]
    if include_D:
        labels.append("Supplier Confirmation")
    if include_E:
        labels.append("Expedite Review")

    nodes = {label: Transition(label) for label in labels}
    po = StrictPartialOrder()
    for node in nodes.values():
        _add_powl_node(po, node)

    A = nodes["Register Order"]
    B = nodes["Credit Check"]
    C = nodes["Engineering Review"]
    F = nodes["Approve Configuration"]
    G = nodes["Release Production"]
    H = nodes["Archive Case"]

    edges = [(A, B), (A, C), (B, F), (C, F), (F, G), (G, H)]

    if include_D:
        D = nodes["Supplier Confirmation"]
        edges += [(A, D), (D, F)]

    if include_E:
        E = nodes["Expedite Review"]
        edges += [(A, E), (B, E), (C, E), (E, F)]

    for source, target in edges:
        _add_powl_edge(po, source, target)

    return po

po00 = build_permissive_po(False, False)
po10 = build_permissive_po(True, False)
po01 = build_permissive_po(False, True)
po11 = build_permissive_po(True, True)

model_permissive = OperatorPOWL(Operator.XOR, [po00, po10, po01, po11])
```

**Behavior deliberately excluded / boundary.**
Reasonable generalization includes optional D/E, any B/C interleaving, D after one or both checks, E before or after D after both checks, and E without D. Forbidden behavior remains:
- G before F; H before G.
- B or C after F.
- D after F.
- E before both B and C, or E after F.
- Multiple D or multiple E.
- Loops, rework, cancellation, or additional unlisted activities.
The explicit risky relaxation is that D may occur before either B or C, which is not supported by D5 but is included to test sensitivity to missing prerequisites.

**Known underfitting risks.**
- It over-generalizes D placement; it may admit infeasible Supplier Confirmation-before-checks behavior.
- It still assumes no rework and at most one D/E.
- It does not model missingness separately from true optionality.
- It is less suitable for compliance enforcement but useful for exploration.

# Permissive POWL
def _add_powl_node(po, node):
    if hasattr(po, "add_node"):
        po.add_node(node)
    elif hasattr(po, "children"):
        try:
            po.children.add(node)
        except AttributeError:
            po.children.append(node)
    else:
        raise AttributeError("Cannot add node to StrictPartialOrder")

def _add_powl_edge(po, source, target):
    po.order.add_edge(source, target)

def build_permissive_po(include_D, include_E):
    labels = [
        "Register Order", "Credit Check", "Engineering Review",
        "Approve Configuration", "Release Production", "Archive Case"
    ]
    if include_D:
        labels.append("Supplier Confirmation")
    if include_E:
        labels.append("Expedite Review")

    nodes = {label: Transition(label) for label in labels}
    po = StrictPartialOrder()
    for node in nodes.values():
        _add_powl_node(po, node)

    A = nodes["Register Order"]
    B = nodes["Credit Check"]
    C = nodes["Engineering Review"]
    F = nodes["Approve Configuration"]
    G = nodes["Release Production"]
    H = nodes["Archive Case"]

    edges = [(A, B), (A, C), (B, F), (C, F), (F, G), (G, H)]

    if include_D:
        D = nodes["Supplier Confirmation"]
        edges += [(A, D), (D, F)]

    if include_E:
        E = nodes["Expedite Review"]
        edges += [(A, E), (B, E), (C, E), (E, F)]

    for source, target in edges:
        _add_powl_edge(po, source, target)

    return po

# 9. Recommendation and Data-Collection Plan

Recommend `model_balanced` for immediate operational use. It is the best compromise: it respects D1–D4 and D6, admits the observed variants, models B/C uncertainty as interleaving rather than forced sequence, and treats D absence as an allowed skip/missing condition instead of certifying it as truly optional. It is more robust than conservative to unseen legitimate interleavings and missing Supplier Confirmation events, but less risky than permissive because it still requires D after at least one check before approval.

Recommend `model_permissive` for sensitivity analysis and stress testing. Use it to ask: “What would change if D5 is weaker than stated or if Supplier Confirmation can occur before either principal check?” The conservative model should be kept as an audit baseline to measure over-generalization and to compare exact-case coverage.

Concrete data-collection plan:
- Export the missing `external/stocked` attribute at order/component level and a boolean “Supplier Confirmation required” flag. This is the single most important missing attribute.
- Add lifecycle timestamps for B, C, D, E, F: schedule, start, complete, cancel. Start/complete overlap is needed to distinguish true concurrency from XOR-sequential logging.
- Add an integration-missingness flag for Supplier Confirmation: event expected, event missing, source system, extraction batch. Around 5–10% suspected missingness must be modeled as missing, not as a business skip.
- Record ingestion timestamp separately from event timestamp to avoid treating same-timestamp ingestion order as causal.
- Collect expedite reason and whether D was required/stock-skipped.
- Future traces that maximally distinguish hypotheses:
  - B and C start/complete overlapping intervals, versus strict B-complete-before-C-start. This separates concurrency from XOR sequence.
  - D after B but before C completes, and D after C but before B completes, especially with the external flag. This tests D5.
  - D absent with external flag true versus false. This separates missingness from legitimate stock skip.
  - E before D and after D after both checks; E absent; E with D absent. This tests E/D ordering and optionality.
  - Rare traces with D before either check. If observed, relax D5; if never observed, keep D prerequisite.
- Use attribute-aware conformance checking: condition the process on `external/stocked` and `expedite_required`, then update XOR/partial-order choices.

# 10. Uncertainty Statement

Calibrated confidence:
- D1 start/end: high, ~0.95–0.99.
- D2 Release requires Approve: high, ~0.98.
- D3 both B and C before F: high, ~0.90–0.95.
- D4 D before F when D occurs: medium-high, ~0.85–0.90.
- True concurrency or mere interleaving between B and C: medium, ~0.60–0.70. S2 and bidirectional DFG support concurrency, but D7 prevents proof.
- D optional versus missing/skipped: medium, ~0.65–0.75. S3, S4, and S5 conflict; the absent external/stocked attribute prevents resolving this.
- D5 “D after at least one check”: low-medium, ~0.50–0.60. V5 supports it, but one or two cases are weak evidence.
- E after both B and C, before F, optional at most once: medium-high, ~0.80–0.90.
- D/E unordered when both occur: medium, ~0.70–0.80, supported by V6/V7 and S6.
- The permissive relaxation allowing D before both checks: low confidence, ~0.20–0.30 under D5 as written, but retained for sensitivity.
- Treating D absence as an allowed skip/missing in balanced: medium, ~0.60–0.70.

A plausible alternative interpretation that would materially change the recommendation is that Supplier Confirmation is mandatory for every order, and all absent-D cases are caused by the known 5–10% integration missingness plus perhaps sampling, not by legitimate stock skips. In that world, the balanced and permissive models’ optional D branch is wrong for compliance: a mandatory-D model with silent missing events or a data-quality-aware model would be preferred. Similarly, if S1 is a true hard rule that Credit Check must finish before Engineering Review, the balanced concurrency branch over-generalizes and a sequential XOR or strict process tree with Credit Check before Engineering Review would be safer.
