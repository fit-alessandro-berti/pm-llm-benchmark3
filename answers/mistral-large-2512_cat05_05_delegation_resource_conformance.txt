## 2. Rule Interpretation

**RR1 (Drafter/approver separation)**
- The same human (after alias normalization) must not perform both `Draft_Change_Request` and `Approve_Change` for the same case.

**RR2 (Implementer/verifier separation)**
- The same human must not perform both `Implement_Change` and `Verify_Implementation` for the same case.

**RR3 (High-risk approval authority)**
- For HIGH-risk cases, `Approve_Change` must be performed by:
  - The QM (Asha Rao), or
  - A valid QM delegate (Ben Koch or Eva Novak) if:
    - The delegation’s effective interval covers the event timestamp.
    - The delegation’s scope covers the change.
    - The principal (Asha) is absent or formally unavailable at the time.
    - No prohibited subdelegation occurred.
- A delegation is valid only if its record was created *before* the effective interval. A later database entry (e.g., D-QM-01 created on 2026-08-12 for 2026-08-10 onward) does not retroactively validate earlier actions.

**RR4 (Emergency substitution)**
- For HIGH-risk emergency changes:
  - `Approve_Change` may be performed by the IC (Diego Martins) or a valid IC delegate (Farid Lang) if the emergency flag and safety rationale are credible.
  - `Retrospective_QM_Review` must be performed by the QM or a valid QM delegate within **two business days** (excluding weekends and holidays). Business days are counted as calendar days excluding weekends and site holidays (none in this period).

**RR5 (Identity evidence)**
- Service accounts are not human identities. Actions must be mapped to an authorized human via session evidence (e.g., badge logs, FIDO tokens, CCTV).
- Aliases must be normalized before segregation checks.

**RR6 (Suspicion versus proof)**
- Indicators (repeated pairs, reciprocal approvals, shared workstations, concentrated handovers) are not proof of collusion without supporting evidence (e.g., financial motive, credential compromise, or policy violation).

**Additional clarifications**
- An action by a principal while on leave (e.g., Asha’s VPN session) is treated as a potential credential-sharing violation unless the principal can demonstrate exclusive control.
- Delegations are valid only if the principal was absent *at the time of the event*. A principal’s later unavailability does not retroactively validate an earlier action.

## 6. Control Improvements

1. **Delegation creation and recording**
   - Require delegations to be recorded in the QMS *before* the effective interval begins.
   - Use cryptographic signatures (e.g., DocuSign) with tamper-evident timestamps.

2. **Effective-time recording**
   - Automate delegation start/end times via calendar integration (e.g., Outlook/Exchange).
   - Block delegation creation if the principal is not marked as absent.

3. **Principal availability**
   - Enforce "absence" status in the QMS (e.g., via HR system integration) to prevent delegation misuse.
   - Require principals to certify unavailability for emergency overrides.

4. **Alias management**
   - Consolidate all aliases into a single identity in the QMS (e.g., `u_bk` and `b.koch`  `Ben Koch`).
   - Use directory services (e.g., Active Directory) to enforce single sign-on (SSO).

5. **Individual authentication**
   - Mandate individual re-authentication (e.g., FIDO2 tokens) for service accounts.
   - Disable shared workstations for high-risk activities; enforce session timeouts.

6. **Emergency review**
   - Automate retrospective QM review reminders (e.g., Outlook tasks) with escalation for missed deadlines.
   - Require documented safety rationale for emergency flags.

7. **Pair rotation**
   - Implement formal pair-rotation policies (e.g., no more than 3 consecutive approvals by the same pair).
   - Monitor and flag repeated pairs via PM4Py handover networks.

8. **Network monitoring**
   - Deploy real-time SoD violation alerts (e.g., via PM4Py streaming).
   - Log and review all delegation usage (e.g., SIEM integration).

9. **Evidential retention**
   - Retain session logs (badge, FIDO, CCTV) for 7 years.
   - Store delegation records with cryptographic hashes to prevent tampering.
