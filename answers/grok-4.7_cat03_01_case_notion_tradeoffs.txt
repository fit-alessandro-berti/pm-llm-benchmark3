## 1. Analytical assumptions

A case notion here is a projection rule, not a recovered truth. Choosing an object type makes each object of that type one case. The case contains only events that mention that object in the given event–object relation, ordered by timestamp. Object–object links do not add events unless an explicit propagation step says so.

Convergence means one event is tied to two or more objects of the case type, so flattening copies it into each of those cases. Aggregated frequencies then count one execution once per participating case. In this snapshot that copy step is forced for nine order-level events: e13 (O2, O3), e14 (O3, O4), e16 (O1, O2, O3), e17 (O3, O4), e19 (O2, O3), e22 (O2, O3), e24 (O1, O2, O3), e25 (O2, O3), and e27 (O3, O4).

Divergence means one case object meets several events of the same activity because it is entangled with several objects of another type. The repeats are then ordered only by time. That interleaving creates directly-follows edges between steps that belong to different items, packages, or deliveries. O1 and O3 are the clear divergent orders: each has two Add Item, two Pack Package, two Dispatch, and two Confirm Delivery events. O2 and O3 also each contain two Record Payment events, through M2 and M3.

A copied shared event is both evidence and duplication. It is evidence that the case object really took part in that execution, so the baseline lifecycle keeps the copy. It is duplication as soon as a discovered DFG, log skeleton, or performance statistic treats the copy as another execution. Case-level questions may use the copy. Workload questions need a distinct-event count beside the flattened count.

The baseline uses the stated event–object relations only. Two transformations are allowed later, and only as named variants. The first is deduplication or down-weighting when a frequency is reported: an event shared by \(k\) cases can contribute \(1/k\), or be counted once by event id. The second is path-specific propagation along a stated qualifier, for example attaching e18 to M1 because M1 settles V1 and e18 issues V1. Propagation of every event of an order onto each of its items is a contamination check, not a baseline. Under that rule I11, which is only on e05, e11, e15, and e23, would also inherit O1’s other leg (e12, e16, e24) and O1’s commercial events.

e29 and e30 share the clock time 2026-02-04 11:05 but are different Close Order events on O2 and O3. Equal timestamps are not convergence. No events were added beyond e01–e31. Trace length is not treated as a measure of correctness: O3 has the longest order trace, 13 events, and also the most interleaved one.

## 3. Concrete distortion analysis

**1. Cross-order package P3, order flattening.** e13 (Pack Package, 10:12) relates to O2, O3, I21, I31, and P3, so both O2 and O3 receive it. One warehouse action becomes two pack occurrences. Both cases gain Add Item → Pack Package. That edge is fair as participation evidence for each order. Summing it as packing workload double-counts P3. The effect is context-dependent: harmful for workload, informative for “these orders were packed together.”

**2. Cross-order package P4, order flattening, with a false repeat on O3.** e14 (10:20) is copied into O3 and O4. Inside O3 the timestamp order is e13 → e14, so the DFG gains Pack Package → Pack Package eight minutes later. O3 did not repack one package. I31 went into P3 with O2’s I21, and I32 went into P4 with O4’s I41. O4’s own trace shows a single pack, so O4 looks like a private happy path even though its only package event is shared. Harmful for variant interpretation of O3. The copy into O4 is the only signal of sharing, and only if event ids are retained.

**3. The same packages under package flattening.** P3’s case is only e13 → e16 → e24, and P4’s is only e14 → e17 → e27. Those strings match the shape of private P1 (e11 → e15 → e23). The related-object lists that show two orders per package are discarded by the projection. Four packages look interchangeable. Transit times remain usable: P1 finishes at 14:00, P2 and P3 at 16:00, P4 at 10:00 the next day. Harmful for any question about mixed-order packing; informative for handling-unit duration.

**4. Consolidated delivery D2.** e16 (Dispatch, 11:05) and e24 (Confirm Delivery, 16:00) are each related to O1, O2, and O3, and also to P2, P3, I12, I21, and I31. In the order log, Dispatch occurs six times (O1 twice, O2 once, O3 twice, O4 once) against three real departures, e15, e16, and e17. O1’s DFG contains Dispatch → Dispatch (e15 at 11:00 to e16 at 11:05) and Confirm Delivery → Confirm Delivery (e23 at 14:00 to e24 at 16:00). The five-minute gap is the gap between D1 and D2, not a second attempt at one shipment. On the delivery projection the same consolidation is invisible from the other side: D2 is a clean two-event case of 4h55m with no second package and no third order. One side inflates frequency; the other hides the load. Both readings are harmful if used alone. Together they separate “orders touched by a truck” from “trucks that ran.”

**5. Consolidated invoice V2.** e19 (Issue Invoice, 12:05), e22 (12:40), and e25 (next day 09:00) are each copied into O2 and O3. The order log therefore shows four Issue Invoice occurrences, one per order case, while the invoice objects are only V1, V2, and V3. It also shows four payment participations for the V2 pair, although the payment objects are only M2 and M3. An order-level “invoices issued” KPI is wrong; an “orders appearing on a bill” KPI is the thing the copies actually measure. On the invoice projection the complementary loss appears: V2 is one healthy-looking billing case, and the fact that it covers two orders is gone. Harmful for finance totals. Informative only when the unit is stated as order participation.

**6. Partial payments and the payment–delivery loop.** M2 `partially_settles` V2 at e22, and M3 `completes_settlement` at e25. Both events are named Record Payment. On the invoice DFG, V2 is Issue Invoice → Record Payment → Record Payment, which is easily read as duplicate collection or rework. The qualifier that separates the two instalments is not in the activity label. Projected onto orders, the same pair produces both directions of a loop. Record Payment → Confirm Delivery arises as e21 → e23 on O1, e22 → e24 on O2 and on O3, and e26 → e27 on O4. Confirm Delivery → Record Payment arises as e24 → e25 on O2 and on O3. O3 is stricter still: e25 sits between the two confirmations e24 (D2, 16:00) and e27 (D3, next day 10:00), so the completing instalment appears to separate two deliveries. A log skeleton built on all four orders cannot put Record Payment always before Confirm Delivery. That inconsistency is real in the timestamps and harmful if mined as a control-flow cycle. It is informative if it is reported as “for V2, the second instalment is after D2’s confirmation and before D3’s.”

**7. Near-singleton payment lifecycles.** Flattening on Payment yields four cases with one event each and no directly-follows edge. M1 does not contain e18, M4 does not contain e20, and neither M2 nor M3 contains e19, because Issue Invoice was not related to the payment object. M2 and M3 also do not co-occur, so this projection cannot show that they are successive settlements of V2. The sequence exists on V2 (e19 → e22 → e25) and in the object–object qualifiers. Using Payment as a lead object truncates the process to a register of four timestamps. That is harmful for discovery and acceptable only as an object list joined back to Invoice.

**8. Split-order interleaving moves the wait onto the wrong edge.** O1’s true legs are e15 → e23 (D1, 11:00 to 14:00, 3h) and e16 → e24 (D2, 11:05 to 16:00, 4h55m). Neither pair is a directly-follows edge. Between them the trace inserts e18 and e21, and it pairs e15 with e16. O4 is the cleaner illustration of performance bias. Its trace is e04, e10, e14, e17 (Dispatch 11:15), e20 (Issue Invoice 12:10), e26 (Record Payment next day 09:30), e27 (Confirm Delivery 10:00), e31. The long gap that a DFG will highlight is e20 → e26, about 21h20m. The physical transit is e17 → e27, 22h45m, and it is not an edge. The same overnight wait is concurrent with the unpaid invoice. A delay diagnosis that blames collection for O4’s cycle time is not supported by the object split; D3 had already left at 11:15. The item and delivery projections keep that wait on Dispatch → Confirm Delivery for I41 and D3. This distortion is harmful for root-cause timing and is specific to divergent order cases.

A related masking effect sits on top of these edges. Create-to-close is about 26h for every order: O1 from e01 09:00 to e28 11:00, O2 from e02 09:02 to e29 11:05, O3 from e03 09:04 to e30 11:05, and O4 from e04 09:06 to e31 11:10. Item confirmation ranges from 4h45m for I11 (e05 09:15 to e23 14:00) to about 24h37m for I32 (e09 09:23 to e27 10:00). O1 is still open for about 19h after its later confirmation e24. Close Order is its own event, not a synonym for delivery or for payment. An order-level cycle time that starts at Create and ends at Close flattens the only large performance contrast in the log.

## 4. Traditional versus object-centric analysis portfolio

Build five flattened logs, and do not discover a model on Payment.

The order log can answer: the identity and create-to-close duration of O1–O4; whether every order reaches Close Order; which orders participate in a shared event id; and how many Add Item or Pack Package steps one order contains. It cannot safely answer how many packages were packed, how many trucks departed, how many invoices were issued, how much settlement happened, or how long a specific leg took. Those answers are the inflated counts and the broken Dispatch–Confirm edges above.

The item log can answer the fulfilment variant and the lead time of I11, I12, I21, I31, I32, and I41. All six variants are the same four activities, so a DFG here is a description of item flow. It cannot answer cash questions, and a count of Dispatch rows is a count of items shipped (6), not of departures (3).

The package log can answer pack-to-confirm time for P1–P4 and can show that P2 and P3 carry the same dispatch and confirm event ids. It cannot say that P3 and P4 are cross-order.

The delivery log can answer departure count and transit time with no copying: three cases, durations 3h, 4h55m, and 22h45m. It cannot say what D2 consolidated.

The invoice log can answer issue-to-first-payment and issue-to-final-payment, and it is the only flat log in which V2’s two payments appear once each. It cannot equate bills with orders, and it should carry the settlement qualifier into the event attributes before anyone interprets Record Payment → Record Payment.

Questions that need an object-centric view:

- An OC-DFG is required to see Dispatch → Confirm Delivery as a delivery-type and item-type path at the same time as Issue Invoice → Record Payment as an invoice-type path, without forcing those families into one directly-follows chain.
- An object-type graph is required for the static design: orders contain items, packages pack items, deliveries carry packages, invoices bill orders, payments settle invoices. That graph is where P3, P4, D2, and V2 show up as multi-object nodes even when a flat DFG looks linear.
- An event-type / object-type graph is required to explain truncation: Create Order and Close Order meet only Order; Add Item meets Order and Item; Pack Package meets Order, Item, and Package; Dispatch and Confirm Delivery add Delivery; Issue Invoice meets Order and Invoice; Record Payment adds Payment. Any lead type missing from a column will lose that activity.
- An object-interaction summary is required for co-occurrence strength: O2 and O3 share e13, e16, e19, e22, e24, and e25; O3 and O4 share e14, e17, and e27; O1 and O2 share only e16 and e24. The same summary will not pair M2 with M3, because they never share an event. The instalment relationship is an object–object fact through V2, so the interaction summary has to be read next to the qualifier table.
- Equivalent-execution clustering is justified as a homogeneity test on the proposed primary type. The four orders do not have the same directly-follows relation, so a single order DFG is an average across non-equivalent executions. Item activity sequences are equivalent even though their timestamps and partner objects differ. The cluster contents should be reported; they are not a discovered “true” case notion.

Contradictory numbers are reconciled by naming the unit before comparing views. “Departures” means distinct Dispatch event ids, which is 3. “Order participations in a departure” means order rows on e15, e16, and e17, which is 6. “Items shipped” is 6. “Packages moved” is 4. “Bills issued” is the three invoice objects, not the four order-side copies of Issue Invoice. “Settlement movements” is four payment objects, of which two belong to V2. When the order DFG lacks Dispatch → Confirm Delivery and the delivery DFG has it, both are right about their own directly-follows relation; transit time is taken from Delivery, Item, or Package, and concurrency with invoicing is taken from the order timestamp list. Disagreement triggers a unit check, not a vote for the longest trace.

## 5. Lead-object decision

**B. Use Order as the primary lead object, with mandatory secondary lifecycles for Item, Delivery, and Invoice. Package is a useful logistics companion. Payment stays an object of the invoice lifecycle, not a case notion.**

Decision criteria were: coverage of the activity vocabulary; alignment with the events that open and close the commitment; whether start-to-end duration is still meaningful after sharing; how badly convergence and divergence damage the internal DFG; and whether other types isolate the damaged parts. Order is the only type that meets the first two. Item, package, delivery, invoice, and payment each miss whole activities. Create Order and Close Order exist only as order events.

The strongest supporting evidence is the event–object table itself: every event from e01 through e31 names at least one of O1–O4, and the four closes are unshared, so each order has a real start and a real end. Secondary views then repair specific holes. Item restores the unbroken Add → Pack → Dispatch → Confirm path and separates I31’s 16:00 confirmation from I32’s next-morning confirmation. Delivery restores a one-event-one-case transit time, including D3’s 22h45m. Invoice restores V2 as one bill with two payments.

The strongest counterargument is that the internal order DFG is the worst model in the portfolio, and O3, the longest trace, is the worst case inside it. Shared packages P3 and P4, shared delivery D2, shared invoice V2, and the two-instalment schedule all meet in O3. A miner that is allowed to see only order cases will report repeated packing, repeated dispatch, and a payment–confirmation loop. Coverage of activities was purchased by accepting exactly those distortions. Choosing Order because its traces are longest would be the wrong reason; length here is a warning.

Residual risk is small-sample overfitting plus metric slippage. There are four orders. O4’s linear eight-event path and O3’s thirteen-event path will both be “the” order model if they are dropped into one discovery run. Create-to-close times are almost identical, so a dashboard of order cycle time will hide the D3 overnight wait and the early confirmation of I11. Nothing in the log says why O1 stays open for about 19h after e24. That gap must remain unexplained.

The decision would change under a different question or a different extraction. If the only decision is carrier performance, Delivery becomes the lead and Order becomes context. If the only decision is collection, Invoice becomes the lead. If a future log attached logistics events only to the executing package or delivery, Order would no longer see those events without a declared propagation rule, and a single lead would no longer be defensible on this evidence. Position A, Order alone, would be acceptable only for a status extract that refuses to publish an order DFG frequency as workload. Position C would be right for a redesign program that treats packing, carriage, and settlement as peer processes with no primary customer object. In the snapshot that was actually given, orders are already present on every event and are the objects that close, so they can lead, provided the secondary lifecycles stay in the same report.

## 6. PM4Py analysis outline

The block assumes a pm4py OCEL whose `ocel:type` values are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, and whose event, object, and relation frames use the standard `ocel:eid`, `ocel:activity`, `ocel:timestamp`, `ocel:oid`, and `ocel:type` columns. Printed models are not a verdict. The participation table is the check on inflation; cluster membership is the check on whether one order model is homogeneous.

```python
import pm4py
import pandas as pd

print(ocel)

events = ocel.events.copy()
objects = ocel.objects.copy()
relations = ocel.relations.copy()

activity_event_freq = events["ocel:activity"].value_counts()
object_type_freq = objects["ocel:type"].value_counts()
print(activity_event_freq)
print(object_type_freq)

linked = relations.merge(events, on="ocel:eid").merge(objects, on="ocel:oid")
participation_summary = (
    linked.groupby(["ocel:activity", "ocel:type"])
    .agg(
        distinct_events=("ocel:eid", "nunique"),
        distinct_objects=("ocel:oid", "nunique"),
        participations=("ocel:eid", "size"),
    )
    .reset_index()
)
participation_summary["extra_copies"] = (
    participation_summary["participations"] - participation_summary["distinct_events"]
)
print(participation_summary.sort_values(["ocel:activity", "ocel:type"]))

if "ocel:qualifier" in relations.columns:
    qualifier_freq = relations["ocel:qualifier"].value_counts()
    print(qualifier_freq)

lead_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flat_logs = {}
dfg_by_type = {}
skeleton_by_type = {}
flat_activity_freq = {}

for ot in lead_types:
    flat_logs[ot] = pm4py.ocel_flattening(ocel, ot)
    dfg_by_type[ot] = pm4py.discover_dfg(flat_logs[ot])
    skeleton_by_type[ot] = pm4py.discover_log_skeleton(flat_logs[ot])
    counts = {}
    for trace in flat_logs[ot]:
        for ev in trace:
            name = ev["concept:name"]
            counts[name] = counts.get(name, 0) + 1
    flat_activity_freq[ot] = counts

# Compare inflated flat counts with one-row-per-event counts.
# Dispatch is the telling row: delivery flat count should match
# distinct events; order and item flat counts should not.
frequency_reconciliation = pd.DataFrame(flat_activity_freq).fillna(0).astype(int)
frequency_reconciliation["distinct_events"] = frequency_reconciliation.index.map(
    activity_event_freq
)
print(frequency_reconciliation)

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Homogeneity test for the primary lead. Read which orders share a
# cluster. Do not treat one cluster, or four, as the correct case notion.
order_equivalence_clusters = pm4py.cluster_equivalent_ocel(ocel, object_type="Order")
item_equivalence_clusters = pm4py.cluster_equivalent_ocel(ocel, object_type="Item")
print(order_equivalence_clusters)
print(item_equivalence_clusters)
```

What has to be read off these objects, rather than off a drawing: `extra_copies` must be 0 for Delivery and Invoice and Payment, and positive for Order on Pack Package, Dispatch, Confirm Delivery, Issue Invoice, and Record Payment. The order skeleton must fail to fix a single order between Record Payment and Confirm Delivery. The delivery DFG should contain only Dispatch → Confirm Delivery. The payment DFG should contain no edges. `interactions` should be checked for the absence of any M2–M3 co-occurrence before that absence is “repaired” with the qualifier table.

## 7. Sensitivity and validation plan

**Shared-event weighting.** Recompute every flattened activity count in two ways: raw case rows, and distinct `ocel:eid`. For Dispatch the raw order figure is 6 and the distinct figure is 3; for Issue Invoice the figures are 4 and 3; for Record Payment they are 6 and 4. A third weighting gives each case row the weight \(1/k\), where \(k\) is the number of cases of that type containing the event. Under that weighting, e16 contributes 1 in total across O1, O2, and O3, while e15 still contributes 1 from O1 alone. The within-case edges of a split order must stay in the structural DFG: O1 really has both e15 and e16. Weighting changes workload totals; it does not delete O1’s second leg. The validation passes only if published workload numbers move down to the distinct-event column and published “orders affected” numbers stay at the participation column.

**Direct relations versus propagation.** Keep the baseline item traces at four events. Then build one declared enrichment and one negative control. The enrichment adds, to each payment, the Issue Invoice event of the invoice named by its qualifier: e18 joins M1, e19 joins both M2 and M3, and e20 joins M4. Each payment case should become Issue Invoice → Record Payment, and M2 must not receive e25. The negative control copies every O1 event onto both I11 and I12. I11 should then incorrectly gain e16 and e24, which belong to I12’s D2 leg, and its clean four-event variant should break. If a propagated “end-to-end item” log is shown, it has to be this controlled path, not the negative control. The same comparison on orders should be nearly idle: orders are already on every event, so propagation does not repair the order DFG.

**Change the lead object on two fixed questions.** Question A: “How many dispatches happened?” Expected answers from the flat counts are 6 (Order), 6 (Item), 4 (Package), 3 (Delivery), 0 (Invoice), 0 (Payment), and 3 distinct events. Question B: “What is the clock time from dispatch to confirmation of the slow overnight movement?” The delivery case D3 answers 22h45m on the edge e17 → e27. The item cases I32 and I41 put that wait on the same edge. The order case O4 does not contain that edge; its long directly-follows wait is e20 → e26, about 21h20m. If a lead-object change cannot reproduce the D3 edge, that lead is not allowed to publish transit SLA numbers. Repeating the pair of questions after swapping the primary label from Order to Invoice should move the headline duration from about 26h create-to-close to V1’s 30 minutes, V2’s 20h55m, and V3’s 21h20m, which is a different phenomenon.

**Three OC-DFG frequency definitions.** For each activity, store distinct events, distinct objects per type, and total participations. The Dispatch row should read: 3 events; orders 4 distinct and 6 participations; items 6 and 6; packages 4 and 4; deliveries 3 and 3. The Record Payment row should read: 4 events; orders 4 distinct and 6 participations; invoices 3 distinct and 4 participations, because V2 occurs on both e22 and e25; payments 4 and 4. Pack Package should read 4 events, 6 order participations, 6 item participations, and 4 package participations. Create Order and Close Order should show 4, 4, and 4 on the order type, with zeros elsewhere. Any dashboard that shows a single frequency for Dispatch or Record Payment fails this check. The three columns answer three questions that this log has already shown to be different.
