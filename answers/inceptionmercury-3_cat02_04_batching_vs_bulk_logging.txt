# 1. Cluster diagnoses

Assumptions used in this section:

- I treat `start` as the local beginning of the activity interval and `complete` as its local end, as supplied.  
- Waiting time is computed as `start - queue_arrival`; service time is `complete - start`.  
- Cluster IDs are used as independent fragments; no cross-cluster case or resource matching is assumed.  
- PM4Py batch labels are treated as temporal-pattern detections, not proof of physical execution semantics.  
- Source precision is the documented resolution, not necessarily the true accuracy of the source.

# 3. Consequences for performance analysis

Definitions used here: waiting time = `start - queue_arrival`; service time = `complete - start`. Conformance statements assume a conventional serial process model where each case has one interval and one resource.

- **G1 — genuine fixture batch**  
  Waiting is real but partly a batching policy: items wait 2–6 minutes from queue arrival until the four-item fixture starts at 09:00. Service appears as 3 minutes per case, but one fixture/station is occupied for a 3-minute cycle containing four items; item-level throughput is four items per cycle. If a tool treats four identical intervals as four separate resource occupations, utilization is overestimated by up to 4×. A serial model will flag simultaneous starts; a batch model is the correct conformance target.

- **G2 — start batching**  
  Waiting includes time spent waiting for the group start at 10:00. Service times are inflated for later cases because the common start makes them appear to take 8–27 minutes whereas the completion spacing suggests about 6–7 minutes of actual inspection per item. Overlapping intervals from the same inspector are not additive: the union of busy time is 10:00–10:27, but summing per-case durations would overcount work. Bottleneck detection sees a start spike and a regular completion cadence, which may look like a cyclic bottleneck rather than deliberate batching. A conformance model needs to allow a shared start event with separate completion events.

- **G3 — end batching / folder submission**  
  If start times are true per-case review starts, waiting to start is usable. Service times, however, are not trustworthy because the 11:30 completion is a folder-submission event, not four independent service completions. The spacing between starts, about 6–8 minutes, is a better upper-bound proxy for serial review work if no idle gaps are assumed. Using the common completion makes T-C appear continuously busy from 11:02 to 11:30 and creates a completion surge at 11:30. Conformance should model “review each case” separately from “submit folder,” otherwise the model will infer long-running overlapping reviews that may not have happened.

- **G4 — sequential processing**  
  The first case waits 7 minutes from arrival to its 12:05 start; later cases wait 10–19 minutes because they arrive while the backlog exists. Service durations of 4 minutes appear clean and adjacent. If the unexplained 12:05 start was caused by an earlier capacity loss, waiting correctly includes that loss; if it was ordinary idle time, waiting overstates demand. Utilization is high and nearly continuous from 12:05 to 12:25. The process pattern is serial, so conformance is usually straightforward; the main risk is over-interpreting exact minute-boundary adjacency as proof of zero gaps.

- **G5 — shared account / concurrency**  
  Waiting can still be interpreted per case if starts are true action starts. Service durations, though, do not measure focused effort: overlapping intervals may reflect multiple analysts under one login or one analyst multitasking. Utilization of `analyst_pool` is the sum of multiple people’s work and cannot be assigned to an individual. This creates a false bottleneck at the pool account. Conformance models that assume one resource cannot execute overlapping cases will either generate violations or require an artificial concurrent-resource model.

- **G6 — end-of-shift/bulk logging**  
  G6-like data produce both inflated waiting and near-zero service. If tickets were actually handled before 17:00 and only closed in bulk, recorded start/complete times of 17:00 turn all queue waiting into `queue_arrival  17:00`, inflating waiting by up to about 3 hours. Because start equals complete, service time is zero. Utilization therefore shows no busy time, while the queue appears enormous. A bottleneck model sees an impossible state: a large queue with no service. These rows should be excluded from quantitative service and utilization analysis until the actual resolution times can be recovered.

- **G7 — 15-min timestamp coarsening**  
  Waiting is only known to within roughly 15 minutes because the rounded start could be before or after the true start. All service times appear as 15 minutes, which is an artifact of the quarter-hour grid. Utilization creates apparent simultaneous manual measurements and periodic 15-minute busy blocks. Conformance cannot determine the true order of the five measurements. The data should be treated as interval-censored, not as exact event times.

- **G8 — queue accumulation after safety-check/downtime**  
  The first repair starts at 15:38, after the recorded safety-check window, while repair arrivals accumulated at 15:00–15:08. If the safety check caused the capacity loss, the waiting times include a real blocking interval. The clock mismatch between the safety system and repair queue means the exact offset is uncertain. Service times of 7 minutes appear valid for the subsequent sequential triage. Without modeling the safety check as a non-available blocking state, the repair resource appears idle even though it was unavailable. Conformance should include the safety-check interval as a blocking/resource-unavailable activity.

# 5. Robustness and alternative explanations

**If resource IDs are trusted versus treated as shared accounts**

Trusting resource IDs makes G5 look like a single highly multitasking analyst, with high apparent utilization of `analyst_pool`. Treating `analyst_pool` as a shared login changes the interpretation: the same overlap pattern can be explained by two or three analysts working in parallel under one ID. Per-person utilization then cannot be measured at all. For machine resources like RBT-7, T-D, or T-H, the resource ID is more reliable, but shared terminals or shift workers could still create serial-identity confounds if the same resource ID is used across workers.

**If timestamps are exact versus interval-censored by stated precision**

Exact timestamp interpretation makes G7 look like five measurements starting at 14:00 and ending at 14:15. Interval-censored interpretation says each true start and completion lies somewhere in a 15-minute window around those grid values; the measurements may be serial, parallel, or a mixture. Similarly, G2’s 10:00 start equality could be an exact group start or merely several starts within the same minute. G6’s zero service could be exactly zero or merely a service shorter than the one-minute display precision, although the manual bulk form makes the logging-artifact interpretation much more likely.

**Cases where the same temporal pattern supports multiple physical explanations**

- G2: identical starts with staggered ends could be a real “begin group” batch, one inspector multitasking, or 1-minute timestamp rounding hiding slightly different starts.
- G3: identical ends could be a folder-level batch completion, a delayed form submission after serial reviews, or end-of-shift data entry.
- G5: overlapping intervals could be multiple analysts sharing one login, one analyst multitasking, or VDI session-level timestamps that do not align with focused work.
- G7: quarter-hour-aligned starts and completions could be a genuine batch of measurements, five serial measurements rounded into the same bins, or coarse summary logging.

# 6. Data-collection redesign

Prioritized recommendations:

1. **Capture execution timestamps at the point of physical action.**  
   Record actual start and completion events from the device, scanner, PLC, or user action, not only from form submission or database insertion. This directly addresses G2, G3, and G6.

2. **Keep `recorded_at` separate and add a submission/batch ID.**  
   Log insertion time independently from execution time. If a form covers multiple cases, store the form ID and the individual action timestamps for each case.

3. **Use unique badge/person/session identity.**  
   Avoid pooled logins such as `analyst_pool`. If a shared account cannot be avoided, create a session ID and a person ID inside the session.

4. **Synchronize source clocks or record clock offsets.**  
   This is necessary for G8 and for any cross-system comparison of queue arrivals, safety events, starts, and completions.

5. **Emit explicit group/batch identifiers.**  
   Capture fixture ID, folder ID, bulk-form ID, batch number, workstation run ID, or inspection group ID. This separates physical batching from logging batching.

6. **Record workstation capacity and concurrency limits.**  
   Store the number of physical slots, fixture capacity, and whether a resource can handle multiple cases simultaneously. This helps disambiguate G1 and G2.

7. **Record pause/resume, maintenance, safety-check, and downtime events as intervals.**  
   These are not idle time; they are non-available capacity. G8 is the clearest example.

8. **Preserve timestamp precision metadata and raw rounded values.**  
   If a legacy system rounds to 15 minutes, do not convert rounded values into exact timestamps. Store the precision and use interval-censored analysis where appropriate.

# 7. Final adjudication

**High-confidence interpretations**

- G1: genuine fixture-level simultaneous batch.  
- G2: start batching with sequential completion.  
- G3: end batching or delayed folder submission.  
- G6: end-of-shift/bulk close-out artifact.  
- G7: coarse 15-minute timestamp rounding.

**Should be excluded or interval-censored in queue analysis**

- G6 should be excluded from quantitative waiting/service/utilization analysis until actual resolution times are known.  
- G7 should be interval-censored, not treated as exact clock times.  
- G5 should be excluded from resource-level utilization and concurrency conclusions unless analyst identities can be recovered.  
- G3 service times should be recalculated or interval-censored; the common completion time is a submission event, not a service completion.

**Require operational validation before any performance conclusion**

- G8: validate the safety-check clock offset and confirm that the safety check caused the queue accumulation.  
- G4: confirm whether the 12:05 start gap was caused by prior capacity loss, idle time, or upstream delay.  
- G1: if per-item throughput is needed, validate whether the four fixture positions are processed in parallel or merely batched within one fixture cycle.  
- G2: confirm the semantics of the “begin group” button and whether individual inspection starts were actually logged.
