    Okay, proceeding## 1. Duplicate-handling decision tree

To minimize semantic damage, the pipeline must distinguish between technical redundancy and legitimate concurrency. The following decision tree guides the classification of candidate event pairs $(E_a, E_b)$ sharing identical or near-identical timestamps and activities.

1.  **Check Technical Identity**: Do `source_event_key` and `payload_hash` match exactly across sources?
    *   **Yes**: Mark as **Exact Technical Duplicate**. Action: **Drop** $E_b$, retain $E_a$.
    *   **No**: Proceed to Step 2.

2.  **Check Object Overlap**: Do $E_a$ and $E_b$ share any Object IDs (E2O relations)?
    *   **No**: They are **Concurrent Distinct Events**. Action: **Retain Both Unchanged**.
    *   **Yes**: Proceed to Step 3.

3.  **Check Physical Reality**: Is there external evidence (reconciliation report, domain fact) confirming they describe the same physical action?
    *   **Yes (Verified Pair)**: e.g., e03/e04. Action: **Merge Attributes and Relations**. Create a new canonical event ID; aggregate payload hashes; retain provenance.
    *   **No**: Proceed to Step 4.

4.  **Check Abstraction Level**: Does one system provide detailed state (e.g., WMS location) while another provides summary status (e.g., ERP balance)?
    *   **Yes**: e.g., e06/e07. Action: **Retain Both with Refined Labels**. Qualify activity name (e.g., `Pack Package (WMS)` vs `Pack Package (ERP)`).
    *   **No**: Proceed to Step 5.

5.  **Check Object Multiplicity**: Do the shared objects imply distinct instances (e.g., Payment M1 vs M2)?
    *   **Yes**: e.g., e13/e14. Action: **Retain Both Unchanged**.
    *   **No**: Proceed to Step 6.

6.  **Check Lifecycle Constraints**: Do domain rules dictate a strict sequence despite timestamp equality?
    *   **Yes**: e.g., Auth before Capture. Action: **Retain Both, Enforce Order**.
    *   **No**: Mark as **Unresolved Candidate**. Action: **Quarantine for Review**.

This tree ensures we do not collapse distinct payments (M1/M2) or concurrent item picks (I1/I2) while resolving true cross-system noise (e03/e04).

## 3. Timestamp-tie ordering rules

When timestamps are identical (second-level precision), a deterministic partial-order-to-total-order policy is required for process mining algorithms that assume linear sequences. However, this order must not falsely imply causality.

**Ordering Hierarchy:**
1.  **Domain Constraints (Semantic):** Hard rules derived from business logic. (e.g., `Authorize Payment` MUST precede `Capture Payment`).
2.  **Object Lifecycle (Semantic):** State progression of shared objects. (e.g., `Pick Item` MUST precede `Pack Package` for the same Item).
3.  **Within-Source Sequence (Deterministic):** Use `source_seq` if available within the same source system.
4.  **Ingestion Time (Deterministic Fallback):** Use `ingested_at` ONLY if all above fail.
5.  **Stable Fallback (Deterministic):** Lexicographical sort on `eid`.

**Why Microseconds are Dangerous:**
Adding synthetic microseconds (e.g., `10:00:00.001`) to break ties creates a **false story**. It implies a causal chain where none was recorded. In OCEL, concurrency is a first-class citizen. Forcing a total order converts parallel activities into serial dependencies, artificially inflating path complexity and suggesting rework loops where events were merely logged simultaneously.

**Intended Orders:**
*   **10:00 Block (Picking/Packing):**
    1.  e03/e04 merged (Pick I1) [Must happen before packing]
    2.  e05 (Pick I2) [Parallel to I1, but logically before pack]
    3.  e06 (Pack WMS) [Contains I1+I2]
    4.  e07 (Pack ERP) [Summary after WMS]
*   **10:15 Block (Logistics):**
    1.  e08 (WMS Release) [Internal warehouse state]
    2.  e09 (Carrier Accept) [External acceptance]
    3.  e10 (Handover) [Physical transfer]
*   **12:00 Block (Finance):**
    1.  e11/e16 merged (Issue Invoice)
    2.  e12 (Auth M1)
    3.  e13 (Capture M1)
    4.  e14 (Capture M2) [Parallel to M1 capture]
    5.  e15 (ERP Summary) [Post-payment update]

*   `original_timestamp`: UTC string from source.
*   `adjusted_timestamp`: Timestamp used for sorting (if modified).
*   `attributes_map`: JSON mapping which source contributed which attribute.
*   `discarded_conflicts`: List of attributes dropped due to conflict.
*   `confidence_score`: Numeric score (0-1) of the decision.
*   `reviewer`: User ID or "System-Auto".

**Reconstruction:**
An analyst can reconstruct the raw view by querying the `source_eids` list against the `ocel_raw` table. By filtering `ocel_clean` where `source_eids` contains a specific ID, they can map the aggregated result back to its components. If `merge_rule` is `NONE`, the event is untouched. This allows auditing whether e14 was truly distinct or accidentally merged.

## 9. Failure modes and safeguards

1.  **Collapsing distinct partial payments**: Treating e13 and e14 as duplicates because they share O1/V1. *Safeguard*: Require unique Payment Object ID match for duplication.
