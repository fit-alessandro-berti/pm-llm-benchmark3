## 1. Modeling assumptions

- **Object types and capitalization**
  - `Order`: `O100`, `O200`
  - `Item`: `I1`, `I2`, `I3`
  - `Package`: `P1`, `P2`
  - `Delivery`: `D1`, `D2`
  - `Invoice`: `V1`
  - `Payment`: `M1`, `M2`

- **E2O qualifier vocabulary**
  - `created`
  - `contains`
  - `added`
  - `reserved`
  - `packed`
  - `dispatched`
  - `carried`
  - `issued`
  - `billed`
  - `recorded`
  - `partially_settles`
  - `confirmed`
  - `closed`

  Qualifiers express the event-specific role of the related object. For example, an `Issue Invoice` event is related to invoice `V1` with qualifier `issued` and to each order with qualifier `billed`.

- **O2O direction conventions**
  - `Order -> Item`: `contains`
  - `Package -> Item`: `packs`
  - `Delivery -> Package`: `carries`
  - `Invoice -> Order`: `bills`
  - `Payment -> Invoice`: `partially_settles`

  O2O edges are source-level business relationships, not inferred graph edges.

- **Direct downstream logistics and finance relations**
  - Logistics events are related directly to operationally involved `Order`, `Item`, `Package`, and/or `Delivery` objects where that involvement is explicit in the narrative.
  - Financial events are related directly to `Invoice`, `Payment`, and billed `Order` objects where stated.
  - The `Record Payment` events are not related directly to Orders because payment allocation to individual orders is not specified. They are related to `M1`/`M2` and `V1`.

- **Preventing analytical propagation from being confused with source facts**
  - The `relations` table contains only direct, source-supported E2O facts.
  - The `o2o` table contains persistent business relationships.
  - No inferred Order links are inserted merely because an Item is in a Package or because a Payment settles an Invoice billing an Order.
  - Analytical tools may propagate context through O2O or shared events, but that propagation is not written back into `relations`.

- **PM4Py version assumption**
  - The pipeline assumes an OCEL 2.0-capable PM4Py release exposing `pm4py.objects.ocel.obj.OCEL` and functions such as `ocel_flattening`, `discover_ocdfg`, `discover_otg`, `discover_etot`, and `discover_oc_petri_net`.
  - If a specific PM4Py version has a different OCEL constructor or function name, only the construction/API call should be adapted; the four DataFrames and their semantics should remain unchanged.

## 3. Data-model audit

### Objects

| Object type | Objects |
|---|---|
| `Order` | O100, O200 |
| `Item` | I1, I2, I3 |
| `Package` | P1, P2 |
| `Delivery` | D1, D2 |
| `Invoice` | V1 |
| `Payment` | M1, M2 |

### O2O qualifiers and cardinalities

| O2O qualifier | Direction | Cardinality |
|---|---|---:|
| `contains` | Order  Item | 3 |
| `packs` | Package  Item | 3 |
| `carries` | Delivery  Package | 2 |
| `bills` | Invoice  Order | 2 |
| `partially_settles` | Payment  Invoice | 2 |

### Activities and touched object types

| Activity | Object types touched directly in E2O |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Order, Item, Package |
| Dispatch Package | Order, Item, Package, Delivery |
| Issue Invoice | Order, Invoice |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Order, Item, Package, Delivery |
| Close Order | Order |

The most consequential convergence/divergence event is **E07, `Pack Package` for P1**. It directly connects `P1` with `I1`, `I3`, `O100`, and `O200`. This is where two order streams converge operationally into one package.

A second important convergence event is **E11, `Issue Invoice`**, which connects `V1` to both `O100` and `O200`. The subsequent payments `M1` and `M2` converge financially on the same invoice.

## 4. Expected flattened behavior

### Order flattening

- **Approximate trace shape**
  - `O100`:
    - Create Order
    - Add Item
    - Add Item
    - Reserve Stock
    - Pack Package for P1
    - Pack Package for P2
    - Dispatch Package for P1
    - Dispatch Package for P2
    - Issue Invoice
    - Confirm Delivery for D1
    - Confirm Delivery for D2
    - Close Order
  - `O200`:
    - Create Order
    - Add Item
    - Reserve Stock
    - Pack Package for P1
    - Dispatch Package for P1
    - Issue Invoice
    - Confirm Delivery for D1
    - Close Order

- **Copied shared events**
  - `Reserve Stock` appears in both Order traces.
  - The P1 packing, dispatch, and delivery confirmation events appear in both Order traces.
  - `Issue Invoice` appears in both traces because V1 bills both orders.

- **Omitted lifecycle aspects**
  - Payments are omitted because `Record Payment` is intentionally linked only to Payment and Invoice, not directly to Orders.
  - The flattened Order log does not directly show M1 or M2.

- **Likely DFG edges**
  - `Create Order -> Add Item`
  - `Add Item -> Reserve Stock`
  - `Reserve Stock -> Pack Package`
  - `Pack Package -> Dispatch Package`
  - `Dispatch Package -> Issue Invoice`
  - `Issue Invoice -> Confirm Delivery`
  - `Confirm Delivery -> Close Order`

  O100 also produces repeated `Add Item`, `Pack Package`, `Dispatch Package`, and `Confirm Delivery` behavior because it is split across P1 and P2.

- **Misleading interpretations**
  - The flattened view can make P1-related work look like independent work performed twice, once for each order, although it was one shared operational event.
  - It may imply a simple sequential per-order process even though P1 physically combines items from two orders.
  - Since payments are absent, an analyst might incorrectly conclude that closing orders is unrelated to payment settlement.

### Package flattening

- **Approximate trace shape**
  - `P1`: Pack Package -> Dispatch Package -> Confirm Delivery
  - `P2`: Pack Package -> Dispatch Package -> Confirm Delivery

- **Copied shared events**
  - No package-level copying between P1 and P2 occurs because each package has its own pack, dispatch, and confirm events.
  - The fact that P1 belongs to two orders is not duplicated within package flattening; P1 remains one package case.

- **Omitted lifecycle aspects**
  - Order creation and item-addition lifecycle events are omitted.
  - Invoice and payment settlement lifecycle events are omitted.
  - The shared reservation is omitted because `Reserve Stock` is not directly related to Package objects.

- **Likely DFG edges**
  - `Pack Package -> Dispatch Package`
  - `Dispatch Package -> Confirm Delivery`

- **Misleading interpretations**
  - The package log can appear highly regular and simple, hiding that P1 is operationally exceptional because it contains I1 and I3 from different orders.
  - It cannot explain why P1’s dispatch affects two orders.

### Delivery flattening

- **Approximate trace shape**
  - `D1`: Dispatch Package -> Confirm Delivery
  - `D2`: Dispatch Package -> Confirm Delivery

- **Copied shared events**
  - No event is copied between D1 and D2 because each delivery has separate dispatch and confirmation events.

- **Omitted lifecycle aspects**
  - Packing and reservation are omitted because they are related to packages/items/orders rather than directly to deliveries.
  - Billing and payments are omitted.
  - Order closure is omitted.

- **Likely DFG edges**
  - `Dispatch Package -> Confirm Delivery`

- **Misleading interpretations**
  - Both deliveries appear structurally identical, despite D1 carrying P1, which is linked to two orders, while D2 carries P2 for only O100.
  - Delivery flattening hides the cross-order consolidation occurring upstream.

### Invoice flattening

- **Approximate trace shape**
  - `V1`: Issue Invoice -> Record Payment -> Record Payment

- **Copied shared events**
  - Both payment events are present in the same invoice trace because M1 and M2 settle V1.
  - The invoice issuance is a single event despite billing two orders.

- **Omitted lifecycle aspects**
  - Order creation, item handling, packing, dispatch, delivery confirmation, and order closure are omitted.
  - The Invoice trace does not reveal which order should receive which part of M1 or M2.

- **Likely DFG edges**
  - `Issue Invoice -> Record Payment`
  - `Record Payment -> Record Payment`

- **Misleading interpretations**
  - A flattened invoice trace can suggest that payment settlement is a simple invoice-local lifecycle.
  - It obscures that V1 combines O100 and O200, and that there is no stated allocation of the 100 and 150 amounts to individual orders.

### Why Payment flattening is particularly weak

Each Payment object has only one directly related event:

- `M1`: Record Payment
- `M2`: Record Payment

Thus Payment traces have length one. A DFG has no meaningful within-trace transitions, and a log skeleton has almost no process structure to infer. Payment-level flattening is useful for inspecting payment attributes such as amount, but weak for sequence discovery.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should preserve object-type-specific behavior without forcing all relationships into one case notion.

Expected patterns include:

- `Order` behavior contains branching and repeated logistics:
  - O100 reaches both P1 and P2 pathways.
  - O200 reaches only the P1 pathway.
- `Package` behavior is compact:
  - Pack -> Dispatch -> Confirm.
- `Delivery` behavior is compact:
  - Dispatch -> Confirm.
- `Invoice` behavior:
  - Issue Invoice -> Record Payment -> Record Payment.
- `Payment` behavior is one-event-per-object.

P1 should create visible coupling between the Order and Package perspectives because it involves I1/O100 and I3/O200. V1 similarly couples O100 and O200 with M1 and M2 through the invoice/payment perspective.

### OTG

The object-type graph should show meaningful type-level connectivity:

- `Order` connected to `Item` through containment and item-related events.
- `Item` connected to `Package`.
- `Package` connected to `Delivery`.
- `Order` connected to `Invoice`.
- `Invoice` connected to `Payment`.

The graph should expose two principal chains:

1. Operational chain:
   `Order -> Item -> Package -> Delivery`

2. Financial chain:
   `Order -> Invoice -> Payment`

P1 bridges O100 and O200 operationally. V1 bridges O100 and O200 financially. M1 and M2 both point toward the same settlement context around V1.

### ET–OT graph

The event-type/object-type graph should show which activities use which object types:

- `Reserve Stock` touches `Order` and `Item`.
- `Pack Package`, `Dispatch Package`, and `Confirm Delivery` touch multiple operational types.
- `Issue Invoice` connects `Order` and `Invoice`.
- `Record Payment` connects `Payment` and `Invoice`.
- `Close Order` is only an Order lifecycle activity.

This makes the cross-object coordination explicit. In particular:

- P1-related activities connect multiple object types simultaneously.
- V1-related issuance and settlement show the transition from Order/Invoice coordination to Invoice/Payment coordination.
- M1 and M2 should be associated with `Payment` and `Invoice`, not falsely with individual orders.

### Object-centric Petri net

## 6. Modeling alternatives

### 1. Source-minimal E2O relations

Under a strict source-minimal policy:

- `Pack Package` might relate only to Package and Items.
- `Dispatch Package` might relate only to Package and Delivery.
- `Confirm Delivery` might relate only to Delivery.
- `Issue Invoice` might relate only to Invoice.
- `Record Payment` might relate only to Payment and Invoice.

Effects:

- Order flattening becomes shorter and may omit pack/dispatch/confirmation events.
- Package and Delivery flattenings remain strong.
- Cross-order coordination through P1 becomes visible mainly through O2O rather than direct shared E2O events.
- OC-DFG and OC-Petri-net discovery may show less direct synchronization between Order and logistics types.

The underlying business story is unchanged; only the direct observation policy is narrower.

### 2. Full operational involvement, used in the pipeline

Under this policy:

- Explicitly involved Orders and Items are directly linked to reservation, packing, dispatch, and confirmation events.
- P1-related events directly include both O100 and O200 because the narrative states that P1 combines their items and that packing is related to both orders.
- Financial events remain conservative: payments are linked to Invoice and Payment, but not to Orders without allocation information.

Effects:

- Order flattening exposes the actual operational impact of shared package P1.
- OC analyses more visibly capture convergence between O100 and O200.
- There is greater risk of relation inflation if such direct involvement is asserted too broadly.

### 3. O2O-propagated analytical relations

Under this policy:

- Store only direct event relations in `relations`.
- During analysis, infer Order context from Item/Package/Delivery O2O links.
- For example, a dispatch of P1 can be analytically connected to O100 and O200 by traversing:
  `P1 -> I1/I3 -> O100/O200`.

Effects:

- The source OCEL remains parsimonious and auditable.
- Analysis can produce richer order-centric views.
- Results depend on propagation rules, traversal depth, direction, and time semantics.
- Analysts must label inferred links as derived context rather than observed event-object relations.

### 4. Invoice-centered financial policy

A further defensible policy is to relate `Issue Invoice` only to V1 and relate payments only to V1 and M1/M2, leaving Order links exclusively in O2O `bills` edges.

Effects:

- Invoice flattening remains the same.
- Order flattening loses direct issuance visibility.
- Order-to-invoice coupling becomes structural rather than event-level.
- This can be appropriate where invoice issuance is recorded by finance systems without direct event-level order references.

## 7. Failure modes

1. **Relation inflation**  
   Adding every transitively connected object to every event makes the OCEL appear more synchronized than the source process actually was. For example, relating M1 directly to O100 and O200 would imply payment allocation facts that are not given.

2. **Missing direct E2O links**  
   If E07 does not directly relate to both O100 and O200, Order-centric analysis may fail to reveal that P1 operationally combines two orders.

3. **Treating O2O propagation as observation**  
   Inferring Order involvement through `Package -> Item -> Order` may be analytically useful, but it is not equivalent to a source-system event relation. Derived edges should not be silently inserted into `relations`.

4. **Duplicate shared events after flattening**  
   A shared event such as `Pack Package` for P1 appears in more than one flattened Order trace. Counting flattened events across cases can overstate the number of real-world executions.

5. **Ambiguous payment allocation**  
   V1 bills both O100 and O200, but the narrative does not allocate the 100 and 150 payments across orders. Directly associating M1 or M2 with one order would create unsupported semantics.

6. **Overly short Payment traces**  
   Each Payment object participates only in one `Record Payment` event. Payment flattening cannot support meaningful DFG discovery and can produce trivial or misleading models.

7. **Constructor or API version mismatch**  
   PM4Py OCEL APIs vary by release. A constructor might require positional rather than keyword arguments, or visualization/discovery function names may differ. The DataFrames should remain unchanged while the isolated API invocation is adapted.

8. **False total order for same-time events**  
   Event logs often sort equal timestamps arbitrarily. This dataset has no timestamp ties, but a general pipeline should not infer causality solely from DataFrame row order when timestamps are equal.

9. **Qualifier inconsistency**  
   Using `packed` for a Package in one event and `contains` for the same event role elsewhere weakens interpretability. Qualifier vocabulary should be consistent and role-oriented.

10. **Event/relation attribute mismatch**  
   If a relation repeats a different timestamp or activity from its event row, PM4Py discovery can operate on corrupted semantics. The pipeline explicitly validates this.

11. **Wrong object types in relations**  
   A relation row identifying P1 as an `Item`, for example, creates inconsistent type-level graphs and can distort OTG or ET–OT results.

12. **Confusing payment amount with an object**  
   Modeling `100` or `150` as separate objects would incorrectly turn an event attribute into a participant in process behavior. Amount belongs in the `events` table.
