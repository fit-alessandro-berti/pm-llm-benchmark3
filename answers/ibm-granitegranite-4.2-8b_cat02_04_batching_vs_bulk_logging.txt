  If resource IDs are treated as unique (no shared account), queue analysis might assume sequential work per analyst, leading to overestimated waiting times if multiple analysts work concurrently on different cases under the same login. - **General for G1–G8**:  
  - **Waiting time bias**: For endbatch clusters (G3, G6), using `start` as work start overestimates waiting if `start` actually reflects batch submission. For queueaccumulation clusters (G8), using `start` without gap awareness underestimates waiting if queue builds before start.  
  - **Service time bias**: For coarsening clusters (G7), exact interpretation overestimates service time; precisionaware bounds reduce bias. For endbatch clusters (G3, G6), `complete` may equal submission time, so service time could be shorter than actual work duration if submission lags completion.  
  - **Resource utilization bias**: Overestimated waiting + underestimated service (due to end batch) can appear low utilization; underestimated waiting + overestimated service can appear high utilization. Batch detection via PM4Py without explanation awareness may merge genuine sequential work with batch patterns, inflating batch size and underestimating utilization at intermediate points.  
  - **Bottleneck detection bias**: If queue accumulation (G8) is misinterpreted as start batching, the bottleneck may be missed at the queue; if end batching (G3/G6) is misinterpreted as concurrent, the bottleneck at submission may be missed. PM4Py batch discovery with default `merge_distance` may detect a batch that includes both queued and submitted items, obscuring the true queue buildup.

> **Specific to G6**: As described, `start`=17:00 and `complete`=17:00 with `recorded_at` at 17:01–17:01 suggests bulk submission (end batch). Calculating waiting = `start`  `queue_arrival` (e.g., 17:00  14:05 = 2h55m) overestimates queue time, while service time (`complete`  `start`) = 0 may underestimate actual measure time. Thus, utilization (service / (start + wait)) could be very low (near 0), masking that the resource was busy all day. A smaller `merge_distance` (e.g., 300s) might still detect a batch at 17:00, but if analysis assumes start = work start, the batch signature could be mislabelled as "end batching" causing incorrect queue conclusions.

# 6. Data-collection redesign

> **Prioritized recommendations** (addressing execution timestamps, recording timestamps, clocks, identity, batch identifiers, capacity, pauses, precision metadata). Priorities reflect impact on reducing ambiguity in queue/performance analysis:

1. **Record work start and work complete separately from form submission:**  
   - Add `work_start` (when activity begins at the resource, e.g., button press or cell start) and `work_complete` (when activity finishes at the resource).  
   - Add `form_submitted_time` for bulk forms (e.g., `manual_bulk_form`). Clarify in UI/template that `start` in logs = `work_start`, `complete` = `work_complete`; form submission time goes to `form_submitted_time`.  
   > *Why:* Eliminates ambiguity whether `start`=17:00 means work start or submission time (G6). Enables correct waiting = `work_start`  `queue_arrival`.

2. **Include unique badge/session ID per worker for operational tasks:**  
   - Require badge swipe or login with unique ID for each worker performing activities (e.g., inspectors, packers, analysts). For shared accounts (e.g., `analyst_pool`), log `analyst_name` or `session_id` at activity start/complete (if feasible; if not, minimize shared account use for queue analysis).  
   > *Why:* Reduces `shared-account artifact` confusion (G5); allows reliable `resource` identity in queue analysis. Metadata (e.g., "analyst_pool used by 2 analysts at a time") can be recorded if sharing unavoidable.

3. **Document and store timestamp precision metadata with every record:**  
   - Automatically include `precision` (e.g., "1 sec", "1 min", "15 min") and `precision_bounds` (e.g., ±0.5×precision for rounding; e.g., ±30s for 1min precision) in the database row. Do not round `start`/`complete` in logs; store raw as given (e.g., "09:00" for 1min precision).  
   > *Why:* Makes coarsening detectable (G7); allows analysis to use bounds (e.g., service time  [work_start  0.5×precision, work_complete + 0.5×precision]). Avoids equating identical timestamps with simultaneity.

4. **Log queue size at arrival and departure for each resource:**  
   - At `queue_arrival`, record `queue_size_arrival` (number waiting including the arriving item). At `work_start` (when resource begins the activity), record `queue_size_start` (number waiting just before start).  
   > *Why:* Directly shows queue buildup (e.g., G8 queue accumulation) and distinguishes it from batch start. Enables backlog calculation without inferring from `start``queue_arrival` gap alone.

5. **Capture pause/resume events:**  
   - Add optional `pause_reason` and `pause_time` fields when a resource stops work (e.g., cell idle, safety check active, manual review paused). Resume event includes `resume_time`.  
   > *Why:* Explains gaps (e.g., G8 repair queue may pause during safety check), clarifies whether queue accumulation is due to capacity loss or downtime. Helps distinguish queue buildup from concurrent work.

6. **Sync all operational clocks; record clock offsets if sync not possible:**  
   - Use a single NTP source for PLC, tablet, desktop, scanner, VDI. If safety-check clock cannot sync (per context), at each repair triage event record `safety_offset = repair_queue_clock - safety_clock` (if measurable; e.g., operator notes offset or system logs both times).

   > *Why:* Distinguishes operational batch (cell processes 4 items together) from logging batch (bulk form submission). Allows PM4Py batch discovery to be interpreted with context (e.g., "RBT-7 batch" vs "manual bulk submit batch").
