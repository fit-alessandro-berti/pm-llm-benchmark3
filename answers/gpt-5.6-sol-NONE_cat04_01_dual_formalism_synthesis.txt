# 1. Assumptions and Interpretation

1. **Risk route.** After `Analyze Root Cause`, an XOR selects either:
   - low risk: one `Supervisor Review`; or
   - high risk: both `Quality Review` and `Regulatory Review`, unordered and therefore potentially concurrent.
   The unrepresented risk datum determines the XOR choice externally.

2. **Supplier consultation.** Supplier involvement is represented by an XOR between `Consult Supplier` and a silent transition. Consultation occurs at most once, must follow root-cause analysis, and must precede release.

3. **Passing inspection.** Because pass/fail is not part of the event label, a loop represents zero or more failed iterations followed by a final passing `Inspect Trial`. In the POWL model, each loop body is `Execute Trial  Inspect Trial`, and the redo part is `Adjust Parameters`. Thus every redo semantically means that the preceding inspection failed, while loop exit means that it passed.

4. **Duplicate labels.** The process-tree model below does **not** duplicate visible labels. Duplicate labels would make conformance and activity-level interpretation ambiguous and would still require careful synchronization. The POWL loop naturally repeats the same transition labels without statically duplicating them.

5. **Process-tree approximation policy.** I use a **conservative under-approximation**. Root-cause work, approvals, planning, design, and any supplier consultation are completed before the trial loop starts. This excludes intended approval/trial and supplier/trial overlap, but does not release material before an obligation is complete.

6. **Meaning of overlap.** “May overlap” is interpreted as absence of a precedence constraint and thus true concurrency in the model semantics. A sequential event log records only a linearization of that concurrency.

7. **Completion-time traces.** A precedence edge between two visible activities constrains their recorded completion order. The narrative sometimes says “may start only after.” Under the stated completion-event abstraction, I approximate such lifecycle constraints by completion precedence. Start/complete lifecycle events would be needed to represent overlap durations exactly.

8. **Initial and terminal events.** `Register Deviation` is the unique first visible activity, `Release Material` follows all required obligations, and `Archive Case` is the unique final visible activity.

9. **POWL loop interpretation.** `OperatorPOWL(Operator.LOOP, [body, redo])` is assumed to have process-tree-style `body (redo body)*` semantics. Consequently, at least one trial is performed, and `Adjust Parameters` can occur only between inspections and subsequent executions.

10. **POWL supplier node placement.** The XOR node itself follows root-cause analysis and precedes release. If its silent branch is selected, it adds no visible event; if consultation is selected, that visible activity inherits those constraints.

# 3. PM4Py Process-Tree Model

The conservative tree completes the two prerequisite streams—including approvals and the optional supplier decision—before starting the trial loop:

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->(
      'Analyze Root Cause',
      +(
        'Design Corrective Action',
        X('Supervisor Review', +('Quality Review', 'Regulatory Review')),
        X(tau, 'Consult Supplier')
      )
    )
  ),
  *(
    ->('Execute Trial', 'Inspect Trial'),
    'Adjust Parameters'
  ),
  'Release Material',
  'Archive Case'
)
```

Here `->` is sequence, `+` is parallel, `X` is XOR, `*` is loop, and `tau` is silent. The loop has language:

```text
(Execute Trial, Inspect Trial)
(Adjust Parameters, Execute Trial, Inspect Trial)*
```

Self-contained construction code:

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def activity(label):
    return ProcessTree(label=label)

def silent():
    return ProcessTree(label=None)

def operator_node(operator, children):
    node = ProcessTree(operator=operator)
    node.children = []
    for child in children:
        node.children.append(child)
        child.parent = node
    return node

register = activity("Register Deviation")

contain_plan = operator_node(
    Operator.SEQUENCE,
    [
        activity("Contain Material"),
        activity("Plan Verification"),
    ],
)

high_risk = operator_node(
    Operator.PARALLEL,
    [
        activity("Quality Review"),
        activity("Regulatory Review"),
    ],
)

risk_route = operator_node(
    Operator.XOR,
    [
        activity("Supervisor Review"),
        high_risk,
    ],
)

supplier_optional = operator_node(
    Operator.XOR,
    [
        silent(),
        activity("Consult Supplier"),
    ],
)

analysis_obligations = operator_node(
    Operator.PARALLEL,
    [
        activity("Design Corrective Action"),
        risk_route,
        supplier_optional,
    ],
)

analysis_stream = operator_node(
    Operator.SEQUENCE,
    [
        activity("Analyze Root Cause"),
        analysis_obligations,
    ],
)

pretrial_work = operator_node(
    Operator.PARALLEL,
    [
        contain_plan,
        analysis_stream,
    ],
)

trial_body = operator_node(
    Operator.SEQUENCE,
    [
        activity("Execute Trial"),
        activity("Inspect Trial"),
    ],
)

trial_loop = operator_node(
    Operator.LOOP,
    [
        trial_body,
        activity("Adjust Parameters"),
    ],
)

tree = operator_node(
    Operator.SEQUENCE,
    [
        register,
        pretrial_work,
        trial_loop,
        activity("Release Material"),
        activity("Archive Case"),
    ],
)
```

The tree represents unique start/end, independent initial streams, the risk XOR, concurrent high-risk reviews, optional supplier consultation, the repeat-until trial pattern, and safe release synchronization. It does **not** exactly represent the asymmetric join in which the trial waits only for planning and design while approvals and supplier consultation continue independently. Instead, the parallel block joins all pretrial obligations before `Execute Trial`. It therefore excludes approval/trial and supplier/trial overlap. It also cannot represent activity start times from completion-only labels, and pass/fail remains an interpretation of loop continuation or exit rather than an explicit data condition.

# 4. PM4Py POWL Model

The POWL model places the independently progressing obligations in one strict partial order. Only required dependencies receive edges:

```text
POWL root nodes:
  R  = Register Deviation
  C  = Contain Material
  A  = Analyze Root Cause
  P  = Plan Verification
  D  = Design Corrective Action
  RR = XOR(
         Supervisor Review,
         PO(Quality Review, Regulatory Review; no edge)
       )
  S  = XOR(tau, Consult Supplier)
  T  = LOOP(
         PO(Execute Trial -> Inspect Trial),
         Adjust Parameters
       )
  L  = Release Material
  Z  = Archive Case

Edges:
  R -> C
  R -> A
  C -> P
  A -> D
  A -> RR
  A -> S
  P -> T
  D -> T
  T -> L
  RR -> L
  S -> L
  L -> Z
```

Self-contained Python code:

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Atomic activities
register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")

supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")

consult = Transition(label="Consult Supplier")
skip_supplier = SilentTransition()

execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
adjust = Transition(label="Adjust Parameters")

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

# High-risk route: both reviews, with no order between them.
high_risk = StrictPartialOrder(nodes=[quality, regulatory])

# Exactly one risk route is selected.
risk_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor, high_risk],
)

# Supplier consultation is optional and occurs at most once.
supplier_optional = OperatorPOWL(
    operator=Operator.XOR,
    children=[skip_supplier, consult],
)

# One trial body is Execute -> Inspect.
trial_body = StrictPartialOrder(nodes=[execute, inspect])
trial_body.order.add_edge(execute, inspect)

# LOOP semantics: body (redo body)*.
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, adjust],
)

# Root partial order
powl = StrictPartialOrder(
    nodes=[
        register,
        contain,
        analyze,
        plan,
        design,
        risk_route,
        supplier_optional,
        trial_loop,
        release,
        archive,
    ]
)

# Registration precedes both initial work streams.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Selective downstream dependencies.
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, risk_route)
powl.order.add_edge(analyze, supplier_optional)

# The trial waits only for planning and design.
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronizes trial completion, approval, and supplier choice.
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_route, release)
powl.order.add_edge(supplier_optional, release)

# Unique terminal order.
powl.order.add_edge(release, archive)
```

Intentional non-edges carry important meaning:

- `Contain Material` and `Analyze Root Cause` are unconnected because they are independent after registration.
- `Plan Verification` is unconnected to analysis, design, risk review, and supplier consultation because it depends only on containment.
- `Design Corrective Action`, the risk route, and supplier choice are mutually unconnected after their common analysis prerequisite.
- `Quality Review` and `Regulatory Review` have no internal edge because either completion order is valid.
- The risk route and supplier node have no edge to or from the trial loop, except that all three precede release. They may therefore overlap or appear in either completion order, subject to their own prerequisites.
- Transitive order is intentional: for example, registration precedes release through intervening nodes without a redundant direct edge.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and analysis are independent after registration. | Parallel branches represent this. | Two nodes share only the registration predecessor. | Neither at completion-event level. | Either stream may finish first. |
| Split dependencies into planning/design | Planning depends only on containment; design only on analysis. | Represented locally, but enclosing parallel branches later join too much. | Direct edges `contain  plan` and `analyze  design`. | Tree becomes overconstrained at the pretrial join. | Tree may falsely reject cases whose approvals remain open when trial starts. |
| Risk route | XOR between supervisor-only and both high-risk reviews. | Exact control-flow choice; high-risk reviews parallel. | XOR node with an unordered high-risk partial order. | Data-to-choice mapping is absent in both. | Models cannot verify whether recorded case risk selected the correct branch. |
| Approval and trial overlap | Trial need not wait for approval, but release must. | Not supported by the chosen tree: all approval finishes before trial. | Risk route and trial are unordered but both precede release. | Tree overconstrains; POWL closely matches. | Tree inflates apparent approval lead-time compliance and rejects legitimate overlap. |
| Optional supplier consultation | Zero or one consultation after analysis; selected consultation precedes release. | XOR with `tau`, but consultation must finish before trial. | XOR with `SilentTransition`; node follows analysis and precedes release. | Tree overconstrains overlap; POWL matches control flow. | Tree can misclassify expedited trial work as nonconforming. |
| Repeat-until behavior | One or more execute/inspect cycles; adjustment exactly between failed and next cycles. | Binary loop gives `EI (A EI)*`. | LOOP over ordered body and adjustment redo. | Outcome semantics remain abstract in both. | Neither model can independently prove that a particular inspection really failed or passed. |
| Release synchronization | Passing final inspection, chosen review route, and selected consultation must all finish. | Safe but synchronizes them earlier than necessary. | Three independent predecessor nodes join at release. | Tree overconstrains timing; neither admits unsafe early release. | POWL better detects true release-readiness violations. |
| “May overlap” | No order constraint, ideally concurrent execution. | Some parallelism exists, but cross-branch overlap is lost. | Unconnected partial-order nodes encode concurrency directly. | Completion logs still show only linearizations. | Duration-level overlap cannot be established without lifecycle timestamps. |
| Unique start and end | Registration first; archive last after release. | Root sequence enforces both. | Root edges and transitive dependencies enforce both. | Neither, assuming standard partial-order execution semantics. | Cases with missing or displaced endpoints are rejected. |
| Duplicate-label risk | Repeated trials reuse the same activity names across iterations. | No static duplicate leaves; loop re-executes its body. | No static duplicates; loop repeats its transitions. | Iteration identity remains unobservable. | Event-to-iteration alignment may be ambiguous during conformance diagnostics. |

# 7. Preferred Representation and Validation Plan

The **POWL model is the canonical representation**. Its root partial order directly captures the non-block-structured dependency graph: planning and design alone enable the trial, while approvals and supplier consultation proceed independently and synchronize only at release. The process tree should be retained as a conservative interoperability approximation, not treated as the authoritative specification.

A concrete validation plan is:

1. **Construction checks**
   - Traverse both models and verify every expected visible label.
   - Confirm exactly one static transition per visible activity label in each model.
   - Confirm one silent supplier-skip transition and no unintended visible duplicates.
   - Inspect POWL edges against the dependency table, including the intentional absence of approval-to-trial and supplier-to-trial edges.

2. **Conversion to accepting Petri nets**
   ```python
   import pm4py

   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   ```
   Conversion availability can depend on the installed PM4Py version and supported POWL constructs. A successful conversion establishes tool compatibility, not semantic fidelity.

3. **Soundness checks**
   ```python
   tree_sound = pm4py.check_soundness(
       tree_net, tree_im, tree_fm, print_diagnostics=True
   )
   powl_sound = pm4py.check_soundness(
       powl_net, powl_im, powl_fm, print_diagnostics=True
   )
   ```
   Inspect diagnostics for dead transitions, improper completion, residual tokens, and deadlocks. Soundness does not prove correspondence to the narrative.

4. **Bounded or sampled playout**
   - Sample both source models and, where useful, converted nets with `pm4py.play_out`.
   - Impose a practical event or loop bound, such as at most three trial iterations.
   - Check that the POWL sample includes both orders of high-risk reviews, both initial-stream orders, approval-after-execution traces, and supplier-after-execution traces.
   - Check that the tree sample never places approvals or supplier consultation after trial execution begins.

5. **Explicit positive tests**
   - Replay or align traces A1–A5.
   - Expect all five to fit POWL.
   - Expect A1 and A5 to fit the tree, while A2–A4 expose its documented under-approximation.

6. **Explicit negative tests**
   - Replay or align F1–F3 and require nonfitness in both models.
   - Add mutation tests by moving `Release Material` before each obligation separately, removing the second execution after adjustment, and inserting a second supplier consultation.

7. **Silent and duplicate-label checks**
   - Verify that choosing the supplier-skip branch emits no visible event and does not create an observable empty case.
   - Inspect converted-net silent transitions for livelocks, especially around XOR and loop routing.
   - Count static visible labels and ensure that repeated `Execute Trial`/`Inspect Trial` observations arise from loop execution, not duplicate static leaves.
   - During alignments, inspect whether silent routing can bypass any selected visible obligation.

8. **Limitations**
   - Finite playout cannot prove correctness of an unbounded loop.
   - Petri-net soundness is structural/behavioral and does not validate business data conditions.
   - Completion-only traces cannot validate start-time prerequisites or actual temporal overlap.
   - Risk, supplier involvement, and inspection outcomes are not represented as data guards.
   - Conversion may introduce silent routing whose structure differs by PM4Py version.
   - Alignment fitness can be affected by costs and duplicate-label ambiguity, so raw fitness alone is not sufficient.

# 8. Final Self-Critique

1. The POWL model assumes that ordering a composite XOR or loop node correctly induces ordering over its selected internal behavior; this should be verified against the exact PM4Py version’s operational semantics and converter.

2. The completion-event abstraction cannot faithfully express the narrative’s start-time constraints or distinguish genuine duration overlap from two permissible completion orders.

3. The process tree is deliberately restrictive: it loses legitimate approval/trial and supplier/trial overlap. A duplication-based tree might preserve more traces, but would introduce label ambiguity and synchronization risks that are avoided here.
