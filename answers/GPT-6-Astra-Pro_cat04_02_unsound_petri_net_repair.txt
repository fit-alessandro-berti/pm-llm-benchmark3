# 1. Executive Verdict

**The net is a workflow net, but it is not sound for the supplied initial and final markings.** It has a unique source, a unique sink, and every node lies on a directed source-to-sink path.

The principal defect is that `t_join_waived` consumes only the waiver token. Unlike `t_join_normal`, it neither waits for nor consumes completed analysis.

Consequently, authorization can occur before mandatory analysis. Completing analysis first does not solve the problem: the waiver route still leaves an analysis-completion token outside the sink. Thus, reaching a marking containing a sink token is not necessarily reaching `fm`.

The preferred repair adds the missing input arc `p_analysis_done -> t_join_waived`. This preserves parallel branch release, both review alternatives, their visible labels, and clean completion.

# 2. Structural Diagnosis

**Interpretation.** I use ordinary, untimed, unit-weight Petri-net semantics: a transition requires tokens in all its input places and, when fired, consumes those input tokens and produces its output tokens. This is the enabledness and execution semantics used by the PM4Py functions below. 

For the business interpretation, firing a visible activity represents completing that activity. The silent split releases both branches; it does not establish literal simultaneous starts or model activity durations. The supplied marking represents one case.

| Element or subnet                                | Intended role                                                 | Actual structural effect                                                                      | Potential symptom                                                             |
| ------------------------------------------------ | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `source -> t_register -> p_ready`                | Register the case before further work                         | Consumes the initial token and enables the split                                              | No defect in this subnet                                                      |
| `t_split`                                        | Release analysis and review in parallel                       | Consumes one token from `p_ready`; produces one in `p_analysis` and one in `p_review`         | Two branch obligations must eventually be reconciled                          |
| `p_analysis -> t_analyze -> p_analysis_done`     | Mandatory analysis                                            | Analysis completion produces a token whose only consumer is `t_join_normal`                   | On the waiver route, completed analysis becomes stranded                      |
| `p_review -> t_standard_review -> p_review_done` | Complete the standard-review alternative                      | Consumes the single review token and supplies the normal join                                 | Correctly excludes subsequently choosing waiver                               |
| `p_review -> t_waive_review -> p_waived`         | Complete a visibly recorded waiver instead of standard review | Competes with standard review for the same review token                                       | The exclusive choice is correct; its downstream synchronization is not        |
| `t_join_normal`                                  | Synchronize analysis with standard review                     | Requires and consumes both `p_analysis_done` and `p_review_done`; produces one decision token | Correct completion on the standard route                                      |
| `t_join_waived`                                  | Synchronize analysis with the selected waiver outcome         | Requires only `p_waived`; acts as a one-input forwarding transition                           | Premature authorization and an unconsumed analysis obligation                 |
| `p_decision -> t_authorize -> sink`              | Authorize after both obligations are satisfied                | Authorization requires only the decision token, regardless of which join produced it          | The defective waiver join can enable authorization                            |
| `im = {source: 1}`                               | Start exactly one case                                        | Initially enables only `t_register`                                                           | Appropriate initial marking                                                   |
| `fm = {sink: 1}`                                 | Finish with one sink token and no tokens elsewhere            | Acceptance requires this exact marking; sink presence alone is insufficient                   | Waiver executions can appear finished operationally but fail exact acceptance |
| Whole directed graph                             | Connect all model elements between source and sink            | Every place and transition lies on some directed source-to-sink path                          | A workflow-net check passes despite the behavioral defect                     |

The workflow-net check concerns the unique source, unique sink, and source-to-sink path condition—not whether the tokens needed along those paths can coexist during execution. 

For example, the analysis subnet has a graph path to the sink through `t_join_normal`. After waiver is selected, however, the required `p_review_done` token cannot be produced. **Graph connectivity is therefore not evidence of an executable completion path from every reachable marking.**

Every transition can fire in some execution from `im`; none is globally unfireable. Nevertheless, executions containing the waiver transition cannot reach `fm`. The failure concerns completion and synchronization, not an unreachable transition.

# 3. Marking-Based Counterexample

All unlisted places have zero tokens. Enabled-transition sets include silent transitions.

**Counterexample 1: authorization before analysis**

The following complete sequence of firings is legal in the original net:

`t_register -> t_split -> t_waive_review -> t_join_waived -> t_authorize -> t_analyze`

| Step | Fired transition | Resulting nonzero marking        | Enabled transitions                                | Observation                                                     |
| ---- | ---------------- | -------------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| 0    | —                | `{source: 1}`                    | `t_register`                                       | Start at `im`                                                   |
| 1    | `t_register`     | `{p_ready: 1}`                   | `t_split`                                          | Registration completed                                          |
| 2    | `t_split`        | `{p_analysis: 1, p_review: 1}`   | `t_analyze`, `t_standard_review`, `t_waive_review` | One token exists in each parallel branch                        |
| 3    | `t_waive_review` | `{p_analysis: 1, p_waived: 1}`   | `t_analyze`, `t_join_waived`                       | Waiver is recorded; analysis has not occurred                   |
| 4    | `t_join_waived`  | `{p_analysis: 1, p_decision: 1}` | `t_analyze`, `t_authorize`                         | The decision token is produced without analysis                 |
| 5    | `t_authorize`    | `{p_analysis: 1, sink: 1}`       | `t_analyze`                                        | Authorization occurred before analysis; this is **not** `fm`    |
| 6    | `t_analyze`      | `{p_analysis_done: 1, sink: 1}`  | None                                               | A non-final deadlock: the analysis-completion token is stranded |

Step 5 is an improper completion marking but **not yet a deadlock**: `t_analyze` remains enabled. That firing consumes the outstanding analysis token, but only transforms it into a token that can no longer be consumed.

At step 6, the only consumer of `p_analysis_done` is `t_join_normal`, which also needs `p_review_done`. Producing that token requires `t_standard_review`, but waiver already consumed the only `p_review` token. The split cannot fire again, so that missing review token cannot be regenerated.

Thus:

$$
M_6=\{\texttt{p\_analysis\_done}:1,\ \texttt{sink}:1\}
\neq
fm=\{\texttt{sink}:1\}.
$$

**Counterexample 2: analysis first still does not permit proper completion**

This distinguishes the synchronization defect from merely scheduling authorization too early:

`t_register -> t_split -> t_analyze -> t_waive_review -> t_join_waived -> t_authorize`

| Step | Fired transition | Resulting nonzero marking             | Enabled transitions                                | Observation                                                      |
| ---- | ---------------- | ------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 0    | —                | `{source: 1}`                         | `t_register`                                       | Start at `im`                                                    |
| 1    | `t_register`     | `{p_ready: 1}`                        | `t_split`                                          | Registration completed                                           |
| 2    | `t_split`        | `{p_analysis: 1, p_review: 1}`        | `t_analyze`, `t_standard_review`, `t_waive_review` | Both branch tokens created                                       |
| 3    | `t_analyze`      | `{p_analysis_done: 1, p_review: 1}`   | `t_standard_review`, `t_waive_review`              | Mandatory analysis has completed                                 |
| 4    | `t_waive_review` | `{p_analysis_done: 1, p_waived: 1}`   | `t_join_waived`                                    | Both business obligations have completed                         |
| 5    | `t_join_waived`  | `{p_analysis_done: 1, p_decision: 1}` | `t_authorize`                                      | The join fails to consume completed analysis                     |
| 6    | `t_authorize`    | `{p_analysis_done: 1, sink: 1}`       | None                                               | Authorization follows analysis, but exact completion still fails |

The conclusions are stronger than “some unfortunate schedule deadlocks”:

* **Every execution that fires `t_waive_review` loses the option to reach `fm`.**
* Some such executions authorize before analysis; others authorize afterward.
* Both standard-review completion orders can reach `fm` through `t_join_normal`.

Consequently, the original net’s accepted complete traces exclude waiver altogether, even though waiver-related firings and unsafe authorization are reachable.

# 4. Minimal-Repair Alternatives

**Edit-cost model.** Each added or removed arc, place, or transition costs one:

$$
c=
\#\text{arc additions/removals}
+\#\text{place additions/removals}
+\#\text{transition additions/removals}.
$$

Redirecting an arc costs two: one removal and one addition. Removing a node also incurs the costs of removing its incident arcs. Arc weights, initial/final markings, and visible labels remain fixed. Metadata such as the net’s name is outside this structural cost.

Business-policy changes are declared separately; a low structural cost does not make them acceptable automatically.

| Repair                                         | Exact edits                                                                                                      | Edit cost                        | Preserved intent                                                                        | Changed behavior                                                                                                                                                      | New risk                                                                                                    |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **A — Proper waiver-specific synchronization** | Add `p_analysis_done -> t_join_waived`                                                                           | **1:** one arc addition          | Mandatory analysis; either review outcome; either completion order; exact final marking | The waiver join now waits for and consumes completed analysis                                                                                                         | Future modifications must keep the two alternative joins consistent                                         |
| **B — Shared normal synchronization**          | Remove `t_join_waived -> p_decision`; add `t_join_waived -> p_review_done`; retain every node and all other arcs | **2:** one removal, one addition | Same visible behavior as A; mandatory analysis and both review alternatives             | Waiver now follows `t_join_waived -> p_review_done -> t_join_normal`; `p_review_done` means “review requirement satisfied,” not necessarily standard review performed | Shared-place provenance can be misinterpreted; the waiver route has an additional silent step relative to A |
| **C — Synchronize at waiver recording**        | Add `p_analysis_done -> t_waive_review`; leave both joins unchanged                                              | **1:** one arc addition          | Mandatory analysis, exactly one review outcome, and clean completion                    | **Policy change:** waiver may be recorded only after analysis. The waiver transition consumes completed analysis itself                                               | Prevents early waiver recording and introduces an additional business-ordering restriction                  |

**Minimality and distinctness**

**A is globally minimum-cost for the original intent.** Cost zero leaves the proven defect unchanged. A costs one and corrects it, meeting that lower bound.

**C also costs the minimum possible nonzero amount**, but implements a stricter policy. It is behaviorally different from A: the visible sequence

`t_register -> t_waive_review -> t_analyze -> t_authorize`

is accepted by A, with appropriate silent firings, but excluded by C. Their structural costs tie; their business semantics do not. C must not be deployed as an equivalent implementation without approval of that added dependency.

**B is not globally minimum under this cost model.** It is minimum within the shared-synchronization repair family that retains the existing nodes and makes `t_join_normal` the sole producer of decision tokens. The old waiver-to-decision arc must be removed, and a replacement onward arc must be added: at least two edits.

Removing only the old arc destroys waiver completion. Adding only the new arc leaves the bypass and produces both a decision token and a review-completion token, potentially enabling a second authorization after the normal join.

A and B preserve the same accepted visible language, but their internal structures differ. In B, `t_join_waived` can fire before analysis finishes because it only forwards the waiver outcome toward the real synchronization. In A, that transition itself performs the synchronization. I do not claim that A and B represent different observable business policies.

**Why A is sound**

At `{p_analysis: 1, p_waived: 1}`, A disables `t_join_waived` and leaves `t_analyze` enabled. After analysis completes, the waiver join consumes both tokens and produces one decision token.

More generally, every reachable unfinished marking can progress: any outstanding branch can complete; once both obligations are complete, exactly the join matching the selected review outcome is enabled. Both routes then reach `fm`. The single review token prevents both outcomes—and therefore both joins—from being used in one case. Each transition occurs in some successful execution.

A useful additional check is the invariant

$$
I(M)=2\sum_{p\in H}M(p)+\sum_{p\in P\setminus H}M(p)=2,
$$

where

$$
H=\{\texttt{source},\texttt{p\_ready},\texttt{p\_decision},\texttt{sink}\}.
$$

Every transition in A preserves this quantity. A sink token accounts for the entire value of two, forcing every other place to be empty. In the original model, `t_join_waived` increases this quantity by one—precisely the unmatched branch obligation.

The invariant establishes proper completion; the progression argument establishes the option to complete. Neither argument alone should substitute for the other.

# 5. Corrected PM4Py Code

The following standalone code constructs **Repair A**. Its only structural difference from the supplied net is the added input arc to `t_join_waived`.

```python
import pm4py
from pm4py.objects.petri_net.obj import PetriNet, Marking
from pm4py.objects.petri_net.utils import petri_utils

repaired_net = PetriNet("parallel_review_with_waiver_repaired")

r_places = {
    name: PetriNet.Place(name)
    for name in (
        "source", "p_ready", "p_analysis", "p_review",
        "p_analysis_done", "p_review_done", "p_waived",
        "p_decision", "sink"
    )
}
repaired_net.places.update(r_places.values())

r_transitions = {
    name: PetriNet.Transition(name, label)
    for name, label in (
        ("t_register", "Register Case"),
        ("t_split", None),
        ("t_analyze", "Perform Analysis"),
        ("t_standard_review", "Perform Standard Review"),
        ("t_waive_review", "Record Review Waiver"),
        ("t_join_normal", None),
        ("t_join_waived", None),
        ("t_authorize", "Authorize Case"),
    )
}
repaired_net.transitions.update(r_transitions.values())

r_arcs = [
    ("source", "t_register"),
    ("t_register", "p_ready"),
    ("p_ready", "t_split"),
    ("t_split", "p_analysis"),
    ("t_split", "p_review"),
    ("p_analysis", "t_analyze"),
    ("t_analyze", "p_analysis_done"),
    ("p_review", "t_standard_review"),
    ("t_standard_review", "p_review_done"),
    ("p_review", "t_waive_review"),
    ("t_waive_review", "p_waived"),
    ("p_analysis_done", "t_join_normal"),
    ("p_review_done", "t_join_normal"),
    ("t_join_normal", "p_decision"),
    ("p_waived", "t_join_waived"),
    # Repair A: the waiver join must also consume completed analysis.
    ("p_analysis_done", "t_join_waived"),
    ("t_join_waived", "p_decision"),
    ("p_decision", "t_authorize"),
    ("t_authorize", "sink"),
]
r_nodes = {**r_places, **r_transitions}
for source_name, target_name in r_arcs:
    petri_utils.add_arc_from_to(
        r_nodes[source_name], r_nodes[target_name], repaired_net
    )

repaired_im = Marking({r_places["source"]: 1})
repaired_fm = Marking({r_places["sink"]: 1})
```

# 6. Diagnostic and Reachability Code

This block assumes the original `net`, `im`, and `fm`, and the repaired variables above, exist.

The requested `check_soundness` API returns a `(boolean, diagnostics)` tuple; the code unpacks it rather than testing the truthiness of the tuple. The currently inspected source also marks this API deprecated, so deployment should use a tested version that exposes the requested interface. 

`get_enabled_transitions` returns transition objects. The helper checks membership in that set before calling `semantics.execute`, which itself returns `None` for a disabled transition. It never uses weak firing or inserts missing tokens. 

Although `convert_to_reachability_graph` accepts `fm`, its Petri-net implementation constructs reachable markings from `im`; providing `fm` does not restrict the graph to successful executions. This is important for finding the defective waiver states. 

```python
import pm4py
from collections import deque
from pm4py.objects.petri_net.obj import PetriNet, Marking
from pm4py.objects.petri_net import semantics


def marking_text(marking: Marking) -> str:
    entries = sorted(
        (place.name, count)
        for place, count in marking.items() if count != 0
    )
    return "{" + ", ".join(f"{name}: {count}" for name, count in entries) + "}"


def enabled_names(pn: PetriNet, marking: Marking) -> list[str]:
    return sorted(t.name for t in pm4py.get_enabled_transitions(pn, marking))


def fire_named(pn: PetriNet, marking: Marking, name: str) -> Marking:
    matches = [t for t in pn.transitions if t.name == name]
    if len(matches) != 1:
        raise ValueError(f"Expected exactly one transition named {name!r}.")

    transition = matches[0]
    if transition not in pm4py.get_enabled_transitions(pn, marking):
        raise ValueError(
            f"{name} is disabled at {marking_text(marking)}; "
            f"enabled={enabled_names(pn, marking)}"
        )

    result = semantics.execute(transition, pn, marking)
    if result is None:
        raise RuntimeError("Enabledness and execution unexpectedly disagree.")
    return result


def show_sequence(pn, start, final, sequence):
    marking = Marking(start)
    print("0", "im", marking_text(marking), enabled_names(pn, marking))
    for step, name in enumerate(sequence, start=1):
        marking = fire_named(pn, marking, name)
        print(step, name, marking_text(marking), enabled_names(pn, marking))
    print("Exact final marking:", marking == final)
    return marking


def marking_key(marking):
    return frozenset((p, count) for p, count in marking.items() if count != 0)


def find_authorization_without_analysis(pn, start):
    # Explore all reachable prefixes that have not fired t_analyze.
    initial = Marking(start)
    queue = deque([(initial, [])])
    seen = {marking_key(initial)}

    while queue:
        marking, path = queue.popleft()
        enabled = sorted(
            pm4py.get_enabled_transitions(pn, marking),
            key=lambda transition: transition.name
        )
        for transition in enabled:
            if transition.name == "t_analyze":
                continue
            if transition.name == "t_authorize":
                return path + [transition.name]

            successor = fire_named(pn, marking, transition.name)
            key = marking_key(successor)
            if key not in seen:
                seen.add(key)
                queue.append((successor, path + [transition.name]))

    return None


diagnostic_results = {}
reachability_graphs = {}

for title, pn, start, final in (
    ("original", net, im, fm),
    ("repaired", repaired_net, repaired_im, repaired_fm),
):
    print("\nMODEL:", title)
    is_workflow_net = pm4py.check_is_workflow_net(pn)
    is_sound, diagnostics = pm4py.check_soundness(
        pn, start, final, print_diagnostics=True
    )
    initial_enabled = pm4py.get_enabled_transitions(pn, start)
    reachability_graph = pm4py.convert_to_reachability_graph(pn, start, final)

    diagnostic_results[title] = (is_workflow_net, is_sound, diagnostics)
    reachability_graphs[title] = reachability_graph

    print("Workflow net:", is_workflow_net)
    print("Sound:", is_sound)
    print("Initially enabled:", sorted(t.name for t in initial_enabled))
    print("Reachability states:", len(reachability_graph.states))
    print(
        "Analysis-bypass witness:",
        find_authorization_without_analysis(pn, start)
    )


early_authorization = [
    "t_register", "t_split", "t_waive_review",
    "t_join_waived", "t_authorize", "t_analyze",
]
analysis_first = [
    "t_register", "t_split", "t_analyze",
    "t_waive_review", "t_join_waived", "t_authorize",
]

print("\nORIGINAL: authorization before analysis")
show_sequence(net, im, fm, early_authorization)

print("\nORIGINAL: analysis before authorization")
show_sequence(net, im, fm, analysis_first)

print("\nREPAIRED: the original bypass must be blocked")
try:
    show_sequence(
        repaired_net, repaired_im, repaired_fm, early_authorization
    )
except ValueError as exc:
    print("Blocked:", exc)
else:
    raise AssertionError("The repaired net still admits the original bypass.")

print("\nREPAIRED: waiver first, then mandatory analysis")
completed = show_sequence(
    repaired_net, repaired_im, repaired_fm,
    [
        "t_register", "t_split", "t_waive_review",
        "t_analyze", "t_join_waived", "t_authorize",
    ],
)
assert completed == repaired_fm
assert not pm4py.get_enabled_transitions(repaired_net, completed)
assert find_authorization_without_analysis(repaired_net, repaired_im) is None
```

| Check or property                        | Original                    | Repair A                               |
| ---------------------------------------- | --------------------------- | -------------------------------------- |
| Workflow-net check                       | Passes                      | Passes                                 |
| Soundness check                          | Rejects as unsound          | Expected to confirm soundness          |
| Initially enabled transition             | Only `t_register`           | Only `t_register`                      |

# 7. Repair Trade-Offs and Residual Risks

**Outcome distinguishability**

A preserves both visible transitions and their labels: `Perform Standard Review` and `Record Review Waiver`. Their separate completion places also preserve the selected route until synchronization. After either join reaches `p_decision`, the marking alone no longer identifies the route; the event history must retain that information.

B preserves those visible labels too, but deliberately merges the outcomes earlier into `p_review_done`. A dashboard must not interpret that place as proof that a standard review occurred.

A visible waiver transition models the recording action. It does not by itself establish that a durable waiver record exists, that required fields were completed, or that an authorized person recorded it. Those requirements need explicit execution controls and evidence.

**Silent transitions and duplicate behavior**

A adds no silent transition and no silent loop. Although its joins share `p_analysis_done`, they cannot both be enabled in a reachable marking: their other input places represent mutually exclusive review outcomes. There is therefore no duplicate authorization introduced by the repair.

B has additional internal ordering possibilities. After waiver, its forwarding transition may occur before or after analysis without changing the visible activity sequence. Such silent interleavings should not be counted as distinct business variants or mistaken for additional review work.

**Soundness is necessary, not sufficient**

Soundness alone does not prove alignment with every business expectation. Repair C illustrates this directly: it completes soundly but excludes the originally allowed waiver-before-analysis completion order.

Likewise, the model does not establish actual temporal overlap, resource availability, analysis quality, or waiver eligibility. Soundness establishes the option to complete within the modeled transition system—not a real-world deadline or guaranteed service execution.

**Regression tests**

The following are visible projections: `t_split` and the appropriate silent joins must be included by execution or explored when checking trace acceptance.

| Test category                               | Visible sequence or condition                                          | Expected result for A                            |
| ------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| Positive: analysis before standard review   | `t_register -> t_analyze -> t_standard_review -> t_authorize`          | Accepted; exact `repaired_fm`                    |
| Positive: standard review before analysis   | `t_register -> t_standard_review -> t_analyze -> t_authorize`          | Accepted; exact `repaired_fm`                    |
| Positive: analysis before waiver            | `t_register -> t_analyze -> t_waive_review -> t_authorize`             | Accepted; exact `repaired_fm`                    |
| Positive: waiver before analysis            | `t_register -> t_waive_review -> t_analyze -> t_authorize`             | Accepted; exact `repaired_fm`                    |
| Negative: missing analysis                  | `t_register -> t_waive_review -> t_authorize`                          | Authorization impossible                         |
| Negative: missing review outcome            | `t_register -> t_analyze -> t_authorize`                               | Authorization impossible                         |
| Negative: analysis only after authorization | `t_register -> t_waive_review -> t_authorize -> t_analyze`             | Authorization impossible at the offending prefix |
| Negative: both review outcomes              | Any execution containing both `t_standard_review` and `t_waive_review` | Impossible                                       |
| Negative: duplicate authorization           | Any execution containing two `t_authorize` firings                     | Impossible                                       |
| Negative: premature start                   | Analysis, review, or authorization before registration                 | Impossible                                       |

Incomplete but legal prefixes, such as registration followed by waiver, should be recognized as **in progress**, not rejected merely because they have not reached the final marking.

**Detecting an accidental analysis bypass**

Check the prefix property

$$
\forall \sigma\text{ reachable},\qquad
\#_{\texttt{t\_authorize}}(\sigma)
\leq
\#_{\texttt{t\_analyze}}(\sigma).
$$

For this one-execution-per-activity net, it expresses that analysis must already have occurred whenever authorization occurs. The helper in Section 6 specifically searches for its violation.

Do not restrict this check to accepted complete traces. The original net would misleadingly satisfy “all accepted authorizations have preceding analysis,” because its defective waiver executions never reach `fm`.

Also do not require a token in `p_analysis_done` at authorization time: the correct join has already consumed that token. Use execution history, a monitoring state, or equivalent reachability reasoning.

Finally, these conclusions are for the supplied **single-case** initial marking. A shared uncolored net initialized with several cases does not inherently prevent a join from combining different cases’ tokens. Deployment must preserve case isolation or case-aware token correlation.

# 8. Final Recommendation

**Deploy Repair A:** add `p_analysis_done -> t_join_waived`.

It is a globally minimum one-arc correction that preserves the complete stated policy: analysis remains mandatory, waiver and standard review remain alternatives, either branch may complete first, and authorization leaves exactly the final marking. The synchronization requirement is explicit at both joins, making the correction straightforward to audit.

**Use Repair B as the fallback** when the implementation architecture favors a single shared synchronization point. Its two-edit cost is justified by centralizing the authorization prerequisite. Preserve the waiver event, document the broader meaning of `p_review_done`, and ensure silent forwarding is not treated as additional business work.

Do not substitute Repair C without approving its stricter sequencing policy.

Before deployment, require both workflow-net and soundness checks, acceptance of all four positive visible traces, rejection of the negative traces, and an exhaustive prefix-level check for authorization without prior analysis. Completion must mean equality with the supplied final marking—not merely a token appearing in the sink.
