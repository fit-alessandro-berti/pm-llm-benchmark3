## 1. Target definition
**Primary target**: *Time-to-default after activation with right-censoring and competing risks*.
- **Prediction time**: At the *k*-th event (e.g., after 3 events or 7 days) of each application.
- **Horizon**: 90 days post-activation.
- **Unit of analysis**: Application (case).
- **Population**: All applications that reach *Account Activated* (excluding rejected/withdrawn/transferred/open cases).
- **Estimand**: Probability of default within 90 days of activation, conditioned on the prefix up to prediction time.

**Alternative target**: *Multi-state outcome* (Activated  Default/Non-Default/Rejected/Withdrawn/Transferred/Open).
- **Why different**: Answers "What is the likely final state of the application?" rather than "Will it default if activated?" This avoids counterfactual assumptions but requires modeling competing risks.

**Justification for primary target**:
- Aligns with business need (early warning for *activated* accounts).
- Explicitly acknowledges selection bias (only activated cases have observed defaults).
- Handles right-censoring (immature cases) and competing risks (transfers/rejections).

---

## 2. Cohort construction
**Inclusion**: All 48,000 applications started between 1 Jan 2024–31 Dec 2025.
**Exclusion**: None (all cases are analyzed under their observed outcomes).
**As-of rule**: Prefixes are extracted at prediction time (e.g., after 3 events or 7 days), using only events  prediction time.

**Cohort-flow table**:
| **Group**                     | **Count** | **Label Status**               |
|-------------------------------|----------|--------------------------------|
| Activated + matured           | 21,600   | Labeled (default/non-default)  |
| Activated + immature          | 3,600    | Right-censored                 |
| Rejected                      | 9,100    | Competing outcome (no default) |
| Withdrawn                     | 5,700    | Competing outcome             |
| Transferred (60% linked)     | 2,900    | Partially observed             |
| Still-open                    | 5,100    | Right-censored                 |

**Notes**:
- Transferred cases are treated as competing risks (not non-defaults).
- Open cases are censored at extraction date (15 Feb 2026).

## 3. Censoring and missing-label strategy
**Primary strategy**:
- **Right-censoring**: Immature activated cases (3,600) and open cases (5,100) are censored at their last observed time.
- **Competing risks**: Rejected/withdrawn/transferred cases are modeled as absorbing states (not defaults).
- **Delayed labels**: For activated cases with missing feeds (partner-originated), treat as right-censored if no outcome by extraction date.

**Sensitivity analysis**:
- Assume all censored cases are non-defaults (optimistic bias).
- Assume all censored cases are defaults (pessimistic bias).

**Assumptions**:
- *Testable*: Policy change effects (post-1 July 2025) can be validated temporally.
- *Untestable*: Counterfactual default risk for rejected cases (no activation).

---

## 4. Prefix extraction
**Approach**:
- Use `pm4py.get_prefixes_from_log` with `max_length=3` (fixed event count) or `max_time=7d` (elapsed time).
- **Handling loops**: Document request loops are preserved in prefixes (no truncation).
- **Activity renaming**: Map renamed activities (post-15 Oct 2025) to pre-migration names using a lookup table.
- **Short cases**: Cases with <3 events are padded with `NA` or excluded if <1 event.

**As-of safeguards**:
- Filter events in prefixes to `time:timestamp  prediction_time`.
- Drop columns like `final_limit` (post-activation) or `collection_status` (post-default).

## 5. Process-aware features
**Static case attributes**:
- `case:requested_amount`, `case:region`, `case:channel`.

**Prefix-derived features**:
- Control-flow: `pm4py.discover_dfg` (frequency of paths in prefix).
- Timing: `pm4py.extract_temporal_features_dataframe` (e.g., time since last event).
- Rework: Count of `Identity/KYC Check`  `Credit Review` loops.
- Resource: `org:resource` experience (at event time, not extraction time).

**Historical reference data**:
- Aggregated risk scores from past cases (if available).

## 6. Leakage audit

| **Feature/Data Element**      | **Leakage/Bias Risk**               | **Valid Availability Rule**               | **Keep/Repair/Drop** | **Rationale**                          |
|-------------------------------|-------------------------------------|-------------------------------------------|----------------------|----------------------------------------|
| `final_limit`                 | Post-activation leakage             | Only after Contract Signed                | Drop                 | Not available at prediction time       |
| `decision_reason`             | Post-decision leakage               | Only after Accept/Reject                  | Drop                 | Future information                     |
| `collection_status`           | Post-default leakage                | Only after Account Activated              | Drop                 | Directly reveals outcome               |
| Future events                 | Temporal leakage                    | `time:timestamp  prediction_time`        | Drop                 | Violates as-of principle               |
| `documents_total`             | Same-day leakage                    | Use snapshot *before* prediction time      | Repair (lag)         | May include future docs                |
| `risk_score` (updated)        | Lookahead bias                      | Use last value  prediction time          | Keep (with lag)      | Valid if timestamped                   |
| Resource experience           | Extraction-time bias                | Use experience at event time              | Repair (join historical) | Current value is misleading       |
| `label_available_at`          | Label maturity bias                 | Only for activated cases                  | Keep (for censoring) | Needed to identify censored cases      |

## 7. Validation design
**Temporal split**:
- Train: Cases started 1 Jan 2024–30 Jun 2025 (pre-policy change).
- Validation: 1 Jul 2025–30 Sep 2025 (post-policy, pre-migration).
- Test: 1 Oct 2025–31 Dec 2025 (post-migration).

**Metrics**:
- For primary target: Concordance index (C-index) for survival analysis.
- For multi-state: Macro F1 across states.
- Calibration: Compare predicted vs. observed default rates in bins.

**Why not random split**:
- Policy/migration changes induce distribution shift.
- Label maturity varies over time (immature cases in test).

**Subgroup analysis**:
- Stratify by `case:region`, `case:channel`, and pre/post-policy.

---

## 8. Limitations and decision-use boundary
**Claims**:
- The model predicts default risk *conditional on activation*.
- It does not estimate counterfactual default risk for rejected cases.

**Cannot claim**:
- Causal effect of credit review on default (selection bias).
- Performance on transferred cases (missing linkage).

**Deployment risks**:
1. **Feedback loop**: Model may influence activation decisions, changing the data-generating process.
2. **Concept drift**: Post-2026 policy changes may invalidate assumptions.
3. **Label delay**: External feeds may introduce latency, requiring re-training.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py
from datetime import timedelta

# --- CONFIG ---
PRED_TIME = timedelta(days=7)  # Prediction horizon after case start
MAX_PREFIX_LEN = 3             # Max events per prefix
CUTOFF_DATE = pd.Timestamp("2026-02-15")
TRAIN_END = pd.Timestamp("2025-06-30")
VAL_END = pd.Timestamp("2025-09-30")

# --- LOAD DATA ---
df = pd.read_csv("applications_events.csv", parse_dates=["time:timestamp"])
df = pm4py.format_dataframe(df, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")

# --- CASE-LEVEL OUTCOMES ---
# Identify terminal states (as of CUTOFF_DATE)
activated = df[df["concept:name"] == "Account Activated"]["case:concept:name"].unique()
defaulted = df[df["default_90d"] == True]["case:concept:name"].unique()
rejected = df[df["concept:name"] == "Rejected"]["case:concept:name"].unique()
withdrawn = df[df["concept:name"] == "Withdrawn"]["case:concept:name"].unique()
transferred = df[df["concept:name"] == "Transferred"]["case:concept:name"].unique()
open_cases = df[df["time:timestamp"] > CUTOFF_DATE]["case:concept:name"].unique()

# --- COHORT FLOW ---
print(f"Total cases: {df['case:concept:name'].nunique()}")
print(f"Activated + labeled: {len(activated & defaulted)} defaults, {len(activated - defaulted)} non-defaults")
print(f"Rejected: {len(rejected)}, Withdrawn: {len(withdrawn)}, Transferred: {len(transferred)}, Open: {len(open_cases)}")

# --- PREFIX EXTRACTION ---
# Filter events up to prediction time (case start + PRED_TIME)
df["case_start"] = df.groupby("case:concept:name")["time:timestamp"].transform("min")
df["prediction_time"] = df["case_start"] + PRED_TIME
prefix_df = df[df["time:timestamp"] <= df["prediction_time"]]

# Get prefixes (max length = MAX_PREFIX_LEN)
prefixes = pm4py.get_prefixes_from_log(prefix_df, max_length=MAX_PREFIX_LEN)

# --- FEATURE ENGINEERING ---
# Static features (e.g., requested amount)
static_features = df.drop_duplicates("case:concept:name")[["case:concept:name", "case:requested_amount", "case:region"]]

# Temporal features (e.g., time between events)
prefixes = pm4py.insert_case_service_waiting_time(prefixes, case_id_key="case:concept:name", timestamp_key="time:timestamp")

# --- LEAKAGE AUDIT ---
leakage_check = {
    "final_limit": ("Drop", "Post-activation"),
    "collection_status": ("Drop", "Post-default"),
    "documents_total": ("Repair", "Same-day leakage risk")
}
print("Leakage audit:", leakage_check)

# --- TEMPORAL SPLIT ---
train_cases = df[df["case_start"] <= TRAIN_END]["case:concept:name"].unique()
val_cases = df[(df["case_start"] > TRAIN_END) & (df["case_start"] <= VAL_END)]["case:concept:name"].unique()
test_cases = df[df["case_start"] > VAL_END]["case:concept:name"].unique()
```
