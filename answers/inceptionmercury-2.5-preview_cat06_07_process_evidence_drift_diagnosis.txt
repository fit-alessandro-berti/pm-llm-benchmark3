## 2. Competing explanations and timeline

**January–March:** The system operates baselined. Variants (V1–V3) stable, label maturity 100%, and metrics consistent. No drift.

**April:** The decline is primarily a data-pipeline failure. The workflow-system migration renamed `Initial Diagnosis Completed`, causing feature pipeline breaks (17% unknown activity, 14% missing features). Predictions used wrong events, collapsing AUROC (0.810.67). This is not genuine concept drift.

**May:** Partial recovery. Mapping patches deployed, unknown activity fell to 2%, but some cached features were not recomputed. Metrics improved (AUROC 0.78) but remained slightly degraded.

**June:** A real process/mix change occurred due to the remote-routing policy. V2 share rose to 52%, lowering observed breach rate (0.15). However, AUROC remained stable (0.79), suggesting the model handled the variant shift; no recalibration needed solely for this.

**July–August:** Supplier performance drifted significantly. Median `Order Part  Part Received` time grew from 65h (July) to 130h (August). This created a genuine concept shift for V3 cases, where mature breach rates jumped to 0.64. This is process-driven concept drift.

**September:** Population shift overlapped process issues. Partner Z (24% cases) arrived, routing more cases through V3 and rural paths. Observed breach rate (0.31) reflects mix change, not just model failure. Label maturity dropped to 82% due to longer paths.

**October:** Severe label censoring. API backlog left only 55% of labels matured. Observed breach rate (0.16) is artificially low because long-resolution cases are not yet labeled. Comparing October to mature months is invalid.

## 3. Diagnostic tests

1.  **Label-maturity curves and fixed-vintage backtesting**
    *   *Test:* Track breach rates for Jan–Oct cohorts at fixed delays (e.g., 90 days post-case).
    *   *Expected:* Sep/Oct rates rise over time; Aug rate stabilizes at 0.64.
    *   *Hypothesis A (Censoring):* Oct observed rate will increase as backlog clears.
    *   *Hypothesis B (Concept Change):* Aug rate stabilizes; Oct does not rise significantly.

2.  **Recomputation after activity-label normalization and duplicate cleaning**
    *   *Test:* Re-run pipeline on Apr–May logs with corrected mapping and deduplication.
    *   *Expected:* Unknown activity drops to ~0.2%; features align with Jan baseline.
    *   *Hypothesis A (Pipeline Bug):* Metrics match pre-April levels.
    *   *Hypothesis B (Model Failure):* Metrics remain poor post-computation.

3.  **Calibration and discrimination stratified by variant, source, and month**
    *   *Test:* Calculate ECE and AUROC for V1, V2, V3 separately.
    *   *Expected:* V3 ECE degrades significantly in Aug/Sep; V1/V2 stable.
    *   *Hypothesis A (Concept Drift):* V3 ECE remains poor even after feature fixes.
    *   *Hypothesis B (Population Shift):* V3 ECE recovers when adjusting for Z share.

4.  **Comparison of process variants and DFG/performance-DFG edges**
    *   *Test:* Extract DFG edges for all months; isolate `Order Part  Part Received` duration.
    *   *Expected:* V3 median duration doubles in Aug/Sep/Oct vs Jan.
    *   *Hypothesis A (Process Drift):* DFG edge time matches breach rate rise.
    *   *Hypothesis B (Randomness):* Edge time is stable while breach rates fluctuate.

5.  **Tests of whether the outcome relationship conditional on the same path changed**
    *   *Test:* Compare breach rate for V3 cases with identical `Order Part` duration in Jan vs. Aug.
    *   *Expected:* Breach rate increases for same duration (Aug > Jan).
    *   *Hypothesis A (Concept Drift):* Same duration yields higher breach probability.
    *   *Hypothesis B (Process Drift only):* Same duration yields same probability.

6.  **Population reweighting or transport-style checks for Partner Z**
    *   *Test:* Apply inverse probability weighting to Sep/Oct data to match Jan population mix.
    *   *Expected:* Weighted breach rate aligns with historical baselines.
    *   *Hypothesis A (Population Shift):* Model is correct; distribution changed.
    *   *Hypothesis B (Model Failure):* Weighted performance still poor.

7.  **Feature missingness and lineage audits**
    *   *Test:* Audit feature generation logs for Apr–May; count records missing `queue` feature.
    *   *Expected:* High missingness in Apr/May; resolves post-patch.
    *   *Hypothesis A (Pipeline Bug):* Missingness correlates with metric drops.
    *   *Hypothesis B (External Change):* Missingness stable while metrics change.

## 4. Recalibration-versus-retraining decision

**Immediate Containment:** Freeze model updates for October. Observed breach rate is censored; using it for training will introduce label noise. Continue serving predictions with a warning flag.

**Short-Term Recalibration:** Perform calibration (e.g., Platt scaling) using January–June data where labels are mature and pipelines were stable. This stabilizes outputs for V1/V2 before full retraining.

**Feature Repair:** Re-process April–May data with corrected event mappings and duplicate removal. Do not train on April predictions. Include new features for Partner Z attributes (rural travel, device age).

**Full Retraining:**
*   **Safe Data:** January–July (after pipeline fixes).
*   **Unsafe Data:** October (immature labels). August–September (concept/population shifts).
*   **Strategy:** Train a variant-specific model or a segmented model (V1/V2 vs V3) to handle concept drift in the parts-dependent path without affecting standard routing.

## 5. Monitoring architecture

**Design:**
1.  **Predictive Monitor:** AUROC/Brier (weekly). Threshold: drop >0.1 triggers investigation.
2.  **Calibration Monitor:** ECE by variant. Alert if ECE >0.10.
3.  **Label-Maturity Monitor:** % matured labels at cutoff. Alert if <90%.
4.  **Data-Quality Monitor:** Unknown activity share, missing features, duplicate rate.
5.  **Process-Variant Monitor:** V1/V2/V3 distribution changes.
6.  **Performance-DFG Monitor:** Median edge times (`Order Part  Part Received`).
7.  **Population Monitor:** Partner Z case share.
8.  **Intervention Monitor:** Retraining status (blocked if label maturity <90%).

**Dependencies:** Label-maturity alarm must block Retraining trigger. Data-quality alarm blocks Feature-Input validation.

```python
import pandas as pd
import pm4py

def extract_monthly_process_evidence(csv_path):
    """
    Extracts auditable monthly summaries from field_service_events.csv.
    """
    df = pd.read_csv(csv_path)
    
    # 1. Normalize renamed diagnosis labels
    df['activity'] = df['activity'].replace({
        'Diagnostic Assessment Completed': 'Initial Diagnosis Completed'
    })
    
    # 2. Handle duplicate events (keep latest timestamp per case/activity)
    df = df.sort_values(['case_id', 'timestamp']).drop_duplicates(
        subset=['case_id', 'activity'], keep='last'
    )
    
    # 3. Convert to event log format
    log = pm4py.format_dataframe(df, case_id='case_id', activity_key='activity', timestamp_key='timestamp')
    
    summaries = []
    months = df['timestamp'].dt.strftime('%Y-%m').unique()
    
    for month in sorted(months):
        cohort = log[pm4py.filter_time_range(log, month, month)]
        
        # 4. Case-start vs event-calendar cohorts
        start_events = cohort[cohort['activity'] == 'Case Created']
        
        # 5. Discover DFG and variants
        dfg = pm4py.discover_dfg(cohort)
        variants = pm4py.get_variants(cohort)
        
        # 6. Extract temporal features (e.g., duration)
        temporal_features = pm4py.extract_temporal_features_dataframe(cohort)
        
        # Calculate key metrics
        breach_rate = (cohort['outcome'] == 'Breach').mean() if 'outcome' in cohort.columns else None
        v3_share = (cohort['variant'] == 'V3').mean() if 'variant' in cohort.columns else None
        
        summaries.append({
            'month': month,
            'start_cases': len(start_events),
            'breach_rate': breach_rate,
            'v3_share': v3_share,
            'variant_count': len(variants)
        })
    
    return pd.DataFrame(summaries)
```

## 6. Risks of acting on the wrong diagnosis

1.  **Retraining on immature labels:** Training on October data where 45% of labels are pending will teach the model to predict breaches for short-term resolved cases while ignoring long-term risks.
    *   *Mitigation:* Enforce a strict 90% label-maturity threshold before any dataset is included in training.

2.  **Calibrating around a pipeline bug:** If you recalibrate on April–May data, you are fitting to systematic errors caused by event renaming.
    *   *Mitigation:* Exclude April–May from calibration datasets; verify pipeline backfills before use.

3.  **Ignoring genuine supplier-driven concept drift:** Treating August’s breach rise as a "data problem" instead of a process reality might lead to ignoring the supplier contract.
    *   *Mitigation:* Trigger operational reviews (not just model reviews) when V3 DFG edge times exceed SLAs.

4.  **Attributing Partner Z shift to unfair behavior:** Assuming the model is biased against Partner Z without evidence, then forcing bias corrections that degrade performance for all rural cases.
    *   *Mitigation:* Validate model performance for Partner Z independently; use feature augmentation rather than model modification.
