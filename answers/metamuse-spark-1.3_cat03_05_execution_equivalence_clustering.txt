## 1. Equivalence design space

We fix a lead object `o* : Order`. An execution `X(o*)` is the set of events related to `o*`, the set of objects co-related to those events (including `EXT-*` objects centered on another Order), E2O incidence with qualifiers if present, and O2O relations with qualifiers.

### R1. Activity-sequence equivalence

**Definition:** Let `trace(o*) = [act(e1),...,act(en)]` ordered by timestamp, ties broken deterministically. `X ~seq Y` iff their traces are equal as sequences.

Operationally: project each execution to list of activity labels, compare with `==`.

**Preserved:** ordered activity labels, trace length, repetition count e.g. two `Pack Package` vs one, two `Record Payment` vs one, presence of `Return Item / Inspect Return`.

**Discarded:** all objects: types, identifiers, multiplicities, `EXT` flags, E2O/O2O relations and qualifiers, timestamp distances, attribute values. In particular E2O arity is lost: `Dispatch{Order;Package;Delivery}` and `Dispatch{Order;Item;Package;Delivery}` have same label.

**RST:** Yes, reflexive, symmetric, transitive. It is equality of a derived string.

**Concurrency:** Fragile. If two events have identical timestamps, total-order listing imposes an arbitrary linear extension. Two defensible repairs: (a) sort same-timestamp events lexicographically by activity and compare, (b) treat same-time slice as multiset and compare slices in order. Without this, `Pack P41; Dispatch D41; Pack P42` vs interleavings can spuriously distinguish cases.

R1 alone is **not object-centric**.

### R2. Typed structural equivalence under identifier renaming

**Definition:** `X ~struct Y` iff there exists a bijection `fO: ObjX -> ObjY` and `fE: EvX -> EvY` such that:

- `type(fO(o))=type(o)`, `isEXT(fO(o))=isEXT(o)`;
- `act(fE(e))=act(e)` and timestamp order is preserved: `e1<e2 => fE(e1)<fE(e2)`;
- E2O preserved: `(e,o)` present in X iff `(fE(e),fO(o))` present in Y, with same E2O qualifier if any, and same object-type grouping;
- O2O topology among objects in the execution preserved with qualifiers, e.g. `packs, carries, bills, settles, replaces, removed_before_dispatch`.

This is labelled graph isomorphism of the event-object bipartite graph plus O2O edges, respecting order labels.

**Preserved:** activities in order, object types, per-event multiplicities per type e.g. `Pack:1 Order+2 Item+1 Package` vs `1 Order+1 Item+1 Package`, cross-event identity: that the same `P11` packed and dispatched, `EXT` vs local distinction, O2O qualifiers.

**Discarded:** raw local identifiers `O1 vs O2, I11 vs I22, P11 vs P21`, timestamp magnitudes, item-addition identifier order when activity labels identical, attribute payloads like amounts.

**RST:** Yes. Identity gives reflexivity, inverse gives symmetry, composition gives transitivity. Strictly an equivalence relation.

**Concurrency:** As defined with total order it over-distinguishes concurrent packings. Robust variant `~struct-partial`: replace total order by partial order `e1 precedes e2` if `time(e1)<time(e2)` and not same-time, plus causal constraint `Pack(P) < Dispatch(P)` for same package. Then require DAG isomorphism. This would equate different linear extensions of concurrent `Pack P31 / Pack P32`.

### R3. Business-semantic equivalence (preferred)

**Definition:** `X ~biz Y` iff their business-feature signatures `B(X)=B(Y)`, where `B` is:

```
B = (
  log_isolated: bool,  // no EXT-Order/Item in Pack/Dispatch
  fin_isolated: bool,  // no EXT-Order in Issue/Record
  n_pack_events, n_distinct_packages, items_per_package: multiset,
  n_deliveries, packages_per_delivery: multiset,
  n_invoices, orders_per_invoice,
  n_payments, payments_per_invoice,
  qualifiers: {removed_before_dispatch?, partial_settlement?, repack_replaces?},
  motifs: {substitution?, return_inspect_repack?}
)
```

Two executions are equivalent if all components match. In practice this is stricter than R1 but intentionally coarser than raw-identifier equality and interpretable: it keeps multiplicities, externality, qualifiers and lifecycle motifs, discards local naming and exact interleaving that does not change causal packaging.

**Preserved:** isolated vs pooled logistics/finance, fragmentation counts, qualifier semantics, rework loop.

**Discarded:** local ids, which of `I11/I12` added first, exact timestamps, lexicographic package numbers, whether split packs were `P31 then P32` or reverse if causal dispatch constraints hold.

**RST:** Yes, equality on derived vector, hence reflexive, symmetric, transitive.

**Concurrency:** Handled by counts and causal multisets, not linear extension. `Pack P41;Dispatch D41;Pack P42;Dispatch D42` signature records `2 packs, 2 deliveries, 1:1 mapping`, invariant to shifting second pack before first dispatch as in X3 vs X4 only if mapping preserved. Same-time `Pack` events collapse to `n_pack_events=2`.

### R4. Outcome / reporting equivalence (coarse, auxiliary)

**Definition:** `X ~outcome Y` iff `delivered(o*)=delivered` and `settled(o*)=settled` in terms of order-level coverage, ignoring how: number of packages/deliveries/payments, sharing, rework collapsed.

Useful to show why finest is not best: all X1-X8 are delivered and paid at order level, so R4 puts all in one cluster. It preserves business outcome, discards everything else. RST holds. Concurrency irrelevant. We do not recommend it for compliance, but it is the right grain for KPI reporting.

## 2. Canonical signatures

Reproducible scheme for R3, invariant to local renaming, sensitive to types, multiplicities, externality, order/partial order, E2O, O2O qualifiers, repetitions.

Idea: deterministically rename local objects, then hash ordered event patterns + O2O qualifier multiset + motif detectors.

```python
def canonical_signature(exec, lead_id):
    # exec: events sorted by (time, activity, id)
    # each event: {act, e2o: [(otype, oid, e2o_qual)]}
    # o2o: [(otype1, oid1, qual, otype2, oid2)]
    # 1. classify objects
    obj_type = {}  # oid -> otype
    is_ext = lambda oid: oid.startswith("EXT-")
    for e in exec.events: 
        for otype, oid, _ in e.e2o:
            obj_type[oid] = otype
    # 2. deterministic renaming of locals: order by (otype, first_appearance, degree)
    first = {}; deg = {}
    for idx, e in enumerate(exec.events):
        for _, oid, _ in e.e2o:
            first.setdefault(oid, idx)
            deg[oid] = deg.get(oid, 0) + 1
    locals_sorted = sorted([o for o in obj_type if not is_ext(o)],
                           key=lambda o: (obj_type[o], first[o], deg[o], o))
    canon = {o: f"{obj_type[o]}#{i}" for i, o in enumerate(locals_sorted)}
    # EXT kept as EXT-<otype>-<role-index> by first appearance, not raw id
    # 3. event pattern in (partial-)order
    pattern = []
    for e in exec.events:
        # count per (otype, ext_flag)
        cnt = {}
        for otype, oid, q in e.e2o:
            key = (otype, "EXT" if is_ext(oid) else "LOC", q)
            cnt[key] = cnt.get(key, 0) + 1
        # canonical incidence: sorted list to be order-invariant within event
        inc = tuple(sorted(cnt.items()))
        pattern.append((e.act, inc))
    # optionally compress to partial order: keep causal edges Pack(P)->Dispatch(P)
    # via same canon package identity; here we keep total order for R2,
    # but derive multiset features for R3:
    feats = {
      "log_isolated": no EXT in Pack/Dispatch events,
      "fin_isolated": no EXT in Issue/Record events,
      "n_pack": count(act=="Pack Package"),
      "items_per_pack": sorted([items in each Pack]),
      "n_dispatch": count(act=="Dispatch"),
      "packs_per_dispatch": sorted([...]),
      "n_pay": count(act=="Record Payment"),
      "quals": sorted(set(q for o2o quals + e2o quals)),
      "has_return_loop": ("Return Item" in acts and "Pack Package" after return),
      "has_removed": ("removed_before_dispatch" in quals),
    }
    # 4. O2O qualifier multiset with canon types (not ids)
    o2o_sig = sorted([(obj_type[a], q, obj_type[b]) for a,q,b in exec.o2o])
    return (tuple(pattern), tuple(o2o_sig), tuple(sorted(feats.items())))
```

Properties: local `I11 vs I22` map to `Item#0, Item#1` identically; `EXT-OA` stays `EXT`; repeated `Pack` yields repeated pattern entries; qualifiers preserved; same-time events can be grouped into a frozenset slice before tuple conversion to implement partial-order variant.

## 4. Cluster interpretations

**SEM-Clean (X1,X2). Signature:** `isolated_log=T, isolated_fin=T, packs={[2]}, deliveries={[1]}, pays={[1]}, quals={packs,carries,bills,settles}, motifs={}`. Business: standard pick-pack-dispatch-bill-collect with full quantity correspondence. Risks/opportunities: low handling cost, baseline for SLA benchmarking, automation candidate. Flattening: Order-flattened log represents well; Package- or Delivery-flattened also single row. Stable under repair: swapping Add order, renaming ids, removing duplicate timestamp tie does not change cluster.

**SEM-SplitConsol (X3). Signature:** `packs={[1],[1]}, deliveries={[P31,P32]}, pays={[1]}`. Business: line-level split packing e.g. size/warehouse constraint but consolidated shipment. Cost: extra pack handling but single delivery cost. Risk: mispick per package; opportunity: bin optimization. Flattening: Order-flattening hides two packs (needs Pack count); Package-flattening splits into two traces losing consolidation. Stable: yes, unless second Pack imputed as duplicate and deduplicated.

**SEM-SplitFrag (X4). Signature:** `packs={[1],[1]}, deliveries={[P41],[P42]}, pays=2 {partial,complete}`. Business: fragmented fulfilment with staggered shipment and split settlement. Risk: double shipping cost, partial-payment dunning complexity, customer experience split. Opportunity: faster partial delivery. Flattening: Order-flattening shows interleaved Pack/Dispatch correctly but loses 1:1 pack-delivery mapping without O2O; Payment-flattening needed to see partial vs complete. Stable only if payment multiplicity kept as structure; if converted to amount attribute, merges toward X3.

**SEM-SharedLog (X5). Signature:** `log_isolated=F (Pack: O5+EXT-OA, I51+I52+EXT-IA), fin_isolated=T`. Business: pooled packing/delivery across orders, e.g. same carrier bin. Risk: cost allocation, liability if shared package lost, cross-order delay coupling, privacy. Opportunity: transport consolidation. Flattening: single-Order projection falsely suggests isolated execution; must keep EXT objects or joint connected component. Unstable if external objects filtered as noise: collapses to SEM-Clean incorrectly.

**SEM-SharedFin (X6). Signature:** `log_isolated=T, fin_isolated=F (V61 bills O6+EXT-OB, M61 unallocated)`. Business: joint invoice, e.g. corporate account. Risk: order-level DSO/credit misstatement, unallocated payment reconciliation, compliance for revenue recognition. Opportunity: reduced invoicing cost. Flattening: Order-flattening duplicates invoice/payment to each order, overstating receivables unless allocation rule added. Stable if EXT retained; collapses to SEM-Clean if EXT ignored.

**SEM-Substituted (X7). Signature:** `like Clean + Dispatch arity includes Item + qual removed_before_dispatch`. Business: one item substituted/removed after packing but before dispatch; invoice may over-bill if based on pack. Risk: billing dispute, inventory mismatch, hidden stockout. Flattening: Order-flattening and even E2O without qualifiers show X1-identical trace; qualifier-aware O2O essential. Borderline stable: if qualifier dropped, merges to SEM-Clean; if Dispatch-Item link treated as noise, same merge. Hence compliance must preserve qualifiers.

**SEM-Rework (X8). Signature:** `Return Item + Inspect Return + second Pack/Dispatch, O2O replaces P81->P82 for I82`. Business: post-delivery return, inspection, repack, redelivery; closed loop. Risk: reverse-logistics cost, quality signal, second delivery failure. Opportunity: refurbish/resell. Flattening: Order-flattening preserves long sequence but Package-flattening fragments into P81 vs P82 without `replaces` link; Delivery-flattening splits D81/D82. Stable if Return/Inspect activities kept; collapses toward SplitFrag if Return/Inspect collapsed as generic events.

Coarser business views are defensible: `SEM-SplitConsol + SEM-SplitFrag = Fragmented fulfilment`; `SEM-SharedLog + SEM-SharedFin = Non-isolated execution`. We keep them separate in preferred clustering because delivery/payment fragmentation and logistics vs finance sharing imply different owners and controls.

## 5. Borderline cases

**X1 vs X2:** Under R1 and R2/R3 they are equivalent. Defensible disagreement: raw-identifier equality (`pm4py` exact key without canonicalization, see §6) separates them because `I11/I12` vs `I21/I22` and `P11 vs P21` differ as strings, plus Add-item identifier order differs. Canonicalized isomorphism merges them. Business view must merge: identifier order is data-entry order, not business difference. Keeping them separate would be overfitting to surrogate keys.

**X1 vs X5:** Under R1 they merge (identical 7-label sequence). Under R2/R3 they split: Pack has `2 Orders, 3 Items` vs `1 Order, 2 Items`, Dispatch carries shared package. One definition says same process variant; another says isolated vs pooled logistics. Flattened to Order, X5 looks like X1; on full OCEL with EXT, costs/risks differ. This is the canonical example why label-only clustering is not object-centric.

**X1 vs X6:** Same pattern mirrored to finance. R1 merges; R2 splits on `Issue Invoice` arity `2 Orders vs 1`; R3 splits as `fin_isolated`. A payment-amount view that treats `M61` amount as covering two orders could even argue X6 is normal if allocation existed, but supplied O2O says `without order-level allocation`, so settlement semantics differ. Ignoring EXT merges; preserving EXT splits.

**X1 vs X7:** R1 merges; even E2O-count-insensitive structural check merges. R2 with E2O arity splits because Dispatch in X7 carries explicit `Item:I72` link; R3 splits decisively on qualifier `removed_before_dispatch` and substitution motif. One view says identical happy path; qualifier-aware view says impaired fulfilment with billing risk. This shows O2O qualifiers can outweigh label identity for compliance.

**X3 vs X4:** R1 splits (8 vs 10 events), R2 splits, R3 splits (our preferred). Disagreement arises under coarser operational segmentation: both are `multi-package` vs single-package baseline, so a 2-valued feature `split_pack?` merges them. Similarly if payment multiplicity is demoted to amount attribute (`€100 in 1 vs 2 instalments`) and delivery consolidation ignored, they merge. We keep separate because `1 delivery/1 pay vs 2 deliveries/2 pays` changes cost and dunning. Partial-order view does not merge them either because pack-delivery mapping `2:1 vs 1:1+1:1` differs.

**X4 vs X8:** Both have `2 Packs, 2 Dispatches` and extended traces, tempting to merge as `fragmented delivery`. R1 splits (Return/Inspect present only in X8, 10 vs 11 events), R2 splits on activity set and O2O `replaces`, R3 splits as `staggered fulfilment vs rework loop`. A definition that collapses repeated same-label events (see §7) still keeps them separate because Return/Inspect remain, but a definition that ignores Return as `logistics noise` or treats second Pack/Dispatch as generic split would merge. Business semantics must not merge: X4 is planned split, X8 is unplanned reverse logistics with quality implication.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py's exact clustering builds, per lead object (`Order`), the connected execution: events related to the Order plus co-related objects, and derives a string/tuple key per execution roughly:

```
key(o*) = tuple( (act(e), sorted((otype, oid, e2o_qual) for o in E2O(e))) for e in time-order )
          + tuple(sorted O2O edges with oids if included)
```

What it preserves: full ordered activity list, exact E2O incidence including raw `oid` strings and per-event multiplicities, repetitions. Depending on parameters it may include O2O edges/qualifiers or not, but by default it is identifier-sensitive and total-order-sensitive.

Why raw ids make clusters too fine: `X1` key contains `I11,I12,P11,D11,V11,M11`, `X2` contains `I22,I21,P21,...`. Even after sorting within event, keys differ, so exact clustering returns singletons where business sees duplicates. Similarly `P31 vs P41` splits X3/X4 further than needed, and timestamp tie order can split concurrent packs. Large `EXT` fan-in explodes keys.

Canonicalize/post-process: rename locals per execution before keying, retain EXT flag, optionally abstract to counts/qualifiers, then cluster on canonical key and optionally aggregate to business features.

When exact equivalence is preferable: for audit reproducibility, deduplication, caching, regression testing of extraction pipelines, and proving that two executions are byte-identical. For operational segmentation and root-cause, coarser R3 is preferable to avoid hundreds of singleton variants differing only by surrogate keys.

`max_objs` / large components: if `Pack P51` connects `O5+EXT-OA`, the connected component for `O5` includes another Order's subgraph. Without bound, one component can swallow many orders (giant component), making per-lead executions huge and clustering infeasible. `max_objs` truncates traversal, but truncation can cut `EXT-IA` or second delivery, silently moving X5Clean or X4X3. Must log truncation and treat truncated executions as `uncertain`.

```python
import pm4py

# ocel: OCEL 2.0 with Order as lead type
lead_type = "Order"

# 1. exact identifier-sensitive clustering (baseline, too fine)
exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel, object_type=lead_type, max_objs=100
)  # dict: cluster_key -> list[lead_oid]  (API shape version-dependent)

# 2. custom canonicalization: rename locals, keep EXT flag, keep quals
def canonical_key_for_lead(ocel, lead_oid):
    exec_view = pm4py.filter_ocel_connected(ocel, lead_oid)  # conceptual helper
    # reuse function from §2
    return canonical_signature(exec_view, lead_oid)

canon_to_leads = {}
for oid in ocel.objects[ocel.objects["ocel:type"]==lead_type]["ocel:oid"]:
    k = canonical_key_for_lead(ocel, oid)
    canon_to_leads.setdefault(k, []).append(oid)

# 3. aggregate to business-semantic clusters (R3)
def to_biz(canonical_key):
    pattern, o2o_sig, feats = canonical_key
    feats = dict(feats)
    # coarse business rules
    if not feats["log_isolated"] and feats["fin_isolated"]:
        return "SEM-SharedLog"
    if feats["log_isolated"] and not feats["fin_isolated"]:
        return "SEM-SharedFin"
    if feats["has_return_loop"]:
        return "SEM-Rework"
    if feats["has_removed"]:
        return "SEM-Substituted"
    if feats["n_pack"]>1 and feats["n_dispatch"]==1:
        return "SEM-SplitConsol"
    if feats["n_pack"]>1 and feats["n_dispatch"]>1 and not feats["has_return_loop"]:
        return "SEM-SplitFrag"
    return "SEM-Clean"

biz_clusters = {}
for k, leads in canon_to_leads.items():
    biz_clusters.setdefault(to_biz(k), []).extend(leads)
print(biz_clusters)
```

## 7. Robustness analysis

**Ignore all O2O qualifiers:** X1 vs X7 merge. `removed_before_dispatch P71->I71`, `partially_settles/completes_settlement`, `replaces P81->P82` lost. SEM-Substituted collapses to SEM-Clean; SEM-SplitFrag vs SEM-SplitConsol distinction weakens to delivery/payment counts only; SEM-Rework still distinct via Return/Inspect activities but loses repack semantics. Compliance impact severe: substitution hidden.

**Ignore external objects (drop EXT-OA/OB, EXT-IA):** X5SEM-Clean (Pack appears `1 Order+2 Items`), X6SEM-Clean (Invoice appears single-order). Shared-resource risks disappear. This is what Order-flattened logs do by default. Robust only if research question is strictly intra-order flow; misleading for cost allocation and delay attribution.

**Collapse repeated same-label events (deduplicate consecutive or all repeats to one):** X3 `Pack,PackPack` merges toward X1 at label level; X4 `Pack...PackPack`, `Dispatch...DispatchDispatch`, `Pay,PayPay` merges toward X3/X1. Counts essential to R3 lost. X8 `Pack...PackPack` still distinct due to Return/Inspect, but fragmentation signal lost. Defensible only for outcome reporting (R4), not for operations.

**Pack/Dispatch total order  partial order:** X1,X2,X5,X6,X7 unaffected (single Pack/Dispatch). X3 internal order of `Pack P31/P32` becomes irrelevant — desirable robustness to concurrency. X3 vs X4 remain distinct because causal mapping differs: X3 has `P31,P32  D31` (many-to-one), X4 has `P41D41, P42D42` (one-to-one staggered) plus payment split. However if partial-order abstraction also abstracts mapping to mere counts `2 packs, 1 vs 2 dispatches`, X3/X4 still split on delivery count; only linear-extension noise removed. If interleaving `Pack-Dispatch-Pack-Dispatch` vs `Pack-Pack-Dispatch` treated as equivalent, X3/X4 would incorrectly merge — so partial order must retain per-package causality.

**Payment multiplicity as amount attribute:** If two `Record Payment` events replaced by `Invoice amount=100, paid_amount=100`, X4 merges toward X3 (both fully paid single invoice). Partial vs complete qualifier becomes `first instalment vs final`. Loses dunning-step signal but gains comparability for finance KPIs. Recommended as dual view: keep structural count for process analysis, add amount attribute for reporting.

## 8. Limitations and recommendation

Limitations: eight executions cannot validate frequencies; canonical renaming depends on tie-breaking when objects are symmetric (two identical items) — different tie-breakers yield different intermediate ids though our count-based R3 is stable; EXT detection relies on supplied `EXT-` prefix, in real OCELs externality must be inferred via lead-component overlap heuristics which are threshold-sensitive; qualifiers like `removed_before_dispatch` may be missing or inconsistently logged, making SEM-Substituted fragile; `max_objs` truncation can silently reassign shared/fragmented cases.

Recommended level per purpose — no single notion dominates:

- **Compliance monitoring: R3 with full qualifiers + R2 exact check.** Must distinguish X1 vs X7 (substitution) and X5/X6 sharing (allocation rules). Exact `~struct` proves violation instances; `~biz` groups them into controllable categories. Label-only is unsafe.
- **Operational segmentation: R3 coarse variant (5 groups: Clean, Fragmented, Shared, Substituted, Rework).** Merge X3+X4 as Fragmented for capacity planning if delivery cost abstracted, or keep split if logistics costed per delivery; merge X5+X6 as Shared for dependency management. Balances actionability vs sparsity; finest partition creates too many singletons to staff.
- **Root-cause analysis: R3 fine + partial-order causal mapping.** Needs pack-delivery linkage, return loop, qualifier to separate planned split (X4) from rework (X8) and hidden removal (X7). Requires O2O and E2O arity; collapsed or EXT-filtered views misattribute causes.
- **Descriptive reporting: R4 outcome + R1 counts.** Report `delivered & paid %`, average packs/deliveries/payments per order. Coarse grouping communicates KPIs; fine structural variants would overwhelm stakeholders.

In short: use exact/canonical for auditability, business-semantic for action, outcome for communication.
