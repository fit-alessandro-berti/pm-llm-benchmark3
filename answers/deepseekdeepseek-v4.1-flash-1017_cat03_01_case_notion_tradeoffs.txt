## 1. Analytical assumptions

I interpret a **case notion** as a projection of the OCEL onto one selected object identity: each event directly related to that object becomes part of that object’s case, ordered by timestamp. I do not treat this projection as the underlying process; it is a viewpoint optimized for a family of questions. **Convergence** means several object lifecycles meet in one object or event, e.g. P3 packs items for O2 and O3, D2 carries P2 and P3, and V2 bills O2 and O3. **Divergence** means one object’s fulfilment path splits across multiple objects, e.g. O1 splits across P1/P2 and D1/D2, while O3 splits across P3/P4 and D2/D3.

Copied shared events are **both evidence and duplication**. They are evidence that multiple objects genuinely participated in the same activity, e.g. e16 is one dispatch of D2 involving O1, O2, O3, P2 and P3. They are duplication when a flattened log counts e16 separately in the O1, O2 and O3 cases and then treats those copies as independent process executions. I therefore permit direct-E2O flattening as the baseline and would allow an explicitly labelled propagated-relation variant only as a sensitivity check, not as silent ground truth. No relation should be propagated through O2O links unless the transformation is documented.

## 3. Concrete distortion analysis

1. **Cross-order package P3 under Order flattening.** e13 is directly related to O2, O3, I21, I31 and P3. When flattened on Order, e13 is copied into both O2 and O3 cases. For O2, the apparent path includes Add Item e07Pack e13Dispatch e16Invoice e19Payment e22Confirm e24Payment e25Close e29. For O3, e13 also appears alongside e14, because O3 is in both P3 and P4. This inflates the frequency of P3-related Pack/Dispatch/Confirm edges and makes O2/O3 appear synchronized. The effect is informative about cross-order packaging but harmful if the copied e13/e16/e24 events are counted as independent order activities.

2. **Cross-order package P4 under Order and Package flattening.** P4 packs I32 from O3 and I41 from O4, and e14/e17/e27 relate to O3/O4. In the O3 order case, P4 appears as an additional Pack e14, Dispatch e17 and Confirm e27 alongside P3’s e13/e16/e24. This serialises what are logically two package streams into one order trace: O3 gets more Pack/Dispatch/Confirm steps than O4, partly because P4 is shared with O4. Under Package flattening, P4 is a single PackDispatchConfirm case, so O3/O4 convergence is hidden. This is context-dependent: useful for seeing that O3 had two packages, misleading for average order activity duration.

3. **Consolidated delivery D2 under Delivery flattening.** D2’s case is just e16e24. D1 has e15e23 and D3 has e17e27, so all three deliveries produce the same two-activity variant even though D2 consolidates P2/P3 and O1/O2/O3. The delivery-per-case frequency says “one D2 delivery,” not “three orders were dispatched and confirmed together.” The performance interval from e16 at 11:05 to e24 at 16:00 applies to all three orders and both packages. This is informative for delivery-level SLA but harmful for per-order delay attribution.

4. **Consolidated invoicing V2 under Invoice flattening.** V2 has e19e22e25, whereas V1 has e18e21 and V3 has e20e26. Invoice flattening correctly shows the two-instalment settlement of V2, but it hides that V2 bills both O2 and O3. If the same events are flattened on Order, e19/e22/e25 are copied into both O2 and O3, making each order look as if it underwent two payment steps. That is partly true for the shared invoice but misleading if interpreted as independent order payment behaviour.

5. **Partial payments M2/M3 under Payment flattening.** M2 is only e22 and M3 is only e25. On a Payment flattening, these are two separate singleton cases; there is no edge e22e25 and no case-level evidence that M2 partially settles V2 before M3 completes settlement. The relation is recoverable only through V2 or through O2O qualifiers. This truncation is harmful for discovering a settlement process, but it is informative for counting payment events.

6. **Near-singleton lifecycle under Payment flattening.** M1 e21, M2 e22, M3 e25 and M4 e26 each produce a one-event case. D1/D2/D3 are also only two-event lifecycles. On Payment flattening, the DFG has no meaningful internal edges and performance is undefined or zero-length. Choosing Payment because it is “small and clean” would remove all process context and is not a defensible end-to-end lead.

7. **O1 split across P1/P2 under Package flattening.** O1 has e11/P1 and e12/P2, then e15/P1/D1 and e16/P2/D2, and confirms via e23 and e24. Package flattening creates one P1 case with e11e15e23 and one P2 case with e12e16e24. O1’s Create e01, Add Item e05/e06 and Close e28 are absent. The package cases look independent, so package-level analysis cannot answer whether O1 was completed as one order.

8. **Shared D2 events under Item flattening.** e16 and e24 are related to I12, I21 and I31. On Item flattening, e16 and e24 are copied into three item cases. I21 and I31 both then appear as Add ItemPack Package e13Dispatch e16Confirm e24, despite belonging to different orders O2 and O3. This creates apparent item equivalence and frequency inflation for e16/e24. It is useful for item-level traceability but misleading if copied events are counted as separate dispatch/confirmation activities.

9. **O1’s double Dispatch/Confirm under Order flattening.** O1 contains both e15/e23 and e16/e24, so its trace has two Dispatch and two Confirm Delivery events. e16/e24 are also shared with O2/O3 via D2. The DFG edge structure can look like a split/parallel path, but the timestamp ordering serialises it as Dispatch e15Dispatch e16Payment e21Confirm e23Confirm e24Close e28. This is informative about O1’s split fulfilment, but harmful if the analyst assumes a single linear order-fulfilment path.

## 4. Traditional versus object-centric analysis portfolio

I would still create **Order-flattened logs** because Order is the only object type with Create Order and Close Order, and it answers order-variant, throughput and completion questions. I would also create **Invoice-flattened logs** for settlement and consolidated billing, **Package/Delivery-flattened logs** for cross-order packaging and logistics, and **Item/Payment-flattened logs only as narrow audits**. These logs should carry annotations for shared-event copies, e.g. e16 has three related orders, so its contribution to an order-level frequency should be weighted or reported separately.

Order flattening can safely answer: which orders reached Close Order, which activities occurred for each order, and how O1’s P1/P2 split appears in sequence. Invoice flattening can safely answer: which invoices received one versus two payments, and how V2 differs from V1/V3. Package flattening can safely answer: which packages were packed, dispatched and confirmed. Delivery flattening can safely answer delivery-level dispatch-to-confirm duration.

Questions requiring object-centric analysis include: how P3 simultaneously involves O2/O3 and I21/I31; how P4 involves O3/O4; how D2 connects P2 and P3 and thereby O1/O2/O3; how V2 connects O2/O3 and is paid by M2/M3. These require an OC-DFG, OTG, ET–OT graph, object interaction summary or equivalent-execution clustering. Contradictions between flattened and object-centric views should be reconciled by treating the flattened log as a projection: if Order flattening shows O2/O3 both having two payments, the OCEL shows this is due to shared V2, not two independent order payments. If Package flattening hides O3’s two packages, the OC-DFG/OTG should expose P3 and P4 relationships.

## 5. Lead-object decision

**Position B: Use a primary lead object plus explicitly secondary lifecycles.**

**Decision criteria.** The lead object should cover the start and end of fulfilment, support operational questions, and not erase consolidation/divergence that matters for interpretation. Coverage of Create/Close, direct participation in major activities, and ability to reconcile shared objects are the key criteria.

**Strongest supporting evidence.** Order is the only object type directly related to all Create Order events e01–e04 and all Close Order events e28–e31. It also directly covers Add Item (e05–e10), Pack Package (e11–e14 where orders are directly related), Dispatch (e15–e17), Issue Invoice (e18–e20), Record Payment (e21–e22/e25–e26) and Confirm Delivery (e23–e27). Other types are too short: Payment cases are near-singletons, Delivery cases are two events, and Package cases omit order creation and closure.

**Strongest counterargument.** No single Order-flattened log is sufficient for end-to-end analysis because the process deliberately crosses object boundaries: P3 connects O2/O3; P4 connects O3/O4; D2 connects O1/O2/O3; V2 connects O2/O3 and is paid by M2/M3. Order flattening duplicates e16/e24 across O1/O2/O3 and duplicates V2 events across O2/O3. Thus Order is a useful lead but cannot be the sole case notion.

**Residual risk.** O3’s order case appears longer because it contains both P3 and P4 streams, and O1’s order case contains both P1 and P2 streams. Performance measures at order level may mix true order delay with shared-package/dispatch synchronisation. Invoice and payment analysis also requires secondary Invoice/Payment views, especially for M2/M3.

**Conditions for changing the decision.** If the study question shifts to logistics, Package or Delivery should become primary. If it shifts to billing and settlement, Invoice should become primary. If the goal is conformance of multi-object coordination rather than order-level performance, I would move toward position C and reject a single lead object, using object-centric artefacts as the primary analysis.

## 6. PM4Py analysis outline

```python
import pm4py
import pandas as pd

# Basic OCEL inspection
print(ocel)

# Activity and object-type frequency inspection.
# get_extended_table() expands E2O relations, so de-duplicate for event/object counts.
ext = ocel.get_extended_table()

activity_frequency_unique_events = (
    ext.drop_duplicates("ocel:eid")
       .groupby("ocel:activity")
       .size()
       .sort_values(ascending=False)
)

object_type_frequency_unique_objects = (
    ext.drop_duplicates(["ocel:type", "ocel:oid"])
       .groupby("ocel:type")
       .size()
       .sort_values(ascending=False)
)

print("Activity frequency (unique events):")
print(activity_frequency_unique_events)
print("Object-type frequency (unique objects):")
print(object_type_frequency_unique_objects)

# Flattened logs for all six object types.
object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flattened_logs = {
    ot: pm4py.ocel_flattening(ocel, ot)
    for ot in object_types
}

# Per-object-type DFG and log skeleton.
flattened_dfg = {}
flattened_dfg_start = {}
flattened_dfg_end = {}
flattened_skeletons = {}

for ot, log in flattened_logs.items():
    dfg, start_activities, end_activities = pm4py.discover_dfg(log)
    flattened_dfg[ot] = dfg
    flattened_dfg_start[ot] = start_activities
    flattened_dfg_end[ot] = end_activities
    flattened_skeletons[ot] = pm4py.discover_log_skeleton(log)

# Object-centric artefacts.
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
object_interactions_summary = pm4py.ocel_objects_interactions_summary(ocel)

# Position B justifies clustering Order executions as a diagnostic,
# not as a replacement for the object-centric view.
equivalent_order_clusters = pm4py.cluster_equivalent_ocel(ocel, "Order")

# Sensitivity annotation: how many Order objects directly share each event.
order_e2o = ext[ext["ocel:type"] == "Order"][["ocel:eid", "ocel:oid"]].drop_duplicates()
order_copy_multiplier = (
    order_e2o.groupby("ocel:eid")["ocel:oid"]
    .nunique()
    .rename("n_related_orders")
)
event_weight_order = (1.0 / order_copy_multiplier).rename("order_copy_weight")

print("Flattened DFG keys:", flattened_dfg.keys())
print("OC-DFG:", ocdfg)
print("OTG:", otg)
print("ET-OT:", etot)
print("Object interactions summary:", object_interactions_summary)
print("Equivalent Order clusters:", equivalent_order_clusters)
print("Order copy multiplier:", order_copy_multiplier)
print("Order event weight:", event_weight_order)

# Do not treat the flattened DFGs as ground truth.
# Reconcile them with ocdfg, otg, etot, interactions summary,
# and the equivalent-order clusters before drawing process conclusions.
```

## 7. Sensitivity and validation plan

1. **Remove or down-weight copied shared events.** Recompute Order-flattened DFGs and performance using a weight of `1 / number_of_related_orders` for e13, e14, e16, e17, e19, e22, e24, e25 and e27. Compare unweighted and weighted edge frequencies for Pack, Dispatch, Confirm Delivery and Record Payment. If the conclusions for O2/O3 depend entirely on copied e16/e24/e19/e22/e25, state that the result is shared-event driven rather than order-specific.

2. **Compare direct E2O with an explicitly propagated-relation variant.** Build a separate Order-propagated log by tracing through O2O links such as P3O2/O3, P4O3/O4, D2P2/P3, and V2O2/O3. Label it as a derived sensitivity log. Check whether propagation introduces edges not present in direct-E2O flattening, and validate each new edge against the supplied object relations. In particular, do not let propagation turn M2/M3 into independent evidence for both O2 and O3 without acknowledging V2.

3. **Change the lead object.** Repeat the main questions under Invoice, Package and Delivery lead views. Invoice lead should be used to test the V2 two-instalment finding; Package lead should be used to test P3/P4 cross-order packaging; Delivery lead should be used to test D2 consolidation. If the Order view says O3 has two payments but the Invoice view shows one consolidated V2, reconcile them as an order projection versus invoice settlement distinction.

4. **Compare event-based, unique-object-based, and total-object-based frequencies in the OC-DFG.** For e16, the event count is one, but the participating-object count includes O1/O2/O3, P2/P3, D2 and several items. For e13, the event count is one while the order count is two and item count is two. Report both event frequencies and object-participation frequencies so that shared activities are not under- or over-represented.

5. **Check performance under shared timestamps.** Recompute order cycle times with shared events allocated equally, to the earliest related object, and to the latest related object. Compare O1, O2 and O3 on e16/e24 and O2/O3 on e22/e25. This tests whether P3/P4/D2/V2 create artificial synchronisation in order-level performance.

6. **Validate near-singleton and truncated lifecycles.** Explicitly mark Payment, Delivery and Package cases as truncated. For Payment, compare direct Payment flattening with an Invoice-based settlement view. For Package, compare P1/P2 against O1 and P3/P4 against O2/O3/O4. If a conclusion relies on Payment or Delivery having an internal process, treat it as unsupported and move to the OCEL or Invoice/Package secondary views.
