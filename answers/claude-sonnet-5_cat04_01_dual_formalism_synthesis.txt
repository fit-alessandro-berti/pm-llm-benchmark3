# 1. Assumptions and Interpretation

1. **Low/high-risk choice**: represented purely as a control-flow XOR between two mutually exclusive sub-processes — `Supervisor Review` (low) versus the concurrent pair `Quality Review`  `Regulatory Review` (high). No data attribute "risk level" is encoded; the model only commits to *which activities occur*, per requirement 11.
2. **Optional supplier consultation**: represented as an XOR between a silent () transition and `Consult Supplier`. Selection is a data condition external to control-flow, so both branches are always structurally available; the log-level data attribute that "decided" it is not modeled.
3. **Passing inspection**: `Inspect Trial` is a single event label used both for passing and failing inspections. The repeat/exit decision after `Inspect Trial` is modeled as a **silent** control-flow choice inside the loop, not as a labelled outcome. This is a genuine information loss but is unavoidable given "activities are recorded at completion time" (requirement 11) — the model cannot certify *which* `Inspect Trial` occurrence was the passing one from labels alone.
4. **Duplicate visible labels**: **not permitted** in either model. Both the process tree and the POWL model use each of the 14 activity labels exactly once as a leaf/transition. This avoids duplicate-label ambiguity in conformance checking, at the cost of needing synchronization/gating approximations (tree only) instead of duplicating e.g. a second copy of `Analyze Root Cause`.
5. **Process-tree approximation policy**: **conservative (safe) under-approximation via phase merging**. Wherever the true dependency graph is non-block-structured (Plan Verification/Design Corrective Action crossing the containment/analysis branches; approval route and supplier consultation only needing `Analyze Root Cause` but modeled as waiting for the full second phase), the tree delays the dependent activity until a *superset* of its true prerequisites is satisfied. Every trace accepted by the tree is a trace consistent with the intended dependencies; some intended-valid traces (with earlier starts) are excluded. No invalid trace is ever admitted by this policy.
6. **"May overlap" interpretation**: interpreted as **true concurrency** (free interleaving, both orders of completion valid), not merely "no stated order." Where the narrative says "may overlap," we place the corresponding nodes as siblings of a `PARALLEL`/`AND` node (tree) or leave them non-adjacent in the partial order (POWL), not as an unspecified/implicit sequence.

# 3. PM4Py Process-Tree Model

## 3.1 Compact expression

```
SEQ(
  RegisterDeviation,
  AND( ContainMaterial, AnalyzeRootCause ),
  AND( PlanVerification, DesignCorrectiveAction ),
  AND(
    LOOP( SEQ(ExecuteTrial, InspectTrial), AdjustParameters ),
    XOR( SupervisorReview, AND(QualityReview, RegulatoryReview) ),
    XOR( tau, ConsultSupplier )
  ),
  ReleaseMaterial,
  ArchiveCase
)
```

## 3.2 Python construction

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label=None):
    return ProcessTree(label=label)

def make_op(operator, children):
    node = ProcessTree(operator=operator)
    node.children = children
    for c in children:
        c.parent = node
    return node

# Leaves
reg        = leaf("Register Deviation")
contain    = leaf("Contain Material")
analyze    = leaf("Analyze Root Cause")
planverif  = leaf("Plan Verification")
design     = leaf("Design Corrective Action")
sup_rev    = leaf("Supervisor Review")
qual_rev   = leaf("Quality Review")
reg_rev    = leaf("Regulatory Review")
consult    = leaf("Consult Supplier")
exec_trial = leaf("Execute Trial")
inspect    = leaf("Inspect Trial")
adjust     = leaf("Adjust Parameters")
release    = leaf("Release Material")
archive    = leaf("Archive Case")
tau_supp   = leaf(None)   # silent: supplier not consulted

# Phase 1: containment / root-cause branches start concurrently
phase1 = make_op(Operator.PARALLEL, [contain, analyze])

# Phase 2: verification planning & corrective-action design
phase2 = make_op(Operator.PARALLEL, [planverif, design])

# Risk route
qr_rr      = make_op(Operator.PARALLEL, [qual_rev, reg_rev])
risk_route = make_op(Operator.XOR, [sup_rev, qr_rr])

# Optional supplier consultation
supplier_choice = make_op(Operator.XOR, [tau_supp, consult])

# Trial loop: (Execute Trial, Inspect Trial), optionally Adjust Parameters and repeat
trial_body = make_op(Operator.SEQUENCE, [exec_trial, inspect])
trial_loop = make_op(Operator.LOOP, [trial_body, adjust])

# Phase 3: trial cycle overlapping approval route and supplier consultation
phase3 = make_op(Operator.PARALLEL, [trial_loop, risk_route, supplier_choice])

tree = make_op(Operator.SEQUENCE, [reg, phase1, phase2, phase3, release, archive])
```

## 3.3 Approximation discussion (what the tree cannot represent exactly)

The tree **cannot** represent, without the phase-merging approximation:

- **D4/D5 cross-independence**: the real dependency graph lets `Plan Verification` start as soon as `Contain Material` finishes, *regardless* of `Analyze Root Cause`'s progress, and symmetrically for `Design Corrective Action`. Because `phase1` is a `PARALLEL` block, the tree forces **both** `Contain Material` and `Analyze Root Cause` to finish before either `Plan Verification` or `Design Corrective Action` may start. This excludes valid traces where, e.g., `Plan Verification` starts before `Analyze Root Cause` completes.
- **D6/D9 early starts**: the true model lets the risk route and `Consult Supplier` start immediately after `Analyze Root Cause`, concurrently with `Plan Verification`/`Design Corrective Action` still running. Because these are placed in `phase3` (gated behind `phase2`), the tree forces them to wait until **both** `Plan Verification` and `Design Corrective Action` are done — stricter than required.
- These are the **only** losses. Internal concurrency once `phase3` begins (`trial_loop`  `risk_route`  `supplier_choice`), the loop semantics (D14–D17), and the release AND-join (D18) are represented **exactly**.

This is a documented **conservative under-approximation**: every string accepted by the tree is dependency-consistent with the true model; some true-valid strings (early risk-route/supplier/plan-verification starts) are rejected.

# 4. PM4Py POWL Model

## 4.1 Compact description

```
PO {
  nodes: RegisterDeviation, ContainMaterial, AnalyzeRootCause, PlanVerification,
         DesignCorrectiveAction, TrialLoop, RiskRoute, SupplierChoice,
         ReleaseMaterial, ArchiveCase

  edges:
    RegisterDeviation -> ContainMaterial
    RegisterDeviation -> AnalyzeRootCause
    ContainMaterial        -> PlanVerification
    AnalyzeRootCause       -> DesignCorrectiveAction
    AnalyzeRootCause       -> RiskRoute
    AnalyzeRootCause       -> SupplierChoice
    PlanVerification       -> TrialLoop
    DesignCorrectiveAction -> TrialLoop
    TrialLoop              -> ReleaseMaterial
    RiskRoute              -> ReleaseMaterial
    SupplierChoice         -> ReleaseMaterial
    ReleaseMaterial        -> ArchiveCase
}
where
  TrialLoop      = LOOP( SEQ(ExecuteTrial, InspectTrial), AdjustParameters )
  RiskRoute      = XOR( SupervisorReview, PO{QualityReview, RegulatoryReview | no edges} )
  SupplierChoice = XOR( tau, ConsultSupplier )
```

## 4.2 Python construction

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def t(label):
    return Transition(label=label)

reg_t        = t("Register Deviation")
contain_t    = t("Contain Material")
analyze_t    = t("Analyze Root Cause")
planverif_t  = t("Plan Verification")
design_t     = t("Design Corrective Action")
sup_rev_t    = t("Supervisor Review")
qual_rev_t   = t("Quality Review")
reg_rev_t    = t("Regulatory Review")
consult_t    = t("Consult Supplier")
exec_t       = t("Execute Trial")
inspect_t    = t("Inspect Trial")
adjust_t     = t("Adjust Parameters")
release_t    = t("Release Material")
archive_t    = t("Archive Case")

# Quality Review || Regulatory Review: concurrent (no edge between them)
qr_rr_po = StrictPartialOrder(nodes=[qual_rev_t, reg_rev_t])

# Risk route: XOR(Supervisor Review, Quality Review || Regulatory Review)
risk_route = OperatorPOWL(Operator.XOR, [sup_rev_t, qr_rr_po])

# Optional supplier consultation: XOR(skip, Consult Supplier)
supplier_choice = OperatorPOWL(Operator.XOR, [SilentTransition(), consult_t])

# Trial body: Execute Trial -> Inspect Trial
trial_body = StrictPartialOrder(nodes=[exec_t, inspect_t])
trial_body.order.add_edge(exec_t, inspect_t)

# Trial loop: do = trial_body, redo = Adjust Parameters
trial_loop = OperatorPOWL(Operator.LOOP, [trial_body, adjust_t])

powl = StrictPartialOrder(nodes=[
    reg_t, contain_t, analyze_t, planverif_t, design_t,
    trial_loop, risk_route, supplier_choice, release_t, archive_t
])

# Start
powl.order.add_edge(reg_t, contain_t)
powl.order.add_edge(reg_t, analyze_t)

# Containment branch -> verification planning
powl.order.add_edge(contain_t, planverif_t)

# Root-cause branch -> design + approval + supplier
powl.order.add_edge(analyze_t, design_t)
powl.order.add_edge(analyze_t, risk_route)
powl.order.add_edge(analyze_t, supplier_choice)

# Trial gating: needs both design and verification planning (AND-join)
powl.order.add_edge(planverif_t, trial_loop)
powl.order.add_edge(design_t, trial_loop)

# Release synchronization (AND-join)
powl.order.add_edge(trial_loop, release_t)
powl.order.add_edge(risk_route, release_t)
powl.order.add_edge(supplier_choice, release_t)

# End
powl.order.add_edge(release_t, archive_t)
```

## 4.3 Why unconnected node pairs remain concurrent

- `contain_t` / `analyze_t`: no edge — both depend only on `reg_t` (D3).
- `planverif_t` / `analyze_t`, `planverif_t` / `design_t`, `contain_t` / `design_t`: no edges — the true dependency graph never relates verification planning to root-cause analysis directly, nor containment to corrective-action design (D4, D5 are independent chains).
- `trial_loop` / `risk_route`, `trial_loop` / `supplier_choice`: no edges — approval and supplier consultation may overlap the entire trial cycle (D13, D11).
- `risk_route` / `supplier_choice`: no edges — both depend only on `analyze_t`, independently of each other.
- `qual_rev_t` / `reg_rev_t` (inside `qr_rr_po`): no edge — concurrent completion order (D8).

This POWL model therefore has **no approximation locus**: every relation in Section 2 is either an explicit edge or an explicit absence-of-edge, matching the intended semantics directly (subject only to the inherent pass/fail-label abstraction, assumption 3).

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams (CM, ARC) | Fully concurrent after RD | Exact (`AND` phase1) | Exact (no edge, both from `reg_t`) | None | Both models correctly permit any containment/analysis interleaving. |
| Split dependencies (PVCM only; DCAARC only) | PV independent of ARC; DCA independent of CM | **Under-constrained relative to spec: over-synchronized** — both PV and DCA delayed until *both* CM and ARC finish | Exact | Tree: overconstraint (excludes valid early starts) | Tree may reject genuinely compliant early-start logs, producing false conformance alarms. |
| Risk route (XOR low/high; QRRR) | Exclusive route selection; QR/RR concurrent within high route | Exact | Exact | None | Both faithfully forbid mixed routes and preserve QR/RR order-freedom. |
| Overlap of approval and trial | Approval need not finish before trial starts | Exact **once phase3 is entered** | Exact | Tree: entry into the overlap zone itself is delayed (see row 2) | Once trial has legitimately started in the tree's model, full concurrency with approval is preserved; only the *start point* is late. |
| Optional supplier consultation | Starts after ARC; may overlap DCA/PV/approvals/trial; finishes before RM | **Overconstrained**: gated behind full phase2 (PV & DCA) instead of ARC alone | Exact | Tree: overconstraint | Real supplier-engagement logs that start consultation early would be flagged nonconforming by the tree but not by POWL. |
| Repeat-until (loop) behavior | ExecuteInspect repeats via Adjust Parameters until pass; AP never after pass | Exact (`LOOP(seq, redo)` always ends on "do") | Exact (same construct) | None | Both models correctly forbid AP after the terminal inspection. |
| Release synchronization (AND-join of trial-pass, approval, supplier) | RM requires all three complete | Exact (`phase3` join) | Exact (three edges into `release_t`) | None | Both correctly forbid premature release. |
| Duplicate-label risk | N/A (no duplication used) | Not used | Not used | N/A (deliberately avoided) | Avoiding duplication keeps replay/alignment unambiguous at label level; the price paid instead is the tree's phase-merging overconstraint above. |

# 7. Preferred Representation and Validation Plan

**Preferred representation: the POWL model.** It reproduces every relation in Section 2 exactly using direct partial-order edges (or documented absence of edges for concurrency), with no synchronization approximation anywhere — the phase-merging loss that affects the process tree simply does not arise, because POWL's `StrictPartialOrder` lets AND-join dependencies be attached to individual predecessor sets rather than to whole sibling blocks. The process tree remains useful as a conservative, strictly-more-restrictive approximation (e.g., for tools that require pure block structure), but should not be treated as the reference model.

**Validation plan**

1. **Conversion to Petri nets**: `net_pt, im_pt, fm_pt = pm4py.convert_to_petri_net(tree)` and `net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)`. Inspect the resulting nets visually for the expected AND/XOR/loop gadgets around `Execute Trial`/`Design Corrective Action`/`Plan Verification`.
2. **Soundness checking**: `pm4py.check_soundness(net_pt, im_pt, fm_pt, print_diagnostics=True)` and the analogous call for the POWL-derived net. Both are expected to report sound workflow nets (no dead transitions, proper completion, option to complete) given the well-formed loop/XOR/AND gadgets.
3. **Bounded/sampled playout**: `pm4py.play_out(tree, parameters={"maxTraceLength": 30})` and the POWL equivalent, capping loop unrollings (e.g., at most 4 trial iterations) to obtain a finite representative sample; check that every sampled trace starts with RD, ends with AC, contains RM immediately before AC, and never contains AP as the last activity before RM.
4. **Explicit positive/negative trace tests**: replay the eight Section 5 witnesses against both converted nets (e.g., via token-based replay or alignments) and confirm perfect fitness for A1–A4 and for A5 **only** against the POWL net (with the expected fitness deficiency against the tree net, matching the documented approximation), and confirm replay failure at the identified earliest violation point for F1–F3 on both nets.
5. **Silent-behavior / duplicate-label check**: enumerate all visible transition labels in each converted net and assert each of the 14 activity labels maps to exactly one visible transition (no duplicates), and separately enumerate silent transitions to confirm they correspond only to the documented optional-supplier skip and the loop's redo/exit choice — not to any additional undocumented silent routing.
6. **Limitations**: soundness checking validates structural well-formedness, not narrative fidelity — it will not detect the phase-merging approximation (Section 3.3), which must be checked via the targeted witness A5, not via soundness alone. Bounded playout with capped loop iterations cannot prove the absence of rare violating interleavings at higher iteration counts. The eight hand-authored witnesses are illustrative, not an exhaustive test suite over the full interleaving space of QR/RR against ET/IT/AP cycles.

# 8. Final Self-Critique

1. **Semantic**: abstracting "passing Inspect Trial" as a silent loop-exit decision means neither model can express or check any property that depends on distinguishing a passing `Inspect Trial` event from a failing one at the label level (e.g., "no more than 3 failed inspections"); this is a genuine semantic gap in what conformance results against these models can certify, not merely a tooling limitation.
2. **Structural**: the chosen phase-merging approximation for the process tree collapses *all* cross-branch slack into two coarse phase boundaries for readability; a more finely merged tree could reduce the excluded-behavior surface (e.g., by separately gating supplier consultation only on Design Corrective Action rather than on the full phase2), at the cost of a harder-to-read nested expression. The trade-off was chosen for clarity, not minimality of loss.
