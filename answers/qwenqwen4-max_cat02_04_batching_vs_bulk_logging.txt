def supported_kwargs(fn, wanted):
    try:
        sig = inspect.signature(fn)
    except (TypeError, ValueError):
        return dict(wanted)
    pars = sig.parameters
    if any(p.kind == inspect.Parameter.VAR_KEYWORD for p in pars.values()):

    return {k: v for k, v in wanted.items() if k in pars}

Two readings must be compared rather than merged: (a) **logging artifact** — the tickets were resolved earlier, so true waiting is *overstated* and true service is *understated* (the resolution work is missing entirely); (b) **policy-batched real work (H10)** — closing is genuinely a <1-min click performed at shift end, so waiting is *real but policy-induced*, service really is 0, and the bottleneck is the **unlogged resolution step**, not T-F. Under A3/A4 censoring, service is bounded at 0–2 min per item (14 min total), still negligible against 103 min of waiting. Either way, T-F would be wrongly acquitted by a utilization-based bottleneck analysis ("0% busy, infinite speed") while a queue-based analysis would wrongly blame T-F for a 103-min queue. Conformance: zero-duration events are often treated as silent/ steps or dropped by time-aware alignments, silently deleting seven cases from fitness statistics.

**G7.** Coarsening dominates everything. Four of five waits are negative (1, 4, 7, 11 min), which is *logically impossible* under exact semantics — proof that at least one of {rounding, clock skew A2} is active. Service bounds under A4 are 0–45 min per item; utilization spans 0–500%. Interestingly, resource-level throughput (5 items per 15-min bucket = 20/h) is identical under batch and serial readings, but **per-item service differs 5×** (15 vs 3 min), which is exactly what staffing and simulation models consume. The `recorded_at` ladder (+60 s per record) is finer-grained than the lifecycle fields and is the only usable timing evidence — but it is ambiguous between serial execution and serial typing (§5). Conformance: all ties  arbitrary ordering  non-deterministic alignment costs.

**G8.** Waiting (48.2 min mean) and service (7 min) are internally consistent, and the drain is 100% busy. The bias risk is **attribution**: if the safety block is real and clocks are aligned, the 38-min initial wait is exogenous capacity loss, and T-H is a *victim*, not a structural bottleneck. If the safety check was T-H's own unlogged activity, T-H was busy 15:00–15:38 and its utilization is *understated* by ~35 min, converting "idle capacity" into hidden work. If arrivals were simply an upstream burst, the block is coincidental. Conformance: a model without a blocking activity cannot explain the 38-min gap and will assign the delay to T-H.

def union_busy_s(g):
    iv = sorted([(r.start_ts, r.complete_ts) for r in g.itertuples() if r.dur_s > 0])
    tot, cs, ce = 0.0, None, None
    for s, e in iv:
        if cs is None: cs, ce = s, e
        elif s <= ce:  ce = max(ce, e)
        else:          tot += (ce-cs).total_seconds(); cs, ce = s, e
    return tot + ((ce-cs).total_seconds() if cs is not None else 0.0)

def overlap_stats(g):
    rows, hit, pairs, ov = list(g.itertuples()), set(), 0, 0.0
    for a, b in itertools.combinations(rows, 2):
        lo, hi = max(a.start_ts, b.start_ts), min(a.complete_ts, b.complete_ts)
        if hi > lo:                                   # STRICT: adjacency != overlap
            pairs += 1; ov += (hi-lo).total_seconds(); hit.update([a.case, b.case])
    return pairs, len(hit)/len(rows), ov

def max_conc(g):
    pts = []
    for r in g.itertuples():
        if r.dur_s > 0:
            pts += [(r.start_ts, 1), (r.complete_ts, -1)]
    pts.sort(key=lambda x: (x[0], x[1]))              # ends before starts at ties
    cur = mx = 0
    for _, d in pts: cur += d; mx = max(mx, cur)
    return mx

def adjacency(g):
    gg = g.sort_values(["start_ts", "seq"]).reset_index(drop=True)
    ok = tot = okp = totp = 0
    for i in range(len(gg)-1):
        a, b = gg.loc[i], gg.loc[i+1]
        eq = int(a.complete_ts == b.start_ts); tot += 1; ok += eq
        if a.dur_s > 0 and b.dur_s > 0: totp += 1; okp += eq
    return (ok/tot if tot else np.nan, okp/totp if totp else np.nan)

def max_backlog(g):
    pts = [(r.queue_arrival_ts, 1) for r in g.itertuples()] + \
          [(r.complete_ts, -1) for r in g.itertuples()]
    pts.sort(key=lambda x: (x[0], x[1]))
    cur = mx = 0
    for _, d in pts: cur += d; mx = max(mx, cur)
    return mx

**How to read the output, and where PM4Py and pandas are expected to disagree.**

- G1, G6, G7 all present start = end equality, so a temporal detector will tend to give them the *same* category (a "simultaneous"-type label). pandas separates them decisively: G6 has `zero_frac = 1.0` and a single insert burst; G7 has `prec_s = 900` and `neg_wait = 4`; G1 has a documented 4-slot fixture and 2–3 s lags. **Same label, three different physical stories.**
- G4 and G8 have `adj_pos = 1.0`, `ov_rate = 0` — the classic "sequential batch" temporal pattern. Whether they survive `merge_distance = 0` depends on whether the implementation merges gap  tol or gap < tol; a disappearance at md = 0 is an implementation detail, **not** evidence against serial work.
- G2 and G3 will typically be detected only through their equal start (resp. end) side; raising `merge_distance` to 300–900 s can pull their staggered counterparts (6–7 min apart) into the same batch, manufacturing "batches" that the fine structure contradicts.
- `min_batch_size` is a size filter, not evidence: at 2 everything qualifies; at 4 all eight clusters still qualify; at 5 the *most physically real* batch (G1, n = 4) would vanish while G6 (n = 7, pure logging) survives. Parameter sensitivity must never be read as confirmation.
- G5 exceeds capacity, which no temporal detector can know: PM4Py sees overlap, pandas sees `max_conc = 4 > cap = 3`.
- Coverage gaps are printed per configuration so that any dropped zero-duration or start-less event is visible; suspect clusters are flagged in `diag["suspect"]` and never silently removed.

# 5. Robustness and alternative explanations

**(a) Resource IDs trusted vs treated as shared/pooled.**

- **G5 flips most.** Trusted single identity: 233% utilization, 4-fold overlap  either impossible data or extreme multitasking; the cluster would be quarantined. Pooled (documented 3): U = 78%, average concurrency 2.33, and the anomaly narrows to the single 8-minute window 13:12–13:20 where 4 > 3 — i.e. *one* inflated interval or an understated cap, not a corrupt cluster. The remedy differs too: trusted  fix timestamps; pooled  fix identity.
- **G1 is a capacity question, not an identity question.** RBT-7 is one machine with four slots; "shared account" is the wrong frame. If the fixture claim were false, G1 would collapse to H9 (fan-out logging) and per-item service would rise from 45 s to 3 min — a 4× capacity error.
- **If T-B…T-H were also shared (not documented, so a hypothesis only),** G2's equal starts could be several inspectors starting together, and G3's equal ends a joint sign-off. But note the *asymmetry*: a perfect adjacency chain across five cases (G4, G8) is **unlikely** if two or more people worked independently — long exact chains are evidence for either one serial worker or a system-generated `start := previous complete` rule. Trusting IDs therefore *strengthens* H4 for G4/G8 while *weakening* H1 for G2.
- **Conformance consequences:** resource-aware checks (separation of duties, handover-of-work, resource-activity fitness) are only valid under trusted identity. Under pooling they must be run at team level or suppressed.

**(b) Exact timestamps vs interval-censoring by stated precision (plus the extract grid, A3).**

| cluster | censoring half-width | does the diagnosis survive? |
|---|---|---|
| G1 | 60 s (extract) vs 3-min cycle | Yes. Items start within the same minute; a 4-up cycle remains the best explanation. Sub-minute simultaneity is *not* provable. |
| G2 | 60 s vs 6–7 min end deltas | Yes. Start equality could hide 59 s of spread — irrelevant; the staggered ends are far larger than the censoring. |
| G3 | 60 s vs 7–8 min start deltas | Yes. Submission-lag conclusion robust; the exact 11:30 tie is only minute-level. |
| G4 / G8 | 60 s vs 4 / 7 min services | Mostly. "Zero gap" becomes "gap  [0, 60) s" (or 59 s overlap); service 4 ± 1 / 7 ± 1 min; utilization 100%  ~95–100%. Serial reading intact. |
| G5 | 60 s vs 8-min over-capacity window | Yes. The 4 > 3 violation lasts 8 min, far beyond censoring. |
| G6 | 60 s | **Qualitatively changes the wording:** service is not literally 0 but bounded 0–2 min per item (14 min total). Seven rapid clicks inside one minute are *fully consistent* with H10 (real work), so "zero service" must be reported as a bound, not a fact. Waiting 103 ± 2 min is unchanged in substance. |
| G7 | 900 s (documented) | **No point estimate survives.** start  [13:45,14:15], complete  [14:00,14:30]  duration  [0,45] min, waiting for M05  [0,19] min. Batch vs serial is unidentifiable. |

**Rounding-rule sensitivity for G7 (why the rule must be documented).** Under *floor-start / ceil-complete*, a serial 3-min-per-item story (starts 14:00, 14:03, 14:06, 14:09, 14:12; completions 14:03…14:15) reproduces the logged values exactly. Under *round-to-nearest*, that same story fails (M04/M05 starts would log as 14:15), but a genuine batch completing ~14:15 with records typed at 14:16–14:20 fits. Under a *symmetric* envelope both fit. So the physical conclusion is a function of an **undocumented rounding rule** — the textbook definition of an unidentifiable cluster.

**At least three cases where one temporal pattern supports several physical explanations (five given):**

1. **G1 vs G7 — identical start/end equality.** G1: multi-slot fixture, fine source, 3-min plausible cycle  genuine batch. G7: 15-min grid, negative waits  coarsening. The *pattern* is the same; only precision metadata and capacity context separate them. Strip the metadata and they are indistinguishable.
2. **G4 vs G8 — identical perfect adjacency.** Both are consistent with (i) serial single-piece flow, (ii) `start := previous complete` derivation, (iii) FIFO drain of a backlog. G8 adds an exogenous block, but with unsynchronised clocks the block could be coincidental, or could be T-H's own unlogged work.
3. **G3 — end equality.** Bulk submission after a folder (H3) and a genuine collective release decision at 11:30 (H1-like) produce identical logs. The worker's statement favours H3; it is testimony, not measurement.
4. **G5 — 4-fold overlap.** Three parallel analysts, or one multitasker, or case-opencase-close intervals with idle time inside. All three produce overlapping intervals; only badge data or pause/resume events can separate them.
5. **G6 — zero duration.** Administrative back-fill (work happened earlier) vs genuine shift-end clicking (work happens now, takes seconds). The waiting figure is identical; the *meaning* of the waiting, and the location of the bottleneck, are opposite.

**Additional non-causal caution.** Five clusters begin on an exact hour. Shift/meal boundaries (09:00 start, 13:00 post-lunch, 17:00 shift end) and hour-default form values are both plausible; the extract cannot distinguish them, and this correlation should not be used as evidence for any cluster's physical story.

# 6. Data-collection redesign

Priorities are ordered by *analytic value unlocked per unit of effort*; P0 items are prerequisites for any queueing conclusion.

**P0 — Make execution time mean execution.**
1. Capture `start` and `complete` **at the moment of the action, per item**, never inherited from a group/folder/fixture record. Where a group button is unavoidable (G2), emit a distinct `group_open` event and leave item `start` null rather than copying the group time — an explicit null is analytically safer than a plausible fake.
2. Separate the three moments that are currently conflated: `work_complete`, `form_submitted`, `record_inserted`. G3 and G6 become interpretable the day this lands.
3. Add an event-provenance flag per timestamp: `measured | derived | defaulted | rounded | entered`. Derived/chained starts (G4/G8 hypothesis H9) then stop being invisible.
4. For tickets, capture `resolved_at` separately from `closed_at`; this single field decides between H3 and H10 for G6.

**P1 — Identity and capacity.**
5. Badge-level identity for every human event; never a shared login. Where a pool is operationally real (G5), model it as a **team resource with declared capacity** and keep the individual badge on each event.
6. Declare workstation capacity as data: slots (RBT-7 = 4), concurrent-case policy, WIP limits. Without it, overlap cannot be classified as batch vs multitasking vs artifact.
7. Machine/slot identifiers (`fixture_id`, `nest_position`) so a 4-up cycle is represented as one cycle with four members, not four independent services.

**P1 — Clocks.**
8. NTP/PTP-sync all sources; stamp every event with `clock_domain_id` and the source's estimated offset with uncertainty. Log the offset estimate as a first-class field so cross-system waiting (G7's negative waits, G8's 3-min residual) can be corrected *or* honestly bounded.
9. Never let an upstream `queue_arrival` and a local `start` be subtracted without a documented offset; publish a per-source  with confidence interval.

**P2 — Grouping and interruption semantics.**
10. Explicit `batch_id` / `group_id` / `folder_id` / `submission_id` linking members to their operational container. This converts every hypothesis in §2 into a join.
11. Full lifecycle transition model: `start  suspend  resume  complete`, with reason codes (safety block, starvation, break, rework). This yields touch time vs elapsed time (fixes G5) and makes G8's capacity loss visible instead of inferred.
12. Log blocking activities (e.g. the T-H safety check) **in the same log and clock domain** as the work they block, with the affected resource.

**P2 — Precision metadata.**
13. Store granularity **and rounding rule** (`floor | nearest | ceil | mixed`) **and** accuracy, plus the **raw pre-rounded value** wherever it exists. Publish a per-field censoring interval so downstream tools can interval-censor automatically instead of guessing (G7).
14. Preserve sub-minute resolution in exports: the current extract prints all lifecycle fields as `HH:MM` even for 1-sec sources, silently degrading G1/G4/G8.

**P3 — Validation and contracts.**
15. A two-week shadow-logging / time-and-motion study on the four decisive questions: PLC fan-out vs per-item stamping (G1), begin-group semantics (G2), shift-end closure policy (G6), MES rounding rule (G7).
16. Automated data-quality contracts at ingestion: `arrival  start  complete` (after offset correction), `duration > 0` unless flagged `instantaneous`, overlap  declared capacity, lifecycle grid residuals monitored. Route violations to a quarantine stream that is **reported, not dropped**.
17. Interim analysis rules until P0–P2 land: G6 excluded from service/utilization; G7 interval-censored only; G3/G2 end-anchored reconstruction with the last case right-censored; G5 pool-level metrics only; G1 cycle-level metrics only.

# 7. Final adjudication

**High confidence (80) — interpretation of the *logging semantics*, which is not the same as confidence about the physics:**
- **G6 (90):** the timestamps are administrative, not executional. Whether the underlying work was earlier (H3) or genuinely instantaneous at 17:00 (H10) remains open, but no service/utilization number from these rows is usable.
- **G7 (88):** coarsening is established, principally by the four impossible negative waits plus the 900-s grid alignment. The physical execution mode is **not identifiable**.
- **G1 (85):** genuine 4-up batch is the best explanation, conditional on the documented fixture capacity and on the PLC not fanning one cycle record out to four items.
- **G3 (82)** and **G2 (80):** submission-side (G3) and start-side (G2) logging artifacts, each corroborated by an independent UI/testimony statement, with staggered counterparts that behave like serial work.

**Usable for conventional queue analysis, with stated caveats:**
- **G4:** the only cluster where waiting (13 min mean), service (4 min), utilization (100%) and throughput (15/h) can be taken at face value — *provided* `start` is confirmed measured rather than chained. Even then, censoring widens service to 4 ± 1 min.
- **G8:** waiting and service are internally consistent (48.2 / 7 min), but the *attribution* of the 38-min initial wait to the safety block is unverified because the clocks differ, and the block may be T-H's own unlogged activity. Report the waiting; do not yet report the cause.

**Exclude or interval-censor in queue analysis:**
- **G6 — exclude** from service, utilization and throughput; if waiting is reported at all, label it a **policy-driven upper bound** and censor completion to `[arrival, 17:00]`.
- **G7 — interval-censor everything** (duration 0–45 min, waiting 0–19 min); no point estimates, no bottleneck ranking, no conformance ordering.
- **G3 — censor completions** to `[next start, submission]`, right-censor E04 at 11:30; flow times are inflated by up to 22 min if taken raw.
- **G2 — censor starts**; use end-anchored serial reconstruction (waiting 23 min, service 6.75 min) and report it as hypothesis-conditional (A9).
- **G5 — suppress resource-level metrics**; pool-level utilization (78% of 3) is reportable only as an upper bound on effort, since intervals are case-open durations.
- **G1 — keep, but re-unitise:** cycle-level metrics (3 min per 4 items, 80 items/h); never sum per-item service.

**Require operational validation before any performance conclusion:**
1. **G5** — badge audit and pause/resume capture; the 13:12–13:20 window with concurrency 4 > cap 3 must be resolved as identity aggregation, multitasking, or interval inflation.
2. **G7** — obtain the rounding rule and shadow-time five measures; until then the cluster is unidentifiable, not "a batch".
3. **G8** — measure the scannersafety clock offset and integrate the safety activity; only then can the 38-min wait be called capacity loss rather than unlogged work or an upstream burst.
4. **G6** — confirm whether tickets were resolved before 17:00; this determines whether the 103-min queue is real waiting or a logging illusion.
5. **G1** — verify per-item stamping vs cycle fan-out and confirm the 4-slot fixture; a 4× capacity error hinges on it.
6. **G2** — confirm that "begin group" writes the same start onto all items, and whether the 6–7 min completion increments are serial handling or interleaved inspection.

**Overall stance:** only G4 (and G8's execution segment) support conventional single-server queueing metrics; G1 supports cycle-level metrics; G2, G3, G5 support reconstruction under explicit hypotheses; G6 and G7 support **bounds only**. Identical timestamps were treated throughout as a *temporal pattern* whose physical meaning is supplied by precision metadata, capacity, identity reliability and insertion behaviour — never by the equality itself, and never by a PM4Py batch label.
