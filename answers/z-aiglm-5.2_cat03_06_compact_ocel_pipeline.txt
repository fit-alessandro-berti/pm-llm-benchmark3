## 1. Modeling assumptions

**Object types (exact capitalization):** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. Object identifiers are kept verbatim (`O100`, `I1`, `P1`, `D1`, `V1`, `M1`, …).

**E2O qualifier vocabulary** (per `(event, object)` relation):
- `created` — Order that is created or closed (`Close Order` reuses `closed`).
- `recipient` — Order receiving an added Item.
- `added` — Item being added.
- `reserved` — Item being reserved.
- `involved` — Order *directly* involved in a logistics event at source level (used for the genuinely shared Reserve Stock and Pack P1 events).
- `content` — Item placed into a Package.
- `packed` — Package being packed.
- `dispatched` — Package being dispatched.
- `carrier` — Delivery carrying a Package.
- `billed` — Order billed by an Invoice.
- `issued` — Invoice being issued.
- `recorded` — Payment being recorded.
- `settled` — Invoice being settled by a Payment.
- `propagated` — Order relation that is **not** a source-system fact but an analytical propagation downstream of a Package/Delivery/Invoice. This qualifier is what distinguishes observation from inference (see below).
- `closed` — Order being closed.
- `confirmed` — Delivery being confirmed.

**O2O direction conventions:** relations always point from the *aggregate/container* object to the *constituent/dependent* object, except for the financial chain, which follows the causal direction (Invoice  Order is "bills", Payment  Invoice is "settles"):
- `Order  Item` qualifier `contains`
- `Package  Item` qualifier `packs`
- `Delivery  Package` qualifier `carries`
- `Invoice  Order` qualifier `bills`
- `Payment  Invoice` qualifier `partial_settles` / `completes_settlement`

**Direct vs. propagated relations.** Logistics events (`Dispatch Package`, `Confirm Delivery`) are *not* directly observed against Orders by the source system; only Packages and Deliveries appear on those event records. The relation to Orders is therefore propagated through the O2O graph and is tagged `propagated` so a reviewer can filter it out. Conversely, `Reserve Stock` and `Pack P1` are stated to *operationally* involve both Orders, so they use the `involved` qualifier (a source fact). `Issue Invoice` and `Close Order` are source-direct and use `billed`/`closed`.

**Preventing confusion between observation and propagation.** The qualifier column carries the semantic provenance. Any analysis that wants *only source-system facts* filters `relations.ocel:qualifier != 'propagated'`. Any analysis that wants an *operational end-to-end Order view* keeps the propagated rows. The O2O table is never used to silently mint E2O rows at runtime in the stored dataset — propagation is materialised once, at construction time, and stamped.

**Version-dependent PM4Py assumption.** I assume a recent PM4Py (2.5) where `OCEL(events=…, objects=…, relations=…, o2o=…)` exists in `pm4py.objects.ocel.obj`, and where `pm4py.discover_dfg`, `pm4py.discover_log_skeleton`, `pm4py.ocel_flattening`, `pm4py.discover_ocdfg`, `pm4py.discover_otg`, `pm4py.discover_etot`, `pm4py.discover_oc_petri_net`, `pm4py.ocel_objects_interactions_summary`, `pm4py.ocel_get_object_types`, and `pm4py.ocel_object_type_activities` are importable. If a given PM4Py build splits the OCEL constructor (e.g., requires `parameters={...}` for column names) the only adjustment needed is at the single construction line; the four DataFrames themselves are unchanged.

# ---------------------------------------------------------------------------

etot = pm4py.discover_etot(ocel)

interactions = pm4py.ocel_objects_interactions_summary(ocel)

# ---------------------------------------------------------------------------
# I. Optional visualisations (commented out; require a GUI/matplotlib back-end).

print("\nPipeline complete. Stored: ocdfg, otg, etot, ocpn, interactions, "
      "flattened, dfgs, skeletons.")

- **E7 (Pack P1)** is the principal convergence point: a single event aggregates items I1 (from O100) and I3 (from O200) into one Package, so flattening on `Package` produces a single P1 trace, while flattening on `Order` makes E7 appear in both the O100 and O200 traces — a duplicated shared event that any traditional single-case miner would count twice.
- **E11 (Issue Invoice V1)** converges two Orders into a single Invoice; flattening on `Invoice` collapses both order lifecycles into one V1 trace, losing the order-level differentiation.
- **E12/E15 (Record Payments)** share the V1 invoice: under the `Invoice` flattening these payments look like two steps in one trace; under the `Payment` flattening they become two trivially short, unrelated single-activity traces.

- *O100 trace:* Create Order  Add Item (I1)  Add Item (I2)  Reserve Stock  Pack P1  Pack P2  Dispatch P1  Dispatch P2  Issue Invoice  Confirm Delivery D1  Confirm Delivery D2  Close Order. (Reserve Stock and Pack P1 appear here too because they involved O100.)
- *O200 trace:* Create Order  Add Item (I3)  Reserve Stock  Pack P1  Dispatch P1  Issue Invoice  Confirm Delivery D1  Close Order.
- *Copied shared events:* E6 (Reserve Stock), E7 (Pack P1), E9 (Dispatch P1), E11 (Issue Invoice), E13 (Confirm D1) appear in **both** traces — a classic divergence problem.
- *Omitted aspects:* the Payment events (E12, E15) are not directly attached to Orders, so they vanish from the Order log; Invoice-level payment semantics are lost.
- *Likely DFG edges:* Create Order  Add Item  (Reserve Stock  Pack Package  Dispatch Package)*  Issue Invoice  Confirm Delivery  Close Order. The payment gap looks like a missing branch between Issue Invoice and Close Order.
- *Misleading interpretation:* the Order DFG suggests Reserve Stock / Pack P1 happened *twice*, once per order, and hides that P1 physically merged items from two different customers.

**Package flattening.** Two cases: P1, P2.
- *P1 trace:* Pack Package  Dispatch Package  (Confirm Delivery D1 — propagated from D1).
- *P2 trace:* Pack Package  Dispatch Package  Confirm Delivery D2.
- *Copied shared events:* none across packages, but E7 only — items I1, I3 are not the case id, so the Order dimension is gone.
- *Omitted aspects:* creation of the orders, reservation of stock, invoicing, payment, closing — i.e., almost everything outside logistics.
- *Likely DFG edges:* Pack Package  Dispatch Package  Confirm Delivery. Very linear.
- *Misleading interpretation:* the Package view suggests packaging is fully decoupled from sales and finance, which is false at the process level.

**Delivery flattening.** Two cases: D1, D2.
- *D1 trace:* Dispatch Package (E9)  Confirm Delivery (E13). P1's Pack event is *not* attached to D1 (only the Dispatch is), so the trace is short.
- *D2 trace:* Dispatch Package (E10)  Confirm Delivery (E14).
- *Copied shared events:* none.
- *Omitted aspects:* everything upstream of dispatch, all payment flows.
- *Likely DFG edges:* Dispatch Package  Confirm Delivery.
- *Misleading interpretation:* Deliveries look like a self-contained two-step subprocess with no link to orders or invoices; one might wrongly conclude that confirmation does not depend on packing.

**Invoice flattening.** One case: V1.
- *V1 trace:* Issue Invoice  Record Payment (M1)  Record Payment (M2). Possibly Confirm Delivery events too if their propagated Order relations are kept, but with `propagated` excluded, V1's trace contains only the three financial events.
- *Copied shared events:* none across cases (only one case).
- *Omitted aspects:* order creation, items, packaging, delivery — the entire fulfilment side collapses to a single object.
- *Likely DFG edges:* Issue Invoice  Record Payment  Record Payment.
- *Misleading interpretation:* V1 looks like a stand-alone billing subprocess; the fact that V1 bills *two* orders is invisible because Order is not the case id.

**Why Payment flattening is especially weak.** Each Payment is a single event in a single case. M1's trace is `[Record Payment]` and M2's trace is `[Record Payment]`. There are no edges to discover, no variants, no concurrency. Payment is intrinsically a leaf in the object graph — the only thing connecting M1/M2 to the rest of the process is the O2O edge `Payment  Invoice`, which flattening destroys. So the Payment view produces two trivial one-event logs and zero usable structural information.

## 5. Expected object-centric structures

**OC-DFG.** Expect edges `Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Confirm Delivery` at the level of object types, plus a separate branch `Issue Invoice  Record Payment` that joins `Order` to `Invoice`/`Payment`. The OC-DFG should make visible that `Reserve Stock` synchronises two `Item` tokens (I1, I3) and two `Order` tokens (O100, O200), and that `Pack Package` consumes items belonging to two different Orders. P1 should appear as the locus where the I1/O100 and I3/O200 paths converge into a single `Package` token, and `Dispatch Package` followed by `Confirm Delivery` is where the Package path diverges back to two Orders.

**OTG (Object-Type Graph).** Expected interactions:
- `Order  Item` through `Add Item`, `Reserve Stock`, `Pack Package`.
- `Item  Package` through `Pack Package`.
- `Package  Delivery` through `Dispatch Package`, `Confirm Delivery`.
- `Order  Invoice` through `Issue Invoice`.
- `Invoice  Payment` through `Record Payment`.
The OTG should show P1 as the structural reason `Order` and `Package` are coupled in two directions: P1 *packs* items from both O100 and O200, so the `Package  Item  Order` triangle is non-trivial. It should also expose that V1 is a single `Invoice` object coupled to *two* `Order` objects — a many-to-many OTG arc.

**ET–OT (Event-Type / Object-Type graph).** Expected to show `Reserve Stock`, `Pack Package` (for P1) and `Issue Invoice` as **synchronising** event types (multiple object types of the same kind consumed/produced at once). E6 should appear with both `Order` and `Item` columns populated for two distinct OIDs each, and E7 likewise for two `Order` + two `Item` + one `Package`. Conversely, `Close Order`, `Record Payment`, and `Confirm Delivery` should appear as mono-type event types per occurrence.

**Object-centric Petri net.** The OCPN should contain places for each object type with typed tokens, transitions per activity, and — crucially — *synchronising transitions* at `Reserve Stock`, `Pack P1`, `Issue Invoice V1` and `Record Payment` (against V1). It is *not* uniquely determined: depending on the miner's parameters, `Dispatch P1`/`Confirm D1` may either (a) only consume/produce `Package` and `Delivery` tokens and leave `Order` tokens untouched (no propagated relations), or (b) consume/produce `Order` tokens too (with propagated relations). P1, by spanning O100 and O200, is the place where a single transition may produce two `Order` token movements from one event firing — the canonical OCPN convergence signature. V1, similarly, is where two `Order` tokens collapse into one `Invoice` token; M1 and M2 are two `Payment` firings that consume the same `Invoice` token in succession.

**Object-interactions summary.** Expect to see explicitly that:
- I1 interacts with both O100 (Add Item, Reserve Stock, Pack Package) and P1 (Pack Package, via the O2O `packs` edge) — a hub object.
- I3 interacts with O200 and P1.
- P1 interacts with I1, I3, D1, and (propagated) O100 and O200.
- V1 interacts with O100, O200, M1, M2 — the financial hub.
- M1 and M2 each interact only with V1, confirming that Payment is a leaf.

## 6. Modeling alternatives

**Alternative A — Source-minimal relations.** Drop every `propagated` row. Logistics events are only ever related to Package/Delivery; invoicing only to Invoice; payment only to Payment and Invoice. Order traces stop at `Issue Invoice`. *Effect on discovery:* the Order DFG becomes shorter and stops at `Issue Invoice`; Package/Delivery/Invoice traces are unaffected. The OCPN loses the synchronisation between `Dispatch P1`/`Confirm D1` and the `Order` place, making P1's cross-order nature invisible at the Order level. The business story is unchanged, but the *process* picture looks more decoupled than it really is operationally.

**Alternative B — Full operational involvement.** Tag *all* logistics events (`Dispatch Package`, `Confirm Delivery`) as `involved` for the Orders whose items transit through that Package/Delivery, not as `propagated`. *Effect on discovery:* the Order DFG gains `Dispatch Package` and `Confirm Delivery` steps for both O100 and O200; P1's events appear under both orders without an explicit "this is inference" flag. Discovery is richer, but a reader can no longer tell which relations were observed by the source system and which were derived — a traceability loss.

**Alternative C — O2O-only analytical propagation at query time.** Do not materialise propagated E2O rows at all. Instead, store only source relations and rely on a PM4Py flattening that *traverses* the O2O graph (e.g., expanding a Package's items' orders) when the user requests an Order view. *Effect on discovery:* the stored OCEL is smaller and free of inference; the on-the-fly Order log is identical to Alternative B but is clearly a derived artefact. The downside is that PM4Py's built-in `ocel_flattening` does not, by default, walk O2O edges, so this requires custom code and is more brittle across PM4Py versions.

**Alternative D — Package-level payments (rejected here).** Attach M1 and M2 to Orders via a fraction split (e.g., M1 settles 40% of O100's bill). *Effect:* the Order log would suddenly contain `Record Payment` steps, but the allocation is a business assumption that the narrative does *not* license (V1 bills *both* orders jointly; amounts are not split). Adding such E2O rows would silently mint facts not present in the source — exactly the failure mode the `propagated` qualifier exists to prevent.

## 7. Failure modes

1. **Relation inflation.** Adding propagated E2O rows for every transitive O2O hop (e.g., D1  P1  I1  O100 and D1  P1  I3  O200, and also D1  P1  I1, etc.) multiplies relation rows; flattening then double/triple counts events. Mitigation: propagate only the *minimal* set needed for analysis and tag with `propagated`.
2. **Missing direct E2O links.** Forgetting to relate E6 (`Reserve Stock`) to both O100 and O200, or E11 (`Issue Invoice`) to both orders, destroys the convergence structure that the OCPN is supposed to surface.
3. **Treating O2O propagation as observation.** Reporting `Dispatch P1` as a "fact about O200" in a flattened Order log, without a qualifier, misrepresents an inference as a source-system observation and breaks audit traceability.
4. **Duplicate shared events after flattening.** E7 appears in both the O100 and O200 flattened traces; a naive frequency count then reports `Pack Package` happening twice when it happened once. Reviewers must read counts in the OCEL, not in a flattened log.
5. **Ambiguous payment allocation.** Treating M1's 100 units as "O100's payment" because it appears first is unjustified — V1 bills both orders jointly, and there is no per-order split in the narrative.
6. **Overly short Payment traces.** Flattening on `Payment` yields two one-event cases (`[Record Payment]` × 2); running a discovery algorithm produces an empty/tautological model. Payment should be analysed only through the O2O `settles` edge into V1.
7. **Constructor/API version mismatch.** Different PM4Py builds rename the OCEL constructor signature, the qualifier column, or move `discover_etot`/`discover_otg`. The construction line must be isolated so the four DataFrames remain semantically identical across builds.
8. **False total order for same-time events.** Although this scenario has no timestamp ties, a sorter that uses `(ocel:timestamp, ocel:eid)` *as if* the second key were a logical order can produce a misleading "happened-before" relation; sort keys are tie-breakers, not causal evidence.
9. **O2O direction misuse.** Storing `Item  Order` instead of `Order  Item` for `contains`, or `Invoice  Payment` instead of `Payment  Invoice` for `settles`, silently reverses the semantic reading of the qualifier and can corrupt O2O-based propagations.
10. **Type case drift.** Writing `order`/`Order` inconsistently makes `ocel_object_type_activities` report two separate types and breaks flattening lookups.

## 8. Final semantic checks

A reviewer can verify the construction against the narrative by inspecting:

1. `objects` contains exactly 12 rows with types `Order`×2, `Item`×3, `Package`×2, `Delivery`×2, `Invoice`×1, `Payment`×2.
2. `events` contains exactly 17 rows, `ocel:eid` is unique, and `E12`/`E15` carry `payment_amount` of 100 and 150 respectively; all other rows have `None`.
3. All timestamps are timezone-aware UTC and E14, E15, E16, E17 are on 2026-04-07; everything else on 2026-04-06.
4. Relations for E7 (`Pack P1`) include exactly one `Package` row (P1), two `Item` rows (I1, I3) and two `Order` rows (O100, O200) with qualifier `involved`.
5. Relations for E11 (`Issue Invoice V1`) include exactly one `Invoice` row (V1) and two `Order` rows (O100, O200) with qualifier `billed`.
6. `o2o` contains 12 rows; the `bills` qualifier appears exactly twice (V1O100, V1O200) and the `packs` qualifier appears exactly three times, with P1 linked to both I1 and I3.
7. No relation row has `ocel:qualifier == "propagated"` for E1–E8 or E11–E12, E15–E17; only E9, E10, E13, E14 carry `propagated`, and only against `Order` objects.
8. The merged `events`/`relations` check confirms that for every `(eid)` the `ocel:activity` and `ocel:timestamp` columns match exactly.
9. The `o2o` row `(M2, V1, "completes_settlement")` exists and `(M1, V1, "partial_settles")` exists; no Payment row points to anything other than V1.
10. `pm4py.ocel_object_type_activities(ocel)` returns `Order` touching at least `Create Order`, `Add Item`, `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Issue Invoice`, `Confirm Delivery`, `Close Order`; `Payment` touches only `Record Payment`; `Invoice` touches only `Issue Invoice` and `Record Payment`.
