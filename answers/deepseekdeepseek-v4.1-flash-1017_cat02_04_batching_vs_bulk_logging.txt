    if prec == 1:

    if prec == 60:
        return float((ts.dt.second == 0).mean())

# 3. Consequences for performance analysis

**G1 (RBT-7 fixture).** If this is a genuine simultaneous batch, waiting from `queue_arrival` to 09:00 is the time until fixture start; early arrivals may have waiting inflated if items were actually loaded before 09:00. Service time per item as 09:0309:00=3 min is defensible as fixture occupancy, but summing four 3-min services gives 12 min of work in a 3-min window and can falsely show >100% utilization if capacity=4 is ignored. Throughput is 4 items per 3 min; bottleneck should be modeled as fixture capacity 4, not four serial resources.

**G2 (T-B inspection group start).** The common 10:00 start likely overstates overlap and understates per-item queue waiting for later cases if actual inspection occurred sequentially after 10:00. Service times computed as completion10:00 are 8, 14, 21, and 27 min; these likely overestimate individual service and double-count group setup/wait. Treating T-B as one resource while all cases are active from 10:00 can drive utilization above 100% and create a false bottleneck. A group-start model with serial completions is more defensible.

**G3 (T-C common completion).** The common 11:30 completion likely reflects form submission after finishing folders, not true completion for every case. Waiting from arrival to start may be less biased if starts are true review starts, but service times are overestimated for cases actually finished earlier. Utilization appears high because all reviews remain “open” until 11:30 under one T-C, which can inflate bottleneck severity and create conformance anomalies. Actual completion should be interval-censored before `recorded_at`.

**G4 (T-D serial FIFO).** With 1-sec scanner precision, waiting and service are relatively credible: each item waits 7–19 min and receives 4 min of service. Mistaking this sequential pattern for a simultaneous batch would understate some waiting and distort service/utilisation, but the data themselves support single-server serial processing. Bottleneck is T-D capacity 1 during 12:05–12:25; queue build-up is due to arrival rate exceeding 4-min service, not necessarily downtime.

**G5 (analyst_pool shared VDI).** Overlaps may be genuine concurrent analysis or a shared-account artifact. Waiting to first start is about 15–16 min for all cases, but individual queue waiting depends on which analyst picked up which case. Service times are 10–25 min. If `analyst_pool` is treated as one resource, summed service time is about 70 min over 30 min, implying >200% utilization and a false individual bottleneck. If treated as a pool of up to three analysts, utilization is closer to 70/(3×30)78%, but individual workloads remain unidentified. Conformance checks assuming one resource per case may flag overlaps.

**G6 (manual bulk close).** `start=complete=17:00` forces service time to 0 for every case. Waiting from `queue_arrival` to 17:00 becomes 35–175 min, which can be inflated if work started earlier or was interleaved. This is exactly how G6-like data produce both inflated waiting and near-zero service: the original arrival remains real, but the bulk close writes a synthetic common end-of-shift start/end, so all elapsed time is charged to waiting and no time to service. Utilization appears zero until 17:00 then instantaneous, bottleneck detection is impossible, and throughput appears as a single burst.

**G7 (legacy MES quarter-hour rounding).** Rounded starts can precede queue arrival, producing negative waits for M02–M05 and biasing waiting downward. All service times appear as 15 min; five such services in one 15-min bucket create >100% utilization if T-G is treated serially, which is likely a coarsening artifact or an unresolved batch. Throughput appears as a 14:15 burst. Waiting, service, utilization, and bottleneck estimates should be interval-censored to the stated 15-min precision rather than treated as exact.

**G8 (safety-check capacity loss).** Waiting from 15:00–15:08 arrivals to 15:38–16:06 starts is 38–58 min; much of this is likely forced waiting during the safety-check interval 15:00–15:35. If downtime is ignored, T-H looks inefficient. Service time of 7 min per case is credible if scanner precision and clocks are trusted. def overlap_rate_for_group(g):
    n = len(g)
    if n < 2:
        return 0.0, 0
    intervals = list(zip(g["start"], g["complete"]))
    overlap_pairs = 0
    for i in range(n):
        for j in range(i + 1, n):
            s1, e1 = intervals[i]
            s2, e2 = intervals[j]
            if pd.notna(s1) and pd.notna(e1) and pd.notna(s2) and pd.notna(e2):
                if max(s1, s2) < min(e1, e2):
                    overlap_pairs += 1

        q += delta

# 5. Robustness and alternative explanations

**Resource IDs trusted vs treated as shared accounts.** If `analyst_pool` is trusted as one worker, G5 contains impossible overlap: four cases are active around 13:12–13:20 while one resource should be serial. Under that interpretation one would have to call the data corrupt, or invoke multitasking. If `analyst_pool` is treated as a shared account for up to three analysts, most overlap becomes plausible pool concurrency, but four concurrent active cases still exceed stated capacity and require multitasking, 1-min timestamp coarsening, or an unrecorded fourth analyst. For G1, trusting `RBT-7` as a four-item fixture makes simultaneous batch plausible; if it were a shared login, the same timestamps would be much less interpretable. G2 and G3 use single workstation IDs; if those IDs were actually shared or batch-entry accounts, common starts/ends could reflect shared logging rather than one worker’s batch.

**Timestamps exact vs interval-censored by stated precision.** For G1 and G4, 1-sec precision makes exact start/complete equality and adjacency strong evidence. For G2, G3, G5, G6, and G8, 1-min precision still permits most qualitative conclusions, but exact second-level ordering should not be overinterpreted. For G7, the 15-min precision is dominant: 14:00 and 14:15 are buckets, so identical starts/ends and negative waits are expected artifacts. Under interval censoring, G6’s 17:00 start/complete becomes “somewhere before or at the bulk-entry time,” not a zero-duration service. G8’s safety interval must be clock-aligned before treating 15:38 as the true post-downtime start.

**Same temporal pattern supporting multiple physical explanations.**  
- G1: identical start and end for four cases could be a genuine four-item fixture batch, or fixture-level PLC logging of a common setup/load followed by one completion signal.  
- G3: common completion at 11:30 could be end batching/bulk submission, end-of-folder form entry, timestamp coarsening, or several reviews completed earlier but submitted together.  
- G5: overlapping intervals could be genuine concurrent work by multiple analysts under one shared login, one analyst multitasking, a shared-account artifact, or coarse timestamps merging near-simultaneous work.  
- G6: start=complete=17:00 could be a manual bulk-close form, end-of-shift data entry, timestamp coarsening, or a backlog cleared at the end of shift; the source semantics strongly favor bulk submission but do not prove physical execution.  
- G7: five cases starting at 14:00 and ending at 14:15 could be a real batch, start/end batching, or simply 15-min rounding; the rounding rule makes physical simultaneity non-identifiable.

# 6. Data-collection redesign

1. **Capture item-level execution start/complete separately from group/setup events.** Record true per-item start, pause/resume, and complete, plus separate fixture/group “begin group” and “end group” events. This is the highest priority for G1, G2, G3, and G6.
2. **Separate source execution time, local device time, and database `recorded_at`.** Preserve all three, with timezone and clock offsets. For G6, a bulk form must record “actual work start/end” independently of the submission timestamp.
3. **Synchronize clocks across PLC, tablet, desktop form, legacy MES, scanner, safety system, and database.** Log offset and last sync time. G8 cannot be interpreted confidently without aligning safety and repair clocks; G7 needs clock metadata because negative waits indicate mismatch or rounding.
4. **Retain badge-level resource identity and pool membership.** For `analyst_pool`, record actual badge ID, pool ID, and concurrent capacity. For workstation IDs, record whether the ID is a device, a login, a team, or a shared account.
5. **Emit explicit group/batch identifiers and capacity metadata.** For RBT-7, include fixture ID and capacity=4. For T-B, include group ID and per-item sequence. For T-C and T-F, include folder/batch ID and whether completion means physical finish or administrative submission.
6. **Log pause/resume, blocking, downtime, and reason codes.** For T-H, record safety-check start/end and repair-resource availability. For T-D/G4, log starvation vs blocked vs processing so queue build-up is not mistaken for batching.
7. **Store timestamp precision and rounding rules as metadata.** For legacy MES, include documented rounding rule, original unrounded value if available, and interval bounds. For manual forms, include whether timestamps are auto-filled at submission or manually entered.
8. **Add batch-aware conformance and performance rules.** Distinguish physical capacity from logging capacity: a four-item fixture should not be validated as four serial services; a bulk form should not be validated as zero-duration work.

# 7. Final adjudication

**High-confidence interpretations.** G1 is highly likely a genuine four-item fixture batch or fixture-level common start/end, with capacity=4. G2 is best interpreted as start batching/common setup with separate completions. G3 is best interpreted as end batching/bulk submission or common completion. G4 is serial FIFO processing, not physical batching. G6 is almost certainly a bulk-close/logging batch, not physical zero-duration work. G7 is dominated by 15-min timestamp coarsening. G8 is best interpreted as a safety/downtime backlog followed by serial drain, subject to clock synchronization.

**Exclude or interval-censor in queue analysis.** G6 should not contribute start/complete service times; use `recorded_at` only as an upper bound and interval-censor actual work between `queue_arrival` and `recorded_at`. G7 must be interval-censored to 15-min windows and negative waits should not be treated as real. G3 completion should be interval-censored to before the form-submission/recorded time. G2 common start should be treated as a group-start timestamp, not per-item physical start. G8 waits should be adjusted for safety/downtime and clock skew.

**Require operational validation before performance conclusions.** G5 requires badge-level validation: the shared `analyst_pool` cannot support individual utilization or bottleneck conclusions until actual analyst identities and pool capacity are known. G2 and G3 need confirmation of whether completion means physical completion or administrative submission. G7 needs the actual MES rounding rule and original timestamps. G8 needs confirmation of the safety-check/repair clock offset and whether T-H was truly unavailable from 15:00–15:35. G1 is interpretable but should still be validated that PLC events are fixture-level rather than item-level.
