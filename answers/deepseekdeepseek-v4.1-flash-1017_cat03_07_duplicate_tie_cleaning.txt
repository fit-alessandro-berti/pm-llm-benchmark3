def topological_order(eids, edges, priority=None):
    from collections import defaultdict
    import heapq
    eids = list(eids)
    priority = priority or {e: (0,str(e)) for e in eids}
    indeg = {e:0 for e in eids}
    adj = defaultdict(list)
    for a,b in edges:
        if a in indeg and b in indeg:
            adj[a].append(b); indeg[b]+=1
    heap = [(priority[e], e) for e in eids if indeg[e]==0]
    heapq.heapify(heap)
    out=[]
    while heap:
        _,e=heapq.heappop(heap); out.append(e)
        for n in adj[e]:
            indeg[n]-=1
            if indeg[n]==0: heapq.heappush(heap,(priority[n],n))
    if len(out)!=len(eids): raise ValueError("cycle")
    return out
```

## 1. Duplicate-handling decision tree

For each candidate group sharing activity and/or timestamp, and possibly objects:

1. **Is it an exact technical duplicate?** Same original source event key, same payload hash, same source, same activity and timestamp, and identical relation set.  
    **Drop later/redundant copy**, keep one canonical event, retain alias/provenance. If any attribute or relation differs, go to 2.

2. **Is there strong reconciliation evidence of one physical event observed by multiple systems?** Example: e03/e04, same physical scan recorded by WMS and scanner, despite enrichment differences.  
    **Merge attributes and relations into one canonical event**. Prefer source-authoritative attributes by field; keep conflicting payloads under provenance. If no reconciliation evidence, go to 6.

3. **Is one event a derived summary/status from a detailed event?** Example: detailed WMS pack transaction plus ERP status generated from a WMS message; ERP invoice/payment summary.  
    If derivation is explicit and the summary adds no independent lifecycle step, **merge into the detailed event** in an evidence-based scenario, preserving both. Otherwise **retain both with refined labels** such as `WMS detail` and `ERP status/summary`.

4. **Is this a harmonization collision?** Same harmonized label but different original source activity semantics, e.g. warehouse release vs carrier acceptance both mapped to `Dispatch Package`.  
    **Retain both and refine labels/qualifiers** using original source activity; do not merge solely because the harmonized label and objects coincide.

5. **Are these concurrent same-label events involving different objects?** Example: e13/e14 use different Payment objects M1/M2 while sharing O1/V1.  
    **Retain both unchanged or object-qualified**. Never merge by common order/invoice alone.

6. **Unresolved candidate?** Same label/time/object set, no authoritative key, conflicting source semantics.  
    **Quarantine for review** or retain both with qualifiers. Do not drop.

## 3. Timestamp-tie ordering rules

Use a two-stage policy. First construct a semantic partial order; only then derive a deterministic total order for tooling. Original timestamps remain unchanged.

**Semantic/justified rules**
- Domain constraints from source facts: e12 < e13 for M1; e09 < e10; e15 after payment messages e12/e13/e14; picks before packing when the packing event includes picked items; packing before dispatch; dispatch before delivery confirmation.
- Shared-object lifecycle: for the same item/package/order, do not place `Pack Package` before the picks it contains, nor `Confirm Delivery` before dispatch/handover.
- Source-specific semantics: e08 warehouse release before e09 carrier acceptance before e10 handover, unless later evidence proves e08/e09 are one transition.
- Within-source sequence: meaningful only within one source, e.g. PSP sequence 400<401<402 can stabilize e12 before e13 and e13 before e14, but it is not proof of global business concurrency behavior.

**Deterministic, non-semantic rules**
- Stable fallback by canonical eid/source key.
- Ingestion time may be recorded but is not a business order; do not use it as primary ordering.
- Optional synthetic order timestamps may be added only after the semantic DAG and deterministic fallback are fixed.

Do not add microseconds before deciding order. If we set e03/e04/e05 to 10:00:00.001/.002/.003, e13/e14 to .001/.002, etc., we invent a physical sequence, alter durations, and encode ingestion/canonical order as business causality. It can falsely turn concurrent picks or partial payments into precedence.

**Intended orders/alternatives**
- 10:00 e03–e07: canonical e03/e04 merged; e05 is a distinct I2 pick. Admissible: e03 and e05 concurrent before e06; e06 before e07 if retained as ERP status. Deterministic fallback: e03  e05  e06  e07.
- 10:15 e08–e10: e08 release  e09 carrier acceptance  e10 handover. Alternative: if e08/e09 are later confirmed as one transition, merge them in an evidence-based scenario; otherwise do not.
- 12:00 e11–e16 after merges: e11/e16 merged as Invoice V1. Semantic constraints: e12 < e13; e15 after e12/e13/e14. e14 is independent of e13. Admissible total orders include e11  e12  e13  e14  e15 or e11  e12  e14  e13  e15, with e15 last. Deterministic fallback may put e13 before e14 by PSP source sequence, but this is not proof of true payment order.

    ocel_conservative, "e11", "e16",
    "same_invoice_V1_authoritative_attributes", refined_activity="Issue Invoice"

    ocel_conservative.events.get("refined_activity", ocel_conservative.events["activity"])

ocel_conservative.events.loc["e06", "refined_activity"] = "Pack Package (WMS detail)"

# 3. Semantic DAG, then deterministic total order
edges = [
    ("e03", "e06"), ("e05", "e06"), ("e06", "e07"), ("e06", "e08"),
    ("e08", "e09"), ("e09", "e10"), ("e10", "e17"),

    seq = list(g.index.astype(str))
    edges += list(zip(seq, seq[1:]))

order = topo_order(ocel_conservative, edges)
ocel_conservative.events["clean_order"] = (
    ocel_conservative.events.index.astype(str).map({e: i for i, e in enumerate(order)})
)
ocel_conservative = pm4py.ocel_sort_by_additional_column(ocel_conservative, "clean_order")

# Add synthetic timedelta only after order is fixed; original timestamp remains.
try:
    ocel_conservative = pm4py.ocel_add_index_based_timedelta(
        ocel_conservative, "timestamp", "order_timestamp"
    )
except TypeError:
    ocel_conservative = pm4py.ocel_add_index_based_timedelta(
        ocel_conservative, timestamp_column="timestamp", index_column="clean_order"
    )
validate(ocel_conservative)

# 4. Evidence-based merge alternative: only after reviewer confirmation
ocel_evidence = normalize(clone(ocel_conservative))
ocel_evidence = merge_verified_pair(
    ocel_evidence, "e06", "e07",
    "reviewed_same_pack_transition_detail_plus_ERP_status",

# 5. Aggressive library scenario: separate copy, explicit warning
ocel_aggressive = normalize(clone(ocel_conservative))

## 7. Sensitivity analysis

| Dataset | Event/E2O count | Main effects |
|---|---:|---|
| Raw | 17 / 44 | Same-time events create apparent concurrency and duplicate labels; e13/e14/e15 all look like `Capture Payment`; e08/e09 look like duplicate dispatch. |
| Conservative | 15 / 39 | Removes verified scan and invoice duplicates; keeps abstraction and distinct payments; refines e08/e09/e10 and e15. |
| Evidence-based merge | about 14 / 37 | Also merges e06/e07 if confirmed; reduces apparent pack rework but risks erasing ERP status. |
| Aggressive library merge | about 10–12 / varies | May collapse e03/e04/e05, e06/e07, e08/e09, and e13/e14/e15; creates false simplification and false object co-occurrence. |

Concrete interpretation changes:
1. Raw `e03/e04` duplicate increases Pick Item–Item frequency for I1; conservative halves it.
2. Aggressive `e03/e04/e05` merge creates a synthetic event containing I1 and I2, adding false I1–I2 OTG relation.
3. Raw e06/e07 yields two pack-like steps for P1; evidence merge removes one, changing Order/Item DFG and apparent rework.
4. Raw e08/e09 both `Dispatch Package` can create a self-loop or duplicate dispatch; refined conservative shows release  carrier acceptance; aggressive merge shortens logistics and hides release.
5. Raw e11/e16 duplicates invoice issuance V1; conservative merge removes invoice rework.
6. Aggressive e13/e14 merge hides M2 and creates a synthetic M1–M2 relation; Payment-flattened DFG loses one capture path.
7. Refining e15 from `Capture Payment` to Payment Summary removes false capture/rework after e13/e14 and changes ET–OT weights for Capture Payment–Payment.
8. e12e13 authorizecapture M1 changes durations if e13 is merged or reordered; performance metrics must use original timestamps plus explicit `clean_order`, not synthetic microseconds as real time.

OTG relations change mainly when aggressive merging combines object sets, e.g. adding I1–I2 or M1–M2 co-occurrence. ET–OT weights change when duplicate events are removed or e15 is reclassified. OC-DFG frequencies should be reported as event-frequency counts per clean order, with a sensitivity flag for unresolved/merged candidates.

## 8. Audit trail and reversibility

Use an immutable raw OCEL plus an append-only merge/provenance log keyed by canonical event ID.

Required schema fields:
- `canonical_eid`
- `source_event_ids` array
- `merge_rule` and `rule_version`
- `reviewer_or_process`
- `original_activity`, `refined_activity`
- `original_timestamp`, `order_timestamp`, `clean_order`
- `source`, `source_event_key`, `payload_hash`
- `attributes_retained_by_source` JSON
- `discarded_conflicts` JSON
- `relations_from_each_source` JSON or original E2O relation snapshots
- `confidence`, `reason`, `alternative_scenario`

To reconstruct the raw view, load the frozen raw backup or expand the alias table: for each canonical event, restore all source event IDs, original activities, original timestamps, source-specific attributes, and original E2O relations from the snapshots. Merged synthetic attributes and refined labels remain in the audit log but are not substituted back. Because raw is immutable and relation snapshots are retained, analysts can reproduce conservative, evidence-based, and aggressive views without guessing.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments** e13/e14 by common O1/V1. Safeguard: require full object-set difference analysis; never merge if Payment objects differ.
2. **Converting abstraction-level updates into false rework** e06/e07 or e15. Safeguard: refine labels and keep summary/status events unless derivation is reviewed.
3. **Ordering by ingestion time**. Safeguard: use ingestion only as audit metadata; primary order is semantic DAG plus deterministic fallback.
4. **Treating shared objects as proof of duplication**. Safeguard: check object roles, complete object sets, source keys, and source-authoritative semantics.
5. **Unioning incompatible E2O relations**. Safeguard: merge relations only for verified same business event; otherwise keep separate and record conflicts.
6. **Changing durations through synthetic microseconds**. Safeguard: preserve original timestamp and add any synthetic order timestamp only as a derived field after semantic ordering.
7. **Losing source-authoritative attributes** during e11/e16 merge. Safeguard: store per-source attributes separately; never overwrite Billing fields with ERP defaults without authority rules.
8. **Applying duplicate functions to the whole OCEL without candidate inspection**. Safeguard: pre-check candidate groups, run aggressive functions on separate copies, and validate resulting relations.
9. **Ignoring harmonization collisions** such as e08/e09. Safeguard: maintain original activity labels and refine harmonized labels.
10. **Destroying reversibility** by editing raw in place. Safeguard: immutable raw hash plus append-only provenance and relation snapshots.
