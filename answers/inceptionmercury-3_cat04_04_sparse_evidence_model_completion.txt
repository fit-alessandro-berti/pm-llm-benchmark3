A key point about the DFG: an edge such as `Credit Check  Engineering Review` means that in those cases Credit Check was completed immediately before Engineering Review in the log. The reverse edge means other cases had the opposite completion order. Both directions can be produced by alternative sequential choices, by a parallel region whose completion order varies, by activity overlap, or by ingestion-order artifacts. The existence of both directions does not by itself prove concurrency, and the absence of a direction does not prove that concurrency is impossible.

# 2. Shared Assumptions

- **Completion semantics.** Every observed event is a completion. “Before” always means “completed before” in the visible trace. Activity start times and durations are unknown.
- **Same-timestamp ordering.** If two activities have the same completion timestamp, the ingestion order determines the trace order. We do not interpret that as proof of simultaneity.
- **Single execution.** Each activity label appears at most once per case in the observed data. We model no loops or repeats for `Register Order`, `Credit Check`, `Engineering Review`, `Supplier Confirmation`, `Expedite Review`, `Approve Configuration`, `Release Production`, or `Archive Case`.
- **Start/end and approval suffix.** `Register Order` is first, `Archive Case` is last, and all 30 traces show `Approve Configuration  Release Production  Archive Case` as the suffix. We adopt this suffix in all models. D2 only implies `Approve Configuration` before `Release Production`, but we additionally assume there are no unobserved activities between them in the current activity scope.
- **Missing Supplier Confirmation data.** Absence of `Supplier Confirmation` is represented as a skip/optional branch. This deliberately conflates the two possible explanations:
  1. the component was stocked, so Supplier Confirmation was not required;
  2. the event was lost by the integration system.
  Since the external/stocked attribute is absent, this conflation is unavoidable in the control-flow model.
- **Optionality representation.** Optional activities are represented with silent transitions in XOR choices: `XOR(tau, activity)` for one optional activity, or an enumerated any-order optional block for two optional activities.
- **No probabilities.** The trace counts are not encoded as weights or frequencies. The models are qualitative control-flow hypotheses.
- **No causal interpretation.** The accepted completion order in a model is an abstraction, not a statement that one activity causes the next.
- **S1 not used.** S1 conflicts with 11 observed traces containing Engineering Review before Credit Check and with S2. We do not enforce S1 in any candidate, but we flag it in the uncertainty statement.

# 3. Conservative Candidate

## Inductive bias

The conservative model assumes the observed 30 traces are exhaustive: any completion order not observed is treated as unsupported. This maximizes fidelity to the sample and produces a high-precision baseline, but it intentionally overfits. It does not use the medium-confidence domain rules to invent unobserved interleavings.

## Compact formal expression

\[
M_C = \oplus(
\rightarrow(R,C,E,S,A,P,Z),
\rightarrow(R,E,C,S,A,P,Z),
\rightarrow(R,C,E,A,P,Z),
\rightarrow(R,E,C,A,P,Z),
\rightarrow(R,C,S,E,A,P,Z),
\rightarrow(R,C,E,S,X,A,P,Z),
\rightarrow(R,E,C,X,S,A,P,Z)
)
\]

where \(R\) = Register Order, \(C\) = Credit Check, \(E\) = Engineering Review, \(S\) = Supplier Confirmation, \(X\) = Expedite Review, \(A\) = Approve Configuration, \(P\) = Release Production, \(Z\) = Archive Case, and \(\oplus\) means XOR choice.

## PM4Py code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def pt(operator=None, label=None, children=None):
    t = ProcessTree(operator=operator, label=label)
    if children:
        t.children = list(children)
    return t

def leaf(label):
    return pt(label=label)

def seq_labels(labels):
    return pt(operator=Operator.SEQUENCE, children=[leaf(x) for x in labels])

def xor_nodes(*nodes):
    return pt(operator=Operator.XOR, children=list(nodes))

def fix_parents(t, parent=None):
    t.parent = parent
    for c in t.children:
        fix_parents(c, t)

conservative_variants = [
    ["Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
     "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Engineering Review", "Credit Check", "Supplier Confirmation",
     "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Credit Check", "Engineering Review",
     "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Engineering Review", "Credit Check",
     "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Credit Check", "Supplier Confirmation", "Engineering Review",
     "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
     "Expedite Review", "Approve Configuration", "Release Production", "Archive Case"],
    ["Register Order", "Engineering Review", "Credit Check", "Expedite Review",
     "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case"],
]

model_conservative = xor_nodes(*[seq_labels(v) for v in conservative_variants])
fix_parents(model_conservative)
```

## Behavior deliberately excluded

- Any unobserved ordering of `Credit Check`, `Engineering Review`, and `Supplier Confirmation`.
- Any trace with `Expedite Review` but no `Supplier Confirmation`, e.g. `R,C,E,X,A,P,Z`.
- Any trace with `Supplier Confirmation` completed before both visible check completions.
- Any repeated activity, loop, or trace that does not start with Register Order or end with Archive Case.

## Known underfitting risks

- New but legitimate interleavings will be rejected.
- The model cannot distinguish missing Supplier Confirmation events from true stock skips.
- The model ignores the medium-confidence rules D4, D5, and D6.
- Duplicate labels across branches make the model less compact and scaling to more variants is linear but increasingly costly for alignments.

# 4. Balanced Candidate

## Inductive bias

The balanced model accepts the observed traces and generalizes only where a domain rule explicitly justifies the generalization. It is a finite partial-order language: Credit Check and Engineering Review may complete in either order, Supplier Confirmation may visibly appear after the first completed check or after both checks, and Expedite Review may appear before or after Supplier Confirmation once both checks are complete.

## Decision between sequence, concurrency, and partial order

- **Credit Check and Engineering Review:** I do not use a `parallel` operator. The completion logs cannot prove concurrency, so I represent the two checks as an interleaving/weak-order alternative. The balanced model allows both `C` before `E` and `E` before `C`, without claiming true simultaneity.
- **Supplier Confirmation:** D5 says Supplier Confirmation may begin after either check has produced enough information. In completion-order terms, the balanced model therefore requires that a visible Supplier Confirmation completion occur after at least one check completion. This yields `C S E`, `E S C`, `C E S`, and `E C S`, plus no-Supplier-Confirmation versions.
- **Expedite Review:** D6 requires Expedite Review to be after both checks and before Approve Configuration. S6 says it can be before or after Supplier Confirmation. Therefore, after the checks, I allow optional Supplier Confirmation and optional Expedite Review in any order.
- **Partial order vs. explicit tree:** The ProcessTree below enumerates the allowed completions rather than using a single `` node, because PM4Py process trees do not natively express the asymmetric constraint “Supplier Confirmation after at least one check, but Expedite Review after both checks.”

## Compact formal expression

\[
M_B = \rightarrow(R,\ XOR(
\rightarrow(C,\ XOR(\rightarrow(S,E,optX), \rightarrow(E,optSX))),
\rightarrow(E,\ XOR(\rightarrow(S,C,optX), \rightarrow(C,optSX)))
), A,P,Z)
\]

where

\[
optX = XOR(\tau, X)
\]

and

\[
optSX = XOR(\tau, S, X, \rightarrow(S,X), \rightarrow(X,S)).
\]

`optSX` accepts any subset and any order of the optional Supplier Confirmation and Expedite Review activities.

## PM4Py code

```python
from itertools import permutations
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def pt(operator=None, label=None, children=None):
    t = ProcessTree(operator=operator, label=label)
    if children:
        t.children = list(children)
    return t

def leaf(label):
    return pt(label=label)

def silent():
    return pt(label=None)

def seq_nodes(*nodes):
    return pt(operator=Operator.SEQUENCE, children=list(nodes))

def seq_labels(labels):
    return seq_nodes(*[leaf(x) for x in labels])

def xor_nodes(*nodes):
    return pt(operator=Operator.XOR, children=list(nodes))

def fix_parents(t, parent=None):
    t.parent = parent
    for c in t.children:
        fix_parents(c, t)

def optional_x():
    return xor_nodes(silent(), leaf("Expedite Review"))

def optional_sx():
    branches = []
    for size in range(3):
        for p in permutations(["Supplier Confirmation", "Expedite Review"], size):
            branches.append(silent() if not p else seq_labels(p))
    return xor_nodes(*branches)

c_branch = xor_nodes(
    seq_nodes(leaf("Credit Check"), leaf("Supplier Confirmation"), leaf("Engineering Review"), optional_x()),
    seq_nodes(leaf("Credit Check"), leaf("Engineering Review"), optional_sx())
)

e_branch = xor_nodes(
    seq_nodes(leaf("Engineering Review"), leaf("Supplier Confirmation"), leaf("Credit Check"), optional_x()),
    seq_nodes(leaf("Engineering Review"), leaf("Credit Check"), optional_sx())
)

model_balanced = seq_nodes(
    leaf("Register Order"),
    xor_nodes(c_branch, e_branch),
    leaf("Approve Configuration"),
    leaf("Release Production"),
    leaf("Archive Case")
)

fix_parents(model_balanced)
```

## Behavior deliberately excluded

- `Supplier Confirmation` completing before both `Credit Check` and `Engineering Review`, e.g. `R,S,C,E,A,P,Z`.
- `Expedite Review` completing before both `Credit Check` and `Engineering Review`.
- Any repeated activity.
- Any activity after `Archive Case`.
- `Approve Configuration` before either check, or `Release Production` before Approve Configuration.

## Known underfitting risks

- If D5 is interpreted on start times rather than visible completions, then `R,S,C,E,A,P,Z` could be legitimate; the balanced model would underfit such cases.
- If S1 is true and the Engineering-Review-before-Credit-Check traces are logging errors, the balanced model is too permissive.
- If the missing Supplier Confirmation rate is closer to 10%, the no-Supplier-Confirmation skip branch under-represents missing-data cases.

# 5. Permissive Candidate

## Inductive bias

The permissive model treats the domain rules as constraints, not as a description of the observed paths. A trace is accepted if it is a topological sort of one of four strictly partially ordered models. It deliberately allows `Supplier Confirmation` to complete before both visible check completions, because D5 says it may begin after either check has produced *enough information*, which is not necessarily the same as the check’s completion event.

## Compact formal expression

\[
M_P = XOR(N_{00}, N_{01}, N_{10}, N_{11})
\]

where \(N_{ab}\) contains `Supplier Confirmation` if \(a=1\) and contains `Expedite Review` if \(b=1\). The constraints in each \(N_{ab}\) are:

- `Register Order` precedes `Credit Check`, `Engineering Review`, and, if present, `Supplier Confirmation`.
- `Credit Check` and `Engineering Review` both precede `Approve Configuration`.
- If `Supplier Confirmation` is present, it precedes `Approve Configuration`.
- If `Expedite Review` is present, both `Credit Check` and `Engineering Review` precede it, and it precedes `Approve Configuration`.
- `Approve Configuration` precedes `Release Production`, which precedes `Archive Case`.

No order is imposed between `Credit Check`, `Engineering Review`, and `Supplier Confirmation`, except that `Expedite Review` must be after both checks.

## PM4Py code

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition

def make_spo(activities, edges):
    spo = StrictPartialOrder()
    trans = {}
    for a in activities:
        trans[a] = Transition(a)
        spo.order.add_node(trans[a])
    for src, tgt in edges:
        spo.order.add_edge(trans[src], trans[tgt])
    try:
        spo.elements = list(trans.values())
    except Exception:
        pass
    return spo

base_activities = [
    "Register Order", "Credit Check", "Engineering Review",
    "Approve Configuration", "Release Production", "Archive Case"
]

base_edges = [
    ("Register Order", "Credit Check"),
    ("Register Order", "Engineering Review"),
    ("Credit Check", "Approve Configuration"),
    ("Engineering Review", "Approve Configuration"),
    ("Approve Configuration", "Release Production"),
    ("Release Production", "Archive Case"),
]

sp_no = make_spo(base_activities, base_edges)

sp_s = make_spo(
    base_activities + ["Supplier Confirmation"],
    base_edges + [
        ("Register Order", "Supplier Confirmation"),
        ("Supplier Confirmation", "Approve Configuration"),
    ]
)

sp_x = make_spo(
    base_activities + ["Expedite Review"],
    base_edges + [
        ("Credit Check", "Expedite Review"),
        ("Engineering Review", "Expedite Review"),
        ("Expedite Review", "Approve Configuration"),
    ]
)

sp_both = make_spo(
    base_activities + ["Supplier Confirmation", "Expedite Review"],
    base_edges + [
        ("Register Order", "Supplier Confirmation"),
        ("Supplier Confirmation", "Approve Configuration"),
        ("Credit Check", "Expedite Review"),
        ("Engineering Review", "Expedite Review"),
        ("Expedite Review", "Approve Configuration"),
    ]
)

try:
    xor_op = OperatorPOWL.Operator.XOR
except AttributeError:
    xor_op = "XOR"

model_permissive = OperatorPOWL(
    operator=xor_op,
    children=[sp_no, sp_s, sp_x, sp_both]
)
```

## Boundary between reasonable generalization and forbidden behavior

Reasonable generalization in the permissive model permits any completion order consistent with the domain rules, including `Supplier Confirmation` before the visible completions of both checks. That is the main “risky” boundary: it is defensible only because D5 refers to “enough information”, not to completion, and because only completions are logged.

Behavior that remains forbidden:

- `Expedite Review` before both `Credit Check` and `Engineering Review`.
- `Approve Configuration` before `Credit Check` or `Engineering Review`.
- `Release Production` before `Approve Configuration`.
- `Register Order` not first.
- `Archive Case` not last.
- Repeated activities.
- Any activity label outside the modelled activity set.

## Behavior deliberately excluded

- `R,C,X,E,A,P,Z`: Expedite Review before Engineering Review completion.
- `R,C,E,P,A,Z`: Release Production before Approve Configuration.
- `R,C,E,S,A,P,Z,S`: repeated Supplier Confirmation after Archive Case.
- Any trace in which `Approve Configuration` occurs before an activity that is required before it.

## Known underfitting risks

- The permissive model has low underfitting risk relative to broad domain rules, but it has high false-positive risk.
- It may accept `Supplier Confirmation`-before-both-checks traces that are actually impossible because D5’s “enough information” is not available that early.
- It does not distinguish true missing Supplier Confirmation events from true skips, so it underrepresents data quality if 5–10% of Supplier Confirmation events are missing.

### Intentionally excluded traces

- **Conservative**
  - `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case`: not one of the observed exact variants; earliest violation occurs at the third event, because the only observed R,E branch expects Credit Check next.
  - `Register Order, Credit Check, Engineering Review, Expedite Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case`: not in the exact variant list; earliest violation occurs at the fifth event, where the observed R,C,E,S branch expects Supplier Confirmation before Expedite Review.

- **Balanced**
  - `Register Order, Supplier Confirmation, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case`: Supplier Confirmation completes before both visible check completions, violating the balanced reading of D5.
  - `Register Order, Credit Check, Expedite Review, Engineering Review, Approve Configuration, Release Production, Archive Case`: Expedite Review completes before Engineering Review, violating D6.
  - `Register Order, Credit Check, Engineering Review, Supplier Confirmation, Supplier Confirmation, Approve Configuration, Release Production, Archive Case`: repeated Supplier Confirmation violates single-execution.

- **Permissive**
  - `Register Order, Credit Check, Expedite Review, Engineering Review, Approve Configuration, Release Production, Archive Case`: Expedite Review before Engineering Review, violating D6.
  - `Register Order, Credit Check, Engineering Review, Release Production, Approve Configuration, Archive Case`: Release Production before Approve Configuration, violating D2.
  - `Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case, Supplier Confirmation`: Supplier Confirmation after Archive Case, violating the end rule and single-execution.

# 8. Validation Code

```python
import pm4py
from itertools import permutations
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition

# ----------------------------------------------------------------------
# Reconstruct the 30-case log
# ----------------------------------------------------------------------
def make_log_from_strings(strings):
    try:
        return pm4py.parse_event_log_string(strings)
    except Exception:
        return pm4py.parse_event_log_string("\n".join(strings))

observed_variants = [
    (12, "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (7,  "Register Order,Engineering Review,Credit Check,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (4,  "Register Order,Credit Check,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (3,  "Register Order,Engineering Review,Credit Check,Approve Configuration,Release Production,Archive Case"),
    (2,  "Register Order,Credit Check,Supplier Confirmation,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Expedite Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Engineering Review,Credit Check,Expedite Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
]

trace_strings = []
for count, s in observed_variants:
    trace_strings.extend([s] * count)

log = make_log_from_strings(trace_strings)

# Shared ProcessTree helpers
# ----------------------------------------------------------------------

    t = ProcessTree(operator=operator, label=label)
    if children:
        t.children = list(children)
    return t

def leaf(label):
    return pt(label=label)

def silent():
    return pt(label=None)

def fix_parents(t, parent=None):
    t.parent = parent
    for c in t.children:
        fix_parents(c, t)

def seq_nodes(*nodes):
    return pt(operator=Operator.SEQUENCE, children=list(nodes))

def seq_labels(labels):
    return seq_nodes(*[leaf(x) for x in labels])

def xor_nodes(*nodes):
    return pt(operator=Operator.XOR, children=list(nodes))

    leaf("Register Order"),

    leaf("Approve Configuration"),

# Permissive POWL model

def make_spo(activities, edges):
    spo = StrictPartialOrder()
    trans = {}
    for a in activities:
        trans[a] = Transition(a)
        spo.order.add_node(trans[a])
    for src, tgt in edges:
        spo.order.add_edge(trans[src], trans[tgt])
    try:
        spo.elements = list(trans.values())
    except Exception:
        pass
    return spo
```

# 9. Recommendation and Data-Collection Plan

## Recommendation

Use **`model_balanced`** for immediate use. It fits all 30 observed cases, encodes the most defensible medium-confidence rules, and avoids the most controversial S-before-both-completions behavior.

Use **`model_permissive`** for sensitivity analysis. If future data show Supplier Confirmation completing before both visible check completions, the permissive model should replace the balanced model.

Use **`model_conservative`** only for retrospective reporting of the historical 30 cases, not for prediction of future orders.

## Data-collection plan

1. **Export lifecycle timestamps.** Collect both `start_timestamp` and `complete_timestamp` for every activity. This resolves the main ambiguity about whether Credit Check and Engineering Review overlap.
2. **Add the missing attribute.** Export `external/stocked` or `supplier_confirmation_required` for each order. This directly distinguishes true Supplier Confirmation skips from missing events.
3. **Add event IDs.** Record ingestion order independently of timestamps, avoiding S7’s same-timestamp ambiguity.
4. **Capture “enough information” milestones.** If D5 remains important, log a separate milestone event when Credit Check or Engineering Review has produced enough information for Supplier Confirmation to begin.
5. **Audit integration gaps.** Compare supplier-confirmation source records against the process-log events to estimate the true 5–10% missing rate.
6. **Collect maximally informative traces.**

   - `Register Order, Supplier Confirmation, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case` would discriminate balanced from permissive.
   - `Register Order, Supplier Confirmation, Engineering Review, Credit Check, Expedite Review, Approve Configuration, Release Production, Archive Case` would test the combination of D5 start semantics and D6.
   - `Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case` would confirm whether Expedite Review can occur without Supplier Confirmation.
   - Repeated traces of the already-observed `R,C,E,S,X,A,P,Z` and `R,E,C,X,S,A,P,Z` would help estimate the frequency of the two Expedite/S supplier orderings.
   - True start timestamps for `R,C,E,...` versus `R,E,C,...` would show whether the two checks are actually concurrent.

# 10. Uncertainty Statement

Calibrated confidence in the major modeling decisions:

- **Single execution / no loops:** high, about 85%.
- **Register Order first, Archive Case last, and Approve  Release  Archive suffix:** high, about 90%.
- **Credit Check and Engineering Review may complete in either order:** medium-high, about 75%. This is supported by S2 and by the observed variants, but D7 prevents proof of concurrency.
- **Balanced model’s requirement that Supplier Confirmation completion occur after at least one visible check completion:** medium, about 60%. This is a completion-order interpretation of D5.
- **Optional Supplier Confirmation as a silent skip:** medium, about 55%. The ambiguity is caused by S4 versus S5.
- **Expedite Review optional, after both checks, before Approval, at most once:** medium-high, about 80%.
- **Conservative model as a future-predictive model:** low, about 20%. It is high-confidence only as a reproduction of the historical sample.

A plausible alternative interpretation that would materially change the recommendation is: **S1 is true and S2 is false**. If Credit Check must finish before Engineering Review starts, then the 11 observed Engineering-Review-before-Credit-Check traces are logging errors or timestamp artifacts. In that case, the models should enforce Credit Check before Engineering Review, and the balanced model would be too permissive. Another material alternative is that D5 is based on internal “enough information” milestones rather than check completions; then Supplier Confirmation may legitimately complete before both visible check completions, making the permissive model more accurate than balanced. A third alternative is that missing Supplier Confirmation events are closer to 10% and no true stocked skips exist; then Supplier Confirmation should be mandatory with a missing-event compensation layer rather than a silent skip.
