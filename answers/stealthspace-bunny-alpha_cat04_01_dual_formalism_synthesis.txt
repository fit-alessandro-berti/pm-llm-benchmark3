# 1. Assumptions and Interpretation

1. **Scope and event semantics.** Each model describes one material-deviation case. A visible trace lists activity **completion events**, not start events. Thus, `C  V` means that `Contain Material` must complete before `Plan Verification` can start or complete.

2. **Concurrency versus ordering.** “May overlap” is interpreted as the absence of a causal order: both concurrent execution and an arbitrary serialization consistent with the dependencies are allowed. It does not require simultaneous execution. The POWL model represents this with independently executable activities and partial-order edges. The process-tree approximation necessarily serializes several of these activities.

3. **Risk-route choice.** After `Analyze Root Cause`, an exclusive choice selects:
   - `Supervisor Review`; or
   - a parallel branch containing both `Quality Review` and `Regulatory Review`.

   This is a control-flow approximation, not a low-risk/high-risk data predicate. The two high-risk reviews have no order between them, so either completion order is allowed.

4. **Optional supplier consultation.** An exclusive choice selects either:
   - a silent “supplier absent” branch; or
   - `Consult Supplier`.

   This preserves optionality and at-most-once execution, but not dependence of the choice on case data. The silent branch is not a visible “no supplier” event.

5. **Inspection outcomes.** No visible `Inspection Passed` activity is introduced. Instead, the trial structure has two control outcomes after an inspection:
   - exit the trial loop, semantically interpreted as acceptance; or
   - execute `Adjust Parameters` and start another trial.

   **Outcome guards cannot be enforced by the activity-only model.** Consequently, the structural models may permit exit after an inspection that actually failed, or retry after an inspection that actually passed. The models are therefore not guaranteed to enforce the result-dependent part of the inspection requirement.

6. **No adjustment after the chosen exit.** In both implementations, once the trial loop takes its exit branch, `Adjust Parameters` is no longer reachable before release. This is a structural *no-rework-after-exit* guarantee. It is not a data-sensitive guarantee that every passing inspection must select exit.

7. **Unbounded repetition.** The trial loop allows arbitrarily many failed iterations, followed by one abstractly accepted iteration. It is not bounded to two trials.

8. **Duplicate visible labels.** Duplicate visible labels are permitted where structurally necessary. In the process tree, the do-part and redo-part each contain their own `Execute Trial` and `Inspect Trial` nodes, yielding the visible-label pattern  
   `E I (J E I)*`.  
   These are not two mandatory trials and are not the same Python object attached to two parents. The POWL model uses one visible node for each of these activities.

9. **Process-tree approximation policy.** The process tree uses a **conservative under-approximation of structural completion-order behavior**:
   - it serializes the independent post-root work streams;
   - it completes the selected approval route and optional consultation before starting any trial; and
   - it consequently excludes some intended overlaps.

   It does not serialize a release before its selected approval and supplier gates. Its result-dependent inspection behavior remains under-constrained, as explained above.

10. **No duplicated approval or supplier gates.** The process tree does not duplicate whole review or consultation subtrees merely to create an approximate release join. This avoids admitting spurious repeated reviews or consultations.

11. **No timing or fairness assumptions.** Activity durations, priorities, resource contention, and fairness between enabled POWL transitions are outside the model. A sampled event order demonstrates feasibility, not elapsed time or simultaneous execution.

# 2. Intended Dependency Specification

The following aliases are used in the dependency table and the compact POWL description:

- `R` = Register Deviation
- `C` = Contain Material
- `A` = Analyze Root Cause
- `V` = Plan Verification
- `D` = Design Corrective Action
- `S` = Supervisor Review
- `Q` = Quality Review
- `G` = Regulatory Review
- `P` = Consult Supplier
- `E` = Execute Trial
- `I` = Inspect Trial
- `J` = Adjust Parameters
- `L` = Release Material
- `Z` = Archive Case
- `H = XOR(S, PARALLEL(Q,G))`
- `U = XOR(_no_supplier, P)`
- `W` = trial loop

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | `R` | All remaining work | Precedence and boundary | Every case starts with registration; all work is downstream of it. |
| D2 | `R` | `C`, `A` | Parallel initiation | Containment and root-cause analysis may start independently after registration. |
| D3 | `C` | `V` | Completion-to-start precedence | Verification planning requires completed containment, not completed root-cause analysis. |
| D4 | `A` | `D` | Completion-to-start precedence | Corrective-action design requires completed root-cause analysis. |
| D5 | `A` | `H` | Exclusive choice | The approval route is selected after root-cause analysis. |
| D6 | `Q`, `G` | Each other | Concurrency | Both reviews are required for high risk, with no causal order between them. |
| D7 | `A` | `U` | Optional choice | Supplier selection occurs after root-cause analysis. Exactly one supplier branch is taken. |
| D8 | `D`, `V` | `W` | Join before trial | A trial requires both corrective-action design and verification planning. |
| D9 | `H` | `W` | No order | Approval need not be complete before trial execution. |
| D10 | `U` | `D`, `V`, `H`, `W` | No order, subject to D7 | Supplier consultation may overlap the other post-root-cause work. |
| D11 | `E` | `I` | Sequence within a trial cycle | Every execution is followed by inspection. |
| D12 | Failed abstract `I` | `J` | Outcome-controlled sequence | A failed inspection causes parameter adjustment. |
| D13 | `J` | Next `E` | Loop back-edge | Adjustment is followed by a new trial cycle. |
| D14 | Accepted abstract `I` | Loop exit | Outcome-controlled exit | Passing inspection ends repetition; no adjustment follows that chosen exit. |
| D15 | `H` | `L` | Synchronization | Only the selected approval route is required, but it must be complete before release. |
| D16 | Selected `P` | `L` | Conditional synchronization | Selected supplier consultation must complete before release. If the skip branch is selected, no supplier completion is required. |
| D17 | `W` | `L` | Synchronization | Release requires completion of the abstractly accepted trial loop. |
| D18 | `L` | `Z` | Precedence and boundary | Archiving occurs only after release and is the final activity. |

The supplier’s at-most-once property comes from the exclusive optional branch, not from an additional precedence edge. Similarly, low-risk/high-risk selection is a control alternative without a data guard.

# 3. PM4Py Process-Tree Model

The compact expression below uses `sequence`, `parallel`, `xor`, and `loop`. For a two-child loop, the first child is the **do-part** and the second is the **redo-part**.

```text
sequence(
  Register Deviation,
  parallel(
    Contain Material,
    Analyze Root Cause
  ),
  Plan Verification,
  Design Corrective Action,
  xor(
    Supervisor Review,
    parallel(Quality Review, Regulatory Review)
  ),
  xor(
    _no_supplier,
    Consult Supplier
  ),
  loop(
    sequence(Execute Trial, Inspect Trial),
    sequence(
      Adjust Parameters,
      sequence(Execute Trial, Inspect Trial)
    )
  ),
  Release Material,
  Archive Case
)
```

Here, `_no_supplier` is an unlabeled leaf node. The loop admits:

```text
E I (J E I)*
```

The code below constructs that expression directly, so it does not depend on a parser or on undefined helper functions.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def make(operator, label=None, children=()):
    """Create a node, attach every child, and set its parent explicitly."""
    if operator is None:
        node = ProcessTree()
    else:
        node = ProcessTree(operator)

    if label is not None:
        node.label = label

    for child in children:
        child.parent = node
        node.children.append(child)

    return node


def act(label):
    return make(None, label=label)


registration = act("Register Deviation")

containment = act("Contain Material")
root_cause = act("Analyze Root Cause")

initial_work = make(
    Operator.PARALLEL,
    children=[containment, root_cause]
)

planning = act("Plan Verification")
design = act("Design Corrective Action")

supervisor = act("Supervisor Review")
quality = act("Quality Review")
regulatory = act("Regulatory Review")

approval_route = make(
    Operator.XOR,
    children=[
        supervisor,
        make(
            Operator.PARALLEL,
            children=[quality, regulatory]
        )
    ]
)

supplier = act("Consult Supplier")
supplier_absent = make(None)  # Unlabeled silent/skip leaf.

optional_supplier = make(
    Operator.XOR,
    children=[supplier_absent, supplier]
)

# A do-part and a redo-part, each with its own activity instances.
trial_loop = make(
    Operator.LOOP,
    children=[
        make(
            Operator.SEQUENCE,
            children=[
                act("Execute Trial"),
                act("Inspect Trial")
            ]
        ),
        make(
            Operator.SEQUENCE,
            children=[
                act("Adjust Parameters"),
                make(
                    Operator.SEQUENCE,
                    children=[
                        act("Execute Trial"),
                        act("Inspect Trial")
                    ]
                )
            ]
        )
    ]
)

release = act("Release Material")
archive = act("Archive Case")

tree = make(
    Operator.SEQUENCE,
    children=[
        registration,
        initial_work,
        planning,
        design,
        approval_route,
        optional_supplier,
        trial_loop,
        release,
        archive
    ]
)
```

The process tree preserves the start/end boundary, the two initial parallel activities, the exclusive approval alternatives, concurrent high-risk reviews, optional supplier participation, and the unbounded trial-loop shape. It deliberately serializes approval and supplier work before **all** trial work rather than only before release. Consequently, it rejects legal witnesses such as W2, W3, and W5.

It also joins the two initial streams before either planning or design can occur. Thus, planning effectively waits for both containment and root-cause analysis, and design effectively waits for both as well, rather than retaining the intended split dependencies.

The tree cannot directly express the required “three independently progressing obligations join only at release” pattern without either serializing the obligations or duplicating visible gate activities. The chosen approximation serializes them; a duplication-based alternative could introduce repeated reviews or consultations and their associated false traces.

Finally, the tree has no data guards. Its loop may terminate after any inspection, and it may retry after a passing inspection. Likewise, its XOR branches are always selectable. The silent supplier branch is an explicit control alternative, not evidence that case data selected “no supplier.”

# 4. PM4Py POWL Model

Using the aliases from Section 2, the compact POWL structure is:

```text
R -> {C, A}
C -> V
A -> {D, H, U}

V -> W
D -> W

H -> L
U -> L
W -> L
L -> Z

H = XOR(S, PARALLEL(Q, G))
U = XOR(_no_supplier, P)

W = LOOP(
       E -> I -> XOR(_exit, J),
       J returns to E
     )
```

The first child of `W` is the mandatory do-part. Its second child is the redo-part: choosing `J` returns to `E`, while choosing the silent exit completes the loop. In particular, there is no skip before the first `E`, so release cannot occur without at least one trial cycle.

The cross-branch dependencies are added directly to the root partial order.

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


def act(label):
    return Transition(label)


# Visible activities: one node per activity type.
r = act("Register Deviation")
c = act("Contain Material")
a = act("Analyze Root Cause")
v = act("Plan Verification")
d = act("Design Corrective Action")

s = act("Supervisor Review")
q = act("Quality Review")
g = act("Regulatory Review")

p = act("Consult Supplier")

e = act("Execute Trial")
i = act("Inspect Trial")
j = act("Adjust Parameters")

l = act("Release Material")
z = act("Archive Case")

# Exactly one selected approval route.
approvals = OperatorPOWL(
    Operator.XOR,
    [
        s,
        OperatorPOWL(
            Operator.PARALLEL,
            [q, g]
        )
    ]
)

# Exactly one supplier branch. The silent node has no visible name.
supplier_absent = SilentTransition()
supplier_choice = OperatorPOWL(
    Operator.XOR,
    [supplier_absent, p]
)

# Mandatory do-part: E -> I.
inspection_cycle = StrictPartialOrder([e, i])
inspection_cycle.order.add_edge(e, i)

# Redo-part: exit the loop, or adjust and return to E.
pass_exit = SilentTransition()
after_inspection = OperatorPOWL(
    Operator.XOR,
    [pass_exit, j]
)

trials = OperatorPOWL(
    Operator.LOOP,
    [inspection_cycle, after_inspection]
)

# One accepting partial order contains all top-level model elements.
powl = StrictPartialOrder([
    r, c, a, v, d,
    approvals, supplier_choice,
    e, i, j, trials,
    l, z
])

# Entry and the two initial work streams.
powl.order.add_edge(r, c)
powl.order.add_edge(r, a)

# Split dependencies.
powl.order.add_edge(c, v)
powl.order.add_edge(a, d)

# Post-root-cause alternatives.
powl.order.add_edge(a, approvals)
powl.order.add_edge(a, supplier_choice)

# Trial join.
powl.order.add_edge(v, trials)
powl.order.add_edge(d, trials)

# Release synchronization.
powl.order.add_edge(approvals, l)
powl.order.add_edge(supplier_choice, l)
powl.order.add_edge(trials, l)

# Final boundary.
powl.order.add_edge(l, z)
```

The sequence from `inspection_cycle` to `after_inspection`, and the loop-back from `j` to the next `e`, are supplied by the `LOOP` do/redo semantics. They are not omitted cross-branch dependencies.

The intentionally absent edges are meaningful:

- **No `C  A` or `A  C`:** the two initial activities may progress in either order.
- **No `V  D` or `D  V`:** planning and design remain independent after their respective prerequisites.
- **No `Q  G` or `G  Q`:** both high-risk reviews may execute concurrently.
- **No approval-to-trial edge:** reviews and supplier consultation may overlap design, planning, and the entire trial cycle.
- **No supplier-to-design/planning/trial edge:** consultation may overlap those activities, while its branch still must finish before release.
- **No adjustment after the silent exit:** the exit path proceeds toward release, not back to another cycle.
- **No source other than `r` and no sink other than `z`:** all model elements are downstream of registration and upstream of archiving.

Some unconnected activities are alternatives rather than concurrent participants: the low- and high-risk routes are under one XOR, and the supplier and silent branches are alternatives under another XOR. A lack of a direct edge does not override those exclusive-scope semantics.

As in the tree, the inspection result cannot be tested. The silent exit can be selected after either actual inspection outcome. The model guarantees that no adjustment follows the **chosen exit**, but not that an actual passing inspection must choose it.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Start and end | Registration precedes all work; release precedes archiving. | Exact at the structural level. | `r` is the sole source and `z` the sole sink in the relevant partial order. | Neither is structurally over-constrained here. | A case cannot begin with work or archive before release. |
| Two initial work streams | Containment and root-cause analysis may overlap. | Explicit parallel branch. | Independent edges `r  c` and `r  a`. | Exact for the initial pair. | Supports either completion order without serializing them. |
| Split planning/design dependencies | Planning waits only for containment; design waits only for root cause. | Both occur after the entire initial parallel branch, in the fixed order planning then design. | Direct edges `c  v` and `a  d`; no edge between `v` and `d`. | Process tree is over-constrained. | The tree delays work that could start earlier and can distort elapsed-time and staffing estimates. |
| Risk route | Exclusive route selection after root cause; low risk requires supervisor; high risk requires concurrent quality and regulatory reviews. | Exclusive route selection exists, but only after planning and design. Quality/regulatory concurrency is exact within the high-risk branch. | Exclusive selection directly after root cause; no edge between `q` and `g`. | Process tree over-constrains route timing. Neither model has a risk-data guard. | A trace can select a route inconsistent with actual risk data, weakening compliance analysis. |
| Approval overlap with trial | Approval need not finish before trial starts and may overlap the entire trial cycle. | Approval finishes before every trial iteration. | Only `d, v  trials`; approval instead synchronizes at `l`. | Process tree is over-constrained; POWL is structurally faithful. | The tree can substantially delay trials that business rules allow to start early. |
| Optional supplier | Optional after root cause, at most once, complete before release, otherwise unordered. | Exactly one of silent skip or supplier; supplier is before the trial and release. | Exactly one branch directly after root cause; only `supplier_choice  l` constrains its completion relative to later work. | Process tree is over-constrained; POWL preserves the intended timing flexibility. Neither is data-conditioned. | The tree can miss valid supplier/trial overlap; either model can admit a supplier choice inconsistent with case data. |
| Repeat-until behavior | Every failed inspection is followed by adjustment and a new cycle; passing inspection ends repetition. | `E I (J E I)*`, with no adjustment on the loop-exit path. | A mandatory `E  I` do-part followed by retry/exit; adjustment returns to `E`. | Loop shape is faithful in both; POWL avoids duplicate visible E/I nodes. | Unbounded retries are representable, but the models do not guarantee that the inspection result selected the right branch. |
| No adjustment after accepted exit | No rework follows the accepted terminal inspection. | Structurally true after loop exit. | Structurally true after the silent exit. | Structurally faithful, but under-constrained relative to an external passing-inspection predicate. | A real passing inspection can be followed by unnecessary adjustment and an extra trial. |
| Release synchronization | Selected approval, selected supplier if any, and accepted trial must all be complete. | Enforced by requiring approval and supplier before the trial, then the trial before release. | Enforced by `approvals  l`, `supplier_choice  l`, and `trials  l`. | POWL is structurally faithful; the tree obtains safety by over-constraining earlier ordering. | POWL permits independent progress while preventing premature release; the tree is safe but less timely. |
| Inspection result semantics | Release requires an actual passing inspection. | Any terminal inspection can be interpreted as the exit. | Either outcome branch can follow any inspection. | Both are under-constrained with respect to data-conformant behavior. | A failed inspection can be followed by release; excessive trial/rework can also occur after a pass. |
| Duplicate-label risk | Repetition should not imply repeated supplier consultations, approval routes, or cases. | E and I appear in two structural positions; no approval or supplier duplication is introduced. | One visible node per activity type; repeated executions reuse that node. | Tree has structural duplicate labels; POWL has none, although either can have repeated executions in a trace. | Log consumers must not infer case boundaries or repeated business actions solely from repeated labels such as `Execute Trial`. |

# 7. Preferred Representation and Validation Plan

**Preferred canonical representation: the POWL model.**

It directly expresses the split dependencies `C  V` and `A  D`, keeps approvals and supplier consultation independent of trial progress, and synchronizes those obligations only at release. It also represents unbounded repetition with one visible `Execute Trial` node, one visible `Inspect Trial` node, and a silent loop exit. The process tree remains useful as a deliberately conservative approximation for demonstrations that do not need the intended cross-branch concurrency.

The preferred model still has the explicitly acknowledged inspection-result limitation.

## Validation plan

1. **Convert both models to process Petri nets.**

   Using a PM4Py version with the documented generic process-net interface:

   ```python
   import pm4py

   net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)
   ```

   For the usual process-net projection, treat the returned final marking `fm_*` as the accepting marking. If a backend returns a net without explicit acceptance semantics, first project it to a process net or attach an explicit accepting sink place. Successful compilation alone is not evidence of semantic fidelity.

2. **Run soundness checks on the converted nets.**

   ```python
   pm4py.check_soundness(
       net_powl, im_powl, fm_powl, print_diagnostics=True
   )
   pm4py.check_soundness(
       net_tree, im_tree, fm_tree, print_diagnostics=True
   )
   ```

   Inspect diagnostics rather than treating a Boolean result as a conformance certificate. Classical Petri-net soundness concerns behavior from the initial marking to the accepting marking; it does not establish equivalence to the narrative or validate the external risk, supplier, and inspection facts.

3. **Perform bounded and sampled playout.**

   On a version supporting the `max_points` parameter:

   ```python
   sampled_powl = pm4py.play_out(
       powl, variant="pm4py", n=200, max_points=300
   )
   sampled_tree = pm4py.play_out(
       tree, variant="pm4py", n=200, max_points=300
   )
   ```

   For native POWL playouts, visible events can be extracted as follows:

   ```python
   def visible_names(playout):
       return [
           item.name
           for item in playout
           if isinstance(item, Transition)
           and not isinstance(item, SilentTransition)
       ]
   ```

   Check that visible playouts begin and end correctly, that supplier consultation occurs at most once, and that both Q/G orders and approval/trial overlap are represented. A playout stopped at `max_points` is a truncated exploration, not a forbidden trace.

4. **Run explicit positive trace tests.**

   Store the eight visible witness sequences verbatim and replay them from the initial marking, allowing necessary silent transitions but comparing the resulting visible sequence exactly.

   W1 through W5 must be accepted by POWL. They should expose the process tree’s conservative differences:
   - W2 and W5 require design and planning to remain independent.
   - W3 permits supplier consultation before design.
   - W4 permits consultation during the trial cycle.

   Also test a zero-retry accepted cycle and a cycle with several adjustments to confirm the loop is unbounded structurally rather than accidentally limited to two iterations.

5. **Run explicit negative trace tests.**

   - **F1:** Before the `Plan Verification` step, no containment token can exist. The net must reject the prefix; the expected first failure is the missing `C  V` dependency.
   - **F2:** Under an external high-risk oracle, release must be rejected until both `Quality Review` and `Regulatory Review` have completed.
   - **F3:** Under an external “first inspection passed” oracle, adjustment after the first inspection must be rejected. This is an expected **failing conformance test** for the current activity-only models and must not be silently waived or reported as a negative result already enforced structurally.

   Negative tests should examine transition enabling and token states where possible, rather than merely checking whether a label occurs somewhere in a sampled log.

6. **Test silent behavior and duplicate labels explicitly.**

   - Verify that the POWL supplier-skip and loop-exit nodes are `SilentTransition` instances with no visible activity name.
   - Confirm that a playout without supplier consultation contains no visible supplier event.
   - Confirm that a supplier-involved playout contains no second `Consult Supplier` completion.
   - Before conversion, count POWL visible node definitions and verify that each of the 14 activity names occurs exactly once as a node definition.
   - Inspect the process-tree source and verify that E and I each have two structural instances, whereas S, Q, G, and P each have one.
   - Do not equate conversion-generated transition counts with source-node counts: compiler implementations may add internal transitions or duplicate states.

7. **Use bounded exhaustive exploration for additional confidence.**

   Enumerate converted-net paths up to a small bound, such as three or five trial executions, and test local invariants:
   - no archive before release;
   - no release before the selected approval and supplier obligations;
   - no adjustment after a chosen silent loop exit;
   - at most one supplier completion;
   - no zero-trial release.

   This remains finite-state reasoning only within the chosen bound.

8. **Limitations of the plan.**

   - Sampling gives no coverage guarantee.
   - Bounded exploration cannot exhaust the unbounded loop.
   - Petri-net soundness is not equivalence checking against the specification.
   - Positive completion traces do not prove real-time concurrency.
   - External risk, supplier-selection, and inspection-result facts cannot be reconstructed from these activity-only logs.
   - Compiler-specific silent behavior and internal duplication require source-to-net inspection.

# 8. Final Self-Critique

1. **The inspection-result semantics remain incomplete.** Neither model enforces the actual pass/fail predicate. In particular, an activity-only POWL model cannot simultaneously allow failed inspections to cause retries, require passing inspections to stop, and prevent premature release without an outcome representation or a data-aware guard.

2. **The process-tree model is intentionally not behaviorally equivalent to POWL.** It excludes legal approval/trial, supplier/trial, and post-root-cause overlaps. It is therefore unsuitable as a conformance oracle for the full narrative, even though its release gates are conservatively ordered.

3. **Validation remains finite and observational.** Playout and bounded exploration cannot establish exhaustive behavior over the unbounded loop, and visible completion traces cannot prove concurrent timing, identify case boundaries, or recover the omitted case facts.
