## 1. Target definition

**Primary target: activation-conditional 90-day default risk, modeled as time-to-default with right censoring.**

Let:

- \(A = 1\) if the application eventually reaches `Account Activated` under the historical process, including linked partner-originated activations when linkage is available.
- \(T_D\) be the time from activation to a default event.
- \(X\) be the information available at the prediction time, e.g., the first few application events.
- \(C\) be the censoring time, determined by the extraction date, the 90-day horizon, and outcome-feed latency.

The primary estimand is:

\[
R(x) = P(T_D \le 90 \mid A=1, X=x)
\]

or, equivalently for a binary 90-day view:

\[
Y = 1\{\text{default within 90 days after activation}\}
\]

observed only for activated accounts whose outcome has matured. Activated accounts that have not matured by the extraction date are **right-censored**, not labeled as non-default.

**Prediction time.** The primary prediction point is the first three canonical events of the application:

1. `Application Started`
2. `Identity/KYC Check`
3. `Credit Review`

If fewer than three canonical events occur before the case terminates, the available prefix is used and the case is flagged as `prefix_truncated`. An elapsed-time prefix, for example all events within 24 hours of `Application Started`, is also constructed as a sensitivity/alternative representation.

**Horizon.** The horizon is 90 days after `Account Activated`. Because the external outcome feed may arrive 7–35 days after the 90-day horizon, a conservative maturity rule is used:

\[
\text{label\_available\_at} = \text{activation\_time} + 90\text{ days} + \text{feed\_delay}
\]

where `feed_delay` can be taken from `label_available_at` when available, or from a conservative maximum such as 35 days when not observed.

**Unit of analysis.** One original credit application case. Transferred cases are linked through the transfer linkage table where possible. If a transferred case reappears under a new identifier and activation/default outcomes are observed, it is treated as an activated case for the primary target, with the original application prefix used for prediction. If linkage is unavailable, the outcome is treated as missing follow-up, not as non-default.

**Population.** The primary default-risk model is estimated on applications that reach activation, including matured and immature activated accounts. Rejected, withdrawn, unlinked transferred, and still-open applications are outside the conditional default-risk estimand because they were not exposed to the activated-account default outcome under the observed process.

**Why this is defensible.** This formulation respects the actual outcome definition: `default_90d` is only meaningful after activation. It avoids the misleading shortcut of treating rejected, withdrawn, open, or transferred applications as observed non-defaults. It also preserves uncertainty by separating matured outcomes from censored or selectively unobserved outcomes.

**Credible alternative target: policy-conditional expected default for all applications.**

A different estimand is:

\[
E(x) = P(A=1, Y=1 \mid X=x)
\]

under the historical activation policy. This answers: “What is the expected number or probability of defaults generated by this application if the current process and policy are unchanged?”

Rejected and withdrawn applications may contribute zero realized default under the observed policy because no account was activated. However, this is not the same as saying they have low credit risk if approved. Still-open applications are not matured and must be censored or modeled through a multi-state process. Transferred applications are selectively unobserved unless linked. This alternative is useful for portfolio-level expected-loss triage, but it conflates activation probability and default risk and should be reported separately.

**Another alternative: multi-state competing-outcome model.**

A multi-state model can estimate probabilities of:

- activation without default by 90 days,
- activation with default by 90 days,
- rejection,
- withdrawal,
- transfer with unknown follow-up,
- still open.

This answers a process-triage question rather than a pure activated-account default-risk question. It is statistically defensible for all applications but requires stronger modeling of transfer linkage, open-case censoring, and competing events.

## 2. Cohort construction

### Inclusion rules

The full study population is all 48,000 applications with `Application Started` between 2024-01-01 and 2025-12-31.

For the **primary activation-conditional default model**, include:

1. Cases with `Account Activated` observed by the extraction date.
2. Cases with a valid prediction prefix: at least one event and preferably the first three canonical events.
3. Linked transferred cases if the linkage table connects them to an activated account and activation time can be reconstructed.
4. Matured activated cases for labeled binary/survival analysis.
5. Immature activated cases as right-censored observations.

For the **policy-conditional or multi-state alternative**, include all applications but assign different outcome states or censoring statuses.

### Exclusion rules

Exclude from the primary default-risk model:

1. Rejected applications, unless used in a separate activation or multi-state model.
2. Withdrawn applications, unless used in a separate activation or multi-state model.
3. Unlinked transferred applications, unless modeled as missing follow-up or competing events in an alternative target.
4. Still-open applications without activation, unless modeled as ongoing or censored under a policy target.
5. Cases with no usable prefix after canonicalization and deduplication, if any.

Do **not** exclude or relabel these cases as non-default merely to force a binary outcome.

### As-of rules

- Event features are generated using only events with timestamp \(\le\) prediction time.
- `final_limit`, `decision_reason`, `collection_status`, `default_90d`, and post-activation events are not feature inputs.
- `label_available_at` is used only for outcome maturity, not as a predictor.
- Outcome maturity is evaluated as of a configurable cutoff, here `data_extract_time = 2026-02-15`.
- Activity names are canonicalized before prefix construction to handle the 2025-10-15 migration.
- Duplicate events are removed before counting events for fixed-length prefixes.
- Daily snapshot features such as `documents_total` are used only if they can be made as-of the prediction date; otherwise they are dropped.

## 3. Censoring and missing-label strategy

### Ordinary right censoring

A case is ordinarily right-censored if it has activated but the 90-day follow-up window has not fully elapsed by the extraction date.

Example:

- Activation: 2025-12-01
- 90-day horizon: 2026-03-01
- Extraction: 2026-02-15

The case is censored at 76 days. It is not labeled non-default.

### Delayed labels

A case may have passed the 90-day horizon but still lack the outcome feed because of the 7–35 day delay.

Example:

- Activation: 2025-10-01
- 90-day horizon: 2025-12-30
- Feed delay: 20 days
- Expected label availability: 2026-01-19
- Extraction: 2026-02-15

If `label_available_at` is observed and is after the extraction date, the case is censored. If the feed has not arrived even though the expected maturity date has passed, it is treated as delayed/missing and censored, with sensitivity analysis for MNAR behavior.

### Selection through activation

Activation is not ordinary censoring for the primary target. The primary target is defined conditional on activation. Rejected, withdrawn, and unactivated open cases do not have an observed default outcome under activation. Treating them as non-default would answer a different question: realized policy outcomes, not default risk among activated accounts.

For the primary model, activation selection is handled by:

- restricting the estimand to activated accounts,
- reporting the selected nature of the model,
- optionally adding a separate activation model for all applications.

### Transfer as competing event or missing follow-up

Transfer can mean different things:

1. **Linked transfer with activation on partner platform:** include as activated if the linked account activation and outcome are observable.
2. **Linked transfer without activation:** treat as non-activated under the observed linked process.
3. **Unlinked transfer:** outcome is selectively unobserved; do not assume non-default.
4. **Partner-originated activated account with missing feed:** censored, but likely MNAR because partner feeds are permanently missing more often.

For the primary conditional default model, unlinked transfers are excluded or treated as missing follow-up. For a multi-state or policy target, transfer can be modeled as a competing event or as a partially observed state.

### Permanently missing outcome feeds

Some activated accounts, especially partner-originated accounts, may never receive an outcome feed. This is not ordinary censoring if the missingness depends on latent default risk. It is potentially MNAR.

The primary strategy is to censor them and explicitly model missingness risk. Sensitivity analyses must test whether results change under plausible MNAR assumptions.

### Primary analysis strategy

Use a **survival model on activated accounts** with right censoring:

- Time origin: `Account Activated`.
- Event: default recorded within 90 days.
- Censoring:
  - if no default and not matured by extraction, censor at `min(90 days, extraction_date - activation_date)`;
  - if matured and no default, event indicator is 0 at 90 days;
  - if matured and default, event indicator is 1 at observed default time.
- Use IPCW or discrete-time survival with censoring weights to handle delayed labels when censoring depends on observed features such as `source_system`, `channel`, `region`, and prefix features.
- For the all-application business question, pair this with a separate activation model and report expected policy-conditional default as:

\[
P(A=1 \mid X) \times P(Y=1 \mid A=1, X)
\]

but keep the two components transparent.

### Sensitivity analyses

1. **Complete-case matured analysis:** use only the 21,600 matured activated accounts. This is simple but can be biased if delayed labels are informative.
2. **Survival with censoring:** include the 3,600 immature activated accounts as censored. This is the primary recommended approach.
3. **IPCW for delayed feeds:** estimate censoring probabilities from observed features and feed latency patterns.
4. **Competing-risk model for all applications:** model activation, rejection, withdrawal, transfer, open, and default as competing states.
5. **Policy-conditional expected default:** use two-stage activation and default models.
6. **MNAR tipping-point analysis for partner-originated missing feeds:** assume increasing default rates among permanently missing partner accounts and observe how estimates change.
7. **Transfer linkage sensitivity:** compare linked-transfer cases with unlinked-transfer cases; test whether results change if unlinked transfers are assumed to have the same, higher, or lower default risk.

### Assumptions and testability

| Assumption | Testability | Notes |
|---|---|---|
| Delayed-feed censoring is independent of default risk given observed features | Partially testable | Can check observed covariate distributions by feed latency, but unobserved latent risk cannot be verified |
| Missing partner feeds are MAR conditional on source_system/channel/region | Partially testable | Linkage and feed patterns can be observed, but permanent missingness may be MNAR |
| Unlinked transfers have no informative default risk beyond observed features | Not fully testable | No outcome feed for many unlinked transfers |
| Rejected/withdrawn cases have no observed default under activation | Testable/definitional | They were not activated under the observed process |
| Counterfactual default risk for rejected cases is exchangeable with activated cases given prefix | Untestable | Requires causal/no-unmeasured-confounding assumptions |
| Policy-conditional expected default under historical policy is stable | Partially testable | Can monitor drift, but deployment changes may violate stability |

## 4. Prefix extraction

### Fixed event-count prefixes

The primary fixed prefix is the first three canonical events:

1. `Application Started`
2. `Identity/KYC Check`
3. `Credit Review`

Procedure:

1. Canonicalize activity names using a migration mapping.
2. Remove duplicate events with the same case, canonical activity, and timestamp.
3. Sort events by case and timestamp, with deterministic tie-breaking by original row order if available.
4. Take the first three events per case.
5. Set `prediction_time` to the timestamp of the third event.
6. If a case has fewer than three events before terminal state, use all available events and set `prefix_truncated = True`.

Fixed-count prefixes are useful for comparability across cases, but they may miss early document loops that occur after the third event.

### Elapsed-time prefixes

The elapsed-time prefix includes all canonical events with:

\[
\text{event\_timestamp} \le \text{start\_time} + 24\text{ hours}
\]

This captures:

- repeated document requests,
- early rework loops,
- unusually slow or fast processing,
- cases that remain in `Credit Review` without a third event.

For elapsed-time prefixes, `prediction_time` is the nominal cutoff, not the last observed event. Features must still be filtered to events at or before the cutoff.

### Handling short cases

If a case has fewer than three events:

- do not fabricate missing events,
- use the observed prefix,
- include `prefix_event_count`,
- include `prefix_truncated`,
- evaluate performance separately for truncated prefixes.

### Handling repeated document loops

Repeated `Request Documents -> Credit Review` loops affect both prefix types:

- In fixed-count prefixes, loops after event 3 are excluded by design.
- In elapsed-time prefixes, loops within 24 hours are included.
- Features should include loop count, number of document requests, and time spent in rework.

### Handling activity renaming

Before prefix construction, map post-migration activity names to canonical names. Example:

- `KYC Check (new)`  `Identity/KYC Check`
- `CreditReview`  `Credit Review`
- `RequestDocs`  `Request Documents`
- `AccountActivated`  `Account Activated`
- `DefaultRecorded`  `Default Recorded`

After mapping, deduplicate events. Validate that DFGs and variants before and after migration are comparable.

### Preventing future information leakage

For each case:

1. Compute `prediction_time`.
2. Keep only events with `time:timestamp <= prediction_time`.
3. Remove columns that are populated only after the prediction point.
4. For updated attributes such as `risk_score`, use the value at the latest event at or before `prediction_time`.
5. For daily snapshot features such as `documents_total`, use only if the snapshot date is strictly before the prediction date, or exclude them.
6. Never use `final_limit`, `decision_reason`, `collection_status`, `default_90d`, activation events, contract events, collections events, or default events as predictors.

## 7. Validation design

### Why random split is misleading

A random case split would mix:

- pre-policy-change and post-policy-change applications,
- pre-migration and post-migration activity names,
- matured and immature outcomes,
- different feed-latency regimes,
- different partner-originated missingness patterns,
- different activation-selection probabilities.

This can produce optimistic performance, poor calibration on future periods, and misleading subgroup estimates.

### Temporal validation scheme

Use case start time for splitting. A practical scheme for the available window is:

| Split | Application start period | Purpose |
|---|---|---|
| Train | 2024-01-01 to 2025-06-30 | Pre-policy-change baseline |
| Validation | 2025-07-01 to 2025-10-14 | Policy-change shift |
| Test | 2025-10-15 to 2025-12-31 | Migration and late-period shift |

Because outcomes require 90 days plus feed delay, evaluation must be as-of label maturity. For each split:

- train only on cases whose prediction time and label availability are in the past relative to the training cutoff;
- validate only on cases whose outcomes are matured or properly censored at the validation cutoff;
- test only on cases whose outcomes are matured or properly censored at the test cutoff.

A rolling-origin backtest is preferable:

1. Fit on matured cases with prediction time  2025-06-30.
2. Evaluate on matured cases with prediction time 2025-07-01 to 2025-10-14.
3. Evaluate on matured cases with prediction time 2025-10-15 to 2025-12-31.
4. Repeat with earlier as-of cutoffs to simulate deployment before the 2026-02-15 extraction.

For cases that are not matured, use survival metrics rather than discarding them.

### Handling policy change

- Report performance separately before and after 2025-07-01.
- Include `policy_period` as a known calendar feature only if the future policy state is known at prediction time.
- Test interactions between `policy_period` and key features.
- Consider retraining or recalibration after policy change.
- Do not assume the same prefix has the same activation probability or default risk before and after the policy change.

### Handling system migration

- Canonicalize activity names before validation.
- Compare prefix variants and DFGs before and after 2025-10-15.
- Report performance separately before and after migration.
- Check whether duplicate-event handling changes prefix length or timing features.
- If mapping uncertainty remains, exclude ambiguous migrated cases in a sensitivity analysis.

### Handling label maturity

- Matured activated cases can be evaluated as binary 90-day outcomes.
- Immature activated cases should be included as censored observations in survival evaluation.
- Delayed-feed cases should be censored at the appropriate time, not treated as non-default.
- Permanently missing feeds should be reported as a separate subgroup and analyzed with MNAR sensitivity.

### Evaluation metrics

For the primary survival target:

- IPCW time-dependent AUC at 90 days.
- C-index or IPCW concordance.
- Integrated Brier score up to 90 days.
- IPCW Brier score.
- Calibration slope and intercept using IPCW-weighted calibration.
- Reliability diagrams by predicted risk decile.
- Top-decile default rate and lift.
- Net benefit or decision-curve metrics if thresholds are used.

For matured binary evaluation:

- AUPRC, because default prevalence is 12.5% among matured activated accounts.
- ROC AUC.
- Brier score.
- Expected calibration error.
- Precision/recall at operational thresholds.
- False-positive and false-negative rates by subgroup.

For multi-state or policy-conditional evaluation:

- Macro AUC across states.
- Competing-risk concordance.
- Cumulative incidence calibration.
- Expected default count calibration.
- State-transition accuracy for activation, rejection, withdrawal, transfer, and open.

### Subgroup performance

Report performance by:

- policy period,
- migration period,
- channel,
- region,
- requested amount decile,
- `risk_score` decile,
- prefix length,
- truncated vs complete prefix,
- linked vs unlinked transfers,
- partner-originated vs non-partner accounts,
- feed-latency regime,
- matured vs censored activated cases.

### Distribution shift monitoring

- Population Stability Index for static and prefix features.
- KL divergence or Wasserstein distance for `risk_score` trajectories.
- Variant frequency drift.
- DFG transition probability drift.
- Label prevalence drift.
- Censoring rate drift.
- Missing-feed rate drift.
- Activation probability drift.
- Calibration drift over time.

## 8. Limitations and decision-use boundary

### What the study can claim

The study can estimate predictive associations between early application prefixes and 90-day default risk among accounts that are activated under the historical process. It can also estimate, with stronger assumptions, the expected default risk generated by applications under the historical activation policy.

It can produce:

- calibrated risk scores for activated accounts,
- survival estimates with censoring,
- uncertainty due to delayed labels,
- subgroup performance under policy and migration shifts,
- process-aware explanations of early warning signals.

### What the study cannot claim

The study cannot directly estimate “90-day default for every application” without additional assumptions.

It cannot claim:

- causal default risk for rejected applications,
- causal default risk for withdrawn applications,
- counterfactual default risk for applications that would have been approved under a different policy,
- complete outcome risk for unlinked transferred applications,
- unbiased population default risk if missing feeds are MNAR,
- stable future performance if deployment changes activation or collection behavior.

Rejected, withdrawn, open, and unlinked transferred cases should not be treated as observed non-defaults. They are either outside the conditional default estimand, censored, competing outcomes, or selectively unobserved.

### Predictive association versus counterfactual risk

A high predicted score for an activated account means:

\[
\text{This prefix is associated with higher observed default risk among activated accounts.}
\]

It does not mean:

\[
\text{This rejected applicant would have defaulted if approved.}
\]

The second statement requires counterfactual assumptions such as no unmeasured confounding and exchangeability between approved and rejected applicants with similar prefixes.

### Deployment effects on the data-generating process

Deployment can change the data-generating process in at least three ways:

1. **Selection change:** If the model is used to reject high-risk applicants, the future activated population will be truncated. The model will no longer be evaluated on the same population it was trained on.

2. **Intervention change:** Early warning may trigger additional document requests, manual review, limits changes, or collections interventions. These actions can change both activation probability and default risk, creating feedback loops.

3. **Missingness change:** If partner routing or linkage processes change, the probability of permanently missing outcome feeds may change. Partner-originated accounts may become more or less observable, altering censoring mechanisms.

Additional deployment risks include activity renaming, new event sources, changed credit-policy thresholds, and altered customer behavior. Continuous monitoring, recalibration, and periodic re-estimation are required.

### Decision-use boundary

The model is appropriate for:

- triage among applications likely to activate,
- prioritizing early manual review,
- estimating expected defaults under the current policy,
- monitoring process and outcome drift.

It is not appropriate for:

- treating rejected applicants as low-risk without counterfactual analysis,
- making causal claims about approval effects,
- using `final_limit`, `decision_reason`, or `collection_status` as predictors,
- ignoring immature or missing outcomes,
- assuming stable performance across policy changes or platform migrations.

activation = log.loc[log[ACT] == "Account Activated", [CASE, TS]].groupby(CASE)[TS].min().rename("activation_time")
default_event = log.loc[log[ACT] == "Default Recorded", [CASE, TS]].groupby(CASE)[TS].min().rename("default_event_time")
last_act = log.sort_values(TS).groupby(CASE)[ACT].last().rename("last_activity")
label_avail = log.dropna(subset=["label_available_at"]).groupby(CASE)["label_available_at"].max().rename("label_available_at")
default_label = log.dropna(subset=["default_90d"]).groupby(CASE)["default_90d"].first().rename("default_90d")
case = pd.concat([start, activation, default_event, last_act, label_avail, default_label], axis=1)

# TODO: join transfer linkage table here. If linked activation/default is observed,
# update activation_time/default_event_time/terminal_status before cohort assignment.
def terminal_status(row):
    if pd.notna(row["activation_time"]):
        return "activated"
    if row["last_activity"] == "Rejected":
        return "rejected"
    if row["last_activity"] == "Withdrawn":
        return "withdrawn"
    if row["last_activity"] == "Transferred":
        return "transferred"
    return "open"

case["terminal_status"] = case.apply(terminal_status, axis=1)
case["label_available_at"] = case["label_available_at"].fillna(case["activation_time"] + HORIZON + FEED_DELAY)
case["matured"] = case["activation_time"].notna() & (case["label_available_at"] <= EXTRACT)
case["survival_time_days"] = (EXTRACT - case["activation_time"]).dt.days
case["event_indicator"] = (
    case["default_event_time"].notna()
    & ((case["default_event_time"] - case["activation_time"]).dt.days <= 90)
).astype("Int64")
case.loc[case["matured"] & case["default_90d"].notna(), "event_indicator"] = pd.to_numeric(case["default_90d"], errors="coerce").astype("Int64")
case.loc[case["matured"] & case["event_indicator"].isna(), "event_indicator"] = 0

# Temporal split by application start. Random split is intentionally not used.
def split_by_start(t):
    if t < pd.Timestamp("2025-07-01"):
        return "train"
    if t < pd.Timestamp("2025-10-15"):
        return "validation"
    return "test"

case["split"] = case["start_time"].map(split_by_start)
# A convenience baseline could call pm4py.split_train_test, but it would mix policy/migration periods.

# Fixed-length prefixes for process mining audit.
prefix_log = pm4py.get_prefixes_from_log(log, prefix_length=PRED_EVENTS)
prefix_variants = pm4py.get_variants(prefix_log)
dfg, sa, na = pm4py.discover_dfg(prefix_log)
print(f"prefix variants={len(prefix_variants)}; DFG nodes={len(sa)}; DFG edges={len(dfg)}")

# Build an as-of prefix table. Primary prefix: first PRED_EVENTS canonical events.
log["event_idx"] = log.groupby(CASE).cumcount()
fixed_events = log[log["event_idx"] < PRED_EVENTS]
case["pred_time"] = fixed_events.groupby(CASE)[TS].max()
case["prefix_event_count"] = fixed_events.groupby(CASE).size()
case["prefix_truncated"] = case["prefix_event_count"] < PRED_EVENTS

# Elapsed-time prefix (sensitivity/alternative): all events within PRED_HOURS of start.
time_events = log.merge(case[["start_time"]], left_on=CASE, right_index=True)
time_events = time_events[time_events[TS] <= time_events["start_time"] + timedelta(hours=PRED_HOURS)]
case["pred_time_elapsed"] = time_events.groupby(CASE)[TS].max()
case["elapsed_prefix_event_count"] = time_events.groupby(CASE).size()

# Feature events are filtered to the fixed prediction time and forbidden columns are removed.
prefix_events = log.merge(case[["pred_time"]], left_on=CASE, right_index=True)
prefix_events = prefix_events[prefix_events[TS] <= prefix_events["pred_time"]]
feature_cols = [c for c in prefix_events.columns if c not in FORBIDDEN and c not in {"pred_time", "event_idx"}]
prefix_features = prefix_events[feature_cols].copy()
prefix_features = prefix_features.sort_values([CASE, TS])
prefix_features["gap_hours"] = (
    prefix_features[TS] - prefix_features.groupby(CASE)[TS].shift()
).dt.total_seconds() / 3600

feat = prefix_features.groupby(CASE).agg(
    last_activity=(ACT, "last"),
    max_gap_hours=("gap_hours", "max"),
    doc_request_count=(ACT, lambda s: s.str.contains("Request Documents", na=False).sum()),
    risk_score_last=("risk_score", "last"),
    risk_score_first=("risk_score", "first"),
)
feat["risk_score_delta"] = feat["risk_score_last"] - feat["risk_score_first"]
feat = feat.join(case[[
    "start_time", "pred_time", "prefix_event_count", "prefix_truncated",
    "terminal_status", "matured", "event_indicator", "split",
]])
feat["prefix_elapsed_hours"] = (feat["pred_time"] - feat["start_time"]).dt.total_seconds() / 3600

# Leakage audit checks.
audit = prefix_features.merge(case[["pred_time"]], left_on=CASE, right_index=True)
post_prefix_violations = int((audit[TS] > audit["pred_time"]).sum())
forbidden_in_features = [c for c in prefix_features.columns if c in FORBIDDEN]
forbidden_in_model_features = [c for c in feat.columns if c in FORBIDDEN]
print(f"post-prefix event rows={post_prefix_violations}; forbidden feature columns={forbidden_in_features}; forbidden model columns={forbidden_in_model_features}")

# Cohort and label counts.
print("total cases:", len(case))
print(case["terminal_status"].value_counts(dropna=False).to_dict())
print(case["split"].value_counts(dropna=False).to_dict())
activated = case["terminal_status"].eq("activated")
print("matured activated:", int((activated & case["matured"]).sum()))
print("censored activated:", int((activated & ~case["matured"]).sum()))
print("labeled default:", case.loc[activated & case["matured"], "default_90d"].value_counts(dropna=False).to_dict())
