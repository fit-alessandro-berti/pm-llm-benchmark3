# 1. Assumptions and Interpretation

1. **Risk Route Representation**: The risk evaluation choice occurs implicitly after `Analyze Root Cause`. Low-risk cases execute `Supervisor Review`. High-risk cases execute `Quality Review` and `Regulatory Review` in parallel (represented as concurrent transitions without mutual order constraints). The choice is modeled as an exclusive choice ($\text{XOR}$) between `Supervisor Review` and the parallel block $\text{PAR}(\text{Quality Review}, \text{Regulatory Review})$.
2. **Optional Supplier Consultation Representation**: `Consult Supplier` is modeled as an exclusive choice ($\text{XOR}$) between the transition `Consult Supplier` and an unobservable silent transition ($\tau$). This guarantees that the activity occurs at most once per process instance.
3. **Abstraction of Inspection Outcomes**: Inspection outcomes (pass/fail) are not recorded as distinct data attributes or event labels. Instead, a successful inspection is modeled as the natural exit of a loop. A trial attempt consists of the sequence $\text{Execute Trial} \rightarrow \text{Inspect Trial}$. A failure triggers `Adjust Parameters`, followed by another trial attempt. The final `Inspect Trial` in any trace represents the passing inspection that enables progression to `Release Material`.
4. **Duplicate Visible Labels Policy**: Duplicate activity labels are strictly avoided in both models. Each activity label in the narrative is mapped to exactly one visible transition object.
5. **Process Tree Approximation Policy**: Process Trees cannot natively express non-block-structured cross-branch synchronizations (such as `Execute Trial` requiring both `Plan Verification` from the containment branch and `Design Corrective Action` from the analysis branch while allowing approval routes to overlap trials). We adopt a **permissive over-approximation policy** for the Process Tree. All concurrent branches after `Register Deviation` are grouped into a top-level parallel block. This preserves operational flexibility and avoids deadlock, but under-constrains execution order by allowing downstream actions (such as approvals or trials) to start earlier than intended.
6. **Interpretation of "May Overlap"**: "May overlap" is interpreted as true control-flow concurrency (absence of mutual ordering constraints). In sequential trace logs, activities from overlapping streams may interleave in any order.

# 3. PM4Py Process-Tree Model

### Process Tree String Structure
```text
-> (
    'Register Deviation',
    + (
        -> ( 'Contain Material', 'Plan Verification' ),
        -> ( 'Analyze Root Cause', 'Design Corrective Action' ),
        X ( 'Supervisor Review', + ( 'Quality Review', 'Regulatory Review' ) ),
        X ( 'Consult Supplier', tau ),
        * ( -> ( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' )
    ),
    'Release Material',
    'Archive Case'
)
```

### Python Construction Code
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Root sequence: Start -> Parallel Body -> Release -> Archive
tree = ProcessTree(operator=Operator.SEQUENCE)

rd = ProcessTree(label="Register Deviation", parent=tree)
tree.children.append(rd)

par_body = ProcessTree(operator=Operator.PARALLEL, parent=tree)
tree.children.append(par_body)

rm = ProcessTree(label="Release Material", parent=tree)
tree.children.append(rm)

ac = ProcessTree(label="Archive Case", parent=tree)
tree.children.append(ac)

# Branch 1: Containment stream (Contain Material -> Plan Verification)
seq_cm_pv = ProcessTree(operator=Operator.SEQUENCE, parent=par_body)
par_body.children.append(seq_cm_pv)
cm = ProcessTree(label="Contain Material", parent=seq_cm_pv)
seq_cm_pv.children.append(cm)
pv = ProcessTree(label="Plan Verification", parent=seq_cm_pv)
seq_cm_pv.children.append(pv)

# Branch 2: Analysis stream (Analyze Root Cause -> Design Corrective Action)
seq_arc_dca = ProcessTree(operator=Operator.SEQUENCE, parent=par_body)
par_body.children.append(seq_arc_dca)
arc = ProcessTree(label="Analyze Root Cause", parent=seq_arc_dca)
seq_arc_dca.children.append(arc)
dca = ProcessTree(label="Design Corrective Action", parent=seq_arc_dca)
seq_arc_dca.children.append(dca)

# Branch 3: Risk Review stream (Supervisor Review XOR (Quality Review PAR Regulatory Review))
xor_risk = ProcessTree(operator=Operator.XOR, parent=par_body)
par_body.children.append(xor_risk)
sr = ProcessTree(label="Supervisor Review", parent=xor_risk)
xor_risk.children.append(sr)

par_high_risk = ProcessTree(operator=Operator.PARALLEL, parent=xor_risk)
xor_risk.children.append(par_high_risk)
qr = ProcessTree(label="Quality Review", parent=par_high_risk)
par_high_risk.children.append(qr)
regr = ProcessTree(label="Regulatory Review", parent=par_high_risk)
par_high_risk.children.append(regr)

# Branch 4: Optional Consult Supplier stream (Consult Supplier XOR tau)
xor_cs = ProcessTree(operator=Operator.XOR, parent=par_body)
par_body.children.append(xor_cs)
cs = ProcessTree(label="Consult Supplier", parent=xor_cs)
xor_cs.children.append(cs)
cs_tau = ProcessTree(label=None, parent=xor_cs)  # Silent transition
xor_cs.children.append(cs_tau)

# Branch 5: Trial Loop stream (*(Execute Trial -> Inspect Trial, Adjust Parameters))
loop_trial = ProcessTree(operator=Operator.LOOP, parent=par_body)
par_body.children.append(loop_trial)

seq_trial = ProcessTree(operator=Operator.SEQUENCE, parent=loop_trial)
loop_trial.children.append(seq_trial)
et = ProcessTree(label="Execute Trial", parent=seq_trial)
seq_trial.children.append(et)
it = ProcessTree(label="Inspect Trial", parent=seq_trial)
seq_trial.children.append(it)

ap = ProcessTree(label="Adjust Parameters", parent=loop_trial)
loop_trial.children.append(ap)
```

### Approximation Discussion
The Process Tree cannot represent the cross-branch dependency where `Execute Trial` waits for both `Plan Verification` (from Branch 1) and `Design Corrective Action` (from Branch 2) while allowing `Supervisor Review` / `Quality Review` / `Consult Supplier` to start only after `Analyze Root Cause` and overlap with trial execution. Placing all five streams in a top-level `PARALLEL` operator creates a permissive over-approximation. Consequently, the Process Tree allows `Execute Trial`, `Supervisor Review`, or `Consult Supplier` to execute immediately after `Register Deviation`, violating preconditions DEP-05, DEP-06, DEP-07, and DEP-08.

# 4. PM4Py POWL Model

### Compact POWL Description
```text
POWL Model (StrictPartialOrder):
Nodes:
  - rd: Transition("Register Deviation")
  - cm: Transition("Contain Material")
  - arc: Transition("Analyze Root Cause")
  - pv: Transition("Plan Verification")
  - dca: Transition("Design Corrective Action")
  - risk_choice: OperatorPOWL(XOR, [
        Transition("Supervisor Review"),
        StrictPartialOrder([Transition("Quality Review"), Transition("Regulatory Review")])
    ])
  - cs_choice: OperatorPOWL(XOR, [
        Transition("Consult Supplier"),
        SilentTransition()
    ])
  - trial_loop: OperatorPOWL(LOOP, [
        StrictPartialOrder("Execute Trial" -> "Inspect Trial"),
        Transition("Adjust Parameters")
    ])
  - rm: Transition("Release Material")
  - ac: Transition("Archive Case")

Edges:
  rd -> cm, rd -> arc
  cm -> pv
  arc -> dca, arc -> risk_choice, arc -> cs_choice
  pv -> trial_loop, dca -> trial_loop
  trial_loop -> rm, risk_choice -> rm, cs_choice -> rm
  rm -> ac
```

### Python Construction Code
```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# 1. Atomic transitions
rd = Transition(label="Register Deviation")
cm = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")
pv = Transition(label="Plan Verification")
dca = Transition(label="Design Corrective Action")

# 2. Risk Route Choice
sr = Transition(label="Supervisor Review")
qr = Transition(label="Quality Review")
regr = Transition(label="Regulatory Review")
high_risk = StrictPartialOrder(nodes=[qr, regr])  # Unconnected nodes = parallel execution
risk_choice = OperatorPOWL(operator=Operator.XOR, children=[sr, high_risk])

# 3. Optional Consult Supplier Choice
cs = Transition(label="Consult Supplier")
tau_cs = SilentTransition()
cs_choice = OperatorPOWL(operator=Operator.XOR, children=[cs, tau_cs])

# 4. Trial Loop
et = Transition(label="Execute Trial")
it = Transition(label="Inspect Trial")
trial_seq = StrictPartialOrder(nodes=[et, it])
trial_seq.order.add_edge(et, it)

ap = Transition(label="Adjust Parameters")
trial_loop = OperatorPOWL(operator=Operator.LOOP, children=[trial_seq, ap])

# 5. End transitions
rm = Transition(label="Release Material")
ac = Transition(label="Archive Case")

# 6. Top-level Partial Order Construction
powl = StrictPartialOrder(
    nodes=[rd, cm, arc, pv, dca, risk_choice, cs_choice, trial_loop, rm, ac]
)

# Add directed precedence edges
powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)
powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, risk_choice)
powl.order.add_edge(arc, cs_choice)
powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dca, trial_loop)
powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(risk_choice, rm)
powl.order.add_edge(cs_choice, rm)
powl.order.add_edge(rm, ac)
```

### Unconnected Node Concurrency Explanation
- **`risk_choice` and `trial_loop`**: Leaving no direct edge between `risk_choice` and `trial_loop` permits review actions (`Supervisor Review` or `Quality/Regulatory Review`) to interleave freely with trial executions (`Execute Trial` $\rightarrow$ `Inspect Trial` $\rightarrow$ `Adjust Parameters`), reflecting Requirement 7.
- **`cs_choice` and `trial_loop` / `risk_choice` / `dca` / `pv`**: `cs_choice` depends only on `arc` and precedes `rm`. It remains intentionally unconnected to trial and approval nodes so supplier consultation can overlap any downstream activities after root cause analysis, reflecting Requirement 6.
- **`cm` / `pv` and `arc` / `dca`**: No edges exist between containment activities and analysis activities, allowing containment and root-cause streams to run in true parallel after registration.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| **Two initial streams** | CM and ARC start independently after RD. | Modeled in top-level `PARALLEL`. | Partial order edges `RD -> CM` and `RD -> ARC`. | Exact match in both models. | Operations can perform containment and root cause analysis in parallel without bottleneck. |
| **Split dependencies (PV, DCA)** | PV requires CM; DCA requires ARC. | CM/PV and ARC/DCA are parallel sequence branches. | Partial order edges `CM -> PV` and `ARC -> DCA`. | Exact match in both models. | Prevents starting verification planning without containment, or design without root cause analysis. |
| **Risk route selection** | SR or (QR + RegR) chosen after ARC. | Placed in parallel branch alongside initial tasks. | Partial order edge `ARC -> risk_choice`. | Process Tree underconstrains (allows reviews before ARC). POWL is exact. | Tree permits premature supervisor/regulatory reviews before root cause is analyzed; POWL enforces proper sequencing. |
| **Approval / Trial overlap** | Approvals can occur before, during, or after trial work. | Approvals and trial loop are parallel siblings. | `risk_choice` and `trial_loop` have no ordering edges between them. | Exact match in both models. | Approvals do not block physical trial testing, shortening case processing lead times. |
| **Optional supplier consultation** | CS optional, starts after ARC, completes before RM. | XOR(CS, tau) branch in top-level parallel block. | Partial order edges `ARC -> cs_choice` and `cs_choice -> RM`. | Process Tree underconstrains (allows CS before ARC). POWL is exact. | Tree allows contacting supplier before deviation root cause analysis begins; POWL prevents premature outreach. |
| **Repeat-until trial cycle** | ET -> IT; if fail, AP -> ET -> IT; ends on pass. | LOOP(SEQ(ET, IT), AP). | OperatorPOWL(LOOP, [SEQ(ET, IT), AP]). | Exact match in both models. | Correctly models iterative engineering adjustments until inspection criteria are satisfied. |
| **Release synchronization** | RM waits for Trial completion, Risk Route, and CS (if selected). | RM is sequential target after parallel block. | Partial order edges from `trial_loop`, `risk_choice`, and `cs_choice` to `RM`. | Exact match in structure; Tree underconstrains upstream prerequisites. | Ensures unapproved or unverified material is never released to production. |
| **Duplicate-label risk** | Avoid activity label duplication to preserve clear event logs. | Avoided, but at the cost of over-approximating control flow. | Avoided completely while preserving exact partial-order constraints. | Process Tree trades control-flow precision for single-label representation. POWL avoids trade-off. | Process Tree logs may conform to invalid trace sequences; POWL maintains precise behavioral semantics. |

# 7. Preferred Representation and Validation Plan

### Preferred Representation
The **PM4Py POWL model** is the canonical representation. It natively models non-block-structured partial order dependencies using explicit graph edges (`StrictPartialOrder.order.add_edge`), ensuring exact enforcement of cross-branch synchronizations (e.g., `PV` and `DCA` preceding `Execute Trial`, and `ARC` preceding approval routes) without resorting to activity label duplication or over-approximating process execution order.

### Concrete Validation Plan

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder


def validate_powl_model(powl_model: StrictPartialOrder):
    # 1. Convert POWL model to Accepting Petri Net
    net, initial_marking, final_marking = pm4py.convert_to_petri_net(powl_model)

    # 2. Soundness Checking
    is_sound = pm4py.check_soundness(
        net, initial_marking, final_marking, print_diagnostics=True
    )
    print(f"Model Soundness: {is_sound}")

    # 3. Playout Sampling
    simulated_log = pm4py.play_out(net, initial_marking, final_marking)
    print(f"Generated {len(simulated_log)} trace variants via playout.")

    # 4. Trace Conformance Testing (Positive and Negative Witnesses)
    test_traces = [
        # Allowed trace TR-01
        (
            [
                "Register Deviation",
                "Contain Material",
                "Analyze Root Cause",
                "Plan Verification",
                "Design Corrective Action",
                "Supervisor Review",
                "Execute Trial",
                "Inspect Trial",
                "Release Material",
                "Archive Case",
            ],
            True,
        ),
        # Forbidden trace TR-06 (Premature Trial before PV)
        (
            [
                "Register Deviation",
                "Analyze Root Cause",
                "Design Corrective Action",
                "Execute Trial",
                "Contain Material",
                "Plan Verification",
                "Inspect Trial",
                "Supervisor Review",
                "Release Material",
                "Archive Case",
            ],
            False,
        ),
        # Forbidden trace TR-07 (Premature SR before ARC)
        (
            [
                "Register Deviation",
                "Supervisor Review",
                "Contain Material",
                "Analyze Root Cause",
                "Plan Verification",
                "Design Corrective Action",
                "Execute Trial",
                "Inspect Trial",
                "Release Material",
                "Archive Case",
            ],
            False,
        ),
    ]

    # Replay test cases using token-based replay or alignments
    for i, (trace_events, expected) in enumerate(test_traces, start=1):
        # Build mini-log format
        trace_log = pm4py.objects.log.obj.EventLog(
            [
                pm4py.objects.log.obj.Trace(
                    [
                        pm4py.objects.log.obj.Event({"concept:name": act})
                        for act in trace_events
                    ]
                )
            ]
        )
        replay_result = pm4py.conformance_diagnostics_token_based_replay(
            trace_log, net, initial_marking, final_marking
        )
        is_fit = replay_result[0]["trace_is_fit"]
        status = "PASSED" if is_fit == expected else "FAILED"
        print(
            f"Test Trace {i}: Expected Fit={expected}, Actual Fit={is_fit} -> [{status}]"
        )


# Run validation plan

```

### Specific Checks for Silent Transitions and Labels
- **Silent Transition ($\tau$) Reachability Check**: Ensure that choosing the silent branch in `cs_choice` does not leave unconsumed tokens or prevent reaching the final marking during token replay.
- **Unique Label Mapping Audit**: Verify that the set of visible labels in the generated Petri net exactly matches the 14 activity labels listed in the Process Narrative.

### Validation Plan Limitations
- Playout sampling is finite and bounded; it may not cover all arbitrary interleavings of concurrent branches or arbitrary loop iteration counts ($N > 2$).
- Conversion of complex POWL partial orders to Petri nets can introduce silent transitions that increase non-determinism during token replay diagnostics.

# 8. Final Self-Critique

1. **Semantic Weakness (Data Abstraction Loss)**: The control-flow model represents the loop exit (`Inspect Trial` passing) purely via standard structural loop operators (`Operator.LOOP`). It abstracts away data attributes (such as inspection parameters or defect counts). Consequently, the model permits infinite loops of `Adjust Parameters -> Execute Trial -> Inspect Trial` without expressing business rules that cap maximum trial iterations before escalating to case termination.
2. **Semantic Weakness (Supplier Advice Impact)**: Modeling `Consult Supplier` as an independent concurrent choice that synchronizes only at `Release Material` allows traces where supplier consultation completes late in the case lifecycle without feeding back into `Design Corrective Action` or trial parameter selection, even though engineering context implies supplier feedback would influence corrective design.
3. **Representation/Tooling Limitation**: Converting POWL models containing mixed constructs (partial order graphs, nested XOR choices, and LOOP operators) into accepting Petri nets produces complex subnet structures with silent transitions ($\tau$). This can negatively impact performance during alignment-based conformance checking on large event logs.
