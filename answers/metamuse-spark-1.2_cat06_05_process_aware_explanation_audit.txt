## 2. Process-model consistency checks

A credible audit must test explanations against temporal and process constraints, not only statistical importance. Recommended suite:

**A. Prefix-time availability test (point-in-time feature audit)**
* Purpose: enforce `feature_timestamp <= t0`. Every feature must carry a `feature_as_of_time` or be derived only from events with `event_time <= t0`.
* Implementation: during validation recompute all features from raw events filtered to `prefix = trace[0:t0]`. Compare recomputed value to stored explanation value; mismatches flag leakage (e.g., `total_duration`, `full_variant`, `doc_count_snapshot`, `risk_score_current`).
* Role/limitation: catches temporal leakage but does not detect process impossibility.

**B. Activity-order feasibility (normative vs descriptive)**
* Normative BPMN/declare model above is ground truth, not the discovered DFG. Checks include:
  - **Footprint / declarative constraints:** `Precedence(Claim Registered, Coverage Check)`, `ExclusiveChoice(fast-track vs evidence loops)`, `Precedence(Damage Assessment, Settlement Decision)`, `Precedence(Settlement Decision, Claim Closed)`, `Constraint If Appeal then PrecededBy(Partial OR Deny)`, `AtMostOne(Claim Closed)` before close (allow repeat `Settlement Decision` iff `Appeal` occurred), `NotCoExistence(Claim Closed before Damage Assessment)`.
  - **Trace alignment / conformance checking:** align each full trace and each prefix against normative model; compute fitness and detect violations (e.g., `Closed -> Assessment` yields alignment cost).
* Purpose: distinguishes *frequent* DFG edge from *allowed* edge. A frequent mined edge (`Closed->Assessment` due to same-timestamp swap) is not a normative rule.
* Limitation: declarative checks need expert-curated constraints; overly strict model may flag legitimate variation (e.g., parallel Fraud Investigation interleaving). Use as filter + human review.

**C. Same-timestamp ambiguity check**
* Detect events sharing `timestamp` within same case. Require reliable `sequence_index` / `event_order` column to disambiguate. If index missing/null, mark ordering as `uncertain` and exclude from sequential pattern mining and DFG discovery for explanation.
* For Case Z: identical timestamps for `Closed` and `Assessment` with missing index  explain invalidated. Re-mine only with `order_by timestamp, sequence_index`.

**D. Complete-trace information test**
* Flag any feature whose lineage SQL scans beyond `t0`: `COUNT(*) OVER entire trace`, `MAX(team)` at close, `variant_id = concat(all activities)`, `appeal_seen_anywhere = exists(event=Appeal)`, `last_role`. Automated lineage parser: feature depends on `trace` without `WHERE event_time <= t0`.
* Distinguishes `prefix_variant` (defensible) from `full_trace_variant` (leakage).

**E. Enabled / impossible / future-possible classification at t0**
* At prediction prefix `Registered->CoverageCheck`, compute process state (enabled activities) via token replay: enabled = `{Damage Assessment, Documents Requested, Fraud Investigation}` (depending on trigger). Compare:
  - **Impossible at t0:** `Appeal`, `Settlement Decision`, `Claim Closed` (preconditions not met)  any explanation referencing them as observed is impossible/leakage.
  - **Enabled but not yet observed:** `Documents Requested`, `Fraud Investigation`  may be future; not observed at t0 so pattern `Requested->Received` cannot have occurred.
  - **Future-possible but not enabled:** `Appeal->Decision` requires passing through Decision first  two steps away.
* This separates Case-pattern `Appeal->Decision` (feasible later, but future-possible now) from `Closed->Assessment` (never feasible).

**F. Repeated activity legitimacy check**
* Coarse label `Settlement Decision Recorded` repeat is only allowed if `Appeal` intervenes. Validate via alignment: sequence `DECISION-APP-DECISION` is conforming; `DECISION-DECISION` without appeal violates constraint.
* Ensures explanation `Appeal -> Settlement Decision` is not confused with an illegitimate duplicate decision.

Together, A+D catch leakage, B+C+F catch process inconsistency, E clarifies why future-feasible patterns still must be excluded at t0. All require prefix-only recomputation as baseline.

## 3. Alternative feature interpretations

**Defensible predictive signal (temporally available, process-feasible, stable)**
* `initial_damage_complexity`, `elapsed_since_registration_at_t0`
* May be claimed as: *associated with higher/lower predicted breach risk conditional on model and training distribution*.
* May NOT be claimed as: causal effect, or that intervening on the feature alone will change outcome. No interventional guarantee.

**Process-state / congestion signal (temporally available, reflects system load, not intrinsic claim property)**
* `queue_length_at_t0` (validated), `elapsed_since_registration_at_t0` (also state)
* May be claimed as: *the system state at t0 indicates higher likelihood of breach*; useful for triage/prioritization.
* May NOT be claimed as: actionable root cause - reducing measured queue without changing capacity does not fix congestion. Operational actionability requires capacity lever, not cosmetic metric change.

**Proxy requiring fairness / robustness review (available but correlates with sensitive or non-causal factors)**
* `claimant_region`, `claimant_channel = Broker` (and implicitly `initial_reserve` if it proxies severity)
* May be claimed as: *predictive association* in training period, subject to confounding by repair-network coverage, language, socioeconomic factors.
* May NOT be claimed as: "region/channel *drives* delay" causally. Must not drive automated adverse decisions without fairness audit (disparate impact, calibration by group, stability over region). Consider mitigation: exclude, residualize, or constrain model; always disclose correlation.

**Drift / calendar proxy (available but non-stationary)**
* `calendar_week`
* May be claimed as: *predictive in observed period* due to alignment with policy change/holiday. Must disclose confound.
* May NOT be claimed as: stable operational rule ("week 52 is worse"). Requires out-of-time validation, deconfounding, and monitoring. If policy change explains effect, use explicit `policy_version` feature instead.

**Unusable until lineage is repaired (conceptually valid but current lineage leaks future)**
* `final_handler_team`  `handler_team_at_t0`; `prior_claim_count_before_t0` (fix SQL predicate); `same_day_document_count_snapshot`  `doc_count_as_of_t0`; `risk_score_current`  `risk_score_as_of_t0`; `last_resource_role`  `role_at_t0`; `employee experience`  historized experience; `num_document_requests_total`  prefix count; `full_trace_variant_id`/`appeal_seen_anywhere` have no prefix analogue with same meaning.
* May NOT be claimed at all until point-in-time repair and prefix-only recomputation are proven via test A. After repair they may move to defensible or proxy categories.

Standards summary: *Predictive validity* = available at t0 + reliably measured. *Causal interpretation* requires additional assumptions (no confounding, interventional evidence) - never inferred from SHAP. *Operational actionability* requires a lever that changes the outcome without breaking the feature's measurement. *Fairness review* required for proxies even if predictive.

## 5. Recommendations for explanation validation

**P0 - Block leakage at source (feature store)**
* Enforce point-in-time (PIT) correctness: every feature must be registered with `feature_timestamp` and materialized via `AS OF t0` joins. Adopt SCD2 / temporal tables for `handler_team`, `risk_score`, `employee_experience`, `reserve`. Reject `extraction_date` as cutoff.
* Separate `*_at_t0` vs `*_total`/`*_anywhere` namespaces; ban complete-trace aggregates for t0 models in CI.

**P0 - Prefix-only recomputation gate**
* In training and explanation pipelines, compute features from `events WHERE event_time <= t0` only. Add automated test: `recomputed_prefix_value == served_value`; fail build on mismatch. Apply to `prior_claim_count`, `doc_count`, `variant_id`.

**P0 - Process-conformance tests in CI**
* Maintain normative model as code (BPMN + Declare constraints). Run alignment/footprint checks on each batch: verify no `Close before Assessment`, no `Appeal without Decision`, repeated `Decision` only after `Appeal`, Fraud Investigation may interleave. Quarantine trace patterns violating constraints and flag sequence explanations containing impossible edges.

**P1 - Timestamp & ordering hygiene**
* Require `sequence_index` for all events; treat same-timestamp without index as `ordering_uncertain` and exclude from DFG/pattern mining. Validate ingestion order vs event time.

**P1 - Calibration after feature removal**
* Removing top-leakage features (`total_duration`, `appeal`, `full_variant`, `num_requests_total`, `final_decision`) will change score distribution. Refit or recalibrate (Platt/isotonic) and re-establish decision thresholds on out-of-time holdout; report new AUC/PR and expected breach rate before redeployment.

**P1 - Explanation stability & necessity tests**
* Test stability: bootstrap prefix, small timestamp jitter, and queue tolerance ±5min; flag fragile explanations. Test necessity: remove each driver and measure  prediction; leaked features often show inflated necessity.

**P1 - Proxy / fairness analysis**
* For `region`, `channel`, `reserve`: audit calibration and false-positive rate by group, measure correlation with protected attributes, test within-group predictive value. Document trade-off: predictive validity  justification for use. Consider fairness-constrained alternatives or explicit inclusion of repair-network coverage variable to deproxy.

**P1 - Drift & calendar handling**
* Replace raw `calendar_week` with explicit `policy_version` and `holiday_indicator` where possible; otherwise evaluate `week` only with out-of-time validation and stability monitoring. Monitor PSI / drift for all features.

**P2 - Monitoring for schema/process drift**
* Monitor: distribution of prefix length at t0, rate of `Fraud Investigation`, proportion of appeals, queue snapshot missing rate, same-timestamp rate, feature freshness lag. Alert on schema changes (new decision values, team reorg) that invalidate explanations.

**P2 - Documentation & review**
* Each explanation must carry provenance: `t0`, `feature_as_of_time`, `conformance_status`, and `causal_boundary` disclaimer ("predictive association, not interventional effect"). Require process-mining sign-off for any sequence pattern explanation.
