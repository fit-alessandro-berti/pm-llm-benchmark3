## 1. Analytical assumptions

**Case notion, convergence, divergence:**
- A *case notion* defines what constitutes a process instance (e.g., an Order, an Item, a Package). *Convergence* occurs when multiple objects of the same type (e.g., Orders) are linked to a single event (e.g., a Dispatch event involving O1, O2, O3). *Divergence* occurs when a single object (e.g., Order O1) is linked to multiple events of the same type (e.g., multiple Dispatch events).
- In OCEL 2.0, shared events are explicitly copied into every relevant case during flattening. I treat these as *both evidence and duplication*: they are valid process steps but may inflate frequency metrics if not handled carefully.

**Copied shared events:**
- I consider them as *evidence* (they reflect real-world occurrences) but also as *duplication* (they artificially increase event counts in flattened logs). Their treatment depends on the analytical goal: for end-to-end analysis, they may be retained; for frequency-sensitive tasks, they may need filtering or weighting.

**Analytical transformations permitted:**
- I allow *explicit relation propagation* through O2O links (e.g., inferring that an event related to Package P1 is also related to Order O1 via the `packs` relation) only when explicitly justified by business logic (e.g., for end-to-end Order analysis). This is not done silently but only as a deliberate transformation for specific questions.

## 3. Concrete distortion analysis

### 1. Cross-order package consolidation (Package flattening)
- **Affected flattening**: Package
- **Events/objects**: e13 (Pack Package: O2, O3, I21, I31, P3), e14 (Pack Package: O3, O4, I32, I41, P4), e16 (Dispatch: O1, O2, O3, I12, I21, I31, P2, P3, D2), e24 (Confirm Delivery: O1, O2, O3, I12, I21, I31, P2, P3, D2)
- **Distortion**: In Package flattening, P3 and P4 are treated as single cases, but their events involve multiple orders (O2/O3 for P3; O3/O4 for P4). The DFG will show "convergent" edges (e.g., Dispatch  Confirm Delivery for P3) that actually represent three orders, inflating the apparent complexity of the package’s lifecycle. The *convergence risk* is high: the flattened DFG for P3 will show a single trace with events e13, e16, e24, but these events are shared with O2 and O3, distorting frequency metrics.
- **Effect**: Harmful for package-centric analysis if the goal is to understand package-specific behavior, as the traces are artificially long and conflate multiple orders.

### 2. Cross-order package consolidation (Order flattening)
- **Affected flattening**: Order
- **Events/objects**: e13 (Pack Package: O2, O3, I21, I31, P3), e16 (Dispatch: O1, O2, O3, I12, I21, I31, P2, P3, D2), e24 (Confirm Delivery: O1, O2, O3, I12, I21, I31, P2, P3, D2)
- **Distortion**: In Order flattening, the shared events (e13, e16, e24) are copied into the traces for O2 and O3, creating duplicate events in their lifecycles. For example, O2’s trace will include e13 (Pack Package), e16 (Dispatch), and e24 (Confirm Delivery), even though these events are shared with O3. This inflates the event count for O2 and O3, distorting frequency metrics (e.g., "O2 has 10 events" is misleading because 3 are shared).
- **Effect**: Harmful for frequency-sensitive analysis (e.g., bottleneck detection) but informative for understanding cross-order interactions.

### 3. Consolidated delivery (Delivery flattening)
- **Affected flattening**: Delivery
- **Events/objects**: e16 (Dispatch: O1, O2, O3, I12, I21, I31, P2, P3, D2), e24 (Confirm Delivery: O1, O2, O3, I12, I21, I31, P2, P3, D2)
- **Distortion**: In Delivery flattening, D2’s trace includes e16 and e24, which involve three orders (O1, O2, O3) and two packages (P2, P3). The DFG will show a single edge from Dispatch to Confirm Delivery for D2, but this edge actually represents the consolidation of three orders. The *divergence risk* is low (D2’s lifecycle is clear), but the *convergence risk* is high: the flattened DFG overrepresents the complexity of D2’s role.
- **Effect**: Harmful for delivery-centric analysis if the goal is to understand D2’s specific behavior, as the trace conflates multiple orders.

### 4. Consolidated invoicing (Invoice flattening)
- **Affected flattening**: Invoice
- **Events/objects**: e19 (Issue Invoice: O2, O3, V2), e22 (Record Payment: O2, O3, V2, M2), e25 (Record Payment: O2, O3, V2, M3)
- **Distortion**: In Invoice flattening, V2’s trace includes e19, e22, and e25, which involve two orders (O2, O3) and two partial payments (M2, M3). The DFG will show edges from Issue Invoice  Record Payment (twice), but these edges represent two orders and two payments. The *convergence risk* is high: the flattened DFG overrepresents the complexity of V2’s lifecycle.
- **Effect**: Harmful for invoice-centric analysis if the goal is to understand V2’s specific behavior, as the trace conflates multiple orders and payments.

### 5. Partial payments (Payment flattening)
- **Affected flattening**: Payment
- **Events/objects**: e22 (Record Payment: O2, O3, V2, M2), e25 (Record Payment: O2, O3, V2, M3)
- **Distortion**: In Payment flattening, M2 and M3 are treated as separate cases, each with a single event (Record Payment). The DFG will show two traces (M2 and M3) with one event each, but these payments are part of a single settlement for V2. The *divergence risk* is high: the flattened DFG artificially fragments the payment process into two short traces, losing the context of partial payments.
- **Effect**: Harmful for payment-centric analysis if the goal is to understand settlement patterns, as the traces are too short and lack context.

### 6. Near-singleton lifecycle (Item flattening)
- **Affected flattening**: Item
- **Events/objects**: I11 (e05, e11, e15, e23), I12 (e06, e12, e16, e24), I21 (e07, e13, e16, e24), I31 (e08, e13, e16, e24), I32 (e09, e14, e17, e27), I41 (e10, e14, e17, e27)
- **Distortion**: In Item flattening, each item has a short lifecycle (4 events), but the traces are fragmented (e.g., I11’s trace: Add Item  Pack Package  Dispatch  Confirm Delivery). The DFG will show simple linear paths for each item, but these paths lack order-level context (e.g., I11 and I12 belong to O1). The *divergence risk* is high: the flattened DFG artificially shortens lifecycles by ignoring order-level interactions.
- **Effect**: Harmful for end-to-end analysis but informative for item-level questions.

### 7. Artificial lifecycle truncation (Order flattening)
- **Affected flattening**: Order
- **Events/objects**: O2 and O3 share events e13 (Pack Package), e16 (Dispatch), e19 (Issue Invoice), e22 (Record Payment), e24 (Confirm Delivery), e25 (Record Payment), e30 (Close Order)
- **Distortion**: In Order flattening, O2 and O3 have artificially short lifecycles because many events are shared. For example, O2’s trace includes e13, e16, e19, e22, e24, e25, e30, but these events are shared with O3. The *lifecycle truncation risk* is high: the flattened traces for O2 and O3 are shorter than their true lifecycles because shared events are not duplicated in the real world.
- **Effect**: Harmful for lifecycle analysis (e.g., "How long does it take to fulfill O2?") because the traces underrepresent the true duration.

### 8. Overrepresentation of convergence in DFG (Order flattening)
- **Affected flattening**: Order
- **Events/objects**: e16 (Dispatch: O1, O2, O3, ...), e24 (Confirm Delivery: O1, O2, O3, ...)
- **Distortion**: In Order flattening, the DFG will show edges like Dispatch  Confirm Delivery for O1, O2, and O3, but these edges are shared events. The *frequency inflation risk* is high: the DFG will overrepresent the frequency of Dispatch  Confirm Delivery because the same edge is copied into three traces.
- **Effect**: Harmful for frequency-sensitive analysis (e.g., bottleneck detection) because the edge frequency is artificially inflated.

## 4. Traditional versus object-centric analysis portfolio

### Flattened logs to create:
1. **Order-flattened log**: For end-to-end order fulfillment analysis (e.g., "How long does it take to fulfill an order?"). Must account for convergence and duplication.
2. **Package-flattened log**: For package consolidation analysis (e.g., "Which packages consolidate multiple orders?").
3. **Invoice-flattened log**: For invoice and payment tracking (e.g., "How are invoices settled?").

### Questions each flattened log can answer safely:
- **Order-flattened log**:
  - End-to-end order lifecycles (e.g., time from Create Order to Close Order).
  - Order-specific bottlenecks (e.g., delays between Dispatch and Confirm Delivery).
  - *But*: Cannot safely answer cross-order questions (e.g., "Which packages consolidate multiple orders?").

- **Package-flattened log**:
  - Package consolidation patterns (e.g., P3 packs items from O2 and O3).
  - Package routing (e.g., which deliveries carry which packages).
  - *But*: Cannot safely answer order-level questions (e.g., "How long does it take to fulfill O2?").

- **Invoice-flattened log**:
  - Invoice settlement patterns (e.g., V2 is paid in two instalments).
  - Payment timing (e.g., time between Issue Invoice and Record Payment).
  - *But*: Cannot safely answer order-level questions (e.g., "Which orders are billed by V2?").

### Questions requiring object-centric analysis:
- **Cross-order interactions**: Use OC-DFG or OTG to analyze events like e13 (Pack Package: O2, O3, P3) or e16 (Dispatch: O1, O2, O3, P2, P3, D2).
- **Consolidation patterns**: Use ET–OT graph to analyze how orders, packages, and deliveries interact (e.g., P3 consolidates O2 and O3).
- **Partial payments**: Use object interaction summary to analyze how M2 and M3 relate to V2 and O2/O3.
- **Lifecycle truncation**: Use OC-DFG to analyze the true duration of O2’s lifecycle, accounting for shared events.

### Reconciling contradictory findings:
- If the Order-flattened log shows O2’s lifecycle as 10 events but the OC-DFG shows 15 events (due to shared events), the discrepancy is due to duplication in the flattened log. The OC-DFG provides the ground truth.
- For frequency metrics, compare edge frequencies in the flattened DFG (inflated) with the OC-DFG (accurate).

## 5. Lead-object decision

**Decision**: **B. Use a primary lead object (Order) plus explicitly secondary lifecycles (Package, Invoice).**

### Decision criteria:
1. **Business relevance**: Orders are the primary business entity in order fulfillment. Most questions (e.g., "How long does it take to fulfill an order?") are order-centric.
2. **Convergence vs. divergence**: Order flattening preserves end-to-end lifecycles but suffers from convergence (shared events). Package and Invoice flattening are secondary but provide critical context for consolidation patterns.
3. **Distortion tolerance**: Order flattening’s distortions (e.g., frequency inflation) are manageable with explicit handling (e.g., filtering shared events or using OC-DFG for validation).
4. **Complementarity**: Package and Invoice flattening address specific questions (e.g., consolidation) that Order flattening cannot.

### Strongest supporting evidence:
- Orders are the only object type that can answer end-to-end fulfillment questions (e.g., time from Create Order to Close Order).
- Cross-order interactions (e.g., P3 packs O2 and O3) are critical for understanding consolidation, but Order flattening alone cannot capture them without secondary analysis.

### Strongest counterargument:
- Order flattening suffers from convergence and duplication, distorting frequency metrics and lifecycles. A pure Order-centric approach may mislead frequency-sensitive analysis.

### Residual risk:
- Frequency inflation in Order-flattened DFG may lead to incorrect bottleneck detection. Mitigation: Use OC-DFG for validation or filter shared events in the flattened log.

### Conditions to change decision:
- If the primary questions shift to package consolidation or invoice settlement, Package or Invoice could become the primary lead object.
- If the process becomes more order-centric (e.g., no cross-order consolidation), Order flattening alone may suffice.

## 7. Sensitivity and validation plan

### Sensitivity checks:
1. **Remove or down-weight copied shared events**:
   - Compare Order-flattened DFG with and without shared events (e.g., e16, e19, e22).
   - Expected: Frequency inflation in shared edges (e.g., Dispatch  Confirm Delivery) should decrease.

2. **Compare direct E2O relations with propagated-relation variant**:
   - Create a variant of the OCEL where O2O relations (e.g., `packs`) are propagated to E2O relations (e.g., Pack Package events for P3 also include O2 and O3).
   - Compare the Order-flattened DFG with and without propagation.
   - Expected: Propagation should reduce convergence in Order flattening but may introduce noise.

3. **Change the lead object**:
   - Re-run analysis with Package as the lead object.
   - Compare Package-flattened DFG with Order-flattened DFG.
   - Expected: Package-flattened DFG should show clearer consolidation patterns (e.g., P3’s lifecycle) but lose order context.

4. **Compare frequency metrics**:
   - Compare edge frequencies in:
     - Order-flattened DFG (inflated due to shared events).
     - OC-DFG (accurate).
     - Package-flattened DFG (focused on consolidation).
   - Expected: Order-flattened DFG will overrepresent frequencies for shared edges (e.g., Dispatch  Confirm Delivery).

### Validation:
- Use OC-DFG as the ground truth for cross-order interactions (e.g., P3 consolidating O2 and O3).
- For end-to-end order questions, validate Order-flattened lifecycles against OC-DFG, accounting for shared events.
- For consolidation questions, validate Package-flattened DFG against ET–OT graph.
