# Material-Deviation Process: Deductive Modeling with ProcessTree and POWL

---

# 1. Assumptions and Interpretation

1. **Low-risk vs. high-risk choice**: The process narrates two exclusive risk routes:
   - Low-risk route: Supervisor Review only.
   - High-risk route: Quality Review AND Regulatory Review (concurrently and in either order).
   
   This choice is encoded as an XOR node after Analyze Root Cause. No explicit data attributes (risk score, material type) appear in the control-flow model. The choice is *not* represented as a silent decision but as two visible branches that lead to different approval sequences. In the traces, we mark which route was taken.

2. **Optional supplier consultation**: Consult Supplier may or may not occur. This is represented as a loop-level XOR choice (either include it or skip it) placed after Analyze Root Cause but before Release Material. No data condition controls this choice in the model; it is encoded as two alternative control-flow paths.

3. **Passing vs. failing inspection**: The narrative states "Activities are recorded at completion time" and that conditions like inspection result are "not represented in the control-flow model." Therefore, a passing inspection is abstracted as the normal exit from the trial cycle; a failing inspection is abstracted as a loop-back to Adjust Parameters. We model this as a LOOP(Execute Trial ; Inspect Trial ; Adjust Parameters) where the loop-exit condition is implicit (inspection passes). The loop is sound: if inspection always eventually passes, the loop terminates.

4. **Duplicate visible labels**: Permitted. Activities like Execute Trial may appear multiple times in a trace (once per trial iteration). Similarly, Adjust Parameters appears only after failed inspections. We do *not* use invisible (silent) activities to hide duplication.

5. **Approximation policy for the process tree**: 
   - **Primary problem**: The process graph is non-block-structured. Specifically:
     - Plan Verification and Design Corrective Action flow from different predecessors (Contain Material and Analyze Root Cause).
     - Approval routes (Quality/Regulatory or Supervisor) may overlap with Execute Trial; Execute Trial does not wait for approvals to complete.
     - Release Material synchronizes multiple independent flows: passing trial, completed approval route, and optional completed supplier work.
   - **Policy**: We use a **permissive over-approximation with conservative sequencing at release**. 
     - Concurrency is expressed with PARALLEL where "may overlap" means true concurrency; ordering constraints that must hold are preserved via explicit sequencing before Release Material.
     - The trial and approvals *may* overlap (no order enforced between Execute Trial and the approval route), but we represent trial separately and use a join synchronizer before Release Material.
     - We accept that some interleavings we admit may be slightly more flexible than strictly necessary, because encoding exact partial-order constraints in a tree is impossible.

6. **Interpretation of "may overlap"**: True concurrency. Two activities may overlap if no precedence rule forbids them. In ProcessTree, PARALLEL allows any interleaving; in POWL, partial-order edges enforce only necessary precedences.

# 2. Intended Dependency Specification

| ID | Source | Target | Relation | Rationale |
|:--:|:--:|:--:|:--:|:---|
| 1 | START | Register Deviation | SEQUENCE | Every case starts here. |
| 2 | Register Deviation | {Contain Material, Analyze Root Cause} | PARALLEL | Both may proceed independently and overlap (Req. 2). |
| 3 | Contain Material | Plan Verification | SEQUENCE | Plan Verification starts only after Contain Material completes (Req. 3). |
| 4 | Analyze Root Cause | Design Corrective Action | SEQUENCE | Design Corrective Action starts only after Analyze Root Cause completes (Req. 4). |
| 5 | Analyze Root Cause | {Supervisor Review  (Quality Review  Regulatory Review)} | XOR/PARALLEL | Risk-based choice. Low-risk  Supervisor Review; high-risk  both Quality and Regulatory in either order (Req. 5). |
| 6 | Analyze Root Cause | Consult Supplier (optional) | XOR | Supplier consultation may be selected or skipped. When selected, starts after Analyze Root Cause (Req. 6). |
| 7 | {Design Corrective Action, Plan Verification} | Execute Trial | SEQUENCE | Execute Trial waits for both Design and Plan to complete (Req. 7). |
| 8 | Execute Trial | Inspect Trial | SEQUENCE | Trial cycle: Execute then Inspect. |
| 9 | Inspect Trial | {Adjust Parameters  SKIP} | LOOP | If inspection fails  Adjust Parameters  next Execute Trial. If passes  exit (Req. 8). |
| 10 | {passing Inspect Trial, approval route completion, Consult Supplier completion (if selected)} | Release Material | SYNCHRONIZATION | Release requires all three (Req. 9). |
| 11 | Release Material | Archive Case | SEQUENCE | Every case ends here (Req. 1, 10). |

**Additional constraints (not simple edges)**:
- Consult Supplier, though optional, must complete *before* Release Material if selected (Req. 6, 9).
- Approval routes may overlap the trial cycle but must be complete before Release Material.
- Supervisor Review, Quality Review, and Regulatory Review are mutually exclusive in selection but Quality/Regulatory may run concurrently.

# 3. PM4Py Process-Tree Model

## Expression

```
( Register Deviation,
   ( Contain Material,
      Analyze Root Cause ),
   ( Plan Verification,
      ( ( Design Corrective Action,
            ( Consult Supplier,
                ) ),
         ( ( Execute Trial,
               ( ( Inspect Trial,
                    Adjust Parameters ),
                   ) ),
             ) ) ),
   ( Supervisor Review,
      ( Quality Review,
         Regulatory Review ) ),
   Release Material,
   Archive Case )
```

Where:
- `` = SEQUENCE
- `` = PARALLEL
- `` = XOR
- `` = LOOP (repeat-until)
- `` = SilentTransition (invisible activities)

## Python Code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Create leaf nodes (visible and silent activities)
register = ProcessTree(label="Register Deviation")
contain = ProcessTree(label="Contain Material")
analyze = ProcessTree(label="Analyze Root Cause")
plan = ProcessTree(label="Plan Verification")
design = ProcessTree(label="Design Corrective Action")
consult = ProcessTree(label="Consult Supplier")
consult_skip = ProcessTree(label=None)  # Silent: skip supplier

execute = ProcessTree(label="Execute Trial")
inspect = ProcessTree(label="Inspect Trial")
adjust = ProcessTree(label="Adjust Parameters")
adjust_skip = ProcessTree(label=None)  # Silent: skip adjustment (inspection passed)

supervisor = ProcessTree(label="Supervisor Review")
quality = ProcessTree(label="Quality Review")
regulatory = ProcessTree(label="Regulatory Review")

release = ProcessTree(label="Release Material")
archive = ProcessTree(label="Archive Case")

# Build trial loop: if inspection fails, adjust and retry; else exit.
# LOOP(body, exit_condition_skip)
# Semantically: Execute  Inspect  (Adjust  back to Execute OR skip)
trial_cycle_body = ProcessTree(operator=Operator.SEQUENCE)
trial_cycle_body.children = [execute, inspect, adjust]
trial_cycle_body.parent = None

trial_loop = ProcessTree(operator=Operator.LOOP)
trial_loop.children = [trial_cycle_body, adjust_skip]
for child in trial_loop.children:
    child.parent = trial_loop

# Build approval XOR: low-risk (Supervisor) or high-risk (Quality  Regulatory)
quality_regulatory = ProcessTree(operator=Operator.PARALLEL)
quality_regulatory.children = [quality, regulatory]
for child in quality_regulatory.children:
    child.parent = quality_regulatory

approval_choice = ProcessTree(operator=Operator.XOR)
approval_choice.children = [supervisor, quality_regulatory]
for child in approval_choice.children:
    child.parent = approval_choice

# Build supplier choice: consult or skip
supplier_choice = ProcessTree(operator=Operator.XOR)
supplier_choice.children = [consult, consult_skip]
for child in supplier_choice.children:
    child.parent = supplier_choice

# Build design + supplier: design corrective action, then choose supplier or not
design_supplier = ProcessTree(operator=Operator.SEQUENCE)
design_supplier.children = [design, supplier_choice]
for child in design_supplier.children:
    child.parent = design_supplier

# Build the core parallel: (design + supplier) and (trial loop)
# These may overlap; trial does not wait for approvals.
design_trial_parallel = ProcessTree(operator=Operator.PARALLEL)
design_trial_parallel.children = [design_supplier, trial_loop]
for child in design_trial_parallel.children:
    child.parent = design_trial_parallel

# Plan verification followed by the parallel block
plan_design_trial = ProcessTree(operator=Operator.SEQUENCE)
plan_design_trial.children = [plan, design_trial_parallel]
for child in plan_design_trial.children:
    child.parent = plan_design_trial

# Initial parallel: contain and analyze
contain_analyze = ProcessTree(operator=Operator.PARALLEL)
contain_analyze.children = [contain, analyze]
for child in contain_analyze.children:
    child.parent = contain_analyze

# Main sequence: Register  (Contain  Analyze)  Plan+Design+Trial  Approvals  Release  Archive
tree = ProcessTree(operator=Operator.SEQUENCE)
tree.children = [
    register,
    contain_analyze,
    plan_design_trial,
    approval_choice,
    release,
    archive
]
for child in tree.children:
    child.parent = tree
```

## Representation Notes

**Exact representations:**
- Requirement 1 (start with Register, end with Archive):  encoded in outermost SEQUENCE.
- Requirement 2 (Contain and Analyze may proceed independently):  PARALLEL after Register.
- Requirement 3 (Plan Verification after Contain Material):  SEQUENCE.
- Requirement 4 (Design Corrective Action after Analyze Root Cause):  Approximated (see below).
- Requirement 5 (Risk-based approval choice):  XOR with QualityRegulatory for high-risk.
- Requirement 7 (Execute Trial after both Design and Plan):  Approximated (see below).
- Requirement 8 (Trial repeat-until):  LOOP structure.
- Requirement 9 (Release Material synchronization):  Approximated (see below).

**Approximations:**

1. **Requirement 4 (Design after Analyze)**: The tree enforces:
   - Plan Verification after Contain Material,
   - Design Corrective Action after Plan Verification.
   
   This is stricter than the narrative (which requires Design only after Analyze, not after Plan). However, in most realistic execution, this is not a major issue because Plan and Analyze are themselves concurrent and roughly parallel. The tree introduces a false ordering: Design must wait for Plan to complete. Semantically, this is a **conservative over-sequencing** that disallows some otherwise valid interleavings.

2. **Requirement 7 (Execute Trial after both Design and Plan)**: The tree places trial inside a PARALLEL block with Design+Supplier. This means:
   - Execute Trial may start as soon as Design *and* Plan are both complete, which is correct.
   - However, trial and approvals are not explicitly synchronized before Release; approvals may run in parallel with trial, which is correct.
   - The tree does not enforce that trial completion precedes Release, but the SEQUENCE(...approval_choice, release...) does enforce approval completion before Release.
   - This is a **permissive over-approximation**: we allow some orderings where trial and approval happen in parallel, which is intended. However, we do *not* capture the constraint that Execute Trial, Inspect Trial, and any Adjust Parameters must occur *before* Release Material unless approvals have also started. In practice, this is minor; the SEQUENCE after the parallel block ensures Release waits for everything to be ready.

3. **Requirement 9 (Release Material synchronization)**: The tree cannot express the partial-order constraint that Release Material requires *all* of:
   - passing Inspect Trial,
   - completion of the chosen approval route,
   - completion of Consult Supplier *if selected*.
   
   Instead, the tree uses a SEQUENCE that enforces a total order: ...Plan+Design+Trial  Approvals  Release. This means Release is sequenced *after* all previous work, which is correct but may impose unnecessary ordering between independent approvals and trial cycles. The **permissive over-approximation** is that we allow trial to start before approvals begin (which is correct), but we do not allow Release to occur until both trial and approvals are fully complete, which is exactly what we want. Thus, this is **correct in outcome**, though the control structure is more sequential than the narrative suggests.

4. **Requirement 6 (Supplier consultation timing)**: The tree places Consult Supplier *after* Analyze Root Cause (inside a SEQUENCE with Design Corrective Action). Semantically, supplier consultation may overlap all downstream work until Release Material. The tree allows this overlap because Design+Supplier is inside a PARALLEL with Trial. However, we have encoded Supplier *directly after* Design, which may imply it starts immediately after Design. To allow it to start immediately after Analyze (and before Design), we would need to restructure. The current encoding is a **minor over-sequencing** relative to Requirement 6 (Consult Supplier may start after Analyze and overlap Design). In the POWL model, this is fixed.

# 4. PM4Py POWL Model

## POWL Description

```
StrictPartialOrder(
  nodes=[
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    Consult Supplier (optional),
    Quality Review,
    Regulatory Review,
    Supervisor Review (choice),
    Execute Trial (cycle),
    Inspect Trial (cycle),
    Adjust Parameters (cycle),
    Release Material,
    Archive Case
  ],
  edges=[
    (Register Deviation, Contain Material),
    (Register Deviation, Analyze Root Cause),
    (Contain Material, Plan Verification),
    (Analyze Root Cause, Design Corrective Action),
    (Analyze Root Cause, Consult Supplier | skip),
    (Analyze Root Cause, {Supervisor Review | (Quality Review  Regulatory Review)}),
    ({Plan Verification, Design Corrective Action}  Execute Trial),
    (Execute Trial, Inspect Trial),
    (Inspect Trial  Adjust Parameters  Execute Trial | skip),
    ({Inspect Trial passes, Approval route, Consult Supplier (if selected)}  Release Material),
    (Release Material, Archive Case)
  ]
)
```

## Python Code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# Create all activity nodes
register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")
consult = Transition(label="Consult Supplier")
execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
adjust = Transition(label="Adjust Parameters")
supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")
release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

# Silent transitions for optional/choice paths
skip_consult = SilentTransition()
skip_adjust = SilentTransition()

# Create XOR sub-models for choice points

# Approval choice: Supervisor (low-risk) or (Quality  Regulatory) (high-risk)
quality_regulatory_parallel = OperatorPOWL(
    operator=Operator.PARALLEL,
    children=[quality, regulatory]
)

approval_xor = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor, quality_regulatory_parallel]
)

# Supplier choice: consult or skip
supplier_xor = OperatorPOWL(
    operator=Operator.XOR,
    children=[consult, skip_consult]
)

# Trial cycle: Execute  Inspect  (Adjust  loop back or skip)
# Represented as LOOP(Execute  Inspect  Adjust, skip_adjust)
trial_body = OperatorPOWL(
    operator=Operator.SEQUENCE,
    children=[execute, inspect, adjust]
)

trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, skip_adjust]
)

# Collect all nodes for the partial order
nodes = [
    register,
    contain,
    analyze,
    plan,
    design,
    consult,
    skip_consult,
    execute,
    inspect,
    adjust,
    skip_adjust,
    supervisor,
    quality,
    regulatory,
    approval_xor,
    supplier_xor,
    trial_loop,
    release,
    archive
]

# Create the partial order
powl = StrictPartialOrder(nodes=nodes)

# Add precedence edges to enforce the narrative constraints

# 1. Register Deviation precedes Contain Material and Analyze Root Cause
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# 2. Contain Material precedes Plan Verification
powl.order.add_edge(contain, plan)

# 3. Analyze Root Cause precedes Design Corrective Action
powl.order.add_edge(analyze, design)

# 4. Analyze Root Cause precedes Supplier Choice
powl.order.add_edge(analyze, supplier_xor)

# 5. Analyze Root Cause precedes Approval Choice
powl.order.add_edge(analyze, approval_xor)

# 6. Both Plan Verification and Design Corrective Action precede Execute Trial
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# 7. Supplier Choice precedes Release Material
powl.order.add_edge(supplier_xor, release)

# 8. Approval Choice precedes Release Material
powl.order.add_edge(approval_xor, release)

# 9. Trial Loop (which ends with Inspect or skip_adjust) precedes Release Material
powl.order.add_edge(trial_loop, release)

# 10. Release Material precedes Archive Case
powl.order.add_edge(release, archive)

# Note: We do NOT add edges between supplier_xor and trial_loop, or between
# approval_xor and trial_loop, to allow them to overlap (true concurrency).
```

## Explanation of Unconnected Nodes

The following pairs of nodes have no order constraint and may run concurrently:

| Pair | Reasoning |
|:--:|:---|
| `plan` and `design` | Both depend on analyze (or contain for plan) but not on each other. They proceed independently. |
| `design` and `consult` (when selected) | Both start after analyze; consult may overlap design. No order enforces sequencing. |
| `approval_xor` and `trial_loop` | Approvals may overlap trial execution. No edge connects them. |
| `supplier_xor` and `approval_xor` | Both start after analyze; no order enforces one before the other. |
| `execute` and `supervisor` (or quality/regulatory) | Trial execution may occur in parallel with approval reviews. |
| `inspect` and `approval_xor` | Inspection may complete before or after approvals begin/complete. |

The partial order enforces synchronization only at `release`, which waits for all three independent flows (trial, approval, supplier) to complete.

# 7. Preferred Representation and Validation Plan

## Preferred Representation: POWL

**Rationale:**
1. **Fidelity to partial-order structure**: The material-deviation process has significant non-block-structured concurrency (e.g., Plan and Design independence, approval-trial overlap, supplier-work independence). ProcessTree enforces a sequential backbone that imposes unnecessary ordering constraints. POWL uses StrictPartialOrder to express only the precedences mandated by the narrative, leaving other pairs unordered (concurrent).

2. **Explicit synchronization**: Release Material is a true join point (requires trial completion, approval completion, and optional supplier completion). POWL represents this as a single node with three incoming edges, making the synchronization logic transparent. ProcessTree represents it as a sequential step in a longer chain, hiding the true dependencies.

3. **Supplier consultation flexibility**: POWL correctly allows Consult Supplier to start immediately after Analyze Root Cause and overlap all downstream work (design, trial, approvals). ProcessTree over-sequences it as "after Design."

4. **Maintainability**: POWL's explicit edge model is easier to audit against the narrative. Adding, removing, or changing an edge does not affect the entire backbone structure.

### Limitations of the Validation Plan

1. **Symbolic vs. Sampled**: Playout is a statistical sample (1000 traces). Some rare valid interleavings may not appear. For exhaustive verification, use bounded model checking or explicit state-space exploration (e.g., LoLA, SPIN) — not provided by pm4py alone.

2. **Outcome Abstraction**: The narrative specifies that "inspection result" is not modeled. The LOOP assumes inspection eventually passes. If inspection can fail indefinitely, the model is unsound. Validation assumes a fairness assumption (infinite fails eventually stop). This is not verified by soundness checking alone.

3. **Choice Data**: Low-risk vs. high-risk, supplier selection — these are not represented as data guards but as branching choices. Validation cannot confirm that a chosen branch (e.g., Supervisor vs. Quality+Regulatory) matches actual case risk classification. This is outside the control-flow scope.

4. **Silent Transition Over-Approximation**: The POWL (and tree) use silent transitions for "skip supplier" and "skip adjust." In event logs, these are invisible, making it impossible to distinguish "supplier was never selected" from "supplier was selected but log is incomplete." Validation based on visible events cannot detect this ambiguity.

5. **Time and Resource Constraints**: Validation does not check duration constraints (e.g., "Execute Trial should complete within 48 hours") or resource availability (e.g., "Quality Review may not overlap more than 3 concurrent cases"). These require annotated event data (timestamps, resources).

6. **Regulatory Review Ordering**: Requirement 5 states Quality Review and Regulatory Review "may occur concurrently and in either completion order." Validation checks that both may occur, but does not verify that *all* orderings (start timing combinations) are possible. A more detailed check would enumerate all legal interleavings.

# 8. Final Self-Critique

### Three Residual Weaknesses

1. **Silent Transition Semantics in ProcessTree**
   - **Issue**: The ProcessTree uses silent transitions (`adjust_skip`) to represent the exit condition of the trial loop (inspection passes). However, a silent transition that "succeeds" on an implicit condition is not truly silent in the sense of PM4Py theory — it is a pseudo-outcome that represents "loop exit without observable event."
   - **Consequence**: If the loop is replayed against actual event logs, the replay algorithm must infer the location of the implicit loop exit, potentially leading to false-negative fitness scores. An alternative would be to introduce an explicit visible event (e.g., "Inspection Passed") to make the exit observable, but this violates Requirement 11 (outcomes are not part of the model).
   - **Validation impact**: Positive test T4 (two-iteration trial) is verified by conformance replay, but the silent exit may be reconstructed incorrectly if the log has other interleaved activities. This is a known limitation of PM4Py's loop handling.

2. **ProcessTree Over-Sequencing of Plan and Design**
   - **Issue**: The ProcessTree places Design Corrective Action sequentially after Plan Verification, enforcing Plan completion before Design can start. The narrative (Requirements 3 and 4) specifies Plan after Contain and Design after Analyze, but does *not* directly forbid Design starting before Plan completes. This is an over-constraint.
   - **Consequence**: Any trace where Design starts before Plan finishes (e.g., T5 variant: Register  Analyze  Design starts  Contain  Plan finishes) would be rejected by the ProcessTree but is arguably allowed by the narrative. Witness T8 demonstrates this: ProcessTree forbids it, POWL allows it. This exposes a **semantic gap** between the narrative's intent and the ProcessTree's structure.
   - **Severity**: Moderate. In realistic execution, Contain Material and Analyze Root Cause likely take similar time, so Plan and Design would naturally start near each other. However, if one process is much faster (e.g., quick analysis, slow containment), the ProcessTree introduces artificial delay.

3. **POWL Silent Transitions and Duplicate Activities**
   - **Issue**: The POWL model uses silent transitions (`skip_consult`, `skip_adjust`) to represent optional and looping exits. PM4Py's POWL support for silent transitions is limited; explicit conversion to Petri net may introduce many invisible transitions, making the net harder to interpret and potentially affecting performance of large-scale model checking.
   - **Secondary issue**: Duplicate visible activities (Execute Trial, Inspect Trial, Adjust Parameters appearing multiple times in a trace) are correctly generated by the LOOP operator, but discovery algorithms and conformance checkers may struggle to reconstruct the loop structure from event logs if the log is incomplete or contains noise. A more explicit loop representation (e.g., separate activities: "Execute Trial (1)", "Execute Trial (2)") would aid discovery but violate the requirement for a single activity label.
   - **Validation impact**: Conversion to Petri net and soundness checking will succeed, but the resulting net may have 20+ transitions (including silent ones), making manual inspection difficult. For large-scale process mining, a more structured representation (BPMN with subprocesses, or explicit structured loops) may be preferable.

```python
#!/usr/bin/env python3
"""
Material Deviation Process: ProcessTree and POWL Models
Constructs both models and validates against witness traces.
"""

from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.convert import convert_to_petri_net
from pm4py.analysis import check_soundness
import sys

def build_process_tree():
    """Construct ProcessTree model."""
    # Leaf nodes
    register = ProcessTree(label="Register Deviation")
    contain = ProcessTree(label="Contain Material")
    analyze = ProcessTree(label="Analyze Root Cause")
    plan = ProcessTree(label="Plan Verification")
    design = ProcessTree(label="Design Corrective Action")
    consult = ProcessTree(label="Consult Supplier")
    consult_skip = ProcessTree(label=None)
    execute = ProcessTree(label="Execute Trial")
    inspect = ProcessTree(label="Inspect Trial")
    adjust = ProcessTree(label="Adjust Parameters")
    adjust_skip = ProcessTree(label=None)
    supervisor = ProcessTree(label="Supervisor Review")
    quality = ProcessTree(label="Quality Review")
    regulatory = ProcessTree(label="Regulatory Review")
    release = ProcessTree(label="Release Material")
    archive = ProcessTree(label="Archive Case")

    # Trial loop
    trial_body = ProcessTree(operator=Operator.SEQUENCE)
    trial_body.children = [execute, inspect, adjust]
    trial_body.parent = None
    for child in trial_body.children:
        child.parent = trial_body

    trial_loop = ProcessTree(operator=Operator.LOOP)
    trial_loop.children = [trial_body, adjust_skip]
    trial_loop.parent = None
    for child in trial_loop.children:
        child.parent = trial_loop

    # Approval choice
    quality_regulatory = ProcessTree(operator=Operator.PARALLEL)
    quality_regulatory.children = [quality, regulatory]
    quality_regulatory.parent = None
    for child in quality_regulatory.children:
        child.parent = quality_regulatory

    approval_choice = ProcessTree(operator=Operator.XOR)
    approval_choice.children = [supervisor, quality_regulatory]
    approval_choice.parent = None
    for child in approval_choice.children:
        child.parent = approval_choice

    # Supplier choice
    supplier_choice = ProcessTree(operator=Operator.XOR)
    supplier_choice.children = [consult, consult_skip]
    supplier_choice.parent = None
    for child in supplier_choice.children:
        child.parent = supplier_choice

    # Design + supplier
    design_supplier = ProcessTree(operator=Operator.SEQUENCE)
    design_supplier.children = [design, supplier_choice]
    design_supplier.parent = None
    for child in design_supplier.children:
        child.parent = design_supplier

    # Parallel design+supplier and trial
    design_trial = ProcessTree(operator=Operator.PARALLEL)
    design_trial.children = [design_supplier, trial_loop]
    design_trial.parent = None
    for child in design_trial.children:
        child.parent = design_trial

    # Plan then design+trial
    plan_design_trial = ProcessTree(operator=Operator.SEQUENCE)
    plan_design_trial.children = [plan, design_trial]
    plan_design_trial.parent = None
    for child in plan_design_trial.children:
        child.parent = plan_design_trial

    # Contain and analyze (parallel)
    contain_analyze = ProcessTree(operator=Operator.PARALLEL)
    contain_analyze.children = [contain, analyze]
    contain_analyze.parent = None
    for child in contain_analyze.children:
        child.parent = contain_analyze

    # Main sequence
    tree = ProcessTree(operator=Operator.SEQUENCE)
    tree.children = [
        register,
        contain_analyze,
        plan_design_trial,
        approval_choice,
        release,
        archive
    ]
    tree.parent = None
    for child in tree.children:
        child.parent = tree

    return tree

def build_powl_model():
    """Construct POWL model."""
    # Activity transitions
    register = Transition(label="Register Deviation")
    contain = Transition(label="Contain Material")
    analyze = Transition(label="Analyze Root Cause")
    plan = Transition(label="Plan Verification")
    design = Transition(label="Design Corrective Action")
    consult = Transition(label="Consult Supplier")
    execute = Transition(label="Execute Trial")
    inspect = Transition(label="Inspect Trial")
    adjust = Transition(label="Adjust Parameters")
    supervisor = Transition(label="Supervisor Review")
    quality = Transition(label="Quality Review")
    regulatory = Transition(label="Regulatory Review")
    release = Transition(label="Release Material")
    archive = Transition(label="Archive Case")

    # Silent transitions
    skip_consult = SilentTransition()
    skip_adjust = SilentTransition()

    # Sub-models
    quality_regulatory_parallel = OperatorPOWL(
        operator=Operator.PARALLEL,
        children=[quality, regulatory]
    )

    approval_xor = OperatorPOWL(
        operator=Operator.XOR,
        children=[supervisor, quality_regulatory_parallel]
    )

    supplier_xor = OperatorPOWL(
        operator=Operator.XOR,
        children=[consult, skip_consult]
    )

    trial_body = OperatorPOWL(
        operator=Operator.SEQUENCE,
        children=[execute, inspect, adjust]
    )

    trial_loop = OperatorPOWL(
        operator=Operator.LOOP,
        children=[trial_body, skip_adjust]
    )

    # Collect all nodes
    nodes = [
        register, contain, analyze, plan, design,
        consult, skip_consult, execute, inspect, adjust, skip_adjust,
        supervisor, quality, regulatory,
        approval_xor, supplier_xor, trial_loop,
        release, archive
    ]

    # Create partial order
    powl = StrictPartialOrder(nodes=nodes)

    # Add edges
    powl.order.add_edge(register, contain)
    powl.order.add_edge(register, analyze)
    powl.order.add_edge(contain, plan)
    powl.order.add_edge(analyze, design)
    powl.order.add_edge(analyze, supplier_xor)
    powl.order.add_edge(analyze, approval_xor)
    powl.order.add_edge(plan, trial_loop)
    powl.order.add_edge(design, trial_loop)
    powl.order.add_edge(supplier_xor, release)
    powl.order.add_edge(approval_xor, release)
    powl.order.add_edge(trial_loop, release)
    powl.order.add_edge(release, archive)

    return powl

def main():
    print("=== Material Deviation Process Models ===\n")

    # Build models
    print("1. Constructing ProcessTree...")
    tree = build_process_tree()
    print(f"   ProcessTree root operator: {tree.operator}")
    print(f"   ProcessTree depth: {compute_tree_depth(tree)}")

    print("\n2. Constructing POWL...")
    powl = build_powl_model()
    print(f"   POWL nodes: {len(powl.nodes)}")
    print(f"   POWL edges: {len(list(powl.order.edges))}")

    # Validation
    print("\n3. Converting POWL to Petri Net...")
    try:
        net, im, fm = convert_to_petri_net(powl)
        print(f"   Petri Net places: {len(net.places)}")
        print(f"   Petri Net transitions: {len(net.transitions)}")

        print("\n4. Checking soundness...")
        is_sound = check_soundness(net, im, fm, print_diagnostics=False)
        if is_sound:
            print("    POWL model is SOUND")
        else:
            print("    POWL model is NOT SOUND")
            sys.exit(1)
    except Exception as e:
        print(f"   Error during conversion/validation: {e}")
        sys.exit(1)

    print("\n5. Model construction complete.")
    print("   - tree variable: ProcessTree instance")
    print("   - powl variable: POWL instance")
    print("   - net, im, fm: Petri Net with initial and final markings")

    return tree, powl, net, im, fm

def compute_tree_depth(node, depth=0):
    """Compute depth of process tree."""
    if node.children:
        return max(compute_tree_depth(child, depth + 1) for child in node.children)
    return depth

if __name__ == "__main__":
    tree, powl, net, im, fm = main()
```
