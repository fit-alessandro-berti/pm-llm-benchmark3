## 2. Process-model consistency checks

To guarantee process validity, models and explanations must pass an automated **Process-Aware Validation Suite** before deployment:

```
                      +---------------------------------------+
                      |         Raw Claims Data Stream        |
                      +---------------------------------------+
                                          |
                                          v
                      +---------------------------------------+
                      |   1. Point-in-Time Prefix Cutoff      |
                      |   (Discard events > t0 timestamp)     |
                      +---------------------------------------+
                                          |
                                          v
                      +---------------------------------------+
                      |   2. Sequence Index Disambiguation    |
                      |   (Order identical-timestamp events)  |
                      +---------------------------------------+
                                          |
                                          v
                      +---------------------------------------+
                      |   3. Declarative Normative Check      |
                      |   (Validate structural state rules)   |
                      +---------------------------------------+
                                          |
                                          v
                      +---------------------------------------+
                      |   4. Multi-Instance Semantic Rules    |
                      |   (Verify appeal/redecision loops)    |
                      +---------------------------------------+
                                          |
                                          v
                      +---------------------------------------+
                      | Validated Prefix Feature Vector (t0)  |
                      +---------------------------------------+
```

### Validation Suite Components
1. **Point-in-Time Prefix Cutoff ($t_0$ Filtering):**
   * *Mechanism:* Truncate the trace to events where $\text{timestamp}(e) \le t_0$. Any attribute derived from events $> t_0$ is flagged as temporal leakage and blocked.
2. **Same-Timestamp Disambiguation:**
   * *Mechanism:* When $\text{timestamp}(e_i) == \text{timestamp}(e_j)$, enforce ordering using a deterministic system sequence index (`event_id` or transaction sequence). If sequence data is missing, the event pair is flagged as ambiguous and excluded from sequence feature extraction.
3. **Declarative Normative Constraints:**
   * *Mechanism:* Define hard process constraints (e.g., LTL / Declare logic: `Claim Closed` CANNOT occur before `Damage Assessment Completed`). Any pattern breaching these constraints is rejected as a logging artifact or processing error.
4. **Complete-Trace vs. Prefix State Verification:**
   * *Mechanism:* Compare feature extraction logic against prefix state. Attributes referencing case termination (e.g., `final_*`, `total_*`, `full_trace_*`) are programmatically denied.
5. **State Enablement and Reachability Analysis:**
   * *Mechanism:* Evaluate whether an activity is *enabled*, *impossible*, or *future-possible* at $t_0$. At $t_0$ (`Coverage Check Completed`), `Damage Assessment Completed` is *future-possible*, while `Appeal` is *currently disabled* (requires a prior `Partial` or `Deny` decision). Explanations must never cite currently disabled activities as past actions.
6. **Multi-Instance Semantic Rules (Appeals and Re-decisions):**
   * *Mechanism:* Recognize that identical activity labels can legitimately recur under valid sub-processes. For instance, `Settlement Decision Recorded` $\rightarrow$ `Appeal` $\rightarrow$ `Settlement Decision Recorded` is semantically valid, whereas repeating `Settlement Decision Recorded` without an intervening `Appeal` or `Reopening` event is flagged as an invalid state transition.

### Role & Limitations of Process Mining Formalisms
* **Directly-Follows Graphs (DFG):** Useful for quick transition frequency checks, but **cannot enforce normative correctness**. A frequent DFG edge (e.g., `Claim Closed -> Damage Assessment Completed`) may simply reflect a system batch logging bug rather than a valid process flow.
* **Footprint Matrices & Declarative Rules:** Set absolute behavioral boundaries (e.g., precedence, parallel execution). They catch process impossibilities that statistical aggregations ignore.
* **Alignment & Prefix Conformance:** Maps observed prefixes against a normative reference model. This isolates true process delay from data acquisition anomalies.

## 3. Alternative feature interpretations

Surviving and repaired features must be correctly interpreted to avoid misleading operational stakeholders:

```
  +-----------------------------------------------------------------------------------+
  |                                FEATURE CATEGORIES                                 |
  +-----------------------------------+---------------+-------------------------------+
  | Category                          | Valid for     | NOT Valid for                 |
  |-----------------------------------|---------------|-------------------------------|
  | Defensible Predictive Signal      | Prediction    | Direct Causal Attribution     |
  | Process-State / Congestion Signal | Action / Sizing| Managerial Fault / Blame      |
  | Proxy (Fairness & Robustness)     | Prediction    | Performance Profiling/Bias    |
  | Drift / Calendar Proxy            | Risk Tracking | Root-Cause Process Diagnosis  |
  | Unusable (Lineage Defect)         | Neither       | Any Use (Requires Repair)     |
  +-----------------------------------+---------------+-------------------------------+
```

### 1. Defensible Predictive Signals
* **Features:** `elapsed_since_registration_at_t0`, `initial_damage_complexity`, `initial_reserve`.
* **What MAY be claimed:** Higher initial damage complexity and higher initial reserve correlate with higher risk of target breach due to structural work content. `elapsed_since_registration_at_t0` directly quantifies lost slack time.
* **What MAY NOT be claimed:** That reducing initial reserve values will causally speed up the process, or that registration delay *caused* structural claim complexity.

### 2. Process-State / Congestion Signals
* **Features:** `queue_length_at_t0`.
* **What MAY be claimed:** High operational queue volume at $t_0$ increases breach risk due to processing latency and resource contention.
* **What MAY NOT be claimed:** That individual claim attributes caused the delay, or that individual claim handlers are performing poorly.

### 3. Proxies Requiring Fairness / Robustness Review
* **Features:** `claimant_region`, `claimant_channel`.
* **What MAY be claimed:** Regional or channel origin provides empirical predictive risk weight due to variations in local repair network density, third-party communication latency, or submission formats.
* **What MAY NOT be claimed:** That regional origin or filing channel is an operational root cause or a fair basis for prioritizing/deprioritizing service level allocation.

### 4. Drift / Calendar Proxies
* **Features:** `calendar_week`.
* **What MAY be claimed:** Claims active during specific calendar weeks exhibit higher breach risk due to environmental factors (holiday staffing drops, weather events, or annual policy shifts).
* **What MAY NOT be claimed:** That the calendar week itself is an operational lever or that process efficiency has structurally changed without controlling for seasonal volume spikes.

### 5. Unusable Until Lineage is Repaired
* **Features:** `prior_claim_count_before_t0`, `same_day_document_count_snapshot`, `final_handler_team`, `risk_score_current`.
* **What MAY be claimed:** Nothing. These features contain temporal leakages or data pipeline defects.
* **What MAY NOT be claimed:** No predictive, causal, or operational inferences can be drawn until query boundaries, snapshot times, and point-in-time joins are strictly fixed.

## 5. Recommendations for explanation validation

```
 +-----------------------------------------------------------------------------------+
 |                         EXPLANATION GOVERNANCE ROADMAP                             |
 +-----------------------------------------------------------------------------------+
 | Phase 1: Data Architecture & Feature Store Fixes (Point-in-Time Joins)            |
 | Phase 2: Prefix-Only Recomputation & Model Recalibration                         |
 | Phase 3: Automated Process-Conformance & Lineage CI/CD Integration                |
 | Phase 4: Explanation Stability, Fairness, and Drift Monitoring                    |
 +-----------------------------------------------------------------------------------+
```

### Phase 1: Feature Store Design & Historical Lineage Fixes
1. **Implement Point-in-Time Feature Store Joins:**
   * Enforce point-in-time joins (`AS OF` query operators) for all predictive features. 
   * Restrict historical features (e.g., `prior_claim_count`) strictly to `event_timestamp < t0_timestamp`.
2. **Snapshot Timestamping for Dynamic Attributes:**
   * Require explicit timestamping for all mutable entities (e.g., `risk_score_at_t0`). Prohibit joining live operational table states (`extraction_date`) into training datasets.
3. **Fix Batch Aggregation Lookaheads:**
   * Modify nightly snapshot tables (e.g., `same_day_document_count_snapshot`) to calculate cumulative counts using strict microsecond filtering: `event_timestamp <= t0_timestamp`.

### Phase 2: Model Recalibration & Prefix Filtering
1. **Prefix Truncation Execution:**
   * Re-train prediction models using *only* feature vectors derived strictly at or before $t_0$.
2. **Model Recalibration:**
   * Baseline model performance (AUC/Brier score) before and after removing leaked features. Quantify real predictive capability separate from lookahead leakage.

### Phase 3: Automated Process-Conformance Validation in CI/CD
1. **Automated Lineage Rules in CI/CD Pipeline:**
   * Implement automated assertions that fail pipeline builds if complete-trace variables (`total_*`, `final_*`, `full_trace_*`, post-$t_0$ patterns) exist in early-prediction training matrices.
2. **Timestamp Sequence Disambiguation Assertions:**
   * Require ingestion pipelines to generate monotonic integer sequence IDs (`event_seq_id`) for events occurring within the same millisecond timestamp.

### Phase 4: Explanation Stability, Fairness, and Drift Monitoring
1. **Separate Predictive, Causal, and Actionable Explanations:**
   * Restrict ML SHAP outputs to **predictive risk scoring dashboards**. 
   * Prevent automated systems from displaying correlations (e.g., `claimant_region`, `calendar_week`) as actionable operational recommendations without controlled experimental validation.
2. **Proxy and Fairness Analysis:**
   * Conduct disparate impact and subgroup validation across protected proxy attributes (`claimant_region`, `claimant_channel`). Ensure predictive models do not enforce unequal service allocation.
3. **Continuous Monitoring for Schema and Process Drift:**
   * Deploy real-time drift detectors on feature distributions, process variants, and SHAP value stability. Alert process engineers when underlying process changes (e.g., workflow re-routing) degrade model calibration or explanation credibility.
