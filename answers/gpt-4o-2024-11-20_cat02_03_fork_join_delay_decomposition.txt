# 1. Delay-decomposition definitions

### Notation & Structure
- Let \( c \) index a case (F01 to F12) and \( i \in \{A, B, C\} \) a branch.
- Timestamps: \( arrival_c, fork\_release_c, final\_start_c, final\_end_c \) define the process stages at the case level, while \( start_{i,c}, end_{i,c} \) represent branch-specific activity.
- Key definitions:
    - **Upstream elapsed time before fork release**: 
      \[
      upstream\_elapsed_c = fork\_release_c - arrival_c
      \]
    - **Branch queue waiting**:
      \[
      Q_{i,c} = start_{i,c} - fork\_release_c
      \]
    - **Branch active service**:
      \[
      S_{i,c} = end_{i,c} - start_{i,c}
      \]
    - **Branch synchronization wait** (time a branch is idle after completing until `join_ready`):
      \[
      W_{i,c} = join\_ready_c - end_{i,c},
      \]
      where:
      \[
      join\_ready_c = \max(end_{A,c}, end_{B,c}, end_{C,c})
      \]
      Synchronization waits across \( \{A, B, C\} \) do not directly add to total flow time because they overlap sequentially under the fork-join rule.
    - **Elapsed fork-join stage time**:
      \[
      fork\_join\_elapsed_c = join\_ready_c - fork\_release_c
      \]
    - **Downstream queueing before final start**:
      \[
      downstream\_queue_c = final\_start_c - join\_ready_c
      \]
    - **Final active service**:
      \[
      final\_service_c = final\_end_c - final\_start_c
      \]
    - **Total case flow time**:
      \[
      total\_flow\_time_c = final\_end_c - arrival_c
      \]

### Why Synchronization Waiting Cannot Be Double-counted
Synchronization waits for each branch relate to the same `join_ready` event defined as the maximum branch completion:
\[
\text{If } W_{i,c} = join\_ready_c - end_{i,c}, \text{ then } W_{A,c} + W_{B,c} + W_{C,c} \geq fork\_join\_elapsed_c.
\]
Explicitly summing across all branches would inflate total flow since each branch waits independently of others.

# 4. Counterfactual redesign analysis

### Scenario 1: Reduce A service time (-20%)
Direct benefit only for critical-A cases (F01, F11). Cases critical on B/C will see no change. Moderate flow improvement overall.

### Scenario 2: Reduce B queue delay (-50%)
Significant reduction for B-critical cases (8/12). Largest potential flow gain.

### Scenario 3: Add final capacity
Flow improved for downstream-bound cases; unpredictability risk without resolving sync waits.

1. **Focus on B Queue Reduction** (Scenario 2).
   - Impact: Large flow reduction.
   - Risk: None-queue factors persist.

   - Impact: Smaller but distributed gain.
