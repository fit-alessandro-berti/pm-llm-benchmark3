## 2. Process-model consistency checks

### Validation Suite Design

We propose a **prefix-time alignment and declarative conformance checker** that validates every explanation against the normative process model and temporal constraints. The suite consists of the following components:

#### a. **Prefix-Time Availability Check**
- **Purpose**: Ensure every feature used in prediction or explanation is computable from events and data available at or before `t0`.
- **Method**:
  - For each feature, define a **prefix-time window** `[t_start, t0]` where `t_start` is the earliest allowed timestamp (e.g., registration time).
  - Validate that all timestamps used in feature computation fall within this window.
  - For derived features (e.g., counts, durations), ensure aggregation uses only events in the prefix.
- **Limitations**:
  - Cannot detect semantic misuse (e.g., using future events in logic).
  - Requires accurate event timestamps and sequence indices.

#### b. **Activity-Order Feasibility Check (Declarative Constraints)**
- **Purpose**: Ensure that any sequence pattern or activity pair in an explanation is **enabled** by the process model at `t0`.
- **Method**:
  - Encode normative process as a **declarative model** (e.g., Linear Temporal Logic or Simple Declare constraints):
    - `Coverage Check Completed`  `Damage Assessment Completed` or `Documents Requested`
    - `Documents Requested`  `Documents Received`  `Documents Validated` (with possible loops)
    - `Settlement Decision Recorded`  `Appeal` (only after decision)
    - `Claim Closed`  after final `Settlement Decision Recorded`
  - For each explanation, check that:
    - The pattern does not violate any constraint.
    - All activities in the pattern are **enabled** at `t0` (i.e., their enabling conditions are satisfied).
  - Flag impossible patterns (e.g., `Claim Closed` before `Damage Assessment Completed`).
- **Limitations**:
  - Declarative models may not capture all operational nuances.
  - Assumes correct event ordering; sensitive to timestamp precision.

#### c. **Same-Timestamp Ambiguity Check**
- **Purpose**: Detect events with identical timestamps that may be ordered incorrectly.
- **Method**:
  - Identify all event pairs with identical timestamps in the prefix.
  - Use a **sequence index** (if available) to determine order.
  - If no index exists, flag as ambiguous and reject patterns relying on order.
  - For Case Z: `Claim Closed` and `Damage Assessment Completed` at same timestamp  **invalid order**  remove pattern.
- **Limitations**:
  - Sequence index may not be reliable.
  - Cannot resolve ambiguity without additional metadata.

#### d. **Complete-Trace Feature Check**
- **Purpose**: Detect features that require information beyond the prefix.
- **Method**:
  - For each feature, define whether it is **prefix-computable**.
  - Features like `total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id` are **complete-trace-only**  flag as leaked.
  - Replace with prefix-computable proxies (e.g., `prefix_duration_hours`, `appeal_opened_before_t0`).
- **Limitations**:
  - May reduce predictive power; requires careful proxy design.

#### e. **Activity Enablement Check**
- **Purpose**: Determine whether an activity mentioned in an explanation is **enabled**, **impossible**, or **future-possible** at `t0`.
- **Method**:
  - Use process state at `t0` to evaluate:
    - `Damage Assessment Completed`: enabled only if fast track or after evidence collection.
    - `Appeal`: enabled only after `Settlement Decision Recorded`.
    - `Fraud Investigation Opened`: enabled at any time after coverage check.
  - Flag explanations that refer to **impossible** or **future-possible** activities.
- **Limitations**:
  - Requires accurate process state reconstruction at `t0`.

#### f. **Repeated Settlement Decision Handling**
- **Purpose**: Validate that explanations respect the semantics of repeated `Settlement Decision Recorded` events.
- **Method**:
  - Only allow `Settlement Decision Recorded` events that are **final** or **appealed**.
  - Ensure that `Appeal` events are only explained in context of prior decisions.
  - In local explanations, avoid using `final_decision` as a feature if it occurs after `t0`.
- **Limitations**:
  - Requires tracking appeal semantics in data model.

## 5. Recommendations for explanation validation

### Prioritized Plan

#### **Phase 1: Feature Store and Lineage Repair (Critical)**
1. **Implement prefix-only feature computation**:
   - Recompute all top-12 features using only events and data available at or before `t0`.
   - Replace leaked features with prefix-computable proxies:
     - `total_case_duration_hours`  `prefix_duration_hours` (elapsed from registration to `t0`)
     - `appeal_seen_anywhere`  `appeal_opened_before_t0` (boolean)
     - `num_document_requests_total`  `num_document_requests_before_t0`
     - `full_trace_variant_id`  `prefix_trace_variant_id`
     - `same_day_document_count_snapshot`  `documents_uploaded_before_t0`
2. **Fix mutable lineage defects**:
   - Ensure `final_handler_team` reflects team at `t0` or remove.
   - Recompute `prior_claim_count_before_t0` with `claim_created_at < t0`.
   - Store timestamps for `risk_score_current` and `last_resource_role`; use values at `t0`.
3. **Enhance feature store**:
   - Add `valid_from` and `valid_until` timestamps to all features.
   - Store feature computation logic and data sources.
   - Implement versioning for feature definitions.

#### **Phase 2: Process Conformance and Validation Suite (High)**
4. **Deploy process-aware validation suite**:
   - Integrate prefix-time alignment, declarative conformance, and same-timestamp checks into model training and inference pipelines.
   - Reject any explanation that violates process constraints.
5. **Implement DFG/Declarative checks**:
   - Use process mining tools (e.g., PM4Py) to validate prefix traces against normative models.
   - Flag impossible sequences (e.g., `Claim Closed` before `Damage Assessment Completed`).
6. **Add sequence index enforcement**:
   - Ensure all event logs include a reliable sequence index for same-timestamp events.

#### **Phase 3: Calibration and Fairness Review (Medium)**
7. **Recalibrate model after feature removal**:
   - Retrain model using only prefix-computable features.
   - Recalibrate predicted probabilities to ensure alignment with observed breach rates.
8. **Conduct fairness and proxy analysis**:
   - Review `claimant_region`, `claimant_channel`, and `prior_claim_count_before_t0` for disparate impact.
   - Perform subgroup analysis (e.g., by region, channel) to detect bias.
   - Document proxy relationships and avoid causal claims.
9. **Explanation stability testing**:
   - Use SHAP or LIME to test stability of explanations after feature repair.
   - Monitor for large shifts in feature importance rankings.

#### **Phase 4: Monitoring and Drift Detection (Medium)**
10. **Monitor for schema and process drift**:
    - Track changes in event logs, process variants, and feature distributions.
    - Alert on deviations from normative process constraints.
11. **Implement operational feedback loop**:
    - Allow case handlers to flag incorrect explanations.
    - Use feedback to improve process models and feature definitions.
12. **Document causal boundaries**:
    - Clearly label which features are predictive vs. causal.
    - Provide guidance to users on appropriate operational actions (e.g., resource allocation vs. claim simplification).

#### **Phase 5: Governance and Documentation (Ongoing)**
13. **Maintain explanation audit trail**:
    - Log all features used in predictions and explanations.
    - Store lineage metadata for regulatory review.
14. **Update operating policies**:
    - Clarify that explanations are predictive, not causal.
    - Define acceptable use cases for model outputs.
