FEP-1 COMPENSATING-CONTROL CONFORMANCE REVIEW — PAYMENT PROCESS, CASES AP-201 … AP-209

Framing used throughout
- "Nominal FEP-1 result" = did the same human resource perform Prepare_Payment and Release_Payment on a completed payment (the rule as written).
- "Control-objective result" = was the risk that FEP-1 exists to address (one actor initiating and authorising an erroneous or fraudulent transfer that becomes irrevocable) actually controlled, by whatever combination of controls, at the time the money could still have been stopped.
- The two can diverge in both directions: a same-user payment can meet the objective (independent gate elsewhere in time), and a distinct-user payment can fail it (second eye not independent, or not looking).
- Outcomes (loss / no loss) are evidence about the control environment but are not the verdict. A EUR 900,000 release with no reliable bank-ownership check that turned out legitimate is still a control failure; a duplicate that was blocked is a control success even though the same user tried both steps.
- Irrevocability point = Bank_Settlement (per "Additional facts"). The bank's 24-hour recall practice extends recoverability somewhat past settlement but is "uncertain" territory; I treat the pre-settlement window as the reliable stop window and the 24-hour window as a partial-recovery window.

Calendar note: 2026-05-04 is a Monday. "One business day" therefore ends 2026-05-05 for all releases here; 2026-05-08 is Friday, 2026-05-09 is Saturday, 2026-05-12 is Tuesday.

## 1. Control-Objective Decomposition

FEP-1 bundles several distinct objectives / threat scenarios. Each row states what the four available controls can and cannot do for that scenario. Prevent = stops the release or settlement; Detect = surfaces the defect afterwards; Correct = can still recover/stop; Fail = does not address it.

| # | Objective / threat scenario | AV-2 (automated pre-release validation) | MG-4 (independent L3+ manager) | RA-7 (retrospective audit / recall) | ED-1 (emergency single-operator permission) |
|---|---|---|---|---|---|
| O1 | Honest keying / data error by the preparer (wrong amount, wrong vendor, wrong account, duplicate) | Prevents the mechanical subset: duplicate invoice, operator-limit breach, PO mismatch, account not owned by vendor. Fails for "plausible but wrong" amounts inside limits and PO tolerance. | Prevents if before release and substantive (compares invoice, bank details, receipt). Detects/corrects if before settlement. Rubber-stamp = fails. | Detects; corrects only if inside recall window. | Does not address directly; it only conditions when a single operator may proceed. Conditions 2–5 shrink the error surface (small amount, stable vendor, AV pass). |

Key takeaways from the decomposition: AV-2 covers O1/O2 mechanics only; MG-4 is the only control that can address O3 preventively and it does so only when substantive, independent, and before irrevocability; RA-7 is the only control that addresses O4 at the population level and is corrective only inside the recall window; ED-1 is a set of preconditions, not a control in itself — it borrows all its protection from AV-2, MG-4 and RA-7 being genuinely satisfied.

## 2. Equivalence and Sufficiency Test

A compensating package is assessed on seven dimensions. Each dimension is scored Strong / Adequate / Weak / Absent against what a genuinely independent second releaser would provide. The overall class is determined by the weakest dimension that matters for the threat actually present in the case (not by averaging).

| Dimension | Question asked | Strong | Adequate | Weak | Absent |
|---|---|---|---|---|---|
| Timing | When, relative to Release_Payment and Bank_Settlement, does the independent human act? | Before Release_Payment (hard gate) | After release but before settlement, with an actual stop mechanism and enough time to use it | After settlement but inside the 24-hour recall window | After the recall window |
| Independence | Is the second human free of hierarchy, incentive, credential, and workstation entanglement with the preparer? | L3+, not in reporting line, no shared credentials/workstation, no personal link | L3+, different reporting line, no known conflict | Same reporting line or unresolved conflict (m09 rates u23) | Same person, or second identity operated by the same person |
| Coverage | Does the package cover the threat that this case actually presents (O1–O8)? | Covers mechanical checks and receipt and bank ownership | Covers mechanical checks and either receipt or bank ownership | Covers mechanical checks only (AV-2 alone) | Relevant check unavailable or not performed (AV-2 outage with unsigned checklist) |
| Overrideability | Can the preparer neutralise the control? | No override possible by preparer; override requires a separately authenticated independent manager acting in person | Override possible but logged and reviewed before settlement | Override possible by anyone holding a manager credential | Override performed by the preparer (AP-202) |
| Recoverability | If the control fails, can the money still be stopped or recovered? | Money not yet released | Settlement pending; recall reliably available | Inside the uncertain 24-hour recall window | Settled and recall window closed |
| Evidence quality | Can we prove what was reviewed, by whom, with what result? | Contemporaneous, itemised review record (invoice, bank, receipt) plus system logs | Approval event plus narrative statement of what was reviewed | Approval event only ("Manager_Ratify" with no content) | No signed record (unsigned checklist), or record created after the fact |
| Collusion resistance | How many independent humans must fail or collude for loss to occur? | ≥ 2 independent humans plus a machine gate whose result they see | 2 humans (one machine-gated) | 1 human plus a machine gate | 1 human, machine gate absent or overridden by that human |

Classification rule
- Fully equivalent: Timing Strong or Adequate; Independence Strong; Coverage matches the case threat; Overrideability not by the preparer; Evidence quality at least Adequate; Collusion resistance ≥ 2 humans. The package delivers a genuinely independent human judgment before irrevocability. (AP-203 is the archetype.)
- Partially equivalent: Independence Strong and the human acts before irrevocability, but one of timing (post-release), coverage (manager did not see AV result / receipt depth unknown), or evidence quality is only Adequate/Weak; or a formal ED-1 precondition failed without changing the substantive protection. Tolerable if case risk (amount, vendor, bank change) is low or medium and the gap is not the gap the threat would exploit.
- Merely mitigating: The only independent human action occurs after settlement but inside the recall window, or the independent human acts before settlement but without evidence of substantive review; or AV-2 passed but coverage does not touch the case's actual threat (e.g. receipt fraud). Risk reduced, objective not met.
- Ineffective: Independent human action absent, conflicted, or after the recall window; or control overridden by the preparer; or key check unavailable and not replaced. Any single "Absent" on Independence, Overrideability, or Coverage-for-the-present-threat puts the package here regardless of the other dimensions.

Why "same expected loss" is not the only standard
1. Tail behaviour, not mean behaviour, is what FEP-1 protects. A package can have equal expected loss but a much fatter tail (one unrecoverable EUR 900k event versus many EUR 2k errors). Four-eyes exists to cap the single-actor catastrophic event; a mean-preserving package that shifts mass to the tail is not equivalent.
2. Expected loss depends on an unknown and endogenous fraud base rate. Weak controls change behaviour (moral hazard, deterrence); the probability of an attempt is a function of the control itself, so the estimate cannot be made control-neutral.
3. Ex-ante demonstrability. Regulators, auditors and boards require controls that can be shown to have operated at the decision time. An outcome-based expected-loss argument uses information (was the vendor legitimate?) that was not available when the release button was pressed. Control adequacy must be judged on what was knowable then.
4. Non-financial harms. Sanctions breaches, data-privacy, reputational damage and criminal-liability exposure are not captured by EUR loss.
5. Accountability is itself an objective (O7). A package with identical expected loss but no attributable authoriser fails the governance purpose of the rule.
6. Recoverability asymmetry. Two packages with equal expected loss differ if one leaves a stop window and the other does not; the option value of being able to stop is not in the expectation.
7. Fairness and consistency. A case-by-case expected-loss standard would allow "it was a good vendor" to excuse the same behaviour that would be condemned when the vendor turns out bad; the control standard must be the same for both.

Therefore the test above uses expected loss as one input to Residual risk and Severity, but classifies on structural criteria (timing, independence, coverage, overrideability, recoverability, evidence, collusion resistance).

Chosen semantics for "manager acts after Release_Payment but before Bank_Settlement"
I classify this as a hybrid ("interceptive") control and I score it on Timing as Adequate, not Strong, for three reasons:
1. Form versus effect. In form it is detective: the operator has already done the thing FEP-1 forbids (initiate and authorise alone), and the manager is checking a fait accompli. In effect it can be preventive because the loss event (irrevocable settlement) has not yet occurred, and an independent human with a stop mechanism can prevent it.
2. Conditionality. Whether the effect is preventive depends on facts outside the manager's action: the settlement lag (80–90 minutes in AP-201/207, 56 minutes in AP-208), the existence of a cancel/hold facility, and whether the manager knows and is expected to use it. If any of these is absent, the action collapses to detective. That is why AP-207 carries a caveat and AP-208's ratification is plainly detective.
3. Behavioural difference. A gate before release changes the preparer's incentives (nothing moves without a second person); a review after release does not stop a determined single actor from trying and relies on someone noticing in time. That deterrence gap is real even when the recovery window is respected.
Consequently, in the sufficiency test, MG-4-before-settlement satisfies ED-1 condition 6 literally and can support OBJECTIVE_MET when the manager's review is substantive and stop capability is evidenced (AP-207), but it never scores as high as MG-4-before-release (AP-203), and it cannot compensate for a failed AV-2 coverage on the present threat (it would not have rescued AP-208 unless the manager had personally verified the bank account change).

## 5. Counterfactual and Residual-Risk Analysis

Qualitative likelihood language: "remote" (would require multiple unlikely coincidences), "low", "moderate", "high", "near-certain". Any number given is illustrative only and labelled as such.

AP-202 (EUR 480,000, realised loss)
- Most plausible loss mechanism: insider-facilitated vendor fraud. A new vendor is created, bank details are changed two hours before payment to an account controlled by an employee's relative, the preparer releases the payment himself, and the one control that fired (AV-2 warning on bank change and operator limit) is neutralised with a supervisor's override credential.
- Control that broke the causal chain: none. AV-2 detected the right thing and was overridden; MG-4 was conflicted and two days late; RA-7 came after the recall window.
- What remained exposed: everything — the full amount, unrecoverable.
- Under a truly independent second releaser: the chain breaks with high likelihood at the release step, because an independent releaser sees a new vendor, a two-hour-old bank change, no receipt, an AV warning and an override request from the preparer. Only collusion with the releaser, or the releaser also being impersonated via credential misuse, keeps the fraud alive. Illustrative: residual loss likelihood falls from near-certain (given the intent) to low.
- Residual risk if only ED-1 conditions had been enforced: ED-1 would have been unavailable on amount, vendor age, bank change and override, so enforcement alone would have forced a second human in.

AP-204 (EUR 220,000, fabricated receipt)
- Loss mechanism: payment for services not rendered, supported by a fabricated receipt; the fabrication survives both a distinct releaser and AV-2 (which does not check receipt).
- Control that broke the chain: none before settlement. RA-7 detected it four days later, outside the recall window.
- What remained exposed: the amount, plus the other 36 payments handled by the same pair in 30 days.
- Under a truly independent second releaser (someone not sharing a workstation with u12, not paired 37 times, expected to verify the service against operational evidence): moderate to high chance the fabrication is caught if the releaser actually checks receipt against a delivery/timesheet record; low chance if the releaser's role is limited to matching invoice to PO (a fabricated receipt can be internally consistent). Illustrative: loss likelihood falls from high to moderate — this threat (O3) is only partly addressed by a second releaser and needs a receipt-verification step by someone outside the payment cell.
- Key residual exposure: the second-eye control has unknown independence; until the workstation and org-design questions are answered, every u12/u13 payment carries the AP-204 uncertainty.

AP-208 (EUR 900,000, no loss)
- Loss mechanism: account diversion after a bank-detail change three days earlier (classic business-email-compromise pattern), released during an AV-2 outage so bank-ownership was never checked, by a single operator under an emergency token, settled 56 minutes later.
- Control that broke the chain: none. The outcome was legitimate because the bank change happened to be genuine, not because anything verified it.
- What remained exposed at release time: the full EUR 900,000 for one hour before settlement, then unrecoverably.
- Under a truly independent second releaser: the chain breaks with moderate to high likelihood — an independent releaser confronted with a EUR 900k payment, an eight-month-old vendor, a three-day-old bank change and an unavailable validation service should refuse or perform a call-back to a known vendor number. It does not break with certainty (the releaser can be hurried by the "emergency" and the token gives false comfort). Illustrative: had the account been fraudulent, loss likelihood drops from near-certain to low-moderate.
- Design lesson: the emergency token was the vector that made the failure possible; ED-1 must be technically blocked when AV-2 is unavailable or amount ≥ 100k.

AP-201 (EUR 1,800, no loss)
- Loss mechanism: honest keying error (wrong amount / wrong vendor) or a small-ticket diversion by the preparer.
- Control that would break the chain: AV-2 for duplicates/limits/ownership; m04's pre-settlement review for wrong amount/vendor (90-minute window); nothing for a small diversion inside limits to a vendor account already established, other than the low amount cap.
- What remained exposed: at most EUR 1,800, low-risk vendor; the exposure that matters is behavioural (habitual same-user handling by convenience normalises the pattern that made AP-202 possible).
- Under a truly independent second releaser: little change in expected loss for this payment (remote either way); large change in process integrity — the token-less same-user path would not exist. Illustrative: per-payment loss likelihood remote in both worlds; the value of enforcement is in the population, not the case.

AP-207 (EUR 35,000, no loss)
- Loss mechanism: an error or diversion in a genuine safety emergency by the single operator.
- Control that breaks the chain: m15's substantive review 80 minutes before settlement (interceptive), with AV-2 covering the mechanical checks and a 22-hour audit as backstop.
- What remained exposed: the interval 14:05–14:40 in which nothing human had reviewed the release, plus the dependency on a stop mechanism being real; also the O3 residual (receipt) that m15's review of "all supporting evidence" mitigates but cannot eliminate.
- Under a truly independent second releaser before release: the residual shrinks from low to remote; the 35-minute unreviewed interval disappears. The difference is small at this amount and vendor profile, which is why ED-1 is a reasonable design for cases like this one and not for AP-208.

AP-206 (EUR 95,000, no loss)
- Loss mechanism: error or diversion under time pressure of a production outage.
- Control that breaks the chain: m11's approval before release (preventive in timing); AV-2 pass before release.
- What remained exposed: m11 approved without the AV result (a duplicate or ownership issue would have had to be caught by AV-2 alone, which it was); the depth of m11's review is undocumented, so the O3 residual (receipt) is unknown; the token trail is weak.

- What remained exposed: nothing for this payment; process-wise, u44's willingness to attempt a same-user release without a token is a signal to monitor.
- Under a truly independent second releaser: no change in this case; AV-2 was sufficient for the covered threat.

## 6. Evidence and Monitoring Recommendations

Principle: every rule below produces an alert, i.e. a reason to collect evidence and reach a judgment. None of them is proof of misconduct. A high same-user rate can be an understaffing problem; a repeated pair can be a deliberately designed two-person cell; a late audit can be an audit-capacity issue. The alert's purpose is to force the evidence question, and the evidence collected must be able to prove the negative as well as the positive.

Evidence to collect systematically (contemporaneously, not reconstructed later)
1. For every approval/ratification event: what was reviewed (invoice, bank details, receipt/service evidence, AV result), by whom, at what time, with authentication method; a ratify event without content should be treated as Weak evidence.
2. Token lifecycle: request time, requester, issuer, justification text, issue time, expiry; clock-synchronised with the payment system so that "token before Prepare" is verifiable to the second.
3. Override events: the human physically performing the override (device, IP, workstation, session), not just the credential used; a second-factor tied to the manager's person.
4. Settlement and recall data from the bank: settlement timestamp, recall request timestamp and result, so that "before settlement" and "inside recall window" are facts, not assumptions.
5. AV-2 availability log and, during outages, a signed manual checklist naming the person (not the preparer) who performed the bank-ownership verification and the method (call-back to a known number).
6. Workstation and session telemetry for payment roles: concurrent logins, shared devices, badge presence, so that "distinct user" can be substantiated as "distinct human".
7. Vendor master-data change history with approver identity and effective time, joined to payments.
8. Audit work-programme content per case (checked receipt? checked bank ownership? checked pattern?), not just the Audit_Review event.

Monitoring rules (alerts; thresholds are starting points to be calibrated on the population)
- Same-user rate: share of completed payments where preparer = releaser, per week, per operator, per business unit. Alert if the unit rate exceeds a low single-digit percentage or if any operator exceeds a handful per month; in this sample it is 6 of 8 (75%), which is itself an alert on the sample. Split the rate into "with valid token" and "without token" — the second must be zero.
- Same-user attempt rate: include blocked/cancelled attempts (AP-205); a rising attempt rate with a flat completion rate indicates people probing the control.
- Override rate: overrides per 100 payments and per credential; alert on any override where the overriding credential's owner is the preparer's supervisor, where the overrider's device/IP matches the preparer's session (AP-202 pattern), or where the override occurs within a few minutes of the warning without any documented review.
- Late manager approval: distribution of (manager event − Release_Payment) and (manager event − Bank_Settlement); alert if the manager acts after settlement on any same-user payment, and if the pre-settlement margin is under a defined minimum (e.g. 30 minutes) because that margin is what makes the hybrid control preventive in effect.
- Manager-before-AV: alert when the manager approval precedes the AV result (AP-206), since the approval was given without that information.
- Audit-before-recall-window: share of same-user payments whose Audit_Review occurs within 24 hours of release and within one business day; alert on any same-user payment outside both, and on any payment over a threshold amount audited after the window (AP-202, AP-204, AP-208).
- Repeated resource pairs: for each (preparer, releaser) pair, count and share of that pair's payments among each member's payments over a rolling 30 days; alert when a pair's share exceeds a high proportion (e.g. more than half of either member's payments) or when the absolute count is anomalous (37 in 30 days). Treat as a design question first (is there a documented two-person cell?), a collusion question second.
- Shared workstations: alert when the preparer and releaser of the same payment used the same device or overlapping sessions, or when the releaser's session started within minutes of the preparer's on the same machine. A shared workstation is compatible with a legitimate cell; it is incompatible with proving independence, so such payments should receive a receipt-verification audit by default.
- Bank-change proximity: alert on any payment where the vendor bank account changed within 7 days (AV-2 already does so) and escalate to mandatory independent call-back when combined with any of: amount above a threshold, vendor age under one year, same-user handling, AV-2 outage, or override.
- Control outages: alert on any Release_Payment during an AV-2 unavailability window; policy should hold such payments (no single-operator release, mandatory MG-4 before release, signed manual checklist) and audit 100% of them within one business day.
- Token hygiene: alert on tokens issued after Prepare_Payment, tokens issued for amounts ≥ 100k or for vendors with recent bank changes, tokens issued by the same person repeatedly to the same operator, and tokens whose justification is missing.
- Conflict-of-interest map: maintain and enforce a list of manager–operator reporting relationships so that MG-4 cannot be performed by a manager who rates the preparer; alert on any breach.

Distinguishing alert from proof
- An alert is a statistical or rule-based deviation; proof of misconduct requires intent-relevant evidence (who benefited, who knew, what the documents actually were). The u12/u13 pattern is an alert; the fabricated receipt in AP-204 is a finding about a document; collusion is a conclusion that would require evidence about the two people, which is not yet available.
- Recommended disposition language: "control-objective failure" (a finding about the control, provable from timing and coverage), "unexplained pattern" (an alert awaiting explanation), "suspected misconduct" (referral standard requiring evidence beyond the log). AP-202 meets the referral standard; AP-204 meets it for the document and is an unexplained pattern for the pair; AP-209 is an unexplained pattern; AP-208 is a control-objective failure with no misconduct indication.

## 7. PM4Py and pandas Checking Code

Notes on PM4Py behaviour that cannot be guaranteed across versions (verified against 2.7.23.8; the code is written to cope with either behaviour):
- `pm4py.filter_four_eyes_principle` changed semantics. Older 2.x releases hard-coded "return the violating cases" (internally `positive=False`). Newer releases add a `keep_violations` argument defaulting to `False`, so the bare call returns the *conforming* cases; you must pass `keep_violations=True` to obtain violators. The code inspects the signature, passes the argument when it exists, and cross-checks the result against a transparent pandas rule; if PM4Py returns the complement, the script says so and uses the pandas set.
- The underlying LTL checker joins all `Prepare_Payment` rows to the *last* `Release_Payment` row per case and drops rows with missing resources. Consequently (a) cases with no `Release_Payment` (AP-205) are never returned in either mode, hence the separate blocked-attempt step; (b) blank resources must be filled with `SYSTEM` before filtering or those rows are dropped; (c) cases with multiple releases are judged on the last release only.
- `pm4py.format_dataframe` adds `@@index` / `@@case_index` columns and re-parses timestamps; behaviour with timezone-aware inputs has varied, so timestamps are parsed with `pd.to_datetime(utc=True)` first. Some versions emit deprecation warnings when a DataFrame is passed; they are suppressed.
- Business-day arithmetic uses `numpy.busday_count` with the default Monday–Friday calendar; corporate holidays are not modelled.
