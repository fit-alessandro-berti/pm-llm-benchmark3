import pm4py
from pm4py.objects.petri_net.obj import Marking

def copy_marking(m):
    c = Marking()
    for p, w in m.items():
        c[p] = w
    return c

def format_marking(m):
    return {p.name: m[p] for p in sorted(m.keys(), key=lambda x: x.name)}

def fire_named_transition(net, marking, tname):
    enabled = pm4py.get_enabled_transitions(net, marking)
    enabled_names = {t.name for t in enabled}
    if tname not in enabled_names:
        raise ValueError(f"Transition {tname} is not enabled; enabled: {sorted(enabled_names)}")
    trans = next(t for t in net.transitions if t.name == tname)
    new_marking = copy_marking(marking)
    for arc in trans.in_arcs:
        p = arc.source
        w = arc.weight
        if new_marking.get(p, 0) < w:
            raise ValueError(f"Insufficient tokens in {p.name}")
        new_marking[p] -= w
        if new_marking[p] == 0:
            del new_marking[p]
    for arc in trans.out_arcs:
        p = arc.target
        new_marking[p] = new_marking.get(p, 0) + arc.weight
    return new_marking

def run_sequence(net, initial_marking, sequence, label):
    print(f"--- {label} ---")
    m = copy_marking(initial_marking)
    print(f"Initial marking: {format_marking(m)}")
    for tname in sequence:
        enabled = pm4py.get_enabled_transitions(net, m)
        enabled_names = sorted(t.name for t in enabled)
        print(f"Before {tname}: enabled={enabled_names}; marking={format_marking(m)}")
        if tname not in enabled_names:
            print(f"BLOCKED: {tname} is not enabled.")
            return m
        m = fire_named_transition(net, m, tname)
        print(f"After {tname}: marking={format_marking(m)}")
    final_enabled = pm4py.get_enabled_transitions(net, m)
    print(f"Final marking: {format_marking(m)}")
    print(f"Final enabled transitions: {sorted(t.name for t in final_enabled)}")
    return m

# Workflow-net status

print("Repaired is workflow net:", pm4py.check_is_workflow_net(repaired_net))

The net is structurally a workflow net: it has a unique source, a unique sink, and every node lies on some source-to-sink path. It should **not** be expected to be sound. The principal defect is that `t_join_waived` consumes only `p_waived`; it does not consume or wait for `p_analysis_done`. Consequently, on the waiver route, `t_authorize` can fire while `p_analysis` is still marked, or after `t_analyze` while `p_analysis_done` remains unconsumed. A token may exist in `sink`, but the exact final marking `{sink: 1}` is not reached. Business consequence: waived cases can be authorized without mandatory analysis, or can deadlock with leftover analysis tokens, so the process is non-compliant and cannot reliably close.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `im` | Unique workflow start | Initial token is in `source`; only `t_register` is initially enabled. | None by itself. |
| `t_register`, `p_ready` | Case registration | Produces one token for the split. | None by itself. |
| `t_split` | Parallel split starting analysis and review | Produces one token in `p_analysis` and one token in `p_review`. | Correctly creates parallel branches. |
| Analysis branch: `p_analysis -> t_analyze -> p_analysis_done` | Mandatory analysis | `p_analysis_done` is consumed only by `t_join_normal`. | On the waiver route, either `p_analysis` or `p_analysis_done` can remain unconsumed. |
| Standard review branch: `p_review -> t_standard_review -> p_review_done` | Standard review outcome | Produces `p_review_done`, which synchronizes with analysis at `t_join_normal`. | Works correctly when standard review is selected. |
| Waiver branch: `p_review -> t_waive_review -> p_waived` | Formal waiver outcome | Produces `p_waived`, which feeds only `t_join_waived`. | Waiver outcome is not synchronized with analysis completion. |
| `t_join_normal` | AND-join for analysis + standard review | Consumes `p_analysis_done` and `p_review_done`, then produces `p_decision`. | Enabled only on the standard-review path. |
| `t_join_waived` | Intended waiver synchronization | Consumes only `p_waived` and produces `p_decision`. It is not a two-input join. | Authorization can proceed without analysis completion. |
| `p_decision`, `t_authorize`, `sink` | Authorization and final completion | `t_authorize` consumes whatever token arrives in `p_decision` and puts a token in `sink`. | Can fire too early on waiver path; may leave residual tokens. |
| `sink`, `fm` | Unique workflow end | Final marking is intended to be exactly `{sink: 1}`. | Sink can be marked while other places still contain tokens. |
| Source-to-sink path condition | Workflow-net structural check | Every place/transition lies on at least one path from `source` to `sink`. | The net passes a structural workflow-net check even though its behavior is unsound. |

# 3. Marking-Based Counterexample

**Counterexample 1: waiver route, authorization before analysis**

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source: 1}` | `{t_register}` | Initial marking `im`. |
| 1 | `t_register` | `{p_ready: 1}` | `{t_split}` | Case registered. |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `{t_analyze, t_standard_review, t_waive_review}` | Parallel tokens created: one for analysis, one for review. |
| 3 | `t_waive_review` | `{p_analysis: 1, p_waived: 1}` | `{t_analyze, t_join_waived}` | Waiver selected; `p_review` consumed. Analysis token remains. |
| 4 | `t_join_waived` | `{p_analysis: 1, p_decision: 1}` | `{t_analyze, t_authorize}` | `t_join_waived` did not wait for analysis. `t_authorize` is already enabled. |
| 5 | `t_authorize` | `{p_analysis: 1, sink: 1}` | `{t_analyze}` | A token exists in `sink`, but the exact final marking `fm = {sink: 1}` has **not** been reached because `p_analysis` remains. |
| 6 | `t_analyze` | `{p_analysis_done: 1, sink: 1}` | `` | The leftover analysis token is converted into `p_analysis_done`, but that token cannot be consumed. `t_join_normal` lacks `p_review_done`; `t_join_waived` lacks `p_waived`. Dead end outside the final marking. |

This shows that `t_authorize` can occur **before** `t_analyze` on the waiver route.

**Counterexample 2: waiver route, analysis before authorization**

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source: 1}` | `{t_register}` | Initial marking `im`. |
| 1 | `t_register` | `{p_ready: 1}` | `{t_split}` | Case registered. |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `{t_analyze, t_standard_review, t_waive_review}` | Parallel branches created. |
| 3 | `t_analyze` | `{p_analysis_done: 1, p_review: 1}` | `{t_standard_review, t_waive_review}` | Analysis completed; review choice still open. |
| 4 | `t_waive_review` | `{p_analysis_done: 1, p_waived: 1}` | `{t_join_waived}` | Waiver selected. `t_join_normal` is not enabled because `p_review_done` is absent. |
| 5 | `t_join_waived` | `{p_analysis_done: 1, p_decision: 1}` | `{t_authorize}` | `t_join_waived` consumes only `p_waived`; it leaves `p_analysis_done` behind. |
| 6 | `t_authorize` | `{p_analysis_done: 1, sink: 1}` | `` | Again, a token exists in `sink`, but the exact final marking is not reached. The leftover `p_analysis_done` cannot be consumed. |

This shows that even when `t_analyze` occurs **before** `t_authorize`, the waiver path still cannot reach the exact final marking.

The standard-review path does not exhibit this defect: for example,  
`t_register, t_split, t_analyze, t_standard_review, t_join_normal, t_authorize`  
reaches `{sink: 1}` exactly.

# 4. Minimal-Repair Alternatives

Edit-cost model used below:

- Add or remove one arc: cost `1`.
- Add or remove one place: cost `3`.
- Add or remove one transition: cost `3`.
- Changing only a name or label: cost `0`.
- If a place or transition is removed, removal of each incident arc is counted separately.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| R1: make waiver join wait for analysis completion | Add one arc: `p_analysis_done -> t_join_waived`. In code: `petri_utils.add_arc_from_to(p_analysis_done, join_waived, repaired_net)`. | 1 | Analysis remains mandatory on both standard and waiver paths. Authorization occurs only after analysis and the selected review outcome are complete. Parallel start is preserved; analysis and waiver may complete in either order. | On the waiver path, `t_join_waived` and therefore `t_authorize` are blocked until `t_analyze` has completed. The original premature waiver authorization is removed. | `p_analysis_done` now feeds two silent joins. Correctness still relies on the XOR choice at `p_review`. If future edits allow both review outcomes, the model could become confusing. |
| R2: waiver cancels pending analysis | Add one arc: `p_analysis -> t_waive_review`. In code: `petri_utils.add_arc_from_to(p_analysis, waive_review, repaired_net)`. | 1 | Standard-review path remains unchanged. Waiver remains distinguishable by its visible label. The net becomes sound. | Business policy changes: waiver no longer requires analysis. Waiver consumes the pending analysis token, so analysis cannot occur after waiver. If analysis fires first, waiver becomes impossible. | This violates the original mandatory-analysis rule unless the business explicitly accepts waiver as an analysis exemption. It also introduces a race between `t_analyze` and `t_waive_review`. |

Under this cost model, cost `0` cannot repair the net because the unmodified net is unsound. Both R1 and R2 achieve cost `1`, so they are minimal under the chosen model.

No single arc deletion repairs the defect: deleting an arc from the waiver join deadlocks the waiver path; deleting an analysis arc breaks the standard path; deleting `p_analysis_done -> t_join_normal` breaks standard synchronization; deleting `p_review -> t_waive_review` removes the waiver alternative and leaves dead waiver elements. Adding places or transitions would cost at least `3`, so such repairs are more expensive.

R1 and R2 tie numerically but differ semantically. R1 is the preferred policy-preserving minimal repair because it retains mandatory analysis while allowing parallel completion. R2 is a minimal policy-changing repair: it makes the model sound by allowing waiver to bypass analysis.

import pm4py
from pm4py.objects.petri_net.obj import Marking


def copy_marking(marking):
    copied = Marking()
    for place, weight in marking.items():
        copied[place] = weight
    return copied


def format_marking(marking):
    return {p.name: marking[p] for p in sorted(marking.keys(), key=lambda x: x.name)}


def fire_named_transition(net, marking, transition_name):
    enabled = pm4py.get_enabled_transitions(net, marking)
    enabled_names = {t.name for t in enabled}

    if transition_name not in enabled_names:
        raise ValueError(
            f"Transition {transition_name} is not enabled. "
            f"Enabled transitions: {sorted(enabled_names)}"
        )

    transition = next(t for t in net.transitions if t.name == transition_name)
    new_marking = copy_marking(marking)

    for arc in transition.in_arcs:
        place = arc.source
        weight = arc.weight
        if new_marking.get(place, 0) < weight:
            raise ValueError(f"Insufficient tokens in place {place.name}.")
        new_marking[place] -= weight
        if new_marking[place] == 0:
            del new_marking[place]

    for arc in transition.out_arcs:
        place = arc.target
        new_marking[place] = new_marking.get(place, 0) + arc.weight

    return new_marking


def run_sequence(net, initial_marking, sequence, label):
    print(f"--- {label} ---")
    marking = copy_marking(initial_marking)
    print(f"Initial marking: {format_marking(marking)}")

    for transition_name in sequence:
        enabled = pm4py.get_enabled_transitions(net, marking)
        enabled_names = sorted(t.name for t in enabled)
        print(
            f"Before {transition_name}: "
            f"enabled={enabled_names}; marking={format_marking(marking)}"
        )

        if transition_name not in enabled_names:
            print(f"BLOCKED: {transition_name} is not enabled.")
            return marking

        marking = fire_named_transition(net, marking, transition_name)
        print(f"After {transition_name}: marking={format_marking(marking)}")

    final_enabled = pm4py.get_enabled_transitions(net, marking)
    print(f"Final marking: {format_marking(marking)}")
    print(f"Final enabled transitions: {sorted(t.name for t in final_enabled)}")
    return marking

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of waiver and standard review under R1**  
  The selected repair, R1, preserves distinguishability. Standard review and waiver remain separate visible transitions: `t_standard_review` and `t_waive_review`. They also produce different review-outcome places: `p_review_done` versus `p_waived`. The joins are silent, but the preceding visible review transition still distinguishes the path.

- **Duplicate behavior and silent-transition confusion**  
  R1 does not create duplicate visible behavior for the same business case. A case can take either the standard-review path or the waiver path, not both, because there is only one token in `p_review`. However, `t_join_normal` and `t_join_waived` are silent transitions. If only visible labels are logged, the exact join used may not be explicit. This is not a soundness problem, but it can reduce diagnostic clarity in process mining or conformance checking.

- **Soundness is not proof of business compliance**  
  Soundness only proves structural/behavioral properties such as proper completion and absence of leftover tokens at completion. It does not prove that the model encodes the correct business policy. For example, R2 is sound but changes the policy by allowing waiver to bypass analysis. Even for R1, soundness does not validate whether the waiver was legally justified or whether the analysis was substantively adequate.

- **Positive regression traces**  
  The following transition sequences should be accepted by the repaired model:
  - `t_register, t_split, t_analyze, t_standard_review, t_join_normal, t_authorize`
  - `t_register, t_split, t_standard_review, t_analyze, t_join_normal, t_authorize`
  - `t_register, t_split, t_analyze, t_waive_review, t_join_waived, t_authorize`
  - `t_register, t_split, t_waive_review, t_analyze, t_join_waived, t_authorize`

- **Negative regression traces**  
  The following should be blocked or flagged:
  - `t_register, t_split, t_waive_review, t_join_waived, t_authorize`  
    Missing mandatory analysis.
  - `t_register, t_split, t_standard_review, t_join_normal, t_authorize`  
    Missing mandatory analysis.
  - `t_register, t_authorize`  
    Authorization without any review or analysis.
  - Any attempt to perform both `t_standard_review` and `t_waive_review` in the same case.
  - Any trace where `t_authorize` occurs before both analysis completion and the selected review outcome.

- **Detecting accidental bypass of mandatory analysis**  
  Use conformance checking or alignments between event logs and the repaired model. In particular, query for cases containing `Record Review Waiver` and `Authorize Case` but no `Perform Analysis`. Under R1, such traces should be impossible in the model. In production logs, they should be treated as conformance violations. For model-level assurance, one can also inspect the reachability graph and assert that no marking enables `t_authorize` unless a join requiring `p_analysis_done` has occurred or is enabled.

# 8. Final Recommendation

Deploy **R1**, the one-arc addition `p_analysis_done -> t_join_waived`. It is the best repair because it restores soundness while preserving the original business policy: analysis remains mandatory, the waiver remains a formally recorded alternative to standard review, and authorization occurs only after both the analysis and the selected review outcome are complete. It also preserves the intended parallelism: analysis and the waiver may complete in either order, but the waiver join cannot pass until analysis has finished.

Use **R2** only as a fallback if the business explicitly changes the rule to allow a waiver to cancel analysis. R2 is equally cheap under the edit-cost model, but it is not a policy-preserving fix: waiver consumes the pending analysis token, prevents later analysis, and makes analysis mandatory only for standard review. That creates a compliance risk if the original rule remains binding.

Before deployment, run the diagnostic code, confirm that the repaired net is sound, and add regression tests for both positive interleavings and negative missing-analysis traces. In production, monitor for cases containing `Record Review Waiver` and `Authorize Case` without `Perform Analysis`; under the selected repair, such traces should be impossible in the model and should be treated as conformance violations if observed.
