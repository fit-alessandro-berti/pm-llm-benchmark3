## 1. Model scope and state variables

The appropriate twin is a **calendar-aware stochastic discrete-event simulation** with data-dependent routing, parallel task synchronization, shared resource queues, and explicit cross-case dependence. It should not sample independent historical traces: that would reproduce neither seasonal congestion nor architect bursts, inspection batching, correlated objections, resource-calendar interruptions, or policy-induced changes in routing. The supplied 18-month log, process tree, timing summaries, calendars, and data gaps define the initial calibration envelope. 

### Boundary

The operational boundary should begin slightly before the observed `Submit application` event and end at final resolution:

1. **Application preparation / intention to submit.** This unobserved state is needed because D1 and D7 can add applicant effort, defer submission, or cause abandonment. The observed log begins only at submission.
2. **Municipal permit processing**, from submission through permit or rejection, including missing-document loops, technical reviews, notice, inspection, drafting, legal review, and rework.
3. **Appeal/reconsideration**, when an appeal reopens planning, inspection, drafting, or legal work.
4. **Final terminal state:** permit issued, application finally rejected, withdrawn, or administratively abandoned.

Construction after permit issuance is outside the twin. Emergency decisions removed from the historical log should either be excluded from both calibration and policy comparison or represented as a separately parameterized priority class; they must not silently be treated as ordinary cases.

Two outcome perspectives should be retained:

* **Municipal perspective:** elapsed processing time, queueing, resource use, cost, backlog, and compliance.
* **Applicant/public perspective:** pre-submission effort, response delays, appointments, travel, transparency, and objection handling.

This distinction prevents D1 or D7 from appearing beneficial merely because they move delay outside the observed permit process.

### Entities

| Entity                         | Important attributes and state                                                                                                                                                                                                                                  |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application                    | Case type, district, architect, value, fire/environment/public-notice indicators, latent building area, latent sensitive-district status, prior-violation status, submission quality, objection propensity, readiness for inspection, applicable policy version |
| Task token                     | Activity, enablement time, queue-entry time, start and completion time, prerequisites, required skill, assigned resource, service requirement, interruption state                                                                                               |
| Architect/applicant            | Architect identifier, burst propensity, submission-quality random effect, outstanding related applications, response-time profile                                                                                                                               |
| Municipal worker/resource pool | Skill set, calendar, capacity, current assignment, location where relevant, remaining workload, utilization and absence state                                                                                                                                   |
| Inspection trip or batch       | District, cases included, planned route, maximum holding time, travel component, no-shows, inspector                                                                                                                                                            |
| Public-notice episode          | Statutory minimum, latent objection state, shared neighborhood shock, outreach status, hearing or council dependency                                                                                                                                            |
| Calendar/policy regime         | Holidays, council weeks, peak months, resource changes, policy activation date, grandfathering rule                                                                                                                                                             |
| Related-case cluster           | Architect-week group, neighborhood or parcel group, district inspection group, shared objection or document-quality effect                                                                                                                                      |

### Case and task state

Each case should retain at least:

* `case_id`, case type, district, architect and application value;
* observed routing flags and indicators showing whether each flag is known, missing, or imputed;
* current process marking or set of enabled tasks;
* applicable reviews and outstanding prerequisites;
* timestamps for submitted, enabled, queued, started, interrupted, resumed and completed;
* cumulative municipal service, applicant delay, calendar delay, queueing, travel and statutory notice time;
* rework counts by stage and previous outcomes;
* age, SLA threshold, remaining slack and aging-priority status;
* inspection readiness, no-show state and batch membership;
* public-notice latent state and shared objection-cluster identifier;
* final outcome and any post-decision appeal state.

Missing values such as `prior_violations`, building area or environmental sensitivity must be represented as **unknown**, not converted to `False`.

### Control-flow semantics

The process tree supplies a single-case structural backbone:

* completeness checking can loop;
* Planning is mandatory;
* Fire and Environmental review are optional parallel branches;
* public notice is optional;
* inspection can loop;
* Decision drafting is a synchronization point;
* Legal check is optional;
* permit and rejection are alternative terminal outcomes.

The executable twin must supplement the tree in several ways:

* Fire, Environmental, Public notice and Legal routes need attribute-based guards.
* `Decision drafting` is enabled only after all applicable reviews, public notice and inspection have completed.
* Planning, Legal and appeal rework are not represented fully in the simplified tree.
* The explicit `Completeness rework` activity in the tree may not be recorded in the log; for example, a repeated `Completeness check` can occur without an intervening event carrying that label.
* Policy changes need versioned routing rules.
* Calendars, resources, batch formation, priorities and cross-case dependencies are outside process-tree semantics.

### Resource pools, queues and calendars

The baseline simulation should contain separate queues and skill pools:

| Pool                    | Baseline representation                                                                                                                                   |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Completeness clerks     | Five workers, Monday–Friday 08:00–16:00; effective completeness capacity four on Mondays while one clerk supports the portal                              |
| General planners        | Six workers able to handle all case types, Monday–Friday 09:00–17:00                                                                                      |
| Simple-only planners    | Two workers limited to Simple renovation, Monday–Friday 09:00–17:00                                                                                       |
| Fire reviewers          | Capacity equivalent to two workers, available Tuesday–Thursday                                                                                            |
| Environmental reviewers | Three workers with explicit non-permit blocks covering approximately 40% of their calendars; preferable to replacing them with a constant fractional pool |
| Schedulers              | A scheduling pool calibrated from resource records; `scheduler_1` in the excerpt is not evidence of a permanent one-person capacity                       |
| Inspectors              | Four field workers Tuesday–Friday, with route-dependent travel and batch assignment                                                                       |
| Legal officers          | Two workers; council-meeting-week blackouts except for separately modeled urgent cases                                                                    |
| Portal/system           | Effectively unconstrained service capacity, but timers and statutory calendars still apply                                                                |

Baseline queue discipline can be FIFO within legally defined priority classes. Interventions then alter the discipline:

* D6 introduces aging priority and reserved planner capacity.
* D3 introduces a district-specific batch queue with a maximum holding time.
* D5 introduces legal pre-check work into the same legal capacity unless additional staffing is explicitly funded.
* D4 adds capacity only in March–May and September–November.

Waiting should emerge from task enablement, queue discipline, calendars and resource competition. It should not be sampled independently from a historical waiting-time distribution except for external actors and explicitly exogenous delays.

### Cross-case dependencies

At least four dependence mechanisms are needed:

1. **Architect burst process.** Large architects generate clustered arrivals rather than independent submissions. A shared architect-level quality effect can also correlate missing-document and rework probabilities.
2. **Neighborhood objection shocks.** Related cases in a neighborhood, parcel group or district-time window can share a latent objection environment. This is not the same as claiming that objections were observed.
3. **Inspection batching.** Cases in the same district can wait for a batch, share travel and influence one another’s inspection time.
4. **Shared queues and calendars.** All cases interact through congestion, skill constraints, absences, council weeks and holidays.

An enriched relational layer should therefore contain links such as:

`application ↔ architect`, `application ↔ neighborhood/parcel`, `application ↔ inspection batch`, and `application ↔ council period`.

The existing flattened log remains useful for PM4Py analysis, but it is not the complete simulation state model.

## 2. Parameter-estimation plan

### Log preparation and process-mining layer

The full event log should first be transformed into an auditable canonical table:

* parse timestamps and establish their lifecycle meaning;
* normalize time zone and daylight-saving transitions;
* remove exact duplicates without removing legitimate repeated activities;
* preserve incomplete and still-open cases for censoring analysis;
* distinguish system, applicant and municipal events;
* forward-fill case attributes only after verifying they are case-constant;
* create data-quality indicators for missing start times, missing routing attributes and reconstructed calendars;
* identify policy or system changes during the 18-month period.

PM4Py should be used for formatting, variants, DFGs, performance DFGs, process-tree parsing, conformance diagnostics and synthetic-log comparison. Its current API includes `format_dataframe`, `parse_process_tree`, `get_variants`, `discover_dfg`, `discover_performance_dfg`, `get_case_arrival_average` and `insert_case_service_waiting_time`. ([GitHub][1])

The PM4Py layer should not serve as the simulation engine. In particular:

* a performance DFG based only on completion timestamps measures elapsed time between recorded completions, not pure queueing or service;
* a process tree cannot encode resource calendars, attribute guards, correlated arrivals, batch formation or policy effect sizes;
* one general business-hours calendar is insufficient for the different clerk, fire, inspector, environmental and legal calendars.

### Arrival process

Use the first `Submit application` event per case. Construct a daily count series including zero-arrival days.

A suitable baseline is an overdispersed non-homogeneous count model:

[
N_d \sim \text{NegBin}(\mu_d,\phi)
]

with

[
\log \mu_d =
\beta_0+
f_{\text{trend}}(d)+
\beta_{\text{month/season}}+
\beta_{\text{weekday}}+
\beta_{\text{holiday}}+
\beta_{\text{season}\times\text{weekday}}.
]

The fitted process must reproduce, within uncertainty:

* the 1.7× March–May and September–November effect relative to January–February;
* the 2.2× Monday-versus-Wednesday pattern;
* observed annual or monthly trend;
* overdispersion and serial clustering.

Case type, district and architect should be sampled conditionally rather than from independent marginal proportions. For example:

[
P(\text{type},\text{district}\mid
\text{month},\text{weekday},\text{architect class}).
]

For the top architects, add a Poisson-cluster, hurdle-negative-binomial or self-exciting component:

1. generate an architect submission episode;
2. sample the number of applications in the episode;
3. place them within a short window;
4. correlate their district, document quality and project characteristics.

Compare candidate arrival models using blocked predictive likelihood and their ability to reproduce weekly-count variance, autocorrelation, burst-size distribution and maximum weekly load—not only mean interarrival time.

The PM4Py global case-arrival average is useful as a diagnostic but is not an adequate arrival generator for this non-stationary process.

### Service times

For activities with genuine start and completion timestamps:

1. calculate service duration in working and elapsed time;
2. remove calendar-closed intervals only according to that activity’s resource calendar;
3. stratify by activity, case type, district, resource class, rework iteration and policy period;
4. fit empirical-bootstrap, lognormal, gamma or Weibull candidates;
5. retain worker or team random effects where sample sizes support them.

Model travel separately from inspection service:

[
T_{\text{inspection task}}
==========================

T_{\text{travel}}
+
T_{\text{on-site}}
+
T_{\text{administrative}}.
]

Travel can depend on district, previous location, route size and batching. D3 and D4 must affect the appropriate components rather than multiplying total inspection duration indiscriminately.

When only the supplied median and p90 are available, a lognormal approximation can be used as a temporary prior:

[
\mu=\log(\text{median}),\qquad
\sigma=
\frac{\log(p90)-\log(\text{median})}{1.2816}.
]

This is a fallback, not a claim that the data are lognormal. The fitted distribution should be replaced or updated with raw durations.

Special cases require structural distributions:

* `Receive missing documents`: external response duration, not municipal service.
* `Public-notice period`: 14-day minimum plus a latent objection-dependent extension.
* System activities: near-deterministic short service, unlimited capacity.
* Legal work: service requirement plus calendar interruption.
* Environmental review: possible mixture for cases needing consultant input.

### Waiting and enablement

Queue waiting should be defined as:

[
W_j =
\text{service_start}_j-
\text{enabled_at}_j.
]

`enabled_at` is determined by process semantics, not simply by the preceding row in timestamp order. Examples:

* Planning, Fire and Environmental reviews become enabled after completeness is accepted.
* Decision drafting becomes enabled at the maximum completion time of all applicable upstream branches.
* Legal check becomes enabled after drafting.
* An inspection rework task becomes enabled after the failed inspection result.
* A reworked review may require renewed applicant input before entering a municipal queue.

With completion-only timestamps, the preceding completion-to-current-completion interval is a **sojourn or transition-gap observation**, not an identifiable service/waiting decomposition. Use three sources to address this:

* the subset with start timestamps;
* HR calendars and workload snapshots;
* model-based multiple imputation constrained by activity p50/p90 summaries and feasible working intervals.

Calibration should compare simulated waiting distributions against the empirical summaries, but the simulator should generate waiting through resources and calendars.

### Routing probabilities

Estimate conditional routing models for:

* missing-document request;
* Fire review;
* Environmental review;
* Public notice;
* Legal check;
* issue versus reject;
* appeal and each rework route.

Candidate predictors include case type, district, architect, value, observed requirement flags, calendar period and previous rework. Use hierarchical logistic models or regularized tree models, with calibration checks by case type and district.

Known positive rules override statistical estimates:

* `requires_fire=yes` implies Fire review;
* `requires_environment=yes` implies Environmental review;
* Complex variance implies Public notice.

Unknown building-area thresholds, environmentally sensitive districts and prior violations should be represented through external enrichment or latent variables. They must not be inferred as negative solely because the attribute is absent.

The process tree is a normative structural constraint, while empirical routing estimates determine optional branch probabilities and deviations.

### Rework

Derive observable rework indicators from repeated activities and recurrent segments, then distinguish:

* completeness-document loops;
* Planning rework;
* inspection rework;
* Legal rework;
* post-decision appeal.

Estimate:

[
P(\text{rework at stage }s
\mid \text{case attributes, prior loops, resource and season})
]

and a conditional distribution for the number of iterations. A hurdle model is preferable to one geometric probability when many cases have no rework but a small subset has repeated loops.

Rework service time should depend on iteration and reason class. If the reason text cannot be coded reliably, use coarse latent classes and wide uncertainty rather than a precise-looking classifier.

### Resource calendars and capacity

Use the reconstructed HR calendars as initial priors, then compare them with the temporal pattern of observed starts and completions.

Estimate or validate:

* effective attendance and absence;
* part-time or non-permit blocks;
* activity-resource eligibility;
* meeting and training interruptions;
* holiday and council-week rules;
* overtime or work occurring outside the nominal calendar;
* daily productivity variation.

Environmental reviewers should be modeled as three workers with blocked calendar periods where possible. A constant capacity of 1.8 FTE would match the average but understate periods when all three are available or simultaneously occupied elsewhere.

For legal officers, council-week restrictions must be supplied as actual date ranges. Emergency exceptions cannot be estimated from a log from which emergency cases were removed.

### Applicant and third-party response

Estimate applicant-response time from `Request missing documents` to `Receive missing documents`, accounting for right censoring. Candidate models include:

* short-response and long-response mixtures;
* lognormal or Weibull survival models;
* architect-level random effects;
* case-type and number-of-request effects;
* probability of no response or abandonment.

Inspection readiness, no-shows, consultant-report delays and appeal filing are also external clocks. They should not consume municipal resources while waiting, though subsequent rescheduling and communication do.

### Public-notice and objection process

Do not label long public-notice durations as observed objections. Use a latent mixture:

[
T_{\text{notice}}
=================

14\text{ days}
+
I_{\text{latent objection}},
T_{\text{extension}}
+
T_{\text{calendar delay}}.
]

Possible parameterizations should be compared because objection prevalence and extension length are not separately identifiable from duration alone. External objection registers, hearing records or complaint systems would materially improve identification.

Add a shared district/neighborhood-period random effect to allow several related cases to experience a common objection shock.

D9 effect estimates cannot be learned from the baseline log alone. They require expert priors, a pilot, or evidence from a comparable program.

### Inspection batching and related cases

Identify candidate historical batches by:

* same inspector;
* same date or route window;
* same district;
* short time between consecutive inspections.

Estimate:

* batch-size distribution;
* additional holding time before route formation;
* per-case travel reduction by batch size and district;
* no-show and route-disruption probability.

Related-case effects should be estimated with comparisons that control for seasonal load and district. Otherwise a low travel time among batched cases may be confounded by easier districts or deliberate low-load scheduling.

### Policy-effect parameters

The baseline log identifies process behavior, not the causal effects of policies that have not yet been implemented. Each candidate intervention therefore needs uncertain effect parameters:

* D1: reduction in missing-document odds, applicant effort and possible abandonment.
* D2: eligible share, prior-violation data coverage, audit rate and false low-risk classification.
* D3: travel reduction, maximum batch holding time and batch disruption.
* D4: temporary worker productivity and onboarding loss.
* D5: early legal work, avoided late rework and duplicated work.
* D6: aging threshold, reserved hours and release-to-normal-queue rule.
* D7: appointment adherence and displacement of submissions by weekday.
* D8: triage accuracy, review-time reduction and rework from false negatives.
* D9: warning accuracy, outreach workload and reduction in objection extension.

Represent these as distributions or low/base/high scenarios, not fixed known effects.

## 3. Assumptions

| Category                           | Baseline assumption                                                                                                                                                                  | Required uncertainty treatment                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Arrivals**                       | Submissions follow a non-homogeneous, overdispersed daily process. Case attributes are conditional on season and architect class. Major architects generate clustered episodes.      | Compare negative-binomial, cluster and self-exciting alternatives. Include uncertainty in annual trend, burst size and appointment adherence.                    |
| **Service times**                  | Human service requirements are drawn separately from queue waiting and calendar closure. Distributions vary by activity, case type, district and rework iteration.                   | Use hierarchical partial pooling and empirical/bootstrap alternatives. Completion-only observations do not identify service time.                                |
| **Routing**                        | Observed positive requirement flags are binding. Missing attributes remain unknown. Applicable reviews run in parallel and drafting waits for all required branches.                 | Test conservative, central and permissive imputations for missing area, environmental sensitivity and prior violations.                                          |
| **Resources/calendars**            | Nominal calendars are initially correct, with individual blocked periods for non-permit work where available. Appeals can reopen the case.                              | Use reason-class scenarios because text coding is unreliable. They can be heavy-tailed and censored.                                               | Include slow-response, abandonment, consultant-delay and no-show scenarios. D1 can shift effort before submission.                                               |
| **Cross-case dependencies**        | Architect episodes, neighborhood objections and inspection batches create dependence beyond shared queues.                                                                           | Compare no-dependence, estimated-dependence and strong-dependence scenarios to quantify how much results rely on the enriched model.                             |
| **Non-stationary demand**          | Month, weekday, holiday and trend effects continue unless a stress scenario changes them. Peak-month staffing activates according to calendar month rather than current backlog.     | Test higher peaks, altered Monday concentration, long-term growth and shifted seasonality.                                                                       |
| **Missing data**                   | Missing objection, area, environmental-sensitivity and prior-violation fields are not treated as negative. Emergency cases are outside the main estimand unless separately modeled.  | Use multiple parameter draws or latent-state scenarios. Report results conditional on each missing-data interpretation and the value of obtaining external data. |

Additional operational assumptions should be explicitly versioned:

* D2 applies only when the municipality can affirmatively verify “no prior violations.” Unknown history remains inspection-required.
* D5 uses legal-officer time; parallelization is not free capacity.
* D6 releases reserved planner time to the normal queue after a defined cutoff when no eligible aging case is waiting.
* D7 changes submission timing rather than deleting demand; any abandonment is reported separately.
* D8 may prioritize or fast-track Environmental review but does not waive a legally required review.
* D9 acts through outreach, earlier evidence collection or hearing preparation; it does not retroactively create an observed objection label.
* Cases already in progress when a policy begins follow an explicit grandfathering rule. Both “new submissions only” and “eligible active cases” transitions should be tested.

## 5. Warm-up, replications, and uncertainty treatment

### Simulation modes

Use two complementary modes.

**Historical replay mode**

* Feed the simulator actual arrival timestamps and observed case attributes.
* Initialize from a real snapshot of work in progress.
* Do not use a statistical warm-up.
* Compare synthetic downstream events with the held-out actual events.

This mode is best for calibration and short-term operational validation.

**Long-run policy mode**

* Simulate at least 36 calendar months.
* Use the first 12 months as a provisional warm-up because demand and calendars have an annual cycle.
* Collect primary metrics for months 13–36.
* Admit cases only through the end of month 36, but continue the engine until those cases finish or are administratively censored.
* Attribute results to cases arriving in the measurement window, avoiding artificially favorable end-of-run truncation.

Because Complex variance cases have a p90 near 260 days, verify the 12-month warm-up with Welch plots of backlog, aged WIP and resource utilization. Extend warm-up to 18 months if the initialization effect remains visible.

A separate transition experiment should report the first 30, 90, 180 and 365 days after policy activation. A policy can have good long-run performance but a harmful implementation backlog.

### Initial state

Preferred initialization is an observed cross-sectional snapshot containing:

* every active case;
* completed prerequisites;
* outstanding tasks;
* task ages;
* current queues;
* scheduled inspections;
* public-notice elapsed time;
* resources already busy or absent.

When unavailable, generate an initial state by running the baseline for one or more annual cycles and sampling a snapshot at the same calendar date as policy activation.

### Replications

Start with 30–50 paired replications for screening. Increase sequentially until the relevant confidence-interval half-widths are acceptable, for example:

* overall SLA percentage: at most 1 percentage point;
* case-type SLA percentage: at most 2 percentage points;
* median duration difference: at most 1–2 days;
* p90 duration difference: at most 5% of the baseline p90;
* peak backlog difference: at most 5%.

Tail-heavy scenarios may require 100–300 or more replications. The stopping rule should be declared before inspecting which policy appears best.

### Random numbers

Use common random numbers across policy alternatives:

* the same potential application intentions;
* the same case attributes;
* the same baseline service requirements;
* the same applicant-response draws;
* the same absence and objection shocks.

A policy then changes routing, timing or capacity rather than receiving a more favorable random world.

Use independent named streams for:

* arrivals;
* case attributes and architect bursts;
* routing;
* service requirements;
* applicant/third-party delays;
* objections;
* absences and no-shows.

For strong alignment across policies, generate random values by stable keys such as `(replication, case_id, task_type, iteration)` rather than relying only on sequential generator calls.

Publish the master seeds and software/environment version.

### Confidence and credible intervals

For ordinary stochastic uncertainty:

* use paired replication differences;
* report 95% paired t intervals when approximately symmetric;
* use percentile or BCa bootstrap intervals for medians, p90/p95, fairness gaps and maximum backlog;
* use Wilson or beta-binomial intervals for SLA proportions.

For parameter uncertainty, use a nested design:

1. draw an outer parameter set from bootstrap samples or a Bayesian posterior;
2. run paired policy replications inside that draw;
3. aggregate both within-world randomness and between-parameter uncertainty.

Report separately:

* Monte Carlo uncertainty conditional on calibrated parameters;
* calibration or parameter uncertainty;
* policy-effect uncertainty.

### Heavy-tailed durations

Do not summarize performance only by the mean. Report:

* median;
* p75, p90, p95 and, where stable, p99;
* restricted mean duration up to a declared horizon;
* probability of exceeding case-type SLA thresholds;
* aged-WIP survival curves;
* maximum and peak backlog distributions.

For applicant responses, objections and appeals:

* include right-censored cases;
* compare empirical resampling, mixture and survival-model tails;
* use tail-stress multipliers;
* do not winsorize away operationally real long cases.

Rare extreme outcomes should be shown with wider intervals rather than removed.

### Sensitivity analysis

Use three layers:

* **Local sensitivity:** one-at-a-time changes in calendars, effect sizes, batch windows and routing thresholds.
* **Global sensitivity:** Latin-hypercube or quasi-random parameter samples, followed by variance-based or rank-based importance analysis.
* **Structural sensitivity:** alternative arrival, objection, rework and dependency models.

Particularly important uncertain parameters are:

* D1 effectiveness versus applicant effort;
* D2 unknown-prior-violation share;
* D3 batch holding versus travel savings;
* temporary-inspector productivity;
* legal pre-check duplication;
* objection prevalence and correlation;
* architect burst intensity;
* separation of service and waiting when starts are missing.

---

## 6. Validation strategy

### Face validation

Run structured walkthroughs with clerks, planners, reviewers, inspectors, legal officers, applicants and policy staff.

Use case animations and queue snapshots to check:

* when tasks become enabled;
* which resource can perform them;
* how work crosses holidays and council weeks;
* how an inspection batch is formed and released;
* what happens after missing documents, failed inspections and appeals;
* whether D5 genuinely consumes legal capacity;
* whether D6 priority behavior matches the proposed operating rule.

Ask reviewers to identify impossible simulated cases rather than merely saying whether aggregate results “look reasonable.”

### Event-log replay validation

Use actual arrivals and case attributes for a historical period, while simulating service, queues and routing.

Compare:

* generated activity sequences;
* variant frequencies;
* completion dates;
* number and timing of rework loops;
* queue entry and service-start times where observed;
* final outcomes;
* active WIP at monthly snapshots.

Export the simulated history in the same event-log schema and run the same PM4Py analyses on real and simulated logs. The comparison must use equivalent timestamp semantics; if the historical log records only completion events, also compare a completion-only projection of the synthetic log.

### Distributional validation

Validation targets should include more than overall throughput.

| Target                               | Suggested provisional acceptance band                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Monthly arrival counts               | Mean and seasonal profile within sampling uncertainty; typical monthly error below about 5–10%             |
| Monday/Wednesday submission ratio    | Historical estimate inside the simulated 95% interval                                                      |
| Case mix                             | Each main case type within about 1–2 percentage points                                                     |
| Major variant shares                 | Within about 2 percentage points, with rare variants assessed collectively and individually where possible |
| Median case duration by variant/type | Within about 5–10%                                                                                         |
| p90 duration by variant/type         | Within about 10–15%, recognizing wider uncertainty for rare variants                                       |
| Applicant-response duration          | Median, p90 and censoring rate reproduced                                                                  |
| Public-notice duration               | Point mass near the minimum and long-tail shape reproduced without claiming observed objections            |
| Weekly completions                   | Mean, variance, seasonality and autocorrelation reproduced                                                 |
| Rework counts                        | Zero-loop share and repeated-loop tail reproduced                                                          |
| District inspection duration         | D3/D5 ordering and travel-tail differences reproduced                                                      |

These are starting tolerances, not universal standards. Tight tolerances on one aggregate should not compensate for a visibly wrong queue or tail.

### Resource-utilization validation

For each pool, compare:

* busy hours by day and week;
* fraction of available calendar used;
* number of tasks started and completed;
* queue length and oldest-task age;
* work outside nominal calendars;
* resource-task eligibility;
* geographic inspection routes;
* council-week legal output.

A model that matches case duration only by assigning unrealistic utilization or idle time is invalid.

### Bottleneck validation

Validate dynamic bottlenecks rather than assuming a single fixed bottleneck.

Perturb one capacity at a time by approximately ±10–20% and inspect:

* throughput response;
* queue migration;
* p90 changes;
* utilization of downstream resources;
* accumulation of synchronized tasks before Decision drafting.

Expected qualitative responses include:

* more inspector capacity should initially reduce inspection waiting but may expose drafting or legal constraints;
* faster Environmental review may increase synchronized arrivals at drafting;
* D2 may reduce the value of D4;
* D5 can move legal work earlier without increasing legal throughput;
* D6 may reduce aging tails while increasing ordinary planner waits.

Counterintuitive results should be investigated, not automatically rejected, but they require trace-level explanations.

### Cross-case validation

Validate dependence explicitly:

* distribution of applications per architect-week;
* top-20 architect share;
* within-architect correlation of missing documents and rework;
* same-district inspection batch sizes;
* travel reduction by batch size;
* clustering of long public-notice episodes by district or neighborhood period;
* variance of weekly workload relative to an independent-case counterfactual.

Run an intentionally independent-case model as a diagnostic. If it gives similar results under all stresses, either the dependencies are genuinely weak or the enriched model has not been implemented effectively.

### Out-of-sample validation

Use blocked, rolling-origin validation rather than random event splitting.

For example:

1. fit on an initial 9–12 months;
2. validate the following 3–6 months;
3. roll the window forward;
4. ensure that both peak and non-peak periods appear in validation folds.

Assess forecasts of arrivals, backlog, durations, routing, rework and resource usage. Keep an untouched final period for model-selection confirmation.

New interventions cannot be directly validated from a baseline log. Before municipality-wide adoption, conduct a limited pilot or phased rollout and compare observed effects with the simulation’s predictive interval.

---

## 7. Decision criteria

The municipality should select from a **robust Pareto set**, not declare one mathematically optimal policy from an unvalidated simulator.

Because statutory or managerial SLA values were not provided, evaluate the real municipality-approved thresholds when available. For early analysis, a sensitivity grid could use:

* Simple renovation: 20, 30 and 45 elapsed days;
* New residential: 60, 90 and 120 days;
* Commercial: 90, 120 and 150 days;
* Complex variance: 180, 240 and 300 days.

These are scenario cut points, not asserted legal deadlines.

### Metrics and provisional guardrails

| Dimension                   | Required statistic                                                                             | Provisional decision rule                                                                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Central duration            | Median by case type and variant                                                                | Prefer at least 5% or 2–3 days improvement where targeted; do not accept material deterioration in untargeted types                                            |
| Tail duration               | p90 and p95 by case type, district and major variant                                           | Prefer at least 10% tail reduction; no major group should worsen by more than 5% or approximately three days without an explicit trade-off decision            |
| SLA compliance              | Percentage within every tested SLA by case type                                                | Prefer at least a 3-point improvement in targeted groups; no case type should fall by more than 1 point                                                        |
| Fairness across districts   | Risk-adjusted SLA and p90 gaps, especially D3/D5 versus others                                 | Do not increase the maximum district SLA gap by more than 2 points; preferably reduce it by at least 20%                                                       |
| Fairness across architects  | Results for top-20, other repeat and occasional architects, adjusted for case mix              | No group loses more than 2 SLA points because of appointment or prioritization rules; report pre-submission delay as well                                      |
| Resource utilization        | Available-time utilization by pool and peak four-week average                                  | Sustainable central range approximately 65–85%; investigate pools above 90% for prolonged periods or above 95% for two consecutive weeks                       |
| Rework                      | Cases with any loop, loops per case and rework workload                                        | D1 should materially reduce missing-document loops; no policy should increase another rework category by more than about 1–2 points without offsetting benefit |
| Backlog                     | Total WIP, aged WIP, peak backlog and end-of-year backlog                                      | No upward trend under baseline demand; prefer at least 10% lower peak or aged backlog                                                                          |
| Recovery                    | Time to return within 10% of normal backlog after stress                                       | Prefer recovery within one seasonal quarter; reject policies that leave persistent carryover into the next peak                                                |
| Applicant burden            | Pre-submission delay, response effort, appointment waiting and number of contacts              | Municipal improvement must not be achieved mainly by moving an equivalent or larger delay to applicants                                                        |
| Inspection quality          | Audited error, missed-risk rate and later enforcement/rework                                   | D2 must satisfy a legally approved risk ceiling; unknown prior violations remain ineligible                                                                    |
| Environmental/legal quality | Late escalation, duplicated work and overturned decisions                                      | D5/D8 must not increase late conflict or incorrect routing beyond agreed guardrails                                                                            |
| Public participation        | Notice duration, objection resolution and false-positive outreach                              | D9 must preserve procedural rights; faster duration alone is not sufficient                                                                                    |
| Cost                        | Staff cost, temporary capacity, travel, system cost and cost per additional SLA-compliant case | Compare incremental cost-effectiveness and budget feasibility                                                                                                  |
| Robustness                  | Probability of improvement over parameter draws and stress scenarios                           | Prefer policies beneficial in at least 80–90% of plausible parameter draws and non-harmful in all core stresses                                                |
| Evidence strength           | Validation and policy-effect uncertainty                                                       | Do not deploy a high-impact rule solely because its point estimate is favorable when its interval includes substantial harm                                    |

### Selection procedure

1. **Apply legal, safety and procedural guardrails first.** D2, D8 and D9 may not trade required controls for speed.
2. **Remove dominated policies.** A policy is dominated if another is no worse on duration, SLA, fairness, resource use, applicant burden and cost, and is better on at least one.
3. **Assess robust dominance.** Repeat the comparison across parameter draws and S1–S6.
4. **Publish trade-offs.** If a weighted score is used, disclose weights and show how rankings change under alternative weights.
5. **Prefer reversible pilots when uncertainty is high.** D3, D4, D6 and D7 are easier to pilot than an irreversible no-inspection rule.
6. **Monitor post-deployment drift.** Re-estimate arrivals, service, routing, applicant behavior and policy effects regularly, particularly after a new regulation or portal change.

A credible conclusion is therefore of the form: “D3+D4 is on the robust Pareto frontier under the tested assumptions and merits a pilot,” not “D3+D4 is exactly optimal.”

def load_raw_log(
    csv_path: Optional[str | Path] = None,
    source_timezone: Optional[str] = None,
) -> pd.DataFrame:
    """
    Load with pandas, not pm4py.read_csv.

    source_timezone should be supplied in production when timestamps are local.
    Setting ambiguous/nonexistent DST timestamps to 'raise' is intentional:
    timestamp ambiguity should be corrected, not silently guessed.
    """
    if csv_path is None:
        df = pd.read_csv(StringIO(EXCERPT_CSV))
    else:
        df = pd.read_csv(Path(csv_path))

    required = {CASE_ID, ACTIVITY, END_TIME}
    missing = required.difference(df.columns)
    if missing:
        raise ValueError(f"Missing required columns: {sorted(missing)}")

    end_ts = pd.to_datetime(df[END_TIME], errors="raise")
    if source_timezone is not None and end_ts.dt.tz is None:
        end_ts = end_ts.dt.tz_localize(
            source_timezone,
            ambiguous="raise",
            nonexistent="raise",
        ).dt.tz_convert("UTC")
    df[END_TIME] = end_ts

    if START_TIME in df.columns:
        start_ts = pd.to_datetime(df[START_TIME], errors="coerce")
        if source_timezone is not None and start_ts.dt.tz is None:
            start_ts = start_ts.dt.tz_localize(
                source_timezone,
                ambiguous="raise",
                nonexistent="raise",
            ).dt.tz_convert("UTC")
        df[START_TIME] = start_ts

    yes_no = {
        "yes": True,
        "no": False,
        "true": True,
        "false": False,
        True: True,
        False: False,
    }
    for column in BOOLEAN_COLUMNS:
        if column in df.columns:
            # Unmapped/missing values remain unknown rather than becoming False.
            df[column] = df[column].map(yes_no).astype("boolean")

    return df.sort_values([CASE_ID, END_TIME], kind="stable").reset_index(drop=True)


def format_for_pm4py(df: pd.DataFrame) -> pd.DataFrame:
    kwargs: dict[str, Any] = {
        "case_id": CASE_ID,
        "activity_key": ACTIVITY,
        "timestamp_key": END_TIME,
    }

    # Only advertise a start timestamp to PM4Py when it is actually complete.
    if START_TIME in df.columns and df[START_TIME].notna().all():
        kwargs["start_timestamp_key"] = START_TIME

    return pm4py.format_dataframe(df.copy(), **kwargs)


@dataclass
class PM4PyDiagnostics:
    variants: Mapping[tuple[str, ...], Any]
    frequency_dfg: Mapping[tuple[str, str], Any]
    performance_dfg: Mapping[tuple[str, str], Any]
    start_activities: Mapping[str, int]
    end_activities: Mapping[str, int]
    case_arrival_average_seconds: float
    rework_cases_per_activity: Mapping[str, int]


def compute_pm4py_diagnostics(log_df: pd.DataFrame) -> PM4PyDiagnostics:
    variants = pm4py.get_variants(
        log_df,
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        case_id_key=CASE_ID,
    )

    frequency_dfg, starts, ends = pm4py.discover_dfg(
        log_df,
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        case_id_key=CASE_ID,
    )

    # With completion-only timestamps, this is elapsed time between recorded
    # completions. It must not be interpreted as pure service time.
    performance_dfg, _, _ = pm4py.discover_performance_dfg(
        log_df,
        business_hours=False,
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        case_id_key=CASE_ID,
    )

    arrival_average = pm4py.get_case_arrival_average(
        log_df,
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        case_id_key=CASE_ID,
    )

    rework = pm4py.get_rework_cases_per_activity(
        log_df,
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        case_id_key=CASE_ID,
    )

    return PM4PyDiagnostics(
        variants=variants,
        frequency_dfg=frequency_dfg,
        performance_dfg=performance_dfg,
        start_activities=starts,
        end_activities=ends,
        case_arrival_average_seconds=float(arrival_average),
        rework_cases_per_activity=rework,
    )


@dataclass
class TimingDiagnostics:
    event_dataframe: pd.DataFrame
    case_timing_dataframe: Optional[pd.DataFrame]
    median_service_by_activity_seconds: Mapping[str, float]
    has_complete_start_timestamps: bool


def add_timing_columns(log_df: pd.DataFrame) -> TimingDiagnostics:
    """
    Add defensible timing columns.

    Completion gaps are always observable, but they are not queue waits.
    Service/waiting/sojourn columns are computed only when every event has a
    valid start timestamp.
    """
    out = log_df.sort_values([CASE_ID, END_TIME], kind="stable").copy()
    out["@observed_completion_gap_seconds"] = (
        out.groupby(CASE_ID, sort=False)[END_TIME]
        .diff()
        .dt.total_seconds()
    )

    has_starts = (
        START_TIME in out.columns
        and len(out) > 0
        and out[START_TIME].notna().all()
    )

    if not has_starts:
        out["@event_service_time_seconds"] = np.nan
        out["@@case_service_time_seconds"] = np.nan
        out["@@case_waiting_time_seconds"] = np.nan
        out["@@case_sojourn_time_seconds"] = np.nan
        return TimingDiagnostics(
            event_dataframe=out,
            case_timing_dataframe=None,
            median_service_by_activity_seconds={},
            has_complete_start_timestamps=False,
        )

    out["@event_service_time_seconds"] = (
        out[END_TIME] - out[START_TIME]
    ).dt.total_seconds()

    if (out["@event_service_time_seconds"] < 0).any():
        raise ValueError("At least one completion precedes its start timestamp.")

    case_timing = pm4py.insert_case_service_waiting_time(
        out,
        service_time_column="@@case_service_time_seconds",
        waiting_time_column="@@case_waiting_time_seconds",
        sojourn_time_column="@@case_sojourn_time_seconds",
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        start_timestamp_key=START_TIME,
        case_id_key=CASE_ID,
    )

    median_service = pm4py.get_service_time(
        out,
        aggregation_measure="median",
        activity_key=ACTIVITY,
        timestamp_key=END_TIME,
        start_timestamp_key=START_TIME,
        case_id_key=CASE_ID,
    )

    return TimingDiagnostics(
        event_dataframe=out,
        case_timing_dataframe=case_timing,
        median_service_by_activity_seconds=median_service,
        has_complete_start_timestamps=True,
    )


def parse_reference_process_tree():
    """
    Parse the structural baseline.

    Limitations:
    - no data-dependent guards;
    - no Planning/Legal/appeal rework;
    - no resources, calendars, priorities or batches;
    - no cross-case dependencies;
    - 'Completeness rework' may be unrecorded in the actual log.
    """
    try:
        return pm4py.parse_process_tree(PROCESS_TREE_STRING)
    except Exception as exc:
        raise RuntimeError(
            "The installed PM4Py parser rejected the supplied simplified "
            "process-tree notation. Check parser/version syntax before "
            "manually rebuilding the tree."
        ) from exc


def estimate_daily_arrival_lookup(log_df: pd.DataFrame) -> pd.DataFrame:
    """
    Minimal descriptive estimator.

    Production calibration should replace this lookup with a negative-binomial
    GAM/GLM or cluster-process model and should include architect bursts.
    """
    submissions = (
        log_df.loc[log_df[ACTIVITY].eq("Submit application")]
        .sort_values(END_TIME)
        .drop_duplicates(CASE_ID, keep="first")
        .copy()
    )
    if submissions.empty:
        raise ValueError("No Submit application events found.")

    first_day = submissions[END_TIME].min().floor("D")
    last_day = submissions[END_TIME].max().floor("D")
    all_days = pd.date_range(first_day, last_day, freq="D")

    daily_counts = (
        submissions.set_index(END_TIME)[CASE_ID]
        .resample("D")
        .nunique()
        .reindex(all_days, fill_value=0)
    )

    frame = pd.DataFrame(
        {
            "date": all_days,
            "count": daily_counts.to_numpy(),
            "month": all_days.month,
            "weekday": all_days.weekday,
        }
    )

    lookup = (
        frame.groupby(["month", "weekday"], as_index=False)["count"]
        .agg(mean_count="mean", variance="var", observations="size")
    )
    return lookup

@dataclass(frozen=True)
class CalendarSpec:
    """
    weekday_hours uses Python weekday numbers: Monday=0, Sunday=6.
    """
    weekday_hours: Mapping[int, tuple[time, time]]
    blackout_dates: frozenset[pd.Timestamp] = frozenset()
    availability_fraction: float = 1.0
    capacity_by_weekday: Mapping[int, int] = field(default_factory=dict)


@dataclass(frozen=True)
class ResourcePoolSpec:
    name: str
    capacity: int
    calendar: CalendarSpec
    skills: frozenset[str]


def weekday_hours(start_hour: int, end_hour: int) -> dict[int, tuple[time, time]]:
    return {
        weekday: (time(start_hour, 0), time(end_hour, 0))
        for weekday in range(5)
    }


def build_baseline_resource_pools(
    council_blackout_dates: Iterable[pd.Timestamp] = (),
) -> dict[str, ResourcePoolSpec]:
    clerk_calendar = CalendarSpec(
        weekday_hours=weekday_hours(8, 16),
        # One of five clerks is assigned to portal support on Monday.
        capacity_by_weekday={0: 4, 1: 5, 2: 5, 3: 5, 4: 5},
    )
    planner_calendar = CalendarSpec(
        weekday_hours=weekday_hours(9, 17),
    )
    fire_calendar = CalendarSpec(
        weekday_hours={
            1: (time(8, 0), time(16, 0)),  # Tuesday
            2: (time(8, 0), time(16, 0)),  # Wednesday
            3: (time(8, 0), time(16, 0)),  # Thursday
        },
    )
    environmental_calendar = CalendarSpec(
        weekday_hours=weekday_hours(9, 17),
        availability_fraction=0.60,
    )
    inspector_calendar = CalendarSpec(
        weekday_hours={
            1: (time(8, 0), time(16, 0)),
            2: (time(8, 0), time(16, 0)),
            3: (time(8, 0), time(16, 0)),
            4: (time(8, 0), time(16, 0)),
        },
    )
    legal_calendar = CalendarSpec(
        weekday_hours=weekday_hours(9, 17),
        blackout_dates=frozenset(
            pd.Timestamp(d).normalize() for d in council_blackout_dates
        ),
    )
    always_open = CalendarSpec(
        weekday_hours={
            day: (time(0, 0), time(23, 59, 59))
            for day in range(7)
        },
    )

    return {
        "clerks": ResourcePoolSpec(
            name="clerks",
            capacity=5,
            calendar=clerk_calendar,
            skills=frozenset(
                {"Completeness check", "Request missing documents"}
            ),

        "planners_general": ResourcePoolSpec(
            name="planners_general",
            capacity=6,
            calendar=planner_calendar,
            skills=frozenset(
                {
                    "Planning review",
                    "Decision drafting",
                    "Completeness rework",

@dataclass
class RNGStreams:
    arrivals: np.random.Generator
    attributes: np.random.Generator
    routing: np.random.Generator
    service: np.random.Generator
    external_delays: np.random.Generator
    objections: np.random.Generator
    disruptions: np.random.Generator

    @classmethod
    def from_master_seed(cls, seed: int) -> "RNGStreams":
        children = np.random.SeedSequence(seed).spawn(7)
        generators = [np.random.default_rng(child) for child in children]
        return cls(*generators)


class ArchitectBurstModel(Protocol):
    def generate_clustered_cases(
        self,
        day: pd.Timestamp,
        ordinary_case_count: int,
        rng: np.random.Generator,
    ) -> list[CaseState]:
        ...


class ArrivalGenerator:
    """
    Non-homogeneous arrivals plus a separate architect-cluster component.

    daily_intensity should be a fitted callable, not a global exponential rate.
    """

    def __init__(
        self,
        daily_intensity: Callable[[pd.Timestamp], float],
        burst_model: ArchitectBurstModel,
    ) -> None:
        self.daily_intensity = daily_intensity
        self.burst_model = burst_model

    def generate(
        self,
        start: pd.Timestamp,
        end: pd.Timestamp,
        rng_count: np.random.Generator,
        rng_attributes: np.random.Generator,
        demand_multiplier: float = 1.0,
    ) -> list[CaseState]:
        cases: list[CaseState] = []

        for day in pd.date_range(start.normalize(), end.normalize(), freq="D"):
            rate = max(0.0, self.daily_intensity(day) * demand_multiplier)
            count = int(rng_count.poisson(rate))

            # The burst model assigns architect IDs, correlated attributes,
            # within-day times, and related-case identifiers.
            cases.extend(
                self.burst_model.generate_clustered_cases(
                    day=day,
                    ordinary_case_count=count,
                    rng=rng_attributes,
                )
            )

        return cases


class RoutingModel:
    """
    Combines normative rules, learned conditional probabilities and policy
    guards. Missing attributes remain explicitly unknown.
    """

    def __init__(
        self,
        policy: PolicySpec,
        learned_parameters: Mapping[str, Any],
    ) -> None:
        self.policy = policy
        self.parameters = learned_parameters

    def eligible_for_d2(self, case: CaseState) -> bool:
        return (
            self.policy.simple_no_inspection_rule
            and case.case_type == "Simple renovation"
            and case.application_value < self.policy.no_inspection_value_threshold
            and case.prior_violations is False
        )

    def required_reviews(
        self,
        case: CaseState,
        rng: np.random.Generator,
    ) -> set[str]:
        required = {"Planning review"}

        if case.requires_fire is True:
            required.add("Fire-safety review")
        elif case.requires_fire is None:
            # Placeholder: draw from a calibrated model conditional on case
            # attributes. Do not equate None with False.
            p = float(self.parameters["p_fire_when_flag_missing"](case))
            if rng.random() < p:
                required.add("Fire-safety review")

        if case.requires_environment is True:
            required.add("Environmental review")
        elif case.requires_environment is None:
            p = float(self.parameters["p_environment_when_flag_missing"](case))
            if rng.random() < p:
                required.add("Environmental review")

        if (
            case.case_type == "Complex variance"
            or case.requires_public_notice is True
        ):
            required.add("Public-notice period")
        elif case.requires_public_notice is None:
            p = float(self.parameters["p_notice_when_flag_missing"](case))
            if rng.random() < p:
                required.add("Public-notice period")

        if not self.eligible_for_d2(case):
            required.update({"Inspection scheduling", "Site inspection"})

        return required

    def drafting_is_enabled(
        self,
        case: CaseState,
        applicable_reviews: set[str],
    ) -> bool:
        return applicable_reviews.issubset(case.completed_tasks)


@dataclass
class InspectionBatch:
    district: str
    cases: list[CaseState]
    released_at: pd.Timestamp


class DistrictInspectionBatcher:
    def __init__(self, policy: PolicySpec) -> None:
        self.policy = policy
        self.waiting_by_district: dict[str, list[tuple[pd.Timestamp, CaseState]]] = {}

    def offer(
        self,
        case: CaseState,
        ready_at: pd.Timestamp,
    ) -> Optional[InspectionBatch]:
        if not self.policy.district_batching:
            return InspectionBatch(
                district=case.district,
                cases=[case],
                released_at=ready_at,
            )

        queue = self.waiting_by_district.setdefault(case.district, [])
        queue.append((ready_at, case))

        if len(queue) >= self.policy.minimum_batch_size:
            cases = [item[1] for item in queue]
            self.waiting_by_district[case.district] = []
            return InspectionBatch(
                district=case.district,
                cases=cases,
                released_at=ready_at,
            )

        return None

    def release_expired(
        self,
        now: pd.Timestamp,
        business_day_adder: Callable[[pd.Timestamp, float], pd.Timestamp],
    ) -> list[InspectionBatch]:
        released: list[InspectionBatch] = []

        for district, queue in list(self.waiting_by_district.items()):
            if not queue:
                continue

            oldest_ready = queue[0][0]
            deadline = business_day_adder(
                oldest_ready,
                self.policy.maximum_batch_hold_business_days,
            )
            if now >= deadline:
                released.append(
                    InspectionBatch(
                        district=district,
                        cases=[item[1] for item in queue],
                        released_at=now,
                    )
                )
                self.waiting_by_district[district] = []

        return released

class DigitalTwin:
    """
    Skeleton of a custom discrete-event engine.

    A production implementation may use SimPy or retain this explicit event
    calendar. PM4Py is intentionally not used to allocate resources.
    """

    def __init__(
        self,
        experiment: ExperimentSpec,
        resources: Mapping[str, ResourcePoolSpec],
        arrival_generator: ArrivalGenerator,
        routing_model: RoutingModel,
        calibrated_parameters: Mapping[str, Any],
        streams: RNGStreams,
        start: pd.Timestamp,
        arrival_end: pd.Timestamp,
    ) -> None:
        self.experiment = experiment
        self.resources = dict(resources)
        self.arrival_generator = arrival_generator
        self.routing_model = routing_model
        self.parameters = calibrated_parameters
        self.streams = streams
        self.start = start
        self.arrival_end = arrival_end

        self.event_queue: list[ScheduledEvent] = []
        self._sequence = itertools.count()
        self.cases: dict[str, CaseState] = {}
        self.event_log_rows: list[dict[str, Any]] = []
        self.queue_snapshots: list[dict[str, Any]] = []

        self.inspection_batcher = DistrictInspectionBatcher(
            experiment.policy
        )

    def schedule(
        self,
        timestamp: pd.Timestamp,
        event_type: str,
        payload: Any,
    ) -> None:
        heapq.heappush(
            self.event_queue,
            ScheduledEvent(
                timestamp=timestamp,
                sequence=next(self._sequence),
                event_type=event_type,
                payload=payload,
            ),
        )

    def initialize(self) -> None:
        generated_cases = self.arrival_generator.generate(
            start=self.start,
            end=self.arrival_end,
            rng_count=self.streams.arrivals,
            rng_attributes=self.streams.attributes,
            demand_multiplier=self.experiment.demand_multiplier,
        )

        for case in generated_cases:
            if case.submitted_at is None:
                raise ValueError(
                    f"Generated case {case.case_id} has no submission time."
                )
            self.cases[case.case_id] = case
            self.schedule(case.submitted_at, "CASE_ARRIVAL", case.case_id)

        # A calibrated production model would also schedule:
        # - holidays/council-period starts and ends;
        # - resource absences;
        # - batch-release checks;
        # - a real initial WIP snapshot.

    def run(self) -> dict[str, float]:
        self.initialize()

        while self.event_queue:
            event = heapq.heappop(self.event_queue)

            if event.event_type == "CASE_ARRIVAL":
                self._handle_case_arrival(event)
            elif event.event_type == "TASK_ENABLED":
                self._handle_task_enabled(event)
            elif event.event_type == "TASK_START":
                self._handle_task_start(event)
            elif event.event_type == "TASK_COMPLETE":
                self._handle_task_complete(event)
            elif event.event_type == "APPLICANT_RESPONSE":
                self._handle_applicant_response(event)
            elif event.event_type == "RELEASE_INSPECTION_BATCH":
                self._handle_batch_release(event)
            else:
                raise ValueError(f"Unknown event type: {event.event_type}")

        return self._summarize_metrics()

    def _handle_case_arrival(self, event: ScheduledEvent) -> None:
        """
        Apply D1/D7 pre-submission effects before this point in the arrival
        model. Enqueue Completeness check here.
        """
        case = self.cases[event.payload]
        self.schedule(event.timestamp, "TASK_ENABLED", (case.case_id, "Completeness check"))

    def _handle_task_enabled(self, event: ScheduledEvent) -> None:
        """
        Production logic:
        - set enabled_at;
        - choose eligible queue/resource pool;
        - apply FIFO, aging or batch policy;
        - find next calendar-open capacity;
        - schedule TASK_START.
        """
        raise NotImplementedError("Implement queue and calendar allocation.")

    def _handle_task_start(self, event: ScheduledEvent) -> None:
        """
        Draw service requirement from a stable case/task keyed random stream,
        apply interruptions and travel, then schedule TASK_COMPLETE.
        """
        raise NotImplementedError("Implement service and interruption logic.")

    def _handle_task_complete(self, event: ScheduledEvent) -> None:
        """
        Update the process marking. Enable parallel branches, synchronize
        Decision drafting, sample stage-specific rework and handle terminal
        outcomes or appeal.
        """
        raise NotImplementedError("Implement routing and synchronization.")

    def _handle_applicant_response(self, event: ScheduledEvent) -> None:
        raise NotImplementedError("Implement external response completion.")

    def _handle_batch_release(self, event: ScheduledEvent) -> None:
        raise NotImplementedError("Implement route and inspector allocation.")

    def _summarize_metrics(self) -> dict[str, float]:
        """
        Production output should include case-level records, resource histories,
        queue snapshots and a synthetic event log. This placeholder shows the
        expected experiment-runner interface.
        """
        completed = [
            case for case in self.cases.values()
            if case.terminal_outcome is not None
        ]
        return {
            "submitted_cases": float(len(self.cases)),
            "completed_cases": float(len(completed)),
            # Add p50/p90/p95, SLA, backlog, fairness, utilization, rework,
            # applicant effort, travel, cost and quality metrics.
        }


def run_experiments(
    experiments: Sequence[ExperimentSpec],
    engine_factory: Callable[
        [ExperimentSpec, RNGStreams], DigitalTwin
    ],
    replication_seeds: Sequence[int],
) -> pd.DataFrame:
    """
    Uses the same replication seed for every experiment, implementing common
    random numbers at the stream level.

    A stronger implementation should use keyed draws by case/task so policy-
    induced changes in the number of random calls do not break alignment.
    """
    rows: list[dict[str, Any]] = []

    for replication, seed in enumerate(replication_seeds):
        for experiment in experiments:
            streams = RNGStreams.from_master_seed(seed)
            engine = engine_factory(experiment, streams)
            metrics = engine.run()

            rows.append(
                {
                    "experiment": experiment.name,
                    "replication": replication,
                    "seed": seed,
                    **metrics,
                }
            )

    return pd.DataFrame(rows)

The most important implementation separation is:

* **PM4Py layer:** canonical event log, variants, DFGs, performance diagnostics, conformance, process-tree handling and comparison of real versus synthetic logs.
* **Simulation layer:** non-stationary arrivals, resource allocation, task enablement, calendars, service requirements, external delays, rework, policy guards, batching and cross-case dependence.
* **Experiment layer:** common random numbers, parameter draws, replications, stresses, confidence intervals and decision metrics.

That separation makes it possible to update the calibrated process-mining evidence without entangling it with intervention logic, while still producing synthetic event logs that can be audited through the same PM4Py pipeline.
