## 2. Process-model consistency checks

The suite below runs as a blocking gate in the feature-engineering and explanation pipelines. Each check is stated with its role and its limits.

**A. Prefix-time availability (as-of correctness).**
For every case, materialise the prefix `σ≤t0` and require every feature to be a pure function of it plus context data with `valid_from ≤ t0 < valid_to`. Implementation: each feature declares a lineage contract (source table, timestamp column, aggregation window); a static analyser rejects any window whose upper bound is not bounded by t0, and any join to a table lacking bitemporal columns. A dynamic *shadow recomputation* re-derives features from the prefix and diffs against the stored values; any non-zero diff is a leak. `<= extraction_date` predicates and nightly-snapshot joins are caught here.
*Limit:* it verifies the declared lineage, not the semantics of an undeclared upstream mutation; it needs the SCD history to exist in the first place.

**B. Activity-order feasibility (conformance).**
Encode the normative model as a Petri net / process tree and run alignment-based conformance on complete traces. Alignments give a cost-minimal repair (moves on log/model) and localise exactly *where* a trace deviates, which distinguishes a genuine deviation from a recording artifact. Footprint (directly/eventually-follows matrix) comparison between log and model gives a cheap first screen: `Claim Closed → Damage Assessment Completed` shows up as a footprint violation immediately. Declarative constraints (Declare) express the rules that matter here compactly: `precedence(Settlement Decision Recorded, Appeal)`, `response(Appeal, Settlement Decision Recorded)`, `precedence(Damage Assessment Completed, Settlement Decision Recorded)`, `end(Claim Closed)`, `not-succession(Claim Closed, *)`.
*Limits:* alignment cost is sensitive to move-cost configuration; a mined DFG is descriptive, so a frequent edge is evidence of what the log records, not of what is permitted. `Claim Closed → Damage Assessment Completed` may be frequent in the DFG and is still not a rule. Conversely a rare but legitimate path (appeal reconsideration) must not be pruned as noise. Normativity comes from the documented process and domain sign-off, not from frequency thresholds.

**C. Same-timestamp ambiguity.**
Group events by (case, timestamp). If a group has >1 event and no reliable monotone sequence index, mark the ordering as *unresolved*. For each unresolved group, enumerate the permutations that are model-feasible; if exactly one is feasible, adopt it and record the imputation; if several are, propagate the ambiguity — do not silently accept the ingestion order. Any directly-follows feature spanning an unresolved group is flagged and excluded from explanations. Emit a per-case `ordering_confidence` and a log-level rate of unresolved ties as a data-quality KPI. Case Z is the canonical instance: the feasible reading is `Damage Assessment Completed` before `Claim Closed`, so the "+0.18 pattern" is an artifact and must not appear in any explanation.
*Limit:* feasibility-based repair assumes the normative model is complete; it can mask a real but undocumented behaviour.

**D. Complete-trace information detection.**
Automated tests per feature: (i) *suffix-invariance* — recompute the feature on the prefix and on the full trace; equal values are required. (ii) *truncation sensitivity* — if the value changes when future events are hidden, the feature is complete-trace. (iii) *name/semantic screen* — flag tokens like `total_`, `final_`, `last_`, `_anywhere`, `_current`, `full_trace`, `num_*_total`; every one of the five critical leaks here is caught by this cheap screen. (iv) *label-proximity screen* — flag any single feature with AUC above a threshold on its own, or whose removal collapses performance, for manual lineage review.

**E. Explanation-time modality check.**
Every activity referenced by an explanation is classified against the state of the prefix at t0 into: **already occurred** (`Claim Registered`, `Coverage Check Completed`), **enabled now** (`Damage Assessment Completed` on the fast track, `Documents Requested`, and — subject to a trigger — `Fraud Investigation Opened`), **future-possible but not enabled** (`Documents Received`, `Settlement Decision Recorded`, `Appeal`, `Claim Closed`), and **impossible/ill-formed** (`Claim Closed → Damage Assessment Completed`). This is computed from the marking of the normative net after replaying the prefix. Rule: explanations may cite already-occurred facts as evidence; may cite enabled activities as *risks or options*; must phrase future-possible activities as hypotheses with no observed value; must never cite impossible ones. `Appeal → Settlement Decision Recorded` is future-possible and legitimate in the model — it is banned at t0 for *temporal* reasons only, which is a different verdict from the same-timestamp artifact, and the audit report must record the two differently.

**F. Repeated `Settlement Decision Recorded` legitimacy.**
Because the activity label is coarse, add an occurrence index and check: a second decision is legitimate iff it is preceded by an `Appeal`, which in turn is preceded by a first decision with outcome Partial or Deny. A second decision without an intervening appeal, or after Approve/Withdrawn, is a data defect or an undocumented practice and must be escalated, not auto-repaired. Consequences beyond conformance: label definition (does the 10-day clock stop at the first decision, at closure, or restart on reconsideration?) and any duration feature must state which occurrence they use. Refine the label at the event level (`Settlement Decision Recorded#1` / `#2`) so downstream logic cannot conflate them.

**G. Gate and reporting.** The suite runs on every training build and every scoring batch, and produces a signed feature manifest (feature → lineage contract → check results). Explanations are rendered only for features present in an all-green manifest; a red check invalidates the explanation, not merely annotates it.

## 3. Alternative feature interpretations

**(a) Defensible predictive signal — admissible at t0, stable lineage.**
`initial_damage_complexity`, `elapsed_since_registration_at_t0` (better: remaining working-hours slack to the 10-day target), `claimant_channel`, `initial_reserve` (conditional on as-of validation), `prior_claim_count_before_t0` after the SQL repair, and prefix-derived timing such as registration-to-coverage-check latency.
*May claim:* these are known at t0, are associated with breach in the fitted model, and can legitimately be used for triage and prioritisation. *May not claim:* that changing them changes the outcome, or that they are the reason a case will be late. Complexity in particular is a marker of the work required, not a lever.

**(b) Process-state / congestion signal.**
`queue_length_at_t0`, plus the recommended additions: work-in-progress per team, arrivals in the last 24h, staffed capacity, and backlog age at t0.
*May claim:* the strongest operational mechanism in the whole set — waiting time in a loaded system rises with load, and load is manipulable by staffing and routing, so this class is the most plausibly *actionable*. *May not claim:* a quantified causal effect from SHAP magnitude. Congestion is endogenous (busy periods coincide with claim surges and with the calendar effects below), so a load–delay coefficient from an observational model is not a policy elasticity; validate it with a staged staffing change or a queueing model before promising that "adding N handlers removes M% of breaches."

**(c) Proxy requiring fairness / robustness review.**
`claimant_region`, `claimant_channel`, and any resource/team attribute once repaired to as-of-t0.
*May claim:* predictive association; and, after decomposition, a legitimate operational reading (e.g. repair-network density, local vendor lead times). *May not claim:* that region or the claimant is the cause of delay. These features may encode the organisation's own service disparities, so the model can entrench them: if region predicts breach because a region is under-served, using region to deprioritise cases makes it worse. Required treatment: decompose into mechanism variables and test residual signal; measure error-rate and outcome disparities across region/channel groups; check stability under region resampling and under geographic shift; and, most importantly, constrain the *use* — congestion-driven resourcing is a benign use, claimant-facing adverse treatment is not. Deleting the feature is not automatically the fair choice; it hides the disparity while leaving proxies (postcode, repair vendor, language) in place.

**(d) Drift / calendar proxy.**
`calendar_week`, and by extension any feature entangled with the policy change and the holiday period.
*May claim:* it improves in-sample and near-term fit by absorbing regime shifts. *May not claim:* transportability. A week index has no meaning next year; the model will silently extrapolate a holiday effect onto an ordinary week. Preferred treatment: replace with the mechanism (`working_days_to_target`, `holiday_overlap_days`, `policy_regime_id`), evaluate with time-blocked splits that hold out whole regimes, and treat any residual week effect as a drift alarm rather than a feature.

**(e) Unusable until lineage is repaired.**
`risk_score_current` (needs a timestamped score history; if none was retained, historical rows cannot be reconstructed and the feature must be dropped from the backfill even if it becomes available going forward), `same_day_document_count_snapshot` (needs event-level upload timestamps), `final_handler_team` → `assigned_team_at_t0`, `last_resource_role` → `role_at_t0`, employee experience (needs an SCD join as-of event date), `prior_claim_count_before_t0` (one-line predicate fix, cheapest repair with real value).
*May claim:* nothing at present — these features must not appear in any explanation until the repair and full recomputation of the training set are complete. *May not claim:* that a 65% agreement rate makes `final_handler_team` "mostly fine"; the disagreeing 35% is the informative and leaking part.

**Standards, kept distinct.**
*Predictive validity:* the feature is computable from admissible information and improves out-of-time, out-of-regime generalisation. *Causal interpretation:* additionally requires an identification argument — intervention, natural experiment, or explicit assumptions about confounding — and SHAP never supplies one. *Operational actionability:* additionally requires a lever the organisation controls (staffing, routing, prioritisation, document-request policy) and evidence that pulling it moves the outcome; complexity and region are not levers, queue length and routing are. *Fairness review:* a separate axis applying to features that are individually valid and even actionable, asking who bears the burden of the decisions the model enables, and covering proxies, disparate error rates, feedback loops, and permissible use rather than mere statistical performance.

## 5. Recommendations for explanation validation

**P0 — stop the bleeding (days).**
1. Quarantine the current model and all published explanations. The top four global features and all five sequence patterns are inadmissible, so reported performance and the importance ranking are not evidence of anything; communicate this plainly rather than patching the narrative. Withdraw the Case X/Y/Z scores.
2. Apply the automated leakage screens from §2.D as a hard CI gate: suffix-invariance, truncation sensitivity, the naming screen (`total_`, `final_`, `last_`, `_anywhere`, `_current`, `full_trace`), and single-feature AUC outliers. Nothing ships while a screen is red.
3. Fix the two cheap lineage defects immediately: the `prior_claim_count_before_t0` predicate (`< t0`) and the employee-experience as-of join. Both are one-query changes with real value.

**P1 — feature-store and temporal design (weeks).**
4. Make the feature store bitemporal: every feature row carries `event_time` (when the fact became true) and `ingestion_time` (when the system learned it), and every read is an as-of join at t0 using `ingestion_time`, not `event_time` — a fact that was true but not yet recorded is not usable.
5. Require a machine-checked lineage contract per feature (source, timestamp column, aggregation window, mutability class, prediction points at which it is admissible). Reject any feature whose window upper bound is not bounded by the prediction timestamp, and any join to a table without SCD history.
6. Convert mutable fields (`risk_score`, reserve, team assignment, resource role) into append-only histories going forward. Be explicit that history not retained cannot be reconstructed: some features are permanently unavailable for historical training, and approximating them is itself a leak.
7. Ban nightly/daily snapshot joins for intra-day prediction points; require event-level timestamps or drop the feature.
8. Guarantee training/serving parity by generating both from the same prefix-only recomputation code path, with an automated diff on a sample of live scoring requests.

**P2 — process conformance and label integrity (weeks).**
9. Restore a monotone ingestion sequence index; implement the same-timestamp ambiguity handling of §2.C, and publish the unresolved-tie rate as a data-quality KPI.
10. Run the alignment/footprint/Declare suite of §2.B on every ingest batch; alert on new footprint violations and on conformance-cost drift. Keep the normative model under domain sign-off and version control, and explicitly do not promote frequent DFG edges to rules.
11. Add occurrence indices to `Settlement Decision Recorded`, validate the appeal-precedence rule, and write down the breach-clock definition (first decision vs closure, appeal time in or out) as a versioned artifact that both label generation and duration features reference.
12. Implement the explanation-time modality check of §2.E in the explanation renderer, so an explanation citing an impossible or unobserved-future activity cannot be emitted at all.

**P3 — rebuild, calibrate, re-baseline (weeks).**
13. Retrain on the admissible feature set. Expect a large, honest drop in AUC; report the leakage-free baseline against the trivial base rate and against a simple rules baseline, and decide on that basis whether a t0 model is worth deploying at all.
14. Recalibrate after every feature removal — removing dominant features changes the score distribution, so previously fitted thresholds and any prioritisation policy are invalid. Report reliability diagrams and Brier scores, not only ranking metrics.
15. Consider multiple prediction points instead of forcing everything into t0. Features that are genuine leaks at t0 (document-cycle turnaround, fraud-investigation opening, first decision outcome) are perfectly legitimate at later re-scoring points; a staged re-scoring design recovers most of the discarded signal legitimately.
16. Validate with time-blocked and regime-held-out splits so the policy change and the holiday period are out-of-sample at least once; a random split will flatter the calendar proxies.

**P4 — explanation quality, fairness, monitoring (ongoing).**
17. Measure explanation stability: rerun attribution under bootstrap resamples, seeds, and background-set choices, and report driver-rank agreement. Suppress drivers whose sign or presence is unstable. Prefer attributions computed against a well-defined reference population and document the background choice, since SHAP values are meaningless without it.
18. Enforce a language policy in the explanation templates: associational verbs by default ("is associated with", "is a marker of"), causal or actionable phrasing only for drivers with a registered identification argument. The current interpretation column would fail this policy on all twelve rows.
19. Run proxy and disparity analysis on region, channel, and any resource attribute: group-wise error rates and calibration, region-resampling robustness, and mechanism decomposition. Constrain permitted uses — resourcing and prioritisation yes, claimant-facing adverse treatment no — and check for feedback loops where deprioritising a predicted-breach region makes its service worse and confirms the prediction.
20. Monitor in production for schema drift (new/renamed/repopulated columns, changes to refresh schedules), process drift (new variants, changed footprints, shifting appeal rates), feature-distribution drift, and explanation drift (sudden reordering of top drivers). Any of these triggers a re-run of the full audit suite.
21. Institutionalise the audit: a signed feature manifest per model version, a written statement of what may and may not be claimed for each retained feature, and periodic re-audit — leakage is reintroduced by ordinary upstream maintenance far more often than it is designed in.
