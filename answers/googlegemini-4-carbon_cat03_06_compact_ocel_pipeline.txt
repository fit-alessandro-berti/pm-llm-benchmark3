## 1. Modeling assumptions

### Object types and capitalization
We model six canonical object types using singular `PascalCase` nouns:
- `Order` (`O100`, `O200`)
- `Item` (`I1`, `I2`, `I3`)
- `Package` (`P1`, `P2`)
- `Delivery` (`D1`, `D2`)
- `Invoice` (`V1`)
- `Payment` (`M1`, `M2`)

### E2O qualifier vocabulary
Every event-to-object (`relations`) record carries a role-specific `snake_case` qualifier in `ocel:qualifier` describing *how* the object participates in that event:
- Order lifecycle: `created_order` (`Create Order`), `parent_order` (`Add Item`), `allocating_order` (`Reserve Stock`), `fulfilled_order` (`Pack Package`), `billed_order` (`Issue Invoice`), `closed_order` (`Close Order`).
- Item lifecycle: `added_item` (`Add Item`), `reserved_item` (`Reserve Stock`), `packed_item` (`Pack Package`).
- Logistics lifecycle: `packed_package` (`Pack Package`), `dispatched_package` (`Dispatch Package`), `carrier_delivery` (`Dispatch Package`), `confirmed_delivery` (`Confirm Delivery`).
- Financial lifecycle: `issued_invoice` (`Issue Invoice`), `target_invoice` (`Record Payment`), `recorded_payment` (`Record Payment`).

Monetary amounts (`100.0` for `M1`, `150.0` for `M2`) are modeled strictly as an event-level attribute (`payment_amount`, alongside `currency="MU"`) on `events`, never as separate objects.

### O2O direction conventions
Object-to-object (`o2o`) edges are directed (`ocel:oid` $\rightarrow$ `ocel:oid_2`) from the aggregating, carrying, billing, or settling entity toward its target:
- `Order` $\xrightarrow{\text{contains}}$ `Item` (`O100` $\rightarrow$ `I1`, `I2`; `O200` $\rightarrow$ `I3`)
- `Package` $\xrightarrow{\text{packs}}$ `Item` (`P1` $\rightarrow$ `I1`, `I3`; `P2` $\rightarrow$ `I2`)
- `Delivery` $\xrightarrow{\text{carries}}$ `Package` (`D1` $\rightarrow$ `P1`; `D2` $\rightarrow$ `P2`)
- `Invoice` $\xrightarrow{\text{bills}}$ `Order` (`V1` $\rightarrow$ `O100`, `O200`)
- `Payment` $\xrightarrow{\text{partially\_settles}}$ `Invoice` (`M1` $\rightarrow$ `V1`, reflecting the initial 100-unit installment)
- `Payment` $\xrightarrow{\text{completes\_settlement}}$ `Invoice` (`M2` $\rightarrow$ `V1`, reflecting the second partial payment of 150 units that completes settlement of `V1` prior to order closure)

### Direct source relations vs. downstream logistics and finance
We enforce a **domain-boundary E2O policy** grounded in realistic enterprise source systems (OMS, WMS, TMS, ERP/AR):
1. **Boundary-bridging events link to `Order` (and `Item` where applicable):**
   - `Reserve Stock` (`e06`) allocates `I1` and `I3` directly against `O100` and `O200`.
   - `Pack Package` (`e07`, `e08`) represents WMS packing-slip execution, which links the `Package`, packed `Item`(s), and parent `Order`(s). Because event 7 establishes that `Pack Package` relates to parent Orders (`O100` and `O200`), we apply the same schema rule consistently to event 8 (`P2`, `I2`, and parent `O100`).
   - `Issue Invoice` (`e11`) represents consolidated ERP billing, directly linking `V1` to `O100` and `O200`.
2. **Purely downstream logistics and settlement events do *not* link directly to `Order` or `Item`:**
   - `Dispatch Package` (`e09`, `e10`) links only `Delivery` and `Package` (shipping manifest handoff).
   - `Confirm Delivery` (`e13`, `e14`) links only `Delivery` (carrier proof-of-delivery).
   - `Record Payment` (`e12`, `e15`) links only `Payment` and `Invoice` (Accounts Receivable cash application against `V1`).

### Preventing confusion between source facts and analytical propagation
Base `relations` contain **only** direct transactional observations recorded by the operational system at runtime. Static structural paths (such as tracing `D1` $\rightarrow$ `P1` $\rightarrow$ `I1` $\leftarrow$ `O100` or `M1` $\rightarrow$ `V1` $\rightarrow$ `O100`) reside exclusively in `o2o`. If an analyst needs transitive linkage (e.g., end-to-end Order lead-time analysis covering delivery confirmation or cash collection), propagation must be computed in a separate derived DataFrame or view with an explicit qualifier namespace (such as `derived:via_o2o`), leaving the base OCEL immutable.

### Version-dependent PM4Py assumptions
- **Constructor:** `pm4py >= 2.7.9` supports OCEL 2.0 `o2o` directly via `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`. We isolate instantiation in a small helper so older `2.7.x` builds that lacked the `o2o` keyword argument fall back gracefully by attaching `ocel.o2o = o2o` without changing any DataFrame semantics.
- **Graph discovery helpers:** Standard PM4Py exposes `discover_ocdfg`, `discover_oc_petri_net`, `ocel_flattening`, and `ocel_objects_interactions_summary` at top level, while `pm4py.discover_otg` and `pm4py.discover_etot` are version- or extension-dependent in some distributions. The pipeline invokes `pm4py.discover_otg(ocel)` and `pm4py.discover_etot(ocel)` directly when present and isolates deterministic structural fallbacks if run against a PM4Py build where those two aliases are absent.

def validate_ocel_tables(
    events: pd.DataFrame,
    objects: pd.DataFrame,
    relations: pd.DataFrame,
    o2o: pd.DataFrame,
) -> None:
    """Enforce referential integrity, uniqueness, timezone awareness, and metadata consistency."""
    # Mandatory column checks
    assert {"ocel:eid", "ocel:activity", "ocel:timestamp"}.issubset(events.columns)
    assert {"ocel:oid", "ocel:type"}.issubset(objects.columns)
    assert {
        "ocel:eid", "ocel:activity", "ocel:timestamp", "ocel:oid", "ocel:type", "ocel:qualifier"
    }.issubset(relations.columns)
    assert {"ocel:oid", "ocel:oid_2", "ocel:qualifier"}.issubset(o2o.columns)

    # Timezone-awareness check
    assert isinstance(events["ocel:timestamp"].dtype, pd.DatetimeTZDtype), "events timestamps must be tz-aware"
    assert isinstance(relations["ocel:timestamp"].dtype, pd.DatetimeTZDtype), "relations timestamps must be tz-aware"

    # Unique primary keys
    assert events["ocel:eid"].is_unique, "Duplicate ocel:eid detected in events"
    assert objects["ocel:oid"].is_unique, "Duplicate ocel:oid detected in objects"

    # Referential integrity (no orphan IDs)
    valid_eids = set(events["ocel:eid"])
    valid_oids = set(objects["ocel:oid"])
    assert set(relations["ocel:eid"]).issubset(valid_eids), "Orphan ocel:eid found in relations"
    assert set(relations["ocel:oid"]).issubset(valid_oids), "Orphan ocel:oid found in relations"
    assert set(o2o["ocel:oid"]).issubset(valid_oids), "Orphan source ocel:oid found in o2o"
    assert set(o2o["ocel:oid_2"]).issubset(valid_oids), "Orphan target ocel:oid_2 found in o2o"

    # Activity, timestamp, and object-type consistency between base tables and relations
    merged_ev = relations.merge(
        events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
        on="ocel:eid",
        suffixes=("_rel", "_ev"),
    )
    assert (merged_ev["ocel:activity_rel"] == merged_ev["ocel:activity_ev"]).all(), "Activity mismatch in relations"
    assert (merged_ev["ocel:timestamp_rel"] == merged_ev["ocel:timestamp_ev"]).all(), "Timestamp mismatch in relations"

    merged_obj = relations.merge(objects[["ocel:oid", "ocel:type"]], on="ocel:oid", suffixes=("_rel", "_obj"))
    assert (merged_obj["ocel:type_rel"] == merged_obj["ocel:type_obj"]).all(), "Object type mismatch in relations"

    # Absence of duplicate relation rows
    assert not relations.duplicated(subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]).any(), "Duplicate E2O rows"
    assert not o2o.duplicated(subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"]).any(), "Duplicate O2O rows"


def instantiate_ocel(
    events: pd.DataFrame,
    objects: pd.DataFrame,
    relations: pd.DataFrame,
    o2o: pd.DataFrame,
) -> OCEL:
    """Isolated constructor line for OCEL 2.0 compatibility across PM4Py 2.7.x releases."""
    try:
        return OCEL(events=events, objects=objects, relations=relations, o2o=o2o)
    except TypeError:
        # Adjustment for older PM4Py builds (<2.7.9) without o2o in OCEL.__init__
        ocel_ fallback = OCEL(events=events, objects=objects, relations=relations)
        ocel_fallback.o2o = o2o
        return ocel_fallback


def discover_otg_safe(ocel: OCEL) -> Any:
    """Invoke pm4py.discover_otg with an isolated structural fallback if absent in the installed PM4Py build."""
    if hasattr(pm4py, "discover_otg"):
        return pm4py.discover_otg(ocel)

    # Structural fallback: directed O2O type edges + undirected E2O co-occurrence counts
    obj_types = ocel.objects.set_index("ocel:oid")["ocel:type"].to_dict()
    o2o_type_edges: Dict[Tuple[str, str, str], int] = {}
    if ocel.o2o is not None and not ocel.o2o.empty:
        for _, row in ocel.o2o.iterrows():
            key = (obj_types[row["ocel:oid"]], obj_types[row["ocel:oid_2"]], row["ocel:qualifier"])
            o2o_type_edges[key] = o2o_type_edges.get(key, 0) + 1

    e2o_cooccurrence: Dict[Tuple[str, str], int] = {}
    for _, grp in ocel.relations.groupby("ocel:eid"):
        types = sorted(set(grp["ocel:type"]))
        for i, t1 in enumerate(types):
            for t2 in types[i + 1 :]:
                e2o_cooccurrence[(t1, t2)] = e2o_cooccurrence.get((t1, t2), 0) + 1

    return {"o2o_type_edges": o2o_type_edges, "e2o_type_cooccurrence": e2o_cooccurrence}


def discover_etot_safe(ocel: OCEL) -> Any:
    """Invoke pm4py.discover_etot with an isolated bipartite fallback if absent in the installed PM4Py build."""
    if hasattr(pm4py, "discover_etot"):
        return pm4py.discover_etot(ocel)

    # Bipartite Event-Type (activity) <-> Object-Type cardinality summary
    grouped = (
        ocel.relations.groupby(["ocel:activity", "ocel:type", "ocel:eid"])["ocel:oid"]
        .nunique()
        .reset_index(name="objects_per_event")
    )
    etot_summary = (
        grouped.groupby(["ocel:activity", "ocel:type"])["objects_per_event"]
        .agg(events_touched="count", min_objs="min", max_objs="max")
        .to_dict("index")
    )
    return etot_summary

### High-consequence convergence and divergence events
- **`e06` (`Reserve Stock`) — Order & Item Convergence:** Synchronizes two `Order` instances (`O100`, `O200`) and two `Item` instances (`I1`, `I3`) in one shared warehouse allocation event, while bypassing `I2`.
- **`e07` (`Pack Package` for `P1`) — Cross-Order Fulfillment Convergence:** Binds `P1` to items from distinct orders (`I1` from `O100`, `I3` from `O200`). Coupled with **`e08` (`Pack Package` for `P2`)**, it simultaneously induces **split-order divergence** for `O100`, whose items diverge across `P1` and `P2` (and subsequently `D1` and `D2`).
- **`e11` (`Issue Invoice` for `V1`) — Financial Convergence:** Merges `O100` and `O200` onto a single billing lifecycle (`V1`).
- **`e12` & `e15` (`Record Payment` for `M1`, `M2`) — Installment Convergence / Invoice Divergence:** Two distinct `Payment` lifecycles (`M1`, `M2`) converge sequentially onto the single `Invoice` (`V1`), which from `V1`'s perspective acts as repeated execution (divergence) of `Record Payment`.

## 4. Expected flattened behavior

### `Order` (`O100`, `O200`)
- **Approximate trace shape:** Two cases of lengths 8 and 6:
  - `O100`: `Create Order (e01)` $\rightarrow$ `Add Item (e02)` $\rightarrow$ `Add Item (e03)` $\rightarrow$ `Reserve Stock (e06)` $\rightarrow$ `Pack Package (e07)` $\rightarrow$ `Pack Package (e08)` $\rightarrow$ `Issue Invoice (e11)` $\rightarrow$ `Close Order (e17)`.
  - `O200`: `Create Order (e04)` $\rightarrow$ `Add Item (e05)` $\rightarrow$ `Reserve Stock (e06)` $\rightarrow$ `Pack Package (e07)` $\rightarrow$ `Issue Invoice (e11)` $\rightarrow$ `Close Order (e16)`.
- **Copied shared events:** `e06` (`Reserve Stock`), `e07` (`Pack Package`), and `e11` (`Issue Invoice`) are duplicated into *both* traces (3 real events become 6 log rows).
- **Omitted lifecycle aspects:** Carrier handoff (`Dispatch Package`), physical delivery proof (`Confirm Delivery`), and cash collection (`Record Payment`) disappear completely.
- **Likely DFG edges:** `(Create Order, Add Item): 2`, `(Add Item, Add Item): 1`, `(Add Item, Reserve Stock): 2`, `(Reserve Stock, Pack Package): 2`, `(Pack Package, Pack Package): 1`, `(Pack Package, Issue Invoice): 2`, `(Issue Invoice, Close Order): 2`.
- **Misleading interpretations:**
  1. *False activity counts:* Analysts will think 2 stock reservations, 3 packing operations, and 2 invoices occurred instead of 1, 2, and 1.
  2. *Phantom idle bottleneck:* `Issue Invoice -> Close Order` spans ~23.5 hours with zero intervening events, disguising the real operational wait on overnight delivery `D2` (`e14` at `09:00` Day 2) and final payment `M2` (`e15` at `10:00` Day 2).
  3. *Masked item-level gap:* `O100` appears to pass cleanly through `Reserve Stock`, hiding that `I2` was never included in `e06`.

### `Package` (`P1`, `P2`)
- **Approximate trace shape:** Two uniform 2-event traces:
  - `P1`: `Pack Package (e07)` $\rightarrow$ `Dispatch Package (e09)`.
  - `P2`: `Pack Package (e08)` $\rightarrow$ `Dispatch Package (e10)`.
- **Copied shared events:** None (`P1` and `P2` share no events).
- **Omitted lifecycle aspects:** Upstream order/item intake and stock reservation, downstream `Confirm Delivery`, and all billing/payment steps.
- **Likely DFG edges:** `(Pack Package, Dispatch Package): 2` (with `start={Pack Package: 2}`, `end={Dispatch Package: 2}`).
- **Misleading interpretations:** `P1` and `P2` look structurally identical and independent, concealing that `P1` is a cross-order consolidated parcel (`O100` + `O200`) whereas `P2` is a split shipment of `O100`.

### `Delivery` (`D1`, `D2`)
- **Approximate trace shape:** Two uniform 2-event traces:
  - `D1`: `Dispatch Package (e09)` $\rightarrow$ `Confirm Delivery (e13)` (duration: 3h 00m).
  - `D2`: `Dispatch Package (e10)` $\rightarrow$ `Confirm Delivery (e14)` (duration: 22h 45m).
- **Copied shared events:** None.
- **Omitted lifecycle aspects:** Warehouse packing, item contents, commercial orders, invoicing, payment, and order closure.
- **Likely DFG edges:** `(Dispatch Package, Confirm Delivery): 2`.
- **Misleading interpretations:** While transit-time variance (3h vs. 22.75h) is visible, the flattened view gives no indication that `D1` carries goods for *two* orders (`O100` and `O200`) or why `O200` still could not close at `13:00` on Day 1 when `D1` arrived (because consolidated invoice `V1` remained unpaid until `M2` on Day 2).

### `Invoice` (`V1`)
- **Approximate trace shape:** One 3-event trace:
  - `V1`: `Issue Invoice (e11)` $\rightarrow$ `Record Payment (e12)` $\rightarrow$ `Record Payment (e15)`.
- **Copied shared events:** None across cases (only one `Invoice` exists).
- **Omitted lifecycle aspects:** All commercial ordering, fulfillment, shipping, and `Close Order` completion.
- **Likely DFG edges:** `(Issue Invoice, Record Payment): 1`, `(Record Payment, Record Payment): 1`.
- **Misleading interpretations:** Traditional DFG tooling flags the `(Record Payment, Record Payment)` self-loop as payment rework or duplicate-posting error rather than two distinct `Payment` objects (`M1`, `M2`) settling a consolidated multi-order bill.

### Why flattening on `Payment` is particularly weak
Flattening on `Payment` yields two degenerate single-event traces: `M1 = [Record Payment (e12)]` and `M2 = [Record Payment (e15)]`. Every trace has length 1, so `pm4py.discover_dfg` produces an **empty directly-follows set** (`{}`), `start_activities == end_activities == {'Record Payment': 2}`, and the log skeleton loses all inter-activity constraints. Even the chronological progression from `M1` (`100` MU) to `M2` (`150` MU) disappears because `M1` and `M2` become isolated cases with no shared anchor (`V1`).

## 5. Expected object-centric structures

- **OC-DFG (`pm4py.discover_ocdfg`):** Eliminates flattening distortion by typing every arc by object type and distinguishing *event counts* from *object counts*. Along `Order`, `e06` (`Reserve Stock`), `e07` (`Pack Package` for `P1`), and `e11` (`Issue Invoice` for `V1`) each register an event frequency of `1` while carrying `2` `Order` arcs (`O100`, `O200`). At `Issue Invoice`, `O100` and `O200` synchronize with `V1`'s creation; `V1` then advances along `Invoice`-typed arcs through `Record Payment` (`e12` with `M1`, `e15` with `M2`), while `P1` hands off from `Order`/`Item` packing (`e07`) onto `Package`-typed dispatch (`e09`) and `Delivery`-typed confirmation (`e13`).
- **OTG (`pm4py.discover_otg`):** Reveals the schema-level backbone connecting the six object types. `Order` sits at the commercial hub, coupled via E2O/O2O to `Item` and `Package` on the fulfillment branch (extending to `Delivery`) and to `Invoice` on the financial branch (extending to `Payment`). Crucially, there are *no* direct edges between `{Delivery, Package}` and `{Invoice, Payment}`—showing that physical logistics and financial settlement interact only through `Order`.
- **ET–OT Graph (`pm4py.discover_etot`):** Highlights many-to-many synchronization points via bipartite event-type to object-type cardinalities:
  - Single-type activities (`Create Order`, `Confirm Delivery`, `Close Order`) have degree 1.
  - Handoff activities (`Add Item`, `Dispatch Package`, `Record Payment`) have degree 2 with strictly $1:1$ per-event object multiplicity (e.g., one `Invoice` `V1` paired with one `Payment` `M1` or `M2` per `Record Payment` execution).
  - Multi-instance synchronization activities (`Reserve Stock`, `Pack Package`, `Issue Invoice`) exhibit $1:N$ multiplicity within single events (`e07` touches one `Package` `P1` alongside two `Item`s and two `Order`s `O100`, `O200`; `e11` touches one `Invoice` `V1` alongside `O100` and `O200`).
- **Object-Centric Petri Net (`pm4py.discover_oc_petri_net`):** Models typed places per object type and transitions per activity, using **variable arcs** where a single transition consumes/produces multiple tokens of the same type—specifically `Order` and `Item` on `Reserve Stock` and `Pack Package` (driven by `P1` combining `O100` and `O200`), and `Order` on `Issue Invoice` (driven by `V1` billing `O100` and `O200`)—contrasted with standard single-token arcs for `Package` (`P1`, `P2`), `Delivery` (`D1`, `D2`), `Invoice` (`V1`), and `Payment` (`M1`, `M2`). *Note:* An OCPN discovered from a 17-event log does **not** have a single uniquely determined interpretation; depending on the underlying discovery miner (e.g., Inductive Miner settings on flattened projections and variable-arc inference rules), concurrency vs. loop placement around `Add Item`, `Pack Package`, and `Record Payment`, as well as silent ($\tau$) transitions, may vary while remaining replay-consistent with the log. Furthermore, because `Close Order` (`e16`, `e17`) touches only `Order`, an E2O-discovered OCPN will not automatically enforce a hard guard requiring `D2` confirmation and `M2` payment before `Close Order` unless O2O/state guards are explicitly incorporated.
- **Object-Interactions Summary (`pm4py.ocel_objects_interactions_summary`):** Enumerates concrete instance-level co-attendance across events. It explicitly surfaces that `O100` and `O200` co-interact in `e06`, `e07`, and `e11`; that `P1` bridges `O100`, `O200`, `I1`, and `I3` in `e07` before pairing with `D1` in `e09`; and that `V1` bridges `O100` and `O200` in `e11` before interacting sequentially with `M1` (`e12`) and `M2` (`e15`). Notably, `M1` and `M2` never directly co-occur in the same event—their sibling relationship is mediated through `V1`.

## 6. Modeling alternatives

1. **Policy A — Strictly Source-Minimal (Local-Entity) E2O Relations:**
   - *Rule:* Each event links only to the immediate primary entity of its local microservice: `Reserve Stock` (`e06`) links only to `I1` and `I3` (omitting `O100`, `O200`), and `Pack Package` (`e07`, `e08`) links only to `Package` and `Item` (omitting `Order`).
   - *Discovery impact:* `Order` flattened traces shrink drastically (`Create Order -> Add Item -> Issue Invoice -> Close Order`), making `Order` look purely administrative/financial. In the OC-DFG and OCPN, `Order` no longer has variable arcs on `Reserve Stock` or `Pack Package`; all warehouse convergence (`P1` combining `O100` and `O200`) must be reconstructed indirectly via `Item` flows (`Add Item` $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package`).
2. **Policy B — Extended Operational Handoff Involvement:**
   - *Rule:* Shared physical handoffs retain both container levels: `Confirm Delivery` (`e13`, `e14`) links to both `Delivery` (`D1`/`D2`) and carried `Package` (`P1`/`P2`), and `Close Order` (`e16`, `e17`) verifies and links `Invoice` `V1` alongside `Order`.
   - *Discovery impact:* `Package` traces gain a 3rd step (`Pack Package -> Dispatch Package -> Confirm Delivery`), exposing the 20-hour arrival gap between `P1` and `P2` inside the `Package` DFG. Linking `V1` to `Close Order` introduces a direct synchronizing arc from `Record Payment (M2)` $\xrightarrow{\text{Invoice}}$ `Close Order` in the OC-DFG and OCPN, making financial settlement a visible prerequisite for order closure—at the cost of duplicating `Close Order` onto `V1`'s flattened trace.
3. **Policy C — O2O-Propagated Analytical Relations (Full Transitive Closure):**
   - *Rule:* Propagate upstream `Order` and `Item` references across `o2o` (`contains`, `packs`, `carries`, `bills`, `partially_settles`/`completes_settlement`) onto `Dispatch Package`, `Confirm Delivery`, and `Record Payment`.
   - *Discovery impact:* Flattening on `Order` yields complete end-to-end customer journeys including shipping and payment events. However, **convergence distortion explodes**: `Record Payment` (`e12`, `e15`) and `Dispatch Package`/`Confirm Delivery` for `P1`/`D1` are duplicated across *both* `O100` and `O200`, variable arcs proliferate across nearly every transition in the OCPN, and `Order` appears to actively participate in carrier POD scans and bank-ledger postings where the source systems had no Order context.

## 7. Failure modes

1. **Relation inflation (over-linking E2O):** Attaching every transitively related object to every event turns `ocel_objects_interactions_summary` into a near-complete clique, obscures true system handoffs in the ET–OT graph, and causes OCPN discovery to infer spurious variable arcs everywhere.
2. **Missing direct E2O bridge links:** Omitting `O100` and `O200` from `Issue Invoice` (`e11`) while relying solely on `o2o` (`V1 bills O100/O200`) severs the financial subgraph (`Invoice`, `Payment`) from the commercial/fulfillment subgraph (`Order`, `Item`, `Package`, `Delivery`) in standard E2O-driven OC-DFG and OCPN algorithms.
3. **Treating O2O propagation as empirical observation:** Materializing propagated relations directly into `relations` without distinguishing qualifiers makes it impossible to tell whether the carrier's TMS actually validated `O100` during `Confirm Delivery` or whether an analyst retroactively joined tables—corrupting compliance and audit checks.
4. **Duplicate shared events after flattening (convergence distortion):** Flattening on `Order` duplicates `e06`, `e07`, and `e11`. Summing event counts or costs across flattened cases double-counts warehouse labor and invoice totals.
5. **Ambiguous payment allocation across consolidated orders:** `M1` (`100` MU) and `M2` (`150` MU) settle `V1` (`250` MU total), which bills both `O100` and `O200`. Neither E2O nor O2O specifies how much of `M1` applies to `O100` vs. `O200`. Naively propagating `M1` to both Orders risks falsely concluding that `O200` was paid in full at `11:30` on Day 1 (or over-allocating `250` MU to *each* order).
6. **Overly short `Payment` traces:** Because `M1` and `M2` each participate in only one event (`Record Payment`), single-type projections on `Payment` produce zero DFG arcs and cannot capture installment ordering or partial-vs-final settlement state transitions without `Invoice` context.
7. **Constructor and API version mismatch:** Passing `o2o=o2o` to `OCEL(...)` raises a `TypeError` in older PM4Py 2.x releases predating OCEL 2.0 support, and top-level helper names (`discover_otg`, `discover_etot`) can vary across PM4Py minor versions or wrappers if not isolated behind compatibility adapters.
8. **False total order for same-time events:** Although all 17 timestamps in this dataset are strictly increasing (`08:00` through `10:35` next day), real batch logs frequently emit identical timestamps (e.g., bulk `Add Item` lines or simultaneous `Close Order` jobs). Standard DFG and flattening routines break ties deterministically by row/ID order, inventing sequential edges (`A -> B`) where true concurrency existed.
