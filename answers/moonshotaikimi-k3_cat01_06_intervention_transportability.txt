## 5. Quantitative transport scenarios

**Reasoning that maps evidence to ranges.**
- At A, the structural upper bound of parallelization is min(3.5, 7.2)  **3.5h** (10.7h sequential  7.2h parallel). The observed 9h therefore contains 5.5h from capacity (+11% FTE  +8.3% throughput), mix shift (4840% high-complexity), API, and huddles.
- At B, the analogous bound is min(3.4, 8.1) = **3.4h**, attainable only where both checks are startable at Register: the **38% digital** segment (1,292 cases/6 months).
- For the 62% originals segment, identity already overlaps the 18h receipt wait (DFG: Registerboth; IdentityOriginals 1,020), and Document Check is legally gated — expected gain  0h, at most 1–2h from automatic release-on-receipt.
- The population median case is an originals case (62%), so the **overall median barely moves** even when the digital stratum improves. The p90 (110h) is driven by originals-delay variance and the legal/supplement loop (26.5% of reviews), which the intervention never touches — and can worsen via congestion.
- Capacity arithmetic (131 cases/wk vs 4/7/3/2 pools and elapsed service times of 3.4/8.1h) implies "service" times embed waiting and the document pool is near saturation — so simultaneous release creates arrival bursts.

## 6. Candidate Site B intervention

**Process specification.**

- **Eligibility (wave 1):** channel = digital-complete at Register AND not public-sector/high-value AND low/medium complexity. **Wave 2 (exploratory):** originals cases, concurrency limited to Identity  Originals Receipt with auto-release of Document Check on receipt.
- **Concurrent tasks:** for eligible cases, Identity Check and Document Check are *created* simultaneously at Register; execution is pull-based. For originals cases, Identity Check and Originals Receipt are concurrent (already legal); Document Check is released by the receipt event.
- **Mandatory statutory prerequisites:** Originals Receipt before Document Check when required; Legal Review for mandated cases; Assessment AND-join; decision before Notify. Untouched.
- **Queue and WIP controls:** per-reviewer cap of 6 open verification tasks (adopted from A as a separate practice); pool-level WIP caps; release Identity only when the identity pool has slack; aging-based priority to protect the tail.
- **Resource responsibilities:** roles remain separate; no cross-role execution in wave 1; a coordinator role owns eligibility tagging at Register.
- **Legal-review and supplement loops:** Request Supplement invalidates the prior Document Check; a versioned *Document Re-Check* (delta documents only) and *Re-Assessment* are triggered; loop counter capped at 2 before escalation; legal-flagged cases excluded from wave 1.
- **Logging:** dual active task ownership enabled for pilot cases, or event-time captured separately from commit-time; back-entry forbidden beyond 24h; eligibility decision, release times, and pool assignment logged.

**POWL-style description / partial-order relation set** (`<` = must precede; `` = unordered):

```text
SiteB_candidate =
->( Register,
    X( +( IdentityCheck, DocumentCheck ),                     // digital, eligible
       PO{ OriginalsReceipt < DocumentCheck ; IdentityCheck  OriginalsReceipt } ),
    Assessment,                                               // AND-join
    X( tau,                                                   // no legal review
       *( LegalReview, ->( RequestSupplement, DocumentReCheck, ReAssessment ) ) ),
    X( Approve, Reject ),
    Notify )

Relation set (main chain):
Register < IdentityCheck ; Register < OriginalsGate(XOR: OriginalsReceipt | tau)
OriginalsGate < DocumentCheck            // tau fires instantly for digital claims
IdentityCheck < Assessment ; DocumentCheck < Assessment
Assessment < LegalGate ; LegalGate < X(Approve,Reject) < Notify
RequestSupplement < DocumentReCheck < ReAssessment < LegalReview   // loop body
IdentityCheck  OriginalsReceipt ; IdentityCheck  DocumentCheck (digital branch only)
```

The pilot reads **fidelity** and **mechanism** on separate axes. Fidelity metrics: true overlap computed from event-time (not commit-time) timestamps, share of treated cases with both tasks legally startable at release, lock-violation/back-entry rate, WIP-cap compliance. Mechanism metrics: waiting-before-Assessment and cycle-time change *conditional on achieved overlap*, document-pool utilization, treated-vs-control p90, rework and appeals.

Four cells: high fidelity + effect  transport supported, scale. High fidelity + no effect  **mechanism failure** at B (structural modifiers dominate: originals gate, saturation); do not scale regardless of A's headline. Low fidelity + no effect  **implementation failure**; fix the case lock and release logic, rerun; nothing inferred about transport. Low fidelity + apparent effect  suspect timestamp artifact; audit before crediting.

Cross-site: re-analyze A with mix standardization and capacity adjustment to bound A's true effect, then compare to B's stratum-specific estimates; heterogeneity across strata, mapped to the modifiers, identifies the transport boundary. Control-arm waiting drift >1h signals shared-queue contamination; then treat case-level contrasts as lower bounds and rely on stepped-wedge team contrasts.

## 8. PM4Py model-construction code

```python
"""
Transportability models: Site A before/after trees + Site B candidate POWL.

FIDELITY NOTE: process trees / POWL encode CONTROL FLOW ONLY. They cannot
express: data-dependent branching probabilities (62% originals, 40% legal
review are case attributes -- the XORs below are nondeterministic), resource
pools and capacity (4/7/3/2 reviewers), the single-owner case lock, WIP
limits, queue disciplines, durations/timestamps, or rework probabilities.
Those layers must come from simulation annotations or the pilot.
"""
import pm4py

# ---- 1) Site A: before & after process trees ------------------------------
A_BEFORE = ("->( 'Register', 'Identity Check', 'Document Check', "
            "'Assessment', X( 'Approve', 'Reject' ), 'Notify' )")
A_AFTER  = ("->( 'Register', +( 'Identity Check', 'Document Check' ), "
            "'Assessment', X( 'Approve', 'Reject' ), 'Notify' )")
tree_a_before = pm4py.parse_process_tree(A_BEFORE)
tree_a_after  = pm4py.parse_process_tree(A_AFTER)

# ---- 2) accepting Petri nets ----------------------------------------------
net_ab, im_ab, fm_ab = pm4py.convert_to_petri_net(tree_a_before)
net_aa, im_aa, fm_aa = pm4py.convert_to_petri_net(tree_a_after)

# ---- 3) Site B candidate as POWL ------------------------------------------
from pm4py.objects.powl.obj import (StrictPartialOrder, OperatorPOWL,
                                    Transition, SilentTransition)
from pm4py.objects.process_tree.obj import Operator   # XOR / LOOP operators

register    = Transition("Register")
identity    = Transition("Identity Check")
originals   = Transition("Originals Receipt")
doc_check   = Transition("Document Check")
assessment  = Transition("Assessment")
legal       = Transition("Legal Review")
supplement  = Transition("Request Supplement")
doc_recheck = Transition("Document Re-Check")   # distinct label for the loop
reassess    = Transition("Re-Assessment")       # (duplicate labels confuse logs)
approve     = Transition("Approve")
reject      = Transition("Reject")
notify      = Transition("Notify")
tau_no_orig = SilentTransition()   # digital channel: originals not required
tau_no_leg  = SilentTransition()   # legal review not required

# originals gate: receive originals OR skip (digital claims)
originals_gate = OperatorPOWL(Operator.XOR, [originals, tau_no_orig])

# supplement loop: do LegalReview; optionally redo
# ->(RequestSupplement, Document Re-Check, Re-Assessment) and loop back
redo = StrictPartialOrder(nodes=[supplement, doc_recheck, reassess])
redo.order.add_edge(supplement, doc_recheck)
redo.order.add_edge(doc_recheck, reassess)
legal_loop = OperatorPOWL(Operator.LOOP, [legal, redo])
legal_gate = OperatorPOWL(Operator.XOR, [legal_loop, tau_no_leg])

decision = OperatorPOWL(Operator.XOR, [approve, reject])

# ---- 4) top-level strict partial order with EXPLICIT AND-join edges -------
site_b = StrictPartialOrder(nodes=[register, identity, originals_gate,
                                   doc_check, assessment, legal_gate,
                                   decision, notify])
site_b.order.add_edge(register, identity)          # rule 2
site_b.order.add_edge(register, originals_gate)    # rule 3
site_b.order.add_edge(originals_gate, doc_check)   # rule 4 (tau => immediate for digital)
site_b.order.add_edge(identity, assessment)        # rule 5: Assessment waits for identity
site_b.order.add_edge(doc_check, assessment)       # rule 5: Assessment waits for documents
site_b.order.add_edge(assessment, legal_gate)      # rule 6
site_b.order.add_edge(legal_gate, decision)        # rule 8
site_b.order.add_edge(decision, notify)            # rule 8
# no edge identity<->originals_gate / identity<->doc_check  =>  concurrency

# ---- 5) POWL -> accepting Petri net ---------------------------------------
try:
    net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b)
except Exception:  # older PM4Py: call the POWL converter variant directly
    from pm4py.objects.powl.converter.variants.powl_to_petri import apply as powl2net
    net_b, im_b, fm_b = powl2net(site_b)

# ---- 6) workflow-net / soundness checks -----------------------------------
def check(name, net, im, fm):
    try:
        wf = pm4py.check_is_workflow_net(net)
    except Exception:
        wf = "check unavailable"
    try:
        sound = pm4py.check_soundness(net, im, fm)
    except Exception:
        try:
            from pm4py.algo.analysis.woflan import algorithm as woflan
            sound = woflan.apply(net, im, fm, parameters={})
        except Exception:
            sound = "check unavailable"
    print(f"{name}: workflow-net={wf}, sound={sound}")

check("A before", net_ab, im_ab, fm_ab)
check("A after ", net_aa, im_aa, fm_aa)
check("B cand. ", net_b,  im_b,  fm_b)

# ---- 7) optional playout ---------------------------------------------------
log = pm4py.play_out(net_b, im_b, fm_b, parameters={"max_trace_length": 15})
for trace in list(log)[:6]:
    print(" | ".join(e["concept:name"] for e in trace))

# ---- 8) what this model CANNOT encode --------------------------------------
# - data dependence: whether originals are legally required or legal review is
#   triggered is a case attribute; the XOR gates above are nondeterministic.
# - resources/capacity: the 4/7/3/2 pools, WIP caps, and queue discipline.
# - the single-owner case lock and its workarounds (back-entry).
# - durations, timestamps, originals-arrival delays, and rework probabilities.
# Consequence: soundness of the net says nothing about cycle-time transport;
# it only certifies that the control-flow skeleton is well-formed.
```

## 9. Recommendation

`conditional go`

**What to transfer:** the mechanism, not the metric. Transfer (i) *segmented concurrency* — simultaneous creation of Identity Check and Document Check only for cases whose documents are complete at registration; (ii) *event-driven release* — Document Check auto-released on Originals Receipt for the 62% originals segment, the only legal form of "parallelism" there; (iii) A's WIP cap (six open verification tasks per reviewer), adapted to B's pools, as a separately adoptable practice; (iv) the instrumentation lesson — event-time logging separated from commit-time, without which no effect at B can be credibly measured.

**What not to copy:** the universal, all-team, two-week big-bang; the expectation of a nine-hour median gain — an unidentified mixture of capacity (+11% FTE), mix shift, API, and huddle effects, of which at most ~3.5h is structural even at A; and any attempt to start Document Check before originals arrive.

**First subgroup:** digital-channel, non-public/non-high-value cases (~23% of volume, 780 cases per six months), stratified by complexity. Here both checks are legally startable, the legal loop is absent, and lock-workaround risk is contained.

**Expected benefits:** within-stratum median cycle reduction of roughly 3–5h (the 3.4h identity service plus one removed handoff), population median 1–2h, negligible p90 effect. **Risks:** document-pool saturation converting released work into queue; lock-driven back-entry corrupting measurement; earlier arrivals congesting the two-reviewer legal pool and worsening the tail; rework if checks start on incomplete document sets.

**Expansion triggers:** fidelity 60% true overlap with <5% back-entry; treated-stratum median improvement 2h with p90 non-inferior (within +3h); rework and appeals non-inferior; control-arm waiting drift <1h. **Modification triggers:** low fidelity  fix the case lock and event-time logging first; document-pool utilization >85%  add pull-based release or capacity before scaling. **Abandonment triggers:** full fidelity with no waiting reduction (mechanism failure — modifiers dominate), p90 degradation >10h, or rework +3pp. Statutory ordering remains untouched throughout.

## 10. Assumption register

1. A's overlap increase (871%) reflects real concurrency, not mainly improved timestamp recording — needed to attribute any of A's gain to parallelization — audit A's event-time vs commit-time fields and system logs — if false, the transferable effect shrinks toward the small structural bound or zero.
2. A's waiting reduction is not fully explained by +2 FTE, mix shift, and huddles — needed to expect any queueing benefit at B — re-analyze A with mix standardization and per-FTE capacity adjustment plus a negative-control process — if false, B should expect only the ~3.4h critical-path saving on eligible cases.
3. For B's digital cases, identity and document checks are informationally independent — needed for safe parallel execution — conformance-check the digital subset; interview reviewers about shared preconditions — if false, parallel starts cause rework and the eligible share shrinks.
4. B's document pool has slack or arrivals can be smoothed — needed for released tasks to become output rather than queue — measure utilization, queue length, and the touch-time vs elapsed-time split — if false, the bottleneck-shift scenario dominates; add capacity or pull release first.
5. The case lock can be relaxed or event-time logging implemented for the pilot — needed for fidelity and measurement — sandbox test plus back-entry audit — if false, defer rollout and run an IT-fix arm first.
6. Originals delay is exogenous to verification scheduling — needed to treat the 18h delay as untouchable by this intervention — analyze receipt timestamps against release times — if false, a different intervention (earlier originals chasing) may dominate.
7. The two-reviewer legal pool can absorb earlier arrivals, or legal cases can be excluded — needed to protect the tail — monitor legal queue length and utilization during the pilot — if false, exclude legal-flagged cases permanently or add legal capacity.
8. B's case mix and demand remain stable during the pilot — needed for identification — weekly mix monitoring with randomized assignment within strata — if false, before/after contrasts repeat A's confounding; rely on randomized contrasts only.
