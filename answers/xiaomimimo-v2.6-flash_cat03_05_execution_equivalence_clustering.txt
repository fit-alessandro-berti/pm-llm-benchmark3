## 1. Equivalence design space

**Common notation.** An execution is `X = (E, , ; O, , ext; E2O; Q)`:
events `E` with timestamp order `` (events sharing a timestamp form one *step*), labels ``; objects `O` with type `  {Order, Item, Package, Delivery, Invoice, Payment}` and flag `ext` (true iff the id starts with `EXT`); event–object incidences `E2O`; and `Q`, a set of qualified object–object tuples `(relation, object tuple, qualifier)`.

### E1 — Activity-sequence equivalence (ASE)
**Definition.** `(X) = L,…,L_k`, where `L_i` is the *multiset* of labels in step `i`. `X ASE Y  (X)=(Y)`.
**Preserves:** event count, label multiplicities, step order. **Discards:** every object-level fact — types, ids, E2O arity, O2O topology, qualifiers, externality, object multiplicities.
**Properties:** equality on a canonical string  reflexive, symmetric, transitive. **Concurrency:** within-step order is deliberately ignored (multiset); if no timestamps exist, the whole trace becomes one step (coarsest).
**Classes here:** `{X1,X2,X5,X6,X7}`, `{X3}`, `{X4}`, `{X8}`.

### E2 — Typed structural equivalence under identifier renaming (TSE)
**Definition.** `X TSE Y` iff there exist a label-preserving, step-preserving bijection `f : E_X  E_Y` and a bijection `g : O_X  O_Y` with `(g(o))=(o)`, `ext(g(o))=ext(o)`, `(e,o)E2O_X  (f(e),g(o))E2O_Y`, and each tuple of `Q_X` maps to a tuple of `Q_Y` with the same relation name and qualifier. Local ids are *opaque*; only the `EXT` flag is semantic.
**Preserves:** types, multiplicities, externality, E2O incidence and per-event arity, O2O relations + qualifiers, event order, repeated activities. **Discards:** identifier strings, absolute timestamps, within-event id list order (groups are sets).
**Properties:** an equivalence relation; `TSE  ASE` strictly (a renaming bijection induces a label-sequence bijection).
**Concurrency:** `f` must map steps bijectively, with an arbitrary label-preserving matching inside each step.
**Classes here:** `{X1,X2}`, `{X3}`, `{X4}`, `{X5}`, `{X6}`, `{X7}`, `{X8}`.

### E3 — Business-semantic equivalence (BSE) — *preferred*
**Definition.** `X BSE Y  (X)=(Y)`, where
- `m` — local object multiplicity vector per type (externals counted separately);
- `f` — fulfillment code: `(#Pack events, #Dispatch events, #packages, #deliveries, sorted multiset of local itempackage degrees, max packages per delivery, #local items in >1 package)`;
- `s` — settlement code: `(#invoices, #payments, max payments per invoice, sorted payment qualifiers)`;
- `c` — **closure flag**: `False` iff any external object appears in any `E2O` of this execution or in any of its `Q` tuples (refinement key only: attachment domain `{logistics, finance}`);
- `q` — sorted multiset of O2O qualifiers;
- `r` — motif flags: `return_repack` (a `Return Item` exists  some local item has package-degree > 1), `removal_at_dispatch` (`removed_before_dispatch` present).

**Preserves:** multiplicities, topology shape, qualifiers, motifs, closure. **Discards:** ids, exact times, id-list order, and (at top level) *where* externality attaches.
**Properties:** equality on an image  equivalence. `BSE` **coarsens** `TSE` here (X5, X6 merge) and, on this data set, **refines** `ASE`; in general BSE and ASE are incomparable (BSE drops ordering, ASE drops objects).
**Concurrency:** all counts/degrees are order-insensitive; motifs are evaluated as "exists a linear extension containing the pattern", so same-time events never split a class.

### E4 — Causal partial-order equivalence (used in §7)
Label-annotated poset induced by object causality (`pack  dispatch of carried package`, `dispatch  return  repack  second dispatch`), identifiers abstracted; equivalent iff the labelled posets are isomorphic (isomorphism  equivalence). Concurrency is *preserved* rather than flattened.

## 2. Canonical signatures

Renaming is performed first (type, first appearance, ids sorted inside each E2O group); the preferred key is then computed from the canonical form.

```python
from collections import defaultdict, Counter

def canonical_form(x, lead="Order"):
    """Rename local objects by (type, first appearance); keep EXT flags."""
    evs = sorted(x.events, key=lambda e: (e.t, e.label))
    ren, seen = {}, defaultdict(int)
    def touch(oid, typ):
        if oid in ren: return
        if oid.startswith("EXT"): ren[oid] = "EXT-" + typ
        else:
            seen[typ] += 1; ren[oid] = f"{typ}{seen[typ]}"
    for e in evs:                                   # ids inside a group are a SET
        for typ, ids in e.refs:
            for i in sorted(ids): touch(i, typ)
    steps = []                                      # same timestamp -> one step
    for e in evs:
        groups = tuple(sorted((t, tuple(sorted(ren[i] for i in ids)),
                               any(i.startswith("EXT") for i in ids)) for t, ids in e.refs))
        node = (e.label, groups)
        if steps and steps[-1][0] == e.t: steps[-1][1].append(node)
        else: steps.append([e.t, [node]])
    trace = tuple((t, tuple(sorted(ns, key=repr))) for t, ns in steps)
    o2o   = tuple(sorted((r.name, tuple(sorted(ren[i] for i in r.objs)), r.qual or "")
                         for r in x.o2o))
    local = {t: sorted(i for i in ren.values() if i.startswith(t))
             for t in {i.split("0")[0] for i in ren.values() if not i.startswith("EXT")}}
    return {"trace": trace, "o2o": o2o, "local": local, "ren": ren}

def semantic_key(x, lead="Order"):
    cf  = canonical_form(x, lead)
    tr, o2o, loc = cf["trace"], cf["o2o"], cf["local"]
    L    = lambda n: [r for r in o2o if r[0] == n]
    packs, carries, settles = L("packs"), L("carries"), L("settles")
    nodes = [nd for _, ns in tr for nd in ns]
    is_local = lambda i: not i.startswith("EXT-")

    item_deg = Counter(i for _, o, _ in packs for i in o[1:] if is_local(i))
    per_del  = [len(o) - 1 for _, o, _ in carries]
    fulfil = (sum(1 for l, _ in nodes if l == "Pack Package"),
              sum(1 for l, _ in nodes if l == "Dispatch"),
              len(loc.get("Package", [])), len(loc.get("Delivery", [])),
              tuple(sorted(item_deg.values())), max(per_del or [0]),
              sum(1 for d in item_deg.values() if d > 1))
    pay_per_inv = Counter(i for _, o, _ in settles for i in o[1:])
    settle_q = tuple(sorted(q for _, _, q in settles if q))
    fin = (len(loc.get("Invoice", [])), len(loc.get("Payment", [])),
           max(pay_per_inv.values() or [0]), settle_q)

    domains, ext = set(), False
    for l, groups in nodes:
        if any(e for _, _, e in groups):
            ext = True
            domains.add("finance" if l in {"Issue Invoice", "Record Payment"} else "logistics")
    ext = ext or any(not is_local(i) for _, o, _ in o2o for i in o)
    quals = tuple(sorted({q for _, _, q in o2o if q}))
    labs  = Counter(l for l, _ in nodes)
    r = tuple(sorted(k for k, v in {
            "return_repack":      labs["Return Item"] > 0 and max(item_deg.values(), default=0) > 1,
            "removal_at_dispatch": "removed_before_dispatch" in quals}.items() if v))

    top = (m := tuple((t, len(loc.get(t, []))) for t in
                      ("Order", "Item", "Package", "Delivery", "Invoice", "Payment")),
           fulfil, fin, not ext, quals, r)
    return top, tuple(sorted(domains))          # (top-level key, refinement key)
```

`top` is the reproducible signature; the refinement key (attachment domain) is reported but not used for top-level equality.

## 4. Cluster interpretations

**S1 `{X1,X2}` — Isolated standard fulfillment.** *Signature:* `1P·1D | INV1·PAY1 | closed | no qualifiers`. One package, one dispatch, one invoice, one settlement, no cross-order objects. This is the conformance baseline: risks are minimal, opportunity is straight-through automated approval and templated KPI baselines. A plain Order-case flattening represents it perfectly — it is precisely the case flattening was designed for. Stable: renaming, qualifier removal, and payment normalization all leave it intact; its *size* is only sensitive to upstream repairs that delete partner links (pushing S4 members in).

**S2 `{X3}` — Consolidated split packing.** *Signature:* `2P·1D | INV1·PAY1 | closed`. Two packages (warehouse/SKU/carrier constraints) share one dispatch. Risk: delivery-level evidence is shared — damage or delay on D31 cannot be attributed to a package; opportunity: measurable consolidation savings. Poor flattening: a **delivery- or package-keyed** flattening duplicates D31 in both package cases (double counting), while an order flattening over activity *sets* erases the 2-vs-1 package structure and makes X3 look like S1. Stable under finance repairs; fragile if package multiplicity is counted from events after same-label collapsing.

**S3 `{X4}` — Split fulfillment with staged settlement.** *Signature:* `2P·2D | INV1·PAY2{partial,complete} | closed`. Two independent packdispatch chains and a partial-then-complete settlement of one invoice (deposit/balance or partial shipment). Risks: revenue-timing and reconciliation, dunning on the partial payment, doubled transport cost; opportunity: cycle-time KPI from `partial_settles` to `completes_settlement`. Poor flattening: a **payment-keyed** view splits one order into two cases and hides that both settle the *same* invoice; a label-set order view hides both the second dispatch and the second payment. Stable to id noise and to partial-order abstraction (multiplicities survive), unstable if payments become amounts (§7 P5).

**S4 `{X5,X6}` — Non-closed (externally coupled) execution.** *Signature:* `1P·1D | INV1·PAY1 | non-closed`. The execution cannot be explained from the order's own object universe: a partner order's objects sit inside the logistics events (X5) or the financial events (X6). Risks: order-sliced cost, revenue and cycle-time KPIs are wrong; trace incompleteness when monitoring on `Order`; revenue allocation on a shared invoice (X6); shared physical evidence on a shared dispatch (X5). Opportunity: detection of consolidated shipping / marketplace or dropship billing. Poor flattening: **any order-keyed flattening** — external objects are silently dropped, so X5 and X6 degrade into S1 *without any warning*. Stability: the most fragile cluster — it exists only because the `EXT` marker and cross-order links are retained; dropping them merges S4 into S1, adding a recovered partner link splits it. The logistics/finance sub-split inside S4 is also repair-sensitive.

**S5 `{X7}` — Dispatch-time item removal.** *Signature:* `1P·1D | INV1·PAY1 | closed | {removed_before_dispatch}`. An item that was packed is removed or substituted before dispatch, recorded only as a qualifier (plus an extra item reference on `Dispatch`). Risks: inventory discrepancy, delivered contents  invoiced contents, undetected substitution. Opportunity: exception mining candidate. Poor flattening: label-only flattening shows a *perfect happy path* — this is the canonical case where structural equality hides a business exception. Stability: fragile — it survives only while both the qualifier and the derived item incidence are kept; normalizing `Dispatch` back to `(Order, Package, Delivery)` merges X7 into S1. It becomes robust if an explicit `Replace/Remove Item` activity is logged.

**S6 `{X8}` — Return and repack loop.** *Signature:* `2P·2D | INV1·PAY1 | closed | {replaces, return_repack}`. Post-delivery return  inspection  repack  second dispatch of the same item, with one invoice/payment. Risks: rework and double transport cost; item I82 belongs to two packages, so item-keyed analytics double count. Opportunity: return-loop cycle time and inspection yield. Poor flattening: a **package-keyed** view splits P81 and P82 into unrelated cases, destroying the causal loop; a delivery-keyed view hides that D82 re-delivers an already delivered item. Fairly stable: `Return Item`/`Inspect Return` are hard labels; only a repair that re-instantiates the returned item as a new object removes the degree-2 feature (the motif flag still holds).

## 5. Borderline cases

Treating `I11,I12` as a set (as the notation intends) merges them; treating it as a sequence splits them. A second splitter would be time-derived naming. **(X3 vs X4).** All three split them, but for different reasons: ASE by order (`P,P,D` + 1 payment vs `P,D,P,D` + 2 payments), TSE by structure, BSE by `2P·1D` vs `2P·2D` and settlement multiplicity. **(X4 vs X8).** All three split them, but the salient feature differs. (a) A fulfillment-topology-only semantics (count packages and deliveries, ignore finance and rework) yields `2P·2D` for both  merge. (b) The full signature splits: X4 has *disjoint* itempackage membership and staged settlement; X8 has an item packed twice plus `Return/Inspect` and a `replaces` relation. (c) A third, fragile position: if returns are traced in a separate process and payment multiplicity becomes an amount, X8 loses its labels and X4 loses its payment count — the entire distinction then rests on one O2O degree, `(1,1)` vs `(1,2)`.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the key preserves.** The PM4Py clustering groups lead objects whose *induced sub-structures are exactly identical*: activity label per event, the literal object ids referenced by each event, and the O2O tuples with qualifiers, i.e. an exact fingerprint of the **named** structure (verify composition against your `pm4py.__version__`). It is therefore an isomorphism test over log rows, not over renamed shapes.

**Why raw ids make it too fine.** X1 and X2 are isomorphic yet land in different clusters because their ids differ; in a real log every execution has unique ids, so without internal canonicalization every cluster is a singleton. External ids compound this: two orders sharing a package (X5-type) get identical keys only if their *entire* neighborhood matches, so one differing partner splits both.

**Canonicalization / post-processing.** (i) *Pre-canonicalize*: rename local objects by (type, first appearance), treat E2O groups as sets, bucket timestamps into steps, rebuild a derived OCEL, then call the exact clusterer — it now returns isomorphism classes. (ii) *Post-aggregate*: group the returned clusters by the Section-2 `top` key (majority vote per cluster). (iii) *Cross-tab diagnostics*: same exact cluster but different semantic key  versioning/renaming artifact; same semantic key but different exact cluster  id noise — both are repair candidates.

**When exact is preferable.** Audit/compliance reproduction (you must name the objects that participated), debugging extraction pipelines, master-data deduplication, and any domain where identifiers carry meaning (partner-coded ids, `EXT` markers). Exactness is also right when the population is small and each execution is inspected individually.

**`max_objs` and large connected executions.** A cap on objects per key truncates the fingerprint; if the kept subset depends on traversal order, two isomorphic executions can disagree. Shared packages or consolidated deliveries inflate *every* participating order's neighborhood, so keys either degenerate into one giant cluster (partners all match) or into singletons (one partner differs), with super-linear cost. Practical mitigations: restrict to a depth-1 neighborhood of the lead object, exclude `EXT` objects from the key and store them as an attribute, set `max_objs` generously and deterministically, and cluster on the canonicalized reduced graph.

```python
import pm4py
from collections import defaultdict, Counter

ocel = pm4py.read_ocel("orders.ocel")
LEAD = "Order"

obj_type = ocel.objects["ocel:type"].to_dict()
e2o, o2o = ocel.e2o, ocel.o2o
ev_objs  = e2o.groupby("ocel:event_id")["ocel:object_id"].apply(list).to_dict()
obj_evs  = e2o.groupby("ocel:object_id")["ocel:event_id").apply(list).to_dict()  # see note

def execution(lead_id):
    evs  = sorted(obj_evs[lead_id], key=lambda e: ocel.events.at[e, "ocel:timestamp"])
    objs = {o for e in evs for o in ev_objs[e]}
    rels = o2o[o2o["ocel:object_id_source"].isin(objs) &
               o2o["ocel:object_id_target"].isin(objs)]
    return assemble(evs, objs, rels)          # -> object with .events / .o2o (Sec. 2)

leads = ocel.objects.index[ocel.objects["ocel:type"] == LEAD]

# (1) exact clustering as shipped by PM4Py
raw = pm4py.cluster_equivalent_ocel(
          ocel, parameters={"object_type": LEAD, "max_objs": 10000})

# (2) renaming-invariant keys for every lead object
keys = {lid: semantic_key(execution(lid))[0] for lid in leads}   # top-level key only

# (3) canonical aggregation: re-merge exact clusters sharing a semantic key
agg = defaultdict(set)
for cid, members in normalize(raw):                 # dict or list, version-dependent
    k = Counter(keys[m] for m in members).most_common(1)[0][0]   # majority vote
    agg[k] |= set(members)

# (4) diagnostics
# same raw cluster / different key  -> identifier or version artefact
# same key / different raw cluster  -> id-driven over-splitting (X1 vs X2 pattern)
# non-closed keys (S4)              -> flag: order-sliced KPIs unreliable
```

## 7. Robustness analysis

**P1 — ignore all O2O qualifiers.** `S3` survives (two payment *objects* still give `PAY2`); `S6` survives (`Return/Inspect` labels + item degree 2); `S5` is at risk: X7 still differs from X1 by E2O arity at `Dispatch`, so it stays separate *unless* the derived item incidence is normalized too — then `S5  S1` and the class disappears. `S2`, `S4` unchanged.

**P2 — ignore external objects.** Both `EXT` objects and cross-order incidences are dropped: X5 and X6 become structurally X1, so `S4` dissolves and `S1 = {X1,X2,X5,X6}`; TSE correspondingly merges `T4,T5` into `T1`. ASE is unaffected. This is the perturbation with the largest blast radius.

**P3 — collapse repeated same-label events.** Under run-collapse, `(X3)` becomes `C,A,P,D,V,M`, so ASE merges X3 into the big class; X4 (`…P,D,P,D…`) and X8 stay separate. The *semantic* clustering is invariant **provided** multiplicities are read from objects/O2O rather than from events: `n_packages=2` and `payments-per-invoice=2` persist even if the corresponding duplicate events are merged or dropped. Recommendation: treat object/O2O counts as authoritative and event counts as derived.

**P4 — Pack/Dispatch as a partial order (E4).** The *interleaving* difference between X3 and X4 vanishes; they remain distinct only through delivery count and packages-per-delivery. If one additionally interprets a consolidated dispatch as `k` concurrent single-package dispatches, `S2` and `S3` merge (given P5). X8's loop survives (causality forces `Return  second Pack`); X1/X2/X5/X6/X7 are unaffected (linear single pack/dispatch).

**P5 — payment multiplicity as an amount.** `S3` loses `PAY2{partial,complete}`: its finance code equals S1's, so the staged-settlement monitoring capability disappears, though `2P·2D` keeps it apart from `S1` and `S2`. Combined with P4, `S3` drifts into `S2`. No merge occurs from P5 alone.

Overall: `S6` and `S2` are the most robust; `S4` and `S5` are the most repair-sensitive; `S1` is the "absorption basin" that gains members whenever detail is lost.

## 8. Limitations and recommendation

- **Compliance monitoring  TSE (or finer).** Retain qualifiers, externality and per-event incidence — ideally with identifiers. False merges are expensive (an unnoticed shared invoice or a silent item removal is a finding); false splits merely cost extra rules. This is where `cluster_equivalent_ocel` in exact form belongs.
- **Operational segmentation  the preferred BSE.** You need stable, actionable groups (warehouse, carrier, billing actions) that are invariant to id noise and log versioning, while still exposing package/delivery topology and closure.
- **Root-cause analysis  hierarchical.** Generate candidates with BSE, then drill down with TSE/E4 to isolate the *single* differing feature (one extra delivery, one qualifier, one payment). A single level either drowns you in singletons (TSE) or hides the difference (ASE).
- **Descriptive reporting  ASE plus object-multiplicity columns.** Communicable, stable, easy to roll up — but it must always carry object counts and closure flags, otherwise it is not object-centric at all.

**Why no single notion is best.** Each purpose has a different asymmetry between false merges and false splits and a different invariance requirement: reporting wants invariance to identifiers and incidental ordering; compliance wants invariance to *nothing* but naming; segmentation wants invariance to log-repair artifacts; root-cause analysis wants sensitivity to exactly one feature at a time. An equivalence relation is a declared list of "facts I agree to ignore" — and that list is a lens choice, not a property of the data. Hence the four recommended levels, used together as a hierarchy rather than competing for the title of *the* correct clustering.
