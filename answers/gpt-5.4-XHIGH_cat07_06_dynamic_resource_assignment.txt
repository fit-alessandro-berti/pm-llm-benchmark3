# 1. Objectives and constraints
**Optimization objectives**

- Protect SLA performance first for urgent and high-priority work, using both remaining SLA time and expected delay from queueing, handovers, and weak skill match.
- Reduce avoidable errors, rework, and appeals by preventing clear skill mismatches and by avoiding unnecessary owner changes on complex cases.
- Preserve continuity of ownership when the case is complex or handover cost is high, especially when reassignment counts are already elevated.
- Distribute work fairly by considering open cases, hours remaining today, and overtime risk rather than raw availability alone.
- Create controlled skill development opportunities on normal and low-priority work when SLA slack is adequate and a safe fallback exists.
- Maintain resilience by avoiding single-specialist bottlenecks in Security and Approval and by not routing everything to the same low-load person.

**Hard safety and compliance constraints**

- Skill level `0` is ineligible.
- `Security Review` must be done by skill `3`, or by skill `1-2` only with explicit supervision from `R7_Gita` or `R8_Hugo`.
- `Final Approval` must be finalized by skill `2-3`. Skill `1` may prepare but may not finalize.
- No high-priority or urgent case may be assigned below skill `2` unless the assignment is explicitly supervised.
- No resource may receive more than `4` new assignments in the batch.
- `Quality Check` batching is allowed only for normal/low priority with more than `24h` SLA remaining.
- For high-complexity cases with high handover cost, continuity is the default unless the current owner has skill `0-1` and safe supervision is not feasible, or SLA risk makes specialist override necessary.

**Soft preference trade-offs**

- Prefer specialists on urgent, high-complexity, or error-sensitive work, but not at the cost of creating chronic specialist queues.
- Prefer continuity when reassignment count is already high or handover cost is medium/high.
- Penalize assignments to `overtime risk = high` unless the case is urgent and lower-risk eligible options are not available.
- Count a case as training-supporting only when the development goal is documented and the training mode is safe:
  `direct assignment` for allowed skill levels,
  `supervised execution` where rules permit it, or
  `shadow/preparation` when hard rules prevent direct execution.
- Use explainable override reasons rather than claiming a single global optimum.

# 2. Assignment policy
Use a two-stage policy: first remove unsafe or non-compliant options, then rank the remaining options with a transparent weighted score.

**Step 1: Case ordering**

- Rank cases by `priority`, then by `SLA time remaining`, then by `complexity`, then by `reassignment_count`.
- In practice, the front of the queue is: urgent cases with less than `4h` remaining, then other urgent/high cases with less than `8-10h`, then normal/low cases.

**Step 2: Eligibility filtering**

For each case, create candidate assignments as either a single resource or an allowed supervised pair.

```text
eligible(case, candidate):
  reject if candidate skill == 0
  reject if candidate already has 4 new assignments in this batch
  reject if hours_remaining_today is critically low and case is urgent with no start capacity

  if case.activity == "Security Review":
      allow solo only for skill 3
      allow supervised pair only for skill 1-2 with supervisor in {R7_Gita, R8_Hugo}
      otherwise reject

  if case.activity == "Final Approval":
      allow solo only for skill 2-3
      allow prep+finalize pair for skill 1 preparer plus skill 2-3 finalizer
      otherwise reject

  if case.priority in {"high", "urgent"} and candidate skill < 2:
      reject unless supervised

  if case.complexity is high and handover_cost is high and owner change is proposed:
      reject by default unless owner skill <= 1 and safe supervision is not enough,
      or SLA risk is severe enough to justify a specialist override
```

**Step 3: Candidate scoring**

For each eligible candidate, compute:

`total_score = 0.35*SLA + 0.20*Skill + 0.20*Continuity + 0.15*WorkloadFairness + 0.05*Training + 0.05*Resilience`

**SLA urgency scoring**

- Start with a case urgency base: `urgent > high > normal > low`.
- Increase score when `sla_time_remaining` is small relative to expected service and waiting time for that activity/resource combination.
- Penalize candidates likely to create extra waiting today because of low hours remaining, high current load, or likely handover delay.

Example logic:

```text
sla_slack = sla_remaining
            - expected_service_time(activity, candidate_skill_band)
            - expected_waiting_time(candidate_resource)
            - expected_handover_delay(if owner changes)

SLA score is high when slack is small but still recoverable by that candidate.
```

**Skill-match scoring**

- Skill `3`: best for urgent, security, approval, high complexity, and repeated-loop cases.
- Skill `2`: good default for most work, especially if continuity is strong.
- Skill `1`: only valuable for low-risk learning cases or explicitly supervised work.
- Add extra penalty when a weak-skill option is proposed on a case with known rework or appeal sensitivity.

**Continuity and handover-cost scoring**

- Strong bonus if the current owner keeps the case and has acceptable skill.
- Smaller bonus for a supervised or paired assignment that keeps the owner involved.
- Strong penalty for changing owner when:
  the case is high complexity,
  handover cost is high,
  or `reassignment_count >= 2`.
- Moderate penalty for low-complexity, low-handover work where rebalancing is beneficial.

**Workload and overtime fairness scoring**

- Compute a simple load index such as `open_cases / hours_remaining_today`.
- Reward candidates with lower load index and lower overtime risk.
- Apply a heavy penalty to `overtime risk = high` on non-urgent work when a safer eligible candidate exists.
- Keep a visible per-batch counter to enforce the `max 4` rule.

**Training and development scoring**

- Only consider training bonuses on normal/low work, or on high work where the assignee already meets the minimum skill and the training action is only shadow/preparation.
- Reward candidates whose documented training priority matches the required skill.
- Require an SLA buffer and a clear backstop:
  checkpoint review,
  named supervisor,
  or finalizer for approvals.

**Resilience and bottleneck avoidance**

- Penalize repeatedly sending security and approval work to the same specialist when a compliant competent alternative exists.
- Reward use of competent non-specialists on lower-risk work to keep backup capacity alive.
- Reward batching for `Quality Check` when the batching rule is met.
- Preserve scarce security specialists for work that truly needs them.

**Tie-breaking**

1. Prefer the current owner when the score difference is small and continuity risk is material.
2. Then prefer the lower overtime-risk resource.
3. Then prefer the lower load index.
4. Then prefer the candidate with better collaboration fit to the owner/team, using handover and working-together network evidence.
5. If still tied, rotate fairly within role peers.

**Exception handling**

- If no candidate is eligible, escalate to a human coordinator and log `assignment_reason = manual_exception`.
- If the best option violates a soft rule, allow it only with an explicit reason such as:
  `urgent_specialist_override`,
  `continuity_override`,
  `overtime_override`,
  `training_with_checkpoint`,
  `batching_rebalance`.
- Persist the chosen reason and the main score components so the decision is auditable.

# 4. Comparison with baseline policies
| Dimension | First-available routing | Specialist-only routing | Proposed dynamic policy |
|---|---|---|---|
| Expected throughput | High immediate starts, but end-to-end throughput is weakened by rework, misrouting, and extra handovers | Good per-case service quality, but queueing at scarce specialists slows flow | Balanced: urgent risky work gets the right expertise, while lower-risk work is spread and quality work is batched |
| SLA risk | Volatile. It may start work quickly, but cases like `C001`, `C007`, and `C016` are exposed to delay from weak skill and later rework | Lower for urgent difficult cases, but can increase when Security/Approval specialists become bottlenecks | Lower overall because it combines specialist routing where necessary with continuity and rebalancing where safe |
| Error/rework risk | Highest, because skill `1` assignments are likely on complex or repeated-loop work if the person is merely available | Lowest immediate error risk, but not always lowest total risk because ownership breaks can add waiting and more reassignments | Lower than first-available and usually close to specialist-only, while avoiding some handover-driven rework |
| Fairness of workload | Can overload the few people who happen to have the lowest open-case count today | Can overload the same specialists repeatedly, regardless of overtime risk | Explicitly balances open cases, hours remaining, and overtime risk, with justified exceptions only |
| Skill development | Accidental rather than planned, and often unsafe | Weak, because learning opportunities are crowded out by specialists | Structured and auditable: training is deliberate, bounded, and linked to documented priorities |
| Continuity of ownership | Weak; owner continuity is mostly incidental | Often weak; the highest-skill person wins even when the current owner is adequate | Strong where continuity risk is high, but not absolute when SLA or compliance needs dominate |
| Resilience to absence or bottlenecks | Superficially flexible, but can hide growing skill mismatch and repeated rework | Brittle; it deepens dependency on a small set of specialists | Better resilience by preserving specialists for truly specialist work and using competent alternatives on safer cases |

The trade-off is intentional. The dynamic policy may sacrifice some short-term purity of specialization and some immediate-start speed on a few cases, but it reduces the known failure modes of both baselines: unsafe weak-skill routing on one side and specialist queue fragility on the other.

# 5. Explanation to workers
Assignments are made in layers, not by a black box and not as a judgment about any one person. First, the system checks what is allowed: required skill, security and approval rules, supervision needs, and whether someone has already received too many new cases in the current batch. After that, it weighs urgency, continuity, current workload, overtime exposure, and planned development goals.

Urgent or risky work is routed to people who can finish it safely. Complex cases usually stay with their current owner when changing hands would likely slow them down or create rework. Normal and low-priority work is where we deliberately create learning opportunities, but only when SLA room exists and a checkpoint, supervisor, or final approver is named. We also avoid pushing extra routine work onto people already at high overtime risk when a safe alternative exists.

Each assignment should carry a short reason such as `urgent specialist routing`, `continuity on high-handover case`, `training with checkpoint`, or `overtime-aware rebalance`. That reason is there so workers can understand the decision, question it when local context is missing, and request an override when the real situation differs from the data.

# 6. Process-mining audit indicators
| Indicator | How to measure from the log | Why it matters |
|---|---|---|
| Handover frequency | Count owner/resource changes within each case; segment by `handover_cost_band`, `case_complexity`, and `concept:name`. Use `discover_handover_of_work_network` to see which transitions are driving handoffs. | Checks whether the policy is really preserving continuity where it should |
| Reassignment count | Track the distribution of `reassignment_count` at assignment events and the share of cases exceeding `2` reassignments | Directly linked to the cited rework and appeal risk increase |
| Skill mismatch | Join assignments to the skill matrix and compute cases where assigned skill is below the preferred threshold, plus whether supervision/finalizer was present when required | Shows whether risky assignments are creeping in even if they remain technically allowed |
| Workload distribution | Compare assignment counts, load index, and queue share by resource/team; report spread measures such as p90/p10 or Gini-like imbalance | Audits fairness and whether the same people are repeatedly absorbing work |
| Overtime risk exposure | Percentage of new assignments sent to `overtime risk = high` resources, broken down by priority and `assignment_reason` | Verifies whether overtime overrides are exceptional rather than routine |
| SLA misses | Miss rate overall and by `assignment_reason`, `required_skill`, `priority`, and assignee skill band; compare assigned slack at dispatch to actual completion | Tests whether the policy is protecting the right cases, not just average flow |
| Rework/appeal after assignment | Share of cases that later enter `Rework Correction` or known appeal outcomes after each routing pattern | Connects assignment choices to downstream quality, not just first-step speed |
| Training assignment share | Percentage of normal/low assignments tagged as training-supporting, separated into `direct`, `supervised`, and `shadow/prep` modes | Audits the 20% development target and whether training is safe rather than cosmetic |
| Specialist bottleneck indicators | Waiting time and queue length for Security/Approval, share of those activities done by top specialists, and concentration of work by resource | Reveals whether the policy is drifting toward specialist-only behavior |
| Deviations from assignment policy | Count cases where logs show rule violations: unsupervised high-priority work below skill `2`, non-compliant security/approval routing, `>4` assignments per batch, batching outside rule, or overtime override without justification | Ensures the actual operating policy matches the stated policy |

**Recommended audit views**

- Compare indicators by `assignment_reason` to see whether each override type is paying off.
- Use `discover_working_together_network` and `discover_activity_based_resource_similarity` to check whether the set of viable backups is broadening or shrinking over time.
- Use `discover_organizational_roles` to see whether real work patterns still match the intended role boundaries.
- Use `discover_batches` on `Quality Check` to verify that batching occurs only for eligible normal/low cases with enough SLA buffer.
- Use service and waiting time statistics before and after deployment to see whether continuity rules reduce the median handover penalty on complex work.

# 7. PM4Py implementation sketch
```python
import pandas as pd
import pm4py

# Load and format
df = pd.read_csv("event_log.csv")
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)
log = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# Add service/waiting-time information for later SLA and handover analysis
log = pm4py.insert_case_service_waiting_time(
    log,
    case_id_key="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)
service_time = pm4py.get_service_time(log)

# Performance structure: useful for activity-level waiting and bottleneck analysis
perf_dfg, start_acts, end_acts = pm4py.discover_performance_dfg(log)

# Resource-network diagnostics
handover_net = pm4py.discover_handover_of_work_network(
    log,
    resource_key="org:resource"
)
working_together_net = pm4py.discover_working_together_network(
    log,
    resource_key="org:resource"
)
resource_similarity = pm4py.discover_activity_based_resource_similarity(
    log,
    activity_key="concept:name",
    resource_key="org:resource"
)
roles = pm4py.discover_organizational_roles(
    log,
    resource_key="org:resource",
    activity_key="concept:name"
)

# Optional visual audit artifacts
pm4py.save_vis_sna(handover_net, "handover_network.png")
pm4py.save_vis_sna(working_together_net, "working_together.png")

# Focused filters for audit slices
security_log = pm4py.filter_event_attribute_values(
    log,
    "concept:name",
    ["Security Review"]
)
approval_log = pm4py.filter_event_attribute_values(
    log,
    "concept:name",
    ["Final Approval"]
)

# Example throughput slice: near-SLA or slow cases
slow_cases = pm4py.filter_case_performance(
    log,
    min_performance=24 * 3600  # example threshold, tune per process
)

# Variant analysis: useful for rework loops and repeated diagnosis/rework behavior
variants = pm4py.get_variants(log)

# Quality batching audit
quality_log = pm4py.filter_event_attribute_values(
    log,
    "concept:name",
    ["Quality Check"]
)
batches = pm4py.discover_batches(
    quality_log,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource"
)

# Join policy metadata and skill matrix for rule-based audits
skill_matrix = pd.DataFrame([
    # org:resource, required_skill, skill_level, overtime_risk, training_priority
])

assignments = log[log["assignment_reason"].notna()].copy()
assignments = assignments.merge(
    skill_matrix,
    how="left",
    on=["org:resource", "required_skill"]
)

# Policy deviation flags
assignments["is_high_prio"] = assignments["case_priority"].isin(["high", "urgent"])
assignments["security_violation"] = (
    (assignments["concept:name"] == "Security Review") &
    (
        (assignments["skill_level"] < 3) &
        (~assignments["assignment_reason"].str.contains("supervis", case=False, na=False))
    )
)
assignments["approval_violation"] = (
    (assignments["concept:name"] == "Final Approval") &
    (assignments["skill_level"] < 2)
)
assignments["high_prio_weak_skill_violation"] = (
    assignments["is_high_prio"] &
    (assignments["skill_level"] < 2) &
    (~assignments["assignment_reason"].str.contains("supervis", case=False, na=False))
)
assignments["overtime_override"] = (
    (assignments["overtime_risk"] == "high") &
    (~assignments["case_priority"].eq("urgent"))
)

# Training-share audit
assignments["training_support"] = assignments["assignment_reason"].str.contains(
    "training|shadow|checkpoint|prepare",
    case=False,
    na=False
)
training_share = (
    assignments[assignments["case_priority"].isin(["normal", "low"])]
    ["training_support"]
    .mean()
)

# Example specialist bottleneck audit
security_assignments = assignments[assignments["concept:name"] == "Security Review"]
specialist_concentration = (

    .value_counts(normalize=True)
)
```

In production, the key design choice is to log not just the chosen assignee, but also the decision context: `assignment_reason`, whether supervision was used, the owner-change flag, the candidate skill level, the workload snapshot at assignment time, and the relevant soft-rule override. That makes the policy explainable to workers and directly auditable with process-mining indicators.
