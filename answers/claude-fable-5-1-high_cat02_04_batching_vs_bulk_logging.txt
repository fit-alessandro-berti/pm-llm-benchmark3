# 1. Cluster diagnoses

Conventions used throughout: "observation" = directly in the table; "derived" = arithmetic on the table; "hypothesis" = a physical explanation that fits the observations; "assumption" = something I add and label. All durations in minutes unless stated. Waiting = `start − queue_arrival`; service = `complete − start`; recording lag = `recorded_at − complete`.

Two cross-cutting observations that shape several rows:

- O-A (minute-aligned "1 sec" sources). G1, G4 and G8 come from sources documented at 1-second precision and `recorded_at` does carry seconds (…:02, …:05, …:06), yet every `start` and `complete` in those three clusters falls exactly on :00 seconds (14 timestamp pairs). Under genuine second-level recording of human or machine events this is essentially impossible by chance; the lifecycle fields are therefore either minute-truncated by the source (precision metadata is wrong for those fields) or generated by a clocked/derived mechanism (e.g. a scan that closes item i and opens item i+1). The `precision` column describes the source, not the field.
- O-B (arrival-after-start in G7). M02–M05 have `start` 14:00 but `queue_arrival` 14:01–14:11, so the recorded start precedes the arrival by 1–11 min. This is physically impossible under a single clock and is the signature of rounding, not of work.

# 3. Consequences for performance analysis

General mechanisms. (i) A shared `start` earlier than the true per-item start deflates waiting and inflates service and utilization. (ii) A shared `complete` later than the true per-item completion inflates service and utilization and hides the true drain order. (iii) A `start` that is copied from the submission time (G6) inflates waiting and deflates service to zero. (iv) Rounding widens or shrinks intervals depending on direction; it never preserves order within a bucket. (v) Any hypothesis that multiplies apparent concurrency for a single-capacity resource makes utilization exceed 100% and flags a phantom bottleneck; any hypothesis that hides concurrency for a pool makes the pool look overloaded per head.

Why G6-like data produces both inflated waiting and near-zero service. The bulk form writes the same clock reading into `start` and `complete`. Waiting is computed as `start − queue_arrival`; because `start` has been pushed to the moment of data entry, every minute between the real closing act and 17:00 is added to waiting. Service is computed as `complete − start`; because the two fields are the same value, service collapses to exactly zero irrespective of how long the closure actually took. The two distortions are the same error seen from both sides: the real service interval is not deleted, it is absorbed into waiting. The tell-tale is that the errors are perfectly correlated (all service = 0, all waits end at the same instant), which no real queue produces. Any downstream utilization (0%) or bottleneck ranking ("closing is free, the queue in front of it is the problem") is therefore an artifact of the form, not of the process.

    # the simplified API reads the interval start from the default 'start_timestamp' column
    res = pm4py.discover_batches(log, merge_distance=merge_distance, min_batch_size=min_batch_size,
                                 activity_key="concept:name", timestamp_key="time:timestamp",

    return pd.DataFrame(rows)

# ---- independent pandas diagnostics ---------------------------------------
def overlap_rate(g):
    g = g.sort_values("start")
    iv = list(zip(g["start"], g["complete"]))
    pairs = [(a, b) for i, a in enumerate(iv) for b in iv[i + 1:]]
    if not pairs:
        return 0.0, 0
    ov = [max(a[0], b[0]) < min(a[1], b[1]) for a, b in pairs]  # strict: touching intervals do not overlap
    events = sorted([(s, 1) for s, _ in iv] + [(c, -1) for _, c in iv], key=lambda x: (x[0], x[1]))
    cur = mx = 0
    for _, d in events:
        cur += d
        mx = max(mx, cur)
    return sum(ov) / len(pairs), mx

def adjacency_rate(g):
    g = g.sort_values("start")
    if len(g) < 2:
        return float("nan")
    return (g["start"].iloc[1:].values == g["complete"].iloc[:-1].values).mean()

rows = []

    ovr, maxc = overlap_rate(g)

What the script shows when run on this data (observations from execution, PM4Py 2.7.x):

- PM4Py labels with `complete` as `time:timestamp` are identical across all seven (`merge_distance`, `min_batch_size`) combinations: G1 Simultaneous; G2 Batching on Start; G3 Batching on End; G4 Sequential batching; G5 Concurrent batching; G6 Simultaneous; G7 Simultaneous; G8 Sequential batching. Stability is expected here because each cluster is one resource–activity group with no gaps larger than 0 s between consecutive intervals, so `merge_distance` never has anything to merge or split; `min_batch_size` up to 4 is below every cluster size. The stability therefore says nothing about physical semantics.
- Swapping in `recorded_at` as completion flips several labels: G1 → Batching on Start (the 1-second spread of insertion times breaks end equality), G7 → Batching on Start (insertion times 14:16–14:20 break the rounded end equality), and G4/G8 → Concurrent batching (the 3–6 s recording lag makes touching intervals overlap). This is the "behaviour under a smaller tolerance" column of Section 2 realised: the category is a property of which field and resolution one feeds in, not of the work.
- The pandas side contradicts PM4Py's "Simultaneous" in two of three cases: G6 has `svc_zero_share` = 1.0 (zero-length intervals) and G7 has four `start_before_arrival` flags, negative median waiting and a `max_queue_len` of 1 that is physically inconsistent with five items arriving over 13 min into a 15-min service. Only G1 has a "Simultaneous" label that survives the independent checks (short and uniform recording lag, arrivals before start, machine resource). G1, G4 and G8 all carry `claims_1s_uses_1min`, the O-A granularity flag.
- `max_concurrency` = 4 for G5 with a documented pool of ≤3 people is the single quantitative contradiction that forces "multitasking or mis-timing" into the G5 diagnosis regardless of how the shared-account question is resolved.

# 5. Robustness and alternative explanations

Resource IDs trusted (one identifier = one worker with capacity 1) versus treated as shared accounts (identifier = pool of unknown size):

- G5 changes category. Trusted: one analyst with 4-way overlap → concurrent work/multitasking, utilization 233%, a flagrant bottleneck. Shared: up to 3 servers → pool utilization ~78%, no bottleneck, but the recorded `resource` cannot enter any per-person analysis, and the fourth simultaneous item still needs an explanation. Neither reading is rejectable with the supplied evidence.
- G3 changes ranking. Trusted: a single reviewer cannot genuinely have four reviews open with 28/20/13/6-minute durations without multitasking, which favours bulk submission (my top choice). If the desktop_form login were shared by several reviewers, the four staggered starts could be four people who all submitted at a joint 11:30 hand-over, and the recorded durations would be roughly true elapsed times. The statement by T-C makes the single-person reading more likely, but it is a testimony, not a log field.
- G2 is nearly invariant: even with several inspectors, a single shared start with per-item staggered completions is still a "begin group" artefact; only the utilization figure would move.
- G6 is invariant in mechanism (bulk form), but with a shared account the waiting-time bounds widen because different clerks may have closed tickets at different times before the form was filled.
- G1, G4, G7, G8 are machine- or scanner-anchored; identity is not the binding uncertainty.

Timestamps exact versus interval-censored by stated precision (and by the O-A finding that "1 sec" lifecycle fields behave as 1 min):

- G7 is the extreme case. Exact reading: five simultaneous 15-min measurements, negative waits. Censored reading (start ∈ [14:00, 14:15), complete ∈ (14:00, 14:15] or [14:15, 14:30) depending on the undocumented rule): waits ∈ [0, ~14), service ∈ (0, 30), concurrency anywhere from 1 to 5. With the extra assumption that recording never precedes completion, complete ≤ recorded_at (14:16–14:20), which shrinks the service range to (0, ~20) and, if work was serial, to ≈4 min per item. Conclusions about G7 are therefore entirely assumption-driven.
- G1 at 1-min censoring: start ∈ [09:00, 09:01), complete ∈ [09:03, 09:04); the four items may have started up to 59 s apart, so "simultaneous" is a minute-resolution statement. It still holds at fixture level (recorded_at 09:03:02–:03 spans one second).
- G4/G8 at 1-min censoring: adjacency becomes an artefact of truncation — a scan at 12:09:04 that closes P01 and opens P02 gives both 12:09; with true seconds, P02 might have started at 12:09:30 after 26 s of handling. Service estimates carry ±1 min error on a 4-min value (±25%) and ±1 min on 7 min (±14%).
- G2/G3/G5 at 1-min censoring: relative orderings within the same minute are lost (e.g. whether A04's start 13:12 truly preceded A02's completion 13:20 is safe, but 1-min gaps are not).
- G6: censoring is irrelevant; the fields are not measurements of the activity at all.

Same temporal pattern, multiple physical explanations (at least three required; six listed):

1. Identical start and identical end (G1, G6, G7): genuine fixture-level batch (G1), bulk data entry with duplicated clock reading (G6), and rounding to a coarse grid (G7). PM4Py labels all three "Simultaneous"; only recording lag, duration (zero vs positive), source type and the arrival/start ordering separate them.
2. Shared start, staggered ends (G2): a group-start button with serial work; genuine parallel inspection of co-located items; or a coarse "start" rounded down to the hour while ends are recorded live (the G7 mechanism applied to one field only).
3. Staggered starts, shared end (G3): bulk submission after serial work; genuine multitasking by one reviewer; several reviewers behind one login finishing at a joint hand-over; or a completion field that is populated by a batch job (e.g. a scheduled commit at 11:30).
4. Perfect adjacency with constant durations (G4, G8): back-to-back serial work by a diligent operator; a derived lifecycle where one scan closes item i and opens item i+1 (idle time hidden inside "service"); or a system that paces/gates releases on a fixed cycle.
5. Overlapping, nested intervals under one identifier (G5): several people on a shared account; one person interrupting and resuming; or "start" meaning "record opened" rather than "work begun", so the intervals overstate concurrency.
6. Long arrival-to-first-start gap followed by a dense drain (G8): capacity loss (safety check); a deliberate release-in-waves policy; or an upstream clock that runs ahead of the local clock (which would also explain the unverifiable 15:35→15:38 gap).

# 6. Data-collection redesign

Prioritised by how much interpretive ambiguity each item removes in this data set (1 = highest).

1. Separate execution timestamps from recording timestamps, and never let a form default one from the other. `start` and `complete` must be captured by an action at the point of work (scan, button, sensor) and must be nullable; if unknown they stay blank rather than being copied from the submission time. This alone removes the G6 zero-duration/inflated-wait artefact and makes "bulk submission" visible as recording lag instead of as fake execution times. Keep `recorded_at` as a mandatory, system-generated field.
2. Store per-event timestamp precision and rounding rule as metadata (e.g. `ts_precision_s`, `ts_rounding ∈ {none, floor, ceil, nearest}`) per field, not per source, and store the unrounded value where the source has it. G7 becomes analysable; the O-A inconsistency (1-sec source, minute-aligned lifecycle) becomes detectable at ingestion.
3. Synchronise source clocks (NTP) and log clock offsets per source per day; record which clock stamped `queue_arrival` versus `start`. Negative waits (G7) and unverifiable gaps (G8 safety check vs repair queue) are otherwise unresolvable.
4. Badge-level or session-level identity behind shared logins: capture the badge/SSO identity at each lifecycle event, or at least a workstation/session id, and keep a resource→capacity table (heads per pool, positions per fixture). G5 becomes interpretable; the G1 fixture capacity of 4 becomes a data attribute rather than folklore.
5. Explicit group/batch identifiers with their own lifecycle: when a "begin group", "folder submit", fixture load or bulk close is used, emit a batch event (`batch_id`, `batch_start`, `batch_complete`, `batch_size`) and link items to it. This lets G1/G2/G3/G6 be modelled as batch servers rather than as coincidences, and lets PM4Py-style detections be validated against declared batches.
6. Per-item start for grouped UIs: add a lightweight "pick up item" action (or infer it from the previous completion and flag it as inferred with a boolean `start_is_derived`). G2 and the scanner-derived starts in G4/G8 then carry an explicit provenance flag.
7. Pause/resume (suspend/resume) lifecycle transitions and unavailability events (safety check, break, downtime) for resources, on the same clock as the item events. This separates blocked time from queueing (G8) and hands-on time from elapsed time in multitasking (G5, G3).
8. Workstation capacity and WIP limits as master data (positions on a fixture, bench slots, maximum open items per analyst). Any observed concurrency above capacity is then automatically a data-quality alert rather than an analyst's judgment call.
9. Retain `sequence_no` and add the client-side event time versus server insert time for every record, so that entry order, entry speed (G7's one-per-minute typing rhythm) and back-dating can be audited.

# 7. Final adjudication

High-confidence interpretation possible now:

- G1: fixture-level simultaneous batch of 4 items per 3-min cycle; use as a capacity-4 batch server. Only caveat is minute-level lifecycle precision and unknown per-item work inside the cycle.
- G4: serial processing with a 4-min inter-scan cycle; throughput and cycle time are reliable, busy/idle split is not identifiable. Flag `start` as derived.
- G8: 35–38 min capacity loss followed by a serial drain at 7 min per item; waiting must be decomposed into blocked and queued components. Requires a clock-offset check against the safety system before the exact outage length is quoted, but the qualitative conclusion is robust.
- G2: start-batching artefact; reconstruct per-item starts as previous completions (labelled assumption) or interval-censor them. After reconstruction the cluster is usable for service and waiting analysis with roughly ±1–2 min uncertainty per item.

Exclude from service-time analysis and interval-censor in queue analysis:

- G6: service time is unobserved (0 is impossible); waiting is bounded by [0, 17:00 − arrival] per ticket. Report sojourn to closure-record only, with the explicit statement that it is an upper bound on operational waiting. Do not let it enter utilization or bottleneck rankings.
- G7: all lifecycle values are rounded; use intervals (start ≥ max(arrival, 14:00), complete ≤ recorded_at) and report ranges, not points. Negative waits must be clipped to the censoring interval, not to zero, and the cluster must not feed a concurrency or utilization metric.
- G3: exclude the recorded completions from service-time statistics; either reconstruct completions as next starts (assumption of serial work, supported by T-C's statement and by the coherent 8/7/7/6 schedule) or censor complete_i ∈ [start_i, 11:30]. Waiting times can be used if starts are confirmed to be recorded live.

Require operational validation before any performance conclusion:

- G5: the shared-account versus multitasking question decides whether the pool is at 78% or a single analyst is at 233%; badge logs, VDI session ids, or a short observation of the team are needed. Until then, report elapsed times per item and total throughput of the pool (4 items in 30 min), and refrain from any per-resource statement.
- G3 (secondary): confirm with T-C whether starts are captured when a folder is opened or typed at submission; this changes waiting-time validity.
- G8 (secondary): confirm the clock offset between the safety system and the repair queue so the outage can be quoted precisely.
- G1/G4/G8 (metadata): confirm with the PLC/scanner owners whether lifecycle fields are minute-truncated or clock-scheduled, so the stated 1-sec precision can be corrected in the source catalogue.

Overall: the PM4Py labels are correct descriptions of the timestamp patterns in all eight clusters and wrong as descriptions of physical execution in at least G6 and G7 ("Simultaneous") and arguably G2 and G3 (the "batching" is in the UI or the submission, not in the work). Three clusters (G1, G4, G8) support quantitative performance analysis with modest caveats; two (G2, G3) support it after a labelled reconstruction; two (G6, G7) support only interval-censored statements; one (G5) supports no resource-level statement until identity is resolved.
