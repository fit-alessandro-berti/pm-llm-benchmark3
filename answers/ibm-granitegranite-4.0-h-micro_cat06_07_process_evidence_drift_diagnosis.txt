## 2. Competing explanations and timeline

**January–March:** The system was stable, with low breach rates and mature labels. No notable drift.

**April:** A major schema change renamed `Initial Diagnosis Completed` to `Diagnostic Assessment Completed`. This caused:
- Immediate label prefix errors.
- Incomplete feature backfill for April records.
- Duplicate events removed only after 20 April, leading to incomplete cohort data.

**May–June:** The label-mapping patch solved the naming issue, but duplicate events persisted. The system stabilized with mature labels and a reduced unknown activity share. No drift detected.

**July:** The remote-routing policy increased V2 usage. This coincided with a shift in breach rates (0.19  0.19) and a drop in label maturity (98%  98%). Concept drift likely due to process mix change.

**August:** The parts supplier's delivery issues began. V3 usage rose (25%  35%), breach rates spiked (0.28  0.31), and median elapsed time for `Order Part -> Part Received` increased (35 h  65 h). This suggests a combination of process and supplier-driven drift.

**September:** Partner Z's share increased to 24%. V3’s breach rate rose (0.30  0.45) and label maturity slowed (82%  55%). Concept drift from population shift and process changes in V3 are likely.

**October:** The outcome API backlog affected breach labels. V3’s breach rate remained high (0.61), but overall breach rates dropped to 0.16. Label delay and censoring are significant, with incomplete cohort data.

## 3. Diagnostic tests

1. **Label-maturity curves and fixed-vintage backtesting:**
   - Expected result under covariate drift: Mature V3 labels should show stable breach rates.
   - Expected result under concept drift: V3 breach rates should diverge from V1/V2.

2. **Recompute after activity-label normalization and duplicate cleaning:**
   - Expected result under label delay/censoring: Correcting labels should reduce unknown activity share and improve breach rate accuracy.
   - Expected result under concept drift: Breach rates should still diverge between variants.

3. **Calibration and discrimination stratified by variant, source, and month:**
   - Expected result under process drift: Calibrated risk predictions should align with observed breaches in V3, showing higher risk.
   - Expected result under label delay: Calibration may appear stable but will not reflect true risk.

4. **Comparison of process variants and DFG/performance-DFG edges:**
   - Expected result under process drift: DFG and performance-DFG edges will show significant delays in V3.
   - Expected result under label delay: DFG/performance-DFG edges may appear stable despite delays.

5. **Tests of whether the outcome relationship conditional on the same path changed:**
   - Expected result under concept drift: Conditional breach rates for V3 will differ from V1/V2.
   - Expected result under label delay: Conditional breach rates may appear stable.

6. **Population reweighting or transport-style checks for Partner Z:**
   - Expected result under population shift: Model performance for Partner Z should improve with reweighting.
   - Expected result under label delay: Performance may not improve without addressing labels.

7. **Feature missingness and lineage audits:**
   - Expected result under covariate drift: Missing delivery-time features should correlate with increased breach rates.
   - Expected result under concept drift: Missing features should not fully explain changes in breach rates.

## 4. Recalibration-versus-retraining decision

- **April:** Immediate containment needed. Fix the pipeline issue by backfilling missing features and normalizing labels.
- **May–June:** Perform short-term recalibration focusing on V2 and V3. Avoid training until pipeline issues are resolved.
- **July–August:** Implement variant-specific recalibration for V2 and V3, given the process and supplier-driven drift.
- **September–October:** Conduct full retraining with stratified data, ensuring labels are mature and pipeline issues are resolved. Consider segment-specific models for V3 and Partner Z.

## 5. Monitoring architecture

1. **Predictive Monitor:** Tracks breach rate trends and alerts on significant deviations.
2. **Calibration Monitor:** Ensures predicted risk aligns with actual breach rates across variants.
3. **Label-Maturity Monitor:** Tracks the proportion of mature labels by month and variant.
4. **Data-Quality Monitor:** Detects missing activities, duplicate events, and feature completeness.
5. **Process-Variant Monitor:** Observes changes in the proportion of V1, V2, and V3 usage.
6. **Performance-DFG Monitor:** Monitors elapsed times across process variants and edges.
7. **Population Monitor:** Tracks changes in population segments (e.g., Partner Z) and their impact on performance.
8. **Intervention/Deployment Monitor:** Alerts on the need for model updates or process adjustments.

**Python code sketch for monthly process-evidence extraction:**

```python
import pandas as pd
import pm4py

# Read data
df = pd.read_csv('field_service_events.csv')

# Normalize labels
df['normalized_label'] = df['label'].replace({'Initial Diagnosis Completed': 'Diagnostic Assessment Completed'})

# Filter events within a month
def filter_month(df, month):
    return df[ (df['event_timestamp'].dt.month == month) & (df['event_timestamp'].dt.year == 2026) ]

# Extract DFG
def extract_dfg(df, month):
    return pm4py.discover_dfg(df, event_stream=filter_month(df, month))

# Extract performance DFG
def extract_perf_dfg(df, month):
    return pm4py.discover_performance_dfg(df, event_stream=filter_month(df, month))

# Extract variants
def extract_variants(df):
    return pm4py.discover_variants(df, event_stream=df)

# Extract temporal features
def extract_temporal_features(df):
    return pm4py.extract_temporal_features_dataframe(df)

# Monthly summaries
for month in range(1, 11):
    print(f"Month {month}:")
    dfg = extract_dfg(df, month)
    print(f"DFG shape: {dfg.shape}")
    perf_dfg = extract_perf_dfg(df, month)
    print(f"Performance DFG shape: {perf_dfg.shape}")
    variants = extract_variants(df)
    print(f"Variants: {variants}")
    temporal_features = extract_temporal_features(df)
    print(f"Temporal features shape: {temporal_features.shape}")
```

## 6. Risks of acting on the wrong diagnosis

1. **Retraining on Immature Labels:** This could lead to biased risk predictions, especially for V3 cases. Mitigation: Perform fixed-vintage backtesting and only use mature labels for training.

2. **Calibrating Around a Pipeline Bug:** If the calibration is based on flawed predictions, the model may appear well-calibrated but still provide inaccurate risk assessments. Mitigation: Validate calibration against a held-out mature dataset before deployment.

3. **Ignoring Genuine Supplier-Driven Concept Drift:** Failing to account for the parts supplier issue could result in underestimating breach risks for V3 cases. Mitigation: Incorporate supplier reliability metrics and consider transport-style feature reweighting.

4. **Partner Z Population Shift Without Stratified Evidence:** Treating Partner Z’s shift as model unfairness without evidence could lead to biased resource allocation. Mitigation: Conduct stratified analysis, reweighting, and consider variant-specific models to ensure fairness and accuracy.
