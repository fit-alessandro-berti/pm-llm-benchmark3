# 1. Objectives and constraints

## Optimization objectives (multicriteria, not singleobjective)
- **Shortterm throughput**: reduce waiting by assigning work quickly to available, capable resources.
- **Quality / error prevention**: match required skill and avoid unsupported trainee execution.
- **Workload fairness**: spread new assignments, protect colleagues at high overtime risk.
- **Skill development**: use safe cases to support documented training priorities.
- **Continuity of ownership**: avoid unnecessary handovers, especially on highcomplexity / highhandovercost cases.
- **SLA risk control**: urgent/high cases must be routed to resources who can finish in time.
- **Resilience**: avoid overloading the few specialists in bottleneck skills (Security, Approval, Rework).

## Hard / safety / compliance constraints
1. Skill eligibility: `skill = 0` excludes a resource from that activity.
2. High/urgent priority cases cannot go to skill `<2` unless explicitly supervised by a specialist.
3. Security Review: only skill `3`, or skill `1–2` under explicit supervision by `R7_Gita` or `R8_Hugo`.
4. Final Approval: only skill `2–3`; skill `1` may prepare but not finalize.
5. Quality batching allowed only for `normal/low` priority and `SLA > 24h`.
6. Max **4 new assignments** per resource in a decision batch.
7. Avoid assigning new work to `overtime risk = high` resources unless SLA is urgent and no safer alternative exists.

## Soft / preference tradeoffs
- Continuity vs. load balancing: keeping the current owner avoids handover cost but may concentrate work.
- Specialistonly vs. trainee development: specialists reduce errors but block development and create queues.
- Batched execution improves throughput but reduces flexibility.
- Supervision pairs improve compliance but consume specialist capacity.

There is **no single obvious optimum**; the policy below makes explicit tradeoffs between these dimensions.

# 2. Assignment policy

## Algorithm / pseudocode

```text
INPUT: queue Q, resource table R, current ownership, SLA, complexity,
       handover_cost, reassignment_count, training_priority, overtime_risk

PARAMETERS (adjustable weights, not throughput-only):
  w_sla, w_skill, w_cont, w_fair, w_train, w_resil

FOR each case c IN Q ORDER BY SLA_urgency DESC:
  1. ELIGIBILITY FILTER
     candidates = { r IN R | skill(r, c.required_skill) > 0 }
     IF c.priority IN {urgent, high}:
         candidates = { r | skill >= 2 OR
                        (skill >= 1 AND supervisor_available(r, c)) }
     IF c.required_skill == "Security":
         candidates = { r | skill == 3 OR
                        (1 <= skill <= 2 AND r.supervisor IN {R7_Gita, R8_Hugo}) }
     IF c.required_skill == "Approval":
         candidates = { r | skill >= 2 }   # rule 7
     EXCLUDE candidates where overtime_risk == high
         UNLESS c.priority == urgent AND no other eligible resource

  2. PERCANDIDATE SCORING
     FOR r IN candidates:
        U = SLA_urgency_score(c)                # urgent>high>normal>low
        S = skill_score(r, c.required_skill)     # 1..3, +0.5 if supervised trainee
        H = continuity_score(c, r)
            # +2 if r == current_owner and skill OK
            # -handover_cost_weight(c) if owner changes
            # extra -1 if reassignment_count(c) >= 2 and owner changes
        W = fairness_score(r)
            # -open_cases(r), -new_assign_count(r),
            # penalty if overtime_risk == medium/high
        T = training_score(r, c)
            # +1 if r.training_priority == c.required_skill and overtime != high
            # +0.5 if supervised trainee on non-high priority
        B = resilience_score(r, c)
            # penalty if r is one of few specialists for c and already loaded

        score(r) = w_sla*U + w_skill*S + w_cont*H
                   + w_fair*W + w_train*T + w_resil*B

  3. SELECTION
     r* = argmax score(r)
     TIEBREAK: lowest current open cases, then most hours remaining, then resource id

  4. BOOKKEEPING
     new_assign_count[r*] += 1
     IF new_assign_count[r*] > 4: mark r* ineligible for remaining cases
     IF supervision needed: register supervised pair (r*, supervisor)

OUTPUT: assignment map, supervision map, assignment_reason
```

## Explanation of scoring components
- **SLA urgency scoring**: bands `urgent / high / normal / low` converted to numeric weights.
- **Skillmatch scoring**: rewards competent/specialist execution and supervised trainee execution.
- **Continuity / handover scoring**: protects current owner when skill is sufficient; penalises changes on `high` handovercost or alreadyreassigned cases.
- **Workload / overtime fairness**: subtracts opencase load and adds stronger penalty for `high` overtime risk.
- **Training / development**: bonus when the case safely develops a documented training priority.
- **Resilience / bottleneck avoidance**: penalises piling more work on the few `skill = 3` resources in Security/Approval/Rework when alternatives exist.
- **Exception handling**: if no eligible nonhighovertime resource remains for an urgent case, allow highovertime resource and log a `deviation`.

# 4. Comparison with baseline policies

| Dimension | Firstavailable routing | Specialistonly routing | Proposed explainable dynamic policy |
|---|---|---|---|
| **Expected throughput** | Highest shortterm assignment speed, but later rework delays | Lower shortterm speed due to specialist queues | Moderate; batches and continuity preserve realistic throughput |
| **SLA risk** | High for urgent/specialist tasks: may assign Approval to skill 1 or Security to unsupervised skill 1 | Good for urgent (specialists), but nonurgent queues behind few specialists | Controlled: urgent/high kept with capable owners; normal tasks balanced |
| **Error / rework risk** | High: skill mismatches, trainee without supervision, extra reassignments | Lowest skillmismatch, but reassignment of alreadyowned cases adds handover errors | Lower than firstavailable; avoids unsupported trainees and excess reassignments |
| **Fairness of workload** | Poor: lowestload resources absorb everything regardless of skill | Poor: specialists overloaded, others idle | Better: highovertime resources offloaded, new work spread |
| **Skill development** | Random, often unsafe | None (no trainee use) | Deliberate and safe (e.g., C009); limited here by skill/overtime constraints |
| **Continuity of ownership** | Worst: ignores current owner and handover cost | Mixed: often reassigns to highestskill even when current owner is competent | Strong: keeps owners unless skill/supervision forces change |
| **Resilience / bottlenecks** | Ignores bottleneck skills | Creates Security/Approval/Rework bottlenecks | Actively avoids piling all specialist work on R7/R8/R6 alone |

**Tradeoff summary:**  
Firstavailable maximises immediate assignment but violates compliance and increases rework. Specialistonly improves quality but harms fairness, development, and resilience. The proposed policy accepts slightly more planning effort and a few supervised exceptions in exchange for safer SLA outcomes, fairer load, and preserved continuity.

# 5. Explanation to workers

> **Why did my case get assigned this way?**
>
> - **If your case is urgent or highly complex, we try to keep it with the colleague who already knows it**, unless they are not allowed to do the task alone. This avoids costly handovers and protects the customer relationship.
> - **When a colleague is already at high overtime risk, we move routine or normalpriority work to someone with more capacity**, so we do not burn out the team and everyone stays safer on SLA.
> - **Specialist tasks such as Security and Final Approval are only done by colleagues with the right level or with a specialist watching**, because mistakes there are expensive.
> - **Training is built in where it is safe**: for example, a routine diagnosis is left with a trainee who is building diagnosis skills, while an urgent approval goes to an experienced approver.
> - **Batching is used for lowrisk quality checks** so that two similar cases are handled together, saving time without hurting the customer.
> - **Supervision is not a punishment**; it is a way to let someone learn or to keep a case safe when the owner is not yet a specialist.
>
> The system does not just “give work to the first free person.” It looks at skills, deadlines, how many times a case has already moved, and who is overloaded, then explains the choice in the `assignment_reason` field.

# 6. Processmining audit indicators

Using the event log columns (`org:resource`, `current_owner`, `reassignment_count`, `handover_cost_band`, `workload_snapshot`, `assignment_reason`, `sla_deadline`, `required_skill`, `case_priority`), audit the deployed policy with at least:

1. **Handover frequency** – count of `org:resource` changes within a case; compare against `discover_handover_of_work_network`.
2. **Reassignment count** – distribution of `reassignment_count`; alert when >2 (historical rework risk).
3. **Skill mismatch** – compare `required_skill` with discovered role/skill level; flag assignments where skill < required band.
4. **Workload distribution** – track `workload_snapshot` / open cases per resource; check Gini or maxmin fairness.
5. **Overtime risk exposure** – number of new assignments to resources with `overtime risk = high` (should be near zero except urgent deviations).
6. **SLA misses** – cases where event timestamp exceeds `sla_deadline`; slice by priority and assignment reason.
7. **Rework / appeal after assignment** – frequency of subsequent `Rework Correction` or appeal activities per original owner.
8. **Training assignment share** – proportion of assignments where `assignment_reason` mentions training and resource `training_priority` matches activity.
9. **Specialist bottleneck indicators** – queue length and waiting time for activities where only few resources have skill 3 (Security, Approval, Rework), using `discover_performance_dfg` and `get_service_time`.
10. **Deviations from assignment policy** – cases where `assignment_reason` contains “exception/deviation” or where predicted policy score differs from actual logged assignment; monitor via `get_variants` and manual review.
