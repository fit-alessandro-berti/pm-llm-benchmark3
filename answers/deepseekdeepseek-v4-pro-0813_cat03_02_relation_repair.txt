## 1. Consistency rules and evidence model

- **Hard invariant**
  - H1. Every E2O relation must refer to an existing event ID and an existing object ID. Every O2O relation must refer to two existing object IDs.
  - H2. Duplicate identical relations are not allowed.
  - H3. O2O qualifiers are directional: `DEL-X carries PK-7` is not equivalent to `PK-7 carries DEL-X`.

- **Strong default**
  - S1. `Create Order` normally has exactly one Order object.
  - S2. `Add Item` normally has one Order and one Item.
  - S3. `Pack Item` normally has one Item and one Package, unless a scanner outage creates an item-only row.
  - S4. `Dispatch Package` normally has one Package and one Delivery; bulk dispatch may cover multiple packages.
  - S5. `Confirm Delivery` may concern a delivery, multiple deliveries, or only a customer/order if the carrier identifier is lost.
  - S6. `Issue Invoice` has one Invoice and one or more Orders. Arithmetic equality is supporting evidence, not proof.
  - S7. `Record Payment` has exactly one Payment and normally one Invoice, but unapplied cash is possible.

- **Weak heuristic**
  - W1. Identifier similarity or prefix/wildcard matching between event attributes and object IDs is informative.
  - W2. Timestamp closeness and lifecycle order increase plausibility.
  - W3. Matching customer or route increases plausibility.
  - W4. Amount equality with declared values or invoice totals is suggestive, not decisive.
  - W5. A candidate repair is stronger if it also preserves existing O2O direction and cardinality.

- **Evidence against a repair**
  - E1. The event’s `observed_related_objects` already omits the candidate object, especially when the event has another plausible object.
  - E2. The repair would create a suspicious mixed-order package or otherwise unusual lifecycle.
  - E3. The relation is supported only by arithmetic equality, such as invoice or payment total matching.
  - E4. The identifier is uncertain, such as `N-421?` or `N-42*`.
  - E5. The repair would force an object into a complete lifecycle without direct event evidence.

I combine these by treating the observed relations as anchors. For each missing candidate, I ask whether there is a direct event attribute pointing to a specific object, whether the lifecycle order permits the relation, whether the relation creates a cardinality problem, and whether the amount/customer/route evidence merely corroborates a relation already suggested by identifiers. Direct identifiers such as `PK8-2` or `N-421?` are treated as stronger than arithmetic matching. When only arithmetic or wildcard evidence exists, I leave the relation unresolved or mark it provisional.

## 8. Over-repair warnings

1. **Forcing ev11 to confirm both deliveries**  
   Adding ev11  DEL-X and ev11  DEL-Y makes the delivery lifecycle look complete. If the portal actually lost the carrier identifier and ev11 was only an order-level confirmation, this fabricates delivery confirmation and inflates on-time-delivery behavior.

2. **Forcing ev08 into PK-8 without acknowledging the mixed-order package**  
   The repair creates a package containing items from ORD-A and ORD-B. If that is false, process mining will manufacture a material-flow interaction between two orders and may hide an unrecorded reconciliation of a scanner-outage row.

3. **Forcing INV-44 to bill ORD-B purely because 130 + 100 = 230**  
   This can falsely make ORD-B appear invoiced and paid. If the invoice total included fees, discounts, taxes, or an unrecorded adjustment, the repair would corrupt revenue and order-level performance views.

4. **Forcing PAY-2 to settle INV-44 purely because 100 + 130 = 230**  
   This can hide unapplied cash or a different receivable. It would make an open invoice appear closed and misclassify the payment type.

5. **Adding delivery confirmation to both orders and both deliveries**  
   This can duplicate one event across several objects. In flattened logs, one `Confirm Delivery` event may appear once for ORD-A, once for ORD-B, once for DEL-X, and once for DEL-Y, inflating activity frequencies and making one physical action look like multiple confirmations.

6. **Creating O2O edges only to mirror assumed E2O edges and then treating them as independent**  
   For example, `ev08 -> PK-8` and `PK-8 packs IT-B1` both come from the same scanner evidence. Treating the O2O edge as independent confirmation would produce false confidence in a provisional repair.

7. **Completing every lifecycle by default**  
   The dataset intentionally has missing relations. Completing all Orders, Deliveries, Invoices, and Payments may remove exactly the exceptions that matter: scanner outages, unapplied cash, partial delivery, or lost portal identifiers. A conservative repair should preserve some incompleteness.
