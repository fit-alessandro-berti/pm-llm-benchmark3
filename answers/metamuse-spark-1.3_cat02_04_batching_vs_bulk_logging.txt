Key comparative insight: identical `start` + staggered `end` (G2) and staggered `start` + identical `end` (G3) are mirror images. Both can arise from (a) true concurrent work with common start/end plus varied service, or (b) true sequential work with one side logging-collapsed. Adjacency test distinguishes: if ends/start stagger equals plausible service cadence (G2: 6-8 min, G3: 6-8 min, G4/G8: 4/7 min), sequential-batch logging is more parsimonious than assuming service times exactly mimic sequential gaps by coincidence.

# 3. Consequences for performance analysis

General mechanism: `waiting = start - queue_arrival`, `service = complete - start`, `utilization = busy time / available time`, bottleneck = where waiting piles or service appears long. Logging batches corrupt one or both terms. PM4Py batch labels detect temporal proximity, not which term is corrupt.

- G1 (genuine parallel batch): Waiting 2-6 min (09:00 minus 08:54-08:58) is real queue for fixture; service 3 min is batch cycle, not per-item 3 min serial. Bias if misread as serial: dividing by 4 underestimates throughput (true 4 per 3 min); treating as 4 overlapping 3-min tasks overstates single-resource utilization 4x. If misread as sequential with start batching, service underestimated per item. Correct: model RBT-7 capacity 4, batch service 3 min. Bottleneck analysis valid if capacity annotated.
- G2 (common start masks sequential): Waiting using logged 10:00 overstates for later items if true work started later; e.g., S04 waiting logged as 6 min (10:00-09:54) but true waiting ~27 min if served fourth (10:21 start). Service using logged start overstates: S04 logged 27 min vs true ~6 min. Utilization of T-B appears 100% overlapped (4x concurrent) vs true ~100% serial busy 10:00-10:27 — same busy span but wrong concurrency (claims multitask). Bottleneck: inflates service-time variance, may falsely flag inspection as slow multitasked station. Correction restores uniform ~6-8 min service.
- G3 (common completion masks sequential): Waiting understated or correct for early items if start true, but service overstated for early items and understated for late if complete is submit: E01 logged 28 min vs true ~8 min; E04 logged 6 min vs true ~6 min (last item least biased). Utilization appears bursty concurrent at end. Bottleneck falsely flags review duration variance and end-of-period overload. Estimates: true busy likely 11:02-11:30 continuous; logged view shows 4 parallel 6-28 min tasks.
- G4 (clean serial chain): No material bias. Waiting 3-7 min (start minus arrival: e.g., P05 19 min? compute: 12:21-12:02=19 min — grows as queue drains, normal FIFO). Service stable 4 min. Utilization ~100% 12:05-12:25. Bottleneck signal trustworthy. Calling it sequential batching does not bias if modelled as single-server FIFO. Only bias if forced into parallel-batch model.
- G5 (shared account): If trusted as one analyst, overlap implies multitasking: service times 15-25 min overlapping suggests inflated utilization >100% (e.g., 4 concurrent = 400% at 13:12-13:20) and false concurrency bottleneck. Waiting (13:00-12:45=15 min etc.) mixes queues of different humans. If split across 2-3 analysts, per-person utilization normal, waiting shorter. Direction: single-ID assumption inflates utilization and overlap rate, distorts service distribution (mixes workers). Must not rank analysts or do conformance on resource.
- G6 (bulk close): Creates both inflated waiting and near-zero service simultaneously — explicitly: waiting = 17:00 minus 14:05-16:25 = 35-175 min appears as huge queue, but part is real queue (tickets open) and part is unmeasured work time collapsed into logging delay; service = 17:00-17:00 = 0 appears as instantaneous efficiency. Mechanism: true `start`/`complete` replaced by form-submit time; execution interval censored entirely. Utilization appears 0 then 7 closes in 1 min (infinite throughput). Bottleneck falsely flags upstream queue (long wait) while hiding close-work capacity (zero service). Throughput spike 7/min is logging throughput, not physical. Conformance: false long-wait violations + false instant-service compliance.
- G7 (coarsening to 15 min): Waiting quantized to ±15 min (e.g., M01 2 min true vs 2 min logged coincidentally; M05 arrival 14:11 start logged 14:00 gives negative -11 min waiting if naively computed). Service uniformly 15 min hides variance; utilization appears 100% parallel (5x) vs unknown true (likely serial 5x~? inside bin). Bottleneck: false synchrony suggests batch station and masks true order/cadence. Any percentile or critical-path analysis invalid at <15 min scale.
- G8 (downtime queue + serial): Waiting 30-65 min (e.g., Q01 38 min) is largely starvation 15:00-15:38, not congestion from slow service; service stable 7 min after resumption is trustworthy. Bias if downtime ignored: attributes waiting to triage capacity (false bottleneck at T-H) and inflates mean waiting; if clock offset ignored, waiting bound uncertain by minutes. Utilization 0% then 100% 15:38-16:13 correctly shows capacity loss then drain, but only if idle gap annotated with safety-check. Throughput 0 then 1 per 7 min is recovery, not steady rate.

# 5. Robustness and alternative explanations

- Resource IDs trusted vs shared: If `analyst_pool` trusted as one worker, G5 overlap rate 1.0 with varied starts implies 4-way multitasking, utilization >100%, service 10-20 min concurrent. If treated as shared (context: up to 3 analysts), same overlap implies 2-3 parallel workers with normal utilization; no multitasking inference allowed. Similarly, if RBT-7 trusted as machine with capacity 4, G1 overlap is expected parallelism; if mistrusted as single human, G1 would be flagged impossible concurrency. G2/G3/G4/G8 singletons T-B/T-C/T-D/T-H are plausibly single humans — trusting them supports sequential reconstruction; treating them as potentially shared would reopen concurrent-team explanations (e.g., G2 four inspectors starting together) but context (single begin button, single reviewer statement) argues against. Recommendation: report both: trusted-ID utilization and shared-ID-censored utilization; exclude G5 from per-resource benchmarks until badge resolved.
- Timestamps exact vs interval-censored by precision: If exact, G7 14:00-14:15 x5 is a perfect simultaneous batch and G6 17:00 zero-duration is instantaneous work. If interval-censored (±0.5 sec for 1-sec, ±30 sec for 1-min, ±7.5 min for 15-min with unknown rounding direction), G7 collapses: true starts/ends could lie anywhere in quarter-hour bins, ordering lost, waiting/service have ±15 min bounds (including negative naive waiting). G2/G3 1-min equality/adjacency becomes uncertain to ±1 min: G4/G8 1-sec adjacency (exact chain) survives, but G2/G3 sequential gaps 6-8 min survive coarsening (larger than precision) while simultaneity claims weaken. G6 zero-duration under 1-min censoring means true service in [0,2) min per case plus unknown distribution across afternoon — still bulk, but waiting bounds widen. Robust rule: only assert patterns larger than precision; censor G7 entirely, keep G1/G4/G8 point estimates, downgrade G2/G3/G5/G6 service to intervals.
- At least three patterns with multiple physical explanations:
  1. Start-equal + end-equal (G1 vs G6 vs G7): genuine parallel fixture (G1), bulk-form replication (G6), coarse rounding to same bin (G7). Same PM4Py simultaneous-batch label, three physics. Discriminators: capacity metadata, recorded_at spread, precision, arrival spread.
  2. Start-equal + end-staggered (G2): (a) concurrent multitask with common setup, (b) sequential work with group-start logging, (c) single begin-button UI artifact with true serial completions. Discriminators: completion gaps matching service cadence and UI context favor (b/c) over (a).
  3. End-equal + start-staggered (G3): (a) concurrent work with common submit/deadline, (b) sequential work with deferred folder submission, (c) batch oven/fixture finishing together despite staggered loading. Discriminators: adjacency of starts to prior gaps and reviewer testimony favor (b); without testimony (a) and (c) remain viable.
  4. Extra: heavy overlap with varied starts/ends (G5): (a) one-worker multitasking, (b) multi-worker shared login, (c) long parallel cases with queue. Discriminators require badge data; timestamps alone cannot decide.
  5. Idle gap then chained sequence (G8): (a) downtime capacity loss then FIFO drain, (b) late shift start / operator unavailability, (c) clock offset between queue and execution systems. Discriminators require synced clocks and downtime log join.

# 6. Data-collection redesign

Prioritized, concrete:

1. Execution vs recording separation (highest): mandate two non-nullable fields per event — `execution_start`, `execution_complete` (operator/machine asserted) and `recorded_at` (system insertion, auto). For bulk forms, require per-case execution times or explicit null with reason code (deferred entry), never default to submit time. Backfill rule: reject zero-duration bulk submits at entry.
2. Group/batch identifiers: add `batch_id` / `group_id` + `batch_size` + `batch_role` (parallel fixture vs serial folder vs logging-only group). RBT-7 PLC should emit fixture-cycle ID linking 4 cases; tablet begin-group should emit group ID but retain per-case actual start (or null); desktop folder submit should emit folder ID separate from per-review complete.
3. Resource/badge identity: replace shared logins (`analyst_pool`, generic tablets) with badge tap / SSO per case; retain both `login_id` and `person_id` + `station_id`. For automation, log `equipment_id` + `fixture_position` + `capacity`. Without this G5-class ambiguity persists.
4. Workstation capacity and setup metadata: master data for parallel capacity (RBT-7=4), single-server flags (T-B/T-D/T-H/T-C=1), setup vs processing split. Enables correct utilization (batch service counted once, not n times).
5. Pause/resume and downtime events: first-class `downtime_start/end`, `pause`, `safety_check`, `break` with synced NTP clocks; joinable to queue build-up (would validate G8). Require clock-sync health flag per source.
6. # 7. Final adjudication

- High confidence interpretable (use with annotation): G1 genuine simultaneous batch (use as parallel batch, capacity 4); G4 clean serial flow (use as-is for waiting/service/utilization benchmark); G6 bulk submission (confidently a logging artifact — usable only as upper bound on completion and demonstration of bias, not as performance).
- Exclude or interval-censor in queue analysis: G6 exclude service/utilization entirely, censor waiting to [arrival, 17:01] bound; G7 censor both start and complete to 15-min intervals, exclude from any <15-min service/waiting ranking; G2 start-censor (replace logged start with sequential inference or interval), G3 completion-censor (treat 11:30 as submit). Overall: do not equate PM4Py batch detection with physical batching.
