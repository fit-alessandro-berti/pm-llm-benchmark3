# 1. Objectives and constraints

## Optimization objectives (soft, ordered by stakeholder priority)

The policy does not have a single objective. It balances seven goals that frequently pull in different directions:

1. **SLA compliance** — minimize late completions; urgent/high-priority cases must start promptly.
2. **Skill match / quality** — the assigned resource must be capable enough to do the work correctly first time, reducing rework and appeals.
3. **Case continuity** — minimize owner changes; historical evidence shows that handovers on high-complexity cases add ~2.7 h waiting and that >2 reassignments correlate with 1.8× rework and 1.4× appeals.
4. **Throughput** — keep cases moving; balanced queues, avoid idle resources.
5. **Workload fairness & overtime exposure** — distribute load, protect high-overtime-risk workers, cap assignments at 4 per batch.
6. **Skill development** — at least 20 % of normal/low-priority assignments should advance documented training priorities when SLA risk permits.
7. **Resilience / bottleneck avoidance** — no single team or specialist should be a single point of failure.

These objectives are explicitly *not* collapsed into one scalar for the final answer; the scoring function below weights them, but the trade-offs are discussed qualitatively in § 4.

PROCEDURE AssignCases(queue, resources, skill_matrix, batch_context)


# ---------- STEP 1 — ORDER CASES BY URGENCY ----------
sort queue by:  priority(urgent > high > normal > low),
                then SLA_remaining ascending,
                then complexity descending

# ---------- STEP 2 — ELIGIBILITY FILTERING ----------
FOR each case C in sorted_queue:

    candidates  empty set

    FOR each resource R:

        s  skill_matrix[R][C.required_skill]

        # H1: absolute skill filter
        IF s == 0 THEN CONTINUE

        # H2: security supervision rule
        IF C.activity == "Security Review" AND s < 3 THEN
            IF NOT (R is C.current_owner AND supervision_by(R7_Gita|R8_Hugo) feasible)
            THEN CONTINUE

        # H3: approval rule
        IF C.activity == "Final Approval" AND s < 2 THEN
            CONTINUE                      # skill-1 may prepare, not assign

        # H4: priority-skill floor
        IF C.priority IN {urgent, high} AND s < 2 THEN
            IF NOT supervision_available(C.required_skill)
            THEN CONTINUE

        # H5: batch assignment cap
        IF new_assignments(R) >= 4 THEN CONTINUE

        # S2: overtime guard (soft, but hard-filtered when safer alt exists)
        IF R.ot_risk == "high" AND C.sla_remaining > "4h"
           AND exists_safer_alternative(C, R)
        THEN CONTINUE

        candidates.add(R)

    IF candidates is EMPTY:
        # --- exception handling ---
        LOG violation, ESCALATE to supervisor
        IF C.priority IN {urgent, high}:
            ALLOW OT-high resource if it is the only option
            FLAG for manual approval
        CONTINUE (hold case in queue)

    # ---------- STEP 3 — SCORING ----------

    FOR each R in candidates:

        score  0

        # (a) SLA urgency — dynamic weight by priority
        w_sla  {urgent: 0.35, high: 0.25, normal: 0.15, low: 0.10}[C.priority]
        urgency  1 / (C.sla_remaining_hours + 0.5)        # smaller SLA  higher
        score += w_sla × urgency × 10                      # scale to comparable range

        # (b) skill-match score
        w_skill  0.20
        score += w_skill × (s / 3.0)

        # (c) continuity / handover-cost score
        w_cont  0.20
        IF R == C.current_owner THEN
            multiplier  {high: 1.5, medium: 1.2, low: 1.0}[C.handover_cost_band]
            IF C.complexity > 0.7 AND C.handover_cost_band == "high"
            THEN multiplier  2.0                         # S1 reinforcement
            score += w_cont × 1.0 × multiplier
        ELSE
            score += w_cont × 0.0                         # no continuity benefit

        # (d) workload & overtime fairness score
        w_load  0.10
        load_norm  1 / (R.open_cases + 1)
        ot_factor  {low: 1.0, medium: 0.6, high: 0.2}[R.ot_risk]
        score += w_load × load_norm × ot_factor

        # (e) training / development score  (only for normal / low priority)
        w_train  0.10
        IF C.priority IN {normal, low} THEN
            IF R.training_priority == C.required_skill
               AND sla_sufficient_for_training(C)
            THEN score += w_train × 1.0
            ELSE score += w_train × 0.0
        ELSE
            score += w_train × 0.0                         # never for urgent/high

        # (f) resilience / bottleneck avoidance
        w_res  0.05
        team_pressure  current_batch_load[R.team] / total_queue
        score += w_res × (1.0  team_pressure)

        total[R]  score

    # ---------- STEP 4 — TIE-BREAKING (lexicographic) ----------
    best  resource in candidates maximising:
        1. total[R]                                  # primary: composite score
        2. (R == C.current_owner) ? 1 : 0            # continuity tie-break
        3. ot_rank(R) where low=2, medium=1, high=0  # overtime tie-break
        4. R.open_cases                             # lighter load
        5. s (higher skill)                          # quality tie-break

    # ---------- STEP 5 — EXCEPTION / SUPERVISION CHECK ----------
    IF C.activity == "Security Review" AND s < 3:
        supervisor  pick_available(["R7_Gita", "R8_Hugo"])
                     preferring lower open_cases, then lower OT risk
        RETURN Assignment(C, resource=R3, supervisor=supervisor)

    IF C.priority IN {urgent, high} AND s < 2:
        supervisor  find_qualified_supervisor(C.required_skill)
        RETURN Assignment(C, resource=R3, supervisor=supervisor)

    RETURN Assignment(C, resource=best, supervisor=none)
```

**Design notes:**

* **Weights are not static** — the SLA weight scales up for urgent cases, and the continuity multiplier amplifies on high-complexity / high-handover-cost cases (mirroring the 2.7 h evidence).
* **Training is gated**: the training bonus only activates for normal/low priority and only when SLA headroom exceeds a configurable threshold (e.g., SLA remaining > 2 × estimated service time).
* **Resilience** is a light but real term: if one team already absorbs a disproportionate share of the batch, remaining cases steer toward other teams *when skill permits*.
* **Exception handling** always prefers a documented supervisor over an unsafe solo assignment; if no option exists, the case is escalated rather than silently mis-assigned.

# 4. Comparison with baseline policies

## 4.1 Characteristic behavior of each baseline

| | First-available | Specialist-only | Proposed policy |
|---|---|---|---|
| Routing logic | Lowest open-case count, skill  0 only | Highest skill for required skill, tie-break by open cases | Weighted multi-objective score (SLA, skill, continuity, load, OT, training, resilience) with hard rule filtering |
| Typical pattern | Sprays work to lightly-loaded team (Quality, Risk) regardless of expertise | Concentrates all SecurityHugo/Gita, all ApprovalFarid, all DiagnosisDavid/Celine | Keeps most owners, intervenes only where evidence supports it (3 reassignments in this batch) |

## 4.2 Dimension-by-dimension comparison

### Expected throughput
| Policy | Assessment |
|---|---|
| **First-available** | **Highest raw throughput in the short term.** Lightest-loaded resources start immediately, minimizing queue length. However, skill mismatches cause rework loops that erode throughput over the full case lifecycle. |
| **Specialist-only** | **Lowest throughput for bottlenecked stages.** Security (only 2 specialists) and Approval (few competent resources) form queues. Utilization of non-specialists is wasted. |
| **Proposed** | **Middle ground with better long-run throughput.** Specialist work stays with specialists (no unnecessary reassignment), but light touches (C010  Farid, C006  Jonas) prevent queue buildup at over-loaded resources. Throughput on a full-case basis — including rework — is expected to exceed specialist-only because bottlenecks are relieved. |

### SLA risk
| Policy | Assessment |
|---|---|
| **First-available** | **Mixed.** Fast start for all cases, but skill mismatch on urgent cases (e.g., assigning Security at skill 1 without supervision) can cause rejection/escalation cycles that *extend* effective service time beyond the original SLA. |
| **Specialist-only** | **High SLA risk in Security and Approval.** Hugo (7 open + 3 Security cases) and Farid become chokepoints. C001 with only 3 h may miss SLA if Hugo is already handling C008/C015. |
| **Proposed** | **Lowest expected SLA miss rate.** Urgent cases (C001, C002, C011) are handled by specialist owners or supervised pairs. C010 is moved off an overloaded Bruno to an underloaded Farid, preventing a bottleneck. Dynamic SLA weighting in the score explicitly steers resources toward imminent deadlines. |

### Error / rework risk
| Policy | Assessment |
|---|---|
| **First-available** | **Highest.** Assigning to low-skill resources causes errors; frequent reassignments (>2 threshold) multiply rework by 1.8×. First-available tends to reassign whenever a lighter-loaded resource appears. |
| **Specialist-only** | **Lowest immediate errors** but induces *hidden rework*: specialist queues cause case stalling, leading to workarounds and complaints (1.4× appeal rate evidence from similar handover-heavy patterns). |
| **Proposed** | **Low-to-moderate.** Specialist stays on specialist work; only C009 (deliberate trainee work on a low-complexity case) accepts elevated skill-mismatch risk. Supervision on C001 caps the risk. The deliberate, documented nature of each reassignment limits exposure. |

### Fairness of workload
| Policy | Assessment |
|---|---|
| **First-available** | **Best short-term fairness** — balances open-case counts. But concentrates *unskilled* work on over-used low-skill resources and ignores overtime risk (could overload David, Bruno, Iris further if they happen to be lightest at some moment). |
| **Specialist-only** | **Worst fairness.** Specialists become overloaded; non-specialists idle. R3_Celine, R7_Gita, R8_Hugo, R6_Farid absorb disproportionate load. Iris (Quality skill 3) gets nothing, Amal (Eligibility skill 3) gets nothing. |
| **Proposed** | **Good fairness with purposeful exceptions.** Bruno (OT high) is relieved of C010. Iris (OT high) is relieved of C006. Farid (OT low, underloaded) gains C010. Jonas (OT low, lightest) gains C006 + C013. David keeps C003/C014 despite overload because he is the only specialist — this is the acknowledged fairness cost, flagged for monitoring. |

### Skill development
| Policy | Assessment |
|---|---|
| **First-available** | **Unintentional development** — trainees may get work, but without structure. No link to documented training priorities. Risk of unsupervised high-priority work at low skill. |
| **Specialist-only** | **No development.** Specialists never give up work; trainees never practice. R1_Amal (diagnosis trainee), R6_Farid (diagnosis trainee) receive zero skill-building assignments. |
| **Proposed** | **Structured development.** C009 advances Amal's diagnosis training on a normal-priority, 0.44-complexity case with 22 h headroom. C015 supports Eva's and Jonas's security training through shadowing (safe: Hugo performs the work). 22 % of normal/low assignments support training  20 % target. The policy explicitly *refuses* to use training as an excuse for high-priority work at skill < 2. |

### Continuity of case ownership
| Policy | Assessment |
|---|---|
| **First-available** | **Worst continuity.** Ignores current owner entirely. Every batch risks re-assigning the same case to whoever is currently lightest. This triggers the >2 reassignment  1.8× rework cascade. |
| **Specialist-only** | **Poor continuity.** Ignores ownership; even if owner has adequate skill, specialist routing overrides it. High-complexity cases (C001, C007, C016) face unnecessary reassignment. |
| **Proposed** | **Best continuity.** 13 of 16 cases keep their current owner. Only 3 reassignments occur, each justified (low handover cost + workload relief or new case). High-complexity / high-handover cases (C001, C007, C016) explicitly retain owner per S1. |

### Resilience to absence or bottlenecks
| Policy | Assessment |
|---|---|
| **First-available** | **Good structural resilience** (work spread wide) but **fragile to quality**: if a lightly-loaded trainee is absent, the case stalls until someone more skilled picks it up — and that reassignment costs time. |
| **Specialist-only** | **Worst resilience.** Hugo is on Security for C001 + C008 + C015 = 3/3 Security cases. If Hugo is absent, all Security work halts. Farid holds C002 + C010 + C011 = 3/3 urgent Approval + Negotiation. |
| **Proposed** | **Moderate-to-good resilience.** Security is split across Celine (C001, supervised), Gita (C008), Hugo (C015) — three resources touch Security. Approval spans Farid (C002, C010). Diagnosis spans David (C003) and Eva (C016). The team-bottleneck term (5 % weight) prevents stacking one team. However, Team B holds 7/16 cases — if an entire team is absent, this is a structural gap reflecting real skill distribution, not a policy failure. |

# 5. Explanation to workers

> **How assignments are decided — and why**
>
> Every time activities are ready for work, our system suggests who should handle them. The suggestion is **not** an algorithm making decisions in isolation — it is a transparent set of reasons, reviewed by a supervisor before going live. Here is what goes into it:
>
> **1. Only capable people are considered.**
> We start by removing anyone whose skill level for that particular task is zero — no exceptions. For high-priority work, only people at competent level (2) or above can be assigned directly. Trainees (level 1) can only handle such work with a named supervisor beside them. Security tasks always require a specialist (level 3) or a trainee working under the explicit supervision of Gita or Hugo.
>
> **2. Deadlines matter.**
> If a case has only a couple of hours left before its SLA, that case gets priority attention in the assignment logic. Urgent and high-priority cases are scored higher for speed, which may mean we pick someone slightly less ideal on other dimensions to get the case moving now.
>
> **3. We prefer keeping the current owner.**
> Historical data shows that changing who owns a case — especially a complex one — adds roughly 2.7 hours of waiting time and increases the risk of rework. If the current owner already has the right skill, we almost always keep them, even if someone else has a higher skill level. The one exception: if the owner has no skill or only trainee-level skill on a high-complexity case and we cannot arrange supervision, we will reassign.
>
> **4. We watch who is overloaded.**
> People already carrying many cases or flagged with high overtime risk are less likely to receive *new* work — unless there is no other option. When we do relieve someone (for example, moving a case off a colleague who is stretched thin), we prefer cases with low handover cost so the change is smooth.
>
> **5. We build skills deliberately.**
> About one in five normal- or low-priority tasks is chosen specifically to help someone develop a skill they are meant to be training in. For example, if Amal is working on diagnosis training and a low-complexity diagnosis case comes up with plenty of SLA time, that case may stay with Amal rather than going to a specialist — with the understanding that someone reviews the output. **This never happens on urgent or high-priority work without supervision.**
>
> **6. We plan for the unexpected.**
> If a key person is away, we do not want all security work to stop. The system gently spreads tasks across teams so no single person or team is the only one who can do a job.
>
> **What this means for you:**
> - If you see your name on a case you already own, that is usually because the system trusts your continuity — not because no one else could do it.
> - If you see a new case appear, there is a specific reason listed (workload relief, skill match, training).
> - If you are asked to supervise a colleague, it is because you have the specialist skill and the case needs exactly that.
> - If you disagree with an assignment, say so — the reasons are visible and challengeable.

# 6. Process-mining audit indicators

Each indicator below can be computed from the event log columns provided. Target values are tunable, but initial suggested thresholds are given.

| # | Indicator | Definition (from event log) | Formula / method | Target / threshold | Purpose |
|---|---|---|---|---|---|
| **I1** | **Handover frequency** | Proportion of activities where `org:resource`  previous `org:resource` for the same case | `handovers / total_activities` after sorting by `time:timestamp` within each `case:concept:name` | < 15 % of transitions | Detect excess ownership changes |
| **I2** | **Reassignment count per case** | Number of resource changes within a case lifetime | Count distinct `org:resource` values per case  1; group distribution | 95th percentile  2; zero cases > 3 | Monitor 1.8× rework threshold |
| **I3** | **Skill mismatch rate** | Assignments where `required_skill` score for assigned `org:resource` is below 2 (for high/urgent) or below 3 (for Security) | Join log with skill matrix; flag `skill_assigned < threshold(priority, activity)` | 0 % for urgent/high (unsupervised); 0 % for Security unsupervised | Compliance with H2, H3, H4 |
| **I4** | **Supervision coverage** | Proportion of sub-threshold assignments with a documented supervisor | Filter assignments where `skill < 2`; check `assignment_reason` contains "supervised by"; verify supervisor has `skill  3` | 100 % | H2, H4 audit |
| **I5** | **Workload distribution (Gini)** | Gini coefficient of `workload_snapshot` across resources at each assignment point | `Gini(resource_workload_counts)` per time window | Gini  0.35 (moderate equality) | Fairness (S5) |
| **I6** | **Overtime risk exposure** | Count of new assignments given to resources with `overtime_risk = high` when `sla_deadline` was not urgent | Filter `assignment events where overtime_risk='high' AND case_priority  'urgent'` |  1 per batch; all flagged with justification | S2 compliance |
| **I7** | **SLA misses** | Cases where `time:timestamp` of completion > `sla_deadline` | `complete_time > sla_deadline` per case; rate and trend by assignment policy period | < 5 % overall; 0 % for urgent | Primary quality KPI |
| **I8** | **Rework / appeal after assignment** | Cases with rework activity or appeal activity that occurred after an assignment or reassignment | Detect rework/appeal `concept:name` events; correlate with recent `org:resource` change using `reassignment_count` | Rework rate for reassigned cases  baseline; rework rate for skill-mismatched  3 % | Cost of errors |
| **I9** | **Training assignment share** | Proportion of normal/low-priority assignments where `assignment_reason` contains "training" and `required_skill` matches the resource's `training_priority` | `training_count / normal_low_total` per batch |  20 % (S3) | Development tracking |
| **I10** | **Specialist bottleneck index** | For each skill, the ratio of cases assigned to the top-1 specialist vs. total cases needing that skill | `max_cases_by_one_resource / total_skill_needing_cases` per skill per period |  0.6 (no one specialist holds > 60 % of a skill's cases) | Resilience (S5) |
| **I11** | **Policy deviation rate** | Assignments where `assignment_reason = 'manual_override'` or where no automated score matches the actual assignment | Compare automated recommendation (re-run scoring) vs. actual `org:resource`; count mismatches | < 10 % of assignments; all deviations documented | Explainability & trust |
| **I12** | **Service time by skill level** | Average `get_service_time` grouped by (required_skill, skill_assigned) | Service time at skill 1 vs. skill 2 vs. skill 3 for same activity | skill-1 time within 1.5× of skill-3 time; otherwise investigate | Cost of skill mismatch |
| **I13** | **Queue time / waiting time** | Per case, the time between the previous activity completion and current activity start | Derived from `insert_case_service_waiting_time`; compare across assignment policies | Median waiting time  2 h; no systematic increase | Throughput proxy |

**Audit workflow:** run I1–I13 monthly; trigger review if any indicator exceeds its threshold for two consecutive periods; investigate with I11 (deviation) and I4 (supervision) first as leading indicators.

import pandas as pd

roles = pm4py.discover_organizational_roles(log)

# Group by resource × activity to see if skill-1 workers take significantly longer

# 6.  AUDIT INDICATOR COMPUTATION
# 

def compute_audit_indicators(log_df: pd.DataFrame,
                             skill_matrix: pd.DataFrame) -> pd.DataFrame:
    """Compute all audit indicators from the event log + reference data."""

    indicators = {}

    # --- I1: Handover frequency ---
    sorted_df = log_df.sort_values(["case:concept:name", "time:timestamp"])
    handovers = sorted_df.groupby("case:concept:name")["org:resource"].apply(
        lambda x: (x != x.shift()).sum() - 1
    )
    total_trans = sorted_df.groupby("case:concept:name").size() - 1
    indicators["handover_frequency"] = handovers.sum() / total_trans.sum()

    # --- I2: Reassignment count distribution ---
    indicators["reassignment_p95"] = handovers.quantile(0.95)
    indicators["cases_over_2_reassignments"] = (handovers > 2).sum()

    # --- I3: Skill mismatch ---
    def skill_of(row):
        res = row["org:resource"]
        sk = row["required_skill"]
        if res in skill_matrix.index and sk in skill_matrix.columns:
            return skill_matrix.loc[res, sk]
        return -1

    sorted_df["skill_assigned"] = sorted_df.apply(skill_of, axis=1)
    mismatch = (
        (sorted_df["case_priority"].isin(["urgent", "high"])) &
        (sorted_df["skill_assigned"] < 2)
    ) | (
        (sorted_df["concept:name"] == "Security Review") &
        (sorted_df["skill_assigned"] < 3)
    )
    indicators["skill_mismatch_rate"] = mismatch.sum() / len(sorted_df)

    # --- I5: Workload Gini ---
    wl = sorted_df["workload_snapshot"].dropna().values
    if len(wl) > 1:
        sorted_wl = np.sort(wl)
        n = len(sorted_wl)
        gini = (2 * np.sum((np.arange(n) + 1) * sorted_wl)) / (n * np.sum(sorted_wl)) - (n + 1) / n
        indicators["workload_gini"] = gini

    # --- I6: OT risk exposure ---
    ot_high_not_urgent = (
        (sorted_df["assignment_reason"].str.contains("overtime_risk=high", na=False)) &
        (~sorted_df["case_priority"].isin(["urgent"]))
    ).sum()
    indicators["ot_high_exposure"] = ot_high_not_urgent

    # --- I9: Training share ---
    normal_low = sorted_df[sorted_df["case_priority"].isin(["normal", "low"])]
    training = normal_low["assignment_reason"].str.contains("training", na=False)
    indicators["training_share"] = training.sum() / max(len(normal_low), 1)

    # --- I11: Policy deviation ---
    deviations = sorted_df["assignment_reason"].str.contains(
        "manual_override|deviation", na=False
    ).sum()
    indicators["policy_deviation_rate"] = deviations / len(sorted_df)

    return pd.DataFrame(indicators, index=[0])


# Run audit
audit_df = compute_audit_indicators(log_df, skill_matrix)
print("=== Policy Audit Indicators ===")
print(audit_df.T)
```
