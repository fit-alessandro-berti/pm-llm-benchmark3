# 1. Assumptions and Interpretation

1. **Observation boundary.** Each visible activity denotes its completion event. Therefore, a relation (A \prec B) means that `B` cannot complete before `A` has completed. The models do not represent activity-start timestamps, durations, resources, or actual intervals of execution.

2. **Meaning of “may overlap.”** “May overlap” is interpreted as true control-flow concurrency: neither activity is causally ordered before the other. In a visible completion trace, concurrency appears as the set of permitted linearizations rather than as simultaneous timestamps. Thus, both completion orders are allowed, but actual temporal overlap cannot be established from this completion-only model. In POWL, this is represented by leaving nodes unconnected in a partial order; PM4Py defines such nodes as concurrent. ([GitHub][1])

3. **Low-risk/high-risk choice.** The risk route is represented as an exclusive choice:

   * low risk: exactly one `Supervisor Review`;
   * high risk: exactly one `Quality Review` and one `Regulatory Review`, with no order between them.

   Because risk data is absent, the XOR is nondeterministic. The model cannot verify that the branch chosen for a particular case agrees with its actual risk classification.

4. **Optional supplier consultation.** Supplier involvement is represented as `XOR(Consult Supplier, τ)`. The visible branch contains one consultation and therefore enforces “at most once”; the silent branch represents no consultation. Because the supplier-involvement attribute is absent, the model cannot determine which branch is correct for a particular case.

5. **Passing inspection.** A trial iteration is `Execute Trial → Inspect Trial`. When the loop continues through `Adjust Parameters` and another iteration, the preceding inspection is interpreted as failed. The inspection after which the loop exits is interpreted as passing. This is a positional abstraction: no event attribute explicitly records pass or fail.

6. **Duplicate visible labels.** Duplicate static visible-label nodes are not used. Each of the 14 activity labels has one node in each model. Repeated `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` occurrences arise by revisiting the same loop submodel, not by creating duplicate visible leaves. This avoids unnecessary ambiguity in conformance mappings.

7. **Process-tree approximation policy.** The process tree is a **conservative under-approximation** of the data-erased intended language. It introduces one synchronization barrier after both work-product branches have completed:

   * `Contain Material → Plan Verification`; and
   * `Analyze Root Cause → Design Corrective Action`.

   Only after that barrier may the approval route, supplier option, and trial loop run in parallel. This preserves the safety-critical prerequisites of the trial and the release synchronization, but excludes intended cases where approval or supplier consultation begins early, immediately after root-cause analysis.

8. **POWL fidelity claim.** The POWL model is intended to be exact at the stated abstraction boundary: visible completion events, nondeterministic data-erased choices, and the positional interpretation of inspection results. It does not claim exactness with respect to unrecorded risk data, supplier data, inspection outcomes, or physical execution intervals.

# 3. PM4Py Process-Tree Model

```text
->(
  'Register Deviation',
  +(
    ->(
      'Contain Material',
      'Plan Verification'
    ),
    ->(
      'Analyze Root Cause',
      'Design Corrective Action'
    )
  ),
  +(
    X(
      'Supervisor Review',
      +(
        'Quality Review',
        'Regulatory Review'
      )
    ),
    X(
      'Consult Supplier',
      tau
    ),
    *(
      ->(
        'Execute Trial',
        'Inspect Trial'
      ),
      'Adjust Parameters'
    )
  ),
  'Release Material',
  'Archive Case'
)
```

The first parallel block constructs the two prerequisite work products. The second parallel block concurrently executes the selected approval route, the optional consultation, and the trial loop. In the binary loop, the first child is executed once; every continuation executes `Adjust Parameters` and then repeats `Execute Trial → Inspect Trial`.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def activity(label: str) -> ProcessTree:
    """Create one visible process-tree leaf."""
    return ProcessTree(label=label)


def silent() -> ProcessTree:
    """Create an invisible tau leaf."""
    return ProcessTree()


def operator_node(
    operator: Operator,
    *children: ProcessTree,
) -> ProcessTree:
    """
    Create an operator node and explicitly maintain both sides
    of every parent-child relationship.
    """
    parent = ProcessTree(operator=operator)

    for child in children:
        parent.children.append(child)
        child.parent = parent

    return parent


# Initial work-product streams.
containment_stream = operator_node(
    Operator.SEQUENCE,
    activity("Contain Material"),
    activity("Plan Verification"),
)

analysis_stream = operator_node(
    Operator.SEQUENCE,
    activity("Analyze Root Cause"),
    activity("Design Corrective Action"),
)

work_products = operator_node(
    Operator.PARALLEL,
    containment_stream,
    analysis_stream,
)

# Risk-dependent approval route.
high_risk_route = operator_node(
    Operator.PARALLEL,
    activity("Quality Review"),
    activity("Regulatory Review"),
)

approval_route = operator_node(
    Operator.XOR,
    activity("Supervisor Review"),
    high_risk_route,
)

# Optional, at-most-once supplier consultation.
supplier_option = operator_node(
    Operator.XOR,
    activity("Consult Supplier"),
    silent(),
)

# One or more trial iterations:
# (Execute Trial, Inspect Trial)
# (Adjust Parameters, Execute Trial, Inspect Trial)*
trial_iteration = operator_node(
    Operator.SEQUENCE,
    activity("Execute Trial"),
    activity("Inspect Trial"),
)

trial_loop = operator_node(
    Operator.LOOP,
    trial_iteration,
    activity("Adjust Parameters"),
)

# Conservative barrier:
# approval, supplier consultation, and trial work are enabled only
# after both initial work-product streams have completed.
release_obligations = operator_node(
    Operator.PARALLEL,
    approval_route,
    supplier_option,
    trial_loop,
)

tree = operator_node(
    Operator.SEQUENCE,
    activity("Register Deviation"),
    work_products,
    release_obligations,
    activity("Release Material"),
    activity("Archive Case"),
)


def assert_parent_links(node: ProcessTree) -> None:
    """Fail fast if any explicit parent pointer is inconsistent."""
    for child in node.children:
        assert child.parent is node
        assert_parent_links(child)


assert tree.parent is None
assert_parent_links(tree)
```

PM4Py’s `ProcessTree` constructor supports explicit `operator`, `parent`, `children`, and `label` fields, while the operator enumeration contains sequence, XOR, parallel, and loop operators. The helper above therefore appends every child and sets its parent explicitly. ([GitHub][2])

The tree represents requirements 1, 3, 4, 9, and 10 exactly at visible-trace level, and it represents the visible repetition pattern in requirement 8 exactly under the positional pass/fail convention. Requirement 2 is represented only as order-theoretic concurrency, not measured temporal overlap. Requirement 5 is structurally represented, but the risk data guard is absent. Requirement 6 is approximated twice: the supplier-data guard is absent, and consultation is incorrectly delayed until both work-product streams finish. Requirement 7 is only partially preserved: approvals and trial work can overlap inside the second parallel block, but approval cannot begin immediately after analysis while planning or design is still underway. Requirement 8 cannot encode the actual inspection result. Relative to the data-erased intended language, the added barrier creates false negatives but does not admit an unsafe early trial, incomplete release, or invalid loop ordering.

# 4. PM4Py POWL Model

```text
HIGH_RISK =
  PO(
    nodes = {
      'Quality Review',
      'Regulatory Review'
    },
    order = {}
  )

APPROVAL =
  X(
    'Supervisor Review',
    HIGH_RISK
  )

SUPPLIER =
  X(
    'Consult Supplier',
    tau
  )

TRIAL_ITERATION =
  PO(
    nodes = {
      'Execute Trial',
      'Inspect Trial'
    },
    order = {
      'Execute Trial' --> 'Inspect Trial'
    }
  )

TRIAL =
  *(
    TRIAL_ITERATION,
    'Adjust Parameters'
  )

ROOT =
  PO(
    nodes = {
      'Register Deviation',
      'Contain Material',
      'Analyze Root Cause',
      'Plan Verification',
      'Design Corrective Action',
      APPROVAL,
      SUPPLIER,
      TRIAL,
      'Release Material',
      'Archive Case'
    },

    order = transitive_closure({
      'Register Deviation' --> 'Contain Material',
      'Register Deviation' --> 'Analyze Root Cause',

      'Contain Material' --> 'Plan Verification',

      'Analyze Root Cause' --> 'Design Corrective Action',
      'Analyze Root Cause' --> APPROVAL,
      'Analyze Root Cause' --> SUPPLIER,

      'Plan Verification' --> TRIAL,
      'Design Corrective Action' --> TRIAL,

      APPROVAL --> 'Release Material',
      SUPPLIER --> 'Release Material',
      TRIAL --> 'Release Material',

      'Release Material' --> 'Archive Case'
    })
  )
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# Visible activity nodes.
register = Transition("Register Deviation")
contain = Transition("Contain Material")
analyze = Transition("Analyze Root Cause")
plan = Transition("Plan Verification")
design = Transition("Design Corrective Action")

supervisor = Transition("Supervisor Review")
quality = Transition("Quality Review")
regulatory = Transition("Regulatory Review")

supplier = Transition("Consult Supplier")

execute = Transition("Execute Trial")
inspect = Transition("Inspect Trial")
adjust = Transition("Adjust Parameters")

release = Transition("Release Material")
archive = Transition("Archive Case")


# High-risk route: both reviews are required, but no order is imposed.
high_risk_route = StrictPartialOrder([
    quality,
    regulatory,
])

# Low-risk versus high-risk route.
approval_route = OperatorPOWL(
    Operator.XOR,
    [
        supervisor,
        high_risk_route,
    ],
)

# Optional, at-most-once supplier consultation.
supplier_skip = SilentTransition()

supplier_option = OperatorPOWL(
    Operator.XOR,
    [
        supplier,
        supplier_skip,
    ],
)

# One trial iteration.
trial_iteration = StrictPartialOrder([
    execute,
    inspect,
])
trial_iteration.order.add_edge(execute, inspect)

# One or more iterations:
# trial_iteration (adjust trial_iteration)*
trial_loop = OperatorPOWL(
    Operator.LOOP,
    [
        trial_iteration,
        adjust,
    ],
)

# Root partial order.
powl = StrictPartialOrder([
    register,
    contain,
    analyze,
    plan,
    design,
    approval_route,
    supplier_option,
    trial_loop,
    release,
    archive,
])

# Start and initial independent streams.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Local prerequisites.
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)

# Analysis enables the independently progressing approval
# and supplier obligations.
powl.order.add_edge(analyze, approval_route)
powl.order.add_edge(analyze, supplier_option)

# Both work products are required before the trial loop can begin.
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronizes all independently progressing obligations.
powl.order.add_edge(approval_route, release)
powl.order.add_edge(supplier_option, release)
powl.order.add_edge(trial_loop, release)

# Mandatory final ordering.
powl.order.add_edge(release, archive)

# StrictPartialOrder is represented as a transitive relation.
# The calls above state the cover dependencies; this completes
# all implied precedence edges before validation.
powl.order.add_transitive_edges()
powl.validate_partial_orders()
```

PM4Py’s POWL implementation accepts visible `Transition` nodes, `SilentTransition`, binary XOR/loop `OperatorPOWL` nodes, and `StrictPartialOrder` nodes. A target partial-order node cannot execute before its source submodel has completed, while unconnected nodes are concurrent. The implementation also validates irreflexivity and transitivity; `add_transitive_edges()` computes the closure of the explicitly supplied cover edges. ([GitHub][1])

After transitive closure, the remaining incomparabilities are intentional:

* `Contain Material` and `Analyze Root Cause` are independent initial streams.
* `Plan Verification` and `Design Corrective Action` are unordered because each has its own predecessor.
* Planning or design may overlap an approval whose own prerequisite has been met.
* The approval route, supplier option, and trial loop are pairwise unordered after their respective prerequisites, so their internal events may interleave.
* `Quality Review` and `Regulatory Review` are unconnected because both are required but neither precedes the other.
* Supplier consultation is unordered with containment, planning, design, approval, and trial work, except that analysis precedes it and release follows it.

All other required orders arise either from a direct `.order.add_edge(...)` call or from its transitive consequences.

# 7. Preferred Representation and Validation Plan

The **POWL model should be canonical**. Its root partial order directly expresses the non-block-structured dependencies without duplicating visible activities and without inserting the process tree’s artificial barrier. The process tree remains useful as a conservative interchange or discovery target for tooling that requires block structure, but its false-negative region must be documented and monitored.

1. **Structural validation.**

   * Run `powl.validate_partial_orders()` after transitive closure.
   * Recursively verify every process-tree parent pointer, as in `assert_parent_links`.
   * Assert that the source models contain exactly one visible node for each of the 14 labels.
   * Verify that the root POWL has only `register` as a start node and only `archive` as an end node after closure.
   * Inspect the transitive reduction to confirm that it contains the intended cover dependencies rather than accidental extra edges.

2. **Conversion to accepting Petri nets.**

   ```python
   import pm4py

   pt_net, pt_im, pt_fm = pm4py.convert_to_petri_net(tree)
   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   ```

   Current PM4Py conversion dispatch distinguishes POWL from ordinary process trees and supports conversion of both to accepting Petri nets. The POWL converter realizes partial orders with hidden split/join and dependency-routing transitions, and realizes loop control with additional hidden transitions. ([GitHub][3])

3. **Soundness checks.**

   ```python
   pt_soundness = pm4py.check_soundness(
       pt_net,
       pt_im,
       pt_fm,
       print_diagnostics=True,
   )

   powl_soundness = pm4py.check_soundness(
       powl_net,
       powl_im,
       powl_fm,
       print_diagnostics=True,
   )
   ```

   Diagnostics should be examined for dead transitions, deadlocks, improper completion, residual tokens, and nonterminating silent behavior. A sound converted net is necessary operational evidence, but it is not proof that the model matches the narrative: a semantically incorrect model can still convert into a perfectly sound workflow net.

4. **Bounded and sampled playout.**

   * Play out the converted nets rather than relying only on their diagrams.
   * Because the trial loop makes the language infinite, impose a finite trace-length or iteration bound, such as one through three trial iterations.
   * Require generated samples covering low and high risk, both review completion orders, supplier selected and skipped, and approval events before, during, and after trial events.
   * Include randomized playout to search for surprising interleavings in addition to systematic bounded enumeration.

5. **Explicit positive and negative trace tests.**

   * Convert the eight witness traces into an event log and run alignment-based or equivalent accepting-net conformance checks.
   * Expected POWL result: accept A1–A5 and reject F1–F3.
   * Expected process-tree result: accept A1, A2, A4, and A5; deliberately reject A3; reject F1–F3.
   * Add mutation tests that move one event across a dependency boundary: trial before planning, design before analysis, consultation before analysis, release before one high-risk review, and archive before release.
   * Add multiplicity tests: zero trial iterations, two consultations, adjustment without another iteration, and a second supervisor review.

6. **Differential bounded-language test.**

   * Build a small reference oracle from the dependency specification rather than from either PM4Py model.
   * For each risk route, supplier choice, and one-to-three trial iterations, enumerate or sample topological linearizations of the intended dependency graph.
   * Check within the bound that:
     [
     L_{\text{tree}} \subseteq L_{\text{intended}}
     ]
     and that the missing tree behavior consists of documented early-approval or early-supplier cases.
   * Check that:
     [
     L_{\text{POWL}} = L_{\text{intended}}
     ]
     within the same bound.
   * Any POWL-only trace not accepted by the oracle would expose a missing edge; any oracle trace rejected by POWL would expose an accidental edge.

7. **Silent-behavior and label checks.**

   * Inspect every converted transition whose label is `None`.
   * Verify that there is no complete source-to-sink execution containing only silent transitions and no silent path that bypasses registration, the trial iteration, release, or archive.
   * Search for silent cycles that can fire indefinitely without visible progress.
   * Confirm that the silent supplier branch permits zero consultations but not two consultations.
   * Count visible labels in the converted nets and investigate any conversion-introduced duplicate transition labels.
   * Verify specifically that repeated trial occurrences arise through loop markings rather than through several visible transitions carrying the same label.

8. **Validation limitations.**

   * No finite playout proves equality of infinite loop languages.
   * Petri-net soundness does not prove agreement with data-dependent business rules.
   * Completion-only traces cannot validate actual overlap, start-time prerequisites, or durations.
   * Alignments involving many silent transitions may have several equally optimal explanations.
   * Conversion tests also test the converter implementation; they do not independently prove the source model’s semantics.
   * Risk, supplier involvement, and inspection outcome require separate attribute-aware validation or guarded-model extensions.

# 8. Final Self-Critique

1. **Data-dependent semantics remain external.** The models can enforce the shape of low- and high-risk routes, supplier optionality, and trial repetition, but cannot determine whether a particular case chose the correct route or whether the final inspection truly passed.

2. **Concurrency is only order-theoretic.** Treating absence of precedence as true concurrency is appropriate for control-flow modeling, but completion-only events cannot distinguish physical overlap from sequential execution in either order. The models therefore do not fully capture the narrative’s temporal interpretation.

3. **Runtime verification remains version-sensitive.** The constructors, operators, partial-order validation, and conversion calls were checked against the current PM4Py release-branch source, and the witness languages were checked deductively, but the snippets still require execution in the target PM4Py environment. Converter details, soundness return formats, or playout parameters can change between installed versions.
