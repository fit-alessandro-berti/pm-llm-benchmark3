## 1. Analytical assumptions

I interpret a **case notion** as the rule that groups events into traces by choosing one object type as the case identifier (e.g., one trace per `Order`, per `Package`, etc.), using only the given E2O relations. A **flattened log on object type X** therefore contains one trace per X-instance, with every event that directly references that X copied into that trace.

I use:

- **Convergence**: one case (one object of the chosen type) represents the execution of **multiple higher-level business units** that analysts might otherwise want to distinguish. Examples in this OCEL are:
  - `P3` and `P4` packages that mix items from multiple orders (events `e13`, `e14`, `e16`, `e17`, `e24`, `e27`);
  - `D2` and `D3` deliveries consolidating multiple packages/orders (`e16`, `e17`, `e24`, `e27`);
  - `V2` invoice that bills both `O2` and `O3` (`e19`, `e22`, `e25`).
- **Divergence**: one higher-level business unit has its behaviour **split across multiple cases** for the chosen object type. For example:
  - order `O1` split across packages `P1` and `P2` (`e11`, `e12`, `e15`, `e16`, `e23`, `e24`);
  - order `O3` split across items `I31` and `I32` (`e08`, `e09`, `e13`, `e14`, `e16`, `e17`, `e24`, `e27`);
  - invoice `V2`’s settlement split across payments `M2` and `M3` (`e22`, `e25`) when flattening on `Payment`.

I treat **copied shared events** (e.g., `e16`, `e19`, `e22`, `e24`, `e25`, `e27`) as **both evidence and duplication**:

- As **evidence**, they truthfully indicate that multiple objects participated in the same operational step (e.g., `D2` carrying `P2` and `P3` for `O1`, `O2`, `O3`).
- As **duplication**, each shared event inflates counts and can bias performance if naively analysed per case; for example, `e16` appears in three order traces (`O1`, `O2`, `O3`) although it is a single dispatch.

Analytically, I would:

- Use the **given E2O relations as the primary ground truth** for all flattenings.
- Allow **explicitly constructed propagated variants** for sensitivity analysis:
  - propagate along `contains` (`Order`–`Item`), `packs` (`Package`–`Item`), `carries` (`Delivery`–`Package`), `bills` (`Invoice`–`Order`), and `settles`/`partially_settles`/`completes_settlement` (`Payment`–`Invoice`);
  - keep these propagated OCELs separate from the original, and compare metrics (e.g., one OC-DFG on direct E2O vs another on propagated relations).
- When flattening, treat **multi-object events with the chosen object type as weighted candidates** for certain metrics (e.g., count each instance of `e16` for `O1`, `O2`, `O3` as weight 1/3 in some order-level KPIs) to mitigate duplication without discarding the evidence.

## 3. Concrete distortion analysis

### 3.1 Cross-order package P3 in order-based flattening (frequency inflation, harmful)

**Flattening:** `Order`.  
**Objects/events:** `P3` (`e13`, `e16`, `e24`), orders `O2`, `O3`.  

Event `e13` packs `I21` and `I31` into `P3` while referencing both `O2` and `O3`. Events `e16` and `e24` dispatch and confirm `P3` via `D2`, again listing `O2` and `O3` (and, for `e16` and `e24`, also `O1` via `P2`). In an order-flattened log, each of these three events appears **twice**, once in the trace for `O2` and once for `O3`.

As a result, DFG edges such as `Pack Package → Dispatch` and `Dispatch → Confirm Delivery` are counted **twice for the same physical shipment of `P3`**. If we compute “average number of dispatches per order” or resource utilisation at dispatch time, the consolidated shipment is misrepresented as two independent dispatch operations. This bias is generally **harmful** for order-level operational KPIs, because it inflates both frequency and implied effort of shared logistics.

### 3.2 Cross-order package P4 in order-based flattening (variant misclassification, context-dependent)

**Flattening:** `Order`.  
**Objects/events:** `P4` (`e14`, `e17`, `e27`), orders `O3`, `O4`.  

Package `P4` is filled in `e14` using items `I32` and `I41` from `O3` and `O4`. It is then dispatched and delivered via `D3` in `e17` and `e27`, both referencing `O3` and `O4`. In the order-based log, `O3`’s trace shows two distinct package lifecycles (`P3` via `e13`, `e16`, `e24` and `P4` via `e14`, `e17`, `e27`) and two deliveries (`D2`, `D3`), while `O4` shows only the `P4` chain.

An order-level variant analysis might therefore classify `O3` as a “complex” variant with **two dispatches and two deliveries**, and `O4` as a simpler single-dispatch variant. Yet in reality `P4` is a single cross-order package whose extra complexity is partly driven by consolidation with `O4`. This distortion is **context-dependent**: it is harmful if we interpret “number of dispatches per order” as a proxy for customer complexity, but informative if we are explicitly studying which orders participate in multi-order consolidation schemes.

### 3.3 Cross-order package P3 in package-based flattening (lifecycle merging, harmful for order-centric questions)

**Flattening:** `Package`.  
**Objects/events:** `P3` (`e13`, `e16`, `e24`), orders `O2`, `O3`.  

In a package-based log, `P3`’s trace consists of `Pack Package` (`e13`), `Dispatch` (`e16`), and `Confirm Delivery` (`e24`). Because `e13`, `e16`, and `e24` refer simultaneously to `O2` and `O3`, the single `P3` case **merges fulfilment of two orders**. Any DFG derived from this log treats that merged flow as a single unit.

If we ask “lead time from packing to delivery for orders in consolidated packages,” the package-based view measures exactly that. However, if we misinterpret a package trace as standing in for a single order’s lifecycle, we underestimate customer-level lead times for `O2` and `O3`, and we cannot see that these orders are also partially fulfilled via other artefacts (e.g., `P4` for `O3`). Thus, for order-centric KPIs the distortion is **harmful**, while for pure logistics optimisation (e.g., evaluating performance of multi-order packages as artefacts) it can be **informative**.

### 3.4 Cross-order items in item-based flattening (over-counted consolidated shipment, harmful)

**Flattening:** `Item`.  
**Objects/events:** items `I12`, `I21`, `I31` linked via `P2` and `P3` in `e12`, `e13`, `e16`, `e24`.  

Dispatch `e16` and delivery confirmation `e24` both reference three items: `I12` (order `O1`), `I21` (order `O2`), and `I31` (order `O3`), all sent together via `P2` and `P3` on `D2`. In an item-based log, `e16` and `e24` are **triplicated**: once in each of the traces for `I12`, `I21`, and `I31`. The DFG thus shows three occurrences of `Dispatch → Confirm Delivery` for what is operationally a single consolidated delivery.

If analysts compute “average number of deliveries per item” or throughput times per item, they will see a clean chain `Add Item → Pack Package → Dispatch → Confirm Delivery` with high frequency on the final edge, but they may falsely assume **three separate deliveries** rather than one shared shipment. This bias is **harmful** for associating logistics cost or carrier utilisation to items, though it can still be used carefully to identify which items tend to be shipped in consolidated form.

### 3.5 Consolidated delivery D2 in delivery-based flattening (case convergence, context-dependent but risky)

**Flattening:** `Delivery`.  
**Objects/events:** `D2` (`e16`, `e24`), packages `P2`, `P3`, orders `O1`, `O2`, `O3`.  

Delivery `D2` in `e16` and `e24` involves two packages (`P2`, `P3`) and three orders (`O1`, `O2`, `O3`). Under a delivery-based case notion, the `D2` trace represents all of these orders combined. The DFG for deliveries collapses to `Dispatch → Confirm Delivery`, and there is no within-trace evidence that `D2` is structurally different from `D1` (single-order, `O1` via `P1`) or `D3` (two orders, `O3`, `O4`).

If we use this log to assess “delivery reliability,” the convergence is somewhat acceptable: the focus is on the artefact `D2` itself and its elapsed time between `e16` and `e24`. But if we try to back-infer order-level behaviour (e.g., “orders with consolidated delivery have shorter/longer lead times”), we can no longer attribute performance to individual orders—there is only one case for all three. Hence the effect is **context-dependent but risky**, especially for customer-level SLA analysis.

### 3.6 Consolidated invoicing via V2 in invoice-based flattening (DFG loop and blended behaviour, informative but easy to misread)

**Flattening:** `Invoice`.  
**Objects/events:** `V2` (`e19`, `e22`, `e25`), orders `O2`, `O3`, payments `M2`, `M3`.  

Invoice `V2` is issued once for both `O2` and `O3` in `e19`, partially settled in `e22` (`M2`, qualifier `partially_settles`), and fully settled in `e25` (`M3`, qualifier `completes_settlement`). The invoice-based DFG shows a path `Issue Invoice → Record Payment → Record Payment`, with `V2` as the sole example of a two-step payment chain, while `V1` and `V3` show simple `Issue Invoice → Record Payment` paths (`e18`/`e21`, `e20`/`e26`).

If we treat this DFG as describing “typical customer payment behaviour,” the uniqueness of `V2` may be over-generalised, especially because it embodies **both multi-order and multi-instalment behaviour**. However, for financial analysis the pattern is **informative**: `V2` clearly highlights consolidated billing and staged payments for `O2` and `O3`. The trap lies in forgetting that this one complex invoice case actually aggregates two separate orders and their joint risk profile.

### 3.7 Partial payments in payment-based flattening (lifecycle truncation, harmful)

**Flattening:** `Payment`.  
**Objects/events:** `M2`, `M3` (`e22`, `e25`), invoice `V2`, orders `O2`, `O3`.  

When flattening on `Payment`, each payment object (`M1`–`M4`) forms a one-event lifecycle containing only `Record Payment` (`e21`, `e22`, `e25`, `e26`). For `V2`, the partial and complete settlements appear as two completely independent cases, `M2` and `M3`, with no trace-level link between them. The DFG degenerates into a single activity `Record Payment` with no meaningful edges.

Analysts looking only at this payment-based log cannot detect that `M2` and `M3` jointly settle the same multi-order invoice `V2`, nor that their timing (`e22` vs `e25`) reflects a staggered settlement pattern. Any notion of a payment **lifecycle** is thus truncated, which is **harmful** for questions about invoice clearing behaviour or credit risk—those require at least invoice-level or object-centric analysis.

### 3.8 Near-singleton lifecycle for deliveries and payments (artificial process simplicity, harmful)

**Flattening:** `Delivery` and `Payment`.  
**Objects/events:** `D1`, `D2`, `D3` (`e15`, `e16`, `e17`, `e23`, `e24`, `e27`); `M1`–`M4` (`e21`, `e22`, `e25`, `e26`).  

Each delivery has only two events (`Dispatch`, `Confirm Delivery`), and each payment only one (`Record Payment`). The resulting traces are extremely short: for `D1`, just `e15`→`e23`; for `M1`, only `e21`. A DFG discovered from such logs will show either a trivial `Dispatch → Confirm Delivery` chain or a single-activity model.

This artificial simplicity hides important dependencies: the time between `Create Order` and `Dispatch` (e.g., `e01`→`e15` for `O1`) and between `Confirm Delivery` and `Issue Invoice` or `Record Payment` (e.g., `e23`→`e18`→`e21` for `O1`) is invisible. Consequently, performance analysis on these flattened logs might falsely suggest that the process is inherently simple and tightly controlled, when in fact complexity has merely been **pushed into other object types**. This distortion is generally **harmful** if the logs are used in isolation.

### 3.9 Lifecycle truncation in package- and item-based flattenings (harmful)

**Flattening:** `Package` and `Item`.  
**Objects/events:** `P1`–`P4` (`e11`–`e17`, `e23`, `e24`, `e27`), items `I11`–`I41` (`e05`–`e10`).  

In package-based traces, lifecycles start at `Pack Package` (`e11`–`e14`) and end at `Confirm Delivery` (`e23`, `e24`, `e27`); in item-based traces, they start at `Add Item` (`e05`–`e10`) and similarly end at delivery confirmation. For example, `P1`’s lifecycle is `e11`→`e15`→`e23`, and `I11`’s is `e05`→`e11`→`e15`→`e23`. Neither perspective includes order creation (`e01`–`e04`), invoicing (`e18`–`e20`), or payments (`e21`, `e22`, `e25`, `e26`).

This leads to **systematic underestimation of end-to-end lead times**: analysts might report that “items are delivered within at most two hours after being added” (e.g., `e05`→`e23` for `I11`), while ignoring the potentially longer pre-order and post-delivery phases that matter for revenue recognition and cash flow. The truncation is **harmful** whenever the goal is to understand the full customer or financial lifecycle, but may be acceptable for strictly internal warehouse logistics.

## 4. Traditional versus object-centric analysis portfolio

### 4.1 Flattened logs worth creating and safe questions

- **Order-flattened log (`Order` as case):**
  - **Safe questions:** distribution of time from `Create Order` to `Close Order` per order (`e01`–`e04`, `e28`–`e31`); number of items per order based on `Add Item` events (`e05`–`e10`); presence of cross-order artefacts (orders that reference `P3`, `P4`, `D2`, `D3`, `V2` via `e13`, `e14`, `e16`, `e17`, `e19`, `e22`, `e24`, `e25`, `e27`).  
  - **Use:** end-to-end order SLAs, identification of orders exposed to consolidation, and rough order-level lead-time analysis (with explicit caveats about duplicated shared events).

- **Item-flattened log (`Item` as case):**
  - **Safe questions:** per-item picking and handling times, such as from `Add Item` to `Pack Package` and to `Confirm Delivery` (e.g., `I21`: `e07`→`e13`→`e16`→`e24`); detection of items more frequently involved in consolidated shipments (`I21`, `I31`, `I32`, `I41` vs `I11`).  
  - **Use:** warehouse efficiency and consolidation patterns at item level, not financial or order-completion questions.

- **Package-flattened log (`Package` as case):**
  - **Safe questions:** time from packing to delivery (`e11`→`e23`, `e12`→`e24`, `e13`→`e24`, `e14`→`e27`); rate of single-order vs cross-order packages (`P1`/`P2` vs `P3`/`P4`).  
  - **Use:** optimisation of packaging and carrier utilisation; evaluation of whether cross-order consolidation (e.g., `P3`, `P4`) improves or harms delivery times.

- **Delivery-flattened log (`Delivery` as case):**
  - **Safe questions:** dispatch-to-confirmation times for `D1`–`D3`; comparison of single-order (`D1`) vs multi-order (`D2`, `D3`) deliveries in terms of elapsed time between `Dispatch` and `Confirm Delivery`.  
  - **Use:** carrier performance; last-mile SLA compliance, not order-level or invoice-level behaviour.

- **Invoice-flattened log (`Invoice` as case):**
  - **Safe questions:** time from `Issue Invoice` to first and final `Record Payment` for each invoice (`V1`, `V2`, `V3`); proportion of invoices with staged payments (`V2` vs `V1`, `V3`); identification of consolidated invoices (`V2` referencing both `O2` and `O3`).  
  - **Use:** receivables ageing, payment behaviour, and consolidation strategies; not logistics.

- **Payment-flattened log (`Payment` as case):**
  - **Safe questions:** simple statistics over individual payments (timestamps of `e21`, `e22`, `e25`, `e26`, amounts if available).  
  - **Use:** essentially as an event table for financial postings; unsuitable for process discovery.

### 4.2 Questions requiring object-centric views

Certain questions inherently require **object-centric models** such as OC-DFG, OTG, ET–OT graph, and object interaction summaries:

- **Coupled logistics–billing behaviour:** “Do orders that are shipped via consolidated packages (`P3`, `P4`) also tend to be billed via consolidated invoices (`V2`) and partial payments?” This involves joint patterns over orders, packages, deliveries, invoices, and payments (`O2`, `O3`, `P3`, `P4`, `D2`, `D3`, `V2`, `M2`, `M3`) and cannot be answered safely from any single flattened log.
- **Impact of consolidation on order lead time:** we need an OC-DFG on orders and packages/deliveries to compare `O2`/`O3` (which use `P3`, `P4`, `D2`, `D3`) against `O1` and `O4` that have simpler logistics. A single case notion hides whether faster or slower performance is driven by multi-object coordination.
- **Allocation of payments to orders under consolidated invoicing:** especially for `V2`, the ET–OT graph is necessary to understand how `M2` and `M3` conceptually relate to `O2` and `O3`. Any flattened view either duplicates these payments per order (order-based log) or loses per-order allocation (invoice-based log).
- **Equivalent-execution clustering:** we may wish to cluster orders based on their **full multi-object execution context**, e.g., “simple single-package/single-invoice orders” (`O1`, `O4`) vs “cross-order consolidated and partially paid orders” (`O2`, `O3`). This justifies using `pm4py.cluster_equivalent_ocel` on the OCEL, not on a flattened log.

### 4.3 Reconciling contradictory findings

When flattened and object-centric views disagree (e.g., order-based DFG shows a high frequency of dispatches per order, while delivery-based logs show only three deliveries), I would:

- Use the **OC-DFG and OTG** to trace which edges are inflated by duplicated shared events (e.g., edges passing through `D2`, `D3`, `V2`).
- Compare **event-based vs object-based normalisations** (e.g., count edges per underlying delivery or per invoice vs per order trace) to identify whether a discrepancy stems from convergence or divergence.
- Rely on the **ET–OT graph and object interaction summary** to explain how many objects of each type participate in each shared event (e.g., `e16` spans 3 orders, 3 items, 2 packages, and 1 delivery).
- Prefer the **object-centric explanation** as the canonical narrative, and treat flattened views as specialised projections whose statistics must be interpreted through that multi-object lens.

## 5. Lead-object decision

I choose **B. Use a primary lead object plus explicitly secondary lifecycles**.

### 5.1 Decision criteria

My criteria are:

- **Semantic centrality:** does the object align with how stakeholders talk (“order”, “shipment”, “invoice”)?
- **Lifecycle completeness:** does the object see a rich set of activities across the process phases (creation, fulfilment, billing, settlement, closure)?
- **Stability under consolidation patterns:** how severely do cross-order packages (`P3`, `P4`), deliveries (`D2`, `D3`), and invoices (`V2`) distort traces?
- **Duplication management:** can event duplication around shared artefacts be managed without completely undermining the analysis?

### 5.2 Strongest supporting evidence for an order-led view

- Only **orders** have an explicit **start and end** in the event log: `Create Order` (`e01`–`e04`) and `Close Order` (`e28`–`e31`), plus visibility into logistics (`e11`–`e17`, `e23`, `e24`, `e27`), invoicing (`e18`–`e20`), and payments (`e21`, `e22`, `e25`, `e26`).
- Every other object type has a **truncated lifecycle**:
  - items start at `Add Item` and end at delivery;
  - packages start at `Pack Package`;
  - deliveries start at `Dispatch` and end at `Confirm Delivery`;
  - invoices start at `Issue Invoice` and end at last `Record Payment`;
  - payments are single events.
- Stakeholders naturally ask order-centric questions: “When did `O2` complete?” “Was `O3` shipped in multiple packages?” “Which orders were billed together?” These all map directly to the order-based traces.

Thus, using **orders as the primary lead object** offers the best single-case alignment with end-to-end business semantics, while still exposing references to logistics and financial objects.

### 5.3 Strongest counterarguments

- Cross-order packages (`P3`, `P4`), deliveries (`D2`, `D3`), and the consolidated invoice (`V2`) generate **substantial duplication and ambiguity** in order-based flattening:
  - events `e13`, `e14`, `e16`, `e17`, `e24`, `e27` involving `P3`, `P4`, `D2`, `D3` are replicated across affected orders;
  - invoice `V2`’s lifecycle (`e19`, `e22`, `e25`) appears in both `O2` and `O3` traces.
- As a result, the order-based DFG may **overstate the number of dispatches, deliveries, and payment steps per order** and misattribute logistics effort when consolidation is heavy.
- For certain analyses, a logistics- or finance-centred lead object (package, delivery, invoice) may be more natural and less distorted than orders.

These are serious concerns and justify not declaring orders as the *only* case notion.

### 5.4 Residual risk under decision B

By design, decision B acknowledges and manages residual risk:

- Even with orders as primary, **shared events remain duplicated**, so careless KPIs (e.g., counting dispatch events per order without considering `D2`, `D3`) will still be biased.
- Some phenomena, such as **partial payments on consolidated invoices** (`V2`, `M2`, `M3`) or **cross-order logistics** (`P3`, `P4`, `D2`), are simply more transparent when invoices, packages, or deliveries are treated as cases.
- Analysts might over-trust order-based traces and ignore secondary lifecycles, missing insights that only appear when clustering equivalent OCEL executions or studying the OTG.

To mitigate this residual risk, I would institutionalise a practice of always pairing the order-based view with at least package- and invoice-based secondary views plus object-centric diagnostics.

### 5.5 Conditions that would change the decision

I would reconsider the lead-object decision if:

- **Consolidation became ubiquitous:** if most packages and invoices were cross-order (many `P3`/`P4`-like objects and more `V2`-like invoices), order-based traces would become so heavily duplicated that they might cease to be interpretable as single-customer journeys.
- **Analytical focus shifted decisively** to logistics or finance:
  - for a study purely about carrier performance, a delivery- or package-led primary case notion might dominate;
  - for IFRS revenue-recognition audits, invoices could become the primary cases, with orders as secondary.
- **Tooling and users embraced object-centric models** to the point where flattened logs were used only as derived artefacts for specific KPIs; then we might explicitly reject any single lead object (moving towards option C in practice).

Given the current snapshot, however, I find **orders as primary with explicit secondary lifecycles** the most defensible compromise.

## 7. Sensitivity and validation plan

1. **Removing or down-weighting copied shared events.**  
   - Construct alternative flattened logs (especially for `Order` and `Item`) where multi-object events such as `e13`, `e14`, `e16`, `e17`, `e19`, `e22`, `e24`, `e25`, `e27` are either removed or **weighted by 1 / (# of affected cases)**. For example, in the order-based log, count `e16` with weight 1/3 in `O1`, `O2`, `O3` instead of 1.  
   - Recompute DFGs and performance metrics to see how much KPIs like “average number of dispatches per order” or “time from packing to delivery” change. Large shifts would confirm that conclusions are sensitive to event duplication around consolidated packages (`P3`, `P4`), deliveries (`D2`, `D3`), and invoices (`V2`).

2. **Comparing direct E2O relations with a propagated-relation variant.**  
   - Build a **propagated OCEL** where relations are extended along O2O links: for example, propagate from `Order` to `Package` via `contains` + `packs` so that packing events (`e11`–`e14`) are also seen as indirectly related to orders beyond those explicitly listed; similarly propagate from `Invoice` to `Package` via `bills` + `contains` + `packs`.  
   - Discover OC-DFGs and OTGs on both the **direct** and **propagated** versions and compare, for example, whether edges connecting `Issue Invoice` (`e19`) to dispatch/confirmation activities through shared orders (`O2`, `O3`) become more prominent. Deviations will show how much our understanding depends on strict vs propagated E2O semantics.

3. **Changing the lead object and comparing projections.**  
   - Repeat key analyses (DFG discovery, performance metrics) with **Invoice** and **Package** as temporary lead objects instead of `Order`. Compare, for instance, the distribution of “time from last delivery to final payment” inferred from order-based traces for `O2` and `O3` with the corresponding invoice-based metrics for `V2` (`e24`/`e27` to `e25`).  
   - Investigate whether consolidation effects (e.g., `P3`, `P4`, `D2`, `D3`, `V2`) that look beneficial or harmful in one projection appear neutral or opposite in another. This triangulation highlights where conclusions are artefacts of the chosen case notion.

4. **Comparing frequency metrics on the OC-DFG: events vs unique objects vs total objects.**  
   - For selected OC-DFG edges (e.g., `Pack Package → Dispatch` and `Dispatch → Confirm Delivery` for logistics; `Issue Invoice → Record Payment` and `Record Payment → Record Payment` for finance), compute three metrics:
     - frequency by **events** (raw count of events like `e13`, `e16`, `e24`, `e19`, `e22`, `e25`);
     - frequency by **unique objects of each type** involved (orders, packages, invoices);
     - frequency by **total objects** (counting multi-object events proportionally across participants).  
   - Compare, for example, how often `Dispatch → Confirm Delivery` appears per event (3 deliveries), per order (5 order-participations via `D1`, `D2`, `D3`), and per package (4 packages). Large discrepancies, particularly around `D2` and `V2`, will validate where flattened logs are inflating or deflating behaviour relative to the multi-object ground truth.

Together, these sensitivity checks ensure that any substantive conclusion about the order-fulfilment process is robust to event duplication, relation propagation choices, and the choice of lead object, and is properly normalised against the underlying multi-object structure encoded in the OCEL.
