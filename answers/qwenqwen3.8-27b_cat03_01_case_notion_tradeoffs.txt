## 1. Analytical assumptions

- **Case notion:** A case is one object instance of the selected object type. Its trace is the time-ordered set of events directly related to that object in the E2O relation set. If an event is related to multiple objects of the chosen type, it is copied into each relevant case.
- **Convergence:** Multiple distinct objects become tied to the same event, timestamp, or activity, causing traces to align artificially. Example: `e16` is directly related to `O1`, `O2`, and `O3`, so an Order flattening shows the same Dispatch event in three order cases.
- **Divergence:** One business operation is split across multiple object cases, causing fragmentation, missing transitions, or apparent loops. Example: `O1` is split across `P1` and `P2`, producing two Pack/Dispatch/Confirm sequences in the same order trace.
- **Copied shared events:** I treat them as **both** evidence of cross-object interaction **and** duplication. They are valid for interaction analysis but should be down-weighted when estimating event frequency, DFG edge support, or performance.
- **Permitted transformations:** I permit explicit relation propagation through O2O links only as a labelled analytical variant, not as the default flattening. For example, `P3` can be propagated to `O2` and `O3` through `I21` and `I31`; `D2` can be propagated to `O1`, `O2`, and `O3` through `P2` and `P3`; `M2`/`M3` can be propagated to `O2`/`O3` through `V2`.

## 3. Concrete distortion analysis

1. **Order flattening — `O1` split shipment creates repeated cycles.**  
   `O1` is packed into `P1` and `P2`: `e11` and `e12`, dispatched as `e15` and `e16`, confirmed as `e23` and `e24`. In the `O1` trace, this can produce apparent `Pack Package -> Pack Package`, `Dispatch -> Dispatch`, and `Confirm Delivery -> Confirm Delivery` edges. This is not necessarily rework; it is split shipment. Harmful if interpreted as process failure; informative if labelled as multi-package fulfilment.

2. **Order flattening — shared dispatch `e16` inflates Dispatch frequency.**  
   `e16` is directly related to `O1`, `O2`, and `O3`. In an Order flattening, Dispatch appears in three order cases at 11:05, although only one dispatch event exists. DFG edges involving Dispatch may be over-weighted, and performance analysis may treat three orders as having independent dispatch completions. Harmful for frequency estimation; informative for consolidation.

3. **Order flattening — shared confirmation and payment `e24`/`e25` create apparent synchronization.**  
   `e24` is copied into `O1`, `O2`, and `O3` at 16:00; `e25` is copied into `O2` and `O3` at 09:00 the next day. This inflates Confirm Delivery and Record Payment frequencies and makes the orders appear synchronized. Harmful for variant mining; informative for multi-order delivery and settlement.

4. **Package flattening — `P3` cross-order packaging is hidden.**  
   `e13` relates `O2`, `O3`, `I21`, `I31`, and `P3`. In a Package flattening, `P3` has only `e13 -> e16 -> e24`, the same shape as `P1`. The DFG cannot distinguish `P3` from a single-order package. Harmful for order-level analysis; informative only for package count and package lead time.

5. **Package flattening — `P4` cross-order packaging is hidden.**  
   `e14` relates `O3`, `O4`, `I32`, `I41`, and `P4`. In a Package flattening, `P4` has only `e14 -> e17 -> e27`. The cross-order nature of `P4` is invisible in the package trace. Performance such as `P4` 10:20–next day 10:00 may be attributed to one order, although it spans `O3` and `O4`. Context-dependent.

6. **Delivery flattening — `D2` consolidation is truncated.**  
   `e16` and `e24` relate `O1`, `O2`, `O3`, `I12`, `I21`, `I31`, `P2`, `P3`, and `D2`. In a Delivery flattening, `D2` is only `Dispatch -> Confirm Delivery`. The DFG is homogeneous, and `D2`’s 11:05–16:00 duration may be read as a single shipment, although it consolidates two packages and three orders. Context-dependent: useful for transport KPIs, misleading for order fulfilment.

7. **Invoice flattening — `V2` consolidated invoicing hides order coverage.**  
   `e19` relates `O2`, `O3`, and `V2`. In an Invoice flattening, `V2` is one case with one Issue event. If invoice cases are used to count order-level billing coverage, `V2` under-represents the fact that two orders are billed together. If the question is invoice lifecycle, the flattening is correct. Context-dependent.

8. **Invoice/Payment flattening — `V2` partial payments create a variant that disappears in Payment flattening.**  
   `e22` is `M2` partially settling `V2`; `e25` is `M3` completing settlement of `V2`. Invoice flattening shows a `Record Payment -> Record Payment` transition for `V2`. Payment flattening makes `M2` and `M3` singleton cases, losing the sequence. Order flattening copies both events into `O2` and `O3`, inflating payment frequency. Harmful if interpreted as duplicate payments; informative for instalment settlement.

9. **Payment flattening — near-singleton lifecycle.**  
   `M1`, `M2`, `M3`, and `M4` each have one event: `e21`, `e22`, `e25`, `e26`. The DFG contains only `Record Payment`. No settlement lead time, no partial-to-complete sequence, and no lifecycle state can be derived. Harmful for performance analysis; suitable only as a payment census.

10. **Delivery flattening — near-singleton lifecycle.**  
   `D1`, `D2`, and `D3` each have two events: `e15`/`e23`, `e16`/`e24`, `e17`/`e27`. The DFG contains only `Dispatch -> Confirm Delivery`. `D3`’s 11:15–next day 10:00 duration may be biased by `P4`’s cross-order composition and later confirmation. Context-dependent for transport analysis, insufficient for end-to-end fulfilment.

## 4. Traditional versus object-centric analysis portfolio

Flattened logs that should still be created:

- **Order log:** safe for order-to-close duration, close rate, order-level payment state, and split-shipment variants. Must down-weight copied shared events such as `e16`, `e24`, and `e25`.
- **Package log:** safe for pack-to-confirm lead time, dispatch reliability, and package-level consolidation count. Cannot answer order closure or billing questions.
- **Invoice log:** safe for issue-to-settlement duration and partial-payment variants, especially `V2` with `e22` and `e25`.
- **Item log:** optional for item flow and cross-order package membership, but only when combined with object-centric views.
- **Delivery log:** optional for dispatch-to-confirm KPIs only.
- **Payment log:** not useful as a process log; use only for payment event census.

Questions requiring object-centric views:

- **Cross-order package composition:** use OTG/ET–OT to inspect `e13` for `P3` with `O2`/`O3` and `e14` for `P4` with `O3`/`O4`.
- **Consolidated delivery:** use OC-DFG/OTG/ET–OT to inspect `e16`/`e24` for `D2` with `P2`, `P3`, `O1`, `O2`, and `O3`.
- **Consolidated invoicing:** use ET–OT to inspect `e19` for `V2` with `O2` and `O3`.
- **Partial settlement:** use OTG/ET–OT to inspect `V2`, `M2`, and `M3` with settlement qualifiers.
- **Equivalent execution clustering:** use clustering on the Order lead object to compare `O1`/`O3` split-shipment behaviour against `O2`/`O4` single-package behaviour, while interpreting clusters with the OC-DFG.

Reconciliation rule: if a flattened DFG shows repeated activity or strong transitions, first check whether the same event is shared across objects. If `ocdfg`/`etot` shows one event connected to multiple objects, report it as a shared interaction, not as independent repetition. If a propagated-relation variant adds edges, label them as derived, not native E2O evidence.

## 5. Lead-object decision

**Position B: Use a primary lead object plus explicitly secondary lifecycles.**  
Primary lead object: **Order**. Secondary lifecycles: **Package**, **Invoice**, and optionally **Delivery**/Item.

- **Decision criteria:** lifecycle completeness, stable identity, end-to-end business coverage, ability to represent financial and fulfilment state, and manageability of distortion.
- **Strongest supporting evidence:** Order is the only object type with a complete business lifecycle in this OCEL. `O1`–`O4` are created in `e01`–`e04`, contain items, are packed, dispatched, confirmed, invoiced, paid, and closed in `e28`–`e31`. No other object type spans creation through closure.
- **Strongest counterargument:** Order flattening duplicates shared logistics and financial events. `e16` and `e24` are copied across `O1`, `O2`, and `O3`; `e13`/`e14` hide cross-order packages; `V2` consolidates `O2` and `O3`; `O1` and `O3` produce repeated Pack/Dispatch/Confirm cycles because of split packages.
- **Residual risk:** frequency inflation, apparent synchronization, and performance bias if copied shared events are treated as independent order activity. The order view may also understate logistics complexity because package/delivery consolidation is compressed into copied events.
- **Conditions to change decision:** if the analytical goal becomes warehouse or transport efficiency, make **Package** or **Delivery** primary with Order secondary. If the goal becomes cash application, make **Invoice** primary. If order identity or close events were missing, reject a single lead object and use a fully object-centric portfolio.
