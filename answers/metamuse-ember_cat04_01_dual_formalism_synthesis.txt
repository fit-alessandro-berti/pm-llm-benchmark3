# 1. Assumptions and Interpretation

1. **Completion-time trace abstraction.** Activities are atomic events recorded at completion. A precedence in a model therefore means that the predecessor completes before the successor can complete, and in execution that the successor starts after the predecessor completes. The model cannot directly observe starts or durations.
2. **Meaning of “may overlap.”** “May overlap” is interpreted only as absence of an order constraint, not as mandatory true simultaneity. In both formalisms this is represented by unordered, interleavable activities. Sequential execution with either completion order is trace-equivalent to overlapping execution with the same completion order.
3. **Low-risk / high-risk choice.** This is represented by an exclusive choice, XOR: either the single low-risk activity Supervisor Review, or the high-risk parallel pair Quality Review and Regulatory Review. Exactly one route is taken. The risk predicate itself is not encoded; the choice is nondeterministic control flow after Analyze Root Cause.
4. **Optional supplier consultation.** Consult Supplier is represented by XOR with a silent skip: either Consult Supplier once or a silent transition producing no visible event. It is outside the trial loop, hence at most once. Whether data require consultation is not encoded; both branches are control-flow possibilities.
5. **Passing inspection.** A passing inspection is abstracted as exiting the trial loop after Inspect Trial. Adjust Parameters, as the loop redo part, presupposes that the preceding Inspect Trial failed. Thus a trace with $k$ Execute Trial–Inspect Trial cycles and $k-1$ Adjust Parameters between them is interpreted existentially: earlier inspections failed and the last passed. The actual inspection result is not an event label and cannot be verified from the visible trace.
6. **Duplicate visible labels.** Duplicate visible labels are not permitted in either submitted model. Every visible activity has exactly one syntactic occurrence, except that Execute Trial, Inspect Trial, and Adjust Parameters can fire repeatedly as loop iterations. No subtree for Execute Trial, Release Material, or another activity is duplicated. A duplicated-subtree tree was rejected because it would require two visible occurrences in a trace, make replay ambiguous, and could admit two releases.
7. **Process-tree approximation policy.** The process tree uses a conservative under-approximation: its language is intended to be a subset of the intended language. It preserves safety-critical synchronizations, especially Execute Trial after both Plan Verification and Design Corrective Action and Release Material after all obligations, but excludes some intended traces in which approval or supplier activities occur early. The alternative permissive tree that would admit Execute Trial before Plan Verification or Design Corrective Action was rejected as unsafe.
8. **Choice and optionality are not data-deterministic.** A case may take the low-risk or high-risk branch, take or skip Consult Supplier, and exit the loop after any iteration, as far as control flow is concerned. External case data must be checked separately if the route, supplier need, or inspection outcome has to agree with the case.
9. **Scope.** Each case contains one Register Deviation at the start and one Archive Case at the end. Mandatory activities occur once, except for the trial loop. Cancellation, re-registration, resources, calendars, and multiple interleaved cases are outside the model.

# 3. PM4Py Process-Tree Model

**Process-tree expression**

```text
->('Register Deviation',
   /\ ( ->('Contain Material', 'Plan Verification'),
          ->('Analyze Root Cause', 'Design Corrective Action') ),
   /\ ( x('Supervisor Review',
             /\('Quality Review', 'Regulatory Review')),
          * ( ->('Execute Trial', 'Inspect Trial'),
                'Adjust Parameters'),
          x('Consult Supplier', tau) ),
   'Release Material',
   'Archive Case')
```

**Python construction**

```python
import pm4py

tree_string = (
    "->('Register Deviation', "
    "/\\(->('Contain Material', 'Plan Verification'), "
    "->('Analyze Root Cause', 'Design Corrective Action')), "
    "/\\(x('Supervisor Review', /\\('Quality Review', 'Regulatory Review')), "
    "*(->('Execute Trial', 'Inspect Trial'), 'Adjust Parameters'), "
    "x('Consult Supplier', tau)), "
    "'Release Material', 'Archive Case')"
)
tree = pm4py.parse_process_tree(tree_string)
```

Because `pm4py.parse_process_tree(...)` is used, no manual parent/child object construction is needed in this code; the parser builds the parent/child hierarchy from the nested operator parentheses. The outer `->` is the sequence Register Deviation, first parallel phase, second parallel phase, Release Material, Archive Case. The first `/\` interleaves the sequence Contain Material–Plan Verification with Analyze Root Cause–Design Corrective Action, so those two work streams are independent but both must finish before the second phase starts. The second `/\` interleaves the risk-route XOR, the trial loop, and the supplier XOR, and all three must finish before Release Material. In the risk route, `x` chooses Supervisor Review alone or the `/\` pair Quality Review and Regulatory Review. In the trial loop, `*` makes Execute Trial–Inspect Trial the do part and Adjust Parameters the redo part, so Adjust Parameters can occur only between two trial cycles. In `x('Consult Supplier', tau)`, `tau` is the silent leaf producing no visible event; it represents not selecting supplier consultation.

The process tree is a conservative under-approximation, and its exactness losses are these: approval activities and Consult Supplier cannot occur before both Plan Verification and Design Corrective Action have completed, because they are placed in the second parallel phase after the first parallel phase, whereas the intended behaviour allows Supervisor Review, Quality Review, Regulatory Review, and Consult Supplier to start immediately after Analyze Root Cause and to overlap Plan Verification and Design Corrective Action; consequently the risk-route and supplier selections cannot be represented as occurring at the moment of Analyze Root Cause, only as activities delayed until after the planning/design join, and traces in which an approval or supplier activity completes in the window after Analyze Root Cause but before that join are excluded; the tree also cannot represent the data predicates “low risk”, “high risk”, “supplier involved”, or the actual inspection result, representing them only through XOR choice, optional XOR with silent tau, and loop exit as an existential passing inspection, although the resulting activity-count and ordering constraints for the chosen branch, at most one supplier consultation, and no Adjust Parameters after the final Inspect Trial are preserved.

# 4. PM4Py POWL Model

**Compact POWL description**

```text
root = StrictPartialOrder(
  nodes = {RD, CM, ARC, PV, DCA, APPROVAL, SUPPLIER, TRIAL, RM, AC},
  edges = {RD->CM, RD->ARC, CM->PV, ARC->DCA, ARC->APPROVAL,
           ARC->SUPPLIER, PV->TRIAL, DCA->TRIAL,
           APPROVAL->RM, SUPPLIER->RM, TRIAL->RM, RM->AC}
)
APPROVAL = XOR(SR, StrictPartialOrder{QR, RR with no edge})
SUPPLIER = XOR(CS, tau)
TRIAL = LOOP(StrictPartialOrder{ET->IT}, AP)
```

**Python construction**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
    Operator,
)

rd = Transition(label="Register Deviation")
cm = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")
pv = Transition(label="Plan Verification")
dca = Transition(label="Design Corrective Action")
rm = Transition(label="Release Material")
ac = Transition(label="Archive Case")

et = Transition(label="Execute Trial")
it = Transition(label="Inspect Trial")
ap = Transition(label="Adjust Parameters")
sr = Transition(label="Supervisor Review")
qr = Transition(label="Quality Review")
rr = Transition(label="Regulatory Review")
cs = Transition(label="Consult Supplier")
skip_cs = SilentTransition(label="tau")

high_risk = StrictPartialOrder(nodes=[qr, rr])
approval_route = OperatorPOWL(Operator.XOR, [sr, high_risk])
supplier_option = OperatorPOWL(Operator.XOR, [cs, skip_cs])

trial_do = StrictPartialOrder(nodes=[et, it])
trial_do.order.add_edge(et, it)
trial_loop = OperatorPOWL(Operator.LOOP, [trial_do, ap])

powl = StrictPartialOrder(
    nodes=[rd, cm, arc, pv, dca, approval_route, supplier_option, trial_loop, rm, ac]
)

powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)
powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, approval_route)
powl.order.add_edge(arc, supplier_option)
powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dca, trial_loop)
powl.order.add_edge(approval_route, rm)
powl.order.add_edge(supplier_option, rm)
powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(rm, ac)
```

The intentionally unconnected root-level pairs are exactly the following incomparable pairs. First, CMARC, CMDCA, CMAPP, CMCSX, ARCPV, PVDCA, PVAPP, PVCSX, DCAAPP, and DCACSX: each side depends only on its own predecessor chain, Plan Verification only on Contain Material and Design Corrective Action, the approval route, and supplier consultation only on Analyze Root Cause, while Contain Material and Analyze Root Cause are independent after Register Deviation, so no intended precedence exists between these cross-stream pairs and any completion order consistent with their own predecessors is allowed. Second, APPCSX, APPTRIAL, and CSXTRIAL: these are the three post-analysis obligations that must all precede Release Material but are intended to overlap independently, in particular approvals may overlap the trial cycle and supplier consultation may overlap approvals and trials. Third, inside the high-risk submodel, QRRR: both reviews are required in the high-risk route but neither precedes the other. Supervisor Review is not concurrent with Quality Review and Regulatory Review, because they are XOR alternatives; Consult Supplier is not concurrent with the silent skip, because they are XOR alternatives; and Adjust Parameters is not concurrent with Execute Trial and Inspect Trial, because the LOOP operator places the redo part between successive do-part cycles. Every other root pair without a direct edge is transitively ordered, for example Register Deviation reaches all nodes, Contain Material reaches the trial loop, Release Material, and Archive Case through Plan Verification, Analyze Root Cause reaches the trial loop, Release Material, and Archive Case through Design Corrective Action, the approval route, or supplier consultation, Plan Verification and Design Corrective Action reach Release Material and Archive Case through the trial loop, and the approval route, supplier option, and trial loop reach Archive Case through Release Material, so those pairs are not concurrent despite having no direct edge.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Contain Material and Analyze Root Cause start after Register Deviation and are unordered. | First parallel phase interleaves the two sequences exactly. | Register Deviation forks to both with no edge between them. | Neither, exact under the completion-trace abstraction. | Both models preserve legitimate completion orders in which either work stream finishes first. |
| Split dependencies into planning and design | Plan Verification depends only on Contain Material; Design Corrective Action depends only on Analyze Root Cause. | The two sequences in the first phase express this, but approvals and supplier consultation are gated until both sequences finish. | Direct edges Contain Material to Plan Verification and Analyze Root Cause to Design Corrective Action express this exactly, with no cross edges. | Process tree overconstrains downstream timing; POWL neither. | The tree can falsely reject or delay legitimate early approvals and supplier work; the POWL model does not. |
| Risk route | After Analyze Root Cause, exactly one of Supervisor Review alone or Quality Review and Regulatory Review together is required. | XOR of Supervisor Review and the parallel Quality Review–Regulatory Review pair expresses the activity sets, but only after the planning/design phase. | XOR node after Analyze Root Cause with a concurrency submodel for the high-risk pair expresses route and timing. | Process tree overconstrains timing; POWL neither on control flow, while both are data-underconstrained because risk attributes are ignored. | The tree may force unnecessary waiting before review; conformance with either model alone cannot prove the route matches the recorded risk level. |
| Overlap of approval and trial | Approvals and trial are unordered after their own predecessors and both precede release. | After the planning/design phase, approval and trial are parallel and can interleave, but approvals cannot begin before that phase ends. | No edge between approval route and trial loop, with edges from both to Release Material. | Process tree overconstrains the start of approvals; POWL neither. | The tree excludes cases where review starts during planning or design; the POWL model keeps trial-before-approval and approval-before-trial traces permissible. |
| Optional supplier consultation | At most once, after Analyze Root Cause, overlapping later work, before Release Material if selected. | XOR with silent tau gives at most once and before Release Material, but only after the planning/design phase. | XOR with SilentTransition after Analyze Root Cause and before Release Material gives the intended timing and at most once. | Process tree overconstrains timing; POWL neither on control flow, while both are data-underconstrained about whether consultation was needed. | The tree may reject an early supplier consultation; POWL conformance still needs a data check to detect a missing needed consultation. |
| Repeat-until behaviour | Execute Trial and Inspect Trial repeat after Adjust Parameters until an inspection passes; Adjust Parameters never follows the passing inspection. | LOOP do part Execute Trial–Inspect Trial and redo Adjust Parameters enforce another cycle after adjustment. | LOOP do part and redo Adjust Parameters enforce the same trace structure. | Neither on trace structure, but both underconstrain the real pass or fail result because it is not labelled. | A trace shape can be accepted even if inspection data say the wrong cycle passed; inspection outcomes must be validated from case data. |
| Release synchronization | Release Material requires passing Inspect Trial, completed selected approval route, and selected Consult Supplier if present. | Release Material is sequenced after the parallel phase containing trial, approval, and supplier option. | Edges from trial loop, approval route, and supplier option to Release Material express the join directly. | Neither, exact under the abstraction. | Both models prevent premature release in the visible trace language. |
| Trial synchronization | Execute Trial requires both Plan Verification and Design Corrective Action. | Execute Trial is in a later phase than the parallel planning/design phase. | Edges from Plan Verification and Design Corrective Action to the trial loop express the join. | Neither. | Both models prevent a trial without both work products. |
| Duplicate-label risk | Activities are identifiable and should not be confused by duplicated model nodes. | Each visible label occurs syntactically once; loop repetition is by refiring, not by duplicated subtrees. | Each visible Transition label is unique; loop repetition is by refiring the same loop children. | Neither. | Replay and activity counting remain unambiguous; a duplication-based tree would instead risk two Execute Trial or two Release Material occurrences and ambiguous attribution. |

# 7. Preferred Representation and Validation Plan

The POWL model should be canonical. It expresses the cross-branch partial order directly with edges such as Plan Verification to trial loop and Analyze Root Cause to approval route, so it preserves early approvals and early supplier consultation without admitting a premature trial. The conservative process tree remains useful as a readable projection and as an intentionally stricter comparator, but using it as the enforcement model would systematically reject legitimate cases merely because review or supplier work began before planning and design both finished. The POWL model also contains no duplicated visible labels and makes the silent supplier-skip branch explicit.

A concrete validation plan is:

1. **Structural identity checks.** Collect all POWL Transition labels and assert that the visible label set contains each activity exactly once; assert that SilentTransition occurs only as the supplier-skip XOR branch; compute the transitive closure of the partial order and compare it with the relations D01 to D21, including the 13 incomparable root pairs and Quality Review versus Regulatory Review listed in Section 4.
2. **Conversion to an accepting Petri net where supported.** Convert the POWL model with `pm4py.convert_to_petri_net(powl)` and use the returned initial and final markings; also convert the process tree as a comparator. Check that the final marking is reachable, that no tokens remain outside the final marking at acceptance, and that visible Petri-net transitions correspond one-to-one to model activity labels apart from loop refiring.
3. **Soundness checking of converted nets.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` and require the standard weak-soundness results: from every reachable marking the final marking is reachable, proper completion holds, and there are no dead transitions. Inspect diagnostics rather than treating a successful conversion as proof of business fidelity.
4. **Bounded and sampled playout.** Use `pm4py.play_out(powl, ...)` with a fixed loop bound, for example at most three trial cycles, and a fixed number of traces, for example 5,000 sampled traces, supplemented by deterministic enumeration for a loop bound of two where feasible. Check every generated trace with an independent precedence checker built from Section 2, and record coverage of low and high routes, supplier present and absent, one to three loop cycles, approval before and after trial start, and supplier before and after trial completion.
5. **Explicit positive and negative trace tests.** Use T01 to T08 as regression tests by replaying each trace on the converted Petri net and asserting the verdicts in Section 5, including the deliberate difference on T04. Add positive tests for three trial cycles, approval after the trial loop, and supplier consultation after the trial loop; add negative tests for Execute Trial before Design Corrective Action, Release Material before a present Consult Supplier, Quality Review without Regulatory Review, both risk routes in one case, Consult Supplier twice, and a case ending with Adjust Parameters.
6. **Silent-behaviour and duplicate-label checks.** Verify that traces exercising the silent supplier-skip branch contain no extra visible event and zero Consult Supplier occurrences, while traces selecting the supplier branch contain exactly one; verify that in all playouts Execute Trial count equals Inspect Trial count and Adjust Parameters count equals that common count minus one; search the converted net for a reachable cycle consisting only of silent transitions; and check that loop repetition is refiring of one Execute Trial transition rather than two distinct transitions with the same visible label.
7. **Log and data conformance beyond control flow.** Replay real cases and join the control-flow result with case attributes for risk level, supplier involvement, and inspection outcome; assert that the observed approval route matches risk, that supplier consultation matches the recorded need, and that the last inspection before release is marked passing. Report control-flow conformance and data conformance separately.

The limitations of this plan are that Petri-net soundness proves properties of the converted net, not fidelity to the narrative; conversion may introduce its own silent transitions or API-dependent mappings that must be inspected; bounded playout can miss rare interleavings or more than three trial cycles; token replay on completion-order traces cannot validate start times, durations, resources, risk predicates, supplier need, or actual inspection results; loop exit remains an existential interpretation of passing; and PM4Py version differences in process-tree parsing, POWL constructors, silent-transition handling, playout parameters, and soundness functions can change tool behaviour even when the intended partial order is unchanged.

# 8. Final Self-Critique

1. **Semantic weakness concerning data.** The POWL model is exact only for the abstract control-flow trace language. It will accept a low-risk approval route in a case whose data say high risk, accept no supplier consultation in a case whose data say consultation was required, and accept Adjust Parameters after a real passing inspection if a further trial cycle follows, because the model treats branch choice and loop exit nondeterministically. This is a semantic over-approximation relative to the business data, not merely a coding issue.
2. **Semantic weakness concerning starts and overlap.** Because the narrative records activities at completion time, both models can accept a trace in which a successor started before its predecessor completed but completed afterwards. The models therefore verify the necessary completion-order condition, not the stated start-time condition, and “overlap” remains only absence of precedence rather than evidence of simultaneous execution.
3. **Implementation and witness-coverage weakness.** The process-tree string uses quoted multi-word labels and the conventional silent `tau`, while the POWL code uses `SilentTransition(label="tau")` and positional `OperatorPOWL` construction; these depend on PM4Py version conventions and could fail or convert `tau` differently in another release. The eight witnesses isolate early approval as the tree approximation, but they do not isolate early Consult Supplier as a separate tree-rejected trace, nor do they exercise a three-cycle trial, so the empirical coverage is narrower than the validation plan claims in principle.
