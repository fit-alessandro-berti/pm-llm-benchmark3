## 1. Equivalence design space

Let \(E_X\) denote the events in the execution centered on the lead `Order`.

**1. Activity-sequence equivalence, \(\equiv_A\).**  
Definition: \(X\equiv_A Y\) iff their timestamp-ordered activity-label sequences are equal. Repetitions count, so `Pack, Pack` differs from `Pack`.

- **Preserves:** activity labels, repetitions, and event order.
- **Discards:** all object identities, types, multiplicities, E2O incidence, O2O relations, externality, and attributes.
- **Equivalence properties:** equality of a fixed sequence is reflexive, symmetric, and transitive.
- **Concurrency:** same-timestamp events form an unordered multiset. The signature is then a sequence of activity multisets rather than an arbitrary row order.

This yields four clusters: baseline-shaped X1, X2, X5, X6, and X7; double-pack X3; interleaved pack/dispatch/payment X4; and return-shaped X8.

**2. Typed structural equivalence under renaming, \(\equiv_T\).**  
Represent an execution as a colored temporal incidence graph:

- event nodes colored by activity and timestamp-bucket rank;
- object nodes colored by type, local/external status, and lead/non-lead role;
- E2O edges preserving event-object incidence and multiplicity;
- O2O edges preserving relation names and direction, but not yet free-text qualifier payloads.

\(X\equiv_T Y\) iff an isomorphism exists that renames only local object and event identifiers while preserving these colors, incidence, and order.

- **Preserves:** typed cardinalities, repeated objects, identity co-reference, package composition, shared objects, external flags, event order, and O2O topology.
- **Discards:** identifier spelling, exact time deltas, amounts and other attributes, and qualifier semantics.
- **Equivalence properties:** graph isomorphism is an equivalence relation.
- **Concurrency:** timestamp-bucket ranks are preserved, while events in one bucket are unordered. If causal dependencies are supplied, they can be added as colored edges.

X1 and X2 are structurally identical despite item-ID reversal. X3–X8 each receive a distinct structural cluster.

**3. Preferred business-semantic equivalence, \(\equiv_S\).**  
Use a deterministic feature tuple containing:

1. the canonical typed incidence graph above;
2. normalized O2O qualifier motifs:
   - `removed_before_dispatch`  `SUBSTITUTION`;
   - `replaces` after a return  `RETURN_REPACK`;
   - `partially_settles` and `completes_settlement`  `INSTALLMENT`;
3. stage-wise external sharing, distinguishing logistics (`Item`, `Package`, `Delivery`) from finance (`Invoice`, `Payment`);
4. lifecycle and cardinality features such as package count, delivery count, payment count, and shared-object dimension.

Unknown qualifier strings are retained verbatim rather than assigned invented meanings.

- **Preserves:** business-relevant topology, multiplicities, external sharing, qualifier-controlled substitutions and returns, repeated activities, and event order.
- **Discards:** raw local IDs, ordering of IDs inside one event, exact timestamp distances, monetary amounts, customer/product attributes, and implementation-specific spelling.
- **Equivalence properties:** equality of a finite canonical tuple is an equivalence relation.
- **Concurrency:** handled as for \(\equiv_T\), using timestamp buckets or an explicit partial order.

The preferred semantic partition is \( \{X1,X2\}, \{X3\}, \{X4\}, \{X5\}, \{X6\}, \{X7\}, \{X8\} \). This is not presented as universally finest or best: reporting may roll S2/S3 up as “multi-package fulfillment,” S4/S5 as “cross-order execution,” and S6/S7 as “corrective execution.”

## 2. Canonical signatures

The following scheme enumerates all identifier renamings that preserve object type, externality, and lead status, then chooses the lexicographically smallest encoding. This is practical for compact executions; production implementations can replace enumeration with color refinement or canonical graph labeling.

```python
from collections import defaultdict
from itertools import permutations, product
from hashlib import sha256

def normalize_qualifier(q):
    if q is None:
        return ""
    q = str(q).strip()
    known = {
        "removed_before_dispatch": "SUBSTITUTION",
        "partially_settles": "INSTALLMENT_PARTIAL",
        "completes_settlement": "INSTALLMENT_COMPLETE",
        "replaces": "RETURN_OR_REPLACEMENT",
    }
    return known.get(q, q)   # Unknown qualifiers are preserved verbatim.


def canonical_signature(events, o2o_edges, object_types, lead_id):
    """
    events: [{
        "activity": str,
        "bucket": int,       # timestamp-rank; equal buckets are concurrent
        "objects": [oid, ...]
    }]
    o2o_edges: [(source_oid, relation, target_oid, qualifier), ...]
    object_types: {oid: object_type}
    """

    def external(oid):
        # For this exercise. In production, use an explicit metadata flag.
        return str(oid).startswith("EXT")

    objects = set(object_types)
    for event in events:
        objects.update(event["objects"])
    for source, _, target, _ in o2o_edges:
        objects.update([source, target])

    # Identifiers may be exchanged only within the same semantic color.
    classes = defaultdict(list)
    for oid in objects:
        color = (
            object_types[oid],
            external(oid),
            oid == lead_id,
        )
        classes[color].append(oid)

    class_items = sorted(
        (color, sorted(ids)) for color, ids in classes.items()
    )
    domains = [list(permutations(ids)) for _, ids in class_items]

    best = None

    for choices in product(*domains):
        renaming = {}
        for (color, _), permutation in zip(class_items, choices):
            obj_type, is_external, is_lead = color
            for i, old_id in enumerate(permutation):
                renaming[old_id] = (
                    obj_type,
                    "EXT" if is_external else "LOCAL",
                    "LEAD" if is_lead else "NONLEAD",
                    i,
                )

        by_bucket = defaultdict(list)
        for event in events:
            refs = tuple(sorted(renaming[o] for o in event["objects"]))
            by_bucket[event["bucket"]].append((event["activity"], refs))

        # Sorting inside a bucket makes equal-time events unordered.
        encoded_events = tuple(
            (bucket, tuple(sorted(by_bucket[bucket])))
            for bucket in sorted(by_bucket)
        )

        encoded_o2o = tuple(sorted(
            (
                renaming[source],
                relation,
                normalize_qualifier(qualifier),
                renaming[target],
            )
            for source, relation, target, qualifier in o2o_edges
        ))

        candidate = (encoded_events, encoded_o2o)
        if best is None or repr(candidate) < repr(best):
            best = candidate

    return {
        "canonical": best,
        "digest": sha256(repr(best).encode("utf-8")).hexdigest(),
    }
```

The digest is invariant to local identifier renaming and relation-row order, but preserves repeated events, typed incidence, external status, temporal buckets, O2O direction, and normalized qualifiers. Exact timestamp values and monetary amounts are intentionally absent.

## 4. Cluster interpretations

“Stable” below means stable under identifier renumbering, relation-row ordering, timestamp-tie normalization, qualifier spelling normalization, and removal of exact duplicate rows—not deletion of semantic events.

- **S1 — Normal isolated fulfillment**
  - **Signature:** two local items, one package, delivery, invoice, and payment; no external objects.
  - **Behavior:** ordinary order-to-cash execution.
  - **Risks/opportunities:** useful baseline for cycle-time and automation benchmarking.
  - **Poor flattening:** ordinary Order flattening is adequate for reporting, although it still loses item/package identity.
  - **Stability:** highly stable under reasonable repair; missing or duplicate events would move it elsewhere.

- **S2 — Consolidated multi-package shipment**
  - **Signature:** two packages carried by one delivery; normal invoice/payment.
  - **Behavior:** packing is split, likely for handling or capacity, while transport is consolidated.
  - **Risks/opportunities:** greater handling and tracking complexity, but possible freight consolidation.
  - **Poor flattening:** an activity-only flattening cannot preserve the package-to-delivery partition.
  - **Stability:** stable to swapping the two Pack events; unstable if packages are merged or split during repair.

- **S3 — Split shipment with installment settlement**
  - **Signature:** independently dispatched packages and two payments against one invoice.
  - **Behavior:** non-atomic fulfillment and staged cash collection.
  - **Risks/opportunities:** delivery-promise, inventory-allocation, dunning, and cash-application risk.
  - **Poor flattening:** activity flattening loses which package belongs to which delivery and how both payments settle one invoice.
  - **Stability:** stable to payment renaming; collapsing payments into one total would incorrectly merge it toward S1.

- **S4 — Cross-order package sharing**
  - **Signature:** external order/item participate in packing and dispatch; invoice remains local.
  - **Behavior:** transport or packaging consolidation across orders.
  - **Risks/opportunities:** lower transport cost, but contamination of custody, tracking, item ownership, and charge-back.
  - **Poor flattening:** conventional Order flattening either duplicates the shared package in both cases or silently removes the external participation.
  - **Stability:** stable if externality is metadata; deleting external objects turns it into S1.

- **S5 — Cross-order consolidated billing**
  - **Signature:** normal local logistics; one invoice/payment shared with an external order.
  - **Behavior:** consolidated invoicing or shared payment without order-level allocation.
  - **Risks/opportunities:** billing convenience, but revenue recognition, tax, dispute, and cash-application risks.
  - **Poor flattening:** duplicating the invoice into each Order can double-count revenue; dropping the external Order hides consolidation.
  - **Stability:** stable to identifier repair; deleting `EXT-OB` changes it to S1.

- **S6 — Item substitution/removal**
  - **Signature:** two items packed initially, one removed before dispatch and the replacement explicitly dispatched.
  - **Behavior:** substitution, correction, or availability-driven replacement.
  - **Risks/opportunities:** inventory, customer-consent, pricing, and audit risk; substitutions may improve fill rate.
  - **Poor flattening:** activity-only flattening makes it look identical to the baseline.
  - **Stability:** qualifier spelling can be repaired safely. Dropping the qualifier removes the explicit substitution evidence, although the extra Dispatch-item incidence remains anomalous unless also repaired.

- **S7 — Return, inspection, and redispatch**
  - **Signature:** initial dispatch, item return and inspection, replacement package, and second dispatch.
  - **Behavior:** reverse logistics and recovery rather than a simple split shipment.
  - **Risks/opportunities:** return cost, quality diagnosis, resale/refurbishment, and customer-experience monitoring.
  - **Poor flattening:** flattening may show the activities but loses the links from returned item to original delivery and replacement package.
  - **Stability:** unstable under global deduplication of repeated `Pack` or `Dispatch`; stable under identifier and tie-order repair.

## 5. Borderline cases

- **X1 versus X2.** A raw-ID exact encoding distinguishes O1/I11/I12 from O2/I21/I22. Renaming-invariant activity, structural, and semantic equivalence correctly merge them. The reversed item-ID order across the two `Add Item` events is also insignificant because IDs carry no local meaning.

- **X1 versus X5.** A lead-Order-local or activity-only projection sees the same baseline sequence. An external-sharing-aware relation separates them because packing and dispatch involve another order and item. Thus “same process for O5” and “same isolated logistics execution” are defensible but answer different questions.

- **X1 versus X6.** Their logistics topology and activity sequence match. Finance-aware equivalence separates X6 because one invoice/payment covers two orders without allocation. A logistics-only clustering would merge them; an accounting or audit clustering must not.

- **X1 versus X7.** Activity-label equality merges them. E2O-aware structural equivalence separates them because Dispatch explicitly includes Item I72; qualifier-aware semantics additionally recognizes substitution/removal. A coarse operational view may consider X7 successful baseline fulfillment, while compliance should preserve the substitution.

- **X3 versus X4.** A “multi-package order” profile could group both. Typed incidence separates consolidated delivery from two deliveries, while payment-aware semantics further separates X4’s installment settlement. Consolidation/grouping information, not merely package count, is decisive.

- **X4 versus X8.** A coarse “two-package/two-delivery exception” segmentation can group both as non-atomic fulfillment. Lifecycle semantics separates staged split delivery with installments from return, inspection, repacking, and redispatch. One concerns settlement and delivery scheduling; the other reverse logistics.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

For the classic PM4Py OCEL implementation, the returned mapping is conceptually of the form:

```text
cluster_key -> [lead_object_id, lead_object_id, ...]
```

The classic key is an ordered serialization of the lead object’s selected event slice. Each event fingerprint contains its activity and its related object references, typically object type/object ID pairs in deterministic order. Repetitions and the timestamp-implied event order are therefore preserved. Calendar timestamps are generally used for ordering rather than compared as business-normalized durations. Event attributes, amounts, derived lifecycle motifs, and—unless a newer OCEL 2.0 variant explicitly adds them—the supplied O2O edges and qualifier semantics are not interpreted as business features.

The precise key representation is implementation- and version-specific, so it should be inspected and treated as opaque rather than parsed as a stable business label.

Raw identifiers make exact keys too fine because `O1`, `O2`, `I11`, and `I22` distinguish behaviorally identical executions. External identifiers are also more useful as an `external=true` role plus co-reference structure than as literal strings. If event IDs are serialized, the problem becomes even more severe: nearly every execution becomes a singleton.

A sound post-processing strategy is therefore:

1. call PM4Py to obtain its exact groups;
2. recompute a renaming-invariant canonical signature for each returned lead object;
3. merge PM4Py groups having the same signature;
4. optionally retain the exact PM4Py key as a drill-down child of the semantic cluster.

Exact equivalence remains preferable for forensic audit, duplicate/shared-event detection, data-lineage checks, and testing whether canonicalization accidentally merges distinct objects. It is usually too brittle for management segmentation.

`max_objs` is a computational guard, not a semantic equivalence criterion. Depending on the version, it may bound the lead objects processed or the object neighborhood encoded. Large shared logistics or finance hubs can create very large connected executions, causing skipped/truncated cases, giant keys, memory pressure, and many singleton clusters. Such cases should be labeled “excluded/truncated,” not mistaken for a rare semantic class.

```python
import pm4py
import pandas as pd
from collections import defaultdict

# canonical_signature is the function defined above.

EID = "ocel:eid"
ACT = "ocel:activity"
TS  = "ocel:timestamp"
OID = "ocel:oid"
OT  = "ocel:type"

# Adapt these names once to the OCEL version being used.
SRC, DST, REL, QUAL = "source", "target", "relation", "qualifier"

def make_lead_view(ocel, lead_id):
    relations = ocel.relations
    events_df = ocel.events

    event_ids = relations.loc[
        relations[OID] == lead_id, EID
    ].drop_duplicates()

    selected_events = (
        events_df[events_df[EID].isin(event_ids)]
        .sort_values([TS, EID], kind="mergesort")
    )

    timestamp_buckets = {
        timestamp: i
        for i, timestamp in enumerate(sorted(selected_events[TS].unique()))
    }

    selected_relations = relations[relations[EID].isin(event_ids)]
    object_types = dict(zip(ocel.objects[OID], ocel.objects[OT]))

    events = []
    for row in selected_events.itertuples(index=False):
        event_id = getattr(row, EID.replace(":", "_"), None)
        # More robustly, access selected_events rows as dictionaries in production.

    for _, row in selected_events.iterrows():
        refs = selected_relations.loc[
            selected_relations[EID] == row[EID], OID
        ].tolist()

        events.append({
            "activity": row[ACT],
            "bucket": timestamp_buckets[row[TS]],
            "objects": refs,
        })

    involved_objects = set(selected_relations[OID])
    o2o_edges = []

    if hasattr(ocel, "o2o") and ocel.o2o is not None and len(ocel.o2o):
        o2o = ocel.o2o
        relevant = o2o[
            o2o[SRC].isin(involved_objects) &
            o2o[DST].isin(involved_objects)
        ]
        o2o_edges = [
            (r[SRC], r.get(REL, "related"), r[DST], r.get(QUAL))
            for _, r in relevant.iterrows()
        ]

    return events, o2o_edges, object_types


raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    "Order",
    max_objs=100,
)

semantic_clusters = defaultdict(list)
exact_children = defaultdict(set)

for pm4py_key, members in raw_clusters.items():
    lead_ids = members if isinstance(members, (list, tuple, set)) else [members]

    for lead_id in lead_ids:
        events, o2o_edges, object_types = make_lead_view(ocel, lead_id)
        signature = canonical_signature(
            events,
            o2o_edges,
            object_types,
            lead_id=lead_id,
        )
        digest = signature["digest"]
        semantic_clusters[digest].append(lead_id)
        exact_children[digest].add(repr(pm4py_key))

summary = {
    digest: {
        "size": len(leads),
        "example_orders": leads[:5],
        "number_of_exact_pm4py_keys": len(exact_children[digest]),
    }
    for digest, leads in semantic_clusters.items()
}
```

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** X4 remains separate because two payment events remain structurally visible, but installment semantics are lost. X8 remains separate because return and repack events remain. X7 also remains typed-structurally distinct because Dispatch includes an Item, but it can no longer be confidently labeled substitution; if the extra incidence is repaired as instrumentation noise, X7 joins S1.

- **Ignore external objects.** Removing `EXT-OA` and `EXT-IA` makes X5 structurally identical to X1. Removing `EXT-OB` makes X6 identical to X1. Thus S4 and S5 collapse into S1. This may be appropriate for lead-order-only reporting but is unsafe for logistics or accounting.

- **Collapse repeated same-label events.** Run-length collapsing turns X1/X2 into `Create–Add–Pack–Dispatch–Invoice–Payment`; X3 also obtains that shape, losing its package split. X4’s separated Packs remain, while its adjacent Payments collapse. Global collapsing additionally removes X4’s second Pack/Dispatch and X8’s second Pack/Dispatch, making split shipment and redispatch nearly invisible. Object-aware aggregation should retain occurrence counts even when display labels are collapsed.

- **Use a Pack/Dispatch partial order.** Independent Add or Pack events may commute, so their timestamp tie order no longer matters. Object-based dependencies still separate X3’s two-package-to-one-delivery structure from X4’s two independent package-delivery branches. X8’s returned-item-to-repack dependency also remains. No supplied assignments change merely from this refinement.

- **Represent payments only as an amount.** If X4’s two payments are replaced solely by their sum, it can appear financially equivalent to X1. Retaining a payment schedule or installment count preserves S3. Amount abstraction is useful for financial totals but insufficient for liquidity, dunning, and settlement-timing analysis.

## 8. Limitations and recommendation

- **Compliance monitoring:** use typed structural equivalence enriched with external flags and O2O qualifiers. Substitutions, shared invoices, and unallocated payments may be control violations even when activity labels match.
- **Operational segmentation:** use the preferred business-semantic clusters. They produce actionable groups such as consolidated shipping, split shipment, shared logistics, consolidated billing, substitution, and returns.
- **Root-cause analysis:** start with typed structural equivalence and drill down to exact IDs, attributes, and timestamps. Excessive abstraction can remove the causal link being investigated.
- **Descriptive reporting:** use semantic rollups or activity-sequence clusters, depending on the audience. Seven operational clusters may be too detailed for an executive report.

No single relation is best because these purposes trade off audit precision, statistical robustness, interpretability, and actionability. Exact identity is valuable as evidence but poor as a business category; activity labels are readable but conceal precisely the object-centric behavior that matters.
