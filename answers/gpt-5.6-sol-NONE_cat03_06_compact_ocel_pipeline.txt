## 1. Modeling assumptions

- **Object types:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`.
- **E2O qualifiers:**
  - `created`, `item_added`, `stock_reserved`, `packed`, `dispatched`, `delivered`, `billed`, `payment_recorded`, and `closed`.
  - `operational_context` marks analytically useful direct links to an Order that are implied by the described operational event, rather than the event’s primary object.
  - `package_content` and `delivery_content` similarly identify Item participation in packing and dispatch/delivery events.
  - `invoice_context` links payment events to their Invoice.
- **O2O directions:** parent/context object is in `ocel:oid`, dependent/content object is in `ocel:oid_2`:
  - Order `contains` Item;
  - Package `packs` Item;
  - Delivery `carries` Package;
  - Invoice `bills` Order;
  - Payment `partially_settles` or `completes_settlement` Invoice.
- **Direct event relations:** logistics events are related directly to their Package or Delivery, relevant Items, and affected Orders. Invoice and payment events are related directly to the Invoice and both billed Orders; payment events are also related to their Payment object. This rich policy makes convergence and divergence visible in event-centric analyses.
- These additional analytical links are distinguished from primary source facts through qualifiers such as `operational_context`, `package_content`, `delivery_content`, and `invoice_context`. In a production OCEL, a separate provenance attribute or relation layer would be preferable; here the qualifier carries that distinction.
- The code assumes `from pm4py.objects.ocel.obj import OCEL` and the constructor
  `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`.
  If a PM4Py release uses a different constructor or import path, only the isolated construction line should be adapted; the four DataFrames and their semantics remain unchanged.
- PM4Py discovery APIs can vary slightly by release. The calls below target the current high-level API; in particular, some releases may call the OC-Petri-net visualization function `view_ocpn` instead of `view_oc_petri_net`.

import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL


# ---------------------------------------------------------------------------
# Helpers
# ---------------------------------------------------------------------------

def utc(value):
    """Construct a timezone-aware UTC Timestamp."""
    return pd.Timestamp(value, tz="UTC")


# ---------------------------------------------------------------------------
# Events
# ---------------------------------------------------------------------------

event_rows = [
    ("e01", "Create Order",       utc("2026-04-06 08:00"), None, None),
    ("e02", "Add Item",           utc("2026-04-06 08:05"), None, None),
    ("e03", "Add Item",           utc("2026-04-06 08:06"), None, None),
    ("e04", "Create Order",       utc("2026-04-06 08:10"), None, None),
    ("e05", "Add Item",           utc("2026-04-06 08:12"), None, None),
    ("e06", "Reserve Stock",      utc("2026-04-06 08:30"), None, None),
    ("e07", "Pack Package",       utc("2026-04-06 09:00"), None, None),
    ("e08", "Pack Package",       utc("2026-04-06 09:05"), None, None),
    ("e09", "Dispatch Package",   utc("2026-04-06 10:00"), None, None),
    ("e10", "Dispatch Package",   utc("2026-04-06 10:15"), None, None),
    ("e11", "Issue Invoice",      utc("2026-04-06 11:00"), None, None),
    ("e12", "Record Payment",     utc("2026-04-06 11:30"), 100.0, "MU"),
    ("e13", "Confirm Delivery",   utc("2026-04-06 13:00"), None, None),
    ("e14", "Confirm Delivery",   utc("2026-04-07 09:00"), None, None),
    ("e15", "Record Payment",     utc("2026-04-07 10:00"), 150.0, "MU"),
    ("e16", "Close Order",        utc("2026-04-07 10:30"), None, None),
    ("e17", "Close Order",        utc("2026-04-07 10:35"), None, None),
]

events = pd.DataFrame(
    event_rows,
    columns=[
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "payment_amount",
        "currency_unit",
    ],
)

# Nullable numeric type keeps non-payment rows as missing rather than objects.
events["payment_amount"] = events["payment_amount"].astype("Float64")


# ---------------------------------------------------------------------------
# Objects
# ---------------------------------------------------------------------------

object_rows = [
    ("O100", "Order"),
    ("O200", "Order"),
    ("I1", "Item"),
    ("I2", "Item"),
    ("I3", "Item"),
    ("P1", "Package"),
    ("P2", "Package"),
    ("D1", "Delivery"),
    ("D2", "Delivery"),
    ("V1", "Invoice"),
    ("M1", "Payment"),
    ("M2", "Payment"),
]

objects = pd.DataFrame(object_rows, columns=["ocel:oid", "ocel:type"])


# ---------------------------------------------------------------------------
# Event-to-object relations
#
# rel_spec contains only event ID, object ID, and qualifier. Activity,
# timestamp, and type are populated by joining to the authoritative event and
# object tables, guaranteeing consistency by construction.
# ---------------------------------------------------------------------------

rel_spec = [

    ("e01", "O100", "created"),

    # e02/e03: items added to O100
    ("e02", "O100", "item_added"),
    ("e02", "I1",   "item_added"),
    ("e03", "O100", "item_added"),
    ("e03", "I2",   "item_added"),

    # e04/e05: create O200 and add I3
    ("e04", "O200", "created"),
    ("e05", "O200", "item_added"),
    ("e05", "I3",   "item_added"),

    # e06: shared stock reservation for I1/I3 and both orders
    ("e06", "I1",   "stock_reserved"),
    ("e06", "I3",   "stock_reserved"),
    ("e06", "O100", "operational_context"),
    ("e06", "O200", "operational_context"),

    # e07: P1 combines I1 and I3 from O100 and O200
    ("e07", "P1",   "packed"),
    ("e07", "I1",   "package_content"),
    ("e07", "I3",   "package_content"),
    ("e07", "O100", "operational_context"),
    ("e07", "O200", "operational_context"),

    # e08: P2 contains I2 from O100
    ("e08", "P2",   "packed"),
    ("e08", "I2",   "package_content"),
    ("e08", "O100", "operational_context"),

    # e09: D1 dispatches P1, which contains I1/I3 from both orders
    ("e09", "D1",   "dispatched"),
    ("e09", "P1",   "dispatched"),
    ("e09", "I1",   "delivery_content"),
    ("e09", "I3",   "delivery_content"),
    ("e09", "O100", "operational_context"),
    ("e09", "O200", "operational_context"),

    # e10: D2 dispatches P2/I2 for O100
    ("e10", "D2",   "dispatched"),
    ("e10", "P2",   "dispatched"),
    ("e10", "I2",   "delivery_content"),
    ("e10", "O100", "operational_context"),

    # e11: one invoice bills both orders
    ("e11", "V1",   "billed"),
    ("e11", "O100", "billed"),
    ("e11", "O200", "billed"),

    # e12: M1 records a partial payment against V1, affecting both billed orders
    ("e12", "M1",   "payment_recorded"),
    ("e12", "V1",   "invoice_context"),
    ("e12", "O100", "invoice_context"),
    ("e12", "O200", "invoice_context"),

    # e13: D1/P1/I1/I3 delivered; both orders are affected
    ("e13", "D1",   "delivered"),
    ("e13", "P1",   "delivered"),
    ("e13", "I1",   "delivery_content"),
    ("e13", "I3",   "delivery_content"),
    ("e13", "O100", "operational_context"),
    ("e13", "O200", "operational_context"),

    # e14: D2/P2/I2 delivered for O100
    ("e14", "D2",   "delivered"),
    ("e14", "P2",   "delivered"),
    ("e14", "I2",   "delivery_content"),
    ("e14", "O100", "operational_context"),

    # e15: M2 completes settlement of V1
    ("e15", "M2",   "payment_recorded"),
    ("e15", "V1",   "invoice_context"),
    ("e15", "O100", "invoice_context"),
    ("e15", "O200", "invoice_context"),

    ("e16", "O200", "closed"),

    rel_spec,
    columns=["ocel:eid", "ocel:oid", "ocel:qualifier"],
)

relations = (
    relations
    .merge(
        events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
        on="ocel:eid",
        how="left",
        validate="many_to_one",
    )
    .merge(
        objects[["ocel:oid", "ocel:type"]],
        on="ocel:oid",
        how="left",
        validate="many_to_one",
    )
    [[
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "ocel:oid",
        "ocel:type",
        "ocel:qualifier",
    ]]
)


# ---------------------------------------------------------------------------
# Object-to-object relations
# Direction: contextual/parent object -> dependent/content object.
# ---------------------------------------------------------------------------

o2o_rows = [
    ("O100", "I1",   "contains"),
    ("O100", "I2",   "contains"),
    ("O200", "I3",   "contains"),

    ("P1",   "I1",   "packs"),
    ("P1",   "I3",   "packs"),
    ("P2",   "I2",   "packs"),

    ("D1",   "P1",   "carries"),
    ("D2",   "P2",   "carries"),

    ("V1",   "O100", "bills"),
    ("V1",   "O200", "bills"),

    ("M1",   "V1",   "partially_settles"),
    ("M2",   "V1",   "completes_settlement"),
]

o2o = pd.DataFrame(
    o2o_rows,
    columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"],
)


# ---------------------------------------------------------------------------
# Validation
# ---------------------------------------------------------------------------

assert len(events) == 17
assert events["ocel:eid"].is_unique
assert objects["ocel:oid"].is_unique
assert events["ocel:timestamp"].dt.tz is not None

event_ids = set(events["ocel:eid"])
object_ids = set(objects["ocel:oid"])

assert set(relations["ocel:eid"]).issubset(event_ids)
assert set(relations["ocel:oid"]).issubset(object_ids)
assert set(o2o["ocel:oid"]).issubset(object_ids)
assert set(o2o["ocel:oid_2"]).issubset(object_ids)

assert not relations.duplicated(
    subset=[
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "ocel:oid",
        "ocel:type",
        "ocel:qualifier",
    ]
).any()
assert not o2o.duplicated(
    subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"]
).any()

# Recheck that every relation repeats the authoritative event values.
event_lookup = events.set_index("ocel:eid")
for row in relations.itertuples(index=False, name=None):
    eid, activity, timestamp, oid, object_type, qualifier = row
    assert activity == event_lookup.loc[eid, "ocel:activity"]
    assert timestamp == event_lookup.loc[eid, "ocel:timestamp"]

# Recheck relation object types.
object_type_lookup = objects.set_index("ocel:oid")["ocel:type"]
assert relations.apply(
    lambda r: r["ocel:type"] == object_type_lookup.loc[r["ocel:oid"]],
    axis=1,
).all()

# Ensure every event and object participates in at least one E2O relation.
assert set(events["ocel:eid"]) == set(relations["ocel:eid"])

# OCEL construction -- isolate this line if the installed PM4Py constructor
# signature or import path differs.
# ---------------------------------------------------------------------------

ocel = OCEL(
    events=events,
    objects=objects,
    relations=relations,
    o2o=o2o,

# Basic inspection

    .value_counts()

print(object_type_frequencies)

print("\nObject types returned by PM4Py:")
print(object_types)

activities_per_object_type = pm4py.ocel_object_type_activities(ocel)

print(activities_per_object_type)

flattened_logs = {}
flattened_dfgs = {}
flattened_log_skeletons = {}

for object_type in required_flattenings:

# ---------------------------------------------------------------------------

ocdfg = pm4py.discover_ocdfg(ocel)

## 3. Data-model audit

### Objects

| Object type | Objects | Count |
|---|---|---:|
| Order | O100, O200 | 2 |
| Item | I1, I2, I3 | 3 |
| Package | P1, P2 | 2 |
| Delivery | D1, D2 | 2 |
| Invoice | V1 | 1 |
| Payment | M1, M2 | 2 |

### O2O qualifiers

| Qualifier | Directed relations | Cardinality |
|---|---|---:|
| `contains` | O100I1, O100I2, O200I3 | 3 |
| `packs` | P1I1, P1I3, P2I2 | 3 |
| `carries` | D1P1, D2P2 | 2 |
| `bills` | V1O100, V1O200 | 2 |
| `partially_settles` | M1V1 | 1 |
| `completes_settlement` | M2V1 | 1 |

### Activities and touched object types

| Activity | Object types touched under this policy |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Order, Item, Package |
| Dispatch Package | Order, Item, Package, Delivery |
| Issue Invoice | Order, Invoice |
| Record Payment | Order, Invoice, Payment |
| Confirm Delivery | Order, Item, Package, Delivery |
| Close Order | Order |

Especially consequential relation sets are:

- **e06 Reserve Stock:** joins I1 and I3 and, directly, O100 and O200.
- **e07 Pack Package P1:** creates visible convergence because P1 combines I1/O100 and I3/O200.
- **e11 Issue Invoice V1:** converges both Orders into one Invoice.
- **e12 and e15 Record Payment:** each payment event is shared by V1 and both Orders. This makes the financial lifecycle visible in Order traces but can look like duplicated payment behavior after flattening.
- **e13 Confirm Delivery D1:** one confirmation simultaneously affects D1, P1, I1, I3, O100, and O200.

## 4. Expected flattened behavior

### Order flattening

Approximate traces are:

- **O100:**  
  `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Dispatch Package  Dispatch Package  Issue Invoice  Record Payment  Confirm Delivery  Confirm Delivery  Record Payment  Close Order`
- **O200:**  
  `Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Record Payment  Confirm Delivery  Record Payment  Close Order`

Shared events e06, e07, e09, e11, e12, e13, and e15 occur in both Order traces. They are projections of the same event, not two executions.

Likely Order DFG edges include:

- `Create Order  Add Item`;
- `Add Item  Add Item` for O100;
- `Add Item  Reserve Stock`;
- `Reserve Stock  Pack Package`;
- `Pack Package  Pack Package` for O100;
- `Pack Package  Dispatch Package`;
- `Dispatch Package  Dispatch Package` for O100;
- `Dispatch Package  Issue Invoice`;
- `Issue Invoice  Record Payment`;
- `Record Payment  Confirm Delivery`;
- for O100, `Confirm Delivery  Confirm Delivery`;
- `Confirm Delivery  Record Payment`;
- `Record Payment  Close Order`.

The projection exposes broad order lifecycle timing, but it can misleadingly suggest that each Order independently executed shared packing, invoicing, and payment events. It also hides the fact that O100’s items split across P1/P2 and D1/D2, while P1 also contains an O200 item.

### Package flattening

Approximate traces are:

- **P1:** `Pack Package  Dispatch Package  Confirm Delivery`
- **P2:** `Pack Package  Dispatch Package  Confirm Delivery`

Likely DFG edges are therefore:

- `Pack Package  Dispatch Package`;
- `Dispatch Package  Confirm Delivery`.

No event is copied between P1 and P2 under the chosen E2O relations. P1’s events are, however, shared with two Orders and two Items in the original OCEL.

The flattened view omits Order creation, item addition, reservation, invoicing, payment, and closure. More importantly, the simple P1 trace does not reveal that P1 converges I1 from O100 and I3 from O200. It can falsely make P1 and P2 look structurally equivalent despite their different cross-order content.

### Delivery flattening

Approximate traces are:

- **D1:** `Dispatch Package  Confirm Delivery`
- **D2:** `Dispatch Package  Confirm Delivery`

Likely DFG edge:

- `Dispatch Package  Confirm Delivery`.

No Delivery event is copied between D1 and D2. The projection omits package creation/packing, item and order history, invoicing, payment, and closure. It also hides that D1 carries P1, which combines two Orders, whereas D2 carries only P2 for O100. A traditional delivery log could therefore suggest two interchangeable delivery cases.

### Invoice flattening

V1 has one trace:

`Issue Invoice  Record Payment  Record Payment`

Likely DFG edges:

- `Issue Invoice  Record Payment`;
- `Record Payment  Record Payment`.

There are no copied events across multiple Invoice traces because only V1 exists. The trace correctly shows two payment-recording events, but it omits the Payment-object distinction unless event/object details are inspected: e12 concerns M1 for 100, and e15 concerns M2 for 150. It also omits the operational logistics and may obscure that V1 bills both O100 and O200.

With only one Invoice trace, frequencies and behavioral constraints are anecdotal rather than generalizable. The repeated `Record Payment` activity should not be interpreted as rework: it represents intended partial settlement followed by completion.

### Why Payment flattening is particularly weak

M1 and M2 each participate in exactly one `Record Payment` event. Payment flattening would therefore produce two one-event traces. It cannot show:

- that both payments settle the same Invoice V1;
- that M1 is partial and M2 completes settlement;
- the sequence between issuing V1, M1, and M2;
- the relationship to O100 and O200.

Those semantics live primarily in the Invoice trace and in O2O links. A Payment DFG would contain nodes but essentially no directly-follows behavior.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should preserve per-object-type directly-follows behavior without forcing one universal case notion:

- Orders show creation, item addition, shared operational steps, billing, two payments, delivery confirmations, and closure.
- Packages show `Pack Package  Dispatch Package  Confirm Delivery`.
- Deliveries show `Dispatch Package  Confirm Delivery`.
- Invoice V1 shows `Issue Invoice  Record Payment  Record Payment`.
- Payment objects M1 and M2 each contribute a singleton `Record Payment` lifecycle.
- P1’s packing, dispatch, and confirmation events connect to items belonging to both O100 and O200, exposing convergence unavailable in a single Package trace.
- V1 and its two payment events similarly converge the financial histories of O100 and O200.

Because different object types induce different directly-follows edges through the same events, the graph should be read with its object-type annotations rather than as one ordinary DFG.

### OTG

The object-type graph should reflect these type-level interactions:

- `Order—Item` through containment and shared events;
- `Package—Item` through packing;
- `Delivery—Package` through carrying and shared dispatch/delivery events;
- `Invoice—Order` through billing;
- `Payment—Invoice` through settlement;
- additional event-observed interactions such as `Order—Package`, `Order—Delivery`, `Order—Payment`, and `Item—Delivery`, caused by the rich E2O policy.

P1 is the important bridge between `Package`, `Item`, and `Order`; V1 bridges `Invoice`, both Orders, and payments M1/M2. Depending on PM4Py’s OTG implementation, edge counts may derive from co-occurrence, O2O, or both, but the qualitative connectivity should remain.

### ET–OT

The event-type/object-type graph should show which activity types involve which object types:

- `Pack Package` connects to Package, Item, and Order;
- `Dispatch Package` and `Confirm Delivery` connect to Delivery, Package, Item, and Order;
- `Issue Invoice` connects to Invoice and Order;
- `Record Payment` connects to Payment, Invoice, and Order.

This graph makes the modeling policy especially visible. For example, direct Order links on payment events create a `Record Payment—Order` edge; a source-minimal policy would omit it even though V1 still bills O100 and O200 through O2O.

### Object-centric Petri net

The discovered net should represent interacting lifecycles rather than six independent logs. Plausible structures include:

- an Order flow beginning at `Create Order` and ending at `Close Order`;
- Package and Delivery flows around packing, dispatch, and confirmation;
- an Invoice flow from issue through repeated payment recording;
- synchronization around P1-related events and V1-related events.

P1 may induce multi-object synchronization because one package operation involves I1/O100 and I3/O200. V1 similarly synchronizes O100 and O200 at issue and at the M1/M2 payment events.

The exact net is algorithm- and parameter-dependent. It is not a uniquely determined causal interpretation of the narrative; discovered places and token semantics must be checked against the chosen E2O policy.

### Object-interactions summary

The summary should highlight high-connectivity objects and co-occurrence pairs:

- **P1** interacts with I1 and I3, D1, O100, and O200.
- **V1** interacts with O100, O200, M1, and M2.
- **M1** and **M2** are indirectly linked through their shared Invoice V1 and co-occur with V1 and both Orders at their respective payment events.
- **O100** has broader logistics involvement than O200 because it has two Items, two Packages, and two Deliveries.
- **O200** converges with O100 through P1 and V1 despite being a distinct Order.

The exact output schema and counting convention depend on the PM4Py version.

## 6. Modeling alternatives

### 1. Source-minimal E2O relations

Only attach each event to objects explicitly named as immediate event participants:

- Pack P1 relates to P1, I1, and I3, but not directly to O100/O200.
- Dispatch D1/P1 relates to D1 and P1, perhaps not Items or Orders.
- Payment M1 relates to M1 and V1, but not directly to Orders.

O2O retains all structural business relationships. Package and Invoice projections remain informative, but Order flattening becomes much shorter and omits logistics/payment steps. OTG and ET–OT are sparser. This is closest to strict source-system observation.

### 2. Full operational involvement

Use the policy implemented above: relate logistics events directly to Package, Delivery, Items, and affected Orders; relate invoice/payment events directly to V1 and both Orders.

This produces richer Order traces and makes convergence visible directly at event level. It also increases interaction counts and creates more OC-DFG edges. The cost is relation inflation and a greater need for provenance-aware qualifiers.

### 3. O2O-propagated analytical relations

Store source-minimal E2O as authoritative data, then derive a second analytical relation set by traversing:

- DeliveryPackageItemOrder;
- PaymentInvoiceOrder.

The resulting discovery may resemble the full-involvement policy, but derived links must be marked, for example with `relation_origin="derived"` or qualifiers prefixed by `derived_`. Otherwise consumers may incorrectly treat inference as direct observation.

### 4. Lifecycle-owner-only relations

Attach each event only to the object whose lifecycle it most directly advances:

- Pack to Package;
- Dispatch/confirm to Delivery;
- issue to Invoice;
- payment record to Payment.

All cross-object semantics remain in O2O. Flattened traces become very short, ET–OT becomes nearly one-to-one, and OC discovery may miss synchronization because shared events no longer connect the relevant objects directly. This is clean but analytically sparse.

### 5. Selective propagation

Propagate logistics to Orders but not Items, or propagate finance to Invoice and Orders but not vice versa. This can support a specific analysis while controlling density. For example, Order fulfillment analysis may justify direct Order links for dispatch and delivery, while Item-level payment links would usually be unjustified. Discovery changes accordingly, but the underlying P1/V1 business story does not.

## 7. Failure modes

1. **Relation inflation:** attaching every downstream event to every transitively reachable object can create dense, noisy graphs and exaggerated interaction frequencies.

2. **Missing direct E2O links:** if an analysis expects event co-participation, keeping a relationship only in O2O may cause Order traces to omit shipping or payment behavior.

3. **Treating O2O propagation as observation:** an inferred DeliveryOrder relation is not necessarily a source-recorded fact. Without provenance, users may overstate data quality or causality.

4. **Duplicate shared events after flattening:** e07, e11, e12, e13, and e15 appear in multiple Order traces. Counting rows across flattened traces would overcount executions.

5. **Ambiguous payment allocation:** M1=100 and M2=150 settle V1, but the narrative does not allocate either amount between O100 and O200. Direct Order links must not be interpreted as monetary allocation.

6. **Overly short Payment traces:** each Payment has one event, so Payment flattening gives no lifecycle order or useful DFG edges.

7. **Constructor/API version mismatch:** an installed PM4Py version may expose a different OCEL import path, constructor signature, visualization name, or discovery return format. The adapter should change only the API boundary, not DataFrame semantics.

8. **False total order for same-time events:** a traditional trace representation may impose row or event-ID order on timestamp ties. This example has no ties, but a robust implementation must not infer causality from arbitrary ordering when ties occur.

9. **Inconsistent copied columns:** if relation activity or timestamp differs from the referenced event, PM4Py may produce incorrect ordering or activity labels. The join-based construction and assertions prevent this.

10. **O2O direction reversal:** encoding ItemOrder while documenting OrderItem changes directional summaries and traversal logic.

11. **Duplicate relation rows:** repeated `(event, object, qualifier)` rows can inflate frequencies and interaction statistics without adding semantics.
