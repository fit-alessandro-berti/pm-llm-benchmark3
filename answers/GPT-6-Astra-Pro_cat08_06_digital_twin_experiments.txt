# 1. Model scope and state variables

**Build a shared-resource, calendar-aware discrete-event simulation, augmented with explicit relationships between applications.** PM4Py should support log preparation, process-model handling, and diagnostics; a separate simulation engine should implement resource contention, applicant behavior, scheduling decisions, and policy changes.

The central modeling principle is that **case durations are outputs of interacting mechanisms—not independent durations sampled for complete historical variants**. The supplied context explicitly identifies architect submission bursts, related applications, geographic inspection opportunities, and neighborhood objections affecting multiple cases. These mechanisms must survive the transition from the flattened log to the simulator.  

## Boundary and observation clocks

The operational boundary should include application submission through the initial permit/rejection decision, plus modeled reopening and appeal episodes. Report **time to initial decision** separately from **time to final disposition after modeled appeals**; the supplied material does not establish an appeal-filing window or a definitive final-closure rule.

For D1 and D7, extend the boundary upstream to when an applicant is ready to begin the submission process. Maintain two clocks:

* **Municipal elapsed time:** formal submission to decision.
* **Applicant-experienced elapsed time:** preparation/checker/appointment entry to decision.

Otherwise, delaying formal submission could appear to improve performance without reducing the applicant’s total delay.

## Entities and state

| Entity            | Required state                                                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application       | Case type, district, architect, value, observed requirement flags, verified or imputed missing attributes, submission time, preparation-entry time, policy version, age, current outcome, priority, rework counts, and appeal status. |
| Activity instance | Activity and occurrence ID, enabling time, queue-entry time, start/resume/pause/completion times, remaining work, required skills, assigned resource, result version, and blocking reason.                                            |
| Resource          | Skills, case-type eligibility, dated availability, current assignment, remaining work, non-permit duties, and—where relevant—location.                                                                                                |
| Dependency group  | Related-case membership and provenance, architect response state, inspection-bundle membership, and shared neighborhood-objection state.                                                                                              |
| System            | Shared queues, scheduled future events, inspection routes, available appointment slots, council calendar, backlog by stage and age, and active policy configuration.                                                                  |

Retain **observed, reconstructed, and scenario-imputed** values as separate fields. A neighborhood group inferred for sensitivity analysis must not be presented as an observed relationship.

## Control-flow interpretation

The supplied process tree is a useful structural starting point, but not a complete executable specification. It permits parallel Planning, Fire-safety, and Environmental reviews, represents optional activities without data guards, and contains only completeness and inspection loops. It does not encode the stated Planning, Legal, or appeal-related rework. 

Three extensions are necessary:

1. **Guarded routing and synchronization.** Known requirements override probabilistic routing. Decision drafting becomes eligible only when every applicable prerequisite has a valid result. Initially retain the tree’s review-join → public notice → inspection ordering; relaxing that ordering would be a separate, authorized structural experiment.
2. **Versioned rework.** A revision invalidates specified results and dependent work—not necessarily the entire case. In-flight tasks must not subsequently publish stale results as valid. Planning, inspection, legal, and appeal rework need distinct return points.
3. **Explicit observation mapping.** `Completeness rework` is a visible tree activity but is absent between the repeated completeness checks in P001. Do not insert it into the historical log as an observed event. Document whether the executable model treats it as an internal transition or whether instrumentation is missing.

D5 should create a **pre-check**, not automatically remove the final required legal control. D2 should record an auditable exemption decision and omit inspection scheduling only where no inspection-related work remains.

Cross-case mechanisms should include shared architect-response shocks, shared objection extensions, and inspection bundles. Sharing an architect or district establishes a **potential relationship**, not an automatic requirement that every such case wait for every other case.

# 2. Parameter-estimation plan

## Start with consistency and identifiability checks

The full 18-month data, rather than the two-case excerpt, would be needed for estimation. The excerpt supports implementation tests and exposes issues that calibration must resolve.

**Calendar consistency.** For example, P001’s Fire-safety review is recorded on Saturday, January 17, 2026, outside the stated Tuesday–Thursday availability. Its Site inspection is recorded on Saturday, February 7, outside the stated field-visit days. Possible explanations include delayed recording, authorized exceptions, or an illustrative excerpt that is not calendar-faithful. These are hypotheses, not established explanations. Do not silently expand the calendars or delete these records.  

**Capacity consistency.** A conditional offered-load check is particularly important:

Assume that 31,200 represents arrivals over 18 months, each requires one Planning review, and the 3.5-hour median is genuine hands-on work representative of those arrivals. For nonnegative service time with median \(m\), the mean is at least \(m/2\). Planning work would therefore require at least approximately

$$
\frac{31{,}200}{18}\times\frac{3.5}{2}
=3{,}033\text{ planner-hours/month}.
$$

Using an explicitly illustrative 21.7 working days per month, eight planners supply approximately

$$
8\times8\times21.7=1{,}389\text{ scheduled hours/month},
$$

before Decision drafting or rework. This is a **conditional workload bound, not an observed utilization estimate**. The volume, cohort definition, service-time interpretation, staffing coverage, or backlog growth must be reconciled before treating the summaries as a stable baseline.  

A simulator that quietly scales down service times until the queues look plausible would conceal this issue rather than resolve it.

## Estimation components

| Component                       | Estimation approach                                                                                                                                                   | Limitation or safeguard                                                                                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Arrivals                        | Identify initial submissions; fit calendar-exposure-adjusted month, weekday, and intraday effects, with trend and architect-level clustering.                         | The supplied ratios do not determine all month/day intensities. Normalize against the actual observation window and avoid adding bursts on top of an already complete arrival total. |
| Architect bursts and attributes | Fit architect-week cluster sizes and within-cluster submission offsets; jointly sample case type, district, value, and requirement flags.                             | Preserve the top-20 architects’ 31% share without assuming they generate all dependency effects.                                                                                     |
| Active service                  | Use verified work segments or reliable start/completion records corrected for interruptions and allocation. Fit activity-, type-, and rework-dependent distributions. | Start-to-completion elapsed time can still contain inactivity. Completion-only gaps cannot identify active work.                                                                     |
| Queue waiting                   | Reconstruct enabling from all applicable prerequisites, then measure enabling-to-start where starts exist.                                                            | Queue waiting should normally emerge from the simulation; historical waiting summaries are validation targets, not extra sampled delays.                                             |
| Routing                         | Enforce known rules; estimate remaining decisions conditional on case attributes, results, and policy version.                                                        | Missing area, district sensitivity, and violation history are not negative findings.                                                                                                 |
| Rework                          | Estimate return destination, repeated work, response delay, and probabilities conditional on type, results, and iteration number.                                     | Repeated labels alone do not reliably identify rework reasons. Audit a sample of the unstructured text.                                                                              |
| External responses              | Estimate request-to-receipt and consultant-response distributions, including open requests and architect-level correlation.                                           | Do not assign these delays to municipal service capacity.                                                                                                                            |
| Objections                      | Use an explicitly latent extension model and audited external evidence where available.                                                                               | Long public-notice duration is a proxy, not a directly observed objection label.                                                                                                     |
| Calendars and travel            | Expand HR data into dated resource availability; estimate travel from dispatch/route records or audited samples.                                                      | Distinguish geographic travel, batch formation, applicant readiness, and inspector queueing.                                                                                         |

The arrival model must reproduce the supplied seasonal and weekday relationships, while allowing correlated submissions rather than assuming an independent Poisson stream for every application. 

For a preliminary positive service-time distribution, a lognormal matching median \(m\) and p90 \(q\) has

$$
\mu=\log m,\qquad
\sigma=\frac{\log(q/m)}{1.28155}.
$$

This is a **candidate parameterization**, not an identified distribution. Compare it with other plausible families and audited empirical distributions. Introduce a shared case-complexity effect so that unusually difficult applications can have several long activities rather than independently sampled difficulty at each stage.

Do not apply that formula mechanically to Public-notice period or “3h + travel.” The notice summary describes a fixed minimum and objection-related extension, while the inspection summary mixes service and travel. The 60-day notice figure does not establish an unconditional p90 or an objection probability. 

For a properly reconstructed activity instance:

$$
W_{\text{elapsed}}
=t_{\text{start}}-t_{\text{enabled}},
$$

where enabling is determined from the applicable prerequisite results—not simply the previous event in timestamp order. Separate resource contention, calendar closure, intentional batching, and external blocking in the simulation ledger.

Use PM4Py for formatting, variants, frequency/performance DFGs, process-tree parsing, and conformance diagnostics. A performance DFG summarizes timestamp-based directly-follows performance; it is not a resource-contention model or proof of causal precedence between parallel reviews. ([GitHub][1])

For a lower-is-better metric \(Y\), an interaction contrast is

$$
I_{AB}=Y_{AB}-Y_A-Y_B+Y_0.
$$

A negative contrast indicates additional improvement beyond the sum of standalone improvements on that metric. Report its uncertainty.

A particularly important interaction is **D2 × D3**: eliminating eligible inspections can release capacity while making remaining bundles slower to fill. D3 therefore needs a timer-driven maximum-wait release, not a rule that waits indefinitely for the next compatible application.

# 5. Warm-up, replications, and uncertainty treatment

## Initialization and warm-up

For an **operational forecast**, initialize from a dated snapshot containing active cases, completed results, queued and in-progress work, outstanding requests, bundle membership, and calendar commitments. Do not discard an artificial warm-up period: current backlog is part of the decision problem.

Residual times must be conditioned on current progress. An applicant request already unanswered for 30 days should not receive a fresh unconditional response-time draw.

For **longer-term structural comparisons** without a reliable snapshot, use ensembles of plausible initial backlogs. Start with a proposed 12-month initialization period followed by 24 measurement months, and compare 6/12/24-month initialization choices at matching seasonal phases. Assess convergence of month-specific backlog and age profiles—not just an overall average.

**Do not warm away instability.** If offered workload exceeds feasible capacity, growing backlog is a finding.

## Run length and censoring

Measure at least two complete annual cycles for seasonal policy comparisons. Continue ordinary arrivals during a follow-up period for the measurement cohort; stopping all new arrivals would artificially improve the completion times of outstanding cases.

A proposed starting configuration is 24 measurement months plus 12 months of follow-up, extended where needed. Preserve unresolved cases as censored. If follow-up is insufficient to identify a p90 or p99, report that limitation and appropriate bounds rather than a completed-case-only quantile.

## Replications and random numbers

Use 30 independent pilot replications per setting, then allocate additional replications to credible contenders—typically 100–300 as a planning range, subject to a predeclared precision and computation budget.

A suggested precision target is a confidence-interval half-width for the **paired p90 difference** no greater than the larger of two days or 5% of baseline p90, and approximately one percentage point for key SLA-rate differences.

Use a recorded master seed, such as `20260907`, and mechanism-specific random streams. Pair policies on the same offered applications, case difficulty, calendar disruptions, and shared external shocks. Key draws by replication, mechanism, case/group, activity, and occurrence—not by the order in which the engine requests randomness. Otherwise, skipping an inspection can misalign every later draw.

## Separate uncertainty sources

Use an outer loop over plausible parameter draws or bootstrapped datasets and an inner loop over simulation replications:

$$
Y_{p,b,r}
=
\text{outcome under policy }p,
\text{ parameter draw }b,
\text{ replication }r.
$$

Report conditional Monte Carlo intervals for paired policy differences separately from parameter uncertainty. Keep structural scenarios—such as alternative calendar interpretations—as explicit scenario envelopes unless probabilities over those models are defensible.

Historical resampling should preserve relevant temporal and dependency blocks. Individual-case bootstrapping alone would destroy the shared shocks the twin is intended to represent.

For heavy tails, retain extreme observations, model censoring, report restricted mean duration and exceedance probabilities, and treat p99 as exploratory when the effective number of independent clusters is small. Do not truncate long simulated cases merely to stabilize a mean.

# 6. Validation strategy

Validation should proceed through explicit gates rather than one overall goodness-of-fit score.

| Validation type                     | Checks and evidence                                                                                                                                                                                                                                               |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Face validation**                 | Walk clerks, planners, reviewers, inspectors, schedulers, and applicant representatives through difficult scenarios: missing documents, stale reviews, objections, council closures, no-shows, and partially formed inspection bundles.                           |
| **Event-log replay validation**     | Replay historical submissions and observed attributes; progressively condition on observed routing and external responses. Check whether the model can explain event ordering and timing without forcing observed completion times or hiding missing transitions. |
| **Distributional validation**       | Compare duration distributions, rework counts, outcome shares, stage waits, arrival bursts, and notice-duration tails by type, season, district, architect group, and consistently defined variant group.                                                         |
| **Resource-utilization validation** | Compare productive work, travel, overtime, and unavailable time against HR/operational evidence. Use available permit-working hours as a denominator and also report absolute hours. Completion counts alone do not establish utilization.                        |
| **Bottleneck validation**           | Record why each task is blocked and which prerequisite delays each join. Apply small controlled capacity/calendar changes to distinguish a resource constraint from external delay or synchronization. Repeat by season and case type.                            |
| **Out-of-sample validation**        | Use chronological fitting, tuning, and holdout windows—for example 12/3/3 months—while recognizing that 18 months provides limited seasonal replication and incomplete maturity for long cases.                                                                   |

Historical variant durations and stage-wait summaries should be checked together, not substituted for each other. Matching a variant’s p90 while producing impossible staffing requirements is not successful validation. 

Before empirical validation, enforce implementation invariants:

* No resource double-booking, prohibited assignment, or unmodeled work outside availability.
* No drafting or decision with missing or invalid required results; no D2 exemption without verified eligibility.
* No notice completion before its applicable minimum, duplicated route travel, lost application, or bundle left waiting after its maximum-wait timer expires.

Generate both a **full simulation event log** and an **observation-equivalent log** that reflects the historical logging limitations. Compare historical completion-only data with the latter, while validating resource consumption and synchronization against the full internal ledger.

Finally, historical fit does not identify D1–D9’s causal effects. Use appropriately authorized pilots or staged rollouts to estimate uptake, effort changes, defect consequences, and spillovers. Where cases share architects, districts, or resources, assess outcomes for the whole affected portfolio—not only the treated applications.

# 7. Decision criteria

Select policies through **hard admissibility checks followed by a multi-objective comparison**. The source supplies no SLA deadlines, cost budget, or acceptable defect-risk threshold. Those must remain named inputs rather than be inferred from historical medians or variant durations.

The following numerical ranges are **proposed decision thresholds for agreement with the municipality**.

| Dimension                 | Metric                                                                                                                    | Proposed selection criterion                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Median and tail duration  | Median, p90, p95; restricted mean; initial decision and appeal-inclusive disposition separately.                          | Seek at least 5% median or 10% p90 improvement, without unacceptable deterioration in other types.                                                  |
| SLA compliance            | \(P(T\leq S_k)\) for each case type \(k\), using the approved clock and treatment of pauses.                              | An agreed target such as 95%, or a material improvement where that target is currently infeasible. Report percentage-point changes and uncertainty. |
| District fairness         | Raw and case-mix-standardized durations, compliance, and oldest-case age.                                                 | Suggested non-inferiority margin: no district p90 deterioration beyond the larger of two days or 5%, with uncertainty and sample-size checks.       |
| Architect fairness        | Top-20 versus other architects, small-architect appointment access, bundle waiting, and comparable-case outcomes.         | Benefits must not depend on systematically deprioritizing small or infrequent applicants.                                                           |
| Resource sustainability   | Active utilization, overtime, travel, duty displacement, and staff-specific workload.                                     | Treat sustained productive utilization above roughly 85–90% as a review trigger, not a universal hard limit or optimal target.                      |
| Rework and quality        | Any-rework probability, repeated activities per submitted case, appeals, verified errors, and downstream defects.         | No control violations; a provisional rework non-inferiority margin such as +1 percentage point. D2 needs a separately approved safety gate.         |
| Backlog and recovery      | Work in progress, age distribution, net backlog growth, peak carryover, and recovery time.                                | No hidden instability in the baseline-demand scenario; agree a seasonal recovery target, initially testing four to eight weeks.                     |
| Cost and applicant burden | Municipal hours/costs, temporary staffing, checker/triage effort, preparation time, appointment waiting, and abandonment. | Stay within an agreed budget and avoid “improvement” caused only by shifting delay outside the formal submission clock.                             |
| Robustness                | Paired effects across parameter draws and stress scenarios; downside risk and regret.                                     | Prefer policies whose benefits survive plausible uncertainty. Do not average away failures of mandatory controls or severe subgroup harm.           |

Count permits and rejections separately. Faster rejection is not automatically better service, and lower formal intake is not automatically higher efficiency.

**Decision recommendation:** first resolve baseline workload and calendar inconsistencies. Then compare bounded, reversible configurations of D1, D3, and D4, alongside D2 only where eligibility and safety can be verified. D5/D6 require close monitoring of downstream congestion; D8/D9 especially depend on better evidence about classification and objection mechanisms.

D10 should advance only if its joint benefits exceed its costs and disadvantages under the interaction experiments. The supplied evidence does not justify declaring it—or any other policy—optimal.

def load_excerpt(source_tz: str) -> pd.DataFrame:
    """Supply the source timezone explicitly; it is absent from the log."""
    events = pd.read_csv(StringIO(EVENTS))
    attributes = pd.read_csv(StringIO(ATTRIBUTES))
    df = events.merge(attributes, on=CASE, validate="many_to_one")

    if df[[CASE, ACT, END]].isna().any().any():
        raise ValueError("Missing mandatory event fields")

        pd.to_datetime(df[END], errors="raise")
        .dt.tz_localize(
            source_tz, ambiguous="raise", nonexistent="raise"
        )
        .dt.tz_convert("UTC")
    )
    return (
        df.sort_values([CASE, END], kind="stable")
        .reset_index(drop=True)

        out.groupby(CASE)[END].diff().dt.total_seconds()
    )
    out["service_elapsed_s"] = np.nan
    out["queue_elapsed_s"] = np.nan
    out["active_service_s"] = np.nan

    if "start_timestamp" in out:
        service = (
            out[END] - out["start_timestamp"]
        ).dt.total_seconds()
        if service.dropna().lt(0).any():
            raise ValueError("Completion precedes start")
        out["service_elapsed_s"] = service

        # Enabling must use ALL applicable predecessors, not row order.
        if "enabled_timestamp" in out:
            waiting = (
                out["start_timestamp"] - out["enabled_timestamp"]
            ).dt.total_seconds()
            if waiting.dropna().lt(0).any():
                raise ValueError("Start precedes enabling")
            out["queue_elapsed_s"] = waiting

    # Fill active_service_s only from verified work/allocation segments.
    # Missing starts in this excerpt therefore remain missing.
    return out


def mine_log(df: pd.DataFrame) -> tuple[pd.DataFrame, dict[str, Any]]:
    import pm4py

    log = pm4py.format_dataframe(
        df.copy(),
        case_id=CASE,
        activity_key=ACT,
        timestamp_key=END,
    )

    # Parsing does NOT add guards, calendars, or omitted rework paths.
    tree = pm4py.parse_process_tree(" ".join(TREE.split()))
    variants = pm4py.get_variants_as_tuples(log)
    dfg, starts, ends = pm4py.discover_dfg(log)
    pdfg, _, _ = pm4py.discover_performance_dfg(
        log, business_hours=False, perf_aggregation_key="all"
    )

    submissions = log.loc[
        log[ACT].eq("Submit application")
    ].copy()
    if submissions[CASE].duplicated().any():
        raise ValueError(
            "Resolve duplicate initial submissions before arrival analysis"
        )
    arrival_s = (
        pm4py.get_case_arrival_average(submissions)
        if len(submissions) > 1 else np.nan
    )

    timed = timing_columns(log)
    interval_medians = None
    if "start_timestamp" in timed:
        valid = timed.dropna(
            subset=["start_timestamp", END]
        ).copy()
        if len(valid):
            interval_medians = pm4py.get_service_time(
                valid,
                start_timestamp_key="start_timestamp",
                aggregation_measure="median",
            )
            # These are elapsed intervals, not necessarily active work.

    return timed, dict(
        pm4py_version=pm4py.__version__,
        tree=tree,
        variants=variants,
        dfg=dfg,
        start_activities=starts,
        end_activities=ends,
        performance_dfg=pdfg,
        arrival_average_s=arrival_s,
        interval_medians_s=interval_medians,
    )


@dataclass(frozen=True)
class KeyedRandom:
    root: int
    parameter_draw: int
    replication: int

    def stream(self, *key: str | int) -> np.random.Generator:
        # Unique mechanism/entity/activity/visit/draw key.
        # No policy ID: shared mechanisms remain paired across policies.
        payload = json.dumps([
            self.root, self.parameter_draw, self.replication, *key
        ])
        seed = int.from_bytes(
            sha256(payload.encode()).digest()[:16], "big"
        )
        return np.random.default_rng(seed)

@dataclass
class PermitState:
    case_id: str
    attrs: dict[str, Any]
    required: set[str]
    valid_results: set[str] = field(default_factory=set)
    revision: int = 0
    visits: dict[str, int] = field(default_factory=dict)

    def invalidate(self, affected: set[str]) -> None:
        self.revision += 1
        self.valid_results.difference_update(affected)

    def drafting_ready(self) -> bool:
        return self.required <= self.valid_results


class RoutingPolicy:
    @staticmethod
    def required_for_drafting(attrs,
                              experiment: Experiment) -> set[str]:
        def resolved_bool(key):
            value = attrs.get(key)
            if not isinstance(value, (bool, np.bool_)):
                raise ValueError(f"Unresolved routing fact: {key}")
            return bool(value)

        required = {"Planning review"}

        fire = (
            attrs["requires_fire"] == "yes"
            or resolved_bool("area_requires_fire")
        )
        environment = (
            attrs["requires_environment"] == "yes"
            or resolved_bool("sensitive_district")
        )
        notice = (
            attrs["case_type"] == "Complex variance"
            or attrs["requires_public_notice"] == "yes"
            or resolved_bool("other_notice_required")
        )

        for applies, activity in (
            (fire, "Fire-safety review"),
            (environment, "Environmental review"),
            (notice, "Public-notice period"),
        ):
            if applies:
                required.add(activity)

        # Unknown violation history is NOT exemption evidence.
        prior = attrs.get("prior_violations")
        clear_history = (
            isinstance(prior, (bool, np.bool_)) and not bool(prior)
        )
        waive = (
            "D2" in experiment.interventions
            and attrs["case_type"] == "Simple renovation"
            and attrs["application_value"] < 50000
            and clear_history
            and attrs.get("violation_history_verified") is True
        )
        if not waive:
            required.add("Site inspection")

        return required


@dataclass
class RunOutput:
    events: pd.DataFrame
    cases: pd.DataFrame
    resource_ledger: pd.DataFrame
    # events: full lifecycle/enabling/result-version information.
    # cases: includes open/censored cases and upstream waiting.
    # ledger: active work, travel, availability, and queue snapshots.


class DigitalTwin:
    def __init__(self, theta, snapshot,
                 calendars: ResourceCalendars):
        self.theta = theta
        self.snapshot = snapshot
        self.calendars = calendars
        self.cases: dict[str, PermitState] = {}
        self.queues: dict[str, list] = {}  # SHARED resource queues.
        self.bundles: dict[str, list[str]] = {}

    def run(self, offers, shared_shocks, experiment, rng,
            start, cohort_end, observation_end) -> RunOutput:
        """Calendar-aware DES adapter contract.

        - Apply D1/D7 before formal submission.
        - Enforce guarded routing and versioned joins.
        - Advance one shared event calendar with skill constraints.
        - Pause resumable work at closures.
        - Place inspection routes in feasible field-work windows.
        - Dispatch bundles at size OR maximum-wait timer.
        - Charge travel once per route, not once per bundled case.
        - Propagate shared shocks to all linked applications.
        - Model response/notice timers separately from active service.
        - Do not add empirical queue waits as extra delays.
        - Retain required final legal control under D5.
        - Continue arrivals during cohort follow-up.
        """
        raise NotImplementedError(
            "Implement a shared-resource, calendar-aware DES"
        )


def run_experiments(
    experiments: Iterable[Experiment],
    parameter_draws,
    snapshot,
    calendars,
    arrivals: ArrivalModel,
    dependencies: DependencyModel,
    start,
    cohort_end,
    observation_end,
    replications=30,
    root_seed=20260907,
    engine_factory: Callable[..., DigitalTwin] = DigitalTwin,
):
    if not start < cohort_end <= observation_end:
        raise ValueError("Invalid observation/cohort window")

    designs = list(experiments)
    for draw_id, theta in enumerate(parameter_draws):
        for rep in range(replications):
            rng = KeyedRandom(root_seed, draw_id, rep)

            # One shared stochastic world for all policies in this pair.
            offers = arrivals.generate(
                start, observation_end, theta, rng
            )
            shocks = dependencies.generate(
                offers, start, observation_end, theta, rng
            )

            for experiment in designs:
                twin = engine_factory(
                    deepcopy(theta),
                    deepcopy(snapshot),
                    deepcopy(calendars),
                )
                output = twin.run(
                    deepcopy(offers),
                    deepcopy(shocks),
                    experiment,
                    rng,
                    start,
                    cohort_end,
                    observation_end,
                )
                yield dict(
                    parameter_draw=draw_id,
                    replication=rep,
                    experiment=experiment.name,
                    output=output,
                )
