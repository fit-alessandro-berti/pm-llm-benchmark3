# 4. Network and conformance analyses

```python
import numpy as np
import pandas as pd
import pm4py

# Load and standardize
df = pd.read_csv("procure_to_pay.csv")
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True, errors="coerce")
df = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
)

# Use an "effective" human resource for sensitivity tests
df["effective_resource"] = df["org:resource"]
shared_gita = df["org:resource"].eq("Approver_Gita") & df["entered_by"].notna()
df.loc[shared_gita, "effective_resource"] = df.loc[shared_gita, "entered_by"]

# 1) Four-eyes filters
po_viol = pm4py.filter_four_eyes_principle(
    df,
    "Create Purchase Order",
    "Approve Purchase Order",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
    resource_key="effective_resource",
    keep_violations=True,
)

bank_pay_viol = pm4py.filter_four_eyes_principle(
    df,
    "Change Vendor Bank Details",
    "Payment Approval",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
    resource_key="effective_resource",
    keep_violations=True,
)

# 2) Networks: compare on full data and after cleaning shared-account / legacy effects
handover = pm4py.discover_handover_of_work_network(
    df, beta=0, resource_key="effective_resource",
    timestamp_key="time:timestamp", case_id_key="case:concept:name"
)
working_together = pm4py.discover_working_together_network(
    df, resource_key="effective_resource",
    timestamp_key="time:timestamp", case_id_key="case:concept:name"
)
subcontracting = pm4py.discover_subcontracting_network(
    df, n=2, resource_key="effective_resource",
    timestamp_key="time:timestamp", case_id_key="case:concept:name"
)

# 3) Emergency vs non-emergency comparison
emerg = pm4py.filter_event_attribute_values(df, "emergency_flag", [True])
non_emerg = pm4py.filter_event_attribute_values(df, "emergency_flag", [True], retain=False)

emerg_variants = pm4py.get_variants(emerg)
non_emerg_variants = pm4py.get_variants(non_emerg)

emerg_fast_po = pm4py.filter_paths_performance(
    emerg,
    ("Create Purchase Order", "Approve Purchase Order"),
    min_performance=0,
    max_performance=15 * 60,
    keep=True,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)

non_emerg_fast_po = pm4py.filter_paths_performance(
    non_emerg,
    ("Create Purchase Order", "Approve Purchase Order"),
    min_performance=0,
    max_performance=15 * 60,
    keep=True,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)

# 4) Timing diagnostics
df_wait = pm4py.insert_case_service_waiting_time(
    df,
    service_time_column="@@service_time",
    sojourn_time_column="@@sojourn_time",
    waiting_time_column="@@waiting_time",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)

fast_bank_pay = pm4py.filter_paths_performance(
    df,
    ("Change Vendor Bank Details", "Payment Approval"),
    min_performance=0,
    max_performance=30 * 60,
    keep=True,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)

segment = pm4py.filter_between(
    df,
    "Emergency Override",
    "Retrospective Justification",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)

# 5) Declarative / skeleton checks
# Declare can test the basic response rule: if Emergency Override occurs,
# Retrospective Justification should eventually occur in the same case.
declare_model = pm4py.discover_declare(
    emerg,
    allowed_templates={"response"},
    considered_activities={"Emergency Override", "Retrospective Justification"},
    min_support_ratio=0.8,
    min_confidence_ratio=0.8,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    case_id_key="case:concept:name",
)
declare_diag = pm4py.conformance_declare(
    emerg, declare_model, return_diagnostics_dataframe=True
)

# Add a custom audit check for "different human" and "within 3 working days"
eo = df[df["concept:name"].eq("Emergency Override")][
    ["case:concept:name", "time:timestamp", "effective_resource", "source_system"]
].rename(columns={
    "time:timestamp": "eo_ts",
    "effective_resource": "eo_res",
    "source_system": "eo_src",
})
rj = df[df["concept:name"].eq("Retrospective Justification")][
    ["case:concept:name", "time:timestamp", "effective_resource", "source_system"]
].rename(columns={
    "time:timestamp": "rj_ts",
    "effective_resource": "rj_res",

pairs = eo.merge(rj, on="case:concept:name", how="left")

pairs["working_days"] = np.busday_count(
    pairs["eo_ts"].dt.date.values.astype("datetime64[D]"),
    pairs["rj_ts"].dt.date.values.astype("datetime64[D]")
)
pairs["same_human"] = pairs["eo_res"].eq(pairs["rj_res"])
retro_breaches = pairs[
    pairs["rj_ts"].isna() |
    pairs["same_human"] |
    (pairs["working_days"] > 3)
]

# Optional log-skeleton baseline: learn from routine clean cases, then test exceptions

legacy = pm4py.filter_event_attribute_values(df, "source_system", ["legacy_erp"])
quarter_close = pm4py.filter_event_attribute_values(df, "source_system", ["quarter_close_upload"])
```

- Compare emergency and non-emergency subsets separately. If fast approvals and PO-approval breaches are mostly confined to emergency cases with proper retrospective review, that supports operational urgency rather than collusion.

# 5. Evidence that would materially change the assessment

**Evidence that would increase concern**

- Raw system logs showing the same natural person performed both `Change Vendor Bank Details` and `Payment Approval`, not just the same shared or mapped account.
- `V-77x` bank-detail changes with no maintenance ticket, no vendor callback verification, and payment released within minutes to a newly changed account.
- Repeated use of the same beneficiary bank account across multiple vendors, or a mismatch between vendor legal name and destination account data.
- Access logs showing overlapping credentials, unusual IP/device patterns, or after-hours changes for the `Lena/Kim` cases.
- Non-emergency cases in the `Carla/Gita` or `Dan/Hugo` clusters with the same fast timing, same-person approvals, or missing retrospective justification.
- Missing `Goods Receipt` / `Invoice Match` evidence, or repeated payment approvals after failed automated-match exceptions without documented reason.

**Evidence that would reduce concern**

- A documented `V-77x` banking-platform migration plan with signed approvals, upload control totals, batch IDs, and reconciled vendor callback confirmations.
- Source-system mapping documentation proving that `legacy_erp` conflated `Bot_PO` and human approvers, plus corrected extracts showing segregation was preserved.
- Detailed `entered_by` and assistant audit trail demonstrating that the shared `Approver_Gita` account masks multiple distinct humans rather than one person doing both steps.
- Emergency incident tickets, on-call rosters, clinical stock-out records, or facilities outage logs matching the fast `Carla/Gita` and `Dan/Hugo` cases.
- Original quarter-close migration files showing that same-timestamp retrospective justifications were imported artifacts rather than live workflow behavior.
- Policy or SOP evidence that some vendor-master maintenance activities are intentionally bundled, with independent downstream payment controls outside the visible event log.

# 6. Cautious audit-report wording

The event-log evidence is most consistent with a combination of legitimate emergency handling, informal specialization, and material data-quality limitations, with a narrower subgroup that warrants higher-priority review. The strongest benign pattern is seen in the `Buyer_Carla -> Approver_Gita` and `Buyer_Dan -> Manager_Hugo` flows: these cases are heavily concentrated in emergency medical supplies and weekend facilities repairs, and their unusually short approval times are therefore plausibly explained by operational urgency. Those cases still represent control pressure and possible compensating-control weakness, but they do not, on their own, support an allegation of collusion or other misconduct.

The most concerning subgroup is `VendorMaster_Lena + AP_Kim`, particularly cases involving vendor family `V-77x`. That subgroup combines `Change Vendor Bank Details` and `Payment Approval` exceptions, high-value transactions, very short elapsed times, strong vendor concentration, and heavy use of `manual_upload`. This pattern does not establish fraud or collusion as fact, but it is less readily explained by ordinary workload specialization alone and should be the first target for targeted document review, vendor-master testing, and access-log analysis.

Interpretation of all resource-based findings is constrained by known data-quality issues, including a shared `Approver_Gita` account, `quarter_close_upload` migration artifacts, missing linkage to vendor-maintenance tickets, and `legacy_erp` mapping errors that can blur bot and human activity. Accordingly, we recommend targeted follow-up on the `V-77x` bank-change/payment cases, non-emergency fast-approval exceptions, and a focused data-quality remediation exercise before any stronger conclusion is drawn.
