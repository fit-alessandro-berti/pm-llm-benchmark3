**Discussion of key audit points:**

- **True concurrency vs arbitrary interleaving:** The POWL model specifies that `assess_risk` and `prepare_evidence` are unordered after `register`, meaning they may fire in any order but not truly in parallel. In the Petri net, they become concurrent transitions enabled from the same place, which pm4py may represent with a single place and two outgoing transitions. Conversion to BPMN often maps this to a sequence flow or, if fortunate, a parallel gateway. The audit marks this as `approximated` for PetriBPMN because BPMN’s parallel gateway enforces true concurrency (both branches fire simultaneously in some semantics), potentially overapproximating the source’s arbitrary interleaving. Conversely, a sequence flow would underapproximate by forcing order.

- **Lack of an edge between Optional Legal Review and verification:** The source has no controlflow edge between `optional_legal` and `verification_loop`; both are enabled after `assess_risk` and are independent. In the Petri net, both have edges from the `assess_risk` transition but no mutual edge. When converting to BPMN, this independence may be modeled as two separate exclusive gateways downstream of `Assess Risk`, or as a single exclusive gateway with overlapping paths. The `ambiguous` term reflects that BPMN gateway placement can visually suggest ordering (e.g., one after another) even when the underlying net permits concurrency.

- **Silent optional behavior:** `skip_legal` is a `SilentTransition` with label `None`. In the Petri net, this becomes a tau transition. Hiding tau (as required in roundtrip validation) merges the XOR choice, making the “optional” aspect invisible in trace logs. The `PetriBPMN` and `BPMN round trip` columns mark this `ambiguous` because BPMN exclusive gateways typically model visible choices; a silent tauhidden choice may render as an alwaystaken path or be omitted entirely, losing the semantic nuance of optionality.

- **Binaryloop semantics:** `verification_loop` uses `Operator.LOOP` with children `[trial_body, correct_defect]`. The POwl semantics mandate at least one iteration of `configure_trial  inspect_trial  correct_defect`, with `correct_defect` separating each repetition. Petrinet conversion typically unrolls loops into cycles with a backedge. BPMN loop visualization (iteration markers) may or may not align with the `correct_defect` separator. The audit marks `PetriBPMN` and `BPMN round trip` as `approximated` because BPMN’s loop construct counts iterations globally, whereas the source ties iteration separation to `correct_defect` and has no explicit guard for termination.

- **Join before Release Change:** Both `optional_legal` and `verification_loop` have edges to `release_change`, modeling a synchronization/join. In the Petri net, this is a confluence of transitions. BPMN represents this as a parallel gateway (if both branches must complete) or as sequential completion depending on gateway type. The `expected preserved` terms for `POWLPetri` and `BPMN round trip` confirm that the join is structurally maintained, but `PetriBPMN` may approximate it with a parallel gateway, potentially altering the perceived semantics if the viewer reads “both must run in parallel” rather than “both must finish before release”.

- **Activitylabel uniqueness:** All transitions in the source POWL have distinct labels (`Register Change`, `Assess Risk`, etc.). pm4py’s conversions preserve labels as activity names. The audit confirms `validated preserved` across all pipelines; no label collision occurs. However, the silent `skip_legal` has label `None`, which may be dropped or renamed during BPMN export, an issue noted in the `ambiguous` entries for I3.

- **Initial and final markings:** The POWL source has a clear start (`register`) and end (`archive_change` after `release_change`). pm4py’s `convert_to_petri_net` sets initial marking to include the start transition’s place and final marking to include the end transition’s place. This mapping is `validated preserved` for all nets and roundtrips, as confirmed by the soundness diagnostics running without markingrelated errors.

- **Gateway or routingnode ambiguity in BPMN visualization:** BPMN’s exclusive (XOR) and parallel (AND) gateways map loosely from POWL’s `Operator.XOR` and structural concurrency. An XOR gateway with a silent child (`skip_legal`) can be misread as a standard decision point where both branches are visible, erasing the “optional/silent” semantics. A LOOP operator may render as a BPMN “loop” marker on a sequence flow, but without the `correct_defect` visual separator, the iteration semantics drift. These ambiguities are why the audit uses `approximated` and `ambiguous` terms and why visualsemantics review (Section 6) is necessary.

# ----------------------------------------------------------------------
# Bounded visibletrace exploration comparing roundtripped nets
# ----------------------------------------------------------------------
def explore_visible_traces(net, im, fm, max_visible=3, max_loop_iter=2, hide_labels=None):
    """Explore visible traces up to a bounded length, hiding tau (None) labels.

    Returns a set of trace strings (visible activities separated by '->') that
    end in the exact final marking fm, without infinite silent cycling, and
    respecting a loopiteration bound.
    """
    if hide_labels is None:
        hide_labels = {None}  # hide transitions with label None (tau)

    from pm4py.util import exec_utils
    from collections import deque

    # Helper: get enabled transitions at a marking, hide tau
    def get_enabled_visible(marking):
        enabled = pm4py.get_enabled_transitions(net, marking)
        visible = []
        for t in enabled:
            label = t.label
            if label is not None and label not in hide_labels:
                visible.append(t)
            # If label is None (tau) or in hide_labels, skip for visible trace
        return visible

    # Helper: advance marking by a transition
    def fire_transition(net, marking, t):
        # Use pm4py's lowlevel marking update; returns new marking
        try:
            new_marking = pm4py.apply_marking_change(net, marking, t, post=True)
            return new_marking
        except Exception:
            return None

    explored = set()
    # Initial marking
    init_marking = im
    # Queue: (current_marking, trace_string, loop_iteration_count)
    # loop_iteration_count tracks how many times we've gone through the verification loop
    queue = deque()
    queue.append((init_marking, "", 0))

    while queue:
        marking, trace, loop_cnt = queue.popleft()

        # Check if we are in the final marking – record trace if so
        if marking == fm:
            # Only record if trace is nonempty or we allow empty (initial = final)
            if trace not in explored:
                explored.add(trace)
            # Do not extend further from final marking (trace completed)
            continue

        # Bound: visible length + loop iteration guard
        # We count visible activities in trace
        visible_cnt = trace.count("->") + 1 if trace else 0
        if visible_cnt >= max_visible:
            continue  # do not extend beyond visible bound

        # Bound: loop iteration count – if we've exceeded max_loop_iter, stop extending
        if loop_cnt > max_loop_iter:
            continue

        enabled = get_enabled_visible(marking)
        for t in enabled:
            new_marking = fire_transition(net, marking, t)
            if new_marking is None:
                continue

            # Determine if this transition contributes to a loop iteration
            # Heuristic: if t is part of the verification loop (configure_trial, inspect_trial, correct_defect),
            # increment loop_cnt; else reset or keep.
            # Here we use a simple labelbased check for defensibility:
            label = t.label
            new_loop_cnt = loop_cnt
            if label in ("Configure Trial", "Inspect Trial", "Correct Defect"):
                # Only count as loop iteration if we are already in a loop-prone context
                # (rough heuristic: if trace already contains a loop marker or loop_cnt < max_loop_iter)
                if loop_cnt < max_loop_iter:
                    new_loop_cnt += 1
                else:
                    continue  # already at iteration bound
            else:
                new_loop_cnt = 0  # reset for nonloop activities

            new_trace = f"{trace}->{label}" if trace else str(label)
            queue.append((new_marking, new_trace, new_loop_cnt))

    return explored

# 6. Visual-Semantics Review

The BPMN rendering of the converted model may be misread even when the underlying accepting Petri net is behaviorally acceptable. Key sources of ambiguity include:

- **Parallel gateways (AND):** The unordered pair `assess_risk` / `prepare_evidence` may be visualized with a parallel gateway, suggesting that both activities occur simultaneously in every execution. In reality, the source allows arbitrary interleaving (any order, but not true concurrency). Viewers might infer parallel execution where only sequential interleaving is intended.

- **Exclusive gateways (XOR):** The optionallegal XOR with a silent `skip_legal` child is prone to misinterpretation. A BPMN exclusive gateway typically displays both outgoing paths as visible choices. Without explicit annotation, stakeholders may assume both `Legal Review` and `skip_legal` are observable activities, erasing the “optional/silent” semantics. The silent transition’s absence in the rendered BPMN can make the optionality appear deterministic.

- **Loop visualization:** The `verification_loop` using `Operator.LOOP` may be rendered as a BPMN “loop” icon on the sequence `Configure Trial  Inspect Trial  Correct Defect`. However, BPMN loop markers count iterations globally and do not natively surface the `correct_defect` separator that the source uses to delimit repeated iterations. The diagram may suggest an unstructured repetition, obscuring the requirement that each repetition is separated by defect correction.

- **Silent routing nodes:** Taulabeled transitions (e.g., `skip_legal`) are typically invisible in BPMN diagrams. If the conversion collapses the XOR into a single path, the diagram loses the conditional optionality entirely. If both branches are shown, the viewer cannot discern which is the “default” and which is the silent skip, potentially leading to incorrect process assumptions.

- **Graph layout ordering:** PM4Py’s BPMN layout algorithm arranges activities based on the Petri net’s place/transition structure, which may impose a lefttoright sequence that does not reflect the source’s semantic independence. For instance, `optional_legal` and `verification_loop` both appear after `assess_risk` in the net, but layout might place one strictly above or before the other, suggesting a temporal order that the model does not enforce.

**Proposed annotations / documentation to reduce ambiguity:**

1. **Explicit gateway types:** Label XOR gateways with `<<optional>>` or `<<XOR (legal/silent)>>` notes; label AND/parallel gateways with `<<unordered interleaving>>` to distinguish from true concurrency.
2. **Iteration markers:** Add a footnote or diagram text: “Each loop iteration includes `Correct Defect` before the next `Configure Trial`. Minimum one iteration required.”
3. **Silentchoice legend:** Include a small key: ` = silent optional (not recorded in trace)`. Attach this to the XOR gateway involving `skip_legal`.
4. **Concurrency disclaimer:** Place a caption: “Activities marked with `` may occur in any order after `Register Change`; they are not guaranteed simultaneous.”
5. **Join notation:** At the `Release Change` synchronization point, add `` (join) notation to clarify that both the optionallegal branch and the verification loop must complete before release.
6. **Traceability map:** Provide a supplemental table mapping BPMN activity IDs back to POWL transition labels and operators, enabling reviewers to trace visual elements to the authoritative source.

# 7. Rejection Criteria

A conversion result should be rejected or quarantined under any of the following conditions:

1. **Unsound workflow net:** `pm4py.check_is_workflow_net(net)` returns `False`, or `pm4py.check_soundness(net, im, fm)` reports nontermination, dead transitions, or marking violations. The source model is structurally sound (a start, a clear end, proper joins); any conversion that admits release before verification or an unreachable archive must be rejected.
2. **Loss of required interleaving:** The converted model enforces an order between `assess_risk` and `prepare_evidence` (e.g., via sequence flow where the source permits any order). This collapses the source’s concurrency/absenceoforder invariant and is a semantic mismatch.
3. **Admission of Release Change before verification loop completion:** If the BPMN/net permits `Release Change` to fire when the verification loop has not yet executed at least one full iteration (`configure_trial  inspect_trial  correct_defect`), the conversion violates I9 and must be quarantined.
4. **Collapse of optional behavior:** The XOR between `Legal Review` and `skip_legal` is rendered as a simple sequence or parallel branch, making the optionality visible or alwaystaken. If the roundtrip or soundness diagnostics show the silent choice lost, the result is rejected.
5. **Failed exactfinalmarking test in roundtrip:** After converting POWL  Petri  BPMN  Petri, the final marking of the regenerated net must equal the original `fm_from_powl` exactly. If `fm_rt  fm_from_powl` (place equality check fails), the conversion drift is unacceptable and the result is quarantined.
6. **Activitylabel duplication or loss:** Any transition in the converted BPMN or Petri net carries a label not present in the source POWL, or two source transitions map to the same BPMN activity. This breaks traceability and semantic fidelity.
7. **Processtree conversion failure not caught:** If the secondary pipeline (POWL  Petri  process tree  BPMN) is attempted without a `try/except`, an unhandled exception propagates and corrupts the workflow. The code must catch and interpret exceptions; a failure left unhandled is a technical rejection criterion.

**Avoiding roundtrip drift in future edits:**
- Treat the POWL model as the immutable canonical source. Any modification to the process model must be done by editing the POWL source and rerunning the full conversion pipeline.
- After each edit, regenerate all derivatives (Petri net, BPMN, roundtripped nets) and rerun the validation suite (soundness, traces, footprints). Do not manually adjust derived models, as this introduces drift.

# 9. Residual Uncertainty

Even if every test in the validation suite passes (soundness OK, traces match under the bound, footprints preserved, roundtrip markings equal), the following claims **cannot be established** definitively:

1. **Exact number of verification iterations in practice:** The source model enforces “at least one” verification iteration via the `LOOP` operator but provides no guard or condition for loop termination. The bounded trace exploration (max 2 iterations) can confirm that 1 or 2 iterations are possible, but it cannot prove that more iterations are impossible or that the process will always stop after a specific count. The loop’s exit semantics are inherently underspecified.

2. **True concurrency versus arbitrary interleaving for `assess_risk` / `prepare_evidence`:** The Petri net representation may exhibit both transitions enabled from the same place, which pm4py’s reachability graph explores as interleaved sequences. However, the source POWL’s “unordered after registration” does not explicitly guarantee true parallel execution nor forbid it. The conversion cannot distinguish whether the modeler intended true concurrent execution (both can fire in the same instant) or merely unordered sequential execution; behavioral equivalence under true/concurrent semantics remains unverified.

3. **Stakeholdervisible meaning of the silent XOR choice (`skip_legal`):** Hiding `tau` transitions (as required for trace exploration) collapses the XOR between `Legal Review` and the silent skip into a single path. Even with annotations (Section 6), the precise “optionality” perception—whether a stakeholder interprets the path as “may be skipped unseen” or “always executed but invisible”—depends on external documentation and is not recoverable from the model alone. The conversion can preserve the structural XOR but cannot certify the semantic intent of the silent routing node.

4. **Release Change synchronization completeness:** The model states that `Release Change` waits for both the optionallegal branch and the verification loop, but it does not specify whether the wait is a strict join (both must complete before release starts) or a permissive “release may start once the first branch finishes while the second continues in parallel.” The Petri net’s conuence of edges models a join, yet BPMN gateway type (XOR vs. AND) and layout can sway interpretation. Without explicit modeling of conditional release triggers, the exact synchronization contract remains ambiguous.

5. **Preservation of binaryloop separation by `correct_defect` across arbitrary iteration counts:** The audit confirms that each iteration includes `correct_defect`, but the validation bound (e.g., max 2 iterations) only samples a subset of possible runs. It cannot certify that `correct_defect` always appears between repetitions at any depth, nor that the loop cannot “skip” the separator under certain (unmodeled) conditions. The semantic invariant I7 is structurally enforced in the POWL, but its behavioral enforcement in any finitestate abstraction is only probable, not provable without a full unbounded model checker.
