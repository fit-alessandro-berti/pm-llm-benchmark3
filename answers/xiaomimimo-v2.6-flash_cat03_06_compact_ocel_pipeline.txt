**Do logistics/financial events relate directly to Orders and Items?** Four explicit rules, applied uniformly (this build implements **full operational involvement**):

- **R1** — every object literally named by the event gets a direct E2O row.
- **R2** — every order whose state the event advances gets a direct E2O row; on shared events this yields one row per affected order (Reserve Stock, Pack Package, Dispatch Package, Issue Invoice, Confirm Delivery all touch **O100 and O200**).
- **R3** — Items get direct E2O rows *only* where the item is the physical subject: Add Item, Reserve Stock, Pack Package. Item-level delivery/invoice/closure status is deliberately **not** asserted; it is reachable through O2O (`contains_item`, `packs_item`, `carries_package`).
- **R4** — Record Payment links to Invoice + Payment only. No order-level allocation is asserted, because the narrative never splits 100/150 between O100 and O200.

**Keeping propagation distinguishable from source facts.** Structural multi-hop knowledge lives *only* in `o2o`; nothing derived is ever materialized into `relations`. The two tables also use disjoint qualifier vocabularies (`dispatched_order` is an event role; `carries_package` is a structure), so a reviewer can tell them apart without a provenance column. The convention for any future derived row is a reserved `derived_` prefix (or a separate `relations_derived` frame); this build contains **zero** `derived_` rows, hence every row of `relations` is a source fact. Validation rejects any qualifier outside the declared vocabularies, so a stray derived row cannot sneak in unnoticed.

**Version-dependent PM4Py assumption.** The single line `OCEL(events=..., objects=..., relations=..., o2o=...)` is isolated and commented. `discover_dfg` may return a `(dfg, start, end)` tuple or a dict — the code handles both. `discover_otg`, `discover_etot`, `discover_oc_petri_net` are resolved through a `_require()` helper that raises a loud, actionable `AttributeError` instead of silently degrading; the fix is to upgrade/re-import PM4Py, **never** to reshape the DataFrames.

def validate_frames(events, objects, relations, o2o) -> None:
    problems: list[str] = []

    # 1) unique event ids
    if events["ocel:eid"].duplicated().any():
        problems.append("duplicate ocel:eid in events")

    # 2) unique object ids
    if objects["ocel:oid"].duplicated().any():
        problems.append("duplicate ocel:oid in objects")

    # 3) timestamps: datetime dtype, tz-aware, sorted
    if not pd.api.types.is_datetime64_any_dtype(events["ocel:timestamp"]):
        problems.append("ocel:timestamp is not datetime dtype")
    elif events["ocel:timestamp"].dt.tz is None:
        problems.append("ocel:timestamp is naive - must be timezone-aware")
    elif not events["ocel:timestamp"].is_monotonic_increasing:
        problems.append("event timestamps are not sorted by eid")

    # 4) no orphan event ids in relations
    orphan_e = sorted(set(relations["ocel:eid"]) - set(events["ocel:eid"]))
    if orphan_e:
        problems.append(f"orphan ocel:eid in relations: {orphan_e}")

    # 5) no orphan object ids in relations or o2o
    known = set(objects["ocel:oid"])
    orphan_ro = sorted(set(relations["ocel:oid"]) - known)
    if orphan_ro:
        problems.append(f"orphan ocel:oid in relations: {orphan_ro}")
    orphan_oo = sorted((set(o2o["ocel:oid"]) | set(o2o["ocel:oid_2"])) - known)
    if orphan_oo:
        problems.append(f"orphan ocel:oid in o2o: {orphan_oo}")

    # 6) activity / timestamp consistency between events and relations
    chk = relations.merge(events, on="ocel:eid",
                          suffixes=("", "__ev"), validate="many_to_one")
    bad = chk[(chk["ocel:activity"] != chk["ocel:activity__ev"]) |
              (chk["ocel:timestamp"] != chk["ocel:timestamp__ev"])]
    if len(bad):
        problems.append(f"{len(bad)} relation rows disagree with their event row")

    # 6b) object type consistency between objects and relations
    chk_o = relations.merge(objects, on="ocel:oid",
                            suffixes=("", "__obj"), validate="many_to_one")
    bad_o = chk_o[chk_o["ocel:type"] != chk_o["ocel:type__obj"]]
    if len(bad_o):
        problems.append(f"{len(bad_o)} relation rows carry a wrong ocel:type")

    # 7) no duplicate relation rows
    dup_r = relations.duplicated(subset=["ocel:eid", "ocel:oid", "ocel:qualifier"])
    if dup_r.any():
        problems.append(f"{int(dup_r.sum())} duplicate relation rows")

    # 8) vocabulary + type-capitalization discipline
    bad_q = sorted(set(relations["ocel:qualifier"]) - E2O_QUALIFIERS)
    if bad_q:
        problems.append(f"unknown E2O qualifiers: {bad_q}")
    bad_q2 = sorted(set(o2o["ocel:qualifier"]) - O2O_QUALIFIERS)
    if bad_q2:
        problems.append(f"unknown O2O qualifiers: {bad_q2}")
    bad_t = sorted(set(objects["ocel:type"]) - set(OBJECT_TYPES))
    if bad_t:
        problems.append(f"unexpected object types (capitalization drift?): {bad_t}")

    # 9) O2O sanity
    if (o2o["ocel:oid"] == o2o["ocel:oid_2"]).any():
        problems.append("O2O self loops present")
    dup_o = o2o.duplicated(subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])
    if dup_o.any():
        problems.append(f"{int(dup_o.sum())} duplicate O2O rows")

    # 10) coverage: no event without relations, no object never referenced
    unreferenced_ev = sorted(set(events["ocel:eid"]) - set(relations["ocel:eid"]))
    if unreferenced_ev:
        problems.append(f"events without any E2O relation: {unreferenced_ev}")
    covered = set(relations["ocel:oid"]) | set(o2o["ocel:oid"]) | set(o2o["ocel:oid_2"])
    if covered != known:
        problems.append(f"objects never referenced anywhere: {sorted(known - covered)}")

    if problems:
        raise AssertionError("OCEL validation failed:\n  - " + "\n  - ".join(problems))

    ties = int(events["ocel:timestamp"].duplicated().sum())
    print(f"VALIDATION OK  events={len(events)} objects={len(objects)} "
          f"relations={len(relations)} o2o={len(o2o)}  timestamp_ties={ties}")

## 4. Expected flattened behavior

**Flatten on Order** — two traces.

| Case | Trace shape (chronological) | Length |
|---|---|---|
| O100 | Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Dispatch Package  Dispatch Package  Issue Invoice  Confirm Delivery  Confirm Delivery  Close Order | 12 |
| O200 | Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order | 8 |

- **Copied shared events**: `{e06, e07, e09, e11, e13}` — five physical events appear in *both* traces. This is normal flattening behaviour, but their activity frequencies double if the two flattened logs are naively concatenated.
- **Likely DFG edges (11 distinct, 18 weighted transitions)**: `Create OrderAdd Item` (2), `Add ItemAdd Item` (1), `Add ItemReserve Stock` (2), `Reserve StockPack Package` (2), `Pack PackagePack Package` (1), `Pack PackageDispatch Package` (2), `Dispatch PackageDispatch Package` (1), `Dispatch PackageIssue Invoice` (2), `Issue InvoiceConfirm Delivery` (2), `Confirm DeliveryConfirm Delivery` (1), `Confirm DeliveryClose Order` (2). Start = {Create Order: 2}; End = {Close Order: 2}.
- **Log skeleton** would impose invariants such as *Create Order always before Close Order*, *Issue Invoice always before Close Order*, *Confirm Delivery always before Close Order*, *Reserve Stock always before Pack Package*, with the mirror-image `never_before` pairs.
- **Omitted lifecycle aspects**: package identity, delivery identity, invoice identity, payment amounts, and the fact that O100's two sub-flows (P1/D1 vs P2/D2) are genuinely concurrent in warehouse terms but serialised by timestamp.
- **Misleading interpretations**: (i) the log looks like one tidy linear pipeline, hiding that e07 merges O200's goods into O100's package; (ii) `Dispatch Package  Dispatch Package` reads as "two dispatches in sequence" when D1 and D2 were independent shipments; (iii) `Confirm Delivery  Close Order` for O100 compresses a next-day D2 confirmation and a same-day D1 confirmation into one undifferentiated step; (iv) `Reserve Stock` looks order-local although it was a joint stock decision.

**Flatten on Package** — two traces: P1 = `Pack Package  Dispatch Package`, P2 = `Pack Package  Dispatch Package`.
- **Copied shared events**: none *between* the two package traces (e07 belongs only to P1, e08 only to P2); but e07/e08 are duplicated relative to the Order flattening.
- **DFG**: one edge `Pack Package  Dispatch Package` (weight 2). Start = {Pack Package: 2}, End = {Dispatch Package: 2}.
- **Omitted**: package confirmation (lives on Delivery), invoicing, payment, closure; and crucially **the mixed-order provenance of P1** — the flattened log makes P1 and P2 look structurally identical.
- **Misleading**: every package appears to complete its lifecycle at dispatch; cycle-time conclusions ("packing to dispatch = 60 min for P1, 70 min for P2") ignore that P1's packing had to synchronise two orders.

**Flatten on Delivery** — D1 = `Dispatch Package  Confirm Delivery` (10:00  13:00, 3 h), D2 = `Dispatch Package  Confirm Delivery` (10:15  09:00 next day, 22.75 h).
- **DFG**: one edge `Dispatch Package  Confirm Delivery` (weight 2). Start/End as expected.
- **Copied shared events**: none between D1 and D2; e09/e13 are shared with O100/O200 traces, e10/e14 with O100's.
- **Omitted**: which packages travelled (the activity names are generic), which orders were served, and that D1's confirmation closed obligations for **two** orders at once.
- **Misleading**: a control-flow-only DFG makes D1 and D2 look interchangeable; only a *performance* DFG over the same flattening exposes the ~7× SLA gap between them.

**Flatten on Invoice** — one trace: V1 = `Issue Invoice  Record Payment  Record Payment`.
- **DFG**: `Issue Invoice  Record Payment` (1), `Record Payment  Record Payment` (1). Start = {Issue Invoice: 1}, End = {Record Payment: 1}.
- **Event attributes survive**, so `payment_amount` sums to 250 (100 + 150) — the only place where a quantitative reconciliation is possible.
- **Misleading**: the `Record Payment  Record Payment` edge reads as a *loop* when it is in fact two distinct partial payments; with n=1 there is no case comparison, so no conformance discrimination at all. Nothing in this trace says which order each payment settles.

**Why Payment flattening is especially weak.** Each Payment object is touched by exactly **one** event (M1  e12 only, M2  e15 only). Both traces therefore have length 1, the DFG is the empty dict, start and end activities coincide (`Record Payment`), and the log skeleton reduces to a single-activity set with zero ordering invariants. Inductive/alpha miners produce a single transition with no meaningful structure, and replay-based conformance has no discriminating power — it will happily accept any fabricated variant. On top of that, rule R4 deliberately withholds order links, so even a richer Payment log could never say *which* order M1 or M2 settled: the allocation simply does not exist in the narrative (100 + 150 = 250 against a joint V1 liability). Short, single-touch, unallocated objects should be analysed as **objects in the object-centric view**, not as cases.

## 5. Expected object-centric structures

**OC-DFG.** Six object flows with clear starts and ends: Order starts at `Create Order` and ends at `Close Order`; Item starts at `Add Item` and ends at `Pack Package` (a direct consequence of rule R3 — items are not linked to dispatch/confirm/close); Package starts at `Pack Package` and ends at `Dispatch Package`; Delivery starts at `Dispatch Package` and ends at `Confirm Delivery`; Invoice starts at `Issue Invoice` and ends at `Record Payment`; Payment is a singleton flow starting and ending at `Record Payment`. The interesting structure is at the **intersections**: `Add Item` and `Reserve Stock` sit at OrderItem; **`Pack Package` sits at OrderItemPackage — the triple intersection where P1 pulls I1 (from O100) and I3 (from O200) into one node**; `Dispatch Package` sits at OrderPackageDelivery, where O100 *diverges* onto D1 and D2 while O200 follows only the D1 branch; **`Issue Invoice` sits at OrderInvoice, where V1 joins O100 and O200**; `Record Payment` sits at InvoicePayment, showing M1 and then M2 advancing the single V1 flow; `Confirm Delivery` sits at OrderDelivery. Crucially there is **no OrderPayment intersection** — the OC-DFG will visually demonstrate that payments never directly touch orders under this policy.

**OTG (object type graph).** Expected edges: Order–Item, Order–Package, Order–Delivery, Order–Invoice, Item–Package, Package–Delivery, Invoice–Payment (7 edges). Expected *absences*: Order–Payment, Item–Delivery, Item–Invoice, Item–Payment, Package–Invoice, Package–Payment, Delivery–Invoice, Delivery–Payment. The type graph is therefore two loosely joined cliques bridged at **Order** (everything operational) and **Invoice** (everything financial), with V1 as the only bridge between them. Caveat worth stating to a reviewer: if the implementation derives edges from O2O alone, Order–Package and Order–Delivery disappear (there is no structural OrderPackage link — packages are only reachable through items), so the edge set is implementation-dependent and must be read alongside the E2O matrix in section 3.

**ET–OT graph.** 9 activities × 6 object types = **18 edges**: Create Order(1), Add Item(2), Reserve Stock(2), Pack Package(3), Dispatch Package(3), Issue Invoice(2), Record Payment(2), Confirm Delivery(2), Close Order(1). `Pack Package` is the highest-degree activity node (3 types), followed by `Dispatch Package`. The graph shows that **Item never meets Invoice or Payment**, and **Payment meets only Invoice** — the structural reason per-order settlement KPIs are unavailable.

**Object-centric Petri net.** One expects places per object type (or per object), transitions per activity, and read/synchronisation arcs where an activity spans several types. The substantive expectations: `Pack Package` is a genuine **AND-join** requiring tokens from O100 *and* O200 (and the items) simultaneously — P1 cannot be packed until both orders have reserved stock; `Dispatch Package` is a synchronisation of an order token, a package token and a delivery token; `Issue Invoice` is another AND-join over O100 and O200; `Record Payment` must fire twice against V1's settlement place before V1 can be considered fully settled and O100/O200 can close; **O100 must fork** so that both its P1/D1 branch and its P2/D2 branch complete before `Close Order` fires, while O200 needs only the P1/D1 branch. *This is not a uniquely determined reading*: whether shared activities **consume** or merely **read** the order tokens, whether tokens are per-object or per-type, whether `Close Order` requires delivery confirmation as a hard precondition or only as a weak ordering, and whether the net is 1-safe, are all design choices made by the discovery algorithm and possibly by the analyst's post-processing. Different settings yield different, equally valid nets.

**Object-interactions summary.** Expected per-object counts: O100  12 events / 8 distinct activities; O200  8 events / 8 distinct activities; I1  3 (Add, Reserve, Pack); I2  2 (Add, Pack); I3  3 (Add, Reserve, Pack); P1  2 (Pack, Dispatch); P2  2; D1  2 (Dispatch, Confirm); D2  2; **V1  3 (Issue, Record Payment ×2)**; M1  1; M2  1. Expected interaction neighbourhoods: O100 touches {O200, I1, I2, I3, P1, P2, D1, D2, V1} = 9 other objects (the hub); **P1 touches {O100, O200, I1, I3, D1} = 5 — the widest *cross-order* bridge, which quantitatively confirms that P1 is the object that fuses the two orders**; **V1 touches {O100, O200, M1, M2} = 4**, the financial hub; M1 and M2 touch only V1. This summary is where the single-touch weakness of M1/M2 becomes visible without any flattening at all.

## 6. Modeling alternatives

All four below tell the *same* business story; they differ only in **which invariants discovery is able to verify**.

**(1) Source-minimal relations.** E2O rows exist only for objects literally named by each event. Reserve Stock and Pack Package keep their order links (the narrative names them), but Dispatch Package loses O100/O200, Confirm Delivery loses them, and `Pack Package (P2)` loses O100. Relation count drops **41  34 (17 %)**; O100's trace shrinks from 12 to ~7 events, O200's from 8 to 6. Consequences: the Order DFG becomes `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order`, and the log skeleton **can no longer enforce "delivered before closed"** — a variant that closes an order with an undelivered package becomes conformant. The OTG loses the Order–Delivery edge entirely, and the OC-DFG shows Delivery as an island reachable only from Package. Cheapest to extract from a raw event log, but delivery SLA conformance is silently disabled.

**(2) Full operational involvement (what this build implements).** Rule R1–R4 as stated: 41 E2O rows, all affected orders directly linked, items linked only at their physical subject, payments linked only to the invoice. Consequences: Order traces include dispatch and delivery-confirmation milestones, so `Confirm Delivery always before Close Order` becomes a checkable invariant; the OTG gains Order–Delivery and Order–Package; the OC-DFG exposes both the P1 convergence and the O100{D1,D2} divergence; five events are copied into two Order traces, which is the price of order-centric completeness. This is the richest policy that still avoids asserting anything the narrative does not state.

**(3) O2O-propagated analytical relations.** Start from source-minimal and then materialize derived rows: every event linked to a package also links its packed items and their orders; every event linked to a delivery also links its packages, their items and their orders; every event linked to an invoice also links the billed orders and the settling payments. Even one hop inflates counts materially — e09 grows from 2 to 6 rows, e13 from 1 to 6, e14 from 1 to 4, e12/e15 from 2 to 4 each — pushing the table from 34 toward ~55; full transitive closure approaches the 17 × 11 = 187-row ceiling, at which point the E2O bipartite graph is nearly complete. Consequences: the Item flow extends all the way to `Close Order`, enabling item-level delivery KPIs that are *derived, not observed*; the OTG gains Item–Delivery and Item–Invoice and, if payments propagate, **Order–Payment — which fabricates exactly the per-order payment allocation the narrative never provides**; the OC-DFG's intersections multiply until most activities touch most types, destroying sparsity; conformance checking becomes over-permissive because nearly every activity now satisfies nearly every ordering constraint. Useful as an explicit, separately-marked analytical layer (`derived_` prefix), never as the source table.

**(4) Order-allocated payments (bonus).** Split M1/M2 into order-scoped pseudo-events or add `paid_order` links (say M1O100, M2O200). This would make Payment traces length 2–3 and enable per-order settlement cycle time — but it invents a fact: the narrative gives only a joint V1 liability of 250 with no split. Any such row must be flagged as an assumption, not a relation.

## 7. Failure modes

1. **Relation inflation.** Transitive-closure or "link everything to everything" policies inflate 41 rows toward 187. Symptoms: DFG edge weights scale with relation multiplicity rather than with physical occurrences; `ocel_object_type_activities` reports nearly every activity under every type; the OTG degenerates into a complete graph; OC-DFG intersections become indistinguishable; conformance checking accepts almost any variant because cross-object constraints are always satisfiable. *Mitigation*: declared qualifier vocabulary + row-count budget asserted in validation.

2. **Missing direct E2O links.** Dropping Orders from Dispatch/Confirm (source-minimal taken too far) makes Order traces end at `Issue Invoice` before closure, silently removing the delivery-before-close invariant and the OTG's Order–Delivery edge. The log still "works" — it simply stops checking the most business-critical ordering.

3. **Treating O2O propagation as observation.** If rows derived from `contains_item`/`packs_item`/`carries_package` are written into `relations` without a `derived_` marker, a reviewer cannot distinguish a source-system fact from an inference. The concrete harm here is asserting "M2 completes settlement of O200" — a claim no table in the narrative supports. *Mitigation*: disjoint qualifier vocabularies per table, plus zero-tolerance validation for undeclared qualifiers.

4. **Duplicate shared events after flattening.** `{e06, e07, e09, e11, e13}` appear in both Order traces. Concatenating flattened logs into one "traditional log" double-counts `Pack Package`, `Dispatch Package`, `Issue Invoice` and `Confirm Delivery`, inflating frequency-based metrics and distorting cycle-time averages. Conversely, a well-meaning dedup on `(activity, timestamp)` would *delete* legitimate rows. *Mitigation*: keep flattenings in a dict keyed by object type (as done) and never merge them into a single frame for frequency analysis.

5. **Ambiguous payment allocation.** 100 + 150 = 250 settles a joint V1 with no per-order split. Any attempt to attribute M1 to O100 or M2 to O200 is fabrication; worse, an inferred allocation propagated as a relation (failure mode 3) makes the error invisible. The honest statement is: per-order settlement is *not measurable* from this dataset.

6. **Overly short Payment traces.** M1 and M2 each touch exactly one event, so Payment-flattened traces have length 1, an empty DFG, coincident start/end activities and a trivial skeleton. This yields zero conformance discrimination and can produce the false assurance "no deviations detected". *Mitigation*: analyse single-touch objects through `ocel_objects_interactions_summary` and the OC-DFG rather than by flattening.

7. **Constructor/API version mismatch.** `OCEL(events=..., objects=..., ...)` may be spelled `ocel_events=...` in some builds; `discover_dfg` may return a tuple or a dict; `discover_otg`/`discover_etot`/`discover_oc_petri_net` may be absent or renamed. The danger is "fixing" it by reshaping or dropping DataFrames. *Mitigation*: one isolated, commented construction line; `_require()` for entry points; tuple/dict handling for `discover_dfg`.

8. **False total order for same-time events.** This example has **no timestamp ties** (all 17 timestamps are distinct — validation reports `timestamp_ties=0`), so the failure does not materialise here. But it is latent: if a warehouse system batched `Confirm Delivery` for D1 and D2 into one instant, or if timestamps were truncated to the hour (08:00/08:05/08:06 would collide), flattening and DFG discovery would impose an arbitrary sequence, inventing a spurious edge such as `Confirm Delivery  Confirm Delivery` and hiding true concurrency. *Mitigation*: keep sub-minute resolution, sort stably by `(timestamp, eid)`, and prefer structures (OC-DFG, OC Petri net) that do not presuppose a global order.

9. **Object-type capitalization drift.** Writing `order` alongside `Order` splits the type: `ocel_get_object_types` returns 7 types, `ocel_flattening(ocel, "Order")` returns an empty log, and all per-type statistics silently halve. *Mitigation*: `OBJECT_TYPES` closed set checked in validation.

10. **Inconsistent qualifiers.** Using `bills_order` in one row and `bills` in another splits O2O cardinality tables, corrupts interaction summaries, and — if applied to `contains_item` — breaks every reachability query from Order to Item. *Mitigation*: both vocabularies declared as frozensets and enforced.

11. **Modeling the payment amount as an object.** Creating `Amount100`/`Amount150` objects would add a phantom type, add edges to the ET–OT graph and OTG, appear in interaction summaries, and break the requirement that amounts are event attributes — while making the 250 reconciliation harder, not easier.

## 8. Final semantic checks

A reviewer can inspect the generated tables directly for these assertions (all hold for this build):

1. **Object census.** `objects` has exactly 11 rows, 11 distinct `ocel:oid`, and type counts **Order 2, Item 3, Package 2, Delivery 2, Invoice 1, Payment 2**, with capitalization drawn only from `{Order, Item, Package, Delivery, Invoice, Payment}`.

2. **Event census and time discipline.** `events` has exactly 17 rows with 17 distinct `ocel:eid`, all `ocel:timestamp` values tz-aware UTC, strictly increasing in eid order, minimum `2026-04-06T08:00+00:00`, maximum `2026-04-07T10:35+00:00`, and **zero** duplicate timestamps.

3. **Relation integrity.** `relations` has exactly 41 rows, contains none of the mandatory columns missing, has no duplicate `(ocel:eid, ocel:oid, ocel:qualifier)` triples, has no orphan `ocel:eid` or `ocel:oid`, and for every row the `(ocel:activity, ocel:timestamp)` triple is **byte-identical** to the corresponding row in `events` while `ocel:type` is identical to the type in `objects`.

4. **O2O integrity.** `o2o` has exactly 12 rows with qualifier cardinalities **3 / 3 / 2 / 2 / 1 / 1** for `contains_item / packs_item / carries_package / bills_order / partially_settles / completes_settlement`, no self-loops, no duplicate triples, no orphan oids, and subject-first direction (e.g. `V1 bills_order O100`, `M1 partially_settles V1`, `M2 completes_settlement V1`).

5. **Order membership sets.** O100 relates to exactly `{e01, e02, e03, e06, e07, e08, e09, e10, e11, e13, e14, e17}` (12 events) and O200 to exactly `{e04, e05, e06, e07, e09, e11, e13, e16}` (8 events); their intersection is exactly the five shared events `{e06, e07, e09, e11, e13}` — the convergence set identified in section 3.

6. **Cross-order item mixing.** I1 and I3 co-occur in both `e06` and `e07` although they belong to different orders (`O100 contains_item I1`, `O200 contains_item I3`), while I2 and I3 never co-occur in any single event — they only meet inside O100's flattened trace. Equivalently: `P1 packs_item {I1, I3}` but `P2 packs_item {I2}` only.

7. **Payment honesty.** `payment_amount` is non-null on exactly two rows, both with activity `Record Payment` (e12 = 100.0, e15 = 150.0), summing to 250.0; **no event that carries a non-null amount has an Order among its E2O objects**, and no `Payment` appears in any Order's relation set — confirming that allocation is deliberately withheld.

8. **Per-type activity signature.** `pm4py.ocel_object_type_activities` yields Order  8 activities including `Create Order` and `Close Order`; Package  exactly `{Pack Package, Dispatch Package}`; Delivery  exactly `{Dispatch Package, Confirm Delivery}`; Invoice  exactly `{Issue Invoice, Record Payment}`; Payment  exactly `{Record Payment}`; Item  exactly `{Add Item, Reserve Stock, Pack Package}`.

9. **V1 as the unique financial bridge.** V1 is the sole `Invoice`; both O100 and O200 are reachable from it via `bills_order`; exactly two payments reach it, M1 strictly before M2 in timestamp, and only M2 carries the qualifier `completes_settlement` — so "settlement completes only after e15 at 2026-04-07T10:00" is a directly checkable statement.
