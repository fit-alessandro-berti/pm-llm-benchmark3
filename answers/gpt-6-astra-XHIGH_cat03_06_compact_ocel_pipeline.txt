## 1. Modeling assumptions

The object types are exactly `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, with this capitalization. All IDs are globally unique. An event appears once in `events`, even when several objects participate.

I use explicit event participation where the narrative supplies it, and a small, documented logistics enrichment. Reserve Stock and packing P1 explicitly involve both Orders. Packing P2 is analytically related to O100. Dispatch events are analytically related to the packed Items and their Orders; confirmation events are analytically related to the carried Packages, their Items, and their Orders. Thus logistics appear in useful Order, Item, and Package lifecycles.

Issue Invoice directly relates V1 to both Orders. Each Record Payment relates only its Payment and V1. I do not assign either payment to an Order or Item. The two payments contribute 100 and 150 units and jointly settle V1 according to the narrative; no allocation between O100 and O200 is given.

The E2O qualifier vocabulary is:

| Qualifier | Meaning |
|---|---|
| `created_order` | Order created by this event |
| `parent_order` | Order receiving an added Item |
| `added_item` | Item added by this event |
| `reserved_item` | Item explicitly reserved |
| `involved_order` | Order explicitly participating in reservation or packing |
| `packed_package` | Package being packed |
| `packed_item` | Item being packed |
| `dispatched_package` | Package being dispatched |
| `carrying_delivery` | Delivery used for dispatch |
| `issued_invoice` | Invoice being issued |
| `billed_order` | Order explicitly billed at issuance |
| `recorded_payment` | Payment being recorded |
| `credited_invoice` | Invoice receiving a payment contribution |
| `confirmed_delivery` | Delivery being confirmed |
| `closed_order` | Order being closed |
| `context_order`, `context_item`, `context_package` | Participation added by the stated O2O traversal rules |

Every E2O row also has `relation_origin`, either `source` or `derived_o2o`. Here, “source” means explicitly supplied by the narrative, not evidence about an actual source database. The source-only relation table is retained separately. An inferred link does not replace or duplicate an existing source link. Discovery usually uses E2O incidence without treating qualifiers or provenance as constraints, so these labels support auditing; they do not make discovery automatically discount inferred links.

O2O directions are Order → Item (`contains`), Package → Item (`packs`), Delivery → Package (`carries`), Invoice → Order (`bills`), and Payment → Invoice (`partially_settles`). Both M1 and M2 are partial contributions; M2 is the final contribution in this observation window. O2O describes the observed business structure, without asserting that every relationship existed throughout the entire time window.

The pipeline assumes a PM4Py installation exposing the high-level functions named in the question, accepting an OCEL as their first argument and a flattened pandas DataFrame for conventional discovery. Flattening is assumed to produce `case:concept:name`, `concept:name`, and `time:timestamp`. The OCEL constructor is isolated below. If a release has a different constructor, adapt only that compatibility point while retaining the four tables, including qualifiers and O2O. If a named discovery API is unavailable or renamed, its documented equivalent needs an adapter; silently substituting a different analysis would not be equivalent. Graph return containers, annotations, and visualization options may vary by version.

# This model chooses one role per event/object pair. OCEL in general may
# legitimately permit multiple different qualifiers for the same pair.
link_rows = []
seen_pairs = set()
for eid, participants in source_links.items():
    for oid, qualifier in participants:
        assert (eid, oid) not in seen_pairs
        seen_pairs.add((eid, oid))
        link_rows.append((eid, oid, qualifier, "source"))


def related_oids(oid, qualifier, reverse=False):
    """Traverse one explicitly selected O2O relation, in a chosen direction."""
    source_col, target_col = (
        ("ocel:oid_2", "ocel:oid") if reverse
        else ("ocel:oid", "ocel:oid_2")
    )
    mask = o2o[source_col].eq(oid) & o2o["ocel:qualifier"].eq(qualifier)
    return sorted(o2o.loc[mask, target_col].unique())


def add_context(eid, oid, qualifier):
    """Preserve an existing source role rather than adding a second row."""
    if (eid, oid) not in seen_pairs:
        seen_pairs.add((eid, oid))
        link_rows.append((eid, oid, qualifier, "derived_o2o"))


def add_package_context(eid, package):
    add_context(eid, package, "context_package")
    for item in related_oids(package, "packs"):
        add_context(eid, item, "context_item")
        for order in related_oids(item, "contains", reverse=True):
            add_context(eid, order, "context_order")


# Restricted enrichment: no generic transitive closure and no finance traversal.
# Packing/dispatch already have a source Package. E07's Orders are also source.
for eid in ["E07", "E08", "E09", "E10"]:
    for oid, role in source_links[eid]:
        if role in {"packed_package", "dispatched_package"}:
            add_package_context(eid, oid)

# Delivery -> carried Package -> packed Items -> their containing Orders.
for eid in ["E13", "E14"]:
    for delivery, role in source_links[eid]:
        if role == "confirmed_delivery":
            for package in related_oids(delivery, "carries"):
                add_package_context(eid, package)

raw_relations = pd.DataFrame(
    link_rows,
    columns=["ocel:eid", "ocel:oid", "ocel:qualifier", "relation_origin"],
)
# Joining from the authoritative tables avoids separately typed activities,
# timestamps, or object types drifting out of sync with their master records.
relations = (
    raw_relations
    .merge(
        events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
        on="ocel:eid", how="left", validate="many_to_one",
    )
    .merge(objects, on="ocel:oid", how="left", validate="many_to_one")
    [[
        "ocel:eid", "ocel:activity", "ocel:timestamp",
        "ocel:oid", "ocel:type", "ocel:qualifier", "relation_origin",
    ]]
    .sort_values(["ocel:timestamp", "ocel:eid", "ocel:oid"], kind="stable")
    .reset_index(drop=True)
)
source_relations = relations.loc[relations["relation_origin"].eq("source")].copy()

# Referential, temporal, and semantic validation.

assert not objects.isna().any().any()

assert set(relations["ocel:eid"]) <= set(events["ocel:eid"])

assert set(o2o["ocel:oid"]) <= set(objects["ocel:oid"])
assert set(o2o["ocel:oid_2"]) <= set(objects["ocel:oid"])
assert set(source_links) == set(events["ocel:eid"])
assert set(relations["ocel:eid"]) == set(events["ocel:eid"])

assert not relations.duplicated().any()
assert not relations.duplicated(["ocel:eid", "ocel:oid", "ocel:qualifier"]).any()
assert not relations.duplicated(["ocel:eid", "ocel:oid"]).any()
assert not o2o.duplicated().any()

by_event = events.set_index("ocel:eid")
by_object = objects.set_index("ocel:oid")["ocel:type"]
assert relations["ocel:activity"].eq(
    relations["ocel:eid"].map(by_event["ocel:activity"])

assert relations["ocel:timestamp"].eq(
    relations["ocel:eid"].map(by_event["ocel:timestamp"])

assert relations["ocel:type"].eq(relations["ocel:oid"].map(by_object)).all()

o2o_endpoint_types = {

## 4. Expected flattened behavior

The trace shapes below are exact activity sequences for the chosen relation policy. For compactness, C = Create Order, A = Add Item, R = Reserve Stock, P = Pack Package, S = Dispatch Package, B = Issue Invoice, Y = Record Payment, D = Confirm Delivery, and X = Close Order. DFG counts refer to ordinary directly-following occurrences in the flattened traces.

| Flattening | Cases and trace shapes | Likely DFG edges |
|---|---|---|
| Order | O100: C → A → A → R → P → P → S → S → B → D → D → X. O200: C → A → R → P → S → B → D → X. | C→A, A→R, R→P, P→S, S→B, B→D, D→X each have count 2. A→A, P→P, S→S, D→D each have count 1. |
| Package | P1 and P2: P → S → D. | P→S and S→D each have count 2. |
| Delivery | D1 and D2: S → D. | S→D has count 2. |
| Invoice | V1: B → Y → Y. | B→Y and Y→Y each have count 1. |

**Order.** E06, E07, E09, E11, and E13 are each copied into both Order cases. There are 20 flattened rows representing 15 distinct original events; the two payment events are absent. E01/E04 and E16/E17 remain different creation and closure events, respectively.

The apparent packing, dispatch, and confirmation self-loops in O100 are different package/delivery branches, not evidence of rework. A→A records two Items being added. Edges such as S→S connect operations on different Packages only because the Order view sorts them into one sequence. The trace alone cannot preserve the full Item-to-Package-to-Delivery mapping or show that O100 and O200 shared the same physical operation. Payment progress is omitted despite both Orders' O2O connection to V1. Closure follows settlement in the narrative's timeline, but this Order flattening does not establish settlement as a checked closure condition.

**Package.** No event is copied into two Package cases: each logistics event involves exactly one Package. Some of these same original events also appear in other object-type projections. Delivery confirmation reaches Package here because of enrichment. Creation, addition, reservation, billing, payments, and Order closure are omitted. Both traces look identical despite P1 containing two Items from two Orders and P2 containing one Item. Thus identical activity variants conceal materially different coordination requirements.

The timestamps retain different dispatch-to-confirmation durations: 3 hours for P1/D1 and 22 hours 45 minutes for P2/D2. These are elapsed observed intervals, not automatically active handling time or SLA violations.

**Delivery.** No event is shared between the two Delivery cases. Packing is omitted because these packing events have no Delivery E2O link, even though O2O later connects a Delivery to a Package. Order and Item preparation, billing, payment, and closure also disappear. The two simple traces obscure that D1 serves portions of two Orders and D2 serves O100's remaining Item. The activity-only frequency DFG is identical for both cases; performance data distinguishes their durations.

**Invoice.** There is one case, so there are no within-view copies across invoices. The two Y occurrences are distinct payment events, E12 and E15, not duplication of one event. Order creation, logistics, and closure are absent. The B→Y→Y sequence exposes two contributions, but a conventional activity DFG does not encode amounts, Payment identity, or which Orders V1 bills. It must not be interpreted as “each Order pays twice” or as two full settlements. Amounts remain authoritative in `events`, regardless of how a PM4Py release carries optional attributes into flattened output.

**Log skeletons.** With such small samples, skeletons describe observations rather than reliable general business rules. In Order, C, R, B, and X occur once per case; A, P, S, and D occur once or twice. The latter four happen to have equal occurrence counts within each Order, which can generate equivalence constraints even though they concern different business entities. Ordering constraints follow the sequences above. Package and Delivery have fixed short sequences; Invoice has one B and two Y events. Default noise settings and implementation details affect the reported constraint representation. An Invoice skeleton observing exactly two payments is not evidence that all future invoices require exactly two.

**Payment would be particularly weak.** M1 and M2 would each have the singleton trace Y. There would be two start/end occurrences and no directly-following edges. This view cannot show invoice issuance, the gap between installments, their combined settlement, or Order/delivery progress. M1–V1 and M2–V1 O2O links do not automatically import V1's lifecycle into Payment flattening.

## 5. Expected object-centric structures

**OC-DFG.** Typed directly-following edges should reproduce the per-object lifecycle patterns above while retaining a shared activity framework. The Item perspective adds useful distinctions: I1 and I3 follow A→R→P→S→D, while I2 follows A→P→S→D because no reservation for I2 was recorded. This difference should be retained rather than filled with an invented event.

P1's packing and subsequent logistics involve O100 and O200 simultaneously; the V1 issuance also touches both Orders. However, an aggregated OC-DFG is not a substitute for inspecting the underlying event/object IDs and O2O edges to recover exact instance membership. Order, Package, and Delivery edges remain perspective-specific: temporal adjacency within O100 does not prove a causal dependency between its two delivery branches.

Frequency choices matter. Reserve Stock has one unique event, two related Orders, and two related Items. Counting unique events, unique objects, or event/object incidences answers different questions. Similarly, Issue Invoice is one event with one Invoice and two Orders. OC-DFG labels must be interpreted using the selected metric rather than by adding counts across object types.

**OTG.** The type topology should make the connection between ordering, logistics, billing, and payments visible. The explicit qualified O2O topology is Order → Item ← Package ← Delivery, together with Payment → Invoice → Order. Instance inspection establishes that P1 connects I1 of O100 and I3 of O200, and that V1 connects both Orders to M1 and M2.

For an OTG based on E2O type co-occurrence, the enriched logistics events additionally connect every distinct pair among Order, Item, Package, and Delivery. Issue Invoice adds Order–Invoice; Record Payment adds Invoice–Payment. There is no direct Order–Payment co-occurrence in this policy. Same-type interactions, if represented, include the two Orders and the two Items at shared events. Graph direction, self-edge handling, and edge annotations depend on the API's definition. In particular, co-occurrence edges must not be labeled as qualified ownership facts merely because O2O is also present. A type graph summarizes connectivity; instance-level cardinalities still require the tables.

**ET–OT.** The event-type/object-type incidence view should match the activity/type audit table. Reserve Stock touches Order and Item; Pack Package touches Order, Item, and Package; Dispatch Package and Confirm Delivery touch all four logistics types; Issue Invoice touches Order and Invoice; Record Payment touches Invoice and Payment. The absence of Record Payment–Order and Record Payment–Item edges is deliberate. It expresses the chosen E2O scope, not an assertion that payment has no business relevance to those objects. Incidence alone does not show that P1 contains two Orders' Items or that V1 has two contributing Payments.

**Object-centric Petri net.** Discovery should expose typed lifecycle components with shared activity transitions connecting them. Packing coordinates Packages with Items and Orders; dispatch and confirmation coordinate Deliveries with those logistics objects; issuance connects V1 to O100 and O200; recording payments connects M1 and M2 individually to V1. Depending on the discovery algorithm, variable arcs can represent changing participation multiplicities, such as two Orders/Items for P1 versus one for P2.

There is no uniquely determined Petri-net interpretation of these 17 events. The miner can generalize repetitions, infer loops, or choose different structures according to its algorithm and settings. It need not enforce exactly two payments, their amounts, the exact P1 membership, or a settlement-before-closure rule. Most control-flow discovery does not turn qualified O2O links or amount attributes into guards. Enriched logistics links may introduce synchronization that a source-only model would lack. Sparse evidence and model discovery do not establish soundness, causality, or financial conformance.

**Object-interactions summary.** This should expose co-participation in original events. If the API returns event-level or directed rows, first aggregate by distinct event ID and unordered object pair to interpret the following counts:

- O100 and O200 share five events: E06, E07, E09, E11, and E13.
- P1 shares three events with O100 and three with O200: E07, E09, and E13. Two of those links per Order were analytically added.
- V1 shares E11 with each Order, E12 with M1, and E15 with M2.
- M1 and M2 have no direct shared event. They are connected through V1, which receives both contributions.

Co-participation does not mean ownership. For example, I3 co-occurs with O100 in shared operations, but the only `contains` owner of I3 remains O200. Similarly, the summary must not allocate M1's 100 units or M2's 150 units to either Order based on connectivity.

## 6. Modeling alternatives

1. **Source-minimal E2O.** Use only `source_relations`, retaining all explicit participation, including both Orders at E06, E07, and E11. Order traces shrink to C→A→A→R→P→B→X for O100 and C→A→R→P→B→X for O200. O100 loses its P2 packing visibility, and both Orders lose dispatch and confirmation. Package traces become P→S because confirmation explicitly names only the Delivery. Delivery and Invoice traces stay as above. This policy closely reflects the supplied event records but leaves important analytical lifecycle gaps; O2O still preserves the business structure.

2. **Full operational involvement.** Relate logistics and financial operations to all substantively involved Orders and, where desired, Items. Relative to the implemented policy, V1 issuance could also touch I1, I2, and I3, and both payment events could touch O100, O200, and those billed Items. Order traces would then include both installments; OC-DFG and ET–OT would gain financial edges for Orders and Items, and the Petri net would gain corresponding synchronization. This can support end-to-end questions, but broader business involvement is not equivalent to observed participation or allocated revenue. In this narrative those additional links must be marked inferred unless separately supplied as observations.

3. **Purpose-specific O2O propagation.** Preserve the source OCEL as the baseline and produce a labeled analytical OCEL for a particular question. For fulfillment analysis, use the exact logistics traversals implemented above. For invoice-to-Order payment visibility, traverse Payment → Invoice → Order only for payment events. This produces Order payment steps while leaving unrelated Item or Package histories out. Results depend on the selected directions, qualifiers, event classes, and any relationship validity times. Such joins change what discovery sees without changing the original event records or their business meaning.

These are alternative relation policies over one connected process, not six independently invented traditional logs. Unrestricted undirected transitive propagation is especially unhelpful here: all 12 objects lie in one connected O2O component, so connecting every event to every reachable object would create 204 E2O rows and make every object's trace contain all 17 events, including activities preceding some objects' first observed participation.

## 7. Failure modes

1. **Relation inflation.** Expanding participation through an entire connected component creates artificial interactions and synchronization, erasing lifecycle distinctions. Even the bounded enrichment used here increases E2O from 34 to 49 rows, so frequencies must state their unit.

2. **Missing direct E2O links.** O2O connectivity alone does not place an event in a flattened lifecycle. Omitting the explicit Orders at E06/E07/E11 contradicts the narrative; omitting analytical confirmation-to-Package links is a defensible policy but changes Package discovery.

3. **Treating propagation as observation.** Storing inferred context with indistinguishable source qualifiers suggests the source explicitly reported it. Preserve source rows, use provenance and distinct context qualifiers, and compare discoveries under both policies.

4. **Counting flattened copies as new events.** E07 appears in two Order cases but remains one packing operation. Counting flattened rows overstates event volume and potentially cost or workload. Conversely, globally dropping repeated event IDs from a flattened log would remove valid participation from one of the cases.

5. **Ambiguous payment allocation.** V1 bills both Orders, but neither installment is allocated between them. The 250-unit total belongs to V1's payment history. Even if payments were propagated to Orders, summing 250 for each Order would double-count value.

6. **Overly short Payment traces.** Each Payment has only Record Payment. Absence of edges reflects the chosen entity granularity and E2O scope, not instant end-to-end settlement or absence of an invoice lifecycle.

7. **Constructor/API version mismatch.** Unsupported constructor parameters, missing discovery functions, different return schemas, or incompatible visualization calls can break otherwise valid data. Isolate the constructor adjustment and any documented API adapters; do not drop O2O or rename business types to conceal incompatibility.

8. **False total order for simultaneous events.** This dataset has no timestamp ties. In other data, sorting equal timestamps by event ID or input position gives a reproducible sequence but does not establish causal order. A standard flattened DFG can therefore contain arbitrary adjacency; preserve concurrency or partial-order evidence where available.

9. **Drifting denormalized attributes and duplicate relations.** A mistyped relation timestamp, activity, or type can change lifecycle ordering or discovery. Joining authoritative tables and validating both row uniqueness and endpoint consistency prevents these errors. Deduplication must preserve distinct qualified roles when a different model legitimately uses them.

10. **Confusing repetition with rework or causality.** O100's P→P, S→S, and D→D concern different branches; V1's Y→Y concerns installments. A temporal edge is not proof of a required dependency, failure, or repeated execution on the same Package.

11. **Inferring universal rules from tiny samples.** One Invoice and two Orders cannot establish general payment counts, routing probabilities, cardinality limits, or compliance requirements. A skeleton or discovered net may overfit the sample or generalize beyond it.

12. **Confusing interaction with containment or historical validity.** Shared operations make O100 interact with I3, without making I3 an O100 Item. Static O2O links also do not establish when a Package assignment or invoice relationship became valid; broad backward propagation can manufacture pre-creation participation.
