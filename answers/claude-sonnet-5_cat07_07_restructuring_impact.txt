# 1. Mechanism map

| Restructuring action | Direct structural change | Expected process-mining effect | Log signature to watch |
|---|---|---|---|
| Merge N_Tech/S_Tech/E_Tech into Technical Shared Service | Removes 3 local specialist nodes, creates 1 central node | **Nominal handover reduction**: the "embedded tech specialist  same local caseworker" local loop disappears; replaced by "local caseworker  Technical Shared Service" and return edge | Handover-of-work network: fewer distinct local loop edges, but edge weight concentrates on 2 new edges with higher wait |
| Centralize Specialist/Legal/Risk/difficult QC into shared queues | Multiple destination roles collapse into fewer queue nodes | **Central queue formation**: high in-degree/out-degree for shared-service resources; queueing theory (M/M/1-like) predicts nonlinear wait growth as utilization rises | Discover_dfg on shared-service activities shows growing self-loop/wait times; `get_service_time` on shared-service activities rises with volume |
| Routing rules force high-complexity + legal/risk/security to shared queues | Volume funneled disproportionately to shared service | **Specialist utilization increase** (management's intended effect) | Resource utilization stats from organizational roles discovery; but same mechanism raises queue-wait for exactly the cases most sensitive to delay (high complexity) |
| Remove local supervisor, add shared approval queue | Approval decision decoupled from local case owner | **Role clarity reduction**: handover network shows many-to-one/one-to-many approval edges with no consistent resource pairing; **accountability diffusion** | Working-together network sparsity/instability across resource pairs release-to-release; increased "case:concept:name" resources touching a case (reassignment_count) |
| Local tech absorbed centrally | Local caseworkers lose informal/adjacent tech contact | **Local expertise loss**: fewer informal "local caseworker  embedded tech" edges (pre-referral triage) disappears entirely | Drop in short-duration low-formality edges in handover network; possible **rise** in formal specialist referrals for cases that previously never needed one (leakage effect) |
| Consolidation may raise average utilization near capacity (91-93% legal/risk already) | Central queues run close to saturation | **Resilience to absence reduction**: with only one queue and centralized staff, any absence/spike causes system-wide backlog rather than team-local backlog | Spike in `case_service_waiting_time` variance; `get_variants` reveals new long-tail variants after specific dates (proxy for local absence events) |
| Same routing rules & queue applied uniformly across teams | East (already tech-saturated) offloads locally-scarce resource; North/South give up abundant embedded expertise for shared access | **Fairness across teams**: East's cycle time/rework may *improve* while North/South's may *worsen* — restructuring is not neutral across teams | Segment DFG/performance-DFG and rework rate by `team`; compare pre/post delta per team, not pooled average |
| Standardized decisions via shared queue | Reduced discretion for local/regional accommodation | **Fairness across customer segments**: customers requiring regional/language handling see additional generic handover step | Filter by `customer_segment`, compare handover count & wait time before/after; look for a rise in cross-team/generic handling for accommodation-needing segments |

# 2. Scenario forecasts

## Optimistic scenario
- **Handover pattern**: Nominal handover count per case drops (matches management table); local loop edges vanish cleanly; specialist-return edge is fast and reliable.
- **Queue/waiting-time pattern**: Shared-service median wait stabilizes near forecast (~4h for Tech, ~10.5h for Legal/Risk) because volume increase is absorbed by better load-balancing across specialists; utilization rises to target (~15pp) without saturation.
- **Cycle-time distribution**: Median and 90th percentile both improve; tail cases (high complexity) also benefit from faster expert access.
- **Rework and quality**: Rework rate falls because standardized, higher-skill review reduces inconsistent judgment; QC rework loop shrinks.
- **Role clarity/accountability**: Shared approval queue develops a small number of high-throughput consistent reviewers; case ownership remains traceable via reassignment_count staying low.
- **Fairness**: East gains most (relief from overload); North/South lose only marginal expertise since caseworkers still contact shared service informally at similar speed; customer segments requiring accommodation see no material handover increase because informal side-channel communication persists.
- **Early warning signs (that this scenario is unfolding)**: `case_service_waiting_time` for Technical/Legal/Risk stays flat or falls as volume grows; reassignment_count stable; rework_flag rate drops across all teams; no growth in tail (90th pct) cycle time.

## Central (most likely) scenario
- **Handover pattern**: Nominal handovers per case fall as predicted, but new handover types (Tech Shared Service, shared approval queue) become high-frequency chokepoints; cross-team handover shrinks but a new "queue-internal reassignment" pattern emerges.
- **Queue/waiting-time pattern**: Median wait roughly matches management estimate on average, but variance increases substantially — some periods (post-absence, end-of-month spikes) show multi-day queue backlog even though median looks fine.
- **Cycle-time distribution**: Median cycle time improves modestly; 90th percentile improves less than median or stays flat — tail cases (esp. high complexity + legal/risk overlap) get worse because they now stack in two shared queues sequentially.
- **Rework and quality**: Rework rate improves for simple/medium cases (standardization helps) but rises for cases needing regional nuance or fast informal escalation, since informal pre-check no longer exists.
- **Role clarity/accountability**: Handover-of-work and working-together networks become less "sticky" — resource pairs recombine every cycle, making it hard to discover consistent organizational roles; discover_organizational_roles output shows blurred role boundaries, especially around approval.
- **Fairness**: East benefits (as under optimistic), but North/South show a widening SLA-miss and rework gap relative to East — pooled averages mask this divergence. Customer segments needing regional/language handling see one extra handover step, worsening their SLA specifically.
- **Early warning signs**: Divergence between mean and 90th percentile cycle time growing over time; per-team rework/SLA trends diverging (East improving, North/South flat or worsening); increase in `reassignment_count` for legal/risk/security cases; queue self-loop frequency rising in DFG.

## Adverse scenario
- **Handover pattern**: Nominal handover count falls (matches management's "success" metric) but total case touch-time and total distinct resources per case rise — a "hidden handover" effect where nominal steps decrease while informal back-and-forth (emails/notes) increases outside logged activities.
- **Queue/waiting-time pattern**: Technical Shared Service and Legal/Risk queue both approach saturation (near the 90%+ utilization already seen in Legal/Risk); wait times balloon nonlinearly, especially for high-complexity cases which are explicitly routed there by rule (utilization > 90% region  queueing collapse).
- **Cycle-time distribution**: Median may still look flat or slightly better (simple case volume dominates average), but tail (90th/99th percentile) cycle time worsens sharply — a classic case of average masking failure.
- **Rework and quality**: Rework rises overall as caseworkers lose the ability to triage informally (previously prevented unnecessary referrals) — over-referral floods shared queues; QC rework loop grows because centralized reviewers lack case/customer context.
- **Role clarity/accountability**: Shared approval queue creates a diffusion-of-responsibility pattern — outcome disputes cannot be traced to a specific decision-maker; discover_organizational_roles shows unstable/rotating role assignment; increase in unresolved or re-opened cases.
- **Fairness**: East's gain is real but small relative to North/South's loss of local expertise and rising SLA-miss/rework; customer segments needing regional/language accommodation experience disproportionately higher handover count, wait time, and rework — a fairness/equity problem hidden in the topline average.
- **Early warning signs**: Legal/Risk or Technical Shared Service utilization crossing ~85-90% (queueing theory inflection); growing gap between median and 90th percentile cycle time; rework rate rising specifically for high-complexity and legal/risk/security cases; local team satisfaction and SLA metrics diverging by team/segment even as pooled average holds steady; increase in undocumented rework (case reopened without rework_flag set) suggesting workaround behavior.

# 4. Risks invisible in average cycle time

1. **Tail latency masking**: A flat or improved mean cycle time can coexist with a much worse 90th/99th percentile if queueing saturation affects only a subset of cases (e.g., high complexity + legal/risk overlap). Averages are dominated by simple, high-volume cases that don't touch the shared queues as heavily.
2. **High-complexity case degradation**: Routing rules explicitly send complex cases to the shared queue — exactly where saturation risk is greatest. If these are a minority of cases, their delay can be statistically invisible in the pooled average while representing the organization's most important, highest-value work.
3. **Local knowledge erosion (slow-moving)**: Loss of embedded technical familiarity with regional customer conventions is a multi-month/multi-quarter effect. Average cycle time will not detect this until rework and misclassification rates climb — a lagging, not leading, signal.
4. **Fairness divergence across teams**: East's improvement can offset North/South's degradation in a blended average, hiding a structural inequity where two of three teams are worse off.
5. **Learning/skill-development stagnation**: If local staff no longer handle hard cases, their competency plateaus or declines — a slow, compounding effect with no direct cycle-time signature until a local staffing gap or shared-service outage forces local handling of a complex case and it fails badly.
6. **Accountability diffusion / exception mishandling**: Shared approval queues can process routine cases fine (keeping the average stable) while systematically mishandling unusual/edge-case scenarios (e.g., a case needing regional exception) because no one owns escalation — this shows up as intermittent, hard-to-detect failures, not as a shift in average timing.
7. **Fairness across customer segments**: Segments needing language or regional accommodation may be quietly absorbing extra handover steps that don't move the aggregate average much (they're a minority of volume) but represent a serious equity failure.
8. **Resilience/single point of failure**: A well-functioning shared service can look identical, on average, to a fragile one until an absence spike or demand surge occurs — average cycle time computed over a "normal" period gives false confidence about behavior under stress.

# 5. Pilot design

**Pilot scope**
- Migrate technical specialist and shared approval queue functions for **one team only (recommend North or South, not East)**, keeping the other two teams as-is. Choosing a team *not* already tech-saturated isolates the effect of restructuring from East's pre-existing overload, which would otherwise confound results.
- Alternatively, run a **stratified pilot**: shared service handles only medium-complexity cases first; high-complexity cases remain local for phase 1, added in phase 2 once queue behavior is understood.

**Comparison group**
- Remaining two teams (untouched) serve as concurrent control.
- East, structurally different (pre-existing overload), analyzed separately as its own natural experiment rather than pooled with North/South comparison.

**Pre/post observation window**
- Baseline: minimum 3 months of pre-change log data (to capture monthly/seasonal variation and existing tail behavior).
- Post: minimum 3 months post-cutover, with explicit exclusion or flagging of the first 2–4 weeks (transition/learning-curve noise) from steady-state comparison, but retained for change-management diagnostics.

**Segmentation**
- By **team** (pilot vs. control vs. East).
- By **case_complexity** (esp. isolate high-complexity subgroup for tail analysis).
- By **required_specialty** (legal/risk/security vs. technical vs. none).
- By **customer_segment**, specifically flagging segments with known language/regional accommodation needs.

**Guardrail metrics** (trigger review if breached)
- Shared-service utilization > 85% sustained over any 2-week window.
- 90th percentile cycle time for high-complexity cases increases >15% vs. baseline.
- Rework rate for any single team or segment increases >20% relative vs. baseline.
- SLA miss rate for any customer segment increases beyond a pre-agreed threshold (e.g., +5pp).
- Reassignment_count median increases (proxy for ownership confusion).

**Staff feedback collection**
- Structured surveys pre/post from caseworkers and supervisors on perceived role clarity, decision ownership, and access to informal technical advice.
- Rapid-cycle retrospectives (bi-weekly) during pilot with front-line staff, explicitly probing informal workaround behavior not visible in the log (e.g., off-system consultations).
- Anonymous channel for reporting fairness/accommodation concerns.

**Rollback or adjustment triggers**
- Any guardrail metric breach sustained for 2 consecutive reporting periods  pause expansion, root-cause via HoW network and performance DFG diff.
- Evidence of fairness divergence (team or segment falling significantly behind pooled average)  do not scale until routing rules or capacity adjusted.
- Local expertise proxy (e.g., local rework on cases handled without shared service, or staff skill-confidence survey) shows decline  introduce hybrid model (local first-pass triage retained) instead of full centralization.
- If accountability/ownership complaints spike disproportionately  restructure approval queue design before continuing rollout.

# 6. Recommendation

**Pilot first — do not proceed to full rollout, and do not reject outright.**

The proposed model has a plausible, mechanistically sound upside (East-type teams facing specialist overload could genuinely benefit, and standardization could reduce inconsistent decisions), but it also carries structurally embedded risks — central queue saturation, tail-latency growth for exactly the highest-value cases, fairness divergence between East and North/South, and slow-moving losses (local expertise, learning, accountability) that will not show up in early average cycle-time data. Management's own success metric (aggregate cycle time and utilization gain) is precisely the metric least able to detect the countervailing risks staff have raised.

Recommendation is **conditional**:
- Proceed only via the phased/stratified pilot described in Section 5, with pre-registered guardrail metrics and segmented (not pooled) reporting.
- Full rollout should be considered only after at least one full quarter of stable post-cutover data showing no guardrail breaches **and** no divergence between team-level and segment-level outcomes — not just a favorable pooled average.
- East should not be used as the representative case for "success" — its baseline overload biases it toward apparent improvement regardless of whether the shared-service design is actually sound for North/South.

**What management should explicitly not infer from early averages:**
- A falling or flat pooled average cycle time in the first weeks does **not** mean tail risk, fairness, or expertise-loss problems are absent — these are lagging and segment-specific effects.
- An improvement driven by East's relief does **not** generalize to North/South, which had different baseline conditions (surplus, not deficit, of local expertise).
- Reduced *nominal* handover count does not mean reduced *effective* coordination burden — informal, unlogged coordination (workarounds) may be increasing exactly when the formal handover count looks better.
- Stable average utilization does not preclude periodic saturation/backlog during demand spikes or staff absence; only variance and peak analysis reveal resilience.

# 7. PM4Py analysis sketch

```python
import pandas as pd
import pm4py

# ---------------------------------------------------------
# 0. Load & format logs (pre and post change), keep raw copies
# ---------------------------------------------------------
df_pre  = pm4py.format_dataframe(pd.read_csv("log_pre.csv"),
                                  case_id="case:concept:name",
                                  activity_key="concept:name",
                                  timestamp_key="time:timestamp")
df_post = pm4py.format_dataframe(pd.read_csv("log_post.csv"),
                                  case_id="case:concept:name",
                                  activity_key="concept:name",
                                  timestamp_key="time:timestamp")

def to_log(df):
    return pm4py.convert_to_event_log(df)

log_pre, log_post = to_log(df_pre), to_log(df_post)

# ---------------------------------------------------------
# 1. Handover-of-work network: compare pre vs post
# ---------------------------------------------------------
how_pre  = pm4py.discover_handover_of_work_network(log_pre)
how_post = pm4py.discover_handover_of_work_network(log_post)
# compare edge weights: new central-service edges, disappearance of local loops
def edge_diff(net_pre, net_post):
    edges_pre = {(u, v): w for (u, v), w in net_pre.items()}
    edges_post = {(u, v): w for (u, v), w in net_post.items()}
    all_edges = set(edges_pre) | set(edges_post)
    return pd.DataFrame([
        {"from": u, "to": v,
         "pre": edges_pre.get((u, v), 0),
         "post": edges_post.get((u, v), 0)}
        for (u, v) in all_edges
    ])
how_diff = edge_diff(how_pre, how_post)

# ---------------------------------------------------------
# 2. Working-together & subcontracting networks
# ---------------------------------------------------------
wt_pre  = pm4py.discover_working_together_network(log_pre)
wt_post = pm4py.discover_working_together_network(log_post)

sc_pre  = pm4py.discover_subcontracting_network(log_pre)
sc_post = pm4py.discover_subcontracting_network(log_post)
# Rising subcontracting to shared-service resources => central-queue formation signal

# ---------------------------------------------------------
# 3. Resource similarity & role discovery: role-clarity check
# ---------------------------------------------------------
sim_pre  = pm4py.discover_activity_based_resource_similarity(log_pre)
sim_post = pm4py.discover_activity_based_resource_similarity(log_post)
roles_pre  = pm4py.discover_organizational_roles(log_pre)
roles_post = pm4py.discover_organizational_roles(log_post)
# Instability / fragmentation of roles post-change => role clarity erosion

# ---------------------------------------------------------
# 4. DFG and performance DFG: cycle time distribution, not just mean
# ---------------------------------------------------------
dfg_pre,  sa_pre,  ea_pre  = pm4py.discover_dfg(log_pre)
dfg_post, sa_post, ea_post = pm4py.discover_dfg(log_post)

perf_pre  = pm4py.discover_performance_dfg(log_pre)
perf_post = pm4py.discover_performance_dfg(log_post)
# extract percentiles, not just mean, from performance dfg edge statistics

# ---------------------------------------------------------
# 5. Service / waiting time analysis
# ---------------------------------------------------------
df_pre_wt  = pm4py.insert_case_service_waiting_time(df_pre)
df_post_wt = pm4py.insert_case_service_waiting_time(df_post)

svc_pre  = pm4py.get_service_time(log_pre,  aggregation_measure="median")
svc_post = pm4py.get_service_time(log_post, aggregation_measure="median")
# repeat aggregation_measure="perc90" or manual percentile calc for tail-risk detection

def percentile_by_group(df, group_cols, value_col, q=0.9):
    return df.groupby(group_cols)[value_col].quantile(q).reset_index()

tail_pre  = percentile_by_group(df_pre_wt,  ["team", "case_complexity"], "case_service_waiting_time", 0.9)
tail_post = percentile_by_group(df_post_wt, ["team", "case_complexity"], "case_service_waiting_time", 0.9)

# ---------------------------------------------------------
# 6. Segmentation: team, complexity, specialty, customer_segment
# ---------------------------------------------------------
def segmented_compare(df, dim):
    return df.groupby(dim).agg(
        n_cases=("case:concept:name", "nunique"),
        rework_rate=("rework_flag", "mean"),
        reassign_mean=("reassignment_count", "mean")
    ).reset_index()

for dim in ["team", "case_complexity", "required_specialty", "customer_segment"]:
    seg_pre  = segmented_compare(df_pre, dim)
    seg_post = segmented_compare(df_post, dim)
    print(f"--- {dim}: PRE ---\n", seg_pre)
    print(f"--- {dim}: POST ---\n", seg_post)

# Filter by team/complexity/specialty/segment for targeted sub-log analysis
log_east_pre  = pm4py.filter_event_attribute_values(log_pre,  "team", ["East"], level="case")
log_hc_post   = pm4py.filter_event_attribute_values(log_post, "case_complexity", ["high"], level="case")
log_legalrisk_post = pm4py.filter_event_attribute_values(
    log_post, "required_specialty", ["legal", "risk", "security"], level="case")

# ---------------------------------------------------------
# 7. Variants: resilience / diversity of process paths
# ---------------------------------------------------------
variants_pre  = pm4py.get_variants(log_pre)
variants_post = pm4py.get_variants(log_post)
print("Distinct variants pre:",  len(variants_pre))
print("Distinct variants post:", len(variants_post))
# fewer variants post-change may indicate standardization OR loss of adaptive local handling

rare_variants_post = pm4py.filter_variants(
    log_post, variants_post, retain=False  # keep only infrequent variants -> tail behavior
)

# ---------------------------------------------------------
# 8. Rework and SLA analysis
# ---------------------------------------------------------
rework_pre  = pm4py.get_rework_cases_per_activity(log_pre)
rework_post = pm4py.get_rework_cases_per_activity(log_post)

def sla_miss_rate(df, sla_hours=120):
    case_durations = df.groupby("case:concept:name")["time:timestamp"].agg(lambda x: (x.max() - x.min()).total_seconds()/3600)
    return (case_durations > sla_hours).mean()

for team in ["North", "South", "East"]:
    d_pre  = df_pre[df_pre["team"] == team]
    d_post = df_post[df_post["team"] == team]
    print(team, "SLA miss pre:",  sla_miss_rate(d_pre))
    print(team, "SLA miss post:", sla_miss_rate(d_post))

# ---------------------------------------------------------
# 9. Temporal features (for trend / early-warning tracking)
# ---------------------------------------------------------
temporal_features_post = pm4py.extract_temporal_features_dataframe(log_post)
# use to build weekly rolling utilization / waiting-time trend charts per resource/team,
# enabling leading-indicator dashboards (Section 3) rather than a single pre/post point estimate
```

**Interpretation logic to apply on top of the code:**
- Always compute metrics **segmented** (team × complexity × specialty × customer_segment) before looking at any pooled number.
- Track **percentiles, not just means**, for cycle time and waiting time.
- Treat **falling nominal handover counts** as inconclusive unless corroborated by stable/improved rework and SLA metrics *within each segment*.
- Use **variant diversity** and **role discovery stability** as proxies for resilience and role clarity, not just throughput numbers.
