# Transaction-Review Compliance Assessment

## 1. Temporal Data Semantics

**State reconstruction.** Within each case I impose a total order on events by `(time:timestamp, event_index)`. State is last-write-wins per attribute: an event mutates an attribute only if its cell for that attribute is non-blank. Blank cells are no-ops, never null-writes. State at any event `e` is the composition of all mutations strictly ordered before `e` (mutations at `e` itself would count; no release event here carries mutations). Forward-fill only — future values are never copied backward, and final-row attribute values are never projected onto earlier events (no final-state leakage).

**Equal timestamps (R7).** When two events share a timestamp, `event_index` breaks the tie and the consequence is stated explicitly. TX-311 is the live case: at 16:20, `Enhanced_Review` (index 3) precedes `Update_Jurisdiction`DE (index 4), so the review ran under US jurisdiction and the release state is DE.

**Material changes.** For R4, an increase is measured against the amount in effect at the latest Standard/Enhanced Review (stepwise basis): >20% increase invalidates that review for amount-dependent obligations; decreases never do; an increase from an unknown basis is not classifiable. For R1's "latest material data change" I use a broad reading: >20% amount increases plus any risk escalation, customer-type change, or jurisdiction change. A narrower amount-only reading changes no classification in this log (it only alters the TX-311 audit narrative; see §4).

**Four distinct time notions.**
- *Event time*: when the logged activity occurred (e.g., Release_Funds TX-302 at 09:40).
- *Effective time*: when a value legally operates (EX-77 `effective_from` 09:00; XZ sanctions listing).
- *Record time*: when a fact entered the system (Record_Exemption at 11:00 for both TX-302/TX-310 — an outage artifact, not the approval time).
- *Evidence time*: when evidentiary artifacts were created (EX-77 qualified signature 09:05; EX-88 signing certificate created 10:30 — *after* the 10:00 release it is supposed to cover).

Obligations are evaluated against event/effective time; late records are admissible as evidence of earlier approval only when independent evidence-time artifacts corroborate them (R5).

**Missing vs. low.** A blank amount/risk/jurisdiction/customer-type is "unknown," never "zero/LOW/DE/CORPORATE" (R6). TX-305's settlement amount (next day) is reliable at settlement time only; it is not an immutable release payload and must not leak backward into the release state.

**Pseudo-logic** (Datalog-style; every temporal test is directed — obligations at release `q` look backward via `precedes(·, q)`; R3's rescreen looks forward from update `u` toward `q`):

```
# R7 — total order
precedes(e1,e2) :- time(e1) < time(e2).
precedes(e1,e2) :- time(e1) = time(e2), event_index(e1) < event_index(e2).

# State: last write wins; blanks are no-ops; nothing from after q
state(c,a,v,q) :- mutates(e,c,a,v), at_or_before(e,q),
                  not (mutates(e2,c,a,_,_), precedes(e,e2), at_or_before(e2,q)).
unknown(c,a,q) :- not state(c,a,_,q).

# Material change (restarts review currency for R1/R2 relevance)
material(e) :- amount_update(e,A0,A1), known(A0), known(A1), A1 > 1.2*A0.      % R4
material(e) :- risk_change(e,_,HIGH); cust_change(e,_,PEP); jur_change(e,_,_).

# R1
trigger(r1,c) :- release(c,q), state(c,jur,J,q), J != DE, state(c,amt,A,q), A >= 100000.
satisfied_r1(c) :- release(c,q), enhanced_review(c,e), precedes(e,q),
                   not (material(m), precedes(e,m), precedes(m,q)).            % ER after latest material change
satisfied_r1(c) :- release(c,q), exemption(c,X), waives(X,r1),
                   valid(X, t_q), scope_match(X,c,q).
violated(r1,c) :- trigger(r1,c), not satisfied_r1(c).

# R2
violated(r2,c) :- release(c,q), (state(c,risk,HIGH,q); state(c,cust,PEP,q)),
                  not (enhanced_review(c,e), precedes(e,q), relevant(e,c,q),
                       compliance_approve(c,a), precedes(e,a), precedes(a,q)).
relevant(e,c,q) :- not (changes_risk_or_cust(m,c), precedes(e,m), precedes(m,q)).

# R3  (forward-looking obligation)
triggered(r3,c) :- release(c,q), state(c,jur,J,q), sanctions_update(c,u,J), precedes(u,q),
                   not (sanctions_screen(c,s), precedes(u,s), precedes(s,q)).  % u after latest pre-release screen
violated(r3,c) :- triggered(r3,c),
                  not (sanctions_screen(c,s2), precedes(u,s2), precedes(s2,q)).
% NB: any screen in (u,q) would have defeated the trigger, so triggered(r3) entails violated(r3);
% the redundancy is intentional and auditable.

# R4
invalid_for_amount(e,q) :- review(c,e), release(c,q), precedes(e,q),
    amount_update(c,u,A0,A1), precedes(e,u), precedes(u,q), A1 > 1.2*A0,
    not (review(c,e2), precedes(u,e2), precedes(e2,q)).
% A1 <= A0 (decrease): never invalidates. unknown(A0) or unknown(A1): not classifiable -> R6.

# R5 (defeasible)
valid(X,t) :- approved_by(X,Head_Compliance), effective_from(X) <= t, t <= expires(X),
              scope(X,J,C,M), state(c,jur,J,t), state(c,cust,C,t), state(c,amt,A,t), A <= M,
              sig_time(X,s), cert_time(X,k), s <= t, k <= t.                   % strong: crypto evidence predates use
valid(X,t) :- db_record(X,d), d > t, independent_corroboration(X,approval_at,t), approval_at <= t.
~valid(X,t) :- displayed_approval(X,g), g <= t, cert_time(X,k), k > t.          % backdating defeats displayed field
weak(W) :- witness(W,c), interested(W,c).                                      % requester testimony alone insufficient

# R6
indeterminate(R,c) :- trigger(R,c), decisive_attr(R,a), unknown(c,a,q), not resolved(R,c).
```

## 4. Ambiguities and Alternative Readings

**TX-302 (explicit).** Two readings converge: (a) ER path satisfies R1 regardless of the exemption  COMPLIANT; (b) if the referenced exemption must itself be valid, EX-77 still passes R5 (qualified signature 09:05, hash valid, documented outage explains the 11:00 record — the sanctioned "late record as evidence of earlier approval"). The result flips to NONCOMPLIANT only if the qualified signature were invalidated (revocation/hash break) **and** the ER were judged out of scope for R1. It would also become load-bearing (and still pass) had a material change occurred between 09:20 and 09:40.

**TX-305 (the INDETERMINATE case, explicit).** R6 applies: the R1 trigger (amount  100k) can neither be established nor excluded. Resolutions: an immutable release payload showing  100k  R1 triggered and satisfied by the 11:15 ER  COMPLIANT; payload < 100k  not triggered  COMPLIANT. Under the precautionary reading ("unknown amount  treat as high-value"), the ER exists  COMPLIANT. If settlement  release (fees, partial settlement), the 150k figure is irrelevant. No reading in R1–R7 produces a violation, so the residual risk is evidentiary, not substantive — hence INDETERMINATE at Medium severity, not NONCOMPLIANT. The control gap is the missing immutable release payload.

**TX-310 (explicit).** Decisive: certificate created 10:30, after the 10:00 release, so the displayed 08:50 approval is a backdated artifact; R5 says a displayed backdated field alone is not conclusive, and the sole corroborating witness is the transaction requester (interested party). Would change to JUSTIFIED_EXCEPTION if: independent contemporaneous corroboration emerged (e.g., Head_Compliance server/mail log  10:00); trusted-timestamping proof showed the 10:30 certificate re-wrapped a genuinely earlier signature; or clock-skew evidence showed true release time  10:30 (window valid until 12:00). The checking code conservatively emits REVIEW_REQUIRED here; the narrative resolves to NONCOMPLIANT by applying R5's evidentiary standard.

**TX-311 (explicit).** Tie-break consequence: ER (idx 3) precedes the jurisdiction change (idx 4) at 16:20, so the release state is DE and R1 is not activated. Alternatives: (1) without a reliable `event_index`, the 16:20 order is unknowable  the state at release could be US  R1 triggered, but the ER at 16:20 still postdates the material amount change at 16:10  COMPLIANT under amount-only materiality; (2) under broad materiality (jurisdiction change counts), had the jurisdiction stayed US the 16:20 idx-4 change would postdate the ER  R1 violated. Classification is insensitive here, but the audit narrative is not — which is exactly why tie-breaks must be logged.

**TX-307.** Default: NONCOMPLIANT (the semantic fact says a standard-packet approval does not cure a missing ER). A defensible alternative treats Head_Compliance approval as a senior compensating override  JUSTIFIED_EXCEPTION, but only if a specific rule version grants that override; absent that, curing would swallow R2's ER requirement.

**TX-309.** If provenance showed the 15:28 update was a data-correction (typo fix) rather than a commercial increase, R4 would not invalidate the ER  COMPLIANT. Likewise if the 15:25 ER's reviewed packet documented a committed 145k forecast. Requires change-reason and review-payload fields that the log lacks.

**TX-304.** If the list update carried a future effective time (e.g., listing effective 09:00), release at 08:45 predates listing  R3 not triggered  COMPLIANT. Or a rescreen may have run in a second system and not been logged; cross-system correlation would resolve it.

        return "REVIEW_REQUIRED", "exemption id absent from register"

    if not (r["effective_from"] <= t <= r["expires"]):
        return "INVALID", "release outside exemption validity window"
    if r["jurisdiction"] != jur or r["customer_type"] != cust:
        return "INVALID", "scope mismatch (jurisdiction/customer type)"
    if pd.notna(amt) and amt > r["max_amount"]:
        return "INVALID", "amount above exemption cap"
    if "R1" not in str(r["waives"]):
        return "INVALID", "exemption does not waive the triggered rule"
    if pd.notna(r["signature_time"]) and pd.notna(r["cert_created"]) \
            and r["signature_time"] <= t and r["cert_created"] <= t:
        return "VALID", "qualified signature and certificate predate release"
    if pd.notna(r["db_record_time"]):
        return "REVIEW_REQUIRED", ("approval time not machine-verifiable "
                                   "(late record / backdating suspicion); human evidence review needed")
    return "INVALID", "no admissible approval evidence"

def strictly_after(t1, p1, t2, p2):

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A flattened log tempts the checker to use end-of-trace attributes for earlier events: TX-311's final jurisdiction is DE, hiding that the review ran under US; TX-305's final amount is 150,000, which would fabricate an R1 trigger at 11:30 from a next-day settlement.
2. **Post-hoc records and exemptions.** `Record_Exemption` at 11:00 sits inside the TX-302/TX-310 traces after the releases; a control-flow model sees the activity "present" and accepts the exemption, conflating record time with approval time — fatal for EX-88 (certificate 10:30 > release 10:00) and irrelevant-but-lucky for EX-77.
3. **Material changes after review.** TX-309's ER is invalidated seven minutes before release by a +22.9% change; TX-301's Standard_Review by +56%. Both traces contain the "right" review activity, so sequence-only conformance passes them while the substantive obligation fails.
4. **Conditional activation.** R1–R3 fire only under data guards. A data-blind `precedence(Compliance_Approve, Release_Funds)` over-flags compliant TX-308/TX-311 (and TX-302, satisfied via ER); conversely a model containing `Standard_Review  Release` under-detects TX-307, where the activities exist but the PEP condition demands an Enhanced_Review.
5. **Missing data.** TX-305 has no amount anywhere before release. Defaulting to zero silently skips R1; defaulting high false-alarms. INDETERMINATE must be a first-class outcome; control-flow conformance has no such value.
6. **Same-timestamp ordering.** TX-311's ER and jurisdiction change share 16:20; without `event_index` the release state (US vs DE) is undefined and conformance results become unstable across runs or tools.
7. **Effective vs record vs evidence time.** EX-77 (approved 09:05, recorded 11:00) and EX-88 (displayed 08:50, certified 10:30) are indistinguishable to a sequence checker yet have opposite compliance outcomes.
8. **Threshold arithmetic invisibility.** The 20% materiality test is computed over stepwise bases (TX-306 +4.5% harmless; TX-309 +22.9% fatal); percentages are not activities.
9. **Review scope opacity.** TX-307's `Compliance_Approve` "approved standard review packet" only in a note; control flow cannot see packet scope.
10. **Trace-end assumptions.** Settlement_Confirmed arrives the next day; "release ends the case" models mis-handle late-arriving cross-system facts.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** At Release_Funds, write a hash-chained record of {amount, risk_level, jurisdiction, customer_type, rule_version, exemption_id + full exemption snapshot, decision, timestamp}; Settlement_Confirmed references the payload hash. This single change resolves TX-305 and hardens every R1/R2 evaluation.
- **Split time columns.** Every state-bearing and approval event carries `effective_time`, `record_time`, `signature_time`, and `certificate_time`. Outage-delayed inserts use an outbox pattern that preserves the original event time alongside the record time (TX-302/310).
- **Rule versioning.** Stamp each decision-relevant event with `rule_version` and the parameter set (thresholds like 100,000 / 20%), so cases are evaluated under the rule in force and policy changes never rewrite history.
- **First-class exemption objects.** Register entries with machine-readable scope (jurisdiction, customer type, amount cap), validity interval, `waives[]`, approver identity, and pointers to approval evidence (qualified signature, certificate, independent attestations). Release references must snapshot the scope.
- **Change provenance.** Every Update_* event records actor, reason, prior value, new value, source system, and a correction-vs-commercial-change flag — disambiguating TX-309 and future TX-305s.
- **Stable total ordering.** A monotonic per-case sequence number plus logical clocks for cross-system merges, so same-timestamp ties (TX-311) are deterministic and auditable.
- **Richer review events.** `review_type` (standard/enhanced), packet reference/hash, amount reviewed, reviewer role/qualification — making TX-307's "standard packet" machine-checkable.
- **Sanctions events with effective times.** List updates carry list version, jurisdiction, and effective time; a rescreen task is auto-created with a deadline before release and a hard block while pending (TX-304).
- **INDETERMINATE as a workflow state.** Require a `Human_Disposition` event (decision, rationale, actor, evidence links) so indeterminate cases converge to determinate, reviewable outcomes.
- **Object-centric logging (OCEL).** Model exemptions, sanctions lists, and reviews as objects related to the case, avoiding the distortions that flattening multi-object reality into a single trace inevitably produces.
