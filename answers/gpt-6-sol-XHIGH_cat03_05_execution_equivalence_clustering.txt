## 1. Equivalence design space

I treat each X as an Order-centered execution, retaining the supplied events and O2O statements. An event occurrence is distinct even when its activity repeats. Object identifiers are tokens, not business attributes; the `EXT` prefix is a supplied externality flag. I do not infer unlisted events, amounts, or O2O edges. The following are equivalence relations because each is equality of a specified signature, rather than an informal judgment of similarity.

**Activity-sequence equivalence (A).** Let `A(X)` be the tuple of activity labels in timestamp order. Define `X ~A Y` iff `A(X)=A(Y)`. This preserves activity names, their order, and repetitions. It discards object types and counts, E2O incidence, O2O edges and qualifiers, identifiers, and externality. Thus the five baseline-looking traces can agree despite different logistics or finance. Equality makes ~A reflexive, symmetric, and transitive. With simultaneous events, I would encode each timestamp layer as a multiset of activity labels, sorted only for serialization. This respects concurrency while retaining repeated labels; an arbitrary database tie-break would not define equivalence.

**Typed structural equivalence (T).** Represent an execution as a colored, directed multigraph: event-occurrence vertices carry activity and temporal position; object vertices carry type and a local/external flag; E2O edges carry any supplied role or qualifier; O2O edges carry direction, relation name, and qualifier. Include all supplied incidence, even an Item mentioned at Dispatch. Define `X ~T Y` iff a bijection of event and object vertices preserves those colors, edges, multiplicities, and temporal order. Only local identifiers may be renamed; external identifiers may also be renamed among external objects of the same type, since their spelling is not meaningful. External status itself cannot change. Repeated events remain separate. The relation discards the spellings of identifiers and timestamps' absolute clock values, but retains their order, or time-layer order when ties exist. It is reflexive, symmetric, and transitive: identity, inverse, and composition of the required isomorphisms supply the three proofs. For same-time events, permit any permutation within their layer while preserving all incidence and causal edges; do not serialize them in input order.

**Business-semantic equivalence (S), preferred for segmentation.** Define a deterministic, precedence-ordered motif signature. First classify as `SHARED_LOG` if a package or its dispatch links this Order to an external Order or Item; otherwise `SHARED_FIN` if its invoice or payment is shared with an external Order; otherwise `RETURN_REPACK` if an item is returned and subsequently repacked and dispatched; otherwise `REPLACEMENT` if supplied qualified O2O information records replacement or removal before dispatch; otherwise `SPLIT` if at least two distinct packages are packed for the lead Order; otherwise `STANDARD`. The order of rules is part of the definition, so a future execution with several motifs still gets one reproducible class. Here `SPLIT` deliberately includes both one consolidated delivery and separate deliveries, and ignores payment count. A descriptive secondary profile records those differences without defining the class. This signature preserves the presence and domain of cross-order sharing, return/rework and replacement motifs, and the one-versus-multiple-package distinction. It discards exact IDs, exact counts beyond the split threshold, most event interleavings, delivery count within `SPLIT`, and payment count. It is reflexive, symmetric, and transitive because it is equality of a function. Same-time events are a partial order: “subsequently” requires a causal or strict temporal path, not merely the written order of a tied timestamp. If that path cannot be established, classify the motif as unresolved rather than assert a return cycle.

These relations are intentionally different projections. For example, A cannot see the cross-order boundary, whereas T distinguishes the two delivery topologies within S's `SPLIT` class. All three definitions compare executions, not their literal Order IDs.

## 2. Canonical signatures

The following scheme gives a reproducible S key and a useful T audit key. Parse each event as an occurrence with an activity, a time layer, and a multiset of typed object incidences. Parse O2O notes as supplied directed, labeled edges with qualifiers. Mark objects beginning `EXT` as external. Never create an absent O2O edge merely because an event makes one plausible.

For T, partition object vertices by (type, external flag) and event vertices by (activity, time layer). Enumerate bijections within those partitions, serialize all vertex colors, E2O incidence, and directed qualified O2O edges under each bijection, and take the lexicographically smallest serialization. This exponential reference algorithm is precise; graph-isomorphism software can replace enumeration. Identical event labels at different times remain distinct; events tied in time can permute within their layer. A canonical signature is therefore independent of local object names and input row order within a tie. Crucially, a “removed before dispatch” edge and a plain package–item edge serialize differently.

Here is Python-like pseudocode for the cheaper preferred S key. The helper predicates inspect only supplied events and O2O statements. `lead_packages` counts distinct Package objects in Pack events involving the lead Order. `after` uses a causal/strict-time relation; it returns false or unknown for an unresolved tie. A real implementation should keep unknown as a separate diagnostic state.

```python
def semantic_signature(execution, lead_order):
    external_logistics = any(
        involves(lead_order, e)
        and e.activity in {"Pack Package", "Dispatch"}
        and has_external_order_or_item(e, execution.o2o)
        for e in execution.events
    )
    external_finance = any(
        involves(lead_order, e)
        and e.activity in {"Issue Invoice", "Record Payment"}
        and has_external_order(e, execution.o2o)
        for e in execution.events
    )
    returned_repacked = any(
        same_item(r, p) and same_item(p, d)
        and after(p, r) and after(d, p)
        for r in events(execution, "Return Item")
        for p in events(execution, "Pack Package")
        for d in events(execution, "Dispatch")
    )
    replacement = any(
        edge.qualifier in {"replaces", "removed_before_dispatch"}
        for edge in execution.o2o
    )
    package_count = len(lead_packages(execution, lead_order))

    if external_logistics:
        return ("SHARED_LOG",)
    if external_finance:
        return ("SHARED_FIN",)
    if returned_repacked:
        return ("RETURN_REPACK",)
    if replacement:
        return ("REPLACEMENT",)
    if package_count >= 2:
        return ("SPLIT",)
    return ("STANDARD",)
```

The signature's stated invariants, rather than a vague resemblance, determine membership. For auditing, store alongside it the T key and a secondary tuple such as (package count, delivery count, payment count, cross-order domain). Secondary fields explain within-class variation but do not silently change S.

## 3. Cluster assignments

The A labels denote exact activity-label traces. T labels denote the qualified, externality-aware typed graphs just defined. S labels are the preferred motif keys. “2P/1D/1M” means two packages, one delivery, one payment.

| X2 | A0 | T0 | STANDARD | 1P/1D/1M; local | X1 after type-preserving identifier renaming |

## 4. Cluster interpretations

**STANDARD — one local fulfillment and local finance path.** X1–X2 have two items packed together, one package and delivery, and one invoice and payment. They provide a useful low-friction reference path. A traditional case trace flattened by Order depicts their activity sequence adequately, but loses the item–package membership needed to establish that both items traveled together. This cluster is stable under harmless identifier repair and reordered identifiers. It would change if evidence appeared that a package or invoice was shared, or that an item was removed before dispatch.

**SPLIT — more than one package without a supplied return, replacement, or cross-order motif.** X3 consolidates two packages in one delivery; X4 dispatches them separately and records partial then completing payments. The shared operational issue is packing fragmentation, with opportunities to consolidate packages and to compare shipping and payment handling by secondary profile. Flattening by Order can show two Pack events but cannot faithfully represent that X3 has one delivery carrying both packages while X4 has two package–delivery pairs. The cluster is stable under renaming and repairs of event order within independent branches. It is sensitive to missing or duplicated Pack/Package records; the X4 payment interpretation also requires the supplied qualifiers.

**SHARED_LOG — cross-order logistics.** X5's package contains an external Order's item, and Dispatch also links both Orders. This may be legitimate consolidation, but the package creates coupled fulfillment, tracking, and exception handling. Flattening by Order either duplicates a shared package across cases or hides the other Order's item. The classification is stable if the external association is reliably captured, but disappears if extraction trims the neighboring Order or its item. Its invoice remains local, which matters when measuring logistics versus finance sharing.

**SHARED_FIN — cross-order finance.** X6 has local logistics but an invoice that bills two Orders and a payment with no order-level allocation. The risk is attributing the full invoice or payment to O6, especially in per-Order revenue or settlement metrics. Flattening by Order duplicates the invoice/payment or assigns them arbitrarily. The class is stable under ID repair, but not under a repair that removes the external billing link. The data do not justify inventing a split amount or saying O6 alone is paid.

**REPLACEMENT — qualified substitution/removal before shipment.** X7 initially packs both items, yet I72 replaces I71 and P71–I71 is qualified `removed_before_dispatch`. Its dispatch also mentions I72. This suggests changed shipped contents and possible inventory or customer-service implications. An Order-level activity trace looks baseline and hides the item change. Stability depends on preserving the qualified relation: if qualifiers are lost, the precise replacement interpretation cannot be recovered solely from the labels. The extra Dispatch–Item incidence remains evidence of a structural difference, but does not independently prove why it happened.

**RETURN_REPACK — post-dispatch rework.** X8 dispatches a package, records the return and inspection of I82, then repacks and redispatches that item. This is a second logistics cycle, with cost, quality, and lead-time implications. Flattening by Order shows repeated Pack and Dispatch but cannot attach the return, replacement package, and second delivery to the same item. It is stable if the return/repack sequence and I82 links survive repair. If one of those links is missing, classify it as an unresolved return rather than fabricate a complete cycle.

## 5. Borderline cases

**X1 versus X2:** They are equal under A, T, and S. Literal-ID equality would split them, since O1/I11 and O2/I22 are different tokens; that is defensible for record identity but useless for execution-pattern equivalence. Their opposite item-ID ordering is harmless under a type-preserving graph mapping.

**X1 versus X5:** A groups them because their activity labels and repetition match. T and S split them because P51 and its Dispatch include external Order/item participation. If an analyst deliberately projects away all external objects, X5 may become equivalent to X1; that projection answers a narrower local-path question and suppresses shared logistics.

**X1 versus X6:** A groups them, as would a local-only trace that drops EXT-OB. T and S split them: V61 bills two Orders and M61 is not allocated by Order. A policy focused only on local packing would group them, while financial attribution requires separation.

**X1 versus X7:** A groups them. T separates them because Dispatch has an Item incidence and the qualified O2O graph differs. S separates them because replacement/removal changes the fulfilled item set. A qualification-blind analysis might group the apparent one-package flows; it must then label the shipped-item semantics unknown, not assume both items were shipped.

**X3 versus X4:** They are unequal under A and T: X4 has an extra Dispatch, Delivery, and Payment and interleaves packing and dispatch. S groups them by the primary split-package motif. A delivery-granular or settlement-granular business signature would separate them, quite reasonably for shipping cost or receivables analysis.

**X4 versus X8:** A, T, and S all separate them. A coarser metric such as “two packages and two deliveries for one Order” would group them. That is defensible for capacity reporting, but X8's return/inspection/repack loop and X4's partial settlement imply different causes and interventions. Equal cardinalities alone are therefore not a sufficient root-cause equivalence.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

Use `pm4py.cluster_equivalent_ocel(ocel, "Order", max_objs=...)` as a source of exact execution clusters, then make the desired equivalence explicit. Its raw key is an implementation-level execution fingerprint, not a promise of typed graph isomorphism or business equivalence. In the event/object key representation, activity occurrences, their ordering, and their associated object identifiers are retained; repeated occurrences and E2O participation therefore matter. Literal object tokens can remain in the key, so X1 and X2 can receive different exact keys despite an obvious type-preserving renaming. An exact key must not be assumed to preserve our external/local distinction, all qualified O2O edges, invoice allocation, or payment amounts merely because the input OCEL has them. Those fields must be checked in the installed release or added by the independent canonicalization above. In particular, exact equality of a library key should not be described as equality of the full qualified T graph without verifying its serialized fields.

This outline keeps the Order type explicit and aggregates PM4Py's returned exact groups by our own identifier-invariant signature. The small adapter accounts for releases that return one OCEL or a collection of OCELs per key; if a release returns another wrapper, adapt only that line. `make_execution` extracts the lead Order and supplied event, object, and O2O tables from each sublog, preserving `EXT` flags; `semantic_signature` is the function above.

```python
from collections import defaultdict
import pm4py

lead_type = "Order"
raw_groups = pm4py.cluster_equivalent_ocel(
    ocel, lead_type, max_objs=100000
)
business_groups = defaultdict(list)

for raw_key, value in raw_groups.items():
    sublogs = value if isinstance(value, (list, tuple)) else [value]
    for sublog in sublogs:
        for order_id in lead_objects(sublog, lead_type):
            execution = make_execution(sublog, order_id)
            key = semantic_signature(execution, order_id)
            business_groups[key].append((raw_key, order_id))

for key, members in sorted(business_groups.items()):
    print(key, len(members))
```

For a strict T post-process, replace `semantic_signature` with the colored-graph canonical serializer and group by that result. Keep the raw key as provenance, not as the semantic label. Exact equivalence is preferable when investigating duplicate records, replaying an execution, or checking whether two extracted sublogs are literally identical under the PM4Py implementation. It is too fine for many operational summaries. A low `max_objs` can limit or omit large connected executions, depending on the implementation; increasing it can make extraction and graph canonicalization costly. Shared packages or invoices can connect several Order neighborhoods, so record any capped or excluded cases and compare cluster frequencies only over the same extraction rule.

## 7. Robustness analysis

**Ignore all O2O qualifiers.** T still separates X7 from X1 because X7's Dispatch includes I72, but the `removed_before_dispatch` meaning is lost. Under the stated S rule, X7 moves from REPLACEMENT to STANDARD unless a separately retained, explicit replacement edge still establishes the motif. X4's two payments remain observable, but their partial-versus-completing settlement meaning vanishes. X8's return sequence still supports RETURN_REPACK even if the “replaces” qualifier on P82 is dropped.

**Ignore external objects and their links.** X5 and X6 move to STANDARD under S, and their local projections may become T-isomorphic to X1/X2. This is a material change, not a renaming choice. It makes cross-order logistics and billing risks invisible. If only the `EXT` flag is lost but the extra Order and Item vertices remain, T may still separate them by multiplicity; specify which projection is used.

**Collapse repeated same-label events.** If this means one occurrence per activity over the whole case, A can merge X3 and X4 with the baseline label set; it erases the two Pack events and X4's two Dispatch and Payment events. X8 still has Return Item and Inspect Return. T and S remain unchanged if the operation is only a label-summary view and original events/objects are retained. If occurrences are actually deleted, package multiplicity may still be recoverable from objects, but event-incidence evidence and the return cycle can be damaged. Collapsing only *consecutive* equal labels has a smaller effect: X4's alternating Pack/Dispatch sequence survives, while its consecutive payments merge.

**Treat Pack and Dispatch order as a partial order.** Permit independent package branches to commute, but preserve Pack(P) before Dispatch carrying P and, for X8, Dispatch(D81) before Return(I82) before repack and redispatch. X4's P41–D41–P42–D42 written interleaving then becomes equivalent to other schedules of the same two branch topology. It still differs from X3's single delivery carrying both packages and from X8's causally linked return. Our S assignments do not change; T may merge new schedule variants not present here.

**Represent payment multiplicity by amounts or settlement state.** X4's two Payment vertices could become one invoice-level “partially then fully settled” history. If both count and history are discarded, T loses one discriminator; X4 still differs from X3 by delivery topology. S already ignores payment count, so the assignments stay put. A financial compliance view should preserve the partial-to-final history or amounts rather than treat the two records as one undifferentiated payment.

## 8. Limitations and recommendation

For **compliance monitoring**, use T with qualified relations, event order or partial order, and any required amount and allocation attributes: the cross-order invoice, pre-dispatch removal, and partial settlement are material controls. For **operational segmentation**, use S plus its secondary delivery/payment profile, so the sample is grouped by actionable motifs without fragmenting every shipping variant. For **root-cause analysis**, start from T and inspect the actual incidence and temporal paths within a semantic cluster; X3 and X4 illustrate why the secondary structure matters. For **descriptive reporting**, A is a compact account of activity patterns, provided reports explicitly label it as trace-only and add separate counts for packages, deliveries, shared objects, and returns.

These recommendations answer different questions. A compresses well but loses object relations; T retains evidence but can produce many small groups; S encodes chosen business priorities and can hide a secondary difference such as X4's payment fragmentation. The sample supplies no amounts, exact timestamps, or full lifecycle of external Orders, so no equivalence can establish revenue allocation, elapsed-time performance, or whether cross-order sharing was authorized. Report the signature definition and extraction boundary with every cluster count, and keep the underlying graph available for review.
