## 1. Target definition

The current label does not identify “90-day default for every application.” Default after activation is undefined for an application that receives no account, and the 21,600 labeled accounts are selected through activation, outcome maturity, and feed availability. Rejection is not evidence of a non-default credit outcome.

**Primary target: an application-pathway distribution under the lender’s observed operating policy.** At landmark time \(L\), predict these six mutually exclusive outcomes:

1. Account activated within 90 days after \(L\), followed by default within 90 days after activation.
2. Account activated within that application window, with no default during its first 90 days.
3. Rejected before activation within the application window.
4. Withdrawn before activation within the application window.
5. Transferred before activation within the application window.
6. No activation, rejection, withdrawal, or transfer by \(L+90\) days.

Acceptance and contract signing are intermediate states. An accepted but unactivated application can therefore have outcome 6. A later activation, after the application window, does not retrospectively change that endpoint. Transfer is an absorbing exit from the originating platform for this primary target, regardless of subsequent partner performance. Validate the assumed ordering of these dispositions; contradictory or reused identifiers require adjudication.

The primary prediction time is immediately after the registered Application Started event, using only information available then. Supplementary models update the forecast after specified early event counts or elapsed times, while the application remains before its first final decision or exit. Their estimands condition on being eligible at that later landmark; they do not represent all original applications.

The unit is a registered application episode in the 48,000-application source cohort, not an event or necessarily a unique borrower. Source identifiers must be made globally unambiguous. Linked continuations belong to dependence groups and must not be mistaken for independent new applications or used to rewrite a transfer into an originating-platform activation. If the registry actually counts duplicated identifiers for the same originating episode, reconcile that discrepancy before claiming 48,000 distinct applications.

The population is all registered applications starting from 1 January 2024 through 31 December 2025, including those absent from the labeled export. The application disposition horizon is 90 days from the landmark; activated cases then receive a separate 90-day account horizon. Thus the latest substantive endpoint occurs by \(L+180\) days. Feed delay affects when that endpoint becomes observable, not its definition.

The estimand is \(P(J=j\mid X_L,L,\text{source and operating-policy context})\), with probabilities summing to one. The early warning probability is the first component: activation within the application window **and** default during the account’s first 90 days. It describes the observed-policy pathway, rather than creditworthiness under forced activation. Retain all six components when communicating the score: a small default-pathway probability can reflect a high rejection probability. The 90-day activation window is a declared operational choice and should be checked against alternative windows, not optimized to obtain convenient labels.

Credible alternatives answer different questions:

- **Conditional account risk:** \(P(D_{90}=1\mid X_L,A\le L+90)\). This predicts default among applications activated within the window. It may support account-risk forecasting, but conditions on future selection and cannot be presented as every applicant’s default risk. Conditioning on eventual activation without a finite activation window also creates an ill-defined follow-up requirement.
- **Time to default after activation:** start the account clock at activation and estimate default-free survival with right censoring. This needs actual default occurrence dates and reliable observation endpoints. The supplied binary label alone does not reveal an exact default time; Default Recorded may be a reporting timestamp. Interval-censored or binary-horizon analysis is possible when occurrence dates cannot be recovered.
- **Policy-specific counterfactual account risk:** default if an application were activated under a specified underwriting, limit, pricing, and servicing policy. This requires causal assumptions and information beyond these selectively observed outcomes. It is not identified merely by weighting the existing labeled export.

## 2. Cohort construction

Start with the complete application registry and event records, not with the 21,600-row ML export. Confirm that applications_events.csv contains all 48,000 cases and their relevant events; if it contains only the labeled cohort, this study cannot be implemented from that file alone. Require a valid original start and a stable case identity. Preserve legitimate document loops. Document malformed timestamps, ambiguous identity, impossible paths, and unresolved duplicate events as data-quality exceptions with counts, rather than quietly selecting a cleaner outcome cohort.

Separate three clocks: event occurrence, account outcome horizon, and label availability. For an analysis made at knowledge cutoff \(C\), event follow-up ends at \(E(C)=\min(C,\text{31 December 2025})\). A label is usable only if its genuine availability time is at or before \(C\), its account has activated, and its outcome horizon has matured. February extraction does not supply January–February application events. A row carrying a repeated label on an old event does not make that label available at that event’s date.

|---|---:|---|
| Activated, labeled non-default | 18,900 | Observed account mark 0 after activation; use only when available at the relevant analysis cutoff. |
| Activated, labeled default | 2,700 | Observed account mark 1 after activation; same availability restriction. |
| Rejected | 9,100 | Observed competing application disposition, not an account default label. |

These are snapshot counts, not the six landmark-target counts. A labeled activation outside a landmark’s activation window does not become outcome 1 or 2 for that landmark; similarly, a rejection after the window does not replace “pending at 90 days.” Reconstruct every target using its own landmark and cutoff.

The provided counts do not identify the division of the 3,600 between horizon immaturity and feed delay, nor the number of permanently missing feeds. “Not mature” must not become a permanent explanation for every unavailable outcome. Report overdue or unresolved feeds within the activated population without adding them again to the 48,000 total. The observed 2,700/21,600 = 12.5% is a default proportion among labeled activated accounts, not a default rate for all applications or necessarily all activated accounts.

At the start landmark, eligibility must not depend on future activation, case length, outcome observation, or eventual feed receipt. At later landmarks, a case is eligible only if the required information has actually arrived and the final decision/exit has not already occurred. Identity and prefix-availability exclusions must be counted by channel, region, period, and observed disposition. Keep training inclusion, target ascertainment, and evaluation eligibility as separate flags.

## 3. Censoring and missing-label strategy

The mechanisms require different treatment:

- **Ordinary right censoring:** a still-at-risk application has not reached a disposition before the event-observation endpoint. It contributes observed preactivation risk time; it is not rejected or non-default. Activated accounts with unfinished account horizons also have incomplete follow-up, although a binary-only feed does not provide the default-free exposure needed for ordinary exact-time survival analysis.
- **Delayed labels:** the account’s 90-day endpoint has passed, but its result has not yet arrived. These are unresolved binary marks, not necessarily unfinished clinical or financial follow-up. The usual 7–35-day delay is an operational observation, not a guaranteed maximum.
- **Selection through activation:** only activated applicants possess the observed account outcome. This is a substantive transition determined partly by underwriting and applicant behavior, not random label censoring. Rejected and withdrawn applicants never enter the account outcome risk set.
- **Transfer:** a competing disposition for the primary source-platform target. For a borrower-wide target that follows partner accounts, transfer instead creates linkage and follow-up missingness; 60% linkage is not a random sample unless justified.
- **Permanently missing feeds:** potentially informative loss of ascertainment among activated accounts, especially partner-originated accounts. Additional waiting does not necessarily recover these outcomes.

**Primary analysis:** estimate preactivation competing transitions using all eligible applications, retaining administrative censoring. A discrete-time cause-specific hazard model can represent pending review, document rework, acceptance, signing, and the absorbing dispositions. Ordinary cause-specific analysis removes competing exits from subsequent risk sets; calculating cumulative incidence must retain their probability mass, not treat them as ordinary independent loss to follow-up.

Attach a binary 90-day default mark to activation. Estimate that mark among administratively mature activated accounts, using the same landmark features, activation time, and calendar context. For mark training, initially require activation plus 90 days plus a 35-day reporting allowance to precede the fit cutoff. This avoids preferentially using only the fastest feeds from recent activations. Available earlier labels may be stored for later evaluation, but are not selectively added to this conservative mark-training risk set. Within the mature risk set, retain cases with missing marks to estimate the probability of feed observation; use inverse-ascertainment weighting or an explicitly specified missing-data likelihood if the required assumptions and overlap hold. Do not use inverse activation weights to manufacture credit outcomes for rejected applicants.

For a simplified single pending state, the default-pathway probability has the form

\[
P(J=\text{activated default}\mid X_L)
=\int_0^{90} S_{\mathrm{pre}}(u^-\mid X_L)\,
\lambda_A(u\mid X_L)\,m_{90}(X_L,u)\,du,
\]

where competing rejection, withdrawal, and transfer hazards enter preactivation survival, and \(m_{90}\) is conditional account default risk given activation at \(L+u\). A discrete-time implementation replaces the integral by a sum. An expanded process-state model uses activation-state occupancy probabilities instead. Future activity, decision, or updated score values cannot be plugged into an early forecast: integrate future transitions and any required future covariates rather than supplying realized values.

Administrative censoring must be conditionally independent given the modeled history/calendar, and feed observation must be conditionally independent of the account mark given the ascertainment covariates. Both require appropriate support. Recent activation periods with no mature outcomes have zero maturity support: weights cannot identify their mark risk. Forecasting there requires transport assumptions from earlier periods, which the policy change makes questionable. Missingness weights should be stabilized, audited for extremes, and accompanied by results under alternative truncation choices.

Use at least these sensitivity analyses:

1. Vary the reporting allowance, activation window, calendar strata, and ascertainment specification. Compare conservative mature-only estimates with delay-adjusted estimates and repeated extractions when available.
2. For mature missing feeds, vary default risk through a stated odds shift, especially by partner origin. Also report worst-case bounds. If a stratum has missing fraction \(r\) and observed-mark default proportion \(p\), its unrestricted account-risk bounds are \([(1-r)p,(1-r)p+r]\); propagate these through activation probabilities. These bounds concern activated missing outcomes, not unobserved defaults under forced activation of rejected cases.
3. Keep transfer absorbing in the primary analysis, then examine a distinct linked downstream target. Show linkage selection by prefix/channel/calendar and bounds or assumptions for unlinked transfers. Do not silently switch target populations between results.

Observed activation frequencies, missingness associations, arrival-lag distributions among received labels, weight overlap, and subgroup drift can be examined. Repeated extracts can partially distinguish delays from persistent absence. Conditional independent censoring and missing-at-random feeds are not proven by such diagnostics; feed lag itself can depend on default. Permanently missing outcomes, defaults under rejected applicants’ hypothetical activation, and transfer outcomes without linkage/follow-up are fundamentally unidentified without stronger assumptions or new data. Provide group/time bootstrap intervals for sampling uncertainty and separate sensitivity ranges for this identification uncertainty.

## 4. Prefix extraction

Construct each prefix from an event history ordered by a stable recorded event sequence, using timestamps normalized to UTC. Event occurrence time must agree with operational availability; retrospective imports require ingestion/first-available timestamps. The supplied schema cannot prove historical availability of backfilled events. Labels and forbidden attributes are separated before creating any PM4Py log.

For fixed event-count landmarks, use the first \(k\) verified events, for example \(k=1,3,5\), and set \(L\) to the last included event’s actual availability time. Require that the \(k\)-th event exists and occurs before acceptance, rejection, withdrawal, transfer, or activation for this early-decision use. PM4Py returns shortened prefixes for short traces; those are not genuine \(k\)-event landmarks. Report their missing coverage and retain their earlier start predictions. Never pad a short case with its terminal event or select only cases that eventually reach \(k\).

For elapsed-time landmarks, use events available by start plus 24 hours or seven days. Require observation through that landmark and no prior final decision/exit. A still-open case with just its start event can receive an elapsed-time update; a case already closed cannot. Do not choose elapsed time from the eventual case duration.

Preserve repeated document requests and returns to Credit Review as separate legitimate events. Remove only confirmed ingestion retries. Without event IDs, identical-looking rows can be genuine repeated actions; flag ambiguity and repair through provenance. Quarantine an unresolved duplicate from a prefix only when it is already present in that prefix, not because a duplicate appears later in the case.

Use a documented activity dictionary to map verified migration aliases to consistent concepts; fit no outcome-driven mappings. Retain source/version indicators and audit residual unseen names. Timestamp ties need reliable sequence identifiers for exact event-count order. Otherwise reject a count boundary that splits a tie, represent fully observed tied activities as a set, and avoid invented control-flow order. Elapsed prefixes include the whole tied timestamp block. Report these replay limitations rather than promising unsupported coverage of every application.

Separate availability sources explicitly:

For historical reference features in training rows, use rolling/out-of-fold past-only construction rather than each row’s own eventual outcome. ## 7. Validation design

Use rolling temporal fits and prospective scoring. Group all prefixes of a case, and known linked continuations, together. A case-start split is primary; for known linkage groups spanning periods, purge overlapping groups rather than move later episodes into an earlier training snapshot. Unknown linkage remains a material limitation. Use a deployment-like gap or conservative source restrictions as sensitivity checks; neither guarantees removal of unknown overlap.

A concrete initial schedule is:

- Fit on 2024 starts using information and labels available immediately before 1 January 2025. Unresolved training cases contribute appropriate censored process observations; their future labels are unavailable for this fit.
- Score January–June 2025 starts prospectively. Use only validation labels available by the 1 July update for tuning/calibration, with censoring and maturity support restrictions. Later-arriving validation labels can assess those frozen predictions, but cannot retrospectively justify an earlier tuning decision.
- Freeze the chosen specification, optionally refit on information available by 1 July, and score July–December 2025 starts. Keep July–September and the post-15-October migration cohorts separately visible, and examine cases whose decision/follow-up spans a policy change. Each later rolling update gets its own training, calibration, and knowledge cutoff.

A late event-count landmark from an earlier-start case must use the model version actually available at its landmark, or be excluded from that snapshot’s training/calibration. Fit all preprocessing and historical references inside each temporal fold. The skeleton uses partition-specific cutoffs and only admits prefixes available by those cutoffs; actual prospective scoring requires dated model versions as well.

Maturity is a major limit here. Guaranteed completion of the chosen pathway plus a 35-day reporting allowance can require \(90+90+35=215\) days from the landmark. By 15 February 2026, that conservative window is available only for landmarks on or before 15 July 2025. Also, a full unresolved application window needs events through \(L+90\); with this event export that requires \(L\le\) 2 October 2025. Earlier observed exits can be classified sooner, but selecting only those resolved cases biases evaluation.

Consequently, the snapshot supports a fully mature test chiefly in early July, not a complete late-2025 test. Later cohorts can provide supported partial-follow-up transition assessments and some observed account marks. Censoring adjustment requires follow-up support; it cannot nonparametrically identify an entirely unobserved horizon in a new regime. The 15 October migration landmark would need application events through mid-January 2026 and, conservatively, outcome/feed observation through 18 May 2026. Extend the event export as well as the feed to evaluate it fully. Report provisional/extrapolative findings explicitly.

Evaluate the complete six-state distribution using multiclass log loss and Brier score, with appropriate censored/coarsened likelihood or separately modeled censoring/ascertainment weights when labels are incomplete. Check calibration of each competing disposition, activation probability, the joint default-pathway probability, and the conditional account mark. For the default-pathway component, competing outcomes have their own observed category; a cause-specific binary scoring indicator does not create an account-level non-default label for those cases.

Use cumulative-incidence calibration and observed-versus-predicted pathway frequencies at prespecified times, transition-specific error measures, and precision–recall/discrimination for observed mature account marks as secondary measures. Apply missingness correction to mark metrics where defensible; do not report complete-case AUROC as population validation. Assess decision utility using stated warning costs and capacity, rather than maximizing AUROC alone. Do not compute exact-time default concordance from Default Recorded unless its occurrence-time semantics are established.

Report coverage, number at risk, label/feeding maturity, censoring proportions, weight effective sample size, uncertainty intervals, and subgroup calibration by channel, region, source/partner origin, requested amount, and policy/migration period. Audit shifted prefix distributions, new activity names, loop frequency, inter-event times, activation selection, label observation, and resource workload. Use clustered bootstrap intervals across cases/linked groups, with calendar blocks when assessing temporal dependence; multiple prefixes are not independent observations.

A random case split mixes policy and migration regimes, lets later label knowledge influence earlier deployment, places repeated linked journeys on both sides, and overrepresents readily labeled activated cases. It answers an easier retrospective interpolation question while concealing the deployment and selection problems.

## 8. Limitations and decision-use boundary

The study can estimate observed-policy application pathways and, with stated ascertainment assumptions, default risk conditional on activation. It cannot claim that rejected, withdrawn, transferred, or still-open applicants would have avoided default if granted credit. A low joint pathway risk may result from exclusion from credit; it is not evidence of low counterfactual account risk.

Activation selection is part of the primary estimand. Feed selection is an observation problem requiring assumptions or bounds. Prediction remains association: resource workload, channel, or a review loop can predict a pathway without causing default. Calibration on the labeled export alone establishes neither population calibration nor equitable underwriting. Unknown transfer linkage, absent historical availability versions, informative missing feeds, and immature policy/migration cohorts limit identification and generalization.

At least five deployment changes can alter the data-generating process:

1. Using warnings to reject or accept applicants changes activation probabilities and the composition of observed account outcomes.
2. Changing limits, pricing, or account terms changes post-activation default risk, even with the same application prefix.
3. Asking flagged applicants for additional documents changes loop frequency, elapsed times, withdrawal, and which later landmarks are reached.
4. Routing flagged cases to specialists/partners changes workload, transfer frequencies, linkage, and feed ascertainment.
5. Intensified monitoring or collections can prevent default or improve its detection, changing both the outcome and its availability process.

Use the forecast for monitoring and review under a declared policy, display activation and competing-pathway probabilities beside default-pathway risk, and distinguish sampling intervals from missing-data sensitivity ranges. Avoid presenting unsupported partner/new-regime predictions as precise. Record interventions and preserve outcome follow-up after deployment. Evaluating a new approval policy or treatment effect requires a separate causal design, preferably controlled or otherwise defensibly identified; predictive performance under historical selection is insufficient.

## 9. PM4Py-oriented Python implementation skeleton

The skeleton assumes the supplied file is the complete, globally keyed source cohort; static attributes are historically valid; event timestamps reflect availability; and outcome values are binary mature-horizon marks. The migration dictionary and linkage map must be populated from audited local provenance. It retains unresolved labels, quarantines ambiguous duplicates already present in a prefix, and rejects contradictory process identities rather than silently selecting their outcomes. PM4Py handles event preparation, prefixes, and training-only process diagnostics; transition and missingness models are connected separately.

```python
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
EVENT_END = pd.Timestamp("2025-12-31 23:59:59.999999999", tz="UTC")
EXTRACT = pd.Timestamp("2026-02-15", tz="UTC")  # use the actual extraction instant
TRAIN_END, VAL_END = pd.Timestamp("2025-01-01", tz="UTC"), pd.Timestamp("2025-07-01", tz="UTC")
ASOF = {"train": TRAIN_END, "validation": VAL_END, "test": EXTRACT}
D90, LAG = pd.Timedelta(days=90), pd.Timedelta(days=35)
K = 1  # primary start-event landmark; rerun with 3 or 5 for eligible updates
RENAMES = {"Accept": "Accepted", "Reject": "Rejected"}  # extend using a verified migration dictionary
LINK_GROUP = {}  # populate from audited linkage; unlinked transfers remain competing exits
raw = pd.read_csv("applications_events.csv", dtype={CASE: "string"})
for c in [TS, "label_available_at", "data_extract_time"]:
    raw[c] = pd.to_datetime(raw[c], utc=True, errors="raise")
assert raw[[CASE, ACT, TS, "data_extract_time"]].notna().all().all()
raw = raw.loc[raw["data_extract_time"].le(EXTRACT)].copy()
raw[ACT] = raw[ACT].replace(RENAMES)
duplicate_at = raw.loc[raw.duplicated(keep=False)].groupby(CASE)[TS].min()
print("Exact duplicate rows:", int(raw.duplicated().sum()))
# Only enable this after confirming identical rows are ingestion retries, not distinct events.
CONFIRMED_EXACT_RETRIES = False
if CONFIRMED_EXACT_RETRIES:
    raw = raw.drop_duplicates()
raw["_row"] = np.arange(len(raw))
# Historical replay assumes occurrence-time availability; ingestion history is otherwise required.
SAFE = [CASE, ACT, TS, "org:resource", "case:channel", "case:region", "case:requested_amount", "source_system", "_row"]
e = raw.loc[raw[TS].between(pd.Timestamp("2024-01-01", tz="UTC"), EVENT_END), SAFE].copy()
e = e.sort_values([CASE, TS, "_row"])
cases = e.loc[e[ACT].eq("Application Started")].groupby(CASE)[TS].min().to_frame("started")
assert len(cases) == 48000 and e[CASE].isin(cases.index).all(), "Reconcile the complete application registry"
cases["activated"] = e.loc[e[ACT].eq("Account Activated")].groupby(CASE)[TS].min()
EXIT = {"Rejected", "Withdrawn", "Transferred"}
DISPOSITION = EXIT | {"Account Activated"}
terminal = e.loc[e[ACT].isin(EXIT)].drop_duplicates(CASE).set_index(CASE)
cases["terminal_at"], cases["terminal_type"] = terminal[TS], terminal[ACT]
STOP = DISPOSITION | {"Accepted"}
cases["stop"] = e.loc[e[ACT].isin(STOP)].groupby(CASE)[TS].min()
cases["bad_path"] = cases["activated"].notna() & cases["terminal_at"].notna()
cases["unresolved_duplicate_at"] = duplicate_at if not CONFIRMED_EXACT_RETRIES else pd.Series(pd.NaT, index=cases.index, dtype="datetime64[ns, UTC]")
assert not cases.bad_path.any(), "Adjudicate inconsistent paths or reused IDs; do not silently select clean outcomes"
assert e[TS].ge(e[CASE].map(cases.started)).all(), "Events precede the recorded application start"
cases["split"] = np.select([cases.started.lt(TRAIN_END), cases.started.lt(VAL_END)], ["train", "validation"], default="test")
cases["group"] = cases.index.to_series().map(LINK_GROUP).fillna(cases.index.to_series())
cases["cross_split"] = cases.groupby("group")["split"].transform("nunique").gt(1)

def labels_at(cut):
    r = raw.loc[raw["label_available_at"].le(cut) & raw["default_90d"].notna()]
    g = r.groupby(CASE)["default_90d"].agg(["min", "max"])
    assert g["min"].eq(g["max"]).all() and g["min"].isin([0, 1]).all()
    assert g.index.isin(cases.index).all()
    assert r["label_available_at"].ge(r[CASE].map(cases.activated) + D90).all()
    assert (cases.loc[g.index, "activated"] + D90).le(cut).all(), "Invalid maturity/activation metadata"
    return g["min"]

y_extract = labels_at(EXTRACT)
cases["snapshot_status"] = cases.terminal_type.fillna("open")
a = cases.activated.notna()
cases.loc[a, "snapshot_status"] = "activated_horizon_pending"
cases.loc[a & (cases.activated + D90).le(EXTRACT), "snapshot_status"] = "activated_feed_pending"
cases.loc[a & (cases.activated + D90 + LAG).le(EXTRACT), "snapshot_status"] = "activated_feed_overdue"
cases.loc[y_extract.index, "snapshot_status"] = y_extract.map({0: "labeled_nondefault", 1: "labeled_default"})
print("Snapshot flow:", cases.snapshot_status.value_counts().to_dict(), "bad paths:", int(cases.bad_path.sum()))

# PM4Py receives a whitelist, never labels, decision fields, or collection fields.
formatted = pm4py.format_dataframe(e[SAFE], case_id=CASE, activity_key=ACT, timestamp_key=TS)
log = pm4py.convert_to_event_log(formatted)
p = pm4py.convert_to_dataframe(pm4py.get_prefixes_from_log(log, length=K))
b = p.groupby(CASE)[TS].agg(n="size", L="max").join(cases)
next_time = e.groupby(CASE)[TS].apply(lambda s: s.iloc[K] if len(s) > K else pd.NaT)
# A count prefix must not split a timestamp tie; row order is not a trustworthy causal order.
b["tie_ok"] = next_time.reindex(b.index).isna() | next_time.reindex(b.index).gt(b.L)

def outcomes_at(cut, landmarks):
    event_cut = min(cut, EVENT_END)
    observed = e.loc[e[TS].le(event_cut) & e[ACT].isin(DISPOSITION)]
    first = observed.drop_duplicates(CASE).set_index(CASE)[[ACT, TS]]
    z = landmarks[["L"]].join(first.rename(columns={ACT: "disposition", TS: "at"}))
    z["deadline"] = z.L + D90
    resolved = z["at"].le(z.deadline)
    z["target"] = "censored_preactivation"
    z.loc[~resolved & z.deadline.le(event_cut), "target"] = "pending_at_90d"
    z.loc[resolved, "target"] = z.loc[resolved, "disposition"]
    activated = resolved & z.disposition.eq("Account Activated")
    z.loc[activated, "target"] = "activated_horizon_pending"
    z.loc[activated & (z["at"] + D90).le(cut), "target"] = "activated_feed_pending"
    z.loc[activated & (z["at"] + D90 + LAG).le(cut), "target"] = "activated_feed_overdue"
    z["default_90d"] = labels_at(cut).reindex(z.index).where(activated & (z["at"] + D90).le(cut))
    known = activated & z.default_90d.notna()
    z.loc[known, "target"] = z.loc[known, "default_90d"].map({0: "activated_nondefault_90d", 1: "activated_default_90d"})
    end = z["at"].where(resolved, z.deadline).clip(upper=event_cut)
    z["pre_followup_days"] = (end - z.L).dt.total_seconds().div(86400).clip(lower=0)
    z["pre_event"] = resolved
    z["mark_window_complete"] = activated & (z["at"] + D90 + LAG).le(cut)
    z["mark_observed"] = z.mark_window_complete & z.default_90d.notna()
    # Restrict mark training to mark_window_complete; estimate feed-observation weights within that set.
    # Competing-risk hazards use pre_event/followup; activated binary marks need ascertainment modeling.
    # A missing mark is never filled with zero; this is not exact-time default survival data.
    return z
```
