## 1. Temporal Data Semantics
- **State Reconstruction**: The state is reconstructed sequentially. Events are processed in order of `time:timestamp`.
- **Handling Blanks**: Blank attribute cells denote "no update" and inherit the most recent known value (forward-fill). They do not reset the attribute to null.
- **Equal Timestamps**: When timestamps are identical, the `event_index` acts as the definitive tie-breaker to establish the chronological sequence.
- **Material Changes**: A material change is defined strictly as an amount increase > 20% relative to the amount at the time of the latest review. Decreases or unknown amounts do not trigger this.
- **Final Attributes**: Case-level final attributes are ignored for historical evaluation. The state at any given event is solely determined by events that occurred prior to or at that exact moment.
- **Time Dimensions**:
  - *Event time*: The timestamp when the action occurred in the source system.
  - *Effective time*: When an exemption or status becomes legally active.
  - *Record time*: When the event was inserted into the database (can be delayed).
  - *Evidence time*: The timestamp of cryptographic signatures or immutable proofs.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| R1 | `Release_Funds` AND `jurisdiction != DE` AND `amount >= 100000` | `Enhanced_Review` | `Enhanced_Review` < `Release_Funds` AND no material change in between | Event time of `Release_Funds` | Valid exemption waiving R1 | INDETERMINATE | Cryptographic proof of exemption |
| R2 | `Release_Funds` AND (`risk_level == HIGH` OR `customer_type == PEP`) | `Enhanced_Review` AND `Compliance_Approve` | `Enhanced_Review` < `Compliance_Approve` < `Release_Funds` | Event time of `Release_Funds` | None | INDETERMINATE | N/A |
| R3 | `Release_Funds` AND `Sanctions_List_Update` matches `jurisdiction` | `Sanctions_Screen` | `Sanctions_List_Update` < `Sanctions_Screen` < `Release_Funds` | Event time of `Release_Funds` | None | INDETERMINATE | N/A |
| R4 | `Update_Amount` | N/A | N/A | Event time of `Update_Amount` vs `Enhanced_Review` | None | INDETERMINATE | N/A |
| R5 | `Release_Funds` referencing exemption | `Record_Exemption` or external proof | Approval evidence time <= `Release_Funds` | Event time of `Release_Funds` | None | INDETERMINATE | Cryptographic signature or reliable witness |
| R6 | Any rule evaluation | N/A | N/A | Event time | None | Classify as INDETERMINATE | External resolution |
| R7 | Any rule evaluation | N/A | `event_index` resolves ties | Event time | None | N/A | N/A |

**Formal Pseudo-logic:**
```logic
R1: Release_Funds(t_rel) ∧ State(t_rel).jur ≠ 'DE' ∧ State(t_rel).amount ≥ 100000 ⇒ 
    (∃ t_rev < t_rel : Enhanced_Review(t_rev) ∧ ¬(∃ t_upd ∈ (t_rev, t_rel) : Material_Change(t_upd, t_rev))) 
    ∨ Valid_Exemption(t_rel, 'R1')

R2: Release_Funds(t_rel) ∧ (State(t_rel).risk = 'HIGH' ∨ State(t_rel).type = 'PEP') ⇒ 
    ∃ t_rev, t_app : Enhanced_Review(t_rev) ∧ Compliance_Approve(t_app) ∧ (t_rev < t_app < t_rel)

R3: Release_Funds(t_rel) ∧ (∃ t_list < t_rel : Sanctions_List_Update(t_list) ∧ t_list.jur = State(t_rel).jur) ⇒ 
    ∃ t_scr : Sanctions_Screen(t_scr) ∧ (t_list < t_scr < t_rel)

R4: Material_Change(t_upd, t_rev) ⇔ Update_Amount(t_upd) ∧ State(t_upd).amount > 1.20 * State(t_rev).amount

R5: Valid_Exemption(t, rule) ⇔ ∃ e : Exemption(e) ∧ e.rule = rule ∧ e.approved_by = 'Head_Compliance' 
    ∧ e.effective_from ≤ t ∧ e.expires > t ∧ Matches_Scope(e, State(t)) ∧ Evidence_Time(e) ≤ t

R6: (State(t).amount = NULL ∨ State(t).risk = NULL ∨ State(t).jur = NULL ∨ State(t).type = NULL) ⇒ INDETERMINATE

R7: t1 < t2 ⇔ t1.timestamp < t2.timestamp ∨ (t1.timestamp = t2.timestamp ∧ t1.event_index < t2.event_index)
```

## 4. Ambiguities and Alternative Readings
- **TX-302**: The exemption record was inserted late due to an outage. If policy strictly requires the database record to exist prior to release for control-flow conformance, this would be NONCOMPLIANT. However, accepting cryptographic evidence of prior approval makes it COMPLIANT.
- **TX-305 (INDETERMINATE)**: The amount is missing at release. If we retroactively accept the settlement amount (150,000) as the release amount, R1 triggers, and since an `Enhanced_Review` occurred, the case becomes COMPLIANT. If the true amount was < 100k, R1 wouldn't trigger at all.
- **TX-310 (INDETERMINATE)**: Exemption EX-88 relies on a backdated PDF and a signature created after release. If the oral approval by the transaction requester is deemed legally sufficient despite the conflict of interest, it's a JUSTIFIED_EXCEPTION. If rejected due to the crypto signature post-dating the release, it's NONCOMPLIANT.
- **TX-311**: Jurisdiction changed to DE *after* the `Enhanced_Review` but *before* `Release_Funds` at the exact same timestamp (ordered by `event_index`). If policy intent dictates that the jurisdiction at the time of review must match the release, this might be a loophole. Under strict event-time semantics, R1 only checks jurisdiction at `Release_Funds`, making it COMPLIANT.

## 6. Why Control-Flow-Only Conformance Is Insufficient
1. **Final-State Leakage**: Control-flow models often attach variables at the trace level (final state), causing past events to be evaluated against future data (e.g., evaluating a review against an amount that was updated later).
2. **Post-Hoc Exemptions**: Control-flow can verify if an `exemption_id` exists in the trace, but cannot validate if the cryptographic signature timestamp precedes the `Release_Funds` event.
3. **Material Changes After Review**: A control-flow model sees `Enhanced_Review` followed by `Release_Funds` as compliant, ignoring that an intermediate `Update_Amount` invalidated the review.
4. **Conditional Activation**: Rules like R1 trigger only on continuous variables (amount >= 100k). Pure control-flow cannot branch on data thresholds.
5. **Missing Data**: Control-flow models cannot natively reason about `UNKNOWN` values or distinguish between "missing" and "zero", which is critical for obligations like R6.
6. **Same-Timestamp Ordering**: Standard process mining tools rely on timestamps. When events share a timestamp (e.g., TX-311), control-flow models may shuffle them, whereas data-aware models use `event_index` for deterministic state transitions.

## 7. Recommended Logging and Control Improvements
- **Immutable Release Payloads**: Log the exact state (amount, jurisdiction, risk) directly inside the `Release_Funds` event payload to eliminate ambiguity about the state at release.
- **Effective/Record/Signature Timestamps**: Separate these timestamps in the exemption register to automate validity checks and detect backdating.
- **Rule Versioning**: Include the active policy version in the event log to ensure historical transactions are evaluated against the rules active at the time.
- **Exemption Scope**: Use machine-readable formats (e.g., JSON) for exemption scopes rather than free-text notes.
- **Change Provenance**: Log the reason and source for data changes (e.g., "customer request", "adverse media hit") to better assess material changes.
- **Stable Event Ordering**: Enforce strict monotonic sequence numbers (`event_index`) across the entire distributed system, not just within identical timestamps.
