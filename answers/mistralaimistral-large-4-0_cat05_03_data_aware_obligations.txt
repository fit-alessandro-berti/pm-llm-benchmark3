## 1. Temporal Data Semantics

- **State reconstruction:** Within each case, sort events by `(time:timestamp, event_index)`. A blank attribute cell means “no update at this event,” not “set to null.” Therefore I forward-fill only from earlier events in the same case, never copying future values backward.
- **Event time vs. effective time vs. record time vs. evidence time:**
  - **Event time** is the timestamp in the log.
  - **Effective time** is when an attribute update takes effect; by default it is the event timestamp unless evidence explicitly establishes another effective time.
  - **Record time** is when a record was written, e.g., `Record_Exemption` at 11:00.
  - **Evidence time** is when evidence was created or signed, e.g., a qualified digital signature timestamp or certificate creation time.
- **Same-timestamp ordering:** When two events share a timestamp, `event_index` is the tie-breaker. Example: in TX-311, `Enhanced_Review` has `event_index=3` and `Update_Jurisdiction` has `event_index=4` at 16:20. Therefore the review occurred before the jurisdiction change, so at review time the jurisdiction was still US; at release it was DE.
- **Material changes:** An amount increase of more than 20 percent after the latest `Standard_Review` or `Enhanced_Review` invalidates that review for amount-dependent obligations. A decrease does not by itself invalidate a review. Other changes that affect obligation triggers—risk reclassification to/from HIGH, customer-type change to/from PEP, jurisdiction changes—are treated as material for the relevant rules.
- **Final attributes:** Final case attributes are not copied backward. Each obligation is evaluated using the latest known value at the relevant event.
- **Missing data:** Missing amount, risk, jurisdiction, or customer type is treated as unknown, not as a low-risk default. If a decisive trigger cannot be established or excluded, the case is INDETERMINATE unless other evidence resolves it.

### Formal pseudo-logic

Define:

```text
prior(e1, e2)  (ts(e1) < ts(e2))  (ts(e1) = ts(e2)  idx(e1) < idx(e2))
prior_or_same(e1, e2)  prior(e1, e2)  e1 = e2
state_at(e, attr, v)  latest event e' with prior_or_same(e', e) in same case that updates attr, value v
material_amount_change(e)  amount_before(e, a1)  amount_after(e, a2)  a1 known  a2 > a1 * 1.20
material_change(e)  material_amount_change(e)  risk_changed(e)  jurisdiction_changed(e)  customer_type_changed(e)
```

**R1**

```text
trigger_R1(r)  release(r)  state_at(r, jurisdiction, J)  J  "DE" 
                 state_at(r, amount, A)  A  100000

latest_material_before(r, m)  material_change(m)  prior(m, r) 
    ¬m' (material_change(m')  prior(m', r)  prior(m, m'))

enhanced_ok_R1(r)  e (enhanced_review(e)  prior(e, r) 
    (¬m latest_material_before(r, m)  m (latest_material_before(r, m)  prior(m, e))))

exemption_ok_R1(r)  x (exemption_claimed(r, x)  valid_exemption_R5(x, r))

violation_R1(r)  trigger_R1(r)  ¬(enhanced_ok_R1(r)  exemption_ok_R1(r))
```

Direction: `prior(m, e)` means material change `m` is before enhanced review `e`.

**R2**

```text
trigger_R2(r)  release(r)  (state_at(r, risk_level, "HIGH")  state_at(r, customer_type, "PEP"))

relevant_enhanced(r, e)  enhanced_review(e)  prior(e, r) 
    ¬e' (enhanced_review(e')  prior(e', r)  prior(e, e'))

violation_R2(r)  trigger_R2(r)  ¬(e relevant_enhanced(r, e) 
    c compliance_approve(c)  prior(e, c)  prior(c, r))
```

Direction: `e < c < r`.

**R3**

```text
latest_screen_before(r, s)  sanctions_screen(s)  prior(s, r) 
    ¬s' (sanctions_screen(s')  prior(s', r)  prior(s, s'))

trigger_R3(r)  release(r)  state_at(r, jurisdiction, J) 
    u (sanctions_list_update(u, J)  prior(u, r) 
        (¬s latest_screen_before(r, s)  s (latest_screen_before(r, s)  prior(s, u))))

violation_R3(r)  trigger_R3(r)  ¬s2 (sanctions_screen(s2)  prior(u, s2)  prior(s2, r))
```

Direction: `s < u < s2 < r`.

**R4**

```text
material_amount_change(e)  amount_before(e, a1)  amount_after(e, a2)  a1 known  a2 > a1 * 1.20

latest_review_before(e, v)  review(v)  prior(v, e) 
    ¬v' (review(v')  prior(v', e)  prior(v, v'))

invalidated_review(e)  material_amount_change(e)  v (latest_review_before(e, v))
```

Direction: `v < e`.

**R5**

```text
valid_exemption(x, r) 
    approved_by(x, "Head_Compliance") 
    effective_from(x)  trigger_time(r) 
    expires(x)  trigger_time(r) 
    scope_jurisdiction(x) = state_at(r, jurisdiction) 
    scope_customer_type(x) = state_at(r, customer_type) 
    scope_amount_max(x)  state_at(r, amount) 
    evidence_supports_approval_at(x, trigger_time(r))
```

Direction: `effective_from  trigger  expiry`; approval evidence time ` trigger`.

**R6**

```text
unknown(attr, r)  state_at(r, attr, unknown)

indeterminate_obligation(r)  obligation_trigger_depends_on(attr, r) 
    unknown(attr, r)  ¬ other evidence resolving attr at r
```

**R7**

```text
state_at(e, attr, v)  latest event e' with prior_or_same(e', e) in same case that updates attr, value v

prior(e1, e2)  (ts(e1) < ts(e2))  (ts(e1) = ts(e2)  idx(e1) < idx(e2))
```

## 4. Ambiguities and Alternative Readings

- **TX-301:** If an `Enhanced_Review` had occurred after 08:20 and before 08:25, R1 would be satisfied. If jurisdiction were DE or amount < 100k, R1 would not trigger. Given the facts, NONCOMPLIANT.
- **TX-302:** If the `Enhanced_Review` at 09:20 were absent, the valid EX-77 exemption would make the case JUSTIFIED_EXCEPTION. If EX-77 evidence were weak, the Enhanced_Review still makes it COMPLIANT. The result is robust.
- **TX-303:** If a `Compliance_Approve` had occurred after 10:20 and before 10:30, R2 would be satisfied. If the risk reclassification to HIGH were reversed before release, R2 would not trigger. Given the facts, NONCOMPLIANT.
- **TX-304:** If a new `Sanctions_Screen` occurred after 08:30 and before 08:45, R3 would be satisfied. If XZ were not added to the sanctions list, R3 would not trigger. Given the facts, NONCOMPLIANT.
- **TX-305:** INDETERMINATE. If an immutable release payload showed amount  100k, R1 would be triggered and the Enhanced_Review at 11:15 would satisfy it  COMPLIANT. If amount < 100k  COMPLIANT. If amount  100k and no Enhanced_Review  NONCOMPLIANT. If the settlement amount 150000 could be definitively linked to the release amount via an immutable payload, then R1 would be triggered and satisfied. Given the facts, INDETERMINATE.
- **TX-306:** If the amount increase at 12:30 were > 20%, R4 would invalidate the Enhanced_Review and R1 would require a new review  NONCOMPLIANT. If `Compliance_Approve` were before `Enhanced_Review`, R2 would be violated. Given the facts, COMPLIANT.
- **TX-307:** If a true `Enhanced_Review` had occurred after 13:05 and before release, R2 would be satisfied. If customer_type were not PEP, R2 would not trigger. Given the facts, NONCOMPLIANT.
- **TX-308:** If the amount decrease were actually an increase > 20%, R4 would invalidate the Enhanced_Review and R1 would require a new review. If amount at release were < 100k, R1 would not trigger. Given the facts, COMPLIANT.
- **TX-309:** If the 15:28 increase were  20%, the Enhanced_Review would remain valid and R1 would be satisfied. If a new Enhanced_Review occurred after 15:28 and before 15:35, the case would be COMPLIANT. Given the facts, NONCOMPLIANT.
- **TX-310:** If independent, non-interested evidence showed EX-88 approval existed before 10:00—e.g., a qualified signature timestamp before release, a system log, or an independent witness—the exemption would be valid and R1 satisfied  JUSTIFIED_EXCEPTION. If an Enhanced_Review had occurred before release, the case would be COMPLIANT. Given the facts, NONCOMPLIANT.
- **TX-311:** If the release jurisdiction were non-DE—e.g., if `Update_Jurisdiction` had not occurred or occurred after release—R1 would be triggered at release (amount 115k, non-DE). Because the jurisdiction change at 16:20 event_index 4 is after `Enhanced_Review` event_index 3, the Enhanced_Review would not be after the latest material change, so R1 would be violated unless a new Enhanced_Review occurred after 16:20. If event_index ordering were reversed (`Update_Jurisdiction` before `Enhanced_Review`), at review time jurisdiction would be DE, but release would still be DE, so R1 would not trigger. If amount < 100k, R1 would not trigger. Given the facts, COMPLIANT.

        (case_df['timestamp'] < rel_ts) |
        ((case_df['timestamp'] == rel_ts) & (case_df['event_index'] < rel_idx))
    )
    return case_df[mask]


def latest_event(prior_df, activity):
    sub = prior_df[prior_df['activity'] == activity]
    if sub.empty:
        return None
    sub = sub.sort_values(['timestamp', 'event_index'])
    return sub.iloc[-1]


release_rows = df[df['activity'] == 'Release_Funds'].copy()
results = []

for _, rel in release_rows.iterrows():
    case = rel['case']
    case_df = df[df['case'] == case]
    prior = prior_events(case_df, rel)

    std_rev = latest_event(prior, 'Standard_Review')
    enh_rev = latest_event(prior, 'Enhanced_Review')
    comp_app = latest_event(prior, 'Compliance_Approve')
    sanc_screen = latest_event(prior, 'Sanctions_Screen')
    sanc_update = latest_event(prior, 'Sanctions_List_Update')

    mat_changes = prior[prior['material_change']]
    latest_mat = (
        mat_changes.sort_values(['timestamp', 'event_index']).iloc[-1]
        if not mat_changes.empty else None
    )

    reviews = prior[prior['activity'].isin(['Standard_Review', 'Enhanced_Review'])]
    latest_review = (
        reviews.sort_values(['timestamp', 'event_index']).iloc[-1]
        if not reviews.empty else None
    )

    # R4: material amount change after latest review invalidates review for amount-dependent obligations
    r4_review_invalidated = False
    if latest_review is not None:
        mat_amount_after = prior[
            prior['material_amount_change'] &
            (prior['sort_key'] > latest_review['sort_key'])

    # State at release
    amount = rel['amount']
    risk = rel['risk_level']
    juris = rel['jurisdiction']
    cust = rel['customer_type']

    amount_unknown = pd.isna(amount)
    risk_unknown = pd.isna(risk)
    juris_unknown = pd.isna(juris)
    cust_unknown = pd.isna(cust)

    # R1
    if amount_unknown or juris_unknown:
        r1_triggered = None
    else:
        r1_triggered = (juris != 'DE') and (amount >= 100000)

    r1_enh_ok = False
    if enh_rev is not None:
        if latest_mat is None:
            r1_enh_ok = True
        else:
            r1_enh_ok = enh_rev['sort_key'] > latest_mat['sort_key']

    exemption_id = rel['exemption_id']
    r1_exemption_formal_ok = False
    r1_evidence_ok = False
    exemption_info = None
    exemption_displayed_approval = pd.NaT
    exemption_effective_from = pd.NaT
    exemption_expires = pd.NaT

    if pd.notna(exemption_id):
        ex_row = exemptions[exemptions['exemption_id'] == exemption_id]
        if not ex_row.empty:
            ex = ex_row.iloc[0]
            exemption_info = ex['evidence_quality']
            exemption_displayed_approval = ex['displayed_approval']
            exemption_effective_from = ex['effective_from']
            exemption_expires = ex['expires']

            formal_ok = (
                ex['approved_by'] == 'Head_Compliance' and
                ex['effective_from'] <= rel['timestamp'] and
                ex['expires'] >= rel['timestamp'] and
                not amount_unknown and ex['scope_amount_max'] >= amount and
                not juris_unknown and ex['scope_jurisdiction'] == juris and
                not cust_unknown and ex['scope_customer_type'] == cust
            )
            r1_exemption_formal_ok = formal_ok
            r1_evidence_ok = bool(ex['evidence_supports_timely_approval'])

    r1_exemption_ok = r1_exemption_formal_ok and r1_evidence_ok
    r1_satisfied = r1_enh_ok or r1_exemption_ok

    # R2
    if risk_unknown or cust_unknown:
        r2_triggered = None
    else:
        r2_triggered = (risk == 'HIGH') or (cust == 'PEP')

    if comp_app is not None and enh_rev is not None:

    else:

        update_juris = sanc_update['jurisdiction']

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage:** Control-flow conformance may use final case attributes to judge earlier events. In TX-311, the final jurisdiction is DE, but at `Enhanced_Review` time the jurisdiction was still US. In TX-309, the final amount is 145000, but the review at 15:25 was invalidated by the later material increase.
2. **Post-hoc exemptions:** Control-flow sees `Record_Exemption` after release and may treat the exemption as valid at release. In TX-310, EX-88 was recorded at 11:00 after release at 10:00, and the signing certificate was created at 10:30, after release. Control-flow cannot distinguish record time from approval time.
3. **Material changes after review:** Control-flow may see `Enhanced_Review` before release and pass, ignoring that amount increased > 20% after the review (TX-309) or after a `Standard_Review` (TX-301).
4. **Conditional activation:** Rules trigger only on data conditions—amount  100k, risk HIGH, PEP, jurisdiction non-DE, sanctions-list update. Control-flow conformance typically checks activity presence/order, not data-dependent activation. TX-303 R2 is triggered by risk HIGH; TX-304 R3 is triggered by a sanctions-list update.
5. **Missing data:** Control-flow may treat missing amount as zero or low-risk, leading to a false pass. In TX-305, the release amount is unknown; data-aware semantics require INDETERMINATE, not a silent default.
6. **Same-timestamp ordering:** Control-flow may not respect `event_index` tie-breakers. In TX-311, `Enhanced_Review` and `Update_Jurisdiction` share 16:20; event_index 3 precedes event_index 4. Without the tie-breaker, the state at review could be misreconstructed.
7. **Review type distinction:** `Standard_Review` is not `Enhanced_Review`. In TX-307, a `Standard_Review` and a `Compliance_Approve` of a standard packet do not satisfy R2’s `Enhanced_Review` requirement.
8. **Exemption scope and evidence quality:** Control-flow cannot evaluate whether an exemption’s jurisdiction, customer-type, and amount scope match the case, or whether approval evidence existed at the obligation trigger. TX-302 and TX-310 both have late database records, but only TX-302 has strong evidence of timely approval.
9. **Temporal validity of reviews:** R4 invalidates a review after a material amount change. Control-flow only sees that a review exists, not whether it remained valid.
10. **Late evidence vs. effective time:** `Record_Exemption` at 11:00 is not the same as approval at 09:05 (TX-302) or a certificate created at 10:30 (TX-310). Control-flow cannot represent these distinctions.

## 7. Recommended Logging and Control Improvements

- **Immutable release payloads:** Capture amount, jurisdiction, risk, and customer type at release with a cryptographic hash; prevent post-hoc alteration.
- **Effective/record/signature timestamps:** Separate `effective_time`, `record_time`, `signature_time`, and `certificate_creation_time` for exemptions and approvals.
- **Rule version:** Log the rule version applied at decision time, e.g., `R1 v2026.04`.
- **Exemption scope:** Store structured scope—jurisdiction, customer type, amount maximum, waived rules—and references to approval evidence.
- **Change provenance:** Log who/what changed each attribute, old value, new value, reason, and effective time.
- **Stable event ordering:** Include a monotonic `event_index` and timestamp with an explicit tie-breaker; avoid same-timestamp ambiguity by using sequence numbers.
- **Data quality flags:** Use explicit unknown/missing flags rather than blanks; avoid silent defaults.
- **Review type and scope:** Log review type (`Standard_Review` vs. `Enhanced_Review`), what was reviewed, and which obligations it covers.
- **Sanctions list versioning:** Log the sanctions-list version at screen time and at update time.
- **Compliance approval linkage:** Link `Compliance_Approve` to the specific `Enhanced_Review` and case attributes it approved.
- **Audit trail for late records:** Record insertion time, outage reason, and evidence of earlier approval.
