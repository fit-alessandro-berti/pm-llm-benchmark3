## 1. Analytical assumptions

**Case notion.** The choice of an object type whose instances become trace identifiers when the OCEL is flattened into a classical event log: every event directly related (E2O) to such an object is copied into its trace; events related to no instance of the type are dropped.

**Convergence.** An event related to several objects of the chosen type is replicated into each of their traces. Example: e16 (Dispatch) is related to O1, O2 and O3, so flattening on Order creates three copies of one physical truck departure. Convergence inflates event and edge frequencies and lets one real duration enter performance statistics multiple times.

**Divergence.** Within one trace, several instances of *another* object type each contribute their own occurrences of the same activity, producing repetitions that look like loops or rework. Example: O1 contains two items (I11, I12), so its trace holds Add Item twice (e05, e06), Pack Package twice (e11, e12), Dispatch twice (e15, e16) and Confirm Delivery twice (e23, e24) without any rework.

**Copied shared events: evidence, duplication, or both?** Both, depending on the question. From a single order's perspective, "my goods were dispatched at 11:05" (a copy of e16) is legitimate evidence with correct timing for that case. For aggregate statistics — activity counts, DFG edge frequencies, mean edge durations, workload — the copy is duplication and must be corrected or flagged. I treat copies as *evidence at trace level* and *duplication at log level*; every log-level metric gets a deduplicated companion metric.

**Permitted transformations.** I permit explicit, documented propagation through O2O links as an analytical variant — e.g., propagating `V2 bills O2/O3` down to items so item lifecycles gain financial milestones, or `P3 packs I21` so a package inherits its items' Add Item events. I never propagate silently: every propagated variant is compared against the direct-E2O variant (Section 7). I also permit down-weighting an event copy by 1/n (n = number of related case objects) in frequency statistics.

## 3. Concrete distortion analysis

1. **Cross-order package P3, Order flattening (required example 1).** Event e13 (Pack Package, O2+O3+I21+I31+P3) is copied into both O2's and O3's traces. The order log then shows 6 Pack Package occurrences (e11, e12, e13×2, e14×2) although only 4 physical packing operations happened. Any packing-station workload estimate from this log overstates effort by 50%. *Harmful* for frequency/workload analysis; *informative* at trace level (each order really was packed at that instant).

2. **Cross-order package P4 and O3's double-pack self-loop (required example 2).** O3's trace contains both e13 (10:12, P3) and e14 (10:20, P4), producing the DFG edge Pack Package→Pack Package with an 8-minute duration. A reader sees "repacking/rework within 8 minutes"; the truth is that O3's two items were split into two parcels that also carry other orders' goods. The same interleaving later yields Dispatch→Dispatch (e16→e17) in O3. *Context-dependent*: it correctly signals order splitting, but the loop semantics are wrong.

3. **Consolidated delivery D2 (required example).** e16 and e24 relate to three orders each (O1, O2, O3). On Order flattening, both are tripled, so D2's dispatch-to-confirm duration of 4h55 enters the Dispatch→Confirm performance statistic three times, while D1's 3h enters once. The frequency-weighted mean transit time is dragged toward the consolidated shipment; a bottleneck analysis would blame Dispatch→Confirm disproportionately on what is a single truck. *Harmful* for performance averages unless copies are down-weighted by 1/3.

4. **Consolidated invoice V2 (required example).** e19 (Issue Invoice, O2+O3+V2) is doubled on Order flattening, giving 4 Issue Invoice occurrences against 3 real invoices (V1, V2, V3). A finance dashboard fed from the order log would report the wrong invoice volume, and per-invoice averages (e.g., issue-to-settlement) would double-count V2's 21-hour settlement span. On the Invoice log the count is correct. *Harmful* on the Order log, *absent* on the Invoice log.

5. **Partial payments M2/M3 (required example).** On the Order flattening, O2's trace is Create (e02)→Add Item (e07)→Pack (e13)→Dispatch (e16)→Issue Invoice (e19)→Record Payment (e22)→Confirm Delivery (e24)→Record Payment (e25)→Close (e29). Two dangers: (a) Record Payment looks like a rework loop; (b) the apparent variant "pay, then receive delivery, then pay again" suggests a delivery-conditional payment policy, when in fact V2 was simply settled in two instalments (M2 partially_settles, M3 completes_settlement) whose timing is independent of D2. Only the Invoice flattening (V2: e19→e22→e25) states the instalment story plainly. *Context-dependent*: informative if you know the O2O qualifiers, misleading otherwise.

6. **Near-singleton lifecycles: Payment and Delivery (required example).** Flattening on Payment yields four traces of length 1 (M1={e21}, M2={e22}, M3={e25}, M4={e26}); the DFG has no edges and `discover_log_skeleton` would emit trivially satisfied constraints. Delivery is barely better: three traces of exactly Dispatch→Confirm Delivery. Any "process model" mined from these logs is vacuous, yet an unwary analyst might report "100% conformance, one variant" as a finding. *Harmful* if presented as process discovery; the underlying durations remain useful as KPIs.

7. **Lifecycle truncation on Item.** No item is related to Issue Invoice, Record Payment or Close Order events. I41's case runs 09:25 (e10) → next-day 10:00 (e27), while its order O4 runs 09:06 (e04) → next-day 11:10 (e31). An item-based cycle-time report understates end-to-end duration and completely misses that O4's payment (e26) arrived only 30 minutes before delivery confirmation. *Harmful* for end-to-end claims, *harmless* for logistics-only claims.

8. **Divergence self-loops in O1.** O1's trace contains e23 (Confirm Delivery, 14:00, D1) directly followed by e24 (Confirm Delivery, 16:00, D2). The DFG edge Confirm Delivery→Confirm Delivery with a 2-hour "duration" measures nothing operational — it is the gap between two independent shipments of a split order (P1 via D1, P2 via D2). Sojourn-time analysis of Confirm Delivery on the order log is polluted by such gaps. *Harmful* for activity-level performance; *informative* as a split-shipment indicator.

9. **Variant explosion on Order.** The four order traces have lengths 12 (O1), 9 (O2), 13 (O3) and 8 (O4) and four distinct activity sequences. With only four cases, every case is its own variant; frequency-based variant filtering would be meaningless, and a discovered model would either overfit (trace net) or over-generalise (flower-like). *Context-dependent*: with real data volumes, the pattern would persist proportionally.

10. **Item log's deceptive uniformity.** All six items share the single variant Add Item→Pack Package→Dispatch→Confirm Delivery. This "perfectly structured process" conceals that I31 and I32 (same order O3) travelled in different packages (P3, P4) and different deliveries (D2, D3) with confirmation times 16:00 vs next-day 10:00 — an 18-hour intra-order spread invisible in any single item trace. *Harmful* if uniformity is reported as process health.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs worth creating.**
- **Order log** — the only view containing all eight activities; use it for order-level cycle time (e.g., O4: e04→e31), order-level conformance to the intended macro-sequence, and per-order SLA reporting. Every aggregate statistic must ship with the 1/n-down-weighted variant (9 of 40 event copies are duplicates).
- **Item log** — safe for logistics conformance ("every added item was packed, dispatched, confirmed") and per-item transit analysis.
- **Invoice log** — safe and undistorted for billing/settlement analysis; it is the *only* flattening in which V2's instalments (e19, e22, e25) appear with correct multiplicity and no copies.
- **Delivery "log"** — keep only as a two-column KPI table (dispatch time, confirm time per D1–D3), not as a process-mining input.
- **Payment log** — do not create; attach M1–M4 as attributes of Record Payment events instead.

**Questions requiring object-centric artefacts.**
- "Which orders share physical resources?" needs the **object interaction summary** / **OTG**: the O2O edges P3–{I21, I31}, P4–{I32, I41}, D2–{P2, P3}, V2–{O2, O3} are exactly the facts every flattening either hides or duplicates.
- "How many *physical* dispatches occurred and how long did each take?" needs the **OC-DFG** with event-based (not object-based) frequency annotations, so e16 counts once.
- "Which activities touch which object types?" needs the **ET–OT graph** — it exposes immediately that Payment participates in one activity and Delivery in two, disqualifying them as case notions before any log is built.
- "Are there structurally equivalent executions?" needs **equivalent-execution clustering**: O1 (split order, two parcels, two deliveries) vs O2 (single item, shared parcel, shared invoice) vs O4 (single item, shared parcel, own invoice) form distinct interaction shapes that trace variants alone do not capture.

**Reconciling contradictions.** When a flattened metric and an OC metric disagree (e.g., order log: 6 Pack Package events; OC-DFG: 4), the OC number is authoritative for *counting physical work*, and the flattened number is authoritative for *per-case experience* ("how many packing touchpoints did this order have?"). The reconciliation rule is: report both, label them "process instances" vs "case touchpoints," and never let a copied event contribute more than 1/n to any cross-case aggregate.

## 5. Lead-object decision

**Position B: Order as primary lead object, with Invoice and Item as explicitly secondary lifecycles, and the OC-DFG as the arbitration layer.**

- **Decision criteria.** (1) Activity coverage: the lead type should touch as many activities as possible. (2) Business alignment: cases should match the unit customers and management reason about. (3) Bounded, correctable convergence: duplication must be quantifiable. (4) No silent loss of a critical sub-process.

- **Strongest supporting evidence.** Order is the only type related to all eight activities — Item stops at Confirm Delivery, Invoice starts at Issue Invoice, Package/Delivery/Payment cover 3, 2 and 1 activities respectively. Every event in the log (e01–e31) is directly related to at least one order, so the Order flattening loses no events, only adds copies, and the copy count is exactly known (9 of 40). Criteria 1, 2 and 3 are all satisfied by Order and by nothing else.

- **Strongest counterargument.** The Order log misrepresents precisely the phenomena that make this snapshot interesting: consolidation (e13, e14, e16, e19 all become "private" per-order events), instalments (e22/e25 look like rework), and split shipments (O1's self-loops). One could argue this disqualifies any single lead — position C — because the process's essence *is* the many-to-many structure.

- **Why B rather than C.** Rejecting a lead object entirely leaves no vehicle for the questions stakeholders actually ask (order cycle time, order SLA, order conformance). The distortions are enumerable and mechanically correctable (down-weighting, deduplication, O2O annotation), whereas the absence of any case-level view is not correctable. The secondary Invoice lifecycle covers the one sub-process (instalment settlement of V2) the Order view garbles; the secondary Item lifecycle provides the clean logistics conformance check.

- **Residual risk.** Analysts consuming only the Order log will still misread Pack→Pack (O3) and Record Payment loops (O2, O3) as rework; consolidated-delivery durations remain over-weighted in any statistic that escapes the down-weighting discipline. With only four orders, every trace is a unique variant, so variant-based communication is fragile.

- **Conditions for changing the decision.** I would move to position C (no lead object; OC-first analysis) if consolidation intensified — e.g., if most packages routinely packed 3+ orders or deliveries carried most of the order book, making the copy ratio dominate the log. I would move to position A (Item alone) if the analysis scope were formally narrowed to warehouse logistics, where Item's zero-divergence, uniform lifecycle is ideal and the missing financial events are out of scope.

## 6. PM4Py analysis outline

```python
import pm4py
import pandas as pd

# --- 0. Global inspection: what is in the OCEL at all ---
print(ocel)

activity_counts = ocel.events["ocel:activity"].value_counts()
object_type_counts = ocel.objects["ocel:type"].value_counts()
print(activity_counts)
print(object_type_counts)

# ET-OT view: which activity touches which object type.
# This alone disqualifies Payment (1 activity) and Delivery (2) as case notions.
etot_graph = pm4py.discover_etot(ocel)

# Object-type interaction structure (P3-{I21,I31}, D2-{P2,P3}, V2-{O2,O3} ...)
otg_graph = pm4py.discover_otg(ocel)
interactions_summary = pm4py.ocel_objects_interactions_summary(ocel)

# --- 1. Reference model: object-centric DFG (authoritative for counts) ---
ocdfg = pm4py.discover_ocdfg(ocel)
# NOTE: ocdfg carries event-, unique-object- and total-object-based
# frequency annotations; Section 7 compares them explicitly. Visual
# inspection of ocdfg does NOT settle convergence/divergence semantics;
# the numeric comparisons below do.

# --- 2. Flattenings under comparison ---
flat_logs = {}
for ot in ["order", "item", "package", "delivery", "invoice", "payment"]:
    flat_logs[ot] = pm4py.ocel_flattening(ocel, ot)

# Quantify convergence-induced duplication per flattening:
duplication_report = {
    ot: {
        "copies": len(df),
        "distinct_events": df["ocel:eid"].nunique()
        if "ocel:eid" in df.columns else None,
    }
    for ot, df in flat_logs.items()
}
print(duplication_report)  # expect order: 40/31, item: 24/16, package: 12/10

# --- 3. Classical discovery on the primary (Order) and secondary logs ---
order_dfg, order_start, order_end = pm4py.discover_dfg(flat_logs["order"])
invoice_dfg, invoice_start, invoice_end = pm4py.discover_dfg(flat_logs["invoice"])
item_dfg, item_start, item_end = pm4py.discover_dfg(flat_logs["item"])

# Inspect the artifact edges predicted analytically:
suspect_edges = [("Pack Package", "Pack Package"),
                 ("Confirm Delivery", "Confirm Delivery"),
                 ("Record Payment", "Record Payment"),
                 ("Confirm Delivery", "Record Payment")]
order_artifacts = {e: order_dfg.get(e, 0) for e in suspect_edges}
print(order_artifacts)

# Declarative view on the Order log: with 4 traces / 4 variants an
# imperative model is unreliable; the skeleton's constraints are safer.
order_skeleton = pm4py.discover_log_skeleton(
    flat_logs["order"], noise_threshold=0.0)

# --- 4. Equivalent-execution clustering ---
# Justified by the Section-5 decision: with Order as lead object, we need
# to know whether order-centric executions share interaction structure
# (O1 split-shipment vs O2/O3 consolidated vs O4 own-invoice shapes).
order_execution_clusters = pm4py.cluster_equivalent_ocel(ocel, "order")
print({k: len(v) for k, v in order_execution_clusters.items()})
```

## 7. Sensitivity and validation plan

1. **Down-weighting copied shared events.** Recompute all activity and DFG-edge frequencies on the Order log with each event copy weighted 1/n (n = number of related orders): e16 and e24 at 1/3; e13, e14, e19, e22, e25 at 1/2. Validation target: weighted Pack Package frequency must return to 4, Issue Invoice to 3, Dispatch to 3, matching the OC-DFG event counts. Any metric that shifts by more than ~20% between raw and weighted versions is flagged as convergence-sensitive and must not be reported from the flattened log alone.

2. **Direct E2O versus propagated relations.** Build a propagated variant in which invoice and payment events are pushed through O2O links onto items (V2→O2/O3→I21/I31/I32) and item events onto packages. Compare item-log lifecycles before (4 activities, ending at Confirm Delivery) and after (financial tail included). If conclusions about "item cycle time" change materially — they will, since I41's case would extend from next-day 10:00 to 11:10 and gain Record Payment — then any report using the item view must state which relation regime it used.

3. **Lead-object swap.** Re-run the Section-6 pipeline with Item, then Invoice, as the lead object, and diff three findings: (a) number of Record Payment loops (Order: 2 apparent; Invoice: 1 real, on V2), (b) Pack Package volume (Order: 6; Item: 6; OC ground truth: 4), (c) end-to-end duration distribution. Persistent findings across leads (e.g., D3's long transit e17→e27) are robust; findings that appear only under one lead (e.g., "payment rework") are artifacts of that case notion and are quarantined.

4. **Frequency-annotation comparison in the OC-DFG.** For each OC-DFG node and edge, compare event count, unique-object count, and total-object count. Dispatch should show 3 events but 9 order-object participations (O1×2 via e15/e16, O2×1, O3×2, O4×1 — 6 order participations — plus package/delivery participations depending on the annotation set); large gaps between event count and object count localise exactly where convergence lives (e16, e24) without inspecting raw data. Nodes where all three counts agree (Issue Invoice per invoice, Dispatch per delivery) are safe for classical reporting.

5. **Degenerate-lifecycle guard.** Recompute the log skeleton and DFG after excluding Delivery and Payment as candidate case notions and verify that no analysis deliverable silently depends on their flattened logs; the Payment log's four single-event traces (e21, e22, e25, e26) must never feed a discovery algorithm, only KPI tables.
