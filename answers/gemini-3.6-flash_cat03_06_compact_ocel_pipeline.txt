## 1. Modeling assumptions

### Object Types and Capitalization
We define six primary object types, using TitleCase convention:
- **`Order`**: Represents top-level customer orders (`O100`, `O200`).
- **`Item`**: Represents individual ordered product line items (`I1`, `I2`, `I3`).
- **`Package`**: Represents physical shipping containers (`P1`, `P2`).
- **`Delivery`**: Represents outbound transport executions (`D1`, `D2`).
- **`Invoice`**: Represents financial billing documents (`V1`).
- **`Payment`**: Represents financial payment transactions (`M1`, `M2`).

### E2O Qualifier Vocabulary
Event-to-Object (E2O) relations use explicit, functional qualifiers to indicate the exact role an object plays in an event:
- **`target`**: The primary object created, modified, or closed by the event (e.g., creating `O100`, closing `O200`).
- **`parent_order`**: Links item-level events (e.g., `Add Item`) back to the owning order.
- **`item`**: An `Item` object being reserved or packed during an operation.
- **`package`**: A `Package` object being packed or dispatched.
- **`delivery`**: A `Delivery` object carrying packages or receiving confirmation.
- **`invoice`**: An `Invoice` object being issued or paid against.
- **`payment`**: A `Payment` object being recorded.
- **`billed_order`**: An `Order` associated with an invoice creation event.
- **`related_order`**: An `Order` directly referenced in joint operations (e.g., stock reservation, packing).

### O2O Direction Conventions
Object-to-Object (O2O) relationships represent static or structural links, directed from parent/container to child/component:
- **`contains`** (`Order` $\rightarrow$ `Item`): `O100` $\rightarrow$ `I1`, `O100` $\rightarrow$ `I2`, `O200` $\rightarrow$ `I3`.
- **`contains`** (`Package` $\rightarrow$ `Item`): `P1` $\rightarrow$ `I1`, `P1` $\rightarrow$ `I3`, `P2` $\rightarrow$ `I2`.
- **`carries`** (`Delivery` $\rightarrow$ `Package`): `D1` $\rightarrow$ `P1`, `D2` $\rightarrow$ `P2`.
- **`bills`** (`Invoice` $\rightarrow$ `Order`): `V1` $\rightarrow$ `O100`, `V1` $\rightarrow$ `O200`.
- **`partially_settles`** / **`completes_settlement`** (`Payment` $\rightarrow$ `Invoice`): `M1` $\rightarrow$ `V1` (`partially_settles`), `M2` $\rightarrow$ `V1` (`completes_settlement`).

### Logistics and Financial Event Association Strategy
In this dataset:
- **Direct Source Relations**: Logistics events (`Pack Package`, `Dispatch Package`, `Confirm Delivery`) connect directly to their operational objects (`Package`, `Delivery`, and participating `Item` objects). Financial events (`Record Payment`) connect directly to `Payment` and `Invoice`.
- **Operational Direct Relations**: Shared operational events like `Reserve Stock` and `Pack Package P1` explicitly reference both affected `Item` objects (`I1`, `I3`) and their respective parent `Order` objects (`O100`, `O200`) because both orders actively participated in the stock allocation and packing batch.
- **Analytical Relation Propagation**: Indirect dependencies (e.g., linking `Confirm Delivery D1` back to `O100` and `O200`) are deferred to graph/O2O traversal during analysis rather than hardcoded into E2O relations. This separation prevents artificial event duplication during flattening and ensures that process mining metrics (such as throughput time and handover frequencies) accurately reflect physical reality.

### PM4Py Version-Dependent Assumptions
- PM4Py versions $\ge 2.3.0$ / $2.7.x$ support the OCEL 2.0 object-centric data model.
- We import `OCEL` from `pm4py.objects.ocel.obj` (or instantiate via PM4Py internal representation). If a specific environment uses `from pm4py.objects.ocel.ocel import OCEL`, the instantiation line `ocel = OCEL(events=..., objects=..., relations=..., o2o=...)` remains identical.
- Event attributes (e.g., payment amounts) reside in the `events` DataFrame.

| **`completes_settlement`** | `Payment` $\rightarrow$ `Invoice` | `M2`$\rightarrow$`V1` | N-to-1 ($* \dots 1$) |

### Critical Events for Convergence and Divergence
1. **`Reserve Stock` (`e6`) & `Pack Package` (`e7`) — Convergence/Divergence Point**:
   `e6` and `e7` bind items from two separate orders (`I1` from `O100` and `I3` from `O200`) into a shared batch operation and container (`P1`). This creates structural convergence (multiple items merged into one package event) and cross-order interaction divergence during trace flattening.
2. **`Issue Invoice` (`e11`) — Financial Synchronization Point**:
   `e11` binds two orders (`O100` and `O200`) to a single invoice (`V1`). It is the financial convergence point, causing subsequent payment events (`e12`, `e15`) to radiate across both order processes.

## 4. Expected flattened behavior

### Order Flattening (`Order`)
- **Approximate Trace Shape**: 2 traces (`O100`, `O200`).
  - Trace `O100`: `Create Order` $\rightarrow$ `Add Item` (x2) $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package` (x2) $\rightarrow$ `Issue Invoice` $\rightarrow$ `Close Order`.
  - Trace `O200`: `Create Order` $\rightarrow$ `Add Item` $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package` $\rightarrow$ `Issue Invoice` $\rightarrow$ `Close Order`.
- **Copied Shared Events**: `e6` (`Reserve Stock`), `e7` (`Pack Package`), and `e11` (`Issue Invoice`) appear in both `O100` and `O200` traces.
- **Omitted Lifecycle Aspects**: Granular package dispatch timestamps (`e9`, `e10`) and delivery confirmations (`e13`, `e14`) are missing if not directly linked to orders, as well as individual payment execution timestamps (`e12`, `e15`).
- **Likely DFG Edges**: `Create Order` $\rightarrow$ `Add Item` $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package` $\rightarrow$ `Issue Invoice` $\rightarrow$ `Close Order`.
- **Misleading Interpretations**: Appears as if `O100` and `O200` independently executed reservation and invoicing, hiding the fact that `V1` was a shared invoice and `P1` was a consolidated package.

### Package Flattening (`Package`)
- **Approximate Trace Shape**: 2 traces (`P1`, `P2`).
  - Trace `P1`: `Pack Package` $\rightarrow$ `Dispatch Package`.
  - Trace `P2`: `Pack Package` $\rightarrow$ `Dispatch Package`.
- **Copied Shared Events**: None across packages, as `P1` and `P2` are distinct.
- **Omitted Lifecycle Aspects**: Order creation, item addition, stock reservation (if E2O on `e6` lacks package reference), invoicing, payments, and final order closure.
- **Likely DFG Edges**: `Pack Package` $\rightarrow$ `Dispatch Package`.
- **Misleading Interpretations**: Presents shipping execution as isolated from order readiness, concealing item-level backorders or billing dependencies.

### Delivery Flattening (`Delivery`)
- **Approximate Trace Shape**: 2 traces (`D1`, `D2`).
  - Trace `D1`: `Dispatch Package` $\rightarrow$ `Confirm Delivery`.
  - Trace `D2`: `Dispatch Package` $\rightarrow$ `Confirm Delivery`.
- **Copied Shared Events**: None between `D1` and `D2`.
- **Omitted Lifecycle Aspects**: Entire upstream order capture, item packing, and downstream payment processes.
- **Likely DFG Edges**: `Dispatch Package` $\rightarrow$ `Confirm Delivery`.
- **Misleading Interpretations**: Evaluates logistics purely as a standalone transport loop, hiding customer-facing order delivery lead times.

### Invoice Flattening (`Invoice`)
- **Approximate Trace Shape**: 1 trace (`V1`).
  - Trace `V1`: `Issue Invoice` $\rightarrow$ `Record Payment` (M1) $\rightarrow$ `Record Payment` (M2).
- **Copied Shared Events**: None (only one invoice present).
- **Omitted Lifecycle Aspects**: Item-level picking, packing, dispatching, and physical delivery confirmations.
- **Likely DFG Edges**: `Issue Invoice` $\rightarrow$ `Record Payment` $\rightarrow$ `Record Payment`.
- **Misleading Interpretations**: Distorts payment velocity by presenting payments in isolation from whether the physical goods were actually delivered.

### Why Flattening on `Payment` is Weak
Flattening on `Payment` yields two micro-traces (`M1` and `M2`), each containing a single event `Record Payment`. Payment objects possess no sequential lifecycle of their own in this system; they are discrete point-in-time transactions. Flattening on `Payment` completely loses process context, providing zero insights into workflow routing or cycle times.

## 5. Expected object-centric structures

### OC-DFG (Object-Centric Directly-Follows Graph)
- **Nodes**: Activities color-coded or annotated with object type involvement.
- **Edges**:
  - `Order`: `Create Order` $\rightarrow$ `Add Item` $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package` $\rightarrow$ `Issue Invoice` $\rightarrow$ `Close Order`.
  - `Item`: `Add Item` $\rightarrow$ `Reserve Stock` $\rightarrow$ `Pack Package`.
  - `Package`: `Pack Package` $\rightarrow$ `Dispatch Package`.
  - `Delivery`: `Dispatch Package` $\rightarrow$ `Confirm Delivery`.
  - `Invoice`: `Issue Invoice` $\rightarrow$ `Record Payment`.
  - `Payment`: Self-contained at `Record Payment`.
- **Explicit Object Insights**: Discloses that `Pack Package` bridges `Item`, `Package`, and `Order`, showing that physical consolidation occurs prior to dispatch.

### OTG (Object Type Graph)
- Displays structural coupling between object types based on shared event occurrences:
  - `Order` $\longleftrightarrow$ `Item` (via `Add Item`, `Reserve Stock`, `Pack Package`)
  - `Order` $\longleftrightarrow$ `Package` (via `Pack Package`)
  - `Order` $\longleftrightarrow$ `Invoice` (via `Issue Invoice`)
  - `Package` $\longleftrightarrow$ `Item` (via `Pack Package`)
  - `Package` $\longleftrightarrow$ `Delivery` (via `Dispatch Package`)
  - `Invoice` $\longleftrightarrow$ `Payment` (via `Record Payment`)

### ET–OT Graph (Event Type – Object Type Graph)
- Bipartite graph mapping event types to object types:
  - `Reserve Stock` connects to `Item` and `Order`.
  - `Pack Package` connects to `Package`, `Item`, and `Order`.
  - `Dispatch Package` connects to `Delivery` and `Package`.
  - `Issue Invoice` connects to `Invoice` and `Order`.
  - `Record Payment` connects to `Payment` and `Invoice`.

### Object-Centric Petri Net
- Synchronizes multiple Petri net sub-nets (one per object type) through shared transitions:
  - Transition `Pack Package` acts as a synchronizing transition requiring tokens from `Item` places, `Order` places, and producing a token in `Package` places.
  - Transition `Issue Invoice` synchronizes `Order` sub-nets with the `Invoice` sub-net.
  - Correctly models concurrent execution: `Confirm Delivery D1` and `Confirm Delivery D2` can fire independently or in parallel without blocking invoice payments.

### Object-Interactions Summary

## 6. Modeling alternatives

### Alternative 1: Source-Minimal E2O Policy
- **Description**: Events are linked **strictly** to the primary target object recorded in the underlying relational database table (e.g., `Add Item` $\rightarrow$ `Item` only; `Pack Package` $\rightarrow$ `Package` only; `Issue Invoice` $\rightarrow$ `Invoice` only).
- **Impact on Discovery**:
  - Removes `Order` from `Pack Package` and `Issue Invoice`.
  - Simplifies the OC-DFG and Petri net by eliminating cross-type transition synchronization.
  - **Trade-off**: Requires process miners to rely heavily on O2O query traversals to reconstruct end-to-end order flows; flattening on `Order` loses packing and invoicing events unless explicit O2O expansion is enabled during flattening.

### Alternative 2: Full Operational Involvement Policy
- **Description**: Every event is explicitly linked to **all** objects remotely touched by the operation via E2O relations (e.g., `Confirm Delivery D1` is given explicit E2O links to `D1`, `P1`, `I1`, `I3`, `O100`, `O200`).
- **Impact on Discovery**:
  - Ensures flattening on `Order` includes every downstream physical logistics event.
  - **Trade-off**: Causes severe event inflation and artificial loop duplications in discovery algorithms. A single delivery confirmation appears as multiple identical events across order process maps, masking true resource bottlenecks.

### Alternative 3: O2O-Propagated Analytical Relations Policy
- **Description**: Raw E2O tables maintain minimal source truths, but prior to process discovery, an automated graph traversal algorithm expands E2O links dynamically along active O2O paths (e.g., `Delivery` $\xrightarrow{carries}$ `Package` $\xrightarrow{contains}$ `Item` $\xrightarrow{contained\_in}$ `Order`).
- **Impact on Discovery**:
  - Keeps source data clean while providing full configuration flexibility during analysis.
  - Allows the analyst to toggle the depth of relational propagation (e.g., propagate up to 1 hop vs full structural closure) depending on whether they are analyzing logistics bottlenecks or financial settlement latency.

## 7. Failure modes

1. **Relation Inflation**: Hardcoding transitive E2O links (e.g., attaching `D1`, `P1`, `I1`, `I3`, `O100`, `O200` to `Confirm Delivery`) causes event duplication in flattened logs, inflating event counts and warping frequency metrics.
2. **Missing Direct E2O Links**: Omitting direct operational references (e.g., omitting `Item` from `Reserve Stock`) forces process discovery to see `Reserve Stock` as an unattached order event, hiding item-level stock shortages.
3. **Treating O2O Propagation as Raw Observation**: Mistaking synthetically derived/propagated E2O relations for raw source database facts leads to false audit claims about which business entity executed a specific transaction.
4. **Duplicate Shared Events After Flattening**: Flattening an OCEL on a high-level entity (`Order`) when events are shared across entities causes multi-counting of timestamps and cycle times in conventional PM4Py algorithms.
5. **Ambiguous Payment Allocation**: Linking `M1` (100 units) and `M2` (150 units) to `V1` without item-level or order-level lines leaves it mathematically indeterminate how payment coverage is split between `O100` and `O200` without extra attribute modeling.
6. **Overly Short Payment Traces**: Flattening on short-lived transaction objects (`Payment`) creates trivial 1-event traces, making sequential pattern discovery impossible for that object type.
7. **Constructor/API Version Mismatch**: Passing OCEL 1.0 JSON/XML structures or mismatched DataFrame column names (e.g. `ocel:oid2` instead of `ocel:oid_2`) to PM4Py OCEL 2.0 constructors raises runtime `KeyError` or schema validation exceptions.
8. **False Total Order for Same-Time Events**: In datasets with identical timestamps across distinct events, naive sorting creates deterministic total orderings that do not reflect true concurrent execution. (While this dataset uses distinct timestamps, process engines must handle timestamp ties via explicit event tie-breaker keys).
