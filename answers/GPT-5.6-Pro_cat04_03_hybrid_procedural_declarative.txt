# 1. Policy Interpretation and Conflict Resolution

The hybrid model below treats the stable backbone as lifecycle behavior, R1–R11 as policy constraints with different semantic needs, and R12 as a warning-oriented performance norm. It does not infer emergency authorization or other missing facts from the activity sequence. 

## Material assumptions

| ID  | Assumption                                                                                                                                                                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A1  | T1–T8 are complete traces because each contains `Close Onboarding`. For live, incomplete cases, an outstanding response obligation is **pending**, not yet a failure.                                                                                                                                                                |
| A2  | `Activate Vendor` and `Reject Vendor` are the “final outcomes” referenced by R3. `Release First Payment` and `Close Onboarding` are later lifecycle events, not alternative primary outcomes.                                                                                                                                        |
| A3  | A clarification can be requested at any point after `Receive Onboarding Request` and before the primary outcome. A pending clarification does not stop checks, classification, or approvals, because R3 only prohibits another request and a final outcome.                                                                          |
| A4  | `Receive Clarification` is not unsolicited: it closes one preceding `Request Clarification`. This supports one-for-one clarification cycles in the procedural and Log-Skeleton layers.                                                                                                                                               |
| A5  | At most one sanctions escalation is unresolved at a time. A further `Sanctions Escalation` is permitted after the previous one has received an `Obtain Legal Opinion`. This is necessary because the log has no escalation/opinion correlation identifier.                                                                           |
| A6  | `Obtain Legal Opinion` is treated as sanctions-escalation-related. An independent legal opinion for another purpose would require an additional event attribute or a separate activity label.                                                                                                                                        |
| A7  | For R9, the applicable bank verification is every `Verify Bank Account` event before the applicable approval. A post-approval re-verification caused by R11 is not compared retrospectively with the earlier approver.                                                                                                               |
| A8  | Resource equality is exact equality of `org:resource`. Shared accounts, aliases, changed employee identifiers, or delegation are data-quality issues rather than acceptable evidence of segregation.                                                                                                                                 |
| A9  | The procedural interpretation of R11 is deliberately stronger than bare eventuality: after activation, each visible bank-change cycle is `Change Bank Details → Suspend Vendor → Verify Bank Account`, after which payment may occur. No other post-change activities are specified, so this is a transparent conservative ordering. |
| A10 | `Close Onboarding` occurs exactly once and no business event occurs after it.                                                                                                                                                                                                                                                        |
| A11 | All time rules use elapsed time. No business calendar, working-hours calendar, or pause semantics is supplied.                                                                                                                                                                                                                       |
| A12 | When events have equal timestamps, a stable event-order attribute is required. Timestamp order alone would otherwise be insufficient to decide precedence.                                                                                                                                                                           |
| A13 | The `support` and `confidence` values in the DECLARE dictionary are normative configuration metadata. They are not estimated from the eight examples and do not prove that a rule is correct.                                                                                                                                        |
| A14 | The implemented procedural model uses strict R5. Missing emergency evidence does not create an inferred emergency exception.                                                                                                                                                                                                         |

## Two defensible resolutions of R5/R6

**Resolution A — strict legal precedence.** R5 is the operative hard policy. If a sanctions escalation exists, the opinion must occur before activation. R6 is treated as an unimplemented operational proposal because the log cannot prove either emergency status or joint authorization. Under this resolution, T6 is noncompliant at `Activate Vendor@13`.

**Resolution B — guarded emergency exception.** R5 is the default, but R6 overrides it when all of the following are present:

1. `emergency_authorized = True`;
2. authorization occurred no later than activation;
3. separate legal and operations authorizer identities are recorded;
4. the legal opinion occurs no more than 24 elapsed hours after activation; and
5. the opinion can be associated with the unresolved escalation.

Without those attributes, the activity sequence is `policy-dependent`; it cannot be certified as an emergency exception.

A third possible implementation would version the policies by business unit, jurisdiction, or effective date, for example `policy_version="strict-R5"` versus `policy_version="R6-enabled"`. That avoids pretending the two statements apply simultaneously to every case.

## Implemented choice and its risk

`procedural_model` implements **Resolution A, strict R5**. This can produce false-positive violations for genuinely authorized emergencies such as T6. The alternative would be more operationally permissive but would create a serious false-negative risk: any activation-before-opinion trace could be described after the fact as an emergency even though the event log contains no evidence of authorization. The strict choice therefore favors auditability until emergency evidence is instrumented.

# 3. Procedural Backbone

## Compact formal description

Using `;` for sequence, `∧` for concurrency, `⊕` for exclusive choice, and `*` for repetition:

```text
Receive Onboarding Request ;
(
    Capture Master Data
    ∧ Run Sanctions Screening
    ∧ Verify Bank Account
) ;
Classify Risk ;
(
      Reject Vendor
  ⊕   Manager Approval ; Activate Vendor
  ⊕   Enhanced Due Diligence ; Compliance Approval ; Activate Vendor
)

Accepted suffix:
    (Change Bank Details ; Suspend Vendor ; Verify Bank Account)* ;
    Release First Payment ;
    Close Onboarding

Rejected suffix:
    Reject Vendor ;
    (Obtain Legal Opinion if an escalation is still pending) ;
    Close Onboarding
```

Two independent state monitors are composed with that lifecycle:

* **Clarification state:** `ready` or `pending`. A request moves to `pending`; receipt returns to `ready`; activation and rejection require `ready`.
* **Sanctions state:** `not escalated`, `opinion pending`, or `opinion done`. Screening creates this state; escalation moves it to pending; legal opinion resolves it. Under strict R5, activation is disabled in the pending state.

## Modeling explanation

The AND split and join express genuine independence of the three initial checks. A sequential event log will show an interleaving of these transitions, but that interleaving does not imply that one check causally enables another.

The three silent transitions after `Classify Risk` implement the primary XOR. This makes R1 and the conditional approval structure of R2 structural properties rather than after-the-fact filters.

The clarification monitor is intentionally independent of the lifecycle token. Therefore T5 can perform `Classify Risk` and `Manager Approval` while clarification is pending, but `Activate Vendor` is disabled. This follows the exact wording of R3 rather than adding an unsupported “all work stops” assumption.

The sanctions monitor is also independent. `Sanctions Escalation` becomes enabled only after `Run Sanctions Screening`, satisfying R7. Due diligence and approval can continue while an opinion is pending, but strict activation cannot occur. This is why T6 first becomes procedurally invalid at `Activate Vendor@13`, not at `Enhanced Due Diligence` or `Compliance Approval`.

The post-activation bank-change loop is included because it affects whether payment is enabled. The same visible label `Verify Bank Account` appears on two distinct transitions: the initial parallel check and the post-change re-verification. That distinction is available in Petri-net state but lost in a flat activity-only DECLARE or Log-Skeleton relation.

The net deliberately excludes resource identities, emergency authorization, the emergency 24-hour guard, and statistical duration thresholds. Those belong to other layers.

PM4Py’s alternate-response semantics require each source occurrence to have a target occurrence after it and before the next source occurrence; the constraint is vacuously satisfied when the source never occurs. Its response, precedence, and non-succession checks use the tuple’s first activity as the source or required predecessor. ([GitHub][1])

| Template         | Encoded rule                                          | Direction and meaning                                                                                                                               |
| ---------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `init`           | `Receive Onboarding Request`                          | The first visible activity must be `Receive Onboarding Request`.                                                                                    |
| `noncoexistence` | `("Reject Vendor", "Activate Vendor")`                | The two labels may not both occur, in either order. This is R1.                                                                                     |
| `noncoexistence` | `("Manager Approval", "Compliance Approval")`         | The approval types may not both occur.                                                                                                              |
| `noncoexistence` | `("Enhanced Due Diligence", "Manager Approval")`      | A case containing EDD may not also contain manager approval.                                                                                        |
| `noncoexistence` | `("Reject Vendor", "Manager Approval")`               | A rejected case may not contain manager approval.                                                                                                   |
| `noncoexistence` | `("Reject Vendor", "Compliance Approval")`            | A rejected case may not contain compliance approval.                                                                                                |
| `altresponse`    | `("Request Clarification", "Receive Clarification")`  | Every request must receive a later response before another request. The response need not be the immediately next event.                            |
| `response`       | `("Sanctions Escalation", "Obtain Legal Opinion")`    | Escalation creates a future legal-opinion obligation. Opinion may occur without this rule requiring escalation first.                               |
| `response`       | `("Manager Approval", "Activate Vendor")`             | Manager approval creates a future activation obligation. It does not say every activation must have manager approval.                               |
| `response`       | `("Compliance Approval", "Activate Vendor")`          | Compliance approval creates a future activation obligation. It does not say every activation must have compliance approval.                         |
| `response`       | `("Reject Vendor", "Close Onboarding")`               | Rejection must eventually be followed by closure.                                                                                                   |
| `response`       | `("Release First Payment", "Close Onboarding")`       | Payment release must eventually be followed by closure.                                                                                             |
| `response`       | `("Change Bank Details", "Suspend Vendor")`           | Every bank-details change creates a future suspension obligation.                                                                                   |
| `response`       | `("Change Bank Details", "Verify Bank Account")`      | Every bank-details change requires a later verification. Because the label is reused, this does not alone enforce that verification before payment. |
| `precedence`     | `("Run Sanctions Screening", "Sanctions Escalation")` | If escalation occurs, screening must already have occurred. The tuple is `(required predecessor, constrained activity)`.                            |
| `succession`     | `("Enhanced Due Diligence", "Compliance Approval")`   | Combines response and precedence: EDD requires later compliance approval, and compliance approval requires earlier EDD.                             |
| `succession`     | `("Activate Vendor", "Release First Payment")`        | Activation and first payment must either both be absent or occur in that order. Occurrence limits remain the Log Skeleton’s responsibility.         |
| `nonsuccession`  | `("Activate Vendor", "Obtain Legal Opinion")`         | The two may coexist only when the opinion is before activation. Unlike noncoexistence, it does not ban both labels in every order.                  |

A normal `response(A, B)` permits unrelated activities between A and B. A `chainresponse(A, B)` would require B to be the immediately next event, so chain response is deliberately not used for clarification, legal opinion, suspension, or closure.

`precedence(A, B)` constrains B but creates no future obligation when A occurs. `response(A, B)` creates a future obligation when A occurs but does not require A before every B. `succession` combines both directions.

The DECLARE model is intentionally incomplete with respect to R2. Adding both `precedence(Manager Approval, Activate Vendor)` and `precedence(Compliance Approval, Activate Vendor)` would incorrectly require both approvals. The procedural XOR remains authoritative.

```python
        "Manager Approval": {0, 1},
        "Compliance Approval": {0, 1},

        "Reject Vendor": {0, 1},
        "Activate Vendor": {0, 1},
        "Release First Payment": {0, 1},

        "Close Onboarding": {1},
    },

    "directly_follows": set(),
}
```

For PM4Py Log Skeletons, `(A, B)` in `always_before` means that if A occurs, B must have occurred previously; `(A, B)` in `always_after` means that A requires B later. `equivalence` compares occurrence counts, `never_together` is symmetric mutual exclusion, and `activ_freq` provides allowed count sets. ([GitHub][2])

## Pair orientations

| Relation           | Pair or group                                               | Interpretation                                                                                                                        |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `equivalence`      | `Request Clarification`, `Receive Clarification`            | Complete cases contain the same number of requests and receipts. This uses A4.                                                        |
| `equivalence`      | `Activate Vendor`, `Release First Payment`                  | A complete rejected case has zero of both; a complete accepted case has one of both.                                                  |
| `always_before`    | Each initial check paired with `Receive Onboarding Request` | Receipt precedes each check. The constrained check is first in the tuple.                                                             |
| `always_before`    | `Classify Risk` paired separately with all three checks     | Classification requires all three prior checks.                                                                                       |
| `always_before`    | `Sanctions Escalation`, `Run Sanctions Screening`           | Escalation requires earlier sanctions screening.                                                                                      |
| `always_before`    | `Manager Approval`, `Classify Risk`                         | Manager approval requires prior risk classification.                                                                                  |
| `always_before`    | `Enhanced Due Diligence`, `Classify Risk`                   | EDD requires prior classification.                                                                                                    |
| `always_before`    | `Compliance Approval`, `Enhanced Due Diligence`             | Compliance approval requires prior EDD.                                                                                               |
| `always_before`    | `Reject Vendor`, `Classify Risk`                            | Rejection requires prior classification.                                                                                              |
| `always_before`    | `Activate Vendor`, `Classify Risk`                          | Activation requires prior classification, but this relation cannot express the disjunctive approval predecessor.                      |
| `always_before`    | `Release First Payment`, `Activate Vendor`                  | Payment requires prior activation.                                                                                                    |
| `always_before`    | `Change Bank Details`, `Activate Vendor`                    | Only post-activation bank changes are admitted.                                                                                       |
| `always_before`    | `Suspend Vendor`, `Change Bank Details`                     | Suspension requires an earlier bank-details change.                                                                                   |
| `always_before`    | `Receive Clarification`, `Request Clarification`            | A receipt requires some earlier request; it does not match individual cycles.                                                         |
| `always_after`     | `Request Clarification`, `Receive Clarification`            | A request must eventually have a later receipt.                                                                                       |
| `always_after`     | `Sanctions Escalation`, `Obtain Legal Opinion`              | Escalation must eventually have a later opinion.                                                                                      |
| `always_after`     | Each approval paired with `Activate Vendor`                 | An approval must lead to activation. This does not state that every activation has an approval.                                       |
| `always_after`     | `Activate Vendor`, `Release First Payment`                  | Accepted cases must eventually reach first payment.                                                                                   |
| `always_after`     | `Release First Payment`, `Close Onboarding`                 | Payment must eventually lead to closure.                                                                                              |
| `always_after`     | `Reject Vendor`, `Close Onboarding`                         | Rejection must eventually lead to closure.                                                                                            |
| `always_after`     | `Change Bank Details`, `Suspend Vendor`                     | A bank change requires later suspension.                                                                                              |
| `always_after`     | `Change Bank Details`, `Verify Bank Account`                | A bank change requires some later verification.                                                                                       |
| `never_together`   | Five listed pairs                                           | Each pair is symmetric, regardless of tuple order.                                                                                    |
| `directly_follows` | Empty                                                       | None of the requirements justifies mandatory adjacency. Clarification, escalation work, and other cross-cutting events may intervene. |

The Log Skeleton deliberately omits the R5 opinion-before-activation condition. An unconditional `("Activate Vendor", "Obtain Legal Opinion")` in `always_before` would require an opinion before every activation, including cases with no escalation.

The R11 entries are necessary but not sufficient. They do not distinguish the initial verification from a re-verification or prove that the new verification is before the later payment. The Petri net and timestamp-aware check remain authoritative.

# 6. Temporal Profile

```python
temporal_profile = {
    (
        "Request Clarification",
        "Receive Clarification",
    ): (
        48 * 60 * 60,   # 172800 seconds
        24 * 60 * 60,   #  86400 seconds
    ),

    (
        "Sanctions Escalation",
        "Obtain Legal Opinion",
    ): (
        12 * 60 * 60,   # 43200 seconds
        6 * 60 * 60,    # 21600 seconds
    ),

    (
        "Activate Vendor",
        "Release First Payment",
    ): (
        72 * 60 * 60,   # 259200 seconds
        36 * 60 * 60,   # 129600 seconds
    ),
}

zeta = 2.0
```

| Pair                                            | Mean | Standard deviation | Two-standard-deviation interval |
| ----------------------------------------------- | ---: | -----------------: | ------------------------------: |
| `Request Clarification → Receive Clarification` | 48 h |               24 h |                          0–96 h |
| `Sanctions Escalation → Obtain Legal Opinion`   | 12 h |                6 h |                          0–24 h |
| `Activate Vendor → Release First Payment`       | 72 h |               36 h |                         0–144 h |

PM4Py temporal profiles compare elapsed times between eventually-following activity pairs and flag observations outside `mean ± zeta × standard deviation`. ([GitHub][3])

These deviations are warnings rather than automatic control-flow failures for three reasons:

1. R12 explicitly says to flag rather than automatically reject.
2. The distributions describe expected performance, not legal impossibility.
3. A missing target event has no duration to compare. For example, T5’s missing clarification receipt is a procedural and DECLARE failure, not a statistical-duration observation.

The profile also has no business-calendar semantics. A 34-hour escalation-to-opinion interval is evaluated as 34 elapsed hours even if it spans a weekend.

# 7. Resource- and Data-Aware Checks

## Required attributes and missing-data treatment

| Check                                          | Required attributes                                                                                                 | Treatment when missing                                                                                                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R9 segregation of duties                       | `case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`                                               | Do not certify the rule. Return `not evaluated`, raise a data-quality issue, and prevent a “fully compliant” status.                                                   |
| R6 emergency exception                         | Base attributes plus `emergency_authorized`, `authorization_timestamp`, `legal_authorizer`, `operations_authorizer` | Under strict policy, the exception is unavailable and activation-before-opinion fails. Under guarded analytics, return `policy-dependent`; do not infer authorization. |
| R11 occurrence-sensitive ordering              | Case, activity, timestamp, and a stable order for timestamp ties                                                    | If order is ambiguous, return `not evaluated`. Do not guess which verification belongs to a change.                                                                    |
| Repeated escalation or bank-change correlation | Preferably `escalation_id`, `opinion_for_escalation_id`, and `bank_change_id`                                       | Without IDs, use the explicitly stated serialized-cycle assumption and disclose it.                                                                                    |

## Executable-style dataframe validation

```python
from __future__ import annotations

from typing import Literal
import pandas as pd

CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"
RES = "org:resource"

APPROVALS = {"Manager Approval", "Compliance Approval"}


def is_true(value) -> bool:
    if value is True or value == 1:
        return True
    return str(value).strip().lower() == "true"


def result(rule: str, status: str, detail: str) -> dict:
    return {"rule": rule, "status": status, "detail": detail}


def validate_case(
    case_df: pd.DataFrame,
    conflict_policy: Literal["strict", "guarded_emergency"] = "strict",
) -> list[dict]:
    """
    Checks R9, the R5/R6 conflict, and occurrence-sensitive R11.

    Expected base columns:
      case:concept:name, concept:name, time:timestamp, org:resource

    Guarded-emergency columns:
      emergency_authorized, authorization_timestamp,
      legal_authorizer, operations_authorizer
    """
    required = {CASE, ACT, TS, RES}
    missing = required - set(case_df.columns)
    if missing:
        return [
            result(
                "schema",
                "not evaluated",
                f"Missing base columns: {sorted(missing)}",
            )
        ]

    g = case_df.copy()
    g["__row_order"] = range(len(g))
    g[TS] = pd.to_datetime(g[TS], utc=True, errors="coerce")
    g = g.sort_values([TS, "__row_order"], kind="mergesort")

    if g[TS].isna().any():
        return [
            result(
                "timestamp completeness",
                "not evaluated",
                "At least one timestamp is missing or unparsable.",
            )
        ]

    findings: list[dict] = []
    activates = g[g[ACT].eq("Activate Vendor")]
    approvals = g[g[ACT].isin(APPROVALS)]

    # ---------- R9a: Verify Bank Account vs applicable approval ----------
    if activates.empty:
        findings.append(
            result(
                "R9 verify/approval segregation",
                "not evaluated",
                "Rejected or unfinished case: no applicable accepted-case approval.",
            )
        )
    elif len(activates) != 1:
        findings.append(
            result(
                "R9 verify/approval segregation",
                "not evaluated",
                "Activation count is not one, so the applicable approval is ambiguous.",
            )
        )
    else:
        activation = activates.iloc[0]
        approval_candidates = approvals[approvals[TS] < activation[TS]]

        if len(approval_candidates) != 1:
            findings.append(
                result(
                    "R9 verify/approval segregation",
                    "not evaluated",
                    "Exactly one approval before activation is needed to select "
                    "the applicable approval.",
                )
            )
        else:
            approval = approval_candidates.iloc[0]
            verifies = g[
                g[ACT].eq("Verify Bank Account")
                & (g[TS] < approval[TS])
            ]

            relevant = pd.concat([verifies, approval_candidates])
            missing_resource = (
                relevant[RES].isna().any()
                or relevant[RES].astype(str).str.strip().eq("").any()
            )

            if verifies.empty:
                findings.append(
                    result(
                        "R9 verify/approval segregation",
                        "not evaluated",
                        "No pre-approval bank verification was found.",
                    )
                )
            elif missing_resource:
                findings.append(
                    result(
                        "R9 verify/approval segregation",
                        "not evaluated",
                        "A relevant resource identifier is missing.",
                    )
                )
            elif approval[RES] in set(verifies[RES]):
                findings.append(
                    result(
                        "R9 verify/approval segregation",
                        "fail",
                        f"{approval[RES]!r} performed both bank verification "
                        "and the applicable approval.",
                    )
                )
            else:
                findings.append(
                    result(
                        "R9 verify/approval segregation",
                        "pass",
                        "All pre-approval verification resources differ from "
                        "the applicable approver.",
                    )
                )

    # ---------- R9b: Capture Master Data vs Activate Vendor ----------
    captures = g[g[ACT].eq("Capture Master Data")]

    if activates.empty:
        findings.append(
            result(
                "R9 capture/activation segregation",
                "not evaluated",
                "No activation event.",
            )
        )
    elif captures.empty or len(activates) != 1:
        findings.append(
            result(
                "R9 capture/activation segregation",
                "not evaluated",
                "Capture or unique activation event is missing.",
            )
        )
    elif pd.concat([captures, activates])[RES].isna().any():
        findings.append(
            result(
                "R9 capture/activation segregation",
                "not evaluated",
                "A relevant resource identifier is missing.",
            )
        )
    elif set(captures[RES]).intersection(set(activates[RES])):
        findings.append(
            result(
                "R9 capture/activation segregation",
                "fail",
                "A resource performed both master-data capture and activation.",
            )
        )
    else:
        findings.append(
            result(
                "R9 capture/activation segregation",
                "pass",
                "Capture and activation resources are disjoint.",
            )
        )

    # ---------- Strict R5 or guarded R6 emergency exception ----------
    if len(activates) == 1:
        activation = activates.iloc[0]
        activation_time = activation[TS]

        escalations = g[
            g[ACT].eq("Sanctions Escalation")
            & (g[TS] < activation_time)
        ]

        if escalations.empty:
            findings.append(
                result(
                    "R5/R6 activation before opinion",
                    "pass",
                    "No pre-activation sanctions escalation.",
                )
            )
        else:
            last_escalation_time = escalations.iloc[-1][TS]
            opinions_before = g[
                g[ACT].eq("Obtain Legal Opinion")
                & (g[TS] > last_escalation_time)
                & (g[TS] < activation_time)
            ]

            if not opinions_before.empty:
                findings.append(
                    result(
                        "R5/R6 activation before opinion",
                        "pass",
                        "The latest escalation has an opinion before activation.",
                    )
                )

            elif conflict_policy == "strict":
                findings.append(
                    result(
                        "R5/R6 activation before opinion",
                        "fail",
                        "Strict R5: activation occurred with an unresolved escalation.",
                    )
                )

            else:
                evidence_columns = {
                    "emergency_authorized",
                    "authorization_timestamp",
                    "legal_authorizer",
                    "operations_authorizer",
                }

                if not evidence_columns.issubset(g.columns):
                    findings.append(
                        result(
                            "R5/R6 activation before opinion",
                            "policy-dependent",
                            "Emergency evidence columns are absent.",
                        )
                    )
                else:
                    authorized = is_true(
                        activation.get("emergency_authorized")
                    )
                    authorization_time = pd.to_datetime(
                        activation.get("authorization_timestamp"),
                        utc=True,
                        errors="coerce",
                    )
                    legal_authorizer = activation.get("legal_authorizer")
                    operations_authorizer = activation.get(
                        "operations_authorizer"
                    )

                    opinions_after = g[
                        g[ACT].eq("Obtain Legal Opinion")
                        & (g[TS] > activation_time)
                        & (g[TS] > last_escalation_time)
                    ]

                    missing_evidence = (
                        not authorized
                        or pd.isna(authorization_time)
                        or pd.isna(legal_authorizer)
                        or pd.isna(operations_authorizer)
                        or str(legal_authorizer).strip() == ""
                        or str(operations_authorizer).strip() == ""
                    )

                    if missing_evidence:
                        findings.append(
                            result(
                                "R5/R6 activation before opinion",
                                "policy-dependent",
                                "Emergency authorization is missing or not affirmative.",
                            )
                        )
                    elif legal_authorizer == operations_authorizer:
                        findings.append(
                            result(
                                "R5/R6 activation before opinion",
                                "fail",
                                "Legal and operations authorization came from "
                                "the same identity.",
                            )
                        )
                    elif authorization_time > activation_time:
                        findings.append(
                            result(
                                "R5/R6 activation before opinion",
                                "fail",
                                "Authorization was recorded after activation.",
                            )
                        )
                    elif opinions_after.empty:
                        findings.append(
                            result(
                                "R5/R6 activation before opinion",
                                "fail",
                                "No legal opinion followed emergency activation.",
                            )
                        )
                    else:
                        opinion_delay = (
                            opinions_after.iloc[0][TS] - activation_time
                        )
                        status = (
                            "pass"
                            if opinion_delay <= pd.Timedelta(hours=24)
                            else "fail"
                        )
                        findings.append(
                            result(
                                "R5/R6 activation before opinion",
                                status,
                                f"Post-activation opinion delay: {opinion_delay}.",
                            )
                        )

    # ---------- R11 post-activation bank-change cycles ----------
    if len(activates) == 1:
        activation_time = activates.iloc[0][TS]
        changes = g[
            g[ACT].eq("Change Bank Details")
            & (g[TS] > activation_time)
        ]

        for cycle_no, (_, change) in enumerate(
            changes.iterrows(),
            start=1,
        ):
            change_time = change[TS]
            next_changes = changes[changes[TS] > change_time]
            next_change_time = (
                next_changes.iloc[0][TS]
                if not next_changes.empty
                else None
            )

            suspends = g[
                g[ACT].eq("Suspend Vendor")
                & (g[TS] > change_time)
            ]
            if next_change_time is not None:
                suspends = suspends[suspends[TS] < next_change_time]

            if suspends.empty:
                findings.append(
                    result(
                        f"R11 bank-change cycle {cycle_no}",
                        "fail",
                        "No suspension follows the bank change before "
                        "the next bank change.",
                    )
                )
                continue

            suspend_time = suspends.iloc[0][TS]
            later_payments = g[
                g[ACT].eq("Release First Payment")
                & (g[TS] > change_time)
            ]

            violating_payment = False
            for _, payment in later_payments.iterrows():
                reverifications = g[
                    g[ACT].eq("Verify Bank Account")
                    & (g[TS] > suspend_time)
                    & (g[TS] < payment[TS])
                ]
                if reverifications.empty:
                    violating_payment = True
                    break

            findings.append(
                result(
                    f"R11 bank-change cycle {cycle_no}",
                    "fail" if violating_payment else "pass",
                    (
                        "A later payment lacks a post-change, post-suspension "
                        "bank re-verification."
                        if violating_payment
                        else "Suspension follows the change and every later "
                        "payment is preceded by re-verification."
                    ),
                )
            )

    return findings
```

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement

R1, R3, R4, R7, R8, and parts of R10–R11 appear in more than one layer. This is intentional defense in depth, but the layers must not be treated as votes:

* Procedural conformance is authoritative for lifecycle routing and enabledness.
* DECLARE is authoritative for explicitly assigned case-wide policy constraints.
* Log Skeleton is authoritative for its assigned occurrence bounds.
* The resource/data layer is authoritative for R6 and R9.
* The temporal layer produces warnings only.

A secondary layer disagreeing with the authoritative layer is a modeling diagnostic, not a reason to average the results.

## R5/R6 is a genuine policy contradiction

Strict R5 and emergency R6 cannot both be unconditional. Adding an ordinary emergency activation transition while retaining unconditional strict non-succession would make the hybrid internally contradictory. The selected policy version and its evidence must be visible in every conformance result.

## Loops and repeated activity labels

`Verify Bank Account` denotes both an initial check and a post-change re-verification. An activity-only constraint such as precedence from verification to payment can be satisfied by the initial verification even when the required post-change verification is absent.

Repeated clarification cycles create a similar issue. Count equivalence establishes equal totals but does not pair each response with its request. Alternate response adds ordering, while the Petri-net monitor provides the final-outcome gate.

Multiple sanctions escalations are also problematic. A simple response rule can allow one later opinion to satisfy several earlier escalation occurrences. The procedural model avoids that ambiguity by allowing one unresolved escalation at a time. A production log should instead record an `escalation_id`.

Temporal profiles over repeated labels may compare multiple eventually-following combinations rather than the intended matched cycle. Request/response or escalation/opinion correlation identifiers would make the timing analysis more defensible.

## Post-activation inconsistency risks

R10 allows only one `Release First Payment`, while R11 refers to “any later” first payment. Therefore:

* several bank changes may precede the one payment;
* once first payment has occurred, there can be no second first-payment event;
* a bank change after first payment would retain a suspension obligation but no longer have a later first payment to constrain.

The procedural model resolves this by allowing bank changes only between activation and first payment and by closing after payment. If post-payment maintenance is a real business process, it should be modeled as a separate lifecycle rather than forced into onboarding.

The net also strengthens R11 to `Change → Suspend → Verify`. R11 explicitly requires suspension eventually and verification before payment, but does not expressly say suspension must precede verification. That strengthening should be confirmed with the policy owner.

## Vacuity

Several DECLARE rules can pass without testing the intended business scenario:

* `response(Manager Approval, Activate Vendor)` passes when no manager approval occurs.
* `response(Compliance Approval, Activate Vendor)` passes when no compliance approval occurs.
* Both therefore fail to prove that an activated case has one approval.
* `precedence(Run Sanctions Screening, Sanctions Escalation)` passes whenever no escalation occurs.
* `noncoexistence` passes when either or both activities are absent.
* The R5 escalation-response composition passes cases without escalation.

This is why the procedural XOR is necessary for R2 and why activations should not be certified solely through the DECLARE result.

For live cases, a response obligation is also not immediately a completed-trace violation. Monitoring must distinguish `pending` from `violated`.

## Missing attributes

The following information is absent but materially important:

* emergency flag and policy version;
* authorization timestamp;
* identities and roles of both emergency authorizers;
* escalation/opinion correlation identifier;
* bank-change/re-verification correlation identifier;
* verification purpose or phase;
* stable event ordering for timestamp ties;
* authoritative resource identity rather than display name;
* possibly `risk_class`, to verify that the selected low- or high-risk route matches the classification result.

Without these fields, some apparently precise conformance findings are only conservative approximations.

## Timestamp-only limitations

Point timestamps do not reveal activity duration, work suspension, or whether two tasks truly overlapped. The three initial checks are procedurally concurrent, but timestamp order alone shows only their recorded completion order.

Elapsed timestamps also do not show:

* whether weekends or holidays should be excluded;
* whether an opinion was prepared before its recorded completion event;
* whether authorization occurred outside the system before activation;
* whether clocks were synchronized;
* which event came first when timestamps tie.

A 24-hour emergency rule therefore requires an explicit elapsed-time definition and reliable timestamps.

## Support and confidence are not normative truth

The `support=1.0` and `confidence=1.0` values are configuration placeholders. They do not establish that stakeholders agree, resolve R5/R6, or demonstrate that a rule held historically. They must not be used to convert contradictory policy statements into an apparently certain model.

Similarly, discovering high support from these eight traces would not justify treating the pattern as policy. Several test cases are deliberately nonconforming.

## Other model blind spots

The procedural model permits checks, classification, and approvals while clarification is pending. That is consistent with R3 but would underconstrain the process if clarification is intended to suspend all substantive work.

The model permits `Reject Vendor` while a sanctions opinion is pending and then requires the opinion before closure. This follows R4 and the fact that R5 mentions activation specifically. If rejection must terminate all legal work immediately, that policy must be added explicitly.

An unsolicited legal opinion is excluded procedurally but not explicitly forbidden by the requirements. A broader legal-review use case would need a separate path or event purpose attribute.

# 10. Deployment Recommendation

The **canonical procedural representation** should be the accepting Petri net, stored and versioned as the lifecycle model. It expresses concurrency, the classification join, exclusive outcome routes, clarification state, sanctions state, and post-activation bank-change cycles without forcing non-block-structured behavior into a ProcessTree.

The **authoritative policy registry** should assign each rule to one owner and one primary checker:

| Policy category                               | Authoritative representation                             |
| --------------------------------------------- | -------------------------------------------------------- |
| Lifecycle, route selection, and enabledness   | Accepting Petri net                                      |
| Case-wide activity obligations and exclusions | DECLARE                                                  |
| Activity-count invariants                     | Log Skeleton                                             |
| R5/R6 policy selection and emergency evidence | Data-aware decision rule                                 |
| Segregation of duties                         | Resource-aware validation                                |
| Occurrence-specific bank-change matching      | Timestamp/data-aware validation, backed by the Petri net |
| Statistical timing expectations               | Temporal profile, warning severity                       |

Conformance should run in this order:

1. **Schema and data-quality validation.** Check required columns, timestamp parseability, resource completeness, event ordering, and case completeness.
2. **Policy-version resolution.** Determine strict R5 versus guarded R6 before selecting procedural and declarative rules. Missing emergency evidence should not silently select the permissive policy.
3. **Procedural alignment or replay.** Detect impossible ordering, missing lifecycle activities, unresolved clarification at outcome, contradictory terminal outcomes, and invalid post-activation sequences.
4. **DECLARE conformance.** Evaluate cross-cutting obligations and exclusions, retaining individual rule deviations rather than only an aggregate fitness value.
5. **Log-Skeleton conformance.** Check occurrence counts and broad before/after invariants.
6. **Resource- and occurrence-aware validation.** Resolve the applicable approval, run both segregation checks, and match post-change suspension and verification events.
7. **Temporal-profile conformance.** Add warnings for unusual elapsed times without converting them into control-flow failures.
8. **Conflict consolidation.** Apply the designated authoritative layer per requirement instead of majority voting.

Results should be presented per requirement with:

* policy version;
* authoritative layer;
* primary violation;
* triggering event and timestamp;
* related earlier event;
* missing evidence;
* secondary-layer findings;
* severity of `fail`, `warning`, `policy-dependent`, or `not evaluated`;
* the earliest decisive violation and any later consequences.

For T6, the user-facing result should not merely say “nonconforming.” Under strict R5 it should report activation with an unresolved escalation at hour 13. Under guarded R6 it should report that the 10-hour post-activation opinion delay satisfies the time condition but that emergency authorization is unprovable from the available data.

Finally, T1–T8 should be retained as regression tests. Any model or policy update should reproduce the matrix above or explicitly document why a verdict changed.
