

## 1. Equivalence design space

To cluster the executions meaningfully, we distinguish three equivalence relations that progressively incorporate object-centric detail.

1. **Activity-sequence equivalence:** Two executions are equivalent if their sequences of activity labels are identical.
   - *Definition:* A sequence of activity labels $L = (a_1, a_2, \dots, a_n)$.
   - *Preserved:* Label order, repeated events (e.g., multiple Record Payments).
   - *Discarded:* All object identifiers, types, multiplicities, relations, and external flags.
   - *Properties:* Reflexive, symmetric, transitive.
   - *Concurrency:* If multiple events share a timestamp, we treat their relative order as deterministic in the input sequence or require stable ordering (e.g., event ID) to maintain a canonical linearization.

2. **Typed structural equivalence under identifier renaming:** Two executions are equivalent if their object-centric graphs are isomorphic after abstracting away concrete identifiers while preserving type and incidence.
   - *Definition:* For each execution, construct a graph $G=(V,E)$ where $V$ are object instances typed by their ObjectType and $E$ are links derived from event inputs/outputs. Isomorphism $\phi$ maps $V \to V'$ preserving types and edge connectivity relative to the lead Order.
   - *Preserved:* Object types (Order, Item, Package), event type multiplicity per object, incidence structure (e.g., Pack connects 1 Order + N Items + 1 Package), external object flags (e.g., EXT- prefix treated as distinct type or external marker).
   - *Discarded:* Concrete IDs (O1 vs O2), event timestamps, specific O2O qualifier strings.
   - *Properties:* Reflexive, symmetric, transitive (isomorphism is an equivalence relation).
   - *Concurrency:* Same as above; edges are added based on the provided sequence.

3. **Business-semantic equivalence:** Two executions are equivalent if they exhibit the same business pattern regarding logistics, finance, and lifecycle modifications.
   - *Definition:* Equivalence classes defined by motifs: single-package single-delivery vs. split-pack vs. split-delivery vs. shared external resources (cross-order) vs. lifecycle exceptions (replacement/return).
   - *Preserved:* Multiplicities of key resources (packages, payments per invoice), external-object flags (shared orders), O2O qualifiers (removed_before_dispatch), and post-dispatch loops (Returns).
   - *Discarded:* Exact event timestamps, minor label variations.
   - *Properties:* Reflexive, symmetric, transitive (defined by pattern classification).
   - *Concurrency:* Handled by grouping same-type events within a phase (e.g., all Pack events before any Dispatch).

## 2. Canonical signatures

For **Typed structural equivalence**, we define a canonical signature that renames identifiers and captures topology:

```python
def canonical_signature(execution):
    # Map concrete IDs to abstract counters per type
    type_counts = {}
    type_seq = {}
    external_flags = set()
    events = []

    for event in execution.events:
        # Map event label
        label = event.activity
        
        # Map objects
        objs = []
        for (obj_type, obj_id) in event.object_map:
            # Normalize ID
            if obj_id.startswith('EXT'):
                canonical_id = obj_type + '_ext'
                external_flags.add(obj_type)
            else:
                canonical_id = obj_type + '_' + str(type_counts.get(obj_type, 0))
                type_counts[obj_type] = type_counts.get(obj_type, 0) + 1
            
            objs.append((obj_type, canonical_id))
        
        events.append((label, tuple(objs)))
    
    # Create signature string
    sig = (len(events), tuple(e[0] for e in events), tuple(type_counts.values()), 
           sorted(list(external_flags)))
    return sig
```

This signature is invariant to local identifier renaming (e.g., O1O2), preserves object types and multiplicities (counts per type), flags external objects, and captures repeated activities via the event label sequence.

## 4. Cluster interpretations

**Core Fulfillment (X1, X2):**
*   **Signature:** Single Order, single package, single delivery, isolated finance.
*   **Business behavior:** Standard e-commerce fulfillment.
*   **Risks/Opportunities:** High throughput; low complexity. Good for automation.
*   **Flattening issue:** Flattening loses item-to-package association.
*   **Stability:** Stable under data repair.

**Logistics Split (X3, X4):**
*   **Signature:** Multiple packages, potentially multiple deliveries.
*   **Business behavior:** Split shipments due to inventory location or weight constraints.
*   **Risks/Opportunities:** Higher shipping costs, tracking complexity. Opportunity for consolidation analysis.
*   **Flattening issue:** Flattening merges shipments, hiding delay risks.
*   **Stability:** Stable; split patterns are persistent.

**Shared Resources (X5, X6):**
*   **Signature:** External objects participate in lifecycle.
*   **Business behavior:** Cross-order consolidation (e.g., drop shipping or consolidated billing).
*   **Risks/Opportunities:** Billing disputes if external allocation is unclear. Opportunity for volume discounts.
*   **Flattening issue:** Flattening treats external orders as internal objects, causing confusion.
*   **Stability:** Stable if external object flags are preserved.

**Lifecycle Exception (X7, X8):**
*   **Signature:** Post-pack modification (replacement or return loop).
*   **Business behavior:** Quality control failure or customer return.
*   **Risks/Opportunities:** Inventory shrinkage; cost recovery potential.
*   **Flattening issue:** Flattening treats Return as new activity, losing object continuity.
*   **Stability:** Sensitive to qualifier interpretation (e.g., ignoring `removed_before_dispatch`).

## 5. Borderline cases

**X1 vs X2:** Activity equivalence agrees (same labels). Typed structural agrees (isomorphic). Business semantics agree. Disagreement arises only in exact identifier matching.

**X1 vs X5:** Activity equivalence agrees (same labels). Typed structural disagrees (X5 has external object type). Business semantics disagree (isolated vs shared). If external object flags are ignored, X5 collapses to X1.

**X1 vs X6:** Similar to X1 vs X5. Financial sharing is structurally invisible unless invoice multiplicity is tracked.

**X1 vs X7:** Activity equivalence agrees. Typed structural agrees (graph isomorphism is preserved if `removed_before_dispatch` qualifier is ignored). Business semantics disagree (replacement vs straight-through). If qualifiers are discarded, X7 looks like X1.

**X3 vs X4:** Activity equivalence differs (X4 has more events). Typed structural differs (X4 has two Dispatch events vs X3 one). Business semantics may group them (Logistics Split), but partial payment complexity distinguishes them.

**X4 vs X8:** Activity equivalence differs (X8 has Return/Inspect). Typed structural differs (X8 modifies existing packages). Business semantics both represent exceptions but X8 is post-delivery while X4 is multi-shipment.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py key structure preserves exact object identifiers and types in its canonical representation for exact matching. This means raw object IDs (like O1 vs O2) cause executions to cluster separately even if they follow the same process. 

To coarsen, we should canonicalize object IDs before clustering (e.g., mapping Order IDs to generic "Lead" and external IDs to "Shared"). The `max_objs` parameter in PM4Py might truncate object histories, breaking equivalence for complex cases like X8. We use exact equivalence for data quality checks, where ID consistency matters, but we prefer canonicalized equivalence for process mining.

```python

    # 3. Cluster

    return clusters
```

## 7. Robustness analysis

1. **Ignore all O2O qualifiers:** X7 (replacement) would collapse to X1. This is risky for quality monitoring but useful for high-level throughput analysis.
2. **Ignore external objects:** X5 and X6 collapse to X1. This simplifies process mining but risks misallocating costs to internal orders.
3. **Collapse repeated same-label events:** X2 (Add Item swapped) would match X1 under canonicalization if activity order is ignored; X4 payments collapse to one. This hides partial payment patterns.
4. **Treat Pack/Dispatch order as partial:** X3 (Pack-Pack-Dispatch) and X4 (Pack-Dispatch-Pack-Dispatch) differ under partial order because X4 interleaves operations. If we relax to "Pack before Dispatch for same item," they group together.
5. **Payment multiplicity as attribute:** If Record Payment amounts are merged, X4 (partial) matches X1 (full). This hides financial risk (partial payments).

## 8. Limitations and recommendation

No single equivalence works for all goals:

- **Compliance monitoring:** Use **Typed structural**. We must detect exact violations of business rules (e.g., multiple Dispatch). External objects must be flagged.
- **Operational segmentation:** Use **Business-semantic**. We want to group similar workflows (split logistics vs straight-through) to assign resources.
- **Root-cause analysis:** Use **Activity-sequence + Typed structural**. We need to compare exact event patterns while ignoring identifier noise.
- **Descriptive reporting:** Use **Business-semantic**. Summaries like "Split shipment rate" are more informative than raw graph counts.

Recommendation: Adopt a layered equivalence approach. Use canonicalized Typed Structural for clustering (as the baseline) and annotate clusters with Business-Semantic tags. This ensures reproducibility while allowing business users to interpret results without getting lost in technical isomorphism details.
