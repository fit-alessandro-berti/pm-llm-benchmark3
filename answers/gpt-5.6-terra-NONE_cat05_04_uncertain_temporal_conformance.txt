## 1. Normalization Assumptions

### Interval construction

For each recorded timestamp:

1. Apply its display-resolution interval on the source clock.
2. Convert the local clock interval to UTC using the stated time zone.
3. Correct for clock offset using:

\[
\text{true time}=\text{recorded clock time}-\text{clock offset}
\]

If offset is \([a,b]\), corrected true time is:

\[
[\text{recorded lower}-b,\ \text{recorded upper}-a]
\]

All intervals below are closed for readability. Where a source says `59.999`, this is represented as `:59.999` rather than an open upper bound.

### Display semantics used

| System | Recorded-clock interval used before offset correction |
|---|---|
| HUB | displayed second ±0.5 seconds |
| OPS-BER | floor-to-minute: `[HH:MM:00, HH:MM:59.999]` |
| SENSOR | nearest 10 seconds: ±5 seconds around display |
| VENDOR-NY | floor-to-minute |
| LEGACY-BER | floor-to-minute, with both DST folds considered where applicable |
| MOBILE-LON | nearest minute: ±30 seconds around display |

### Time-zone conversion

- Berlin on 2026-06-01 uses CEST, UTC+02:00.
- New York on 2026-06-01 uses EDT, UTC04:00.
- London on 2026-06-01 uses BST, UTC+01:00.
- Berlin on 2025-10-26 at 02:xx is ambiguous:
  - DST fold 0 / CEST: UTC+02:00
  - DST fold 1 / CET: UTC+01:00

### Clock-offset treatment

Examples:

- HUB: ±0.5 second display uncertainty and offset \([-1,+1]\) seconds yields a total true-time interval of ±1.5 seconds.
- OPS-BER: floor-minute plus offset \([-90,+120]\) seconds means a displayed minute maps to a 270-second true-time interval.
- SENSOR: ±5 seconds rounding plus ±5 seconds offset gives ±10 seconds.
- VENDOR-NY: one minute floor plus ±180 seconds offset yields a 420-second interval.
- MOBILE-LON: ±30 seconds rounding plus ±300 seconds clock offset yields ±330 seconds before considering entry delay.

### T-404 inferred Investigation_Start

`Investigation_Start` is not logged. I infer it from:

\[
\text{Investigation Start}=\text{Investigation Complete}-\text{signed duration}
\]

The signed duration is 18–25 minutes. Since `Investigation_Complete` is HUB ±1.5 seconds, inferred start is:

- earliest start: completion earliest minus 25 minutes;
- latest start: completion latest minus 18 minutes.

This is an inferential interval, not direct event evidence.

### T-405 DST fold and causal ordering

Each LEGACY-BER timestamp has two possible UTC intervals, one for each DST fold. I retain the alternatives rather than collapsing immediately.

The stated ingestion order is treated as a weak causal constraint:

\[
Alert\_Received \le Investigation\_Start \le Containment\_Complete
\]

It rules out fold assignments that make the activities impossible in that order. It does not eliminate within-minute resolution uncertainty or clock uncertainty.

The surviving chronology requires:

- Alert in the first 02:50 occurrence (CEST),
- Investigation Start in the second 02:05 occurrence (CET),
- Containment Complete in the second 02:42 occurrence (CET).

### T-406 mobile entry delay

Primary treatment: the user may have entered the displayed time up to five minutes late, so the record time can lag actual occurrence by 0–5 minutes. This shifts the occurrence estimate earlier:

\[
T_{occurrence}=T_{recorded,true}-[0,300s]
\]

Thus it expands the lower bound earlier but does not move the upper bound later.

Alternative semantic treatment: if the mobile entry is only a late administrative record and does not purport to time the actual start, it should not be used as occurrence-time evidence. Under that stricter view, S1 and profile timing involving `Investigation_Start` are indeterminate rather than merely interval-uncertain.

### T-407 Alert_Sent versus Alert_Received

`Alert_Sent` is not assumed identical to `Alert_Received`.

Network evidence supplies delivery latency of 0–20 minutes, so an inferred receipt interval is derived from Alert_Sent plus latency. The plausible-but-unlogged causal assumption that receipt is not after Investigation_Start is shown separately:

- without causal truncation: receipt may occur up to 20 minutes after send;
- with causal truncation: receipt is bounded above by Investigation_Start.

Because no receipt acknowledgement exists, T-407 findings involving Alert_Received remain assumption-dependent.

### Classification conventions

For maximum-duration SLA rules:

- `CERTAIN_PASS`: all feasible durations are at or below the threshold.
- `CERTAIN_VIOLATION`: all feasible durations exceed the threshold.
- `POSSIBLE_VIOLATION`: interval spans the threshold.
- `INDETERMINATE`: missing/unreliable event semantics, unbounded inference, contradiction, or non-testability.

For profile bands:

\[
[\mu-\zeta\sigma,\ \mu+\zeta\sigma]
\]

- wholly inside: `CERTAIN_PASS`;
- wholly below or wholly above: `CERTAIN_VIOLATION`;
- overlapping the band boundary: `POSSIBLE_VIOLATION`;
- insufficient or semantically invalid evidence: `INDETERMINATE`.

Severity and confidence are qualitative:

- Severity: Critical / High / Medium / Low / Informational.
- Confidence: High for direct HUB evidence, Medium for bounded source-clock evidence, Low for inferred or semantically disputed evidence.

## 5. PM4Py Temporal-Conformance Code

```python
"""
Interval-based incident-response timing analysis plus a deliberately lossy
midpoint-only PM4Py comparison.

Requirements:
    pip install pandas pm4py

This script does not read external files.

Important limitation:
PM4Py temporal conformance APIs consume point timestamps. The midpoint log
created below is explicitly a lossy approximation and does NOT resolve:
- clock-offset ranges,
- timestamp rounding/flooring,
- DST fold ambiguity,
- inferred-event uncertainty,
- missing receipt semantics,
- causal-order uncertainty.

The interval conclusions are produced by this script's own interval logic.
"""

from __future__ import annotations

from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo
from itertools import product
import pandas as pd

try:
    import pm4py
except ImportError as exc:
    raise SystemExit("Install PM4Py first: pip install pm4py") from exc


UTC = timezone.utc


@dataclass(frozen=True)
class TimeInterval:
    lo: datetime
    hi: datetime
    label: str = ""

    def __post_init__(self):
        if self.lo.tzinfo is None or self.hi.tzinfo is None:
            raise ValueError("Intervals must be timezone-aware")
        if self.lo > self.hi:
            raise ValueError(f"Invalid interval: {self.lo} > {self.hi}")

    def duration_to(self, later: "TimeInterval") -> "TimeInterval":
        """Feasible duration interval for later - self."""
        return TimeInterval(
            lo=later.lo - self.hi,
            hi=later.hi - self.lo,
            label=f"{self.label}->{later.label}",
        )

    def midpoint(self) -> datetime:
        return self.lo + (self.hi - self.lo) / 2

    def iso(self):
        return f"[{self.lo.isoformat()}, {self.hi.isoformat()}]"


def utc_dt(s: str) -> datetime:
    return datetime.fromisoformat(s.replace("Z", "+00:00")).astimezone(UTC)


def local_dt(
    year: int, month: int, day: int,
    hour: int, minute: int, second: int = 0,
    tzname: str = "UTC", fold: int = 0
) -> datetime:
    return datetime(year, month, day, hour, minute, second,
                    tzinfo=ZoneInfo(tzname), fold=fold)


def clock_interval_floor_minute(local_display: datetime) -> tuple[datetime, datetime]:
    base = local_display.replace(second=0, microsecond=0)
    return base, base + timedelta(seconds=59, milliseconds=999)


def clock_interval_exact_second(local_display: datetime) -> tuple[datetime, datetime]:
    return (
        local_display - timedelta(seconds=0.5),
        local_display + timedelta(seconds=0.5),
    )


def clock_interval_round(local_display: datetime, seconds: float) -> tuple[datetime, datetime]:
    half = timedelta(seconds=seconds / 2.0)
    return local_display - half, local_display + half


def normalize_one(
    local_lo: datetime,
    local_hi: datetime,
    offset_lo_seconds: float,
    offset_hi_seconds: float,
    label: str,
) -> TimeInterval:
    """
    offset = recorded_clock - true_clock.
    Therefore true = recorded - offset.

    If offset is [a,b]:
      true interval = [recorded_lo - b, recorded_hi - a].
    """
    rec_lo_utc = local_lo.astimezone(UTC)
    rec_hi_utc = local_hi.astimezone(UTC)
    return TimeInterval(
        lo=rec_lo_utc - timedelta(seconds=offset_hi_seconds),
        hi=rec_hi_utc - timedelta(seconds=offset_lo_seconds),
        label=label,
    )


def normalize_hub(utc_string: str, label: str) -> list[TimeInterval]:
    dt = utc_dt(utc_string)
    lo, hi = clock_interval_exact_second(dt)
    return [normalize_one(lo, hi, -1, 1, label)]


def normalize_ops_ber(
    year, month, day, hour, minute, label,
    weak=False
) -> list[TimeInterval]:
    local = local_dt(year, month, day, hour, minute, tzname="Europe/Berlin")
    lo, hi = clock_interval_floor_minute(local)
    if weak:
        # T-409 special engineering estimate [-12 min, +12 min]
        return [normalize_one(lo, hi, -720, 720, label)]
    return [normalize_one(lo, hi, -90, 120, label)]


def normalize_vendor_ny(year, month, day, hour, minute, label) -> list[TimeInterval]:
    local = local_dt(year, month, day, hour, minute, tzname="America/New_York")
    lo, hi = clock_interval_floor_minute(local)
    return [normalize_one(lo, hi, -180, 180, label)]


def normalize_sensor(utc_string: str, label: str) -> list[TimeInterval]:
    dt = utc_dt(utc_string)
    lo, hi = clock_interval_round(dt, 10)
    return [normalize_one(lo, hi, -5, 5, label)]


def normalize_mobile_lon(
    year, month, day, hour, minute, label,
    entry_delay_occurrence=True
) -> list[TimeInterval]:
    local = local_dt(year, month, day, hour, minute, tzname="Europe/London")
    lo, hi = clock_interval_round(local, 60)
    interval = normalize_one(lo, hi, -300, 300, label)
    if entry_delay_occurrence:
        # User may enter timestamp 0..5 minutes after occurrence:
        # occurrence = true_record_time - delay
        interval = TimeInterval(
            lo=interval.lo - timedelta(minutes=5),
            hi=interval.hi,
            label=label,
        )
    return [interval]


def normalize_legacy_ber_folds(year, month, day, hour, minute, label) -> list[TimeInterval]:
    """
    Returns both possible DST folds for Europe/Berlin on the ambiguous date.
    Each local minute is floor-to-minute and offset is [-60,+60] seconds.
    """
    out = []
    for fold in (0, 1):
        local = local_dt(year, month, day, hour, minute,
                         tzname="Europe/Berlin", fold=fold)
        lo, hi = clock_interval_floor_minute(local)
        out.append(normalize_one(lo, hi, -60, 60, f"{label};fold={fold}"))
    return out


def infer_start_from_complete(
    completion: TimeInterval,
    duration_min_seconds: int,
    duration_max_seconds: int,
    label: str,
) -> TimeInterval:
    """
    Start = completion - duration, duration in [min,max].
    Earliest start = completion.lo - max_duration.
    Latest start = completion.hi - min_duration.
    """
    return TimeInterval(
        lo=completion.lo - timedelta(seconds=duration_max_seconds),
        hi=completion.hi - timedelta(seconds=duration_min_seconds),
        label=label,
    )


def duration_intervals(
    earlier_alternatives: list[TimeInterval],
    later_alternatives: list[TimeInterval],
    require_nonnegative=False,
) -> list[TimeInterval]:
    """
    Preserves alternative intervals. Does not automatically convex-hull them.

    If require_nonnegative=True, intervals entirely below zero are removed;
    partially negative intervals are clipped at zero. This implements a causal
    feasibility constraint only when that assumption is explicitly chosen.
    """
    result = []
    for a, b in product(earlier_alternatives, later_alternatives):
        d = a.duration_to(b)
        if require_nonnegative:
            if d.hi.total_seconds() < 0:
                continue
            if d.lo.total_seconds() < 0:
                d = TimeInterval(
                    lo=datetime.fromtimestamp(0, tz=UTC),
                    hi=datetime.fromtimestamp(d.hi.total_seconds(), tz=UTC),
                    label=d.label,
                )
        result.append(d)
    return result


def seconds_interval(d: TimeInterval) -> tuple[float, float]:
    epoch = datetime(1970, 1, 1, tzinfo=UTC)
    return (
        (d.lo - epoch).total_seconds(),
        (d.hi - epoch).total_seconds(),
    )


def duration_seconds(d: TimeInterval) -> tuple[float, float]:
    """
    Duration intervals are represented here as TimeInterval-like objects only
    in some helper paths. This utility is for normal event subtraction below.
    """
    raise NotImplementedError


def dur_bounds(earlier: TimeInterval, later: TimeInterval) -> tuple[float, float]:
    return (
        (later.lo - earlier.hi).total_seconds(),
        (later.hi - earlier.lo).total_seconds(),
    )


def classify_max_duration(bounds: tuple[float, float], maximum_seconds: float) -> str:
    lo, hi = bounds
    if lo > hi:
        return "INDETERMINATE"
    if hi <= maximum_seconds:
        return "CERTAIN_PASS"
    if lo > maximum_seconds:
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"


def classify_profile(
    bounds: tuple[float, float],
    average_seconds: float,
    std_seconds: float,
    zeta: float,
) -> str:
    lo, hi = bounds
    band_lo = average_seconds - zeta * std_seconds
    band_hi = average_seconds + zeta * std_seconds

    if lo > hi:
        return "INDETERMINATE"
    if lo >= band_lo and hi <= band_hi:
        return "CERTAIN_PASS"
    if hi < band_lo or lo > band_hi:
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"


def fmt_bounds(bounds: tuple[float, float]) -> str:
    return f"[{bounds[0]:.3f}, {bounds[1]:.3f}] s"

def classify_union_max(bounds_list: list[tuple[float, float]], max_s: float) -> str:
    """
    Union-aware conservative classification:
      - all alternatives entirely pass => CERTAIN_PASS
      - all alternatives entirely violate => CERTAIN_VIOLATION
      - otherwise possible violation
    """
    if not bounds_list:
        return "INDETERMINATE"
    classes = [classify_max_duration(b, max_s) for b in bounds_list]
    if all(c == "CERTAIN_PASS" for c in classes):
        return "CERTAIN_PASS"
    if all(c == "CERTAIN_VIOLATION" for c in classes):
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

    bounds_list: list[tuple[float, float]], avg: float, sd: float, zeta: float

        return "CERTAIN_PASS"
    if all(c == "CERTAIN_VIOLATION" for c in classes):
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

""")
```

## 6. Evidential Sufficiency

| Case | Result needing more evidence | Minimum additional evidence for certainty | Evidence type |
|---|---|---|---|
| T-401 | S1 possible violation | OPS-BER event-level offset or authenticated UTC event timestamp narrowing start uncertainty to one side of 15 minutes | Stronger synchronization evidence |
| T-401 | AlertStart profile possible violation | Same as S1, or a profile policy with zeta=3 | Synchronization / statistical-policy evidence |
| T-402 | S2 possible violation | A tighter OPS-BER offset bound or direct UTC start timestamp; only ~31.5 seconds of upper uncertainty matter | Stronger synchronization evidence |
| T-402 | AlertContainment profile possible violation | Better alert/start correlation is irrelevant; direct interval is driven mainly by OPS start only if using chained evidence, but direct pair is AlertContainment and could be made certain by precise HUB confirmation if display uncertainty policy changes | Timestamp-resolution policy |
| T-403 | S1/profile possible violation | Vendor receipt timestamp with signed server UTC time, NTP telemetry, or a corroborated HUB alert ingestion timestamp | Stronger synchronization evidence |
| T-404 | S1 and S2 possible violations | Direct Investigation_Start event, or signed duration narrowed enough to establish whether start was before/after the threshold boundary | Missing activity evidence / duration evidence |
| T-404 | Profile AlertStart possible violation | Same: direct start or narrower investigation duration | Missing activity / duration evidence |
| T-406 | S1/profile possible violation | Clarify whether mobile timestamp means occurrence time or late data-entry time; obtain device sync telemetry and user action audit time | Semantic evidence plus synchronization evidence |
| T-407 | S1 and receipt-based profiles indeterminate | Receipt acknowledgement, message broker delivery receipt, correlated endpoint log, or causal ID proving actual Alert_Received time | Missing activity evidence / causal provenance |
| T-407 | Nominal negative receipt-to-start durations | Evidence that receipt precedes start, such as automated workflow transition or acknowledgement | Semantic/causal evidence |
| T-408 | InvestigationContainment profile possible violation at zeta=2 | No extra timestamp evidence is needed for SLA certainty; for profile certainty, choose zeta policy or obtain a more precisely defined profile distribution/boundary convention | Statistical-policy evidence |
| T-409 | S1 indeterminate | Actual NTP diagnostics for the hour, source clock trace, signed server timestamp, or a causal workflow record proving alert-before-start | Stronger synchronization and causal evidence |
| T-409 | S2/profile possible violation | Narrow the weak ±12-minute offset bound to approximately ±10 minutes or better; direct UTC timestamp is preferable | Stronger synchronization evidence |

Additional distinctions:

- **Synchronization evidence** resolves clock-offset uncertainty: NTP/PTP telemetry, signed server timestamps, device monotonic-clock mapping, source-side offset measurements.
- **Missing activity evidence** resolves absent lifecycle events: actual `Investigation_Start`, actual `Alert_Received`, acknowledgement records.
- **Duration evidence** resolves inferred-event uncertainty: a signed investigation start/end record, more precise duration certification, workflow-system timestamps.
- **Semantic evidence** resolves what a timestamp means: “entered at” versus “occurred at,” “sent” versus “received,” completion versus start, and whether causal ordering is legally enforceable.

For certain violations such as T-402 S1, T-405 S1, and T-408 S2/S3, better evidence may refine severity but is not needed to establish the stated conclusion under the declared bounds.

## 7. Governance Recommendation

### Timestamp and storage controls

1. Store all event timestamps in UTC with an ISO-8601 offset:
   - preferred: `2026-06-01T08:00:00.123456Z`;
   - retain original local representation separately.

2. Preserve raw source timestamps:
   - raw text;
   - source time zone;
   - offset from UTC;
   - DST fold where applicable;
   - precision/resolution;
   - parser assumptions.

3. Do not overwrite raw evidence with normalized timestamps or midpoint estimates.

4. Store timestamp uncertainty explicitly:
   - source resolution;
   - rounding or flooring semantics;
   - clock-offset confidence interval;
   - normalization method and version;
   - source synchronization status.

### Clock and synchronization controls

1. Require NTP/PTP monitoring for operational systems.
2. Retain offset telemetry at sufficient granularity to support incident reconstruction.
3. Alert on clock drift exceeding a defined operational threshold.
4. Use authenticated NTP or signed time attestations for external and mobile systems where feasible.
5. Mark evidence from sources lacking contemporaneous offset telemetry as lower-confidence.

### Time-zone and DST controls

1. Require explicit IANA time-zone identifiers, not only abbreviations such as CET/CEST.
2. Persist UTC offset at event creation.
3. Persist DST `fold` for ambiguous local times.
4. Reject or flag local timestamps in DST overlap periods when fold is absent.
5. Avoid relying on local wall-clock times for SLA enforcement.

### Lifecycle and event semantics

1. Define event lifecycle semantics explicitly:
   - Alert_Sent;
   - Alert_Received;
   - Alert_Acknowledged;
   - Investigation_Start;
   - Investigation_Complete;
   - Containment_Start;
   - Containment_Complete;
   - Close_Incident.

2. Distinguish:
   - occurrence time;
   - observation time;
   - recording/entry time;
   - ingestion time;
   - processing completion time.

3. For mobile/manual entries, capture both:
   - user-entered claimed occurrence time;
   - system capture/submit time;
   - device synchronization state.

4. Require workflow transitions to emit durable event IDs and causal identifiers linking:
   - sent message;
   - delivery;
   - receipt;
   - acknowledgement;
   - investigation action;
   - containment action.

### Provenance controls

For each event, retain:

- source system and host/device identity;
- actor or service identity;
- raw payload;
- ingestion timestamp;
- source timestamp;
- timezone and fold;
- clock-offset estimate and method;
- event precision;
- correction history;
- signature, hash, or tamper-evident log reference where applicable.

### Enforcement policy

Adopt an explicit interval-enforcement policy rather than silently using point timestamps.

Recommended policy:

| Interval result | Operational treatment |
|---|---|
| CERTAIN_PASS | Treat as compliant |
| CERTAIN_VIOLATION | Treat as established breach, subject to normal evidentiary review |
| POSSIBLE_VIOLATION | Flag for investigation; do not automatically impose legal/disciplinary consequences unless policy expressly permits risk-based enforcement |
| INDETERMINATE | Treat as evidential deficiency; require remediation of logging, synchronization, or semantics |

For legal or contractual SLA enforcement, interval overlap with a violation region should normally be insufficient by itself to establish a breach. It is sufficient to trigger review, evidence preservation, and source-quality remediation.

For operational risk management, the organization may choose a stricter policy: any possible violation triggers escalation. That should be documented as a risk-control policy, not misrepresented as proof of an SLA breach.
