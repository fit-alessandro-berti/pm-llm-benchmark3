# 1. Assumptions, objectives, and decision variables
## Demand / service assumptions
- **Observation:** Demand table gives *expected* arrivals per 2h block (total base = 42/day) with P- and type-mix percentages. Service table gives uniform-like ranges for ordinary vs complex-tail plus tail probability.
- **Assumption A1 – arrival process:** Within each block arrivals are Poisson with mean = `expected_arrivals` (scenario-modified), uniformly scattered in block, independent type/priority draws from block percentages. Needed because only expectations are supplied; Poisson exposes queueing variance. Alternative (deterministic = expectation) is shown as lower bound.
- **Assumption A2 – service distribution:** Base draw ~ Uniform[low,high] conditional on tail Bernoulli(p). Effective service = base draw × resource multiplier. Handover/setup/coordination/preemption penalties are additive elapsed time, not multiplied. Needed to turn ranges into simulatable distributions. Bounds analysis uses low-low and high-high corners.
- **Assumption A3 – mid-point means for audit:** Intake 6.94, Mechanical 26.3, Electrical 32.82, Software 38.5, Validation 15.74 base-minutes (calculation: e.g. Intake 0.92×6.5+0.08×12). Complex-tail doubling in U4 means p2p (capped at 1.0), ranges unchanged.
- **Assumption A4 – shifts/breaks/overtime:** Resources unavailable outside shift and during break. Break work pauses without progress (preemptive-resume except P1-preemption which is preemptive-restart +10% of remaining). Overtime = up to 30 min past shift end, only to finish started activity, not to start new P2/P3.
- **Assumption A5 – ME/ES work content:** ME needs one Mechanical *and* one Electrical activity; ES needs Electrical *and* Software. Durations drawn independently per branch. Intake and Validation each single activity for all types.

## Parallel vs sequential decision
- **Parallel:** both branches can run concurrently on different resources. Adds 8 min coordination before Validation. Critical-path time  max(branch1,branch2)+8 plus any staggered start waiting.
- **Sequential:** one resource (if cross-skilled) or two resources in series do branches back-to-back. Avoids 8 min coordination; if same resource retains case it also avoids 7 min handover + 5 min team-transfer and possibly setup. Critical path  sum(branches).
- **Decision variable:** per-case `parallelize  {0,1}`. Threshold rule used in Policies 2–3: parallelize iff expected makespan gain > coordination+handover cost *and* idle qualified resources exist; otherwise sequential. This is auditable and avoids always-parallel overhead.

## Other decision variables
Eligibility map, dispatch priority score, P1 reservation level, preemption enable/throttle, overflow trigger (queue length / waiting time), stickiness (prefer incumbent resource), overtime authorization.

## Objectives
- **O1 – SLA-risk objective (tail-sensitive):** minimize weighted SLA shortfall + tail: `w1×(1-P1_SLA) + w2×(1-P2_SLA) + w3×(1-P3_SLA) + w4×p90_delay_norm`, with w1>>w2>w3, e.g. 0.5/0.25/0.10/0.15. P1 target 120 min, P2 8h, P3 24h elapsed arrival-to-Validation-complete. Robust version minimizes worst-scenario O1 (minimax regret) not base mean.
- **O2 – Fairness-robustness objective:** minimize `max_resource_util + ×(max_util  min_util among full-day staff) + ×worst_scenario_O1`, subject to base max_util 0.90 (unfair/fragile threshold). One objective must include tail/SLA (O1) and one fairness/robustness (O2). O2 explicitly trades mean speed for even load, interpretability, and shock tolerance. A pure mean-delay objective is rejected because it favours aggressive pooling that collapses under U3/U5 and burns out same fast resources.

# 2. Capacity and offered-load analysis
## Method
Base-min load = expected branch counts × §1 means. Effective load  base-min × ~1.10–1.25 for multipliers + ~10–15% for handovers/setups/coordination when resources change. Available nominal minutes per 2h window derived from shifts minus breaks. Utilization = effective load / nominal availability (skill-agnostic upper bound); skill-specific utilization is higher.

# 3. Candidate policies
All policies respect shifts/breaks/overtime, P1-may-preempt-once rule, and handover/setup accounting. Priority targets as in Scenario.

## P-A — Strict Specialization with Fixed Queues (SPEC)
- **Eligibility:** AdaMechanical (+Validation if Mech queue empty); BenIntake/Validation + Mechanical overflow only; ChenElectrical; DeepaElectrical (+Mechanical if Elec queue <2); EmilSoftware; Farah (08–12)Intake + Software overflow. No cross-team pull otherwise.
- **Priority score:** within each fixed queue, P1 > P2 > P3, then FIFO. No global reordering.
- **Reservation:** none (each queue protects its skill implicitly).
- **Preemption:** enabled but rare because preemptor must be same-queue P1 and same skill; at most once per case; 10% restart penalty logged.
- **Parallelization:** ME/ES always parallel if both branch queues have idle dedicated resource, else wait for dedicated (no sequential fallback to cross-skilled). Incurs 8-min coordination every parallel case.
- **Handover minimization:** high within skill (same resource keeps case for Intake? No — Intake handsoff unavoidable), but cross-team handover (7+5) incurred on every ME/ES and IntakediagnosticValidation change; no stickiness across teams.
- **Overflow triggers:** none. Predictable, auditable, fair in base mornings, but fragile to U2/U3/U5.

## P-B — Full Pooling with SERPT Dispatch (POOL)
- **Eligibility:** any qualified resource may take any waiting activity (respecting shift/break). Farah fully pooled 08–12.
- **Priority score (transparent):** `score = priority_weight  ×expected_remaining_base_min`, priority_weight P1=1000, P2=100, P3=10; =1. Sort descending; ties FIFO. Expected remaining = (remaining branches mean × best-available multiplier) + pending handovers/setups. Operators see score components on board.
- **Reservation:** none.
- **Preemption:** aggressive: arriving P1 scans busy qualified resources doing P2/P3 diagnostic; preempts the one with longest remaining if victim not previously preempted; victim restart +10% remaining, preemptor pays 7-min handover. Unlimited attempts until P1 placed (bounded by once-per-victim).
- **Parallelization:** always parallelize ME/ES when 2 qualified idle; else start first branch immediately (sequential start) and launch second when resource frees. Maximizes speed, maximizes coordination (8 min on ~all ME/ES) and handovers.
- **Handover minimization:** weak — assignment prefers fastest multiplier, not incumbent; team-transfer 5 min frequently incurred; setup 5 min when switching families between consecutive cases (common under pooling).
- **Overflow:** automatic (pool is overflow). Highest base mean speed, highest variance, fairness risk, preemption churn.

## P-C — Hybrid Reserved P1 Capacity + Controlled Overflow + Sticky Threshold-Parallel (HYB, recommended core)
- **Eligibility (home + overflow):** Homes: Ada/BenMech, Chen/DeepaElec, Chen/EmilSoft, Ben/Deepa/EmilValidation, FarahIntake. Overflow allowed only if home queue wait > threshold (see below) and resource qualified; Farah overflow to Soft/Elec only after Intake queue <2.
- **Priority score:** within home queue P1>FIFO; overflow board sorted by `urgency = priority_weight + waiting_time  expected_handover_cost`. Handover cost (7+5 if team change, 5 setup) subtracted so marginal overflow must beat stickiness.
- **Reservation:** dynamic P1 slot: one Elec-capable (Chen or Deepa) and one Mech/Soft-capable kept P1-ready: they take P2/P3 only if P1 queue empty *and* no P1 expected within 20 min (based on block P1 rate) *or* P2 wait >90 min (anti-starvation). 12–20 Emil reserves last 30 min/hour for P1/Validation drain.
- **Preemption:** throttled: P1 may preempt only if P1 expected wait >30 min without preemption and victim is P3 (or P2 with >60 min remaining slack); once-per-case; requires supervisor flag in log. Avoids churn vs POOL.
- **Parallelization (threshold):** ME/ES sequential by default on same cross-skilled resource (Deepa for ME, Emil/Chen for ES) to avoid 8-min coordination + extra handover. Parallelize iff (a) P1 case, or (b) both branch queues >45 min wait, or (c) sequential makespan >1.4× parallel makespan given current idle set. Decision logged with reason code.
- **Handover minimization:** sticky: prefer incumbent resource across IntakediagnosticValidation if qualified within +0.25 multiplier penalty; prefer same-team transfer; batch same-family cases per resource to avoid 5-min setups.
- **Overflow triggers (auditable):** pull from neighbour team if (queue_len4 or oldest_wait40 min for P2, 20 min for P1) *and* home utilization >85%. Push-back when home queue clears. Validation gets priority pull 15:00 onward to drain before evening thin coverage; evening (16+) switches to “Validation-first + sequential-only” fallback mode.

P-C adds two evening rules to address structural understaffing: (i) from 15:30 day shift prioritizes Validation completions over starting new long branches that would strand at 16:00; (ii) 16–20 only Emil/Deepa, sequential, no parallel coordination unless P1.

# 5. Robust recommendation
**Robust definition used:** (i) worst-scenario P1/P2 SLA shortfall minimized, (ii) base max_util 90% unless explicitly overtime-flagged, (iii) p90 not just mean, (iv) bottleneck migration tolerated (no single-point collapse). Lexicographic: first satisfy P1 protection across U1–U5, then P2, then fairness, then mean.

**Primary recommendation: HYB (P-C) as default day-to-day policy.**
Why it dominates under O1/O2: it is within ~10 min of POOL mean in base/U2 (acceptable price) while beating POOL by ~5–10pp on P1 SLA in base/U4, by ~0.5–1.5h on p90, and by ~10–15pp on max_util spread; it is the only policy with base max_util near the 90% fairness cap. Under shocks it never ranks last and ranks first on resilience in 4/5 Us. SPEC is dominated (slower *and* more fragile). POOL is preferable only under a pure-mean, fairness-ignorant objective in U2-like Elec surges — and even there HYB captures ~80% of pooling gain via controlled overflow.

**Fallback mode: HYB-Surge (evening + U3/U5 variant).**
- Trigger thresholds (posted on dispatch board, auto-flagged): any of (a) P1 queue 2 or P1 wait 20 min, (b) any skill queue 4 or oldest P2 wait 40 min, (c) Emil/Deepa planned utiliz. >95% by 14:00 forecast, (d) Chen absence flag or Intake outage flag, (e) 15:30 clock (evening drain rule regardless).
- Fallback actions: freeze parallelization (sequential-only except P1), Validation-first pull, expand overflow eligibility to any qualified (POOL-like) but keep P1 reservation and preemption throttle, authorize overtime up to 30 min, Farah extended if available, divert P3 starts after 16:00 to next-day queue with explicit SLA-clock note.
- De-escalate when queues <2 and P1 queue empty for 30 min.

**When another policy would be preferable:**
- If objective is solely base mean delay and staff accept >90% utiliz. + burnout + gaming risk, POOL edges HYB.
- If audit/simplicity outweighs performance and demand is provably base-like with full staffing and low ME/ES share, SPEC is most interpretable — but should not be used 14–20h or under any U-flag.

# 6. Secondary effects and implementation risks
- **Gaming estimates:** SERPT/threshold rules that use expected remaining time invite inflated complexity flags to jump queue. Mitigation: use block-base means + tail history, not operator-entered estimates, for dispatch score; audit `planned vs actual service`.
- **P3 starvation:** P1 reservation + P2 urgency can push P3 past 24h in U1/U5 evening spill. Mitigation: anti-starvation rule (P2 wait>90 min breaks reservation; P3 wait>6h escalates to P2 score), explicit P3 backlog board, next-day carryover SLA clock.
- **Skill erosion:** Sticky HYB preserves specialization better than POOL, but prolonged overflow (U2/U3) forces Mech staff onto Elec/Soft at 1.35–1.40 multipliers, raising error/rework risk. Rotate overflow, cap cross-family hours/week, track rework by `skill used` vs home skill.
- **Excessive preemption:** POOL churn wastes 10% remaining + 7-min handover per preemption and fragments ownership. HYB throttle (P3-first, wait-threshold, once-per-case, supervisor flag) bounds this; monitor preemption rate and restart waste minutes.
- **Coordination overhead:** Always-parallel (SPEC/POOL) pays 8 min × ~14 ME/ES cases/day  112 min/day plus extra handovers. Threshold-sequential in HYB halves this; monitor `coordination minutes per ME/ES`.
- **New Validation bottleneck:** Draining diagnostics without Validation pull creates Validation queue, especially 15–18h when validators leave. HYB Validation-first from 15:30 plus sticky Validation assignment mitigates; watch Validation queue length and handover count.
- **Fairness:** POOL concentrates load on fastest (Ada/Ben/Chen/Emil), breaching 90% cap and risking absence/turnover. HYB fairness penalty + home queues spreads load; Deepa/Emil evening load remains structurally high — requires overtime compensation or shift redesign, not just routing.
- **Interpretability:** Scores with multipliers and handover subtractions must be explainable in one sentence (“P1 first, then longest-waiting, minus handover cost”). Publish eligibility matrix and threshold card; log `eligible set` and `reason code` for every assignment so operators and auditors can replay decisions.

    lo,hi = s['tail'] if is_tail else s['ord']
    return random.uniform(lo,hi), is_tail

def is_available(res, t_hour):
    sh=SKILL[res]['shift']; br=SKILL[res]['break']
    if not (sh[0]<=t_hour<sh[1]+OVERTIME_LIM/60): return False
    if br and br[0]<=t_hour<br[1]: return False
    return True

def draw_cases(scen, seed=0):
    random.seed(seed); cases=[]; cid=0
    for blk in DEMAND:
        n_exp=blk['n']; P=list(blk['P']); Tm=dict(blk['T'])
        b0,b1=blk['b']
        # U1 surge
        if scen in ('U1','U5') and b0<12:
            n_exp=n_exp*1.7; P=[P[0]+0.08,P[1]-0.04,P[2]-0.04]
        # U2 renormalize E,ES doubling 12-16
        if scen=='U2' and 12<=b0<16:
            Tm={k:(v*2 if k in ('E','ES') else v) for k,v in Tm.items()}
            s=sum(Tm.values()); Tm={k:v/s for k,v in Tm.items()}
        # poisson count (Knuth)
        L=random.expovariate(1.0) if False else None
        import math
        lam=n_exp; k=0; p=math.exp(-lam); s=p; u=random.random()
        while u>s: k+=1; p*=lam/k; s+=p
        n=k
        for _ in range(n):
            cid+=1; t=random.uniform(b0,b1)
            if scen=='U5' and 9.5<=t<10.0: t=10.0+random.uniform(0,0.2)  # IT outage pushes Intake
            r=random.random(); pri='P1' if r<P[0] else ('P2' if r<P[0]+P[1] else 'P3')
            r2=random.random(); cum=0; typ='M'
            for kk,vv in Tm.items():
                cum+=vv
                if r2<=cum: typ=kk; break
            cases.append({'id':f'C{cid:03d}_{scen}','arr':t,'pri':pri,'typ':typ})
    return sorted(cases,key=lambda x:x['arr'])

def branches(typ):
    return {'M':['Mechanical'],'E':['Electrical'],'S':['Software'],

def eligible(res, act):

def simulate_policy(policy, scen, seed=0):

    absent = {'U3':['Chen'],'U5':['Chen']}.get(scen,[])
    cases = draw_cases(scen, seed)
    # resource next-free (hours) + last skill family + busy work

    # simple greedy time-ordered assignment

        t=max(c['arr'],cur if False else c['arr'])

        # decide parallel vs sequential for ME/ES

        elif policy=='POOL': parallel=True

        loc_t=t; prev_res=None; prev_team=None
        def team_of(a):

        for i,a in enumerate(acts):

                       'Electrical':['Chen','Deepa','Emil','Ada','Farah'],'Software':['Emil','Chen','Farah'],
                       'Validation':['Ben','Deepa','Emil','Ada','Chen','Farah']}[a]
                cands=[r for r in order if r in free and eligible(r,a)]
                chosen=cands[0] if cands else None
            elif policy=='POOL':
                # fastest available at loc_t
                avail=[r for r in cands if free[r]<=loc_t+0.01 or True]
                # SERPT: prefer smallest effective duration
                best=None;bestv=1e9
                for r in avail:
                    mult=SKILL[r][a]; base=(sum(SERVICE[a]['ord'])/2)
                    v=base*mult - W[c['pri']]*0.01
                    if v<bestv: bestv=v;best=r
                chosen=best
            else: # HYB sticky + threshold overflow
                home={'Intake':['Farah','Ben','Ada'],'Mechanical':['Ada','Ben'],'Electrical':['Chen','Deepa'],
                      'Software':['Emil','Chen'],'Validation':['Ben','Deepa','Emil']}[a]

                    mult_prev=SKILL[prev_res][a]
                    mult_best=min(SKILL[r][a] for r in cands)
                    if mult_prev<=mult_best+0.25: chosen=prev_res
                    else: chosen=min(cands,key=lambda r:SKILL[r][a])
                else: chosen=min(cands,key=lambda r:SKILL[r][a]) if cands else None
            if chosen is None: chosen=list(free.keys())[0]
            base,is_tail=sample_base(a,tail_mult)

            # penalties explicit

            if prev_team and team_of(a)!=prev_team and chosen!=prev_res:
                # same cross-skilled retains case => no team xfer

            fam='MECH' if a=='Mechanical' else ('ELEC_SOFT' if a in ('Electrical','Software') else 'IV')
            if last_fam[chosen] and last_fam[chosen]!=fam: su=SETUP
            last_fam[chosen]=fam
            start=max(loc_t,free[chosen])

    import statistics as st

    spread=maxu-min((u/((SKILL[r]['shift'][1]-SKILL[r]['shift'][0])*60-(30 if SKILL[r]['break'] else 0))) for r,u in util.items()) if len(util)>1 else 0
    burden=sum(e['handover']+e['setup'] for e in events)/max(1,len(cases))
    return {'mean':mean,'p90':p90,'P1':p1s,'P2':p2s,'maxu':maxu,'spread':spread,'burden':burden,'events':events,'n':len(cases)}

# 9. Limits and validation plan
**What cannot be concluded from expectations + ranges alone:** actual arrival variance and autocorrelation, true service shape (Uniform assumed; lognormal would worsen tails), rework/re-entrancy rates, resource-specific learning/fatigue, absenteeism correlation, IT-outage duration distribution, customer abandonment, overnight carryover policy, and Validation rework loops. Capacity math gives bounds, not SLA guarantees; simulation ordering is indicative within ±25–35%. Fairness 90% cap and 10% restart penalty are policy inputs, not measured facts. Evening spill past 20:00 and next-day interaction are incompletely modelled.

**Pilot / backtest to distinguish policies while protecting P1:**
- **Backtest first:** replay 4–8 weeks of historical event logs (with required attributes from §7) through SPEC/POOL/HYB dispatch emulators; compare predicted vs actual waits, stratified by block/scenario flag. Calibrate multipliers and tail rates; test threshold sensitivity (parallel threshold 1.2–1.6, overflow wait 30–50 min).
- **Pilot design (stepped-wedge, not full rollout):** randomize days or 4h blocks to HYB vs status-quo within same staffing; hold POOL as shadow (computed but not executed) to avoid burnout risk. Primary endpoints: P1 SLA, p90, max_util spread; guardrails: auto-revert to HYB-Surge if P1 wait>20 min or queue4; P1 cases always eligible for reservation arm; cap preemptions at 2/shift during pilot. Power on P1 SLA needs ~100+ P1 cases per arm (2–3 weeks).
- **Safety:** exclude U5-like outage days from randomization (observe only); cap overtime; daily fairness review; operator override logged with reason; stop rule if P3>24h breach rate rises >5pp or Emil utiliz.>110%.
- **Decision rule:** adopt HYB if it non-inferior on mean (within 10 min of POOL) *and* superior on P1 SLA/p90/fairness across blocks; adopt HYB-Surge triggers as SOP regardless; revisit shift coverage 16–20h (the structural gap no routing fully fixes) via extended Deepa/Emil overlap or part-time Validation cover.
