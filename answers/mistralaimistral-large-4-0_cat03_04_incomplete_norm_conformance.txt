## 1. Conformance semantics

I distinguish seven classes of deviation:

- **Forbidden behavior**: an observed relation is explicitly disallowed by the norm. This is a closed-world judgment: if the relation is observed, it is noncompliant regardless of frequency. Examples: N3, T6, E10.
- **Missing mandatory behavior**: a mandatory relation is absent within its stated scope. This is closed-world only after scope and abstraction are confirmed. A missing directly-follows edge is not automatically a missing business obligation if the norm actually means “eventually” or if intermediate events are legitimate.
- **Unexpected but unregulated behavior**: an observed relation is not covered by the norm. Under open-world assumptions, absence from the norm is not noncompliance. Examples: `Validate Order -> Issue Invoice`, `Manual Compliance Review -> Customer`, `Package object_codeath Delivery`, `Reopen Order -> Close Order`.
- **Typical-pattern absence**: a typical relation is absent in some cases. This is not a violation because typical norms explicitly allow legitimate exceptions. Examples: N2, N5, T3.
- **Likely data-quality error**: the observed graph edge is suspected to be an artifact of extraction, identifier reuse, or join logic rather than a real business relation. Example: `Sensor Heartbeat -> Invoice`.
- **Abstraction mismatch**: the normative rule is stated at one abstraction level, but the observed summary uses another. The clearest case is N1: “eventually enter validation” is approximated by a directly-follows edge.
- **Insufficient evidence**: the summary lacks denominators, scope flags, or event-level detail needed to decide compliance.

Open-world versus closed-world matters because the norm is closed-world only for explicitly forbidden relations and for mandatory columns within their stated scope. Everywhere else, unmodeled behavior is permitted. Therefore, rare or unmodeled relations must not be escalated merely because they are absent from the normative edge set.

## 3. Detailed reasoning by model family

### OC-DFG

The OC-DFG model can establish directly-follows relations between lifecycle events for the same object type. It is useful for detecting forbidden sequences and for counting how often a normative sequence appears.

It cannot establish whether an intermediate event occurred, whether a relation is eventually satisfied, or whether an object was inside the stated scope. The summary uses directly-follows counts, but N1 is worded as “eventually enter validation.” That is an abstraction mismatch: an order with an unrecorded review event between `Create Order` and `Validate Order` would be counted as missing even though the business rule may be satisfied.

Counts and scopes matter. N1 has 98/100; the two missing orders are candidate violations only if they are standard orders and no intermediate review exists. N4 has 198/200 externally shipped packages; the two missing packages are candidate violations only if they were truly intended for external shipment and no intermediate event explains the gap. N3 is forbidden and directly observed twice, so it is a violation regardless of frequency. N2 and N5 are typical, so their absences are not violations. N6 is unspecified, so `Reopen Order -> Close Order` is unregulated.

The danger of interpreting an “eventually expected” rule as a directly-follows rule is that it creates false missing-mandatory findings. N1 explicitly says “eventually,” but the summary approximates it with directly-follows. The two missing orders may simply have an unrecorded review event. The same caution applies to N4 if packing and dispatch are not always adjacent.

### OTG

The OTG model can establish object-to-object interactions, cobirth, and codeath. It shows which object types participate together in events.

It cannot establish event type, sequence, or whether an interaction is required or forbidden without mapping back to event types. OTG weights alone do not provide denominators. For example, T1 is mandatory for an `Add Item` interaction, and the observed weight is 1450. That looks conforming only if the number of `Add Item` interactions is 1450. But ET-OT shows `Add Item -> Item` 1450 and `Add Item -> Order` 1448, which raises a cross-model inconsistency.

T2 is mandatory for a `Dispatch Package` interaction. OTG shows 200 `(Package, object_interaction, Delivery)` edges, which looks conforming. But ET-OT shows only 198 `Dispatch Package -> Delivery` edges, and the context says two dispatch events lack a Delivery relation. Thus the same business situation is conforming at the OTG abstraction and suspicious at the ET-OT abstraction. This is a strong signal of extraction inconsistency or abstraction mismatch.

T6 is forbidden and observed once. That is a violation. T3 is typical and observed 92 times, which is normal. T4 and T5 are unspecified, so their observed edges are unregulated. The seven `Package object_codeath Delivery` edges are also unregulated because the norm says nothing about codeath.

### ET–OT

The ET–OT model can establish which object types are bound to which event types. It is the right level for checking mandatory event-object bindings such as E1–E8.

It cannot establish object-to-object relations, sequence, or directly-follows behavior. A missing ET–OT edge may be a real process gap, a scope exclusion, or a data extraction problem.

E1, E3, E4, E5, and E7 appear conforming. E2 shows 1448 `Add Item -> Order` edges against 1450 `Add Item -> Item` edges, suggesting two `Add Item` events lack an Order relation. E6 shows 198 `Dispatch Package -> Delivery` edges, suggesting two dispatch events lack a Delivery object, though both have a carrier reference in an event attribute. E8 shows 92 `Record Payment -> Invoice` edges and one `Record Payment -> Payment` edge without an Invoice. Because the norm says the exception is only for events explicitly typed as unapplied cash, and none are so typed, this is a candidate missing mandatory behavior. E10 is forbidden and observed once, but the context strongly suggests a data-quality error from a reused numeric identifier.

A relation can be conforming at one abstraction and suspicious at another. `Dispatch Package -> Delivery` is missing at the ET–OT level, while the OTG shows 200 Package-Delivery interactions. `Add Item -> Order` is missing at the ET–OT level, while the OTG shows 1450 Order-Item interactions. These conflicts must be resolved before treating them as business violations.

## 6. Norm-completeness assessment

1. **N1 abstraction: “eventually” vs directly-follows.**  
   Operational risk: false missing-mandatory findings when intermediate events exist.  
   Clarification: state whether `Create Order -> Validate Order` is directly-follows or eventually-follows, and list allowed intermediate events.  
   Status: mandatory with explicit abstraction.

2. **N4 scope: “packages intended for external shipment” is undefined.**  
   Operational risk: the denominator cannot be verified, so missing pack->dispatch edges may be misclassified.  
   Clarification: define an attribute or rule that marks a package as intended for external shipment.  
   Status: mandatory within the defined scope.

3. **E8 unapplied-cash exception is not typed in the snapshot.**  
   Operational risk: legitimate unapplied cash is flagged as a violation.  
   Clarification: add an explicit event type or attribute for unapplied cash.  
   Status: mandatory with a typed exception.

4. **T2/E6 Delivery object vs carrier reference.**  
   Operational risk: dispatch events with a carrier reference but no Delivery object are flagged even though the shipment may be traceable.  
   Clarification: state whether a carrier reference satisfies the Delivery relation or whether a Delivery object is mandatory.  
   Status: mandatory if the object is required; otherwise typical or explicitly unspecified.

5. **OTG vs ET-OT count semantics.**  
   Operational risk: conflicting conformance signals, as seen for Add Item and Dispatch Package.  
   Clarification: define whether OTG weight counts events, object pairs, or interactions, and how it maps to ET-OT.  
   Status: explicitly unspecified or a data-quality rule.

6. **Identifier governance for E10.**  
   Operational risk: reused numeric identifiers create false forbidden edges.  
   Clarification: add an identifier uniqueness and join-integrity rule.  
   Status: forbidden for real sensor-invoice linkage; mandatory data-quality rule for identifier reuse.

7. **N2 and N5 typical exceptions are not enumerated.**  
   Operational risk: legitimate intermediate events or credit exceptions cannot be distinguished from drift.  
   Clarification: list allowed intermediate events for N2 and allowed credit exceptions for N5.  
   Status: typical.

8. **N6 `Reopen Order -> Close Order` is unspecified.**  
   Operational risk: reopened orders are ungoverned.  
   Clarification: decide whether reopen-close is allowed, forbidden, or typical.  
   Status: explicitly unspecified or typical.

9. **`Package object_codeath Delivery` is unregulated.**  
   Operational risk: simultaneous lifecycle end may be acceptable or may indicate a process defect.  
   Clarification: state whether codeath is acceptable for package-delivery confirmation.  
   Status: explicitly unspecified or typical.
