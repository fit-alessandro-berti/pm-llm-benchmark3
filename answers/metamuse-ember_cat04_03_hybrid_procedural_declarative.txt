# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

- **A1. Completed cases.** All test cases are treated as completed because each ends with `Close Onboarding`. Conformance of an in-progress case, which may not yet have reached an eventual response, would be reported as pending rather than definitively failed.
- **A2. Event order.** The sequence in a trace is the order of events. Timestamps are event times, treated as completion times for elapsed-time calculations. Equal timestamps would require a secondary sequence attribute; none is present.
- **A3. Risk is not logged.** No `risk_class` event or case attribute is available. The procedural model therefore infers the low-risk and high-risk routes from the approval activities, rather than verifying that `Classify Risk` actually produced the corresponding risk value.
- **A4. Clarification placement.** The backbone does not state where clarification occurs. The procedural tree places the clarification loop after the three checks and before `Classify Risk`, as in T2 and T5. Clarification after classification must be reviewed under DECLARE and the external deadline check, not automatically accepted by the tree.
- **A5. Escalation placement.** Sanctions escalation is modelled procedurally only in the high-risk escalated branch, again following T6 and T7. R7 allows escalation after screening more generally; the tree is therefore a conservative approximation.
- **A6. Resource identity.** Segregation of duties compares exact `org:resource` values. No role, team, delegate, or user-inheritance attribute is available.
- **A7. Activity semantics.** Performing an activity is not the same as its business outcome. For example, `Obtain Legal Opinion` does not prove that the opinion was favourable, and `Manager Approval` does not by itself identify an approval decision attribute.
- **A8. No post-activation activities in the tree.** `Change Bank Details`, `Suspend Vendor`, a second `Verify Bank Account`, and a later payment are deliberately excluded from the procedural backbone and handled by the external layer.
- **A9. Final outcome for clarification.** For the external R3 check, the final outcomes are `Reject Vendor`, first `Activate Vendor`, and `Close Onboarding`. A clarification request must be answered before the first of these following the request.
- **A10. Times are elapsed clock hours.** No business calendar, timezone, working-hours calendar, or service-level calendar is supplied.

## R5/R6 conflict

### Resolution A: strict R5, fail-closed

Whenever `Sanctions Escalation` occurs, `Obtain Legal Opinion` must occur before `Activate Vendor`. The event log cannot invoke an emergency exception. T6 is therefore non-conforming under the implemented model.

### Resolution B: conditional R6 emergency exception

Activation may precede the legal opinion only if:

1. joint authorization was given outside the log;
2. the opinion subsequently arrives within 24 hours.

The log does not contain the authorization. Timing can be checked, but authorization cannot. T6 has Activation at hour 13 and Legal Opinion at hour 23, a 10-hour gap, and Escalation at hour 6 to Legal Opinion at hour 23, a 17-hour gap. It satisfies both plausible 24-hour timing anchors, but that proves only a necessary condition, not the emergency exception.

### Resolution C: provisional activation

Activation is allowed procedurally but marked provisional, payment is held, and the case remains open until the opinion arrives. This is operationally attractive, but it creates a third state not described by either R5 or R6 and would require an explicit provisional status in the log.

## Chosen implementation

Resolution A is implemented as the authoritative automated policy, with the external layer returning `policy-dependent` for T6 rather than silently upgrading it to a pass. R5 says the opinion must precede activation “under all circumstances,” while the R6 authorization is not auditable from the log.

Compliance risk of this choice: a genuinely authorized emergency activation may be flagged as a failure and delayed. That is a business and operational risk. The opposite choice would be worse from a control perspective: anyone could activate before the opinion and later claim an unrecorded emergency authorization, making the sanctions control unauditable. The safe deployment path is fail-closed automation plus a documented manual override process that captures the authorization separately.

# 3. Procedural Backbone

## Formal description

```text
PT := SEQ(
  Receive Onboarding Request,
  AND(Capture Master Data, Run Sanctions Screening, Verify Bank Account),
  LOOP(SEQ(Request Clarification, Receive Clarification), tau),
  Classify Risk,
  XOR(
    SEQ(Reject Vendor, Close Onboarding),
    SEQ(Manager Approval, Activate Vendor, Release First Payment, Close Onboarding),
    SEQ(Enhanced Due Diligence, Compliance Approval, Activate Vendor,
        Release First Payment, Close Onboarding),
    SEQ(Sanctions Escalation, Enhanced Due Diligence, Obtain Legal Opinion,
        Compliance Approval, Activate Vendor, Release First Payment,
        Close Onboarding)
  )
)
```

## PM4Py code

```python
try:
    from pm4py.objects.process_tree.proc_model import ProcessTree, Operator
except ImportError:
    from pm4py.objects.process_tree.proc_model import ProcessTree
    from enum import Enum
    class Operator(Enum):
        SEQUENCE = "SEQUENCE"
        AND = "AND"
        XOR = "XOR"
        LOOP = "LOOP"

def leaf(label):
    return ProcessTree(label=label)

def node(operator, *children):
    return ProcessTree(operator=operator, children=list(children))

def seq(*children):
    return node(Operator.SEQUENCE, *children)

def par(*children):
    return node(Operator.AND, *children)

def xor(*children):
    return node(Operator.XOR, *children)

def loop(redo, exit_child):
    return node(Operator.LOOP, redo, exit_child)

tau = ProcessTree(label=None)

procedural_model = seq(
    leaf("Receive Onboarding Request"),
    par(
        leaf("Capture Master Data"),
        leaf("Run Sanctions Screening"),
        leaf("Verify Bank Account")
    ),
    loop(
        seq(
            leaf("Request Clarification"),
            leaf("Receive Clarification")
        ),
        tau
    ),
    leaf("Classify Risk"),
    xor(
        seq(
            leaf("Reject Vendor"),
            leaf("Close Onboarding")
        ),
        seq(
            leaf("Manager Approval"),
            leaf("Activate Vendor"),
            leaf("Release First Payment"),
            leaf("Close Onboarding")
        ),
        seq(
            leaf("Enhanced Due Diligence"),

            leaf("Release First Payment"),
            leaf("Close Onboarding")
```

## Explanation

- **Concurrency:** `AND` permits any interleaving of Capture, Screening, and Verify. This explains T2 and T3, where the order of the three checks differs.
- **Choice:** The final XOR selects exactly one of rejection, Manager route, ordinary high-risk route, or escalated high-risk route. This is the authoritative encoding of R2 within the backbone.
- **Clarification loop:** The LOOP redo part is a complete Request/Receive pair and the exit is silent. It therefore permits zero or more complete pairs, but not an unpaired request, because the loop cannot exit in the middle of the redo sequence.
- **Escalation approximation:** The escalated branch places Escalation after Classify and Legal Opinion before Compliance and Activate. This encodes strict R5, but it does not allow escalation in a low-risk or rejected case. That restriction is an explicit block-structured approximation; DECLARE and the external check remain more general for R7 and R4.
- **Terminal outcomes:** Every XOR branch ends with `Close Onboarding`. No activity is allowed after Close.
- **Post-activation behaviour:** `Change Bank Details`, `Suspend Vendor`, re-verification, and a later payment are excluded. Including them in the main tree would require a post-activation loop and would conflict with the at-most-once Release rule, as discussed in Section 9.
- **Risk limitation:** The tree cannot verify that Classify Risk actually selected the low or high route, because no risk attribute is present.

# 4. DECLARE Model

DECLARE direction conventions used here are:

- `response(A, B)`: if A occurs, B must occur later.
- `precedence(A, B)`: if B occurs, A must have occurred earlier.
- `succession(A, B)`: both directions are required.
- `altresponse(A, B)`: each A must be responded to by B before the next A.
- `noncoexistence(A, B)`: A and B must not both occur, in either order.

Not used are `chainresponse`, `chainprecedence`, and `chainsuccession`, because immediate adjacency is not generally required. `nonsuccession` and `nonchainsuccession` are weaker than the required exclusions: for example, nonsuccession could forbid Reject after Activate while still allowing Activate after Reject. `coexistence` is not used because co-occurrence alone would permit the wrong order. `absence` is not used because no activity is universally forbidden.

# 5. Log-Skeleton Model

The orientation used here is:

- `always_before(A, B)`: if B occurs, A must occur before B.
- `always_after(A, B)`: if A occurs, B must occur after A. This is the inverse of `always_before(B, A)`.
- `never_together(A, B)`: A and B do not co-occur.
- `equivalence(A, B)`: A and B co-occur.
- `directly_follows(A, B)`: A is immediately followed by B. No such adjacency is asserted.

`always_after` is left empty because it would be exactly the inverse of `always_before` and would duplicate the same constraints. For example, the inverse of `always_before(Activate, Release)` would be `always_after(Release, Activate)`.

`directly_follows` is empty because none of the normative requirements fixes immediate adjacency. In particular, EDD is not directly followed by Compliance in T7 because Legal Opinion intervenes.

The skeleton overlaps DECLARE precedence, succession, and noncoexistence, but it cannot express response or alternate response. A pair such as `always_before(Request Clarification, Receive Clarification)` would mean Receive requires a prior Request, not that Request requires a later Receive. Consequently, the skeleton passes T5 even though the clarification is unanswered. It also cannot express conditional Legal-before-Activate, so it passes T6.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}

zeta = 2.0
```

The corresponding elapsed-time intervals are:

| Pair | Mean | Standard deviation | Mean ± 2 standard deviations |
|---|---:|---:|---:|
| Request Clarification  Receive Clarification | 48 h | 24 h | 0 h to 96 h |
| Sanctions Escalation  Obtain Legal Opinion | 12 h | 6 h | 0 h to 24 h |
| Activate Vendor  Release First Payment | 72 h | 36 h | 0 h to 144 h |

Pair matching is first-target-after-source, in trace order. If no target follows a source, the temporal result is `not evaluated`, not a pass. This matters in T5 and T8.

Temporal deviations are warnings because R12 calls them expectations to flag. A mean and standard deviation do not establish a hard deadline, the underlying distributions are not supplied, and the large standard deviations make the intervals broad. Business calendars and clock-hour versus working-hour distinctions are also unavailable. A case can therefore satisfy precedence while receiving a temporal warning, as in T7, where Legal Opinion is late relative to Escalation but still precedes Activate.

# 7. Resource- and Data-Aware Checks

## Required attributes

- Case identifier.
- `concept:name` for the activity.
- `time:timestamp` for ordering and elapsed times.
- `org:resource` for segregation of duties.
- `emergency_joint_authorization` for R6, either as a case attribute or as an attribute on the Activate event.

If `org:resource` is missing, the segregation check returns `not evaluated` and generates a data-quality warning; missing identity must not be treated as “different people.” If timestamps are missing, event order is used for precedence, but elapsed-time and 24-hour checks return `not evaluated`. If the emergency authorization attribute is missing, R6 cannot be verified.

```python
import pm4py

FINAL_OUTCOMES = {"Reject Vendor", "Activate Vendor", "Close Onboarding"}
APPROVALS = {"Manager Approval", "Compliance Approval"}

def event_name(event):
    return event.attributes.get("concept:name")

def event_resource(event):
    return event.attributes.get("org:resource")

def event_time(event):
    return event.attributes.get("time:timestamp")

def last_index_before(events, index, activity):
    for j in range(index - 1, -1, -1):
        if event_name(events[j]) == activity:
            return j
    return None

def check_four_eyes_pairwise(trace):
    events = list(trace)
    findings = []
    for i, event in enumerate(events):
        if event_name(event) in APPROVALS:
            verify_index = last_index_before(events, i, "Verify Bank Account")
            if verify_index is None:
                findings.append(("not_evaluated", i, "No preceding Verify Bank Account"))
            elif event_resource(event) is None or event_resource(events[verify_index]) is None:
                findings.append(("not_evaluated", i, "Missing org:resource for four-eyes check"))
            elif event_resource(event) == event_resource(events[verify_index]):
                findings.append(("fail", i, "Verify and approval performed by same resource"))
        if event_name(event) == "Activate Vendor":
            capture_index = last_index_before(events, i, "Capture Master Data")
            if capture_index is None:
                findings.append(("not_evaluated", i, "No preceding Capture Master Data"))
            elif event_resource(event) is None or event_resource(events[capture_index]) is None:
                findings.append(("not_evaluated", i, "Missing org:resource for four-eyes check"))
            elif event_resource(event) == event_resource(events[capture_index]):
                findings.append(("fail", i, "Capture and Activate performed by same resource"))
    return findings

def check_emergency_legal_policy(trace):
    events = list(trace)
    escalation = [i for i, e in enumerate(events) if event_name(e) == "Sanctions Escalation"]
    legal = [i for i, e in enumerate(events) if event_name(e) == "Obtain Legal Opinion"]
    activate = [i for i, e in enumerate(events) if event_name(e) == "Activate Vendor"]
    if not escalation or not activate:
        return ("pass", None, "R5 is conditional on Escalation and Activate")
    if not legal:
        return ("fail", activate[0], "Escalation without later Legal Opinion")
    legal_index = legal[0]
    activate_index = activate[0]
    if legal_index < activate_index:
        return ("pass", legal_index, "Legal Opinion precedes Activate")
    legal_time = event_time(events[legal_index])
    activate_time = event_time(events[activate_index])
    escalation_time = event_time(events[escalation[0]])
    authorization = trace.attributes.get("emergency_joint_authorization")
    if authorization is None:
        authorization = events[activate_index].attributes.get("emergency_joint_authorization")
    if legal_time is None or activate_time is None or escalation_time is None:
        return ("not_evaluated", activate_index, "Missing timestamps for 24-hour R6 check")
    activation_to_legal_hours = (legal_time - activate_time).total_seconds() / 3600.0
    escalation_to_legal_hours = (legal_time - escalation_time).total_seconds() / 3600.0
    if authorization is not True:
        return ("policy-dependent", activate_index, "R6 timing may pass, but joint authorization is not in the log")
    if activation_to_legal_hours <= 24.0 and escalation_to_legal_hours <= 24.0:
        return ("policy-dependent", activate_index, "R6 exception is supported by timing and logged authorization; governance review still required")
    return ("fail", activate_index, "Legal Opinion is outside the 24-hour R6 window")

def check_clarification_deadline(trace):
    events = list(trace)
    for i, event in enumerate(events):
        if event_name(event) != "Request Clarification":
            continue
        answered = False
        for j in range(i + 1, len(events)):
            if event_name(events[j]) == "Request Clarification":
                break
            if event_name(events[j]) in FINAL_OUTCOMES:
                break
            if event_name(events[j]) == "Receive Clarification":
                answered = True
                break
        if not answered:
            return ("fail", i, "Clarification not answered before next request or final outcome")
    return ("pass", None, "All clarification requests answered before next request or final outcome")

def check_post_activation(trace):
    events = list(trace)
    activate = [i for i, e in enumerate(events) if event_name(e) == "Activate Vendor"]
    if not activate:
        return ("not_evaluated", None, "No activation")
    findings = []
    for change in [i for i, e in enumerate(events) if event_name(e) == "Change Bank Details" and i > activate[0]]:
        suspended = any(event_name(events[j]) == "Suspend Vendor" for j in range(change + 1, len(events)))
        if not suspended:
            findings.append(("fail", change, "Change Bank Details without later Suspend Vendor"))
        for release in [i for i, e in enumerate(events) if event_name(e) == "Release First Payment" and i > change]:
            reverified = any(event_name(events[j]) == "Verify Bank Account" for j in range(change + 1, release))
            if not reverified:
                findings.append(("fail", release, "Later Release without re-verification after Change Bank Details"))
    return findings

def resource_data_layer(log):
    results = {}
    for trace in log:
        case_id = trace.attributes.get("case:concept:id", "unknown-case")
        result = {
            "four_eyes_pairwise": check_four_eyes_pairwise(trace),
            "emergency_legal_policy": check_emergency_legal_policy(trace),
            "clarification_deadline": check_clarification_deadline(trace),
            "post_activation": check_post_activation(trace)
        }
        results[case_id] = result
    return results
```

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement

Precedence appears in the tree, DECLARE, and skeleton. Noncoexistence appears in DECLARE and skeleton. Occurrence counts appear in the tree, `exactly_one`, and `activ_freq`. Duplication is useful for explanation and mining, but the dashboards must identify one authoritative layer per requirement; otherwise, one violation may be counted several times as if it were several independent failures.

## Loops and post-activation changes

The clarification loop requires complete pairs, while a skeleton `directly_follows` rule could incorrectly require adjacency. The model therefore leaves `directly_follows` empty.

Post-activation behaviour creates a deeper conflict. R10 allows Release at most once, but R11 speaks of a later Release after re-verification. If the first Release has already occurred, the later Release violates R10. If Change occurs between Activate and the first Release, R11 can be read as requiring re-verification before that first Release. The external check can detect either pattern, but the requirements need clarification.

A Verify after a bank change would also break a hypothetical rule requiring every Verify to be followed by Classify. That is why the model uses existence for Verify rather than claiming that every Verify is part of the initial parallel block.

## Vacuity

DECLARE response and precedence are vacuously satisfied when their triggering activity is absent. T3 passes approval-related rules because there is no approval. T1 passes Escalation rules because there is no Escalation. Skeleton equivalence is similarly vacuous when both activities are absent. High aggregate conformance percentages can therefore conceal the fact that a rule was never activated. Reports should distinguish fulfilled, violated, and vacuous rules.

## Conditional rules that basic formalisms cannot express

Conditional Legal-before-Activate is the central example. Unconditional DECLARE precedence would require Legal Opinion before every Activate and would falsely fail T1 and T2. A similar issue applies to “exactly one approval if accepted”: the outcome is known only later in the trace, while DECLARE has no conditional XOR template. The procedural XOR and external checks are needed for these conditional forms.

## Missing case attributes

The log lacks risk class, emergency authorization, approval decision, legal-opinion outcome, bank-verification result, required approver role, and case-level SLA attributes. Consequently:

- low versus high risk cannot be validated against Classify;
- R6 cannot be verified;
- an activity named Approval cannot be distinguished from a rejected approval event;
- obtaining an opinion cannot be distinguished from obtaining a suitable opinion.

## Timestamp-only limitations

Temporal evaluation assumes that the event timestamp is the relevant completion time. There are no lifecycle transitions, working calendars, time zones, or multiple-instance identifiers. With repeated Clarification or Escalation activities, FIFO pairing is an assumption. Equal timestamps also make order ambiguous.

## Support and confidence are not normative truth

The DECLARE dictionary sets `support` to 1.0 because these are policy assertions, not because the support was learned from a log. `confidence` records modeler confidence in the interpretation. Neither value should be averaged into a compliance score. A frequently violated rule remains normative, and a rare but compliant path remains compliant.

# 10. Deployment Recommendation

## Canonical representation and authority

The ProcessTree in Section 3 should remain the canonical procedural representation because it is human-readable, executable in PM4Py, and directly represents concurrency, choice, loops, and terminal outcomes. It should not be the sole authority for all requirements.

The policy registry should identify the authoritative layer for each requirement, using the mapping in Section 2:

- procedural tree for the backbone and accepted-case XOR;
- DECLARE for flexible response, precedence, succession, and exclusion rules;
- Log Skeleton for occurrence counts and pairwise mined or asserted relations;
- temporal profile for warnings;
- resource/data layer for segregation, conditional Legal-before-Activate, emergency policy, clarification deadlines, and post-activation checks.

DECLARE and Log Skeleton models should be generated or reviewed from that registry rather than maintained as independent hand-edited sources.

## Check order

1. **Data completeness:** case ID, activity, timestamp, and resource presence. Missing required attributes produce `not evaluated`, not `pass`.
2. **Procedural replay:** identify the earliest structural deviation and the fitting branch.
3. **Resource/data checks:** segregation, conditional R5/R6, clarification deadline, and post-activation obligations.
4. **DECLARE conformance:** report fulfilled, violated, and vacuous rules separately.
5. **Log Skeleton conformance:** report count, ordering, and exclusion failures.
6. **Temporal profile:** report warnings only after the hard control-flow and resource checks.

## Surfacing contradictory findings

The user interface should show the full layer matrix for each case, the earliest decisive violation, and the authoritative requirement owner. It should not average layer scores.

- `fail` means a normative rule is violated under the chosen policy.
- `warning` means a temporal expectation is deviated from but the case is not automatically rejected.
- `policy-dependent` means the log cannot decide the case, especially T6 without external authorization evidence.
- `not evaluated` means the relevant activity, pair, or attribute is absent; it must not be displayed as positive compliance.

For T6, the interface should state both outcomes explicitly: fail under strict R5, and conditional pass under R6 only if credible joint-authorization evidence is added. Urgent cases should enter a documented human override workflow rather than being silently reclassified.

Finally, the event schema should be extended prospectively with `risk_class`, `emergency_joint_authorization`, approval decision, legal-opinion outcome, and a business-calendar identifier. Until those attributes exist, the hybrid design must preserve the distinction between what the activities show and what the business policy actually requires.
