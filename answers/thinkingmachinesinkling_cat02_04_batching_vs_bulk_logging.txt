```python
def overlap_rate(intervals):
    # intervals: list of (start, end)
    n = len(intervals)
    if n < 2:
        return 0.0
    overlap = 0
    for i in range(n):
        for j in range(i+1, n):
            s1, e1 = intervals[i]
            s2, e2 = intervals[j]
            if max(s1,s2) < min(e1,e2):
                overlap += 1
    return overlap / (n*(n-1)/2)
```

```python
# Overlap rate per resource
def resource_overlap(sub):
    # sub: DataFrame for one resource with start/complete
    intervals = list(zip(sub['start'], sub['complete']))
    n = len(intervals)
    if n < 2:
        return 0.0
    overlap = 0
    for i in range(n):
        s1, e1 = intervals[i]
        for j in range(i+1, n):
            s2, e2 = intervals[j]
            # Overlap if intervals intersect with positive length
            if max(s1, s2) < min(e1, e2):
                overlap += 1
    total_pairs = n*(n-1)/2
    return overlap / total_pairs if total_pairs > 0 else 0.0
```

# 5. Robustness and alternative explanations

**Resource-ID trust vs. shared-account treatment**

- *If resource IDs are trusted literally*: `G5` (`analyst_pool`) is interpreted as one person performing 4 overlapping tasks, implying impossible multitasking (>100% load for 13:10–13:20) and severe overload. This biases utilization upward and misplaces the bottleneck onto a single phantom worker.
- *If treated as shared-account artifacts*: The same temporal pattern supports distributed work among up to 3 analysts. Utilization should then be computed at the pool level or disaggregated by session; without disaggregation, per-resource metrics remain ambiguous. This is the defensible interpretation given the explicit context.

**Exact timestamps vs. interval-censored by stated precision**

- *G1 and G2 (1 sec / 1 min)*: At exact values, equality is strong. If interval-censored (e.g., ±0.5 sec or ±30 sec), the start equality in G1 could hide micro-stagger, but 3-min coincidence still favors batching. In G2, minute-level censoring could hide stagger up to ~30 sec, but the spread of ends (6–19 min) is well outside censoring, supporting sequential or group processing.
- *G7 (15 min)*: Treating 14:00 and 14:15 as exact gives false precision. Under interval-censoring (e.g., true start in [13:52.5, 14:07.5]), the apparent equality collapses, and true durations could vary widely. This eliminates false synchronization and requires interval-based waiting/service estimates.
- *G6 (1 min, but start=complete)*: Even with ±30 sec censoring, the interval is essentially zero; the near-zero service artifact is robust to censoring.

**Three cases where the same temporal pattern supports multiple physical explanations**

1. **G1 (all start/end equal):** Could be (a) a 4-slot fixture processing items together, (b) rapid serial execution hidden within 1-sec resolution, or (c) four separate automated cells mistakenly mapped to the same resource ID. The pattern alone cannot distinguish fixture batching from resource mislabeling.
2. **G2 (shared start, spread ends):** Supports (a) a group-start button followed by sequential inspections, (b) concurrent inspections with a shared initiation event but individual completions, or (c) one worker logging a group start once and finishing items one by one. The spread of ends favors (a) or (c) over pure concurrency.
3. **G6 (all 17:00):** Could be (a) a true simultaneous bulk closure event (7 people closing together), (b) a single bulk-form entry of work completed at various earlier times, or (c) an automated end-of-shift sweep that stamps all open tickets. The source name (`manual_bulk_form`) and queue spread strongly favor (b).

# 6. Data-collection redesign

Prioritized by impact on batch detection, queue analysis, and resource metrics:

1. **Execution timestamps (workstation-level)** — Capture true `start` and `complete` at the device/workstation, not via bulk forms or post-hoc submission. Prevents G3-style bulk-submission artifacts and G6-style zero-duration entries.
2. **Resource / badge identity** — Eliminate shared accounts (`analyst_pool`). Require individual badge or session token for every event (`G5`). Enables correct per-resource utilization and overlap detection.
3. **Source clock synchronization** — Synchronize queue, scanner, tablet, desktop, legacy MES, and safety-system clocks to NTP. Document and log offsets (`G8`). Prevents false gap/delay interpretation.
4. **Explicit group / batch identifiers** — Add `fixture_id`, `group_id`, or `batch_id` fields (`G1`, `G2`, `T-B` screen). Removes need to infer batches solely from timestamp equality.
5. **Pause / resume and downtime events** — Log safety checks, maintenance, and capacity losses (`G8`) as explicit resource-unavailable intervals with start/end. Allows exclusion or adjustment in waiting-time calculations.
6. **Workstation capacity and occupancy** — Record fixture slots used (`G1`: 4/4), screen availability (`T-B`), and scanner status. Distinguishes physical concurrency from logging artifacts.
7. **Timestamp precision metadata and rounding rules** — Document not only nominal precision but actual resolution and any applied rounding (`G7`). Prohibit undocumented rounding; if rounding is required, store both raw and rounded values.
8. **Separate recording and event timestamps** — Keep `recorded_at` (database insertion) distinct from execution time (`G1`–`G8`). Use `recorded_at` for data-quality audits, not for service-time computation.

# 7. Final adjudication

**High-confidence interpretations (use with minor correction)**
- **G1:** Fixture batching; correct as simultaneous batch. Apply batch-level resource-time accounting.
- **G4:** Accurate sequential pipeline; minimal bias. Safe for standard queue/service/utilization analysis.
- **G6:** Bulk-form artifact; interpretation is highly confident, but the *physical execution* is unknown. Must **not** be used for service-time or per-case waiting-time analysis without validation.

**Exclude or interval-censor in queue/service analysis**
- **G6:** **Exclude** from point-estimate service/wait analysis (service  0, wait artificially inflated). If retained, treat both start and complete as interval-censored near 17:00 and queue-to-start as censored over the workday.
- **G7:** **Interval-censor** all start/end values within ±7.5 min (15-min rounding). Do not compute precise durations or rank tasks by service time.
- **G8:** **Adjust for downtime**; if clock alignment is unverified, interval-censor the first-start gap and treat wait times as bounded (e.g., lower bound after 15:35, upper bound using raw 15:00). Service times are usable.
- **G5:** **Exclude from individual-resource metrics**; include only at pool level or after disaggregation. Overlap-based utilization is invalid for a single worker.

**Require operational validation before any performance conclusion**
- **G2:** Validate whether `start` for S02–S04 reflects true task initiation or only group initiation. Without individual start logs, service and wait for later cases are unreliable.
- **G3:** Validate actual review-completion times (e.g., per-item form fields or audit logs). Bulk submission at 11:30 hides true finish spread.
- **G5:** Validate badge-level assignment for A01–A04. Without it, concurrent vs. interleaved vs. multitasking cannot be resolved.
- **G8:** Validate clock offset between queue system and scanner, and confirm mapping of the 15:00–15:35 safety-check event. Without this, the 38-min initial gap is uninterpretable.

**General recommendation:** Use `G4` as the baseline for unbiased sequential metrics; use `G1` for batch-capacity studies (with corrected resource accounting); treat `G6` and `G7` as data-quality case studies rather than performance data; and resolve identity, clock, and logging semantics for `G2`, `G3`, `G5`, and `G8` before drawing bottleneck or utilization conclusions.
