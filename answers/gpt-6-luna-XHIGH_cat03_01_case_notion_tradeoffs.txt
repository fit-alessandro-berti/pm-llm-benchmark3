## 1. Analytical assumptions

A case notion chooses an object type whose individual objects define the traces in a conventional event log. An event directly related to several objects of that type is copied into each such object's trace. Convergence means multiple objects or process strands meet at a shared object or event (for example, two orders sharing a package or invoice). Divergence means one business object or order's work is split across multiple objects or traces, as with O1 using P1 and P2. These are structural properties, not automatically defects.

A copied shared event is both evidence and duplication: it evidences that each case object participated in the one recorded event, but each copy is not another occurrence. Thus, event counts, variant counts, and DFG frequencies in a flattened log must not be read as counts of independent executions without qualification. Direct E2O links are the baseline. I would not silently propagate them through O2O links. For a separate analytical view, I would permit explicit, provenance-preserving propagation along named qualifiers (for example Order contains Item, Package packs Item, Delivery carries Package), deduplicate by original event ID for occurrence counts, and compare it against the direct-relation result. Invoices and payments need their own business rules; graph reachability alone should not imply that every event of an associated object belongs to every related order.

## 3. Concrete distortion analysis

1. **Order flattening, P3 cross-order pack (e13; O2/O3).** The one Pack Package event appears in both order traces. A DFG can count the same pack occurrence twice and make Add Item→Pack Package support look like two executions. This is harmful for occurrence-frequency claims, but informative that the operation joins items from two orders.

2. **Order flattening, P4 cross-order pack (e14; O3/O4).** The same effect occurs for O3 and O4, while O3 also has e13. O3's trace has two shared pack events and can look like a longer or more complex packing path than O2/O4. That is informative about O3's split handling, but comparing raw DFG frequencies or cycle times as if each event were independent is misleading.

3. **Package flattening, cross-order contents (P3/P4; e13/e14).** P3's trace joins O2's I21 and O3's I31; P4 joins O3's I32 and O4's I41. A Package→Dispatch→Confirm path is valid for package handling, but it hides which order/item strand is delayed. If used to infer order variants, a single package variant wrongly stands in for multiple orders. This is context-dependent: useful for package operations, harmful for order attribution.

4. **Delivery and package flattening, consolidated D2 (e16/e24).** D2 carries P2 and P3 and directly names O1/O2/O3. On package flattening, e16/e24 are copied to both P2 and P3; on order flattening, they are copied into three order traces. One dispatch and confirmation can therefore contribute two package cases and three order cases. The D2 interval itself is informative, but these copies inflate counts if read as separate dispatches/deliveries.

5. **Invoice flattening, consolidated V2 (e19/e22/e25; O2/O3).** V2 is one invoice covering two orders. The invoice trace correctly has one issue and two payment events; the order projection places each of these events in both O2 and O3. This can make order DFGs report two Issue Invoice events and two instances of each payment across the pair, though there was one invoice and one occurrence of each payment. It is informative about association, but not evidence of duplicated billing.

6. **Order flattening, partial settlement (e22/e25; M2/M3).** Both O2 and O3 directly relate to the partial-payment event e22 and completion event e25. Each order appears to have an Issue Invoice→Record Payment→Record Payment sequence. Without amount allocation, one cannot tell whether either order was individually partially settled; the semantics are that M2 partially settles shared V2 and M3 completes V2. Counting per-order payment sequences as independent settlements is harmful; retaining the shared invoice/payment links is essential.

7. **Item flattening, truncated lifecycle (e05–e10 through item handling, compared with e18–e31).** Items participate in Add Item, some pack/dispatch/confirmation events, but no Invoice, Record Payment, or Close Order event directly names an item. For example, I21 can show e07/e13/e16/e24, then stop, although O2 has e19/e22/e25/e29. A short trace or apparent end after delivery is a projection boundary, not proof that the item or order process ended there. This is harmful for lifecycle completeness, while still useful for physical-handling elapsed time.

8. **Payment flattening, near-singleton lifecycle (M1–M4; e21/e22/e25/e26).** Each payment case has exactly one Record Payment event. A discovered DFG has no within-case edge, and duration from first to last event is zero/undefined. This is a structural truncation, not a fast process or a one-step settlement lifecycle. Transaction-level counts are useful; conformance, variants, and cycle-time conclusions are not.

9. **Delivery flattening, almost deterministic DFG (D1–D3).** Each delivery has Dispatch→Confirm Delivery and only two directly related events. The apparent 100% edge frequency follows from the event model and tiny sample, rather than demonstrating that all order fulfilment follows this control flow. The three transit times differ (3h, 4h55m, 22h45m), which is a useful delivery-level signal but not order completion time.

10. **Order flattening, shared events make variants look more alike (e16/e24 and e19/e22/e25).** O2 and O3 have the same explicitly shared D2 and V2 events, so their sequences can converge in a DFG or variant summary even though O2 has one item/package strand and O3 spans P3/P4 and D2/D3. The shared pattern is evidence of common infrastructure; it masks distinct item and delivery composition if treated as complete behavioral equivalence.

## 4. Traditional versus object-centric analysis portfolio

I would create Order, Item, Package, Delivery, Invoice, and Payment projections as named, purpose-specific views, retaining original event IDs and a flag for copied rows. Order is the most useful conventional overview for create-to-close and explicit order-linked work. Item is for handling milestones; Package is for pack-to-confirm transit; Delivery is for dispatch-to-confirm transit; Invoice is for issue and settlement sequence; Payment is for transaction counts and attributes, not DFG lifecycle discovery. Every view should report both projected row counts and distinct original event counts.

Questions about which orders share packages, deliveries, or invoices need the OC-DFG plus the object interaction summary; those preserve co-participation better than a single case projection. The OTG is suited to the structural paths O1→I11/I12→P1/P2→D1/D2 and O2/O3→P3→D2 and O3/O4→P4→D3. The ET–OT graph helps show that e13/e14/e16/e19/e22/e25 link several orders or object types, and distinguishes an event's participation pattern from its case-copy count. Equivalent-execution clustering can be used exploratorily to group object traces under an explicitly chosen object type and relation policy, but it cannot establish that two orders, packages, or invoices are semantically interchangeable. I reject one lead type, so I would not use clustering to crown a single lead.

When views disagree, first ask whether they count original events, object-event relations, or projected rows; then inspect the event IDs and relations. For example, an Order DFG may count e16 three times while the OC-DFG records one dispatch event connected to three orders and D2. Report the order-local participation and the unique event count side by side. Treat differences caused by direct versus propagated relations as alternative assumptions, not as evidence that one view has repaired the other.

## 5. Lead-object decision

**C. Reject a single lead object for this process.**

- **Decision criteria:** A lead should preserve the question's required lifecycle, avoid treating shared events as independent, and represent both split and consolidated work. No object type here meets all three criteria.
- **Strongest supporting evidence:** Orders alone have explicit creation and closure (e01–e04, e28–e31), but O1 splits across P1/P2, O3 across P3/P4 and D2/D3, P3/P4 cross order boundaries, D2 consolidates three orders, and V2 consolidates O2/O3. Item, package, delivery, invoice, and payment cases each omit material parts of the wider process; payment cases are singletons.
- **Strongest counterargument:** Order is the most plausible primary case because its traces span Create Order to Close Order and include many downstream events. For a management question specifically defined as “order lead time,” selecting Order is defensible and likely more interpretable than the other five projections.
- **Residual risk:** Without a stated allocation policy, even an object-centric view cannot attribute V2's instalments or shared package/delivery delays to individual orders. Direct E2O projections may also omit events that business users intuitively associate through O2O relations.
- **Change conditions:** I would choose Order as a primary lead with secondary package/delivery/invoice lifecycles if the decision goal were explicitly order lead time and the business accepted shared-event attribution. I would choose Package or Delivery for a transport SLA, Invoice for settlement SLA, or Item for item-handling performance if the goal were narrowed accordingly and completeness limits were accepted.

## 6. PM4Py analysis outline

```python
import pm4py

# Assumes `ocel` is already loaded as a PM4Py OCEL. Keep direct E2O links intact.
print(ocel)

# Inspect event activity counts, object inventory by type, and direct event-object
# participation counts. These are different denominators.
print("Events by activity:")
print(ocel.events["ocel:activity"].value_counts(dropna=False))
print("Objects by type:")
print(ocel.objects["ocel:type"].value_counts(dropna=False))

relation_types = ocel.relations[["ocel:eid", "ocel:oid"]].merge(
    ocel.objects[["ocel:oid", "ocel:type"]], on="ocel:oid", how="left"
)
relation_activities = relation_types.merge(
    ocel.events[["ocel:eid", "ocel:activity"]], on="ocel:eid", how="left"
)
print("Direct event-object relation rows by type and activity:")
print(relation_activities.groupby(["ocel:type", "ocel:activity"]).size())
print("Distinct events by type and activity:")
print(relation_activities.groupby(["ocel:type", "ocel:activity"])["ocel:eid"].nunique())

object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flat_logs = {}
dfgs = {}
log_skeletons = {}
for object_type in object_types:
    flat_log = pm4py.ocel_flattening(ocel, object_type)
    flat_logs[object_type] = flat_log
    dfgs[object_type] = pm4py.discover_dfg(flat_log)
    log_skeletons[object_type] = pm4py.discover_log_skeleton(flat_log)

# Cross-object views retain relations that a case projection separates.
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
object_interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Store and inspect results as structured outputs; visualizations alone do not
# decide whether a repeated event is a copy, a distinct event, or a valid link.
print("DFGs by case object type:", dfgs)
print("Log skeletons by case object type:", log_skeletons)
print("OC-DFG:", ocdfg)
print("OTG:", otg)
print("ET-OT graph:", etot)
print("Object interaction summary:", object_interactions)
```

## 7. Sensitivity and validation plan

1. **Copied-event weighting:** Recompute activity and DFG support using projected rows, distinct original event IDs, and a fractional weight of 1/n for an event copied into n cases of the selected type. Compare the effect of e13/e14, e16/e24, and V2 events. Keep copies for participation analysis; down-weight them only for occurrence-frequency comparisons.

2. **Direct versus propagated relations:** Run the baseline on supplied E2O relations. In a separate, labeled variant, propagate selected events along specified O2O paths such as Order contains Item, Package packs Item, and Delivery carries Package. Preserve source event ID and path qualifier, avoid silently adding Invoice/Payment events to every reachable order, and deduplicate unique event counts. Check which order/item variants and durations change.

3. **Change the lead object:** Compare order, item, package, delivery, invoice, and payment traces against the same named business question. Verify lifecycle endpoints and identify missing directly related event types. In particular, test whether an apparent item end or payment singleton is merely a case boundary.

4. **OC-DFG denominator sensitivity:** For each activity/edge, compare frequency by distinct events, number of distinct related objects, and total object-event relations. e16 should differ sharply across these measures because one event names multiple orders, packages, and one delivery. Label each denominator in reports; none is a substitute for the others.

5. **Shared-object sensitivity:** Recompute order and item summaries with shared package/delivery/invoice events marked, excluded from independent-case frequency, or retained only as annotations. Compare variants and cycle-time distributions. Excluding shared events can erase real coordination, so report it as a sensitivity view rather than the preferred truth.

6. **Performance boundary and allocation checks:** Calculate Order create-to-close, Package pack-to-confirm, Delivery dispatch-to-confirm, and Invoice issue-to-final-payment separately, using their actual event IDs. Do not compare these durations as though they measured the same interval. For V2, test alternative allocation policies for M2/M3 only if amounts or an approved business rule are available; otherwise leave order-level settlement time unallocated.
