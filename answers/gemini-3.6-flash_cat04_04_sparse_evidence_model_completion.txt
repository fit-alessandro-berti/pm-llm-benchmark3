### DFG Directionality and Concurrency Analysis

A Directly-Follows Graph (DFG) records observed sequential transitions between activities. The presence of bidirectional transitions—such as $(CC, ER): 17$ and $(ER, CC): 11$, or $(SC, ER): 2$ and $(ER, SC): 13$—**does not prove concurrency by itself**. 

Bidirectional DFG edges can arise from three distinct underlying phenomena:
1. **True Concurrency (Interleaving):** Two independent, overlapping activities finish in arbitrary order depending on system workload (supported by S2).
2. **Exclusive Choice / Alternative Pathways:** Path A then B is chosen for subclass X, while Path B then A is chosen for subclass Y (e.g., customer tier routing).
3. **Looping / Rework:** Activity A leads to B, which triggers rework back to A (e.g., $A \rightarrow B \rightarrow A$).

Because completion-order timestamps only record the instant an activity finishes (D7, S7), a DFG cannot distinguish between two parallel processes running concurrently and a single-threaded system switching context between two sequential steps. Abductive domain reasoning (S2, S6, D3) is required to infer true concurrency from bidirectional DFG edges.

# 2. Shared Assumptions

To ensure internal consistency across candidate models, all hypotheses share the following baseline assumptions:

1. **Completion Semantics:** Log entries represent atomic activity completion events. Interleaving in logs reflects completion order, not start or execution bounds.
2. **Optionality Abstraction for Supplier Confirmation:** $SC$ is modeled as an optional branch ($\text{XOR}(SC, \tau)$). This single control-flow abstraction accounts for both domain skipping (stocked components per S4) and logging pipeline drops (5–10% missing events per S5), because the absence of an attribute tag in the exported dataset prevents separating system noise from domain choice.
3. **Terminal and Initial Anchors:** Every case strictly begins with `Register Order` and strictly ends with the sequence `Approve Configuration` $\rightarrow$ `Release Production` $\rightarrow$ `Archive Case` (D1, D2).
4. **Single-Occurrence Bounds:** `Expedite Review` occurs at most once per case (D6). No rework loops are supported by the observed traces or rules.
5. **Data Ingestion Invariants:** Identical completion timestamps are ordered by ingestion index (S7), meaning microscopic latency in database writes does not imply process precedence.

# 3. Conservative Candidate

### Inductive-Bias Statement
The conservative candidate assumes zero unobserved generalization. It treats the 30 observed cases as an exhaustive representation of valid process execution pathways. It trades off structural simplicity and precision for zero risk of admitting illegal behavior, modeling the process as an explicit choice over the seven observed trace variants.

### Formal Expression
$$\mathcal{M}_{cons} = \bigvee_{i=1}^{7} \sigma_i$$
Where $\sigma_1 \dots \sigma_7$ represent the exact activity sequences of variants 1 through 7.

In Process Tree notation:
$$\text{XOR}\Big(\rightarrow(RO, CC, ER, SC, AC, RP, ACa), \rightarrow(RO, ER, CC, SC, AC, RP, ACa), \dots\Big)$$

### Behavior Deliberately Excluded
- The trace `RO, CC, ER, ExR, AC, RP, ACa` (Expedite Review executed without Supplier Confirmation).
- The trace `RO, ER, CC, SC, ExR, AC, RP, ACa` (Expedite Review after Supplier Confirmation when Engineering Review finished first).
- Any execution where $SC$ runs before $ER$ when $ER$ finishes first (`RO, ER, SC, CC, AC, RP, ACa`).

### Known Underfitting/Overfitting Risks
- **Extreme Overfitting:** Fits the 30 observed instances perfectly, but fails to generalize to valid unobserved trace combinations permitted by domain rules (e.g., V6 ordering applied to V2 check completion order).
- **Poor Scalability:** Uses duplicate label transitions across 7 branches; as variant counts grow, the model size expands exponentially.
- **Structural Underfitting:** Fails to capture the true underlying concurrent structure asserted by S2 and D3.

# 4. Balanced Candidate

### Inductive-Bias Statement
The balanced candidate encodes true domain concurrency and partial-order dependencies. It assumes $CC$ and $ER$ run in parallel, that $ExR$ strictly requires both checks to complete, and that $SC$ is an optional activity that requires at least one primary check to start. This balances domain compliance with reasonable generalization, filtering out data-logging artifacts while admitting valid interleavings.

### Formal Expression
$$\mathcal{M}_{bal} = RO \rightarrow \mathcal{PO}_{mid} \rightarrow AC \rightarrow RP \rightarrow ACa$$

Where $\mathcal{PO}_{mid}$ is a POWL Partial Order over nodes $\{CC, ER, \text{XOR}(SC, \tau), \text{XOR}(ExR, \tau)\}$ with order edges:
$$CC \prec ExR, \quad ER \prec ExR, \quad CC \prec SC$$

### PM4Py Model Definition
```python
from pm4py.objects.powl.obj import (
    OperatorPOWL,
    SilentTransition,
    StrictPartialOrder,
    Transition,
)
from pm4py.objects.process_tree.obj import Operator

# Terminals
t_ro = Transition(label="Register Order")
t_cc = Transition(label="Credit Check")
t_er = Transition(label="Engineering Review")
t_ac = Transition(label="Approve Configuration")
t_rp = Transition(label="Release Production")
t_aca = Transition(label="Archive Case")

# Optional Nodes via POWL XOR
opt_sc = OperatorPOWL(
    Operator.XOR, [Transition(label="Supplier Confirmation"), SilentTransition()]
)
opt_exr = OperatorPOWL(
    Operator.XOR, [Transition(label="Expedite Review"), SilentTransition()]
)

# Partial Order for Middle Activities
po_mid = StrictPartialOrder(nodes=[t_cc, t_er, opt_sc, opt_exr])
po_mid.order.add_edge(t_cc, opt_exr)
po_mid.order.add_edge(t_er, opt_exr)
po_mid.order.add_edge(t_cc, opt_sc)

# Overall Balanced POWL Model
model_balanced = OperatorPOWL(
    Operator.SEQUENCE, [t_ro, po_mid, t_ac, t_rp, t_aca]
)
```

### Rationale for Sequence vs. Concurrency vs. Partial Order
- **$CC$ vs $ER$ (Concurrency):** Both orders appear frequently in traces ($19 \times CC \rightarrow ER$, $11 \times ER \rightarrow CC$). S2 confirms parallel execution. Modeled as concurrent (no edge between $CC$ and $ER$).
- **$ExR$ (Strict Partial Order):** D6 and S6 state $ExR$ requires completion of both checks. Edges $CC \prec ExR$ and $ER \prec ExR$ guarantee compliance regardless of interleaving.
- **$SC$ (Partial Order):** D5 notes $SC$ can start once information is available from either check. Variant 5 shows $CC \rightarrow SC \rightarrow ER$. Edge $CC \prec SC$ allows $SC$ to proceed immediately after $CC$ completes without waiting for $ER$, while leaving $SC$ concurrent with $ExR$.

### Behavior Deliberately Excluded
- $ExR$ executing prior to $CC$ or $ER$ completion (violates D6/S6).
- $SC$ executing before $CC$ has started (violates minimum information constraint D5).
- Skipping $AC, RP,$ or $ACa$, or altering the terminal release sequence (violates D1/D2).

### Known Underfitting/Overfitting Risks
- **Overfitting Risk:** Enforces $CC \prec SC$ based on Variant 5. If domain reality allows $ER$ alone to trigger $SC$ ($ER \rightarrow SC \rightarrow CC$), this model will reject that trace.
- **Underfitting Risk:** Allows $ExR$ and $SC$ to run in parallel after $CC$ and $ER$, which might admit minor operational timing anomalies not intended by procurement.

# 5. Permissive Candidate

### Inductive-Bias Statement
The permissive candidate minimizes control-flow constraints by placing all intermediate activities ($CC, ER, SC, ExR$) into a fully parallel AND-block where $SC$ and $ExR$ are optional. It prioritizes admitting any potential logging variation or unobserved execution sequence, accepting low precision in exchange for maximum recall across unseen operational edge cases.

### Formal Expression
$$\mathcal{M}_{perm} = RO \rightarrow \Big( CC \parallel ER \parallel \text{XOR}(SC, \tau) \parallel \text{XOR}(ExR, \tau) \Big) \rightarrow AC \rightarrow RP \rightarrow ACa$$

### PM4Py Model Definition
```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree

# Optional Sub-trees
opt_sc_pt = ProcessTree(operator=Operator.XOR)
opt_sc_pt.children.append(ProcessTree(label="Supplier Confirmation"))
opt_sc_pt.children.append(ProcessTree(label=None))  # Silent Tau

opt_exr_pt = ProcessTree(operator=Operator.XOR)
opt_exr_pt.children.append(ProcessTree(label="Expedite Review"))
opt_exr_pt.children.append(ProcessTree(label=None))  # Silent Tau

# Parallel Middle Block
par_block = ProcessTree(operator=Operator.PARALLEL)
par_block.children.append(ProcessTree(label="Credit Check"))
par_block.children.append(ProcessTree(label="Engineering Review"))
par_block.children.append(opt_sc_pt)
par_block.children.append(opt_exr_pt)

# Sequential Main Model
model_permissive = ProcessTree(operator=Operator.SEQUENCE)
model_permissive.children.append(ProcessTree(label="Register Order"))
model_permissive.children.append(par_block)
model_permissive.children.append(ProcessTree(label="Approve Configuration"))
model_permissive.children.append(ProcessTree(label="Release Production"))
model_permissive.children.append(ProcessTree(label="Archive Case"))
```

### Boundary Between Generalization and Forbidden Behavior
- **Allowed:** Any arbitrary interleaving of $CC, ER, SC,$ and $ExR$ between $RO$ and $AC$ (e.g., $ExR$ running first, $SC$ running before all checks).
- **Forbidden:** Re-ordering or omitting structural milestones ($RO$ start, $AC \rightarrow RP \rightarrow ACa$ end); executing loop iterations or duplicate instances of checks; skipping $CC$ or $ER$.

### Known Underfitting Risks
- **Severe Precision Loss:** Admits compliance violations, such as conducting an $ExR$ before financial ($CC$) or technical ($ER$) viability has been evaluated.
- **Masking Process Bottlenecks:** Concurrency hides true missing dependencies, making automated conformance checking ineffective at detecting process drift.

### Analytical Limitations
Automated metrics and playout have inherent theoretical limits:
1. **Sampled Playout Limitation:** Playout algorithms generate bounded samples. They do not prove language equivalence or structural containment ($\mathcal{L}(M_1) \subseteq \mathcal{L}(M_2)$) for infinite or highly concurrent model spaces.
2. **Alignment Metric Artifacts:** Alignment fitness evaluates cost-optimal moves. Silent transitions ($\tau$) can introduce alignment path ties, which may slightly alter calculated generalization scores across different PM4Py versions.

# 10. Uncertainty Statement

Every major modeling choice relies on specific assumptions about data quality and process mechanics. The table below details the calibration of confidence and potential structural failure modes:

| Modeling Decision | Assumed Principle | Confidence | Primary Vulnerability / Risk |
| :--- | :--- | :--- | :--- |
| **$CC \parallel ER$ Concurrency** | S2 statement & bidirectional DFG ($17 \times CC \rightarrow ER$, $11 \times ER \rightarrow CC$). | **High (90%)** | S1 finance statement might be enforced in specific operational sub-units, making $ER \rightarrow CC$ a compliance breach rather than valid concurrency. |
| **Optionality of $SC$** | S4 domain logic & S5 pipeline drop note. | **High (95%)** | S5 pipeline bug repairs might reveal $SC$ is mandatory for ALL orders, making missing $SC$ cases 100% data errors. |
| **Edge $CC \prec SC$ in Balanced Model** | Variant 5 ($CC \rightarrow SC \rightarrow ER$) & Rule D5. | **Medium (65%)** | $SC$ might actually require information from $ER$ in certain orders ($ER \prec SC$), making Variant 5 an unrecorded compliance breach. |
| **Edges $CC, ER \prec ExR$ in Balanced Model** | Rule D6 & Compliance Statement S6. | **High (85%)** | Informal organizational workarounds might allow partial verbal expedite approvals before formal $ER$ sign-off. |

### Plausible Alternative Interpretation
If legacy ingestion logs (S7) artificially scrambled millisecond timestamps, and S1 (Finance) represents a strict mandatory rule, then all 11 traces exhibiting $ER \rightarrow CC$ are **out-of-order data ingestion glitches or compliance violations**. 

Under this alternative hypothesis:
1. $CC$ strictly precedes $ER$ in true business logic.
2. The true model is a sequential pipeline: $RO \rightarrow CC \rightarrow ER \rightarrow \text{XOR}(SC, \tau) \rightarrow \text{XOR}(ExR, \tau) \rightarrow AC \rightarrow RP \rightarrow ACa$.

Adopting this alternative hypothesis would invalidate `model_permissive` and `model_balanced`, replacing them with a strict sequential process model where all variations in $ER/CC$ ordering are flagged as data quality issues or process non-conformance.
