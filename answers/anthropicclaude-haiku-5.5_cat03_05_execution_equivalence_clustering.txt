## 1. Equivalence design space

**Lead execution.** For a lead object `o` of type `Order`, let `E(o)` be the sub-execution containing every event with an E2O edge to `o`, every object participating in those events, and the O2O edges among those objects. All relations below compare `E(o)`, not the whole log. External objects (`EXT-*`) are objects whose lifecycle is centred on another order. Their externality is a supplied flag, not something inferred from identifier strings.

**R1. Activity-sequence equivalence (ASE).**
Let (X) be the sequence of activity labels in `E(X)`, ordered by timestamp. Then X ASE Y iff (X) = (Y).
- *Concurrency:* events with identical timestamps form a block. Labels inside a block are sorted, and blocks are compared in order.
- *Invariants:* label order, label multiplicity, and repetition.
- *Discarded:* all object types, identifiers, E2O incidence, multiplicities, O2O qualifiers, externality.
- *Properties:* reflexive, symmetric, and transitive, because it is equality of a canonical key.

**R2. Typed structural equivalence under renaming (TSE).**
X TSE Y iff there is a bijection  from the objects of `E(X)` to those of `E(Y)` such that:
-  preserves object type and local/external status;
-  maps event i to event i with the same activity label (events are matched in timestamp order);
- for every event, the E2O incidence set is preserved under ;
- every qualified O2O edge (src, dst, qualifier) is mapped to an edge with the same qualifier.

For same-timestamp blocks,  maps blocks to blocks and incidence is compared within the block.
- *Invariants:* the full typed, ordered, qualified hypergraph.
- *Discarded:* identifier strings and the numeric order of identifiers. The raw timestamp values are discarded beyond their order.
- *Properties:* this is isomorphism of finite labelled ordered structures, so it is reflexive, symmetric, and transitive.

**R3. Business-semantic equivalence (BSE).**
Let (X) be a set of business flags computed from `E(X)`:
- `DLV_SINGLE` / `DLV_MULTI`: whether more than one local Delivery exists.
- `PAY_SINGLE` / `PAY_PARTIAL` / `PAY_MULTI_UNEXPLAINED`: one payment; or several payments with a `partially_settles` qualifier; or several payments without that qualifier.
- `EXT_LOGISTICS`: an external object participates in a Pack or Dispatch event.
- `EXT_FINANCIAL`: an external object participates in an Invoice or Payment event.
- `REPAIR_RETURN`: a Return Item event exists.
- `REPAIR_SUBSTITUTION`: an O2O qualifier of `removed_before_dispatch` or `replaces` exists.

X BSE Y iff (X) = (Y).
- *Invariants:* the flags above.
- *Discarded:* package counts, item counts, exact event order, activity repetition beyond its effect on flags, identity.
- *Properties:* it is the kernel of a function, so it is reflexive, symmetric, and transitive. A tolerance variant ("differ by at most one flag") would be reflexive and symmetric but not transitive, so I do not use it.
- *Concurrency:*  ignores order, so simultaneous events are handled trivially.

**R4. Fulfilment-shape equivalence (FSE, optional).**
Project `E(X)` onto local Package, Delivery, and Item objects, keeping only Pack, Dispatch, and Return events and their E2O incidence. X FSE Y iff these projections are isomorphic. This ignores invoices, payments, and external objects. It is an operational view of how the goods move.

**Preferred relation.** I use BSE for semantic clustering, with TSE as its renaming-invariant precursor. ASE is a cheap descriptive baseline. FSE is used for operational segmentation.

## 2. Canonical signatures

The typed canonical form assigns labels by first appearance in the timestamp-ordered sequence. Local objects are labelled `Type#k`. External objects are labelled `EXT:Type#k` in their own order of appearance. This labelling depends on the sequence and the types, not on identifier strings. It is a complete invariant for X1–X8 because each event introduces at most one new local object. The code below states that assumption. For general logs, a colour-refinement step would be needed to break ties.

The BSE signature is then computed from counts and flags, which are invariant by construction.

```python
from collections import Counter

REPAIR_QUALIFIERS = {"removed_before_dispatch", "replaces"}
LOGISTICS_ACTS = {"Pack Package", "Dispatch"}
FINANCE_ACTS = {"Issue Invoice", "Record Payment"}

def canonical_typed_form(events, o2o, is_ext):
    """events: [(activity, {obj_type: [oid, ...]})] in timestamp order.
    o2o: [(src, dst, qualifier)]; is_ext: oid -> bool.
    Assumes each event introduces at most one new local object (true for X1-X8);
    otherwise apply colour refinement before labelling new objects."""
    label, seen = {}, Counter()
    out = []
    for activity, objs in events:
        tokens = []
        for t in sorted(objs):
            for oid in objs[t]:
                if oid not in label:
                    kind = "EXT" if is_ext(oid) else "L"
                    seen[(kind, t)] += 1
                    label[oid] = f"{'EXT:' if kind == 'EXT' else ''}{t}#{seen[(kind, t)]}"
            tokens.append((t, tuple(sorted(label[o] for o in objs[t]))))
        out.append((activity, tuple(tokens)))
    o2o_canon = tuple(sorted((label[s], label[d], q) for s, d, q in o2o))
    return tuple(out), o2o_canon

def business_flags(events, o2o, is_ext):
    types = {}
    for _, objs in events:
        for t, ids in objs.items():
            for oid in ids:
                types[oid] = t
    local = lambda t: {o for o, tt in types.items() if tt == t and not is_ext(o)}
    flags = set()

    flags.add("DLV_MULTI" if len(local("Delivery")) > 1 else "DLV_SINGLE")
    n_pay = len(local("Payment"))
    partial = any(q == "partially_settles" for _, _, q in o2o)
    if n_pay <= 1:
        flags.add("PAY_SINGLE")
    elif partial:
        flags.add("PAY_PARTIAL")
    else:
        flags.add("PAY_MULTI_UNEXPLAINED")

    for activity, objs in events:
        has_ext = any(is_ext(o) for ids in objs.values() for o in ids)
        if has_ext and activity in LOGISTICS_ACTS:
            flags.add("EXT_LOGISTICS")
        if has_ext and activity in FINANCE_ACTS:
            flags.add("EXT_FINANCIAL")
        if activity == "Return Item":
            flags.add("REPAIR_RETURN")
    if any(q in REPAIR_QUALIFIERS for _, _, q in o2o):
        flags.add("REPAIR_SUBSTITUTION")
    return frozenset(flags)

def bse_signature(events, o2o, is_ext):
    return business_flags(events, o2o, is_ext)
```

The flag set is invariant to renaming. Each term is computed from counts, qualifiers, and externality, not from identifier strings. The FSE projection can be obtained by filtering `events` to logistics activities and object types before calling `canonical_typed_form`.

## 4. Cluster interpretations

**S1 Closed-single-settlement (X1, X2, X3).**
- *Signature:* one delivery, one invoice, one full payment, no external objects, no repair qualifiers. Package count and item count are free.
- *Business behaviour:* the order is fulfilled and billed as a single commercial unit. Multi-parcel dispatch is an operational variant, not a change in the commercial commitment.
- *Risks and opportunities:* this is the default benchmark. Splitting into packages is still visible to operations through FSE, so the semantic view does not hide routing cost.
- *Flattening that misrepresents it:* ASE separates X3 from X1 because Pack appears twice. That is a packaging detail, so ASE over-splits it.
- *Stability:* stable under identifier repair and under duplicate-pack collapse, because flags do not count packages. It would change if a missing Delivery link made the single delivery look absent.

**S2 Staged-ship-and-settle (X4).**
- *Signature:* two deliveries and a payment set containing one `partially_settles` and one completing payment.
- *Business behaviour:* the seller ships in two waves and accepts payment in two instalments. The second payment is a settlement completion, not a duplicate.
- *Risks and opportunities:* reconciliation and aging of the open receivable. The split can also be used to measure time-to-cash after partial shipment.
- *Flattening that misrepresents it:* a payment count of two, without the qualifier, looks like a duplicate charge. Collapsing repeated events also makes X4 identical to X1 in ASE.
- *Stability:* fragile. If the `partially_settles` qualifier is lost, it moves to `PAY_MULTI_UNEXPLAINED`, which an anomaly detector may flag as a duplicate. The cluster is stable only if the qualifier is trustworthy or the amount attribute can substitute for it.

**S3 Cross-order-logistics (X5).**
- *Signature:* a single delivery and payment, plus an external item packed into a shared package.
- *Business behaviour:* two orders share one parcel. Freight, damage liability, and returns must be allocated between them.
- *Risks and opportunities:* freight-cost misallocation, and liability disputes if one order's cancellation affects the shared package. Consolidation across orders can also be an opportunity for cost savings.
- *Flattening that misrepresents it:* order-level views and ASE show a normal lifecycle. The sharing exists only at the object level.
- *Stability:* stable if externality is correctly recorded. If EXT-IA is misattributed to O5, the signature falls back to S1, which would hide the sharing.

**S4 Cross-order-financial (X6).**
- *Signature:* a single local package and delivery, but an invoice and payment linked to EXT-OB.
- *Business behaviour:* one invoice covers two orders, and one payment settles it without an allocation record.
- *Risks and opportunities:* revenue-recognition error, double-counted receivables, and unreconciled cash. The opportunity is to build an allocation step.
- *Flattening that misrepresents it:* the logistics view is identical to X1, and the per-order invoice count looks normal. Only the invoice-level link exposes the problem.
- *Stability:* stable under typical repair. If an allocation record is added later, the case should become a new subtype, not return to S1.

**S5 Substitution-in-flight (X7).**
- *Signature:* a substitution qualifier, and an item appearing in Dispatch that is not the original packed item.
- *Business behaviour:* the packed contents changed before shipping, but the invoice still reflects the original order.
- *Risks and opportunities:* mismatch between shipped contents and billed items. Substitution can also indicate supplier-side stockouts.
- *Flattening that misrepresents it:* ASE identifies X7 as X1. Only the Item in Dispatch and the qualifier reveal the substitution.
- *Stability:* depends on the qualifier. If `removed_before_dispatch` is dropped, X7 joins S1. The Dispatch-Item fact is an independent fallback signal and should be used to restore the flag.

**S6 Return-and-repack (X8).**
- *Signature:* two deliveries, a Return Item event, a second Pack of the returned item, and a substitution qualifier.
- *Business behaviour:* an item was returned, inspected, and repacked into a new package for a second delivery. One invoice and one payment cover the whole order.
- *Risks and opportunities:* returns cost, inspection latency, and the risk of a repacked item lacking a correct return disposition. Opportunity: reverse-logistics analytics.
- *Flattening that misrepresents it:* ASE places it alone, but Pack and Dispatch repetitions look like duplicate processing. Counting Packs alone would suggest a split shipment rather than a return.
- *Stability:* moderately stable. If the Return Item event loses its Delivery link, the event is still counted by activity, so the return flag survives, but the link to D81 is lost.

## 5. Borderline cases

**X1 vs X2.** ASE, TSE, and BSE all say equal. Only raw-identifier keys say different. The difference that X2 added I22 before I21 is an identifier-order artefact and must be ignored. This pair checks that the method is not sensitive to identifier strings.

**X1 vs X5.** ASE says equal. TSE says different because one package contains an external item. BSE says different because of `EXT_LOGISTICS`. A logistics-only analyst could defend grouping X5 with X1 on the grounds that the local lifecycle is the same. The disagreement is over whether the lead's cluster should reflect shared resources. A second disagreement concerns item count: if external items are counted, X5 has three items, otherwise two.

**X1 vs X6.** ASE says equal, and FSE says equal because the logistics are identical. TSE and BSE differ because the invoice and payment are shared. The question is whether the semantic cluster of a lead should be defined by its full lifecycle or by one sub-lifecycle. The full-lifecycle choice (BSE) is more defensible for finance; the logistics-only choice (FSE) is defensible for operations.

**X1 vs X7.** ASE says equal. TSE differs because the Dispatch event carries an Item and the O2O qualifier is present. BSE differs only if qualifiers are used. If one counts only fulfilment entities (packages, deliveries, invoices, payments), X7 looks the same as X1. The disagreement is about whether item-level substitution is a structural difference or merely a quantity change.

**X3 vs X4.** ASE differs because the dispatch count differs (one Dispatch in X3, two in X4). TSE differs in the Delivery structure. BSE differs in both delivery count and payment pattern. A package-count view would group them together, since both have two packages. The disagreement is whether the cluster is driven by parcels or by shipments. For shipments, X3 and X4 differ; for parcels, they match.

**X4 vs X8.** Both have two packages and two deliveries, so FSE distinguishes them only because X8's Return touches a Delivery. A bag-of-events view makes them similar, since both show two Pack and two Dispatch events. BSE separates them through the return flag and through the payment pattern (partial versus single). Operations would group them as two-shipment orders. Compliance would separate them because X8 contains a return and a repack of the same item.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the key preserves.** As I understand the implementation, the exact key preserves activity labels, participating object types, and the ordered incidence of events within a bounded connected sub-execution. Some versions treat O2O qualifiers and externality as absent unless they are reflected in identifiers. Check your installed version for the exact key, the keyword name, and the return type. I do not assume them here.

**Why raw identifiers make clusters too fine.** If identifiers are included, X1 and X2 are separate, and the same is true for any two orders with isomorphic structure but different identifier strings. Exact clustering on raw identifiers answers "which objects are literally the same", not "which executions are the same".

**Canonicalization and post-processing.** Compute canonical forms (Section 2) for each lead. Merge pm4py clusters whose leads share a BSE signature. Use pm4py as an exact-equivalence check on small components, and use the lead-level signature for segmentation across the full log.

**When exact equivalence is preferable.** Exact equivalence is preferable for compliance evidence, reproducibility checks, and automated tests, where a difference must be detected even if it is operationally trivial.

**`max_objs` and large components.** Exact comparison grows quickly with component size. Leads in components larger than the bound may be omitted from the pm4py output. Such leads must still be classified by the lead-level signature. Large components also tend to be shared-resource cases (like X5 and X6), so omitting them would bias the results toward local-only executions.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"
MAX_OBJS = 12            # verify keyword name and semantics in your pm4py version
EXTERNAL_IDS = set()     # supply from the source system's ownership table

# (bse_signature, canonical_typed_form and business_flags from Section 2 assumed defined)

otype = dict(zip(ocel.objects["ocel:oid"], ocel.objects["ocel:type"]))
is_ext = lambda oid: oid in EXTERNAL_IDS

def lead_view(ocel, lead):
    rel = ocel.relations
    eids = rel.loc[rel["ocel:oid"] == lead, "ocel:eid"]
    sub = rel[rel["ocel:eid"].isin(eids)].sort_values(["ocel:timestamp", "ocel:eid"])
    events = []
    for _, g in sub.groupby("ocel:eid", sort=False):
        objs = defaultdict(list)
        for oid, t in zip(g["ocel:oid"], g["ocel:type"]):
            objs[t].append(oid)
        events.append((g["ocel:activity"].iloc[0], dict(objs)))
    ids = set(sub["ocel:oid"])
    o2o = ocel.o2o[ocel.o2o["ocel:oid"].isin(ids) & ocel.o2o["ocel:oid_2"].isin(ids)]
    o2o = list(zip(o2o["ocel:oid"], o2o["ocel:oid_2"], o2o["ocel:qualifier"]))
    return events, o2o

# Step 1: exact equivalence on bounded components (pm4py)
raw_clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=MAX_OBJS)

# Step 2: lead-level signatures for every lead (works beyond max_objs)
lead_ids = [o for o, t in otype.items() if t == LEAD_TYPE]
lead_sig, lead_act = {}, {}
for lead in lead_ids:
    events, o2o = lead_view(ocel, lead)
    lead_sig[lead] = bse_signature(events, o2o, is_ext)
    lead_act[lead] = tuple(a for a, _ in events)     # ASE key

# Step 3: consistency check against pm4py clusters
exact_members = set()
for cl in raw_clusters:
    leads = [o for o in cl if otype.get(o) == LEAD_TYPE]
    exact_members.update(leads)
    if len({lead_sig[l] for l in leads}) > 1:
        print("pm4py cluster spans several BSE signatures:", leads)
uncovered = [l for l in lead_ids if l not in exact_members]  # e.g. beyond max_objs

# Step 4: aggregate into business clusters
LABELS = {
    frozenset({"DLV_SINGLE", "PAY_SINGLE"}): "S1 Closed-single-settlement",
    frozenset({"DLV_MULTI", "PAY_PARTIAL"}): "S2 Staged-ship-and-settle",
    frozenset({"DLV_SINGLE", "PAY_SINGLE", "EXT_LOGISTICS"}): "S3 Cross-order-logistics",
    frozenset({"DLV_SINGLE", "PAY_SINGLE", "EXT_FINANCIAL"}): "S4 Cross-order-financial",
    frozenset({"DLV_SINGLE", "PAY_SINGLE", "REPAIR_SUBSTITUTION"}): "S5 Substitution-in-flight",
    frozenset({"DLV_MULTI", "PAY_SINGLE", "REPAIR_RETURN", "REPAIR_SUBSTITUTION"}): "S6 Return-and-repack",
}
clusters = defaultdict(list)
for lead, sig in lead_sig.items():
    clusters[LABELS.get(sig, f"unlabelled {sorted(sig)}")].append(lead)
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** ASE and FSE are unaffected. TSE loses the substitution qualifier, but X7 still differs through the Item in Dispatch. BSE moves X7 into S1 and places X4 in `PAY_MULTI_UNEXPLAINED`, which keeps it distinct from X1 but changes its label. X8 keeps its return flag and its cluster. The result shows that qualifiers are essential for the S5 and S2 labels, but the Dispatch-Item fact provides a partial fallback.

**Ignore external objects.** ASE is unaffected. TSE partly survives, because X5 has three items against two and X6 has two orders on one invoice. BSE moves X5 and X6 into S1, erasing the two main cross-order risks. This is the most consequential perturbation. External status must be preserved for compliance.

**Collapse repeated same-label events.** ASE is badly affected. X3 becomes Create, Add, Add, Pack, Dispatch, Invoice, Payment, which matches X1, X4 also matches X1 after collapse, and X5, X6, and X7 are unchanged. Only X8 stays distinct because of Return and Inspect. The same collapse hides the second delivery in X4 and X8. BSE is mostly robust because it counts distinct identifiers, not events. The partial-payment flag still depends on the qualifier.

**Treat Pack and Dispatch as a partial order.** If each package is ordered before its own dispatch, but unrelated Pack and Dispatch events are unordered, then X3 has two Packs before one Dispatch, and X4 has two chains. Those partial orders remain different, so the distinction survives. A coarser variant that treats all Pack and Dispatch events as an unordered block would merge X3 and X1 in ASE, because the Pack count and the Dispatch count would both be compared only as multisets. X3 would differ from X1 only through multiplicity. X8 stays distinct because Return must follow Dispatch.

**Payment multiplicity as an amount attribute.** If the two payments in X4 are replaced by one payment with a partial-amount attribute, ASE merges X4 with X1, and S2 disappears unless the amount attribute is used. BSE can preserve S2 through an amount flag, but only if the amount is available and consistent. This shows that payment structure and payment amount carry overlapping information.

## 8. Limitations and recommendation

The chosen flags are a judgement, not a neutral abstraction. For example, the choice to ignore package count is what places X3 in S1, and the choice to flag any multi-payment pattern shapes S2. The method also depends on externality and qualifier data quality. Small changes in those inputs move executions between clusters, as Section 7 shows.

**Compliance monitoring.** Use BSE with externality and repair flags, and never drop them. Compliance needs to detect shared financial objects, substitutions, and returns, and a coarse cluster can hide them. Package and item counts can be ignored here.

**Operational segmentation.** Use FSE. Operations need to know how many parcels and deliveries an order required, and whether items were substituted or returned. Settlement details are secondary.

**Root-cause analysis.** Use TSE with identifiers retained as lookup keys. Root cause depends on the exact path, including which item went into which package and which return led to which repack. Equivalence classes can group similar patterns, but the investigation must return to instance-level identifiers.

**Descriptive reporting.** Use a coarse BSE view, with named families such as "closed", "staged", "cross-order", "substitution", and "return". Dashboards should avoid ASE for exceptions, since it places X5, X6, and X7 with the baseline.

No single equivalence notion serves all four purposes. Compliance needs sensitivity to sharing and repair, operations needs sensitivity to shipment shape, root cause needs instance-level paths, and reporting needs a small number of readable categories. Each purpose requires a different projection of the same lead executions, and the finest partition is rarely the most useful one.
