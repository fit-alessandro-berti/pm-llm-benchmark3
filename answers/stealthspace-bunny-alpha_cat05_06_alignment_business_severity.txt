## 1. Materiality Framework

I use the following **provisional operational-triage scale**, not a canonical or legal severity ranking:

| Severity | Business interpretation |
|---|---|
| **1 — Negligible** | No demonstrated policy breach or customer harm. The difference is technical noise, an established activity alias, or a fitting silent transition. |
| **2 — Bounded mismatch / assurance gap** | A real modeling, scope, or evidence weakness, but no demonstrated failure of the required approval route or loss of necessary notification. |
| **3 — Material control failure** | A substantiated control breach or material assurance failure with meaningful potential exposure, but without the strongest evidence of an irreversible unauthorized payment. |
| **4 — Serious control failure** | An unauthorized payment route, required control missing from reliable evidence, or another failure likely to cause material financial, customer, or regulatory harm. |
| **5 — Critical control failure** | A documented severe failure involving irreversible payment before required approval, or comparable evidence of a major loss of payment control. |

The assessment considers:

- **Control objective:** authorization, correct-payee protection, required assessment, and timely notification are different objectives. A missing model token is not automatically a failure of the underlying objective.
- **Amount and exposure:** payout amount, fraud risk, and beneficiary-bank changes affect potential harm. A EUR 4,500 payment after a recent bank change can be more concerning than a larger payment with fully verified controls.
- **Reversibility:** an actual payment before approval is less reversible than a missing log event that can still be substantiated.
- **Timing:** approval recorded after payment is different from approval merely logged late. A recent bank change has heightened payee-verification risk.
- **Customer and regulatory harm:** duplicate attempts, denied claims, withdrawals, and notification failures have different impacts. Potential harm is not evidence that harm occurred.
- **Recurrence:** the monthly retry and auto-approval populations justify systemic remediation even where an individual case has low severity.
- **Evidence reliability:** immutable bank timestamps and linked case records carry more weight than unsupported verbal assurances or mutable text links. Conversely, a valid external document can establish that an activity occurred even when the core log lacks it.
- **Model scope:** payable-claim models should not automatically be treated as authoritative for denied or withdrawn claims. Scope uncertainty lowers confidence in the normative conclusion, not necessarily the business severity of an otherwise serious event.

**Severity and confidence are separate.** Severity estimates plausible business consequence given the control failure; confidence estimates how well the supplied evidence supports that interpretation. For example, CL-604 has high-confidence evidence of late approval, while the missing fraud event leaves uncertainty about whether screening occurred. That uncertainty does not erase the documented payment-before-approval failure.

A synchronization proves a recorded activity, not its timeliness. Except for CL-608’s stated three-hour notification, the supplied information does not establish the 24-hour notification timing. A missing event is therefore treated as an **evidence or sequencing gap**, not proof that the activity never happened.

## 6. Why Alignment Cost Is Not Business Risk

Alignment cost answers: **“How many visible edits does this chosen representation require under the selected cost function?”** It does not answer: **“What business control failed, how much money is exposed, or how certain are we?”**

The supplied cost function assigns unit cost to every visible `L` and `M`. That makes several materially different problems indistinguishable:

- **CL-601 has raw cost 3, entirely from harmless UI telemetry.**
- **CL-604 has raw cost 3, but it contains a documented severe payment-before-approval failure.** Equal cost does not imply equal risk.
- **CL-610 has raw cost 0 and violates both P1 and P2.** The process tree permits the activity sequence, while the business overlay forbids that route for a recent bank change.
- **CL-605 also has raw cost 0, but the supplied facts show an eligible claim and a fitting silent transition.** Zero cost can mean genuine fit or a control failure not represented by the activity sequence.
- **CL-602, CL-603, CL-606, and CL-608 all have raw cost 1**, yet they represent, respectively, a high-exposure fraud-evidence deficiency, a benign retry, externally evidenced assessment, and a potentially compliant alternative-channel notification.
- **CL-607 and CL-612 both have raw cost 4**, but the dominant issue is lifecycle/scope modeling after a legitimate stop—not four failed payment controls.
- **CL-611 has raw cost 2 because one activity has two names.** Counting both directions of the alias exaggerates the number of distinct business discrepancies.

Several structural limitations follow:

1. **Cost-function design:** all visible edits have equal weight. A UI event, an alias label, and a missing mandatory fraud screen each cost one. Expected financial loss, control criticality, and reversibility are absent.
2. **Hidden moves:** `T(tau)` costs zero because the model transition is fitting and need not be logged. That is appropriate technical behavior, but it does not demonstrate that the hidden transition tests the correct business conditions.
3. **Data conditions:** event names do not encode EUR 18,000 versus EUR 800, LOW versus HIGH risk, or a bank change one hour ago. Data-aware policy failures can therefore be perfectly synchronous and cost zero.
4. **Model scope:** a payable-only tree penalizes a legitimate denial or withdrawal. High cost can arise from inappropriate process scope rather than harmful operations.
5. **Activity granularity:** aliases and cross-system activities can make the same substantive work look absent. Conversely, a single logged activity can conceal a missing prerequisite.
6. **Duplicated telemetry:** a retry can add a log event without adding a business obligation. Counting edits measures logging behavior, not necessarily customer impact.
7. **Missing-but-external evidence:** CL-606 has a signed assessment despite `M(Assess Loss)`, and CL-608 has a timely external notification despite `M(Notify Claimant)`. The core log is incomplete, not necessarily the business process.
8. **Irreversibility:** the paired `L(Pay Claim)`/`M(Pay Claim)` in CL-604 is cheaply repairable as an alignment but represents an actual payment that cannot simply be undone by moving a token. P3 explicitly overrides cheap alignment repair.
9. **Evidence uncertainty:** `M` is an unmatched requirement under the supplied representation. It does not prove nonperformance, particularly where external evidence may exist.

Accordingly, business severity must remain a separate, evidence-based judgment supported by the alignment—not a rescaled alignment cost.

## 7. PM4Py Reproduction and Aggregation Code

The following code uses only inline data. The synthetic timestamps merely enforce event order; they are not asserted business timestamps. It deliberately keeps the core-log-only inputs: external adjuster and portal evidence is not injected as original core events, because doing so would change the supplied diagnostic input.

The code accepts current PM4Py alignment objects and common variants representations. Alternative optimal alignments, internal silent transitions, or formatting differences can change the reproduced cost. The supplied alignments and raw costs remain authoritative.

def field(obj, name, default=None):
    if isinstance(obj, Mapping) and name in obj:
        return obj[name]
    return getattr(obj, name, default)


def choose_alignment(alignment):
    variants = field(alignment, "variants", None)
    if variants is not None and len(variants) > 0:
        return min(
            variants,
            key=lambda v: float(field(v, "cost", float("inf"))),
        )
    return alignment


def extract_moves(alignment):
    for name in ("moves", "move", "alignment"):
        candidate = field(alignment, name, None)
        if candidate is not None:
            break

    if isinstance(candidate, Mapping):
        for nested_name in ("moves", "move", "alignment"):
            nested = field(candidate, nested_name, None)
            if nested is not None:
                candidate = nested
                break

    # An entirely silent trace may legitimately have no visible moves.
    if candidate is None:
        return []

    return list(candidate)


def move_text(value):
    if value is None:
        return None
    if isinstance(value, (tuple, list)):
        return " ".join(str(part) for part in value)
    return str(value)


def classify_move(log_move, model_move):
    log_text = move_text(log_move)
    model_text = move_text(model_move)

    if log_text is not None and model_text is not None:
        return "S"
    if log_text is not None and model_text is None:
        return "L"
    if (
        log_text is None
        and model_text is not None
        and "tau" not in model_text.lower()
    ):
        return "M"

    # A model-only tau move is a fitting silent transition.
    return "T"
