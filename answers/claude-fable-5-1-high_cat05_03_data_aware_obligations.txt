## 1. Temporal Data Semantics

**Ordering.** Each event is positioned by the pair `(time:timestamp, event_index)`. Event `e1` is *strictly before* `e2` (written `e1 ≺ e2`) iff `ts(e1) < ts(e2)`, or `ts(e1) = ts(e2)` and `idx(e1) < idx(e2)`. All "before/after" language below refers to this order, never to row order in the CSV or to the final row of a case. Consequence for TX-311: `Enhanced_Review` (idx 3) ≺ `Update_Jurisdiction` (idx 4) at 16:20, so the review saw jurisdiction US and the release saw jurisdiction DE.

**State reconstruction.** For every case I maintain a state vector `(amount, risk_level, jurisdiction, customer_type)`. The value that governs an event `e` is the value carried by the latest state-setting event `e' ≼ e` in the same case (a forward fill in `(ts, idx)` order). A blank cell means "no update at this event", so blanks are skipped by the fill, not written as null. Two rows are deliberately **excluded** from state-setting: the `jurisdiction` column of `Sanctions_List_Update` (it names the jurisdiction added to the list, it is not a case update; in TX-304 the case was already XZ so nothing changes either way) and the `amount` on `Settlement_Confirmed` (a settlement-time observation, not the release-time amount). An attribute that has never been set is **unknown (⊥)**, never defaulted (R6): TX-305's amount is ⊥ at 11:00, 11:15 and 11:30.

**No backward propagation.** Final case attributes are not used to evaluate earlier events. TX-305's 150,000 settlement amount is not the amount at release; TX-311's final jurisdiction DE is not the jurisdiction at the time of the review; TX-309's final amount 145,000 was not what the Enhanced_Review at 15:25 saw (118,000).

**Effective time by default = event time.** An `Update_*` or `Risk_Reclassify` takes effect at its own `(ts, idx)`. Only an explicit effective-time field (the exemptions' `effective_from`) overrides that.

**Material change.** For amount-dependent obligations, the baseline is the amount that governed at the time of the review being tested (not the previous update), so several small increases that cumulatively exceed 20 percent do invalidate. An increase > 20 percent of that baseline is material (R4); a decrease or an increase ≤ 20 percent is not; an increase from or to ⊥ is unclassifiable. Any change of jurisdiction, risk_level or customer_type is a material data change for the rules that depend on that attribute (R1: amount, jurisdiction; R2: risk_level, customer_type, and the amount-dependence of the review itself).

**Four clocks.**
- *Event time*: when the business event happened (`time:timestamp`; e.g. Release_Funds TX-310 at 10:00).
- *Effective time*: from when a value/authorisation governs (EX-88 `effective_from` 08:00; an Update_Amount is effective at its own event time).
- *Record time*: when the fact was written to the system of record (`Record_Exemption` 11:00 in TX-302 and TX-310, both after release). Late record time alone is not a deviation.
- *Evidence time*: the earliest moment at which independent evidence proves the fact existed (EX-77: qualified signature 09:05, before release 09:40; EX-88: signing certificate created 10:30, after release 10:00; the displayed 08:50 is a field, not evidence).
An exemption justifies a release only if `effective_time ≤ trigger`, `evidence_time ≤ release` (or evidence otherwise reliably establishes prior existence), and scope matches; record time may be later.

**Trigger evaluation.** Every rule is evaluated at `Release_Funds` on the state vector governing that event, using three-valued logic: a trigger is TRUE, FALSE or UNKNOWN. UNKNOWN triggers that no other evidence resolves yield INDETERMINATE (R6).

**Formal pseudo-logic** (three-valued; `≺` = strictly before in `(ts, idx)` order; `⊥` = unknown).

```
val(c,a,e)        := value of a in max≺{e' ≼ e : case(e')=c ∧ a set in e' ∧ act(e') ∉ excluded(a)}   ; ⊥ if none
excluded(jurisdiction) = {Sanctions_List_Update};  excluded(amount) = {Settlement_Confirmed}
r                 := Release_Funds of c
lastER(r)         := max≺{e : act(e)=Enhanced_Review ∧ e ≺ r}          (⊥ if none)
lastSR(r)         := max≺{e : act(e)=Standard_Review ∧ e ≺ r}
lastSS(r)         := max≺{e : act(e)=Sanctions_Screen ∧ e ≺ r}

-- R4 (modifier)
matAmt(rev,r)     := val(amount,r) > 1.2 * val(amount,rev)        ; UNK if either side ⊥ and an Update_Amount lies in (rev,r)
changed(a,rev,r)  := ∃e. rev ≺ e ≺ r ∧ val(a,e) ≠ val(a,rev)
invalidated(rev,r):= matAmt(rev,r)                                 ; decrease ⇒ false; UNK propagates

-- R1
trig1(r)  := val(jurisdiction,r) ≠ DE ∧ val(amount,r) ≥ 100000    ; UNK if jurisdiction=⊥ or (jur≠DE ∧ amount=⊥)
validER1(r):= lastER(r) ≠ ⊥ ∧ ¬invalidated(lastER(r),r) ∧ ¬changed(jurisdiction,lastER(r),r)
sat1(r)   := validER1(r) ∨ exempt(r,R1)
viol1(r)  := trig1(r)=T ∧ sat1(r)=F ;  indet1(r) := (trig1(r)=UNK ∧ validER1(r)≠T) ∨ (trig1=T ∧ sat1=UNK)

-- R2
trig2(r)  := val(risk_level,r)=HIGH ∨ val(customer_type,r)=PEP    ; UNK only if both ⊥ or the known one is non-triggering and the other ⊥
validER2(r):= lastER(r) ≠ ⊥ ∧ ¬invalidated(lastER(r),r) ∧ ¬changed(risk_level,lastER(r),r) ∧ ¬changed(customer_type,lastER(r),r)
sat2(r)   := validER2(r) ∧ ∃a. act(a)=Compliance_Approve ∧ lastER(r) ≺ a ≺ r ∧ lastMaterialChange(r) ≺ a
             -- a Compliance_Approve of a Standard_Review packet does not instantiate a (default reading)
viol2(r)  := trig2(r)=T ∧ sat2(r)=F

-- R3
trig3(r)  := ∃u. act(u)=Sanctions_List_Update ∧ listJur(u)=val(jurisdiction,r) ∧ lastSS(r) ≺ u ≺ r
sat3(r)   := ∀ such u. ∃s. act(s)=Sanctions_Screen ∧ u ≺ s ≺ r
viol3(r)  := trig3(r) ∧ ¬sat3(r)

-- R5 (defeasible)
formal(x,r) := approver(x)=Head_Compliance ∧ R1 ∈ waives(x) ∧ effective_from(x) ≤ ts(r) ∧ expires(x) ≥ ts(r)
               ∧ scopeJur(x)=val(jurisdiction,r) ∧ scopeCust(x)=val(customer_type,r) ∧ val(amount,r) ≤ scopeAmt(x)
proven(x,r) := evidence_time(x) ≤ ts(r) ∧ ¬contradicted(x)          -- signature/certificate, not the displayed field
exempt(r,R1):= referenced(x,r) ∧ formal(x,r) ∧ proven(x,r)
               -- defeater: displayed_approval ≤ ts(r) alone does NOT establish proven(x,r)
               -- record_time(x) > ts(r) does NOT by itself defeat exempt(r,R1)

-- R6 / R7
classify(c) := NONCOMPLIANT      if ∃i. viol_i(r)=T
             | JUSTIFIED_EXCEPTION if trig1=T ∧ ¬validER1 ∧ exempt(r,R1)=T ∧ no other violation
             | INDETERMINATE     if any indet_i(r) ∨ any trigger UNK not resolved by other evidence
             | COMPLIANT         otherwise
-- R7: every val(·) above uses ≼ on (ts, event_index); val(a, last event of case) is never substituted.
```

## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).** The R1 trigger hinges on an amount that is ⊥ at release. Evidence that would resolve it: an immutable release payload or payment-instruction message with the amount; a signed ER document stating the amount reviewed; a feed-recovery log showing when the amount was first populated. If the amount was 150,000 from creation and the ER covered it, the ER at 11:15 satisfies R1 → COMPLIANT. If the amount was populated after 11:15 (an increase from ⊥, unclassifiable under R4), the ER is stale → NONCOMPLIANT. A permissible alternative reading: "an ER exists before release and no data change is logged after it, so R1 is satisfied whatever the amount" → COMPLIANT. I reject it because the review document explicitly has no amount and R6 forbids assuming that the missing value was benign or stable. Treating the settlement amount as the release amount would be final-state leakage.

**TX-302 (COMPLIANT).** Alternative: JUSTIFIED_EXCEPTION if the assessor gives primacy to the invoked exemption. Nothing in the evidence changes the outcome; the classification would flip only if (a) the ER were shown to be invalid (e.g. an unlogged material change between 09:20 and 09:40) and (b) the QES at 09:05 were shown to be forged — both would be needed for NONCOMPLIANT. Record time 11:00 is irrelevant given evidence time 09:05.

**TX-310 (NONCOMPLIANT, evidence-based).** Alternative: INDETERMINATE, on the ground that oral approval at 08:45 cannot be excluded and the rules say cases with contradictory evidence have no canonical answer. I prefer NONCOMPLIANT because R5 places the burden on the evidence ("the evidence supports that approval existed at the relevant time") and the only pre-release indications are a displayed field (explicitly non-conclusive) and an interested witness, while the objective artefact (certificate creation 10:30) post-dates release. Evidence that would flip to JUSTIFIED_EXCEPTION: an independent contemporaneous artefact of approval before 10:00 (Head_Compliance e-mail server log, ticketing entry, recorded call, a second disinterested witness), or a signature produced with a key that existed before 10:00. Alternative that would keep NONCOMPLIANT even with proof: if the policy required the exemption to be *recorded* before release (it does not).

**TX-311 (COMPLIANT).** Same-timestamp ordering: idx 3 (ER) ≺ idx 4 (jurisdiction → DE). Consequence: the ER covered the US state, not the DE state; R1 is nevertheless not triggered because "current jurisdiction" at release is DE. Reverse tie-break (jurisdiction change first): the ER would cover the DE state; still not triggered → COMPLIANT. Reading under which the jurisdiction change is disregarded (erroneous or effective later): R1 triggers (US, 115,000), but the ER at 16:20 follows the material amount change at 16:10 → still COMPLIANT. Result flips to NONCOMPLIANT only under a policy reading that a review must be redone after any jurisdiction change regardless of direction, or if the DE update were shown to be fraudulent and made after the release. The change provenance (ops11, no KYC resource, no evidence field) deserves a control review independent of the classification.

**TX-306 (COMPLIANT).** Alternative reading: "latest material data change" in R1 means any Update_Amount, not only >20% increases → the CA/ER would predate the 12:30 change → NONCOMPLIANT. I reject it because R4 defines materiality and the note "increase below 20 percent" is deliberate. A cumulative-baseline reading (230,000 vs 220,000 baseline = +4.5%) gives the same result.

**TX-308 (COMPLIANT).** The boundary is at exactly 100,000; "at least" is inclusive so R1 is triggered, and the ER satisfies it. If the threshold were read as strictly greater than 100,000, R1 would not trigger — same classification. The decrease-does-not-invalidate clause is decisive; a policy that required re-review after any change would flip it.

**TX-307 (NONCOMPLIANT).** The stated default is that a CA over a standard packet does not cure the missing ER. A defended alternative ("hc03 is Head Compliance and approved the PEP exposure, so the substance of R2 was met") would yield JUSTIFIED_EXCEPTION at best, but R2's text requires the CA to follow "the relevant Enhanced_Review", which is a sequencing requirement that cannot be met without an ER.

**TX-304 (NONCOMPLIANT).** Would flip to COMPLIANT only if the list update's effective time were shown to be after 08:45 (e.g. a list published at 08:30 with effective date the next day) or if a Sanctions_Screen between 08:30 and 08:45 had been lost from the log.

def _changed(prev, cur):
    if pd.isna(prev) and pd.isna(cur):
        return False
    if pd.isna(prev) or pd.isna(cur):
        return True
    return prev != cur

def review_status(ev, release_row, attrs_for_rule):
    """Is a review still valid at release for the attributes the rule depends on?
    Amount baseline = amount that governed at the review event (not the previous update)."""
    if ev is None:
        return dict(exists=False, ts=pd.NaT, valid=False, unknown=False, reasons=["absent"])
    after = log[(log["case:concept:name"] == release_row["case:concept:name"]) &
                (log["order_key"] > ev["order_key"]) &
                (log["order_key"] < release_row["order_key"])]
    reasons, unknown = [], False
    for a in attrs_for_rule:
        if a == "amount":
            base, now = ev["cur_amount"], release_row["cur_amount"]
            if pd.isna(base) or pd.isna(now):
                if (after["concept:name"] == "Update_Amount").any() or pd.isna(now):
                    unknown = True
                    reasons.append("amount_unknown_at_review_or_release")
            elif now > base * 1.20:
                reasons.append(f"amount_increase_{(now/base-1):.1%}_after_review")
        else:
            if after[f"chg_{a}"].any():
                reasons.append(f"{a}_changed_after_review")
    valid = (len(reasons) == 0) and not unknown
    return dict(exists=True, ts=ev["time:timestamp"], idx=int(ev["event_index"]),
                valid=valid, unknown=unknown, reasons=reasons)


def exemption_check(ex_id, release_row, rule):
    if pd.isna(ex_id) or ex_id is None:
        return dict(claimed=False)
    ex = EXEMPTIONS.set_index("exemption_id").loc[ex_id]
    rel_ts = release_row["time:timestamp"]
    checks = dict(
        claimed=True, exemption_id=ex_id, waives_rule=(ex["waives"] == rule),
        approver_ok=(ex["approved_by"] == "Head_Compliance"),
        scope_jur_ok=(ex["scope_jurisdiction"] == release_row["cur_jurisdiction"]),
        scope_cust_ok=(ex["scope_customer_type"] == release_row["cur_customer_type"]),
        scope_amt_ok=(None if pd.isna(release_row["cur_amount"])
                      else bool(release_row["cur_amount"] <= ex["scope_amount_max"])),
        effective_ok=(ex["effective_from"] <= rel_ts),
        not_expired=(ex["expires"] >= rel_ts),
        record_after_release=bool(ex["record_time"] > rel_ts),
        evidence_before_release=bool(ex["evidence_time"] <= rel_ts),
        evidence_contradiction=bool(ex["evidence_contradiction"]),
        evidence_time=ex["evidence_time"], record_time=ex["record_time"],
    )
    scope_ok = checks["scope_jur_ok"] and checks["scope_cust_ok"] and checks["scope_amt_ok"] is True
    formal_ok = checks["waives_rule"] and checks["approver_ok"] and scope_ok \
        and checks["effective_ok"] and checks["not_expired"]
    checks["formal_ok"] = bool(formal_ok)
    checks["evidence_ok"] = checks["evidence_before_release"] and not checks["evidence_contradiction"]
    # An exemption is only *proven* if formally valid and evidenced before release.
    # Late record time alone does not defeat it; a displayed backdated field alone does not prove it.
    checks["proven_valid"] = checks["formal_ok"] and checks["evidence_ok"]
    checks["needs_human_judgment"] = checks["formal_ok"] and not checks["evidence_ok"]
    return checks

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A trace-level or case-attribute check sees TX-311 as "DE" and TX-309 as "145,000" for the whole case. Evaluated on final state, TX-311's ER looks irrelevant and TX-309's ER looks like it covered the final amount; TX-305 acquires a phantom amount of 150,000 from settlement. R7 requires the value at the event, which needs a per-event state reconstruction, not case attributes.

2. **Post-hoc exemptions and clock confusion.** `Record_Exemption` occurs after `Release_Funds` in both TX-302 and TX-310. A DECLARE `precedence(Record_Exemption, Release_Funds)` fails for both, yet the right answer differs (EX-77 valid, EX-88 unproven) because it depends on evidence time (09:05 signature vs 10:30 certificate) that is not an event in the trace at all. Control flow cannot distinguish record time from effective time from evidence time.

3. **Material changes after review.** `precedence(Enhanced_Review, Release_Funds)` is satisfied in TX-309, but the review was invalidated by a +22.9% increase after it. Whether an event "counts" depends on arithmetic over attribute values at two different points in time (baseline at the review, value at release) and on a threshold and direction (decrease in TX-308 is fine, +4.5% in TX-306 is fine). No activity-sequence constraint can express "the amount now exceeds 1.2 × the amount then".

4. **Conditional activation.** R1–R3 are obligations only when the state satisfies a predicate (non-DE ∧ ≥100k; HIGH ∨ PEP; list update for the current jurisdiction). A control-flow model must either require ER everywhere (false positives on TX-304, TX-307's R1 leg, TX-311) or nowhere (false negatives on TX-301, TX-310). Data-conditional DECLARE (MP-Declare) helps, but even then the activation condition must be evaluated on reconstructed event-time state, not on the event's own payload (the Release_Funds row is blank).

5. **Missing data.** TX-305's release has no amount. A control-flow check happily passes it (ER precedes release). A naive data check that fills blanks with 0 or with the settlement amount produces a confident wrong answer in one direction or the other. R6 requires a third truth value and a REVIEW_REQUIRED outcome, which conformance checkers do not produce natively.

6. **Same-timestamp ordering.** TX-311's ER and jurisdiction update share 16:20. Sorting by timestamp alone gives an arbitrary order; some tools drop or reorder ties. The `event_index` tie-break determines which state the review saw. Here the outcome is robust, but in a mirror case (DE → US at the same instant as the review) the tie-break alone would decide COMPLIANT vs NONCOMPLIANT.

7. **Activity-label conflation and packet scope.** `Standard_Review` is not `Enhanced_Review` (TX-301, TX-307, TX-310), and a `Compliance_Approve` over a standard packet is not the R2 approval (TX-307). Control-flow checks match labels; they cannot inspect what the approval covered or whether the approver was Head_Compliance.

8. **Exogenous events and cross-entity state.** `Sanctions_List_Update` is not a step of the transaction; it is a change in an external reference list that becomes relevant only if its payload equals the case's current jurisdiction. A trace-order rule "Sanctions_Screen after Sanctions_List_Update" would fire for every case in which a list update happens to appear, regardless of jurisdiction, and would miss updates logged outside the case.

9. **Threshold boundaries and baselines.** "At least 100,000" (TX-308 at exactly 100,000) and "more than 20 percent" measured against the review baseline rather than the previous update are numeric semantics that must be coded explicitly; sequence models have no notion of them.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** `Release_Funds` must carry the full governing state (amount, currency, jurisdiction, risk_level, customer_type, beneficiary, exemption references) as a hashed, signed payload, with the hash stored in the log. This would have made TX-305 determinate and would prevent silent state drift between review and release.
- **Review payload and scope.** `Standard_Review`, `Enhanced_Review` and `Compliance_Approve` must record the state snapshot reviewed (amount baseline, jurisdiction, risk, customer type), the review type, the packet reference, and which rules the review is asserted to satisfy (`covers=[R1,R2]`). TX-307's "approved standard review packet" would then be machine-detectable.
- **Three explicit timestamps on every event and register row.** `event_time` (business occurrence), `effective_time` (from when the value/authorisation governs), `record_time` (system write). Add `evidence_time` and `evidence_ref` (signature timestamp, certificate serial, TSA token) on exemptions and approvals, so late records (TX-302) can be distinguished from backdated ones (TX-310) without manual forensics.
- **Qualified time-stamping of approvals at creation.** Exemption approvals must be signed with a key that already exists and time-stamped by a trusted TSA at approval time; a certificate created after the release must automatically flag the exemption as unproven. Oral approvals must be followed by a system acknowledgement from the approver's own account within a short window.
- **Exemption scope as structured data.** Store `waives`, `scope_jurisdictions`, `scope_customer_types`, `amount_min/max`, `effective_from`, `expires`, `approved_by_role`, `approver_id`, `rule_version` in the register, and log `Exemption_Invoked` as an event at release with the register version used, so the scope match can be checked mechanically at release time rather than reconstructed.
- **Rule version and decision evidence at release.** Log `rule_version`, the evaluated triggers (`R1_triggered`, `R2_triggered`, …), the obligations the release engine believed were satisfied, and their evidence references. This turns the release into a checkable decision record and exposes cases where the engine used stale state.
- **Change provenance.** Every `Update_*` and `Risk_Reclassify` should carry `changed_by`, `change_reason`, `source_system`, `old_value`, `new_value`, `approval_ref` where required, and the KYC/document reference for jurisdiction and customer-type changes. TX-311's jurisdiction change by the ops user who also raised the amount would be flagged for four-eyes review; TX-305's missing amount would be logged as an explicit `Amount_Unavailable` event with a reason.
- **Stable, total event ordering.** Keep `event_index` as a monotonically increasing per-case sequence assigned by the system of record at commit time, log at millisecond or better resolution, and publish the tie-break rule. Consider a per-case logical clock so that same-timestamp events (TX-311) have an unambiguous, auditable order.
- **Explicit state-change events for exogenous data.** Sanctions list updates should be logged as reference-data events with `list_version`, `jurisdiction`, `effective_time`, and screening events should record the `list_version` screened against. R3 then becomes "release list_version ≥ latest effective list_version for current jurisdiction" and is mechanically checkable.
- **Hard controls in addition to logging.** Block release when the governing amount is null; block release when the latest amount-dependent review baseline is exceeded by more than 20 percent or when jurisdiction/risk/customer type changed after the latest review; require an ER event before a Compliance_Approve can be tagged as R2-relevant; require a Sanctions_Screen with a current list version before release.
- **Unknown-value handling.** Represent unknown values explicitly (a dedicated `UNKNOWN` marker distinct from "no update") and require downstream engines to treat them as blocking, so that missing data cannot be interpreted as low-risk by default.
