# 1. Objectives and constraints
### Optimization Objectives (to be balanced, not maximized alone)
1.  **Throughput & Flow:** Minimize average waiting time for assignment + service time. Avoid unnecessary queuing on specialist bottlenecks.
2.  **SLA Adherence:** Minimize probability and severity of deadline misses, prioritizing urgent/high priority and short `SLA time remaining`.
3.  **Quality / Error Reduction:** Minimize skill-mismatch, rework and appeal risk.
4.  **Continuity & Case Ownership:** Minimize costly handovers, especially for high `reassignment_count` and high `handover_cost_band` / high `case_complexity`.
5.  **Skill Development:** Provide supervised training assignments aligned with `Training priority` without exposing high-priority cases to unsupervised trainees.
6.  **Workload Fairness & Well-being:** Balance distribution of `workload_snapshot` and `hours remaining today`, protect resources with `overtime risk = high`.
7.  **Resilience:** Avoid single points of failure (Security, Approval queues); maintain cross-skilled backup capacity.

### Hard Constraints - Safety / Compliance (must not be violated)
*   **H1-Skill 0:** `skill == 0` = not allowed, never assigned even with supervision.
*   **H2-Security Review:** Requires `skill == 3` OR (`skill == 1-2` WITH explicit supervision by `R7_Gita` or `R8_Hugo` on same case). `skill 0` cannot be supervised into Security.
*   **H3-Final Approval:** Requires `skill == 2-3` to finalize. `skill == 1` may *prepare* case only under supervision of `skill 2-3` who retains final accountability.
*   **H4-High Priority Protection:** No `priority == high` or `urgent` assigned to `skill == 1` or `0` unless supervised pair is assigned and supervisor is available. Supervised trainee executes under time-bounded review.
*   **H5-Skill Filtering:** All candidates filtered to `skill >=1` before scoring (except supervised routes explicitly checked).

### Soft Constraints / Preferences - Trade-offs (weighted, auditable)
*   **S1-Capacity Fairness:** No resource receives >4 new assignments in current batch. Soft limit: penalize assignment if `Current open cases >= 11` or `Hours remaining < 4.0`. High `overtime risk` resources penalized heavily, only overridden if `SLA urgent` and no safer `skill >=2` alternative exists.
*   **S2-Continuity Preference:** For `handover_cost_band == high` AND `case_complexity >= 0.7`, prefer `current_owner` if `skill >=2` (or `skill ==1` with feasible supervision). Keeping a weak owner (`skill 1`) adds ~3.3h service time; changing owner adds ~2.7h waiting + increases rework risk 1.8x after >2 reassignments. Decision must explicitly trade these.
*   **S3-Training Share:** At least 20% of `priority == normal/low` assignments where `SLA remaining > 20h` and `complexity < 0.6` should support `Training priority` if risk acceptable. Highly complex / urgent cases are not training cases.
*   **S4-Batching:** `Quality Check` may be batched only if `priority in [normal,low]` AND `SLA remaining > 24h`. Batching must not introduce SLA risk to batch members.
*   **S5-Resilience / Bottleneck Avoidance:** If a skill has <3 qualified specialists and queue length >2, prefer developing secondary capacity via supervised assignments rather than queuing all cases to specialists, unless SLA < 8h.

> No single objective dominates. The policy explicitly trades waiting time vs. rework risk vs. fairness vs. development.

# 2. Assignment policy
### Explainable Dynamic Policy - Scoring + Rules (human-readable weights)

**Step 0 - Eligibility Filtering**
```
for each case C with required_skill = S:
  candidates = { R | R.skill[S] >= 2 }  # directly eligible
  supervised_candidates = { (R_trainee, R_sup) | 
        R_trainee.skill[S]==1 AND R_sup.skill[S]>=2 (or >=3 for Security/Approval) 
        AND supervision allowed by H2/H3/H4 AND R_sup.hours_remaining > 2h }
  eligible = candidates  supervised_candidates
  remove any R where R.skill[S]==0
  remove candidates violating H1-H4
  if eligible empty -> escalate to team lead, do not auto-assign
```

**Step 1 - Scoring (0-10 per dimension, auditable)**
For each eligible R (or pair P):
1.  **SLA Urgency Score:** `U = 10 * f(priority, sla_remaining, complexity)` . `urgent: sla<4h=10; high<8h=8-9; normal<20h=5; low=1-3`. Boost +2 if `priority==urgent` and +1 if `complexity>0.7`.
2.  **Skill-Match Score:** `M = {3:10, 2:7, 1+supervision:5, 1 unsupervised:0}` . Specialist gets 10, competent 7. For supervised pair, score is 5 (reflects learning value but higher oversight cost).
3.  **Continuity Score:** `C = 10 if R == current_owner & handover_cost==high; 7 if medium; 5 if low; 0 if reassignment would be 4th+` . Apply penalty `-4` if `R != current_owner` AND `reassignment_count >=2`.
4.  **Workload / Overtime Fairness Score:** `F = 10 - (open_cases - 5) - penalty_overtime` . `penalty: low 0, medium 2, high 4` . Minus `+3` if `hours_remaining <4h`. Score floor 0. This implements S1.
5.  **Training / Development Score:** `D = 7` if `R.training_priority == S` AND `priority in [normal,low]` AND `SLA>20h` AND `M>=5` ; `D=3` if competence building but not priority; `D=0` if `priority==urgent/high` or `skill==3` already. Supervised pairs inherit trainee's D.
6.  **Resilience / Bottleneck Score:** `B = 0` normally; `-5` if assigning to a solo specialist bottleneck when a competent alternative (`skill 2`) exists and `SLA>8h`; `+3` if assignment creates secondary capacity in scarce skill (Security/Approval).

**Step 2 - Weighted Total (weights explainable, tunable)**
```
Total = 0.30*U + 0.25*M + 0.15*C + 0.15*F + 0.10*D + 0.05*B
# Weights reflect: SLA+safety first, but not only throughput
# If high-complexity + high-handover -> S5 boost: C weight temporarily 0.25, M 0.15
```
Log all sub-scores into `assignment_reason` for audit.

**Step 3 - Selection, Tie-breaking and Exception Handling**
```
Rank eligible by Total descending
Apply fairness cap: skip R if they already have 4 assignments in this batch -> next
If U >=8 (urgent): choose highest M among top-3 F>=4; do not choose high-overtime unless no F>=4 alternative -> document exception
If high-complexity/high-handover and current_owner skill>=2 and in top 3 -> prefer owner even if -1 point deficit (S2)
Tie-break in order: 1) higher skill 2) lower open_cases 3) more hours_remaining 4) supports training without SLA risk 5) same team as current_owner to reduce handover
Exception: If no eligible without violating overtime or skill, escalate with reason: "SLA risk forced overtime" or "supervised supervision required"
Batching: Group Quality Checks with same resource, sla>24h, normal/low only; treat batch as single assignment for fairness cap
```

Socio-technical notes: Scores are shown to workers as plain language reasons (see §5). Supervisors are not penalized for supervision time; supervision is counted as 0.5 workload unit.

# 5. Explanation to workers

**How assignments are made — transparent, not punitive**

We assign work using five questions you can check for every case:

1.  **Is it urgent or risky to wait?** Cases close to SLA or marked high/urgent go first and get the most experienced available person for that skill.
2.  **Does the person have the right skill?** Security and Final Approval need a specialist or a trainee *with* a named specialist watching that specific case. We never assign a skill you don't have, and we never leave a high-priority customer with an unsupervised trainee.
3.  **Do we already know this customer/case?** If you own a complex case and a handover would add extra waiting and extra mistakes, we try to keep it with you — even if someone else is slightly more specialist — unless the case needs a skill you don't have. Every extra handover past two makes rework almost twice as likely.
4.  **Are workloads fair and safe?** We look at how many open cases you have and hours left today. People with high overtime risk get less new work unless a customer is truly urgent and there is no safe alternative. No one gets more than four new cases off this list.
5.  **Are we learning together?** For routine cases with plenty of SLA time, we sometimes pair a trainee with a specialist supervisor. The supervisor remains responsible, and the pairing matches your recorded training priority. This is how we avoid bottlenecks where only two people can do Security or Approval. You won't be given trainee work on a VIP urgent case without backup.

**What you will see in the assignment list:**

*   **Who & why:** e.g., "C001  Hugo — urgent enterprise Security needs specialist; previous owner Celine not qualified alone; Hugo has capacity."
*   **Trade-off in plain language:** e.g., "C007 stays with Celine even though Hugo is free — fourth handover would add risk, and Celine is fully qualified."
*   **Supervision pairs are joint accountability:** Both names are logged, supervision time counts. The trainee does the work, the specialist reviews before completion.

**No hidden scoring:** If you disagree, you can see your scores for skill match, urgency, continuity, workload and training, and raise an exception. Exceptions (e.g., "assigned despite high overtime because SLA 2h and no alternative") must be written in `assignment_reason` and are audited — not used for performance blame, but to improve staffing.

**Resilience is shared:** We deliberately avoid sending every difficult case to the same specialist, even though that looks efficient today — it burns people out and leaves us stuck if they are absent. Spreading supervised learning protects the whole team.

# 6. Process-mining audit indicators

Calculated from event log with `assignment_reason`, `reassignment_count`, `workload_snapshot`, `handover_cost_band`. Evaluate weekly/monthly and per-team.

*   **Handover frequency:** `handover_rate = # handovers (org:resource change between consecutive events in same case) / # cases` ; also *handover density* from `pm4py.discover_handover_of_work_network` . Alert if rate  >15% after policy change. Segment by `handover_cost_band`.
*   **Reassignment count:** Distribution of `reassignment_count` per case at completion; `% cases with >2 reassignments` ; trend median. Correlate with outcome.
*   **Skill mismatch:** `% assignments where resource skill <2 for required_skill` (and % with <2 without supervision flag); `% Security without skill 3 or valid supervisor (R7/R8)`; `% Approval finalized by skill 1`. Filter with `pm4py.filter_event_attribute_values`.
*   **Workload distribution:** Gini coefficient of `workload_snapshot` at assignment time across resources; max-min gap of open cases; `% batches where a resource got >4 new cases`. Track overtime exposure.
*   **Overtime risk exposure:** `# assignments to high-overtime-risk resources / total assignments` overall and for `priority != urgent` (should be 0); average `hours remaining today` at assignment.
*   **SLA misses:** `% cases missing sla_deadline` overall and by priority; `SLA miss rate for urgent vs normal`; median `waiting time` (`pm4py.insert_case_service_waiting_time` / `pm4py.get_service_time`) vs SLA remaining at assignment.
*   **Rework / appeal after assignment:** `rework_rate = # cases with Rework Correction or repeated Technical Diagnosis loop / # cases`; `appeal_rate`; compare `>2 reassignments` cohort vs `<=2` (expect 1.8x/1.4x). Segment by skill-mismatch cohort.
*   **Training assignment share:** `# normal/low assignments where resource training_priority == required_skill / # normal/low assignments` (target 20%); `# supervised assignments / total`; completion rate of supervised cases vs solo.
*   **Specialist bottleneck indicators:** Queue length per scarce skill (Security, Approval) at assignment time; `service waiting time` for cases assigned to skill 3 vs skill 2; utilization ratio `specialist open cases / total open`. Performance DFG shows waiting before Security/Approval.
*   **Deviations from assignment policy:** `% cases where assignment_reason != policy top rank or where hard constraints H1-H4 violated` (audit exception log). Track `assignment_reason` completeness; manual overrides reasons.

Thresholds trigger review, not punishment. All indicators sliced by `team`, `case_priority`, `required_skill`.
