## 1. Equivalence design space

Represent execution X by its distinguished lead Order, typed objects, events, E2O incidences, and directed O2O relations. Mark EXT objects as external independently of their identifiers. Treat the supplied event positions as ordered observations; do not infer unreported events, amounts, or relations. X2's explicitly stated topology supplies its renamed X1 relations.

**Activity-sequence equivalence, A.** Two executions are equivalent exactly when their sequences of activity labels agree, including repetitions. Preserve label order and event counts; discard objects, incidence, qualifiers, and attributes. With genuinely simultaneous events, compare ordered timestamp blocks, each containing a multiset of labels. Discard absolute timestamps and durations. Here every supplied position is a separate block.

**Typed structural equivalence, T.** Construct a graph with event vertices colored by activity and object vertices colored by type, externality, and lead status. Preserve E2O incidence, event precedence, and directed O2O edges, including parallel-edge multiplicity, but erase O2O qualifier labels. Two executions are equivalent exactly when a color-preserving graph isomorphism exists. Identifiers, absolute timestamps, amounts, and qualifier meanings are discarded. Thus T preserves more than object counts or per-object activity traces. For simultaneous events, retain precedence between timestamp blocks and allow permutations within a block. An alternative fully qualified structural relation would also preserve O2O labels.

**Preferred business-semantic equivalence, B.** Compare the feature tuple defined below. Preserve local item/invoice counts, delivery and payment object/event counts, logistics and financial sharing, and observed replacement, return/repack, and staged-settlement motifs. Deliberately discard package counts, parcel grouping, incidental interleavings, identities, and O2O details outside those motifs. This groups X3 with the baseline: parcel consolidation differs, but each has one dispatch, one delivery, one recorded payment, and no observed corrective or sharing motif.

All three are reflexive, symmetric, and transitive because each is equality of a fixed canonical representation, or graph isomorphism. They are not similarity thresholds. B uses precedence only to recognize lifecycle motifs, so concurrent independent branches may commute. Unknown or absent evidence means “motif not observed,” not proof that the business condition never occurred.

## 2. Canonical signatures

Use B as the operational segmentation key:

`(items, invoices, deliveries, dispatches, payment_objects, payment_events, L, F, S, R, T)`.

L/F indicate observed external participation in logistics/finance. S indicates an Item replacement paired with removal of the old Item before dispatch. R indicates return, inspection, packing of the same Item, and dispatch of that package. T indicates distinct partial and completing payments linked to the same Invoice. Packages are intentionally absent from the counts.

The following Python-like pseudocode assumes parsed objects, explicitly supplied relations, and a precedence predicate. IDs are used to join records within an execution; only invariant counts and predicates enter the key.

```python
LOGISTICS = {"Pack Package", "Dispatch"}
FINANCE = {"Issue Invoice", "Record Payment"}

def semantic_signature(x):
    # x.objects[id] has fields type, external, lead
    # x.events contain activity and a set of object IDs
    # x.o2o contains (source_id, qualifier, target_id)
    # x.before(a, b) means strict precedence, not arbitrary tie order
    def local_count(typ):
        return sum(o.type == typ and not o.external
                   for o in x.objects.values())

    def ids(e, typ):
        return {oid for oid in e.objects if x.objects[oid].type == typ}

    def events(activity):
        return [e for e in x.events if e.activity == activity]

    def rels(qualifier, source_type, target_type):
        return {(s, t) for s, q, t in x.o2o
                if q == qualifier
                and x.objects[s].type == source_type
                and x.objects[t].type == target_type}

    def external_participation(activities):
        return any(x.objects[oid].external
                   for e in x.events if e.activity in activities
                   for oid in e.objects)

    L = external_participation(LOGISTICS)
    F = external_participation(FINANCE)

    # Also recognize sharing explicitly documented only through O2O.
    L |= any(x.objects[item].external
             for _, item in rels("packs", "Package", "Item"))
    F |= any(x.objects[order].external
             for _, order in rels("bills", "Invoice", "Order"))

    replacement = rels("replaces", "Item", "Item")
    removal = rels("removed_before_dispatch", "Package", "Item")
    dispatched_packages = set().union(
        *(ids(e, "Package") for e in events("Dispatch")))
    S = any(old == removed and package in dispatched_packages
            for new, old in replacement for package, removed in removal)

    # Require a common Item across return, inspection and packing,
    # and a common Package across that packing and its dispatch.
    R = any(x.before(r, i) and x.before(i, k) and x.before(k, d)
            and bool(ids(r, "Item") & ids(i, "Item") & ids(k, "Item"))
            and bool(ids(k, "Package") & ids(d, "Package"))
            for r in events("Return Item")
            for i in events("Inspect Return")
            for k in events("Pack Package")
            for d in events("Dispatch"))

    partial = rels("partially_settles", "Payment", "Invoice")
    complete = rels("completes_settlement", "Payment", "Invoice")
    T = any(v1 == v2 and p1 != p2
            for p1, v1 in partial for p2, v2 in complete)

    return (local_count("Item"), local_count("Invoice"),
            local_count("Delivery"), len(events("Dispatch")),
            local_count("Payment"), len(events("Record Payment")),
            int(L), int(F), int(S), int(R), int(T))
```

Externality comes from the supplied EXT convention, not accidental ID spelling after renaming. For T, an exhaustive canonicalizer can enumerate bijections within object-color classes and event-color/time classes, serialize precedence and all incidence edges under each bijection, and select the lexicographically smallest serialization. That is reproducible, though expensive; a graph canonical-labeling implementation is preferable at scale.

## 4. Cluster interpretations

**B0 — isolated forward fulfillment.** Signature: two local Items, one Invoice, one dispatch/delivery, one recorded payment, no selected motif. X1–X3 differ in parcel organization. Consolidation offers transport efficiency; splitting packages may increase handling costs, which should remain available as a secondary measure. Order-only traces hide X3's branching; Package-only traces obscure the consolidated delivery. Stable under renaming and harmless scheduling repair; changed boundary membership or repaired payment multiplicity can change assignment. Payment recording alone does not establish full monetary settlement.

**B1 — split delivery with staged settlement.** Signature: D2/2, P2/2, T=1. X4 fulfills two package branches separately and records partial then completing invoice settlement. Risks include uneven delivery completion and reconciliation mistakes; opportunities include installment and partial-shipment coordination. A flattened Order trace repeats activities without explaining which package or payment each concerns. Stable under renaming, but sensitive to merging payment records or losing settlement qualifiers. Completion is stated for the Invoice; amounts are unspecified.

**B2 — shared logistics.** Signature: L=1. X5 combines another Order's Item with O5's Items in one package/delivery while invoicing O5 separately. Consolidation may reduce costs, but creates coordination and cost-allocation dependencies. Separate Order traces duplicate shared logistics and hide coupling. Stable only when extraction retains external participants; clipping them can turn this into B0.

**B3 — shared finance.** Signature: F=1. X6 has ordinary local logistics but a joint Invoice and unallocated payment. Shared billing may simplify collection; attributing settlement to O6 individually remains unresolved. Order flattening can duplicate the same invoice/payment and suggest unsupported order-level settlement. Stable under renaming, but boundary clipping or adding allocation information changes the interpretation.

**B4 — pre-dispatch substitution.** Signature: S=1. X7 records replacement of I71 by I72 and removal of I71 before dispatch. Inventory and invoice consistency require attention; the data does not specify billed item amounts. Activity-only Order traces conceal the substitution, while unqualified package membership can suggest both Items shipped. Stable when qualifier evidence survives; qualifier loss destabilizes this semantic assignment.

**B5 — return and repack.** Signature: D2/2, P1/1, R=1. X8 returns and inspects I82, then repacks and dispatches it using a replacement package. Track reverse-logistics costs and avoid counting the second dispatch as additional original demand. Delivery-only traces split the cycle; Order traces hide which Item returned. Stable under ID repair, but sensitive to missing return/inspection evidence or precedence repairs that break the motif.

## 5. Borderline cases

**X1 versus X2.** Raw-ID equality separates them; T and B merge them. A consistent mapping sends the first-added X1 Item to X2's first-added Item, despite opposite numeric suffix order. Sorting IDs before mapping would introduce an unsupported distinction.

**X1 versus X5.** A merges identical activity sequences; T and B separate external logistics sharing. A projection retaining only local E2O participation can also merge them, but explicitly discards cross-order coupling.

**X1 versus X6.** A, or a logistics-only equivalence, merges them. B separates shared finance because the payment cannot be attributed independently to O6. Equal local multiplicities do not resolve this dependency.

**X1 versus X7.** A merges them; B preserves replacement qualifiers and separates them. T also separates them: X7 has direct Item incidence at Dispatch and additional O2O edges, even after qualifier labels are erased. Thus qualifier loss does not necessarily erase structural differences.

**X3 versus X4.** An equivalence recording only two Items in two packages could merge them. T and B separate one versus two deliveries and one versus two payments; X4 also explicitly records staged settlement. This is a business distinction beyond scheduling.

**X4 versus X8.** A coarse multiplicity summary of two packages and two deliveries merges them. B separates original split fulfillment with installments from corrective return/repack with one payment. Qualified structure also distinguishes disjoint package contents from I82 recurring across packages.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

Distinguish PM4Py's implementation key from A, T, and B. The dictionary-based scheme freezes its type/relation representation into a hashable key: type entries describe objects and their types, and relation entries describe labeled event–object participation. Exact equality preserves the fields actually serialized, including raw identifiers wherever retained. It is not automatically typed graph isomorphism or qualified lifecycle equivalence.

The question does not pin a PM4Py version or supply its key schema. Consequently, timestamp inclusion, ordering, duplicate handling, and O2O qualifier inclusion must be verified for the installed implementation; claiming all these are preserved would be unjustified. The exact invariant guaranteed by a returned key is equality of that serialization. In particular, neither external ownership nor settlement allocation can be recovered from fields absent from it.

Raw IDs can make equivalent renamed executions occupy separate buckets. Canonicalize member executions using Section 2, then regroup across returned buckets. Do not canonicalize IDs independently per event, which would lose object continuity. Conversely, if a raw bucket omits semantic distinctions, its members may require splitting.

```python
from collections import defaultdict
import pm4py

# ocel already exists. Keep external neighbors needed to identify sharing.
# Choose max_objs according to the installed splitter's extraction semantics.
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel, "Order", max_objs=2

semantic_clusters = defaultdict(list)
key_audit = []
for raw_key, members in raw_clusters.items():
    key_audit.append((type(raw_key).__name__, repr(raw_key)))
    for subocel in members:
        # Custom adapter: tables -> objects, events, E2O, qualified O2O,
        # lead metadata, external ownership, and timestamp precedence.
        # Ownership must come from the original extraction context;
        # multiple Order objects alone do not identify the lead.
        x = execution_view(subocel, lead_type="Order", context=ocel)

# Inspect key_audit before making implementation-specific key claims.

```

`execution_view` is an explicit custom-adapter placeholder. If extraction loses qualifiers or boundary provenance, retain them separately from the original OCEL; post-processing cannot restore missing evidence. `max_objs` affects extraction scope, not semantic distance or the number of clusters. A restrictive limit may suppress shared-order context; larger scopes may produce overlapping or large connected executions. Validate what the installed splitter limits. Large executions increase memory and canonicalization costs, especially for exhaustive isomorphism search.

Exact equivalence is useful for reproducible extraction checks, detailed variant inspection, or enforcing a precisely specified representation. Business segmentation benefits from consciously coarser keys.

## 7. Robustness analysis

**Ignore all O2O qualifiers.** T already does so and stays unchanged. In B, S and T become unobserved: X7 merges with B0, while X4 remains separate through delivery/payment counts. X8's event-based return/repack motif survives. Retained unqualified edges still contain structural evidence.

**Ignore external objects.** Removing their vertices and incidences sets L/F to zero, merging X5 and X6 into B0. Their activity clusters remain unchanged. Structural merging additionally requires matching retained O2O edges: sparse notes must not be repaired by inventing missing local relations.

**Collapse repeated same-label events.** Define the operator explicitly. Collapsing consecutive runs merges X3's activity sequence with the baseline after both Add runs are collapsed. X4's alternating Pack/Dispatch remains distinct. If merged events retain unioned object incidences, its two payment objects and settlement qualifiers survive, although its payment-event count becomes one. Globally collapsing every repeated label additionally erases X4's branching activity sequence. Either operation loses occurrence information and requires recomputing signatures.

**Use partial rather than total Pack/Dispatch order.** Preserve pack-before-dispatch constraints for each package and return-cycle dependencies; common attachment to the lead Order alone need not force causality. Independent branches may commute. T becomes less sensitive to interleavings, but these typed clusters remain separated by incidence/count differences. B assignments stay unchanged when its motifs' necessary precedence survives.

**Represent payments through amounts instead of multiplicity.** This could group installment and single-payment cases by total settlement, but no amounts are supplied. X4's completion qualifier supports invoice completion, not numerical equality with another execution. Dropping payment counts alone still leaves delivery and motif differences; inventing equal totals would be unsupported.

## 8. Limitations and recommendation

For **compliance monitoring**, use fully qualified typed structure plus relevant attributes and explicit checks for boundary ownership, allocation, and settlement evidence. For **operational segmentation**, use B, retaining package count as a secondary measure. For **root-cause analysis**, inspect qualified object graphs and causal motifs, with drill-down to individual events. For **descriptive reporting**, use B-level counts and activity summaries while preventing duplicate counting of shared events.

The notes are compact and do not provide amounts, full temporal relation histories, or an extraction rule. Report absent evidence explicitly and assess sensitivity to boundary and qualifier repairs. Exact structural clustering can oversegment harmless differences; coarse clustering can hide financial and fulfillment dependencies. The appropriate relation depends on which distinction supports the intended decision.
