## 1. Temporal Data Semantics
- **State Reconstruction**: State is reconstructed by forward-filling attribute values from the most recent event where the attribute was updated. Blank cells are treated as "no update" (not null), meaning the previous value persists unless explicitly changed.
- **Handling Blanks**: If an attribute is blank at an event, its value is the last known value before that event. If no prior value exists (e.g., at `Create_Transaction`), it remains blank/unknown.
- **Ordering Equal Timestamps**: Events with the same timestamp are ordered by `event_index` (ascending). For example, in TX-311, `Update_Jurisdiction` (event_index 4) occurs after `Enhanced_Review` (event_index 3) at the same timestamp.
- **Material Changes**: A material change is any update to `amount`, `risk_level`, `jurisdiction`, or `customer_type` that could affect obligations (e.g., amount  EUR 100,000, jurisdiction not DE, risk_level HIGH, or customer_type PEP).
- **Final Attributes**: The final attribute value at an event is only authoritative for that event and subsequent events until another update occurs. For example, the `amount` at `Release_Funds` is the last updated value before release, not the final case state.
- **Time Distinctions**:
  - **Event Time**: Timestamp of the event in the log.
  - **Effective Time**: When an update becomes authoritative (e.g., `exemption_id` effective_from).
  - **Record Time**: When a record is created (e.g., `Record_Exemption` at 11:00).
  - **Evidence Time**: When supporting evidence (e.g., digital signatures, witness statements) is generated.

## 6. Why Control-Flow-Only Conformance Is Insufficient
1. **Final-State Leakage**: Control-flow checks assume the final case state is authoritative for all prior events, but R7 requires event-time semantics.
2. **Post-Hoc Exemptions**: Exemptions like EX-88 (TX-310) are referenced at `Release_Funds` but may lack strong evidence until later (e.g., late signing certificate).
3. **Material Changes After Review**: R4 invalidates reviews if the amount increases >20% after review, which cannot be captured by control-flow alone.
4. **Conditional Activation**: Rules like R1 and R2 are conditionally triggered by data (e.g., `amount >= 100,000`), not just event sequences.
5. **Missing Data**: R6 requires handling unknown values (e.g., TX-305), which control-flow cannot address.
6. **Same-Timestamp Ordering**: TX-311 shows that event_index must resolve ordering at the same timestamp, which control-flow cannot enforce without explicit data.
7. **Late Evidence**: Exemption evidence (e.g., TX-302) may arrive after `Release_Funds`, requiring temporal reasoning beyond control-flow.
8. **Exemption Scope Mismatch**: Exemptions must match the state at the obligation trigger (e.g., jurisdiction, amount), which control-flow cannot validate.

## 7. Recommended Logging and Control Improvements
1. **Immutable Release Payloads**: Include a cryptographic hash of the release state (amount, jurisdiction, risk, customer type) at `Release_Funds` to prevent post-hoc changes.
2. **Effective/Record/Signature Timestamps**: Separate fields for:
   - `exemption_effective_from` (when the exemption becomes valid).
   - `exemption_record_time` (when the exemption is logged).
   - `exemption_signature_time` (when the exemption is signed).
3. **Rule Version**: Include a `rule_version` field in events to track policy changes over time.
4. **Exemption Scope**: Standardize exemption scope fields (e.g., `jurisdiction`, `customer_type`, `amount_min`, `amount_max`) for programmatic validation.
5. **Change Provenance**: Log `change_reason` for updates (e.g., "customer increased order", "adverse-media hit") to justify material changes.
6. **Stable Event Ordering**: Use a globally unique event ID (e.g., UUID) instead of `event_index` to avoid timestamp collisions.
7. **Material Change Flags**: Explicitly mark events that trigger material changes (e.g., `is_material_change=True` for `Update_Amount` if >20% increase).
8. **Audit Trails**: Include `audit_user` and `audit_timestamp` for all state-changing events to trace accountability.
