# 1. Executive Verdict

The net is structurally a workflow net: it has one source place, one sink place, and every node lies on some source-to-sink path. It should **not** be expected to be sound. The principal defect is that `t_join_waived` is not actually a join: it consumes only `p_waived` and can produce `p_decision` without waiting for `t_analyze`/`p_analysis_done`. As a result, a waiver case can reach a token in `sink` while leaving either `p_analysis` or `p_analysis_done` behind, so the exact final marking `fm = {sink:1}` is never reached on the waiver route. Business consequence: waiver cases can be authorized before mandatory analysis is complete, and successful completion leaves an unconsumable analysis token.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `t_register`, `p_ready`, `t_split` | Register and start parallel analysis/review branches | Correct: `t_split` places one token in `p_analysis` and one in `p_review` | Parallel branch creation works |
| `p_review`, `t_standard_review`, `t_waive_review` | Exclusive review outcome: standard review or recorded waiver | Correct XOR-like choice from the single `p_review` token: only one of the two transitions can fire | Waiver and standard review are mutually exclusive for a case |
| `t_analyze`, `p_analysis_done` | Mandatory analysis completion | Analysis is generated independently and must complete for the normal join | On waiver route, analysis token can be bypassed unless the waiver join waits for it |
| `t_join_normal` | Synchronize analysis completion and standard review completion | Correct: has inputs `p_analysis_done` and `p_review_done`, outputs `p_decision` | Standard-review path can terminate cleanly |
| `p_waived`, `t_join_waived` | Synchronize waiver with mandatory analysis, then authorize | Defective: `t_join_waived` has only `p_waived` as input and outputs `p_decision`; it is a single-input transition, not a join | Waiver can proceed without analysis completion; leftover analysis token remains |
| `p_decision`, `t_authorize`, `sink` | Authorize only after analysis plus selected review outcome | Authorization is enabled whenever `p_decision` exists, regardless of how it was produced | `t_authorize` can fire with `p_analysis` or `p_analysis_done` still marked |
| Initial/final markings | `im = {source:1}`, `fm = {sink:1}` | Source and sink are unique, but exact final marking is not reachable from waiver choices | Token may exist in `sink` while extra token remains elsewhere |
| Source-to-sink path condition | Workflow-net structural condition | Every place and transition is on some source-to-sink path | Workflow-net check can pass despite unsound waiver synchronization |

# 3. Marking-Based Counterexample

Legal firing sequence on the original net:

`t_register`, `t_split`, `t_waive_review`, `t_join_waived`, `t_authorize`, `t_analyze`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source:1}` | `t_register` | Start from `im` |
| 1 | `t_register` | `{p_ready:1}` | `t_split` | Case registered |
| 2 | `t_split` | `{p_analysis:1, p_review:1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | Parallel analysis/review tokens created |
| 3 | `t_waive_review` | `{p_analysis:1, p_waived:1}` | `t_analyze`, `t_join_waived` | Waiver route selected; analysis still pending |
| 4 | `t_join_waived` | `{p_analysis:1, p_decision:1}` | `t_analyze`, `t_authorize` | Defect: waiver “join” fires without analysis completion |

`t_register`, `t_split`, `t_waive_review`, `t_analyze`, `t_join_waived`, `t_authorize`

Normalize waiver into review-done | Remove arc `t_join_waived -> p_decision`; add arc `t_join_waived -> p_review_done` | 1 semantic arc retarget; primitive cost 2 arcs | Mandatory analysis retained because authorization ultimately requires `t_join_normal` with `p_analysis_done` | Waiver is converted to `p_review_done`; both standard and waiver routes then use `t_join_normal` as the sole authorization gate | `p_review_done` conflates “standard review completed” and “waiver recorded” at the marking level; audit must rely on transition history |

Repair A is the globally smallest primitive repair: it adds exactly one arc and changes no existing behavior except making the waiver join wait for analysis completion. Repair B is behaviorally distinct: it redirects the waiver outcome into the normal join path. Under the semantic arc-edit model, A and B both cost one arc operation. Under a strict primitive add/remove model, A is uniquely cheapest at cost 1, while B is the cheapest repair in the “normalize waiver through `p_review_done`” family at cost 2. Neither repair removes unrelated nodes or changes visible labels.

import pm4py
from pm4py.objects.petri_net.obj import Marking


def marking_str(marking):
    return "{" + ", ".join(
        f"{p.name}:{marking[p]}"
        for p in sorted(marking, key=lambda p: p.name)
        if marking[p] > 0
    ) + "}"


def fire_named(petri_net, marking, transition_name):
    transition = next(
        (t for t in petri_net.transitions if t.name == transition_name),
        None
    )
    if transition is None:
        raise ValueError(f"Unknown transition: {transition_name}")

    enabled = pm4py.get_enabled_transitions(petri_net, marking)
    if transition not in enabled:
        enabled_names = sorted(t.name for t in enabled)
        raise ValueError(
            f"Transition {transition_name} is not enabled. "
            f"Enabled transitions: {enabled_names}"
        )

    new_marking = Marking()
    for place, tokens in marking.items():
        new_marking[place] = tokens

    for arc in transition.in_arcs:
        weight = arc.weight if arc.weight is not None else 1
        new_marking[arc.source] -= weight
        if new_marking[arc.source] == 0:
            del new_marking[arc.source]

    for arc in transition.out_arcs:
        weight = arc.weight if arc.weight is not None else 1
        new_marking[arc.target] += weight

    return new_marking

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of waiver and standard review:** In Repair A, `t_standard_review` and `t_waive_review` remain distinct visible transitions, and `t_join_normal` vs `t_join_waived` remain distinct silent transitions. However, after either join produces `p_decision`, the place marking no longer shows which review type occurred; audit relies on transition history/logs. If the business requires a durable marking-level waiver flag all the way to authorization, a place-based encoding would need additional modeling.

- **Silent-transition duplication/confusion:** Repair A keeps the existing silent transitions. There is no duplicate token-producing path: the single `p_review` token goes through either `t_standard_review` or `t_waive_review`, and the corresponding join fires only when its required inputs exist. The risk is future policy change: if the model is later modified to allow both standard review and waiver on the same case, `p_analysis_done` would be shared between two joins and could be consumed by only one, leaving the other blocked.

- **Soundness does not prove full business alignment:** Soundness only proves proper completion and absence of dead/improper tokens relative to `fm`. It does not prove that the visible event order matches all policy constraints, that authorization credentials are checked, or that waiver approval is recorded with correct data. Conformance checking, regression traces, and possibly data-aware constraints are still needed.

- **Regression tests:** Positive traces should include standard review after analysis, waiver after analysis, and waiver selected before analysis but authorization only after analysis completes. Negative traces should include waiver authorization before analysis, authorization without any review outcome, both standard review and waiver for the same case, duplicate authorization, and any final marking with `sink` plus a token in `p_analysis` or `p_analysis_done`.

- **Detect accidental bypass of mandatory analysis:** Add a reachability or temporal query asserting that no marking contains `sink` together with `p_analysis` or `p_analysis_done`. In event-log terms, require `Perform Analysis` before `Authorize Case` whenever `Record Review Waiver` is present. A model-level invariant can also check that `t_join_waived` is enabled only when both `p_waived` and `p_analysis_done` are marked.

# 8. Final Recommendation

Deploy **Repair A**. It is the smallest primitive edit, preserves the explicit waiver token `p_waived`, and makes `t_join_waived` a true two-input synchronization with `p_analysis_done`. It directly enforces the key business rule: authorization after a waiver still requires the mandatory analysis to be complete. The main residual risk is that `p_analysis_done` is shared between the normal and waiver joins, so future changes that allow both review outcomes must revisit the model.

Use **Repair B** as the fallback if the organization prefers a single authorization gate through `t_join_normal`. Repair B is behaviorally clean and keeps mandatory analysis, but it conflates standard review completion and waiver completion into `p_review_done`; audit then depends more heavily on transition history. For either repair, regression-test the waiver-before-analysis trace and assert that exact final marking has only the sink token.
