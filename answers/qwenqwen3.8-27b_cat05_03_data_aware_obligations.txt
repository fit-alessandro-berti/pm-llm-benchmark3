## 1. Temporal Data Semantics

I reconstruct case state as an event-time state machine, not as a final-case snapshot.

- **Event ordering:** Within each case, events are ordered by `(time:timestamp, event_index)`. `event_index` is the tie-breaker when timestamps are equal. An event with the lower `event_index` at the same timestamp is treated as occurring first.
- **Blank cells:** A blank attribute cell means “no update at this event.” It does **not** mean the attribute was set to null. Missing values are forward-filled only from earlier events within the same case. Future values are never copied backward into earlier events.
- **State at an event:** The state at event `e` is the latest known nonblank value for each attribute among events in the same case with order `<= e`. For a `Release_Funds` event, the governing state is the state at that release event, including same-timestamp updates that precede the release by `event_index`.
- **Final attributes:** Final case attributes are not used to evaluate earlier obligations. For example, a jurisdiction that becomes `DE` after an earlier review is not treated as if it were `DE` before the change.
- **Material changes:** For the purposes of these rules, I treat the following as material case-attribute changes:
  - `Create_Transaction` as the initial material data baseline;
  - `Risk_Reclassify`;
  - `Update_Jurisdiction`;
  - `Update_Customer_Type`;
  - `Update_Amount` only when the amount increases by more than 20% from a known prior amount.
  
  A decrease does not, by itself, invalidate a review. An amount change from an unknown amount is not treated as a known material increase; it produces an unknown-data flag instead.
- **Time distinctions:**
  - **Event time:** the timestamp of the logged event.
  - **Effective time:** when the attribute or exemption legally takes effect. Unless evidence establishes otherwise, an attribute update is effective at its event timestamp.
  - **Record time:** when the system inserted or updated a record, such as a late database insert.
  - **Evidence time:** when reliable approval evidence exists, such as a qualified digital signature timestamp. A late record can evidence an earlier approval, but a backdated displayed field alone is not conclusive.
- **Missing data:** Missing amount, risk, jurisdiction, or customer type is not defaulted to a low-risk value. If a decisive trigger cannot be established or excluded, the affected obligation is `INDETERMINATE`.

### Formal pseudo-logic

Define temporal order:

```text
before(e1, e2)  := (time(e1), event_index(e1)) < (time(e2), event_index(e2))
after(e1, e2)   := before(e2, e1)
at_or_before(e1, e2) := before(e1, e2) or (time(e1) = time(e2) and event_index(e1) <= event_index(e2))
```

State reconstruction:

```text
state(case, attr, e) :=
    value of attr from latest nonblank update f in case
    such that at_or_before(f, e)
    unknown if no such update exists
```

Latest event:

```text
latest(case, P, e) :=
    max { f | P(f) and at_or_before(f, e) }
    none if no such event exists
```

Material change:

```text
MaterialChange(f) :=
    Create_Transaction(f)
    or Risk_Reclassify(f)
    or Update_Jurisdiction(f)
    or Update_Customer_Type(f)
    or (Update_Amount(f)
        and KnownAmountBefore(f)
        and AmountAfter(f) > 1.2 * AmountBefore(f))
```

Amount review invalidation:

```text
AmountReviewInvalid(review, release) :=
    exists u:
        Update_Amount(u)
        and after(review, u)
        and before(u, release)
        and KnownAmountBefore(u)
        and AmountAfter(u) > 1.2 * AmountBefore(u)
```

Exemption validity:

```text
ExemptionValid(ex, case, release, R1) :=
    ApprovedByHeadCompliance(ex)
    and EffectiveFrom(ex) <= time(release)
    and Expires(ex) >= time(release)
    and ScopeMatches(ex, state(case, release))
    and Waives(ex, R1)
    and ApprovalEvidenceBefore(ex, release)

ApprovalEvidenceBefore(ex, release) :=
    exists ev:
        ReliableApprovalEvidence(ev, ex)
        and time(ev) <= time(release)
```

Indeterminacy:

```text
Indeterminate(rule, case, release) :=
    a decisive state value required by rule is unknown
    and no reliable evidence resolves it
```

```text
R1Obligation(case, release) :=
```

## 4. Ambiguities and Alternative Readings

### TX-305 — INDETERMINATE

The result changes if the release amount is established by reliable pre-release or immutable release-time evidence.

- If an immutable release payload or reliable pre-release record shows amount **below 100,000**, R1 is not triggered and the case can be `COMPLIANT`, assuming no other triggered rule is violated.
- If reliable evidence shows amount **at least 100,000** at release and no material amount change occurred after the 11:15 Enhanced_Review, R1 could be `COMPLIANT` because the Enhanced_Review occurred before release.
- If reliable evidence shows amount **at least 100,000** but also shows that the amount increased by more than 20% after the Enhanced_Review, or that the Enhanced_Review did not cover the amount-dependent state, the case becomes `NONCOMPLIANT`.
- If the 150,000 settlement amount is accepted as conclusive evidence of the release amount, the case may become determinate. However, the prompt states there is no immutable release payload, so settlement evidence alone is not sufficient for a definitive compliance conclusion.

### TX-310 — INDETERMINATE

The result changes depending on whether EX-88 is treated as a valid pre-release exemption.

- If independent evidence establishes Head_Compliance approval before 10:00, with valid AE/CORPORATE/<=250,000 scope and valid effective/expiry times, EX-88 could be valid and the case could be `JUSTIFIED_EXCEPTION` because R1 is waived.
- If the qualified signing certificate at 10:30 is treated as conclusive that no valid approval existed before release, EX-88 is invalid and the case is `NONCOMPLIANT` because there is no Enhanced_Review.
- If the witness statement is treated as reliable and oral approval is accepted as sufficient evidence, the case could become `JUSTIFIED_EXCEPTION`.
- If a different interpretation treated Standard_Review as sufficient for R1, the case could become `COMPLIANT`, but that conflicts with the explicit semantic fact that Standard_Review is not an Enhanced_Review.

### TX-302 — Alternative readings

TX-302 is classified as `JUSTIFIED_EXCEPTION` because the release invoked a valid R1 exemption. However, an alternative classification is possible.

- If classification is based strictly on whether all required controls were present, TX-302 could be `COMPLIANT` because an Enhanced_Review occurred at 09:20 before release.
- If the exemption were invalid, the case would still likely be `COMPLIANT` because the Enhanced_Review satisfies R1.
- The case would become `NONCOMPLIANT` only if the Enhanced_Review were absent or invalid and the exemption were also invalid or not in force at release.
- If a post-Enhanced material data change occurred before release and the exemption were invalid, R1 could fail. No such material change appears in the log.

### TX-311 — Alternative readings

TX-311 is `COMPLIANT` because the release state is DE, so R1 is not triggered.

- If `event_index` were ignored and the same-timestamp Enhanced_Review and jurisdiction update were treated as simultaneous with no ordering, the case could become `INDETERMINATE` because it would be unclear whether the jurisdiction changed before or after the review.
- If the jurisdiction update had changed the case to a non-DE jurisdiction after the Enhanced_Review, R1 would be triggered at release and the Enhanced_Review would not be after the latest material data change, producing `NONCOMPLIANT`.
- If DE were not treated as the safe-harbor jurisdiction under R1, the case could be re-evaluated as an R1 case. Under the stated rule, DE is not a trigger.
- If the 90,000 to 115,000 amount increase were unknown rather than known, R4 and R1 could become indeterminate.

### TX-306 — Alternative readings

TX-306 is `COMPLIANT` under the reading that a below-20% amount increase is not a material amount change for R4.

- If any amount change, even below 20%, were treated as a material data change for R1, the 12:30 increase after the 12:15 Enhanced_Review could make R1 fail.
- If the Compliance_Approve were not by an authorized compliance authority, or if it were not genuinely after the relevant Enhanced_Review, R2 could fail.
- If the PEP or HIGH risk status had changed after the Enhanced_Review, the enhanced review might not be relevant to the release state.

### TX-308 — Alternative readings

TX-308 is `COMPLIANT` because the later amount change is a decrease and R4 says a decrease does not by itself invalidate a review.

- If any amount change were treated as material for R1 regardless of direction, the 14:25 decrease after the 14:20 Enhanced_Review could make the review fail.
- If the threshold were interpreted as strictly greater than 100,000 rather than “at least 100,000,” R1 would not be triggered. The stated rule uses “at least,” so 100,000 triggers R1.
- If the Enhanced_Review were absent, the case would be `NONCOMPLIANT`.

### TX-309 — Alternative readings

TX-309 is `NONCOMPLIANT` because the final amount increase invalidates the Enhanced_Review.

- If a new Enhanced_Review had occurred after the 15:28 increase and before release, the case could be `COMPLIANT`.
- If a valid R1 exemption had been in force, the case could be `JUSTIFIED_EXCEPTION`.
- If the increase were measured from the original 95,000 to 145,000, the increase is still over 20%, so the conclusion remains `NONCOMPLIANT`.

```python
def assess_exemption(row):
    if pd.isna(row.get("exemption_id")):
        return "NONE"
    if row.get("waives") != "R1":
        return "NOT_APPLICABLE"
    if row.get("approved_by") != "Head_Compliance":
        return "INVALID"
    if pd.isna(row.get("effective_from")) or pd.isna(row.get("expires")):
        return "INVALID"
    if row["effective_from"] > row["release_time"] or row["expires"] < row["release_time"]:
        return "INVALID"
    if pd.isna(row.get("ex_jurisdiction")) or pd.isna(row.get("ex_customer_type")):
        return "INVALID"
    if row["ex_jurisdiction"] != row["jurisdiction"] or row["ex_customer_type"] != row["customer_type"]:
        return "INVALID"
    if pd.notna(row.get("max_amount")):
        if pd.notna(row["amount"]) and row["amount"] > row["max_amount"]:
            return "INVALID"
        if pd.isna(row["amount"]):
            return "UNKNOWN_SCOPE"

    sig = row.get("exemption_signature_time")
    disp = row.get("exemption_displayed_approval_time")
    qual = row.get("evidence_quality")

    # Strong qualified signature before release is sufficient.
    if pd.notna(sig) and sig <= row["release_time"] and qual == "strong":
        return "VALID"

    # Displayed approval before release is not conclusive if evidence is weak or contradicted.
    if pd.notna(disp) and disp <= row["release_time"]:
        if qual == "strong":
            return "VALID"
        if (pd.notna(sig) and sig > row["release_time"]) or qual == "weak":
            return "CONFLICTING"

    return "INVALID"

def coarse_status(row):
    # Missing decisive data requires human evidential judgment.

    if (
        row["r1_status"] == "TRIGGERED"
        and not row["r1_review_met"]
        and row["r1_exemption_status"] in ("CONFLICTING", "UNKNOWN_SCOPE")
    ):
        return "REVIEW_REQUIRED"

    violations = []

    if row["r1_status"] == "TRIGGERED" and not row["r1_review_met"]:
        if row["r1_exemption_status"] != "VALID":
            if row["r1_exemption_status"] in ("CONFLICTING", "UNKNOWN_SCOPE"):
                return "REVIEW_REQUIRED"
            violations.append("R1")

    if row["r2_status"] == "TRIGGERED" and not row["r2_review_met"]:
        violations.append("R2")

    if row["r3_status"] == "TRIGGERED" and not row["r3_met"]:
        violations.append("R3")

    if violations:
        return "NONCOMPLIANT"

    # If a valid R1 exemption is invoked for a triggered R1 case, label as justified exception.
    if row["r1_status"] == "TRIGGERED" and row["r1_exemption_status"] == "VALID":
        return "JUSTIFIED_EXCEPTION"

    return "COMPLIANT"

    "\nNote: control-flow or DECLARE-style checks above are coarse. "
    "They do not enforce amount thresholds, review invalidation by material amount changes, "
    "exemption evidence time, scope matching, missing-data indeterminacy, or same-timestamp ordering."
)
```

## 6. Why Control-Flow-Only Conformance Is Insufficient

Control-flow-only conformance checks whether the right event types appear in the right sequence. That is necessary but not sufficient here because the obligations are conditional on data values, evidence timing, and state changes.

1. **Final-state leakage.**  
   A control-flow check may use the final case state to evaluate earlier events. For example, TX-311 ends in `DE`, but the jurisdiction became `DE` after the Enhanced_Review by `event_index`. If the final state is copied backward, the timing of the jurisdiction change is lost. Conversely, a final amount may not have been the amount present when a review occurred.

2. **Post-hoc exemptions.**  
   TX-302 and TX-310 both have `Record_Exemption` events after `Release_Funds`. A control-flow check may see an exemption event and either ignore it or incorrectly accept it. The decisive question is not when the database record was inserted, but whether reliable approval evidence existed before the obligation trigger.

3. **Material changes after review.**  
   TX-301 and TX-309 show that a review can occur before release but still be invalid because the amount increased by more than 20% after the review. A control-flow check that only sees `Review -> Release` would pass both cases, even though the review no longer satisfies the amount-dependent obligation.

4. **Conditional activation.**  
   R1 applies only when jurisdiction is not `DE` and amount is at least 100,000. R2 applies only when risk is `HIGH` or customer type is `PEP`. R3 applies only when the current jurisdiction is added to the sanctions list after the latest screen. Control-flow cannot condition obligations on these data values.

5. **Missing data.**  
   TX-305 has no amount at create, review, or release. A control-flow check may see `Enhanced_Review -> Release_Funds` and pass, but the R1 trigger cannot be established because the amount is unknown. The correct result is indeterminate, not compliant.

6. **Same-timestamp ordering.**  
   TX-311 has Enhanced_Review and Update_Jurisdiction at the same timestamp. Without `event_index`, the ordering is ambiguous. The policy requires that event_index 3 precedes event_index 4, so the jurisdiction changed after the review. Control-flow using only timestamps cannot resolve this.

7. **Review type and scope.**  
   TX-307 has a Standard_Review and a Compliance_Approve, but no Enhanced_Review. A coarse control-flow check that treats any review as sufficient would incorrectly pass the case. R2 requires an Enhanced_Review specifically.

8. **Exemption scope and validity.**  
   An exemption must match jurisdiction, customer type, amount scope, waiver, effective time, expiry, and approval evidence. Control-flow cannot verify that EX-77 or EX-88 actually applies to the release state or was valid before release.

## 7. Recommended Logging and Control Improvements

To make future decisions more determinate, the event log and control system should capture immutable, time-stamped, rule-relevant evidence.

- **Immutable release payloads.**  
  Every `Release_Funds` event should include an immutable payload containing amount, risk level, jurisdiction, customer type, rule version, referenced review IDs, referenced exemption IDs, and a cryptographic hash. This prevents post-release settlement data from being confused with release-time data.

- **Separate timestamps.**  
  Events should distinguish:
  - event time;
  - effective time;
  - record time;
  - approval time;
  - signature time;
  - evidence time.  
  A late database record should not be treated as the approval time if a reliable earlier signature exists.

- **Explicit attribute changes.**  
  Every attribute change should be an explicit event with:
  - old value;
  - new value;
  - effective time;
  - record time;
  - source system;
  - user or system identity;
  - reason code;
  - provenance link to supporting evidence.  
  Amount changes should include prior amount, new amount, percentage change, and whether the change is known or estimated.

- **Rule versioning.**  
  Each release and review should record the policy rule version used. This makes it possible to evaluate historical cases against the rules that were in force at the time.

- **Exemption lifecycle data.**  
  Exemptions should store:
  - exemption ID;
  - approver identity;
  - approval evidence timestamp;
  - effective_from;
  - expires;
  - jurisdiction scope;
  - customer-type scope;
  - amount scope;
  - waived rules;
  - rule version;
  - record insertion time;
  - evidence quality or validation status.

- **Review scope and validity.**  
  Reviews should record:
  - review ID;
  - review type;
  - reviewer;
  - attributes reviewed;
  - amount reviewed;
  - jurisdiction and customer type reviewed;
  - validity start;
  - invalidation triggers;
  - linked case state snapshot or hash.

- **Sanctions list versioning.**  
  Sanctions list updates should include:
  - list version;
  - jurisdiction added or removed;
  - effective time;
  - source;
  - screening result linkage.  
  Screens should reference the list version used.

- **Stable event ordering.**  
  Use a globally stable ordering key, such as `(case_id, timestamp, event_index, source_sequence, event_id)`. Do not rely on wall-clock timestamp alone.

- **Explicit unknowns.**  
  Use explicit `UNKNOWN` values and data-quality flags instead of blank cells. Missing amount, risk, jurisdiction, or customer type should trigger a data-quality exception rather than a silent low-risk default.

- **Rule engine output.**  
  The system should emit a decision record for each release containing:
  - triggered rules;
  - state snapshot used;
  - obligations;
  - satisfied controls;
  - failed controls;
  - exemptions considered;
  - exemption validity status;
  - indeterminate items;
  - evidence references.

- **Pre-release control gates.**  
  The release workflow should block or flag release when:
  - a triggered rule has no required control;
  - a review was invalidated by a material change;
  - a sanctions list update requires a new screen;
  - required data is unknown;
  - an exemption is missing, expired, out of scope, or not evidenced before release.
