# 1. Review Scope and Assumptions

This review distinguishes three major usecases for a process model in a governed environment:

- **Exploration** – discovering behavioural patterns, communicating the rough flow to business stakeholders, and supporting fast iteration. In exploration a model may be deliberately permissive to accommodate noise and missing data; low precision is tolerable if fitness and comprehension are high.
- **Conformance Enforcement / Compliance** – checking whether real executions obey business rules (P1–P7). A compliance model must reject policyforbidden behaviour and accept all legitimate variants. Metrics that reward noise tolerance are dangerous here.
- **Simulation & prediction** – generating whatif scenarios; requires a structurally sound model that does not overgenerate impossible traces.

The two submitted models target different purposes: Model S argues “robustness to missing events”, effectively aiming at exploration; Model C claims “auditreadiness”, i.e., compliance. The third alternative discussed in §7 is designed for *compliance with honest admission of missing attributes*, but can also be reused for communication after validation.

The board must recognise that no model built from a log lacking the `external/internal` and `affected-check` attributes can fully satisfy P3 and P6. Hence any selection must be accompanied by a **postmodel policycheck layer** that uses outofband data.

   (P4: Expedite Review must follow both checks)

4. **Expedite Review before one of the checks**  
   `Register Dossier  Technical Review  Expedite Review  Credit Check  Manager Approval  Release Order`  
   (parallel interleaving allows any ordering, including the one above)

5. **Parallel reexecution of checks without correction**  
   The model cannot produce a second `Credit Check` or `Technical Review` (each child executes at most once), so it does not *admit* suspicious duplicates (see B8). However, it also **rejects all traces containing `Correct Dossier`**, making it impossible to model legitimate corrections (P6).

6. **Supplier Review absent for external orders** – the model is indifferent, which is a blind spot for compliance if external attribute is missing.

7. **Any ordering of Supplier and Expedite Review** – acceptable under P4, but it also allows both to be skipped, which may be a policy concern even for internal/domestic orders if the organisation sometimes expects Expedite.

The permissiveness caused by the choices is not a deliberate noisetolerance strategy for *optional* activities – it accidentally dissolves **mandatory** gates. This is an accidental semantic flaw, not an intentional design choice.

# 4. Adversarial Review of Model C

## Strongest case for Model C
- Each branch was mined from a frequent log variant; the model is a direct trace catalogue, giving it extremely high precision on the training set (0.941) and a clean “audit trail” appearance.
- It explicitly lists variants containing `Correct Dossier`, showing awareness of the correction loop (though only one variant is included).
- F8 argues that unseen behaviour should be treated as noncompliant, which justifies low holdout fitness.
- For a stable process with a small set of approved paths, the model might be acceptable.

## Strongest case against Model C
Model C suffers from pathological overfitting and maintenance fragility.

### Branch enumeration and missing combinations
The XOR enumerates only 8 sequences. Many legitimate combinations that satisfy P1–P7 are missing, leading to catastrophically low holdout fitness (0.744). For example:
- `Register Dossier  Technical Review  Credit Check  Auto Approval  Release Order` (B2 – forbidden by C, but policy says valid)
- `Register Dossier  Technical Review  Credit Check  Supplier Review  Expedite Review  Auto Approval  Release Order` (valid external/urgent, B5 – rejected)
- Any sequence where `Correct Dossier` is followed by only one repeated check (e.g., only `Technical Review`); see §5 B6.

### Duplicate labels
With 8 branches, the activities “Credit Check”, “Technical Review”, etc., appear multiple times as separate transitions in the flat net (total 33 duplicate labels). This leads to ambiguous alignment mappings, complicates conformance diagnostics, and makes the model unmaintainable – changing the order of checks would require editing 8+ branches.

### Correction handling
Correction is captured only as one rigid pattern: `Credit Check  Technical Review  Correct Dossier  Credit Check  Technical Review`. It cannot represent:
- correction that affects only one check,
- more than one correction cycle,
- interleaving of the repeated checks.

### Holdout degradation
The sharp drop from 0.973 to 0.744 cannot be explained solely by truly noncompliant holdout traces; the data analyst (F4) states that several holdout cases combine `Supplier Review`, `Auto Approval`, and alternate check order in ways absent from training. These are *legitimate* unseen combinations, meaning Model C is rejecting valid business cases.

### High precision may be an artifact of memorising training variants
Because the log does not contain explicit negative examples and the model is exactly the disjunction of frequent training sequences, precision is measured only against those sequences. In effect, the model is a **positive trace acceptor** for the training set, not a general policycompliant model. The absence of duplicatecheckwithoutcorrection in the log may be accidental, not a guarantee that such behaviour is impossible.

### Maintainability
Adding a new legitimate variant would require appending yet another enumerated sequence, expanding the duplicatelabel count and making the model even harder to understand and verify.

# 6. Likely Metric Pathologies

The ten listed pathologies are ranked by estimated decision impact (highest first):

1. **Positivelogonly precision (F5)**  
   Model C’s 0.941 precision was computed only on traces present in the log. Without a curated negative suite containing policyforbidden traces (B3, B4, duplicate checks without correction), precision is essentially a measure of how closely the model mirrors the log, not its ability to reject violations. This drastically overstates C’s compliance value.

2. **Optionalisation of mandatory behaviour inflating fitness**  
   Model S achieves nearperfect fitness because it allows skipping Credit Check and Technical Review. This makes it resilient to missing events in the log, but the high fitness metric hides the fact that the model admits traces that are explicitly forbidden by business rules.

3. **Missingevent bias**  
   The log may be incomplete (F4: “some Supplier Review events may also be missing”). If a model designs around this by making everything optional, it appears favourable on fitness and generalization while undermining the very concept of a mandatory check. The metrics then reward a model that has abandoned policy fidelity.

4. **Duplicatelabel effects**  
   The 33 duplicate labels in Model C cause alignment to match events to multiple transitions with the same label, affecting fitness, precision, and runtime. It can artificially boost alignment fitness (a trace with one “Credit Check” can match any of the many CC transitions) but also introduces spurious nondeterminism that corrupts precision and generalisation calculations.

5. **Generalization rewarded by excessive permissiveness**  
   S’s high generalisation (0.907) arises because it can generate almost any interleaving of the four checks; it accepts behaviours far beyond the log, many of which are invalid. The metric penalises a model like C that refuses unseen paths, but does not distinguish between legitimate unseen behaviour and policy breaks.

6. **Train/holdout leakage or split sensitivity**  
   Without seeds and preprocessing code, we cannot exclude the possibility that the 20% holdout was not independently representative. The drop in C’s holdout fitness could be exacerbated by a split that left out rare combinations. Reproducibility is impossible to verify.

7. **Alignmentcost sensitivity**  
   The default standardcost function penalises model moves and log moves equally. If the cost were biased to favour modelside skipping (as with  transitions), S’s fitness would look even higher, while C’s would suffer from its many sequential constraints. The lack of published cost settings means we cannot compare alignment scores on an equal footing.

8. **Silenttransition effects**  
   S’s  choices hide missing mandatory checks as silent actions in the alignment, making the model appear to perfectly explain traces that actually lack required steps. The conformance diagnostics built on such alignments will not flag policy violations.

9. **Stakeholderscore methodology**  
   The subjective 1–5 score was collected informally, likely from a small group that already had a preference. A simple picture may outscore a messy net even if the messy net is closer to the truth. This metric should not influence a compliance decision.

10. **Runtime confounding by model size**  
    C’s 440 ms median is slower, but that is largely due to its 8branch enumeration and duplicate transitions. A wellstructured model of similar policy compliance could be much faster, so the runtime difference is not an inherent quality signal.

# 7. Third Alternative

Model `third` is a blockstructured process tree that directly implements P1–P7, admits the limitations of missing attributes, and is designed to be safer than Model S and more generalisable and maintainable than Model C.

### Compact formal description (process tree syntax)

```
->( 'Register Dossier',
    *( +( 'Credit Check', 'Technical Review' ),
       'Correct Dossier' ),
    +( X('Supplier Review', ), X('Expedite Review', ) ),
    X('Manager Approval', 'Auto Approval'),
    'Release Order'
)
```

**Operators**:
- `*(DO,REDO)` : loop – execute DO at least once; then optionally execute REDO and repeat DO. Applied to the mandatorychecks block.
- `+(A,B)` : parallel interleaving – A and B each execute exactly once, may interleave.
- `X(...)` : exclusive choice.

### PM4Py construction code

```python
import pm4py

model_third_str = (
    "->( 'Register Dossier', "
    "*( +( 'Credit Check', 'Technical Review' ), 'Correct Dossier' ), "
    "+( X('Supplier Review', tau), X('Expedite Review', tau) ), "
    "X('Manager Approval', 'Auto Approval'), "
    "'Release Order' )"
)

model_third = pm4py.parse_process_tree(model_third_str)
# Convert and verify soundness
net, im, fm = pm4py.convert_to_petri_net(model_third)
pm4py.check_soundness(net, im, fm, print_diagnostics=True)
```

### Declarative constraints / external checks

Because the `external/internal` attribute is absent from the log, the model cannot conditionally require Supplier Review. A **posthoc policy check** must be applied to conformance results:

```python
# pseudo-code
if order_type == 'EXTERNAL' and 'Supplier Review' not in trace:
    flag_policy_violation("Missing Supplier Review for external order")
```

If the required attribute becomes available, the model itself could be conditioned, but currently the honest approach is to accept the trace in the model and escalate the policy decision.

### Semantics for each policy

- **P1** – `Register Dossier` first, `Release Order` last; sequence operator enforces this.
- **P2** – `Credit Check` and `Technical Review` are mandatory (no  alternatives in the doblock). The parallel interleaving `+(CC,TR)` allows any order.
- **P3** – `Supplier Review` is optional via `X(Supplier Review, )`, because the attribute is missing. External orders will be caught by the posthoc check.
- **P4** – `Expedite Review` is optional, follows the mandatorychecks block (the loop must finish before the parallel block), and can interleave with Supplier Review. The parallel block `+( X(SR,), X(ER,) )` places ER either before or after SR.
- **P5** – Exactly one approval: `X('Manager Approval', 'Auto Approval')` after the optional reviews.
- **P6** – Correct Dossier may repeat via the loop `*( +(CC,TR), 'Correct Dossier' )`. After any execution of `Correct Dossier`, the whole doblock (both mandatory checks) repeats. This overapproximates: it repeats both checks even if only one was affected, but that is a safe, policyconservative choice given the missing `affectedcheck` attribute. It never misses a needed recheck.
- **P7** – A repeated mandatory check cannot occur without a preceding `Correct Dossier` because the net does not contain an explicit backedge from the checks to themselves; the only way to reenter the doblock is via the REDO transition labelled `Correct Dossier`. Therefore surprise duplicates are impossible.

### Limitations caused by missing attributes

1. **Supplier Review cannot be made conditional**: all traces without Supplier Review pass the model, even if they are external. The model alone does not flag the violation; the governance layer must intervene.
2. **Correction always repeats both Credit and Technical Check**, even if the correction affects only one. This may cause extra work in practice but ensures no incomplete reverification. If `affectedcheck` data became available, a refined model could offer a choice after `Correct Dossier` between repeating only CC, only TR, or both.
3. **No distinction between multiple correction cycles**: the loop allows arbitrarily many corrections, which is appropriate.

The model does **not** silently treat mandatory activities as optional; Credit and Technical Check are strictly required before any optional block.

# 9. Validation Experiments

A governanceworthy evaluation must be reproducible and adversarial, covering both statistical conformance and businesspolicy soundness.

### 9. Stakeholder comprehension measurement
Formalise: recruit 5 business analysts unfamiliar with the models, present each model as a BPMNlike diagram with a 10minute explanation, then administer a 10item multiplechoice test covering allowed paths, correction behaviour, and approval rules. Score out of 10; report median.

### 10. Decision rule for rejection despite good aggregate metrics
A model is **rejected** if it meets **any** of:
- Accepts 1 trace from the negative suite.
- Holdout fitness on the *compliant subset* (as validated by domain experts) drops below 0.95.
- Fails to discharge the correction loop (i.e., cannot replay a trace with one correction).
- Stakeholder comprehension score < 70 % correct.

This rule ensures that metric optimisation cannot mask policy failures.

# 10. Governance Recommendation

- **Model S** may be **retained for exploration** only. Its simplicity helps business users understand the rough sequence, but under no circumstances may it be used for conformance checking or compliance reporting, because it accepts traces that omit mandatory checks.
- **Model C** should be **retired**. Its maintenance cost (33 duplicate labels, fragile branch enumeration), inability to generalise to unseen but valid combinations, and misleadingly high precision without negative testing make it unsuitable for any governed use.
- **Third alternative** is **recommended for compliance**, subject to the following conditions:
  1. The posthoc `externalSupplier Review` check must be operational and documented.
  2. The model passes the validation experiments in §9, especially the negative suite and unseencombination tests.
  3. Until an `affectedcheck` attribute is available, the board accepts the conservative rechecking of both Credit and Technical checks after every correction.
  4. Stakeholder comprehension scores are formally measured and meet the threshold.

If any condition fails, the model must be refined (e.g., by integrating the external attribute if the log is enriched) before deployment.

# 11. Dissenting View

The third alternative, while an improvement, still compromises on two policy requirements that could expose the organisation to risk. First, it unconditionally repeats **both** Credit and Technical checks after a correction. If most corrections in reality affect only one check, the model will treat legitimate partialrework traces as noncompliant, potentially blocking orders and generating unnecessary rework. This overconstraint could create operational friction and undermine user trust. Second, by omitting the Supplier Review condition, a purely modelbased compliance pipeline might silently approve an external order that missed Supplier Review if the posthoc check is misconfigured or not executed. An integrated, attributeconditioned model (e.g., using the POWL StrictPartialOrder with conditional on `order_type`) would prevent this gap altogether, but we lack the attribute today.

A defender of Model C could argue that its trace catalogue, although brittle, guarantees that every accepted path was approved in the past – a conservative posture that avoids the risks of generating new combinations. The board might therefore prefer to delay deployment and instead invest in enriching logs with `external/internal` and `affectedcheck` data, then build a fully constraintaware model.

**What evidence would change the recommendation:** If a detailed audit of historical orders shows that corrections frequently involve only one check, and that forcing both to repeat would cause significant delays, the third alternative would need to be replaced with a conditional rework model. If the external/internal attribute can be added to the source system within a short timeframe, the governance recommendation should shift to waiting for that data and constructing a model with both conditional Supplier Review and selective rework, potentially using a declarative layer. Finally, if a controlled stakeholder comprehension study reveals that the loop construct in the third model is confusing to endusers even after training, a simpler linear path with adhoc rework annotations might be considered.
