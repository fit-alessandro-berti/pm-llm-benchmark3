## 1. Analytical assumptions

- **Case notion** – The object type whose life-cycle is traced when flattening the OCEL. A “case” is one instance of that type. Flattening pulls all events related to that instance into a single trace, duplicating shared events.
- **Convergence** – Multiple objects of the same type participate in the **same event**. In the flat log this produces one copy of the event in each converged object’s trace, inflating the apparent number of times the event occurred.
- **Divergence** – A single object participates in events that belong to **distinct, potentially parallel** sub-processes (e.g. an order split across several packages). In a flattened log this yields a trace with multiple branches, which correctly shows the object’s own journey but may complicate the DFG with repeated activity occurrences.
- **Copied shared events** – I treat them as **both** evidence that the object participated in that activity and as duplication that distorts simple frequency counts. Their timestamps are identical across copies, so any performance metric that relies on unique timestamps (e.g. waiting times computed from successive copies) may be biased.
- **Analytical transformations** – I permit relation propagation through the given O2O links (contains, packs, carries, bills, settles) as an optional transformation to enrich traces where direct E2O relations are insufficient. In this OCEL, direct relations already include the Order object in every event; therefore propagation is not needed for Order flattening but could be used to attach financial events to Items or Packages.

Lifecycle truncation before financial events prevents endtoend analysis. | **Low** – useful only for warehouse subprocess. |

## 3. Concrete distortion analysis

1. **Crossorder package e13 (Pack Package)**  
   *Affected flattening:* Order (also Item, Package)  
   *Events/objects:* e13 related to O2, O3, I21, I31, P3  
   *Distortion:* In the Orderflattened log e13 appears **twice**, once in O2’s trace and once in O3’s trace. The DFG edge from “Add Item” to “Pack Package” will be counted twice for a single physical packing act. This **inflates the apparent frequency** of packing activities across orders.  
   *Effect:* **Harmful** if the goal is to count actual pack operations; **informative** only if one explicitly interprets the event copy as representing the order’s participation.

2. **Crossorder package e14 (Pack Package)**  
   *Affected flattening:* Order, Item, Package  
   *Events/objects:* e14 with O3, O4, I32, I41, P4  
   *Distortion:* Same as above – e14 duplicated for O3 and O4. The total number of “Pack Package” events in the flat log becomes 7 while only 4 pack operations occurred.  
   *Effect:* **Harmful** for resourceplanning analyses that rely on activity counts.

3. **Consolidated delivery e16 (Dispatch)**  
   *Affected flattening:* Order (O1,O2,O3), Item (I12,I21,I31), Package (P2,P3)  
   *Events/objects:* e16 dispatches P2 and P3 together, carrying items from three orders.  
   *Distortion:* The Orderflattened log copies e16 **three times**, making it appear that three separate Dispatch events occurred. The DFG edge “Pack Package”  “Dispatch” (or “Add Item”  “Dispatch”) is inflated, and the fact that a single physical dispatch consolidated two packages is obscured.  
   *Effect:* **Harmful** for logistics analysis; it hides the consolidation strategy and overreports dispatch frequency.

4. **Consolidated invoicing e19 (Issue Invoice)**  
   *Affected flattening:* Order (O2,O3)  
   *Events/objects:* e19 issues invoice V2 for orders O2 and O3.  
   *Distortion:* e19 is copied into both O2’s and O3’s traces, suggesting two distinct invoices were generated, whereas only one invoice V2 exists. Invoicecount metrics would be **double the true value**.  
   *Effect:* **Harmful** for invoicing efficiency or revenue analysis; the sharedinvoice relationship is lost.

5. **Partial payments on V2 (Record Payment e22 and e25)**  
   *Affected flattening:* Invoice (V2), Order (O2,O3)  
   *Events/objects:* V2 is settled by M2 (e22) and M3 (e25).  
   *Distortion:* In the Invoiceflattened log, V2’s trace correctly shows two successive “Record Payment” events, which is **informative** and accurately reflects an instalment plan. In the Orderflattened log, both O2 and O3 receive copies of e22 and e25, creating two “Record Payment” events per order. Although technically correct (both orders are indeed linked to both payments), the causal relation “this payment was the first instalment” is lost when viewing the order trace alone. An analyst might misinterpret the two payment events as duplicate payments.  
   *Effect:* **Contextdependent** – accurate if accompanied by invoice detail, misleading if treated as independent payments.

6. **Nearsingleton lifecycle – Payment flattening**  
   *Affected flattening:* Payment (M1M4)  
   *Events/objects:* Each payment is related only to its own Record Payment event (M1e21, M2e22, M3e25, M4e26).  
   *Distortion:* Traces consist of a single event; no DFG edges can be mined, no performance indicators exist. All information about which invoice or order was paid is stripped away.  
   *Effect:* **Harmful** – the flattened log is analytically useless.

7. **Item lifecycle truncation**  
   *Affected flattening:* Item  
   *Events/objects:* Items never appear in Create Order, Issue Invoice, Record Payment, or Close Order events.  
   *Distortion:* The item’s trace ends after “Confirm Delivery” (e23/e24/e27). The time from “Add Item” to “Confirm Delivery” can be measured, but the full order cycle (e.g., time from order creation to payment) cannot. Performance metrics that rely on order closure are impossible.  
   *Effect:* **Harmful** for endtoend analysis; limited use only for warehouse subprocess KPI.

8. **Confirm Delivery duplication (e24)**  
   *Affected flattening:* Order (O1,O2,O3), Item (I12,I21,I31)  
   *Events/objects:* e24 confirms delivery of P2 and P3, involving three orders.  
   *Distortion:* Three copies of e24 appear in the Orderflattened log even though a single delivery confirmation event occurred. The DFG edge “Dispatch”  “Confirm Delivery” would be counted three times for one actual event, and the time between dispatch and delivery might be averaged over the duplicated timestamps, yielding misleading statistics.  
   *Effect:* **Harmful** for delivery performance monitoring; the real event multiplicity is hidden.

## 4. Traditional versus objectcentric analysis portfolio

**Flattened logs worth creating**  
- **Orderflattened log** – still the best singleobject view of the endtoend order lifecycle. It can safely answer: “What is the typical sequence of activities for an order?” and “How long does it take from order creation to closure?” **provided** that duplicate events are flagged and performance measures use only the *first* or *last* occurrence of a shared event per trace (e.g. use the maximum timestamp of “Confirm Delivery” for each order).  
- **Invoiceflattened log** – safely answers billingrelated questions: “How long does it take to issue an invoice after order creation?” (by joining with order data) and “How are payments structured?” The partialpayment pattern is correctly preserved.  
- **Itemflattened log** – safely answers warehouse questions: “What is the dwell time of an item from pick to dispatch confirmation?”

**Questions that must be answered with objectcentric techniques**  
- *How many crossorder packages are created, and which orders share them?*  Use the **OCDFG** to see the true multiplicity of “Pack Package” and “Dispatch” events, and **OTG** (ObjectType Graph) to visualise which orders are packed together.  
- *What is the real frequency of dispatch events?*  **OCDFG** shows each event exactly once, with counts of participating objects of each type.  
- *Which combinations of object types are typical in an execution?*  **ET–OT graph** (EventType to ObjectType mapping) reveals that “Dispatch” involves Order, Item, Package, and Delivery, while “Issue Invoice” involves Order and Invoice.  
- *How strongly are objects coupled?*  **Object interactions summary** quantifies convergence (e.g. how many orders share a package) and divergence (how many packages an order spawns).  
- *Are there distinct behaviour clusters among orders (e.g. orders that are always split vs. those shipped alone)?*  **Equivalentexecution clustering** on the OCEL (grouping by objectlifecycle similarity) can separate such clusters without imposing a flat case notion.

**Reconciling flattened and objectcentric views**  
- Compare the total count of an activity in the Orderflattened log (6 “Dispatch” occurrences) with the **distinct event count** in the OCDFG (3 unique Dispatch events). Flag the duplication ratio.  
- Use the OTG to overlay the true object relationships onto the order traces: a trace that shows two “Dispatch” events can be annotated with the fact that they correspond to two packages, and that one of those packages was shared with another order.  
- When the flattened DFG suggests a loop (e.g. “Record Payment”  “Record Payment” for an order), check the Invoiceflattened log and the object interactions to confirm whether that loop is caused by partial settlement or by true rework.  
- Performance metrics (e.g. cycle time) calculated from the flattened log should be validated by recalculating on the OCEL using **eventlevel aggregation** (e.g. maximum timestamp over all events related to an order) rather than on duplicate–inflated trace durations.

## 5. Leadobject decision

**Position B – Use a primary lead object (Order) together with explicitly defined secondary lifecycles (Invoice, Item, Package).**

*Decision criteria*  
- Coverage of the endtoend process – the lead object must appear in all relevant stages.  
- Acceptable distortion – duplication due to convergence must be manageable through analytical controls.  
- Analytical utility – the flattened log must support the most frequent business questions without requiring objectcentric tools for every query.

*Strongest supporting evidence*  
Order is the only object type that directly participates in **every activity type** recorded in the log (Create Order, Add Item, Pack Package, Dispatch, Issue Invoice, Record Payment, Confirm Delivery, Close Order). The direct E2O relations are comprehensive; no relation propagation is required. Consequently, a single Orderflattened log provides the longest, most complete traces and the richest process context.

*Strongest counterargument*  
Convergence of orders into shared packages, deliveries, and invoices causes **severe event duplication**. The flattened log inflates the apparent number of packing, dispatch, and deliveryconfirmation events, which may mislead analysts who treat the log as a faithful record of physical activities. The crossorder consolidation patterns are obscured, making it impossible to answer questions like “How many dispatch trips were made?” from the flat log alone.

*Residual risk*  
Users, especially those accustomed to traditional process mining, may trust the duplicated event frequencies and derive incorrect throughput or cost figures. Even with warnings, the flattened DFG can suggest a more fragmented process than reality.  
To mitigate this risk, any report derived from the Order log must explicitly quote the duplication factor and crossreference the OCDFG counts.

*Conditions for changing the decision*  
If the logistics operation frequently consolidated orders (e.g. majority of packages contain items from multiple orders), the duplication would become the dominant signal and the Order log would no longer provide a faithful representation. In that scenario I would **reject a single lead object** (Position C) and rely entirely on objectcentric analysis, using the OCEL’s native object interactions and the OCDFG as the primary discovery artefact. Secondary flattened logs (Item, Package, Invoice) would be retained for subprocess drilldown but never elevated to a global lead.

## 7. Sensitivity and validation plan

1. **Duplicationaware frequency analysis**  
   - Flatten on Order as usual.  
   - Derive a *deduplicated* event list by keeping only one copy of each event (by event ID) and count occurrences of each activity.  
   - Compare the deduplicated counts (Pack=4, Dispatch=3, Confirm=3, etc.) with the duplicated counts from the Orderflat log.  
   - Compute the **duplication ratio** (e.g. Dispatch appears 6÷3 = 2.0× inflated). This quantifies the inflation risk.

2. **Direct E2O vs. relationpropagated flattening**  
   - Create an Itemflattened log using only the direct E2O relations (as in Section2).  
   - Produce a **propagatedrelation variant**: From the O2O relation `Order contains Item`, follow `Order bills Invoice` and `Invoice settled by Payment` to attach Invoice and Payment events to each Item.  
   - Compare the two Itemflat logs: the propagated variant will include Issue Invoice, Record Payment, and Close Order events (whereas the direct variant lacks them).  
   - *Check* whether the addition of financial events changes the perceived duration (e.g. “Add Item” to “Close Order” now possible) and whether any duplication arises from items that share an order. This highlights how propagation can “complete” a lifecycle at the cost of further duplication.

3. **Changing the lead object**  
   - Flatten on Invoice (as the primary lifecycle).  
   - Compare the sequence and covered activities with the Orderflat log (Invoice misses Create Order, Add Item, Pack, Dispatch, Confirm Delivery, Close Order).  
   - Assess which business questions could still be answered (e.g. invoicetocash cycle) and which are lost.  
   - This tests the dependence of the analysis on the chosen lead object and supports the justification for a hybrid approach.

4. **Frequency metric comparison**  
   - From the **OCDFG**, extract the number of unique occurrences per activity (eventlevel count).  
   - From the **Orderflat log**, count total number of times each activity appears across all traces.  
   - Additionally, count the **number of distinct Order objects** that participate in each activity (available from the OCDFG annotations).  
   - Compare these three figures to illustrate how objectcentric analysis separates physical event counts from “participation” counts, and how the flat log confounds them. For example, for Dispatch: 3 unique events, 4 distinct orders involved, but 6 event copies in the Orderflat log. The discrepancy quantifies the convergence effect and guides the selection of the right metric for the question at hand.
