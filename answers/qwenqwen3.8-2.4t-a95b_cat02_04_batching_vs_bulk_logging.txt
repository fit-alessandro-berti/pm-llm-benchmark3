def pairwise_overlap(g):
    g = g.sort_values("start").reset_index(drop=True)
    n=len(g); overlapped=np.zeros(n, dtype=bool); pair_overlap_sec=0.0; simultaneous_ties=0
    for i in range(n):
       for j in range(i+1,n):
          s=max(g.at[i,"start"], g.at[j,"start"])

def pairwise_overlap(g):
    g = g.sort_values("start").reset_index(drop=True)
    n = len(g)
    if n == 0:
        return pd.Series({"events_with_positive_overlap": 0, "overlap_rate": np.nan, "pairwise_overlap_sec": 0.0, "simultaneous_tie_pairs": 0})
    overlapped = np.zeros(n, dtype=bool)
    pair_overlap_sec = 0.0
    tie_pairs = 0
    for i in range(n):
        for j in range(i+1, n):
            s = max(g.at[i, "start"], g.at[j, "start"])
            e = min(g.at[i, "complete"], g.at[j, "complete"])
            if pd.notna(s) and pd.notna(e):
                if e > s:
                    pair_overlap_sec += (e - s).total_seconds()
                    overlapped[i] = True
                    overlapped[j] = True
                if g.at[i, "start"] == g.at[j, "start"] and g.at[i, "complete"] == g.at[j, "complete"]:
                    tie_pairs += 1
    return pd.Series({
        "events_with_positive_overlap": int(overlapped.sum()),
        "overlap_rate": float(overlapped.mean()),
        "pairwise_overlap_sec": pair_overlap_sec,
        "simultaneous_tie_pairs": tie_pairs,
    })

def equality_metrics(g):
    if len(g) == 0:
        return pd.Series({"n_events": 0, "distinct_starts": 0, "distinct_completes": 0, "max_same_start": 0, "max_same_complete": 0, "max_same_start_complete": 0})
    return pd.Series({
        "n_events": len(g),
        "distinct_starts": g["start"].nunique(),
        "distinct_completes": g["complete"].nunique(),
        "max_same_start": g.groupby("start").size().max(),
        "max_same_complete": g.groupby("complete").size().max(),
        "max_same_start_complete": g.groupby(["start", "complete"]).size().max(),
    })

def lag_metrics(g):
    lag = g["record_lag_sec"].dropna()
    if len(lag) == 0:
        return pd.Series({"median_record_lag_sec": np.nan, "max_record_lag_sec": np.nan})
    return pd.Series({"median_record_lag_sec": lag.median(), "max_record_lag_sec": lag.max()})

def granularity_metrics(g):
    return pd.Series({
        "precision_sec": g["precision_sec"].iloc[0] if len(g) else np.nan,
        "start_boundary_pct": 100.0 * g["start_on_precision_boundary"].astype(float).mean() if len(g) else np.nan,
        "complete_boundary_pct": 100.0 * g["complete_on_precision_boundary"].astype(float).mean() if len(g) else np.nan,
        "zero_duration_pct": 100.0 * g["zero_duration"].astype(float).mean() if len(g) else np.nan,
    })

def queue_metrics(g):
    if len(g) == 0:
        return pd.Series({"arrivals_before_first_start": 0, "start_before_queue_count": 0, "median_queue_to_start_min": np.nan, "max_queue_to_start_min": np.nan, "median_queue_to_complete_min": np.nan, "queue_span_min": np.nan})
    first_start = g["start"].min()
    return pd.Series({
        "arrivals_before_first_start": int((g["queue_arrival"] < first_start).sum()) if pd.notna(first_start) else np.nan,
        "start_before_queue_count": int(g["start_before_queue"].sum()),
        "median_queue_to_start_min": g["queue_to_start_min"].median(),
        "max_queue_to_start_min": g["queue_to_start_min"].max(),
        "median_queue_to_complete_min": g["queue_to_complete_min"].median(),
        "queue_span_min": (g["queue_arrival"].max() - g["queue_arrival"].min()).total_seconds() / 60.0,
    })

- **Service time**: Durations of 10–25 minutes may be real case durations, but attribution to `analyst_pool` is ambiguous. If multiple analysts used the same login, each duration may belong to a different person.
- **Utilization**: If treated as one resource, overlapping intervals produce utilization above 100%. If treated as a pool of up to three analysts, utilization can be computed against capacity 3, but four overlapping cases during 13:12–13:20 exceed the stated capacity, indicating either identity ambiguity, timestamp approximation, pauses, or an incorrect capacity assumption.
- **Throughput**: Throughput is observable at the pool level, but individual productivity and bottleneck attribution are not.
- **Bottleneck/conformance**: Conformance checks based on a single resource identity are unreliable. The cluster should be analyzed as a pooled resource or excluded from individual-level conclusions.

**G6 — end batching/bulk submission or end-of-shift backfill**

- **Waiting**: Queue-to-logged-complete waiting is 35–175 minutes. This is inflated as a work-waiting metric because it includes unrecorded work, administrative delay, queue time, and bulk entry.
- **Service time**: Logged service time is zero for every ticket. This understates any real review or closure effort. If closure is purely an instantaneous administrative state change, zero may be technically correct, but the work content is missing.
- **Utilization**: Start equals complete, so interval-based utilization is zero or undefined. Counting all seven closures at 17:00 creates a fake spike.
- **Throughput**: Seven completions appear in one minute, creating an artificial end-of-period throughput burst.
- **Bottleneck/conformance**: This is the clearest example of how bulk logging can create both inflated waiting and near-zero service: `queue_arrival` is far before the bulk timestamp, so waiting looks long, while the bulk form collapses start and complete to the same timestamp, so service looks zero. Bottleneck analysis may falsely identify ticket closing as a sudden bottleneck at 17:00.

**G7 — timestamp coarsening / interval-censored lifecycle**

- **Waiting**: Naive queue-to-start waiting is negative for four of five cases because `start=14:00` precedes queue arrivals after 14:00. This is impossible under normal flow and strongly indicates rounding or backdating.
- **Service time**: The fixed 15-minute service time is not credible as a true duration; it is the quarter-hour interval produced by rounding.
- **Utilization**: All five intervals overlap completely from 14:00 to 14:15. If treated as exact, this implies impossible parallel use of one manual resource. If treated as interval-censored, utilization is unidentified within broad bounds.
- **Throughput**: All completions appear at 14:15, producing a coarse throughput spike.
- **Bottleneck/conformance**: Point-based conformance and bottleneck analysis should not be performed without raw timestamps or an interval model. The cluster should be represented by time bounds, not exact points.

**G8 — queue accumulation after capacity loss, then sequential batching**

- **Waiting**: Queue-to-start waiting is 38–58 minutes. Much of this is plausibly the 15:00–15:35 safety-check hold plus subsequent serial queueing. Clock differences mean the exact waiting time is uncertain.
- **Service time**: The 7-minute durations are consistent and supported by 1-second scanner precision. They are likely usable if scans represent execution.
- **Utilization**: The resource appears idle or unavailable before 15:38, then continuously busy from 15:38 to 16:13. This is a realistic capacity-loss-then-recovery pattern.
- **Throughput**: Throughput after the hold is about one item every 7 minutes.
- **Bottleneck/conformance**: The bottleneck may be the safety check or the hold that caused queue accumulation, not the repair triage activity itself. Conformance analysis should allow an external hold event and clock offset.

def pairwise_overlap(g):
    g = g.sort_values("start").reset_index(drop=True)
    n = len(g)
    if n == 0:
        return pd.Series({
            "events_with_positive_overlap": 0,
            "overlap_rate": np.nan,
            "pairwise_overlap_sec": 0.0,
            "simultaneous_tie_pairs": 0
        })

    overlapped = np.zeros(n, dtype=bool)
    pair_overlap_sec = 0.0
    tie_pairs = 0

    for i in range(n):
        for j in range(i + 1, n):
            s = max(g.at[i, "start"], g.at[j, "start"])
            e = min(g.at[i, "complete"], g.at[j, "complete"])
            if pd.notna(s) and pd.notna(e):
                if e > s:
                    pair_overlap_sec += (e - s).total_seconds()
                    overlapped[i] = True
                    overlapped[j] = True
                if g.at[i, "start"] == g.at[j, "start"] and g.at[i, "complete"] == g.at[j, "complete"]:
                    tie_pairs += 1

    return pd.Series({
        "events_with_positive_overlap": int(overlapped.sum()),
        "overlap_rate": float(overlapped.mean()),
        "pairwise_overlap_sec": pair_overlap_sec,
        "simultaneous_tie_pairs": tie_pairs,
    })

def equality_metrics(g):

        "distinct_completes": g["complete"].nunique(),
        "max_same_start": g.groupby("start").size().max(),
        "max_same_complete": g.groupby("complete").size().max(),
        "max_same_start_complete": g.groupby(["start", "complete"]).size().max(),
    })

def lag_metrics(g):

def granularity_metrics(g):

# 5. Robustness and alternative explanations

**Resource IDs trusted versus treated as shared accounts**

| Cluster / scope | If resource IDs are trusted as individual workers/resources | If resource IDs may be shared or pooled |
|---|---|---|
| G1 | `RBT-7` is a machine cell; individual identity is less problematic, but capacity must be modeled as a four-item fixture. | Shared account is not the main issue; batch semantics remain the main issue. |
| G2–G4, G6, G8 | Single-resource interpretations are mostly coherent: one inspector, one packer, one closer, one triage operator. | If tablets/scanners/forms are shared, utilization and responsibility become ambiguous. Overlaps or rapid sequences could reflect multiple people using one ID. |
| G5 | If `analyst_pool` is treated as one person, the data are impossible or highly suspicious because four cases overlap and the stated pool size is up to three. | The overlaps become plausible as a shared-account artifact. Metrics must be computed at pool level with capacity up to 3, and even then the four-way overlap requires validation. |
| All clusters | Resource-based conformance checks can be applied directly. | Resource-based conformance checks should be weakened or replaced by pool/session-level checks. |

**Timestamps exact versus interval-censored by stated precision**

| Cluster | If timestamps are treated as exact | If timestamps are interval-censored by stated precision |
|---|---|---|
| G1 | Exact same start/end strongly supports a simultaneous batch cycle. | With 1-second precision, uncertainty is small; batch interpretation remains dominant, but PLC logging semantics still matter. |
| G2 | Exact common start supports a deliberate group start. | With 1-minute precision, true starts could differ within the minute, but the UI context still favors group start. |
| G3 | Exact common completion supports bulk submission. | With 1-minute precision, true completions could differ within the minute; still, all completions in the same minute strongly suggests bulk submission. |
| G4 | Exact adjacency strongly supports serial processing. | With 1-second precision, uncertainty is small; serial interpretation is robust. |
| G5 | Exact overlaps suggest concurrent work or shared account. | With 1-minute precision, overlaps are still too large to be explained by rounding alone; identity remains the main uncertainty. |
| G6 | Exact zero duration suggests instantaneous closure or bad lifecycle capture. | With 1-minute precision, true duration could be less than a minute, but the bulk form and 2+ hour arrival spread still argue against true service time. |
| G7 | Exact interpretation is invalid: starts precede arrivals and all durations are exactly 15 minutes. | Interval-censored interpretation is required. True starts/completes may lie within quarter-hour windows; point estimates should not be used. |
| G8 | Exact adjacency supports serial processing after a hold. | With 1-second precision, serial processing is robust, but the safety-system clock offset means the exact start of availability is uncertain. |

**At least three cases where the same temporal pattern supports multiple physical explanations**

1. **G1: identical start and end timestamps**  
   This can mean a genuine simultaneous four-item batch on one fixture, or it can mean the PLC recorded one batch cycle and applied the same cycle timestamps to all four items. The temporal pattern alone does not prove item-level physical concurrency.

2. **G3/G6: identical completions or zero-duration completions**  
   Identical completions can mean end batching/bulk submission, a genuine common deadline, instantaneous administrative closure, or end-of-shift backfill. In G6, `start=complete=17:00` can be a true instantaneous state change or a bulk data-entry artifact.

3. **G5: overlapping intervals under one resource ID**  
   Overlaps can mean shared-account use by multiple analysts, true concurrent work by a pooled resource, multitasking by one person, or coarse logging of interrupted work. The supplied context says shared login is possible, but identity is missing.

4. **G7: quarter-hour ties**  
   The 14:00–14:15 pattern can be timestamp coarsening, a real batch, a common setup, or interval-censored serial work. The documented 15-minute precision makes coarsening the most defensible explanation, but it does not identify the underlying physical pattern.

| Priority | Area | Recommendation | Why it matters for this data |
|---|---|---|---|
| P1 | Execution timestamps | Capture item-level true `work_start`, `work_complete`, and any pause/resume times, separate from UI submission time. | G2, G3, G6, and G7 all suffer from ambiguity between execution and logging. |

# 7. Final adjudication

**Clusters that can be interpreted with high confidence, with the stated caveat**

- **G4**: High confidence as sequential serial processing of a short backlog, assuming scanner start/complete reflect execution.
- **G8**: High confidence as queue accumulation followed by serial clearing, with the caveat that the safety-system clock offset and exact blocking effect need validation.
- **G1**: High confidence that the pattern is a batch/cycle event, but it must be modeled as a four-item fixture cycle, not four independent parallel resource tasks.
- **G2**: High confidence that the equal starts are a group-start/logging artifact rather than four independent physical starts.
- **G3**: High confidence that the equal completions are bulk submission/end batching rather than true simultaneous completion.
- **G6**: High confidence that the timestamps represent bulk administrative entry or closure, not usable service durations.
- **G7**: High confidence that the point timestamps are coarsened/rounded, but low confidence in the underlying true execution times.

**Clusters that should be excluded from point-based queue analysis or interval-censored**

- **G7**: Exclude from point-based waiting/service/utilization analysis. Use interval-censored bounds based on the 15-minute precision and recover the rounding rule if possible.
- **G6**: Exclude from service-time and utilization analysis unless closure is confirmed to be truly instantaneous. Waiting to bulk submission can be reported, but it should be labeled as administrative delay, not pure queue waiting.
- **G5**: Exclude from single-resource utilization and individual accountability analysis until identity or session data are recovered. Pool-level analysis with capacity up to 3 is possible, but the four-way overlap still requires validation.
- **G2 and G3**: Do not use raw overlapping intervals for single-resource utilization. Use bounds or corrected serial estimates: for G2, completion increments are more plausible service proxies; for G3, start-to-start increments or folder-level work windows are more plausible than start-to-bulk-complete durations.
- **G1**: Do not use four overlapping item intervals as four units of resource busy time. Normalize by fixture capacity or analyze at batch-cycle level.

**Clusters requiring operational validation before performance conclusions**

- **G1**: Validate whether PLC timestamps are item-level or fixture-cycle-level, and whether the four items are physically processed simultaneously.
- **G2**: Validate the “begin group” button semantics and whether inspectors ever work on multiple items concurrently.
- **G3**: Validate whether staggered starts are true case openings and whether completions are only folder submission times.
- **G5**: Validate the number of analysts, shared-login behavior, and whether four overlapping cases can occur due to pauses, incomplete status updates, or more than three analysts.
- **G6**: Validate whether ticket closure is instantaneous administrative action or whether actual work occurred earlier and was backfilled.
- **G7**: Validate the legacy MES rounding rule and obtain raw timestamps if available.
- **G8**: Validate the clock offset between the safety system and repair queue, and confirm whether the safety check fully blocked repair triage.
