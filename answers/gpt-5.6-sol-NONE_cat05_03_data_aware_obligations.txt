## 1. Temporal Data Semantics

- Events are ordered within each case by `(time:timestamp, event_index)`. Thus a lower `event_index` is earlier when timestamps are equal.
- Blank attribute cells mean **no update**. State is reconstructed by forward-filling each changing attribute—`amount`, `risk_level`, `jurisdiction`, and `customer_type`—only from prior events in that order. Future values are never copied backward.
- The state governing `Release_Funds` is the state immediately after applying any updates on that release event. A final case attribute is not presumed to have governed earlier events.
- A material data change is an update to data relevant to an obligation. For R1 this includes at least amount, jurisdiction, and customer type where exemption matching is relevant. For R2 it includes risk and customer type, plus amount changes that invalidate an amount-dependent Enhanced Review. R4 separately determines whether an amount increase invalidates a review.
- For R4, compare an amount update with the latest known amount at the latest Standard or Enhanced Review:
  - increase `>20%`: review invalidated for amount-dependent obligations;
  - decrease: not invalidated merely because it occurred after review;
  - increase from an unknown review amount: not safely classifiable.
- Four time notions remain distinct:
  - **Event time:** when the transaction event happened.
  - **Effective time:** when an exemption or other fact legally became operative.
  - **Record time:** when the database recorded it.
  - **Evidence time:** when reliable evidence was created, signed, or independently timestamped.
- A record created after release may prove an earlier fact, but only if reliable evidence supports the earlier effective approval. EX-77 has such evidence; EX-88 does not conclusively establish timely approval.
- For equal timestamps, source order is decisive. In TX-311, Enhanced_Review at index 3 precedes the jurisdiction change at index 4. The review therefore occurred while jurisdiction was US; the later DE value is not copied backward.
- Missing decisive state is not defaulted to benign values. If a trigger cannot be established or excluded, the result is `INDETERMINATE` unless independent evidence resolves it.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| R1 | At release, jurisdiction  DE and amount  100,000 | Enhanced_Review | After latest relevant material change and before release | Event-time state at release, plus state/history around review | Matching exemption valid before trigger/release, waiving R1 | Unknown jurisdiction or amount that could change activation  indeterminate | Review timestamp/order; amount and jurisdiction history; exemption approval, effective, expiry, scope and evidence timestamps |
| R2 | At release, risk = HIGH or customer type = PEP | Enhanced_Review and then Compliance_Approve | Relevant Enhanced_Review < Compliance_Approve < release; Enhanced Review must remain valid | Release risk/type; review-time and subsequent change history | No stated exemption | Unknown risk/type that could activate rule  indeterminate | Review packet/type, approval linkage and event ordering |
| R3 | Current release jurisdiction was added after latest screen but before release | New Sanctions_Screen | latest prior screen < applicable list update < new screen < release | Release jurisdiction and list/screen history | None stated | Unknown jurisdiction or update applicability  indeterminate | Versioned sanctions-list update and screening result/version |
| R4 | Amount increases by >20% after latest Standard or Enhanced Review | New valid review where amount-dependent obligation applies | review < qualifying increase < replacement review < release | Amount known at review and later updates | Decrease alone does not invalidate | Unknown baseline means increase cannot safely be classified | Amount observed by review, update provenance, review timestamp |
| R5 | Exemption asserted against an obligation | Timely Head_Compliance approval with matching effective scope | approval must exist by relevant time; effective_from  trigger; trigger < expiry | State at obligation trigger | Valid exemption according to all criteria | Missing/contradictory approval evidence  exemption unresolved | Signatures, signer identity, certificate timestamp, scope, effective/expiry and record time |
| R6 | Decisive trigger attribute absent | Evidence resolving missing value | Evidence must support value at relevant event, not merely later state | Relevant event-time snapshot | None | Indeterminate if activation cannot be established or excluded | Immutable event payload or reliable contemporaneous evidence |
| R7 | Any temporal comparison | None; establishes evaluation semantics | Earlier means lower `(timestamp,event_index)`; updates apply at their event | Event-time state | Explicit evidence of another effective time | Ambiguous ordering  indeterminate unless resolved | Stable event index or sequence ID and timestamp provenance |

Let `e1  e2` mean:

```text
e1.timestamp < e2.timestamp
or
(e1.timestamp = e2.timestamp and e1.event_index < e2.event_index)
```

Let `State(c,e,a)` be the latest nonblank update of attribute `a` at an event `u` such that `u  e`. Let `Release(c,r)` identify a release event.

Concise pseudo-logic:

```text
R1:
TriggerR1(c,r) :=
    Release(c,r)
     State(c,r,jurisdiction) is known
     State(c,r,jurisdiction)  DE
     State(c,r,amount) is known
     State(c,r,amount)  100000.

ComplyR1(c,r) :=
    ValidExemption(c,r,R1)
     h [EnhancedReview(c,h)
           LatestRelevantMaterialChange(c,r)  h
           h  r
           ¬InvalidatedForAmount(c,h,r)].

If an operand decisive to TriggerR1 is unknown and both activation and
nonactivation remain possible, classify R1 as indeterminate.

R2:
TriggerR2(c,r) :=
    Release(c,r)
     (State(c,r,risk)=HIGH  State(c,r,customer_type)=PEP).

ComplyR2(c,r) :=
    h,a [EnhancedReview(c,h)
           ComplianceApprove(c,a)
           h  a  r
           RelevantToCurrentR2State(c,h,r)
           ¬InvalidatedForAmount(c,h,r)].

A Compliance_Approve linked only to Standard_Review does not satisfy R2.

R3:
TriggerR3(c,r) :=
    s,u [s = LatestSanctionsScreenBefore(c,r)
           SanctionsListUpdate(u, State(c,r,jurisdiction))
           s  u  r].

ComplyR3(c,r) :=
    s2,u [SanctionsListUpdate(u, State(c,r,jurisdiction))
            u  s2  r
            SanctionsScreen(c,s2)].

R4:
InvalidatedForAmount(c,v,r) :=
    Review(c,v)
     u [v  u  r
           Known(AmountAtReview(c,v))
           Amount(c,u) > 1.20 * AmountAtReview(c,v)
           no later qualifying review occurs after u and before r].

If AmountAtReview(c,v) is unknown and a later amount may be an increase,
the invalidation result is indeterminate. A decrease is not invalidating.

R5:
ValidExemption(c,r,k) :=
    x [Referenced(c,r,x)
         Waives(x,k)
         ApprovedBy(x,Head_Compliance)
         EvidenceSupportsApprovalExistingBy(x,r)
         EffectiveFrom(x)  ObligationTriggerTime(c,r,k)
         ObligationTriggerTime(c,r,k) < Expires(x)
         ScopeMatches(x, State(c,r,jurisdiction),
                          State(c,r,customer_type),
                          State(c,r,amount))].

RecordTime(x) > r does not alone defeat validity, and displayed
ApprovalTime(x) < r does not alone prove validity.

R6:
If a missing attribute is decisive and neither Trigger nor ¬Trigger can
be established from admissible evidence, Outcome := INDETERMINATE.

R7:
All state and temporal predicates use  and  over
(timestamp,event_index). No terminal state is projected backward.
```

“Latest material change” should be interpreted relative to the obligation. A literal interpretation that every jurisdiction update invalidates an Enhanced Review produces an issue in TX-311; that ambiguity is discussed below.

## 4. Ambiguities and Alternative Readings

### TX-302

The late database insertion does not imply post-hoc approval. The qualified signature timestamp of 09:05 and documented outage strongly establish that Head_Compliance approval existed before the 09:40 release.

The result could change if:

- the signature did not authenticate the exemption content or signer;
- the signed document’s scope differed from the register;
- the amount, jurisdiction, or customer type at release differed from the reconstructed state; or
- “matching exemption was already valid” required database registration before release rather than substantive approval. That reading is not supported by R5 and would improperly equate record time with approval time.

Because an Enhanced Review occurred at 09:20, TX-302 may alternatively be classified `COMPLIANT` rather than `JUSTIFIED_EXCEPTION`. The chosen classification highlights that the referenced exemption itself is valid.

### TX-305

The 150,000 settlement amount is reliable only at settlement time. It does not establish the release amount because:

- settlement occurred the next day;
- there is no immutable release payload;
- the facts say settlement “may equal” the release amount rather than must equal it.

If a signed release instruction, ledger snapshot, or review attachment showed that the amount was 150,000 at 11:30, R1 would activate. The existing Enhanced Review could satisfy R1 only if evidence showed it reviewed that amount/current state; its document currently has no amount. Conversely, reliable evidence that the release amount was below 100,000 would make R1 inactive. Hence `INDETERMINATE`.

### TX-310

EX-88 has matching displayed scope and dates, but the evidence of approval existing before release is contradictory:

- displayed approval: 08:50;
- alleged oral approval: 08:45;
- release: 10:00;
- qualified certificate creation: 10:30;
- witness: transaction requester, not independent.

A contemporaneous call recording, Head_Compliance confirmation backed by immutable metadata, signed approval token, or independent witness could establish timely approval and yield `JUSTIFIED_EXCEPTION`. Proof that no approval occurred until certificate creation would yield `NONCOMPLIANT`. Treating a displayed backdated field as conclusive would conflict with R5.

### TX-311

By event order, the Enhanced Review occurred at index 3 while jurisdiction was US, and the jurisdiction changed to DE at index 4. It is incorrect to say the review saw DE merely because both events share 16:20.

Under the primary reading, R1 is evaluated at release, where jurisdiction is DE, so R1 is inactive and the case is `COMPLIANT`.

Alternative readings include:

1. **Broad material-change reading:** every jurisdiction change after review requires a new Enhanced Review, even when the new state removes the R1 trigger. This could produce a deviation, though it sits uneasily with “At Release_Funds” and would require a review for an obligation no longer active.
2. **Persistent-trigger reading:** once R1 was activated by the 115,000/US state before review, it persists despite a later change to DE. The policy does not expressly state persistence, so this is weaker than the release-state reading.
3. **Substantive materiality reading:** USDE is nonmaterial to R1 because it lowers or removes the obligation. This supports the primary compliant result.

A rule-versioned definition of “material change,” including whether trigger-removing changes invalidate reviews, would resolve the ambiguity.

### TX-301

The amount increase is unambiguously over 20%. Even if the Standard Review had occurred after the increase, it would still not meet R1 because a Standard Review is not an Enhanced Review. A valid matching exemption or a post-increase Enhanced Review before release would change the outcome.

### TX-307

The Compliance Approve note explicitly says it approved a standard packet. Under the supplied semantic fact, that cannot cure the missing Enhanced Review. The result would change only if evidence showed that the packet actually contained and the approver considered a completed Enhanced Review, or if policy were interpreted to allow approval itself to subsume the enhanced-review function. That interpretation conflicts with R2’s requirement for both events.

### TX-308

The decrease does not invalidate the Enhanced Review. A stricter interpretation requiring every amount change—up or down—to cause rereview would make the case noncompliant, but that would contradict R4’s express statement that a decrease does not by itself invalidate review.

The coarse code intentionally leaves evidential disputes as `REVIEW_REQUIRED`. ## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage:** A conventional case table may show TX-311 as DE and accidentally attribute DE to the earlier Enhanced Review. Correct event-time reconstruction shows the review occurred while the state was US.
2. **Conditional activation:** The same trace fragment can be compliant or noncompliant depending on amount, jurisdiction, risk, and customer type. `Release_Funds` does not always require Enhanced Review.
3. **Post-hoc exemptions:** A trace sees `Record_Exemption` after release but cannot decide whether it records a valid earlier approval, as with EX-77, or weak/backdated evidence, as with EX-88.
4. **Material changes after review:** The sequence `Enhanced_Review  Update_Amount  Release_Funds` is not inherently compliant or noncompliant. TX-308 has a non-invalidating decrease; TX-309 has an invalidating increase over 20%.
5. **Missing data:** Control flow cannot distinguish a genuinely low amount from an unknown amount. TX-305 must not be treated as below threshold merely because amount is absent.
6. **Same-timestamp ordering:** Timestamp-only discovery may treat TX-311’s review and jurisdiction update as simultaneous or reorder them. `event_index` establishes that the update occurred after review.
7. **Review type semantics:** `Standard_Review` and `Enhanced_Review` may look like interchangeable review activities in a simple model, but policy explicitly distinguishes them.
8. **Approval linkage/content:** A `Compliance_Approve` event is insufficient without knowing what packet it approved. TX-307’s approval concerns a standard packet.
9. **Sanctions-list applicability:** A generic list-update event matters only if it concerns the current jurisdiction and falls after the relevant screen but before release.
10. **Evidence versus occurrence:** An event log records assertions; it does not by itself establish reliability, signer authority, certificate validity, or whether a displayed effective date is genuinely supported.
11. **Scope matching:** Exemption validity depends on amount ceiling, jurisdiction, customer type, waiver type, expiry, and approval authority—not merely the presence of an exemption ID.
12. **Rule-relative materiality:** A jurisdiction change may activate, remove, or leave an obligation unchanged. A pure precedence model cannot express this nuanced effect.

DECLARE-style precedence can express statements such as “Enhanced Review precedes Release,” but not faithfully “if release-state jurisdiction is non-DE and release-state amount is at least 100,000, require a non-invalidated Enhanced Review after the latest legally material change unless a timely, evidenced, scope-matching exemption waives only R1.”

## 7. Recommended Logging and Control Improvements

1. **Immutable release payload**
   - Store signed or hash-addressed release-time amount, currency, jurisdiction, risk, customer type, sanctions-list version, and exemption reference.
   - Include the exact state version consumed by the release decision.

2. **Separate temporal fields**
   - Record `event_time`, `effective_time`, `record_time`, `ingestion_time`, and `signature_time`.
   - Preserve certificate creation and trusted timestamp-authority times separately from displayed document dates.

3. **Stable event ordering**
   - Use a monotonic per-case sequence number assigned at source.
   - Preserve source-system sequence, transaction ID, and tie-breaker through ETL and PM4Py export.
   - Define ordering across systems where list updates and transaction events interact.

4. **Review scope snapshots**
   - Each review should store the reviewed amount, jurisdiction, risk, customer type, source-data versions, and document hash.
   - Record whether the review is Standard or Enhanced and which rule obligations it satisfies.

5. **Approval linkage**
   - `Compliance_Approve` should reference the exact Enhanced Review ID and packet hash.
   - Record approver role, authority at approval time, decision, conditions, and signature evidence.

6. **Exemption structure**
   - Log exemption ID, waived rule IDs, jurisdiction scope, customer-type scope, amount bounds, currency, effective/expiry times, approver, signature timestamp, record timestamp, and evidence strength.
   - Do not represent approval solely through free text or a displayed backdated field.

7. **Change provenance**
   - For every update, record old value, new value, reason, source system, actor, source-document ID, confidence, and effective time.
   - For amounts, record currency and conversion rate/version where thresholds are EUR-based.

8. **Automated materiality calculation**
   - Persist review baseline amount and calculated percentage change.
   - Generate an explicit `Review_Invalidated` event identifying the review, rule, threshold, and triggering update.
   - Distinguish increases, decreases, and unknown-baseline changes.

9. **Sanctions controls**
   - Version every sanctions list.
   - Store affected jurisdictions/entities and effective time for each update.
   - Each screen should identify the list version, screening inputs, result, and immutable response.

10. **Rule versioning**
    - Store the policy/rule version evaluated at review, approval, exemption, and release.
    - Define rule-specific “material change,” including whether trigger-removing changes require rereview.

11. **Missing-value controls**
    - Represent “unknown,” “not applicable,” “not yet received,” and “no update” distinctly.
    - Block release or require an explicit authorized override when decisive fields are unknown.

12. **Decision audit events**
    - Emit a `Release_Compliance_Decision` event containing activated rules, satisfied obligations, accepted exemptions, unresolved facts, rule-engine version, input-state hash, and decision rationale.
    - Preserve both machine determination and any human override with separate identities and timestamps.
