# **1. Stipulated Facts, Disputed Propositions, and Burden of Proof**

  - Manual_Procurement_Approval before Activate_Supplier.
  - Different requester and manual approver (resource rule).
- **PD-3** (pilot) allows Auto_Approve for LOW-risk DE suppliers in approved corporate groups (2026-06-01 to 2026-07-31), with Quality_Review deferred up to 2 business days.
- **FD-7** (emergency) permits provisional activation without Quality_Review or manual approval (2026-07-10–12), with retrospective compliance required.
- **N4** (CRM migration) caused notification data loss (70% missing post-migration).
- **Observed Cases** show:
  - SUP-701: Strict CS-9 compliance.
  - SUP-702: PD-3 compliant (Auto_Approve, deferred Quality_Review).
  - SUP-703: PD-3 misapplied (ineligible supplier).
  - SUP-704/SUP-705: FD-7 compliance (provisional activation, retrospective approval).
  - SUP-706: Notification missing (data quality issue).
  - SUP-707: Request_More_Info loop (not in M0).
  - SUP-708: Sanctions_Check after activation (violates CS-9).
  - SUP-709: Rejected lead (scope ambiguity).
  - SUP-710: Reactivation (no explicit policy).
  - SUP-711: Duplicate Register_Supplier (data artifact).
  - SUP-712: Same requester/approver (resource rule violation).
  - SUP-713: Label equivalence (QA_Clearance  Quality_Review).
  - SUP-714: Post-pilot Auto_Approve (no permanent policy).
  - SUP-715: Approver/quality reviewer are spouses (conflict of interest).

### **Disputed Propositions (Requiring Authority/Interpretation)**
- **Scope of M0**: Does M0 apply to rejected leads (SUP-709)? To reactivations (SUP-710)?
- **Pilot Authority**: Was PD-3 retroactively approved? Did operations normalize pilot flows without formal amendment?
- **Emergency Continuation**: Did FD-7’s intent persist after expiry (SUP-705)?
- **Notification Completeness**: Is missing notification (SUP-706) a data issue or a process deviation?
- **Request_More_Info**: Is this a loop or a series of parallel checks? Should it be in M0?
- **Label Equivalence**: Is QA_Clearance functionally equivalent to Quality_Review (SUP-713)?
- **Conflict of Interest**: Does CS-9 explicitly prohibit approver/quality reviewer relationships (SUP-715)?

### **Burden of Proof**
- **Noncompliance**: Must show a case violates CS-9’s **control-flow** or **resource rules** *and* lacks a valid exception (PD-3, FD-7, or formal amendment).
- **Exception Acceptance**: Must demonstrate:
  - The deviation was **intentionally authorized** (e.g., PD-3, FD-7).
  - The exception was **applied correctly** (e.g., SUP-702 meets PD-3 criteria).
  - **Data quality** does not obscure intent (e.g., SUP-706’s notification loss is not a process violation).
- **Model/Data Defect**: Must show M0’s **scope**, **concurrency**, or **labeling** misrepresents reality (e.g., missing loops, incorrect concurrency).

# **2. Prosecution Brief: Noncompliance Case**

### **Formal Authority and Expiry**
- **CS-9 is the supreme standard**; PD-3 and FD-7 are **temporary exceptions** with explicit expiry dates.
  - PD-3 expired 2026-07-31. Post-pilot Auto_Approve (SUP-714) is **unauthorized**.
  - FD-7 expired 2026-07-12. SUP-705’s activation lacks retrospective approval documentation.
- **No formal amendment** exists for permanent Auto_Approve or relaxed approval rules. Operations’ normalization (SUP-714) is **policy circumvention**.

### **Deviations Hidden by M0**
- M0’s **strict concurrency** masks:
  - **SUP-708**: Sanctions_Check *after* activation (violates CS-9’s "before activation" rule).
  - **SUP-704/SUP-705**: Provisional activation without manual approval (FD-7 was emergency-only).
- **Missing loops**: SUP-707’s Request_More_Info cycles are **unmodeled**, enabling indefinite delays.

### **High-Risk Cases**
- **SUP-703**: PD-3 ineligible (HIGH-risk foreign supplier), but Auto_Approve was used. **No retrospective approval**.
- **SUP-708**: Sanctions_Check after activation. **No transactions occurred before clearance**, but the model allows it.
- **SUP-715**: Approver/quality reviewer are spouses. **No conflict-of-interest disclosure**, violating implicit CS-9 intent.

### **Desirable Outcomes  Policy Amendment**
- Operations’ preference for Request_More_Info loops (SUP-707) does not justify **retroactive policy change**.
- **Auto_Approve normalization** (SUP-714) is **gaming the system** until formal approval.

### **Aggregate Evidence**
- **312 Auto_Approve cases** in pilot window: 289 compliant, 14 ineligible (SUP-703), 9 ambiguous.
- **47 Request_More_Info cases**: All activated after evidence arrived, but **no formal loop in M0**.
- **Notification missingness**: 29% post-migration (SUP-706) suggests **data, not process**, is the issue—but missing notifications still violate CS-9’s "Notify_Requester" requirement.

### **Conclusion**
The operation **systematically violates CS-9** by:
1. Misapplying PD-3 (SUP-703, SUP-714).
2. Ignoring FD-7’s expiry (SUP-705).
3. Bypassing manual approval (SUP-708).
4. Failing resource rules (SUP-712, SUP-715).
5. Lacking formal amendments for desirable practices (Request_More_Info loops).

**M0 is a facade**—it does not reflect actual deviations or exceptions.

# **3. Defense Brief: Model and Scope Defects**

### **M0 is Obsolete**
- **PD-3 and FD-7 were not incorporated** into M0 despite operational necessity.
- **CRM migration (N4)** broke notification tracking, but M0 remains unchanged.
- **Reactivations (SUP-710)** and **rejected leads (SUP-709)** are **out of scope** but occur in practice.

### **Missing Concurrency and Loops**
- **Sanctions_Check and Quality_Review** are correctly concurrent in M0, but:
  - **FD-7 allows Quality_Review after activation** (SUP-704/SUP-705).
  - **Request_More_Info is a loop**, not a parallel task (SUP-707).
- **Auto_Approve is missing**—M0 only models Manual_Procurement_Approval.

### **Pilot/Emergency Overlays**
- **PD-3 was a steering-committee decision**, not a formal amendment. Operations **normalized it** post-expiry (SUP-714).
- **FD-7’s intent persisted informally** (SUP-705), but no written extension exists.
- **Compliance observer’s note** ("monitored exception") suggests **de facto acceptance**.

### **Data Quality vs. Process**
- **SUP-706’s missing notification** is a **data artifact**, not a process deviation.
- **SUP-711’s duplicate Register_Supplier** is a **logging error**, not a control-flow issue.
- **SUP-713’s QA_Clearance** is functionally equivalent to Quality_Review (audit confirms).

### **Scope Ambiguities**
- **Rejected leads (SUP-709)**: Process owner says M0 begins after pre-screen; model owner says it applies to all cases. **Ambiguity favors operations**.
- **Reactivations (SUP-710)**: No explicit policy, but prior certification remains valid. **De facto compliance**.

### **Risk vs. Limits on Informal Practice**
- **SUP-703 (PD-3 misapplication)**: Ineligible but low-risk (EUR 180K). **No harm occurred**.
- **SUP-708 (Sanctions after activation)**: No transactions before clearance. **No actual risk**.
- **SUP-715 (Conflict of interest)**: No disclosure, but no evidence of bias. **Policy violation, but low material risk**.

### **Conclusion**
M0 is **incomplete** because it:
1. Omits **pilot/emergency routes**.
2. Lacks **loop support** for Request_More_Info.
3. Does not account for **reactivations/rejected leads**.
4. Assumes **perfect data quality** (notions).

**Operations adapted to real-world constraints**—M0 is **theoretical**.

# **6. Revised Normative Architecture**

### **Layered Architecture**
| Layer | Component | Purpose | Example Rules |
|-------|-----------|---------|---------------|
| **1. Control-Flow (POWL)** | StrictPartialOrder + OperatorPOWL | Model standard, pilot, emergency, and loop paths. | Sanctions  Quality  (Manual_Approve  Activate)  Auto_Approve  Provisional_Activate |
| **2. Data-Aware Constraints** | DECLARE/log-skeleton | Enforce eligibility, timing, and amount rules. | `Auto_Approve  (LOW_RISK  DE  CORPORATE_GROUP_MEMBER)` |
| **3. Resource Rules** | pandas/data checks | Enforce requester/approver separation, conflicts. | `requester_id  manual_approver_id` |
| **4. Policy Overlays** | Organizational controls | Govern pilots/emergencies (e.g., FD-7 expiry). | `FD-7_active  Provisional_Activate  Quality_Review(deferred)` |
| **5. Scope Rules** | Explicit documentation | Clarify rejected leads, reactivations, withdrawals. | `Rejected_Lead  NOT(Register_Supplier  Quality_Review)` |

### **Key Improvements**
1. **Pilot Route**: Explicit Auto_Approve branch with eligibility checks.
2. **Emergency Route**: Provisional_Activate with retrospective approval.
3. **Request_More_Info**: Modeled as a **repeatable silent transition** (or parallel task with evidence validation).
4. **Rejected Leads**: Explicit exclusion from M0 scope.
5. **Reactivations**: New path with prior certification validation.
6. **Notification**: Stable `notification_id` + immutable timestamps.

# **7. PM4Py Model and Data Proposal**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# ===== CONTROL-FLOW MODEL =====
# Standard path: Sanctions  Quality  (Manual_Approve  Activate)  Reject
sanctions = Transition(label="Sanctions_Check")
quality = Transition(label="Quality_Review")
checks = StrictPartialOrder(nodes=[sanctions, quality])

manual_approve = Transition(label="Manual_Procurement_Approval")
activate = Transition(label="Activate_Supplier")
standard_branch = StrictPartialOrder(nodes=[manual_approve, activate])
standard_branch.order.add_edge(manual_approve, activate)

reject = Transition(label="Reject_Supplier")
standard_decision = OperatorPOWL(operator=Operator.XOR, children=[standard_branch, reject])

# Pilot path: Auto_Approve (with eligibility check)
auto_approve = Transition(label="Auto_Approve")
pilot_branch = StrictPartialOrder(nodes=[auto_approve])
pilot_decision = OperatorPOWL(operator=Operator.XOR, children=[pilot_branch, reject])

# Emergency path: Provisional_Activate (with retrospective approval)
provisional_activate = Transition(label="Provisional_Activate")
emergency_branch = StrictPartialOrder(nodes=[provisional_activate])
emergency_decision = OperatorPOWL(operator=Operator.XOR, children=[emergency_branch, reject])

# Request_More_Info loop (approximation: parallel task with evidence validation)
request_info = Transition(label="Request_More_Info")
info_loop = StrictPartialOrder(nodes=[request_info])
info_loop.order.add_edge(request_info, request_info)  # SilentTransition could model repetition

# Main model: Register  Checks  Decision  Notify  Close
register = Transition(label="Register_Supplier")
notify = Transition(label="Notify_Requester")
close = Transition(label="Close_Case")

# Combine all branches under a higher-level XOR (standard, pilot, emergency)
main_decision = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        standard_decision,
        pilot_decision,
        emergency_decision
    ]
)

# Full model: Register  Checks  Decision  Notify  Close
M_REVISED = StrictPartialOrder(nodes=[register, checks, main_decision, notify, close])
M_REVISED.order.add_edge(register, checks)
M_REVISED.order.add_edge(checks, main_decision)
M_REVISED.order.add_edge(main_decision, notify)
M_REVISED.order.add_edge(notify, close)

# ===== DATA-AWARE RULES (pandas checks) =====
# Example: Auto_Approve eligibility
def check_auto_approve_eligibility(event_log):
    eligible = event_log[
        (event_log["supplier_risk"] == "LOW") &
        (event_log["country"] == "DE") &
        (event_log["corporate_group_member"] == True)
    ]
    return eligible

# ===== RESOURCE RULES =====
def check_requester_approver_separation(event_log):
    return not (event_log["requester_id"] == event_log["manual_approver_id"])

# ===== POLICY OVERLAYS =====
# Example: FD-7 active period (2026-07-10 to 2026-07-12)
def is_emergency_active(timestamp):
    return pd.Timestamp(timestamp).tz_localize(None) >= pd.Timestamp("2026-07-10") and \
           pd.Timestamp(timestamp).tz_localize(None) <= pd.Timestamp("2026-07-12")

# ===== EVENT/DATA COLLECTION PROPOSAL =====
# Stable fields:
# - notification_id (UUID, immutable)
# - rule_version_id (e.g., "CS-9.2025-01-01")
# - eligibility_snapshot (timestamped risk/country/corporate_group)
# - actor_aliases (requester_id  [alias1, alias2])
# - emergency_authority (signed declaration for FD-7 extensions)
# - effective_timestamp (when rule took effect)
```

### **Limitations and Approximations**
1. **Request_More_Info Loop**: POWL cannot natively model repetition. A **silent transition** or **parallel task with evidence validation** is used instead.
2. **Emergency Continuation**: FD-7’s intent is **not modeled**—requires **organizational control** (e.g., signed declarations).
3. **Label Equivalence**: QA_Clearance is **mapped to Quality_Review** via data checks, not POWL.
4. **Rejected Leads**: Explicitly **excluded** from M0 scope via **scope rules**.

### **Data Collection Requirements**
| Field | Type | Purpose |
|-------|------|---------|
| `notification_id` | UUID | Stable reference for notifications |
| `rule_version_id` | String | Tracks policy changes (e.g., "CS-9.2025-01-01") |
| `eligibility_snapshot` | Timestamp + JSON | Risk/country/corporate_group at decision time |
| `actor_aliases` | JSON | Resolves requester/approver IDs to humans |
| `emergency_authority` | Signed doc | Justifies FD-7 extensions |
| `effective_timestamp` | ISO8601 | When rule took effect |
