## 1. Modeling assumptions

### Object types and capitalization
- Orders: "Order"
- Items: "Item"
- Packages: "Package"
- Deliveries: "Delivery"
- Invoice: "Invoice"
- Payment: "Payment"

### E2O qualifier vocabulary
- `packs`: Package contains Item(s)
- `carries`: Delivery carries Package(s)
- `bills`: Invoice bills Order(s)
- `settles`: Payment partially or fully settles Invoice(s)
- `closes`: Order closes

### O2O direction conventions
- O2O relations represent relationships between Orders and other objects (Items, Packages, Deliveries, Invoices, Payments). They are directional, from Order to the related objects.

### Logistics and financial events
- Logistics events (Pack, Dispatch, Confirm Delivery) are directly related to Packages and Deliveries.
- Financial events (Invoice, Payment, Close) are directly related to Orders and Invoices.

### Prevention of analytical relation propagation confusion
- While constructing the DataFrames, E2O relations duplicate the matching activity and timestamp from the events table to maintain referential integrity.
- To prevent confusion with source-system facts, O2O relations are explicitly defined to be analytical in nature and not direct source relations.

### PM4Py assumptions
- The code assumes PM4Py version 4.0 and above.
- PM4Py's `OCEL` constructor is used to create the in-memory dataset.

## 3. Data-model audit

### Object types and objects
| Object Type | Objects |
|-------------|---------|
| Order       | O100, O200 |
| Item        | I1, I2, I3 |
| Package     | P1, P2 |
| Delivery    | D1, D2 |
| Invoice     | V1 |
| Payment     | M1, M2 |

### O2O qualifier cardinality
| O2O Qualifier | Cardinality |
|---------------|-------------|
| contains      | 1:many (Order to Items) |
| packs         | 1:many (Package to Items) |
| carries       | 1:many (Delivery to Packages) |
| bills         | 1:many (Invoice to Order) |
| settles       | 1:many (Payment to Invoice) |
| closes        | 1:1 (Order to Order) |

### Activity and object types touched
| Activity | Object Types |
|----------|--------------|
| Create Order | Order |
| Add Item | Order |
| Pack Package | Package |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice |
| Record Payment | Invoice, Payment |
| Close Order | Order |

### Consequential event
The `Record Payment` event is especially consequential for convergence or divergence, as it directly affects the financial state of the associated Invoice.
