def overlap_rate(sub):

## Timestamps exact vs. interval-censored

- **G1:** If exact (1-sec PLC), 4 identical 09:00 starts and 09:03 completes are strong evidence of a genuine fixture batch. If censored to ±1 sec, still strong — the equality is not a rounding artifact.
- **G4, G8:** Scanner 1-sec precision; if exact, the serial/adjacent pattern is definitive. If censored ±1 sec, adjacency may be approximate (±1 sec), but the pattern holds.
- **G6:** If exact, start=complete=17:00 means zero service — clearly a logging artifact (work cannot be instantaneous). Interval-censoring to ±1 min does not help; the problem is not precision but *what the timestamp represents* (submission, not execution).
- **G7:** If exact, 5 items starting at 14:00 with arrivals at 14:01–14:11 is *causally impossible* (start before arrival). Interval-censoring to ±15 min resolves this: real start  [14:00, 14:15), arrivals within this band, so true waiting is unknown but non-negative. Any queue or service analysis on G7 is meaningless without de-censoring.
- **G2, G3, G5:** 1-min precision; if exact, patterns hold. If censored ±1 min, small offsets in completions (e.g., G2's 6-min gaps) are too large to be artifacts; G3's common 11:30 end is too far from individual finishes to be rounding.

## Three cases where the same temporal pattern supports multiple physical explanations

1. **G1 (start equality + end equality, 4 items):** Could be (a) genuine simultaneous fixture batch (all 4 processed in one PLC cycle), (b) start batching where the fixture was loaded over 4–6 min and the PLC started once full, or (c) a PLC logging cycle that timestamps all loaded items with the cycle start/end regardless of individual load order. The data alone cannot distinguish (a) from (b) without fixture load/unload events.

2. **G5 (staggered starts, interleaved completions, shared login):** Could be (a) 2–3 analysts working in parallel behind one login (concurrent work), (b) one analyst multitasking with context switching, or (c) coarse 1-min timestamps masking rapid sequential switches. Without badge-level identity, all three are consistent.

3. **G7 (all start=14:00, all complete=14:15, 5 items):** Could be (a) timestamp coarsening of genuinely sequential work (real times distributed across 14:00–14:15 but rounded), (b) a genuine batch of 5 simultaneous measurements (if the station has 5+ parallel stations), or (c) a single 15-min batch cycle on a multi-item fixture. The legacy MES rounding rule makes (a) most likely, but (b) and (c) cannot be excluded without station capacity data.

# 6. Data-collection redesign

**Priority 1 — Separate execution timestamps from recording timestamps (addresses G3, G6):**
- The root problem in G3 and G6 is that `complete` reflects *form submission* or *bulk data entry*, not actual work completion.
- Recommendation: Add an `actual_complete` field populated by a workstation action (button press, scanner read, PLC signal) distinct from `recorded_at`. For bulk forms, require per-item completion entry or a scan event per item.

**Priority 2 — Resource/badge-level identity (addresses G5):**
- Replace `analyst_pool` with per-individual badge login. If shared VDI is unavoidable, capture badge ID from a separate authentication event and retain it in the log.
- For machines (RBT-7, T-G), log fixture/station ID and fixture slot to distinguish genuine parallel capacity from single-stream work.

**Priority 3 — Source clock synchronization (addresses G8):**
- The repair queue and safety system have different clocks. Implement NTP or a shared time service across all sources. At minimum, record each source's clock offset relative to a reference and store it as metadata.

**Priority 4 — Raw signal preservation before rounding (addresses G7):**
- The legacy MES rounds to 15-min boundaries. If raw signals exist upstream, capture them before rounding. If not, document the rounding rule and tag all affected events as interval-censored with `[start - 15min, start + 15min)` bounds.

**Priority 5 — Group/batch identifiers (addresses G1, G2):**
- Add explicit batch/group IDs: for RBT-7, a fixture load ID; for T-B, a group-begin session ID. This separates *intended operational batches* from *coincidental timestamp equality*.

**Priority 6 — Pause/resume events (addresses G6, G8):**
- Capture pause (safety check start) and resume events in the same log. For G6, capture per-ticket actual close time. For G8, the safety-check event is in a different system — integrate it.

**Priority 7 — Timestamp precision metadata (all clusters):**
- Already partially present (`precision` column), but extend to include: rounding rule (round-down, round-nearest, bucket), true accuracy estimate, and whether `start`/`complete` are measured or inferred.

**Priority 8 — Workstation capacity metadata:**
- Store per-station parallel capacity (e.g., RBT-7 = 4 slots, T-G = unknown). Without this, PM4Py batch discovery cannot distinguish "batch of 4 = full fixture" from "batch of 4 = unusual accumulation."

# 7. Final adjudication

## Clusters interpretable with high confidence

- **G4 (Pack item):** Clean serial pattern, fine-grained scanner precision, consistent 4-min service, non-overlapping intervals. PM4Py will likely detect this as a sequential batch, and the independent diagnostics confirm adjacency. Performance metrics are trustworthy.

- **G6 (Close ticket):** The diagnosis — bulk submission at shift end — is high-confidence. The *interpretation* is clear; what is *not* trustworthy are the metrics. The data tells us *why* the metrics are wrong, which is itself actionable. Exclude from service-time analysis; interval-censor waiting time with acknowledgment that real close times are unknown.

## Clusters that should be excluded or interval-censored in queue analysis

- **G7 (Manual measure):** Exclude from any exact waiting-time or service-time calculation. Interval-censor to ±15 min. The negative-waiting flag (arrivals after the recorded start) is the proof that timestamps are not exact. Utilization is undecidable. PM4Py may detect a "simultaneous batch" here, but this is a coarsening artifact, not a physical batch.

- **G6 (Close ticket):** As above — exclude from service-time; waiting time is upper-bound only (actual close time  [queue_arrival, 17:00]).

- **G5 (Root-cause analysis):** Exclude from utilization analysis until resource identity is resolved. If treated as 1 resource, utilization is impossible (>100% overlap). If treated as 3, utilization is defensible but unverified. Interval-censor with a note that the resource count is uncertain (1–3).

## Clusters requiring operational validation before performance conclusions

- **G1 (Apply label):** High probability of genuine batch, but requires confirmation that all 4 items were loaded before the PLC cycle started (vs. loaded during the cycle). Fixture load/unload events would resolve this. Waiting time is approximately correct; per-item service time within the batch is not measurable from this data.

- **G2 (Surface inspection):** Start batching is clear, but per-item service time is conflated with intra-group waiting. Requires per-item actual start (scan or button press) to decompose. Utilization is approximately correct if work is serial within the group.

- **G3 (Release review):** End batching / bulk submission is the most likely explanation, but without per-review actual completion, service time is overestimated for early-started items and waiting may be underestimated if reviews were actually delayed. Requires separating "review finished" from "form submitted."

- **G8 (Repair triage):** Queue accumulation after capacity loss is well-supported, but the exact boundary of the safety check (and clock offset between systems) introduces uncertainty. Waiting time is approximately correct (±a few minutes from clock skew); service time is accurate (scanner, 1-sec). Requires clock reconciliation for precise bottleneck timing.
