def map_events_to_clusters(evs, ref):
    clusters, cases = set(), []
    case_lookup = dict(zip(ref["case"], ref["cluster"]))
    for e in evs:
        ident = e[0] if isinstance(e, (list, tuple)) else e
        key = str(ident)
        if key in case_lookup:
            cases.append(key); clusters.add(case_lookup[key]); continue
        try:
            idx = int(ident)
            if idx in set(ref.index):
                clusters.add(ref.loc[idx, "cluster"]); cases.append(str(ref.loc[idx, "case"]))
        except (TypeError, ValueError):
            pass
    return sorted(clusters), cases

def pairwise_overlap(g):
    """(#overlapping pairs, #pairs) using strict interval overlap
    (zero-length events never 'overlap' -> flags degenerate G6)."""
    s = g["start"].to_numpy(); e = g["complete"].to_numpy()
    ov = tot = 0
    for i, j in itertools.combinations(range(len(g)), 2):
        tot += 1
        if s[i] < e[j] and s[j] < e[i]:
            ov += 1
    return ov, tot

def max_parallel(g):
    """max #open intervals (starts processed before ends at ties = optimistic)."""
    ev = []
    for _, r in g.iterrows():
        ev.append((r["start"], 1)); ev.append((r["complete"], -1))
    ev.sort(key=lambda t: (t[0], -t[1]))
    cur = best = 0
    for _, d in ev:
        cur += d; best = max(best, cur)
    return best

        cur += d
        best = max(best, cur)
    return best

# 5. Robustness and alternative explanations

**Resource IDs trusted vs treated as shared accounts.**

| cluster | IDs trusted | IDs treated as shared | what flips |
|---|---|---|---|
| G1 | one robot cell; batch credible; capacity 4/cycle | RBT-7 a tag over several cells | capacity and utilization math would halve/change; fixture-capacity match argues for trust |
| G2 | one inspector  common start *must* be an artifact (ends are serial) | two inspectors behind T-B  some overlap real | staffing recommendation halves; service inflation shrinks |
| G3 | one reviewer, serial + deferred submit | two reviewers  some overlap real | less service inflation, same bulk-submission conclusion |
| G5 | single worker: 233% utilization  "data broken" verdict | 3 analysts: ~78% pooled  "staffing adequate" verdict | the *same numbers* flip the conclusion from data-error to capacity-fine |
| G6 | single clerk bulk-entering | same either way | bulk entry dominates; identity irrelevant |
| G8 | single tech, serial catch-up | triage pool | waiting attribution to the safety hold survives either way |

**Timestamps exact vs interval-censored by stated precision.**

- **G7 (15 min):** under floor(start)/ceil(complete) [A3], all five measurements are confined to [14:00, 14:15] — serial 5 × ~3 min fits exactly — while the undocumented-rule worst case widens bounds to (13:45, 14:30]. Per-item service  (0, 30) min; M05's wait  [11, +4); utilization anywhere in (0%, 500%]. Censoring does not select between "serial batch" and "simultaneous batch"; it correctly destroys the point estimates. Negative waits must be read as censoring artifacts, never as early starts.
- **G6 (start = end):** if stamps are *exact*, service is exactly zero, which is physically impossible for closure work — the "exact" reading itself forces the logging-batch interpretation. Censoring true closure to [queue_arrival, 17:01] leaves service  (0, 176] min and waiting  [0, 175]: only bounds, hence exclusion from KPIs.
- **G2, G3, G5 (1 min):** ±1 min censoring leaves every structural conclusion intact (minimum staggers are 5–8 min  2 min); G5's smallest overlap margin is 8 min, so concurrency survives.
- **G1, G4, G8 (1 sec):** effectively exact; conclusions robust to ±2 s.

**Cases where one temporal pattern supports multiple physical explanations (four, exceeding the required three):**

1. *Same start + same end* (PM4Py "parallel"): G1 = physical fixture batch, G6 = end-of-shift bulk entry, G7 = pure quantization. Also "one machine program stamps all units" vs "four parallel machines under one tag".
2. *Same start + staggered ends* (PM4Py "concurrent"): G2 = begin-group button artifact, or genuinely parallel inspection fed by one start signal, or one multitasking inspector.
3. *Staggered starts + same end* (also "concurrent"): G3 = deferred folder submission, or a common release gate at 11:30 that all reviews truly satisfied, or concurrent reviews coincidentally finishing together.
4. *Perfect adjacency chains*: G4 = steady-state takt vs G8 = post-downtime catch-up — locally identical patterns with opposite causal stories for waiting and opposite improvement levers.

# 6. Data-collection redesign

Prioritized; each item names the failure modes it eliminates.

1. **P1 — Execution timestamps at the point of work.** For human tasks, capture item-presented, first-touch, last-touch, and submit as separate scanner/PLC-grade events; never let a form's submit time stand in for execution (fixes G2 start, G3 end, G6 entirely).
2. **P2 — Recording timestamps and provenance retained.** Keep `recorded_at`, source ID, and insertion order forever; alarm when recording lag  duration (automatic G6 detector).
3. **P3 — Badge-level identity.** `org:resource` = person (badge), plus station/asset ID as a separate attribute; pooled logins only as an explicit group attribute with a documented headcount (resolves G5; disambiguates G2).
4. **P4 — Explicit batch/group identifiers.** `fixture_load_id`, `inspection_group_id`, `folder_id`, `submission_id` linking items that share an operational or logging batch; converts inference into a join (resolves G1, G2, G3 interpretation).
5. **P5 — Clock governance.** NTP-sync all sources, store per-source offset/drift, and correlate cross-system events (e.g., safety holds) by event ID rather than by timestamp (resolves G8's 3-minute ambiguity).
6. **P6 — Capacity and parallelism metadata.** Fixture slots, stations behind each account, shift calendar — bounds plausible physical concurrency and makes utilization checks possible (G1, G5).
7. **P7 — Pause/resume and downtime events with reason codes.** Distinguishes blocked from idle and multitasking from continuous work (G8 attribution; G5 service validity).
8. **P8 — Precision metadata and raw values.** Documented granularity *and rounding rule* per source, raw unrounded values retained, plus a schema flag "interval-censored" so downstream tools censor automatically (G7).
9. **P9 — Lifecycle completeness rules.** Mandatory start and complete; an explicit "instantaneous" flag so zero-duration can never silently masquerade as real work (G6).
10. **P10 — Queue semantics.** Keep upstream `queue_arrival`, local enqueue, and first-possible-start as three distinct fields so upstream delay, downtime, and local queueing are separable (G8, and batch-fill waits in G1/G2).

# 7. Final adjudication

**Interpretable with high confidence (with stated semantics):**
- **G4** — genuine serial service; all performance metrics usable as-is (reference cluster).
- **G1** — batch semantics settled at the *fixture-cycle* level: per-item waits are real batch-fill time, service must be reported per cycle; per-item service is not recoverable and must not be summed.
- **G6** — the *diagnosis* is near-certain (end-of-shift bulk entry), even though its performance metrics are worthless.
- **G7** — the *diagnosis* is certain (15-min quantization); the underlying execution order is unrecoverable from this source.

**Exclude or interval-censor in queue/performance analysis:**
- **G6:** exclude from service time and utilization; waiting only as interval-censored [queue_arrival, 17:01]; report completion counts, not durations.
- **G7:** interval-censor all times to the quarter-hour bin (wider if the rounding rule remains unknown); suppress point estimates; negative waits are censoring artifacts.
- **G1:** aggregate service to the fixture cycle (else 4× utilization inflation).
- **G2:** waiting to the group start is usable but must be labeled "batch formation"; service from the pinned start is inflated for later items — model serially or censor.
- **G3:** waiting is usable; completion is a submission event — censor true finish to  11:30 and  start; disperse the phantom 11:30 downstream surge.
- **G5:** waiting is usable; utilization and staffing conclusions only as a range conditioned on analyst count.

**Require operational validation before any performance conclusion:**
- **G5:** badge data, analysts on shift, pause/resume behavior (the 4-simultaneous > 3-analyst excess must be explained).
- **G2:** number of inspectors behind T-B; per-item first-touch logging.
- **G8:** measured clock offset between repair queue and safety system; safety-hold reason codes; arrival-feed completeness after 15:08.
- **G7:** the MES rounding rule and any raw unrounded values.
- **G3:** per-review submission events; **G6:** form-open/edit audit trail to recover true closure times; **G1:** fixture program (slot order and per-slot steps).

Overarching principle: identical timestamps are claims about the *logging* system, not about the work. PM4Py's "parallel/concurrent/sequential" labels classify temporal patterns; only the joint use of queue arrivals, recording lag, documented precision, capacity limits, and identity evidence can promote a pattern into a physical statement — and where that evidence is absent (G5 identity, G7 resolution, G8 clocks), the honest output is a bounded interval plus a validation request, not a point estimate.
