## 1. Duplicate-handling decision tree

When integrating multi-system enterprise logs (ERP, WMS, handheld scanners, carrier APIs, billing, and payment gateways), identical timestamps and activity names do not necessarily indicate duplicate records. To minimize semantic damage, candidate event groups sharing a timestamp window and object references are evaluated through a six-level hierarchical decision tree.

```
Candidate Group Evaluation [Shared Timestamp & Related Object Overlap]
│
├── [Level 1: Exact Technical Identity]
│   └── Identical source system, source event key, and payload hash?
│       └── YES ──► Exact Technical Duplicate
│                   └── Action: DROP redundant record; retain canonical instance.
│
├── [Level 2: Cross-Source Physical Equivalence]
│   └── Distinct systems, identical physical action confirmed by reconciliation key, matching object set?
│       └── YES ──► Same Physical Event Observed by Multiple Systems
│                   └── Action: MERGE attributes and relations; retain canonical eid; record provenance.
│
├── [Level 3: Multi-Level Abstraction & Lineage]
│   └── One event is operational shop-floor execution; the other is a derived ERP/ledger status update?
│       └── YES ──► Summary Event Derived from Detailed Event
│                   ├── Conservative: RETAIN BOTH with refined labels or qualifiers.
│                   └── Evidence-based: MERGE attributes into operational event; drop summary.
│
├── [Level 4: Harmonization Collisions]
│   └── Distinct business transitions mapped to an identical activity label during ETL?
│       └── YES ──► Harmonization Collision Between Semantically Distinct Source Activities
│                   └── Action: RETAIN BOTH with refined labels or qualifiers (un-harmonize).
│
├── [Level 5: Concurrent Independent Entities]
│   └── Shared timestamp and activity, but disjoint or partially disjoint fine-grained objects?
│       └── YES ──► Concurrent Same-Label Events Involving Different Objects
│                   └── Action: RETAIN BOTH UNCHANGED (never merge or drop).
│
└── [Level 6: Unresolved Provenance]
    └── Shared activity and timestamp with conflicting attributes and no reconciliation proof?
        └── YES ──► Unresolved Candidate
                    └── Action: QUARANTINE FOR REVIEW (isolate from active log).
```

### Terminal Decisions and Definitions

1. **Exact technical duplicate**: Replay or multi-ingestion of the identical system record (`source`, `source_event_key`, and `payload_hash` match). Terminal Action: **drop** redundant record.
2. **Same physical event observed by multiple systems**: Independent system observations of one real-world occurrence confirmed by reconciliation reports. Terminal Action: **merge attributes and relations**, retaining authoritative values and full provenance.
3. **Summary event derived from a detailed event**: Status propagation where an ERP milestone mirrors prior operational execution. Terminal Action: **retain both with refined labels or qualifiers** (conservative) or **merge attributes and relations** (evidence-based).
4. **Harmonization collision between semantically distinct source activities**: Generic labeling that conceals distinct lifecycle transitions (e.g., warehouse release vs. carrier intake). Terminal Action: **retain both with refined labels or qualifiers** to restore domain semantics.
5. **Concurrent same-label events involving different objects**: Parallel operations on different physical or financial entities (e.g., picking different items or partial payment captures). Terminal Action: **retain both unchanged**.
6. **Unresolved candidate**: Ambiguous collisions lacking external reconciliation. Terminal Action: **quarantine for review** to prevent model distortion.

## 3. Timestamp-tie ordering rules

### Partial-Order-to-Total-Order Policy

When disparate systems log events at second-level granularity (`10:00:00`, `10:15:00`, `12:00:00`), timestamp ties cannot be sorted arbitrarily without violating process physics. A deterministic five-tier resolution policy transforms partial orders into valid total orders:

1. **Tier 1: Domain & Lifecycle Constraints (Semantic Precedence)**
   - Hard business lifecycles govern causality across shared objects:
     - *Fulfillment*: Items must be picked before packaging, and packaged before dispatch: $\text{Pick Item} \prec \text{Pack Package} \prec \text{Dispatch Package}$.
     - *Finance*: Invoice issuance precedes payment authorization and capture: $\text{Issue Invoice} \prec \text{Authorize Payment} \prec \text{Capture Payment}$.
     - *Custody*: Goods must be released from the warehouse before carrier acceptance, which precedes formal signed handover: $\text{Warehouse Release} \prec \text{Carrier Acceptance} \prec \text{Handover to Carrier}$.
2. **Tier 2: Within-Source Monotonic Sequence (`source_seq`) (Semantic Precedence)**
   - Where events originate from the same system, the monotonic counter `source_seq` provides authoritative ordering:
     - Carrier: `C-400` (`source_seq: 1`, `e09`) $\prec$ `C-401` (`source_seq: 2`, `e10`).
     - PSP: `P-700` (400, `e12`) $\prec$ `P-701` (401, `e13`) $\prec$ `P-702` (402, `e14`).
     - WMS: `W-77` (100, `e03`) $\prec$ `W-78` (110, `e06`) $\prec$ `W-79` (120, `e08`).
     - Scanner: `S-901` (551, `e04`) $\prec$ `S-902` (552, `e05`).
     - ERP: `ER-100` (10) $\prec$ `ER-101` (20) $\prec$ `ER-150` (30) $\prec$ `ER-200` (40) $\prec$ `ER-201` (41).
3. **Tier 3: Cross-System Lineage & Abstraction Hierarchy (Semantic Precedence)**
   - Operational shop-floor executions precede derived enterprise status updates:
     - Detailed WMS packing (`e06`) precedes ERP status posting (`e07`).
     - PSP transactional captures (`e13`, `e14`) precede ERP invoice balance summary (`e15`).
4. **Tier 4: Object-Level Deterministic Tie-Breaker (Deterministic Technical)**
   - Genuine concurrent operations on parallel objects are ordered deterministically by primary object identifier string ($I_1 \prec I_2$ for items; $M_1 \prec M_2$ for payments).
5. **Tier 5: Stable Fallback Order (Deterministic Technical)**
   - Residual ties are broken using ascending canonical event identifiers (`eid`).

### Semantic vs. Deterministic Classification

- **Semantic Rules (Tiers 1, 2, 3)** enforce physical and organizational reality. Violating them yields impossible traces (e.g., packing before picking or capturing before authorizing).
- **Deterministic Rules (Tiers 4, 5)** are reproducible tie-breakers that prevent stochastic sorting in discovery algorithms. They do not claim to prove physical sub-second sequence.

### Pitfalls of Premature Microsecond Injection

Injecting synthetic fractional seconds (e.g., adding row index milliseconds $+1\,\text{ms}, +2\,\text{ms}$) *prior* to establishing semantic ordering permanently hardcodes an arbitrary physical sequence into the data. Process discovery algorithms treat timestamp differences as absolute empirical truths.
- If arbitrary microsecond injection places `e13` (Capture) at `12:00:00.001` and `e12` (Authorize) at `12:00:00.002`, miners discover an impossible lifecycle violation ($\text{Capture} \rightarrow \text{Authorize}$) or spurious rework loops.
- Similarly, sorting by `ingested_at` reflects network queue jitter rather than business causality: `e04` (ingested at `10:00:03`) would appear after `e03` (ingested at `10:00:01`), and ERP status updates (`10:01:00`) would be separated from operational packing by a full minute, distorting shop-floor lead times. Synthetic microsecond deltas must only be applied *after* semantic sorting.

### Cluster Orders

- **Cluster 10:00:00 (Fulfillment: e03, e04, e05, e06, e07)**:
  - *Deduplication*: `e04` merged into `e03`.
  - *Intended Total Order*:
    $$\mathbf{e03} \text{ (Pick } I_1\text{)} \longrightarrow \mathbf{e05} \text{ (Pick } I_2\text{)} \longrightarrow \mathbf{e06} \text{ (Pack Package [WMS])} \longrightarrow \mathbf{e07} \text{ (Pack Package [ERP Status])}$$
  - *Admissible Alternative*: $e05 \rightarrow e03 \rightarrow e06 \rightarrow e07$ (since parallel picks are physically concurrent).
- **Cluster 10:15:00 (Logistics: e08, e09, e10)**:
  - *Deduplication*: None. Labels un-harmonized to distinguish warehouse release from carrier intake.
  - *Intended Total Order*:
    $$\mathbf{e08} \text{ (Dispatch [Warehouse Release])} \longrightarrow \mathbf{e09} \text{ (Accept [Carrier Intake])} \longrightarrow \mathbf{e10} \text{ (Handover to Carrier)}$$
  - *Admissible Alternative*: None. Logistics custody transfer and Carrier `source_seq` 1 $\prec$ 2 enforce this exact sequence.
- **Cluster 12:00:00 (Financial: e11, e12, e13, e14, e15, e16)**:
  - *Deduplication*: `e16` merged into `e11`.
  - *Intended Total Order*:
    $$\mathbf{e11} \text{ (Issue Invoice)} \longrightarrow \mathbf{e12} \text{ (Authorize Payment } M_1\text{)} \longrightarrow \mathbf{e13} \text{ (Capture Payment } M_1\text{)} \longrightarrow \mathbf{e14} \text{ (Capture Payment } M_2\text{)} \longrightarrow \mathbf{e15} \text{ (Capture [ERP Summary])}$$
  - *Admissible Alternative*: $e11 \rightarrow e12 \rightarrow e14 \rightarrow e13 \rightarrow e15$ (only if $M_1$ and $M_2$ captures were executed asynchronously; PSP monotonic sequence $401 \prec 402$ strongly favors $e13 \prec e14$).

## 4. Conservative cleaning pipeline

The conservative cleaning pipeline is governed by the principle of **minimal intervention**: it removes only events with audited proof of cross-system redundancy, preserves multi-system abstraction layers, refines harmonized labels, and enforces deterministic ordering while strictly maintaining original data integrity.

### Pipeline Specification

1. **Targeted Verified Deduplication**:
   - Merge `e04` into `e03`: Confirmed identical physical scan. Retain `e03` as canonical; drop `e04`. Union attributes (preserving WMS bin location and scanner hardware ID).
   - Merge `e16` into `e11`: Confirmed identical invoice creation for $V_1$. Retain `e11` as canonical; drop `e16`. Merge ERP ledger accounts with Billing tax breakdown and invoice PDF link.
2. **Activity Refinement (De-Harmonization & Qualification)**:
   - Un-harmonize logistics events: Refine `e08` to `Dispatch Package [Warehouse Release]` and `e09` to `Accept Package [Carrier Intake]`. This eliminates false self-loops and captures the dock custody boundary.
   - Qualify abstraction-level status events: Refine `e07` to `Pack Package [ERP Status]` and `e15` to `Capture Payment [ERP Summary]`. This prevents status messages from masquerading as physical rework.
3. **Preservation of Legitimate Concurrency**:
   - Retain `e05` (Pick of Item $I_2$) as distinct from `e03` (Pick of Item $I_1$).
   - Retain `e14` (Capture of Payment $M_2$) as distinct from `e13` (Capture of Payment $M_1$).
4. **Metadata Preservation**:
   - Preserve immutable raw fields: `original_timestamp`, `original_activity`, `source`, and `source_event_key`.
   - All merged attributes and source keys are written to an auxiliary audit log.
5. **Deterministic Sequencing & Epsilon Delta**:
   - Sort using the five-tier policy. Generate an adjusted sorting timestamp by adding an imperceptible, non-destructive index-based delta ($\epsilon = 1\,\text{ms}$) solely to support legacy process mining tools requiring strict monotonicity, leaving `original_timestamp` intact for duration calculations.

### Retained Event Count

From the raw log of **17 events**, the conservative pipeline removes exactly **2 events** (`e04` and `e16`), yielding an expected retained count of **15 events**:
$$\{e01, e02, e03, e05, e06, e07, e08, e09, e10, e11, e12, e13, e14, e15, e17\}$$
Total Event-to-Object (E2O) relations decrease from 41 to **36** (removing 3 relations from `e04` and 2 from `e16`).

## 5. Aggressive alternatives

### Scenario 1: Evidence-Based Semantic Merging

This scenario collapses multi-tier enterprise architectures into a unified operational process trace:
- **Verified Cross-System Merges**: `e03/e04` and `e11/e16` are merged as in the conservative pipeline.
- **Abstraction Collapse**:
  - `e07` (ERP Pack Package update) is identified as a message propagation of `e06` (WMS Pack Package) and collapsed into `e06`. Attributes are unioned, and `ER-150` is stored in provenance.
  - `e15` (ERP Capture Payment summary) is identified as an accounting reflection of PSP transactions `e13` and `e14`. It is moved to an auxiliary financial audit table and removed from the operational log.
- **Logistics Disambiguation**: `e08` and `e09` are retained with refined labels (`Warehouse Release` vs. `Carrier Acceptance`).
- **Concurrency Preserved**: `e05` ($I_2$) and `e14` ($M_2$) are strictly preserved.
- **Retained Event Count**: **13 events** ($\{e01, e02, e03, e05, e06, e08, e09, e10, e11, e12, e13, e14, e17\}$). Total E2O relations: **32**.
- **Semantic Trade-offs & Damage**: System synchronization latencies (WMS-to-ERP and PSP-to-ERP message queues) become completely unobservable. Lagging ERP background batch jobs cannot be detected.

### Scenario 2: Mechanically Aggressive PM4Py Merging

This scenario reflects the automated, uninspected execution of library deduplication routines (e.g., executing `pm4py.ocel_merge_duplicates` or grouping naively on `(activity, timestamp)` across the log):
- **Timestamp 10:00:00 (`Pick Item`)**: `e03`, `e04`, and `e05` share timestamp and activity. All three are merged into a single event `e03`.
- **Timestamp 10:00:00 (`Pack Package`)**: `e06` and `e07` are merged into a single event.
- **Timestamp 10:15:00 (`Dispatch Package`)**: `e08` and `e09` are merged into a single event.
- **Timestamp 12:00:00 (`Issue Invoice`)**: `e11` and `e16` are merged into a single event.
- **Timestamp 12:00:00 (`Capture Payment`)**: `e13`, `e14`, and `e15` share timestamp and activity. All three are merged into a single event.
- **Retained Event Count**: **10 events** ($\{e01, e02, e03_{\text{merged}}, e06_{\text{merged}}, e08_{\text{merged}}, e10, e11_{\text{merged}}, e12, e13_{\text{merged}}, e17\}$). Total E2O relations: **~27**.
- **Semantic Damage**: Severe. Item $I_2$'s independent pick is eradicated. The custody transfer boundary between warehouse and carrier is erased. Multi-payment capture ($M_1, M_2$) is destroyed.

### Why `have_common_object=True` Fails to Protect e13 and e14

A common heuristic in process mining pipelines is to condition deduplication on shared object references (`have_common_object=True` or checking whether the intersection of related objects is non-empty). **This heuristic completely fails to protect `e13` and `e14`.**

In an OCEL, events simultaneously relate to multiple objects across different entity types:
- `e13` (Capture $M_1$) relates to: $\{O_1, V_1, M_1\}$.
- `e14` (Capture $M_2$) relates to: $\{O_1, V_1, M_2\}$.

When evaluating `e13` and `e14`:
1. Both events share the identical activity label: `Capture Payment`.
2. Both events share the identical timestamp: `2026-05-18 12:00:00`.
3. Evaluating the intersection of related objects:
   $$\{O_1, V_1, M_1\} \cap \{O_1, V_1, M_2\} = \{O_1, V_1\} \neq \emptyset$$
Because the intersection contains Order $O_1$ and Invoice $V_1$, `have_common_object` evaluates to **`True`**. The automated algorithm concludes that both events refer to the same invoice payment and merges them, discarding $M_2$ or unioning $\{M_1, M_2\}$ into a single composite capture. This destroys the split-payment domain model, corrupting all downstream payment auditing, fraud monitoring, and financial reconciliation.

"""
OCEL Duplicate Cleaning and Deterministic Ordering Pipeline.
Assumes `ocel_raw` exists as a valid pm4py.objects.ocel.obj.OCEL instance.
"""

import copy
import pandas as pd
import numpy as np
import pm4py


def validate_referential_integrity(ocel: pm4py.OCEL, context: str = "") -> bool:
    """Validates that relations reference existing events and objects without orphans."""
    event_ids = set(ocel.events["ocel:eid"])
    rel_event_ids = set(ocel.relations["ocel:eid"])
    object_ids = set(ocel.objects["ocel:oid"])
    rel_object_ids = set(ocel.relations["ocel:oid"])

    orphan_rel_events = rel_event_ids - event_ids
    orphan_rel_objects = rel_object_ids - object_ids

    if orphan_rel_events:
        raise ValueError(
            f"[{context}] Referential Integrity Violation: Relations reference "
            f"non-existent events: {orphan_rel_events}"
        )
    if orphan_rel_objects:
        raise ValueError(
            f"[{context}] Referential Integrity Violation: Relations reference "
            f"non-existent objects: {orphan_rel_objects}"
        )
    return True


def merge_verified_pair(
    ocel: pm4py.OCEL,
    canonical_eid: str,
    duplicate_eid: str,
    attribute_priority: dict,
    provenance_log: list,
    rule_name: str,
) -> pm4py.OCEL:
    """
    Merges a verified duplicate event into a canonical event, updating attributes,
    unioning object relations, logging provenance, and ensuring referential integrity.
    """
    events_df = ocel.events
    relations_df = ocel.relations

    canonical_mask = events_df["ocel:eid"] == canonical_eid
    duplicate_mask = events_df["ocel:eid"] == duplicate_eid

    if not canonical_mask.any() or not duplicate_mask.any():
        raise KeyError(
            f"Events {canonical_eid} or {duplicate_eid} not found in events table."
        )

    canonical_row = events_df[canonical_mask].iloc[0]
    duplicate_row = events_df[duplicate_mask].iloc[0]

    # 1. Attribute Merging based on priority
    merged_attrs = {}
    discarded_attrs = {}
    for col in events_df.columns:
        if col in ["ocel:eid", "ocel:timestamp", "ocel:activity"]:
            continue
        pref_source = attribute_priority.get(col, canonical_row.get("source"))
        if duplicate_row.get("source") == pref_source and pd.notna(
            duplicate_row.get(col)
        ):
            merged_attrs[col] = duplicate_row[col]
            discarded_attrs[col] = canonical_row.get(col)
        else:
            merged_attrs[col] = canonical_row.get(col)
            discarded_attrs[col] = duplicate_row.get(col)

    for col, val in merged_attrs.items():
        events_df.loc[canonical_mask, col] = val

    # 2. Union Relations (re-point duplicate relations to canonical)
    dup_rel_mask = relations_df["ocel:eid"] == duplicate_eid
    relations_df.loc[dup_rel_mask, "ocel:eid"] = canonical_eid
    relations_df.drop_duplicates(
        subset=["ocel:eid", "ocel:oid", "ocel:type"], inplace=True
    )

    # 3. Audit Logging
    provenance_log.append(
        {
            "canonical_eid": canonical_eid,
            "source_eids": [canonical_eid, duplicate_eid],
            "rule_name": rule_name,
            "retained_attributes": merged_attrs,
            "discarded_conflicts": discarded_attrs,
        }
    )

    # 4. Drop duplicate event from events table
    events_df = events_df[events_df["ocel:eid"] != duplicate_eid].copy()
    ocel.events = events_df
    ocel.relations = relations_df

    validate_referential_integrity(ocel, context=f"merge_{canonical_eid}_{duplicate_eid}")
    return ocel

        ocel.events.groupby(["ocel:timestamp", "ocel:activity"])

            keys=("source_event_key", list),
        )
        .reset_index()
    )
    candidates = grouped[grouped["event_count"] > 1]
    return candidates

# Step C: Deterministic Semantic Sorting (Hierarchy Tiers 1-5)
def compute_semantic_sort_rank(row: pd.Series) -> int:
    """Assigns an integer rank based on domain lifecycle and source sequences."""
    act = row["ocel:activity"]
    source = row.get("source", "")
    seq = row.get("source_seq", 0)

## 7. Sensitivity analysis

Cleaning and deduplication pipelines directly alter the graph topology, relation structures, and lifecycle durations of an OCEL. The following table and comparative analysis quantify these shifts across **Raw**, **Conservative**, **Evidence-Based Merge**, and **Mechanically Aggressive Library Merge** datasets.

### Metric Comparison

| Dimension / Metric | Raw Log | Conservative Cleaning | Evidence-Based Merge | Aggressive Library Merge |
|---|---|---|---|---|
| **Total Event Count** | 17 | 15 | 13 | 10 |
| **Total E2O Relations** | 41 | 36 | 32 | ~27 |
| **Order ($O_1$) Path Length** | 17 events | 15 events | 13 events | 10 events |
| **Item $I_1$ Trace Length** | 3 events (`e03`, `e04`, `e06`) | 2 events (`e03`, `e06`) | 2 events (`e03`, `e06`) | 2 events (`e03`, `e06`) |
| **Item $I_2$ Trace Length** | 2 events (`e05`, `e06`) | 2 events (`e05`, `e06`) | 2 events (`e05`, `e06`) | **1 event** (`e06` only; `e05` lost) |
| **Payment $M_1$ Trace Length** | 2 events (`e12`, `e13`) | 2 events (`e12`, `e13`) | 2 events (`e12`, `e13`) | 2 events (`e12`, `e13_{\text{merged}}`) |
| **Payment $M_2$ Trace Length** | 1 event (`e14`) | 1 event (`e14`) | 1 event (`e14`) | **0 events** (`e14` lost/merged into $M_1$) |
| **Invoice $V_1$ Trace Length** | 6 events | 5 events | 4 events | 3 events |
| **False Rework Self-Loops** | 4 loops | 0 loops (resolved by labels) | 0 loops (resolved by merge) | 0 loops (false removal) |
| **OTG Connectivity** | Fully connected | Fully connected | Fully connected | Distorted ($M_2$ disconnected) |

### Graph and Process Interpretations

1. **Order-Flattened Directly-Follows Graph (DFG)**:
   - In the **Raw log**, the Order trace exhibits artificial self-loops: `Pick Item -> Pick Item`, `Pack Package -> Pack Package`, `Dispatch Package -> Dispatch Package`, and `Capture Payment -> Capture Payment` (all with apparent duration 0s).
   - In the **Conservative log**, de-harmonization and qualification transform these loops into valid milestone progressions (`Pack Package [WMS]` $\rightarrow$ `Pack Package [ERP Status]` and `Warehouse Release` $\rightarrow$ `Carrier Intake`).
   - In the **Aggressive log**, all loops are deleted, presenting an oversimplified, false linear path.
2. **Item-Flattened DFG**:
   - For Item $I_1$, the Raw log contains redundant picks (`e03 -> e04`). Both Conservative and Evidence-Based pipelines correctly reduce this to $\text{Pick Item} \rightarrow \text{Pack Package}$.
   - For Item $I_2$, Conservative and Evidence-Based pipelines preserve $\text{Pick Item} (e05) \rightarrow \text{Pack Package} (e06)$. In the Aggressive pipeline, `e05` is dropped; $I_2$'s lifecycle begins abruptly at `Pack Package`, creating an orphaned item packing anomaly.
3. **Payment-Flattened DFG**:
   - In Conservative and Evidence-Based logs, Payment $M_1$ follows $\text{Authorize Payment} (e12) \rightarrow \text{Capture Payment} (e13)$, while $M_2$ exhibits a single direct $\text{Capture Payment} (e14)$.
   - In the Aggressive log, `e13`, `e14`, and `e15` are collapsed. Payment $M_2$ is either dropped or merged into $M_1$. If relations are unioned, $M_2$ falsely inherits an authorization step (`e12`), inventing a non-existent authorization event for $M_2$.
4. **OC-DFG Edges and ET-OT Weights**:
   - In the Raw log, ET-OT graph weights for `Capture Payment` to `Order` and `Pick Item` to `Item` are inflated (weight 3).
   - Conservative cleaning normalizes ET-OT frequencies to true operational counts: 2 picks (`I1`, `I2`) and 2 operational captures (`M1`, `M2`), plus 1 qualified ERP summary. Aggressive merging suppresses ET-OT weights to 1 across all tied clusters, hiding multi-item and multi-payment business scale.
5. **Object-to-Object (OTG) Relations**:
   - In Raw and Conservative logs, Invoice $V_1$ is correctly linked to Payments $M_1$ and $M_2$.
   - In the Aggressive log, collapsing captures into a single event creates a false direct equivalence between $M_1$ and $M_2$ or severs $M_2$ completely from $V_1$, corrupting the financial object topology.

### Six Concrete Edges/Patterns Whose Interpretation Changes

1. **`Pick Item` $\rightarrow$ `Pick Item` (on Order $O_1$)**:
   - *Raw*: Apparent immediate rework loop (frequency = 2, duration = 0s).
   - *Conservative*: Valid sequential representation of two distinct physical item picks ($I_1$ then $I_2$, frequency = 1, duration = 0s).
   - *Aggressive*: Completely eliminated (frequency = 0); implies the entire order was picked in a single instantaneous event.
2. **`Pick Item` $\rightarrow$ `Pack Package` (on Item $I_2$)**:
   - *Raw & Conservative*: Normal fulfillment lifecycle ($e05 \rightarrow e06$, duration = 0s).
   - *Aggressive*: **Edge destroyed**. $I_2$ appears in `Pack Package` without ever having been picked.
3. **`Pack Package` $\rightarrow$ `Pack Package` (on Package $P_1$)**:
   - *Raw*: Apparent packaging rework loop (duration = 0s).
   - *Conservative*: Transformed into $\text{Pack Package [WMS]} \rightarrow \text{Pack Package [ERP Status]}$, measuring enterprise message bus ingestion latency.
   - *Evidence-Based / Aggressive*: Edge eliminated.
4. **`Dispatch Package` $\rightarrow$ `Dispatch Package` (on Delivery $D_1$)**:
   - *Raw*: Apparent double-dispatch error.
   - *Conservative*: Transformed into $\text{Warehouse Release} \rightarrow \text{Carrier Intake}$, measuring dock handover dwell time.
   - *Aggressive*: Merged into a single instantaneous event; warehouse-to-carrier custody transfer boundary is erased.
5. **`Authorize Payment` $\rightarrow$ `Capture Payment` (on Payment $M_2$)**:
   - *Raw & Conservative*: Edge does not exist for $M_2$ (direct capture).
   - *Aggressive*: False edge created if relations are unioned during merging, ascribing $M_1$'s authorization (`e12`) to $M_2$.
6. **`Issue Invoice` $\rightarrow$ `Issue Invoice` (on Invoice $V_1$)**:
   - *Raw*: Apparent duplicate billing loop (duration = 0s).
   - *Conservative & Evidence-Based*: Merged into single canonical invoice issuance ($e11$); loop eliminated without data loss.

## 8. Audit trail and reversibility

To comply with enterprise compliance standards and process mining governance, every modification must be fully reversible, allowing any analyst to reconstruct the exact raw OCEL view.

### Provenance Schema (`event_provenance` Table)

| Column Name | Data Type | Description |
|---|---|---|
| `canonical_eid` | String (PK) | The event ID retained in the active cleaned OCEL. |
| `source_eids` | Array[String] | Complete list of all raw event IDs contributing to this canonical event. |
| `merge_rule_id` | String | Unique identifier of the cleaning rule applied (e.g., `RULE_VERIFIED_WMS_SCANNER_MERGE`). |
| `rule_version` | String | Version tag of the cleaning pipeline algorithm (e.g., `v2.4.1`). |
| `reviewer_or_pipeline` | String | Identifier of automated engine run or manual reviewer user ID. |
| `original_activity` | String | Raw activity label prior to refinement. |
| `refined_activity` | String | Refined or qualified activity label assigned. |
| `original_timestamp` | Timestamp | Raw source timestamp (unaltered UTC). |
| `adjusted_timestamp` | Timestamp | Timestamp after deterministic ordering and epsilon injection. |
| `retained_attributes` | JSON / Map | Key-value mapping of all attribute values retained, including source attribution. |
| `discarded_conflicts` | JSON / Map | Key-value mapping of conflicting attribute values that were superseded. |
| `confidence_score` | Float | Confidence level of the merge decision ($0.0 - 1.0$). |
| `justification_reason` | String | Human-readable explanation and reconciliation reference key. |

### Exact Raw View Reconstruction

An analyst can losslessly reconstruct `ocel_raw` from `ocel_cleaned` and `event_provenance` by executing a deterministic inverse function:

1. Initialize `ocel_reconstructed` as a copy of `ocel_cleaned`.
2. For each record in `event_provenance` where `len(source_eids) > 1`:
   - Identify `canonical_eid` in `ocel_reconstructed.events`.
   - Retrieve original raw event records for all IDs in `source_eids` from the immutable raw audit store.
   - Remove `canonical_eid` from `ocel_reconstructed.events`.
   - Append all raw source event records, restoring raw `eid`, `original_timestamp`, and `original_activity`.
3. Restore `ocel_reconstructed.relations` by reloading backed-up raw relations matching active raw `eid`s (undoing relation unioning).
4. For all remaining events, reset `ocel:timestamp = original_timestamp` and `ocel:activity = original_activity`.
5. Validate referential integrity between events, relations, and objects. The resulting log is bit-level identical to `ocel_raw`.

## 9. Failure modes and safeguards

Automated duplicate cleaning pipelines in OCEL environments are vulnerable to severe failure modes if domain semantics are neglected. Below are eight primary failure modes and their mandatory architectural safeguards.

1. **Collapsing Distinct Partial Payments**:
   - *Mechanism*: Grouping on `(activity == 'Capture Payment', timestamp)` collapses `e13` ($M_1$) and `e14` ($M_2$) into a single transaction.
   - *Safeguard*: **Object-Type-Specific Granularity Check**. Deduplication must require strict equivalence on the finest-grained participating object type (`Payment`), not merely on coarse parent objects (`Order`, `Invoice`). If lower-level object IDs differ, deduplication is prohibited.
2. **Converting Abstraction-Level Updates into False Rework**:
   - *Mechanism*: Treating WMS physical packing (`e06`) and ERP status confirmation (`e07`) as identical events creates an artificial zero-duration rework self-loop ($\text{Pack} \rightarrow \text{Pack}$).
   - *Safeguard*: **Multi-Level Abstraction Tagging & Label Qualification**. Downstream integration events must either be qualified (`[ERP Status]`) or explicitly tagged with an abstraction metadata column (`abstraction_level: summary`) and excluded from physical process discovery models.
3. **Ordering by Ingestion Time**:
   - *Mechanism*: Sorting by `ingested_at` inverts true physical causality due to asynchronous queue delays, placing ERP status updates minutes after shop-floor activities or interleaving scans incorrectly.
   - *Safeguard*: **Strict Prohibition of Ingestion Time for Business Ordering**. `ingested_at` is restricted exclusively to technical ingestion auditing and SLA latency calculations. It must never serve as a sorting key in business process discovery.
4. **Treating Shared Objects as Proof of Duplication**:
   - *Mechanism*: Assuming that any two events sharing activity, timestamp, and a common object (`have_common_object=True`) are duplicates (e.g., merging `e13` and `e14` because both reference $O_1$ and $V_1$).
   - *Safeguard*: **Exact Object-Set Equality Enforcement**. Automated merging requires identical related object sets across all object types ($\mathcal{O}_{e1} = \mathcal{O}_{e2}$). Any partial intersection triggers Level 5 (Concurrency) or Level 6 (Quarantine).
5. **Unioning Incompatible Event-to-Object (E2O) Relations**:
   - *Mechanism*: Merging an invoice-level balance update (`e15`, referencing $\{O_1, V_1\}$) into a specific payment capture (`e13`, referencing $\{O_1, V_1, M_1\}$), or unioning item sets so that picking $I_1$ appears to pick $I_2$.
   - *Safeguard*: **Relation Cardinality Constraints & Schema Validation**. Summaries must not inherit specific low-level object instances without explicit itemized allocation keys. Merging logic must validate that relation unions do not violate declared domain cardinalities.
6. **Changing Durations Through Synthetic Microseconds**:
   - *Mechanism*: Injecting arbitrary microsecond offsets prior to determining domain order, which permanently distorts lead times and inverts process steps (e.g., placing capture before authorization).
   - *Safeguard*: **Immutable Original Timestamps & Post-Sort Epsilon Application**. The original timestamp column (`original_timestamp`) remains immutable. Non-destructive epsilon deltas ($\le 1\,\text{ms}$) are added strictly *after* domain lifecycle sorting, and only to a secondary analytical timestamp column.
7. **Losing Source-Authoritative Attributes**:
   - *Mechanism*: Using arbitrary merge rules (e.g., SQL `FIRST()` or `LAST()`) that overwrite high-precision WMS warehouse bin locations with generic scanner payloads, or discard billing tax breakdowns in favor of ERP defaults.
   - *Safeguard*: **Attribute Master-Authority Matrix**. Attribute merging must be driven by an explicit system-of-record configuration matrix defining authoritative sources per attribute domain (e.g., WMS for spatial/inventory data; Billing for tax/discount calculations; ERP for general ledger codes).
8. **Applying Duplicate Functions to the Entire OCEL Without Pre-Inspection**:
   - *Mechanism*: Running global library deduplication (`pm4py.ocel_merge_duplicates`) blindly across an entire log without isolating candidate duplicate groups.
   - *Safeguard*: **Targeted Scope Candidate Inspection & Dry-Run Reporting**. All deduplication routines must operate strictly on explicitly inspected candidate clusters identified by pre-check filters. The pipeline must generate a dry-run impact report detailing dropped/merged events before committing changes to the primary analytical log.
