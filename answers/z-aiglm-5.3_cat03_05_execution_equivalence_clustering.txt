### Section 1: Equivalence design space

**E0 — Exact (identifier-literal) equivalence.** Operational: two executions equivalent iff identical activity sequences and identical raw object identifiers in every event (the PM4Py exact-key notion). Invariants: everything recorded. Discarded: nothing. RST: yes (string equality). Concurrency: total order required; ties broken deterministically or treated as blocks. **E1 — Activity-sequence equivalence.** Def: executions equivalent iff their label sequences (timestamp order; same-timestamp events as unordered multiset block) are equal. Concurrency: per-timestamp label multiset (bag) to avoid tie-break sensitivity; alternatively all same-timestamp labels sorted.

**E2 — Typed structural equivalence under identifier renaming.** Def: exists bijection  between events and  between objects s.t. (i) event order preserved (total order; or partial order variant E2p), (ii) labels equal, (iii)  type- and externality-preserving (EXT objects map only to EXT objects of same type; local to local), (iv) E2O incidence preserved: e references o iff (e) references (o). from collections import Counter, defaultdict

```python
def semantic_signature(events):
    """events: list of dicts {activity, ts, objects: [(type, oid), ...]}
       ordered by timestamp; returns a hashable, renaming-invariant tuple."""
    ext = lambda oid: str(oid).startswith("EXT")

    lab = Counter(e["activity"] for e in events)

    def objs(act, t, side):
        # multiplicity of type-t objects (local/ext side) in events with label act
        return sum(1 for e in events if e["activity"] == act
                     for (ty, oid) in e["objects"]
                     if ty == t and ext(oid) == (side == "ext"))

    pkgs  = {oid for e in events if e["activity"] == "Pack Package"
                          for (ty, oid) in e["objects"] if ty == "Package"}
    dels  = {oid for e in events if e["activity"] == "Dispatch"
                          for (ty, oid) in e["objects"] if ty == "Delivery"}
    invs  = {oid for e in events if e["activity"] == "Issue Invoice"
                          for (ty, oid) in e["objects"] if ty == "Invoice"}

    items_per_pkg = tuple(sorted(
        Counter(oid for e in events if e["activity"] == "Pack Package"
                for (ty, oid) in e["objects"] if ty == "Item").values()))

    pkgs_per_del = tuple(sorted(
        Counter(oid for e in events if e["activity"] == "Dispatch"
                for (ty, oid) in e["objects"] if ty == "Package").values()))

    pays_per_inv = tuple(sorted(
        Counter(oid for e in events if e["activity"] == "Record Payment"
                for (ty, oid) in e["objects"] if ty == "Invoice").values()))

    sig = (
        tuple(sorted(lab.items())),                       # label multiset
        len(pkgs), items_per_pkg,                         # logistics multiplicities
        len(dels), pkgs_per_del,
        objs("Dispatch", "Item", "loc") > 0,              # dispatch-time item ref (substitution)
        objs("Pack Package", "Order", "ext") > 0,         # shared logistics
        objs("Pack Package", "Item",  "ext") > 0,
        len(invs),
        objs("Issue Invoice", "Order", "ext") > 0,        # shared finance
        objs("Record Payment", "Order", "ext") > 0,
        pays_per_inv,
        len(pays_per_inv) > 1,                            # multi-payment (partial settlement)
        qualifiers(events),                               # O2O qualifier vocabulary, sorted
    )
    return sig
```

```python
import pm4py
from collections import defaultdict, Counter

LEAD_TYPE = "Order"
OTYPES = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

# ------------------------------------------------------------------
# 0) Baseline: PM4Py exact clustering (identifier-literal keys)
# ------------------------------------------------------------------
exact = pm4py.cluster_equivalent_ocel(ocel)          # list of sub-OCELs

# ------------------------------------------------------------------
# 1) Slice into Order-centered executions (lead object type = Order)
#    events are assigned to every LOCAL Order they reference;
#    external orders (EXT*) are kept as flags, not as leads.
# ------------------------------------------------------------------
def order_centered_executions(ocel):
    tab = ocel.get_extended_table()                  # event rows, one col per object type
    evs = {}
    for _, r in tab.iterrows():
        objs = [(t, str(oid)) for t in OTYPES
                    for oid in (r[t] if isinstance(r[t], list) else [])]
        evs[r["ocel:eid"]] = {"act": r["ocel:activity"],
                              "ts": r["ocel:timestamp"], "objs": objs}
    out = defaultdict(list)
    for eid, e in sorted(evs.items(), key=lambda kv: kv[1]["ts"]):
        for t, oid in e["objs"]:
            if t == LEAD_TYPE and not oid.startswith("EXT"):
                out[oid].append(e)                   # lead object found
    return dict(out)

# ------------------------------------------------------------------
# 2) Canonicalization: local ids -> typed ordinals, EXT ids -> flag
#    (invariant to local identifier renaming; preserves externality)
# ------------------------------------------------------------------
def canonical_execution(events):
    rename, form = {}, []
    for e in events:
        prof = Counter()
        for t, oid in e["objs"]:
            if oid.startswith("EXT"):
                prof[(t, "EXT")] += 1
            else:
                rename.setdefault((t, oid), (t, rename_count(rename, t)))
                prof[rename[(t, oid)]] += 1
        form.append((e["act"], tuple(sorted(prof.items()))))
    return tuple(form)

def rename_count(rename, t):
    return sum(1 for (ty, _) in rename if ty == t)

# ------------------------------------------------------------------
# 3) Aggregate exact clusters -> canonical clusters -> semantic rollup
# ------------------------------------------------------------------
def postprocess(clusters):
    canon_groups, sem_groups = defaultdict(list), defaultdict(list)
    for sub_ocel in clusters:
        for lead, events in order_centered_executions(sub_ocel).items():
            canon_groups[canonical_execution(events)].append(lead)
            sem_groups[semantic_signature(events)].append(lead)   # Section 2
    return canon_groups, sem_groups

canon, sem = postprocess(exact)
# canon: X1 and X2 now share a key; sem: preferred business clusters
for sig, leads in sorted(sem.items(), key=lambda kv: -len(kv[1])):
    print(len(leads), leads, sig)
```

```python
def semantic_signature(events):
    """events: [{act, ts, objs:[(type, oid)...]}] in canonical order.
       Returns a hashable, renaming-invariant signature (equivalence E3)."""
    is_ext = lambda oid: str(oid).startswith("EXT")
    label_counts = Counter(e["act"] for e in events)

    # ---- logistics multiplicities ----
    pkg_items, del_pkgs, inv_pays = defaultdict(set), defaultdict(set), defaultdict(int)
    dispatch_item_refs = 0
    ext_in = Counter()                                  # (phase, type) -> #EXT refs
    for e in events:
        objs = e["objs"]
        if e["act"] == "Pack Package":
            pkg = next(o for t, o in objs if t == "Package")
            pkg_items[pkg] |= {o for t, o in objs if t == "Item"}
        elif e["act"] == "Dispatch":
            d = next(o for t, o in objs if t == "Delivery")
            del_pkgs[d] |= {o for t, o in objs if t == "Package"}
            dispatch_item_refs += sum(1 for t, o in objs if t == "Item")
        elif e["act"] == "Record Payment":
            inv = next(o for t, o in objs if t == "Invoice")
            inv_pays[inv] += 1
        for t, o in objs:
            if is_ext(o):
                ext_in[(e["act"], t)] += 1

    sig = (
        tuple(sorted(label_counts.items())),                    # lifecycle motif (labels)
        len(pkg_items),
        tuple(sorted(len(v) for v in pkg_items.values())),      # items per package
        len(del_pkgs),
```

```python
from collections import Counter, defaultdict

def semantic_signature(events):
    """events: [{'act':str,'ts':datetime,'objs':[(type,oid),...]},
    sorted by (ts, act). Hashable, renaming-invariant signature for E3."""
    ext = lambda oid: str(oid).startswith("EXT")

    labels = Counter(e["act"] for e in events)

    pkg_items, del_pkgs, inv_pays = defaultdict(set), defaultdict(set), Counter()
    dispatch_item_ref, ext_touch = 0, set()
    for e in events:
        objs = e["objs"]
        if e["act"] == "Pack Package":
            p = next(o for t, o in objs if t == "Package")
            pkg_items[p] |= {o for t, o in objs if t == "Item"}
        elif e["act"] == "Dispatch":
            d = next(o for t, o in objs if t == "Delivery")
            del_pkgs[d] |= {o for t, o in objs if t == "Package"}
            dispatch_item_ref += sum(1 for t, o in objs if t == "Item")
        elif e["act"] == "Record Payment":
            inv_pays[next(o for t, o in objs if t == "Invoice")] += 1
        ext_touch |= {(e["act"], t) for t, o in objs if ext(o)}

    return (
        tuple(sorted(labels.items())),                          # repeated activities
        len(pkg_items),
        tuple(sorted(len(v) for v in pkg_items.values())),      # items per package
        len(del_pkgs),
```

## 4. Cluster interpretations

**SEM-1 — Clean single-shot (X1, X2).** Signature: one package (2 items)  one delivery  one invoice  one payment; no externality; no qualifiers. *Behavior:* textbook order-to-cash. *Risks/opportunities:* none specific; it is the reference class for deviation analytics and the prime automation candidate. *Flattening:* Order-type flattening is faithful here — this is the only cluster where flattening is harmless. *Stability:* fully stable; X1 vs X2 differ only by renaming and Add-Item order, both ignored by design.

**SEM-2 — Split packages, consolidated delivery (X3).** *Behavior:* warehouse splits two items into two boxes, one consignment. *Risks:* partial-package loss within a delivery, receiving complexity; *opportunity:* freight consolidation savings. *Flattening:* Order-flattening keeps both Pack events but loses which items are in which box and that one Delivery carries both; Package-flattening shatters the order. *Stability:* stable.

**SEM-3 — Split packages, split deliveries, partial settlement (X4).** *Behavior:* sequential per-package fulfillment; one invoice settled in two installments. *Risks:* cash-application ambiguity, dunning on residual balance, per-shipment exceptions; *opportunity:* monitor the "final payment exists" norm. *Flattening:* Order-flattening shows two payments but loses invoice binding and the partial/final qualifiers — a naive duplicate-payment detector would misfire. *Stability:* partly stable — payment count survives, but the settlement semantics depends on qualifiers (Section 7).

**SEM-4 — Shared logistics (X5).** *Behavior:* co-packing and co-shipping with another order (EXT-OA); invoice private to O5. *Risks:* coupled exceptions (the other order's cancellation or return propagates), cost-allocation vs billing mismatch (shared box, private invoice). *Flattening:* an Order-flattened O5 is indistinguishable from SEM-1 — a dangerous false baseline; sharing exists only in E2O/O2O. *Stability:* not stable under externality-blind repair (collapses into SEM-1); stable if a boolean "foreign order touched" is retained.

**SEM-5 — Shared finance (X6).** *Behavior:* consolidated invoicing across O6 and EXT-OB; one payment settles without order-level allocation. *Risks:* revenue-recognition split, unallocatable cash application, credit-note complexity. *Flattening:* Order-flattening either duplicates the shared invoice (double-counted revenue) or drops the other order's share; the allocation gap disappears entirely. *Stability:* as SEM-4 — collapses to SEM-1 if externality is ignored.

**SEM-6 — Substitution before dispatch (X7).** *Behavior:* one item replaced or removed before shipping; the package initially packed both. Whether V71 bills the shipped configuration is not recorded — the signature records the substitution, not the billing scope. *Risks:* invoice accuracy, expectation mismatch; *opportunity:* substitution-rate analytics. *Flattening:* every flattening is label-identical to SEM-1; only the Dispatch–item incidence and qualifiers reveal it. *Stability:* fragile — survives only while both incidence and qualifiers are preserved.

**SEM-7 — Return and re-fulfillment (X8).** *Behavior:* post-delivery return of one item, inspection, repack, reshipment; invoice and payment after rework. *Risks:* double shipping cost, refund-vs-replacement decisions, inventory accuracy, billing timing. *Flattening:* Order-flattening keeps Return/Inspect labels but loses which item returned and that P82 replaces P81 for I82; Item-flattening fragments the order. *Stability:* stable — the motif is label-visible; qualifier loss degrades detail but not membership.

A defensible dissenter treats intra-event object lists as ordered tuples, or names objects by first appearance and requires stable listing — but nothing in the notation justifies that. The disagreement is purely a renaming policy.

**X1 vs X5.** E1 merges (identical labels). E2/E3 separate via multiplicity (Pack touches two orders, three items) plus externality. A defensible merger is a *lead-order projection* that strips foreign objects to enforce per-order isolation — then X5 literally becomes X1. Whether sharing is "the other execution's business" or "this execution's semantics" is a modeling choice; I preserve it because the operational coupling is real.

**X1 vs X6.** E1 merges; E2/E3 separate via the second (EXT) order on Invoice and Payment. A *logistics-phase-only* equivalence legitimately merges them — X6's physical flow is X1's — which is right for warehouse segmentation and wrong for finance compliance. Phase scoping decides the answer.

**X1 vs X7.** E1 merges. E2 separates *only* because Dispatch references `Item:I72` — one extra E2O edge. A schema-normalized E2 (many models restrict Dispatch to {Order, Package, Delivery}) merges X7 into X1; then only qualifier-aware E3 separates; drop qualifiers too and X7 is a false baseline. Incidence and qualifiers are complementary carriers of the same fact.

**X3 vs X4.** E1, E2, E3 all separate (label counts, delivery count, payment pattern). A defensible merger is the coarse motif "multi-package fulfillment" — acceptable for capacity planning, wrong for cash-application monitoring. Separately, without settlement qualifiers X4's second payment is indistinguishable from a double-posting data error; qualifiers decide "exception vs. defect."

**X4 vs X8.** All relations separate (X8 carries Return/Inspect). A defensible merger is "two fulfillment waves": count packdispatch cycles, treat payments as amounts, ignore inter-wave labels — both have two waves and a replacement relation (P82 replaces P81; M42 completes V41). The trigger of wave two (planned split vs. exception return) is the business difference, and only labels plus qualifiers carry it.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the key preserves.** In current PM4Py, `cluster_equivalent_ocel` splits an OCEL into sub-OCELs using exact equivalence keys built from the activity label and the concrete object identifiers involved. The key therefore preserves: activity labels, raw object ids, literal E2O incidence, and (via the object table) types. It discards every abstraction: renaming invariance, multiplicity patterns, externality as a flag, qualifiers, order relaxations.

**Why raw ids make it too fine.** X1 and X2 — the same business behavior — land in different clusters; in real logs nearly every execution is id-literal-unique, so exact clustering degenerates to singletons and cannot support segmentation or generalization.

**Canonicalization / post-processing.** (1) Slice into Order-centered executions; (2) rename local ids to typed ordinals, reduce EXT ids to type-level placeholders; (3) recompute keys and merge clusters sharing canonical keys; (4) roll up to semantic signatures. Alternatively, rewrite the OCEL with canonical ids and re-run the function.

**When exact is preferable.** Duplicate/defect detection (the same event recorded twice with identical ids), audit replay where literal bindings are evidence, regression testing after system migration, and as the leaf level of an abstraction lattice from which coarser clusters are derived.

**`max_objs` and large connected executions.** Keys grow with object-set size; a cap truncates keys, causing collisions (false merges) or loss of distinguishing power. Worse, shared objects (EXT-OA, EXT-OB, shared invoices) stitch many orders into one connected component, so clustering returns few giant, effectively unique clusters with memory and time blow-ups. Mitigate via lead-object slicing, externality masking, and bounded keys with collision audits.

```python
import pm4py
from collections import defaultdict, Counter

LEAD_TYPE = "Order"
OTYPES = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

# 0) PM4Py baseline: exact, identifier-literal keys -------------------
exact = pm4py.cluster_equivalent_ocel(ocel)   # list of sub-OCELs

# 1) Slice into Order-centered executions (lead type = Order) ---------
def order_centered(ocel):
    tab = ocel.get_extended_table()           # rows = events, one column per object type
    evs = {}
    for _, r in tab.iterrows():
        objs = [(t, str(oid)) for t in OTYPES
                for oid in (r[t] if isinstance(r[t], list) else [])]
        evs[r["ocel:eid"]] = {"act": r["ocel:activity"],
                              "ts": r["ocel:timestamp"], "objs": objs}
    out = defaultdict(list)
    for eid in sorted(evs, key=lambda k: (evs[k]["ts"], evs[k]["act"])):
        for t, oid in evs[eid]["objs"]:
            if t == LEAD_TYPE and not oid.startswith("EXT"):
                out[oid].append(evs[eid])     # leads are LOCAL Orders only
    return dict(out)

# 2) Canonicalization: local ids -> typed ordinals, EXT -> flag -------
def canonical(events):
    rename, form = {}, []
    for e in events:
        prof = Counter()
        for t, oid in e["objs"]:
            if oid.startswith("EXT"):
                prof[(t, "EXT")] += 1         # externality kept, identity dropped
            else:
                n = sum(1 for (ty, _) in rename if ty == t)
                rename.setdefault((t, oid), (t, n))
                prof[rename[(t, oid)]] += 1
        form.append((e["act"], tuple(sorted(prof.items()))))
    return tuple(form)                        # E2 key: order- and incidence-preserving

# 3) Post-process: canonical merge + preferred semantic rollup ---------
def postprocess(clusters):
    canon, sem = defaultdict(list), defaultdict(list)
    for sub in clusters:
        for lead, events in order_centered(sub).items():
            canon[canonical(events)].append(lead)          # merges X1/X2-type fragments
            sem[semantic_signature(events)].append(lead)   # E3 clustering (Section 2)
    return canon, sem

canon_clusters, sem_clusters = postprocess(exact)
for sig, leads in sorted(sem_clusters.items(), key=lambda kv: -len(kv[1])):
    print(f"{len(leads):5d} orders  {sig}")
```

## 7. Robustness analysis

1. **Ignore all O2O qualifiers.** Partition SEM-1…7 is unchanged (X4 kept by two payments, X7 by the Dispatch item reference, X8 by labels), but resolution degrades: X4's partialfinal pattern becomes a bare "two payments" (indistinguishable from double-posting), X8's package-replacement detail vanishes. Conditional instability: if Dispatch is also schema-normalized, X7 collapses into SEM-1.
2. **Ignore external objects.** The most damaging perturbation. X5 and X6 lose their sharing flags and their residual incidence equals SEM-1's, giving {SEM-1 = X1, X2, X5, X6}, X3, X4, X7, X8. Sharing becomes invisible. Recommended repair: keep a per-phase boolean "foreign-order touch" even when identity is unavailable.
3. **Collapse repeated same-label events.** Within E1, the label multiset becomes a set and X1–X7 merge into one cluster (only X8, with Return/Inspect, stays distinct) — proof that repetition counts are load-bearing. Within E3, the label field coarsens but all other fields hold the seven-way split.
4. **Pack/Dispatch as a partial order (E2p).** No membership change among the eight (no pair differs only by interleaving), but the equivalence universe coarsens: X4 becomes equivalent to a sequential two-wave variant. Acceptable for logistics motifs; dangerous if extended to payment timing (pay-before-dispatch  pay-after). Restrict the relaxation to fulfillment activities.
5. **Payments as an amount attribute.** X4's signature becomes one payment with an amount split — still distinct from SEM-2 (two deliveries) and SEM-1, so membership holds, but the partial-settlement compliance signal disappears; if delivery cardinality were also collapsed, X4 would merge into SEM-2.

Overall: the preferred partition is robust to perturbations 1, 3, 4, 5 and breaks only under externality-blindness (2); X7 is the most fragile member.

## 8. Limitations and recommendation

- **Compliance monitoring:** fine, qualifier-aware equivalence — E2 plus E3's externality/qualifier fields, with identifiers retained for evidence binding. False merges (X6X1) would hide revenue-recognition and settlement-allocation violations.
- **Operational segmentation:** preferred E3 (SEM-1…7, optionally rolled up to {standard, split-fulfillment, shared-execution, rework}) — stable, human-readable, matched to routing and automation decisions.
- **Root-cause analysis:** two-stage coarse-to-fine — start from motif-level rollups to localize anomalous populations (e.g., shared-execution orders), then drill into E2/E3 signatures to identify mechanisms.
- **Descriptive reporting:** E3 with explicit rollups and externality rates, reporting both fine counts and coarse shares.

No single notion serves all four purposes: compliance punishes false merges and needs literal bindings; reporting punishes false splits and needs generalization; root-cause analysis needs both at different stages. E1 is cheap but blind to objects; E0/E2 are precise but do not generalize. The abstraction lattice — with documented, reproducible moves between levels — is the deliverable, not any single partition.
