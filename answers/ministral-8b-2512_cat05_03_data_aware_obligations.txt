## 1. Temporal Data Semantics
### State Reconstruction
- **Event-time state**: Attributes are forward-filled within each case until the next update. Blanks indicate no change (not `null`).
- **Equal timestamps**: Resolved by `event_index` (earlier index takes precedence).
- **Material changes**: Any non-blank update to `amount`, `risk_level`, `jurisdiction`, or `customer_type` is material.
- **Effective time**: Attribute updates take effect at their event timestamp unless evidence (e.g., notes) specifies otherwise.
- **Record vs. evidence time**:
  - Record time = event timestamp (e.g., `Update_Amount` at 12:30).
  - Evidence time = timestamp of supporting artifacts (e.g., exemption approval at 09:05 for EX-77).
- **Final attributes**: Do not retroactively apply to past events. Only the state at the trigger event matters.

## 6. Why Control-Flow-Only Conformance Is Insufficient
1. **Final-state leakage**: Control-flow checks assume the final state reflects all obligations, but obligations may depend on intermediate states (e.g., R4’s material change after review).
2. **Post-hoc exemptions**: Exemptions like EX-88 are recorded *after* release, making conformance checks impossible without temporal reasoning.
3. **Material changes**: R4 requires tracking amount changes *after* reviews, which cannot be captured by simple event ordering.
4. **Conditional activation**: Rules like R1 only apply if jurisdiction/amount meet thresholds, requiring data-dependent checks.
5. **Missing data**: INDETERMINATE cases (e.g., TX-305) cannot be resolved without external evidence, which control-flow ignores.
6. **Same-timestamp ordering**: R7 requires explicit `event_index` handling, which control-flow tools cannot infer.

## 7. Recommended Logging and Control Improvements
1. **Immutable release payloads**: Include `amount`, `jurisdiction`, and `customer_type` in release records to avoid reliance on settlement data.
2. **Effective/record/signature timestamps**: Explicitly log approval times (e.g., `exemption_approved_at`) to distinguish from record times.
3. **Rule versioning**: Track which rule versions apply to each case to avoid ambiguity.
4. **Exemption scope**: Standardize scope fields (e.g., `exemption_amount_scope`) to avoid interpretation errors.
5. **Change provenance**: Log who/why attributes changed (e.g., `updated_by=kyc01, reason=adverse-media`).
6. **Stable event ordering**: Enforce unique timestamps or use `event_id` for unambiguous ordering.
