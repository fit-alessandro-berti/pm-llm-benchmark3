

## 1. Stipulated Facts, Disputed Propositions, and Burden of Proof

**Stipulated Facts:**
- CS-9 (N1) mandates Manual_Procurement_Approval before Activate_Supplier, with Sanctions_Check and Quality_Review.
- PD-3 (N2) allowed Auto_Approve for specific low-risk DE suppliers between 2026-06-01 and 2026-07-31, permitting post-activation Quality_Review.
- FD-7 (N3) allowed provisional activation before Manual/Quality for critical relief between 2026-07-10 and 2026-07-12.
- Both PD-3 and FD-7 expired automatically with no formal extensions documented.
- M0 (Current POWL) enforces Manual_Approval; it has no Auto_Approve branch, no loop for Request_More_Info, and no emergency path.
- From 2026-07-01, 30% of notifications failed to mirror to onboarding logs (N4).
- Case traces are immutable event logs; resource identity comes from separate HR tables.

**Disputed Propositions:**
- *Scope:* M0 applies to "cases," but CS-9 allows abbreviated pre-screen for rejected leads. Is SUP-709 inside M0?
- *Resource Rule:* CS-9 requires Requester  Approver; M0 ignores this. Is this a workflow deviation or a data check?
- *Expiry:* Can operations treat PD-3/FD-7 flows as permanent practices after expiry (SUP-705, SUP-714)?
- *Data Integrity:* Does missing CRM evidence (SUP-706) imply non-notice, or is it a logging defect?

**Burden of Proof:**
- *Noncompliance:* Requires showing a trace deviates from M0/CS-9, authority for exception is invalid (e.g., expired), and risk is material.
- *Exception Acceptance:* Requires demonstrating trace fits valid policy overlay (Pilot/Emergency) during active dates, conditions met, and authorization exists.

## 2. Prosecution Brief

The core control architecture (M0/CS-9) remains the governing authority. Pilot and Emergency directives (PD-3/FD-7) are time-bound legal instruments that expire with documented extension. Continuing them post-expiry normalizes exceptions into policy.

**Key Violations:**
1. **Unauthorized Auto-Approval:** SUP-703 and SUP-714 use Auto_Approve without eligibility or during expired windows. SUP-703 is especially severe (High-Risk supplier, EUR 180k spend, ineligible pilot).
2. **Post-Expiry Emergencies:** SUP-705 and SUP-714 rely on expired authority. Operations' "belief" cannot override written expiration dates.
3. **Sanctions Bypass:** SUP-708 activates a High-Risk supplier before Sanctions_Check. No emergency justified this. This violates fundamental risk control.
4. **Resource Conflict:** SUP-712 has the requester and approver as the same human. CS-9 mandates distinct humans; M0 ignores this, but the rule exists.
5. **Normalization of Deviations:** Aggregate data shows 14 ineligible Auto_Approve cases despite eligibility checks.

Desirable practices (Request_More_Info) do not retroactively amend written policy without formal adoption. We must enforce M0/CS-9 to ensure financial and reputational integrity. Deviations like SUP-703 and SUP-708 are not "data issues"—they are control failures.

## 3. Defense Brief

M0 represents a theoretical state that no longer matches operational reality or authority. It excludes critical paths authorized by the organization (Auto_Approve, Emergency) and fails to encode necessary checks (Resource, Request_More_Info).

**Key Defects:**
1. **Obsolete Control Flow:** M0 lacks the Auto_Approve branch authorized by PD-3. SUP-702 is a compliant case under active PD-3; punishing it ignores the policy overlay.
2. **Scope Ambiguity:** M0 begins at `Register_Supplier`. SUP-709 describes a rejected lead from pre-screen. If pre-screen is outside M0, SUP-709 should not be judged against M0.
3. **Data Loss:** SUP-706 lacks notification in logs due to CRM migration (N4). The event exists in CRM (mutable link). Penalizing system migration failures is unjust.
4. **Missing Logic:** M0 has no loop for Request_More_Info. SUP-707 follows the loop; penalizing this ignores business desirability.
5. **Lifecycle Gaps:** SUP-710 is a reactivation. CS-9 has no explicit reactivation path; SUP-710 fits "Register" logic but misses `Quality_Review`. If the supplier was pre-qualified, this is a scope gap.
6. **Semantic Stability:** SUP-713 used QA_Clearance instead of Quality_Review. This is a label change.

The prosecution treats model rigidity as compliance. M0 needs revision to capture Auto, Emergency, and RMI. SUP-705 and SUP-714 may be procedural drift, but SUP-702 and SUP-704 are justified. We reject the notion that all deviations are violations.

## 6. Revised Normative Architecture

**Layer 1: Control Flow (POWL)**
- **Model:** M1 (Revised).
- **Features:** Adds `Auto_Approve` branch and `Emergency_Provisional` branch. Adds `Request_More_Info` subprocess (with self-reference approximation).

**Layer 2: Constraints (Data/Declare)**
- **Resources:** Requester  Approver; Spouses/Same-lineage COI checks.
- **Timing:** Quality_Review within 2 days (post-activation for pilot/emergency).
- **Financial:** Spend caps (EUR 20k emergency).

**Layer 3: Policy Overlays (Governance)**
- **Versions:** Policy versioning table (PD-3 Active, Expired, etc.).
- **Exceptions:** Explicit temporary exception logging (who authorized, why, date).

**Layer 4: Scope & Lifecycle**
- **Rejected Leads:** Explicit boundary (pre-screen is NOT in M1).
- **Reactivations:** Separate model or flags (No Quality if recent certification).

**Location of Constraints:**
- POWL handles control flow (Parallel checks, XOR decision, branches).
- Data Checks handle attributes (Amounts, Dates, Identity).
- Organizational Controls handle Conflict of Interest and COI approvals.

from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition
from pm4py.objects.process_tree.obj import Operator
from typing import List, Dict, Any

# --- Revised Model M1: POWL Construction ---
# Note: StrictPartialOrder is acyclic. Request_More_Info loops must be approximated
# by a subprocess or self-reference in a ProcessTree (if supported), but here
# we define it as an explicit optional path before Decision.

# Transitions
t_register = Transition(label="Register_Supplier")
t_sanctions = Transition(label="Sanctions_Check")
t_quality = Transition(label="Quality_Review")
t_manual = Transition(label="Manual_Procurement_Approval")
t_auto = Transition(label="Auto_Approve")
t_emergency = Transition(label="Emergency_Provisional_Activation")
t_activate = Transition(label="Activate_Supplier")
t_reject = Transition(label="Reject_Supplier")
t_notify = Transition(label="Notify_Requester")
t_close = Transition(label="Close_Case")
t_rmi = Transition(label="Request_More_Info")

# Concurrent Checks (Standard Route)
checks = StrictPartialOrder(nodes=[t_sanctions, t_quality])
# Parallel check does not enforce order; M1 ensures both fire.

# Approved Branches (Standard)
standard_manual = StrictPartialOrder(nodes=[t_manual, t_activate])
standard_manual.order.add_edge(t_manual, t_activate)

# Auto Branch (Low-Risk Pilot)
auto_branch = StrictPartialOrder(nodes=[t_auto, t_activate])
auto_branch.order.add_edge(t_auto, t_activate)

# Emergency Branch (Critical Relief)
emergency_branch = StrictPartialOrder(nodes=[t_emergency, t_activate])
emergency_branch.order.add_edge(t_emergency, t_activate)

# Decision: XOR between Standard, Auto, Emergency, or Reject
branch_list = [standard_manual, auto_branch, emergency_branch, t_reject]
decision = OperatorPOWL(operator=Operator.XOR, children=branch_list)

# Decision to Notify to Close
notify_close = StrictPartialOrder(nodes=[t_notify, t_close])
notify_close.order.add_edge(t_notify, t_close)

# Main Assembly
M1 = StrictPartialOrder(nodes=[t_register, checks, decision, notify_close])
M1.order.add_edge(t_register, checks)
M1.order.add_edge(checks, decision)
M1.order.add_edge(decision, t_notify)
