## 1. Analytical assumptions

**Case notion.** I treat a "case notion" as the choice of an object type that serves as the spine of a flattened event log: every event directly related to an object of that type is copied into that object's trace, and the resulting trace is treated as a unit of analysis. No relation propagation is performed unless I explicitly say so.

**Convergence.** Convergence occurs when a single physical event is copied into multiple cases of the same flattened log. The event e16 (Dispatch, 11:05) is directly related to O1, O2, and O3; flattening on Order therefore places e16 in three separate order traces. Convergence inflates event frequencies and can create spurious independence between observations that are, in reality, one shared operation.

**Divergence.** Divergence occurs when one logical business entity (e.g., one delivery, one invoice, one package) is scattered across multiple cases, so that the flattening fragments a unitary real-world event into case-internal artefacts that cannot be reassembled. Flattening on Order, for instance, splits V2's payment history across the O2 and O3 traces, so the two-instalment settlement of V2 is not visible as a single financial lifecycle.

**Shared events.** I treat copied shared events as both evidence and duplication. They are evidence that the event genuinely involved multiple objects (e.g., D2 really does carry packages for three orders). They are duplication because each copy contributes a separate frequency count and a separate performance observation to the DFG, even though the event occurred once. I will mark every frequency or performance metric derived from a shared event as context-dependent unless I explicitly justify otherwise.

**Analytical transformations.** By default I use only the E2O relations as given. I will, in one sensitivity check, define a *propagated-relation variant* in which O2O links (e.g., Order–contains–Item, Package–packs–Item, Delivery–carries–Package) are transitively closed so that, for example, e05 (Add Item, related to O1 and I11) also becomes related to P1 and D1. I treat this as a deliberate analytical transformation, not a default.

**Effect:** In the order DFG, the edge Dispatch  Confirm Delivery gains +3 frequency from e16e24 (one real delivery counted three times). The dispatch-to-confirm latency for D2 (4h55m) is recorded as three independent observations (O1, O2, O3), inflating the sample size. If a analyst computes mean delivery time from the order log, D2's single window dominates with pseudoreplication.
**Verdict:** Harmful for statistical inference; informative for identifying which orders shared a delivery.

### Distortion 4 — Consolidated invoice V2 in the Order flattening (semantic blurring of payments)
**Affected flattening:** Order.
**Citation:** e19 (Issue Invoice, 12:05) relates to O2 and O3. e22 (Record Payment, 12:40, M2 partial) and e25 (Record Payment, 14:00 next day, M3 complete) both relate to O2 and O3.
**Effect:** In O2's trace, the DFG shows Issue Invoice (e19)  Record Payment (e22)  Record Payment (e25), suggesting O2 received two payments. In reality, V2 is one consolidated invoice for O2+O3, settled in two instalments (M2 partial, M3 complete). The order log cannot distinguish "two instalments on one invoice" from "two separate payments." O3's trace shows the identical pattern, so the payment count is doubled (4 payment events across O2+O3 vs 2 actual payments on V2).
**Verdict:** Harmful for revenue analytics; the invoice flattening resolves this correctly.

### Distortion 5 — Partial payment semantics visible only in the Invoice flattening
**Affected flattening:** Invoice (the only flattening that preserves this correctly).
**Citation:** V2's trace: e19 (Issue Invoice)  e22 (Record Payment, M2, qualifier "partially_settles")  e25 (Record Payment, M3, qualifier "completes_settlement").
**Effect:** The invoice log correctly shows a two-event payment lifecycle for V2. However, the invoice log loses all connection to the orders (O2, O3) and to the physical fulfillment. If one asks "did O2's items ship before V2 was fully settled?" the invoice log alone cannot answer, because it does not contain Dispatch or Confirm Delivery events.
**Verdict:** Informative within its scope; context-dependent if used without the order log.

### Distortion 6 — Near-singleton Payment lifecycle
**Affected flattening:** Payment.
**Citation:** M1: e21 only. M2: e22 only. M3: e25 only. M4: e26 only.
**Effect:** The DFG consists of four isolated "Record Payment" nodes with no edges. There is no variant, no throughput time, no concurrency. Any process-mining question about payment flow is unanswerable. This is a degenerate flattening.
**Verdict:** Harmful as a lead object; useful only as a reference table (payment  invoice mapping).

### Distortion 7 — Item flattening lifecycle truncation
**Affected flattening:** Item.
**Citation:** I11's trace: e05 (Add Item)  e11 (Pack)  e15 (Dispatch)  e23 (Confirm Delivery). No Create Order, no Invoice, no Payment, no Close Order.
**Effect:** The item DFG is a clean four-activity linear chain. If used as the primary process model, it suggests the process ends at delivery, completely omitting the financial closure. An analyst comparing item-log variants would see all six items as having the "same" variant, hiding the fact that O1 (I11, I12) was split across two deliveries while O4 (I41) went through a cross-order package.
**Verdict:** Harmful for end-to-end analysis; informative for tracking physical item provenance.

### Distortion 8 — Package flattening order-attribution loss
**Affected flattening:** Package.
**Citation:** P3's trace: e13 (Pack)  e16 (Dispatch)  e24 (Confirm Delivery). P3 packs I21 (O2) and I31 (O3), but the package log contains no order identifiers.
**Effect:** The DFG for P3 is identical to P1's DFG (Pack  Dispatch  Confirm). There is no way to detect that P3 is a cross-order package while P1 is a single-order package. A frequency analysis would count four packages, all with the same 3-event lifecycle, suggesting uniform packaging behaviour when the underlying order structure differs fundamentally.
**Verdict:** Harmful for understanding order-to-package mapping; context-dependent for pure logistics.

### Distortion 9 — O1 split-package performance bias in the Order flattening
**Affected flattening:** Order.
**Citation:** O1's trace includes e15 (Dispatch via D1, 11:00)  e23 (Confirm Delivery, 14:00, latency 3h) and e16 (Dispatch via D2, 11:05)  e24 (Confirm Delivery, 16:00, latency 4h55m).
**Effect:** If one computes "average dispatch-to-confirm time for O1," the result is (3h + 4h55m)/2  3h58m. But D1 is a solo delivery and D2 is a consolidated delivery involving three orders. Averaging the two conflates fundamentally different delivery routes. This bias is invisible in the order DFG because both edges are labelled "Dispatch  Confirm Delivery."
**Verdict:** Context-dependent; harmful if used for SLA reporting without disaggregating by delivery.

### Distortion 10 — Delivery flattening eliminates all upstream context
**Affected flattening:** Delivery.
**Citation:** D2's trace: e16 (Dispatch)  e24 (Confirm Delivery). No pack, order, invoice, or payment events.
**Effect:** The DFG is Dispatch  Confirm Delivery for all three deliveries. D2's 4h55m window is correctly a single observation (no convergence), but the analyst cannot tell that D2 involved three orders, two packages, and a consolidated invoice. Delivery as lead object produces the cleanest performance metric but the most impoverished process model.
**Verdict:** Harmful for end-to-end; informative for delivery-window benchmarking.

## 4. Traditional versus object-centric analysis portfolio

### Flattened logs to create

**Order log** — Create as the primary flattened log. Safe questions:
- "What is the activity sequence from order creation to closure, per order?" (e01–e31, four cases).
- "Which orders shared a dispatch or confirmation event?" (identifiable by shared timestamps, though DFG does not encode this).
- "Did every order close?" (e28–e31 confirm all four closed).

Unsafe questions for the order log alone:
- "How many deliveries occurred?" (inflated: e16/e24 counted 3×).
- "How many invoices were issued?" (inflated: e19 counted 2×).
- "Was V2 fully settled?" (partial vs complete not distinguishable).

**Invoice log** — Create as a secondary financial log. Safe questions:
- "Which invoices had multiple payment events?" (V2: e22, e25).
- "What is the time from invoice issue to final settlement?" (V1: e18e21, 30min; V2: e19e25, 21h; V3: e20e26, 21.5h).

**Package log** and **Delivery log** — Create as tertiary logistics logs. Safe questions:
- "Pack-to-dispatch time per package" (e11e15 for P1: 1h; e13e16 for P3: 53min; etc.).
- "Dispatch-to-confirm time per delivery" (D1: 3h; D2: 4h55m; D3: 22h45m).

**Item log** — Create only if physical provenance tracking is the goal.

**Payment log** — Do not create as a process log; use as a lookup table.

### Questions requiring object-centric techniques

| Question | Required technique |
|---|---|
| "How many physical deliveries occurred, and which orders did each involve?" | OC-DFG with Delivery as the central object type, cross-referenced to Order via E2O on e16/e24. |
| "Is the V2 two-instalment payment correlated with O2 and O3's delivery confirmation?" | ET–OT graph: relate Invoice and Order co-occurrence in e19, e22, e25. |
| "Which packages are cross-order, and does this affect delivery latency?" | Object interaction summary on Package–Order pairs (P3O2/O3, P4O3/O4) combined with delivery timestamps. |
| "What is the true end-to-end variant, accounting for shared events without double-counting?" | Equivalent-execution clustering to group events by shared object participation, avoiding convergence inflation. |
| "Does the OTG reveal that Invoice and Delivery lifecycles run concurrently for some orders?" | OTG, overlaying Invoice and Delivery sub-lifecycles for O2/O3. |

### Reconciling contradictory findings

If the order DFG reports "6 Record Payment events" (e21, e22, e25 counted 2× each across O2+O3, plus e26) but the invoice DFG reports "3 Record Payment events" (e21, e22, e25, e26 = 4, but M2 and M3 both on V2), the reconciliation rule is: **physical-event count = unique event IDs; case-internal count = sum over flattened cases.** The order log's 6 payment events are 4 unique events (e21, e22, e25, e26) with e22 and e25 each doubled by convergence. The invoice log's 4 payment events are the true unique count. When metrics disagree, default to the unique-event count from the OC-DFG and annotate the flattened-log count as "case-relative frequency."

## 5. Lead-object decision

**Decision: B. Use a primary lead object (Order) plus explicitly secondary lifecycles (Invoice for financial, Package/Delivery for logistics).**

### Decision criteria
1. **Activity coverage:** The lead object should participate in the widest set of activity types to support end-to-end analysis.
2. **Convergence tolerance:** The lead object should minimise the ratio of duplicated events to unique events.
3. **Semantic completeness:** The lead object should preserve business-meaningful distinctions (e.g., partial vs complete payment, solo vs consolidated delivery).
4. **Traceability to physical operations:** The lead object should connect financial and physical flows.

### Strongest supporting evidence
Order is the only object type that touches all 31 events and all 9 activity types (Create Order, Add Item, Pack Package, Dispatch, Issue Invoice, Record Payment, Confirm Delivery, Close Order). No other flattening captures more than 4 activity types (Item: 4; Package: 3; Delivery: 2; Invoice: 2; Payment: 1). For end-to-end lifecycle questions, Order is indispensable.

However, the Order log has 10 duplicated event copies (convergence on e13, e14, e16, e17, e19, e22, e24, e25, e27), and it cannot distinguish M2 (partial) from M3 (complete) on V2. Therefore Order alone is insufficient. The Invoice log uniquely preserves the partial/complete settlement semantics for V2 (e22 vs e25), and the Delivery log uniquely provides unconsolidated delivery-window metrics (D2's 4h55m as a single observation rather than three).

### Strongest counterargument
The Order log's convergence on D2 (e16, e24 triple-counted) and V2 (e19, e22, e25 double-counted) means that any frequency or performance metric derived from it is systematically biased. A purist could argue that no flattened log should be primary and that only the OC-DFG / OTG should be used. This is valid for frequency and performance analytics but sacrifices the interpretability of trace-level variant analysis, which requires a case spine.

### Residual risk
Even with Order as primary and Invoice/Delivery as secondary, the cross-order packages P3 and P4 remain structurally invisible in any single flattening. P3 serves O2 and O3 simultaneously, and no flattened log can represent this as a single trace. Only the object interaction summary or OTG can reveal it.

### Conditions under which I would change my decision
- If the analysis goal were purely financial (billing and settlement), I would switch the primary to Invoice.
- If the goal were purely logistics (delivery SLA), I would switch to Delivery.
- If the goal were to identify cross-order co-packaging patterns as the central question, I would reject any lead object (position C) and rely solely on OC-DFG + object interaction summary.

## 7. Sensitivity and validation plan

### Check 1 — Remove or down-weight copied shared events
Re-flatten on Order but, for each event ID that appears in more than one order case (e13, e14, e16, e17, e19, e22, e24, e25, e27), retain the event in only the first order case (by timestamp within case) and mark the others as "shared-reference" events excluded from DFG frequency computation. Compare the resulting DFG edge frequencies with the standard order DFG. Expected change: the Dispatch  Confirm Delivery edge loses 4 frequency units (e16e24 was 3×, now 1× for D2; e17e27 was 2×, now 1× for D3), revealing that the "true" delivery count is 3, not 7.

### Check 2 — Direct E2O vs propagated-relation variant
Construct a propagated OCEL in which every event related to an Item also becomes related to the Package that packs it and the Delivery that carries it (transitively through O2O). Re-flatten on Order. Expected change: events e05–e10 (Add Item) now also carry Package and Delivery identifiers, but since flattening on Order already includes these events via the direct O1/I11 relation, the order DFG structure should not change. However, the Package and Delivery flattened logs gain Add Item events, enriching their otherwise truncated lifecycles. Compare the Package DFG with and without propagation: propagated Package DFG should show Add Item  Pack Package  Dispatch  Confirm Delivery (4 activities vs 3). This test reveals whether the shortness of the Package/Delivery lifecycle is a real business property or an artefact of sparse E2O annotation.

### Check 3 — Change the lead object
Re-run the full DFG and log-skeleton discovery with Invoice as lead instead of Order. Compare the financial lifecycle model: Invoice DFG shows Issue Invoice  Record Payment  Record Payment (for V2 only), a pattern absent from the Order DFG where Record Payment appears as a single activity without distinguishing partial from complete. Then switch to Delivery as lead and compare delivery-window distributions: D2's latency (4h55m) is a single observation in the Delivery log but appears as three observations (O1, O2, O3) in the Order log. This quantifies the pseudoreplication effect.

### Check 4 — Frequency metrics: events vs unique objects vs total objects
For each activity in the OC-DFG, compute three frequency measures: (a) count of unique event IDs, (b) count of unique objects of each type related to those events, (c) total E2O relation tuples. For Dispatch: (a) = 3 (e15, e16, e17), (b) = 3 unique deliveries (D1, D2, D3) but 6 unique orders (O1, O2, O3, O4 — O1, O2, O3 appear in both e16 and e24; actually unique orders touching Dispatch = O1, O2, O3, O4 = 4), (c) = total E2O tuples for Dispatch events. The ratio (c)/(a) measures convergence intensity per activity. Dispatch should show a high ratio (many objects per event), confirming it is a convergence hotspot. Close Order should show a ratio of 1.0 (one order per event), confirming it is divergence-free. This metric systematically identifies which activities are safe for flattened-log frequency analysis and which require OC-DFG unique-event counts.
