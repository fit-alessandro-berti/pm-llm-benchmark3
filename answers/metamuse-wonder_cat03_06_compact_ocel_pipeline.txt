## 1. Modeling assumptions

- **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, all singular and capitalized. Object IDs retain the identifiers in the narrative: `O100`, `O200`, `I1`–`I3`, `P1`–`P2`, `D1`–`D2`, `V1`, and `M1`–`M2`.
- **E2O qualifier vocabulary:**
  - `created` — the event creates the linked object, used for an `Order` at order creation and a `Package` at packing.
  - `added_item` / `target_order` — an item-addition event links the added `Item` and the receiving `Order`.
  - `reserved_item` / `affected_order` — stock reservation links each reserved `Item` and each explicitly affected `Order`.
  - `packed_item` / `source_order` — packing links each packed `Item` and the `Order` from which that item originates; the created `Package` uses `created`.
  - `dispatched_package` / `dispatched_via` — dispatch links the `Package` and its `Delivery`.
  - `issued_invoice` / `billed_order` — invoice issue links the created `Invoice` and each billed `Order`.
  - `recorded_payment` / `settled_invoice` — payment recording links the `Payment` and the `Invoice` it pays against.
  - `confirmed_delivery` — delivery confirmation links only the confirmed `Delivery`.
  - `closed_order` — order closure links only the closed `Order`.
- **O2O direction conventions:** `ocel:oid` is the source and `ocel:oid_2` is the target, read in the direction of the qualifier: `Order --contains--> Item`, `Package --packs--> Item`, `Delivery --carries--> Package`, `Invoice --bills--> Order`, and `Payment --partially_settles--> Invoice`. Both payments use `partially_settles`: the narrative gives payment amounts of 100 and 150 but no invoice total, so completion of settlement by `M2` is not asserted.
- **Direct versus propagated relations:** Logistics and financial events are related directly only to the objects they operationally manipulate. Dispatch links `Package`–`Delivery` but not `Order` or `Item`; delivery confirmation links only `Delivery`; payments link `Payment`–`Invoice` but not `Order`; closure links only `Order`. Two exceptions are deliberately source-level, because the narrative explicitly states them: joint stock reservation links both items and both orders, packing `P1` links both source orders, and invoice issue links both billed orders. All other reachability, such as `Payment  Invoice  Order` or `Delivery  Package  Item  Order`, is left to O2O traversal.
- **Trade-off and provenance:** Direct source relations preserve the source-system facts and expose genuine convergence at `Reserve Stock`, `Pack Package P1`, and `Issue Invoice`. Adding every transitively reachable `Order` and `Item` to every downstream event would make flattened order traces look complete, but would inflate relations, copy shared events into many more traces, exaggerate directly-follows evidence, and disguise propagation as observation. Therefore propagated relations are **not** placed in `relations`. If an analytical variant is needed, it should be built as a separate DataFrame, given `derived_…` qualifiers and, ideally, a provenance column, and only then supplied to a separately named OCEL.
- **Version-dependent PM4Py assumption:** The code assumes a constructor equivalent to `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` from `pm4py.objects.ocel.obj`. If another PM4Py release exposes the class elsewhere or accepts different keyword names, only that isolated construction line should be adapted; the four DataFrames and their semantics remain unchanged.

    "Orphan event ID in relations."

## 3. Data-model audit

**Object types and their objects**

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

**O2O qualifiers and cardinality**

| O2O qualifier | Direction | Rows |
|---|---|---|
| `contains` | Order  Item | 3 (O100I1, O100I2, O200I3) |
| `packs` | Package  Item | 3 (P1I1, P1I3, P2I2) |
| `carries` | Delivery  Package | 2 (D1P1, D2P2) |
| `bills` | Invoice  Order | 2 (V1O100, V1O200) |
| `partially_settles` | Payment  Invoice | 2 (M1V1, M2V1) |

**Activities and the object types they touch (direct E2O policy)**

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Item, Order |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

**Especially consequential events:** `E06 Reserve Stock` (I1, I3, O100, O200), `E07 Pack Package P1` (P1, I1, I3, O100, O200), and `E11 Issue Invoice` (V1, O100, O200) are the convergence/divergence hotspots. Each is a single event related to both orders, so any order flattening copies it into both order traces, and any per-type frequency count sees it once while trace-based counts see it twice. `E07` additionally binds together items originating in different orders, making `P1` the physical point where the two order lifecycles merge.

## 4. Expected flattened behavior

**Order flattening.** Approximate traces: `O100 = Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Issue Invoice  Close Order` (8 events); `O200 = Create Order  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order` (6 events). Copied shared events: `E06 Reserve Stock`, `E07 Pack Package P1`, and `E11 Issue Invoice` each appear in both traces, so 17 source events become 20 trace events. Omitted lifecycle aspects: dispatch, delivery confirmation, and payments have no direct `Order` link, so logistics completion and settlement are invisible. Likely DFG edges include `Create OrderAdd Item`, `Add ItemReserve Stock`, `Reserve StockPack Package`, `Pack PackagePack Package` (an artifact of O100 having two packs, not a loop in the process), `Pack PackageIssue Invoice`, and `Issue InvoiceClose Order`; `O200` closes before `O100` in wall-clock time but that ordering is *between* traces and invisible. Misleading interpretation: it looks as if orders are invoiced and then closed with no delivery or payment in between, and the self-loop on `Pack Package` suggests repetition rather than two distinct packages.

**Package flattening.** Approximate traces: `P1 = Pack Package  Dispatch Package`; `P2 = Pack Package  Dispatch Package` (2 events each). Copied shared events: none between packages, although `E07 Pack Package P1` is shared in the OCEL with items and orders. Omitted aspects: delivery confirmation (linked only to `Delivery`), order creation, item addition, invoicing, and payment. Likely DFG edge: only `Pack PackageDispatch Package`. Misleading interpretation: packages appear to vanish at dispatch; the model cannot show that `D1` was confirmed a day earlier than `D2`, nor that `P1` mixes two orders.

**Delivery flattening.** Approximate traces: `D1 = Dispatch Package  Confirm Delivery`; `D2 = Dispatch Package  Confirm Delivery`. Copied shared events: none. Omitted aspects: everything before dispatch — packing, item composition, orders — and all finance. Likely DFG edge: only `Dispatch PackageConfirm Delivery`. Misleading interpretation: deliveries look like a trivial two-step process with identical behavior, hiding that `D1`/`P1` is the cross-order shipment and that confirmation of `D2` occurred almost a day after `D1`.

**Invoice flattening.** One trace: `V1 = Issue Invoice  Record Payment  Record Payment`. Copied shared events: `E11` is shared with both orders in the OCEL but appears once here. Omitted aspects: which orders were billed (visible only via O2O), deliveries, closure, and the identity/amount distinction between payments — `M1` (100) and `M2` (150) collapse into the same activity label. Likely DFG edges: `Issue InvoiceRecord Payment` and a `Record PaymentRecord Payment` self-loop. Misleading interpretation: the self-loop looks like an arbitrary repeatable payment activity; nothing shows partial settlement semantics, cumulative amount (250), or that payment continued after `D1` was confirmed but before `D2` closed the second order.

**Why Payment flattening is particularly weak:** each payment is a case with exactly one event (`M1: Record Payment`; `M2: Record Payment`). Both traces are length 1, the DFG has no edges at all, and a log skeleton can express almost nothing. The two payments are structurally indistinguishable despite different amounts and timestamps, their shared target `V1` becomes invisible, and the fact that they jointly settle one invoice spanning two orders is entirely lost. Payment is a participating object, not a viable case notion here.

## 5. Expected object-centric structures

- **OC-DFG:** Per-type directly-follows arcs should show the order chain (`Create OrderAdd ItemReserve StockPack PackageIssue InvoiceClose Order`), the package chain (`Pack PackageDispatch Package`), the delivery chain (`Dispatch PackageConfirm Delivery`), and the invoice chain (`Issue InvoiceRecord PaymentRecord Payment`). Crucially, shared activities such as `Pack Package` and `Record Payment` carry multiple object-type annotations, so `P1`'s packing event simultaneously advances the `Item`, `Package`, and both `Order` perspectives without duplicating the event. Frequencies on arcs will differ per object type — e.g., `Pack Package` has frequency 2 for `Package` but touches three item-events and three order-event incidences — which is exactly the divergence/convergence signal flattening distorts.
- **OTG (object type graph):** Nodes are the six object types; edges summarize which types co-occur at events. Expect strong `Order–Item`, `Item–Package`, `Package–Delivery`, `Order–Invoice`, and `Invoice–Payment` connections, plus `Order–Package` co-occurrence through packing. The graph should make the hub roles visible: `Item` bridges `Order` and `Package`; `Invoice` bridges `Order` and `Payment`.
- **ET–OT graph:** Each of the nine activities connects to the object types in the audit table above. `Pack Package` and `Reserve Stock` will have the highest type degree (three types each, and multiple object instances), `Confirm Delivery` and `Create Order`/`Close Order` the lowest. This bipartite view predicts flattening quality per type: types linked to many activities (Order) yield rich traces; types linked to few (Delivery, Payment) yield degenerate ones.
- **Object-centric Petri net:** Expect one place per object type with type-specific transitions for each activity, so a single `Pack Package` transition consumes/produces tokens for `Package`, `Item`, and `Order` places simultaneously — faithfully representing that packing `P1` synchronizes `I1`/`O100` with `I3`/`O200`. `Issue Invoice` similarly synchronizes `V1` with both orders, and each `Record Payment` transition binds one `Payment` token with the persistent `V1` token. This net is one plausible discovered interpretation, not a uniquely determined ground truth: discovery choices (e.g., how repeated `Record Payment` bindings or the two `Add Item` events per order are generalized) can vary.
- **Object-interactions summary:** Expect the densest interactions around the shared objects: `V1` interacts with `O100`, `O200`, `M1`, and `M2`; `P1` interacts with `I1`, `I3`, both orders, and `D1`; `O100` interacts with the most objects overall (I1, I2, P1, P2, V1). `O200`'s interaction profile is a subset centered on `I3`, `P1`, and `V1`, exposing the asymmetry between the two orders, while `M1` and `M2` each interact only with `V1`, quantifying their peripheral, single-link role.

## 6. Modeling alternatives

1. **Source-minimal relations (even stricter than the chosen policy):** Link each event only to the object it creates or primarily manipulates — e.g., `Reserve Stock` links only items, `Pack Package` only the package and items, `Issue Invoice` only `V1`. Orders then lose `Reserve Stock` and `Issue Invoice` from their flattened traces unless O2O traversal is applied, flattening on `Order` fragments into creation/addition/closure only, and the OC-DFG shows fewer cross-type synchronizations. Discovery looks "cleaner" but understates genuine shared events that the narrative explicitly declares.
2. **Full operational involvement (the chosen policy):** Events link every object they directly manipulate or explicitly reference, including both orders at reservation, `P1` packing, and invoicing, but nothing transitively downstream. Flattened order traces are meaningful yet end at invoicing/closure; the OC-DFG and OCPN show real synchronization points without inventing observations. This balances fidelity and analytical usefulness.
3. **O2O-propagated analytical relations:** Derive additional E2O rows by transitive closure over O2O — payments also link to both orders, dispatch and confirmation also link to packages, items, and orders, closure links to everything upstream. Flattened order traces become end-to-end (`…DispatchConfirmPaymentClose`), and flattened DFGs appear richer, but at a cost: event frequencies inflate massively (one payment event counted for two orders, one confirmation for many objects), directly-follows edges appear that no source system ever observed in that order context, and convergence artifacts (spurious loops and parallelism) multiply. The business story is unchanged; only the evidentiary status of the relations has changed, which is why such rows must be marked as derived if used at all.

## 7. Failure modes

1. **Relation inflation:** Propagating all reachable objects into every event multiplies relation rows, inflates activity frequencies per object type, and manufactures DFG edges; models look more connected than the source process is.
2. **Missing direct E2O links:** Conversely, omitting the explicit order links at `E06`, `E07`, or `E11` breaks order traces and hides true convergence, making `P1`'s cross-order nature undiscoverable from events alone.
3. **Treating O2O propagation as observation:** O2O states static containment (`V1 bills O100`), not that an event was observed for that order; silently converting it into E2O rows confuses structure with behavior and invalidates frequency and conformance claims.
4. **Duplicate shared events after flattening:** `E06`, `E07`, and `E11` each appear in both order traces, so flattened event counts exceed 17; reporting these as distinct process executions double-counts work and cost.
5. **Ambiguous payment allocation:** `M1` (100) and `M2` (150) settle `V1` jointly for two orders, but no allocation of amounts to `O100` versus `O200` exists; any per-order revenue or settlement analysis would be fabricated.
6. **Overly short Payment traces:** Flattening on `Payment` yields two one-event traces with no DFG edges; discovery, skeleton, and conformance results are vacuous, and the amounts that distinguish `M1` from `M2` disappear.
7. **Constructor/API version mismatch:** OCEL class location, constructor keywords, and function names (e.g., OTG/ET–OT discovery, OCPN viewing) differ across PM4Py versions; pinning or isolating the construction line prevents a version bump from corrupting the dataset semantics.
8. **False total order for same-time events:** Flattening imposes a sequence within a trace; if two events shared a timestamp, timestamp sorting would invent an order. This example deliberately has no timestamp ties, but the pipeline should not be assumed tie-safe without a secondary ordering key.
9. **Cardinality blindness in discovery:** Most discovery algorithms ignore that `Pack Package` binds a variable number of items or that `Record Payment` repeats against one invoice; discovered nets may permit unbounded or single bindings that misrepresent `P1` (two items, two orders) and `V1` (two payments).
10. **Activity-label collapse:** Distinct real-world occurrences share labels (`Add Item` ×3, `Record Payment` ×2), so label-based models merge them; object identity, not the label, carries the real distinction.

## 8. Final semantic checks

A reviewer can manually verify the construction by inspecting the four tables:

1. `events` has exactly 17 rows with unique IDs `E01`–`E17`, UTC-aware timestamps in strictly increasing order, and amounts 100 and 150 on the two `Record Payment` rows only.
2. `objects` has exactly 12 rows: two `Order`, three `Item`, two `Package`, two `Delivery`, one `Invoice`, two `Payment`, with no amount modeled as an object.
