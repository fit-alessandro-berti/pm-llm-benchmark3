def cluster_diag(sub):

    n = len(sub)
    # overlap pairwise
    pairs = 0
    overlaps = 0
    for i in range(n):
        for j in range(i+1, n):
            s1,e1 = sub.iloc[i][["start","complete"]]
            s2,e2 = sub.iloc[j][["start","complete"]]
            if pd.notna(s1) and pd.notna(e1) and pd.notna(s2) and pd.notna(e2):
                pairs += 1
                if max(s1,s2) < min(e1,e2):
                    overlaps += 1
    overlap_rate = overlaps / pairs if pairs else np.nan
    start_counts = sub["start"].value_counts(dropna=True)
    complete_counts = sub["complete"].value_counts(dropna=True)
    max_start_eq = int(start_counts.max()) if len(start_counts) else 0
    max_complete_eq = int(complete_counts.max()) if len(complete_counts) else 0
    lag_sec = (sub["recorded_at"] - sub["complete"]).dt.total_seconds()
    ts = pd.concat([sub["start"], sub["complete"]]).dropna().sort_values().drop_duplicates()

        events.append((r["queue_arrival"], 1))
        events.append((r["start"], -1))
    # arrivals before starts at same timestamp

    q = 0
    maxq = 0
    for _, delta in events:
        q += delta
        maxq = max(maxq, q)
    wait_min = (sub["start"] - sub["queue_arrival"]).dt.total_seconds()/60
    return pd.Series({

def cluster_diag(sub):
    sub = sub.sort_values("sequence_no").copy()
    n = len(sub)

    pairs = 0
    overlaps = 0
    for i in range(n):
        for j in range(i + 1, n):
            s1, e1 = sub.iloc[i]["start"], sub.iloc[i]["complete"]
            s2, e2 = sub.iloc[j]["start"], sub.iloc[j]["complete"]
            if pd.notna(s1) and pd.notna(e1) and pd.notna(s2) and pd.notna(e2):
                pairs += 1
                if max(s1, s2) < min(e1, e2):
                    overlaps += 1

    overlap_rate = overlaps / pairs if pairs else np.nan

    start_counts = sub["start"].value_counts(dropna=True)
    complete_counts = sub["complete"].value_counts(dropna=True)
    max_start_eq = int(start_counts.max()) if len(start_counts) else 0
    max_complete_eq = int(complete_counts.max()) if len(complete_counts) else 0

    lag_sec = (sub["recorded_at"] - sub["complete"]).dt.total_seconds()

    ts = pd.concat([sub["start"], sub["complete"]]).dropna().sort_values().drop_duplicates()
    gaps = ts.diff().dt.total_seconds().dropna()
    min_gap = gaps[gaps > 0].min() if (gaps > 0).any() else np.nan

    valid = sub[
        sub["queue_arrival"].notna()
        & sub["start"].notna()
        & (sub["start"] >= sub["queue_arrival"])
    ]
    invalid_start_before_queue = int(n - len(valid))

    events = []
    for _, r in valid.iterrows():
        events.append((r["queue_arrival"], 1))
        events.append((r["start"], -1))
    events.sort(key=lambda x: (x[0], -x[1]))  # arrival before start at same timestamp

    q = 0
    maxq = 0
    for _, delta in events:
        q += delta
        maxq = max(maxq, q)

    wait_min = (sub["start"] - sub["queue_arrival"]).dt.total_seconds() / 60.0

    return pd.Series({
        "cases": n,
        "resource": sub["resource"].iloc[0] if n else None,
        "precision_sec": sub["precision_sec"].iloc[0] if n else np.nan,
        "overlap_rate": overlap_rate,
        "max_start_eq": max_start_eq,
        "max_complete_eq": max_complete_eq,

        "median_record_lag_sec": lag_sec.median(),

# 5. Robustness and alternative explanations

**If resource IDs are trusted as true single resources.** G1 becomes impossible as four simultaneous item-level operations unless RBT-7 is modelled as a batch-capacity machine. G2, G3, and G6 become strong evidence for start/end batching or bulk logging because T-B, T-C, and T-F appear to be single resources. G5 becomes physically impossible because one `analyst_pool` resource would have four overlapping root-cause analyses and summed duration exceeding elapsed time. G7 becomes either a true five-item simultaneous batch on T-G or, more plausibly, timestamp coarsening. G8 remains sequential after a downtime gap.

**If resource IDs are treated as potentially shared.** G5 changes from “one impossible resource” to “up to three analysts, with ambiguous attribution and possible multitasking.” G1, G2, G3, G6, G7, and G8 have no stated shared-account caveat, so they remain less affected. However, any station ID such as T-B or T-C could in principle be a shared terminal or account; without badge identity, that cannot be fully excluded.

**If timestamps are exact.** G1 looks like a real simultaneous four-item batch; G2 looks like a common begin followed by serial completion; G3 looks like common completion/bulk submission; G4 looks like FIFO sequential processing; G5 looks like heavy concurrency; G6 looks like zero-duration bulk close; G7 looks like a five-item simultaneous batch; G8 looks like downtime followed by sequential processing.

**If timestamps are interval-censored by stated precision.** G7 becomes largely uninterpretable at item level because a 15-minute precision bucket can hide simultaneous, sequential, or partially overlapping work. G2, G3, G5, and G6 have 1-minute precision, so equalities and overlaps within the same minute are weaker evidence. G1, G4, and G8 have 1-second precision, so their equalities, adjacencies, and overlaps are relatively strong, though not proof of physical execution.

At least three cases where the same temporal pattern supports multiple physical explanations:

1. **G1 identical start/end:** genuine simultaneous batch on a four-item fixture, versus common start/end logging of a fixture cycle, versus PLC event compression.
2. **G2 common start plus staggered completions:** start batching/common setup, versus sequential batching after a group-begin button, versus one inspector using shared completion buttons.
3. **G3 staggered starts plus common completion:** end batching/bulk submission, versus timestamp coarsening at 1-minute precision, versus end-of-folder administrative completion.
4. **G4 adjacent non-overlapping intervals:** deliberate sequential batching, versus ordinary FIFO single-server queue, versus recovery from an unrecorded upstream capacity loss before 12:05.
5. **G5 overlapping analyst-pool intervals:** genuine concurrent work by multiple analysts, versus one analyst multitasking, versus shared-account artifact, versus 1-minute timestamp coarsening.
6. **G7 identical 15-minute intervals:** real manual-measure batch, versus legacy MES quarter-hour rounding, versus both.
7. **G8 queue then sequential processing:** queue accumulation after safety-check capacity loss, versus ordinary FIFO queue, versus sequential batching after restart.

# 6. Data-collection redesign

Prioritized recommendations:

1. **Separate lifecycle semantics.** Capture `queue_arrival`, `available_for_work`, `process_start`, `process_end`, `form_submit`, and `recorded_at` as distinct fields. Never reuse a submission timestamp as both start and complete.
2. **Resource and badge identity.** Replace shared logins with badge/session IDs. Store both worker ID and workstation/account ID. For `analyst_pool`, log which analyst performed each case and whether multitasking occurred.
3. **Explicit batch/group identifiers.** Add `batch_id`, `group_id`, `fixture_id`, `parent_case_id`, and `batch_role` fields. Distinguish physical batch, setup batch, completion batch, and administrative bulk submission.
4. **Clock synchronisation.** Use NTP or equivalent across PLC, tablet, desktop, VDI, safety, and legacy MES sources. Record clock offset and uncertainty. For T-H, align safety-check and repair-queue clocks before causal analysis.
5. **Timestamp precision and accuracy metadata.** Store raw timestamps plus documented precision, rounding rule, and estimated accuracy. Avoid rounding at source when possible. Keep both raw and rounded values.
6. **Workstation capacity and calendars.** Record resource capacity, fixture capacity, parallel slots, shift calendar, breaks, maintenance, safety checks, and other downtime. Capacity must be known to interpret overlapping intervals.
7. **Pause/resume and interruption events.** Log pauses, resumes, rework, waiting for material, waiting for approval, and preemption. These are needed to distinguish multitasking from elapsed service time.
8. **Bulk-submission flags.** When a form closes many cases at once, record a `bulk_submission_id` and do not treat the submission timestamp as physical completion.
9. **Validation rules.** Enforce `queue_arrival <= start <= complete` unless a documented preemption explains otherwise. Flag cases where start precedes queue arrival, where start=complete, or where batch size exceeds workstation capacity.

# 7. Final adjudication

**High-confidence interpretations.** G6 can be interpreted with high confidence as an administrative bulk-close/end-batching pattern; its start/complete fields should not be used for service-time or queue-time analysis. G1 can be interpreted with high confidence as a batch compatible with RBT-7 capacity, though item-level execution order remains unknown. G4 can be interpreted with high confidence as sequential single-resource processing with accurate scanner timestamps. G8 can be interpreted with high confidence as downtime/capacity-loss queue accumulation, subject to clock-offset validation.

**Should be excluded or interval-censored.** G6 should be excluded from service-time, utilisation, and queue-waiting analyses unless actual close times are recovered. G7 should be interval-censored because 15-minute rounding makes exact starts, completes, and overlaps unreliable; it should not be used for precise waiting or service-time conclusions. G5 should be interval-censored at the resource-attribution level: durations may be usable, but per-worker utilisation and bottleneck attribution require badge identity. G2 and G3 should be interval-censored for item-level service times until common start or common completion semantics are verified.

**Require operational validation before performance conclusions.** G1 needs fixture/batch IDs and item loading order. G2 needs validation of what “begin group” actually starts. G3 needs separation of review completion from form submission. G5 needs badge-level analyst identity and multitasking rules. G7 needs raw clocks and the legacy MES rounding rule. G8 needs clock alignment between the safety system and repair queue. Until those validations are done, aggregate throughput may be defensible, but waiting time, service time, utilisation, and bottleneck conclusions should be treated as provisional.
