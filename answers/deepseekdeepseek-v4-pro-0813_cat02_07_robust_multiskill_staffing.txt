# 6. Secondary effects and implementation risks

- Gaming of estimates: if dispatch uses expected service times, staff may pad estimates; service time ranges should be updated by process mining, not self-reported. Need independent event log.

- Coordination overhead: parallel branches add 8 min; too much parallelization can create handover/setup and coordination burden; threshold.

- Fairness: resource utilization fair; avoid always assigning to fastest resource; use load balancing; but fairness can increase handover/setup.
- Human interpretability: dispatch rules must be simple score, not black-box; display score components in dashboard. Operators can override with reason code.
- Cross-skill setup churn: batching; not switching too often.

# 1. Assumptions, objectives, and decision variables

## Service-time and demand assumptions

- Service times are mixtures of two uniform distributions: with probability `p` the “complex-tail” interval is used; otherwise the “ordinary” interval is used. Since no mode is given, I use the interval midpoint as the expectation for each component.
  - Example: Mechanical expected base service = `(1-0.15) * ((18+28)/2) + 0.15 * ((35+55)/2) = 26.3` minutes.
- Resource multipliers apply **after** the base service draw:
  - `actual_service = base_draw * resource_multiplier`.
- Arrival blocks are used as expected arrival counts. For load approximations I treat demand as deterministic in expectation; for any stochastic simulation, block counts would be Poisson or similar.
- Priority mix is assumed independent of case type unless a policy deliberately changes that assumption.
- Handover/data-entry delay is `+7` minutes whenever a case changes resource between Intake, diagnostic work, or Validation.
- A further `+5` minutes is added for a mechanical-to-electrical/software handover unless the same cross-skilled resource retains the case.
- Resource skill-family switch between consecutive diagnostic cases adds `+5` setup minutes.
- Parallel ME/ES branches add `+8` minutes coordination before Validation.
- Preemption is allowed for P1 over lower-priority diagnostic activities only. If preempted, the interrupted lower-priority case incurs a restart penalty of `10%` of its remaining active service time. A case is preempted at most once.
- Overtime is limited to `30` minutes per resource.
- Planned utilization above `90%` for any individual resource is treated as unfair/fragile in the base scenario.

## How ME/ES parallelism is decided

For load accounting, an ME case consumes mechanical and electrical service work; an ES case consumes electrical and software service work. Whether the branches run in parallel or sequentially does not remove the total service volume:

- Parallel:
  - Critical path shortens for the case.
  - Adds `8` minutes coordination before Validation.
  - Consumes two resources at the same time.
- Sequential:
  - Avoids the `8` minutes coordination.
  - Lengthens the case critical path: `M + E` or `E + S`.
  - Can be done by one cross-skilled resource.

I assume a policy may choose parallel when two qualified resources are likely to be available and the expected parallel critical path plus coordination is shorter than sequential execution. Otherwise, sequential is preferred.

## Objectives

Two objective formulations are used.

### Objective 1: SLA / tail-risk objective

Minimize risk-weighted SLA misses:

\[
\text{risk} = 0.5 \cdot P1\_miss + 0.3 \cdot P2\_miss + 0.2 \cdot P3\_miss
\]

where `P1_miss`, `P2_miss`, and `P3_miss` are the fractions of cases missing their priority target. P1 misses are weighted most heavily.

### Objective 2: Fairness / robustness objective

Lexicographic or penalized objective:

1. Maintain P1 SLA above `90%` in base and above a degraded threshold in stress scenarios.
2. Maximize P2 SLA as far as practical.
3. Keep `max_resource_utilization` below `90%` in base when possible.
4. Keep utilization fairness spread below `20` percentage points where feasible.
5. Keep handover/setup burden below about `20` minutes per case on average.

Robustness is defined as: the policy should not collapse a single skill queue, should degrade gracefully under U1–U5, and should protect P1 work even when aggregate capacity is insufficient.

# 3. Candidate policies

## Policy A: Strict specialization with fixed queues

Operational rules:

- Intake: any available resource.
- Mechanical queue: primarily Ada and Ben; Deepa is overflow only if mechanical queue exceeds `60` minutes or P1/P2 SLA is at risk.
- Electrical queue: primarily Chen and Deepa; Emil is overflow only for P1/P2 if electrical queue exceeds `45` minutes.
- Software queue: primarily Chen and Emil; Farah is overflow only for P1/P2 before `12:00` if software queue exceeds `30` minutes.
- Validation: any available resource, but primary Validation resources are Ben, Deepa, and Emil.
- Dispatch score:
  - priority class first: `P1 > P2 > P3`;
  - then FIFO arrival time.
- Preemption:
  - P1 may preempt a lower-priority diagnostic activity.
  - Maximum one preemption per case.
  - Restart penalty modeled as `0.1 * remaining_service` on the interrupted activity.
- ME/ES:
  - Parallel only if both required primary resources are free.
  - Otherwise sequential on a cross-skilled resource: Ada or Deepa for ME; Chen, Emil, or Farah for ES.
- Handover minimization:
  - Weak. Fixed queues often produce an Intake resource, a diagnostic specialist, and a different Validation resource.
  - Handover burden is high.

## Policy B: Full pooling to any qualified resource

Operational rules:

- Eligibility: any resource with a multiplier for the required activity may perform it.
- Dispatch score:
  - `P1 > P2 > P3`;
  - within the same priority, use shortest expected remaining processing time using the specific resource’s multiplier;
  - tie-break: choose the qualified resource with the lowest current scheduled workload.
- Preemption:
  - P1 may preempt lower-priority diagnostic work.
  - Same restart-penalty rule as Policy A.
- ME/ES:
  - Parallelize when `max(M, E) + 8 < M + E` for ME, or `max(E, S) + 8 < E + S` for ES, and two qualified resources are available.
  - Otherwise sequential on one cross-skilled resource.
- Handover minimization:
  - Stronger than strict specialization: if the same resource is qualified for the next activity and will be available within `15` minutes, retain the case.
- Fairness:
  - Dispatch favors lower loaded qualified resources to balance utilization.
- Risk:
  - No P1 capacity reservation. If many P2/P3 cases occupy cross-skilled resources, P1 may wait or require preemption.

## Policy C: Hybrid reserved P1 capacity with controlled cross-skill overflow

Operational rules:

- Primary resources:
  - Mechanical: Ada, Ben.
  - Electrical: Chen, Deepa.
  - Software: Chen, Emil.
  - Validation: Ben, Deepa, Emil with others as eligible overflow.
- P1 reservation:
  - Reserve about `20%` of primary diagnostic capacity for P1/P2 in the next `120` minutes.
  - P1 cases may preempt P2/P3 diagnostic work.
  - P1 cases bypass ordinary FIFO and are assigned to the earliest available qualified primary resource.
- Overflow triggers:
  - Electrical queue predicted to exceed `45` minutes for P1/P2, or `120` minutes for P3: allow Ada and/or Emil on Electrical.
  - Software queue predicted to exceed `60` minutes for P1/P2: allow Farah before `12:00` or Chen if available.
  - Mechanical queue predicted to exceed `60` minutes: allow Deepa and/or Farah.
  - After `16:00`, lower overflow thresholds to `30` minutes because capacity is scarce.
- Dispatch score:
  - `P1`: earliest available qualified primary resource, with preemption if needed.
  - `P2`: lexicographic `priority`, then expected completion time, then resource load.
  - `P3`: only if P1/P2 queues are not at risk; oldest P3 gets a fairness increment.
- P3 starvation guard:
  - If any P3 case has waited more than `4` hours and P1 SLA is not at risk, allocate up to `10%` of diagnostic capacity to P3.
- ME/ES:
  - Parallel if both required skills have at least two qualified resources and expected parallel critical path plus coordination is shorter than sequential.
  - Else sequential on one cross-skilled resource.
  - After `16:00`, default to sequential unless the case is P1.
- Handover minimization:
  - Same-resource retention if qualified and available within `15` minutes.
  - Avoid mechanical-to-electrical/software handover penalty where possible by using cross-skilled resources.
- Setup control:
  - Batch same-skill-family work for a resource where possible.
  - When a resource switches skill family between consecutive diagnostic cases, record the `5`-minute setup.

# 5. Robust recommendation

## Primary recommendation

**Policy C: hybrid reserved P1 capacity with controlled cross-skill overflow** is the recommended primary operating policy.

Why it is better under the stated objectives:

- It explicitly reserves P1 capacity, unlike full pooling.
- It uses strict specialization where efficient, but does not allow fixed queues to become brittle under shocks.
- It activates overflow only on thresholds, limiting excessive setup/handover and slower-resource use.
- It controls ME/ES parallelization so after `16:00` scarce resources are not wasted on coordination.
- It includes a P3 starvation guard.

## Fallback mode

Trigger fallback when:

- Predicted P1 queue wait exceeds `45` minutes for `30` consecutive minutes, or
- Rolling P1 SLA attainment falls below `90%`, or
- U5-type combined stress is declared.

Fallback rules:

- Stop starting new P3 diagnostics.
- Allow all qualified resources to work on P1/P2.
- Parallelize ME/ES only for P1/P2 if it shortens critical path.
- Use overtime first for P1/P2.
- If P1 wait still exceeds `60` minutes, stop starting new P2 diagnostics unless there is no waiting P1.

Return to normal mode when:

- No threshold has been breached for `60` minutes, and
- Projected load/capacity ratio is below about `1.05`.

## Cases where another policy would be preferable

- **Strict specialization** can be preferable when demand is stable, setup costs are high, and accountability/ownership matter more than queue balancing. It is not robust to U1, U2, U3, or U5.
- **Full pooling** can be preferable if cross-training is deep, speed multipliers are close to `1.0`, and setup/handover penalties are low. In this dataset, full pooling is useful but risks P1 because it has no reservation.

## Capacity caveat

The hybrid policy cannot fix the base aggregate overload. It can only allocate the overload more safely. A sustainable solution would require:

- More software and electrical capacity, especially after `16:00`;
- Cross-training a second resource on Software at close to `1.0` speed;
- Demand smoothing from afternoon/evening to earlier blocks;
- Reduced complex-tail work through preventive diagnostics.

---

# 6. Secondary effects and implementation risks

## Gaming of estimates

If dispatch uses estimated service times, staff may inflate expected durations. Use process-mining actual service durations rather than self-reported estimates for policy calibration.

## Starvation of P3 work

P1/P2 priority plus P1 reservation can starve P3. Use explicit P3 aging rules and reserve a small fraction of capacity for oldest P3 cases.

## Skill erosion

Full pooling can reduce specialization and make slower multipliers the norm. Rotate staff through primary and overflow roles, and monitor service-time multipliers.

## Excessive preemption

P1 preemption can create restart penalties and whipsaw lower-priority work. Monitor preemption rate per day and per resource. If preemption is frequent, add more P1 reserved capacity.

## Coordination overhead

Parallel ME/ES adds `8` minutes coordination and consumes two resources. If parallelization is used too aggressively, it increases handover and coordination burden. Use critical-path thresholds, not a default preference for parallel.

## New bottleneck at Validation

If diagnostics are accelerated, Validation can become the next bottleneck. Monitor Validation queue and service time separately.

## Fairness

A fastest-resource-first dispatch rule can overload Emil, Deepa, or Chen while others have idle time. Use utilization-aware tie-breaking and fairness caps. Fairness can increase handover/setup, so the hybrid policy trades these off with thresholds.

## Human interpretability

Operators need to see why a case is assigned to a resource. The dispatch score should be explainable:

- priority class;
- waiting time;
- expected remaining processing time;
- resource load;
- overflow trigger.

Overrides should be allowed with a reason code.

def mid(a, b):
    return (a + b) / 2


def exp_service(activity, scenario):
    o_min, o_max, c_min, c_max, p = SERVICE[activity]
    if scenario == "U4" and activity in DIAG:
        p = min(1.0, p * 2)
    return (1 - p) * mid(o_min, o_max) + p * mid(c_min, c_max)


def scenario_blocks(scenario):
    blocks = [dict(b) for b in BLOCKS]

    if scenario in ("U1", "U5"):
        for b in blocks:
            if b["start"] < 240:
                b["arr"] *= 1.7
                b["P1"] += 0.08
                old_remaining = b["P2"] + b["P3"]
                remaining = 1 - b["P1"]
                b["P2"] = remaining * b["P2"] / old_remaining
                b["P3"] = remaining - b["P2"]

    if scenario == "U2":
        for b in blocks:
            if 240 <= b["start"] < 480:
                b["E"] *= 2
                b["ES"] *= 2
                total = b["M"] + b["E"] + b["S"] + b["ME"] + b["ES"]
                for t in ["M", "E", "S", "ME", "ES"]:
                    b[t] /= total

    return blocks


def available_minutes(resource, start, end, scenario):
    if scenario in ("U3", "U5") and resource == "Chen":
        return 0.0
    shift = SKILLS[resource]["shift"]
    if end <= shift[0] or start >= shift[1]:
        return 0.0
    s = max(start, shift[0])
    e = min(end, shift[1])
    minutes = e - s
    br = SKILLS[resource].get("break")
    if br:
        bs, be = br
        overlap = max(0, min(e, be) - max(s, bs))
        minutes -= overlap
    return max(0.0, minutes)


def total_resource_minutes(scenario):
    total = 0.0
    for res in SKILLS:
        for b in BLOCKS:
            total += available_minutes(res, b["start"], b["end"], scenario)
    return total


def block_workload(b, scenario):
    arr = b["arr"]
    counts = {t: arr * b[t] for t in ["M", "E", "S", "ME", "ES"]}
    w = {
        "Intake": arr * exp_service("Intake", scenario),
        "Mechanical": (counts["M"] + counts["ME"]) * exp_service("Mechanical", scenario),
        "Electrical": (counts["E"] + counts["ME"] + counts["ES"]) * exp_service("Electrical", scenario),
        "Software": (counts["S"] + counts["ES"]) * exp_service("Software", scenario),
        "Validation": arr * exp_service("Validation", scenario),
        "Coordination": (counts["ME"] + counts["ES"]) * 8.0,
    }
    return w


def workload(scenario):
    w = {"Intake": 0, "Mechanical": 0, "Electrical": 0, "Software": 0, "Validation": 0, "Coordination": 0}
    for b in scenario_blocks(scenario):
        bw = block_workload(b, scenario)
        for k in w:
            w[k] += bw[k]
    return w


def total_arrivals(scenario):
    return sum(b["arr"] for b in scenario_blocks(scenario))


def policy_skill_capacity(policy, skill, scenario):
    if policy == "strict":
        resources = PRIMARY[skill]
        overflow = []
    elif policy == "full":
        resources = [r for r in SKILLS if SKILLS[r].get(skill) is not None]
        overflow = []
    elif policy == "hybrid":
        resources = PRIMARY[skill]
        overflow = OVERFLOW[skill]
    else:
        resources, overflow = PRIMARY[skill], []

    cap = 0.0
    for res in set(resources + overflow):
        mult = SKILLS[res].get(skill)
        if mult is None:
            continue
        for b in BLOCKS:
            avail = available_minutes(res, b["start"], b["end"], scenario)
            if avail <= 0:
                continue
            if res in overflow and policy == "hybrid":
                avail *= 0.5  # controlled overflow: only half of overflow capacity assumed usable
            cap += avail / mult
    return cap


def peak_block_rho(scenario, capacity_factor):
    peaks = []
    for b in scenario_blocks(scenario):
        load = sum(block_workload(b, scenario).values())
        cap = sum(available_minutes(r, b["start"], b["end"], scenario) for r in SKILLS) * capacity_factor
        peaks.append(load / max(1.0, cap))
    return max(peaks)


def clip(x, lo, hi):
    return max(lo, min(hi, x))


def policy_metrics(policy, scenario):
    p = POLICY_PARAMS[policy]
    w = workload(scenario)
    arr = total_arrivals(scenario)

    base_load = sum(w.values())
    burden = HANDOVER_SETUP_BURDEN[policy] * arr
    effective_load = base_load + burden

    base_cap = total_resource_minutes(scenario)
    overtime_resources = 5 if scenario in ("U3", "U5") else 6
    cap = base_cap + 30 * overtime_resources
    if scenario == "U5":
        # 30-minute Intake IT outage: conservative aggregate capacity loss placeholder
        cap -= 30

    cap *= p["capacity_factor"]
    rho = effective_load / max(1.0, cap)
    peak = peak_block_rho(scenario, p["capacity_factor"])

    skill_utils = {}
    for skill in ["Mechanical", "Electrical", "Software", "Validation", "Intake"]:
        skill_utils[skill] = w.get(skill, 0) / max(1.0, policy_skill_capacity(policy, skill, scenario))
    max_skill_util = max(skill_utils.values()) * 100
    fairness = (max(skill_utils.values()) - min(skill_utils.values())) * 100

    avg_service = effective_load / max(1.0, arr)

    # Transparent heuristic delay model; this is a scaffold, not a validated DES.
    if rho < 0.90:
        wait = avg_service * (rho / (1 - rho))
    elif rho < 0.95:
        wait = avg_service * 18.0
    else:
        wait = avg_service * 18.0 + avg_service * 8.0 * (rho - 0.95)

    wait += 30.0 * max(0.0, peak - 1.0)
    mean_delay_h = (avg_service + wait) / 60.0
    p90_h = mean_delay_h * 1.6 + 0.5

    p1_sla = clip(0.95 - 0.35 * max(0.0, rho - 1.0) - 0.08 * max(0.0, peak - 1.15) + p["p1_shift"], 0.30, 0.97)
    p2_sla = clip(0.72 - 0.55 * max(0.0, rho - 0.95) - 0.10 * max(0.0, peak - 1.10) + p["p2_shift"], 0.05, 0.80)

    return {
        "scenario": scenario,
        "policy": policy,
        "mean_delay_h": mean_delay_h,
        "p90_delay_h": p90_h,
        "P1_SLA_pct": p1_sla * 100,
        "P2_SLA_pct": p2_sla * 100,
        "max_skill_util_pct": max_skill_util,
        "fairness_spread_pp": fairness,
        "rho": rho,
    }


def sample_service(activity, scenario):
    o_min, o_max, c_min, c_max, p = SERVICE[activity]
    if scenario == "U4" and activity in DIAG:
        p = min(1.0, p * 2)
    if random.random() < p:
        return random.uniform(c_min, c_max)
    return random.uniform(o_min, o_max)


def assign_resource_for_activity(activity, typ, policy):
    if policy == "strict":
        mapping = {"Intake": "Ada", "Mechanical": "Ada", "Electrical": "Chen", "Software": "Emil", "Validation": "Ben"}
    elif policy == "full":
        mapping = {"Intake": "Deepa", "Mechanical": "Ben", "Electrical": "Deepa", "Software": "Emil", "Validation": "Deepa"}
    else:
        mapping = {"Intake": "Ada", "Mechanical": "Ada", "Electrical": "Deepa", "Software": "Emil", "Validation": "Ben"}
    return mapping.get(activity, "Ada")


def generate_event_log(scenario="base", policy="hybrid"):
    random.seed(42)
    events = []
    case_counter = 0
    blocks = scenario_blocks(scenario)

    for b in blocks:
        n = int(round(b["arr"]))
        for _ in range(n):
            case_counter += 1
            case_id = f"case-{case_counter}"
            prio = random.choices(["P1", "P2", "P3"], weights=[b["P1"], b["P2"], b["P3"]], k=1)[0]
            typ = random.choices(["M", "E", "S", "ME", "ES"], weights=[b["M"], b["E"], b["S"], b["ME"], b["ES"]], k=1)[0]

            current = DAY_START + timedelta(minutes=b["start"] + random.uniform(0, 120))

            acts = ["Intake"]
            if typ == "M":
                acts.append("Mechanical")
            elif typ == "E":
                acts.append("Electrical")
            elif typ == "S":
                acts.append("Software")
            elif typ == "ME":
                acts += ["Mechanical", "Electrical"]  # sequential scaffold
            elif typ == "ES":
                acts += ["Electrical", "Software"]  # sequential scaffold
            acts.append("Validation")

            prev_res = None
            for act in acts:
                res = assign_resource_for_activity(act, typ, policy)
                mult = SKILLS[res].get(act)
                if mult is None:
                    mult = 1.0
                dur = sample_service(act, scenario) * mult
                start = current
                end = start + timedelta(minutes=dur)

                events.append({
                    "case:concept:name": case_id,
                    "concept:name": act,
                    "queue_entry_timestamp": start,
                    "start_timestamp": start,
                    "time:timestamp": end,
                    "org:resource": res,
                    "priority": prio,
                    "case_type": typ,
                    "skill_used": act,
                    "policy": policy,
                    "scenario": scenario,
                    "parallel_branch": typ in ("ME", "ES"),
                    "actual_service_min": dur,
                    "handover_min": 7 if prev_res and prev_res != res else 0,
                    "setup_min": 0,  # simplified scaffold
                })

                if prev_res and prev_res != res:
                    current = end + timedelta(minutes=7)
                else:
                    current = end
                prev_res = res

    return pd.DataFrame(events)

# 9. Limits and validation plan

## What cannot be concluded from expected arrivals and service ranges alone

- Exact queue lengths, p90 delays, and SLA attainment require a stochastic discrete-event simulation.
- The service-time intervals do not specify a distribution; expected midpoint calculations can hide heavy-tail behavior.
- The offered-load analysis assumes independence and omits sequence-dependent setup, preemption timing, and break effects at fine granularity.
- The table values in Section 4 are directional ranges, not validated simulation results.

## Pilot / backtest design

A safe validation plan should:

1. Run a **shadow mode** for 2-4 weeks:
   - Keep the current operating policy for actual work.
   - Compute what the hybrid policy would have assigned.
   - Compare queue indicators without disrupting real cases.
2. Run a **small pilot** in a lower-risk block:
   - Use hybrid policy only for P2/P3 cases first.
   - Keep P1 cases on the existing best-priority path.
3. Use a **staged rollout**:
   - Phase 1: activate hybrid overflow triggers only.
   - Phase 2: activate P1 reservation and preemption rules.
   - Phase 3: activate ME/ES parallelization thresholds.
4. Backtest against U1-U5 scenarios:
   - Replay historical cases under synthetic demand shocks.
   - Compare SLA attainment, utilization, and fairness.
5. Monitor safety metrics:
   - P1 SLA below `90%` triggers immediate fallback.
   - Preemption rate over `15%` of P2/P3 diagnostic starts triggers review.
   - Any resource utilization over `95%` for more than `60` minutes triggers workload review.

The key operational conclusion is not that hybrid removes overload; it is that hybrid best protects P1 and degrades more fairly under uncertainty than strict specialization or complete pooling.
