## 1. Target definition

### Primary target: 90-day default risk among activated accounts

- **Unit of analysis:** one credit application/activated account, after resolving known cross-platform duplicate identities where linkage is available.
- **Prediction time:** a fixed, operationally identifiable early prefix landmark, primarily the timestamp of the **third canonical event**—normally Credit Review—provided it occurs before acceptance, rejection, withdrawal, transfer, activation, or default. A secondary deployment view uses an elapsed-time landmark 24 hours after Application Started.
- **Outcome origin:** Account Activated.
- **Horizon:** default within 90 days after activation.
- **Population:** applications observed at the prediction landmark that subsequently activate under the historical lending policy.
- **Outcome:** `default_90d = 1` if default occurs within 90 days of activation; `0` only when verified default-free follow-up through day 90 is available.
- **Estimand:**  
  \[
  P(D\leq 90\mid X_{\text{prefix}}, A=1,\text{ historical policy/regime})
  \]
  where \(A=1\) denotes eventual activation.

This is a **conditional, policy-dependent prognosis**, not default risk for every applicant. It is defensible because default is well-defined after credit exposure, aligns with the stored outcome, and does not invent outcomes for rejected, withdrawn, transferred, or open applications. Its limitation is selection through activation: it is not directly suitable for comparing applicants independently of the approval policy.

The first-few-events model may score all applications operationally, but its probability is interpretable only for cases that would activate under a sufficiently similar policy. Scores for cases outside that support must be flagged as extrapolations, not presented as observed all-applicant default probabilities.

### Credible alternative: all-application multi-state prediction

At the same prefix landmark, predict probabilities by a fixed application-time horizon, for example:

1. activated and default within 90 days of activation;
2. activated and verified non-default through day 90;
3. rejected;
4. withdrawn;
5. transferred/unlinked;
6. still open or not outcome-mature.

This answers a **process-outcome** question—“what is likely to happen to this application under the current process?”—rather than pure credit risk. Rejection and withdrawal are competing process outcomes, not non-defaults. Because “activated and non-default by 90 days” can mature well after the application horizon, this is naturally implemented as a multi-state/competing-risk model with explicit state transitions and censoring.

Another valid formulation is **time to default from activation**, with verified non-default accounts right-censored at their last reliable follow-up. A policy-specific counterfactual,
\[
P(D^{A=1}\leq90\mid X),
\]
would ask what would happen if every applicant were activated. It requires positivity, consistency, exchangeability/no unmeasured confounding, and outcome ascertainment assumptions that these observational data cannot establish.

## 2. Cohort construction

### Inclusion and as-of rules

1. Start from all applications with Application Started between 2024-01-01 and 2025-12-31.
2. Use only rows with event timestamp at or before both:
   - the analysis cutoff; and
   - the row’s `data_extract_time`.
3. Canonicalize activity names using a versioned migration map. Deduplicate migration duplicates using case/linkage identity, canonical activity, timestamp, resource, and source-system information.
4. Link transferred identifiers only where the linkage table supports it. Preserve a linkage-quality flag; do not probabilistically merge unsupported cases in the primary analysis.
5. Build features solely from events/values recorded by the prediction timestamp.
6. For the primary target, require:
   - a valid early landmark before terminal decision or activation;
   - observed activation;
   - reliable follow-up through activation + 90 days;
   - label ingestion by the analysis cutoff.
7. A positive label requires a valid default outcome by day 90. A negative requires affirmative follow-up through day 90, not merely a missing default event.
8. Cases activated too recently, or with a label still within its expected 7–35-day delivery period, are not training negatives.
9. For temporal evaluation, re-run these rules at each historical backtest cutoff rather than using labels that became available later.

The supplied categories exactly partition the 48,000 applications. The event reconstruction should reconcile to them; mismatches become a data-quality exception.

| Cohort state at 2026-02-15 | Count | Primary-target role | Statistical status |
|---|---:|---|---|
| Activated, mature, verified non-default | 18,900 | Eligible labeled outcome if landmark valid | Label 0 |
| Activated, mature, default within 90 days | 2,700 | Eligible labeled outcome if landmark valid | Label 1 |
| Rejected | 9,100 | Not a primary-target negative | Competing process outcome; default under activation undefined |
| Withdrawn | 5,700 | Not a primary-target negative | Competing process outcome |
| Transferred | 2,900 | Not a primary-target negative | Competing event and possible loss to follow-up; 60% linkable |
| Still open | 5,100 | Excluded from binary training at this cutoff | Right-censored application process |
| Activated, outcome/feed not mature | 3,600 | Excluded from binary training until mature | Delayed label and/or ordinary censoring |
| **Total** | **48,000** |  |  |

The 21,600 mature activated accounts are the maximum binary-label pool, not automatically the final analytic cohort. Landmark validity, duplicate resolution, reliable negative ascertainment, and permanent-feed checks can reduce it. Exclusions and counts must be reported.

## 3. Censoring and missing-label strategy

The mechanisms must not be conflated:

- **Ordinary right censoring:** an activated account has not yet accumulated 90 days of observable follow-up by the cutoff, or an application remains open. Its outcome may occur later.
- **Delayed labels:** the 90-day window has ended, but the external feed may take another 7–35 days. Before arrival, missingness is administrative delay, not a negative outcome.
- **Selection through activation:** rejection, withdrawal, and some transfers prevent observation—and may prevent the very definition—of default under the observed exposure. This is not ordinary censoring.
- **Transfer:** transfer is a competing application-state transition. It can additionally induce missing follow-up when the partner identifier cannot be linked.
- **Permanently missing feeds:** especially among partner-originated activated accounts, an outcome can remain unobserved after the normal delay window. This is potentially informative missingness, not routine administrative censoring.

### Primary strategy

Use a **landmark binary model among historically activated accounts with mature, reliable 90-day ascertainment**. At each analysis cutoff:

1. require activation + 90 days to have elapsed;
2. allow a conservative 35-day feed-lag grace period for inclusion as a verified negative;
3. allow positives once validly observed, but use the same fixed as-of rules during evaluation;
4. exclude unresolved or permanently missing feeds from the complete-case primary fit;
5. model/report the probability of activation and label observability from prefix features, regime, channel, source, region, and transfer status;
6. report overlap and performance stratified by these probabilities.

Inverse-probability weighting for outcome-feed observability can be used when overlap is adequate, but it does **not** identify default risk for rejected applicants.

### Sensitivity analyses

1. **Feed-missingness sensitivity:** compare complete-case estimates with inverse-probability-of-observation weighting and pattern-mixture/tipping-point analyses. For unresolved partner outcomes, vary their default rate from the observed comparable rate to materially worse rates.
2. **Survival analysis:** model time from activation to default, administratively censoring at reliable last follow-up. Use IPCW metrics if censoring depends on measured variables.
3. **Competing-state analysis:** model rejection, withdrawal, transfer, activation, and open/censoring from application start. This assesses process outcomes without calling rejection non-default.
4. **Transfer bounds:** analyze known linked transfers, unlinked transfers as loss to follow-up, and extreme-case bounds. Apply linkage-probability weighting only if linkage missingness is plausibly explained by observed data.
5. **Activation-selection diagnostics:** estimate activation propensity and restrict reporting to regions of common support. A counterfactual all-activated analysis, if shown, must be explicitly exploratory and accompanied by unmeasured-confounding sensitivity analysis.

### Assumptions and identifiability

- **Testable/descriptive:** observed feed delays; maturity arithmetic; event completeness; duplicate rates; linkage rates; covariate balance; positivity in observed covariates; calibration drift; whether known outcomes appear after their `label_available_at`.
- **Partially testable:** conditional independent censoring, missing-at-random feeds, and linkage-at-random. Their implications can be assessed using observed predictors and resolved cases but not proved.
- **Fundamentally untestable here:** outcomes under activation for rejected/withdrawn applicants, no unmeasured confounding of activation and default, outcomes for permanently unlinked transfers, and the stability of outcomes under a new decision policy.

## 4. Prefix extraction

All prefix construction is performed independently at each historical cutoff after sorting by canonical timestamp and a deterministic tie-breaker. Prefix rows must satisfy:

\[
\text{event time}\leq\text{prediction time}\leq\text{as-of cutoff}.
\]

### Fixed event-count prefixes

Create \(k=1,2,3,5\) event prefixes with `pm4py.get_prefixes_from_log`. The principal landmark is \(k=3\). Each derived prefix is assigned an identifier distinct from the original case ID so that several prefixes from one case cannot cross train/test boundaries. Stop a prefix before terminal/decision events if the intended use is pre-decision warning.

Cases with fewer than \(k\) observed events are not padded with future events. They are either:

- scored by a separate “up-to-\(k\)” model with prefix length/missing-position indicators; or
- excluded from the exact-\(k\) analysis and reported explicitly.

### Elapsed-time prefixes

For landmarks such as 6, 24, or 48 hours after Application Started, include only events with timestamps at or before start + landmark duration. Require that the case is still eligible and observed at that landmark; otherwise treat the prior state as a competing event rather than silently retaining it.

Repeated document loops remain in sequence. Features include loop count, Credit Review re-entry count, Request Documents  Credit Review transitions, elapsed loop duration, and time since the latest request. Do not collapse legitimate repetitions during duplicate removal.

Pre/post-migration names are mapped to canonical activities through an auditable dictionary. Raw activity name and source-system/version indicators are retained for data-quality and shift monitoring, but the predictive control-flow representation uses canonical names. Near-duplicate removal must be narrow enough not to erase real rapid repeats.

## 5. Process-aware features

### Static case attributes

Available at or before the landmark:

- channel, region, requested amount;
- application start hour/day/week/month;
- source system and partner-origin flag;
- policy regime: before/after 2025-07-01;
- migration regime: before/after 2025-10-15;
- transfer-linkage availability where known at prediction time.

Static fields must themselves be versioned if they can be corrected later.

### Prefix-derived features

- **Control flow:** canonical activity counts, latest activity, prefix length, direct-follow counts, variant/trace encoding, whether KYC and Credit Review have occurred.
- **Rework:** document request count, Credit Review visits, review re-entry count, repeated KYC, number and duration of loops.
- **Timing:** elapsed time since start, inter-event mean/max/last duration, time in current state, weekend/night indicators.
- **Resource/queue:** number of distinct resources, resource handoffs, latest team/resource, queue waiting time inferred from event transitions where semantics support it.
- **Risk information:** latest `risk_score` at or before the landmark, first score, within-prefix change, number of updates, and age of latest score.
- **Missingness/data quality:** absent expected event, timestamp ties, duplicate flag, source-system change, and missing prefix values.

A DFG and variant frequencies may be learned on **training prefixes only** for diagnostics or encoding. Full-case DFGs must not be used to create early-warning features.

### Features requiring historical reference data

- resource workload immediately before the landmark;
- rolling channel/region volumes and queue lengths;
- resource tenure/experience reconstructed as of event time;
- prior-30/90-day activity or variant frequency;
- historical approval/default rates, fitted out-of-fold and lagged;
- novelty relative to the training DFG.

These require point-in-time-correct reference tables. They must be computed using records available before the case landmark and re-fitted inside each temporal fold.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Post-decision field reveals acceptance and underwriting result | Use only for a model intentionally run after final decision | **Drop** from early model | Unavailable at first events and strongly encodes selection |
| `decision_reason` | Populated at/after Accept or Reject | Must have a recorded timestamp no later than a post-decision landmark | **Drop** | Leaks terminal decision and cannot support pre-decision warning |
| `collection_status` | Post-activation; may directly reveal default | Never use for pre-activation or 90-day default prediction | **Drop** | Direct target/post-outcome leakage |
| Future events, including Contract Signed, Account Activated, Collections Contact, Default Recorded | Reveal activation, follow-up, or outcome | Retain only rows with event time at or before prefix time | **Filter/drop from features** | Full traces would expose future states |
| `documents_total` | Nightly snapshot may include uploads later on the same day | Reconstruct from timestamped document events up to prefix; otherwise use prior completed-day snapshot | **Repair or drop** | Calendar-date equality is insufficient for point-in-time availability |
| Updated `risk_score` | Later revisions may encode downstream review | Use latest value whose event/valid-from time is at or before prefix; retain score age | **Repair/keep** | Early versions are valid; final warehouse value is not |
| Resource experience | Extraction-time value backfills future experience | Reconstruct tenure from HR effective-dated history as of event time | **Repair or drop** | Present value misstates historical information |
| `default_90d` | Direct target leakage when repeated on events | Use only in outcome construction after feature generation | **Drop from features** | Label must never enter the prefix table |
| `label_available_at` | Encodes outcome/feed process and future knowledge | Use only for as-of eligibility, censoring, and missingness audit | **Drop from predictors** | Availability often correlates with outcome/source |
| `data_extract_time` | Can reveal batch, maturity, or future corrections | Use as an as-of validity constraint and audit field | **Drop from model** | Operational metadata, not prefix information |
| Activation/terminal timestamps | Reveal eventual pathway | Use for cohort/outcome construction, not early predictors | **Drop from predictors** | Conditions on or reveals future selection |
| Full-case variant or DFG features | Include transitions after prediction | Derive variant/DFG from truncated training prefixes only | **Repair** | PM features are safe only after truncation |
| Transfer linkage table | Linkage may be resolved after prediction | Use for identity/outcome reconciliation; predictive use only if linkage status existed then | **Restricted** | Avoids future linkage information and duplicate outcomes |

## 7. Validation design

### Temporal backtesting

Use case start time—not random assignment—and rebuild labels/features at each vintage.

A practical scheme is:

1. **Development train:** 2024-01-01 to 2025-03-31.
2. **Validation:** 2025-04-01 to 2025-06-30, immediately before the policy change.
3. **Policy-shift test:** 2025-07-01 to 2025-10-14.
4. **Migration-era test:** 2025-10-15 onward, but only include cases whose outcomes are mature at the historical scoring cutoff.

Because the extraction date is 2026-02-15, a conservative binary test requiring activation + 90 + 35 days will not include many late-2025 activations. Therefore:

- publish a **mature test** ending at the latest activation date supported by the cutoff;
- report later cohorts only as application/activation drift monitoring until labels mature;
- subsequently run rolling out-of-time vintages as feeds arrive.

Use expanding-window backtests, refitting all preprocessing, frequency encodings, calibration, and missingness models within each training window. Applications linked across platforms or producing multiple prefixes remain in one fold.

The 2025-07-01 policy change must be evaluated as a distinct regime, with calibration intercept/slope and activation propensity monitored before and after it. The 2025-10-15 migration period requires separate duplicate-rate, unknown-activity, missingness, and feature-shift checks. If canonicalization cannot make the periods comparable, train regime-specific models or limit the deployment scope.

### Metrics

For the primary mature binary target:

- log loss and Brier score;
- calibration curve, calibration-in-the-large, and calibration slope;
- AUROC and average precision, with prevalence reported;
- sensitivity, specificity, PPV, and alert volume at prespecified operational thresholds;
- decision-curve/net-benefit analysis if action costs are defined.

For right-censored survival sensitivity analyses:

- time-dependent AUC;
- IPCW Brier score/integrated Brier score;
- calibration at 90 days.

Provide case-level bootstrap confidence intervals. Evaluate channel, region, requested-amount band, source system, partner origin, policy regime, migration regime, and prefix length. Small groups receive uncertainty intervals rather than unstable rankings.

Track covariate drift, activation rate, outcome-observation rate, score distributions, population stability measures, unknown activities, and calibration drift. A random case split is misleading because it mixes policy regimes, allows near-identical time/process conditions into all folds, hides feed maturity, and can leak linked cases or prefixes across folds.

## 8. Limitations and decision-use boundary

The study can estimate predictive associations between early prefix information and 90-day default **among accounts activated and observed under historical policies**, within demonstrated support. It can also separately describe process outcomes for all applications.

It cannot establish:

- default risk for rejected or withdrawn applicants;
- what would happen if every applicant were approved;
- causal effects of approval, document requests, review routing, or intervention;
- unbiased partner outcomes when permanent feed missingness is informative;
- stability after a major policy, platform, or intervention change.

Activation is both a business decision and a selection mechanism. A well-calibrated conditional model may still be poorly calibrated for all applicants. Reweighting measured variables cannot remove unmeasured selection or make an undefined exposure outcome observed.

Deployment can change the data-generating process through at least:

1. **Decision feedback:** high-risk scores cause rejection or lower limits, removing or changing the outcomes that would otherwise be observed.
2. **Process adaptation:** staff request more documents, reroute cases, or delay activation based on the score, changing prefix sequences and activation timing.
3. **Applicant behavior:** warnings or additional friction increase withdrawal, transfer, or strategic application behavior.
4. **Label feedback:** fewer activated high-risk accounts change default prevalence and model calibration.
5. **Operational gaming:** resources may alter activity recording or risk-score updates to influence alerts.

The score should support controlled early-warning actions, not be interpreted as a counterfactual approval score without a causal design. Deployment should log scores, actions, policy versions, and randomized or otherwise identifiable intervention variation where feasible.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import numpy as np
import pm4py

PATH = "applications_events.csv"
AS_OF = pd.Timestamp("2026-02-15 23:59:59", tz="UTC")
POLICY_CHANGE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION = pd.Timestamp("2025-10-15", tz="UTC")
CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"

# Version this mapping from migration documentation; examples are placeholders.
ACTIVITY_MAP = {
    "KYC Verification": "Identity/KYC Check",
    "Credit Assessment": "Credit Review",
    "Document Request": "Request Documents",
}
TERMINALS = {"Accepted", "Rejected", "Withdrawn", "Transferred"}
POST_PREFIX_ACTS = {
    "Contract Signed", "Account Activated",
    "Collections Contact", "Default Recorded"
}
FORBIDDEN_FEATURES = {
    "final_limit", "decision_reason", "collection_status", "default_90d",
    "label_available_at", "data_extract_time"
}

# ---------- Read and enforce the extraction-vintage perspective ----------
date_cols = [TS, "label_available_at", "data_extract_time"]
df = pd.read_csv(PATH)
for c in date_cols:
    df[c] = pd.to_datetime(df[c], errors="coerce", utc=True)

df = df[df[TS].notna() & (df[TS] <= AS_OF)].copy()
# A row cannot be used before its own extract/batch time.
df = df[df["data_extract_time"].isna() |
        (df["data_extract_time"] <= AS_OF)].copy()

df["activity_raw"] = df[ACT]
df[ACT] = df[ACT].replace(ACTIVITY_MAP)
df["migration_regime"] = (df[TS] >= MIGRATION).astype("int8")

# Narrow exact-duplicate rule: do not collapse legitimate document loops.
dedup_key = [CASE, ACT, TS, "org:resource", "source_system"]
df["was_duplicate"] = df.duplicated(dedup_key, keep="first")
df = df.loc[~df["was_duplicate"]].sort_values(
    [CASE, TS, ACT], kind="mergesort"
)

# PM4Py formatting uses the supplied schema columns.
event_df = pm4py.format_dataframe(
    df, case_id=CASE, activity_key=ACT, timestamp_key=TS
)

# ---------- Case state and maturity as of the configurable cutoff ----------
def first_time(g, names):
    s = g.loc[g[ACT].isin(names), TS]
    return s.min() if len(s) else pd.NaT

def case_summary(g):
    activation = first_time(g, {"Account Activated"})
    terminal = first_time(g, TERMINALS)
    rejected = first_time(g, {"Rejected"})
    withdrawn = first_time(g, {"Withdrawn"})
    transferred = first_time(g, {"Transferred"})

    # Label can be repeated. It is usable only when it was available by AS_OF.
    known = g[
        g["default_90d"].notna()
        & g["label_available_at"].notna()
        & (g["label_available_at"] <= AS_OF)
    ].sort_values("label_available_at")
    label = known["default_90d"].iloc[-1] if len(known) else np.nan
    label_at = known["label_available_at"].iloc[-1] if len(known) else pd.NaT

    # Conservative maturity: 90-day outcome horizon + maximum 35-day feed lag.
    mature_by_time = (
        pd.notna(activation)
        and activation + pd.Timedelta(days=125) <= AS_OF
    )
    return pd.Series({
        "case_start": g[TS].min(),
        "case_end_observed": g[TS].max(),
        "activation_time": activation,
        "terminal_time": terminal,
        "rejected_time": rejected,
        "withdrawn_time": withdrawn,
        "transferred_time": transferred,
        "label": label,
        "label_at": label_at,
        "mature_by_time": mature_by_time,
        "channel": g["case:channel"].iloc[0],
        "region": g["case:region"].iloc[0],
        "source_system": g["source_system"].iloc[0],
    })

cases = df.groupby(CASE, sort=False).apply(case_summary)
cases.index.name = CASE
cases["policy_regime"] = np.where(
    cases["case_start"] < POLICY_CHANGE, "pre_policy", "post_policy"
)

def state(r):
    if pd.notna(r.activation_time):
        if pd.notna(r.label):
            return "activated_mature_labeled"
        return ("activated_time_mature_feed_missing"
                if r.mature_by_time else "activated_not_mature")
    if pd.notna(r.rejected_time):
        return "rejected_competing"
    if pd.notna(r.withdrawn_time):
        return "withdrawn_competing"
    if pd.notna(r.transferred_time):
        return "transferred_competing_or_lost"
    return "open_right_censored"

cohort_counts = cases.apply(state, axis=1).value_counts(dropna=False)
print("Reconstructed cohort counts:\n", cohort_counts)
print("Total applications:", len(cases))
# Production: reconcile this total and category mapping to the stated 48,000.

# Primary complete-case target; a verified negative should additionally require
# an affirmative reliable follow-up indicator if the warehouse provides one.
eligible = cases[
    cases["activation_time"].notna()
    & cases["mature_by_time"]
    & cases["label"].notna()
].copy()

# ---------- Temporal split by case start, never a blind random split ----------
def temporal_split(start):
    if start < pd.Timestamp("2025-04-01", tz="UTC"):
        return "train"
    if start < POLICY_CHANGE:
        return "validation_pre_policy"
    if start < MIGRATION:
        return "test_policy_shift"
    return "test_migration_era"

cases["split"] = cases["case_start"].map(temporal_split)
eligible["split"] = eligible["case_start"].map(temporal_split)
print(pd.crosstab(eligible["split"], eligible["label"]))

# ---------- Fixed k-event prefixes ----------
# Keep only cases that reach exactly k events; short cases are reported and
# modeled separately rather than padded using future events.
K = 3
log = pm4py.convert_to_event_log(event_df)
prefix_log = pm4py.get_prefixes_from_log(log, K)
prefix_df = pm4py.convert_to_dataframe(prefix_log)

# PM4Py versions may create a derived prefix case ID. Preserve original case ID
# before this step in production if multiple prefix lengths are generated.
prefix_df = prefix_df.sort_values([CASE, TS])
prefix_sizes = prefix_df.groupby(CASE).size()
exact_ids = prefix_sizes[prefix_sizes == K].index
short_prefix_count = int((prefix_sizes < K).sum())
prefix_df = prefix_df[prefix_df[CASE].isin(exact_ids)].copy()
prefix_end = prefix_df.groupby(CASE)[TS].max().rename("prefix_time")

# Hard temporal assertion: no event after its prefix endpoint.
assert prefix_df.join(prefix_end, on=CASE)[TS].le(
    prefix_df.join(prefix_end, on=CASE)["prefix_time"]
).all()

# Early-warning landmark: exclude prefixes already containing future/terminal
# states. For alternative post-decision models, define another landmark.
bad_ids = prefix_df.loc[
    prefix_df[ACT].isin(POST_PREFIX_ACTS | TERMINALS), CASE
].unique()
prefix_df = prefix_df[~prefix_df[CASE].isin(bad_ids)].copy()

# ---------- Point-in-time prefix features only ----------
prefix_df["risk_score"] = pd.to_numeric(
    prefix_df["risk_score"], errors="coerce"
)
prefix_df["event_no"] = prefix_df.groupby(CASE).cumcount() + 1
prefix_df["delta_sec"] = (
    prefix_df.groupby(CASE)[TS].diff().dt.total_seconds()
)
prefix_df["is_doc_request"] = prefix_df[ACT].eq("Request Documents")
prefix_df["is_review"] = prefix_df[ACT].eq("Credit Review")
prefix_df["resource_change"] = (
    prefix_df.groupby(CASE)["org:resource"].transform(
        lambda s: s.ne(s.shift()).astype(int)
    )
)

features = prefix_df.groupby(CASE).agg(
    prefix_len=("event_no", "max"),
    prefix_time=(TS, "max"),
    elapsed_sec=(TS, lambda s: (s.max() - s.min()).total_seconds()),
    mean_gap_sec=("delta_sec", "mean"),
    max_gap_sec=("delta_sec", "max"),
    document_requests=("is_doc_request", "sum"),
    review_visits=("is_review", "sum"),
    distinct_resources=("org:resource", "nunique"),
    resource_handoffs=("resource_change", lambda s: max(int(s.sum()) - 1, 0)),
    latest_risk_score=("risk_score", "last"),
    first_risk_score=("risk_score", "first"),
    risk_updates=("risk_score", lambda s: int(s.notna().sum())),
    duplicate_indicators=("was_duplicate", "sum"),
)
features["risk_score_change"] = (
    features["latest_risk_score"] - features["first_risk_score"]
)

# Static attributes and targets are joined only after prefix feature creation.
features = features.join(cases[
    ["channel", "region", "policy_regime", "split"]
], how="left")
model_table = features.join(eligible[["label"]], how="inner")

# Leakage audit: forbidden raw fields cannot survive into the feature table.
leaked = FORBIDDEN_FEATURES.intersection(model_table.columns)
assert not leaked, f"Leakage columns present: {sorted(leaked)}"
assert not prefix_df[ACT].isin(POST_PREFIX_ACTS).any()
print("Exact-prefix cases:", len(features),
      "short prefixes reported:", short_prefix_count)
print("Model table by split:\n", model_table.groupby("split").size())

# Optional process diagnostics must be fit on TRAIN PREFIXES ONLY.
train_ids = model_table.index[model_table["split"].eq("train")]
train_prefix_df = prefix_df[prefix_df[CASE].isin(train_ids)]
train_prefix_log = pm4py.convert_to_event_log(
    pm4py.format_dataframe(
        train_prefix_df, case_id=CASE, activity_key=ACT, timestamp_key=TS
    )
)
dfg, start_acts, end_acts = pm4py.discover_dfg(train_prefix_log)
variants = pm4py.get_variants(train_prefix_log)
print("Training-prefix DFG edges:", len(dfg), "variants:", len(variants))

# Next steps:
# 1) fit the binary activated/mature model and calibration by temporal fold;
# 2) model activation and feed-observation probabilities for diagnostics/IPW;
# 3) connect activation-to-default records to a survival library externally;
#    PM4Py is used for process preparation, not fabricated survival modeling.
```
