## 1. Normalization Assumptions

I use the following explicit, conservative interval semantics.

1. **Clock-offset direction**
   - `clock_offset = recorded_clock - true_clock`.
   - If the source offset bound is `[a, b]`, then the true time is `recorded time - offset`, with offset in `[a, b]`.
   - Therefore, after resolution uncertainty is applied, an offset interval `[a, b]` expands the true-time interval by subtracting `b` from the earliest recorded time and subtracting `a` from the latest recorded time.

2. **Resolution uncertainty is applied before clock correction**
   - **HUB**: displayed second with measurement uncertainty `±0.5 s`, then offset `[-1, +1] s`. Net conservative interval: displayed time `±1.5 s`.
   - **OPS-BER / VENDOR-NY / LEGACY-BER floor-to-minute**: displayed `HH:MM` means recorded clock in `[HH:MM:00, HH:MM:59.999…]`. I use the conservative closed bounding interval `[HH:MM:00, HH:MM+1:00]` before offset correction. Sub-millisecond endpoint differences are immaterial to the conclusions.
   - **SENSOR round-to-nearest-10-seconds**: displayed `HH:MM:SS` means recorded clock in `[HH:MM:SS-5, HH:MM:SS+5]`, then offset `[-5, +5]`, giving a net conservative interval of `±10 s` around the displayed value.
   - **MOBILE-LON round-to-nearest-minute**: displayed `HH:MM` means recorded clock in `[HH:MM-30, HH:MM+30]`, then source-clock offset `[-300, +300]`.

3. **Time-zone conversion**
   - June 2026 dates:
     - `Europe/Berlin` is CEST, UTC+2.
     - `Europe/London` is BST, UTC+1.
     - `America/New_York` is EDT, UTC4.
   - Local clock uncertainty and offset uncertainty are applied in local time, then the resulting true local interval is converted to UTC.

4. **DST fold semantics for LEGACY-BER on 2025-10-26**
   - Berlin local times `02:00` through `02:59` occur twice:
     - fold 0 / first occurrence: CEST, UTC+2;
     - fold 1 / second occurrence: CET, UTC+1.
   - For each ambiguous minute-level timestamp I initially construct both fold alternatives.
   - The stated ingestion order `Alert_Received < Investigation_Start < Containment_Complete` is treated as a true-event ordering constraint for T-405. That constraint eliminates all but one fold combination:
     - Alert at `02:50` must be first-fold CEST;
     - Investigation_Start at `02:05` must be second-fold CET;
     - Containment_Complete at `02:42` must be second-fold CET.
   - If the ingestion-order assumption were rejected, the event intervals would remain disjoint DST-fold unions; I preserve those unconstrained unions in the notes.

5. **T-404 inferred Investigation_Start**
   - `Investigation_Start = Investigation_Complete - investigation_duration`.
   - The signed work record gives duration `[18, 25] minutes = [1080, 1500] seconds`.
   - I retain HUB timestamp uncertainty and duration uncertainty fully; I do not collapse to a point estimate.

6. **T-407 Alert_Received inference**
   - `Alert_Sent` is not treated as definitionally identical to `Alert_Received`.
   - I infer a feasible `Alert_Received` interval as `Alert_Sent + delivery_latency`, with latency `[0, 20] minutes`.
   - For the primary SLA/profile test, I apply the explicitly stated causal assumption: receipt must not be after `Investigation_Start`. This is labeled as an assumption, not a logged fact.
   - Without that causal assumption, T-407 S1 is treated as indeterminate/weakly testable; I show this separately.

7. **MOBILE-LON entry delay**
   - The mobile timestamp is user-entered. The prompt says the user may have entered the displayed time up to five minutes late.
   - I treat the entry delay as **occurrence uncertainty** in the primary analysis: the activity could have occurred up to 300 seconds before the entered mobile clock reading. Thus the primary occurrence interval is expanded backward by up to 5 minutes.
   - I also state the alternative: if the delay is treated purely as record-creation delay and the entered displayed time is assumed to be the occurrence-time clock reading, the mobile occurrence interval would be narrower. This alternative materially affects T-406 S2.

8. **SLA classification semantics**
   - For an ordered pair, negative feasible durations are treated as lifecycle-order violations, not as passes.
   - `CERTAIN_PASS`: every feasible duration is nonnegative and within the SLA limit.
   - `CERTAIN_VIOLATION`: every feasible duration violates the SLA, either because all durations are negative/order-violating or because all exceed the limit.
   - `POSSIBLE_VIOLATION`: feasible durations include both pass and violation outcomes.
   - `INDETERMINATE`: missing event, unbounded evidence, internally inconsistent evidence, or a required semantic assumption is not accepted.

9. **Temporal-profile classification semantics**
   - Primary profile analysis in Section 3 uses `zeta = 2`.
   - Sensitivity uses `zeta = 1, 2, 3`.
   - Acceptance band: `average ± zeta * standard_deviation`.
   - If the feasible duration interval is wholly inside the band: `CERTAIN_PASS`.
   - If wholly below or wholly above the band: `CERTAIN_VIOLATION`.
   - If partially overlapping: `POSSIBLE_VIOLATION`.
   - If evidence is missing or not testable: `INDETERMINATE`.

10. **Midpoints**
   - Midpoints are used only in Section 5 for a secondary PM4Py comparison and are explicitly labeled as lossy. They are never used to replace interval conclusions in Sections 3 or 4.
