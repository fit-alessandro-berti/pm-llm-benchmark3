## 1. Target definition
**Primary target (chosen):** A competing multi-state outcome under the observed policy, measured from an early landmark. Let $\tau$ be the timestamp of the 3rd canonical event for a case (normally the first Credit Review). The primary estimand is the vector of cumulative-incidence probabilities from $\tau$:

$$F_j(t \mid H_\tau) = P(\text{state } j \text{ by time } t \mid \text{prefix history } H_\tau, \text{reached } \tau)$$

for mutually exclusive states $j$: (a) activated and defaulted within 90 days after activation, (b) activated and confirmed non-default within 90 days after activation, (c) rejected, (d) withdrawn, (e) transferred. The operational score extracted from this vector is $F_{\text{activated-default}}$, always reported alongside $P(\text{activated}\mid H_\tau)$ and the decomposition into activation and conditional default.

- **Unit of analysis:** one application episode (`case:concept:name`) in this system — not an applicant or person. A transferred case reappearing under a new ID is a second episode unless linkage proves otherwise.
- **Population:** all applications started 1 Jan 2024–31 Dec 2025 that reach $\tau$ without prior terminal event or activation. Inference is under the policy in force at each case’s start; it is not a hypothetical population in which everyone is accepted.
- **Prediction time:** $\tau$, the 3rd event. **Horizon:** follow-up from $\tau$ until the earliest of: competing terminal event, activation + 90 days outcome confirmation, or administrative censoring at extraction (15 Feb 2026). Rejected, withdrawn, and transferred cases are their own states — never recoded as “non-default,” because default under non-activation is undefined in the observed data.

**Why this is defensible:** it is well-defined for every case reaching $\tau$, does not invent counterfactual outcomes, separates activation selection from default risk, and supports early triage (e.g., review intensity, document chasing) without pretending the model estimates what would have happened had a rejected applicant been accepted.

**Alternative 1 — conditional binary default among the activated:** $P(\text{default\_90d}=1 \mid H_\tau, \text{activated}=1)$, fit only on the 21,600 mature activated accounts. This answers “given activation, what is the risk?” and is useful for post-decision pricing — but at $\tau$ activation is a future event, so conditioning on it induces selection bias, and the model cannot be applied to all applications without a separate activation model and reject-inference assumptions. Retained as a secondary, clearly-labeled estimand.

**Alternative 2 — time to default after activation (landmark at activation):** a survival target with right censoring. This answers post-activation monitoring, not early warning; it discards the early prefix and would suffer immortal-time bias if early features were used with an activation-time origin uncritically.

**Alternative 3 — policy-specific counterfactual:** $P(\text{default\_90d}^{\text{do(activate all)}})$. This answers “what if we changed the acceptance policy?” but requires consistency, positivity, and no unmeasured confounding of activation — none verifiable here, since rejected applicants were never exposed to credit. Explicitly not the primary target.

## 2. Cohort construction
**Inclusion:** all 48,000 applications with a start event in the observation window; for the primary analysis, cases that reach $\tau$ (3rd event) before any terminal event or activation, with a valid start timestamp.

**Exclusion (primary model only):** cases that terminate or activate before the 3rd event, or never reach 3 events by extraction. These are excluded from the landmark risk set — counted in the flow, never coded as negatives — and examined in $k=2$ sensitivity analyses. No case is excluded because its label is missing, immature, partner-originated, or transferred.

**As-of rules:** (i) features are reconstructed strictly from events $\le \tau$; (ii) outcomes are followed to the 15 Feb 2026 extraction; (iii) a case is “mature-labeled” only if `label_available_at` $\le$ extraction; (iv) static attributes must be the values known at $\tau$ (e.g., requested amount as of $\tau$, not a later update); (v) duplicate migration events are deduplicated at event level, not case level.

| Final state at extraction | n | % of 48,000 | Status | Treatment |
|---|---:|---:|---|---|
| Activated, mature label: default | 2,700 | 5.6% | Labeled (event) | State (a) |
| Activated, mature label: non-default | 18,900 | 39.4% | Labeled (event) | State (b) |
| Activated, outcome/feed not yet mature | 3,600 | 7.5% | Not yet mature / right-censored | Censored at extraction; never negative |
| Rejected | 9,100 | 19.0% | Competing outcome | State (c); default undefined |
| Withdrawn | 5,700 | 11.9% | Competing outcome | State (d) |
| Transferred | 2,900 | 6.0% | Competing event / loss to follow-up | State (e); 60% linkable elsewhere |
| Still open | 5,100 | 10.6% | Right-censored | Censored; may activate later |
| **Total** | **48,000** | **100%** | | |

The aggregate snapshot does not identify how many cases reach the 3-event landmark; the pipeline computes this cross-tabulated against final state and reports it alongside the table above rather than fabricating a number. The observed default proportion among mature activated accounts is 2,700/21,600 = 12.5% — this is a conditional, selected quantity, not the default rate for all applications (5.6% of the full cohort activated and defaulted).

## 3. Censoring and missing-label strategy
Five distinct mechanisms must not be conflated:

| Mechanism | Cases affected | Primary handling |
|---|---|---|
| Ordinary right censoring | 5,100 still open; 3,600 activated but immature | Contribute follow-up until extraction; IPCW in evaluation |
| Delayed labels | Feed arrives 7–35 days after the 90-day horizon | Maturity defined by `label_available_at`, not activation+90; cases within the lag window are censored, not negative |
| Selection through activation | Only 25,200/48,000 ever activate; activation depends on prefix, policy era, amount, channel | Part of the observed policy in the primary estimand; modeled explicitly only for the secondary conditional target |
| Transfer | 2,900 cases; 40% unlinkable, possible reappearance as a new ID | Primary: competing event under this platform’s policy. Sensitivity: censoring at transfer |
| Permanently missing feeds | Partner-originated activated accounts have elevated missingness; size unquantified in aggregates | IPCW under MAR given observed covariates; tipping-point sensitivity (below) |

**Primary strategy:** competing-risk analysis from $\tau$ (Aalen–Johansen descriptively; cause-specific discrete-time hazards for prediction), with inverse-probability-of-censoring weights estimated from start time, source system, channel, and region. No imputation of outcomes for rejected, withdrawn, transferred, or immature cases.

**Sensitivity analyses:** (1) treat transfer as censoring instead of competing; (2) mature-activated-only binary model for the conditional estimand, unweighted vs. IPW for activation and label observation; (3) tipping-point analysis for permanently missing partner feeds, varying the assumed default odds among missing vs. observed within strata (e.g., odds ratios 0.5, 1, 2); (4) exclusion of partner-originated cases and of linked transfer duplicates; (5) separate pre/post 1 July 2025 policy-era fits.

**Testability:** covariate balance after IPW, censoring-model fit, missingness vs. observed covariates, activation-propensity overlap/positivity by era, and duplicate rates are testable or partially testable. Fundamentally untestable from these data: the default outcomes of never-activated applicants, MNAR structure of permanently missing feeds, identity of the 40% unlinked transfers, and absence of unmeasured confounding for activation.

## 4. Prefix extraction
- **Primary:** fixed event-count prefix, $k=3$ (Application Started  Identity/KYC Check  first Credit Review). This guarantees every case is at the same process stage at prediction time. Sensitivity: $k=2, 4, 5$.
- **Secondary:** elapsed-time landmarks at 24h, 72h, and 7 days from start, using all events $\le$ landmark. These answer a different question (“what do we know by Tuesday?”) and mix process stages, so they are reported separately, never pooled with event-count results.
- **Short cases:** if a case terminates or activates before $k$, it is not in that landmark’s risk set. No padding with future events, no backward-filling. Cases stuck below $k$ at extraction are censored for that landmark.
- **Document loops:** each Credit Review re-entry counts as an event, so an event-count prefix can cut mid-loop at larger $k$; loop count, loop duration, and “open loop at $\tau$” are recorded as features. At $k=3$ the prefix ends at the first Credit Review, so loops only enter via the elapsed-time landmarks and $k\ge4$ sensitivities.
- **Activity renaming (15 Oct 2025 migration):** a fixed, audited oldnew activity map is applied before any counting; raw names are retained for audit. Exact duplicates (same case, canonical activity, timestamp, resource) are dropped and the count logged; remaining near-duplicates are flagged in a migration-era sensitivity. The map is not learned from future data.

All prefix statistics (counts, durations, temporal features) are computed from the truncated trace only; scalers, encoders, and reference distributions are fit within each training fold.

## 5. Process-aware features
Available at $\tau$ only; grouped by provenance:

| Group | Examples | Source |
|---|---|---|
| Static case attributes | channel, region, requested amount (as of $\tau$), source system / partner flag | Known at start/$\tau$ |
| Control-flow (prefix) | activity counts and proportions, last activity, activity bigrams, prefix variant, number of Credit Review entries, handoffs | Prefix trace |
| Timing (prefix) | start$\tau$ duration, inter-event gaps, dwell per activity, time since last event, share of time in Credit Review | Prefix trace |
| Rework (prefix) | document-request loop count, completed vs. open loops at $\tau$, loops per day, repeated KYC/Credit Review cycles | Prefix trace |
| Resource / queue (prefix + reference) | distinct resources, same-resource continuity, resource’s open-case load and starts in prior 7/28 days | Prefix + historical, as-of |
| Resource experience (repaired) | experience at event time, reconstructed from effective-dated HR records; dropped if unreconstructable | Historical reference |
| Cohort / calendar | policy era (pre/post 1 Jul 2025), migration era, start month, weekday/hour at $\tau$, amount percentile within prior-90-day cohort | Cohort + reference |
| Historical reference | rolling prior-90-day activation rate and mature-default rate (labels available before $\tau$ only, shrinkage with minimum n), median prefix duration of prior cohort | Expanding window, lagged |

`risk_score` enters as the last value with timestamp $\le\tau$, plus its update count and missingness indicator up to $\tau$. `documents_total` is recomputed as the count of document events $\le\tau$ (see §6).

## 6. Leakage audit
| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final decision; reveals acceptance and indirectly risk | Never at $\tau$ | Drop | Post-decision field; using it trains a decision detector, not early warning |
| `decision_reason` | Populated at/after Accept/Reject; directly encodes the decision | Never at $\tau$ | Drop | Leaks the competing outcome (rejection/acceptance) |
| `collection_status` | Updated after activation; collections activity directly reveals default | Never at $\tau$ | Drop | Post-outcome variable; target leakage by construction |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Encode activation, competing states, and the outcome itself | Events with timestamp $\le\tau$ only (none of these normally qualify) | Drop / truncate | Prefix truncation is the core leakage control; enforced by event-rank filter and audit assert |
| `documents_total` | Nightly snapshot includes uploads later the same calendar day than $\tau$ | Recomputed count of document events $\le\tau$ | Repair | Original field mixes intra-day future information; event-level recomputation is as-of correct |
| Updated `risk_score` | Later updates may incorporate post-$\tau$ information, including decision outcomes | Last value with timestamp $\le\tau$, plus count/missingness to $\tau$ | Repair | Event-sourced as-of value; the warehouse “latest” column is not as-of |
| Resource experience | Stored at extraction time; reflects future tenure and post-$\tau$ staffing | Experience at event time from effective-dated records | Repair or drop | Extraction-time value is future information; if history is unavailable, drop rather than proxy |
| Label availability (`label_available_at`, `default_90d` on events) | Requiring label availability at sampling induces maturity selection; label columns repeated on events invite direct use as features | Used only to define maturity/censoring and as the outcome after maturity check; never a predictor | Keep for outcome only | Separates outcome definition from features; maturity is a cohort property, not a signal |
| Historical target encodings / aggregates | Full-sample means leak future outcomes into training | Rolling, lagged windows using only labels with `label_available_at` $\le\tau$ | Repair | Prevents temporal leakage in both training and backtests |
| Full-log process statistics (DFG, variant frequencies, normalizers) | Fit on complete traces including post-$\tau$ behaviour | Fit on prefix traces within the training fold only | Repair | Aggregate full-log statistics are subtle future-information channels |

## 7. Validation design
**Temporal, rolling-origin backtests** (random splits are rejected — see below):

| Origin | Fit set | Evaluation cohort (by case start) | Purpose |
|---|---|---|---|
| 1 Jan 2025 | Starts before 2025-01-01 with `label_available_at`  2025-01-01 | Starts 2025-01-01–2025-03-31 | Pre-policy temporal performance |
| 1 Jul 2025 | Starts before 2025-07-01 with `label_available_at`  2025-07-01 | Starts 2025-07-01–2025-08-31 | Post-policy, pre-migration transport |
| Post-migration | — | Starts  2025-10-15 | Prospective monitoring only (activation/rejection drift); default performance deferred until label maturity |

The `label_available_at` purge is essential: training cases whose labels would not yet have arrived at the evaluation origin are excluded from that fold’s fit, simulating a real backtest. All preprocessing (encodings, imputers, censoring/activation propensity models) is fit inside each fold.

**Why a random case split is misleading here:** it mixes pre/post-policy eras so the model never has to transport across the 1 July 2025 threshold change; it places migration-duplicate traces and linked transfer reappearances in both train and test; it lets future labels contaminate aggregates; and it ignores the 125-day (90 + up to 35) label-maturity lag, overstating both performance and deployability.

**Metrics:** for the primary competing-risk target — IPCW Brier score per state, multiclass log loss on maturity-known cases, one-vs-rest IPCW AUROC for activated-default, and calibration of predicted cumulative incidence against Aalen–Johansen estimates by decile. For the secondary conditional target — AUROC, AUPRC, Brier, calibration intercept/slope, and decision-curve utility at review-capacity thresholds chosen on validation, not test. Confidence intervals by case-level bootstrap (clustering linked transfers). Subgroups: policy era, migration era, source system (partner vs. direct), channel, region, amount bands. Drift monitoring: PSI on prefix features, activation/rejection rates, and calibration intercept over time.

## 8. Limitations and decision-use boundary
**What the study can claim:** under the observed policy, cases reaching the 3-event landmark can be ranked by their probability of eventually activating and defaulting, and the competing pathways (rejection, withdrawal, transfer) can be quantified — with calibrated uncertainty and explicit censoring.

**What it cannot claim:** the counterfactual default risk of rejected or withdrawn applicants had they been accepted; any causal effect of model-guided rejection or document requests; performance for post-migration cohorts until their labels mature; performance for partner-originated accounts with permanently missing feeds beyond the sensitivity range; or applicant-level risk for the 40% of transfers that cannot be linked.

**Predictive association vs. selection vs. counterfactual:** the primary score is an association under a specific selection process (who reaches $\tau$, who gets activated). It describes the world as operated, not the world under a different acceptance policy. Any use that changes who is activated changes the estimand itself.

**Deployment feedback loops (at least three):** (1) *Selective labels:* using the score to reject or deprioritize cases removes their chance to default, making future “non-defaults” self-fulfilling and corrupting retraining data. (2) *Process adaptation:* model-triggered document requests or senior-resource assignment changes loop counts and timing features, shifting the input distribution the model was validated on. (3) *Applicant/broker adaptation:* brokers learn which prefixes score well and alter amounts, channels, or application timing, inducing gaming and covariate shift. (4) *Policy/process drift:* future threshold changes or system migrations alter both the prefix distribution and the outcome relationship. Mitigations: shadow-mode deployment first, periodic revalidation against mature labels only, calibration monitoring by era and source system, and a standing rule that model scores never auto-reject.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py

CASE_ID = "case:concept:name"
ACTIVITY = "concept:name"
TIMESTAMP = "time:timestamp"
RESOURCE = "org:resource"
CUTOFF = pd.Timestamp("2026-02-15")
PREFIX_K = 3  # first Credit Review; sensitivity: 2, 4 and 72h landmarks
TERMINAL_ACTIVITIES = {"Rejected", "Withdrawn", "Transferred"}  # canonical names
ACTIVITY_MAP = {}  # ASSUMPTION: fill with audited Oct-2025 old->new activity names
FORBIDDEN = ["final_limit", "decision_reason", "collection_status", "default_90d",
             "label_available_at", "documents_total", "data_extract_time"]

def main():
    df = pd.read_csv("applications_events.csv",
                     parse_dates=[TIMESTAMP, "label_available_at", "data_extract_time"])
    df = df.sort_values([CASE_ID, TIMESTAMP]).reset_index(drop=True)
    df[ACTIVITY] = df[ACTIVITY].replace(ACTIVITY_MAP)

    # Migration duplicates: drop only exact duplicates; log the number removed.
    n_before = len(df)
    df = df.drop_duplicates(subset=[CASE_ID, ACTIVITY, TIMESTAMP, RESOURCE])
    print(f"Removed {n_before - len(df)} exact duplicate events")

    # ---- Case-level outcome / censoring info, reconstructed as of CUTOFF ----
    start_time = df.groupby(CASE_ID)[TIMESTAMP].min().rename("start_time")
    activation_time = (df.loc[df[ACTIVITY] == "Account Activated"]
                         .groupby(CASE_ID)[TIMESTAMP].min().rename("activation_time"))
    terminal_events = df[df[ACTIVITY].isin(TERMINAL_ACTIVITIES)].sort_values(TIMESTAMP)
    terminal_time = terminal_events.groupby(CASE_ID)[TIMESTAMP].min().rename("terminal_time")
    terminal_activity = (terminal_events.groupby(CASE_ID)[ACTIVITY].first()
                         .rename("terminal_activity"))
    label_available_at = (df.groupby(CASE_ID)["label_available_at"].max()
                            .rename("label_available_at"))
    # ASSUMPTION: repeated default_90d values within a case are consistent; audit this.
    default_value = df.groupby(CASE_ID)["default_90d"].max().rename("default_value")
    case_info = pd.concat([start_time, activation_time, terminal_time,
                           terminal_activity, label_available_at, default_value],
                          axis=1).reset_index()
    case_info["mature"] = (case_info["label_available_at"].notna()
                           & (case_info["label_available_at"] <= CUTOFF))

    def classify(r):
        if pd.notna(r["terminal_activity"]):
            return {"Rejected": "rejected_competing", "Withdrawn": "withdrawn_competing",
                    "Transferred": "transferred_competing_or_lost"}[r["terminal_activity"]]
        if pd.notna(r["activation_time"]) and r["mature"] and pd.notna(r["default_value"]):
            return "activated_default" if r["default_value"] == 1 else "activated_no_default"
        if pd.notna(r["activation_time"]):
            return "activated_not_yet_mature_censored"  # never code as non-default
        return "still_open_censored"

    case_info["state"] = case_info.apply(classify, axis=1)
    print("\nCohort flow (all applications):")
    print(case_info["state"].value_counts(dropna=False))

    # ---- Prefixes: events with rank <= K only; tau is the K-th event time ----
    df["event_rank"] = df.groupby(CASE_ID).cumcount() + 1
    df_prefix = df[df["event_rank"] <= PREFIX_K].copy()
    tau = (df_prefix.loc[df_prefix["event_rank"] == PREFIX_K]
           .set_index(CASE_ID)[TIMESTAMP].rename("tau"))
    case_info = case_info.set_index(CASE_ID).join(tau).reset_index()
    # Landmark cohort: reached tau before terminal/activation (times are event times).
    reached = case_info["tau"].notna()
    for col in ["terminal_time", "activation_time"]:
        reached &= case_info[col].isna() | (case_info[col] >= case_info["tau"])
    cohort = case_info[reached].copy()
    print(f"\nReached {PREFIX_K}-event landmark: {len(cohort):,} of {len(case_info):,}")

    # Post-prefix data repair examples: as-of risk score and document count.
    risk_rows = df_prefix.dropna(subset=["risk_score"]).groupby(CASE_ID).tail(1)
    risk_asof = risk_rows.set_index(CASE_ID)["risk_score"].rename("risk_score_tau")
    doc_counts = (df_prefix.assign(is_doc=df_prefix[ACTIVITY].str.contains("Document", na=False))
                  .groupby(CASE_ID)["is_doc"].sum().rename("documents_tau"))

    # ---- PM4Py log built ONLY from prefix events and non-forbidden columns ----
    df_model = df_prefix.drop(columns=[c for c in FORBIDDEN if c in df_prefix.columns])
    log_prefix = pm4py.format_dataframe(df_model, case_id=CASE_ID,
                                        activity_key=ACTIVITY, timestamp_key=TIMESTAMP)
    dfg = pm4py.discover_dfg(log_prefix)       # audit only; not a feature fit on full log
    variants = pm4py.get_variants(log_prefix)  # audit only; prefix variants
    prefixes = pm4py.get_prefixes_from_log(log_prefix, variant="positive",
                                           min_prefix_length=PREFIX_K)
    print(f"DFG edges: {len(dfg)}; prefix variants: {len(variants)}; prefixes: {len(prefixes)}")

    temporal = pm4py.extract_temporal_features_dataframe(log_prefix)
    if "case_id" in temporal.columns:
        temporal = temporal.rename(columns={"case_id": CASE_ID})
    elif CASE_ID not in temporal.columns:
        temporal = temporal.reset_index().rename(columns={"index": CASE_ID})
    temporal = temporal.drop(columns=[c for c in ["start_time", "tau", "state"]
                                      if c in temporal.columns])
    features = temporal.merge(cohort[[CASE_ID, "start_time", "tau", "state"]],
                              on=CASE_ID, how="inner")
    features = features.join(risk_asof, on=CASE_ID).join(doc_counts, on=CASE_ID)
    # pm4py.split_train_test(log) is only a convenience/random baseline; not used here.

    # ---- Temporal split by case start; label purge is applied at fitting time ----
    def split_name(start):
        if start <= pd.Timestamp("2024-12-31"):
            return "train"
        if start <= pd.Timestamp("2025-06-30"):
            return "validation"
        return "post_policy_test"  # post-migration starts reported separately
    features["split"] = features["start_time"].apply(split_name)
    print("\nTemporal split sizes:")
    print(features.groupby(["split", "state"]).size())

    # ---- Leakage audit ----
    assert not (set(FORBIDDEN) & set(features.columns)), "Forbidden column in features"
    max_prefix = df_prefix.groupby(CASE_ID)[TIMESTAMP].max().rename("max_prefix_time")
    audit = cohort.set_index(CASE_ID).join(max_prefix)
    assert (audit["max_prefix_time"] == audit["tau"]).all(), "Post-prefix event leaked"
    print("Leakage audit passed: max prefix event time == tau; no forbidden columns.")

    # SURVIVAL / COMPETING-RISK HOOKUP (not in PM4Py): join features to cohort event and
    # censor times (tau, activation_time, terminal_time, label_available_at) and fit
    # Aalen-Johansen or cause-specific discrete-time hazards. Censored / immature cases
    # contribute until censoring and are never recoded as activated_no_default.
    return {"case_info": case_info, "cohort": cohort, "features": features,
            "dfg": dfg, "variants": variants}

if __name__ == "__main__":
    main()
```
