## 1. Control-Objective Decomposition

The nominal Four-Eyes Principle (FEP-1) is a structural mechanism designed to prevent unilateral initiation and release of funds. Decomposing FEP-1 into specific threat scenarios demonstrates how compensating controls address—or fail to address—the underlying control objectives.

| Threat Scenario / Sub-Objective | AV-2 (Automated Validation) | MG-4 (Independent Manager Approval) | RA-7 (Retrospective Audit & Recall) | ED-1 (Emergency Single-Operator Protocol) |
| :--- | :--- | :--- | :--- | :--- |
| **1. Unilateral Fraudulent Diversion**<br>*(Fictitious vendor or unauthorized bank account substitution)* | **Preventive / Detective:** Strong against recent bank changes (<7 days), sanctions, and account ownership mismatches. Fails if compromised account is aged >7 days or warning is overridden. | **Preventive / Detective:** Strong if performed pre-settlement and manager substantively verifies bank details against independent vendor master records. Fails if rubber-stamped or if credentials are shared. | **Detective / Corrective:** Detects post-facto; corrective only if completed within the 24-hour bank recall window. Fails if funds are immediately withdrawn by the fraudster. | **Preventive (Scope-Limiting):** Restricts exposure by banning new vendors (<180 days), recent bank changes (<7 days), and amounts  EUR 100k. |
| **2. Unilateral Clerical / Fat-Finger Error**<br>*(Duplicate payment, wrong amount, wrong invoice)* | **Preventive:** High coverage via duplicate invoice check, PO match, and operator limit enforcement. | **Preventive:** High coverage if manager compares invoice to payment proposal before settlement. | **Detective / Corrective:** High recovery likelihood for established vendors even outside the 24h window via commercial clawback/credit note, though administratively costly. | **Preventive:** Mandates a clean AV-2 pass without override, ensuring baseline automated error checks remain intact. |
| **3. Fictitious Commercial Substance**<br>*(Payment for unrendered services or fabricated goods receipts)* | **Fails to Address:** Checks formal PO match in system, not physical reality or commercial reasonableness. | **Preventive:** Effective only if the L3+ manager has operational visibility and reviews authentic supporting service/goods receipts prior to settlement. | **Detective:** Can uncover fabricated receipts via deep-dive forensic audit, often too late for unilateral bank recall. | **Fails to Address Directly:** Relies entirely on the embedded MG-4 and RA-7 requirements to verify commercial substance. |
| **4. Credential Compromise / Session Hijacking**<br>*(One physical actor operating two nominal user accounts)* | **Fails to Address:** Validates system account limits, not biometric or physical operator identity. | **Preventive / Detective:** Independent manager review catches unauthorized payments if the manager's own credentials are not the ones compromised. | **Detective:** Can correlate workstation IDs, IP logs, and badge access post-facto to expose physical single-actor control. | **Fails to Address:** Formalizes single-user operation, making it critical that the MG-4 approver is genuinely independent and authenticated. |
| **5. Collusive Fraud**<br>*(Preparer and Releaser/Approver conspiring)* | **Fails to Address:** Cannot detect human conspiracy if system parameters (limits, aged vendor) are respected, though it creates an audit trail of overrides. | **Preventive / Fails:** Prevents collusion between lower-level clerks, but fails if the manager is the colluding party or under a conflict of interest (e.g., direct supervisor sharing credentials). | **Detective:** Primary control against two-person collusion, provided the auditor (RA-7) is structurally independent of the payment unit. | **Detective (via mandatory RA-7):** Forces 100% audit within 1 business day, elevating the detection risk for colluding operators and managers. |

## 2. Equivalence and Sufficiency Test

A compensating control package cannot be evaluated merely by counting whether an activity occurred. It must be evaluated across seven structural dimensions:

1. **Timing:** Does the control act *before* `Release_Payment` (purely preventive), *between* `Release_Payment` and irrevocable `Bank_Settlement` (settlement-preventive), within the 24-hour bank recall window (corrective), or after settlement is irrevocable (purely detective)?
2. **Independence:** Is the compensating actor free from hierarchical dependency, shared performance incentives, and physical co-location/session-sharing with the preparer?
3. **Coverage:** Do the controls collectively cover formal accuracy (PO, limits, duplicates), counterparty integrity (bank ownership, aged vendor), and substantive validity (actual receipt of goods/services)?
4. **Overrideability:** Can the control be bypassed by the preparer, or via borrowed/compromised credentials without triggering an immediate hard block?
5. **Recoverability:** If a control acts post-release, what is the realistic probability of stopping the outflow or recalling the funds based on vendor relationship and banking mechanics?
6. **Evidence Quality:** Is there verifiable telemetry proving a substantive review occurred (e.g., checked receipts, verified bank ownership), rather than an unsigned checklist or rubber-stamp click?
7. **Collusion Resistance:** Does the control architecture disrupt repeat pairing and shared physical environments?

### Four-Tier Sufficiency Standard

*   **Fully Equivalent (`OBJECTIVE_MET`):** The package prevents unilateral fund outflow prior to irrevocable `Bank_Settlement`. It requires full coverage (clean AV-2 pass + substantive independent MG-4 review of receipts and bank details before settlement) or strict compliance with all ED-1 conditions. Residual risk is no higher than under nominal FEP-1.
*   **Partially Equivalent (`OBJECTIVE_PARTIALLY_MET`):** Minor procedural or timing deviations exist (e.g., missing emergency token for a low-risk payment, or token logged minutes late), *provided* substantive pre-settlement MG-4 review and clean AV-2 validation occurred, and audit completed within the recall window.
*   **Merely Mitigating (Tolerable only for low risk; otherwise `OBJECTIVE_FAILED`):** Controls act only after `Bank_Settlement`, or pre-settlement controls have coverage gaps, but recovery remains feasible (e.g., long-established vendor, timely RA-7 audit).
*   **Ineffective (`OBJECTIVE_FAILED`):** Unilateral action is combined with bypassed/unavailable AV-2, post-settlement or conflicted MG-4, late RA-7 audit outside the recall window, or evidence of collusion/credential sharing.

### Why "Same Expected Loss" is Not the Only Standard
Internal control design is not purely an actuarial exercise where a high probability of a small loss equals a low probability of a catastrophic loss ($\mathbb{E}[L] = P \times L$). First, **tail-risk and liquidity constraints** mean a single EUR 900,000 unrecoverable outflow (like AP-208) can threaten operational liquidity even if the probability is low. Second, **fiduciary and regulatory standards** require demonstrable process integrity; allowing unchecked unilateral overrides erodes control culture and invites systemic fraud (moral hazard). Third, **auditability** requires deterministic evidence that rules are enforced, not post-hoc luck that a high-value unvalidated payment happened to be legitimate.

## 4. Preventive–Detective–Corrective Comparison

| Control Mechanism | Preventive Capacity | Detective Capacity | Corrective Capacity | Structural Limitations & Failure Modes |
| :--- | :--- | :--- | :--- | :--- |
| **FEP-1 (Nominal Four-Eyes)** | **Primary:** Prevents unilateral error or fraud prior to `Release_Payment`. | **Secondary:** Second operator detects errors made by the first during pre-release review. | **None:** Acts prior to release; does not recover funds once settled. | Defeated by collusion, credential sharing, shared workstations (`AP-204`/`AP-209`), or superficial "rubber-stamp" releasing. |
| **AV-2 (Automated Validation)** | **Primary:** Hard-blocks duplicates (`AP-205`) or emits warnings before `Release_Payment`. | **Primary:** Flags bank changes (<7d), sanctions, PO mismatches, and limit breaches. | **None:** Purely pre-release gating. | Blind to physical service/goods receipt (`AP-204`), vulnerable to manager override abuse (`AP-202`), and ineffective during service outages (`AP-208`). |
| **MG-4 (Pre-Release Approval)** | **Primary:** Prevents unauthorized release via independent L3+ review (`AP-203`, `AP-206`). | **Primary:** Detects commercial unreasonableness or missing receipts before release. | **None:** Acts before release occurs. | Vulnerable to supervisor conflicts of interest, credential sharing (`AP-202`), or superficial review. |
| **MG-4 (Post-Release, Pre-Settlement Ratification)** | **Hybrid (Settlement-Preventive):** Prevents irrevocable outflow (`Bank_Settlement`). | **Primary (Release-Detective):** Detects unauthorized `Release_Payment` in the staging queue. | **Hybrid (Internal Cancellation):** Aborts queued payment instruction before bank execution (`AP-201`, `AP-207`). | Requires a time buffer between `Release_Payment` and `Bank_Settlement`. Fails if settlement is instantaneous or ratification occurs post-settlement (`AP-208`). |
| **RA-7 (Retrospective Audit & Recall)** | **None:** Acts strictly after payment release/settlement (except via general deterrence). | **Primary:** Uncovers fabricated receipts (`AP-204`), override abuse (`AP-202`), and outages (`AP-208`). | **Conditional:** Corrective *only* if completed within the 24h bank recall window (`AP-201`, `AP-203`, `AP-206`, `AP-207`, `AP-209`). | Loses corrective power after 24 hours (`AP-202`, `AP-204`, `AP-208`) or if a fraudulent recipient immediately drains the receiving account. |
| **ED-1 (Emergency Protocol)** | **Boundary-Setting:** Caps exposure (<EUR 100k, aged vendor, no bank change) and mandates AV-2/MG-4. | **Trigger:** Flags single-operator cases for mandatory 100% 1-day RA-7 audit. | **Enabler:** Ensures audit occurs within the 24h recall window. | Not an independent control; fails completely if system does not hard-enforce preconditions when emergency tokens are used (`AP-208`). |

### Semantics of Post-Release, Pre-Settlement Manager Action (`Manager_Ratify`)
Classifying a manager action that occurs *after* `Release_Payment` but *before* `Bank_Settlement` (as seen in `AP-201` and `AP-207`) requires distinguishing between **workflow state** and **economic reality**:
*   **With respect to the internal workflow event (`Release_Payment`):** The control is **detective and internally corrective**. The operator has already committed a workflow violation by releasing the payment alone; the manager detects this queued instruction and can cancel/abort it internally.
*   **With respect to the control objective (preventing unauthorized fund outflow / `Bank_Settlement`):** The control is **preventive**. Because bank settlement is the point of economic irrevocability, an independent manager who verifies supporting documents and ratifies the transaction *while it is still held in the pre-settlement payment queue* prevents unauthorized funds from leaving the company's custody. Therefore, in this evaluation framework, pre-settlement ratification is treated as **Hybrid (Workflow-Detective / Settlement-Preventive)** and is functionally sufficient to meet the control objective if performed substantively by an independent manager.

    log_df[log_df["concept:name"].str.contains("Validate")]
    .groupby("case:concept:name")["concept:name"]

    log_df[log_df["concept:name"] == "Override_Warning"][
        "case:concept:name"

def evaluate_case_flags(row):
    cid = row.name
    # Nominal FEP-1 check
    if cid in blocked_cases:
        fep_flag = "BLOCKED_PRE_RELEASE"
    elif cid in pm4py_fep_cases or (row["prep_user"] == row["rel_user"]):
        fep_flag = "VIOLATED_SAME_USER"
    else:
        fep_flag = "CONFORMING_DISTINCT_USERS"

    # AV-2 Coverage Flag
    evs = av_events.get(cid, [])
    if "Automated_Validate_Block" in evs:
        av_flag = "BLOCKED"
    elif "Automated_Validate" in evs and cid not in override_events:
        av_flag = "CLEAN_PASS"
    elif "Automated_Validate_Warning" in evs and cid in override_events:
        av_flag = "WARNING_OVERRIDDEN"
    else:
        av_flag = "UNAVAILABLE_OR_BYPASSED"

    # Manager Timing & Independence Flag
    if pd.isna(row["mgr_ts"]):
        mgr_flag = "NO_MANAGER_REVIEW"
    elif not row["mgr_indep"]:
        mgr_flag = "CONFLICTED_MANAGER"
    elif pd.notna(row["rel_ts"]) and row["mgr_ts"] < row["rel_ts"]:
        mgr_flag = "PRE_RELEASE_INDEP"
    elif (
        pd.notna(row["effective_stl_ts"])
        and row["mgr_ts"] < row["effective_stl_ts"]
    ):
        mgr_flag = "POST_REL_PRE_SETTLEMENT_INDEP"
    else:
        mgr_flag = "LATE_POST_SETTLEMENT"

    # Audit Timing Flag (24h recall window vs Release)
    if pd.isna(row["aud_ts"]):
        aud_flag = "NO_AUDIT"
    else:
        hours_to_audit = (
            row["aud_ts"] - row["rel_ts"]
        ).total_seconds() / 3600.0
        aud_flag = (
            f"WITHIN_24H ({hours_to_audit:.0f}h)"
            if hours_to_audit <= 24.0
            else f"LATE_GT_24H ({hours_to_audit:.0f}h)"
        )

    # ED-1 Eligibility Flag (for single-user completed cases)
    if fep_flag == "VIOLATED_SAME_USER":
        ed1_ok = (
            row["token_status"] == "PRE_PREP"
            and row["amount"] < 100000
            and row["vendor_days"] >= 180
            and not row["bank_change_7d"]
            and av_flag == "CLEAN_PASS"
            and mgr_flag in ["PRE_RELEASE_INDEP", "POST_REL_PRE_SETTLEMENT_INDEP"]
            and aud_flag.startswith("WITHIN_24H")
        )
        if ed1_ok:
            ed1_flag = "ED1_ELIGIBLE_FULL"
        elif (
            row["token_status"] == "POST_PREP"
            and row["amount"] < 100000
            and av_flag == "CLEAN_PASS"
            and mgr_flag == "PRE_RELEASE_INDEP"
        ):
            ed1_flag = "ED1_LATE_TOKEN_ONLY"
        else:
            ed1_flag = "ED1_INELIGIBLE"
    else:
        ed1_flag = "N/A"

    # Collusion / Repeat Pair Flag
    pair_flag = (
        "REPEATED_PAIR_SHARED_WS"
        if (row["shared_ws"] or row[" pair_30d"] > 10)
        else "NORMAL"
    )
    bank_flag = "RECENT_BANK_CHG_7D" if row["bank_change_7d"] else "STABLE_BANK"

    return pd.Series(
        [
            fep_flag,
            ed1_flag,
            av_flag,
            mgr_flag,
            aud_flag,
            bank_flag,
            pair_flag,
        ],
        index=[
            "FEP_Status",
            "ED1_Check",
            "AV2_Status",
            "MG4_Timing_Indep",
            "RA7_Audit_Window",
            "Bank_Risk",
            "Pair_Anomaly",
        ],
    )


evidence_table = summary.apply(evaluate_case_flags, axis=1)
