# 3. Consequences for performance analysis

- **G1 (genuine simultaneous batch):** If modelled as independent sequential activities, **waiting time** from `queue_arrival` to `start` would be interpreted correctly for the first item but seriously overestimated for the last (09:0008:58). **Service time** would appear as 3min per item, but the resource effectively handles four items in a single 3minute operation; consequently **resource utilisation** would be inflated (4×3min / 3min = 400% if overlap is ignored). Batchaware analysis corrects this: true utilisation is 100% during the 3minute batch window, and waiting time should be measured from arrival to batch start for all items.

- **G2 (start batching):** **Waiting time** from arrival to the recorded `start` reflects the delay until the group begins, which includes accumulation wait; it is a meaningful queue metric if the goal is to capture delay until work can start. However, individual **service times** are accurately reflected by varying completion times. The common start creates artificial overlap; a naïve concurrency view will show the resource as working on four items simultaneously, overstating instantaneous **utilisation** (the total work is serial, so true utilisation should be sum of service times divided by the period from first start to last complete). Bottleneck analysis will misrepresent the resource capacity unless the startbatching artefact is removed.

- **G3 (end batching):** **Waiting time** from arrival to start is not directly biased (starts are recorded individually). **Service times** are inflated because completion is postponed to 11:30; true processing times are shorter. This also inflates **utilisation** (the resource appears occupied until 11:30 for all items, while it may have been idle earlier). Throughput appears to be released in a burst at 11:30, distorting flowrate estimates. Operational commitment times are trustworthy, but performance analysis must use corrected completion timestamps.

- **G4 (sequential batching):** No evident bias. Metrics computed directly from the log are reliable, except that the resource never has idle time between items; if in reality microgaps exist, utilisation will be slightly overestimated, but with 1s precision this is negligible.

- **G5 (sharedaccount artifact):** When treated as a single resource, the overlapping intervals cause **waiting time** to appear shorter than real peranalyst queues (cases are apparently started sooner). **Service times** per case may be correct, but the resource appears to be working on multiple cases simultaneously. **Utilisation** will exceed 100% in any straightforward computation (sum of durations / clock time), falsely flagging an overloaded bottleneck. Conformance checking will show severe deviations from a serial resource rule. Correct analysis requires splitting the shared account by badge or modelling a resource pool.

- **G6 (bulk submission):** This pattern is the most dangerous for performance analysis. **Waiting time** from `queue_arrival` to `start` is artificially extended to endofshift (hours of apparent delay). **Service time** becomes zero (or nearzero) because `start = complete`. This combination can create a phantom bottleneck where the resource seems to process an arbitrary number of items in zero time after a huge queue. Metrics like throughput, utilisation, and waiting time are completely invalid. If such data cannot be corrected, it must be excluded from timebased metrics.

- **G7 (timestamp coarsening):** The 15minute rounding compresses or stretches all durations. **Waiting time** from a fineresolution `queue_arrival` to a coarsened `start` will be biased by up to 15min. **Service times** are forced into 15minute blocks, hiding true variability. **Utilisation** computed from the coarsened intervals will show the resource busy for a 15minute block that might contain five items; without knowing the actual individual durations, utilisation can be severely over or underestimated. Intervalcensored analysis (treating each timestamp as an interval) is appropriate.

- **G8 (queue accumulation after capacity loss):** The data faithfully reflect a real operational event. **Waiting time** includes the delay caused by the safety check; if that downtime is modelled as a separate activity (e.g., “safety check”), the waiting time can be correctly attributed. **Service times** are accurately captured by the sequential chain. The resource appears idle until 15:38, then fully utilised, which matches reality. The main bias risk is the undocumented clock skew between the safety system and the repair log; if not corrected, the cause of the queue may be misattributed.

# 5. Robustness and alternative explanations

**Trusting resource IDs vs. treating them as shared accounts**

- **G5** changes radically under different trust: if `analyst_pool` is taken as a single worker, the overlapping intervals must be interpreted as extreme multitasking. The observed concurrency then implies a single analyst handling four rootcause analyses in parallel, which is physically possible but improbable. This would change resource utilisation from “pool capacity” to “individual performance” and would mislead any queuing model that assumes serial work. With correct badgelevel identities, the concurrency is explained by multiple workers, enabling a normal pool analysis.  
- **G1, G2, G3, G4, G6, G7, G8** all use resources that are most likely individual (`RBT-7` cell, `T-B`, `T-C`, etc.), so treating them as shared accounts is not supported by context and would create false concurrency artefacts.

**Timestamps exact vs. intervalcensored by stated precision**

- **G7** (15min precision): If we treat timestamps as exact, we would compute a fixed 15minute service time and artificially sharp waiting times. In reality, the true start and complete lie somewhere within the quarterhour intervals. Analysing the data as intervalcensored (e.g., start  [14:00, 14:15), complete  (14:00, 14:15] or more complex rounding) gives bounds on waiting and service times, preventing false certainty.  
- **G6** (1min precision but likely bulk entry): Even if we model the precision as 1minute, the equality at 17:00 would still be exact to the minute interval, so censoring does not remove the zeroservice problem—the true cause is absent timestamps, not coarse precision.  
- **G2** (1min precision): The equal starts (10:00) might actually be spread over the minute if we had subminute data, but the groupbutton design ensures they remain identical regardless; intervalcensoring here would incorrectly introduce an artificial spread.

**At least three cases where the same temporal pattern supports multiple physical explanations**

1. **G1 – simultaneous vs. sequential batching under identical timestamps**  
   The log shows equal start and equal end for four items. The automated cell could process them all at once (simultaneous batch) or move them onebyone within the 3minute window and log the cycle start/end. The temporal signature alone cannot distinguish parallel from fast sequential processing; the fixturecapacity context tips the scale toward parallel.

2. **G5 – shared account vs. genuine multitasking**  
   Overlapping intervals can be produced either by several individuals sharing an account or by one person rapidly switching between tasks. The same pattern of overlapping active periods appears in both scenarios. Only external information (number of analysts, badge data) can resolve the ambiguity.

3. **G7 – timestamp coarsening vs. real simultaneous batch**  
   All starts and completions are forced to 14:00 and 14:15 by the 15minute rounding. These timestamps would look exactly the same whether the five measurements were taken as a genuine batch (e.g., all measured together in a 15minute slot) or if they were measured sequentially but collapsed by the coarsening. Distinguishing them requires raw, subquarterhour timestamps.

# 6. Data-collection redesign

Prioritised recommendations for future data collection:

1. **Separate execution timestamps from logging timestamps**  
   Record `start_execution` and `complete_execution` as the true process times, captured automatically when the activity begins and ends. The existing `start`/`complete` fields should reflect these physical moments, not when the transaction is written to the database.  
2. **Store raw timestamps with the highest available precision**  
   Capture times at millisecond or microsecond level (or at least 1 second) even if the user interface shows minutes. The true precision that can be trusted should be stored as metadata (e.g., `precision_effective_ms`), not just the nominal display resolution.  
3. **Integrate badgelevel identity and disallow shared accounts**  
   Every action must be linked to a unique, traceable user. Shared accounts (e.g., `analyst_pool`) must be replaced by individual badges, with the pool membership stored separately for capacity planning.  
4. **Log group/batch identifiers explicitly**  
   When items are processed as a batch—whether in a fixture, on a single button press, or in a bulk submission—emit a batch ID or a group start/end event. This removes the ambiguity between temporal collocation and physical grouping.  
5. **Capture pause, resume, and downtime events**  
   Mandatory events such as “safety check” should appear as activities in the event log with their own start and complete timestamps. This avoids unexplained queue buildups and allows capacityloss modelling.  
6. **Synchronise clocks across all data sources**  
   Implement NTP or equivalent time synchronisation and log the clock source and last synchronisation offset. Crosssystem events (queue arrival vs. processing start) will then be comparable without manual correction.  
7. **Record timestamp precision and truncation/rounding rules**  
   For legacy systems that round timestamps (e.g., MES quarterhour rounding), store both the original timestamp (if possible) and document the exact rounding method (floor/ceil/round, to what boundary).  
8. **Standardise lifecycle transition logging**  
   Use complete lifecycle: `schedule, assign, start, suspend, resume, complete, abort`. Even if not all are used initially, the schema should support them, and missing transitions should be flagged, not silently coalesced.
