```python
def canonical_bse_signature(execution):
    # execution: list of events with activity, objects (type, id, is_external), qualifiers
    # map local ids per type to canonical indices
    id_maps = {}
    canon_events = []
    for ev in execution:
        # sort objects by (type, is_external, local_id)
        objs = ev['objects']
        # assign canonical ids
        canon_objs = []
        for o in sorted(objs, key=lambda x: (x['type'], x['is_external'], x['id'])):
            key = (o['type'], o['is_external'])
            if key not in id_maps: id_maps[key] = {}
            if o['id'] not in id_maps[key]:
                id_maps[key][o['id']] = len(id_maps[key]) + 1
            canon_objs.append((o['type'], o['is_external'], id_maps[key][o['id']]))
        # signature for event
        ev_sig = (ev['activity'], tuple(sorted(canon_objs)), tuple(sorted(ev.get('qualifiers', []))))
        canon_events.append(ev_sig)
    return tuple(canon_events)
```

## 1. Equivalence design space

We define three primary equivalence relations, plus a brief note on a fourth, to navigate the structural and semantic spectrum of the eight executions.

**1. Activity-sequence equivalence (ASE)**
- *Definition*: Two executions are ASE-equivalent if the projection of events onto the lead object type (`Order`) yields identical totally ordered sequences of activity labels. Formally, let $\sigma_E = \langle a_1, a_2, \dots, a_n \rangle$ be the activity label sequence for execution $E$. Then $E \sim_{ASE} E'$ iff $\sigma_E = \sigma_{E'}$.
- *Invariants preserved*: The exact ordering and multiplicity of activity types.
- *Information discarded*: All object identifiers, object types, E2O incidences, external flags, and O2O qualifiers.
- *Properties*: Reflexive, symmetric, and transitive (it is exact string equality on label sequences).
- *Concurrency*: If events share timestamps, they are sorted by activity label lexicographically to produce a canonical total order; alternatively, one could require isomorphic labeled posets.

**2. Typed structural equivalence under identifier renaming (TSE)**
- *Definition*: Two executions are TSE-equivalent if there exists a bijection renaming local object identifiers such that (a) the activity sequence matches, and (b) for every event, the multiset of involved object *types* and their per-event cardinalities matches, ignoring exact identifier values. For this study, we explicitly *discard* external objects (`EXT` prefix) from the event incidence to test whether the local execution topology is identical without cross-order context.
- *Invariants preserved*: Activity sequence, E2O object types, and local per-event object multiplicities (e.g., two `Item` objects in a `Pack`).
- *Information discarded*: Local identifier syntax, external-object flags (and the objects themselves), and O2O qualifiers such as `removed_before_dispatch`.
- *Properties*: Reflexive, symmetric, and transitive (it is isomorphism of typed event templates modulo renaming).
- *Concurrency*: Handled by comparing labeled posets of typed templates; total-order projections are used for the given data.

**3. Business-semantic equivalence (BSE) — preferred**
- *Definition*: Two executions are BSE-equivalent if they are TSE-equivalent **and** the external-object flags are retained in E2O incidence, **and** O2O qualifiers and lifecycle motifs (e.g., `Return Item`, `removed_before_dispatch`) are matched. This is graph isomorphism of the annotated object-centric graph modulo local ID renaming.
- *Invariants preserved*: Everything in TSE plus external sharing, qualifier semantics, and reverse-logistics motifs.
- *Information discarded*: Only the syntactic values of local identifiers.
- *Properties*: Reflexive, symmetric, and transitive.
- *Concurrency*: Same as TSE, but qualifiers annotate edges/nodes in the poset.

**4. Qualified lifecycle equivalence (QLE – optional finer relation)**
A fourth relation could distinguish partial vs. complete settlement qualifiers on payments (as in X4) from single-shot settlement. BSE as defined above already separates X4 from X1 due to payment multiplicity, but QLE would force explicit qualifier-label matching even when multiplicities coincide.

## 2. Canonical signatures

For the preferred BSE relation, we define a reproducible canonical-signature scheme. It relabels local identifiers per type by first appearance, retains external flags, counts multiplicities, and appends sorted qualifiers.

```python
def canonical_bse_signature(events):
    # events: list of dicts: {'act': str, 'objs': list of (type, id, is_ext), 'quals': list of str}
    id_maps = {}      # (type, is_ext) -> {raw_id: canon_idx}
    canon_events = []
    for ev in events:
        canon_objs = []
        for (otype, oid, is_ext) in sorted(ev['objs'], key=lambda x: (x[0], x[1], x[2])):
            key = (otype, is_ext)
            id_maps.setdefault(key, {})
            if oid not in id_maps[key]:
                id_maps[key][oid] = len(id_maps[key]) + 1
            canon_objs.append((otype, is_ext, id_maps[key][oid]))
        ev_sig = (
            ev['act'],
            tuple(sorted(canon_objs)),
            tuple(sorted(ev.get('quals', [])))
        )
        canon_events.append(ev_sig)
    return tuple(canon_events)
```
This signature is invariant under local renaming, preserves external flags and qualifiers, and is fully reproducible.

## 4. Cluster interpretations

**B1 – Isolated Standard (X1, X2)**
- *Signature*: Single `Order` with two `Item`s packed into one `Package`, one `Dispatch`, one `Invoice`, one `Payment`. No external objects, no qualifiers.
- *Business behavior*: Classic single-parcel mail-order fulfillment with clean settlement.
- *Risks/Opportunities*: Low risk; prime candidate for automation and benchmarking.
- *Poor flattening*: None—traditional flat tables represent this well, which is why it masks other clusters if used exclusively.
- *Stability*: Fully stable under data repair; renaming never alters semantics.

**B2 – Split Fulfillment (X3, X4)**
- *Signature*: Multiple `Pack` events for one `Order`; X3 consolidates into one `Delivery`, X4 splits into two `Delivery` events and two `Payment` events (partial settlement).
- *Business behavior*: Order split into multiple shipments, either consolidated or sequentially dispatched.
- *Risks/Opportunities*: Opportunity for partial-delivery KPIs; risk of invoice/payment reconciliation errors (especially X4).
- *Poor flattening*: A flat row-per-package model duplicates invoice/payment data, creating double-counting if not aggregated.
- *Stability*: Stable, though X4’s partial-payment qualifier could be lost in naive repairs, merging it toward X3.

**B3 – Cross-Object Shared (X5, X6)**
- *Signature*: Includes `EXT` flagged objects in logistics (X5) or financial (X6) events.
- *Business behavior*: Collaborative fulfillment (shared consignment) or joint billing across orders.
- *Risks/Opportunities*: Revenue leakage or mis-attribution if external linkages are ignored; opportunity for cross-sell logistics optimization.
- *Poor flattening*: Traditional flattening drops `EXT` rows, making X5/X6 indistinguishable from B1 and hiding inter-order dependencies.
- *Stability*: Unstable if external objects are pruned during data cleaning; then collapses into B1.

**B4 – Item Replacement (X7)**
- *Signature*: `Pack` includes two items, but `Dispatch` explicitly carries one `Item` and an O2O qualifier `removed_before_dispatch` links the package to the other item.
- *Business behavior*: Substitution or removal of an item prior to shipment while reusing the same package ID.
- *Risks/Opportunities*: Audit/compliance risk; customer trust if silent substitution occurs.
- *Poor flattening*: Looks identical to B1 in activity labels and local counts, completely hiding the qualifier.
- *Stability*: Highly unstable under qualifier loss; degrades directly to B1.

**B5 – Return & Repack (X8)**
- *Signature*: Forward `Pack`/`Dispatch`, then `Return Item`, `Inspect Return`, second `Pack`/`Dispatch` with repack qualifier.
- *Business behavior*: Post-shipment return, inspection, and reshipment of a replacement item.
- *Risks/Opportunities*: Inventory shrinkage risk; opportunity for reverse-logistics optimization.
- *Poor flattening*: Linear flat logs either drop the return cycle or create confusing duplicate order rows.
- *Stability*: Stable; the distinct activities (`Return`, `Inspect`) survive most repairs.

## 5. Borderline cases

- **X1 vs X2**: ASE, TSE, and BSE all treat them as equivalent. However, a defensible *attribute-sequence* equivalence that encodes item-add order would separate them because X1 adds `I11` then `I12`, while X2 reverses the order. We reject that as it conflates arbitrary local IDs with semantics.
- **X1 vs X5**: ASE groups them (identical label sequence). TSE (with EXT dropped) also groups them. BSE separates them because X5’s `Pack` and `Dispatch` carry `EXT` objects, meaning the logistics execution is not isolated. A business analyst caring about order isolation will disagree with the ASE view.
- **X1 vs X6**: Same as above; ASE/TSE group, BSE separates due to shared `Invoice`. A financial auditor (BSE) sees a commingled invoice; an operations dashboard (ASE) sees a standard order.
- **X1 vs X7**: ASE groups (labels match). TSE separates because `Dispatch` in X7 includes an `Item` type in E2O incidence. BSE further separates due to the `removed_before_dispatch` qualifier. A data-modeler using strict type templates diverges from ASE.
- **X3 vs X4**: ASE separates (different pack/dispatch interleaving). TSE separates (1 vs 2 deliveries, 1 vs 2 payments). BSE groups them as "Split Fulfillment" but notes sub-variants. A coarse business segmentation groups them; a logistical process-miner separates them.
- **X4 vs X8**: ASE and TSE clearly separate (X8 has return motif). Yet both have multiple packs/dispatches. A naive *multiplicity-only* structural view might cluster them as "multi-package", but BSE correctly separates forward-split (X4) from reverse-logistics (X8).

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` partitions an OCEL into sub-logs where each cluster contains executions with identical object-centric graph structure, typically keyed by tuples of `(activity, frozenset of (object_id, object_type))` per event and connected components.

- *Exact information preserved*: Raw object IDs, types, and event-activity labels. It does not natively understand O2O qualifiers unless encoded as event attributes.
- *Raw IDs too fine*: Because X1 uses `O1` and X2 uses `O2`, the raw key structure treats them as non-equivalent, producing overly fine clusters.
- *Canonicalization*: We must first relabel local IDs (as in Section 2) or inject a canonical ID map into object attributes before calling the function. Post-processing then merges clusters whose canonical signatures match.
- *Exact vs coarse*: Exact equivalence is preferable for conformance checking (e.g., detecting deviations from a reference model). Coarser business clustering is better for dashboarding.
- *max_objs / large connected executions*: `max_objs` limits the size of connected object graphs to avoid memory explosion. In X5, `EXT-OA` could pull an entire external order’s graph, bloating the component. We should bound `max_objs` or pre-filter external edges.

```python
import pm4py
from pm4py.objects.ocel.util import clustering

# Assume 'ocel' is loaded; first canonicalize IDs by adding attr 'canon_id'
for obj in ocel.objects:
    ocel.objects[obj]['canon_id'] = f"{ocel.objects[obj]['ocel:type']}_{hash(obj)%1000}"

# Cluster using exact equivalence on canonical graph
clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=500)

# Custom aggregation: merge clusters by BSE signature
agg = {}
for c in clusters:
    sig = canonical_bse_signature(c)
    agg.setdefault(sig, []).append(c)
print(f"Merged {len(clusters)} raw clusters into {len(agg)} BSE clusters")
```

## 7. Robustness analysis

- *Ignore all O2O qualifiers*: X7 loses `removed_before_dispatch`; its BSE signature collapses to match B1. The hidden substitution becomes invisible, demonstrating qualifier criticality.
- *Ignore external objects*: X5 and X6 lose `EXT` incidence; their BSE signatures collapse into B1. Cross-order dependencies vanish, making the log appear as isolated baselines.
- *Collapse repeated same-label events*: In X4, the two `Record Payment` events fuse into one, and the two `Pack`/`Dispatch` pairs may fuse, making its ASE/TSE signature resemble X1. This incorrectly merges X4 into A1/T1.
- *Partial order instead of total*: If `Pack` events are treated as concurrent, X3 (`P,P,D`) and X4 (`P,D,P,D`) both satisfy "all packs precede their dispatches" as a poset, potentially merging them in a relaxed TSE.
- *Payment multiplicity as amount*: If X4’s two payments are summed into one event with `amount=total`, the structural multiplicity difference disappears; X4 looks like X1 under TSE, hiding partial-settlement behavior.

## 8. Limitations and recommendation

No single equivalence notion fits all analytics needs:

- **Compliance monitoring**: Use **BSE (fine)**. It preserves qualifiers (X7) and external sharing (X5/X6), ensuring audits catch silent substitutions and joint billing.
- **Operational segmentation**: Use **coarse BSE (B1–B5)**. Grouping split fulfillments (B2) and returns (B5) supports logistics planning without drowning in ID-level noise.
- **Root-cause analysis**: Use **BSE with qualifiers** (or QLE). Distinguishing partial payments and repacks is essential to trace defects.
- **Descriptive reporting**: Use **ASE or TSE**. Executives need simple activity funnel counts; ASE’s `C,A,A,P,D,I,R` metric is sufficient and stable.

The eight executions demonstrate that activity labels alone (ASE) mask external dependencies and qualifiers; typed structure (TSE) masks cross-order sharing; only business-semantic equivalence captures the full operational reality, yet it is too detailed for high-level reporting. Hence, a layered equivalence strategy is recommended.
