## 2. Process-model consistency checks

A credible validation suite should combine lineage checks, process-model conformance, and explanation-specific admissibility tests.

**Point-in-time availability tests**
- Maintain a feature registry with lineage metadata: source event IDs, aggregation window, event time, valid-from/valid-to, extraction time, and prediction time.
- For every feature, assert `max_source_event_time <= t0` except where a documented tolerance exists.
- For aggregates, assert the aggregation window ends at or before `t0`.
- For mutable features, require a versioned value as of `t0`; if only “current” values exist, fail the feature.
- For `queue_length_at_t0`, require snapshot time at or before `t0`, or explicitly test sensitivity to the ±5 minute tolerance.
- For `same_day_document_count_snapshot`, recompute using only document upload timestamps `<= t0`.
- For `prior_claim_count_before_t0`, recompute using `claim_created_at < t0` and exclude the current claim.

**Activity-order feasibility tests**
- Encode the normative process as declarative constraints, for example:
  - `Claim Registered` precedes first `Coverage Check Completed`.
  - After first `Coverage Check Completed`, allowed next activities include `Damage Assessment Completed`, `Documents Requested`, or `Fraud Investigation Opened` if a trigger exists.
  - Evidence cycles require `Documents Requested -> Documents Received -> Documents Validated`; loops are allowed.
  - `Damage Assessment Completed` precedes first `Settlement Decision Recorded`.
  - `Appeal` is allowed only after `Partial` or `Deny`.
  - A second `Settlement Decision Recorded` is allowed only after an `Appeal`.
  - `Claim Closed` follows a final decision or withdrawal.
- Replay only the prefix at `t0` through the normative model. Reject explanations that require activities not present in the prefix.
- Classify referenced activities as:
  - **occurred at `t0`**: admissible as observed evidence.
  - **enabled at `t0`**: allowed by the process but not yet observed; may inform priors, not observed contributions.
  - **future-possible**: can occur in some valid continuation; not admissible as an explanation of `t0` evidence.
  - **impossible**: violates precedence or occurs after closure; reject and investigate data error.
  - **ambiguous**: same timestamp and no reliable sequence index; do not infer order.

**Same-timestamp ambiguity tests**
- If two events have identical or near-identical timestamps and no reliable sequence index, treat them as concurrent/partially ordered.
- Do not create directed DFG edges from ambiguous same-timestamp pairs.
- Test whether at least one linearization satisfies the normative model; if not, flag a data-quality or process-model violation.
- Apply this especially to `Claim Closed` and `Damage Assessment Completed`, and to `Coverage Check Completed` followed by `Fraud Investigation Opened`.

**Complete-trace feature detection**
- Flag any feature whose lineage includes closure, final decision, last resource, total duration, full variant, appeal anywhere, or total document requests.
- Features such as `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, `final_handler_team`, and `last_resource_role` must not be presented as early warnings unless replaced by prefix-only versions.

**Explanation-specific checks**
- Map each SHAP feature to its source events and valid time.
- Reject local explanations that cite future or impossible activities.
- Sequence-pattern explanations must be generated from prefix-only patterns or explicitly labeled as post-hoc outcome signatures.
- Repeated `Settlement Decision Recorded` events are semantically legitimate only after `Appeal` following `Partial` or `Deny`; otherwise flag as data error.

**Role and limits of process-mining checks**
- Alignment checks can measure conformance but can be misled by same-timestamp ordering or by aligning future events if the prefix is not enforced.
- Footprint checks show which activities occur but not when they become available.
- Prefix checks are essential for `t0` validity but do not by themselves prove feature lineage.
- DFG edges are descriptive; a frequent DFG edge is not automatically a normative rule and may reflect ingestion order, concurrency, loops, or outcome leakage.
- Declarative constraints are useful for feasibility but require complete process rules and reliable event ordering.

## 5. Recommendations for explanation validation

1. **P0: Freeze and quarantine current explanations**
   - Mark current global and local explanations as post-hoc unless lineage proves `t0` availability.
   - Remove or quarantine critical leaked features: `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, `last_resource_role`, and `risk_score_current`.

2. **P0: Rebuild a point-in-time feature store**
   - Store `event_time`, `valid_from`, `valid_to`, `extraction_time`, source event IDs, aggregation window, and feature version.
   - Require as-of joins at `t0`.
   - Emit the feature timestamp with every SHAP contribution so explanations can be audited.
   - Treat mutable features as invalid unless a version at `t0` exists.

3. **P0: Recompute prefix-only features and rerun explanations**
   - Generate features only from events at or before first `Coverage Check Completed`.
   - Replace complete-trace features with prefix-derived equivalents:
     - `team_at_t0` instead of `final_handler_team`.
     - `documents_received_before_t0` instead of `num_document_requests_total`.
     - `risk_score_at_t0` instead of `risk_score_current`.
     - `role_at_t0` instead of `last_resource_role`.
     - `documents_uploaded_at_or_before_t0` instead of nightly same-day snapshot.
   - Recompute local SHAP values after removing leakage.

4. **P1: Add process-conformance and admissibility tests**
   - Implement prefix replay against the normative process model.
   - Classify every referenced activity as occurred, enabled, future-possible, impossible, or ambiguous.
   - Use partial-order logic for same-timestamp events unless a reliable sequence index exists.
   - Validate repeated `Settlement Decision Recorded` events only after `Appeal` following `Partial` or `Deny`.
   - Block explanations that cite future or impossible activities.

5. **P1: Recalibrate and retrain after leakage removal**
   - Retrain using only admissible `t0` features.
   - Evaluate discrimination, calibration, and breach-rate estimates separately by region, channel, queue bucket, and calendar period.
   - Accept that performance may drop; do not recover performance with outcome proxies or future path features.
   - Compare old and new predictions to quantify how much apparent performance was leakage.

6. **P1: Improve explanation stability and interpretability**
   - Test SHAP stability across model seeds, correlated feature groups, and time windows.
   - Group highly correlated proxies and report grouped importance rather than unstable individual attributions.
   - Require local explanations to include admissibility status and feature timestamps.
   - Provide counterfactual or intervention-style explanations only for features that are operationally manipulable, such as queue routing or staffing, not for immutable claimant attributes.

7. **P2: Conduct proxy and fairness analysis**
   - Review `claimant_region`, `claimant_channel`, `prior_claim_count_before_t0`, and any language or socioeconomic proxies.
   - Measure disparate impact and false-positive/false-negative rates across protected or sensitive groups.
   - Decompose proxies into operational mechanisms such as repair-network coverage, documentation burden, or service availability.
   - Require human review and recourse for adverse decisions influenced by proxy features.

8. **P2: Monitor schema, process, and drift continuously**
   - Alert on missing sequence indices, identical timestamps, new activities, changed activity labels, or new loops.
   - Monitor queue snapshot tolerance, document snapshot timing, feature valid-time coverage, and extraction-date joins.
   - Track calendar, policy, holiday, and staffing changes that may make `calendar_week` or congestion features unstable.
   - Monitor explanation leakage indicators, such as future activities appearing in local SHAP values or complete-trace features entering production.
