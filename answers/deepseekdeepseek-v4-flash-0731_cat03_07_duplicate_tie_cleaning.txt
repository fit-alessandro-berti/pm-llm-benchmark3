## 1. Duplicate-handling decision tree

Walk each candidate pair/group through the tree until one terminal decision is reached.

```
1. Are the rows identical in all technical fields:
   same source, same source_event_key, same timestamp, same payload_hash,
   same related-object set, and no differing business attribute?

    Exact technical duplicate
     Terminal: DROP all but one canonical row.
     Preserve the dropped source IDs in provenance.

2. Does an external reconciliation or stable business identifier prove that
   two rows are observations of the same physical occurrence, even though
   payloads/attributes differ?

   Examples: e03/e04 = same scan per reconciliation report;
             e11/e16 = same invoice issuance per invoice number V1.

    Same physical event observed by multiple systems
     Terminal: MERGE attributes and relations into one canonical event.
     Do not drop one source silently.
     Preserve original source_event_key, source, payload_hash, and original timestamp.

3. Is one event a source-system summary/status update derived from a detailed event,
   with a subset or same relation set, or with no discriminating object?

   Examples: e06/e07; e13/e15; e14/e15.

    Summary event derived from a detailed event
     Terminal: CONSERVATIVELY RETAIN BOTH with refined labels/qualifiers.
     Do not merge by default.
     A separate evidence-based scenario may merge them only with an explicit merge rule.

4. Do two events share the same harmonized activity label and timestamp, but their
   original source semantics are different?

   Example: e08 = warehouse release; e09 = carrier acceptance; both were mapped to
   "Dispatch Package".

    Harmonization collision between semantically distinct source activities
     Terminal: RETAIN BOTH with refined labels/qualifiers.
     Do not merge because they share all modeled objects.

5. Do two events share the same harmonized activity label and timestamp, and share
   some objects, but differ on a discriminating object?

   Examples: e03/e05 differ by item I1 vs I2;
             e13/e14 differ by payment M1 vs M2.

    Concurrent same-label events involving different objects
     Terminal: RETAIN BOTH with refined labels/qualifiers.
     Never union their relation sets.

6. Any remaining candidate with no verified rule, no clear object discriminator, or
   contradictory evidence.

    Unresolved candidate
     Terminal: QUARANTINE FOR REVIEW.
     Do not merge, drop, or relabel automatically.
```

## 3. Timestamp-tie ordering rules

Original timestamps remain the business timestamps. Adjusted timestamps are only deterministic ordering keys.

Semantic rules, applied first:

1. **Domain constraints**
   - Pick events must occur before packing the same package.
   - Packing must occur before dispatch/handover.
   - Warehouse release occurs before carrier acceptance; carrier acceptance occurs before handover.
   - Authorize Payment (M1) must precede Capture Payment (M1).
   - Payment messages must precede the ERP payment summary.
   - Invoice issuance must precede payment events on the same invoice.
   - Dispatch/handover must precede delivery confirmation.

2. **Within-source sequence**
   - `source_seq` is meaningful only within one source.
   - Same source, same timestamp: ascending `source_seq`.
   - For example, in SCANNER, e04 (`S-901`, seq 551) precedes e05 (`S-902`, seq 552).
   - In CARRIER, e09 (`C-400`, seq 1) precedes e10 (`C-401`, seq 2).
   - In PSP, e12 (`P-700`, seq 400) precedes e13 (`P-701`, seq 401) and e14 (`P-702`, seq 402).

3. **Lifecycle constraints on shared objects**
   - Use object lifecycle only when it is known: O1, P1, D1, V1, M1, M2.
   - Example: V1 must exist before payments referencing V1.
   - M1 must be authorized before captured.
   - P1 must be packed before dispatched.

4. **Source-specific semantics**
   - WMS detailed events precede ERP summary events generated from WMS messages: e06 before e07.
   - PSP capture events precede ERP payment summary: e13/e14 before e15.
   - Carrier acceptance precedes handover: e09 before e10.

Merely deterministic rules:

5. **Ingestion time is not business order**
   - `ingested_at` may be used only as a technical trace field, never as the primary business ordering rule.
   - Across sources, ingestion order is unreliable.

6. **Stable fallback order**
   - After semantic constraints, if a tie remains, order by `eid` lexicographically.
   - This is deterministic but does not assert physical truth.

Adding microseconds before deciding semantic order encodes a false story because it makes arbitrary tie-breakers look like measured timestamps. For example, if e13/e14/e15 are all at `12:00:00`, adding synthetic microseconds before deciding they are distinct makes it look like M2 capture followed M1 capture in real time. Downstream algorithms may then infer a false causal edge and calculate fake durations. The correct procedure is: decide duplicates and semantics first, then add a deterministic order key, while storing `original_timestamp` unchanged.

Intended orders:

- **e03–e07 at 10:00**  
  `e03/e04 -> e05 -> e06 -> e07`  
  Alternative admissible order: e03/e04 and e05 are concurrent. If scanner `source_seq` is not treated as a business-order proof, they may be swapped. Still, e06/e07 must follow both picks, and e06 must precede the ERP summary e07.

- **e08–e10 at 10:15**  
  `e08 -> e09 -> e10`  
  e08 is warehouse release, e09 is carrier acceptance, e10 is handover. This order is semantically intended.

- **e11–e16 at 12:00 after duplicate decisions**  
  `e11 (merged with e16) -> e12 -> e13 -> e14 -> e15`  
  Alternative admissible order: e13 and e14 are concurrent with respect to business dependencies. PSP `source_seq` orders them in the source stream, but that order is source-internal and should not be interpreted as a dependency between M1 and M2.

import copy
import warnings
import pandas as pd
import pm4py


def normalize_ocel(ocel):
    """Deep-copy and normalize an OCEL so raw is never mutated."""
    ocel = copy.deepcopy(ocel)
    ev = ocel.events.copy()

    if "eid" in ev.columns and "ocel:eid" not in ev.columns:
        ev = ev.rename(columns={"eid": "ocel:eid"})
    if "timestamp" in ev.columns and "ocel:timestamp" not in ev.columns:
        ev = ev.rename(columns={"timestamp": "ocel:timestamp"})
    if "activity" in ev.columns and "ocel:activity" not in ev.columns:
        ev = ev.rename(columns={"activity": "ocel:activity"})

    if "original_activity" not in ev.columns:
        ev["original_activity"] = ev["ocel:activity"]
    if "original_timestamp" not in ev.columns:
        ev["original_timestamp"] = ev["ocel:timestamp"]

    if not hasattr(ocel, "relations") or ocel.relations is None:
        if "related_objects" in ev.columns:
            rows = []
            for _, r in ev.iterrows():
                objs = r["related_objects"]
                if isinstance(objs, str):
                    objs = [x.strip() for x in objs.split(",") if x.strip()]
                for o in objs:
                    rows.append({
                        "ocel:eid": r["ocel:eid"],
                        "ocel:oid": o,
                        "ocel:qualifier": "related",
                        "ocel:timestamp": r["ocel:timestamp"],
                    })
            ocel.relations = pd.DataFrame(rows)

    ocel.events = ev
    return ocel


def validate_referential_integrity(ocel):
    ev_ids = set(ocel.events["ocel:eid"])
    rel = ocel.relations
    if rel is not None and len(rel):
        assert set(rel["ocel:eid"]).issubset(ev_ids), "relations refer to missing event"
        if hasattr(ocel, "objects") and ocel.objects is not None and "ocel:oid" in ocel.objects.columns:
            assert set(rel["ocel:oid"]).issubset(set(ocel.objects["ocel:oid"])), "relations refer to missing object"
    print(
        "Referential integrity OK; events=%d relations=%d"
        % (len(ocel.events), 0 if rel is None else len(rel))
    )


def candidate_duplicate_groups(ocel):
    ev = ocel.events.copy()
    ev["_cand"] = ev["ocel:activity"].astype(str) + "|" + ev["ocel:timestamp"].astype(str)
    groups = ev.groupby("_cand")["ocel:eid"].agg(list)
    groups = groups[groups.apply(len) > 1]
    print("Pre-check candidate groups by activity+timestamp:")
    for k, v in groups.items():
        print(" ", k, "->", v)
    return groups


def verified_pair_merge(ocel, keep_eid, merge_eid, rule):
    """Merge two verified duplicate events into keep_eid, preserving all provenance."""
    ocel = copy.deepcopy(ocel)
    ev = ocel.events
    rel = ocel.relations

    if "ocel:qualifier" not in rel.columns:
        rel["ocel:qualifier"] = "related"

    keep_idx = ev.index[ev["ocel:eid"] == keep_eid][0]
    merge_idx = ev.index[ev["ocel:eid"] == merge_eid][0]

    keep = ev.loc[keep_idx].to_dict()
    merge = ev.loc[merge_idx].to_dict()
    new = dict(keep)

    new["merged_from_eids"] = [keep_eid, merge_eid]
    new["merge_rule"] = rule

    if "source_event_key" in keep and "source_event_key" in merge:
        new["source_event_key"] = [keep["source_event_key"], merge["source_event_key"]]
    if "source" in keep and "source" in merge:
        new["source"] = [keep["source"], merge["source"]]

    structural = {
        "ocel:eid", "ocel:activity", "ocel:timestamp",
        "original_activity", "original_timestamp",
        "source_event_key", "source", "source_seq",
        "ingested_at", "payload_hash",
        "merged_from_eids", "merge_rule", "related_objects",
    }

    for col, val in merge.items():
        if col in structural:
            continue
        if col not in keep or keep[col] != val:
            src = str(merge.get("source", "source2"))
            new[f"{src}__{col}"] = val

    rel_keep = rel[rel["ocel:eid"] == keep_eid].copy()
    rel_merge = rel[rel["ocel:eid"] == merge_eid].copy()
    if len(rel_merge):
        rel_merge["ocel:eid"] = keep_eid

    combined = pd.concat([rel_keep, rel_merge], ignore_index=True)
    if len(combined):
        combined = combined.drop_duplicates(
            subset=["ocel:eid", "ocel:oid", "ocel:qualifier"], keep="first"
        )

    rel = rel[~rel["ocel:eid"].isin([keep_eid, merge_eid])]
    if len(combined):
        rel = pd.concat([rel, combined], ignore_index=True)
    ocel.relations = rel

    if "related_objects" in keep:
        obj_ids = rel[rel["ocel:eid"] == keep_eid]["ocel:oid"].unique().tolist()
        new["related_objects"] = obj_ids

    ev = ev.drop(index=[keep_idx, merge_idx])
    ev = pd.concat([ev, pd.DataFrame([new])], ignore_index=True)
    ocel.events = ev

    validate_referential_integrity(ocel)
    return ocel


def refine_activity(ocel, eid, new_activity):
    ocel = copy.deepcopy(ocel)
    if "original_activity" not in ocel.events.columns:
        ocel.events["original_activity"] = ocel.events["ocel:activity"]
    if "refined_activity" not in ocel.events.columns:
        ocel.events["refined_activity"] = ocel.events["ocel:activity"]
    ocel.events.loc[ocel.events["ocel:eid"] == eid, "refined_activity"] = new_activity
    ocel.events.loc[ocel.events["ocel:eid"] == eid, "ocel:activity"] = new_activity
    return ocel


def assign_order_key(ocel):
    """Deterministic order: original timestamp, then semantic tie_rank, then eid."""
    ev = ocel.events.copy()

    tie_rank = {
        "e03": 0, "e05": 1, "e06": 2, "e07": 3,
        "e08": 0, "e09": 1, "e10": 2,
        "e11": 0, "e12": 1, "e13": 2, "e14": 3, "e15": 4,
    }

    ev["tie_rank"] = ev["ocel:eid"].map(tie_rank).fillna(0).astype(int)
    ev["order_key"] = (
        ev["ocel:timestamp"].astype("int64").map(lambda x: f"{x:020d}")
        + "_"
        + ev["tie_rank"].map(lambda x: f"{x:04d}")
        + "_"
        + ev["ocel:eid"].astype(str).str.zfill(10)
    )
    ocel.events = ev
    return ocel

## 7. Sensitivity analysis

| Dataset | Event count | E2O relation count | Dominant changes |
|---|---:|---:|---|
| Raw | 17 | 44 | Duplicate e03/e04 and e11/e16 remain; e08/e09 and e13/e14/e15 share identical labels; false self-loops and inflated frequencies appear. |
| Conservative | 15 | 39 | Verified duplicates merged; distinct object labels and source-specific labels preserved; no same-label `Dispatch->Dispatch` or `Capture->Capture` self-loop from harmonization. |
| Evidence-based merging | 14 | 37 | e06/e07 merged; packing abstraction edge removed; still preserves I1/I2 and M1/M2 separately. |
| Aggressive library merge | 10 | 28 | Distinct picks, carrier acceptance, payment details, and ERP summary collapsed; M1 and M2 co-occur in one event. |

Concrete edges/patterns whose interpretation changes:

1. `Validate Order -> Pick Item` frequency changes: raw = 3; conservative/evidence = 2; aggressive = 1.
2. `Pick Item -> Pack Package` frequency is inflated by the duplicate e03/e04 in raw and collapsed in aggressive.
3. `Dispatch Package -> Dispatch Package` self-loop appears in raw; conservative replaces it with `Dispatch Package (warehouse release) -> Dispatch Package (carrier acceptance)`.
4. `Pack Package (WMS detail) -> Pack Package (ERP summary)` is present in conservative, but disappears in the evidence-based scenario when e06/e07 are merged.
5. `Authorize Payment -> Capture Payment` is correct for M1 in raw and conservative, but aggressive merging makes it appear also for M2.
6. `Capture Payment -> Capture Payment` self-loop appears in raw; conservative replaces it with `Capture Payment (M1) -> Capture Payment (M2) -> Capture Payment (ERP summary)`, where the M1->M2 edge is a deterministic tie artifact, not a business dependency.
7. OTG `Payment-Payment` co-occurrence appears only in the aggressive scenario because M1 and M2 are forced into the same event.

Performance measurements should always be computed from `original_timestamp`, not from the synthetic adjusted timestamp. Otherwise zero-time ties become fake durations and true concurrency is hidden.

## 8. Audit trail and reversibility

The provenance schema should contain:

- `canonical_eid`
- `source_event_ids`
- `source_event_keys`
- `source_systems`
- `merge_rule`
- `reviewer_or_rule_version`
- `original_activity`
- `refined_activity`
- `original_timestamp`
- `adjusted_timestamp`
- `attributes_retained` (JSON, source-prefixed)
- `discarded_conflicts` (JSON)
- `confidence`
- `reason`

To reconstruct the raw view, an analyst should:

1. Start from the immutable raw event and relation tables.
2. Expand every `canonical_eid` using `source_event_ids`.
3. Restore each source event's `original_activity`, `original_timestamp`, `source`, `source_event_key`, and source-prefixed attributes.
4. Restore original relations from the raw relation table rather than from the merged union.

No transformation should overwrite raw tables. Merging should always append provenance.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments**  
   Merging e13/e14 because both are `Capture Payment` at the same timestamp.  
   Safeguard: never merge events whose related object sets differ by a Payment object.

2. **Converting abstraction-level updates into false rework**  
   Keeping e06/e07 with identical labels creates duplicate `Pack Package` events.  
   Safeguard: refine labels or explicitly model abstraction levels.

3. **Ordering by ingestion time**  
   `ingested_at` is not business order.  
   Safeguard: use domain constraints, lifecycle constraints, and within-source sequence first.

4. **Treating shared objects as proof of duplication**  
   e13/e14 share O1 and V1 but are different payments.  
   Safeguard: require full relation-set comparison, not merely common objects.

5. **Unioning incompatible E2O relations**  
   Merging e13 with e15 would attach M1 to an ERP summary that never observed M1.  
   Safeguard: do not union summary and detail relation sets without an explicit rule.

6. **Changing durations through synthetic microseconds**  
   Adding microseconds before semantic ordering invents fake timestamps.  
   Safeguard: use `original_timestamp` for duration calculations; treat adjusted timestamps only as a deterministic order.

7. **Losing source-authoritative attributes**  
   Dropping e04 or e16 entirely loses scanner/billing attributes.  
   Safeguard: merge attributes with source prefixes and preserve all source IDs.

8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups**  
   `ocel_drop_duplicates` or `ocel_merge_duplicates` can collapse e08/e09 if labels are still identical.  
   Safeguard: run a pre-check, refine collision labels, and use verified-pair merges for uncertain cases.

9. **Refining labels too aggressively**  
   Over-splitting activities makes process discovery too fine-grained.  
   Safeguard: keep `original_activity` and use `refined_activity` as an optional display/analysis label.

10. **Dropping e05 or e14 as “same timestamp duplicates”**  
   These are distinct events with distinct objects.  
   Safeguard: include an explicit no-drop test for object-discriminator differences.
