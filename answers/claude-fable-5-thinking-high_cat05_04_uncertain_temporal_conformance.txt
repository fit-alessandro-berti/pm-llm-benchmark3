## 1. Normalization Assumptions

**Interval construction (order of operations).** For every recorded value I build a feasible true-UTC interval in three steps, in this order:
1. **Resolution expansion (before clock correction, as instructed).** The recorded value is expanded into the set of clock times consistent with the display/rounding semantics:
   - HUB: exact second with measurement uncertainty ±0.5 s → clock ∈ [t−0.5 s, t+0.5 s].
   - OPS-BER, VENDOR-NY, LEGACY-BER: floor to minute → clock ∈ [m:00, m+1:00).
   - SENSOR: round to nearest 10 s → clock ∈ [t−5 s, t+5 s].
   - MOBILE-LON: round to nearest minute → clock ∈ [t−30 s, t+30 s].
2. **Clock correction.** With `clock_offset = recorded_clock − true_clock ∈ [a, b]`, true time = clock − offset, so a clock interval [lo, hi] maps to true ∈ [lo − b, hi − a]. (Example OPS-BER, offset [−90 s, +120 s]: true ∈ [lo − 120 s, hi + 90 s].)
3. **Event-specific widening** (mobile entry delay, inferred events, DST alternatives), described below.

Intervals are treated as closed; the half-open minute [m:00, m+1:00) is handled as [m:00, m+60 s] — the ≤1 ms difference is immaterial to every classification below.

**Time-zone conversion.** All local recorded times are converted to UTC before offset correction (offsets are constant, so the order of tz conversion and rounding does not change the result). On 2026-06-01: CEST = UTC+2 (OPS-BER), EDT = UTC−4 (VENDOR-NY), BST = UTC+1 (MOBILE-LON).

**DST fold (T-405).** On 2025-10-26, Europe/Berlin local 02:00–02:59 occurs twice: fold 0 = CEST (UTC = local − 2 h) and fold 1 = CET (UTC = local − 1 h). Each LEGACY-BER event initially yields a **union of two disjoint intervals**. The ingestion-order constraint (Alert_Received < Investigation_Start < Containment_Complete in true time) is then used to prune infeasible fold combinations. I assume ingestion order reflects true occurrence order; this is a substantive assumption and is flagged in the confidence column.

**Inferred start (T-404).** Investigation_Start = Investigation_Complete − duration, with duration ∈ [1080 s, 1500 s] from the signed work record. Interval arithmetic: start ∈ [complete_lo − 1500 s, complete_hi − 1080 s]. All uncertainty is retained; no midpoint substitution.

**Missing receipt (T-407).** Alert_Sent ≠ Alert_Received. Under the stated (unlogged) evidence, Alert_Received ∈ Alert_Sent + [0 s, 1200 s]. I additionally adopt the causal assumption "receipt not after Investigation_Start" as the **primary** scenario, which caps Alert_Received at the upper bound of Investigation_Start and floors the S1 duration at 0. Both the latency bound and the causal cap are explicitly conditional; without them the case is INDETERMINATE.

**Mobile entry delay (T-406).** Primary assumption **A1**: the recorded value is the device-stamped *entry* time, and the event may have occurred up to 300 s *before* it — the delay shifts my estimate of **occurrence time**, extending the interval's lower bound by 300 s. Alternative **A2**: the user typed the clock time they observed at occurrence, so the delay affects only the *record* time and the occurrence interval is unchanged. This choice materially changes S2 for T-406 (see Sections 3–4), so both are reported.

**Causal floors.** Where a hard ordering is asserted by evidence (T-405 ingestion order, T-407 causal assumption), negative durations are excluded. For T-409, the weak ±12 min offset makes a negative Alert→Investigation duration arithmetically feasible; the primary analysis imposes duration ≥ 0 (investigation cannot precede its alert) and flags the result as low-confidence.

**T-409 offset.** NTP diagnostics are missing; the weak engineering estimate offset ∈ [−720 s, +720 s] replaces the standard OPS-BER bound. Conclusions for this case are conditional on accepting that estimate.

**Classification semantics.** SLA rules are one-sided maxima tested against the feasible duration interval [d_lo, d_hi]: CERTAIN_PASS if d_hi ≤ limit; CERTAIN_VIOLATION if d_lo > limit; POSSIBLE_VIOLATION otherwise. Temporal-profile bands are two-sided [mean − ζ·sd, mean + ζ·sd]: wholly inside = CERTAIN_PASS, wholly outside (below or above) = CERTAIN_VIOLATION, partial overlap = POSSIBLE_VIOLATION. Pairs with a missing endpoint event are INDETERMINATE (not testable). Midpoints are used **only** in the Section 5 lossy comparison log.

        approximation, run through pm4py.conformance_temporal_profile for
        zeta in {1, 2, 3}, then compared against the interval conclusions.
PM4Py does NOT natively resolve timestamp uncertainty; Part B collapses each
interval to its midpoint and is therefore only a point-estimate diagnostic.
No external files are read.
"""
import itertools
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo

import pandas as pd

UTC = timezone.utc
S = lambda x: timedelta(seconds=x)

SOURCES = {
    #  name        tz                  resolution      offset bound (a, b) s
    "HUB":        ("UTC",              "exact_half_s", (-1.0,   1.0)),
    "OPS-BER":    ("Europe/Berlin",    "floor_min",    (-90.0,  120.0)),
    "SENSOR":     ("UTC",              "round_10s",    (-5.0,   5.0)),
    "VENDOR-NY":  ("America/New_York", "floor_min",    (-180.0, 180.0)),
    "LEGACY-BER": ("Europe/Berlin",    "floor_min",    (-60.0,  60.0)),
    "MOBILE-LON": ("Europe/London",    "round_min",    (-300.0, 300.0)),
}

def to_utc(naive, tzname, fold=0):
    if tzname == "UTC":
        return naive.replace(tzinfo=UTC)
    # fold=0 -> first occurrence of an ambiguous local time (summer offset),
    # fold=1 -> second occurrence (winter offset). Irrelevant outside DST folds.
    return naive.replace(tzinfo=ZoneInfo(tzname), fold=fold).astimezone(UTC)

def resolution_iv(rec, res):
    # Resolution/rounding uncertainty applied BEFORE clock correction.
    return {
        "exact_half_s": (rec - S(0.5), rec + S(0.5)),
        "floor_min":    (rec,          rec + S(60)),
        "round_10s":    (rec - S(5),   rec + S(5)),
        "round_min":    (rec - S(30),  rec + S(30)),
    }[res]

def true_iv(naive, system, fold=0, off_override=None,
            extra_early=0.0, extra_late=0.0):
    """Feasible true-UTC interval. clock_offset = recorded - true in [a,b]
    => true in [rec_lo - b, rec_hi - a]. extra_early/late widen the
    OCCURRENCE-time estimate (e.g. mobile entry delay under assumption A1)."""
    tzname, res, off = SOURCES[system]
    a, b = off_override if off_override else off
    lo, hi = resolution_iv(to_utc(naive, tzname, fold), res)
    return (lo - S(b) - S(extra_early), hi - S(a) + S(extra_late))

dt = datetime
EV = {}          # (case, activity) -> single feasible interval (post-pruning)
NOTES = {}

def put(case, act, iv, note=""):
    EV[(case, act)] = iv
    if note:
        NOTES[(case, act)] = note

# ---- directly observed events -------------------------------------------
put("T-401", "Alert_Received",       true_iv(dt(2026,6,1,8,0,0),   "HUB"))
put("T-401", "Investigation_Start",  true_iv(dt(2026,6,1,10,14),   "OPS-BER"))
put("T-401", "Containment_Complete", true_iv(dt(2026,6,1,8,51,10), "SENSOR"))
put("T-401", "Close_Incident",       true_iv(dt(2026,6,2,9,0,0),   "HUB"))

put("T-402", "Alert_Received",       true_iv(dt(2026,6,1,9,0,0),   "HUB"))
put("T-402", "Investigation_Start",  true_iv(dt(2026,6,1,11,18),   "OPS-BER"))
put("T-402", "Containment_Complete", true_iv(dt(2026,6,1,10,2,0),  "HUB"))

put("T-403", "Alert_Received",       true_iv(dt(2026,6,1,4,0),     "VENDOR-NY"))
put("T-403", "Investigation_Start",  true_iv(dt(2026,6,1,8,16,0),  "HUB"))
put("T-403", "Containment_Complete", true_iv(dt(2026,6,1,8,58,0),  "HUB"))

put("T-404", "Alert_Received",       true_iv(dt(2026,6,1,10,0,0),  "HUB"))
invc = true_iv(dt(2026,6,1,10,35,0), "HUB")
# Inferred start = complete - duration, duration in [1080, 1500] s (signed record)
put("T-404", "Investigation_Start", (invc[0] - S(1500), invc[1] - S(1080)),
    "INFERRED from Investigation_Complete minus signed 18-25 min duration")
put("T-404", "Containment_Complete", true_iv(dt(2026,6,1,10,55,0), "HUB"))

put("T-406", "Alert_Received",       true_iv(dt(2026,6,1,12,0,0),  "HUB"))
# Assumption A1 (primary): timestamp is entry time; occurrence may be up to
# 300 s EARLIER -> widens the occurrence-time lower bound (not just record time).
put("T-406", "Investigation_Start",
    true_iv(dt(2026,6,1,13,14), "MOBILE-LON", extra_early=300.0),
    "A1: entry delay widens occurrence estimate; A2 would drop extra_early")
put("T-406", "Containment_Complete", true_iv(dt(2026,6,1,12,52,0), "HUB"))

sent = true_iv(dt(2026,6,1,14,0,0), "HUB")
put("T-407", "Alert_Sent", sent)
invs7 = true_iv(dt(2026,6,1,14,17,0), "HUB")
put("T-407", "Investigation_Start", invs7)
# Alert_Received = Sent + [0, 1200] s, capped by causal assumption
# "receipt not after Investigation_Start" (plausible, NOT logged).
put("T-407", "Alert_Received",
    (sent[0], min(sent[1] + S(1200), invs7[1])),
    "INFERRED: latency bound [0,20] min + unlogged causal cap; conditional")
put("T-407", "Containment_Complete", true_iv(dt(2026,6,1,14,55,0), "HUB"))

put("T-408", "Alert_Received",       true_iv(dt(2026,6,1,15,0,0),  "HUB"))
put("T-408", "Investigation_Start",  true_iv(dt(2026,6,1,15,10,0), "HUB"))
put("T-408", "Containment_Complete", true_iv(dt(2026,6,1,16,5,0),  "HUB"))
put("T-408", "Close_Incident",       true_iv(dt(2026,6,3,6,30,0),  "HUB"))

put("T-409", "Alert_Received",       true_iv(dt(2026,6,1,16,0,0),  "HUB"))
# NTP diagnostics missing: weak engineering estimate +/-12 min replaces bound.
put("T-409", "Investigation_Start",
    true_iv(dt(2026,6,1,18,4), "OPS-BER", off_override=(-720.0, 720.0)),
    "WEAK offset evidence; conclusions conditional")
put("T-409", "Containment_Complete", true_iv(dt(2026,6,1,16,35,0), "HUB"))

# ---- T-405: DST-fold union + ingestion-order pruning ---------------------
t405_local = [("Alert_Received",       dt(2025,10,26,2,50)),
              ("Investigation_Start",  dt(2025,10,26,2,5)),
              ("Containment_Complete", dt(2025,10,26,2,42))]
alts = {a: {f: true_iv(loc, "LEGACY-BER", fold=f) for f in (0, 1)}
        for a, loc in t405_local}
surviving = []
for combo in itertools.product((0, 1), repeat=3):
    ivs = [alts[a][f] for (a, _), f in zip(t405_local, combo)]
    # ingestion order (true time): Alert < Start < Complete must be feasible
    if all(ivs[i][0] < ivs[i + 1][1] for i in range(2)):
        surviving.append((combo, ivs))
print("T-405 surviving fold combinations (0=CEST first pass, 1=CET second):")
for combo, ivs in surviving:
    print("  folds", combo, [(iv[0].isoformat(), iv[1].isoformat()) for iv in ivs])
# Union over surviving branches per activity; here exactly one branch survives,
# so each union is a single interval (pruning, not midpoint collapsing).
for i, (act, _) in enumerate(t405_local):
    los = [ivs[i][0] for _, ivs in surviving]
    his = [ivs[i][1] for _, ivs in surviving]
    put("T-405", act, (min(los), max(his)),
        "DST fold resolved by ingestion-order constraint")

# ---- interval arithmetic and classification ------------------------------
def dur_iv(a, b, floor=None):
    lo = (b[0] - a[1]).total_seconds()
    hi = (b[1] - a[0]).total_seconds()
    if floor is not None:
        lo = max(lo, floor)
    return (lo, hi)

def classify_max(d, limit):
    if d[1] <= limit: return "CERTAIN_PASS"
    if d[0] >  limit: return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

def classify_band(d, mean, sd, zeta):
    lo, hi = mean - zeta * sd, mean + zeta * sd
    if d[0] >= lo and d[1] <= hi: return "CERTAIN_PASS"
    if d[1] <  lo or  d[0] >  hi: return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

SLA = {"S1": ("Alert_Received", "Investigation_Start", 900),
       "S2": ("Investigation_Start", "Containment_Complete", 2700),
       "S3": ("Containment_Complete", "Close_Incident", 129600)}
TEMPORAL_PROFILE = {
    ("Alert_Received", "Investigation_Start"):      (600.0,   180.0),
    ("Investigation_Start", "Containment_Complete"):(2100.0,  600.0),
    ("Alert_Received", "Containment_Complete"):     (2700.0,  720.0),
    ("Containment_Complete", "Close_Incident"):     (86400.0, 21600.0),
}
# Causal duration floors where evidence asserts ordering (see report).
FLOORS = {("T-407", "Alert_Received", "Investigation_Start"): 0.0,
          ("T-409", "Alert_Received", "Investigation_Start"): 0.0}

cases = sorted({c for c, _ in EV})
interval_rows = []
for c in cases:
    for rule, (a, b, lim) in SLA.items():
        if (c, a) in EV and (c, b) in EV:
            d = dur_iv(EV[(c, a)], EV[(c, b)], FLOORS.get((c, a, b)))
            interval_rows.append(dict(case=c, test=rule, pair=f"{a}->{b}",
                                      dur_lo=d[0], dur_hi=d[1],
                                      result=classify_max(d, lim)))
        else:
            interval_rows.append(dict(case=c, test=rule, pair=f"{a}->{b}",
                                      dur_lo=None, dur_hi=None,
                                      result="INDETERMINATE (missing event)"))
    for (a, b), (m, sd) in TEMPORAL_PROFILE.items():
        if (c, a) in EV and (c, b) in EV:
            d = dur_iv(EV[(c, a)], EV[(c, b)], FLOORS.get((c, a, b)))
            for z in (1, 2, 3):
                interval_rows.append(dict(case=c, test=f"profile z={z}",
                                          pair=f"{a}->{b}",
                                          dur_lo=d[0], dur_hi=d[1],
                                          result=classify_band(d, m, sd, z)))
interval_df = pd.DataFrame(interval_rows)
print("\n=== INTERVAL-BASED CLASSIFICATIONS ===")
print(interval_df.to_string(index=False))

# ---- Part B: MIDPOINT-ONLY log (LOSSY APPROXIMATION) ----------------------
print("\n=== MIDPOINT LOG: LOSSY APPROXIMATION, secondary comparison only ===")
mid_rows = [dict(case_id=c, activity=a,
                 timestamp=iv[0] + (iv[1] - iv[0]) / 2,
                 approximation="MIDPOINT_LOSSY")
            for (c, a), iv in sorted(EV.items()) if a != "Alert_Sent"]
mid_df = pd.DataFrame(mid_rows).sort_values(["case_id", "timestamp"])

try:
    import pm4py
    log_df = pm4py.format_dataframe(mid_df.copy(), case_id="case_id",
                                    activity_key="activity",
                                    timestamp_key="timestamp")
    for z in (1, 2, 3):
        diag = pm4py.conformance_temporal_profile(log_df, TEMPORAL_PROFILE,
                                                  zeta=z)
        print(f"\n-- pm4py temporal-profile deviations, zeta={z} --")
        # Diagnostic shape is version-dependent: recent PM4Py returns one list
        # per case, each deviation typically (act_a, act_b, duration, n_stdevs).
        # This block only prints; it makes no assumption beyond iterability.
        try:
            case_ids = sorted(mid_df["case_id"].unique())
            for cid, devs in zip(case_ids, diag):
                if devs:
                    print(f"  {cid}: {devs}")
        except Exception as e:
            print("  raw diagnostics (unexpected shape):", diag, "|", e)
except ImportError:
    print("pm4py not installed; interval analysis above is unaffected.")

print("""
=== COMPARISON: midpoint diagnostics vs interval conclusions ===
The midpoint log is a point-estimate projection: every POSSIBLE_VIOLATION
collapses to a binary flag depending on which side of the band the midpoint
happens to fall. Examples: T-401 Alert->Start midpoint (855 s) is flagged at
zeta=1 as if it were a definite deviation, while the interval verdict is only
POSSIBLE (feasible 718.5-991.5 s straddles the 780 s band edge); conversely
T-404's Start->Contain midpoint (~2490 s) is NOT flagged at zeta=1 although
feasible durations reach 2703 s (interval verdict: POSSIBLE). T-409's midpoint
(270 s) is flagged below-band although most of its feasible range lies inside.
Certain findings on HUB-only pairs (T-408) agree with the midpoint run because
those intervals are only a few seconds wide.
PM4Py's temporal-profile checker consumes exact timestamps and does not model
timestamp uncertainty; only the interval analysis distinguishes CERTAIN from
POSSIBLE outcomes.""")

## 6. Evidential Sufficiency

For each non-certain finding, the minimum additional evidence that would make it certain, grouped by evidence type:

**Synchronization evidence (tighter clock-offset bounds or higher resolution):**
- **T-401 S1 / Alert→Start profile (POSSIBLE):** an OPS-BER offset bound tighter than about ±45 s, or second-resolution OPS-BER timestamps, would shrink [718.5, 991.5] to one side of 900 s. Either stronger NTP telemetry for that hour or the raw (unfloored) OPS-BER timestamp suffices.
- **T-402 S2 (POSSIBLE, margin 61.5 s):** same fix — the entire ambiguity comes from OPS-BER's minute floor plus offset; a raw seconds timestamp alone would nearly settle it.
- **T-403 S1 / profiles (POSSIBLE):** event-level synchronization for VENDOR-NY (e.g., a signed NTP offset sample near 08:00 UTC, or receipt of the same alert on a HUB-logged channel). The vendor's ±3 min bound is the dominant uncertainty.
- **T-409 S1/S2 (POSSIBLE/conditional):** replacement of the ±12 min engineering guess with actual NTP diagnostics for that hour. Until then the case is at best conditional; if the estimate is rejected the S1 finding is INDETERMINATE.
- **T-408 Start→Contain profile at ζ=2 (POSSIBLE by a 6 s straddle):** sub-second HUB timestamps (removing the ±1.5 s envelope) would resolve which side of the 3300 s edge the true duration falls on.

**Missing activity evidence:**
- **T-402/T-403/T-404/T-405/T-406/T-407/T-409 S3 and Contain→Close profile (INDETERMINATE):** a logged Close_Incident event is the only cure; no synchronization improvement helps.
- **T-404 S1/S2 (POSSIBLE):** a directly logged Investigation_Start event would eliminate the inference entirely; failing that, see duration evidence below.
- **T-407 S1 (POSSIBLE/conditional):** a logged Alert_Received event or a delivery acknowledgment with a timestamp. That is strictly stronger than any improvement to the latency bound.

**Duration evidence:**
- **T-404:** a tighter signed duration (e.g., 20–21 min instead of 18–25 min) would move both S1 and S2 to certainty; the current 7-minute width is the binding constraint, not the HUB clocks.
- **T-407:** a narrower delivery-latency bound (e.g., [0, 4] min from network telemetry) would make S1 a certain pass even without an acknowledgment.

**Semantic evidence:**
- **T-406 S2 (assumption-dependent POSSIBLE):** documentation of what the mobile app records — device-stamped entry time (A1) versus user-recalled occurrence time (A2). Under A2 the case is already a certain S2 pass; the classification hinges on this single semantic fact, plus optionally app telemetry bounding the entry delay.
- **T-405 (all findings conditional):** confirmation that ingestion sequence numbers reflect true occurrence order (e.g., a monotonic ingest counter with documented semantics), and ideally a logged UTC ingest timestamp or the DST fold flag itself. The fold pruning is only as strong as that assumption.
- **T-407:** organizational confirmation that Alert_Sent-to-received latency semantics apply and that investigation cannot precede receipt — currently plausible but unlogged.

## 7. Governance Recommendation

**Timestamp storage.** Store all event times in UTC with explicit offset provenance; additionally retain the raw, unmodified source timestamp (original zone, original resolution, pre-rounding value where the source has it). Never overwrite raw values with normalized ones — every finding in Section 3 depended on reconstructing the pre-rounding interval.

**Resolution metadata.** Record, per source, the display/rounding rule (floor vs round, granularity) as machine-readable metadata. The difference between "floor to minute" and "round to minute" moved interval bounds by up to 60 s in this log and changed classifications.

**Clock and offset telemetry.** Require continuous NTP (or PTP) offset telemetry per source, stored as time-series with the events; a per-event offset bound should be joinable at analysis time. T-409 shows the cost of a single missing diagnostic window: findings degrade from measurable to conditional. External vendors (VENDOR-NY) should contractually supply either synchronization attestations or event-level offset samples.

**Time zone and DST fold.** Log the IANA zone identifier and the fold/UTC-offset actually in force at write time (e.g., store `2025-10-26T02:42+01:00` rather than bare local time). A one-bit fold flag would have eliminated the entire T-405 branch analysis.

**Lifecycle semantics.** Enforce explicit start/complete lifecycle transitions per activity (SENSOR events are completions; T-404 lacked a start). SLA rules should be defined against declared lifecycle states, and missing lifecycle events should be a logged data-quality incident, not a silent gap.

**Causal identifiers.** Propagate correlation IDs from Alert_Sent through Alert_Received to Investigation_Start, with per-hop send/receive timestamps and acknowledgments. T-407 was only assessable via an unlogged causal assumption; a receipt acknowledgment converts it to a measured quantity. Similarly, ingestion sequence numbers should have documented ordering semantics (T-405).

**Human-entered timestamps.** For mobile/manual entries, capture both the device-stamped entry time and the user-asserted occurrence time, plus an app-measured entry latency where possible. The A1/A2 ambiguity in T-406 flipped an SLA classification and is entirely preventable.

**Enforcement policy on interval overlap.** Adopt an explicit, published policy distinguishing the three verdict classes: (1) CERTAIN_VIOLATION → enforceable breach (T-402 S1, T-408 S2/S3 here); (2) POSSIBLE_VIOLATION → not automatically enforceable; triggers an evidence-improvement workflow (Section 6) and is reported with the feasible interval and worst-case margin; (3) INDETERMINATE → data-quality escalation, never an SLA verdict. Overlap alone should not suffice for penalties against parties, but should suffice for internal alerting and remediation tracking. Publish the tolerance and ζ conventions in advance (Section 4 shows classifications flipping on 1.5–3 s margins), and require that any point-estimate (midpoint) reporting be labeled as lossy and accompanied by the interval verdict.
