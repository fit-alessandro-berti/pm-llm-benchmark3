## 1. Interaction-graph description

The useful object-centric graph is not a job-only DFG. It is a typed graph with at least these node types:

- **Job**: J1–J6
- **Component**: C1–C6
- **ComponentLot**: L7, L8
- **Machine**: CNC-2, OVEN-1, TEST-1
- **Tool**: FIX-A, RACK-7, CAL-3
- **Batch**: B1, B2
- **Shipment**: S1, S2, S3

Important edge types and qualifiers:

| Edge type | Direction | Status |
|---|---|---|
| `requires` | Job  Component | Direct O2O |
| `contains` | ComponentLot  Component | Direct O2O |
| `batches` | Batch  Job | Direct O2O |
| `consolidates` | Shipment  Job | Direct O2O |
| `uses` / `processes` | Batch/Job  Machine/Tool | Direct from event-object relations |
| `acquires` / `releases` | Job  Tool | Direct for FIX-A; partly inferred elsewhere |
| `waits_for` | Job  Batch/Tool/Lot/Shipment | Inferred from timestamps, not recorded as events |
| `quarantine` / `release` | ComponentLot  Component/Job | Direct event, but job links are inconsistent |

At least three higher-order motifs matter:

1. **Batch–Machine–Tool–Job–Component motif**  
   `B1` uses `OVEN-1` and `RACK-7` and batches `J1,J2,J3`; the single `Batch Cure` event also relates to `C1,C2,C3`. This couples three jobs through one synchronization barrier.

2. **Job–Tool–Machine contention motif**  
   `J3` holds `FIX-A` while `J4` waits at `CNC-2`. The later `Machine Process` event for `J4` relates to `J4,C4,CNC-2,FIX-A`, so the tool is part of the same resource requirement.

3. **Job–Component–ComponentLot coupling motif**  
   `J2` requires `C2`, `J5` requires `C5`, and both `C2` and `C5` are contained in `L7`. A `Quarantine Lot` and later `Release Lot` event relate to `L7,C2,C5,J2,J5`.

4. **Job–Shipment consolidation motif**  
   `S1` consolidates `J1` and `J4`; `J1` is packed long before `J4`, but dispatch waits for both.

5. **Job–Machine–Tool calibration motif**  
   `J5` and `J6` both require `TEST-1` and `CAL-3` for `Final Test`; `CAL-3` recalibration sits between their tests.

Compact edge-list representation:

```text
Direct O2O:
J1 requires C1; J2 requires C2; J3 requires C3;
J4 requires C4; J5 requires C5; J6 requires C6

L7 contains C2, C5
L8 contains C1, C3

B1 batches J1, J2, J3
B2 batches J4, J5

S1 consolidates J1, J4
S2 consolidates J2, J3
S3 consolidates J5, J6

B1 uses OVEN-1, RACK-7
B2 uses OVEN-1, RACK-7

J3 acquires/releases FIX-A
J4 uses FIX-A, CNC-2
J5 uses TEST-1, CAL-3
J6 uses TEST-1, CAL-3

Inferred waiting edges:
J1 waits_for B1
J2 waits_for B1
J4 waits_for FIX-A
J5 waits_for L7 release
J6 waits_for CAL-3
J1 waits_for S1
```

The `waits_for` edges are not observed events. They are inferred from timestamp gaps and resource feasibility.

## 2. Quantitative delay decomposition

Each calculation below states a counterfactual. None of these is causal proof.

1. **B1 synchronization wait for J1**  
   J1 ready at 08:10; B1 starts at 12:05.  
   Wait = 12:05  08:10 = **3 h 55 min**.  
   *Counterfactual:* if J1 could be cured immediately when ready, or placed in a single-job batch, this wait would be zero.

2. **B1 synchronization wait for J2**  
   J2 ready at 08:25; B1 starts at 12:05.  
   Wait = 12:05  08:25 = **3 h 40 min**.  
   *Counterfactual:* same as above.

3. **Total B1 synchronization-induced waiting**  
   J1: 3 h 55 min; J2: 3 h 40 min; J3: 12:05  11:55 = 10 min.  
   Total = 3:55 + 3:40 + 0:10 = **7 h 45 min**.  
   *Counterfactual:* if all three jobs could be cured as soon as each was ready, total waiting would be zero. This assumes the “ready for batch” timestamps are trustworthy.

4. **FIX-A-associated delay for J4**  
   J4 reaches CNC-2 at 09:50. J3 releases FIX-A at 11:40. J4’s `Machine Process` starts at 11:45.  
   Observed wait from arrival to start = 11:45  09:50 = **1 h 55 min**.  
   CNC-2 is idle from 10:05 to 10:47, so the machine was at least partly available.  
   *Counterfactual:* if FIX-A had been available at 09:50, or if J4 had an alternate fixture, J4 could plausibly have started at 09:50. The implied delay is **1 h 55 min**.  
   Alternative decomposition: from FIX-A release at 11:40 to J4 start at 11:45 is only 5 min, so most of the wait occurs before the tool is released.

5. **S1 consolidation delay for J1**  
   J1 packed at 13:30; S1 dispatches at 19:25.  
   Observed pack-to-dispatch wait = 19:25  13:30 = **5 h 55 min**.  
   The shipment-flattened median `Create Shipment  Load` is 0.8 h and `Load  Dispatch` is 0.3 h, totaling 1.1 h.  
   If J1 had been dispatched without waiting for J4, expected dispatch  13:30 + 1.1 h = 14:36.  
   Excess over that counterfactual = 19:25  14:36 = **4 h 49 min**.  
   *Counterfactual:* J1 is shipped as soon as it is packed, or placed in a shipment not held for J4.

6. **CAL-3-associated delay for J6**  
   J6 ready for final test at 16:05; observed test start at 17:25.  
   Total wait = 17:25  16:05 = **1 h 20 min**.  
   Decomposition:
   - J5 tests 16:10–16:35: 25 min
   - CAL-3 recalibration 16:35–17:20: 45 min
   - residual gap 17:20–17:25: 5 min  
   If no recalibration were required after J5, J6 could plausibly start at 16:35.  
   CAL-3-associated delay = 45 + 5 = **50 min**.  
   *Counterfactual:* CAL-3 is available immediately after J5, or recalibration is not required between tests. TEST-1 is otherwise idle from 16:35 to 17:25.

7. **B2 / RACK-7 / OVEN-1 idle window**  
   J4 ready at 13:10; B2 starts at 14:50, so J4 waits **1 h 40 min**.  
   J5 ready at 14:40; B2 starts at 14:50, so J5 waits **10 min**.  
   OVEN-1 is idle from 12:55 to 14:50 = **1 h 55 min**.  
   RACK-7 is recorded as cleaning/quarantine until 14:35.  
   *Counterfactual:* if RACK-7 were available and batch policy allowed J4 to run alone, B2 could start at 13:10. The observed start is 14:50. This is not proof because J5 readiness and batch policy may be the real constraint.

8. **L7 quarantine duration**  
   `Quarantine Lot` at 10:20; `Release Lot` at 13:50.  
   Duration = 13:50  10:20 = **3 h 30 min**.  
   J5 did not proceed until after release, but J5 is ready for B2 at 14:40, which is 50 min after release.  
   *Counterfactual:* if L7 had been released at 10:20, J5 might have become ready earlier. The data do not prove this. For J2, B1 starts at 12:05 before the 13:50 release, so the lot release did not block B1 start; a supervisor override is recorded.

## 4. What flattening misses

### Job viewpoint

- **Visible:** direct job lifecycle stages, median times, rework loops, and the fact that no job has an extreme total duration.
- **Hides/duplicates:** waiting for batch, tool, lot, or shipment; duplicates shared events such as `Batch Cure` across J1, J2, J3; misses lot events not directly linked to jobs; hides that J1’s `Pack  Dispatch` is 5 h 55 min while the median is 1.1 h.
- **Misleading conclusion:** the job-flattened DFG suggests a smooth flow with no severe bottleneck.

### Machine viewpoint

- **Visible:** machine utilization, activity sequence, and gaps between machine events.
- **Hides/duplicates:** tool holds, batch synchronization, upstream and downstream waits; gaps may be caused by missing tools or batch policy, not machine capacity.
- **Misleading conclusion:** OVEN-1 at 44% utilization with a 73-min gap looks underused, but the machine is idle while jobs wait for batch partners or RACK-7.

### Batch viewpoint

- **Visible:** batch composition, batch start/end, jobs in the batch, machine and tool used.
- **Hides/duplicates:** individual job readiness times, waiting before batch start, lot/tool constraints, downstream shipment waits.
- **Misleading conclusion:** B1 starting at 12:05 looks efficient, but it hides J1 waiting 3 h 55 min and J2 waiting 3 h 40 min.

### Tool viewpoint

- **Visible:** acquire/release, cleaning/quarantine, calibration events, tool utilization.
- **Hides/duplicates:** jobs waiting for the tool, machine idle caused by tool absence, cascading effects.
- **Misleading conclusion:** FIX-A held 09:00–11:40 is visible, but J4’s 1 h 55 min wait is not; CAL-3 recalibration 16:35–17:20 is visible, but J6’s delay is not.

### ComponentLot viewpoint

- **Visible:** lot composition, quarantine/release events, affected components.
- **Hides/duplicates:** job-level impact, inconsistent links to jobs, supervisor overrides.
- **Misleading conclusion:** L7 quarantine 10:20–13:50 is visible, but the J2 override and J5 waiting are not.

### Shipment viewpoint

- **Visible:** shipment creation, load, dispatch, consolidated jobs.
- **Hides/duplicates:** packed-job waiting before load; duplicates job completion events; hides mismatch between job ready times.
- **Misleading conclusion:** shipment-flattened DFG shows `Create  Load` 0.8 h and `Load  Dispatch` 0.3 h, suggesting fast dispatch, while J1 waits 5 h 55 min after packing.

### Why low machine utilization coexists with long job waiting

Machine utilization measures machine event time, not job flow. Jobs can wait for batch partners, tools, lot release, or shipment consolidation while machines are idle. A batch cure is a single machine event that occupies OVEN-1, but jobs may wait hours before that event. Likewise, TEST-1 can be idle while CAL-3 is recalibrating, and CNC-2 can be idle while FIX-A is held by another job.

## 5. Object-lifecycle evidence

### Narrative 1: B1 batch synchronization

Objects: **Job J1/J2/J3, Component C1/C2/C3, Batch B1, Machine OVEN-1, Tool RACK-7**.

- **Temporal precedence:** J1 ready 08:10, J2 ready 08:25, J3 ready 11:55; `Batch Cure` at 12:05 relates to B1, OVEN-1, RACK-7, J1, J2, J3, C1, C2, C3.
- **Resource feasibility:** the batch cure requires OVEN-1 and RACK-7; all three jobs and components are linked to the same event. No evidence shows OVEN-1 or RACK-7 unavailable before 12:05.
- **Policy constraints:** B1 waits for all three jobs; J1 and J2 wait for J3.
- **Causal speculation:** the 3 h 55 min and 3 h 40 min waits are plausibly caused by batch synchronization, not machine capacity. This is not proven because there is no explicit `Wait for Batch` event.

### Narrative 2: FIX-A contention at CNC-2

Objects: **Job J3, Job J4, Component C4, Machine CNC-2, Tool FIX-A**.

- **Temporal precedence:** J3 acquires FIX-A at 09:00 and releases it at 11:40. J4 reaches CNC-2 at 09:50. CNC-2 is idle 10:05–10:47. J4’s `Machine Process` starts at 11:45 and relates to J4, C4, CNC-2, FIX-A.
- **Resource feasibility:** J4’s process requires CNC-2 and FIX-A. CNC-2 is idle from 10:05 to 10:47, so the machine is at least partly feasible; FIX-A is held by J3 until 11:40, so the tool is not feasible.
- **Policy constraints:** there is no `Wait for Tool` activity; tool allocation gives FIX-A to J3, and J4 cannot preempt.
- **Causal speculation:** J4’s 1 h 55 min wait is plausibly due to FIX-A contention. Alternative: J4 may have needed setup or another hidden step.

### Narrative 3: CAL-3 recalibration and S3 consolidation

Objects: **Job J5, Job J6, Machine TEST-1, Tool CAL-3, Shipment S3**.

- **Temporal precedence:** J5 and J6 ready for final test at 16:00 and 16:05. J5 tests 16:10–16:35. CAL-3 is recalibrated 16:35–17:20. J6 tests 17:25–17:50. S3 consolidates J5 and J6 and dispatches 35 min after the last job is packed.
- **Resource feasibility:** `Final Test` requires TEST-1 and CAL-3. TEST-1 is idle 16:35–17:25, so the machine is feasible; CAL-3 is unavailable during recalibration.
- **Policy constraints:** recalibration occurs after J5’s test; shipment consolidation waits for both jobs.
- **Causal speculation:** J6’s 50-min CAL-3-associated delay is plausibly caused by recalibration. S3 dispatch is downstream of J6’s late test. This is not proven because recalibration may be mandatory.

### Narrative 4: L7 lot coupling

Objects: **Job J2, Job J5, Component C2, Component C5, ComponentLot L7, Batch B1/B2, Machine OVEN-1**.

- **Temporal precedence:** L7 quarantine at 10:20, release at 13:50. J2 ready for B1 at 08:25; B1 starts 12:05. J2 entered B1 before release via supervisor override. J5 ready for B2 at 14:40, after release.
- **Resource feasibility:** C2 and C5 both belong to L7; lot release is a shared prerequisite for both jobs, but J2’s override breaks the normal resource constraint.
- **Policy constraints:** quarantine/release policy applies to the lot; supervisor override is recorded in a separate system.
- **Causal speculation:** J5 did not proceed until after release, but J5 is ready at 14:40, after release, so the release may have delayed earlier operations rather than B2 start. J2’s override makes the lot coupling inconsistent. This is not proven.

## 6. Intervention portfolio and spillovers

### Intervention 1: Dynamic batch splitting or partial-batch release

- **Target mechanism:** batch synchronization.
- **Expected benefit:** reduce J1/J2 wait of 3 h 55 / 3 h 40 min; reduce J4 wait of 1 h 40 min; reduce OVEN-1 idle time.
- **Jobs/objects helped:** J1, J2, J3, J4, J5; B1, B2; OVEN-1.
- **Jobs/objects potentially harmed:** more setups and cleaning may affect RACK-7; J3 may face more frequent batch changes; cure profile may require full loads.
- **New cost/risk:** more batches, more energy, more tool cleaning, quality risk if cure profile requires full load.
- **Perverse incentive metric:** OVEN-1 utilization or number of batches; could incentivize over-batching or running partial loads.
- **Object-centric evaluation design:** compare Job–Batch–Machine–Tool OCDFG before/after; measure job ready-to-batch-start waiting, batch size, OVEN-1 idle, RACK-7 cleaning frequency.

### Intervention 2: Tool pool expansion and tool scheduling

- **Target mechanism:** shared-tool contention.
- **Expected benefit:** reduce J4’s 1 h 55 min FIX-A wait; reduce J6’s 50 min CAL-3-associated delay; reduce RACK-7-related idle.
- **Jobs/objects helped:** J3, J4, J5, J6; CNC-2, TEST-1, OVEN-1; FIX-A, CAL-3, RACK-7.
- **Jobs/objects potentially harmed:** jobs using tools if preempted; maintenance workload; capital cost.
- **New cost/risk:** extra tools, calibration/cleaning may be rushed, tool wear.
- **Perverse incentive metric:** tool utilization; could incentivize overuse or delayed maintenance.
- **Object-centric evaluation design:** track Job–Tool–Machine event graph; infer wait-for-tool from timestamps; measure tool cleaning/calibration durations and job waiting.

### Intervention 3: Shipment decoupling or maximum-wait consolidation window

- **Target mechanism:** shipment consolidation.
- **Expected benefit:** reduce J1’s 5 h 55 min pack-to-dispatch wait; improve on-time dispatch.
- **Jobs/objects helped:** J1, J4, S1; also J2/J3/S2 and J5/J6/S3.
- **Jobs/objects potentially harmed:** J4 may need a separate shipment; transport cost may rise; customer requirements may be violated.
- **New cost/risk:** more shipments, higher logistics cost, customer penalties.
- **Perverse incentive metric:** shipment count or dispatch lead time; could incentivize shipping partial or empty shipments.
- **Object-centric evaluation design:** measure Job–Shipment consolidation wait, pack-to-dispatch per job, shipment fill rate, number of shipments.

### Intervention 4: Logging and data-integration improvement

- **Target mechanism:** data-integration artifacts.
- **Expected benefit:** make hidden waits visible; improve bottleneck diagnosis.
- **Jobs/objects helped:** all jobs, analysts, managers.
- **Jobs/objects potentially harmed:** none operationally; logging overhead.
- **New cost/risk:** log volume, data quality, alert fatigue.
- **Perverse incentive metric:** number of wait events logged; could incentivize logging waits without reducing them.
- **Object-centric evaluation design:** compare OCDFG before/after; measure frequency of `Wait for Batch`, `Wait for Tool`, `Wait for Lot`, `Wait for Shipment` events; measure missing lot-job links.

### Intervention 5: Expedite lot release / quarantine review

- **Target mechanism:** component-lot release coupling.
- **Expected benefit:** reduce J5 delay; avoid J2 supervisor override.
- **Jobs/objects helped:** J2, J5, L7, C2, C5.
- **Jobs/objects potentially harmed:** quality risk if release is too early; other jobs using L7.
- **New cost/risk:** releasing nonconforming lots.
- **Perverse incentive metric:** lot release cycle time; could incentivize premature release.
- **Object-centric evaluation design:** track ComponentLot–Job event graph; measure quarantine duration, job waiting after lot events, override frequency.

### Intervention 6: Supervisor override governance

- **Target mechanism:** policy exceptions.
- **Expected benefit:** reduce hidden coupling and quality risk.
- **Jobs/objects helped:** J2, L7, B1.
- **Jobs/objects potentially harmed:** J2 may wait if override is not allowed.
- **New cost/risk:** slower flow.
- **Perverse incentive metric:** override count; could incentivize hiding overrides.
- **Object-centric evaluation design:** track override events linked to jobs, lots, and batches.

## 8. Falsification and additional data

### Observations that would weaken the top-ranked explanation (batch synchronization)

1. If OVEN-1 was actually down or occupied from 08:10 to 12:05, then J1/J2 waiting was not primarily batch synchronization.
2. If J1/J2 “ready for batch” timestamps are not trustworthy—e.g., jobs were staged early but not actually ready—then the 3 h 55 / 3 h 40 min waits are overstated.
3. If J3’s readiness at 11:55 was itself delayed by upstream lot or tool problems, then B1’s 12:05 start may be an upstream effect, not a batch-policy barrier.
4. If B1’s 12:05 start was caused by RACK-7 cleaning/quarantine or OVEN-1 unavailability, then batch synchronization is not the main cause.
5. If J1/J2 would have waited anyway for inspection or another downstream step, then batch wait is not the binding constraint.
6. If shipment or lot delays dominate total lead time, batch waiting may be large but not the main cause of cascading delays.
7. If B2’s 14:50 start is only 10 min after J5’s readiness, then batch synchronization is weak for B2; only J4’s 1 h 40 min wait is substantial.

### Additional fields or event types that would discriminate among hypotheses

1. Explicit `Wait for Batch`, `Wait for Tool`, `Wait for Lot`, and `Wait for Shipment` events with start/end timestamps.
2. Job readiness timestamps with reason codes distinguishing “ready” from “staged.”
3. Machine state events: idle, down, setup, processing, with start/end times.
4. Tool state events: acquire, release, cleaning, calibration, quarantine, with start/end times and job links.
5. Batch policy parameters: minimum batch size, maximum wait, cure profile requirements.
6. Shipment policy parameters: consolidation window, customer constraints, latest dispatch time.
7. Lot event links to specific jobs, plus override events and override reasons.
8. Component-level genealogy and quality status.
