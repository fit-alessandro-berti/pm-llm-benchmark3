# 1. Review Scope and Assumptions

**Intended use cases are not interchangeable.**  
- **Exploration / discovery:** A permissive model can be useful to see “what is possible in the log,” but it must be labeled exploratory and must not be used to approve or reject cases. High fitness and generalization are acceptable only if false acceptance is explicitly tolerated.  
- **Conformance enforcement / audit:** The model must enforce mandatory checks, exactly-one approval, expedite ordering, and policy-conditional supplier review. False accepts of forbidden behavior are more dangerous than false rejects, but false rejects of legitimate unseen combinations also create operational risk and audit fatigue. Precision against a curated negative suite matters more than positive-log precision.  
- **Simulation:** Neither original model is suitable without resource, time, probability, and attribute semantics. Model S’s parallel optional block would simulate absurd cases; Model C would simulate only enumerated historical variants.  
- **Stakeholder communication:** Model S is easier to read but communicates a false policy. Model C is difficult to read and maintain. A good third model needs layered communication: a simple procedural backbone, plus explicit conditional and correction rules.

**Assumptions.** I interpret PM4Py process-tree operators as: `->` sequence, `X` exclusive choice, `+` parallel, `*` loop, and `tau` silent/optional. Model S accepts any interleaving of the four optional activities in its parallel block, enforces exactly one approval, and cannot repeat activities. Model C is a finite XOR of the eight listed full traces; it has no loop and no silent skips. Reported metrics are not treated as ground truth. Missing `external/internal` and `affected-check` attributes are latent variables: they must produce `UNDETERMINED` or manual-review status, not be silently converted into “optional.”

# 3. Adversarial Review of Model S

**Strongest case for Model S.**  
Model S is small, fast, comprehensible, and robust to missing or irregular events. It enforces the obvious lifecycle boundaries and exactly one approval. For exploratory process discovery and business-user discussion, it communicates “there are several optional activities around the approval path” without drowning users in branch enumeration. Its high training/holdout fitness and high token generalization follow from its broad language.

**Strongest case against Model S.**  
Its broad language is not merely noise tolerance; it encodes policy errors. Credit Check and Technical Review are mandatory, but Model S makes them optional. Expedite Review must follow both mandatory checks, but Model S places it in the same optional parallel block. Supplier Review is conditional on an external/internal attribute, but Model S ignores the condition. Its permissiveness is therefore not just “missing events are tolerated”; it silently rewrites the governing policy.

**Concrete undesirable or policy-ambiguous behaviors admitted by Model S.**  

1. **Missing mandatory checks, forbidden B3:**  
   `Register Dossier, Manager Approval, Release Order`  
   S accepts because all four optional checks are skipped. Policy forbids this.

2. **Expedite before mandatory checks, forbidden B4:**  
   `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   S accepts because the whole block is parallel and optional. Policy requires Expedite after both mandatory checks.

3. **External order without Supplier Review:**  
   `Register Dossier, Credit Check, Technical Review, Manager Approval, Release Order`  
   S accepts even if the order is external and Supplier Review is required. The missing attribute is not modeled at all.

4. **Legitimate correction rejected despite safe policy:**  
   `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order`  
   S rejects because Correct Dossier and loops are absent. This is not a false accept, but it shows the model cannot express P6.

5. **Repeated check without correction is rejected, but by accident:**  
   `Register Dossier, Credit Check, Technical Review, Credit Check, Manager Approval, Release Order`  
   S rejects because each check appears at most once in the tree. This is desirable for P7, but S does not contain explicit correction semantics; it simply cannot loop.

6. **Ambiguous approval interaction with supplier/expedite:**  
   `Register Dossier, Supplier Review, Expedite Review, Auto Approval, Release Order`  
   S accepts even with no Credit or Technical. If those events are merely missing from the log, the model excuses a serious control failure rather than reporting missingness.

**Intentional noise tolerance vs accidental semantic flaw.** A small amount of intentional permissiveness might be defensible for exploring incomplete logs. But placing mandatory checks in `X(activity,tau)` and putting Expedite in the same parallel block as checks is an accidental semantic flaw: it confuses “may be absent from an imperfect log” with “is allowed by policy.” That is why high fitness and high token generalization are not redeeming here.

**Strongest case for Model C.**

| B5 `Register, Technical, Credit, Supplier, Expedite, Auto, Release` | Yes | No | Plausible valid external/urgent case. | C is too rigid; S is permissive but may accept for wrong reasons. Third should accept with external/supplier data check. |
| B6 `Register, Credit, Technical, Correct, Technical, Manager, Release` | No | No | Policy-dependent: valid only if correction affected Technical alone. | S lacks correction; C correction branch requires both checks. Third should accept conditionally with affected-check data. |
| B7 `Register, Credit, Technical, Supplier, Manager, Release` | Yes | Yes | Valid external case. | Both can accept simple supplier case; S does not enforce external requirement. |
| B8 `Register, Credit, Technical, Credit, Manager, Release` | No | No | Suspicious/forbidden without correction. | Both reject here; third must also reject explicitly via correction-control semantics. |

# 6. Likely Metric Pathologies

The pathologies below are ranked by likely decision impact for a governance board.

1. **Positive-log-only precision / absence of a negative behavior suite (highest impact).**  
   F5 states precision was computed only against observed positive traces. This does not establish that forbidden behavior is rejected. Model C’s 0.941 precision may partly reflect memorization; Model S’s 0.584 is not directly comparable to policy specificity. A model cannot be approved for compliance on positive-only precision.

2. **Fitness and generalization rewarded by optionalizing mandatory behavior.**  
   Model S achieves high training/holdout fitness and high token generalization partly because it makes Credit Check, Technical Review, Supplier Review, and Expedite Review optional and arbitrarily ordered. This is not benign noise tolerance; it permits B3 and B4. Any aggregate score that rewards this must be overridden by hard policy constraints.

3. **Missing attributes and missing-event bias.**  
   The log lacks `external/internal` and `affected-check` attributes. F4 also warns that Supplier Review events may be missing. S’s optional Supplier Review and optional mandatory checks are rewarded when events are absent. C’s exact branches reject missing events and unseen combinations. Neither cleanly distinguishes “missing from log” from “not performed.”

4. **Train/holdout leakage and split sensitivity.**  
   No random seeds, preprocessing code, or exact held-out cases were supplied. C’s branches may have been derived from the training split; holdout fitness drops to 0.744. S’s holdout fitness remains high because it accepts almost everything, not because it captures policy. Reproducibility is mandatory before believing either metric.

5. **Duplicate-label and branch-enumeration effects.**  
   Model C’s reported duplicate-label count of 33, combined with branch enumeration, makes alignment diagnostics, ownership, and impact analysis difficult. Duplicate labels can cause ambiguous alignment paths and obscure which business rule a branch is intended to represent. High precision on positives does not compensate for poor maintainability.

6. **Silent-transition effects.**  
   Model S contains multiple `tau` alternatives by making activities optional. Silent transitions can improve fitness and token-based generalization while hiding semantic skips. A skipped mandatory check may appear as a valid silent choice rather than a missing-event anomaly.

7. **Alignment-cost sensitivity.**  
   No alignment-cost settings were reported. Fitness, precision, and runtime all depend on model-move and log-move costs. C’s 0.440 s median runtime and lower fitness may change under different cost configurations. Results should be reported across documented cost settings.

8. **Stakeholder-score methodology.**  
   The 4.4 vs 1.9 informal comprehension scores are not a validated measure. S may be “easy” because it tells a simpler but false story. C may be “hard” because of branch clutter. The board should not use this score without a documented comprehension protocol and policy quiz.

# 7. Third Alternative

I design `model_third` as a **block-structured procedural backbone plus attribute/declarative policy checks**. The procedural backbone enforces the hard lifecycle and approval order while allowing conditional supplier review and correction/recheck cycles. The declarative checker enforces external/internal supplier requirements, affected-check correction semantics, and returns `UNDETERMINED` rather than silently accepting when attributes are missing.

**Compact formal description.**  
Let activities be `R` Register, `C` Credit Check, `T` Technical Review, `S` Supplier Review, `E` Expedite Review, `D` Correct Dossier, `M` Manager Approval, `A` Auto Approval, `O` Release Order. The control-flow language is approximately:

1. `R` first, `O` last.
2. Initial mandatory block: `C` and `T` each exactly once, in either order.
3. Zero or more correction cycles: `D` followed by exactly one or both of `C`,`T`; if both, either order. Repeated mandatory checks are allowed only after `D`.
4. Optional `S` may occur anywhere after `R` and before approval. Optional `E` may occur once after the initial mandatory block and after all correction/rechecks, and before approval. `S` and `E` may occur in either order relative to each other.
5. Exactly one of `M` or `A` occurs before `O`.
6. Data checks: if `external=True`, `S` is required; if missing and `S` absent, mark `UNDETERMINED`; if `correction_affected` is present, the checks repeated after each `D` must equal the affected set; if missing, mark `UNDETERMINED` for that correction.

**PM4Py code.**

```python
import pm4py
from collections import Counter

model_third_tree_string = """
->(
  'Register Dossier',
  +(
    ->(
      +('Credit Check', 'Technical Review'),
      *(
        tau,
        ->(
          'Correct Dossier',
          X(
            'Credit Check',
            'Technical Review',
            +('Credit Check', 'Technical Review')
          )
        )
      ),
      X('Expedite Review', tau)
    ),
    X('Supplier Review', tau)
  ),
  X('Manager Approval', 'Auto Approval'),
  'Release Order'
)
"""

model_third_tree = pm4py.parse_process_tree(model_third_tree_string)
model_third_net, model_third_im, model_third_fm = pm4py.convert_to_petri_net(model_third_tree)

MANDATORY = {"Credit Check", "Technical Review"}
APPROVALS = {"Manager Approval", "Auto Approval"}

def check_policy_v3(trace, attrs=None):
    """
    Returns (status, details) where status in {"valid", "invalid", "undetermined"}.
    This checker is intentionally explicit about missing attributes.
    """
    attrs = attrs or {}
    issues, undetermined, notes = [], [], []

    if not trace:
        return "invalid", {"issues": ["empty trace"], "undetermined": [], "notes": []}

    if trace[0] != "Register Dossier":
        issues.append("P1: must start with Register Dossier")
    if trace[-1] != "Release Order":
        issues.append("P1: must end with Release Order")

    approvals = [i for i, a in enumerate(trace) if a in APPROVALS]
    if len(approvals) != 1:
        issues.append("P5: exactly one approval required")
    appr = approvals[0] if approvals else len(trace)
    if appr >= len(trace) - 1:
        issues.append("P5: approval must precede release")
    if any(i > appr for i, a in enumerate(trace) if a != "Release Order"):
        issues.append("P5: no activity other than Release after approval")

    mand = [(i, a) for i, a in enumerate(trace) if i < appr and a in MANDATORY]
    corr = [i for i, a in enumerate(trace) if a == "Correct Dossier" and i < appr]
    if any(i > appr for i, a in enumerate(trace) if a == "Correct Dossier"):
        issues.append("P6: correction after approval")

    first_corr = corr[0] if corr else appr
    initial = [(i, a) for i, a in mand if i < first_corr]
    cnt = Counter(a for _, a in initial)
    if cnt["Credit Check"] != 1 or cnt["Technical Review"] != 1:
        issues.append(f"P2: initial mandatory counts are {dict(cnt)}")

    # Correction blocks: for each Correct Dossier, collect mandatory checks until next correction or approval.
    blocks = []
    for k, c in enumerate(corr):
        nxt = corr[k + 1] if k + 1 < len(corr) else appr
        repeated = [a for i, a in enumerate(trace[c + 1:nxt], start=c + 1) if a in MANDATORY]
        blocks.append((c, repeated))
        if not repeated:
            issues.append(f"P6: correction at index {c} has no recheck")
        cc = Counter(repeated)
        if any(cc[x] > 1 for x in MANDATORY):
            issues.append(f"P6: correction at index {c} repeats the same check more than once")

    # Every mandatory occurrence after first correction must lie in some correction interval.
    for i, a in mand:
        if i < first_corr:
            continue
        in_block = any(
            c < i < (corr[k + 1] if k + 1 < len(corr) else appr)
            for k, c in enumerate(corr)
        )
        if not in_block:
            issues.append(f"P7: repeated {a} at index {i} is not inside a correction block")

    # Affected-check semantics.
    affected_list = attrs.get("correction_affected")  # e.g. [ {"Technical Review"}, {"Credit Check"} ]
    if blocks:
        if affected_list is None:
            undetermined.append("P6: correction_affected attribute is missing")
        else:
            if len(affected_list) != len(blocks):
                issues.append("P6: correction_affected length does not match correction count")
            else:
                for (c, repeated), affected in zip(blocks, affected_list):
                    if set(repeated) != set(affected):
                        issues.append(
                            f"P6: correction at index {c} repeated {repeated}, "
                            f"but affected set is {sorted(affected)}"
                        )

    # Supplier Review.
    supplier_positions = [i for i, a in enumerate(trace) if a == "Supplier Review"]
    if len(supplier_positions) > 1:
        issues.append("P3: more than one Supplier Review")

    external = attrs.get("external", attrs.get("sourcing"))
    if isinstance(external, str):
        val = external.strip().lower()
        if val in {"external", "true", "1", "yes"}:
            external = True
        elif val in {"internal", "false", "0", "no"}:
            external = False
        else:
            external = None

    if external is True and len(supplier_positions) != 1:
        issues.append("P3: external order requires Supplier Review")
    elif external is False and len(supplier_positions) > 0:
        notes.append("P3: Supplier Review present on internal order; confirm whether allowed")
    elif external is None and len(supplier_positions) == 0:
        undetermined.append("P3: external/internal attribute missing and Supplier Review absent")

    # Expedite Review.
    expedite_positions = [i for i, a in enumerate(trace) if a == "Expedite Review"]
    if len(expedite_positions) > 1:
        issues.append("P4: at most one Expedite Review")
    if expedite_positions:
        e = expedite_positions[0]
        mand_positions = [i for i, a in enumerate(trace) if a in MANDATORY]
        if mand_positions and e < max(mand_positions):
            issues.append("P4: Expedite Review must follow all mandatory checks/rechecks")
        if e > appr:
            issues.append("P4: Expedite Review must precede approval")

    if any(i > appr and a in MANDATORY for i, a in enumerate(trace)):
        issues.append("P2/P5: mandatory check after approval")

    status = "invalid" if issues else ("undetermined" if undetermined else "valid")
    return status, {"issues": issues, "undetermined": undetermined, "notes": notes}

model_third = {
    "kind": "hybrid_procedural_declarative",
    "tree": model_third_tree,
    "net": model_third_net,
    "initial_marking": model_third_im,
    "final_marking": model_third_fm,
    "mandatory_checks": list(MANDATORY),
    "approvals": list(APPROVALS),
    "optional_supplier": "Supplier Review",
    "optional_expedite": "Expedite Review",
    "policy_checker": check_policy_v3,
}
```

**Required external checks / dictionaries.**  
- `external` or `sourcing`: Boolean or enum `{internal, external}` per case. Missing is not silently treated as internal.  
- `correction_affected`: list of sets, one per `Correct Dossier`, e.g. `[{"Technical Review"}, {"Credit Check", "Technical Review"}]`. Missing yields `UNDETERMINED` for correction validity.  
- Resource/approval authority checks are not in the log; if Manager vs Auto Approval depends on amount/source, that must be added as a data constraint.

**Explicit semantics.**  
- **Mandatory checks:** Initial `Credit Check` and `Technical Review` are both required exactly once in either order. They cannot be skipped.  
- **Optional Supplier Review:** Control-flow allows zero or one Supplier Review anywhere before approval. Data policy requires one for external orders. If sourcing is missing and Supplier Review is absent, status is `UNDETERMINED`.  
- **Expedite Review ordering:** At most one, after all mandatory checks and correction rechecks, before approval. Supplier Review is independent and may occur before or after Expedite Review.  
- **Exactly-one approval:** Exactly one of Manager Approval or Auto Approval occurs before Release Order.  
- **Correction/recheck:** `Correct Dossier` may repeat. Each correction must be followed by at least one and at most both mandatory checks; if both, either order. If `correction_affected` is present, the repeated set must equal the affected set. Repeated mandatory checks without a correction are rejected by the control-flow and checker.

**Limitations from missing attributes.**  
The model cannot know whether a supplier review was required when `external/internal` is absent. It cannot prove that only affected checks were repeated when `correction_affected` is absent. For compliance use, such cases must be `UNDETERMINED` and routed to manual review; for exploration, they can be flagged. If missingness is pervasive, no model should claim full compliance.

# 9. Validation Experiments

The evaluation must be reproducible and must separate exploratory vs enforcement claims.

**1. Reproducible case splits, seeds, and preprocessing.**

```python
from datetime import datetime, timedelta
import random
import numpy as np
import pandas as pd
import pm4py
from pm4py.objects.log.obj import EventLog, Trace, Event

# Pin and publish: pm4py version, Python version, hardware, code, seeds,
# filters, case-id field, timestamp ordering, and attribute extraction.

def traces_to_eventlog(traces, name="synthetic"):
    log = EventLog()
    for i, seq in enumerate(traces):
        tr = Trace()
        tr.attributes["concept:name"] = f"{name}_{i}"
        for j, act in enumerate(seq):
            e = Event()
            e["concept:name"] = act
            e["time:timestamp"] = datetime(2024, 1, 1) + timedelta(seconds=j)
            tr.append(e)
        log.append(tr)
    return log

def make_stratified_split(cases_df, seed=20240517, test_frac=0.20):
    """
    cases_df columns: case_id, stratum
    stratum should include external/internal/missing, approval type,
    supplier present, expedite present, correction affected, check order.
    Publish the resulting split file and hashes.
    """
    rng = np.random.default_rng(seed)
    parts = []
    for _, grp in cases_df.groupby("stratum", dropna=False):
        ids = grp["case_id"].to_numpy()
        rng.shuffle(ids)
        n_test = max(1, int(round(len(ids) * test_frac))) if len(ids) > 1 else 0
        parts.append(pd.DataFrame({"case_id": ids[:n_test], "split": "test"}))
        parts.append(pd.DataFrame({"case_id": ids[n_test:], "split": "train"}))
    return pd.concat(parts, ignore_index=True)
```

```python
def drop_events(log, p, seed):
    rng = random.Random(seed)
    out = EventLog()
    for tr in log:
        nt = Trace()
        nt.attributes.update(tr.attributes)
        for e in tr:
            if rng.random() >= p:
                nt.append(e)
        out.append(nt)
    return out

def duplicate_events(log, p, seed):
    rng = random.Random(seed)
    out = EventLog()
    for tr in log:
        nt = Trace()
        nt.attributes.update(tr.attributes)
        for e in tr:
            nt.append(e)
            if rng.random() < p:
                nt.append(e)
        out.append(nt)
    return out
```

**9. Stakeholder comprehension protocol.**  
Use a documented sample, balanced by role and experience. Ask users to classify B1–B8 and the additional adversarial traces as valid/forbidden/needs-review, then explain why. Measure correctness, time, confidence, and inter-rater agreement. Do not use a single informal 1–5 score. Test both the full third model and a simplified communication view.

**10. Decision rule for rejection despite good aggregate metrics.**  
Reject a model for enforcement if any of the following hold:  
- It accepts any trace in the mandatory-check, exactly-one-approval, or repeated-check-without-correction negative suite.  
- It cannot be shown sound or reachable due to conversion errors.  
- Missing `external/internal` or `correction_affected` attributes are silently treated as optional/valid rather than `UNDETERMINED`.  
- Holdout degradation is large and driven by legitimate unseen combinations, not just noncompliance.  
- Precision on the curated negative suite is unacceptably low.  
- Stakeholder policy-quiz error rate is high even if the informal score is high.  
- Alignment runtime is operationally infeasible or highly sensitive to undocumented costs.  

For exploration, a model may be retained despite these failures only if it is clearly labeled non-enforcing and never drives approval decisions.

# 10. Governance Recommendation

**Exploration use.**  
Model S may be used only as an exploratory “optional-activity map” with a visible warning: it does not represent mandatory checks or policy ordering. It must not be used for conformance, audit, approval, or operational decisions. Model C may be used as a regression catalog of known observed variants and for comparing whether a new case resembles a frequent historical variant. It should not be treated as the governing process because it rejects legitimate unseen combinations and is difficult to maintain.

**Compliance use.**  
Neither original model is recommended for compliance. Model S is unacceptable because it permits mandatory-check and expedite-ordering violations. Model C is too brittle and overfit; its high positive-log precision does not compensate for holdout degradation, branch enumeration, duplicate-label ambiguity, and inability to handle affected-check corrections cleanly. The third alternative is the only candidate for compliance, and only after the validation program above is passed.

**Retirement.**  
Retire Model S from any enforcement or policy role. Retire Model C as a candidate enterprise process model; keep it, if useful, as a historical variant catalog or regression artifact, not as the normative model. The organization should adopt `model_third` as the governance candidate, with manual review for `UNDETERMINED` cases.

**Conditions before deploying the third alternative.**  
- The PM4Py process tree must be sound, and reachability checks must show no release before approval and no dead required transitions.  
- The curated negative suite must have zero false accepts for hard constraints P2, P5, P7, and expedite ordering.  
- `external/internal` and `correction_affected` data must be captured or generated. Until then, missing-attribute cases must be routed to review, not auto-approved.  
- Holdout tests must be stratified and reproducible, with seeds and preprocessing published.  
- Stakeholder comprehension must be tested by policy quiz, not informal score.  
- Runtime and alignment-cost sensitivity must be documented.  
- Ownership and change impact must be mapped to small blocks, not enumerated traces.

# 11. Dissenting View

The recommendation may be too harsh on Model C and too optimistic about the hybrid. If the holdout drop is driven by unapproved missing-supplier events, repeated checks without corrections, or undeclared behavior, C’s 0.744 fitness is not evidence of overfitting but evidence that the log is contaminated. In a regulated audit, false acceptance is usually worse than false rejection; C’s high training precision and strict branch control may be safer until model_third’s external/internal and correction-affected data are populated. The hybrid also depends on data constraints that do not yet exist. Without those attributes, it will either block many legitimate cases as undetermined or, worse, teams will bypass the undetermined status and release orders. Its correction loop and supplier parallelization are more general, but also create policy-ambiguous traces that Model C simply refuses. If operations can tolerate manual review, C’s “unseen means escalate” stance may be preferable. I would change my decision if stratified holdout shows C’s rejections are mostly legitimate unseen combinations, if negative-suite testing shows model_third has false accepts without attributes, or if the organization cannot populate sourcing and affected-check fields; then C could remain a conservative manual-review gate and S a pure exploration view, while the hybrid is not yet deployable.
