## 1. Duplicate-handling decision tree

Candidate generation must be broader than the eventual merge rule. Grouping by activity, timestamp, or shared objects is useful for review, but never constitutes proof of duplication.

1. **Is this a replay of the same source record?**
   - Require the same source and `source_event_key`, compatible `source_seq`, identical business timestamp/activity, equivalent payload and relations, and differences confined to ingestion metadata.
   - **Exact technical duplicate:** retain one canonical event and **drop only the redundant technical copy**. Preserve every replay ID, ingestion time, and payload hash in lineage.
   - If the source key agrees but business content conflicts, treat it as an **unresolved candidate**, not an exact duplicate.

2. **Is there independent evidence that multiple records observe one physical/business event?**
   - Examples include reconciliation reports, message correlation IDs, or a common invoice identity supported by source documentation.
   - **Verified same event:** **merge attributes and relations into a canonical composite**, with field-level source authority and complete member lineage. Do not merely keep the first payload.
   - If observation latency or system-specific processing is itself analytically important, **retain both with observation qualifiers** and a `same_business_event` link instead.

3. **Is one record derived from another at a different abstraction level?**
   - For a verified one-to-one summary/detail pair, an evidence-based scenario may **merge into the detailed event**, retaining summary attributes as source-namespaced observations.
   - If the abstraction is useful, the summary aggregates several detailed events, or the correspondence is uncertain, **retain both with refined labels/qualifiers** and a `derived_from` link. A summary must not inherit detailed object relations automatically.

4. **Did harmonization combine different source activities?**
   - Inspect original source labels and documented semantics.
   - **Harmonization collision:** **retain both with refined labels or qualifiers**. Restore the source distinction; do not merge attributes or relations merely because timestamps and objects coincide.

5. **Are these concurrent, same-label events distinguished by their objects or business identifiers?**
   - Different items, payments, packages, or source transaction keys are strong counter-evidence to duplication.
   - **Distinct concurrent events:** **retain both unchanged**, except for optional explanatory qualifiers. Shared higher-level objects do not override this distinction.

6. **Is evidence insufficient or contradictory?**
   - **Unresolved candidate:** retain both unchanged in the working log, flag the candidate set, and **quarantine it for review** in a decision queue. A strict publication may quarantine copies separately, but must never delete the raw records.

## 3. Timestamp-tie ordering rules

Construct a partial order first, then a reproducible topological projection:

1. **Original business timestamps** order different timestamp groups. Within a tie, they provide no order.
2. **Semantic domain constraints** include explicit facts such as e12e13 and e09e10. Summary generation can constrain *observation order* when message lineage is established.
3. **Within-source `source_seq`** may constrain records from that source after its monotonic meaning is validated. Never compare WMS sequence 100 with scanner sequence 551 or PSP sequence 400.
4. **Lifecycle constraints** must be validated per object type. Item/package lifecycles can support pick-before-pack; a payment state machine supports authorization-before-capture for M1. Sharing O1 alone must not create a lifecycle chain through every event.
5. **Source-specific semantics** distinguish release, acceptance, handover, detail, and summary. A fixed source priority such as “ERP before carrier” is not semantic.
6. **`ingested_at`** is diagnostic only. It is neither a business-order rule nor a preferred tie-breaker.
7. **Stable fallback:** run Kahn’s topological sort and choose among ready nodes by canonical eid, or another fixed source/key/eid tuple. Record `order_key` and `tie_group_id`. This step is deterministic, not semantic. Cycles or timestamp/constraint conflicts require review.

Adding microseconds before this process would turn input order, ingestion order, or alphabetical order into apparently causal directly-follows edges. It would also manufacture durations. Synthetic timestamps are acceptable only afterward, in a separate algorithm view.

    return True

def merge_verified(ocel, keep, absorb, rule, reason,
                   authority=None, relation_mode="identical"):
    """
    Canonical composite merge with full snapshots.

    relation_mode='identical' permits only identical relation scopes.
    relation_mode='subset' permits absorbed relations to be a subset of the
    detailed canonical event's relations. It never performs a blind union.
    authority maps an attribute name to its authoritative source system.
    All nonselected/conflicting values remain in lineage_json and raw input.
    """
    authority = authority or {}
    ev = ocel.events
    ids = ev[EID].astype(str)
    assert keep in set(ids) and absorb in set(ids)

    keep_rels = relation_set(ocel, keep)
    absorb_rels = relation_set(ocel, absorb)
    if relation_mode == "identical":
        assert keep_rels == absorb_rels, "Incompatible E2O scopes"
    elif relation_mode == "subset":
        assert absorb_rels <= keep_rels, "Not a safe detail/summary scope"
    else:
        raise ValueError("Unsupported relation policy")

    rows = {}
    for eid in (keep, absorb):
        rows[eid] = ev.loc[ids == eid].iloc[0].copy()

    ki = ev.index[ids == keep][0]
    for column, source_name in authority.items():
        if column not in ev.columns:
            continue
        for row in rows.values():
            if row.get("source") == source_name:
                ev.at[ki, column] = row[column]

    for column in ("lineage_json", "merged_member_eids"):
        if column not in ev.columns:
            ev[column] = ""
    snapshot = {eid: row.to_dict() for eid, row in rows.items()}
    ev.at[ki, "lineage_json"] = json.dumps(snapshot, default=str)
    ev.at[ki, "merged_member_eids"] = json.dumps([keep, absorb])

    audit.append({
        "canonical_eid": keep,
        "source_eids": [keep, absorb],
        "merge_rule": rule,
        "rule_version": "v1",
        "reason": reason,
        "attribute_authority": authority,
        "relation_mode": relation_mode,
        "snapshots": snapshot
    })

    # Canonical relations already contain the permitted absorbed scope.
    ocel.relations = ocel.relations[
        ocel.relations[EID].astype(str) != absorb].copy()
    ocel.events = ev[ev[EID].astype(str) != absorb].copy()
    validate_ocel(ocel)
    return ocel

def relabel(ocel, mapping):

        mask = ocel.events[EID].astype(str) == eid
        assert mask.sum() == 1
        ocel.events.loc[mask, ACT] = new_label
    return ocel

## 7. Sensitivity analysis

Counting each listed object membership once, the expected sizes are:

| Dataset | Events | E2O relations | Principal interpretation |
|---|---:|---:|---|
| Raw | 17 | 44 | Observation-rich, but duplicate and harmonization effects remain |
| Conservative | 15 | 39 | Two verified composite merges; legitimate concurrency and abstractions retained |
| Evidence-based merge | 14 | 37 | Additionally absorbs e07; e06 retains its four detailed relations |
| Aggressive library merge | 10 | Approximately 28 with union/deduplicated relations | Library/version-dependent; useful only as a damage counterfactual |

The actual aggressive relation count must be measured: a library that keeps canonical relations rather than unioning them can lose even more objects.

**Order-flattened DFG.** Under a row/index tie projection, raw data can contain `Pick ItemPick Item` twice, `Pack PackagePack Package`, `Dispatch PackageDispatch Package`, repeated `Issue Invoice`, and several capture self-transitions. Conservative cleaning changes their meanings rather than merely reducing counts:

1. `Pick ItemPick Item` falls from two raw transitions to one, e03e05. That remaining self-loop represents picks of different items, not established rework.
2. `Pack PackagePack Package` becomes `Pack PackagePacking Status Update`; evidence merging removes the latter observation entirely.
3. `Dispatch PackageDispatch Package` becomes `Release from WarehouseCarrier Acceptance`. Aggressive merging instead leaves one generic dispatch and erases that boundary.
4. A possible `Issue InvoiceIssue Invoice` loop disappears after verified merging, without discarding either source’s attributes.
5. Raw `Capture Payment` frequency is three, but one occurrence is e15’s summary. Conservative frequency is two: one `Capture PaymentCapture Payment` edge for M1/M2, followed by `Capture PaymentInvoice Payment Summary`. Aggressive frequency is one and the partial-payment pattern disappears.
6. Raw tie sorting can also produce a misleading edge back into `Issue Invoice` from a payment-labelled event because e16 occurs late in the table. Conservative summary-last ordering removes that artefact without claiming it proves physical order.

**Item-flattened DFG.** For I1, raw can show `Pick ItemPick ItemPack Package`; conservative shows `Pick ItemPack Package`. I2 retains its own e05e06 path. Aggressive merging hides the two concurrent picks and can make one canonical pick event appear to serve both items.

**Payment-flattened DFG.** M1 remains `Authorize PaymentCapture Payment`; M2 remains a separate capture-only path in raw and conservative data. e15 is absent from payment flattening because it has no Payment object. With union semantics, aggressive merging makes M1 and M2 share one capture event; with canonical-relation semantics, M2 might disappear altogether.

**OC-DFG, ET–OT, and OTG.** Conservative OC-DFG frequencies distinguish two picks, two captures, and one invoice issuance, while introducing semantically useful release/acceptance and summary edges. Raw duplicate observations inflate Pick–Item, Pick–Package, Issue Invoice–Invoice, and related weights. Raw also assigns `Capture Payment–Invoice` weight to e15; conservative moves that contribution to `Invoice Payment Summary–Invoice`. Aggressive capture merging reduces event-based Capture–Payment weight while potentially making one event reference two Payment objects. OTG co-occurrence weights therefore change even where no new object-type edge appears; a single aggressive event can become artificial evidence for tighter Order–Invoice–Payment coupling.

Finally, apparent loops, processing times, and handoffs are highly sensitive. Aggressive dispatch merging removes warehouse-to-carrier performance analysis. Treating e06/e07 as two physical packs creates false packing rework; merging them unconditionally removes ERP integration latency. Synthetic microseconds create artificial pick, capture, and handover durations. Lifecycle and performance KPIs should use original timestamps, report tied intervals as unresolved at second precision, and use the strict view only for algorithms requiring distinct timestamps.

## 8. Audit trail and reversibility

Use three linked provenance structures:

- **Event lineage:** `canonical_eid`, `source_eid`, source system/key/sequence, member role, original payload hash, original/refined activity, original/adjusted timestamp, original E2O snapshot, and raw-row hash.
- **Decisions:** rule ID/version, reviewer, evidence reference, confidence, reason, scenario, relation policy, ordering constraints, deterministic fallback, and review status.
- **Attribute lineage:** canonical attribute, source eid/value, selected value, authority rule, nonselected or conflicting value, and disposition. “Discarded” means excluded from the canonical view, not deleted from provenance.

The raw view is reconstructed most safely by reloading immutable `ocel_raw` using the recorded raw-log hash. A self-contained cleaned export can also be expanded: restore each member snapshot and its original eid, activity, timestamp, source metadata, attributes, and relations; remove canonical composites and synthetic ordering/timestamps; then verify hashes and counts. Refined labels and ordering projections are therefore reversible transformations.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments:** e13/e14 share O1/V1. Require compatible Payment identity before merging and explicitly assert e14’s survival.
2. **False rework from abstraction-level updates:** repeated Pack or Capture labels can represent status/summary records. Refine labels and mark abstraction level rather than counting loops automatically.
3. **Ordering by ingestion time:** e07/e15 arrive later technically. Exclude `ingested_at` from business ordering and use it only for ingestion diagnostics.
4. **Treating shared objects as proof:** common O1, P1, or V1 is candidate evidence only. Inspect discriminating Item, Payment, Delivery, and source transaction identities.
5. **Unioning incompatible E2O relations:** merging e15 into a capture could attach M1/M2 to an invoice summary. Require identical or explicitly approved subset scopes; otherwise retain separate events.
6. **Changing durations through synthetic microseconds:** downstream tools may report artificial processing times. Preserve original timestamps and confine adjustments to a disposable algorithm view.
7. **Losing source-authoritative attributes:** first/last-row-wins can discard WMS location or billing/ERP invoice attributes. Use field-level authority and source-namespaced conflict retention.
8. **Applying duplicate functions to the whole OCEL:** activity/timestamp groups contain known counterexamples. Inspect candidate reports first and restrict library operations to justified scenarios.
9. **Comparing source sequences across systems or creating cycles:** sequence numbers have only local meaning. Validate monotonicity, map merged-member constraints carefully, and quarantine cycles.
10. **Irreversible IDs or dangling relations:** canonicalization can strand E2O rows or erase member identity. Validate event/object references, uniqueness, expected survivors, counts, and lineage after every transformation.
