# 1. Evidence Ledger

The evidence identifies a family of possible processes, not a unique causal model. The candidates below model **completed activity sequences**. Their accepted languages are nested: conservative ⊂ balanced ⊂ permissive. They contain respectively 7, 14, and 18 distinct complete traces; these are language sizes, not estimated probabilities.

All 30 records contain R, C, E, A, P, Z exactly once. S appears in 23 and X in 2. C appears before E in 19 complete traces and E before C in 11. In every recorded S case, C is before S; E is before S in 21 of those 23. These are descriptive frequencies, not universal constraints.

**Why bidirectional DFG edges do not prove concurrency.** C→E and E→C can arise from concurrent work, an XOR choice between two sequential orders, different policies in different case classes, or ingestion ordering of timestamp ties. In general, repetitions can also create both directions, although these particular traces contain no repetitions. Likewise, the two directions between S and X establish two recorded orders, not temporal overlap. A DFG also discards the surrounding case context, so connecting its edges freely can generate paths that no observed case contains.

# 2. Shared Assumptions

1. **Observation semantics and scope.** Each visible node denotes a logged completion, not an activity's full start-to-finish interval. A model ordering is an order of these abstract occurrences. Neither a ProcessTree parallel operator nor incomparable POWL nodes establish actual overlap. The scope is completed, successful, single-pass orders; cancellation, failure, rework, and open cases are outside the supplied evidence.

2. **Common skeleton and cardinalities.** Every complete modeled trace has R first, exactly one C and E, then A before P, and Z last. It contains at most one S and at most one X. A, P, and Z form the observed terminal sequence. The absence of loops, the single occurrences, and terminal adjacency are explicit assumptions stronger than D1/D2 alone. D3, D4, and D6 are adopted as shared constraints despite their less-than-high confidence.

3. **Hidden requirement and missingness.** A visible trace without S has at least two possible explanations: no supplier confirmation was required, or required confirmation occurred but its event was lost. An actual omission of required confirmation is a third possibility to investigate, not a compliant explanation inferred by these models. If an external component requires confirmation, an accepted visible omission can be consistent with compliance only through a suitable hidden, completed confirmation. The models cannot establish that this happened.

4. **No invented attribute guard.** External/stocked status is not present, so none of the candidates implements or learns a reliable data-dependent guard. For mixed-component orders, the eventual guard may need to mean “any component requires confirmation.” The seven absent events cannot be allocated between causes from this export. Under a homogeneous loss mechanism, a 5–10% event-loss rate on roughly 23–30 true confirmations would suggest only a few missing events, but this is a rough sensitivity argument, not a case classification or an identified skip rate.

5. **Optionality is an observation abstraction.** Write `Y? = XOR(τ,Y)`, where τ is silent. For X, τ represents no expedite review. For S, τ conflates legitimate non-requirement with a completed but unlogged confirmation. Conservative enumeration represents the same distinction through branches without an S label. No candidate labels these hidden causes separately, and no branch probability is inferred. In particular, random playout frequencies are not business probabilities.

6. **Policy conflicts remain visible.** No candidate treats S1 as a universal lifecycle constraint. All accept the recorded E-before-C orders. If S1 is authoritative and the timestamps are reliable, some observations are deviations rather than examples to generalize. Conversely, accepting those sequences does not settle the conflict in favor of S2.

For the expressions below, `·` denotes sequence, `∥` denotes shuffle/parallel composition of completion occurrences, and `XOR` chooses one child. `PO(N;F)` denotes a partial order on child nodes N generated by precedence edges F and their transitive closure. Each child must finish before a successor child is enabled. Optional children may finish silently.

# 3. Conservative Candidate

**Inductive bias.** This is a closed-world model of the seven exported variants, with their common boundaries factored out. It prioritizes avoiding unsupported additional complete traces over recovering the underlying business process. Frequencies describe the evidence but do not change its language. The model intentionally preserves accidental correlations, such as observing X only together with S. It therefore overfits this sample and can underfit the true process at the same time.

**Compact formal expression**

Let `T(w) = R · w · A · P · Z`. Then:

```text
model_conservative = T(XOR(
    C·E·S, E·C·S, C·E, E·C, C·S·E, C·E·S·X, E·C·X·S
))
```

**Self-contained PM4Py code — ProcessTree**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

LABEL = {
    'R': 'Register Order', 'C': 'Credit Check',
    'E': 'Engineering Review', 'S': 'Supplier Confirmation',
    'X': 'Expedite Review', 'A': 'Approve Configuration',
    'P': 'Release Production', 'Z': 'Archive Case',
}

def leaf(symbol):
    return ProcessTree(label=LABEL[symbol])

def tree(operator, *children):
    node = ProcessTree(operator=operator)
    node.children = list(children)
    for child in children:
        child.parent = node
    return node

def sequence(symbols):
    return tree(Operator.SEQUENCE, *(leaf(s) for s in symbols.split()))

cores = ['C E S', 'E C S', 'C E', 'E C', 'C S E',
         'C E S X', 'E C X S']
model_conservative = tree(
    Operator.SEQUENCE,
    leaf('R'),
    tree(Operator.XOR, *(sequence(core) for core in cores)),
    leaf('A'), leaf('P'), leaf('Z'),
)
```

Each XOR alternative needs **fresh node objects**, even when labels repeat. Duplicate labels across alternatives are allowed: a complete case chooses one branch and does not execute every same-named node. Such duplication can make alignments less identifiable and split transition-frequency evidence used by structural or replay-based metrics. Enumeration grows with the number and length of variants; it is a poor scalable substitute for discovering a shared dependency structure.

**Behavior deliberately excluded**

- Every unrecorded complete sequence, including E·S·C, despite D5 making it plausible.
- X without a visible S, and new combinations of X with otherwise observed check/supplier orders.
- S before both principal completions, repeated activities, and deviations from the common completion skeleton.

**Known underfitting risks**

- New legitimate interleavings require new branches even when no business rule has changed.
- Loss of S from either expedite trace produces C·E·X or E·C·X, neither of which is accepted. Thus, observed non-expedite omissions do not make this model generally robust to the stated logging fault.
- Sparse external/stocked and expedite combinations remain excluded because they were not sampled.
- Any real rework, exception handling, or lifecycle overlap absent from the visible variants remains unrepresented.

# 4. Balanced Candidate

**Inductive bias.** This candidate combines shared approval prerequisites with modest recombination of optional activities. It leaves the principal check completions unordered, allows supplier completion after at least one principal completion, and allows expedite completion after both checks regardless of supplier presence or relative position. The supplier prerequisite is a deliberately stronger, observable proxy for D5's ambiguous “enough information.” The model admits an engineering-enabled supplier route despite all 23 recorded S events following C, because D5 specifically supports either source. That choice is a declared generalization, not a discovered fact.

**Compact formal expression**

```text
S? = XOR(τ,S)                     X? = XOR(τ,X)
Q_C = PO({C,E,S?,X?}; {C<S?, C<X?, E<X?})
Q_E = PO({C,E,S?,X?}; {E<S?, C<X?, E<X?})
model_balanced = R · XOR(Q_C,Q_E) · A · P · Z
```

Its visible-language constraint on a present S is `(C before S) OR (E before S)`. This is a disjunctive prerequisite. Putting both edges into one partial order would instead require **both** completions and would reject V5. The two POWL alternatives express the union of the two enabling hypotheses. They overlap when both checks precede S or S is absent; this is not evidence of an exclusive business decision, nor are the two principal checks alternatives to each other.

**Self-contained PM4Py code — POWL**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

LABEL = {
    'R': 'Register Order', 'C': 'Credit Check',
    'E': 'Engineering Review', 'S': 'Supplier Confirmation',
    'X': 'Expedite Review', 'A': 'Approve Configuration',
    'P': 'Release Production', 'Z': 'Archive Case',
}

def poset(children, edges):
    relation = set(edges)
    while True:
        expanded = relation | {
            (i, k) for i, j in relation for j2, k in relation if j == j2
        }
        if expanded == relation:
            break
        relation = expanded
    if any(i == j for i, j in relation):
        raise ValueError('Cyclic partial order')
    node = StrictPartialOrder(children)
    for i, j in sorted(relation):
        node.order.add_edge(children[i], children[j])
    return node

def optional_powl(symbol):
    return OperatorPOWL(
        Operator.XOR, [SilentTransition(), Transition(LABEL[symbol])]
    )

def supplier_gate(gate):
    children = [Transition(LABEL['C']), Transition(LABEL['E']),
                optional_powl('S'), optional_powl('X')]
    return poset(children, [(gate, 2), (0, 3), (1, 3)])

children = [
    Transition(LABEL['R']),
    OperatorPOWL(Operator.XOR, [supplier_gate(0), supplier_gate(1)]),
    Transition(LABEL['A']), Transition(LABEL['P']), Transition(LABEL['Z']),
]
model_balanced = poset(children, [(i, i + 1) for i in range(4)])
```

**Sequence, concurrency, and partial-order decisions**

- **C and E:** They are mandatory and incomparable within either POWL branch. V1/V2 and D7 make a fixed universal completion order unjustified; S2 supports the unordered hypothesis. This represents both completion orders without claiming actual overlap. An XOR of sequential check orders remains observationally indistinguishable when only those two completions are considered.
- **S:** It is optional in the observed-event sense. A present S follows at least one check completion, but need not follow both. This retains C·S·E from V5 and adds E·S·C using D5. Requiring C specifically would fit the data but would ignore D5's engineering-enabled possibility. Allowing S before either completion is reserved for the permissive sensitivity model.
- **X:** It is independently optional, follows both check completions, and is incomparable with S once prerequisites permit their respective occurrences. D6/S6 justify this; V6/V7 directly support both S–X orders. Independent optionality admits X with no visible S, through either stocked components or event loss; no such combination was observed.
- **A and the suffix:** A waits for both checks and every present optional activity. R and A·P·Z remain sequential boundaries. These joins implement D3/D4/D6, rather than relying on particular DFG paths.

**Behavior deliberately excluded**

- S as the first completion after R, even if a check might already have supplied partial information.
- X before either check has completed, X after A, or more than one X.
- Approval without both checks, supplier completion after approval, production release before approval, and repetition/rework.

**Known underfitting risks**

- A supplier may finish using partial information while both checks are still running; the completion-based supplier gate would incorrectly reject that visible order.
- A real exception to D3 or D6, or a tie artifact that displays X before a prerequisite, is rejected without a lifecycle-aware repair layer.
- Conditional eligibility, component-level repetition, rework, and additional exception routes are not represented.

The two gate branches duplicate C/E/S/X labels and can accept the same word through different internal paths. This is disclosed modeling redundancy, with implications for transition-frequency metrics; it does not mean an activity is repeated within a case.

# 5. Permissive Candidate

**Inductive bias.** This candidate removes the unverified requirement that a principal check must fully complete before supplier completion. It interprets D5 literally as an information-availability condition that may occur during a check, and projects that unlogged milestone out of the completion model. S can consequently finish before either principal completion. Approval and expedite prerequisites remain unchanged. The extra freedom is specifically about unobserved supplier interleavings, not arbitrary permutations or weakened approval controls.

**Compact formal expression**

```text
model_permissive = R · [ ((C ∥ E) · X?) ∥ S? ] · A · P · Z
```

For example, R·S·C·E·A·P·Z has a plausible hidden lifecycle refinement: after R, start C; C produces sufficient information; S starts and finishes; C and E finish; approval follows. This satisfies the information interpretation of D5 even though S is the first visible completion after registration. The tree does not observe or enforce the hidden milestone. If D5 actually requires a **completed** check, this interpretation is wrong and those additional traces must be forbidden.

**Self-contained PM4Py code — ProcessTree**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

LABEL = {
    'R': 'Register Order', 'C': 'Credit Check',
    'E': 'Engineering Review', 'S': 'Supplier Confirmation',
    'X': 'Expedite Review', 'A': 'Approve Configuration',
    'P': 'Release Production', 'Z': 'Archive Case',
}

def leaf(symbol):
    return ProcessTree(label=LABEL[symbol])

def tree(operator, *children):
    node = ProcessTree(operator=operator)
    node.children = list(children)
    for child in children:
        child.parent = node
    return node

def optional_tree(symbol):
    return tree(Operator.XOR, ProcessTree(), leaf(symbol))

model_permissive = tree(
    Operator.SEQUENCE,
    leaf('R'),
    tree(Operator.PARALLEL,
         tree(Operator.SEQUENCE,
              tree(Operator.PARALLEL, leaf('C'), leaf('E')),
              optional_tree('X')),
         optional_tree('S')),
    leaf('A'), leaf('P'), leaf('Z'),
)
```

**Boundary of reasonable generalization**

The model allows any ordering of a present S relative to C/E/X that can be explained by unlogged information availability, while X still follows C and E and all present work precedes A. It also allows combinations of independent optional decisions, such as X without a visible S. These are hypotheses to test. Physically skipping a required supplier action on an external-component case remains contrary to the adopted domain rule; the completion-only tree cannot distinguish that breach from loss of its event.

**Behavior deliberately excluded**

- X before both principal completions, after approval, or repeated.
- Approval before either principal completion or before any present S/X; release without prior approval.
- Missing principal checks, repeated supplier/check activities, cancellation, rework, and changes to the R…A·P·Z skeleton.
- A lifecycle in which S begins before any sufficient information exists is not endorsed, although the projected tree cannot detect that condition from completion labels alone.

**Known underfitting risks**

- The common single-pass assumptions still exclude legitimate repeated checks, separate confirmations per supplier, and post-approval revisions.
- Missing events other than S and real exceptions to the adopted prerequisites remain unsupported.
- It cannot describe timing, resource constraints, or conditions determining supplier/expedite eligibility.

Its main additional **overgeneralization** risk is admitting S-first completions that would be impossible if supplier work requires a fully completed principal check. Its structurally simple tree should not be mistaken for stronger evidence.

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|

Fitness alone cannot select the process explanation because every candidate fits the observed visible sequences. Alignment precision is relative to this small log, and replay-based generalization is a heuristic, not evidence that an unseen trace is valid. Duplicate transitions, silent routing, and Petri-net encoding affect structural and replay-based scores. Tiny deviations of a reported aggregate fitness from one can also arise from silent-move costs or normalization; exact acceptance is checked separately below.

# 8. Validation Code

The following script is independent of the preceding code blocks. It reconstructs all 30 cases, builds all three candidates, converts them to accepting Petri nets `(net, im, fm)`, checks soundness, attempts every requested metric, enumerates bounded executions, performs sampled playout, and checks an explicit positive/negative suite. An additional permutation specification checks that the implementation matches the declared finite languages; it does not validate the business assumptions.

This code was run locally with PM4Py 2.7.23.8. All three soundness checks and the manual suite passed, and exhaustive exploration returned 7, 14, and 18 complete visible traces respectively. All four requested metric APIs ran successfully. The script prints their returned values rather than treating them as estimates of causal truth. It reports unavailable/failed metric APIs explicitly; a missing or failing soundness check is not treated as success.

```python
import itertools
from collections import Counter, deque

import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)
from pm4py.objects.petri_net import semantics

LABEL = {
    'R': 'Register Order', 'C': 'Credit Check',
    'E': 'Engineering Review', 'S': 'Supplier Confirmation',
    'X': 'Expedite Review', 'A': 'Approve Configuration',
    'P': 'Release Production', 'Z': 'Archive Case',
}
VARIANTS = [
    (12, 'R C E S A P Z'), (7, 'R E C S A P Z'),
    (4, 'R C E A P Z'), (3, 'R E C A P Z'),
    (2, 'R C S E A P Z'), (1, 'R C E S X A P Z'),
    (1, 'R E C X S A P Z'),
]

def word(symbols):
    return tuple(LABEL[s] for s in symbols.split())

# Every call creates fresh nodes, including repeated labels in XOR branches.
def leaf(symbol):
    return ProcessTree(label=LABEL[symbol])

def tree(op, *children):
    node = ProcessTree(operator=op)
    node.children = list(children)
    for child in children:
        child.parent = node
    return node

def sequence(symbols):
    return tree(Operator.SEQUENCE, *(leaf(s) for s in symbols.split()))

def optional_tree(symbol):
    return tree(Operator.XOR, ProcessTree(), leaf(symbol))

def poset(children, edges):
    # Explicit transitive closure; edges refer to child indices.
    relation = set(edges)
    while True:
        expanded = relation | {
            (i, k) for i, j in relation for j2, k in relation if j == j2
        }
        if expanded == relation:
            break
        relation = expanded
    if any(i == j for i, j in relation):
        raise ValueError('Cyclic partial order')
    node = StrictPartialOrder(children)
    for i, j in sorted(relation):
        node.order.add_edge(children[i], children[j])
    return node

def optional_powl(symbol):
    return OperatorPOWL(
        Operator.XOR, [SilentTransition(), Transition(LABEL[symbol])]
    )

def supplier_gate(gate):
    # 0=C, 1=E, 2=S?, 3=X?. C and E remain incomparable.
    children = [Transition(LABEL['C']), Transition(LABEL['E']),
                optional_powl('S'), optional_powl('X')]
    return poset(children, [(gate, 2), (0, 3), (1, 3)])

def build_models():
    conservative = tree(
        Operator.SEQUENCE, leaf('R'),
        tree(Operator.XOR, *(sequence(core) for core in [
            'C E S', 'E C S', 'C E', 'E C', 'C S E',
            'C E S X', 'E C X S',
        ])), leaf('A'), leaf('P'), leaf('Z'),
    )
    balanced_children = [
        Transition(LABEL['R']),
        OperatorPOWL(Operator.XOR, [supplier_gate(0), supplier_gate(1)]),
        Transition(LABEL['A']), Transition(LABEL['P']), Transition(LABEL['Z']),
    ]
    balanced = poset(balanced_children, [(i, i + 1) for i in range(4)])
    permissive = tree(
        Operator.SEQUENCE, leaf('R'),
        tree(Operator.PARALLEL,
             tree(Operator.SEQUENCE,
                  tree(Operator.PARALLEL, leaf('C'), leaf('E')),
                  optional_tree('X')),
             optional_tree('S')),
        leaf('A'), leaf('P'), leaf('Z'),
    )
    return {'conservative': conservative, 'balanced': balanced,
            'permissive': permissive}

models = build_models()
model_conservative = models['conservative']
model_balanced = models['balanced']
model_permissive = models['permissive']

# Net reachability, including silent transitions; no replay-cost heuristic.
def marking_key(marking):
    return frozenset((place, count) for place, count in marking.items() if count)

def accepts(net, im, fm, trace, state_limit=200000):
    queue = deque([(im, 0)])
    seen = {(marking_key(im), 0)}
    final = marking_key(fm)
    while queue:
        marking, index = queue.popleft()
        if index == len(trace) and marking_key(marking) == final:
            return True
        for transition in semantics.enabled_transitions(net, marking):
            if transition.label is None:
                next_index = index
            elif index < len(trace) and transition.label == trace[index]:
                next_index = index + 1
            else:
                continue
            next_marking = semantics.execute(transition, net, marking)
            key = (marking_key(next_marking), next_index)
            if key not in seen:
                seen.add(key)
                if len(seen) > state_limit:
                    raise RuntimeError('Acceptance search incomplete: state limit')
                queue.append((next_marking, next_index))
    return False

def bounded_language(net, im, fm, max_events=8, state_limit=200000):
    queue = deque([(im, ())])
    seen = {(marking_key(im), ())}
    accepted = set()
    final = marking_key(fm)
    while queue:
        marking, trace = queue.popleft()
        if marking_key(marking) == final:
            accepted.add(trace)
        for transition in semantics.enabled_transitions(net, marking):
            next_trace = trace
            if transition.label is not None:
                if len(trace) == max_events:
                    continue
                next_trace = trace + (transition.label,)
            next_marking = semantics.execute(transition, net, marking)
            key = (marking_key(next_marking), next_trace)
            if key not in seen:
                seen.add(key)
                if len(seen) > state_limit:
                    raise RuntimeError('Language search incomplete: state limit')
                queue.append((next_marking, next_trace))
    return accepted

# Independent finite-language specification, used only as a code oracle.
def intended_languages():
    balanced, permissive = set(), set()
    for has_s in [False, True]:
        for has_x in [False, True]:
            core = ['C', 'E'] + (['S'] if has_s else []) + (['X'] if has_x else [])
            for order in itertools.permutations(core):
                positions = {symbol: i for i, symbol in enumerate(order)}
                if has_x and not (positions['C'] < positions['X']
                                  and positions['E'] < positions['X']):
                    continue
                trace = word(' '.join(('R',) + order + ('A', 'P', 'Z')))
                permissive.add(trace)
                if not has_s or (min(positions['C'], positions['E']) < positions['S']):
                    balanced.add(trace)
    return {'conservative': observed, 'balanced': balanced, 'permissive': permissive}
```

The parser supplies synthetic timestamps; these are not used to infer overlap or real precedence. The acceptance search follows silent transitions and requires the exact final marking after consuming the entire word. It does not equate an approximately fitting alignment with membership.

The exhaustive claim is deliberately narrow. These three syntactically loop-free models contain six mandatory visible activities and at most two optional ones per execution. Therefore no complete visible trace can exceed eight events, and exhausting the bounded search verifies their entire visible languages. The script raises an error if its state budget is exceeded. For an arbitrary model with loops or unbounded markings, a length bound can miss behavior and even bounded-visible exploration may require a state limit. Sampled playout never proves language inclusion, and the script's inclusion assertion for sampled words concerns only the words actually generated.

# 9. Recommendation and Data-Collection Plan

Use **model_balanced immediately for descriptive analysis and provisional conformance screening**, with supplier-absence cases marked “requirement or logging status unresolved.” Its prerequisites are understandable, it retains every recorded case, and it generalizes the two rare expedite traces using explicit domain statements. Use **model_permissive for sensitivity analysis**, especially to determine whether conclusions depend on interpreting D5 as a full-completion gate. Keep conservative as the empirical reference when reporting how much behavior each generalization adds.

None of the completion-only candidates can certify that an external-component order actually received required confirmation. For a compliance decision, the hidden guard and source confirmation evidence must be recovered. This follows from the task's specific missing attribute and missing-event statements, rather than from a failure of Petri-net soundness.

**1. Reconcile the existing 30 cases before drawing stronger conclusions.**

- Recover order/component classification, source confirmation records, and export delivery records for all seven no-S cases. Classify each as confirmation not required, confirmation completed but missing from export, required confirmation not performed, or unresolved. Record the evidence for the classification.
- Check source timestamps and tie groups for all 11 E-before-C cases, the two C·S·E cases, and both expedite cases. Retain the original source and ingestion ordering separately.
- Resolve with process owners whether S1 is a mandatory policy, a historical practice, a particular customer/order-class rule, or a misunderstanding. Resolve what D5 means operationally: completed check, partial result, or another data prerequisite. Determine whether an expedite review can legitimately occur on a stocked-component case.

**2. Instrument a prospective cohort of approximately 100–200 completed orders, extending collection if key strata remain rare.**

| Information to collect | Concrete fields or events | Ambiguity reduced |
|---|---|---|
| Case and component identity | Order ID, component/line-item ID, supplier ID where applicable, bill-of-materials version, order class, applicable policy version. | Mixed-component requirements, separate confirmations, and hidden populations with different routing rules. |
| Supplier requirement | External/stocked classification at decision time, `supplier_confirmation_required`, decision timestamp, reason, stock availability, and rule/version used. | Conditional mandatory behavior versus true optionality. |
| Activity lifecycle | Activity-instance ID; scheduled, enabled, start, complete, and, where relevant, suspend/resume timestamps; completion status/outcome. | Actual overlap, waiting, repeated instances, and whether “complete” produced a usable result. |
| Information availability | Explicit `credit_information_ready` and `engineering_information_ready` milestones, sufficient-result type, timestamp, and the prerequisite reference used to enable S. | Full-completion versus partial-information supplier gates; C-enabled versus E-enabled work. |
| Expedite decision | Eligibility/request flag, reason, decision timestamp, applicable prerequisite references, and start/complete timestamps. | Whether X is independent of supplier requirement or belongs to a restricted route. |
| Approval and release linkage | Approval decision/version and the approval reference used by production release. | Actual prerequisite satisfaction rather than adjacency alone. |
| Logging integrity | Immutable source event ID, source system, source timestamp and precision, ingestion timestamp/index, export batch, retry/deduplication status, and delivery reconciliation. | Tie artifacts, clock differences, event loss, and whether missingness is clustered by system or case type. |

Synchronize source clocks or record their offsets and timestamp resolution. Preserve lifecycle events instead of flattening them into a single completion record. Separate incomplete/open cases from completed ones in evaluation. Require enough cases in each external/stocked and expedited/non-expedited group to inspect the relevant questions; absence of a rare combination in this cohort alone is not proof of prohibition.

**3. Prioritize observations that distinguish the hypotheses.**

| Future observation, using reconciled events and resolved ties | What it would distinguish |
|---|---|
| R E S C A P Z | Supports an engineering-enabled supplier route and contradicts a universal C-completion prerequisite for S. Admitted by balanced/permissive, rejected by conservative. One such reliable case is more informative about that gate than many additional C·E·S cases. |
| R S C E A P Z or R S E C A P Z, with a sufficient-information milestone before S starts | Distinguishes permissive from balanced and supports the partial-information interpretation. Without the milestone and lifecycle data, it could still be an ordering or data-quality issue. |
| R C E X A P Z or R E C X A P Z, with confirmed stocked status and a healthy export | Demonstrates X without any required supplier action, weakening the observed X-with-S correlation. If the same visible trace instead has a reconciled hidden S event, it diagnoses missingness rather than that business-route independence. |
| A no-S trace such as R C E A P Z, with external requirement established and source records reconciled | Distinguishes missing logging from a real compliance failure. The visible word alone cannot make that distinction. |
| Both C-before-E and E-before-C traces with `max(start_C,start_E) < min(complete_C,complete_E)` | Positive-duration interval overlap contradicts a strict non-overlapping sequence or XOR of non-overlapping sequential orders. Suspend/resume data may still be needed to distinguish active simultaneous work from overlapping activity spans. |
| Both check orders, but always non-overlapping and predictably selected by a recorded route/policy attribute | Supports an XOR choice between sequential routes. Lack of observed overlap alone does not prove that concurrency is forbidden. A consistent C-finish-before-E-start rule supports S1's sequence for the relevant class. |
| R C S A P Z or R E S A P Z, with the principal omission independently verified as legitimate | Would support a genuinely alternative-check route and require revising D3. This is different from XOR between two orders in which both checks still occur. Without verification it is a missing-event or violation candidate, not evidence for XOR. |
| R C S X E A P Z with trustworthy completion times | Challenges the shared X-after-both constraint at X. It should trigger investigation of D6/S6 or the event semantics, rather than automatic broadening. |

To test supplier enablement more directly, use naturally occurring check delays or a controlled test environment in which one check is delayed while information-ready milestones are recorded. Observe whether S becomes enabled from the other check, and whether enablement depends on completion or a partial result. This targets the disputed mechanism instead of relying only on whichever activity happens to finish first.

**4. Validate prospectively and report uncertainty by subgroup.**

Freeze the three hypotheses before scoring the new cohort. Report exact accepted-case proportions, deviations, and the requested PM4Py metrics by requirement class, expedite status, source system, and time period. Review the business validity of accepted unobserved variants as well as rejected cases: better fitness can result from accepting real violations. Report sample sizes and uncertainty intervals for empirical rates rather than interpreting small differences as decisive.

Use case-level temporal holdout and, as a stress test, hold out entire rare variants to expose conservative memorization. On reconciled cases, deliberately mask known S events at approximately 5% and 10%, comparing independent deletion with loss clustered by integration batch. Keep the original ground truth so that logging tolerance is assessed separately from tolerance of actual missing supplier work. This will expose the conservative expedite-omission failure and quantify how much the optional-S abstraction hides. Reassess the model once the requirement guard and information prerequisites are known; ideally retain a distinct business-process model and an observation-loss model.

# 10. Uncertainty Statement

The confidence assessments below concern the process claims, not whether the supplied code implements the declared languages. The latter was checked by soundness, exact trace acceptance, and finite-language enumeration.

| Modeling decision | Calibrated confidence and limitation |
|---|---|
| R and Z as intended boundaries; A before P | High, supported by D1/D2 and all observed cases. This does not establish universal adjacency or exclude other case types. |
| Both C and E before A | Medium-to-high: D3 and all 30 traces agree, but unusual policy exceptions or outcome-dependent routes were not sampled. |
| Single-pass activities and fixed A·P·Z suffix | Moderate for the stated sample scope; weaker as a universal business-process claim. Rework and revisions remain plausible. |
| Acceptance of both C/E completion orders | High as a requirement for representing this export faithfully. |
| Actual C/E concurrency or overlap | Low-to-moderate as a hypothesis: S2 supports it, S1 conflicts, and completion orders cannot decide. A parallel-capable representation has stronger support than a claim that overlap actually occurred. |
| Conditional legitimate omission of S | Moderate, because S3/S4 provide a coherent conditional explanation. Which particular cases qualify is unknown. |
| Some S events are lost | Moderate based on S5; the asserted rate is approximate and not independently measured here. Attribution of any individual omission is low confidence until source reconciliation. |
| S must follow at least one completed check | Low-to-moderate. Every observed S satisfies it, but D5 refers to information availability rather than necessarily completion. It is the balanced candidate's principal simplifying assumption. |
| Either check can enable S | Low-to-moderate. D5 says so, but all recorded S cases follow C; the engineering-only enabling situation has not been observed. |
| S may complete before both checks | Low, but plausible under an explicit partial-information lifecycle refinement. This motivates sensitivity analysis rather than the immediate default. |
| X occurs at most once, after both checks and before A | Medium-to-high from D6/S6 and both observations, with only two X cases providing empirical support. |
| No fixed S–X order | Moderate-to-high for visible sequences: both orders are directly observed and S6 permits them. Actual overlap is still unknown. |
| X independent of supplier requirement/presence | Low-to-moderate. Domain statements do not prohibit the combination, but both observed X cases include S. Source reconciliation and a stocked expedited case would be informative. |

At least three alternative interpretations could materially change the recommendation:

- If S1 is confirmed as the authoritative rule for this population, E-before-C traces should be investigated as timing artifacts or actual violations. A normative model with C before E would then be more appropriate for compliance than a model selected to fit all recorded cases.
- If supplier work is shown to start from sufficient partial information and sometimes finish before either check, the balanced completion gate is too restrictive; permissive, or preferably an explicit lifecycle/milestone model, should become the descriptive default. Conversely, a verified full-completion gate would rule out permissive's four S-first additions.
- If every relevant order actually requires supplier confirmation and omissions are logging failures, a business model with mandatory S plus an explicit event-loss layer should replace business optionality. The same visible completion language could still fit, while its compliance interpretation would change substantially.

The seven recorded variants establish what appeared in this export. They do not identify why those sequences occurred, whether unobserved combinations are impossible, or which invisible actions actually took place.
