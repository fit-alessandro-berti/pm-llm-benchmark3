# 1. Assumptions and Interpretation

1.  **Risk Choice (Low/High):** Represented as an exclusive choice (`XOR`) immediately following `Analyze Root Cause`. One branch contains `Supervisor Review`; the other contains a parallel block of `Quality Review` and `Regulatory Review`.
2.  **Optional Supplier:** Represented as an exclusive choice (`XOR`) between a `SilentTransition` (no supplier) and `Consult Supplier`. This choice occurs after `Analyze Root Cause`.
3.  **Passing Inspection:** Abstracted as the exit condition of a loop. The loop body is `Execute Trial` -> `Inspect Trial`. The loop redo path includes `Adjust Parameters`. A trace exits the loop (proceeds to `Release`) only when the `Inspect Trial` activity is not followed by `Adjust Parameters`.
4.  **Duplicate Labels:** Duplicate visible labels are **not permitted**. Each activity label corresponds to a unique node in the model to preserve conformance checking semantics.
5.  **Process Tree Approximation Policy:** **Conservative Under-approximation.** The Process Tree cannot express the cross-branch synchronization where `Execute Trial` waits for `Plan` and `Design` but *not* `Approvals` (which share the `Analyze` ancestor). The Tree model will force `Execute Trial` to wait for `Approvals` and `Supplier` to complete, excluding valid concurrent behaviors where Trial overlaps Approvals. This is chosen to prevent unsafe behavior (starting Trial before Verification Plan is ready) at the cost of flexibility.
6.  **"May Overlap":** Interpreted as **true concurrency**. In the POWL model, this is represented by the absence of a partial order edge. In the Process Tree, it is represented by `Operator.PARALLEL`, subject to the structural limitations noted in Assumption 5.

# 3. PM4Py Process-Tree Model

The Process Tree uses a nested structure to approximate the dependencies. Note that `Execute Trial` is placed *after* the parallel block containing `Approvals` and `Supplier`. This enforces that `Trial` waits for `Approvals` and `Supplier`, which is an **under-approximation** of the intended behavior (where they may overlap). This is necessary because Process Trees cannot synchronize `Trial` with `Design` (Branch A) while keeping it parallel to `Approvals` (Branch A) and `Plan` (Branch B).

```text
->(
  'Register Deviation',
  /(
    ->('Contain Material', 'Plan Verification'),
    ->(
      'Analyze Root Cause',
      /(
        'Design Corrective Action',
        XOR(
          'Supervisor Review',
          ->('Quality Review', 'Regulatory Review')
        ),
        XOR(
          tau,
          'Consult Supplier'
        )
      )
    )
  ),
  LOOP(
    ->('Execute Trial', 'Inspect Trial'),
    'Adjust Parameters'
  ),
  'Release Material',
  'Archive Case'
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def build_process_tree():
    # Leaf nodes
    register = ProcessTree('Register Deviation')
    contain = ProcessTree('Contain Material')
    plan = ProcessTree('Plan Verification')
    analyze = ProcessTree('Analyze Root Cause')
    design = ProcessTree('Design Corrective Action')
    supervisor = ProcessTree('Supervisor Review')
    quality = ProcessTree('Quality Review')
    regulatory = ProcessTree('Regulatory Review')
    supplier = ProcessTree('Consult Supplier')
    silent = ProcessTree(None) # tau
    execute = ProcessTree('Execute Trial')
    inspect = ProcessTree('Inspect Trial')
    adjust = ProcessTree('Adjust Parameters')
    release = ProcessTree('Release Material')
    archive = ProcessTree('Archive Case')

    # Sub-structures
    # Containment Branch
    contain_branch = ProcessTree(operator=Operator.SEQUENCE)
    contain_branch.children = [contain, plan]
    contain.parent = contain_branch
    plan.parent = contain_branch

    # Approval XOR (Low vs High)
    # High risk is Parallel(Quality, Regulatory)
    high_risk = ProcessTree(operator=Operator.PARALLEL)
    high_risk.children = [quality, regulatory]
    quality.parent = high_risk
    regulatory.parent = high_risk
    
    approval_xor = ProcessTree(operator=Operator.XOR)
    approval_xor.children = [supervisor, high_risk]
    supervisor.parent = approval_xor
    high_risk.parent = approval_xor

    # Supplier XOR (None vs Consult)
    supplier_xor = ProcessTree(operator=Operator.XOR)
    supplier_xor.children = [silent, supplier]
    silent.parent = supplier_xor
    supplier.parent = supplier_xor

    # Analyze Branch (Design + Approvals + Supplier in Parallel)
    # Note: To satisfy Tree structure, we group these under Analyze.
    analyze_parallel = ProcessTree(operator=Operator.PARALLEL)
    analyze_parallel.children = [design, approval_xor, supplier_xor]
    design.parent = analyze_parallel
    approval_xor.parent = analyze_parallel
    supplier_xor.parent = analyze_parallel

    analyze_branch = ProcessTree(operator=Operator.SEQUENCE)
    analyze_branch.children = [analyze, analyze_parallel]
    analyze.parent = analyze_branch
    analyze_parallel.parent = analyze_branch

    # Initial Parallel (Containment vs Analyze)
    initial_parallel = ProcessTree(operator=Operator.PARALLEL)
    initial_parallel.children = [contain_branch, analyze_branch]
    contain_branch.parent = initial_parallel
    analyze_branch.parent = initial_parallel

    # Trial Loop
    trial_body = ProcessTree(operator=Operator.SEQUENCE)
    trial_body.children = [execute, inspect]
    execute.parent = trial_body
    inspect.parent = trial_body

    trial_loop = ProcessTree(operator=Operator.LOOP)
    trial_loop.children = [trial_body, adjust]
    trial_body.parent = trial_loop
    adjust.parent = trial_loop

    # Main Sequence
    root = ProcessTree(operator=Operator.SEQUENCE)
    root.children = [register, initial_parallel, trial_loop, release, archive]
    register.parent = root
    initial_parallel.parent = root
    trial_loop.parent = root
    release.parent = root
    archive.parent = root

    return root

tree = build_process_tree()
```

**Approximation Disclosure:**
The Process Tree cannot model the requirement that `Execute Trial` waits for `Design` and `Plan` but *overlaps* with `Approvals`. In the tree above, `Execute Trial` (inside `trial_loop`) is a sibling to the `initial_parallel` block in the main sequence. This means `Execute Trial` waits for the `initial_parallel` block to complete. Since `Approvals` and `Supplier` are inside the `Analyze` branch of `initial_parallel`, `Execute Trial` is forced to wait for them to finish. This excludes valid traces where `Execute Trial` runs concurrently with `Quality Review` or `Consult Supplier`. This is a **conservative under-approximation** chosen to ensure `Plan` and `Design` are definitely complete before `Trial` starts, adhering to safety over flexibility.

# 4. PM4Py POWL Model

The POWL model uses explicit partial order edges to handle the cross-branch synchronization exactly. `Execute Trial` depends on `Plan` and `Design`. `Release` depends on `Trial`, `Approvals`, and `Supplier`. `Approvals` and `Supplier` depend only on `Analyze`. This allows `Trial` to overlap `Approvals`.

```text
POWL Model Structure:
Nodes: All Activities + Silent Transitions for XOR/Loop logic.
Edges: Explicit precedence via StrictPartialOrder.
Blocks: XOR for Risk/Supplier, LOOP for Trial.
```

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.powl.obj import Operator as POWLOperator

def build_powl():
    # Transitions
    t_register = Transition('Register Deviation')
    t_contain = Transition('Contain Material')
    t_analyze = Transition('Analyze Root Cause')
    t_plan = Transition('Plan Verification')
    t_design = Transition('Design Corrective Action')
    
    t_supervisor = Transition('Supervisor Review')
    t_quality = Transition('Quality Review')
    t_regulatory = Transition('Regulatory Review')
    
    t_supplier = Transition('Consult Supplier')
    t_silent_supplier = SilentTransition()
    
    t_execute = Transition('Execute Trial')
    t_inspect = Transition('Inspect Trial')
    t_adjust = Transition('Adjust Parameters')
    
    t_release = Transition('Release Material')
    t_archive = Transition('Archive Case')

    # Approval XOR Block
    # High Risk: Parallel(Quality, Regulatory)
    high_risk_parallel = OperatorPOWL(POWLOperator.PARALLEL, [t_quality, t_regulatory])
    # Low Risk: Supervisor
    # XOR between Supervisor and High Risk
    approval_xor = OperatorPOWL(POWLOperator.XOR, [t_supervisor, high_risk_parallel])

    # Supplier XOR Block
    supplier_xor = OperatorPOWL(POWLOperator.XOR, [t_silent_supplier, t_supplier])

    # Trial Loop Block
    # Body: Execute -> Inspect
    # Redo: Adjust (which leads back to Body in Loop semantics)
    # PM4Py POWL Loop: LOOP(Body, Redo) -> Body (Redo Body)*
    trial_body = OperatorPOWL(POWLOperator.SEQUENCE, [t_execute, t_inspect])
    trial_loop = OperatorPOWL(POWLOperator.LOOP, [trial_body, t_adjust])

    # Root Partial Order
    root = StrictPartialOrder([])
    
    # Add all top-level nodes to the root set
    # We add transitions and blocks. 
    # Note: In POWL, blocks are nodes too.
    all_nodes = [
        t_register, t_contain, t_analyze, t_plan, t_design,
        approval_xor, supplier_xor, trial_loop,
        t_release, t_archive
    ]
    # We need to ensure internal nodes of blocks are reachable. 
    # StrictPartialOrder usually takes the set of all nodes (including internal).
    # For simplicity in construction, we add the blocks and transitions.
    # However, StrictPartialOrder constructor expects a set of nodes.
    # We will add them and then define edges.
    
    # Collect all atomic transitions and operators for the node set
    nodes_set = {
        t_register, t_contain, t_analyze, t_plan, t_design,
        t_supervisor, t_quality, t_regulatory,
        t_silent_supplier, t_supplier,
        t_execute, t_inspect, t_adjust,
        t_release, t_archive,
        high_risk_parallel, approval_xor, supplier_xor, trial_body, trial_loop
    }
    
    root = StrictPartialOrder(nodes_set)

    # Define Edges (Precedence)
    order = root.order

    # 1. Start
    order.add_edge(t_register, t_contain)
    order.add_edge(t_register, t_analyze)

    # 2. Containment Branch
    order.add_edge(t_contain, t_plan)

    # 3. Analyze Branch
    order.add_edge(t_analyze, t_design)
    order.add_edge(t_analyze, approval_xor)
    order.add_edge(t_analyze, supplier_xor)

    # 4. Trial Synchronization (Cross-Branch Join)
    # Trial waits for Plan AND Design
    order.add_edge(t_plan, trial_loop)
    order.add_edge(t_design, trial_loop)

    # 5. Release Synchronization
    # Release waits for Trial, Approvals, and Supplier
    order.add_edge(trial_loop, t_release)
    order.add_edge(approval_xor, t_release)
    order.add_edge(supplier_xor, t_release)

    # 6. End
    order.add_edge(t_release, t_archive)

    return root

powl = build_powl()
```

**Concurrency Explanation:**
-   **`t_plan` and `t_design`:** No edge between them. They are concurrent (after `Register`).
-   **`trial_loop` and `approval_xor`:** No edge between them. `trial_loop` depends on `t_design`, `approval_xor` depends on `t_analyze`. Since `t_design` depends on `t_analyze`, `approval_xor` can start as soon as `t_analyze` finishes. `trial_loop` starts when `t_plan` and `t_design` finish. If `t_plan` takes longer than `approval_xor`, `approval_xor` finishes before `trial_loop` starts. If `t_plan` is fast, `trial_loop` starts while `approval_xor` is running. The lack of an edge allows this overlap.
-   **`trial_loop` and `supplier_xor`:** Similarly, no edge allows overlap.
-   **`t_quality` and `t_regulatory`:** Inside `high_risk_parallel`, no edge enforces order, allowing concurrency.

# 7. Preferred Representation and Validation Plan

**Preferred Representation:** **POWL Model.**
**Defense:** The manufacturing process contains non-block-structured dependencies (cross-branch synchronization for `Execute Trial` and `Release Material`). The Process Tree forces a hierarchical serialization that under-approximates concurrency (forcing `Approvals` before `Trial`). POWL explicitly models partial orders, capturing the intended flexibility without sacrificing safety constraints. This yields higher fitness during conformance checking on real event logs where overlaps occur.

**Validation Plan:**
1.  **Conversion to Petri Net:** Use `pm4py.convert_to_petri_net(powl)` to generate a Petri Net. This provides a visual verification of the synchronization points (places with multiple incoming/outgoing arcs).
2.  **Soundness Checking:** Run `pm4py.check_soundness(net, im, fm)` on the converted net. This ensures no deadlocks exist (e.g., `Release` waiting for a branch that never completes) and proper completion (tokens end in `Archive`).
3.  **Sampled Playout:** Use `pm4py.play_out(powl, no_of_traces=100)` to generate synthetic logs. Inspect traces to verify that `Execute Trial` sometimes precedes `Supervisor Review` (validating overlap).
4.  **Explicit Trace Tests:**
    *   **Positive:** Replay Trace T5 (Overlap). Expect: POWL fits, Tree deviates.
    *   **Negative:** Replay Trace T7 (Bad Loop). Expect: Both reject.
5.  **Silent/Duplicate Check:** Verify that `SilentTransition` in POWL and `tau` in Tree do not appear in the generated activity lists of played-out traces, ensuring they only control flow.
6.  **Limitations:** The validation relies on the correctness of the PM4Py conversion algorithms. The "Pass/Fail" inspection logic remains an approximation in both models as it relies on loop structure rather than data predicates.

# 8. Final Self-Critique

1.  **Semantics of Loop Exit:** Both models use a structural loop (`LOOP(Body, Redo)`). This technically allows the process to exit the loop after *any* `Inspect Trial`. It does not enforce that `Adjust Parameters` *must* occur if the inspection "fails" because "Fail" is not an event. The model assumes the operator chooses to exit only on "Pass", but the control flow permits exiting early.
2.  **Supplier Dependency Granularity:** In the POWL model, `Consult Supplier` depends on `Analyze Root Cause`. In reality, one might know a supplier is needed before the root cause is fully analyzed (e.g., immediately upon deviation registration if material origin is suspect). The model enforces `Analyze` first, which might be a slight over-constraint based on the text "When selected, it may start only after Analyze Root Cause." (I followed the text, but real-world nuance might differ).
3.  **POWL API Complexity:** The manual construction of `StrictPartialOrder` with explicit node sets and edges is verbose and error-prone compared to the Process Tree string parser. A mistake in adding a node to the `nodes_set` but not connecting it could lead to a disconnected graph that `check_soundness` might catch but is hard to debug visually in code.
