## 3. Consequences for performance analysis

### G1 – Start Batching (RBT-7 fixture)

**Waiting time bias:**  
- **Observation:** Queue arrivals 08:54–08:58; first start at 09:00.  
- **Bias mechanism:** If all four items are assumed to have entered the queue at their respective arrival times, the reported waiting time for L04 is 09:00  08:58 = 2 min, but L01 waited 09:00  08:54 = 6 min. If we instead assume all four arrived by 08:58 and the fixture was set up *once* at 09:00, then all items have waiting time 6 min. The alternative (treating each start as individual) inflates the *variability* of waiting time without changing the *mean*, but can distort SLA compliance metrics if thresholds are tight.  
- **Direction:** Waiting time reported per case may underestimate true queue build-up; mean is misleading if mixed with other activities.

**Service time bias:**  
- **Observation:** All report 3 min service (09:00–09:03), but RBT-7 processes 4 items in parallel.  
- **Bias mechanism:** If "service time" is defined as per-item processing time, then 3 min is correct. If it is defined as per-item throughput time including setup, then we are double-counting setup. If we sum service times across the four items (12 min) and compare to wall-clock time (3 min), we compute resource utilization correctly (4 items × 1 min effective service = 4 min ÷ 3 min actual = 1.33×, indicating a mismatch or overlapping setup).  
- **Direction:** Service time is correct per item; utilization calculation requires clarity on whether setup is amortized or assigned to one case.

**Resource utilization bias:**  
- **Observation:** RBT-7 is busy 09:00–09:03 (3 min in the observation window).  
- **Bias mechanism:** If we count 4 items × 3 min = 12 "item-minutes" of work in 3 wall-clock minutes, the resource appears to be 12 ÷ 3 = 4× overloaded, which is incorrect. Correct interpretation: 1 resource unit × 3 min = 3 unit-minutes of availability consumed by the fixture holding 4 items.  
- **Direction:** Naive summation of per-case service times inflates utilization; must account for parallelism in the fixture.

**Bottleneck detection bias:**  
- **Observation:** All four cases complete with zero lag (recorded_at = 09:03:02–09:03:03).  
- **Bias mechanism:** If RBT-7 is the only bottleneck, the queue should grow unbounded before 09:00 and shrink after 09:03. The fact that queue arrivals are spread suggests other upstream steps are also constrained. However, if the fixture fills to capacity (4 items) and does not accept more until it completes, then waiting time for items 5+ would spike. The current data does not show cases L05–L08, so we cannot diagnose whether this is a real bottleneck or just one batch cycle.  
- **Direction:** If batch size is always 4, fixture capacity is not a bottleneck; if arrival rate varies, queue waiting times may show periodic spikes.

### G2 – Sequential Batching with Common Start Session (T-B tablet)

**Waiting time bias:**  
- **Observation:** Queue arrivals 09:42–09:54 (12 min spread); all start at 10:00.  
- **Bias mechanism:** Waiting times are 10:00  {09:42, 09:46, 09:49, 09:54} = {18, 14, 11, 6} min respectively. If "begin group" button at 10:00 is interpreted as a system-wide session start (not individual task start), then all four cases have the reported waiting time. However, if completion times (10:08, 10:14, 10:21, 10:27) reflect the actual time each task ended (not a button-press), then work is sequential, and the waiting times are not equivalent.  
- **Direction:** Reported waiting time (queue to shared start) overstates the true queue delay; actual waiting depends on which item in the sequence a given case occupies. If we use queue_arrival to first completion, the true waiting is {26, 28, 32, 33} min, which is much longer and shows increased waiting as queue backlogs.

**Service time bias:**  
- **Observation:** Completions are 10:08, 10:14, 10:21, 10:27 (durations from 10:00: 8, 14, 21, 27 min).  
- **Bias mechanism:** If service time is defined as [complete  start], then times are {8, 14, 21, 27} min, which are not identical. This contradicts the idea that all four items undergo the same task in parallel; instead, it confirms sequential processing. The *inter-completion* spacing is {6, 7, 6} min, suggesting each item takes ~6–7 min to process *plus* the cumulative effect of holding the device for earlier items.  
- **Direction:** Service time increases per case, masking the true per-item duration (~6–7 min); reported times conflate queuing within the batch with service.

**Resource utilization bias:**  
- **Observation:** T-B is busy from 10:00–10:27 (27 min for 4 cases).  
- **Bias mechanism:** If we report utilization as "4 cases × average service time" ÷ resource time, we get {8+14+21+27} ÷ 4 ÷ 27 = 17.5 ÷ 27 = 0.65 (65%), which suggests spare capacity. However, the resource is continuously occupied; the spare capacity is an artifact of the metric definition. True utilization is 27 min occupied ÷ 27 min = 100%.  
- **Direction:** Naive per-case service time summation underestimates true resource utilization.

**Bottleneck detection bias:**  
- **Observation:** Queue arrivals span 09:42–09:54; the session does not start until 10:00 (a 18–6 min wait after arrival).  
- **Bias mechanism:** The "begin group" button is a potential checkpoint or merge point. If this is a mandatory step to start any task (e.g., session initialization), then T-B could be a bottleneck that processes one group per time interval. To diagnose this, we would need to know if other groups exist or if T-B is idle between 09:54 and 10:00.  
- **Direction:** Without inter-group data, we cannot determine if T-B is a bottleneck; local queuing within the group is likely, but system-level bottleneck status is unknown.

### G3 – End Batching / Form Submission (T-C desktop form)

**Waiting time bias:**  
- **Observation:** Queue arrivals 10:40–11:05 (25 min); all complete (and recorded) at 11:30–11:31.  
- **Bias mechanism:** If we compute waiting as [complete  queue_arrival], we get {50, 38, 32, 25} min. However, the "complete" timestamp is the form submission time, not the time each individual task finished. The context states "form submitted after finishing folder," suggesting that internal work concludes before submission. If we use [recorded_at  queue_arrival], we get {51, 39, 33, 26} min, which is very similar and still overstates true waiting if the individuals began work shortly after arrival.  
- **Direction:** Reported waiting time inflates because it includes time from arrival to form submission (not arrival to task start); actual waiting (to task start) is likely much shorter (5–10 min); the difference is execution time, not waiting.

**Service time bias:**  
- **Observation:** All reported service times are 28 min (11:30  11:02 = 28 min is the *maximum* interval; others are shorter: 20, 13, 6 min).  
- **Bias mechanism:** If we use reported [complete  start] times {28, 20, 13, 6}, we see decreasing durations, which is inconsistent with a fixed task (review activity). However, the context says "reviews are performed throughout the half-hour," suggesting continuous work, and then the form is submitted. If the form submission time is 11:30 for all four cases, and the true task ends are unknown, we cannot reliably compute service time. One interpretation: tasks end ~5–10 min before form submission (idle time before submission), and true service times are {23–25, 15–18, 8–10, 1–3} min, which are more plausible.  
- **Direction:** Service time is severely biased upward if computed as [form_submission  start]; individual task durations are underestimated.

**Resource utilization bias:**  
- **Observation:** T-C is engaged from ~11:02 to ~11:30 (28 min reported), but multiple people are reviewing simultaneously based on staggered start times.  
- **Bias mechanism:** If T-C is a shared resource (e.g., a shared review folder or a terminal), then the reported window is meaningful only if work is serial on that resource. If multiple reviewers work in parallel (e.g., on different folders or sections), then T-C's true utilization is unclear. If we assume serial access to a form, and the form is locked from 11:02–11:30, then utilization is 28 min ÷ (window available) = high. If parallel work is allowed, utilization is not a meaningful metric for T-C alone.  
- **Direction:** Utilization is either very high (if serial) or undefined (if parallel); the data do not clarify which.

**Bottleneck detection bias:**  
- **Observation:** All four cases queue before 11:05 and do not complete until 11:30 (25–50 min waiting).  
- **Bias mechanism:** If the form submission is the only way to close cases, and the form can be submitted in bulk (multiple cases at once), then T-C is a *serial bottleneck* that accumulates cases until a batch submission occurs. This could be by design (end-of-shift closure) or by constraint (one form per submission). To confirm, we would need to know the form's submission rules (can it handle multiple cases in a single submission?).  
- **Direction:** G3 strongly suggests T-C (or the review+submission workflow) is a bottleneck; waiting times are high and inflated due to batch submission; SLA compliance may be poor even if individual review time is acceptable.

### G4 – Perfect Sequential Batching (T-D scanner)

**Waiting time bias:**  
- **Observation:** Queue arrivals 11:58–12:02 (4 min); starts are 12:05, 12:09, 12:13, 12:17, 12:21.  
- **Bias mechanism:** Using queue_arrival to start, waiting times are {7, 10, 13, 17, 19} min. However, the first case starts at 12:05, suggesting a 5–7 min delay before any work begins (possible system initialization, or batching delay). Subsequent cases start ~4 min after their queue arrival *and* when the prior case completes. The true waiting is driven by the prior case, not the queue, for cases P02–P05.  
- **Direction:** Reported waiting time (queue to start) suggests a fixed delay (~5–7 min baseline) plus a queuing delay per case position. Mean waiting increases linearly with batch depth, biasing SLA metrics and throughput estimates.

**Service time bias:**  
- **Observation:** Service times (complete  start) are {4, 4, 4, 4, 4} min (all identical at 1-sec precision).  
- **Bias mechanism:** This is the least-biased service time in the dataset; each case takes 4 min, and there are no confounds with batching or aggregation. However, the queue_arrival to complete times are {11, 14, 17, 21, 23} min, which are not 4 min. These longer times represent waiting within the sequence.  
- **Direction:** Service time is accurate; no bias. The bias in the previous metric (waiting) is correctly separated.

**Resource utilization bias:**  
- **Observation:** T-D is busy from 12:05–12:25 (20 min for 5 cases).  
- **Bias mechanism:** Utilization = (5 cases × 4 min service) ÷ (20 min available) = 20 ÷ 20 = 100%. The resource is fully utilized, with no idle gaps. This is correct; the 4-case gap between the queue arrival (11:58 first, 12:02 last) and the start (12:05 first) may represent a small delay in picking up the queue, or it may represent queue arrival rounding to 1-min granularity.  
- **Direction:** Resource utilization is accurately represented; no bias.

**Bottleneck detection bias:**  
- **Observation:** The inter-arrival times (queue_arrival spacing) are {1, 1, 1, 1} min (sequential queue entries), and the inter-start times are {4, 4, 4, 4} min (matching the service time). This creates a *pile-up* of cases in the queue before the first start, and then a steady release at the service rate.  
- **Bias mechanism:** If T-D is the only resource in a downstream chain (e.g., pack  ship), then it is a bottleneck: the arrival rate (1 case/min) exceeds the service rate (4 min/case). The queue will grow without bound if arrivals continue. To confirm bottleneck status, we need to know if upstream rates are fixed or if they can absorb the queue.  
- **Direction:** G4 is a clear bottleneck: service rate (0.25 cases/min) < arrival rate (1 case/min); waiting times will continue to increase, and the system is unsustainable at current arrival rates.

### G5 – Concurrent Work or Shared-Account Artifact (analyst_pool)

**Waiting time bias:**  
- **Observation:** Queue arrivals 12:45–12:57 (12 min); starts 13:00–13:12 (12 min); waiting times (start  queue) are {15, 15, 16, 15} min (all ~15 min).  
- **Bias mechanism:** If `analyst_pool` is a shared login and three analysts are logged in, the start time is when the individual analyst began work, not when the resource became available. True waiting is the interval from queue_arrival to when an analyst became available, which is unknown. Reported waiting is 15 min, but if one analyst started at 13:00 and a second at 13:05, the true wait for the second analyst was only ~5 min (not 15 min). The 15 min average conflates per-analyst waiting with pooled-resource waiting.  
- **Direction:** Reported waiting time is biased upward if it does not account for the fact that different analysts (sub-resources) became available at different times. True waiting is lower; reported waiting suggests a sequential queue, but the resource is actually a pool.

**Service time bias:**  
- **Observation:** Service times (complete  start) are {25, 15, 20, 10} min.  
- **Bias mechanism:** If `analyst_pool` is truly three concurrent analysts, these service times represent the actual work duration per analyst, and there is no bias. However, if the resource is a single shared login shared by time-slicing (unlikely for a VDI session), then service time could be inflated by task-switching overhead. The variability {25, 15, 20, 10} is plausible for three analysts working independently.  
- **Direction:** Service time is likely accurate; no major bias unless task-switching is extreme.

**Resource utilization bias:**  
- **Observation:** Overlapping time intervals: [13:00–13:25], [13:05–13:20], [13:10–13:30], [13:12–13:22].  
- **Bias mechanism:** If we compute utilization as (sum of service times) ÷ (number of resources × time window), we get (25+15+20+10) ÷ (3 × 30 min) = 70 ÷ 90 = 0.78 (78% utilization per analyst, on average). However, if `analyst_pool` is a single resource, utilization = (70 min work) ÷ (67 min available, from 13:00–13:30+) = >100%, which implies task-switching or overlap (multitasking), and the resource is overloaded. This is a critical ambiguity.  
- **Direction:** If three analysts: utilization is ~78% per analyst, reasonable. If one resource: utilization is >100%, impossible without parallelism. The shared-account label suggests the former, but the overlapping intervals are consistent with the latter.

**Bottleneck detection bias:**  
- **Observation:** Completion times are {13:25, 13:20, 13:30, 13:22}, which are not ordered by start time. A02 starts at 13:05 but completes before A01 (which starts at 13:00).  
- **Bias mechanism:** This inversion is strong evidence that either: (1) there are multiple analysts working in parallel (not a bottleneck), or (2) the recorded completion times are inaccurate (e.g., due to delayed logging). If concurrent work by multiple analysts is normal, T-C is not a bottleneck; if one analyst is task-switching, the system is congested. The queue arrivals are spread over 12 min, and the queue appears to be processing at the rate of ~4 cases per ~30 min = 0.13 cases/min, while the arrival rate is ~4 cases / 12 min = 0.33 cases/min. If this is sustained, the queue will grow, suggesting a bottleneck.  
- **Direction:** Ambiguous. If three analysts, utilization is reasonable and there is no bottleneck (in fact, cases are being resolved in parallel, reducing wait). If one resource, it is a bottleneck and overloaded.

### G6 – End-of-Shift Bulk Form Submission (T-F manual_bulk_form)

**Waiting time bias:**  
- **Observation:** Queue arrivals 14:05–16:25 (140 min, over 2 hours); all complete at 17:00 (recorded 17:01).  
- **Bias mechanism:** Waiting times (complete  queue_arrival) are {115, 88, 62, 50, 36, 28, 35} min. However, the "complete" time is the form submission time (17:00), not the time each case was closed or reviewed. The true work window for each case is unknown; it could be that all cases were closed between 14:05 and 16:30 (as they arrived), and then batch-submitted at 17:00. Alternatively, the work was deferred until just before 17:00, and the reported waiting time is inflated by the submission delay.  
- **Direction:** Reported waiting time is **severely inflated** because it includes submission lag. True waiting (to task start) is likely much smaller (e.g., 5–20 min); the apparent 30–115 min waiting is due to the end-of-shift submission batching, not queue congestion.

**Service time bias:**  
- **Observation:** All cases report start = complete = 17:00, so service time = 0 min.  
- **Bias mechanism:** This is clearly incorrect. No task is completed in zero time. The most likely explanation is that all cases were pre-work (analyzed, closed, resolved offline), and 17:00 is the bulk submission time, not the actual completion time. True service times are unknown and could range from 5 to 140 min (if work was spread over the 2+ hour window) or could be a few minutes (if all cases were batch-processed just before submission).  
- **Direction:** Reported service time is **biased to zero**, which is completely misleading. True service time is unknown and cannot be inferred without additional data (e.g., timestamps of individual closures, or work logs).

**Resource utilization bias:**  
- **Observation:** T-F is (nominally) busy from 17:00–17:00 (0 min of bulk submission), but the queue spans 14:05–16:25 (140 min).  
- **Bias mechanism:** If work was performed online (14:05–16:25), then the utilization window is 140 min, and utilization is 100% (no idle). If work was deferred and 17:00 is a bulk submission, then the utilization window is 1 min (form submission), and reported utilization is 700% (7 cases × ~0 reported service time per case ÷ 1 min availability), which is nonsensical.  
- **Direction:** Reported resource utilization is **uninformative**; the resource is either fully utilized (if work was online) or the data are insufficient to compute utilization (if work was batch-processed offline).

**Bottleneck detection bias:**  
- **Observation:** All seven cases queue before 16:25 and are not recorded as complete until 17:00. The queue arrival times are spread over 140 min, with no visible closure until the bulk submission.  
- **Bias mechanism:** T-F appears to be a **severe bottleneck**: cases accumulate in the queue for over 2 hours before being submitted. However, this is likely an artifact of the form-submission process, not a true resource constraint. If cases can be worked in parallel (e.g., multiple clerks filling out different sections), then T-F is not a bottleneck for execution; it is a bottleneck for submission (a manual synchronization point). To diagnose the true bottleneck, we need to know whether cases are blocked until submission (in which case the submission process is a bottleneck) or whether they are completed offline and submission is merely a logging step (in which case the bottleneck is elsewhere, or absent).  
- **Direction:** **G6 is a critical false positive for bottleneck detection.** The high waiting time (2+ hours) and zero service time are artifacts of end-of-shift batch submission, not resource exhaustion. Without distinguishing work time from submission time, any performance analysis will be severely distorted.

### G7 – Timestamp Rounding (legacy_MES at 15-min granularity)

**Waiting time bias:**  
- **Observation:** Queue arrivals 13:58–14:11 (13 min); starts all 14:00 (rounded); waiting times (start  queue) are {2, 59, 56, 56, 49} min.  
- **Bias mechanism:** The legacy_MES rounding rule snaps all starts to the nearest 15-min boundary. If the rule rounds 13:45–14:00 down to 14:00, and 14:00–14:15 to 14:00 (or 14:15), then the apparent start time is identical for all cases, but the true start times could be up to 15 min apart. Given queue arrivals 13:58–14:11, the true start could be anywhere in [13:45, 14:15); if we assume start = queue_arrival for the case closest to 14:00 (M02 at 14:01), then true start  14:01, and the rounding rule snaps this to 14:00. For M01 (13:58), the true start is unknown: it could be 14:00 (if the case waits 2 min) or anywhere up to 14:15 (if queued longer). The reported waiting times assume all starts = 14:00, but true waiting is uncertain by ±7.5 min.  
- **Direction:** Reported waiting time is **uncertain by ±7.5 min per case**, masking the true distribution. Mean waiting time could be off by up to 50–100%; SLA compliance metrics are unreliable.

**Service time bias:**  
- **Observation:** All cases report service time = 15 min (14:15  14:00 = 15 min); no variation.  
- **Bias mechanism:** The rounding rule snaps all complete times to 14:15 (the next quarter-hour after start). The true completion time for each case is unknown: it could be anywhere in [14:00, 14:15). If tasks have different durations (e.g., M01 takes 10 min, M02 takes 12 min), the rounding rule obscures this variation. True service times could range from 1 to 15 min, but all are reported as 15 min.  
- **Direction:** Reported service time is **biased upward** (inflated to the granule width, 15 min); true service times are *shorter* and more variable than reported. Efficiency metrics (throughput, utilization) are biased downward (appear worse than true).

**Resource utilization bias:**  
- **Observation:** T-G is (nominally) busy from 14:00–14:15 (15 min reported) for 5 cases, with total reported service time = 75 min.  
- **Bias mechanism:** Reported utilization = 75 ÷ 15 = 500%, which is impossible (indicates 5 workers in parallel or incorrect accounting). True utilization depends on the true completion times (which are interval-censored). If true service times are {8, 10, 9, 11, 12} min (for example), and work is serial, then the true utilization window is ~50–60 min, and utilization  50 ÷ 50 = 100% (fully utilized). If work is parallel, then utilization = min(T-G availability, 15 min available) ÷ 15 min = up to 100%.  
- **Direction:** Reported resource utilization is **nonsensical** (>100%); the rounding rule makes per-case service times unreliable, and aggregated metrics fail.

**Bottleneck detection bias:**  
- **Observation:** Queue arrivals span 13:58–14:11 (13 min); cases are queued before they start (waiting times > 0).  
- **Bias mechanism:** Cases are queued, suggesting upstream demand exceeds T-G capacity. However, due to rounding, we cannot tell if the queue is growing (e.g., 30 min wait for the last case) or stable (2 min wait throughout). If the true service time is ~10 min per case (vs. reported 15 min), then T-G can process 6 cases per hour. With 5 cases in 13 min, the arrival rate is ~23 cases/hour, far exceeding T-G capacity. If true service is 15 min per case, the arrival rate is ~23 cases/hour and capacity is 4 cases/hour, still exceeding capacity. T-G is likely a bottleneck, but the rounding obscures the severity.  
- **Direction:** T-G is **likely a bottleneck**, but the 15-min granularity makes it impossible to quantify waiting or service time accurately. Operational validation is essential.

### G8 – Sequential Batching with System Downtime (T-H scanner, safety check 15:00–15:35)

**Waiting time bias:**  
- **Observation:** Queue arrivals 15:00–15:08 (8 min); first start at 15:38 (38 min after first queue arrival, or 3 min after safety check ends at 15:35); subsequent starts chain: 15:38, 15:45, 15:52, 15:59, 16:06.  
- **Bias mechanism:** If we compute waiting as [start  queue_arrival], we get {38, 43, 48, 54, 58} min. However, 33 of those 38+ minutes are consumed by the safety check (15:00–15:35), not by queuing. The true waiting (before work could even start due to resource availability) is [15:35  queue_arrival] = {35, 30, 26, 20, 17} min for each case. If we subtract the downtime, the adjusted waiting is [start  15:35] = {3, 10, 17, 24, 31} min, which represents queuing *after* the system came back. The last case (Q05, queue 15:08) waits 3 min before the resource fails (due to safety check), then waits 17 additional minutes after recovery.  
- **Direction:** Reported waiting time is **inflated by downtime**, which is not a queue delay but a system constraint. Adjusted waiting (excluding planned downtime) is lower. SLA metrics must account for downtime; otherwise, waiting times are falsely elevated.

**Service time bias:**  
- **Observation:** Service times (complete  start) are {7, 7, 7, 7, 7} min (all identical at 1-sec precision).  
- **Bias mechanism:** Each case takes 7 min to complete, and there is no bias; the service time is accurate. This is similar to G4.  
- **Direction:** Service time is accurate; no bias.

**Resource utilization bias:**  
- **Observation:** T-H is busy from 15:38–16:13 (35 min for 5 cases × 7 min service = 35 min work).  
- **Bias mechanism:** Utilization = 35 ÷ 35 = 100% (during the working window). However, if we include the downtime window (15:00–15:35, 35 min), then the full observation window is 15:00–16:13 (73 min), and utilization = 35 ÷ 73 = 48%. The choice of window (work-only vs. clock-time) dramatically affects the reported utilization.  
- **Direction:** Reported resource utilization depends critically on whether downtime is included. If downtime is **not** excluded, utilization is underestimated; if downtime is correctly excluded, utilization is accurately represented.

**Bottleneck detection bias:**  
- **Observation:** Queue arrivals are 15:00–15:08; all cases are released from the queue after 15:35. The arrival rate is ~5 cases / 8 min  37 cases/hour; the service rate is ~60 min ÷ 7 min/case  8.6 cases/hour (post-recovery). If the safety check lasts 35 min every hour, then the effective service rate is 8.6 cases/hour × (60  35) ÷ 60  3.6 cases/hour. With an arrival rate of 37 cases/hour and effective service of 3.6 cases/hour, T-H is a **critical bottleneck**.  
- **Bias mechanism:** The safety check downtime is a planned pause that reduces effective capacity. However, if the downtime is not accounted for, the bottleneck severity is underestimated. For example, if we compute bottleneck likelihood as arrival_rate / peak_service_rate = 37 / 8.6  4.3 (i.e., a 4-case backlog per hour), we miss the fact that the downtime exacerbates the problem.  
- **Direction:** T-H is a **severe bottleneck**, with downtime amplifying the queue delay. Waiting times are inflated by downtime, but even after excluding downtime, the queue grows unbounded at current arrival rates.

# Parse all times as datetime (2026-05-26)
def parse_time(time_str, full_str=False):
    """Parse HH:MM or HH:MM:SS to datetime on 2026-05-26."""
    if not time_str or time_str == '':
        return pd.NaT
    parts = time_str.split(':')
    hour = int(parts[0])
    minute = int(parts[1])
    second = int(parts[2]) if len(parts) > 2 else 0
    return pd.Timestamp('2026-05-26') + pd.Timedelta(hours=hour, minutes=minute, seconds=second)

    recording_lags = cluster_df['recording_lag_sec'].dropna().values
    
    # Overlap detection: count pairs with overlapping [start, complete] intervals
    overlap_count = 0
    for i in range(len(cluster_df)):
        for j in range(i+1, len(cluster_df)):
            si, ei = cluster_df.iloc[i]['start'], cluster_df.iloc[i]['complete']
            sj, ej = cluster_df.iloc[j]['start'], cluster_df.iloc[j]['complete']
            if pd.notna(si) and pd.notna(ei) and pd.notna(sj) and pd.notna(ej):
                # Check if [si, ei] and [sj, ej] overlap
                if not (ei <= sj or ej <= si):
                    overlap_count += 1
    
    # Queue arrival pattern: inter-arrival gaps
    queue_arrivals_sorted = cluster_df['queue_arrival'].dropna().sort_values()
    inter_arrivals = (queue_arrivals_sorted.diff()).dt.total_seconds() if len(queue_arrivals_sorted) > 1 else []
    
    # Adjacency: check if start[i+1]  complete[i] (within 10 sec tolerance)
    cluster_df_sorted = cluster_df.sort_values('sequence_no')
    adjacency_count = 0
    adjacency_details = []
    for i in range(len(cluster_df_sorted) - 1):
        curr_complete = cluster_df_sorted.iloc[i]['complete']
        next_start = cluster_df_sorted.iloc[i+1]['start']
        if pd.notna(curr_complete) and pd.notna(next_start):
            gap = (next_start - curr_complete).total_seconds()
            if gap <= 10:
                adjacency_count += 1
                adjacency_details.append(f"{cluster_df_sorted.iloc[i]['case']}->{cluster_df_sorted.iloc[i+1]['case']}: {gap:.0f}s")

## 5. Robustness and alternative explanations

### 5.1 Resource identity: Trusted vs. Shared-Account Scenarios

**Assumption:** All resource IDs are individual workers (trusted).

| Cluster | Implication | Effect on waiting | Effect on utilization |
|---------|----------|------------|-----------|
| G1 | RBT-7 is a single automated cell; resource identity is reliable. | Waiting time estimates are accurate (queue builds before the cell). | Utilization = 1 (cell is fully used in each batch). |
| G2 | T-B is a single tablet; resource identity is reliable. | Waiting time estimates are accurate; the 18-min maximum wait (S01) reflects queue buildup. | Utilization = 100% during 27-min window; spare capacity depends on inter-batch intervals. |
| G5 | `analyst_pool` is a shared VDI login; resource identity is **unreliable**. | Waiting time is **overstated** if computed as [start  queue_arrival]; true waiting per analyst is unknown. Aggregate waiting may be lower if multiple analysts are available. | Reported utilization is nonsensical (>100%) unless we know how many analysts share the login. |
| G6 | T-F is a single form resource; resource identity is reliable. | Waiting time is heavily biased by bulk submission (see Section 3); true waiting is unknown. | Utilization is uninformative (0 reported service time). |

**Assumption:** Resource IDs are pools or shared accounts; individual identity is unavailable.

| Cluster | Implication | Effect on waiting | Effect on utilization |
|---------|----------|------------|-----------|
| G1 | RBT-7 could be a cell pool (if there are multiple identical cells); cases could be routed to any cell. | Waiting time is **reduced** if multiple cells are available; reported waiting assumes single cell. | Utilization per cell is lower; total utilization across the pool is unknown. |
| G5 | `analyst_pool` has 1–3 analysts; individual badge IDs are unknown. | Waiting time (aggregate) is biased **upward** if we assume serial queueing; true waiting depends on how many analysts are idle. | Utilization is correct only if we know the pool size. |
| G6 | T-F is a shared form; multiple clerks might fill it simultaneously. | Waiting time is biased **downward** if multiple clerks work in parallel (not serial). | Utilization is not defined for a shared resource without knowing the number of operators. |

**Conclusion:** G5 and G6 are highly sensitive to resource identity reliability. **Recommendation: Retroactively obtain badge IDs or user session logs for analyst_pool and T-F.**

### 5.2 Timestamp Semantics: Exact vs. Interval-Censored

**Assumption:** Timestamps are exact (to the stated precision; e.g., 1-sec precision means ±0.5 sec).

| Cluster | Implication |
|---------|-----------|
| G1, G4, G8 | All timestamps (queue_arrival, start, complete) are accurate to ±0.5 sec. Batch detection is reliable. |
| G2, G3, G5, G6 | Timestamps are accurate to ±30 sec (1-min precision). Cases with identical start times (e.g., G3) could differ by up to 1 min in true time; they may not be simultaneous. |
| G7 | Timestamps are rounded to ±7.5 min boundaries (15-min precision, undocumented rule). All temporal analysis is fundamentally uncertain by ±7.5 min per field. |

**Assumption:** Timestamps are interval-censored (reported value is the rounding boundary; true value is within ±precision/2).

| Cluster | Implication |
|---------|-----------|
| G1 | 09:00 true start is in [08:59:59.5, 09:00:00.5]; no cases can be distinguished at sub-second granularity. Batch detection (whether genuine or setup) is robust. |
| G3 | 11:30 true complete is in [11:29:30, 11:30:30]; all four cases report completion in a 1-min window. They may complete over a wider range (e.g., 11:28–11:31) without interval-censoring the data. |
| G7 | All start times are in [13:52:30, 14:07:30]; all complete times are in [14:07:30, 14:22:30]. Within this window, no temporal order can be inferred; cases are indistinguishable. **Interval-censoring is mandatory for G7.** |

**Consequence for G6:** If we interval-censor 17:00, the true start is in [16:59:30, 17:00:30] and true complete is also in [16:59:30, 17:00:30]. The reported service time = 0 could actually span the entire interval, or could be negative (impossible). **Interval-censoring G6 service time is uninformative and should be replaced with a missing-value indicator.**

### 5.3 Three Cases Supporting Multiple Physical Explanations

#### Case 1: G1 (Apply label, RBT-7)

**Pattern:**  
- Queue arrivals: 08:54, 08:55, 08:56, 08:58 (staggered by 1–2 min).  
- Start: all 09:00.  
- Complete: all 09:03.

**Explanation A – Genuine Simultaneous Batch:**  
The RBT-7 fixture holds 4 items; items arrived over 4 minutes and were held in an upstream buffer. At 09:00, the fixture was loaded with all 4 items, and they were labeled in parallel in 3 minutes (09:00–09:03). **Implication:** No batching delay; items were queued upstream, not on the fixture.

**Explanation B – Start Batching / Setup:**  
Items arrived at 08:54–08:58 and queued on the fixture. At 09:00, the labeling process began (e.g., a setup step that applies settings to the fixture), and all items were processed in parallel. **Implication:** Setup time is zero or included in the 3-min window; the true service time per item is ~0.75 min (3 min ÷ 4 items) if serial, or 3 min if truly parallel.

**Explanation C – Timestamp Coarsening (1-sec precision boundary):**  
True start times could be 08:59:30–09:00:30 (within ±0.5 sec of 09:00). Items could have started sequentially (e.g., 08:59:40, 08:59:50, 09:00:00, 09:00:10), but all round to 09:00 at the 1-sec boundary. **Implication:** Start times are not reliably equal; we cannot distinguish simultaneity from short sequential delays.

**How to Distinguish:**  
- Obtain RBT-7 logs (PLC timestamp with finer granularity, e.g., milliseconds).  
- If the PLC reports all four starts within a 1-sec window, simultaneity is likely.  
- If the PLC reports 4-min staggered starts, **Explanation C is correct**, and all three cases were sequential queuing and processing.

---

#### Case 2: G3 (Release review, T-C desktop form)

**Pattern:**  
- Queue arrivals: 10:40, 10:52, 10:58, 11:05 (12–17 min apart).  
- Start: 11:02, 11:10, 11:17, 11:24 (8–7 min apart, staggered).  
- Complete: all 11:30.  
- Recorded_at: all 11:31.

**Explanation A – End Batching / Bulk Form Submission:**  
Four reviewers work in parallel on separate cases (starting at 11:02, 11:10, 11:17, 11:24). Each completes at different times (let's say 11:28, 11:20, 11:27, 11:22 true completion), but the form is not submitted until all four are finished (or until a deadline, 11:30). The form submission time 11:30 is recorded for all cases. **Implication:** True service times are unknown (5–28 min per case); reported 11:30 is a submission timestamp, not a completion timestamp.

**Explanation B – Concurrent Work with Asynchronous Completion:**  
Four reviewers work in parallel on a shared resource (e.g., T-C is a review workstation with a shared database). They access it at different times (11:02, 11:10, 11:17, 11:24) and complete independently. The database records all updates at 11:30 (due to a bulk sync or end-of-hour logging). **Implication:** True completion times are spread over [11:02, 11:30]; the 11:30 timestamp is a logging artifact, not a true completion.

**Explanation C – Timestamp Coarsening (1-min precision boundary, end-of-minute rule):**  
The desktop_form system rounds all times down to the nearest minute (or to a fixed end-of-minute boundary, e.g., XX:30). True start times could be 11:02–11:09, 11:10–11:16, 11:17–11:23, 11:24–11:29. True complete times could be spread over [11:00, 11:59], but all round to 11:30. **Implication:** No true concurrency; the identical 11:30 complete is a rounding artifact.

**How to Distinguish:**  
- Obtain case-level completion logs (e.g., database commit timestamps, form field update logs).  
- If true completions are spread (e.g., 11:18, 11:22, 11:27, 11:28), **Explanation A or B is correct**.  
- If true completions all cluster within 1 min (e.g., 11:29:30–11:30:30), **Explanation C is likely**.

#### Case 3: G6 (Close ticket, T-F manual_bulk_form)

**Pattern:**  
- Queue arrivals: 14:05, 14:32, 14:58, 15:10, 15:44, 16:02, 16:25 (over 140 min, scattered throughout the afternoon).  
- Start: all 17:00.  
- Complete: all 17:00.  
- Recorded_at: all 17:01.

**Explanation A – End-of-Shift Bulk Form Submission:**  
Cases arrived throughout the afternoon and were closed (resolved) at the time of arrival or shortly after. At 17:00 (end-of-shift), the clerk filled out a bulk form listing all 7 cases and submitted it. The 17:00 timestamp is a system-assigned submission time, not the true time each case was closed. **Implication:** True service times are ~5–20 min per case (time to close each case); the reported 0-min service and 140-min waiting are artifacts of the batching process.

**Explanation B – Queue Accumulation after Capacity Loss:**  
Cases arrived throughout the afternoon but could not be processed due to a system outage, downtime, or resource unavailability (e.g., T-F was broken or the clerk was in a meeting). At 17:00, the system recovered or the clerk became available, and all 7 cases were suddenly processed in a single bulk submission (0-min service time for each, meaning the form was filled in < 1 min). **Implication:** True service times are negligible (< 1 min per case); waiting times are 140–35 min, dominated by the unavailability period.

**Explanation C – Clock Skew or Logging Synchronization:**  
The manual_bulk_form system has a clock set incorrectly or out of sync with the queue arrival system. Cases were logged in the queue with their true arrival times (14:05–16:25), but the form system recorded the current time (17:00) instead of the case arrival or completion time. **Implication:** The true completion time is unknown; 17:00 is not meaningful for any individual case.

**How to Distinguish:**  
- Obtain user logs (when did the clerk start working on T-F? when did each case get assigned?).  
- Check T-F system logs (when was the form submitted? is there a bulk-submission timestamp separate from individual case timestamps?).  
- Verify system availability (was T-F unavailable from 14:05–16:25?).  
- If Explanation A is correct, the individual case files should have closure timestamps (independent of T-F) showing true completion around the queue-arrival time.  
- If Explanation B is correct, the T-F logs should show a ~1-min form-fill time at 17:00, and case files should also show closure at 17:00.  
- If Explanation C is correct, the case files and queue logs will contradict the form timestamps.

## 6. Data-collection redesign

### Priority 1: Lifecycle Timestamps (Critical Gaps)

**Current deficiency:**  
- `start` and `complete` are reported by the local source, but there is no record of what events they represent (e.g., does `complete` mean "user clicked finish" or "system recorded the update"?).  
- G6 demonstrates the risk: zero service time is not operational; it is a data collection failure.

**Recommendation:**

1. **Split lifecycle timestamps into granular events:**
   - `queue_arrival_time`: when the work item first entered the queue (upstream system, authoritative).
   - `work_start_time`: when the worker began execution (local worker action or sensor event).
   - `first_resource_contact_time`: when the resource (tool, machine, device) started processing (e.g., PLC timestamp).
   - `work_complete_time`: when the worker finished execution (local action).
   - `resource_release_time`: when the resource was released (e.g., PLC signals task done).
   - `form_submission_time`: when the data entry or batch submission occurred (system action).
   - `database_commit_time`: when the change was persisted (database event).

2. **Collect all timestamps at the source** with the highest available precision (e.g., millisecond from PLC, not 1-sec rounded).

3. **For each source system (PLC, tablet, desktop_form, etc.), document:**
   - True timestamp precision (e.g., clock resolution of the device).
   - Any rounding, batching, or post-processing rules applied.
   - Synchronization method (NTP, periodic sync, manual clock set).

**Impact:**  
- G6 would have separate `work_complete_time` (when the case was closed) and `form_submission_time` (17:00), allowing accurate service time and waiting time computation.  
- G7 would have documented the 15-min rounding rule upfront, and we could apply interval-censoring correctly.

---

### Priority 2: Recording Timestamps and Latency (High Impact)

**Current deficiency:**  
- `recorded_at` is the database insertion time, but it is unclear if this represents immediate logging or delayed batching.

**Recommendation:**

1. **Record the time the event was generated** (at the source) **separately from the time it was logged** (database insertion).
   - `event_timestamp` (source time, authoritative).
   - `logged_at` (database insertion time).
   - `latency_sec` = `logged_at`  `event_timestamp` (automatically computed).

2. **For sources with batching delays** (e.g., G6 manual_bulk_form), record:
   - `generated_at` (when the event occurred at the source).
   - `batched_with_count` (how many events were batched together).
   - `batch_submitted_at` (when the batch was logged).

3. **Alert on anomalies:**
   - If latency > 5 min, flag the event as delayed.
   - If multiple events have identical `logged_at`, investigate batching.

**Impact:**  
- G3 and G6 would immediately show high latency, prompting investigation.
- G7 would reveal that all 5 events were recorded with ~3–4 sec spread (not simultaneous bulk entry), which is a clue that they are not a simultaneous batch.

---

### Priority 3: Source Clock Synchronization (Medium Priority)

**Current deficiency:**  
- No indication of how or whether timestamps from different sources (PLC, tablet, desktop_form, scanner) are synchronized.

**Recommendation:**

1. **Implement NTP (Network Time Protocol) on all source systems** and log the synchronization status (offset, last sync time).

2. **For each source, record:**
   - `source_clock_offset_sec` (difference between source clock and authoritative clock, e.g., NTP server).
   - `clock_sync_timestamp` (when the last synchronization occurred).
   - `clock_drift_rate_ppm` (parts per million; how fast the source clock drifts).

3. **If sources have different time zones or daylight saving rules, explicitly document and convert all timestamps to a common reference timezone (e.g., UTC).**

**Impact:**  
- G8 mentions "safety system and repair queue have different clocks." Explicit clock offset documentation would clarify whether Q01's queue arrival at 15:00 aligns with the safety check start at 15:00.  
- G2 "begin group" button at 10:00 could be checked against tablet clock drift; if the tablet was 2 min slow, the true time was 10:02, reducing the apparent wait.

---

### Priority 4: Resource and Badge Identity (High Priority)

**Current deficiency:**  
- G5 uses `analyst_pool` without badge-level granularity, making it impossible to compute per-analyst utilization or to detect shared-account effects.

**Recommendation:**

1. **Capture individual user identity at the source:**
   - `badge_id` (RFID badge or username login).
   - `session_id` (unique session token, useful for shared accounts).
   - `workstation_id` (which physical workstation was used).

2. **For shared-account systems** (e.g., shared_VDI), correlate badge logins with case assignments:
   - When a case is opened, record which badge logged in.
   - When a case is closed, record the closing badge (may differ from opening badge).

3. **Distinguish between:**
   - **Resource**: the tool or machine (e.g., T-D scanner).
   - **Operator**: the person using the resource (badge_id).
   - **Work session**: a period of time a user is logged into a shared system.

**Impact:**  
- G5 would be split into individual analysts, and true concurrent work (or serial with shared-account overlap) would be distinguishable.  
- Utilization metrics would be per-analyst, not per-pool.

---

### Priority 5: Batch and Group Identifiers (Medium Priority)

**Current deficiency:**  
- No explicit batch or group ID; batches are inferred from temporal patterns (error-prone).

**Recommendation:**

1. **If work is organized into batches, capture batch metadata:**
   - `batch_id` (e.g., RBT-7 fixture ID, form submission ID).
   - `batch_size` (how many items or cases in the batch).
   - `batch_start_time` and `batch_end_time` (when the batch as a unit began and ended).

2. **If work has upstream/downstream dependencies (e.g., queues, service gates), record:**
   - `upstream_gate_id` (e.g., "begin group" button in G2).
   - `gate_open_time` and `gate_close_time`.
   - `queue_id` (which queue does this case belong to?).

3. **For automated systems (PLC, MES), export the internal batch/lot ID** if available.

**Impact:**  
- G1 would have RBT-7 fixture ID, confirming that all 4 cases were on one fixture.  
- G2 would have the group-session ID, clarifying whether the 10:00 start is a shared session start or four independent starts.  
- G6 would have form submission ID, explicitly separating the bulk form from individual case work.

---

### Priority 6: Workstation Capacity and Configuration (Low Priority)

**Current deficiency:**  
- No explicit capacity data (how many items can RBT-7 hold? can T-B process multiple cases in parallel?).

**Recommendation:**

1. **For each resource, document static capacity:**
   - `resource_type` (e.g., "automated_cell", "tablet", "form", "scanner").
   - `max_concurrent_items` (how many items can be processed in parallel).
   - `max_queue_depth` (how many items can be queued).
   - `setup_time_sec` (time to configure or prepare the resource).
   - `teardown_time_sec` (time to reset the resource).

2. **For each work session, record dynamic capacity:**
   - `queue_depth_at_arrival` (how many items were queued when this case arrived?).
   - `resource_available_time` (when is the resource free for the next item?).

**Impact:**  
- G1: Knowing that RBT-7 can hold 4 items confirms that all 4 cases (L01–L04) are on one batch; L05 would wait for the next cycle.  
- G4: Knowing that T-D has serial capacity (1 item at a time) confirms the sequential batching pattern.

### Priority 7: Pause, Resume, and Downtime Events (Medium Priority)

**Current deficiency:**  
- G8 mentions a safety check (15:00–15:35), but there is no explicit downtime event in the event log; it must be inferred from the data.

**Recommendation:**

1. **Log all system pause, resume, and downtime events:**
   - `downtime_start_time` and `downtime_end_time`.
   - `downtime_reason` (planned maintenance, safety check, system failure, operator break).
   - `downtime_type` (planned or unplanned).

2. **For each resource, track:**
   - `resource_state_transition` (idle  busy  idle, or busy  paused  busy).
   - `reason_for_state_change` (operator action, automatic timeout, system error).

3. **Ensure downtime events are timestamped with the same precision as work events.**

**Impact:**  
- G8 would have an explicit downtime event (safety check 15:00–15:35), allowing easy correction of waiting-time and utilization metrics.  
- Queue analysis would automatically exclude downtime periods from utilization calculations.

### Priority 8: Timestamp Precision Metadata (Low Priority)

**Current deficiency:**  
- `precision` column documents the stated granularity (e.g., "1 sec", "15 min"), but there is no indication of:
  - Whether timestamps are rounded, truncated, or exact.
  - Whether the precision is consistent across all events from a source.
  - Whether the stated precision matches the true achievable precision.

**Recommendation:**

1. **For each timestamp field, record:**
   - `stated_precision_sec` (e.g., 1, 60, 900).
   - `rounding_method` (e.g., "down", "nearest", "up", "undocumented").
   - `true_achievable_precision_sec` (based on hardware or software clock resolution).
   - `interval_censoring_bounds_sec` (e.g., ±0.5 for 1-sec precision, ±7.5 for 15-min precision).

2. **For sources with special rounding rules (e.g., G7 legacy_MES), document the rule explicitly in the source metadata, not just the precision.**

3. **Validate precision: compare timestep between events and confirm it matches the stated precision.**

**Impact:**  
- G7 would have documented the undocumented 15-min rounding rule, avoiding confusion and enabling proper interval-censoring.
- G2 (1-min precision) would have explicit bounds, allowing uncertainty quantification in batch detection.

**G7 (Manual measure, T-G):**  **Low confidence** (timestamp granularity obscures causality)
