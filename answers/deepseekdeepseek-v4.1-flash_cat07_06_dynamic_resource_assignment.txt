- Support documented training priorities without increasing SLA risk.
- Avoid specialist bottlenecks in Security, Approval, and Rework.
- Keep the policy explainable to workers and auditable from event logs.

**Hard/safety/compliance constraints**
- Skill `0` means not allowed.
- Security Review: skill `3`, or skill `1–2` only under explicit supervision by `R7_Gita` or `R8_Hugo`.
- Final Approval: skill `2–3`. Skill `1` may prepare, not finalize.
- No high-priority case to skill `<2` unless supervised.
- No resource may receive more than 4 new assignments in this batch.
- Quality Check batching only for normal/low priority with SLA remaining `>24h`.
- Avoid high-overtime-risk resources unless SLA risk is urgent and no safer alternative exists.
- For high-complexity/high-handover cases, prefer continuity unless the current owner is skill `0/1` and supervision is infeasible.

**Soft/preference trade-offs**
- Continuity may be broken for training, fairness, or bottleneck relief if SLA remains acceptable.
- Specialist routing is preferred for risky work, but not to the point of creating queues.
- Training assignments are supported when priority is normal/low and supervision exists.
- Workload fairness is measured by current open cases plus new batch assignments.
- Resilience favors cross-training and avoiding over-reliance on one or two specialists.

# 2. Assignment policy

**Policy name:** SLA-aware, continuity-preserving, skill-development routing.

**Pseudocode**
```text
priority_rank = {urgent: 4, high: 3, normal: 2, low: 1}
priority_weight = {urgent: 4.0, high: 3.0, normal: 1.5, low: 0.8}

sort queue by:
  SLA urgency descending, then priority_rank descending, then complexity descending

state:
  assigned_count[resource] = 0
  new_assignments = []

for case in sorted_queue:
    candidates = []

    for resource in resources:
        if assigned_count[resource] >= 4:
            continue

        skill = skill_matrix[resource, case.required_skill]
        if skill == 0:
            continue

        if case.required_skill == "Security":
            if skill < 3:
                if not supervision_by_R7_or_R8_available(case, resource):
                    continue
                else:
                    supervisor = best_security_supervisor()
            else:
                supervisor = None

        if case.required_skill == "Final Approval" and skill < 2:
            # skill 1 may prepare only; finalizer must be skill 2–3
            continue

        if case.priority in ["urgent", "high"] and skill < 2:
            if not supervised_case(case, resource):
                continue

        if resource.overtime_risk == "high" and case.priority in ["normal", "low"]:
            continue

        if hours_remaining[resource] <= estimated_activity_time(case) * service_factor:
            continue

        score = score_candidate(case, resource, supervisor)

        candidates.append((score, resource, supervisor))

    if candidates is empty:
        relax_soft_constraints_in_order(case)
        # Never violate Security, Final Approval, or high-priority skill rules.
        # Escalate to team lead if SLA < 2h and no safe candidate exists.

    chosen = max(candidates by score, tie_break)
    assigned_count[chosen.resource] += 1
    if chosen.supervisor:
        assigned_count[chosen.supervisor] += 1
    new_assignments.append(chosen)


function score_candidate(case, resource, supervisor):
    U = priority_weight[case.priority] * (1 / max(0.5, case.sla_hours))
    if case.sla_hours <= 4:
        U += 5.0

    S = 1.5 * (skill / 3.0)
    if skill == 1 and not supervisor:
        S -= 1.0
    if supervisor:
        S += 0.5   # supervised learning still has value

    C = 0
    if resource == case.current_owner:
        C += {"low": 0.5, "medium": 1.5, "high": 2.5}[case.handover_cost_band]
    if case.reassignment_count >= 2 and resource == case.current_owner:
        C += 1.5
    if resource != case.current_owner and case.handover_cost_band == "high":
        C -= 1.5

    W = -0.6 * (resource.open_cases / 10.0)
    W -= 0.8 * assigned_count[resource]
    W += {"low": 0.0, "medium": -1.0, "high": -2.5}[resource.overtime_risk]

    T = 0
    if case.priority in ["normal", "low"]:
        if case.required_skill == resource.training_priority:
            T += 2.0
        if skill == 1 and supervisor:
            T += 1.0
    else:
        if skill == 1:
            T -= 2.0

    R = 0
    if resource is sole_specialist_for(case.required_skill):
        R -= 1.5
    if resource.team != case.team:
        R += 0.3
    if resource.open_cases < 6:
        R += 0.5

    supervision_penalty = -0.5 if supervisor else 0.0

    return U + S + C + W + T + R + supervision_penalty


tie_break:
  1. lower assigned_count[resource]
  2. lower overtime_risk
  3. higher hours_remaining
  4. current owner
  5. resource ID
```

**Exception handling**
- If no candidate passes hard constraints, first relax team preference and minor continuity penalties.
- If still none, allow medium-overtime resource before high-overtime resource.
- High-overtime resource is allowed only for urgent/high cases and only with manager approval.
- Security and Final Approval rules are never relaxed.
- If SLA `< 2h` and no safe candidate exists, escalate rather than silently assigning unsafe work.

# 4. Comparison with baseline policies

| Dimension | First-available routing | Specialist-only routing | Proposed dynamic policy |
|---|---|---|---|
| Expected throughput | High short-term because it uses least-loaded resources, but can be inefficient due to skill mismatch. | High quality per case, but queues form around few specialists. | Moderate to high: urgent/high cases get skilled or supervised resources; normal/low cases are distributed. |
| SLA risk | Poor for urgent/high if mismatched or trainee-only; can miss deadlines despite low queue. | Low immediate risk for specialist cases, but high queue risk in Security/Approval/Negotiation. | Lower urgent/high risk: specialists and continuity used where SLA is tight; normal/low balanced. |
| Error/rework risk | Higher: first-available ignores specialization except skill 0. | Low immediate errors, but overload and fatigue may increase later errors. | Lower than first-available; slightly higher than specialist-only for supervised training cases, but controlled. |
| Fairness of workload | Loads low-open-case resources heavily; may still overwork high-overtime resources. | Overloads a few specialists such as R3, R6, R7/R8, R10. | Better: high-overtime R2/R4/R9 receive no new cases; caps at 4. |
| Skill development | Almost none; training is accidental. | Almost none; specialists stay specialists. | Explicit: C003 and C009 support diagnosis training under supervision. |
| Continuity of case ownership | Weak: owner changes to whoever is least loaded. | Mixed: specialist routing may change owners even for high-handover cases. | Strong for high-complexity/high-handover C001, C007, C016 and many current owners. |
| Resilience to absence/bottlenecks | Fragile: depends on broad assignment but lacks skill depth. | Fragile: reliance on R6, R7/R8, R3/R4, R10 creates bottlenecks. | More resilient: R8/R7 share Security, R6/R5 cover Approval/Negotiation, R10 batches Quality, R3 supervises diagnosis/rework. |

No policy is universally optimal. First-available minimizes idle time but risks rework. Specialist-only minimizes immediate mismatch but creates queues. The proposed policy accepts some slower trainee work on normal cases to gain development and fairness while protecting urgent/high-risk work.

# 5. Explanation to workers

We are not assigning work by queue length alone. For each case, we first check whether the activity is allowed by skill and safety rules. Security and Final Approval have strict rules. Urgent and high-priority cases must go to a qualified person or a supervised pair. After that, we look at SLA urgency, skill fit, whether changing owner would add costly handover, current workload, overtime risk, and whether the case can support documented training.

This means you may receive fewer new cases if you already have many open cases or high overtime risk. That is not a performance penalty; it is workload protection. You may receive a trainee or supervised case if it is normal/low priority and the SLA allows safe development. You may also see a case stay with the same owner even if someone else is slightly faster, because avoiding another handover can reduce rework and waiting.

If a case is urgent, we will favor qualified specialists and people with context. If you feel an assignment is unsafe or unrealistic, raise it immediately; the policy allows escalation, especially when SLA is under 2 hours and no safe candidate exists.

# 6. Process-mining audit indicators

- **Handover frequency**: number of cases where `org:resource` changes between consecutive events, divided by total cases. Use `pm4py.discover_handover_of_work_network`.
- **Reassignment count**: max or mean `reassignment_count` per case, segmented by priority and handover-cost band.
- **Skill mismatch**: join actual `org:resource` with the skill matrix and required skill; flag assignments below required threshold, especially for Security, Final Approval, and high-priority cases.
- **Workload distribution**: open cases plus new assignments per resource; monitor Gini/standard deviation and whether any resource exceeds 4 new assignments.
- **Overtime risk exposure**: count new assignments to resources with `overtime_risk = high`, especially for normal/low priority.
- **SLA misses**: compare case completion or next-event time against `sla_deadline`; segment by priority and assigned resource.
- **Rework/appeal after assignment**: link assignment decisions to later rework, correction, or appeal activities.
- **Training assignment share**: share of normal/low-priority assignments where required skill equals the resource’s `training_priority`; target at least 20%.
- **Specialist bottleneck indicators**: queue length and waiting time for skill-3-only activities, especially Security, Approval, and Rework. Use `pm4py.discover_batches` and performance DFGs.
- **Deviations from assignment policy**: compare actual `org:resource` against the policy recommendation stored in `assignment_reason` or an audit table.

def audit_policy(df, skill_matrix, overtime_table, policy_assignments):
    df = df.sort_values(["case:concept:name", "time:timestamp"])
    df["prev_resource"] = df.groupby("case:concept:name")["org:resource"].shift()
    handovers = df[
        df["prev_resource"].notna() &
        (df["prev_resource"] != df["org:resource"])
    ]
    handover_frequency = (
        handovers["case:concept:name"].nunique() /
        df["case:concept:name"].nunique()
    )

    reassignment_per_case = (
        df.groupby("case:concept:name")["reassignment_count"].max()
    )

    # Skill mismatch: depends on required threshold per activity
    enriched = df.merge(
        skill_matrix,
        on=["org:resource", "required_skill"],
        how="left"
    )
    skill_mismatch = enriched[
        enriched["skill_score"] < enriched["required_min"]
    ]

    workload = df.groupby("org:resource").size()

    overtime_exposure = df.merge(
        overtime_table,
        on="org:resource",
        how="left"
    ).groupby("org:resource")["overtime_risk"].first()

    training_share = (
        df[
            (df["case_priority"].isin(["normal", "low"])) &
            (df["required_skill"] == df["training_priority"])
        ]["case:concept:name"].nunique()
        /
        df[df["case_priority"].isin(["normal", "low"])]["case:concept:name"].nunique()
    )

    deviations = df.merge(
        policy_assignments,
        on="case:concept:name",
        how="left"
    )
    deviations = deviations[
        deviations["org:resource"] != deviations["recommended_resource"]
    ]

    return {
        "handover_frequency": handover_frequency,
        "reassignment_per_case": reassignment_per_case.describe().to_dict(),
        "skill_mismatch_count": len(skill_mismatch),
        "workload_distribution": workload.describe().to_dict(),
        "overtime_exposure": overtime_exposure.value_counts().to_dict(),
        "training_share": training_share,
        "policy_deviations": len(deviations),
    }
