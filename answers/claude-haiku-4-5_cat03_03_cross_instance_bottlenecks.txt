# Object-Centric Analysis: Hidden Coupling in Six-Job Manufacturing System

## 1. Interaction-graph description

### Node types and semantics
- **Job** (J1–J6): control points; represent customer/production orders
- **Component** (C1–C6): material instances; one-to-one with jobs in this system
- **ComponentLot** (L7, L8): batching containers coupling multiple jobs' materials
- **Machine** (CNC-2, OVEN-1, TEST-1): resource processors with utilization and scheduling state
- **Tool** (FIX-A, RACK-7, CAL-3): sub-machine-level fixtures and calibration entities; finer-grained contention
- **Batch** (B1, B2): logical groupings of jobs for synchronized processing, different cardinality than component lots
- **Shipment** (S1–S3): consolidation containers; couple completion timing across jobs

### Edge types and evidence status

**Direct observations** (from event logs):
- `Job requires Component` (6 edges): one-to-one binding
- `ComponentLot contains Component` (4 edges): lot-to-component membership
- `Batch batches Job` (5 edges): batch-to-job membership
- `Shipment consolidates Job` (6 edges): shipment-to-job membership
- `Machine processes Job` / `Tool acquires Job` (inferred from event relations)

**Inferred or partially recorded**:
- `Tool held_by Job` during `Machine Process`: J3FIX-A (explicit), J4FIX-A (implicit waiting), J5CAL-3 (implicit recalibration)
- `ComponentLot waits_for_release`: L7's quarantine affects J2 and J5 inconsistently
- `Batch waits_for_synchronization`: B1 and B2 both require OVEN-1 and RACK-7 availability
- `Shipment delays_job`: J1 held from 13:30 to 19:25 pending J4

### Higher-order motifs

**Motif 1: Batch-Tool-Machine-Job (synchronization bottleneck)**
```
B1 --batches--> {J1, J2, J3}
           \--requires--> OVEN-1
           \--requires--> RACK-7 (exclusive lock)
B1 --contains--> {L8, L7}
     \--L8 contains {C1, C3}
     \--L7 contains {C2, C5}
```
The `Batch Cure` event at 12:05 on OVEN-1 using RACK-7 synchronizes the readiness of J1 (ready 08:10), J2 (ready 08:25), and J3 (ready 11:55). Waiting arises not from machine unavailability but from batch formation policy: the batch cannot start until all constituent jobs' components are staged and the shared tool (RACK-7) is free.

**Motif 2: ComponentLot-Job-Batch-Machine (inconsistent coupling)**
```
L7 --contains--> {C2, C5}
           \--used_in--> {J2, J5}
                    \--batches-in--> {B1, B2}
                                \--process--> OVEN-1
```
J2 (in B1) was supervised overridden past quarantine at 10:20, but J5 (in B2) honored the release at 13:50. This creates a latent resource fault: if L7 had remained locked for both, B1 could not form at 12:05. The inconsistency is not in the process but in the **integration and data-linking pipeline**: the quarantine event was not related to J2 in the primary event extraction, so the flattening does not record it.

**Motif 3: Shipment-Job-Batch-Tool (delayed-job consolidation)**
```
S1 --consolidates--> {J1, J4}
              \--batches-in--> {B1, B2}
                          \--requires--> RACK-7
J1 --packed-at--> 13:30
J4 --packed-at--> 19:10
S1 --dispatches-at--> 19:25
```
J1 is ready 5 h 55 min before S1 dispatch, entirely due to waiting for J4. J4's delay stems from B2's synchronization on J5's readiness (14:40) plus tool contention (RACK-7 cleaning 12:55–14:35). The shipment thus transmutes batch/tool delays into job-completion delays indirectly.

## 2. Quantitative delay decomposition

### Calculation 1: Batch synchronization delay for J1 and J2 in B1

**J1:**
- Ready for batch: 08:10
- Batch Cure starts: 12:05
- Observed synchronization waiting: **3 h 55 min**
- Counterfactual: If J1 could proceed solo (no batch requirement), it would begin curing at 08:10.
- Attributable to: waiting for J2 and J3 (J3 not ready until 11:55).
- Caveat: J1's readiness timestamp assumes component C1 is staged; no evidence of upstream delays specific to J1.

**J2:**
- Ready for batch: 08:25
- Batch Cure starts: 12:05
- Observed synchronization waiting: **3 h 40 min**
- Counterfactual: If J2 alone could enter B1, it would begin at 08:25 (assuming OVEN-1 and RACK-7 are free).
- Attributable to: waiting for J3 (latest) and downstream resource availability.
- Additional constraint: C2 is in L7, which undergoes quarantine at 10:20. J2 was overridden past this lockout, but if the lockout had applied strictly, J2 would wait until 13:50. Here, J2 was permitted to proceed at ~10:20 (or earlier), so the quarantine is not the primary cause of the 08:2512:05 gap.
- **Net delay estimate: 3 h 40 min, primarily batch synchronization on J3.**

### Calculation 2: Fixture contention delay for J4

**Observed timeline:**
- J3 holds FIX-A: 09:00–11:40 (exclusive lock, 2 h 40 min)
- J4 reaches CNC-2: 09:50
- CNC-2 idle: 10:05–10:47 (42 min)
- J4's Machine Process starts: 11:45

**Decomposition:**
- J4 arrives at 09:50, when FIX-A is held by J3 (will be until 11:40).
- Counterfactual 1 (no fixture contention): If FIX-A were available at J4's arrival (09:50), and CNC-2 were immediately available, J4 could start at 09:50 + setup time. Setup time is not directly given, but the typical sequence is Setup  Machine Process. Assume 10 min setup  start ~10:00.
- Counterfactual 2 (current system): J4 must wait for J3 to release FIX-A (11:40), then acquire and set up, starting at 11:45.
- **Waiting time attributable to fixture contention: 11:45  09:50 = 1 h 55 min.**
- **Caveat:** CNC-2 is idle 10:05–10:47 (42 min) even though J4 has not yet acquired FIX-A. This could indicate either (a) other jobs were processed, (b) setup for a different job, or (c) unrecorded waiting for another constraint. The 42 min gap is *not* explicable by FIX-A alone; however, FIX-A availability from 11:40 onward is the most obvious trigger for J4's process start at 11:45.
- **Conservative estimate: 1 h 10 min** (from 10:47, end of idle, to 11:45), attributed to FIX-A + other setup overhead.

### Calculation 3: Shipment consolidation delay for J1 in S1

**Observed timeline:**
- J1 packed: 13:30
- J4 packed: 19:10
- S1 dispatches: 19:25
- Time J1 waits in shipment state: 19:25  13:30 = **5 h 55 min**

**Counterfactual (individual dispatch):**
- If J1 were dispatched individually 25 min after packing (matching S2 and S3 policy), dispatch would occur at 13:55.
- Shipment consolidation delay: 19:25  13:55 = **5 h 30 min** (assuming uniform 25 min overhead for S1).
- Attributable to: waiting for J4 to complete all processing and packing.

**Caveat:** The delay is real but is a consequence of J4's prior delays (from batch synchronization and tool contention). S1 policy does not cause J4's delay; it *exposes* it by forcing J1 to wait.

### Calculation 4: Lot quarantine and release for J5

**Observed timeline:**
- L7 quarantine: 10:20
- L7 release: 13:50
- J5 ready for batch: 14:40
- B2 starts: 14:50

**Counterfactual (no quarantine):**
- If L7 were not quarantined, C5 (and C2 for J2) could proceed at ~09:50 (or whenever the lot was initially created).
- Assume J5's "ready" timestamp (14:40) would be shifted earlier by 13:50  10:20 = **3 h 30 min**, to ~11:10.
- Attributable delay if strict: 3 h 30 min.
- **Actual impact on B2 start:** J5 is ready at 14:40; B2 starts at 14:50. The lot release at 13:50 is *not* the bottleneck for B2 start; rather, J4's readiness at 13:10 and RACK-7 availability (until 14:35) are. Thus, the quarantine delay to J5 is *masked* by other batch constraints.
- **Conservative estimate: 0 min** (the quarantine does not delay B2 start), but **3 h 30 min latent delay** if J5 were on a critical path for a different shipment or batch.

### Calculation 5: Calibration recalibration delay for J6

**Observed timeline:**
- J5 ready for final test: 16:00
- J5 tests: 16:10–16:35 (25 min)
- CAL-3 recalibrated: 16:35–17:20 (45 min)
- J6 ready for test: 16:05
- J6 tests: 17:25–17:50
- TEST-1 idle: 16:35–17:25 (50 min)

**Counterfactual (no recalibration):**
- If CAL-3 did not require recalibration between J5 and J6 tests, J6 could start at ~16:40 (5 min after J5 ends, for tool changeover or release).
- Actual start: 17:25.
- Delay attributable to CAL-3 recalibration: 17:25  16:40 = **45 min** (matching the recalibration event duration).
- **Caveat:** The recalibration may be required by process specification (e.g., thermal drift, regulatory mandate) rather than congestion. If recalibration is mandatory after every test, the delay is policy-driven, not resource-contention-driven.
- J6 itself was not ready until 16:05, so the critical waiting from J6's perspective is 17:25  16:05 = **1 h 20 min**, of which 45 min is recalibration and 35 min is the time gap from J6's readiness to recalibration start.

## 4. What flattening misses

### Job-flattened DFG

**What it makes visible:**
- Average process flow: Release  Stage  Machine  Inspect  Pack  Dispatch
- Per-job cycle times and variance
- Rework frequency (2 out of 6 jobs)

**What it hides:**
- **Synchronization waiting:** J1 and J2 do not have explicit "wait for batch" activity; the delay from 08:25 to 12:05 is attributed to "Stage Component" or "Machine Process," flattening it into one arc.
- **Tool contention:** J4's waiting for FIX-A is not a separate activity; it appears as longer "Machine Process" or is hidden entirely if waiting occurs before arrival at CNC-2.
- **Lot coupling:** J2's quarantine (L7) is not in the Job flattening, so J2 appears to proceed at the same rate as J1, masking the latent risk.
- **Shipment consolidation:** J1's 5h 55min wait is not visible; J1 appears to finish when it is packed (13:30), not when it is dispatched (19:25).

**Misleading conclusions:**
- All six jobs have similar flow times (no outlier exceeds 1.8). This suggests **even process efficiency**, but it hides the fact that J1 and J4 are coupled via S1, and their actual completion times are not independent.
- The two rework instances (2 out of 6) appear random and low-frequency. In fact, the jobs with rework might have been selected for inspection due to tool condition (e.g., FIX-A wear) or batch homogeneity; without the tool and batch context, rework looks stochastic, not systematic.

### Machine-flattened summary

**What it makes visible:**
- Machine utilization: CNC-2 54%, OVEN-1 44%, TEST-1 58% — all below 60%, suggesting no saturation.
- Typical activity sequences and idle time.

**What it hides:**
- **Job queuing:** OVEN-1 is idle from 12:55 to 14:50 (115 min), but this is not "machine idle" — it is *RACK-7 unavailable*. The machine-flattening does not distinguish between machine-free and resource-unavailable.
- **Batch formation delays:** B1's `Batch Cure` at 12:05 is recorded as a single event. The flattening does not show that OVEN-1 was technically available at 12:05 but the batch could not start until all jobs were ready.
- **Tool recalibration:** TEST-1 is idle 16:35–17:25, but this is not process idle; it is waiting for CAL-3 recalibration. The event "Recalibrate CAL-3" is not attached to TEST-1 in the machine flattening.
- **Interaction with upstream resources:** CNC-2 idle gaps (e.g., 10:05–10:47) are recorded, but the cause (FIX-A hold by J3) is not visible in the machine view.

**Misleading conclusions:**
- Low utilization suggests **excess capacity and no bottleneck**. This is false. The bottleneck is earlier (component staging, tool availability, batch formation) or later (shipment consolidation). Adding more work to these machines would not improve throughput without addressing the upstream bottlenecks.
- The longest idle gap (73 min on OVEN-1) appears to be a scheduling inefficiency, but it is actually the necessary synchronization time for batch formation (B1 ends at ~12:55, B2 is ready at 14:50).

### Batch-flattened DFG

**What it makes visible:**
- Batch  Machine  Unbatch flow
- Batch dwell time on machine

**What it hides:**
- **Per-job delays within the batch:** B1 contains J1, J2, J3. The flattened batch DFG shows B1 entering OVEN-1 at 12:05 and exiting at ~13:00 (estimated). But J1 and J2 were ready at 08:10 and 08:25, respectively; the batch DFG attributes the wait to *batch formation*, not to *individual job readiness*.
- **Shipment coupling across batches:** B1 and B2 are processed separately, but J1 (from B1) and J4 (from B2) are consolidated in S1. The batch flattening does not reveal this downstream coupling.
- **Tool and component-lot constraints:** B1 and B2 both require RACK-7; the flattening does not model this exclusive dependency.

**Misleading conclusions:**
- Batch efficiency (cycle time per job in batch) appears good. However, the batch-formation delay (3h 40min for J1 and J2) is hidden, making the batching policy look benign.

### Tool-flattened DFG

**What it makes visible** (if a tool flattening existed):
- Tool acquire/release events
- Tool contention (time between release by one job and acquire by the next)

**What it hides:**
- **Machine-job-tool interaction:** FIX-A is held by J3 from 09:00 to 11:40, but the flattening would not show that J4 is blocked from CNC-2 as a result.
- **Tool-batch coupling:** RACK-7 is used by B1 and B2; a tool flattening would show sequential batches, but not the synchronization delay within each batch.

**Misleading conclusions:**
- FIX-A and RACK-7 appear to have reasonable hold times (2h 40min and ~1h, respectively). Without visibility into how many jobs are blocked during each hold, the tool flattening might suggest tool efficiency is acceptable, whereas the *damage* is substantial (J4 blocked 1h 55min, B2 delayed 115 min).

### ComponentLot-flattened DFG

**What it makes visible:**
- Lot creation  quarantine/release  lot consumption flow

**What it hides:**
- **Job-level impact:** L7's quarantine at 10:20 and release at 13:50 are recorded, but the flattening does not show that J2 was overridden and J5 was strictly locked. This creates an inconsistency that violates causality.
- **Multi-job coupling within lot:** L7 contains C2 and C5, used by J2 and J5. The lot flattening shows two jobs benefiting from one lot, but does not reveal the *risk* that if the quarantine had been enforced on both, both jobs would be delayed.

**Misleading conclusions:**
- Quarantine duration (3h 30min) is recorded, but the impact on job cycle time is not. If J5 arrives at the quarantine window, the delay is real; if J2 is overridden, the delay is avoided. The flattening does not distinguish between *avoidable* and *unavoidable* delays.

### Shipment-flattened DFG

**What it makes visible:**
- Shipment creation  load  dispatch flow
- Shipment cycle time: ~1.1 h (median)

**What it hides:**
- **Wait for consolidation:** S1 shows Load at ~19:10 and Dispatch at 19:25 (15 min). But J1 was packed at 13:30; the flattening does not record the 5h 55min gap between J1's packing and S1's formation.
- **Job-consolidation coupling:** S1 consolidates J1 and J4, but the flattening does not show which job was the bottleneck or whether the consolidation was necessary.

**Misleading conclusions:**
- Shipment cycle time is short (~1.1 h), suggesting shipments are processed quickly. This ignores the fact that jobs sit packed for hours waiting for shipment partners. The true cycle time from job pack to shipment dispatch is much longer.

### Why low machine utilization coexists with long job waiting

**Causal explanation:**
Machines are **downstream resources**. They are idle because their **input is throttled** by:
1. **Batch synchronization:** Jobs are held until the batch is complete, reducing arrival rate at machines.
2. **Tool contention:** Jobs wait for sub-machine tools (FIX-A, RACK-7, CAL-3) before arriving at machines, increasing inter-arrival time.
3. **Component-lot releases:** J2 and J5 are delayed by L7 quarantine, reducing the flow of jobs into batches.
4. **Upstream scheduling:** Jobs are released on different schedules (J1 at 08:10, J3 at 11:55); this staggering reduces simultaneous demand on machines.

**Consequence:** Machines have **capacity slack**, but jobs **experience long wait times**. This is characteristic of **pull-push mismatch** or **batch-oriented processing with synchronization constraints**.

## 5. Object-lifecycle evidence

### Narrative 1: J4 through batch, tool, machine, and shipment

**Timeline:**
- 09:50: J4 arrives at CNC-2, ready to be processed.
- 09:50–11:40: J4 blocked waiting for FIX-A (held by J3).
- 11:45: J4's Machine Process starts on CNC-2 (after FIX-A released at 11:40 and acquisition + setup completed).
- 11:50 (est.): J4's Machine Process completes; moves to next stage.
- 13:10: J4 ready for batch (B2).
- 14:40: J5 ready for batch (B2).
- 14:35: RACK-7 cleaning/quarantine completes.
- 14:50: B2 (containing J4, J5) enters OVEN-1 for Batch Cure.
- ~15:50 (est.): B2 exits OVEN-1.
- 19:10: J4 packed.
- 19:25: S1 (containing J1, J4) dispatches.

**Objects and causal chain:**
```
J4 --ready-at-09:50--> CNC-2
  --waits-for--> FIX-A (held by J3)
  --acquires-FIX-A-at-11:40--> CNC-2.Machine_Process (11:45–11:50)
  --exit-Machine--> B2 (batch formation, waits for J5 and RACK-7)
  --enters-OVEN-1-at-14:50--> B2.Batch_Cure
  --exit-Batch--> Inspect, Pack (19:10)
  --wait-in-shipment--> S1 (waits for J1 consolidation; S1 contains J1, J4)
  --dispatch-at-19:25--> S1.Dispatch
```

**Temporal precedence:**
- J3's FIX-A release (11:40)  J4's CNC-2 start (11:45): +5 min setup
- J4 ready for batch (13:10), J5 ready (14:40): batch must wait for J5, +90 min
- RACK-7 ready (14:35), B2 ready (14:50): RACK-7 availability +15 min slack
- J4 packed (19:10), S1 dispatch (19:25): +15 min; but J1 waiting since 13:30 (5h 55min)

**Resource feasibility:**
- FIX-A is exclusive; J3 holds it until 11:40. No alternative fixture is available.
- RACK-7 is exclusive and undergoing cleaning; delay is not resource choice but maintenance schedule.
- OVEN-1 is available from 13:00 onward (B1 exits ~13:00), but B2 formation is synchronization-gated on J5 and RACK-7, not machine availability.

**Policy constraints:**
- Batch policy: J4 and J5 must cure together; cannot split batch.
- Shipment policy: S1 contains J1 and J4; cannot dispatch before both are ready.
- Tool policy: FIX-A is tied to CNC-2 for certain job types (J3, J4); no cross-machine tool sharing.

**Causal speculation:**
- If FIX-A had been available at 09:50, J4 could start at 10:00, finishing by ~11:00, making batch readiness 11:00 instead of 13:10. This would advance B2 entry to ~12:10 (if RACK-7 were ready), but RACK-7 cleaning runs until 14:35, so B2 would still be delayed to 14:50.
- If B2 could form with J4 alone (no synchronization with J5), B2 would enter at 13:20, exiting by ~14:20. J4 would then be packed by ~17:20, and S1 could dispatch at 17:45 (vs. actual 19:25). **Gain: 1h 40min**, but foregone: batching efficiency (unknown).
- If S1 could dispatch J1 alone, J1 would leave at 13:55. **Gain for J1: 5h 30min**, but increased shipment cost and logistics overhead.

  --enters-B1-at-12:05--> OVEN-1.Batch_Cure (using RACK-7)
  --exit-Batch--> Inspect, Pack (13:30)

**Temporal precedence:**
- J2 ready (08:25)  B1 start (12:05): 3h 40min, waiting for J3
- L7 quarantine (10:20)  L7 release (13:50): 3h 30min lock
- B1 entry (12:05)  B1 exit (~13:00)  J2 pack (13:30): +1.5h for downstream
- J2 pack (13:30)  S2 dispatch (15:10): ~1h 40min (vs. ~25min for S2 and S3)

**Resource feasibility:**
- RACK-7 is held from ~12:05–13:00 by B1, and is unavailable 12:55–14:35 for cleaning/quarantine. J2 does not use RACK-7 itself; it uses OVEN-1 as part of B1.
- L7 is locked; J2 cannot proceed if strict enforcement applies. But J2 *did* proceed at 12:05, suggesting override.

**Policy constraints:**
- Batch policy: J2 must wait for J1 and J3 (all in B1) before curing.
- Lot policy: C2 is in L7; quarantine should lock all components in the lot. However, J2 was permitted to proceed despite the lock on L7. This is either (a) a policy exception, (b) data inconsistency, or (c) the component was released before the lot quarantine was formally recorded.
- Shipment policy: S2 consolidates J2 and J3 (from the same batch B1); dispatch is delayed by the slower job or a fixed delay after the last pack.

**Causal speculation:**
- If L7 quarantine had been strictly enforced, J2 could not proceed until 13:50, preventing B1 from forming at 12:05. B1 would be delayed to 13:50 at earliest (if J3 is already ready by then, which it is at 11:55). **Potential delay: ~1h 45min for B1**.
- If J3 were not in B1 (single-job batch), B1 would form at J2's readiness (08:25) + J1's readiness (08:10), so ~08:25. B1 would exit at ~09:25, and J2 would be packed by ~10:55, dispatching with S2 at ~11:20. **Gain: 3h 50min** for J2, but lost batching efficiency.
- The latent risk is that J2 is coupled to L7, and L7 is also coupled to J5 (in a different batch, B2). If both J2 and J5 are strictly locked, the lot becomes a sequential bottleneck for two separate batches. This is a **hidden multi-batch dependency**.

**Policy constraints:**

- If J5 and J6 required **different** calibrations (e.g., J5 for thermal components, J6 for structural), the recalibration is unavoidable. If they require the **same** calibration, the recalibration might be redundant if performed within a time window (e.g., <1 hour).

## 8. Falsification and additional data

### Observations that would weaken the top-ranked hypothesis (batch synchronization + tool contention)

1. **J3's staged component was not actually ready at 11:55; the timestamp is a data error.** If J3's true readiness is 12:00, then B1's start at 12:05 is not batch-synchronization delay but rather immediate dispatch post-readiness, suggesting batch-formation overhead, not job readiness variance.

2. **B1 and B2 do not require synchronization; they are formed on a first-come, first-served basis, and J1 and J2 were held by an earlier process (e.g., design review, customer approval) until 12:05.** This would shift the bottleneck from batch policy to upstream approval gates.

3. **OVEN-1 was actually busy or under maintenance until 12:05, not idle.** The idle gap from 13:00 to 12:55 (or lack thereof) would indicate the machine is the true bottleneck, not batch formation.

4. **J4 and J5 are not in the same batch (B2).** If they are in different batches and OVEN-1 is large enough to process them sequentially in quick succession, the delay would not be synchronization-gated on J5's readiness.

5. **RACK-7 cleaning is not a real constraint; it is a default placeholder in the system, and jobs do not actually need RACK-7 exclusively.** If RACK-7 can be used concurrently by multiple batches or if OVEN-1 does not require RACK-7, then the cleaning/quarantine event is misleading.

6. **S1 consolidation policy is dynamic and can be overridden by a customer SLA.** If S1 can dispatch J1 early (breaking consolidation), then the 5h 55min delay is avoidable, not forced. This would reduce the severity of the shipment bottleneck.

---

### Additional fields or event types that would discriminate among hypotheses

1. **`Batch-formation-decision` event:** timestamp, decision rule (e.g., "time threshold," "job-count threshold," "readiness threshold"), decision rationale (e.g., "waiting for J3," "RACK-7 unavailable," "batch size policy"). This would clarify whether batch-start delays are due to policy or resource unavailability.

2. **`Job-readiness-state` change log:** per-job, timestamps when readiness changes (component staged, tool acquired, lot released). This would disambiguate between "job is truly ready" and "timestamp is a system artifact."

3. **`Tool-hold` and `Tool-wait` events:** explicit acquisition and release of FIX-A, RACK-7, CAL-3 per job or batch. Currently, tool contention is inferred from machine idle gaps; explicit logging would confirm or refute.

4. **`Lot-quarantine-decision` and `Lot-release-decision` events:** who authorized the quarantine (quality, supervisor), reason (e.g., "failed inspection," "material variance"), and release decision. This would show whether lot holds are systematic or ad-hoc.

5. **`Batch-efficiency-metric`:** actual throughput per batch (jobs per hour), cost per job within batch, thermal/time waste (if any). This would enable cost-benefit analysis of batch sizes.

6. **`Shipment-consolidation-decision` event:** timestamp, logic (e.g., "awaiting J4 for consolidation," "SLA deadline," "cost optimization"), alternative shipment options (could J1 be shipped alone?).

7. **`Machine-setup` and `Machine-changeover` events:** distinct from "Machine Process," with duration. This would isolate setup time from processing time and reveal if setup is the hidden overhead.

8. **`Supervisor-override` event:** timestamp, object affected (e.g., "J2 released from L7 quarantine"), decision, and authorization. This would explain data inconsistencies and policy exceptions.

9. **`Resource-capacity-constraint` event:** at decision points (batch formation, job release), explicitly log which resources (machine, tool, lot) are the binding constraint. This would move constraint identification from inference to observation.

10. **`SLA-or-priority` per job or shipment:** SLA delivery deadline, priority level, customer name. This would show if early-ready jobs like J1 have a hard deadline that S1 consolidation violates.

11. **`Process-parameter` per batch or job:** thermal profile, cure time, required calibration tolerance, etc. This would explain why CAL-3 recalibration is necessary and whether it can be batched or parallelized.

12. **`Component-lot-traceability` to component, job, and batch:** a complete mapping showing which components are in which lots, used in which jobs, and batched when. Currently, only 4 components in 2 lots are linked; this is too sparse. A full mapping would reveal hidden multi-job coupling.

## Summary of Key Insights

**The six-job system is tightly coupled across four dimensions:**

1. **Batch synchronization:** J1 and J2 are held for J3, creating a 3h 40min delay with no machine bottleneck.
2. **Tool contention:** J4 waits 1h 55min for FIX-A, and J6 waits 45min for CAL-3 recalibration, reducing effective capacity despite low machine utilization.
3. **ComponentLot latent coupling:** L7 quarantine affects both J2 and J5 inconsistently, creating a data-integration artifact that masks risk.
4. **Shipment consolidation:** S1 forces J1 to wait 5h 55min for J4, transmuting upstream delays into job-completion delays.

**Flattening hides all four**: traditional DFG per object type shows normal flow and low machine utilization, suggesting no bottleneck exists. Object-centric analysis reveals the hidden structure: synchronization, tool contention, and consolidation are the primary mechanisms, not machine capacity.

**Interventions must target the synchronization and tool layers**, not machine capacity. Adding machine throughput (e.g., faster ovens) would have minimal impact as long as batching and tool contention remain unaddressed.
