## 2. Raw-versus-normalized interpretation

The raw-versus-mapped fitness gap is the clearest evidence of logging or semantic drift. In January and February, raw and mapped fitness are essentially identical, around 0.92–0.93. In March, raw fitness falls to 0.55 while mapped fitness remains 0.90, which implies that much of the apparent conformance collapse is caused by the migration: `Validate Eligibility` became `Eligibility Screen`, duplicated `Open Case` events appeared, and resource identifiers became more often missing. The gap does not imply that the real process was unchanged; it only shows that the old raw labels no longer match the old model.

A label mapping can recover conformance because the control-flow position of `Eligibility Screen` appears to match `Validate Eligibility`: the normalized DFG keeps `Register -> Eligibility` at 100 per 100 cases and `Eligibility -> CollectDocs` at 98 in March. But mapping one activity name does not prove that validation content, decision quality, resources, or downstream behavior remained stable.

Duplicated technical events primarily distort directly-follows relations, variants, start activities, and raw alignments. Missing resources distort organizational mining, handover networks, workload, fairness, and team-specific diagnostics. They should not be treated as random missingness because the observations say resource missingness is concentrated in migrated activities.

Post-May patterns cannot be dismissed as logging drift alone. Mapped fitness remains fairly high, but supplier Z share, rework variants, `Assess -> Request Info`, cycle time, and p90 all move materially after May. Those changes survive label normalization and align with known operational events.

The primary monitoring population should be the full normalized case population, not only stable standard cases, because management’s SLA exposure and customer impact occur at the whole-process level. However, every primary alert should automatically decompose into supplier, complexity, priority, and resource/team strata. A stable non-Supplier-Z standard-complexity segment is useful as a sentinel, but making it the primary population would condition away exactly the supplier and seasonal mechanisms that matter operationally.

Seasonality should be handled with seasonally matched reference windows for October–November and with stratified expected ranges for high-complexity share and volume. Multiple testing should be handled by grouping monitors into families—schema, behavior, performance, resource, outcome—and requiring either persistence across windows or corroboration across independent artifacts before operational escalation. The alert logic should be metric-specific: label drift can be sudden and binary, while queue and temporal-profile drift should use rolling distributional bands and segmentation.

# 1. Validate the data.
required_monthly_cols = {
    "month", "cases", "high_complexity_pct", "supplier_z_pct",
    "fast_variant_pct", "rework_variant_pct", "median_cycle_h",
    "p90_cycle_h", "raw_model_fitness", "mapped_model_fitness",
    "distinct_activity_labels", "missing_resource_pct",
    "duplicate_open_case_pct"
}
missing_cols = required_monthly_cols - set(monthly.columns)
if missing_cols:
    raise ValueError(f"Missing monthly columns: {sorted(missing_cols)}")

if monthly["month"].duplicated().any():
    raise ValueError("Duplicate months in monthly summary.")

for col in [
    "high_complexity_pct", "supplier_z_pct", "fast_variant_pct",
    "rework_variant_pct", "missing_resource_pct", "duplicate_open_case_pct"
]:
    if not monthly[col].between(0, 100).all():
        raise ValueError(f"{col} contains values outside 0..100.")

for col in ["raw_model_fitness", "mapped_model_fitness"]:
    if not monthly[col].between(0, 1).all():
        raise ValueError(f"{col} contains values outside 0..1.")

if not (monthly["p90_cycle_h"] >= monthly["median_cycle_h"]).all():
    raise ValueError("p90_cycle_h should be at least median_cycle_h.")

rate_cols = [c for c in dfg_rates.columns if c != "month"]
if dfg_rates[rate_cols].isna().any().any():
    raise ValueError("DFG rate table contains missing values.")

# 2. Calculate baseline-relative changes.
baseline = monthly[monthly["month"].dt.month.isin([1, 2])].mean(numeric_only=True)

change_cols = [
    "cases", "high_complexity_pct", "supplier_z_pct",
    "fast_variant_pct", "rework_variant_pct", "median_cycle_h",
    "p90_cycle_h", "raw_model_fitness", "mapped_model_fitness",
    "missing_resource_pct", "duplicate_open_case_pct"
]

    changes[f"{col}_delta_vs_baseline"] = monthly[col] - baseline[col]
    if baseline[col] != 0:
        changes[f"{col}_pct_vs_baseline"] = 100 * (monthly[col] - baseline[col]) / baseline[col]

    l1_from_jan = float((vec - baseline_vec).abs().sum())

        "mean_abs_from_jan": mean_abs_from_jan,

def make_normalized_event_log_view(
    df: pd.DataFrame,
    case_id_col: str = "case:concept:name",
    activity_col: str = "concept:name",
    timestamp_col: str = "time:timestamp",
    resource_col: str = "org:resource",
    normalized_activity_col: str = "concept:name_normalized"
) -> pd.DataFrame:
    """
    Return a normalized copy without overwriting the original event log.
    Mapping reflects the benchmark evidence: Eligibility Screen is the
    migrated label for Validate Eligibility. Duplicate technical Open Case
    events are removed conservatively within each case.
    """
    required = {case_id_col, activity_col, timestamp_col}
    missing = required - set(df.columns)
    if missing:
        raise ValueError(f"Missing required event-log columns: {sorted(missing)}")

    out = df.copy()
    out[timestamp_col] = pd.to_datetime(out[timestamp_col], errors="raise")
    out[normalized_activity_col] = out[activity_col].replace({
        "Eligibility Screen": "Validate Eligibility"
    })

    # Conservative removal of repeated technical Open Case events.
    # This does not remove the first Open Case, because some logs may use it legitimately.
    out = out.sort_values([case_id_col, timestamp_col, activity_col]).copy()
    duplicate_open = (
        out[normalized_activity_col].eq("Open Case")
        & out.duplicated(subset=[case_id_col, normalized_activity_col], keep="first")
    )
    out = out.loc[~duplicate_open].copy()

    return out


def format_for_pm4py(
    df: pd.DataFrame,
    case_id_col: str = "case:concept:name",
    activity_col: str = "concept:name",
    timestamp_col: str = "time:timestamp"
):
    """
    Format a dataframe for PM4Py. The caller may pass either the raw activity
    column or a normalized activity column; the original dataframe need not be
    overwritten.
    """
    import pm4py

    formatted = pm4py.format_dataframe(
        df.copy(),
        case_id=case_id_col,
        activity_key=activity_col,
        timestamp_key=timestamp_col
    )
    return formatted


def slice_time_window(

    end_time: str,

):
    """
    Slice a PM4Py-formatted dataframe/log to a time window.

    """

    return pm4py.filter_time_range(

def compute_monthly_dfgs(
    df: pd.DataFrame,
    case_id_col: str = "case:concept:name",
    activity_col: str = "concept:name",
    timestamp_col: str = "time:timestamp"
) -> dict:
    """
    Compute monthly DFGs. Returns a dictionary keyed by YYYY-MM.
    """
    import pm4py

    working = df.copy()
    working[timestamp_col] = pd.to_datetime(working[timestamp_col], errors="raise")
    results = {}

    for month_start, month_df in working.groupby(pd.Grouper(key=timestamp_col, freq="MS")):
        if month_df.empty:
            continue
        formatted = pm4py.format_dataframe(
            month_df.copy(),
            case_id=case_id_col,
            activity_key=activity_col,
            timestamp_key=timestamp_col
        )
        dfg, start_activities, end_activities = pm4py.discover_dfg(formatted)
        results[month_start.strftime("%Y-%m")] = {
            "dfg": dfg,
            "start_activities": start_activities,
            "end_activities": end_activities,
            "n_events": len(month_df),
            "n_cases": month_df[case_id_col].nunique()
        }

    return results

def compare_raw_and_normalized_views(
    df: pd.DataFrame,
    case_id_col: str = "case:concept:name",
    activity_col: str = "concept:name",
    timestamp_col: str = "time:timestamp"

## 9. Provisional attribution

The strongest conclusion is that the March conformance collapse is primarily a logging and semantic migration effect, not a business-process collapse. The evidence is unusually strong: raw fitness drops from about 0.925 to 0.55, while mapped fitness remains 0.90; the DFG fragment is nearly stable after mapping; distinct labels, duplicate technical events, and missing resources all move at the same time. I would assign high confidence, around 90–98%, to this attribution.

The second strongest conclusion is that May introduces real behavioral drift through supplier-driven rework. Supplier Z exposure rises sharply from 18% in April to 43% in May, rework variant share rises to 24%, and normalized `Assess -> Request Info` rises from 12 per 100 cases in March to 24 in May. Because Supplier Z serves a non-random subset and was already somewhat more complex, I would not assign all rework to Supplier Z. Still, the timing and signature justify high confidence, around 75–90%, that Supplier Z is a major cause.

Performance drift is best attributed to interacting rework, capacity, and queueing mechanisms. The May rework shock creates more assessment demand; the June assessor departures reduce capacity; the July priority rule likely redistributes waiting; and the October renewal season increases both volume and high-complexity share. The observation that `Assess` service time changes only modestly while reconstructed waiting before `Assess` increases much more makes queueing a stronger explanation than slower individual work. Confidence is high that queueing is central, but only medium for the exact split among staffing, priority, and backlog.

The seasonal attribution for October–November is also strong: volume and high-complexity share both jump, senior assessment becomes much more frequent, and p90 peaks. The weaker conclusion is whether October’s senior-assessment increase reflects real behavior, better recording, or both.

I would revise this account if event-level, stratified analyses showed that non-Supplier-Z standard-complexity cases had the same rework increase in May, that queue waiting did not change after the staffing cut, or that senior assessment in October was purely a relabeling artifact with unchanged resources, durations, and decision paths.

## 10. Monitoring decision rules

1. `IF raw conformance fitness drops sharply while mapped fitness stays near its reference range, THEN open a schema/semantic incident and freeze business attribution until raw-versus-normalized traces are compared, BECAUSE label migration and technical events can imitate control-flow drift.`

2. `IF mapped rework edges such as Assess -> Request Info and Request Info -> Collect Documents rise within Supplier Z cases and remain elevated after controlling for complexity, THEN trigger supplier document-quality remediation, BECAUSE incomplete bundles should produce exactly that loop signature.`

3. `IF median or p90 cycle time rises while Assess service time is stable but waiting before Assess increases, THEN diagnose capacity or queueing drift before retraining process models, BECAUSE the deterioration is occurring in the queue rather than in task execution.`

4. `IF standard-priority cases wait longer after July while high-complexity cases wait less or no longer, THEN review the priority rule and reserve capacity for standard cases, BECAUSE priority policies can improve one class by displacing delay to another.`

5. `IF October–November volume and high-complexity share exceed non-seasonal baselines but resemble historical renewal seasons, THEN apply seasonal reference bands rather than classifying the pattern as novel drift, BECAUSE recurring population drift should not be monitored with ordinary-month thresholds.`

6. `IF missing resource identifiers exceed the migration-era tolerance or concentrate in specific activities, teams, or source systems, THEN suppress or qualify handover, workload, and fairness conclusions for those strata, BECAUSE non-random missingness biases organizational mining.`

7. `IF December-style improvement coincides with both lower load and an intervention, THEN evaluate the intervention with stratified or difference-in-differences comparisons before declaring success, BECAUSE lower seasonal pressure, supplier recovery, overtime, and document-quality actions are mediated and confounded.`
