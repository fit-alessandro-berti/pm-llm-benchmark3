## 1. Equivalence design space

### 1.1 Activity-sequence equivalence

**Definition.** Let `E` be an execution as an ordered list of events. Define the projection

`L(E) = [activity(e1), activity(e2), ..., activity(en)]`.

Two executions are activity-sequence equivalent iff `L(E1) = L(E2)`.

**Invariants preserved.** Activity labels and their temporal order; counts of each activity label.

**Information discarded.** All object types, object identities, external flags, event-object incidence, and O2O relations. This is a purely control-flow notion and is not truly object-centric.

**Properties.** Equality of strings is reflexive, symmetric, and transitive, so this is an equivalence relation.

**Concurrency.** If two events have the same timestamp, the relationship is not a total order. In that case the definition should be modified to compare, for each timestamp, a multiset of activity labels, or compare the Hasse diagram of the activity partial order instead of a linear sequence.

---

### 1.2 Typed structural equivalence under identifier renaming

**Definition.** Build a labeled graph `G(E)` for an execution:

- event nodes, one per event position, labeled by activity;
- object nodes, labeled by object type and by whether the object is local or external (`EXT`);
- incidence edges between an event node and each object node referenced by that event;
- optionally, O2O relation edges between object nodes, labeled by the qualifier, if O2O notes are to be included.

Two executions are typed-structurally equivalent iff there is a bijection between their object-node sets that preserves object type, external flag, and all incidence edges, while event labels and event order are preserved.

**Invariants preserved.** Event order, activity labels, object types, local/external distinction, event-object incidence, and, in the full version, O2O qualifiers.

**Information discarded.** Raw local object identifiers. The actual names `I11` and `I22` are not meaningful unless they carry an explicitly supplied semantic distinction.

**Properties.** Graph isomorphism is reflexive, symmetric, and transitive, so this is an equivalence relation.

**Concurrency.** If events are unordered at the same time, the event node set becomes a partially ordered set rather than a sequence. The isomorphism must then preserve the partial order, not a chosen linear extension.

---

### 1.3 Business-semantic equivalence

**Definition.** Two executions are business-semantically equivalent iff they have the same canonical semantic signature. The signature is defined in Section 2. It combines:

- event order and activity labels;
- per-event object-type multiplicities, including external-object counts;
- overall typed object multiplicity counts;
- O2O qualifier counts by source type, target type, and qualifier.

**Invariants preserved.** The shape of the fulfillment process: how many packages are created, how many shipment legs occur, whether invoicing and payment are shared with external orders, whether items are replaced or returned, and whether payment is split.

**Information discarded.** Exact object identities, exact object-to-object identity links beyond type-level counts, and non-semantic attribute values.

**Properties.** Equality of computed signatures is reflexive, symmetric, and transitive.

**Concurrency.** The signature uses the observed total order. If the true process is a partial order, the signature should be computed from the partial-order representation, treating independent concurrent events as unordered.

---

### 1.4 Optional fourth relation: local lead-object equivalence

One additional defensible equivalence ignores external objects entirely:

**Definition.** Remove all `EXT` object references from the event log, then apply typed structural equivalence or business-semantic equivalence to the remaining local execution.

Under this relation, X5 and X6 collapse into the same cluster as X1 and X2, because their local order lifecycle looks like a normal single-order execution. This is useful when the analysis is explicitly scoped to one order owner and intentionally ignores shared logistics or shared finance.

## 2. Canonical signatures

The preferred equivalence in this answer uses the following canonical semantic signature. The Python-like code below is invariant to local identifier renaming but preserves object types, multiplicities, external flags, event order, per-event incidence counts, and O2O qualifiers.

```python
from collections import Counter

def canonical_event_frame(event):
    """
    event.object_refs: list of (role, obj_type, is_external)
    A frame records, for each activity, counts of object references
    grouped by (role, type, external flag).
    """
    counts = Counter()
    for role, obj_type, is_external in event.object_refs:
        counts[(role, obj_type, is_external)] += 1
    return (event.activity, tuple(sorted(counts.items())))

def canonical_semantic_signature(execution):
    """
    execution.events_sorted_by_time: ordered event list.
    execution.objects: all objects in the execution.
    execution.o2o_relations: (source_type, source_ext, qualifier,
                              target_type, target_ext)
    """

    event_frames = []
    for ev in execution.events_sorted_by_time:
        event_frames.append(canonical_event_frame(ev))

    object_profile = Counter()
    for obj in execution.objects:
        object_profile[(obj.type, obj.is_external)] += 1

    o2o_profile = Counter()
    for rel in execution.o2o_relations:
        o2o_profile[(rel.source_type, rel.source_ext,
                     rel.qualifier,
                     rel.target_type, rel.target_ext)] += 1

    return (
        tuple(event_frames),
        tuple(sorted(object_profile.items())),
        tuple(sorted(o2o_profile.items()))
    )
```

This signature intentionally works at the typed-multiplicity level. It does not preserve the exact identity link between, say, a specific package and a specific delivery. For exact graph-level identity, typed structural equivalence in Section 1.2 is the better tool. For business segmentation, this signature is more stable and more meaningful.

## 4. Cluster interpretations

### S1 — Simple single-package fulfillment

**Signature.** One order, two items, one package, one delivery, one invoice, one payment. No external objects. No O2O qualifiers.

**Business behavior.** A standard order-to-cash process: all items are picked and packed together, shipped once, invoiced once, and paid once.

**Risks and opportunities.** Low operational risk. Opportunities include automation of a clean, straight-through process.

**Traditional flattening.** Flattening by order or by package works well here. Little information is lost.

**Stability.** Stable. If the number of items, packages, invoices, or payments changes, the signature changes.

---

### S2 — Split-package consolidated shipment

**Signature.** Two package events, each containing one item; one dispatch event containing both packages and one delivery; one invoice and one payment.

**Business behavior.** The order is physically split into two packages for size, weight, or inventory reasons, but both packages travel on the same delivery.

**Risks and opportunities.** Lower freight cost and better customer experience because one delivery arrives. However, if one package is lost or delayed, the whole order is incomplete. Consolidation may require waiting for both packages to be ready.

**Traditional flattening.** Flattening by order hides package-level granularity. Flattening by package splits one order into two unrelated cases and loses the consolidated delivery.

**Stability.** Stable under identifier renaming. If two Pack events are merged into one event with two packages, the event sequence changes but the business meaning remains the same; our signature would see a different cluster.

---

### S3 — Split shipments with split payment

**Signature.** Two packages, two separate deliveries, one invoice, and two payment events. The O2O notes describe one partial settlement and one completing settlement.

**Business behavior.** The order is fulfilled across two independent shipment legs. The customer pays the single invoice in two installments.

**Risks and opportunities.** Higher shipping cost, multiple delivery promises, and revenue-recognition complexity. The split payment creates credit and collections risk.

**Traditional flattening.** Flattening by delivery creates two separate cases and the invoice/payment may appear split across them. Flattening by order hides the fact that there are two deliveries.

**Stability.** Stable if two distinct payment events genuinely represent two cash receipts. If the two payments are actually a single payment recorded in two rows, the signature should be chosen differently.

---

### S4 — Cross-order logistics sharing

**Signature.** Activity labels match S1, but the Pack and Dispatch events reference an external order and an external item. The local order has one package, one delivery, one local invoice, and one local payment.

**Business behavior.** The package contains items belonging to more than one order. The local order is not the sole owner of the logistics execution.

**Risks and opportunities.** Potential cost sharing and shipment consolidation are opportunities. Risks include inventory ownership ambiguity, damage/loss allocation, and carrier liability disputes.

**Traditional flattening.** Flattening by the local order creates a package containing items that are not in that order. Flattening by package mixes orders and may duplicate events across cases.

**Stability.** Stable as long as external-object flags are preserved. If external references are stripped, S4 collapses into S1.

---

### S5 — Cross-order invoicing and payment

**Signature.** Local logistics are identical to S1, but the Invoice and Payment events reference an external order. The O2O relation says one invoice bills both the local order and the external order.

**Business behavior.** Billing is centralized or shared across orders. Payment is received at a level above the individual order.

**Risks and opportunities.** Shared invoicing can reduce administrative cost. Risks include revenue misattribution, tax/invoice compliance issues, and difficulty allocating cash to specific orders.

**Traditional flattening.** Flattening by order double-counts the shared invoice/payment. Flattening by invoice aggregates orders and loses the local order view.

**Stability.** Stable if external object references are preserved. If external references are ignored, S5 collapses into S1.

---

### S6 — Replacement/removal before dispatch

**Signature.** The activity sequence looks like S1, but the Dispatch event references an item, and the O2O qualifiers record `removed_before_dispatch` and `replaces`.

**Business behavior.** An item was originally packed but replaced or removed before the package was dispatched. The final dispatched package contains the replacement item rather than the originally added set.

**Risks and opportunities.** High risk of customer surprise, wrong-item claims, and pick/pack errors. A clear qualifier is essential for quality control and root-cause analysis.

**Traditional flattening.** Flattening by activity labels alone makes this execution look exactly like a normal order. This is a dangerous misrepresentation.

**Stability.** Stable if O2O qualifiers are retained. If qualifiers and the dispatch-item incidence are discarded, S6 merges with S1 in a purely label-based view.

---

### S7 — Return, inspect, repack, and reshipment

**Signature.** The execution contains an initial pack and dispatch, then a Return Item event, an Inspect Return event, a second Pack event, and a second Dispatch event. One invoice and one payment occur after the reverse-logistics cycle.

**Business behavior.** An item was delivered, returned, inspected, repacked, and dispatched again. The order lifecycle includes a reverse-logistics loop.

**Risks and opportunities.** Return reason analysis, quality inspection, and inventory restocking are important. Risks include duplicate shipping costs, damaged returned goods, and unclear ownership during the return leg.

**Traditional flattening.** Flattening by order shows extra activities but loses per-item lifecycle states. Flattening by delivery creates two unrelated shipping cases.

**Stability.** Stable if the Return and Inspect events are preserved. If they are collapsed or removed, the cluster changes.

---

## 5. Borderline cases

### X1 versus X2

Activity-sequence equivalence and typed structural equivalence agree: X1 and X2 are equivalent. The only differences are raw local identifiers and the order in which the two identical Add Item events appear.

A defensible disagreement would arise if local identifiers were treated as meaningful product codes or if the first Add Item event were interpreted as the “primary” item. Under the stated constraints, identifiers are not meaningful, so there is no reason to separate X1 and X2.

### X1 versus X5

Activity-sequence equivalence groups them together. A business-semantic view that focuses only on the local order may also group them, because O5 still has one package, one delivery, one invoice, and one payment.

Typed structural equivalence and the preferred semantic signature separate them because X5 introduces external order and item objects in the logistics events. This is a real business difference: the local order is not isolated in the physical supply chain.

### X1 versus X6

The same comparison applies on the financial side. Activity sequence is identical. A logistics-only analysis would group them. Typed structural equivalence and financial business semantics separate them because X6 shares an invoice and payment with an external order.

### X1 versus X7

Again, the activity sequence is identical. If the analysis only looks at activity labels, X7 appears normal.

Typed structural equivalence separates X7 because the Dispatch event carries an Item reference. The preferred semantic signature additionally captures the O2O qualifiers `removed_before_dispatch` and `replaces`. This is an important borderline case: a label-only equivalence would hide a real substitution/removal event.

### X3 versus X4

Both executions contain one order, two items, two packages, and one invoice. If the analysis only asks “was the order fulfilled and paid?”, X3 and X4 are similar.

Activity-sequence equivalence, typed structural equivalence, and the preferred semantic signature separate them. X3 has one consolidated delivery and one payment; X4 has two independent deliveries and two payments. The operational risk profile differs significantly.

### X4 versus X8

Both executions have two package events and two delivery events. A very coarse equivalence that counts only shipment legs and one invoice would place them in the same cluster.

The preferred semantic signature separates them because X8 contains Return Item and Inspect Return activities, whereas X4 is a forward split shipment. The business semantics are different: X4 is outbound fulfillment; X8 is outbound plus reverse logistics and reshipment.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py function `cluster_equivalent_ocel` builds a canonical key for each execution centered on a lead object type. The key structure preserves:

- activity labels and event order;
- object types;
- event-object incidence;
- object multiplicity within events;
- the local/external distinction through external object references;
- O2O relations when they are represented in the OCEL.

The function removes the dependence on raw local object identifiers by canonicalizing them, usually by replacing identifiers with positional or structural placeholders. This is why X1 and X2 can be considered equivalent even though their object identifiers differ.

Raw object identifiers make exact clusters too fine because identifiers such as customer IDs, product SKUs, package barcodes, and invoice numbers are not process-behavioral information. Keeping them in the key would split every normal execution into its own cluster.

To obtain coarser business clusters, post-process the PM4Py clusters with a custom canonicalization step:

```python
from collections import defaultdict
import pm4py

ocel = pm4py.read_ocel("ocel.jsonocel")

raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    lead_object_type="Order",
    max_objs=1000,
)

semantic_clusters = defaultdict(list)

for _, member_execution_ids in raw_clusters.items():
    for exec_id in member_execution_ids:
        sig = canonical_semantic_signature(ocel, exec_id)
        semantic_clusters[sig].append(exec_id)

for cluster_number, (sig, ids) in enumerate(semantic_clusters.items(), 1):
    print(cluster_number, len(ids), sig)
```

Exact equivalence is preferable when compliance, audit, or process discovery requires the precise sequence of events and object interactions. It is less useful for descriptive reporting, because it creates too many small clusters.

`max_objs` is important for practical use. A connected execution can become large when multiple orders share packages or invoices, as in X5 and X6. If `max_objs` is too small, large executions may be truncated or excluded, producing incomplete clusters. If it is too large, memory and runtime can grow quickly.

## 7. Robustness analysis

### Ignore all O2O qualifiers

If O2O qualifiers are ignored:

- S4 and S5 remain distinct because external objects are still present in event frames.
- X7 loses `removed_before_dispatch` and `replaces`, but the Dispatch event still contains an Item reference; it does not fully merge into S1 unless the dispatch-item incidence is also ignored.
- X4 loses the partial/complete settlement labels, but the two Record Payment events remain.

Ignoring qualifiers makes X7 less clearly distinct and weakens the semantic meaning of X4.

### Ignore external objects

If all external objects are removed:

- X5 loses the external order and external item in Pack and Dispatch, so its local signature becomes identical to S1.
- X6 loses the external order in Invoice and Payment, so it also becomes identical to S1.

This corresponds to the local lead-object equivalence defined in Section 1.4. It is useful for a local-order view but hides shared logistics and shared finance.

### Collapse repeated same-label events

If only consecutive same-label events are collapsed:

- X3 becomes one Pack event with two packages rather than two Pack events. It remains distinct from S1 because the package multiplicity is two.
- X4 becomes one Record Payment event with two payment object references, but the interleaved Pack-Dispatch-Pack-Dispatch structure remains.

If all repeated same-label events are collapsed globally, X4 becomes `Create, Add, Add, Pack, Dispatch, Invoice, Payment`, but its object multiplicities still distinguish it from S1. The business semantics are preserved only if multiplicities are retained.

### Treat Pack and Dispatch order as a partial order

If Pack and Dispatch events are compared as a partial order rather than a total order, X4’s two independent pack-dispatch chains may commute. X3 still has one Dispatch event carrying two packages, while X4 has two Dispatch events, so they remain distinct. If dispatch consolidation is ignored, X3 and X4 become more similar.

### Treat payment multiplicity as an amount attribute

If the two payments in X4 are seen as one total payment amount split into two transactions, X4 becomes financially equivalent to X3’s single payment. However, X4 still has two deliveries, so it remains distinct from X3 unless delivery structure is also ignored.

## 8. Limitations and recommendation

No single equivalence notion is best for all purposes.

- **Compliance monitoring:** Use typed structural equivalence with O2O qualifiers and external flags. Compliance often needs exact objects, exact order, and exact shared relationships.
- **Operational segmentation:** Use the preferred business-semantic clusters S1–S7. They highlight differences in package count, delivery count, payment structure, external sharing, and reverse logistics.
- **Root-cause analysis:** Use exact typed structural equivalence, and do not aggregate away object identities. A failure involving a specific package, item, or delivery needs object-level traceability.
- **Descriptive reporting:** Use activity-sequence equivalence or even coarser business summaries. Reports generally need volume, frequency, and trend information, not exact object graphs.

The main limitation of any single equivalence is that it discards information useful for another purpose. Activity-sequence equivalence is too coarse for object-centric questions. Typed structural equivalence is often too fine for operational segmentation. The business-semantic signature is useful for segmentation but cannot answer a compliance question such as “which package carried the returned item?” Therefore, the right approach is to compute multiple equivalence layers and choose the appropriate layer for each use case.
