## 2. Process-Model Consistency Checks

### **Validation Suite Design**
1. **Prefix-Time Availability Checks**
   - **Alignment Check**: For each feature, verify it is computed from events with `timestamp  t0`. Use a declarative rule:
     ```sql
     SELECT feature_name
     FROM features
     WHERE EXISTS (
       SELECT 1 FROM feature_lineage
       WHERE event_timestamp > t0
     );
     ```
   - **Lineage Timestamp Audit**: Ensure all features have explicit `feature_timestamp` fields (or derive them from event timestamps).

2. **Activity-Order Feasibility**
   - **DFG Validation**: Build a dynamic workflow graph (DFG) from the normative process. For each observed trace prefix, check:
     - **Enabled Activities**: Only activities allowed by the current state (e.g., `Documents Requested` can only follow `Coverage Check Completed` if not in fast-track).
     - **Impossible Transitions**: Flag traces where `Damage Assessment Completed` precedes `Documents Requested` (violates normative order).
   - **Tool**: Use a prefix-DFG library (e.g., [PyWorkflows](https://github.com/awslabs/pyworkflows)) to simulate state transitions.

3. **Same-Timestamp Ambiguity**
   - **Sequence Index Check**: For events with identical timestamps, verify the presence of a reliable `sequence_index` field. If missing:
     ```python
     def is_order_ambiguous(events):
         return len(events) > 1 and all(
             e['timestamp'] == events[0]['timestamp'] for e in events[1:]
         ) and 'sequence_index' not in events[0]
     ```
   - **Remediation**: Assign sequence indices during ingestion or drop ambiguous events.

4. **Complete-Trace Detection**
   - **Feature Scope Audit**: For each feature, check if it depends on:
     - Future events (e.g., `appeal_seen_anywhere`).
     - Aggregations over the entire trace (e.g., `num_document_requests_total`).
   - **Rule**: Features must be computable from the prefix up to `t0`.

5. **Semantic Legitimacy of Repeated Events**
   - **Appeal Handling**: After `Partial`/`Deny`, allow a `Settlement Decision Recorded` event only if it follows an `Appeal` event. Flag traces where:
     ```sql
     SELECT *
     FROM traces
     WHERE EXISTS (
       SELECT 1 FROM events e1, events e2
       WHERE e1.event_type = 'Settlement Decision Recorded'
         AND e2.event_type = 'Appeal'
         AND e1.timestamp > e2.timestamp
         AND NOT EXISTS (
           SELECT 1 FROM events e3
           WHERE e3.event_type = 'Appeal'
             AND e3.timestamp BETWEEN e2.timestamp AND e1.timestamp
         )
     );
     ```

6. **Footprint Checks**
   - **Process Conformance**: Ensure no feature uses data from outside the claim’s footprint (e.g., cross-claim statistics).

---
**Limitations**:
- DFG checks assume the normative process is complete (e.g., may miss unmodeled exceptions).
- Lineage timestamps must be stored explicitly (not inferred).

## 5. Recommendations for Explanation Validation

### **Prioritized Plan**
1. **Feature-Store Design**
   - **Action**: Enforce explicit `feature_timestamp` for all features.
   - **Tool**: Use a feature store with lineage tracking (e.g., Feast, Tecton).
   - **Metric**: 100% of top-12 features must have `feature_timestamp  t0`.

2. **Historical Feature Timestamps**
   - **Action**: Audit all features for post-`t0` contamination. For each:
     - Replace `total_case_duration_hours` with `elapsed_since_registration_at_t0`.
     - Fix `prior_claim_count_before_t0` SQL to use `< t0`.
   - **Tool**: Write a validation query to flag features with `feature_timestamp > t0`.

3. **Prefix-Only Recomputation**
   - **Action**: Retrain the model using only prefix-available features (e.g., `documents_received_before_t0`, `appeal_triggered_at_t0`).
   - **Metric**: Compare SHAP values before/after; target <5% drop in AUC.

4. **Process-Conformance Tests**
   - **Action**: Implement the validation suite from Section 2 as part of the CI/CD pipeline.
   - **Tools**:
     - **Prefix Checks**: Use [PyWorkflows](https://github.com/awslabs/pyworkflows) for DFG validation.
     - **Lineage Checks**: Custom SQL queries to audit feature timestamps.
   - **Metric**: 0 critical failures in production traces.

5. **Calibration After Feature Removal**
   - **Action**: Recalibrate the model after removing leaked features. Use:
     - **Stability Check**: Ensure SHAP values for retained features (e.g., `elapsed_since_registration`) remain stable.
     - **Fairness Check**: Re-audit `claimant_region` for bias after feature removal.

6. **Explanation Stability**
   - **Action**: Monitor SHAP value drift for retained features (e.g., `queue_length_at_t0`). Set alerts for >10% change.
   - **Tool**: Use [SHAP Explainer](https://github.com/slundberg/shap) with drift detection.

7. **Proxy/Fairness Analysis**
   - **Action**: For proxies like `claimant_region`:
     - **Decomposition**: Use counterfactual analysis to isolate socioeconomic effects.
     - **Mitigation**: Replace with process-irrelevant features (e.g., `repair_network_coverage_score`).
   - **Tool**: [AIF360](https://aif360.mybluemix.net/) for fairness metrics.

8. **Monitoring for Schema/Process Drift**
   - **Action**: Track:
     - **Schema Drift**: New event types or missing timestamps.
     - **Process Drift**: Changes in activity frequencies (e.g., more appeals).
   - **Tool**: [River](https://river-apache.github.io/) for concept drift detection.
   - **Metric**: Alert on >15% change in event distribution.

---
**Key Trade-offs**:
- **Predictive vs. Causal**: Retain predictive signals (e.g., `queue_length`) but avoid causal claims.
- **Fairness vs. Utility**: Replace biased proxies (e.g., `claimant_region`) with process-irrelevant features.
- **Stability vs. Accuracy**: Prefix-only recomputation may reduce AUC but ensures temporal validity.
