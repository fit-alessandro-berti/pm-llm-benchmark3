# 2. Assignment policy

## 2.1 High-level design

The policy is a **scored rule-based engine** with three phases:

1. **Phase A — Eligibility filter** removes resources that violate hard constraints.
2. **Phase B — Multi-criteria score** ranks remaining resources; scores are normalized to 0–1.
3. **Phase C — Apply hard rules again** (continuity override, overtime cap, cap of 4 new assignments), then assign.

The score is explainable: each component has a published formula and a verbal reason. Workers can ask "why did I get this case?" and the system produces the component-by-component breakdown.

## 2.2 Pseudocode

```python
def assign_case(case, resources, history, batch_assignments):
    # ===== PHASE A: ELIGIBILITY =====
    eligible = []
    for r in resources:
        if r.skill[case.required_skill] == 0:                       # H1
            continue
        if case.priority in ("urgent", "high") and r.skill[case.required_skill] < 2:
            if not feasible_supervision(case, r):                    # H2
                continue
        if case.next_activity == "Security Review":
            if r.skill["Security"] < 3 and r.id not in ("R7_Gita","R8_Hugo"):
                continue                                             # H3
        if case.next_activity == "Final Approval" and r.skill["Approval"] < 2:
            continue                                                 # H4
        if case.next_activity == "Quality Check" and case.priority in ("urgent","high"):
            # H5: only normal/low batched; for these priorities no batching
            pass
        if r.overtime_risk == "high" and case.sla_remaining_h > 12:
            # H8: avoid adding to high-OT unless urgent
            continue
        if batch_assignments.count(r) >= 4:                          # H7
            continue
        eligible.append(r)

    if not eligible:
        return escalate_to_supervisor(case, reason="no eligible resource")

    # ===== PHASE B: SCORING =====
    scores = {}
    for r in eligible:
        s_sla    = sla_urgency_score(case)        # 0..1, higher = more urgent
        s_skill  = skill_match_score(case, r)     # 0..1
        s_cont   = continuity_score(case, r)      # 0..1
        s_work   = workload_score(r)              # 0..1 (lower load => higher score)
        s_ot     = overtime_penalty(r)            # 0..1 discount
        s_train  = training_score(case, r)        # 0..1
        s_resil  = resilience_score(case, r, batch_assignments)  # 0..1
        s_conti  = handover_cost_score(case, r)   # 0..1 (lower cost => higher score)

        total = ( 0.25 * s_sla
                + 0.20 * s_skill
                + 0.15 * s_cont
                + 0.10 * s_work
                - 0.10 * s_ot
                + 0.10 * s_train
                + 0.10 * s_resil
                + 0.10 * s_conti )
        scores[r] = total

    # ===== PHASE C: HARD-RULE OVERRIDES =====
    # H6: high complexity + high handover cost -> keep owner if owner is eligible
    if case.complexity >= 0.70 and case.handover_cost_band == "high":
        if case.current_owner in eligible and case.current_owner.skill[case.required_skill] >= 2:
            return case.current_owner

    # Tie-breaking: prefer lower current cases, then lower overtime risk, then training match
    best = max(scores, key=lambda r: (scores[r], -r.open_cases, -r.overtime_risk_rank, s_train))
    return best
```

## 2.3 Component formulas (published to workers)

```
sla_urgency(case) = clamp( (24 - case.sla_remaining_h) / 24, 0, 1 )
                    # 0 when SLA > 24h, 1 when already breached

skill_match(case,r) = r.skill[case.required_skill] / 3
                    # 0.33 trainee, 0.67 competent, 1.0 specialist

continuity(case,r) = 1.0 if r == case.current_owner else 0.0
                    # bumped down to 0.5 if r.team != case.current_owner.team

workload(r)        = 1 - clamp(r.open_cases / 15, 0, 1)

overtime_penalty(r) = {low:0.0, medium:0.3, high:0.7}[r.overtime_risk]

training(case,r)   = 1.0 if case.required_skill == r.training_priority
                     else 0.5 if r.skill[case.required_skill] >= 2
                     else 0.0
                    # bonus only when SLA buffer > 12h

resilience(case,r,batch) = 1 - min(1, count_skill3_in_batch(batch, r) / 2)
                    # avoid stacking specialist-required cases on same resource

handover_cost(case,r) = {low:1.0, medium:0.6, high:0.2, none:1.0}[case.handover_cost_band]
                    # only used when r != current_owner
```

# 4. Comparison with baseline policies

The comparison below is **structural**, not empirical — without an event log we cannot give precise numbers, but the relative trade-offs are well-defined.

| Dimension | First-available | Specialist-only | Proposed dynamic policy |
|---|---|---|---|
| **Expected throughput (now)** | Highest — minimal idle time | Lowest — specialists become bottlenecks | Middle — specialists for SLA + urgent, competent for routine |
| **SLA risk (urgent cases)** | High — skill-1 resources may take complex work | Lowest — best skills always used | Low — specialist routed, with supervised fallback |
| **SLA risk (routine)** | Lower waiting but higher rework later | Similar waiting to first-available, better rework | Balanced — continuity + skill match |
| **Error / rework risk** | High — skill mismatch is the main failure mode | Lowest on paper; in practice, specialist queue saturation increases wait-induced errors | Medium-low — competent workers handle routine, specialists handle risky work |
| **Workload fairness** | Naturally fairer on count, but ignores team/skill mix | Worst — R6_Farid, R7/R8, R3/R4 get overloaded | Balanced — explicit workload + overtime scoring |
| **Skill development** | Worst — trainees never get stretch work | Worst — specialists handle everything; juniors are idle | Best of the three — explicit training component, supervised when SLA allows |
| **Continuity of ownership** | Poor — every free slot takes next case | Mixed — picks by skill, not by ownership | Best — continuity is scored and overridden only by H-rules |
| **Resilience to absence** | Best — many resources touch each activity | Worst — single points of failure (R7/R8 for Security, R6 for Approval) | Middle — distributes specialist work, monitors bottleneck resources |
| **Explainability to workers** | Easy ("you were free") | Easy ("you scored highest on this skill") | High — full breakdown is published |
| **Auditability** | Weak — no rule to deviate from | Strong — clear rule | Strong — deviations are explicit and recorded |

**Headline trade-offs:**

- *First-available* wins on raw throughput but loses on rework and skill development. Given the historical finding that >2 reassignments cause 1.8× rework and 1.4× appeals, and that low-skill work on complex cases adds 3.3h of service time, this policy quietly transfers throughput from now to rework later.
- *Specialist-only* wins on error rate today but creates a queue on R6_Farid (3 specialist-eligible cases: C002, C010, C011 — all Approval or Negotiation). With 5 open cases and 6.5h, R6 can absorb the batch, but the policy would scale poorly: R7_Gita and R8_Hugo would be the only Security options for 4 cases (C001, C008, C015, plus future), and they have 4.5h and 5.5h free respectively.
- *Proposed* is a deliberate compromise: it routes urgent/complex work to specialists (preserving first-available's worst pain point), uses continuity to avoid paying handover cost (specialist-only's blind spot), and reserves trainee-supervised stretches for low-SLA-risk cases (both baselines ignore this).

**There is no single optimum.** The right policy depends on what the organization is optimizing for: pure throughput  first-available; pure quality  specialist-only; sustainable, explainable service  the proposed policy.

# 5. Explanation to workers

> **How we decide who gets which case**
>
> The system does not pick favorites and it does not pick on anyone. Every assignment is the result of a small set of rules that the same rules apply to everyone, every day. Here is what we look at, in plain language:
>
> 1. **Can you do the work safely?** If the case is sensitive (Security, Approval) and the urgency is high, we route to a specialist. If no specialist is free, we pair you with a supervisor. We will never put a trainee in front of a high-risk case alone.
> 2. **Is the clock ticking?** If the customer is waiting, that case jumps up the list. We protect SLAs first because they are promises we made.
> 3. **Are you already on the case?** We try hard to keep the same person on the same case. Every handover is a small risk — context gets lost, the customer has to repeat themselves, the error rate goes up. So unless there is a real reason to move a case, we don't.
> 4. **How full is your plate?** We track how many open cases you have and how much time you have left today. We try to spread the work so nobody burns out. We also avoid piling more work onto people who are already close to overtime.
> 5. **Will this help you grow?** If you have told us you want to develop a particular skill, and the case is not too urgent, we may give it to you with a senior on standby. That's how you become the specialist for the next round.
> 6. **Are we putting too much specialist work on one person?** If so, we share it. We don't want to be one sick-day away from a queue.
>
> **If you got a case and it does not feel right**, ask your team lead. The system records *why* it chose you, with a breakdown by rule. If the reason looks wrong, that is a bug or a missing fact — and we want to fix it. If you think *you* would be a better owner for a case, the system supports a re-route request; it does not get held against you.
>
> We are not trying to replace your judgment. The policy is a starting point, not a verdict. Your professional view overrides the score when the two disagree, and the override is itself logged so we can learn from it.

- `discover_performance_dfg` with `performance="waiting_time"` produces a DFG colored by the median handover cost — directly visualizing the "expensive transitions" the policy tries to avoid.

### Closing loop

Each batch's assignments are written back to the event log with `assignment_reason` = the top 2 scoring components and `risk_to_monitor` = the largest risk dimension. At the end of the week, the audit script recomputes indicators 1–14, the team reviews deviations, and the policy is updated in version control. This makes the policy **auditable by construction**: every decision is replayable against the same log it produces.
