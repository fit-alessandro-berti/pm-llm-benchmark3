## 6. Revised Normative Architecture

The architecture separates concerns into five layers. No single POWL can enforce all of them.

**L1 — Base Control-Flow (POWL)**
A family of partial-order sub-models representing the physical sequence of activities: concurrent checks, linear approvals, activation, notification, closure, and a loop approximation for Request_More_Info. This layer answers “what activities occur and in what order?”

**L2 — Policy-Overlay Governance (Table/Rule Engine)**
A normalized, versioned table that selects which L1 branch is active for a given case. Columns include: `rule_version` (CS-9, PD-3, FD-7, future amendment), `effective_from/to`, `case_type` (new, reactivation, rejected lead), `risk_level`, `corporate_group_approved`, `pilot_eligible`, `emergency_declared`, `spend_cap`, `approval_type` (manual/auto/retrospective), `quality_timing` (pre/post/provisional), `notification_service_version`, and `authority_document_id`. This layer answers “which policy overlay applies, and is it in force?”

**L3 — Data-Aware Eligibility and Constraint Checks (Pandas / SQL / DECLARE-style)**
Quantitative and categorical rules enforced against event data and case attributes: risk classification, group membership snapshots, spend caps (e.g., EUR 20,000), date-window checks (pilot/emergency expiry), actor identity (canonical IDs, not aliases), and notification stability (`notification_id` must be immutable foreign key, not mutable text). This layer answers “do the case attributes satisfy the selected overlay?”

**L4 — Resource, Conflict, and Organizational Controls (Organizational / DECLARE Log-Skeleton)**
Constraints outside pure control flow: separation of duties (requester  approver, resolved via canonical identity, not aliases), conflict-of-interest disclosure (spousal relationships, reporting lines), delegation evidence, and audit trails for ontology changes (label mappings). These can be expressed as DECLARE/log-skeleton constraints (e.g., `AtMostOne` on approval roles per canonical identity; `NotCoExistence` of undisclosed conflicts) or as organizational-sign-off workflows.

**L5 — Scope and Version Rules**
Explicit scope definitions:
- **New onboarding:** full L1 standard/pilot/emergency/rejected paths.
- **Reactivation:** distinct sub-model (not M0); prior quality certification validity must be verified in L3.
- **Rejected pre-screen:** abbreviated path (sanctions  reject  notify  close) allowed only if `scope_flag = rejected_lead` and no activation occurs; quality review is not required.
- **Withdrawal/Abandoned:** explicit silent exit path.
- **Event ontology versions:** `label_version` and `service_version` (e.g., Quality_Review v1 vs QA_Clearance v2) with approved mapping tables.

**What belongs where**
- **POWL:** activity ordering, concurrency, branch selection structure, loop approximation.
- **Policy-overlay table / rule engine:** which branch is authorized, for how long, under what conditions.
- **Pandas / data checks:** eligibility snapshots, amount caps, date arithmetic, canonical identity resolution, notification ID stability.
- **Organizational controls / DECLARE:** resource separation, conflict disclosure, delegation, audit of ontology changes.
- **Event-log design:** immutable timestamps, foreign-key notification links, version IDs, eligibility snapshots at case start, actor aliases resolved to canonical IDs.

## 7. PM4Py Model and Data Proposal

**Limitation statement:** POWL expresses control-flow structure well but cannot natively enforce quantity caps, risk classifications, date windows, canonical identity separation, or dynamic policy selection. The revised model below therefore includes the structural routes (standard concurrent checks, manual approval, auto-approval pilot, emergency provisional, rejected pre-screen, notification-before-close, and a loop approximation). All eligibility, amount, time, identity, and authority conditions must be enforced by the policy-overlay table and data checks that accompany the code.

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# ------------------------------------------------------------------
# Transitions
# ------------------------------------------------------------------
register        = Transition(label="Register_Supplier")
request_info    = Transition(label="Request_More_Info")
sanctions       = Transition(label="Sanctions_Check")
quality         = Transition(label="Quality_Review")
manual_approval = Transition(label="Manual_Procurement_Approval")
activate        = Transition(label="Activate_Supplier")
auto_approve    = Transition(label="Auto_Approve")
retrospective   = Transition(label="Retrospective_Approval")
reject          = Transition(label="Reject_Supplier")
notify          = Transition(label="Notify_Requester")
close_case      = Transition(label="Close_Case")

# ------------------------------------------------------------------
# L1 Pre-phase: Register -> Request_More_Info (repetition approximated)
# Note: True repetition requires event-level counting (L3 data rules).
# ------------------------------------------------------------------
pre_nodes = [register, request_info]
pre = StrictPartialOrder(nodes=pre_nodes)
pre.order.add_edge(register, request_info)

# ------------------------------------------------------------------
# L1 Sub-models for concurrent checks and branch internals
# ------------------------------------------------------------------
# Standard concurrent checks (Sanctions || Quality)
checks = StrictPartialOrder(nodes=[sanctions, quality])
# No ordering edge between sanctions and quality => concurrent.

# Standard approved branch: checks -> manual -> activate
std_approval = StrictPartialOrder(nodes=[manual_approval, activate])
std_approval.order.add_edge(manual_approval, activate)

# Pilot branch internal: sanctions -> auto -> activate
pilot_approval = StrictPartialOrder(nodes=[auto_approve, activate])
pilot_approval.order.add_edge(auto_approve, activate)

# ------------------------------------------------------------------
# L1 Full branch paths (each ends with notify then close, in correct order)
# ------------------------------------------------------------------
# Standard: checks -> approval -> notify -> close
std_nodes = [checks, std_approval, notify, close_case]
std = StrictPartialOrder(nodes=std_nodes)
std.order.add_edge(checks, std_approval)
std.order.add_edge(std_approval, notify)
std.order.add_edge(notify, close_case)

# Pilot: sanctions (with implicit validation) -> auto/activate -> notify -> quality (retrospective) -> close
# We use a nested partial order for the retrospective tail.
pilot_tail = StrictPartialOrder(nodes=[notify, quality, close_case])
pilot_tail.order.add_edge(notify, quality)
pilot_tail.order.add_edge(quality, close_case)

pilot_nodes = [sanctions, pilot_approval, pilot_tail]
pilot = StrictPartialOrder(nodes=pilot_nodes)
pilot.order.add_edge(sanctions, pilot_approval)
pilot.order.add_edge(pilot_approval, pilot_tail)

# Emergency / provisional: sanctions -> activate -> notify -> (quality || retrospective) -> close
emerg_post = StrictPartialOrder(nodes=[notify, quality, retrospective, close_case])
emerg_post.order.add_edge(notify, quality)
emerg_post.order.add_edge(notify, retrospective)
emerg_post.order.add_edge(quality, close_case)
emerg_post.order.add_edge(retrospective, close_case)

emerg_nodes = [sanctions, activate, emerg_post]
emerg = StrictPartialOrder(nodes=emerg_nodes)
emerg.order.add_edge(sanctions, activate)
emerg.order.add_edge(activate, emerg_post)

# Rejected / pre-screen: sanctions -> reject -> notify -> close
rej_nodes = [sanctions, reject, notify, close_case]
rej = StrictPartialOrder(nodes=rej_nodes)
rej.order.add_edge(sanctions, reject)
rej.order.add_edge(reject, notify)
rej.order.add_edge(notify, close_case)

# ------------------------------------------------------------------
# L1 Route selection (XOR) among standard, pilot, emergency, rejected
# ------------------------------------------------------------------
routes = [std, pilot, emerg, rej]
route_selector = OperatorPOWL(operator=Operator.XOR, children=routes)

# ------------------------------------------------------------------
# L1 Root: Pre-phase -> Route selection
# ------------------------------------------------------------------
root_nodes = [pre, route_selector]
root = StrictPartialOrder(nodes=root_nodes)
root.order.add_edge(pre, route_selector)

# The revised POWL model is `root`. It must be combined with L2-L5.
```

**Event / Data-Collection Proposal (L3–L5)**

| Data element | Requirement | Enforcement layer | Rationale |
|---|---|---|---|
| `event_id` | UUID per event; immutable | Log design | Prevents duplicate log corruption (SUP-711) |
| `source_transaction_id` | Stable reference; same for duplicates | Data check | Distinguishes logging duplicates from real repeats |
| `notification_id` | Immutable foreign key linking onboarding log to CRM; not mutable text | Data check / L4 | Fixes SUP-706; enables stable audit |
| `service_version` | CRM/onboarding version at event time | Log design | Explains label/service mismatches |
| `label_version` | Ontology version (e.g., Quality_Review v1, QA_Clearance v2) | Log design / L5 | Resolves SUP-713 via approved mapping table |
| `rule_version_id` + `authority_doc_id` | References active policy at case start | L2 table | Proves which overlay applies (PD-3, FD-7, CS-9) |
| `eligibility_snapshot` | Risk, group, country at `Register_Supplier` timestamp | L3 data check | Prevents ineligible pilot use (SUP-703) |
| `actor_canonical_id` + `alias_resolution_evidence` | Resolved human identity; delegation records linked | L4 organizational | Detects alias fraud (SUP-712) |
| `conflict_disclosure_flag` + `relationship_type` | Required disclosure for spousal/reporting-line conflicts; null if none | L4 organizational | Exposes hidden conflicts (SUP-715) |
| `request_info_cycle_count` + `evidence_received_flag` | Count of `Request_More_Info`; boolean that evidence arrived before next decision | L3 data check | Formalizes safe loop (SUP-707) |
| `activation_timestamp` + `sanctions_timestamp` + `quality_timestamp` | Source-system timestamps (not log-entry times) | L3 data check | Detects true sequence inversions (SUP-708) |
| `spend_amount` + `cap_remaining` | Real-time or retrospective spend tracking against `spend_cap_eur` | L3 data check | Enforces FD-7 cap (SUP-704, 705) |
| `emergency_extension_doc_id` | Required if emergency actions occur outside directive window | L2 table | Would resolve SUP-705 authority gap |
| `reactivation_flag` + `prior_cert_valid` | Explicit flag and validation for reactivations | L5 scope / L3 | Brings SUP-710 into scope |
| `scope_flag` | `full` / `abbreviated` / `reactivation` / `withdrawn` | L5 scope | Clarifies SUP-709 scope ambiguity |

**Implementation note:** The `root` POWL object should be instantiated in a conformance-checking pipeline that first applies L2 (select active branch by `rule_version` and `effective_to`), then L3 (validate eligibility, amounts, identity, timestamps), then L4 (check resource/conflict/delegation rules, possibly via DECLARE constraints over the event log), and finally compares the observed trace to the selected L1 path. If L3 or L4 rejects a case, the case is noncompliant regardless of L1 structural fit. If L1 does not contain an activity present in the log (e.g., `Request_More_Info` outside the approximate pre-phase), L3 cycle-count rules determine whether repetition is permitted. This layered separation prevents hiding organizational failures inside an inadequate control-flow model.
