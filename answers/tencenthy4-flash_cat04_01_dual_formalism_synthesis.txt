# 1. Assumptions and Interpretation

1. **Trace order is completion order.** A precedence edge `x -> y` means the completion/occurrence of `x` must precede the occurrence of `y`; activities not ordered may complete in either order.

2. **Low-risk/high-risk is represented as an XOR choice after Analyze Root Cause.** Because case data are not modeled, the choice is nondeterministic at the control-flow level:
   - low branch: `Supervisor Review`;
   - high branch: `Quality Review || Regulatory Review`.

3. **Supplier consultation is an optional XOR after Analyze Root Cause.** The model has a silent skip branch and one visible `Consult Supplier` branch. Selection depends on unrepresented data, so the model admits both alternatives nondeterministically and permits consultation at most once.

4. **Inspection outcome is abstracted by loop control flow, not by data.** `Execute Trial -> Inspect Trial` is the loop body. A failed inspection is represented by a silent failure transition followed by `Adjust Parameters`, after which the loop repeats. A passing inspection is represented by exiting the loop. Thus the final `Inspect Trial` is inferred to have passed because no subsequent `Adjust Parameters` occurs.

5. **Duplicate visible labels are not permitted.** Duplicating labels such as `Analyze Root Cause` as hidden synchronization checkpoints would create observable repeated activities and distort conformance. All visible labels occur exactly once in each model.

6. **The process tree uses a conservative under-approximation.** Exact non-block-structured synchronization is not expressible as a process tree without changing traces. I therefore exclude some legal interleavings—especially approval/trial overlap and supplier/trial overlap—rather than admit unsafe release behavior.

7. **“May overlap” is interpreted as true concurrency/absence of an order constraint where possible.** In the POWL this is represented by leaving nodes unordered in the `StrictPartialOrder`. In the process tree it is represented by `PARALLEL` only where the block structure permits it.

8. **The POWL is the more faithful representation.** It directly represents the release synchronization as separate incoming dependencies from the trial loop, selected approval route, and optional supplier route, while leaving those branches unordered with respect to trial execution.

# 3. PM4Py Process-Tree Model

Compact expression:

```text
->(
  Register Deviation,
  +(
    ->(Contain Material, Plan Verification),
    ->(
      Analyze Root Cause,
      +(
        Design Corrective Action,
        X(Supervisor Review, +(Quality Review, Regulatory Review)),
        X(tau, Consult Supplier)
      )
    )
  ),
  O(
    ->(Execute Trial, Inspect Trial),
    ->(tau, Adjust Parameters)
  ),
  Release Material,
  Archive Case
)
```

Here `->` is sequence, `+` is parallel, `X` is XOR, `O` is loop, and `tau` is silent. The first parallel node represents the two initial work streams. The nested parallel after `Analyze Root Cause` represents design, risk approval, and optional supplier work. The loop represents repeated `Execute Trial`–`Inspect Trial` cycles with a silent failure branch leading to `Adjust Parameters`.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label=None):
    # label=None is a silent tau leaf in PM4Py process trees.
    return ProcessTree(operator=None, label=label)

def operator_node(operator, *children):
    node = ProcessTree(operator=operator)
    # Explicit parent/child handling.
    for child in children:
        node.children.append(child)
        child.parent = node
    return node

# Leaves
register_deviation = leaf("Register Deviation")
contain_material = leaf("Contain Material")
analyze_root_cause = leaf("Analyze Root Cause")
plan_verification = leaf("Plan Verification")
design_corrective_action = leaf("Design Corrective Action")

supervisor_review = leaf("Supervisor Review")
quality_review = leaf("Quality Review")
regulatory_review = leaf("Regulatory Review")

skip_supplier = leaf(None)
consult_supplier = leaf("Consult Supplier")

execute_trial = leaf("Execute Trial")
inspect_trial = leaf("Inspect Trial")
failure_tau = leaf(None)
adjust_parameters = leaf("Adjust Parameters")

release_material = leaf("Release Material")
archive_case = leaf("Archive Case")

# Risk route: low = Supervisor; high = Quality and Regulatory in parallel.
high_risk_reviews = operator_node(
    Operator.PARALLEL,
    quality_review,
    regulatory_review,
)
risk_route = operator_node(
    Operator.XOR,
    supervisor_review,
    high_risk_reviews,
)

# Optional supplier consultation.
supplier_route = operator_node(
    Operator.XOR,
    skip_supplier,
    consult_supplier,
)

# Post-root-cause work: design, approval, and supplier are concurrent here.
post_root_cause = operator_node(
    Operator.PARALLEL,
    design_corrective_action,
    risk_route,
    supplier_route,
)

containment_stream = operator_node(
    Operator.SEQUENCE,
    contain_material,
    plan_verification,
)

root_cause_stream = operator_node(
    Operator.SEQUENCE,
    analyze_root_cause,
    post_root_cause,
)

initial_parallelism = operator_node(
    Operator.PARALLEL,
    containment_stream,
    root_cause_stream,
)

# PM4Py loop convention used here: first child is the do part, second child is redo.
# Exiting after Inspect Trial without the redo child is the abstract passing inspection.
trial_body = operator_node(
    Operator.SEQUENCE,
    execute_trial,
    inspect_trial,
)
trial_redo = operator_node(
    Operator.SEQUENCE,
    failure_tau,
    adjust_parameters,
)
trial_loop = operator_node(
    Operator.LOOP,
    trial_body,
    trial_redo,
)

tree = operator_node(
    Operator.SEQUENCE,
    register_deviation,
    initial_parallelism,
    trial_loop,
    release_material,
    archive_case,
)
```

The tree represents exactly the registration/archive bookends, initial concurrency between containment and root-cause analysis, `Plan Verification` after containment, design and approval after root-cause analysis, the low/high XOR route, concurrency of the two high-risk reviews, optional supplier consultation, and the trial loop under the silent-outcome abstraction. It does **not** represent the intended non-block structure exactly. Because all children of a process-tree `PARALLEL` join before the enclosing `SEQUENCE` proceeds, approval and supplier work are forced to complete before the trial loop. This excludes legal traces where approvals or supplier consultation occur during or after the trial but before release. Consequently the tree over-constrains trial start and under-generates intended behavior. It also cannot represent release as a synchronization point for independently progressing obligations; it approximates this by synchronizing them earlier. The route/outcome choices remain nondeterministic rather than data-driven.

# 4. PM4Py POWL Model

Compact description:

```text
ROOT = StrictPartialOrder with nodes:
  Register Deviation,
  Contain Material,
  Analyze Root Cause,
  Plan Verification,
  Design Corrective Action,
  RiskRouteXOR,
  SupplierXOR,
  TrialLoop,
  Release Material,
  Archive Case

ROOT edges:
  Register Deviation -> Contain Material
  Register Deviation -> Analyze Root Cause
  Contain Material -> Plan Verification
  Analyze Root Cause -> Design Corrective Action
  Analyze Root Cause -> RiskRouteXOR
  Analyze Root Cause -> SupplierXOR
  Plan Verification -> TrialLoop
  Design Corrective Action -> TrialLoop
  TrialLoop -> Release Material
  RiskRouteXOR -> Release Material
  SupplierXOR -> Release Material
  Release Material -> Archive Case

RiskRouteXOR = XOR(
  Supervisor Review,
  StrictPartialOrder{ Quality Review || Regulatory Review }
)

SupplierXOR = XOR(tau, Consult Supplier)

TrialLoop = LOOP(
  TrialBody = StrictPartialOrder{ Execute Trial -> Inspect Trial },
  FailRedo  = StrictPartialOrder{ tau_failure -> Adjust Parameters }
)
```

```python
    operator=Operator.XOR,
    children=[skip_supplier, consult_supplier],
)

trial_body = StrictPartialOrder(nodes=[execute_trial, inspect_trial])
trial_body.order.add_edge(execute_trial, inspect_trial)

fail_redo.order.add_edge(failure_tau, adjust_parameters)

    operator=Operator.LOOP,
    children=[trial_body, fail_redo],

# Root partial order.
root = StrictPartialOrder(
    nodes=[
        register_deviation,
        contain_material,
        analyze_root_cause,
        plan_verification,
        design_corrective_action,
        risk_choice,
        supplier_choice,
        trial_loop,
        release_material,
        archive_case,

)

# Required root dependencies.
root.order.add_edge(register_deviation, contain_material)
root.order.add_edge(register_deviation, analyze_root_cause)
root.order.add_edge(contain_material, plan_verification)
root.order.add_edge(analyze_root_cause, design_corrective_action)
root.order.add_edge(analyze_root_cause, risk_choice)
root.order.add_edge(analyze_root_cause, supplier_choice)
root.order.add_edge(plan_verification, trial_loop)
root.order.add_edge(design_corrective_action, trial_loop)
root.order.add_edge(trial_loop, release_material)
root.order.add_edge(risk_choice, release_material)
root.order.add_edge(supplier_choice, release_material)
root.order.add_edge(release_material, archive_case)

powl = root
```

Every intentionally unordered pair may remain concurrent because no narrative constraint orders their completions: `Contain Material` and `Analyze Root Cause` are the two initial streams; `Plan Verification`, `Design Corrective Action`, the risk route, and supplier work may interleave subject only to their own prerequisites; `Quality Review` and `Regulatory Review` are explicitly unordered; and, crucially, `risk_choice` and `supplier_choice` are unordered with respect to `trial_loop`, allowing approvals and supplier consultation to occur before, during, or after trial cycles as long as they complete before release.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | `Contain Material` and `Analyze Root Cause` may overlap after registration. | Represented by top-level `PARALLEL`. | Represented by two unordered root successors of registration. | None. | Initial containment and investigation can proceed concurrently. |
| Plan/design split dependencies | `Plan Verification` after containment; `Design Corrective Action` after root-cause analysis; trial after both. | Dependencies are present, but trial also waits for approval and supplier because of the parallel join. | Direct edges enforce `Contain -> Plan -> Trial` and `Analyze -> Design -> Trial`; no extra approval/supplier wait. | Process tree over-constrains trial start. | Valid trials may be delayed; conformance may falsely reject legal concurrent execution. |
| Risk route | Low: `Supervisor Review`; high: `Quality Review` and `Regulatory Review` concurrent. | XOR after root-cause analysis; high branch is parallel. | XOR node after root-cause analysis; high branch is a strict partial order with no edge between reviews. | Both are permissive because data guards are absent. | Control-flow conformance cannot verify that the correct risk route was chosen for the actual case data. |
| Approval/trial overlap | Approval route need not be complete before trial and may overlap trial work. | Not represented; approvals complete before the trial loop. | `risk_choice` is unordered with respect to `trial_loop` and only ordered before release. | Process tree under-generates legal behavior. | False nonconformance for cases where reviews finish during or after trial but before release. |

# 7. Preferred Representation and Validation Plan

The canonical representation should be the **POWL model**. It preserves the intended partial-order structure directly: approvals and supplier consultation depend on root-cause analysis and release, but not on trial start; trial depends on design and verification planning; and release synchronizes all three obligation streams. The process tree is useful as a simpler block-structured approximation, but its false negatives are material for this process.

Validation plan:

1. **Convert to accepting Petri nets where supported.** Use `pm4py.convert_to_petri_net(tree)` and `pm4py.convert_to_petri_net(powl)`, capturing `(net, initial_marking, final_marking)` for each model. Treat successful conversion as evidence that the PM4Py objects are well-formed, not as proof of semantic fidelity.

2. **Check soundness.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both converted nets. Both should be sound; failures would indicate construction or conversion problems around XOR/LOOP structure.

3. **Perform bounded or sampled playout.** Generate bounded traces with a maximum trace length sufficient for at least two trial iterations, for example length 30, and sample several hundred traces. Check that samples include: low-risk and high-risk routes, supplier skip and supplier selected cases, single-cycle and multi-cycle trials, and high-risk reviews in both completion orders.

4. **Run explicit positive and negative trace tests.** Build a small event log containing W1–W5 and X1–X3. Replay or align them against the converted nets. Expected results:
   - POWL accepts W1–W5 and rejects X1–X3.
   - Process tree accepts W1, W2, W5; rejects X1–X3; and also rejects W3/W4 as known under-approximation false negatives.

5. **Check silent behavior and duplicate-label risk.** At source level, verify that visible `Transition`/leaf labels are unique in each model. Verify that the two silent nodes are exactly the supplier-skip branch and the failed-inspection gate. In replay, confirm that the supplier-skip branch emits no `Consult Supplier` event and that any redo after inspection includes `Adjust Parameters` before the next `Execute Trial`. Inspect converted nets for additional silent transitions introduced by conversion rather than assuming source-level silence is preserved one-to-one.

6. **Limitations.** Soundness does not prove that the model matches the narrative. Bounded playout may miss long or rare interleavings. Token replay/alignment results depend on implementation cost settings and visible labels only; they cannot validate hidden risk data or actual inspection results. Conversion may introduce internal silent structure, and PM4Py LOOP semantics should be confirmed against the installed version.

# 8. Final Self-Critique

1. The process-tree under-approximation rejects legal traces W3 and W4; if used for conformance, it would create false alarms for valid approval/trial and supplier/trial overlap.

2. The POWL still abstracts away case data: it admits low/high/supplier/pass/fail alternatives independently, so it cannot verify that the chosen risk route or inspection outcome matched reality.

3. The pass/fail distinction is inferred from visible control flow rather than observed labels; traces with missing or misrecorded `Adjust Parameters` would be semantically ambiguous.
