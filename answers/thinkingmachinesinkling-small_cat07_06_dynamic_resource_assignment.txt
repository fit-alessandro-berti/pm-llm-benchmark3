```
FUNCTION AssignBatch(cases, resources):
  FOR each case in cases:
    eligible = FilterBySkill(case.required_skill, resources)
    eligible = FilterHardConstraints(eligible, case) // Security, Approval, quality batch, high-priority supervision
    eligible = FilterWorkload(eligible, max_new=4, overtime_risk)
    
    // Score each eligible
    score = 0
    score += SLA_urgency(case) * w1 // urgent/high gets boost
    score += Skill_Match(resource, case) * w2 // 3 better than 2, etc.
    score += Continuity_Score(resource, case.current_owner, case.handover_cost_band) * w3 // high if same owner and low cost
    score += Workload_Fairness(resource, resource.current_open_cases) * w4 // prefer lower open
    score += Overtime_Penalty(resource.overtime_risk, case.priority) * w5 // penalize high overtime unless urgent
    score += Training_Score(resource.training_priority, case.required_skill, case.priority) * w6 // boost if matches and SLA safe
    score += Resilience_Bottleneck(resource, case.required_skill) * w7 // avoid over-concentrating specialists
    
    // Exception handling
    IF case.complexity > 0.7 AND case.handover_cost == "high":
      IF resource == case.current_owner AND resource.skill >= 2:
        score += CONTINUITY_BONUS // strongly prefer continuity
      ELSE IF resource.skill >= 2:
        score += 0 // okay to switch if skill high? Actually if current owner skill <2 and supervision feasible, allow switch.
      ELSE IF resource.skill == 0 or 1 and supervision_feasible(case):
        score += SUPERVISION_BONUS // allow with supervision
    
    IF case.required_skill == "Security":
      IF resource.skill == 3: score += 10
      ELSE IF resource.skill in [1,2] AND supervision_by(R7,R8): score += 5
      ELSE: exclude
    
    // Tie-break
    SELECT resource with max score
    IF tie: prefer lower current_open_cases, then lower reassignment_count impact, then random.
    
    IF assignment changes owner:
      IF case.reassignment_count >= 2 AND case.complexity > 0.7:
        REQUIRES_APPROVAL // exception handling
    RETURN assignment
```

# 1. Objectives and constraints

**Optimization objectives (soft / preference)**
- **Throughput & SLA risk:** Minimize waiting for urgent and high-complexity cases, especially when SLA time remaining is short.
- **Skill development:** Allocate a targeted share of normal/low-priority work to trainees where supervision is feasible and SLA is safe.
- **Workload fairness:** Prevent localized overload; respect hourly capacity and open-case balances.
- **Continuity of ownership:** Protect case-specific knowledge by reducing unnecessary handovers, especially when handover cost is high and reassignment counts are already elevated.
- **Resilience / bottleneck avoidance:** Avoid over-concentrating specialist roles (Security, Approval) so that absence of one specialist does not freeze the queue.
- **Explainability:** Every assignment should be defensible in plain language to workers and auditable via process mining.

**Hard / compliance constraints**
- **C1 (Capacity):** No resource receives more than 4 new assignments in the current decision batch.
- **C2 (Safety / supervision):** High-priority cases must not be assigned to skill level < 2 unless explicit supervision by a qualified specialist (e.g., R7_Gita or R8_Hugo for Security; R5_Eva / R6_Farid / R8_Hugo / R10_Jonas for Approval) is documented.
- **C3 (Security rule):** Security Review requires skill 3 directly, or skill 1–2 only under supervision by R7_Gita or R8_Hugo.
- **C4 (Approval rule):** Final Approval requires skill 2–3; skill 1 may prepare but not finalize.
- **C5 (Batching):** Quality Check may be batched only when priority is normal/low and SLA time remaining > 24 h.
- **C6 (Overtime guard):** Avoid assigning more work to resources with overtime risk = “high” (R2_Bruno, R4_David, R9_Iris) unless the case SLA is urgent and no safer alternative exists.
- **C7 (Complexity / continuity):** For high-complexity cases with high handover cost, continuity is strongly preferred unless the current owner has skill 0 or 1 and supervision is infeasible.
- **C8 (Training share):** At least ~20% of normal/low-priority assignments should support documented training priorities when SLA risk remains acceptable.

**Trade-off framing (no single optimum)**
We do not maximize one metric alone. A “best” assignment is a negotiated balance: keeping a specialist on a high-complexity case improves continuity but increases specialist bottleneck risk; sending a trainee to a simple, long-SLA case develops skills but slightly raises service-time variance. The policy uses a composite score with tunable weights so workers and auditors can see *why* a trade-off was accepted.

# 2. Assignment policy

```text
FUNCTION DynamicAssignment(batch_cases, resource_matrix, event_log_snapshot):
  # Pre-compute batch-level limits
  new_assignments = MAP(resource -> 0)

  FOR each case IN batch_cases (sorted by SLA urgency, then complexity):
    
    # 1. ELIGIBILITY FILTERING BY SKILL & RULE CONSTRAINTS
    eligible = resources WHERE resource.skill[case.required_skill] >= 1
    eligible = Filter(eligible, skill >= 0)
    
    # Hard exclusions
    IF case.required_skill == "Security":
        eligible = Filter(eligible, skill == 3 OR (skill IN [1,2] AND supervision_by(R7,R8)))
    IF case.required_skill == "Approval":
        eligible = Filter(eligible, skill IN [2,3])
    IF case.priority == "urgent" OR case.priority == "high":
        eligible = Filter(eligible, NOT (skill == 1 AND NOT supervised))
    IF case.required_skill == "Quality" AND case.batch_eligible:
        eligible = Filter(eligible, batch_compatible == TRUE)
    
    # 2. WORKLOAD / OVERTIME / BATCH FAIRNESS FILTER
    eligible = Filter(eligible, new_assignments[resource] < 4)
    eligible = Filter(eligible, NOT (overtime_risk == "high" AND case.priority != "urgent" 
                                    AND exists_alternative))
    
    # 3. SCORING (higher = preferred)
    FOR r IN eligible:
        score = 0
        
        # 3a. SLA urgency scoring
        score += 10 * urgency_boost(case.sla_remaining, case.priority)
        # urgent (< 6h) gets high weight; low (>24h) gets low weight
        
        # 3b. Skill-match scoring
        skill_score = resource.skill[case.required_skill]  # 3 > 2 > 1
        score += 5 * skill_score
        
        # 3c. Continuity / handover-cost scoring
        IF r == case.current_owner:
            score += 8
            IF case.handover_cost_band == "high" AND case.reassignment_count > 2:
                score += 6  # strongly protect continuity
        ELSE IF case.handover_cost_band == "low":
            score += 1   # low cost to switch
        ELSE IF case.handover_cost_band == "high":
            score -= 2   # penalize switch on high-cost cases
        
        # 3d. Workload and overtime fairness
        score -= 2 * (resource.current_open_cases / 10)  # penalize overload
        IF resource.overtime_risk == "high" AND case.priority != "urgent":
            score -= 4
        IF resource.overtime_risk == "low":
            score += 1
        
        # 3e. Training / development scoring
        IF resource.training_priority == case.required_skill 
           AND case.priority IN ["normal","low"] 
           AND case.sla_remaining > 12h:
            IF resource.skill[case.required_skill] == 1:
                score += 4  # trainee value; supervision required in practice
            ELSE IF resource.skill[case.required_skill] >= 2:
                score += 2  # upskilling via exposure
        
        # 3f. Resilience / bottleneck avoidance
        # Penalize over-concentration in specialist skills
        specialist_load = count(eligible, skill == 3 for same_skill)
        IF specialist_load > 2:
            score -= 2
        IF resource.team == "Risk" AND case.required_skill != "Security":
            score -= 1  # keep Risk focused
        
        # 3g. Exception / continuity override for complex + high handover
        IF case.complexity > 0.7 AND case.handover_cost_band == "high":
            IF r == case.current_owner AND r.skill >= 2:
                score += 10  # continuity dominates
            ELSE IF r.skill == 0 OR 1 AND supervision_feasible(r, case):
                score += 3   # supervised switch okay
    
    # 4. SELECTION & EXCEPTION HANDLING
    best = argmax(score)
    
    IF best != case.current_owner AND case.reassignment_count >= 2 
       AND case.complexity > 0.7:
        # Exception: high rework risk; flag for supervisor approval
        flag_for_review(case, best, reason="high_reassignment_complexity")
    
    # 5. DOCUMENT ASSIGNMENT REASON
    assignment_reason = BuildReason(case, best)  # e.g., "continuity+specialist", 
    # "training_supervised", "workload_fairness", "batch_eligible"
    
    # 6. UPDATE BATCH STATE
    new_assignments[best] += 1
    case.assigned_resource = best
    case.reassignment_count += (best != case.current_owner ? 1 : 0)
    
  RETURN assignments
```

**Key design choices embedded in the score**
- Continuity gets a large bonus for high-complexity/high-handover cases, but only if skill is adequate; if the owner is a trainee (skill 1) and no supervision is feasible, continuity is overruled by safety.
- Training gets a moderate bonus only when SLA is safe; it never overrides urgent SLAs or high-priority unsupervised rules.
- Workload fairness is linear, not punitive; high-overtime resources are penalized only when alternatives exist.
- Tie-break order: (1) lower current open cases, (2) lower reassignment impact, (3) documented training match, (4) team balance.
