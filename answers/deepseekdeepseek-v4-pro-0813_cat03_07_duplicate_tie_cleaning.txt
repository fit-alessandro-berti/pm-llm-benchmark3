## 1. Duplicate-handling decision tree

Use the following terminal rules. “Duplicates” are never inferred from equal activity and timestamp alone.

```text
Candidate comparison
 Exact technical duplicate?
   same timestamp, activity, source, source_event_key, payload_hash, related objects,
   and no known semantic distinction
    drop one row, keep one canonical row, record duplicate source IDs
 Same physical event observed by multiple systems?
   known reconciliation or authoritative business identity exists
    merge attributes and relations onto one canonical event; keep all provenance
 Summary event derived from a detailed event?
   e.g. detailed WMS pack vs ERP status update
    conservative: retain both with refined labels/qualifiers
    aggressive evidence-merge only: merge if rule explicitly approves abstraction loss
 Harmonization collision between semantically distinct source activities?
   e.g. WMS release vs carrier acceptance mapped to same activity label
    retain both; refine labels/qualifiers; never merge
 Concurrent same-label events involving different objects?
   e.g. pick I1 vs pick I2, capture M1 vs capture M2
    retain both; add object qualifiers; never merge on activity+timestamp alone
 Shared object but conflicting object roles or incompatible authorities?
    quarantine for review; do not auto-merge
 Unresolved candidate
     quarantine for review; preserve original event unchanged
```

## 3. Timestamp-tie ordering rules

The pipeline keeps `original_timestamp` immutable. It creates a deterministic `tie_break_rank` for linearization only.

Rules:

1. **Domain constraints — semantic.**  
   Invoice must precede payment; pick must precede pack; warehouse release must precede carrier acceptance; carrier acceptance must precede handover.

2. **Within-source sequence — semantic within a source.**  
   Use `source_seq` only when comparing events from the same source. Example: PSP e12e13e14.

3. **Lifecycle constraints on shared objects — semantic.**  
   A package cannot be packed before its items are picked; a payment method cannot be captured before its authorization.

4. **Source-specific semantics — semantic.**  
   WMS release and carrier acceptance are not the same transition merely because they share `Dispatch Package`. ERP summary follows PSP capture messages.

5. **Ingestion time — technical deterministic fallback only.**  
   `ingested_at` is not business order.

6. **Stable fallback order — technical deterministic.**  
   Use eid lexicographic order, then source-specific priority, then payload hash if necessary.

Adding microseconds before deciding semantic order is dangerous because it writes a false story into the timestamp: durations, waiting times, lifecycle latencies, and downstream performance mining will interpret a tie-break as physical temporal distance. The synthetic order must remain a separate column, never replace or overwrite `timestamp`.

Intended orders:

**10:00 e03–e07 after duplicate decisions**

- e03 canonical `Pick Item (I1)` from e03/e04
- e05 `Pick Item (I2)`
- e06 `Pack Package (WMS detail)`
- e07 `Pack Package (ERP summary)`

Admissible alternative: e05 before e03/e04 is also defensible only as a linearization; e06/e07 must appear after both picks.

**10:15 e08–e10**

- e08 `Dispatch Package (Warehouse Release)`
- e09 `Dispatch Package (Carrier Acceptance)`
- e10 `Handover to Carrier`

This order is domain-constrained and not merely arbitrary.

```python
import copy
import json
import pandas as pd
import pm4py
from collections.abc import Iterable

EVENT_ID_COL = "eid"
OBJ_COL = "related_objects"

def events_df(ocel):
    return ocel.events.copy()

def relations_df(ocel):
    for attr in ("relations", "e2o", "event_objects"):
        if hasattr(ocel, attr):
            df = getattr(ocel, attr).copy()
            if "event_id" in df.columns and "object_id" in df.columns:
                return df
    return None

def set_relations_df(ocel, df):
    for attr in ("relations", "e2o"):
        if hasattr(ocel, attr):
            setattr(ocel, attr, df)
            return ocel
    raise AttributeError("No known OCEL relation table to write")

def parse_objects(value):
    if isinstance(value, str):
        return {o.strip() for o in value.split(",") if o.strip()}
    if isinstance(value, Iterable):
        return set(value)
    return set()

def ensure_provenance_columns(ocel):
    ev = ocel.events
    for col, default in [
        ("original_timestamp", ev["timestamp"]),
        ("original_activity", ev["activity"]),
        ("original_source", ev["source"]),
        ("original_source_event_key", ev["source_event_key"]),
    ]:
        if col not in ev.columns:
            ev[col] = default

def precheck_candidate_duplicate_groups(events, group_cols):
    groups = (
        events.groupby(group_cols)[EVENT_ID_COL]
        .agg(list)
        .loc[lambda s: s.str.len() > 1]
        .to_dict()
    )
    return groups

def merge_verified_pair(
    ocel,
    keep_eid,
    drop_eid,
    merge_rule,
    refined_activity=None,
    confidence="high",
    reason=""
):
    """Merge two verified event rows and union their object relations.

    This is intentionally not a generic group-by merge. The pair must be
    verified by a business rule or reconciliation report.
    """
    events = events_df(ocel)
    rel = relations_df(ocel)

    keep_idx = events.index[events[EVENT_ID_COL] == keep_eid][0]
    drop_idx = events.index[events[EVENT_ID_COL] == drop_eid][0]
    keep_row = events.loc[keep_idx].copy()
    drop_row = events.loc[drop_idx].copy()

    # Preserve original values before overwriting.
    ensure_provenance_columns(ocel)
    events = ocel.events.copy()

    # Merge source provenance.
    merged_sources = sorted({str(keep_row["source"]), str(drop_row["source"])})
    merged_keys = sorted({str(keep_row["source_event_key"]), str(drop_row["source_event_key"])})
    events.loc[keep_idx, "source"] = ";".join(merged_sources)
    events.loc[keep_idx, "source_event_key"] = ";".join(merged_keys)
    events.loc[keep_idx, "merged_source_event_ids"] = json.dumps(
        [
            {"eid": keep_eid, "source": keep_row["source"], "source_event_key": keep_row["source_event_key"]},
            {"eid": drop_eid, "source": drop_row["source"], "source_event_key": drop_row["source_event_key"]},
        ]
    )

    # Merge object relations.
    keep_objects = parse_objects(keep_row.get(OBJ_COL, ""))
    drop_objects = parse_objects(drop_row.get(OBJ_COL, ""))
    union_objects = keep_objects | drop_objects
    events.loc[keep_idx, OBJ_COL] = ", ".join(sorted(union_objects))

    if rel is not None:
        rel = rel[rel["event_id"] != drop_eid].copy()
        existing_for_keep = set(rel.loc[rel["event_id"] == keep_eid, "object_id"])
        new_rows = []
        for oid in union_objects - existing_for_keep:
            new_rows.append({"event_id": keep_eid, "object_id": oid})
        if new_rows:
            rel = pd.concat([rel, pd.DataFrame(new_rows)], ignore_index=True)
        set_relations_df(ocel, rel)

    # Drop the duplicate event row.
    events = events[events[EVENT_ID_COL] != drop_eid].reset_index(drop=True)

    # Refine label if requested.
    if refined_activity is not None:
        events.loc[events[EVENT_ID_COL] == keep_eid, "activity"] = refined_activity

    ocel.events = events
    return ocel

def refine_labels(ocel, refinements):
    events = events_df(ocel)
    ensure_provenance_columns(ocel)
    for eid, new_label in refinements.items():
        idx = events.index[events[EVENT_ID_COL] == eid]
        if len(idx):
            events.loc[idx, "original_activity"] = events.loc[idx, "activity"]
            events.loc[idx, "activity"] = new_label
    ocel.events = events
    return ocel

def assert_referential_integrity(ocel):
    ev = events_df(ocel)
    rel = relations_df(ocel)

    assert ev[EVENT_ID_COL].notna().all()
    assert ev["timestamp"].notna().all()
    assert ev["activity"].notna().all()
    return True
```

## 7. Sensitivity analysis

| Dataset | Event count | E2O count | Main DFG/OC-DFG changes | ET–OT and OTG changes | Loops, rework, lifecycle effects |
|---|---:|---:|---|---|---|
| Raw | 17 | 44 | Duplicate edges inflated by e03/e04, e11/e16; possible false `PickPick`, `PackPack`, `DispatchDispatch` edges if timestamp sorted naively | Item E2O weight inflated by duplicated I1 scan; Order–Invoice coupling duplicated | Repeated same-label events look like rework; performance durations may be distorted by ingestion ordering |
| Conservative | 15 | 39 | Duplicate I1 and invoice edges removed; refined labels avoid false rework loops | I1 weight normalized; no false Payment-object coupling | Concurrency at e03/e05 preserved; lifecycle order e08e09e10 clear; no synthetic timestamp damage |
| Evidence-based merge | 14 | 37 | `Pack Package (WMS detail)Pack Package (ERP summary)` edge removed; pack abstraction collapsed | I1/I2 relations from WMS detail event now assigned to merged pack event; OTG event becomes more connected | Pack-to-dispatch path shortens artificially; message latency between WMS detail and ERP summary becomes invisible |
| Aggressive library merge | 9 | 25 | Distinct `Capture Payment (M1)` and `Capture Payment (M2)` collapsed; dispatch stages collapsed; pick detail collapsed | M1/M2 become attached to the same event despite being separate payments; I1/I2 picks lose separate identity; ERP summary acquires Payment relations | Lifecycle stages disappear; false legal/logistics concurrency appears; SLA measurements may become meaningless |

At least six concrete edges/patterns whose interpretation changes:

1. `Validate Order  Pick Item` frequency is inflated by e03/e04 duplication in raw, reduced in conservative.
2. `Pick Item (I1)  Pack Package` is double-counted by e03/e04, normalized after merge.
3. `Issue Invoice  Authorize Payment` is double-counted by e11/e16, normalized after merge.
4. `Pack Package (WMS detail)  Pack Package (ERP summary)` is a meaningful abstraction edge but becomes a false rework edge without label refinement.
5. `Dispatch Package (Warehouse Release)  Dispatch Package (Carrier Acceptance)  Handover` is preserved by conservative ordering but collapses into one node under aggressive merge.
6. `Authorize Payment (M1)  Capture Payment (M1)` and `Capture Payment (M2)` are distinct payment paths; aggressive merge couples M1 and M2 in one event.
7. `Capture Payment (M1)  Payment Summary (ERP)` is a legitimate summary relation; if e15 is merged into capture events, ERP summary semantics are destroyed.
8. `Pack Package  Dispatch Package` frequency changes when e06/e07 are merged or left separate.

## 8. Audit trail and reversibility

Recommended provenance schema:

| Column | Purpose |
|---|---|
| `canonical_event_id` | Canonical retained event ID |
| `source_event_ids` | JSON list of source event IDs incorporated into the canonical event |
| `source_event_keys` | JSON list of original `source_event_key` values |
| `merge_rule` | e.g. `verified_same_physical_scan`, `verified_same_invoice`, `none`, `evidence_based_pack_merge` |
| `reviewer_or_rule_version` | Human or rule version responsible for the decision |
| `original_activity` | Activity before refinement |
| `refined_activity` | Activity after refinement, if any |
| `original_timestamp` | UTC business timestamp before any adjustment |
| `synthetic_sort_timestamp` | Optional synthetic order timestamp, separate from business timestamp |
| `attributes_retained_by_source` | JSON: attributes kept from each source |
| `discarded_conflicts` | JSON: conflicting values that were not chosen |
| `confidence` | High, medium, low |
| `reason` | Human-readable justification |

For relation union provenance, use a second table:

| Column | Purpose |
|---|---|
| `canonical_event_id` | Canonical event |
| `object_id` | Related object |
| `source_event_ids` | Source events contributing the relation |
| `relation_rule` | `original`, `union`, `qualified_merge` |
| `reviewer_or_rule_version` | Decision owner |

An analyst can reconstruct the raw view because `ocel_raw` is never mutated. For each canonical event, `source_event_ids` can be joined back to the raw event table to expand merged events into their original rows. For label refinements, `original_activity` restores the activity label. For object relations, `relation_provenance` restores which source event originally contributed each relation.

## 9. Failure modes and safeguards

| Failure mode | Example | Safeguard |
|---|---|---|
| Collapsing distinct partial payments | e13 and e14 both `Capture Payment` at 12:00 | Require equality of Payment object IDs, not merely shared invoice or order |
| Converting abstraction-level updates into false rework | e06/detail vs e07/summary or e15/summary | Refine labels; keep separate unless a named evidence rule explicitly approves merge |
| Ordering by ingestion time | e12/e13/e14 may appear in inconsistent order | Use ingestion only as fallback; primary order uses domain and source sequence |
| Treating shared objects as proof of duplication | e13/e14 share O1 and V1 | Common objects are necessary but not sufficient; compare object identities by type |
| Unioning incompatible E2O relations | Adding I1/I2 to ERP summary in e07; adding M1/M2 to e15 | Union objects only after same-physical-event verification or explicitly accepted abstraction merge |
| Changing durations through synthetic microseconds | Adding microseconds before semantic order makes false latencies | Keep original timestamp immutable; add separate synthetic sort column |
| Losing source-authoritative attributes | ERP and Billing both authoritative for invoice fields | Merge by attribute authority; store conflicts, never silently overwrite |
| Applying duplicate functions to the whole OCEL without inspecting candidate groups | `ocel_drop_duplicates` or `ocel_merge_duplicates` on all events | Run pre-check candidate groups; apply library functions only to justified groups; protect known distinct eids like e05 and e14 |
