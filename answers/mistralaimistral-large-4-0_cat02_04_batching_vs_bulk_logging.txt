**G6-like data creates both inflated waiting and near-zero service** because the same timestamp is used as both start and complete for all cases: waiting = 17:00  queue_arrival (large), while service = complete  start = 0. This is a logging artifact, not a physical process.

No rows are dropped; G6 zero-duration and G7 negative-wait rows are retained and flagged. PM4Py batch labels are treated as temporal-pattern detections, not proof of physical execution semantics.

def overlap_rate(sub):
    n = len(sub)
    if n < 2:
        return 0.0
    starts = sub["start_ts"].values
    ends = sub["complete_ts"].values
    overlaps = 0
    total = 0
    for i in range(n):
        for j in range(i + 1, n):
            total += 1
            if starts[i] < ends[j] and starts[j] < ends[i]:
                overlaps += 1
    return overlaps / total if total else 0.0

# 5. Robustness and alternative explanations

**Assumption A — Resource IDs are trusted as individual workers.** Under this assumption, G5’s overlapping intervals imply one worker doing concurrent work, which is possible only as multitasking; naive utilization can exceed 100%. G1 RBT-7 is a machine, so trusted. G2/G3/G4/G6/G7/G8 individual resources are likely trusted, but G6 manual bulk form may still be one worker.

**Assumption B — Resource IDs may be shared accounts.** Under this assumption, G5 overlaps are expected and physical concurrency is plausible. G1 RBT-7 is not a shared account. G6 T-F could be shared? Not indicated. Identities must be split before utilization analysis.

**Assumption C — Timestamps are exact.** Under this assumption, G7 negative waits are impossible, so the data must be wrong; G6 zero durations are real but implausible; G2/G3 equality is real.

**Assumption D — Timestamps are interval-censored by stated precision.** Under this assumption, G7 start/complete lie somewhere within a 15-minute rounding interval, removing negative waits and artificial equality. G2/G3/G5 1-min precision means identical minute timestamps may hide up to 60 sec differences; G1/G4/G8 1-sec precision has minor effect. G6 1-min precision still leaves zero duration.

| Same temporal pattern | Clusters | Explanation A | Explanation B | Discriminating evidence |
|---|---|---|---|---|
| Identical start and end | G1, G6, G7 | Genuine simultaneous batch (G1) | Bulk end-of-shift entry (G6) or timestamp coarsening (G7) | G1 fixture capacity + PLC 1-sec; G6 manual_bulk_form + queue spread; G7 15-min precision + negative waits |
| Identical start, staggered completions | G2 | Start batching/common setup | Concurrent work/multitasking | Single begin group button vs separate completion buttons |
| Staggered starts, identical completions | G3 | End batching/bulk submission | Genuine simultaneous completion | Context says form submitted after folder; recorded_at clustered |
| Overlapping intervals under same resource | G5 | Shared-account artifact | One worker multitasking | shared_VDI context, badge identity not retained |
| Adjacent start=previous complete | G4, G8 | Sequential batching | Queue accumulation after capacity loss (G8) | G8 safety-check event 15:00–15:35; G4 no capacity loss evidence |

# 6. Data-collection redesign

1. **Execution timestamps (highest priority):** Capture per-case start and complete from the process/device, not from batch-level buttons. Add pause/resume/suspend/abort lifecycle events. For G2, replace “begin group” with per-item start; for G3, separate review completion from form submission; for G6, record actual work completion before bulk closure.
2. **Resource/badge identity:** Use individual badge IDs or named logins; for shared VDI, capture session ID and map to badge. Avoid shared accounts for performance analysis.
