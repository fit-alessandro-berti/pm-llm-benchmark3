# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**
- Events are atomic and identified by `concept:name`; resources are strings from the `org:resource` or `resource` attribute.
- Timestamps are strictly ordered within each trace (no out-of-order writes).
- The “stable procedural backbone” (1–5) is mandatory sequential/parallel/choice structure; cross-cutting rules are optional or exceptional.
- “Before any final outcome” in R3 means before `Reject Vendor`, `Activate Vendor`, or `Close Onboarding`.
- “Applicable approval” in R9 means the approval actually executed in the branch (`Manager Approval` for low-risk; `Compliance Approval` for high-risk).

**R5 / R6 conflict**
- **R5 (strict):** After `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor`.
- **R6 (exception):** Emergency activation may precede the opinion, but only with joint external authorization (not in the event log), and the opinion must arrive within 24 h.

**Two resolutions**
1. **Conservative / Activity-only (chosen for implemented layers):** Enforce R5 as an unconditional `precedence` / `always_before` rule. R6 is treated as an external policy exception that must be recorded outside the log (e.g., a `case_attributes` table with `joint_authorized=True`). If that external record is absent, the case is a violation.
2. **Exception-conditional:** Allow `Activate Vendor` before `Obtain Legal Opinion` only when `joint_authorized` is true and the inter-event gap  86 400 s (24 h). If the attribute is missing, the check is inconclusive.

**Chosen resolution and compliance risk**
I implement **Resolution 1** in all activity-only formalisms (procedural choice excludes the exception; DECLARE encodes unconditional precedence; Log Skeleton uses `always_before`). The external layer (Section 7) applies Resolution 2 when `joint_authorized` is present.  
*Compliance risk:* A legitimate emergency activation without an external authorization record will be flagged as a hard failure (false positive). To mitigate, the deployment layer must mandate that operations log the joint-authorization record immediately; otherwise the conservative model blocks the case, which is appropriate for a “controlled” onboarding process.

# 3. Procedural Backbone

## 3.1 Compact formal description

The backbone is a sequential process with a parallel block and a terminal exclusive choice.

- `Receive Onboarding Request`
- `||` (`Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account`)
- `Classify Risk`
- `X` (choice):
  - `Reject Vendor`  `Close Onboarding`
  - `Manager Approval`  `Activate Vendor`  `Release First Payment`  `Close Onboarding`
  - `Enhanced Due Diligence`  `Compliance Approval`  `Activate Vendor`  `Release First Payment`  `Close Onboarding`

**Approximations / exclusions**
- `Request Clarification` / `Receive Clarification` are omitted from the structured backbone; they are modeled as floating cross-cutting events (see DECLARE / external layer).
- `Sanctions Escalation` / `Obtain Legal Opinion` are not embedded in main branches; they are allowed before/during classification and before activation via DEC/EXT rules.
- `Change Bank Details`, `Suspend Vendor`, and second `Verify Bank Account` are excluded; handled externally (R11).
- Emergency activation exception (R6) is not represented; authoritatively blocked by R5 in this layer.

## 3.3 Explanation of features

- **Concurrency:** The `||` operator allows `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` to occur in any order and interleaved.
- **Choices:** The terminal `X` enforces exactly one outcome branch per case (reject, low-risk accept, high-risk accept).
- **Clarification loops:** Not structured; the backbone assumes clarification, if needed, does not prevent classification or approval, but the DECLARE `response` rule (Section 4) ensures pairing and ordering relative to final outcomes via external sequence filters.
- **Terminal outcomes:** `Close Onboarding` is always final; `Reject Vendor` and `Activate Vendor` are mutually exclusive by branch design.
- **Post-activation behavior:** `Change Bank Details` / `Suspend Vendor` are deliberately excluded from the procedural tree because they depend on a post-activation state not representable without an explicit data/state layer.

| `precedence` | `(Run Sanctions Screening, Sanctions Escalation)` | Escalation cannot occur before screening | Structural guard (R7) |
| `precedence` | `(Classify Risk, Manager Approval)` etc. | Approval requires classification first | Structural backbone support |
| `noncoexistence` | `(Reject Vendor, Activate Vendor)` | Both cannot appear | **Noncoexistence  Nonsuccession**: noncoexistence forbids both at all; nonsuccession would allow A before B but not B before A |
| `exactly_one` | `Activate Vendor` | Must occur exactly once if present in model scope | Here enforced globally; rejected cases violate if interpreted strictly, so procedural branch is authoritative for absence |
| `absence` | `Sanctions Escalation` | Optional at 0 occurrences | Weak; used only to show optionality, not a strict rule |

### Overlap / disagreement notes
- **Always_before vs procedural:** The skeleton confirms structural orders (checks before classify, approvals before activate). It does not enforce “eventually” (response); that is DECLARE.

- **Activ_freq:** `Verify Bank Account` allows 2 (R11); approvals allow {0,1} because branches are mutually exclusive.

**Why warnings rather than automatic violations**
Time is an observational property, not a logical prerequisite for process correctness. A case with a 90-hour delay to first payment (T1, 71h is fine; T6, 77h is fine; but extreme outliers) may be legitimate due to treasury holds, holidays, or manual checks. The profile with `zeta=2.0` flags statistical outliers for audit (mean ± 2 = 72±72h so range [0,144h] for release; 12±12h = [0,24h] for opinion) but does not block case closure. Only the external resource/data layer can block; temporal is advisory.

# 7. Resource- and Data-Aware Checks

```python
def check_four_eyes(trace_df, act1="Verify Bank Account", act2="Manager Approval"):
    """R9: applicable approval resource must differ from Verify resource."""
    res_verify = trace_df.loc[trace_df["concept:name"] == act1, "resource"]
    res_approve = trace_df.loc[trace_df["concept:name"].isin(["Manager Approval", "Compliance Approval"]), "resource"]
    if res_verify.empty or res_approve.empty:
        return "not_evaluated"  # missing data
    if set(res_verify) & set(res_approve):
        return "fail"
    return "pass"

def check_capture_vs_activate(trace_df):
    res_capture = trace_df.loc[trace_df["concept:name"] == "Capture Master Data", "resource"]
    res_activate = trace_df.loc[trace_df["concept:name"] == "Activate Vendor", "resource"]
    if res_capture.empty or res_activate.empty:
        return "not_evaluated"
    if set(res_capture) == set(res_activate):
        return "fail"
    return "pass"

def check_r3_before_final_outcome(trace_df):
    """Every Request Clarification must have Receive Clarification before last final event."""
    requests = trace_df.loc[trace_df["concept:name"] == "Request Clarification"].index
    receipts = trace_df.loc[trace_df["concept:name"] == "Receive Clarification"].index
    final_indices = trace_df[trace_df["concept:name"].isin(["Reject Vendor","Activate Vendor","Close Onboarding"])].index
    if requests.empty:
        return "pass"
    # Pairwise: each request must have a receipt after it and before final outcome
    for r_idx in requests:
        later_receipts = receipts[receipts > r_idx]
        later_final = final_indices[final_indices > r_idx]
        if later_receipts.empty or (not later_receipts.empty and later_receipts[0] > (later_final[0] if not later_final.empty else float('inf'))):
            # If final occurs before receipt, or no receipt at all
            if not later_receipts.empty:
                first_receipt = later_receipts[0]
                if not later_final.empty and first_receipt > later_final[0]:
                    return "fail"
            else:
                return "fail"
    return "pass"

def check_r6_emergency_policy(trace_df, external_auth_df=None):
    """
    R6 / R5 conflict resolution.
    Required attributes: concept:name, time:timestamp, resource.
    External: external_auth_df with columns [case_id, joint_authorized: bool, authorization_time].
    """
    if "Sanctions Escalation" not in trace_df["concept:name"].values:
        return "pass"  # not applicable
    
    has_opinion = "Obtain Legal Opinion" in trace_df["concept:name"].values
    act_idx = trace_df.index[trace_df["concept:name"] == "Activate Vendor"]
    op_idx = trace_df.index[trace_df["concept:name"] == "Obtain Legal Opinion"]
    
    # If opinion exists before activation -> R5 satisfied regardless
    if has_opinion and not act_idx.empty and not op_idx.empty and op_idx[0] < act_idx[0]:
        return "pass"
    
    # If activation before opinion (emergency scenario)
    if not act_idx.empty and (op_idx.empty or act_idx[0] < op_idx[0]):
        # Check external authorization
        if external_auth_df is None or external_auth_df.empty:
            return "fail_misising_auth"  # missing attribute -> conservative failure
        auth = external_auth_df.get("joint_authorized", False)
        if not auth.iloc[0] if hasattr(auth, "iloc") else not auth:
            return "fail_no_auth"
        # Must arrive within 24h
        act_time = trace_df.loc[act_idx[0], "time:timestamp"]
        if op_idx.empty:
            return "fail_opinion_missing"
        op_time = trace_df.loc[op_idx[0], "time:timestamp"]
        delta_hours = (op_time - act_time).total_seconds() / 3600.0
        if delta_hours > 24.0:
            return "fail_late_opinion"
        return "pass_with_warning"  # emergency allowed but flagged
    
    return "fail"
```

**Required event attributes**
- `concept:name`, `time:timestamp`, `resource` (for R9).
- For R6: external table `joint_authorized`; if missing, default to `fail` (conservative).

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement (R1, R8, R10):** R1 is enforced by procedural `X`, DECLARE `noncoexistence`, and Log Skeleton `never_together`. This is consistent but redundant; a violation will be caught by all three, which is safe for a controlled process.
- **Inconsistency under loops:** If `Request Clarification` repeats, `response` guarantees only eventual pairing, not “before the very next request.” Without an explicit chain template, a second request could occur before the first response if the log is dirty, though R3 requires it not to happen. The external sequence check (Section 7) is needed to close this gap.
- **Vacuity:** `precedence(Obtain Legal Opinion, Activate Vendor)` is vacuously true for all non-escalated cases (no opinion needed). It therefore over-approximates R5 but does not harm non-escalated traces; the external layer must restrict enforcement to escalated cases to avoid false negatives.
- **Missing case attributes:** No `emergency_authorized` field, no `bank_changed` flag, and no `case_status` (accepted/rejected) are present at event time. This forces conservative assumptions (fail if missing) and prevents fully automated R6 / R11 validation.
- **Timestamp-only limitations:** Concurrent events (`Capture`, `Run`, `Verify`) have ordering in the log due to millisecond/second resolution, but true concurrency is not observable; direct-follows relations for concurrent activities are unreliable.
- **Support/confidence as normative truth:** All DECLARE rules carry `support=1.0`, implying they were observed in 100 % of training traces. If future cases contain rare but valid exceptions (e.g., emergency without authorization in legacy records), the model will falsely reject them. Confidence values (e.g., 0.90 for R5 precedence) should be interpreted as model reliability, not policy authority; the authoritative policy remains the procedural backbone plus external rules.

# 10. Deployment Recommendation

- **Canonical procedural representation:** The ProcessTree in Section 3 (`procedural_model`). It should be used for structural conformance (`pm4py.conformance_process_tree` or alignment) because it captures mandatory concurrency and exclusive outcomes efficiently.
- **Authoritative policy layer:** 
  - **Hard control-flow / behavioral:** DECLARE (`declare_model`) is authoritative for cross-cutting relational rules (R3, R4, R5, R7, R8, R1). 
  - **Frequency / ordering:** Log Skeleton (`log_skeleton`) is authoritative for occurrence counts and always-before/never-together constraints that are mined from observed behavior.
  - **Resource / state / exception:** The external validation layer (Section 7) is authoritative for R6 (emergency), R9 (segregation of duties), and R11 (post-activation bank changes). No activity-only formalism can recover these.
- **Conformance check order:**
  1. **Procedural** — eliminate structurally impossible traces (wrong order of backbone).
  2. **DECLARE** — check behavioral constraints (response, precedence, noncoexistence).
  3. **Log Skeleton** — verify occurrence frequencies and invariant ordering.
  4. **Temporal Profile** (`temporal_profile`, `zeta=2.0`) — generate audit warnings; never block solely on time.
  5. **Resource / Data / External** — apply `filter_four_eyes_principle`, resource inequality checks, and R6 external authorization verification.
- **Contradictory findings surfacing:** If procedural passes but DECLARE fails (e.g., T5 missing clarification response), report `Hard Fail — Declarative Violation`. If procedural and DECLARE pass but resource layer fails (T4), report `Hard Fail — Resource Violation`. If temporal profile flags but all control layers pass (T7), report `Warning — Temporal Deviation`. If R6 authorization is missing (T6), report `Policy-Dependent — Missing Emergency Authorization Record`. Display layered summaries so users see which layer failed and whether it is structural, declarative, temporal, or resource-based.
