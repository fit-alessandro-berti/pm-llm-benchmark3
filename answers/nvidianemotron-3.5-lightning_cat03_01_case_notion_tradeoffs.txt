## 1. Analytical assumptions

In this OCEL 2.0 snapshot, the “case notion” is not fixed; it is determined by the object type chosen for flattening. Flattening on a given object type produces a classical event log where each trace corresponds to the lifecycle of instances of that object type, and every event directly related via E2O (the “Related objects” column) is included. Events related to multiple object types are copied into every relevant case, as specified by OCEL semantics. I treat this copying as **both evidence of cross-object dependencies and a duplication artifact** that must be explicitly accounted for in interpretation; it is not a neutral operation but a representational choice.

- **Convergence** refers to the phenomenon where distinct object instances come to share events through copying, potentially making their traces appear similar or merging variant boundaries. In this OCEL, shared events such as e16 (Dispatch) and e24 (Confirm Delivery) are directly related to O1, O2, and O3, and will be copied into each of those three order traces under Order flattening, creating convergence that can mask the fact that one physical event serves multiple orders.

- **Divergence** refers to the artificial shortening or thinning of a lifecycle when the chosen object participates in only one or two event types, thereby excluding richer contextual activity. This is exemplified by Delivery traces (2 events) and Payment traces (1 event each), where the full preobject activity is lost.

Permitted analytical transformations include **explicit propagation of O2O relations** (e.g., propagating “contains” from Order to Item) as a deliberate flag, but I will **not silently assume such propagation** without notation, because it can hide consolidation semantics (e.g., making O1’s split across P1 and P2 appear as a singlepackage flow). All reasoning below will reference the original E2O relation sets rather than propagated derivatives, unless an explicit transformation is proposed and justified.

## 4. Traditional versus objectcentric analysis portfolio

### Flattened logs that should still be created
- **Orderflattened log**: Safe for answering “What is the progress of order X from creation to closure?” when the analyst is prepared to correct for sharedevent duplication (e16, e24, e13). Useful for individual order tracking, SLA monitoring, and posthoc audit where the case identity is the primary concern.
- **Invoiceflattened log**: Safe for financial audit questions such as “When was invoice V2 issued and how were its payments recorded?” when the dualorder origin and instalment structure are explicitly referenced via E2O metadata.
- **Packageflattened log**: Appropriate for operationslevel questions like “What is the average time between packing and confirmation for package P3?” when orderlevel context is irrelevant or handled separately.

### Questions requiring objectcentric artefacts
- **OCDFG (objectcentric DFG)**: Required for any analysis of crossobject variants, frequencies, or behaviours that involve consolidation. The OCDFG retains E2O multiplicities and can reveal, for example, that Dispatch e16 is shared across O1, O2, O3 and that Confirm Delivery e24 similarly consolidates those orders. It would prevent the frequency inflation described in Distortion 7.
- **OTG (objecttype graph)**: Needed to visualise and reason about the E2O relation structure (e.g., which object types are directly related to which events). The OTG makes explicit that e16 is related to both Dispatch and multiple object types (O1, O2, O3, items, packages, delivery), supporting informed flattening choices.
- **ET–OT (event–objecttype) graph**: Useful for exploring how events interact with object types across the process. For instance, the ETOT graph would show that e19 (Issue Invoice) is related to O2, O3, and V2, highlighting V2’s role as a consolidation point without requiring flattening.
- **Object interaction summary**: An OCELspecific summary that aggregates how often each object type appears in each activity’s Related objects set. This would quickly reveal, for example, that P3 appears in e13 and e16, flagging its crossorder role.
- **Equivalentexecution clustering** (if adopting decision C): To group executions that share the same underlying objecttype trajectory regardless of the chosen lead object, enabling comparison of, say, “orders that travelled through D2” vs “orders that did not.”

### Reconciling contradictory findings
When a flattened log suggests a simple lifecycle (e.g., Delivery traces of length 2) while an OCDFG reveals rich crossobject dependencies, the reconciliation procedure is:
1. **Identify the lead object** used for the flattening and document the E2O set that was used.
2. **Inspect the OTG** to locate all events that are directly related to the lead object but also appear in other object types’ E2O sets.
3. **Crossreference the object interaction summary** to quantify how many traces the shared events are copied into.
4. **Adjust the analysis** either by (a) filtering out copied shared events if the goal is perobject lifecycle fidelity, or (b) retaining them with explicit flags if the goal is to study consolidation patterns.
5. **If needed, switch to an OCDFG or OTGbased view** to recover the hidden structure, then map findings back to the flattened log for reporting to stakeholders accustomed to classical event logs.

## 5. Lead-object decision

**Position C: Reject a single lead object for this process.**

### Decision criteria
1. **Distortion minimisation**: The chosen lead object should not artificially truncate lifecycles or inflate event frequencies beyond repair. All six object types produce significant distortions in this OCEL.
2. **Completeness of lifecycle representation**: The lead object should, in its natural flattening, accommodate the majority of process steps (creation, modification, fulfilment, invoicing, payment, closure) without requiring extensive posthoc patching.
3. **Representation of business facts**: The flattening should make explicit, not hide, the stated business facts: O1 split across P1/P2, P3 involving O2&O3, P4 involving O3&O4, D2 consolidating three orders, V2 consolidating O2&O3 and paid in two instalments, and the nearsingleton lifecycle risk.

### Strongest supporting evidence
- The business facts are **explicitly designed** to test crossobject consolidation: O1 is split across two packages; P3 and P4 each contain items from two different orders; D2 consolidates P2 and P3, involving three orders (O1, O2, O3); V2 consolidates O2 and O3 and is paid in two instalments (M2 + M3). These facts are **structural** to the process and cannot be captured by a singleobject flattening without loss or distortion.
- Every object type either **truncates lifecycles** (Delivery: 2 events; Payment: 1 event) or **introduces massive event duplication** (Order: shared e16, e24 copied into three traces; Item: shared e13, e14, e24, e16 copied across items; Package: shared e16, e24 across P2/P3).
- The “shared event copying” mechanism of OCEL, while semantically necessary, creates **systematic convergence** that distorts variant frequencies and DFG structures regardless of which object type is chosen as lead.

### Strongest counterargument
- **Traditional processmining practice** often selects “Order” as the default case notion for orderfulfilment processes. An Orderflattened log is immediately familiar to practitioners, provides traceable lifecycles from Create Order to Close Order, and requires no additional OCELspecific expertise to interpret basic progress (e.g., “Is order O1 dispatched?”).
- If the analytical goal is **restricted to orderlevel timing** (e.g., cycle time from order creation to delivery confirmation for a single order), the Order flattening is **pragmatically sufficient** without needing the full objectcentric apparatus.

### Residual risk
Even rejecting a single lead object does not eliminate all distortion; analysts must still decide how to aggregate or cluster across object types. Residual risks include:
- Misinterpretation when sharing aggregated findings (e.g., “average dispatch time”) without clarifying which consolidation path was counted.
- Difficulty in communicating results to stakeholders accustomed to singlecase logs.
- The need for supplementary OCDFG or OTG artefacts to make the multilead view intelligible.

### Conditions under which the decision would change
- If the analytical scope **narrows** to a single, nonconsolidating subprocess (e.g., “track only order O1’s endtoend progress, ignoring O2–O4 and all package sharing”), then **Position A (select Order as lead)** becomes defensible with the qualification that sharedevent copying must be explicitly corrected.
- If a **multiobject clustering** approach is adopted where the process is partitioned by consolidation pattern (e.g., “orders routed through D2” vs “orders routed through D1/D3”), then **Position B (primary lead + secondary lifecycles)** could be realised by taking Order as primary and attaching secondary Package/Delivery/Invoice lifecycles as conditional branches.
- If **tooling** evolves to natively support OCELflattening with automatic sharedevent deduplication and provenance tracking, the practical pain of Position C would decrease, though the structural necessity of rejecting a single lead object would remain because the process model is inherently multiobject.

## 7. Sensitivity and validation plan

At least four sensitivity checks are described below. Each checks the robustness of the analytical conclusions to a specific modelling choice.

### 1. Removing or downweighting copied shared events
- **Procedure**: In each flattened log, identify events that are directly related to multiple object types (e.g., e16, e24 in Order flattening; e13, e14, e24 in Item flattening; e16, e24 in Package flattening). Create a variant flattening where these events are **excluded** from the E2O set (or marked as “external” and omitted from traces). Recompute DFGs, trace lengths, and variant frequencies.
- **Goal**: Quantify how much of the observed event frequency inflation (Distortion 7) and lifecycle shortening (Distortions 6, 8) is attributable to the sharedevent copying mechanism versus genuine process behaviour.
- **Expected outcome**: DFG edges involving e16/e24 in Order flattening will drop significantly, trace lengths will shorten, and variant distributions will become more differentiated. This check confirms that the distortions identified in Section 3 are primarily artefacts of the copying semantics.

### 2. Comparing direct E2O relations with an explicitly propagatedrelation variant
- **Procedure**: Construct a variant where O2O relations are **propagated** transitively. For example, since O1 “contains” I11 and I12, and I11 is “packed” in P1, a propagated relation might link O1  P1  D1 automatically. Apply this propagation before flattening on each object type, then compare the resulting traces, DFGs, and lifecycle lengths with the directE2O variant.
- **Goal**: Test whether propagating O2O links (as some analysts might be tempted to do) reduces perceived complexity or, conversely, further hides consolidation semantics (e.g., making O1’s split across P1/P2 appear as a single package path).
- **Expected outcome**: Propagation will likely **increase** distortion for Package and Order flattenings by masking the O1split and crossorder package facts (P3 involving O2,O3, etc.). It may also artificially lengthen some traces (e.g., adding prepack events to Delivery traces), but at the cost of semantic accuracy. This check warns against silent propagation.

### 3. Changing the lead object
- **Procedure**: Repeat the full analytical pipeline (flattening, DFG discovery, variant frequency computation, OCDFG/OTG inspection) for **each** of the six object types as the lead. Record key metrics: average trace length, number of distinct DFG edges, frequency of consolidationrelated events (e16, e24, e13, e14, e19, e22, e25), and the count of nearsingleton lifecycles (traces of length 2).
- **Goal**: Provide a transparent sidebyside comparison that no single lead object dominates; the metrics will quantitatively demonstrate the tradeoffs (e.g., Order has the longest traces but high duplication; Delivery has the shortest but reveals consolidation; Payment has length1 traces but zero contextual richness).
- **Expected outcome**: The metric matrix will confirm the qualitative ratings in Section 2 and the distortion descriptions in Section 3, reinforcing the decision to reject a single lead (Position C) or to adopt Position B with explicit secondary lifecycles.

### 4. Comparing frequency metrics based on events, unique objects, and total objects in the OCDFG
- **Procedure**: From the global OCDFG (discovered via `pm4py.discover_ocdfg(ocel)`), extract three frequency metrics for each activity:
  1. **Eventbased frequency**: Count of raw event occurrences in the OCEL (from `pm4py.ocel_activity_frequency`).
  2. **Uniqueobject frequency**: Count of distinct object instances (from `pm4py.ocel_object_frequency`) that are related to the activity via E2O.
  3. **Totalobject frequency in OCDFG**: Sum of edge weights or occurrences of the activity node in the OCDFG, which inherently accounts for multiplicities across object types (e.g., Dispatch e16 contributing to O1, O2, O3 simultaneously).
- **Goal**: Compare how these three metrics diverge across activities, especially consolidation points (Dispatch e16, Confirm Delivery e24, Issue Invoice e19, Record Payment e22/e25). Plot or tabulate the ratios (e.g., totalobject / eventbased frequency for e16 should be ~3, reflecting its threeorder involvement).
- **Expected outcome**: Activities with high consolidation (e16, e24, e19, e22/e25) will show large ratios between totalobject and eventbased frequencies, explicitly quantifying the “copying” effect. Activities with low consolidation (e01–e04 Create Order) will have ratios near 1. This check provides a numerical foundation for the qualitative convergence/divergence ratings in Section 2 and helps analysts decide whether to apply correction factors when interpreting flattenedlog frequencies.
