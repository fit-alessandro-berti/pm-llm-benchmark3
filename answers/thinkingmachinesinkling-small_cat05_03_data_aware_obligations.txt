## 1. Temporal Data Semantics

**Reconstruction.** Each case is reconstructed by ordering events by `(time:timestamp, event_index)`. Blank attribute cells (`amount`, `risk_level`, `jurisdiction`, `customer_type`, `exemption_id`) mean “no update at this event”; they do **not** nullify the previous value. Within a case, state propagates forward by last-known-value fill (forward fill only). The final row of a case is **not** copied backward.

**Equal timestamps.** When two events share a timestamp, `event_index` is the tie-breaker. The lower index is effective first; the higher index overrides blanks and updates the state for subsequent evaluation. Example: TX-311 `Enhanced_Review` (index 3) occurs before `Update_Jurisdiction` (index 4) at `16:20:00Z`; at the moment of review the jurisdiction is still `US`, and only after index 4 does it become `DE`.

**Material changes.** For R1–R4 I treat a data change as *material* when:
- `jurisdiction`, `risk_level`, or `customer_type` changes (directly affects rule triggers); or
- `amount` increases by **>20 %** relative to the amount at the latest Standard/Enhanced Review (R4 invalidation); or
- `amount` decreases (not invalidating per R4, and not resetting R1’s temporal window).  
A non-material amount change (e.g., +4.5 %) does not require a new Enhanced_Review for R1 because R4 does not invalidate the existing review.

**Effective vs. record vs. evidence time.**
- **Event time** (`time:timestamp`) = when the action occurred.
- **Effective time** = when the attribute change governs obligations (same as event time unless explicitly stated otherwise; here it is the event time).
- **Record time** = when the database/system wrote the row (e.g., `Record_Exemption` at 11:00 is record time; approval may have been effective earlier).
- **Evidence time** = when proof of the event/exemption was created (e.g., signed PDF, digital signature timestamp, witness statement). For exemptions, evidence time is decisive per R5: a backdated display field alone is not conclusive.

**State at `Release_Funds`.** For each rule evaluation I use the latest non-blank value at or before the release timestamp, ordered by `(time, event_index)`. Unknown/missing values (`amount` blank at release, `amount` blank at review) are **not** defaulted to `0` or `LOW`; they yield `INDETERMINATE` when the trigger cannot be established or excluded (R6).

## 4. Ambiguities and Alternative Readings

**INDETERMINATE: TX-305.** The release event carries no amount, and the review document carries none either. The settlement record at `2026-04-07T08:00:00Z` states `amount=150000` with the note “settlement amount may equal release amount.” If that settlement were treated as authoritative and the amount at release were therefore `100000` (and jurisdiction `CA` non-DE), R1 would trigger and the missing amount in the review would be a deviation. If instead the release amount were `<100000` (or if the settlement is a later separate flow), R1 would not trigger. A definitive decision requires either (a) an immutable release payload recording amount at `11:30`, or (b) an authoritative feed timestamped at or before release. **Alternative:** If the settlement amount is accepted as the release amount, the case becomes NONCOMPLIANT because R1 is triggered by `CA/150k` but the `Enhanced_Review` at 11:15 lacks an amount record, so its validity for amount-dependent obligations is unverified, and no post-material-change review exists (no later update after 11:15, but the review itself is not demonstrably amount-validated).

**TX-302 (exemption timing/evidence).** The exemption is strongly supported by a qualified digital signature at `09:05` and a valid hash, with a documented outage explaining the `11:00` database insert. **Alternative:** If the 09:05 timestamp were proven to be a clock error or if the outage documentation were later retracted, the exemption would be unproven at `09:40`; then R1 would be violated (foreign `GB`, `180k`, no Enhanced_Review after any material change—there is none, but the obligation would remain unwaived).

**TX-305 (missing amount / review validity).** The `Enhanced_Review` at 11:15 exists but its document has no amount. **Alternative:** If the review procedure implicitly covered “current order” and the release message omitted amount only due to a display bug, and if the settlement `150k` is accepted, then the review might be considered sufficient for R1 if the amount was unchanged since review; however, because we do not know whether the amount changed between 11:15 and 11:30, we cannot exclude an unrecorded update. Thus it remains `INDETERMINATE`.

**TX-310 (post-hoc exemption / backdated approval).** The release at `10:00` references `EX-88`. The PDF displays `08:50`, but the signing certificate was created at `10:30`. **Alternative 1:** If the 08:50 time is accepted solely on the PDF display and the witness statement (despite the requester conflict) is corroborated by an independent compliance officer, EX-88 could be deemed valid at 10:00, making the case a `JUSTIFIED_EXCEPTION` (R1 waived) rather than NONCOMPLIANT—though R2 is not triggered here, so only R1 matters. **Alternative 2:** If the certificate time is controlling, EX-88 is invalid at 10:00, and the case is clearly NONCOMPLIANT (Standard_Review  Enhanced_Review; no Enhanced_Review exists). The decisive change is independent corroboration of approval at or before 10:00.

**TX-311 (same-timestamp ordering).** At `16:20`, index 3 (`Enhanced_Review`) precedes index 4 (`Update_Jurisdiction` to `DE`). **Alternative:** If the tie-breaker were ignored and `Update_Jurisdiction` were treated as occurring first, the review would have been conducted under `DE` jurisdiction; since `DE` turns off R1, the result is still COMPLIANT. But if the jurisdiction had changed to a non-DE country (e.g., `FR`) at index 4, ignoring the index would falsely place the review after the change and incorrectly satisfy R1. Conversely, if index 3 were after index 4, the review would have been under `DE` and R1 (if later changed back to `US`) would require a new review. **Decisive evidence:** The source-system `event_index` must be preserved; any analysis that sorts only by timestamp without index misorders the state at 16:20.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A trace-checker that uses case-level final attributes (`amount=145000`, `jurisdiction=DE`) to evaluate all events would wrongly treat TX-311’s review at 16:20 as occurring under `DE`; in reality, due to `event_index`, it occurred under `US`, and only the release state is `DE`. Rules must use per-event state, not final case state.

2. **Post-hoc exemptions (R5).** TX-302 records `EX-77` at 11:00 but the release is at 09:40. A control-flow model that only checks “exemption exists somewhere in trace” would incorrectly accept it; R5 requires evidence of approval at or before release (`09:05` signature). TX-310 has a release reference to `EX-88` at 10:00 but the cert is at 10:30; sequence alone cannot distinguish backdated/late records.

3. **Material changes after review (R4).** TX-309 contains `Enhanced_Review` at 15:25 and `Update_Amount` at 15:28 with a +22.9 % increase. A pure activity-sequence checker sees “Enhanced_Review before Release_Funds” and approves, missing that R4 invalidates the review because the amount changed materially after it.

4. **Conditional activation (R1/R2/R3).** These rules are *data-conditioned*, not activity-conditioned. R1 activates because `jurisdiction=US` and `amount=125000` at release (TX-301). A process model without data attributes cannot know whether R1 applies to a given trace; the same sequence `Create -> Review -> Release` can be compliant in one case (low amount) and non-compliant in another (high amount).

5. **Missing data (R6).** TX-305 has blank `amount` at both review and release. A control-flow checker with no data layer sees a valid sequence (`Enhanced_Review` -> `Release_Funds`) and may mark it compliant. R6 requires that missing amount not be defaulted; without an amount payload, R1 is indeterminate.

6. **Same-timestamp ordering (R7).** In TX-311, `Enhanced_Review` and `Update_Jurisdiction` share `16:20`. Without `event_index`, the order is ambiguous; the correct order (review first, update second) changes whether R1 applies at release. A timestamp-only log cannot resolve tie-breakers required for state evolution.

Additionally, **review-type semantics** (Standard vs. Enhanced) and **packet-content evidence** (TX-307’s `Compliance_Approve` reviewing only a standard packet) are invisible to control-flow conformance, which treats all approval nodes identically.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload:** At `Release_Funds`, log an unmodifiable record (`release_payload`) containing `amount`, `jurisdiction`, `risk_level`, `customer_type`, `exemption_id`, and `rule_version`. This eliminates ambiguity from later settlement messages (TX-305).

- **Separate time dimensions for exemptions:** Log three timestamps for every exemption: (a) `approval_time` (when the head approved), (b) `effective_from` (when it takes effect), (c) `record_time` (DB insert), and (d) `signature_time` / `hash_valid_time` (cryptographic evidence). Do not rely solely on a displayed `approval` field.

- **Effective / record / evidence time metadata:** For every `Update_Amount`, `Update_Jurisdiction`, etc., include `update_source` and `update_provenance`. For reviews, embed `reviewed_amount`, `reviewed_jurisdiction`, and `reviewed_customer_type` directly in the event, so R4 comparison does not require reconstructing state.

- **Stable event ordering:** Guarantee monotonically increasing `event_index` within each case and enforce it at ingestion; do not allow out-of-order inserts without versioning.

- **Exemption scope fields embedded in case events:** When `Release_Funds` references `exemption_id`, include the claimed scope (`jurisdiction`, `customer_type`, `amount_max`) in the event for automated R5 scope matching.

- **Rule version tagging:** Add `rule_version` to each review and release event so that future changes to thresholds (e.g., R1 amount) do not retroactively alter historical evaluations.

- **Mandatory enhanced-review typing:** Distinguish `Standard_Review` and `Enhanced_Review` in both event names and payload metadata; include `packet_type` in `Compliance_Approve` so that approval of a standard packet cannot be mistaken for enhanced approval (TX-307).

- **Amount-change event explicit flag:** For `Update_Amount`, include `previous_amount` and `percent_change` fields, making R4 computation explicit rather than reconstructed.

- **Sanctions-list event ancestry:** Link `Sanctions_List_Update` to prior `Sanctions_Screen` events by `screen_id` or chain reference, simplifying R3 evaluation.
