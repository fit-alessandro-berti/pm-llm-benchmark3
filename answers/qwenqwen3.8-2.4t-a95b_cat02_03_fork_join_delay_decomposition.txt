# 1. Delay-decomposition definitions

Let case index be \(c\) and branch index be \(i \in \{A,B,C\}\).

Timestamps:

- \(a_c\) = `arrival`
- \(f_c\) = `fork_release`
- \(s_{ci}\) = branch \(i\) start timestamp
- \(e_{ci}\) = branch \(i\) completion timestamp
- \(fs_c\) = `final_start`
- \(fe_c\) = `final_end`

All durations below are in minutes.

## Abort assumptions made explicit

- **Assumption 1: AND-fork / AND-join.** `fork_release` is the earliest time any branch may begin, and `final_start` may begin only after all three branches complete. This is the Join semantics implied by the prompt.
- **Assumption 2: Branch queue starts at fork release.** A branch cannot queue before `fork_release`; any delay from `fork_release` to branch start is branch-specific queueing.
- **Assumption 3: Deterministic tie rule.** If two or more branches complete at the same `join_ready` time, report the critical branch in alphabetical order \(A \prec B \prec C\). This affects labels only, not elapsed time.

## Components

Upstream elapsed time before fork release:

\[
U_c = f_c - a_c
\]

Branch-specific queue waiting:

\[
Q_{ci} = \max(0, s_{ci} - f_c)
\]

In the supplied data no branch starts before `fork_release`, so \(\max(0,\cdot)\) does not change any value, but it makes the definition robust.

Branch active service:

\[
S_{ci} = e_{ci} - s_{ci}
\]

Branch elapsed time from fork release to branch completion:

\[
P_{ci} = Q_{ci} + S_{ci}
\]

Join ready time, not directly logged:

\[
J_c = \max_i e_{ci}
\]

Critical branch:

\[
\text{critical}_c \in \arg\max_i e_{ci}
\]

with the alphabetical tie rule above.

Branch-specific synchronization waiting after completion:

\[
W_{ci} = J_c - e_{ci}
\]

This is nonnegative under AND-join semantics.

Elapsed fork-join stage time:

\[
H_c = J_c - f_c = \max_i P_{ci}
\]

Downstream queueing before final activity \(F\):

\[
D_c = fs_c - J_c
\]

Final service:

\[
V_c = fe_c - fs_c
\]

Total case flow time:

\[
T_c = fe_c - a_c
\]

With the definitions above:

\[
T_c = U_c + H_c + D_c + V_c
\]

or equivalently:

\[
T_c = U_c + \max_i(Q_{ci}+S_{ci}) + D_c + V_c
\]

## Why summing all branch synchronization waits double counts

For every branch:

\[
Q_{ci} + S_{ci} + W_{ci} = H_c
\]

because each branch’s elapsed branch span plus its post-completion synchronization wait ends at the same join instant \(J_c\). Therefore:

\[
\sum_i W_{ci}
=
3H_c - \sum_i(Q_{ci}+S_{ci})
\]

This sum is not an elapsed duration. It represents parallel slack across multiple branches. It can even exceed the actual fork-join elapsed time. For example, in F07:

- \(H_c = 75\) minutes
- \(W_{C,A} + W_{C,B} + W_{C,C} = 25 + 0 + 52 = 77\) minutes

So adding all branch synchronization waits to a flow-time decomposition would double count, and in some cases more than double count, the same clock time. The non-double-counting elapsed decomposition must use only the maximum branch span \(H_c\), not the sum of branch spans or synchronization waits.

## Interpretation and influence ranking

### 1. B is the strongest branch-level controller

B is the most influential branch even though its mean service time is lower than A’s.

Evidence:

- B is the last-completing branch in 8 of 12 cases.
- B has the highest mean branch elapsed time, \(19.2 + 37.5 = 56.7\) minutes, compared with A’s constant 50 minutes.
- B has the largest tail: branch elapsed times of 75 minutes in F07 and F12, and 65 minutes in F03, F06, and F09.
- A 50% reduction in B queue delay produces a much larger estimated direct fork-join saving than a 20% reduction in A service time: 92.5 minutes aggregate versus 15 minutes aggregate under the counterfactual assumptions in Section 4.

This is the key distinction: A has the largest mean service time, but B has the largest mean queue-plus-service time and the largest variability. In a max-based join, variability and queue delay matter as much as service time.

### 2. A is second because it creates a stable floor

A is never queued in the observed data and always takes exactly 50 minutes. Therefore, it is critical only when B and C are unusually short:

- F01: B elapsed time is 45, so A at 50 is critical.
- F11: B elapsed time is 40, so A at 50 is critical.

A’s importance is not that it frequently dominates, but that it sets a 50-minute floor. If B is improved, A becomes the next limiting branch in several cases. This is visible in the B-queue counterfactual, where A becomes critical or co-critical after B queue reduction.

### 3. C is third overall, but it controls outlier cases

A and C both have 2 critical cases, so by critical-branch frequency they tie. However, their influence is not identical.

C has:

- low mean service time, about 20.2 minutes;
- the highest mean synchronization wait, 30.4 minutes;
- occasional queue spikes: 35 minutes in F04 and 25 minutes in F08.

The high synchronization wait does not mean C delays the process; it usually means C finishes early and waits for A or B. But when C’s queue spikes, it can become critical, as in F04 and F08. Thus C is not the primary controller, but it is a meaningful tail-risk contributor.

Honest tie statement: A and C tie on critical count. A is ranked above C for systemic control because A’s 50-minute constant span is a larger floor and limits the benefit of B improvements. C is ranked below A but should not be ignored because C queue spikes cause the only two C-critical cases.

# 4. Counterfactual redesign analysis

- **Assumption CF-1:** Only the targeted component changes. All other branch queues, branch services, upstream elapsed times, and final service times remain as observed.

A has the largest mean service time, but reducing A alone has small effect because A is usually not the path-limiting branch. Speeding a noncritical branch may produce no case-level benefit.

Secondary effects:

- If A capacity is freed, A could potentially accept earlier fork releases or reduce future A queueing, but no A queueing is observed in this data.
- If final station start times are fixed or congested, even the F01/F11 improvements may be absorbed as extra downstream waiting.

- New B elapsed time = \(S_B + 0.5 Q_B\).
- New fork-join elapsed time = \(\max(A\ elapsed, new\ B\ elapsed, C\ elapsed)\).

- F02, F03, F05, F06, F07, F09, F10, F12.
- Savings are not always equal to the B queue reduction because another branch can become critical.

Important capping effects:

- In F06, B elapsed falls from 65 to 50, so the saving is 15 minutes because A remains at 50.
- In F10, B elapsed falls from 55 to 45, but the fork-join max only falls to A’s 50, giving 5 minutes of saving.
- In F07 and F12, B remains critical but with reduced fork-join elapsed time of 60, saving 15 minutes each.

Cases with zero benefit:

- F01: A is critical and B is not close enough to matter.
- F04 and F08: C is critical because of C queue spikes.
- F11: A is critical.

Secondary effects:

- B queue reduction shifts control toward A in several cases.
- Earlier `join_ready` times may increase downstream queueing if final-station scheduling does not respond.
- If B queue reduction is achieved by adding B capacity, B resource utilization may rise and the bottleneck may move downstream or to A.

## CF3: Add final-station capacity or otherwise reduce downstream queueing

This counterfactual targets \(D_c = final\_start - join\_ready\).

Optimistic case: eliminate downstream queueing entirely.

- Direct saving equals observed downstream queue.
- Aggregate saving = 176 minutes.
- Mean saving = 14.67 minutes per case.

More conservative variant: reduce downstream queue by 50%.

- Aggregate saving = 88 minutes.
- Mean saving = 7.33 minutes per case.

Cases with zero benefit:

- None under full or 50% reduction, because every observed case has positive downstream queue.

But the nature of the downstream queue is uncertain. Using the observed final resource sequence as an interpretation, not as a proven cause:

- Some downstream waiting is consistent with a same-resource predecessor still being busy.
- Other downstream waiting is not explained by the observed two-resource sequence and may reflect release policy, batching, administrative holds, or synchronized decision making.

Under that interpretation, only part of the 176 minutes may be removable by physical capacity alone. If the remaining waiting is policy-related, adding another final resource may not eliminate it. A scheduling or release-policy redesign may be required.

Masking effect:

- If branch improvements make cases ready earlier but final start times do not move earlier, downstream queueing increases and total flow time may not improve.
- Therefore, final-station pull or release synchronization can be a prerequisite for realizing branch-stage improvements.

# 5. Recommended redesigns and risks

## Redesign 1: Reduce and stabilize B queue delay

Recommended intervention: reduce B queue delay by at least 50%, for example by reserved B capacity, better batch release timing, priority dispatch for B, or load leveling into unused B slots.

### Throughput

B is the branch that most often determines `join_ready`. Reducing B queue delay should reduce the fork-join stage length and could increase completed-case throughput if the final station can absorb earlier joins. However, throughput improvement is not guaranteed unless final-station holds or final queueing do not absorb the gain.

### Flow-time tail

This redesign directly targets the worst observed fork-join cases:

- F07: estimated fork-join saving of 15 minutes.
- F12: estimated fork-join saving of 15 minutes.
- F06: estimated saving of 15 minutes.
- F09: estimated saving of 12.5 minutes.

Because B produces the highest tail branch elapsed times, reducing B queue delay should reduce the right tail of total flow time.

### Resource utilization

B utilization may increase if queue delay is reduced by adding capacity or prioritizing B. If B currently has hidden idle periods due to batching or setup, better scheduling may improve both flow time and utilization. Because branch resource calendars are not in the data, the exact B capacity effect cannot be verified.

### Possible new bottlenecks

A becomes more exposed after B queue reduction. A’s constant 50-minute span becomes the floor in several cases, including F02, F05, F06, and F10 under the 50% B-queue reduction counterfactual. If B is improved further, reducing A service time may become more valuable.

### Synchronization effects

A and C synchronization waits would generally decrease because `join_ready` occurs earlier. However, if final dispatch is not changed, some synchronization waiting may simply move from the fork-join stage to the downstream stage.

### What to pilot or measure first

Pilot B queue reduction on a subset of cases and measure:

- B queue time distribution.
- Frequency of B as critical branch.
- Fork-join elapsed time.
- `final_start - join_ready`, to detect whether gains are absorbed downstream.
- Total flow time and its upper tail.

## Redesign 2: Implement final-station pull or release synchronization

Recommended intervention: start the final decision as soon as `join_ready` occurs when a final resource is available, instead of holding cases downstream. This may involve removing batch release rules, cross-training F1/F2, or adding capacity only if resource-bound waiting is confirmed.

### Throughput

The final station has two resources and final service time is constantly 20 minutes. Pure final-service capacity does not appear to be the only limitation, because some downstream waiting is not explained by prior final-resource occupancy. If downstream waiting is caused by policy or synchronization rules, a pull policy may improve throughput without adding physical capacity.

### Flow-time tail

Downstream queueing is the second-largest average reduction opportunity after the fork-join stage:

- Mean downstream queue = 14.7 minutes.
- Largest observed downstream queues are 20 minutes in F10 and F11, and 18 minutes in F04.

Reducing downstream queueing can reduce total flow time directly and can also make branch-stage improvements visible.

### Resource utilization

If final resources currently wait for scheduled release windows, a pull policy may make their work pattern more continuous. This may increase observed utilization, but it may also reduce deliberate buffer time. If buffers exist for quality or documentation reasons, removing them may create compliance risk.

### Possible new bottlenecks

If downstream waiting is reduced, the fork-join stage becomes the dominant visible bottleneck. That increases the importance of B queue control and, later, A service time. If B remains unstable, final resources may experience more variable arrivals.

### Synchronization effects

This redesign directly reduces post-join waiting. It does not reduce branch synchronization waiting among A, B, and C, but it prevents branch-stage improvements from being hidden after the join.

### What to pilot or measure first

Before adding a third final resource, pilot a pull rule and measure:

- `final_start - join_ready`.
- Split downstream waiting into resource-availability waiting and unexplained hold time.
- Final resource idle time and busy time.
- Whether earlier final starts create quality, documentation, or decision-quality issues.
- Whether branch-stage improvements translate into total flow-time improvements.

# 7. Limits of inference

Several important concluding points cannot be identified from the supplied timestamps alone.

## Causality is not proven

The decomposition describes observed timing relationships under an assumed AND-fork / AND-join model. It does not prove that reducing B queue delay or downstream queueing would cause the estimated savings. The counterfactuals are model-based estimates, not observed interventions.

## Branch resource capacity is not observed

The data show branch start and completion times, but they do not show:

- how many A, B, or C resources exist;
- whether branches can run in parallel across cases;
- whether queueing is caused by capacity, setup, batching, priority rules, or resource absence;
- whether service times include waiting inside the branch activity.

Therefore, the recommendation to reduce B queueing should be tested with resource data or a pilot.

## Work preemption and internal branch waiting are not visible

The timestamps define only branch start and end. They do not show whether work was continuous, preempted, interrupted, or partially blocked inside the branch. `branch_service` here is start-to-end duration, not necessarily pure value-added processing time.

## Final-station waiting may not be a pure capacity queue

`final_start - join_ready` is interpreted as downstream queueing under the model assumptions. However, it could include:

- scheduled release windows;
- batching of release decisions;
- administrative handoffs;
- quality or documentation checks;
- deliberate synchronization with F1/F2 availability;
- policy rules unrelated to physical capacity.

The observed final service time is constant at 20 minutes and the final station has two resources, so physical final-service capacity alone may not explain all downstream waiting.

## One-minute timestamp precision

All times are accurate to one minute. Very short waits, exact ties, sub-minute ordering, and small counterfactual effects may be obscured.

## Small sample

There are 12 cases from one day. The rankings and means are indicative, but statistical confidence is limited. Tail behavior, especially for B and C queue spikes, should be validated on a larger sample before major redesign investment.
