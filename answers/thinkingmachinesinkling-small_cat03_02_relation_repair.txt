## 8. Over-repair warnings

1. **Forcing `ev08` to `PK-7`:** If a repairer ignores `scanner_ref=PK8-2` and assigns the item to the only other package (`PK-7`), `PK-7` would contain two different items with different scanner prefixes, destroying the scanner-to-package mapping and creating false double-pack events in the DFG.
2. **Forcing `ev11` to `DEL-Y` as the unique delivery:** Assigning `CONFIRM DELIVERY` exclusively to `DEL-Y` (N-421) would require ignoring the stronger `PK-7``DEL-X` life chain and inventing a direct link between `ORD-A` and `PK-8` that does not exist in the event table.
3. **Using `230 = 130 + 100` as proof of `INV-44` billing both orders:** This is arithmetic over-repair. If the invoice actually includes taxes, shipping fees, or a third unlogged order, adding `ORD-B` to `ev12` creates false attribution and corrupts the `Issue Invoice`  `Order` cardinality in the OTG.
4. **Creating `O2O DEL-Y carries PK-8` and then using it to “confirm” `ev10`:** This introduces circularity. The O2O is derived solely from the E2O event reference; it provides no independent confirmation. Treating it as corroboration in a process model would falsely boost confidence in the repair.
5. **Completing `ORD-B` by inventing missing events or forced relations:** For example, adding `ev12``ORD-B` and `PAY-2``INV-44` without event-level evidence produces an artificially symmetric process. The flattened `Order` trace for `ORD-B` would then mirror `ORD-A`, hiding the true partial-state evidence that one order completed faster or was recorded differently.
6. **Treating `PK-8` as a single-item package:** If `PK-8` is forced to contain only `IT-A2` (rejecting `IT-B1`), then `IT-B1` becomes permanently unpacked. But if `PK-8` is forced to contain both without accepting `ev08`, the package weight (2.9) might be inconsistent—though weights are approximate, aggressive repair might invent false inventory logic.

These warnings underscore that **uncertainty preservation is a feature**, not a failure, of the dataset. The conservative repair (Bundle A) keeps the process realistic: some objects have full lifecycles, others have fragments, and arithmetic matches remain heuristics rather than axioms.
