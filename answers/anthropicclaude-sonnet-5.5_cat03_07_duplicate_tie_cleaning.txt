## 1. Duplicate-handling decision tree

Rules are evaluated in order, and the first match wins. Equal activity plus equal timestamp only makes an event a *candidate*, never a duplicate. Pairs with different activities (e.g. e09/e10) are not duplicate candidates and go straight to ordering.

- **Q1. Same source, same `source_event_key` (or `source_seq`), same activity, timestamp and relations?**
  - Payload hash identical  **T1 exact technical duplicate: DROP** the later copy and log it.
  - Key identical but payload or relations differ  **T7 key collision or versioned update: QUARANTINE.**
- **Q2. Is the harmonized label shared although `original_activity` has different semantics?**  **T4 harmonization collision: RETAIN BOTH with refined labels or qualifiers.** Shared objects are irrelevant here.
- **Q3. Do the events differ in a discriminating object type (Item, Payment)?**  **T5 concurrent same-label events: RETAIN BOTH UNCHANGED.**
- **Q4. Is there independent evidence of one business transition, and are the E2O sets type-compatible?** Evidence means a reconciliation report, a shared business key, or a message ID.  **T2 same physical event seen by several systems: MERGE attributes and relations.** The merge uses an attribute-authority map, and conflicts are logged.
- **Q5. Is one event coarser and derived from another (object subset, "generated from message")?**
  - Single proven parent  **T3a.** The conservative scenario RETAINS BOTH, with a refined label and `abstraction_level=summary`. The evidence-based scenario MERGES the summary into the detail event as an observation.
  - Several parents, or no object linking it to one parent  **T3b: RETAIN BOTH with a refined label.** Never merge into a single parent, and record `derived_from` in provenance.
- **Q6. Anything else  T6 unresolved: QUARANTINE.** Both events stay in the analytic log, flagged and unmerged, and go to a review queue.

| e09/e10 | Different activities, e09 known to precede e10 | Retain unchanged, order constraint e09<e10 | Very high | e09, e10 | None | None | Own rows | Same-second timestamps misread as duplicates |
| e11/e16 | Same invoice issuance V1 (fact 6) | T2 merge | High (0.9) | e11 | Per-attribute authority: ERP for ERP fields, BILLING for billing fields; conflicts logged | Union (O1, V1) | Both rows, including B-9 | Invoice-lifecycle granularity differs between systems |
| e13/e14 | Two captures, M1 vs M2 | T5 retain unchanged | Very high (0.95) | e13, e14 | None | None | Own rows | `have_common_object` merge fabricates one capture |
| e13/e15 | ERP balance summary after payment messages; no Payment object | T3b retain both; e15 relabelled "Update Invoice Balance (ERP)" | Medium-high (0.8) | e13, e15 | None | Never add M1 to e15 | `derived_from` in audit | Merging attributes M1 alone to an aggregate |
| e14/e15 | As above, for M2 | T3b retain both | Medium-high | e14, e15 | None | Never add M2 to e15 | `derived_from` = e13, e14 | e15 cannot be attributed to a single payment |

Variant: if e15 is demoted to an invoice-level attribute sidecar, it leaves the event table but stays in provenance. If a reviewer doubts e11/e16, keep both with qualifiers.

## 3. Timestamp-tie ordering rules

Within each tie group, build a DAG from the rules below, then run a topological sort. The sort picks the lowest fallback key among available nodes. A cycle means the group is quarantined, not forced.

1. **Domain constraints (semantic).** Facts: e09<e10, e12<e13, e12/e13/e14<e15, and ERP summary after WMS message (e06e07). Assumptions, flagged `basis=assumption`: Pick before Pack for shared items, and e08 before e09.
2. **Within-source sequence (semantic only in restricted cases).** It applies only inside one source, never across sources, and only when the events share a lifecycle object (Item, Package, Delivery, Payment). The e13/e14 PSP sequence is deterministic only, because the events concern different Payments.
3. **Lifecycle on shared objects (semantic):** I1/I2 picked before packed, and M1 authorized before captured.
4. **Source-specific semantics (semantic):** summaries follow their details, and carrier acceptance precedes handover.
5. **Ingestion time (deterministic only).** It breaks ties among still-unordered events and never overrides rules 1–4.
6. **Stable fallback (deterministic):** (`source`, `source_seq`, `source_event_key`, `eid`).

Each event gets `order_basis`  {constraint, fallback}. A total order is a reproducible linearization, not evidence of physical order.

**Why early microseconds mislead.** Adding microseconds before deciding semantics asserts strict precedence that the data never showed. If added by ingestion or source order, it can place e15 before e13 or scanner before WMS, and the false order then looks like real data. It creates non-zero durations, such as AuthorizeCapture lasting microseconds. It also breaks later duplicate detection, because equal timestamps no longer match. Keep `original_timestamp`, and use synthetic deltas only in an ordering-only view.

**Intended orders (conservative dataset):**
- **10:00:** e03(+e04)  e05  e06  e07.
  - Constraints: e03<e06, e05<e06, e06e07.
  - The other admissible order is e05, e03, e06, e07.
  - If e06/e07 are merged: e03, e05, e06.
- **10:15:** e08  e09  e10.
  - Only e09<e10 is factual.
  - Admissible alternatives: e09, e08, e10, or e09, e10, e08 if the release assumption is dropped.
- **12:00:** e11(+e16)  e12  e13  e14  e15.
  - Constraints: e12<e13, e11<e15 by ERP seq 40<41, and e12/e13/e14<e15.
  - e11 may sit anywhere before e15, and e14 anywhere before e15. e13 and e14 are genuinely concurrent.
  - Without merging, e16 would follow e11 by ingestion fallback only.

## 4. Conservative cleaning pipeline

1. Snapshot raw. Add `original_timestamp`, `original_activity`, `canonical_eid` and `merged_from`.
2. Pre-check candidate groups (activity, timestamp, key, object sets, differing Item or Payment).
3. Drop exact technical duplicates only. None exist here, since all (source, key) pairs are unique, so the guarded drop is a no-op.
4. Merge verified pairs e03/e04 and e11/e16 with conflict-preserving rules.
5. Refine labels for e07, e08, e09 and e15, keeping originals.
6. Assign `order_rank`, sort by it, and optionally build a separate index-timedelta view.
7. Validate referential integrity.

Events: 17  2 = **15**. E2O relations: 44  3  2 = **39**. Legitimate concurrency is untouched: e03 and e05, e13 and e14, and all abstraction-level events remain.

## 5. Aggressive alternatives

**B. Evidence-based semantic merging.** This is A plus the e06/e07 merge, conditional on a message-ID link. e15 is either retained (**14 events, 37 E2O**) or demoted to a sidecar (13 events, 35 E2O). Likely damage: if the link is wrong, a real ERP-level transition disappears. ERP-side latency, such as the 60 s ingestion lag, also becomes invisible.

**C. Mechanical PM4Py merging.** `ocel_merge_duplicates(have_common_object=True)` merges:
- e03/e04/e05 into one event;
- e06/e07;
- e08/e09;
- e11/e16;
- e13/e14/e15.

The result is **10 events** and about **28 E2O** (union, version-dependent). Damage:
- I1 and I2 are "picked together".
- The carrier-acceptance step vanishes.
- One capture event relates to M1, M2, O1 and V1.
- Attributes of non-first rows are lost.

Variant C2: `ocel_drop_duplicates` on the whole OCEL removes duplicate activity/timestamp/object relation rows. As documented, it would strip e05 of O1 and P1, and empty e04, e09 and e16 (about 28 E2O). Verify this on your PM4Py version.

**Why `have_common_object=True` does not protect e13/e14.** It only tests whether any object is shared. e13 and e14 share O1 and V1, but differ in the discriminating objects M1 and M2. Here O1 belongs to all 17 events, so the flag is trivially true and behaves like False. A safe guard compares objects type by type, for Item and Payment at least, and requires independent evidence.

## 6. PM4Py-oriented Python implementation

```python
import copy, heapq, json
import pandas as pd
import pm4py

EID, OID, ACT, TS, QUAL = "ocel:eid","ocel:oid","ocel:activity","ocel:timestamp","ocel:qualifier"
STRICT_TYPES    = {"Item", "Payment"}                        # discriminate concurrent same-label events
LIFECYCLE_TYPES = {"Item", "Package", "Delivery", "Payment"}
PROTECTED = {EID, TS, ACT, "original_timestamp", "original_activity",
             "canonical_eid", "merged_from", "refined_activity"}
RULE_VERSION = "v1.0"
audit = []

def clone(o): return copy.deepcopy(o)

def sync_relations(o):                       # relations carry copies of activity/timestamp
    e = o.events.drop_duplicates(EID).set_index(EID)
    o.relations[ACT] = o.relations[EID].map(e[ACT]).values
    o.relations[TS]  = o.relations[EID].map(e[TS]).values
    return o

def add_provenance(o):
    o = clone(o); ev = o.events
    ev["original_timestamp"] = ev[TS]; ev["original_activity"] = ev[ACT]
    ev["refined_activity"] = ev[ACT]; ev["canonical_eid"] = ev[EID]; ev["merged_from"] = ev[EID]
    return o

prov = add_provenance(ocel_raw)              # ocel_raw is never modified

# ---------- pre-check of candidate groups (inspect BEFORE any dedup call) ----------
def precheck(o):
    ev = o.events
    objs = o.relations.groupby(EID)[OID].agg(lambda s: tuple(sorted(s)))
    typ = o.objects.set_index(OID)["ocel:type"]
    rows = []
    for (ts, act), g in ev.groupby([TS, ACT]):
        if len(g) < 2: continue
        ids = list(g[EID])
        differs = any(len({tuple(x for x in objs[i] if typ[x] == t) for i in ids}) > 1
                      for t in STRICT_TYPES)
        rows.append(dict(ts=ts, activity=act, eids=ids, sources=sorted(g["source"].unique()),
                         same_key=g.duplicated(["source", "source_event_key"], keep=False).any(),
                         identical_objects=len({objs[i] for i in ids}) == 1,
                         differing_item_or_payment=differs))
    return pd.DataFrame(rows)

print(precheck(prov))       # e.g. e03/e04/e05: differing items -> NOT an exact-duplicate group

EXACT_KEYS = ["source", "source_event_key", ACT, TS, "payload_hash"]
exact_eids = prov.events[prov.events.duplicated(EXACT_KEYS, keep=False)][EID].tolist()  # [] here

def subset(o, eids):
    s = clone(o)
    s.events = s.events[s.events[EID].isin(eids)].copy()
    s.relations = s.relations[s.relations[EID].isin(eids)].copy()
    s.objects = s.objects[s.objects[OID].isin(s.relations[OID])].copy()
    return s

def drop_exact_only(o, eids):
    """ocel_drop_duplicates works on activity/timestamp/object relation rows, so it is
    applied ONLY to a subset holding true technical duplicates, never the whole OCEL."""
    if not eids: return o
    part = pm4py.ocel_drop_duplicates(subset(o, eids))
    gone = set(eids) - set(part.relations[EID])
    out = clone(o)
    out.events = out.events[~out.events[EID].isin(gone)]
    out.relations = out.relations[~out.relations[EID].isin(gone)]
    audit.extend(dict(source_event_ids=[e], merge_rule="R0-exact", action="drop",
                      rule_version=RULE_VERSION) for e in gone)
    return out

# ---------- verified-pair merge ----------
def merge_verified_pairs(o, pairs):
    out = clone(o)
    typ = out.objects.set_index(OID)["ocel:type"]
    strict = lambda s: {x for x in s if typ[x] in STRICT_TYPES}
    for p in pairs:
        c, ds = p["canon"], p["dups"]; ids = [c] + ds
        ev = out.events.set_index(EID, drop=False)
        if not set(ids) <= set(ev.index): continue
        objs = {i: set(out.relations.loc[out.relations[EID] == i, OID]) for i in ids}
        compat = all(strict(objs[d]) == strict(objs[c]) if p["mode"] == "same"
                     else strict(objs[d]) <= strict(objs[c]) for d in ds)
        if ev.loc[ids, TS].nunique() != 1 or not compat:
            audit.append(dict(source_event_ids=ids, merge_rule=p["rule"], action="quarantine",
                              reason="timestamp/object incompatibility")); continue
        conflicts = {}
        for d in ds:
            for col in out.events.columns:
                if col in PROTECTED: continue
                cv, dv = ev.at[c, col], ev.at[d, col]
                if pd.isna(cv) and pd.notna(dv):
                    out.events.loc[out.events[EID] == c, col] = dv       # fill gaps
                elif pd.notna(dv) and cv != dv:
                    conflicts.setdefault(col, {})[d] = str(dv)           # keep as conflict
        rel = out.relations
        rel.loc[rel[EID].isin(ds), EID] = c
        out.relations = rel.drop_duplicates([EID, OID, QUAL])            # union of E2O
        out.events.loc[out.events[EID] == c, "merged_from"] = "|".join(ids)
        out.events = out.events[~out.events[EID].isin(ds)]
        audit.append(dict(canonical_eid=c, source_event_ids=ids, merge_rule=p["rule"],
                          confidence=p["conf"], reason=p["reason"], rule_version=RULE_VERSION,
                          original_activity=ev.loc[ids, "original_activity"].tolist(),
                          discarded_conflicts=json.dumps(conflicts),
                          source_rows=ev.loc[ids].astype(str).to_dict("records")))
    return sync_relations(out)

def refine_labels(o, mapping, rule):
    out = clone(o)
    for eid, new in mapping.items():
        m = out.events[EID] == eid
        if m.any():
            audit.append(dict(canonical_eid=eid, merge_rule=rule, action="relabel",
                              original_activity=out.events.loc[m, "original_activity"].iloc[0],
                              refined_activity=new, rule_version=RULE_VERSION))
            out.events.loc[m, [ACT, "refined_activity"]] = new
    return sync_relations(out)

# ---------- ordering ----------
HARD_EDGES = [("e03","e06","fact/lifecycle"), ("e05","e06","fact/lifecycle"),
              ("e06","e07","fact"), ("e08","e09","assumption"), ("e09","e10","fact"),
              ("e12","e13","fact"), ("e11","e15","ERP seq"), ("e12","e15","fact"),
              ("e13","e15","fact"), ("e14","e15","fact")]

def assign_order(o, edges):
    out = clone(o); ev = out.events
    alias = {x: r[EID] for _, r in ev.iterrows() for x in str(r["merged_from"]).split("|")}
    objs = out.relations.groupby(EID)[OID].agg(set)
    typ = out.objects.set_index(OID)["ocel:type"]
    ing = pd.to_datetime(ev["ingested_at"].astype(str), errors="coerce").fillna(pd.Timestamp.max)
    key = {e: (t, s, q, k, e) for e, t, s, q, k in
           zip(ev[EID], ing, ev["source"], ev["source_seq"], ev["source_event_key"])}
    rank, basis, n = {}, {}, 0
    for ts, g in ev.groupby(TS, sort=True):
        ids = list(g[EID]); succ = {i: set() for i in ids}
        indeg = dict.fromkeys(ids, 0); constrained = set()
        def add(a, b):
            a, b = alias.get(a, a), alias.get(b, b)
            if a in succ and b in succ and a != b and b not in succ[a]:
                succ[a].add(b); indeg[b] += 1; constrained.update([a, b])
        for a, b, _ in edges: add(a, b)
        for _, s in g.groupby("source"):                  # within-source only
            rows = s.sort_values("source_seq")[EID].tolist()
            for i, a in enumerate(rows):
                for b in rows[i+1:]:
                    if {x for x in objs[a] & objs[b] if typ[x] in LIFECYCLE_TYPES}:
                        add(a, b)
        heap = [(key[i], i) for i in ids if indeg[i] == 0]; heapq.heapify(heap); seq = []
        while heap:                                       # fallback key is deterministic only
            _, i = heapq.heappop(heap); seq.append(i)
            for j in sorted(succ[i]):
                indeg[j] -= 1
                if indeg[j] == 0: heapq.heappush(heap, (key[j], j))
        if len(seq) != len(ids):
            raise ValueError(f"cycle at {ts}: quarantine group {ids}")
        for i in seq:
            rank[i] = n; basis[i] = "constraint" if i in constrained else "fallback"; n += 1
    ev["order_rank"] = ev[EID].map(rank); ev["order_basis"] = ev[EID].map(basis)
    out.relations["order_rank"] = out.relations[EID].map(rank)
    return out

def sort_ordered(o):
    return pm4py.ocel_sort_by_additional_column(clone(o), "order_rank")

# ---------- validation ----------
def guard_one_payment_per_event(o):
    pay = set(o.objects.loc[o.objects["ocel:type"] == "Payment", OID])
    cnt = o.relations[o.relations[OID].isin(pay)].groupby(EID)[OID].nunique()
    return cnt[cnt > 1].index.tolist()

def validate(o, name, strict_prov=True):
    ev, rel, ob = o.events, o.relations, o.objects; bad = []
    if not ev[EID].is_unique: bad.append("duplicate eid")
    if not set(rel[EID]) <= set(ev[EID]): bad.append("E2O -> missing event")
    if not set(ev[EID]) <= set(rel[EID]): bad.append("event without E2O")
    if not set(rel[OID]) <= set(ob[OID]): bad.append("E2O -> missing object")
    if rel.duplicated([EID, OID, QUAL]).any(): bad.append("duplicate E2O")
    if not (rel[EID].map(ev.set_index(EID)[ACT]) == rel[ACT]).all(): bad.append("activity out of sync")
    if strict_prov:
        for c in ["original_timestamp", "original_activity", "source", "source_event_key"]:
            if c not in ev or ev[c].isna().any(): bad.append(f"lost {c}")
    mp = guard_one_payment_per_event(o)
    if mp: bad.append(f"events with >1 Payment: {mp}")
    print(name, len(ev), len(rel), bad or "OK")
    return bad

# ---------- scenario A: conservative ----------
PAIRS_STRONG = [
  dict(canon="e03", dups=["e04"], mode="same", rule="R2-recon", conf=.95, reason="reconciliation report: same scan"),
  dict(canon="e11", dups=["e16"], mode="same", rule="R2-invoice-no", conf=.90, reason="same invoice V1")]
REFINE_A = {"e07": "Record Pack Status (ERP)", "e08": "Release Package from Warehouse",
            "e09": "Accept Package by Carrier", "e15": "Update Invoice Balance (ERP)"}

stage1 = merge_verified_pairs(drop_exact_only(prov, exact_eids), PAIRS_STRONG)
A = sort_ordered(assign_order(refine_labels(stage1, REFINE_A, "R4-label"), HARD_EDGES))
A_view = pm4py.ocel_add_index_based_timedelta(clone(A))   # ordering view ONLY; timestamps synthetic
# Durations must use original_timestamp, never A_view["ocel:timestamp"].

# ---------- scenario B: evidence-based (needs confirmed message-ID link) ----------
PAIRS_EVIDENCE = [dict(canon="e06", dups=["e07"], mode="summary", rule="R3-derived-summary",
                       conf=.60, reason="ERP status generated from WMS message")]
B = merge_verified_pairs(stage1, PAIRS_EVIDENCE)
B = refine_labels(B, {k: v for k, v in REFINE_A.items() if k != "e07"}, "R4-label")
B = sort_ordered(assign_order(B, HARD_EDGES))

# ---------- scenario C: mechanical (WARNING) ----------
# WARNING: merges ALL same activity+timestamp events sharing ANY object (O1 is in every event).
# It merges e05 into e03/e04, e14 into e13, e09 into e08, and loses non-first attributes/provenance.
C = pm4py.ocel_merge_duplicates(clone(prov), have_common_object=True)

for name, o, strict in [("raw", prov, True), ("A", A, True), ("B", B, True), ("C", C, False)]:
    validate(o, name, strict)        # C is expected to fail the payment guard
pd.DataFrame(audit).to_json("audit_trail.json", orient="records", default_handler=str)
```

## 7. Sensitivity analysis

Counts (events / E2O): raw 17/44, conservative 15/39, evidence-based 14/37 (13/35 with e15 demoted), aggressive library 10/28.

- **Order-flattened DFG.**
  - Raw contains PickPick, PackPack, DispatchDispatch, Issue InvoiceIssue Invoice, and CaptureCapture loops.
  - Conservative keeps PickPick (I1 then I2) and CaptureCapture (M1 then M2). These are legitimate multiplicity, but the flattening hides it. It adds PackRecord Pack Status and ReleaseAcceptHandover.
  - Evidence-based drops the PackRecord Pack Status edge.
  - Aggressive loses Release/Accept and the Pick/Capture multiplicity, leaving one Capture node.
- **Item-flattened DFG.**
  - Raw I1 has a PickPickPack artifact.
  - Conservative and evidence-based give PickPack for both I1 and I2.
  - Aggressive gives both items the same merged Pick event.
- **Payment-flattened DFG.**
  - M1 is AuthorizeCapture in every dataset except aggressive, where the merged Capture also belongs to M2.
  - M2 is Capture only, because the data has no authorization for it. e15 is absent because it has no Payment.
  - Aggressive makes M2 look co-captured with M1.
- **OC-DFG edges and frequencies.** Event-couple counts fall after merging (e.g. CaptureCapture in Invoice/Order). Unique-object counts stay similar. Aggressive merging decouples the two metrics, so a single event carries two payments.
- **ET–OT weights.**

| Pair | Raw | Conservative | Aggressive |
|---|---|---|---|
| Pick Item–Item | 3 | 2 | 1 (one event, two items) |
| Issue Invoice–Invoice | 2 | 1 | 1 |
| Capture Payment–Payment | 2 | 2 | 1 (one event, two payments) |

  Also: Capture–Invoice is 3 raw and 2 conservative, plus a separate Update Balance–Invoice edge of 1. Pack–Package is 2 raw, then 1 plus Record Pack Status–Package 1.
- **OTG relations.** Type-level edges (Order–Item, Package–Delivery, Invoice–Payment) are nearly unchanged, but their weights shrink. Aggressive merging creates Payment–Payment co-occurrence (M1–M2), and "I1 and I2 picked together" at the object level.
- **Rework and loops.** Raw has five spurious self-loops. Conservative keeps only true multi-object repetition. Evidence-based removes the pack loop. Aggressive hides real repetition.
- **Lifecycle and performance.**
  - PickDispatch (15 min) and DispatchConfirm Delivery are stable in all datasets.
  - Zero-second steps stay zero unless synthetic deltas are used.
  - Ingestion lags, such as e15 at 60 s, are not business durations.
  - Aggressive loses the ReleaseAccept and AuthorizeCapture intervals.

Concrete edges or patterns whose interpretation changes:
1. Pick ItemPick Item.
2. Pack PackagePack Package vs Pack PackageRecord Pack Status (ERP).
3. Dispatch PackageDispatch Package vs ReleaseAcceptHandover.
4. Issue InvoiceIssue Invoice.
5. Capture PaymentCapture Payment (concurrent M1/M2) vs Capture PaymentUpdate Invoice Balance.
6. The Authorize PaymentCapture Payment edge for M1, and M2's missing authorization.
7. The Payment–Payment co-occurrence that appears only in aggressive merging.

## 8. Audit trail and reversibility

Keep four tables:
- **`event_provenance`:** canonical_eid, source_event_ids, merge_rule, rule_version/reviewer, confidence, reason, original_activity, refined_activity, original_timestamp, adjusted_timestamp (null unless an ordering view was used), order_rank, order_basis.
- **`attribute_provenance`:** canonical_eid, attribute, value, source_eid, chosen flag, conflict_reason. This records which source each retained attribute came from and what was discarded.
- **`relation_provenance`:** canonical_eid, oid, qualifier, contributing_eids, action.
- **`raw_snapshot`:** immutable events and relations with a hash.

To reconstruct the raw view, load `raw_snapshot`. For a scenario, remove its canonical rows, restore the rows listed in `source_event_ids`, reset `ocel:activity` from `original_activity` and `ocel:timestamp` from `original_timestamp`, and drop ordering columns. A hash comparison against the snapshot verifies the round trip.

## 9. Failure modes and safeguards

1. **Collapsing M1/M2 partial payments.** Safeguard: strict type-wise object equality plus `guard_one_payment_per_event`.
2. **Turning abstraction-level updates into false rework.** Safeguard: `abstraction_level` and refined labels.
3. **Ordering by ingestion time.** It can put e15 or e16 before their causes. Safeguard: ingestion is used only as a late deterministic tie-breaker.
4. **Treating shared objects as proof of duplication.** Safeguard: Q2/Q3 run before Q4 and require independent evidence.
5. **Unioning incompatible E2O relations.** Safeguard: compatibility check, with quarantine on failure.
6. **Synthetic microseconds changing durations.** Safeguard: durations come from `original_timestamp`, and deltas exist only in a separate view.
7. **Losing source-authoritative attributes.** Safeguard: an authority map and logged conflicts.
8. **Applying duplicate functions to the whole OCEL.** Safeguard: pre-check, and use on a subset only.
9. **Stale relation copies after relabelling.** Safeguard: `sync_relations` and the validation check.
10. **Cross-source `source_seq` comparison** (e.g. scanner 551 vs WMS 100). Safeguard: sequence is used within a source only.
11. **Cyclic constraints forced into a total order.** Safeguard: the group is quarantined.
12. **Overconfident merges of summaries.** Safeguard: the e06/e07 merge requires a message-ID link, and e15 is never merged into a single payment.
