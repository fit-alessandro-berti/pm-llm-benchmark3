*Discussion on DFG and Concurrency:* The frequency DFG shows both `Credit Check -> Engineering Review` (17 times) and `Engineering Review -> Credit Check` (11 times). While this bidirectional footprint is a classic symptom of concurrency, by itself, it does not prove actual parallel execution; it could theoretically represent an exclusive choice (XOR) between two strict sequences. However, statement S2 confirms that the checks actually run in parallel, which is what causes the arbitrary completion-order linearizations seen in the log.

# 2. Shared Assumptions

- **Event-completion semantics**: Because we only have completion timestamps (D7, S7), we assume activities are modeled as atomic transitions. Any true overlapping duration is abstracted into interleaved completion events.
- **Missing vs. Skipped Supplier Confirmation**: Because the external/stocked attribute is missing (S5) and 5–10% of SC events are dropped due to integration issues, we cannot deterministically predict when SC should occur based on data attributes. We assume SC can be modeled structurally as a non-deterministic choice (XOR with a silent transition, `tau`), acknowledging this abstracts away the missing data routing logic.
- **Optionality representation**: Optional activities (Supplier Confirmation, Expedite Review) are structurally modeled as an XOR block containing the activity and a silent transition (`tau`).
- **Data Quality Filtering**: S1 (Finance manager) is explicitly contradicted by the log (where ER finishes before CC 11 times) and by S2. We assume S1 is a desired policy rather than a systemic constraint and discard it for modeling purposes.

# 3. Conservative Candidate

**Inductive-bias statement**: The conservative model strictly limits behavior to the exact sequences observed in the event log. It assumes the log is a completely representative sample of all permissible behavior and treats unseen interleavings as forbidden. By using an XOR enumeration of the 7 variants, it avoids any risk of accepting unobserved sequences, but results in a highly duplicated, unscalable model that treats concurrency as mutually exclusive sequential paths.

**Compact formal expression**:
$M_{cons} = \bigoplus_{i=1}^{7} \sigma_i$
(where $\sigma_i$ is the exact sequence of activities for variant $i$).

**PM4Py Code**:
```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def make_sequence(acts):
    return ProcessTree(operator=Operator.SEQUENCE, children=[ProcessTree(label=a) for a in acts])

v1 = make_sequence(["Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case"])
v2 = make_sequence(["Register Order", "Engineering Review", "Credit Check", "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case"])
v3 = make_sequence(["Register Order", "Credit Check", "Engineering Review", "Approve Configuration", "Release Production", "Archive Case"])
v4 = make_sequence(["Register Order", "Engineering Review", "Credit Check", "Approve Configuration", "Release Production", "Archive Case"])
v5 = make_sequence(["Register Order", "Credit Check", "Supplier Confirmation", "Engineering Review", "Approve Configuration", "Release Production", "Archive Case"])
v6 = make_sequence(["Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation", "Expedite Review", "Approve Configuration", "Release Production", "Archive Case"])
v7 = make_sequence(["Register Order", "Engineering Review", "Credit Check", "Expedite Review", "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case"])

model_conservative = ProcessTree(operator=Operator.XOR, children=[v1, v2, v3, v4, v5, v6, v7])
```

**List of behavior deliberately excluded**:
- Any interleaving of CC, ER, SC, and EX not explicitly seen in the 7 variants (e.g., `RO -> CC -> ER -> EX -> AC...` without SC).
- True concurrency semantics (partial orders).

**List of known underfitting risks**:
- **Severe Overfitting / Poor Generalization**: By explicitly enumerating variants, the model fails to capture the underlying process logic.
- **Duplicate Labels & Scalability**: CC, ER, SC, and EX are duplicated across up to 7 branches. If the log grows to hundreds of variants, the XOR enumeration becomes computationally intractable for state space analysis.

# 4. Balanced Candidate

**Inductive-bias statement**: The balanced model generalizes the variants into a partial order based on the domain rules, explicitly modeling true concurrency while respecting observed precedence constraints. It uses POWL to cleanly represent partial orders without duplicating labels, capturing the optionality of SC and EX while conservatively anchoring SC to post-CC based on empirical observation.

**Compact formal expression**:
$RO < \{CC, ER\}$, $\{CC, ER\} < EX_{opt}$, $\{EX_{opt}, SC_{opt}\} < AC < RP < ARC$
Empirical restriction: $CC < SC_{opt}$.

**Deciding between sequence, concurrency, and partial order**:
- **CC and ER**: Modeled as fully concurrent (no partial order edge between them). The DFG and S2 explicitly support their parallel execution.
- **Supplier Confirmation (SC)**: Modeled as an optional block ($SC_{opt}$). To balance generalization with evidence, we add a precedence edge $CC < SC_{opt}$. While D5 says SC can follow *either* CC or ER, the log strictly shows it following CC in 100% of observations. Adding this edge prevents wild unobserved behavior while still allowing SC to be concurrent with ER.
- **Expedite Review (EX)**: Modeled as optional ($EX_{opt}$). D6 and S6 enforce it must follow *both* CC and ER. Therefore, explicit edges $CC < EX_{opt}$ and $ER < EX_{opt}$ are used.
- **SC vs EX**: No ordering edge between them. They can interleave (as seen in variants 6 and 7).

**PM4Py Code**:
```python
from pm4py.objects.powl.obj import StrictPartialOrder, Transition, SilentTransition, OperatorPOWL
from pm4py.objects.process_tree.obj import Operator

ro = Transition("Register Order")
cc = Transition("Credit Check")
er = Transition("Engineering Review")
sc = Transition("Supplier Confirmation")
ex = Transition("Expedite Review")
ac = Transition("Approve Configuration")
rp = Transition("Release Production")
arc = Transition("Archive Case")

opt_sc = OperatorPOWL(operator=Operator.XOR, children=[sc, SilentTransition()])
opt_ex = OperatorPOWL(operator=Operator.XOR, children=[ex, SilentTransition()])

model_balanced = StrictPartialOrder(nodes=[ro, cc, er, opt_sc, opt_ex, ac, rp, arc])
model_balanced.order.add_edge(ro, cc)
model_balanced.order.add_edge(ro, er)
model_balanced.order.add_edge(cc, opt_sc)
model_balanced.order.add_edge(cc, opt_ex)
model_balanced.order.add_edge(er, opt_ex)
model_balanced.order.add_edge(opt_sc, ac)
model_balanced.order.add_edge(opt_ex, ac)
model_balanced.order.add_edge(ac, rp)
model_balanced.order.add_edge(rp, arc)
```

**List of behavior deliberately excluded**:
- SC occurring before CC completes (e.g., `RO -> SC -> CC...`).
- EX occurring before both CC and ER complete.
- AC occurring before SC or EX completes.

**List of known underfitting risks**:
- By enforcing $CC < SC_{opt}$, we risk underfitting if the empirical absence of $ER \rightarrow SC \rightarrow CC$ was merely an artifact of the small sample size (violating the full flexibility implied by D5).
- Abstracting SC and EX as silent-transition XORs loses the strict data-driven routing logic.

# 5. Permissive Candidate

**Inductive-bias statement**: The permissive model prioritizes maximum generalization within the broad bounds of domain rules. It removes empirical artifacts (like SC always following CC) that lack strong domain backing, fully trusting D5 that SC can happen essentially independently of CC as long as it starts after the order is registered and precedes AC.

**Compact formal expression**:
$RO < \{CC, ER, SC_{opt}\}$, $\{CC, ER\} < EX_{opt}$, $\{EX_{opt}, SC_{opt}\} < AC < RP < ARC$

**Boundary definition**:
The boundary for "reasonable generalization" is defined by explicitly removing the $CC < SC_{opt}$ dependency, allowing SC to execute concurrently with CC. However, behavior remains strictly forbidden if EX bypasses CC or ER (respecting D6 and S6 strict compliance) or if AC bypasses any incomplete upstream checks.

**PM4Py Code**:
```python
ro_p = Transition("Register Order")
cc_p = Transition("Credit Check")
er_p = Transition("Engineering Review")
sc_p = Transition("Supplier Confirmation")
ex_p = Transition("Expedite Review")
ac_p = Transition("Approve Configuration")
rp_p = Transition("Release Production")
arc_p = Transition("Archive Case")

opt_sc_p = OperatorPOWL(operator=Operator.XOR, children=[sc_p, SilentTransition()])
opt_ex_p = OperatorPOWL(operator=Operator.XOR, children=[ex_p, SilentTransition()])

model_permissive = StrictPartialOrder(nodes=[ro_p, cc_p, er_p, opt_sc_p, opt_ex_p, ac_p, rp_p, arc_p])
model_permissive.order.add_edge(ro_p, cc_p)
model_permissive.order.add_edge(ro_p, er_p)
model_permissive.order.add_edge(ro_p, opt_sc_p)  # Removed CC -> SC dependence
model_permissive.order.add_edge(cc_p, opt_ex_p)
model_permissive.order.add_edge(er_p, opt_ex_p)
model_permissive.order.add_edge(opt_sc_p, ac_p)
model_permissive.order.add_edge(opt_ex_p, ac_p)
model_permissive.order.add_edge(ac_p, rp_p)
model_permissive.order.add_edge(rp_p, arc_p)
```

**List of behavior deliberately excluded**:
- EX occurring before CC or ER (strict compliance S6).
- AC occurring before CC, ER, SC, or EX (strict domain rules D2, D3, D4).

**List of known underfitting risks**:
- High likelihood of accepting physically impossible real-world traces if SC actually fundamentally depends on CC data.
- By maximizing generalization, precision drops, meaning the model is less useful for strict conformance checking of the SC activity's timing.

**Intentionally Excluded Traces**:

- **Conservative Model**:
  - `RO, CC, ER, EX, AC, RP, ARC` | Earliest violated constraint: The XOR tree lacks any variant branch containing EX but lacking SC.
  - `RO, SC, CC, ER, AC, RP, ARC` | Earliest violated constraint: SC immediately follows RO, failing all 7 XOR sequence prefixes.
- **Balanced Model**:
  - `RO, SC, CC, ER, AC, RP, ARC` | Earliest violated constraint: `CC < opt_SC`. SC cannot execute before CC.
  - `RO, CC, EX, ER, AC, RP, ARC` | Earliest violated constraint: `ER < opt_EX`. EX cannot execute before ER.
- **Permissive Model**:
  - `RO, ER, EX, CC, AC, RP, ARC` | Earliest violated constraint: `CC < opt_EX`. EX cannot execute before CC.
  - `RO, CC, ER, AC, SC, RP, ARC` | Earliest violated constraint: `opt_SC < AC`. SC cannot execute after AC.

*Note on limitations*: Sampled play-out APIs cannot exhaustively verify inclusion, though our models are acyclic. Additionally, computing generalization via `pm4py.generalization_tbr` is computationally heavy and may not fully reflect true structural generalization on such small logs.

# 9. Recommendation and Data-Collection Plan

**Recommendation**: The **Balanced candidate** is recommended for immediate use. It correctly identifies the core partial order without overfitting to the exact 7 observed variants, honoring the strict compliance requirement (EX requires CC and ER) while allowing reasonable concurrency. The **Permissive candidate** should be used for sensitivity analysis to stress-test downstream analytics against edge cases (e.g., what if SC executes entirely independently of CC?).

**Data-Collection Plan**:
1. **Missing Data**: Expose and ingest the `external_vs_stocked` CRM attribute to deterministically route the XOR choice for SC, distinguishing legitimate skips from missing log events.
2. **Timestamp Granularity**: Collect `start` and `complete` lifecycle timestamps. This will conclusively resolve whether CC and ER are truly concurrent (overlapping intervals) or just arbitrarily sequenced.
3. **Informative Traces**: Monitor for the trace `RO -> SC -> CC -> ER -> AC -> RP -> ARC`. If this trace is successfully executed in reality, we must relax the Balanced model to the Permissive one. If it is rejected by the system (e.g., the UI blocks it), it confirms the Balanced model's `CC < SC` empirical constraint.

# 10. Uncertainty Statement

- **Concurrency of CC and ER**: *High confidence.* Although D7 warns about ingestion indexing, S2 explicitly states they are run in parallel, strongly justifying a concurrent split.
- **SC Precedence (CC < SC)**: *Low-to-Medium confidence.* The balanced model enforces this because the 30 traces never show SC before CC. However, D5 implies ER alone could theoretically trigger SC. If D5 is entirely accurate in its edge cases, the Balanced model underfits.
- **Optionality of SC**: *High confidence.* S4 confirms stocked components skip SC, making it structurally optional, even though data quality (S5) obfuscates the deterministic routing.
- **Alternative Interpretation**: If the 5-10% missing SC events are actually *mandatory* external checks that were bypassed by systemic failure, then modeling SC as structurally optional (XOR with tau) normalizes a compliance violation. Under this alternative interpretation, SC must be mandatory, and "missing" SCs should trigger non-conformance alerts rather than perfectly fitting a `tau` transition. This would drastically alter the recommendation, shifting focus to fixing integration errors rather than accepting the variants.
