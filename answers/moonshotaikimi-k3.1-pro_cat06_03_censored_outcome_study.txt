## 1. Target definition

The requested outcome, “90-day default for every application,” is not directly observed and is not well-defined without saying what activation decision is to be imagined. Rejection is not evidence of default-free credit performance.

**Primary formulation: an observed-policy, application-level multi-state target.** From an early pre-decision prefix, model the subsequent states:

- activation on the source platform;
- rejection;
- withdrawal;
- transfer;
- still in process;
- and, following activation, default within 90 days.

The unit of analysis is one source application episode. Where transfer linkage is available, linked records must also be grouped for de-duplication, uncertainty estimation, and validation.

The primary prediction landmark \(\tau\) is immediately after the third canonical pre-decision event. The population is applications that have reached that landmark without an earlier Accept, terminal decision, transfer, or activation. Shorter cases require earlier-landmark models; they are not padded with terminal events.

For a pre-specified 90-day process-transition window, the headline quantity is

\[
R^{(e)}_{90,90}(x)=
P\!\left(T_A\leq \tau+90\text{ days},\;Y_{90}=1
\mid X_\tau=x,\text{ at risk at }\tau,\text{ policy era }e\right),
\]

where \(T_A\) is source-platform activation time and \(Y_{90}\) is defined only on the activated branch. Thus, default follow-up can extend as far as 180 days after \(\tau\), plus outcome-feed delay. The 90-day activation window is an explicit design choice; 30- and 180-day windows are useful sensitivities, not horizons to tune for performance.

This is the **absolute probability of an application-to-default pathway under the observed source-lender policy**. It is estimated separately, or explicitly standardized, for the pre- and post-1-July-2025 policy eras. A pooled estimate is only a descriptive mixture of those policies.

The model should also report activation probability, the other state probabilities, and conditional activated-account default risk. Otherwise, a low \(R\) could be misread as good credit quality when it merely reflects likely rejection or transfer. \(R\) must not be fitted as a convenient binary label with rejected, withdrawn, transferred, or open cases coded as zero.

This formulation is operationally useful for forecasting default-bearing activations and process outcomes under the current policy. Statistically, it uses all at-risk applications for process transitions while restricting the default outcome model to accounts for which default is defined.

**Alternative formulation: conditional activated-account risk.** A simpler account-monitoring target is

\[
Q^{(e)}(x)=P(Y_{90}=1\mid \text{activated in policy era }e,X=x).
\]

It can be scored at activation using information available then. If scored from an earlier prefix, it is explicitly conditional on the post-prefix event of eventual activation. With reliable default-event dates, this becomes time to default after activation, with right censoring and a 90-day administrative horizon. It answers “among accounts the process activates, which default?”—not “what would happen if any applicant were activated?”

A policy-specific counterfactual target, such as default risk if an applicant were activated under a proposed policy, answers a third question. It requires a well-defined intervention, consistency, exchangeability, positivity, adequate follow-up, and assumptions about interference and policy-induced behavior. The current export alone cannot identify it.

Partner-originated accounts with missing feeds are not an additional cohort row—the supplied counts do not say how they overlap the activated categories.

## 3. Censoring and missing-label strategy

- **Ordinary right censoring:** An activated account whose 90-day horizon has not finished can contribute observed follow-up, provided there is a reliable last-follow-up time. Open applications are likewise censored for subsequent activation or competing transitions. Censoring at extraction must not be confused with observing default-free status.
- **Delayed labels:** The 90-day outcome may already be determined while its feed is still pending. It is temporarily unavailable for an as-of fit, not a negative label. Conversely, `label_available_at` is not the default event time.
- **Selection through activation:** Rejected, withdrawn, and never-activated open cases are not merely censored default observations. For them, the observed-policy default outcome is undefined. Activation weighting cannot, by itself, create a valid all-applicant default outcome.
- **Transfer:** Transfer is an absorbing competing event for the explicitly source-platform estimand. For a broader “default anywhere” question, it is loss of follow-up, potentially informative. Linkage can recover some outcomes but linkage itself is incomplete and possibly selective.
- **Permanently missing outcome feeds:** A matured account with no feed is not automatically ordinary administrative censoring. Because partner origin predicts missingness, treating all such accounts as non-default—or casually dropping them—can bias both risk estimates and subgroup comparisons.

**Primary analysis strategy**

1. Fit the pre-activation process as a multi-state or competing-risk model, using all applications at risk. Rejection, withdrawal, and source-platform transfer remain separate states; open cases contribute censoring information.
2. Fit the activated-account default component separately by policy era. If reliable default dates exist, use a survival model with 90-day administrative censoring. If only `default_90d` is trustworthy, use a binary 90-day model with explicitly matured/observable outcomes and observation or censoring weights; do not invent event times from recording dates.
3. Estimate label-observation and censoring probabilities using only legitimately available covariates, including activation calendar time, policy era, channel, source system, and partner status. Inspect weight tails, effective sample sizes, and positivity.
4. Combine activation-time and default predictions by g-computation to estimate \(R_{90,90}\), while reporting its components and uncertainty.

**Sensitivity analyses**

- Compare a conservatively maturity-restricted analysis with IPCW/censoring-aware analysis. Similar point estimates would not prove correctness, but large differences would warn about calendar and feed-arrival selection.
- For unresolved activated feeds, use pattern-mixture or delta-adjusted analyses: allow missing accounts’ default odds to differ from observed accounts, especially for partner-originated cases. Best/worst-case bounds should also be reported when decision conclusions are fragile.
- For a broader cross-platform target, compare linked-transfer follow-up, censoring unlinked transfers with weights, and outcome bounds. For the source-platform target, retain transfer as a competing state.
- Repeat estimates by policy era and case-mix standardization; a pooled IPCW estimate is not a solution to policy drift.

Observed delay patterns, missing-feed associations with observed covariates, linkage rates, policy-era differences, and censoring-model fit are testable. Conditional independent censoring or missing-at-random assumptions are only partially testable. Outcome dependence among permanently missing feeds, outcomes of unlinked transfers, and counterfactual default under a different activation policy are fundamentally untestable from these data without external information or stronger assumptions.

## 4. Prefix extraction

- Canonicalize activities with an effective-dated, source-system crosswalk for the 15 October 2025 migration. Preserve raw activity, source system, and a migration indicator. Remove only defensible duplicates and use a stable event order, with timestamp ties disclosed.
- Construct a safe pre-decision event stream. Accepted/Rejected/Withdrawn/Transferred, Contract Signed, Account Activated, Collections Contact, Default Recorded, and everything following the first stop event are excluded from the prefix feature stream.
- For fixed \(k=3\), the prediction timestamp is the third safe event’s timestamp. Features may use that event and earlier events only. PM4Py prefix extraction is applied to this safe stream, followed by an explicit event-count and timestamp audit.
- Cases with fewer than three safe events are not padded with a synthetic terminal activity or a future event. Report prefix-model coverage and provide \(k=1\) or \(k=2\) models where operationally useful. Multiple landmark rows from one case must remain clustered in validation and bootstrapping.
- For elapsed-time prefixes, set \(L=\text{application start}+\Delta\), for example 24 or 72 hours. Include only events and event-versioned attributes available by \(L\). A case already resolved before \(L\) is no longer at risk; a case with no recent event can still have queue and time-since-last-event features.
- Same-day snapshot values are not sufficient for elapsed-time prefixes: availability must be at timestamp precision, not merely calendar-date precision.
- Document loops remain in the event sequence. Compute document-request counts, repeated Credit Reviews, review-to-review times, and completed loop counts within the prefix. A loop-collapsed variant can help encoding, but rework counts must not be lost.
- Full-case variants, total case duration, and full-case directly-follows graphs are not prefix features.

## 5. Process-aware features

| Feature class | Examples and availability rules |
|---|---|
| Static case attributes | Original channel, region, requested amount, application-start calendar fields, and initial source system. Verify that these are immutable originals rather than extraction-time overwrites. |
| Prefix control flow | Canonical last activity, previous transition, activity one-hot counts, prefix length, number of unique activities, and prefix variant. Rare-variant mappings must be learned from training prefixes only. |
| Timing | Application age at \(\tau\), prefix duration, inter-event elapsed times, time since last event, hour/weekend indicators, and time spent in repeated review loops. With one timestamp per event, inter-event time is observable; actual service time and queue time are not separately identifiable without additional semantics. |
| Resource and queue | Last resource, unique-resource count, handoffs, resource changes, and workload/queue proxies at \(\tau\). Workload must be reconstructed from events available by \(\tau\), not from end-of-case status. Extraction-time employee experience is excluded. |
| Rework | Credit Review repetitions, document requests, completed document loops, repeated KYC activities, and within-prefix changes in these counts. Never use total lifetime rework. |
| Risk-score history | Last event-versioned `risk_score` at or before \(\tau\), number of updates, and within-prefix change. The score’s version and availability must be checked, particularly across the policy change. |
| Cohort/calendar | Policy era at prediction, migration era, start month/season, and application calendar cohort. These measure drift; they do not eliminate it. |
| Historical reference features | Training-only variant frequencies, past-only queue statistics, and carefully lagged rollout or acceptance rates. Any historical default-rate feature would additionally require labels to have been available by \(\tau\); otherwise it should be omitted. |

Process discovery and variants are useful for describing training prefixes and measuring measurement drift. They are not causal representations of the process. Likewise, a PM4Py service/waiting-time transformation should not be interpreted as recovering true service and queue durations when the source data contain only one timestamp per event.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Reveals the final credit decision and post-prefix processing | Unavailable at the pre-decision landmark | **Drop** | Direct post-decision leakage |
| `decision_reason` | Populated at or after Accept/Reject and can reveal the outcome | Only usable for predictions made after such a decision, which is not this study | **Drop** | Terminal-decision leakage |
| `collection_status` | Post-activation and may directly encode default | Never available at the application prefix | **Drop from features** | Direct outcome proxy |
| Contract Signed, Account Activated, Collections Contact, Default Recorded, and other future events | Full-case prefixes, durations, or variants reveal activation and collections outcomes | Use only in a segregated outcome/state table; feature events must satisfy event index and timestamp \(\leq\tau\) | **Keep, segregated** | Needed for outcomes, unsafe as predictors |
| `documents_total` | Nightly snapshot can include uploads later on the prediction day | Reconstruct from document events with upload/availability timestamp \(\leq\tau\) | **Repair or drop** | Date-only as-of joining is insufficient |
| Updated `risk_score` | Taking the case’s last or maximum value can import post-prefix revisions | Use the last event-versioned value and changes wholly within the prefix | **Repair** | Useful only with event-time semantics |
| Resource experience | Stored at extraction, not at the historical event | Require valid-time employee history; otherwise unavailable | **Drop current field; repair only with history** | Future employee state can leak time and staffing changes |
| `default_90d` | Direct target leakage if repeated on event rows | Outcome table only; never merge into predictors | **Keep as outcome only** | Also requires activation and maturity semantics |
| `label_available_at` | Using later labels in an early backtest creates availability leakage; using it as a predictor reveals outcome processing | Use for as-of label eligibility and delay audits only | **Keep for audit, not features or default time** | Separates outcome existence from information availability |
| Full-log DFGs, variants, target encodings, queue aggregates | Can incorporate test cases, future events, or unavailable labels | Fit reference objects on training data and compute each case from past-only information | **Repair** | Prevents subtle aggregate leakage |
| Case ID and transfer linkage | Repeated IDs can memorize cases; linked episodes can cross folds | IDs are not predictors; use linkage for de-duplication, grouped splitting, and follow-up | **Repair/govern** | Residual unlinked duplication remains a limitation |
| `source_system` / `data_extract_time` | Source may encode migration and feed mechanisms; extraction time is snapshot metadata | Source is usable only if known at \(\tau\); extraction time is never a predictor | **Keep source with audit; drop extraction time** | Distinguishes measurement shift from snapshot leakage |

## 7. Validation design

The primary validation is rolling, temporal, and reconstructed as of each model-fit date:

- Use earlier rolling folds for development, for example validation in 2024 Q4, 2025 Q1, and 2025 Q2, with training restricted to earlier case starts.
- An implementable final development split is: training starts before 1 April 2025; validation starts from 1 April through 30 June 2025; and a post-policy test with starts from 1 July through 30 September 2025.
- Post-migration starts from 15 October through 31 December 2025 form a separate measurement- and drift-focused evaluation cohort.
- At every fold, rebuild training outcomes using only labels available at that fold’s fit date. Fit imputers, encoders, variant references, censoring models, and calibration on training data only.
- Split by application start time, while keeping linked transfer episodes together. Report activation-time and prediction-time distributions as well, because start-time splitting alone does not guarantee equal outcome maturity.

The July policy change requires separate pre/post performance and calibration. A model trained before July cannot be presumed valid afterward merely because policy era is a feature. Post-policy recalibration or retraining must wait for adequate outcome information and must not treat pending cases as negatives.

Migration performance must be reported separately after activity canonicalization and duplicate handling. Otherwise, a change in variant frequencies or feature missingness can be mistaken for a change in credit risk.

Label maturity is especially restrictive. The conditional default endpoint needs activation plus 90 days and feed time; the primary compound endpoint can require up to 180 days after \(\tau\), plus feed time. Consequently, parts of the post-policy test—and much of the post-migration cohort—are not mature by 15 February 2026. If censoring-adjusted estimates have inadequate effective follow-up, the correct result is “not yet estimable with useful precision,” not a complete-case leaderboard.

**Evaluation**

- For the multi-state target: IPCW time-dependent Brier scores or integrated Brier scores, state-occupation calibration at fixed horizons, and calibration-in-the-large and slope for \(R_{90,90}\). Time-dependent discrimination is secondary.
- For conditional 90-day default: censoring-aware Brier score and 90-day calibration, with AUROC and PR AUC as supplementary measures. With valid event times, add survival calibration, integrated Brier score, and an appropriate censoring-robust concordance measure.
- Report alert coverage and performance at a pre-specified operating capacity, but only with censoring/maturity handling.
- Use linked-episode bootstraps and temporal block uncertainty intervals; report censoring proportions and effective sample sizes alongside metrics.
- Stratify by policy era, migration era, channel, region, source/partner, feed-observation status, prefix coverage, and rework. Where outcomes are missing, report that performance is conditional on observed feeds rather than claiming subgroup correctness.
- Monitor activity/variant distributions, inter-event times, resource workload, activation and transfer rates, label delay, missing-feed rates, feature missingness, calibration, and score coverage.

A random case split mixes policy and migration regimes, makes recent and old cohorts look interchangeable, and hides label-maturation and calendar-selection effects. Related linked episodes and full-log reference features can further inflate it. Even a technically random `pm4py.split_train_test` baseline would therefore not estimate deployment performance.

## 8. Limitations and decision-use boundary

The study can estimate predictive associations under the observed source-lender process, conditional default risk among activated accounts, and—if validation supports it—calibrated observed-policy pathway risk for specified landmarks and eras.

It cannot establish:

- a default outcome for rejected, withdrawn, or never-activated applicants;
- that the 12.5% default fraction in the 21,600-row export is the portfolio or applicant default rate;
- that a low pathway risk means low counterfactual credit risk rather than low activation probability;
- causal effects of acceptance, limits, staff actions, document requests, or the model itself;
- reliable performance in periods or subgroups without sufficient mature outcome follow-up.

Selection into activation, selection into label maturity, missing partner feeds, and incomplete transfer linkage are distinct problems. No single weighting procedure makes all of them disappear. Unlinked transfers and permanently missing feeds may leave material uncertainty best expressed through sensitivity intervals or bounds.

Deployment can itself change the data-generating process in several ways:

1. Using the score for acceptance or activation changes the selected population and therefore future labels, positivity, and calibration.
2. Using it for limits, pricing, outreach, or collections changes the default outcome being predicted.
3. Routing alerts to staff changes queues, document loops, withdrawals, transfers, and the prefix features themselves.
4. Applicants, partners, or staff may adapt to the score, while changes in partner routing or feed infrastructure alter missingness and linkage.

Accordingly, the conditional model is suitable, at most, for activated-account monitoring unless further validated. The multi-state score can support observed-policy monitoring and manual review, but should not by itself justify automatic decline, pricing, or claims about applicant creditworthiness. Policy allocation decisions require a separate causal/policy evaluation, ideally including a prospective rollout with continued outcome measurement.

import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"

OBS_END = pd.Timestamp("2025-12-31 23:59:59")
K = 3
TERMINALS = {"Rejected", "Withdrawn", "Transferred"}
STOP = TERMINALS | {
    "Accepted", "Contract Signed", "Account Activated",
    "Collections Contact", "Default Recorded"

    "final_limit", "decision_reason", "collection_status", "documents_total",
    "default_90d", "label_available_at", "data_extract_time"
}
# Required before use: approved effective-dated crosswalk for the 2025-10-15 migration.

raw[ACT] = raw[ACT].astype("string").str.strip().replace(ACTIVITY_CROSSWALK)

# Assumption: these exact duplicates are migration duplicates; review near-duplicates separately.

duplicate_mask = raw.duplicated(dedup_keys, keep="first")
dedup = raw.loc[~duplicate_mask].copy()

ev = dedup.loc[dedup[TS].le(event_cutoff)].copy()

ids = pd.Index(ev[CASE].unique(), name=CASE)

out["activation"] = (
    ev.loc[ev[ACT].eq("Account Activated")].groupby(CASE)[TS].min()
)
terminal = (
    ev.loc[ev[ACT].isin(TERMINALS)]
      .sort_values([CASE, TS, "_row"]).groupby(CASE).first()
)

out["terminal_state"] = terminal[ACT]
out["status"] = "open_or_unobserved"
for state in TERMINALS:
    mask = out["activation"].isna() & out["terminal_state"].eq(state)
    out.loc[mask, "status"] = state.lower()
out.loc[out["activation"].notna(), "status"] = "activated"

activated = out["activation"].notna()
open_mask = out["activation"].isna() & out["terminal_time"].isna()
out["process_censor_at"] = pd.NaT
out.loc[open_mask, "process_censor_at"] = event_cutoff
out["horizon_end"] = out["activation"] + pd.Timedelta(days=90)
out["horizon_complete"] = activated & out["horizon_end"].le(CUTOFF)
out["feed_sla_mature"] = activated & (
    out["horizon_end"] + pd.Timedelta(days=35)
).le(CUTOFF)
out["activated_followup_to"] = pd.NaT
out.loc[activated, "activated_followup_to"] = (
    out.loc[activated, "horizon_end"]
       .where(out.loc[activated, "horizon_end"].le(CUTOFF), CUTOFF)
)
# This is only an administrative upper limit: use an earlier actual last-feed/contact
# time when available. Absence of a feed must not be treated as observed default-free time.

# Labels are visible only if their availability timestamp passes the as-of cutoff.
lab = raw.loc[
    raw["default_90d"].notna()
    & raw["label_available_at"].notna()
    & raw["label_available_at"].le(CUTOFF)
].copy()
lab["y"] = pd.to_numeric(lab["default_90d"], errors="coerce")
lab = lab.loc[lab["y"].isin([0, 1])]
if (lab.groupby(CASE)["y"].nunique() > 1).any():
    raise ValueError("Conflicting as-of labels require source reconciliation")
lab_case = (
    lab.sort_values("label_available_at").groupby(CASE)
       .agg(default_90d=("y", "last"),
            label_first_available=("label_available_at", "min"))
)
out = out.join(lab_case)
out["label_observed"] = out["default_90d"].notna()
out["right_censored_90d"] = (
    activated & ~out["horizon_complete"] & ~out["default_90d"].eq(1)
)
out["feed_pending_or_missing"] = (
    activated & out["horizon_complete"] & ~out["label_observed"]
)
out["usable_binary_label"] = (
    activated & out["label_observed"]
    & (out["horizon_complete"] | out["default_90d"].eq(1))
)

out["cohort"] = out["status"]
out.loc[activated & out["default_90d"].eq(0), "cohort"] = "activated_labeled_non_default"
out.loc[activated & out["default_90d"].eq(1), "cohort"] = "activated_labeled_default"
out.loc[activated & ~out["label_observed"] & ~out["horizon_complete"], "cohort"] = (
    "activated_immature_or_censored"
)
out.loc[activated & ~out["label_observed"] & out["horizon_complete"], "cohort"] = (
    "activated_feed_pending_or_missing"
)
cohort_counts = out["cohort"].value_counts()

# ---------- Safe fixed-length prefixes ----------
ev = ev.sort_values([CASE, TS, "_row"])
ev["_stop_seen"] = ev.groupby(CASE)[ACT].transform(

safe["_seq"] = safe.groupby(CASE).cumcount()

    safe, case_id=CASE, activity_key=ACT, timestamp_key=TS

prefix = pm4py.get_prefixes_from_log(formatted, length=K)
counts = prefix.groupby(CASE).size()
eligible = counts.loc[counts.eq(K)].index     # No padding of short cases

    prediction_time=(TS, "max"), last_seq=("_seq", "max")

# Re-derive feature events and enforce both event-position and timestamp boundaries.
fe = safe.merge(cut, left_on=CASE, right_index=True, how="inner")
fe = fe.loc[
    fe["_seq"].le(fe["last_seq"]) & fe[TS].le(fe["prediction_time"])

X["start"] = g[TS].min()
X["n_events"] = g.size()
X["n_credit_reviews"] = g[ACT].apply(lambda s: int(s.eq("Credit Review").sum()))
X["n_document_requests"] = g[ACT].apply(lambda s: int(s.eq("Request Documents").sum()))
X["review_rework"] = (X["n_credit_reviews"] - 1).clip(lower=0)
X["n_resources"] = g["org:resource"].nunique()
X["last_activity"] = g[ACT].last()
X["risk_score_updates"] = g["risk_score"].count()
X["risk_score_last"] = g["risk_score"].last()  # Assumes event-versioned, not overwritten values
X["prefix_hours"] = (X["prediction_time"] - X["start"]).dt.total_seconds() / 3600
for col in ["case:channel", "case:region", "case:requested_amount"]:
    X[col] = g[col].first()                    # Validate that these are original static values
X["post_policy"] = X["prediction_time"].ge(pd.Timestamp("2025-07-01")).astype(int)
X["post_migration"] = X["prediction_time"].ge(pd.Timestamp("2025-10-15")).astype(int)
X["start_month"] = X["start"].dt.month
X["start_dayofweek"] = X["start"].dt.dayofweek

assert g.size().eq(K).all()
assert g[TS].max().le(cut["prediction_time"]).all()
assert not BANNED.intersection(X.columns)      # Labels and post-prefix fields stay out of X

        starts.ge(pd.Timestamp("2025-04-01")) & starts.lt(pd.Timestamp("2025-07-01"))
    ],
    "test_post_policy": X.index[
        starts.ge(pd.Timestamp("2025-07-01")) & starts.lt(pd.Timestamp("2025-10-01"))

training_variant_reference = pm4py.get_variants(train_prefix)

    "raw_applications": raw[CASE].nunique(),
    "asof_applications": len(out),
    "exact_duplicate_events_removed": int(duplicate_mask.sum()),
    "activation_terminal_conflicts": int(
        (out["activation"].notna() & out["terminal_time"].notna()).sum()
    ),
    "nonactivated_with_default_label": int((~activated & out["label_observed"]).sum()),
    "eligible_prefix_cases": len(X),

    assert len(out) == raw[CASE].nunique()     # Must reconcile to 48,000 in this snapshot
