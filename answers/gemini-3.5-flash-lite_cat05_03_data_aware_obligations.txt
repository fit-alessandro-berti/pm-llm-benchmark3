## 1. Temporal Data Semantics

To perform an audit of transaction-review compliance under dynamic attributes, we must separate **Event Time** (`time:timestamp`), **Effective Time**, **Record Time**, and **Evidence Time**.

*   **Event Time (`time:timestamp`):** The chronometric timestamp recorded in the event log when an operation is executed in the source system. When timestamps collide, `event_index` strictly orders the sequence of state modifications or operations.
*   **Effective Time:** The actual point in time from which an attribute value or policy designation legally governs the transaction. Unless explicit out-of-band metadata establishes otherwise, attribute updates take effect at their event time.
*   **Record Time:** The physical timestamp when a transaction record, review document, or exemption is committed to a persistent database or ledger (e.g., late database inserts like EX-77 or EX-88). Record time is distinct from effective time and does not retroactively sanitize prior processing unless backed by cryptographically verifiable evidence.
*   **Evidence Time:** The timestamp established by external validators, digital signatures, or cryptographically secure logs (e.g., qualified digital timestamps) that proves when an artifact (such as an exemption approval or signature) actually existed.

### State Reconstruction and Missing Data
*   **Blank Attributes:** Blank attribute cells in the event log indicate "no update at this event," *not* a reset to null or default values. We maintain case-level state using forward-fill semantics: an attribute retains its latest known value until explicitly updated.
*   **Unknown and Missing Initial Values:** If a transaction is created with missing attributes (e.g., amount omitted in TX-305), we do *not* impute low-risk defaults (R6). The state remains `INDETERMINATE` for amount-dependent rules until positive evidence resolves it.
*   **Same-Timestamp Ordering:** When events share an identical timestamp, the `event_index` attribute acts as the deterministic tie-breaker. Operations with a lower `event_index` execute logically prior to those with a higher `event_index` within that microsecond.
*   **Material Changes & Invalidation:** Under R4, an amount increase exceeding 20% relative to the baseline established at the most recent review invalidates that review for amount-dependent obligations. Decreases or increases $\le 20\%$ do not invalidate reviews.

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **R1** | `Release_Funds` | `Enhanced_Review` | Review must be **after** the latest material data change and **before** release | Current jurisdiction $\neq$ DE AND Amount $\ge 100,000$ | Valid exemption matching scope and approved by Head Compliance | If amount or jurisdiction is missing/indeterminate, classify as INDETERMINATE | Signed review artifacts, qualified time signatures |
| **R2** | `Release_Funds` | `Enhanced_Review` AND `Compliance_Approve` | `Enhanced_Review` then `Compliance_Approve`, both before release | Current risk == HIGH OR current customer_type == PEP | None | If risk or customer type is missing, treat as INDETERMINATE | Compliance approval logs, review documentation |
| **R3** | `Release_Funds` | `Sanctions_Screen` | Screen must occur **after** `Sanctions_List_Update` and **before** release | Current jurisdiction added to sanctions list between initial screen and release | None | If jurisdiction is blank, INDETERMINATE | Sanctions engine logs, list version stamps |
| **R4** | `Update_Amount` (Increase $>20\%$) | Subsequent `Enhanced_Review` or `Standard_Review` | Must occur between the increase and `Release_Funds` | Amount delta $> 0.20 \times \text{baseline\_review\_amount}$ | Amount decreases or increases $\le 20\%$ | If baseline amount is unknown, cannot safely classify | Amount change audit trail |
| **R5** | Exemption application | `Head_Compliance` approval | Approval must be prior to obligation trigger; unexpired | Exemption scope matches jurisdiction, customer type, and amount | Cryptographically verified out-of-band evidence (e.g., qualified timestamp) | Backdated UI fields alone are insufficient | Qualified digital signature timestamp, witness corroboration |
| **R6** | Any evaluation | None | N/A | Missing amount, risk, jurisdiction, or customer type | None | Do not default to low-risk; classify as INDETERMINATE | Complete state logs |
| **R7** | Any evaluation | None | Use `event_index` tie-breaker | Latest known attribute value at event time | None | N/A | Source system microsecond ordering |

### Formal Pseudo-Logic (R1–R7)

```prolog
% R1: Foreign High-Value Enhanced Review
viates_R1(C) :-
    event(C, T_rel, Release_Funds),
    jurisdiction(C, J, T_rel), J \= 'DE',
    amount(C, Amt, T_rel), Amt >= 100000,
    \+ valid_exemption(C, T_rel),
    \+ (
        enhanced_review(C, T_rev),
        T_rev < T_rel,
        T_rev > latest_material_change(C, T_rel)
    ).

% R2: High-Risk or PEP Approval
violates_R2(C) :-
    event(C, T_rel, Release_Funds),
    (risk(C, 'HIGH', T_rel) ; customer_type(C, 'PEP', T_rel)),
    \+ (
        enhanced_review(C, T_rev1), compliance_approve(C, T_app),
        T_rev1 < T_app, T_app < T_rel
    ).

% R3: Sanctions List Update
violates_R3(C) :-
    event(C, T_rel, Release_Funds),
    sanctions_list_update(C, J, T_upd),
    latest_screen(C, T_scr),
    T_scr < T_upd, T_upd < T_rel,
    \+ (sanctions_screen(C, T_scr2), T_scr2 > T_upd, T_scr2 < T_rel).

% R4: Material Amount Increase (>20%)
invalidates_review(C, T_rev) :-
    amount_update(C, Amt_new, T_upd),
    prior_review(C, T_rev, Amt_base),
    T_rev < T_upd,
    Amt_new > (Amt_base * 1.20).

% R5: Exemption Validity
valid_exemption(C, T) :-
    exemption_record(C, Ex),
    approved_by(Ex, 'Head_Compliance'),
    effective_from(Ex) =< T,
    expires_at(Ex) >= T,
    scope_matches(Ex, C, T),
    verified_evidence(Ex).

% R6: Missing Data Indeterminacy
indeterminate(C, Attr, T) :-
    missing(Attr, C, T),
    \+ resolved_by_context(Attr, C, T).

% R7: Temporal Event Ordering
effective_state(C, Attr, Val, T, E_Idx) :-
    update_event(C, Attr, Val, T, E_Idx),
    \+ (update_event(C, Attr, _, T2, E_Idx2), (T2 > T ; (T2 == T, E_Idx2 > E_Idx))).
```

## 4. Ambiguities and Alternative Readings

*   **TX-302 (EX-77 Exemption Lag):** 
    *   *Evaluation:* Considered `JUSTIFIED_EXCEPTION`. 
    *   *Alternative Reading / Decisive Evidence:* If the qualified digital signature at 09:05 were proven to be backdated or forged, EX-88's pattern would apply, rendering the release non-compliant under R1.
*   **TX-305 (Missing Amount Feed):** 
    *   *Evaluation:* Classified as `INDETERMINATE`. 
    *   *Alternative/Interpretation:* If an auditor adopts a strict strict-liability interpretation where missing amount data defaults to non-compliant when combined with settlement confirmation ($\ge 100k$), TX-305 would be classified as `NONCOMPLIANT` for failing to execute an Enhanced Review. Conversely, if settlement figures are retroactively accepted as effective at release, it violates R1.
*   **TX-310 (EX-88 Invalid Exemption & Late Evidence):** 
    *   *Evaluation:* Classified as `NONCOMPLIANT`. 
    *   *Alternative/Interpretation:* If the oral testimony of the transaction requester (ops10) were legally accepted as binding oral approval under institutional bylaws prior to release, EX-88 could be deemed valid, shifting the case to `JUSTIFIED_EXCEPTION`.
*   **TX-311 (Same-Timestamp Jurisdiction Update):** 
    *   *Evaluation:* Classified as `COMPLIANT`. 
    *   *Alternative/Interpretation:* Event index 3 (`Enhanced_Review`) preceded event index 4 (`Update_Jurisdiction: DE`) at `16:20:00`. Had the jurisdiction update preceded the review, an enhanced review would technically have been redundant because the jurisdiction became `DE` (exempting it from R1). However, because the enhanced review executed *before* the jurisdiction change, compliance is independently satisfied.

## 6. Why Control-Flow-Only Conformance Is Insufficient

Relying strictly on control-flow process discovery (e.g., standard Petri net conformance or token-based replay) fails in regulatory compliance audits due to the following six distinct failure modes:

1. **Final-State Leakage:** Control flow checks often evaluate attributes against the final case state rather than the point-in-time value when the obligation triggered. This causes retrospective masking of historical violations.
2. **Post-Hoc Exemptions:** A trace may show `Release_Funds` followed by `Record_Exemption` (as in TX-302 and TX-310). Control-flow algorithms treat this as an acceptable sequence if the transition exists, ignoring that the legal exemption must be valid *prior* to fund release.
3. **Material Changes After Review:** Standard process models see `Standard_Review` followed by `Release_Funds` as a compliant path. They cannot evaluate whether an intervening `Update_Amount` (+50%) invalidated the review under R4.
4. **Conditional Activation:** Whether an `Enhanced_Review` is mandatory depends entirely on numeric thresholds ($\ge 100,000$), risk ratings (`HIGH`), and jurisdictions (`!= DE`). Pure control-flow models treat all traces identically regardless of data payload values.
5. **Missing Data & Indeterminacy:** Control-flow traces assume data attributes always exist. When data feeds fail (TX-305), control-flow conformance silently ignores the absence of risk or amount data, leading to false positives or negatives.
6. **Same-Timestamp Ordering:** When multiple events share an exact microsecond timestamp (TX-311), control-flow parsers may ingest them in arbitrary database fetch order rather than respecting `event_index` tie-breakers, altering the logical precedence of reviews versus jurisdiction updates.

## 7. Recommended Logging and Control Improvements

To ensure future transaction-review decisions are fully determinate, auditable, and compliant, the following technical and procedural controls must be implemented:

*   **Immutable Release Payloads:** The `Release_Funds` event must serialize an immutable snapshot of all governing attributes (`amount`, `risk_level`, `jurisdiction`, `customer_type`, and active `exemption_id`) directly into the event log payload at the exact moment of execution.
*   **Cryptographic & Timestamp Provenance:** All review sign-offs, compliance approvals, and exemption records must capture three distinct timestamps:
    1. *Effective Timestamp* (when the decision legally applies).
    2. *Record Timestamp* (when committed to the database).
    3. *Signature Timestamp* (a qualified cryptographic timestamp from an independent Time Stamping Authority). UI-displayed backdated fields must be cryptographically rejected.
*   **Rule Versioning Header:** Every event log entry must record the active `rule_engine_version` hash, ensuring that retrospective audits evaluate transactions against the exact policy definitions active at event time.
*   **Strict Exemption Scoping & Validation API:** Integrate an automated Exemption Ledger API into the transaction pipeline. Exemptions must be cryptographically bound to exact transaction hashes and scopes (`jurisdiction`, `customer_type`, `max_amount`) before fund release is unlocked.
*   **Automated Change Provenance & Delta Tracking:** The source system must record amount deltas and percentage changes as explicit event attributes on every `Update_Amount` event, automatically flagging whether an increase exceeds the 20% material review threshold (R4).
*   **Strict Event Sequencing & Microsecond Ordering:** Enforce system-wide monotonic nanosecond counters or mandatory `event_index` validation at the database driver level to eliminate timestamp collisions and guarantee unambiguous event ordering.
