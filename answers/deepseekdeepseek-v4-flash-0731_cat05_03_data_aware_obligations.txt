## 1. Temporal Data Semantics

Reconstruction uses event-time state, not final-case state. A blank attribute cell is **not** a null assignment; it means “no update at this event.” Within each case, values are forward-filled in ascending `(time:timestamp, event_index)` order, so the value in force at an event is the latest known value before that event. Future events are never copied backward.

Equal timestamps are ordered by `event_index`; an event with a smaller `event_index` occurs before one with a larger `event_index` at the same timestamp. A release obligation is evaluated on the state after all prior events, including same-timestamp events with lower indices.

Evidence time is distinguished from event time and record time. An event can be logged later, but the obligation uses the event’s stated timestamp when that is supported by evidence. For approvals and exemptions, record insertion time is not conclusive approval time; the signature, certification, or other evidence must support existence before the relevant obligation trigger. A displayed backdated effective time alone is not sufficient.

## 4. Ambiguities and Alternative Readings

- **TX-302**: The exemption appears in the database only at 11:00, after release. The qualified signature at 09:05 and documented outage support timely approval. If the judge treated “not yet inserted” as “not yet approved,” the exemption would fail, but the case would still be compliant because the Enhanced_Review itself was valid and on time. The exemption would only be decisive if the Enhanced_Review had been missing.

- **TX-305**: The settlement amount is reliable after settlement, but there is no immutable release payload. If an immutable release payload proved the amount was 150,000 at release, then R1 would be triggered. The existing Enhanced_Review at 11:15 after Create_Transaction at 11:00 and before Release at 11:30 would likely satisfy R1, provided the amount was not unknown at creation under R4. Without that immutable payload, the result remains INDETERMINATE.

- **TX-310**: EX-88 is invalid under R5 because the signing certificate was created after release, and the only oral-evidence witness is the transaction requester. If independent evidence proved oral approval before release, the missing Enhanced_Review could be excused under the exemption and the case would become JUSTIFIED_EXCEPTION rather than NONCOMPLIANT. If a contemporaneous signed approval timestamp existed before release, the result would likewise change.

- **TX-311**: The `event_index` ordering at 16:20 matters: `Enhanced_Review` is event_index 3, `Update_Jurisdiction` is event_index 4. Therefore the jurisdiction changed to `DE` after the review, and at release the jurisdiction is `DE`, so R1 is not triggered. If the jurisdiction update had been before the review and the final jurisdiction remained DE, R1 would still not be triggered. But if the updated jurisdiction had been a non-DE high-risk jurisdiction, the review-before-update ordering would have been a violation.

- **TX-306**: A literal reading of “after the latest material data change” could require a new Enhanced_Review after any amount update, even a 4.5% increase. I interpret R4 as defining amount materiality for amount-dependent obligations: only >20% increases invalidate a review. Under that reading, TX-306 is compliant. If the judge required fresh review after any amount update, TX-306 would be NONCOMPLIANT.

- **TX-308**: A decrease from 140,000 to 100,000 occurs after the Enhanced_Review. R4 says a decrease does not invalidate a review. Therefore the review remains valid. If one treated any amount update, including a decrease, as requiring a fresh review, TX-308 would be NONCOMPLIANT.

    last_screen = latest_event_before(case, "Sanctions_Screen", rel_time, rel_idx)
    last_list_update = latest_event_before(case, "Sanctions_List_Update", rel_time, rel_idx)

    has_er_before_release = last_er is not None
    has_ca_before_release = last_ca is not None
    ca_after_er = False
    if last_er is not None and last_ca is not None:
        ca_after_er = earlier(
            last_er["time:timestamp"],
            last_er["event_index"],
            last_ca["time:timestamp"],
            last_ca["event_index"],
        )

    # R3 coarse check
    r3_trigger = False
    if last_screen is not None and last_list_update is not None:
        list_after_screen = earlier(
            last_screen["time:timestamp"],
            last_screen["event_index"],
            last_list_update["time:timestamp"],
            last_list_update["event_index"],
        )
        list_before_release = earlier(
            last_list_update["time:timestamp"],
            last_list_update["event_index"],
            rel_time,
            rel_idx,
        )
        if list_after_screen and list_before_release:
            r3_trigger = True

    # R4 coarse: did any >20% amount increase occur after last Enhanced_Review and before release?
    r4_invalidated_last_er = False
    if last_er is not None:
        case_events = df[df["case:concept:name"] == case].copy()
        # previous amount in the sorted state, used for increase ratio
        case_events["prev_amount"] = case_events["amount"].shift(1)
        for _, ev in case_events.iterrows():
            if not earlier(last_er["time:timestamp"], last_er["event_index"], ev["time:timestamp"], ev["event_index"]):
                continue
            if not earlier(ev["time:timestamp"], ev["event_index"], rel_time, rel_idx):
                continue
            old = ev.get("prev_amount")
            new = ev.get("amount")
            try:
                old_v = float(old) if pd.notna(old) and str(old).strip() != "" else None
                new_v = float(new) if pd.notna(new) and str(new).strip() != "" else None
                if old_v is not None and new_v is not None:
                    if new_v > 1.2 * old_v:
                        r4_invalidated_last_er = True
            except Exception:
                pass

    diagnostics.append({
        "case": case,
        "release_time": rel_time,
        "release_index": rel_idx,
        "amount_at_release": amount,
        "risk_level_at_release": risk,
        "jurisdiction_at_release": jur,
        "customer_type_at_release": ctype,
        "claimed_exemption_id": claimed_ex,
        "amount_unknown": amount_unknown,
        "risk_unknown": risk_unknown,
        "jurisdiction_unknown": jur_unknown,
        "customer_type_unknown": ctype_unknown,
        "r1_trigger": r1_trigger,
        "r2_trigger": r2_trigger,
        "r3_trigger": r3_trigger,
        "has_enhanced_review_before_release": has_er_before_release,
        "has_compliance_approve_before_release": has_ca_before_release,
        "ca_after_er": ca_after_er,
        "r4_invalidated_last_er": r4_invalidated_last_er,
    })

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage**: A final amount or jurisdiction may be recorded after release, but the earlier decision used a different state. Control-flow traces ignore attribute snapshots.

2. **Post-hoc exemptions**: A database insert at 11:00 can mention an exemption that allegedly existed at 09:00. Control-flow conformance sees the insert but cannot decide whether the exemption was timely approved.

3. **Material changes after review**: A review may occur before a >20% amount increase. Control-flow presence of `Enhanced_Review` looks sufficient, but the review is no longer valid for amount-dependent obligations.

4. **Conditional activation**: Whether `Enhanced_Review` is needed depends on data values such as amount, jurisdiction, risk, and customer type. Control-flow conformance only knows the activity names, not the conditions.

5. **Missing data**: If the amount is unknown at release, no control-flow pattern can distinguish “amount under threshold” from “amount over threshold but not recorded.” Missing data requires an INDETERMINATE classification, not a trace-level pass/fail.

6. **Same-timestamp ordering**: Two activities at the same timestamp may have an `event_index` order. Control-flow conformance usually loses the index, so it cannot decide whether the jurisdiction change happened before or after the review.

7. **Review-type semantics**: `Standard_Review` and `Enhanced_Review` are distinct; a control-flow trace may show a review occurred, but the wrong review type cannot satisfy the rule.

8. **Evidence vs. event time**: Control-flow conformance treats all events as equally reliable, but a late record or interested witness may be insufficient evidence for timely approval. Human evidence evaluation is required.

---

## 7. Recommended Logging and Control Improvements

- **Immutable release payload**: Store amount, risk, jurisdiction, customer type, and exemption ID in a signed payload at release time. This prevents later settlement or final-case data from being used incorrectly.
- **Effective time and record time**: For attribute updates and approvals, record both `effective_time` and `record_time`. This distinguishes the time the fact became true from the time it was logged.
- **Signature/certificate timestamps**: Exemptions and approvals should carry qualified signature/certificate timestamps, not only displayed approval dates. Displayed backdated fields must not be accepted.
- **Rule version and rule scope**: Log which version of the policy rules applied to each release, and which rule each exemption waives.
- **Exemption scope**: Store jurisdiction, customer type, amount range, effective time, expiration, and rule waiver in a structured form so scope matching is automatic.
- **Change provenance**: Attribute updates should include the source system, source event, and previous value, so material-change analysis is deterministic.
- **Stable event ordering**: Use a monotonic global event sequence or `event_index` persisted in the log. Do not rely on database insert order.
- **Unknown-value markers**: If an amount feed is unavailable, log a sentinel like `UNKNOWN` with a reason, not a blank. This prevents treating a failure to record as a low-risk default.
