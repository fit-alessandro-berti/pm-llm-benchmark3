# 1. Delay-decomposition definitions

- `upstream_elapsed(c)` = `fork_release(c)` - `arrival(c)`: time from case entry to when all branch work is permitted to begin (fork_release).

- For branch `i  {A,B,C}` and case `c`:
  - `queue_i(c)` = `start_i(c)` - `fork_release(c)`: time branch `i` waits for its resource after the fork release (0 by scenario).
  - `service_i(c)` = `end_i(c)` - `start_i(c)`: active work duration for branch `i`.

- `join_ready(c)` = max(`A_end(c)`, `B_end(c)`, `C_end(c)`)`: earliest time F may start, since F can begin only after all branches complete. Not directly logged; inferred from branch end times.

- `downstream_queue(c)` = max(0, `final_start(c)` - `join_ready(c)`)`: time F spends waiting to start after all branches are done (if `final_start` > `join_ready`). Represents queueing at the final station.

- `final_service(c)` = `final_end(c)` - `final_start(c)`: time F takes to complete the release decision.

- `total_flow_time(c)` = `final_end(c)` - `arrival(c)`: overall case flow time.

- `elapsed_fork_join(c)` = `join_ready(c)` - `fork_release(c)`: time from fork release to all branches completed.

- `sync_wait_i(c)` = max(0, `join_ready(c)` - `end_i(c)`)`: for analysis only; the time between branch `i`'s completion and when F can start (`join_ready`). Note: this is **not** a queueing time experienced by branch `i` (the branch is already finished at `end_i`), but used to identify the last-completing branch. Thus, summing `sync_wait_i` over branches does **not** equal elapsed time or cause double-counting in flow decomposition, because `elapsed_fork_join` already covers the fork stage duration, and `queue_i + service_i` are per-branch activities.

- **Why summing branch synchronization waits would double count**: If one naively added `sync_wait_i = join_ready - end_i` for all branches (with `end_i < join_ready`), the sum would be `(k-1)*join_ready - sum_{non-last} end_i` for `k=3`, which mixes the latest completion time (`join_ready`) with earlier completions. This sum does not correspond to any physical queueing time (branches don't queue after completion), and would incorrectly inflate influence analysis if treated as elapsed branch stage time. Instead, `elapsed_fork_join = join_ready - fork_release` correctly captures the fork stage duration without double-counting, while per-branch `queue_i` and `service_i` are disjoint (each branch's queue and service are unique to that branch).

*influence_rank*: "high" for B (most frequent critical, longer service + queue), "medium" for A (frequent service, no queue), "low" for C (short service, rarely critical). "avg_sync_wait" is average `sync_wait_i = join_ready - end_i` for cases where branch i is not the critical (last) branch. - B is critical in 8/12 cases, A in 2, C in 2.

- A has zero queue (A_start=fork_release always), service ~50 min; influences join when it is critical (F01,F11), but rarely.

- B has queue 5-30 min and service 30-45 min; often last due to longer tail (F03=45, F07=45, F12=45), so its completion frequently determines join_ready.

- C has short service (18-22 min), often small queue, rarely last (only F04,F08), so less influence.

- Downstream queue varies 8-20 min, but B's role as frequent last-completing branch means reducing B's service/queue often reduces join_ready, whereas reducing A (zero queue) only helps when A is critical (2 cases), which may switch to B if accelerated.

- Tail contribution: B has max service 45 min (vs A 50), but B occurs more often as critical, so cumulative tail risk higher for B.

- Influence ranking: B > A > C, as B most frequently controls join_ready and has both service and queue that can be reduced in frequency.

#5 Recommended redesigns and risks

1. **Reduce B queue delay by 50%** (via branch scheduling or resource preemption):

   - *How*: Allow B to start earlier if possible, e.g., reserve B resource to start at fork_release or earlier if no congestion (but fork_release is earliest permitted start; queue reduction means if B resource is free at fork_release, start immediately). In data, B often has queue (5-30 min), suggesting B resource busy when fork_release occurs.
   - *Throughput*: May increase throughput if B queue reduction frees F earlier in pipeline, but depends on F capacity.
   - *Flow-time tail*: Reduces tail for B-critical cases (8/12), reduces average downstream_queue from ~13 min to ~6 min; tail (e.g., max downstream 2010 min).
   - *Resource utilization*: B resource utilization same (service time), but start earlier may reduce idle time between cases, improving utilization.
   - *New bottlenecks*: C might become more frequent critical if B queue reduced but A still 0 queue; but C is short, unlikely. F queue may reduce, so less risk of F becoming bottleneck.
   - *Pilot*: Track B_start - fork_release for 5 cases; measure join_ready and downstream_queue; compare with baseline.

2. **Add one F resource (total 3 instead of 2) or buffer at F**:

   - *How*: Introduce temporary F buffer or schedule F with capacity 1.5 per minute, or let F start if resource free.
   - *Throughput*: Slightly increase max throughput if F was previously congested; in data, F1/F2 alternate, some downstream_queue >0, so buffer helps.
   - *Flow-time tail*: Downstream_queue tail reduces (max 2010 min), average down 13~7 min.
   - *Resource utilization*: F utilization may stay same or decrease idle time; no new branch bottleneck.
   - *New bottlenecks*: Less likely; branches already have queues, F is downstream, so reducing F queue is safe.
   - *Pilot*: Deploy F buffer of 30 min; monitor downstream_queue; measure final_start - join_ready; if <5 min often, success.

- Risks:

  - Branch queue reduction assumes B resource availability; if B resource always busy, queue persists. Pilot measures actual B_start.

  - Adding F capacity may not help if branch stage is longer than F queue; but data shows branch join often precedes F queue, so F queue is significant.

  - Reducing A queue (option 1) has low impact as A rarely critical; avoid wasting effort on A.

# 1. Delay-decomposition definitions

- `upstream_elapsed(c)` = `fork_release(c)` - `arrival(c)`: Time from case entry to when all branch work is *permitted* to begin (fork release). This captures the upstream preparation phase before branches can start.

- For branch `i  {A,B,C}` and case `c`:
  - `queue_i(c)` = `start_i(c)` - `fork_release(c)`: Time branch `i` waits for its resource *after* the fork release. By scenario definition, `start_i(c)  fork_release(c)`, so `queue_i(c)  0`. This is the branch-specific queue waiting *immediately after* the fork.
  - `service_i(c)` = `end_i(c)` - `start_i(c)`: Active work duration for branch `i`. No queueing *during* service is assumed; service starts at `start_i` and ends at `end_i` as logged.

- `join_ready(c)` = max(`A_end(c)`, `B_end(c)`, `C_end(c)`)`: Earliest possible time `F` may start, since `F` can begin only after *all* branches complete. Not directly logged; inferred from branch end times. This is a definition under the stated rule ("F may start only after all three branches have completed").

- `downstream_queue(c)` = max(0, `final_start(c)` - `join_ready(c)`)`: Time `F` spends waiting to start *after* all branches are done. Represents queueing at the final station when `final_start > join_ready`. If `final_start  join_ready`, `downstream_queue(c) = 0` (no queue).

- `final_service(c)` = `final_end(c)` - `final_start(c)`: Time `F` takes to complete the release decision. Fixed per case as logged.

- `total_flow_time(c)` = `final_end(c)` - `arrival(c)`: Overall case flow time from arrival to final completion. This is the observable, ground-truth metric.

- `elapsed_fork_join(c)` = `join_ready(c)` - `fork_release(c)`: Time from when branches can start (fork release) to when all branches are done (join ready). This is the *stage duration* for the parallel branch phase, not a sum of branch times.

- `sync_wait_i(c)` = max(0, `join_ready(c)` - `end_i(c)`) *for analysis only*: Time between branch `i`'s completion and when `F` becomes ready to start (`join_ready`). **Important**: This is *not* a queueing time experienced by branch `i` (the branch is already finished at `end_i`); it is a temporal gap used *solely* to identify which branch determines `join_ready` (the last-completing branch). Thus, summing `sync_wait_i` over branches does **not** represent elapsed branch stage time and avoids double-counting when analyzing influence.

- **Why summing all branch synchronization waits would double count**: If one naively added `sync_wait_i = join_ready - end_i` for all branches (treating it as actual waiting), the sum would be `(k-1)*join_ready - sum_{non-last} end_i` for `k=3`. Since `join_ready` is determined by the *latest* `end_i`, this sum mixes the latest completion with earlier ones and does not correspond to any physical queue length. It would incorrectly inflate perceived influence of non-last branches if treated as elapsed time. Instead, `elapsed_fork_join = join_ready - fork_release` correctly gives the stage duration, while per-branch `queue_i + service_i` are disjoint (each branch’s queue and service are unique to that branch). Double-counting occurs only if one mistakenly adds `sync_wait_i` to flow time components; our decomposition separates `queue_i` (branch queue after fork), `service_i` (branch work), `downstream_queue` (F queue after join), and `upstream_elapsed`, with `join_ready` used only for identification (not summation in flow time).

# 7. Limits of inference

The provided timestamps (arrival, fork_release, branch starts/ends, final start/end) are complete-event data accurate to one minute, but they do **not** reveal the following:

- **Branch resource capacities**: The data shows only one branch instance per case (e.g., A_start, A_end), so we cannot know how many resources support branch A/B/C (e.g., is there 1 or 2 A resources?). `queue_i = start_i - fork_release` estimates wait after fork_release but assumes no resource contention *within* the branch phase beyond the observed queue; we cannot confirm if queues arise from resource limits or scheduling policies.

- **Preemption**: Branch intervals are logged as continuous from `start_i` to `end_i` (no intermediate events), so we cannot infer if work could be preempted (e.g., paused for F availability). Thus `service_i = end_i - start_i` is the total active time observed; we do not know if part could have been done later.

- **Exact F scheduling policy**: `final_start` is the earliest F can start in the logged data, but we cannot distinguish if it started immediately at `join_ready` (no F queue) or was delayed due to F resource busy (e.g., F1/F2 contention). The computed `downstream_queue = final_start - join_ready` is correct *if* `final_start  join_ready` and F starts as soon as possible after branches finish; however, if the organization uses a release policy (e.g., F starts at a fixed time regardless of `join_ready`), `downstream_queue` might overstate queue. Data shows `final_start  join_ready` consistently, so `downstream_queue  0` is valid under the "start only after all branches" rule. We cannot know if F could have started earlier in some cases due to policy.

- **Causation vs correlation**: We can observe that cases where a branch is critical (sets `join_ready`) often have larger downstream queues (e.g., B-critical cases frequently have downstream 15–20 min), but we cannot prove that reducing B queue *causes* downstream reduction without intervention; it's a consistent pattern in the data. However, we cannot rule out external factors (e.g., arrival rate changes), though the data is snapshot-like with no time series given.

- **New bottlenecks from changes**: Counterfactuals estimate effects (e.g., B queue reduction reduces `join_ready`), but we cannot simulate long-term stability (e.g., if F capacity increases, could branches start earlier causing F to wait less, but branch queues might increase if resources compete — however, scenario says "branches can queue independently", so no direct branch-F resource conflict). Still, without observing multi-case dynamics, pilot testing is necessary to verify.

- **Double-counting avoidance**: The decomposition explicitly separates `queue_i` (after fork), `service_i`, `downstream_queue`, and uses `join_ready = max(end_i)` for criticality. PM4Py's standard directly-follows or performance DFG would identify parallel branches but not the `join_ready` constraint or downstream queue length; it might infer that F follows all branches but not the exact gap `final_start - join_ready`. Thus custom pandas max-based calculation is necessary and correct for this scenario.

In summary: we can accurately compute `upstream_elapsed`, `queue_i`, `service_i`, `join_ready`, `downstream_queue`, and `total_flow_time` from logged events. We can identify which branch is critical per case (unique max end). We cannot infer resource counts, preemption, exact F release policy nuances, or long-term bottleneck emergence without additional data (e.g., multi-case logs with timing overlaps). Counterfactual estimates are conservative and based on per-case arithmetic; pilot validation is recommended for redesigns.
