# 1. Evidence Ledger

The 30 observed traces, the DFG, the domain rules (D1–D7), and the stakeholder/data-quality statements (S1–S7) are catalogued below. A recurring theme: a directly-follows relation observed in *both* directions (e.g. Credit Check → Engineering Review and Engineering Review → Credit Check) is consistent with concurrency, but it is *also* consistent with an exclusive choice between two sequential orderings, or with a data artifact (equal completion timestamps broken by ingestion index). With completion-only timestamps we never observe overlap of *durations*; we only observe an *order of finish events*. Two finish-order permutations therefore under-determine the underlying relation: they cannot distinguish true parallelism (`AND`), a modeled interleaving/partial order, or an `XOR` over two sequences. This is the central identifiability gap of the whole exercise.

**Why bidirectional DFG edges do not prove concurrency.** A concurrency (`AND`) construct generates *all* interleavings of the finish events, so both CC→ER and ER→CC would appear. But an `XOR` between the two sequences ⟨CC, ER⟩ and ⟨ER, CC⟩ produces exactly the same two directly-follows edges, and so does a partial order that leaves CC and ER unordered. Frequencies (17 vs 11) merely reflect how often each finish order occurred; they do not reveal whether the activities overlapped in time. Because only completion timestamps exist (S7), overlap is unobservable in principle. Hence "both directions present" is necessary but not sufficient for concurrency, and we treat the CC/ER relation as a genuinely undecided hypothesis (D7).

# 2. Shared Assumptions

Common to `model_conservative`, `model_balanced`, and `model_permissive`:

- **A1 — Event-completion semantics.** Every event is a *completion* event (S7). Ordering reflects finish order only; ties are ingestion-index artifacts. No statement about start times, duration, or true overlap is derivable. Therefore any `AND`/partial-order we introduce is a *modeling hypothesis*, not an observation.
- **A2 — Fixed boundaries.** Register Order is the unique start and Archive Case the unique end (D1, start/end activities = 30/30).
- **A3 — Deterministic tail.** Approve Configuration → Release Production → Archive Case is a fixed sequence (DFG all 30; D2). AC is the synchronizing point that all upstream pre-requisites must precede.
- **A4 — CC and ER both required before AC.** Every trace contains both Credit Check and Engineering Review before Approve Configuration (D3, all variants). Models differ only in the *relation* between CC and ER, not in their presence.
- **A5 — Supplier Confirmation optionality.** SC is present in 22/30 and absent in 8/30 (V3+V4). We treat SC as *optional in control flow*. **Disclosed abstraction:** two distinct causes are conflated into one XOR-skip branch — (a) legitimate stocked-component skips (S4) and (b) 5–10% integration-dropped SC events (S5). Because the external/stocked attribute was not exported (S5), we cannot distinguish them; the "skip" branch therefore represents *"SC absent for either reason."* This is a deliberate over-simplification, flagged per the task.
- **A6 — Expedite Review optionality.** Expedite is optional and occurs at most once (D6, 2/30). Modeled as an optional (XOR-with-silent) branch executed after both checks and before AC.
- **A7 — Optionality representation.** Optionality is encoded as `XOR(activity, τ)` (a silent skip) in process trees, and as an `OperatorPOWL(Operator.XOR, [activity, SilentTransition()])` node embedded in partial orders for POWL models. We do not use duplicate labels except where explicitly discussed for the conservative XOR enumeration.
- **A8 — No hidden activities.** The eight labels are the complete alphabet; no unlogged mandatory steps are assumed.
- **A9 — S1 is treated as a claimed constraint, not ground truth**, because it is directly contradicted by observed ER-first traces (V2, V4). Only the conservative model preserves a CC-first *option*; none enforces S1 as a hard global rule.

# 3. Conservative Candidate

**Inductive-bias statement.** The conservative model minimizes admitted behavior: it should accept (close to) *only* the behavior actually witnessed, plus what high-confidence rules force. It refuses to generalize CC/ER into concurrency (which would multiply admitted interleavings), refuses to let SC float freely, and encodes exactly the observed structural shapes as an explicit choice (`XOR`) over the seven observed variant skeletons, collapsed where they share the fixed head/tail. Its bias is toward *precision over generalization*: it will underfit (reject plausible unseen behavior) rather than overfit (admit unsupported behavior). It is the right object for compliance auditing, not for prediction.

**Compact formal expression.** Let the fixed tail be `T = →(Approve Configuration, Release Production, Archive Case)`. The model is an exclusive choice over the observed pre-AC skeletons:

```
model_conservative =
  →( Register Order,
     ×( →(CC, ER),                 # V1, V3 head (SC handled by variant)
        →(ER, CC),                 # V2, V4 head
        →(CC, ER, SC),             # V1 with SC
        →(ER, CC, SC),             # V2 with SC
        →(CC, SC, ER),             # V5
        →(CC, ER, SC, Expedite),   # V6
        →(ER, CC, Expedite, SC) ), # V7
     Approve Configuration, Release Production, Archive Case )
```

To keep the tree faithful and avoid duplicating the whole tail, only the *pre-AC* region is enumerated as an XOR; the shared `→(AC, RP, Archive)` tail is factored out once. Because each XOR branch is a distinct sequence of *the same* labels (CC, ER, SC, Expedite recur across branches), a Petri-net conversion will introduce **duplicate/relabeled transitions** for CC, ER, SC per branch.

**PM4Py code — `model_conservative` (ProcessTree via string):**

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Enumerated XOR over observed pre-AC skeletons, shared tail factored out.
# Abbreviations expanded to full labels via parse_process_tree.
conservative_tree_str = (
    "-> ( 'Register Order', "
    "    X ( -> ( 'Credit Check', 'Engineering Review' ), "
    "        -> ( 'Engineering Review', 'Credit Check' ), "
    "        -> ( 'Credit Check', 'Engineering Review', 'Supplier Confirmation' ), "
    "        -> ( 'Engineering Review', 'Credit Check', 'Supplier Confirmation' ), "
    "        -> ( 'Credit Check', 'Supplier Confirmation', 'Engineering Review' ), "
    "        -> ( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review' ), "
    "        -> ( 'Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation' ) ), "
    "    'Approve Configuration', 'Release Production', 'Archive Case' )"
)

model_conservative = pm4py.parse_process_tree(conservative_tree_str)
```

**Behavior deliberately excluded.**
- SC starting after ER-only when SC is present in the CC-first branch beyond the enumerated orders (e.g. ⟨ER, CC, SC⟩ *is* included, but ⟨ER, SC, CC⟩ is **not**, since it was never observed).
- Expedite in any position other than the two observed placements (no ⟨CC, ER, Expedite, SC⟩ etc. unless it matches V6/V7 exactly).
- Any interleaving of CC/ER as concurrency; only the two witnessed finish orders are allowed.
- SC skipped *together with* Expedite present (never observed).

**Known underfitting risks.**
- Rejects clearly plausible unseen combinations (e.g. Expedite in the SC-skip case, or ⟨ER, SC, CC⟩) that domain rules would permit — high precision, poor generalization.
- **Duplicate-label / scalability problem:** enumerating variants means CC, ER, SC appear in many branches; the Petri net gets many transitions labelled identically, which (i) complicates alignment-based diagnostics (label ambiguity), and (ii) scales combinatorially — k optional/reorderable activities can produce O(k!) branches. This approach is defensible only because the observed variant set is tiny (7). It does not scale and is brittle to any new variant.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model encodes the *most plausible generalization* while explicitly quarantining uncertainty. It commits to a **partial order (POWL)**: CC and ER are left mutually unordered (both must complete before AC, but their relative order is free), reflecting D3/D7/S2 without asserting true concurrency; SC is an *optional* activity whose start is gated on *at least one* of CC/ER (D5) and which, when present, precedes AC (D4); Expedite is optional (≤1), gated after *both* checks, unordered w.r.t. SC, and before AC (D6/S6). This generalizes beyond the seven witnessed orders (it admits, e.g., ⟨ER, SC, CC⟩) but stays within the domain rules. Its bias balances precision and recall: it will admit some unobserved-but-plausible traces and exclude domain-violating ones.

**How the four relations are decided.**
- **Credit Check vs Engineering Review → partial order (unordered), *not* AND, *not* sequence.** Both finish orders are frequent (V1 17 vs V2/V4 11), ruling out a fixed sequence and refuting S1 as a hard rule. We do *not* use an explicit `AND` operator because completion-only data (S7, D7) cannot evidence true overlap; a POWL partial order with no edge between CC and ER captures "either finish order is legal" without over-claiming concurrency. This is the honest middle: interleaving is *allowed*, concurrency is *not asserted*.
- **Supplier Confirmation → optional, start gated by ≥1 check (D5).** V5 (⟨CC, SC, ER⟩) shows SC can precede ER, so SC is *not* joined on both checks. We model SC as an optional node placed with a precedence edge from the *earlier-available* check region. In a strict partial order we cannot encode "after CC OR after ER" directly (partial orders express AND-joins on edges), so the balanced model places SC unordered w.r.t. CC and ER individually but ordered before AC, and represents optionality via an inner XOR-with-silent. **Disclosed abstraction:** "gated by either check" is approximated by "unordered with the checks but before AC," which is slightly more permissive than D5 literally states.
- **Expedite Review → optional XOR(τ), after both checks, before AC, unordered vs SC (S6/D6).** Placed with edges from CC and ER into the Expedite node and from Expedite to AC; no edge to/from SC.
- **Approve Configuration → synchronizing join.** All of {CC, ER, and SC-or-its-skip, Expedite-or-its-skip} precede AC (edges into AC), then the fixed tail.

**Compact formal expression (POWL partial order).** Nodes: `RO, CC, ER, SC?=×(SC,τ), EX?=×(Expedite,τ), AC, RP, Arch`. Edges (`→` = strict precedence):
`RO→CC, RO→ER, CC→SC?, ER→SC?, CC→EX?, ER→EX?, SC?→AC, EX?→AC, CC→AC, ER→AC, AC→RP, RP→Arch`. No edge between CC and ER (unordered); no edge between SC? and EX? (unordered).

**PM4Py code — `model_balanced` (POWL):**

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

RO   = Transition(label="Register Order")
CC   = Transition(label="Credit Check")
ER   = Transition(label="Engineering Review")
AC   = Transition(label="Approve Configuration")
RP   = Transition(label="Release Production")
ARCH = Transition(label="Archive Case")

# Optional Supplier Confirmation: XOR(SC, tau)
SC_opt = OperatorPOWL(operator=Operator.XOR,
                      children=[Transition(label="Supplier Confirmation"),
                                SilentTransition()])
# Optional Expedite Review (<=1): XOR(Expedite, tau)
EX_opt = OperatorPOWL(operator=Operator.XOR,
                      children=[Transition(label="Expedite Review"),
                                SilentTransition()])

model_balanced = StrictPartialOrder(
    nodes=[RO, CC, ER, SC_opt, EX_opt, AC, RP, ARCH]
)
order = model_balanced.order
# Register Order first
order.add_edge(RO, CC)
order.add_edge(RO, ER)
# CC and ER unordered w.r.t. each other (NO edge between them)
# SC gated after checks (approx of "either check"), optional
order.add_edge(CC, SC_opt)
order.add_edge(ER, SC_opt)
# Expedite after both checks, optional
order.add_edge(CC, EX_opt)
order.add_edge(ER, EX_opt)
# SC and Expedite unordered w.r.t each other (NO edge between them)
# Everything joins before Approve Configuration
order.add_edge(CC, AC)
order.add_edge(ER, AC)
order.add_edge(SC_opt, AC)
order.add_edge(EX_opt, AC)
# Deterministic tail
order.add_edge(AC, RP)
order.add_edge(RP, ARCH)
```

**Behavior deliberately excluded.**
- CC/ER *repetition* or loops (no evidence).
- SC or Expedite appearing *after* AC (violates D4/D6).
- Expedite occurring more than once, or without both checks.
- Multiple SC occurrences.

**Known underfitting/overfitting risks.**
- *Overfitting-away* (under-permission): the "SC after both checks" edges are slightly stricter than D5 ("either check"); a case where SC finishes before one check would be rejected even though D5 permits it.
- *Over-permission*: by leaving CC/ER unordered, it admits ⟨ER, SC, CC, …⟩ style traces never observed — plausible per rules but unverified. Reasonable but a recall-precision trade the balanced model accepts.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model admits *all* behavior consistent with the *broad* domain rules, generalizing aggressively: CC and ER run in explicit **concurrency (`AND`/parallel)**, SC and Expedite are both fully optional and concurrent with the checks (subject only to "before AC"), and it commits to the concurrency hypothesis that S2 asserts. Its bias favors *generalization/recall over precision*: it will accept many unobserved interleavings. It is suited to exploration and "what-if" playout, not compliance. The forbidden region is deliberately narrow — only violations of the *high-confidence* rules (D1, D2, and "both checks before AC," AC→RP→Archive tail).

**Boundary between reasonable generalization and forbidden behavior.** *Reasonable:* any interleaving of CC, ER, and (optional) SC before AC; Expedite optionally anywhere after both checks and before AC; SC present or absent. *Forbidden (hard):* AC before either check (violates D3); RP without AC (D2); anything before RO or after Archive (D1); SC or Expedite after AC (D4/D6); Expedite without both checks or more than once (D6). Everything between these is admitted.

**Compact formal expression (ProcessTree).**

```
model_permissive =
  →( Register Order,
     ∧( ×(Credit Check … see note), ... )   # conceptual
   )
```
Concretely, using a parallel block over CC, ER and optional SC, then optional Expedite, then the tail:

`→( RO, ∧( CC, ER, ×(SC, τ) ), ×(Expedite, τ), AC, RP, Archive )`.

Note this places optional SC *concurrently* with the checks (SC may finish before, between, or after CC/ER), and Expedite as a sequential optional gate after the parallel block (guaranteeing "after both checks," satisfying D6) and before AC. This is the deliberate over-generalization: it lets SC finish before either check, which D5 does not require but does not strictly forbid.

**PM4Py code — `model_permissive` (ProcessTree):**

```python
import pm4py

permissive_tree_str = (
    "-> ( 'Register Order', "
    "     ^ ( 'Credit Check', "
    "         'Engineering Review', "
    "         X ( 'Supplier Confirmation', tau ) ), "
    "     X ( 'Expedite Review', tau ), "
    "     'Approve Configuration', 'Release Production', 'Archive Case' )"
)

model_permissive = pm4py.parse_process_tree(permissive_tree_str)
```

**Behavior deliberately excluded (even here).**
- AC before completion of both CC and ER (the `∧` block must finish before the sequential AC) — preserves D3.
- RP without AC; activities outside the RO…Archive envelope.
- Expedite before the checks (it is sequential *after* the parallel block).
- Expedite more than once; SC more than once.

**Known overfitting/generalization risks.**
- *Precision collapse:* the `∧` over {CC, ER, SC-opt} admits 12+ interleavings, most never observed (e.g. ⟨SC, CC, ER⟩ before any check-finish, ⟨SC, ER, CC⟩), so precision on the 30 cases will be low.
- *Concurrency over-claim:* asserts true parallelism that S7/D7 say is unknowable — an explicit, disclosed hypothesis, not a fact.
- Conflates SC missingness with optionality even more loosely than balanced (SC can vanish anywhere).

# 7. Comparative Model Matrix

Assessments are qualitative / interval-valued (no fabricated metric values).

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| Expected fitness on 30 observed cases | High (~1.0): all 7 variants explicitly enumerated | High (~1.0): all observed orders lie within the partial order + optional SC/Expedite | High (~1.0): parallel block subsumes all observed interleavings |
| Expected precision risk | Very low precision risk (high precision); admits almost only observed | Moderate: admits some unseen but rule-consistent interleavings | High precision risk (low precision): admits many unseen interleavings |
| Generalization potential | Poor: rejects plausible unseen behavior | Good: generalizes CC/ER order and SC placement within rules | Very high but indiscriminate |
| Structural simplicity | Low (many XOR branches, duplicate labels) | Moderate (one partial order + two optional XORs) | High (compact tree: one AND, two XOR-skips, sequence tail) |

| Robustness to missing SC events (S5) | Fragile: a dropped SC must match a specific no-SC branch; new SC-skip order rejected | Robust: SC optionality absorbs 5–10% drops in any order | Most robust: SC fully optional/concurrent |
| Handling of unseen interleavings | Rejects them (by design) | Admits rule-consistent ones, rejects rule-violating | Admits nearly all pre-AC interleavings |
| Suitability: compliance vs exploration | Compliance/audit (conformance gate) | Balanced default for monitoring + prediction | Exploration / what-if / stress-testing only |

```python
)
model_permissive = pm4py.parse_process_tree(permissive_tree_str)

candidates = {"conservative": model_conservative,
              "balanced": model_balanced,
              "permissive": model_permissive}

# ---------------------------------------------------------------
# 2-5. Convert, soundness, metrics, playout
# ---------------------------------------------------------------
def evaluate(name, model):
    print(f"\n===== {name} =====")
    net, im, fm = pm4py.convert_to_petri_net(model)
    try:
        sound = pm4py.check_soundness(net, im, fm, print_diagnostics=True)
        print("soundness:", sound)
    except Exception as e:
        print("soundness check unavailable:", e)
    for fn, label in [
        (lambda: pm4py.fitness_alignments(log, net, im, fm), "fitness_alignments"),
        (lambda: pm4py.precision_alignments(log, net, im, fm), "precision_alignments"),
        (lambda: pm4py.generalization_tbr(log, net, im, fm), "generalization_tbr"),
        (lambda: pm4py.simplicity_petri_net(net, im, fm), "simplicity"),
    ]:
        try:
            print(label, "=", fn())
        except Exception as e:
            print(label, "unavailable:", e)
    # 5. bounded / sampled playout (NOT a proof of language inclusion)
    try:
        played = pm4py.play_out(net, im, fm)  # sampled/bounded traces
        seen = set()
        for tr in played:
            seen.add(tuple(ev["concept:name"] for ev in tr))
        print(f"sampled playout produced {len(seen)} distinct traces (sample, not exhaustive)")
    except Exception as e:
        print("playout unavailable:", e)
    return net, im, fm

nets = {n: evaluate(n, m) for n, m in candidates.items()}

# ---------------------------------------------------------------
# 6. Manual positive/negative trace suite (token-based replay per trace)
# ---------------------------------------------------------------
from pm4py.algo.conformance.tokenreplay import algorithm as tr_alg

positive = [  # should fit balanced/permissive; conservative fits only observed
    "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case",
    "Register Order,Engineering Review,Supplier Confirmation,Credit Check,Approve Configuration,Release Production,Archive Case",  # unseen, balanced/permissive
]
negative = [  # must be rejected by all
    "Register Order,Credit Check,Approve Configuration,Engineering Review,Release Production,Archive Case",  # AC before ER (D3)
    "Register Order,Credit Check,Engineering Review,Approve Configuration,Supplier Confirmation,Release Production,Archive Case",  # SC after AC (D4)
]

def replay_fit(name, net, im, fm, trace_strs):
    sub = pm4py.parse_event_log_string(trace_strs)
    res = tr_alg.apply(sub, net, im, fm)
    return [r["trace_is_fit"] for r in res]

for name,(net,im,fm) in nets.items():
    print(f"\n[{name}] positive fit:", replay_fit(name,net,im,fm,positive))
    print(f"[{name}] negative fit (want all False):", replay_fit(name,net,im,fm,negative))
```

**Stated limitations.** Sampled/bounded `play_out` enumerates a *finite sample* of the (for the permissive model, combinatorially large) language; it **cannot prove language inclusion or equivalence** between models, nor exhaustively certify that a model rejects every undesirable trace. Precision/generalization from alignments are heuristic aggregates, not proofs. Duplicate-labelled transitions in the conservative net can make alignment costs ambiguous. For infinite/large languages we rely on the manual positive/negative suite plus targeted playout, and explicitly do *not* claim the sample characterizes the full language.

# 9. Recommendation and Data-Collection Plan

**Immediate use:** `model_balanced`. It fits all 30 cases, encodes the high-confidence rules (D1–D4, D6), honestly treats CC/ER order as unordered rather than asserting concurrency (respecting D7/S7), and absorbs 5–10% missing SC events (S5) via optionality — the best precision/generalization/explainability trade for monitoring and prediction.

**Sensitivity analysis:** `model_conservative` (as a strict conformance/compliance gate — flags anything not previously witnessed) paired with `model_permissive` (to explore how much extra behavior the concurrency hypothesis would license). Using conservative + permissive as *bounds* brackets the balanced model's assumptions.

**Data-collection plan to resolve the core ambiguities.**
- **Add lifecycle timestamps (start + complete)** for Credit Check and Engineering Review. This is the single most informative change: overlapping start/complete intervals would confirm true concurrency (favor permissive `∧`); strictly non-overlapping intervals with a consistent order would favor a sequence or XOR-of-orders (favor conservative/S1). Resolves D7 directly.
- **Export the external/stocked attribute** (and repair the SC integration gap, S5). This separates *legitimate SC skips* (stocked) from *missing events* (integration bug), decoupling A5's conflation. Then SC optionality can be made *conditional* (data attribute → SC required), sharpening both precision and D3/D4.
- **Collect more Expedite Review cases** to estimate its true rate and confirm its ordering vs SC (S6): does Expedite ever occur without SC, and is it truly unordered w.r.t. SC?
- **Maximally informative future traces:**
  - A trace where SC *completes before any check completes* → tests D5's "either check" and discriminates balanced (rejects) vs permissive (admits).
  - A trace with ⟨ER, SC, CC⟩ ordering → distinguishes conservative (rejects) from balanced/permissive (admit).
  - A trace with start/complete overlap of CC and ER → distinguishes concurrency (permissive) from sequence/XOR (conservative).
  - A stocked-flagged case that skips SC → confirms optionality is legitimate, not missingness.

# 10. Uncertainty Statement

Calibrated confidence per major decision (High ≈ >85%, Medium ≈ 50–80%, Low ≈ <40%):

- **RO start / Archive end / AC→RP→Archive tail (High).** Backed by all 30 cases and D1/D2.
- **Both CC and ER required before AC (High).** Universal in data + D3.
- **CC/ER modeled as unordered rather than sequential (High that fixed sequence is wrong; Medium on the specific "unordered partial order" choice vs true `AND`).** Both finish orders are common, refuting S1 as a hard rule; but whether the true relation is concurrency or an XOR of two sequences is genuinely unknowable from completion timestamps (D7, S7).
- **SC as optional (Medium-High).** 8/30 absent supports optionality; but S5 says 5–10% of SC events are simply *missing*, so an unknown fraction of the 8 "skips" are data artifacts, not real optionality. Confidence that SC is *sometimes* legitimately skipped is high (S4); confidence in the exact skip rate is low.
- **SC gated on "either check" vs "both checks" (Low-Medium).** D5 (low-med) vs a stricter join reading; the balanced model approximates this and may be slightly off.
- **Expedite optional, ≤1, after both checks, before AC (Medium).** Only 2 observations; ordering vs SC inferred mainly from S6, not data.

**Plausible alternative interpretation that would change the recommendation.** If lifecycle data revealed that Credit Check and Engineering Review genuinely execute in parallel (S2 confirmed) *and* that SC skips are overwhelmingly legitimate stocked-component cases (not missingness), then the **permissive concurrency model would become the correct default**, not merely an exploration tool — the balanced partial order would then be under-permissive and would wrongly flag valid parallel/early-SC executions. Conversely, if timestamps showed CC strictly precedes ER (S1 vindicated, the ER-first traces being logging-tie artifacts per S7), a **CC-then-ER sequential model** would dominate and both the balanced and permissive choices would be over-general. Either finding would materially change the recommendation.
