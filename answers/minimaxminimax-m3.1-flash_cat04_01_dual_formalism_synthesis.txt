# 1. Assumptions and Interpretation

1. **Activities are completion events.** A trace records the order in which activity completions become visible. There are no separate start events, durations, or resource-allocation constraints.

2. **Concurrency means logical concurrency, not simultaneous execution.** “May overlap” means that neither activity must precede the other in the partial order: both can become enabled, and their completions may be interleaved. Because a trace is linear, literal simultaneous completion is not represented.

3. **Risk selection is structural rather than data-driven.** After `Analyze Rootiation`—more precisely, after `Analyze Root Cause` completes—the model chooses exactly one structural route:
   - a single `Supervisor Review`; or
   - a concurrent pair, `Quality Review` and `Regulatory Review`.
   
   The model does not inspect a “low risk” or “high risk” data attribute.

4. **Supplier consultation is an exclusive optional branch.** A choice selects either `Consult Supplier` once or an invisible skip transition. Selection is possible only after `Analyze Root Cause`. The actual reason for selecting it is not represented.

5. **A passing inspection is abstracted by loop exit.** The final, successful `Inspect Trial` is represented by exiting the trial loop. Executing `Adjust Parameters` means that the preceding inspection is interpreted as failed and that another trial cycle must follow. Thus, there is no separate “inspection passed” event. Relative to the full data-dependent narrative, both models are intentionally underconstrained about why an inspection succeeds or fails.

6. **A trial cycle contains at least one execution–inspection pair.** A failing inspection causes `Adjust Parameters` and then another `Execute Trial`–`Inspect Trial` cycle. A final inspection completes the loop. There is no initial `Adjust Parameters` and no adjustment after the successful final inspection.

7. **No model-level duplication of visible labels is used.** Each visible activity has one model occurrence. Repeated `Execute Trial` and `Inspect Trial` occurrences at runtime are loop repetitions, not duplicate model nodes. The supplier skip is silent rather than a duplicated visible label. A duplication-based approximation was therefore not needed.

8. **The process-tree policy is a conservative under-approximation of the data-free control-flow behavior.** The chosen tree does not admit a trial before the approval route or an optional supplier consultation is complete. Consequently, it excludes some intended approval/trial and supplier/trial interleavings. This is deliberate: the tree does not admit a trial before its `Plan Verification` and `Design Corrective Action` gates, nor a release before its selected obligations.

9. **The POWL model uses the intended partial-order dependencies directly.** In particular, the approval route and supplier consultation are not forced into the trial’s synchronization join. The trial is gated only by `Plan Verification` and `Design Corrective Action`.

10. **The selected obligations, not all possible obligations, gate release.** A low-risk case waits for `Supervisor Review`; a high-risk case waits for both quality and regulatory review. `Consult Supplier` is awaited only on the branch where it was selected.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | Register Deviation | Contain Material and Analyze Root Cause | Precedence/fork | Every case starts by registering the deviation; the two initial work streams may then proceed independently. |
| D2 | Contain Material | Analyze Root Cause | Concurrency; no order | The two initial streams are explicitly allowed to overlap. |

| D6 | Low-risk route | Supervisor Review | Precedence | The low-risk route consists of supervisor review. |

# 3. PM4Py Process-Tree Model

The following is a schematic expression. `||` denotes parallel composition, `XOR` denotes exclusive choice, `LOOP[do, redo]` uses PM4Py’s do–redo loop convention, and `tau` denotes an invisible skip.

```text
Register Deviation
 ->
 (
     (Contain Material -> Plan Verification)
     ||
     (
         Analyze Root Cause
         ->
         (
             Design Corrective Action
             ||
             (Supervisor Review XOR (Quality Review || Regulatory Review))
             ||
             (Consult Supplier XOR tau)
         )
     )
 )
 -> LOOP[
        do   = (Execute Trial -> Inspect Trial),
        redo = Adjust Parameters
    ]
 -> Release Material
 -> Archive Case
```

The code below constructs that expression directly rather than relying on a parser’s string grammar.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def pt_leaf(label):
    """Create a labeled leaf, or an invisible leaf when label is None."""
    node = ProcessTree(label=label)
    node.operator = None
    node.parent = None
    return node


def pt_op(operator, *children):
    """Create an operator node and establish all direct parent/child links."""
    node = ProcessTree(label=None)
    node.operator = operator
    node.children = list(children)
    for child in node.children:
        child.parent = node
    return node


register_deviation = pt_leaf("Register Deviation")
contain_material = pt_leaf("Contain Material")
analyze_root_cause = pt_leaf("Analyze Root Cause")
plan_verification = pt_leaf("Plan Verification")
design_corrective_action = pt_leaf("Design Corrective Action")
supervisor_review = pt_leaf("Supervisor Review")
quality_review = pt_leaf("Quality Review")
regulatory_review = pt_leaf("Regulatory Review")
consult_supplier = pt_leaf("Consult Supplier")
execute_trial = pt_leaf("Execute Trial")
inspect_trial = pt_leaf("Inspect Trial")
adjust_parameters = pt_leaf("Adjust Parameters")
release_material = pt_leaf("Release Material")
archive_case = pt_leaf("Archive Case")

# A label of None is PM4Py's invisible/silent process-tree leaf.
skip_supplier = pt_leaf(None)

# Exactly one approval route is selected.
high_risk_route = pt_op(
    Operator.PARALLEL,
    quality_review,
    regulatory_review,
)
risk_route = pt_op(
    Operator.XOR,
    supervisor_review,
    high_risk_route,
)

# Consult Supplier is selected at most once, or is silently skipped.
optional_supplier = pt_op(
    Operator.XOR,
    consult_supplier,
    skip_supplier,
)

# These activities become available after root-cause analysis.
post_analysis = pt_op(
    Operator.PARALLEL,
    design_corrective_action,
    risk_route,
    optional_supplier,
)

analysis_branch = pt_op(
    Operator.SEQUENCE,
    analyze_root_cause,
    post_analysis,
)

containment_branch = pt_op(
    Operator.SEQUENCE,
    contain_material,
    plan_verification,
)

# The process-tree join also waits for approval and optional supplier work.
pre_trial_join = pt_op(
    Operator.PARALLEL,
    containment_branch,
    analysis_branch,
)

# PM4Py LOOP convention: the first child is the mandatory body;
# executing the second, redo child causes another execution of the body.
trial_body = pt_op(
    Operator.SEQUENCE,
    execute_trial,
    inspect_trial,
)
trial_loop = pt_op(
    Operator.LOOP,
    trial_body,
    adjust_parameters,
)

tree = pt_op(
    Operator.SEQUENCE,
    register_deviation,
    pre_trial_join,
    trial_loop,
    release_material,
    archive_case,
)
```

The tree represents the start/end rules, the two initial branches, the containment-to-planning and analysis-to-design dependencies, the exclusive risk route, the concurrent high-risk reviews, the at-most-once supplier choice, the trial loop, and release/archive ordering.

Its deliberate approximation is the `pre_trial_join`. A process tree cannot independently join only `Plan Verification` and `Design Corrective Action` while leaving the approval route and supplier branch outside that join. Consequently:

- The tree requires the approval route to complete before `Execute Trial`, excluding intended traces where approval overlaps or follows trial work.
- It requires a selected `Consult Supplier` to complete before `Execute Trial`, excluding intended supplier/trial overlap.
- It preserves the safe release synchronization and does not introduce a trial before planning and design are complete.

The supplier skip is silent, so an omitted consultation is not a visible event. Inspection outcomes remain data-semantic abstractions: loop exit is interpreted as success and redo as failure. Parallel branches express logical concurrency through possible interleavings, not simultaneous event firing.

# 4. PM4Py POWL Model

A compact schematic description is:

```text
Register -> {Contain, Analyze}

Contain -> Plan
Analyze -> Design
Analyze -> Risk = XOR(Supervisor, (Quality || Regulatory))
Analyze -> Supplier = XOR(Consult, SILENT)

Plan   -> TrialLoop
Design -> TrialLoop

TrialLoop = LOOP(body = Execute -> Inspect, redo = Adjust)

Risk, Supplier, TrialLoop -> Release -> Archive
```

Here `||` means that the two reviews have no precedence edge. Edges to `Risk`, `Supplier`, and `TrialLoop` are edges to operator nodes; PM4Py expands each such edge to the operator’s entry.

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register_deviation = Transition(label="Register Deviation")
contain_material = Transition(label="Contain Material")
analyze_root_cause = Transition(label="Analyze Root Cause")
plan_verification = Transition(label="Plan Verification")
design_corrective_action = Transition(label="Design Corrective Action")
supervisor_review = Transition(label="Supervisor Review")
quality_review = Transition(label="Quality Review")
regulatory_review = Transition(label="Regulatory Review")
consult_supplier = Transition(label="Consult Supplier")
execute_trial = Transition(label="Execute Trial")
inspect_trial = Transition(label="Inspect Trial")
adjust_parameters = Transition(label="Adjust Parameters")
release_material = Transition(label="Release Material")
archive_case = Transition(label="Archive Case")

skip_supplier = SilentTransition()

# High-risk reviews are a nested partial-order fragment with no edge.
# They are therefore concurrent and may complete in either order.
high_risk_reviews = StrictPartialOrder(
    nodes=[quality_review, regulatory_review]
)

# Exactly one approval route.
risk_xor = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor_review, high_risk_reviews],
)

# Optional supplier consultation: one visible execution or one silent skip.
supplier_xor = OperatorPOWL(
    operator=Operator.XOR,
    children=[consult_supplier, skip_supplier],
)

# The mandatory loop body is Execute Trial followed by Inspect Trial.
trial_body = StrictPartialOrder(
    nodes=[execute_trial, inspect_trial]
)
trial_body.order.add_edge(execute_trial, inspect_trial)

# Executing Adjust Parameters causes another mandatory trial body.
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, adjust_parameters],
)

# Make the nested parent/child relationships explicit.
supervisor_review.parent = risk_xor
high_risk_reviews.parent = risk_xor
quality_review.parent = high_risk_reviews
regulatory_review.parent = high_risk_reviews

consult_supplier.parent = supplier_xor
skip_supplier.parent = supplier_xor

trial_body.parent = trial_loop
adjust_parameters.parent = trial_loop
execute_trial.parent = trial_body
inspect_trial.parent = trial_body

top_nodes = [
    register_deviation,
    contain_material,
    analyze_root_cause,
    plan_verification,
    design_corrective_action,
    risk_xor,
    supplier_xor,
    trial_loop,
    release_material,
    archive_case,
]

powl = StrictPartialOrder(nodes=top_nodes)
for node in top_nodes:
    node.parent = powl

# Registration and the two independent initial work streams.
powl.order.add_edge(register_deviation, contain_material)
powl.order.add_edge(register_deviation, analyze_root_cause)

# Split dependencies.
powl.order.add_edge(contain_material, plan_verification)
powl.order.add_edge(analyze_root_cause, design_corrective_action)

# Route selection occurs only after root-cause analysis.
powl.order.add_edge(analyze_root_cause, risk_xor)
powl.order.add_edge(analyze_root_cause, supplier_xor)

# The trial waits for planning and design, but not for approvals/supplier.
powl.order.add_edge(plan_verification, trial_loop)
powl.order.add_edge(design_corrective_action, trial_loop)

# Release synchronizes the independent obligations.
powl.order.add_edge(risk_xor, release_material)
powl.order.add_edge(supplier_xor, release_material)
powl.order.add_edge(trial_loop, release_material)

# Archive is last.
powl.order.add_edge(release_material, archive_case)
```

The intentionally unconnected pairs remain concurrent as follows:

- `Contain Material` and `Analyze Root Cause` have a common predecessor but no order between them.
- `Plan Verification` may overlap root-cause analysis, design, supplier consultation, approvals, or trial work; only containment constrains it.
- `Design Corrective Action` may overlap planning, the approval route, supplier consultation, or trial work.
- `Quality Review` and `Regulatory Review` have no edge between them.
- The selected approval route has no edge to the trial in either direction, so approval may finish before, during, or after the trial cycle.
- `Consult Supplier` has no edge to design, planning, approval, or trial work; only analysis precedes its selection and release follows its completion or skip.
- `Adjust Parameters` is constrained only by the loop structure: it follows an inspection and must be followed by another execution–inspection body.
- No unrelated serialization edges are added. Thus, every other pair not governed by one of the listed dependencies is eligible for either completion order.

As in the process tree, supplier omission is represented by silent behavior, and the reason for retrying or exiting the trial loop is not encoded as data.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Start and end | Every case starts with registration and ends with archiving. | Exact. | Exact. | None structurally. | Prevents malformed case lifecycles from being accepted. |
| Two initial work streams | Containment and root-cause analysis may overlap. | Exact parallel branches; completions may interleave. | Exact: both follow registration and have no mutual edge. | None structurally. | Captures the intended early parallelism. |
| Planning/design split | Planning follows containment; design follows analysis; neither has an unnecessary dependency on the other. | Exact within the two branches. | Exact direct edges. | None structurally. | Avoids falsely serializing the two work products. |
| Risk route | Exactly one low- or high-risk route is selected after analysis. | Exact XOR structure. | Exact XOR structure. | Control-flow exact; data-semantic underconstraint in both because the actual risk value is absent. | A structurally valid trace can still be inconsistent with the case’s real risk classification. |
| Concurrent high-risk reviews | Both reviews are required and may complete in either order. | Exact parallel pair. | Exact nested partial order with no edge. | None structurally. | Prevents omission of either review while preserving concurrency. |
| Approval/trial overlap | Approval may finish before, during, or after trial work. | Approval must finish before the trial starts. | No approval–trial edge exists. | Process tree is overconstrained and under-approximates allowed traces; POWL is structurally exact. | Tree-based conformance or performance estimates would understate approval/trial overlap. |
| Optional supplier consultation | Zero or one consultation, starting after analysis and completing before release if selected. | Selection and at-most-once behavior are exact; a selected consultation must also finish before trial start. | Selection is exact through XOR with a silent skip; consultation may overlap all preparatory and trial work. | Process tree overconstrains supplier timing; both models are data-semantic underconstrained about whether consultation is selected. | POWL better supports supplier-involved case timing and avoids treating a deliberate skip as a visible event. |
| Repeat-until behavior | Failed inspection causes adjustment and another cycle; success ends the loop without adjustment. | Do–redo loop with exit interpreted as success. | Do–redo loop with exit interpreted as success. | Structurally faithful, but data-semantic underconstraint in both: retry versus exit is freely chosen. | Model traces cannot, by themselves, prove that a real inspection result justified the decision. |
| Release synchronization | Release waits for the selected approval route, selected supplier consultation, and successful trial. | Exact, but with the stronger pre-trial approval/supplier ordering. | Exact through the three incoming synchronization obligations. | Process tree overconstrained; POWL structurally exact. | POWL avoids false rejection of cases in which approval or supplier work overlaps the trial. |
| Duplicate-label risk | One model occurrence per visible label; runtime loop repetitions are expected. | No visible duplicates. | No visible duplicates. | None. | Label-frequency analytics can distinguish model duplication from legitimate repeated trial events. |

# 7. Preferred Representation and Validation Plan

The canonical representation should be the **POWL model**. Its direct edges preserve the intended non-block-structured dependencies:

- planning is gated only by containment;
- design is gated only by analysis;
- the trial is gated by planning and design;
- approvals and supplier consultation are independent of trial progress;
- release is the synchronization point.

The process tree is useful as a conservative approximation and as a comparison model, but its broad pre-trial join produces systematic false negatives for approval/trial and supplier/trial overlap.

A concrete validation plan is:

1. **Construct and inspect both models.**
   - Verify the source-level parent/child structures.
   - Inventory all transitions and operators.
   - Confirm that the tree and POWL each contain exactly one visible node for each narrative activity.
   - Confirm that the POWL root has all the explicit edges shown in the code.

2. **Convert to accepting Petri nets.**

   ```python
   import pm4py

   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
   ```

   Inspect the initial markings, final markings, silent transitions, and places implementing the XOR and LOOP operators. Conversion success is not evidence of semantic fidelity.

3. **Run soundness checking on both converted nets.**

   ```python
   powl_soundness = pm4py.check_soundness(
       powl_net, powl_im, powl_fm, print_diagnostics=True
   )
   tree_soundness = pm4py.check_soundness(
       tree_net, tree_im, tree_fm, print_diagnostics=True
   )
   ```

   If diagnostics fail, inspect the loop and silent-skip construction rather than assuming that the source model is wrong. Soundness is a structural property of the converted net, not proof that it matches the business narrative.

4. **Use bounded or sampled playout.**
   - Generate at least 1,000 traces from the POWL model and, where supported, from its Petri net.
   - Apply a per-trace event cutoff to control the unbounded retry loop.
   - Normalize traces to visible labels.
   - Check that:
     - low-risk traces contain `Sup` and neither `Qual` nor `RegRev`;
     - high-risk traces contain both `Qual` and `RegRev` and not `Sup`;
     - `Supplier` occurs zero or one time;
     - every `Adjust` is followed by another `Exec`–`Inspect` pair;
     - `Release` occurs after all selected obligations.
   - Absence from a finite sample is not proof of impossibility.

5. **Run exact positive and negative trace tests.**
   - Use `A1`–`A5` as positive tests. Each must have an accepting firing sequence in the POWL net.
   - Use `F1`–`F3` as negative tests. Each must have no accepting firing sequence matching its visible event sequence.
   - A concrete replay procedure is a depth-first search over enabled Petri-net transitions:
     - visible transitions must match the next visible symbol;
     - silent transitions may fire without consuming a visible symbol;
     - the test succeeds only if the final marking is reached.
   - `A3` specifically checks two trial iterations.
   - `F3` specifically checks that an adjustment cannot be the last loop event before release.

6. **Check silent behavior and duplicate labels.**
   - For supplier-absent traces such as `A1`, verify that a silent supplier-skip path reaches release.
   - For supplier-present traces such as `A3` and `A5`, verify exactly one visible `Supplier` event and no silent supplier skip.
   - Audit the source models and converted nets for repeated visible transition labels. Repeated runtime occurrences of `Exec` and `Inspect` are expected; multiple model instances with the same visible label would require explanation.
   - Check that the silent skip is never emitted as a visible `Consult Supplier` event.

7. **Compare the approximations deliberately.**
   - `A4` and `A5` should be accepted by POWL and rejected by the process tree.
   - `F1`–`F3` should be rejected by both.
   - Treat this difference as a regression oracle for the documented tree policy, not as a conversion defect.

Limitations include finite playout coverage, unbounded loop behavior, silent-event ambiguity in real logs, version-dependent conversion details, and the absence of actual risk, supplier-selection, and inspection-result data. In particular, neither soundness checking nor sampled playout proves that an executed model choice corresponds to the real-world case data.

# 8. Final Self-Critique

1. **The inspection semantics remain data-semantic abstractions.** The models cannot prove that a retry was caused by a failed inspection or that loop exit represented a successful inspection. A production model should bind these decisions to explicit data or observable outcomes.

2. **The process-tree model knowingly excludes a substantial family of intended traces.** Its pre-trial join is safe but can materially understate approval/trial and supplier/trial concurrency, so its statistics should not be compared directly with POWL-derived statistics.

3. **Validation cannot establish full narrative fidelity.** Finite replay, soundness checks, and playout sampling can expose implementation errors, but they do not prove that real cases select the correct risk route, make justified supplier decisions, or record inspection outcomes consistently.
