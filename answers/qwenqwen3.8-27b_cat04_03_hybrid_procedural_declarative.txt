import pandas as pd

HOUR = 3600

def _activities(case_df):
    return set(case_df["activity"].dropna())

def _resources(case_df, activity):
    if "resource" not in case_df.columns:
        return None
    vals = case_df.loc[case_df["activity"] == activity, "resource"].dropna()
    if vals.empty:
        return set()
    return set(vals)

def _first_ts(case_df, activity):
    if "timestamp" not in case_df.columns:
        return None
    vals = case_df.loc[case_df["activity"] == activity, "timestamp"].dropna()
    if vals.empty:
        return None
    return float(vals.min())

def _first_ts_after(case_df, activity, after_ts):
    if after_ts is None:
        return None
    sub = case_df[(case_df["activity"] == activity) & (case_df["timestamp"] > after_ts)]
    if sub.empty:
        return None
    return float(sub["timestamp"].min())

def _first_ts_between(case_df, activity, start_ts, end_ts):
    if start_ts is None or end_ts is None:
        return None
    sub = case_df[(case_df["activity"] == activity) &
                  (case_df["timestamp"] > start_ts) &
                  (case_df["timestamp"] < end_ts)]
    if sub.empty:
        return None
    return float(sub["timestamp"].min())

# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. **Case and event model**  
   Each event has at least: `case_id`, `activity`, `timestamp`, and, where required, `resource`. Timestamps in the test cases are relative hours; for temporal calculations I convert them to seconds.

2. **Activity labels are normative**  
   The exact labels given in the scenario are the only labels used in the models and checks.

3. **Accepted vs rejected cases**  
   - A case is treated as **accepted** if `Activate Vendor` occurs.  
   - A case is treated as **rejected** if `Reject Vendor` occurs.  
   - T8 contains both, so it is a contradictory terminal outcome.

4. **Procedural backbone vs cross-cutting behavior**  
   The procedural model represents the stable onboarding backbone:
   - receipt,
   - three initial checks,
   - classification,
   - one terminal route.

   Cross-cutting activities such as `Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, and `Suspend Vendor` are not forced into the block-structured backbone unless doing so would be misleading. They are handled in declarative, log-skeleton, temporal, or external validation layers.

5. **Clarification placement assumption**  
   For the procedural tree, I assume clarification is a **pre-classification data-completeness loop**: it can occur after the three initial checks and before `Classify Risk`, with zero or more request/response cycles.  
   This is an approximation. If the business allows clarification after classification or during approvals, the procedural tree is not sufficient, and the external clarification validator in Section 7 becomes authoritative.

6. **Post-activation behavior**  
   `Change Bank Details`, `Suspend Vendor`, and any additional `Verify Bank Account` after activation are treated as **post-onboarding lifecycle behavior**. They are deliberately excluded from the canonical procedural backbone because:
   - the backbone ends with `Close Onboarding`,
   - `Release First Payment` is constrained to occur at most once by R10,
   - R11 nevertheless mentions “any later Release First Payment”, creating a tension.

   These behaviors are validated externally in Section 7.

7. **Missing attributes**  
   If a required attribute such as `resource` or `timestamp` is missing, the affected check is marked `not evaluated` and routed to manual review. It is not automatically passed.

8. **Temporal profile semantics**  
   Temporal deviations are **warnings**, not automatic control-flow violations. They are compliance monitoring signals, not hard process failures.

9. **Support/confidence metadata**  
   `support` and `confidence` in the DECLARE dictionary are metadata. Setting `support = 1.0` does not make a rule legally binding; the policy interpretation in this document is the normative source.

## R5/R6 conflict

The conflict is:

- **R5, Legal department:** after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` under all circumstances.
- **R6, Operations department:** emergency activation may occur before `Obtain Legal Opinion`, but only when jointly authorized outside the event log, and the opinion must arrive within 24 hours.

These are incompatible if interpreted as unconditional log-only rules.

### Resolution A: Legal-strict

`R5` is treated as absolute for the automated event-log model. `R6` is not merged into the log-only conformance model. If `Sanctions Escalation` occurs and `Activate Vendor` occurs before `Obtain Legal Opinion`, the case fails.

**Compliance risk:**  
This may block legitimate emergency activations. It creates operational risk and may encourage shadow workarounds or after-the-fact documentation.

### Resolution B: Operations-exception

`R6` is treated as a valid exception to `R5`, but only when an external joint-authorization record exists and the legal opinion arrives within 24 hours after activation. Because the event log does not contain the emergency attribute, the automated layer cannot prove the exception. It should therefore report `policy-dependent` or route to manual review. If external evidence is supplied, the case can pass.

**Compliance risk:**  
This creates an audit gap if emergency authorizations are not reliably stored. It may allow unlogged exceptions to be waived manually.

## Chosen resolution for the implemented model

For the implemented model below, I choose **Resolution A: Legal-strict** for the automated log-only layer.

Reason: the event log does not contain the emergency authorization attribute, so the automated layer cannot verify the R6 exception. A conservative compliance baseline should fail the case rather than silently accept an unproven exception.

If the organization decides that operations policy is authoritative, the model can be redeployed with `resolution="operations"` and an external exception store. That is a different policy deployment, not a silent combination of R5 and R6.

# 3. Procedural Backbone

## Compact formal description

The canonical backbone is:

```text
Receive Onboarding Request
  ->
  (
    Capture Master Data
    ||
    Run Sanctions Screening
    ||
    Verify Bank Account
  )
  ->
  loop(
    Request Clarification
    ->
    Receive Clarification
  )*
  ->
  Classify Risk
  ->
  (
    Reject Vendor
    ->
    Close Onboarding
    |
    Manager Approval
    ->
    Activate Vendor
    ->
    Release First Payment
    ->
    Close Onboarding
    |
    Enhanced Due Diligence
    ->
    Compliance Approval
    ->
    Activate Vendor
    ->
    Release First Payment
    ->
    Close Onboarding
  )
```

Where:

- `->` means sequence,
- `||` means parallel/concurrent execution,
- `|` means exclusive choice,
- `loop(...)*` means zero or more iterations.

## Explanation of modeling choices

### Concurrency

The three initial checks are modeled as a parallel node:

```text
Capture Master Data || Run Sanctions Screening || Verify Bank Account
```

This matches the statement that they may proceed concurrently after receipt.

### Choice

After `Classify Risk`, the model uses an exclusive choice:

- reject route,
- low-risk manager-approval route,
- high-risk enhanced-due-diligence/compliance-approval route.

This enforces the primary outcome structure.

### Clarification loops

The clarification loop is placed after the three initial checks and before `Classify Risk`:

```text
loop(Request Clarification -> Receive Clarification)*
```

This allows zero or more clarification cycles before classification.

This is an approximation. If clarification may occur during the parallel checks or after classification, the process tree cannot express that without becoming non-block-structured or requiring a more expressive model. The external clarification validator in Section 7 is then authoritative for the full R3 requirement.

### Terminal outcomes

Each branch ends with `Close Onboarding`:

- rejection branch: `Reject Vendor -> Close Onboarding`
- low-risk branch: `Manager Approval -> Activate Vendor -> Release First Payment -> Close Onboarding`
- high-risk branch: `Enhanced Due Diligence -> Compliance Approval -> Activate Vendor -> Release First Payment -> Close Onboarding`

This enforces that rejection and activation are mutually exclusive in the backbone.

### Deliberately excluded behavior

The procedural backbone deliberately excludes:

- `Sanctions Escalation`,
- `Obtain Legal Opinion`,
- `Change Bank Details`,
- `Suspend Vendor`,
- post-activation additional `Verify Bank Account` events.

Reasons:

1. `Sanctions Escalation` and `Obtain Legal Opinion` can interleave with classification, approvals, and activation in ways that are not cleanly block-structured.
2. `Change Bank Details` and `Suspend Vendor` are post-activation lifecycle behavior.
3. R11 allows another `Verify Bank Account` after activation, which would conflict with a strict backbone tree that places `Verify Bank Account` only before classification.
4. R10 says `Release First Payment` occurs at most once, while R11 mentions “any later Release First Payment”, creating a modeling tension.

Therefore, procedural conformance should be run on a **backbone projection** or with post-activation lifecycle events masked out. Cross-cutting behavior is checked in the other layers.

## Rule semantics table

| Rule | Direction and semantics | Policy rationale |
|---|---|---|
| `existence("Receive Onboarding Request")` | The activity must occur in the case. | Every case starts with receipt. |
| `existence("Classify Risk")` | The activity must occur in the case. | Classification is mandatory before outcome. |
| `existence("Close Onboarding")` | The activity must occur in the case. | Every onboarding case must close. |
| `init("Receive Onboarding Request")` | `Receive Onboarding Request` must be the first activity. | It starts every case. |
| `response(Receive Onboarding Request, Capture Master Data)` | If receipt occurs, capture must occur later. | Capture is required after receipt. |
| `response(Receive Onboarding Request, Run Sanctions Screening)` | If receipt occurs, sanctions screening must occur later. | Screening is required after receipt. |
| `response(Receive Onboarding Request, Verify Bank Account)` | If receipt occurs, bank verification must occur later. | Bank verification is required after receipt. |
| `response(Request Clarification, Receive Clarification)` | If a clarification request occurs, a clarification response must occur later. | Weak encoding of R3. |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | If escalation occurs, legal opinion must occur later. | Encodes R4. |
| `response(Enhanced Due Diligence, Compliance Approval)` | If EDD occurs, compliance approval must occur later. | High-risk route order. |
| `response(Manager Approval, Activate Vendor)` | If manager approval occurs, activation must occur later. | Low-risk route order. |
| `response(Compliance Approval, Activate Vendor)` | If compliance approval occurs, activation must occur later. | High-risk route order. |
| `response(Activate Vendor, Release First Payment)` | If activation occurs, first payment must occur later. | Activation must be followed by payment. |
| `response(Release First Payment, Close Onboarding)` | If first payment occurs, close must occur later. | Accepted cases close after payment. |
| `response(Reject Vendor, Close Onboarding)` | If rejection occurs, close must occur later. | Rejected cases close after rejection. |
| `response(Change Bank Details, Suspend Vendor)` | If bank details change, suspension must occur later. | Approximate encoding of R11. |
| `precedence(Capture Master Data, Classify Risk)` | If classification occurs, capture must have occurred earlier. | Classification requires capture. |
| `precedence(Run Sanctions Screening, Classify Risk)` | If classification occurs, sanctions screening must have occurred earlier. | Classification requires screening. |
| `precedence(Verify Bank Account, Classify Risk)` | If classification occurs, bank verification must have occurred earlier. | Classification requires bank verification. |
| `precedence(Classify Risk, Manager Approval)` | If manager approval occurs, classification must have occurred earlier. | Approval follows classification. |
| `precedence(Classify Risk, Compliance Approval)` | If compliance approval occurs, classification must have occurred earlier. | Approval follows classification. |
| `precedence(Classify Risk, Reject Vendor)` | If rejection occurs, classification must have occurred earlier. | Rejection follows classification. |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | If escalation occurs, screening must have occurred earlier. | Encodes R7. |
| `precedence(Activate Vendor, Release First Payment)` | If first payment occurs, activation must have occurred earlier. | Payment cannot precede activation. |
| `noncoexistence(Reject Vendor, Activate Vendor)` | Reject and activate cannot both occur. | Encodes R1. |
| `noncoexistence(Manager Approval, Compliance Approval)` | Manager and compliance approvals cannot both occur. | Encodes R2/R8. |
| `noncoexistence(Enhanced Due Diligence, Manager Approval)` | EDD and manager approval cannot both occur. | Encodes R8. |
| `noncoexistence(Reject Vendor, Manager Approval)` | Rejection and manager approval cannot both occur. | Encodes R2 for rejected cases. |
| `noncoexistence(Reject Vendor, Compliance Approval)` | Rejection and compliance approval cannot both occur. | Encodes R2 for rejected cases. |
| `noncoexistence(Reject Vendor, Enhanced Due Diligence)` | Rejection and EDD cannot both occur. | Rejected cases should not enter high-risk route. |
| `noncoexistence(Reject Vendor, Release First Payment)` | Rejection and first payment cannot both occur. | Rejected vendors are not paid. |

Important distinctions:

- **Response**: if source occurs, target must occur later.
- **Precedence**: if target occurs, source must have occurred earlier.
- **Noncoexistence**: the two activities cannot both occur in the same case.
- **Existence**: the activity must occur at least once.
- **Init**: the activity must be first.

## Orientation and overlap explanation

### `always_before`

All `always_before` pairs are oriented as:

```text
(earlier_activity, later_activity)
```

Examples:

- `("Manager Approval", "Activate Vendor")` means: if both occur, manager approval is before activation.
- `("Activate Vendor", "Release First Payment")` means: if both occur, activation is before first payment.
- `("Reject Vendor", "Close Onboarding")` means: if both occur, rejection is before close.

I intentionally did **not** include:

- `("Verify Bank Account", "Classify Risk")` in `always_before`, because R11 allows another `Verify Bank Account` after activation, which is after classification. A global always-before constraint could be too strong if interpreted as all occurrences before all occurrences.
- `("Request Clarification", "Receive Clarification")`, because multiple clarification cycles can interleave.
- `("Obtain Legal Opinion", "Activate Vendor")`, because R6 allows emergency activation before legal opinion under an external exception.
- `("Change Bank Details", "Suspend Vendor")`, because post-activation change behavior may involve multiple lifecycle events and is better handled externally.

### `always_after`

I leave `always_after` empty to avoid duplicating inverse constraints already represented in `always_before`.

### `never_together`

These pairs encode hard mutual exclusion:

- reject vs activate,
- manager vs compliance,
- EDD vs manager,
- reject vs approvals/EDD/payment.

Orientation is irrelevant for `never_together`; I store one ordered pair for consistency.

### `activ_freq`

This encodes R10 for terminal and payment activities:

- `Activate Vendor`: 0 or 1,
- `Reject Vendor`: 0 or 1,
- `Release First Payment`: 0 or 1.

It also encodes structural single-occurrence expectations for:

- `Receive Onboarding Request`,
- `Classify Risk`,
- `Close Onboarding`,
- `Manager Approval`,
- `Compliance Approval`,
- `Enhanced Due Diligence`.

I do not fix `Verify Bank Account` to `{1}` because R11 allows another verification after activation.

### `directly_follows`

I leave this empty because the policy does not mandate immediate succession. Timestamps may vary, and direct-follow constraints would be too brittle.

### Overlap and disagreement

Overlap:

- `never_together` overlaps DECLARE `noncoexistence`.
- `always_before` overlaps DECLARE `precedence` and some `response` constraints.
- `activ_freq` overlaps R10 and some procedural single-occurrence structure.

Disagreement:

- The log skeleton is weaker than the procedural model because it cannot express exclusive choice or loops.
- The log skeleton omits some conditional temporal constraints that are handled by DECLARE or external checks.
- The log skeleton does not encode R5 as `always_before(Obtain Legal Opinion, Activate Vendor)` because that would be invalid under R6.

## Why temporal deviations are warnings

The R12 temporal expectations are statistical compliance signals. They are not hard control-flow constraints because:

1. Real processes have legitimate variance.
2. A late or early event may still be procedurally valid.
3. Temporal deviation should trigger monitoring or review, not automatic rejection, unless a separate hard deadline policy exists.
4. The emergency 24-hour condition in R6 is a hard exception condition, but it depends on an external authorization attribute and is therefore handled in the resource/data layer, not as a statistical temporal profile.

With `zeta = 2.0`, a pair is flagged when the observed elapsed time is outside:

```text
mean - 2 * standard_deviation
mean + 2 * standard_deviation
```

# 7. Resource- and Data-Aware Checks

The following checks cover requirements that activity-only models cannot fully express:

- segregation of duties,
- emergency legal-opinion policy,
- clarification loop integrity,
- post-activation bank-change behavior.

Required attributes:

- `case_id`
- `activity`
- `timestamp`
- `resource`
- optional: `emergency_authorized`

Missing attribute behavior:

- Missing `resource` for a relevant activity: check returns `not_evaluated`; case should be routed to manual review.
- Missing `timestamp` for a relevant activity: temporal/conditional check returns `not_evaluated`.
- Missing `emergency_authorized` under the operations resolution: check returns `policy_dependent`.
- Missing `case_id` or `activity`: data-quality failure before policy checks.

```python
import pandas as pd

HOUR = 3600


def _activities(case_df):
    return set(case_df["activity"].dropna())


def _resources(case_df, activity):
    """
    Return the set of resources for an activity.
    Return None if the resource attribute is missing.
    Return empty set if the activity does not occur.
    """
    if "resource" not in case_df.columns:
        return None

    vals = case_df.loc[case_df["activity"] == activity, "resource"].dropna()
    if vals.empty:
        return set()
    return set(vals)


def _first_ts(case_df, activity):
    """
    Return the earliest timestamp for an activity, or None.
    Assumes numeric timestamps in seconds.
    """
    if "timestamp" not in case_df.columns:
        return None

    vals = case_df.loc[case_df["activity"] == activity, "timestamp"].dropna()
    if vals.empty:
        return None
    return float(vals.min())


def _first_ts_after(case_df, activity, after_ts):
    if after_ts is None:
        return None

    sub = case_df[
        (case_df["activity"] == activity) &
        (case_df["timestamp"] > after_ts)
    ]
    if sub.empty:
        return None
    return float(sub["timestamp"].min())


def _first_ts_between(case_df, activity, start_ts, end_ts):
    if start_ts is None or end_ts is None:
        return None

    sub = case_df[
        (case_df["activity"] == activity) &
        (case_df["timestamp"] > start_ts) &
        (case_df["timestamp"] < end_ts)
    ]
    if sub.empty:
        return None
    return float(sub["timestamp"].min())


def check_sod_verify_approval(case_df):
    """
    R9:
    Resource performing Verify Bank Account must differ from
    the resource performing the applicable approval.
    """
    acts = _activities(case_df)

    verify_res = _resources(case_df, "Verify Bank Account")

    approval_res = set()
    has_approval = False

    for act in ("Manager Approval", "Compliance Approval"):
        if act in acts:
            has_approval = True
            res = _resources(case_df, act)
            if res is None:
                return "not_evaluated"
            approval_res |= res

    if not has_approval:
        return "pass"

    if verify_res is None:
        return "not_evaluated"

    if verify_res & approval_res:
        return "fail"

    return "pass"


def check_sod_capture_activate(case_df):
    """
    R9:
    Resource performing Capture Master Data must differ from
    the resource performing Activate Vendor.
    """
    acts = _activities(case_df)

    if "Activate Vendor" not in acts:
        return "pass"

    capture_res = _resources(case_df, "Capture Master Data")
    activate_res = _resources(case_df, "Activate Vendor")

    if capture_res is None or activate_res is None:
        return "not_evaluated"

    if capture_res & activate_res:
        return "fail"

    return "pass"


def check_legal_emergency(case_df, resolution="strict"):
    """
    R5/R6:
    If Sanctions Escalation occurs and Activate Vendor occurs,
    legal opinion must precede activation unless an approved
    emergency exception exists.

    resolution="strict":
        R5 is absolute in the log-only model.

    resolution="operations":
        R6 is a valid exception if external authorization exists
        and legal opinion arrives within 24 hours after activation.
    """
    acts = _activities(case_df)

    if "Sanctions Escalation" not in acts:
        return "pass"

    esc_ts = _first_ts(case_df, "Sanctions Escalation")
    act_ts = _first_ts(case_df, "Activate Vendor")
    leg_ts = _first_ts(case_df, "Obtain Legal Opinion")

    if esc_ts is None or act_ts is None:
        return "not_evaluated"

    if leg_ts is None:
        return "fail"

    if leg_ts < act_ts:
        return "pass"

    # Activation occurred before legal opinion.
    if resolution == "strict":
        return "fail"

    # Operations resolution: require external exception evidence.
    if "emergency_authorized" not in case_df.columns:
        return "policy_dependent"

    authorized = bool(case_df["emergency_authorized"].fillna(False).max())

    if not authorized:
        return "fail"

    if leg_ts - act_ts <= 24 * HOUR:
        return "pass"

    return "fail"


def check_clarification_loop(case_df):
    """
    R3:
    Every Request Clarification must be answered before the next
    clarification request and before any final outcome.
    """
    if "timestamp" not in case_df.columns:
        return "not_evaluated"

    final_outcomes = {
        "Reject Vendor",
        "Activate Vendor",
        "Close Onboarding",
    }

    open_request_ts = None

    for row in case_df.sort_values("timestamp").itertuples():
        if row.activity == "Request Clarification":
            if open_request_ts is not None:
                return "fail"
            open_request_ts = float(row.timestamp)

        elif row.activity == "Receive Clarification":
            if open_request_ts is not None and float(row.timestamp) >= open_request_ts:
                open_request_ts = None

        elif row.activity in final_outcomes:
            if open_request_ts is not None:
                return "fail"

    if open_request_ts is not None:
        return "fail"

    return "pass"


def check_change_bank_details(case_df):
    """
    R11:
    If Change Bank Details occurs after activation:
      - Suspend Vendor must eventually follow.
      - If a later Release First Payment occurs, another
        Verify Bank Account must occur between change and release.
    """
    acts = _activities(case_df)

    if "Change Bank Details" not in acts:
        return "pass"

    change_ts = _first_ts(case_df, "Change Bank Details")
    activate_ts = _first_ts(case_df, "Activate Vendor")

    if change_ts is None or activate_ts is None or change_ts < activate_ts:
        return "not_evaluated"

    suspend_ts = _first_ts_after(case_df, "Suspend Vendor", change_ts)
    if suspend_ts is None:
        return "fail"

    release_ts = _first_ts_after(case_df, "Release First Payment", change_ts)
    if release_ts is not None:
        verify_ts = _first_ts_between(
            case_df,
            "Verify Bank Account",
            change_ts,
            release_ts,
        )
        if verify_ts is None:
            return "fail"

    return "pass"


def resource_data_layer(log_df, resolution="strict"):
    """
    Evaluate the external resource/data/conditional layer per case.
    """
    verdicts = {}

    for case_id, case_df in log_df.groupby("case_id"):
        checks = {
            "sod_verify_approval": check_sod_verify_approval(case_df),
            "sod_capture_activate": check_sod_capture_activate(case_df),
            "legal_emergency": check_legal_emergency(case_df, resolution),
            "clarification_loop": check_clarification_loop(case_df),
            "change_bank_details": check_change_bank_details(case_df),
        }

        if "fail" in checks.values():
            verdict = "fail"
        elif "policy_dependent" in checks.values():
            verdict = "policy_dependent"
        elif "not_evaluated" in checks.values():
            verdict = "not_evaluated"
        else:
            verdict = "pass"

        verdicts[case_id] = verdict

    return verdicts
```

## T6 conflict-resolution detail

### Strict legal resolution

- `Sanctions Escalation` occurs at hour 6.
- `Activate Vendor` occurs at hour 13.
- `Obtain Legal Opinion` occurs at hour 23.

Because activation occurs before legal opinion after escalation, the strict model fails the case.

### Operations-exception resolution

- Activation before legal opinion is allowed only if externally jointly authorized.
- Legal opinion arrives 10 hours after activation.
- 10 hours is within the 24-hour limit.

Therefore:

- If the event log lacks `emergency_authorized`, the automated verdict is `policy-dependent`.
- If an external exception store confirms joint authorization, the case can pass under the operations resolution.

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement across layers

Several constraints are enforced in multiple layers:

- R1: procedural exclusive choice, DECLARE noncoexistence, log skeleton `never_together`.
- R8: procedural branches, DECLARE noncoexistence, log skeleton `never_together`.
- R4: DECLARE response, external legal-opinion check.
- R7: DECLARE precedence, log skeleton `always_before`.
- R10: log skeleton `activ_freq`, procedural single-occurrence structure.

This duplication is useful for monitoring, but it creates drift risk. If one layer is updated and another is not, findings may conflict. Each layer should reference stable policy IDs.

## Constraints that become inconsistent under loops or post-activation changes

### Clarification loops

R3 allows several request/response cycles. A global `always_before(Request Clarification, Receive Clarification)` log-skeleton constraint can be too strong if interpreted as all requests before all responses. Therefore, the log skeleton omits that pair.

### Post-activation verification

R11 allows another `Verify Bank Account` after activation. This conflicts with a naive backbone model that treats `Verify Bank Account` as only an initial pre-classification activity. The procedural tree models the initial verification only; post-activation verification is handled externally.

### Bank change and payment

R11 says another `Verify Bank Account` must occur before any later `Release First Payment`. R10 says `Release First Payment` occurs at most once. If “later release” means a subsequent payment after the first payment, R10 and R11 are in tension. The model treats R10 as authoritative for the onboarding case and treats R11 as a post-onboarding lifecycle check.

### Terminal close vs post-activation behavior

The backbone ends with `Close Onboarding`. But R11 allows `Change Bank Details` and `Suspend Vendor` after activation. It is unclear whether these occur before close, after close, or in a separate vendor lifecycle case. This is a blind spot.

## Vacuity in declarative rules

Many DECLARE rules are vacuously true when the source activity does not occur:

- `response(Sanctions Escalation, Obtain Legal Opinion)` is vacuously true in T1, T2, T3, T4, T5, and T8.
- `response(Change Bank Details, Suspend Vendor)` is vacuously true in all provided tests.
- `precedence(Run Sanctions Screening, Sanctions Escalation)` is vacuously true when escalation does not occur.

Vacuity is not a violation, but it means a passing DECLARE check does not prove that the relevant policy path was exercised.

## Missing case attributes

The event log does not contain:

- risk classification value,
- emergency authorization flag,
- joint authorization reference,
- vendor master data quality indicators,
- case state,
- exception workflow IDs.

Because of this, several policies cannot be fully validated from activity sequences alone.

## Timestamp-only limitations

Timestamps alone cannot validate:

- whether an emergency activation was jointly authorized,
- whether a resource had the required role or clearance,
- whether data was actually corrected after clarification,
- whether bank details were verified against authoritative sources,
- whether legal opinion content was sufficient.

Temporal profiles also cannot enforce hard maximums such as the 24-hour emergency opinion condition unless combined with exception attributes.

## Risk of treating support/confidence metadata as normative truth

In the DECLARE dictionary, `support = 1.0` and `confidence` values are metadata. They should not be interpreted as legal proof that a rule is universally valid.

In particular:

- A rule with `support = 1.0` in a small log may be an artifact of the sample.
- A rule with high confidence may still be operationally undesirable.
- Normative force comes from the policy interpretation, not from the numeric metadata.

# 10. Deployment Recommendation

## Canonical procedural representation

Use the **ProcessTree** from Section 3 as the canonical representation of the stable onboarding backbone.

Reasons:

- The backbone is block-structured.
- Parallelism, exclusive choice, and loops are naturally expressible.
- It is easier to audit than a POWL or Petri net for this process.
- It cleanly separates terminal outcomes.

Procedural conformance should be run on a backbone projection or with post-activation lifecycle events masked out.

## Authoritative policy layer

No single formalism should be the sole authority. Use a layered policy registry:

| Policy area | Authoritative layer |
|---|---|
| Stable backbone order and terminal exclusivity | ProcessTree |
| Simple conditional activity invariants | DECLARE |
| Coarse occurrence and mutual-exclusion invariants | Log Skeleton |
| Statistical timing expectations | Temporal Profile |
| Segregation of duties | Resource/data layer |
| Emergency legal-opinion exception | External exception/data layer |
| Clarification loop integrity | External clarification validator |
| Post-activation bank-change behavior | External conditional sequence validator |

## Recommended conformance order

Run checks in this order:

1. **Data-quality validation**
   - required attributes exist,
   - timestamps are parseable,
   - case IDs are present,
   - resource attributes exist where required.

2. **Procedural conformance**
   - validate the canonical backbone,
   - detect missing mandatory activities,
   - detect invalid branch combinations,
   - detect terminal outcome conflicts.

3. **Log-skeleton conformance**
   - validate coarse occurrence counts,
   - validate mutual exclusion,
   - validate basic ordering invariants.

4. **DECLARE conformance**
   - validate response, precedence, noncoexistence, existence, and init rules,
   - provide rule-level diagnostics.

5. **Resource/data and external conditional checks**
   - segregation of duties,
   - emergency legal-opinion policy,
   - clarification loop integrity,
   - post-activation bank-change behavior.

6. **Temporal-profile monitoring**
   - compute elapsed-time deviations,
   - emit warnings,
   - do not automatically reject solely because of temporal deviation.

## Surfacing contradictory findings

Findings should be surfaced with:

- policy ID,
- layer,
- severity,
- earliest decisive event,
- affected case ID,
- conflicting policy statements if applicable.

Recommended severity mapping:

- Procedural terminal conflict: `fail`
- DECLARE noncoexistence of reject/activate: `fail`
- SoD violation: `fail`
- Unanswered clarification before final outcome: `fail`
- Strict R5 violation: `fail`
- R5/R6 conflict without external authorization: `policy-dependent`
- Temporal deviation: `warning`
- Missing required attribute: `not evaluated` plus manual review

For T8, the user should see:

```text
FAIL: R1 / procedural / terminal conflict
Earliest decisive event: Reject Vendor@10 after Activate Vendor@9
Also violated: Activate Vendor without later Release First Payment
```

For T6, the user should see:

```text
FAIL under strict legal resolution:
  R5: Obtain Legal Opinion@23 after Activate Vendor@13 following Sanctions Escalation@6

Alternative under operations resolution:
  POLICY-DEPENDENT if no external emergency authorization exists
  PASS if external joint authorization exists and legal opinion arrives within 24 hours
```

This layered approach avoids forcing every requirement into one notation, preserves the distinction between control-flow, resource, data, and time-sensitive obligations, and makes the R5/R6 conflict explicit rather than silently resolved.
