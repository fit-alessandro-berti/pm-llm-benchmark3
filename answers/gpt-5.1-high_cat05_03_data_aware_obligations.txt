## 1. Temporal Data Semantics

I treat the log as defining a piecewise-constant event-time state per case. Events are ordered primarily by `time:timestamp` and secondarily by `event_index` (R7). For each case, I sort events by `(time:timestamp, event_index)` and maintain a running state vector over attributes `amount`, `risk_level`, `jurisdiction`, `customer_type`, and `exemption_id`. A non-blank cell at an event updates that attribute from that event’s timestamp onward; a blank cell means “no update” and leaves the prior value unchanged. There is no backward propagation: a value learned later in the case (e.g., at `Settlement_Confirmed`) does not retroactively change earlier state.

I distinguish four time notions:
- **Event time**: `time:timestamp` of the log event (e.g., `Release_Funds`, `Enhanced_Review`, `Sanctions_List_Update`).
- **Effective time**: the time an obligation or exemption is stated to take effect (e.g., exemption `effective_from` fields).
- **Record time**: when evidence is written to a system (e.g., `Record_Exemption` database insert at 11:00, settlement record time).
- **Evidence time**: timestamps on signatures or external evidence (e.g., qualified-signature time on exemption PDFs, settlement date, witness statements).

When reconstructing state at a given event (especially `Release_Funds`), I:
- Use the latest known attribute values as of that event’s **event time**, ordered by `event_index` for ties.
- Respect **effective time** when assessing exemptions: an exemption can satisfy an obligation at event `E` only if its effective_from ≤ event time of `E` and independent evidence supports that the approval already existed at that time (R5).
- Treat **record time** and **evidence time** as meta-evidence about whether an exemption or amount was actually in force at event time, but they never move the underlying event itself.

**Material changes** are identified from the event-time state:
- **Amount**: a change event where the new amount is more than 20% higher than the previous known amount after the latest Standard or Enhanced review is a “material amount change” that invalidates that review for amount-dependent obligations (R4). Decreases, and increases from an unknown prior amount, do not safely classify the review; increases ≤ 20% are non-material for R4.
- **Risk level**: a transition into `HIGH` is a material change for R2.
- **Customer type**: a transition into `PEP` is a material change for R2.
- **Jurisdiction**: any change of jurisdiction is material for R1 and R3 (especially when crossing into or out of DE, or into jurisdictions affected by sanctions-list updates).
- **Sanctions list**: `Sanctions_List_Update` is a material change for R3 for the jurisdictions it affects.

For each Release event, I identify the **latest material data change** before that release (including material amount changes, risk upgrades to HIGH, `customer_type` becoming PEP, jurisdiction changes, and relevant `Sanctions_List_Update` events). I then check whether required reviews or screens occur after that material change and before release (R1–R3), considering invalidation rules from R4.

Final case attributes (e.g., the last jurisdiction or amount in the trace) are used only when they are already in force by event time at `Release_Funds`. I never project the final state backward: for TX-311, for example, the Enhanced_Review occurs while jurisdiction is still US and only afterward (same timestamp, higher event_index) does `Update_Jurisdiction` switch to DE, so R1’s foreign-high-value logic is evaluated using US at review time but DE at release time. Missing amounts, risk, jurisdiction, or customer type are treated as **unknown**, not as low or benign values (R6); when an obligation trigger depends decisively on an unknown attribute at event time, I classify the case as INDETERMINATE unless other evidence makes the trigger clearly present or absent.

### 2.2 Pseudo-logic formalization (directional temporal relations)

I use a Datalog-like notation. Let:
- `Event(c, i, a)` denote an event in case `c` with index `i` (ordered by timestamp then event_index) and activity name `a`.
- `time(c, i)` be its event time.
- `before((c, i1), (c, i2))` mean `(time(c, i1) < time(c, i2))` or `(time(c, i1) = time(c, i2) ∧ i1 < i2)` (R7).
- `state_at(c, i, attr, v)` mean that at event `(c, i)`, attribute `attr` has value `v` after forward-filling earlier events in the same case.
- `unknown(c, i, attr)` mean that `attr` is unknown at `(c, i)`.
- `last_material_change(c, i, j)` mean `j < i` is the greatest index in case `c` such that a material data change (per R1, R3, R4) occurred at event `(c, j)`.
- `last_review(c, i, j, kind)` mean `j < i` is the greatest index in case `c` where `kind ∈ {standard, enhanced}` occurred.
- `valid_exemption_for_R1(c, i, ex)` mean exemption `ex` is valid for case `c` at event `(c, i)` per R5.

**Ordering helper:**

`before((c, i1), (c, i2)) :- time(c, i1) < time(c, i2).`  
`before((c, i1), (c, i2)) :- time(c, i1) = time(c, i2), i1 < i2.`

**R1 (foreign high-value enhanced review):**

Trigger:
- `R1_trigger(c, i) :- Event(c, i, 'Release_Funds'), state_at(c, i, jurisdiction, j), j ≠ 'DE', state_at(c, i, amount, a), a ≥ 100000.`
- `R1_trigger_indeterminate(c, i) :- Event(c, i, 'Release_Funds'), state_at(c, i, jurisdiction, j), j ≠ 'DE', unknown(c, i, amount).`

Satisfaction via review:
- `R1_satisfied_by_review(c, i) :- R1_trigger(c, i), last_material_change(c, i, j), Event(c, k, 'Enhanced_Review'), before((c, j), (c, k)), before((c, k), (c, i)), not R4_invalidates_review(c, k, i).`

Satisfaction via exemption:
- `R1_satisfied_by_exemption(c, i) :- R1_trigger(c, i), valid_exemption_for_R1(c, i, ex).`

Violation:
- `R1_violation(c, i) :- R1_trigger(c, i), not R1_satisfied_by_review(c, i), not R1_satisfied_by_exemption(c, i).`

Indeterminate due to missing data:
- `R1_indeterminate(c, i) :- R1_trigger_indeterminate(c, i).`

**R2 (high-risk or PEP approval):**

Trigger:
- `R2_trigger(c, i) :- Event(c, i, 'Release_Funds'), state_at(c, i, risk_level, 'HIGH').`
- `R2_trigger(c, i) :- Event(c, i, 'Release_Funds'), state_at(c, i, customer_type, 'PEP').`
- `R2_trigger_indeterminate(c, i) :- Event(c, i, 'Release_Funds'), (unknown(c, i, risk_level); unknown(c, i, customer_type)).`

Satisfaction:
- `R2_satisfied(c, i) :- R2_trigger(c, i), Event(c, k, 'Enhanced_Review'), Event(c, l, 'Compliance_Approve'), before((c, k), (c, l)), before((c, l), (c, i)), not R4_invalidates_review(c, k, i), Compliance_Approve_relates_to_enhanced(c, k, l).`

Violation:
- `R2_violation(c, i) :- R2_trigger(c, i), not R2_satisfied(c, i).`

Indeterminate due to missing data:
- `R2_indeterminate(c, i) :- R2_trigger_indeterminate(c, i).`

**R3 (sanctions-list update):**

Let `SanctionsAdded(j, t)` mean jurisdiction `j` was added to the sanctions list at time `t` (from `Sanctions_List_Update` and possibly global data).

Trigger:
- `R3_trigger(c, i) :- Event(c, i, 'Release_Funds'), state_at(c, i, jurisdiction, j), last_sanctions_screen(c, i, s), SanctionsAdded(j, t_add), time(c, s) < t_add < time(c, i).`

Satisfaction:
- `R3_satisfied(c, i) :- R3_trigger(c, i), Event(c, k, 'Sanctions_Screen'), before((c, last_update_j), (c, k)), before((c, k), (c, i)).`
  - where `last_update_j` is the index of the `Sanctions_List_Update` for jurisdiction `j` before `i`.

Violation:
- `R3_violation(c, i) :- R3_trigger(c, i), not R3_satisfied(c, i).`

**R4 (material amount change):**

Let `prev_amount(c, i, a_prev)` be the last known amount before event `(c, i)`.

- `R4_material_increase(c, i) :- Event(c, i, 'Update_Amount'), prev_amount(c, i, a_prev), state_at(c, i, amount, a_new), a_prev ≠ unknown, a_new > a_prev * 1.2.`
- `R4_invalidates_review(c, k, i) :- R4_material_increase(c, j), last_review(c, j, k, _kind), before((c, k), (c, j)), before((c, j), (c, i)).`
- `R4_indeterminate(c, i) :- Event(c, i, 'Update_Amount'), prev_amount(c, i, unknown), state_at(c, i, amount, a_new).`

Decreases:
- By policy text, a decrease does not by itself invalidate: `R4_does_not_invalidate_on_decrease(c, i) :- Event(c, i, 'Update_Amount'), prev_amount(c, i, a_prev), state_at(c, i, amount, a_new), a_new ≤ a_prev.`

**R5 (exemption validity for R1):**

Let `Exemption(ex, j_scope, ct_scope, a_max, waives, approved_by, effective_from, expires_at, evidence_strength, signature_time)` come from the exemption register and supporting evidence.

`valid_exemption_for_R1(c, i, ex) :- Event(c, i, 'Release_Funds'), state_at(c, i, jurisdiction, j), state_at(c, i, customer_type, ct), state_at(c, i, amount, a), Exemption(ex, j_scope, ct_scope, a_max, 'R1', 'Head_Compliance', eff, exp, evidence_strength, sig_t), j = j_scope, ct = ct_scope, a ≤ a_max, eff ≤ time(c, i) < exp, Evidence_supports_prior_approval(evidence_strength, sig_t, time(c, i)).`

Where `Evidence_supports_prior_approval` encodes the qualitative assessment (strong digital signature before release vs. suspiciously late signature contradicting displayed time).

**R6 (missing data):**

For any rule `R` and event `(c, i)`:
- If the trigger predicates of `R` rely on an attribute `attr` such that `unknown(c, i, attr)` and no other evidence fixes `attr`, then `R_indeterminate(c, i)` holds and neither `R_violation` nor `R_satisfied` can be concluded.

**R7 (event-time semantics):**

All state relations (`state_at`, `prev_amount`, `last_material_change`, `last_review`) are defined using `before` and case-local ordering by `(time:timestamp, event_index)`. Final-state values are never retroactively assigned to earlier events; they only affect `state_at` for events at or after the change that introduced them.

## 4. Ambiguities and Alternative Readings

### 4.1 TX-305 (INDETERMINATE due to missing amount)

TX-305 illustrates R6’s missing-data guidance. At creation, Enhanced_Review, and release, the amount is missing; only at `Settlement_Confirmed` the next day do we see 150,000 with a note that the settlement amount “may equal release amount.” Under a strict event-time reading, we cannot assert that the release amount was ≥ 100,000, nor that it was < 100,000, so R1’s trigger is genuinely INDETERMINATE. Likewise, we cannot determine whether there was any material amount increase after the Enhanced_Review (R4) because the pre- and post-review amounts are unknown at the relevant times.

Evidence that would resolve the ambiguity includes:
- An immutable release payload (e.g., signed payment message or ledger snapshot) showing the exact amount at `Release_Funds`.
- A system-of-record link that proves the settlement amount is exactly the amount released in this transaction, without subsequent adjustments.
- A clear audit trail of any intermediate amendments between release and settlement.

If immutable evidence showed that the release amount was 150,000, R1 would clearly trigger at release (foreign, ≥ 100k). Because an Enhanced_Review exists and no material amount increase can be shown after that review (still assuming no hidden interim changes), R1 would likely be satisfied and TX-305 could be classified COMPLIANT. Conversely, if evidence showed the release amount was, say, 80,000, R1 would not trigger and the case would again be COMPLIANT. Only if evidence showed a late material increase after the Enhanced_Review would TX-305 likely become NONCOMPLIANT under R4.

### 4.2 TX-302 (late-recorded but well-evidenced exemption)

In TX-302, EX-77 is recorded in the database at 11:00, after `Release_Funds` at 09:40, but the exemption register provides strong evidence that approval existed earlier: a qualified digital signature timestamp at 09:05, effective_from 09:00, and a documented outage explaining the late insert. Under the policy text, “A late database record can be evidence of earlier approval,” and the strong cryptographic evidence makes it reasonable to treat EX-77 as valid at release.

An alternative, stricter reading could require that approval be evidenced before release by a record whose own evidence time does not post-date release (e.g., refusing to accept outage explanations). Under that interpretation, TX-302 might be considered NONCOMPLIANT unless the Enhanced_Review alone is deemed sufficient (which in practice it is for R1, making EX-77 redundant). Additional evidence that could strengthen the exemption-centric justification includes:
- Independent system logs (e.g., HSM or signing-service logs) showing the approval action at or before 09:05.
- Tamper-evident records linking the qualified signature to the specific exemption ID and scope.

Even under stricter evidence standards, however, TX-302 remains COMPLIANT because the Enhanced_Review itself satisfies R1 without needing to rely on EX-77.

### 4.3 TX-310 (post-hoc exemption evidence and conflicting times)

TX-310 is intentionally ambiguous. EX-88 is scope-correct and claims approval at 08:50, effective from 08:00, but the qualified signing certificate is created at 10:30, after `Release_Funds` at 10:00. A witness (the requester) asserts oral approval at 08:45, but this witness is not independent. Under R5, “a displayed backdated field alone is not conclusive,” and here the backdated display is contradicted by the signature time. On a strict interpretation, we should not treat EX-88 as valid at release, leading to a NONCOMPLIANT classification for lack of Enhanced_Review or proved exemption.

However, different organizations might adopt alternative evidential thresholds:
- A more lenient approach might accept oral approval combined with a later formalization, especially if line management or Head_Compliance confirm the story, yielding a JUSTIFIED_EXCEPTION classification.
- Additional evidence such as Head_Compliance’s signed email before 10:00, independent log entries from an approval workflow engine, or HSM logs showing the signature key being used earlier (with later publication) could upgrade EX-88 from doubtful to clearly valid at release, making the case COMPLIANT.

Conversely, if forensic evidence showed that the PDF and its timestamps were manipulated after the fact, TX-310 would not only be NONCOMPLIANT with R1 but might indicate deliberate backdating or fraud, raising severity.

### 4.4 TX-311 (same-timestamp ordering and final-state leakage)

In TX-311, `Enhanced_Review` and `Update_Jurisdiction` share the same timestamp (16:20), but event_index clarifies ordering: event 3 (Enhanced_Review) precedes event 4 (Update_Jurisdiction). At review time, the jurisdiction is still US, and at `Release_Funds` (16:30) the jurisdiction is DE. Because R1 is triggered only when “current jurisdiction is not DE” at release, TX-311 is COMPLIANT under a strict event-time reading.

Alternative interpretations illustrate risks:
- If we ignored `event_index` and treated same-timestamp events as unordered, we might argue that jurisdiction could already be DE at review time, questioning whether the review was needed or whether a DE-focused control set applied.
- If we leaked final-state DE backward to all earlier events, we would incorrectly conclude that R1 never triggered (even at times when the case was clearly foreign), potentially masking necessary controls during the US phase.

Better evidence to reduce ambiguity would include explicit recording of both old and new jurisdiction values with effective_from times and immutable logs of when the change was requested vs. applied. This would make it easier to reason about whether the review covered the correct risk profile and whether any transient foreign exposure needed additional controls.

### 4.5 Additional ambiguities (TX-308 and interpretation of “material”)

TX-308 depends on whether a 140k→100k amount decrease between Enhanced_Review and release is considered a “material data change” for R1’s requirement that the review occur “after the latest material data change.” R4 states that decreases “do not by themselves invalidate a review,” which I interpret as meaning they are not material in the sense that would require a new Enhanced_Review. Under a different reading—treating any large absolute change as “material” regardless of direction—TX-308 might require a second Enhanced_Review or at least documentation explaining why a large decrease does not affect the risk assessment.

Evidence that would clarify this edge case includes formal policy documents defining “material change” thresholds and whether they are strictly one-sided (> 20% increase only) or symmetric.

def reconstruct_state(df: pd.DataFrame) -> pd.DataFrame:
    # Forward-fill changing attributes within each case without copying future values backward
    state_cols = ["amount", "risk_level", "jurisdiction", "customer_type", "exemption_id"]
    df = df.copy()
    df[state_cols] = (
        df.groupby("case:concept:name")[state_cols]
        .ffill()
        .reset_index(drop=True)
    )
    # Track previous state for change detection
    df["prev_amount"] = df.groupby("case:concept:name")["amount"].shift(1)
    df["prev_risk_level"] = df.groupby("case:concept:name")["risk_level"].shift(1)
    df["prev_customer_type"] = df.groupby("case:concept:name")["customer_type"].shift(1)
    df["prev_jurisdiction"] = df.groupby("case:concept:name")["jurisdiction"].shift(1)
    return df


def track_key_events_and_material_changes(df: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()

    # Flags for key review/screening events
    df["is_standard_review"] = df["concept:name"] == "Standard_Review"
    df["is_enhanced_review"] = df["concept:name"] == "Enhanced_Review"
    df["is_compliance_approve"] = df["concept:name"] == "Compliance_Approve"
    df["is_sanctions_screen"] = df["concept:name"] == "Sanctions_Screen"
    df["is_sanctions_update"] = df["concept:name"] == "Sanctions_List_Update"
    df["is_update_amount"] = df["concept:name"] == "Update_Amount"

    # Last times of key events as-of each event
    def last_time(col_flag: str) -> pd.Series:
        return (
            df["time:timestamp"]
            .where(df[col_flag])
            .groupby(df["case:concept:name"])
            .ffill()
        )

    df["t_last_standard_review"] = last_time("is_standard_review")
    df["t_last_enhanced_review"] = last_time("is_enhanced_review")
    df["t_last_compliance_approve"] = last_time("is_compliance_approve")
    df["t_last_sanctions_screen"] = last_time("is_sanctions_screen")
    df["t_last_sanctions_update"] = last_time("is_sanctions_update")

    # Material amount increase (>20%) after last Standard/Enhanced review
    df["amount_increase"] = (df["amount"] > df["prev_amount"]) & df["prev_amount"].notna()
    df["amount_increase_pct"] = (df["amount"] - df["prev_amount"]) / df["prev_amount"]
    df["is_material_amount_increase"] = (
        df["is_update_amount"]
        & df["amount_increase"]
        & (df["amount_increase_pct"] > 0.2)
    )
    df["amount_increase_from_unknown"] = df["is_update_amount"] & df["prev_amount"].isna() & df["amount"].notna()

    # Risk, customer type, and jurisdiction changes
    df["is_risk_to_high"] = (df["risk_level"] == "HIGH") & (df["prev_risk_level"] != "HIGH")
    df["is_customer_to_pep"] = (df["customer_type"] == "PEP") & (df["prev_customer_type"] != "PEP")
    df["is_jurisdiction_change"] = (df["jurisdiction"] != df["prev_jurisdiction"]) & df["prev_jurisdiction"].notna()

    # Union of material data changes relevant for the obligations
    df["is_material_data_change"] = (
        df["is_material_amount_increase"]
        | df["is_risk_to_high"]
        | df["is_customer_to_pep"]
        | df["is_jurisdiction_change"]
        | df["is_sanctions_update"]
    )

    df["t_last_material_change"] = (
        df["time:timestamp"]
        .where(df["is_material_data_change"])
        .groupby(df["case:concept:name"])
        .ffill()
    )

    # Last review time (max of standard/enhanced)
    df["t_last_any_review"] = df[["t_last_standard_review", "t_last_enhanced_review"]].max(axis=1)

    return df


def evaluate_coarse_rules(df: pd.DataFrame, ex: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()

    # Join exemption register on exemption_id
    df = df.merge(ex, how="left", on="exemption_id", suffixes=("", "_ex"))

    # Consider only Release_Funds events for obligation evaluation
    rel = df[df["concept:name"] == "Release_Funds"].copy()

    # Unknown flags
    rel["amount_unknown_at_release"] = rel["amount"].isna()
    rel["risk_unknown_at_release"] = rel["risk_level"].isna()
    rel["jurisdiction_unknown_at_release"] = rel["jurisdiction"].isna()
    rel["customer_type_unknown_at_release"] = rel["customer_type"].isna()

    # Coarse R1 trigger (ignoring INDETERMINATE case for now)
    rel["R1_trigger"] = (
        (rel["jurisdiction"] != "DE")
        & rel["amount"].ge(100000)
    )
    rel["R1_trigger_indeterminate"] = (
        (rel["jurisdiction"] != "DE")
        & rel["amount"].isna()
    )

    # Enhanced review coverage and material-change ordering
    rel["has_enhanced_review"] = rel["t_last_enhanced_review"].notna()
    # If no material change recorded, treat t_last_material_change as -inf for comparison
    rel["t_last_material_change_filled"] = rel["t_last_material_change"]
    rel.loc[rel["t_last_material_change_filled"].isna(), "t_last_material_change_filled"] = rel["time:timestamp"].min()

    rel["R1_enhanced_after_material"] = (
        rel["has_enhanced_review"]
        & (rel["t_last_enhanced_review"] >= rel["t_last_material_change_filled"])
        & (rel["t_last_enhanced_review"] <= rel["time:timestamp"])
    )

    # Exemption in scope and plausibly valid (coarse)
    rel["has_exemption"] = rel["exemption_id"].notna()
    rel["exemption_scope_match"] = (
        rel["has_exemption"]
        & (rel["jurisdiction"] == rel["scope_jurisdiction"])
        & (rel["customer_type"] == rel["scope_customer_type"])
        & rel["amount"].le(rel["scope_amount_max"])
    )
    rel["exemption_time_window_ok"] = (
        rel["has_exemption"]
        & (rel["effective_from"] <= rel["time:timestamp"])
        & (rel["time:timestamp"] < rel["expires_at"])
    )
    # Coarse evidence strength: EX-77 is "strong", EX-88 is "weak"
    rel["exemption_evidence_strong"] = rel["evidence_quality"].str.contains("strong", na=False)
    rel["R1_exemption_candidate"] = (
        rel["has_exemption"]
        & (rel["waives"] == "R1")
        & rel["exemption_scope_match"]
        & rel["exemption_time_window_ok"]
    )
    rel["R1_exemption_considered_valid"] = rel["R1_exemption_candidate"] & rel["exemption_evidence_strong"]

    rel["R1_coarse_satisfied"] = rel["R1_trigger"] & (
        rel["R1_enhanced_after_material"] | rel["R1_exemption_considered_valid"]
    )

    # Coarse R2
    rel["R2_trigger"] = (rel["risk_level"] == "HIGH") | (rel["customer_type"] == "PEP")
    rel["R2_trigger_indeterminate"] = rel["risk_unknown_at_release"] | rel["customer_type_unknown_at_release"]
    rel["has_compliance_approve"] = rel["t_last_compliance_approve"].notna()
    rel["R2_order_ok"] = (
        rel["has_enhanced_review"]
        & rel["has_compliance_approve"]
        & (rel["t_last_enhanced_review"] <= rel["t_last_compliance_approve"])
        & (rel["t_last_compliance_approve"] <= rel["time:timestamp"])
    )
    rel["R2_coarse_satisfied"] = rel["R2_trigger"] & rel["R2_order_ok"]

    # Coarse R3
    rel["R3_trigger"] = (
        rel["t_last_sanctions_screen"].notna()
        & rel["t_last_sanctions_update"].notna()
        & (rel["t_last_sanctions_screen"] < rel["t_last_sanctions_update"])
        & (rel["t_last_sanctions_update"] < rel["time:timestamp"])
    )
    # A new screen is required after list update; here we approximate by checking that the
    # last screening is not older than the last update
    rel["R3_coarse_satisfied"] = (
        rel["R3_trigger"]
        & (rel["t_last_sanctions_screen"] >= rel["t_last_sanctions_update"])
        & (rel["t_last_sanctions_screen"] <= rel["time:timestamp"])
    )

    # Coarse R4: material amount increase after last review
    # We approximate by checking whether the last material amount increase time is after last review time
    rel["t_last_material_amount_increase"] = (
        df["time:timestamp"]
        .where(df["is_material_amount_increase"])
        .groupby(df["case:concept:name"])
        .ffill()
        .loc[rel.index]
    )
    rel["R4_material_increase_after_review"] = (
        rel["t_last_material_amount_increase"].notna()
        & rel["t_last_any_review"].notna()
        & (rel["t_last_material_amount_increase"] > rel["t_last_any_review"])
        & (rel["t_last_material_amount_increase"] <= rel["time:timestamp"])
    )

    # Simple automatic label: this is intentionally coarse and may produce REVIEW_REQUIRED
    def auto_label(row: pd.Series) -> str:
        if row["amount_unknown_at_release"]:
            return "REVIEW_REQUIRED"
        if row["R1_trigger_indeterminate"]:
            return "REVIEW_REQUIRED"
        if row["R1_trigger"] and not row["R1_coarse_satisfied"]:
            return "REVIEW_REQUIRED"
        if row["R2_trigger"] and not row["R2_coarse_satisfied"]:
            return "REVIEW_REQUIRED"
        if row["R3_trigger"] and not row["R3_coarse_satisfied"]:
            return "REVIEW_REQUIRED"
        if row["R4_material_increase_after_review"]:
            # Any material increase after last review should be flagged for review
            return "REVIEW_REQUIRED"
        return "OK_BASIC_RULES"

    rel["auto_label"] = rel.apply(auto_label, axis=1)
    return rel


def coarse_controlflow_check(df: pd.DataFrame) -> pd.DataFrame:
    """
    Demonstrates a simple control-flow-style (DECLARE-like) trace-order check:
    for each case, is there an Enhanced_Review before the first Release_Funds?
    This deliberately ignores all data conditions.
    """
    rows = []
    for case_id, g in df.groupby("case:concept:name"):
        g_sorted = g.sort_values(["time:timestamp", "event_index"])
        release_times = g_sorted.loc[g_sorted["concept:name"] == "Release_Funds", "time:timestamp"]
        enhanced_times = g_sorted.loc[g_sorted["concept:name"] == "Enhanced_Review", "time:timestamp"]
        if release_times.empty:
            rows.append(
                {
                    "case:concept:name": case_id,
                    "enhanced_before_release_controlflow": False,
                    "note": "no release",
                }
            )
            continue
        first_release_time = release_times.min()
        has_enhanced_before_release = (
            (enhanced_times < first_release_time).any()
        )
        rows.append(
            {
                "case:concept:name": case_id,
                "enhanced_before_release_controlflow": bool(has_enhanced_before_release),
                "note": "ignores jurisdiction/amount/risk data",
            }
        )
    return pd.DataFrame(rows)

                "R1_trigger",
                "R1_trigger_indeterminate",
                "R1_coarse_satisfied",
                "R2_trigger",
                "R2_coarse_satisfied",

                "R3_coarse_satisfied",
                "R4_material_increase_after_review",

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage (TX-311 and others).** A control-flow model that only checks whether certain activities occur in a given order (e.g., Enhanced_Review before Release_Funds) cannot detect when obligations depend on *the state at release* rather than final state smeared across the trace. For example, in TX-311, if we copied the final jurisdiction DE backward or ignored event_index ordering at the same timestamp, we would mis-evaluate when the case was “foreign” vs. “DE,” affecting whether R1 ever triggered. Control-flow alone cannot encode that R1’s trigger is “jurisdiction ≠ DE AND amount ≥ 100k *at release time*,” not “jurisdiction at any time.”

2. **Post-hoc exemptions and record-time vs. event-time (TX-302, TX-310).** A pure control-flow view sees `Record_Exemption` and perhaps a reference to an exemption before or after Release_Funds, but cannot reason about whether the *approval* actually existed at release. TX-302 is acceptable because strong evidence (digital signature at 09:05, outage explanation) shows EX-77 was valid before release, while TX-310 is problematic because EX-88’s signature time (10:30) contradicts the displayed approval time and witness testimony is biased. Control-flow conformance cannot represent evidence strength, effective_from vs. record time, or contradictions in timestamps and thus cannot distinguish justified exemptions from post-hoc backdating.

3. **Material changes after review (TX-301, TX-309).** R4 says that a > 20% amount increase after the latest Standard or Enhanced review invalidates that review for amount-dependent obligations. In TX-309, Enhanced_Review at 118k is invalidated by an increase to 145k before release; in TX-301, the Standard_Review at 80k is invalidated by a large increase to 125k. A simple DECLARE constraint like “Enhanced_Review RESPONDED_EXISTENCE Release_Funds” would treat TX-309 as compliant because Enhanced_Review occurs before Release_Funds, but it cannot see that the review was done on the wrong amount and has been invalidated by R4.

4. **Conditional activation based on data (R1, R2, R3).** R1, R2, and R3 all depend on data conditions at the trigger event: foreign vs. DE jurisdiction and amount threshold (R1), risk_level HIGH or customer_type PEP (R2), and sanctions-list updates between the last screen and release (R3). Control-flow-only models cannot express “if amount ≥ 100k and jurisdiction ≠ DE, then Enhanced_Review before Release_Funds” or “if risk is HIGH or customer is PEP, then Enhanced_Review and Compliance_Approve in this order.” They either over-approximate (requiring Enhanced_Review before every Release_Funds, including low-risk domestic ones) or under-approximate (allowing high-risk/PEP releases without the required approvals).

5. **Missing data and INDETERMINATE outcomes (TX-305).** TX-305 has missing amount at creation, review, and release, with only a later settlement amount and a weak note that it “may” equal the release amount. Control-flow models cannot represent that we genuinely do not know whether R1 triggered. They would treat TX-305 identically to a low-value CA transaction with known amount < 100k, or to a high-value CA transaction, depending on how the model is parameterized. R6 explicitly requires that we classify such cases as INDETERMINATE, which is not a standard outcome of control-flow conformance checking.

6. **Same-timestamp ordering and micro-temporal semantics (TX-311).** R7 requires that for events sharing a timestamp we use event_index to break ties. In TX-311, the fact that Enhanced_Review (event_index 3) precedes Update_Jurisdiction (event_index 4) is critical: the review is done while jurisdiction is US, and only afterward does the case become DE. Control-flow models that only know activity sequences and coarse timestamps cannot represent micro-ordering within the same timestamp or its impact on obligations, leading to ambiguous or incorrect interpretations of whether the review covered the correct jurisdictional risk profile.

7. **Sanctions-list dynamics and external state (TX-304).** R3 depends on the relationship between the time of the last sanctions screen, the time the jurisdiction is added to the sanctions list, and the release time. In TX-304, sanctions screening at 08:10 is superseded by a list update at 08:30 before release at 08:45. A control-flow perspective that checks merely for the presence of a `Sanctions_Screen` before `Release_Funds` would consider this compliant, ignoring that the list changed in between and that another screen is required. This kind of dependency on external, evolving reference data cannot be captured by control-flow alone.

Overall, control-flow-only conformance can detect gross ordering issues (e.g., releases with no review at all), but it cannot:
- Respect event-time vs. record-time vs. evidence-time distinctions.
- Express thresholds and conditional triggers based on amounts, risk, jurisdiction, or customer type.
- Capture invalidation of reviews due to later data changes.
- Represent missing data and INDETERMINATE classifications.
- Handle same-timestamp ordering or state changes between events with identical coarse timestamps.

## 7. Recommended Logging and Control Improvements

To make future decisions more determinate and automatable, I recommend the following logging and control enhancements:

- **Immutable release payloads.** Log an immutable, signed payload at each `Release_Funds` event containing at least: amount, currency, jurisdiction(s) of payer and payee, risk_level, customer_type, applicable sanctions-list version, and explicit references to the reviews and approvals relied upon. Store a cryptographic hash of the payload in an append-only ledger so later systems cannot silently alter it. This would resolve ambiguities like TX-305’s unknown amount at release.

- **Explicit effective, record, and signature timestamps.** For exemptions, approvals, and sanctions-list versions, record: (a) effective_from, (b) record_time (when written to the database), and (c) signature_time (from a tamper-evident signing service). Enforce that signature_time ≤ effective_from ≤ any obligation trigger that relies on the approval, and log any deviations. This would clarify cases like TX-302 and TX-310 and allow systems to automatically reject releases that rely on post-hoc or weakly evidenced exemptions.

- **Rich change-provenance for material attributes.** For amount, risk_level, jurisdiction, customer_type, and sanctions flags, log each change as its own event with both old and new values, reason codes, and the actor/system responsible. Include a “materiality” tag based on policy thresholds (e.g., > 20% increase). This would make it easier to identify when R4 invalidates a review and to trace why and when a case became HIGH risk or PEP.

- **Rule versioning and obligation traceability.** At each review, approval, sanctions screen, and release, log the active rule set version and the obligations evaluated, including whether each was satisfied, waived by exemption, or postponed. This would help explain decisions when policies change over time and make regulatory back-testing feasible.

- **Stable intra-timestamp ordering.** Always record a stable, monotonic sequence number (like `event_index`) per case and ensure it is exposed in analytics systems. For events generated by multiple subsystems within the same second, use a global monotonic counter or logical clock to preserve the true causal order. TX-311 shows how crucial this is for interpreting the timing of jurisdiction changes relative to reviews.

- **Sanctions-list version tagging.** When performing `Sanctions_Screen` and `Release_Funds`, log the specific sanctions-list version (e.g., hash or version ID) used. When a `Sanctions_List_Update` occurs, create explicit references to which screens are now stale. This would allow automated detection of R3 violations instead of relying on manual reasoning over external list updates.

- **Structured exemption evidence.** For each exemption, store structured evidence metadata (approval medium, approver identity, signing key, evidence strength categorization) and link it to specific transactions that rely on it. Requiring that release systems verify this metadata in real time would prevent reliance on dubious post-hoc exemptions and support clear, machine-evaluable application of R5.
