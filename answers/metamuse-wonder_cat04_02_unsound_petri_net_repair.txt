# 1. Executive Verdict

No. Structurally, this is not a workflow net: `t_waive_review` has no input place and therefore neither it nor `p_waived` lies on a source-to-sink path, although the designated source and sink are otherwise unique. Consequently, soundness should not be expected. The principal defects are the unconstrained waiver transition and `t_join_waived`, which synchronizes only the waiver and not mandatory analysis. Authorization can therefore reach `sink` before, or without, analysis, while analysis and review tokens remain behind. The business consequence is an apparently completed but improperly authorized case, plus unbounded waiver firings and possible duplicate authorization.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `im=[source]` | Unique start, one case token | `source` has no incoming arcs and initially contains one token | Correct start marking |
| `t_register` | Register case | Consumes `source`, produces `p_ready` | Correct sequential start |
| `t_split` | AND-split after registration | Consumes `p_ready`; produces one token in each of `p_analysis` and `p_review` | Correctly starts both parallel branches |
| Analysis branch: `p_analysis -> t_analyze -> p_analysis_done` | Mandatory analysis | Structurally present and initially supplied by the split | Token can remain unconsumed on the implemented waiver path |
| Standard review: `p_review -> t_standard_review -> p_review_done` | One review alternative | Consumes the review token and produces `p_review_done` | Correct for the standard-review alternative |
| Waiver: `t_waive_review -> p_waived` | Alternative review outcome | `t_waive_review` has an empty preset, so it is enabled in every marking and consumes no `p_review` token | Waiver is not an alternative to standard review; it can fire repeatedly, making `p_waived` unbounded |
| `p_review` token on waiver route | Should be consumed by whichever review outcome is chosen | Neither `t_waive_review` nor `t_join_waived` consumes it | Leftover review token after waiver authorization |
| `t_join_normal` | AND-join for analysis plus standard review | Requires both `p_analysis_done` and `p_review_done`, then produces `p_decision` | Correct synchronization for the standard-review route only |
| `t_join_waived` | AND-join for analysis plus waiver | Requires only `p_waived`; it does not require `p_analysis_done` | Analysis can be bypassed; both joins can also produce separate `p_decision` tokens for one case |
| `t_authorize`, `p_decision`, `sink` | Authorize only after proper synchronization; unique end | `t_authorize` faithfully consumes `p_decision` and produces `sink`, but can receive `p_decision` prematurely from `t_join_waived` | A sink token may coexist with leftover branch tokens |
| `fm=[sink]` | Exact proper completion | Requires exactly one sink token and no tokens elsewhere | Can be violated even when a token exists in `sink` |
| Source-to-sink path condition | Every node should lie on a path from `source` to `sink` | All nodes except the waiver subnet do; `t_waive_review` has no incoming path from `source`, and `p_waived` is reachable only through it | Not a workflow net, independently of behavioral soundness |

The core problem is therefore not merely an informal “AND/XOR mismatch.” Two precise structural facts cause the behavior: the waiver transition has an empty preset, and the waiver join has a smaller preset than the business synchronization requires.

# 3. Marking-Based Counterexample

A legal firing sequence exposing premature authorization is:

```text
t_register, t_split, t_waive_review, t_join_waived, t_authorize
```

This sequence never fires `t_analyze`, yet produces a token in `sink`.

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `source=1` | `t_register`, `t_waive_review` | `t_waive_review` is already enabled before registration because its preset is empty |
| 1 | `t_register` | `p_ready=1` | `t_split`, `t_waive_review` | Case is registered; waiver remains unconstrained |
| 2 | `t_split` | `p_analysis=1, p_review=1` | `t_analyze`, `t_standard_review`, `t_waive_review` | The AND-split creates one token in each parallel branch, as intended |
| 3 | `t_waive_review` | `p_analysis=1, p_review=1, p_waived=1` | `t_analyze`, `t_standard_review`, `t_waive_review`, `t_join_waived` | Waiver consumes neither `p_review` nor any other token; it can fire again |
| 4 | `t_join_waived` | `p_analysis=1, p_review=1, p_decision=1` | `t_analyze`, `t_standard_review`, `t_waive_review`, `t_authorize` | Waiver synchronization ignores both outstanding branch tokens |
| 5 | `t_authorize` | `p_analysis=1, p_review=1, sink=1` | `t_analyze`, `t_standard_review`, `t_waive_review` | `t_authorize` occurred after — in fact without — `t_analyze`; a sink token exists, but this is not `fm`, because `fm` is exactly `sink=1` with no other tokens |

Thus, at Step 5, “a token exists in the sink” is true, while “the exact final marking `fm` has been reached” is false.

The leftover tokens cannot simply disappear. `p_analysis` can be consumed only by `t_analyze`, producing `p_analysis_done`. `p_review` can be consumed only by `t_standard_review`, because `t_waive_review` has no input arc from it; that produces `p_review_done`. Those two leftovers could then enable `t_join_normal`, producing a second `p_decision` and potentially a second `t_authorize` and second sink token. Alternatively, if only one leftover branch is completed, its done-token has no enabled join and remains stuck. No transition consumes arbitrary leftover tokens merely to clean up the marking.

**Second counterexample: unbounded and repeated waiver behavior**

From `im`, fire:

```text
t_waive_review, t_waive_review, t_join_waived, t_join_waived,
t_authorize, t_authorize
```

After the two waiver firings, the marking includes `source=1, p_waived=2`. The two `t_join_waived` firings produce `p_decision=2`, and the two authorizations produce `sink=2`, while `source=1` remains. More repetitions produce arbitrarily many tokens, so the net is unbounded. It also permits authorization before registration. This is an additional defect caused directly by the empty preset of `t_waive_review`.

# 4. Minimal-Repair Alternatives

Edit-cost model: adding or removing one arc costs 1; adding or removing one place costs 1; adding or removing one transition costs 1. Renaming costs 0 but is not counted as a semantic repair. Marking changes are not needed in these repairs.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| A. Give the waiver path its own proper two-input synchronization | Add arc `p_review -> t_waive_review`; add arc `p_analysis_done -> t_join_waived`. Keep `t_join_waived -> p_decision` as the waiver-path join | 2 arc additions | Analysis remains mandatory on both routes; standard review and waiver remain distinct visible outcomes; authorization still follows synchronization | Waiver now consumes the review token; `t_join_waived` requires both `p_waived` and `p_analysis_done`; the two joins compete for `p_analysis_done`, so exactly one can fire for a case | Two silent joins must be kept conceptually distinct; future editors could mistake them for duplicate synchronization |
| B. Rewire the waiver outcome into the normal synchronization | Add arc `p_review -> t_waive_review`; add arc `p_waived -> t_join_normal`; remove arc `p_waived -> t_join_waived`; remove arc `t_join_waived -> p_decision`; remove transition `t_join_waived`; remove place `p_waived` is **not** done because it remains the waiver outcome place feeding the common join. However, `t_join_normal` would then require `p_analysis_done`, `p_review_done`, and `p_waived`, so this exact form is invalid as an XOR merge | Not valid as stated | — | — | Shows why simply adding `p_waived` to the existing AND-join is wrong: it would require both review outcomes |
| B, corrected form: unify review outcomes before one join | Add arc `p_review -> t_waive_review`; change waiver output by removing arc `t_waive_review -> p_waived` and adding arc `t_waive_review -> p_review_done`; remove arc `p_waived -> t_join_waived`; remove arc `t_join_waived -> p_decision`; remove transition `t_join_waived`; remove place `p_waived` | 7: 3 arc additions/removals counted as add `p_review->t_waive_review`, remove `t_waive_review->p_waived`, add `t_waive_review->p_review_done`, remove `p_waived->t_join_waived`, remove `t_join_waived->p_decision`, plus remove one transition and one place | Analysis remains mandatory; exactly one review outcome produces `p_review_done`; the single existing join synchronizes it with analysis | Waiver and standard review become indistinguishable at the place/join level, though their visible transition labels remain distinct in traces; only one silent join remains | Loss of a separate waiver state may weaken auditability or reporting if downstream logic expects `p_waived`; removing elements is more disruptive |

For clarity, Repair B’s cost is: arc additions = 2 (`p_review->t_waive_review`, `t_waive_review->p_review_done`), arc removals = 3 (`t_waive_review->p_waived`, `p_waived->t_join_waived`, `t_join_waived->p_decision`), transition removal = 1, place removal = 1; total = 7.

**Minimality justification.** Any valid repair preserving mandatory analysis must do at least two things. First, it must give `t_waive_review` an input that consumes the review-branch token, otherwise the waiver remains enabled independently of the case state and unbounded. The cheapest such fix is one added arc, `p_review -> t_waive_review`. Second, it must make waiver authorization depend on completed analysis; the cheapest way is one added arc from `p_analysis_done` to the waiver join. Hence the lower bound under this cost model is 2 for a repair that preserves the existing places and transitions. Repair A attains that bound, so it is minimal. Repair B is not globally minimal; it is minimal only within the more restrictive design family that insists on a single synchronization transition and a single review-done place, which forces removal of the separate waiver join/place structure. There is no tie between A and B under the stated cost model.

A policy-changing variant — for example, explicitly declaring that waiver also waives analysis — would require a clearly approved business-policy change and additional care to consume or prevent the analysis token. It is not treated as a valid minimal repair here because, as drawn, merely letting `t_join_waived` consume `p_analysis` would create a race with `t_analyze` and could still deadlock if analysis completed first.

from pm4py.objects.petri_net.obj import PetriNet, Marking
from pm4py.objects.petri_net.utils import petri_utils

repaired_net = PetriNet("parallel_review_with_waiver_repaired")

source = PetriNet.Place("source")

p_analysis = PetriNet.Place("p_analysis")

    repaired_net.places.add(p)

# 6. Diagnostic and Reachability Code

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking


def marking_to_dict(marking):
    return {place.name: count for place, count in marking.items() if count > 0}


def fire_named_transition(net_to_fire, marking, transition_name):
    enabled = pm4py.get_enabled_transitions(net_to_fire, marking)
    enabled_names = {transition.name for transition in enabled}
    print(f"Enabled before firing: {sorted(enabled_names)}")
    print(f"Marking before firing: {marking_to_dict(marking)}")

    if transition_name not in enabled_names:
        raise ValueError(
            f"Transition {transition_name!r} is not enabled; "
            f"enabled transitions are {sorted(enabled_names)}"
        )

    transition = next(t for t in enabled if t.name == transition_name)

    new_marking = Marking()
    for place, count in marking.items():
        new_marking[place] = count

    for arc in transition.in_arcs:
        place = arc.source
        new_marking[place] = new_marking[place] - arc.weight
        if new_marking[place] <= 0:
            del new_marking[place]

    for arc in transition.out_arcs:
        place = arc.target
        new_marking[place] = new_marking[place] + arc.weight

    print(f"Fired: {transition_name}")
    print(f"Marking after firing: {marking_to_dict(new_marking)}")
    return new_marking


def run_counterexample(net_to_run, initial_marking, label):
    print(f"\n=== Counterexample attempt on {label} ===")
    sequence = [
        "t_register",
        "t_split",
        "t_waive_review",
        "t_join_waived",
        "t_authorize",
    ]
    marking = Marking()
    for place, count in initial_marking.items():
        marking[place] = count

    for transition_name in sequence:
        try:
            marking = fire_named_transition(
                net_to_run, marking, transition_name
            )
        except ValueError as exc:
            print(f"STOP: {exc}")
            break

    print(f"Final marking for {label}: {marking_to_dict(marking)}")
    print(
        f"Enabled at end for {label}: "
        f"{sorted(t.name for t in pm4py.get_enabled_transitions(net_to_run, marking))}"
    )
    return marking

In the original initial marking, `t_waive_review` is enabled alongside `t_register`; in the repaired net, only `t_register` should initially be enabled. The repaired net should pass the workflow-net check and is expected to be reported sound, subject to confirmation by actually running the diagnostics.

# 7. Repair Trade-Offs and Residual Risks

**Distinguishability of waiver and standard review.** Repair A preserves the distinction most strongly at the state level: standard review ends in `p_review_done`, waiver ends in `p_waived`, and separate silent joins consume those states. Even in Repair B, the visible transition labels `Perform Standard Review` and `Record Review Waiver` remain distinguishable in event traces, but the resulting place state no longer distinguishes them. If waiver status matters for audit, compensation, reporting, or later compliance checks, Repair A is safer.

**Silent transitions and possible confusion.** Both repairs retain silent transitions: `t_split`, and one or two silent joins. Repair A has two silent joins that share the input `p_analysis_done`. This is not duplicate behavior in a harmful sense: the token in `p_analysis_done` is consumed by exactly one join, and which join can fire is determined by whether the review branch produced `p_review_done` or `p_waived`. Still, silent joins can confuse trace interpretation because authorization readiness is not directly visible as a named business event. Model documentation should state that `t_join_normal` means “analysis + standard review complete” and `t_join_waived` means “analysis + waiver complete.”

**Soundness versus business alignment.** Soundness alone does not prove alignment with the business rule. A sound net could, for example, make analysis optional, reorder activities, or authorize after the wrong combination of outcomes while still completing properly. Conversely, the business rule imposes a specific precedence constraint: `t_authorize` must be preceded by `t_analyze` and by exactly one of `t_standard_review` or `t_waive_review`. That constraint must be tested explicitly, not inferred from a soundness boolean.

**Positive regression traces.** At minimum, test these accepted traces, allowing interleavings of the parallel visible activities:

- `Register Case, Perform Analysis, Perform Standard Review, Authorize Case`
- `Register Case, Perform Standard Review, Perform Analysis, Authorize Case`
- `Register Case, Perform Analysis, Record Review Waiver, Authorize Case`
- `Register Case, Record Review Waiver, Perform Analysis, Authorize Case`

Each should reach exactly `repaired_fm`, with no enabled transition required afterward and no leftover tokens.

**Negative regression traces.** Test that these are rejected or cannot complete properly:

- Authorization after waiver but before analysis.
- Authorization after standard review but before analysis.
- Authorization after analysis with neither standard review nor waiver.
- Both standard review and waiver for the same case.
- Waiver before registration, repeated waiver for the same case, or repeated authorization.
- Any trace reaching a sink token while `p_analysis`, `p_review`, `p_analysis_done`, `p_review_done`, or `p_waived` remains marked.

**Detecting accidental bypass of mandatory analysis.** Add a conformance or reachability assertion that every path from `repaired_im` to a marking enabling `t_authorize` has previously fired `t_analyze`. Operationally, regression tests should attempt the waiver counterexample and assert that `t_join_waived` is not enabled until `p_analysis_done` is marked. In logs, an alert rule can flag any case where `Authorize Case` occurs and no earlier `Perform Analysis` event exists for that case. Periodic model checks should also verify that `t_waive_review` still has `p_review` as an input and that `t_join_waived` still has both `p_waived` and `p_analysis_done` as inputs, protecting against later accidental arc deletion.

# 8. Final Recommendation

Deploy Repair A. It is minimal under the stated edit-cost model, attaining the two-arc lower bound, and it preserves the original topology, places, transitions, and visible labels. Most importantly, it preserves the business distinction between standard review and waiver while making analysis mandatory on both authorization paths. Its main residual risk—two similar silent joins—is manageable through naming documentation and targeted regression tests.

Use Repair B as the fallback if stakeholders prefer a single synchronization point and a single review-done state. That design is structurally simpler at the join but more invasive, removes `p_waived` and `t_join_waived`, and weakens state-level auditability of waiver cases. It should be adopted only if downstream consumers do not need to distinguish the waiver state after the review outcome has been recorded.
