## 1. Consistency rules and evidence model

We treat the dataset as a partially observed process log where object lifecycles are fragmented across events and object-to-object (O2O) relations are sparse. Repairs are guided by defeasible rules rather than hard axioms. The evidence model combines identifier heuristics, temporal ordering, arithmetic consistency, and structural plausibility.

### Rules and Classifications

| Rule ID | Description | Classification | Rationale |
|---|---|---|---|
| **R1** | `Create Order` relates to exactly one Order. | Hard invariant | Domain semantics enforce 1:1 creation. |
| **R2** | `Add Item` relates to one Order and one Item. | Hard invariant | Structural constraint on packing preparation. |
| **R3** | `Pack Item` relates to one Item and one Package. | Strong default | Scanner prefixes (e.g., `PK8-1`, `PK8-2`) strongly suggest a shared package context. Scanner outages may omit the package object, but the package usually exists. |
| **R4** | `Dispatch Package` relates to one Package and one Delivery. | Strong default | Logistics semantics; bulk dispatch is possible but rare and usually flagged. |
| **R5** | `Confirm Delivery` may relate to one or more Deliveries/Orders. | Weak heuristic | Portal logs may aggregate confirmations or lose carrier IDs. `external_ref` wildcards increase ambiguity. |
| **R6** | `Issue Invoice` may relate to multiple Orders; total amount is evidence, not proof. | Strong default | Invoicing often aggregates orders. Arithmetic matching supports but does not prove inclusion due to taxes/fees. |
| **R7** | `Record Payment` relates to one Payment and normally one Invoice. | Strong default | Unapplied cash exists but is less common than settled invoices. |
| **R8** | Identifier prefix similarity (e.g., `N-420` vs `N-421?`) is informative. | Weak heuristic | Wildcards and question marks in `external_ref` suggest fuzzy matching. |
| **R9** | Route hints (`NORTH`) and carrier refs must align. | Strong default | A package dispatched to `NORTH` should map to a delivery with route `NORTH`. |
| **R10** | Lifecycle order must be preserved (Create  Add  Pack  Dispatch  Confirm  Invoice  Pay). | Hard invariant | Temporal causality cannot be violated. |

### Evidence Combination Strategy

1.  **Identifier Similarity:** `ev10` has `external_ref=N-421?`. `DEL-Y` has `carrier_ref=N-421`. The suffix `?` and the exact prefix match provide strong abductive evidence for `ev10`  `DEL-Y`.
2.  **Scanner Proximity:** `ev07` uses `scanner_ref=PK8-1` for `IT-A2``PK-8`. `ev08` uses `scanner_ref=PK8-2` for `IT-B1`. The shared `PK8` prefix implies the same station/package context. This supports `ev08`  `PK-8` and `PK-8` packs `IT-B1`.
3.  **Arithmetic Consistency:** `INV-44` total is 230. `ORD-A` declared value is 130; `ORD-B` is 100. Sum is 230. `PAY-1` is 100; `PAY-2` is 130. The perfect partition suggests `INV-44` covers both orders and both payments settle it. This is strong evidence for `INV-44` bills `ORD-B` and `PAY-2` settles `INV-44`.
4.  **Route/Carrier Alignment:** `PK-8` has `route_hint=NORTH`. `DEL-X` and `DEL-Y` both have `route=NORTH`. `ev09` dispatches `PK-7` via `N-420` (`DEL-X`). `ev10` dispatches `PK-8` via `N-421?` (`DEL-Y`). This creates a consistent dispatch mapping.
5.  **Ambiguity in `ev11`:** `external_ref=N-42*` matches both `N-420` and `N-421`. `ev11` links only to `ORD-A`. If `ev11` confirms `DEL-Y` (which carries `PK-8` containing `IT-B1` of `ORD-B`), we would expect a link to `ORD-B` unless the confirmation is partial or the link is missing. If `ev11` confirms `DEL-X` (which carries `PK-7` containing only `IT-A1` of `ORD-A`), the link to `ORD-A` is partial but plausible. The ambiguity prevents a unique resolution.

### Bundle B: Aggressive Confirmation / Full Lifecycle
*   **Strategy:** Resolve `ev11` to maximize confirmation coverage, assuming the wildcard `N-42*` targets `DEL-Y` and the confirmation implicitly covers `ORD-B` via `PK-8`.

    *   `ORD-B`: Now fully confirmed. Lifecycle complete.

### Bundle C: Partial Confirmation Hypothesis

## 8. Over-repair warnings

1.  **False Split Order:** Assuming `IT-B1` is in `PK-8` without scanner evidence could create a phantom split packing. If `IT-B1` is actually in a missing `PK-9`, the repair forces a cross-order package that doesn't exist, distorting route and weight analysis.
2.  **Phantom Delivery:** Linking `ev11` to `DEL-Y` based on `N-42*` could create a confirmation for `DEL-Y` when it actually confirms `DEL-X`. This would falsely indicate `DEL-X` is unconfirmed and `DEL-Y` is confirmed, skewing carrier performance metrics.
3.  **Incorrect Payment Application:** Assuming `PAY-2` settles `INV-44` without explicit relation might be wrong if `PAY-2` is unapplied cash or settles a different invoice. This would falsely show `INV-44` as fully settled and `PAY-2` as settled, hiding a potential reconciliation issue.
4.  **Circular Confirmation Logic:** Inferring `ev11` confirms `ORD-B` because `ev11` confirms `DEL-Y` and `DEL-Y` carries `IT-B1` creates a dependency chain. If `ev11` is actually `DEL-X`, the entire inference collapses. Over-repair propagates this error.
5.  **Invoice Over-Valuation:** Assuming `INV-44` bills `ORD-B` because of arithmetic match ignores the possibility of taxes/fees. If `INV-44` only bills `ORD-A` with high tax, linking `ORD-B` creates a false relationship, implying `ORD-B` is invoiced when it is not, and `PAY-1` is misapplied.
6.  **Lifecycle Duplication:** Adding `PK-8 packs IT-B1` and `DEL-Y carries PK-8` might duplicate relations if `IT-B1` was already packed in `PK-7` (unlikely but possible if data is messy). This could create a multi-carrier package scenario that is operationally invalid.
7.  **Event-Object Mismatch:** Adding `ev08 -> PK-8` assumes `PK-8` is the package. If `PK-8` is a scanner ID and the package is missing, adding `PK-8` as object might confuse scanner IDs with package IDs. The repair must ensure `PK-8` is a valid package object.

These warnings emphasize the need for conservative repairs and explicit uncertainty handling, especially for wildcards and arithmetic inferences.
