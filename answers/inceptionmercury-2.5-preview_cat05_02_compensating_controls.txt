

## 1. Control-Objective Decomposition
FEP-1 decomposes into five critical threat scenarios:

1.  **Initiation Authorization Convergence:** One actor initiates and approves. AV-2 prevents duplicates; MG-4 provides independent review; RA-7 detects later.
2.  **Vendor/Account Substitution:** Account details altered during processing. AV-2 checks recent changes; MG-4 validates supporting documents; RA-7 audits changes post-event.
3.  **Amount Overrun:** Payments exceed limits. AV-2 checks operator limits; MG-4 authorizes large amounts; RA-7 flags exceptions.
4.  **Commercial Collusion:** Multiple actors coordinate fraud. AV-2 cannot detect intent; MG-4 is weakened by relationship; RA-7 detects pattern over time.
5.  **Recovery Failure:** Loss occurs before detection. AV-2 blocks proactively; MG-4 blocks pre-settlement; RA-7 enables recall if timely.

MG-4 fails on collusion resistance; AV-2 fails on commercial reasonableness. RA-7 is inherently reactive, so it corrects only if recovery windows remain open.

## 2. Equivalence and Sufficiency Test
A compensating package is equivalent only if it replicates the FEP-1 control properties without introducing new failure modes.

*   **Timing:** Prevention must occur before settlement. MG-4 after release but before settlement is preventive; after settlement, it is detective.
*   **Independence:** Approver must lack reporting or compensation ties. A supervisor reviewing their direct report fails independence.
*   **Coverage:** Automated checks must cover all data points (duplicate, bank, vendor). Gaps reduce sufficiency.
*   **Overrideability:** Manual override weakens AV-2 unless reviewed by a separate authority.
*   **Recoverability:** RA-7 is sufficient only if audit completes before bank recall window (typically 24h).
*   **Evidence Quality:** A clean AV-2 pass does not validate receipt of goods.

"Same expected loss" is insufficient because two controls might stop money flow but differ on integrity (e.g., blocking a transaction vs. letting it pass and later auditing). Loss prevention protects capital; objective protection protects process integrity.

## 4. Preventive–Detective–Corrective Comparison

| Control | Primary Mode | Timing Requirement | Failure Condition | Semantic Note |
|---|---|---|---|---|
| AV-2 | Preventive | Before Release | Blocked | Purely preventive if it stops release; warning with override is hybrid. |
| MG-4 | Hybrid | Before Settlement | Post-release/Pre-settlement | Prevents settlement; detects errors post-release. |
| MG-4 | Detective | After Settlement | Any | Cannot stop loss; purely corrective/detective. |
| RA-7 | Detective | 1 Day (Emergency) | Delay | Detects defects; corrective only if recovery window open. |
| RA-7 | Corrective | Within Recall Window | N/A | Active corrective if funds recalled. |

Manager action before settlement but after Release_Payment acts as a final barrier preventing irrevocable transfer. While technically "detective" of the release decision, it functions preventively regarding the settlement event.

## 5. Counterfactual and Residual-Risk Analysis

*   **AP-202:** Loss mechanism is vendor fraud via unauthorized bank change. AV-2 warning overridden by conflicted manager. Remaining exposure: Complete loss. With independent releaser: Higher likelihood of catching bank change.
*   **AP-204:** Loss mechanism is collusive fake service receipt. AV-2 passed (duplicate check ok). Remaining exposure: Loss found later. With independent second releaser: May not stop collusion if coordinated, but shared workstation audit would flag faster.
*   **AP-208:** Loss mechanism is unauthorized payment to new vendor with recent bank change. AV-2 unavailable. With independent second releaser: Manual check would likely flag change if validated properly.
*   **AP-203:** Loss mechanism is minimal (machine repair critical). AV-2 passed. Independent second user would validate but add latency. Current controls suffice.
*   **AP-206:** Loss mechanism is timing gap (token after prep). Controls largely functional otherwise. Independent second user would reduce risk if token failure was systemic.

## 6. Evidence and Monitoring Recommendations
Collect and monitor the following metrics to detect degradation:

*   **Same-user rate:** Track % of payments with identical Prepare/Release users outside ED-1 cases.
*   **Override rate:** Track % of AV-2 warnings overridden; escalate if >1%.
*   **Late manager approval:** Flag any MG-4 occurring after Release_Payment or settlement.
*   **Audit-before-recall-window:** Verify RA-7 completion time relative to release time for high-risk cases.
*   **Repeated resource pairs:** Identify frequent Prepare/Release pairs (e.g., u12/u13) and cross-reference shared workstation logs.
*   **Bank-change proximity:** Flag payments where vendor bank changed within 7 days; require MG-4.
*   **Control outages:** Monitor AV-2 service health (AP-208 case).

An alert triggers investigation; proof of misconduct requires additional external verification (e.g., bank recall status, fraud investigation).
