## 1. Normalization Assumptions

Let A, I, C, and L mean Alert_Received, Investigation_Start, Containment_Complete, and Close_Incident. All displayed interval endpoints below are UTC. For a recorded local timestamp, I first apply its resolution rule to get a range of source-clock readings, convert that range to UTC, then subtract the possible clock offset: if the offset is [a,b], true time is in [earliest reading − b, latest reading − a]. A HUB second therefore has a ±1.5 s true-time range; a SENSOR reading has ±10 s. A floored minute has a 60 s half-open reading range. I display its upper *supremum* and calculate conservative closed bounds; none of the classifications depends on inclusion of an endpoint.

I use the specified CEST, EDT, and BST offsets, not a fixed offset for each city. On 2025-10-26 in Berlin, 02:xx occurs twice: fold 0 is CEST (UTC+2), and fold 1 is CET (UTC+1). For T-405 I apply the operational order A ≤ I ≤ C, supported by ingestion order and the activity meanings. This leaves only folds (0,1,1). Ingestion order alone would not prove event order; conclusions for this case depend on that causal assumption.

For T-404, the signed 18–25 minute duration is elapsed time from Investigation_Start to Investigation_Complete. I subtract the *whole* duration range from the latter event's HUB interval. For T-407, I conditionally treat network delivery as establishing a receipt within 0–20 minutes of Alert_Sent and apply receipt ≤ investigation start. There is no direct receipt observation. If the network bound describes only a possible delivery and delivery itself is unproven, every result involving A in T-407 is **INDETERMINATE**.

For T-406, my primary interpretation is that the mobile timestamp describes a late *recording*: actual investigation start can precede the normalized mobile timestamp by 0–5 minutes. This is an occurrence-time adjustment in addition to ±5 minutes of clock offset and ±30 seconds of rounding. If the user instead entered the actual occurrence time accurately and merely submitted the record later, the 5 minutes affect only submission time; the alternate occurrence interval and its consequences appear below. For T-409, I provisionally use the weak ±12 minute engineering offset as a bound, then apply A ≤ I. Results involving I are conditional on that bound being valid.

SLA tolerance is an **added** allowance, not a change to the observed times. The main findings use zero allowance and profile ζ = 1. For a duration interval [l,u], a one-sided SLA passes certainly if u ≤ cap, violates certainly if l > cap, and otherwise has a possible violation. Profile bands are inclusive and two-sided. “Certain” refers to every feasible time **under the stated evidence assumptions**, not to the trustworthiness of those assumptions.

## 5. PM4Py Temporal-Conformance Code

The code uses interval endpoints as conservative infima/suprema. It keeps the T-405 raw fold alternatives, filters causal branches, and applies the two other stated causal constraints. It needs `pandas` and `pm4py` installed. PM4Py operates only on the separately labeled midpoint log; its diagnostic layout can vary by version, so only the final display function treats its return value as a generic object.

```python
    events[("T-405", act)] = interval

# Inferred start from signed duration; preserve the complete interval.
end_lo, end_hi = events[("T-404", "Investigation_Complete")]
events[("T-404", I)] = (end_lo - pd.Timedelta(minutes=25),
                         end_hi - pd.Timedelta(minutes=18))

# Conditional network-delivery model, with receipt <= investigation start.
sent_lo, sent_hi = events[("T-407", "Alert_Sent")]
i_lo, i_hi = events[("T-407", I)]
events[("T-407", A)] = (sent_lo,
                         min(sent_hi + pd.Timedelta(minutes=20), i_hi))

# Causal projection for the weak T-409 investigation interval.
a_lo, a_hi = events[("T-409", A)]
i_lo, i_hi = events[("T-409", I)]
events[("T-409", I)] = (max(i_lo, a_lo), i_hi)

def durations(case, first, second):
    """Feasible duration bounds, preserving case-specific causal coupling."""
    lo1, hi1 = events[(case, first)]
    lo2, hi2 = events[(case, second)]
    lower = (lo2 - hi1).total_seconds()
    upper = (hi2 - lo1).total_seconds()
    if (case in ("T-407", "T-409")) and (first, second) == (A, I):
        lower = max(0.0, lower)
    if case == "T-409" and (first, second) == (I, C):
        upper = (hi2 - max(lo1, a_lo)).total_seconds()
    return (lower, upper)

def one_sided(bounds, cap):
    lo, hi = bounds
    if hi <= cap: return "CERTAIN_PASS"
    if lo > cap: return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

def two_sided(bounds, band):
    lo, hi = bounds
    left, right = band
    if left <= lo and hi <= right: return "CERTAIN_PASS"
    if hi < left or lo > right: return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

for case in sorted(raw["case"].unique()):
    for pair, cap in sla.items():
        if all((case, act) in events for act in pair):
            b = durations(case, *pair)
            print(case, "SLA", pair, b,
                  [one_sided(b, cap + allowance)
                   for allowance in (0, 120, 300)])
    for pair, (mean, sd) in profile.items():
        if all((case, act) in events for act in pair):
            b = durations(case, *pair)
            print(case, "profile", pair, b,
                  [two_sided(b, (mean - z * sd, mean + z * sd))
                   for z in (1, 2, 3)])

# LOSSY APPROXIMATION: point timestamps below are interval midpoints.
# PM4Py is not being asked to normalize clocks, DST folds, or missing events.
mid_rows = []
for (case, act), (low, high) in events.items():
    if act in {A, I, C, L}:
        mid_rows.append({
            "case:concept:name": case,
            "concept:name": act,
            "time:timestamp": low + (high - low) / 2,
        })
midpoint_df = pd.DataFrame(mid_rows)
midpoint_df["time:timestamp"] = pd.to_datetime(
    midpoint_df["time:timestamp"], utc=True)
midpoint_log = pm4py.format_dataframe(
    midpoint_df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
)

def show_pm4py_diagnostics(value):
    # Diagnostic schema is version-dependent; do not assume column names.
    if isinstance(value, pd.DataFrame):
        print(value.to_string(index=False))
    else:
        print(repr(value))

for z in (1, 2, 3):
    print("PM4Py midpoint-only diagnostics, zeta =", z)
    diagnostic = pm4py.conformance_temporal_profile(
        midpoint_log, profile, zeta=z)
    show_pm4py_diagnostics(diagnostic)

    # Side-by-side logical comparison, independent of diagnostic schema.
    for case in sorted(raw["case"].unique()):
        for pair, (mean, sd) in profile.items():
            if not all((case, act) in events for act in pair):
                continue
            b = durations(case, *pair)
            band = (mean - z * sd, mean + z * sd)
            p1 = midpoint_df.loc[
                (midpoint_df["case:concept:name"] == case) &
                (midpoint_df["concept:name"] == pair[0]),
                "time:timestamp"].iloc[0]
            p2 = midpoint_df.loc[
                (midpoint_df["case:concept:name"] == case) &
                (midpoint_df["concept:name"] == pair[1]),
                "time:timestamp"].iloc[0]
            midpoint_seconds = (p2 - p1).total_seconds()
            midpoint_accepts = band[0] <= midpoint_seconds <= band[1]
            print(case, pair, "midpoint_accepts=", midpoint_accepts,
                  "interval=", two_sided(b, band))
```

A midpoint diagnostic can accept a pair whose feasible interval has violations, or flag a pair whose interval also contains passing times. It is therefore a diagnostic comparison, never a replacement for the interval classification. The code assumes PM4Py's temporal-profile dictionary uses activity-pair keys and (mean seconds, standard deviation seconds) values, and that `conformance_temporal_profile` accepts `zeta=`; diagnostic columns and presentation are deliberately isolated in `show_pm4py_diagnostics`.

## 6. Evidential Sufficiency

For any PV result, a decisive new bound must put the **entire feasible duration** either inside or outside the relevant acceptance region. Merely supplying another midpoint is insufficient.

- **Stronger synchronization:** T-401 S1/P1 needs a narrower OPS-BER offset near the 15-minute SLA and 13-minute profile edge. T-402 S2/P2 needs synchronization tight enough to resolve its 45-minute edge; its S1 is already certainly late at zero tolerance. T-403 S1/P1/P3 needs a vendor event-level offset measurement or a trusted receipt timestamp. T-405 S1/P1 needs per-event clock calibration and second-level readings after fold identification. T-409 S1/P1/P2 needs actual NTP logs or an independently timestamped start; that also tests whether the provisional ±12-minute bound is valid.
- **Duration or missing-start evidence:** T-404 S1/S2/P1/P2 needs a logged Investigation_Start, or a narrower signed investigation-duration range. Because S2/P2 exceed the 2700 s edge by only 3 s at the upper bound, sufficiently precise evidence around that edge is decisive.
- **Mobile semantic and clock evidence:** T-406 S1/S2/P1/P2 needs an audit trail distinguishing occurrence time from entry/submission time, plus reliable device offset and timestamp resolution. Under the late-submission-only interpretation, S2 and P2 already become certain passes; resolving the semantic question is the minimum first step.
- **Missing activity and causal evidence:** T-407 S1/P1 needs a receipt acknowledgment or other proof of actual delivery, its time, and a causal link to investigation. That evidence can also make its conditional P3 certain without relying on delivery inference. If receipt existence is not established, its A-related findings remain INDETERMINATE. T-405 needs a logged fold or trustworthy causal identifiers if the A≤I≤C interpretation is challenged.
- **Missing closure evidence:** For T-402–T-407 and T-409, a Close_Incident event tied to the same case, with timestamp resolution and clock bounds, is the minimum needed to test S3/P4. A “still open” state and an observation cutoff could instead establish a lower bound sufficient for a certain S3 breach, provided the cutoff is after the 36-hour deadline and closure truly had not occurred.

Some PV profile findings persist at wider ζ because they cross a **lower** bound: T-407 P1 and T-409 P1 include nearly simultaneous A and I, while T-409 P2 includes durations below the ζ=1 lower edge. Additional evidence must narrow the relevant side of the range. If a purported clock bound is only an informal guess, it cannot support a certain pass or violation; the proper status is INDETERMINATE pending telemetry or independent corroboration.

## 7. Governance Recommendation

Store an immutable UTC event time **and** the original raw timestamp, source time zone, UTC offset, and DST fold. Record each source's rounding or flooring rule and resolution. Retain event-level or tightly time-matched clock-offset telemetry with a stated confidence bound, especially for vendors and mobile devices. Separate occurrence, entry, ingestion, and synchronization times.

Define lifecycle events explicitly: Investigation_Start versus Investigation_Complete, and Containment_Complete as a completion event. Capture Alert_Sent and Alert_Received separately, with delivery acknowledgment and causal identifiers linking the same notification, incident, and investigation. Keep signed duration evidence with its units, interval, provenance, and signer.

For enforcement, use **certain violations** for automatic hard-SLA action; route possible violations to evidence review and leave indeterminate cases unresolved until the missing fact or semantic rule is supplied. Do not turn interval overlap alone into a breach finding. Publish the tolerance policy and the rule for whether an interval merely overlapping the acceptance region counts as provisional compliance; statistical-profile deviations should trigger investigation, not automatically be treated as legal SLA violations.
