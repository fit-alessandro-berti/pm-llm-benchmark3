## 1. Target definition
**Primary Target:** Probability of Default within 90 days post-activation, conditional on account activation ($P(D_{90} \mid \text{Activated}, \mathcal{H}_t)$).
*   **Unit of Analysis:** Case (Credit Application ID).
*   **Population:** All cases that reached the "Account Activated" milestone prior to the label maturity cutoff.
*   **Prediction Time ($t$):** End of the "Credit Review" phase (immediately before the Accept/Reject decision event).
*   **Horizon:** 90 days following Account Activation.
*   **Estimand:** Expected value of the binary outcome $Y=1$ if default occurs within 90 days of activation, $Y=0$ otherwise, estimated using prefix history $\mathcal{H}_t$.

**Alternative Target:** Multi-state Competing Risk Survival Model.
*   **Definition:** Time-to-event where events are {Default, Activate-NoDefault, Reject, Withdraw, Transfer}.
*   **Why Different:** This answers "What happens to this application?" rather than "Will this loan default?". It allows modeling the selection mechanism (Approval) explicitly.
*   **Justification for Primary:** The business request focuses on capital protection ("early warning"). Operational workflows typically separate *underwriting* (Accept/Reject) from *portfolio monitoring* (Default). Modeling default only on activated accounts avoids semantic nonsense (a rejected applicant cannot default on the loan) while providing actionable risk scores for funded portfolios. However, this introduces **selection bias**: the model does not estimate risk for the full applicant pool, only those the bank chose to fund.

## 2. Cohort construction

**Exclusion Rules:**

2.  Cases where "Account Activated" + 90 days > Data Extraction Date (15 February 2026) — these are right-censored/unlabeled.

## 3. Censoring and missing-label strategy
**Classification of Missingness:**
1.  **Ordinary Right Censoring:** Open cases and Activated cases where $<90$ days have passed since activation.
2.  **Delayed Labels:** Activated cases where the external feed is pending (7–35 day lag).
3.  **Selection Through Activation:** Rejected/Withdrawn cases lack a default label because exposure did not occur. This is structural, not random.
4.  **Transfer Mechanism:** Transferred cases (2,900) represent informative missingness. If high-risk cases are transferred to partners, omitting them biases the dataset toward lower risk.
5.  **Permanently Missing:** Partner-originated accounts without outcome feeds.

**Primary Analysis Strategy:**
Train a binary classifier on the 21,600 labeled cases (Activated + Mature). Treat the problem as supervised learning on a selected subset.
*   **Assumption:** Conditional independence of censoring given covariates (i.e., within the activated population, maturity delay is unrelated to default risk).

**Sensitivity Analysis:**
Perform a **Inverse Probability Weighting (IPW)** simulation on the 3,600 censored activated cases. Estimate propensity of maturity based on region/channel/amount. Re-weight the training set to approximate the full activated population distribution.
*   **Testable:** Distribution of covariates between mature and immature activated cases.
*   **Untestable:** Whether the 2,900 transferred cases would have defaulted had they stayed (requires partner data).

## 4. Prefix extraction
**Strategy:**
Prefixes are extracted up to the **last event before "Account Accepted"** (which precedes Activation).
*   **Fixed Event Count:** Capture first $k=5$ events. Useful for very early warning but loses context of loops.
*   **Elapsed Time:** Capture all events within $T=14$ days of Application Start.
*   **Hybrid Approach:** Used here. All events occurring before the decision timestamp, limited to max 10 events to prevent tail leakage.

**Handling Edge Cases:**
*   **Short Cases:** If a case ends before the prediction point (e.g., immediate rejection), it is excluded from the target population (not applicable to default prediction).
*   **Rework Loops:** "Request Documents" returning to "Credit Review" counts as distinct events. Aggregated features (count of loops) capture rework intensity.
*   **Activity Renaming:** Apply a canonicalization map (e.g., `Check_ID_v2` -> `Identity/KYC Check`) before prefix extraction to ensure consistent DFG variants across the migration date (15 Oct 2025).

## 5. Process-aware features
**Static Case Attributes:**
*   `case:requested_amount` (Log-transformed).
*   `case:channel`, `case:region`.
*   `org:resource` (Resource ID encoded via target encoding on historical default rates).

**Prefix-Derived Features (Available at Prediction Time):**
*   **Control Flow:** Number of unique activities seen, number of loops in Credit Review, variant hash (sequence fingerprint).
*   **Timing:** Elapsed time from Start to Current Event, average inter-arrival time.
*   **Resource:** Cumulative workload of handler (events/hour) at time of event.
*   **Content:** Count of document upload events (`documents_total` snapshot truncated to current time).

**Historical Reference Data:**
*   Resource Experience: Calculated from historical logs *prior* to the current case start date (to avoid leakage of current case impact on resource stats).

## 7. Validation design
**Temporal Split Scheme:**
*   **Training:** 1 Jan 2024 – 30 June 2025. (Captures pre-policy-change behavior).
*   **Validation:** 1 July 2025 – 31 Dec 2025. (Captures post-policy-change behavior).
*   **Test:** 1 Jan 2026 – 15 Feb 2026. (Latest matured data).
*   **Note:** Cases starting in late 2025 are excluded from training/test if their 90-day horizon extends past 15 Feb 2026.

**Why Not Random Split:**
A random split mixes policy regimes (pre/post-July 2025). The model might learn "Pre-July patterns" and fail on "Post-July patterns". Additionally, random splitting leaks future label maturity into training (training on cases that haven't matured yet).

**Metrics:**
*   **Discrimination:** AUC-ROC, PR-AUC (due to class imbalance).
*   **Calibration:** Brier Score, Reliability Diagram. Critical because probabilities drive capital reserves.
*   **Stability:** PSI (Population Stability Index) between Training and Validation cohorts to detect policy drift.

## 8. Limitations and decision-use boundary
**Claims:**
*   The model predicts the likelihood of default *for loans already approved*.
*   The model captures process inefficiencies (loops, delays) correlated with higher risk.

**Non-Claims:**
*   The model does **not** predict default risk for rejected applicants (counterfactual unknown).
*   The model does **not** guarantee accuracy if underwriting policy changes again (distribution shift).

**Deployment Effects:**
1.  **Berkson’s Paradox:** If the model is used to reject more applicants, the remaining approved pool becomes lower risk, causing the model to appear miscalibrated (over-predicting default).
2.  **Feedback Loop:** High-risk flags may trigger stricter collection, altering the "default" definition or timing.
3.  **Data Drift:** If "Credit Review" duration shortens due to automation, timing features will shift.

import pandas as pd
import pm4py
from datetime import datetime, timedelta

# 1. Load and Parse Data
df = pd.read_csv('applications_events.csv', parse_dates=['time:timestamp', 'data_extract_time'])
# Canonicalize activity names for migration handling
activity_map = {'Check_ID_v2': 'Identity/KYC Check', 'New_Credit_Review': 'Credit Review'}
df['concept:name'] = df['concept:name'].map(activity_map).fillna(df['concept:name'])

# 2. Define Cutoffs and Filters
EXTRACTION_DATE = datetime(2026, 2, 15)
POLICY_CHANGE = datetime(2025, 7, 1)
MIGRATION_DATE = datetime(2025, 10, 15)

# Identify terminal events per case
case_ends = df.groupby('case:concept:name')['time:timestamp'].max().reset_index()
case_ends.rename(columns={'time:timestamp': 'case_end_time'}, inplace=True)
df = df.merge(case_ends, on='case:concept:name')

# Filter for cases with mature labels (Activation + 90 days <= Extraction)
# Assume 'Account Activated' is a specific activity name
activation_times = df[df['concept:name'] == 'Account Activated'][['case:concept:name', 'time:timestamp']]
activation_times.columns = ['case:concept:name', 'activation_time']
df = df.merge(activation_times, on='case:concept:name', how='left')

# Define Label Maturity Rule
def is_mature(row):
    if pd.isna(row['activation_time']): return False
    return (row['activation_time'] + timedelta(days=90)) <= EXTRACTION_DATE

df['is_mature'] = df.apply(is_mature, axis=1)
train_val_df = df[(df['time:timestamp'] < POLICY_CHANGE)] # Pre-policy change for training
test_df = df[(df['time:timestamp'] >= POLICY_CHANGE) & df['is_mature']] # Post-policy for validation

# 3. Format for PM4Py
log_train = pm4py.format_dataframe(train_val_df, 
                                   case_id_col='case:concept:name', 
                                   activity_col='concept:name', 
                                   timestamp_col='time:timestamp')

# 4. Prefix Extraction (Before Decision)
# We assume 'Account Accepted' is the decision point. Stop prefix there.
decision_stop = 'Account Accepted'
prefix_log = pm4py.filter_traces(log_train, lambda trace: [ev for ev in trace if ev['concept:name'] != decision_stop])

# Get fixed-length prefixes for feature engineering
prefixes = pm4py.get_prefixes_from_log(prefix_log, k=5) 

# 5. Feature Engineering (Audit against Leakage)
features = []
for case_id, trace in zip(prefix_log._cases, prefix_log):
    row = {}
    row['case_id'] = str(case_id)
    
    # Static features (ensure available at start)
    start_event = trace[0]
    row['requested_amount'] = start_event.get('case:requested_amount', 0)
    row['channel'] = start_event.get('case:channel', '')
    
    # Process features
    row['duration_days'] = (trace[-1]['time:timestamp'] - trace[0]['time:timestamp']).days
    row['event_count'] = len(trace)
    row['has_loop'] = 1 if len([x for x in trace if x['concept:name'] == 'Credit Review']) > 1 else 0
    
    # LEAKAGE CHECK: Ensure no final_limit or decision_reason included
    # These columns should be dropped from raw DF before this step if present
    features.append(row)

feat_df = pd.DataFrame(features)

# 6. Target Alignment (Join Label)
# Join maturity status and actual label back to case level
case_labels = train_val_df[train_val_df['is_mature']][['case:concept:name', 'default_90d']].drop_duplicates()
feat_df = feat_df.merge(case_labels, left_on='case_id', right_on='case:concept:name', how='left')

# 7. Basic Audit Output
