# 1. Objectives and constraints

The policy is intentionally **multi-objective**. It should not optimize only for immediate throughput, because the historical evidence shows that ignoring handovers, skill mismatch, and overload creates rework, appeals, and bottlenecks.

## Optimization objectives

1. **Protect SLA and customer commitments**
   - Urgent and high-priority cases should be staffed with resources who can complete them safely within the remaining SLA time.
   - Scarce specialist capacity should be reserved for activities where it is truly needed, especially Security Review and Final Approval.

2. **Maintain service quality and reduce error/rework**
   - Assign work only to resources with adequate skill.
   - Use supervision where a trainee assignment is developmentally useful but not yet fully safe.
   - Avoid repeated unnecessary reassignments, especially on complex cases.

3. **Support sustainable throughput**
   - Short-term speed matters, but not if it creates rework, overload, or later SLA breaches.
   - Batch low-risk work where appropriate, such as eligible Quality Check cases.

4. **Develop skills in a controlled way**
   - Use documented training priorities.
   - Prefer training assignments on normal/low-priority cases with sufficient SLA buffer.
   - Ensure supervision is explicit and logged.

5. **Balance workload fairly**
   - Avoid repeatedly assigning new work to already overloaded resources.
   - Protect resources with high overtime risk unless there is no safer alternative.
   - Respect the batch cap of no more than 4 new assignments per resource.

6. **Preserve continuity where it creates value**
   - Keep current owners on high-complexity or high-handover-cost cases when their skill is sufficient.
   - Avoid changing ownership on cases that already have many reassignments.

7. **Improve resilience**
   - Avoid creating single points of failure, especially in Security and Approval.
   - Build backup capability through supervised exposure, observation, and cross-team assignments where safe.

---

## Hard safety and compliance constraints

These are treated as non-negotiable unless an explicit, logged managerial exception is made.

| Constraint | Meaning |
|---|---|
| Skill authorization | A resource with skill level 0 may not perform the required activity. Observation/shadowing is allowed only if the qualified resource performs the decision-making work. |
| Security Review | Must be performed by skill level 3, or by skill level 1–2 only under explicit supervision by R7_Gita or R8_Hugo. |
| Final Approval | Must be finalized by skill level 2–3. Skill level 1 may prepare but not finalize. |
| High-priority skill floor | Urgent/high-priority cases must not be assigned to skill level below 2 unless a qualified supervisor is explicitly assigned. |
| Maximum new assignments | No resource receives more than 4 new assignments in the current decision batch. |
| High overtime protection | Resources with overtime risk = high should not receive new assignments unless the case is urgent and no safer alternative exists. Any exception must be logged. |
| Quality batching | Quality Check may be batched only for normal/low priority cases with SLA time remaining > 24 hours. |
| Supervision feasibility | A supervised assignment is valid only if the supervisor has sufficient skill, available hours, and does not exceed the assignment cap. |

---

## Preference trade-offs and soft constraints

These are optimized, but they can conflict. The policy makes the trade-offs explicit rather than pretending there is one obvious optimum.

| Preference | How it is treated |
|---|---|
| Continuity | Strongly preferred for high-complexity, high-handover-cost, or repeatedly reassigned cases. It can be overridden by urgent SLA risk, insufficient skill, or compliance rules. |
| Training | At least 20% of normal/low-priority assignments should support documented training priorities when SLA risk remains acceptable. Training should not compromise urgent/high-priority work unless supervision is strong. |
| Workload fairness | Prefer resources with lower open cases, more remaining hours, and lower overtime risk. |
| Specialist preservation | Avoid using scarce specialists for work that competent non-specialists can safely perform. |
| Bottleneck avoidance | Avoid over-concentrating Security, Approval, or high-complexity Diagnosis work on one person or one team. |
| Reassignment control | Avoid increasing reassignment count beyond 2 unless there is a clear safety, fairness, or SLA reason. |

# 2. Assignment policy

The policy is a **constrained scoring policy**. It first filters out invalid or unsafe assignments, then scores the remaining candidates using explainable factors.

It should be re-run dynamically, for example every 15–30 minutes or when any of the following occurs:

- New case arrives.
- SLA remaining changes materially.
- Resource becomes unavailable.
- Case priority changes.
- A handover or supervision request is opened.
- A case is blocked or reworked.

---

## High-level algorithm

```text
For each decision batch:

1. Reset each resource's new_assignment_count = 0.

2. Sort cases by:
   a. priority: urgent > high > normal > low
   b. SLA time remaining ascending
   c. complexity descending
   d. handover cost descending

3. For each case in sorted order:

   a. Identify required skill and activity-specific rules.

   b. Generate candidate assignments:
      - Single qualified resource.
      - Supervised pair if trainee use is allowed and useful.
      - Observer/shadow pair only if the primary resource remains fully accountable.

   c. Eligibility filtering:
      - Reject skill level 0 for performing the activity.
      - Reject Security Review unless:
          resource skill = 3, or
          resource skill = 1/2 and supervisor is R7_Gita or R8_Hugo.
      - Reject Final Approval finalization unless resource skill >= 2.
      - Reject urgent/high assignment to skill < 2 unless supervised.
      - Reject resources already at 4 new assignments.
      - Reject high-overtime-risk resources unless:
          case is urgent, and
          no safer feasible alternative exists.
      - For Quality Check batching:
          only batch if priority is normal/low and SLA remaining > 24h.

   d. Score each feasible candidate.

   e. Select the highest-scoring candidate.

   f. Tie-breaking:
      - If scores are close, prefer current owner.
      - Then prefer lower handover cost.
      - Then prefer lower workload and lower overtime risk.
      - Then prefer training value if training quota is not yet met.
      - Then prefer earlier SLA protection.

   g. Log:
      - assignment_reason
      - supervisor if any
      - exception reason if any
      - expected risk indicators
```

---

## Scoring model

A transparent scoring model could use the following weights. The exact weights should be reviewed with operations, HR, and service management.

```text
Total score =
    0.30 * SLA urgency score
  + 0.20 * skill-match score
  + 0.15 * continuity / handover-cost score
  + 0.15 * workload and overtime fairness score
  + 0.10 * training / development score
  + 0.10 * resilience / bottleneck-avoidance score
  - hard-constraint penalties
```

---

## 1. SLA urgency scoring

Purpose: prioritize cases where delay is costly or likely.

```text
priority_weight:
  urgent = 30
  high   = 20
  normal = 10
  low    = 0

sla_pressure = 10 * exp(-SLA_hours_remaining / 8)

complexity_pressure = 5 * case_complexity

SLA_score = priority_weight + sla_pressure + complexity_pressure
```

Additional rules:

- If SLA remaining is less than 4 hours, apply a strong bonus to candidates who can start immediately.
- If the resource has low remaining hours today, penalize assignments that cannot realistically be completed today.

---

## 2. Skill-match scoring

Purpose: reduce error, rework, and supervision burden.

```text
skill_level:
  0 = not allowed
  1 = trainee
  2 = competent
  3 = specialist

skill_score = 30 * skill_level / 3
```

Adjustments:

- Add bonus if the resource is a specialist and the case is high complexity.
- Add bonus if the resource has the exact required skill and no supervision is needed.
- Penalize skill level 1 on high-complexity cases unless supervision is strong.
- Penalize skill level 2 on urgent security/approval cases if a specialist is available and capacity allows.
- For Security Review, skill level 3 is strongly preferred unless a supervised skill 1–2 assignment is explicitly feasible.

---

## 3. Continuity and handover-cost scoring

Purpose: avoid the known cost of unnecessary owner changes.

```text
If current owner is retained:
  continuity_score = 25

If current owner has skill 1 but is retained with supervision:
  continuity_score = 15

If owner changes:
  continuity_score = 0
```

Penalties for changing owner:

```text
handover_cost_penalty:
  low    = 3
  medium = 10
  high   = 20

reassignment_penalty:
  if existing reassignment_count >= 2 and owner changes:
      add 15 penalty

complexity_penalty:
  if case_complexity > 0.75 and owner changes:
      add 10 penalty
```

Exception:

- If the current owner has skill 0 or 1, the SLA is urgent, and a specialist can reduce material risk, the policy may override continuity. The reason must be logged as `sla_override_continuity`.

---

## 4. Workload and overtime fairness scoring

Purpose: avoid overload and protect high-overtime-risk resources.

```text
workload_score =
    20 * (1 - current_open_cases / max_open_cases)
  + 10 * (hours_remaining_today / 8)
  - overtime_penalty
  - 5 * new_assignments_already_in_batch
```

Overtime penalty:

```text
overtime_risk:
  high   = 20
  medium = 8
  low    = 0
```

Rules:

- High-overtime-risk resources should not receive normal/low-priority work if a safer alternative exists.
- If a high-overtime-risk resource must receive urgent work, log `urgent_no_safe_alternative`.
- Handover duties are not counted as full new case assignments, but they should be considered in capacity planning.

---

## 5. Training and development scoring

Purpose: meet the training target without endangering SLAs.

```text
training_score = 0

If required skill matches the resource's documented training priority:
  if case priority is normal or low:
    if SLA remaining is comfortable:
      if supervisor is available:
        training_score += 15

If the assignment is observation/shadowing only:
  training_score += 8

If case is urgent/high:
  training_score is allowed only if:
    the trainee is not the accountable performer, or
    the trainee has skill >= 2 and supervision is strong.
```

Training assignments must produce an explicit `assignment_reason`, such as:

- `training_supervised`
- `training_observation`
- `training_future_capability`

---

## 6. Resilience and bottleneck avoidance

Purpose: prevent over-reliance on scarce specialists or single resources.

```text
resilience_score = 0

Add bonus:
  +10 if assignment creates a backup capability through supervised exposure.
  +5 if assignment batches compatible work efficiently.
  +5 if assignment reduces dependence on a single team for a critical skill.

Subtract penalty:
  -15 if assignment increases load on a scarce specialist beyond a threshold.
  -10 if multiple urgent cases are assigned to the same resource in one batch.
  -5 if the resource is already the dominant owner for that activity.
```

Historical process-mining indicators can inform this part:

- `pm4py.discover_handover_of_work_network` can reveal harmful handover patterns.
- `pm4py.discover_activity_based_resource_similarity` can identify possible backups.
- `pm4py.discover_organizational_roles` can detect structural bottlenecks.
- `pm4py.discover_batches` can identify where batching is already working.

---

## Tie-breaking and exception handling

When two or more candidates have similar scores:

1. Prefer keeping the current owner if skill is sufficient.
2. Prefer the lower handover-cost option.
3. Prefer the resource with lower open cases and lower overtime risk.
4. Prefer the assignment that helps meet the training quota.
5. Prefer the assignment that reduces specialist concentration.
6. Prefer the resource in the same team or role already close to the case.

If no feasible assignment exists:

- Try adding a supervisor.
- Try splitting preparation and finalization, where allowed.
- Try batching low-priority work.
- Defer low-priority work if SLA allows.
- Escalate to a team lead for an explicit exception.
- Log the exception in `assignment_reason`.

# 4. Comparison with baseline policies

There is no single obvious optimum. The best policy depends on how much weight the organization gives to immediate throughput, error prevention, fairness, learning, and resilience.

---

## Likely behavior of first-available routing

First-available routing assigns cases to the resource with the lowest open cases and enough hours, ignoring specialization except skill level 0.

In this queue, it would tend to favor resources such as:

- R10_Jonas because open cases are low.
- R6_Farid because open cases are low.
- R3_Celine because open cases are moderate.
- R8_Hugo because open cases are moderate.

However, it would create several problems:

- It may assign high-priority negotiation or diagnosis work to skill level 1 resources.
- It may ignore continuity on high-handover cases.
- It may create hidden skill mismatch even when the case is technically assigned.
- It may reduce immediate waiting time but increase rework and reassignment later.

---

## Likely behavior of specialist-only routing

Specialist-only routing assigns each case to the highest-skilled resource for the required skill, breaking ties by open cases.

In this queue, it would tend to concentrate work on:

- R8_Hugo and R7_Gita for Security Review.
- R6_Farid for Approval and Negotiation.
- R3_Celine for Diagnosis and Rework.
- R10_Jonas, R8_Hugo, or R9_Iris for Quality.

This reduces immediate skill mismatch, but creates other problems:

- Security and Approval become bottlenecks.
- R3 and R6 may become overloaded.
- Continuity may be ignored, for example by moving C016 away from R5.
- Training opportunities are reduced because specialists take most work.
- Workload fairness worsens because the best specialists receive disproportionate demand.

---

## Comparison table

| Dimension | First-available routing | Specialist-only routing | Proposed explainable dynamic policy |
|---|---|---|---|
| Expected short-term throughput | May appear high because low-load resources are used quickly. | May be high for simple specialist tasks, but lower overall due to specialist queues. | Balanced. Some cases move slightly slower, but rework and overload are reduced. |
| Sustainable throughput | Lower than expected because skill mismatch increases rework and handovers. | Can suffer because scarce specialists become bottlenecks. | Higher sustainability due to workload caps, supervision, and batching. |
| SLA risk | Higher for complex, urgent, or security-sensitive cases. | Lower for skill-critical cases, but higher where specialist queues form. | Low to moderate. Urgent cases receive specialist or competent capacity, with handover risk explicitly managed. |
| Error/rework risk | High due to skill mismatch and weak continuity. | Low immediate technical error risk, but rework can rise from handovers and delays. | Moderate to low. Skill match, supervision, and continuity are balanced. |
| Workload fairness | Superficially fair by open cases, but ignores overtime risk and skill burden. | Poor. Specialists and high-capability resources are overloaded. | Better. High-overtime resources are protected, caps are enforced, and work is spread. |
| Skill development | Accidental and uncontrolled. Trainees may receive risky work without supervision. | Poor. Specialists take most work, reducing learning opportunities. | Controlled. Training is supervised, logged, and concentrated where SLA risk is acceptable. |
| Continuity of ownership | Poor. Cases move to whoever is available. | Poor when a higher-skilled resource exists elsewhere. | Moderate to good. Current owner is retained for C007, C008, C009, C011, C012, C015, C016. Controlled changes occur only with reason. |
| Resilience to absence | Fragile. Many resources may lack required skill. | Fragile. Absence of one specialist can stop critical activities. | Better. Supervised pairs, observers, and cross-team assignments create future backup, though Security remains structurally scarce. |
| Explainability | Low. “Lowest workload” is easy but ignores why work succeeds. | Medium. “Highest skill” is easy but ignores fairness and continuity. | High. Each assignment can be explained using urgency, skill, continuity, workload, training, and resilience. |
| Auditability | Weak unless skill mismatch and rework are tracked. | Weak for fairness and training. | Strong because assignment reasons, exceptions, supervision, and batch rules can be logged. |

# 5. Explanation to workers

The following explanation could be shown directly to workers.

---

## How assignments are decided

We use a transparent assignment process that considers several things at once:

- Customer urgency and SLA risk.
- The skills required for the next activity.
- Your current workload and remaining available hours.
- Whether keeping the current owner avoids a costly handover.
- Whether the case can safely support your development goals.
- Whether we are overloading a small number of specialists.

The goal is not simply to give work to the fastest available person. We also want to avoid rework, protect people from excessive overtime, and create safe learning opportunities.

---

## Why some cases stay with the current owner

Some cases remain with the current owner because changing ownership would create avoidable delay or rework risk. This is especially true when:

- The case is complex.
- The handover cost is high.
- The case has already been reassigned several times.
- The current owner has sufficient skill.

For example, keeping continuity on complex rework or diagnosis cases can prevent repeated handovers and customer frustration.

---

## why some cases move to another colleague

A case may be moved when:

- The current owner is overloaded or at high overtime risk.
- The activity requires a specialist authorization.
- The SLA is tight and the current owner cannot safely complete the work in time.
- A lower-risk colleague has the right skill level.

When a case is moved, we try to use a structured handover. The previous owner may still be asked to provide context, but the goal is not to add their full workload back to them.

---

## Why some assignments include supervision or observation

Some assignments are used for development. If you are assigned a case as a trainee, a qualified colleague will be named as supervisor. This is not a judgment that you are incapable. It is a way to build capability safely.

If you are assigned as an observer, you are not expected to make the final decision. The primary resource remains accountable.

Training assignments are chosen where the customer impact and SLA risk are acceptable.

---

## Why we protect some colleagues from new assignments

Resources with high overtime risk or very high open case counts may receive fewer or no new assignments in a batch. This is not punitive. It is intended to protect sustainable working and reduce error risk.

If an urgent case absolutely requires their involvement, the exception will be logged and explained.

---

## What you can do if an assignment feels wrong

If you receive an assignment and believe that:

- The SLA is unrealistic,
- You lack the required skill or authorization,
- Supervision is not actually available,
- The workload is unsafe,
- Or the handover information is missing,

then you should flag it immediately. The policy is designed to be challenged and improved, not followed blindly.

Every assignment should have a clear reason code, such as:

- `sla_urgent_specialist`
- `continuity_high_handover`
- `workload_fairness`
- `training_supervised`
- `batch_quality`
- `high_overtime_exception`

These reason codes make the policy auditable and help us improve it over time.

---

# 6. Process-mining audit indicators

The deployed policy should be audited continuously using the event log. The log should contain, at minimum, the provided columns, plus explicit fields for supervisor and assignment reason where possible.

---

## Core audit indicators

| Indicator | Definition | How to measure | What to watch for |
|---|---|---|---|
| Handover frequency | Number of owner changes per case or per day. | Detect changes in `current_owner` or `org:resource` across events. Use `pm4py.discover_handover_of_work_network`. | Rising handover frequency on complex cases. |
| Reassignment count | Count of reassignments per case. | Use `reassignment_count` or compute from owner-change events. | Cases with count > 2 should have higher rework/appeal monitoring. |
| Skill mismatch rate | Share of events where resource skill is below required threshold. | Join event log with skill matrix using `org:resource` and `required_skill`. | High mismatch on urgent/high cases is a serious policy failure. |
| Unauthorized Security/Approval rate | Security Review performed without required skill or supervision; Final Approval finalized by skill < 2. | Filter `Security Review` and `Final Approval` events, then check skill and supervisor fields. | Any nonzero unauthorized Security Review rate should trigger immediate audit. |
| Workload distribution | Fairness of new assignments and open cases across resources. | Compute open cases per resource, new assignments per batch, and Gini coefficient. Use `workload_snapshot`. | Persistent overload of specialists or high-overtime resources. |
| Overtime risk exposure | Amount of new work assigned to resources with high overtime risk. | Filter events by resources with `Overtime risk = high`. Compare assigned effort against `Hours remaining today`. | High-overtime resources receiving normal/low work without exception. |
| SLA miss rate | Share of cases completed after `sla_deadline`. | Compare final event timestamp with `sla_deadline`. Use `pm4py.filter_case_performance` and time calculations. | SLA misses concentrated in Security, Approval, or high-complexity cases. |
| SLA near-miss rate | Cases completed close to deadline or with excessive waiting. | Use `pm4py.insert_case_service_waiting_time` to analyze waiting and service time. | Growing waiting time before specialist activities. |
| Rework after assignment | Rate of `Rework Correction` or appeal-like variants after an assignment decision. | Use `pm4py.get_variants` and `pm4py.discover_performance_dfg`. Filter cases where rework occurs after assignment. | Rework spikes after trainee assignments, handovers, or skill mismatch. |
| Training assignment share | Percentage of normal/low-priority assignments that support documented training. | Filter normal/low cases and count those with `assignment_reason` containing training. | Training share below 20% or training occurring on urgent cases without strong supervision. |
| Supervision effectiveness | Whether supervised assignments reduce errors compared with unsupervised trainee work. | Use `pm4py.discover_working_together_network` to identify pairs, then compare rework rates. | Supervised cases with rework rates similar to unsupported mismatch cases. |
| Specialist bottleneck indicator | Queue length, waiting time, and utilization for Security and Approval specialists. | Filter Security Review and Final Approval events. Use service/waiting time and resource utilization. | R7/R8 or approval specialists becoming persistent bottlenecks. |
| Batch compliance | Whether Quality Check batching only occurs for allowed cases. | Use `pm4py.discover_batches` and filter Quality Check cases by priority and SLA remaining. | Batching urgent or near-SLA Quality Check cases. |
| Policy deviation rate | Share of assignments violating hard constraints or requiring exceptions. | Compare each assignment against policy rules. Count exceptions in `assignment_reason`. | Rising deviation rate indicates policy drift or capacity shortage. |
| Continuity preservation rate | Share of high-complexity/high-handover cases kept with current owner when skill is sufficient. | Filter high complexity/high handover cases and compare `current_owner` with assigned resource. | Low continuity preservation with no documented SLA or safety reason. |

---

## Suggested audit views

1. **Daily operational view**
   - SLA misses and near misses.
   - Urgent cases assigned to skill < 2 without supervision.
   - High-overtime resources receiving new work.
   - Security and Approval queue depth.

2. **Weekly fairness and development view**
   - Workload Gini by team.
   - New assignments per resource.
   - Training assignment share.
   - Supervised assignment outcomes.

3. **Monthly structural view**
   - Handover network changes.
   - Organizational role concentration.
   - Resource similarity and backup coverage.
   - Rework/appeal rates by assignment reason.
   - Bottleneck trends in Security and Approval.

# Simple Gini coefficient for workload distribution
def gini(values):
    values = sorted(values)
    n = len(values)
    if n == 0:
        return 0
    total = sum(values)
    if total == 0:
        return 0
    cumulative = 0
    weighted_sum = 0
    for i, v in enumerate(values, start=1):
        cumulative += v
        weighted_sum += i * v
    return (2 * weighted_sum) / (n * total) - (n + 1) / n

workload_gini = gini(list(new_assignments_per_resource))

    security_approval_events
    .groupby("org:resource")["case:concept:name"]
    .nunique()
)
