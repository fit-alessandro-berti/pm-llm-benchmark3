## 1. Equivalence design space

Let an execution be a lead-Order-centered structure \(E=(V_E,V_O,I_E,R_O,\prec)\), where \(V_E\) is its event set, \(V_O\) is its object set, \(I_E\) is event-to-object incidence, \(R_O\) is the set of directed object-to-object relations, and \(\prec\) is the event order. A local renaming is a bijection on object identifiers that preserves the object type and the external flag. I treat an identifier beginning with \`EXT\` as externally centered, independently of its literal suffix.

### Activity-sequence equivalence

Define

\[
E \mathrel{\sim_A} F \quad\Longleftrightarrow\quad
L(E)=L(F),
\]

where \(L(E)\) is the sequence of activity labels in event order. Repeated labels are repeated entries; they are not reduced to a set. For the executions in the question, this gives, for example, \`Create, Add Item, Add Item, Pack, Dispatch, Issue Invoice, Record Payment\` for X1, X2, X5, X6, and X7.

The invariants are the activity vocabulary, event count, repetition count, and order of the labels. It discards all object identifiers and types, object multiplicities, E2O incidence, O2O topology, external-object status, qualifiers, event attributes, and timing gaps. It also cannot tell whether two equal-label events concern the same or different objects.

With equality of these normalized label sequences, the relation is reflexive, symmetric, and transitive. My default concurrency convention is that events with distinct timestamps are ordered, while events at the same timestamp form a multiset block whose labels are sorted before comparison. Thus an arbitrary serialization of concurrent equal-time events is not significant, although multiplicity within the block remains significant. If an explicit partial order is available, the stronger alternative is isomorphism of the activity-labeled event posets; that preserves the given causal order and leaves incomparable events interchangeable.

### Typed structural equivalence under identifier renaming

Construct a typed incidence graph \(G_T(E)\). It has:

- an event vertex for every event, colored by activity and its order position (or by activity and timestamp/poset position for concurrent events);
- an object vertex for every object, colored by \`(object type, external flag)\`;
- a typed E2O edge for every event-object participation, including its role if a role is available; and
- a directed O2O edge for every explicit unqualified relation such as \`contains\`, \`packs\`, \`carries\`, \`bills\`, or \`settles\`.

Then \(E\sim_T F\) when there is a color-preserving graph isomorphism between these graphs that preserves strict event order, or preserves the event partial order in the concurrent version. The isomorphism is allowed to rename local and external object identifiers, but cannot change object types or the external flag. O2O edge labels are preserved, while qualifiers attached to edges are deliberately omitted from this relation.

This preserves event and object counts, repeated activities, per-event typed incidence, multiplicities of objects of each type, package/item and delivery/package topology, unqualified sharing, and the order of lifecycle events. It discards literal identifiers, absolute timestamps and durations, event attributes such as amounts, and qualifier meanings such as \`removed_before_dispatch\`, \`partially_settles\`, or \`completes_settlement\`. It also discards any relation not represented in the input structure.

Graph isomorphism with the stated color and order constraints is reflexive, symmetric, and transitive. For same-time events, I use an order-preserving isomorphism on the strict-order quotient and permit permutations within each same-time antichain. If explicit causal edges exist among same-time events, those edges are included in the partial order.

### Business-semantic equivalence

For the preferred relation, I compare a canonical business graph rather than literal identifiers. Its signature retains the following business facts:

1. the ordered or partially ordered lifecycle motif, including repeated activities and motifs such as return/repack;
2. counts of local and external objects by type;
3. the E2O incidence needed to recover item-to-package, package-to-delivery, invoice-to-order, and payment-to-invoice multiplicities;
4. whether an external Order or external Item participates in logistics or finance; and
5. normalized O2O qualifiers and lineage motifs, including replacement, removal before dispatch, partial/completing settlement, return, inspection, repack, and package replacement.

Two executions are business-semantically equivalent, \(E\sim_B F\), when these normalized facts are equal after local identifier renaming. The normalization ignores the names of local objects, the order of objects inside an event's object set, absolute dates and time gaps, and arbitrary order among genuinely concurrent events. It does not ignore a repeated event, an object multiplicity, a cross-order edge, or a qualifier that changes the business interpretation.

This is an equivalence relation because it is equality of a deterministic canonical signature: it is reflexive, symmetric, and transitive. Same-time independent events are represented as an unordered block, while explicit precedence constraints are retained. A semantic implementation that intentionally removes more detail, for example all payment states, is also an equivalence relation, but it is a different and coarser relation.

## 2. Canonical signatures

I use the following canonical signature for \(\sim_B\). The input records are assumed to have this conceptual form:

\`\`\`python
# event["objects"] contains (object_type, object_id) pairs
# relation["src"] and relation["dst"] contain (object_type, object_id)
# event["qualifiers"] and relation["qualifier"] are optional
# events are sorted by timestamp; equal-time events are a concurrency block
\`\`\`

The code enumerates the possible renamings within each \`(type, external_flag)\` color class and chooses the lexicographically least serialization. This is simple and reproducible for compact executions. A production implementation can replace the enumeration with a colored-graph canonical-labeling library.

\`\`\`python
from collections import defaultdict
from itertools import permutations, product


def is_external(obj_id):
    return str(obj_id).startswith("EXT")


def obj_key(obj):
    # obj is {"type": ..., "id": ..., "external": optional}
    ext = obj.get("external", is_external(obj["id"]))
    return (obj["type"], obj["id"], bool(ext))


def endpoint_token(endpoint, rename):
    typ, oid = endpoint
    return (typ, bool(is_external(oid)), rename[(typ, oid)])


def qualifier_token(q, rename):
    if q is None:
        return None
    # A qualifier may optionally carry endpoints or an event position.
    endpoints = tuple(sorted(
        endpoint_token(x, rename) for x in q.get("endpoints", [])
    ))
    return (q.get("name"), q.get("event_index"), endpoints)


def event_atom(event, rename, event_index):
    incidences = []
    for typ, oid in event.get("objects", []):
        incidences.append((typ, bool(is_external(oid)), rename[(typ, oid)]))
    incidences = tuple(sorted(incidences))
    qualifiers = tuple(sorted(
        qualifier_token(q, rename)
        for q in event.get("qualifiers", [])
    ))
    return (event["activity"], incidences, qualifiers, event_index)


def ordered_event_part(execution, rename):
    atoms = [event_atom(e, rename, i)
             for i, e in enumerate(execution["events"])]
    # The listed order is used for strict timestamps. Equal-time events
    # become a sorted block, so their arbitrary serialization is ignored.
    result = []
    i = 0
    while i < len(execution["events"]):
        t = execution["events"][i].get("time")
        j = i + 1
        while (j < len(execution["events"])
               and execution["events"][j].get("time") == t):
            j += 1
        block = atoms[i:j]
        if j - i == 1:
            result.append(("event", block[0]))
        else:
            # Drop the input position inside a concurrent block.
            block = [(a, inc, q, None) for a, inc, q, _ in block]
            result.append(("concurrent_block", tuple(sorted(block))))
        i = j
    return tuple(result)


def canonical_signature(execution):
    # objects must include every object in the lead Order component,
    # including objects that occur only in an O2O relation.
    groups = defaultdict(list)
    for obj in execution["objects"]:
        ext = obj.get("external", is_external(obj["id"]))
        groups[(obj["type"], bool(ext))].append(obj["id"])
    groups = [(color, tuple(sorted(ids)))
              for color, ids in sorted(groups.items())]

    best = None
    permutation_choices = [list(permutations(ids)) for _, ids in groups]
    for choices in product(*permutation_choices):
        rename = {}
        for (typ, ext), ordered_ids in zip(groups, choices):
            for rank, oid in enumerate(ordered_ids):
                # The type and external bit are part of the canonical name.
                rename[(typ, oid)] = f"{typ}:{int(ext)}:{rank}"

        o2o = []
        for r in execution.get("o2o", []):
            src = endpoint_token(r["src"], rename)
            dst = endpoint_token(r["dst"], rename)
            o2o.append((r["relation"], src, dst,
                        qualifier_token(r.get("qualifier"), rename)))
        o2o = tuple(sorted(o2o))

        # Keep the semantic incidence, not raw IDs. The lead object type
        # is normally Order; all external objects in its component remain.
        candidate = (
            execution.get("lead_type", "Order"),
            ordered_event_part(execution, rename),
            o2o,
        )
        if best is None or candidate < best:
            best = candidate
    return best
\`\`\`

The event index in \`event_atom\` is retained for strict order and then removed inside a concurrent block. Object lists within one event are sorted, so X1 and X2 can map the item from the first \`Add Item\` event to different literal identifiers while producing the same signature. The canonical signature keeps repeated event atoms, typed multiplicities, external flags, E2O incidence, and qualified O2O edges. For a coarser segmentation key, I would project this signature to counts and motifs—for example, \`(package_count, delivery_count, payment_count, package_item_partition, delivery_package_partition, sharing_flags, qualifier_motifs)\`—but I use the stronger signature above for the preferred clusters in this answer.

## 3. Cluster assignments

The activity clusters are defined by the normalized activity words shown in the table. The typed structural relation includes unqualified E2O/O2O structure; the preferred semantic relation additionally includes qualifiers and external-sharing semantics.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature | Main reason |
|---|---|---|---|---|---|
| X1 | A1 | T1 | S1 | local; 2 items; 1 package carrying both; 1 delivery; 1 invoice; 1 payment; no qualifiers | Isolated baseline |
| X2 | A1 | T1 | S1 | same as X1 after a type-preserving rename | Same topology and lifecycle; Add Item order is not an observable difference |
| X3 | A2 | T2 | S2 | local; 2 one-item packages; 1 delivery carrying both; 1 invoice; 1 payment | Split packing with consolidated delivery |
| X4 | A3 | T3 | S3 | local; 2 one-item packages; 2 one-package deliveries; 1 invoice; 2 qualified payments | Split shipment and partial/completing settlement |
| X5 | A1 | T4 | S4 | 2 local items plus external item/order; shared package and delivery; local-only billing | Cross-order logistics sharing |
| X6 | A1 | T5 | S5 | local logistics; invoice shared with external Order; one unallocated payment | Cross-order financial sharing |
| X7 | A1 | T6 | S6 | baseline counts plus replacement/removal lineage for the item | Item substitution hidden by a superficially similar flow |
| X8 | A4 | T7 | S7 | initial two-item package, return/inspection, one-item repack and second delivery; package replacement | Return and repack lifecycle |

Thus the preferred partition is \`{X1, X2}\`, \`{X3}\`, \`{X4}\`, \`{X5}\`, \`{X6}\`, \`{X7}\`, \`{X8}\`. It is intentionally conservative about business semantics: sharing, lineage, and lifecycle qualifiers are material even when the activity labels look familiar.

## 4. Cluster interpretations

### S1 — Isolated baseline: X1 and X2

Signature: \`items=2, packages=1, deliveries=1, invoice=1, payment=1, external-sharing=false, replacement/return=false\`.

This is a normal single-package, single-delivery, fully paid Order. It is a good candidate for straight-through processing and baseline KPI comparison. The main risks are ordinary scan, packing, invoice, and payment reconciliation failures; the cluster itself does not expose item-level quality unless the E2O links are retained.

A one-trace-per-Order flattening represents the phase sequence reasonably well, but represents item-to-package membership and delivery evidence poorly. The cluster is stable under reasonable identifier repair and harmless reordering of the two \`Add Item\` records, provided the package, delivery, invoice, and payment links are not inferred away.

### S2 — Split packages with consolidated delivery: X3

Signature: \`packages=2, each package has one item, deliveries=1, delivery carries both packages, payments=1\`.

The warehouse split the order into two packages but consolidated them into one delivery. This may be an intentional packing or inventory decision and can create a freight-consolidation opportunity. Risks include missed package scans, partial warehouse completion being mistaken for shipment completion, and poor visibility into which item was delayed.

A traditional flattened Order trace may show two \`Pack\` events and one \`Dispatch\`, but it loses the package/item partition and the fact that one delivery carries both packages. The cluster is stable if the two package links and consolidated delivery link are explicit. It is unstable if a repair procedure merges packages merely because they share an Order or invents separate deliveries from package count.

### S3 — Split deliveries with partial payment: X4

Signature: \`packages=2 one-item packages, deliveries=2 one-package deliveries, payments=2, first partial and second completing\`.

This is a genuinely split fulfillment: each package travels in its own delivery, while the invoice is settled in installments. It offers incremental fulfillment and cash-collection visibility, but creates reconciliation, customer-notification, tax, and completion-state risks. A completion rule based only on the existence of one payment or one dispatch will be wrong.

A flattened Order event log can retain the count of \`Dispatch\` and \`Record Payment\` events, but usually loses delivery-to-package allocation and the partial/completing distinction. The cluster is stable when payment qualifiers or amounts are reliable. If payment state is reconstructed from amounts, it can change when tolerances, reversals, or missing payment allocations are repaired.

### S4 — Cross-order logistics sharing: X5

Signature: \`external Order and external Item participate in one package and delivery; invoice bills only the local Order\`.

The logistics execution is not isolated: a package for O5 contains an item belonging to another Order, and the external Order is also present in the logistics events. This may be intentional consolidation or a warehouse pooling operation, but it creates ownership, inventory attribution, privacy, chargeback, and fulfillment-authority risks.

A traditional Order trace is almost identical to S1 and therefore represents the sharing badly. The cluster is stable only if external flags and cross-order O2O edges are trustworthy. If an ETL repair strips the \`EXT\` markers or replaces them with local surrogates, X5 will incorrectly move into S1.

### S5 — Cross-order financial sharing: X6

Signature: \`local logistics; one invoice bills local and external Orders; one payment settles the invoice without an Order allocation\`.

This is a shared financial object rather than shared logistics. Consolidated billing may be an opportunity, but the missing order-level allocation is a material risk for tax, credit, refunds, dispute handling, and revenue recognition.

Flattening to one trace per local Order makes this look like S1 and normally has no place to represent the external bill-to party or the allocation gap. The cluster is stable if the invoice's external Order relation is explicit. It is not stable under a repair that assigns the invoice to one Order by default or infers a payment allocation that is not present.

### S6 — Qualified replacement: X7

Signature: \`baseline counts plus I71 removed before dispatch and I72 replacing it; the dispatch still points to P71 and I72\`.

The business behavior is substitution or removal-and-replacement, not an ordinary two-item shipment. The opportunity is controlled substitution with customer approval; the risks are wrong-item delivery, warranty/serial-number breaks, inventory leakage, and noncompliance when the original item must be traceable.

Activity-only flattening represents it poorly because it produces the same activity word as S1. Even an unqualified graph may miss the intended lineage if the extra \`Item\` incidence on \`Dispatch\` is treated as noise. The cluster is stable when the qualifier and item lineage are captured. It is fragile if qualifiers are dropped or if a repair rewrites the package membership to contain only the final item without retaining the replacement fact.

### S7 — Return and repack: X8

Signature: \`initial package/delivery; item return and inspection; second package/delivery for the returned item; P82 replaces P81 for I82; one invoice/payment\`.

This is a reverse-logistics and re-shipment motif. It may recover a customer relationship or correct a damaged shipment, but it carries costs and risks of duplicate shipment, inventory state errors, duplicate credit/invoice handling, and loss of chain of custody.

A flat trace can show that a return occurred, but it does not reliably show which item returned, which package was replaced, or that P82 is a repack after inspection. The cluster is stable when the return and package lineage are explicit. It is less stable when return is inferred only from a later \`Pack\` event or when timestamps are repaired so that the repack appears before the return.

## 5. Borderline cases

- **X1 versus X2.** Activity-sequence equivalence groups them, and typed graph isomorphism also groups them: the first and second \`Add Item\` events have the same label, so a valid object bijection can map their items in either identifier order. Literal-identifier equality, or an exact PM4Py key containing raw IDs, separates them. This is a case where execution identity is too fine for template equivalence.

- **X1 versus X5.** Activity-sequence equivalence groups them because their activity words are identical. A logistics-only semantic projection that counts only local objects also groups them. Typed structural equivalence with external flags, or business semantics that preserves cross-order package membership, separates them. The disagreement is whether external sharing is an operational exception or irrelevant context.

- **X1 versus X6.** Activity equivalence and a semantic projection restricted to logistics group them. A typed structure that includes all event participants separates them, and a financial-semantic relation necessarily separates them because V61 bills two Orders and the payment is not allocated at Order level. The difference is invisible if invoice scope is omitted.

- **X1 versus X7.** Activity equivalence groups them. A relation that ignores qualifiers and treats the extra \`Item\` on \`Dispatch\` as an annotation may also group them. A relation preserving qualified item lineage separates them: I71 was removed and I72 replaced it. A strict typed incidence relation separates them even before qualifiers because the Dispatch E2O incidence differs.

- **X3 versus X4.** A package-partition-only relation can group them: both have two one-item packages. An order-sensitive relation separates them because X3 packs both packages before one consolidated dispatch, whereas X4 dispatches two packages separately; payment multiplicity and partial/completing state also differ. Thus “two packages” is not enough to define split-fulfillment equivalence.

- **X4 versus X8.** A coarse count relation that sees two package events and two dispatch events can group them, especially if it ignores activity names for return/inspection and ignores payment multiplicity. A lifecycle-semantic relation separates them: X4 is two forward deliveries with two payments, while X8 is a return, inspection, and repack of one already dispatched item, followed by a second delivery and one payment.

## 6. Relation to \`pm4py.cluster_equivalent_ocel\`

\`pm4py.cluster_equivalent_ocel\` is useful as an exact lead-object clustering primitive, but its key should not be confused with typed graph isomorphism. Conceptually, for each lead object it builds an ordered tuple of event contributions of the form

\`\`\`python
(
    event_activity,
    per_selected_object_type_tuple_of_related_object_ids,
)
\`\`\`

The per-type tuples are the event's selected OCEL object map, and repeated events produce repeated contributions. The lead object's related event sequence is therefore preserved; the activity labels, their repetition and order, the selected object types, the related object membership/identifiers, and the per-event object multiplicities/co-occurrences are preserved. The exact tuple nesting may vary with the OCEL version, but the comparison payload is the activity plus the selected typed object map in event order.

The key does not canonicalize object identifiers. It does not, by itself, encode the business meaning of an \`EXT\` prefix, O2O qualifiers, replacement lineage, partial versus completing payment, event attributes, amounts, or absolute time gaps. It also only sees object types included through \`object_types\`; omitted types cannot affect equality. Object-to-object relations that are not represented by event co-occurrence are not reconstructed by this key.

Raw identifiers make exact clusters too fine because an otherwise identical execution with O1/I11/P11 and one with O2/I21/P21 produce different key entries. If the lead identifier is included in the serialized event map, it is an additional source of this problem. Consequently, X1 and X2 can be separated by a literal-key comparison even though they are equivalent under type-preserving renaming. External objects can make the key even more specific, while an external object represented only as a string does not automatically acquire an external semantic flag.

I would use PM4Py to obtain the initial lead-Order grouping, then recompute an identifier-invariant signature for every Order and group by that signature. The post-processing should not blindly merge raw clusters; it should verify that all objects in the proposed merged group have the same canonical typed incidence, external flags, and qualifiers. A practical outline is:

\`\`\`python
from collections import defaultdict
import pm4py

lead_type = "Order"
selected_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

# The returned mapping is conceptually {raw_key: [lead_order_ids]}.
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    lead_obj_type=lead_type,
    object_types=selected_types,
    max_objs=20,
)

# Adapt this small adapter to the OCEL column names in use. It extracts
# one lead-Order component in the record format used by canonical_signature.
def execution_record_for_order(ocel, order_id, selected_types):
    # 1. collect events containing (lead_type, order_id);
    # 2. collect all selected objects on those events;
    # 3. add explicit O2O neighbors and their external flags;
    # 4. retain event order and O2O qualifiers;
    # 5. return {"lead_type": "Order", "objects": ..., "events": ..., "o2o": ...}.
    raise NotImplementedError  # adapter is data-schema specific

semantic_clusters = defaultdict(list)
for raw_key, order_ids in raw_clusters.items():
    for order_id in order_ids:
        record = execution_record_for_order(
            ocel, order_id, selected_types
        )
        sig = canonical_signature(record)  # custom ID-invariant step
        semantic_clusters[sig].append(order_id)

# semantic_clusters now merges raw PM4Py groups only when the stronger
# business-aware canonical signatures agree.
\`\`\`

For production use, the adapter can first construct a typed event/object graph and then use a graph-canonicalization library rather than factorial permutation enumeration. If exact identifier-level evidence is needed, I retain the raw PM4Py key and the original Order IDs alongside the canonical cluster.

Exact equivalence is preferable when the question is whether two recorded executions are byte-for-byte or schema-for-schema replicas, when a compliance control requires the exact participating objects, or when investigating one concrete case. A coarser canonical business cluster is preferable for cross-case segmentation, because literal IDs are incidental to the business pattern.

\`max_objs\` is a practical guard against very large event object maps and combinatorial keys. It can exclude, truncate, or otherwise limit comparable structure depending on the PM4Py version and the code path, so it must be treated as a possible source of information loss rather than as a semantic rule. A large connected execution—especially one with shared objects linking many Orders—can produce long keys, slow comparisons, and clusters dominated by a hub object. I would filter to relevant types, split at a justified lead-Order component boundary, record any cap-induced loss, and avoid claiming equivalence when the cap hides a distinguishing object.

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** S1, S2, S4, and S5 are unchanged because the supplied distinguishing facts are unqualified structure or external incidence. X4 loses \`partially_settles\` versus \`completes_settlement\` and becomes merely “two payments against one invoice.” X7 loses its explicit replacement/removal semantics; it remains distinct under a signature that still preserves its extra Dispatch-to-Item incidence, but can collapse toward S1 if that incidence is treated as a noisy annotation. X8 loses the explicit package-replacement qualifier, although its Return/Inspect events and second package/delivery still distinguish it. This perturbation turns important business exceptions into structural look-alikes.

- **Ignore external objects.** Removing external objects and their incidences makes X5's local projection equal to X1 and makes X6's local financial projection equal to X1. Thus S4 and S5 collapse into S1. The logistics and financial sharing risks disappear from the representation, not from the business process. X1/X2 and X3/X4/X7/X8 are otherwise unchanged by this perturbation.

- **Collapse repeated same-label events.** At the activity level, X1, X2, X5, X6, and X7 already share the same word; collapsing repetitions also brings X3 and X4 closer because their repeated \`Pack\`/\`Dispatch\` events are no longer fully visible. If all repeated labels are collapsed to one occurrence, X1 through X7 have nearly the same activity set, while X8 still retains \`Return Item\` and \`Inspect Return\`. A semantic signature that still retains object counts can keep S2, S3, and S7 separate, but a signature that also collapses multiplicities will merge single- and split-package behavior. This is why repeated events are structural information, not cosmetic noise.

- **Treat Pack and Dispatch order as a partial order.** X4 becomes invariant to the arbitrary ordering of the two independent package/delivery branches; reversing the P41/P42 branch order should not form a new cluster. X3 remains distinct because one delivery carries both packages, and X8 remains distinct if the return-to-inspection-to-repack precedence is retained. If all event order is discarded and only a multiset is kept, many “which package was dispatched first” root-cause questions become unanswerable, although the delivery and payment multiplicities still distinguish X3 from X4.

- **Treat payment multiplicity as an amount attribute.** X4's two \`Record Payment\` events can be represented as one aggregate payment amount, so it may merge with a one-payment split-delivery execution under a payment-count-insensitive relation. It should not merge with S1 if delivery multiplicity and package-to-delivery allocation remain in the signature. The partial/completing distinction then depends on amounts, tolerances, reversals, and allocation data; missing or repaired amounts can change the cluster even when the raw event count did not change.

## 8. Limitations and recommendation

No equivalence relation is universally correct. Activity sequences are robust to identifier noise but over-collapse cases that differ in ownership, lineage, or financial scope. Typed isomorphism is reproducible and explanatory but remains brittle when a harmless schema detail creates an extra incidence. Business semantics depends on a maintained vocabulary for qualifiers and on reliable repair rules for missing O2O links, external flags, concurrency, and payment state.

My recommendations are:

- **Compliance monitoring:** use a qualifier-aware, typed canonical graph with exact event order or explicit causal partial order. Keep the raw identifiers and source evidence attached for audit; use the canonical signature only to group comparable cases. Do not discard external objects, payment allocation, replacement lineage, or return/repack relations.

- **Operational segmentation:** use the preferred business-semantic signature, usually with a controlled coarsening. Ignore literal IDs and harmless same-time ordering, but retain object multiplicities, package/delivery partitions, external sharing, and lifecycle motifs. The S1-S7 partition is a useful starting segmentation for these eight executions.

- **Root-cause analysis:** use typed structure plus qualifiers and retain the concrete object IDs in the case view. Canonical clustering can find comparable cases, but diagnosis needs the exact item, package, delivery, invoice, and payment lineage, including the order in which events and repairs occurred.
