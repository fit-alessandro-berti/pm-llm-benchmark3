## 1. Control-Objective Decomposition

FEP-1 is not merely an activity-counting rule. It protects several related objectives across three temporal boundaries:

1. **Authorization boundary:** before `Release_Payment`.
2. **Loss boundary:** before irrevocable `Bank_Settlement`.
3. **Recovery boundary:** while recall or recovery remains realistically available.

A control may therefore prevent an unauthorized release, prevent financial loss after a release has occurred, detect a defect, or support recovery. Those effects are not equivalent. The controls and case facts below are taken from the supplied scenario. 

| Objective or threat scenario                                                                                                                          | AV-2                                                                                                                       | MG-4                                                                                                                                                               | RA-7                                                                                                                      | ED-1                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Prevent one person from initiating and authorizing the payment end-to-end**                                                                      | Partially preventive. It can stop enumerated errors, but it does not create an independent human decision.                 | Preventive if an independent manager acts before release. Hybrid if after release but before stoppable settlement. Detective after settlement.                     | Detective; corrective only while recall or recovery is realistic. It does not prevent initial self-authorization.         | A conditional alternative control package. It does not eliminate the objective; it substitutes a documented emergency pathway containing automated, managerial, and audit checks. |
| **2. Detect duplicate invoices, sanctions issues, account-ownership problems, recent bank changes, operator-limit breaches, and basic PO mismatches** | Strongly preventive for these specified tests when fully operational and not overridden. A warning is weaker than a block. | Can prevent or detect the issue if the manager actually examines the relevant material.                                                                            | Can detect missed or overridden issues. It may support recall if timely.                                                  | Requires a full AV-2 pass without override and excludes recent bank changes.                                                                                                      |
| **3. Establish that goods or services were received and that the payment is commercially reasonable**                                                 | Does not address this objective. A clean pass is not evidence of receipt or commercial substance.                          | Potentially strong if the manager reviews the invoice, receipt or service report, bank details, and commercial context. Rubber-stamping provides little assurance. | Can detect fabricated or missing evidence, although detection may be too late for recovery.                               | Relies mainly on a substantive MG-4 review; the AV-2 requirement alone does not cover this threat.                                                                                |
| **4. Prevent misuse of override credentials or deliberate suppression of warnings**                                                                   | A hard block is preventive. A warning can be defeated, especially if override credentials are shared or compromised.       | Useful only when the manager is genuinely independent and the override identity is authenticated. Later ratification does not cure credential misuse.              | Can detect unusual override patterns, credential sharing, or unsupported rationales. Recovery depends on timing.          | Overrides are not permitted: AV-2 must pass cleanly. Consequently, an override is a hard exception failure.                                                                       |
| **5. Resist collusion, conflicted review, and routine rubber-stamping**                                                                               | Limits some rule-based fraud but does not detect collusion, fabricated commercial evidence, or who controls an account.    | Fails if the manager is conflicted, participates in the scheme, or merely ratifies.                                                                                | An organizationally independent audit can detect pair concentration, fabricated evidence, and suspicious review behavior. | Still vulnerable to collusion. | **7. After that, recovery is uncertain.                       | Requires both pre-settlement manager action and timely audit, thereby combining preventive and recovery layers.                                                                   |
| **8. Preserve reliable human identity and accountability**                                                                                            | Does not establish who controlled a compromised account or shared service identity.                                        | Helps only if manager identity, credentials, level, and conflict status are trustworthy.                                                                           | Can investigate device, session, MFA, and credential evidence, if those records exist.                                    | Does not make a shared account an independent human actor. Identity assurance remains a prerequisite.                                                                             |
| **9. Detect account-redirection fraud around vendor-master changes**                                                                                  | Strong where ownership and recent-change checks run and cannot be overridden.                                              | Can independently reverify the bank change and supporting authority.                                                                                               | May detect redirection, but often too late after settlement.                                                              | Prohibits emergency single-operator processing when a bank change occurred during the previous seven days.                                                                        |

The most important limitation is **threat coverage**: AV-2 is strong within its defined tests but cannot compensate for every threat that human separation is intended to address. Conversely, a genuine independent manager who examines commercial evidence can cover matters that AV-2 cannot.

## 2. Equivalence and Sufficiency Test

A compensating package should be assessed as a vector of control properties rather than by asking whether “some control occurred.”

| Dimension                | Sufficiency question                                                                                                                                        | Typical downgrade                                                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Timing**               | Did an independent control act before release, or at least before an enforceably stoppable settlement? Was audit completed while recall remained available? | Manager action after settlement is detective, not preventive. Audit outside the recovery window contributes little corrective capacity. |
| **Independence**         | Was the reviewer a different authenticated human, L3 or above, outside the preparer/releaser chain and free of unresolved conflicts?                        | Shared credentials, shared accounts, supervisor pressure, family relationships, or unexamined pair concentration weaken independence.   |
| **Coverage**             | Together, did the controls cover the material causal paths: data error, bank redirection, unsupported purchase, fraud, and exception abuse?                 | AV-2 alone cannot establish receipt, commercial reasonableness, or absence of collusion.                                                |
| **Overrideability**      | Could the operator suppress, override, or bypass the control? Was any override separately authenticated and justified?                                      | A warning overridden by the same operator provides little preventive assurance. ED-1 specifically requires no override.                 |
| **Recoverability**       | If prevention failed, could the transaction still be stopped, recalled, or recovered?                                                                       | Detection after the normal 24-hour recall opportunity is primarily forensic.                                                            |
| **Evidence quality**     | Is there evidence of what was reviewed, by whom, when, using which credentials and data?                                                                    | A bare `Manager_Ratify` event does not prove review of invoice, bank account, and receipt.                                              |
| **Collusion resistance** | Would the package still work if the preparer and nominal reviewer cooperated, routinely paired, or shared a workstation?                                    | Fixed pairs, shared devices, credential sharing, and rubber-stamping reduce the incremental assurance of nominal separation.            |
| **Risk proportionality** | Is the remaining uncovered threat acceptable given bank-change recency, vendor maturity, reversibility, commercial evidence, and exposure?                  | High-value, recent-bank-change, new-vendor, or control-outage cases require stronger evidence. Amount alone is never decisive.          |

**Fully equivalent:** The package closes the material threat paths before the loss boundary, uses a genuinely independent reviewer, is not operator-overridable, has credible evidence, preserves recovery capacity, and resists plausible collusion. For same-user processing, all ED-1 conditions must be satisfied. This normally supports `OBJECTIVE_MET`.

**Partially equivalent:** Most material risks are controlled, but one nontrivial deficiency remains—for example, manager action occurs only after release, audit narrowly misses the recall window, or an administrative eligibility fact is unverified. This supports `OBJECTIVE_PARTIALLY_MET` only where the remaining exposure is bounded and remediation is required.

**Merely mitigating:** A control reduces a subset of risks but leaves the original self-authorization or principal fraud mechanism operative. A clean AV-2 pass without an independent review is a common example. Depending on the remaining exposure, the final classification may be partial or failed.

**Ineffective:** Controls were unavailable, overridden, non-independent, unsupported, or too late to influence settlement or recovery. This normally supports `OBJECTIVE_FAILED`.

“Same expected loss” is not the only valid equivalence standard because:

* Equal averages can hide radically different catastrophic tail risks.
* Segregation creates deterrence, accountability, and evidence, not only loss reduction.
* A repeatable exception can create a scalable attack path even when one observed payment was harmless.
* Expected-loss estimates are highly uncertain for collusion, credential compromise, and rare fraud.
* Mandatory eligibility conditions may be governance constraints rather than variables that can be traded away for a low estimated loss.
* A control that happens to produce the correct outcome once may still be structurally ineffective.

## 4. Preventive–Detective–Corrective Comparison

| Control                                      | Primary character                               | Preventive contribution                                                                 | Detective contribution                                                      | Corrective contribution                                                               | Principal limitations                                                                                                                                           |
| -------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AV-2**                                     | Preventive automated control                    | Blocks or warns on its six specified tests before release                               | Warnings and decision logs expose risk indicators and overrides             | Normally none after release, except information supporting later recall               | Limited coverage; warnings are overrideable; does not validate receipt, commercial reasonableness, collusion, or actual account controller                      |
| **MG-4 before release**                      | Preventive human authorization                  | Prevents the operator from completing release without independent challenge             | Also detects errors or suspicious evidence during review                    | Not normally needed if the payment is stopped                                         | Independence, manager level, review substance, and credential integrity must be proven                                                                          |
| **MG-4 after release but before settlement** | **Hybrid**                                      | Preventive relative to financial loss if settlement is held and the manager can stop it | Detective relative to the already completed release and any FEP-1 deviation | Corrective insofar as it cancels or reverses a queued instruction before settlement   | Weaker than pre-release approval; the self-authorization already occurred, evidence may be influenced by ratification bias, and stop authority may be uncertain |
| **MG-4 after settlement**                    | Detective                                       | No ordinary preventive effect                                                           | Can identify error, fraud, or policy failure                                | Only exceptional recovery, legal action, or remediation                               | Does not retroactively authorize the payment or restore segregation                                                                                             |
| **RA-7**                                     | Detective with conditional corrective effect    | No direct prevention of the original release                                            | Detects defects, exception misuse, repeated patterns, and review failures   | Partly corrective when audit occurs while stop, recall, or recovery remains available | A late audit may be only forensic; audit quality and independence matter                                                                                        |
| **ED-1**                                     | Conditional permission and control architecture | Forces a package of eligibility, automated, managerial, and timing safeguards           | Requires 100% retrospective audit                                           | Preserves recall opportunity through timely audit                                     | Not a standalone activity; failure of any mandatory condition invalidates the permission                                                                        |

The classification of post-release, pre-settlement manager action depends on the observation boundary:

* Relative to **`Release_Payment`**, it is detective and potentially corrective because the prohibited or risky release has already occurred.
* Relative to **irreversible financial loss**, it is preventive if the instruction is genuinely held and the manager can stop settlement.
* It is therefore best described as **hybrid**, not simply preventive. It can make a package substantively strong at the loss boundary, as in AP-207, without erasing the nominal release-level deviation.

## 6. Evidence and Monitoring Recommendations

**Evidence collection**

| Evidence                                   | Required content                                                                                                                                | Purpose                                                                         |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Human identity and access**              | Named human behind every account; MFA event; credential owner; session ID; device and workstation; concurrent sessions; privileged override use | Distinguish real human separation from shared credentials or account compromise |
| **Manager qualification and independence** | Manager level, reporting line, conflict declarations, relationship to vendor and operator, override authority                                   | Establish MG-4 eligibility rather than inferring it from an activity label      |
| **Review substance**                       | Invoice, bank data, receipt/service report, PO, review fields opened, attestation, review duration, comments, and decision                      | Distinguish substantive review from rubber-stamping                             |
| **AV-2 execution evidence**                | Service version, status of each subcheck, input data, block/warning result, override identity and rationale, outage start/end                   | Establish actual coverage and detect degraded controls                          |
| **Emergency-token evidence**               | Issuance, activation and expiry timestamps; issuer; reason; linked incident; authoritative clock; ingestion delay                               | Resolve cases such as AP-206 and detect backdating                              |
| **Vendor-master history**                  | Exact creation date, bank-change timestamp, changer, approver, previous account, ownership-verification evidence                                | Assess vendor age and bank-change proximity                                     |
| **Settlement and recovery**                | Queue status, settlement timestamp, hold/cancel authority, recall request, bank response, recovery outcome                                      | Determine whether post-release controls were genuinely preventive or corrective |
| **Pair and organizational design**         | Team structure, designated payment cells, rotation policy, pair frequencies, supervisory review                                                 | Distinguish legitimate specialization from uncontrolled pair concentration      |
| **Audit workpapers**                       | Audit start and completion, procedures performed, evidence reviewed, findings, recall decision                                                  | Establish RA-7 quality, not just occurrence                                     |

**Monitoring rules**

| Metric                         | Definition and segmentation                                                                                                                         | Recommended treatment                                                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Same-user rate**             | Completed cases where preparer and releaser resource sets intersect ÷ completed payments. Segment valid ED-1, invalid ED-1, and no emergency token. | Any same-user completed payment without a provisionally valid ED-1 package should generate an immediate high-priority review. Track both case count and value.   |
| **Override rate**              | AV warnings overridden ÷ AV warnings, by operator, credential owner, manager, bank-change status, and amount band                                   | Hard alert when the operator uses another person’s credential, when bank change is recent, or when override concentration rises.                                 |
| **Late manager approval**      | Categorize manager action as before release, after release/before settlement, after settlement, or settlement unknown                               | Treat after-settlement actions as critical exceptions. Report post-release/pre-settlement actions separately rather than presenting them as normal pre-approval. |
| **Audit before recall window** | Same-user emergency releases audited within 24 hours ÷ all such releases                                                                            | Target 100%. Also calculate the formal “one business day” measure using the applicable business calendar; do not conflate the two.                               |
| **Repeated resource pairs**    | Directed preparer→releaser pair frequency, pair share, duration of repeated pairing, and concentration relative to team size                        | Alert on unusual concentration, especially when coupled with defects, overrides, or shared workstations. High concentration alone is not proof of collusion.     |
| **Shared workstations**        | Cases where preparer and releaser use the same device/session, overlap in time, or show implausible credential switching                            | Escalate same-session or impossible-travel patterns. A shared workstation alone may reflect a legitimate payment cell.                                           |
| **Bank-change proximity**      | Hours from vendor-bank change to prepare and release, with bands of 0–24h, 1–7d, and over 7d                                                        | Prohibit ED-1 within seven days. Require independent ownership verification for all very recent changes.                                                         |
| **Control outages**            | Releases during AV unavailability or degraded mode ÷ releases; duration and affected value                                                          | ED-1 releases during AV outage should be zero. Freeze or route affected cases to enhanced independent review.                                                    |
| **Token-timing anomalies**     | Token activation after prepare, token issued immediately before release, expired token, or log-clock disagreement                                   | Preserve source logs and investigate before drawing a misconduct conclusion.                                                                                     |
| **Audit finding recurrence**   | Repeat defects by resource, pair, workstation, vendor, control version, or manager                                                                  | Use recurrence to prioritize investigation; avoid treating one correlated pattern as causal proof.                                                               |

An alert is **evidence of elevated uncertainty**, not proof of misconduct. The u12/u13 pair may be a legitimate dedicated two-person cell; a shared workstation may be operationally normal; a recent bank change may be genuine; and an override may occasionally be justified. A misconduct finding requires identity evidence, review records, vendor relationships, credential telemetry, and an opportunity for the relevant people to explain the pattern.

def tri_bool(value):
    """Return True, False, or None for missing evidence."""

def preliminary_ed1_evidence(row: pd.Series) -> str:
    """
    Assess only documented ED-1 eligibility evidence.

    This is not an objective-level or final compliance verdict.
    """
    if (
        not bool(row["completed_release"])
        or not bool(row["nominal_four_eyes_violation"])

    uncertainties: list[str] = []

    token_active = tri_bool(row["emergency_token_active"])
    token_before = tri_bool(row["token_before_prepare"])
    token_uncertain = tri_bool(row["token_timing_uncertain"])

    if token_active is False:
        failures.append("NO_ACTIVE_TOKEN")
    elif token_active is None:
        uncertainties.append("TOKEN_STATUS_UNKNOWN")
    elif token_before is False:
        failures.append("TOKEN_NOT_BEFORE_PREP")
        if token_uncertain is True:
            uncertainties.append("TOKEN_TIMESTAMP_MAY_BE_DELAYED")
    elif token_before is None:
        uncertainties.append("TOKEN_PREP_ORDER_UNKNOWN")

    if row["amount_eur"] >= 100_000:
        failures.append("AMOUNT_NOT_BELOW_100K")

    vendor_old_enough = tri_bool(row["vendor_ge_180d"])
    if vendor_old_enough is False:
        failures.append("VENDOR_LT_180D")
    elif vendor_old_enough is None:
        uncertainties.append("VENDOR_AGE_NOT_ESTABLISHED")

    recent_bank_change = tri_bool(
        row["bank_change_within_7d"]
    )
    if recent_bank_change is True:
        failures.append("BANK_CHANGE_WITHIN_7D")
    elif recent_bank_change is None:
        uncertainties.append("BANK_CHANGE_STATUS_UNKNOWN")

    if not bool(row["av_pass_no_override"]):
        failures.append("AV_NOT_FULL_PASS_NO_OVERRIDE")

    timing = row["manager_timing_flag"]
    if timing in {
        "BEFORE_RELEASE",
        "AFTER_RELEASE_BEFORE_SETTLEMENT",
    }:
        pass
    elif timing == "AFTER_SETTLEMENT":
        failures.append("MANAGER_AFTER_SETTLEMENT")
    elif timing == "AFTER_RELEASE_SETTLEMENT_UNKNOWN":
        uncertainties.append(
            "MANAGER_BEFORE_SETTLEMENT_NOT_ESTABLISHED"
        )
    else:
        failures.append("NO_MANAGER_APPROVAL_BEFORE_SETTLEMENT")

    if row["manager_independence"] != "YES":
        failures.append("MANAGER_INDEPENDENCE_NOT_ESTABLISHED")

    audit_in_window = tri_bool(
        row["audit_before_24h_recall_proxy"]
    )
    if audit_in_window is not True:
        failures.append("AUDIT_NOT_WITHIN_24H_PROXY")

    manager_level = row["manager_level_l3_verified"]
    if manager_level == "NO":
        failures.append("MANAGER_BELOW_L3")
    elif manager_level != "YES":
        uncertainties.append("MANAGER_L3_LEVEL_UNVERIFIED")

    if failures:
        result = "PRELIMINARY_FAIL=" + ",".join(failures)
        if uncertainties:
            result += "; UNCERTAINTY=" + ",".join(uncertainties)
        return result

    if uncertainties:
        return (
            "PROVISIONAL_PASS_PENDING="
            + ",".join(uncertainties)
        )

    return "PRELIMINARY_PASS"

In the current PM4Py release source, `filter_four_eyes_principle` exposes `keep_violations=False` by default, meaning the default call filters violations out rather than retaining them; the code therefore explicitly sets `keep_violations=True` and contains a compatibility check for older versions. 

The underlying rule compares the set of resources performing the first activity with the set performing the second and treats a nonempty intersection as a violation. It only evaluates cases containing both activities. Consequently, it does not detect AP-205 as a completed-payment violation, does not establish whether two usernames represent independent humans, and does not evaluate timing, collusion, manager quality, AV coverage, settlement, or recoverability. Those remain separate evidential judgments. ([github.com][1])
