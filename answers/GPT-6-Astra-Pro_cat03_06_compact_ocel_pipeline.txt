## 1. Modeling assumptions

**I use one OCEL with explicit narrative relations plus narrowly scoped analytical relations.** The analytical relations support useful Order, Item, and Package lifecycles, but remain distinguishable from relationships explicitly stated for individual events.

**Object types.** The exact, case-sensitive type names are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Object identifiers are globally unique across these types.

**E2O qualifiers.** Qualifiers describe an object’s role in an event; separate provenance columns explain whether the link was stated or derived.

| Object type | E2O qualifier vocabulary                                                                                                                                                    |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order       | `created_order`, `closed_order`, `owning_order` for item addition, `affected_order` for logistics, `billed_order` for invoice issuance, `billed_order_context` for payments |
| Item        | `added_item`, `reserved_item`, `packed_item`, `shipment_item`                                                                                                               |
| Package     | `packed_package`, `shipment_package`                                                                                                                                        |
| Delivery    | `dispatched_delivery`, `confirmed_delivery`                                                                                                                                 |
| Invoice     | `issued_invoice`, `credited_invoice`                                                                                                                                        |
| Payment     | `recorded_payment`                                                                                                                                                          |

**O2O direction.** `ocel:oid` is the subject and `ocel:oid_2` is the target: Order **contains** Item; Package **packs** Item; Delivery **carries** Package; Invoice **bills** Order; Payment **partially_settles** Invoice. Inverse rows are not duplicated. Both Payments use `partially_settles` because each is an installment; this does not deny that they cumulatively settle V1.

**Downstream participation policy.**

* Logistics events receive explicit E2O rows for the affected Packages, Items, and Orders. Where these links are not stated in the event description, they are derived through the appropriate O2O paths.
* Invoice issuance relates to V1 and both Orders. Each payment relates to its Payment object, V1, and both Orders as **invoice-level context, not monetary allocation**. Financial events do not relate to Items, Packages, or Deliveries.
* Propagation is activity-specific, not unrestricted graph traversal. In particular, P2/D2 events never reach O200, and future Deliveries or Payments are not attached retrospectively to earlier events.

The stated O2O memberships are assumed to remain valid when used; no repacking, reassignment, additional stock reservation, or invoice-close event is invented.

**Provenance.** `relations_source` retains the explicit narrative links; `relations_derived` retains analytical additions. The combined `relations` includes `relation_origin` and `derivation_rule`. The flattened views also retain this lineage. These are application-level audit columns, not a claim that every OCEL serializer standardizes them. Discovery runs on the deliberately enriched view; provenance does not automatically make discovery algorithms discount derived links.

**Version assumptions.** The pipeline assumes the requested high-level PM4Py functions and the documented OCEL constructor. The constructor is isolated in `make_ocel`. For a version with a different constructor, adjust that adapter while preserving all four tables—including O2O—rather than dropping unsupported data. The code also checks for missing discovery functions and preserves their native return values instead of assuming every model is a conventional Petri-net triple. ([GitHub][1])

## 4. Expected flattened behavior

PM4Py flattening selects objects of one type as cases and includes their E2O-related events. Its implementation joins through E2O relations; it does not automatically traverse the O2O table. It also retains event identifiers, allowing copies to be traced back to the original events. ([GitHub][2])

| Flattening | Cases | Rows | Distinct original events | Additional copies |
| ---------- | ----: | ---: | -----------------------: | ----------------: |
| Order      |     2 |   24 |                       17 |                 7 |
| Package    |     2 |    6 |                        6 |                 0 |
| Delivery   |     2 |    4 |                        4 |                 0 |
| Invoice    |     1 |    3 |                        3 |                 0 |

**Order.**

O100’s 14-event trace is:

Create Order → Add Item ×2 → Reserve Stock → Pack Package ×2 → Dispatch Package ×2 → Issue Invoice → Record Payment → Confirm Delivery ×2 → Record Payment → Close Order.

O200’s 10-event trace is:

Create Order → Add Item → Reserve Stock → Pack Package → Dispatch Package → Issue Invoice → Record Payment → Confirm Delivery → Record Payment → Close Order.

The seven shared events are `e06`, `e07`, `e09`, `e11`, `e12`, `e13`, and `e15`. Each appears once in each Order trace, without becoming a second event in the OCEL.

The DFG contains the adjacent activity pairs in these sequences. All non-self edges have frequency two. The self-loops on Add Item, Pack Package, Dispatch Package, and Confirm Delivery each have frequency one, caused by O100’s multiple related objects.

Particularly misleading are the edges Record Payment → Confirm Delivery and Confirm Delivery → Record Payment. They reflect the observed interleaving of financial and logistical events, not proof that delivery confirmation causes another payment.

The flattening covers all 17 events somewhere, but loses the multi-object relationship structure as a native modeling dimension. It cannot distinguish P1’s cross-Order packing from two independent shipments merely by inspecting activity labels. Summing payment amounts across these rows gives **500**, although only **250** was recorded.

**Package.**

P1 has `e07 → e09 → e13`; P2 has `e08 → e10 → e14`. Both traces are:

Pack Package → Dispatch Package → Confirm Delivery.

Both DFG edges have frequency two. No event is duplicated between Package cases because each of these events involves exactly one Package.

Order creation, stock reservation, invoicing, payments, and Order closure are omitted. P1’s two Items from different Orders collapse into one ordinary Package trace. Treating the two traces as independent end-to-end business cases would conceal their shared Order and Invoice context.

**Delivery.**

D1 has `e09 → e13`; D2 has `e10 → e14`:

Dispatch Package → Confirm Delivery.

The single DFG edge has frequency two, with no shared-event duplication between Delivery cases. Packing is omitted because the policy does not attach the future Delivery object to the earlier packing event.

This view measures a useful but narrow elapsed interval: D1 takes 3 hours from dispatch to confirmation; D2 takes 22 hours 45 minutes. Neither interval measures total Order processing time or active labor.

**Invoice.**

V1 has `e11 → e12 → e15`:

Issue Invoice → Record Payment → Record Payment.

The DFG has Issue Invoice → Record Payment with frequency one and Record Payment → Record Payment with frequency one. The repeated payment activity represents M1 and M2, not duplicate recording of a single Payment.

There is only one Invoice case, so nothing is copied between Invoice cases. Logistics and Order closure disappear. This view cannot allocate money between O100 and O200 or independently establish an invoice balance from a supplied face-value attribute, because no such attribute was provided.

**Log-skeleton interpretation.**

Log skeletons include occurrence-count, equal-count, ordering, and other declarative constraints; the pipeline uses zero noise tolerance. ([GitHub][3])

For this dataset, Package and Delivery skeletons should appear highly rigid. The Invoice skeleton should admit one issuance and two payment occurrences. Within each Order trace, Add Item, Pack Package, Dispatch Package, and Confirm Delivery have equal counts—two for O100 and one for O200.

Those are sample properties, not established business rules. In particular, “exactly two payments per Invoice” is not justified as a universal requirement by one Invoice.

**Why Payment flattening is especially weak.**

M1’s trace would contain only `e12`; M2’s only `e15`. Both are singleton Record Payment traces, so their DFG has no edges. This loses the succession of installments against V1 and any preceding invoice lifecycle. A zero observed Payment-trace duration would mean “only one event was recorded for this object,” not “payment processing took no time.”

## 5. Expected object-centric structures

**OC-DFG.** An OC-DFG combines object-type-specific directly-follows structures and supports distinct event/object counting perspectives. Those frequency meanings must be kept separate. ([GitHub][4])

The main contrast is between Order-level repetition and Package-level progression: Pack Package → Pack Package exists for Order but not for Package. Likewise, Record Payment → Record Payment exists for Invoice, whereas individual Payment objects have no directly-follows edge.

For Reserve Stock → Pack Package, `e06 → e07` is **one event pair**, but it is traversed by two Orders and two Items. An annotation of two object traversals must not be presented as two independent reservations.

The Item view also exposes that I2 has Add Item → Pack Package, whereas I1 and I3 pass through Reserve Stock. This is an absence in the supplied log—not permission to invent an I2 reservation or conclude that one was operationally required.

**OTG.** The requested OTG is not simply a visualization of the supplied O2O table. The classic implementation aggregates E2O-derived object interaction, descendants, inheritance, co-birth, and co-death graphs to the object-type level. Its frequencies count object-pair edges in those graphs, rather than repeated co-occurrence events. ([GitHub][5])

It should expose links between the logistical types and Order, and between Invoice, Payment, and Order. O100 and O200 form one interacting Order–Order pair, despite sharing seven events. P1 explains their logistical coupling; V1 explains their financial coupling.

Lifecycle-derived relationships need caution. V1 and M2 both have their last recorded event at `e15`, so a co-death relationship is expected. That means a shared **last observation**, not physical deletion or a discovered accounting rule. ([GitHub][6])

**ET–OT.** This graph is the activity/object-type incidence structure represented by the activity table in section 3. The classic implementation weights an edge by E2O row count. Thus Record Payment–Order has weight four, while Record Payment–Payment and Record Payment–Invoice each have weight two. These are neither payment amounts nor four payment events. ([GitHub][7])

It also makes the policy boundary visible: financial activities touch no Item, Package, or Delivery objects.

**Object-centric Petri net.** PM4Py’s classic discovery builds type-specific lifecycle models and derives multiplicity-related annotations from event/object participation. The resulting structure depends on the data, discovery variant, and parameters. ([GitHub][8])

The expected interpretation is that shared activities connect type-specific behavior: packing P1 involves one Package, two Items, and both O100 and O200; issuing V1 involves one Invoice and both Orders; recording M1 and M2 repeatedly involves V1 but different Payment objects.

However, **there is no uniquely warranted net topology or business interpretation**. Repeated Invoice payment behavior may be generalized beyond exactly two payments. Multiplicity annotations need not enforce “exactly two Orders per Invoice.” The discovery call does not establish a monetary balance guard such as “close only when payments sum to the invoice amount.”

Furthermore, the propagated payment-to-Order links can introduce apparent Order synchronization. That is a consequence of the chosen analytical participation policy, not independent evidence of an operational synchronization requirement.

**Object-interactions summary.** The PM4Py function emits ordered combinations of an event and two distinct related objects. Consequently, one unordered pair ordinarily appears in both directions. The pipeline retains the raw result and separately counts distinct shared events for canonical unordered pairs. ([GitHub][4])

Expected counts include:

| Unordered object pair | Shared events |
| --------------------- | ------------: |
| O100–O200             |             7 |
| O100–P1               |             3 |
| O200–P1               |             3 |
| O100–V1               |             3 |
| O200–V1               |             3 |
| M1–V1                 |             1 |
| M2–V1                 |             1 |
| M1–M2                 |             0 |

M1 and M2 share an Invoice but never participate in the same event. Also, O100 co-occurs with I3 through shared operations even though **I3 belongs only to O200**. Co-occurrence must therefore never be interpreted as `contains`.

## 6. Modeling alternatives

All these policies preserve the 17 events and the underlying business relationships; they differ in which relationships become event participation.

| Policy                                              | E2O treatment                                                                                                                                                         | Discovery consequences                                                                                                                                                                                  |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Source-minimal**                                  | Use the 34 rows in `relations_source`, including the explicitly shared Order links at reservation, P1 packing, and invoice issuance.                                  | Order traces omit dispatch, delivery confirmation, and payments. Package traces stop at dispatch. The resulting gaps reflect extraction scope, not necessarily incomplete business execution.           |
| **Instrumented operational involvement**            | An operational system could explicitly emit the same 53 participants used by this pipeline. That would require evidence beyond the supplied event sentences.          | With identical E2O membership, discovery can be identical to the enriched pipeline even though the provenance is different. Relative to source-minimal extraction, downstream lifecycles become richer. |
| **Whitelisted O2O propagation—the selected policy** | Derive the 19 additional links through activity-specific paths, retaining the 34-row narrative layer.                                                                 | Produces the traces and structures above while allowing a source-only sensitivity analysis. The discovery results describe the enriched analytical view.                                                |
| **Broader financial-context propagation**           | Additionally attach all three billed Orders’ Items to invoice issuance and both payments, using explicitly contextual qualifiers. This adds nine links, for 62 total. | Item lifecycles extend into invoicing and payments; ET–OT and interaction graphs acquire additional financial/Item links. This still supplies no Item prices or monetary allocations.                   |

A useful comparison is to rerun the pipeline with `relations_source` passed through the same constructor adapter. Differences then quantify sensitivity to relation policy, rather than differences in business-event counts.

## 7. Failure modes

| Failure mode                                 | Concrete risk here                                                                                                                         | Control or interpretation                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Relation inflation**                       | Unrestricted propagation through connected Orders, P1, and V1 could make nearly every event appear relevant to nearly every object.        | Use activity-specific paths; audit the 34/19 source-derived split and participant sets.                                                                                      |
| **Missing direct E2O links**                 | Retaining Delivery → Package in O2O alone does not give a Package trace a confirmation event under the verified flattening implementation. | Materialize intended analytical E2O links explicitly and label their provenance. ([GitHub][2])                                                                               |
| **Propagation presented as observation**     | Payment-to-Order context could be reported as a source-system association.                                                                 | Retain source and derived tables, derivation rules, and policy labels; do not assume discovery interprets provenance.                                                        |
| **Duplicate shared events after flattening** | Order flattening contains 24 rows, but only 17 original events.                                                                            | Retain `ocel:eid`; distinguish event counts, case-event counts, and object traversals. Deduplicate only for the metric that requires it.                                     |
| **Ambiguous payment allocation**             | Assigning M1 to O100 and M2 to O200—or charging both amounts to both Orders—would invent accounting facts.                                 | Keep amounts on the two original events; report 250 against V1 without an Order split.                                                                                       |
| **Overly short Payment traces**              | Singleton traces could suggest instantaneous processing or a complete Payment lifecycle.                                                   | Interpret them as observation-limited; use Invoice and interaction views for installment behavior.                                                                           |
| **Constructor/API mismatch**                 | An older installation might lack OTG/ET–OT functions or expose different model return types.                                               | Fail explicitly, isolate the constructor adapter, and retain native discovery returns. Never silently discard O2O.                                                           |
| **False ordering for timestamp ties**        | An event-ID tie-breaker could turn simultaneous or unordered events into a fictitious sequence.                                            | This example has no timestamp ties. For tied future data, use justified ordering, partial-order methods, or tie-order sensitivity analysis—not invented microsecond offsets. |
| **Co-occurrence confused with ownership**    | O100 and I3 interact, but O100 does not contain I3.                                                                                        | Use qualified O2O links for ownership; use interaction summaries only for participation.                                                                                     |
| **Temporal leakage through static O2O**      | A Delivery might be attached to stock reservation because its eventual Package is already known in the completed dataset.                  | Restrict propagation by activity and lifecycle context; do not treat static connectivity as historical participation.                                                        |
| **Overfitting or causal overinterpretation** | A skeleton may suggest exactly two payments; a DFG may suggest payment–delivery dependencies.                                              | Treat these as properties of this tiny, interdependent sample, not universal constraints or causal findings.                                                                 |

## 8. Final semantic checks

A reviewer can inspect the generated tables against these assertions:

| Assertion                                   | Expected evidence                                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Every narrative event exists exactly once.  | `events` has `e01` through `e17`, with the stated activities and UTC timestamps.                       |
| Every stated object exists exactly once.    | Twelve objects across the six exact type names; no amount objects.                                     |
| Order membership is correct.                | O100 contains I1/I2; O200 contains I3; no O100 → I3 `contains` row.                                    |
| P1 genuinely combines Orders.               | P1 packs I1/I3, while those Items have different owning Orders.                                        |
| The reservation is one shared event.        | `e06` relates to I1, I3, O100, and O200; not I2.                                                       |
| Logistics propagation is selective.         | `e09`/`e13` include D1, P1, I1, I3, O100, and O200; `e08`/`e10`/`e14` exclude O200.                    |
| The Invoice remains shared, not duplicated. | Only V1 exists; it bills both Orders, and `e11` is one issuance event.                                 |
| Payments are distinct installments.         | `e12` records M1 and 100; `e15` records M2 and 150; both reference V1.                                 |
| Denormalized E2O fields are faithful.       | Every relation’s activity, timestamp, and object type match its event and object rows.                 |
| Provenance and closure order are preserved. | Exactly 34 narrative plus 19 derived links; O200 closes at 10:30 UTC and O100 at 10:35 UTC on April 7. |

**The central invariant is that seventeen business events remain seventeen events—even when several objects participate and several analytical views contain copies.**
