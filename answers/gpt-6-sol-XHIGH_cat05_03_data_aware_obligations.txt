## 1. Temporal Data Semantics

For each case, sort events by `(time:timestamp, event_index)` and apply every nonblank attribute cell at that event. A blank cell carries forward the previous known value; it never clears a value. Before the first observed value, the state is unknown. The state at `Release_Funds` includes updates on that event and all preceding events in this order, but excludes later events. Thus the EUR 150,000 settlement amount in TX-305 is known at settlement, not at release. A final case attribute is never backfilled into earlier events.

I treat a change as material to a review when it changes an attribute used by the applicable obligation or review scope: jurisdiction, risk, or customer type, or an amount increase exceeding 20% of the amount at the latest review (and, conservatively, of the immediately preceding known amount). A decrease alone is not material under R4. A review resets its amount baseline. An increase from an unknown baseline remains unresolved unless another reliable baseline establishes the percentage. This operational definition makes review relevance explicit; it does not turn every data edit into a new duty under a rule whose release-time trigger is false.

**Event time** orders what occurred in the case; **effective time** says when a fact governed the transaction; **record time** says when it entered a database; **evidence time** says when a signature or other independent proof existed. Attribute updates are effective at their event timestamps unless reliable evidence establishes otherwise. An exemption's displayed effective date is distinct from its approval and signature evidence. A record inserted after release can corroborate prior approval, but cannot itself move approval backward. For equal timestamps within a case, `event_index` determines order: TX-311's Enhanced_Review at index 3 precedes its DE jurisdiction update at index 4. A case-local index does not establish order between different cases' simultaneous global sanctions-list events; that would require a global sequence or another trustworthy timestamp.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| R1 | Release; jurisdiction ≠ DE and amount ≥ EUR 100,000 | Completed Enhanced_Review | Latest relevant material change < review < release | Release state for trigger; review-time state and intervening changes for validity | R5-valid exemption waiving R1 | Unknown decisive amount/jurisdiction makes trigger unknown | Review completion and scope; amount/jurisdiction history; exemption proof if claimed |
| R2 | Release; risk HIGH or customer PEP | Enhanced_Review and Compliance_Approve | Relevant risk/PEP change < enhanced review < approval < release | Release risk/type and review/approval context | None stated; EX-77/88 waive only R1 | If neither limb is proven and one decisive field is unknown, trigger unknown | Risk/KYC history, review completion, approval packet and timestamps |
| R3 | Release; current jurisdiction was added to list after latest screen | New Sanctions_Screen | Previous screen < matching list addition < new screen < release | Release jurisdiction; list and screen history | None stated | Unknown jurisdiction or unorderable update/screen leaves result unresolved | List version/target, update time, screen time/result |
| R4 | Amount increases >20% after latest Standard_Review or Enhanced_Review | Fresh applicable review for any amount-dependent duty | Latest review < material increase < fresh applicable review < release | Prechange, reviewed, and release amounts | Decrease alone does not invalidate | Unknown starting amount prevents safe percentage inference | Immutable amounts, provenance, review baseline |
| R5 | Claimed exemption at an obligation trigger | Prior Head_Compliance approval within scope and validity interval | Effective-from ≤ trigger < expiry; evidenced approval ≤ trigger | Trigger-time jurisdiction, type, amount and exemption scope | Only the rule explicitly waived | Missing scope or disputed prior approval cannot silently waive | Approval identity, signature/other independent evidence, effective/expiry/record times |
| R6 | Decisive trigger attribute absent | Resolve with reliable contemporaneous evidence | Evidence must establish value at the relevant event | Event-time state, never final-state backfill | None | INDETERMINATE if the trigger cannot be proved or excluded and no separate decisive failure resolves outcome | Source payloads, audit trail, corroborated effective times |
| R7 | Every evaluation | Ordered state reconstruction | Within case `(timestamp, event_index)`; strict before/after as specified | Latest known value at each relevant event | Reliable alternative effective time | Ties lacking a trustworthy cross-system order may be indeterminate | Stable sequence, clock and source-order metadata |

Formalization, with `x ≺ y` meaning an earlier `(timestamp, event_index)` in the *same case*, and `x ≼ y` allowing equality. For a global list update and a case event, compare UTC timestamps; equal timestamps without a global order are unresolved. `S_a(c,e)` is the value from the latest nonblank update to attribute `a` with update `≼ e`; if none exists it is `?`. `E`, `A`, `Q`, `L`, and `F` denote Enhanced_Review, Compliance_Approve, Sanctions_Screen, matching sanctions-list addition, and Release_Funds. `M_1` denotes a material change relevant to R1. Three-valued predicates use `?` where evidence is insufficient.

```text
R1: T1(F) := (S_jur(F) != DE) AND (S_amount(F) >= 100000).
    If T1(F)=true, require ValidExemption(F,R1) OR
    exists E [E ≺ F AND Completed(E) AND no M_1 with E ≺ M_1 ≺ F
              AND not InvalidByR4(E,F)].
R2: T2(F) := (S_risk(F)=HIGH) OR (S_type(F)=PEP).
    If T2(F)=true, require exists E,A [E ≺ A ≺ F, Completed(E),
    A approves E's enhanced packet, and E follows the latest change
    that made the release-time HIGH/PEP condition relevant].
R3: For current jurisdiction j=S_jur(F), if a matching L_j exists
    with Q_latest ≺ L_j ≺ F, require Q_new with L_j ≺ Q_new ≺ F.
    Equivalently, the latest pre-release screen must follow that update.
R4: For latest review V, an observed amount update U after V invalidates
    V for amount-dependent duties when amount(U) > 1.20*amount(V)
    (or > 1.20*the immediately preceding known amount). A later
    applicable review resets V. If the necessary base is unknown,
    InvalidByR4 is ?, not false. A decrease does not make it true.
R5: ValidExemption(F,r) := claimed ID waives r AND approved_by=Head_Compliance
    AND effective_from <= time(F) < expires AND scope matches S(F)
    AND credible evidence establishes approval existed by time(F).
    Record time may be later than F; a displayed backdate alone is insufficient.
R6: Unknown decisive input yields an unknown trigger/validity result;
    classify INDETERMINATE unless reliable evidence resolves it or an
    independent, established deviation already decides the case.
R7: Compute every S(c,e) from updates at or before e in the stated order;
    never infer an earlier value from a later case or settlement state.
```

R4 is a review-validity rule, not an independent requirement to perform a review when no amount-dependent obligation applies. R3 presupposes an identifiable prior screen; an absent initial screen may violate another policy, but no such general screening rule was supplied here.

## 4. Ambiguities and Alternative Readings

- **TX-302:** The 11:00 insert is not itself timely approval; the independently timestamped 09:05 valid signature is. If signature verification, scope, or Head_Compliance authority failed, EX-77 would cease to justify an exception. The completed 09:20 Enhanced_Review would still support a COMPLIANT finding unless its completion or relevance were also disproved. Classifying the case COMPLIANT rather than JUSTIFIED_EXCEPTION is also defensible because the exemption is redundant to the completed review; the table records the valid exception invoked at release.
- **TX-305:** A trustworthy immutable release payload, contemporaneous amount feed, or review workpaper stating the amount would establish or exclude R1 and show whether the review covered the relevant amount. The next-day settlement figure alone cannot establish the release amount or an earlier effective time. On a strictly event-label reading, the 11:15 Enhanced_Review may suffice even if the release amount was 150,000; on an evidential reading its missing amount prevents validating review scope and any unobserved material increase. Neither reading licenses backfilling 150,000 into the release.
- **TX-310:** Independently timestamped proof that Head_Compliance actually approved EX-88 orally before 10:00, with the stated scope and effective interval, would support JUSTIFIED_EXCEPTION. Proof that no such oral approval occurred, or a rule requiring completed qualified signing before use, makes the case NONCOMPLIANT. The requester-witness account and displayed backdate are weaker than the 10:30 certificate evidence, but the later certificate does not logically disprove an earlier oral decision. A strict documentary-evidence standard can reasonably classify the current file as NONCOMPLIANT; this assessment leaves the factual oral-approval issue open.
- **TX-311:** The source order makes the enhanced review earlier than the jurisdiction update, even though both show 16:20. At release the current jurisdiction is DE, so the stated R1 trigger is false. Reversing the two indices would change which state the review saw but would not by itself change this release-time outcome. A broader policy that preserves a foreign high-value duty once activated and requires a new review after *every* later jurisdiction change would make this review stale and change the classification; that is an additional policy, not R1 as written. Evidence that the DE update was ineffective at release would activate R1, but the enhanced review already covered the then-US 115,000 state, so that fact alone would still not establish a breach.
- **TX-306 and TX-308:** Evidence that the enhanced review had not completed, or that a later amount change had a different effective amount/time, could overturn the compliant findings. Under the supplied facts, +4.55% in TX-306 and the decrease in TX-308 do not meet R4. TX-308 remains at the inclusive EUR 100,000 R1 threshold.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage:** A trace-only model cannot reconstruct that TX-311 was US before its DE update or that TX-305's later settlement amount was unknown at release. Backfilling final values changes triggers retroactively.
2. **Conditional activation:** The same `Enhanced_Review → Release_Funds` sequence can be required or optional depending on release-time amount, jurisdiction, risk and PEP state. R1's EUR 100,000 boundary also matters.
3. **Material changes after review:** TX-309 contains an Enhanced_Review, yet the later +22.88% amount increase invalidates it. A pure activity-order check would pass it.
4. **Post-hoc exemptions:** A `Record_Exemption` event after release says nothing by itself about prior approval. TX-302 has independent earlier signature evidence; TX-310 has a later certificate and a contested oral claim.
5. **Missing data:** A trace can appear well ordered while a decisive amount remains unknown, as in TX-305. Filling nulls with benign defaults would manufacture a conclusion.
6. **Same-timestamp ordering:** Timestamp-only traces may treat TX-311's review and jurisdiction update as simultaneous or reverse them; index 3 precedes index 4.
7. **Semantic event types and packet linkage:** `Standard_Review` cannot stand in for `Enhanced_Review`; TX-307's approval is explicitly of the standard packet. Activity presence alone cannot establish what an approval covered.
8. **External, global changes:** XZ's list update occurs outside the transaction's review sequence as a global control state. Screening validity depends on the list version and the screen's position relative to its addition.
9. **Different clocks and effective times:** Event, record, effective, and signature times answer different questions. A control-flow trace usually cannot tell whether a backdated field reflects an actual earlier authorization.

## 7. Recommended Logging and Control Improvements

- Persist an **immutable release payload** containing amount, currency, jurisdiction, risk, customer type, exemption ID, source versions, and a cryptographic hash. Link it to the actual payment instruction and settlement identifier.
- Record each attribute change with old/new values, actor, source, reason, provenance, **effective time**, **record time**, and correction/supersession links. Use an explicit unknown value and preserve rejected or delayed updates.
- Give every event a stable per-case sequence and a global ordering key or trustworthy high-resolution timestamp for sanctions-list and other cross-case events. Record clock source and any ordering uncertainty.
- Log review start/completion separately, review type, reviewed attribute snapshot and amount baseline, material-change assessment, reviewer, artifact hash, and rule/policy version. Link each Compliance_Approve to the exact enhanced-review packet and its snapshot.
- Store exemption scope as structured fields: waived rule, jurisdiction, customer type, currency and amount bounds, effective-from/expiry, approver identity and authority, approval decision time, signature/certificate time, database record time, evidence hash, and revocation history. Preserve evidence of oral approvals independently and contemporaneously.
- Version sanctions lists and log each jurisdiction addition with its effective and publication times. Every screening result should identify the list version, target jurisdiction, result, and completion time.
- At release, evaluate versioned R1–R5 predicates against the frozen payload. Block known failures and route unknown or disputed inputs to documented human review. Store the predicate results, evidence references, reviewer decision, and override rationale for later audit.
