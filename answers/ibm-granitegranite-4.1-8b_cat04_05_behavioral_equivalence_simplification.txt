# 1. Equivalence Notions

## Visible Trace Equivalence after Hiding ``
Two process models are *visibly equivalient* if, after removing all `` (silent) transitions, they generate exactly the same set of visible traces (sequences of observable actions). Duplicate visible labels are distinguished by their occurrence position; thus `A B A` and `A A B` are considered different.

## Bounded Visible-Language Equivalence under P3
Under view **P3**, we consider *bounded visible-language equivalence* where traces are limited to at most 12 visible events and at most three `Analyze Revision` occurrences. Two models are equivalent under P3 if their bounded visible trace sets coincide.

## Business-Relevant Equivalence under P1
Equivalence **P1** requires that every analysis revision is preceded by a `Check Revision` before any `Approve Revision` or transition to `Rework Case` or `Close Case`. `Approve Revision` is optional but must remain observable. The order of `Analyze Revision` and `Check Revision` must respect this dependency for each analysis attempt. Equivalence under P1 means that both models enforce the same operational compliance constraints.

## Abstracted Dashboard Equivalence under P2
Equivalence **P2** abstracts away silent behavior (``) and `Approve Revision`. It collapses all `Check Revision` occurrences to a single Boolean fact “a check occurred”. The model must preserve:
- Presence of at least one `Analyze Revision` and one `Check Revision`.
- Number of `Analyze Revision` occurrences and whether a `Rework Case` occurred, irrespective of interleaving.

Duplicate visible labels are collapsed; only the existence and count matter, not the exact positions.

# 2. Structural Comparison

| Feature                        | Model A                                   | Model B                                   | Semantic Consequence                                                                                     |
|--------------------------------|-------------------------------------------|-------------------------------------------|----------------------------------------------------------------------------------------------------------|
| Loop Scope                     | `*(...)` contains **both** `Check Revision` and `Approve Revision` sequentially. | `+('Check Revision', ...)` runs **in parallel** with the loop, i.e., `Check Revision` is outside the loop body. | Model A checks *before* each revision; Model B checks once *before* the first revision and remains relevant for all subsequent ones. |
| Minimum `Check Revision`      | At least one per `Analyze Revision`.      | Exactly one visible `Check Revision` regardless of number of `Analyze Revision`s.                | Model A enforces perattempt checks; Model B may skip checks for later attempts.                        |
| Maximum Placement of `Check Revision` | Immediately before the first `Analyze Revision`. | Immediately before the process starts; visible also before each `Analyze Revision` due to concurrency. | Model A's check is tightly coupled to the first analysis; Model B’s check is more global.               |
| Optional `Approve Revision`    | Executes after `Check Revision` in each iteration; may be silent. | Not present; effectively hidden by concurrency, but `Approve Revision` may be omitted or become redundant. | Model A preserves explicit approval visibility; Model B loses direct visibility, potentially simplifying compliance checks. |
| Concurrency                    | None; sequential execution within the loop. | `Check Revision` runs concurrently with the entire revision loop.                           | Model B introduces parallelism that can affect timing but not the existence of checks.                 |
| Join Before `Close Case`       | Sequential: after the loop terminates, `Close Case` follows. | Same final join; after the concurrent `Check Revision` and loop finish, `Close Case` follows.  | Both models ultimately close the case after all visible work.                                            |

# 5. Bounded Comparison Code

```python
import pm4py
from pm4py.objects.petri import net, factory as petri_factory
from pm4py.algo.simulation.play_out import Vfs
from pm4py.algo.simulation.play_out.parameter_variant import DefaultParameters

# Parsing process trees
tree_a_str = '''
->(
  'Open Case',
  *( 
    ->( 
      +('Analyze Revision', 'Check Revision'),
      X('Approve Revision', tau) 
    ),
    'Rework Case'
  ),
  'Close Case'
)
'''
tree_b_str = '''
->(
  'Open Case',
  +( 
    'Check Revision',
    *( 
      ->( 
        'Analyze Revision',
        X('Approve Revision', tau) 
      ),
      'Rework Case'
    ) 
  ),
  'Close Case'
)
'''

tree_a = pm4py.parse_process_tree(tree_a_str)
tree_b = pm4py.parse_process_tree(tree_b_str)

# Convert to Petri nets
net_a = pm4py.convert_to_petri_net(tree_a)
net_b = pm4py.convert_to_petri_net(tree_b)

# Initialize parameters for play-out (bounded exploration)
params = DefaultParameters(verbose=True)

# Define bounded exploration: max 12 visible events, max 3 'Analyze Revision'
def bounded_visible_filter(trace):
    visible = [e for e in trace if e['concept:name'] != 'tau']
    rev_count = sum(1 for e in visible if e['concept:name'] == 'Analyze Revision')
    len_visible = len(visible)
    return len_visible <= 12 and rev_count <= 3

# Generate traces via play-out (bounded by function)
def generate_bounded_traces(net):
    runner = Vfs(net, params)
    traces = []
    seen = set()
    # Simple breadth-first exploration (pseudo)
    # Here we use pm4py.play_out with a max_depth heuristic; however it is *not* exhaustive.
    # Instead we will simulate bounded depth by setting max_depth parameter.
    runner.max_depth = 6  # approx 2**6 = 64 possible depth, we'll manually filter.
    all_traces = runner.apply()
    for t in all_traces:
        if bounded_visible_filter(t):
            traces.append(t)
    return traces

traces_a = generate_bounded_traces(net_a)
traces_b = generate_bounded_traces(net_b)

# Unique traces per model
unique_a = [t for t in traces_a if not any(pm4py.equal_traces(t, u) for u in traces_b)]
unique_b = [t for t in traces_b if not any(pm4py.equal_traces(t, u) for u in traces_a)]

print("Unique to Model A:", len(unique_a), "traces")
print("Traces:", [bt for bt in unique_a][:5])  # show first 5
print("Unique to Model B:", len(unique_b), "traces")
print("Traces:", [bt for bt in unique_b][:5])
```

*Note*: The above uses `pm4py.play_out`, which samples reachable traces up to a given depth; it is **not exhaustive** for large state spaces. For rigorous equivalence under P3, a breadthfirst search over reachable markings, explicitly filtering by visibleevent count, would be required.

# 6. Stochastic and Footprint Comparison

- **`pm4py.discover_footprints(...)`**: Generates a Markov decision process (MDP) summarizing state transitions. Equal footprints indicate that the set of possible future states from any reachable state is the same, but they do **not** guarantee identical visible traces because hidden actions may differ.
  
- **`pm4py.get_stochastic_language(...)`**: Produces a stochastic language (probability distribution over traces). Even if the stochastic languages are identical, the exact trace sequences may still diverge due to hidden `` actions.

- **`pm4py.compute_emd(...)`**: Earth Mover’s Distance (EMD) quantifies the "transport cost" between two probability distributions over traces. A low EMD suggests similarity but not exact trace equivalence.

**Example code for footprint comparison:**

```python
footprint_a = pm4py.discover_footprints(net_a)
footprint_b = pm4py.discover_footprints(net_b)

print("Footprint comparison:", pm4py.compare_footprints(footprint_a, footprint_b))
```

*Result*: Identical footprints may still differ in visible traces because the footprints abstract away ``. Hence, footprint or stochastic comparison **does not replace** visibletrace equivalence analysis.

# 7. Complexity Comparison

```python
def structural_counts(tree):
    # Count nodes, depth, visible/silent leaves, duplicate labels
    import ast
    class Counter(ast.NodeVisitor):
        def __init__(self):
            self.node_count = 0
            self.max_depth = 0
            self.visible_leaves = set()
            self.silent_leaves = set()
            self.duplicate_visible = {}
        
        def visit(self, node):
            self.node_count += 1
            if isinstance(node, dict):
                # Each dict is a transition
                label = node.get('concept:name')
                self.max_depth = max(self.max_depth, node.get('depth', 0))
                if label == 'tau':
                    self.silent_leaves.add(node)
                else:
                    self.visible_leaves.add(label)
                    self.duplicate_visible[label] = self.duplicate_visible.get(label, 0) + 1
            else:
                super().generic_visit(node)
    Counter().visit(tree)
    return {
        "node_count": Counter.node_count,
        "max_depth": Counter.max_depth,
        "visible_leaf_count": len(Counter.visible_leaves),
        "silent_leaf_count": len(Counter.silent_leaves),
        "duplicate_visible": Counter.duplicate_visible
    }

counts_a = structural_counts(tree_a_str)
counts_b = structural_counts(tree_b_str)

# Simplicity of Petri net (using pm4py.simplicity_petri_net)
simpleness_a = pm4py.simplicity_petri_net(net_a, pm4py.get_default_initial_marking(net_a), pm4py.get_default_final_marking(net_a))
simpleness_b = pm4py.simplicity_petri_net(net_b, pm4py.get_default_initial_marking(net_b), pm4py.get_default_final_marking(net_b))

print("Model A counts:", counts_a)
print("Model B counts:", counts_b)
print("Simpleness A:", simpleness_a)
print("Simpleness B:", simpleness_b)
```

*Observed values (illustrative)*:
- **Model A**: 9 nodes, depth 3, 5 visible leaves (including duplicates), 2 silent leaves, duplicate `Analyze Revision` appears twice.
- **Model B**: 8 nodes, depth 2, 4 visible leaves, 1 silent leaf, no duplicate visible leaves beyond initial.
- **Petrinet simpleness**: both modest; Model B’s parallelism reduces depth.

# 9. Final Recommendation

**For Business View P1 (operational compliance):**  
- **Model A** is appropriate because it enforces a `Check Revision` **before each** `Analyze Revision`, preserving the required perattempt compliance.  
- **Model B** is **not** suitable for P1; it may allow an analysis to proceed without a dedicated check, violating the operational compliance rule.

**For Business View P2 (executive dashboard):**  
Both models can be abstracted to the dashboard view, but **Model B** (or the simplified version) is preferable because it already collapses the perattempt checks into a single visible event, matching the dashboard’s boolean “a check occurred” summary.  

**For Bounded Testing (P3):**  
- **Model A** and **Model B** are **not** equivalent under P3 due to differing permissible interleavings (see counterexamples C1 and C2).  
- If only bounded equivalence is needed for testing, **Model B** should be used with explicit bounds (e.g., enforce a maximum of one `Check Revision` per test suite) to align its behavior with the P3 constraints.

**Simplified Model Recommendation:**  
The simplified model targeting **P2** is recommended for dashboard reporting and executive monitoring because it captures the essential highlevel facts (presence of check, number of analyses, occurrence of rework) while discarding irrelevant lowlevel details (`Approve Revision` and perattempt checks).  

**Limitation Warning:**  
Bounded equivalence (P3) is **evidencebased** and does **not** guarantee unbounded equivalence. Extending test scenarios or relaxing bounds may reveal further differences. Always validate compliance with the most stringent (P1) view when operational regulations are critical.
