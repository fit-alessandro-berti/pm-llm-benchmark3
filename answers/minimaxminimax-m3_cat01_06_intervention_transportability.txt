Shared mechanisms: parallelization reduces idle wait between Identity and Document Check, especially when both are digital and reviewers are cross-trained; WIP caps and shorter queues prevent reviewer hoarding; and the cycle-time benefit flows through reduced waiting before Assessment rather than faster service times.

Site-specific mechanisms: the Originals Receipt gate, the legal-review branch with a supplement loop, the heavier tail, and the strict role silos. The registry API upgrade and queue huddles at Site A are also co-interventions that bias naive before/after comparisons.

Effect modifiers: originals-required share, case complexity, role specialization, IT case lock, legal-review requirement, and rework rate all determine whether parallelization is feasible or even measurable.

A similar control-flow diagram does not guarantee transportability because the *information and physical dependencies* (originals, statute, locks) and the *resource topology* (silos vs. cross-trained pools) are not represented in the process tree. Transportability depends on whether the underlying enabling conditions hold.

## 6. Candidate Site B intervention

Eligibility rules:
- In scope: cases with no originals requirement AND no Legal Review requirement (i.e., private, non-high-value,  € threshold,  38% of total). Optionally extend later to digital cases that have no pending Originals Receipt within a configurable SLA.
- Out of scope until proven: public-sector / high-value cases (40%), originals-required cases (62%), and any case with a known supplement risk.

Tasks and concurrency:
- Register.
- Identity Check and Originals Receipt are created immediately after Register; Identity Check may start as soon as a reviewer is free.
- Document Check is created only when (a) Originals Receipt is logged for originals-required cases, or (b) immediately for digital-only cases.
- For in-scope cases, Identity Check and Document Check are eligible to execute concurrently.
- Assessment requires both Identity and Document Check to be completed.
- For out-of-scope cases, no behavioral change: sequential, as today.

Statutory prerequisites (mandatory):
- Assessment cannot start before both verifications are complete.
- Legal Review and any Request Supplement remain statutory and cannot be bypassed.
- Approve/Reject remain gated by Assessment (and Legal Review where applicable).

Queue and WIP controls:
- WIP cap per ID reviewer: 5; per DOC reviewer: 5; per Assessor: 4.
- Daily 15-minute queue huddle with FIFO release to Assessment.
- DOC tasks for in-scope cases are only auto-released if no originals gate is open and no pending Legal Review exists.

Resource responsibilities:
- ID reviewers: own Identity Check; can pick up DOC only as fallback when their queue is empty.
- DOC reviewers: own Document Check; can pick up Identity Check only as fallback.
- Assessors: own Assessment; pull from a single FIFO queue.
- Legal reviewers: own Legal Review and Request Supplement handling.

Logging requirements:
- All task start/end events must be system-recorded at the moment of state change; back-entry is prohibited and audited weekly.
- A new event `parallel_release` is logged when both verifications are released within 30 minutes of each other.

POWL-style description (partial-order relations, with optional sub-processes):

```text
Register -> IdentityCheck
Register -> OriginalsReceipt         (for cases that may need originals)
Register -> DocumentCheck            (only when originals are not required OR originals already received)
IdentityCheck -> Assessment
DocumentCheck -> Assessment
Assessment -> Decision(Approve | Reject)
Decision -> Notify

# Optional Legal branch (out-of-scope cases):
Assessment -> LegalReview
LegalReview -> Decision(Approve | Reject)
LegalReview -> RequestSupplement
RequestSupplement -> DocumentCheck     (re-entry)
Decision -> Notify

# Concurrency constraint:
# IdentityCheck and DocumentCheck may overlap in time for in-scope cases,
# but Assessment waits for both (partial order enforces this).
```

## 7. Pilot for transport learning

| design element | specification | causal purpose | operational safeguard | process-mining measurement |
|---|---|---|---|---|
| Unit of assignment | Individual case (within team) | Clean identification of effect | Cases are atomic | One row per case in event log |
| Randomization | Stratified randomization within each of two pilot teams (treatment vs. control) | Isolate parallelization effect from secular trends | Pilot limited to 2 of 8 teams initially | Compare outcome distributions |
| Strata | (originals_required: yes/no) × (legal_required: yes/no) × (digital: yes/no) | Detect effect modification | Exclude legal+originals strata from treatment | Subgroup outcome metrics |
| Treatment versions | T0: as-is; T1: in-scope parallel release with WIP cap; T2: in-scope parallel release without WIP cap (process-only) | Distinguish mechanism from queue discipline | T2 only in weeks with no volume surge | Variance comparison |
| Primary outcome | Median waiting before Assessment, by stratum | Tests the causal mechanism | None | Computed from event log |
| Secondary outcomes | Cycle time median/p90, DOC service time, rework %, supplement %, appeals %, overlap % | Tests spillover and quality | Stop if appeals +1 pp in 2 weeks | Same log + appeals register |
| Interference controls | Single shared assessor pool; treat team as fixed effect; cap treatment share to 50% of inflow | Prevents spillover | Rotate control days | Team-level fixed effects in regression |
| Power / minimum support | 200 cases per stratum × arm to detect 2-hour wait change at 80% power | Ensures identifiable effect | Pilot runs until minimum support met | Running tally |
| Duration | 8 weeks per arm; up to 16 weeks total | Captures tail | Pre-specified stop dates | Weekly mining snapshots |
| Stop rules | Appeals +1 pp; rework +3 pp; assessor queue > 2× baseline; IT-lock causes >10% back-entry | Safety | Halt expansion, not pilot | Dashboard alerts |
| Transportability analysis | Estimate stratum-specific effects; compare Site A digital-only  to Site B digital-only ; test interaction with originals and legal flags | Quantifies transport | Use Site A's 8%  71% overlap as an upper bound on artifact risk | Side-by-side DFG comparison |

The pilot separates mechanism failure from implementation failure by combining (a) a randomized control arm that holds queue discipline and IT lock constant, (b) a treatment version without the WIP cap to test whether overlap is a queue-discipline effect, and (c) strict logging that prevents back-entry. If T1 outperforms T0 in waiting before Assessment but T2 does not, the gain is queue-driven, not parallelization-driven. If both T1 and T2 look like Site A's "overlap" without cycle-time improvement, the apparent gain is a logging artifact. Stratum-specific estimates expose heterogeneity that the Site A aggregate hid.

## 8. PM4Py model-construction code

```python
# Site A and Site B process models in PM4Py
# Note: this code encodes control flow only.
# It cannot represent: data-dependent legal requirements,
# resource capacity / WIP caps, case-system locks, or durations.

from pm4py.objects.process_tree.obj import Operator, ProcessTree
from pm4py.objects.powl.obj import (
    StrictPartialOrder, Operator as POWLOperator,
    SilentTransition, Transition,
)
from pm4py.objects.conversion.process_tree import converter as pt_converter
from pm4py.objects.conversion.powl import converter as powl_converter
from pm4py import (
    parse_process_tree, convert_to_petri_net,
    check_is_workflow_net, check_soundness, play_out,
)

# ---- 1. Site A BEFORE ----
site_a_before_tree = parse_process_tree("-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )")
site_a_before_net, site_a_before_im, site_a_before_fm = convert_to_petri_net(site_a_before_tree)

# ---- 2. Site A AFTER ----
site_a_after_tree = parse_process_tree("-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )")
site_a_after_net, site_a_after_im, site_a_after_fm = convert_to_petri_net(site_a_after_tree)

# ---- 3. Site B candidate using POWL ----
# Activities
register    = Transition(label="Register")
id_check    = Transition(label="Identity Check")
orig_recept = Transition(label="Originals Receipt")
doc_check   = Transition(label="Document Check")
assessment  = Transition(label="Assessment")
legal       = Transition(label="Legal Review")
supplement  = Transition(label="Request Supplement")
decision_lr = Transition(label="DecisionLR")  # Approve/Reject after legal
decision    = Transition(label="Decision")    # Approve/Reject after assessment
notify      = Transition(label="Notify")

# Exclusive choice for the legal-required sub-process
xor = POWLOperator.XOR(
    POWLOperator.XOR(Transition(label="Approve"), Transition(label="Reject")),  # direct
    POWLOperator.SEQUENCE(                                                    # legal branch
        legal,
        POWLOperator.XOR(
            POWLOperator.SEQUENCE(supplement, doc_check),  # supplement loop
            POWLOperator.XOR(Transition(label="Approve"), Transition(label="Reject"))
        )
    )
)

# A "digital fast path" where Document Check can start in parallel with Identity Check
parallel = POWLOperator.PARALLEL(id_check, doc_check)

# Partial order that enforces:
#   Register precedes everything
#   Originals Receipt precedes Document Check
#   Identity and Document Check both precede Assessment
#   Assessment precedes Decision
#   Legal branch (if taken) precedes its decision
#   Decision precedes Notify
spo = StrictPartialOrder(nodes=[
    register, id_check, orig_recept, doc_check, assessment, xor, decision, notify
])
spo.order.add_edge(register, id_check)
spo.order.add_edge(register, orig_recept)
spo.order.add_edge(orig_recept, doc_check)
spo.order.add_edge(id_check, assessment)
spo.order.add_edge(doc_check, assessment)
spo.order.add_edge(assessment, xor)
spo.order.add_edge(xor, decision)
spo.order.add_edge(decision, notify)

# ---- 4 & 5. Convert POWL -> Petri net ----
site_b_net, site_b_im, site_b_fm = powl_converter.apply(spo)

# ---- 6. Soundness / workflow-net checks ----
for name, net, im, fm in [
    ("Site A before", site_a_before_net, site_a_before_im, site_a_before_fm),
    ("Site A after",  site_a_after_net,  site_a_after_im,  site_a_after_fm),
    ("Site B",        site_b_net,        site_b_im,        site_b_fm),
]:
    is_wfn = check_is_workflow_net(net)
    is_sound = check_soundness(net)
    print(f"{name}: workflow_net={is_wfn}, sound={is_sound}")

# ---- 7. Optional playout ----
for name, net, im, fm in [
    ("Site A before", site_a_before_net, site_a_before_im, site_a_before_fm),
    ("Site A after",  site_a_after_net,  site_a_after_im,  site_a_after_fm),
    ("Site B",        site_b_net,        site_b_im,        site_b_fm),
]:
    print(f"--- {name} sample traces ---")
    for _ in range(3):
        try:
            trace = play_out(net)
            print(trace)
        except Exception as e:
            print("play_out not available:", e)
            break

# ---- 8. What this model cannot encode ----
# - Data-dependent decisions: e.g., "Originals required" is a data attribute;
#   the model assumes the Originals Receipt path is always taken.
# - Resource capacity: WIP caps, reviewer pools, the 6-task cap at Site A.
# - Case-system locks: a single-owner lock that prevents true concurrency.
# - Durations: service times and Originals Receipt delays are not represented.
# - Rework semantics: the supplement loop is encoded as a sequence edge,
#   but the probability of re-entry is not.
# - Digital channel: not represented; the parallel branch is unconditional.
```

## 9. Recommendation

**conditional go**

The Site A result is not an identified treatment effect. The 9-hour median reduction is confounded by an API upgrade, two additional document-reviewer FTEs, a marketing-driven mix shift toward simpler digital claims, and the introduction of daily queue huddles. The headline overlap metric (8%  71%) is also partly a logging artifact. The only *qualitative* lesson that survives scrutiny is that waiting before Assessment is the largest controllable component of cycle time, and that overlap between verification tasks can reduce that wait. That mechanism is real but its magnitude is unknown.

What should be transferred: the *principle* of releasing Identity and Document Check together for cases where both are digital and where no originals gate and no legal review apply; explicit per-reviewer WIP caps; a strict event-logging discipline that forbids back-entry; and daily queue huddles. These are the only elements that plausibly do the work in Site A.

What should not be copied: a blanket "create both tasks immediately after Register for every case." This is illegal or infeasible for the 62% of Site B cases that require originals, the 40% that require legal review, and it is mechanically blocked by Site B's single-owner case lock and role silos. The Site A-after process tree alone is not portable to Site B.

Subgroup to enter first: private, non-high-value cases that are digital and have no legal review (roughly 20–25% of volume). This stratum mirrors Site A's post-intervention mix and is where the mechanism is identifiable. A second stratum (digital, non-originals but with legal review) should follow only after IT multi-owner support and assessor capacity are confirmed.

Expected benefits: a median cycle-time reduction of 5–8 hours within the pilot stratum, a portfolio median reduction of 1–2 hours, and no change in appeals. Expected risks: a bottleneck shift to the 3-assessor pool and the 7-document-reviewer pool, which could *raise* the p90; a logging artifact that makes the intervention look successful when it is not; and rework rate holding at 17% or rising if supplement loops are not managed.

Triggers for expansion: stratum-specific wait reduction  2 h, p90 flat, appeals flat, overlap metric >40% with verified timestamps. Triggers for modification: assessor queue growth or DOC service time regression. Triggers for abandonment: appeals +1 pp, rework +3 pp, or p90 +10 h in any stratum.

## 10. Assumption register

1. **The Site A wait reduction is partly causal** — needed to justify any transfer — test with a negative control process in the Site B pilot — if false, even the digital-only stratum will show no effect.
2. **Originals Receipt delay is the binding constraint, not Document Check service time** — needed to set the eligibility filter — test by logging Originals Receipt arrival timestamps in Site B — if false, parallelization is feasible for a larger share than 38%.
3. **Site B's case-management lock can be relaxed for in-scope cases** — needed for true concurrency — test with a single-team IT pilot — if false, overlap is administrative only.
4. **Role silos can support a shared handoff queue without headcount increase** — needed because Site A's cross-training is not present — test with a shadow queue in the pilot — if false, hand-offs add latency and the bottleneck shifts.
5. **The assessor pool (3 FTE) has slack during the pilot window** — needed to absorb faster inflow — test with a 2-week capacity study — if false, p90 will rise even if median falls.
6. **Rework and supplement rate are not driven by verification parallelism** — needed to claim no quality regression — test by tracking rework by stratum in the pilot — if false, parallelization worsens the supplement loop.
7. **The Site A overlap metric is at least partially real, not purely a logging artifact** — needed to set a credible upper bound — test by replaying pre-intervention logs with improved timestamps — if false, the apparent mechanism is an illusion.
8. **Daily queue huddles are not the dominant cause of the Site A gain** — needed to credit parallelization rather than queue discipline — test by including a treatment arm without WIP cap in the Site B pilot — if false, the transferred change should be queue discipline, not parallelization.
