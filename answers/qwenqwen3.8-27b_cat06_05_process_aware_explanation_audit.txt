## 2. Process-model consistency checks

A concrete validation suite should treat temporal availability, process feasibility, and explanation semantics as separate gates.

### Prefix-time availability validation

Define `t0` as the timestamp of the first `Coverage Check Completed` event, plus a reliable sequence index where available. The admissible prefix is:

- events with `event_time < t0`, plus
- events with `event_time = t0` only if a reliable sequence index proves they occurred at or before the prediction point and were available to the model at `t0`.

If sequence index is missing, same-timestamp events should be treated as unordered and excluded from ordered patterns.

Checks:

1. **Feature timestamp assertion**  
   Every feature must have a `feature_as_of_time` or equivalent lineage timestamp. Assert:
   - `feature_as_of_time <= t0`
   - for event-derived features, `max(source_event_time) < t0`, or same-timestamp rule satisfied.

2. **SQL and transformation linting**  
   Flag features built from:
   - `extraction_date`
   - `close_date`
   - `final_*`
   - `last_*`
   - `total_*`
   - `any_*`
   - `current` fields without a stored calculation timestamp  
   unless there is an explicit point-in-time override.

3. **Truncated-trace recomputation**  
   For a sample of claims, rebuild each feature using only events up to `t0`. Compare with the stored feature value. Any mismatch indicates leakage or mutable lineage.

4. **Snapshot latency validation**  
   For `queue_length_at_t0`, validate that the queue snapshot timestamp is not materially after `t0`. Store snapshot ID, snapshot time, and tolerance.

### Activity-order feasibility validation

Build a normative process model with hard constraints:

- `Claim Registered` before `Coverage Check Completed`.
- After `Coverage Check Completed`, the next legitimate activities are:
  - `Damage Assessment Completed` for fast track, or
  - `Documents Requested` for evidence cycles.
- `Documents Requested` before `Documents Received` before `Documents Validated`.
- Additional `Documents Requested` cycles are allowed.
- `Damage Assessment Completed` before `Settlement Decision Recorded`.
- `Fraud Investigation Opened` may occur after a trigger and may run in parallel with evidence collection or damage assessment.
- `Settlement Decision Recorded` can be Approve, Partial, Deny, or Withdrawn.
- `Appeal` only after Partial or Deny.
- A second `Settlement Decision Recorded` is legitimate only after an `Appeal` following Partial or Deny.
- `Claim Closed` follows a final decision or withdrawal.
- `Claim Closed` before `Damage Assessment Completed` is process-inconsistent.

At `t0`, immediately after the first `Coverage Check Completed`:

- **Current state:** coverage check completed.
- **Enabled next activities:** `Damage Assessment Completed` or `Documents Requested`; `Fraud Investigation Opened` only if a trigger is known and allowed at that point.
- **Impossible at `t0`:** `Claim Closed`, `Settlement Decision Recorded`, `Appeal`.
- **Future-possible:** all later activities, but not admissible as observed state.

An explanation validator should map each feature or pattern to an activity or process state and block explanations that cite impossible or future-only activities as if they were known at `t0`.

### Same-timestamp ambiguity validation

For every timestamp group:

1. Check whether a reliable `sequence_index` exists.
2. If missing, mark the events as unordered.
3. Do not derive ordered sequence patterns from unordered same-timestamp events.
4. For `t0`, exclude same-timestamp events unless the sequence index and business rule confirm availability at prediction time.

This is essential for Case Z, where `Claim Closed` and `Damage Assessment Completed` share a timestamp and lack sequence index. The pattern `Claim Closed -> Damage Assessment Completed` should not be treated as a real process transition.

### Complete-trace detection

A feature or pattern is complete-trace if its value changes when future events are removed.

Checks:

- Lineage metadata must list source events, time bounds, and transformation logic.
- Run prefix-only recomputation on truncated traces.
- Flag features whose value depends on events after `t0`.
- Flag sequence patterns that include activities after `t0`.

Examples:
- `full_trace_variant_id` is complete-trace.
- `appeal_seen_anywhere` is complete-trace.
- `Appeal -> Settlement Decision Recorded` is complete-trace for a `t0` model, even though it is process-legitimate in a later stage of the claim.

### Explanation activity-status checks

For each explanation term, classify the referenced activity at `t0`:

| Explanation term | Status at `t0` | Action |
|---|---|---|
| `Claim Registered` | current/past | allowed |
| `Coverage Check Completed` | current | allowed |
| `Documents Requested` | future-possible / enabled next | allowed only as expected state, not observed |
| `Damage Assessment Completed` | future-possible / enabled next | allowed only as expected state, not observed |
| `Fraud Investigation Opened` | future-possible unless trigger known | require trigger evidence |
| `Settlement Decision Recorded` | impossible at `t0` | block |
| `Appeal` | impossible at `t0` | block |
| `Claim Closed` | impossible at `t0` | block |
| `Claim Closed -> Damage Assessment Completed` | process-inconsistent | block and data-quality flag |
| `Appeal -> Settlement Decision Recorded` | future-possible, process-legitimate later | block for `t0`, allow for later prediction time |

### Repeated Settlement Decision validation

Repeated `Settlement Decision Recorded` events are not automatically invalid. They are semantically legitimate only if:

1. The first decision is Partial or Deny.
2. An `Appeal` event occurs after the first decision.
3. The second decision occurs after the appeal.
4. Timestamps and sequence index support the order.
5. No appeal follows Approve or Withdrawn.

This check distinguishes a legitimate appeal-reconsideration path from an invalid or misordered decision sequence.

### Role and limitations of conformance methods

- **DFG checks** discover frequent transitions in data. A frequent DFG edge is not automatically a normative rule. It may reflect common practice, data error, or an unmodeled variant.
- **Alignment checks** measure how well traces conform to a model and can identify deviations. They do not prove causality and may miss valid unmodeled variants.
- **Footprint checks** show which activities occurred, but not order or timing. They are insufficient for temporal leakage detection.
- **Prefix checks** are necessary for temporal validity but not sufficient for causal or operational claims.
- **Declarative constraints** can encode hard process rules, such as “Appeal only after Partial/Deny,” but they must be maintained and validated against data quality issues.

## 3. Alternative feature interpretations

There is no single exact accepted feature set. The correct standard depends on the purpose: prediction, explanation, causal inference, operational action, or fairness.

| Class | Examples | What may be claimed | What may not be claimed |
|---|---|---|---|
| Defensible predictive signal | `initial_damage_complexity`, `elapsed_since_registration_at_t0`, `initial_reserve_at_t0` if timestamped, `prior_claim_count_before_t0` after repair, `risk_score_at_t0` after repair, `claimant_channel_at_t0` if verified | These features are point-in-time and historically associated with breach risk. They may be used for ranking and prediction if stable and calibrated. | They do not prove causation. They are not automatically actionable. They require fairness/robustness review if they proxy protected or sensitive characteristics. |
| Process-state or congestion signal | `queue_length_at_t0`, `elapsed_since_registration_at_t0`, `document_count_at_t0` after repair, `fraud_trigger_at_t0` if available, `team_or_resource_at_t0` after repair | The claim is in a particular operational state: congested, late, waiting, assigned to a team, or flagged for investigation. These may support operational monitoring or routing if an intervention is known. | Queue length or elapsed time does not by itself cause breach. It may proxy complexity, staffing, policy, or claim type. Actionability requires a known operational lever. |
| Proxy requiring fairness/robustness review | `claimant_region`, `claimant_channel`, `initial_reserve`, `prior_claim_count`, `resource_role` or `team` after repair | These features may be predictive and retained if validated, monitored, and reviewed for proxy effects. Operational proxies may be preferred, e.g., repair-network coverage, language, channel, reserve size, claim type, or workload. | Region, channel, reserve, or prior claims do not inherently cause delay. They should not be used to justify adverse treatment without fairness review. They should not be presented as causal explanations. |
| Drift/calendar proxy | `calendar_week`, holiday indicators, policy-change indicators, seasonality | Certain periods may have different breach rates due to policy, staffing, holidays, or external conditions. These features may improve prediction if the operational regime is stable or explicitly modeled. | The calendar week itself does not causally cause breach. Do not generalize across policy changes or holidays without controls. Monitor for regime shift. |
| Unusable until lineage is repaired | `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `num_document_requests_total`, `full_trace_variant_id`, current `prior_claim_count_before_t0`, `same_day_document_count_snapshot`, `final_decision`, `risk_score_current`, `last_resource_role`, extraction-date `employee_experience`, future sequence patterns, impossible `Claim Closed -> Damage Assessment Completed` pattern | These may be useful for complete-trace analysis, later-stage prediction, or root-cause analysis after the fact. | They cannot be used in a `t0` prediction or `t0` explanation. They cannot be presented as early warnings, causal reasons, or actionable levers at `t0`. |

Important distinction:

- `Appeal -> Settlement Decision Recorded` is **process-legitimate** in the full claim lifecycle, but it is **temporally unavailable** at `t0`.
- `Claim Closed -> Damage Assessment Completed` is **process-inconsistent** under the normative model and also temporally unavailable at `t0`. It should be treated as a data-quality or ordering problem, not as a valid predictive pattern.

## 5. Recommendations for explanation validation

| Priority | Workstream | Actions | Why it matters |
|---:|---|---|---|
| P0 | Feature-store and temporal repair | Build a point-in-time feature store. Every feature must have `as_of_time`, source event bounds, transformation version, and lineage hash. Remove or quarantine features using `extraction_date`, `final_*`, `last_*`, `total_*`, `any_*`, or untimestamped `current` fields. | Stops obvious leakage and makes early predictions defensible. |
| P0 | Prefix-only recomputation | Recompute features and explanations using only events up to `t0`. For same-timestamp events, require reliable sequence index; otherwise treat events as unordered. | Ensures explanations reflect only information available at prediction time. |
| P0 | Process-conformance tests | Implement normative checks for activity order, repeated settlement decisions, appeal eligibility, and impossible patterns such as `Claim Closed -> Damage Assessment Completed`. | Prevents process-inconsistent patterns from being presented as valid explanations. |
| P0 | Recompute affected predictions and recalibrate | Retrain or recompute models without leaked features. Evaluate discrimination and calibration: AUC, Brier score, log-loss, reliability diagram, and threshold performance for the 10-day target. | Removes target contamination and restores meaningful breach probabilities. |
| P1 | Historical feature timestamps and lineage | Add feature registry metadata: source events, SQL or code version, timestamp logic, snapshot IDs, and truncation tests. Audit joins such as employee experience, queue snapshots, risk scores, and document counts. | Catches subtle mutable-feature leakage that name-based checks miss. |
| P1 | Explanation stability | Compare global and local explanations before/after repair. Use bootstrap, permutation, feature grouping, and sensitivity tests. Flag features whose importance is unstable or driven by rare variants. | Prevents overreliance on noisy or leaked SHAP-like contributions. |
| P1 | Proxy and fairness analysis | Review `claimant_region`, `claimant_channel`, `initial_reserve`, `prior_claim_count`, resource/team features, and related proxies. Test for disparate impact, proxy effects, stability, and operational alternatives. | Avoids deleting all correlated features while preventing unjustified or discriminatory use. |
| P1 | Causal and actionability guardrails | Label explanations as predictive, process-state, proxy, or drift. Require separate evidence before claiming causality or operational actionability. | Keeps predictive monitoring from becoming unsupported causal storytelling. |
| P2 | Monitoring for schema and process drift | Monitor event schema changes, new activity labels, missing sequence indices, timestamp gaps, queue snapshot latency, policy changes, holidays, region/channel distributions, and explanation drift. | Detects when the process, data pipeline, or operational regime changes. |
| P2 | Ongoing validation cadence | Run automated prefix-time, conformance, calibration, and fairness checks on every model refresh and periodically on historical data. | Maintains credibility of explanations over time. |
