# 1. Objectives and constraints

## Optimization Objectives
The policy aims to maximize a composite value function that balances six competing dimensions:
1.  **SLA Compliance:** Minimize probability of deadline misses, prioritizing urgent/high cases.
2.  **Throughput Efficiency:** Reduce waiting and service times by matching skills and avoiding unnecessary handovers.
3.  **Quality & Rework Reduction:** Prevent errors by ensuring skill adequacy and respecting continuity for complex/reassigned cases.
4.  **Workload Fairness:** Distribute assignments evenly to prevent burnout and idle time, respecting overtime risk.
5.  **Skill Development:** Support training priorities for normal/low-priority cases to build long-term capacity.
6.  **Resilience:** Avoid creating single points of failure (bottlenecks) and maintain continuity where handover costs are prohibitive.

## Constraints
### Hard Constraints (Safety/Compliance)
*   **Capacity:** Max 4 new assignments per resource per batch.
*   **Skill Thresholds:**
    *   High/Urgent priority requires skill  2.
    *   Security Review requires skill 3, or skill 1–2 under explicit supervision by R7_Gita or R8_Hugo.
    *   Final Approval requires skill 2–3. Skill 1 may only prepare, not finalize.
*   **Overtime Protection:** Resources with `overtime_risk = high` (R2, R4, R9) cannot receive assignments unless the case is urgent/high and no compliant alternative exists.
*   **Quality Batching:** Quality Check may be batched only if priority is normal/low and SLA remaining > 24h.

### Soft Constraints (Preference Trade-offs)
*   **Training Share:** At least 20% of normal/low-priority assignments should match the resource's `training_priority`, provided SLA risk is acceptable.
*   **Continuity Preference:** For high-complexity cases with high handover cost, keep the current owner unless skill is 0/1 and supervision is infeasible.
*   **Workload Balance:** Prefer resources with lower open-case ratios and higher remaining hours, penalizing high overtime risk.

# 2. Assignment policy

## Policy Name: Balanced Adaptive Routing with Supervision & Fairness (BAR-SF)

The policy uses a multi-criteria scoring mechanism with hard filters.

### Algorithm Pseudocode

```python
def bar_sf_policy(queue_snapshot, resource_matrix):
    assignments = []
    batch_counts = {r: 0 for r in resource_matrix}
    
    # Sort cases by urgency: Urgent > High > Normal > Low
    queue = sort_by_urgency(queue_snapshot)
    
    for case in queue:
        candidates = []
        
        for res in resource_matrix:
            # 1. Hard Eligibility Filter
            if batch_counts[res] >= 4: continue
            if res.overtime_risk == 'high' and case.priority not in ['urgent', 'high']: continue
            
            skill = res.skills[case.required_skill]
            
            # Security/Approval Rules
            if case.required_skill == 'Security' and skill not in [3, 2, 1]: continue
            if case.required_skill == 'Approval' and skill < 2: continue # Skill 1 cannot finalize
            
            # High Priority Skill Check
            if case.priority in ['urgent', 'high'] and skill < 2:
                # Allow only if supervision possible
                if not can_supervise(res, case, resource_matrix): continue
                candidates.append((res, score_supervised(res, case)))
            else:
                candidates.append((res, score_standard(res, case)))
        
        if not candidates:
            # Fallback: Relax OT constraint for urgent cases if no alternative
            fallback = relax_constraints(queue, res, resource_matrix)
            assignments.append(fallback)
        else:
            # 2. Select Best Candidate
            best_res, best_score = max(candidates, key=lambda x: x[1])
            assignments.append((case, best_res))
            batch_counts[best_res] += 1
            
    return assignments

def score_standard(res, case):
    score = 0.0
    # SLA Urgency (Normalized)
    score += sla_weight(case.priority) * inverse_sla_time(case.sla_remaining)
    
    # Skill Match (Diminishing returns for >3 to avoid over-specialization)
    skill = res.skills[case.required_skill]
    score += skill_match_score(skill)
    
    # Continuity Bonus
    if res.id == case.current_owner:
        score += continuity_bonus(case.complexity, case.handover_cost)
        
    # Workload Penalty
    workload_ratio = res.open_cases / (res.hours_remaining * 10) # Normalized
    score -= workload_penalty(workload_ratio)
    
    # Training Bonus (Soft)
    if case.priority in ['normal', 'low'] and res.training_priority == case.required_skill:
        score += training_bonus(case.sla_remaining)
        
    # Resilience/Team Balance
    score += team_capacity_bonus(res.team, case)
    
    return score
```

### Scoring Components
1.  **SLA Urgency:** Urgent cases get a high base multiplier. SLA time is inverted; shorter time = higher score.
2.  **Skill Match:** Score 3 for skill 3, 2 for skill 2, etc. Avoids assigning skill 3 to simple tasks if skill 2 is available to preserve specialist capacity.
3.  **Continuity:** Adds significant points if `res.id == case.current_owner`, scaled by complexity and handover cost. Penalizes handovers for high-complexity/high-cost cases.
4.  **Workload:** Penalizes resources with high `open_cases` relative to `hours_remaining`. Prevents overloading.
5.  **Training:** Adds points if `res.training_priority` matches `case.required_skill` and case priority allows (normal/low).
6.  **Resilience:** Small bonus for assigning to resources in teams with available capacity, preventing cross-team dependency bottlenecks.

### Tie-Breaking
1.  Lower `reassignment_count` (fairness to owner).
2.  Lower `open_cases` (load balancing).
3.  Alphabetical resource ID (determinism).

# 4. Comparison with baseline policies

| Dimension | First-Available Routing | Specialist-Only Routing | BAR-SF (Proposed) |
|---|---|---|---|
| **Expected Throughput** | High (minimizes idle time). | Low (specialists queue up; simple tasks blocked). | **Balanced.** Optimizes flow by using skill 2 resources for normal tasks and avoiding bottlenecks. |
| **SLA Risk** | High. Ignores skill; urgent cases may go to unskilled resources. | Low for complex, High for simple (bottlenecks). | **Low.** Prioritizes SLA urgency and ensures skill thresholds. |
| **Error/Rework Risk** | High. Skill mismatches increase rework. | Low. Specialists ensure quality. | **Low.** Skill matching and continuity reduce rework; supervision mitigates trainee errors. |
| **Fairness of Workload** | Poor. "Rich get richer"; high-load resources get more work. | Poor. Specialists become overloaded; others idle. | **Good.** Penalizes high workload; avoids high-OT resources; limits batch assignments. |
| **Skill Development** | None. Training ignored. | Low. Specialists too busy for trainees. | **High.** Explicitly allocates 20% of normal/low cases to training matches. |
| **Continuity of Ownership** | Low. Frequent reassignments for load balancing. | Low. Cases jump to specialists regardless of history. | **High.** Rewards continuity for high-complexity/high-handover cases. |
| **Resilience** | Low. No backup planning; absences cause immediate failure. | Low. Single points of failure in specialist roles. | **High.** Cross-training via assignments; supervision buffers; avoids single-resource bottlenecks. |

**Reasoning:** First-available routing maximizes short-term throughput but violates compliance (skill 0/1 on urgent cases) and increases long-term rework. Specialist-only routing ensures quality but creates severe bottlenecks (e.g., Security/Approval queues) and ignores fairness. BAR-SF accepts a slight trade-off in immediate throughput for significantly lower SLA risk, rework, and burnout, while actively building workforce resilience through training and balanced load distribution.

# 5. Explanation to workers

> **Why are cases assigned to specific workers?**
>
> This assignment policy is designed to support you, ensure our customers get timely service, and help us all grow. Here's how it works:
>
> *   **Your Workload Matters:** We look at how many cases you have and how much time is left in your day. If you're already busy or at risk of overtime, we'll route cases to colleagues who have capacity. This helps prevent burnout and keeps quality high.
> *   **Continuity for Complex Cases:** If a case is complex or has been handed over many times, we prefer to keep it with you. Handovers can add delays and errors. Sticking with the owner helps resolve cases faster and reduces frustration.
> *   **Skill Matching & Supervision:** We match cases to your skill level. For urgent or high-priority cases, we ensure you have the right expertise. If a case requires a specialist skill you're still developing, we pair you with a supervisor (like R7 or R8) to guide you. This keeps you safe and helps you learn.
> *   **Training Opportunities:** We want to help you build new skills. If you've indicated a training priority (e.g., Diagnosis or Approval), we'll try to assign normal or low-priority cases that match that skill. This is safe because these cases have more time and are supervised if needed.
> *   **Fairness & Team Balance:** We avoid overloading any single person. We also try to keep cases within your team when possible to leverage team knowledge, but we'll route across teams if it helps balance the load or meet urgent deadlines.
>
> **This isn't just an algorithm; it's a tool to help us work together effectively.** You can always flag if a case doesn't fit, or if you need support. Your feedback helps us improve the policy.

# 6. Process-mining audit indicators

To audit the deployed policy, the following indicators should be tracked using event logs:

1.  **Handover Frequency:** `pm4py.discover_handover_of_work_network(log)`. Monitor average handovers per case; target reduction for high-complexity cases.
2.  **Reassignment Count:** Distribution of `reassignment_count` per case. Flag cases with >2 reassignments for root-cause analysis.
3.  **Skill Mismatch:** Count of cases where `required_skill` > `resource_skill` (excluding supervised assignments). Target: 0 for urgent/high.
4.  **Workload Distribution:** Gini coefficient of `workload_snapshot` across resources. Monitor for drift.
5.  **Overtime Risk Exposure:** Percentage of assignments to resources with `overtime_risk=high`. Target: <5% unless SLA critical.
6.  **SLA Misses:** `pm4py.filter_case_performance(log, attribute="sla_deadline")`. Track miss rate by priority and assigned resource.
7.  **Rework/Appeal Rate:** Correlate `assignment_reason` with downstream rework events. High rework on skill 1 assignments without supervision indicates policy failure.
8.  **Training Assignment Share:** Ratio of cases assigned to resources where `resource.training_priority == case.required_skill` for normal/low priority cases. Target: 20%.
9.  **Specialist Bottleneck Indicators:** Throughput time for Security/Approval activities. Monitor queue length and waiting time for specialist resources.
10. **Deviations from Policy:** Log events where manual overrides occurred. Analyze reasons to refine policy weights.
