## 1. Duplicate-handling decision tree

Start from candidate groups only; never apply global same-timestamp/same-activity deletion.

1. **Exact technical duplicate?**  
   Same `source`, same `source_event_key`, same `payload_hash`, same business timestamp/activity, caused by retry/replay.  
   **Terminal action:** drop the redundant technical copy, keep the surviving event’s source key and an audit row.  
   **Rationale:** no business information is lost.

2. **Same physical event observed by multiple systems?**  
   Different source systems provide different observations of one real-world occurrence, supported by reconciliation evidence, shared focal objects, and compatible payloads. Example: e03/e04.  
   **Terminal action:** merge attributes and relations into one canonical event; retain source-level provenance and source-qualified attributes.  
   **Rationale:** one business transition should not be counted twice, but source differences must remain auditable.

3. **Summary event derived from a detailed event?**  
   One event is an abstraction, rollup, or status update generated from another event or from multiple detailed events. Examples: e07 from e06; e15 from payment messages.  
   **Terminal actions:**  
   - If the summary has independent audit or accounting meaning: **retain both with refined labels or qualifiers**.  
   - If a validated derivation link exists and abstraction loss is acceptable: **merge attributes and relations**, recording `derived_from`.  
   - If the summary aggregates multiple detailed events: **do not merge into one detailed event**; retain summary separately or **quarantine**.  
   **Rationale:** abstraction-level events can be analytically useful and should not become false rework.

4. **Harmonization collision between semantically distinct source activities?**  
   Integration mapped different source activities to one common label. Example: e08 “released from warehouse” and e09 “accepted by carrier” both became `Dispatch Package`.  
   **Terminal action:** retain both with refined labels or qualifiers; quarantine only if no safe refined label can be created.  
   **Rationale:** same label is not same semantics.

5. **Concurrent same-label events involving different objects?**  
   Same activity and timestamp, but different focal objects or lifecycle instances. Examples: e03/e05 because I1 vs I2; e13/e14 because M1 vs M2.  
   **Terminal action:** retain both unchanged, or retain both with object-qualified labels.  
   **Rationale:** concurrency is legitimate; object difference defeats duplication.

6. **Unresolved candidate?**  
   Evidence is insufficient, conflicting, or dependent on unavailable source semantics.  
   **Terminal action:** quarantine for review; do not drop or merge destructively.  
   **Rationale:** absent a hidden correct duplicate list, conservatism and reversibility dominate.

## 3. Timestamp-tie ordering rules

The pipeline should first construct a **partial order** from evidence, then apply deterministic tie-breakers only where the partial order remains ambiguous.

**Rule hierarchy:**

1. **Domain constraints** — semantic.  
   Examples: authorization precedes capture for the same payment; handover occurs after carrier acceptance; delivery confirmation occurs after dispatch. These are business truths when supported by facts.

2. **Lifecycle constraints on shared objects** — mostly semantic, but must be validated.  
   Examples: an item pick for a package should precede packing that package; an invoice should exist before payment capture if the order-to-cash lifecycle requires it. Lifecycle rules can be wrong if the process allows pre-authorization or post-billing exceptions.

3. **Within-source sequence** — semantic within a source, deterministic only inside that source.  
   `source_seq` is meaningful only within one source. It can order ERP events relative to ERP events, PSP events relative to PSP events, etc., but it cannot by itself order ERP against PSP.

4. **Source-specific semantics** — semantic.  
   Examples: ERP pack summary e07 is generated after WMS pack e06; ERP payment summary e15 is generated after payment messages. These derivation facts justify ordering summaries after detailed events.

5. **Ingestion time** — technical, not semantic.  
   `ingested_at` may reflect integration latency, retry, or batching. It can be used for auditing or as a very weak deterministic fallback only when no business interpretation is affected. It must never be the primary business order.

6. **Stable fallback order** — deterministic only.  
   Use source priority, `source_event_key`, payload hash, or event id. This creates reproducibility but does not prove physical order.

**Why synthetic microseconds are dangerous:**  
Adding microseconds before deciding semantic order turns an unknown tie into an asserted sequence. DFGs, performance metrics, and conformance checks will treat the synthetic offset as real precision. For example, ordering e07 one microsecond after e06 may create an apparent “Pack  Pack” loop or an artificial ERP delay. Therefore, synthetic offsets should be stored in a separate `adjusted_timestamp` or `ordering_timestamp`, never overwrite `original_timestamp`, and should be generated only after the partial order has been justified.

  If invoice-before-payment is not accepted as semantic, e11 may be concurrent with the PSP events; deterministic fallback can still place e11 first, but that should be labeled deterministic, not proven physical order.

## 4. Conservative cleaning pipeline

The conservative pipeline minimizes semantic damage by deleting or merging only strongly supported duplicates and by preserving abstraction-level events.

**Steps:**

1. **Snapshot and preserve provenance.**  
   Deep-copy the raw OCEL. Add `original_timestamp`, `original_activity`, and retain `source`, `source_event_key`, `source_seq`, `ingested_at`, and `payload_hash`.

2. **Candidate pre-check.**  
   Identify same-timestamp/same-activity groups, object-overlap groups, and exact technical duplicate groups. Do not merge yet.

3. **Exact technical deduplication only.**  
   Apply duplicate dropping only to exact technical retries. In this dataset, no exact technical duplicate is evident, so no event should be removed by this step.

4. **Verified-pair merging.**  
   Merge e03/e04 because reconciliation proves same physical scan. Merge e11/e16 because invoice V1 proves same invoice issuance. Use source-qualified attribute storage so Billing-authoritative and ERP-authoritative fields are not lost.

5. **Refine harmonized labels.**  
   Retain e06/e07, e08/e09, e13/e14, and e15, but add qualifiers:
   - e06: `Pack Package (WMS Detail)`
   - e07: `Pack Package (ERP Summary)`
   - e08: `Dispatch Package (Warehouse Release)`
   - e09: `Dispatch Package (Carrier Acceptance)`
   - e13: `Capture Payment (PSP M1)`
   - e14: `Capture Payment (PSP M2)`
   - e15: `Capture Payment (ERP Invoice Summary)`

6. **Deterministic ordering without deleting concurrency.**  
   Build partial-order constraints, then assign a deterministic `order_rank`. Generate `adjusted_timestamp` only after ranking. Keep `original_timestamp` unchanged. Record that ties remain ties semantically.

7. **Validation and audit.**  
   Validate referential integrity between events, relations, and objects. Write audit rows for every merge, label refinement, and ordering rule.

Performance from pack to dispatch may look cleaner, but the process model becomes less faithful to multi-system accountability.

### Mechanically aggressive PM4Py merging

This scenario uses library merging broadly on candidate groups with same timestamp/activity and common objects, but it should be guarded to avoid prohibited collapses. An unguarded merge could merge e03/e04/e05 and e13/e14/e15, which would drop e05 and e14 and is therefore unacceptable.

For payment events, shared Order and Invoice are context, not identity.

def merge_verified_pair(
    ocel,
    canonical_eid,
    duplicate_eid,
    merge_rule,
    confidence,
    reason,
):
    """
    Custom verified-pair merge.

    This is intentionally conservative:
    - canonical event remains;
    - duplicate event row is removed;
    - relations are unioned by pointing duplicate relations to canonical;
    - conflicting attributes are stored source-qualified rather than silently overwritten.
    """
    ocel = deep_copy_ocel(ocel)
    ocel = ensure_audit(ocel)
    ev = ocel.events.copy()
    rel = ocel.relations.copy()

    if canonical_eid not in ev[EVENT_ID].values:
        return ocel
    if duplicate_eid not in ev[EVENT_ID].values:
        return ocel

    can = ev.loc[ev[EVENT_ID] == canonical_eid].iloc[0]
    dup = ev.loc[ev[EVENT_ID] == duplicate_eid].iloc[0]

    conflicts = {}
    merged_attrs = {}
    dup_source = str(dup.get("source", "duplicate_source"))

    for col in ev.columns:
        if col in {EVENT_ID, "original_timestamp", "original_activity"}:
            continue

        cv = can.get(col)
        dv = dup.get(col)

        cv_missing = pd.isna(cv)
        dv_missing = pd.isna(dv)

        if cv_missing and not dv_missing:
            merged_attrs[col] = dv
        elif not cv_missing and not dv_missing and str(cv) != str(dv):
            conflicts[col] = {"canonical": str(cv), "duplicate": str(dv)}
            merged_attrs[f"{col}__{dup_source}"] = dv

    for col, val in merged_attrs.items():
        ev.loc[ev[EVENT_ID] == canonical_eid, col] = val

    # Union relations by re-pointing duplicate relations.
    rel.loc[rel[REL_EVENT] == duplicate_eid, REL_EVENT] = canonical_eid
    rel = rel.drop_duplicates()

    # Remove duplicate event row.
    ev = ev[ev[EVENT_ID] != duplicate_eid].copy()

    ocel.events = ev
    ocel.relations = rel

    ocel.audit_records.append(
        {
            "canonical_event_id": canonical_eid,
            "source_event_ids": [canonical_eid, duplicate_eid],
            "merge_rule": merge_rule,
            "confidence": confidence,
            "reason": reason,
            "discarded_conflicts": conflicts,
        }
    )
    return ocel

def make_tie_breaker(events_df):
    ev = events_df.set_index(EVENT_ID)

    def key(eid):
        row = ev.loc[eid]
        seq = row.get("source_seq", 0)
        try:
            seq = 0 if pd.isna(seq) else int(seq)
        except Exception:
            seq = 0
        return (
            row.get("original_timestamp"),
            SOURCE_PRIORITY.get(row.get("source"), 99),
            seq,
            str(row.get("source_event_key", "")),
            eid,
        )

    return key


def deterministic_total_order(ocel, precedence):
    """
    Converts a partial order into a deterministic total order.
    The total order is reproducible, not proof of physical truth.
    """
    ocel = deep_copy_ocel(ocel)
    ev = ocel.events.copy()
    nodes = set(ev[EVENT_ID])

    deps = {node: set() for node in nodes}
    for pred, succ in precedence:
        if pred in nodes and succ in nodes:
            deps[succ].add(pred)

    sorter = TopologicalSorter(deps)
    try:
        sorter.prepare()
    except CycleError as exc:
        raise ValueError("Ordering constraints contain a cycle.") from exc

    tie_breaker = make_tie_breaker(ev)
    ordered = []

    while sorter.is_active():
        ready = sorted(sorter.get_ready(), key=tie_breaker)
        for node in ready:
            ordered.append(node)
            sorter.done(node)

    rank = {eid: idx for idx, eid in enumerate(ordered)}
    ev["order_rank"] = ev[EVENT_ID].map(rank).astype(int)
    ocel.events = ev
    return ocel


def apply_ordering_and_timedelta(ocel, precedence, scenario_name):
    """
    Uses PM4Py sorting and index-based timedelta only after order rules are established.
    Original timestamp is restored after creating adjusted_timestamp.
    """
    ocel = deterministic_total_order(ocel, precedence)

    try:
        ocel = pm4py.ocel_sort_by_additional_column(ocel, "order_rank")
    except TypeError:
        ocel.events = ocel.events.sort_values("order_rank").copy()

    # Ensure the business timestamp is the original before applying synthetic offsets.
    ocel.events[TIMESTAMP] = ocel.events["original_timestamp"]

    try:
        ocel = pm4py.ocel_add_index_based_timedelta(
            ocel,
            timestamp_column=TIMESTAMP,
            index_column="order_rank",
            timedelta_unit="us",
        )
    except TypeError:
        # API-independent fallback with the same intent.
        ocel.events = ocel.events.sort_values("order_rank").copy()
        ocel.events[TIMESTAMP] = ocel.events["original_timestamp"] + pd.to_timedelta(
            ocel.events["order_rank"],
            unit="us",
        )

    ocel.events["adjusted_timestamp"] = ocel.events[TIMESTAMP]
    ocel.events[TIMESTAMP] = ocel.events["original_timestamp"]
    ocel.events["ordering_scenario"] = scenario_name
    return ocel


def filter_ocel_by_events(ocel, eids):
    """Creates a subset OCEL for controlled merging."""
    eids = set(eids)
    subset = deep_copy_ocel(ocel)
    subset.events = ocel.events[ocel.events[EVENT_ID].isin(eids)].copy()
    subset.relations = ocel.relations[ocel.relations[REL_EVENT].isin(eids)].copy()
    object_ids = set(subset.relations[REL_OBJECT])
    subset.objects = ocel.objects[ocel.objects[OBJECT_ID].isin(object_ids)].copy()
    return subset


def replace_events_from_subset(full_ocel, subset_ocel, original_subset_eids):
    """Replaces the original subset with the merged subset."""
    full = deep_copy_ocel(full_ocel)
    original_subset_eids = set(original_subset_eids)

    keep_events = full.events[~full.events[EVENT_ID].isin(original_subset_eids)]
    full.events = pd.concat([keep_events, subset_ocel.events], ignore_index=True)

    keep_relations = full.relations[~full.relations[REL_EVENT].isin(original_subset_eids)]
    full.relations = pd.concat(
        [keep_relations, subset_ocel.relations],
        ignore_index=True,
    ).drop_duplicates()

    full.objects = pd.concat(
        [full.objects, subset_ocel.objects],
        ignore_index=True,
    ).drop_duplicates(subset=[OBJECT_ID])

    return full


def pm4py_merge_candidate_subset(ocel, candidate_eids):
    """
    Aggressive PM4Py merge, restricted to a candidate subset.
    This avoids applying a global merge to e05/e14 or other protected events.
    """

        "Aggressive PM4Py merge may collapse semantically distinct same-time events. "
        "Use only with candidate-group inspection and audit.",
        stacklevel=2,

    subset = filter_ocel_by_events(ocel, candidate_eids)

    try:
        merged_subset = pm4py.ocel_merge_duplicates(subset, keep_first=True)
    except TypeError:
        merged_subset = pm4py.ocel_merge_duplicates(subset)

    return replace_events_from_subset(ocel, merged_subset, candidate_eids)

## 7. Sensitivity analysis

### Raw dataset

Expected event count: 17. Expected E2O relation count: 44.

In the **Order-flattened DFG**, O1 shows many same-time parallel branches: duplicate pick observations, two pack observations, two dispatch observations, duplicate invoice issuance, and multiple payment captures plus an ERP payment summary. The DFG may suggest excessive concurrency or rework.

In the **Item-flattened DFG**, I1 appears picked twice if e03 and e04 are both retained, then packed. I2 appears picked once by e05. Pack e06 relates to both items, but e07 lacks item relations, creating an ERP-level pack node disconnected from item detail.

In the **Payment-flattened DFG**, M1 has `Authorize Payment  Capture Payment`. M2 has a standalone `Capture Payment` because no authorization is present. e15 has no Payment object, so payment flattening either drops it or shows an orphan invoice-level capture.

In **OC-DFG edges and frequency metrics**, duplicate observations inflate frequencies. `Pick Item  Pack Package`, `Pack Package  Dispatch Package`, `Issue Invoice  Authorize Payment`, and `Capture Payment` frequencies are overstated because multiple system observations are treated as repeated process steps.

**ET–OT weights** are distorted: `Pick Item  Item` is inflated by e03/e04; `Pack Package  Item` is driven mainly by WMS e06; `Capture Payment  Payment` is incomplete because ERP e15 lacks Payment objects.

**OTG relations** show stronger-than-true associations between I1 and P1 due to duplicate pick relations, and strong V1/M1/V1/M2 associations through payment events. Duplicate invoice events reinforce O1/V1 unnecessarily.

Apparent rework may appear as repeated `Pack Package`, repeated `Dispatch Package`, repeated `Issue Invoice`, and repeated `Capture Payment`. Lifecycle duration measurements are unstable because many events share second-level timestamps. If ingestion time is used, ERP summaries appear artificially delayed by one minute.

### Conservative dataset

Expected event count: 15. Expected E2O relation count: 39.

The **Order-flattened DFG** becomes cleaner: one pick for I1, one pick for I2, two qualified pack events, two qualified dispatch events, one invoice event, and separate payment captures plus ERP summary. The order lifecycle is easier to read, but abstraction-level pairs can still look like repeated activities if refined labels are ignored.

The **Item-flattened DFG** improves substantially: I1 is picked once, I2 is picked once, and both feed packing. The ERP pack summary still does not connect to items, which is correct because it lacks item relations.

The **Payment-flattened DFG** preserves M1 and M2 separately. M1 has authorization and capture; M2 has capture only. e15 remains outside payment-object flattening unless explicitly modeled as an invoice-level summary.

**OC-DFG frequencies** become more truthful. `Pick Item  Pack Package` is no longer inflated by e04. `Issue Invoice  Authorize Payment` is no longer inflated by e16. However, retaining e06/e07 and e08/e09 can still create two pack or dispatch nodes unless refined labels are used in analysis.

**ET–OT weights** improve: `Pick Item  Item` is no longer duplicated for I1. `Capture Payment  Payment` reflects PSP events only, while ERP summary is excluded from Payment-object weights.

**OTG relations** retain the correct object topology but with lower duplicate edge weights. I1-P1, I2-P1, P1-D1, O1-V1, V1-M1, and V1-M2 remain.

Apparent rework is reduced but not eliminated if analysts flatten on harmonized activity only. The pair e13/e14/e15 may still look like repeated capture unless payment object qualifiers are used.

### Evidence-based merge dataset

Expected event count: 14 if e07 is merged into e06. Expected E2O relation count: about 37.

The **Order-flattened DFG** has one pack event instead of two. This removes apparent pack rework and simplifies `Pick Item  Pack Package  Dispatch Package`.

The **Item-flattened DFG** remains mostly correct because e06 already carries I1 and I2. The loss is abstraction: ERP pack status no longer appears as a separate event.

The **Payment-flattened DFG** is unchanged from conservative because e13, e14, and e15 are retained.

**OC-DFG frequencies** for packing and pack-to-dispatch edges decrease. This may improve frequency realism but may also hide the ERP control point.

**ET–OT weights** for `Pack Package  Item` become based on one event, reducing weight but not changing topology.

**OTG relations** remain stable, but edge weights involving P1 and O1 may decrease.

Performance measurements from pack to dispatch become shorter and less variable if the ERP summary previously introduced an apparent second pack timestamp or ingestion lag. The main damage is loss of abstraction-level audit visibility.

### Aggressive library merge dataset

Expected guarded event count: 12. An unguarded aggressive merge could be lower and would likely drop e05 or e14, which is prohibited.

The **Order-flattened DFG** becomes artificially simple: one pack, one dispatch, one invoice, and fewer capture events. This may look clean but hides carrier acceptance, warehouse release, ERP summary, and payment aggregation semantics.

The **Item-flattened DFG** is similar to evidence-based for picks and packing, but dispatch semantics are degraded.

The **Payment-flattened DFG** is damaged if e15 is merged into e13. The ERP invoice-level summary becomes attached to M1 only, even though it may summarize both M1 and M2. M2 remains separate, but the invoice-level reconciliation event is lost.

**OC-DFG frequencies** are undercounted. `Dispatch Package  Handover to Carrier` may appear once with a merged dispatch event, hiding that carrier acceptance, not warehouse release, directly precedes handover. `Capture Payment` frequency is reduced in a way that can hide partial-payment complexity.

**ET–OT weights** become misleading: `Capture Payment  Payment` may appear stronger for M1 if e15 is merged into e13, while ERP invoice-level posting disappears from V1-only analysis.

**OTG relations** may overstate V1-M1 if e15 is absorbed into e13, while V1-M2 remains only through e14.

Apparent rework is minimized artificially, but at the cost of semantic truth. Performance metrics may look faster because concurrent observations and abstraction delays are collapsed.

**Concrete edges or patterns whose interpretation changes:**

1. `Pick Item  Pack Package` in Order flattening: inflated by e03/e04 in raw; cleaner in conservative.
2. `Pick Item (I1)  Pack Package` in Item flattening: duplicate pick edge disappears after merging e03/e04.
3. `Pack Package  Dispatch Package`: raw can create cross-product from e06/e07 and e08/e09; conservative preserves qualifiers; aggressive collapses them.
4. `Dispatch Package  Handover to Carrier`: changes depending on whether e08/e09 are separate or merged.
5. `Issue Invoice  Authorize Payment`: duplicate invoice events inflate raw frequency; conservative merge corrects it.
6. `Authorize Payment  Capture Payment (M1)`: stable semantically, but aggressive merging of e15 into e13 can add invoice-summary meaning to the PSP capture.
7. `Capture Payment  Capture Payment` apparent rework: raw may show repeated captures due e13/e14/e15; conservative distinguishes them; aggressive may hide the issue.
8. `Dispatch Package  Confirm Delivery`: performance interpretation changes if dispatch is represented by warehouse release, carrier acceptance, or a merged ambiguous dispatch event.

## 8. Audit trail and reversibility

Use an append-only provenance schema, for example an `ocel_audit` table:

| Field | Meaning |
|---|---|
| `audit_id` | Unique audit row identifier. |
| `canonical_event_id` | Event retained in the cleaned OCEL. |
| `source_event_ids` | All raw source event identifiers contributing to the canonical event. |
| `source_systems` | ERP, WMS, SCANNER, CARRIER, PSP, BILLING, etc. |
| `merge_rule` | Exact technical drop, verified physical merge, summary merge, label refinement, ordering rule. |
| `rule_version` | Versioned rule set or model version. |
| `reviewer` | Human reviewer or automated pipeline identifier. |
| `original_activity` | Harmonized activity before refinement. |
| `refined_activity` | Qualified activity after cleaning. |
| `original_timestamp` | Raw business timestamp, never overwritten. |
| `adjusted_timestamp` | Synthetic deterministic timestamp, if created. |
| `ordering_rule` | Domain, lifecycle, source sequence, source semantics, ingestion fallback, stable fallback. |
| `attributes_retained` | JSON mapping source event to retained attribute names/values. |
| `discarded_conflicts` | JSON of conflicting values not selected as primary. |
| `relations_retained` | Source-specific E2O relation lineage. |
| `confidence` | High, medium, low. |
| `reason` | Human-readable justification. |

An analyst can reconstruct the raw view by expanding each canonical event using `source_event_ids`, restoring original timestamps and activities from the audit table, recreating source-specific relations from relation lineage, and removing synthetic `adjusted_timestamp` or `order_rank` fields. If the raw event rows are archived rather than physically deleted, reconstruction is exact. If duplicate rows are physically removed, the audit table must store enough attribute and relation detail to regenerate them.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments**  
   Failure: merging e13 and e14 because both share O1 and V1.  
   Safeguard: require identical focal Payment object or payment payload; treat Payment object difference as a hard blocking key.

2. **Converting abstraction-level updates into false rework**  
   Failure: e07 or e15 appears as repeated pack/capture activity.  
   Safeguard: retain refined labels, record `derived_from`, and analyze abstraction-level events separately or with qualifiers.

3. **Ordering by ingestion time**  
   Failure: using `ingested_at` to assert business order, making ERP summaries appear one minute later.  
   Safeguard: use ingestion only for audit or last-resort deterministic fallback; never as primary semantic order.

4. **Treating shared objects as proof of duplication**  
   Failure: merging e13/e14 or e08/e09 because `have_common_object=True`.  
   Safeguard: combine object-type-aware blocking, source semantics, payload comparison, and verified rules.

5. **Unioning incompatible E2O relations**  
   Failure: merging events with different object granularity, such as attaching item relations to an ERP summary that never had them.  
   Safeguard: store relation provenance; do not infer missing relations unless explicitly validated.

6. **Changing durations through synthetic microseconds**  
   Failure: adding microsecond offsets before semantic ordering and then measuring performance.  
   Safeguard: preserve `original_timestamp`; store synthetic order timestamps separately; report ties as ties.

7. **Losing source-authoritative attributes**  
   Failure: choosing ERP or Billing as canonical for e11/e16 and overwriting the other system’s authoritative fields.  
   Safeguard: source-qualified attribute columns and attribute-level provenance.

8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups**  
   Failure: global `drop_duplicates` or `merge_duplicates` collapses semantically distinct same-time events.  
   Safeguard: pre-check candidate groups, use subset merging, validate results, and require audit records.

9. **Assuming deterministic total order proves physical truth**  
   Failure: downstream mining treats the total order as ground truth.  
   Safeguard: store partial-order constraints and flag deterministic tie-breaks as non-semantic.

10. **Quarantine fatigue**  
   Failure: unresolved candidates are silently merged to make the log clean.  
   Safeguard: keep unresolved candidates in a quarantine view and require reviewer sign-off before destructive action.
