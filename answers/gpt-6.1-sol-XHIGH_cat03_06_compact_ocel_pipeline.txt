## 1. Modeling assumptions

The object types are exactly `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, with this capitalization. An event has one identifier regardless of how many objects participate in it. Payment amounts are numeric event attributes, measured in the unspecified monetary units of the narrative.

The E2O qualifier vocabulary describes an object's role in an event:

| Qualifier(s) | Meaning |
|---|---|
| `created_order`, `closed_order` | Order created or closed |
| `containing_order`, `added_item` | Order receiving an item, and that item |
| `affected_order` | Order involved in reservation or packing |
| `reserved_item` | Item whose stock is reserved |
| `packed_package`, `packed_item` | Package assembled, and item packed |
| `dispatched_package`, `dispatch_delivery` | Package dispatched, and delivery carrying it |
| `issued_invoice`, `billed_order` | Invoice issued, and order billed |
| `recorded_payment`, `credited_invoice` | Payment recorded, and invoice receiving the payment |
| `confirmed_delivery` | Delivery confirmed |

O2O relations are directed: Order → Item (`contains`), Package → Item (`packs`), Delivery → Package (`carries`), Invoice → Order (`bills`), and Payment → Invoice (`partially_settles`). Both payments are installments against V1. Together they settle it according to the narrative; using `partially_settles` for both does not mean the invoice remains unpaid after M2. No invoice face amount or allocation between Orders is invented.

The baseline preserves the participation stated in the narrative, plus one explicit modeling inference: packing P2 also affects O100 because P2 packs I2 and O100 contains I2. This relation is marked `relation:origin = "o2o_context"`; the other relations are marked `"narrative"`. The provenance column is an application annotation, not a mandatory OCEL 2.0 column.

Packing relates to Packages, Items, and their Orders. Dispatch relates to its Package and Delivery; confirmation relates only to its Delivery. Invoice issuance relates to V1 and both Orders. Payment recording relates only to its Payment and V1. Thus, dispatch, confirmation, and payment events have no direct Order or Item E2O links in this baseline. O2O paths retain their business context, but ordinary flattening does not automatically traverse those paths.

This policy keeps the event observations compact while making packing consistent across P1 and P2. Broader propagation would produce more complete Order lifecycles but also more copied events and stronger apparent interactions. Any additional propagation should produce a separate analytical OCEL, retaining original event IDs and recording derived roles, rules, and paths. It should not overwrite the baseline or label inferred links as narrative observations.

The pipeline assumes the named PM4Py top-level APIs are available and the stated OCEL constructor accepts `o2o`. Its constructor call is isolated below. For a release with a different constructor, adapt that boundary to supply the same four tables, for example by assigning the O2O table through that release's supported OCEL field after construction. Do not discard O2O or replace object relations with artificial cases. Flattening is normalized to a pandas DataFrame; graph and model return values are retained without assuming a particular release's internal schema. Standard discovery generally uses E2O participation and activity labels; it must not be assumed to enforce qualifiers, payment amounts, or O2O semantics.

## 2. Complete Python pipeline

```python

import pm4py
from pm4py.objects.ocel.obj import OCEL

EID = "ocel:eid"
ACT = "ocel:activity"
TS = "ocel:timestamp"
OID = "ocel:oid"
OTYPE = "ocel:type"
OID2 = "ocel:oid_2"

ORIGIN = "relation:origin"

# Amounts belong to events, not to a separate object type.
event_rows = [

    ("e10", "Dispatch Package", "2026-04-06T10:15:00Z", None),

]
events = pd.DataFrame(
    event_rows, columns=[EID, ACT, TS, "payment_amount"]
)
events[TS] = pd.to_datetime(events[TS], utc=True, errors="raise")
events["payment_amount"] = pd.array(
    events["payment_amount"], dtype="Float64"
)
events = events.sort_values([TS, EID], kind="mergesort").reset_index(drop=True)

objects = pd.DataFrame(
    [
        ("O100", "Order"), ("O200", "Order"),
        ("I1", "Item"), ("I2", "Item"), ("I3", "Item"),
        ("P1", "Package"), ("P2", "Package"),
        ("D1", "Delivery"), ("D2", "Delivery"),
        ("V1", "Invoice"),
        ("M1", "Payment"), ("M2", "Payment"),
    ],
    columns=[OID, OTYPE],
)

# These are directed, static business associations.
o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"),
        ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"),
        ("P1", "I3", "packs"),
        ("P2", "I2", "packs"),
        ("D1", "P1", "carries"),
        ("D2", "P2", "carries"),

        ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"),
        ("M2", "V1", "partially_settles"),
    ],
    columns=[OID, OID2, QUAL],
)

# One event ID is reused across its participating objects.
# Only e08 -> O100 is inferred operational context in this baseline.
e2o_spec = {
    "e01": [("O100", "created_order")],
    "e02": [("O100", "containing_order"), ("I1", "added_item")],
    "e03": [("O100", "containing_order"), ("I2", "added_item")],
    "e04": [("O200", "created_order")],
    "e05": [("O200", "containing_order"), ("I3", "added_item")],
    "e06": [
        ("O100", "affected_order"), ("O200", "affected_order"),
        ("I1", "reserved_item"), ("I3", "reserved_item"),
    ],
    "e07": [
        ("P1", "packed_package"),
        ("I1", "packed_item"), ("I3", "packed_item"),
        ("O100", "affected_order"), ("O200", "affected_order"),
    ],
    "e08": [
        ("P2", "packed_package"), ("I2", "packed_item"),
        ("O100", "affected_order"),
    ],
    "e09": [("P1", "dispatched_package"), ("D1", "dispatch_delivery")],
    "e10": [("P2", "dispatched_package"), ("D2", "dispatch_delivery")],
    "e11": [
        ("V1", "issued_invoice"),
        ("O100", "billed_order"), ("O200", "billed_order"),
    ],
    "e12": [("M1", "recorded_payment"), ("V1", "credited_invoice")],
    "e13": [("D1", "confirmed_delivery")],
    "e14": [("D2", "confirmed_delivery")],
    "e15": [("M2", "recorded_payment"), ("V1", "credited_invoice")],
    "e16": [("O200", "closed_order")],

            EID: eid,
            OID: oid,
            QUAL: qualifier,

        for oid, qualifier in links

assert objects[OID].is_unique, "Duplicate object IDs"

assert set(relation_keys[EID]) <= set(events[EID]), "Orphan E2O event"
assert set(relation_keys[OID]) <= set(objects[OID]), "Orphan E2O object"

# Repeat authoritative event metadata and object type in every E2O row.
relations = relation_keys.merge(

assert relations[[EID, ACT, TS, OID, OTYPE, QUAL]].notna().all().all()
assert relations[TS].dt.tz is not None
assert set(relations[EID]) <= set(events[EID])
assert set(relations[OID]) <= set(objects[OID])
assert set(relations[EID]) == set(events[EID]), "An event has no objects"
assert not relations.duplicated().any(), "Duplicate complete E2O rows"
assert not relations.duplicated([EID, OID, QUAL]).any(), "Duplicate E2O links"
# This model assigns one role per event-object pair.
assert not relations.duplicated([EID, OID]).any()

metadata_check = relations.merge(
    events[[EID, ACT, TS]].rename(
        columns={ACT: "expected_activity", TS: "expected_timestamp"}

    on=EID, how="left", validate="many_to_one",
)
assert metadata_check[ACT].eq(metadata_check["expected_activity"]).all()
assert metadata_check[TS].eq(metadata_check["expected_timestamp"]).all()

assert relations[OTYPE].eq(relations[OID].map(type_by_oid)).all()

assert o2o[[OID, OID2, QUAL]].notna().all().all()
assert set(o2o[OID]) <= set(objects[OID]), "Orphan O2O source"
assert set(o2o[OID2]) <= set(objects[OID]), "Orphan O2O target"
assert not o2o.duplicated([OID, OID2, QUAL]).any(), "Duplicate O2O links"
assert o2o[OID].ne(o2o[OID2]).all(), "Unexpected self-association"
expected_o2o_types = {
    "contains": ("Order", "Item"),
    "packs": ("Package", "Item"),
    "carries": ("Delivery", "Package"),
    "bills": ("Invoice", "Order"),
    "partially_settles": ("Payment", "Invoice"),
}
for source, target, qualifier in o2o.itertuples(index=False, name=None):
    assert (type_by_oid[source], type_by_oid[target]) == expected_o2o_types[qualifier]

assert (len(events), len(objects), len(relations), len(o2o)) == (17, 12, 35, 12)
payments = events.loc[events[ACT].eq("Record Payment")]
assert len(payments) == 2 and payments["payment_amount"].sum() == 250.0
assert events.loc[events[ACT].ne("Record Payment"), "payment_amount"].isna().all()

# Constructor compatibility boundary: adapt only this construction boundary
# if a PM4Py release needs a different way to receive the same O2O table.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)
print("Activity frequencies, counted once per event:")
print(events[ACT].value_counts().sort_index())
print("Object-type frequencies, counted once per object:")
print(objects[OTYPE].value_counts().sort_index())
print("Object types:", pm4py.ocel_get_object_types(ocel))
print("Activities per object type:", pm4py.ocel_object_type_activities(ocel))

# These are projections of one OCEL, not independently constructed logs.
flattened_logs = {}
dfg_results = {}
log_skeletons = {}
flat_keys = {
    "activity_key": "concept:name",
    "timestamp_key": "time:timestamp",
    "case_id_key": "case:concept:name",
}
for object_type in ("Order", "Package", "Delivery", "Invoice"):
    flat = pm4py.ocel_flattening(ocel, object_type)
    if not isinstance(flat, pd.DataFrame):
        flat = pm4py.convert_to_dataframe(flat)
    flat = flat.copy()
    assert set(flat_keys.values()) <= set(flat.columns)
    flat["time:timestamp"] = pd.to_datetime(
        flat["time:timestamp"], utc=True, errors="raise"
    )
    # There are no timestamp ties in this example. Sorting is not a causal claim.
    flat = flat.sort_values(
        ["case:concept:name", "time:timestamp"], kind="mergesort"
    ).reset_index(drop=True)
    flattened_logs[object_type] = flat
    edges, starts, ends = pm4py.discover_dfg(flat, **flat_keys)
    dfg_results[object_type] = {
        "edges": edges,
        "start_activities": starts,
        "end_activities": ends,
    }
    log_skeletons[object_type] = pm4py.discover_log_skeleton(
        flat, noise_threshold=0.0, **flat_keys
    )
    print(object_type, "DFG:", dfg_results[object_type])
    print(object_type, "log skeleton:", log_skeletons[object_type])

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)
object_centric_results = {
    "ocdfg": ocdfg,
    "otg": otg,
    "etot": etot,
    "ocpn": ocpn,
    "interactions": interactions,
}
print("Object interactions summary:")
print(interactions)

# pm4py.view_ocpn(ocpn)
```

## 3. Data-model audit

There are 17 events, 12 objects, 35 E2O links, and 12 directed O2O links. Of the E2O links, 34 come directly from the narrative and one is labeled operational context.

| Object type | Objects | Count |
|---|---|---:|
| Order | O100, O200 | 2 |
| Item | I1, I2, I3 | 3 |
| Package | P1, P2 | 2 |
| Delivery | D1, D2 | 2 |
| Invoice | V1 | 1 |
| Payment | M1, M2 | 2 |

The cardinalities below describe this dataset, not universal business constraints.

| O2O qualifier | Direction and observed cardinality | Links |
|---|---|---:|
| `contains` | Order → Item, 1:N; O100 → I1/I2, O200 → I3 | 3 |
| `packs` | Package → Item, 1:N; P1 → I1/I3, P2 → I2 | 3 |
| `carries` | Delivery → Package, observed 1:1; D1 → P1, D2 → P2 | 2 |
| `bills` | Invoice → Order, 1:N; V1 → O100/O200 | 2 |
| `partially_settles` | Payment → Invoice, N:1; M1/M2 → V1 | 2 |

| Activity | Events | Object types touched by each event |
|---|---:|---|
| Create Order | 2 | Order |
| Add Item | 3 | Order, Item |
| Reserve Stock | 1 | Order × 2, Item × 2 |
| Pack Package | 2 | Package × 1, Order × 1 or 2, Item × 1 or 2 |
| Dispatch Package | 2 | Package × 1, Delivery × 1 |
| Issue Invoice | 1 | Invoice × 1, Order × 2 |
| Record Payment | 2 | Payment × 1, Invoice × 1 |
| Confirm Delivery | 2 | Delivery |
| Close Order | 2 | Order |

The Order link for packing P2 is the provenance-marked inference. The per-type E2O incidence totals are Order 14, Item 8, Package 4, Delivery 4, Invoice 3, and Payment 2; these sum to 35, not 17.

Especially consequential relation sets are:

- **e06:** one reservation involves O100, O200, I1, and I3. Splitting it into separate reservations would lose the stated shared operation.
- **e07:** one packing event involves P1, I1, I3, O100, and O200. It joins two Order contexts into one Package context.
- **e08:** P2 contains I2, so O100 spans P1 and P2. The added Order context creates a second packing occurrence in O100's projection.
- **e11:** V1 is issued once for both Orders. Two Order projections must not be interpreted as two issued invoices.
- **e12/e15:** two distinct Payments connect to the same V1. They are two events and two Payment objects, rather than a duplicated payment event or two invoices.

These associations expose convergence of several Orders into P1 and V1, and divergence of O100's items into two Packages and Deliveries. Their meaning depends on distinguishing one shared event from several object-specific observations of it.

## 4. Expected flattened behavior

With the specified relations and unique timestamps, the activity sequences are deterministic:

| Projection and case(s) | Trace shape |
|---|---|
| Order: O100 | Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Pack Package → Issue Invoice → Close Order |
| Order: O200 | Create Order → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order |
| Package: P1, P2 | Pack Package → Dispatch Package |
| Delivery: D1, D2 | Dispatch Package → Confirm Delivery |
| Invoice: V1 | Issue Invoice → Record Payment → Record Payment |

**Order.** There are 14 flattened event occurrences representing 11 distinct original events. The shared events e06, e07, and e11 are each copied into both Order cases. O100 additionally sees e08 for its second Package. Expected DFG edges and frequencies are:

| Order DFG edge | Frequency |
|---|---:|
| Create Order → Add Item | 2 |
| Add Item → Add Item | 1 |
| Add Item → Reserve Stock | 2 |
| Reserve Stock → Pack Package | 2 |
| Pack Package → Pack Package | 1 |
| Pack Package → Issue Invoice | 2 |
| Issue Invoice → Close Order | 2 |

Both starts are Create Order and both ends are Close Order. Dispatch, delivery confirmation, and payment recording are absent. Therefore Issue Invoice → Close Order is adjacency in this projection despite several intervening business events. The Add Item and Pack Package self-loops reflect different Items and Packages in O100; they do not establish rework. Counting two reservations or two invoices from this flattened log would count shared events twice. The projection also hides that O100 and O200 share P1 and V1.

**Package.** P1 contains e07/e09 and P2 contains e08/e10. Pack Package → Dispatch Package has frequency 2, with packing as the start and dispatch as the end. No event is copied between the two Package cases, because each relevant event involves one Package. P1's packing is nevertheless the same underlying event that appears in both Order traces. Item addition/reservation, Delivery confirmation, Invoice, Payments, and Order closure are omitted. This view cannot establish that P1 mixes two Orders or that dispatch means delivered. Observed packing-to-dispatch intervals are one hour for P1 and one hour ten minutes for P2.

**Delivery.** D1 contains e09/e13 and D2 contains e10/e14. Dispatch Package → Confirm Delivery has frequency 2. No event is copied between Delivery cases. Dispatch events also appear in the Package projection, but this cross-projection reuse must not be counted as additional dispatches. Packing, Items, Orders, invoicing, and payment are absent. The simple activity shape hides consolidation and split fulfillment. The dispatch-to-confirmation intervals are three hours for D1 and 22 hours 45 minutes for D2; a frequency DFG alone does not show that difference.

**Invoice.** V1 contains e11/e12/e15. Issue Invoice → Record Payment and Record Payment → Record Payment each have frequency 1; issuance starts the case and the second recording ends it. There is one Invoice case, so no event is copied between Invoice cases. Its issue event also appears in both Order cases. The repeated payment activity represents M1 and M2, with amounts 100 and 150, rather than re-recording one Payment. Logistics and Order creation/closure are omitted. Although the event attributes retain payment amounts, a standard DFG or log skeleton does not calculate settlement or allocate money to O100 and O200.

The zero-noise log skeletons describe these small projections. For example, both Package traces contain one Pack Package before one Dispatch Package; both Delivery traces contain one dispatch before one confirmation. The Invoice sample contains one issuance and two payment recordings. The Order sample has one or two additions and packings. Constraints inferred from one or two cases are observations of this sample, not reliable universal rules or proof of causality.

Flattening on **Payment** would give M1: Record Payment and M2: Record Payment. Both are singleton traces, with no DFG edges. The Invoice sequence linking installments, their shared V1, settlement timing, and the Order contexts disappear. Payment objects remain useful for identity and attributes, but this baseline supplies too little Payment lifecycle to support substantial control-flow discovery.

## 5. Expected object-centric structures

**OC-DFG.** Activity nodes should be connected by directly-follows edges specific to object type. The Order, Package, Delivery, and Invoice edges should agree with the corresponding projections above. For Items, I1 and I3 follow Add Item → Reserve Stock → Pack Package, whereas I2 follows Add Item → Pack Package. Payment contributes Record Payment as a start/end activity with no Payment-specific succession edge.

The graph can therefore show packing as an intersection of Order, Item, and Package perspectives; dispatch links Package and Delivery perspectives; invoice issuance links Order and Invoice perspectives; and recording links Invoice and Payment perspectives. P1's multi-Order participation and V1's shared billing remain associations of the original shared events. Read event-based and object-incidence metrics separately: e06 is one event involving two Orders and two Items, while e07 is one event involving two Orders, two Items, and one Package. The two packing events involve three Order incidences but only two distinct Orders. These are different counting units. An OC-DFG does not automatically add Order delivery/payment edges by following O2O.

**OTG.** In an E2O-based object-type connectivity view, the observed cross-type connections are Order–Item, Order–Package, Item–Package, Package–Delivery, Order–Invoice, and Invoice–Payment. In particular, P1 connects O100 and O200 operationally at e07, and V1 connects both Orders at e11 and each Payment at its recording. Same-type interactions also exist between O100/O200 and I1/I3; a type graph may suppress or aggregate these as self-type connections. Type aggregation alone cannot distinguish P1 from P2 or express all cardinalities.

The explicit O2O table supplies the directed, qualified business links listed in the audit. If a release's OTG is built from O2O rather than E2O co-occurrence, use those five directed type relationships instead: there is no explicit Order → Package O2O row. In either representation, distinguish a co-participation edge from a qualified containment, billing, or settlement relation. Do not assume graph discovery preserves every qualifier or traverses every O2O path.

**ET–OT.** The event-type/object-type incidence graph should match the activity/type audit table. Pack Package is incident to Order, Item, and Package; Issue Invoice to Order and Invoice; Record Payment to Payment and Invoice. Confirm Delivery is incident only to Delivery under this policy. Where weights are provided, distinguish numbers of events, E2O incidences, and distinct objects. Two Record Payment events involve V1 once each and different Payment objects M1 and M2. This graph describes which types participate, not the sequence of their lifecycles or an allocation of the payments.

**Object-centric Petri net.** The discovered model should coordinate object-type lifecycles at the shared activity labels: Order/Item at addition and reservation; Order/Item/Package at packing; Package/Delivery at dispatch; Order/Invoice at issuance; and Invoice/Payment at recording. P1 demonstrates packing with two Orders and two Items, while P2 demonstrates one Order and one Item. Depending on miner/version, variable-arc annotations may express these multiplicities. V1 has one issuance shared by O100 and O200, followed by recordings of M1 and M2.

The exact places, silent transitions, loops, and variable arcs depend on the algorithm and options. Several nets can explain this small log; there is no uniquely determined net interpretation. A learned payment loop or repeated transition does not by itself encode the amounts 100/150, a balance guard, which Order received money, or a business rule requiring exactly two installments. Similarly, sequencing inferred from observed projections does not establish that every future Order must await the same shared operations.

**Object-interactions summary.** Inspect the summary as evidence of actual event co-participation, rather than assume it expands arbitrary O2O paths. O100 and O200 co-participate in e06, e07, and e11. I1 and I3 co-participate in e06/e07. At e07, P1 interacts with both Orders and both packed Items; at e09 it interacts with D1. V1 interacts with both Orders at issuance and with M1 at e12 and M2 at e15. M1 and M2 never co-participate in an event, and neither Payment directly co-participates with an Order in the baseline.

Some releases return event-level pair rows, others aggregate or expose directed pair representations; interpret counts accordingly and avoid counting both orientations as two business interactions. Co-participation can generate all pairs among an event's objects. It does not mean every such pair has a separate containment or monetary relation. The O2O table remains the explicit reference for those business associations.

## 6. Modeling alternatives

| E2O policy | Construction choice | Effect on discovery |
|---|---|---|
| Strict source-minimal | Keep all narrative participation, including both Orders at e06/e07/e11, but omit inferred e08 → O100. Dispatch remains Package/Delivery, confirmation Delivery, and payment Payment/Invoice. | 34 E2O rows. O100 has seven projected events and no Pack Package → Pack Package edge. Shipping and payments remain invisible in Order traces. P2's Order is recoverable through O2O, rather than direct event participation. |
| Full operational involvement | Explicitly model each shipping event with the Package's Items and their Orders; confirmations also include the carried Package. Relate payments to both billed Orders as invoice-account context, without assigning amounts to them. | Order and Item lifecycles gain shipping/confirmation events; Orders gain payment events. D1 operations are copied across O100 and O200, while D2 operations concern O100. Both payment events appear in both Order cases. Type incidence and interaction graphs become denser, and learned synchronization changes. These extra relations are declared modeling choices. |
| O2O-propagated analytical relations | Retain a baseline and derive a second OCEL with bounded rules, such as Delivery → Package → Item, then reverse `contains` to find affected Orders; or Payment → Invoice → Order for account context. Use derived qualifiers and provenance. | Results can resemble operational enrichment, but depend on the propagation rules. Invoice/account projections may acquire related operational events, and Order projections may acquire payments. The provenance makes their analytical origin inspectable. Original event counts remain 17; E2O incidences and flattened occurrences increase. |

These policies change observed projections and learned models while retaining the same Orders, contents, shipments, shared invoice, and payments. Full operational involvement declares participation as part of the chosen event model; analytical propagation explicitly derives it from other recorded relationships.

Propagation must respect roles and paths. Traversing the entire undirected connected component would eventually attach almost every event to almost every object because V1 connects both Orders. For example, D2 carries only P2/I2; a route through O100 → V1 → O200 must not turn its confirmation into an O200 shipment. Likewise, payment-to-Order context is not payment allocation. A useful narrower alternative is logistics-only enrichment, keeping financial events scoped to Invoice and Payment.

## 7. Failure modes

1. **Relation inflation.** Unbounded propagation creates unrelated event/object participation, larger counts, spurious synchronization, and misleading DFG edges. Use bounded, qualified rules and provenance.
2. **Missing direct E2O links.** Omitting the stated Order links at e06/e07/e11 loses the shared operations in Order projections. More generally, O2O paths do not guarantee a miner or flattening operation will include downstream events; deliberate omissions must be explained.
3. **Treating O2O propagation as observation.** A relationship path supports context, not proof that a source event recorded each reachable object. Preserve narrative links and identify inferred ones, including e08 → O100 here.
4. **Counting flattened shared events as independent executions.** e06, e07, and e11 appear in both Order cases. Summing flattened frequencies inflates physical event counts; generating new event IDs for the copies would also erase sharing.
5. **Ambiguous payment allocation.** V1 bills both Orders, but neither a per-Order invoice breakdown nor installment allocation is given. Assigning M1's 100 to O100 and M2's 150 to O200 would invent facts. Propagating each payment to both Orders must not double-count its amount.
6. **Overly short Payment traces.** One event per Payment gives no Payment DFG edges and little control-flow evidence. This does not mean the shared Invoice lifecycle has no installment process.
7. **Constructor/API version mismatch.** Different constructors, helper availability, graph schemas, or flattening return types can break execution. Adapt the API boundary while preserving the four tables, qualifiers, provenance, UTC timestamps, and stored results; do not silently skip required analyses.
8. **False total order for same-time events.** This example has no ties. In other data, sorting tied events by identifier or row order would invent precedence and DFG edges. A stable sort provides reproducibility, not causal order; handle ties according to an explicit concurrency policy.
9. **Broken referential integrity or repeated metadata.** Orphan IDs, nonunique object IDs, stale activity labels, and mismatched timestamps produce inconsistent lifecycles. Build relations by validated joins and check them against their authoritative tables.
10. **Duplicate relation rows.** Repeating an E2O link can duplicate an event within a case; repeating an O2O edge can inflate association summaries. Validate logical keys, not merely rows that differ in an incidental provenance field.
11. **Ignoring numeric semantics and role qualifiers.** Default activity-based discovery can treat both payment recordings identically and ignore qualifier distinctions. Neither a payment self-loop nor two `partially_settles` links establishes an allocation or a balance calculation. The total 250 is known, but no unstated currency or invoice breakdown should be added.
12. **Overgeneralizing the tiny sample.** A skeleton or Petri net learned from one or two cases may impose apparent mandatory activities, fixed counts, or sequences that are only sample facts. Discovery is not evidence of universal policy.
13. **Misreading static O2O as timed behavior.** The direction Package → Item means packing association; it is not a directly-follows edge. These O2O rows also have no validity intervals, so they do not describe historical changes in containment. Reversing their directions without adjusting traversal rules changes the meaning.
14. **Confusing projected adjacency with complete lifecycle.** Issue Invoice → Close Order in the Order DFG omits payments and delivery events. Package traces ending at dispatch do not establish successful delivery, and no Reserve Stock event for I2 establishes neither a reservation nor a stock violation.
