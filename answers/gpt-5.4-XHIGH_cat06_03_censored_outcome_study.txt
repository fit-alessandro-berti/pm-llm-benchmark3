## 1. Target definition
Primary formulation: predict `default_90d` among applications that are eventually activated under the observed historical policy. The prediction time is a pre-decision landmark, primarily the first 3 events of the case (which should correspond to `Application Started -> Identity/KYC Check -> Credit Review` after activity canonicalization). The horizon is binary default status within 90 days after `Account Activated`, with label observability requiring the external feed to have arrived by the analysis cutoff. The unit of analysis is one application prefix at one predeclared landmark. The primary population is applications that reach the landmark before any terminal pre-activation exit, and that later activate under the observed policy. The estimand is

`Pr(default_90d = 1 | prefix information available at landmark L, eventual activation under the historical policy regime in force at L)`.

This is operationally defensible because `default_90d` is actually defined only once an account is activated. It is statistically defensible because it does not invent labels for rejected, withdrawn, transferred, or still-open applications.

Credible alternative target: a competing-outcome target for all applications under the observed policy,

`Y ∈ {rejected, withdrawn, transferred, activated_nondefault90, activated_default90}`.

That answers a different question: whole-funnel pathway risk from an early prefix, not booked-account default risk conditional on activation. A stronger-assumption counterfactual target such as “default risk if every application were activated” is not chosen as primary because it requires untestable policy and selection assumptions.

## 2. Cohort construction
Build the study from the full event file, not from the current 21,600-row labeled export alone.

Inclusion rules:
- Start from all applications with `case:concept:name` whose first event falls between 2024-01-01 and 2025-12-31.
- Use only events with `time:timestamp <= 2026-02-15` for this extract.
- For a given prefix landmark, include only information timestamped at or before that landmark.

Primary-target inclusion at a fixed landmark:
- The case must have reached the landmark before `Rejected`, `Withdrawn`, `Transferred`, `Accepted`, `Contract Signed`, or `Account Activated`.
- The case must eventually activate under the observed policy.
- `default_90d` must be observable by the extract cutoff for evaluation of the primary target.

Primary-target exclusions from model fitting, but not from the source cohort:
- Rejected, withdrawn, and transferred applications: target undefined for the primary estimand.
- Still-open applications: activation status unresolved at extract.
- Activated applications with no observable 90-day label by extract: retained for maturity and missing-label analysis, not relabeled as non-default.

As-of rules:
- Feature freeze is at the case-specific prefix time, never at extraction time.
- Safe full-maturity date for an activated account is `activation_time + 90 days + 35 days <= 2026-02-15`, so a conservative fully mature activation cutoff is 2025-10-13.
- If `label_available_at` is after 2026-02-15, the label is unavailable for this extract even if the 90-day horizon has ended.

Cohort-flow table for the 48,000 applications:

| Source cohort state at extract | Count | Status for primary target | Interpretation |
|---|---:|---|---|
| Activated with observed `default_90d=0` | 18,900 | Labeled primary cohort | Observable non-default among activated accounts |
| Activated with observed `default_90d=1` | 2,700 | Labeled primary cohort | Observable default among activated accounts |
| Rejected | 9,100 | Excluded from primary label set | Competing terminal pathway; not “non-default” |
| Withdrawn | 5,700 | Excluded from primary label set | Competing terminal pathway; not exposed to credit |
| Transferred | 2,900 | Excluded from primary label set | Off-platform continuation / competing pathway; downstream outcome only partly linkable |
| Still open at extract | 5,100 | Unresolved for primary target | Ordinary right censoring for the all-application pathway question |
| Activated but no observable 90-day label by extract | 3,600 | Unlabeled activated cohort | Mixture of not-yet-mature, delayed, and permanently missing outcome feeds |
| Total | 48,000 | Source cohort | Must be the accounting base for every analysis |

Within the 3,600 activated-but-unlabeled cases, the implementation should split cases into at least two operational subgroups: `not yet mature` (`activation_time > 2025-10-13`) and `overdue/missing label despite maturity` (`activation_time <= 2025-10-13` but no label observed by extract).

## 3. Censoring and missing-label strategy
The study should separate five mechanisms that are often incorrectly collapsed into one “missing label” bucket.

Ordinary right censoring:
- Still-open applications are unresolved process instances by 2026-02-15.
- They are not negative examples.
- They matter directly for the alternative all-application competing-outcome formulation.

Delayed labels:
- Some activated accounts have not completed `90 days after activation + external feed lag` by 2026-02-15.
- These are administratively immature labels, not permanent missingness.

Selection through activation:
- This is not censoring.
- For the primary estimand, the outcome is defined only within the subpopulation that activates under the observed policy.
- Rejected and withdrawn cases should therefore remain outside the labeled primary outcome set.

Transfer:
- Under the primary formulation, transfer ends observation within the lender’s own booking process, so the primary target is undefined there.
- Under the alternative all-application formulation, transfer is a competing pathway.
- In sensitivity analysis, linked transfers can be followed across identifiers when the linkage table exists, but the 60% link rate means representativeness of linked transfers is only partially checkable.

Permanently missing outcome feeds:
- Mature activated cases with no label by extract, especially partner-originated cases, are not ordinary censoring.
- They are outcome missingness in a selected subpopulation and may be informative.

Primary analysis strategy:
- Fit and evaluate the primary booked-account default model only on activated cases with observed mature labels.
- Report it explicitly as a model for historically activated accounts, not for all applications.
- Keep a separate audit table for activated mature cases whose outcome feed is missing, stratified by `source_system`, channel, region, requested amount, and calendar regime.

Sensitivity analyses:
- Inverse-probability-of-label-observation weighting among mature activated cases, using only pre-prefix covariates plus known operational variables such as `source_system` and partner channel.
- Pattern-mixture or bound analysis for overdue missing labels, for example best case (all missing are non-default), worst case (all missing are default), and a partner-specific delta adjustment.
- Secondary all-application competing-outcome model in which `rejected`, `withdrawn`, `transferred`, `activated_nondefault90`, and `activated_default90` are distinct outcomes.
- Transfer follow-up sensitivity: treat transferred cases as terminal at transfer in the main pathway analysis, then rerun on the linked 60% to quantify how much downstream activation/default alters conclusions.

Assumption status:
- Empirical feed-delay distribution is partially testable from observed `label_available_at` among labeled cases.
- Whether missing outcome feeds are conditionally ignorable after observed covariates is fundamentally not testable from these data alone.
- Whether linked transfers are representative of unlinked transfers is only partially testable by comparing observed pre-prefix covariates.
- Any “default if activated” target for rejected or withdrawn cases is counterfactual and fundamentally untestable without much stronger assumptions.

## 4. Prefix extraction
Use predeclared landmarks and enforce them case by case.

Fixed event-count prefixes:
- Primary fixed prefix: first `k=3` events after activity canonicalization, intended to capture the first `Credit Review` entry.
- Sensitivity landmarks: `k=2` and `k=5`.
- A case with fewer than `k` events by its terminal event or by extract is not padded with future information; it is excluded from that `k`-specific cohort and may still appear in a smaller-`k` or time-based cohort.
- Cases whose first `k` events already include `Accepted`, `Rejected`, `Withdrawn`, `Transferred`, `Contract Signed`, or `Account Activated` are excluded from the pre-decision `k`-prefix cohort because the landmark is already contaminated by downstream resolution.

Elapsed-time prefixes:
- Build parallel time-based cohorts such as `24 hours`, `72 hours`, and `7 days` after case start.
- Include only events with `time:timestamp <= start_time + t`.
- If a case terminates before `t`, it is not “completed” with future events; it simply is not at risk for that landmark.

Repeated document loops:
- Preserve them rather than collapsing them away.
- Rework count, number of returns to `Credit Review`, and timing between loop iterations are useful prefix features.

Activity renaming and duplicate events:
- Apply a canonical old-to-new activity mapping before any prefixing, variant extraction, or DFG discovery.
- Deduplicate exact or near-exact migration duplicates using a deterministic rule such as same case, canonical activity, timestamp, resource, and source system.
- Keep an audit count of dropped duplicates because migration-period duplication itself is a drift signal.

## 5. Process-aware features
Static case attributes available at or before start:
- `case:channel`, `case:region`, `case:requested_amount`, `source_system`, start month, start weekday, and a pre/post-2025-07-01 policy-regime indicator.

Prefix-derived control-flow features:
- Current activity at the landmark.
- Prefix length, number of unique activities, counts of `Request Documents`, counts of `Credit Review`, number of review re-entries, whether KYC was repeated, and variant or direct-follows pattern indicators.

Prefix-derived timing features:
- Elapsed time from start to landmark.
- Inter-event gap statistics within the prefix.
- Time since last `risk_score` update.
- Calendar timing such as weekend or after-hours handling if the timestamps support it.

Prefix-derived resource and queue features:
- Number of distinct resources involved by the landmark.
- Handoff count between resources.
- Current reviewer or queue owner if present before the landmark.

Features requiring historical reference data and strict time filtering:
- Reviewer prior processed-case count as of the event time, reconstructed from earlier cases only.
- Rolling queue pressure in the same channel/region at the prefix timestamp.
- Trailing mature activation/default rates by channel, region, or source system, computed only from cases whose labels were already observable before the prefix timestamp.

Risk-score handling:
- Keep the last observed `risk_score` up to the landmark, the first observed score, the number of score updates, and the within-prefix delta.
- Never forward-fill a later score backward into an earlier prefix.

Not valid as predictive features:
- `final_limit`, `decision_reason`, `collection_status`, `default_90d`, and `label_available_at`.

## 6. Leakage audit
| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision | Only valid after acceptance/rejection outcome is known; never valid at early prefix | Drop | Directly encodes downstream underwriting result |
| `decision_reason` | Appears at or after accept/reject | Only available after the decision event | Drop | Post-decision explanation leaks selection outcome |
| `collection_status` | Updated after activation and can directly reveal delinquency/default | Never valid for an origination-prefix model | Drop | Near-direct label leakage |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | Event presence itself reveals the future path | Keep only rows with `time:timestamp <= prefix_time`; drop all later rows | Drop post-prefix events | The event log contains post-prediction activities |
| `documents_total` | Nightly snapshot may include documents uploaded later on the same day than the nominal prediction time | Use only if a real snapshot timestamp exists and is strictly before the prefix time; otherwise do not use for sub-day landmarks | Repair or drop | Same-day look-ahead is likely |
| Updated `risk_score` | Later score updates may be inadvertently carried back into earlier rows | Use the last score observed at or before the prefix time; keep update count and delta only from within-prefix values | Keep after repair | Time-local risk information is valid and useful |
| Resource experience | Stored at extraction time rather than event time | Reconstruct from prior cases/events only; if not reconstructable, exclude | Repair or drop | Extraction-time experience includes future work history |
| `label_available_at` | Encodes label maturity and partner-feed behavior | Use only for cohorting, maturity, and missingness analysis; never as predictor | Drop as predictor, keep for audit | Observation-process leakage |
| `default_90d` | Target value repeated on events when known | Use only in the case-level label table after maturity checks | Drop as predictor | Direct target leakage |

The audit should be executed before every train/validation/test build, not once globally.

## 7. Validation design
The primary split must be temporal by case start time. A random split is misleading because it mixes pre- and post-2025-07-01 policy regimes, mixes pre- and post-2025-10-15 migration vocabulary and duplicate patterns, and lets later operational definitions influence earlier training folds. It also obscures label-maturity imbalance, because late-start cases are much more likely to have unobserved activated outcomes at this extract.

Recommended backtesting design:
- Training window: case starts from 2024-01-01 through 2025-03-31.
- Validation/tuning window: case starts from 2025-04-01 through 2025-06-30.
- Locked primary test window: case starts from 2025-07-01 through 2025-09-30.
- Post-migration structural audit window: case starts from 2025-10-15 through 2025-12-31, but do not claim primary `default_90d` performance there yet because those accounts cannot be fully matured by the 2026-02-15 extract.

Evaluation rules:
- Evaluate the primary target only on activated cases in each holdout whose labels are observed by extract.
- Report the number and composition of activated holdout cases excluded from outcome evaluation because they are immature or feed-missing.
- Recalibrate probabilities separately for the pre- and post-2025-07-01 regime if calibration drift is material.

Metrics for the primary target:
- PR-AUC and ROC-AUC because the default rate among labeled activated accounts is about 12.5%.
- Brier score or log loss for overall probabilistic accuracy.
- Calibration slope/intercept, reliability curves, and expected calibration error.
- Subgroup performance by channel, region, source system/partner origin, requested-amount bands, and policy regime.

Metrics and diagnostics for missingness and drift:
- Label-observation rate among mature activated accounts.
- Duplicate-event rate and activity-name drift around 2025-10-15.
- Variant/DFG drift between train, validation, and later windows.
- Feature missingness and distribution shift by split.

For the secondary all-application competing-outcome formulation, use censoring-aware pathway metrics such as cumulative-incidence Brier score or cause-specific discrimination, but do not replace the primary temporal split with a random split.

## 8. Limitations and decision-use boundary
This study can claim predictive association for `default_90d` among applications that historically became activated under the lender’s observed policy. It cannot claim the counterfactual default risk each rejected, withdrawn, transferred, or still-open applicant would have shown if booked. Activation is a selection mechanism shaped by policy and underwriting, so the primary score is not a policy-free applicant risk measure.

Transferred cases and permanently missing partner feeds create partial observability even within activated populations. The secondary all-application pathway model can answer a whole-funnel question, but that is a different estimand from booked-account default risk.

Deployment can change the data-generating process in several ways:
- If the score changes accept/reject or document-request behavior, the activation-selected population will change.
- If the score reprioritizes queues or assigns cases to different reviewers, waiting times, handoffs, and even observed prefixes will change.
- If high-risk accounts trigger earlier collections, different limits, or enhanced verification, the measured `default_90d` rate will change because the intervention affects outcomes.
- If partner routing changes, transfer propensity and missing-feed patterns will change.
- If post-migration logging rules change again, activity definitions and duplicate rates will shift.

The safe decision boundary is therefore: use the primary model for risk stratification or monitoring within the historically activated portfolio, and use a separate pathway model if the business truly needs an early score on every application.

## 9. PM4Py-oriented Python implementation skeleton
```python
import numpy as np
import pandas as pd
import pm4py

CASE_ID = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"

DATA_CUTOFF = pd.Timestamp("2026-02-15 23:59:59", tz="UTC")
POLICY_CHANGE = pd.Timestamp("2025-07-01 00:00:00", tz="UTC")
MIGRATION_DATE = pd.Timestamp("2025-10-15 00:00:00", tz="UTC")
DEFAULT_HORIZON_DAYS = 90
MAX_FEED_LAG_DAYS = 35
SAFE_ACTIVATION_CUTOFF = DATA_CUTOFF - pd.Timedelta(days=DEFAULT_HORIZON_DAYS + MAX_FEED_LAG_DAYS)
PRIMARY_K = 3
TIME_PREFIX_DAYS = 7

PREACT_TERMINALS = {"Rejected", "Withdrawn", "Transferred"}
POST_PREFIX_FORBIDDEN = {
    "Accepted",
    "Contract Signed",
    "Account Activated",
    "Collections Contact",
    "Default Recorded",
}

ACTIVITY_MAP = {
    # Fill from the validated migration crosswalk before running production studies.
    "KYC Check": "Identity/KYC Check",
    "Identity Check": "Identity/KYC Check",
    "Credit Assessment": "Credit Review",
}


def first_non_null(series):
    series = series.dropna()
    return series.iloc[0] if not series.empty else np.nan


def last_non_null(series):
    series = series.dropna()
    return series.iloc[-1] if not series.empty else np.nan


raw = pd.read_csv(
    "applications_events.csv",
    parse_dates=["time:timestamp", "label_available_at", "data_extract_time"],
)
for col in ["time:timestamp", "label_available_at", "data_extract_time"]:
    raw[col] = pd.to_datetime(raw[col], utc=True, errors="coerce")

raw = raw[raw[TS] <= DATA_CUTOFF].copy()
raw[ACT] = raw[ACT].replace(ACTIVITY_MAP)

# Migration created occasional duplicate rows; keep the rule deterministic and auditable.
raw = raw.sort_values([CASE_ID, TS, ACT, "org:resource"], kind="mergesort")
raw = raw.drop_duplicates(
    subset=[CASE_ID, ACT, TS, "org:resource", "source_system"],
    keep="first",
)

df = pm4py.format_dataframe(raw, case_id=CASE_ID, activity_key=ACT, timestamp_key=TS)
df = df.sort_values([CASE_ID, TS, ACT], kind="mergesort").copy()
df["event_index"] = df.groupby(CASE_ID).cumcount() + 1

# PM4Py process audit on fixed-length prefixes.
event_log = pm4py.convert_to_event_log(df[[CASE_ID, ACT, TS, "org:resource"]].copy())
prefix_log_k3 = pm4py.get_prefixes_from_log(event_log, PRIMARY_K)
dfg, start_activities, end_activities = pm4py.discover_dfg(prefix_log_k3)
variants = pm4py.get_variants(prefix_log_k3)

case_level = df.groupby(CASE_ID).agg(
    start_time=(TS, "min"),
    last_event_time=(TS, "max"),
    case_channel=("case:channel", "first"),
    case_region=("case:region", "first"),
    requested_amount=("case:requested_amount", "first"),
    source_system=("source_system", "first"),
)

activation = (
    df.loc[df[ACT].eq("Account Activated"), [CASE_ID, TS]]
    .groupby(CASE_ID)[TS]
    .min()
    .rename("activation_time")
)

terminal = (
    df.loc[df[ACT].isin(PREACT_TERMINALS | {"Account Activated"}), [CASE_ID, ACT, TS]]
    .sort_values([CASE_ID, TS, ACT], kind="mergesort")
    .drop_duplicates(subset=[CASE_ID], keep="first")
    .set_index(CASE_ID)
    .rename(columns={ACT: "terminal_state", TS: "terminal_time"})
)

labels = df.groupby(CASE_ID).agg(
    default_90d=("default_90d", last_non_null),
    label_available_at=("label_available_at", first_non_null),
)

case_level = case_level.join([activation, terminal, labels])
case_level["outcome_due_time"] = case_level["activation_time"] + pd.Timedelta(
    days=DEFAULT_HORIZON_DAYS + MAX_FEED_LAG_DAYS
)
case_level["activation_mature_by_cutoff"] = (
    case_level["activation_time"].notna()
    & (case_level["activation_time"] <= SAFE_ACTIVATION_CUTOFF)
)
case_level["label_observed_by_cutoff"] = (
    case_level["activation_time"].notna()
    & case_level["default_90d"].notna()
    & case_level["label_available_at"].notna()
    & (case_level["label_available_at"] <= DATA_CUTOFF)
)
case_level["overdue_missing_label"] = (
    case_level["activation_mature_by_cutoff"] & ~case_level["label_observed_by_cutoff"]
)
case_level["not_yet_mature"] = (
    case_level["activation_time"].notna()
    & ~case_level["activation_mature_by_cutoff"]
)


def classify_case(row):
    if bool(row["label_observed_by_cutoff"]):
        return "activated_default90" if int(row["default_90d"]) == 1 else "activated_nondefault90"
    if row["terminal_state"] == "Rejected":
        return "rejected"
    if row["terminal_state"] == "Withdrawn":
        return "withdrawn"
    if row["terminal_state"] == "Transferred":
        return "transferred"
    if bool(row["not_yet_mature"]):
        return "activated_not_yet_mature"
    if bool(row["overdue_missing_label"]):
        return "activated_missing_label"
    return "open"


case_level["cohort_state"] = case_level.apply(classify_case, axis=1)
case_level["split"] = np.select(
    [
        case_level["start_time"] <= pd.Timestamp("2025-03-31 23:59:59", tz="UTC"),
        case_level["start_time"] <= pd.Timestamp("2025-06-30 23:59:59", tz="UTC"),
        case_level["start_time"] <= pd.Timestamp("2025-09-30 23:59:59", tz="UTC"),
        case_level["start_time"] >= MIGRATION_DATE,
    ],
    ["train", "validation", "test", "post_migration_drift_only"],
    default="unscored_gap",
)

# Fixed-length prefix features (primary k=3 landmark).
prefix_k = df[df["event_index"] <= PRIMARY_K].copy()
prefix_flags = (
    prefix_k.groupby(CASE_ID)[ACT]
    .apply(lambda s: s.isin(PREACT_TERMINALS | POST_PREFIX_FORBIDDEN).any())
    .rename("has_terminal_in_prefix")
)

prefix_features = prefix_k.groupby(CASE_ID).agg(
    prefix_time=(TS, "max"),
    n_events=("event_index", "max"),
    current_activity=(ACT, "last"),
    n_doc_requests=(ACT, lambda s: (s == "Request Documents").sum()),
    n_credit_review_visits=(ACT, lambda s: (s == "Credit Review").sum()),
    unique_activities=(ACT, pd.Series.nunique),
    unique_resources=("org:resource", pd.Series.nunique),
    first_risk_score=("risk_score", first_non_null),
    last_risk_score=("risk_score", last_non_null),
)
prefix_features["risk_score_delta"] = (
    prefix_features["last_risk_score"] - prefix_features["first_risk_score"]
)

prefix_features = prefix_features.join(prefix_flags)
prefix_features = prefix_features.join(
    case_level[["start_time", "case_channel", "case_region", "requested_amount", "source_system"]]
)
prefix_features["elapsed_hours"] = (
    (prefix_features["prefix_time"] - prefix_features["start_time"]).dt.total_seconds() / 3600.0
)
prefix_features["post_policy_change"] = prefix_features["prefix_time"] >= POLICY_CHANGE
prefix_features["post_migration"] = prefix_features["prefix_time"] >= MIGRATION_DATE

# Keep only true k-event, pre-decision prefixes.
prefix_features = prefix_features[
    (prefix_features["n_events"] == PRIMARY_K)
    & (~prefix_features["has_terminal_in_prefix"])
].copy()

# Time-based prefix example: first 7 days from case start.
df_with_start = df.join(case_level["start_time"], on=CASE_ID)
time_prefix = df_with_start[
    df_with_start[TS] <= (df_with_start["start_time"] + pd.Timedelta(days=TIME_PREFIX_DAYS))
].copy()

model_df = prefix_features.join(
    case_level[
        [
            "split",
            "cohort_state",
            "activation_time",
            "label_observed_by_cutoff",
            "activation_mature_by_cutoff",
            "overdue_missing_label",
            "default_90d",
        ]
    ],
    how="inner",
)
model_df["y_primary"] = model_df["default_90d"].astype("Int64")

# Primary estimand: activated cases with observed labels only.
model_df = model_df[
    model_df["activation_time"].notna() & model_df["label_observed_by_cutoff"]
].copy()

banned_feature_cols = {
    "final_limit",
    "decision_reason",
    "collection_status",
    "default_90d",
    "label_available_at",
}
feature_cols = [c for c in model_df.columns if c not in banned_feature_cols]

# Leakage checks.
forbidden_in_prefix = prefix_k.loc[prefix_k[ACT].isin(POST_PREFIX_FORBIDDEN), CASE_ID].nunique()
if "documents_total" in df.columns:
    print("documents_total present: require a true snapshot timestamp before using it.")

cohort_counts = (
    case_level["cohort_state"]
    .value_counts(dropna=False)
    .rename_axis("cohort_state")
    .reset_index(name="n")
)
print(cohort_counts)
print(f"Unique k=3 prefix variants: {len(variants)}")
print(f"Cases with forbidden post-decision events inside k=3 prefix: {forbidden_in_prefix}")

train_df = model_df.loc[model_df["split"] == "train", feature_cols + ["y_primary"]]
val_df = model_df.loc[model_df["split"] == "validation", feature_cols + ["y_primary"]]
test_df = model_df.loc[model_df["split"] == "test", feature_cols + ["y_primary"]]

# Fit the primary booked-account default model on train_df / val_df here.
# Sensitivity 1: fit a label-observation model among mature activated cases for IPW.
# Sensitivity 2: replace y_primary with cohort_state for a secondary competing-outcome model.
# A random split helper is intentionally not used; the primary validation is temporal.
```
