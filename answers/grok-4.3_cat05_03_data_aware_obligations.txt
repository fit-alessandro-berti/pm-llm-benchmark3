## 1. Temporal Data Semantics
State is reconstructed by forward-filling non-blank attribute values per case in chronological order using `event_index` as the secondary key within identical timestamps. Blank cells are treated as “no change.” Material changes are identified by comparing the value at an event against the value at the immediately preceding review (Standard_Review or Enhanced_Review). Final attributes are never copied backward. Event time is the `time:timestamp` of the activity; effective time is taken only from explicit evidence fields (e.g., exemption `effective_from`); record time is the database insertion timestamp; evidence time is the qualified signature or witness timestamp. When two events share a timestamp, `event_index` order determines which state is visible to the later activity.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|------|-----------------------------|---------------------------------|---------------------|---------------------|-----------|------------------------|-----------------|
| R1 | Release_Funds; jurisdiction  DE and amount  100000 | Enhanced_Review after latest material change | Enhanced_Review < Release_Funds | Latest amount & jurisdiction at Release_Funds | Valid exemption | INDETERMINATE if amount unknown | Exemption approval record with matching scope and timing |
| R2 | Release_Funds; risk=HIGH or customer_type=PEP | Enhanced_Review then Compliance_Approve | Enhanced_Review < Compliance_Approve < Release_Funds | Latest risk & customer_type at Release_Funds | None | INDETERMINATE if risk or type unknown | Both review and approval events with correct order |
| R3 | Release_Funds; jurisdiction added to sanctions list after last Sanctions_Screen | New Sanctions_Screen after list update | Sanctions_List_Update < new Sanctions_Screen < Release_Funds | Jurisdiction at Release_Funds | None | INDETERMINATE if jurisdiction unknown | Timestamped list-update and subsequent screen |
| R4 | Release_Funds; amount increase >20 % since last review | New Enhanced_Review after increase | Increase event < new Enhanced_Review < Release_Funds | Amount at each review and at Release_Funds | Decrease never invalidates | INDETERMINATE on unknown prior amount | Amount values at successive events |
| R5 | Any obligation that references exemption | Head_Compliance approval, effective_from  trigger, scope match, not expired | Approval evidence  obligation trigger | Exemption attributes at trigger time | None | INDETERMINATE if scope or timing ambiguous | Qualified signature or reliable witness record |
| R6 | Any decisive trigger (amount, risk, jurisdiction, customer_type) | N/A | N/A | N/A | N/A | Classify INDETERMINATE unless other evidence resolves | Explicit values or reliable proxy |
| R7 | All obligations | Use latest known value at event time; `event_index` tie-break | N/A | State visible at the activity’s `event_index` | N/A | N/A | Full event log with timestamps and indices |

Pseudo-logic (Datalog-style):
```
R1_violated(C) :- Release_Funds(C,t), amount(C,t,A)100000, jurisdiction(C,t,J)"DE",
                  not exists ER after last_material_change(C) before t,
                  not valid_exemption(C,t,"R1").
R2_violated(C) :- Release_Funds(C,t), (risk(C,t,"HIGH") or customer_type(C,t,"PEP")),
                  not (Enhanced_Review(C,t1), Compliance_Approve(C,t2), t1<t2<t).
R3_violated(C) :- Release_Funds(C,t), Sanctions_List_Update(C,t_list,J), t_list < t,
                  not Sanctions_Screen(C,t_screen), t_list < t_screen < t.
R4_violated(C) :- amount_increase(C,rev,t) > 0.20, not Enhanced_Review after increase.
R5_valid(E) :- approved_by(E,"Head_Compliance"), effective_from(E)trigger, scope_match(E), not expired(E).
```

## 4. Ambiguities and Alternative Readings
TX-302: Result would flip to NONCOMPLIANT if the qualified signature timestamp were shown to be fabricated or if the outage explanation were false.  
TX-305: Settlement amount 150000 at 08:00 next day would make R1 clearly triggered if an immutable release payload existed; absence of any amount at release time keeps it INDETERMINATE.  
TX-310: Oral-approval witness testimony from a non-interested party plus an earlier qualified signature would change classification to JUSTIFIED_EXCEPTION.  
TX-311: Reversal of event_index order at 16:20 would leave jurisdiction=US at release, triggering R1 and producing NONCOMPLIANT.  
TX-301: Discovery of a backdated exemption record with proper Head_Compliance signature effective before 08:20 would change result to JUSTIFIED_EXCEPTION.  
TX-309: An additional Enhanced_Review performed between the 15:28 increase and 15:35 release would satisfy R4 and yield COMPLIANT.

## 6. Why Control-Flow-Only Conformance Is Insufficient
Control-flow conformance cannot detect final-state leakage, cannot validate post-hoc exemptions recorded after release, cannot recognize material data changes that invalidate earlier reviews, cannot evaluate conditional activation that depends on runtime attribute values, cannot handle missing or unknown attribute values, and cannot apply same-timestamp ordering via `event_index`. It also ignores evidence quality, effective-time versus event-time distinctions, and scope matching required by exemptions.

## 7. Recommended Logging and Control Improvements
Log immutable release payloads containing the exact amount, jurisdiction, risk_level, and customer_type at the instant of Release_Funds. Record three distinct timestamps for every exemption (signature, effective_from, record_time). Store rule version and exemption scope as explicit attributes. Capture change provenance (who, why, previous value) on every Update event. Enforce stable global event ordering by including a monotonically increasing source-system sequence number instead of relying solely on wall-clock timestamps.
