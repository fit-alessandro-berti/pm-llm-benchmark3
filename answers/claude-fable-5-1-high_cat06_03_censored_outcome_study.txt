## 1. Target definition

**Why the request as phrased cannot be answered literally.** "90-day default for every credit application" is only observed for applications that the lender activated. For rejected, withdrawn, transferred-and-unlinked and still-open applications, default within 90 days after activation is not a missing value; it is an undefined quantity under the policy that actually operated. Any number attached to those cases is either a convenience label (wrong) or a counterfactual (requires assumptions that must be stated). The design therefore separates three things: (i) what happens to an application in the process (fully observed, all 48,000), (ii) default after activation (observed only for the 25,200 activated, partially censored), (iii) default that *would* occur if a case were activated (never observed for non-activated cases).

**Primary target (chosen): time to first default after Account Activated, evaluated at a 90-day horizon, among applications that are activated under the policy in force, predicted from the pre-decision prefix.**

- Unit of analysis: one credit application (case). If an applicant identifier exists, all applications of the same applicant are kept in the same split to avoid identity leakage (assumption: an applicant key can be derived; otherwise this is a stated limitation).
- Prediction time \(t_k\): completion timestamp of the \(k\)-th canonical event, primary \(k=3\) (Application Started → Identity/KYC Check → first Credit Review), i.e. the moment the case first reaches a reviewer and strictly before any of Accepted / Rejected / Withdrawn / Transferred. Secondary prediction points: \(k=2,4,5\) and elapsed-time points at 24 h, 72 h and 7 days after Application Started (only for cases still undecided at that time).
- Horizon: 90 days counted from Account Activated (not from prediction time). The lag between prediction and label is therefore variable: time-to-activation + 90 days + 7–35 days of feed delay.
- Population: applications started 2024-01-01…2025-12-31 that reach Account Activated under the credit policy in force at their decision date. Scores are produced for every open application at \(t_k\), interpreted as "risk if this application is activated under the current policy".
- Estimand: \(F_\pi(90 \mid x_k) = P(T \le 90 \mid X_k = x_k, A = 1; \pi)\), the 90-day cumulative incidence of default given the prefix information \(x_k\), conditional on activation \(A=1\) under policy \(\pi\). \(T\) is time from activation to the first Default Recorded / feed-confirmed default; observation is right-censored at the analysis cutoff.
- Label semantics: \(y=1\) only if a default is observed within 90 days of activation; \(y=0\) only if the outcome feed has arrived (`label_available_at` ≤ cutoff) and reports no default; otherwise the case is censored, never "non-default".

**Why this is operationally and statistically defensible.** (1) It is observed: no imputation of outcomes for people who were never exposed to credit. (2) It is the quantity a reviewer needs at Credit Review: the decision variable is the lender's own accept/reject action, so a model that "predicts default for every application" would partly be predicting the lender's own rejection, which is circular. (3) Selection into the population is driven by the lender's decision, made on information that is largely recorded in the log, so the conditional estimand is well defined for a given policy and does not need counterfactual assumptions — it only needs to be labelled as policy-specific. (4) Modelling time-to-default with right censoring uses all 25,200 activated accounts instead of the 21,600 matured ones, removing the maturity truncation that otherwise under-represents recent (post-policy-change, post-migration) activations. (5) Its main weakness is support: prefixes that are almost never activated under \(\pi\) receive extrapolated scores. The design therefore ships an activation-propensity/overlap diagnostic next to every score.

**Credible alternative A — multi-state (competing-outcome) target for all 48,000 applications.** States from the prefix: Activated & default ≤ 90 d, Activated & no default in 90 d, Rejected, Withdrawn, Transferred, still open (censored). Estimated with an illness–death / competing-risks structure: application stage (transitions to Accepted, Rejected, Withdrawn, Transferred; administrative censoring for open cases) followed by the outcome stage after activation. It answers "what will happen to this application under current operations", is useful for capacity and portfolio planning, and provides \(P(A=1\mid x_k)\) which the primary target needs as a support diagnostic. It does *not* answer the credit-risk question: its "default" component \(P(A=1, T\le 90 \mid x_k)\) multiplies credit quality by the lender's acceptance behaviour, so a policy loosening raises it mechanically without anyone's creditworthiness changing.

**Credible alternative B — policy-specific counterfactual: \(P(T\le 90 \mid x_k, do(A=1))\) for all applications.** This is reject inference. It requires either unconfoundedness of the activation decision given \(x_k\) (all information the reviewer used is in the features; violated here because reviewers see documents and `decision_reason` inputs not in the prefix) or an instrument such as the 1 July 2025 threshold change (cases with the same prefix accepted after and rejected before). It can be bounded (Manski-type worst/best case) but not point-identified from these data; it is reported only as a labelled sensitivity analysis, never as the primary output.

**Rejected status quo.** Training a binary classifier on the 21,600 exported rows and reporting it as "default probability of an application" mixes an activation-conditional estimand with a maturity-truncated cohort and is silent about what the score means for non-activated cases. Labelling rejected/withdrawn/open cases as non-default would make the model learn "looks like a case we reject → low risk", the opposite of the intended use.

## 2. Cohort construction

**As-of principle.** Every quantity is computed as it would have been visible at a configurable cutoff \(c\): events with `time:timestamp` ≤ \(c\), feed labels with `label_available_at` ≤ \(c\). Training folds use \(c\) = fold cutoff; the final cohort uses \(c\) = extraction date 2026-02-15. Key dates: horizon complete for activations ≤ 2025-11-17 (extract − 90 d); feed practically complete for activations ≤ 2025-10-13 (extract − 125 d, using the 35-day upper feed delay; re-estimated empirically from `label_available_at`).

**Inclusion (application-stage cohort, used for the multi-state alternative and for the activation-propensity model).**
- Application Started between 2024-01-01 and 2025-12-31 (by canonical activity after alias mapping).
- At least \(k\) canonical events before any decision event, all with timestamp ≤ \(c\); the \(k\)-th event is not a decision event.
- Migration duplicates removed (same case, canonical activity, resource, timestamp within 60 s).

**Inclusion (outcome-stage cohort, primary target).**
- In the application-stage cohort and Account Activated observed at time \(a \le c\).
- Follow-up: from \(a\) to \(\min(a+90\text{ d}, c)\); event = default in that interval; otherwise censored.
- Binary 90-day label defined only when feed arrived (`label_available_at` ≤ \(c\)) or default observed ≤ 90 d.

**Exclusion / handling rules.**
- Rejected, Withdrawn: excluded from the outcome stage (outcome undefined under \(\pi\)); retained in the application stage as competing terminal states.
- Transferred, linked (~60 %): followed under the partner identifier; if activated there, included in the outcome stage with `source_system = partner` and a flag for elevated feed missingness. Transferred, unlinked (~40 %): lost to follow-up at transfer; competing state in the application stage, excluded from the outcome stage.
- Open at \(c\) (no decision): administratively censored in the application stage; not in the outcome stage.
- Activated, feed not arrived: censored (never zero). If \(a + 90 + 35\) d < \(c\) and still no feed → flagged "suspected permanently missing feed", handled in Section 3.
- Prefixes whose \(k\)-th event lies inside a policy/migration boundary window are kept but carry the regime indicator; no case is dropped for this reason.

**Cohort-flow table (as of 2026-02-15; all 48,000 accounted for).**

| Bucket | Cases | Application-stage role | Outcome-stage (primary) role | Observation type |
|---|---|---|---|---|
| Applications started 2024-01-01…2025-12-31 | 48,000 | universe | — | — |
| Rejected | 9,100 | terminal competing state | outcome undefined under observed policy; excluded, not "non-default" | selectively unobserved (by design) |
| Withdrawn | 5,700 | terminal competing state | outcome undefined; excluded | selectively unobserved (applicant decision) |
| Transferred, linkable (~60 %) | ≈1,740 | transition to partner branch | included if activated at partner (elevated feed-missingness flag) | follow-up continues, higher missing-feed risk |

| Open at extraction (no decision yet) | 5,100 | right-censored in application stage | not yet in population | administrative censoring |

## 3. Censoring and missing-label strategy

**Mechanisms, distinguished.**

1. Ordinary right censoring: activated accounts whose 90-day window has not elapsed at \(c\) (activated after 2025-11-17). Follow-up is truncated at \(c\); censoring time is a deterministic function of activation date, hence independent of the outcome conditional on calendar time (and on covariates that drift with calendar time).
2. Delayed labels: the horizon has passed but the feed (7–35 d lag) has not arrived. Absence of a default record is *not* evidence of non-default until `label_available_at` ≤ \(c\). These cases are treated as censored for the binary label; for the survival representation they contribute follow-up only up to the point where Default Recorded events are reliably in the log (assumption: Default Recorded is logged near-real-time; if it only arrives with the feed, censor at the feed frontier \(c - 35\) d instead).
3. Selection through activation: only activated applications have an outcome. This is not censoring; it is a change of population. The primary estimand conditions on it explicitly; the multi-state model quantifies it (\(P(A=1\mid x_k)\)); the counterfactual target requires assumptions about it.
4. Transfer: in the application stage it is a competing event (the case leaves the lender's process). For linked transfers with partner activation it becomes a missing-follow-up mechanism (partner feeds are less reliable). For unlinked transfers it is loss to follow-up before an outcome could be defined. Whether transfer is informative about default is unknown; the linkage itself may be selective.
5. Permanently missing outcome feeds: concentrated in partner-originated accounts. Distinguished from delayed labels by elapsed time beyond the maximal feed delay. Potentially missing-not-at-random (a partner that stops reporting may do so for troubled portfolios).

**Primary analysis.** Discrete-time (weekly) hazard model or Cox model for time to default after activation, administrative censoring at \(c\), covariates = prefix features + regime indicator, fitted on all activated accounts visible at the training cutoff. The 90-day cumulative incidence is the reported score. Censoring is assumed independent of default given calendar time and covariates (administrative censoring: testable by construction; see below). Cases with suspected permanently missing feeds are censored at their last reliable follow-up and additionally carry inverse-probability-of-censoring weights from a censoring model with `source_system`, channel, region and activation month, so that the analysed sample reweights toward the full activated cohort. A fixed-horizon binary companion model (matured labels only, IPCW-weighted) is fitted for comparability with the current warehouse target.

**Sensitivity analyses.**
- S1 Missing-feed bounds: recompute all metrics treating suspected-missing-feed accounts as (a) all defaults, (b) all non-defaults, (c) censored with IPCW (primary). The spread is reported as the uncertainty band due to feed loss; a partner-stratified version isolates the partner effect.
- S2 Transfer handling: exclude all transfers vs. include linked partner activations; compare coefficients and calibration.
- S3 Regime: separate models pre/post 1 July 2025 vs. pooled with regime indicator and regime-interaction terms; report whether the same prefix has different hazard across regimes (expected, because the activated population changed).
- S4 Maturity truncation check: the binary model on the 21,600 export vs. the survival model on 25,200; a material difference quantifies the bias of the current practice.
- S5 Counterfactual (strong assumptions, labelled): activation-propensity model on all decided applications; overlap-weighted extrapolation of the primary model to rejected cases; Manski bounds \([P(\text{def}\mid A{=}1)P(A{=}1),\; P(\text{def}\mid A{=}1)P(A{=}1) + P(A{=}0)]\) on the marginal default rate. Reported to show how wide "default for every application" is, not as a deliverable score.

**Testability.**
- Testable: feed-delay distribution (from `label_available_at` − (activation + 90 d) on matured cases); dependence of missing-feed status on observables (`source_system`, channel, region); administrative-censoring independence given activation date (by construction; verify that censoring time is exactly \(c - a\)); covariate shift between labelled and censored activated accounts (adversarial classifier); duplicate-event rate around the migration.
- Partially testable: informative censoring for suspected-missing feeds — association with observables can be checked, association with the unobserved outcome cannot; whether linked and unlinked transfers differ on observables (yes/no), but not whether they differ on default; stability of the prefix→default relationship across regimes among activated cases (testable within regimes, but the *population* shift confounds the comparison).
- Fundamentally untestable from these data: default risk of rejected/withdrawn applications under activation; MNAR feed loss; unconfoundedness of the activation decision given the prefix; whether the partner's default definition equals the lender's.

## 4. Prefix extraction

**As-of rule.** A prefix at prediction time \(t\) consists of events with `time:timestamp` ≤ \(t\) and, for each of those events, the attribute values recorded on that event row (not values back-filled onto earlier rows by the export). Columns that are only known after the decision or after the outcome (`final_limit`, `decision_reason`, `collection_status`, `default_90d`, `label_available_at`, `data_extract_time`) are removed from the prefix table before feature construction, not merely ignored.

**Ordering.** Stable sort by (case, timestamp, original export row order). The migration created duplicate events; exact duplicates (same case, canonical activity, resource, timestamp within 60 s) are collapsed to the first occurrence, with the removed count reported by period as an audit statistic.

**Fixed event-count prefixes (\(k\) events).** `pm4py.get_prefixes_from_log(log, length=k)` returns the first \(k\) events of every case and keeps shorter cases whole; therefore the pipeline afterwards (a) keeps only cases with exactly \(k\) events in the prefix (a case that ended after 2 events is not a length-3 prefix), (b) drops prefixes that contain a decision activity (Accepted/Rejected/Withdrawn/Transferred), because the primary use-case is pre-decision, and (c) sets the prediction time to the timestamp of the \(k\)-th event and requires it to be ≤ the cutoff. Prefix lengths evaluated: \(k = 2,3,4,5\); \(k=3\) is primary because every activated case has at least Started, KYC and one Credit Review before a decision. For \(k \ge 4\), prefixes are dominated by document loops; the model at \(k=4\) is therefore explicitly "risk for cases that needed a document request", a different sub-population, and is reported as such.

**Elapsed-time prefixes (\(\Delta\) after start).** Prediction time \(t = \text{start} + \Delta\), \(\Delta \in \{24\text{ h}, 72\text{ h}, 7\text{ d}\}\). Events with timestamp ≤ \(t\) are included; cases that already reached a decision by \(t\) are excluded from that horizon (they are no longer candidates for an early warning at \(t\)), and \(t\) must be ≤ cutoff. Elapsed-time prefixes have variable length, which is itself informative (a case with one event after 72 h is slow); fixed-\(k\) prefixes have variable elapsed time. Both are reported.

**Short cases.** Withdrawn or rejected within fewer than \(k\) events are not scored at \(k\) (they are not in the population "open at \(t_k\)"); they still enter the application-stage model at the prefix lengths they do reach. No padding is used for tree/GLM feature tables; sequence models would use masking.

**Repeated document loops.** Credit Review → Request Documents → Credit Review cycles are kept as events in the prefix and summarised as counts (number of Credit Review entries, number of document requests, time spent waiting for documents) rather than as ever-longer one-hot sequences; the raw prefix variant is retained for audit only.

**Activity renaming.** An alias map (post-migration name → canonical name) is applied before any prefix or feature computation; the raw name is kept in `activity_raw`. Post-canonicalisation checks: `pm4py.discover_dfg` start activities must be exactly {Application Started}; `pm4py.get_variants` on prefixes must show no new variants appearing only after 2025-10-15. A `post_migration` indicator is kept as a calendar covariate and monitored so that the model does not learn migration artefacts as risk.

## 5. Process-aware features

All features are computed from the prefix (timestamps ≤ \(t\)) or from reference data whose own availability date is ≤ \(t\).

**Static case attributes (known at Application Started).** `case:channel`, `case:region`, `case:requested_amount` (log-transformed), `source_system` at start (own vs. partner; also a selection/missing-feed proxy), start calendar: hour, weekday, month, holiday flag.

**Prefix-derived features.**
- Control-flow: last activity, activity bag counts, indicator of KYC repeat, number of Credit Review entries so far, number of Request Documents so far, position of first Credit Review, prefix variant hashed (audit only, high cardinality).
- Timing: elapsed time since start, inter-event times (start→KYC, KYC→Credit Review), time spent in KYC, waiting time before first Credit Review, share of the prefix in business hours, whether the prefix spans a weekend.
- Rework: document-loop count, cumulative document waiting time, ratio of loop events to total events.
- Resource / queue: reviewer identifier (encoded with training-period-only statistics, see reference data), as-of resource experience = number of events the resource handled before \(t\) (recomputed from the log, replacing the extraction-time field), number of applications open in the system at \(t\) (started but not decided; computed from events ≤ \(t\) only), arrivals in the previous 7 days, reviewer's open workload at \(t\).
- Application-content dynamics: `risk_score` as recorded on the last prefix event, first-to-last change, number of updates within the prefix; documents actually received on or before \(t\) (event-derived, replacing the nightly `documents_total` snapshot).
- Cohort / calendar: policy regime indicator (start ≥ 2025-07-01), post-migration indicator, week of year. Kept as covariates, but their coefficients are audited: they encode the population shift, not applicant risk, and they must be refreshed at deployment.

**Features requiring historical reference data (as-of joins).** Reviewer- and channel-level historical outcome rates, computed only from accounts whose label was *available* (`label_available_at` ≤ \(t\)), not merely whose activation preceded \(t\); reviewer historical acceptance rate and document-request rate (available earlier, at decision time); regional macro/seasonal baselines. Each is joined with a strict "reference date ≤ \(t\)" condition and lagged by the feed delay; they are recomputed inside every backtest fold from that fold's training window.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final credit decision; encodes acceptance and limit-setting, which are downstream of \(t_k\) and predictive of default | Available only after Accepted/Rejected; never at a pre-decision prefix | Drop | Post-decision value; would also make the model learn the lender's own decision |
| `decision_reason` | Populated at/after Accept/Reject; directly encodes the outcome of the process stage | After decision event only | Drop | Same as above; its presence/absence alone reveals whether a decision exists |
| `collection_status` | Updated after activation; can literally reveal default | Only after Account Activated + collections activity | Drop (use only to cross-check labels) | Direct outcome proxy |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded, decision events) | Their existence, count or timing reveals activation and outcome | Event timestamp ≤ \(t_k\) | Drop from prefix by timestamp filter; assert no decision activity inside prefix | Case length, total duration, end activity are all post-prefix |
| `documents_total` (nightly snapshot) | Includes documents uploaded later on the same calendar day than \(t_k\); documents requested after Credit Review leak the reviewer's decision path | Snapshot timestamp strictly before \(t_k\) (previous night) or event-derived count of documents received ≤ \(t_k\) | Repair | Same-day contamination is a classic snapshot leak; event-derived count is exactly as-of |
| `risk_score` (updated at several events) | Export may carry the latest score on all rows or the final score reflects post-decision recalculation | Use value recorded on events with timestamp ≤ \(t_k\); last non-null within the prefix | Repair | Latest-value back-fill would import decision-stage information |
| Resource experience (stored as of extraction) | Experience at extraction ≥ experience at event; correlates with calendar time and survivorship of employees | Recompute as number of events handled by the resource before \(t_k\) | Repair (drop if resource IDs are unstable across migration) | Extraction-time value is a future quantity |
| `default_90d` repeated on events, `label_available_at` | Label and label-timing columns; `label_available_at` itself reveals activation and feed arrival | Used only to define label maturity and censoring at the cutoff; never as a feature | Drop from features; keep in label logic | Label availability is informative about the label (missing feeds concentrate in partners) |
| `data_extract_time` | Constant; but differences to it encode case age → maturity → label availability | Never | Drop | Pure artefact |
| `source_system` | Legitimate static attribute, but also proxy for transfer and for missing feed | Value as recorded at start; not the last value (transfer changes it) | Keep as-of start value; audit | Distinguish applicant attribute from downstream routing |
| Reviewer / channel historical default rates | Computed with labels not yet available at \(t_k\) (feed delay) or from the test period | Only labels with `label_available_at` ≤ \(t_k\), computed within fold | Repair | Target-encoding with future labels is target leakage |
| Queue / workload counts | Computed from full log including cases that started after \(t_k\) | Only events with timestamp ≤ \(t_k\) | Repair | Future arrivals are not knowable |
| Activity names post-migration, duplicate events | Model learns the migration period (different population, different label maturity) via names/duplicates | Canonical names via alias map; de-duplication; `post_migration` flag monitored | Repair | Artefact, not risk |
| Prefix variant / event count in prefix (fixed-\(k\)) | Harmless for fixed \(k\); for elapsed-time prefixes, count is legitimate signal | Events ≤ \(t\) | Keep | As-of by construction |
| Policy regime indicator | Encodes population shift, not risk; coefficient will not transfer to future regimes | Start date known at \(t_k\) | Keep with monitoring | Necessary for calibration across regimes; disclosed limitation |

Automated checks (implemented in Section 9): forbidden columns absent from the feature table; every event in the prefix table has timestamp ≤ the case's \(t_k\); no decision activity inside prefixes; univariate AUC scan on the labelled subset flagging any single feature with AUC > 0.9 as a suspected leak; feature-importance review after each fold.

## 7. Validation design

**Why a random case split misleads here.** (1) Calendar features, queue features and reference-rate features would let training rows carry information from the same weeks as test rows, inflating performance. (2) The labelled population is maturity-truncated: a random split of matured rows evaluates on cases activated before October 2025 while deployment scores cases from 2026; the policy change (July 2025) and migration (October 2025) would be mixed into both halves, hiding the drop that will occur on the new regime. (3) Migration duplicates or an applicant's repeated applications can land in both train and test. (4) Reviewer-level and channel-level encodings computed over the whole period leak future labels. (5) A random split cannot measure whether the model survives distribution shift, which is the main deployment risk for a selection-dependent estimand.

**Rolling-origin temporal backtest by case start.** Training cutoffs \(c \in\) {2025-01-01, 2025-04-01, 2025-07-01, 2025-10-01}; test window = cases started in \((c, c+91\text{ d}]\). At each cutoff, the training set is rebuilt *as of \(c\)*: only events ≤ \(c\), only labels with `label_available_at` ≤ \(c\), censoring at \(c\), reference features recomputed. Test labels are taken as of the extraction date, with remaining censoring handled by IPCW. This reproduces the true deployment situation, where a model trained at \(c\) has no labels for accounts activated in the previous ~125 days. Fold roles: fold 2025-07-01 measures pre→post policy transfer; fold 2025-10-01 straddles the migration; the last fold has few matured test labels and relies on the survival metrics — this is reported, not hidden. A final hold-out of cases started 2025-10-01…2025-12-31 is touched once.

**Label maturity in evaluation.** Fixed-horizon metrics are computed on test cases with feed arrived, reweighted by IPCW to the full activated test cohort; survival metrics use all activated test cases. The share of censored test cases is printed with every metric.

**Metrics for the primary (survival) target.** IPCW Brier score at 90 d and its integrated version over 0–90 d; time-dependent AUC at 90 d (Uno); Uno's C-index; calibration of predicted 90-day cumulative incidence vs. Kaplan–Meier estimates by predicted-risk decile (calibration-in-the-large, slope via pseudo-observations); sharpness (distribution of predicted risks). Companion binary metrics on matured labels: AUROC, AUPRC (baseline 12.5 %), Brier, reliability diagram, ECE, and decision-oriented recall at the review capacity (e.g. top 10 % flagged) and net benefit across thresholds. All metrics reported per prefix length \(k\) and per elapsed-time point \(\Delta\), giving an earliness–accuracy curve. Baselines: prevalence-only, `risk_score` at \(t_k\) alone, and `pm4py.split_train_test` random-split model (to show the inflation).

**Metrics for the multi-state alternative.** Multiclass log-loss and per-state one-vs-rest AUC for the application stage; Aalen–Johansen-based calibration of cumulative incidences at fixed times after start; calibration of \(P(A=1\mid x_k)\) as the overlap diagnostic.

**Policy change and migration.** Report every metric by regime (start before/after 2025-07-01) and by migration period; compare a pooled model with regime indicator against regime-specific models; examine whether the activation rate for fixed prefix buckets changed (selection shift) separately from whether the hazard among activated changed (outcome shift). Around 2025-10-15, verify that the de-duplication and alias map removed the artefact by checking that variant distributions and per-case event counts are stable across the boundary.

**Subgroup performance.** AUC, Brier and calibration by channel, region, `source_system` (own vs. partner), requested-amount tertile, regime, and by whether the case had a document loop. Minimum-support rule for reporting; flag subgroups whose calibration intercept deviates materially.

**Distribution shift.** Population Stability Index per feature between consecutive folds; adversarial-validation AUC (train vs. test period); monitoring of predicted-risk distribution and activation-propensity overlap for scored cases. Backtest results are summarised as fold-wise curves, not a single averaged number.

## 8. Limitations and decision-use boundary

**What the study can claim.** For an application open at Credit Review, the model estimates the association between its pre-decision prefix and 90-day default *among applications that the lender activated under the policy in force*, with honest handling of censored and delayed labels, and it quantifies how uncertain that estimate is under different treatments of missing feeds and transfers. It can rank open cases for review effort and report calibrated risk for cases that resemble historically activated ones.

**What it cannot claim.** (1) It is predictive association, not causation: waiting time, document loops or reviewer identity are correlates of the process and of the reviewer's private information, not causes of default. (2) It does not estimate the default rate of all applications or of rejected ones; the 12.5 % matured default rate describes activated accounts only. (3) For prefixes that were rarely activated, the score is an extrapolation; the activation-propensity diagnostic must be shown alongside the score and low-overlap cases marked "insufficient support", not "low risk". (4) Counterfactual default risk under a different acceptance policy is only bounded (Section 3, S5). (5) Coefficients of regime and migration indicators describe population shifts and will not transfer to future regimes. (6) Partner-originated accounts have systematically less reliable outcomes; their scores carry wider uncertainty bands. (7) The default definition itself is the lender's/partner's operational definition; changes to it change the target.

**Selection effects to keep in mind.** The model learns from applications that passed a human/policy filter. Features that today predict low risk among activated cases (e.g. quick KYC) may be uninformative in the rejected population; a feature's apparent protective effect can be a selection artefact (Berkson-type conditioning on acceptance).

**Ways deployment would change the data-generating process.**
1. Selective labels feedback: if scores influence rejection, future high-score applications are not activated, so their outcomes are never observed; the training population drifts toward model-approved cases and retraining reinforces the model's own decisions. Mitigation: retain a small randomised or rule-based acceptance stratum, or restrict the model to prioritisation rather than rejection.
2. Behavioural change in the process: reviewers may request documents more often for flagged cases, so document-loop counts and waiting times become consequences of the score instead of signals; prefix features lose their pre-deployment meaning.
3. Outcome intervention: flagged accounts may receive earlier collections contact or lower limits, altering the realised default rate (treatment effect on the label); post-deployment labels no longer measure the untreated risk the model was trained on.
4. Routing and transfer steering: if high-risk cases are transferred to partners, transfer becomes strongly informative censoring and partner feed loss grows exactly where the risk is.
5. Policy or threshold changes and channel-mix shifts (applicants or brokers adapting to known criteria) change \(P(A=1\mid x_k)\) and therefore the conditional estimand.

**Decision-use boundary.** Use for prioritising reviewer attention and for uncertainty-aware early monitoring of the activated portfolio; do not use as an automatic rejection rule, do not report scores for non-activated populations as default probabilities, and re-estimate calibration after every policy change with the as-of backtest before scores are used again.

```python
"""
As-of, censoring-aware data-engineering and audit pipeline for early-warning default prediction.
`# ASSUMPTION:` marks design assumptions; `# HOOK:` marks where survival / competing-risk models plug in.
"""
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS, RES = "case:concept:name", "concept:name", "time:timestamp", "org:resource"
EXTRACT       = pd.Timestamp("2026-02-15", tz="UTC")
POLICY_CHANGE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION     = pd.Timestamp("2025-10-15", tz="UTC")
HORIZON       = pd.Timedelta(days=90)
FEED_LAG_MAX  = pd.Timedelta(days=35)   # ASSUMPTION: feed practically complete 35 d after horizon; re-estimate from label_available_at
K             = 3                        # primary fixed-length prefix: Started -> KYC -> first Credit Review
DECISION      = ["Accepted", "Rejected", "Withdrawn", "Transferred"]
POST_PREFIX_COLS = ["final_limit", "decision_reason", "collection_status", "default_90d",
                    "label_available_at", "data_extract_time", "documents_total"]
# ASSUMPTION: alias map taken from the 2025-10-15 migration mapping (post-migration name -> canonical name)
ALIAS = {"Application Created": "Application Started", "KYC Verification": "Identity/KYC Check",
         "Credit Assessment": "Credit Review", "Documents Requested": "Request Documents",
         "Account Opened": "Account Activated", "Default Flagged": "Default Recorded"}

# ---------- 1. Load, canonicalise activities, remove migration duplicates ----------
df = pd.read_csv("applications_events.csv")
for c in [TS, "label_available_at", "data_extract_time"]:
    df[c] = pd.to_datetime(df[c], utc=True, errors="coerce")
df["activity_raw"] = df[ACT]
df[ACT] = df[ACT].replace(ALIAS)
df = df.sort_values([CASE, TS], kind="mergesort")            # stable: export order breaks timestamp ties
df["_min"] = df[TS].dt.floor("60s")
dup = df.duplicated(subset=[CASE, ACT, RES, "_min"])
print(f"dropped {dup.sum()} suspected duplicates, {(df.loc[dup, TS] >= MIGRATION).mean():.0%} of them post-migration")
df = df.loc[~dup].drop(columns="_min")
df = pm4py.format_dataframe(df, case_id=CASE, activity_key=ACT, timestamp_key=TS)
# as-of resource experience: events handled by the resource BEFORE this event (replaces extraction-time experience)
df["res_events_before"] = df.sort_values(TS, kind="mergesort").groupby(RES).cumcount()
dfg, start_acts, end_acts = pm4py.discover_dfg(df)          # audit only: canonicalisation must leave one start activity
print("start activities:", start_acts, "| end activities:", end_acts)

# ---------- 2. Case table as of a cutoff (nothing after the cutoff is visible) ----------
def case_table(ev, cutoff):
    ev = ev[ev[TS] <= cutoff]
    g = ev.groupby(CASE)
    ct = pd.DataFrame({"start": g[TS].min(), "last_seen": g[TS].max(), "n_events": g.size(),
                       "source_system": g["source_system"].first(), "channel": g["case:channel"].first()})
    for a in DECISION + ["Account Activated", "Default Recorded"]:
        ct["t_" + a.split()[0].lower()] = ev.loc[ev[ACT] == a].groupby(CASE)[TS].min()
    vis = ev[ev["label_available_at"] <= cutoff]              # feed rows already delivered at the cutoff
    ct["label_available_at"] = vis.groupby(CASE)["label_available_at"].min()
    ct["feed_default"] = vis.groupby(CASE)["default_90d"].last()
    ct["state"] = np.select(
        [ct["t_account"].notna(), ct["t_rejected"].notna(), ct["t_withdrawn"].notna(), ct["t_transferred"].notna()],
        ["activated", "rejected", "withdrawn", "transferred"], default="open")   # accepted-but-not-activated stays open
    act = ct["t_account"]
    ct["days_default"] = (ct["t_default"] - act).dt.total_seconds() / 86400
    default_in_h = ct["days_default"] <= 90
    horizon_passed, feed_overdue = act + HORIZON <= cutoff, act + HORIZON + FEED_LAG_MAX <= cutoff
    # Honest binary label: 1 only if default observed in horizon, 0 only if the feed confirmed it, else NaN (censored)
    ct["y90"] = np.select([default_in_h | ct["feed_default"].eq(1), ct["feed_default"].eq(0)], [1.0, 0.0], np.nan)
    ct["label_status"] = np.select(
        [ct["state"] != "activated", ct["y90"].notna(), ~horizon_passed, ~feed_overdue],
        ["not activated", "labelled", "immature (<90d)", "delayed feed"], default="suspect missing feed")
    # Survival representation of the outcome stage, administratively censored at the cutoff
    # ASSUMPTION: 'Default Recorded' is logged near-real-time; otherwise censor at cutoff - FEED_LAG_MAX
    fu = np.minimum((cutoff - act).dt.total_seconds() / 86400, 90)
    ct["time"] = np.fmin(ct["days_default"], fu)
    ct["event"] = default_in_h & (ct["days_default"] <= fu)
    # HOOK: (time, event) feed a discrete-time hazard / Cox model; IPCW weights from a censoring model on
    #       source_system, channel and activation month handle suspected-missing feeds.
    ct["regime"] = np.where(ct["start"] >= POLICY_CHANGE, "post_policy", "pre_policy")
    return ct

ct_now = case_table(df, EXTRACT)
print(pd.crosstab(ct_now["state"], ct_now["label_status"], margins=True))     # cohort-flow table, must total 48,000
print(ct_now.loc[ct_now["label_status"] == "suspect missing feed"].groupby("source_system").size())

# ---------- 3. Prefixes without look-ahead ----------
def fixed_prefixes(ev, k, cutoff):
    pre = pm4py.get_prefixes_from_log(ev[ev[TS] <= cutoff], length=k, case_id_key=CASE)
    n = pre.groupby(CASE)[ACT].transform("size")
    decided = pre.groupby(CASE)[ACT].transform(lambda s: s.isin(DECISION).any())
    pre = pre[(n == k) & ~decided]                # exactly k events and still undecided after event k
    return pre.drop(columns=[c for c in POST_PREFIX_COLS if c in pre.columns])

def elapsed_prefixes(ev, delta, cutoff):
    start = ev.groupby(CASE)[TS].transform("min")
    pre = ev[(ev[TS] <= start + delta) & (start + delta <= cutoff)]
    decided = pre.groupby(CASE)[ACT].transform(lambda s: s.isin(DECISION).any())
    return pre[~decided].drop(columns=[c for c in POST_PREFIX_COLS if c in pre.columns])

def features(pre, ev_all):
    g = pre.groupby(CASE)
    X = pd.DataFrame({
        "t_pred": g[TS].max(), "start": g[TS].min(), "n_prefix_events": g.size(),
        "channel": g["case:channel"].first(), "region": g["case:region"].first(),
        "requested_amount": g["case:requested_amount"].first(), "source_system": g["source_system"].first(),
        "last_activity": g[ACT].last(),
        "n_credit_review": g[ACT].apply(lambda s: (s == "Credit Review").sum()),
        "n_doc_requests": g[ACT].apply(lambda s: (s == "Request Documents").sum()),
        "risk_score_asof": g["risk_score"].last(),             # last non-null value inside the prefix, not the export's final value
        "risk_score_delta": g["risk_score"].last() - g["risk_score"].first(),
        "res_exp_asof": g["res_events_before"].last()})
    X["elapsed_h"] = (X["t_pred"] - X["start"]).dt.total_seconds() / 3600
    X["start_hour"], X["start_dow"] = X["start"].dt.hour, X["start"].dt.dayofweek
    X["post_policy"], X["post_migration"] = X["start"] >= POLICY_CHANGE, X["start"] >= MIGRATION
    docs = pre[pre[ACT] == "Documents Received"].groupby(CASE).size()      # replaces same-day `documents_total` snapshot
    X["docs_received_asof"] = docs.reindex(X.index).fillna(0)
    # system load at t_pred: started but undecided cases at that instant; uses only events dated <= t_pred
    starts = np.sort(ev_all.groupby(CASE)[TS].min().values)
    ends = np.sort(ev_all[ev_all[ACT].isin(DECISION)].groupby(CASE)[TS].min().values)
    tp = X["t_pred"].values
    X["open_cases_at_pred"] = np.searchsorted(starts, tp, side="right") - np.searchsorted(ends, tp, side="right")
    return X

# ---------- 4. Leakage audit ----------
def leakage_audit(X, pre, ct):
    bad = set(X.columns) & set(POST_PREFIX_COLS)
    assert not bad, f"post-prefix columns in feature table: {bad}"
    chk = pre.merge(X[["t_pred"]], left_on=CASE, right_index=True)
    assert (chk[TS] <= chk["t_pred"]).all(), "event after prediction time inside prefix"
    assert not chk[ACT].isin(DECISION).any(), "decision event inside prefix"
    lab = X.join(ct[["y90"]], how="inner").dropna(subset=["y90"])      # univariate separability scan on labelled rows
    pos = lab["y90"] == 1
    for col in lab.select_dtypes("number").columns.drop("y90"):
        auc = (lab[col].rank()[pos].mean() - (pos.sum() + 1) / 2) / max((~pos).sum(), 1)
        if abs(auc - 0.5) > 0.4:
            print(f"LEAK SUSPECT {col}: univariate AUC={auc:.3f}")

pre_now = fixed_prefixes(df, K, EXTRACT)
X_now = features(pre_now, df)
leakage_audit(X_now, pre_now, ct_now)
variants = pm4py.get_variants(pre_now)              # audit: renamed activities must not create new prefix variants
print(pd.Series(variants).sort_values(ascending=False).head(10))

# ---------- 5. Temporal backtest: train on what was knowable at the cutoff, test on later starts ----------
def temporal_folds(ev, cutoffs, test_len=pd.Timedelta(days=91)):
    cols = ["state", "y90", "time", "event", "label_status", "regime"]
    for c in cutoffs:
        ct_c = case_table(ev, c)                                   # labels and censoring exactly as visible at c
        tr = features(fixed_prefixes(ev, K, c), ev).join(ct_c[cols], how="inner")
        tr_out = tr[tr["state"] == "activated"]                    # primary estimand is conditional on activation
        te_ids = ct_now.index[(ct_now["start"] > c) & (ct_now["start"] <= c + test_len)]
        te = X_now.join(ct_now.loc[te_ids, cols], how="inner")
        # HOOK: fit hazard model on tr_out[(time, event)] (rows with y90 NaN are censored, never zeros);
        #       evaluate IPCW Brier(90) / time-dependent AUC on te[state=='activated'];
        #       fit the application-stage multi-state model on all rows of tr (competing outcomes in 'state').
        yield c, tr, tr_out, te

for c, tr, tr_out, te in temporal_folds(df, pd.to_datetime(["2025-01-01", "2025-04-01", "2025-07-01", "2025-10-01"], utc=True)):
    te_out = te[te["state"] == "activated"]
    print(f"cutoff {c.date()} | train all={len(tr)} activated={len(tr_out)} labelled={tr_out['y90'].notna().sum()} "
          f"censored={tr_out['y90'].isna().sum()} | test activated={len(te_out)} labelled={te_out['y90'].notna().sum()} "
          f"| straddles policy change={c < POLICY_CHANGE <= c + pd.Timedelta(days=91)}")
# pm4py.split_train_test(df, train_percentage=0.8) is a random case split: use only as the naive baseline to
# demonstrate optimism; it mixes regimes, migration duplicates and future reference data into training.
```
