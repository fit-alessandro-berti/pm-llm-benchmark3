def canonical_key(execution):
    evs = sorted(execution.events, key=lambda e: e["time"])
    epos = {e.id: i for i,e in enumerate(evs)}

    trails = {}
    ext = {}
    for i,e in enumerate(evs):
        for o in e.objects():
            trails[o.id].append(i)
            ext[o.id] = str(o.id).startswith("EXT")
            otype[o.id] = o.type
    def canon_oid(o):

        return f"{o.type}-{'X' if ext[o] else 'L'}@{','.join(map(str,trails[o]))}"

## 1. Equivalence design space

I use the following equivalence relations. In all three, raw local object identifiers are not meaningful unless they use the `EXT` prefix or are required by the relation definition.

### Relation R1: Activity-sequence equivalence

**Definition.**  
Two executions are R1-equivalent iff their sequences of activity labels are identical:

\[
(a_1, a_2, \dots, a_n) = (b_1, b_2, \dots, b_n).
\]

Object types, object identifiers, external-object flags, E2O incidence, and O2O qualifiers are ignored.

**Invariants preserved:** activity label, event order, number of events, repeated activity labels.

**Information discarded:** all object information, identifier information, object multiplicities, package/delivery/invoice links, O2O qualifiers.

**Formal properties:** R1 is reflexive, symmetric, and transitive, because it is equality of tuples.

**Concurrency handling:** If events have identical timestamps, we first sort by timestamp and then by a stable activity-only order. A true concurrency-aware version would declare two traces equivalent when they become equal after taking a partial order over independent events; I do not use that version in the baseline because all examples are supplied with a total order.

---

### Eq R2: Typed structural equivalence under identifier renaming

Operations definition.

Each execution is represented as a typed event–object graph:

- event nodes are labelled by activity names and ordered by the trace;
- object nodes are labelled by their object type and by an external flag obtained from `EXT` prefix;
- an event node is connected to every object node appearing in that event;
- the graph is taken up to bijective renaming of object identifiers, preserving object type and external flag;
- local identifiers may be renamed, but an `EXT` identifier must remain `EXT`;
- event order is preserved.

Two executions are R2-equivalent iff such a bijective renaming exists.

Informally, R2 is “same activities in the same order with the same object-type incidence multiplicities, but raw names do not matter.”

**Invariants preserved:** object types, object multiplicities, E2O incidence, event order, repeated activities, and whether an object is external.

**Information discarded:** individual identifiers, exact `EXT-OA` vs `EXT-OB` names, O2O qualifiers unless they are encoded as ordinary object-relation edges.

**Formalive:** reflexive, symmetric, transitive, because it is defined by existence of an isomorphism.

**Logical concurrency handling:** if two events have the same timestamp, I treat them as unordered unless the object graph implies a causal ordering. The tie can be resolved by a deterministic canonical ordering; this does not change the isomorphism class.

---

### Eq R3: Business-semantic equivalence

Definition key.

R3 is the relation induced by the **canonical signature in Section 2**. It starts with the R2 graph but adds, in a canonical form:

- external object flags rather than raw `EXT` names;
- multiplicity of objects of the same type with the same lifecycle trail;
- `O2O` relation and qualifier terms, e.g. `partially_settles`, `completes_settlement`, `removed_before_dispatch`, `replaces`;
- lifecycle motifs: normal sale, split packing, split delivery, cross-order logistics sharing, cross-order billing, replacement before dispatch, return-and-repack;
- repeated activities and repeated objects as counts, not as hidden effects.

R3 is not a “sloppy” equivalence. It is exact after deleting raw identifiers. It is meant to classify executions by information that matters for business decisions.

**Invariants preserved:** all structural and relational semantic information listed above, excluding raw local IDs.

**Information discarded:** local identifiers and exact external identifiers.

**Formalive:** R3 is also reflexive, symmetric, and transitive, because equality of canonical signatures is an equality relation.

**Logical concurrency handling:** tied events are sorted deterministically by `(activity, canonical object signature)`. If two tied events are truly independent, any order produces the same R3 signature.

---

## 2. Canonical signatures

The following pseudocode defines the preferred signature used in Section 3. It should be stable under renaming of local identifiers but preserve object types, external flags, event order, E2O incidence, multiplicities, repeated activities, and O2O qualifiers.

```python
from collections import Counter, defaultdict

def canonical_key(execution):
    events = sorted(execution.events, key=lambda e: (e.time, e.origin_id))
    pos = {e.id: i for i, e in enumerate(events)}

    # Incidence trail of every object: event positions where it occurs.
    trail = defaultdict(list)
    is_ext = {}
    otype = {}
    for i, e in enumerate(events):
        for obj in e.objects:
            obj.id2 = obj.id
            otype[obj.id] = obj.type
            is_ext[obj.id] = str(obj.id).startswith("EXT")
            trail[obj.id].append(i)

    def canon_object(oid):
        ext = "X" if is_ext[oid] else "L"
        trail_s = ",".join(str(p) for p in sorted(trail[oid]))
        return f"{otype[oid]}-{ext}@{trail_s}"

    event_terms = []
    for e in events:
        obj_counter = Counter()
        for obj in e.objects:
            obj_counter[(obj.type, canon_object(obj.id))] += 1
        event_terms.append(
            (e.activity, tuple(sorted(obj_counter.items())))
        )

    # O2O relations, including qualifiers, are canonized using the same object keys.
    relation_terms = []
    for rel in getattr(execution, "relations", []):
        source = canon_object(rel.source)
        target = canon_object(rel.target)
        qualifier = str(rel.qualifier)
        relation_terms.append((qualifier, source, target))

    return (tuple(event_terms), tuple(sorted(relation_terms)))
```

A signature is high-level description:

```
signature = (ordered event terms, sorted O2O relation terms)
```

Two executions are placed in the same preferred semantic cluster exactly when their canonical signatures are equal.

## 4. Cluster interpretations

### S-Baseline (`X1`, `X2`)

**Concise signature:**  
One order, two items, one package, one delivery, one invoice, one payment. Every relation is one-to-one after renaming.

**Business behavior:** standard order-to-cash. The customer orders two article lines, they are packed in one shipment, delivered, invoiced, and paid exactly once.

**Operational risks below:** low structural risk. Failure risks are standard: package loss, delayed delivery, payment default.

**Traditional flattening risk:** one-row-per-order flattening is fine for summary metrics, but one-row-per-event flattening would duplicate the order and invoice information. One-row-per-package is still fine here because the package and order are one-to-one.

**Data-repair stability:** very stable. Simple ID repairs do not move the cluster.

---

### S-cluster (`X3`)

**Concise signature:**  
Two items, two packages, one dispatch carrying both packages, one invoice, one payment.

**Business semantics:** the order is split into two packages, probably for weight/packing reasons, and both are dispatched to the same logistics event.

**Opportunities/risks:** tracking at package level may require two tracking numbers; if the single dispatch fails, both packages fail together. Splitting introduces shipping cost allocation. The invoice is still one global invoice.

**Mutable flattening:** a traditional event-log flattening by order sees two `Pack` events and cannot tell whether they are the same dispatch or different. A flat table joining by delivery would create one row per package and duplicate invoice/payment.

**Data-repair stability:** if the two packages are merged, the instance moves to the baseline. If the delivery number is changed, it moves to S3. So the cluster is stable only if package and delivery definitions are stable.

---

### S-cluster (`X4`)

**Concise signature:**  
Two items, two packages, two independent dispatches, one invoice, and two payment events settling the same invoice.

**Operational semantics:** split fulfilment into independent delivery streams, and the customer pays in two instalments rather than one payment.

**Risks:** two deliveries create two arrival windows; the first payment may be partial and the second must complete. Payment allocation rules are implicit.

**Flattening:** flattening to one payment would make the process look like X1 and hide the settlement plan. Flattening to package would multiply invoice/payment.

**Data-repair stability:** stable as long as the second payment remains a separate payment event. If the two payments are coalesced, it becomes a baseline-style execution.

---

### S-cluster (`X5`)

**Concise signature:**  
Local order O5 has two local items and one local package; the Pack event also includes an external order and an external item. Invoice/payment contain only the local order.

**Business semantics:** cross-order parcel sharing. The physical package contains items for a different execution. The local order’s invoice is for its own items only, but the shipping object is shared.

**Operational risks:** cost allocation of shipping, customs/invoice mismatch, warehouse ownership, accidental substitution. A flat analysis of local order will not show the package-level sharing.

**Data-repair stability:** if someone removes `EXT` flags, the cluster collapses to baseline. The cluster is stable only if external objects are explicitly recorded.

---

### S-cluster (`X6`)

**Concise signature:**  
Logistics graph is like baseline; one invoice bills both the local order and an external order; one payment settles the invoice without explicit allocation to the external order.

**Business semantics:** joint billing, for example a corporate payer or consolidated billing statement. The local order does not have an independently settled payment record.

**Risks:** incoming payment may be allocated incorrectly, cross-order tax differences, disputes over overdue accounts.

**Flattening:** a flattening that drops the external order from invoice/payment produces a clean baseline diagram and overstates local payment correctness.

**Data-repair stability:** stable as long as external invoice linkage is retained.

---

### S-cluster (`X7`)

**Concise signature:**  
One package, one dispatch, one invoice, one payment; but before dispatch, one item is replaced by another and the original item is marked `removed_before_dispatch`.

**Business semantics:** replacement of goods before shipment. The facade looks like a normal sell-order flow, but the content of the package differs from the originally ordered items.

**Risks:** billing may include a wrong item, delivery manifest mismatches, replacement actions may be invisible with no O2O qualifiers.

**Flattening:** same as baseline at the level of activity sequence, so a basic process model cannot see replacement. Only object-qualified operations show this.

**Data-repair stability:** if the `O` qualified relation is lost but the item is still present in Dispatch, the execution probably moves to a different anomaly cluster, not baseline. If both the qualifier and the future shape are normalized, it collapses to baseline.

---

### S-cluster (`X8`)

**Concise signature:**  
Order first dispatches two items in one package; one item is returned, inspected, repacked, redispatched; then the invoice and payment happen.

**Business semantics:** a return/repack repair path. A goods defect or customer return result causes an extra dispatch before a final invoice.

**Risks:** double shipment, return quality, inventory duplication, the invoice is issued after the return has been resolved, so the final bill may be wrong.

**Flattening:** if only first shipment is captured, the execution looks like a normal order. If both dispatch events are captured without the return relation, the process seems like an incomplete order.

**Data-repair stability:** stable as long as the return and repack events remain.

### X1 versus X6

For root-cause analysis of returns, these must be distinct; for anomaly detection counts, one might first group them.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is a provided PM4Py function for object-centric execution clustering. I treat its key-repr as an exact structural representation of the lead object’s execution. Its key preserves, at minimum:

- activity names of all events in the execution;
- event order (or timestamp order);
- object identifiers and object types;
- E2O incidence, i.e., which object is connected to which event;
- possibly event attributes if they are included in the OCEL event table;
- it may not consume custom O2O qualified relations unless the O2O is stored as an event-level relation or as a object attribute.

Because the raw PM4Py key preserves raw object identifiers, exact raw keys are too fine. For example:

- `X1` and `X2` have different object IDs such as `O1/ O2`, `P11/P21`.
- A raw clustering algorithm would split them even though they are equivalent under ID renaming.
- Since each new instance has new unique IDs, raw exact-clustering degenerates into individual executions.

A useful post-processing step is to record raw clusters from PM4Py and then merge their executions by a canonical object-binding key. The code outline below shows that.

```python
import pm4py

# Input: an OCEL object residing in the environment.
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    lead_object_type="Order"
)

def canonical_key(execution):
    # Canonicalization method from Section 2.
    # Assume it returns a compact tuple from execution.events
    # and execution.relations.
    ...

business_clusters = {}

# post-process raw PM4Py returned clusters
for cluster_id, executions in raw_clusters.items():
    for ex in executions:
        key = canonical_key(ex)

```

If the result is too fine, simply comparing signatures of each PM4Py cluster and merging equal signatures loses local IDs and gives a more business-oriented cluster. This is the exactness plus canonicalization step.

Exact equivalence is preferable when: someone must compare forensic event-provenance; one must see if two instances differ at data level, see virtual data alignment, or test data not have expected object names. It is not preferable for reporting or segmentation because raw identifiers are not semantic.

For large connected executions, the `max_objs` setting (or max-size parameter if present) is significant:

- the connected component can be huge when package / item / order graphs are connected;
- if `max_objs` limits the object count to e.g. 1000, the algorithm may split one large execution into below-cutoff fragments;
- produced clusters become too fine for large orders or overly coarse if shared external orders connect many executions.

In practice one should choose a low object count for descriptive reporting, and use unbounded or large counts only when one actually wants to verify global connected graph.

## 7. Robustness analysis

### If all O2O qualifiers are ignored

The major differences are affected:

- X7 loses `removed_before_dispatch`; the execution is still not baseline because Dispatch has an item, but the replacement reason is not modeled.
- X8 loses `P82 replaces P81 for I82`; return/repack trace is still visible, but the fact of “item replacement” below the leading order disappears.

If the qualifier is the only evidence of the anomaly, cluster recovery cannot be valid. In these executions, the qualifiers are not the only evidence because the event shape itself also changes for X7 and X8; this makes X7 and X8 more resistant but semantically incomplete.

### If external objects are ignored

X5 and X6 both collapse into X1-like local signature. X7 remains separate because the dispatch event has a local item in Dispatch. X7 stays a process anomaly but is no longer understood as cross-order. This is a dangerous edge case: one could report “normal process” for X5/X6.

### If repeated same-label events are collapsed

`X4` has two `Record Payment` events; X2 has one. Collapsing identical repeated payment events would create X4 as “one payment” and incorrectly merge with a normal single-payment cluster. Collapsing the two consecutive `Pack` events in X4 may merge it with X3 at some high level, but if objects are counted during the collapse, the multiplicity can still be retained. If place tells process model, this can be very wrong.

### If Pack/Dispatch event order is treated as partial order

Because each logistics `Pack` has the same event slot, ordering between unrelated pairs is nonessential. Partial-order treatment generally preserves the distinction between `X3` (one consolidated dispatch) and `X4` (two separate dispatches), because the dispatch event itself identifies either one or two package objects. It improves robustness to before: there is no single best global order of two independent, very valuable ways.

### If payment multiplicity is transformed into an amount attribute

If both X4’s two payments are replaced by a single payment with amount 100%, X4 moves into baseline/S1. If one payment event is emitted per credit token, X4 is structurally distinct. This shows the importance of including payment-event multiplicity and payment qualifiers in a business semantics group.

## 8. Limitations and recommendation

- **Compliance monitoring:** use the canonical signature in Section 2, including O2O qualifiers, external object flags, and total event ordering. It is the only strict enough key because compliance only cares about full valid trace and object-role boundaries.
- **Operational segmentation:** use a business-semantic key rather than raw activity sequence. For example, cluster `X4`, `X5`, `X6`, `X7`, `X8` separately because their logistics, financial, and return risks differ. The baseline semantic S1 is acceptable for standard operational segment.
- **Root-cause analysis:** use signature instead of a single equivalence class. Key problematic motifs should be computed from the canonical signature: external object presence, package count, separate dispatch, multiple payments, return/repack, or replacement. The cluster group no longer matches in root cause; the motifs matter more.
- **Descriptive reporting:** activity-sequence equivalence is often enough for a dashboard process flow. For a dense process map, X1/X2/X3/X4/X7 may be compressed into the same nominal path, because their activity trace is similar. This is useful for viewers but must not be used for audit.

No single equivalence is best for all four. Compliance need exact object semantics; descriptive reporting need process abstraction. Raw identifier equivalence is too fine for any clustering. A good recommendation is to compute analyst-specific canonical signature, then keep the original raw PM4Py cluster attached as an audit argument, and choose among S1–S7 or coarse groupings depending on inverse-risk analysis.
