## 4. Expected flattened behavior

- **Order**: Traces will show `Create Order  Add Item  (Reserve Stock / Pack Package / Dispatch Package / Confirm Delivery)  Close Order`. Shared events (E06, E07, E09, E13) are copied into both O100 and O200 traces. The DFG will show parallel paths between Add Item and Close Order, with heavy co-occurrence edges between logistics activities. Misleading interpretation: flattening obscures that P1 physically merges items from two orders; each Order trace appears self-contained.
- **Package**: P1 trace: `Pack Package  Dispatch Package  Confirm Delivery`. P2 trace: identical. Clean, linear, no shared events. DFG shows strict sequential edges. No lifecycle omission since Packages are leaf logistics objects.
- **Delivery**: Identical to Package traces. DFG matches. Misleading aspect: Deliveries lack financial context; they cannot reveal invoice/payment flow.
- **Invoice**: V1 trace: `Issue Invoice  Record Payment  Record Payment`. Linear. DFG shows direct edges. Omitted lifecycle: no link to Orders/Items unless explicitly propagated, so invoice flattening cannot reconstruct fulfillment paths.
- **Why Payment flattening is weak**: Payments are terminal financial objects with only one activity (`Record Payment`). Flattening yields single-activity traces, destroying sequential structure and making DFG/skeleton discovery trivial and uninformative. They lack upstream lifecycle context.

## 5. Expected object-centric structures

- **OC-DFG**: Will highlight strong co-occurrence between `Pack Package` and `Dispatch Package` for P1/P2, and between `Issue Invoice` and `Record Payment` for V1. Cross-order edges will appear between `Reserve Stock`/`Pack Package` and both O100/O200, revealing the shared fulfillment pattern.
- **OTG**: Shows type-level transitions: `Order  Item` (contains), `Item  Package` (packs), `Package  Delivery` (carries), `Order  Invoice` (bills), `Invoice  Payment` (settles). The graph will expose that `Package` and `Invoice` act as integration hubs bridging operational and financial flows.
- **ET–OT**: Maps events to object state changes. `Pack Package` transitions Items to Packages; `Dispatch Package` transitions Packages to Deliveries; `Record Payment` transitions Invoice state. Highlights how E07 and E09 are the primary drivers of object lifecycle progression.
- **Object-centric Petri net**: Will contain multi-instance places for Orders, Items, Packages, and Payments. Synchronization tokens will converge at `Reserve Stock` and `Pack Package` (P1), and diverge at `Dispatch Package`. The net will not have a unique interpretation due to non-deterministic ordering of parallel order flows, but will correctly model the cross-order packaging constraint.
- **Object-interactions summary**: Matrix will show high interaction density between `Order``Package`, `Package``Delivery`, and `Invoice``Payment`. `Item``Order` and `Item``Package` will also be prominent. Reveals that P1 and V1 are the structural bridges connecting O100 and O200.

## 6. Modeling alternatives

1. **Source-minimal relations**: Link events only to their primary `target` object. E.g., `Pack Package` links only to P1/P2. *Effect*: Flattened Order traces lose logistics visibility; discovery algorithms must rely entirely on O2O traversal, which may fail if propagation isn't implemented. Business story unchanged, but analytical surface area shrinks.
2. **Full operational involvement**: Link every event to every transitively related object via O2O. E.g., `Confirm Delivery` links to D1, P1, I1, I3, O100, O200. *Effect*: Relation table inflates dramatically; DFGs become dense with spurious edges; discovery struggles with noise. Business story preserved but obscured by combinatorial explosion.
3. **O2O-propagated analytical relations**: Keep `relations` strictly observational (only direct links), and let PM4Py algorithms traverse `o2o` to infer cross-object paths. *Effect*: Cleanest data model; discovery results depend on algorithm support for O2O navigation. May miss implicit shared events if algorithms don't handle multi-object synchronization well. Business story remains intact and analytically separable.

## 7. Failure modes

1. **Relation inflation**: Over-linking events to transitively related objects creates dense, noisy DFGs and masks true process structure.
2. **Missing direct E2O links**: Omitting explicit links for shared events (e.g., E07 to O100/O200) forces reliance on O2O propagation, which some discovery algorithms ignore, breaking cross-order analysis.
3. **Treating O2O propagation as observation**: Baking transitive closure into `relations` conflates source facts with derived paths, making it impossible to distinguish system events from analytical artifacts.
4. **Duplicate shared events after flattening**: Flattening copies shared events into multiple object traces, artificially inflating trace lengths and creating false parallelism in traditional process mining.
5. **Ambiguous payment allocation**: Without explicit allocation logic, M1 and M2 both link to V1, but flattening cannot determine which Order's items each payment covers, obscuring financial reconciliation.
6. **Overly short Payment traces**: Flattening on Payments yields single-activity traces, rendering DFG/skeleton discovery useless and hiding settlement sequencing.
7. **Constructor/API version mismatch**: PM4Py's OCEL API evolved; using outdated constructor signatures or algorithm namespaces causes runtime failures without semantic data errors.
8. **False total order for same-time events**: Though this dataset has no ties, real systems often do. Flattening assumes strict temporal ordering, which can misalign concurrent cross-object events and distort DFG edges.
