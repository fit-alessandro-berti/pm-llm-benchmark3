**Optimization objectives (balanced, not maximized singly):**
- **Short-term throughput:** Complete activities quickly without unnecessary waiting.
- **SLA risk reduction:** Prioritize urgent and near-deadline cases; avoid missing deadlines.
- **Error/rework reduction:** Match required skill to resource competence; avoid weak-skill assignments on complex work.
- **Skill development:** Use documented training priorities in supervised or low-risk direct assignments.
- **Workload fairness:** Distribute new work considering current open cases, remaining hours, and overtime exposure.
- **Continuity of ownership:** Preserve current ownership on high-complexity / high-handover cases when skill is adequate.
- **Resilience:** Avoid concentrating critical activities in a single specialist; build supervision paths so absence does not stop the process.

# 2. Assignment policy

The policy is a **scored-filter algorithm** with explicit exception handling. It is explainable as a set of “rules of thumb” applied in sequence.

```text
FOR each case in queue:
  1. ELIGIBILITY FILTERING
     - Remove resources with skill = 0 for the required activity, UNLESS:
       * Activity = Security Review and resource in {R7,R8} can supervise a skill-1/2 worker
       * Activity = Final Approval and a skill-2/3 supervisor is paired
     - Apply Security rule: direct only if skill=3; else supervised pair with R7/R8
     - Apply Approval rule: direct finalizer must have skill>=2
     - For high/urgent priority: drop direct assignments with skill<2 unless a supervisor is in the pair

  2. SLA URGENCY SCORING (S_urg)
     S_urg = 1.0 if SLA_rem <= 4h
             0.7 if 4h < SLA_rem <= 8h
             0.4 if 8h < SLA_rem <= 24h
             0.0 otherwise
     (Higher = more urgency)

  3. SKILL-MATCH SCORING (S_sk)
     S_sk = skill_score / 3  (3=1.0, 2=0.67, 1=0.33, 0=excluded)

  4. CONTINUITY / HANDOVER-COST SCORING (S_con)
     If resource == current_owner:
        S_con = 0.5 - 0.15*reassignment_count - handover_penalty
          (low handover  0, medium  0.15, high  0.3)
     Else:
        S_con = -handover_penalty
     Exception: If complexity > 0.75 AND handover = high AND skill(current_owner) <=1
                 AND supervision feasible  allow supervised continuity instead of direct change.

  5. WORKLOAD & OVERTIME FAIRNESS (S_fair)
     open_norm = open_cases / 14   (scale against max observed)
     hours_norm = max(0, (6 - hours_remaining) / 6)  # less remaining = more loaded
     OT_penalty: high = -0.35, medium = -0.15, low = 0
     Batch guard: if resource already assigned 4 new cases in this batch  S_fair = -inf
     S_fair = - (0.4*open_norm + 0.4*hours_norm + OT_penalty)

  6. TRAINING / DEVELOPMENT SCORING (S_train)
     If case.priority in {normal,low} AND resource.training_priority == required_skill:
        If resource.skill <=1: S_train = +0.35 (supervised learning slot)
        Else: S_train = +0.15 (mentoring / refresh)
     Else: S_train = 0
     Constraint check: total training share >= 20% of normal/low assignments.

  7. RESILIENCE / BOTTLENECK AVOIDANCE (S_bot)
     Count pending queue cases needing the same specialist skill.
     If resource is one of very few specialists (e.g., Security 3) and queue >1:
        apply small negative penalty (-0.1) to prevent total dependency.
     Favor cross-team pairing when it spreads risk (e.g., Risk team supervises Quality trainee).

  8. COMPOSITE SCORE & TIE-BREAKING
     Score = 2.0*S_urg + 2.5*S_sk + 2.0*S_con + 1.5*S_fair + 1.0*S_train + S_bot
     (Weights reflect priority of safety/skill over speed; fairness is non-negotiable.)
     Tie-break order:
       a) Lower reassignment risk for the case
       b) Lower overtime risk of assigned resource
       c) Team alignment (same team preferred if scores equal)
       d) Lower current open cases

  9. EXCEPTION HANDLING
     - If best score violates a hard rule (e.g., unapproved skill 0 on Approval), pick next.
     - If SLA_rem < 4h and complexity > 0.8: override continuity preference and assign direct specialist even if handover is high (document exception).
     - If only one specialist exists for an urgent security case and that specialist is at 4 assignments, allow 5th only with explicit manager flag (not used here; R8/R7 within limits).
```

**Why this is explainable:** Every factor has a name workers recognize—urgency, skill, “who already owns it,” “how busy and tired the team is,” “learning goals,” and “not putting everything on one person.” The weights are not hidden magic; they are priorities agreed with supervisors.

2. **Urgency matters, but not blindly:** Cases with only hours left (C001, C002, C011) go to people who can finish them correctly now. We do not send urgent work to someone who is still learning, unless an expert is right there supervising.

3. **Keep ownership when it saves time:** For complicated cases that have already changed hands (C007 with three prior moves, C016 with high complexity), we try to keep the same worker. Changing owners on complex work adds waiting time and mistakes. We only change when the current worker is already overwhelmed or does not have the right skill.

4. **Protect people who are stretched:** Some colleagues already have very full desks and are at risk of overtime (R2, R4, R9). We did not add more to them today. Instead, we spread new work to people with capacity, like R3, R6, R8, R10, and R1, within a fair limit of four new cases each.

5. **Training is planned, not accidental:** We set aside specific cases for learning goals—R1 practicing diagnosis, R8 learning approval with R6 guiding him, and R5 learning security with R8 guiding her. These are normal or low-urgency cases with enough time in the schedule, so learning does not put customers at risk.

6. **Batching where it makes sense:** Two quality checks (C006, C012) are low urgency and well within deadlines, so they can be handled together by R10. That saves setup time.

7. **Every exception is noted:** When we broke continuity (for example, C001 moved to R8 because the case needed a specialist immediately), we wrote down why. You can ask about any case and we can show the reason.

This is not an automatic “black box.” It is a set of shared rules—urgency, skill, fairness, continuity, and learning—applied with human oversight.

# 6. Process-mining audit indicators

These indicators are designed to be computed from the event log using PM4Py and compared against the policy rules above.

| Indicator | Definition / Log computation | Policy audit purpose |
|---|---|---|
| **Handover frequency** | Count of cases with `reassignment_count > 0`. Use `pm4py.discover_handover_of_work_network` to visualize resource-to-resource transfers per activity. | Check if high-complexity cases are being protected; target <20% unnecessary handovers. |
| **Reassignment count (case-level)** | Derived from event log: count of distinct `org:resource` values in assignment/start events per `case:concept:name`. | Compare against policy intent; flag cases >2 reassigned for root-cause review (historical 1.8x rework risk). |
| **Skill mismatch** | For each assignment event, compare `required_skill` to resource’s skill score (from organizational role matrix). Compute % where assigned skill < required (excluding approved supervision pairs). | Ensure Security/Approval rules are met; detect unauthorized weak-skill direct assignments. |
| **Workload distribution** | At each assignment timestamp, capture `workload_snapshot` (open cases / remaining hours) per `org:resource`. Compute Gini coefficient or variance across resources per day. | Verify fairness; flag if high-OT resources receive disproportionate share. |
| **Overtime risk exposure** | Proportion of new assignments where resource `overtime_risk = high`. Filter log by `assignment_reason` or join with resource table. | Must stay near 0 except documented urgent exceptions; audit justification text. |
| **SLA misses** | Use `pm4py.filter_case_performance` comparing `time:timestamp` of final activity to `sla_deadline`. Compute miss rate by `case_priority`. | Validate urgency scoring effectiveness; high miss rate on urgent = policy failure. |
| **Rework / appeal after assignment** | Filter events where `concept:name` = Rework or Appeal occurring after the assignment event. Link back to assigned resource and skill match. Use `pm4py.discover_performance_dfg` to see loops. | Confirm that weak-skill direct assignments (especially on complex cases) increase downstream rework. |
| **Training assignment share** | Filter assignments where `assignment_reason` includes “training” or pair involves trainee + supervisor, restricted to `case_priority` in {normal, low}. Compute share of all normal/low assignments. | Must be >=20% when SLA risk is acceptable; audit that training is not crowding out urgent work. |
| **Specialist bottleneck indicators** | Use `pm4py.get_service_time` and `pm4py.insert_case_service_waiting_time` for Security/Approval/Diagnosis activities. Measure queue length (time between request and start) per specialist resource (`R7`, `R8`, `R6`, `R3`). | Detect concentration risk; if waiting time for Security grows, expand supervised training (e.g., R5). |
| **Deviations from assignment policy** | Store policy recommendation per case (resource/pair) in a case-level attribute. Compare with actual `org:resource` at execution. Compute deviation rate and reason category (workload override, urgency exception, supervision, manual override). | Ensure explainability; every deviation should have a documented reason aligned with exception rules. |
