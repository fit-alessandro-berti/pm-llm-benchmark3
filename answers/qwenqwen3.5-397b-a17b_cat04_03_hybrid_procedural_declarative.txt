# 1. Policy Interpretation and Conflict Resolution

### Material Assumptions
1.  **Event Log Schema:** The log contains `case_id`, `activity`, `timestamp`, and `resource`. It **does not** contain an `emergency_authorization` boolean or `risk_level` data attribute, as explicitly stated in R6.
2.  **Case Lifecycle:** A case ends at `Close Onboarding`. Activities after `Close Onboarding` (e.g., `Change Bank Details` in R11) are treated as part of a post-onboarding lifecycle or a new case context, but for this model, we assume they can appear in the same trace if the case remains open or if we treat the log as a continuous vendor lifecycle. Given T1-T8 end at `Close Onboarding`, R11 is treated as a constraint on traces that *include* post-activation activities.
3.  **Clarification Loop:** R3 implies a strict request-response pairing. A `Request Clarification` without a matching `Receive Clarification` before the next request or outcome is a violation.

### R5 vs. R6 Conflict Resolution
**Conflict:**
*   **R5 (Legal):** `Sanctions Escalation` $\rightarrow$ `Obtain Legal Opinion` $\rightarrow$ `Activate Vendor`. (Strict Order)
*   **R6 (Operations):** `Sanctions Escalation` $\rightarrow$ `Activate Vendor` $\rightarrow$ `Obtain Legal Opinion` (within 24h). (Reversed Order, Time-Bound)

**Resolution Options:**
1.  **Strict Legal Enforcement (Chosen):** Enforce R5 in the control-flow model. R6 is treated as an exception requiring a data attribute (`emergency_flag`) which is currently missing. Cases violating R5 are flagged as non-compliant unless the missing attribute is retroactively added.
2.  **Relaxed Operational Enforcement:** Allow both orderings in control flow. Enforce the 24h time constraint (R12/Temporal) if the order is reversed. This risks legal non-compliance if the emergency authorization was not actually granted.

**Decision:**
I choose **Strict Legal Enforcement (R5)** for the automated Control Flow (Procedural/DECLARE) layers.
*   **Reasoning:** Control-flow models should enforce the "happy path" and mandatory compliance rules. R6 relies on an out-of-band authorization ("jointly authorized outside the event log") that is invisible to the miner. Enforcing R6 without the attribute would legitimize unauthorized emergency activations.
*   **Compliance Risk:** Valid emergency cases (R6) will be flagged as violations (False Positives) in the control-flow layer. This requires a manual review step (Resource/Data Layer) to clear cases where the missing authorization evidence exists offline.

*   **Concurrency:** The three initial checks are parallel (`PARALLEL`).
*   **Clarification:** Modeled as a `LOOP`. In PM4Py, this allows 0 or more iterations. R3 (pairing) is enforced by the loop body structure, but DECLARE ensures no orphaned requests.
*   **Terminal Outcomes:** The `XOR` split ensures only one path (Reject, Low, High) is taken.
*   **Post-Activation:** `Change Bank Details` and `Suspend Vendor` are excluded from the main tree as they represent a post-onboarding lifecycle (R11). They are handled via DECLARE/Resource checks if present in the log.
*   **Escalation/Legal:** Added as optional parallel activities to prevent structural rejection of traces like T6/T7, deferring ordering logic to DECLARE (R4, R5).

```python
    "Activate Vendor": {
        "template": "at_most_one",
        "support": 1.0,
        "confidence": 1.0
    },
    "Reject Vendor": {
        "template": "at_most_one",
        "support": 1.0,
        "confidence": 1.0
    },
    # R11: Bank Change requires Suspend
    ("Change Bank Details", "Suspend Vendor"): {
        "template": "chain_response",
        "support": 1.0,
        "confidence": 1.0
    }
}
```

### Rule Semantics Table

| Rule Key | Template | Semantics | Direction |
| :--- | :--- | :--- | :--- |
| (Reject, Activate) | `noncoexistence` | Both cannot exist in same case. | Symmetric |
| (Request, Receive) | `response` | If Request occurs, Receive must follow. | Forward |
| (Receive, Request) | `precedence` | Receive cannot occur before Request. | Backward |
| (Escalation, Opinion) | `response` | If Escalation occurs, Opinion must follow. | Forward |
| (Opinion, Activate) | `precedence` | Activate cannot occur before Opinion. | Backward (R5) |
| (Screening, Escalation) | `precedence` | Escalation cannot occur before Screening. | Backward |
| (Manager, Compliance) | `noncoexistence` | Both approvals cannot exist. | Symmetric |
| Activate Vendor | `at_most_one` | Activity occurs max 1 time. | Unary |
| (Change, Suspend) | `chain_response` | Suspend must immediately follow Change. | Forward |

```python
log_skeleton = {

    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Close Onboarding": {1},
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1}
    },
    # Stable Directly Follows (Backbone)
    "directly_follows": {

        ("Release First Payment", "Close Onboarding"),
        ("Reject Vendor", "Close Onboarding")
    }

```

### Overlap and Disagreement
*   **Overlap:** `never_together` duplicates DECLARE `noncoexistence`. `activ_freq` duplicates DECLARE `at_most_one`. This provides redundancy; if DECLARE fails due to noise, Log Skeleton might still catch frequency anomalies.
*   **Disagreement:** `always_before` in Log Skeleton is strict. If `Obtain Legal Opinion` is optional (not in every case), `always_before` might be too strong if interpreted as "in every case". However, in Log Skeleton semantics, `always_before(A, B)` usually means "If B occurs, A must have occurred before". This aligns with R5.
*   **Orientation:** `directly_follows` is specific to the happy path. Traces with Clarification loops will violate `directly_follows` (e.g., Screening $\rightarrow$ Request Clarification), which is expected. Log Skeleton is used here for *stable* backbone relations only.

# 6. Temporal Profile

```python
import math

# Conversion: Hours * 3600 = Seconds
temporal_profile = {
    # R12: Request Clarification -> Receive Clarification
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    # R12: Sanctions Escalation -> Obtain Legal Opinion
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    # R12: Activate Vendor -> Release First Payment
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}

zeta = 2.0
```

### Warning vs. Violation
Temporal deviations are configured as **warnings** because:
1.  **Business Reality:** Delays happen due to external factors (vendor response time, legal backlog) that do not necessarily imply process fraud or control failure.
2.  **Statistical Nature:** The profile uses mean and standard deviation. A value outside $2\sigma$ (zeta=2.0) is statistically rare (approx. 5% probability) but not impossible.
3.  **Separation of Concerns:** Control flow (DECLARE/Procedural) handles *logic* violations (e.g., missing approval). Temporal profiles handle *performance* deviations. A late legal opinion is a performance issue; a missing legal opinion is a compliance issue.

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
import pm4py

def check_resource_and_data_constraints(log_df):
    """
    log_df: Pandas DataFrame with columns ['case_id', 'activity', 'resource', 'timestamp']
    Returns: Dictionary of violations
    """
    violations = {
        "sod_violations": [],
        "emergency_policy_violations": [],
        "missing_attributes": []
    }
    
    # R9: SoD - Verify Bank Account vs Approval
    # Check 1: Verify Bank Account vs Manager Approval
    sod_violations_1 = pm4py.filter_four_eyes_principle(
        log_df, 
        activity1="Verify Bank Account", 
        activity2="Manager Approval"
    )
    # Note: pm4py.filter_four_eyes_principle usually returns log that SATISFIES the principle.
    # We need to identify cases that VIOLATE it (same resource).
    # Implementation detail: We manually check resources per case for robustness.
    
    cases = log_df['case_id'].unique()
    for case in cases:
        case_events = log_df[log_df['case_id'] == case].sort_values('timestamp')
        
        # R9: Verify Bank vs Approvals
        verify_res = case_events[case_events['activity'] == 'Verify Bank Account']['resource'].unique()
        mgr_res = case_events[case_events['activity'] == 'Manager Approval']['resource'].unique()
        comp_res = case_events[case_events['activity'] == 'Compliance Approval']['resource'].unique()
        
        # Check intersection
        if len(verify_res) > 0 and len(mgr_res) > 0:
            if set(verify_res) & set(mgr_res):
                violations["sod_violations"].append(f"Case {case}: Verify Bank & Manager Approval same resource")
        if len(verify_res) > 0 and len(comp_res) > 0:
            if set(verify_res) & set(comp_res):
                violations["sod_violations"].append(f"Case {case}: Verify Bank & Compliance Approval same resource")

        # R9: Capture Master Data vs Activate Vendor
        capture_res = case_events[case_events['activity'] == 'Capture Master Data']['resource'].unique()
        activate_res = case_events[case_events['activity'] == 'Activate Vendor']['resource'].unique()
        if len(capture_res) > 0 and len(activate_res) > 0:
            if set(capture_res) & set(activate_res):
                violations["sod_violations"].append(f"Case {case}: Capture Data & Activate Vendor same resource")

        # R6: Emergency Policy Check
        # Logic: If Activate Vendor occurs BEFORE Obtain Legal Opinion (violates R5),
        # check for 'emergency_flag' attribute.
        activate_time = case_events[case_events['activity'] == 'Activate Vendor']['timestamp']
        opinion_time = case_events[case_events['activity'] == 'Obtain Legal Opinion']['timestamp']
        
        if not activate_time.empty and not opinion_time.empty:
            if activate_time.iloc[0] < opinion_time.iloc[0]:
                # R5 Violation detected. Check R6 exception.
                # Check for attribute 'emergency_authorized' (Assumed column name)
                if 'emergency_authorized' in case_events.columns:
                    is_emergency = case_events['emergency_authorized'].iloc[0]
                    if not is_emergency:
                        violations["emergency_policy_violations"].append(f"Case {case}: Activation before Opinion without emergency flag")
                else:
                    violations["missing_attributes"].append(f"Case {case}: Missing 'emergency_authorized' attribute to validate R6")
                    
    return violations
```

*   **`emergency_authorized`:** Required for R6 exception handling. If missing (as per Scenario), all R5 violations (Activation before Opinion) are treated as hard failures in the Data Layer, flagged for manual review.

# 9. Contradictions, Redundancies, and Blind Spots

1.  **Duplicated Enforcement:** R1 (Mutex) and R10 (Cardinality) are enforced in DECLARE, Log Skeleton, and partially in the Procedural XOR split. This redundancy increases robustness but adds maintenance overhead. If the Process Tree changes, DECLARE rules must be audited.
2.  **Loop Vacuity:** In DECLARE, `response`('Request', 'Receive') is vacuously true if `Request Clarification` never occurs. This is correct behavior, but analysts might misinterpret "Pass" as "Clarification was handled" rather than "Clarification was not needed".
3.  **Missing Case Attributes:** R6 (Emergency) cannot be enforced because the log lacks the `emergency_authorized` attribute. This creates a "Blind Spot" where legitimate emergency cases look like violations.
4.  **Timestamp Limitations:** Temporal Profile relies on event timestamps. If `Receive Clarification` is logged only when entered into the system (not when received from vendor), the elapsed time metric is skewed.
5.  **Support/Confidence Metadata:** Setting `support: 1.0` in DECLARE implies the rule holds for *all* historical data. If the log contains noise, this model will reject valid cases. In production, these should be learned from data (e.g., `support: 0.95`).
6.  **Post-Activation Blindness:** The Procedural model closes the case at `Close Onboarding`. R11 (`Change Bank Details`) occurs after activation. If this happens in a new case ID, the link to the original onboarding is lost, making R11 unenforceable without a persistent `vendor_id` across cases.

# 10. Deployment Recommendation

1.  **Canonical Representation:** Use the **Process Tree** as the primary visualization for stakeholders (easy to understand). Use **DECLARE** as the authoritative enforcement engine for conformance checking (more flexible to deviations).
2.  **Authoritative Policy Layer:** The **DECLARE Model** is authoritative for compliance rules (R1, R3, R4, R5, R8). The **Resource/Data Layer** is authoritative for SoD (R9) and Emergency Exceptions (R6).
3.  **Check Order:**
    1.  **Procedural Conformance:** Filter out traces that are structurally nonsensical (e.g., missing Start/End).
    2.  **DECLARE Conformance:** Identify logical violations (e.g., missing approvals, wrong order).
    3.  **Resource/Data Checks:** Identify SoD violations and missing attributes.
    4.  **Temporal Profile:** Generate performance warnings (do not block process).
4.  **Surfacing Contradictions:**
    *   If a case fails DECLARE (R5) but has a manual override note, it should be flagged as **"Exception Requires Review"**.
    *   SoD violations (R9) should be escalated immediately to Security/Compliance.
    *   Temporal warnings should be aggregated for Process Owner dashboards, not individual case alerts.
5.  **Handling R6:** Implement a mandatory data entry field `emergency_authorized` in the onboarding system. Until then, all R5 violations must be manually reviewed to distinguish between fraud and authorized emergency operations.
