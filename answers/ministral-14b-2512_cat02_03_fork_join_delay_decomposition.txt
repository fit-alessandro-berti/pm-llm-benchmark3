# 1. Delay-decomposition definitions

We decompose case-level flow time into mutually exclusive components using the following definitions for case index `c` and branch index `i  {A,B,C}`:

- **Upstream elapsed time**: `upstream_elapsed_c = fork_release_c - arrival_c`
  *Time from case arrival to when branches can begin.*

- **Branch queue delay**: `queue_delay_i,c = max(0, branch_start_i,c - fork_release_c)`
  *Time branch `i` waits in its own queue after `fork_release`.*

- **Branch active service**: `service_i,c = branch_end_i,c - branch_start_i,c`
  *Actual processing time for branch `i`.*

- **Branch synchronization wait**: `sync_wait_i,c = max(0, join_ready_c - branch_end_i,c)`
  *Time branch `i` waits after completion until the last branch finishes (`join_ready`).*
  **Key insight**: Summing `sync_wait_i,c` across all branches would double-count the elapsed time between `join_ready` and `final_start` because only one branch determines `join_ready`. Instead, we use the **critical branch** (the one with the latest completion) to define `join_ready_c = max(A_end_c, B_end_c, C_end_c)`.

- **Fork-join stage time**: `fork_join_c = join_ready_c - fork_release_c`
  *Total elapsed time from when branches can start until the last branch completes.*

- **Downstream queueing**: `downstream_queue_c = final_start_c - join_ready_c`
  *Time between last branch completion and when the final activity can start (due to resource F1/F2 availability).*

- **Final service**: `final_service_c = final_end_c - final_start_c`
  *Time spent in the final activity.*

- **Total flow time**: `total_flow_time_c = final_end_c - arrival_c`
  *Sum of all components.*

**Critical branch**: The branch with the latest completion (`join_ready_c`) for each case. This branch determines synchronization waits for all other branches.

# 5. Recommended redesigns and risks

### **Redesign 1: Prioritize Branch B Queue Reduction**
**Action**: Allocate additional resources to Branch B to reduce its queue delay (currently 17.5 min on average).
- **Throughput**: Likely to increase, as **B** is the critical branch in 42% of cases.
- **Flow-time tail**: Reduce tail flow times for cases where **B** is critical (e.g., **F07**, **F09**).
- **Resource utilization**: May require hiring or reallocating staff for **B**.
- **New bottlenecks**: If **A** or **C** become critical after **B** is improved, their queue delays may increase.
- **Pilot**: Measure **B**’s queue delay before/after adding resources and track critical branch frequency.

### **Redesign 2: Parallelize Branch A Service**
**Action**: Introduce parallel processing or automation for Branch A to reduce its service time (currently 50 min).
- **Throughput**: May increase, as **A** is critical in 33% of cases.

- **Resource utilization**: May require investment in lab equipment or automation.
- **New bottlenecks**: If **A** is sped up, **B** or **C** may become more critical, increasing their queue delays.
- **Pilot**: Test parallel lab assays and measure service time reduction and critical branch shifts.

# 7. Limits of inference
1. **Causality**: The timestamps do not reveal why branches queue or why certain branches are critical (e.g., resource constraints, workload variability).
2. **Branch Resource Capacity**: We cannot infer how many resources are allocated to each branch or their utilization.
3. **Work Preemption**: The data does not show if branches can be interrupted or preempted.
4. **Downstream Queueing**: The `downstream_queue` column is inconsistent with `final_start` and `join_ready` in some cases (e.g., F02). It may reflect a release policy rather than a true queue.
5. **Branch Dependencies**: No information exists about dependencies between branches (e.g., if **C** depends on **A**’s output).
6. **External Delays**: Delays not logged (e.g., material shortages) cannot be identified.
7. **Resource Contention**: The final station’s resource allocation (F1/F2) is not modeled dynamically; we assume it is a queue.
