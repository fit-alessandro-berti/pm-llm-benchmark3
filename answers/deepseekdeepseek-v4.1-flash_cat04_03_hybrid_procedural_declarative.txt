```python
def resource_check(df):
    # df columns: case_id, activity, timestamp, resource
    violations = []
    for cid, g in df.sort_values("timestamp").groupby("case_id"):

        if "Capture Master Data" in by_act and "Activate Vendor" in by_act:

            r_act = by_act["Activate Vendor"]["resource"].iloc[0]
            if pd.isna(r_cap) or pd.isna(r_act):
                violations.append((cid, "missing_resource", "Capture/Activate"))
            elif r_cap == r_act:
                violations.append((cid, "R9b", "Capture Master Data same as Activate Vendor"))

        if "Verify Bank Account" in by_act and "Activate Vendor" in by_act:
            approv = None
```

# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**

- A case is **accepted** if `Activate Vendor` occurs; it is **rejected** if `Reject Vendor` occurs.
- The three initial checks — `Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account` — are concurrent and may appear in any order before `Classify Risk`.
- `Request Clarification` / `Receive Clarification` is a zero-or-more loop before `Classify Risk` in the procedural backbone. Each request must be answered before the next request and before classification/outcomes.
- Cross-cutting activities `Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, and `Suspend Vendor` are not part of the minimal procedural backbone. They are handled by DECLARE, temporal, and resource/data layers. Procedural conformance is evaluated on the backbone projection unless full replay is explicitly configured with silent self-loops.
- Missing resource or case attributes do **not** count as passing a resource/data rule; they are `not evaluated` or require manual review.
- Temporal-profile deviations are warnings, not automatic control-flow rejections.

**R5/R6 conflict resolutions**

1. **Strict legal interpretation of R5.**
   - If `Sanctions Escalation` occurs, `Obtain Legal Opinion` must occur before `Activate Vendor`.
   - Emergency activation before `Obtain Legal Opinion` is non-conformant because the event log lacks `emergency_joint_authorization` and the required external authorization evidence.

2. **Operational exception interpretation of R6.**
   - `Activate Vendor` may occur before `Obtain Legal Opinion` only if an external case attribute `emergency_joint_authorization == True` exists.
   - In that case, `Obtain Legal Opinion` must occur within 24 hours after `Activate Vendor`.
   - Otherwise, the case is non-conformant under R5.

**Chosen implementation:** I use the **strict legal interpretation** for the automated model. The resource/data layer additionally exposes a configurable operational-exception check. This avoids silently combining incompatible policies: the default verdict is strict, and emergency activation is `policy-dependent` or `fail` unless explicit external authorization is supplied.

**Compliance risk of this choice:** Strict R5 may falsely block legitimate emergency activations that were jointly authorized outside the log. The operational exception reduces that risk but introduces a different risk: if the external authorization attribute is missing, spoofed, or not auditable, unauthorized activation could be accepted.

**Formal description**

```text
P =
seq(
```

**PM4Py-style code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def silent():
    return ProcessTree()

def seq(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

def par(*children):
    return ProcessTree(operator=Operator.PARALLEL, children=list(children))

def loop(body, redo, exit_):
    # PM4Py ProcessTree LOOP is normally three-child: body, redo, exit.
    return ProcessTree(operator=Operator.LOOP, children=[body, redo, exit_])

checks = par(
    leaf("Capture Master Data"),
    leaf("Run Sanctions Screening"),
    leaf("Verify Bank Account")
)

clarify_cycle = seq(
    leaf("Request Clarification"),
    leaf("Receive Clarification")
)

# Zero or more clarification cycles before Classify Risk.
clarify_loop = loop(silent(), clarify_cycle, silent())

reject = seq(
    leaf("Reject Vendor"),
    leaf("Close Onboarding")
)

low = seq(
    leaf("Manager Approval"),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding")
)

high = seq(
    leaf("Enhanced Due Diligence"),
    leaf("Compliance Approval"),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding")
)

outcome = xor(reject, low, high)

procedural_model = seq(
    leaf("Receive Onboarding Request"),
    checks,
    clarify_loop,
    leaf("Classify Risk"),
    outcome
)
```

**Explanation**

- **Concurrency:** the three checks are under a `PARALLEL` operator. They may interleave arbitrarily, but all three must complete before `Classify Risk`.
- **Choices:** after `Classify Risk`, exactly one XOR branch is selected: rejection, low-risk acceptance, or high-risk acceptance.
- **Clarification loops:** the loop allows zero or more `Request Clarification  Receive Clarification` cycles before classification. This is a deliberate approximation: the procedural model enforces clarification completion before classification/outcomes, while DECLARE enforces the request/response pairing.
- **Terminal outcomes:** rejection ends with `Reject Vendor  Close Onboarding`; low-risk acceptance uses `Manager Approval  Activate Vendor  Release First Payment  Close Onboarding`; high-risk acceptance uses `Enhanced Due Diligence  Compliance Approval  Activate Vendor  Release First Payment  Close Onboarding`.
- **Post-activation behavior:** `Change Bank Details` and `Suspend Vendor` are deliberately excluded from the backbone. They are post-activation exception behavior and are checked by the resource/data layer. `Sanctions Escalation` and `Obtain Legal Opinion` are also excluded from the backbone and handled by DECLARE and resource/data checks. For strict full replay, project the log onto the backbone alphabet or add silent self-loops for these cross-cutting activities.

| `response` | `(Change Bank Details, Suspend Vendor)` | If bank details change, suspend must occur later. | Conservative approximation for R11. The authoritative check is resource/data-aware because R11 is conditional on post-activation timing. |
| `precedence` | `(Run Sanctions Screening, Sanctions Escalation)` | Escalation may occur only if sanctions screening already occurred. | R7. `precedence(A,B)` means B cannot happen unless A has happened before. |

**Response vs precedence:** `response(A,B)` means “after A, B eventually occurs.” `precedence(A,B)` means “B may occur only if A occurred before.” They are not inverses and enforce different directions.

**Alternate response vs chain response:** `altresponse(A,B)` allows arbitrary intervening events but forbids the next A before B. `chainresponse(A,B)` would require B to be the immediate next event after A, which is too strong for R3.

**Noncoexistence vs nonsuccession:** `noncoexistence(A,B)` forbids both activities anywhere in the case. `nonsuccession(A,B)` would forbid an ordered occurrence pattern. R1 and R8 are mutual-exclusion requirements, so `noncoexistence` is appropriate.


**Orientation and semantics**

- `always_before(A,B)` means `A` is always before `B` in cases where `B` occurs.
- `always_after` is empty to avoid double-encoding the inverse orientation.
- `never_together(A,B)` is symmetric: the two activities must not both occur.
- `activ_freq(activity) = allowed_counts` gives allowed occurrence counts.
- `directly_follows(A,B)` means `B` immediately follows `A`.

**Overlap and disagreement**

- `never_together` duplicates DECLARE `noncoexistence` for R1 and R8.
- `activ_freq` is the authoritative layer for R10; DECLARE in the simplified dictionary does not encode “at most once” cleanly.
- `always_before(("Run Sanctions Screening","Sanctions Escalation"))` duplicates DECLARE precedence for R7.
- The Log Skeleton does not encode R3’s request/response cycle semantics; DECLARE is authoritative there.
- The Log Skeleton does not encode R4 because “if escalation then legal opinion later” is a conditional response, not a universal precedence over all cases.
- `directly_follows` only includes terminal edges that are stable in the backbone. It does not require `Activate Vendor  Release First Payment` because T6 has `Obtain Legal Opinion` after activation before release, and T8 has activation followed by rejection.

# 7. Resource- and Data-Aware Checks

Required event attributes: `case_id`, `activity`, `timestamp`, `resource`.  
Required case-level attributes where needed: `emergency_joint_authorization` for R6, plus any bank-change authorization metadata if available for R11.

```python
import pandas as pd

def get_case_attribute(case_attrs, case_id, attr_name):
    # case_attrs: DataFrame with columns case_id, attr_name, value
    row = case_attrs[
        (case_attrs["case_id"] == case_id) &
        (case_attrs["attr_name"] == attr_name)
    ]
    if row.empty:
        return None
    return row["value"].iloc[0]

def resource_and_data_checks(df, case_attrs=None, allow_emergency_exception=False):
    violations = []
    if case_attrs is None:
        case_attrs = pd.DataFrame(columns=["case_id", "attr_name", "value"])

    for cid, g in df.sort_values("timestamp").groupby("case_id"):
        g = g.sort_values("timestamp")
        by_act = {a: sub for a, sub in g.groupby("activity")}

        # R9b: Capture Master Data vs Activate Vendor
        if "Capture Master Data" in by_act and "Activate Vendor" in by_act:
            r_cap = by_act["Capture Master Data"]["resource"].iloc[0]
            r_act = by_act["Activate Vendor"]["resource"].iloc[0]
            if pd.isna(r_cap) or pd.isna(r_act):
                violations.append((cid, "R9b", "missing resource for Capture/Activate", "not_evaluated"))
            elif r_cap == r_act:
                violations.append((cid, "R9b", "Capture Master Data and Activate Vendor same resource", "fail"))

        # R9a: Verify Bank Account vs applicable approval
        if "Verify Bank Account" in by_act and "Activate Vendor" in by_act:
            approval = None
            if "Manager Approval" in by_act:
                approval = "Manager Approval"
            if "Compliance Approval" in by_act:
                approval = "Compliance Approval" if approval is None else "BOTH_APPROVALS"
            if approval in ("Manager Approval", "Compliance Approval"):
                r_ver = by_act["Verify Bank Account"]["resource"].iloc[0]
                r_app = by_act[approval]["resource"].iloc[0]
                if pd.isna(r_ver) or pd.isna(r_app):
                    violations.append((cid, "R9a", "missing resource for Verify/Approval", "not_evaluated"))
                elif r_ver == r_app:
                    violations.append((cid, "R9a", "Verify Bank Account and applicable approval same resource", "fail"))
            elif approval == "BOTH_APPROVALS":
                violations.append((cid, "R2/R8", "both Manager and Compliance approvals present", "fail"))

        # R2: accepted/rejected approval obligations
        if "Activate Vendor" in by_act:
            n_app = int("Manager Approval" in by_act) + int("Compliance Approval" in by_act)
            if n_app != 1:
                violations.append((cid, "R2", f"accepted case has {n_app} approvals", "fail"))
        if "Reject Vendor" in by_act:
            if "Manager Approval" in by_act or "Compliance Approval" in by_act:
                violations.append((cid, "R2", "rejected case has an approval", "fail"))

        # R5/R6: escalation, legal opinion, activation
        if "Sanctions Escalation" in by_act and "Activate Vendor" in by_act:
            t_esc = by_act["Sanctions Escalation"]["timestamp"].min()
            t_act = by_act["Activate Vendor"]["timestamp"].min()
            t_olo = by_act["Obtain Legal Opinion"]["timestamp"].min() if "Obtain Legal Opinion" in by_act else None

            if t_olo is None:
                violations.append((cid, "R4/R5", "activation after escalation without legal opinion", "fail"))
            elif t_olo < t_act:
                pass  # strict R5 satisfied
            else:
                # Activation before legal opinion: emergency path.
                auth = get_case_attribute(case_attrs, cid, "emergency_joint_authorization")
                if allow_emergency_exception and auth is True:
                    if (t_olo - t_act) <= 24 * 3600:
                        pass  # R6 satisfied under operational exception
                    else:
                        violations.append((cid, "R6", "legal opinion later than 24h after emergency activation", "fail"))
                elif allow_emergency_exception and auth is None:
                    violations.append((cid, "R6", "missing emergency_joint_authorization", "policy-dependent"))
                else:
                    violations.append((cid, "R5", "activation before legal opinion without valid emergency authorization", "fail"))

        # R11: post-activation bank changes
        if "Change Bank Details" in by_act and "Activate Vendor" in by_act:
            t_act = by_act["Activate Vendor"]["timestamp"].min()
            changes = by_act["Change Bank Details"].sort_values("timestamp")
            for _, ch in changes.iterrows():
                t_ch = ch["timestamp"]
                if t_ch > t_act:
                    # Suspend must eventually follow the change.
                    if "Suspend Vendor" not in by_act:
                        violations.append((cid, "R11", "bank change after activation without Suspend Vendor", "fail"))
                    else:
                        t_susp = by_act["Suspend Vendor"]["timestamp"].min()
                        if t_susp < t_ch:
                            violations.append((cid, "R11", "Suspend Vendor occurs before bank change", "fail"))

                    # If a later Release First Payment exists, require another Verify before it.
                    if "Release First Payment" in by_act:
                        t_rel = by_act["Release First Payment"]["timestamp"].min()
                        if t_rel > t_ch:
                            ver_after = by_act["Verify Bank Account"][
                                by_act["Verify Bank Account"]["timestamp"] > t_ch
                            ]
                            ver_before_rel = ver_after[ver_after["timestamp"] < t_rel]
                            if ver_before_rel.empty:
                                violations.append((cid, "R11", "no re-verification before later Release First Payment", "fail"))

    return violations
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement.** R1 is enforced by procedural XOR, DECLARE `noncoexistence`, Log Skeleton `never_together`, and resource/data R2. R7 is enforced by DECLARE precedence and Log Skeleton `always_before`. R8 is enforced by DECLARE `noncoexistence` and Log Skeleton `never_together`. This redundancy is useful for defense in depth but can produce multiple findings for one root cause.
- **Loops and post-activation changes.** R3 can create multiple `Request Clarification` / `Receive Clarification` cycles. `altresponse` is needed to forbid two requests before a response. R11 becomes ambiguous when `Verify Bank Account` already occurred earlier; the data layer must interpret “another Verify” as an occurrence after the relevant `Change Bank Details` event. If `Change Bank Details` occurs after `Release First Payment`, there may be no “later Release First Payment”; the check should still require `Suspend Vendor` but not demand a re-verification before a nonexistent later release.
- **Vacuity in declarative rules.** Rules involving `Sanctions Escalation`, `Change Bank Details`, or `Request Clarification` pass vacuously when the antecedent never occurs. Support/confidence metadata set to `1.0` in a normative model does not mean the rule was empirically tested; it is a policy assertion. Vacuously satisfied rules should not be reported as positive evidence.
- **Missing case attributes.** The event log does not contain `emergency_joint_authorization`, risk classification, bank-change reason, or external legal authorization. Activity-only models cannot recover these. Missing attributes must lead to `not evaluated`, `policy-dependent`, or manual review, not automatic pass.
- **Timestamp-only limitations.** Timestamps show order and elapsed time, but not causality, authorization, or whether an emergency policy applied. Temporal profiles assume a distribution and use `zeta = 2.0`; they flag unusual durations but do not prove policy violation.
- **Support/confidence metadata.** The DECLARE dictionary uses `support=1.0` and `confidence=1.0` as normative placeholders. In real deployment, these should be replaced by empirical support/confidence or clearly marked as policy rules, not inferred truth.
- **R5/R6 incompatibility.** The legal and operations policies conflict unless emergency authorization is explicitly represented. Strict R5 rejects emergency activation before legal opinion. Operational R6 accepts it only with external authorization and a 24-hour deadline. The model must not silently choose both.

# 10. Deployment Recommendation

**Canonical procedural representation:** the process tree in Section 3 is the canonical backbone. It defines the stable control-flow constraints: start event, concurrent checks, classification, clarification loop, and the three terminal outcomes.

**Authoritative policy layers:**

- **Procedural backbone:** concurrency, XOR outcomes, clarification loop before classification.
- **DECLARE:** cross-cutting activity ordering: clarification response, sanctions escalation response, sanctions escalation precedence, noncoexistence of reject/activate and approval/EDD conflicts.
- **Log Skeleton:** cardinality constraints, especially R10.
- **Temporal profile:** statistical warnings for R12.
- **Resource/data layer:** authoritative for R2 conditional approvals, R5/R6 conflict, R9 segregation of duties, and R11 post-activation bank changes.

**Recommended conformance-check order:**

1. Project the log onto the backbone alphabet and check the procedural model.
2. Run DECLARE conformance for cross-cutting ordering rules.
3. Run Log Skeleton conformance for cardinality and universal precedence.
4. Run temporal-profile conformance with `zeta = 2.0`.
5. Run resource/data checks for R2, R5/R6, R9, and R11.

**How to surface contradictory findings:** report all layer results, but prioritize hard control-flow and resource violations over temporal warnings. If a case passes DECLARE but fails strict R5, show it as “control-flow valid, legal-policy violation.” If the operational exception is enabled and the authorization attribute exists, show it as “policy-dependent: emergency exception accepted” with the 24-hour evidence. If the attribute is missing, route to manual review rather than automatic pass. For T7, show a temporal warning without blocking the case. For T8, surface the earliest decisive violation first, then list later redundant violations so users see the single root cause: contradictory terminal outcomes.
