## 1. Normalization Assumptions

All intervals below are closed conservative bounds. I first construct the uncertainty interval in the source clock's displayed-time domain, then convert its endpoints to UTC, and only then apply the clock-offset correction. If the recorded clock is ahead of true time by `o`, true time is recorded time minus `o`; therefore an offset bound `[a,b]` produces `[recorded-b, recorded-a]` after timestamp-resolution uncertainty has been included.

The timestamp-resolution intervals are:

- HUB exact-to-second with measurement uncertainty: recorded time +/- 0.5 s.
- A floor-to-minute timestamp `hh:mm`: `[hh:mm:00.000, hh:mm:59.999]` in the source clock.
- SENSOR round-to-nearest-10-second: recorded time +/- 5 s.
- A nearest-minute timestamp: recorded time +/- 30 s.

The time-zone conversion uses the stated local zone and the stated CEST, EDT, or BST interpretation. The June timestamps are unambiguous. For LEGACY-BER on 2025-10-26, local 02:xx is represented initially by both folds: UTC is local time minus two hours in the first (CEST) fold or minus one hour in the second (CET) fold. I then impose the supplied ingestion ordering. The only surviving T-405 path is Alert in the first fold, followed by Investigation_Start and Containment_Complete in the second fold. The clock-offset uncertainty remains on every surviving interval; a fold flag would be preferable to inference from order.

For a pair of event intervals `[a,b]` and `[c,d]`, the unconstrained difference is `[c-b,d-a]`. Since the supplied temporal-profile pairs are eventually-following pairs, I retain only non-negative feasible durations; when the intervals overlap, zero is the closure of the feasible positive-duration set. For T-409 I also impose the ordinary lifecycle condition that Investigation_Start is not before Alert_Received. This yields a conservative duration interval, while the marginal Investigation_Start interval still shows that the weak clock bound permits an apparent pre-alert start.

For T-404, `Investigation_Start = Investigation_Complete - [18,25] minutes`, retaining both the HUB uncertainty and the signed duration uncertainty. For T-407, Alert_Sent is not silently treated as receipt. I derive a weak possible receipt window by adding the `[0,20]` minute delivery bound. In the primary conditional analysis I additionally impose the plausible causal constraint `Alert_Received <= Investigation_Start`; because that causal relation is not directly logged, T-407 findings involving receipt are low-confidence. If that assumption is rejected, those receipt-dependent findings become INDETERMINATE.

For T-406, the primary interpretation is that the user may have entered the timestamp up to five minutes after the actual event. Thus the entry-delay interval `[0,300]` seconds is subtracted from the already-normalized entry time, separately from the mobile clock-offset interval. Under the alternative record-only interpretation, the mobile timestamp is uncertainty about when the record was entered, not about occurrence; that alternative narrows the possible start-to-containment duration and changes T-406 S2 at zero SLA tolerance, as noted below.

For the base classifications, SLA tolerance is zero and temporal-profile zeta is 1. The SLA and statistical profile are independent tests: a statistical-profile deviation is not by itself an SLA breach.

    "MOBILE-LON": {"tz": "Europe/London", "kind": "nearest_minute", "offset": (-300, 300)},
}


def parse_naive(value: str) -> datetime:
    return datetime.fromisoformat(value).replace(tzinfo=None)


def clock_interval(value: str, kind: str) -> tuple[datetime, datetime]:
    t = parse_naive(value)
    if kind == "hub":
        return t - timedelta(milliseconds=500), t + timedelta(milliseconds=500)
    if kind == "floor_minute":
        return t.replace(second=0, microsecond=0), t.replace(second=59, microsecond=999000)
    if kind == "nearest_10":
        return t - timedelta(seconds=5), t + timedelta(seconds=5)
    if kind == "nearest_minute":
        return t - timedelta(seconds=30), t + timedelta(seconds=30)
    raise ValueError(kind)


def attach_utc(local_naive: datetime, zone: str, fold: int) -> datetime:
    return local_naive.replace(tzinfo=ZoneInfo(zone), fold=fold).astimezone(UTC)


def is_legacy_ambiguous(value: str, source: str) -> bool:
    t = parse_naive(value)
    return (source == "LEGACY-BER" and t.date().isoformat() == "2025-10-26"
            and t.hour == 2)


def normalize_event(value: str, source: str, entry_delay_as_occurrence=False):
    meta = SOURCE[source]
    local_lo, local_hi = clock_interval(value, meta["kind"])
    folds = (0, 1) if is_legacy_ambiguous(value, source) else (0,)
    result = []
    for fold in folds:
        # Resolution uncertainty is converted before clock correction.
        utc_lo = attach_utc(local_lo, meta["tz"], fold)
        utc_hi = attach_utc(local_hi, meta["tz"], fold)
        off_lo, off_hi = meta["offset"]
        true_lo = utc_lo - timedelta(seconds=off_hi)
        true_hi = utc_hi - timedelta(seconds=off_lo)
        if entry_delay_as_occurrence:
            # Actual occurrence is [0,300] seconds before the entry record.
            true_lo -= timedelta(seconds=300)
        result.append((true_lo, true_hi))
    return result

def intersect_nonnegative(lo, hi):
    return (max(lo, timedelta(0)), hi) if hi >= timedelta(0) else None


def duration_intervals(first, second, eventually_following=True):
    out = []
    for left, right in product(first, second):
        lo = right[0] - left[1]
        hi = right[1] - left[0]
        if eventually_following:
            clipped = intersect_nonnegative(lo, hi)
            if clipped is None:
                continue
            lo, hi = clipped
        out.append((lo.total_seconds(), hi.total_seconds()))
    return sorted(out)


def merge_numeric(intervals_in):
    merged = []
    for lo, hi in sorted(intervals_in):
        if merged and lo <= merged[-1][1]:
            merged[-1] = (merged[-1][0], max(merged[-1][1], hi))
        else:
            merged.append((lo, hi))
    return merged


def classify(durations, acceptance):
    if not durations:
        return "INDETERMINATE"
    accepted = False
    violated = False
    a, b = acceptance
    for lo, hi in durations:
        if lo <= b and hi >= a:
            accepted = True
        if lo < a or hi > b:
            violated = True
    if accepted and violated:
        return "POSSIBLE_VIOLATION"
    if accepted:
        return "CERTAIN_PASS"
    return "CERTAIN_VIOLATION"

## 7. Governance Recommendation

Use UTC as the canonical stored event time, but retain the raw source timestamp, source time zone, UTC offset used, DST fold, timestamp-resolution/rounding semantics, clock-offset estimate and its observation time, and the transformation version. Store an interval or uncertainty object rather than silently replacing uncertain data with a point. Keep both raw and normalized values for audit and reprocessing.

Synchronize every source with authenticated NTP or PTP where feasible, emit signed offset telemetry at event time, and preserve source health and synchronization status. Centralize receipt timestamps at the broker or HUB and attach a causal/event identifier linking Sent, Received, Start, Complete, and Close records. Do not infer receipt from Sent unless the policy explicitly allows it and the delivery evidence is retained.

Make lifecycle semantics explicit: distinguish occurrence, record, send, receipt, start, completion, and close; record whether each timestamp is a start or completion event; and require a source-specific resolution field. For local time, persist the numeric UTC offset and `fold`/ambiguity indicator. Reject or quarantine ambiguous local timestamps when no fold can be established, unless a documented ordering constraint is strong enough and the resulting uncertainty is retained.

For enforcement, publish the interval decision policy in advance. The conservative default should be:

- enforce a maximum only when the entire feasible duration satisfies it (`CERTAIN_PASS`),
- issue an exception or human review when the feasible set overlaps a boundary (`POSSIBLE_VIOLATION`), and
- treat `CERTAIN_VIOLATION` as actionable only when event identity and lifecycle semantics are sufficiently strong.

If the organization instead treats any possible exceedance as a breach, that is a deliberate risk policy rather than a fact recovered from the timestamps; it should be labeled as such and should not be confused with certain non-conformance. Statistical temporal-profile zeta and SLA tolerance should be versioned policy parameters, reported separately, and never used to conceal a hard-rule violation.
