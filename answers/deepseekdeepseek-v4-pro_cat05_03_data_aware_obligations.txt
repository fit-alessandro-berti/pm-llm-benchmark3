## 1. Temporal Data Semantics  
- **State reconstruction** within a case proceeds event by event in `time:timestamp` order, using `event_index` ascending to break ties on identical timestamps. Blanks in an attribute column mean “no update”; the value from the latest non-blank previous event for that case is carried forward. At exactly the timestamp of a new non-blank entry the new value is effective immediately for all later events (including those with the same timestamp but higher index).  
- **Material data change** denotes any update to `amount`, `risk_level`, `jurisdiction`, or `customer_type`. The latest such change before a given event is the last event (in the order above) where at least one of those four attributes received a non-blank value. For R4, a change that increases the amount by more than 20 % relative to the amount at the time of the latest `Standard_Review` or `Enhanced_Review` renders that review invalid **for amountdependent obligations**.  
- **Event time, effective time, record time, evidence time** are kept distinct. The state snapshot uses the event timestamp. When the log shows a late database insert (e.g., `Record_Exemption`) the *effective time* of the approval is judged using the evidence’s creation or signing timestamps, not a backdated displayed field.  
- **Final attributes** of the case (the last known value) are never copied backward; each obligation is evaluated with the state that existed at the release trigger.

The policy explicitly warns against equating settlement with release, so this is not adopted.  

**TX302 (JUSTIFIED_EXCEPTION)**  
- **Alternative interpretation:** If the judge required the exemption record to be physically in the system before release, the late database insert would make the exemption unavailable. Then TX302 would be NONCOMPLIANT. The given evidence of a qualified signature at 09:05 and a documented outage tilts the balance strongly toward a valid exemption; a different policy weighting could overturn that.  

**TX310 (NONCOMPLIANT)**  
- **Alternative interpretation:** An adjudicator could accept the oral approval testimony and the PDF display date, treating the late signing certificate as a procedural delay. If that evidence is deemed sufficient, the exemption would be considered valid, reclassifying the case as JUSTIFIED_EXCEPTION. The policy’s caution about backdated fields and the requester’s bias argues against this, but it is a plausible defence.  

**TX306 (NONCOMPLIANT – material change definition)**  
- **Alternative reading:** If “material data change” is interpreted as a *material* change in the amount (e.g., >20% increase) rather than any attribute update, then the 4.5% increase would not be material. Under that interpretation the `Enhanced_Review` at 12:15 would satisfy R1 because the last material change was the initial creation. The case would become COMPLIANT (R2 already satisfied). This illustrates how the granularity of “material” affects outcomes.  

**TX308 (NONCOMPLIANT – decrease)**  
- **Alternative reading:** If a downward amount adjustment is not considered a *material data change* that resets the requirement, then the `Enhanced_Review` at 14:20 would stay valid for R1 (R4 states a decrease does not invalidate). The policy requires the review after “the latest material data change”; an interpretation that a decrease is not “material” would make TX308 COMPLIANT. The literal text treats any data change as a material change, but a riskbased interpretation could diverge.

## 6. Why ControlFlowOnly Conformance Is Insufficient  

1. **Finalstate leakage** – A controlflow model that looks at the whole trace might see a final `Enhanced_Review` after `Release_Funds` (e.g., if it happened late) and incorrectly deem the case compliant, because it ignores temporal ordering.  
2. **Posthoc exemptions** – A process model checking for an exemption event would accept a `Record_Exemption` that occurs after release, but the exemption must be valid **before** the obligation trigger, which requires evidence timestamps, not just activity presence.  
3. **Material changes after review** – In TX309, the workflow contains `Enhanced_Review` before a >20% increase and then `Release_Funds`. A pure controlflow checker sees the review and release as occurring; it cannot know that the review is invalidated by the amount change.  
4. **Conditional activation** – R1 and R2 fire only when certain attribute thresholds are met at release time. A tracebased model treats all releases identically unless it also inspects the data state, which is not part of control flow.  
5. **Missing data** – TX305 has an amount that never appears, making the obligation trigger indeterminate. Controlflow conformance typically assumes all data is present or uses a default, which would silently misclassify the case.  
6. **Sametimestamp ordering** – TX311 changes jurisdiction at the same timestamp as the `Enhanced_Review`. Only the eventindex tiebreak, together with the forwardfill logic, reveals that the review was performed while jurisdiction was still US, but the release state is DE. A pure activity order model cannot resolve this nuance.  

## 7. Recommended Logging and Control Improvements  

- **Immutable release payload** – Log the exact transaction snapshot that the release command acted upon, including all compliancerelevant attributes (amount, risk, jurisdiction, customer type). This would eliminate speculation about the state at the moment of release.  
- **Separate effectivetime, recordtime, and approvaltime fields** – For exemptions, store the time the approval was granted (with a qualified cryptographic signature), the time it became effective, and the time the database record was created. This distinguishes backdated entries from genuine timely approvals.  
- **Ruleversion identifier** – Each obligation decision should reference the exact rule version that was applied, so that later changes do not make historical cases ambiguous.  
- **Exemption scope attributes** – Record the jurisdiction, customertype, and amountscope of an exemption as structured attributes rather than freetext, enabling precise automated matching.  
- **Change provenance** – For every update event, log both the new value and the previous value (or a reference to the event that last set the value). This makes materialchange detection and invalidation of prior reviews unambiguous.  
- **Stable event ordering** – Use an immutable sequence counter or a monotonically increasing logical clock as the primary ordering tiebreaker, instead of relying solely on system timestamps that may coincide.  
- **Mandatory state snapshot for reviews** – When a review is completed, record the attribute values that were reviewed, creating an audit trail that can be compared with the releasetime state.
