## 1. Consistency rules and evidence model

**Rule inventory and classification**

| # | Rule | Classification |
|---|---|---|
| R1 | Every event id and object id referenced in a relation must exist in the object/event tables | hard invariant |
| R2 | `Record Payment` relates to exactly one Payment | hard invariant (per domain rule 7) |
| R3 | `Create Order`  exactly one Order; `Add Item`  one Order + one Item | strong default |
| R4 | `Pack Item`  one Item + one Package, but an item-only row may be a scanner-outage artifact reconciled later | strong default with a named weak-heuristic escape hatch |
| R5 | `Dispatch Package`  one Package + one Delivery, but a bulk dispatch may cover several packages under one delivery | strong default with escape hatch |
| R6 | `Confirm Delivery` may reference one delivery, several deliveries, or only customer/order | weak heuristic (explicitly multi-valued) |
| R7 | `Issue Invoice`  one Invoice, one-or-more Orders; arithmetic equality of totals is evidence, not proof | weak heuristic |
| R8 | O2O qualifiers are directional and must not be auto-mirrored | hard invariant |
| R9 | Identifier-prefix similarity (e.g. "PK8-2" vs "PK8-1", "N-421?" vs carrier_ref N-421) | weak heuristic |
| R10 | Timestamp co-occurrence (e.g. ev09/ev10 both 10:00) | weak heuristic |
| R11 | Shared customer (C17 on both ORD-A and ORD-B) | weak heuristic, but stacks with R7/R9 |
| R12 | Explicit uncertainty markers in the data itself (`?`, `*`) | evidence against forcing a unique resolution |
| R13 | Existing O2O structure should not be contradicted by a new edge | strong default |

**How evidence is combined.** No single signal is treated as decisive. Identifier-prefix matches (R9) are only weakly informative because scanner/carrier codes can be station names rather than object references. Timestamp equality (R10) can support *either* a merge (bulk dispatch) *or* a split (two independent legs), so it is used to generate competing hypotheses rather than to settle one. Shared customer (R11) raises the *prior* that two orders were fulfilled together, which is why it is invoked for both the PK-8 cross-order packing and the INV-44/ORD-B invoice question. Arithmetic totals (R7) are explicitly demoted below identifier and lifecycle evidence per the task constraints. Cardinality rules (R1–R5) act as the backbone: any proposed edge that would make a "normally-one" relation many-to-many is flagged for higher scrutiny, but not rejected outright, since the rules are defeasible. Explicit uncertainty markers (R12, the `?` in ev10 and the `*` in ev11) are treated as the log *telling us* that even the original recorder was unsure — this is used as a reason to keep confidence capped and to prefer "provisional"/"unresolved" over "accept."

## 3. Alternative repair bundles

**Bundle A — conservative / minimum change.**
Only P1/P2 are accepted (the scanner-outage reconciliation for ev08 is the one case the domain semantics *name explicitly* as normal, and the identifier match is direct). Everything else is left unresolved: ev10 keeps only PK-8 (no delivery attached, treating the "?" as a sign that the delivery leg was never actually captured); ev11 stays attached only to ORD-A with no Delivery object (portal lost the carrier id — rule 5's third case, which needs no additional assumption); INV-44 keeps its single link to ORD-A (ORD-B's invoice/payment path is simply unknown); PAY-2 remains unlinked to any invoice (unapplied cash). Lifecycle coherence: ORD-A has a full CreateAdd ItemPackDispatchConfirmInvoicePayment(partial) chain; ORD-B has only CreateAdd ItemPack(partial), and remains an intentionally incomplete but *plausible* lifecycle (an order that was placed, packed, and whose invoicing/payment we simply cannot see). PAY-2 is a free-floating Payment object, which the domain rules explicitly permit.

**Bundle B — consolidated-customer alternative.**
Accepts P1/P2, P3/P4, P7/P7b, P8/P8b. Story: C17 placed two orders that were consolidated into one package (PK-8), dispatched together via DEL-Y, invoiced together on INV-44 (230 = 130+100), and paid in two installments (PAY-1 for ORD-B's share, PAY-2 for ORD-A's share, summing to 230). ev11 is treated cautiously: because ORD-A's two items now travel via two different deliveries (DEL-X for IT-A1/PK-7, DEL-Y for IT-A2+IT-B1/PK-8), a merged confirmation event covering both legs (P6) is *coherent*, but it stacks two already-provisional hypotheses (P3/P4 and the multi-ack reading of rule 5), so it stays at "unresolved" confidence rather than "accept." This bundle produces a fully coherent, if speculative, two-order joint fulfillment lifecycle, but it is a genuine reinterpretation, not a forced completion.

**Bundle C — bulk-dispatch alternative (contrasts with B on logistics only).**
Accepts P1/P2 (ev08PK-8) but replaces P3/P4 with P5: both PK-7 and PK-8 are dispatched together under DEL-X (same 10:00 timestamp, rule 4's bulk-dispatch clause), and DEL-Y is left as a fully orphaned object — plausible if DEL-Y is a delivery record created for a route that was ultimately not used, or a duplicate registration. Under this bundle, ev11's ambiguity dissolves *within the bundle's own assumptions*: since DEL-Y is never used, ev11 can be tied to DEL-X without violating the "don't force uniqueness" constraint, because the alternative (DEL-Y) is independently ruled out by this bundle's own dispatch reading, not by wishful thinking. Bundle C's financial side (INV-44/ORD-B, PAY-2) is left exactly as in Bundle A, to isolate the logistics variable — the bundles are not mutually exclusive across the invoice/delivery axes and could in principle be recombined.

## 5. Lifecycle and cardinality audit

**Order.** ORD-A gets a fairly complete lifecycle (CreateAdd Item×2Pack×2Dispatch×2ConfirmInvoicePayment). ORD-B's lifecycle depends entirely on the accepted bundle: in Bundle A it terminates after Add Item/Pack, which is a legitimate partial lifecycle, not an error. In Bundle B it gains Invoice and (indirectly, via PAY) Payment links, but note that this support is *only* arithmetic and customer-identity — there is no independent E2O trail (no Dispatch/Confirm event ever names ORD-B), so the P7 edge is not corroborated by two independent evidence channels, only one (financial arithmetic) reinforced by a weak heuristic (shared customer). This should be flagged, not treated as settled.

**Item.** IT-A1, IT-A2 have complete AddPack chains. IT-B1's pack target is the central open question; under any bundle it is not orphaned at the *event* level (ev08 exists) but is orphaned at the *O2O* level unless P2 is accepted.

**Package.** PK-7 has a full O2O chain (packs IT-A1, carried by DEL-X). PK-8 is O2O-complete for IT-A2 but its item-set becomes many-to-many across two Orders if P2 is accepted — a legitimate but unusual cardinality that should be surfaced in any report, not silently normalized.

**Delivery.** DEL-X is anchored by ev09 and O2O `carries PK-7`. DEL-Y has *no* accepted E2O or O2O link unless P3/P4 (Bundle B) or nothing (Bundle A/C, where it is a genuine orphan object). An orphan Delivery object is legitimate — not every registered delivery needs to appear fully in this excerpt of the log.

**Invoice.** INV-44 is anchored to ORD-A independently by both E2O (ev12) and O2O (`bills`), which is a case of *real* dual-channel support. The proposed ORD-B link is not: the O2O edge (P7) and the E2O edge (P7b) are not independent evidence — both are motivated by the same arithmetic coincidence. **This is exactly the circularity to avoid**: one should not first assume the E2O edge, derive the O2O edge from it, and then cite the O2O edge as confirming the E2O edge. Here both P7 and P7b should be understood as a single hypothesis with one evidentiary basis, not two corroborating signals.

**Payment.** PAY-1 is doubly anchored (E2O ev13 + O2O `settles`). PAY-2 has only weak, single-source arithmetic support for any invoice link (P8/P8b) — again a single hypothesis expressed as two relation rows, not independent confirmation.

**Orphans summary.** Bundle A: DEL-Y (fully), ORD-B's invoice/payment tail. Bundle B: no orphans, but at the cost of two low-independent-evidence merges. Bundle C: DEL-Y (fully, by design), same financial orphans as A.

## 6. Downstream process-mining effects

**Unrepaired log.** The OC-DFG shows a dead-end at "Pack Item" for IT-B1 (no Package edge), a dead-end "Dispatch Package" node for PK-8 (no Delivery edge), and ORD-B terminating at "Add Item." The OTG under-counts Order–Invoice and Order–Payment co-occurrence for ORD-B. The ET–OT graph would show `Dispatch Package` connected to Package but with a lower-than-expected Delivery-degree, and `Confirm Delivery` connected only to Order, never Delivery — likely to be (mis)read as "Confirm Delivery never touches Delivery objects," which is an artifact of missing data, not process reality.

**Bundle A effects.** Minimal change: adds one PackPackage edge for IT-B1/PK-8 in the OC-DFG. Order-flattened log for ORD-B remains a two-step trace (Create, Add Item) — short but not obviously broken. Delivery-flattened log gains no new trace for DEL-Y (it simply doesn't appear), which is honest but means DEL-Y's activity frequency is zero, potentially making it look like a "dead" object in reporting.

**Bundle B effects.** The OC-DFG gains a `Dispatch Package  Confirm Delivery` edge through DEL-Y and a `Pack Item(IT-B1)  Dispatch Package(PK-8)` edge; more importantly, it creates an `Issue Invoice  Order` fan-out edge (INV-44 to two Orders), which will visibly change the Invoice-flattened OC-DFG: Invoice-flattened traces will show INV-44 associated with two "Create Order" origins, a 1:N pattern that did not exist before. Equivalent-execution clustering around Order will likely place ORD-A and ORD-B into the *same* case-cluster (via shared Package/Invoice), whereas in Bundle A they remain distinct clusters. Activity frequency computed **per event** is unaffected (14 events regardless of bundle), but frequency computed **per unique object** changes: "Dispatch Package" now touches 2 Deliveries instead of 1 in Bundle B, inflating its object-degree statistic; "Issue Invoice" touches 2 Orders instead of 1. Frequency computed **per total object instance** (counting duplicated O2O fan-out) will overstate INV-44's apparent workload relative to Bundle A.

**Bundle C effects.** Delivery-flattened traces collapse to a single DEL-X trace containing both packages, which will *increase* the apparent frequency of multi-package dispatch patterns in the Delivery-flattened DFG and make DEL-Y disappear from all discovered models entirely (zero-frequency object), a different downstream picture from Bundle B where DEL-Y is a first-class but low-frequency node.

In all repaired bundles, the Order-flattened OC-DFG for ORD-A is stable; the volatility is concentrated in Package/Delivery/Invoice-flattened views and in any object-degree-based frequency metric — exactly where the ambiguous relations live.

## 7. PM4Py-oriented validation outline

```python
import pandas as pd
import pm4py

# --- 1. Copy originals before mutating ---
events_r = events.copy()
objects_r = objects.copy()
relations_r = relations.copy()
o2o_r = o2o.copy()

# --- 2. Append selected (Bundle B) E2O additions ---
e2o_additions = pd.DataFrame([
    {"ocel:eid": "ev08", "ocel:oid": "PK-8", "ocel:qualifier": "packed-into"},
    {"ocel:eid": "ev10", "ocel:oid": "DEL-Y", "ocel:qualifier": "dispatched-via"},
    {"ocel:eid": "ev12", "ocel:oid": "ORD-B", "ocel:qualifier": "for"},
    {"ocel:eid": "ev14", "ocel:oid": "INV-44", "ocel:qualifier": "settles"},
])
relations_r = pd.concat([relations_r, e2o_additions], ignore_index=True)

# --- 3. Append selected O2O additions ---
o2o_additions = pd.DataFrame([
    {"ocel:oid": "PK-8", "ocel:oid_2": "IT-B1", "ocel:qualifier": "packs"},
    {"ocel:oid": "DEL-Y", "ocel:oid_2": "PK-8", "ocel:qualifier": "carries"},
    {"ocel:oid": "INV-44", "ocel:oid_2": "ORD-B", "ocel:qualifier": "bills"},
    {"ocel:oid": "PAY-2", "ocel:oid_2": "INV-44", "ocel:qualifier": "settles"},
])
o2o_r = pd.concat([o2o_r, o2o_additions], ignore_index=True)

# --- 4. Referential-integrity and duplicate checks ---
known_events = set(events_r["ocel:eid"])
known_objects = set(objects_r["ocel:oid"])

bad_e2o = relations_r[~relations_r["ocel:eid"].isin(known_events) |
                       ~relations_r["ocel:oid"].isin(known_objects)]
assert bad_e2o.empty, f"Dangling E2O rows:\n{bad_e2o}"

bad_o2o = o2o_r[~o2o_r["ocel:oid"].isin(known_objects) |
                ~o2o_r["ocel:oid_2"].isin(known_objects)]
assert bad_o2o.empty, f"Dangling O2O rows:\n{bad_o2o}"

dup_e2o = relations_r.duplicated(subset=["ocel:eid", "ocel:oid", "ocel:qualifier"])
dup_o2o = o2o_r.duplicated(subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])
assert not dup_e2o.any() and not dup_o2o.any(), "Duplicate relation rows detected"

# --- 5. Build/update the OCEL object (constructor is version-dependent) ---
# NOTE: pm4py's OCEL constructor signature changed across versions;
# verify against the installed pm4py release before relying on this line.
ocel = pm4py.objects.ocel.obj.OCEL(
    events=events_r, objects=objects_r, relations=relations_r, o2o=o2o_r
)

# --- 6. Discover multi-object models ---
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)          # object-type graph
etot = pm4py.discover_etot(ocel)        # event-type/object-type graph

# --- 7. Flatten on Order and Delivery to inspect single-object views ---
order_log = pm4py.ocel_flattening(ocel, "Order")
delivery_log = pm4py.ocel_flattening(ocel, "Delivery")

# NOTE: pm4py.ocel_o2o_enrichment (if used) only *propagates* existing O2O
# structure algorithmically; it must NOT be treated as evidence that the
# business semantics (e.g. INV-44 bills ORD-B) are correct. It is omitted
# here deliberately.

print(order_log["concept:name"].value_counts())
print(delivery_log["concept:name"].value_counts())
```

## 8. Over-repair warnings

1. **Forcing ev11 to a single Delivery** (rejected as P9) would silently erase the possibility of a split shipment, making the OTG show a clean one-order-one-delivery pattern that never existed and biasing any carrier-performance analysis toward one route.
2. **Accepting INV-44 bills ORD-B purely from arithmetic** could retroactively "explain away" a genuinely separate, unrecorded invoice for ORD-B, making a two-invoice reality look like a one-invoice reality and understating invoicing volume per customer.
3. **Auto-mirroring O2O qualifiers** (e.g., inferring `PK-8 packs DEL-Y` from `DEL-Y carries PK-8`, or `IT-B1 contains PK-8`) would violate directionality (rule 8) and introduce nonsensical reverse edges into the OTG.
4. **Treating PK-8 as an ORD-B-only package** (over-correcting by detaching it from IT-A2) to "simplify" the cross-order mixing would destroy real evidence (ev07) and fabricate a cleaner but false single-order packing lifecycle.
5. **Using `pm4py.ocel_o2o_enrichment`-style derived edges as independent confirmation** of an already-assumed E2O link (the exact circularity flagged in Section 5 for INV-44/ORD-B and PAY-2/INV-44) would make weak, single-source hypotheses appear doubly corroborated, artificially raising confidence scores in any downstream audit.
6. **Completing every object's lifecycle "for tidiness"** (e.g., inventing a Confirm Delivery link for ORD-B, or assuming DEL-Y must carry something) would manufacture edges the log gives no basis for, inflating equivalent-execution clusters around Order and making unrelated orders appear co-executed.
7. **Resolving the bulk-dispatch vs. two-delivery question by timestamp alone** would let a coincidental shared minute (10:00) override the explicit carrier-reference mismatch, producing a Delivery-flattened model with a false multi-package trace or a false extra delivery leg depending on which way the forcing goes.
