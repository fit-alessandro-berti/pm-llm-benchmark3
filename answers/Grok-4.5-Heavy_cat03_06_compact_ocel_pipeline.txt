## 1. Modeling assumptions

- **Object types** (Title Case, singular): `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.  
  Objects: Orders = {O100, O200}, Items = {I1, I2, I3}, Packages = {P1, P2}, Deliveries = {D1, D2}, Invoice = {V1}, Payments = {M1, M2}.

- **E2O qualifier vocabulary** (short, consistent role/activity stems):  
  `creates`, `adds`, `reserves`, `packs`, `dispatches`, `confirms`, `issues`, `records`, `settles`, `closes`.  
  On multi-object events the same qualifier is reused for every related object unless a clearer role word is natural (`settles` for the Invoice on a payment event).

- **O2O direction conventions**: directed from the “owning / container / actor” object to the “contained / acted-upon” object, qualifier reading naturally left-to-right:  
  Order `contains` Item, Package `packs` Item, Delivery `carries` Package, Invoice `bills` Order, Payment `partially_settles` Invoice (both M1 and M2; the narrative never states a total that would justify a `completes_settlement` distinction).

- **Logistics / financial events vs. Orders & Items**:  
  We adopt an *operational-involvement* policy.  
  - Reserve Stock, Pack Package and Dispatch Package are linked directly to the Orders that own the packed items (the narrative explicitly calls out shared packages and joint reservation).  
  - Confirm Delivery is kept lighter (Delivery + Package only).  
  - Issue Invoice links the Invoice and both Orders; Record Payment links only Payment + Invoice (amount stays an event attribute).  
  This still reflects what a source system would typically record on packing/shipping documents, not pure analytical reachability.

- **Preventing confusion of analytical propagation with source facts**:  
  The `relations` table contains *only* the direct E2O links justified by the narrative. Structural composition lives exclusively in `o2o`. Any further transitive closure (e.g. “Order is related to Delivery via Package”) is left to discovery algorithms and is never materialised as an extra row in `relations`. This separation is stated in comments and in the audit tables.

- **PM4Py version assumption**:  
  Recent PM4Py accepts `OCEL(events=…, objects=…, relations=…, o2o=…)`. Older constructors omit the `o2o` keyword; the single constructor line is therefore isolated in a try/except that falls back to assignment of the attribute. Data semantics are never altered.

## 3. Data-model audit

**Objects by type**

| Object type | Objects          |
|-------------|------------------|
| Order       | O100, O200       |
| Item        | I1, I2, I3       |
| Package     | P1, P2           |
| Delivery    | D1, D2           |
| Invoice     | V1               |
| Payment     | M1, M2           |

**O2O qualifiers and cardinalities**

| Qualifier            | Cardinality | Examples                     |
|----------------------|-------------|------------------------------|
| contains             | 3           | O100→I1, O100→I2, O200→I3   |
| packs                | 3           | P1→I1, P1→I3, P2→I2         |
| carries              | 2           | D1→P1, D2→P2                |
| bills                | 2           | V1→O100, V1→O200            |
| partially_settles    | 2           | M1→V1, M2→V1                |

**Activities and the object types they touch**

| Activity            | Object types touched                          |
|---------------------|------------------------------------------------|
| Create Order        | Order                                          |
| Add Item            | Item, Order                                    |
| Reserve Stock       | Item, Order                                    |
| Pack Package        | Package, Item, Order                           |
| Dispatch Package    | Delivery, Package, Order                       |
| Issue Invoice       | Invoice, Order                                 |
| Record Payment      | Payment, Invoice                               |
| Confirm Delivery    | Delivery, Package                              |
| Close Order         | Order                                          |

**Consequential events for convergence / divergence**  
- **e06 (Reserve Stock)** and **e07 (Pack Package P1)** are the primary convergence points: both Orders and the two Items from different Orders share the same event.  
- **e09 (Dispatch P1)** propagates that convergence into the logistics layer.  
- **e11 (Issue Invoice)** is the financial convergence point for both Orders.  
- Divergence appears later: O200 closes before O100, and the two Confirm Delivery events are independent.

## 4. Expected flattened behavior

**Order**  
- Trace shape (approx.): Create Order → Add Item(s) → Reserve Stock → Pack Package → Dispatch Package → Issue Invoice → Close Order.  
- Shared events (e06, e07, e09, e11) are *copied* into both O100 and O200 traces → classic “convergence” artefact.  
- Omitted: pure Delivery confirmations (they do not touch Orders under the chosen policy).  
- Likely DFG edges: Create→Add, Add→Reserve, Reserve→Pack, Pack→Dispatch, Dispatch→Issue, Issue→Close; also the cross-order shared edges appear with multiplicity 2.  
- Misleading interpretation: an analyst might conclude that every Order always packs *two* items or always shares a package; the shared events inflate frequencies.

**Package**  
- P1: Pack → Dispatch → Confirm (plus the Items/Orders that were related at pack time).  
- P2: analogous shorter path.  
- Shared events appear only once per package.  
- DFG is almost linear; little branching.  
- Misleading: the cross-order nature of P1 is invisible once the view is restricted to Package.

**Delivery**  
- Very short traces: Dispatch → Confirm.  
- Almost no branching; DFG is a single edge.  
- Omits everything upstream (Orders, packing decisions).  
- Useful only for pure logistics KPI, not for end-to-end process understanding.

**Invoice**  
- Trace: Issue Invoice → Record Payment (M1) → Record Payment (M2).  
- Both payments appear; the two Orders that are billed are visible only through the original relations, not as cases.  
- DFG shows sequential partial settlements.  
- Misleading: one cannot see *which* Orders are being settled from the flattened Invoice log alone.

**Why Payment flattening is particularly weak**  
Each Payment object participates in only a single “Record Payment” event. The resulting traces are length-1 (or length-2 if the Invoice is also pulled in). Classic discovery algorithms therefore produce empty or trivial DFGs/skeletons; the interesting multi-object settlement semantics live in the O2O and E2O links, which disappear under pure Payment flattening.

## 5. Expected object-centric structures

- **OC-DFG**:  
  Activities are nodes; edges are labelled by object type. Expect strong Order-labelled paths that fork at Reserve/Pack and re-converge at Issue Invoice. Package- and Delivery-labelled edges form two parallel logistics corridors (P1/D1 vs P2/D2). The shared events e06/e07 produce high-frequency multi-type edges involving both O100 and O200.

- **OTG (Object-Type Graph)**:  
  Nodes = object types; edges reflect co-occurrence in events or O2O. Dense clique among Order–Item–Package; Invoice bridges Orders; Payment hangs off Invoice. Delivery is attached via Package.

- **ET–OT graph**:  
  Bipartite activity ↔ object-type incidence. “Pack Package” and “Reserve Stock” have high degree (Order + Item + Package). “Record Payment” only touches Payment + Invoice. Visual inspection immediately shows which activities are multi-type.

- **Object-centric Petri net**:  
  One place/transition subnet per object type, synchronised on shared transitions. Expect a shared transition for Reserve Stock and for Pack P1 that is labelled with both Order and Item/Package colours. The two Close Order transitions remain separate. ## 6. Modeling alternatives

1. **Source-minimal relations**  
   Only the objects that a source system would have written on the atomic event record (e.g. Pack touches only Package + Items; Dispatch touches only Delivery + Package).  
   *Effect*: Order flattening loses logistics; OC-DFG Order edges stop at Pack/Invoice; convergence on P1 becomes visible only after O2O traversal. Discovery results are “cleaner” but incomplete for end-to-end analysis.

2. **Full operational involvement (the policy chosen)**  
   Every downstream event that operationally involves an Order’s items also carries the Order identifier.  
   *Effect*: Flattened Order traces become complete; shared events appear in multiple cases (classic convergence artefact); OC-DFG and OCPN show rich multi-type synchronisation. Relation table is larger but still narrative-faithful.

3. **O2O-propagated analytical relations**  
   Materialise extra E2O rows by walking the O2O graph (e.g. every event that touches a Package also receives the Orders that contain the Items of that Package).  
   *Effect*: Maximum analytic convenience; every Order sees every logistics event. However the `relations` table no longer distinguishes source-system facts from derived reachability; conformance checking and “what was actually recorded” questions become ambiguous. Discovery frequencies are further inflated.

All three policies leave the underlying business story unchanged; they only change which facts are materialised versus left to algorithmic navigation.

## 7. Failure modes

1. **Relation inflation** – linking every possible object produces dense E2O tables; discovery algorithms slow down and frequency metrics become hard to interpret.  
2. **Missing direct E2O links** – if Pack/Dispatch never touch Orders, flattened Order views are truncated and the convergence story disappears.  
3. **Treating O2O propagation as observation** – materialising derived links inside `relations` mixes source facts with analysis, breaking auditability.  
4. **Duplicate shared events after flattening** – the same Reserve/Pack event appears in both O100 and O200 traces; classic DFG frequencies are doubled.  
5. **Ambiguous payment allocation** – both payments settle the same Invoice; without explicit allocation attributes one cannot reconstruct which fraction belongs to which Order.  
6. **Overly short Payment traces** – length-1 (or length-2) cases make classic discovery produce empty models.  
7. **Constructor / API version mismatch** – older PM4Py rejects the `o2o=` keyword; the isolated try/except prevents a hard crash but the analyst must remember to inspect `ocel.o2o`.  
8. **False total order for same-time events** – although this log has distinct timestamps, any future data with ties would be ordered arbitrarily by the DataFrame index, producing non-deterministic DFG edges.
