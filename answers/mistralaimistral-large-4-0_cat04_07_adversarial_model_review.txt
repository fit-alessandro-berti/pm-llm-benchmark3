# 1. Review Scope and Assumptions

I distinguish four intended use cases, because the acceptable fitness/precision trade-off changes sharply across them:

- **Exploration / discovery.** The model is used to understand what happens in the log, to generate hypotheses, and to tolerate noise. High fitness and high generalization are useful; low precision is acceptable if the model is explicitly labelled as non-enforcing.
- **Conformance enforcement.** The model is used to accept or reject cases, or to flag violations. Here the decisive properties are: no mandatory activity may be skipped, forbidden traces must be rejected, optional/required behaviour must be conditioned correctly, and precision must be measured against a curated negative suite, not only against observed positive traces.
- **Simulation / what-if analysis.** The model must be sound, executable, and semantically faithful to ordering, choice, and repetition constraints. A permissive model that can skip mandatory checks is not a safe simulation model.
- **Stakeholder communication.** The model must be understandable to compliance, operations, IT, auditors, and process owners. Simplicity and explainability are primary; a model that only auditors can read is not a communication model.

I assume throughout that:

- “Accepts” means **language membership**: there exists a firing sequence whose visible projection equals the trace. Silent transitions are allowed. This is stricter than “has high alignment fitness” and avoids treating a heavily penalised alignment as acceptance.
- The reported metrics are **evidence, not ground truth**. Neither team supplied seeds, preprocessing code, alignment-cost settings, or the exact held-out cases.
- The `external/internal` attribute and the `affected-check` attribute are missing from the discovery log. Any model that silently treats Supplier Review as universally optional, or silently allows all rechecks after correction, is over-approximating.
- Model S and Model C are not automatically wrong because their metrics differ; the metrics may be measuring different pathologies.

# 3. Adversarial Review of Model S

## Strongest case for Model S

Model S is simple, fast, and easy for business users to read. It achieves high training and holdout fitness, high token-based generalization, and high simplicity. It is robust to missing events and can be used as an exploratory “flower model” that shows the main activities without forcing a rigid sequence. For initial process discovery, it is a reasonable baseline.

## Strongest case against Model S

Model S is not a compliance model. It violates P2, P4, P6, and P7. It makes Credit Check and Technical Review optional, allows Expedite Review before those checks, cannot represent Correct Dossier, and cannot condition Supplier Review on the external/internal attribute. Its high fitness and generalization are largely artifacts of permissiveness.

## Concrete behaviours Model S admits that are undesirable or policy-ambiguous

Acceptance here means language membership with silent transitions allowed.

1. **Missing both mandatory checks**  
   `Register Dossier, Manager Approval, Release Order`  
   This is B3 and is forbidden. Model S accepts it by firing the silent `tau` branches for Credit Check, Technical Review, Supplier Review, and Expedite Review.

2. **Expedite Review before mandatory checks**  
   `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   This is B4 and is forbidden. Model S accepts it because the parallel block allows any interleaving of the four review activities.

3. **Missing one mandatory check**  
   `Register Dossier, Credit Check, Manager Approval, Release Order`  
   Forbidden because Technical Review is mandatory. Model S accepts it by skipping Technical Review.

4. **External case without Supplier Review**  
   `Register Dossier, Credit Check, Technical Review, Manager Approval, Release Order`  
   If the case is externally sourced, P3 requires Supplier Review. Model S accepts this trace regardless of the external/internal attribute because it cannot see that attribute.

5. **Supplier Review before mandatory checks**  
   `Register Dossier, Supplier Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   This is policy-ambiguous. P3 does not explicitly state where Supplier Review must occur, but placing it before the mandatory checks is at least suspicious. Model S admits it.

6. **No correction semantics**  
   `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order`  
   This is B6 and is policy-dependent valid. Model S rejects it because Correct Dossier is not in the model. This is not a safety failure, but it shows Model S cannot represent P6.

## Intentional noise tolerance vs accidental semantic flaws

Intentional noise tolerance would mean: “occasionally a mandatory event is missing from the log, and we want the model to tolerate that with a penalty.” That is not what Model S does. Model S structurally makes Credit Check and Technical Review optional by placing them in exclusive choice with `tau` inside a parallel block. That is an accidental semantic flaw: the model’s language includes traces that policy forbids. The same applies to Expedite Review before the mandatory checks.

# 4. Adversarial Review of Model C

## Strongest case for Model C

Model C is precise on the training log, enforces Credit Check and Technical Review before approval, enforces exactly one approval, and rejects the clearly forbidden probes B3, B4, and B8. For a stable process with a known set of variants, it can serve as an audit-ready catalog of frequent traces.

## Strongest case against Model C

Model C is brittle, complex, slow, and difficult for stakeholders to understand. Its holdout fitness collapses from 0.973 to 0.744, and its token-based generalization is only 0.412. It rejects legitimate combinations such as B5 and B6. Its correction handling is rigid and opaque. Its 33 duplicate labels make impact analysis difficult. Its high training precision may be an artifact of memorizing training variants and measuring precision only against positive traces.

## Branch enumeration

Model C is an XOR of eight enumerated sequences. This is a variant catalog, not a generalizable process model. Adding a new legitimate combination requires adding another branch. The number of branches grows combinatorially with:

- order of Credit Check and Technical Review,
- presence/absence of Supplier Review,
- presence/absence of Expedite Review,
- order of Supplier Review and Expedite Review,
- approval type,
- correction and recheck patterns.

This is unmaintainable.

## Duplicate labels

The reported 33 duplicate labels are a serious pathology. Duplicate labels mean multiple transitions share the same visible label. This creates ambiguity in alignments, makes it harder to reason about which branch fired, and complicates impact analysis. It may also inflate precision by allowing the same observed activity to be matched by different model transitions in different contexts.

## Unseen combinations

Model C rejects several plausible valid traces:

- B5: `Register Dossier, Technical Review, Credit Check, Supplier Review, Expedite Review, Auto Approval, Release Order`
- B6: `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order`
- `Register Dossier, Credit Check, Technical Review, Expedite Review, Auto Approval, Release Order`
- `Register Dossier, Credit Check, Technical Review, Correct Dossier, Credit Check, Manager Approval, Release Order`
- `Register Dossier, Technical Review, Credit Check, Supplier Review, Auto Approval, Release Order`

These are not obviously forbidden. F4 explicitly says holdout cases combine Supplier Review, Auto Approval, and alternate check order in ways absent from training.

## Correction handling

Model C has only one correction branch:

`Register Dossier, Credit Check, Technical Review, Correct Dossier, Credit Check, Technical Review, Manager Approval, Release Order`

This forces:

- Credit Check before Technical Review,
- both checks to repeat after correction,
- Manager Approval rather than Auto Approval,
- exactly one correction.

F6 says a correction may require repeating only Credit Check, only Technical Review, or both. Model C cannot represent that decision transparently.

## Holdout degradation

The drop from 0.973 training fitness to 0.744 holdout fitness is a strong signal of overfitting to training variants. A model that fits training well but fails on holdout is not a safe enforcement model.

## Maintainability

Model C’s low simplicity score, high duplicate-label count, and slow runtime are all symptoms of the same problem: branch enumeration. It is difficult to update, difficult to review, and difficult to explain.

## High precision as a possible artifact

Model C’s 0.941 training precision was computed only against observed positive traces. A model that rejects all unseen behaviour can achieve high precision on the training log while being useless for generalization. F5 confirms that no curated negative behaviour suite was used. Therefore the high precision does not establish that Model C is safe.

# 6. Likely Metric Pathologies

Ranked by likely decision impact:

1. **Positive-log-only precision.**  
   Precision was computed only against observed positive traces. No curated negative suite was used. A model can achieve high precision by rejecting all unseen behaviour. This is the single most dangerous pathology for a compliance decision.

2. **Missing-event bias and optionalizing mandatory behaviour.**  
   If the log is missing events, a model may learn that mandatory checks are optional. Model S’s high fitness may be partly due to skipping missing mandatory checks. F4 notes that some Supplier Review events may be missing, which can bias any model toward treating Supplier Review as optional.

3. **Train/holdout leakage or split sensitivity.**  
   No seeds, preprocessing code, or held-out cases were supplied. Model C’s holdout drop may be due to an unlucky split or to overfitting. Model S’s high holdout fitness may be due to permissiveness rather than generalization.

4. **Alignment-cost sensitivity.**  
   No alignment-cost settings were supplied. Default costs may treat silent transitions as free or penalized. This affects fitness, precision, and the interpretation of “acceptance.” A model that looks fitting under one cost function may be non-fitting under another.

5. **Silent-transition effects.**  
   Model S uses `tau` to skip activities. Silent transitions can inflate fitness by allowing missing mandatory checks without log moves. This is a structural permissiveness, not a measured noise tolerance.

6. **Duplicated-label effects.**  
   Model C has 33 duplicate labels. Duplicate labels create ambiguity, non-free-choice behaviour, and difficulty in impact analysis. They may also inflate precision by allowing the same observed activity to match different model transitions.

7. **Generalization rewarded by excessive permissiveness.**  
   Token-based generalization rewards models that accept more behaviour. Model S’s high generalization may be a symptom of permissiveness, not a sign of quality.

8. **Fitness rewarded by optionalizing mandatory behaviour.**  
   Model S’s high fitness is partly achieved by making mandatory checks optional. Fitness is not a safety metric.

9. **Stakeholder-score methodology.**  
   The 1–5 comprehension score is informal, with no protocol, sample size, or inter-rater reliability. It is not comparable across models.

10. **Runtime confounding by model size.**  
    Model C’s slower runtime may be due to model size, duplicate labels, and branch enumeration. Runtime is an operational constraint, not a quality metric.

# 7. Third Alternative

## Strategy

I propose a **block-structured procedural backbone with an explicit correction loop and post-hoc attribute checks**. The backbone enforces the mandatory checks, the optional reviews, the exactly-one approval, and the correction/recheck structure. Because the `external/internal` and `affected-check` attributes are missing, the model does not silently enforce them; it exposes them as explicit post-hoc policy checks.

## Formal description

```text
Register Dossier;
( (Credit Check; Technical Review)  (Technical Review; Credit Check) );
( Correct Dossier;
  ( Credit Check  Technical Review  (Credit Check; Technical Review)  (Technical Review; Credit Check) )
)*;
( (Supplier Review  Expedite Review) with each branch optional );
( Manager Approval  Auto Approval );
Release Order
```

Where:

- `` is exclusive choice.
- `;` is sequence.
- `*` is zero-or-more repetition.
- `` is parallel composition with optional skip: each of Supplier Review and Expedite Review may occur at most once, in either order.
- `tau` is a silent skip.

## Declarative dictionaries and external checks

```python
MANDATORY_CHECKS = {"Credit Check", "Technical Review"}
OPTIONAL_REVIEWS = {"Supplier Review", "Expedite Review"}
APPROVALS = {"Manager Approval", "Auto Approval"}
CORRECTION_ACTIVITY = "Correct Dossier"

RECHECK_OPTIONS = [
    ("Credit Check",),
    ("Technical Review",),
    ("Credit Check", "Technical Review"),
    ("Technical Review", "Credit Check"),
]


def policy_violations(log, external_attr="case:external", affected_attr="case:affected_checks"):
    """
    Post-hoc policy checks that the backbone cannot enforce because the
    external/internal and affected-check attributes are missing.
    """
    df = pm4py.convert_to_dataframe(log)
    violations = []

    for case_id, group in df.groupby("case:concept:name"):
        acts = group["concept:name"].tolist()

        # P2: mandatory checks present
        for check in MANDATORY_CHECKS:
            if check not in acts:
                violations.append((case_id, f"missing mandatory check: {check}"))

        # P5: exactly one approval
        approvals = [a for a in acts if a in APPROVALS]
        if len(approvals) != 1:
            violations.append((case_id, f"approval count {len(approvals)} != 1"))

        # P4: Expedite Review after both mandatory checks
        if "Expedite Review" in acts:
            if all(c in acts for c in MANDATORY_CHECKS):
                last_mandatory = max(acts.index("Credit Check"), acts.index("Technical Review"))
                if acts.index("Expedite Review") < last_mandatory:
                    violations.append((case_id, "Expedite Review before mandatory checks"))
            else:
                violations.append((case_id, "Expedite Review present but mandatory checks missing"))

        # P7: repeated mandatory check without preceding Correct Dossier
        seen_since_correction = set()
        for act in acts:
            if act == CORRECTION_ACTIVITY:
                seen_since_correction = set()
            elif act in MANDATORY_CHECKS:
                if act in seen_since_correction:
                    violations.append((case_id, f"repeated {act} without preceding Correct Dossier"))
                seen_since_correction.add(act)

        # P3: external supplier requirement
        if external_attr in group.columns:
            is_external = group[external_attr].iloc[0]
            if is_external and "Supplier Review" not in acts:
                violations.append((case_id, "external case missing Supplier Review"))

        # P6: correction recheck
        for i, act in enumerate(acts):
            if act == CORRECTION_ACTIVITY:
                approval_idx = next(
                    (j for j in range(i + 1, len(acts)) if acts[j] in APPROVALS),
                    len(acts)
                )
                rechecks = [a for a in acts[i + 1:approval_idx] if a in MANDATORY_CHECKS]
                if not rechecks:
                    violations.append((case_id, "Correct Dossier without recheck"))

                if affected_attr in group.columns:
                    affected = group[affected_attr].iloc[0]
                    if set(rechecks) != set(affected):
                        violations.append(
                            (case_id, f"rechecks {rechecks} do not match affected checks {affected}")
                        )
                # If affected_attr is missing, the backbone allows any non-empty
                # subset of mandatory checks. This is an explicit uncertainty,
                # not a silent policy decision.

    return violations
```

## Explicit semantics

- **Mandatory checks.** Exactly one Credit Check and exactly one Technical Review must occur, in either order, before any optional review or approval.
- **Optional Supplier Review.** At most one Supplier Review may occur after the mandatory checks and before approval. Because the `external/internal` attribute is missing, the model does not enforce that Supplier Review is required for external cases. That is handled by `policy_violations`.
- **Expedite Review.** At most one Expedite Review may occur after both mandatory checks and before approval. It may occur before or after Supplier Review.
- **Exactly-one approval.** Exactly one of Manager Approval or Auto Approval must occur before Release Order.
- **Correction/recheck.** Zero or more correction loops are allowed. Each loop is a Correct Dossier followed by a non-empty subset of `{Credit Check, Technical Review}` in either order. A repeated mandatory check without a preceding Correct Dossier is rejected by the backbone.

## Limitations caused by missing attributes

- The model cannot enforce that Supplier Review is required only for externally sourced orders. It treats Supplier Review as optional in the backbone and relies on the post-hoc `external_attr` check. If the attribute is missing, P3 cannot be fully enforced.
- The model cannot enforce “only the checks affected by the correction should repeat.” It allows any non-empty subset of `{Credit Check, Technical Review}` after a Correct Dossier. If the `affected-check` attribute is missing, this is an explicit over-approximation.
- The model assumes correction occurs after the mandatory checks and before optional Supplier/Expedite reviews. If corrections can occur after optional reviews, the model must be revised.
- The model does not handle duplicate events as data-quality issues; it rejects repeated mandatory checks without a preceding Correct Dossier.

## Reproducible case splits and preprocessing

```python
import numpy as np
import pandas as pd
import pm4py
from sklearn.model_selection import train_test_split


def preprocess_log(log):
    df = pm4py.convert_to_dataframe(log)
    df["concept:name"] = df["concept:name"].str.strip()
    missingness = df.groupby("case:concept:name")["concept:name"].apply(lambda x: x.isna().sum())
    return pm4py.convert_to_event_log(df), missingness


def split_log(log, test_size=0.2, seed=20240115, stratify_attr="case:external"):
    df = pm4py.convert_to_dataframe(log)
    case_df = df.drop_duplicates("case:concept:name")
    stratify = case_df[stratify_attr] if stratify_attr in case_df.columns else None

    train_cases, holdout_cases = train_test_split(
        case_df["case:concept:name"],
        test_size=test_size,
        random_state=seed,
        stratify=stratify
    )

    train_log = pm4py.convert_to_event_log(df[df["case:concept:name"].isin(train_cases)])
    holdout_log = pm4py.convert_to_event_log(df[df["case:concept:name"].isin(holdout_cases)])
    return train_log, holdout_log
```

## Missing-event and duplicate-event perturbation tests

```python
def perturb_missing(log, seed, drop_prob=0.05):
    rng = np.random.default_rng(seed)
    df = pm4py.convert_to_dataframe(log)
    rows = []
    for case_id, group in df.groupby("case:concept:name"):
        for _, row in group.iterrows():
            if rng.random() > drop_prob:
                rows.append(row)
    return pm4py.convert_to_event_log(pd.DataFrame(rows))


def perturb_duplicate(log, seed, dup_prob=0.05):
    rng = np.random.default_rng(seed)
    df = pm4py.convert_to_dataframe(log)
    rows = []
    for case_id, group in df.groupby("case:concept:name"):
        for _, row in group.iterrows():
            rows.append(row)
            if rng.random() < dup_prob:
                rows.append(row.copy())
    return pm4py.convert_to_event_log(pd.DataFrame(rows))
```

## Evaluation skeleton

```python
def evaluate_model(model, train_log, holdout_log, negative_log, positive_log):
    net, im, fm = pm4py.convert_to_petri_net(model)

    results = {}
    results["soundness"] = pm4py.check_soundness(net, im, fm, print_diagnostics=False)
    results["train_fitness"] = pm4py.fitness_alignments(train_log, net, im, fm)
    results["holdout_fitness"] = pm4py.fitness_alignments(holdout_log, net, im, fm)
    results["train_precision"] = pm4py.precision_alignments(train_log, net, im, fm)
    results["generalization"] = pm4py.generalization_tbr(train_log, net, im, fm)
    results["simplicity"] = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")

    neg_diag = pm4py.conformance_diagnostics_alignments(negative_log, net, im, fm)
    results["negative_full_fitness_count"] = sum(1 for d in neg_diag if d["fitness"] == 1.0)

    pos_diag = pm4py.conformance_diagnostics_alignments(positive_log, net, im, fm)
    results["positive_full_fitness_count"] = sum(1 for d in pos_diag if d["fitness"] == 1.0)

    return results
```

## Stakeholder comprehension protocol

Recruit 12–15 stakeholders from compliance, operations, IT architecture, data analysis, audit, and process ownership. Provide:

- a 30-minute tutorial,
- a one-page model diagram with a legend,
- 20 traces: 10 positive, 10 negative,
- a 5-point Likert scale with defined anchors,
- a confidence rating per trace.

Measure:

- classification accuracy,
- time per trace,
- confidence,
- subjective comprehension score,
- inter-rater reliability (Krippendorff’s alpha).

Use the same protocol for all models, randomize model order, and blind model names.

## Decision rule for rejection despite good aggregate metrics

Reject a model if **any** of the following holds, regardless of aggregate fitness or precision:

- soundness check fails,
- any curated negative trace has full fitness,
- any positive probe has fitness below 1.0,
- holdout fitness is more than 0.05 below training fitness,
- precision on the negative suite is below 1.0,
- stakeholder comprehension accuracy is below 0.80 or mean score is below 3.5,
- median alignment runtime per case exceeds 1.0 second for compliance use,
- duplicate labels exceed 0 without a documented impact analysis.

# 10. Governance Recommendation

- **Model S** may be used **only for exploration and hypothesis generation**. It must not be used for conformance enforcement, simulation, or stakeholder communication of policy. It should be retired from any governance decision pipeline. Its high fitness and generalization are not evidence of safety.
- **Model C** is **not acceptable for compliance or exploration**. It may be archived as a catalog of known training variants. It should be retired from active use. Its low holdout fitness, low generalization, poor simplicity, duplicate labels, and poor stakeholder comprehension make it unsuitable for deployment.
- **Model_third** is the only candidate for compliance use, but it is not yet deployable. Before deployment it must:
  - pass the soundness and reachability checks,
  - pass the curated negative trace suite,
  - pass the attribute-stratified holdout tests,
  - pass the missing-event and duplicate-event perturbation tests,
  - pass the unseen-combination tests,

  - have the `external/internal` attribute added or the post-hoc external check enforced,

  - have no duplicate labels,
  - have acceptable runtime for the expected log volume,
  - receive formal sign-off from compliance, operations, IT architecture, and the process owner.

Neither original model should be deployed for compliance.

# 11. Dissenting View

One could reasonably object that my recommendation is too harsh on Model C and too optimistic about the third alternative. Model C’s high training precision and audit-ready variants may be exactly what a compliance function wants: a model that rejects unseen behaviour until a human approves it. Its low holdout fitness may not indicate overfitting; it may indicate that the holdout contains genuinely noncompliant or unapproved variants. F8 explicitly says unseen behaviour should be treated as noncompliant until approved. Model S’s permissiveness is not a bug for exploration; it is a feature that allows analysts to see the process without being forced into a rigid template. The third alternative, by allowing any non-empty subset of mandatory checks after a Correct Dossier, may be more permissive than policy allows when the affected-check attribute is missing. It also assumes correction occurs before optional reviews, which is not stated in P6. If the external/internal attribute cannot be added, the third alternative’s optional Supplier Review may be unsafe for compliance. A more conservative governance approach might keep Model S for exploration, Model C for enforcement of known variants, and require human review for all unseen combinations, rather than deploying a new model that has not been validated with real data.

Additional evidence that would change my decision: results from the curated negative trace suite for all three models; attribute-stratified holdout results with `external/internal` and `affected-check` attributes present; stakeholder comprehension results from the documented protocol; alignment-cost sensitivity results; a formal proof that Model_third’s correction loop does not allow invalid rechecks; and real deployment data showing missing-event rates. If Model_third fails the negative suite, or stakeholders cannot understand it, or the external attribute cannot be added, then the safer fallback is human-in-the-loop review using Model C for known variants and Model S only for exploration.
