# 1. Assumptions and Interpretation

1. **Risk-level choice representation**: The low-risk vs high-risk routing is modeled as an explicit XOR choice: one branch contains `Supervisor Review` (low risk), the other branch contains a submodel in which both `Quality Review` and `Regulatory Review` must occur (high risk). The underlying data condition (“low” vs “high” risk) is not modeled explicitly; instead, the fact that exactly one of these approval patterns appears in the trace is interpreted as evidence of the chosen risk level.
2. **Optional supplier consultation**: `Consult Supplier` is represented as an optional single-occurence activity via an XOR between a silent skip and the visible activity. This enforces “at most once” in both the process tree and the POWL model, and “selected vs not selected” is interpreted from the presence or absence of `Consult Supplier` in a trace.
3. **Passing inspection abstraction**: The inspection outcome is abstracted purely through control flow. A passing inspection is represented as the last `Inspect Trial` event in the loop, with no subsequent `Adjust Parameters`. Failed inspections are modeled by an `Adjust Parameters` event that occurs strictly between two consecutive `Execute Trial – Inspect Trial` pairs. Thus, any `Inspect Trial` that is followed (later in the trace) by `Adjust Parameters` is implicitly “failing,” while the final `Inspect Trial` without a following `Adjust Parameters` is implicitly “passing.”
4. **Duplicate visible labels**: Duplicate visible labels are *avoided* deliberately. Each activity label from the narrative appears exactly once in the process tree and once (as a `Transition`) in the POWL model. This avoids ambiguity when interpreting logs and keeps alignment between labels and conceptual activities. Any approximation is therefore done structurally (e.g., by reordering or constraining blocks) rather than by duplicating visible labels.
5. **Approximation policy for the process tree**: The process tree is a **conservative under-approximation** of the intended behavior. In particular, it requires all approvals and the (optional) supplier consultation to complete before the trial loop starts, even though the intended semantics permit approvals and consultation to overlap the trial. This sacrifices some allowed concurrency but does not admit behavior that violates any of the stated business rules.
6. **Concurrency interpretation (“may overlap”)**: In the intended specification and in the POWL model, “may overlap” is interpreted as **true concurrency**, i.e., the absence of a precedence edge so that all linearizations that preserve other constraints are possible. In the process tree, only those overlaps that can be expressed via block-structured `PARALLEL` operators (notably between `Contain Material` and `Analyze Root Cause`, and between `Quality Review` and `Regulatory Review` in the high-risk branch) are modeled as true concurrency; other “may overlap” relations (approvals/trial, supplier/trial) are approximated by enforcing a stricter order.

# 3. PM4Py Process-Tree Model

## 3.1 Compact process-tree expression

```text
SEQUENCE(
  "Register Deviation",
  PARALLEL(
    SEQUENCE("Contain Material", "Plan Verification"),
    SEQUENCE(
      "Analyze Root Cause",
      "Design Corrective Action",
      XOR(
        "Supervisor Review",
        PARALLEL("Quality Review", "Regulatory Review")
      ),
      XOR( τ, "Consult Supplier")
    )
  ),
  LOOP(
    SEQUENCE("Execute Trial", "Inspect Trial"),
    "Adjust Parameters"
  ),
  "Release Material",
  "Archive Case"
)
```

Informal reading:
- After `Register Deviation`, two branches execute in parallel: one performs `Contain Material` then `Plan Verification`, the other performs `Analyze Root Cause`, then `Design Corrective Action`, then either low-risk (`Supervisor Review`) or high-risk (`Quality Review` and `Regulatory Review` in parallel), and optionally `Consult Supplier` (or τ-skip).
- Once both parallel branches are complete, a loop repeatedly executes `Execute Trial` followed by `Inspect Trial`, inserting `Adjust Parameters` between iterations, and stops after a final `Execute Trial – Inspect Trial` pair without `Adjust Parameters`.
- Finally, `Release Material` and `Archive Case` complete the case.

## 3.2 Python code constructing the tree

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Leaf activities
register_deviation = ProcessTree(label="Register Deviation")
contain_material = ProcessTree(label="Contain Material")
analyze_root_cause = ProcessTree(label="Analyze Root Cause")
plan_verification = ProcessTree(label="Plan Verification")
design_corrective_action = ProcessTree(label="Design Corrective Action")
supervisor_review = ProcessTree(label="Supervisor Review")
quality_review = ProcessTree(label="Quality Review")
regulatory_review = ProcessTree(label="Regulatory Review")
consult_supplier = ProcessTree(label="Consult Supplier")
execute_trial = ProcessTree(label="Execute Trial")
inspect_trial = ProcessTree(label="Inspect Trial")
adjust_parameters = ProcessTree(label="Adjust Parameters")
release_material = ProcessTree(label="Release Material")
archive_case = ProcessTree(label="Archive Case")

# High-risk approvals: Quality and Regulatory in parallel
high_risk_parallel = ProcessTree(operator=Operator.PARALLEL)
high_risk_parallel.children = [quality_review, regulatory_review]
quality_review.parent = high_risk_parallel
regulatory_review.parent = high_risk_parallel

# Risk route: low-risk vs high-risk
risk_route = ProcessTree(operator=Operator.XOR)
risk_route.children = [supervisor_review, high_risk_parallel]
supervisor_review.parent = risk_route
high_risk_parallel.parent = risk_route

# Optional supplier consultation: τ (skip) vs Consult Supplier
skip_supplier = ProcessTree(label=None)  # silent τ
supplier_choice = ProcessTree(operator=Operator.XOR)
supplier_choice.children = [skip_supplier, consult_supplier]
skip_supplier.parent = supplier_choice
consult_supplier.parent = supplier_choice

# Containment and verification branch
contain_then_plan = ProcessTree(operator=Operator.SEQUENCE)
contain_then_plan.children = [contain_material, plan_verification]
contain_material.parent = contain_then_plan
plan_verification.parent = contain_then_plan

# Analysis, design, approvals, and optional supplier branch
analyze_branch = ProcessTree(operator=Operator.SEQUENCE)
analyze_branch.children = [
    analyze_root_cause,
    design_corrective_action,
    risk_route,
    supplier_choice,
]
for child in analyze_branch.children:
    child.parent = analyze_branch

# Initial parallelization of the two work streams
initial_parallel = ProcessTree(operator=Operator.PARALLEL)
initial_parallel.children = [contain_then_plan, analyze_branch]
contain_then_plan.parent = initial_parallel
analyze_branch.parent = initial_parallel

# Trial loop: (Execute Trial, Inspect Trial) with Adjust Parameters between iterations
trial_once = ProcessTree(operator=Operator.SEQUENCE)
trial_once.children = [execute_trial, inspect_trial]
execute_trial.parent = trial_once
inspect_trial.parent = trial_once

trial_loop = ProcessTree(operator=Operator.LOOP)
trial_loop.children = [trial_once, adjust_parameters]
trial_once.parent = trial_loop
adjust_parameters.parent = trial_loop

# Root sequence: register, initial work, trial loop, release, archive
tree = ProcessTree(operator=Operator.SEQUENCE)
tree.children = [
    register_deviation,
    initial_parallel,
    trial_loop,
    release_material,
    archive_case,
]
for child in tree.children:
    child.parent = tree
```

The variable `tree` holds the root of the constructed process tree.

## 3.3 Approximation and loss of fidelity

This process tree cannot represent the full intended behavior exactly and therefore uses a conservative under-approximation:

1. **Approvals vs trial overlap**: In the intended behavior, the selected approval route (low-risk `Supervisor Review` or high-risk `Quality Review` and `Regulatory Review`) may overlap the trial cycle; `Execute Trial` only depends on `Design Corrective Action` and `Plan Verification`. In the tree, all approvals (and optional supplier consultation) are placed in the `analyze_branch` inside the `initial_parallel` block, which must complete before the `trial_loop` can start. This prevents any overlap between approvals and trials, excluding intended traces where, e.g., `Regulatory Review` finishes while the trial is already running.
2. **Supplier consultation overlap**: The intended semantics allow `Consult Supplier` to overlap design, verification, approvals, and trial work, provided it is complete before `Release Material`. In the tree, `Consult Supplier` is in the same sequential branch as `Design Corrective Action` and approvals inside the `initial_parallel` block and must complete before the trial loop starts. This enforces significantly stronger ordering than required.
3. **Release synchronization**: The intended `Release Material` synchronization condition waits on three potentially independent obligations: a passing trial inspection, completion of the selected approval route, and (if selected) completion of `Consult Supplier`. In the process tree, this is approximated by positioning approvals and supplier consultation before the trial loop and then sequencing `Release Material` after the loop. The explicit three-way synchronization point is thus reduced to “wait until all pre-trial work and the trial loop are over,” which is stricter but easier to express block-structurally.
4. **Data-based conditions**: As required, the process tree does not encode data such as “low” vs “high” risk or inspection outcomes. Instead, these are mapped to structural choices and loop behavior, which means the model cannot prevent, for example, a long sequence of trials where all inspections are implicitly “passing” but the business might consider such repetition unreasonable.

# 4. PM4Py POWL Model

## 4.1 Compact POWL description

```text
Nodes:
  R   = Transition("Register Deviation")
  C   = Transition("Contain Material")
  A   = Transition("Analyze Root Cause")
  PV  = Transition("Plan Verification")
  D   = Transition("Design Corrective Action")

  SR  = Transition("Supervisor Review")
  QR  = Transition("Quality Review")
  RR  = Transition("Regulatory Review")

  CS  = Transition("Consult Supplier")
  τCS = SilentTransition("skip_consult")

  ET  = Transition("Execute Trial")
  IT  = Transition("Inspect Trial")
  AP  = Transition("Adjust Parameters")

  RM  = Transition("Release Material")
  AC  = Transition("Archive Case")

Submodels:
  HIGH = StrictPartialOrder({QR, RR}) with QR and RR unordered.
  RISK = OperatorPOWL(XOR, [SR, HIGH])

  OPT_CS = OperatorPOWL(XOR, [τCS, CS])

  TRIAL_BODY = StrictPartialOrder({ET, IT}) with ET < IT.
  TRIAL_REDO = StrictPartialOrder({AP})
  TRIAL = OperatorPOWL(LOOP, [TRIAL_BODY, TRIAL_REDO])

Root:
  POWL = StrictPartialOrder({
    R, C, A, PV, D,
    RISK, OPT_CS,
    TRIAL,
    RM, AC
  })

Partial-order edges (on POWL.order):
  R < C,  R < A
  C < PV
  A < D, A < RISK, A < OPT_CS
  PV < TRIAL
  D  < TRIAL
  TRIAL < RM
  RISK < RM
  OPT_CS < RM
  RM < AC
```

Intuitively:
- `R` must occur first; `C` and `A` follow and may overlap.
- `PV` depends on `C`; `D`, the risk route, and the supplier-choice block depend on `A`.
- The `TRIAL` loop can start as soon as both `PV` and `D` are complete; it is independent of the approval and supplier blocks.
- `RM` waits for completion of `TRIAL`, the chosen risk route (`RISK`), and the supplier-choice block (`OPT_CS`), after which `AC` terminates the case.

## 4.2 Python code constructing the POWL model

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Leaf transitions
t_register = Transition("Register Deviation")
t_contain = Transition("Contain Material")
t_analyze = Transition("Analyze Root Cause")
t_plan = Transition("Plan Verification")
t_design = Transition("Design Corrective Action")

t_supervisor = Transition("Supervisor Review")
t_quality = Transition("Quality Review")
t_regulatory = Transition("Regulatory Review")

t_consult = Transition("Consult Supplier")
tau_skip_consult = SilentTransition("skip_consult")

t_execute = Transition("Execute Trial")
t_inspect = Transition("Inspect Trial")
t_adjust = Transition("Adjust Parameters")

t_release = Transition("Release Material")
t_archive = Transition("Archive Case")

# High-risk approvals: QR and RR, unordered
high_risk_approvals = StrictPartialOrder({t_quality, t_regulatory})

# Risk route: XOR between low-risk SR and high-risk approvals submodel
risk_route = OperatorPOWL(Operator.XOR, [t_supervisor, high_risk_approvals])

# Optional supplier consultation: XOR between τ-skip and Consult Supplier
supplier_choice = OperatorPOWL(Operator.XOR, [tau_skip_consult, t_consult])

# Trial loop:
#  - body: Execute Trial -> Inspect Trial
#  - redo: Adjust Parameters between iterations
trial_body = StrictPartialOrder({t_execute, t_inspect})
trial_body.order.add_edge(t_execute, t_inspect)

trial_redo = StrictPartialOrder({t_adjust})

trial_loop = OperatorPOWL(Operator.LOOP, [trial_body, trial_redo])

# Root strict partial order
nodes = {
    t_register,
    t_contain,
    t_analyze,
    t_plan,
    t_design,
    risk_route,
    supplier_choice,
    trial_loop,
    t_release,
    t_archive,
}

powl = StrictPartialOrder(nodes)

# Precedence constraints
powl.order.add_edge(t_register, t_contain)
powl.order.add_edge(t_register, t_analyze)

powl.order.add_edge(t_contain, t_plan)

powl.order.add_edge(t_analyze, t_design)
powl.order.add_edge(t_analyze, risk_route)
powl.order.add_edge(t_analyze, supplier_choice)

# Trial needs both design and plan
powl.order.add_edge(t_plan, trial_loop)
powl.order.add_edge(t_design, trial_loop)

# Release waits for trial, approvals, and optional supplier block
powl.order.add_edge(trial_loop, t_release)
powl.order.add_edge(risk_route, t_release)
powl.order.add_edge(supplier_choice, t_release)

# Archive only after release
powl.order.add_edge(t_release, t_archive)
```

The variable `powl` refers to the root `StrictPartialOrder` model.

## 4.3 Concurrency justification for unconnected nodes

Within the root `StrictPartialOrder`, concurrency arises exactly from the absence of edges:

1. **Containment vs root-cause analysis**: `t_contain` and `t_analyze` share only the common predecessor `t_register` and have no edge between them, so they can start in any order or overlap, mirroring the “may proceed independently and overlap” requirement.
2. **Approvals vs trial**: `risk_route` and `trial_loop` have no edge between them; both depend (directly or indirectly) on `t_analyze`, `t_plan`, and `t_design` as specified, but afterward they may interleave arbitrarily, which captures the intended possibility that approvals overlap the trial cycle.
3. **Supplier consultation vs other work**: `supplier_choice` is constrained to occur after `t_analyze` and before `t_release`, but is not ordered against `t_plan`, `t_design`, `risk_route`, or `trial_loop`. This allows consultation to overlap verification planning, corrective-action design, approvals, and the trial, while still being completed before release.
4. **Internal high-risk approvals**: Inside `high_risk_approvals`, `t_quality` and `t_regulatory` share a common context but no order edge, so they may occur in any order or concurrently, as required.
5. **Loop body vs other work**: The trial loop’s internal structure guarantees that each `Execute Trial` precedes its corresponding `Inspect Trial`, with `Adjust Parameters` appearing only between iterations. No external node is ordered with respect to individual loop iterations beyond those explicitly encoded edges, so approvals and supplier consultation can move across trial iterations as long as the global constraints (e.g., completion before `t_release`) are satisfied.

Any pair of nodes that is intentionally left unconnected is so left because the narrative either explicitly allows overlap (“may overlap,” “may proceed independently”) or does not impose a specific ordering, and we want all such interleavings to be retained.

| Release synchronization | `Release Material` requires three conditions: a passing inspection, completion of the selected approval route, and (if chosen) completion of supplier consultation. | Synchronization is approximated by ordering: all approvals and consultation are forced to complete before the trial loop, and `Release Material` is sequenced after the trial loop, so it implicitly waits for all obligations but cannot distinguish which branch contributed which prerequisite or allow approvals/consultation to finish while the trial is running. | Edges enforce `TRIAL < RM`, `RISK < RM`, and `OPT_CS < RM`, meaning release can occur only after the trial loop, whichever risk route was chosen, and the supplier block (if consultation occurred) are all complete, while still allowing them to progress in parallel where permitted. | Process tree under-approximates by baking the synchronization into a stricter total order; POWL is closer to the intended partial-order join. | Using the process tree alone for compliance checking remains safe but may misclassify some feasible as infeasible; the POWL model better supports root-cause analysis on whether late approvals or supplier delays actually caused release delays. |
| Duplicate-label risk | Data-level conditions (risk, inspection result, supplier involvement) are not explicit, so repeated occurrences of the same visible label in different contexts can be ambiguous. | The tree uses each visible label exactly once, so no duplicate-label ambiguity arises. However, if future extensions required label duplication to express non-block patterns, the tree would lack a clear way to distinguish occurrences in analysis. | The POWL model also assigns each visible label to a unique `Transition` instance; optionality and choice are expressed via XOR and partial order, not by duplicating labels. | Both models avoid duplicate-label semantics by design, at the cost of structuring the process and using silent transitions for skips. | Avoiding duplicate labels simplifies log interpretation and conformance checking, reducing the chance that business users misinterpret which occurrence of an activity a particular event corresponds to, though it may make some advanced patterns harder to encode purely structurally. |

# 7. Preferred Representation and Validation Plan

I would treat the **POWL model as the canonical representation** for this process because it can express the key non-block-structured dependencies—especially the independent but synchronized obligations of approvals, supplier consultation, and the trial loop—using explicit partial orders and XOR/LOOP operators, while the process tree must under-approximate these behaviors to remain block-structured. The process tree remains valuable as a simpler, more conservative artifact, but it is less faithful for concurrency-sensitive analysis.

## 7.1 Conversion to accepting Petri nets

1. **Process tree to Petri net**: Use `pm4py.convert_to_petri_net(tree)` to obtain `(net_tree, im_tree, fm_tree)`. This yields a sound workflow net representation of the conservative under-approximation.
2. **POWL to Petri net**: Use `pm4py.convert_to_petri_net(powl)` to obtain `(net_powl, im_powl, fm_powl)`. This net should reflect the richer partial-order and choice/loop structures encoded in the POWL model.

Having both nets enables direct comparison of reachable markings and concurrency patterns.

## 7.2 Soundness checking

For each net, run:

```python
from pm4py import check_soundness

check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)
check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
```

This verifies properties such as proper completion, absence of dead transitions, and boundedness, and will highlight modeling mistakes like unreachable activities or deadlocks introduced by incorrect synchronization.

## 7.3 Bounded or sampled playout

1. **Tree-based playout**: Use `pm4py.play_out(tree, no_traces=N, ...)` with a moderate `N` (e.g., a few thousand) and a bound on loop iterations to generate representative traces from the under-approximating process tree. Inspect these traces to confirm that they respect the narrative dependencies and that no forbidden pattern (e.g., `Adjust Parameters` after the last `Inspect Trial`) occurs.
2. **POWL-based playout**: Use `pm4py.play_out(powl, no_traces=N, ...)` with similar bounds. Pay special attention to traces where approvals and trials overlap and where supplier consultation moves across trial iterations, confirming that these overlap patterns match the intended semantics and that release always synchronizes all required obligations.

Comparing the two sampled languages helps highlight exactly which behaviors are excluded by the process tree relative to the POWL model.

## 7.4 Explicit positive and negative trace tests

1. **Positive tests**: Encode the five allowed witnesses (T1–T5) as an event log and check their conformance against both models using an alignment-based or token-based replay. All five should fit the POWL model. For the process tree, T1, T2, and T4 should fit, while T3 and T5 should be rejected, confirming the documented under-approximation.
2. **Negative tests**: Encode the three forbidden witnesses (F1–F3) and verify that both models reject them, with diagnostics pointing to the earliest violation (e.g., trial before plan/design, release without approvals, release before supplier consultation is finished).

These tests provide targeted regression checks against the most critical constraints and known corner cases.

## 7.5 Checks focused on silent behavior and duplicated labels

1. **Silent transitions**: Inspect the nets derived from both models for silent transitions representing τ-skips (especially for supplier optionality and internal loop mechanics). For these, verify via playout and alignments that:
   - Silent steps do not allow bypassing required visible activities (e.g., skipping all approvals).
   - Silent steps do not create spurious extra behavior such as additional invisible cycles that could lead to livelock.
2. **Duplicate-label robustness**: Although this design deliberately avoids duplicate visible labels, instrumentation in the validation pipeline should include:
   - A check that each visible activity label in the narrative corresponds to exactly one transition in each model.
   - A safeguard that flags any future model changes that introduce additional transitions with the same label, so that their semantics are reviewed explicitly.

## 7.6 Limitations of the validation plan

1. **State-space explosion**: Even with loops bounded during playout, the combination of concurrency and choices can lead to a very large (or infinite) behavioral space, so sampling may miss rare but problematic interleavings, especially those involving long approval delays overlapping multiple trial iterations.
2. **Data and risk semantics**: Since the models intentionally encode only control-flow, the validation plan cannot distinguish, for example, inspecting a sample that is “clearly failing” yet not triggering `Adjust Parameters`, or assigning “high risk” while taking only `Supervisor Review`. It can only check that the structural approvals match the chosen branch.
3. **Approximation asymmetry**: The process tree and POWL nets have different intended scopes: one is conservative, one is more faithful. Soundness and conformance checks can confirm internal consistency but cannot “prove” that either model is a perfect representation of the real-world process; expert review of the differences (such as the overlap of approvals and trials) remains necessary.
4. **Tooling assumptions**: The plan assumes that PM4Py’s POWL-to-Petri-net and playout implementations match the theoretical semantics of XOR, LOOP, and partial orders. Any bugs or undocumented corner cases in these conversions could affect the conclusions and would need separate empirical validation.

# 8. Final Self-Critique

1. **Semantic under-approximation in the process tree**: The process tree deliberately disallows any overlap between approvals/supplier consultation and the trial loop, even though this overlap is central to the intended narrative. While this is documented as a conservative under-approximation, it remains a significant semantic distortion that could mislead performance or compliance analysis if the tree were used in isolation.
2. **POWL semantics and tooling assumptions**: The POWL model assumes typical PM4Py semantics for `OperatorPOWL(Operator.XOR, ...)`, `OperatorPOWL(Operator.LOOP, ...)`, and nested `StrictPartialOrder` objects, but I have not validated the code against a running environment. There is a residual risk that the actual implementation treats certain nested structures differently (e.g., regarding how loop iterations are expanded or how XOR choices interact with the surrounding partial order).
3. **Witness set coverage**: The eight behavioral witnesses focus on relatively short, illustrative traces and a small number of trial iterations. While they do expose the key differences between the two models and several cross-branch violations, they do not exhaustively cover extreme scenarios such as many repeated trial cycles, very late supplier responses, or interleavings where approvals start very early but finish only shortly before release, which could reveal further subtle discrepancies between the intended semantics and the formal models.
