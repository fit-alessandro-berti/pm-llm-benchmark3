## 1. Consistency rules and evidence model

To repair an incomplete Object-Centric Event Log (OCEL 2.0) without imposing unjustified assumptions, we establish a structured hierarchy of consistency rules. Rules are classified by structural certainty:

```
+---------------------------------------------------------------------------------+
|                               RULE CLASSIFICATION                               |
+------------------------------------+--------------------------------------------+
| Category                           | Description & Operational Role             |
+------------------------------------+--------------------------------------------+
| 1. Hard Invariants                 | Non-negotiable structural constraints      |
| 2. Strong Defaults                 | High-probability operational patterns      |
| 3. Weak Heuristics                 | Contextual hints (require multi-feature)   |
| 4. Evidence Against Repair         | Domain contradictions that block links     |
+------------------------------------+--------------------------------------------+
```

### Classification of Rules

1. **Hard Invariants (Structural Constraints)**
   - **HI-1 (Referential Integrity):** Every object ID referenced in event-to-object (E2O) or object-to-object (O2O) relations must exist in the `OBJECTS` definition table.
   - **HI-2 (Temporal Directionality):** An event cannot relate an object to an activity that occurs prior to the object’s creation or after its destruction, unless explicitly modeled as a retroactive logging event.
   - **HI-3 (O2O Qualifier Semantics):** O2O relations are strictly directed as specified in domain semantics (e.g., `DEL-X carries PK-7`, never `PK-7 carries DEL-X`).

2. **Strong Defaults (Domain Process Expectations)**
   - **SD-1 (Pack Item Cardinality):** A `Pack Item` event normally binds exactly one `Item` and one `Package`. An event with an `Item` but missing a `Package` indicates logging failure or unassigned packing.
   - **SD-2 (Record Payment Linking):** A `Record Payment` event normally connects one `Payment` object to one `Invoice` object.
   - **SD-3 (Dispatch Package Binding):** A `Dispatch Package` event links a `Package` to a `Delivery` object representing the execution of the transport leg.

3. **Weak Heuristics (Contextual Evidence)**
   - **WH-1 (Identifier Similarity):** Matching string tokens (e.g., `scanner_ref=PK8-2` $\rightarrow$ `PK-8`; `external_ref=N-421?` $\rightarrow$ `DEL-Y`) suggest relation candidates but do not prove them.
   - **WH-2 (Arithmetic Coherence):** Financial summation (e.g., `ORD-A` declared value $130 + `ORD-B` declared value $100 = `INV-44` total $230) provides circumstantial support for structural grouping, but fees, taxes, or discounts mean equality is non-conclusive.
   - **WH-3 (Attribute Coherence):** Matching metadata attributes (e.g., `route_hint=NORTH` matching `route=NORTH`; `customer=C17` matching `portal_customer=C17`) increases candidate plausibility.

4. **Evidence Against Repair (Counter-Evidence)**
   - **EA-1 (Cross-Customer Contradiction):** Linking an order, invoice, or delivery to an object belonging to a different customer is prohibited unless explicitly modeled as a third-party consolidated shipment.
   - **EA-2 (Cardinality Over-Extension):** Forcing a 1:1 process model on an enterprise log where multi-object handling is standard (e.g., consolidated multi-order packages or multi-order invoices).

---

### Evidence Fusion Model

To evaluate candidate edges without resorting to arbitrary binary decisions, candidate relations are evaluated through a weighted multi-feature scoring model:

$$\text{Score}(e, o) = w_1 S_{\text{ID}} + w_2 S_{\text{Time}} + w_3 S_{\text{Attr}} + w_4 S_{\text{Card}} - w_5 C_{\text{Conflict}}$$

Where:
- $S_{\text{ID}} \in [0, 1]$ represents token overlap (e.g., string matching on identifiers).
- $S_{\text{Time}} \in [0, 1]$ measures temporal closeness and lifecycle alignment.
- $S_{\text{Attr}} \in [0, 1]$ measures matching attributes (Customer C17, Route NORTH).
- $S_{\text{Card}} \in [0, 1]$ rewards compliance with expected object cardinalities.
- $C_{\text{Conflict}} \in [0, 1]$ penalizes explicit contradictions (e.g., cross-customer misalignments).

Decisions are classified as:
- **Accept ($\ge 0.80$):** Strong multi-feature alignment with no structural conflicts.
- **Provisional ($0.50 - 0.79$):** Plausible feature support, but alternative interpretations exist.
- **Unresolved ($0.30 - 0.49$):** Insufficient evidence; left unlinked to prevent false assumptions.
- **Reject ($< 0.30$):** Contradicted by evidence or structural constraints.

### Bundle A: Conservative / Minimum-Change Repair

Bundle A focuses strictly on repairing local execution anomalies supported by identifier heuristics and lifecycle defaults while rejecting speculative financial or delivery aggregations.

* **ev08 and PK-8:** Accepts `ev08` $\rightarrow$ `PK-8` and `PK-8 packs IT-B1`. Scanner reference `PK8-2` and timing (09:05) directly support completing the packaging phase for item `IT-B1`.
* **ev10 and DEL-X/DEL-Y:** Accepts `ev10` $\rightarrow$ `DEL-Y` and `DEL-Y carries PK-8`. String match between `N-421?` and `carrier_ref=N-421` provides clear evidence for assigning `DEL-Y`. `DEL-X` is explicitly rejected.
* **ev11 and Delivery Objects:** Leaves `ev11` unresolved regarding delivery objects (`DEL-X`, `DEL-Y`) and `ORD-B`. `ev11` is retained as an order-level confirmation tied strictly to `ORD-A` via portal event log.
* **INV-44 and ORD-B:** Rejects adding `ev12` $\rightarrow$ `ORD-B` or `INV-44 bills ORD-B`. Retains `ORD-B` as an unbilled order, recognizing that arithmetic equality ($130 + 100 = 230$) is circumstantial and could represent unobserved invoices or line-item tax structures.
* **PAY-2 and INV-44:** Accepts `ev14` $\rightarrow$ `INV-44` and `PAY-2 settles INV-44`. Payment `PAY-2` ($130) exactly clears the balance of `INV-44` ($230 total - $100 `PAY-1`).

**Lifecycle Coherence Assessment:** Produces complete, coherent lifecycles for items (`IT-A1`, `IT-A2`, `IT-B1`), packages (`PK-7`, `PK-8`), deliveries (`DEL-X`, `DEL-Y`), and payment `PAY-2`. `ORD-B` remains partially observed (lacks billing/delivery confirmation), accurately reflecting log incompleteness.

### Bundle B: Consolidated Multi-Order & Customer-Centric Repair

Bundle B operates under the hypothesis that Customer C17’s activities were consolidated across order management, billing, and fulfillment boundaries.

* **ev08 and PK-8:** Accepts `ev08` $\rightarrow$ `PK-8` and `PK-8 packs IT-B1`. Interprets `PK-8` as a multi-order package containing `IT-A2` (from `ORD-A`) and `IT-B1` (from `ORD-B`).
* **ev10 and DEL-X/DEL-Y:** Accepts `ev10` $\rightarrow$ `DEL-Y` and `DEL-Y carries PK-8`, matching the dispatch leg for `PK-8`.
* **ev11 and Delivery Objects:** Accepts `ev11` $\rightarrow$ `DEL-X`, `ev11` $\rightarrow$ `DEL-Y`, and `ev11` $\rightarrow$ `ORD-B`. Interprets `N-42*` as a wildcard confirmation covering both northern route carriers (`N-420` and `N-421`), representing full customer portal delivery acceptance for all active shipments.
* **INV-44 and ORD-B:** Accepts `ev12` $\rightarrow$ `ORD-B` and `INV-44 bills ORD-B`. Treats `INV-44` as a consolidated invoice covering both `ORD-A` ($130) and `ORD-B` ($100).
* **PAY-2 and INV-44:** Accepts `ev14` $\rightarrow$ `INV-44` and `PAY-2 settles INV-44`.

**Lifecycle Coherence Assessment:** Achieves full lifecycle closure for all objects. However, it introduces complex structural dependencies (multi-order packages, multi-order invoices, multi-delivery confirmations) that may mask underlying logging gaps if the actual process operated on discrete single-order paths.

### Verification of Dual-Support & Circular Reasoning Prevention

To maintain sound evidence validation, we distinguish between independent dual-support and circular inference:

```
CIRCULAR INFERENCE (INVALID):
[Uncertain E2O Edge: ev08 -> PK-8]  ===> Assumes O2O Edge: PK-8 packs IT-B1
                                    <=== Claims O2O confirms E2O Edge

INDEPENDENT DUAL-SUPPORT (VALID):
[E2O Evidence: scanner_ref=PK8-2]   ---> Supports ev08 -> PK-8
[Metadata Match: route=NORTH, C17]   ---> Independently supports PK-8 packs IT-B1
```

* **Independent Support Check:**
  - `ev08` $\rightarrow$ `PK-8` is supported by event attribute `scanner_ref=PK8-2`.
  - `PK-8 packs IT-B1` is supported by metadata alignment (`route_hint=NORTH` matching `PK-8`'s route and shared customer `C17`).
* **Circular Reasoning Warning:** Inferring `PK-8 packs IT-B1` solely because `ev08` was linked to `PK-8`, and then using `PK-8 packs IT-B1` as evidence to justify `ev08` $\rightarrow$ `PK-8`, constitutes circular reasoning. In our model, the O2O relation is classified as a derived dependency of the E2O acceptance, not independent evidence.

## 8. Over-repair warnings

Aggressive data repair creates significant risks of obscuring process bottlenecks and inserting artificial execution paths. Five specific domain risks are identified below:

```
+-----------------------------------------------------------------------------------+
|                            OVER-REPAIR RISK MATRIX                                |
+-------------------------------+---------------------------------------------------+
| Risk Category                 | Operational & Analytical Failure                  |
+-------------------------------+---------------------------------------------------+
| 1. False Consolidation        | Masking missing invoices by inventing billing     |
|                               | edges based on arithmetic match                   |
| 2. Erasing Scanner Failures   | Treating unlinked item packing as complete log,   |
|                               | hiding warehouse hardware outages                 |
| 3. Artificial Delivery Sync   | Forcing delivery confirmation to all carriers,    |
|                               | destroying transit lead-time metrics              |
| 4. Metric Inflation           | Duplicate event occurrences in log flattenings    |
| 5. Conformance Distortion     | Masking unbilled order compliance violations      |
+-------------------------------+---------------------------------------------------+
```

### Detailed Over-Repair Risk Scenarios

1. **False Multi-Order Billing Consolidation (Force-linking `ev12` $\rightarrow$ `ORD-B`)**
   - *Failure Mechanism:* Forcing `ev12` to link to `ORD-B` because $130 + 100 = 230$ assumes arithmetic balance proves billing intent.
   - *Impact:* If `ORD-B` was unbilled due to an ERP integration failure, over-repair conceals an active revenue-leakage defect, marking an unbilled order as completed.

2. **Obscuring Warehouse Hardware Outages (Force-linking `ev08` without scanner check)**
   - *Failure Mechanism:* Automatically assigning `ev08` to `PK-8` assuming every item must have a package.
   - *Impact:* If `ev08` lacked a package reference due to a physical scanner failure or handheld buffer crash, repairing the log erases evidence of operational hardware failures in the packing bay.

3. **Distorting Delivery Transit Performance (Force-linking `ev11` $\rightarrow$ `DEL-X` & `DEL-Y`)**
   - *Failure Mechanism:* Binding `Confirm Delivery` (`ev11`) to both `DEL-X` and `DEL-Y` based on wildcard `N-42*`.
   - *Impact:* If `DEL-Y` arrived 2 days after `DEL-X`, force-linking `ev11` to both deliveries artificially aligns their completion timestamps, corrupting carrier SLA lead-time calculations.

4. **Trace Variant Explosion and Metric Inflation in Flattenings**
   - *Failure Mechanism:* Indiscriminately connecting shared events to multiple object instances.
   - *Impact:* Flattening on `Order` under Bundle B causes `Issue Invoice` and `Confirm Delivery` to be duplicated across trace variants, distorting activity execution counts and generating false path combinations in standard DFG miners.

5. **Masking Process Conformance Violations**
   - *Failure Mechanism:* Artificially closing open lifecycles to force conforming process paths.
   - *Impact:* Automated conformance checking against a reference process model will report 100% compliance, masking underlying process anomalies such as unapplied customer payments, orphan shipments, or unbilled customer orders.
