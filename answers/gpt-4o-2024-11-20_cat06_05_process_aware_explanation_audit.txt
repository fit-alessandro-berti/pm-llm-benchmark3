### 2. Process-Model Consistency Checks

To ensure process-aware alignment, the following validation suite is recommended:

1. **Prefix-Time Availability Checks**:  
   Compare feature timestamps and calculation rules against `t0`. Validate that no information beyond `t0` leaks into prediction features.

2. **Activity-Order Feasibility Checks**:  
   Validate sequence conformity to the normative process model. Use declarative constraints or conformance verification to check whether recorded sequences are process-legal (e.g., `Claim Closed` cannot precede `Damage Assessment Completed`).

3. **Same-Timestamp Ambiguity Checks**:  
   For events with identical timestamps, enforce sequence validation using ingestion order or introduce process-defined sequence indexes. Verify that reliance on undocumented or variable ordering is avoided.

4. **Full-Trace Dependency Checks**:  
   Identify features using post-`t0` trace information (e.g., `appeal_seen_anywhere`). These should trigger temporal-leakage flags.

5. **Future-Possibility versus Enabled Activity Checks**:  
   Verify whether variables like `Appeal -> Settlement Decision Recorded` reflect only processes enabled at `t0`, not future hypotheticals. Valid only if appeals have already been initiated by `t0`.

6. **Semantic Repetition Validity**:  
   Validate scenarios where repeated activities (e.g., sequential `Settlement Decision Recorded`) occur. Confirm that repeated events align with appeals, and distinguish appeal decisions from initial resolutions.

### 3. Alternative Feature Interpretations

| Class                            | Features                                                         | Interpretation                             |
|----------------------------------|------------------------------------------------------------------|-------------------------------------------|
| **Defensible Predictive Signal** | `queue_length_at_t0`, `initial_damage_complexity`, `elapsed_since_registration_at_t0`, `initial_reserve` | Direct correlates of process delays; predictive but not necessarily causal. |
| **Process-State or Congestion Signals** | `Documents Requested -> Documents Received`, `Coverage Check Completed -> Fraud Investigation Opened` | Reflect intermediate workflow states only. |
| **Proxy Requiring Fairness/Robustness Review** | `claimant_region`, `claimant_channel`                          | Indirect signals related to delays; audit for disparate impact or operational bias. |
| **Drift/Calendar Proxy**         | `calendar_week`                                                 | Timepoint-specific effects (holidays, policy changes) must be managed carefully. |
| **Unusable Until Lineage Repaired** | `prior_claim_count_before_t0`, `risk_score_current`, `num_document_requests_total`, `same_day_document_count_snapshot`, `last_resource_role`, `final_handler_team` | Cannot be used until proper `t0` lineage or temporal restrictions are applied. |

Claims should avoid causality where only correlations exist, especially in proxy features like `claimant_region` or drift-related issues like `calendar_week`.

### 5. Recommendations for Explanation Validation

1. **Feature-Store Design Improvement**:  
   Enforce prefix-only feature computation with strict lineage definitions tied to `t0`.

2. **Historical Feature Timestamps**:  
   Maintain timestamps for all feature updates to ensure temporal validity is traceable.

3. **Prefix-Only Recomputation**:  
   Recompute existing predictions using only admissible `t0` features as part of an immediate fix.

4. **Process Conformance Tests**:  
   Use declarative rules to validate trace feasibility and sequence order integrity pre-ingestion.

5. **Calibration Post-Feature Removal**:  
   Retrain and recalibrate the model to adjust for features removed due to leakage or inconsistencies.

6. **Explanation Stability**:  
   Measure output stability after retraining to ensure proper substitution or removal impacts.

7. **Proxy and Fairness Audits**:  
   Evaluate features (e.g., region, channel) for fairness risks and disparate impact across demographic groups.

8. **Schema/Process Drift Monitoring**:  
   Continuously monitor operational changes (e.g., new policies, holidays) to mitigate feature drift risks.
