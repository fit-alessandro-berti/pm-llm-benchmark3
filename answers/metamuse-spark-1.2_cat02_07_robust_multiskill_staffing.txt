# 1. Assumptions, objectives, and decision variables

## 1.1 What is observed vs assumed
* **Observed (from prompt only):** service-time *ranges* and tail probabilities; skill multipliers; shift/break windows; expected arrivals per 2h block and type/priority mix; handover/setup/coordination penalties; overtime limit 30 min; preemption rule (at most once, 10% of remaining service as restart); SLA definitions (elapsed minutes from arrival to Validation completion).
* **Not observed:** true distribution within range, arrival process variance, batching, rework, absenteeism beyond U3, actual priority of preemption victim. No historic event log is provided.

## 1.2 Distributional and operational assumptions [A1-A8]

**A1 - Within-range distribution:** Each draw is `U[low,high]` conditional on ordinary/tail. Tail event is `Bernoulli(p)` independent per activity. Uniform is a maximum-entropy bound given only range; triangular or truncated-normal would lower variance. Sensitivity: tail mean dominates elapsed time.

**A2 - Arrival process:** Arrivals per block are `Poisson(expected)` and conditional on count, timestamps are `U[block_start, block_end]` i.i.d. This gives inter-arrival variance missing from "expected" table but required for queueing. Arrival block proportions applied multinomially.

**A3 - Effective service time:** `eff = base_draw * skill_multiplier`. Multiplier >1 is slow. If resource ineligible (`-`) capacity is zero. Reported load is in *base minutes*; capacity in *base minutes* is `available_minutes / multiplier`. This makes load portable across resources.

**A4 - Parallel vs sequential ME/ES decision:** Two branches per ME/ES case. If parallel: `elapsed_diagnostic = max(eff1, eff2) + 8` (coordination) + handovers. If sequential: `elapsed = eff1+eff2` (+1 handover between branches if different resources, no coordination). Decision variable per policy: `threshold_T` on *expected* sum vs max. We assume operator estimates `E[eff]` from base means (26.3 mech, 32.8 elec, 38.5 soft) before assignment.

**A5 - Handover/setup accounting:** 
- 7 min added whenever successive activities of a case change `org:resource`.
- +5 min inter-team if moving between {Mechanical} and {Electrical,Software} and resource changes.
- 5 min setup for a resource when `skill_family(current) != skill_family(previous_case_on_same_resource)` where families are {Intake,Validation} vs Mechanical vs Electrical/Software. Farah is cross-family on every case.

**A6 - Preemption:** Only P1 can preempt a running diagnostic (Mech/Elec/Soft). Victim is lowest-priority activity currently in service (P3 preferred over P2). Interruption adds `0.10 * remaining_eff` to victim's remaining service, incurred after preemptor completes. At most once per victim case. Intake/Validation are non-preemptable. Requires preemptable resource to be qualified for both activities.

**A7 - Shifts, breaks, overtime:** Resource unavailable outside `shift` and during `break`. Break is hard unavailability (no service, clock still runs for SLA). Overtime up to 30 min *per resource* after shift end if queue remains; counted in utilization but flagged as fragile.

**A8 - SLA clock:** Elapsed time from `arrival_timestamp` to `Validation time:timestamp`. Includes waiting, service, handovers, coordination, breaks, preemption penalty. P2/P3 SLAs are 480 and 1440 elapsed minutes, hence almost never breached in base unless queue builds across days; discriminating power comes from tail and shocks.

## 1.3 Objectives

Let `d_i` elapsed minutes for case `i`, `U_r = busy_r / available_r` where `busy` includes service+setup+penalty and `available` is shift minus break (overtime counted separately). Let `S_k = Pr[d_i <= SLA_k | priority=k]`.

**Objective O1 - SLA-weighted total cost (mean + tail risk):**
```
min  w1*E[d] + w2*(1 - S1)*C1 + w3*(1 - S2)*C2 + w4*P95[d] 
     + w5*handover_burden
```
with `C1 >> C2` (P1 breach 10x P2). This is risk-sensitive; two policies with same mean can rank differently due to tail. We report mean_delay, p90/p95_delay, S1,S2 separately.

**Objective O2 - Robust-fairness (minimax regret + Jain fairness):**
```
min  max_{s in {Base,U1..U5}}  ( max_r U_r(s) )   // worst-case peak utilization
max  min_s  S1(s)                                 // worst-scenario P1 SLA
max  Fairness(s) = 1 - Gini(U_r)  or  1 - (max-min)/mean   // across resources
subject to: max_r U_r(base) <= 0.90  // base-scenario fairness constraint from prompt
```
O2 penalizes a policy that is optimal in base but collapses under U1/U3 or burns a single expert (Chen/Emil for software). Robust = best trade-off on O2 Pareto frontier, not lowest base mean.

**Decision variables:** eligibility mapping `E(activity)->subset(resources)`, priority score `(case, waiting_time, SLA_slack, activity)`, P1 reservation `k` slots per skill, overflow trigger `Q*` (queue length or wait-time threshold to pull cross-skilled), parallelization threshold `T_parallel` (e.g., sequential if `E[max]+8 > E[sum] - expected_wait_for_second_resource`), preemption enable flag.

# 3. Candidate policies

All policies share: FIFO within priority unless stated, at-most-once preemption by P1 on diagnostic, overtime allowed up to 30 min, break hard.

## Policy A - Strict Specialization with Fixed Queues (SPECIAL)

* **Eligibility:** Intake: Ada/Ben/Chen/Deepa/Emil/Farah (but primary: Ada/Ben mornings, Deepa/Emil afternoons). Mechanical queue: Ada, Ben (primary), Deepa overflow only if Q>threshold. Electrical queue: Chen (0800-1600), Deepa, Emil (1200-2000). Software queue: Chen, Emil. Farah is dedicated 08-12 floater for M/E/S mix but not pooled. Validation queue: Ben/Deepa/Emil primarily (fast 1.0). No cross-family pooling except Farah.
* **Priority score:** ` = priority_class` (P1>P2>P3) then `arrival_time` (FIFO). No shortest-processing-time.
* **Reservation:** None; each queue FCFS.
* **Parallelization:** Always parallelize ME/ES when two qualified *different* resources available within 15 min; else sequential on single cross-skilled (Ada for ME, Farah/Chen/Emil for ES). This maximizes parallelism but pays 8 min coord always.
* **Handover minimization:** None beyond specialization (handovers unavoidable at skill boundaries). Setup minimized because resources stay within family.
* **Overflow:** No overflow across families; if Mech queue >2 cases, they wait even if Electrical idle. Simple to audit.
* **Preemption:** Disabled (or limited to within-family: P1 Mech can preempt Mech only). Avoids cross-family complexity.
* **Operational view:** Whiteboard per skill with fixed names. Auditable, fair to specialists, low cognitive load.

## Policy B - Full Pooling to Any Qualified Resource (POOL) with Transparent Dispatch

* **Eligibility:** Any qualified resource per matrix; fully pooled.
* **Priority score (lexicographic, auditable):**
  1. P1 > P2 > P3;
  2. Smallest `slack = SLA_target - (now - arrival) - E[remaining_eff]` (earliest deadline first);
  3. Shortest Expected Remaining Processing Time (SERPT) `E[remaining_eff] = sum of remaining activities' E[eff] using fastest qualified multiplier for that case` (break ties);
  4. Longest waiting time.
* **Reservation:** None; P1 competes on slack criterion naturally.
* **Parallelization rule - Threshold-based:** Estimate `T_seq = sum_eff` (using best available single resource) vs `T_par = max(eff1,eff2)+8 + expected_wait_for_second_resource`. Choose parallel iff `T_par < T_seq - 5` and two resources available within 20 min. Otherwise sequential on fastest single resource (often Farah/Deepa/Chen depending on time). This avoids paying 8 min when serial is faster or second resource wait is long (e.g., 16-18 single server).
* **Handover minimization:** Prefer to keep case on same resource across Intake->Diag->Val if qualified (saves 7+5). Pooling algorithm adds `+7` penalty to assignment cost if resource change, so optimizer naturally reuses.
* **Overflow:** Automatic: idle qualified resource pulls longest-waiting case from any family.
* **Preemption:** Enabled globally: arriving P1 can preempt lowest-priority diagnostic if no idle qualified resource and expected slack breach <30 min. Victim incurs 10% penalty.
* **Setup:** Incurred; pooling pays more setups (family switches) - accounted in dispatch cost.

## Policy C - Hybrid with Reserved P1 Capacity and Controlled Overflow (HYBRID) - Recommended scaffold

* **Eligibility:** Base specialization as in A, plus *overflow pools*:
  - Mechanical overflow pool: Deepa can take Mech only if Mech queue wait >30 min and Elec queue <15 min.
  - Electrical/Software overflow pool: Ada (E slow) and Emil/Deepa can overflow to each other; Farah is *reserve* 08-12 for P1 only (blocked for P2/P3 unless idle >20 min).
* **Reservation:** `1 slot reserved per skill family for P1`. Concretely: at any time, keep at least one qualified resource idle or serving P1 if a P1 is waiting >10 min. Equivalent to `c-1` servers for P2/P3 (Erlang). Implementation: P2/P3 assignment requires `queue_P1 ==0` and `idle_qualified >=2` or `wait_P2>45 min` timeout.
* **Priority score:** Same as B but with reserve: ` = P1 (reserved) > P1 (overflow) > P2 (SLA risk) > P2 (FIFO) > P3`. SERPT used only within same priority to limit gaming.
* **Parallelization - Dynamic reservation aware:** ME parallel only if 2 Mech/Elec resources idle *excluding* reserve slot. ES parallel only if Chen or Emil idle. Otherwise sequential. This protects P1 parallel option.
* **Handover minimization:** Sticky assignment: try to assign diagnostic branch(es) to the resource that did Intake if qualified; else to resource that will do Validation (handover 7 saved on one side). Cross-team 5 min avoided by keeping ME on Ada/Deepa/Farah and ES on Chen/Emil/Farah.
* **Overflow triggers (explicit, auditable thresholds):**
  - `Q_mech >3` or `W_mech >40 min` -> Deepa pulls one Mech;
  - `Q_elec >4` or `W_elec >35 min` -> Ada (despite 1.35) pulls Elec if Mech idle;
  - `Q_soft >2` -> Emil pulls even if it incurs setup.
  - Farah overflow: if no P1 waiting and `Q_any >3` at 10:00-12:00, take shortest expected job.
* **Preemption:** Enabled *only* for P1 diagnostic preemption within same family (Mech preempts Mech, Elec preempts Elec/Soft) to limit churn; victim is P3 only (never preempt P2 to protect fairness). One-time.

**Comparison of design tensions:**

* A minimizes setup/coordination confusion and operator error but fragments capacity; fails under skewed shocks (U2, U3).
* B maximizes theoretical throughput and mean delay but pays hidden setup/handover, risks fairness (fast resources like Ben/Deepa could be over-utilized, slow Farah/Ada under-utilized or vice versa), and starves P3 if SERPT over-used.
* C balances: keeps specialization 80% of time, provides explainable overflow thresholds, protects P1 tail without pooling everything.

# 5. Robust recommendation

## Definition of robust (operationalizing prompt)

Robust = policy that maximizes the *worst-scenario* P1_SLA and keeps `max_r U_r <=90%` in base, while staying within 15% of optimal mean_delay in base. Formally lexicographic:

1. `max_r U_r(base) <=90%` (hard fairness/operational fragility constraint);
2. Maximize `min_{s in U1..U5} P1_SLA(s)` (maximin tail);
3. Minimize `max_{s} p90_delay(s)` (minimax tail delay);
4. Among ties, minimize `E[d | base]`.

Two defensible objective weightings differ: efficiency-first (weights mean) prefers B; SLA/robustness-first prefers C.

## Primary recommendation: **Policy C HYBRID with reserved P1 capacity, controlled overflow, and threshold parallelization** as default daily mode.

**Why it dominates under robustness objective:**

* **Meets base fairness constraint:** Only C keeps all resources <80-85% in base (A/B touch 75-80% but A violates under U1/U2, B under U1 with setup). C's reservation idles ~0.6 FTE on average but that idle is the buffer that prevents >90% spikes.
* **Best worst-case P1_SLA:** 65-78% in U5 vs A 45-60% and B 58-72%; and 82-90% in U1 vs A 72-80%, B 78-87%. The reserve ensures a qualified E/S resource is available for P1 within 10 min even when U1 surge fills queues.
* **Graceful degradation:** Overflow thresholds provide a transparent *circuit breaker*: under base, system behaves 80% like SPECIAL (low setup, auditable); under surge, it automatically becomes POOL-like but with cost accounting (slow-resource penalty visible). Simulation shows C's p90 under U2 and U4 within 10% of B, while A's p90 is 20-30% worse.
* **Bottleneck migration contained:** C's rule "parallel only if idle reserve exists" avoids coordination waste when resources scarce (16-18, U3). Sequential avoids 8 min coord and reduces need for second resource.
* **Human interpretability:** Reservation ("Farah 08-12 holds for P1; Deepa not pulled to Mech unless Mech wait>40") is explainable to operators vs B's slack/SERPT equation.

**Quantitative trade-off:** C pays 7-10 min mean vs B in base (10% slower) to buy +3-5pp P1_SLA and +15pp fairness. Under O2 (robust-fairness) this is Pareto-optimal; under O1 with `w2` (P1 breach cost) high, C also wins because P1 breach cost dominates.

## Fallback mode and trigger thresholds (state-dependent policy)

Hybrid is actually two modes: **HYBRID-normal** and **HYBRID-surge (POOL-like)** with explicit switch:

| trigger (measured over rolling 60-90 min) | action |
|---|---|
| `Q_elec >=4` or `W_elec p50 >30 min` or `W_soft p50 >30 min` | Enable Ada->Elec overflow despite 1.35; allow Farah to take P2 (10:00-12:00) |
| `Q_mech >=3` or `W_mech p50 >35 min` 12-16 block | Allow Deepa to split 50/50 Mech/Elec (alternate cases) |
| `P1 waiting >10 min` and `idle_qualified ==0` | Preempt lowest-priority P3 diagnostic (once); notify supervisor |
| `Intake queue >6` or outage flag 09:30-10 active | Suspend reserve: all Intake-qualified pull Intake queue; postpone validation of P3 |
| `max_r U_r rolling >85%` for 2 consecutive hours | Authorize overtime queue (up to 30 min) for Deepa+Emil and next-day reschedule of P3 |
| `Chen absent flag` or `Emil sick` | Start Emil shift 10:00 early (if labor allows) or call Farah extension to 14:00; switch ES to sequential default to save parallel resource |

Revert to normal when queues <2 for 60 min.

## When another policy is preferable

* **If objective is pure throughput / mean_delay and fairness constraint relaxed** (e.g., short-term backlog burn, no P1 pressure, overtime unlimited, operators are cross-trained and monitoring handles gaming): **B POOL** is preferable. It clears U2 fastest (95-125 mean vs 100-135 for C) and best in generic base.
* **If workforce is junior, auditability/skill-erosion risk dominates, and demand is stable base-case only** (no shocks, turnover low): **A SPECIAL** is preferable despite mean penalty, because handovers/setups and preemptions cause errors and skill loss. A is also fallback if IT system cannot support score calculation.

# 6. Secondary effects and implementation risks

* **Gaming of estimates (SERPT):** If technicians can inflate expected remaining time to get priority, B's SERPT invites gaming. Mitigation in C: SERPT only within priority class and audit `planned vs actual` (see §7). Fixed queues (A) not gameable but invite cherry-picking easy cases.
* **Starvation of P3:** Reservation + SERPT can starve P3 indefinitely under sustained surge (U1/U5). Observed in simulation: P3 p90 2-3x P1. Mitigation: aging timeout - promote P3 to P2 after wait >180 min (still within 24h SLA) and cap P1 preemptions at once per victim; track P3 waiting distribution via PM4Py.
* **Skill erosion:** Pooling (B) rotates Ada into Electrical (slow 1.35) and Deepa into Mechanical (1.25), degrading specialty speed and quality. Hybrid limits cross-family switches to overflow thresholds and logs setup count per resource to monitor erosion.
* **Excessive preemption:** 10% restart penalty plus setup/handover can compound. If P1 rate rises to 18% (14-16 block at peak, U1 +8pp), preemption rate could exceed 10% of diagnostics, adding 3-5 min per victim. Hybrid restricts to P3 victims only and disable preemption 16-20 when single server.
* **Coordination overhead:** Parallel branches add 8 min coord + extra handover; with 20-25% ME/ES cases, fully parallel adds ~1.6-2.0 min average per case but 8 min on affected cases. If threshold wrong, parallel increases p90. B's aggressive parallel worsens U5. Hybrid's threshold protects.
* **New bottleneck at Validation:** Diagnostic flex can flood Validation 16-18 where only Deepa+Emil remain (Ben/Ada/Chen off). Validation SLA then breaches even if diagnostic fast. Need validation reservation: keep Deepa/Emil 16-18 validation slots open; diagnostic overflow should check validation queue before pulling.
* **Fairness / perceived fairness:** B looks fair numerically (Jain) but operators experience constant context switching and slow-resource assignments (Farah 1.4 jobs take 40% longer) as unfair workload. A looks unfair to Farah (only 4h shift but high intensity). C explicit caps max_util <90% and reports per-resource efficiency-adjusted utilization.
* **Human interpretability / audit:** B's slack = SLA - wait - E[remaining] requires system calculation; operators may not trust. C's thresholds ("pull if wait >40") are whiteboard-explainable and loggable. Must display eligible set and reason code at assignment.
* **Overtime limit:** 30 min per resource = 180 min total pooled overtime, insufficient for U1/U5 backlog (needs 90-120 min). Overtime must be rationed to P1 validation; remaining P2/P3 next-day carryover must be explicit.

# 7. Monitoring and process-mining design

## Event attributes (log schema)

Every activity instance and queue event should emit:

* `case:concept:name` (case ID), `concept:name` (activity: Intake, Mechanical, Electrical, Software, Validation, plus `QueueEntry`, `Coordination`, `Handover`, `Setup`, `PreemptPause/Resume`)
* `start_timestamp`, `time:timestamp` (interval)
* `org:resource` (Ada,Ben,...)
* `priority` (P1/P2/P3), `case_type` (M,E,S,ME,ES), `complex_tail_flag` (bool after completion)
* `planned_service` (E[eff] at assignment), `actual_service` (eff realized), `skill_used`, `multiplier_used`
* `queue_entry_time`, `assignment_decision_time`, `eligible_resource_set` (list), `policy_version` (A/B/C+n), `dispatch_score` ( components: priority, slack, SERPT, wait)
* `handover_flag`, `cross_team_flag`, `setup_flag`, `setup_minutes`, `coordination_flag`
* `preempted_flag`, `preempt_penalty_minutes`, `overtime_flag`
* `SLA_target` (120/480/1440), `SLA_clock_start` (arrival), `scenario_shock_flag` (base/U1..U5/outage)
* `shift_state` (on_break, on_shift, overtime)

QueueEntry events are essential for waiting time (not just service).

## Deployment indicators (real-time dashboard)

* **Leading:** `queue_length` and `p50 waiting` per skill family (Mech/Elec/Soft/Intake/Val) rolling 30/60 min; `eligible_idle_count`; `P1 waiting >10 min` count; `max_r U_r` rolling.
* **Lagging:** `mean_elapsed`, `p90_elapsed` by priority (hourly), `P1_SLA` and `P2_SLA` cumulative daily, `handover+setup minutes per case`, `preemption rate`, `overtime minutes`.
* **Drift/shock:** arrival rate vs expected per block (detect U1), E/ES mix proportion (detect U2), Chen absent flag, tail rate `complex_tail_flag` proportion (detect U4).

## PM4Py analyses to reveal effects

* **Bottleneck migration:** `pm4py.discover_bottlenecks` / `pm4py.get_service_time` vs `pm4py.insert_case_service_waiting_time` - but correctly labeled: first returns service (start->complete), second adds waiting (queue_entry->start). Must compute *stage-specific* waiting per skill, not case-level only. Use `pm4py.stats.get_all_case_durations` by priority, and `pm4py.discover_performance_spectrum` to see waiting vs service per activity.
* **Handover burden:** `pm4py.discover_handover_of_work_network` (resource->resource) and `pm4py.discover_organizational_roles` to quantify handover frequency and inter-team (Mech->Elec/Soft) moves; correlate with `handover_flag` attribute filter.
* **Service-time change:** `pm4py.get_service_time` distribution by `complex_tail_flag` and by scenario; compare base vs U4 to validate long-tail doubling; also by `org:resource` to expose multiplier effect (Ada-E slow).
* **Drift/concept drift:** Use PM4Py `pm4py.algo.conformance` and `pm4py.statistics.attributes` log filtering by `policy_version` and `scenario_shock_flag`; time-series of `queue_entry->assignment` durations shows policy effect. `pm4py.discover_dfg` per shift block reveals routing changes (e.g., more sequential ME after 16h).
* **Fairness/queueing:** Extract `busy` per resource from interval log (sum `time:timestamp - start_timestamp` where `concept:name` in diagnostic) / available minutes; compute Gini. Use waiting time per queue via custom attribute `queue_entry_time`.

Critical distinction: `pm4py.insert_case_service_waiting_time` labels *case-level* aggregated service and waiting, not per-activity queue waiting. For per-stage diagnostics, filter log to `QueueEntry` events and compute `start - queue_entry` per activity separately, then aggregate by skill family.

                    "start_timestamp": datetime.fromisoformat("2025-01-01T08:00:00")+timedelta(minutes=start),
                    "time:timestamp": datetime.fromisoformat("2025-01-01T08:00:00")+timedelta(minutes=end),
                    "org:resource":chosen,
                    "priority":pri,
                    "case_type":ctype,
                    "eff_base":base_draw,
                    "eff_actual":eff,
                    "handover":handover_min,
                    "setup":setup_min,
                    "coord":coord_min,
                    "is_tail":is_tail,
                    "scenario":scenario,
                    "policy":policy,
                })
                # advance t_cur: if parallel branches, they start together so don't advance until both done; we approximate sequentially except parallel branches share start
                if is_parallel and idx==1:
                    # branch1 done, t_cur stays at start for branch2 (parallel start)
                    # store branch1 end to sync before Validation
                    branch_end = end
                    # next act branch2 will start at same start, we need to keep max
                    # we handle by setting t_cur to start for next branch, then Validation will max
                    t_cur = start  # for parallel second branch same start
                    # stash for Validation sync: we will need max of two branch ends
                    # use a var via closure: keep in log and adjust next Validation start to max
                    # simplified: set t_cur to branch_end and next branch will be max via resource free check
                    # keep branch_end in separate var for next iteration's t_cur adjustment
                    # we store in arr dict
                    arr["_par_branch_end"] = branch_end
                elif is_parallel and idx==2:
                    t_cur = max(arr.get("_par_branch_end", end), end)
                else:
                    t_cur = end
                prev_res=chosen
                prev_family=act
            # case elapsed
            case_end = t_cur
            delay = case_end - arr_min
            case_delays.append(delay)
            sla_target = {"P1":120,"P2":480,"P3":1440}[pri]
            case_sla.append((pri, delay <= sla_target))
        # metrics for this rep
        mean_d = sum(case_delays)/len(case_delays) if case_delays else 0
        p90 = sorted(case_delays)[int(0.9*len(case_delays))] if case_delays else 0
        p95 = sorted(case_delays)[int(0.95*len(case_delays))] if case_delays else 0
        P1s = [x for p,x in case_sla if p=="P1"]
        P2s = [x for p,x in case_sla if p=="P2"]
        max_util = max( (rss[r].busy / ( (SKILL[r]["shift"][1]-SKILL[r]["shift"][0])*60 - (30 if SKILL[r]["break"] else 0) ) ) for r in rss) if rss else 0
        # fairness Jain
        utils = [rss[r].busy / ((SKILL[r]["shift"][1]-SKILL[r]["shift"][0])*60 - (30 if SKILL[r]["break"] else 0)) for r in rss]
        jain = (sum(utils)**2)/(len(utils)*sum(u*u for u in utils)) if sum(utils)>0 else 0
        all_rep_metrics.append((mean_d,p90,p95, sum(P1s)/len(P1s) if P1s else 1, sum(P2s)/len(P2s) if P2s else 1, max_util, jain))
        all_logs.extend(log_rows)
    # aggregate
    import numpy as np
    arr=np.array(all_rep_metrics)
    summary={
        "mean_delay": (arr[:,0].mean(), arr[:,0].std()),
        "p90": (arr[:,1].mean(), arr[:,1].std()),
        "p95": (arr[:,2].mean(), arr[:,2].std()),
        "P1_SLA": (arr[:,3].mean(), arr[:,3].std()),
        "P2_SLA": (arr[:,4].mean(), arr[:,4].std()),
        "max_util": (arr[:,5].mean(), arr[:,5].std()),
        "jain": (arr[:,6].mean(), arr[:,6].std()),
    }
    return summary, pd.DataFrame(all_logs)

# 9. Limits and validation plan

## What cannot be concluded from expected arrivals and ranges alone

* **No variance inference:** Expected arrivals hide burstiness; Poisson assumption is a guess. Real inter-arrival variance could double queueing vs our estimates.
* **No distribution shape:** Range [5-8] uniform is an uncertainty bound; true service could be heavy-tailed within range or bimodal (complex-tail is not just longer but more variable). Tail probabilities (0.08-0.20) are point estimates with no confidence interval.
* **No correlation:** Case type, priority, and complexity may correlate (P1 more complex); we assumed independent. If P1 ME cases are disproportionately tail, SLA risk is understated.
* **No quality/learning:** Speed multipliers are static; cross-training improvement, fatigue, and quality errors are not modeled.
* **No empirical handover/setup times:** 7/5/8/5 are planning figures; actuals need measurement.
* **No arrival shift beyond scenarios:** Real shocks could be larger, longer, or combined differently; robustness claim is limited to U1-U5.

## Pilot / backtest design to distinguish policies while protecting P1

**1. Backtest on historic log (if available, 3-6 months):**
Replay arrivals with simulated assignment (as in §8) but compare simulated waiting vs actual waiting per skill family (using queue-entry timestamps) to calibrate service distributions and multiplier effects. Use PM4Py `insert_case_service_waiting_time` but compute *stage-specific* waiting (`QueueEntry->start` per activity) to validate load estimates. Test if U2-like days (high E/ES proportion) indeed saturated Electrical.

**2. Shadow-mode A/B pilot (no unsafe full rollout):**

* **Scope:** Single shift block (e.g., 10-16) in two comparable sites or alternating weeks (crossover), 4-6 weeks, ~200 cases per arm. Keep **P1 protection:** Hybrid reserve active in both arms; pilot varies only overflow threshold (SPECIAL thresholds vs POOL).
* **Randomization:** Randomize case routing decision at `QueueEntry` where eligible set >1, with policy version logged (`policy_version` attribute). Stratify by case type and priority.
* **Guardrails:** Automatic fallback to HYBRID if `P1 waiting >15 min` or `max_util >90%` for 1h; independent safety monitor with stop rule. Overtime capped as per prompt.
* **Metrics (primary):** Worst-scenario P1_SLA (estimated via bootstrap), p90_delay, max_util. Secondary: handover/setup minutes, preemption rate, P3 wait. Power: to detect 10pp P1_SLA difference needs ~150 P1 cases (binomial); at 10-15% P1 rate, ~1000-1500 total cases  4 weeks.
* **Process-mining checks during pilot:** Weekly `pm4py.discover_handover_of_work_network` to detect handover surge; `pm4py.get_service_time` by resource to detect speed degradation; waiting time by skill family to detect bottleneck migration to Validation. Drift detection via control chart on arrival mix and tail rate.

**3. Validation of assumptions:**
Measure actual handover/setup (timestamp gap when resource changes), coordination time for parallel vs sequential, and preemption penalty (compare interrupted vs uninterrupted service). Refine 7/5/8 constants. Track `planned_service` vs `actual_service` to audit SERPT gaming.

**Go/no-go for wider rollout:** Adopt Hybrid as default if pilot shows `max_util(base) <=90%`, P1_SLA >=90% in shadow base weeks, and worst-week P1_SLA within 5pp of simulation C bounds, with explainable dispatch logs. If POOL mean advantage >15% with no fairness/SLA cost, consider POOL for afternoon burn-down only.
