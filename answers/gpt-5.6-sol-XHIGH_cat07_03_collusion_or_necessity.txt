# 4. Network and conformance analyses

The analysis should be performed twice: first using recorded `org:resource`, and again using a **resolved actor identity** constructed from native authentication records, `entered_by`, `approved_by`, service-account IDs, and delegation data. Bots and shared accounts should be reported separately rather than silently removed.

In current PM4Py interfaces, `positive=False` is intended to retain cases that do not satisfy the principle. This should be verified against a small known test trace and independently cross-checked:

```python
def same_actor_case_ids(frame, activity_1, activity_2, resource=RES):
    left = (
        frame.loc[frame[ACT].eq(activity_1), [CASE, resource]]
        .dropna()
        .drop_duplicates()
    )
    right = (
        frame.loc[frame[ACT].eq(activity_2), [CASE, resource]]
        .dropna()
        .drop_duplicates()
    )
    return set(left.merge(right, on=[CASE, resource], how="inner")[CASE])

po_ids_check = same_actor_case_ids(
    human_view, "Create Purchase Order", "Approve Purchase Order"
)
bank_ids_check = same_actor_case_ids(
    human_view, "Change Vendor Bank Details", "Payment Approval"
)
```

This check should be repeated using `actor_resolved`. Cases with Bot_PO or shared Gita mappings should not be labeled genuine human four-eyes violations until the underlying identity is confirmed.

The reference must be independently verified; otherwise discovery may learn existing noncompliance as normal. Basic Declare and log-skeleton checks do not by themselves enforce “different human” or “within three working days.” Add a resource and calendar check:

```python
HOLIDAYS = corporate_holiday_dates
three_business_days = 3 * pd.offsets.CustomBusinessDay(holidays=HOLIDAYS)

results = []

for case_id, events in emergency.sort_values(TS).groupby(CASE):
    overrides = events[events[ACT].eq("Emergency Override")]
    retros = events[events[ACT].eq("Retrospective Justification")]

    for _, override in overrides.iterrows():
        candidates = retros[retros[TS].ge(override[TS])].sort_values(TS)
        retrospective = None if candidates.empty else candidates.iloc[0]

        deadline_day = override[TS].normalize() + three_business_days
        deadline = deadline_day + pd.Timedelta(days=1) - pd.Timedelta(nanoseconds=1)

        results.append({
            CASE: case_id,
            "override_timestamp": override[TS],
            "retrospective_timestamp": None if retrospective is None else retrospective[TS],
            "missing": retrospective is None,
            "late": retrospective is not None and retrospective[TS] > deadline,
            "same_actual_human": (
                retrospective is not None and
                override["actor_resolved"] == retrospective["actor_resolved"]
            )
        })

retrospective_control_results = pd.DataFrame(results)
```

The exact deadline convention should follow policy, including time zone, holidays, and whether the third working day ends at close of business.

# 6. Cautious audit-report wording

Review of the last-quarter procurement-to-payment event log identified several control exceptions, but it does not provide sufficient evidence to conclude that collusion, fraud, or intentional misconduct occurred. Stable Aline/Elena and Boris/Felix pairings are proportionate to high workloads and routine team routing; they should not be characterized as suspicious solely because they recur. The rapid Carla/Gita and Dan/Hugo paths are substantially associated with emergency medical supplies and weekend repairs, making emergency handling and informal specialization plausible. Nevertheless, documented four-eyes exceptions, late justifications, and any non-emergency outliers require control follow-up.

The most concerning subgroup is VendorMaster_Lena/AP_Kim activity involving vendor family V-77x, particularly high-amount cases using `manual_upload`, the reported bank-change/payment-approval violations, and the 16 short-lag cases. This combination raises control risk, not a finding of misconduct. The recent banking-platform migration and missing case-to-maintenance-ticket links are credible alternative explanations that should be tested transaction by transaction.

We recommend reconciling event identities before substantive conclusions: compare `org:resource` with `entered_by`, `approved_by`, native authentication logs, and delegation records; correct `legacy_erp` bot/human mappings; and recover original timestamps and authors for quarter-close spreadsheet entries. Review all V-77x violation and fast-path cases against migration tickets, independent vendor bank confirmations, change histories, invoices, and payment-release records. Separately, validate the 42 PO exceptions and 17 retrospective-justification exceptions, prioritizing non-emergency, high-value, late, and non-migrated records. Sample the remaining emergency cases for incident evidence, pre-approval review, and timely independent justification. Until completed, the appropriate conclusion is a mixed pattern dominated by specialization, emergency processing, and material data-quality limitations, with a narrower unresolved high-risk cluster requiring targeted investigation.
