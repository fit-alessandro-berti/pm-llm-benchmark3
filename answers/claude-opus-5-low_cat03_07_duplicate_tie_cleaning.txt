## 1. Duplicate-handling decision tree

The tree is evaluated per *candidate group*. A candidate group is the set of events sharing the same harmonized activity label and the same second-level timestamp, plus at least one shared object. Grouping is a *recall* device only: membership in a group is never itself evidence of duplication.

```
For each candidate group G:

Q1. Do two events share (source, source_event_key)?
    YES -> EXACT TECHNICAL DUPLICATE (re-ingestion artifact)
           => DROP the later-ingested copy, keep the earliest ingested row as canonical,
              record dropped source_event_key in provenance. No attribute loss possible.
    NO  -> Q2

Q2. Do they come from DIFFERENT source systems?
    NO (same source, different keys) -> Q3
    YES -> Q4

Q3. Same source, distinct keys, same label, same timestamp.
    Q3a. Do they bind to different object identities of the SAME type
         (e.g. I1 vs I2, M1 vs M2)?
         YES -> CONCURRENT SAME-LABEL EVENTS ON DIFFERENT OBJECTS
                => RETAIN BOTH UNCHANGED. Never merge. Order them only by
                   within-source sequence, and mark as concurrent for analysis.
         NO  -> Q3b
    Q3b. Is there an external reconciliation fact stating identity?
         YES -> treat as exact technical duplicate (drop later source_seq).
         NO  -> UNRESOLVED CANDIDATE => QUARANTINE.

Q4. Cross-system pair. Is there an explicit external reconciliation artifact
    (reconciliation report, shared business key, message correlation id)
    asserting they are the SAME physical occurrence?
    YES -> Q5
    NO  -> Q6

Q5. SAME PHYSICAL EVENT OBSERVED BY MULTIPLE SYSTEMS.
    Q5a. Are the E2O relation sets compatible (one a subset/refinement of the other,
         no contradictory object of the same type)?
         YES => MERGE ATTRIBUTES AND RELATIONS into one canonical event; keep the
                source-authoritative attribute per field; keep both source ids.
         NO  => QUARANTINE (contradictory object binding is a modeling bug, not a merge).

Q6. Is one event a system-generated *status/summary* update triggered by the other
    (message-driven, coarser object binding, later ingestion, coarser payload)?
    YES -> SUMMARY EVENT DERIVED FROM A DETAILED EVENT.
           Default => RETAIN BOTH WITH REFINED LABELS (e.g. `... (ERP status update)`)
                      and an `abstraction_level` attribute; link via `derived_from`.
           Optional aggressive variant => DROP the summary (documented, reversible).
    NO  -> Q7

Q7. Did harmonization map two *different* source activities onto one label
     (source-local semantics differ: "released from warehouse" vs "accepted by carrier")?
     YES -> HARMONIZATION COLLISION.
            => RETAIN BOTH WITH REFINED LABELS (restore source semantics as
               distinct activities or as a qualifier attribute). Never merge.
     NO  -> UNRESOLVED CANDIDATE => QUARANTINE for review; keep both events
            unchanged in the analysis dataset, flagged.
```

Terminal actions used: **drop** (Q1, Q3b-yes), **merge attributes and relations** (Q5a-yes), **retain both with refined labels/qualifiers** (Q6, Q7), **retain both unchanged** (Q3a), **quarantine** (Q3b-no, Q5a-no, Q7-no).

## 3. Timestamp-tie ordering rules

Ordering is done in two stages. **Stage 1** builds a *partial order* from evidence. **Stage 2** linearizes it deterministically. Only Stage 1 carries meaning.

Rule precedence (highest first):

1. **R1 — Domain constraints (semantic).** Hard business facts: `Authorize Payment` ≺ `Capture Payment` for the same Payment object; `Carrier Acceptance` ≺ `Handover to Carrier`; detailed event ≺ derived summary; `Release from Warehouse` ≺ `Carrier Acceptance`; `Pick` ≺ `Pack` for the same package.
2. **R2 — Within-source sequence (semantic, scoped).** If two events share a source, `source_seq` orders them. Valid only inside one source system; never comparable across sources.
3. **R3 — Lifecycle constraints on shared objects (semantic).** Per object, the event sequence must respect its lifecycle (Package: picked → packed → dispatched → delivered; Invoice: issued → paid). This orders events across sources when they touch the same object.
4. **R4 — Source-specific semantics (semantic, weaker).** Systems of record for a transition are usually *earlier* than downstream status consumers (WMS before ERP status; PSP before ERP posting). This is a heuristic prior, defensible but not a hard fact.
5. **R5 — Ingestion time (deterministic only).** `ingested_at` is used **only** as a tiebreaker after R1–R4, and only when no semantic rule applies. Fact 9 says it may contradict business order, so it must never override R1–R4.
6. **R6 — Stable fallback (deterministic only).** Lexicographic `(source, source_event_key, eid)`. Guarantees reproducibility across runs, machines, and pandas versions. Carries zero meaning.

R1–R4 are semantic; R5–R6 are merely deterministic and must be flagged as such in the output dataset (`order_rule_applied` column), so a reader can tell an evidence-backed edge from a coin flip.

**Why microseconds must come last.** If you first spray `+1µs, +2µs, …` over tied events (by row order, by ingestion time, or by pandas' arbitrary sort) and *then* reason about semantics, the artificial timestamps become the input to every downstream algorithm: directly-follows extraction, OC-DFG edges, sojourn times, conformance alignment. The tie-breaking has silently *asserted* an order — and any later semantic analysis is now reading its own noise back as evidence. Concretely, if e07 (ERP summary) received a smaller microsecond offset than e06 (WMS detail) because ERP ingested first in a replay, the log would claim ERP confirmed packing before the warehouse packed it. The rule is: decide the partial order semantically, then materialize the tie-break, and always keep `original_timestamp` untouched (fact 10). A deterministic total order is a *presentation* of a partial order, never proof of the physical order.

**Intended orders.**

*10:00 block (after e03/e04 merge, conservative labels).* Constraints: picks precede packing (R1/R3 on P1); WMS detail precedes ERP status (R1/R4). Picks of I1 and I2 are genuinely concurrent.
- Admissible order A: `e03⊕e04 (Pick I1), e05 (Pick I2), e06 (Pack, WMS), e07 (Pack Confirmed, ERP)`
- Admissible order B: `e05, e03⊕e04, e06, e07` — equally valid; the I1/I2 pick order is unknown.
Within-source `source_seq` (S-901=551 < S-902=552) is a weak tiebreaker that favours A; it is scanner-local and does not prove physical order. The pick pair should be recorded as concurrent, and if only one total order is emitted, the choice must be labelled R2/R6, not semantic.

*10:15 block.* Fully ordered by evidence: `e08 (Release from Warehouse) → e09 (Carrier Acceptance) → e10 (Handover to Carrier)`. R1 gives e08 ≺ e09 (custody), R2 gives e09 ≺ e10 (carrier `source_seq` 1 < 2) and fact 5 confirms it semantically. No fallback needed.

*12:00 block (after e11/e16 merge).* Surviving events: e11⊕e16 (Issue Invoice), e12 (Authorize M1), e13 (Capture M1), e14 (Capture M2), e15 (Payment Posted, ERP summary).
- Order: `e11⊕e16 → e12 → e13 → e14 → e15`.
- Justification: invoice before payment (R3 on V1); e12 ≺ e13 by fact 7 and PSP `source_seq`; e13 ≺ e14 by PSP `source_seq` 401 < 402 (R2, deterministic-semantic within PSP, weak as a claim about M1 vs M2 real-world timing); e15 last by R1 (summary after its sources) and R4/R5 corroboration (ERP ingested at 12:01:00).
- Alternative admissible order: `… e14 → e13 → e15` if the two partial payments are considered concurrent; M1 and M2 are independent Payment objects, so only PSP's within-source sequence separates them.

## 4. Conservative cleaning pipeline

Minimum-change scenario, applied in this order:

1. **Exact technical duplicates.** Scan for repeated `(source, source_event_key)` and repeated `(source, activity, timestamp, payload_hash)`. In this dataset there are **none** — no two rows share a source key or a payload hash. `ocel_drop_duplicates` is therefore safe here *only because the pre-check proved the group is empty*; it is run as a guard, not as a cleaning step.
2. **Verified cross-system pairs only.** Merge e03+e04 and e11+e16 — the only two pairs backed by an explicit external reconciliation artifact (facts 1 and 6). Merge = union of E2O relations (both no-ops here), field-level authority for attributes, both source keys retained.
3. **Refine harmonization collisions.** e08 → `Release from Warehouse`, e09 → `Carrier Acceptance`. `original_activity = "Dispatch Package"` stored on both.
4. **Refine abstraction levels rather than deleting them.** e07 → `Pack Package Confirmed (ERP)`, e15 → `Payment Posted (ERP summary)`, each with `abstraction_level="summary"` and `derived_from`. This is the key move that prevents false rework without discarding data.
5. **Leave concurrency intact.** e03/e05 and e13/e14 untouched; no merge, no relabel.
6. **Order.** Build the partial order from R1–R4, linearize with R5 then R6, write `order_rank`, then apply an index-based timedelta to produce `tiebreak_timestamp`. `original_timestamp` is preserved verbatim on every event.
7. **Quarantine.** Nothing lands in quarantine here, because e06/e07 and e13/e15 are resolved by relabelling rather than by a merge decision — the conservative pipeline defers the abstraction question to the analyst instead of quarantining rows out of the dataset.

**Expected retained event count: 15** (17 raw − e04 merged into e03 − e16 merged into e11). E2O relations: raw has 3+3+3+4+2+3+3+3+2+3+3+2+3+3 … the merges are relation-set no-ops, so the E2O count drops exactly by the relations of the two absorbed events (3 for e04, 2 for e16) with no object losing all its links. Every object O1, I1, I2, P1, D1, V1, M1, M2 remains referenced.

## 5. Aggressive alternatives

**Scenario B — Evidence-based semantic merging.** On top of the conservative result, additionally collapse the two abstraction pairs where a *documented* generation relationship exists: merge e07 into e06, and drop e15 as a derived posting summary (its only unique content, the invoice-level balance, is copied onto e11⊕e16 as an attribute `balance_posted_at`). e08/e09 stay split, e13/e14 stay split.
- **Retained events: 13.** E2O relations fall by e07's 2 and e15's 2.
- **Most likely semantic damage:** the ERP-vs-source latency signal disappears (WMS→ERP packing confirmation lag, PSP→ERP posting lag), so any "time to system-of-record update" KPI becomes unmeasurable. If e07 was in fact triggered by a *different* packing transaction, a real event is lost.

**Scenario C — Mechanically aggressive PM4Py merging.** Apply `ocel_merge_duplicates` (optionally with `have_common_object=True`) to the whole OCEL without candidate-group inspection.
- **Retained events: ~10–11.** All `Pick Item` at 10:00 collapse to one (e03, e04, e05 → 1), both `Pack Package` collapse (e06, e07 → 1), both `Dispatch Package` collapse (e08, e09 → 1), both `Issue Invoice` collapse (e11, e16 → 1), and all three `Capture Payment` collapse (e13, e14, e15 → 1). Survivors: Create, Validate, Pick, Pack, Dispatch, Handover, Issue Invoice, Authorize, Capture, Confirm Delivery ≈ 10.
- **Most likely semantic damage:** this violates two explicit constraints — e05 and e14 are destroyed. The log now claims one pick, one dispatch, one capture; the second item, the warehouse-release/carrier-acceptance custody transfer, and the second partial payment vanish. Relation unioning silently attaches I1+I2 to a single Pick and M1+M2 to a single Capture, producing an event whose object binding corresponds to no real transaction.

**Why `have_common_object=True` does not protect e13 and e14.** The flag only requires that merge candidates share *at least one* object. e13 and e14 share O1 **and** V1 — both are true, so the guard passes — yet they differ on the only object type that distinguishes them: Payment (M1 vs M2). Shared objects are the *norm* in an OCEL, because a case-like object (the Order) and a document object (the Invoice) are attached to nearly every event in the process. Any guard built on object *overlap* is therefore nearly always satisfied and carries almost no discriminative power. The correct guard is object-type-aware and *conflict-based*: refuse to merge two events if there exists an object type on which they bind **different** identities (Payment: M1 ≠ M2; Item: I1 ≠ I2). That guard blocks e13/e14 and e03/e05 correctly, while still permitting e03/e04 and e11/e16 whose bindings are identical. `have_common_object=True` and the conflict guard point in opposite directions here, which is exactly why the library flag must not be treated as a safety feature.

## 6. PM4Py-oriented Python implementation

```python
import copy
import pandas as pd
import pm4py

# --------------------------------------------------------------------------
# 0. Never touch ocel_raw. Every scenario works on a deep copy.
# --------------------------------------------------------------------------
EV, OBJ = "ocel:eid", "ocel:oid"          # adapt to your pm4py column constants
ACT, TS = "ocel:activity", "ocel:timestamp"

def snapshot(ocel):
    """Deep copy + freeze the raw view on every event (idempotent)."""
    o = copy.deepcopy(ocel)
    ev = o.events
    for col, src in [("original_timestamp", TS), ("original_activity", ACT)]:
        if col not in ev.columns:
            ev[col] = ev[src]
    for col in ("source", "source_event_key", "source_seq", "ingested_at", "payload_hash"):
        if col not in ev.columns:
            raise ValueError(f"missing provenance column: {col}")
    if "canonical_sources" not in ev.columns:
        ev["canonical_sources"] = ev.apply(
            lambda r: [f"{r['source']}:{r['source_event_key']}"], axis=1)
    o.events = ev
    return o

# --------------------------------------------------------------------------
# 1. PRE-CHECK: candidate duplicate groups. Inspect before any drop/merge.
# --------------------------------------------------------------------------
def candidate_groups(ocel):
    ev, rel = ocel.events, ocel.relations
    objs = rel.groupby(EV)[OBJ].apply(lambda s: frozenset(s)).rename("objset")
    df = ev.merge(objs, left_on=EV, right_index=True, how="left")
    df["objset"] = df["objset"].fillna(frozenset())
    report = []
    for (a, t), g in df.groupby([ACT, TS]):
        if len(g) < 2:
            continue
        report.append({
            "activity": a, "timestamp": t, "n": len(g),
            "eids": list(g[EV]),
            "sources": sorted(set(g["source"])),
            "exact_key_dupes": g.duplicated(["source", "source_event_key"]).sum(),
            "payload_hash_dupes": g.duplicated(["source", "payload_hash"]).sum(),
            "identical_objsets": g["objset"].nunique() == 1,
            "conflicting_objsets": g["objset"].nunique() > 1,
        })
    return pd.DataFrame(report)

print(candidate_groups(ocel_raw))   # <-- READ THIS before running anything below

# --------------------------------------------------------------------------
# 2. Helpers: object-type-aware conflict guard + verified-pair merge
# --------------------------------------------------------------------------
def objects_by_type(ocel, eid, otype_col="ocel:type"):
    rel = ocel.relations
    sub = rel[rel[EV] == eid]
    if otype_col in sub.columns:
        return sub.groupby(otype_col)[OBJ].apply(set).to_dict()
    return {"_untyped": set(sub[OBJ])}

def has_object_conflict(ocel, e_a, e_b):
    """True if some object TYPE binds different identities -> must not merge."""
    a, b = objects_by_type(ocel, e_a), objects_by_type(ocel, e_b)
    for t in set(a) & set(b):
        if a[t] != b[t] and not (a[t] <= b[t] or b[t] <= a[t]):
            return True
    return False

# Field-level authority: which source wins per attribute on a merge.
AUTHORITY = {
    "location": "WMS", "picker": "WMS",
    "scan_device": "SCANNER", "scan_seq": "SCANNER",
    "invoice_document_id": "BILLING", "tax_lines": "BILLING",
    "ar_account": "ERP", "order_status": "ERP",
}

def merge_verified_pair(ocel, keep_eid, absorb_eid, rule, confidence, reason,
                        audit, force=False):
    """
    Merge absorb_eid into keep_eid:
      - refuses if an object-type conflict exists (unless force=True);
      - unions E2O relations onto keep_eid, then removes absorb_eid rows;
      - resolves attribute conflicts by AUTHORITY, logs the losers;
      - appends one provenance record to `audit`.
    """
    if has_object_conflict(ocel, keep_eid, absorb_eid) and not force:
        raise ValueError(f"object-type conflict: refuse merge {keep_eid}<-{absorb_eid}")

    ev, rel = ocel.events, ocel.relations
    k = ev.index[ev[EV] == keep_eid][0]
    a = ev.index[ev[EV] == absorb_eid][0]
    keep_src, absorb_src = ev.at[k, "source"], ev.at[a, "source"]

    discarded = {}
    for col in ev.columns:
        if col in (EV, ACT, TS, "original_timestamp", "original_activity",
                   "source", "source_event_key", "canonical_sources"):
            continue
        kv, av = ev.at[k, col], ev.at[a, col]
        if pd.isna(kv) and not pd.isna(av):
            ev.at[k, col] = av                      # fill gap
        elif not pd.isna(av) and kv != av:
            winner = AUTHORITY.get(col)
            if winner == absorb_src:
                discarded[col] = {"kept": av, "dropped": kv, "authority": winner}
                ev.at[k, col] = av
            else:
                discarded[col] = {"kept": kv, "dropped": av,
                                  "authority": winner or keep_src}

    ev.at[k, "canonical_sources"] = list(ev.at[k, "canonical_sources"]) + \
                                    list(ev.at[a, "canonical_sources"])

    # union relations, drop absorbed event
    moved = rel[rel[EV] == absorb_eid].copy()
    moved[EV] = keep_eid
    rel = pd.concat([rel, moved], ignore_index=True)
    rel = rel.drop_duplicates(subset=[EV, OBJ])
    rel = rel[rel[EV] != absorb_eid] if False else rel   # absorbed rows already retargeted
    ocel.relations = rel
    ocel.events = ev.drop(index=a).reset_index(drop=True)

    audit.append({"canonical_eid": keep_eid, "absorbed_eid": absorb_eid,
                  "source_event_ids": ev.at[k, "canonical_sources"],
                  "merge_rule": rule, "rule_version": "clean-v1.3",
                  "reviewer": "reconciliation-report-2026-05-20",
                  "confidence": confidence, "reason": reason,
                  "discarded_conflicts": discarded})
    return ocel

def relabel(ocel, eid, new_activity, level, derived_from=None):
    ev = ocel.events
    i = ev.index[ev[EV] == eid][0]
    ev.at[i, ACT] = new_activity                  # original_activity already frozen
    ev.at[i, "abstraction_level"] = level
    if derived_from is not None:
        ev.at[i, "derived_from"] = ",".join(derived_from)
    # keep relations table label column in sync if present
    if ACT in ocel.relations.columns:
        ocel.relations.loc[ocel.relations[EV] == eid, ACT] = new_activity
    return ocel

# --------------------------------------------------------------------------
# 3. Deterministic ordering: semantic partial order first, tiebreak last
# --------------------------------------------------------------------------
DOMAIN_RANK = {                     # R1: intra-timestamp semantic precedence
    "Pick Item": 10, "Pack Package": 20, "Pack Package Confirmed (ERP)": 21,
    "Release from Warehouse": 30, "Carrier Acceptance": 31,
    "Handover to Carrier": 32,
    "Issue Invoice": 40, "Authorize Payment": 41, "Capture Payment": 42,
    "Payment Posted (ERP summary)": 43,
}
SOURCE_RANK = {"WMS": 0, "SCANNER": 0, "PSP": 0, "CARRIER": 1, "BILLING": 1, "ERP": 2}

def build_order_key(ocel):
    ev = ocel.events.copy()
    ev["r1_domain"] = ev[ACT].map(DOMAIN_RANK).fillna(99).astype(int)
    ev["r2_seq"] = ev["source_seq"].astype(int)          # meaningful within source only
    ev["r4_source"] = ev["source"].map(SOURCE_RANK).fillna(9).astype(int)
    ev["r5_ingested"] = pd.to_datetime(ev["ingested_at"])
    ev["r6_stable"] = ev["source"].astype(str) + "|" + ev["source_event_key"].astype(str)
    ev = ev.sort_values(
        by=[TS, "r1_domain", "r4_source", "r2_seq", "r5_ingested", "r6_stable"],
        kind="mergesort").reset_index(drop=True)
    ev["order_rank"] = range(len(ev))
    ev["order_rule_applied"] = "R1>R4>R2 semantic; R5/R6 deterministic-only"
    ocel.events = ev
    return ocel

# --------------------------------------------------------------------------
# 4. Referential integrity validation
# --------------------------------------------------------------------------
def validate(ocel, label):
    ev, rel = ocel.events, ocel.relations
    eids, reids = set(ev[EV]), set(rel[EV])
    problems = []
    if reids - eids:
        problems.append(f"dangling E2O rows for events {sorted(reids - eids)}")
    if ev[EV].duplicated().any():
        problems.append("duplicate canonical eids")
    if hasattr(ocel, "objects"):
        oids = set(ocel.objects[OBJ])
        if set(rel[OBJ]) - oids:
            problems.append(f"unknown objects {sorted(set(rel[OBJ]) - oids)}")
        orphan = oids - set(rel[OBJ])
        if orphan:
            problems.append(f"objects lost all E2O links: {sorted(orphan)}")
    if ev["original_timestamp"].isna().any():
        problems.append("original_timestamp erased")
    print(f"[{label}] events={len(ev)} rel={len(rel)} "
          f"problems={problems or 'none'}")
    return not problems

# ==========================================================================
# SCENARIO 1 — CONSERVATIVE
# ==========================================================================
audit_cons = []
ocel_cons = snapshot(ocel_raw)

# 1a. Exact technical duplicates only. Pre-check first!
cg = candidate_groups(ocel_cons)
exact = int(cg["exact_key_dupes"].sum() + cg["payload_hash_dupes"].sum()) if len(cg) else 0
if exact > 0:
    # Justified: identical (activity, timestamp, object set) re-ingestion rows.
    ocel_cons = pm4py.ocel_drop_duplicates(ocel_cons)
else:
    print("ocel_drop_duplicates skipped: pre-check found 0 exact technical duplicates")

# 1b. Verified cross-system pairs (reconciliation report).
ocel_cons = merge_verified_pair(ocel_cons, "e03", "e04",
    rule="verified_same_physical_event", confidence="high",
    reason="reconciliation report; WMS enriched with location", audit=audit_cons)
ocel_cons = merge_verified_pair(ocel_cons, "e11", "e16",
    rule="verified_same_invoice_issuance", confidence="high",
    reason="same invoice number V1; per-field source authority", audit=audit_cons)

# 1c. Undo harmonization collisions; mark abstraction levels.
ocel_cons = relabel(ocel_cons, "e08", "Release from Warehouse", "detail")
ocel_cons = relabel(ocel_cons, "e09", "Carrier Acceptance", "detail")
ocel_cons = relabel(ocel_cons, "e07", "Pack Package Confirmed (ERP)", "summary", ["e06"])
ocel_cons = relabel(ocel_cons, "e15", "Payment Posted (ERP summary)", "summary",
                    ["e13", "e14"])
# e05 and e14 are deliberately untouched.

# 1d. Order, THEN materialize the tie-break.
ocel_cons = build_order_key(ocel_cons)
ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, "order_rank")
ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons)   # only after ordering
validate(ocel_cons, "conservative")

# ==========================================================================
# SCENARIO 2 — EVIDENCE-BASED SEMANTIC MERGE (documented derivations only)
# ==========================================================================
audit_evid = list(audit_cons)
ocel_evid = copy.deepcopy(ocel_cons)
ocel_evid = merge_verified_pair(ocel_evid, "e06", "e07",
    rule="summary_absorbed_into_detail", confidence="medium",
    reason="ERP status update generated from WMS message", audit=audit_evid)
ocel_evid = merge_verified_pair(ocel_evid, "e11", "e15",
    rule="posting_summary_absorbed_into_invoice", confidence="medium",
    reason="ERP invoice-level balance update; no Payment object", audit=audit_evid)
ocel_evid = build_order_key(ocel_evid)
ocel_evid = pm4py.ocel_sort_by_additional_column(ocel_evid, "order_rank")
ocel_evid = pm4py.ocel_add_index_based_timedelta(ocel_evid)
validate(ocel_evid, "evidence-based")

# ==========================================================================
# SCENARIO 3 — MECHANICALLY AGGRESSIVE (baseline for damage measurement ONLY)
# ==========================================================================
# WARNING: pm4py.ocel_merge_duplicates collapses events sharing activity and
# timestamp. On this log it DESTROYS e05 (distinct pick of I2) and e14 (distinct
# partial payment M2), violates the stated constraints, and unions incompatible
# E2O relations (I1+I2 onto one Pick, M1+M2 onto one Capture).
# `have_common_object=True` does NOT protect e13/e14: they share O1 and V1.
# Produce this dataset only to quantify how much interpretation the merge changes.
ocel_aggr = snapshot(ocel_raw)
ocel_aggr = pm4py.ocel_merge_duplicates(ocel_aggr)   # optionally have_common_object=True
ocel_aggr = build_order_key(ocel_aggr)
ocel_aggr = pm4py.ocel_sort_by_additional_column(ocel_aggr, "order_rank")
ocel_aggr = pm4py.ocel_add_index_based_timedelta(ocel_aggr)
validate(ocel_aggr, "aggressive-library")

pd.DataFrame(audit_evid).to_json("provenance_audit.json", orient="records", indent=2)
```

## 7. Sensitivity analysis

| Dimension | Raw (17 ev) | Conservative (15 ev) | Evidence-based (13 ev) | Aggressive library (~10 ev) |
|---|---|---|---|---|
| Events / E2O | 17 events, full relation set | −2 events; E2O drops by the absorbed duplicates only, no object orphaned | −4 events; ERP summary relations gone | −7 events; relations unioned onto merged rows, several E2O rows collapse and object-type bindings become mixed |
| Order-flattened DFG | Two `Pick Item→Pick Item`, `Pack→Pack`, `Dispatch→Dispatch`, `Issue Invoice→Issue Invoice`, `Capture→Capture` self-loops — all artifacts | Self-loops on Pack/Dispatch/Invoice/Capture removed by merge or relabel; only the genuine `Pick Item→Pick Item` (I1 then I2) remains | Also loses the detail→summary edges; the chain becomes a clean linear backbone | One `Pick`, one `Capture`; the log looks like a single-item, single-payment order |
| Item-flattened DFG | I1: Pick(×2)→Pack; I2: Pick→Pack | I1: Pick→Pack (single); I2 unchanged — the duplicate scan artifact disappears | Same | I1 and I2 share one merged Pick event, so per-item traces become indistinguishable and the item-level fan-out is lost |
| Payment-flattened DFG | M1: Authorize→Capture; M2: Capture only | Unchanged (correct) | Unchanged | M1 and M2 collapse; M2 loses its Capture entirely, so its flattened trace is empty or spuriously attached |
| OC-DFG edges / frequencies | Inflated frequency on duplicated labels | Frequencies match business occurrences; edge count slightly lower | Fewer nodes, higher edge concentration on the WMS/PSP backbone | Edge set structurally different; `Pick→Pack` frequency halves, `Capture` node frequency drops from 3 to 1 |
| ET–OT weights | `Pick Item`–Item weight 3, `Capture Payment`–Payment weight 2, plus `Capture Payment`–Invoice from e15 | `Pick Item`–Item weight 2 (correct); `Payment Posted`–Invoice separated from `Capture Payment`–Payment | ERP summary contributions to ET–OT vanish | `Capture Payment`–Payment weight becomes 2 on a *single* event, falsely suggesting one capture covers two payments |
| OTG relations | Item–Package, Package–Delivery, Invoice–Payment all present | Same, with cleaner support counts | Invoice–Payment edge weakens because e15 no longer links the posting to V1 as an activity | Payment–Payment interaction and the M1/M2 distinction disappear; OTG becomes misleadingly simple |
| Apparent rework / loops | Heavy false rework: three `Capture Payment`, two `Issue Invoice`, two `Pack`, two `Dispatch` | Rework eliminated where it was an artifact; true concurrency (two picks) preserved and marked as concurrent, not as a loop | Rework fully gone; risk of *understating* real retries if any exist | Zero rework by construction — a rework-detection study on this dataset would report a false negative |
| Lifecycle / performance | Zero-duration steps everywhere at 10:00, 10:15, 12:00 | Same original timestamps; `tiebreak_timestamp` gives an ordered but explicitly synthetic microsecond spacing, flagged as non-measurable | Same, fewer steps | Durations computed on merged events are meaningless; the WMS→ERP and PSP→ERP latencies are unrecoverable |

**Six concrete interpretation changes:**
1. `Pick Item → Pick Item` (Order-flattened): 2 occurrences raw → 1 conservative → 0 aggressive. Raw reads as a re-scan; conservative reads as two-item picking; aggressive reads as a one-item order.
2. `Dispatch Package → Dispatch Package`: an artifact edge in raw that becomes the semantically real `Release from Warehouse → Carrier Acceptance` edge under conservative cleaning — and vanishes entirely under aggressive merging, deleting the custody-transfer measurement.
3. `Capture Payment → Capture Payment`: raw suggests a retried capture; conservative shows two concurrent partial payments on M1 and M2; aggressive shows a single capture, destroying the split-payment pattern.
4. `Capture Payment → Payment Posted (ERP summary)`: exists only after conservative relabelling; it is the ERP posting-lag edge and is invisible in both raw (mislabelled as a third capture) and evidence-based/aggressive (merged away).
5. `Pack Package → Pack Package Confirmed (ERP)`: the WMS→ERP confirmation latency edge. Present only in conservative.
6. `Issue Invoice → Issue Invoice`: raw suggests double invoicing (a control-failure signal); the merge removes it — correct if the reconciliation is right, but it also removes the only trace of a potential duplicate-billing incident, which is why the merge must be reversible.
7. ET–OT `Capture Payment`–Payment: weight 2 across 2 events (correct) versus weight 2 on 1 event (aggressive), which changes every object-per-event-type statistic.

## 8. Audit trail and reversibility

Every non-identity transformation writes one record to a side table `provenance_audit`:

```
canonical_event_id        e03
source_event_ids          ["WMS:W-77", "SCANNER:S-901"]
source_eids               ["e03", "e04"]
merge_rule                verified_same_physical_event
rule_version              clean-v1.3
reviewer                  reconciliation-report-2026-05-20 / analyst_id
original_activity         {"e03": "Pick Item", "e04": "Pick Item"}
refined_activity          "Pick Item"
original_timestamp        {"e03": "2026-05-18T10:00:00Z", "e04": "2026-05-18T10:00:00Z"}
adjusted_timestamp        "2026-05-18T10:00:00.000001Z"   (tiebreak only)
order_rank                3
order_rule_applied        "R1 domain > R4 source; R2 within-source; R6 stable fallback"
attributes_from_source    {"location": "WMS", "scan_device": "SCANNER", "picker": "WMS"}
discarded_conflicts       {"resource": {"kept": "wms_user_7", "dropped": "scanner_op_2",
                                        "authority": "WMS"}}
relations_before          {"e03": ["O1","I1","P1"], "e04": ["O1","I1","P1"]}
relations_after           ["O1","I1","P1"]
confidence                high
reason                    "reconciliation report; payload differs only by WMS enrichment"
action                    merge | drop | relabel | retain | quarantine
```

Relabelling and ordering write the same record shape with `action=relabel`/`retain` and empty merge fields. Quarantined groups are written to a `quarantine` table with the same schema plus the unresolved question.

**Reconstructing the raw view.** Three properties make this possible: (i) no source row is ever deleted from the archive — `ocel_raw` is never mutated in place and is stored immutably alongside the cleaned dataset; (ii) every canonical event carries `canonical_sources`, `original_activity`, and `original_timestamp`; (iii) the audit table records `relations_before` for each merge. An analyst therefore reverses the pipeline by: replaying the audit records in reverse `rule_version` order, splitting each canonical event back into its `source_eids`, restoring each split event's `original_activity` and `original_timestamp`, restoring `relations_before`, and reinstating attributes from `discarded_conflicts`. Dropping the `tiebreak_timestamp` and `order_rank` columns returns the log to its original tie structure. Because merges are recorded as *absorptions* with the full pre-state, the reconstruction is lossless and can also be done selectively — e.g. undoing only the e06/e07 merge to re-measure the WMS→ERP lag without discarding the rest of the cleaning.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments (e13/e14).** Cause: merging on activity+timestamp, or trusting `have_common_object=True` when O1/V1 are shared. *Safeguard:* object-type-aware conflict guard — refuse any merge where two events bind different identities of the same object type (M1 ≠ M2). Post-check: assert every Payment object still has ≥1 E2O relation.
2. **Converting abstraction-level updates into false rework.** Cause: keeping e07 and e15 under harmonized labels. *Safeguard:* mandatory `abstraction_level` attribute and label refinement for any event flagged as message-generated; never let a summary share a label with its source event.
3. **Ordering by ingestion time.** Cause: using `ingested_at` as the sort key because it is conveniently unique. Fact 9 says it may contradict business order — e07 ingested at 10:01:00 but e06's business precedence comes from semantics, not ingestion. *Safeguard:* `ingested_at` is rule R5, only reachable after R1–R4 produce a tie, and its use is recorded in `order_rule_applied`.
4. **Treating shared objects as proof of duplication.** Cause: OCEL logs attach the Order to nearly every event, so overlap is ubiquitous. e08/e09/e10 share O1, P1, D1 and are three distinct transitions. *Safeguard:* require an *external* identity artifact (reconciliation report, shared business key) before any cross-system merge; object overlap alone never triggers one.
5. **Unioning incompatible E2O relations.** Cause: merge implementations that blindly union object sets, producing a Pick bound to both I1 and I2 or a Capture bound to M1 and M2. *Safeguard:* the conflict guard runs before the union; merges are permitted only when one relation set is identical to or a strict refinement of the other, and `relations_before` is logged.
6. **Changing durations through synthetic microseconds.** Cause: computing performance metrics on `tiebreak_timestamp`. *Safeguard:* keep `original_timestamp` as the only column any duration computation may read; mark `tiebreak_timestamp` with a column comment and exclude it from performance dashboards. A tie means "unmeasurable at this granularity", not "one microsecond apart".
7. **Losing source-authoritative attributes.** Cause: last-writer-wins merges that overwrite BILLING's invoice document id with an ERP null, or drop WMS's location. *Safeguard:* the explicit `AUTHORITY` field-level table, gap-filling for nulls, and `discarded_conflicts` logging of every value that lost.
8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups.** Cause: running `ocel_drop_duplicates`/`ocel_merge_duplicates` as a reflex preprocessing step. *Safeguard:* `candidate_groups()` must be executed and reviewed first; `ocel_drop_duplicates` is gated behind a check that exact `(source, source_event_key)` or `(source, payload_hash)` repeats actually exist, and `ocel_merge_duplicates` is confined to a clearly labelled damage-measurement scenario.
9. **Harmonization collisions left unrefined.** Cause: trusting the integration layer's label mapping. e09 originally meant "accepted by carrier"; the harmonized `Dispatch Package` invites a merge with e08. *Safeguard:* keep `original_activity` per source and audit any harmonized label that receives events from ≥2 sources with differing source-local semantics.
10. **Fabricating a total order and then reasoning from it.** Cause: linearizing before deciding, or reporting a single trace as *the* trace. *Safeguard:* record the partial order explicitly, expose `order_rule_applied` per event, present alternative admissible orders (e03/e05; e13/e14) to the analyst, and never state that a deterministic total order proves the physical sequence.
11. **Silent non-determinism across runs.** Cause: relying on pandas' default sort or dict iteration for ties. *Safeguard:* the stable fallback R6 on `(source, source_event_key, eid)` and `kind="mergesort"` guarantee byte-identical output for identical input.
12. **Losing the duplicate-billing control signal.** Cause: merging e11/e16 removes the only evidence that two systems both issued an invoice for V1. *Safeguard:* record the merge in the audit trail with `action=merge` and raise a control-check flag whenever two authoritative billing systems emit an issuance for the same invoice number, so the merge is analytically convenient but not evidentially destructive.
