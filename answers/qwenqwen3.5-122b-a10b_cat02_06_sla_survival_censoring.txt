# 1. SLA estimands and time definitions

**Time Origin ($t=0$):** Case creation timestamp corresponding to the `Submit` activity.
**Horizon ($\tau$):** 72 hours (SLA threshold).
**Observation Cutoff:** The frozen extract date determines the maximum observable time for open cases.

We define two distinct estimands to address operational ambiguity:

### Estimand 1: Internal Resolution Probability (Competing Risks)
$$ \text{CIF}_{\text{resolve}}(72) = P(T_{\text{resolve}} \le 72 \mid \text{No prior competing event}) $$
*   **Definition:** Probability that a case reaches `Resolve` within 72 hours, treating `Withdraw`, `Reject`, and `Transfer` as absorbing competing events that preclude internal resolution.
*   **Operational Decision:** Capacity planning for internal staff. If this probability is low, internal resources may be wasted on cases that will leave the system anyway.
*   **Case Contributions:**
    *   **Resolved @ 76h (e.g., S13):** Censored at 72 for the purpose of "Resolution by 72". Does not contribute to $\text{CIF}(72)$.
    *   **Open @ 92h (e.g., S09):** Censored at 72 (we know it was not resolved by 72). Does not contribute to $\text{CIF}(72)$.
    *   **Withdrawn @ 27h (e.g., S06):** Competing event. Prevents resolution contribution.
    *   **Transferred @ 68h (e.g., S08):** Competing event (under assumption 1 below). Prevents resolution contribution.

### Estimand 2: SLA Breach Probability (Survival Complement)
$$ \text{Risk}_{\text{breach}}(72) = 1 - S(72) $$
Where $S(t)$ is the Kaplan-Meier estimate of remaining "at risk" of violating the SLA. Here, "Event" = Resolution. "Failure" = Not Resolved by 72h (includes Open, Withdraw, Reject, Transfer).
*   **Definition:** Probability that a case is **not** marked `resolved` by 72 hours.
*   **Operational Decision:** Contractual compliance reporting. Any case not closed (resolved) by 72h is a breach of the service agreement, regardless of whether it was withdrawn or transferred.
*   **Case Contributions:**
    *   **Resolved @ 76h:** Event occurred after 72. Counts as Breach.
    *   **Open @ 92h:** Still open at 72. Counts as Breach.
    *   **Withdrawn @ 27h:** Not resolved by 72. Counts as Breach.
    *   **Transferred @ 68h:** Not resolved by 72. Counts as Breach.

### Assumptions
1.  **Censoring Mechanism:** `open` cases are right-censored at `duration_or_age_h`. We assume missingness is independent of future resolution given observed history (Non-informative Censoring).
2.  **Transfer Outcomes:** We assume `Transfer` removes the case from the internal observation window permanently.
3.  **Time Granularity:** `duration_or_age_h` is continuous; exact event times between activities are unknown, so we treat activity transitions as instantaneous or bundled into the duration.

# 3. Why naive completed-case analysis is biased

Analyzing only `resolved` cases (S01, S02, S03...) introduces severe biases:

1.  **Survivor Bias (Selection Bias):**
    *   *Example:* Comparing Cohort A vs B using only resolved cases ignores that Cohort B might have higher `transfer` rates. If Cohort B transfers difficult cases faster, their `resolved` average duration looks artificially low (e.g., S16 resolved in 16h), while Cohort A retains them longer (e.g., S03 resolved in 76h).
    *   *Impact:* False conclusion that Cohort B is faster, when it may just be filtering cases differently.

2.  **Informative Censoring (Transfers):**
    *   *Example:* S08 (`transferred` @ 68h) and S32 (`transferred` @ 96h). These cases were likely escalated (see `escalated`=yes). They represent high-complexity cases. Treating them as random censored observations assumes they would have behaved like S01.
    *   *Impact:* Standard Kaplan-Meier overestimates the probability of resolution because it assumes censored cases eventually resolve like the survivors.

3.  **Competing Risks (Withdraw/Reject):**
    *   *Example:* S05 (`rejected` @ 9h). This case consumed resources (`Submit>Screen>Reject`) but did not resolve. Naive analysis excludes it entirely, ignoring the cost of processing failures.
    *   *Impact:* Inflates perceived efficiency (lower cycle time) by ignoring failed attempts.

4.  **Open Cases < 72h vs > 72h:**
    *   *Example:* S15 (`open` @ 35h) vs S09 (`open` @ 92h).
    *   *Distinction:* S15 is currently compliant (risk of breach remains). S09 is already a confirmed breach of the 72h SLA (since it is still open past 72h). A naive average duration calculation mixes these states, masking immediate action items.

# 4. Statistical analysis plan

### Recommended Methods
1.  **Primary Approach: Aalen-Johansen Estimator (Cumulative Incidence)**
    *   **Why:** Handles competing risks (`Withdraw`, `Reject`, `Transfer`) correctly. Unlike Kaplan-Meier, it does not assume censored cases eventually resolve. It provides the true probability of `Resolve` by 72h.
    *   **Usage:** Compare CIF curves between Cohort A and B stratified by Priority.

2.  **Secondary Approach: Fine-Gray Subdistribution Hazards**
    *   **Why:** Allows regression modeling to quantify how `priority`, `cohort`, and `escalated` affect the CIF of resolution.
    *   **Usage:** Identify predictors of SLA breach while accounting for competing risks.

3.  **Alternative: Restricted Mean Time to Event (RMST)**
    *   **Why:** Summarizes the area under the survival curve up to 72h. Less sensitive to tail assumptions than median time.
    *   **Usage:** Provide a single "average productive hours saved" metric for management.

### Avoidance of Pitfalls
*   **Do NOT use Cox Proportional Hazards on Completed Cases:** Violates independence assumption due to competing risks.
*   **Do NOT treat `open` cases as resolved:** They are censored.
*   **Do NOT ignore Transfers:** Must be handled via sensitivity analysis (Section 6).

def encode_survival(df, transfer_policy='competing'):
    """
    transfer_policy: 'censored', 'competing', 'failure'
    """
    df_enc = df.copy()
    
    # Time column
    df_enc['time'] = df_enc['duration_or_age_h']
    
    # Event Indicator for Resolution (Estimand 1: Internal Success)
    # 1 = Resolved, 0 = Censored or Competing
    df_enc['event_resolve'] = (df_enc['observed_status'] == 'resolved').astype(int)
    
    # Competing Risk Codes (0=None, 1=Withdraw, 2=Reject, 3=Transfer)
    cr_map = {'withdrawn': 1, 'rejected': 2, 'transferred': 3, 'resolved': 0, 'open': 0}
    df_enc['cr_code'] = df_enc['observed_status'].map(cr_map)
    
    # Adjust based on Policy
    if transfer_policy == 'failure':
        # Treat Transfer as Resolution Failure for SLA Breach Calc
        # For CIF, this means it's not a competing risk for resolution, it's a non-resolution event
        pass 
    elif transfer_policy == 'censored':
        # Transfer acts like Open (randomly removed)
        df_enc.loc[df_enc['observed_status'] == 'transferred', 'cr_code'] = 0
    
    return df_enc

# 9. Limitations and additional data

1.  **Missing Event Timestamps:** We only have total duration (`duration_or_age_h`). We cannot calculate transition times between activities (e.g., time spent in `Review` vs `Screen`). This prevents accurate estimation of bottleneck stages.
2.  **External Outcomes:** `Transfer` cases lack resolution data. We need an API or feed from the external organization to close the loop on these cases.
3.  **Start/End Dates:** Without calendar dates, we cannot control for seasonality or workload spikes (e.g., end-of-month rush).
4.  **Assignment Mechanism:** Cohort B rollout was not randomized. We lack propensity scores or covariates explaining why specific cases went to Cohort B (selection bias).
5.  **Workload Context:** No data on queue size or agent availability at the time of submission. A high breach rate could be due to volume, not process inefficiency.
6.  **Reason Codes:** `Withdraw` and `Reject` lack reasons (e.g., `Invalid Docs` vs `Customer Request`). Aggregating them obscures root causes.
