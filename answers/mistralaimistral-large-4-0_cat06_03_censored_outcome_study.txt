## 1. Target definition

**Primary target: observed-policy conditional 90-day default risk after activation, with right censoring.**

- **Unit of analysis:** one credit application (`case:concept:name`), with transfer linkage resolved where the linkage table permits.
- **Prediction time:** the earlier of  
  (a) the timestamp of the 3rd event after `Application Started`, or  
  (b) 5 calendar days after `Application Started`.  
  Only events with `time:timestamp <= prediction_time` may be used as features.
- **Horizon:** 90 days after `Account Activated`.
- **Population:** applications that reach `Account Activated` under the observed policy and have at least one pre-activation event.
- **Estimand:**  
  \[
  F(90 \mid X_{\text{pre}}, \text{activated}, \text{policy period})
  =
  P(T_{\text{default}} \le 90 \text{ days} \mid T_{\text{activation}} < \infty, X_{\text{pre}}, \text{policy period})
  \]
  where \(T_{\text{default}}\) is time from activation to default. Equivalently, this is \(1 - S(90 \mid X_{\text{pre}}, \text{activated})\).

This formulation is operationally and statistically defensible because `default_90d` is only defined after activation. It uses the actual stored outcome, avoids labeling rejected/withdrawn/open cases as non-default, and avoids counterfactual assumptions. Its limitation is that it is **conditional on activation**, which is a post-prediction selection event. It does **not** answer “default for every application.”

**Alternative target 1: multi-state / competing-outcome target for all applications.**  
Define states such as `In Progress`, `Rejected`, `Withdrawn`, `Transferred`, `Activated`, `Default within 90 days`, `Event-free at 90 days`, and `Censored`. The estimand could be the cumulative incidence of the composite event “Activated then Default within 90 days” or cause-specific hazards for each transition. This answers a different question: “What is the probability that this application will be activated and then default?” It can be applied to every application and treats rejection/withdrawal/transfer as competing events, not as non-defaults.

**Alternative target 2: policy-specific counterfactual target.**  
\[
P(\text{default}_{90d}=1 \mid \text{do(activate)}, X_{\text{pre}})
\]
for all applications. This is the default risk if the lender activated the application regardless of the observed decision. It requires strong assumptions—no unmeasured confounding, positivity, consistency—and is not identifiable from the observed data alone. It should be clearly labeled as requiring stronger assumptions.

---

## 2. Cohort construction

**Inclusion rules**

- All applications with `Application Started` between 2024-01-01 and 2025-12-31.
- At least one event and a valid `case:concept:name`.
- All events up to the extraction date are retained for outcome construction, but only events up to the prediction time are used for features.

**Exclusion rules**

- Exact duplicate events introduced by the 2025-10-15 migration are removed and logged: same case, normalized activity, timestamp, and resource.
- Cases with no `Application Started` event are excluded if any exist.
- For the **primary** analysis, non-activated cases are excluded because default is undefined for them. They are **not** labeled non-default.

**As-of rules**

- Prediction time: earlier of 3rd event or 5 days after start.
- Outcome maturity: an activated account has a mature outcome if `label_available_at <= 2026-02-15` and the 90-day window after activation is complete.
- Label availability: use the last non-null `label_available_at` per case.

**Cohort-flow table**

| Stage | Count | Disposition in primary analysis |
|---|---:|---|
| Applications started | 48,000 | Universe |
| Activated accounts | 25,200 | Primary population |
| — Activated with matured 90-day outcome (labeled export) | 21,600 | Primary: 18,900 event-free, 2,700 default |
| — Activated but outcome/feed not yet mature | 3,600 | Primary: right-censored; administrative censoring or delayed label |
| Rejected | 9,100 | Competing outcome; excluded from primary; used in multi-state alternative |
| Withdrawn | 5,700 | Competing outcome; excluded from primary; used in multi-state alternative |
| Transferred | 2,900 | Competing outcome / missing follow-up; ~60% linkable; excluded from primary unless linked to an activated account |
| Still open at extraction | 5,100 | Not yet terminal; excluded from primary; used in multi-state alternative as censored in-progress |
| **Total accounted** | **48,000** | |

The 3,600 activated but not-yet-mature cases include both administrative censoring (90-day window incomplete) and delayed labels (window complete but feed not yet arrived). The exact split is computed from the event data.

## 3. Censoring and missing-label strategy

**Distinguishing the mechanisms**

- **Ordinary right censoring:** activated accounts whose 90-day window extends beyond the extraction date; still-open applications in the multi-state alternative.
- **Delayed labels:** the outcome feed arrives 7–35 days after the 90-day horizon. Some activated accounts have a complete 90-day window but `label_available_at > 2026-02-15`. These are **not** non-defaults; they are missing at extraction.
- **Selection through activation:** default is only observed for activated accounts. Rejected, withdrawn, transferred, and open cases are not non-defaults; they are competing outcomes or undefined. The primary analysis conditions on activation. This is a structural selection, not a missing-data problem that can be fixed by imputation.
- **Transfer as competing event or missing follow-up:** transferred cases may reappear under a new identifier. The linkage table covers only about 60% of transfers. Unlinked transfers are missing follow-up; linked transfers can be followed. Transfer is a competing event because it removes the case from the observed platform.
- **Permanently missing outcome feeds:** partner-originated activated accounts have an elevated probability of a permanently missing outcome feed. This is informative missingness and must not be treated as non-default.

**Primary analysis strategy**

Use a survival model for time to default after activation among all 25,200 activated accounts.

- Event time: time from `Account Activated` to default, if observed within 90 days.
- Censoring time: `min(90 days, extraction_date - activation_time, last known event-free time)`.
- Delayed or missing labels are treated as right-censored with a missing-label indicator.
- Use inverse probability of censoring weights (IPCW) for label maturity/availability based on pre-activation covariates and a partner-originated flag.
- Estimate the 90-day cumulative incidence of default from the survival model.

This addresses ordinary right censoring and delayed labels. It does **not** remove selection through activation; that is handled by conditioning on activation and clearly stating the population.

**Sensitivity analyses**

1. **Complete-case analysis** using only the 21,600 matured labels; compare with the primary analysis to assess missingness bias.
2. **Pattern-mixture sensitivity analysis** for missing outcome feeds: assume missing labels have default odds multiplied by \(\delta \in \{1, 1.5, 2, 3\}\) relative to observed labels with the same covariates; report bounds.
3. **Transfer-linkage sensitivity:** treat unlinked transfers as non-activated competing outcomes versus excluding them; include linked transfers with a transfer-in flag.
4. **Policy-period sensitivity:** fit separate models before/after 2025-07-01 and before/after the 2025-10-15 migration; compare coefficients and calibration.

**Assumption testability**

- **Testable:** administrative censoring dates; label maturity timing; policy-change effects on observed covariates and outcomes; duplicate events; transfer linkage rate.
- **Partially testable:** missing at random for delayed labels—we can test association with observed covariates but not with unobserved default; non-informative censoring—we can test observed covariates only.
- **Fundamentally untestable:** counterfactual default risk for rejected/withdrawn applications; missing outcome feed mechanism if it depends on unobserved default; selection through activation as a counterfactual.

## 4. Prefix extraction

**Activity normalization and deduplication**

- Normalize activity names using a mapping table for the 2025-10-15 migration. Keep both raw and normalized activity columns.
- Remove exact duplicate events introduced by migration: same case, normalized activity, timestamp, and resource. Log removed duplicates.
- Sort events by case and timestamp; use a deterministic tie-breaker for identical timestamps.

**Prediction time definitions**

- **Primary fixed event-count prefix:** first 3 events after `Application Started`. If fewer than 3 events occur before 5 days, use all events up to 5 days.
- **Secondary elapsed-time prefix:** all events with `time:timestamp <= case_start + 5 days`.

**Handling special cases**

- **Short cases:** include cases with fewer than 3 events; add a `prefix_length` feature and a `prefix_complete` flag.
- **Repeated document loops:** do not truncate loops. Include loop count, number of `Request Documents` events, number of returns to `Credit Review`, and time spent in loops.
- **Activity renaming:** map post-migration names to canonical pre-migration names before feature construction.

**No future information**

After prefix construction, drop all events with `time:timestamp > prediction_time`. For time-varying columns, take the last value at or before the prediction time.

## 5. Process-aware features

**Static case attributes** (known at application start)

- `case:channel`, `case:region`, `case:requested_amount`, `source_system`
- Application start date/time, calendar features: month, day of week, hour
- Policy-period indicator: pre/post 2025-07-01
- Migration-period indicator: pre/post 2025-10-15

**Prefix-derived features** (from events up to prediction time)

- **Control-flow:** sequence of normalized activities, number of events, number of distinct activities, presence of `Identity/KYC Check`, `Credit Review`, `Request Documents`, `Accept`/`Reject` if within prefix, variant ID from `pm4py.get_variants`, DFG-based features from `pm4py.discover_dfg`.
- **Timing:** time from start to prediction time, time between consecutive events, time spent in each activity, waiting time in queue from `pm4py.insert_case_service_waiting_time`, time from start to KYC, KYC to Credit Review, Credit Review to first Request Documents.
- **Rework:** number of `Request Documents` events, number of returns to `Credit Review`, loop count, duplicate activity count.
- **Resource/queue:** number of distinct resources, resource experience at event time, queue length at event time, number of cases handled by the resource in the last 30 days.
- **Risk score:** last `risk_score` at or before prediction time, number of updates, change in `risk_score` within prefix.
- **Documents:** number of documents requested/uploaded within prefix, `documents_total` as of prediction time, document loop count.

**Historical reference data**

- Employee experience at event time from an HR table keyed by employee and date.
- Queue length at event time from the event log or queue system.
- Historical default rates by channel/region/policy period, computed only from training data.
- Policy-period indicators.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision; leaks post-decision information and is only available for accepted cases. | Only if `final_limit` is known at or before prediction time, which is unlikely. | Drop | Using it would make the model depend on information not available at prediction time and bias estimates. |
| `decision_reason` | Populated at or after Accept/Reject; leaks decision outcome. | Only if the decision occurred before prediction time. | Drop for primary early-warning model | `decision_reason` is a consequence of credit review and may directly encode default risk. |
| `collection_status` | Updated after activation and may directly reveal default. | Only after activation and after a default event. | Drop from features; use only to construct the outcome | `collection_status` is a near-perfect predictor of default and is not available at prediction time. |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | Events after prediction time leak future information. | Only events with `time:timestamp <= prediction_time`. | Drop all events after `prediction_time` from the feature table; use them only for outcome construction and cohort definition | As-of prediction requires no future information. |
| `documents_total` | Nightly snapshot can include documents uploaded later on the same calendar day than the prediction time. | Use the snapshot as of the end of the day before prediction time, or reconstruct from the event log up to prediction time. | Repair by reconstructing from the event log or using the previous day's snapshot; drop if it cannot be made as-of | Same-day later uploads are future information. |
| Updated `risk_score` | May be updated at several events; using the final or latest update after prediction time leaks future information. | Use the last `risk_score` value at or before `prediction_time`. | Keep as-of version; drop any post-prediction updates | `risk_score` is time-varying and must respect the as-of time. |
| Resource experience | Stored as the employee's experience at extraction time, not necessarily at event time. | Use experience as of the event timestamp from HR reference data. | Repair by joining to an HR table keyed by employee and date; drop if not available | Extraction-time experience is not known at event time. |
| Label availability (`default_90d`, `label_available_at`) | Using label availability as a feature leaks outcome maturity and may be associated with default. | Only for outcome construction, not as a feature. | Drop from features; use only to define censoring/missingness | Label availability is a post-outcome administrative variable. |

## 7. Validation design

**Temporal validation**

Split by case start time, not randomly:

- **Train:** `case_start < 2025-07-01` (pre-policy change)
- **Validation:** `2025-07-01 <= case_start < 2025-10-15` (post-policy change, pre-migration)
- **Test:** `case_start >= 2025-10-15` (post-migration)

For the primary target, restrict each split to activated cases. For the multi-state alternative, include all cases.

**Label maturity**

- Create a **mature test set** for binary metrics: cases whose 90-day outcome is mature by the extraction date, or whose event log confirms no default by 90 days.
- For test cases with incomplete follow-up, use survival metrics that handle right censoring.

**Backtesting**

Simulate deployment at multiple cutoffs, e.g., 2025-03-31, 2025-06-30, 2025-09-30, and 2025-12-31, and evaluate on subsequent applications. This mimics real deployment and captures policy and migration shifts.

**Calibration**

- Calibration curves, Brier score, calibration-in-the-large, and calibration slope.
- Recalibrate on the validation set if needed.

**Subgroup performance**

Evaluate by channel, region, requested-amount band, policy period, migration period, partner-originated flag, transfer-in flag, and missing-label indicator.

**Distribution shift**

Monitor Population Stability Index (PSI) for key features between train and test. Compare feature distributions before/after the policy change and migration.

**Metrics**

- Time-dependent AUC at 90 days with inverse probability of censoring weights.
- Brier score at 90 days with censoring weights.
- Calibration-in-the-large and calibration slope.
- Decision curve analysis for business utility.
- For the mature binary subset: AUC, AUPRC, precision/recall at a chosen threshold.

**Why a random case split is misleading**

A random split mixes cases from different policy periods and migration periods, leaks future information, creates dependence between train and test via shared resources or cases, and overestimates performance. It ignores temporal drift and label maturity.

## 8. Limitations and decision-use boundary

**What the study can claim**

The model estimates the observed-policy conditional 90-day default risk after activation for applications that reach activation, using only pre-activation prefix information. It can rank applications by risk within that population.

**What the study cannot claim**

- It does **not** estimate default risk for rejected, withdrawn, transferred, or still-open applications.
- It does **not** estimate counterfactual default risk if the lender changed its activation policy.
- It does **not** predict default for every application.
- It cannot distinguish causal effects from selection effects.

**Predictive association, selection effects, and counterfactual risk**

The model captures predictive associations in the observed data. Because activation is a selection event, the risk estimates are conditional on activation and may be biased for the all-application population. Counterfactual default risk requires assumptions about what would happen if rejected or withdrawn applications were activated.

**Ways deployment could change the data-generating process**

1. **Policy change:** if the lender changes credit thresholds, the activated population changes and the model may become miscalibrated.
2. **Model-driven interventions:** if the model triggers collections or limits, it changes outcomes, creating feedback loops and label bias.
3. **Channel/process changes:** changes in application channels, system migration, or transfer partnerships shift feature distributions.
4. **Selection effects:** if the model is used to reject or transfer more applications, the activation selection mechanism changes, and the conditional-on-activation estimand no longer matches the deployed population.
5. **Data quality changes:** outcome feed delays or missingness patterns may change, affecting label maturity and censoring.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import numpy as np
import pm4py

# -----------------------------
# Configuration and constants
# -----------------------------
CASE_ID = "case:concept:name"
ACTIVITY = "concept:name"
TIMESTAMP = "time:timestamp"
EXTRACTION_DATE = pd.Timestamp("2026-02-15")
PRED_EVENT_COUNT = 3          # primary fixed event-count prefix
PRED_ELAPSED_DAYS = 5         # secondary elapsed-time prefix
HORIZON_DAYS = 90
POLICY_CHANGE = pd.Timestamp("2025-07-01")
MIGRATION_DATE = pd.Timestamp("2025-10-15")

# Activity renaming map for the 2025-10-15 migration (extend with actual names)
ACTIVITY_RENAME = {
    "KYC Check": "Identity/KYC Check",
    "Credit Assessment": "Credit Review",
    # ... add all renamed activities
}

# -----------------------------
# 1. Load and standardize events
# -----------------------------
df = pd.read_csv("applications_events.csv")
df[TIMESTAMP] = pd.to_datetime(df[TIMESTAMP])
df = df.sort_values([CASE_ID, TIMESTAMP]).reset_index(drop=True)

# Remove exact duplicate events introduced by migration
df = df.drop_duplicates(subset=[CASE_ID, ACTIVITY, TIMESTAMP, "org:resource"], keep="first")

# Normalize activity names; keep raw for audit
df["activity_norm"] = df[ACTIVITY].replace(ACTIVITY_RENAME)

# Format as PM4Py event log
log = pm4py.format_dataframe(
    df,
    case_id=CASE_ID,
    activity_key="activity_norm",
    timestamp_key=TIMESTAMP
)

# -----------------------------
# 2. Case-level start, activation, terminal, censoring, label maturity
# -----------------------------
case_start = df.groupby(CASE_ID)[TIMESTAMP].min().rename("case_start")
case_start_df = case_start.reset_index()

activation = (
    df[df["activity_norm"] == "Account Activated"]
    .groupby(CASE_ID)[TIMESTAMP]
    .min()
    .rename("activation_time")
)

terminal = (
    df[df["activity_norm"].isin(["Rejected", "Withdrawn", "Transferred", "Default Recorded"])]
    .groupby(CASE_ID)
    .agg(terminal_activity=("activity_norm", "first"), terminal_time=(TIMESTAMP, "min"))
)

default_time = (
    df[df["activity_norm"] == "Default Recorded"]
    .groupby(CASE_ID)[TIMESTAMP]
    .min()
    .rename("default_time")
)

label_info = (
    df.groupby(CASE_ID)
    .agg(default_90d=("default_90d", "last"), label_available_at=("label_available_at", "last"))
    .reset_index()
)

case_info = (
    pd.concat([case_start, activation, terminal, default_time], axis=1)
    .reset_index()
    .merge(label_info, on=CASE_ID, how="left")
)
case_info["activated"] = case_info["activation_time"].notna()
case_info["horizon_end"] = case_info["activation_time"] + pd.Timedelta(days=HORIZON_DAYS)


def compute_survival(row):
    """Compute time-to-default after activation with right censoring."""
    if not row["activated"]:
        return pd.Series({"surv_time": np.nan, "surv_event": np.nan, "censor_reason": "not_activated"})

    act = row["activation_time"]
    horizon_end = act + pd.Timedelta(days=HORIZON_DAYS)
    default_time = row["default_time"]

    # Observed default within 90 days after activation
    if pd.notna(default_time) and default_time <= horizon_end:
        return pd.Series({"surv_time": (default_time - act).days, "surv_event": 1, "censor_reason": "default"})

    # Mature event-free label
    if (horizon_end <= EXTRACTION_DATE and pd.notna(row["label_available_at"])
            and row["label_available_at"] <= EXTRACTION_DATE and row["default_90d"] == 0):
        return pd.Series({"surv_time": HORIZON_DAYS, "surv_event": 0, "censor_reason": "event_free_mature"})

    # Otherwise right-censored
    censor_time = min(horizon_end, EXTRACTION_DATE)
    surv_time = max((censor_time - act).days, 0)
    reason = "admin_censoring" if horizon_end > EXTRACTION_DATE else "delayed_or_missing_label"
    return pd.Series({"surv_time": surv_time, "surv_event": 0, "censor_reason": reason})


case_info = pd.concat([case_info, case_info.apply(compute_survival, axis=1)], axis=1)

# -----------------------------
# 3. Cohort counts
# -----------------------------
cohort_counts = {
    "total_applications": len(case_info),
    "activated": int(case_info["activated"].sum()),
    "activated_mature_labeled": int(
        (case_info["activated"] & case_info["censor_reason"].isin(["default", "event_free_mature"])).sum()
    ),
    "activated_censored": int(
        (case_info["activated"] & case_info["censor_reason"].isin(["admin_censoring", "delayed_or_missing_label"])).sum()
    ),
    "rejected": int((case_info["terminal_activity"] == "Rejected").sum()),
    "withdrawn": int((case_info["terminal_activity"] == "Withdrawn").sum()),
    "transferred": int((case_info["terminal_activity"] == "Transferred").sum()),
    "still_open": int(
        (~case_info["activated"] & ~case_info["terminal_activity"].isin(["Rejected", "Withdrawn", "Transferred"])).sum()
    ),
}
print("Cohort counts:", cohort_counts)

# -----------------------------
# 4. Temporal train/validation/test split by case start time
# -----------------------------
# Primary split: pre-policy change / post-policy pre-migration / post-migration
train_mask = case_info["case_start"] < POLICY_CHANGE
val_mask = (case_info["case_start"] >= POLICY_CHANGE) & (case_info["case_start"] < MIGRATION_DATE)
test_mask = case_info["case_start"] >= MIGRATION_DATE

# Primary analysis population: activated cases only
primary_train = case_info[train_mask & case_info["activated"]].copy()
primary_val = case_info[val_mask & case_info["activated"]].copy()
primary_test = case_info[test_mask & case_info["activated"]].copy()

# Note: pm4py.split_train_test(log, train_percentage=0.8) is a convenience baseline only;
# the primary validation above is temporal and must not be replaced by a random split.

# -----------------------------
# 5. Prefix extraction without future information
# -----------------------------
# Fixed event-count prefixes using PM4Py
prefixes = pm4py.get_prefixes_from_log(log, length=PRED_EVENT_COUNT)

# Convert prefixes to a DataFrame
prefix_rows = []
for case_id, prefix in prefixes:
    for event in prefix:
        prefix_rows.append({CASE_ID: case_id, **event})
prefix_df = pd.DataFrame(prefix_rows)

# Elapsed-time prefix: all events up to case_start + PRED_ELAPSED_DAYS
df = df.merge(case_start_df, on=CASE_ID)
df["prediction_time_elapsed"] = df["case_start"] + pd.Timedelta(days=PRED_ELAPSED_DAYS)
elapsed_prefix_df = df[df[TIMESTAMP] <= df["prediction_time_elapsed"]].copy()

# For the primary fixed-count prefix, define prediction time as the last prefix event timestamp
prefix_df = prefix_df.merge(
    prefix_df.groupby(CASE_ID)[TIMESTAMP].max().rename("prediction_time_fixed"),
    on=CASE_ID
)

# -----------------------------
# 6. Build as-of feature table (no post-prefix columns/events)
# -----------------------------
# Keep only events up to prediction time
prefix_df = prefix_df[prefix_df[TIMESTAMP] <= prefix_df["prediction_time_fixed"]].copy()

# Drop forbidden post-outcome/post-decision columns from features
FORBIDDEN_COLS = ["final_limit", "decision_reason", "collection_status", "default_90d", "label_available_at"]
feature_df = prefix_df.drop(columns=FORBIDDEN_COLS, errors="ignore")

# As-of risk_score: last value at or before prediction time
risk_asof = (
    prefix_df.sort_values(TIMESTAMP)
    .groupby(CASE_ID)["risk_score"]
    .last()
    .rename("risk_score_asof")
)

# documents_total: in production, reconstruct from document upload events up to prediction_time;
# here we use the last value before prediction_time as a placeholder (see leakage audit)
documents_asof = (
    prefix_df.sort_values(TIMESTAMP)
    .groupby(CASE_ID)["documents_total"]
    .last()
    .rename("documents_total_asof")
)

# Prefix-derived control-flow and rework features
prefix_features = (
    prefix_df.groupby(CASE_ID)
    .agg(
        prefix_length=(TIMESTAMP, "count"),
        distinct_activities=("activity_norm", "nunique"),
        n_request_documents=("activity_norm", lambda x: (x == "Request Documents").sum()),
        n_credit_review=("activity_norm", lambda x: (x == "Credit Review").sum()),
        n_identity_kyc=("activity_norm", lambda x: (x == "Identity/KYC Check").sum()),
        first_activity=("activity_norm", "first"),
        last_activity=("activity_norm", "last"),
    )
    .reset_index()
)

# Static case attributes
static_features = (
    df.groupby(CASE_ID)
    .agg(
        case_channel=("case:channel", "first"),
        case_region=("case:region", "first"),
        requested_amount=("case:requested_amount", "first"),
        source_system=("source_system", "first"),
    )
    .reset_index()
)

# Merge features
feature_table = (
    prefix_features
    .merge(static_features, on=CASE_ID, how="left")
    .merge(risk_asof, on=CASE_ID, how="left")
    .merge(documents_asof, on=CASE_ID, how="left")
    .merge(
        case_info[[CASE_ID, "case_start", "activated", "surv_time", "surv_event", "censor_reason"]],
        on=CASE_ID,
        how="left",
    )
)

# -----------------------------
# 7. Process-aware features with PM4Py (interpretation-justified)
# -----------------------------
# Format prefix log for PM4Py process-aware features
prefix_log = pm4py.format_dataframe(
    prefix_df,
    case_id=CASE_ID,
    activity_key="activity_norm",
    timestamp_key=TIMESTAMP
)

# DFG on the early prefix (control-flow structure)
dfg, start_activities, end_activities = pm4py.discover_dfg(prefix_log)

# Variants in the early prefix (sequence patterns)
variants = pm4py.get_variants(prefix_log)
variant_counts = pd.Series({str(v): len(cases) for v, cases in variants.items()}, name="variant_count")

# Temporal features from the prefix (case duration, time between events)
temporal_features = pm4py.extract_temporal_features_dataframe(prefix_log)

# Insert case service waiting time (queue time) into the prefix log
prefix_log = pm4py.insert_case_service_waiting_time(prefix_log, queue_attribute=None)

# Extract waiting time as a case-level feature
waiting_time = (
    pm4py.convert_to_dataframe(prefix_log)
    .groupby(CASE_ID)["case:service_waiting_time"]
    .first()
    .rename("service_waiting_time")
)

# Merge PM4Py-derived features
feature_table = (
    feature_table
    .merge(temporal_features, on=CASE_ID, how="left")
    .merge(waiting_time, on=CASE_ID, how="left")
)

# -----------------------------
# 8. Leakage audit check
# -----------------------------
def leakage_audit(feature_table, prefix_df):
    issues = []
    # Check forbidden columns
    for col in FORBIDDEN_COLS:
        if col in feature_table.columns:
            issues.append(f"Forbidden column present in features: {col}")
    # Check no post-prediction events
    if (prefix_df[TIMESTAMP] > prefix_df["prediction_time_fixed"]).any():
        issues.append("Post-prediction events found in prefix table")
    # Check risk_score is as-of (no post-prediction updates)
    if "risk_score" in feature_table.columns:
        issues.append("Raw risk_score column should be replaced by risk_score_asof")
    return issues


audit_issues = leakage_audit(feature_table, prefix_df)
print("Leakage audit issues:", audit_issues if audit_issues else "none")

# -----------------------------
```
