## 1. Analytical assumptions

*Case notion.* A case is the lifecycle of a single object instance defined by the events to which it is directly related via E2O. The trace is the time-ordered multiset of those events. Flattening on object type X creates one trace per X-instance and copies every event that is directly related to that instance into the trace.

*Convergence and divergence.* Convergence is the participation of two or more object instances of the same or different types in the same event, e.g. Pack Package e13 is directly related to O2, O3, I21, I31, P3. In an X-flattening the event is copied into each X-case that is related to it, creating artificial synchrony. Divergence is the participation of a single object instance in multiple, partially overlapping event streams, e.g. O1 is related to P1 via e11,e15,e23 and to P2 via e12,e16,e24, so O1 diverges across two package-delivery paths.

*Shared events.* A copied shared event is both evidence of object interaction and duplication. It is evidence of a real business synchronization – P3 is packed once for O2 and O3 – and duplication when the same timestamped activity is inserted into multiple traces. Performance metrics computed on the flattened log therefore mix real duration with copy-induced synchrony.

*Transformations.* The baseline analysis uses only direct E2O relations as given in the event-object table. Relation propagation through O2O links, e.g. inferring that an Add Item event for O1,I11 also relates to P1 because P1 packs I11, is explicitly an analytical transformation and is not applied unless stated. All claims below are grounded in direct relations.

## 3. Concrete distortion analysis

*Order flattening – cross-order package P3 duplication.* Pack Package e13 is directly related to O2,O3,I21,I31,P3. Flattening on Order copies e13 into both O2 and O3 traces. The DFG shows Pack Package  Dispatch for both orders with identical timestamp 2026-02-03 10:12. The apparent variant suggests two independent packings, while the object-centric view shows one shared packing resource. Frequency of Pack Package is inflated by 100% for the pair.

*Order flattening – cross-order package P4 duplication.* Pack Package e14 relates to O3,O4,I32,I41,P4. Both O3 and O4 receive e14 at 2026-02-03 10:20. The trace for O3 shows Pack Package followed immediately by Pack Package from e13, creating an artificial parallel packing pattern for a single order. Performance of O3 packing appears split.

*Order flattening – consolidated delivery D2.* Dispatch e16 is directly related to O1,O2,O3,I12,I21,I31,P2,P3,D2. Confirm Delivery e24 is directly related to the same three orders. Each of O1,O2,O3 gets identical Dispatch and Confirm Delivery timestamps 11:05 and 16:00. The DFG shows perfect synchrony O1O2O3 on Dispatch and Confirm Delivery, suppressing real variance and hiding that D2 consolidates P2 from O1 and P3 from O2/O3.

*Order flattening – consolidated invoicing V2.* Issue Invoice e19 relates to O2,O3,V2. Record Payment e22 relates to O2,O3,V2,M2 and e25 relates to O2,O3,V2,M3. In the Order view each order appears to be invoiced separately and to receive two payments. The business fact that V2 consolidates O2 and O3 is lost, and the partial payment semantics are duplicated.

*Order flattening – partial payments duplicated.* V2 is paid by M2 partially_settles and M3 completes_settlement. In Order traces O2 and O3 each contain e22 then e25. Frequency of Record Payment is doubled and the apparent payment cycle per order is 1 day 21h, whereas the invoice case V2 has a single 1 day 19h settlement cycle with two instalments.

*Payment flattening – near-singleton lifecycle.* Flattening on Payment yields M1:e21, M2:e22, M3:e25, M4:e26. Each trace has length 1 and no precedence. The DFG is empty, performance metrics are undefined, and the relationship to invoices V1,V2,V3 and orders O1-O4 is lost. This is harmful for process analysis but informative for cash accounting.

*Item flattening – lifecycle truncation.* Item I11 trace is e05 Add Item, e11 Pack Package, e15 Dispatch, e23 Confirm Delivery. Create Order e01 for O1 and Close Order e28 are absent because they are not directly related to I11. The apparent lifecycle starts late and ends early, biasing lead-time calculations downward.

*Package flattening – loss of order split.* Package P1 and P2 are independent cases. The Package view is informative for logistics but hides order-level fragmentation.

## 4. Traditional versus object-centric analysis portfolio

Flattened logs to retain:
* Order-flattened log for business KPI: order creation to close, fulfilment cycle time, invoice-to-payment lag. Safe questions: distribution of Close Order times e28-e31, whether Create Order precedes Add Item, and overall variant mix at order granularity. * Package-flattened log for logistics: Pack Package  Dispatch  Confirm Delivery timing per package P1-P4. Safe: delivery lead time per package, e.g. P1 10:00 to 14:00. Unsafe: why P3 and P4 contain items from multiple orders.
* Invoice-flattened log for finance: Issue Invoice  Record Payment per invoice V1-V3. Safe: settlement duration for V2 with two instalments M2,M3. Unsafe: mapping settlement to individual order fulfilment.

Object-centric views required:
* OC-DFG and ET-OT graph to see true synchronization: e13 links O2,O3,P3,I21,I31; e16 links O1,O2,O3,P2,P3,D2. This exposes convergence without duplication.
* OTG to quantify object interactions: O2-O3 share Invoice V2 and Package P3; O3-O4 share Package P4 and Delivery D3.
* Object interaction summary to measure how often a shared event is copied.
Reconciliation: compare order-level cycle time from flattened log with OC-DFG path length that counts shared events once. Divergence between the two indicates duplication bias. Report both numbers with explanation.

## 5. Lead-object decision

Position B. Use a primary lead object plus explicitly secondary lifecycles.

Decision criteria: coverage of end-to-end business question, trace completeness from creation to close, manageability of convergence distortion, and ability to preserve financial linkage.

Strongest supporting evidence: Order is the only type that directly links Create Order e01-e04, Add Item e05-e10, Pack Package e11-e14, Dispatch e15-e17, Issue Invoice e18-e20, Record Payment e21,e22,e25,e26, Confirm Delivery e23,e24,e27, Close Order e28-e31. Business facts about split orders, consolidated packages and invoices are expressed in relation to orders.

Strongest counterargument: Order flattening suffers high convergence risk from shared events e13,e14,e16,e17,e19,e22,e24,e25. Performance metrics and DFG frequencies are inflated and artificial synchrony is introduced between O2/O3 and O3/O4.

Residual risk: Duration and frequency KPIs computed on order-flattened log overstate parallelism and understate variance. Payment instalments for V2 appear duplicated.

Conditions to change decision: If the analytical focus shifts exclusively to physical logistics, Package or Delivery becomes primary lead with Order as secondary. If financial settlement is the sole concern, Invoice becomes primary. A single lead object is indefensible for a holistic analysis because convergence and divergence are both present.

## 7. Sensitivity and validation plan

*Remove or down-weight copied shared events.* Create a variant of the Order flattened log where events with >1 Order relation, e.g. e13,e14,e16,e17,e19,e22,e24,e25, are kept only once per timestamp per order cluster or weighted by 1/k. Compare DFG edge frequencies and mean cycle time to baseline. Large shifts indicate duplication bias.

*Direct E2O vs propagated-relation variant.* Build a second OCEL where relations are propagated one hop via O2O, e.g. link Pack Package e11 to Order O1 via I11 and P1. Re-flatten on Order and compare trace lengths and variants. Propagation increases convergence artificially and should be reported separately.

*Change lead object.* Replicate the full analysis with Package as lead. Compare order fulfilment cycle time derived from Package log by joining via O2O against Order lead cycle time. Systematic differences highlight information loss.

*Frequency metrics basis.* Compute OC-DFG frequencies three ways: per event occurrence, per unique object instance, and per total object participation in the event. For e16 Dispatch, event count =1, unique Order instances =3, total object participation =7. Report all three to avoid misinterpreting inflated frequencies in flattened logs.
