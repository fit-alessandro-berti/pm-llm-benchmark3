## 1. Analytical assumptions

**Case notion.** I treat a case notion strictly as the flattening rule: choose one object type `OT`, create one case per object identifier `o  OT`, and assign to that case the set `{e | (e,o)  E2O}` ordered by `Timestamp`. I do not propagate relations through `O2O` unless explicitly stated. An activity may appear zero, one or many times in a case; the resulting case is not a normative business case but a projection.

**Convergence.** One event `e` is related to `n>1` distinct objects of the type used for flattening. Example: `e13 Pack Package` is directly related to `O2` and `O3`. Convergence is a 1:many `EO` property for a given `OT`. Consequence on flattening: the logical event is copied into `n` traces, inflating event counts by `n` and creating spurious directly-follows observations.

**Divergence.** One case object `o` is related to `m>1` events of the same activity, or to `m>1` distinct objects of a finer-grained type that generate similar events. Example: `O1 contains I11,I12` and therefore relates to two `Add Item` events `e05,e06` and two `Pack Package` events `e11,e12`. Divergence is a 1:many `OE` property. Consequence: apparent repetition, loops or parallelism inside a flattened trace that reflects structural multiplicity, not process rework.

**Copied shared events: evidence *and* duplication.** A copied event is evidence that the flattened object participated. Simultaneously it is duplication at the log level. Deleting it would hide participation; counting it at face value would hallucinate workload. I therefore report both: participation truth (object `o` was involved in `e16`) and log-level distortion (system-wide count of `Dispatch` goes from 3 true events `e15,e16,e17` to 6 Order-flattened occurrences, 3 of them copies of `e16`).

**Analytical transformations permitted.** 
- **Strict direct mode:** use only the supplied `E2O` table. This is the baseline for all matrix ratings.
- **Explicit propagation mode:** for sensitivity analysis only, materialize inferred `E2O'` by traversing `O2O`: e.g. if `e21 Record Payment O1,V1,M1` and `V1 bills O1`, we could propagate `V1`/`M1` events to `I11/I12`, or propagate `D2` events to all `O` that share its `P`. I will never silently propagate; any propagated variant will be labeled as `E2O+O2O` and compared to the direct variant to show what is hidden by the current `E2O` design.

## 3. Concrete distortion analysis

**D1 – Cross-order Package P3, Order flattening:** `e13 Pack Package O2,O3,I21,I31,P3` copied into `O2` trace and `O3` trace. True physical operation count =1, Order-flattened count =2 (+100%). DFG impact: `Add ItemPack Package` edge `e07e13` and `e08e13` both appear, inflating frequency of `Pack Package` from 4 to 6 and suggesting two separate packs where warehouse did one. **Harmful** if used for workload/capacity planning; **informative** only as participation marker if annotated as duplicate.

**D2 – Cross-order Package P4, Order flattening:** `e14 Pack Package O3,O4,I32,I41,P4` duplicated `O3`/`O4`. Variant trap for `O3`: trace shows `e13 Pack P3` at `10:12` followed by `e14 Pack P4` at `10:20` implying sequential packing of two packages for one order. In truth `P4` jointly packs `I32(O3)` and `I41(O4)` – the second pack is not solely `O3` work. DFG creates false edge `PackPack` with frequency 1 for `O3` that object-centric view reveals as two distinct packages sharing a pack. **Harmful** for rework analysis; **context-dependent** if goal is order backlog (then duplication counts as involvement).

**D3 – Consolidated Delivery D2, Order flattening:** `e16 Dispatch O1,O2,O3,I12,I21,I31,P2,P3,D2` and `e24 Confirm Delivery O1,O2,O3,I12,I21,I31,P2,P3,D2` each triplicated across `O1,O2,O3`. DFG edge `DispatchIssue Invoice` appears with `O2,O3` frequency 1 each, implying two dispatches preceded invoicing `e19`, while physically one truck `D2` carried both packages. Performance distortion: mean `PackDispatch` lag sampled thrice at `11:05` distorts confidence intervals; throughput overcounted 3×. **Harmful** for logistics costing.

**D4 – Consolidated Delivery D2, Package flattening:** `e16P2,P3` convergent on `Package` type, so `e16` duplicated across `P2` and `P3` (2×) and `e24` likewise. True `D2` dispatch count 1 becomes 2 package-dispatch occurrences. DFG `PackDispatch` inflated 33% (6 instead of 4 pack-dispatch pairs conceptually). Analyst comparing `Package` DFG frequency of `Dispatch` (6) vs `Delivery` DFG (3) would conclude double dispatch volume. Trap is **harmful** when switching object type without renormalizing.

**D5 – Consolidated Invoicing V2, Order flattening:** `e19 Issue Invoice O2,O3,V2` duplicates `O2`/`O3`; `V2 bills O2,O3` is single `12:05` event counted twice. Order-flattened `Issue Invoice` frequency 4 vs true 3. DFG variant `DispatchIssue InvoiceRecord Payment` appears separately for `O2` and `O3`, hiding that one invoice settled two orders simultaneously. Apparent variant pool 4 traces for 4 orders obscures that `O2` and `O3` share identical financial fate. **Harmful** for accounts-receivable aging; **informative** that both orders participated.

**D6 – Partial Payments V2, Invoice vs Order flattening:** In Invoice flattening, `V2` case contains divergent `e22 Record Payment O2,O3,V2,M2 @12:40` and `e25 Record Payment O2,O3,V2,M3 @09:00 next day` producing DFG self-loop `Record Payment  Record Payment`. In Order flattening, both `e22` and `e25` are duplicated across `O2`/`O3`  payment event count 4 vs true 2, DFG edge `Issue InvoiceRecord Payment` frequency 6 vs 3. If analyst averages time-to-payment at order level, `O2` and `O3` both contribute `~20h` for second installment, double-weighting `V2` in portfolio DSO. **Harmful** for financial KPIs; loop is **informative** only if recognized as compliant installment plan (`partially_settles`  `completes_settlement`).

**D7 – Near-singleton lifecycle Payment (M1-M4):** Flattening on `Payment` yields 4 cases length 1: `M1:e21`, `M2:e22`, `M3:e25`, `M4:e26`. No edges, no variant diversity, `discover_log_skeleton` returns empty relations, `discover_dfg` fails usefulness. Lifecycle truncation is total: 30 of 31 preceding events invisible. An analyst claiming “payment process has no rework” is tautology of data model. **Harmful** as process view; **informative** only as settlement event inventory for reconciliation.

**D8 – Divergence/split Order O1, Order flattening:** `O1 contains I11,I12` leads to `e05 Add I11`, `e06 Add I12`, `e11 Pack P1`, `e12 Pack P2`, `e15 Dispatch D1`, `e16 Dispatch D2` inside single `O1` trace `e01e05e06e11e12e15e16...e23e24e28`. DFG creates artificial sequences `PackPack`, `DispatchDispatch`, `ConfirmConfirm` that appear as loops/rework, while ground truth is split across two packages/deliveries executed in parallel ( `P1/D1` at `10:00/11:00` and `P2/D2` at `10:10/11:05`). Performance bias: time `e11e15` (60m) and `e12e16` (55m) serialized inside one case suggests `O1` spent `65m` packing and 2 dispatches sequentially. **Context-dependent**: divergence faithfully flags that `O1` is complex, but harmful if interpreted as rework.

**D9 – Item flattening financial blindness + propagation temptation:** Direct `Item` flattening drops `e01 Create Order`, `e18-e20 Issue Invoice`, `e21,e22,e25,e26 Record Payment` entirely (6 cases ×0 financial events). Naïve Item DFG suggests delivery ends process (`Confirm Delivery` as end activity). If analyst then propagates `V2` to items via `contains` to “fix” loss, they will create inferred `e19,e22,e25` events for `I21,I31`, introducing reverse distortion: `P3`'s invoice appears as two item-invoices. **Informative** about `E2O` incompleteness; **harmful** if propagation is applied silently.

## 4. Traditional versus object-centric analysis portfolio

**Which flattened logs to still create (and why).**

* **Order-flattened** `ocel_flattened_order` – stakeholder lingua franca. Safe only for order-centric questions with deduplication annotation: *median time `Create OrderClose Order` per order* (`O1 2d2h`, `O2 ~2d2h`, `O3 ~2d2h`, `O4 1d2h`), *order participation inventory* (which packages/deliveries touched `O1`). Must never report raw frequencies without correction.
* **Item-flattened** `ocel_flattened_item` – physical fulfillment accuracy. Safe for: *time `Add ItemPackDispatchConfirm` per item* (e.g. `I11 10:0011:0014:00`), *identify split vs bundled items* (`I21+I31` shared `e13,e16,e24`). 
* **Invoice-flattened** `ocel_flattened_invoice` – finance compliance view. Safe for: *installment pattern `IssueRecordRecord` for `V2`*, *time to settlement per invoice*. 
* **Package/Delivery/Payment-flattened** – create only as KPI slices, never as process models: `Package` for `PackConfirm` sojourn, `Delivery` for `DispatchConfirm` on-time delivery, `Payment` as event inventory. Do not run DFG-based variant comparison on length-1/2 traces.

All other questions involving sharing, consolidation, or end-to-end performance require object-centric artifacts.

**Questions requiring object-centric techniques.**

* *Consolidation detection:* Use `pm4py.discover_ocdfg` – its edge annotations show `events`, `unique objects`, `total objects`. Edge `Pack PackageDispatch` will show 4 events but `total objects` > `events` due to sharing, directly revealing `P3,P4` and `D2`. `pm4py.ocel_objects_interactions_summary` quantifies how many orders interact via `D2` (3 orders, 2 packages) and via `V2` (2 orders).
* *Object-type dependencies:* `pm4py.discover_otg` (Object-Type Graph) makes `Order  Item  Package  Delivery` and `Order  Invoice  Payment` paths explicit; divergence hotspots ( `Order–Item` 1:n) become visible.
* *Activity–object participation:* `pm4py.discover_etot` (E-T-O-T graph) shows `Record Payment` relates to `Invoice+Order+Payment` simultaneously, proving financial events are multi-object and explaining why `Item` flattening drops them.
* *Variant equivalence without duplication:* `pm4py.cluster_equivalent_ocel` (or `pm4py.ocel_cluster_equivalent_execution`) clusters executions by object-graph isomorphism, so `O2` and `O3` sharing `P3/e13/e16/e24` cluster together as one execution pattern instead of two duplicated order traces.

**Reconciling contradictory findings.**

1. **Frequency mismatch:** If Order-flattened DFG reports `Dispatch` frequency 6 while OC-DFG reports 3 events with `total objects =6`, trust OC-DFG event count; report flattened frequency as *participations*, not operations.
2. **Performance divergence:** If flattened Order mean `DispatchConfirm` = ~5h (triple-weighted `D2`), but OC-DFG shows `D2` edge `e16e24` =5h for 3 orders at once, report consolidation benefit: “`D2` delivered 3 orders in one 5h transit – per-order average overstates logistics work by `3×`.”
3. **Variant illusion:** Order-flattened variants suggest `O1` repeated `Pack, Dispatch, Confirm`; OC-DFG shows two package lifecycles `P1/P2` executing in parallel via `O2O`. Resolve by narrating split fulfillment, not rework.
4. **Finance-logistics gap:** Item-flattened trace ends at `Confirm`, Invoice-flattened starts at `Issue`; contradiction (“process ends twice”) is evidence of `E2O` gap. Reconcile by propagating-or-linking via OTG, or by declaring scope: Item view = physical subprocess, Invoice view = financial subprocess, end-to-end only in OC-DFG.

## 5. Lead-object decision

**Position C. Reject a single lead object for this process.**

**Decision criteria.**
1. **End-to-end coverage:** lead must preserve >80% of event types without silent propagation; else end-to-end claim is false.
2. **Truthful frequency:** lead’s duplication factor `flattened occurrences / true events` <1.5 for shared event classes.
3. **Distortion transparency:** lead must not create systematic false edges (`PackPack`, `DispatchDispatch`) that require domain experts to unsee.
4. **Conceptual ownership:** lead object type should be the entity that “owns” the process in domain language without equivocation.

| Criterion | Order | Item | Package/Delivery/Invoice/Payment | Verdict |
|---|---|---|---|---|
| Coverage | 100% event types (only needs E2O) |  ~45% (loses all invoicing/payments) | 19-32% truncated | No single type covers both physical and financial subprocesses in direct mode |
| Frequency truth | 6 dispatch occurrences/3 true =2.0×; Pack 6/4=1.5× | 2.5× for D2 edges | 0 distortion but only because they hide sharing | All that cover end-to-end inflate; those that don’t hide |
| False edges | `PackPack`, `DispatchDispatch`, `ConfirmConfirm` for `O1,O3` | Clean per item | Trivial or degenerate DFGs | Any end-to-end flattening fabricates sequencing |
| Ownership | Order is contractual anchor, but `D2` and `V2` are legally owned by delivery/invoice process, not single order | Item is not business case notion | Package/Delivery own last-mile only | Sharing is not exception but pattern: 4/4 orders affected by cross-order objects (`O1D2`, `O2P3/D2/V2`, `O3P3/P4/D2/D3/V2`, `O4P4/D3`) |

**Strongest supporting evidence.** The snapshot’s design makes consolidation central, not peripheral. Counting true events: 4 `Pack`, 3 `Dispatch`, 3 `Issue Invoice`, 4 `Record Payment` (2 of which are installments for one `V2`). Order flattening converts this to 6 `Pack`, 6 `Dispatch`, 4 `Issue`, 6 `Record` – average 1.8× inflation concentrated exactly on the most business-relevant events (dispatch consolidation and invoice consolidation). Simultaneously, flattening on `Item`/`Package`/`Delivery`/`Invoice` loses the complementary subprocess entirely, and `Payment` yields length-1 traces `M1-M4` that make process discovery meaningless. Therefore any single lead either lies about frequency or abandons end-to-end scope. OC-DFG with its three frequency columns (`events`, `unique objects`, `total objects`) is the only artifact that reports both truthfully.

**Strongest counterargument.** Business stakeholders budget, promise, and complain by `Order`. `Order` cases `O1-O4` align with `Close Order e28-e31`, ownership, and SLA. Rejecting a lead risks analytical paralysis: no primary KPI, fragmented dashboards, and difficulty explaining that “the process has no case.” A qualified lead “Order + annotations” – i.e. position B – would give management a familiar anchor while experts use OC-views in background.

**Why B is insufficient and C is required.** Position B (“primary Order + secondary Invoice/Package”) retains dominance rhetoric. In practice “primary” licenses reporting raw Order-flattened frequencies as headlines and relegating corrections to footnotes – precisely the performance bias in D2 (triple-counted dispatch) and DSO distortion in V2 (double-weighted installment) documented above. Given that sharing touches 100% of orders in this snapshot, qualification cannot be secondary; it must be equal. Rejecting dominance forces equal coexistence of `Order`, `Item`, `Package`, `Delivery`, `Invoice` views, with OC-DFG/OTG/ETOT as arbiter. That is position C.

**Residual risk.** 
- Communication overhead: executives lose single “case count =4” comfort metric; we must report *participations* vs *operations* dual metrics.
- Tooling: classic DFG/SLA mining can’t run directly on OCEL; requires PM4Py OC-pipeline and interpretation training.
- Governance: choice of which object interaction is “exception” vs “designed consolidation” remains domain judgment; OC-views surface it but do not decide it.

**Conditions to change decision.**
- If scope is intentionally narrowed to a subprocess, I would elevate the subprocess owner: `Item` or `Package` for warehouse-only analysis, `Invoice` for finance-only, `Order` for contractual SLA without logistics costing.
- If an explicitly governed `E2O+O2O` propagation is agreed and versioned (e.g., every `Record Payment` propagated to constituent `Item`s with `inferred=true` flag), then propagated `Order` or `Item` could become qualified lead because coverage distortion is controlled and traceable.
- If business fact changes and `P3,P4,D2,V2` become rare exceptions (<5% of events) and duplication factor drops <1.1, the distortion cost of Order lead would fall below communication benefit, justifying B.

## 7. Sensitivity and validation plan

**S1 – Remove/down-weight copied shared events (duplication sensitivity).**
*Method:* Build deduplicated Order log: keep `e13,e14,e16,e17,e19,e22,e24,e25,e27` only in earliest case (by `Create Order` timestamp) and drop other copies; or weight each participation `1/n` where `n=convergence degree` (e.g. `e16` weight 0.33 per `O`). Recompute `dfg_order_weighted` and `skeleton_order_weighted`. Compare KPIs: raw mean time `DispatchConfirm`, frequency of `Pack`, number of variants. *Expected outcome:* weighted `Dispatch` frequency drops 63, `Pack` 64, variant diversity collapses because `O2`/`O3` no longer appear distinct due to `V2`. *Validation:* if headline KPI changes >20% after weighting, flag original metric as duplication-biased and report both participation-weighted and operation counts.

**S2 – Direct E2O vs propagated E2O (relation completeness sensitivity).**
