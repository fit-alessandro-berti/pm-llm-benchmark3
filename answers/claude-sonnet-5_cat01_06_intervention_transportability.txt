**Shared mechanisms**: the core queueing logic — running two independent verification activities concurrently reduces the waiting time contributed by their combined service time, provided capacity absorbs the coincident load. This mechanism is structural, not site-specific.

**Site-specific mechanisms**: statutory gating (`originals_required`), legal review with a supplement loop, hard role specialization, and a case-locking IT constraint. These are absent or weaker at Site A and directly block or dilute the transfer of `treatment_parallelization -> true_overlap`.

**Effect modifiers**: `originals_required`, `legal_capacity`, `IT_case_lock`, `case_complexity`, and `role_specialization` all moderate how much of `treatment_parallelization` converts into `true_overlap` and then into `waiting_before_assessment` reduction. They are selection (`S_`) nodes because they are properties of the site population/infrastructure, not of the intervention itself.

**Why a similar diagram  transportability**: a process tree/DFG describes control-flow *possibility*, not the causal mechanism producing cycle-time reduction. Two systems can share a `+` operator while differing in whether concurrency is *achievable* (IT lock), *legal* (originals gating), *resourced* (specialist pools), or *measured accurately* (timestamp artifacts). Structural isomorphism at the model level does not imply equal mediators or equal moderators in the underlying causal graph.

## 6. Candidate Site B intervention

**Eligibility rules**
- Tier 1 (fully eligible for IDDoc parallel start): originals not legally required AND documents received digitally at Register AND not flagged public-sector/high-value.
- Tier 2 (partial parallel): originals legally required — Identity Check may run parallel with Originals Receipt, but Document Check must wait for Originals Receipt completion (statutory). Once originals arrive, Document Check may still run concurrently with any unfinished Identity Check.
- Tier 3 (unchanged sequencing target for phase 1): public-sector/high-value cases — front-end concurrency permitted per Tier 1/2 rule, but Legal Review and Supplement handling remain fully sequential and untouched.

**Concurrent tasks**
- `Identity Check`  `Document Check` — only Tier 1.
- `Identity Check`  `Originals Receipt` — Tier 2/3 (already partially observed; formalize it).
- `Document Check` remains strictly after `Originals Receipt` when required.

**Mandatory statutory prerequisites (non-negotiable)**
- `Originals Receipt  Document Check` when originals required.
- `Document Check  Identity Check  Assessment`.
- `Assessment  Legal Review` for public-sector/high-value.
- `Legal Review  Request Supplement  {Document Check, Assessment}` loop preserved exactly.

**Queue / WIP controls**
- Per-pool WIP caps, tuned separately: Identity  6 open tasks/reviewer (4 reviewers  cap 24 system-wide); Document  5 open tasks/reviewer (7 reviewers  cap 35); Assessment  4 open/assessor (3 assessors  cap 12) with a release throttle so concurrent ID+Doc completions don't burst into Assessment simultaneously (staggered release / small buffer queue).
- Legal Review capacity is a hard constraint (2 reviewers): parallel front-end changes should not increase Legal arrival rate faster than 2-reviewer service rate; monitor and cap AssessmentLegal handoff rate.

**Resource responsibilities**
- Identity pool executes Identity Check only (no cross-training assumed yet — test cross-training in a later phase).
- Document pool executes Document Check only, gated by Originals Receipt where required.
- Assessors and Legal reviewers unchanged in scope, but instrumented for queue-length monitoring.

**Legal review / supplement handling**
- Unaffected by front-end change. Supplement loop re-enters at Document Check (and possibly Identity re-verification if identity data expired) — this loop must remain intact and separately timestamped.

**Logging requirements**
- Enforce true start/stop timestamps at task level (system-generated, not user-entered) to avoid the Site A "overlap-as-artifact" problem.
- Log tier assignment per case, case-lock workaround usage (flag + reason), and queue length at Assessment/Legal at time of arrival.

**Partial-order relation set (POWL-style)**

```text
Register < Identity_Check
Register < Originals_Receipt
Identity_Check < Assessment            (join)
Document_Check < Assessment            (join)

# Statutory gate (data-conditioned XOR on originals_required)
XOR:
  originals_required = True:
      Originals_Receipt < Document_Check
      Identity_Check  Originals_Receipt   (concurrent, unordered)
  originals_required = False:
      Register < Document_Check
      Identity_Check  Document_Check      (concurrent, unordered)

Assessment < XOR(Approve, Reject)          [when legal_review_required = False]

# Legal branch
XOR:
  legal_review_required = True:
      Assessment < Legal_Review
      Legal_Review < XOR(Approve, Reject, Request_Supplement)
      LOOP: Request_Supplement < Document_Check < Assessment < Legal_Review
  legal_review_required = False:
      Assessment < XOR(Approve, Reject)

XOR(Approve, Reject) < Notify
```

**Separating mechanism failure from implementation failure (220 words):**
The pilot is structured so that Phase 1 isolates whether the *IT and organizational mechanism* required for concurrency actually works — i.e., can tasks truly be owned and executed simultaneously despite the legacy case lock? If `true_overlap` (instrumented, audited timestamps) stays near baseline despite the rule change, that is implementation failure: the intervention was never actually delivered, regardless of outcome. Only if `true_overlap` rises substantially do we proceed to interpret cycle-time and queue-length changes as evidence about the *causal mechanism* itself (whether concurrency, once achieved, reduces waiting-before-assessment and cycle time without proportionally increasing rework or shifting bottlenecks downstream). By stratifying on originals-required and legal-review flags, and by monitoring Assessment/Legal queue lengths and rework/supplement loop frequency as secondary outcomes, the design can attribute a null or harmful result specifically: to lock workaround (implementation), to bottleneck shift at Assessment/Legal (a genuine but unfavorable causal mechanism), or to the front-end mechanism simply not applying to a stratum (statutory non-eligibility). This decomposition prevents the same interpretive error made at Site A, where before/after aggregate change was attributed to the intervention despite multiple co-interventions and no verified mediator.

## 8. PM4Py model-construction code

```python
"""
Site A / Site B process model construction, conversion, and soundness checking.
Requires pm4py >= 2.7 (POWL support).
"""

import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# -----------------------------------------------------------------------
# 1. Site A BEFORE / AFTER process trees (pm4py process tree string syntax)
# -----------------------------------------------------------------------

tree_before_str = (
    "-> ( 'Register', 'Identity Check', 'Document Check', "
    "'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
)

tree_after_str = (
    "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), "
    "'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
)

tree_before = pm4py.parse_process_tree(tree_before_str)
tree_after = pm4py.parse_process_tree(tree_after_str)

# -----------------------------------------------------------------------
# 2. Convert Site A trees to accepting Petri nets
# -----------------------------------------------------------------------

net_before, im_before, fm_before = pm4py.convert_to_petri_net(tree_before)
net_after, im_after, fm_after = pm4py.convert_to_petri_net(tree_after)

print("Site A BEFORE net places/transitions:",
      len(net_before.places), len(net_before.transitions))
print("Site A AFTER  net places/transitions:",
      len(net_after.places), len(net_after.transitions))

# -----------------------------------------------------------------------
# 3. Site B candidate model in POWL, encoding partial statutory order
#    NOTE: POWL cannot express the *data-conditioned* XOR on
#    'originals_required' natively as a variable test; here we model
#    the STRUCTURAL union of both paths (a case may follow either),
#    which over-approximates behavior. True data-conditioning must be
#    enforced operationally / in the case-routing layer, not the model.
# -----------------------------------------------------------------------

register = Transition("Register")
identity_check = Transition("Identity Check")
originals_receipt = Transition("Originals Receipt")
document_check = Transition("Document Check")
assessment = Transition("Assessment")
legal_review = Transition("Legal Review")
request_supplement = Transition("Request Supplement")
approve = Transition("Approve")
reject = Transition("Reject")
notify = Transition("Notify")
tau = SilentTransition()

# --- Legal branch with supplement loop ---
# LOOP body: Legal_Review -> (redo: Request_Supplement -> Document_Check -> Assessment -> Legal_Review again)
# Represent as OperatorPOWL LOOP( do=legal_review_success_path, redo=supplement_path )
supplement_redo = StrictPartialOrder(
    nodes=[request_supplement, document_check, assessment]
)
supplement_redo.add_edge(request_supplement, document_check)
supplement_redo.add_edge(document_check, assessment)

legal_loop = OperatorPOWL(Operator.LOOP, [legal_review, supplement_redo])

decision = OperatorPOWL(Operator.XOR, [approve, reject])

# legal branch is itself optional: XOR(tau, legal_loop) -> decision
legal_optional = OperatorPOWL(Operator.XOR, [tau, legal_loop])

# --- Main partial order ---
# Assessment must wait for BOTH Identity_Check and Document_Check (join),
# and Document_Check must wait for Originals_Receipt (statutory gate,
# modeled here as always-required to keep the join sound; the
# not-required path can be modeled as a separate POWL alternative
# and combined with XOR if a fully split model is desired).
po = StrictPartialOrder(
    nodes=[
        register, identity_check, originals_receipt, document_check,
        assessment, legal_optional, decision, notify,
    ]
)

po.add_edge(register, identity_check)
po.add_edge(register, originals_receipt)
po.add_edge(originals_receipt, document_check)      # statutory gate
po.add_edge(identity_check, assessment)             # join input 1
po.add_edge(document_check, assessment)             # join input 2
po.add_edge(assessment, legal_optional)
po.add_edge(legal_optional, decision)
po.add_edge(decision, notify)

site_b_model = po

# -----------------------------------------------------------------------
# 4. Convert POWL model to accepting Petri net
# -----------------------------------------------------------------------

net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b_model)

# -----------------------------------------------------------------------
# 5. Soundness / workflow-net checks
# -----------------------------------------------------------------------

for name, (net, im, fm) in {
    "Site A before": (net_before, im_before, fm_before),
    "Site A after": (net_after, im_after, fm_after),
    "Site B candidate": (net_b, im_b, fm_b),
}.items():
    try:
        is_wfnet = pm4py.check_is_workflow_net(net)
    except Exception as e:
        is_wfnet = f"error: {e}"
    try:
        soundness = pm4py.check_soundness(net, im, fm)
    except Exception as e:
        soundness = f"error: {e}"
    print(f"{name}: workflow_net={is_wfnet}, soundness={soundness}")

# -----------------------------------------------------------------------
# 6. Playout (optional) - sample traces from Site B candidate
# -----------------------------------------------------------------------

log_b = pm4py.play_out(net_b, im_b, fm_b)
print("\nSample Site B playout traces:")
for i, trace in enumerate(log_b[:5]):
    activities = [ev["concept:name"] for ev in trace]
    print(i, activities)

# -----------------------------------------------------------------------
# 7. Modeling limitations (cannot be encoded in this control-flow model)
# -----------------------------------------------------------------------
"""
- Data-dependent legal requirement: whether Legal_Review / originals-gate
  applies depends on case attributes (public-sector/high-value flag,
  originals_required flag). POWL/Petri nets here encode possible orderings,
  not the case-attribute-conditioned branching; this must be enforced by a
  decision layer (DMN / routing rules) feeding into the model, or by
  building two separate sub-models selected at runtime.
- Resource capacity and role specialization (4 identity / 7 document /
  3 assessment / 2 legal reviewers) are not represented; the net treats
  all enabled transitions as instantly executable, ignoring queueing
  and contention. A queueing or simulation layer (e.g., colored/timed
  Petri nets, or a discrete-event simulation on top of this net) is
  required to capture bottleneck shift effects (Section 5).
- Case locking (only one active task owner in the legacy system) is
  an IT/execution constraint, not a control-flow constraint; the model
  assumes true concurrent execution is possible, which may not hold at
  Site B without a system change or workaround protocol.
- Durations/waiting times (e.g., Originals Receipt delay, service
  times) are not modeled; the net only captures ordering and choice,
  not stochastic timing, so cycle-time and p90 effects cannot be read
  directly off this model and require the scenario analysis in Section 5.
"""
```

## 9. Recommendation

**conditional go**

Site B should adopt the *structural mechanism* Site A demonstrated — that concurrent execution of independent verification activities can shrink the waiting time contributed by their combined service time — but should not copy the intervention wholesale, and should not treat Site A's 9-hour median reduction as an estimate of what to expect. That figure is confounded by an API upgrade, two added reviewers, a favorable case-mix shift, daily huddles, and a possibly artifactual overlap measurement; none of these co-interventions are guaranteed at Site B, and Site B carries structural constraints A never had (statutory originals gating for 62% of cases, mandatory legal review with a supplement loop for 40%, strict role specialization, and a case-locking legacy system).

**What transfers**: the concurrency mechanism itself, restricted to where it is statutorily and operationally feasible — Identity Check running in parallel with Originals Receipt for all cases, and IdentityDocument concurrency only for the ~23–30% of cases where originals are not legally required and legal review does not apply.

**What should not be copied**: blanket "start both immediately after Register for every case" — this is legally impossible for 62% of volume and ignores the specialized, capacity-constrained resource pools and the case-lock problem that could make measured "overlap" a data artifact rather than a real effect.

**Subgroup to pilot first**: Tier 1 — digital documents, originals not required, non-legal-review cases. This is the closest analog to Site A's actual operating conditions and lets us test the mechanism with minimal confounding from statutory gates or the legal bottleneck.

**Expected benefits/risks**: plausible 10–25% reduction in waiting-before-assessment for the eligible ~25% of volume, with limited blended median effect and likely negligible-to-adverse p90 effect due to legal/originals-driven tail cases. Principal risks: case-lock workaround producing false overlap with no real gain, and bottleneck shift into Assessment or Legal Review.

**Evidence to trigger expansion/modification/abandonment**: Expand if Phase 1 shows real (audited) `true_overlap` increase, waiting-before-assessment drops without rework/appeal increase, and Assessment/Legal queues remain stable. Modify (e.g., add WIP throttling, fix IT lock, add legal capacity) if bottleneck-shift or lock-workaround signatures appear. Abandon the front-end-only intervention if rework/appeal rise materially or if the case-lock cannot be resolved, making true concurrency infeasible.

1. **Assumption**: Site A's "true overlap" increase (8%71%) partly reflects real concurrent execution, not solely improved timestamp logging. — *Why needed*: without this, the entire mechanism claim collapses to a measurement artifact. — *How to test*: audit a sample of Site A cases with independent time-stamped system logs vs. self-reported task events. — *Consequence if false*: Site A's intervention produced no real mechanism to transport; Site B pilot should be reframed around logging improvement, not concurrency.

2. **Assumption**: Site B's reviewer pools have enough slack capacity to absorb simultaneous Identity/Document task creation without immediate queue buildup. — *Why needed*: parallelization only saves time if capacity, not just ordering, allows concurrent progress. — *How to test*: pilot Phase 1 queue-length monitoring per pool under Tier 1 cases only. — *Consequence if false*: waiting time shifts rather than shrinks (bottleneck-shift scenario dominates).

3. **Assumption**: The legacy case-locking system can be worked around (or fixed) reliably enough to permit genuine concurrent task ownership. — *Why needed*: this is the mechanical precondition for the entire intervention. — *How to test*: Phase 1 feasibility trial measuring true concurrent task-open intervals vs. lock-workaround frequency. — *Consequence if false*: intervention as specified cannot be delivered; only IdentityOriginals-Receipt (which doesn't need dual case ownership at the Document stage) remains feasible.

4. **Assumption**: The 62%/38% split between originals-required and not-required cases is stable and can be reliably determined at Register. — *Why needed*: eligibility routing depends on this flag being known upfront. — *How to test*: audit historical DFG data for cases where the originals-required flag was corrected after Register. — *Consequence if false*: eligibility misclassification causes cases to be prematurely routed to parallel Document Check in violation of statute.

5. **Assumption**: Legal Review capacity (2 reviewers, 40% of volume) will not be materially increased during the pilot. — *Why needed*: this determines whether front-end speedups translate into back-end congestion (Scenario 5). — *How to test*: confirm staffing plan with management before pilot start. — *Consequence if false*: legal/rework congestion scenario is less likely; p90 risk is lower than projected.
