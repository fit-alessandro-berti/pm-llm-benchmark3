### 3.4 Consequential event whose relation set drives convergence/divergence
- **Event `e6` (Reserve Stock)** and **Event `e7` (Pack Package)** are jointly referenced by both Orders (O100 and O200) because P1 contains items from both orders. Their E2O relations link the event directly to Items I1/I3 and Package P1, creating the first crossorder link in the E2O view. Any flattening that ignores the shared qualifier “jointly” would duplicate the reservation/packing perception for the two orders; the O2O containment already captures the logical grouping, so the E2O relations serve as the observable fact that enables correct divergence analysis.

## 4. Expected flattened behaviour
For each required object type the flattening should produce a trace list where:

- **Order** – traces follow `Create Order  Add Item(s)  Close Order`. Because OrderO100 receives Add Item events e2/e3 and OrderO200 receives e5, the flattened log for OrderO100 contains e1e3 and e16e17 (close), while OrderO200 contains e4e5 and e16e17. The shared “Reserve Stock” (e6) and “Pack Package” (e7) events appear in the Orderflattened traces only indirectly via O2O containment; the flattening copies the event only once per order it directly mentions (O100 for e6/e7 via Item links, O200 for e6/e7 via Item I3). No event is omitted that directly involves the order (e.g., Close Order), but logistics events (Dispatch) are not part of the Order trace because they do not directly act on the order object in the E2O sense.

- **Package** – traces start with the Pack Package event (e7 or e8) and end with Dispatch (e9 or e10). Because PackageP1 participates in OrderO100 (via I1) and OrderO200 (via I3), the flattened Package trace will contain e7 (pack P1), e9 (dispatch D1) and may also contain the shared reserve event e6 if the flattening policy includes “qualifierbased inclusion”; with our conservative policy (include only events whose qualifier directly mentions the package or its items) e6 appears in the P1 trace because it reserves the items that will be packed. P2’s trace contains e8 and e10.

- **Delivery** – traces begin with Dispatch (e9/e10) and end with Confirm Delivery (e13/e14). The flattening copies the dispatch event and the corresponding confirm; it does **not** copy Create Order or Add Item events because they do not directly act on the delivery object.

- **Invoice** – traces start with Issue Invoice (e11) and end with the two payment events (e12 & e15) followed by Close Order events that may reference the invoice indirectly. Because Payment events are linked to the invoice via E2O qualifier “records”, they appear in the invoice’s flattened trace. The flattening does not copy Orderclose events unless they explicitly involve the invoice (they do not), so the invoice trace is `e11  e12  e15` (chronological order guaranteed by timestamps).

- **Why flattening on Payment would be weak** – Payment events are linked only to the Invoice and the Payment object. They lack direct links to Orders or Packages, and their qualifier (“records”) does not indicate involvement of other objects. Flattening on Payment would therefore produce a very short trace (`Record Payment  Record Payment`) that loses the causal link to the preceding Reserve/Pack events and to Order closing, making it impossible to recover the logical flow “reserve  pack  dispatch  invoice  pay”. Thus Payment is **not** used for the four required flattening analyses.

## 5. Expected objectcentric structures
- **OCDFG** – should show edges from `Create Order`  `Add Item` (for each order), `Reserve Stock`  `Pack Package`, `Pack Package`  `Dispatch Package`, `Issue Invoice`  `Record Payment`. Because P1 contains items from both orders, the OCDFG will have a node for PackageP1 and nodes for OrderO100 and OrderO200; edges from `Add Item` (for I1/I2) to `Pack Package` (P1) and from `Add Item` (for I3) to `Pack Package` (P1) will appear, reflecting the crossorder involvement. No edge will directly connect OrderO100 to OrderO200 because the narrative does not describe an orderlevel interaction; the shared logistics is captured via the Package node.

- **OTG (Objecttype Graph)** – nodes for each object type (Order, Item, Package, Delivery, Invoice, Payment) and edges for containment (`Order  Item`, `Package  Item`, `Delivery  Package`, `Invoice  Order`, `Payment  Invoice`). The OTG will reflect the hierarchical containment and the bidirectional billing edge (Invoice  Order and Order  Invoice are both present via O2O). The OTG should not contain edges derived from event sequences (e.g., Order  Package) because O2O only stores static containment; eventlevel edges appear in the OCDFG.

- **ET–OT (EntityType–Object Graph)** – merges entity types with object instances; should show that P1 (Package instance) interacts with I1, I3 and D1; V1 interacts with O100, O200 and Payments. The graph will capture the fact that the same invoice is linked to two orders and two payments, but it will not doublecount the shared reserve/pack relationship.

- **Objectcentric Petri net** – places tokens on Order, Item, Package, Delivery, Invoice, Payment instances at appropriate moments (e.g., Order token after Create Order, Item tokens after Add Item, Package token after Pack Package, Delivery token after Dispatch, Invoice token after Issue Invoice, Payment tokens after Record Payment). Enabled transitions reflect activities that consume/produce tokens consistent with O2O qualifiers (e.g., `Pack` consumes Item tokens and produces Package token). Because P1 uses items from both orders, the net will have parallel flows but no conflict because timestamps order the events (reserve  pack  dispatch). The net should be consistent and not infer additional synchronization beyond the given timestamps.

- **Objectinteractions summary** – should list for each object type the most frequent interacting types (e.g., Order interacts with Item (contains) and Invoice (bills); Package interacts with Item (packs) and Delivery (carries); Invoice interacts with Order (bills) and Payment (settles)). It will highlight the crossorder involvement of P1 (interacts with Item types from both O100 and O200) and the twopayment settlement of V1.

All structures explicitly mention P1, V1, M1, M2, O100, and O200 as required.

## 6. Modeling alternatives (defensible E2O policies)

1. **Sourceminimal relations** – E2O relations contain **only** the direct object that the event creates or modifies (e.g., `Create Order`  Order, `Add Item`  Item, `Pack Package`  Package). No secondary object links (e.g., `Pack Package` does **not** link to the Items it packs). O2O then captures all containment (`Order contains Item`, `Package packs Item`). This reduces relation count but requires downstream analysts to reason about containment via O2O when linking events to items. Tradeoff: flattening on Order will see only Create/Add/Close; Package trace will miss item involvement unless O2O is consulted.

2. **Full operational involvement** – E2O relations include **all** objects that the event logically touches (e.g., `Pack Package` links to Package **and** all Items it packs; `Reserve Stock` links to Items I1/I3). O2O still stores static containment but may also include derived links like “Order contains Package” inferred from the fact that a package packs items belonging to the order. This mirrors the intuitive operational view and makes flattening on Order automatically include Pack events for its items. Tradeoff: relation rows increase (e.g., Pack creates three rows), and O2O may contain extra containment edges that could be confused with source facts if not clearly labeled; however the qualifier vocabulary remains consistent.

3. **O2Opropagated analytical relations** – Keep E2O relations minimal (only the primary object, e.g., Create Order  Order). After constructing OCEL, run a lightweight propagation step that adds E2O rows for derived containment (e.g., “Order contains Package” if a Package packs an Item that belongs to the Order) and for “Payment completes settlement” after the second payment. These propagated rows are marked with a special qualifier `analytical`. Flattening then uses the propagated relations for a *derived* view (useful for higherlevel process mining that wants to see orderlevel package involvement without duplicating event rows). Tradeoff: analytical rows are not part of the sourcesystem fact table; they are clearly flagged (`analytical`) and separate from `ocel:qualifier` used for direct observations. This avoids conflating source facts with derived analytics.

Each alternative respects the mandatory OCEL column set and does **not** change the underlying business narrative; they only differ in granularity of E2O vs. O2O vs. analytical propagation.

## 7. Failure modes (8)

1. **Relation inflation** – adding duplicate E2O rows for the same qualifier (e.g., linking Package to the same Item twice) inflates relation counts and can cause false positive edges in flattening.
2. **Missing direct E2O links** – omitting a required E2O row (e.g., forgetting `Reserves` relation for Items I1/I3) leads to loss of the observable joint reservation fact, weakening divergence detection between the two orders.
3. **Treating O2O propagation as observation** – mistakenly interpreting O2O “contains” edges as events; this would incorrectly place “Order contains Package” into the event log and create spurious traces.
4. **Duplicate shared events after flattening** – if flattening copies a shared event (e.g., Reserve Stock) for both orders without deduplication, the flattened log for each order would contain two copies of the same event ID, breaking log consistency and DFG discovery.
5. **Ambiguous payment allocation** – recording only “Record Payment” without linking to the specific payment amount or invoice qualifier could lead to merging M1 and M2 into a single payment node, obscuring the twostep settlement.
6. **Overly short Payment traces** – flattening on Payment would produce a trace of just the two payment events, losing causal links to Reserve/Pack/Dispatch, making it appear that payment occurs before logistics.
7. **Constructor/API version mismatch** – using `OCEL(...)` from a pre2.0 API or calling `pm4py.discover_*` functions that have different signatures (e.g., requiring a log instead of an OCEL object) raises an exception; the pipeline catches it but prints a warning, which may hide the mismatch if the fallback stub is silently used.
8. **False total order for simultaneous events** – although the example has no exact ties, if timestamps were equal the flattening/DFG discovery might impose an arbitrary order; the pipeline uses the provided UTC timestamps, which are strictly increasing, so this mode does not occur here but would be a risk in real data.

(Additional subtler modes could include inconsistent qualifier spelling, missing timezone info, or orphan object IDs in O2O; the validation steps listed in the pipeline catch many of them.)
