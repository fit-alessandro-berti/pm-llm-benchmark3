## 1. Modeling assumptions

- **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.
- **E2O qualifier vocabulary:**
  - `created`: a new object is created by the event.
  - `added_to_order` / `order_receives_item`: item is added to an order.
  - `stock_reserved`: stock-reservation event directly affects item/order.
  - `packed`: item is packed; `order_fulfilled`: order is affected by packing.
  - `dispatched`: package is dispatched; `order_dispatched`: order is affected by dispatch.
  - `delivery_confirmed`: delivery/package is confirmed; `order_delivered`: order is affected by delivery confirmation.
  - `billed`: order is billed; `payment_received`: invoice receives payment.
  - `closed`: order is closed.
- **O2O direction conventions:** the first column `ocel:oid` is the source/owner/payer/biller; the second column `ocel:oid_2` is the target/member/recipient. Examples: `Order -> Item` for `contains`, `Package -> Item` for `packs`, `Delivery -> Package` for `carries`, `Invoice -> Order` for `bills`, `Payment -> Invoice` for `partially_settles`.
- **Direct source vs propagated relations:** Logistics events relate directly to `Order` and `Package`/`Delivery`, but not directly to `Item` unless an item is explicitly acted on. Financial payment events relate directly only to `Payment` and `Invoice`; invoice issuance also relates to `Order`. I do **not** materialize O2O-propagated rows in `relations`. Static O2O facts stay in `o2o`; any analytical propagation would need to be computed explicitly and labelled as derived, not source-system observation.
- **PM4Py version assumption:** I assume the constructor form `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available. If a PM4Py version exposes `OCEL` from `pm4py` instead of `pm4py.objects.ocel.obj`, replace only the import line; the data semantics do not change.

## 3. Data-model audit

### Object types and objects

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |

### O2O qualifiers and cardinality

| Qualifier | Direction | Edges | Cardinality in this dataset |
|---|---|---|---|
| `contains` | Order -> Item | O100-I1, O100-I2, O200-I3 | one order contains many items; each item belongs to one order |
| `packs` | Package -> Item | P1-I1, P1-I3, P2-I2 | one package packs many items; each item currently packed in one package |
| `carries` | Delivery -> Package | D1-P1, D2-P2 | one-to-one |
| `bills` | Invoice -> Order | V1-O100, V1-O200 | one invoice bills many orders |
| `partially_settles` | Payment -> Invoice | M1-V1, M2-V1 | many payments settle one invoice |

### Activities and touched object types

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Item, Order |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery, Order |
| Issue Invoice | Invoice, Order |

| Confirm Delivery | Delivery, Package, Order |

### Consequential relation sets

- **e7 Pack Package P1** is the most consequential. It touches `Package`, two `Item`s, and two `Order`s. It creates convergence of I1 and I3 from O100/O200 into P1 and later divergence when D1/P1 affects both orders.
- **e6 Reserve Stock** is cross-order and cross-item: O100/O200 and I1/I3 are all touched by one shared event.
- **e11 Issue Invoice V1** links both orders to one invoice, creating financial convergence.
- **e12/e15 Record Payment** link M1/M2 only to V1. This is deliberately sparse and means payments do not directly touch orders.

## 4. Expected flattened behavior

These predictions assume `pm4py.ocel_flattening` builds one traditional trace per object of the requested type from events in which that object occurs in `relations`.

### Order flattening

- **Approximate trace shape:**
  - O100: Create Order, Add Item, Add Item, Reserve Stock, Pack Package, Pack Package, Dispatch Package, Dispatch Package, Issue Invoice, Confirm Delivery, Confirm Delivery, Close Order.
  - O200: Create Order, Add Item, Reserve Stock, Pack Package, Dispatch Package, Issue Invoice, Confirm Delivery, Close Order.
- **Copied shared events:** e6 Reserve Stock, e7 Pack Package P1, e9 Dispatch Package P1, e11 Issue Invoice V1, and e13 Confirm Delivery D1 appear in both O100 and O200 traces.
- **Omitted lifecycle aspects:** Payments M1/M2 are absent because they do not directly relate to Orders. Package and delivery identities are collapsed into repeated activities.
- **Likely DFG edges:** Create Order  Add Item; Add Item  Reserve Stock; Reserve Stock  Pack Package; Pack Package  Pack Package; Pack Package  Dispatch Package; Dispatch Package  Dispatch Package; Dispatch Package  Issue Invoice; Issue Invoice  Confirm Delivery; Confirm Delivery  Confirm Delivery; Confirm Delivery  Close Order.
- **Misleading interpretations:** O100 appears to have two separate pack/dispatch/delivery confirmations rather than two packages/deliveries. The orders also appear financially unclosed because payments are not present.

### Package flattening

- **Approximate trace shape:**
  - P1: Pack Package, Dispatch Package, Confirm Delivery.
  - P2: Pack Package, Dispatch Package, Confirm Delivery.
- **Copied shared events:** none within the Package type.
- **Omitted lifecycle aspects:** order, item, invoice, and payment context are omitted.
- **Likely DFG edges:** Pack Package  Dispatch Package  Confirm Delivery.
- **Misleading interpretations:** packages look like standalone objects; the fact that P1 combines items from two orders is invisible in the flattened trace.

### Delivery flattening

- **Approximate trace shape:**
  - D1: Dispatch Package, Confirm Delivery.
  - D2: Dispatch Package, Confirm Delivery.
- **Copied shared events:** none within the Delivery type.
- **Omitted lifecycle aspects:** package contents, orders, invoice, and payment outcome are omitted.
- **Likely DFG edges:** Dispatch Package  Confirm Delivery.
- **Misleading interpretations:** delivery traces look like a two-step process with no order or package context.

### Invoice flattening

- **Approximate trace shape:**
  - V1: Issue Invoice, Record Payment, Record Payment.
- **Copied shared events:** none within the Invoice type.
- **Omitted lifecycle aspects:** orders, items, packages, and deliveries are omitted.
- **Likely DFG edges:** Issue Invoice  Record Payment; Record Payment  Record Payment.
- **Misleading interpretations:** the trace shows two payments but not that they are partial payments, nor which order they settle.

### Why Payment flattening is especially weak

Each Payment object appears only in its own `Record Payment` event. M1 has a one-event trace; M2 has a one-event trace. There is no preceding or succeeding activity inside the Payment trace, so DFG discovery yields little or no structure. The Payment flattening cannot show invoice settlement progress or order context unless O2O propagation is performed explicitly.

## 5. Expected object-centric structures

- **OC-DFG:** The object-centric DFG should show object-specific flows without flattening duplication. For P1, the flow is `Pack Package  Dispatch Package  Confirm Delivery`; for P2, the same. It will show e6 Reserve Stock as a shared synchronization point across I1, I3, O100, and O200. It will show e7 Pack Package P1 as a convergence where I1 and I3 from two orders meet. V1 is a financial convergence for O100/O200. M1 and M2 are separate payment objects both pointing to V1, not directly to O100/O200.

- **OTG:** The object graph should reveal static relationships: O100 contains I1/I2; O200 contains I3; P1 packs I1/I3, connecting two orders to one package; P2 packs I2; D1 carries P1; D2 carries P2; V1 bills O100/O200; M1/M2 partially settle V1. This highlights P1 and V1 as key convergence objects.

- **ET–OT graph:** This should show which activities synchronize object types. `Reserve Stock` touches Item and Order; `Pack Package` touches Package, Item, and Order; `Dispatch Package` touches Package, Delivery, and Order; `Issue Invoice` touches Invoice and Order; `Record Payment` touches Payment and Invoice. It makes explicit that payment recording does not directly touch Order.

- **Object-centric Petri net:** The discovered net should have typed places and transitions that can represent shared objects without forcing a single total order. For example, it can represent P1 being produced from I1 and I3 in the context of O100/O200, then dispatched and confirmed. It can also represent M1 and M2 as two payment tokens settling V1. The exact net is not uniquely determined; multiple valid nets may be discovered.

- **Object-interactions summary:** The summary should highlight strong interactions around P1, V1, O100, and O200. P1 interacts with I1, I3, O100, O200, and D1. V1 interacts with O100, O200, M1, and M2. M1 and M2 interact only with V1, not with Orders directly. This helps identify where the process converges and diverges.

## 6. Modeling alternatives

1. **Source-minimal relations**
   - Only objects explicitly named in each event are related.
   - Dispatch would touch only Package and Delivery; Confirm Delivery would touch Delivery and Package; payments would touch Payment and Invoice.
   - Discovery result: smaller relation table, less duplicated order-level context, but Order flattening would omit dispatch/delivery confirmation and appear truncated. OC-DFG would lose direct Order-to-Delivery edges.

2. **Full operational involvement**
   - Every event touches all objects transitively reachable through O2O. For example, Dispatch P1 touches D1, P1, I1, I3, O100, and O200; Record Payment touches M1, V1, O100, and O200.
   - Discovery result: richer flattened traces and denser object-centric graphs, but high relation inflation. It blurs the distinction between observed source facts and analytically derived involvement.

3. **O2O-propagated analytical relations**
   - Keep source E2O relations minimal or direct, then explicitly compute a separate derived relation table by propagating over `o2o`, labelling derived rows with a prefix such as `derived:`.
   - Discovery result: provenance is preserved. Users can discover both native and propagated views. The derived view can fill gaps such as payments on Order traces, but must be interpreted as analytical enrichment rather than raw observations.

## 7. Failure modes

1. **Relation inflation:** Adding every possible object to every event creates a dense graph and misleading synchronization.
2. **Missing direct E2O links:** If dispatch or confirmation is not related to Orders, Order flattening becomes too sparse and omits important lifecycle steps.
3. **Treating O2O propagation as observation:** Static O2O edges are not event observations. Propagating them into `relations` without labels invents event-object links.
4. **Duplicate shared events after flattening:** Shared events such as e7 appear in multiple order traces, which can look like repeated execution when flattened.
5. **Ambiguous payment allocation:** M1 and M2 settle V1 but are not allocated to O100/O200. Forcing allocation would create arbitrary order-level payment facts.
6. **Overly short Payment traces:** Payment flattening produces one-event traces, so DFG/log-skeleton analysis on Payment is weak or empty.
7. **Constructor/API version mismatch:** PM4Py versions differ in where `OCEL` lives or what discovery functions return. Isolate the constructor and imports.
8. **False total order for same-time events:** Sorting by timestamp can impose a total order even when events are unordered. This example has no ties, but the risk remains in general.
9. **Timezone-naive timestamps:** Using naive timestamps can mix timezones and break chronological analysis. All timestamps here are UTC-aware.
10. **Duplicate relation rows:** Duplicate E2O rows can inflate object-type activity frequencies and OC-DFG edges. Validation should reject them.
