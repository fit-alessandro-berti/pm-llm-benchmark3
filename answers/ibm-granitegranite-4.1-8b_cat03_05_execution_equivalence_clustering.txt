## 1. Equivalence design space

### 1.1 Activitysequence equivalence  
**Definition**: Two executions are *activitysequence equivalent* if, after normalising event order (allowing simultaneous events to be ordered arbitrarily), each event type (Create, Add Item, Pack, Dispatch, Issue Invoice, Record Payment) occurs exactly once in the same temporal order, irrespective of object identifiers.  
**Preserved**:  
- Linear order of activity types.  
- Number of occurrences of each activity pattern.  
**Discarded**:  
- Specific object IDs (local or external).  
- Detailed multiplicity of items within a package beyond the number of Pack/Dispatch pairs.  
- Qualifiers or lifecycle motifs (e.g., `removed_before_dispatch`).  
**Properties**: Reflexive, symmetric, transitive (by construction).  
**Concurrency handling**: Model concurrent events as a partially ordered relation (e.g., parallel edges) and require a linear extension that preserves the partial order constraints.

### 1.2 Typed structural equivalence under identifier renaming  
**Definition**: Two executions are *typed structurally equivalent* if they contain the same set of object types, each object appears exactly once with the correct cardinalities (e.g., one Create Order, one Issue Invoice per Order), and the event graph (Create  Add Item*  Pack*  Dispatch*  Invoice  Payment) is isomorphic after renaming of local identifiers. External identifiers (`EXT-*`) are preserved as relations of containment.  
**Preserved**:  
- Object types and their lifecycle (Creation, Addition, Packing, Dispatch, Billing, Payment).  
- Relative multiplicities (e.g., two Add Item events per Order, one Issue Invoice per Order).  
- Externalobject relationships (`EXT-*` flag).  
**Discarded**:  
- Exact local IDs (I11, I21, etc.).  
- Order of item addition (Add Item order can differ).  
**Properties**: Reflexive, symmetric, transitive.  
**Concurrency handling**: Uses a strict isomorphism that matches each event with a counterpart; concurrent Pack/Dispatch pairs must map bijectively.

### 1.3 Businesssemantic equivalence (using multiplicities, shared external objects, qualifiers, lifecycle motifs)  
**Definition**: Two executions are *businesssemantically equivalent* if they represent the same commercial intent, identified by:  
1. **Multiplicities** – e.g., one Order  one Invoice  one Payment; multiple Items per Order; multiple Packages per Order when split.  
2. **Externalobject sharing** – use of EXTprefixes (crossorder packaging, invoicing, or payment sharing).  
3. **Qualifiers / lifecycle motifs** – presence of `removed_before_dispatch`, `partial_settlement`, `return_and_repump`, etc.  
4. **Motif preservation** – sequences that model a full lifecycle (Create  Pack  Dispatch  Invoice  Payment) versus variants that include Return/RePack or SplitDelivery patterns.  
**Preserved**:  
- Businesslevel intent (order fulfillment, partial payment, crossorder sharing, returns).  
- Qualitative flags that affect liability (e.g., item replacement).  
- Motif structure (splitpackage vs wholepackage).  
**Discarded**:  
- Exact local identifiers, exact timestamp ordering beyond motif constraints, and homogeneous details of parallel events that do not affect intent.  
**Properties**: Reflexive, symmetric, transitive (identification of same intent yields transitivity).  
**Concurrency handling**: Allows parallelism as long as the highlevel motif (e.g., “both items dispatched separately”) remains intact; otherwise, the motif is refined to capture the nuanced business behavior.

*(Optional 4th relation could be “financialstructural equivalence” focusing solely on invoice and payment graph isomorphism, but the three above suffice for the task.)*

## 2. Canonical signatures  

We adopt *businesssemantic equivalence* as the preferred relation.  
The canonical signature `Sig(execution)` must:

1. **Strip local IDs** – replace all identifiers with type placeholders (`Order:__`, `Item:__`, `Package:__`, `Delivery:__`, `Invoice:__`, `Payment:__`, `EXT-...` for external objects).  
2. **Encode cardinalities** – count occurrences of each activity type and note whether they appear as a single unit or as a set (e.g., `AddItemCount`, `PackCount`, `DispatchCount`).  
3. **Capture externalobject relations** – record any `EXT-` prefixes and their parent orders.  
4. **Mark qualifiers** – list flags such as `replaced_item`, `partial_payment`, `return_cycle`, etc., derived from the O2O notes.  
5. **Ignore ordering of homogeneous steps** – e.g., the order of two `AddItem` events is not encoded; only that there are *N* such events.  
6. **Represent motif patterns** – label a motif as `FULL` (Create  Pack(s)  Dispatch(s)  Invoice  Payment) or `SPLIT_DELIVERY`, `PARTIAL_PAYMENT`, `RETURN`, etc.

**Pythonlike pseudocode**

```python
def canonical_signature(execution):
    sig = {}
    # 1. map identifiers to placeholders
    def ph(id):
        if id.startswith('EXT'):
            return f'EXT-{id}'
        return f'{sig[type_of_object(id)]}-__'
    
    # 2. count activity occurrences (typeagnostic)
    sig['ActivityCounts'] = {
        'Create': 0,
        'AddItem': 0,
        'Pack': 0,
        'Dispatch': 0,
        'IssueInvoice': 0,
        'RecordPayment': 0
    }
    sig['ExternalRefs'] = set()
    sig['Qualifiers'] = set()
    
    prev_event = None
    for act in execution['events']:
        act_type, payload = act['type'], act['payload']
        sig['ActivityCounts'][act_type] += 1
        
        # external object handling
        for obj in payload.values():
            if obj.startswith('EXT'):
                sig['ExternalRefs'].add(obj)
        
        # qualifiers are given in O2O notes; we map them here
        if act_type == 'Dispatch' and payload.get('qualifier'):
            sig['Qualifiers'].add(payload['qualifier'])
        
        # optional: track motif via order of activity types
        if prev_event and prev_event['type'] != act_type:
            motif = infer_motif(prev_event['type'], act_type)
            sig.setdefault('MotifPath', []).append(motif)
        prev_event = act
    
    # 3. replace concrete IDs with placeholders in payload (for debugging)
    sig['PlaceholderPayload'] = {
        k: {ph(v): ph(k) for v in payload.values()}
        for k, payload in execution.get('specific_id_map', {}).items()
    }
    
    return sig
```

The signature is deterministic: renaming local IDs does not affect it, while businesslevel differences (e.g., split delivery) change the `MotifPath` or `Qualifiers`.

## 4. Cluster interpretations  

### S1 – Full standard fulfillment (X1, X2)  
**Signature**: `{Create:1, AddItem:2, Pack:1, Dispatch:1, IssueInvoice:1, RecordPayment:1}; Motif: FULL; Qualifiers: none.**  
**Business behavior**: A single order is created, items are added, packed in one package, dispatched, invoiced, and fully paid in one transaction.  
**Operational risks/opportunities**: Low risk, high opportunity for automation; ideal for highvolume, lowcomplexity workflows.  
**Traditional flattening**: Flattening by raw identifiers would appear identical, but ignoring the *packagelevel* distinction would miss the possibility of split packages.  
**Stability**: Very stable; renaming or minor timing variations do not affect classification.

### S2 – Splitpackage, consolidated delivery (X3)  
**Signature**: Same activity counts; `PackCount=2`, `DispatchCount=1`; `Motif: FULL` with explicit note `split_package_consolidated`.  
**Business behavior**: Order contains multiple items packed separately but shipped together in a single delivery.  
**Risks/opportunities**: May incur higher logistics cost but reduces delivery handling overhead.  
**Traditional flattening** would collapse the two packs into a single observable event, losing the insight into internal packaging strategy.  
**Stability**: Stable as long as the pattern of “multiple packs  single dispatch” persists.

### S3 – Splitpackage, split delivery, partial payment (X4)  
**Signature**: `PackCount=2`, `DispatchCount=2`, `RecordPaymentCount=2`; qualifier `partial_payment`.  
**Business behavior**: Items are sent individually, and payment is split across two transactions (e.g., prepayment for first item, final for second).  
**Risks/opportunities**: Enables flexible financing models but introduces reconciliation complexity.  
**Traditional flattening** would treat the two dispatches as a single delivery if ordering were ignored.  
**Stability**: Stable if partialpayment logic remains unchanged; otherwise, remerging could shift the cluster.

### S4 – Interorder package sharing (X5)  
**Signature**: ExternalRefs present (`EXT-IA`, `EXT-OA`); `CrossPackage: True`.  
**Business behavior**: A package combines items from a primary order and an external order, simplifying logistics for both.  
**Risks/opportunities**: Reduces packaging waste but may complicate billing and liability attribution.  
**Traditional flattening** would see two distinct packs but would miss the shared external relationship.  
**Stability**: Stable under consistent crossorder packaging policies.

### S5 – Interorder invoicing sharing (X6)  
**Signature**: `CrossInvoice: True` (invoice includes `EXT-OB`).  
**Business behavior**: Billing extends beyond the primary order, possibly for a subscription bundle or multicustomer invoice.  
**Risks/opportunities**: Improves revenue visibility but may require joint compliance checks.  
**Traditional flattening** would treat the invoice as belonging solely to `Order:O6`.  
**Stability**: Stable if invoicing rules remain tied to the primary order’s lifecycle.

### S6 – Item replacement/removal before dispatch (X7)  
**Signature**: Qualifier `removed_before_dispatch`.  
**Business behavior**: One item is substituted or withdrawn after the initial packing but before dispatch, often due to defect or customer request.  
**Risks/opportunities**: Provides flexibility for error correction but may delay dispatch.  
**Traditional flattening** would simply see two AddItem events, missing the replacement nuance.  
**Stability**: Stable as long as the replacement workflow is consistently applied.

### S7 – Return and repack workflow (X8)  
**Signature**: Additional `Return`, `Inspect` events; `return_cycle` qualifier; `PackCount=2`.  
**Business behavior**: Order undergoes a return of one item, inspection, repackaging, and a second dispatch.  
**Risks/opportunities**: Supports customer satisfaction but adds handling steps and inventory churn.  
**Traditional flattening** would collapse the return into a simple dispatch change, obscuring the servicelevel aspect.  
**Stability**: Stable under standard return policies; variance in inspection criteria could shift the cluster if it introduces new qualifiers.

## 5. Borderline cases  

### X1 vs X2  
- **Activitysequence equivalence**: Identical (same sequence, same counts).  
- **Typedstructural equivalence**: Identical after renaming; both satisfy T1.  
- **Businesssemantic equivalence**: Identical; signatures are the same.  
- **Borderline**: None; they are unequivocally in S1.  

### X1 vs X5 (crossorder packaging)  
- **Activitysequence equivalence**: Identify (same sequence of activity types, same counts).  
- **Typedstructural equivalence**: Diverges – X1 has no external objects, X5 introduces `EXT-OA` and `EXT-IA`. Thus T1 vs T2.  
- **Businesssemantic equivalence**: Different – S1 vs S4.  
- **Borderline**: If identifiers were considered purely syntactic, one might erroneously cluster them together (ignoring `EXT-` flags). The qualifier `EXT-` forces separation, but a naïve flattening ignoring externality would merge them.  

### X1 vs X6 (crossorder invoicing)  
- **Activitysequence equivalence**: Same (identical sequence, counts).  
- **Typedstructural equivalence**: Same (both satisfy T1).  
- **Businesssemantic equivalence**: Different – S1 vs S5 (different invoice sharing).  
- **Borderline**: Ignoring invoicesharing qualifiers would again merge them, missing the financial coupling.  

### X1 vs X7 (replacement semantics)  
- **Activitysequence equivalence**: Same (identical counts).  
- **Typedstructural equivalence**: Same (both T1).  
- **Businesssemantic equivalence**: Different – S1 vs S6.  
- **Borderline**: A system that only looks at the number of AddItem events would not detect the replacement qualifier; only detailed O2O notes reveal the distinction.  

### X3 vs X4 (splitpackage vs splitdelivery)  
- **Activitysequence equivalence**: Same overall sequence, but **Pack**/ **Dispatch** ordering differs (X3: two Packs, one Dispatch; X4: Pack, Dispatch, Pack, Dispatch).  
- **Typedstructural equivalence**: Both satisfy T1 (same counts).  
- **Businesssemantic equivalence**: Different – S2 vs S3 (different dispatch granularity).  
- **Borderline**: If one only recorded “number of Pack and Dispatch events” and ignored their pairing, the two could be indistinguishable, conflating splitpackageconsolidated with splitdelivery.  

### X4 vs X8 (partial payment vs return/repack)  
- **Activitysequence equivalence**: Both have two Pack, two Dispatch, and additional Return/Inspect steps for X8; counts differ (X4 has two RecordPayment; X8 has two RecordPayment + Return + Inspect).  
- **Typedstructural equivalence**: X4 is T1 (single invoice); X8 is T1 with extra Return/Inspect events  still T1 but enriched.  
- **Businesssemantic equivalence**: Different – S3 vs S7.  
- **Borderline**: If the Return/Inspect events were omitted from analysis, X8 could be misclustered with S3 because the core “splitpackage, splitdelivery” motif remains, losing the return lifecycle insight.  

Thus, the choice of equivalence notion determines where borderline cases fall. Activitysequence equivalence often merges divergent business intent, while businesssemantic equivalence preserves it; the middle ground (typedstructural) preserves structure but may miss finegrained intent like replacement or return cycles.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Information preserved by PM4Py’s `cluster_equivalent_ocel`
- **O2O key structure**: Relations between objects (e.g., Order  Package, Package  Delivery) are retained, allowing detection of shared external objects (`EXT-*`) and lifecycle edges.
- **Disclosed identifier blobs**: Raw local IDs are kept in the OCEL, enabling finegrained equivalence if needed.
- **Event sequence & multiplicity**: The chronological graph and counts of events are preserved, supporting activitysequence and typedstructural methods.

### Why raw identifiers lead to toofine clusters  
When every identifier is treated as distinct, two logically identical processes (e.g., X1 and X2) produce different node IDs, causing `cluster_equivalent_ocel` to output separate clusters. The identifier noise inflates the partitioning beyond business intent.

### Canonicalization / postprocessing steps
```python
from pm4py.cluster_equivalent_ocel import cluster_equivalent_ocel
from pm4py.algo.clustering.equivalent_ocel.viz import apply_canonicalization

def coarser_semantic_clustering(ocel_list):
    # 1. Canonicalize identifiers
    for ocel in ocel_list:
        apply_canonicalization(ocel, variant="object_type_placeholder")
    
    # 2. Run PM4Py clustering on the canonicalized OCELS
    clusters = cluster_equivalent_ocel(ocel_list, parameters={"output_type":"clusters"})
    
    # 3. Postprocess: merge clusters that share the same businesssemantic signature
    merged = merge_by_signature(clusters, canonical_signature_function)
    return merged
```
- **Step1** replaces concrete IDs with placeholders based on type and external flag.  
- **Step2** applies PM4Py’s equivalence clustering on the normalized OCELS.  
- **Step3** aggregates clusters that share the exact businesssemantic signature defined in Section2.

### When exact equivalence is preferable to a coarser business clustering  
- **Compliance monitoring**: Precise sequence verification is needed to ensure each regulatory step is followed exactly (e.g., mandatory payment before dispatch). Exact equivalence guarantees no hidden deviations.  
- **Operational segmentation**: When distinct processes must be isolated for performance metrics (e.g., distinguishing between “singlepackage” and “splitdelivery” systems), finegrained clusters help.  
- **Rootcause analysis**: Identifying the precise structural cause of a failure often requires the smallest distinguishable partition (e.g., a missing `Pack` event).  

### Impact of `max_objs` and large connected executions  
- **`max_objs`**: Limits the number of objects considered in each equivalence class. High values preserve fine distinctions; low values aggressively merge objects, potentially collapsing crossorder relationships prematurely.  
- **Large connected executions**: When many orders share packages, a naïve equivalence may produce a single giant cluster. Using `max_objs` or a secondary clustering (e.g., community detection on the O2O graph) can split the giant into meaningful subclusters (e.g., separate logistic hubs).

## 7. Robustness analysis  

| Perturbation | Effect on cluster assignments (preferred semantic clustering) | Reasoning |
|--------------|-------------------------------------------------------------|-----------|
| **Ignore all O2O qualifiers** | Merges S6 (replacement) and S7 (return) into a more generic “splitpackage” cluster; S4/S5 may be merged with S1 if qualifier does not differentiate crossorder relationships. | Qualifiers are the primary discriminants for replacement, return, and interorder finance; removing them erases those signals. |
| **Ignore external objects** | Collapses S4 (crossorder packaging) and S5 (crossorder invoicing) with S1, because `EXT-*` flags are omitted. | Crossorder links are lost, turning distinct logistics/invoice sharing patterns into ordinary singleorder flows. |
| **Collapse repeated samelabel events** | If a sequence like “AddItem  AddItem” is collapsed to a single “AddItem*”, X3 and X4 would appear identical in activitysequence terms, potentially merging S2 and S3. | The multiplicity of additem events, which distinguishes batch from peritem handling, is erased. |
| **Treat Pack and Dispatch order as a partial order** | Allows variations where Pack may precede Dispatch or Dispatch may precede Pack under concurrency. This would split many current clusters, e.g., S2 could bifurcate into “packthendispatch” and “dispatchthenpack”. | The assumption of strict sequentiality is relaxed, revealing hidden parallelism in splitdelivery scenarios. |
| **Treat payment multiplicity as an amount attribute rather than structure** | Distinguishes S3 (partial payment) from S1 (full payment) only by the numeric settlement amount, potentially leading to S3 being merged with S1 if the amount is abstracted away. | Structural payment behavior (split vs single) is reduced to a scalar, losing the procedural nuance. |

Overall, the preferred semantic clustering (businesssemantic equivalence) remains robust to minor perturbations (e.g., collapsing samelabel events) but is highly sensitive to removal of qualifiers and externalobject flags. The activitysequence and typedstructural clusters would be far less robust under these perturbations, confirming that the chosen equivalence level captures the essential business intent while being resilient to minor variations.

## 8. Limitations and recommendation  

### Limitations  
1. **Qualifier granularity**: Not all O2O notes are captured uniformly; missing or inconsistent qualifiers may cause misclassification.  
2. **Externalobject edgecases**: Very dynamic external objects (e.g., temporary shared resources) may not be stable under identifierplaceholder canonicalization.  
3. **Scalability**: As the number of distinct external objects grows, the O2O graph becomes dense, potentially slowing clustering.  
4. **Payment semantics**: Treating payment multiplicity purely as structural limits detection of amountbased fraud or settlement issues.  

### Recommendation per usecase  

| Usecase | Recommended equivalence level | Rationale |
|----------|------------------------------|-----------|
| **Compliance monitoring** | **Exact activitysequence equivalence** (or typedstructural with full qualifiers) | Guarantees that every mandated step (e.g., payment after dispatch) is observed; no tolerated deviations. |
| **Operational segmentation** | **Businesssemantic equivalence** (our Sclusters) | Groups processes by commercial intent (fulfillment, sharing, returns), allowing clear performance comparisons across distinct business motivations. |
| **Rootcause analysis** | **Typedstructural equivalence + detailed qualifiers** | Preserves the structural backbone while flagging specific anomalies (e.g., `removed_before_dispatch`). This granularity isolates the failure point without conflating unrelated variations. |
| **Descriptive reporting** | **Highlevel businesssemantic clustering** (Sclusters) with aggregated activity counts | Provides concise, businessmeaningful narratives (e.g., “Most orders are standard singlepackage deliveries”) while hiding implementation noise. |

**Why no single notion is optimal**  
- **Exact equivalence** captures minute procedural differences but can produce overly fragmented, hardtointerpret partitions—unsuitable for highlevel insight.  
- **Businesssemantic equivalence** aggregates to meaningful categories but may hide subtle compliance breaches or novel operational innovations.  
- **Typedstructural equivalence** strikes a balance but still depends on the quality of identifier mapping and externalobject handling.  

Thus, practitioners should apply the appropriate level *per* analytical goal, leveraging the full equivalence design space as a layered toolbox.
