# 1. Assumptions and notation

- **A1 (Event-order convention).** Reported nominal times are treated as occurring in process-flow order when they coincide: a completion is recorded before a start, and a start before an arrival at the same nominal timestamp. For WIP counts at a nominal time `t`, we evaluate the state in the interval `(t, t+2.5]` so that a case is not double-counted in both the queue and the server at a handover such as C1’s P07P09 at 11:00.
- **A2 (Rounding).** Every recorded timestamp `t` may represent an actual time in `[t2.5 min, t+2.5 min]`. Therefore a computed interval length has a nominal value plus/minus up to 5 minutes total. We report nominal bounds and explicitly note the rounding envelope.
- **A3 (Capacity).** S1 has two single-task resources I1, I2; S2 has two single-task resources C1, C2. A resource does not execute two different cases simultaneously in reality; apparent overlap is attributed to rounding, delayed logging, or undocumented assistance.
- **A4 (Queue entry).** A case enters the S1 queue at `arrival_s1`. It enters the S2 queue at `s1_end` (when S1 completes). Blank S2 start with completed S1 means the case is waiting for S2 at 14:00.
- **A5 (Missing starts).** If a start is `MISSING`, the start must satisfy  
  `max(arrival or s1_end, previous end on the same resource, end of maintenance if relevant)  start  end`.  
  Service time is then `end  start`, so its lower bound is 0 and its upper bound is `end  lower_bound_of_start`.
- **A6 (Open activities).** `OPEN` means the activity had not completed by 14:00. Elapsed service is computed to 14:00; final service time is right-censored.
- **A7 (Censoring at window end).** For cases still waiting or open at 14:00, elapsed waiting/service is reported, but total sojourn is incomplete and must not be treated as final.
- **A8 (Aggregation).** Fully observed completed cases not explicitly required are aggregated for brevity; required explicit cases are P05, P07, P11, P15, P16, P17, P21, P22.
- **A9 (Subperiods).** We use the full window 08:00–14:00 and, for S2, the C2 maintenance interval 10:55–11:10 plus the post-maintenance interval 11:10–14:00.

# 2. Reconstruction method and formulas

- **S1 waiting time** `W_S1 = s1_start  arrival_s1`. If `s1_start` is missing, bounds are `[L_s1  arrival, U_s1  arrival]` with `L_s1 = max(arrival, previous resource end)` and `U_s1 = s1_end`.
- **S1 service time** `S_S1 = s1_end  s1_start`. With missing start, bounds are `[0, s1_end  L_s1]`; with open end, elapsed `S_S1^elapsed = 14:00  s1_start`.
- **S1 sojourn** `Soj_S1 = s1_end  arrival_s1` (or `14:00  arrival_s1` if open/not started).
- **S2 waiting time** `W_S2 = s2_start  s1_end`. If `s2_start` missing, bounds use `L_s2 = max(s1_end, previous resource end, maintenance end)` and `U_s2 = s2_end`. If still waiting at 14:00, elapsed wait is `14:00  s1_end`.
- **S2 service time** `S_S2 = s2_end  s2_start`; with missing start bounds `[0, s2_end  L_s2]`; with open end elapsed is `14:00  s2_start`.
- **Case total sojourn** for completed cases is `s2_end  arrival_s1` (exact even if an internal start is missing). For open/waiting cases, elapsed total is `14:00  arrival_s1`.
- **WIP.** `WIP_sys(t)` = number of cases with `arrival_s1  t` and not yet S2-complete at `t`. `S1_WIP` splits into waiting-for-S1 and active-S1; `S2_WIP` splits into waiting-for-S2 and active-S2.
- **Throughput** ` = completed services / interval length`.
- **Utilization** `_r = busy_r / available_r`, where `available_r = 360 min` for I1, I2, C1 and `345 min` for C2 (15-min maintenance). Busy time is the sum of service intervals; missing starts shift busy time within the `[0, upper]` envelope, and open ends contribute at least the elapsed time.
- **Lower/central/upper.** Lower waiting = earliest feasible start; upper waiting = latest feasible start. Central = midpoint of nominal bounds. All are expanded by ±5 min total when rounding is explicitly considered.
- **Little’s Law.** Checked only as an accounting identity over the full window where all arrivals and case-minutes are observed; we do not claim steady-state stationarity.

**Hypotheses.**
- The primary bottleneck is **S1** for almost the entire window: it controls entry to the rest of the process and generates the longest cumulative delays.
- **C2 maintenance (10:55–11:10)** removes half of S2 capacity for 15 minutes. This directly prolongs the S2 waits of cases reaching S2 then (especially P08 and P10) by tens of minutes, but it does not create the S1 queue.

**Stable conclusion.** S1 is the dominant bottleneck; C2 outage had a transient, measurable S2 effect; late-window S2 queue buildup is real but not the root cause.
