## 1. Consistency rules and evidence model

To propose repairs for this incomplete OCEL 2.0 dataset, I apply a hierarchy of rules derived from the provided domain semantics. These rules guide the inference of missing Event-to-Object (E2O) and Object-to-Object (O2O) relations without asserting false certainty.

**Hard Invariants**
*   **E2O Cardinality (Creation):** `Create Order` events (ev01, ev02) must relate to exactly one Order object. This is non-negotiable in OCEL 2.0.
*   **Temporal Causality:** An event cannot relate to an object created after the event timestamp. For example, `ev11` (Confirm Delivery) cannot relate to `ORD-A` if `ORD-A` was created after `ev11`. In this dataset, all orders precede deliveries, so this holds.
*   **Object Identity:** An Object ID is unique. `ORD-A` is distinct from `ORD-B`.

**Strong Defaults**
*   **E2O Activity-Object Semantics:** `Pack Item` (ev06, ev07, ev08) normally relates to one Item and one Package. While scanner outages allow item-only relations, the presence of a `scanner_ref` matching a Package ID (PK-7, PK-8) strongly implies the Package relation exists.
*   **O2O Lifecycle Consistency:** If a Package `carries` a Delivery (O2O), the Delivery must exist before the Dispatch event (E2O).
*   **Invoice-Order Aggregation:** `Issue Invoice` (ev12) typically relates to the Invoice and the Order(s) being billed. If an Invoice amount equals the sum of multiple Orders, a strong default suggests the Invoice covers all of them, though this is defeasible (e.g., partial billing).

**Weak Heuristics**
*   **Amount Matching:** `INV-44` (230) = `ORD-A` (130) + `ORD-B` (100). This arithmetic equality is evidence, not proof. It supports a multi-order invoice but does not mandate it (e.g., `ORD-A` could be billed separately later).
*   **Identifier Prefixes:** `external_ref=N-421?` in `ev10` matching `carrier_ref=N-421` in `DEL-Y` is a heuristic link. The `?` explicitly denotes uncertainty, so the confidence should not be 1.0.
*   **Payment Settlement:** `Record Payment` (ev13, ev14) usually settles an Invoice. `PAY-1` is linked to `INV-44`. `PAY-2` (130) matches `ORD-A`'s value, but since `INV-44` covers `ORD-A` (and likely `ORD-B`), `PAY-2` likely settles `INV-44` as well.

**Evidence Against a Repair**
*   **Contradictory Route Data:** If `ev11` linked exclusively to `DEL-Y` (NORTH, N-421), but `ORD-A` items were exclusively in `PK-7` (NORTH, N-420), this would contradict the packing logic. However, `ORD-A` items are split (`IT-A1` in PK-7, `IT-A2` in PK-8), so `ORD-A` spans both routes.
*   **Orphaned Objects:** A repair that leaves `DEL-Y` with no events is weak, but acceptable if the data is truly missing. A repair that links `PAY-2` to `ORD-B` directly (skipping Invoice) contradicts standard accounting O2O patterns (`Payment` -> `Invoice` -> `Order`).

**Evidence Combination Strategy**
I combine identifier similarity (N-421 matches N-421?), temporal proximity (ev10 and ev11 are same day), and attribute consistency (Route NORTH). I prioritize observed O2O structure (e.g., `INV-44` bills `ORD-A`) over inferred O2O structure (e.g., `INV-44` bills `ORD-B`). I only infer E2O relations (e.g., `ev10` -> `DEL-Y`) when the semantic gap is bridged by strong defaults (Dispatch Package -> Delivery).

## 8. Over-repair warnings

1.  **False Invoice Aggregation:** Linking `INV-44` to `ORD-B` (Bundle B) assumes a single invoice covers multiple orders. If the business actually generates separate invoices, this repair corrupts financial compliance reporting.
2.  **Phantom Delivery Confirmation:** Linking `ev11` to `DEL-Y` (Bundle B) assumes the portal event confirmed the specific delivery leg. If `ev11` was a customer self-service click for the *Order* only, linking it to the *Delivery* object implies carrier-level confirmation that did not occur.
3.  **Payment Misallocation:** Linking `PAY-2` to `INV-44` assumes the payment was applied to that specific invoice. If `PAY-2` was an advance payment or for a different unobserved invoice, this creates a false "Paid" status for `INV-44`.
4.  **Scanner Ambiguity:** Linking `ev08` to `PK-8` based on `scanner_ref=PK8-2` assumes the scanner ID is deterministic. If `PK8-2` is a generic scanner ID used across multiple packages, this O2O link is a false positive.
5.  **Circular Event-Object Inference:** Inferring `ev11` links to `DEL-Y` because `ORD-A` is in `PK-8` and `PK-8` is in `DEL-Y` creates a circular dependency where the Event relation is inferred from the Object relation, which itself might be inferred from the Event relation. This must be broken by independent evidence (like the `external_ref`).
