## 1. Conformance semantics

This analysis evaluates **observed behavior against a deliberately incomplete norm**. Classification does not equate "absent from normative model = violation". The semantics used:

**Forbidden behavior:** A relation explicitly marked `forbidden` in the norm (closed-world for this class). Any observed instance is a prima facie violation regardless of frequency. Example: `N3`, `T6`, `E10`. Requires containment even if count is 1. Data-quality may be the root cause, but the class remains forbidden until proven to be a spurious record.

**Missing mandatory behavior:** A relation marked `mandatory` within its stated `Scope/meaning` expected but not observed for in-scope objects/events. Evaluated as `Count/context` against scope, not against total log. Example: `N1`: 98/100 newly created standard Orders show `Create Order -> Validate Order`; the 2 missing are candidates. Mandatory gaps are **not automatically violations** – scope (e.g., `N4`: only externally shipped packages, 200) and abstraction (directly-follows vs eventually) must be examined first.

**Unexpected but unregulated behavior:** An observed relation with no normative entry. Open-world assumption applies: the norm intentionally does not govern it. It is not nonconforming, however rare. Requires business validation, not automatic escalation. Example: `Validate Order -> Issue Invoice` 72 Orders, `Manual Compliance Review -> Customer` 3.

**Typical-pattern absence:** A relation marked `typical` is common/desirable but explicitly allows legitimate exceptions (credit notes, write-offs, open terms, intermediate events). Absence in a subset does not indicate violation; presence confirms expected path. Example: `N2` `Validate Order -> Close Order` 83 Orders, `N5`/`T3` `Issue Invoice -> Record Payment` 92/110. 14 with no successor and 4 write-offs are within the defined exception space pending further evidence.

**Likely data-quality error:** An observed edge violates a mandatory/forbidden rule but contextual evidence points to creation mechanism rather than business action. E.g., join on reused numeric identifier producing `E10` `Sensor Heartbeat -> Invoice` 1, or `E6` split between OTG and ET-OT (200 vs 198). Class is retained as forbidden/missing, but interpretation shifts to data repair and lineage check.

**Abstraction mismatch:** The diagnostic model family misrepresents the business rule. The critical danger here is **interpreting an "eventually expected" rule as a directly-follows rule**. `N1` mandates `Create Order -> Validate Order` eventually; the OC-DFG summary approximates with directly-follows. An unrecorded review event between creation and validation breaks the directly-follows count (98/100) while still satisfying eventually. Same for `N2` where invoice, review or fulfilment events may legitimately interpose between `Validate Order -> Close Order`. OC-DFG alone cannot prove missing mandatory behavior without trace-level eventually check and scope validation.

**Insufficient evidence:** Count alone cannot decide. Missing successor, missing Delivery relation with carrier attribute present, or `Record Payment` without Invoice where unapplied cash is possible but unlabeled, require case attributes, timestamps, object lifecycles, or labeling to adjudicate. Graph summaries provide signal, not verdict.

**Open-world vs closed-world:** The norm is **closed-world only for relations explicitly marked `forbidden` and for mandatory columns within stated scope**. For these, absence of permission = prohibition, and absence of mandatory participation = deviation candidate. It is **otherwise open-world**: unlisted relations, frequencies, codeath edges, customer/risk linkages, or reopening are permitted until explicitly regulated. PM4Py will flag every graph delta; semantic classification must re-introduce open-world tolerance.

## 3. Detailed reasoning by model family

### OC-DFG

**What it can establish:** Order-centric directly-follows sequences for a given object type. It answers "how many objects directly moved from A to B with no other in-between event for that object type?" Useful for flagging forbidden adjacency (`N3` Cancel->Dispatch 2) and for measuring typical/mandatory directly-follows coverage (e.g., `N1` 98/100, `N4` 198/200, `N2` 83, `N5` 92/110). It surfaces raw deltas vs normative graph.

**What it cannot establish:** It cannot prove "eventually" rules, causality, or scope correctness. It cannot distinguish a truly missing event from an unrecorded intermediate event that breaks adjacency. It cannot evaluate time, authorization, or object-state conditions. It cannot detect missing object participations, only event ordering per object type. Counts are per relation, not per trace; 98/100 does not reveal which 2 Orders or why.

**Counts and scopes affect interpretation:** `N4` is scoped to "packages intended for external shipment" (200). The 2 missing must be assessed only within that 200, not against all packages. `N1` is scoped to "newly created standard Orders" (100) – non-standard subtypes might legitimately skip validation, but the summary asserts all 100 are newly created. Without subtype flag, we must assume in-scope and then check abstraction. `N2` and `N5` are typical: 83/unknown and 92/110 are descriptive, not violations; the norm explicitly expects intermediate events may occur and exceptions legitimate. Low frequency alone does not create noncompliance.

**Abstraction divergence:** The same Order can be conforming at eventually level but suspicious at directly-follows level. The 2 Orders lacking `Create Order -> Validate Order` may have `Create Order -> Manual Compliance Review -> Validate Order` – satisfying `N1` eventually but failing DF approximation. Additional context explicitly warns the directly-follows abstraction may be too strict. Danger: interpreting an eventually-expected rule as a directly-follows rule inflates false positives and masks true skips. Mitigation requires trace-level eventually query (`Create precedes Validate`) and review of unmodeled review events. Similarly, `Pack Package -> Dispatch Package` missing in DF may still have pack via bulk or subcontracted event not labeled `Pack Package`.

### OTG

**What it can establish:** Persistent object-to-object associations in the snapshot: `object_interaction`, `object_cobirth`, `object_codeath`. It validates existence of relationships, not ordering. `T1` mandatory `Order-Item` 1450 and `T2` mandatory `Package-Delivery` 200 confirm interaction coverage. `T6` forbidden `Order cobirth Payment` 1 is detectable only here – two objects sharing birth event – revealing systemic atomicity fault.

**What it cannot establish:** It cannot tell if interaction was timely or authorized, nor whether ET-OT participation matches. ## 6. Norm-completeness assessment

**1. No temporal/abstraction definition for "eventually" vs "directly-follows"**
Risk: `N1` and `N2` mandate eventually but are monitored via OC-DFG DF approximation, causing systematic false positives (98/100, 198/200) and disputes over 2 missing cases.
Clarification: Define `N1` as `Create Order` eventually precedes `Validate Order` within X hours, allowing explicitly listed intermediates (e.g., Manual Compliance Review). Add normative `eventually-follows` rule separately from DF visualization.
Status: **mandatory** for eventually rule; explicitly **typical** allowances for intermediates.

**2. Scope ambiguity: "externally shipped Packages" (`N4`) and "standard Orders" (`N1`)**
Risk: 198/200 metric meaningless if flag misapplied; standard vs non-standard Orders may legitimately skip validation. Inflates or hides true gaps.
Clarification: Add object attribute definition: `Package.is_externally_shipped = true` and `Order.order_class = standard`. Scope filter must be part of conformance query.
Status: **mandatory** scope definition (metadata), not new behavior edge.

**3. Unapplied cash exception undefined (`E8`/`T3`/`N5`)**
Risk: 1 payment without Invoice currently violates mandatory rule, yet finance states unapplied cash is possible. No typing rule creates recurring false violations and inconsistent handling of 14 no-successor invoices.
Clarification: Define `Record Payment` subtype attribute `cash_application_type = unapplied` and require `E8` check to exclude those events; define aging thresholds for `N5` typical.
Status: **mandatory** with explicit exception (mandatory when not typed as unapplied); `N5` remains **typical** with tolerance bands.

**4. Customer and RiskCase governance boundary missing (`T4`,`T5`,`E9`)**
Risk: 100 Order-Customer edges and 3 Order-RiskCase/Manual Reviews exist outside policy, creating audit confusion: are they benign or should be governed? Over- or under-escalation likely.
Clarification: Either delegate to external customer/risk policy reference with ID, or mark `T4`,`T5`,`E9` as **explicitly unspecified** with owner and review cadence. Define when Manual Review triggers are required.
Status: **explicitly unspecified** with ownership pointer (or **typical** if risk reviews should be encouraged).

**5. Lifecycle co-termination (`object_codeath`) unregulated – 7 `Package-Delivery` codeaths**
Risk: Shared confirmation event could mask premature closure or double-count delivery; 7 cases currently uninterpretable.
Clarification: Define whether codeath is allowed for confirmation events and which event types may terminate both objects. Add informative metric.
Status: **explicitly unspecified** if allowed; or **typical** if co-termination is desired pattern to monitor.

**6. Rework/reopen, write-off, and cancel-recovery semantics absent (`N6`, Write Off 4)**
Risk: Single `Reopen -> Close` and 4 write-offs have no authorization, time-limit, or state-machine rules; `Cancel -> Dispatch` is forbidden but cancel->reopen->dispatch path is undefined, leaving loophole for 2 critical violations to be laundered via reopen.
Clarification: Define state machine: `Cancel` terminal vs `Reopen` conditions, authorization roles, and whether `Pack->Dispatch` after `Reopen` is permitted. Define write-off approval workflow for `N5` exceptions.
Status: **forbidden** for cancel->dispatch even via reopen (close loophole); **mandatory** authorization for write-off/reopen; **explicitly unspecified** for `Reopen->Close` timing if truly ungoverned.

*Additional ambiguities for prioritization:* No tolerance bands for mandatory/typical frequencies (norm says no statistical bands); no sensor-to-finance identifier uniqueness control for `E10`; no handling of orphan `Add Item` (2 missing Order). Each should receive **mandatory** data-quality constraint or **explicitly unspecified** with monitoring.
