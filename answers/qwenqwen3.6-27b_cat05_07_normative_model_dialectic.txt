1. **Control-Flow Layer (POWL):** Captures mandatory sequencing, concurrency, and branching (Register  Checks  Decision  Activation  Notify  Close). Handles standard, auto-approval, emergency, and rejection paths. Loops are approximated via silent transitions or external iteration markers due to POWL limitations.
2. **Constraint Layer (DECLARE/Log-Skeleton):** Enforces temporal rules (e.g., `Sanctions_Check  Activate_Supplier`, `Quality_Review  2 days after Activate`), response rules (`Request_More_Info  Evidence_Submission`), and exclusion rules (`Reject_Supplier  Activate_Supplier`).
3. **Data-Aware Rule Layer (Pandas/SQL):** Validates eligibility (risk tier, corporate group, geography), financial caps (EUR 20k emergency limit), date windows (directive expiry), and label mappings. Executes as pre/post-checks on event logs.
4. **Resource & COI Layer (Organizational Controls):** Enforces requesterapprover, alias resolution, reporting-line checks, and COI disclosure. Maintained in HR/identity systems, validated via policy engine at decision points.
5. **Policy-Overlay Governance:** Explicit registry of pilots, emergencies, waivers, and amendments with effective/expiry dates, scope boundaries, and audit trails. Overrides baseline only when in-force and in-scope.
6. **Scope Rules:** 
   - *Rejected Leads:* Out of onboarding scope; governed by intake/pre-screen model.
   - *Reactivations:* Separate path requiring validity check of prior Quality_Review and Sanctions_Check.
   - *Withdrawals:* Explicit termination branch with notification.

## 7. PM4Py Model and Data Proposal

**Limitation Note:** POWL does not natively support loops or data/resource constraints. The model below approximates `Request_More_Info` as a parallel branch that converges before approval. Loops should be handled in DECLARE or BPMN. Resource/COI, eligibility, and financial rules are enforced externally.

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# Core transitions
register = Transition(label="Register_Supplier")
sanctions = Transition(label="Sanctions_Check")
quality = Transition(label="Quality_Review")
checks = StrictPartialOrder(nodes=[sanctions, quality])

# Request_More_Info approximation (parallel branch converging pre-approval)
rmi = Transition(label="Request_More_Info")
rmi_silent = SilentTransition(label="_RMI_LOOP_")
rmi_branch = StrictPartialOrder(nodes=[rmi, rmi_silent])

# Approval branches
manual_approval = Transition(label="Manual_Procurement_Approval")
auto_approve = Transition(label="Auto_Approve")
activate = Transition(label="Activate_Supplier")

manual_route = StrictPartialOrder(nodes=[manual_approval, activate])
manual_route.order.add_edge(manual_approval, activate)

auto_route = StrictPartialOrder(nodes=[auto_approve, activate])
auto_route.order.add_edge(auto_approve, activate)

# Emergency/provisional route
provisional = Transition(label="Provisional_Activate")
emergency_checks = StrictPartialOrder(nodes=[provisional, quality, manual_approval])
# In emergency, provisional can precede quality/manual, but all must occur before notify
emergency_route = StrictPartialOrder(nodes=[emergency_checks, activate])
emergency_route.order.add_edge(emergency_checks, activate)

# Rejection
reject = Transition(label="Reject_Supplier")

# Decision XOR
decision = OperatorPOWL(
    operator=Operator.XOR,
    children=[manual_route, auto_route, emergency_route, reject]
)

# Notification & closure
notify = Transition(label="Notify_Requester")
close = Transition(label="Close_Case")

# Assemble M1
M1 = StrictPartialOrder(nodes=[register, checks, rmi_branch, decision, notify, close])
M1.order.add_edge(register, checks)
M1.order.add_edge(checks, decision)
M1.order.add_edge(rmi_branch, decision)  # RMI converges before decision
M1.order.add_edge(decision, notify)
M1.order.add_edge(notify, close)

# Note: POWL cannot enforce temporal caps, eligibility, resource separation, or directive expiry.
# These are delegated to the constraint/data layers described in Section 6.
```

**Event/Data-Collection Proposal**
- `notification_id`: UUID, immutable, generated at CRM handoff.
- `rule_version_id`: Links event to active policy/overlay version.
- `eligibility_snapshot`: JSON blob capturing risk_tier, geography, group_status at decision time.
- `actor_aliases`: Resolved canonical IDs for requester/approver/reviewer with resolution timestamp.
- `delegation_evidence`: Signed delegation record if approver acts via proxy.
- `emergency_pilot_authority`: Reference to overlay_id + signatory.
- `effective_timestamp` & `record_timestamp`: Immutable UTC fields for all events.
- `source_system`: CRM, ERP, or OnboardingLog for traceability.
- `dedup_key`: Source transaction ID to prevent migration duplicates.

This architecture separates control-flow conformance from data/resource compliance, enabling accurate deviation detection while supporting policy agility and auditability.
