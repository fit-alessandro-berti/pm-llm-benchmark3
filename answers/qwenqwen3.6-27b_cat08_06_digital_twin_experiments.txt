# 1. Model scope and state variables

**Boundary & Level of Detail**
The digital twin covers the end-to-end permit lifecycle from portal submission to final permit issuance or rejection. It operates as a discrete-event simulation (DES) at the activity level, explicitly modeling resource contention, calendar constraints, queue disciplines, and cross-case dependencies. Pre-submission consultations and post-permit construction are excluded.

**Entities**
- `Case`: Represents a permit application with attributes (`case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`).
- `ResourcePool`: Pools for Clerks, Planners, Fire Reviewers, Environmental Reviewers, Inspectors, Legal Officers, and System tasks.
- `Queue`: Activity-specific waiting lines with FIFO discipline and aging/priority overrides.
- `ArchitectGroup`: Logical grouping of cases submitted by the same architect within a rolling 7-day window.
- `InspectionBundle`: Geographic grouping of cases in the same district scheduled together.
- `ObjectionWave`: Probabilistic event affecting public-notice duration.

**State Variables**
- *Per Case*: `status`, `current_activity`, `submission_time`, `waiting_time`, `service_time`, `rework_count`, `objection_flag`, `bundle_id`, `district`, `case_type`, `priority_score` (aging-based).
- *Per Resource*: `available`, `current_assignment`, `travel_state` (inspectors), `calendar_active`, `council_week_flag`.
- *Per Queue*: `length`, `head_age`, `discipline`.
- *Global*: `simulation_clock`, `seasonal_multiplier`, `day_of_week`, `holiday_flag`, `backlog_by_type`.

**Cross-Case Dependencies**
- **Architect Clustering**: Arrival rate modulated by architect burst patterns; inspection scheduling considers group readiness.
- **Geographic Batching**: Inspectors bundle cases by district when travel windows overlap, reducing per-case travel time but increasing waiting for the first case in the bundle.
- **Objection Propagation**: Neighborhood objections modeled as district-level probabilistic extensions to the public-notice period, affecting multiple related cases.
- **Shared Resources**: All cases compete for finite FTE pools with strict calendars; contention drives waiting times.

# 2. Parameter-estimation plan

**Arrivals**
- Fit a non-homogeneous Poisson process (NHPP) with multiplicative modifiers: baseline rate × seasonal factor (1.0 for Jan-Feb, 1.7 for Mar-May & Sep-Nov) × day-of-week factor (2.2 for Monday, normalized).
- Model architect bursts using a compound arrival process: top 20 `architect_id` values trigger clustered arrivals with inter-burst intervals estimated from log gaps.

**Service & Waiting Times**
- Since start timestamps are missing, compute raw duration as `next_event_timestamp - current_event_timestamp`. This conflates waiting, service, and downstream synchronization.
- Separate using resource-state conditioning: when the resource pool is idle, duration  service time; when busy, duration  waiting + service. Fit mixture models (Lognormal/Gamma) to medians and p90s from the empirical summary.
- Use `pm4py.discover_performance_dfg` to validate average edge durations against empirical summaries.

**Branching & Routing**
- Extract variant frequencies using `pm4py.discover_variants`. Map to process tree operators (`X`, `+`, `*`).
- Condition branching probabilities on case attributes (`case_type`, `requires_fire`, etc.) using logistic regression or decision trees trained on the log.

**Rework**
- Estimate loop transition probabilities from historical rework rates (e.g., 9% inspection rework, completeness rework ~19%). Model as geometric retry with constant probability per loop.

**Resource Calendars**
- Encode HR-derived calendars explicitly. Validate against completion timestamp distributions (e.g., zero completions on weekends for human tasks, council-week gaps for legal).

**Dependencies**
- Inspection batching threshold and travel time penalties estimated from district-level completion patterns.
- Objection probability and duration extension estimated from public-notice duration tail (p90 vs median) and district sensitivity flags.

**PM4Py Usage**
- `pm4py.format_dataframe` for standardization.
- `pm4py.discover_variants`, `pm4py.discover_dfg`, `pm4py.discover_performance_dfg` for structural and temporal insights.
- `pm4py.parse_process_tree` used with syntax adaptation (see Section 8).

**Missing Data**

- Objections not in log are modeled as probabilistic extensions, not deterministic events.
- Emergency cases excluded; results apply to standard permit pipeline.
- Flattened log underrepresents cross-case links; dependencies modeled via explicit rules rather than log inference.

        timestamp_key='time:timestamp'
    )
    return formatted_df

def parse_process_tree(tree_string: str) -> pm4py.objects.petri.tree:
    """
    Parse simplified process tree string.
    Note: PM4Py's parse_process_tree expects specific syntax (AND, XOR, LOOP, SEQUENCE).
    The provided string uses ->, *, X, +, tau. We convert it to PM4Py-compatible format
    or note limitations. Here we demonstrate a safe parsing approach.
    """
    # Mapping simplified operators to PM4Py syntax
    pm4py_syntax = (
        tree_string
        .replace('->', 'SEQUENCE')
        .replace('*', 'LOOP')
        .replace('X(', 'XOR(')
        .replace('+', 'AND')
        .replace('tau', 'tau')
    )
    # Add parentheses if missing for PM4Py parser
    try:
        tree = pm4py.parse_process_tree(pm4py_syntax)
        return tree
    except Exception as e:
        print(f"Process tree parsing limitation: {e}")
        print("Falling back to manual structure or DFG-based routing.")
        return None

def compute_log_insights(formatted_df: pd.DataFrame) -> dict:
    """Compute variants, DFG, performance DFG, arrival rate, service/waiting times."""
    insights = {}
    
    # Convert to PM4Py log object
    log = log_converter.apply(formatted_df)
    
    # Variants
    variants = pm4py.discover_variants(log)
    insights['variants'] = variants
    
    # Directly Follows Graph (DFG)
    dfg = pm4py.discover_dfg(log)
    insights['dfg'] = dfg
    
    # Performance DFG (average durations per edge)
    perf_dfg = pm4py.discover_performance_dfg(log)
    insights['performance_dfg'] = perf_dfg
    
    # Case arrival average
    case_arrivals = formatted_df.groupby('case:concept:name').first().sort_values('time:timestamp')
    arrival_times = case_arrivals['time:timestamp']
    inter_arrivals = arrival_times.diff().dropna().dt.total_seconds() / 3600
    insights['avg_arrival_rate_cases_per_hour'] = 1.0 / inter_arrivals.mean()
    
    # Service & Waiting times (approximation due to missing start timestamps)
    # Duration = next event timestamp - current event timestamp
    formatted_df = formatted_df.sort_values(['case:concept:name', 'time:timestamp'])
    formatted_df['next_timestamp'] = formatted_df.groupby('case:concept:name')['time:timestamp'].shift(-1)
    formatted_df['raw_duration_hours'] = (formatted_df['next_timestamp'] - formatted_df['time:timestamp']).dt.total_seconds() / 3600
    
    # Split heuristic: if resource pool idle (simulated later), duration  service; else waiting + service
    # Here we store raw duration for later decomposition in simulation
    insights['df_with_durations'] = formatted_df[['case:concept:name', 'concept:name', 'time:timestamp', 'raw_duration_hours']]
    
    return insights
