# 1. Policy Interpretation and Conflict Resolution

## Assumptions
1. **R5/R6 Conflict Resolution**: The legal requirement (R5) states that after Sanctions Escalation, Obtain Legal Opinion must precede Activate Vendor. The operations requirement (R6) allows emergency activation before the opinion, provided it is jointly authorized outside the event log, with the opinion arriving within 24 hours. Since the event log lacks an "emergency" attribute or joint authorization flag, we must choose a conservative interpretation.

2. **Resolution Choice**: We adopt the stricter legal interpretation (R5) as the authoritative policy. This means:
   - **Compliance Risk**: Emergency activations that bypass legal opinion cannot be detected in the log, creating a potential compliance gap. However, this aligns with the legal department's mandate and avoids silent violations of R5.
   - Alternative resolution: Treat any activation following Sanctions Escalation as a violation unless Obtain Legal Opinion occurs first. This is the chosen approach.

3. **Temporal Norms**: Temporal deviations (R12) are treated as warnings, not hard constraints, to avoid false positives in complex cases (e.g., clarification loops).

4. **Resource/Data Attributes**: The log must include `resource` and `timestamp` for all activities. Missing attributes are treated as violations.

# 3. Procedural Backbone

## Formal Description
- **Start**: `Receive Onboarding Request`.
- **Concurrent Paths**: `Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account` (all start after receipt).
- **Join Point**: `Classify Risk` requires all three concurrent paths to complete.
- **Branching**:
  - **Reject**: `Reject Vendor`  `Close Onboarding`.
  - **Low-Risk**: `Manager Approval`  `Activate Vendor`  `Release First Payment`  `Close Onboarding`.
  - **High-Risk**: `Enhanced Due Diligence`  `Compliance Approval`  `Activate Vendor`  `Release First Payment`  `Close Onboarding`.
- **Clarification Loops**: `Request Clarification`  `Receive Clarification` (repeatable) must precede `Classify Risk` if triggered.
- **Sanctions Escalation**: `Sanctions Escalation`  `Obtain Legal Opinion`  `Activate Vendor` (enforced via sequence).

## PM4Py Code
```python
from pm4py.objects.process_tree.obj import ProcessTree
from pm4py.objects.process_tree.pt_operator import Operator

# Build the process tree
root = ProcessTree(operator=Operator.XOR)
receive = ProcessTree(label="Receive Onboarding Request")

# Concurrent paths after receipt
concurrent = ProcessTree(operator=Operator.PARALLEL)
capture = ProcessTree(label="Capture Master Data")
sanctions = ProcessTree(label="Run Sanctions Screening")
verify = ProcessTree(label="Verify Bank Account")
concurrent.children = [capture, sanctions, verify]

# Join point: Classify Risk requires all three
classify = ProcessTree(label="Classify Risk")

# Branching after classification
reject_branch = ProcessTree(operator=Operator.SEQUENCE)
reject = ProcessTree(label="Reject Vendor")
close_reject = ProcessTree(label="Close Onboarding")
reject_branch.children = [reject, close_reject]

low_risk_branch = ProcessTree(operator=Operator.SEQUENCE)
manager_approval = ProcessTree(label="Manager Approval")
activate_low = ProcessTree(label="Activate Vendor")
payment_low = ProcessTree(label="Release First Payment")
close_low = ProcessTree(label="Close Onboarding")
low_risk_branch.children = [manager_approval, activate_low, payment_low, close_low]

high_risk_branch = ProcessTree(operator=Operator.SEQUENCE)
due_diligence = ProcessTree(label="Enhanced Due Diligence")
compliance = ProcessTree(label="Compliance Approval")
activate_high = ProcessTree(label="Activate Vendor")
payment_high = ProcessTree(label="Release First Payment")
close_high = ProcessTree(label="Close Onboarding")
high_risk_branch.children = [due_diligence, compliance, activate_high, payment_high, close_high]

# Combine branches
after_classify = ProcessTree(operator=Operator.XOR)
after_classify.children = [reject_branch, low_risk_branch, high_risk_branch]

# Clarification loop: Request  Receive (repeatable)
clarify_loop = ProcessTree(operator=Operator.LOOP)
request = ProcessTree(label="Request Clarification")
receive = ProcessTree(label="Receive Clarification")
clarify_loop.children = [request, receive]

# Insert clarification loop before Classify Risk if needed
# (Approximated by making Classify Risk optional after concurrent paths)
classify_with_clarify = ProcessTree(operator=Operator.XOR)
classify_with_clarify.children = [classify, clarify_loop]

# Sanctions Escalation path
sanctions_escalation = ProcessTree(operator=Operator.SEQUENCE)
escalate = ProcessTree(label="Sanctions Escalation")
legal_opinion = ProcessTree(label="Obtain Legal Opinion")
activate_after_escalate = ProcessTree(label="Activate Vendor")
sanctions_escalation.children = [escalate, legal_opinion, activate_after_escalate]

# Merge sanctions path into high-risk branch
high_risk_branch.children.insert(0, sanctions_escalation)  # Insert before due diligence

# Full tree
root.children = [receive]
receive.children = [concurrent]
concurrent.children.append(classify_with_clarify)
classify_with_clarify.children.append(after_classify)

procedural_model = root
```

## Explanation
- **Concurrency**: `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` run in parallel.
- **Clarification Loops**: Modeled as a loop between `Request Clarification` and `Receive Clarification`, which can occur before `Classify Risk`.
- **Terminal Outcomes**: `Close Onboarding` follows either rejection or payment.
- **Post-Activation**: `Change Bank Details` and `Suspend Vendor` are not included in the procedural backbone (handled in Log Skeleton).
- **Approximation**: The loop is approximated as an XOR between `Classify Risk` and the clarification loop, which may allow invalid sequences (e.g., `Classify Risk` without prior clarification). This is a limitation of process trees for non-block-structured behavior.

## Explanation
- **Occurrence Constraints**: `activ_freq` enforces R10 (each terminal activity occurs at most once).
- **Ordering**: `always_before`/`always_after` enforce R3, R4, R7, and R11.
- **Mutual Exclusion**: `never_together` enforces R1, R2, and R8.
- **Directly Follows**: Approximates procedural sequences (e.g., `Sanctions Escalation` must directly precede `Obtain Legal Opinion`).

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}
```

## Design Rationale
- **Warnings, Not Violations**: Temporal deviations are treated as warnings because:
  1. Loops (e.g., clarification cycles) can inflate durations.
  2. Real-world delays (e.g., legal reviews) may exceed norms without violating policy.
  3. The `zeta=2.0` threshold flags outliers (e.g., >95% of cases) without blocking valid cases.

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
from pm4py.filtering import filter_four_eyes_principle

def check_resource_constraints(log):
    # Convert log to DataFrame (assuming columns: case:concept:name, activity:concept:name, time:timestamp, org:resource)
    df = pd.DataFrame(log)
    violations = []

    # R9.1: Verify Bank Account resource  approval resource
    approval_activities = ["Manager Approval", "Compliance Approval"]
    verify_bank_resources = df[df["activity:concept:name"] == "Verify Bank Account"]["org:resource"]
    approval_resources = df[df["activity:concept:name"].isin(approval_activities)]["org:resource"]
    if not verify_bank_resources.empty and not approval_resources.empty:
        if set(verify_bank_resources).intersection(set(approval_resources)):
            violations.append("R9.1: Verify Bank Account and approval share a resource")

    # R9.2: Capture Master Data resource  Activate Vendor resource
    capture_resources = df[df["activity:concept:name"] == "Capture Master Data"]["org:resource"]
    activate_resources = df[df["activity:concept:name"] == "Activate Vendor"]["org:resource"]
    if not capture_resources.empty and not activate_resources.empty:
        if set(capture_resources).intersection(set(activate_resources)):
            violations.append("R9.2: Capture Master Data and Activate Vendor share a resource")

    # R6: Emergency-policy conflict (no "emergency" attribute, so flag any activation after Sanctions Escalation)
    sanctions_escalation_times = df[df["activity:concept:name"] == "Sanctions Escalation"]["time:timestamp"]
    activate_times = df[df["activity:concept:name"] == "Activate Vendor"]["time:timestamp"]
    if not sanctions_escalation_times.empty and not activate_times.empty:
        for esc_time in sanctions_escalation_times:
            for act_time in activate_times:
                if act_time < esc_time:
                    violations.append("R6: Activation before Sanctions Escalation (potential emergency bypass)")

    return violations

def check_temporal_deviations(log, temporal_profile, zeta=2.0):
    warnings = []
    for (a, b), (mean, std) in temporal_profile.items():
        # Group by case and compute elapsed time between a and b
        # (Pseudocode; actual implementation would use pm4py's time utilities)
        for case in log:
            a_events = [e for e in case if e["activity:concept:name"] == a]
            b_events = [e for e in case if e["activity:concept:name"] == b]
            if a_events and b_events:
                elapsed = (b_events[0]["time:timestamp"] - a_events[0]["time:timestamp"]).total_seconds()
                if elapsed > mean + zeta * std:
                    warnings.append(f"Temporal deviation: {a}{b} took {elapsed/3600:.1f}h (> {mean/3600 + zeta*std/3600:.1f}h)")
    return warnings
```

## Attribute Requirements
- **Required Columns**: `activity:concept:name`, `time:timestamp`, `org:resource`.
- **Missing Attributes**: If `org:resource` is missing, resource checks return `not evaluated`. If `time:timestamp` is missing, temporal checks return `not evaluated`.

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated Enforcement
- **R1**: Enforced in procedural (`XOR` branch) and DECLARE (`noncoexistence`), and Log Skeleton (`never_together`).
- **R2**: Enforced in DECLARE (`exactly_one`) and Log Skeleton (`never_together`).
- **R8**: Enforced in DECLARE (`noncoexistence`) and Log Skeleton (`never_together`).

## Inconsistencies Under Loops
- **Clarification Loops**: DECLARE `response` and `precedence` rules may vacuously pass if a case has no clarifications (e.g., T1). Log Skeleton's `always_before`/`always_after` are more robust for optional behavior.

## Missing Attributes
- **Emergency Authorization**: R6 cannot be fully enforced due to missing `emergency` attribute. Current check flags all activations after Sanctions Escalation, which may over-flag.

## Timestamp Limitations
- **Temporal Profile**: Only considers first occurrences of activity pairs (e.g., first `Request Clarification`  first `Receive Clarification`). Later pairs are ignored, which may hide violations.

## Support/Confidence Risks
- DECLARE rules with `support=1.0` and `confidence=1.0` assume perfect enforcement, which may not hold in practice (e.g., human error). These should be treated as idealized constraints.

# 10. Deployment Recommendation

## Canonical Representation
- **Procedural Model**: Accepting Petri net (for future extension to post-activation behavior like `Change Bank Details`).
- **Authoritative Policy Layer**: DECLARE model for declarative constraints (R2, R3, R4, R7, R8) and Log Skeleton for occurrence/data-flow constraints (R10, R11).
- **Temporal Checks**: Run last to avoid false positives from loops.
- **Resource Checks**: Run in parallel with procedural checks but surface results separately.

## Conformance Check Order
1. **Procedural**: Fast rejection of invalid control-flow (e.g., co-occurring terminal outcomes).
2. **DECLARE**: Validate declarative constraints (e.g., mutual exclusion).
3. **Log Skeleton**: Check occurrence and data-flow constraints.
4. **Temporal Profile**: Flag deviations as warnings.
5. **Resource/Data Layer**: Validate segregation of duties and emergency policy.

## Contradiction Handling
- **Conflicting Findings**: If procedural fails, stop and report. Otherwise, aggregate results from all layers. For example:
  - If DECLARE flags a violation but Log Skeleton passes, surface both with a note that the procedural model may have allowed the sequence.
  - For T6, highlight the R5/R6 conflict explicitly: "Activation before legal opinion may violate legal policy (R5) but could be emergency-authorized (R6). Requires manual review."

## User Interface
- Present a dashboard with:
  - **Traffic Light**: Overall verdict (pass/fail/warning).
  - **Layer Breakdown**: Which layer failed and why.
  - **Suggestions**: For warnings (e.g., "Clarification took 30h; consider process improvement").
