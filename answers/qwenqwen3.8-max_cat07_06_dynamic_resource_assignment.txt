# 1. Objectives and constraints

This is a **multi-objective socio-technical assignment problem**, not a single-objective optimization. The policy should produce decisions that are operationally useful, explainable, and auditable, while accepting explicit trade-offs.

## Optimization objectives

The policy should simultaneously consider:

1. **Short-term throughput / SLA protection**
   - Urgent and high-priority cases should be assigned to resources with enough remaining capacity and sufficient skill.
   - SLA risk should dominate for cases with very low remaining time.

2. **Error and rework reduction**
   - Avoid skill mismatches, especially for Security Review, Final Approval, and high-complexity cases.
   - Avoid excessive reassignment, because historical evidence shows that cases with more than two reassignments have higher rework and appeal rates.

3. **Workload fairness and overtime protection**
   - Prefer resources with lower open caseloads and lower overtime risk.
   - Protect resources already marked as high overtime risk unless there is no safer alternative.

4. **Skill development**
   - Use low-risk normal/low-priority cases for supervised training when SLA slack exists.
   - Training should align with documented training priorities.

5. **Continuity of case ownership**
   - Preserve ownership for high-complexity cases with high handover cost, unless the current owner cannot perform safely or capacity risk is severe.

6. **Resilience and bottleneck avoidance**
   - Avoid overconcentrating work on scarce specialists, especially in Security Review and Final Approval.
   - Preserve backup capacity and encourage supervised pairing where feasible.

## Hard safety and compliance constraints

These should be treated as non-negotiable unless a documented exception is approved by a supervisor.

| Constraint | Rule |
|---|---|
| Skill zero | A resource with skill `0` must not perform the activity. Observation/shadowing may be allowed if explicitly supervised and no decision rights are given. |
| High-priority skill floor | Urgent/high-priority cases must not be assigned to skill `< 2` unless supervised. |
| Security Review | Must be performed by skill `3`, or by skill `1–2` under explicit supervision by `R7_Gita` or `R8_Hugo`. |
| Final Approval | Must be performed by skill `2–3`. Skill `1` may prepare but not finalize. |
| Quality Check batching | Allowed only for normal/low priority and SLA time remaining `> 24h`. |
| Assignment cap | No resource receives more than `4` new assignments in the batch. |
| High overtime protection | Do not assign new work to high-overtime-risk resources unless the case is urgent and no safer alternative exists. |

## Soft preference trade-offs

These are weighted preferences, not absolute rules.

| Preference | Interpretation |
|---|---|
| Continuity | Prefer current owner when handover cost is high, complexity is high, and the owner has adequate skill or supervision. |
| Training | Prefer supervised training for normal/low cases with SLA slack. |
| Fairness | Prefer lower open cases, more remaining hours, and lower overtime risk. |
| Specialist preservation | Avoid consuming scarce specialist capacity for work that can be safely done by competent non-specialists. |
| Batch efficiency | Batch Quality Check work when allowed. |
| Bottleneck avoidance | Avoid repeatedly assigning to the same scarce resource unless required by safety or SLA. |

There is no single obvious optimum. For example, specialist-only routing may reduce immediate skill risk but can create Security/Approval queues, while first-available routing may reduce waiting but increase rework and reassignment.

# 2. Assignment policy

The proposed policy is an **explainable constrained scoring policy**. It first filters ineligible candidates, then scores eligible candidates using transparent components, then selects the best assignment while recording the dominant reasons.

## High-level algorithm

```text
Input:
  Queue Q = cases awaiting assignment
  Resources R = skills, open cases, hours remaining, overtime risk, training priority
  Historical log priors = service time, waiting time, handover cost, bottleneck indicators

Output:
  Assignment list with resource or supervised pair, reason, trade-off, training flag, risk

For each case in priority order:
  1. Sort cases by:
       urgent > high > normal > low,
       then lower SLA remaining,
       then higher complexity,
       then higher handover cost.

  2. Generate candidate resources or supervised pairs.

  3. Apply hard eligibility filters.

  4. Score each candidate on:
       SLA urgency fit
       skill match
       continuity / handover cost
       workload and overtime fairness
       training value
       resilience / bottleneck avoidance

  5. Select best candidate.

  6. Store explanation:
       top scoring factors,
       constraints satisfied,
       exceptions,
       expected risk.

  7. Update batch state:
       assignments per resource,
       remaining hours,
       training quota,
       specialist utilization.
```

## Eligibility filtering

For each case-resource candidate:

```text
Reject if:
  skill == 0 and the resource would perform the work
  activity == Security Review and skill < 3 unless supervised by R7_Gita or R8_Hugo
  activity == Final Approval and skill < 2
  case priority is urgent/high and skill < 2 unless supervised
  resource already has 4 new assignments in this batch
  resource overtime risk is high and case is not urgent, unless no safer alternative exists
  Quality Check batching conditions are not met for batched assignment
  estimated work time clearly exceeds remaining hours and SLA is inside the current shift,
    unless no alternative exists and exception is approved
```

For supervised pairs:

```text
Trainee may have skill 1 or 2 for normal/low cases.
For urgent/high cases, trainee skill < 2 is allowed only with explicit supervision.
For Security Review, supervisor must be R7_Gita or R8_Hugo.
For Final Approval, the final approver must have skill >= 2.
Skill 0 may only observe/shadow, not perform.
```

## Workload and overtime fairness scoring

Use:

- `current open cases`
- `hours remaining today`
- `overtime risk`
- current batch assignment count

```text
load_ratio =
  (open_cases + new_batch_assignments + 1)
  / median_open_cases

hours_pressure =
  estimated_processing_time / hours_remaining_today

fairness_score =
  1 - min(1, 0.6 * load_ratio + 0.4 * hours_pressure)

if overtime_risk == high:
    fairness_score -= 1.0 unless urgent exception applies
if overtime_risk == medium:
    fairness_score -= 0.3
if overtime_risk == low:
    no penalty
```

## Training and development scoring

Training is favored only when SLA risk is acceptable.

```text
training_score = 0

   and sla_time_remaining is sufficient
   and trainee.training_priority == required_skill
   and supervisor has adequate skill:
       training_score += 1.0

    reject or downgrade
```

- specialist utilization,
- waiting time in Security Review and Final Approval,
- handover-network centrality,

```text
if resource is a scarce specialist and activity is not safety-critical:
    resilience_score -= 0.3

if assignment creates a supervised pair or backup exposure:
    resilience_score += 0.2

    resilience_score += 0.1
```

## Composite score

Weights can vary by case priority.

```text
score =
    w_sla       * sla_score
  + w_skill     * skill_score
  + w_continuity* continuity_score
  + w_fairness  * fairness_score
  + w_training  * training_score
  + w_resilience* resilience_score
```

## Tie-breaking

If multiple candidates have similar scores:

1. Prefer the candidate that satisfies safety rules without exception.
2. Prefer lower SLA risk.
3. Prefer continuity for high-complexity/high-handover cases.
4. Prefer lower workload and lower overtime risk.
5. Prefer documented training value.
6. Prefer lower specialist bottleneck impact.
7. Prefer earlier availability.

## Exception handling

If no fully eligible candidate exists:

```text
1. Try a supervised pair.
2. Try splitting preparation and finalization, where allowed.
3. Escalate to team lead for controlled overtime or deadline renegotiation.
4. If security specialist capacity is missing, escalate immediately; do not assign skill 0.
5. Record the exception in assignment_reason.
```

# 4. Comparison with baseline policies

## Likely behavior of first-available routing

First-available routing assigns work to the resource with the lowest open caseload and enough hours, ignoring specialization except skill `0`.

In this queue, it would tend to favor:

- `R10_Jonas` because open cases are low,
- `R6_Farid` because open cases are low,
- `R3_Celine` because open cases are moderate,
- `R8_Hugo` because open cases are moderate.

It may reduce immediate waiting, but it can create problems:

- Security Review may be assigned to a low-workload resource with insufficient skill unless hard rules override it.
- High-complexity cases may be moved away from current owners.
- Training and continuity are ignored.
- Reassignment count may increase.
- Skill mismatch may increase rework.

## Likely behavior of specialist-only routing

Specialist-only routing assigns each case to the highest-skill resource for the required skill, breaking ties by open cases.

It would tend to route:

- Security Review to `R7_Gita` or `R8_Hugo`,
- Final Approval to `R6_Farid`,
- Technical Diagnosis to `R3_Celine` or `R4_David`,
- Customer Negotiation to `R6_Farid` or `R5_Eva`,
- Quality Check to `R10_Jonas`, `R8_Hugo`, or `R9_Iris`,
- Rework Correction to `R3_Celine`, `R8_Hugo`, or `R9_Iris`.

This can improve immediate skill fit but may create:

- overloading of scarce specialists,
- long queues in Security Review and Final Approval,
- poor continuity where the current owner is not the highest specialist,
- little or no training,
- unfair concentration of work on a few resources.

## Qualitative comparison

| Dimension | First-available routing | Specialist-only routing | Proposed explainable dynamic policy |
|---|---|---|---|
| Expected throughput | May reduce short-term waiting by using low-load resources, but can increase repeat work and reassignment | May reduce errors but can create specialist queues and slower throughput | Balanced: protects urgent work, uses competent resources, batches where safe, avoids overloading specialists |
| SLA risk | Higher for complex/specialized cases if skill mismatch occurs | Lower for skill-critical cases, but higher where specialist capacity is scarce | Low for urgent cases through supervised specialist involvement; some capacity risk remains for C001/C007/C011 |
| Error/rework risk | Higher due to skill mismatch and reassignment | Lower immediate skill risk, but queues may delay detection and increase pressure | Lower than first-available; slightly higher than pure specialist routing where supervised trainees are used, mitigated by supervision and continuity |
| Fairness of workload | Superficially fair by open cases, but ignores overtime risk and skill scarcity | Unfair to scarce specialists; may overload `R6_Farid`, `R8_Hugo`, `R3_Celine` | More balanced; protects high-overtime-risk resources; uses low-load resources; respects assignment cap |
| Skill development | Poor; training ignored | Poor; specialists do all work, trainees excluded | Supports documented training on low-risk cases; uses supervised pairs and observation |
| Continuity of ownership | Poor; cases may move to whoever is available | Poor when specialist is not current owner | Preserves ownership for high-complexity/high-handover cases where safe; accepts handover only when justified |
| Resilience to absence/bottlenecks | Weak; may create skill gaps and repeated handovers | Weak; creates single points of failure around specialists | Better: supervised pairs, backup exposure, overtime protection, bottleneck awareness; still depends on Hugo/Farid for some critical work |

The proposed policy is not universally “best” on every metric. It accepts some extra coordination cost and slightly lower immediate specialization in exchange for fairness, training, continuity, and resilience.

# 5. Explanation to workers

Assignments in this batch are made to balance customer urgency, case complexity, skills, workload, and development. The goal is not to punish anyone or to maximize raw throughput.

The main principles are:

- **Urgent and safety-critical work gets the strongest support.**  
  Security Review and Final Approval have strict skill rules. Where a case is urgent and the current owner needs support, we use supervision rather than forcing an unsafe handover.

- **We protect continuity when handover is expensive.**  
  For complex cases where changing owner would cause delay or rework, we try to keep the current owner involved. For example, C007 remains with Celine because another handover would be costly.

- **We avoid overloading people with high overtime risk.**  
  Some colleagues already have high workload or high overtime risk. Where possible, non-urgent work is routed away from them to protect wellbeing and reduce burnout risk.

- **We use low-risk cases for development.**  
  Training assignments are only used when the SLA has enough slack and a competent supervisor is available. For example, C009 supports Amal’s Diagnosis development with Eva supervising. C015 allows Jonas to observe Security Review under Hugo’s accountability, without performing work beyond his current authorization.

- **We batch work when it is safe.**  
  Quality Check cases C006 and C012 are batched because they are normal/low priority and have more than 24 hours of SLA slack.

- **Some trade-offs are unavoidable.**  
  A few cases are reassigned to protect capacity or reduce overtime risk. Where this happens, the reason is recorded, and the risk is monitored.

If an assignment feels unrealistic, or if a supervised case needs more support, please raise it early. The policy is designed to be adjusted with human judgment, not to replace it.

# 6. Process-mining audit indicators

The deployed policy should be audited continuously using the event log. The log contains case attributes, resource attributes, SLA information, assignment reason, reassignment count, workload snapshot, and handover cost band.

## Core audit indicators

| Indicator | Definition | How to compute | Desired direction |
|---|---|---|---|
| Handover frequency | Number of resource changes per case or per activity transition | Count changes in `org:resource` within each case; validate with `pm4py.discover_handover_of_work_network` | Lower for high-complexity/high-handover cases |
| Reassignment count | Case-level count of reassignments | Use `reassignment_count`; track cases with count `> 2` | Reduce cases exceeding 2 unless justified |
| Skill mismatch | Assignment where resource skill is below required threshold or rule | Join event log with skill matrix; check `required_skill`, `case_priority`, activity-specific rules | Zero for hard-rule violations |
| Supervised mismatch | High-priority case assigned to skill `< 2` without supervision | Check `case_priority`, `resource_skill`, and supervision flag in `assignment_reason` or working-together network | Zero |
| Workload distribution | Fairness of new assignments and open cases | Gini coefficient or coefficient of variation of `workload_snapshot` and batch assignments per resource | More equal, except justified specialist work |
| Overtime risk exposure | Share of non-urgent assignments given to high-overtime-risk resources | Filter `overtime_risk = high` and `case_priority not urgent` | Near zero unless documented exception |
| SLA misses | Cases completed after `sla_deadline` | Compare final event timestamp with `sla_deadline`; also track near misses | Reduce, especially for urgent/high priority |
| SLA near-miss rate | Cases completed close to deadline or with negative slack at assignment | Use `sla_deadline`, assignment timestamp, service/waiting time | Early warning indicator |
| Rework after assignment | Frequency of `Rework Correction` after assignment decision | Filter cases where `concept:name = Rework Correction` occurs after assignment event | Reduce, especially after skill mismatch or >2 reassignments |
| Appeal after assignment | Frequency of appeal events after assignment | Filter appeal activity or case attribute if available | Reduce |
| Training assignment share | Share of normal/low-priority assignments supporting documented training | Filter `case_priority in {normal, low}` and `assignment_reason` contains training; check trainee training priority | At least 20% when SLA risk acceptable |
| Training quality | Rework or SLA impact of training cases | Compare rework/SLA metrics for training vs non-training cases | Training should not materially increase risk |
| Specialist bottleneck | Waiting time and queue length for Security Review and Final Approval | Use `pm4py.discover_performance_dfg`, service/waiting times, and resource utilization | Avoid rising waiting time or concentration |
| Specialist concentration | Share of Security/Approval work handled by top two specialists | Group by `org:resource` for Security Review and Final Approval | Avoid excessive dependence |
| Batch compliance | Quality Check batches only when priority normal/low and SLA > 24h | Filter `Quality Check` events and check batching conditions | Zero violations |
| Policy deviation rate | Assignments not matching recommended policy or hard constraints | Compare actual `assignment_reason` and resource with recommended assignment | Low; exceptions documented |
| Exception rate | Number of approved exceptions | Count `assignment_reason` values such as `urgent_exception`, `overtime_exception`, `supervision_exception` | Monitor trend |
| Continuity preservation rate | Share of high-complexity/high-handover cases kept with current owner | Filter high complexity/high handover and compare assigned resource with `current_owner` | Higher, unless safety/capacity exception |

## Suggested thresholds for monitoring

These should be calibrated from historical data, not imposed blindly.

| Indicator | Example monitoring threshold |
|---|---:|
| Hard skill-rule violations | 0 tolerated |
| High-priority unsupervised skill `< 2` | 0 tolerated |
| Cases with reassignment count `> 2` | Investigate if above 10–15% of active cases |
| Non-urgent assignments to high-overtime-risk resources | Near 0 unless exception |
| Training share for normal/low cases | >= 20% |
| Urgent SLA miss rate | As low as operationally feasible; investigate every miss |
| Security Review waiting time | Monitor trend; alert if median waiting increases materially |
| Workload coefficient of variation | Investigate if persistently high across teams |

## How this supports the policy

The PM4Py outputs can be used in two directions:

### Learning the policy

- `get_service_time` and waiting-time enrichment help estimate how long activities take for different resources and skill levels.
- `discover_handover_of_work_network` helps estimate handover cost and identify risky transitions.
- `discover_activity_based_resource_similarity` helps identify backup resources.
- `discover_organizational_roles` helps detect overdependence on a small specialist group.
- `discover_performance_dfg` shows where Security Review or Final Approval bottlenecks occur.
- `get_variants` helps identify repeated diagnosis/rework loops.

### Auditing the policy

- Compare actual assignments against recommended assignments.
- Measure skill mismatch, supervision compliance, and training share.
- Track SLA misses and near misses.
- Monitor rework/appeal after reassignment or skill mismatch.
- Monitor overtime exposure and workload distribution.
- Detect deviations from approved assignment reasons.

This makes the policy explainable before assignment and auditable after deployment.
