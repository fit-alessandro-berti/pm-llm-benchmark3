# 2. Expected temporal signatures

Use strict overlap, `max(start_i,start_j) < min(complete_i,complete_j)`; touching intervals are adjacent, not overlapping. Equality in the table means equality of recorded values. A smaller tolerance means moving from a 15-minute merge window toward seconds, while still accounting for source precision.

| Hypothesis | Start equality | End equality | Adjacency | Overlap | Recording lag | Source precision | Resource identity reliability | Queue-arrival pattern | Under a smaller time tolerance |
|---|---|---|---|---|---|---|---|---|---|
| Genuine simultaneous batch | Expected for a shared cycle, but item-level starts can differ | Expected for common cycle exit | Not required | Strong, often identical intervals | Usually short for automatic capture; not decisive | Accurate cycle clock strengthens inference | Machine/fixture ID and capacity matter more than worker ID | Items usually available before cycle start | Exact shared cycle survives; incidental near-equalities disappear |
| Start batching/common setup | Same group-start mark | Separate ends are common | May appear among later item tasks | Reported intervals fan out from common start | Can be short despite false per-item starts | Coarse start values can imitate it | A group-button user need not be every item's executor | Typically several items arrive before setup | Exact group-button equality survives; tolerance cannot recover true per-item starts |

The observed exemplars are G1 (shared cycle), G2 (equal start), G3 (equal end), G4/G8 (adjacency), G5 (long overlap under a pooled ID), G6 (bulk form), and G7 (quarter-hour grid). PM4Py labels detect such patterns among an activity/resource pair; they cannot decide which row of this matrix caused a match.

# 3. Consequences for performance analysis

Here “waiting” is `start − queue_arrival`, “service” is `complete − start`, and naive utilization sums service durations against one resource's elapsed time. These are *recorded* metrics. The displayed mean waits, in G1–G8 order, are 4.25, 12.25, 19.5, 13, 15.25, about 103.4, −4.2, and 48.2 minutes. Those figures are not all estimates of physical queue delay.

| Cluster | Waiting-time bias | Service-time bias | Utilization bias | Throughput, bottleneck, and conformance implication |
|---|---|---|---|---|
| G1 | If 09:00 is fixture loading/start, each wait is meaningful; queue order within the fixture is unknown | Three minutes per item may be valid elapsed processing, but 12 item-minutes are one three-minute fixture cycle, not 12 minutes of cell labor | Summing item intervals for one cell overstates load fourfold during the cycle | Four outputs at 09:03 represent one cycle's capacity; a one-item-at-a-time model would falsely mark overlap as nonconforming or the cell as overloaded |
| G2 | A group-button mark at 10:00 makes later items' apparent waits too short if inspection actually begins later | Apparent services of 8/14/21/27 minutes include time awaiting individual attention; 70 summed minutes span only 27 clock minutes | Treating T-B as one worker and summing those intervals inflates busy time | Completion count/order may be sound, but a bottleneck analysis can misplace waiting inside “service”; individual-start conformance is unreliable |
| G3 | Staggered starts may give useful waits if they mark real review begins; otherwise direction is unknown | If reviews finished before 11:30, the 28/20/13/6-minute intervals include time awaiting folder submission; if common signoff is the defined service endpoint, those elapsed durations are valid | 67 summed minutes in a 28-minute window would overstate one worker's active effort unless reviews are truly interleaved | The 11:30 throughput spike and simultaneous completions reflect submission timing; false overlap or completion-order violations can enter conformance checks |

G6 shows why inflated waiting and near-zero service can coexist: assigning an administrative 17:00 mark to **both** lifecycle boundaries moves every ticket's pre-entry interval into `arrival → start`, while collapsing `start → complete` to zero. No conservation law transfers that waiting into measured work. Similarly, G2 can move actual waiting into recorded service by assigning a group start too early.

Only fragments of one activity per case are supplied. No full process path, service-level target, or resource schedule is available, so claims about end-to-end conformance or persistent bottlenecks would exceed the evidence. Count completions for recorded throughput, but do not infer physical production rate from synchronized administrative completions.

# 4. PM4Py and pandas analysis

The script keeps every supplied row in the diagnostic frame, including G6 and G7. It passes rows with nonmissing lifecycle boundaries to PM4Py for **pattern detection only**, reports any rows that cannot be passed, and prints independent diagnostics beside PM4Py categories. PM4Py versions can differ in exact category names and boundary handling; compare the printed categories with the `pattern_hint` and data-quality flags, rather than treating a category as a physical verdict. `merge_distance` is in seconds.

```python
from itertools import combinations
import re
import pandas as pd
import pm4py

META = {
    "G1": ("Apply label", "RBT-7", "PLC", "1 sec"),
    "G2": ("Surface inspection", "T-B", "tablet", "1 min"),
    "G3": ("Release review", "T-C", "desktop_form", "1 min"),
    "G4": ("Pack item", "T-D", "scanner", "1 sec"),
    "G5": ("Root-cause analysis", "analyst_pool", "shared_VDI", "1 min"),
    "G6": ("Close ticket", "T-F", "manual_bulk_form", "1 min"),
    "G7": ("Manual measure", "T-G", "legacy_MES", "15 min"),
    "G8": ("Repair triage", "T-H", "scanner", "1 sec"),
}
# cluster case queue_arrival start complete recorded_at sequence_no
RAW = """

rows = []
for line in RAW.strip().splitlines():
    cluster, case, arrival, start, complete, recorded, seq = line.split()
    activity, resource, source, precision = META[cluster]
    def stamp(value):
        return pd.NaT if value == "-" else pd.Timestamp("2026-05-26 " + value)
    rows.append({
        "cluster": cluster, "case": case, "activity": activity,
        "resource": resource, "source": source, "precision": precision,
        "queue_arrival": stamp(arrival), "start": stamp(start),
        "complete": stamp(complete), "recorded_at": stamp(recorded),
        "sequence_no": int(seq),
    })
df = pd.DataFrame(rows)
df["case:concept:name"] = df["case"]
df["concept:name"] = df["activity"]
df["org:resource"] = df["resource"]
df["start_timestamp"] = df["start"]
df["time:timestamp"] = df["complete"]

# Do not silently discard missing or suspect lifecycle data. Only missing boundaries
# are ineligible for interval batch discovery; they remain in df and in diagnostics.
valid = df["start_timestamp"].notna() & df["time:timestamp"].notna()
valid &= df["start_timestamp"] <= df["time:timestamp"]
log = pm4py.format_dataframe(
    df.loc[valid].copy(), case_id="case:concept:name",
    activity_key="concept:name", timestamp_key="time:timestamp"

def pair_overlap_and_peak(g):
    pairs, overlap = 0, 0
    points = []
    for _, same_resource in g.groupby("resource"):
        intervals = [(a, b) for a, b in zip(same_resource.start,
                    same_resource.complete) if pd.notna(a) and pd.notna(b) and a <= b]
        for (a, b), (c, d) in combinations(intervals, 2):
            pairs += 1
            overlap += max(a, c) < min(b, d)
        for a, b in intervals:
            if a < b:
                points.extend([(a, 1), (b, -1)])
    active = peak = 0
    for _, delta in sorted(points, key=lambda x: (x[0], x[1])):
        active += delta  # ends precede starts at the same instant
        peak = max(peak, active)
    return (overlap / pairs if pairs else float("nan")), peak

def max_equal_size(s):
    counts = s.dropna().value_counts()
    return int(counts.max()) if not counts.empty else 0

def quarter_fraction(s):
    s = s.dropna()
    return ((s.dt.minute % 15 == 0) & (s.dt.second == 0)).mean() if len(s) else float("nan")

    overlap_rate, peak = pair_overlap_and_peak(g)
    lag = (g.recorded_at - g.complete).dt.total_seconds()

    if start_equal == len(g) and end_equal == len(g):

    elif start_equal == len(g):

    elif end_equal == len(g):
        hint = "common-end"

        hint = "sequential"
    elif overlap_rate > 0:
        hint = "overlapping"
    else:
        hint = "mixed"
    flags = []
    if (g.start == g.complete).any(): flags.append("zero-service")
    if (g.start < g.queue_arrival).any(): flags.append("start-before-arrival")
    if cluster == "G5": flags.append("shared-account")
    if cluster == "G7": flags.append("rounded-lifecycle")
    if cluster == "G2": flags.append("group-start-button")
    if cluster == "G3": flags.append("folder-submission")
    if cluster == "G8": flags.append("clock-mismatch-possible")
    if (~valid.loc[g.index]).any(): flags.append("missing-or-invalid-PM4Py-input")
    records.append({
        "cluster": cluster, "n": len(g), "PM4Py_rows": int(valid.loc[g.index].sum()),

        "equal_end_max": end_equal, "adjacent_edges": adjacent,

        "lag_median_s": lag.median(), "lag_max_s": lag.max(),
        "start_quarter_frac": round(quarter_fraction(g.start), 2),
        "end_quarter_frac": round(quarter_fraction(g.complete), 2),
        "lifecycle_minute_frac": round(pd.concat([
            g.start.dropna(), g.complete.dropna()
        ]).dt.second.eq(0).mean(), 2),
        "source_precision": g.precision.iloc[0],
        "arrivals_by_first_start": int((g.queue_arrival <= first_start).sum()),
        "arrival_span_min": (g.queue_arrival.max() - g.queue_arrival.min()).total_seconds() / 60,
        "mean_naive_wait_min": round(wait.mean(), 2),
        "negative_waits": int((wait < 0).sum()),
        "flags": ",".join(flags) or "none",
    })
report = pd.DataFrame(records).set_index("cluster")

# The usual PM4Py result maps (resource, activity) to category -> batches.
# Walk its keys so minor container differences do not hide a detected category.
labels = ("Simultaneous", "Batching on Start", "Batching on End",
          "Sequential", "Concurrent")
def detected_categories(result):
    out = {cluster: set() for cluster in META}
    def walk(node, path=()):
        if isinstance(node, dict):
            for key, value in node.items():
                walk(value, path + (str(key),))
        elif isinstance(node, (list, tuple, set)) and len(node):
            key_path = re.sub(r"[_-]+", " ", " ".join(path)).lower()
            for cluster, (activity, _, _, _) in META.items():
                if activity.lower() in key_path:
                    for label in labels:
                        if label.lower() in key_path:

    walk(result)
    return {cluster: ",".join(sorted(cats)) or "none/unparsed"
            for cluster, cats in out.items()}

for merge_distance in (1, 900):
```

# 5. Robustness and alternative explanations

If resource IDs are trusted as individual executors, G2/G3/G5 contain reported overlaps requiring genuine multitasking, waiting within lifecycle intervals, or bad lifecycle boundaries. In particular, G5 reports four simultaneous open intervals on one ID. If IDs may be shared, G5 is consistent with parallel analysts, but the stated maximum of three means four *exclusive* active tasks still cannot all be true from 13:12 to 13:20. G1's machine ID is a capacity-bearing fixture rather than a single human; its four-way overlap is physically plausible. G4/G8's nonoverlap is robust under either identity assumption, though a shared ID would weaken attribution to one worker.

If displayed times are exact and source clocks synchronized, G4/G8 are clean serial runs, G7 contains impossible pre-arrival starts, and G6 genuinely has zero measured service. If lifecycle times are interval-censored, G7's apparent simultaneity and negative waits can vanish. **Illustrative assumption, not a recovered rounding rule:** if starts are floored to the previous quarter hour and completions ceiled to the next, each G7 true start could lie in `[14:00,14:15)` and each true completion in `(14:00,14:15]`; queue arrival still constrains each start to occur after its arrival. An alternative rounding rule gives different intervals, so the actual rule must be obtained before computing service or waiting bounds. G1/G4/G8 claim one-second source precision, yet their lifecycle values are minute aligned; second-level insert times alone do not establish second-level execution accuracy. Clock offset between upstream arrivals and local starts adds another interval of uncertainty to *every* queue wait, especially G8's link to the safety check.

At least five patterns have multiple physical readings: G1's equal boundaries could be a four-item fixture cycle or one PLC cycle stamp applied to serial internal steps; G2's equal starts could mark joint setup or a group-button shortcut before serial work; G3's equal ends could be common authorization or folder submission after separate finishes; G6's equal zero intervals could be an actual mass-close action or retrospective entry; G7's equal intervals could hide serial work or overlap within the same rounded quarter hour. Adjacency in G4/G8 similarly identifies a serial run but does not identify the scheduling policy or reason for a preceding queue.

# 6. Data-collection redesign

1. **Capture physical lifecycle events first:** per-case first touch, active work start/finish, pause/resume, and actual decision/release time. Keep setup and group start, folder signoff, and administrative submission as distinct event types. This directly resolves G2/G3/G6 and makes active effort separate from elapsed occupancy.
2. **Retain both execution and recording clocks:** store immutable `event_occurred_at`, `recorded_at`, and ingestion time with source, event type, sequence number, and correction history. Bulk forms should link to the original action time, leaving the entry time intact for audit.
3. **Calibrate clocks and preserve precision metadata:** monitor offset and drift between PLC, scanner, tablet, MES, safety system, and upstream queue; record timezone, nominal resolution, rounding rule, and estimated accuracy per field. Preserve raw values before rounding. This is essential for G7 and G8 queue estimates.
4. **Disambiguate workers and capacity:** capture badge identity separately from login, workstation/machine identity, fixture capacity, staffing and availability intervals, and handoffs. A shared account should never be used as a one-person utilization denominator.
5. **Record operational grouping:** persist batch/fixture/folder/run ID, membership, group setup and release events, and the action that formed the group. This distinguishes an actual batch from coincident timestamps and an ordinary serial queue.
6. **Log capacity loss explicitly:** downtime, safety checks, break/maintenance, blocked/unblocked, and return-to-service events on the same synchronized timeline, with affected workstation and reason. This tests whether G8's queue grew during unavailable capacity.

# 7. Final adjudication

G1 can be treated with high confidence as a **shared automated cycle**, while its internal per-item effort remains unknown. G4 and G8 can be treated with high confidence as **recorded serial runs**; whether they are deliberate batches is unresolved. G2 is a strong common-start *logging/setup* pattern, G3 a strong common-end *submission* pattern, and G5 a strong shared-identity warning. These diagnoses are stronger than any inferred labor-time or bottleneck conclusion.

Exclude G6's zero service and administrative starts from point-valued queue/service analysis until action times are recovered. Exclude G7's point waits and services; represent its lifecycle times as interval-censored only after the rounding rule and clock relationship are established. G2/G3 need corrected item-level boundaries before estimating active service or individual waits from the affected boundary. G5 needs badge-level identity and active-work semantics before resource utilization or worker conformance analysis. G8's long waits are provisional until scanner, upstream, and safety clocks and workstation availability are reconciled. G1/G4's waits and G4/G8's scanner service durations are the best-supported local performance measures, subject to ordinary clock and event-definition validation.
