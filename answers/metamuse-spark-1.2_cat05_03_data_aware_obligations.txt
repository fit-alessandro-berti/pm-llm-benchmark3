## 1. Temporal Data Semantics

**Reconstruction principle: event-time, point-in-time state.**

*   **Latest-known-value snapshot:** For each case, state is reconstructed by sorting by `time:timestamp` then `event_index` (source-system order) and forward-filling attributes. The value observed at event `e` is valid from `e.timestamp+e.event_index` inclusive until next update. Query is always *state at e* = forward-fill up to and including `e`.
*   **Blanks = no update:** Empty cells mean no assertion. We do *not* fill with `null/0/LOW`. Implemented via `groupby(...).ffill()`. A missing value stays `NaN/Unknown` until an explicit update.
*   **No backward copy / no final-state leakage:** Final `amount/risk/jurisdiction/customer_type` is never projected backwards. E.g. TX-305 settlement `150,000` on `2026-04-07` is not copied to `Release_Funds` on `2026-04-06`. TX-311 final `DE` is not copied to `Enhanced_Review` at same timestamp but earlier `event_index`.
*   **Equal timestamps:** `event_index` is tie-breaker. If `t1==t2` then `index1<index2` => `e1` happens-before `e2`. Material consequence: TX-311 `Enhanced_Review (16:20,index3)` happens *before* `Update_Jurisdiction DE (16:20,index4)`; state during review is still `US`, state at release is `DE`.
*   **Material data change:** The latest event that changes a decision-relevant attribute: `Update_Amount`, `Update_Jurisdiction`, `Update_Customer_Type`, `Risk_Reclassify`, `Create_Transaction`. For R4 only amount increases >20% are material to invalidation; decreases and <=20% increases do not invalidate. For R1 ordering (`after latest material change`) we apply R4 definition: only >20% increases and jurisdiction/customer-type changes that affect trigger are material; otherwise review remains valid.
*   **Four times distinguished:**
    1.  `event_time` = `time:timestamp` + `event_index` when state becomes effective (R7).
    2.  `effective_time` = exemption `effective_from` - when obligation is waived.
    3.  `record_time` = `Record_Exemption` insertion time (e.g. 11:00) - when system recorded.
    4.  `evidence_time` = signature/witness time when approval can be *proved* to have existed. A qualified signature timestamp proves existence at that time; a displayed field or `record_time` alone does not ; a late `record_time` *can* be evidence of earlier `evidence_time` only if outage + qualified signature corroborates it (EX-77 vs EX-88).

## 2. Normalized Rule Table

| Rule | Trigger event and condition (evaluated on state at trigger) | Required prior/subsequent event | Ordering constraint (direction defined) | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| **R1** Foreign high-value | `Release_Funds` **AND** `jurisdiction != DE` **AND** `amount >=100,000` | `Enhanced_Review` | `latest_material_change < Enhanced_Review < Release_Funds` (strict). Material = R4 >20% increase or jurisdiction change that created trigger. | Latest known `jurisdiction, amount` at `Release_Funds` inclusive | Valid exemption waiving R1 (scope matches, effective  Release, not expired, Head_Compliance approved, evidence_time  Release) | If `amount==Unknown` or `jurisdiction==Unknown` cannot establish `>=100k` or `!=DE` => **INDETERMINATE** unless Enhanced exists that would satisfy regardless | Exemption must have `Head_Compliance` + signature/witness proving approval existed before Release |
| **R2** High-risk/PEP | `Release_Funds` **AND** (`risk_level==HIGH` **OR** `customer_type==PEP`) | `Enhanced_Review` **AND** `Compliance_Approve` (both mandatory) | `Enhanced_Review < Compliance_Approve < Release_Funds`. Compliance must review *enhanced* packet, not standard-only. | Latest `risk_level, customer_type` at Release | No waiver by R1-only exemptions (EX-77/88 scope R1 only) | If `risk==Unknown` or `customer_type==Unknown` => INDETERMINATE (cannot exclude HIGH/PEP) | Compliance resource `hc*` & packet linkage |
| **R3** Sanctions update | `Release_Funds` where `jurisdiction == J` **AND** `Sanctions_List_Update(J)` occurs with `last_Sanctions_Screen < List_Update < Release` | new `Sanctions_Screen` | `List_Update < new_Sanctions_Screen < Release` | Jurisdiction at Release + screen history | None | If jurisdiction unknown => INDETERMINATE for XZ-like risk | List update and screen timestamps |
| **R4** Amount change invalidation | Any `Update_Amount` with `new > old*1.20` after `last_Review` (Standard or Enhanced) | re-review invalidates prior review for amount-dependent obligations (R1) | `last_Review < amount_increase(>20%)` => review invalid unless new review after increase | Amount history with forward-fill; unknown->known not classifiable | Decrease never invalidates; increase from unknown not classifiable | Increase from unknown => INDETERMINATE for R1 dependency | Amount provenance at each event |
| **R5** Exemption validity | Applied when R1 triggered | Exemption record | `evidence_time  effective_from  Release < expires` **AND** `approval == Head_Compliance` **AND** scope matches jurisdiction/customer/amount at Release | Exemption register joined on `exemption_id` at Release | Only if all conjuncts proven | Backdated display without qualified signature => insufficient => exemption invalid | Qualified signature timestamp (EX-77) vs cert creation time (EX-88) + witness independence |
| **R6** Missing data | Any trigger evaluation with NaN | — | — | — | Do not default to low-risk | Classify INDETERMINATE when decisive trigger cannot be established or excluded | Other evidence (e.g. immutable release payload) to resolve |
| **R7** Event-time semantics | All rules | — | Use `order = (timestamp, event_index)` | `state_at(event)=ffill(state)` | Final case attribute not copied backward | — | `event_index` tie-break stated |

**Concise formal pseudo-logic**

```text
Order(e1,e2) := e1.timestamp < e2.timestamp  (e1.timestamp=e2.timestamp  e1.index<e2.index)
State(C,t) := ffill({e.amount,e.risk,e.jurisdiction,e.customer_type | eC  Order(e,t) })

ValidReview(C, release) :=
   rC: r.activity=Enhanced_Review  Order(r,release) 
   mMaterialChanges(C): Order(m,r)  ¬Material(m,r) 
  // Material(m,r) per R4: amount increase >20% between amount at r and amount at release

R1(C,rel) :=
 IF State(C,rel).jurisdiction != "DE"  State(C,rel).amount 100000
 THEN ValidReview(C,rel)  ValidExemption(C,rel,R1) ELSE true

R2(C,rel) :=
 IF State(C,rel).risk="HIGH"  State(C,rel).customer_type="PEP"
 THEN  e,cC: e.activity=Enhanced_Review  c.activity=Compliance_Approve
       Order(e,c)  Order(c,rel)  c.packet_type != StandardOnly ELSE true

R3(C,rel) :=
 IF  uC: u.activity=Sanctions_List_Update  u.jurisdiction = State(C,rel).jurisdiction
        Order(last_Screen(C,rel), u)  Order(u,rel)
 THEN  sC: s.activity=Sanctions_Screen  Order(u,s)  Order(s,rel) ELSE true

R4Invalid( review, release ) :=
  upd_amount: Order(review,upd_amount)Order(upd_amount,release)
    upd_amount.amount > amount_at(review)*1.20
 // from unknown => truth value = Unknown => INDETERMINATE

ValidExemption(C,rel,rule) :=
  ex: C.exemption_id=ex.id  ex.rule_scoperule  ex.approved_by=Head_Compliance
    ex.effective_from  rel.timestamp  ex.expires  ScopeMatches(ex,State(C,rel))
    EvidenceTime(ex)  rel.timestamp  // qualified signature  rel; backdated display alone fails

R6: IF State(C,rel).amount = Unknown  (cannot prove <100k) THEN verdict=INDETERMINATE
R7: all predicates use State(C,rel) not State(C,final_event)
```

Defeasible priority: `ValidExemption` defeats `R1` violation; `R4` defeats `ValidReview`; qualified signature defeats late `record_time` (EX-77); cert-creation time defeats displayed approval (EX-88).

## 4. Ambiguities and Alternative Readings

**TX-302 – alternative fails if outage not documented:** Primary = JUSTIFIED_EXCEPTION. If we *disallow* late-record evidence and require `record_time  Release`, EX-77 would be invalid and we fall back to Enhanced_Review path  still **COMPLIANT**. Only if we both reject signature and argue material change after 09:20 would violation arise, but no such change exists. Interpretation that would flip to NONCOMPLIANT: treat exemption as only valid after DB insert 11:00 (record-time = effective-time fallacy) + claim Enhanced not jurisdictionally scoped – contradicts R5 and evidence table.

**TX-305 – INDETERMINATE, three credible readings:**
*   *Strict R6 (chosen):* INDETERMINATE. Amount at Release Unknown  cannot prove R1 triggered nor excluded. Settlement 150k next day is not immutable release payload; copying forward is leakage.
*   *If settlement trusted as release amount:* Then `150k 100k`  R1 triggered; `Enhanced 11:15` exists before Release but amount at review Unknown  R4 increase from unknown not classifiable  still INDETERMINATE unless you assume review covered 150k.
*   *If you silently default unknown to <100k:* Would incorrectly label COMPLIANT low-risk default – forbidden by R6.

Resolving evidence: immutable `release_payload_amount` logged at `Release_Funds`, enhanced review packet amount field, amount feed provenance.

**TX-310 – contradictory evidence, no single canonical answer:**
*   *Chosen (strict qualified-signature standard):* **NONCOMPLIANT**. R5 requires `evidence_time  Release`. Cert created 10:30 > 10:00  display 08:50 is backdated, not proof. Oral witness (requester) is self-serving  exemption invalid. R1 remains unsatisfied (only Standard).
*   *Alternative defeasible reading  INDETERMINATE or JUSTIFIED_EXCEPTION:* If tribunal credits oral approval 08:45 as sufficient despite lack of signature, and treats backdated field as record-time error but approves effective_time logic, then EX-88 scope matches AE/CORPORATE 250k, effective 08:00 10:00, waives R1  JUSTIFIED_EXCEPTION. If you credit witness partially but not conclusively  INDETERMINATE (cannot decide if exemption existed). Evidence that would flip to compliant: independent Head_Compliance signature timestamp 10:00, or system log of approval call.

**TX-311 – same-timestamp ordering is decisive:**
*   *Chosen:* COMPLIANT. Trigger evaluated at Release snapshot `DE`, so R1 inactive. `Enhanced` at idx3 occurred while still `US/115k` but jurisdiction flipped to DE at idx4 after review. Because material change defined per R4 is >20% *increase* after review, the 27% increase happened *before* review (16:1016:20), so review remains valid if needed. Release in DE needs no review.
*   *Alternative that would yield NONCOMPLIANT:* Ignore `event_index` and assume arbitrary or reverse order, or evaluate R1 at review time not release time (i.e. claim US trigger requires post-jurisdiction-change re-review). Or treat *any* jurisdiction change after review as invalidating it even when it deactivates trigger – would require new review in DE despite exemption for DE. Also if you evaluate jurisdiction at review time incorrectly you would demand another review.

**Two additional ambiguous cases:**
*   **TX-306 – materiality threshold interpretation:** Chosen COMPLIANT (<20% does not invalidate). Alternative strict reading: *any* amount change after review invalidates it  `Update 12:30` would void `Enhanced 12:15`  NONCOMPLIANT needing re-review. Formalization fixes this by defining material as >20% per R4.
*   **TX-308 – decrease misunderstanding:** Chosen COMPLIANT (R4 decrease not invalidating). Alternative: treat decrease to 100k as still triggered but argue review at 140k insufficiently conservative  require re-review  NONCOMPLIANT. Policy explicitly rejects that.

*What the code does vs what requires human judgment:* The script correctly forward-fills state without leakage, resolves same-timestamp order, computes state at `Release_Funds`, tracks last reviews/screens, and produces coarse `REVIEW_REQUIRED` flags. It **does not hard-code** final classifications; `REVIEW_REQUIRED`, `REVIEW_REQUIRED_UNKNOWN`, `COARSE_PASS_NEEDS_R4_CHECK` explicitly signal that a human must evaluate R4 >20% history, exemption evidence quality, exact `event_index` ordering, and missing-data semantics – precisely the limits of control-flow conformance.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1.  **Final-state leakage:** Control-flow miners that use case attributes only at end (e.g. `pm4py` case-level enrichment) would copy `TX-305 Settlement 150k (2026-04-07)` or `TX-311 final DE` back to earlier events, making R1 appear triggered / not triggered incorrectly. Event-time state requires `ffill` up to event, not `bfill` from final.
2.  **Post-hoc exemption / record vs evidence time:** A DECLARE `Response(Release, Record_Exemption)` or existence constraint would see `EX-88 Record_Exemption 11:00` after `Release 10:00` and consider it satisfied, ignoring that the qualified signature `10:30 > Release` invalidates `evidence_time  Release`. Conversely `EX-77` would be flagged as late but is actually valid due to outage-documented `evidence_time 09:05`.
3.  **Material changes after review (R4):** `ChainResponse(Enhanced, Release)` is satisfied for `TX-309` (`Enhanced 15:25 < Release 15:35`) and `TX-306` but R4 invalidates `TX-309` due to `22.9%` increase *after* review while `TX-306` `4.5%` remains valid. Pure ordering cannot express `amount > 1.20 * amount_at_review`.
4.  **Conditional activation (data-aware triggers):** R1 only fires if `jurisdiction != DE  amount 100k`; R2 only if `HIGH  PEP`; R3 only if jurisdiction added after last screen. Standard `Response/Precedence` are unconditional; they would demand `Enhanced_Review` even for `TX-307 DE` (R1 not triggered) or miss `TX-301` violation when amount later crosses threshold.
5.  **Missing data / unknown values:** Control-flow assumes absent events = violation, present = pass. `TX-305 amount Unknown` cannot be treated as `<100k` (low-risk default) nor `100k`; R6 demands `INDETERMINATE`. A conformance checker without `NaN` handling would silently default and misclassify.
6.  **Same-timestamp ordering:** Two events at `16:20` `TX-311` have deterministic `event_index` order `Enhanced (3) < Jurisdiction DE (4)`. A trace model that collapses timestamps to a set or sorts stably would nondeterministically evaluate `DE` at review time, flipping R1 applicability.
7.  **Standard vs Enhanced and packet semantics:** `TX-307` has `Standard_Review + Compliance_Approve` satisfying `Compliance after Review` control-flow, but policy requires `Enhanced` packet; semantic fact `Standard  Enhanced` and `standard packet  enhanced packet` is invisible to activity labels alone.

## 7. Recommended Logging and Control Improvements

*   **Immutable release payload:** Log `amount, jurisdiction, risk, customer_type, exemption_id` as explicit attributes on `Release_Funds` event (effective values at that instant) plus hash, rather than relying on ffilled prior updates; prevents inference disputes (`TX-305`) and enables post-hoc audit.
*   **Bitemporal timestamps:** Every mutable attribute update should store `effective_time` (when business value changes), `record_time` (DB insert), and `event_time` (what we evaluated). Exemptions must store `displayed_approval`, `qualified_signature_timestamp`, `certificate_creation_time`, `effective_from`, `expires`, `record_time`.
*   **Rule version & scope on event:** Add `policy_version, rule_id, exemption_scope_jur/cust/amt` to `Release_Funds` so replay with future rule changes remains determinate.
*   **Change provenance:** `Update_Amount` should include `old_amount, new_amount, reason, source_system, is_material_flag` (>20% computed at write time) and link to review id it invalidates.
*   **Stable ordering:** Enforce monotonically increasing `event_index` globally per case, never reuse timestamp without index; optionally add `logical_clock`. Document tie-breaker in SOP.
*   **Review packet linkage:** `Enhanced_Review` and `Compliance_Approve` must reference `review_id, packet_hash, amount_at_review, jurisdiction_at_review`; compliance event must state `packet_type=Enhanced|Standard` to prevent `TX-307` ambiguity.
*   **Exemption lifecycle:** Require qualified signature *before* effectiveness; block releases referencing `exemption_id` where `evidence_time > release_time` or `cert_created > release_time`; independent approver (not requester witness).
*   **Data quality gates:** Make `amount, jurisdiction, risk, customer_type` mandatory at `Create_Transaction`; feed unavailable  explicit `Unknown` with blocking control until resolved, rather than blank.
*   **Sanctions screening immutability:** `Sanctions_Screen` result and `List_Update` version id logged; automated check `List_Update after last Screen  block Release until new Screen`.
