## 1. Conformance semantics

Object-centric process mining evaluates multi-object logs against partial normative models. Under open-world semantics, absence from a model does not imply noncompliance. We distinguish seven deviation classes:

- **Forbidden behavior**: Explicit negative constraint breaches (e.g., $N3$, $T6$, $E10$). Strict violations, security breaches, or unauthorized process bypasses where zero tolerance applies unless proven to be data artifacts.
- **Missing mandatory behavior**: Omission of expected events, relations, or transitions within defined scopes (e.g., unparented items under $E2$, unvalidated orders under $N1$).
- **Unexpected but unregulated behavior**: Unmodeled relations outside norm coverage that violate no constraints (e.g., customer links under $T4$, compliance reviews under $E9$/$T5$, package-delivery codeath); permissible under open-world semantics.
- **Typical-pattern absence**: Deviations from standard happy paths where the norm accommodates legitimate business exceptions (e.g., write-offs or open terms under $N5$, unapplied cash under $T3$).
- **Likely data-quality error**: Spurious or missing relations from ETL join or extraction defects rather than physical execution (e.g., telemetry key collisions under $E10$, unextracted carrier strings under $E6$).
- **Abstraction mismatch**: Discrepancies where graph models oversimplify higher-order temporal rules (e.g., evaluating an "eventually-follows" rule as a rigid directly-follows DFG edge).
- **Insufficient evidence**: Aggregated graph summaries lacking granular attributes (timestamps, user roles) needed for definitive classification.

### Open-World vs. Closed-World Assumptions

Under a **Closed-World Assumption (CWA)**, all unmodeled behavior is treated as noncompliant, generating false positives in multi-object logs with concurrent lifecycles. We apply a hybrid framework:
1. **Closed-World Scope**: Applies *strictly* to `forbidden` relations and `mandatory` requirements within their stated scope.
2. **Open-World Scope**: Governs all other behaviors; unmodeled transitions and interactions remain permissible unless an explicit negative rule is breached.

## 3. Detailed reasoning by model family

### 3.1. OC-DFG (Object-Centric Directly-Follows Graphs)
- **Capabilities**: Evaluates projected single-object sequential transitions ($e_1 \xrightarrow{ot} e_2$), routing frequencies, and immediate successors.
- **Limitations**: Cannot model cross-object synchronization, parallel branching across types, or non-adjacent temporal constraints.
- **Abstraction Pitfall & "Eventually Expected" Trap ($N1$)**: Norm $N1$ expects standard Orders to eventually undergo validation. However, OC-DFG enforces immediate adjacency. The 2 Orders routed to `Manual Compliance Review` break the directly-follows edge `Create Order -> Validate Order`. A naive DFG check flags these as violations despite fulfilling eventual validation, illustrating how rigid sequential models misdiagnose valid multi-step paths.
- **Forbidden Paths ($N3$) & Concurrency ($N2$)**: DFG analysis detects 2 instances of `Cancel Order -> Dispatch Package`, an explicit breach of $N3$. Conversely, the split between 72 `Validate -> Issue Invoice` and 83 `Validate -> Close Order` captures normal interleaving of billing and fulfillment rather than noncompliance.

### 3.2. OTG (Object Topology Graphs)
- **Capabilities**: Establishes structural topologies across object types: object interactions, cobirth (shared creation), and codeath (shared termination).
- **Limitations**: Structural and atemporal; cannot enforce event sequencing, timing, or intra-object state progression.
- **Cobirth Violations ($T6$) vs. Unregulated Topologies ($T4, T5$, Codeath)**: $T6$ explicitly forbids `(Order, object_cobirth, Payment)`. Detecting 1 cobirth edge establishes a severe architectural violation where an asynchronous payment model was bypassed. In contrast, 100 `Order-Customer` links, 3 `Order-RiskCase` links, and 7 `Package-Delivery` codeath edges represent valid open-world structures that must not be treated as noncompliant.

### 3.3. ET–OT (Event Type to Object Type Graphs)
- **Capabilities**: Validates multi-object event interface signatures and relational cardinality (e.g., verifying `Add Item` binds to `Item` and `Order`).
- **Limitations**: Cannot inspect payload attributes, state validity, or cross-event execution flow.
- **Relational Deficits ($E2$), Data Quality ($E10$), and Attributes ($E6$)**: ET–OT reveals 2 unparented `Add Item` events lacking `Order` links ($E2$). For $E10$ (`Sensor Heartbeat - Invoice`), ET–OT detects a forbidden link that domain context shows is an ETL join collision rather than financial tampering. For $E6$, 2 `Dispatch Package` events lack `Delivery` object nodes because carrier references were stored as event attribute strings, highlighting an extraction gap.

## 4. Mandatory, forbidden, typical, and unregulated behavior

### Mandatory Behavior
- **`Create Order -> Validate Order` (98 Orders)**: Conforms to $N1$. *Condition change*: Non-direct orders conform under an eventually-follows scope, but appear deficient under directly-follows parsing.
- **`Pack Package -> Dispatch Package` (198 Packages)**: Conforms to $N4$.
- **Conforming Bindings & Topology**: `Create Order - Order` (100, $E1$), `Add Item - Item` (1450, $E3$), `Pack Package - Package` (200, $E4$), `Dispatch Package - Package` (200, $E5$), `Record Payment - Payment` (93, $E7$), `Order - Item` (1450, $T1$), `Package - Delivery` (200, $T2$).
- **Mandatory Deficits**: `Add Item - Order` (1448/1450, $E2$); `Dispatch Package - Delivery` (198/200, $E6$; extraction deficit); `Record Payment - Invoice` (92/93, $E8$; shifts to Typical if unapplied cash).

### Forbidden Behavior
- **`Order: Cancel Order -> Dispatch Package` (2 Orders)**: Violates $N3$. Critical process breach.
- **`Order object_cobirth Payment` (1 edge)**: Violates $T6$. High-severity architectural bypass.
- **`Sensor Heartbeat - Invoice` (1 event)**: Violates $E10$. *Condition change*: Data-Quality error if an integer join collision; Compliance Breach if telemetry was intentionally attached to ledgers.

### Typical Behavior
- **`Order: Validate Order -> Close Order` (83 Orders)**: Conforms to $N2$.
- **`Invoice: Issue Invoice -> Record Payment` (92 Invoices)**: Conforms to $N5$ and $T3$.
- **`Invoice: Issue Invoice -> Write Off` (4 Invoices)**: Legitimate exception to $N5$ (bad debt).
- **`Invoice: Issue Invoice with no successor` (14 Invoices)**: Legitimate exception to $N5$ (open credit terms).
- **`Record Payment` without Invoice (1 event)**: Conforms to $T3$ exception *if* authenticated as unapplied cash.

### Unregulated Behavior
- **`Order: Create Order -> Manual Compliance Review` (3 Orders)**: Permissible pre-validation routing.
- **`Manual Compliance Review` with `RiskCase` (3, $E9$) and `Customer` (3)**: Permissible screening.
- **`Order - RiskCase` (3, $T5$) and `Order - Customer` (100, $T4$)**: Permissible topologies.
- **`Package object_codeath Delivery` (7 edges)**: Permissible shared termination.
- **`Order: Reopen Order -> Close Order` (1 Order, $N6$)**: Permissible post-closure adjustment.
- **`Order: Validate Order -> Issue Invoice` (72 Orders)**: Permissible unmodeled billing step.

## 5. PM4Py conformance code sketch

```python
"""
Object-Centric Process Mining (OCPM) Multi-Layered Conformance Pipeline
======================================================================
Assumes:
  - ocel: Observed PM4Py OCEL 2.0 object.
  - norm_ocdfg: dict mapping object_type -> set of normative directly-follows edges.
  - norm_otg: tuple (interaction_edges, cobirth_edges, codeath_edges).
  - norm_etot: tuple (mandatory_etot_edges, forbidden_etot_edges).

Normative metadata (mandatory, forbidden, typical, unspecified) cannot be represented
in raw graph adjacency matrices alone and is maintained in NORM_SEMANTIC_REGISTRY.
"""

import pm4py
from typing import Any, Dict, List, Set, Tuple

# External Normative Metadata Registry defining semantic status and scopes
NORM_SEMANTIC_REGISTRY: Dict[str, Dict[Tuple, Dict[str, Any]]] = {
    "OC-DFG": {
        ("Order", "Create Order", "Validate Order"): {"status": "mandatory", "id": "N1", "temporal": "eventually"},
        ("Order", "Validate Order", "Close Order"): {"status": "typical", "id": "N2"},
        ("Order", "Cancel Order", "Dispatch Package"): {"status": "forbidden", "id": "N3"},
        ("Package", "Pack Package", "Dispatch Package"): {"status": "mandatory", "id": "N4"},
        ("Invoice", "Issue Invoice", "Record Payment"): {"status": "typical", "id": "N5"},
        ("Order", "Reopen Order", "Close Order"): {"status": "unspecified", "id": "N6"},
    },
    "OTG": {
        ("Order", "object_interaction", "Item"): {"status": "mandatory", "id": "T1"},
        ("Package", "object_interaction", "Delivery"): {"status": "mandatory", "id": "T2"},
        ("Invoice", "object_interaction", "Payment"): {"status": "typical", "id": "T3"},
        ("Order", "object_interaction", "Customer"): {"status": "unspecified", "id": "T4"},
        ("Order", "object_interaction", "RiskCase"): {"status": "unspecified", "id": "T5"},
        ("Order", "object_cobirth", "Payment"): {"status": "forbidden", "id": "T6"},
    },
    "ET-OT": {
        ("Create Order", "Order"): {"status": "mandatory", "id": "E1"},
        ("Add Item", "Order"): {"status": "mandatory", "id": "E2"},
        ("Add Item", "Item"): {"status": "mandatory", "id": "E3"},
        ("Pack Package", "Package"): {"status": "mandatory", "id": "E4"},
        ("Dispatch Package", "Package"): {"status": "mandatory", "id": "E5"},
        ("Dispatch Package", "Delivery"): {"status": "mandatory", "id": "E6"},
        ("Record Payment", "Payment"): {"status": "mandatory", "id": "E7"},
        ("Record Payment", "Invoice"): {"status": "mandatory", "id": "E8", "allow_unapplied_cash": True},
        ("Manual Compliance Review", "RiskCase"): {"status": "unspecified", "id": "E9"},
        ("Sensor Heartbeat", "Invoice"): {"status": "forbidden", "id": "E10"},
    }
}


def run_object_centric_conformance(
    ocel: Any,
    norm_ocdfg: Dict[str, Set[Tuple[str, str]]],
    norm_otg: Tuple[Set[Tuple[str, str]], Set[Tuple[str, str]], Set[Tuple[str, str]]],
    norm_etot: Tuple[Set[Tuple[str, str]], Set[Tuple[str, str]]]
) -> Dict[str, Any]:
    """
    Executes PM4Py discovery and structural conformance, preserves raw diagnostics,
    and applies a semantic interpretation layer over the results.
    """
    results: Dict[str, Any] = {
        "raw_discovered": {},
        "raw_diagnostics": {},
        "semantic_findings": []
    }

    # Step 1: Discover observed models from log
    discovered_ocdfg = pm4py.discover_ocdfg(ocel)
    discovered_otg = pm4py.discover_otg(ocel)
    discovered_etot = pm4py.discover_etot(ocel)

    results["raw_discovered"] = {
        "ocdfg": discovered_ocdfg,
        "otg": discovered_otg,
        "etot": discovered_etot
    }

    # Step 2: PM4Py structural conformance checking
    results["raw_diagnostics"] = {
        "ocdfg": pm4py.conformance_ocdfg(ocel, norm_ocdfg),
        "otg": pm4py.conformance_otg(ocel, norm_otg),
        "etot": pm4py.conformance_etot(ocel, norm_etot)
    }

    # Step 3: Semantic interpretation layer

    # 3.1 Evaluate OC-DFG observed transitions
    for ot, dfg_dict in discovered_ocdfg.items():
        for (src, tgt), count in dfg_dict.items():
            key = (ot, src, tgt)
            meta = NORM_SEMANTIC_REGISTRY["OC-DFG"].get(key)

            if meta is None:
                results["semantic_findings"].append({
                    "family": "OC-DFG", "element": key, "count": count,
                    "classification": "UNEXPECTED_BUT_UNREGULATED", "severity": "INFORMATIONAL"
                })
            elif meta["status"] == "forbidden":
                results["semantic_findings"].append({
                    "family": "OC-DFG", "element": key, "count": count, "norm_id": meta["id"],
                    "classification": "FORBIDDEN_BEHAVIOR", "severity": "CRITICAL"
                })
            elif meta["status"] == "typical":
                results["semantic_findings"].append({
                    "family": "OC-DFG", "element": key, "count": count, "norm_id": meta["id"],
                    "classification": "TYPICAL_CONFORMING", "severity": "NONE"
                })
            elif meta["status"] == "mandatory":
                results["semantic_findings"].append({
                    "family": "OC-DFG", "element": key, "count": count, "norm_id": meta["id"],
                    "classification": "MANDATORY_CONFORMING", "severity": "NONE"
                })

    # 3.2 Evaluate OTG observed edges
    edge_types = [("object_interaction", discovered_otg[0]),
                  ("object_cobirth", discovered_otg[1]),
                  ("object_codeath", discovered_otg[2])]
    for rel_name, edge_set in edge_types:
        for ot1, ot2 in edge_set:
            key = (ot1, rel_name, ot2)
            meta = NORM_SEMANTIC_REGISTRY["OTG"].get(key)

            if meta is None:
                results["semantic_findings"].append({
                    "family": "OTG", "element": key,
                    "classification": "UNEXPECTED_BUT_UNREGULATED", "severity": "INFORMATIONAL"
                })
            elif meta["status"] == "forbidden":
                results["semantic_findings"].append({
                    "family": "OTG", "element": key, "norm_id": meta["id"],
                    "classification": "FORBIDDEN_BEHAVIOR", "severity": "HIGH"
                })
            elif meta["status"] == "mandatory":
                results["semantic_findings"].append({
                    "family": "OTG", "element": key, "norm_id": meta["id"],
                    "classification": "MANDATORY_CONFORMING", "severity": "NONE"
                })

    # 3.3 Evaluate ET-OT observed interfaces
    for event_type, object_types in discovered_etot.items():
        for ot in object_types:
            key = (event_type, ot)
            meta = NORM_SEMANTIC_REGISTRY["ET-OT"].get(key)

            if meta is None:
                results["semantic_findings"].append({
                    "family": "ET-OT", "element": key,
                    "classification": "UNEXPECTED_BUT_UNREGULATED", "severity": "INFORMATIONAL"
                })
            elif meta["status"] == "forbidden":
                # Special DQ heuristic for sensor telemetry collisions
                classification = "LIKELY_DATA_QUALITY_ERROR" if "Sensor" in event_type else "FORBIDDEN_BEHAVIOR"
                results["semantic_findings"].append({
                    "family": "ET-OT", "element": key, "norm_id": meta["id"],
                    "classification": classification, "severity": "MEDIUM"
                })
            elif meta["status"] == "mandatory":
                results["semantic_findings"].append({
                    "family": "ET-OT", "element": key, "norm_id": meta["id"],
                    "classification": "MANDATORY_CONFORMING", "severity": "NONE"
                })

    return results
```

## 7. Investigation and remediation plan

### 7.1. Immediate Containment (Priority 1 & 2 Findings)
1. **Intercept Cancelled Shipments ($N3$)**: Issue carrier recall orders for the 2 packages shipped under cancelled Orders; lock WMS dispatch queues for cancelled Order IDs.
2. **Quarantine Cobirth Transaction ($T6$)**: Place an administrative hold on the Order and Payment accounts in the cobirth event; isolate originating API credentials.

### 7.2. Data Repair
1. **Fix Sensor Key Collision ($E10$)**: Patch ETL scripts with namespaced object identifiers (`sensor:101` vs `inv:101`), eliminating spurious telemetry joins.
2. **Standardize Delivery Object Extraction ($E6$)**: Update ingestion logic to extract carrier attribute strings into first-class `Delivery` objects.
3. **Re-link Orphan Cart Items ($E2$)**: Reconcile the 2 orphan `Add Item` events back to session `Order` headers.

### 7.3. Process Investigation
1. **WMS Race Condition ($N3$)**: Analyze timing between cancellation webhooks and warehouse physical scans to verify if queuing latency permitted dispatch before cancellation propagated.
2. **Cobirth Root-Cause Audit ($T6$)**: Audit database logs to determine whether cobirth resulted from a migration script, batch import, or API bypass.
3. **Unapplied Cash Authentication ($E8, T3$)**: Reconcile unlinked `Record Payment` event against bank deposit slips to verify legitimate unallocated customer funds.

### 7.4. Norm Revision
1. **Adopt Declarative Constraints**: Update $N1$ from a directly-follows DFG edge to an eventually-follows rule, accommodating pre-validation reviews.
2. **Codify Open-World Extensions**: Incorporate `Manual Compliance Review` ($E9, T4, T5$) and `Package-Delivery Codeath` into normative models as typical patterns.
3. **Enforce Event Typing Schemas**: Mandate `payment_type` attributes for unapplied cash and require approval objects for invoice write-offs.

### 7.5. Continuous Monitoring & Controls
1. **Real-Time CEP Alerts**: Deploy CEP rules to alert immediately if `Dispatch Package` references a cancelled Order ID.
2. **ETL Validation Gate**: Implement schema validation in data pipelines to block events mapping IoT telemetry to financial entities.
3. **AR Aging Dashboard**: Track open invoices lacking `Record Payment` successors beyond 30/60/90 days to separate active credit terms from bad debt.

## 8. Uncertainty statement

1. **Robust Conclusions**:
   - The 2 `Cancel Order -> Dispatch Package` ($N3$) instances and 1 `Order object_cobirth Payment` ($T6$) edge are unambiguous violations that cannot be excused by open-world assumptions.
   - The 100 `Order-Customer` links, 3 `Manual Compliance Review` workflows, and 7 `Package-Delivery Codeath` edges are robustly classified as permissible behaviors under open-world semantics.

2. **Conclusions Dependent on Norm Incompleteness**:
   - The apparent deficit in `Create Order -> Validate Order` ($N1$) depends on the norm conflating directly-follows adjacency with eventually-follows reachability.
   - Classifications of write-offs and open invoices ($N5$) rely on unmodeled standard commercial credit terms.

3. **Conclusions Dependent on Suspected Data Quality**:
   - The `Sensor Heartbeat -> Invoice` relation ($E10$) is an ETL join artifact caused by identifier reuse across IoT and ERP databases.
   - Missing `Delivery` relations in `Dispatch Package` ($E6$) depend on extraction decisions regarding attributes versus graph object nodes.

4. **Limits of Graph Summaries**:
   - Graph summaries cannot determine causal ordering, verify whether timestamps were back-dated, or confirm transaction authorization without direct inspection of raw event payloads and database logs.
