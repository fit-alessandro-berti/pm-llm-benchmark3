## 1. Modeling assumptions

Object types are lowercase singular: `order`, `item`, `package`, `delivery`, `invoice`, `payment`. Identifiers stay as in the narrative (`O100`, `I1`, `P1`, `D1`, `V1`, `M1`, and their siblings).

E2O qualifiers describe the role of an object in an event. The role key is the pair `(ocel:type, ocel:qualifier)`. Closed vocabulary:

- `created` — order is created
- `added` — item is added
- `receives_item` — order receives that item
- `reserved` — item is reserved
- `shares_reservation` — order operationally shares the reservation
- `packed` — package being assembled, or item placed in it
- `fulfilled` — order treated as a fulfillment participant
- `dispatched` — package or item dispatched
- `used_delivery` — delivery used to move the package
- `issued` — invoice issued
- `billed` — order billed by that invoice event
- `recorded` — payment recorded
- `settles` — invoice to which the payment event applies
- `confirmed` — delivery, package, or item covered by confirmation
- `closed` — order closed

O2O uses a different vocabulary on purpose, so a qualifier join cannot mix master data with events. Direction is `ocel:oid` → `ocel:oid_2`, read as “oid qualifier oid_2”:

- `contains`: order → item
- `packs`: package → item
- `carries`: delivery → package
- `bills`: invoice → order
- `partially_settles`: payment → invoice

Both `M1` and `M2` use `partially_settles`. The invoice total is never stated, so `100 + 150` is not treated as proof that `M2` completes settlement.

Logistics and finance are related as follows. The analyzed OCEL uses one-hop operational involvement, and every E2O row is tagged in `relation_origin`:

- `source`: the narrative names the object, or explicitly says the event is shared by / relates to those orders.
- `analyst_extension`: one documented hop from the named logistics object to its cargo and to the orders that own that cargo. These rows are written out by hand. They are not the result of walking `o2o`.

Under that rule, pack, dispatch, and confirm relate to packages, items, and orders. Issue Invoice relates to `V1`, `O100`, and `O200`, and not to items or logistics objects. Record Payment relates only to the payment and `V1`. Payments are not linked to orders or items. Amounts `100` and `150` are event attributes of `e12` and `e15`.

`relation_origin` is what keeps analytical participation from being mistaken for a source fact. Discovery below sees both origins, because the chosen model includes the extensions. Restricting `relations` to `relation_origin == "source"` rebuilds the source-only log without editing a business fact. O2O is never copied into `relations`. The walk also stops at the finance boundary: nothing follows `bills` or `partially_settles` to attach money to items, packages, deliveries, or orders.

PM4Py assumption: tables follow the OCEL 2.0 column contract, and `OCEL(events=..., objects=..., relations=..., o2o=...)` accepts those four frames and ignores the extra `amount` and `relation_origin` columns. `pm4py.discover_ocdfg`, `pm4py.discover_oc_petri_net`, `pm4py.ocel_flattening`, `pm4py.ocel_get_object_types`, and `pm4py.ocel_object_type_activities` are the stable entry points. `pm4py.discover_otg` and `pm4py.discover_etot` are called by those names. If a build has not bound them, remap only those two lines to that build’s object-type graph and event-type/object-type graph constructors. Do not reshape the four tables. Older OCEL 1.0 code that expects `ocel:omap` inside events, or a constructor without `o2o`, needs that same isolated adapter and not a different story.

```python
# eid, oid, qualifier, relation_origin
RELATION_SPECS = [
    ("e01", "O100", "created", "source"),
    ("e02", "I1", "added", "source"),
    ("e02", "O100", "receives_item", "source"),
    ("e03", "I2", "added", "source"),

    "carries": ("delivery", "package"),
    "bills": ("invoice", "order"),
    "partially_settles": ("payment", "invoice"),
}


def validate(events, objects, relations, o2o):
    problems = []
    if events["ocel:eid"].duplicated().any():
        problems.append("duplicate event ids")
    if objects["ocel:oid"].duplicated().any():
        problems.append("duplicate object ids")
    if not events["ocel:eid"].is_unique or len(events) != 17:
        problems.append("expected 17 unique events")
    expected_oids = {
        "O100", "O200", "I1", "I2", "I3", "P1", "P2", "D1", "D2", "V1", "M1", "M2"
    }
    if set(objects["ocel:oid"]) != expected_oids:
        problems.append("object population does not match the narrative")
    if events["ocel:timestamp"].dt.tz is None:
        problems.append("timestamps are not timezone-aware")
    ordered = events.sort_values(["ocel:timestamp", "ocel:eid"])
    if not ordered["ocel:timestamp"].is_monotonic_increasing:
        problems.append("timestamps are not monotonic in narrative order")
    if not ordered["ocel:timestamp"].is_unique:
        problems.append("this example should have no timestamp ties")
    if list(ordered["ocel:eid"]) != list(events["ocel:eid"]):
        problems.append("eid order is not the narrative order")

    ev_ids = set(events["ocel:eid"])
    ob_ids = set(objects["ocel:oid"])
    if not set(relations["ocel:eid"]).issubset(ev_ids):
        problems.append("orphan event id in relations")
    if not set(relations["ocel:oid"]).issubset(ob_ids):
        problems.append("orphan object id in relations")
    if not set(o2o["ocel:oid"]).issubset(ob_ids) or not set(o2o["ocel:oid_2"]).issubset(ob_ids):
        problems.append("orphan object id in o2o")
    if ev_ids - set(relations["ocel:eid"]):
        problems.append("event with no E2O row")
    if ob_ids - set(relations["ocel:oid"]):
        problems.append("object that participates in no event")
    if relations["ocel:activity"].isna().any() or relations["ocel:type"].isna().any():
        problems.append("relation did not match event or object")

    merged = relations.merge(
        events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
        on="ocel:eid",
        suffixes=("", "_event"),
    )
    same_act = merged["ocel:activity"].eq(merged["ocel:activity_event"]).all()
    same_ts = merged["ocel:timestamp"].eq(merged["ocel:timestamp_event"]).all()
    if not same_act or not same_ts:
        problems.append("activity or timestamp mismatch between events and relations")

    rel_key = ["ocel:eid", "ocel:oid", "ocel:qualifier"]
    if relations.duplicated(rel_key).any() or relations.duplicated(["ocel:eid", "ocel:oid"]).any():
        problems.append("duplicate relation rows for an event-object pair")
    if o2o.duplicated(["ocel:oid", "ocel:oid_2", "ocel:qualifier"]).any():
        problems.append("duplicate o2o rows")
    if o2o["ocel:oid"].eq(o2o["ocel:oid_2"]).any():
        problems.append("o2o self-loop")
    if not set(relations["relation_origin"]).issubset({"source", "analyst_extension"}):
        problems.append("unknown relation_origin")

    for qualifier, typ in zip(relations["ocel:qualifier"], relations["ocel:type"]):
        if typ not in E2O_ALLOWED.get(qualifier, set()):
            problems.append(f"qualifier {qualifier} incompatible with type {typ}")
            break

    type_of = objects.set_index("ocel:oid")["ocel:type"]
    for _, row in o2o.iterrows():
        pair = O2O_TYPE_PAIRS.get(row["ocel:qualifier"])
        actual = (type_of[row["ocel:oid"]], type_of[row["ocel:oid_2"]])
        if pair != actual:
            problems.append(f"o2o type pair mismatch: {row.to_dict()}")
            break

    def oids_of(eid):
        return set(relations.loc[relations["ocel:eid"].eq(eid), "ocel:oid"])

    checks = {
        "e06": {"I1", "I3", "O100", "O200"},
        "e07": {"P1", "I1", "I3", "O100", "O200"},
        "e08": {"P2", "I2", "O100"},
        "e12": {"M1", "V1"},
        "e15": {"M2", "V1"},
        "e16": {"O200"},
        "e17": {"O100"},
    }
    for eid, expected in checks.items():
        if oids_of(eid) != expected:
            problems.append(f"{eid} objects {oids_of(eid)} != {expected}")
    if "I2" in oids_of("e06"):
        problems.append("I2 must not be reserved")
    pay_orders = relations[
        relations["ocel:oid"].isin(["M1", "M2"])
        & relations["ocel:type"].eq("order")
    ]
    order_pays = relations[
        relations["ocel:eid"].isin(["e12", "e15"])
        & relations["ocel:type"].eq("order")
    ]
    if len(pay_orders) or len(order_pays):
        problems.append("payment allocated to an order")
    amount_of = events.set_index("ocel:eid")["amount"]
    if amount_of["e12"] != 100 or amount_of["e15"] != 150:
        problems.append("payment amounts are not 100 and 150")
    if events.loc[~events["ocel:eid"].isin(["e12", "e15"]), "amount"].notna().any():
        problems.append("non-payment event carries an amount")
    if set(o2o["ocel:qualifier"]) != set(O2O_TYPE_PAIRS):
        problems.append("unexpected o2o qualifier")
    if (o2o["ocel:qualifier"].eq("completes_settlement")).any():
        problems.append("completion of settlement is not given")

    if problems:
        raise AssertionError("; ".join(problems))


validate(events, objects, relations, o2o)

# Version-sensitive line: drop `o2o=` only if this PM4Py build is OCEL 1.0,
# and keep the same four tables. Do not fold o2o back into events.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)
print(events["ocel:activity"].value_counts().rename("frequency"))
print(objects["ocel:type"].value_counts().rename("frequency"))
print(pm4py.ocel_get_object_types(ocel))
print(pm4py.ocel_object_type_activities(ocel))
print(relations["relation_origin"].value_counts().rename("relations"))

flat_logs = {}
dfg_by_type = {}
skeleton_by_type = {}
for object_type in ("order", "package", "delivery", "invoice"):
    flat_logs[object_type] = pm4py.ocel_flattening(ocel, object_type)
    dfg_by_type[object_type] = pm4py.discover_dfg(flat_logs[object_type])
    skeleton_by_type[object_type] = pm4py.discover_log_skeleton(flat_logs[object_type])

ocdfg = pm4py.discover_ocdfg(ocel)
# If this build has no discover_otg, remap only this line.
otg = pm4py.discover_otg(ocel)
# If this build has no discover_etot, remap only this line.
etot = pm4py.discover_etot(ocel)
oc_petri_net = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Optional visualization. Requires a local display backend. No paths written.
# pm4py.view_ocdfg(ocdfg)
# pm4py.view_ocpn(oc_petri_net)

print({
    "flat_types": sorted(flat_logs),
    "dfg_types": sorted(dfg_by_type),
    "skeleton_types": sorted(skeleton_by_type),
    "ocdfg_type": type(ocdfg).__name__,
    "otg_type": type(otg).__name__,
    "etot_type": type(etot).__name__,
    "oc_petri_net_type": type(oc_petri_net).__name__,
    "interactions_type": type(interactions).__name__,
})
```

Consequential relation sets:

- **e07 Pack Package** is the sharp logistics convergence. One event binds P1, I1, I3, O100, and O200. P1 therefore mixes the two orders, while I2 is absent, so O100’s goods diverge into the P1 lane and the P2 lane at the same step.
- **e06 Reserve Stock** is the earlier join of O100 and O200, and it already excludes I2. Reservation is shared operationally; it is not yet a package.
- **e11 Issue Invoice** is the financial convergence: V1 with both orders, and with no item, package, delivery, or payment. The two channels meet the orders at different events.
- **e09 and e13** spread P1’s convergence onto D1. That cross-order delivery binding is an `analyst_extension`. On source rows alone, e09 is only P1 and D1, and e13 is only D1, so those events would not themselves join O100 to O200.
- **e12 and e15** matter because of the objects they leave out. Each payment meets only V1. M1 is 100, M2 is 150, and neither is allocated to O100 or O200.

## 4. Expected flattened behavior

Flattening keeps one trace per object. An event linked to two objects of the chosen type is copied into both traces. Directly-follows counts below are counts of those copies. `discover_dfg` here is the frequency DFG: graph, start activities, end activities. Durations stay on the timestamps and do not become edge labels.

**Order (O100, O200).** Shared copies are e06, e07, e09, e11, and e13. Of those, e06, e07, and e11 are source; e09 and e13 are shared only because both orders were extension-linked.

O100: Create Order (e01), Add Item (e02), Add Item (e03), Reserve Stock (e06), Pack Package (e07), Pack Package (e08), Dispatch Package (e09), Dispatch Package (e10), Issue Invoice (e11), Confirm Delivery (e13), Confirm Delivery (e14), Close Order (e17).

O200: Create Order (e04), Add Item (e05), Reserve Stock (e06), Pack Package (e07), Dispatch Package (e09), Issue Invoice (e11), Confirm Delivery (e13), Close Order (e16).

Likely DFG edges and supports: Create Order → Add Item (2), Add Item → Add Item (1), Add Item → Reserve Stock (2), Reserve Stock → Pack Package (2), Pack Package → Pack Package (1), Pack Package → Dispatch Package (2), Dispatch Package → Dispatch Package (1), Dispatch Package → Issue Invoice (2), Issue Invoice → Confirm Delivery (2), Confirm Delivery → Confirm Delivery (1), Confirm Delivery → Close Order (2). Starts and ends: Create Order (2), Close Order (2).

A log skeleton should bound Create Order, Reserve Stock, Issue Invoice, and Close Order at one occurrence per order, and Add Item, Pack Package, Dispatch Package, and Confirm Delivery at one or two. Precedence should place creation first and close last, with invoice issuance after dispatch and before confirmation in both traces.

Omitted from both order traces: Record Payment, so M1, M2, and the amounts are invisible. Omitted from O200 only: the whole P2/D2 lane (e08, e10, e14). I2 never appears as its own identity.

Misleading readings: Reserve Stock, Pack P1, Dispatch D1, Issue Invoice, and Confirm D1 look like two occurrences instead of one shared occurrence. O100’s second pack, dispatch, and confirmation look like rework loops rather than a second package. The order graph looks financially complete enough to close, while payment was never on the order. Copied Confirm D1 makes O200 appear to have “its own” confirmation of a delivery that also carries O100’s I1.

**Package (P1, P2).** No event is copied across packages. Each package is the only package on its events.

P1: Pack Package (e07), Dispatch Package (e09), Confirm Delivery (e13).

P2: Pack Package (e08), Dispatch Package (e10), Confirm Delivery (e14).

DFG: Pack Package → Dispatch Package → Confirm Delivery, support 2 on each edge. Both packages have the same activity string, so the skeleton is a chain of three activities, each with frequency exactly 1. Those three can fall into one frequency-equivalence class while `always_before` still orders them.

Omitted: order creation, item addition, reservation, invoice, both payments, and both closes. Also omitted is any event that would show P1’s two customers. Confirmation is present only through the extension; a source-only filter would end the package trace at dispatch.

Misleading readings: P1 and P2 look interchangeable. Nothing in the DFG says P1 merges O100 and O200 while P2 is private to I2. “Confirm Delivery” sitting in a package trace reads as if the package were the delivery.

**Delivery (D1, D2).** No cross-delivery copies.

D1: Dispatch Package (e09), Confirm Delivery (e13).

D2: Dispatch Package (e10), Confirm Delivery (e14).

DFG: Dispatch Package → Confirm Delivery, support 2. Skeleton: both activities exactly once, dispatch before confirm.

Omitted: packing, which happened before any delivery existed in the E2O sense, plus orders, items, invoice, and payment. The frequency DFG also omits waiting time. D1 runs from 10:00 to 13:00 on 6 April (3 hours). D2 runs from 10:15 on 6 April to 09:00 on 7 April (22 hours 45 minutes). Those durations are in the flattened timestamps only.

Misleading readings: D1 looks like a private one-package shipment. Its cargo P1, and therefore I1 from O100 and I3 from O200, is not in the delivery case notion. The two deliveries look structurally identical.

**Invoice (V1 only).** One object, so nothing is copied. The two payments are two different events in one trace.

V1: Issue Invoice (e11), Record Payment (e12, amount 100), Record Payment (e15, amount 150).

DFG: Issue Invoice → Record Payment (1), Record Payment → Record Payment (1). Start Issue Invoice, end Record Payment. A one-trace skeleton will treat that single history as universal: Issue Invoice once, Record Payment twice, issuance before both recordings. That overfits V1.

Omitted: the entire logistics lifecycle, both closes, and which order was billed beyond the lost object identity of O100 and O200. If the flattener retains non-OCEL columns, `amount` is still on the two payment rows; DFG, skeleton, and Petri-net discovery do not consult it.

Misleading readings: two `Record Payment` steps look like a duplicate posting or a retry loop. M1 versus M2 disappears as soon as the case is the invoice. Nothing allocates 100 or 150 to an order. The trace ends at M2 and does not show that O200 closes at 10:30 and O100 at 10:35.

**Payment flattening is a weak lens here.** M1’s trace is the single event e12, and M2’s trace is the single event e15. There is no within-case directly-follows pair, so the DFG has no edges; both traces start and end at Record Payment. A log skeleton has no precedence between distinct activities. The facts that matter are outside that control flow: both O2O rows point at V1, M1 is before M2, the amounts differ, the invoice total is unknown, and neither payment names an order. Collapsing to the payment type also makes two installments of one invoice look like two unrelated one-step process instances. The invoice flattening, the O2O edges, and the object-interactions summary are the views that still show settlement.

## 5. Expected object-centric structures

These are expected shapes for the model in section 2, including the 15 extension rows. They are not a second, hidden log.

**OC-DFG.** Per object type, directly-follows counts match the flattened traces, while the activity–type map keeps the shared context that flattening drops.

- Orders: the edge list in section 4. Create Order starts both orders; Close Order ends both. Record Payment is absent. The support-1 edges Add Item → Add Item, Pack → Pack, Dispatch → Dispatch, and Confirm → Confirm are exactly O100’s divergence into I1/P1/D1 versus I2/P2/D2, folded into activity labels.
- Items: I1 and I3 follow Add Item → Reserve Stock → Pack Package → Dispatch Package → Confirm Delivery. I2 follows Add Item → Pack Package → Dispatch Package → Confirm Delivery and never Reserve Stock. Merged item edges therefore branch after Add Item. I1 and I3 share e06, e07, e09, and e13 because they travel together in P1. I1 and I2 never share an event.
- Packages: Pack → Dispatch → Confirm, twice, so P1 and P2 are indistinguishable at activity grain. P1’s merge of O100 and O200 is not an edge; it is the multi-type binding of e07, e09, and e13.
- Deliveries: Dispatch → Confirm, twice.
- Invoice: Issue Invoice → Record Payment → Record Payment on V1 alone.
- Payments: M1 and M2 are isolated Record Payment nodes with no payment-type edge.

The type map should show Reserve Stock on item and order; Pack, Dispatch, and Confirm on the logistics types including order; Issue Invoice on invoice and order; Record Payment on payment and invoice only. V1 is where O100 and O200 meet financially. P1 is where they meet physically, together with I1 and I3, on the D1 lane. M1 and M2 appear only opposite V1.

**OTG.** At type grain, P1 versus P2 and M1 versus M2 disappear. O2O alone is the path payment —partially_settles→ invoice —bills→ order —contains→ item ←packs— package ←carries— delivery. Event co-occurrence in this E2O model adds direct logistics edges among order, item, package, and delivery, and it still has no payment–order edge and no edge from invoice or payment to item, package, or delivery. So the type graph can show that finance attaches at the order, through V1, while it cannot show that P1 is the cross-order package and P2 is not, or that M1 and M2 are two partial settlements rather than “payments in general.”

**ET–OT.** A bipartite activity / object-type graph for this relation set:

| Activity | Object types |
|---|---|
| Create Order | order |
| Add Item | item, order |
| Reserve Stock | item, order |
| Pack Package | package, item, order |
| Dispatch Package | package, delivery, item, order |
| Issue Invoice | invoice, order |
| Record Payment | payment, invoice |
| Confirm Delivery | delivery, package, item, order |
| Close Order | order |

Issue Invoice is the only activity that puts V1 on the orders. Record Payment is the only activity that puts M1 and M2 on V1, and orders are not on that edge. That is why an order DFG can show billing and omit settlement. The graph does not encode multiplicity: it cannot say that e07 binds two orders and e08 binds one.

**Object-centric Petri net.** One defensible family of nets, not a unique net, is what the usual “inductive miner per type, then merge transitions by activity label” procedure emits from two order traces and one invoice trace.

- Order places: a sequence Create Order, Add Item, Reserve Stock, Pack Package, Dispatch Package, Issue Invoice, Confirm Delivery, Close Order, with optional redos of Add Item, Pack Package, Dispatch Package, and Confirm Delivery. Those redos are how two traces express “O100 did this twice and O200 once.” They generalize to unbounded repetition and they force every order through Reserve Stock. They do not encode two concurrent packages.
- Item places: after Add Item, a choice between passing through Reserve Stock and skipping it, then Pack, Dispatch, and Confirm. The skip is I2’s real path, promoted to a free choice for any item.
- Package places: a plain sequence Pack → Dispatch → Confirm. Delivery places: Dispatch → Confirm. Invoice places: Issue Invoice followed by two payment recordings, which a miner may draw as a loop of Record Payment or as two successive payment transitions. Payment places: a single Record Payment transition and no internal flow.
- Merged labels make Pack Package one transition shared by package, item, and order places, and likewise for Dispatch and Confirm. Issue Invoice is shared by the invoice place and the order places. Record Payment is shared by payment and invoice places only, so M1 and M2 never move an order token.
- Bindings that a variable-arc heuristic can notice: Pack, Dispatch, and Confirm each have one event with two items and two orders (the P1/D1 events e07, e09, e13) and one event with one item and one order (the P2/D2 events). Package and delivery cardinalities on those events stay 1. Reserve Stock is a single observation with two items and two orders (I1, I3, O100, O200). Issue Invoice is a single observation with one invoice and two orders. With one sample, “always two” and “variable” are both compatible with the data.

Changing the inductive-miner variant, the noise threshold, or dropping the analyst extensions moves Confirm off the package and item nets and moves Dispatch off the order and item nets. The same tables therefore do not determine one OC-PN. The net also does not by itself say that the joint binding is specifically P1 with I1, I3, O100, and O200; that is event-level binding, which the interactions summary carries.

**Object-interactions summary.** Event co-occurrence, which is the reading used here, should show at least:

- O100 with O200 on five events: e06, e07, e09, e11, e13. Those are the reservation, the P1 pack, the D1 dispatch, the shared invoice, and the D1 confirmation. They are never co-present on a payment or on a close.
- P1 with I1, I3, O100, O200, and D1. This is the cross-order logistics clique.
- P2 with I2, O100, and D2 only. P2 does not meet O200. P1 does not meet P2. D1 does not meet D2.
- I1 with I3 on e06, e07, e09, and e13. I1 with I2 on no event, and I2 with I3 on no event. O100 is the object that ties its own two lanes together; the items never reunite.
- V1 with O100 and with O200 on e11 only. V1 with M1 on e12 only, and V1 with M2 on e15 only. M1 with M2 on no event. M1 and M2 with either order on no event. V1 with no item, package, or delivery.

O2O still says M1 partially_settles V1 and M2 partially_settles V1 even though the two payments never participate in one event. The summary’s event view and the O2O view answer different questions and should stay side by side.

## 6. Modeling alternatives

The business story is fixed: two orders, P1 mixing I1 with I3, P2 carrying I2, D1 carrying P1, D2 carrying P2, V1 billing both orders, M1 and M2 paying V1 without an order allocation. The policies below change only which of those facts are materialized as E2O rows, and therefore what discovery can see.

**Source-minimal relations.** Keep a row only when the sentence names the object or explicitly shares the event. Pack P2 loses O100. Dispatch keeps package and delivery only. Confirm keeps the delivery only. Invoice, payment, reserve, and pack P1 stay as they are. Order traces then lose e08, e09, e10, e13, and e14, so O100’s DFG jumps from Pack P1 to Issue Invoice to Close, and O200 never sees a delivery. Package DFGs end at Dispatch. Delivery DFGs are unchanged, because dispatch and confirm already name the delivery. The OC-PN order net loses dispatch and confirmation. Convergence of O100 and O200 remains visible at e06, e07, and e11, and disappears at D1. This is the smallest event log that still records every stated participation. It makes delivery confirmation look as if it were not part of the order lifecycle.

**One-hop operational involvement.** This is the pipeline above. Named participants stay `source`. Cargo and owning orders are added by hand on pack P2, both dispatches, and both confirmations, tagged `analyst_extension`. Order and item DFGs become end-to-end, P1’s shared dispatch and confirmation are copied onto both orders, and O100 grows the divergence loops. Payment rows are still withheld from orders, so the financial ambiguity survives. Discovery reports a fuller fulfillment model and inflates shared logistics counts. Filtering on `relation_origin` recovers the source-minimal view from the same frames.

**O2O-propagated analytical relations.** Start from source-minimal E2O and walk master data automatically: delivery along `carries` to a package, package along `packs` to items, items back along `contains` to orders, invoice along `bills` to orders, payments along `partially_settles` to the invoice and onward. A one-step logistics walk resembles the second policy and will reconstruct D1’s connection to I1, I3, O100, and O200. An unbounded walk does more. Confirmations and dispatches reach V1 by continuing from the orders across `bills`, so the invoice trace fills up with packing and shipping. A further step across `partially_settles` copies that same fulfillment history onto M1 and M2. Propagating payments the other way stamps both 100 and 150 onto both orders and invents an allocation the narrative does not contain. If the generated rows are not tagged, they are indistinguishable from source observations. Discovery then reports a single blended process in which delivering a package appears to be an invoice event and a payment event. The story has not changed; reachability has been mislabeled as observation.

A smaller qualifier variant sits inside any of the three: marking M2 as `completes_settlement` changes the O2O reading of V1 without a stated total. The pipeline keeps both payments on `partially_settles` so that discovery is not handed a closure fact the business text does not give.

## 7. Failure modes

**Relation inflation.** Counting activities on `relations` multiplies an event by its object fan-out. e07 then contributes five “packs,” and e09 six “dispatches,” although each happened once. Frequency for the process has to be computed on `events`, or on distinct `ocel:eid` per activity. The same inflation hits any metric that treats an E2O row as an event occurrence.

**Missing direct E2O links.** Flattening and the OC-DFG only see objects listed on the event. If dispatch and confirm are left on the delivery alone, every order trace is silent about shipping. The resulting DFG looks like orders are invoiced and closed without leaving the building. The absence is a modeling gap, not evidence that dispatch did not happen. O2O still contains D1 carries P1 and P1 packs I1, but those edges are not a substitute for an E2O row unless a declared propagation policy says they are.

**Treating O2O propagation as observation.** Walking `contains`, `packs`, `carries`, `bills`, or `partially_settles` and inserting the results into `relations` records inferred reachability as if the source system had referenced those objects. The dangerous walk is payment → V1 → both orders: M1 and M2 become events of O100 and of O200, and a partial, unallocated settlement looks like each order was paid in full, twice. Leaving `relation_origin` off the extension rows creates the same confusion inside the chosen model.

**Duplicate shared events after flattening.** e06, e07, e09, e11, and e13 each become two order-cases. A dashboard that sums flattened rows reports two reservations and two invoices. Convergence has been rewritten as parallelism. Package and delivery flattenings do not have this particular duplication, because no event names two packages or two deliveries; the failure is type-specific. Comparing flattened counts with `events["ocel:eid"].nunique()` per activity exposes it.

**Ambiguous payment allocation.** The text gives 100 on M1 and 150 on M2 against V1, and it bills V1 to both orders. It does not say how much of either payment belongs to O100 or O200, and it does not say that 250 is the invoice total. Splitting 100/150 across the orders, duplicating both amounts onto both orders, or labeling M2 as the completing payment all add a fact. The model refuses that split by giving e12 and e15 no order rows and by using `partially_settles` for both O2O edges. A later allocation can be added only as a new, labeled assumption.

**Overly short Payment traces.** Each payment object is born in one event. Flattened discovery has no pair to mine, so the payment DFG is empty and the payment Petri net is a single transition. It is easy to drop the type as “structurally trivial” and lose the only settlement mechanism in the log. M1 and M2 are informative as objects related to V1, and as attribute carriers, rather than as processes. A quality check is: if an object type’s median trace length is 1, do not expect a DFG; read its O2O and its partner type instead.

**Constructor or API version mismatch.** An OCEL 1.0 constructor rejects `o2o` or expects object maps nested in events. A 2.0 build expects the prefixed columns used here and can keep `o2o` beside `relations`. `discover_otg` and `discover_etot` may be missing or may live under a graph-transformation module; `ocel_flattening` may return a DataFrame in one release and an `EventLog` in another. Both are valid inputs to `discover_dfg` and `discover_log_skeleton` when the case, activity, and timestamp columns are the usual ones. The failing line should be adapted in isolation. Rebuilding the story as six ordinary logs would hide P1’s joint binding and V1’s joint billing. A type error on `OCEL(...)` is not evidence that the four tables are wrong.

**False total order for same-time events.** This file has 17 distinct timestamps, so a sort by time matches the narrative. The failure is latent. A later extract can easily tie two events. Sorting only by timestamp, then by object id or by dataframe row order, can place Close Order before the payment that was recorded in the same second, or can interleave O100 and O200 differently on each run. The stable key is `(ocel:timestamp, ocel:eid)`, and eids were assigned in narrative order so that a tie breaks the way the story was told. A tie still does not mean the two events were simultaneous in the business sense; it means the clock did not separate them. Dropping the date and sorting by clock time alone is the nearby variant that this file would trigger: e14 at 09:00 on 7 April would sort before e13 at 13:00 on 6 April.

Related failures that sit next to these eight: a generic qualifier such as `related` on every row erases the difference between `billed`, `fulfilled`, and `created`; two qualifiers for the same `(eid, oid)` duplicate that event inside one flattened trace; a naive timestamp parsed without UTC can shift the 7 April events relative to the 6 April events; modeling the amount as its own object invents a seventh type and a fake O2O edge.

## 8. Final semantic checks

A reviewer can confirm the construction from the four tables alone:

1. `events` has exactly the 17 identifiers e01 through e17, in narrative order, with strictly increasing UTC timestamps and no ties. Activities and counts are Create Order 2, Add Item 3, Reserve Stock 1, Pack Package 2, Dispatch Package 2, Issue Invoice 1, Record Payment 2, Confirm Delivery 2, Close Order 2.

2. `objects` has exactly O100 and O200 as `order`, I1–I3 as `item`, P1 and P2 as `package`, D1 and D2 as `delivery`, V1 as `invoice`, and M1 and M2 as `payment`.

3. `o2o` has exactly 12 rows: O100 contains I1 and I2, O200 contains I3, P1 packs I1 and I3, P2 packs I2, D1 carries P1, D2 carries P2, V1 bills O100 and O200, M1 partially_settles V1, M2 partially_settles V1. No row uses `completes_settlement`.

4. e06’s objects are exactly I1, I3, O100, and O200, all `source`. I2 is not on e06. e07’s objects are exactly P1, I1, I3, O100, and O200, all `source`. e08’s objects are P2, I2, and O100, and only O100 is an `analyst_extension`.

5. e12 relates only to M1 and V1 and has amount 100. e15 relates only to M2 and V1 and has amount 150. No other event has an amount. No relation of e12 or e15 has type `order` or `item`.

6. e16 relates only to O200 at 2026-04-07 10:30 UTC. e17 relates only to O100 at 2026-04-07 10:35 UTC. O200 is closed before O100, and both closes are after M2.

7. Every `relations` row matches `events` on activity and timestamp for the same eid, every oid and oid_2 exists in `objects`, and each relation’s `ocel:type` equals that object’s type. `(ocel:eid, ocel:oid)` is unique. There are 34 `source` rows and 15 `analyst_extension` rows, and every extension row belongs to e08, e09, e10, e13, or e14.

8. The cross-order clique is inspectable without a miner: the events whose object set contains both O100 and O200 are e06, e07, e09, e11, and e13. The events that contain P1 also contain I1 and I3. The events that contain P2 also contain I2 and do not contain O200. M1 and M2 never appear in the same event.
