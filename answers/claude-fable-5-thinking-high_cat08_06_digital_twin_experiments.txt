# Simulation-Based Digital Twin for the Building-Permit Process

## 1. Model scope and state variables

**Boundary.** The twin covers the permit lifecycle from portal submission to Issue permit / Reject application, plus the applicant-side and third-party delays that gate municipal work (missing-document responses, consultant reports, objections). Upstream applicant behavior before submission is outside the boundary except where an intervention explicitly changes it (D1 pre-submission checker, D7 appointment slots), in which case it is represented as a modified arrival/attribute process, not as simulated applicant agents. Council politics, appeals courts, and construction after permit issuance are out of scope; appeals are modeled only as a rework branch with an exogenous delay distribution.

**Level of detail.** Discrete-event simulation at activity granularity matching the process tree, with explicit resource pools, calendars, and queues. This is a hybrid of a DES core plus lightweight agent-like constructs for cross-case coupling (architect bundles, district inspection batching, objection clusters). We deliberately do **not** model individual keystrokes or sub-activity steps; the event log cannot support that resolution.

**Entities.**
- *Case (permit application)* — the primary flowing entity.
- *Work item* — an (activity, case) pair sitting in a queue or in service.
- *Inspection bundle* — a batch entity grouping work items for Site inspection by (district, architect, time window).
- *Objection cluster* — a latent entity attached to a public-notice period that can span several related cases in the same district/neighborhood.

**Case state variables.**
- `case_id, case_type ∈ {Simple renovation, New residential, Commercial, Complex variance}`
- `district, architect_id, application_value`
- `requires_fire, requires_environment, requires_public_notice` (with imputation flags when derived rather than observed — see §3 missing data)
- `phase` / marking in the process tree (which branches of the AND-block `+(Planning, Fire?, Env?)` are complete — Decision drafting is gated on the join)
- `n_missing_doc_loops, n_inspection_reworks, n_completeness_reworks, appeal_flag`
- `submit_time, current_activity, per-activity ready/start/complete timestamps`
- `age` (for D6 aging-case reservation), `sla_clock` per case type
- `bundle_id` (if enrolled in an inspection bundle), `objection_cluster_id`
- `low_risk_flag` (value < €50k and no prior violations, for D2)

**Global/system state.**
- Simulation clock; calendar state (weekday, holiday, council-meeting week flag)
- Seasonal demand multiplier (month-of-year), day-of-week submission multiplier
- Per-architect open-application counts and burst state (for correlated arrivals)
- Backlog per queue; aging-case register (for D6)

**Resources and calendars.** Pools exactly as given: clerks (5 FTE, Mon–Fri 08–16, one clerk diverted to portal support Mondays → effective 4 on Mondays), planners (8 FTE, Mon–Fri 09–17, 2 restricted to Simple renovation — modeled as a partitioned pool with overflow rules), fire reviewers (2 FTE-equivalent, Tue–Thu only), environmental reviewers (3 FTE with a 40% capacity reservation, modeled as 1.8 effective FTE or as stochastic interruptions), inspectors (4 FTE, field Tue–Fri, district-dependent travel time added to service time, batching capable), legal officers (2 FTE, capacity ≈ 0 during council-meeting weeks except an urgent-case exception lane), and system tasks with infinite capacity. Applicants/third parties are **not** resources: their response times are exogenous delay distributions attached to `Receive missing documents`, consultant-dependent environmental reviews, and objection handling — this keeps municipal capacity effects separable from demand-side behavior.

**Queues.** One queue per (activity, pool), default FIFO within priority class. Priority/skill rules: Simple-renovation planner partition; D6 introduces an aging-priority lane; legal urgent lane; inspection queue is replaced by a batching queue keyed by district under D3.

**Cross-case dependencies (explicitly modeled, per the constraint).**
1. *Architect bursts*: arrivals are generated by a marked process — a case-level nonhomogeneous Poisson stream plus architect-level burst episodes (a top-20 architect submits a geometrically distributed batch of related cases within the same week). Related cases share district and correlated attributes.
2. *Inspection batching*: cases from the same architect/district can be bundled; bundling reduces per-visit travel time but the first case waits for the bundle to fill or a max-hold timer to expire (both are model parameters).
3. *Objection contagion*: when an objection cluster fires in a district, all concurrently open public-notice periods in that district draw from the extended (60d-tail) duration distribution rather than the 14d minimum.
4. *Shared-resource coupling*: all cases compete for the same finite pools, so interventions on one case type shift queues for others (e.g., D2 frees inspector capacity that Commercial cases absorb).

## 2. Parameter-estimation plan

**PM4Py role.** PM4Py handles log ingestion, model handling, and descriptive statistics that feed the parameter store; it is *not* the simulation engine. Concretely: load the CSV with `pandas.read_csv`, standardize with `pm4py.format_dataframe(df, case_id='case:concept:name', activity_key='concept:name', timestamp_key='time:timestamp')`, parse the given tree with `pm4py.parse_process_tree(tree_string)` (or fall back to `pm4py.discover_process_tree_inductive` on the log and diff against the provided tree), and compute variants (`pm4py.get_variants` / `pm4py.stats.get_variants`), frequency DFG (`pm4py.discover_dfg`), performance DFG (`pm4py.discover_performance_dfg`), and mean case inter-arrival time (`pm4py.get_case_arrival_average`). Conformance checking (`pm4py.conformance_diagnostics_alignments`) verifies the tree explains the log and localizes deviations (which become rework/exception parameters, not noise).

**Arrivals.** Fit a nonhomogeneous Poisson process with a multiplicative rate: base rate × month factor (Mar–May, Sep–Nov = 1.7×) × day-of-week factor (Mon = 2.2× Wed) × hour-of-day profile from portal timestamps. Estimate factors by Poisson regression on daily submission counts. On top, fit the architect burst layer: for the top-20 architects, estimate batch-size distribution and within-week spacing from grouped submissions; residual arrivals form the independent stream. Case-type mix and attribute joint distribution (district, value, requires_* flags) are estimated per season as an empirical joint table, sampled with the case, not independently — attribute correlations (e.g., Complex variance ⇒ public notice) matter for routing.

**Service vs. waiting times.** This is the hardest split because many activities log only completion. Strategy: (a) where start timestamps exist, fit service-time distributions directly per (activity, case_type, district where relevant) — candidate families: lognormal/gamma for reviews, and a fixed-minimum-plus-tail mixture for Public notice; (b) where only completions exist, use the resource-busy heuristic: reconstruct each resource's timeline, assume a resource works one item at a time within calendar hours, and infer start = max(item ready time, resource previous completion, calendar opening) — this yields an *upper bound* on service time and a *lower bound* on waiting; (c) cross-check inferred service medians against the provided empirical table (25 min completeness, 3.5 h planning, etc.) and against staff interviews (face validity). Keep waiting times as an *output* of the simulation (emerging from queues + calendars), never as a sampled input — sampling observed waits would bake the current resourcing into every scenario and invalidate intervention comparison. Flag every inferred split with an uncertainty grade used later in sensitivity analysis.

**Branching probabilities and routing.** Where routing is attribute-driven (fire/environment/public-notice flags), estimate *conditional* rules: logistic models of branch taken vs. case_type, district, value — because the true drivers (building area, environmental sensitivity) are partly missing, the residual randomness stays as a calibrated Bernoulli given attributes. Missing-doc loop probability and loop-count distribution per case type come from counting `Request missing documents` recurrences per case. XOR at Issue/Reject: empirical rejection rate per case type and rework count.

**Rework.** Estimate rework probabilities at each loop point (completeness, inspection, legal/appeal) from repeated-activity patterns and alignment deviations. Since rework *reasons* are unreliably coded, model rework as state-dependent Bernoulli (probability increasing with case complexity and loop count capped by observed maxima) rather than reason-specific submodels; expose the probabilities as sensitivity parameters.

**Resource calendars.** Take HR-reconstructed calendars as priors; validate against event timestamps (e.g., no fire-review completions outside Tue–Thu confirms the calendar; completions during nominal off-hours indicate overtime to be modeled explicitly). Estimate effective capacity (busy fraction) per pool from the reconstructed resource timelines; the environmental 40% reservation is checked against observed throughput vs. nominal 3 FTE.

**Dependencies.** Architect bundling propensity: fraction of same-architect-same-district cases inspected on the same day. Objection proxy: fit a two-component mixture to public-notice durations (≈14d point mass + heavy tail); the tail weight per district/case type is the estimated objection probability — an *inferred latent*, clearly labeled as such.

## 3. Assumptions

**Arrivals.** Nonhomogeneous Poisson with multiplicative seasonality/weekday factors is adequate; no long-run trend beyond the 18-month window (tested in stress scenarios). Architect bursts are exchangeable batches; batch cases share district and correlated attributes. Portal is always available.

**Service times.** Service times are resource-calendar-independent in duration (a 3 h review takes 3 h of working time whenever performed) and independent across cases given (activity, case_type, district), except rework repetitions which may be shorter (learning factor, default 0.8×, sensitivity-tested). Distributions are stationary over the horizon. Where start timestamps were inferred, the estimated service time is treated as an upper bound with an uncertainty band, not a point truth. We explicitly do **not** collapse waiting into service time; where the split is inferred, results are reported with the split-uncertainty band because misallocating wait into service would understate the benefit of capacity interventions and overstate the benefit of process-redesign interventions.

**Routing.** Attribute-driven gates are deterministic given attributes plus a residual Bernoulli absorbing unobserved drivers (building area, sensitivity). The AND-join before Decision drafting is strict (waits for all applicable results). Parallelism inside `+(Planning, Fire, Env)` is true resource-constrained parallelism, not interleaving noise.

**Resources/calendars.** HR calendars are correct up to validated overtime; one person works one item at a time; no cross-pool skill substitution except the two Simple-renovation planners overflowing to the general pool only when their queue is empty (rule, sensitivity-tested). Council-meeting weeks fully block legal work except an urgent lane covering ~5% of legal items. Absence/vacation is modeled as a stationary capacity haircut per pool.

**Rework.** Rework probabilities depend on case type and loop count, not on unmodeled root causes; max loop counts are capped at observed p99. Appeals are exogenous events with fixed probability per case type and an independent delay.

**Applicant/third-party response.** Missing-document response time is applicant-driven, heavy-tailed (lognormal or generalized Pareto tail, median ≈ 5d), independent of municipal load, and unaffected by any intervention except D1 (which reduces loop *probability*, not response speed). Consultant delays in environmental review are exogenous. Objection occurrence probability is exogenous per district; its *duration* consequence is the fitted tail.

**Cross-case dependencies.** Bundling is beneficial only within (architect, district) and same-week windows; objection contagion is limited to concurrent public-notice periods in one district; no other inter-case causal links (e.g., no precedent effects on decisions).

**Non-stationary demand.** The 1.7× seasonal and 2.2× Monday factors persist into the simulated horizon; the case-type mix is season-dependent per the estimated joint table; there is no feedback from permit lead time to demand (no discouraged applicants) — acknowledged limitation.

**Missing data.** Objections are a *latent* variable inferred from the duration mixture — we never treat them as observed; all objection-related conclusions (especially for D9) carry wide credible intervals. Missing start timestamps ⇒ service/wait split uncertainty handled as above. Removed emergency decisions bias the log toward slower cases; we assume they were <1% and fast, so baseline medians are slightly pessimistic. Flattening underrepresents related-case dependencies; the architect-burst layer is calibrated to the observed 31%-from-top-20 statistic as a lower bound on coupling.

## 4. Experiment matrix

All experiments run against the same calibrated baseline, same random-number streams (common random numbers across policies), 18-month horizon after warm-up, and are evaluated on the metric set of §7.

## 5. Warm-up, replications, and uncertainty treatment

**Warm-up.** The system never reaches steady state (seasonality), so use a *cyclo-stationary* approach: simulate 6 months of warm-up initialized with a sampled backlog snapshot (drawn from the log's mid-period WIP: open cases per phase per age), then collect statistics over the following 18 simulated months (one full seasonal cycle plus repetition of the peak seasons). Verify warm-up sufficiency with Welch's method applied to weekly backlog and weekly mean flow time (visual + MSER-5 rule); extend warm-up if the initialized backlog transient is still visible.

**Run length and replications.** 18-month collection window per replication; start with 30 replications per scenario, then apply a sequential procedure: increase replications until the 95% CI half-width on the primary metric (p90 case duration per case type) is below 5% of the baseline value. Heavy-tailed Complex-variance durations will dominate the replication requirement — expect 50–100 replications for tail metrics.

**Seeds and variance reduction.** Dedicated, independent random streams per stochastic component (arrivals, batch sizes, each service-time family, routing, rework, applicant response, objections) so that **common random numbers** work across scenarios: scenario deltas (E_k − E0) are compared pairwise on identical streams, dramatically tightening CIs on differences. Report paired CIs on differences, not just per-scenario CIs.

**Intervals.** 95% confidence intervals from replication means for central metrics; for tail metrics (p90/p95), use bootstrap-over-replications CIs. For parameters carrying epistemic uncertainty (objection probability, service/wait split, rework probabilities), wrap the whole experiment in an outer loop over parameter draws (Latin hypercube over plausible ranges, or posterior draws if Bayesian estimation was used) → report *credible intervals* combining parameter and stochastic uncertainty, clearly separating the two (variance decomposition).

**Sensitivity analysis.** One-at-a-time tornado on the flagged uncertain parameters (service/wait split, objection tail weight, rework probabilities, bundling propensity, learning factor), plus the LHS global analysis with rank-correlation (Sobol-style if budget allows) on the top-3 decision metrics. A conclusion (e.g., "D10 dominates") must hold across the plausible parameter region to be reported as robust.

**Heavy tails.** Fit tails explicitly (lognormal vs. generalized Pareto beyond p90, chosen by mean-excess plots); never truncate silently — if capping at p99.5 for numerical stability, report the cap and its effect. Prefer medians, p90, and exceedance probabilities (P[duration > SLA]) over means; means of heavy-tailed outputs are unstable and misleading.

## 6. Validation strategy

**Face validation.** Walk domain experts (permit-office lead, chief inspector, legal officer) through animated traces of typical and extreme simulated cases per case type; review sanity of queue behavior around Mondays, council weeks, and peak seasons. Confirm the AND-join and bundling logic matches practice.

**Event-log replay validation.** Trace-level: feed the historical arrival sequence (actual cases with actual attributes and actual arrival timestamps) into the twin and compare simulated vs. actual per-case durations and activity sequences; use PM4Py alignments of *simulated logs* against the process tree to confirm the twin only produces model-conformant behavior at the observed deviation rate. Aggregate: compare the simulated DFG and performance DFG (`pm4py.discover_performance_dfg` on the simulated log) edge-by-edge with the historical ones; flag edges whose mean/median times deviate >20%.

**Distributional validation.** Per case type and per variant group: compare simulated vs. empirical duration distributions with QQ-plots and Kolmogorov–Smirnov / Anderson–Darling tests (AD weights tails), targeting the given medians/p90s (e.g., Complex variance 140d/260d). Also validate per-activity waiting-time distributions where waits are inferable — since waits are emergent in the twin, matching them is a genuine test, not a tautology.

**Resource-utilization validation.** Compare simulated busy fractions per pool per weekday against the reconstructed resource timelines; check specific signatures: Monday clerk saturation, Tue–Thu-only fire activity, legal idle during council weeks, inspector utilization by district including travel.

**Bottleneck validation.** Verify the twin reproduces the known bottleneck ranking (environmental 8d wait > site inspection 8d > legal 7d > planning 6d) and the queue-spike timing (post-Monday completeness spikes, peak-season inspection backlog). A twin that gets means right but bottleneck *locations* wrong is unusable for intervention comparison.

**Out-of-sample validation.** Calibrate on months 1–12, validate on months 13–18 (which include one peak season): predict monthly throughput, backlog trajectory, and duration quantiles per case type without refitting; accept if held-out p50/p90 errors are within pre-registered tolerances (e.g., ±10% median, ±20% p90). Additionally, if any real policy or staffing change occurred in the window, use it as a natural experiment: check the twin predicts the direction and rough magnitude of the observed shift.

Only after passing these gates are intervention comparisons reported — and even then as calibrated estimates with uncertainty, never as exact optima.

## 7. Decision criteria

Primary metrics (per case type and overall, all with paired-difference CIs vs. baseline):
- **Median case duration** — improvement threshold: ≥10% reduction for the targeted case types to consider an intervention material.
- **Tail duration (p90, p95)** — no intervention may worsen p90 of *any* case type by >5%; tail-focused policies (D6, D9) judged primarily here.
- **SLA compliance** — P[duration ≤ SLA] with SLAs: Simple 30d, New residential 90d, Commercial 120d, Complex variance 240d; target ≥85% each; hard floor: no case type below 75%.
- **Fairness across districts/architects** — ratio of p90 duration between worst and best district ≤1.5; small-architect vs. top-20 median gap must not grow by >10% (guards against D3/D7 privileging bulk submitters).
- **Resource utilization** — pools sustained in 60–85% busy band during peaks; >90% for >4 consecutive weeks flags fragility even if flow times look fine.
- **Rework** — missing-doc loops per case (D1 target: −40%), inspection rework rate, legal-conflict rework introduced by D5 (must stay <15% of pre-checked cases for D5 to pass).
- **Backlog dynamics** — peak WIP, and *backlog recovery time* after each stress scenario (weeks to return within 10% of pre-shock backlog); recovery time is the primary robustness score.
- **Robustness** — an intervention is "robust" if its sign of benefit on the primary metric persists across S1–S4 and across the epistemic-parameter credible region; report a dominance table (better/worse/indistinguishable per metric).

Selection rule: shortlist interventions that (i) improve their target metric with a paired 95% CI excluding zero, (ii) violate no guardrail (tail, SLA floor, fairness, utilization), and (iii) remain beneficial in ≥3 of 4 stress scenarios. Rank the shortlist by cost-effectiveness (Δ SLA compliance and Δ p90 per euro of implementation cost, cost data supplied by the municipality). Explicitly report that results are *calibrated comparative estimates under stated assumptions* — not proofs of optimality — and pair any go-decision with a staged rollout plus live twin monitoring (compare realized vs. predicted KPIs monthly, recalibrate quarterly).

def load_log(csv_source: str | io.StringIO = None) -> pd.DataFrame:
    raw = pd.read_csv(io.StringIO(LOG_CSV) if csv_source is None else csv_source)
    df = pm4py.format_dataframe(
        raw,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    df = df.sort_values(["case:concept:name", "time:timestamp"]).reset_index(drop=True)
    return df


# ----------------------------------------------------------------------
# Layer 1b: process model. The provided tree string uses standard
# operators ->, X, +, * with tau, which pm4py.parse_process_tree accepts.
# Limitation: the simplified string encodes control flow only — it says
# nothing about data-driven gate conditions (requires_fire etc.),
# resources, or durations; those are carried in the parameter store.
# ----------------------------------------------------------------------

TREE_STRING = (
    "->( 'Submit application', "
    "*( ->( 'Completeness check', X( tau, "
    "->('Request missing documents','Receive missing documents') ) ), "
    "'Completeness rework' ), "
    "+( 'Planning review', X(tau,'Fire-safety review'), "
    "X(tau,'Environmental review') ), "
    "X(tau,'Public-notice period'), "
    "*( ->('Inspection scheduling','Site inspection'), 'Inspection rework' ), "
    "'Decision drafting', X(tau,'Legal check'), "
    "X('Issue permit','Reject application') )"
)


def load_process_tree():
    try:
        return pm4py.parse_process_tree(TREE_STRING)
    except Exception:
        # Fallback: discover from the log and reconcile manually with the
        # documented nominal process (the excerpt is too small for a
        # faithful discovery; flag for analyst review).
        return None

def describe_log(df: pd.DataFrame) -> dict:
    stats = {}
    stats["variants"] = pm4py.get_variants(df)
    stats["dfg"], stats["start_acts"], stats["end_acts"] = pm4py.discover_dfg(df)
    stats["perf_dfg"], _, _ = pm4py.discover_performance_dfg(df)
    stats["case_arrival_avg_seconds"] = pm4py.get_case_arrival_average(df)
    return stats

    return df
