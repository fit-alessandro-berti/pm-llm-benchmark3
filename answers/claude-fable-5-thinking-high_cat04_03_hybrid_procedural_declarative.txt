# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. **Completed cases only.** All conformance statements assume the case has reached `Close Onboarding`. Running cases would make many "always after" and existence claims prematurely false.
2. **"Final outcome" means `Reject Vendor` or `Activate Vendor`.** `Close Onboarding` is an administrative terminator, not the business outcome.
3. **Risk class is not recorded.** The log has no `risk_level` attribute; the low-/high-risk route can only be inferred from which approval activity occurred. This is a modeling constraint, not a fact about the vendor.
4. **Rejection happens only directly after `Classify Risk`.** The backbone lists rejection as one of three primary outcomes after classification; I assume a case cannot be rejected after `Enhanced Due Diligence` has started. This is stricter than many real processes and is flagged as a blind spot in Section 9.
5. **Clarification cycles occur between the three checks and `Classify Risk`** in the procedural model (matching T2 and T5). In reality clarifications could occur elsewhere; the authoritative pairing rule (R3) therefore lives in DECLARE, which is position-independent.
6. **`Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, and `Suspend Vendor` are cross-cutting exception activities**, deliberately excluded from the procedural alphabet. Procedural conformance is computed on the projection of each trace onto the backbone alphabet; the exception activities are governed by DECLARE, the log skeleton, and the data-aware layer.
7. **Timestamps are reliable and hour-granular**; ties are broken by log order.
8. **At most one clarification-free re-verification loop bound.** Log-skeleton `activ_freq` needs finite sets; I bound clarification cycles at 3 and bank-detail changes at 2, and flag the arbitrariness.

## The R5/R6 conflict

R5 (Legal): after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` **under all circumstances**. R6 (Operations): activation may precede the opinion under a joint emergency authorization that is **not in the event log**, with the opinion due within 24 hours. These are contradictory as written: R5 forbids exactly the ordering R6 permits, and the discriminating condition (the authorization) is unobservable. Silently encoding both would produce a model that either always or never fires on emergency traces, hiding the disagreement.

**Resolution A — Strict legal-first (implemented).** R5 is authoritative. Encode `nonsuccession(Activate Vendor, Obtain Legal Opinion)`: once activation happens, a legal opinion may never follow, so whenever both occur the opinion must be first. R6 is rejected for automated checking because its precondition cannot be verified from the log; emergency cases surface as violations and are routed to manual review, where offline authorization evidence can overturn the finding.
*Compliance risk:* false positives on genuinely authorized emergencies, operational friction, and alert fatigue if emergencies are frequent. The risk is one-sided: nothing sanctions-related is silently waved through.

**Resolution B — Lenient with compensating controls.** Drop the ordering rule from DECLARE; keep R4 (`response(Sanctions Escalation, Obtain Legal Opinion)`) so the opinion must still eventually arrive; add a data-aware check requiring (i) a case attribute `emergency_authorized == True` and (ii) opinion within 24 hours of activation whenever the opinion follows activation. Where the attribute is absent (as in this log), the case is marked `policy-dependent`, not `pass`.
*Compliance risk:* a sanctions-flagged vendor can be activated and even paid before legal review, and because the authorization lives outside the log, the automated layer can never positively confirm compliance — it degrades to warnings. Regulators generally dislike controls whose evidence is unauditable.

**Resolution C — Dual reporting.** Run both rule sets and report both verdicts per case, forcing an explicit policy decision by the compliance owner. Honest but operationally noisy; used here only for the T6 analysis.

**Choice:** Resolution A for the implemented DECLARE model. Section 8 shows T6 under both A and B.

# 3. Procedural Backbone

## 3.1 Compact formal description

Process tree over the backbone alphabet (exception activities excluded; see assumption 6):

```
->( 'Receive Onboarding Request',
    +( 'Capture Master Data', 'Run Sanctions Screening', 'Verify Bank Account' ),
    *( tau, ->( 'Request Clarification', 'Receive Clarification' ) ),
    'Classify Risk',
    X( 'Reject Vendor',
       ->( X( 'Manager Approval',
              ->( 'Enhanced Due Diligence', 'Compliance Approval' ) ),
           'Activate Vendor',
           'Release First Payment' ) ),
    'Close Onboarding' )
```

## 3.2 PM4Py code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def op(operator, parent=None):
    node = ProcessTree(operator=operator, parent=parent)
    if parent is not None:
        parent.children.append(node)
    return node


def leaf(label, parent):
    node = ProcessTree(label=label, parent=parent)
    parent.children.append(node)
    return node


def tau(parent):
    node = ProcessTree(parent=parent)  # silent step
    parent.children.append(node)
    return node


root = op(Operator.SEQUENCE)
leaf("Receive Onboarding Request", root)

checks = op(Operator.PARALLEL, root)
leaf("Capture Master Data", checks)
leaf("Run Sanctions Screening", checks)
leaf("Verify Bank Account", checks)

# zero or more Request->Receive clarification cycles
clar_loop = op(Operator.LOOP, root)
tau(clar_loop)
clar_pair = op(Operator.SEQUENCE, clar_loop)
leaf("Request Clarification", clar_pair)
leaf("Receive Clarification", clar_pair)

leaf("Classify Risk", root)

outcome = op(Operator.XOR, root)
leaf("Reject Vendor", outcome)
accept = op(Operator.SEQUENCE, outcome)
route = op(Operator.XOR, accept)
leaf("Manager Approval", route)
high_risk = op(Operator.SEQUENCE, route)
leaf("Enhanced Due Diligence", high_risk)
leaf("Compliance Approval", high_risk)
leaf("Activate Vendor", accept)
leaf("Release First Payment", accept)

leaf("Close Onboarding", root)

procedural_model = root

# accepting Petri net for alignment-based conformance
net, initial_marking, final_marking = pm4py.convert_to_petri_net(procedural_model)
```

## 3.3 Explanation

- **Concurrency.** The three checks run under a PARALLEL operator; any interleaving after receipt is conforming (covers both T1's and T2's orders).
- **Choices.** The outer XOR separates rejection from acceptance; the inner XOR separates the low-risk route (`Manager Approval`) from the high-risk route (`Enhanced Due Diligence` then `Compliance Approval`). The tree thus structurally enforces R1, the "exactly one approval if accepted / none if rejected" half of R2 that DECLARE cannot express, and R8.
- **Clarification loop.** `*(tau, ->(RC, RCv))` admits zero or more complete request/response pairs between the checks and classification. **Disclosed approximation:** real clarifications might occur at other points (e.g., during due diligence); such traces would misalign here even though R3 is satisfied. DECLARE (`altsuccession`) is the authoritative, position-independent pairing rule; the tree's placement is a convenience that matches all given traces.
- **Terminal outcomes.** Every path ends in `Close Onboarding`, after either `Reject Vendor` or `Release First Payment`, per backbone item 5.
- **Deliberately excluded.** `Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, and `Suspend Vendor` are not in the tree. Embedding them would force either an unsound spaghetti of optional interleavings (the opinion legitimately appears before approval in T7 and — under Resolution B — after activation in T6) or an arbitrary fixed position that would generate false procedural violations. A block-structured tree cannot express "optional activity anywhere after X but before/after Y depending on an unobservable flag"; this non-block-structured interaction is the disclosed limitation, handled by projection plus the declarative layers. Post-activation change/suspend behavior is likewise excluded and owned by the data-aware layer (R11).

## Rule semantics

| Template / key | Direction and semantics | Requirement |
|---|---|---|
| `init(Receive Onboarding Request)` | The first event of every case is the onboarding request | Backbone 1 |
| `existence(A)` for ROR, Classify Risk, Close Onboarding | A occurs at least once per case | Backbone 1, 3, 5 |
| `altsuccession(Request Clarification, Receive Clarification)` | Alternate response **and** alternate precedence combined: every request is eventually followed by a response with **no other request in between**, and every response is preceded by a request with no other response in between. Chosen over `chainsuccession` because other activities (e.g., `Classify Risk`) may legally sit between request and response, so a "directly follows" chain template would be wrong; chosen over plain `succession` because plain response would tolerate two open requests, which R3 forbids | R3 |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | Forward eventuality: after every escalation, an opinion eventually occurs. **Response, not precedence:** it obliges the future, it does not constrain what happened before the opinion | R4 |
| `response(Change Bank Details, Suspend Vendor)` | After every bank-detail change, a suspension eventually occurs (over-approximates R11's "after activation" condition; authoritative version in the data layer) | R11 (partial) |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | Backward guard: an escalation may occur **only if** a screening occurred earlier. Precedence does not require escalation to ever happen — it is vacuously satisfied when absent, which is exactly right | R7 |
| `precedence(Activate Vendor, Release First Payment)` | A payment may occur only after activation | Backbone 5 |
| `precedence(Enhanced Due Diligence, Compliance Approval)` | Compliance approval only after due diligence | Backbone 4 / R8 context |
| `precedence(Classify Risk, Activate Vendor)` | Activation only after classification | Backbone 3–4 |
| `noncoexistence(Activate Vendor, Reject Vendor)` | The two activities never occur in the same case, **in any order**. Noncoexistence, not nonsuccession: rejection before activation must be just as illegal as after | R1 |
| `noncoexistence(Manager Approval, Compliance Approval)`, `noncoexistence(Manager Approval, Enhanced Due Diligence)` | Route exclusivity, order-independent | R8 / R2 |
| `noncoexistence(Reject Vendor, Manager Approval)`, `noncoexistence(Reject Vendor, Compliance Approval)` | No approval of any kind in a rejected case | R2 |
| `nonsuccession(Activate Vendor, Obtain Legal Opinion)` | After activation, a legal opinion may **never** follow. **Nonsuccession, not noncoexistence:** both activities may occur in one case (T7 is legal); only the ordering activation-then-opinion is forbidden. Together with `response(SE, OLO)`, this forces opinion-before-activation whenever escalation occurred — the strict R5 reading | R5 (Resolution A) |

All rules carry `support = 1.0` and `confidence = 1.0` because they are **normative policies**, not discovered patterns; Section 9 discusses why these numbers must not be mistaken for empirical evidence.

# 5. Log-Skeleton Model

Orientation convention used throughout: `(a, b) ∈ always_before` means every occurrence of `a` is preceded by at least one earlier `b` in the same case; `(a, b) ∈ always_after` means every occurrence of `a` is eventually followed by an occurrence of `b`; `never_together` and `equivalence` are order-insensitive (equivalence = identical per-case occurrence counts).

## Overlaps, disagreements, and defenses

- **`directly_follows` is deliberately empty.** Concurrency of the three checks and the interleaving of exception activities make every candidate brittle: e.g., `Enhanced Due Diligence` is directly followed by `Compliance Approval` in T2 and T6 but not in T7 (the legal opinion intervenes legally). An empty set is the only defensible population.
- **`equivalence ("Activate Vendor","Release First Payment")`** duplicates backbone item 5 in count form. Caveat: if a suspended vendor (R11) legitimately never gets paid, this pair breaks; it holds for the modeled completed-case universe and correctly fails T8 (activation without payment).
- **`always_before` vs DECLARE `precedence`:** same direction of guard, different strictness — skeleton `always_before` requires the predecessor for *every* occurrence of the anchor, which coincides with `precedence` here because anchors occur at most once. `("Sanctions Escalation","Run Sanctions Screening")` intentionally duplicates R7; `("Compliance Approval","Enhanced Due Diligence")` duplicates the high-risk sequence.
- **`always_after ("Request Clarification","Receive Clarification")`** is strictly weaker than the DECLARE `altsuccession`: it does not forbid a second request before the response. Combined with `equivalence`, it still catches T5 (counts 1 vs 0). DECLARE remains authoritative for R3.
- **`never_together`** duplicates R1/R2/R8 noncoexistence rules; the skeleton is kept as a cheap first-pass screen (Section 10). No pair `("Reject Vendor","Enhanced Due Diligence")` is asserted, because rejection-after-EDD, while off-backbone under assumption 4, is plausible in reality and I do not want the cheap layer to over-claim.
- **No `always_before ("Activate Vendor","Obtain Legal Opinion")`:** that would encode an *unconditional* R5, wrong for non-escalated cases. The skeleton cannot express the conditional; R5 stays in DECLARE.

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800.0,  86400.0),  # 48 h ± 24 h
    ("Sanctions Escalation", "Obtain Legal Opinion"):   ( 43200.0,  21600.0),  # 12 h ± 6 h

}
zeta = 2.0
# pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)
```

A pair is flagged when `|observed − mean| > zeta × std`, i.e. outside 48 ± 48 h, 12 ± 12 h, and 72 ± 72 h respectively.

**Why warnings, not control-flow violations.** R12 says explicitly these expectations are "normative enough to flag but not automatically reject." Beyond that instruction, three design reasons: (1) durations are performance properties, not safety properties — a late legal opinion that still precedes activation (T7) satisfies every ordering obligation; conflating lateness with illegality would erase that distinction. (2) Durations depend on workload, calendars, and time zones that the model does not capture; a hard fail would encode operational noise as compliance breach. (3) The temporal profile evaluates only **realized** pairs: it is structurally silent when the second activity is missing (T5's unanswered clarification produces no measurable interval). A layer that cannot see absence must not be given veto power; existence and order belong to the control-flow layers.

# 7. Resource- and Data-Aware Checks

Required event attributes: `case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`; required case attribute (Resolution B only): `emergency_authorized`.

```python
import pandas as pd

def check_segregation_of_duties(df):
    """R9. Missing org:resource => conservative violation ('unprovable'),
    routed to manual review rather than silently passed."""
    findings = []
    for case_id, g in df.groupby("case:concept:name"):
        def resources(activity):
            vals = g.loc[g["concept:name"] == activity, "org:resource"]
            if vals.isna().any():
                findings.append((case_id, "R9",
                                 f"missing resource on {activity}: cannot prove segregation"))
            return set(vals.dropna())

        approvers = resources("Manager Approval") | resources("Compliance Approval")
        if resources("Verify Bank Account") & approvers:
            findings.append((case_id, "R9",
                             "bank-account verifier equals the applicable approver"))
        if resources("Capture Master Data") & resources("Activate Vendor"):
            findings.append((case_id, "R9",
                             "master-data owner equals the vendor activator"))
    return findings

# pm4py helper for the pairwise checks (verify retain-direction of your
# pm4py version at deployment; the pandas check above is authoritative):
#   pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
#   pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Compliance Approval")
#   pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")


EMERGENCY_WINDOW = pd.Timedelta(hours=24)

def check_emergency_policy(df, case_attributes):
    """R5/R6. Only meaningful under Resolution B; under Resolution A the
    DECLARE nonsuccession rule already fails these cases outright."""
    findings = []
    for case_id, g in df.groupby("case:concept:name"):
        g = g.sort_values("time:timestamp")
        ts = lambda a: g.loc[g["concept:name"] == a, "time:timestamp"]
        se, olo, av = ts("Sanctions Escalation"), ts("Obtain Legal Opinion"), ts("Activate Vendor")
        if se.empty:
            continue                                   # rule not applicable
        if olo.empty:
            findings.append((case_id, "R4", "fail: escalation without legal opinion"))
            continue
        if av.empty or olo.iloc[0] <= av.iloc[0]:
            continue                                   # opinion precedes activation: compliant
        # opinion AFTER activation: emergency clause is the only escape
        authorized = case_attributes.get(case_id, {}).get("emergency_authorized")
        within_24h = (olo.iloc[0] - av.iloc[0]) <= EMERGENCY_WINDOW
        if authorized is True and within_24h:
            findings.append((case_id, "R6", "warning: emergency activation, opinion in window"))
        elif authorized is None:
            findings.append((case_id, "R6",
                             "policy-dependent: authorization evidence is outside the log; "
                             "manual review required" +
                             ("" if within_24h else "; opinion also outside 24 h window")))
        else:
            findings.append((case_id, "R5/R6", "fail: unauthorized or late post-activation opinion"))
    return findings


def check_bank_change(df):
    """R11: change after activation => eventual suspension, and a fresh
    verification between the change and any later payment."""
    findings = []
    for case_id, g in df.groupby("case:concept:name"):
        g = g.sort_values("time:timestamp")
        t = lambda a: list(g.loc[g["concept:name"] == a, "time:timestamp"])
        av = t("Activate Vendor")
        if not av:
            continue
        for change in [c for c in t("Change Bank Details") if c > av[0]]:
            if not any(s > change for s in t("Suspend Vendor")):
                findings.append((case_id, "R11", "fail: bank change without suspension"))
            for pay in [p for p in t("Release First Payment") if p > change]:
                if not any(change < v < pay for v in t("Verify Bank Account")):
                    findings.append((case_id, "R11",
                                     "fail: payment after bank change without re-verification"))
    return findings
```

**Missing-attribute policy.** `org:resource` missing on any R9-relevant event: conservative violation (segregation is unprovable), manual review. `emergency_authorized` missing (as in this log): the emergency check returns `policy-dependent`, never `pass` — the log alone cannot certify R6. Timestamps missing: the case is excluded from temporal and window checks and flagged for data quality.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement.** R1 is enforced three times (procedural XOR, DECLARE `noncoexistence`, skeleton `never_together`); R3 three times; R4, R7, R8 twice. This is deliberate defense-in-depth for cheap screening (Section 10), but reporting must deduplicate by requirement ID, or one root cause (T8's rejection-after-activation) shows up as five findings and users lose the signal.
- **Constraints that break under loops or post-activation change.** The skeleton's `activ_freq` bounds on clarifications ({0..3}) and bank changes ({0..2}) are arbitrary finite caps forced by the formalism; a legitimate fourth clarification cycle would fail the skeleton while satisfying R3. `equivalence(Activate Vendor, Release First Payment)` and `always_after(Activate Vendor, Release First Payment)` break if an R11 suspension legitimately halts payment. `nonsuccession(Activate Vendor, Obtain Legal Opinion)` forbids any second, benign post-activation legal opinion. R11's re-verification clause speaks of "any later Release First Payment" while R10 caps payments at one — the clause only has bite when the bank change happens between activation and the (single) first payment; for changes after the payment, the suspension obligation remains but the re-verification clause is vacuous by construction.
- **Vacuity in declarative rules.** In T1–T5, `response(SE, OLO)`, `precedence(RSS, SE)`, and the nonsuccession rule are all vacuously satisfied because escalation never occurs; in T3 every clarification and activation rule is vacuous too. A dashboard reporting "100% DECLARE conformance" on a log of rejected, escalation-free cases proves almost nothing — vacuous satisfaction must be reported separately from active satisfaction.
- **Missing case attributes.** The two most decision-relevant facts are absent from the log: the risk classification outcome (low/high is only inferred from which approval occurred — circular when validating routing) and the emergency joint authorization (making R6 permanently unverifiable and forcing the R5/R6 verdict to be policy-dependent). A `risk_level` attribute on `Classify Risk` and an `emergency_authorized` case attribute would convert two manual reviews into automated checks.
- **Timestamp-only limitations.** Hour granularity makes same-hour orderings depend on log order; the 24-hour emergency window is measurable but its precondition is not; T7 shows zeta-threshold brittleness (z ≈ 1.94 passes, z = 2.01 would warn) — thresholds on continuous quantities create arbitrary cliffs and should be tuned on historical distributions, not taken from a policy table alone.
- **Support/confidence are not normative truth.** The `support: 1.0 / confidence: 1.0` entries in `declare_model` are metadata slots that discovery algorithms populate empirically. Here they were set by hand to declare rules mandatory. The inverse mistake is worse: discovering `confidence = 1.0` from a log only means no violation was *observed* — with vacuous satisfaction and small samples, a rule can score perfectly while never having been tested. Metadata describes evidence; policy status must be an explicit, separately governed decision.

# 10. Deployment Recommendation

**Canonical procedural representation.** The block-structured process tree of Section 3 is the maintained artifact (sound by construction, human-readable); it is compiled to an accepting Petri net for alignment-based conformance. POWL is unnecessary because the backbone is fully block-structured; the only non-block-structured behavior (escalation/opinion, bank changes) is intentionally outside the procedural alphabet.

**Authoritative policy layer.** DECLARE under Resolution A (strict R5) is authoritative for all cross-cutting ordering and existence policies (R1–R5, R7, R8); the log skeleton is authoritative only for cardinalities (R10); the resource/data layer is authoritative for R9, R6, and R11; the temporal profile is authoritative for R12 and can only produce warnings. The R5/R6 choice is recorded as an explicit, versioned policy decision with Legal as owner; switching to Resolution B is a one-line change (delete the `nonsuccession` entry, activate the emergency check) but requires the `emergency_authorized` attribute to be logged first, otherwise the organization is institutionalizing an uncheckable exception.

**Order of conformance checks.**
1. **Log skeleton** — cheapest screen: counts, `never_together`, gross ordering. Kills obviously broken traces (T8) before expensive alignments.
2. **Procedural alignment** on the projection to the backbone alphabet — localizes *where* control flow breaks (T5's unexitable clarification loop).
3. **DECLARE** — cross-cutting policies, including the R5 verdict on escalation cases (T6).
4. **Resource/data checks** — R9 segregation, R6 emergency evidence, R11 bank-change protocol (T4; T6's manual-review routing).
5. **Temporal profile** (`zeta = 2.0`) — last, and only as warnings (T7).

**Surfacing contradictory findings.** Report per case, keyed by requirement ID, with one finding per requirement even when several layers detect it (layers listed as corroboration); order findings by the earliest decisive violating event. Severity ladder: `fail` > `policy-dependent` > `warning` > `pass`, with vacuously satisfied rules displayed as "not exercised" rather than "satisfied." Findings that flip between R5/R6 resolutions (T6) are shown with both verdicts side by side and a link to the policy decision record — the system must never average or silently pick one, because the disagreement between Legal and Operations is itself the compliance-relevant fact until the joint authorization becomes auditable in the log.
