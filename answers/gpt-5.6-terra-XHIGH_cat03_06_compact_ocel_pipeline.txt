## 1. Modeling assumptions

- Object types use the exact capitalization: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`.

- The E2O qualifier vocabulary is role-oriented:
  - `created_order`
  - `receiving_order`, `added_item`
  - `reservation_order`, `reserved_item`
  - `affected_order`, `packed_package`, `packed_item`
  - `dispatched_package`, `dispatch_delivery`
  - `issued_invoice`, `billed_order`
  - `recorded_payment`, `payment_invoice`
  - `confirmed_delivery`
  - `closed_order`

- O2O direction convention: `ocel:oid` is the source/owner/actor and `ocel:oid_2` is the target. Thus:
  - Order  Item: `contains_item`
  - Package  Item: `packs_item`
  - Delivery  Package: `carries_package`
  - Invoice  Order: `bills_order`
  - Payment  Invoice: `partially_settles`

- `M1` and `M2` both use `partially_settles`. The total invoice amount is not stated, so it would be unsafe to claim that `M2` completes settlement merely because the known payments total 250.

- The E2O table follows a source-direct policy:
  - `Reserve Stock` is directly related to I1, I3, O100, and O200 because the narrative explicitly says it is jointly shared by both orders.
  - `Pack Package P1` is directly related to P1, I1, I3, O100, and O200 because the narrative explicitly states that it relates to both orders.
  - `Pack Package P2` is directly related to P2 and I2, but not directly to O100. O100 is structurally related through O100  I2 and P2  I2 in O2O.
  - Dispatch events directly involve Packages and Deliveries, but do not directly involve Orders or Items.
  - Delivery confirmations directly involve Deliveries only.
  - Invoice issuance directly involves V1 and the billed Orders.
  - Payment recording directly involves the Payment and V1, not the Orders.

- Analytical propagation is kept separate from source facts. `relations` contains only direct event participation stated by the process narrative and carries `relation:provenance = "source_direct"`. O2O rows are declared structural business links. If an enriched impact analysis is needed, derived E2O rows should be created in a separate DataFrame or OCEL copy and marked, for example, `relation:provenance = "derived_o2o"`.

- The pipeline assumes a recent PM4Py version providing `OCEL(events=..., objects=..., relations=..., o2o=...)` and the listed `pm4py` OCEL discovery functions. If a local version has a constructor naming difference, only the isolated constructor line should be adapted; the four DataFrames and their semantics should remain unchanged.

        ("E08", "Pack Package",     "2026-04-06T09:05:00Z", None),
        ("E09", "Dispatch Package", "2026-04-06T10:00:00Z", None),
        ("E10", "Dispatch Package", "2026-04-06T10:15:00Z", None),

objects = pd.DataFrame(
    [
        ("O100", "Order"),
        ("O200", "Order"),
        ("I1", "Item"),
        ("I2", "Item"),
        ("I3", "Item"),

    columns=["ocel:oid", "ocel:type"],
)

# ---------------------------------------------------------------------
# 3. Source-direct E2O relation specifications
#
# No E2O rows are inferred merely through O2O navigation. For example:
# - E08 is directly related to P2 and I2, but not directly to O100.
# - E13/E14 are directly related to deliveries, not to packages/items/orders.
# - E12/E15 are directly related to payment and invoice, not to billed orders.

e2o_specs = [

    ("E02", "O100", "receiving_order"),

    ("E07", "I3", "packed_item"),
    ("E07", "O100", "affected_order"),
    ("E07", "O200", "affected_order"),

    ("E08", "P2", "packed_package"),

    ("E09", "P1", "dispatched_package"),

        "ocel:activity",
        "ocel:timestamp",
        "ocel:oid",
        "ocel:type",
        "ocel:qualifier",

        ("M2", "V1", "partially_settles"),

# ---------------------------------------------------------------------

    "ocel:timestamp",
    "ocel:oid",
    "ocel:type",
    "ocel:qualifier",
}

assert len(objects) == 12
assert events["ocel:eid"].is_unique
assert objects["ocel:oid"].is_unique
assert set(required_relation_columns).issubset(relations.columns)

assert events["ocel:timestamp"].dt.tz is not None
assert relations["ocel:timestamp"].dt.tz is not None

known_event_ids = set(events["ocel:eid"])
known_object_ids = set(objects["ocel:oid"])

assert set(relations["ocel:eid"]).issubset(known_event_ids)
assert set(relations["ocel:oid"]).issubset(known_object_ids)

assert set(o2o["ocel:oid_2"]).issubset(known_object_ids)

assert not relations[list(required_relation_columns)].isna().any().any()
assert not relations.duplicated().any()
assert not relations.duplicated(
    subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]
).any()
assert not o2o.duplicated().any()
assert (o2o["ocel:oid"] != o2o["ocel:oid_2"]).all()

assert (
    relations["ocel:type"]
    == relations["ocel:oid"].map(object_type_by_id)
).all()

relation_event_check = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
    on="ocel:eid",
    how="left",
    suffixes=("_relation", "_event"),
    validate="many_to_one",

assert (
    relation_event_check["ocel:activity_relation"]
    == relation_event_check["ocel:activity_event"]

The most consequential convergence event is E07, `Pack Package` for P1. It connects P1, I1, I3, O100, and O200 in one event. It makes P1 a cross-order package and causes the same event to appear in both Order-flattened traces.

E06, `Reserve Stock`, is also consequential because it directly joins O100 and O200 through a shared reservation. E11, `Issue Invoice`, is the financial convergence point because V1 bills both Orders. Conversely, E08 is a divergence point: P2 serves only I2 and is structurally associated with O100 through O2O but is not directly attached to O100 in E2O.

## 4. Expected flattened behavior

Flattening creates a conventional case notion by treating each object of the selected type as a case. A shared event is copied into each relevant case trace of that type.

| Flattening type | Approximate traces | Copied shared events | Omitted lifecycle aspects | Likely DFG edges and possible misinterpretation |
|---|---|---|---|---|
| `Order` | O100: Create  Add  Add  Reserve  Pack P1  Issue Invoice  Close. O200: Create  Add  Reserve  Pack P1  Issue Invoice  Close. | E06, E07, and E11 appear in both Order cases. | O100 does not directly contain E08, E10, or E14 under this source-direct policy, despite I2 being in P2. Dispatches, confirmations, and payment events are omitted from Order traces. | Create  Add; Add  Add; Add  Reserve; Reserve  Pack; Pack  Issue Invoice; Issue Invoice  Close. The `Add Item  Add Item` edge can look like rework, but it is simply O100 receiving two distinct items. The trace can misleadingly suggest that P1 is the only package relevant to O100. |
| `Package` | P1: Pack  Dispatch. P2: Pack  Dispatch. | None across Package cases: each pack/dispatch event concerns one Package. | Item addition/reservation, delivery confirmation, invoices, payments, and Order closure are absent. | Pack  Dispatch, likely with frequency 2. It can misleadingly present P1 and P2 as independent, identical packages and hide that P1 combines items from O100 and O200. |
| `Delivery` | D1: Dispatch  Confirm. D2: Dispatch  Confirm. | None across Delivery cases. | Package packing is absent because E07/E08 do not directly reference Deliveries. Item, Order, invoice, and payment behavior is also absent. | Dispatch  Confirm, likely with frequency 2. It can misleadingly treat delivery as a simple two-step process without revealing that D1 transports cross-order package P1. |
| `Invoice` | V1: Issue Invoice  Record Payment M1  Record Payment M2. | None across Invoice cases because V1 is the only Invoice. | Delivery confirmations, package composition, Order closures, and any allocation of each payment to O100 versus O200 are absent. | Issue Invoice  Record Payment and Record Payment  Record Payment. The latter self-loop means two installments of the same activity label, not a rework loop. It can misleadingly imply that both payments settle the invoice fully. |

The discovered log skeletons are necessarily weak because the flattened logs are tiny:

- The Package and Delivery skeletons will likely indicate a stable ordering from Pack to Dispatch and Dispatch to Confirm, respectively.
- The Order skeleton may identify some common ordering but cannot reliably infer a general Order process from only O100 and O200.
- The Invoice skeleton is based on one trace and should not be treated as evidence of a robust payment-control rule.

Flattening on `Payment` would be particularly weak. M1 and M2 each have exactly one direct event, `Record Payment`, so Payment flattening produces two one-event traces. There are no directly-follows edges, almost no useful skeleton constraints, and no visibility of how payments relate to O100 and O200 except through V1 and O2O.

## 5. Expected object-centric structures

- **OC-DFG:**  
  The OC-DFG should preserve distinct object-type perspectives simultaneously. The Order perspective contains the shared `Reserve Stock`, `Pack Package`, and `Issue Invoice` events for O100 and O200. The Item perspective distinguishes I1 and I3, which pass through reservation and P1 packing, from I2, which is added and packed into P2 without the shared reservation. The Package perspective shows Pack  Dispatch, while Delivery shows Dispatch  Confirm. The Invoice perspective shows Issue Invoice  Record Payment  Record Payment.

  P1 is structurally important because one `Pack Package` event connects P1 to I1, I3, O100, and O200. V1 similarly converges O100 and O200 financially. M1 and M2 continue the V1 lifecycle but do not directly appear in the Order behavior under this E2O policy.

- **OTG:**  
  The object-type graph should expose the main type-level interaction topology:
  - Order—Item through item addition and joint reservation;
  - Order—Package and Item—Package through E07;
  - Package—Delivery through dispatch;
  - Order—Invoice through invoice issuance;
  - Invoice—Payment through payment recording.

  In particular, the direct E2O policy intentionally does not create Order—Delivery or Order—Payment co-participation edges. Those relationships can be derived structurally, but they are not direct event observations.

- **ET–OT graph:**  
  The event-type-to-object-type graph should make role participation explicit:
  - `Reserve Stock` touches Order and Item.
  - `Pack Package` touches Package and Item for both package events, and also Order for E07.
  - `Dispatch Package` touches Package and Delivery.
  - `Issue Invoice` touches Invoice and Order.
  - `Record Payment` touches Payment and Invoice.
  - `Confirm Delivery` touches Delivery only.

  This graph is useful for seeing where the modeling policy intentionally stops. For example, `Record Payment` does not touch Order, even though V1 bills O100 and O200.

- **Object-centric Petri net:**  
  The discovered object-centric Petri net may identify synchronized behavior around E06 and E07, because those events are shared across multiple Order and Item objects. It may also identify V1 as a point where two Order-related invoice obligations converge and M1/M2 continue the Invoice lifecycle. P1 will likely appear as a package-side object involved in a multi-order packing synchronization.

  The learned net is not uniquely determined. The dataset has only two Orders, two Packages, two Deliveries, one Invoice, and two Payments, so discovery can overfit observed paths. Different miners, thresholds, or relation-enrichment policies may produce different but defensible nets.

- **Object-interactions summary:**  
  The interaction summary should highlight:
  - O100 and I1 at E02;
  - O100 and I2 at E03;
  - O200 and I3 at E05;
  - O100, O200, I1, and I3 jointly at E06;
  - P1, O100, O200, I1, and I3 jointly at E07;
  - P1 and D1 at E09;
  - P2 and D2 at E10;
  - V1, O100, and O200 jointly at E11;
  - M1 and V1 at E12;
  - M2 and V1 at E15.

  M1 and M2 interact with V1 separately; they do not directly co-participate with each other. P1 and V1 are both key convergence objects, but in different domains: P1 combines fulfillment work while V1 combines billing and settlement work.

## 6. Modeling alternatives

1. **Source-minimal direct E2O policy — the policy used here**

   Only entities explicitly participating in the described event receive E2O links. O2O captures enduring structure such as Order  Item and Invoice  Order.

   Effects:
   - Order flattening omits Pack P2, dispatches, confirmations, and payments unless they are explicitly linked to Orders.
   - The resulting DFGs avoid artificial inflation.
   - P1 and V1 remain explicit cross-order convergence points because their shared event relations are directly stated.

2. **Full operational involvement policy**

   Add direct E2O links for every business object operationally affected by an event. For example:
   - Attach O100 to E08 because P2 packs I2 and I2 belongs to O100.
   - Attach P1, I1, I3, O100, and O200 to E13 because D1 confirms the delivery carrying P1.
   - Attach O100 and O200 to payment events because V1 bills both Orders.

   Effects:
   - Order traces become much longer and include P2 packing, dispatches, delivery confirmations, and payment activity.
   - The OTG becomes denser and can contain more direct Order—Delivery and Order—Payment connections.
   - Shared events are replicated into more flattened cases, increasing DFG counts and potentially making synchronization look like repeated independent work.

3. **O2O-propagated analytical relation policy**

   Preserve the source-direct `relations` table unchanged, then produce a separate derived relation table for a specific analysis. For example:
   - From P2  I2 and O100  I2, derive that E08 affects O100.
   - From D1  P1, P1  I1/I3, and Orders  Items, derive Order impact for E09 and E13.
   - From M1/M2  V1 and V1  Orders, derive financial impact on both Orders.

   Effects:
   - An impact-oriented Order DFG can show end-to-end order fulfillment and financial settlement.
   - The source OCEL remains auditable because derived rows are not mixed with observed event participation.
   - Analysts can compare source-direct and derived results to distinguish observed coordination from structural propagation.

4. **Invoice-centric financial policy**

   Model invoice issuance and payment events only against Invoice and Payment objects, leaving the Invoice  Order link exclusively in O2O. This is defensible if financial event systems record only invoice identifiers and do not directly load order references into event records.

   Effects:
   - Invoice flattening remains useful.
   - Order flattening loses `Issue Invoice` unless analytical propagation is added.
   - The ET–OT graph becomes more conservative by showing no direct `Issue Invoice`  Order association.

## 7. Failure modes

1. **Relation inflation**  
   Adding every transitive O2O neighbor to every event can make a single dispatch appear as a direct action on all related Orders, Items, Invoices, and Payments. Flattened logs become longer, DFG edge counts rise, and the model can falsely imply broad operational synchronization.

2. **Missing direct E2O links**  
   Omitting the direct O100/O200 links from E06, E07, or E11 would erase explicitly stated shared work. P1 would no longer appear as a cross-order package in event-level analysis, and V1 would not visibly bill both Orders in the E2O layer.

3. **Treating O2O propagation as observation**  
   O2O states structural business facts; it does not automatically prove that every event involving one endpoint was observed against the other endpoint. Derived propagation must be labeled and kept separate from source-direct E2O rows.

4. **Duplicate shared events after flattening**  
   E07 and E11 occur once in the OCEL but appear in both O100 and O200 traces after Order flattening. Counting flattened rows as unique operational events would double-count the shared event.

5. **Ambiguous payment allocation**  
   M1 and M2 are recorded against V1, which bills O100 and O200, but there is no allocation of 100 or 150 to either Order. It is invalid to infer that one payment belongs to one Order.

6. **Unsupported claim that M2 completes settlement**  
   The amounts add to 250, but the invoice total and settlement status are absent. Marking M2 as `completes_settlement` would add an unsupported financial conclusion.

7. **Overly short Payment traces**  
   Each Payment object has one event. Payment flattening has no meaningful DFG sequence and should not be used as the primary behavioral view.

8. **Constructor or API version mismatch**  
   PM4Py versions may differ in OCEL constructor parameters, graph object representations, or visualization names. The adaptation should be localized to the constructor or API call rather than changing event, object, E2O, or O2O semantics.

9. **Activity/timestamp inconsistency between events and relations**  
   If a relation row carries the wrong activity or timestamp, directly-follows and temporal analyses may silently produce incorrect results. The pipeline explicitly validates equality against the canonical event table.

10. **Identifier collisions or type mismatches**  
    Reusing an object ID across types, such as using `P1` both as a Package and a Payment, would corrupt joins and flattened cases. Global object-ID uniqueness and relation type validation are necessary.

11. **Naive or inconsistent timestamps**  
    Mixing timezone-naive timestamps with UTC timestamps can distort ordering and duration analysis. All timestamps here are parsed as UTC-aware.

12. **False total ordering for timestamp ties**  
    This example has no tied timestamps, so chronological order is unambiguous. In real data, equal timestamps should not be converted into a causal order merely by sorting on event ID or ingestion order; a tie-breaker is deterministic formatting, not evidence of causality.

## 8. Final semantic checks

A reviewer can manually inspect the generated tables and verify at least the following:

1. `events` contains exactly 17 unique event IDs from E01 through E17, and all `ocel:timestamp` values are UTC-aware.

2. `objects` contains exactly 12 globally unique objects with the expected types: two Orders, three Items, two Packages, two Deliveries, one Invoice, and two Payments.

3. The only non-null `amount` values are 100 for E12 and 150 for E15, confirming that payment amounts are event attributes rather than separate objects.

4. Every E2O relation row repeats the exact activity and timestamp of its `ocel:eid` in `events`.
