# 1. Assumptions, objectives, and decision variables

**Evidence status.** The calculations below are planning estimates derived from the prompt, not observed KPIs. In particular, the scenario comparison is deliberately qualitative where the supplied evidence cannot identify a numerical delay or SLA result.

**Demand and service assumptions**

- **A1 — service distributions:** for the central model, ordinary and complex-tail durations are independent uniform draws over their respective ranges. The resource multiplier is applied after drawing the base duration. Thus, for activity \(a\),
  \[
  \mu_a=(1-p_a)\frac{L_o+U_o}{2}+p_a\frac{L_c+U_c}{2}.
  \]
  Uniformity is an assumption, not a consequence of receiving a range. Section 2 therefore also gives an endpoint envelope for total work.
- **A2 — arrivals:** block expected arrivals are used deterministically for capacity analysis. A simulation could use piecewise Poisson arrivals, uniform within each block, with independent multinomial priority and case-type draws. Expected arrivals alone do not establish that process.
- **A3 — independence:** priority, case type, and complexity are initially independent, conditional on the block percentages. Complexity draws are independent across activities. Correlated complex cases would worsen tail risk.
- **A4 — clocks and calendars:** the SLA clock starts at arrival and runs through waiting, breaks, handovers, coordination, outages, and off-shift time. P1/P2/P3 deadlines are therefore 120/480/1,440 elapsed minutes. Breaks and ordinary off-shift pauses do not incur the preemption restart penalty.
- **A5 — calendar horizon:** the supplied shifts describe one day. Next-day staffing and initial backlog are unknown. Consequently, same-day capacity can be analyzed, but 8-hour and 24-hour SLA attainment cannot be determined uniquely.
- **A6 — overhead:** the 7- and 5-minute handover terms are elapsed case delays; the 5-minute setup is also resource-occupied time. The 8-minute parallel coordination term is elapsed time before Validation. If handover or coordination also consumes staff effort, the capacity estimates below become more optimistic.
- **A7 — preemption:** only P1 work can trigger preemption, only a lower-priority diagnostic activity can be interrupted, and a case can be interrupted at most once. If remaining active service is \(R\), the remaining work after resumption is \(1.10R\). Completed service is not lost. A safe dispatch rule should additionally require that predicted P1 benefit exceed the restart, setup, and handover costs.
- **A8 — U2 interpretation:** primarily, expected arrivals in 12:00–16:00 remain unchanged; E and ES type weights are doubled and all type proportions are renormalized. An alternative interpretation—absolute E and ES case counts double, so total arrivals grow—is evaluated as a sensitivity because it is substantially more severe.
- **A9 — U1 priority renormalization:** the additional 8 P1 percentage points are taken from P2 in the two affected blocks. Other reallocations between P2 and P3 change P2/P3 risk, but not the service-load calculations.

**Parallel versus sequential ME/ES execution**

For a two-branch case, let \(s_1,s_2\) be active base durations, \(m_{r,a}\) the resource multiplier, and \(H\) handover/team-move delay. A same-resource sequential execution has approximately

\[
C_{\rm seq}=H_{\rm seq}+s_1m_{r,1}+s_2m_{r,2},
\]

before Validation, ignoring queueing. A parallel execution has approximately

\[
C_{\rm par}=\max_j(w_j+H_j+s_jm_{r_j,j})+8,
\]

where \(w_j\) includes resource wait. Parallel execution is attractive only when its predicted validation-ready time is sufficiently earlier and it does not displace a more urgent case. It **does not reduce total branch work**: capacity still consumes \(s_1m_1+s_2m_2\), on one or two resources.

**Decision variables**

- activity-to-resource assignment and start time;
- fixed-home versus overflow eligibility;
- sequential/parallel choice for every ME/ES case;
- P1 reserve by skill and time interval, and its release rule;
- preemption indicator, constrained to at most one per case;
- setup/handover avoidance and case affinity;
- overtime \(o_r\le 30\) minutes per resource;
- optional emergency staffing or borrowed qualified capacity;
- P3 aging promotion and reserve-release thresholds.

**Objectives**

Let \(T_c\) be arrival-to-Validation-completion time, \(D_{p_c}\) its SLA deadline, \(A_p\) SLA attainment, \(u_r\) resource utilization, and \(H\) handover/setup/preemption burden.

1. **SLA and tail-risk objective**
   \[
   J_{\rm SLA}=
   \sum_p \omega_p(0.90-A_p)_+
   +\lambda\sum_p\operatorname{CVaR}_{0.95}
       \left(\frac{(T_c-D_p)_+}{D_p}\,\middle|\,p_c=p\right)
   +\eta E[H].
   \]
   Unfinished cases at the evaluation horizon must count as SLA failures where appropriate, not be dropped from the completed-case average.

2. **Robustness and fairness objective**
   \[
   J_{\rm RF}=
   \max_{u\in\{base,U1,\ldots,U5\}}
   \left(J_{\rm SLA}(u)+\kappa\,\widetilde B_u+\xi K_u\right)
   +\beta\sum_r(u_r-0.90)_+
   +\gamma\,\operatorname{Gini}(u_r),
   \]
   where \(\widetilde B_u\) is normalized backlog/unfinished work and \(K_u\) is emergency capacity used. A lexicographic implementation is also reasonable: protect avoidable P1 failures first, then minimize worst-case P2/P3 tail delay and backlog, then overtime, unfairness, and coordination burden.

Here, **robust** does not mean “always meets every SLA.” It means graceful degradation across all scenarios, early detection of infeasibility, no hidden starvation, no routine planned utilization above 90%, and explicit escalation when routing alone cannot stabilize the system.

# 3. Candidate policies

**Common transparent priority and safety rules**

- SLA urgency is based on remaining slack: deadline minus current time minus expected remaining elapsed work.
- P1 is served first, earliest deadline first. P2/P3 then use smallest slack, with P3 aging promotion so it cannot wait indefinitely.
- Resource choice, where pooling is allowed, minimizes predicted finish time including resource multiplier, current availability, setup, handover, and coordination. Resource identifier breaks ties.
- A P1 preemption is allowed only if no suitable free/reserved resource exists, P1 is predicted to breach otherwise, the interrupted case has not previously been preempted, and predicted P1 benefit exceeds \(0.10R\) plus switching costs. Preempting nearly completed work is prohibited.
- Validation cannot start until all diagnostic branches have joined and any parallel coordination delay has elapsed.

**Policy A — SPEC: strict diagnostic specialization with fixed queues**

- **Eligibility:** Mechanical uses only Ada/Ben/Deepa; Electrical uses only Chen/Deepa; Software uses only Chen/Emil. Ada does not overflow to Electrical, Emil does not overflow to Electrical, and Farah does not take diagnostic overflow. Intake and Validation use published fixed shift rosters so this policy is not given artificial stage coverage gaps.
- **Dispatch:** FIFO within priority class in each fixed queue; P1 goes to the head. No cross-queue stealing, even when another qualified resource is idle.
- **ME/ES:** branches are split into their specialist queues and treated as parallel-branch execution, with the 8-minute join coordination.
- **Handover/setup:** specialization should reduce diagnostic family setups, but fixed Intake  specialist  Validation routes can create frequent handovers.
- **Preemption:** permitted only on a resource already in the relevant home queue.
- **Overflow:** none. An absent home resource therefore translates directly into queue growth.
- **Operational virtue:** extremely easy to explain and useful as a baseline for measuring whether pooling actually earns its coordination cost.

**Policy B — POOL: full qualified pooling with sticky expected-completion dispatch**

- **Eligibility:** every on-shift qualified resource is eligible, subject to the skill matrix and breaks.
- **Priority score:** P1 first; then P2/P3 by smallest SLA slack; P3 cases older than 12 hours are promoted above P2 work with comfortable slack. FIFO breaks ties.
- **Resource score:** predicted finish time, explicitly including the 7-minute resource-change handover, 5-minute team move where applicable, 5-minute family setup, and the resource multiplier. Staying with the current resource often wins even when another resource is slightly faster.
- **ME/ES:** evaluate the best cross-skilled sequential route and best distinct-resource parallel route. Parallelize P1 work when it improves predicted completion; for P2/P3 require at least a 15-minute improvement after all overhead.
- **Reservation:** none. All capacity is available to the current highest-urgency task.
- **Overflow:** unnecessary because everything is already pooled.
- **Risk:** fastest cross-skilled resources can be monopolized, utilization can become unfair, and long non-P1 Intake/Validation activities can delay a newly arrived P1 because there is no protected lane.

**Policy C — HYBRID: home affinity, dynamic P1 reserve, and controlled overflow**

- **Normal eligibility:** use SPEC’s home queues to preserve affinity and reduce setups, but allow the overflow rules below. Intake and Validation are speed-aware pooled stages with case stickiness.
- **P1 reserve:** every 15 minutes, estimate P1 work by skill over the next 120 minutes using a high service quantile rather than only the mean. Reserve that work plus a 20–25% buffer on the fastest suitable resources, with a 20% floor and a 60% ceiling. Reserve Intake and Validation as well as diagnostics. The base expected P1 active work is roughly 353 base minutes; under U1/U5 it is roughly 586 minutes, before multipliers and overhead, so a fixed small morning reserve is insufficient.
- **Reserve use:** the reserve is virtual where possible. Lower-priority work may use it only if it can finish before the forecast P1 need or can safely be preempted. Otherwise it remains available. Unused reserve is visibly released when no P1 is at risk.
- **Overflow triggers:**
  - P1: immediately when the home route predicts an SLA breach and overflow improves completion after penalties.
  - P2: home wait over 45 minutes or predicted slack below 60 minutes.
  - P3: home wait over three hours and an overflow resource below 80% projected utilization, or P3 slack below two hours.
  - Workload balancing: move work when one qualified resource is projected above 85% and another below 70%, unless the slower resource would worsen urgent completion.
- **Parallelization:** P1 uses the critical-path test. P2/P3 default to sequential execution when system pressure exceeds 85%; parallel execution requires two comfortably loaded resources and at least a 15-minute net saving.
- **Fairness:** avoid nonurgent assignments that push projected block utilization above 85% when a reasonable qualified alternative exists; 90% is an emergency threshold, not a routine target.
- **Escalation:** overtime and external staffing are explicit capacity decisions, not hidden dispatch assumptions.

# 5. Robust recommendation

**Recommend HYBRID, but only as part of a routing-plus-capacity-escalation operating system.** Routing alone is not robust.

It offers the best trade-off under \(J_{\rm RF}\):

- Unlike SPEC, it can respond to U2’s skill-mix shock and U3’s absence.
- Unlike unrestricted POOL, it protects P1 from nonpreemptable work, limits resource churn, and makes utilization/fairness constraints explicit.
- It uses sequential execution for slack work when parallel coordination would consume scarce flexibility, while retaining parallel execution for P1 critical-path reduction.
- It recognizes that a diagnosis speed-up can simply move the queue to Validation and therefore reserves downstream capacity too.

It does **not** dominate on every metric. POOL may produce lower non-P1 delay in U2 if the hybrid reserve is unnecessarily retained. SPEC may be preferable in a future low-load environment where skill development and minimal setup matter more than resilience.

**Immediate staffing implications**

- Validate the central service-load result with observed active service times. If confirmed, 30-minute overtime allowances are not a base-case solution.
- The first coverage requirements are late-day Software/Electrical/Validation capacity and a Mechanical-qualified option after 18:00. Adding undifferentiated morning capacity would not fix these constraints.
- U3/U5 require prearranged backup for Chen’s skills and for Emil’s late Software role. The fairness-oriented aggregate capacity calculation is a lower bound, not a hiring recommendation.

**Fallback: SURGE mode**

Enter SURGE immediately on a declared absence/outage, or when any of the following occurs:

1. any skill’s forecast two-hour work/capacity pressure exceeds 1.0;
2. system or resource planned utilization exceeds 90% for two consecutive 15-minute reviews;
3. forecast P1 attainment falls below a 95% internal buffer, or any P1 has no feasible route within its deadline;
4. P2 work reaches six hours of age or P3 work reaches 20 hours;
5. Validation backlog grows for two consecutive blocks after a diagnostic burst.

SURGE actions are:

- open all qualified overflow and use reason-coded, fastest-safe routing;
- reserve P1 Intake, diagnostic, and Validation capacity;
- suspend non-P1 parallelization and setup-heavy balancing moves;
- invoke the limited overtime and, more importantly, call predetermined additional qualified capacity;
- apply P3 aging visibly rather than silently starving it;
- if capacity remains insufficient, declare an explicit degraded mode and report expected SLA breaches. Do not disguise this as a dispatch problem.

Return to normal HYBRID only after 60 minutes with no P1 at risk, all skill pressures below 85%, and no resource above 85% planned utilization. This hysteresis prevents oscillation.

# 6. Secondary effects and implementation risks

- **Gaming estimates:** dispatch based on planned/remaining service creates incentives to inflate estimates, avoid complex cases, or reclassify priority. Preserve original estimates, actual active time, complexity flags, and override reasons. Do not use planned-service adherence as an individual league table.
- **P3 starvation:** P1 reservation and smallest-slack dispatch can defer P3 indefinitely. Use aging promotion, an oldest-P3 alarm well before 24 hours, and reserve release when P1 is safe. Report unfinished backlog separately from completed-case delay.
- **Skill erosion:** strict homes can narrow experience, while indiscriminate pooling can prevent deliberate skill development. Use supervised rotations and measure performance by skill, not just resource.
- **Excessive preemption:** the restart penalty adds work and can create further setup/handover. “At most once” is not a sufficient control. Require a positive net-benefit test and track the interrupted case’s subsequent delay.
- **Coordination overhead:** parallel branches can improve elapsed P1 time while worsening total staff load and creating a Validation batch. Compare realized critical-path savings with the 8-minute coordination and extra handovers.
- **Validation bottleneck:** faster diagnostic clearing, parallelization, and surge intake all push work downstream. After 18:00, Validation is particularly dependent on Emil. A diagnostic-only utilization dashboard will miss this.
- **Fairness:** expected-completion dispatch naturally gives more work to faster resources. Count setups, handovers, preemption recovery, and overtime as work. Report both raw utilization and utilization conditional on feasible skills; equal utilization regardless of qualification is not necessarily fair or efficient.
- **Human interpretability:** every assignment should display the eligible set, selected resource, estimated finish, home/overflow status, reserve decision, and reason code. An opaque optimizer should not be the only explanation available to operators.
- **Resilience risks:** absence, outage, fatigue from repeated overtime, synchronized timestamps, and overreliance on one cross-skilled person can all invalidate nominal capacity.

# 7. Monitoring and process-mining design

**Deployment indicators**

Review at 15-minute intervals and aggregate by the supplied arrival blocks:

- arrivals, backlog, and oldest age by priority, case type, stage, and required skill;
- active work minus completed service, rather than case count alone;
- skill-specific effective capacity and forecast pressure;
- P1/P2/P3 attainment, at-risk cases, and service-only feasibility;
- mean, p90, and p95 arrival-to-completion time, with unfinished cases and censoring shown;
- queue waiting by stage, separate from active service and off-shift time;
- utilization, reserved-idle time, setup, handover, overtime, and utilization Gini by resource;
- home versus overflow assignments, reserve use/release, preemption count and restart penalty;
- ME/ES sequential/parallel fraction, coordination time, and realized critical-path benefit;
- Validation arrival rate and queue after diagnostic bursts;
- policy version and scenario/shock flag on every metric.

**Event attributes**

The interval event log should contain at least:

- `case:concept:name`, `concept:name`, `start_timestamp`, `time:timestamp`, `org:resource`;
- case type, priority, arrival timestamp, complexity flags, branch ID, and parallel/sequential mode;
- queue-entry timestamp, dependency-ready timestamp, assignment-decision timestamp, and assignment reason;
- the **eligible-resource set as it was at decision time**, selected resource, home/overflow status, and skill used;
- planned base service, resource multiplier, planned adjusted service, actual active service, and elapsed duration;
- pause/resume timestamps, interruption reason, remaining service at preemption, restart penalty, and preemption count;
- handover minutes, team-move minutes, setup minutes, and coordination minutes;
- policy version, scenario/shock flag, shift ID, and overtime flag;
- SLA clock start, deadline, completion/stop timestamp, and breach reason.

Queue and assignment decisions may be stored as separate decision events, but `SYSTEM` events should be filtered before resource handover analysis. Parallel branches require overlapping intervals; their active service must not be mistaken for elapsed critical-path time.

**PM4Py and complementary analyses**

- `format_dataframe` provides a consistent interval dataframe for subsequent process mining.
- Case-level service/waiting enrichment can summarize total case behavior, but its waiting output is **not** a stage-specific queue metric. Queue entry-to-start and dependency-ready-to-start measures should be calculated separately by stage and branch.
- Service-time analysis, stratified by activity, resource, scenario, complexity, and policy version, can reveal multiplier changes or long-tail drift.
- `discover_handover_of_work_network` can expose increasing dependence on Emil/Deepa, avoidable Mechanical  Electrical/Software transfers, and differences between home and overflow modes. Edge frequency should be paired with measured handover minutes.
- Performance DFGs and directly-follows comparisons can reveal rising waiting at Electrical, Software, or Validation and therefore bottleneck migration. Discovery alone does not establish capacity causality.
- Variant and conformance analysis can detect Validation before branch join, unexpected duplicate Intake, unrecorded preemption paths, or policy versions generating unauthorized routes.
- Drift comparisons should use matched time-of-day windows and case-mix adjustment; otherwise U1/U2 demand changes will be misclassified as resource performance drift.

def hm(text):
    h, m = map(int, text.split(":"))
    return 60*h + m

def available(resource, block, scenario):
    """Regular minutes in a block; overtime excluded. U5 outage is skill-specific."""
    if scenario in ("U3", "U5") and resource == "Chen":
        return 0.0
    shift_lo, shift_hi = map(hm, RES[resource]["shift"])
    lo = max(BLOCK_START[block], shift_lo)
    hi = min(BLOCK_START[block] + 120, shift_hi)
    ans = max(0, hi-lo)
    if RES[resource]["break"] is not None:
        b0, b1 = map(hm, RES[resource]["break"])
        ans -= max(0, min(hi,b1)-max(lo,b0))
    return float(ans)

def service_mean(activity, diagnostic_tail_multiplier=1.0):
    row = SERVICE.loc[activity]
    p = row.p_complex
    if activity in DIAG:
        p = min(1.0, p*diagnostic_tail_multiplier)
    ordinary = (row.o_lo + row.o_hi)/2
    complex_ = (row.c_lo + row.c_hi)/2
    return (1-p)*ordinary + p*complex_

def scenario_demand(scenario):
    d = DEMAND.copy()
    tail_mult = 2.0 if scenario == "U4" else 1.0
    if scenario in ("U1", "U5"):
        d.loc[[0,1], "expected_arrivals"] *= 1.7
        d.loc[[0,1], "P1_pct"] += 8
        d.loc[[0,1], "P2_pct"] -= 8       # A9; P3 unchanged
    if scenario == "U2":                  # A8: fixed N, doubled type weights
        type_cols = ["M_pct","E_pct","S_pct","ME_pct","ES_pct"]
        for b in (2,3):
            w = d.loc[b, type_cols].astype(float).copy()
            w["E_pct"] *= 2
            w["ES_pct"] *= 2
            d.loc[b, type_cols] = 100*w/w.sum()
    return d, tail_mult

def offered_work(scenario):
    d, tail_mult = scenario_demand(scenario)
    rows = []
    for b, row in d.iterrows():
        n = row.expected_arrivals
        branch_fraction = {
            "Intake": 1.0,
            "Validation": 1.0,
            "Mechanical": (row.M_pct + row.ME_pct)/100,
            "Electrical": (row.E_pct + row.ME_pct + row.ES_pct)/100,
            "Software": (row.S_pct + row.ES_pct)/100,
        }
        for skill in SKILLS:
            work = n*branch_fraction[skill]*service_mean(skill, tail_mult)
            rows.append({"block":b, "skill":skill, "work":work,
                         "p1_work":work*row.P1_pct/100})
    return pd.DataFrame(rows)

def eligible(policy, skill):
    ans = [r for r in RES if skill in RES[r]["skills"]]
    if policy == "SPEC" and skill in HOME:
        ans = [r for r in ans if r in HOME[skill]]
    return ans
