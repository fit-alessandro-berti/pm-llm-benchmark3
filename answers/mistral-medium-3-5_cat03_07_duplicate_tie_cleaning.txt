## **1. Duplicate-handling decision tree**

```mermaid
graph TD
    A[Start] --> B{Exact technical duplicate?<br>(same eid, source, timestamp, payload_hash)}
    B -->|Yes| C[Drop one, retain provenance]
    B -->|No| D{Same physical event?<br>(reconciliation report, payload_hash variants)}
    D -->|Yes| E[Merge attributes/relations, retain both with qualifiers]
    D -->|No| F{Summary event derived from detailed event?<br>(e.g., ERP status from WMS transaction)}
    F -->|Yes| G[Retain both with refined labels<br>(e.g., "Pack Package (Detailed)" vs. "Pack Package (Summary)")]
    F -->|No| H{Harmonization collision?<br>(same activity label, distinct semantics)}
    H -->|Yes| I[Retain both with disambiguated labels<br>(e.g., "Dispatch (Warehouse)" vs. "Dispatch (Carrier)")]
    H -->|No| J{Concurrent same-label events<br>with different objects?<br>(e.g., e03/e05: Pick Item for I1 vs. I2)}
    J -->|Yes| K[Retain both unchanged]
    J -->|No| L[Unresolved candidate]
    L --> M[Quarantine for review]
```

**Terminal Decisions:**
- **Exact technical duplicate**: Drop one, retain provenance (e.g., ingestion artifacts).
- **Same physical event**: Merge attributes/relations (e.g., e03/e04), retain both with qualifiers if payloads differ.
- **Summary event**: Retain both with refined labels (e.g., e06/e07).
- **Harmonization collision**: Retain both with disambiguated labels (e.g., e08/e09).
- **Concurrent distinct events**: Retain both unchanged (e.g., e03/e05, e13/e14).
- **Unresolved**: Quarantine (e.g., ambiguous e09/e10 if no domain constraints).

## **3. Timestamp-tie ordering rules**

### **Policy Hierarchy (Semantic  Deterministic)**
1. **Domain constraints** (semantic):
   - `e12  e13` (Authorize  Capture for M1).
   - `e09  e10` (Carrier accept  handover).
2. **Within-source sequence** (semantic):
   - Use `source_seq` for events from the same system (e.g., e03 before e06 in WMS).
3. **Lifecycle constraints on shared objects** (semantic):
   - `Pick Item (I1)` (e03/e04)  `Pick Item (I2)` (e05)  `Pack Package` (e06/e07).
4. **Source-specific semantics** (semantic):
   - WMS `Dispatch` (e08)  CARRIER `Dispatch` (e09) (warehouse release  carrier accept).
5. **Ingestion time** (deterministic fallback):
   - Only if all else fails (e.g., e11 vs. e16: ERP ingested before BILLING).
6. **Stable fallback order** (deterministic):
   - Lexicographic sort on `source_event_key` (e.g., `ER-100` < `S-901`).

**Why not microseconds?**
Adding synthetic microseconds (e.g., `10:00:00.001`) implies a false precision. The original timestamps are second-level, and introducing sub-second offsets may encode a narrative (e.g., e03 before e04) that lacks evidence.

### **Intended Orders**
- **e03–e07 (10:00:00)**:
  - `e03` (WMS Pick I1)  `e04` (SCANNER Pick I1)  `e05` (SCANNER Pick I2)  `e06` (WMS Pack)  `e07` (ERP Pack).
  - *Rationale*: WMS `source_seq` (100  110) and lifecycle (pick  pack). e04/e03 are merged but ordered by `source_seq` (WMS:100 < SCANNER:551? No—use ingestion time as fallback: e03 ingested at 10:00:01 < e04 at 10:00:03).

- **e08–e10 (10:15:00)**:
  - `e08` (WMS Dispatch)  `e09` (CARRIER Dispatch)  `e10` (Handover).
  - *Rationale*: Domain rule (e09  e10) and WMS `source_seq` (120) < CARRIER (1).

- **e11–e16 (12:00:00)**:
  - `e11` (ERP Invoice)  `e16` (BILLING Invoice)  `e12` (Authorize)  `e13` (Capture M1)  `e14` (Capture M2)  `e15` (ERP Summary).
  - *Rationale*: Domain rule (e12  e13), ingestion time (e11:12:00:01 < e16:12:00:04), and M1/M2 independence.

## **4. Conservative cleaning pipeline**

**Steps:**
1. **Identify exact duplicates**: None in the sample (all `eid` are unique).
2. **Merge verified same-physical events**:
   - e03/e04: Merge attributes (WMS location + SCANNER metadata), retain both with qualifiers (`activity: "Pick Item (WMS)"`, `"Pick Item (SCANNER)"`).
   - e11/e16: Merge attributes (ERP tax + BILLING line items), retain both with qualifiers.
3. **Disambiguate harmonization collisions**:
   - e08/e09: Rename to `"Dispatch (WMS)"` and `"Dispatch (Carrier)"`.
   - e06/e07: Rename to `"Pack Package (Detailed)"` and `"Pack Package (Summary)"`.
4. **Retain concurrent distinct events**:
   - e03/e05, e13/e14, e14/e15: No changes.
5. **Order ties**:
   - Apply the hierarchy in Section 3 (domain  source_seq  ingestion).
6. **Preserve provenance**:
   - Add columns: `original_activity`, `original_timestamp`, `merge_rule`, `source_event_keys`.

**Expected Retained Event Count**: **17** (all events retained, with refined labels/attributes for 6 pairs).

## **5. Aggressive alternatives**

### **Scenario A: Evidence-based semantic merging**
- **Actions**:
  - Merge e03/e04 into **one event** (WMS attributes take precedence).
  - Merge e06/e07 into **one event** (WMS details + ERP summary).
  - Merge e08/e09 into **one event** (label: `"Dispatch"`).
  - Merge e11/e16 into **one event** (ERP attributes take precedence).
  - Drop e15 (redundant with e13/e14).
- **Retained Count**: **12**.
- **Semantic Damage**:
  - Loses SCANNER metadata (e04).
  - Loses ERP summary abstraction (e07, e15).
  - False unification of WMS/CARRIER dispatch (e08/e09).

### **Scenario B: Mechanically aggressive PM4Py merging**
- **Actions**:
  - Use `pm4py.ocel_merge_duplicates` with `activity` + `timestamp` + `objects` as keys.
  - Merge e03/e04/e05 (same activity/timestamp/objects? No—e05 has I2, so only e03/e04 merged).
  - Merge e06/e07 (same objects? No—e06 has I1/I2, e07 has O1/P1  **not merged**).
  - Merge e08/e09/e10 (same activity/objects  **all merged**).
  - Merge e11/e16 (same objects  **merged**).
  - Merge e12/e13/e14/e15 (same activity/objects? No—e14 has M2, e15 has no Payment  **e12/e13 merged, e14/e15 retained**).
- **Retained Count**: **13**.
- **Semantic Damage**:
  - **e08/e09/e10 merged**: Loses carrier workflow (accept  handover).
  - **e13/e14 not merged**: Correct (M1 vs. M2), but `have_common_object=True` (O1, V1) would **incorrectly merge them** if not filtered by `Payment` object.
  - False rework in DFG if abstraction levels are collapsed.

**Why `have_common_object=True` fails for e13/e14**:
- Both share `O1` and `V1`, but represent **different Payment objects (M1 vs. M2)**. A naive merge would combine them, losing the distinction between partial payments.

import pm4py
from copy import deepcopy
import pandas as pd

# Helper: Custom merge for verified pairs (e.g., e03/e04)
def custom_merge_verified_pairs(ocel, pairs):
    ocel = deepcopy(ocel)
    events = ocel.events
    for (eid1, eid2) in pairs:
        row1 = events[events['eid'] == eid1].iloc[0]
        row2 = events[events['eid'] == eid2].iloc[0]
        # Merge attributes (example: concatenate payload_hash)
        merged_attrs = {
            'activity': f"{row1['activity']} ({row1['source']})",
            'payload_hash': f"{row1['payload_hash']}|{row2['payload_hash']}",
            'source': f"{row1['source']},{row2['source']}",
            'source_event_key': f"{row1['source_event_key']},{row2['source_event_key']}",
            'merge_rule': 'verified_same_physical_event'
        }
        # Create new merged event
        new_eid = f"merged_{eid1}_{eid2}"
        new_row = row1.copy()
        new_row['eid'] = new_eid
        for k, v in merged_attrs.items():
            new_row[k] = v
        # Add to events, drop originals
        events = pd.concat([events, pd.DataFrame([new_row])], ignore_index=True)
        events = events[~events['eid'].isin([eid1, eid2])]
        ocel.events = events
        # Update OCEL relations (simplified; actual implementation needs to handle E2O)
        # ...
    return ocel

# Load raw OCEL (assumed to exist)
ocel_raw = ...  # pm4py.read_ocel("raw_ocel.jsonocel")

# --- Conservative Pipeline ---
ocel_conservative = deepcopy(ocel_raw)
# Step 1: Refine labels for harmonization collisions
ocel_conservative.events.loc[ocel_conservative.events['eid'] == 'e09', 'activity'] = "Dispatch (Carrier)"
ocel_conservative.events.loc[ocel_conservative.events['eid'] == 'e08', 'activity'] = "Dispatch (WMS)"
ocel_conservative.events.loc[ocel_conservative.events['eid'] == 'e07', 'activity'] = "Pack Package (Summary)"
ocel_conservative.events.loc[ocel_conservative.events['eid'] == 'e06', 'activity'] = "Pack Package (Detailed)"

# Step 2: Add provenance columns
ocel_conservative.events['original_activity'] = ocel_conservative.events['activity']
ocel_conservative.events['original_timestamp'] = ocel_conservative.events['timestamp']

# Step 3: Order ties using domain rules + source_seq + ingestion
# Create a temporary column for ordering
ocel_conservative.events['order_key'] = (
    ocel_conservative.events['timestamp'].astype(str) + "_" +
    ocel_conservative.events['source_seq'].astype(str) + "_" +
    ocel_conservative.events['ingested_at'].astype(str)

ocel_conservative = pm4py.ocel_sort_by_additional_column(ocel_conservative, 'order_key')
ocel_conservative.events = ocel_conservative.events.drop(columns=['order_key'])

# Step 4: Validate referential integrity (simplified)
assert len(ocel_conservative.events) == 17  # No drops in conservative

# Drop e07, e09, e15 (redundant)
ocel_aggressive_a.events = ocel_aggressive_a.events[~ocel_aggressive_a.events['eid'].isin(['e07', 'e09', 'e15'])]

ocel_aggressive_a = pm4py.ocel_sort_by_additional_column(ocel_aggressive_a, 'ingested_at')  # Fallback

## **8. Audit trail and reversibility**

**Provenance Schema (SQL-like):**
```sql
CREATE TABLE event_provenance (
    canonical_eid TEXT PRIMARY KEY,
    source_eids TEXT[],  -- Array of original eids
    merge_rule TEXT,     -- e.g., "verified_same_physical", "harmonization_collision"
    reviewer TEXT,        -- e.g., "analyst_001" or "rule_v1.2"
    original_activity TEXT,
    refined_activity TEXT,
    original_timestamp TIMESTAMPTZ,
    adjusted_timestamp TIMESTAMPTZ,  -- If reordered
    attributes_retained JSONB,       -- {source: {key: value}}
    discarded_conflicts JSONB,       -- {key: [value1, value2]}
    confidence TEXT,      -- "high", "medium", "low"
    reason TEXT
);
```

**Reconstruction Process:**
1. **Reverse merges**: For each `canonical_eid`, split into `source_eids` using `merge_rule`.
2. **Restore original labels**: Use `original_activity` and `original_timestamp`.
3. **Reattach attributes**: Distribute `attributes_retained` back to source events.
4. **Reintroduce dropped events**: If `merge_rule = "drop"`, reinsert from quarantine.

## **9. Failure modes and safeguards**

| **Failure Mode**                          | **Safeguard**                                                                 |
|-------------------------------------------|-------------------------------------------------------------------------------|
| Collapsing distinct partial payments (e13/e14) | Filter by `Payment` object (M1 vs. M2) before merging.                     |
| Converting abstraction levels into rework (e06/e07) | Retain both with refined labels; never merge summary/detailed events.       |
| Ordering by ingestion time                | Use ingestion time **only as a fallback** after semantic rules.             |
| Treating shared objects as proof of duplication | Require **additional keys** (e.g., `Payment` object) for merging.            |
| Unioning incompatible E2O relations       | Validate that merged events share **all** objects (not just some).          |
| Changing durations via synthetic microseconds | **Never** add microseconds before establishing semantic order.              |
| Losing source-authoritative attributes    | Preserve all attributes in `attributes_retained`; flag conflicts.          |
| Applying duplicate functions globally     | **Pre-filter** candidate groups (e.g., same activity + timestamp + objects). |
| False causal dependencies (e08e09)      | Use domain rules (e.g., WMS dispatch must precede carrier accept).           |
| Dropping e05 or e14                       | Explicitly exclude them from any merge/drop logic.                          |
| Misinterpreting harmonized labels         | Disambiguate labels (e.g., "Dispatch (WMS)") and document mappings.         |

This pipeline balances **conservatism** (preserving all events with refined labels) and **aggressive merging** (with explicit warnings about semantic risks). The PM4Py implementation demonstrates how to apply these rules while maintaining reversibility. The sensitivity analysis highlights how each cleaning choice affects process mining metrics.
