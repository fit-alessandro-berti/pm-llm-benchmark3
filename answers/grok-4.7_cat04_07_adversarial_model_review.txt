# 1. Review Scope and Assumptions

This review is a governance decision about which language, if any, may drive exploration, conformance enforcement, simulation, and stakeholder communication. The reported scores are unreproducible claims from one 80/20 case split. They are evidence about the submissions, and they are not a ranking.

Four uses, with different failure costs:

- **Exploration.** The model is a hypothesis about observed behavior. Extra legal combinations are acceptable. Traces that skip a mandatory control or reorder a stated precedence are a modeling error. Fitness may sit above precision. Precision is still required to the extent that it marks illegal skips.
- **Conformance enforcement.** A release is allowed only when every hard rule holds. Missing attributes produce an inconclusive verdict, which must not be stored as a pass. False accepts (Model S) are compliance failures. False rejects of policy-legal combinations (Model C) push operations around the control. Fitness and precision are both necessary and still not sufficient. A single forbidden trace in the language disqualifies enforcement use, whatever the aggregate fitness.
- **Simulation.** The language is a generator. Model S would simulate skipped checks and early expedites and would bias cycle time and control counts. Model C would under-generate auto-approval, supplier-plus-expedite, and partial rechecks. A loop needs an explicit iteration cap before any simulation run.
- **Communication.** The picture must be one a process owner can challenge. Fluency is a risk when the fluent picture is unsound. Comprehension testing has to score correct accept/reject judgments on probes, not a 1–5 ease rating.

Assumptions used throughout:

- “Accepts” means the trace is in the process-tree language: a firing with only silent moves and synchronous visible moves. Alignment fitness above zero is a different claim. Under usual PM4Py defaults, a silent model move costs 0, so optional `tau` paths fit absences for free.
- PM4Py operators have their usual meaning: `->` sequence, `+` interleaved parallel, `X` exclusive choice, `*` loop with `*(do, redo)` = do, then zero or more times (redo then do), `tau` a silent step. `X` and `+` are n-ary.
- P1–P7 are the policy. Model C’s eight variants are a sample of frequent behavior, not a definition of the remaining legal product space.
- **Working assumption A-order.** When Supplier Review occurs, it sits in the review block after the initial Credit Check and Technical Review pair, in either order relative to Expedite Review. The written policy does not say this. It is taken from P4 plus every supplier trace the probes and Model C actually show. Interleaving Supplier Review between the two mandatory checks is rejected pending a process-owner ruling.
- **Working assumption A-approval.** Manager Approval and Auto Approval are orthogonal to the review pattern. P5 requires exactly one of them and states no further precondition. If auto-approval is in fact illegal after expedite, supplier review, or correction, that rule is not in the agreed policy and is not encoded here.
- **Working assumption A-recheck.** Each correction is followed by a non-empty recheck of Credit Check, Technical Review, or both. Supplier-only recheck is outside the language until the owner classifies Supplier Review as a correctable check.
- The external/internal attribute and the affected-check attribute are absent. Their absence is reported as inconclusive. It is not encoded by turning Credit Check or Technical Review into skips.
- No new fitness, precision, generalization, simplicity, or runtime numbers are claimed for the third model.

# 2. Metric Interpretation

These measures use incommensurable units (fitness, a precision ratio, a token-replay score, an arc-degree score, seconds, an undocumented count, and an informal Likert score). Averaging them would require weights and a normalization that nobody has justified, and a high aggregate would still hide a mandatory-check skip. The scores stay disaggregated.

Precision was reported only on the training log. The table is therefore not a paired train/holdout conformance profile. Neither team published seeds, the PM4Py version, preprocessing, alignment costs, or the held-out case ids.

# 3. Adversarial Review of Model S

**Strongest case for Model S.** The tree is the right kind of abstraction that Model C never reached. Register Dossier is first and Release Order is last. Credit Check and Technical Review are unordered, so both orders fit. Supplier Review and Expedite Review can appear in either order. Exactly one approval is an `X`, so the model cannot emit both approvals or neither. The net is small, alignments are cheap, business readers can parse it (claimed 4.4), and holdout event mass still fits (claimed 0.981). As a laboratory upper bound on “which activities co-occur between registration and approval,” it is a useful baseline that a tighter model must beat. The discovery slogan “robust to missing events” is a real data-quality concern for Supplier Review (F4), and a silent branch is one way to keep a missing supplier event from dominating fitness.

**Strongest case against Model S.** The same operator was applied to mandatory and optional work. Inside one parallel block, each of Credit Check, Technical Review, Supplier Review, and Expedite Review is `X(activity, tau)`. That is not a calibrated noise model. It changes the control language:

- any subset of the four activities may occur, including the empty subset;
- any order is legal, so Expedite Review can finish before either mandatory check;
- each activity occurs at most once, so a legal recheck is inexpressible;
- Correct Dossier does not occur at all.

Noise tolerance that respected the policy would keep both mandatory checks mandatory, attach `tau` only to Expedite Review and, as an explicitly inconclusive encoding, to Supplier Review, and would charge log moves for garbage events at alignment time. Model S does the opposite: absences of mandatory checks are free model moves, while Correct Dossier and every repeated check are impossible. The slogan does not match the asymmetry. F7 (low precision is fine for exploration) fails because the extra language contains forbidden traces, not only unobserved legal ones. F1 is correct, and the high fitness does not answer it. Fitness is blind to behavior the model adds. Optionalizing a check that the log usually contains does not even lower fitness; it lowers precision, and positive-log precision still does not name the forbidden traces.

**Undesirable or policy-ambiguous traces in the language of S.** Each activity below occurs at most once, approvals are exclusive, and there is no Correct Dossier. Membership is under standard process-tree semantics and is not uncertain for these traces.

1. `Register Dossier, Manager Approval, Release Order` — B3, forbidden. Both mandatory checks take `tau`.
2. `Register Dossier, Credit Check, Auto Approval, Release Order` — Technical Review skipped. Forbidden by P2.
3. `Register Dossier, Technical Review, Manager Approval, Release Order` — Credit Check skipped. Forbidden by P2.
4. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` — B4, forbidden. Expedite precedes both checks because the four activities are one parallel block.
5. `Register Dossier, Expedite Review, Supplier Review, Auto Approval, Release Order` — both reviews, neither mandatory check.
6. `Register Dossier, Supplier Review, Credit Check, Expedite Review, Technical Review, Manager Approval, Release Order` — Expedite Review fires before Technical Review has occurred.
7. `Register Dossier, Credit Check, Technical Review, Supplier Review, Manager Approval, Release Order` — B7. Legal when the order is external. Policy-ambiguous when sourcing is unknown. S accepts it for the same mechanical reason it accepts trace 1, so acceptance is not evidence that P3 was modeled.

**Accidental exclusions, not virtues.** S also rejects `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order` (B6) and `Register Dossier, Credit Check, Technical Review, Credit Check, Manager Approval, Release Order` (B8). B8 is a desirable reject. It is an accident of “no activity can repeat,” which is the same gap that rejects the legal partial recheck in B6. P7 is not represented.

# 4. Adversarial Review of Model C

**Strongest case for Model C.** Every complete trace in the language starts with Register Dossier, contains both mandatory checks before approval, contains exactly one approval, and ends with Release Order. B3 and B4 are outside the language. An auditor can read the eight sequences without understanding operators. Training-log precision of 0.941 and the explicit correction variant show an attempt to stick to behavior the organization has actually seen. F8 is a coherent audit posture if, and only if, the organization has adopted a closed variant catalog. On that posture, an unseen combination is a finding, not a model bug. Duplicate full paths make each approved script locally obvious.

**Strongest case against Model C.** The expression is a sample of variants, not a process. Under the no-correction slice implied by P2, P4, and P5 (two check orders, five supplier/expedite patterns `{none, SR, ER, SR→ER, ER→SR}`, two approvals) there are 20 traces. Model C contains 7 of them, plus one frozen correction script:

| In Model C | Outside Model C, inside that 20 |
|---|---|
| CC→TR→MA; TR→CC→MA; CC→TR→SR→MA; TR→CC→SR→MA; CC→TR→ER→MA; CC→TR→SR→ER→MA; CC→TR→AA | Every auto-approval except CC→TR→AA (7 traces). Every ER-before-SR trace. TR→CC with ER. TR→CC with SR→ER. |

That count is conditional on A-order. It is already enough to show that “mirrors frequent variants” and “audit-ready” are different claims.

Concrete consequences:

- **Branch enumeration.** Adding ER-before-SR, or auto-approval on the supplier path, means copying whole sequences. The edit is multiplicative. This is the maintainability failure in F2.
- **Duplicate labels.** The same logical activity is a different transition on each branch (on the order of several dozen labeled leaves; the reported count of 33 is unauditable). Impact analysis and ownership (F3) attach to the activity, while the net scatters it. Alignments become ambiguous across copies, which inflates runtime and can move fitness and precision.
- **Unseen combinations.** B2 is valid under P2 and P5 and is one label away from branch 2 (`Manager Approval` versus `Auto Approval`) and one order away from branch 8. It is still a non-fit. B5, the natural external urgent case, is a non-fit. Holdout fitness 0.744 is the empirical signature, and F4 names the recombinations involved.
- **Correction handling.** The only correction trace is `Register Dossier, Credit Check, Technical Review, Correct Dossier, Credit Check, Technical Review, Manager Approval, Release Order`. A single affected check (F6, B6), a reversed recheck order, a second correction, a correction combined with supplier or expedite, and a correction followed by auto-approval are all outside the language. The model does not show the decision “which check is affected.”
- **Holdout degradation.** Training fitness is already 0.973, so C is not a complete model of its own training log, yet training precision is 0.941. That pattern is precision by amputation: delete infrequent behavior, look precise on what remains, then lose the holdout when the infrequent behavior shifts. F8 calls the loss a control. P2–P5 authorize many of the deleted combinations, so “unseen” and “noncompliant” are not the same set.
- **High precision as memorization.** With eight exact scripts, precision against the log that produced those scripts is the expected artifact. It was not measured on holdout, and it was not measured on forbidden traces. C’s rejection of B3 and B4 is real and valuable. C’s precision number does not prove that property; the language does.

# 6. Likely Metric Pathologies

Ranked by likely impact on a wrong go-live decision.

1. **Fitness rewarded by optionalizing mandatory behavior.** Alignment fitness asks whether the log plays on the model. It does not ask what else the model plays. `X('Credit Check', tau)` makes a missing credit check a cost-0 model move under usual defaults, so violations of P2 are invisible to fitness whenever they occur, and harmless to fitness whenever they do not. Claimed training fitness 0.992 can coexist with an unsound language. This is the most decision-relevant pathology because it makes S look deployment-ready.

2. **Positive-log-only precision.** F5 is correct. Precision was computed from observed positive traces. It does not score B3, B4, or B8. A model can be precise on what people usually do and still contain a forbidden path. Conversely, deleting legal rare paths raises precision. The two errors are indistinguishable in the published numbers.

3. **Precision by memorization, seen as holdout collapse.** C’s training precision 0.941 beside holdout fitness 0.744 is the classic signature of a variant catalog. Section 4’s 7-of-20 count shows how much agreed behavior was never given a branch. Selecting C for audit use because it is “precise” institutionalizes F2.

4. **Generalization rewarded by excessive permissiveness.** Token-based generalization of 0.907 on S is what the measure does on a small tree whose nodes are traversed by almost every case, including a tree that optionalizes mandatory checks. C’s 0.412 records starved branches. Using the larger number to bless S double-counts permissiveness already visible in the language.

5. **Missing-event bias.** F4 says some Supplier Review events may be missing, and the sourcing attribute was not logged. S explains every missing supplier event for free, and also explains missing credit checks for free. C explains a missing supplier event only when another full branch matches, which silently reclassifies a broken external case as a clean internal case. Neither number separates “internal,” “external and compliant,” and “external with a dropped event.”

6. **Split sensitivity and possible leakage.** One 80/20 split, no seed, no case list, no preprocessing. The C gap (0.973 to 0.744) could move a lot under another split. If frequent variants were mined on the full log and then scored on holdout, the holdout number is leaked and still poor. If they were mined on training only, the gap is an honest warning. These two stories support different governance tones, and the submissions do not distinguish them.

7. **Duplicated-label effects.** C’s copied labels make the synchronous product larger and alignments ambiguous across transitions that business users see as one activity. Fitness and precision then depend on which copy the search returns. The undocumented count of 33, against a leaf surplus of 39 under the obvious definition, means the board does not know what was measured. IT impact analysis (F3) is a property of this structure.

8. **Alignment-cost sensitivity.** Costs were not published. With silent cost 0 and visible model-move cost 1, S’s skips are free and a wrong approval label is expensive. Raising the silent cost, or using a non-unit log-move cost, would move S’s fitness and could reorder S and C on the cases that omit middle activities. Published fitness is conditional on an unknown cost vector.

9. **Silent-transition effects, distinct from the cost default.** The taus in S are not annotations. They are alternative firings, so they change the language, the precision denominator, and play-out. C has no taus and therefore no silent explanation of a partial trace; every deviation is a visible move or a different branch. Comparing fitness across that structural difference without a cost report confuses “fits the log” with “has a skip transition.”

10. **Average fitness hides rare severe violations.** The published figures behave like mean alignment fitness, not like the percentage of perfectly fitting traces. A handful of skipped credit checks, or a handful of correction cases S cannot express, can hide inside 0.992 if the rest of the event mass synchronizes. Enforcement needs both the mean and the perfect-trace rate, plus the list of deviant case ids.

11. **Stakeholder-score methodology.** An informal 1–5 with no instrument, no sample size, and no accuracy check measures fluency. S’s 4.4 is expected and is the mechanism by which an unsound model becomes the local process picture. It should not be plotted on the same axis as fitness.

12. **Runtime confounded by model size.** The median gap (0.018 s versus 0.440 s) tracks the size of the synchronous product and the duplicate-label branching factor. It is a capacity constraint for interactive checking of large volumes. It is not independent evidence of conformance quality, and the median does not describe the slowest cases.

13. **Simplicity confounded by enumeration.** Arc-degree simplicity falls when a catalog is copied into the net. The drop from 0.918 to 0.281 restates “C is a large tree.” It does not choose a semantics.

# 7. Third Alternative

Strategy: a block-structured procedural backbone that encodes only the hard control rules, plus external checks for the two missing attributes. Supplier Review is optional in the net because the log cannot tell external from internal. That optionality is an explicit ignorance encoding, paired with a verdict that stays inconclusive. Credit Check and Technical Review are never given a `tau`.

**1. Formal description.**

```text
Register
· perm(Credit Check, Technical Review)
· ( A · ( B · A )* )
· (Manager Approval ⊕ Auto Approval)
· Release Order
```

- `perm` is either order of both activities.
- `A` is one of: ε, `Supplier Review`, `Expedite Review`, `Supplier Review · Expedite Review`, `Expedite Review · Supplier Review`.
- `B` is `Correct Dossier` followed by one of: `Credit Check`, `Technical Review`, `perm(Credit Check, Technical Review)`.
- The loop is the process-tree loop `*(A, B)`: one `A`, then zero or more times (`B` then `A`). Each later `A` may be empty, so a correction does not force a second visible supplier or expedite event.
- There is no `tau` on either mandatory check, on either approval, on Register Dossier, on Release Order, or on the recheck menu.

**2. PM4Py object.**

```python
import pm4py

model_third_string = """
->(
  'Register Dossier',
  +( 'Credit Check', 'Technical Review' ),
  *(
    +(
      X( 'Supplier Review', tau ),
      X( 'Expedite Review', tau )
    ),
    ->(
      'Correct Dossier',
      X(
        'Credit Check',
        'Technical Review',
        +( 'Credit Check', 'Technical Review' )
      )
    )
  ),
  X( 'Manager Approval', 'Auto Approval' ),
  'Release Order'
)
"""

model_third = pm4py.parse_process_tree(model_third_string)
```

The loop’s do-child is the optional review block. The redo-child is correction plus a non-empty recheck. Duplicate labels are confined to that menu: Credit Check and Technical Review each occur as three leaves (initial pair, single-check recheck, both-check recheck). Every other label occurs once. Surplus label occurrences are 4, against several dozen in Model C. The duplicates are the same business activity; ownership stays on the label, with the recheck copies documented as one capability.

**3. External checks.** These are required. A control-flow fit is not a compliance pass.

```python
CREDIT = "Credit Check"
TECH = "Technical Review"
SUPPLIER = "Supplier Review"
EXPEDITE = "Expedite Review"
CORRECT = "Correct Dossier"
MANAGER = "Manager Approval"
AUTO = "Auto Approval"
MANDATORY = (CREDIT, TECH)
APPROVALS = (MANAGER, AUTO)

def _parse_A(seq, i):
    """Consume one review block. Returns (next_index, activities) or None."""
    seen = []
    while i < len(seq) and seq[i] in (SUPPLIER, EXPEDITE):
        if seq[i] in seen:
            return None
        seen.append(seq[i])
        i += 1
    return i, seen

def _parse_R(seq, i):
    """Non-empty recheck of {Credit, Technical}. Returns (next_index, set) or None."""
    if i >= len(seq):
        return None
    if seq[i] == CREDIT and i + 1 < len(seq) and seq[i + 1] == TECH:
        return i + 2, {CREDIT, TECH}
    if seq[i] == TECH and i + 1 < len(seq) and seq[i + 1] == CREDIT:
        return i + 2, {CREDIT, TECH}
    if seq[i] == CREDIT:
        return i + 1, {CREDIT}
    if seq[i] == TECH:
        return i + 1, {TECH}
    return None

def control_flow_accepts(trace):
    """Specification of the language. Confirm against model_third by play-out and alignments."""
    if len(trace) < 4 or trace[0] != "Register Dossier" or trace[-1] != "Release Order":
        return False
    body = trace[1:-1]
    if body[-1] not in APPROVALS:
        return False
    if any(a in APPROVALS for a in body[:-1]):
        return False
    mid = body[:-1]
    if len(mid) < 2 or set(mid[:2]) != set(MANDATORY):
        return False
    i, seq = 2, mid
    while True:
        parsed = _parse_A(seq, i)
        if parsed is None:
            return False
        i, _ = parsed
        if i == len(seq):
            return True
        if seq[i] != CORRECT:
            return False
        rec = _parse_R(seq, i + 1)
        if rec is None:
            return False
        i = rec[0]

def policy_verdict(trace, attributes=None):
    """
    attributes:
      sourcing: 'external' | 'internal' | None
      affected_checks: None, or a list of iterables, one per Correct Dossier,
                       each drawn from {Credit Check, Technical Review}
    overall is FAIL, CONDITIONAL, or PASS.
    PASS is unreachable while sourcing is missing.
    """
    attributes = attributes or {}
    cf = control_flow_accepts(trace)
    sourcing = attributes.get("sourcing")
    if sourcing == "external":
        p3 = "PASS" if SUPPLIER in trace else "FAIL"
    elif sourcing == "internal":
        p3 = "PASS"  # P3 imposes no prohibition on internal supplier review
    else:
        p3 = "INCONCLUSIVE"

    corrections = [i for i, a in enumerate(trace) if a == CORRECT]
    affected = attributes.get("affected_checks")
    if not corrections:
        p6 = "PASS"
    elif affected is None or len(affected) != len(corrections):
        p6 = "CONDITIONAL"
    else:
        p6 = "PASS"
        for n, start in enumerate(corrections):
            rec = _parse_R(trace, start + 1)
            if rec is None or set(affected[n]) != rec[1]:
                p6 = "FAIL"
                break

    p7 = "PASS"
    for activity in MANDATORY:
        positions = [i for i, a in enumerate(trace) if a == activity]
        for earlier, later in zip(positions, positions[1:]):
            if CORRECT not in trace[earlier + 1:later]:
                p7 = "FAIL"

    if (not cf) or p3 == "FAIL" or p6 == "FAIL" or p7 == "FAIL":
        overall = "FAIL"
    elif p3 == "INCONCLUSIVE" or p6 == "CONDITIONAL":
        overall = "CONDITIONAL"
    else:
        overall = "PASS"
    return {"control_flow": cf, "p3": p3, "p6": p6, "p7": p7, "overall": overall}
```

**4. Semantics encoded.**

- **Mandatory checks.** The initial parallel block requires both Credit Check and Technical Review, in either order, before the review loop, before either approval, and before release. They have no silent alternative.
- **Supplier Review.** Optional in the net (`X` with `tau`), only inside `A`, so after the initial pair and in either order with Expedite Review. Policy status is not “optional in the business.” External orders require it and internal orders do not, and the attribute is absent, so `p3` is `INCONCLUSIVE` on every current case. A missing supplier event must not be read as a passed external control.
- **Expedite Review.** Genuinely optional (P4). It can only fire inside `A`, therefore after both initial mandatory checks, before approval, and in either order with Supplier Review. A later correction can be followed by another `A`, so expedite may also occur after a recheck. Expedite before the initial pair is outside the language.
- **Exactly one approval.** The final `X` emits one of the two approvals, after the loop, immediately before Release Order. Zero approvals, both approvals, and an approval before the checks are outside the language.
- **Correction and recheck.** Correct Dossier may occur any number of times, each time as the start of `B`, each time followed by exactly one menu entry: credit only, technical only, or both in either order. A repeated mandatory check without an intervening Correct Dossier is outside the language (P7). B6 is a control-flow accept and a P6 `CONDITIONAL` until the affected-check attribute is present and equals `{Technical Review}`. A correction with an empty recheck is outside the language.

**5. Limitations caused by the missing attributes.**

- No current case can receive overall `PASS`, because sourcing is unknown. That is intentional. KPIs must count these releases as unverified on P3, not as compliant.
- The recheck menu cannot tell a correct partial recheck from a recheck of the wrong check. B6 stays conditional, not clean.
- A supplier-only correction is rejected. If the owner later classifies Supplier Review as a correctable check, the redo `X` gains the non-empty subsets of `{Credit Check, Technical Review, Supplier Review}` (seven blocks), which is still a local edit rather than a new catalog.
- Supplier Review between Credit Check and Technical Review is rejected under A-order, which is stronger than the written policy and must be signed.
- Expedite Review before a later recheck is in the language. A post-hoc warning (“expedite may be stale”) is appropriate; a hard reject would invent a rule P4 does not state.
- Auto-approval combined with expedite, supplier, or correction is in the language under A-approval. If risk rules actually restrict auto-approval, they are data rules and are not in this log.
- Silent supplier and expedite paths still make ordinary alignment fitness blind to those absences. The split verdict is what prevents that blindness from becoming a pass. Turning the same trick on Credit Check or Technical Review is the Model S failure and is not used.
- The correction loop is unbounded. Simulation must cap iterations at a published maximum (policy cap or the empirical maximum in the log). Conformance on finite traces does not need that cap.
- When both attributes exist, retire the single net’s ignorance encodings and replace them with a two-model family: an internal net with no Supplier Review obligation, and an external net in which Supplier Review is mandatory in `A`, plus a data choice that selects the recheck branch from the affected-check value. Building that family before the attributes exist would invent the data.

# 9. Validation Experiments

No metric below is a result. The skeletons are the measurement protocol. Publish `pm4py.__version__`, the case-id list of every split, the preprocessing script, and the alignment cost functions beside the scores.

**Reproducible splits.** Case-level split, stratified on a variant key that includes activity multiset plus whether Correct Dossier, Supplier Review, Expedite Review, and each approval occur. Repeat on five seeds. Do not split by event.

```python
import hashlib
import numpy as np
import pandas as pd
import pm4py

def variant_key(trace):
    names = tuple(trace)
    flags = (
        "Correct Dossier" in names,
        "Supplier Review" in names,
        "Expedite Review" in names,
        "Auto Approval" in names,
        "Manager Approval" in names,
    )
    return flags + (names,)

def split_cases(log_df, train_fraction=0.8, seed=42):
    case_col, act_col = "case:concept:name", "concept:name"
    keys = {}
    for cid, grp in log_df.groupby(case_col, sort=False):
        keys[cid] = variant_key(tuple(grp.sort_values("time:timestamp")[act_col]))
    rng = np.random.default_rng(seed)
    train_ids, test_ids = [], []
    for key in sorted(set(keys.values()), key=str):
        ids = [cid for cid, k in keys.items() if k == key]
        rng.shuffle(ids)
        if len(ids) == 1:
            train_ids.extend(ids)  # do not invent a holdout copy
            continue
        cut = max(1, min(len(ids) - 1, int(round(train_fraction * len(ids)))))
        train_ids.extend(ids[:cut])
        test_ids.extend(ids[cut:])
    train = log_df[log_df[case_col].isin(train_ids)]
    test = log_df[log_df[case_col].isin(test_ids)]
    manifest = hashlib.sha256(
        ("\n".join(map(str, sorted(map(str, test_ids)))).encode())
    ).hexdigest()
    return train, test, manifest
```

Report fitness separately on each stratum. A single holdout mean is how C’s failure mode was visible and still not diagnostic.

# 10. Governance Recommendation

Retire Model S and Model C as official process models. Keep both as laboratory artifacts: S as the baseline the negative suite must beat, C’s eight traces as regression fixtures for frequent variants.

- **Exploration.** Use the third model’s backbone, labeled as a hypothesis with A-order and A-approval printed on the picture. Do not use Model S in stakeholder workshops. Its fluency is how skipped checks become the local understanding of the process. Do not use Model C as the exploration view; it presents a sample as if it were the process.
- **Communication.** Use the same backbone, and require the accuracy protocol in section 9 before the picture is circulated as “the” process. Publish the split verdict (control flow, P3, P6, P7), not a single green mark.
- **Simulation.** Use neither original. Use the third model only with a published loop cap and with sourcing sampled from an explicit assumption that is displayed on every simulated KPI. Simulated compliance must not be reported while P3 is inconclusive.
- **Compliance enforcement.** Use neither original. Model S accepts B3 and B4. Model C rejects B2 and B5 and has no honest partial-recheck semantics. An interim manual checklist of the forbidden probes is safer than automating either net.

**Conditions before the third alternative is allowed to block or allow a release:**

1. `parse_process_tree` on the installed PM4Py accepts the string, `check_soundness` passes, and play-out matches `control_flow_accepts` on the probe list and on a bounded play-out sample.
2. The negative suite in section 9 is all rejected, and B1, B2, B5, B7, A1, and A3 are control-flow accepts.
3. The process owner signs or amends A-order, A-approval, and the three-entry recheck menu. A5 stays a reject only if that signature is obtained.
4. Overall `PASS` remains unreachable until `sourcing` is logged. Dashboards show P3 as unverified. A release with overall `CONDITIONAL` cannot be counted in a compliance KPI.
5. After `affected_checks` is logged, P6 mismatches are hard fails. Until then, B6-like traces stay conditional.
6. Alignment costs, five stratified seeds, and the case-id manifest are published. Probe verdicts are stable under the cost grid.
7. The comprehension protocol’s accuracy on forbidden probes meets a pre-registered bar for compliance and process-owner readers.
8. Duplicate Credit Check and Technical Review leaves are documented as one capability each, with one owning team.
9. Simulation, if any, uses a loop cap. Conformance jobs report mean fitness and perfect-trace rate separately and list deviant case ids.

Phased use is available before those conditions: the checker may run in advisory mode, writing control-flow failures as findings and writing every case as P3-unverified. Advisory mode is not enforcement.

# 11. Dissenting View

The recommendation treats P1–P5 as a license to generate the Cartesian product of partial rules. That reading is stronger than the record. The same bullets still leave supplier placement, the order of correction against expedite, and the eligibility of auto-approval unresolved, and the third model closes each gap by allowing the behavior. Local, plausible relaxations are exactly how Model S came to treat mandatory checks as skips. A closed catalog of approved variants, which is what Model C approximates, is the more conservative control until the process owner signs the product space. The holdout fitness drop is then evidence that unapproved combinations are reaching production, which is an operational problem and an audit finding, not proof that the catalog should be opened. The third model also reintroduces silent paths for Supplier Review. Under ordinary alignment costs those paths explain a missing supplier event for free, so an external order with a dropped event looks perfectly fit and the data check stays inconclusive forever if the attribute is never captured. Duplicate labels for the two mandatory checks remain, so ownership is still split across transitions. Generalization and fitness will likely flatter this language for the same mechanical reasons they flattered Model S. Elegance is not a control. I would keep the frequent-variant catalog as the enforcement baseline and park the third model in discovery until the attribute work and the signed matrix exist.

That rebuttal would change this recommendation if any of the following were shown. A signed variant matrix that marks the product space as closed would make the catalog the enforcement model, with the third language demoted to an extension queue. Attribute-complete replay that shows which supplier-absent cases are truly internal, and that affected-check values match the recheck menu, would turn P3 and P6 into hard constraints and would justify a real go-live of the family of conditioned models. A play-out trace that violates B3, B4, B8, or A2 would send the third model back. Evidence that operations record `CONDITIONAL` as a pass would block deployment until the KPI definition makes that recording impossible. A comprehension test in which readers apply the eight-variant catalog more accurately than the backbone would keep the catalog as the communication artifact and leave the backbone in the lab.
