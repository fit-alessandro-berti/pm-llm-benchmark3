# 2. Shared Assumptions

These assumptions are common to all three candidates.

1. **Event semantics are completion-only.**  
   Every recorded activity label is treated as the completion of that activity. The order in the log is completion order, not start order or causal order.

2. **Same-timestamp ordering is weak.**  
   Where events have equal timestamps, ingestion order may determine the observed order. All models therefore avoid relying on fine-grained ordering unless supported by a rule or repeated evidence.

3. **Closed activity vocabulary.**  
   The models use only the eight supplied labels. They do not model unobserved repair, rework, cancellation, suspension, or external side effects.

4. **At-most-once activity occurrence.**  
   Unless explicitly stated otherwise, each activity is assumed to occur at most once per case. This is supported by the observed variants but is still an assumption. It keeps the languages finite and avoids infinite-loop hypotheses.

5. **`Register Order` first and `Archive Case` last.**  
   All candidates enforce D1.

6. **Fixed approval/release tail.**  
   All candidates use `Approve Configuration -> Release Production -> Archive Case` as a fixed tail. D2 only requires approval before release, but the log shows no activity between approval, release, and archive. This is a deliberate simplification.

7. **Supplier Confirmation absence is conflated.**  
   Because the external/stocked attribute is missing and S5 warns about missing events, absence of `Supplier Confirmation` is represented as a control-flow alternative. This abstraction does not distinguish:
   - legitimate stocked-component skip;
   - missing `Supplier Confirmation` event;
   - data-integration failure.

8. **Optionality is represented structurally.**  
   Optional behavior is represented by explicit XOR branches or partial-order alternatives. Where silent skips are not used, optionality is visible as alternative observable traces. This makes the abstraction auditable but may duplicate labels across branches.

9. **Duplicate labels are allowed across branches.**  
   In XOR enumerations and some POWL branches, the same activity label may appear in multiple branches. This is necessary for explicit alternative hypotheses but can affect alignment ambiguity, simplicity metrics, and scalability.

10. **Partial order does not assert true concurrency.**  
   In the POWL candidate, absent precedence edges mean that multiple linearizations are allowed. This can be interpreted as concurrency, overlapping work, or case-by-case sequential variation. The model does not prove which interpretation is true.

# 3. Conservative Candidate

## Inductive-bias statement

The conservative candidate memorizes the observed variants and admits no additional complete trace. Its bias is strongly anti-generalization: it treats the seven observed variants as the current known language and refuses to infer concurrency, optional expedite without supplier confirmation, supplier confirmation after engineering-only triggers, or any other unobserved permutation. It is useful as a compliance baseline and as a regression oracle, but it will underfit as soon as a legitimate unseen variant appears.

## Compact formal expression

Using abbreviations:

- `R = Register Order`
- `C = Credit Check`
- `E = Engineering Review`
- `S = Supplier Confirmation`
- `X = Expedite Review`
- `A = Approve Configuration`
- `P = Release Production`
- `Z = Archive Case`

The conservative model is:

```text
R -> XOR(
    C -> E -> S,
    E -> C -> S,
    C -> E,
    E -> C,
    C -> S -> E,
    C -> E -> S -> X,
    E -> C -> X -> S
) -> A -> P -> Z
```

Equivalently, it is an XOR enumeration of the seven observed complete traces.

## Behavior deliberately excluded

The conservative candidate excludes every complete trace not exactly observed, including:

1. `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case`  
   Supplier confirmation after engineering but before credit check.

2. `Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case`  
   Expedite review without supplier confirmation.

3. `Register Order, Engineering Review, Credit Check, Expedite Review, Approve Configuration, Release Production, Archive Case`  
   Expedite review without supplier confirmation in the engineering-first variant.

4. Any rework, repetition, suspension, cancellation, or post-approval interleaving.

5. Any trace where `Supplier Confirmation` is missing from a case that should have had it but the event was lost, unless the resulting trace exactly matches one of the observed no-S variants.

## Known underfitting risks

1. **Fragility to valid unseen variants.**  
   If `Supplier Confirmation` can legitimately occur after `Engineering Review` but before `Credit Check`, the model rejects it.

2. **Fragility to missing `Supplier Confirmation` events.**  
   If an expedite case loses its `Supplier Confirmation` event, the observed trace may become `..., Expedite Review, Approve Configuration, ...`, which the conservative model rejects.

3. **No generalization from D5.**  
   D5 says supplier confirmation may start after either principal check, but the conservative model only admits the observed supplier-confirmation positions.

4. **No concurrency representation.**  
   The model cannot express that `Credit Check` and `Engineering Review` may overlap; it only enumerates completion orders.

5. **Scalability and duplicate-label issue.**  
   XOR enumeration repeats activity labels across branches. As variants grow, the tree grows linearly with the number of observed traces, alignment ambiguity can increase, and the model becomes hard to maintain.

# 4. Balanced Candidate

## Inductive-bias statement

The balanced candidate generalizes the strongest structural evidence while explicitly containing uncertainty. It treats `Credit Check` and `Engineering Review` as unordered mandatory predecessors of approval, because both completion orders are observed and D7 says completion timestamps cannot prove concurrency. It treats `Supplier Confirmation` as optional and, when present, dependent on `Credit Check` but not necessarily on `Engineering Review`; this is biased by V5, where supplier confirmation appears after credit check and before engineering completion, and by the absence of observed supplier confirmation before credit check. It allows `Expedite Review` optionally after both principal checks, with or without `Supplier Confirmation`, because D6 does not condition expedite review on supplier confirmation. This candidate is deliberately neither a memorization nor a full enumeration of all rule-consistent permutations.

## Compact formal expression

Let `` denote unordered partial-order precedence, not proven concurrency.

The balanced model is:

```text
R -> XOR(
    B0,
    B1,
    B2,
    B3
) -> A -> P -> Z
```

where:

```text
B0 = C  E
     no Supplier Confirmation, no Expedite Review

B1 = C -> S
     E is unordered with S
     Supplier Confirmation present, no Expedite Review

B2 = C -> X
     E -> X
     Expedite Review present, no Supplier Confirmation

B3 = C -> S
     C -> X
     E -> X
     S and X are unordered with each other
     E and S are unordered with each other
```

All branches also require:

```text
R before C and E
C before A
E before A
S before A, if present
X before A, if present
A -> P -> Z
```

## PM4Py POWL code

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

R = "Register Order"
C = "Credit Check"
E = "Engineering Review"
S = "Supplier Confirmation"
X = "Expedite Review"
A = "Approve Configuration"
P = "Release Production"
Z = "Archive Case"

def _po(labels, edges):
    """
    Build a StrictPartialOrder from labels and precedence edges.
    Edges are interpreted as strict precedence constraints.
    Absence of an edge means the two activities may appear in either order
    in a linearization, subject to the rest of the partial order.
    """
    po = StrictPartialOrder()
    nodes = {label: Transition(label=label) for label in labels}

    # Ensure all nodes exist in the order graph.
    for node in nodes.values():
        po.order.add_node(node)

    # Add precedence edges.
    for source_label, target_label in edges:
        po.order.add_edge(nodes[source_label], nodes[target_label])

    return po


def _xor(children):
    """
    Defensive constructor for an XOR POWL operator.
    PM4Py APIs can vary slightly by version.
    """
    constructors = [
        lambda: OperatorPOWL(Operator.XOR, children),
        lambda: OperatorPOWL(operator=Operator.XOR, children=children),
    ]

    for constructor in constructors:
        try:
            return constructor()
        except Exception:
            pass

    # Fallback for versions where children can be assigned after construction.
    node = OperatorPOWL(Operator.XOR)
    node.children = children
    return node


# Common mandatory skeleton for all balanced branches.
base_labels = [R, C, E, A, P, Z]
base_edges = [
    (R, C),
    (R, E),
    (C, A),
    (E, A),
    (A, P),
    (P, Z),
]

# B0: no Supplier Confirmation, no Expedite Review.
b0 = _po(
    base_labels,
    base_edges,
)

# B1: Supplier Confirmation present, no Expedite Review.
# Supplier Confirmation is after Credit Check but unordered with Engineering Review.
b1 = _po(
    base_labels + [S],
    base_edges + [
        (C, S),
        (S, A),
    ],
)

# B2: Expedite Review present, no Supplier Confirmation.
# Expedite Review requires both Credit Check and Engineering Review.
b2 = _po(
    base_labels + [X],
    base_edges + [
        (C, X),
        (E, X),
        (X, A),
    ],
)

# B3: Supplier Confirmation and Expedite Review both present.
# Supplier Confirmation after Credit Check.
# Expedite Review after both Credit Check and Engineering Review.
# Supplier Confirmation and Expedite Review are unordered with each other.
b3 = _po(
    base_labels + [S, X],
    base_edges + [
        (C, S),
        (S, A),
        (C, X),
        (E, X),
        (X, A),
    ],
)

model_balanced = _xor([b0, b1, b2, b3])
```

## How sequence, concurrency, and partial order were decided

### `Credit Check` versus `Engineering Review`

The log contains both completion orders:

- `Credit Check` before `Engineering Review` in many cases.
- `Engineering Review` before `Credit Check` in many cases.

S2 suggests parallel execution, but D7 says completion timestamps cannot prove concurrency. Therefore the balanced model does not choose a sequence. It uses an unordered partial order between `Credit Check` and `Engineering Review`. This admits both completion orders without asserting true parallelism.

### `Supplier Confirmation`

The evidence shows three important facts:

1. `Supplier Confirmation` is sometimes absent.
2. When present, it is always before `Approve Configuration`.
3. In V5, it completes after `Credit Check` but before `Engineering Review`.

The balanced model therefore uses a partial-order dependency:

```text
Credit Check -> Supplier Confirmation
```

but no edge:

```text
Engineering Review -> Supplier Confirmation
```

This allows `Supplier Confirmation` to appear before or after `Engineering Review` completion, as long as it occurs after `Credit Check`. It does not admit `Supplier Confirmation` after `Engineering Review` but before `Credit Check`, because that behavior is unobserved. The permissive candidate relaxes this.

### `Expedite Review`

D6 and S6 are strong enough to encode:

```text
Credit Check -> Expedite Review
Engineering Review -> Expedite Review
Expedite Review -> Approve Configuration
```

The observed V6 and V7 show `Expedite Review` after `Supplier Confirmation` in one case and before `Supplier Confirmation` in another. Therefore the balanced model adds no precedence edge between `Supplier Confirmation` and `Expedite Review`.

### Optionality

Optionality is represented by explicit XOR branches:

- no `Supplier Confirmation`, no `Expedite Review`;
- `Supplier Confirmation` only;
- `Expedite Review` only;
- both `Supplier Confirmation` and `Expedite Review`.

This makes the uncertainty visible. It also absorbs some missing-`Supplier Confirmation` scenarios: if a supplier confirmation event is missing from an expedite case, the `Expedite Review`-only branch may still replay the observed trace.

## Behavior deliberately excluded

1. `Supplier Confirmation` before `Credit Check`.  
   Example: `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case`.

2. `Supplier Confirmation` before both principal checks.  
   Example: `Register Order, Supplier Confirmation, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case`.

3. `Expedite Review` before both principal checks are complete.  
   Example: `Register Order, Credit Check, Expedite Review, Engineering Review, Approve Configuration, Release Production, Archive Case`.

4. `Supplier Confirmation` or `Expedite Review` after `Approve Configuration`.

5. Rework, repetition, or activities between `Release Production` and `Archive Case`.

## Known underfitting and overfitting risks

1. **Underfitting if D5 is true in the engineering-trigger direction.**  
   The balanced model rejects `Engineering Review -> Supplier Confirmation -> Credit Check`, which D5 permits.

2. **Underfitting if `Supplier Confirmation` can be triggered by case attributes not visible in the log.**  
   Without external/stocked information, the model cannot condition supplier confirmation on case type.

3. **Overfitting risk from allowing `Expedite Review` without `Supplier Confirmation`.**  
   This is plausible under D6 but unobserved. If business rules later show expedite review only occurs with supplier confirmation, this branch is too permissive.

4. **Underfitting if post-approval changes exist.**  
   The fixed tail `Approve Configuration -> Release Production -> Archive Case` excludes any unobserved post-approval activity.

5. **Duplicate labels across POWL branches.**  
   The balanced POWL model is more compact than full trace enumeration, but it still uses alternative branches with repeated labels.

# 5. Permissive Candidate

## Inductive-bias statement

The permissive candidate admits all reasonable one-pass linearizations consistent with the broad domain rules. It fully accepts D5’s statement that `Supplier Confirmation` may occur after either principal check. It also accepts optional `Expedite Review` with or without `Supplier Confirmation`, as long as expedite review occurs after both checks and before approval. Its boundary is that it still forbids clear rule violations: missing principal checks, supplier confirmation before any principal check, expedite review before both principal checks, approval/release violations, and activity repetition. This candidate is useful for sensitivity analysis and exploration, but it has higher precision risk.

## Compact formal expression

Let `O` be an optional subset of `{S, X}`. The middle part is any permutation of:

```text
{C, E}  O
```

subject to:

```text
if X is present: C < X and E < X
if S is present: C < S or E < S
```

The full language is:

```text
R -> XOR(all valid middle permutations) -> A -> P -> Z
```

This is still finite because activities are assumed to occur at most once.

## PM4Py code

```python
import itertools
import pm4py

R = "Register Order"
C = "Credit Check"
E = "Engineering Review"
S = "Supplier Confirmation"
X = "Expedite Review"
A = "Approve Configuration"
P = "Release Production"
Z = "Archive Case"

def _seq(trace):
    return "sequence(" + ",".join(f"'{a}'" for a in trace) + ")"

middle_traces = set()
optional_activities = [S, X]

for r in range(len(optional_activities) + 1):
    for subset in itertools.combinations(optional_activities, r):
        activities = [C, E] + list(subset)

        for perm in itertools.permutations(activities):
            pos = {activity: i for i, activity in enumerate(perm)}

            # Expedite Review requires both Credit Check and Engineering Review.
            if X in pos:
                if not (pos[X] > pos[C] and pos[X] > pos[E]):
                    continue

            # Supplier Confirmation must occur after at least one principal check.
            if S in pos:
                if not (pos[S] > pos[C] or pos[S] > pos[E]):
                    continue

            middle_traces.add(tuple(perm))

full_traces = sorted(
    {(R,) + middle + (A, P, Z) for middle in middle_traces}
)

permissive_tree_string = (
    "xor(" + ",".join(_seq(t) for t in full_traces) + ")"
)

model_permissive = pm4py.parse_process_tree(permissive_tree_string)
```

## Boundary between reasonable generalization and forbidden behavior

The permissive candidate admits reasonable unobserved combinations such as:

- `Engineering Review -> Supplier Confirmation -> Credit Check`;
- `Expedite Review` without `Supplier Confirmation`;
- `Expedite Review` before or after `Supplier Confirmation`;
- different completion interleavings of the principal checks.

It forbids:

1. `Supplier Confirmation` before both `Credit Check` and `Engineering Review`.
2. `Expedite Review` before both `Credit Check` and `Engineering Review`.
3. Missing `Credit Check` or missing `Engineering Review` before approval.
4. `Supplier Confirmation` or `Expedite Review` after `Approve Configuration`.
5. `Release Production` before `Approve Configuration`.
6. Repeated activities, loops, rework, or additional unobserved labels.

## Behavior deliberately excluded

1. `Register Order, Supplier Confirmation, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case`  
   `Supplier Confirmation` before any principal check.

2. `Register Order, Credit Check, Expedite Review, Engineering Review, Approve Configuration, Release Production, Archive Case`  
   `Expedite Review` before `Engineering Review` completion.

3. `Register Order, Credit Check, Engineering Review, Approve Configuration, Supplier Confirmation, Release Production, Archive Case`  
   `Supplier Confirmation` after approval.

4. Any trace with repeated `Credit Check`, `Engineering Review`, `Supplier Confirmation`, or `Expedite Review`.

## Known underfitting and overfitting risks

1. **Precision risk from broad generalization.**  
   The model admits many traces not observed, some of which may be operationally invalid.

2. **Over-admission due to missing attribute context.**  
   If `Supplier Confirmation` is mandatory only for external components, the model cannot enforce that condition without the missing attribute.

3. **Underfitting if true process has rework.**  
   The at-most-once assumption excludes repeated checks or supplier follow-ups.

4. **Scalability issue.**  
   This candidate is still an XOR enumeration, just generated from constraints. If more optional activities or repeats are added, enumeration can explode.

5. **Duplicate labels.**  
   Each branch repeats the same activity labels, which can affect alignment ambiguity and simplicity metrics.

### Validation limitations

- The models are finite only because we assume at-most-once execution and a closed activity vocabulary. If rework or loops are added, language comparison becomes much harder.
- Sampled playout does not prove language inclusion or equivalence. It only provides examples of allowed behavior.
- Alignment-based fitness can assign non-zero fitness to negative traces because model moves may be skipped. A negative trace with fitness below 1 indicates rejection, but the exact value depends on the cost function.
- PM4Py APIs for POWL and playout can vary by version. The code includes defensive fallbacks, but version-specific adaptation may be needed.
- Duplicate labels across XOR branches can create multiple possible alignments. This does not invalidate the validation, but it can affect metric stability and interpretability.

# 9. Recommendation and Data-Collection Plan

## Recommendation

**Immediate use: `model_balanced`.**  
The balanced candidate is the best operational compromise. It fits all observed traces, encodes the high- and medium-confidence domain rules, allows unordered completion of the principal checks, allows supplier confirmation to overlap with engineering review, and explicitly represents optional supplier confirmation and expedite review. It is suitable for monitoring, compliance checking, and controlled conformance analysis.

**Sensitivity analysis: `model_permissive`.**  
The permissive candidate should be used as a sensitivity model. It shows how conclusions change if D5 is interpreted broadly and if expedite review can occur without supplier confirmation. If alerts or compliance violations disappear only under the permissive model, the underlying issue is likely model uncertainty rather than clear process noncompliance.

The conservative candidate should be retained as an audit baseline or regression oracle, not as the main prospective model.

## Data-collection plan

The main ambiguities can be reduced by collecting the following fields.

### 1. Lifecycle timestamps

Collect not only completion timestamps but also:

- scheduled timestamp;
- start timestamp;
- completion timestamp;
- suspension/resumption timestamps, if applicable;
- ingestion timestamp.

This directly addresses D7 and S7. Overlapping start/completion intervals for `Credit Check` and `Engineering Review` would support concurrency. Strict non-overlapping starts would support sequential variants.

### 2. Case attributes

Collect case-level attributes that explain branching:

- external versus stocked component;
- supplier confirmation required flag;
- number of external components;
- expedite reason code;
- expedite authorization;
- customer priority;
- order type;
- material type.

This would allow replacing the current control-flow optional `Supplier Confirmation` with a data-aware condition.

### 3. Event-quality attributes

Collect:

- integration system ID;
- event version;
- missing-event indicator;
- retry or reconstruction flag;
- whether an event was manually added;
- whether timestamp was estimated.

This addresses S5 and helps separate true skips from missing events.

### 4. Activity-instance identifiers

Use unique activity-instance IDs so that repeated or overlapping instances of the same activity label can be distinguished. This is essential if rework or parallel instances exist.

## Maximally informative future traces

The following future traces would be especially useful for distinguishing competing hypotheses.

| Future trace pattern | What it would distinguish |
|---|---|
| `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case` | Distinguishes balanced credit-triggered supplier confirmation from permissive either-trigger supplier confirmation. If observed, the permissive hypothesis gains support. |
| `Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case` | Tests whether `Expedite Review` can occur without `Supplier Confirmation`. If observed, balanced/permissive expedite-only branches are supported. |
| `Register Order, Engineering Review, Credit Check, Expedite Review, Approve Configuration, Release Production, Archive Case` | Same as above, but with engineering-first completion order. |
| Cases with overlapping `Credit Check` and `Engineering Review` start timestamps | Distinguishes true concurrency from case-by-case sequential variation. |
| Cases where `Credit Check` starts before `Engineering Review` but completes later | Explains S1 versus V2 conflict: finance may control start order while completion order varies. |
| Cases with external attribute true but no `Supplier Confirmation` event | Estimates missing-event rate and tests S5. |
| Cases with stocked attribute true and no `Supplier Confirmation` event | Confirms legitimate skip behavior and supports optional supplier confirmation. |
| Cases with `Expedite Review` always before or always after `Supplier Confirmation` | Determines whether the current unordered relation should be replaced by a sequence. |

# 10. Uncertainty Statement

## Calibrated confidence assessment

| Modeling decision | Confidence | Reason |
|---|---:|---|
| `Register Order` is start and `Archive Case` is end. | High, around 0.95 | D1 is high confidence and all observed variants agree. |
| `Approve Configuration` precedes `Release Production`. | High, around 0.95 | D2 is high confidence and all observed variants agree. |
| Both `Credit Check` and `Engineering Review` are required before approval. | Medium-to-high, around 0.85 | D3 is medium-to-high and all observed variants contain both before approval. |
| `Credit Check` and `Engineering Review` should be unordered in the model. | Medium, around 0.60 | Both completion orders are observed, but D7 prevents confirming concurrency. |
| `Supplier Confirmation` is optional in the control-flow model. | Medium, around 0.75 | V3/V4 show absence, S4 supports skips, but S5 means absence may also be missing data. |
| Balanced model’s `Credit Check -> Supplier Confirmation` dependency. | Low-to-medium, around 0.45 | Supported by observed V5 and absence of supplier-before-credit traces, but D5 allows engineering-triggered supplier confirmation. |
| `Expedite Review` requires both principal checks. | Medium-to-high, around 0.80 | D6 and S6 are consistent with the two observed expedite traces. |
| `Expedite Review` can occur without `Supplier Confirmation`. | Low, around 0.35 | Not observed, but not forbidden by D6/S6. |
| At-most-once execution assumption. | Medium, around 0.70 | Observed log has no repeats, but real processes may contain rework not visible in 30 cases. |

## Plausible alternative interpretation that would change the recommendation

A materially different interpretation is that **all absent `Supplier Confirmation` events in the observed log are missing events, not legitimate stocked skips**. If S5’s integration problem explains the no-S traces, then `Supplier Confirmation` may actually be mandatory for all observed cases, and the correct model would need a mandatory supplier confirmation plus an explicit missing-event or noise model. In that case, the balanced and permissive candidates would be too permissive, and the recommendation would shift toward a data-corrected mandatory-supplier model or, temporarily, a conservative audit model until missingness is quantified.

Another important alternative is that **S1 is true at the start-time level**: `Credit Check` always starts before `Engineering Review`, but completion order varies because durations differ or because the activities overlap. If start timestamps confirm this, the model should separate start precedence from completion order. The current balanced model’s unordered `Credit Check`/`Engineering Review` relation would then be an overgeneralization of the true start logic, even though it may still correctly describe completion-order behavior.
