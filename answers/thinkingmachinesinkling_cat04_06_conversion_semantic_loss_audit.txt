**Key interpretations:**

- **True concurrency vs arbitrary interleaving:** The POWL `StrictPartialOrder` allows true concurrency (`Assess` and `Prepare` can occur in either order, even simultaneously in a true-concurrency semantics). The Petri net representation preserves this as parallel branches (interleaving is a subset of true concurrency). BPMN parallel gateways preserve interleaving but typically do not distinguish true concurrency from arbitrary interleaving unless annotated. This is `ambiguous` at the visualization level.
- **Lack of an edge between Optional Legal Review and verification:** In the source, `optional_legal` and `verification_loop` have no ordering relation except through `Release Change`. The net preserves this absence (no arc between them). BPMN renders them as separate branches that only merge at `Release`, which is correct, but diagram layout often imposes a left-to-right order that is not semantic.
- **Silent optional behavior:** The `SilentTransition` (`skip_legal`) is visible to the converter as a transition without label. In BPMN, silent behavior is typically rendered as a default sequence flow or omitted, which is acceptable but makes stakeholder review harder because the "skip" path is invisible.
- **Binary-loop semantics:** The loop is a binary `LOOP` (`trial_body`, `correct_defect`). The net preserves this exactly: execute first child at least once, then either exit or execute second child and loop back. BPMN loop markers approximate this, but engine-specific loop conditions may differ if not annotated.
- **Join before Release Change:** Both `optional_legal` and `verification_loop` flow into `Release Change`. The net uses a join place. BPMN uses an AND gateway (or implicit merge) before `Release`. The round-trip must preserve this join; if the round-trip net collapses the join into a single input, the invariant is `lost`.

# 6. Visual-Semantics Review

Even when the converted net is sound, the BPMN rendering (`bpmn_from_net`) can be misread:

- **Parallel gateways (AND) vs layout:** The concurrent `Assess Risk` / `Prepare Evidence` pair and the concurrent `optional_legal` / `verification_loop` pair are rendered with parallel gateways (`+` diamonds). However, BPMN diagram layout is not semantics: left-to-right placement does not imply order. A stakeholder may read the diagram top-to-bottom as a sequence (`Assess`  `Prepare`  `Loop`  `Legal`  `Release`), which is false.

- **Exclusive gateway (XOR) for optional legal:** The `XOR` between `Legal Review` and `skip_legal` renders correctly as an exclusive split. However, the silent skip path is invisible or drawn as an unlabeled sequence flow. A reviewer may not realize that the "else" branch is an explicit silent skip rather than a missing path, leading them to believe `Legal Review` is mandatory.

- **Loop visualization:** The `LOOP` (`trial_body`, `correct_defect`) is typically rendered with a loop marker on the `trial_body` boundary or with a feedback arrow from `Correct Defect`. Without annotations, it may appear that `Correct Defect` is a terminal error path rather than an iteration separator. The loop back arrow may be mistaken for an exception flow rather than normal repetition.

- **Silent routing nodes:** Any silent transition inserted by the converter (for synchronization or routing) appears as an unlabeled task or is absorbed into sequence flows. This removes auditability: a stakeholder cannot verify that synchronization occurs exactly at `Release Change` unless they inspect the gateway nodes.

- **Gateway ambiguity at `Release Change`:** `Release` waits for both branches. In BPMN, this is an AND-join. If the converter produces an implicit merge (no visible gateway), the synchronization invariant `IN8` becomes visually ambiguous. The diagram may suggest that either branch alone can proceed to `Release`.

**Proposed annotations / documentation to reduce ambiguity:**

1. **Annotation boxes** attached to `Assess`/`Prepare` stating: "Concurrent—no order required."
2. **Annotation on loop boundary:** "At least one execution of Configure  Inspect; Correct Defect separates iterations."
3. **Annotation on silent XOR path:** "Silent skip—Legal Review is optional; this flow represents absence."
4. **Explicit AND-gateway labels** at every join (`Verification Loop` entry, `Release Change`), with text: "Waits for all incoming branches."
5. **Legend/key** in documentation mapping every BPMN gateway to the source POWL invariant (`IN2`, `IN6`, `IN7`, `IN8`).
6. **Separate "stakeholder view" vs "execution view"** files: one BPMN with annotations for humans, one unannotated BPMN for execution, both derived from the same authoritative `net_from_powl`.

# 7. Rejection Criteria

A conversion result must be rejected or quarantined if any of the following occur:

1. **Unsound workflow net:** `pm4py.check_soundness(...)` returns `False` for `net_from_powl` or any round-trip net. Unsoundness means deadlocks or unreachable final states.
2. **Null initial or final marking:** If `im_from_powl` or `fm_from_powl` is `None`, the accepting-net contract is broken; no stakeholder model should be derived.
3. **Process-tree suppression error:** If Pipeline B raises an exception that is caught but then ignored without logging (i.e., failure is not interpreted). The exception must be explicitly recorded as structural non-block-structure.
4. **Loss of required concurrency/interleaving:** If bounded exploration shows that `Assess` and `Prepare` cannot occur in both orders (e.g., one is serialized before the other in all traces), the net has collapsed `IN2`.
5. **Admission of release before verification:** If a positive witness trace reaches `Release Change` without `verification_loop` completing (or without `optional_legal` when required by synchronization), `IN8` is violated.
6. **Collapse of optional behavior:** If `Legal Review` is forced present in all traces (silent skip removed) or forced absent (XOR collapsed to sequence), `IN3` is lost.
7. **Exact final-marking mismatch:** In bounded exploration, any trace reaching `fm` in the source net but failing to reach the corresponding `fm` in the round-trip net (or vice versa) indicates semantic drift.
8. **Infinite silent cycling:** If bounded exploration detects cycles of silent transitions (`None` labels) that do not progress visible state and are not bounded by the `max_steps`/loop-approximation constraint.

# 8. Canonical Representation Recommendation

- **Authoritative storage:** The `source_powl` (Python object / serialized POWL) is the canonical model. It is the only artifact that explicitly encodes `StrictPartialOrder`, nested `OperatorPOWL`, and `SilentTransition` without approximation.
- **Executable/intermediate canonical:** `net_from_powl` (the accepting Petri net with verified initial and final markings) is the canonical executable representation. It is the closest formal semantics to the POWL and is directly auditable via soundness checks.
- **Derivative visualization:** `bpmn_from_net` is a derivative visualization artifact only. It must never be edited directly; any stakeholder change must be applied to `source_powl` and reconverted through Pipeline A.
- **Process-tree intermediate:** Not permitted as canonical. Pipeline B is allowed only for audit/demonstration of structural failure. If `convert_to_process_tree` succeeds unexpectedly, the result must be quarantined and compared against the authoritative net; it is not trusted as behaviorally equivalent because the source is not block-structured.
- **Validation evidence required with every derivative:**
  - `check_soundness(net, im, fm)` result (`True` + diagnostics).
  - `check_is_workflow_net(net)` result.
  - Footprint object (`discover_footprints`) for behavioral comparison.
  - Bounded exploration report (`exhaustive_under_bound`, final-trace counts, witness trace outcomes).
  - Filename mapping (`net_from_powl.gv`, `bpmn_from_net.bpmn`, etc.).
- **Future edit protocol:** Edit `source_powl` code or its serialized form; regenerate `net_from_powl`; regenerate `bpmn_from_net`; re-run Pipeline B exception check; re-run bounded exploration; update annotations. This avoids round-trip drift (editing BPMN and losing POWL-level invariants like silent skips or loop binary structure).

# 9. Residual Uncertainty

Even if all proposed tests pass, the following claims **cannot** be definitively established:

1. **Full state-space equivalence:** The bounded exploration uses `max_steps=25`, `max_visible=6`, and `max_loop_approx=2`. Unbounded loops or deeper interleavings beyond these bounds are not verified. The claim "the round-trip net is behaviorally identical" is only supported within the bound.
2. **True concurrency preservation under BPMN execution engines:** The Petri net preserves true concurrency, but BPMN execution semantics vary across engines (some serialize parallel branches). The audit validates structural preservation, not engine-specific concurrent execution.
3. **Stakeholder interpretation matches formal semantics:** The BPMN annotations and documentation reduce ambiguity, but no automated test can prove that a human reader will interpret the parallel gateway, silent XOR path, or loop marker correctly.
4. **Invisible silent-transition identity in round-trip:** If `skip_legal` or loop routing silent nodes are merged, split, or replaced by implicit sequence flows during BPMN round-trip, structural identity of silent nodes is not guaranteed—even if visible-trace behavior is preserved within the bound. Only behavioral traces are compared, not node-level graph isomorphism.
