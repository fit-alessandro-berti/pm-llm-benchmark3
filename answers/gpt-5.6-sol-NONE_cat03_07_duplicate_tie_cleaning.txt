## 1. Duplicate-handling decision tree

1. **Are two rows identical technical records?**  
   Compare source, `source_event_key`, source payload identity, activity, timestamp, attributes, and E2O relations.
   - **Yes:** exact technical duplicate  **drop** the later/repeated row, retaining its ingestion/provenance record under the canonical event.
   - **No:** continue.

2. **Is there explicit external or source-key evidence that both records observe the same physical event?**
   - **Yes:** same physical event observed by multiple systems  **merge attributes and relations** into one canonical event. Preserve both source IDs, payloads, labels, timestamps, and conflicts.
   - **No:** continue.

3. **Is one record documented as a generated summary/status update derived from another?**
   - **Yes, and the analytical view intentionally collapses abstraction levels:** **merge attributes and relations**, while recording `derived_from`.
   - **Yes, but the summary is a meaningful event at another abstraction level:** **retain both with refined labels or qualifiers**, e.g. `Pack Package [WMS transaction]` and `Package Status Updated [ERP summary]`.
   - **Uncertain derivation:** continue as unresolved.

4. **Did harmonization collapse semantically different source activities into the same label?**
   - **Yes:** harmonization collision  **retain both with refined labels or qualifiers** using original source semantics. Do not deduplicate based on harmonized activity.
   - **No:** continue.

5. **Do same-label, same-time events concern distinct business objects at the event-defining level?**
   Examples: I1 versus I2, M1 versus M2.
   - **Yes:** concurrent same-label events involving different objects  **retain both unchanged**, or refine labels only for readability.
   - **No:** continue.

6. **Does one row lack the distinguishing object because it is a higher-level summary?**
   - **Documented derivation:** treat under step 3.
   - **Not documented:** unresolved candidate  **retain both unchanged** in the production OCEL and **quarantine for review** in a candidate table. Quarantine means flagging, not necessarily removing from the usable data.

7. **No decisive evidence**
   - Unresolved candidate  **retain both unchanged** and **quarantine for review**. Similar timestamp, activity, payload hash, or shared objects alone is insufficient.

The decision process is evidence-ranked. It must stop when a justified semantic category is reached; duplicate-removal methods should not be stacked mechanically.

## 3. Timestamp-tie ordering rules

Construct a directed acyclic graph for each tied timestamp group, then apply deterministic topological sorting. If semantic constraints conflict, stop and quarantine the conflict rather than silently break it.

Priority of constraints:

1. **Explicit domain constraints — semantic.**  
   Examples: e09 before e10; e12 before e13.
2. **Within-source `source_seq` — semantic only within that source.**  
   It does not compare ERP sequence 30 with WMS sequence 110.
3. **Lifecycle constraints on a shared defining object — semantic.**  
   Authorization precedes capture for M1. A generic activity precedence must not order unrelated M2.
4. **Source-specific semantics — semantic when documented.**  
   Warehouse release precedes carrier acceptance here if source documentation/business rules establish that transition.
5. **Ingestion time — deterministic only.**  
   Use only among still-incomparable events, never as evidence of business order.
6. **Stable fallback — deterministic only.**  
   Sort by source rank, normalized `source_event_key`, and finally canonical `eid`. The source rank is an arbitrary published configuration, not an authority ranking.

The topological result is a reproducible linear extension of a partial order; it does not prove physical sequence. Only after choosing this extension may synthetic microseconds be added. Adding them first—especially from ingestion order—turns a technical arrival pattern into an apparently precise business story.

Intended tied orders:

- **10:00, conservative:** e03/e04 merged as e03; e05; e06; e07.  
  WMS sequence gives e03 before e06. Scanner sequence gives e04 before e05 before merging, supporting e03 before e05. ERP alone does not semantically compare e07 with WMS events, but documented derivation places e06 before e07. The relative order of e05 and e06 is not fully established across sources; `e03, e05, e06, e07` is a deterministic admissible extension, not proof. Without the derivation fact, e07 could remain incomparable with e05/e06.
- **10:15:** e08  e09  e10 if the release-to-acceptance source semantics are accepted. At minimum, e09  e10 is mandatory; e08 could otherwise be incomparable and placed deterministically.
- **12:00 after merging e11/e16:** e11, e12, e13, e14, e15 is one deterministic extension. e12  e13 is semantic. PSP sequence also orders e12  e13  e14, although e13 and e14 are distinct payments. ERP sequence orders e11  e15. There is no general cross-source proof that invoice issuance precedes authorization, or that e15 follows both payment messages from timestamps alone; documented generation may add those edges. Otherwise alternatives such as e12, e13, e14, e11, e15 are admissible.

Adjusted timestamps should be stored separately, e.g. `ordered_timestamp`; all duration analysis should default to `original_timestamp` unless synthetic tie offsets are explicitly requested.

## 4. Conservative cleaning pipeline

1. Deep-copy and validate the raw OCEL.
2. Preserve immutable raw fields: original eid, activity, timestamp, source, source key, payload hash, sequence, ingestion time, attributes, and E2O relations.
3. Normalize datatypes and UTC timestamps without changing values.
4. Generate candidate groups using exact source keys, same activity/time, object overlap, payload similarity, and known lineage. Candidate generation must not itself delete anything.
5. Remove exact technical duplicates only if all relevant event and relation content agrees. None are demonstrated here.
6. Merge only verified same-event pairs:
   - e03/e04  e03;
   - e11/e16  e11.
7. Preserve e06 and e07 as separate abstraction-level events; refine e07 to something such as `Package Status Updated [ERP derived]`.
8. Restore semantic distinctions:
   - e08  `Release Package from Warehouse`;
   - e09  `Carrier Accept Package`;
   - e10 remains `Handover to Carrier`.
9. Retain e05, e13, and e14 as distinct object-specific work. Retain e15 as `Invoice Balance Updated [ERP summary]`, with lineage/review metadata rather than forced payment relations.
10. Build semantic precedence constraints, obtain a deterministic topological order, sort, and only then add a separate index-based timedelta.
11. Validate IDs, E2O references, object references, uniqueness, and merge audit records.

Starting from 17 events, two verified pair merges each reduce the count by one, yielding **15 retained events**. This is minimum-change semantically, despite merging the two strongly supported duplicate observations.

## 5. Aggressive alternatives

### Evidence-based semantic merging

In addition to e03/e04 and e11/e16:

- Merge e06/e07 as one packing transition because e07 is documented as generated from the WMS message.
- Optionally merge e15 with a payment event only if message-level lineage identifies exactly which capture or aggregate it represents. The current facts do not identify M1 versus M2, so the defensible evidence-based scenario leaves e15 separate.

Expected count: **14 events**. If later lineage proves e15 to be a duplicate observation of one specific capture, **13**.

Likely damage: loss of the ERP status-update milestone, flattened abstraction layers, union of detailed item links into an event that the ERP never represented, and distorted source-specific conformance. This remains substantially safer than similarity-based merging.

### Mechanically aggressive PM4Py merging

Apply `pm4py.ocel_merge_duplicates` to a separate copy, typically with matching activity/timestamp and common-object logic. The exact count is version/data-dependent and must be measured, not promised. For this table it may collapse several same-time same-label groups and produce **approximately 10–13 events**.

Most likely damage includes:

- e03/e05 collapsing despite I1 versus I2;
- e08/e09 collapsing despite release versus acceptance;
- e13/e14 collapsing despite M1 versus M2;
- e13/e15 or e14/e15 becoming connected through shared O1/V1;
- e06/e07 collapsing without preserving abstraction.

`have_common_object=True` is only an overlap test. It does not require equality of defining-object sets or the same Payment. e13 and e14 share O1 and V1, so the option does not protect them, even though one capture concerns M1 and the other M2. Safe duplicate logic must compare object roles/types and require agreement on event-defining objects.

## 6. PM4Py-oriented Python implementation

```python
import copy
import inspect
import pandas as pd
import pm4py

# PM4Py OCEL2 commonly uses these names; adapt only this mapping if needed.
EID = "ocel:eid"
ACT = "ocel:activity"
TS = "ocel:timestamp"
OID = "ocel:oid"
OTYPE = "ocel:type"
QUAL = "ocel:qualifier"

def deep_clone(ocel):
    return copy.deepcopy(ocel)

def preserve_raw_fields(ocel):
    ev = ocel.events.copy(deep=True)
    if "original_timestamp" not in ev:
        ev["original_timestamp"] = pd.to_datetime(ev[TS], utc=True)
    if "original_activity" not in ev:
        ev["original_activity"] = ev[ACT]
    ev["source"] = ev["source"].astype("string")
    ev["source_event_key"] = ev["source_event_key"].astype("string")
    ev["original_eid"] = ev.get("original_eid", ev[EID]).astype("string")
    ocel.events = ev
    return ocel

def candidate_precheck(ocel):
    """Candidate generation only: no pair returned here is automatically a duplicate."""
    ev = ocel.events
    rel = ocel.relations[[EID, OID, OTYPE]].drop_duplicates()
    objsets = rel.groupby(EID).apply(
        lambda x: frozenset(zip(x[OTYPE].astype(str), x[OID].astype(str))),
        include_groups=False
    )
    rows = []
    for (_, _), g in ev.groupby([TS, ACT], dropna=False):
        ids = sorted(g[EID].astype(str))
        for i, a in enumerate(ids):
            for b in ids[i + 1:]:
                oa, ob = objsets.get(a, frozenset()), objsets.get(b, frozenset())
                rows.append({
                    "eid_a": a, "eid_b": b,
                    "object_intersection": len(oa & ob),
                    "same_object_set": oa == ob,
                    "requires_review": True
                })
    return pd.DataFrame(rows)

def merge_verified_pairs(ocel, pair_rules):
    """
    pair_rules: list of dicts:
      canonical, absorbed, rule, confidence, attribute_authority (optional dict col->source)

    The canonical event survives. Conflicting non-key attributes are not silently
    overwritten: canonical values stay in the event table, while all source values
    are recorded in merge_audit. Relations are unioned, with exact E2O duplicates
    removed. This function can be extended to materialize namespaced attributes.
    """
    ev = ocel.events.copy(deep=True)
    rel = ocel.relations.copy(deep=True)
    audit = []

    for r in pair_rules:
        keep, drop = r["canonical"], r["absorbed"]
        kr = ev.loc[ev[EID].astype(str).eq(keep)]
        dr = ev.loc[ev[EID].astype(str).eq(drop)]
        if len(kr) != 1 or len(dr) != 1:
            raise ValueError(f"Expected one row each for {keep}, {drop}")

        k, d = kr.iloc[0], dr.iloc[0]
        values = {
            c: {"canonical": None if pd.isna(k[c]) else k[c],
                "absorbed": None if pd.isna(d[c]) else d[c]}
            for c in ev.columns
        }
        audit.append({
            "canonical_eid": keep,
            "source_event_ids": [keep, drop],
            "merge_rule": r["rule"],
            "confidence": r["confidence"],
            "source_values": values,
            "attribute_authority": r.get("attribute_authority", {})
        })

        # Repoint absorbed E2O relations to the canonical event.
        rel.loc[rel[EID].astype(str).eq(drop), EID] = keep
        ev = ev.loc[~ev[EID].astype(str).eq(drop)].copy()

    relation_key = [c for c in [EID, OID, OTYPE, QUAL] if c in rel.columns]
    rel = rel.drop_duplicates(subset=relation_key, keep="first")
    ocel.events, ocel.relations = ev, rel
    ocel.merge_audit = audit
    return ocel

def validate_ocel(ocel):
    assert ocel.events[EID].is_unique, "Duplicate event IDs"
    assert ocel.objects[OID].is_unique, "Duplicate object IDs"
    assert set(ocel.relations[EID]).issubset(set(ocel.events[EID]))
    assert set(ocel.relations[OID]).issubset(set(ocel.objects[OID]))
    assert ocel.events["original_timestamp"].notna().all()
    return True

def call_supported(func, ocel, **kwargs):
    """Avoids assuming every PM4Py release exposes exactly the same keywords."""
    params = inspect.signature(func).parameters
    return func(ocel, **{k: v for k, v in kwargs.items() if k in params})

raw = preserve_raw_fields(deep_clone(ocel_raw))
candidates = candidate_precheck(raw)
print(candidates.to_string(index=False))

# Independent library drop scenario: justified only for exact technical duplicates.
# No semantic pairs are declared exact here; PM4Py's function is demonstrated on
# an isolated copy and its output must be diffed/audited before adoption.
technical_drop = deep_clone(raw)
technical_drop = call_supported(
    pm4py.ocel_drop_duplicates,
    technical_drop,
    have_common_object=True
)
validate_ocel(technical_drop)

# Conservative, verified semantic identity only.
conservative = deep_clone(raw)
conservative = merge_verified_pairs(conservative, [
    {"canonical": "e03", "absorbed": "e04",
     "rule": "reconciliation_same_physical_scan", "confidence": 0.99,
     "attribute_authority": {"location": "WMS"}},
    {"canonical": "e11", "absorbed": "e16",
     "rule": "same_invoice_number_verified", "confidence": 0.99,
     "attribute_authority": {"invoice_financials": "BILLING",
                             "erp_posting_status": "ERP"}}
])

refined = {
    "e07": "Package Status Updated [ERP derived]",
    "e08": "Release Package from Warehouse",
    "e09": "Carrier Accept Package",
    "e15": "Invoice Balance Updated [ERP summary]"
}
conservative.events[ACT] = conservative.events.apply(
    lambda x: refined.get(str(x[EID]), x[ACT]), axis=1
)

# event_order is assumed to come from a validated topological sort of semantic
# constraints; the numeric values below are the chosen deterministic extension.
order = ["e01","e02","e03","e05","e06","e07","e08","e09","e10",
         "e11","e12","e13","e14","e15","e17"]
rank = {eid: i for i, eid in enumerate(order)}
conservative.events["event_order"] = (
    conservative.events[EID].astype(str).map(rank).astype("int64")
)
conservative = pm4py.ocel_sort_by_additional_column(
    conservative, "event_order"
)
# Only now introduce a synthetic tie-break timestamp. original_timestamp remains.
conservative = pm4py.ocel_add_index_based_timedelta(conservative)
validate_ocel(conservative)

# Evidence-based abstraction merge: e06/e07 in addition to verified pairs.
evidence_based = deep_clone(conservative)
evidence_based = merge_verified_pairs(evidence_based, [
    {"canonical": "e06", "absorbed": "e07",
     "rule": "documented_derived_erp_status_collapsed_for_analysis",
     "confidence": 0.85}
])
validate_ocel(evidence_based)

# WARNING: mechanically merges candidates according to PM4Py's duplicate logic.
# It may collapse distinct items/payments when they merely share O1 or V1.
aggressive = deep_clone(raw)
aggressive = call_supported(
    pm4py.ocel_merge_duplicates,
    aggressive,
    have_common_object=True
)
validate_ocel(aggressive)

print({
    "raw": len(raw.events),
    "technical_drop": len(technical_drop.events),
    "conservative": len(conservative.events),
    "evidence_based": len(evidence_based.events),
    "aggressive_measured": len(aggressive.events)
})
```

In production, inspect the exact PM4Py version’s duplicate predicates and diff all removed/merged IDs. The custom audit should preferably be stored as a normal side table rather than only a Python attribute.

### Flattened and object-centric behavior

- **Order-flattened DFG:** raw data shows duplicate-looking patterns such as `Pick Item  Pick Item`, `Pack Package  Pack Package`, `Dispatch Package  Dispatch Package`, `Issue Invoice  Issue Invoice`, and multiple `Capture Payment` occurrences. Conservative cleaning removes the verified pick and invoice duplication, while refined labels turn logistics and summary transitions into interpretable milestones. Evidence merging removes the pack/status edge. Aggressive merging suppresses apparent rework but may suppress genuine work.
- **Item-flattened DFG:** e03/e04 duplication produces repeated I1 picking in raw data. Conservative merging removes that false repetition, while e05 remains visible on I2. Merging e03/e05 would create one broad pick linked to both items and erase item-level multiplicity.
- **Payment-flattened DFG:** M1 correctly shows `Authorize Payment  Capture Payment`; M2 shows a distinct capture without an authorization in the supplied window. e15 has no Payment relation and should not enter Payment traces. Aggressive relation union may falsely attach e15 or collapse M1/M2 captures.
- **OC-DFG:** frequency metrics decrease after verified merges, especially Pick–Pick and Invoice–Invoice patterns. Refined labels add meaningful `Warehouse Release  Carrier Acceptance  Handover` edges. Aggressive merging reduces node/event frequency and may create broad events whose direct-follow semantics mix object types.
- **ET–OT weights:** conservative merging lowers `Pick Item–Item/Package/Order` observation counts and `Issue Invoice–Order/Invoice` counts without losing unique object coverage. Merging e06/e07 can increase the apparent item participation of a combined cross-system event. Mechanical union may make `Capture Payment` appear associated with both M1 and M2.
- **OTG relations:** the underlying object graph should remain stable under verified merges because no object is deleted. However, event-mediated co-occurrence weights change: aggressive union may strengthen or create apparent Payment–Payment, Item–Item, or Payment–Invoice associations.
- **Rework/loops:** raw repeated harmonized labels resemble rework. Conservative refinement distinguishes observation duplication, abstraction, and true milestones. Aggressive merging can make performance look artificially clean.
- **Lifecycle/performance:** original tied timestamps imply zero measured durations among tied events. Synthetic microseconds must not be treated as actual service or waiting time. Merging removes intervals entirely and can shift cycle-time endpoints.

Concrete changing interpretations include:

1. `Pick Item  Pick Item`: duplicate observation versus two item picks.
2. `Pick Item  Pack Package`: readiness transition; frequency changes after I1 deduplication.
3. `Pack Package  Pack Package`: transaction-to-summary abstraction, not necessarily rework.
4. `Dispatch Package  Dispatch Package`: harmonization collision, correctly refined to warehouse release  carrier acceptance.
5. `Carrier Accept Package  Handover to Carrier`: genuine ordered carrier lifecycle.
6. `Issue Invoice  Issue Invoice`: duplicate observation eliminated by verified merge.
7. `Authorize Payment  Capture Payment` for M1: mandatory lifecycle edge that must survive.
8. `Capture Payment  Capture Payment`: may represent M1 then M2, not duplicate capture.
9. `Capture Payment  Invoice Balance Updated`: message-to-summary relation, not another capture.
10. Apparent M1–M2 co-occurrence in an aggressive merged event: a modeling artifact, not proof of one payment.

## 8. Audit trail and reversibility

Use an append-only `event_canonicalization` table with:

- `canonical_eid`;
- ordered `source_event_ids`;
- source, source key, payload hash, and original eid;
- merge/split/refinement rule and rule version;
- reviewer or automated rule identity;
- confidence and human-readable reason;
- original and refined activity per source event;
- original timestamp and adjusted ordering timestamp;
- semantic precedence edges used;
- source attributes as immutable JSON snapshots;
- selected canonical value, attribute authority, and source for every selected field;
- discarded/conflicting values and reason;
- original E2O relations and resulting E2O relations;
- processing run ID and processing timestamp.

No source value should be physically discarded from the audit store. Refined labels and adjusted timestamps are derived fields, not overwrites.

To reconstruct the raw view, select the immutable source-event snapshots and original E2O relations by run/source event ID, restore original activity and timestamp, and ignore canonicalization mappings. For lossless reversibility, retain raw objects and relations in versioned storage and use the audit mapping as a view definition rather than destructive mutation.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments:** e13/e14 share O1/V1 but differ on M1/M2.  
   *Safeguard:* require equality on defining Payment objects.

2. **Converting abstraction updates into false rework:** e06/e07 appear as repeated packing.  
   *Safeguard:* retain/refine source-level semantics and record `derived_from`.

3. **Ordering by ingestion time:** technical latency becomes business sequence.  
   *Safeguard:* use ingestion only after semantic constraints are exhausted.

4. **Treating shared objects as proof of duplication:** most order events share O1.  
   *Safeguard:* object-role/type-aware identity tests plus lineage evidence.

5. **Unioning incompatible E2O relations:** merging e15 into a capture could assign an invoice summary to M1 or M2.  
   *Safeguard:* relation compatibility checks; do not infer missing defining objects.

6. **Changing durations through synthetic microseconds:** zero-time concurrency becomes positive waiting time.  
   *Safeguard:* retain `original_timestamp`; exclude synthetic offsets from performance analysis.

7. **Losing source-authoritative attributes:** one merged invoice value overwrites another system’s authoritative field.  
   *Safeguard:* per-attribute authority map, namespaced raw values, conflict log.

8. **Applying duplicate functions to the whole OCEL without candidate inspection:** legitimate same-time work is collapsed.  
   *Safeguard:* pre-check groups, dry-run diffs, thresholds, and approval gates.

9. **Comparing `source_seq` across systems:** unrelated number scales imply false order.  
   *Safeguard:* enforce sequence only within each source.

10. **Assuming harmonized labels preserve meaning:** e08/e09 both become dispatch.  
    *Safeguard:* preserve original labels and refine known collisions.

11. **Allowing cyclic precedence constraints:** inconsistent rules make ordering arbitrary.  
    *Safeguard:* detect cycles and quarantine the tied group.

12. **Choosing canonical IDs nondeterministically:** repeated runs produce different references.  
    *Safeguard:* published canonical rule, normally earliest stable raw eid or authoritative source key.

13. **Dropping object relations when merging observations:** an enrichment relation disappears.  
    *Safeguard:* audited compatible union, followed by referential-integrity checks.

14. **Believing a total order is ground truth:** stable tie-breaking is mistaken for physical chronology.  
    *Safeguard:* store semantic edges separately and label the total order as one deterministic linear extension.
