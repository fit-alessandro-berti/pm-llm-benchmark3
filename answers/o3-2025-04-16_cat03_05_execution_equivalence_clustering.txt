## 1. Equivalence design space  

We use the same universe for all relations:  
– an execution  = E, , type, incidence, qualifier where  
  E … finite set of events  
   … observed total order (ties allowed for same-timestamp events)  
  type(e) … activity label of e  
  incidence(e, T) … finite multiset of object ids of type T occurring in e  
  qualifier(o, o) … (possibly empty) set of O2O flags (“removed_before_dispatch”, …)  

The lead object type is Order; only the connected component of the created Order is retained.

--------------------------------------------------------------------
1. Activity-sequence equivalence  ()  
Definition:     the sequence of activity labels type(e) projected on the  order is identical.  
Preserved: ordering and repetition of labels.  
Discarded: object types, multiplicities, external flags, O2O qualifiers.  
Properties: reflexive, symmetric, transitive (equality on strings).  
Concurrency: if timestamps tie we sort by event id; ties therefore become an arbitrary but deterministic total order.

--------------------------------------------------------------------
2. Typed structural equivalence under identifier renaming  ()  
Definition: Build the bipartite incidence graph G() whose left nodes are ordered event positions, right nodes are (object-type,local-id) pairs, edges labelled with the object type.  
    there exists a bijection  between the object sets of equal type that  
  a) preserves the “external” flag,  
  b) makes the labelled graphs isomorphic, and  
  c) keeps the  order of events.  
Invariants kept:  
  • number of objects of every type (e.g. 2 Items, 1 Package, …)  
  • which events refer to which multiplicities of each type  
  • whether an object is external to the execution.  
Discarded: concrete local identifiers, O2O qualifiers, meaning of shared objects.  
Properties: reflexive, symmetric, transitive (category isomorphism).  
Concurrency: if events are timestamp-tied we allow any permutation consistent with the original order to be matched.

--------------------------------------------------------------------
3. Business-semantic equivalence  () – preferred  
Definition: Make a signature () =  
(#internal_Items, #internal_Packages, #internal_Deliveries,  
 #external_Items > 0 ?, #external_Packages > 0 ?, #external_Invoices > 0 ?,  
 #Invoices, #Payments,  
 flags: has_multiple_Packages, has_multiple_Deliveries,  
 has_partial_Payment(>1 payment for one invoice),  
 contains_replacement(qualifier=removed_before_dispatch),  
 contains_return(event label “Return Item”)).  

    ()=().  
Preserved: multiplicities that matter to logistics & finance, presence of external sharing, special lifecycle motifs (replacement, return).  
Discarded: exact timing, which item is in which specific package when that does not change the counted multiplicity, concrete ids.  
Properties: reflexive, symmetric, transitive (equality of tuples).  
Concurrency: irrelevant because  ignores order except for the existence of motifs; we detect motifs in any causal order.

--------------------------------------------------------------------
4. Lifecycle-path equivalence  () – optional  
Objects are followed through the classical “triangular” path OrderPackageDelivery and OrderInvoicePayment.  
Two executions are equivalent when both paths have the same cardinalities at every step, regardless of whether objects are shared.  
We omit further use for brevity.

## 2. Canonical signatures (preferred relation )

```python
def semantic_signature(execution):
    """
    execution : list[Event] where
       Event = {'act': str,
                'objs': {type: [id, ...]},
                'qual': set[(id1,id2,str)] }   # O2O qualifiers
    """
    internal = lambda o: not str(o).startswith("EXT")
    
    # Counters ------------------------------------------------------
    counts = {('Item','int'):0, ('Item','ext'):0,
              ('Package','int'):0, ('Package','ext'):0,
              ('Delivery','int'):0, ('Delivery','ext'):0,
              ('Invoice','int'):0, ('Invoice','ext'):0,
              ('Payment','int'):0, ('Payment','ext'):0}
    
    for ev in execution:
        for t, ids in ev['objs'].items():
            for oid in ids:
                key = (t, 'ext') if str(oid).startswith("EXT") else (t, 'int')
                counts[key] = counts.get(key, 0) + (1 if oid not in counts else 0)
    
    # Multiplicity flags -------------------------------------------
    has_multi_pkg      = counts[('Package','int')] > 1
    has_multi_dlv      = counts[('Delivery','int')] > 1
    has_partial_pay    = counts[('Payment','int')] > 1
    has_replacement    = any(q[2]=='removed_before_dispatch' for ev in execution
                                                        for q in ev.get('qual',set()))
    has_return         = any(ev['act']=='Return Item' for ev in execution)
    
    sig = (counts[('Item','int')],
           counts[('Package','int')],
           counts[('Delivery','int')],
           counts[('Item','ext')]>0,
           counts[('Package','ext')]>0 or counts[('Delivery','ext')]>0,
           counts[('Invoice','ext')]>0,
           counts[('Invoice','int')],
           counts[('Payment','int')],
           has_multi_pkg,
           has_multi_dlv,
           has_partial_pay,
           has_replacement,
           has_return)
    return sig
```

The tuple is sorted so that the equality operator `==` implements .  
All local identifiers are ignored; only the “EXT-” prefix survives as a Boolean.

## 4. Cluster interpretations

S0  ( = 2,1,1,0,0,0,1,1,…)  
Business: “happy path” – one parcel, one trip, one invoice, fully paid.  
Opportunities: ideal automation benchmark, expected bulk volume.  
Risk: almost none; deviations show process disturbance.  
Poorly represented by: activity-sequence flattening hides multiplicities but still adequate; graph-only views cannot see whether the package is shared.  
Stability: very high; minor data repair (e.g. reorder events) keeps signature.

S1  ( … multi_pkg=True, multi_dlv=False)  
Behavior: picking split into several boxes but dispatched together.  
Risk: extra handling cost but no customer delay.  
Traditional flattening: would lose which items were in which box.  
Stable as long as packing remains split and delivery consolidated.

S2  (multi_pkg=True, multi_dlv=True, partial_pay=True)  
Behavior: back-order situation, cash collected per shipment.  
Risk: revenue leakage if second payment mis-matched.  
Flattened order-level log cannot show partial payment.  
Sensitive to data repair: merging payments would change cluster.

S3  (external objects in logistics)  
Behavior: co-packed orders to save transport cost.  
Risk: wrong attribution of damage or loss.  
Flattening hides foreign items completely.  
Any deletion of EXT-flags collapses S3 into S0.

S4  (external invoice)  
Behavior: consolidated billing (corporate group invoice).  
Risk: reconciliation problems, cash application complexity.  
Dropping ext-invoice flag pushes execution to S0.

S5  (contains_replacement=True)  
Behavior: item cancellation/replacement before shipment.  
Risk: stock accuracy and refund liability.  
Label-only views false-ly show perfect shipment.  
Ignoring qualifier merges it into S0.

S6  (contains_return=True, multi_pkg=True, multi_dlv=True)  
Behavior: return, quality check, re-dispatch.  
Risk: high cost, customer dissatisfaction.  
Flattened log hides that the same item travelled twice.  
Ignoring Return event merges into S2.

## 5. Borderline cases

1. X1 vs X2  
– : same (labels identical)  
–  & : same; identifier order is irrelevant.  
Only an extremely fine “id-order equivalence” would split them.

2. X1 vs X5  
– : same  
– : different (external item & package flagged)  
– : different because  flag `#external_Items>0` is set only for X5  
A definition that ignores externality would wrongly merge them.

3. X1 vs X6  
– : different (shared Invoice flagged external)  
– : different (`external_Invoice` flag)  
However, a structural relation that treats invoices as mere objects but
ignores externality would merge them.

4. X1 vs X7  
– : same (qualifier not in graph)  
– : different (`contains_replacement=True`)  
Therefore graphs are identical although business meaning changes.

5. X3 vs X4  
– : different (second Dispatch & extra Payment)  
– : different multiplicities  
– : different (multi_dlv / partial_pay flags)  
But a coarser “multi-package equivalence” that ignores delivery count would merge them.

6. X4 vs X8  
Both have two deliveries.  
– : different because X8 has Return events and repack with new package id.  
– : different (`contains_return` flag).  
If Return events were dropped, both would fall into the same cluster.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py’s exact clustering keeps:  
– full event order,  
– every raw object identifier and its entire incident set.  
Therefore X1 and X2 are non-equivalent because item ids differ.

Raw ids make clusters too fine: renaming any object explodes clusters.

Canonicalisation strategy:

```python
from pm4py.objects.ocel import cluster_equivalent_ocel as ceo

# 1) collapse local ids -------------------------------------------
mapping = {}      # {(type,old_id) : new_id(int)}
def canon_id(tp, oid):
    if str(oid).startswith("EXT"):          # keep externals
        return oid
    if (tp, oid) not in mapping:
        mapping[(tp, oid)] = f"{tp}_{len([k for k in mapping if k[0]==tp])}"
    return mapping[(tp, oid)]

ocel_canon = ocel.copy()
for ev in ocel_canon.events:
    for t, ids in ev['objects'].items():
        ev['objects'][t] = [canon_id(t,i) for i in ids]

# 2) run pm4py clustering -----------------------------------------
clusters = ceo.get_equivalent_executions(ocel_canon,
                                         lead_object_type="Order",
                                         max_objs=5000)

# 3) post-aggregate to semantic clusters --------------------------
sem_clusters = {}
for cid, executions in clusters.items():
    sig = semantic_signature(executions[0])     # all share the same sig
    sem_clusters.setdefault(sig, []).extend(executions)
```

Exact equivalence is preferable for:  
– conformance checking of mined models,  
– debugging data extraction,  
– provenance auditing.

With large `max_objs` or highly connected OCEL the number of exact clusters can explode; semantic post-aggregation prevents this.

## 7. Robustness analysis

1. Ignore O2O qualifiers  X7 merges into S0, Return motif lost in X8; replacement and returns vanish.  
2. Ignore external objects  S3 and S4 collapse into S0; cross-order sharing invisible.  
3. Collapse repeated same-label events  X4 would look like X1 (payments merged), X3 loses second Pack flag; clusters S1, S2 melt.  
4. Treat Pack & Dispatch order as partial  X3 and X4 might swap Pack/Dispatch ordering without affecting ; activity-sequence clusters become coarser.  
5. Model payment amount attribute instead of multiplicity  X4 could record one payment of amount = sum(M41,M42); then it would switch from partial pay to baseline cluster.

## 8. Limitations and recommendation

• Compliance monitoring needs the finest view that still ignores benign id renaming  .  
• Operational segmentation (workload routing, KPI dashboards) should use  because it groups by logistic/financial effort.  
• Root-cause analysis profits from even coarser lifecycle-path equivalence to bring together rare deviations (returns, cancellations).  
• Descriptive reporting for management uses activity-sequence clusters: simple, easy to explain.

No single equivalence performs best everywhere:  
– Too fine  information overload;  
– Too coarse  hides actionable variance.  
A layered toolbox, starting with pm4py exact clusters and ending with business-semantic aggregation, gives the best of both worlds.
