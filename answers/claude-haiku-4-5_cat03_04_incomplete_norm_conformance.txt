# NORMATIVE CONFORMANCE ANALYSIS: OBJECT-CENTRIC PROCESS

## 1. Conformance semantics

**Forbidden behavior** is a strict logical negation: a relation marked forbidden must not exist, ever. Under closed-world assumption for this relation, its presence constitutes a violation. Evidence is binary: presence or absence.

**Missing mandatory behavior** is absence of a required relation where its scope applies. A scope applies when: the object type and event triggering condition are satisfied. Under closed-world assumption for mandatory relations within stated scope, absence is a violation—unless the abstraction (e.g., directly-follows vs. eventually-follows) is mismatched or the scope condition is ambiguous.

**Unexpected but unregulated behavior** is a relation not addressed by the norm. Under open-world assumption (default for all unspecified and unaddressed relations), absence of normative coverage does not indicate violation. Its presence is neither compliant nor non-compliant; it is outside the norm's jurisdiction.

**Typical-pattern absence** occurs when a relation marked typical is observed less frequently than expected. Norms marked typical explicitly permit exceptions. Absence does not violate; presence is expected but neither mandatory nor exclusive.

**Likely data-quality error** arises when:
- A relation contradicts a forbidden rule and is implausible given operational context (e.g., a sensor-stream event linked to an Invoice via ID reuse);
- An event relation lacks expected context (e.g., a Record Payment event without an Invoice in a system requiring labeling for unapplied cash);
- An edge exists with very low weight in a deterministic lifecycle (e.g., 1 of 200).

**Abstraction mismatch** occurs when the norm specifies a logical relation (e.g., eventually-follows) but the observed model enforces a stricter form (directly-follows). A 2% gap in `Create Order -> Validate Order` (98 of 100) is evidence of either unrecorded intermediate events or scope boundary issues, not necessarily violation.

**Insufficient evidence** means the summary does not provide enough detail to classify with confidence. For instance, the two Orders missing `Create Order -> Validate Order` may have unrecorded validation; the summary does not distinguish between "validation never occurred" and "validation was not logged in the summative trace."

**Open-world vs. closed-world:** The norm explicitly restricts closed-world to:
- Forbidden relations (T6, E10, N3): these must never occur.
- Mandatory columns within stated scopes (N1, N4, E1–E8): these must occur when their scope's triggering condition holds.

All other relations are open-world. Absence of an unspecified relation is **not** a compliance statement.

## 3. Detailed reasoning by model family

### OC-DFG (Object-Centric Directly-Follows Graph)

**What it can establish:** OC-DFG captures the causal sequence of events within an object type's lifecycle. It can detect:
- Mandatory sequences that are missing (e.g., an Order created but never validated).
- Forbidden sequences that are present (e.g., Cancel Order followed by Dispatch).
- Typical sequences that deviate significantly from expected rates.

**What it cannot establish:**
- Whether an intermediate event was unrecorded or omitted (abstraction problem).
- Whether an absence is due to process variance or data loss.
- The causal intent: did the business deliberately skip a step, or was it an error?
- Branching behavior: OC-DFG is linear; it does not capture "or" logic (e.g., Validate Order -> {Issue Invoice OR Close Order}).

**How counts and scopes affect interpretation:**

The norm N1 (`Create Order -> Validate Order`) is marked **mandatory** with scope "every newly created standard Order." The observation is 98 of 100. This is close but not 100%. Under a strict closed-world reading, 2 violations exist. However:

1. **Abstraction mismatch:** N1 specifies an eventually-follows expectation ("should eventually enter validation") but OC-DFG reports directly-follows. If an Order was validated but intermediate events (e.g., an internal queue step or manual review) were not recorded, the directly-follows edge is broken despite the logical mandate being satisfied.

2. **Scope ambiguity:** "Standard Order" is undefined. The 2 missing Orders might be non-standard (e.g., emergency orders, test Orders). No metadata confirms this, so we flag it as needing verification.

3. **Observation completeness:** The additional context notes that unrecorded review events may explain the gap. This is plausible.

**Conclusion for N1:** Severity Medium, Confidence Medium. Requires investigation; cannot be dismissed as a violation based on the summary alone.

For **N3** (`Cancel Order -> Dispatch Package` forbidden): 2 Orders show this sequence. This is a **critical violation** because:
- The norm is explicitly forbidden (closed-world).
- There is no scope exception ("applies to all Orders").
- Allowing cancellation + dispatch creates a business-logic violation: the customer would receive a package for a cancelled order.

This must be investigated immediately.

For **N2** (`Validate Order -> Close Order` typical): 83 of ~100 Orders close after validation; others enter invoicing workflows instead. This is **benign** because:
- The norm marks it typical, explicitly permitting exceptions.
- The branching is realistic: not all Orders proceed identically.
- No closed-world assumption applies.

### OTG (Object-Type Graph)

**What it can establish:**
- Whether object-interaction edges (e.g., `(Order, object_interaction, Item)`) are present and their cardinality.
- Forbidden co-occurrence rules (e.g., `(Order, object_cobirth, Payment)` is forbidden).
- Mandatory linkages required for certain operations.

**What it cannot establish:**
- Direction: is it Order  Item or Item  Order?
- Multiplicity rules: must an Order have at least 1 Item?
- Temporal constraints: when must the edge exist (before, during, after)?
- Whether an edge is "missing" (absence in an open-world sense) or "not yet created" (temporal).

**How it relates to ET–OT and mandatory scope:**

E2 states: "Every Add Item event" must include an Order (mandatory ET–OT). E3 states: "Every Add Item event" must include an Item (mandatory ET–OT). Together, T1 (mandatory OTG) requires `(Order, object_interaction, Item)` for Add Item interactions. The observation shows 1450 Add Item events, 1448 linking to Order, 1450 linking to Item. The 2-event discrepancy is low-severity but worth resolving.

For **T6** (`(Order, object_cobirth, Payment)` forbidden): 1 edge is observed. **Critical violation.** Cobirth means both objects were created in the same event. This violates the intended segregation: payments should not be born from order creation. This could indicate:
- A data-entry workflow error (payment pre-created).
- A timestamp precision issue (both recorded at the same second, but not truly simultaneous).
- A genuine system bug.

**Severity:** Critical. This requires immediate audit.

For **T2** (`(Package, object_interaction, Delivery)` mandatory): 200 observed. All externally shipped Packages must have Delivery. The OC-DFG summary shows 2 Dispatch Package events without a Delivery relation, but both have a carrier attribute. **Interpretation:** The Delivery object may not yet be created in the snapshot (asynchronous fulfillment), or it exists but is not linked in this extract. **Severity:** Medium. Requires timestamp cross-check.

### ET–OT (Event Type – Object Type)

**What it can establish:**
- Whether an event type creates, modifies, or links to an object type.
- Mandatory associations (every event of type X must involve object type Y).
- Forbidden associations (no event of type X shall involve object type Y).

**What it cannot establish:**
- The cardinality: how many objects of type Y are involved in X?
- Whether the object is created (birth) or just linked (interaction).
- The order of object involvement.

**E10** (`Sensor Heartbeat -> Invoice` forbidden): 1 observed. **Critical violation (data-quality origin).** Sensor events must never touch financial objects. The additional context notes this is a suspected join error on reused numeric IDs. **Confidence: Very high that this is a data error.** **Immediate action:** Delete the edge; validate ID namespaces.

**E6** (`Dispatch Package -> Delivery` mandatory): 198 of 200 Dispatch Package events. Expected 200. **Gap of 2.** The additional context explains: both have a carrier attribute but no Delivery object link. This suggests either:
- Delivery objects are created asynchronously and not yet visible.
- The Delivery object is represented differently (e.g., as an event attribute instead of an object).

**Severity:** Medium. Requires clarification of whether Delivery is always a separate object or sometimes embedded in the Package.

**E8** (`Record Payment -> Invoice` mandatory, except unapplied cash): 93 Record Payment events, 92 linked to Invoice, 1 unlinked. The norm explicitly allows exceptions for unapplied cash, but no event is labeled as such. **Severity:** High. Requires finance reconciliation to confirm whether the 1 payment is legitimately unapplied.

# Call PM4Py conformance functions
ocdfg_conformance = pm4py.conformance_ocdfg(ocel, discovered_ocdfg, norm_ocdfg)

etot_conformance = pm4py.conformance_etot(ocel, discovered_etot, norm_etot)

# Semantic classification layer: overlay status labels and severity
def classify_conformance(pm4py_result, norm_spec, model_type):
    """
    Apply semantic status (mandatory/forbidden/typical/unspecified) and severity
    to PM4Py's graph-based conformance output.
    """
    classified = {
        'model_type': model_type,
        'pm4py_output': pm4py_result,
        'violations': [],
        'benign_deviations': [],
        'conforming': [],
        'unregulated': [],
    }
    
    for norm_item in norm_spec['edges'] if model_type != 'OCDFG' else norm_spec['relations']:
        status = norm_item['status']
        observed_count = pm4py_result.get(norm_item, 0)  # Simplified access
        
        if status == 'forbidden' and observed_count > 0:
            classified['violations'].append({
                'relation': norm_item,
                'observed_count': observed_count,
                'severity': 'critical',
                'action': 'immediate audit required'
            })
        elif status == 'mandatory' and observed_count == 0:
            classified['violations'].append({
                'relation': norm_item,
                'observed_count': 0,
                'severity': 'high',
                'action': 'investigate scope and abstraction'
            })
        elif status == 'typical' and observed_count == 0:
            classified['benign_deviations'].append({
                'relation': norm_item,
                'observed_count': 0,
                'severity': 'low',
                'rationale': 'typical allowance for exceptions'
            })
        elif status == 'unspecified':
            classified['unregulated'].append({
                'relation': norm_item,
                'observed_count': observed_count,
                'severity': 'none',
                'rationale': 'outside norm scope'
            })
        else:
            classified['conforming'].append({
                'relation': norm_item,
                'observed_count': observed_count,
            })
    
    return classified

# Apply semantic layer
ocdfg_classified = classify_conformance(ocdfg_conformance, norm_ocdfg, 'OCDFG')
otg_classified = classify_conformance(otg_conformance, norm_otg, 'OTG')
etot_classified = classify_conformance(etot_conformance, norm_etot, 'ET–OT')

# Print results with severity and justification
print("\n=== OCDFG CONFORMANCE ===")
print(f"Violations: {len(ocdfg_classified['violations'])}")
for v in ocdfg_classified['violations']:
    print(f"  [{v['severity']}] {v['relation']} ({v['observed_count']})")

print(f"\nBenign deviations: {len(ocdfg_classified['benign_deviations'])}")
for b in ocdfg_classified['benign_deviations']:
    print(f"  {b['relation']} - {b['rationale']}")

print(f"\nUnregulated: {len(ocdfg_classified['unregulated'])}")

print("\n=== OTG CONFORMANCE ===")
print(f"Violations: {len(otg_classified['violations'])}")
for v in otg_classified['violations']:
    print(f"  [{v['severity']}] {v['relation']} ({v['observed_count']})")

print("\n=== ET–OT CONFORMANCE ===")
print(f"Violations: {len(etot_classified['violations'])}")
for v in etot_classified['violations']:
    print(f"  [{v['severity']}] {v['relation']} ({v['observed_count']})")

   - Update the norm with explicit scope rules.
