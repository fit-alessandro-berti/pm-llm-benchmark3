# 1. Objectives and constraints

The policy should be treated as a **multi-objective decision rule**, not as a single throughput optimizer. The goal is to assign each pending activity to a safe, explainable resource choice while making the trade-offs visible.

**Assumptions used for this design**

1. **Urgent and high priority** are both treated as “high-priority” for the rule “no high-priority case below skill level 2 unless supervised.”
2. Because no expected activity durations are provided, **hours remaining today** is used as a capacity warning, not as a precise feasibility guarantee. In deployment, expected service times should be learned from the event log.
3. A **supervised pair** means the lower-skill worker may prepare, investigate, or perform bounded work, but the named supervisor is accountable for the decision and final sign-off.
4. For **Security Review**, a resource with skill 0 may only shadow or prepare non-decision material. The accountable performer must be skill 3, or skill 1–2 under explicit supervision by R7_Gita or R8_Hugo.
5. Assignment count is counted mainly on the accountable performer, but supervision and shadowing should still be monitored as workload.

**Hard safety and compliance constraints**

| Constraint type      | Rule                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Basic authorization  | Skill level 0 means “not allowed” as accountable performer.                                                                                            |
| High-priority safety | Urgent/high cases cannot go to skill level 1 unless there is explicit supervision.                                                                     |
| Security Review      | Must be done by skill 3, or by skill 1–2 under R7_Gita or R8_Hugo supervision.                                                                         |
| Final Approval       | Must be finalized by skill 2–3. Skill 1 may prepare only, not finalize.                                                                                |
| Batch Quality Check  | Quality Check may be batched only for normal/low-priority cases with SLA time remaining above 24h.                                                     |
| Assignment cap       | No resource should receive more than 4 new accountable assignments in the decision batch.                                                              |
| Auditability         | Every non-obvious assignment must have a logged `assignment_reason`, especially supervision, continuity exceptions, and high-overtime-risk exceptions. |

**Strong preference constraints and trade-offs**

| Objective         | Preference                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SLA protection    | Urgent and near-deadline work is routed first, with stronger skill requirements and less training experimentation.                                              |
| Skill match       | Prefer skill 3 for high-risk work, skill 2–3 for normal work, and skill 1 only for training or supervised work.                                                 |
| Continuity        | Keep the current owner when handover cost is high, reassignment count is high, or complexity is high, unless the owner’s skill is too weak without supervision. |
| Workload fairness | Prefer lower open-case load and more hours remaining. Avoid giving new work to high-overtime-risk resources unless the continuity/SLA argument is strong.       |
| Training          | At least 20% of normal/low-priority assignments should support documented training priorities when SLA risk allows.                                             |
| Resilience        | Avoid routing everything to the same specialists, especially Security and Approval specialists. Preserve backup capacity and grow supervised capability.        |
| Throughput        | Reduce waiting time through batching, low handover where safe, and avoiding bottlenecks, but not at the cost of unsafe skill mismatch.                          |

The historical evidence matters: cases with more than two reassignments have materially higher rework and appeal rates; changing owner on high-complexity cases adds waiting; keeping a weakly skilled owner also adds service time and rework. The policy therefore should not blindly preserve ownership or blindly route to specialists.

# 2. Assignment policy

A practical policy can be implemented as a **rule-constrained scoring algorithm**.

```text
For each decision batch:

1. Enrich queue
   For each case:
     - read next activity, required skill, priority, SLA time remaining,
       complexity, current owner, reassignment count, handover cost band
     - compute SLA urgency score
     - classify case as immediate / same-day / routine / deferrable

2. Order cases
   Sort primarily by:
     a. SLA urgency score
     b. priority
     c. complexity
     d. handover risk and reassignment count

3. For each case in sorted order:
   A. Build eligible candidate set
      - remove resources with skill 0 for accountable performance
      - apply special rules:
          Security Review:
            allow skill 3 directly
            allow skill 1-2 only with R7_Gita or R8_Hugo supervision
            allow skill 0 only as non-accountable shadowing
          Final Approval:
            allow skill 2-3 as final approver
            allow skill 1 only for preparation
          High/urgent work:
            allow skill 1 only with explicit supervision
          Quality batching:
            allow batch only if priority normal/low and SLA > 24h
      - remove candidates already at 4 new accountable assignments
      - strongly penalize or block high-overtime-risk resources unless
        SLA or continuity makes the exception auditable

   B. Score each candidate or supervised pair
      Total score =
        SLA suitability
        + skill-match score
        + continuity score
        + workload/capacity score
        + training score
        + resilience score
        - handover penalty
        - overtime penalty
        - bottleneck penalty

   C. Select highest explainable candidate
      - if current owner is within a small tolerance of the top score,
        keep continuity
      - if a specialist is scarce and the case is routine, prefer a competent
        non-specialist or supervised trainee
      - if the best candidate is high-overtime-risk, require an exception reason

   D. Log decision
      Store:
        assigned resource
        supervisor, if any
        assignment_reason
        score components
        rejected higher-throughput option, if relevant
        risk_to_monitor

4. Batch and sequence
   - batch only eligible Quality Check cases
   - sequence urgent cases explicitly
   - keep normal/low training cases behind urgent SLA work
```

One explainable scoring scheme is:

```text
priority_score:
  urgent = 1.00
  high   = 0.75
  normal = 0.35
  low    = 0.10

time_pressure:
  SLA <= 4h   = 1.00
  SLA <= 8h   = 0.80
  SLA <= 24h  = 0.50
  SLA <= 48h  = 0.20
  otherwise   = 0.00

sla_urgency =
  0.45 * priority_score
+ 0.35 * time_pressure
+ 0.20 * case_complexity
```

Skill-match scoring:

```text
skill 3 = strong positive
skill 2 = positive
skill 1 = allowed only for low-risk/training or supervised work
skill 0 = not allowed as accountable performer

For urgent/high cases:
  skill 1 is acceptable only if supervised and explicitly logged.
```

Continuity and handover scoring:

```text
continuity bonus:
  + high if candidate is current owner
  + moderate if same team and low handover disruption
  + extra if reassignment_count >= 2

handover penalty:
  none   = 0
  low    = small
  medium = meaningful
  high   = large

Penalty is amplified by:
  - high complexity
  - reassignment_count >= 2
  - historical evidence of rework/appeal after repeated handovers
```

Workload and overtime scoring:

```text
prefer:
  - fewer current open cases
  - more hours remaining today
  - lower overtime risk
  - fewer new assignments in this batch

high-overtime-risk resource:
  avoid unless:
    - urgent SLA risk requires it, or
    - avoiding a harmful reassignment is more important,
    - and the reason is logged.
```

Training scoring:

```text
training bonus applies only when:
  - priority is normal or low
  - SLA risk is acceptable
  - training priority matches the required skill, or the case is explicitly
    marked as a training candidate
  - supervision is available when needed
  - the trainee is not already high overtime risk

Training must never be hidden as normal production routing.
```

Resilience scoring:

```text
penalize:
  - routing all Security Review work to one specialist
  - routing all Final Approval work to one approver
  - using scarce Security specialists for routine non-security work
    when competent alternatives exist
  - creating a single point of failure in a team

reward:
  - safe supervised work that grows backup capability
  - distribution across teams where handover cost is low
  - keeping specialists available for urgent or high-risk cases
```

Tie-breaking:

1. Safer skill and compliance choice.
2. Current owner if handover cost or reassignment count is material.
3. Lower overtime risk.
4. Lower current open cases and more hours remaining.
5. Better team/working-together history.
6. Stable rotation rule to prevent hidden favoritism.

Exception handling:

```text
If no compliant candidate exists:
  - escalate to team lead
  - split work into preparation + final sign-off if allowed
  - record assignment_reason = "exception:no_compliant_capacity"
  - do not silently route to an unqualified resource

If SLA conflict exists for one worker:
  - sequence explicitly
  - define backup trigger, e.g. "if not started within 30 minutes,
    transfer to backup with structured handover"
```

# 5. Explanation to workers

Today’s assignment plan is designed to protect customers, avoid unnecessary rework, and keep workload sustainable.

Some cases are being kept with their current owners because the case history matters. For example, when a case has already been reassigned several times or has high handover cost, moving it again can create more waiting and more rework. That is why C007 stays with Celine and C016 stays with Eva.

Some urgent or regulated tasks need specialist involvement. Security Review and Final Approval have stricter rules, so the policy does not assign them as ordinary queue items. In C001, Celine keeps the case context, but Hugo supervises and signs off because the case is urgent and security-sensitive.

The policy is also trying not to overload people who already have high workload or overtime risk. Bruno and Iris are not being given additional accountable work in this batch because their current workload and overtime risk are high, not because of a negative judgment about their skill.

Training is included only where it is safe. Amal gets a supervised diagnosis opportunity on C009 because it matches her development priority and the SLA gives enough room. Jonas shadows C015 for security development, but Hugo remains accountable because Jonas is not yet authorized for Security Review.

Supervision is meant as a safety net and learning mechanism, not as punishment. Workers and team leads can override an assignment when they know something the system does not know, but the override reason should be logged so the process can be audited and improved.

Good audit practice would compare indicators by `assignment_reason`, for example:

* `continuity:high_handover`
* `sla:urgent_specialist`
* `training:supervised`
* `batch:quality`
* `exception:overtime_continuity`
* `override:human_lead`

That makes the policy explainable after deployment, not only at assignment time.

# 7. PM4Py implementation sketch

```python
import pandas as pd
import numpy as np
import pm4py

# ---------------------------------------------------------------------
# 1. Load and format event log
# ---------------------------------------------------------------------

df = pd.read_csv("service_process_event_log.csv")

df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)
df["sla_deadline"] = pd.to_datetime(df["sla_deadline"], utc=True)

log = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# ---------------------------------------------------------------------
# 2. Resource and organizational mining
# ---------------------------------------------------------------------

# Handover-of-work network: who receives work after whom within a case?
how_net = pm4py.discover_handover_of_work_network(
    log,
    resource_key="org:resource"
)

# Working-together network: who tends to work on the same cases?
wt_net = pm4py.discover_working_together_network(
    log,
    resource_key="org:resource"
)

# Activity-based resource similarity: useful for finding backup resources
# and checking whether training changes actual behavior.
res_sim = pm4py.discover_activity_based_resource_similarity(
    log,
    resource_key="org:resource",
    activity_key="concept:name"
)

# Organizational roles discovered from event behavior.
roles = pm4py.discover_organizational_roles(
    log,
    resource_key="org:resource",
    activity_key="concept:name"
)

# Optional SNA visualization.
pm4py.save_vis_sna(how_net, "handover_network.png")
pm4py.save_vis_sna(wt_net, "working_together_network.png")

# ---------------------------------------------------------------------
# 3. Waiting time, service time, and performance
# ---------------------------------------------------------------------

# Adds case-level service/waiting-time features where supported by the log.
log_with_times = pm4py.insert_case_service_waiting_time(log)

# Activity service times can be used to replace the simplifying assumption
# that "hours remaining today" is only a rough capacity indicator.
service_time = pm4py.get_service_time(
    log,
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# Performance DFG: where time is spent between activities.
perf_dfg = pm4py.discover_performance_dfg(
    log,
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# Variants: useful for detecting rework loops and paths associated with
# particular assignment reasons.
variants = pm4py.get_variants(
    log,
    activity_key="concept:name",
    case_id_key="case:concept:name"
)

# ---------------------------------------------------------------------
# 4. Focused filters for audit
# ---------------------------------------------------------------------

security_log = pm4py.filter_event_attribute_values(
    log,
    "required_skill",
    ["Security"],
    retain=True
)

approval_log = pm4py.filter_event_attribute_values(
    log,
    "required_skill",
    ["Approval"],
    retain=True
)

quality_log = pm4py.filter_event_attribute_values(
    log,
    "concept:name",
    ["Quality Check"],
    retain=True
)

# Cases whose total performance exceeds a 72-hour SLA, if the whole process
# is measured from case start to completion.
slow_cases = pm4py.filter_case_performance(
    log,
    min_performance=72 * 3600
)

# Batch discovery, especially for Quality Check.
batches = pm4py.discover_batches(
    log,
    activity_key="concept:name",
    resource_key="org:resource",
    timestamp_key="time:timestamp"
)

# ---------------------------------------------------------------------
# 5. Derived audit indicators in pandas
# ---------------------------------------------------------------------

df_sorted = df.sort_values(["case:concept:name", "time:timestamp"]).copy()

# Handover indicator
df_sorted["prev_resource"] = (
    df_sorted.groupby("case:concept:name")["org:resource"].shift(1)
)

df_sorted["handover"] = (
    df_sorted["prev_resource"].notna()
    & df_sorted["org:resource"].notna()
    & (df_sorted["org:resource"] != df_sorted["prev_resource"])
)

handover_rate_by_activity = (
    df_sorted.groupby("concept:name")["handover"]
    .mean()
    .sort_values(ascending=False)
)

handover_rate_by_case = (
    df_sorted.groupby("case:concept:name")["handover"]
    .sum()
    .rename("handover_count")
)

# SLA miss indicator
case_completion = (
    df_sorted.groupby("case:concept:name")
    .agg(
        last_event_time=("time:timestamp", "max"),
        sla_deadline=("sla_deadline", "max"),
        max_reassignment_count=("reassignment_count", "max"),
        max_complexity=("case_complexity", "max")
    )
)

case_completion["sla_missed"] = (
    case_completion["last_event_time"] > case_completion["sla_deadline"]
)

sla_miss_rate = case_completion["sla_missed"].mean()

# Rework / appeal after assignment.
# "Appeal" may or may not exist as an activity in the real log.
failure_activities = {"Rework Correction", "Appeal", "Reject"}

case_has_failure = (
    df_sorted.assign(is_failure=df_sorted["concept:name"].isin(failure_activities))
    .groupby("case:concept:name")["is_failure"]
    .max()
)

# Assignment reason quality
assignment_audit = df_sorted[df_sorted["assignment_reason"].notna()].copy()

rework_by_assignment_reason = (
    assignment_audit[["case:concept:name", "assignment_reason"]]
    .drop_duplicates()
    .merge(case_has_failure.rename("later_failure"), on="case:concept:name", how="left")
    .groupby("assignment_reason")["later_failure"]
    .mean()
    .sort_values(ascending=False)
)

# ---------------------------------------------------------------------
# 6. Skill-mismatch audit
# ---------------------------------------------------------------------

skill_matrix = pd.DataFrame([
    # resource, team, overtime risk, training priority,
    # Eligibility, Diagnosis, Negotiation, Security, Approval, Quality, Rework
    ["R1_Amal",   "A",       "medium", "diagnosis",   3, 1, 2, 0, 1, 2, 2],
    ["R2_Bruno",  "A",       "high",   "quality",     3, 0, 2, 0, 2, 1, 1],
    ["R3_Celine", "A",       "low",    "negotiation", 2, 3, 1, 1, 0, 2, 3],
    ["R4_David",  "B",       "high",   "approval",    1, 3, 0, 2, 0, 1, 3],
    ["R5_Eva",    "B",       "medium", "security",    2, 2, 3, 0, 2, 1, 2],
    ["R6_Farid",  "B",       "low",    "diagnosis",   1, 1, 3, 0, 3, 2, 1],
    ["R7_Gita",   "Risk",    "medium", "none",        0, 1, 0, 3, 1, 2, 2],
    ["R8_Hugo",   "Risk",    "low",    "approval",    0, 2, 0, 3, 0, 3, 3],
    ["R9_Iris",   "Quality", "high",   "negotiation", 1, 1, 1, 1, 0, 3, 3],
    ["R10_Jonas", "Quality", "low",    "security",    2, 1, 1, 0, 1, 3, 2],
], columns=[
    "org:resource", "team", "overtime_risk", "training_priority",
    "Eligibility", "Diagnosis", "Negotiation", "Security",
    "Approval", "Quality", "Rework"
])

skill_long = skill_matrix.melt(
    id_vars=["org:resource", "team", "overtime_risk", "training_priority"],
    var_name="required_skill",
    value_name="skill_level"
)

audit = df_sorted.merge(
    skill_long,
    on=["org:resource", "required_skill"],
    how="left"
)

priority_high = audit["case_priority"].isin(["urgent", "high"])

audit["has_supervision"] = (
    audit["assignment_reason"]
    .fillna("")
    .str.contains("supervised|sign-off|supervisor", case=False, regex=True)
)

audit["skill_mismatch"] = False

# Generic mismatch: skill 0 cannot be accountable.
audit.loc[audit["skill_level"].fillna(0) == 0, "skill_mismatch"] = True

# Urgent/high below skill 2 requires supervision.
audit.loc[
    priority_high
    & (audit["skill_level"] < 2)
    & (~audit["has_supervision"]),
    "skill_mismatch"
] = True

# Security rule.
security = audit["required_skill"].eq("Security")
security_skill3 = audit["skill_level"].eq(3)
security_supervised = (
    audit["skill_level"].isin([1, 2])
    & audit["has_supervision"]
    & audit["assignment_reason"].fillna("").str.contains("R7_Gita|R8_Hugo", regex=True)
)

audit.loc[
    security & ~(security_skill3 | security_supervised),
    "skill_mismatch"
] = True

# Final Approval rule.
approval = audit["required_skill"].eq("Approval")
audit.loc[
    approval & (audit["skill_level"] < 2),
    "skill_mismatch"
] = True

skill_mismatch_rate = audit["skill_mismatch"].mean()

# ---------------------------------------------------------------------
# 7. Training assignment share
# ---------------------------------------------------------------------

normal_low = audit["case_priority"].isin(["normal", "low"])

audit["training_supported"] = (
    normal_low
    & (
        audit["training_priority"].str.lower().eq(audit["required_skill"].str.lower())
        | audit["assignment_reason"].fillna("").str.contains("training|shadow", case=False)
    )
)

training_share = (
    audit.loc[normal_low, "training_supported"].mean()
)

# ---------------------------------------------------------------------
# 8. Overtime exposure
# ---------------------------------------------------------------------

overtime_exposure = (
    audit[audit["assignment_reason"].notna()]
    .groupby(["overtime_risk", "case_priority"])
    .size()
    .rename("assignments")
    .reset_index()
)

high_overtime_exceptions = audit[
    (audit["overtime_risk"] == "high")
    & audit["assignment_reason"].notna()
]

# ---------------------------------------------------------------------
# 9. Specialist bottleneck indicators
# ---------------------------------------------------------------------

scarce_skills = audit[audit["required_skill"].isin(["Security", "Approval"])]

specialist_load = (
    scarce_skills.groupby(["required_skill", "org:resource"])
    .agg(
        events=("concept:name", "count"),
        cases=("case:concept:name", "nunique"),
        mismatch_rate=("skill_mismatch", "mean")
    )
    .reset_index()
)

# Waiting/service-time indicators should be joined from log_with_times
# or computed from activity start/complete timestamps if lifecycle data exists.

# ---------------------------------------------------------------------
# 10. Policy deviation audit
# ---------------------------------------------------------------------

# In production, store policy_score and selected_candidate_rank at assignment time.
# Then deviations can be audited without reconstructing the queue perfectly.

deviation_candidates = audit[
    audit["assignment_reason"].fillna("").str.contains("override|exception", case=False)
]

summary = {
    "sla_miss_rate": sla_miss_rate,
    "skill_mismatch_rate": skill_mismatch_rate,
    "training_share_normal_low": training_share,
    "handover_rate_by_activity": handover_rate_by_activity,
    "rework_by_assignment_reason": rework_by_assignment_reason,
    "specialist_load": specialist_load,
    "high_overtime_exceptions": high_overtime_exceptions[
        ["case:concept:name", "concept:name", "org:resource", "assignment_reason"]
    ]
}
```

For learning and recalibration, the same log should be used to estimate:

```text
expected_service_time(activity, skill_level, complexity_band)
expected_waiting_time(activity, resource, workload_snapshot)
probability_of_rework(activity, skill_level, handover_cost_band, reassignment_count)
probability_of_SLA_miss(priority, time_remaining, workload_snapshot, assignment_reason)
```

Those estimates can update the scoring weights periodically. The audit should not only ask “was the case fast?” but also “was the assignment safe, fair, explainable, and sustainable?”
