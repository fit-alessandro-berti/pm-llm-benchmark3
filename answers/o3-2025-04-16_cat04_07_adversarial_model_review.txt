# 1. Review Scope and Assumptions
We distinguish four main *intended* uses.

1. Exploration / discovery workshops – tolerate low precision; fitness > 0.95 and narrative clarity matter most.  
2. Operational monitoring dashboards – need moderate precision ( 0.75) to avoid alert fatigue; false negatives tolerated if labelled “unknown”.  
3. Formal compliance checking – require explicit representation of *all* binding rules (P1–P7); false negatives must be  1 %.  
4. Continuous-improvement simulation – require soundness and replayability, but can embed stochastic “noise” branches.

A single model cannot optimise all four.  Consequently:

• Model-S-style permissiveness is acceptable only for *Exploration*.  
• Compliance or monitoring must trade a few points of fitness for unambiguous semantics and auditable precision.

# 3. Adversarial Review of Model S
Strongest *pro* arguments  
• Excellent fitness and speed – good for fast prototyping.  
• One compact expression understandable by non-experts (score 4.4).  
• High generalisation lets analysts *discover* rare but legal behaviour.

Strongest *con* arguments  
• Ignores mandatory ordering – fails P2, P4.  
• Cannot enforce exactly-one approval (P5): both or none may appear.  
• Correction semantics missing (P6, P7).  
• Silent transitions hide which path was taken.  
• Low precision (0.584) implies many false positives in compliance use.

Undesirable or ambiguous traces still *accepted*:

1. Register, Manager Approval, Release               (violates mandatory checks)  
2. Register, Expedite, Approval, Release             (Expedite before checks)  
3. Register, Credit, Technical, Credit, Approval…   (repeated check w/o correction – P7)  
4. Register, Supplier, Technical, Credit, Approval… (Supplier before checks)  
5. Empty path after  in first +() branch (Register    Approval…) if tree parsed permissively.

The permissiveness comes mostly from the leading “+” (OR) with  children, not from deliberate noise-tolerance.

# 4. Adversarial Review of Model C
Strongest *pro* arguments  
• Enumerates only known frequent variants – high precision (0.941).  
• Explicit duplicate-check loop variant addresses P6 partially.  
• Easier to certify for specific customer codes because every path is listed.

Strongest *con* arguments  
• Branch enumeration = memorisation  poor hold-out fitness 0.744.  
• 33 duplicate labels hinder message correlation.  
• Adding a new combination (e.g., Supplier + Auto Approval) needs another full branch – brittle.  
• Expedite-after-Supplier variant missing (violates P4); Supplier optionality not attribute-guarded.  
• Auto Approval present only in one variant, always without Supplier – contradicts F4/B5.  
• Loop semantics forces *both* checks after every correction, obscuring “affected only” logic (F6).  
• Alignment runtime ×24 slower.  
• High precision could be merely an artefact of fitting every training trace literally.

# 6. Likely Metric Pathologies (ranked by impact)

1. Fitness inflation by optionalising mandatory activities (hits Model S).  
2. Positive-log-only precision – rewards memorisation (Model C).  
3. Train/hold-out split sensitivity – no seed, possible leakage.  
4. Alignment-cost parameter unknown – affects fitness/precision ordering.  
5. Generalisation rewarding permissiveness – favours Model S.  
6. Duplicate labels – may double-count in precision.  
7. Silent-transition inflation – hides non-compliance in Model S.  
8. Runtime confounded by hardware / Python settings.  
9. Stakeholder score methodology not reported – could be anchoring bias.

# 7. Third Alternative
We propose a *block-structured backbone + declarative guards*:

Formal description (pseudo-tree)

SEQ(
  Register Dossier,
  LOOP{           // 0+ corrections
    PAR{ Credit Check , Technical Review }   // order free, both mandatory
    OPT[ Supplier Review ]                   // will be guarded externally by “external_order” attribute
    OPT[ Expedite Review ] AFTER (CreditTech) BEFORE Approval
    XOR{ Manager Approval , Auto Approval }  // exactly one
  } REPEAT-IF( Correct Dossier )
  Release Order
)

Key semantics  
• The PAR block ends when both checks have *at least one* successful execution after the most recent correction.  
• Supplier Review is *required* iff case.attribute[“source”]==“external”. A simple Python guard implements it.  
• Expedite Review may occur at most once and only between completed mandatory checks and approval.  
• Correct Dossier sends flow back to the top of the PAR block.  
• A repeated check without an intervening Correct Dossier triggers a *violation* flag even though the trace can be replayed.

Limitations  
• Because “affected check” attribute is missing, both checks must be repeated after a correction (transparent but stricter).  
• Without the source attribute we conservatively *allow* missing Supplier Review but emit a warning.

## 7.1  PM4Py construction (minimal, self-contained)

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, ProcessTreeNode

def leaf(label):
    return ProcessTree(label=label, node_type=None)

# Build tree
register = leaf("Register Dossier")
credit   = leaf("Credit Check")
tech     = leaf("Technical Review")
supplier = leaf("Supplier Review")
expedite = leaf("Expedite Review")
mgr_app  = leaf("Manager Approval")
auto_app = leaf("Auto Approval")
correct  = leaf("Correct Dossier")
release  = leaf("Release Order")

# Parallel mandatory checks
par_checks = ProcessTree(operator=ProcessTreeOperator.PARALLEL)
par_checks.children = [credit, tech]

# Optional nodes (silent when skipped)
opt_supplier = ProcessTree(operator=ProcessTreeOperator.XOR)
opt_supplier.children = [supplier, ProcessTree(label="tau", node_type=ProcessTreeOperator.TAU)]

opt_expedite = ProcessTree(operator=ProcessTreeOperator.XOR)
opt_expedite.children = [expedite, ProcessTree(label="tau", node_type=ProcessTreeOperator.TAU)]

# Exactly-one approval
xor_approval = ProcessTree(operator=ProcessTreeOperator.XOR)
xor_approval.children = [mgr_app, auto_app]

# Body before possible correction
body = ProcessTree(operator=ProcessTreeOperator.SEQUENCE)
body.children = [par_checks, opt_supplier, opt_expedite, xor_approval]

# Loop around correction
loop = ProcessTree(operator=ProcessTreeOperator.LOOP)
loop.children = [body, correct, ProcessTree(label="tau", node_type=ProcessTreeOperator.TAU)]

# Full model
root = ProcessTree(operator=ProcessTreeOperator.SEQUENCE)
root.children = [register, loop, release]

model_third = root     # <- deliverable
```

## 7.2  External guards

def guard_supplier(case):
    if case.attributes.get("source") == "external":
        return "Supplier Review" in [e["concept:name"] for e in case]
    return True

Acceptance rule: a model is *rejected* for compliance if  
• any policy probe fails, or  
• fitness < 0.90 on test, or  
• precision < 0.75 on negative suite, or  
• unsoundness detected.

Comprehension protocol: five stakeholders each annotate a printed BPMN generated from the tree and answer ten multiple-choice questions; score is % correct.

# 10. Governance Recommendation
• Keep Model S **only** for exploratory workshops; label “NOT FOR COMPLIANCE”.  
• Retire Model C in its current enumerative form – maintenance cost outweighs precision.  
• Adopt the *Third Alternative* for monitoring and as the *baseline* compliance model **provided** it passes the validation experiments above and a domain expert signs off the Supplier-Review guard.

Short-term mitigation: route any trace failing a guard but replayable in the model to manual audit instead of outright rejection.

# 11. Dissenting View
(188 words)

The board is placing significant faith in an un-proven “third alternative” that, while architecturally cleaner, is still speculative.  We have not yet run it on the full historic corpus, nor on the incoming streaming data from the order system.  By relaxing the Supplier-Review requirement to an *external* guard evaluated post-hoc, we introduce a second mechanism whose failure could silently let external orders escape Supplier Review—precisely the control P3 was meant to guarantee.  Moreover, the loop forces both mandatory checks after a correction, contradicting business intent that only the *affected* check should re-run.  This could cause valid traces to be flagged, eroding user trust in the first weeks of deployment.  Finally, all metrics and probes remain alignment-based; they do not measure *data-value* conditions inside activities (e.g., credit score thresholds).  Approving the model now risks another re-engineering cycle in six months.

Evidence that would change this view: (i) full-scale replay on 12 months of data with < 0.5 % unexplained deviations; (ii) a tested attribute-based sub-process for partial re-checks; (iii) penetration test proving that mis-configuration of the external guard cannot bypass Supplier Review.
