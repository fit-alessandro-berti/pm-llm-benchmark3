The sharp June deterioration coincides with three distinct changes in measurement. Renaming classification creates an apparent missing `Classify` and extra `Risk Screen`; gateway routing adds an event absent from the tree; ingestion timestamps can place notification before decision. In the supplied staged analysis, correcting these elements raises fitting traces from 32% to 89%. That pattern strongly favors a measurement contribution, although the increments depend on their order, the alignment settings, and the validity of each repair. The changes do not prove that all underlying actions stayed the same.

In August the policy adds a real sign-off requirement while the normative tree remains unchanged. A valid sign-off can therefore appear as an extra log move. The optional-sign-off candidate improves fitness, but its greater permissiveness also permits missing sign-off on high-value cases and sign-off on any case; fitness alone cannot demonstrate policy adherence. Claim value, effective date, and authorization must be checked separately.

Enhanced-review traces without a recorded compliance check remain ambiguous: a check might have been bypassed, omitted from the source, lost in extraction, or recorded under a different identity. Overrides are reported to be real actions and cannot automatically be discarded as technical noise. Stable appeal, approval, and incident summaries neither prove the deviations are data errors nor rule out noncompliance: outcomes can lag, depend on case mix, or fail to capture undetected violations. The 11 screenshots support an ordering defect in those examined cases, not a proven correction for all 70.

## 6. PM4Py reproduction and model-comparison code

The supplied inputs are aggregated trace strings, with no timestamps, case IDs, claim values, resources, or source sequence. The code uses the order given and does not pretend to reconstruct the source-sequence repair. It compares models on the same August–September data; precision and fitness are descriptive, not proof of policy compliance. The reported aggregate alignment summaries cannot be reconstructed exactly from these variants and may reflect different case populations, preprocessing or alignment settings; for example, all three supplied April–May variants appear to fit the specified tree.

```python
import copy
import pm4py
from pm4py.objects.log.obj import EventLog, Trace

# PM4Py process-tree syntax: the second loop child is the redo activity.
normative_tree = pm4py.parse_process_tree(
    "->('Receive','Classify',X(*('Standard Review','Request Info'),"
    "->('Enhanced Review','Compliance Check')),'Decision','Notify')"
)
candidate_tree = pm4py.parse_process_tree(
    "->('Receive','Classify',X(*('Standard Review','Request Info'),"
    "->('Enhanced Review','Compliance Check')),"
    "X(tau,'Supervisor Sign-off'),'Decision','Notify')"
)
norm_net, norm_im, norm_fm = pm4py.convert_to_petri_net(normative_tree)
cand_net, cand_im, cand_fm = pm4py.convert_to_petri_net(candidate_tree)

variants = {
    'Apr-May': [
        ('Receive,Classify,Standard Review,Decision,Notify', 380),
        ('Receive,Classify,Enhanced Review,Compliance Check,Decision,Notify', 180),
        ('Receive,Classify,Standard Review,Request Info,Standard Review,Decision,Notify', 40),
    ],
    'Jun-Jul': [
        ('Receive,Risk Screen,Queue Routed,Standard Review,Decision,Notify', 270),
        ('Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Decision,Notify', 145),
        ('Receive,Risk Screen,Queue Routed,Standard Review,Notify,Decision', 70),
        ('Receive,Risk Screen,Standard Review,Decision,Notify', 90),
        ('Receive,Classify,Queue Routed,Standard Review,Decision,Notify', 30),
        ('Receive,Risk Screen,Queue Routed,Enhanced Review,Decision,Notify', 25),
        ('Receive,Risk Screen,Queue Routed,Manual Override,Standard Review,Decision,Notify', 20),
    ],
    'Aug-Sep': [
        ('Receive,Risk Screen,Queue Routed,Standard Review,Decision,Notify', 210),
        ('Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Supervisor Sign-off,Decision,Notify', 150),
        ('Receive,Risk Screen,Queue Routed,Enhanced Review,Compliance Check,Decision,Notify', 90),
        ('Receive,Risk Screen,Queue Routed,Standard Review,Supervisor Sign-off,Decision,Notify', 60),
        ('Receive,Risk Screen,Queue Routed,Standard Review,Notify,Decision', 45),
        ('Receive,Risk Screen,Queue Routed,Enhanced Review,Decision,Notify', 30),
        ('Receive,Risk Screen,Queue Routed,Manual Override,Standard Review,Decision,Notify', 35),
    ],
}


def expand_variant_log(rows):
    # Each list entry is one case, with comma-separated activity labels.
    traces = [trace for trace, count in rows for _ in range(count)]
    return pm4py.parse_event_log_string(traces, return_legacy_log_object=True)


def normalize(log, remove_queue=False):
    # Build a fresh log and retain each case's attributes and event metadata.
    result = EventLog()
    for trace in log:
        normalized_trace = Trace(attributes=copy.deepcopy(trace.attributes))
        for source_event in trace:
            event = copy.deepcopy(source_event)
            if event['concept:name'] == 'Risk Screen':
                event['concept:name'] = 'Classify'
            if not (remove_queue and event['concept:name'] == 'Queue Routed'):
                normalized_trace.append(event)
        result.append(normalized_trace)
    return result


def report(label, log, net, im, fm):
    dfg, starts, ends = pm4py.discover_dfg(log)
    alignments = pm4py.conformance_diagnostics_alignments(log, net, im, fm)
    fitness = pm4py.fitness_alignments(log, net, im, fm)
    print('\n', label)
    print('cases:', len(log), 'DFG:', dict(dfg))
    print('start activities:', dict(starts), 'end activities:', dict(ends))
    print('alignment fitness:', fitness)
    print('first alignment diagnostic:', alignments[0] if alignments else None)
    return fitness


logs = {period: expand_variant_log(rows) for period, rows in variants.items()}
for period, raw in logs.items():
    report(period + ' raw, normative model', raw, norm_net, norm_im, norm_fm)
    report(period + ' label mapped, normative model',
           normalize(raw), norm_net, norm_im, norm_fm)
    report(period + ' label mapped and queue removed, normative model',
           normalize(raw, remove_queue=True), norm_net, norm_im, norm_fm)

aug = normalize(logs['Aug-Sep'], remove_queue=True)
report('Aug-Sep normalized, candidate model', aug, cand_net, cand_im, cand_fm)
print('\nAug-Sep alignment precision, normative:',
      pm4py.precision_alignments(aug, norm_net, norm_im, norm_fm))
print('Aug-Sep alignment precision, optional sign-off candidate:',
      pm4py.precision_alignments(aug, cand_net, cand_im, cand_fm))
print('Caveat: source sequence is absent; no ordering repair is performed.')
print('Caveat: an optional sign-off control-flow model cannot enforce the '
      'EUR 50,000 condition or authorization and may overgeneralize.')
print('Caveat: supplied variants do not establish that missing events are '
      'true bypasses, and computed metrics need not match the supplied summaries.')
```

## 7. Provisional conclusion

The primary explanation for the measured conformance collapse is a combination of event representation and model drift. Confidence is **high** that these mechanisms contribute substantially, and **moderate** about their exact shares. The UI renamed classification, the gateway introduced a technical routing event, and the ETL changed ordering semantics. In the supplied June–July analysis, sequentially mapping the label, removing routing events and using source order raises fitting traces from 32% to 89%. These are strong diagnostic contrasts, subject to validating each transformation and the source sequence. The August sign-off requirement then made the control-flow model obsolete: the optional-sign-off candidate raises adjusted fitness from 66% to 86%, though it cannot determine whether sign-off was required or authorized. The supplied variant aggregates alone do not reproduce all reported alignment percentages, so they should not be treated as the original case-level evidence.

A real compliance problem may remain. Confidence is **moderate** that the missing-check and override signals deserve investigation, but **low** that employee noncompliance has been established or that its prevalence or trend is known. The 25 and 30 enhanced-review cases with no recorded check could be actual bypasses or missing records. Overrides are real user actions according to IT, and some may correct routing mistakes. Stable outcome summaries are reassuring only in a limited sense: incident detection is incomplete, case mix may change, and aggregate appeals are not a direct test of mandatory checks.

IT should preserve the raw extract, verify event contracts and reconcile source records before applying versioned label, routing and ordering corrections. Process owners should validate action meanings, update the effective-dated model and supply the high-value and authorization rules. Compliance should prioritize an independently documented, stratified audit of missing-check cases and controls, including source completeness, and assess any confirmed violations under the applicable policy. All three groups should monitor corrected fitness, precision and confirmed exceptions after release changes.

Do not claim that employees caused the aggregate drop, that all reversals or missing checks are logging defects, that the optional model proves high-value compliance, or that unchanged reported outcomes establish safety. These conclusions require case-level evidence and validated policy applicability.

## 8. Model-governance recommendation

1. Version each normative model with its effective dates, policy owner, approval record and applicable case population; preserve historical versions for retrospective checks.
2. Maintain versioned event-semantic contracts defining each activity's business meaning, source, trigger, lifecycle and approved label mappings; validate semantic equivalence before remapping.
3. Maintain an explicit technical-event policy identifying gateway and system events, their provenance and justified filtering rules; retain raw events and audit every transformation.
4. Record original timestamps, ingestion timestamps, source sequence numbers and ordering rules, including their scope and known gaps; test ordering against independent source evidence.
5. Complement control-flow models with effective-dated, data-aware rules for claim value, required sign-off and resource authorization; assess missing or uncertain attributes explicitly.
6. After releases and policy changes, compare versioned variants, frequency DFGs, alignments, fitness and precision against a baseline, and investigate representative cases before interpreting changes as behavioral or compliance deterioration.
