## 2. Process-model consistency checks

To ensure explanations align with the normative process and prediction time, the following validation suite must be implemented:

1.  **Prefix-Time Availability Check**: Every feature used in an explanation must be validated against the `t0` timestamp. This requires a feature store schema that tags every feature value with the specific event timestamp it was captured at. Any feature with a timestamp > `t0` (or `extraction_date` if event-time is not available) must be flagged as leaked.
2.  **Activity-Order Feasibility (DFG Checks)**: The model's sequence patterns must be validated against a Declarative Finite Graph (DFG) of the normative process. A pattern like `Claim Closed -> Damage Assessment` is impossible given the DFG (Claim Closed is a terminal step after Settlement Damage Assessment). The system must reject any pattern that violates the DFG reachability at `t0`.
3.  **Same-Timestamp Ambiguity Resolution**: When events share timestamps (e.g., `Claim Closed` and `Damage Assessment` in Case Z), the ingestion sequence index must be used to determine order. If the index is missing, the pattern is invalid. The validation suite must flag any pattern relying on events with missing sequence indices.
4.  **Complete-Trace vs. Prefix-Trace Distinction**: The explainer must distinguish between features derived from the full trace (e.g., `total_case_duration`) and features derived from the prefix (e.g., `elapsed_since_registration`). Any feature requiring a full trace calculation to be defined is prohibited at `t0`.
5.  **Semantic Legitimacy of Repeated Events**: The system must verify if repeated `Settlement Decision Recorded` events are semantically enabled. An appeal (Step 7) enables a second decision (Step 6). However, if the prefix does not contain an `Appeal` event, a second decision pattern is impossible. The validator must check for the existence of the enabling trigger (`Appeal`) before allowing the pattern.
6.  **Constraint Propagation**: If a feature is identified as leaked (e.g., `risk_score_current`), the model's SHAP contribution must be recalculated using a repaired feature set. The explanation cannot claim a causal link for a feature that was never available to the model at prediction time.

**Limitations**: These checks validate *availability* and *process logic*, not *predictive accuracy*. A feature can be available and process-consistent but still be a spurious proxy (e.g., `calendar_week`). Therefore, statistical validation (stability, calibration) must accompany these structural checks.

## 5. Recommendations for explanation validation

1.  **Feature-Store Design**: Implement a schema where every feature value is immutable and tagged with the exact event timestamp (`t0`) it was captured at. No feature should be joined from a "current" snapshot without a validity check against the prediction timestamp.
2.  **Historical Feature Timestamps**: For mutable features (e.g., risk scores, queue length), store a history of values. The model must be trained and explained using only the value available at the specific event time, not the latest value.
3.  **Prefix-Only Recomputation**: Establish a pipeline to regenerate model features using only the prefix trace up to `t0`. If a feature requires the full trace to compute (e.g., `total_case_duration`), it must be excluded from the training set and explainer.
4.  **Process-Conformance Tests**: Integrate a DFG validator into the model deployment pipeline. Any explanation containing a sequence pattern that is not reachable from `t0` according to the normative process should trigger a failure.
5.  **Calibration After Feature Removal**: After removing leaked features (e.g., `appeal_seen_anywhere`), the model's performance must be validated. If performance drops significantly, the model may have been relying on leakage; explainability will be less useful until the model is retrained on prefix-only data.
6.  **Explanation Stability**: Monitor the stability of SHAP values for retained features (e.g., `queue_length`). If `queue_length` suddenly drives high risk for low-complexity claims, investigate for data drift or proxy effects.
7.  **Proxy/Fairness Analysis**: Conduct a fairness audit on `claimant_region` and `claimant_channel`. If these proxies correlate strongly with protected attributes (e.g., race, income), they must be flagged for mitigation, even if they are predictive.
8.  **Monitoring for Schema/Process Drift**: Continuously monitor the frequency of "impossible" patterns (e.g., `Claim Closed` before `Damage Assessment`). A spike indicates a data ingestion bug or a process change that invalidates the normative model assumptions.
