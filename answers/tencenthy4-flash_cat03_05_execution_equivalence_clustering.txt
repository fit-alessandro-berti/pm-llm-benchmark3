## 1. Equivalence design space

I treat an execution as a timestamp-ordered event sequence with typed event-to-object incidence (E2O) and typed object-to-object relations (O2O). Local identifiers are variables; an `EXT` identifier is a typed object with an external-lifecycle flag.

**1. Activity-sequence equivalence**

- **Definition:** Two executions are equivalent iff their activity-label sequences are identical, ignoring all object references.
- **Preserved:** Activity labels, their order, repeated events.
- **Discarded:** Object types/counts, E2O incidence, O2O topology, qualifiers, externality, item/package/payment multiplicity.
- **Properties:** Reflexive, symmetric, transitive.
- **Concurrency:** I totalize by listed timestamp order and input tie-break. A partial-order variant would compare labeled trace posets instead.

**2. Typed structural equivalence under identifier renaming**

- **Definition:** Executions are equivalent iff there is a bijection between object identifiers preserving object type, local/external status, lead `Order`, event count/order/activity labels, typed E2O incidence, and unqualified O2O edge existence/direction. Qualifier text is ignored here but used by relation 3.
- **Preserved:** Repeated events, event order, object-type multiplicities, external flags, E2O incidence, O2O topology.
- **Discarded:** Concrete local IDs, exact timestamps, O2O qualifier semantics, attribute values.
- **Properties:** Reflexive, symmetric, transitive; it is graph/trace isomorphism with typed colors.
- **Concurrency:** Same total-order convention as above. Under a partial-order version, event posets must be isomorphic.

**3. Business-semantic equivalence, preferred**

- **Definition:** Executions are equivalent iff their canonical business signatures are equal. The signature preserves typed object multiplicities, external flags, activity order/repetition, E2O incidence, O2O qualifiers, and derived lifecycle motifs such as replacement, partial settlement, logistics sharing, invoice sharing, and return/repack.
- **Preserved:** Everything in the canonical signature below, including business-relevant qualifiers and external sharing.
- **Discarded:** Local identifier names, raw `EXT-OA`/`EXT-OB` suffixes, event IDs, exact timestamp values, non-specified attributes.
- **Properties:** Reflexive, symmetric, transitive, because it is equality of canonical forms.
- **Concurrency:** Uses the supplied order; same-time events are deterministically ordered. A partial-order signature could replace the event sequence by a canonical dependency graph.

## 2. Canonical signatures

The preferred signature is identifier-renaming invariant. Objects are canonicalized by type and external/local flag; qualifiers are preserved. External objects are distinguished from local ones, but different external suffixes are not treated as business-meaningful.

```python
def canonical_business_signature(ex):
    # ex.events: [(activity, {object_id: ...})]
    # ex.o2o: [(src_id, tgt_id, qualifier)]
    # ex.object_type: {oid: type}
    # ex.is_external(oid): bool
    # ex.lead_order: oid

    objects = set(ex.object_type)
    color = {
        o: (ex.object_type[o], bool(ex.is_external(o)))
        for o in objects
    }

    def core_signature(cmap):
        events = []
        for activity, objs in ex.events:
            by_type = {}
            for o in objs:
                by_type.setdefault(ex.object_type[o], []).append(cmap[o])
            e2o = tuple(
                (typ, tuple(sorted(ids))) for typ, ids in sorted(by_type.items())
            )
            events.append((activity, e2o))

        object_sig = tuple(
            sorted((cmap[o], ex.object_type[o], int(ex.is_external(o)))
                   for o in objects)
        )

        o2o_sig = tuple(sorted(
            (q or "", ex.object_type[s], cmap[s],
             ex.object_type[t], cmap[t])
            for s, t, q in ex.o2o
        ))

        motifs = (
            "external_objects=" + str(sorted({
                ex.object_type[o] for o in objects if ex.is_external(o)
            })),
            "return_repack=" + str(
                any(a in {"Return Item", "Inspect Return"} for a, _ in ex.events)
                and any("repack" in (q or "").lower() for _, _, q in ex.o2o)
            ),
            "replacement=" + str(
                any("replac" in (q or "").lower() or
                    "removed_before_dispatch" in (q or "").lower()
                    for _, _, q in ex.o2o)
            ),
            "partial_payment=" + str(
                any("partial" in (q or "").lower() or
                    "completes_settlement" in (q or "").lower()
                    for _, _, q in ex.o2o)
            )
        )

        return (object_sig, tuple(events), o2o_sig,
                ("lead", cmap[ex.lead_order]), motifs)

    # Exhaustive in small examples; replace by partition refinement for large logs.
    candidates = []
    for mapping in all_color_preserving_bijections(objects, color,
                                                   fixed_color=color[ex.lead_order]):
        candidates.append(core_signature(mapping))

    return min(candidates)
```

## 4. Cluster interpretations

**BS-1: Local clean flow — X1, X2.**  
Business behavior: two items are packed together, dispatched together, invoiced once, and paid once. No external object or exception qualifier exists. Operational meaning: normal isolated fulfillment. Flattening by activity labels represents it adequately for high-level reporting, but still hides item/package/delivery dependencies. Stable under item renaming and Add-item order changes; unstable only if item or package multiplicity changes.

**BS-2: Split pack / consolidated delivery — X3.**  
Business behavior: items are packed separately but shipped together. Opportunity: reduce delivery cost. Risk: package-level traceability is more complex than in BS-1. A flat Order-level DFG sees “two Pack, one Dispatch” but not that one Delivery carries two Packages. Stable if package identities are local; unstable if log repair merges the two Pack events.

**BS-3: Split logistics and settlement — X4.**  
Business behavior: each item is packed and dispatched separately, and the invoice is settled by a partial payment followed by a completion payment. Opportunities: flexible shipping and installments. Risks: partial settlement compliance, dunning errors, delivery reconciliation. Flattening shows duplicate Dispatch/Record Payment but loses partial-versus-final semantics. Stable if payment qualifiers and package-delivery links are preserved; unstable if payments are collapsed as repeated labels.

**BS-4: External logistics pooling — X5.**  
Business behavior: O5’s items are packed with an external order’s item and shipped on a shared delivery, while O5 alone is invoiced. Opportunity: consolidation across orders. Risk: cost allocation, ownership, customs, returns attribution. Flattening around O5 looks exactly like BS-1 and completely misses external objects. Stable if `EXT` flags are retained; unstable if external columns are stripped.

**BS-5: External invoice pooling — X6.**  
Business behavior: logistics are isolated, but invoice and payment involve another Order. Opportunity: consolidated billing. Risk: no order-level allocation, disputes, revenue attribution. Flat Order-level views look clean because the local logistics sequence is baseline-like. Stable only if external objects in financial events/O2O are preserved.

**BS-6: Item replacement / removal — X7.**  
Business behavior: two items appear, but I72 replaces I71 and I71 is removed before dispatch. This is an exception masked by a baseline activity sequence. Risk: wrong shipped item, credit notes, inventory correction. Flattening by labels cannot detect it; even E2O-only views miss the qualifier semantics. Stable only if qualifiers and the extra Dispatch item reference are reliable.

**BS-7: Return and repack — X8.**  
Business behavior: an item is returned after dispatch, inspected, repacked, and redelivered; P82 replaces P81 for I82. Opportunity: controlled reverse logistics. Risk: duplicate billing, return-loop leakage, replacement package confusion. Flat DFGs show Pack/Dispatch repetition but poorly represent object replacement and item-level return. Stable if Return/Inspect events and repacks/replaces qualifiers are retained.

## 5. Borderline cases

- **X1 vs X2.** Activity-sequence equivalence merges them: both emit the same seven labels. Exact identifier-sensitive equivalence separates them because I11/I12 differ from I22/I21. Typed structural and preferred semantic equivalence merge them because local IDs are ignored and Pack contains a set of two items.

- **X1 vs X5.** Their activity sequences are identical, so label-based clustering merges them. Preferred semantic clustering separates them because X5 has external Order/Item objects in Pack and Dispatch. If a repair drops `EXT` prefixes, or a flat Order-centric projection keeps only local objects, X5 collapses back to BS-1.

- **X1 vs X6.** Again labels match. A local multiplicity-only definition may also merge them because the local logistics structure is baseline-like. Qualified O2O/E2O semantics separates them: X6’s invoice and payment are shared with an external Order and lack allocation.

- **X1 vs X7.** Activity labels are identical. A shallow object-count view may also under-differentiate if it ignores the extra Item at Dispatch and the qualifiers. Typed structural equivalence separates them because Dispatch has an additional E2O item link; preferred semantic equivalence separates them because replacement/removal is explicitly qualified.

- **X3 vs X4.** Both have two items and two packages, so a coarse “split packaging” motif can merge them. Activity-sequence, typed structural, and preferred semantic relations separate them: X3 consolidates delivery, while X4 splits deliveries and has partial payment semantics.

- **X4 vs X8.** A coarse DFG with repeated Pack/Dispatch loops may treat both as non-baseline multi-dispatch executions. Preferred semantics separates them: X4 is forward split fulfillment plus installment payment, while X8 is reverse logistics, inspection, repacking, and package replacement.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` computes exact clusters over connected object-centric executions. Its key is not business-canonical: it preserves raw object identifiers/types, activity labels, E2O incidence in the event table order, and multiplicities; where O2O information is available to the routine, O2O rows/qualifiers are also raw rather than semantically abstracted. It does not rename local IDs, does not interpret `EXT`, and does not project replacement, sharing, or settlement motifs. Therefore X1/X2 can be split merely because O1/I11 differ from O2/I21.

Exact equivalence is preferable when the physical object identity matters, e.g., warranty tracking, regulatory lineage, or debugging a specific order’s object graph. It is too fine for cohort discovery, KPI benchmarking, or variant reporting across orders.

`max_objs` limits component size. Small values can split one business execution into artificial pieces; large components caused by shared resources/invoices can become expensive or be skipped/treated specially. Preselect lead `Order` objects and raise the limit carefully.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"
MAX_OBJS = 20000

# Exact raw-key clusters from PM4Py.
raw_groups = pm4py.cluster_equivalent_ocel(
    ocel,
    parameters={"max_objs": MAX_OBJS}
)

object_type = dict(zip(
    ocel.objects[ocel.objects.object_id_column],
    ocel.objects[ocel.objects.object_type_column]
))

def lead_orders(obj_ids):
    return [o for o in obj_ids if object_type.get(o) == LEAD_TYPE]

def e2o_index(ocel):
    # Build {event_id: {type: set(object_ids)}} from the OCEL event table.
    idx = defaultdict(lambda: defaultdict(set))
    for _, row in ocel.log.iterrows():
        eid = row[ocel.log.event_id_column]
        for typ in ocel.event_object_relationships:
            for oid in ocel.event_object_relationships[typ].get(eid, set()):
                idx[eid][typ].add(oid)
    return idx

E2O = e2o_index(ocel)

def extract_execution(lead, obj_scope):
    ev_ids = [
        eid for eid, objs in E2O.items()
        if lead in objs.get(LEAD_TYPE, set())
        and any(o in obj_scope for os_ in objs.values() for o in os_)
    ]
    # Convert PM4Py rows to the Execution structure used in Section 2,
    # including o2o rows/qualifiers and external flags.
    return build_execution(ocel, lead, ev_ids, obj_scope)

aggregated = defaultdict(list)

for gid, obj_ids in enumerate(raw_groups):
    obj_scope = set(obj_ids)
    for lead in lead_orders(obj_ids):
        ex = extract_execution(lead, obj_scope)
        sig = canonical_business_signature(ex)   # custom semantic canonicalization
        aggregated[sig].append({"raw_group": gid, "lead_order": lead})

# aggregated now gives business-semantic clusters over the PM4Py exact clusters.
```

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** X4 loses partial/final settlement semantics, though two payments still distinguish it from BS-1. X7 loses replacement meaning; if the extra Dispatch item is also ignored, it may collapse toward BS-1. X8 still has Return/Inspect activity labels, but package replacement is hidden.

- **Ignore external objects.** X5 and X6 collapse toward BS-1 if external object columns and O2O edges are removed. This is convenient for local reporting but dangerous for cost allocation and compliance.

- **Collapse repeated same-label events.** X3 may look like a single Pack/Dispatch flow; X4 may lose the partial-payment signal; X8 still has reverse-logistics labels but weaker repack semantics. If object multiplicities are retained, damage is smaller.

- **Treat Pack/Dispatch as partial order.** X3 and X4 remain different because one Delivery versus two Deliveries is structural. If delivery grouping is also ignored, they become closer. X4 and X8 remain distinct because Return/Inspect introduces a different lifecycle phase.

- **Treat payment multiplicity as amount attribute.** If M41/M42 are merely amounts summing to the invoice amount, X4 may merge with single-payment variants. If qualifiers encode partial settlement, preserving structure is safer.

## 8. Limitations and recommendation

- **Compliance monitoring:** Use business-semantic equivalence with qualifiers and external flags. Exceptions such as X7, X8, and X6 are exactly what controls must see.
- **Operational segmentation:** Use a coarser motif projection of the same signature: clean, split logistics, shared logistics, shared finance, replacement, return/repack.
- **Root-cause analysis:** Use the full canonical qualified E2O/O2O signature plus timestamps and attributes; object-level lineage matters.
- **Descriptive reporting:** Activity-sequence clusters are acceptable only if explicitly labeled as flattened activity variants, not as object-centric executions.

No single relation is best because the purposes differ: reporting favors compression, compliance favors exception sensitivity, root-cause analysis favors lineage, and segmentation favors stable motifs. The recommended practice is to keep the exact PM4Py clusters as a raw layer, canonicalize them into the preferred semantic signature, and then project coarser views only for explicitly chosen use cases.
