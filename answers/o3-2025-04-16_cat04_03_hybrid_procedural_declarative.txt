# 1. Policy Interpretation and Conflict Resolution  

Material assumptions  

• “Accepted case”  activity Activate Vendor is present.  
• If neither Manager Approval nor Compliance Approval occurs, the case is rejected.  
• The three “checks” mentioned in the narrative are exactly the activities Capture Master Data, Run Sanctions Screening and Verify Bank Account.  
• “Emergency activation” is an operational reality but is not recorded in the log; therefore it can be recognised only indirectly (opinion comes after activation).  
• 24 hours = 86 400 seconds.  
• The statistical expectations in R12 are soft-thresholds: we never cancel a case solely for violating them – we only raise a warning.  

R5 / R6 conflict – two defensible resolutions  

1. Strong-precedence (legal view, R5 dominates)  
   Obtain Legal Opinion must **always** occur before Activate Vendor.  
   Emergency activations are non-conformant and are escalated manually.  

2. Conditional-precedence (operations view, R6 dominates)  
   If Activate Vendor precedes Obtain Legal Opinion, we **assume** the case is an emergency.  
   We then require (a) Run Sanctions Screening  Activate Vendor, and (b)  
   Activate Vendor  Obtain Legal Opinion within 86 400 seconds.  

Chosen implementation  

We implement resolution 1.  
Reasons:  
• The event log holds no attribute that proves an emergency.  
• Failing fast on a possible legal breach is regarded as the lower compliance risk; operations can still argue an exemption afterwards.  

For transparency the resource/data layer contains a second, parameterised check that can be switched on to evaluate resolution 2. The test-case table shows both outcomes for T6.

# 3. Procedural Backbone  

## 3.1 Formal description (high-level)  

SEQ(  
  Receive Onboarding Request,  
  AND(Capture Master Data, Run Sanctions Screening, Verify Bank Account),  
  Classify Risk,  
  XOR(  
    SEQ(Reject Vendor, Close Onboarding),  
    SEQ(Manager Approval, Activate Vendor, Release First Payment, Close Onboarding),  
    SEQ(Enhanced Due Diligence, Compliance Approval, Activate Vendor, Release First Payment, Close Onboarding)  
  )  
)  

Clarification, escalations, suspensions, etc. are **not** inside the rigid backbone; they live in the DECLARE / external layers so we do not lose block structure.

## 3.2 PM4Py code  

```python
from pm4py.objects.process_tree import ProcessTree, pt_operator
# leaf constructors
def leaf(name): 
    return ProcessTree(label=name)

receive = leaf("Receive Onboarding Request")
capture = leaf("Capture Master Data")
screen  = leaf("Run Sanctions Screening")
verify  = leaf("Verify Bank Account")
classify = leaf("Classify Risk")

reject  = leaf("Reject Vendor")
close   = leaf("Close Onboarding")

mgr_appr = leaf("Manager Approval")
edd      = leaf("Enhanced Due Diligence")
comp_appr = leaf("Compliance Approval")
activate = leaf("Activate Vendor")
pay      = leaf("Release First Payment")

# building the tree
parallel_checks = ProcessTree(children=[capture, screen, verify],
                              operator=pt_operator.PARALLEL)

reject_branch = ProcessTree(children=[reject, close], operator=pt_operator.SEQUENCE)
low_branch = ProcessTree(children=[mgr_appr, activate, pay, close], 
                         operator=pt_operator.SEQUENCE)
high_branch = ProcessTree(children=[edd, comp_appr, activate, pay, close],
                          operator=pt_operator.SEQUENCE)

choice_after_classify = ProcessTree(children=[reject_branch, low_branch, high_branch],
                                    operator=pt_operator.XOR)

root = ProcessTree(children=[receive, parallel_checks, classify, choice_after_classify],
                   operator=pt_operator.SEQUENCE)

procedural_model = root      # required variable name
```

## 3.3 Explanation  

• Concurrency: the PARALLEL node lets the three checks run in any order or simultaneously.  
• Clarification cycles, sanctions escalation, bank changes, suspension etc. are outside the backbone because they are conditional and orthogonal to reachability of end states – making them declarative avoids an unstructured Petri net.  
• Choice: exactly one of the three XOR branches can fire.  
• Post-activation behaviour (bank change  suspend  re-verify) is excluded here and checked by a dedicated script (R11).  
• Each terminal branch _always_ ends with Close Onboarding, which keeps the acceptance condition explicit.

Semantic table  

| Template | (A,B) | Meaning |
|---|---|---|
| noncoexistence | (Reject, Activate) | A and B cannot both appear in the same trace |
| noncoexistence | (EDD, MgrAppr) etc. | Avoid mixed approval paths |
| altresponse | (ReqClar, RecClar) | Every Request Clarification must be followed by one Receive Clarification before another Request Clarification may occur |
| response | (Escalation, Opinion) | If Sanctions Escalation happens, an Opinion will eventually follow |
| precedence | (Activate, Opinion) | Opinion must occur before Activate (strict R5) |
| precedence | (Escalation, Screen) | Screening must be completed before escalation |

Note: existence/absence cardinalities (R10) go to the log skeleton because DECLARE’s `exactly-one` template would affect all traces, including rejected ones.

# 5. Log-Skeleton Model  

```python
log_skeleton = {
    "equivalence": set(),
    "always_before": {("Receive Onboarding Request", "Classify Risk")},
    "always_after": {("Classify Risk", "Close Onboarding")},
    "never_together": {("Reject Vendor", "Activate Vendor")},
    "activ_freq": {
        "Reject Vendor": {0, 1},
        "Activate Vendor": {0, 1},
        "Release First Payment": {0, 1}
    },
    "directly_follows": {
        ("Reject Vendor", "Close Onboarding"),
        ("Release First Payment", "Close Onboarding")
    }
}
```

Explanation  

• `always_before` establishes that the first visible step is always Receive Onboarding Request.  
• `never_together` duplicates R1 for quick skeleton checking.  
• `activ_freq` realises the “at most once” part of R10.  
• Skeleton deliberately stays silent about clarifications and escalation so as not to over-fit the backbone.

# 6. Temporal Profile  

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48*3600, 24*3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12*3600,  6*3600),
    ("Activate Vendor", "Release First Payment"):     (72*3600, 36*3600)
}
zeta = 2.0        # used in the conformance call
```

Why only warnings?  
A long clarification round or a late first payment does not _break_ the process logic; it merely signals operational drift. Therefore the temporal checker returns `warning` when the observed value  [µ  zeta·, µ + zeta·].

# 7. Resource- and Data-Aware Checks  

```python
import pandas as pd
from datetime import timedelta

def check_four_eyes(log_df, act1, act2):
    """Fail if same resource performs act1 and act2 in the same case."""
    bad_cases = []
    for case, df in log_df.groupby("case:concept:name"):
        res1 = set(df[df["concept:name"] == act1]["org:resource"])
        res2 = set(df[df["concept:name"] == act2]["org:resource"])
        if res1 and res2 and not res1.isdisjoint(res2):
            bad_cases.append(case)
    return bad_cases

def check_R9(log_df):
    errs = {}
    errs["Verify-vs-Approval"] = check_four_eyes(
        log_df, "Verify Bank Account", "Manager Approval") + \
        check_four_eyes(log_df, "Verify Bank Account", "Compliance Approval")
    errs["Capture-vs-Activate"] = check_four_eyes(
        log_df, "Capture Master Data", "Activate Vendor")
    return {k:v for k,v in errs.items() if v}

def check_emergency_activation(log_df, strict=True):
    """strict = True   resolution 1 (R5 dominates)
       strict = False  resolution 2 (allows emergency)"""
    viol, warn = [], []
    for case, df in log_df.groupby("case:concept:name"):
        df = df.sort_values("time:timestamp")
        if "Sanctions Escalation" not in df["concept:name"].values:
            continue
        if "Activate Vendor" not in df["concept:name"].values:
            continue
        t_act  = df[df["concept:name"]=="Activate Vendor"]["time:timestamp"].iloc[0]
        t_op   = df[df["concept:name"]=="Obtain Legal Opinion"]["time:timestamp"]
        t_op   = t_op.iloc[0] if not t_op.empty else None

        if strict:
            if t_op is None or t_op > t_act:
                viol.append(case)
        else:   # emergency is allowed but must be inside 24 h
            if t_op is None or (t_op - t_act) > timedelta(hours=24):
                viol.append(case)
            elif t_act < t_op:       # activation first but inside the SLA
                warn.append(case)
    return viol, warn

def check_R11_bank_change(log_df):
    bad_cases = []
    for case, df in log_df.groupby("case:concept:name"):
        labels = df["concept:name"].tolist()
        if "Change Bank Details" in labels and "Activate Vendor" in labels:
            act_idx = labels.index("Activate Vendor")
            # every Change-Suspend-Re-Verify must be after activation
            subs = labels[act_idx+1:]
            while "Change Bank Details" in subs:
                chg = subs.index("Change Bank Details")
                subs_after = subs[chg+1:]
                if "Suspend Vendor" not in subs_after:
                    bad_cases.append(case); break
                sus = subs_after.index("Suspend Vendor")
                # verify must occur between suspend and next Release First Payment
                tail = subs_after[sus+1:]
                if "Release First Payment" in tail:
                    rfp = tail.index("Release First Payment")
                    between = tail[:rfp]
                    if "Verify Bank Account" not in between:
                        bad_cases.append(case); break
                subs = tail
    return bad_cases
```

Missing attributes  

If `org:resource` is not present the four-eyes checks return `“not evaluated”`.

# 9. Contradictions, Redundancies, and Blind Spots  

• R1 is enforced three times (procedural XOR, DECLARE, skeleton) – useful for fast detection but may clutter violation reports.  
• The altresponse rule becomes **vacuous** in traces without Request Clarification; callers must interpret vacuity correctly.  
• Loops that happen after activation (bank changes) are invisible to the backbone; if the external script is not run the model will look perfectly compliant.  
• Pure time stamps cannot prove the external joint authorisation required by R6 – we can only infer.  
• Support/confidence = 1.0 in DECLARE is documentary; nothing in pm4py prevents the analyst from loading a mined model with lower figures and accidentally treating it as normative.  
• Statistical rules (R12) assume normality; extreme skew would produce many false warnings.  
• Missing resource attributes silently disable the four-eyes check – a blind spot that must be covered by dataquality procedures.

# 10. Deployment Recommendation  

1. Canonical procedural representation = the process tree of section 3 – smallest, easiest to maintain.  
2. Authoritative policy layer order:  
   a. Procedural conformance (quick kill for impossible traces)  
   b. DECLARE rules (semantic business constraints)  
   c. Log Skeleton (cardinality & quick exclusions)  
   d. Resource / data-aware scripts (segregation of duties, SLA, bank change cycle)  
   e. Temporal profile (warnings only)  

3. A conformance engine should stop at the first **hard** violation per layer but accumulate all **warnings**.  
4. Conflicting findings (e.g., T6 under the two resolutions) are surfaced with a tag “policy-dependent”, the selected policy variant, and the alternative verdicts so that governance can decide on an exception.  

The hybrid approach keeps the backbone tight, off-loads irregular but important rules to declarative formalisms and scripts, and produces actionable, layered feedback to both operations and compliance.
