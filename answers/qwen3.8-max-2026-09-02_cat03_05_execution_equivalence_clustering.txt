## 1. Equivalence design space

I treat local identifiers such as `O1`, `I11`, `P41` as meaningless names for objects of the corresponding type. Identifiers beginning with `EXT` are not treated as globally meaningful identifiers either, but their `EXT` flag is meaningful: it says that the object belongs to another Order-centric execution. O2O qualifiers are meaningful only when explicitly supplied.

### 1.1 Activity-sequence equivalence, `AS`

**Definition.**  
Two executions are activity-sequence equivalent iff their ordered activity-label traces are equal after normalizing same-time blocks. Formally, for execution `E` with events `e1,...,en` in timestamp order:

```text
sig_AS(E) = (label(e1), label(e2), ..., label(en))
```

If several events have identical timestamps, I sort their labels lexicographically inside the timestamp block, thereby treating them as unordered for this equivalence.

**Invariants preserved.**
- Activity labels.
- Repetition of activities.
- Total order of activity labels, except for same-time blocks.

**Information discarded.**
- Object identifiers.
- Object types and multiplicities.
- E2O incidence.
- O2O relations and qualifiers.
- External-object flags.
- Business meaning of repeated events.

**Equivalence properties.**  
Reflexive, symmetric, transitive. It is equality of normalized label sequences.

**Concurrency handling.**  
Same-timestamp events are sorted and treated as a block. If a true partial order is available, `AS` can be weakened to equality of label multisets per concurrency layer, but in the base definition I use the observed timestamp order.

---

### 1.2 Typed structural equivalence under identifier renaming, `TS`

**Definition.**  
Represent an execution as a typed object-centric hypergraph:

- event nodes labeled by activity label;
- object nodes labeled by object type and `EXT` flag;
- event-object incidence edges;
- event order given by timestamps or by a partial order.

Two executions are typed-structurally equivalent iff there is a bijection between their event nodes and object nodes such that:

1. event activity labels match;
2. event order is preserved, or the same partial order is preserved;
3. object types match;
4. external flags match;
5. event-object incidence is preserved.

Local identifiers are renamed away. External identifiers are also canonicalized, unless an external identifier is known to be globally meaningful; the preserved fact is that the object is external.

**Invariants preserved.**
- Activity labels.
- Event order or event partial order.
- Object types.
- Object multiplicities.
- Which canonical object participates in which events.
- External-object flags.

**Information discarded.**
- Raw local identifiers.
- Raw external identifiers, except for externality.
- O2O qualifiers, unless explicitly added to the graph.
- Business interpretation of payments, replacements, returns, etc.

**Equivalence properties.**  
Reflexive, symmetric, transitive. It is typed graph isomorphism modulo identifier renaming.

**Concurrency handling.**  
If events are concurrent, the total order is replaced by a partial order. Equivalent executions must have isomorphic labeled partial orders. Same-time events are not ordered unless object flow forces ordering.

**Note on exact raw structural equivalence.**  
A stricter relation would preserve raw identifiers or raw event identifiers. That relation is usually too fine for business clustering because X1 and X2 would become different merely because identifiers differ. It is useful for debugging or exact data alignment, not for semantic clustering.

---

### 1.3 Business-semantic equivalence, `BS`

This is my preferred relation for the task.

**Definition.**  
Two executions are business-semantically equivalent iff they have the same canonical business signature. The signature preserves:

- activity motif counts;
- object multiplicities for packages, deliveries, invoices, payments, returns;
- external-sharing domain: logistics, financial, or none;
- normalized O2O qualifiers such as `partial_settles`, `completes_settlement`, `replaces`, `removed_before_dispatch`;
- lead-order lifecycle flags, for example whether the lead Order was created, invoiced, paid, returned, or externally shared.

A schematic signature is:

```text
(
  normalized_event_trace,
  canonical_object_lifecycles,
  normalized_o2o_qualifiers,
  business_flags
)
```

**Invariants preserved.**
- Business-relevant object multiplicities.
- Shared external objects, separated by domain.
- Partial payment and settlement completion.
- Replacement, removal, return, and repack semantics.
- Repeated activities when they indicate distinct business steps.

**Information discarded.**
- Raw local identifiers.
- Arbitrary ordering of independent events, if a partial-order variant is used.
- Low-level differences that do not change the business motif.

**Equivalence properties.**  
Reflexive, symmetric, transitive, provided the signature function is deterministic.

**Concurrency handling.**  
Independent events may be unordered. For example, two `Add Item` events can be treated as concurrent. Concurrency changes the cluster only if it changes multiplicities, qualifiers, or external-sharing flags.

---

### 1.4 Optional fourth relation: causal behavioral equivalence, `CB`

**Definition.**  
Two executions are causally equivalent iff their labeled event partial orders are isomorphic after object renaming. The partial order can be induced by object flow: if the same object participates in two events, those events may be ordered; if different objects are independent, their events may be concurrent.

**Invariants preserved.**
- Causal dependencies.
- Activity labels.
- Object types and external flags, if included in the node labels.

**Information discarded.**
- Arbitrary linearizations.
- Timestamp differences that do not change causality.

**Equivalence properties.**  
Reflexive, symmetric, transitive.

**Concurrency handling.**  
Native. Same-time or reorderable events are not distinguished unless they create different causal dependencies.

## 2. Canonical signatures

The following scheme canonicalizes the preferred business-semantic relation. It is invariant to local identifier renaming but preserves object types, external flags, event participation, O2O qualifiers, repeated activities, and business flags.

```python
from collections import defaultdict
import hashlib

LOGISTICS_ACTIVITIES = {
    "Pack Package",
    "Dispatch",
    "Return Item",
    "Inspect Return",
}

FINANCIAL_ACTIVITIES = {
    "Issue Invoice",
    "Record Payment",
}

REPLACEMENT_PREDICATES = {
    "replaces",
    "removed_before_dispatch",
}

PARTIAL_PAYMENT_PREDICATES = {
    "partial_settles",
    "partially_settles",
}

SETTLEMENT_PREDICATES = {
    "settles",
    "completes_settlement",
}


def is_external(oid: str) -> bool:
    return oid.startswith("EXT")


def canonical_objects(events):
    """
    events: list of dicts
      {
        "activity": str,
        "objects": [(object_type, object_id), ...]
      }

    Returns:
      canon: raw_id -> canonical_id
      obj_type: raw_id -> object_type
      participation: raw_id -> [(event_index, activity), ...]
    """
    participation = defaultdict(list)
    obj_type = {}

    for idx, ev in enumerate(events):
        for typ, oid in ev["objects"]:
            obj_type[oid] = typ
            participation[oid].append((idx, ev["activity"]))

    # Simple first-seen canonicalization.
    # For highly symmetric concurrent objects, replace this by
    # graph-isomorphism / color-refinement canonicalization.
    canon = {}
    counters = defaultdict(int)

    def sort_key(oid):
        first = min(idx for idx, _ in participation[oid])
        return (first, obj_type[oid], is_external(oid), participation[oid])

    for oid in sorted(participation, key=sort_key):
        key = (obj_type[oid], is_external(oid))
        counters[key] += 1
        typ = obj_type[oid]
        suffix = "EXT" if is_external(oid) else "LOCAL"
        canon[oid] = f"{typ}_{suffix}_{counters[key]}"

    return canon, obj_type, participation


def normalize_predicate(pred: str) -> str:
    p = pred.strip().lower().replace(" ", "_")
    if p in {"partially_settles", "partial_settles"}:
        return "partial_settles"
    if p in {"completes_settlement_of", "completes_settlement"}:
        return "completes_settlement"
    if p == "settle":
        return "settles"
    return p


def normalized_o2o(o2o_triples, canon):
    """
    o2o_triples: iterable of (subject_id, predicate, object_id)
    """
    normalized = []
    for s, p, o in o2o_triples:
        if s not in canon or o not in canon:
            # Do not invent missing event participation.
            # Keep only qualifiers over objects observed in the execution.
            continue
        normalized.append((canon[s], normalize_predicate(p), canon[o]))
    return tuple(sorted(normalized))


def business_signature(events, o2o_triples, lead_type="Order", partial_order=False):
    canon, obj_type, participation = canonical_objects(events)

    if partial_order:
        # Simplified partial-order variant:
        # here we only remove total-order sensitivity by sorting events.
        # A production version should build a labeled poset from object flow.
        trace = tuple(
            sorted(
                (
                    ev["activity"],
                    tuple(
                        sorted(
                            (typ, canon[oid], is_external(oid))
                            for typ, oid in ev["objects"]
                        )
                    ),
                )
                for ev in events
            )
        )
    else:
        trace = tuple(
            (
                ev["activity"],
                tuple(
                    sorted(
                        (typ, canon[oid], is_external(oid))
                        for typ, oid in ev["objects"]
                    )
                ),
            )
            for ev in events
        )

    lifecycles = tuple(
        sorted(
            (
                canon[oid],
                obj_type[oid],
                is_external(oid),
                tuple(activity for _, activity in participation[oid]),
            )
            for oid in participation
        )
    )

    quals = normalized_o2o(o2o_triples, canon)

    activities = [ev["activity"] for ev in events]

    flags = {
        "lead_count": sum(
            1
            for oid, typ in obj_type.items()
            if typ == lead_type and not is_external(oid)
        ),
        "lead_created": any(
            ev["activity"] == "Create Order"
            and any(
                typ == lead_type and not is_external(oid)
                for typ, oid in ev["objects"]
            )
            for ev in events
        ),
        "pack_count": activities.count("Pack Package"),
        "dispatch_count": activities.count("Dispatch"),
        "invoice_count": activities.count("Issue Invoice"),
        "payment_count": activities.count("Record Payment"),
        "return_present": any(
            a in {"Return Item", "Inspect Return"} for a in activities
        ),
        "replacement_present": any(
            p in REPLACEMENT_PREDICATES for _, p, _ in quals
        ),
        "partial_payment_present": any(
            p in PARTIAL_PAYMENT_PREDICATES for _, p, _ in quals
        ),
        "settlement_present": any(
            p in SETTLEMENT_PREDICATES for _, p, _ in quals
        ),
        "external_logistics": any(
            is_external(oid) and ev["activity"] in LOGISTICS_ACTIVITIES
            for ev in events
            for _, oid in ev["objects"]
        ),
        "external_financial": any(
            is_external(oid) and ev["activity"] in FINANCIAL_ACTIVITIES
            for ev in events
            for _, oid in ev["objects"]
        ),
    }

    payload = (trace, lifecycles, quals, flags)
    digest = hashlib.sha256(repr(payload).encode("utf-8")).hexdigest()
    return digest, payload
```

The signature is deliberately stricter than activity-label clustering. It keeps object-centric structure while quotienting away arbitrary identifiers.

## 4. Cluster interpretations

### 4.1 `SEM-BASE`: isolated standard order-to-cash

**Signature.** `base; pack=1; dispatch=1; invoice=1; payment=1; ext=none`.

**Business behavior.**  
X1 and X2 represent the clean baseline: one order, two items, one package, one delivery, one invoice, one settlement. The order is fulfilled and paid in a single isolated lifecycle.

**Operational risks or opportunities.**  
Risk is low relative to other clusters. The main opportunity is straight-through processing and automation. This cluster is the reference behavior against which exceptions should be compared.

**Poor flattening.**  
Flattening by `Order` works reasonably well here. Flattening by `Package`, `Delivery`, or `Invoice` can fragment the case, but because there is one object per logistics/financial type, the damage is limited.

**Stability under repair.**  
Stable under identifier renaming, reordering of independent `Add Item` events, and minor timestamp repairs. It remains stable if payments are enriched with amount attributes, provided the settlement remains a single complete settlement.

---

### 4.2 `SEM-SPLIT-CONSOL`: split packages, consolidated delivery

**Signature.** `pack=2; dispatch=1; invoice=1; payment=1; ext=none`.

**Business behavior.**  
X3 packs items separately but dispatches them together. This may happen when items come from different locations, have different availability dates, or require separate handling, but the carrier consolidates the shipment.

**Operational risks or opportunities.**  
The key risk is consolidation failure: one package may be ready while the other is delayed, causing dispatch holds or incomplete shipments. The opportunity is reduced shipping cost through consolidation.

**Poor flattening.**  
An `Order`-only trace hides the fact that there are two packages. A `Package`-centric flattening creates two package cases that both point to the same delivery and invoice, making the consolidation relationship hard to see.

**Stability under repair.**  
Stable if the two `Pack Package` events and the one `Dispatch` event are preserved. It becomes unstable if repeated `Pack Package` events are collapsed, because then X3 looks like the baseline.

---

### 4.3 `SEM-SPLIT-PARTIAL`: split fulfillment and partial payment

**Signature.** `pack=2; dispatch=2; payment=2; partial_settles; completes_settlement`.

**Business behavior.**  
X4 fulfills items as soon as they are packed and allows payment in multiple steps. The first payment partially settles the invoice; the second completes settlement.

**Operational risks or opportunities.**  
Risks include revenue-recognition ambiguity, payment-allocation errors, incomplete delivery tracking, and customer confusion. Opportunities include faster partial fulfillment and flexible payment terms.

**Poor flattening.**  
An `Order`-level flattened trace may show repeated activities but may lose the partial-payment semantics. A `Payment`-centric flattening may lose the connection between deliveries and payment installments.

**Stability under repair.**  
Stable if the two dispatches and the partial/completion payment qualifiers are preserved. If payments are reduced to a single amount attribute without installment or partial-settlement status, this cluster loses its financial distinctiveness.

---

### 4.4 `SEM-EXT-LOG`: cross-order logistics sharing

**Signature.** `base; external_logistics=true; financial_local=true`.

**Business behavior.**  
X5 is locally similar to the baseline, but its package or dispatch involves an external order/item. The physical execution is consolidated with another order-centric execution, while the invoice still bills only the local order.

**Operational risks or opportunities.**  
Risks include cost allocation, responsibility boundaries, custody ambiguity, and dependency on another execution. Opportunities include shipment consolidation and lower logistics cost.

**Poor flattening.**  
An `Order`-only flattening hides the external dependency. A `Package`-centric flattening exposes the shared package but breaks the assumption that each case belongs to one order.

**Stability under repair.**  
Stable as long as `EXT` flags are preserved. If external objects are ignored or incorrectly rewritten as local objects, X5 collapses into the baseline cluster.

---

### 4.5 `SEM-EXT-FIN`: cross-order invoice sharing

**Signature.** `base; external_financial=true; logistics_local=true`.

**Business behavior.**  
X6 has isolated logistics but shares invoice and payment with an external order. The financial lifecycle is not independent.

**Operational risks or opportunities.**  
Risks include reconciliation complexity, tax attribution, dispute handling, and lack of order-level payment allocation. Opportunities include consolidated billing and centralized payment processing.

**Poor flattening.**  
An `Order`-centric flattening hides the fact that the invoice covers multiple orders. An `Invoice`-centric flattening reveals the shared invoice but creates a multi-order case that does not align with single-order reporting.

**Stability under repair.**  
Stable if external financial participants are preserved. If external objects are ignored, X6 becomes indistinguishable from the baseline at the activity and local-object level.

---

### 4.6 `SEM-REPLACE`: replacement or removal before dispatch

**Signature.** `base; replacement=true; removed_before_dispatch`.

**Business behavior.**  
X7 looks like a baseline trace at the activity-label level, but the qualified O2O relations show that one item was replaced or removed before dispatch. The `Dispatch` event also explicitly includes an item, which is a structural clue.

**Operational risks or opportunities.**  
Risks include billing for unavailable or substituted items, inventory mismatch, customer dissatisfaction, and compliance issues if substitution is not authorized. The opportunity is flexible substitution when stock is unavailable.

**Poor flattening.**  
Activity-label flattening hides the replacement completely. Object-centric flattening without O2O qualifiers may show an extra item reference in `Dispatch`, but without the qualifier it is ambiguous.

**Stability under repair.**  
Stable if O2O qualifiers or item-level dispatch incidence are preserved. If qualifiers are ignored and the dispatch is abstracted to package-level only, X7 may incorrectly merge with the baseline.

---

### 4.7 `SEM-RETURN`: return, inspection, and repack

**Signature.** `return=true; inspect=true; pack=2; dispatch=2; lead_created=false`.

**Business behavior.**  
X8 contains a reverse-logistics motif: an item is returned, inspected, repacked, and dispatched again. The supplied trace does not contain `Create Order`; I do not invent it. The missing creation event may be an extraction boundary or a data defect.

**Operational risks or opportunities.**  
Risks include inventory-state errors, refund/replacement confusion, delayed invoicing, and return fraud. Opportunities include refurbishment, resale, and better reverse-logistics control.

**Poor flattening.**  
An `Order`-level flattening may make the second `Pack Package` and `Dispatch` look like duplicate events. A `Delivery`-centric flattening splits the story into two deliveries without explaining why the second exists.

**Stability under repair.**  
Stable if `Return Item` and `Inspect Return` are preserved. Adding a missing `Create Order` during data repair would not remove the return motif. Collapsing repeated `Pack Package`/`Dispatch` events would hide the repack but would not remove the return activities.

## 5. Borderline cases

### 5.1 X1 versus X2

`AS`, `TS`, and `BS` all treat X1 and X2 as equivalent. The only difference is local identifiers and the order in which item identifiers appear in the two `Add Item` events.

Two defensible definitions can disagree:

- **Activity-sequence or typed-structural equivalence:** they are equivalent because labels, object types, multiplicities, and incidence match after renaming.
- **Raw identifier-sensitive exact equivalence:** they are different because `I11/I12` and `I22/I21` differ. This is usually not business-meaningful unless identifiers encode products, which is not stated.

---

### 5.2 X1 versus X5

At the activity-label level, X1 and X5 are identical. The difference is that X5 includes external order/item references in logistics activities.

Two defensible definitions can disagree:

- **Activity-sequence equivalence or local-only business equivalence:** X1 and X5 are equivalent because the local order completes normally.
- **Business-semantic equivalence with external flags:** they are different because X5 depends on an external logistics execution. That dependency creates operational and compliance risks.

---

### 5.3 X1 versus X6

Again, the activity-label trace is baseline-like. The difference is that X6 shares invoice and payment with an external order.

Two defensible definitions can disagree:

- **Fulfillment-centric equivalence:** X1 and X6 are equivalent because the local package/delivery flow is baseline-like.
- **Financial/compliance-oriented equivalence:** they are different because shared invoicing and settlement create allocation and reconciliation risk.

---

### 5.4 X1 versus X7

Activity labels are the same, but X7 contains replacement semantics.

Two defensible definitions can disagree:

- **Activity-sequence equivalence:** X1 and X7 are equivalent.
- **Typed-structural or business-semantic equivalence:** they are different. X7 has an item reference in `Dispatch` and has O2O qualifiers indicating replacement/removal. If one ignores qualifiers and abstracts dispatch to package-level only, X7 may merge with X1, but that abstraction hides a business-important exception.

---

### 5.5 X3 versus X4

Both involve split packages. The difference is that X3 consolidates delivery and payment, whereas X4 splits delivery and uses partial payments.

Two defensible definitions can disagree:

- **Coarse split-package motif equivalence:** X3 and X4 belong together because both have more than one package.
- **Business-semantic equivalence:** they are different because X4 has two deliveries, two payments, and partial settlement. These differences matter for revenue recognition and delivery tracking.

---

### 5.6 X4 versus X8

Both have repeated `Pack Package` and `Dispatch` events.

Two defensible definitions can disagree:

- **Multiplicity/rework equivalence:** X4 and X8 are similar because both are multi-leg executions with repeated logistics activities.
- **Semantic reverse-logistics equivalence:** they are different. X4 is forward split fulfillment; X8 contains return, inspection, and repack. X8 also lacks `Create Order` in the supplied trace and has a different payment pattern.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is best understood as an exact or near-exact object-centric clustering utility. Its key structure preserves the observed object-centric lifecycle of objects: object type, events linked to the object, and the event/object incidence used to build the key. Depending on the OCEL representation, event identifiers, activity names, timestamps, and related object references may be part of the key. The important point is that the key is structural and exact; it is not automatically a business-semantic abstraction.

Raw object identifiers can make exact clusters too fine because local identifiers are usually arbitrary. If X1 and X2 are represented with different object identifiers and the key includes those identifiers or event identifiers tied to them, they may fall into different exact clusters even though they are structurally and semantically identical. Similarly, shared external objects can create large connected components, causing exact keys to become long and brittle.

A good post-processing strategy is:

1. run exact clustering;
2. canonicalize local identifiers;
3. normalize O2O qualifiers;
4. group exact clusters by a business signature;
5. optionally split by external-sharing domain.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# Assume `ocel` is an existing OCEL object.
# The exact API parameter names may vary by PM4Py version.
exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    max_objs=1000,  # useful for large connected components, if supported
)

def lead_objects(ocel):
    for obj_id, obj in ocel.objects.items():
        if obj.object_type == LEAD_TYPE:
            yield obj_id

def events_for_order(ocel, order_id):
    # Return events touching order_id, ordered by timestamp.
    # This helper must preserve event-object incidence.
    raise NotImplementedError

def o2o_for_order(ocel, order_id):
    # Return O2O triples relevant to the order-centric execution.
    raise NotImplementedError

semantic_groups = defaultdict(list)

for order_id in lead_objects(ocel):
    events = events_for_order(ocel, order_id)
    o2o_triples = o2o_for_order(ocel, order_id)
    sig, _ = business_signature(
        events,
        o2o_triples,
        lead_type=LEAD_TYPE,
        partial_order=False,
    )
    semantic_groups[sig].append(order_id)

# Optional: merge PM4Py exact clusters into semantic groups.
merged = defaultdict(list)

for cluster_key, members in exact_clusters.items():
    for member in members:
        if ocel.objects[member].object_type == LEAD_TYPE:
            events = events_for_order(ocel, member)
            o2o_triples = o2o_for_order(ocel, member)
            sig, _ = business_signature(
                events,
                o2o_triples,
                lead_type=LEAD_TYPE,
            )
            merged[sig].append(member)
```

Exact equivalence is preferable when the goal is data-quality checking, exact replay, debugging object lifecycles, or legal audit where every structural difference matters. Coarser business clustering is preferable when the goal is operational reporting, risk segmentation, or process improvement.

`max_objs` matters because object-centric executions can become highly connected through shared packages, deliveries, invoices, or payments. If the clustering routine limits the number of objects considered, it may truncate external dependencies or produce unstable keys. For large OCELs, one should project to lead-object neighborhoods, canonicalize identifiers, and avoid using raw global identifiers as part of the clustering key.

| Perturbation | Effect on clustering |
|---|---|
| Ignore all O2O qualifiers | X7 becomes much closer to X1. If item-level `Dispatch` incidence is also ignored, X7 may merge into `SEM-BASE`. X4 loses the distinction between partial and complete settlement, though it may remain distinct if two payment events are still counted. X8 remains distinct if `Return Item` and `Inspect Return` are preserved. |
| Ignore external objects | X5 and X6 collapse toward `SEM-BASE`, because their local activity and object structure becomes baseline-like. This hides logistics consolidation in X5 and shared billing in X6. |
| Collapse repeated same-label events | If all repeated labels are collapsed, X3 and X4 become much closer to baseline. X3 may become indistinguishable from X1 at the activity level. X4 may also lose its split-payment character if repeated `Record Payment` events are collapsed. X8 still contains return-related labels, but the repack pattern is weakened. |
| Treat Pack/Dispatch order as partial order | X1 and X2 remain equivalent. X3 and X4 remain distinct if multiplicities are preserved: X3 has two packs and one dispatch; X4 has two packs and two dispatches. Partial ordering mainly removes arbitrary distinctions between independent events. |
| Treat payment multiplicity as amount attribute | X4 becomes less financially distinct. If partial/completed status is preserved as an attribute, `SEM-SPLIT-PARTIAL` can remain meaningful. If only total amount is kept, X4 may merge with single-payment clusters on the financial dimension, although its two deliveries still distinguish it structurally. |

## 8. Limitations and recommendation

The main limitation is that the supplied executions mix event-level structure and narrative O2O qualifiers. Some distinctions, especially X7’s replacement semantics, are invisible without qualifiers. Another limitation is that external identifiers are local except for their `EXT` flag; therefore, cross-order identity cannot be resolved beyond externality. X8 also lacks `Create Order`; I preserved that absence rather than inventing an event.

Recommended equivalence levels:

- **Compliance monitoring:** use business-semantic equivalence with O2O qualifiers and external flags. Compliance cares about partial settlement, shared invoices, replacements, and returns.
- **Operational segmentation:** use business-semantic equivalence. It separates split fulfillment, consolidated delivery, external logistics, external finance, replacement, and reverse logistics.
- **Root-cause analysis:** use typed structural equivalence, optionally augmented with qualifiers. It preserves object multiplicities and event-object incidence without prematurely collapsing exceptions.
- **Descriptive reporting:** use activity-sequence equivalence or a very coarse business motif, but only with a warning that it hides object-centric exceptions such as external sharing and replacement.

No single equivalence notion is best for all purposes. Compliance needs exception semantics; operations needs motif segmentation; root-cause analysis needs structural precision; descriptive reporting needs simplicity. The right clustering depends on which differences are considered noise and which differences carry risk.
