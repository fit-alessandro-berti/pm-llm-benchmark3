## 1. Temporal Data Semantics

**State reconstruction.** For each case I order events by `(time:timestamp, event_index)`. I maintain a running "case state" of the mutable attributes `amount`, `risk_level`, `jurisdiction`, `customer_type`, and any exemption reference. The state at any event E is the last non-blank value observed for each attribute at an event whose `(timestamp, event_index)` is less than or equal to E's. This is a *forward* reconstruction only: I never let a value observed later in the trace govern an earlier event.

**Blanks.** A blank attribute cell means "no update at this event," not `null`. Blanks are skipped during forward-fill; they neither overwrite nor erase the carried value. A blank is therefore evidence of *silence*, not of a value.

**Equal timestamps.** When two events share a `time:timestamp`, `event_index` is the strict tie-breaker. The event with the lower `event_index` is earlier and its effect is established first. I state the consequence explicitly wherever it changes an outcome (notably TX-311, where the Enhanced_Review at index 3 precedes the jurisdiction change to DE at index 4 under the same 16:20 timestamp).

**Material changes.** "Material" for amount-dependent obligations (R1, R4) means an amount increase of more than 20% relative to the amount that a prior review was performed against. A decrease is not material and does not invalidate a review. An increase from an *unknown* amount is not safely classifiable (R4 + R6). Jurisdiction changes are material to R1/R3, risk/customer-type changes are material to R2.

**Final attributes.** I do not copy the final case state backward. A late high-value settlement figure (TX-305) or a decreased final amount (TX-308) governs only the events at or after the point where it becomes the effective value; it does not retroactively define the state that governed release unless the evidence establishes that effective time.

**Four distinct clocks.** I separate:
- **Event time** — `time:timestamp` of the logged event (when the activity was recorded to have occurred).
- **Effective time** — the time from which a value/exemption is stipulated to govern (e.g., an exemption's `effective_from`; an amount update's effective time is its event timestamp unless evidence says otherwise).
- **Record time** — when a row was written to the store (e.g., TX-302's `Record_Exemption` database insert at 11:00; TX-310's late record at 11:00).
- **Evidence time** — when the authenticating artifact was created (e.g., EX-77's qualified signature at 09:05; EX-88's signing certificate at 10:30, after release).

An update is effective at its event timestamp unless the evidence explicitly establishes another effective time. Record time later than an obligation trigger does *not* defeat the exemption if independent evidence (a qualified signature) fixes an earlier effective/evidence time (EX-77). Conversely, a displayed/backdated effective field is *not* conclusive when the only authenticating evidence is created after release (EX-88).

**Formal pseudo-logic.** Let `≺` denote strict temporal precedence under the `(timestamp, event_index)` total order; `state(A, t)` = latest-known value of attribute `A` at event time `t`; `R = Release_Funds`.

```
% Direction key: X ≺ Y  ==  X strictly precedes Y.

R1(c):  release(c,R) ∧ state(jurisdiction,R) ≠ DE ∧ state(amount,R) ≥ 100000
        ⇒ ∃ er ( Enhanced_Review(c,er) ∧ er ≺ R
                 ∧ ∀ m (material_change(c,m) ∧ m ≺ R → m ≺ er) )
           ∨ valid_exemption_R1(c,R).

R2(c):  release(c,R) ∧ (state(risk,R)=HIGH ∨ state(ctype,R)=PEP)
        ⇒ ∃ er,ca ( Enhanced_Review(c,er) ∧ Compliance_Approve(c,ca)
                    ∧ er ≺ ca ∧ ca ≺ R
                    ∧ covers(ca, er) ).          % CA must review the Enhanced_Review packet

R3(c):  release(c,R) ∧ ∃ u ( Sanctions_List_Update(c,u)
                    ∧ adds(state(jurisdiction,R)) ∧ latest_Sanctions_Screen(c) ≺ u ∧ u ≺ R )
        ⇒ ∃ s ( Sanctions_Screen(c,s) ∧ u ≺ s ∧ s ≺ R ).

R4(c):  ∀ rev ∈ {Standard_Review, Enhanced_Review}, ∀ up (
          rev ≺ up ∧ up ≺ R ∧ amount(up) > 1.20 · amount_at(rev)
          → ¬valid_for_amount(rev) ).
        % base amount unknown ⇒ relation undefined ⇒ INDETERMINATE (R6).

R5(e,trigger): valid(e,trigger) ⇔
          approved_by(e)=Head_Compliance
          ∧ effective_from(e) ≤ trigger
          ∧ scope_match(e, jurisdiction, ctype, amount@trigger)
          ∧ ¬expired(e, trigger)
          ∧ evidence_supports_approval_at(e, trigger).
        % record_time(e) > trigger allowed IF signature/evidence fixes approval ≤ trigger.
        % displayed backdated field alone (no timely qualified evidence) ⇒ ¬valid.

R6(c,rule): ¬can_establish(trigger(rule),c) ∧ ¬can_exclude(trigger(rule),c)
        ⇒ classify(c,rule) = INDETERMINATE   (never default to low-risk).

R7:  every predicate above reads state(A,t) = last non-blank A at event ⪯ t,
     with (timestamp, event_index) as the total order; equal timestamps ordered by event_index.
```

## 4. Ambiguities and Alternative Readings

**TX-302 (explicit).** Classified JUSTIFIED_EXCEPTION on the strength that a *qualified* signature at 09:05 plus a documented outage explains the 11:00 record time — record time ≠ evidence time. Alternative reading: if one insisted that only the persisted database record can establish approval (record-time-strict policy), the exemption would not be "valid at the trigger" and TX-302 would fall to NONCOMPLIANT (R1 with no waiver). The result flips on whether qualified-signature evidence at effective time overrides a late record.

**TX-305 (INDETERMINATE, explicit).** Turns entirely on the release-time amount. If an immutable release payload had carried the amount, or if policy stipulated that the settlement figure (150k) reliably equals the release amount at release effective time, R1 would trigger and — with an Enhanced_Review before release and no material change — likely resolve to COMPLIANT. Conversely, evidence that the release amount was < 100k would make it COMPLIANT with R1 untriggered. Absent either, R6 forbids defaulting; INDETERMINATE stands. Note the settlement's *evidence/effective time* is the next day, so it cannot be back-projected onto release.

**TX-310 (explicit).** Turns on EX-88's evidence quality. As given, the qualified signing certificate post-dates release (10:30 > 10:00) and the only corroborating witness is the transaction requester (self-interested), so R5's "evidence supports approval existed at the relevant time" fails ⇒ NONCOMPLIANT. If an *independent* attestation or a qualified signature timestamped ≤ release surfaced, EX-88 could become valid and the case JUSTIFIED_EXCEPTION. This is the deliberate contrast with EX-77.

**TX-311 (explicit).** Turns on same-timestamp ordering. Under the stated `event_index` semantics, the Enhanced_Review (idx3) precedes the jurisdiction change to DE (idx4) at 16:20, and the release-time jurisdiction is DE ⇒ R1 does not trigger ⇒ COMPLIANT. Alternative reading A: if the two 16:20 events were treated as simultaneous/unordered, the DE change's effect on release would be ambiguous and the case could become INDETERMINATE. Alternative reading B: if the jurisdiction that *governed the review* (still non-DE at idx3) were the relevant snapshot for R1, then a foreign 115k transaction reviewed before a jurisdiction flip could be read as compliant-by-review; either way the release-time snapshot is DE, so no foreign high-value obligation attaches.

**TX-308 (additional).** If policy read *any* post-review amount change (including decreases) as invalidating, the Enhanced_Review would be void and TX-308 NONCOMPLIANT. R4 explicitly exempts decreases, so it is COMPLIANT; the ambiguity is purely interpretive.

**TX-301 (additional).** Unambiguous as NONCOMPLIANT, but note two independent failure paths converge: (a) never had an Enhanced_Review, and (b) even a prior Standard_Review would be void under R4 (+56%). Only reclassification of "Standard_Review counts as Enhanced_Review" — which the semantic facts forbid — would change it.

```python
    else:
        r1_flag = "NOT_TRIGGERED"

    # R2 trigger
    if (risk == "HIGH") or (ctype == "PEP"):
        r2_ok = (t_enh is not None) and (t_ca is not None) and (t_enh < t_ca < r_ord)
        r2_flag = "OBLIGATION_MET" if r2_ok else "OBLIGATION_UNMET"
    elif pd.isna(risk) or pd.isna(ctype):
        # trigger cannot be excluded when a decisive attribute is unknown
        r2_flag = "INDETERMINATE"
    else:
        r2_flag = "NOT_TRIGGERED"

    # R3 trigger: jurisdiction added to list after last screen, before release, no re-screen
    if t_upd is not None and t_scr is not None and t_scr < t_upd < r_ord:
        rescreen = g[(g["concept:name"] == "Sanctions_Screen") &
                     (g["_ord"] > t_upd) & (g["_ord"] < r_ord)]
        r3_flag = "OBLIGATION_MET" if len(rescreen) else "OBLIGATION_UNMET"
    else:
        r3_flag = "NOT_TRIGGERED"

    # R4 as a modifier flag
    r4_flag = ("INVALIDATES_REVIEW" if material_increase_after_review
               else ("UNCLASSIFIABLE_UNKNOWN_BASE" if increase_from_unknown else "OK"))

    # --- exemption join + R5 evaluation ---
    ex_ref = None
    ex_events = g[g["exemption_ref"].notna()]
    if len(ex_events):
        ex_ref = ex_events.sort_values("_ord")["exemption_ref"].iloc[0]
    ex_verdict = "NONE"
    if ex_ref in EXEMPTIONS:
        e = EXEMPTIONS[ex_ref]
        scope_ok = (juris == e["juris"] and ctype == e["ctype"]
                    and (not amount_unknown) and amount <= e["amount_max"])
        timing_ok = e["effective"] <= r["time:timestamp"] <= e["expires"]
        approved_ok = e["approved_by"] == "Head_Compliance"
        evidence_ok = e["evidence_supports_timely"]  # record_time>trigger tolerated iff evidence
        ex_verdict = ("VALID" if (scope_ok and timing_ok and approved_ok and evidence_ok)
                      else "INVALID")

    # --- Coarse machine label; humans resolve REVIEW_REQUIRED / INDETERMINATE ---
    if amount_unknown and (juris not in (None,) and juris != "DE"):
        machine_label = "INDETERMINATE"
    elif r1_flag == "INDETERMINATE" or r2_flag == "INDETERMINATE":
        machine_label = "INDETERMINATE"
    elif "OBLIGATION_UNMET" in (r1_flag, r2_flag, r3_flag):
        # unmet R1 may be cured by a VALID exemption that waives R1
        if r1_flag == "OBLIGATION_UNMET" and ex_verdict == "VALID" and "R1" in EXEMPTIONS.get(ex_ref, {}).get("waives", []) \
           and r2_flag in ("NOT_TRIGGERED", "OBLIGATION_MET") and r3_flag in ("NOT_TRIGGERED", "OBLIGATION_MET"):
            machine_label = "REVIEW_REQUIRED"  # justified-exception candidate
        else:
            machine_label = "NONCOMPLIANT"
    elif ex_ref in EXEMPTIONS:
        machine_label = "REVIEW_REQUIRED"  # exemption invoked -> needs evidential judgment
    else:
        machine_label = "COMPLIANT"

    rows.append(dict(
        case=case, amount=amount, amount_unknown=amount_unknown, risk=risk,
        jurisdiction=juris, customer_type=ctype,
        R1=r1_flag, R2=r2_flag, R3=r3_flag, R4=r4_flag,
        t_std=t_std, t_enh=t_enh, t_ca=t_ca, t_scr=t_scr, t_list_update=t_upd,
        material_increase_after_review=material_increase_after_review,
        increase_from_unknown_base=increase_from_unknown,
        exemption=ex_ref, exemption_verdict=ex_verdict,
        exemption_record_time=(EXEMPTIONS[ex_ref]["record_time"] if ex_ref in EXEMPTIONS else None),
        exemption_evidence_time=(EXEMPTIONS[ex_ref]["evidence_time"] if ex_ref in EXEMPTIONS else None),
        machine_label=machine_label,
    ))

# --- 7. Case-level diagnostics dataframe ---
diagnostics = pd.DataFrame(rows).set_index("case")
pd.set_option("display.width", 200, "display.max_columns", 50)
print(diagnostics.to_string())

# --- 8. Coarse DECLARE / trace-order check (control-flow ONLY; see section 6) ---
# Example: "Release_Funds must be preceded by Enhanced_Review" as a precedence constraint.
def coarse_precedence(activity_a, activity_b):
    """Returns cases where b occurs without any preceding a (order-only, data-blind)."""
    viol = []
    for case, g in df.groupby("case:concept:name"):
        g = g.sort_values(["time:timestamp", "event_index"])
        seq = list(g["concept:name"])
        for i, act in enumerate(seq):
            if act == activity_b and activity_a not in seq[:i]:
                viol.append(case)
                break
    return viol

print("\nControl-flow-only precedence(Enhanced_Review -> Release_Funds) violations:")
print(coarse_precedence("Enhanced_Review", "Release_Funds"))
# NOTE: This flag is unconditional. It wrongly flags DE/low-value cases that never needed
# an Enhanced_Review, and it CANNOT see amount>=100k, exemption validity, material changes,
# same-timestamp ordering, or unknown values. It is provided only to contrast with the
# data-aware diagnostics above; it must not be used as the compliance verdict.
```

The code emits a diagnostics table with per-rule coarse flags, milestone timestamps, unknown-value flags, exemption record/evidence times, and a `machine_label` that leaves `REVIEW_REQUIRED`/`INDETERMINATE` for human evidential judgment. It never encodes the narrative verdicts as a per-case lookup.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A control-flow model (and naïve data checks) reads the last-known attribute of a case and projects it onto earlier events. TX-308's final 100k or TX-305's next-day 150k would be back-copied onto the release decision, corrupting the snapshot. Correct evaluation needs event-time state, not case-final state.

2. **Post-hoc / late-recorded exemptions.** TX-302's exemption row is inserted at 11:00, *after* the 09:40 release; TX-310's exemption record lands at 11:00 too. A trace-order model either can't see the exemption before release (false violation) or naïvely accepts it (false pass). Distinguishing valid EX-77 from invalid EX-88 requires reasoning over record time vs. evidence time vs. effective time — outside control flow entirely.

3. **Material changes after review.** R4 depends on a numeric comparison (>20% increase) between the amount at review and the amount after an update. TX-309's Enhanced_Review is invalidated by a +22.9% bump; TX-306's +4.5% and TX-308's decrease are not. A DECLARE/precedence check sees "Enhanced_Review then Release_Funds" as satisfied in all three and cannot tell them apart.

4. **Conditional activation.** Obligations fire only under data conditions (amount ≥ 100k, jurisdiction ≠ DE, risk HIGH, customer PEP). TX-311 (DE at release) and TX-304 (60k) don't trigger R1 at all, while TX-301 does. A control-flow constraint is unconditional: making "Enhanced_Review precedes Release_Funds" mandatory over-flags DE/low-value cases and, if made optional, under-flags the ones that needed it.

5. **Missing data.** TX-305 has no release-time amount. Control-flow conformance has no notion of "unknown"; it silently treats the absence as satisfied or defaults it, violating R6. Only a data-aware evaluator can raise INDETERMINATE instead of guessing a low-risk value.

6. **Same-timestamp ordering.** TX-311 hinges on `event_index` distinguishing the Enhanced_Review (idx3) from the jurisdiction change (idx4) at the identical 16:20 timestamp. Most control-flow discovery/conformance treats equal timestamps as unordered or arbitrary, losing the very fact that determines whether the review preceded the change.

7. **(Additional) Semantics of activity identity.** "Standard_Review ≠ Enhanced_Review" and "a Compliance_Approve over a standard packet does not cure a missing Enhanced_Review" (TX-307) are content/scope facts about *what an event certified*, not about ordering. Control-flow labels are opaque to packet scope.

8. **(Additional) Cross-event arithmetic and register joins.** R1 thresholds, R4 percentages, R5 scope matching, and expiry windows require joining events to an external exemption register and doing arithmetic/temporal comparisons — none expressible as trace ordering.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** Persist a signed, tamper-evident snapshot at `Release_Funds` capturing amount, risk, jurisdiction, customer_type, and the exemption_id relied upon. This alone would resolve TX-305 (no release-time amount) and remove reliance on later settlement figures.
- **Explicit four-clock timestamps on every material row.** Record `event_time`, `effective_from`, `record_time` (DB write), and `signature/evidence_time` separately. This is exactly what separates valid EX-77 (signature 09:05, record 11:00) from invalid EX-88 (certificate 10:30 post-release).
- **Rule version stamping.** Tag each evaluation with the policy/ruleset version in force at event time so retroactive rule edits cannot silently re-decide historical cases.
- **Structured exemption scope + independent approval evidence.** Store jurisdiction, customer-type, amount ceiling, waived-rule list, effective/expiry, approver identity, and a qualified signature; require an *independent* attester (not the transaction requester, cf. EX-88) and reject displayed-backdated fields lacking timely qualified evidence.
- **Change provenance.** For every attribute update, log old value, new value, source system, actor, and reason, so amount/jurisdiction/risk trajectories (and R4 percentages) are auditable and material changes are unambiguous.
- **Stable, explicit event ordering.** Emit a monotonic per-case sequence number alongside the timestamp so equal-timestamp events (TX-311) are ordered deterministically at the source rather than reconstructed by `event_index` heuristics.
- **Review-scope attributes.** Annotate each review/approval with the packet type it covered (standard vs. enhanced) and the exact amount/jurisdiction/risk state it examined, so R2 packet-cure questions (TX-307) and R4 review-basis questions are decidable from the log.
- **Sanctions-list versioning.** Log list-version identifiers on both `Sanctions_Screen` and `Sanctions_List_Update` so R3 re-screen obligations can be verified against the specific list state that changed.
