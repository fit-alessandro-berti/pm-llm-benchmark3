# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. Activity labels are exactly the 18 labels listed, with no aliases.
2. A case is identified by `case:concept:name`; events carry `time:timestamp` and `org:resource`.
3. Hours in the test cases are relative to case start and are converted to seconds for the temporal profile.
4. The stable procedural backbone is mandatory for every case; cross-cutting activities are optional unless triggered.
5. Clarification is modeled as a loop before `Classify Risk` in the procedural backbone. The DECLARE layer remains authoritative for the general rule “every request must be answered before the next request and before a final outcome”.
6. `Sanctions Escalation` is treated as part of the high-risk sanctioned route. This is a modeling choice; the rules alone do not explicitly forbid sanctions escalation in a low-risk route, but the implemented process tree keeps the strict legal order.
7. `Change Bank Details` is modeled as one optional pre-release block after activation. Post-release changes and multiple change cycles are deliberately left to external/data-aware validation rather than forced into a block-structured tree.
8. Temporal-profile deviations are warnings, not automatic rejections.

## R5/R6 conflict

The conflict is between:

- **R5 / Legal**: after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` under all circumstances.
- **R6 / Operations**: emergency activation may occur before `Obtain Legal Opinion`, but only when jointly authorized outside the event log, and the opinion must arrive within 24 hours.

### Resolution A — strict legal supremacy

R5 is absolute. R6 is not executable from the activity log because there is no `emergency` attribute or authorization event. Traces such as T6 fail.

**Compliance risk:** legitimate emergency cases that were authorized outside the system will be rejected or flagged.

### Resolution B — managed exception

R5 is the default rule. R6 is an explicit exception checked only in the resource/data layer when an `emergency_joint_authorized` attribute is present and the legal opinion timestamp is within 24 hours of activation. Without that attribute, the trace is evaluated under strict R5.

**Compliance risk:** the decision depends on externally supplied data quality. If the authorization attribute is missing, a valid emergency case fails; if it is recorded wrongly, the exception may hide an unauthorized activation.

### Chosen resolution for the implemented model

I adopt **Resolution B as the overall governance model**, but the activity-only formalisms implement the strict R5 order. The procedural and log-skeleton layers therefore use a conservative strict-R5 model. The resource/data layer separately evaluates the R6 exception. This avoids silently combining two policies in one notation.

## 3.2 PM4Py Python code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def seq(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

def par(*children):
    return ProcessTree(operator=Operator.PARALLEL, children=list(children))

def loop(body, redo):
    return ProcessTree(operator=Operator.LOOP, children=[body, redo])

def silent():
    return ProcessTree(label=None)

procedural_model = seq(
    leaf("Receive Onboarding Request"),

    par(
        leaf("Capture Master Data"),
        leaf("Run Sanctions Screening"),
        leaf("Verify Bank Account")
    ),

    loop(
        silent(),
        seq(leaf("Request Clarification"), leaf("Receive Clarification"))
    ),

    leaf("Classify Risk"),

    xor(
        seq(leaf("Reject Vendor"), leaf("Close Onboarding")),

        seq(
            xor(
                leaf("Manager Approval"),
                seq(leaf("Enhanced Due Diligence"), leaf("Compliance Approval"))
            ),
            leaf("Activate Vendor"),
            xor(
                silent(),
                seq(leaf("Change Bank Details"), leaf("Suspend Vendor"), leaf("Verify Bank Account"))
            ),
            leaf("Release First Payment"),
            leaf("Close Onboarding")
        ),

        seq(
            leaf("Sanctions Escalation"),
            leaf("Enhanced Due Diligence"),
            leaf("Obtain Legal Opinion"),
            leaf("Compliance Approval"),
            leaf("Activate Vendor"),
            xor(
                silent(),
                seq(leaf("Change Bank Details"), leaf("Suspend Vendor"), leaf("Verify Bank Account"))
            ),
            leaf("Release First Payment"),
            leaf("Close Onboarding")
        )
    )
)
```

## 3.3 Explanation

- **Concurrency:** `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` are modeled as a `PAR` block after `Receive Onboarding Request`.
- **Choice:** `Classify Risk` is followed by a three-way XOR: rejection, standard acceptance, or sanctioned high-risk acceptance. The standard acceptance branch chooses either low-risk (`Manager Approval`) or high-risk without sanctions (`Enhanced Due Diligence  Compliance Approval`).
- **Clarification loops:** the tree places a silent-body loop before `Classify Risk`, allowing zero or more `Request Clarification  Receive Clarification` cycles. This is a block-structured approximation; the general rule is further enforced by DECLARE.
- **Terminal outcomes:** `Close Onboarding` occurs either after `Reject Vendor` or after `Release First Payment`.
- **Post-activation behavior:** one optional `Change Bank Details  Suspend Vendor  Verify Bank Account` block is included before `Release First Payment`. Multiple change cycles and post-release changes are deliberately excluded from the procedural model.

## 4.1 Rule semantics

| DECLARE rule | Direction / meaning |
|---|---:|
| `init("Receive Onboarding Request")` | Every trace must start with `Receive Onboarding Request`. |
| `existence(A)` | The mandatory backbone activities must occur at least once. |
| `noncoexistence(A,B)` | `A` and `B` must never occur together in the same case. Pairs encode R1, R2 support, and R8. |
| `altresponse(Request Clarification, Receive Clarification)` | Every `Request Clarification` must eventually be followed by `Receive Clarification`, and no new `Request Clarification` may occur before that `Receive Clarification`. This is different from plain `response`, which would allow multiple requests before the first response. |
| `precedence(Request Clarification, Receive Clarification)` | Every `Receive Clarification` must be preceded by an earlier `Request Clarification`. |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | Every `Sanctions Escalation` must be preceded by `Run Sanctions Screening`. |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | Every `Sanctions Escalation` must eventually be followed by `Obtain Legal Opinion`. |
| `response(Change Bank Details, Suspend Vendor)` | Every `Change Bank Details` must eventually be followed by `Suspend Vendor`. |
| `response(Change Bank Details, Verify Bank Account)` | Every `Change Bank Details` must eventually be followed by another `Verify Bank Account`. |

Note: R5 cannot be encoded as a simple DECLARE `precedence("Obtain Legal Opinion", "Activate Vendor")` because that would incorrectly force legal opinion in low-risk and non-sanctioned cases.

## 5.1 Orientation and overlap

I use the following orientation:

- `equivalence(A,B)`: occurrences of `A` and `B` have identical counts.
- `always_before(A,B)`: whenever both `A` and `B` occur, `A` occurs before `B`.
- `always_after(A,B)`: whenever both `A` and `B` occur, `A` occurs after `B`.
- `never_together(A,B)`: `A` and `B` never co-occur.
- `directly_follows(A,B)`: when `A` occurs in a valid trace, `B` must be the next event.

Overlaps and disagreements:

- `never_together` overlaps with DECLARE `noncoexistence`.
- `always_before` overlaps with several procedural order constraints and DECLARE `precedence` for `Run Sanctions Screening  Sanctions Escalation`.
- `directly_follows` is deliberately sparse because concurrent interleavings make many direct-succession relations unstable.
- `Verify Bank Account` is allowed to occur `{1,2}` because of the post-change re-verification path. It is therefore not placed in equivalence with one-occurrence activities.

Temporal deviations are warnings rather than control-flow rejections because R12 explicitly says these expectations are “normative enough to flag but not automatically reject”. They may indicate delay, scheduling, or data-quality issues but do not by themselves invalidate a case.

## 7.2 Segregation-of-duties checks

```python
import pandas as pd

def check_four_eyes(log: pd.DataFrame):
    findings = []

    required_cols = {
        "case:concept:name",
        "concept:name",
        "time:timestamp",
        "org:resource"
    }

    if not required_cols.issubset(log.columns):
        raise ValueError("Missing required event attributes")

    for case_id, case in log.groupby("case:concept:name", sort=False):

        def resource_of(activity):
            evs = case[case["concept:name"] == activity]
            if evs.empty:
                return None

            vals = evs["org:resource"].dropna().unique()
            if len(vals) == 0:
                return "MISSING"
            if len(vals) > 1:
                return "MULTIPLE"
            return vals[0]

        verify_res = resource_of("Verify Bank Account")
        capture_res = resource_of("Capture Master Data")
        activate_res = resource_of("Activate Vendor")

        # R9a: Verify vs applicable approval
        approvals = case[
            case["concept:name"].isin(["Manager Approval", "Compliance Approval"])
        ]

        for _, appr in approvals.iterrows():
            appr_act = appr["concept:name"]
            appr_res = appr["org:resource"]

            if pd.isna(appr_res):
                findings.append(
                    {
                        "case": case_id,
                        "rule": "R9",
                        "verdict": "warning",
                        "detail": f"missing org:resource for {appr_act}"
                    }
                )
            elif verify_res == "MISSING":
                findings.append(
                    {
                        "case": case_id,
                        "rule": "R9",
                        "verdict": "warning",
                        "detail": "missing org:resource for Verify Bank Account"
                    }
                )
            elif appr_res == verify_res:
                findings.append(
                    {
                        "case": case_id,
                        "rule": "R9",
                        "verdict": "fail",
                        "detail": f"{appr_act} performed by same resource as Verify Bank Account"
                    }
                )

        # R9b: Capture Master Data vs Activate Vendor
        if capture_res == "MISSING" or activate_res == "MISSING":
            findings.append(
                {
                    "case": case_id,
                    "rule": "R9",
                    "verdict": "warning",
                    "detail": "missing org:resource for Capture Master Data or Activate Vendor"
                }
            )
        elif capture_res is not None and activate_res is not None and capture_res == activate_res:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R9",
                    "verdict": "fail",
                    "detail": "Capture Master Data and Activate Vendor performed by same resource"
                }
            )

    return findings
```

PM4Py can be used as a screening helper:

```python
pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Compliance Approval")
pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")
```

However, the explicit function above is authoritative because it handles missing resources and records which approval event caused the violation.

## 7.3 Emergency-policy check

```python
def check_emergency_policy(log: pd.DataFrame):
    findings = []

    for case_id, case in log.groupby("case:concept:name", sort=False):
        acts = case["concept:name"].tolist()

        if "Sanctions Escalation" not in acts:
            continue

        sanctions_time = case.loc[
            case["concept:name"] == "Sanctions Escalation", "time:timestamp"
        ].iloc[0]

        legal_evs = case[case["concept:name"] == "Obtain Legal Opinion"]
        activation_evs = case[case["concept:name"] == "Activate Vendor"]

        if legal_evs.empty:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R4/R5",
                    "verdict": "fail",
                    "detail": "Sanctions Escalation without Obtain Legal Opinion"
                }
            )
            continue

        legal_time = legal_evs["time:timestamp"].iloc[0]

        if activation_evs.empty:
            if legal_time >= sanctions_time:
                continue
            else:
                findings.append(
                    {
                        "case": case_id,
                        "rule": "R4",
                        "verdict": "fail",
                        "detail": "Obtain Legal Opinion before Sanctions Escalation"
                    }
                )
                continue

        activation_time = activation_evs["time:timestamp"].iloc[0]

        if legal_time <= activation_time:
            # Strict R5 satisfied
            continue

        # Activation before legal opinion: strict R5 violation unless R6 exception applies
        auth_vals = []
        if "emergency_joint_authorized" in activation_evs.columns:
            auth_vals = activation_evs["emergency_joint_authorized"].dropna().unique()

        if len(auth_vals) == 0:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R5/R6",
                    "verdict": "fail",
                    "detail": "Activation before Obtain Legal Opinion and missing emergency_joint_authorized"
                }
            )
            continue

        authorized = bool(auth_vals[0])

        if not authorized:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R5/R6",
                    "verdict": "fail",
                    "detail": "Activation before Obtain Legal Opinion without joint authorization"
                }
            )
            continue

        if (legal_time - activation_time).total_seconds() <= 86400:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R6",
                    "verdict": "policy-dependent",
                    "detail": "Emergency exception satisfied: authorized and legal opinion within 24h"
                }
            )
        else:
            findings.append(
                {
                    "case": case_id,
                    "rule": "R5/R6",
                    "verdict": "fail",
                    "detail": "Emergency legal opinion later than 24h after activation"
                }
            )

    return findings
```

What to do when attributes are missing:

- `org:resource` missing on a relevant activity: record a `warning` and do not issue a resource-layer `pass`.
- `emergency_joint_authorized` missing when activation occurs before legal opinion: treat as no emergency exception and record a strict R5 `fail`.
- Activity absent: skip the check for that activity unless a triggered rule is already violated.

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement across layers

- R1 is enforced by DECLARE `noncoexistence`, Log Skeleton `never_together`, and procedural XOR.
- R2 is partially enforced by procedural XOR and DECLARE `noncoexistence`.
- R7 is enforced by DECLARE `precedence` and Log Skeleton `always_before`.
- R8 is enforced by DECLARE `noncoexistence`, Log Skeleton `never_together`, and procedural XOR.
- R11 is partially enforced by the process tree and DECLARE `response`.

Duplication is useful for defense-in-depth but can produce multiple signals for the same violation. A conformance report should group multiple violations under the business rule rather than show them as unrelated.

## Constraints that become inconsistent under loops or post-activation changes

- The process tree supports one pre-release `Change Bank Details` cycle. Multiple cycles, or changes after first payment, are not captured. A general solution would require a non-block-structured loop or an accepting Petri net with loop-back arcs.
- Log Skeleton `activ_freq` for `Verify Bank Account` is set to `{1,2}`. If multiple changes are allowed, this becomes too restrictive.
- The clarification loop in the process tree is block-structured before `Classify Risk`; arbitrary clarification cycles after classification are only partially enforced by DECLARE.

## Vacuity in declarative rules

- `response("Sanctions Escalation", "Obtain Legal Opinion")` is vacuously satisfied in low-risk and standard high-risk cases.
- `altresponse("Request Clarification", "Receive Clarification")` is vacuously satisfied when no clarification occurs.
- Vacuity is not itself a defect, but it means pass results for these constraints do not prove the rule was meaningful in that case.

## Missing case attributes

- The event log has no `emergency` attribute or joint authorization. R6 cannot be verified without external data.
- Resource checks depend on `org:resource`. Missing values create warnings rather than clean passes.

## Timestamp-only limitations

- Timestamps give order, not authorization or causation.
- Relative hours may hide calendars, weekends, or time-zone issues.
- Temporal-profile checks cannot distinguish an acceptable delay caused by external dependency from an internal control failure.

## Risk of treating support/confidence metadata as normative truth

- `support: 1.0` and `confidence: 1.0` in the DECLARE dictionary encode policy belief. They are not empirical support values learned from a log. If discovered support were used, rare violations could incorrectly lower a rule’s authority.
- A conformance model should not be re-mined from a non-conforming log and then interpreted as a normative standard.

# 10. Deployment Recommendation

## Canonical procedural representation

Use the strict ProcessTree from Section 3 as the canonical procedural backbone. It captures the stable control flow cleanly and is executable in PM4Py.

## Authoritative policy layer

- Procedural ProcessTree: authoritative for stable backbone, primary choice, and strict R5 order.
- DECLARE: authoritative for cross-cutting activity order and response rules, especially clarification.
- Log Skeleton: authoritative for occurrence-count constraints and pairwise never-together checks.
- Resource/data layer: authoritative for R9 segregation of duties and the R6 emergency exception.
- Temporal profile: warning-only layer for R12.

## Recommended conformance-check order

1. **Attribute validation:** check required columns and flag missing `org:resource` or missing emergency authorization.
2. **Procedural backbone:** catch gross control-flow deviations.
3. **DECLARE:** catch cross-cutting response, precedence, and noncoexistence violations.
4. **Log Skeleton:** catch frequency and never-together violations.
5. **Resource/data checks:** evaluate R9 and R6.
6. **Temporal profile:** flag elapsed-time deviations as warnings.
7. **Surface results:** group violations by business rule and separate `fail`, `warning`, and `policy-dependent` outcomes.

## Handling contradictory findings

When strict R5 and R6 conflict, the system should label the case as `policy-dependent`, not silently convert a `fail` into a `pass`. The resource/data layer must require explicit `emergency_joint_authorized` evidence before the R6 exception can override the strict R5 result. Contradictions like T6 should be shown to users as: “Strict legal order violated; emergency exception not proven from log attributes.”
