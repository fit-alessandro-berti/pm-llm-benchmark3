| **O6** | **Recoverability — limit the window for irreversible harm** — even if a defective payment is released, it should be caught before bank settlement makes recovery impossible. | **Preventive**: blocks before release, eliminating the recovery problem entirely. | **Hybrid**: if before release, preventive; if after release but before settlement, can halt the irreversible step; if after settlement, purely detective. | **Partially corrective**: effective only if audit occurs within ~24 h (bank recall window). One-business-day SLA may exceed this window. | Cond. 6 (MG-4 before settlement) and cond. 7 (audit within 1 BD) address this, but 1 BD can exceed the 24 h bank recall limit. | The mismatch between ED-1's one-business-day audit SLA and the 24 h bank recall window is a structural gap. |

**Summary**: No single compensating control covers all six objectives. AV-2 is strongest for O1, O2, and O4 but silent on O3, O5, and O6. MG-4 is the broadest control but weakest when rubber-stamped. RA-7 is purely detective with limited corrective capacity. ED-1 layers conditions but still cannot guarantee O3 or O5.

## 2. Equivalence and Sufficiency Test

### Structured Test Criteria

A compensating-control package is evaluated on **seven dimensions**:

| Dimension | Fully Equivalent | Partially Equivalent | Merely Mitigating | Ineffective |
|-----------|-----------------|---------------------|-------------------|-------------|
| **Timing** | Preventive gate before the irreversible step (release or settlement, whichever is later in the causal chain). | Gate after release but before settlement (can still intercept). | Gate after settlement (detective only). | No timing-relevant gate. |
| **Independence** | Reviewer is a different human with no reporting-line conflict, shared credentials, or familial/financial relationship to the preparer. | Different human but with a material relationship (e.g., direct supervisor who sets ratings). | Same human using different credentials or a nominally different shared-service account. | Same human, same credentials, or credentials known to be shared. |
| **Coverage** | Controls address all six objectives from §1 (O1–O6). | Controls address  4 objectives with acceptable residual on the remainder. | Controls address 1–3 objectives; critical gaps remain. | Controls miss the dominant threat scenario for the case. |
| **Overrideability** | Cannot be overridden by the preparer acting alone. | Can be overridden but only by a more senior, independent person with documented justification. | Can be overridden by the preparer using a borrowed or shared credential. | Preparer can unilaterally bypass without any approval trail. |
| **Recoverability** | Defect can still be corrected (payment blocked, recalled, or recovered) after the compensating control detects it. | Defect detected within the bank recall window (~24 h) but correction requires additional action. | Defect detected after the recall window; legal recovery is uncertain. | No mechanism exists to reverse or recover the payment. |
| **Evidence quality** | Documented review with annotations, checklist completion, or attestation that demonstrates genuine scrutiny of invoice, bank details, and supporting receipt. | Automated log entries showing the control executed (AV-2 pass record). | Manager approval timestamp exists but no documentation of what was reviewed. | No audit trail or the trail was fabricated. |
| **Collusion resistance** | Requires coordination among  3 independent actors (e.g., preparer + releaser + manager) to defeat. | Requires coordination between 2 actors; organisational design (rotation, random pairing) makes sustained collusion difficult. | Requires coordination between 2 actors but the same pair is repeated without rotation. | Two actors with persistent pairing, shared workstation, and shared credentials. |

### Classification Rules

A package is **fully equivalent** if and only if it scores "Fully Equivalent" on **Timing, Independence, and Overrideability** AND at least "Partially Equivalent" on all remaining dimensions.

A package is **partially equivalent** if it scores "Fully Equivalent" or "Partially Equivalent" on Timing, Independence, and Overrideability AND at least "Merely Mitigating" on all remaining dimensions.

A package is **merely mitigating** if it provides some risk reduction on at least three dimensions but fails on Independence or Overrideability.

A package is **ineffective** if it fails on Independence AND Overrideability, or if it fails on Coverage and Timing simultaneously.

### Why "Same Expected Loss" Is Not the Only Standard

1. **Deterrent effect**: A visible, independent human reviewer changes the preparer's calculus differently from an automated check. The *probability of attempted* fraud differs even if the *expected loss given an attempt* were identical.
2. **Evidence trail and investigation quality**: Human review generates annotations, email threads, and checklist records that enable post-incident investigation. Automated pass/fail logs do not.
3. **Regulatory and legal compliance**: External auditors and regulators may require demonstrable human oversight irrespective of whether an automated check yields equivalent expected loss.
4. **Organisational trust and culture**: The social accountability of having a named second approver affects organisational norms around payment integrity.
5. **Common-cause failure resilience**: Compensating controls may share failure modes (e.g., a system outage takes down both AV-2 and the manager-notification workflow). A truly independent human releaser using a different system provides architectural diversity.
6. **Cascading systemic risk**: If all payments rely on AV-2 + late manager ratification, a single AV-2 outage creates organisation-wide exposure. The nominal two-person rule distributes the control surface.

## 4. Preventive–Detective–Corrective Comparison

### Control Classification Table

| Control | Timing Relative to Release | Timing Relative to Settlement | Primary Category | Secondary Category | Rationale |
|---------|---------------------------|-------------------------------|------------------|--------------------|-----------|
| **AV-2** (full pass) | Before release | Before settlement | **Preventive** | — | Can block release entirely. Operates before the preparer can execute. |
| **AV-2** (warning) | Before release | Before settlement | **Preventive** (if unoverridden) | — (if overridden, becomes non-functional) | Warning can be overridden by authorised person; effectiveness depends on who overrides. |
| **AV-2** (block) | Before release | Before settlement | **Preventive** | — | Hard block; cannot be overridden by the preparer. Strongest form. |
| **MG-4** (before release) | Before release | Before settlement | **Preventive** | — | Manager review gates the release. No release occurs without approval. |
| **MG-4** (after release, before settlement) | After release | Before settlement | **Detective** (reviews a completed action) | **Preventive** (can still block the irreversible step) | **This is the key hybrid case** (see below). |
| **MG-4** (after settlement) | After release | After settlement | **Detective** | — | Purely post-hoc; cannot reverse the transfer. |
| **RA-7** (within 24 h) | After release | After settlement (usually) | **Detective** | **Partially corrective** | Can identify defects while bank recall is still possible. |
| **RA-7** (after 24 h) | After release | After settlement | **Detective** | — | Defects identified but recovery is uncertain. |
| **ED-1** (all conditions met) | Enables same-user with layered gates | — | **Preventive** (the conditions themselves are gates) | — | A permission structure, not a control per se. The conditions (AV-2, MG-4, RA-7) carry the control weight. |

### Semantics of Post-Release, Pre-Settlement Manager Review

**Chosen classification: Hybrid — detective review with preventive interception capacity.**

**Reasoning**: The question of whether a manager review after release but before settlement is "preventive" or "detective" depends on what we define as the **harm**:

- If the harm is "an unauthorised internal release event"  the release has already occurred  the review is **detective**.
- If the harm is "irrecoverable funds leaving the company"  bank settlement has NOT yet occurred  the review can still prevent the irreversible loss  **preventive** for the terminal outcome.

FEP-1's stated purpose is to "prevent one person from both initiating and authorising an erroneous or fraudulent transfer." The word "transfer" implies funds movement, which occurs at **settlement**, not release. Under this interpretation, a manager who reviews after release but can still halt settlement is performing a **preventive** function with respect to the transfer, even though the review itself examines a completed internal action.

**Practical position**: I classify the act as **hybrid** because:
1. The **review** is detective (examining what happened).
2. The **managerial authority to halt settlement** is preventive (stopping what has not yet happened).
3. The **net effect** is interceptive — it occupies the space between pure prevention and pure detection, and its value depends entirely on whether settlement has already occurred.

This distinction matters materially for AP-201, AP-207, and AP-208. In AP-201 and AP-207, the manager acted before settlement  hybrid with genuine preventive capacity. In AP-208, the manager acted after settlement  purely detective with no corrective capacity (audit was also late).

## 5. Counterfactual and Residual-Risk Analysis

### AP-202 (Critical — Actual Fraud Loss)

**Most plausible loss mechanism**: u23 established a new vendor with a bank account controlled by an employee's relative, prepared and released the payment (same user), overrode AV-2 warnings using m09's override credential, and the non-independent manager (m09, direct supervisor) ratified after settlement and after the recall window.

**Which control breaks the causal chain**:
- AV-2 partially broke it by issuing a warning for the bank change and operator-limit exceedance. The warning was correct and timely.
- The chain was **restored** when u23 used m09's override credential — this collapses the AV-2 control into a single-actor decision.
- A truly independent MG-4 manager (not m09, not anyone who shares credentials with u23) approving **before release** would have broken the chain at the strongest point: the release would not have occurred without independent approval, and the manager would have seen the new vendor, recent bank change, and AV-2 warning.

**What remains exposed**:
- The override-credential-sharing mechanism is a systemic vulnerability: any preparer who obtains a manager's override credential can bypass AV-2 entirely.
- The non-independent manager relationship (m09 sets u23's performance rating) means even formal MG-4 approval is structurally compromised.
- For similar future payments: the same failure mode could recur if credential controls and manager-independence policies are not remediated.

**Under a truly independent second releaser**: The releaser would have needed to independently verify the vendor and bank details, would have seen the AV-2 warning (and could not have overridden it with u23's cooperation alone), and would likely have questioned a new vendor with a 2-hour-old bank change on a EUR 480,000 payment. The payment would most likely have been blocked or escalated. Residual risk would shift from "high probability of undetected fraud" to "low probability, detectable through normal review."

### AP-204 (High — Fabricated Receipt, Formal Compliance)

**Most plausible loss mechanism**: u12 prepared a EUR 220,000 consulting payment with a fabricated service receipt. u13 released it. Their repeated pairing (37 payments in 30 days) and shared workstation suggest either (a) active collusion or (b) u13 rubber-stamping u12's work.

**Which control breaks the causal chain**:
- AV-2 did not break the chain: technical checks (duplicate, sanctions, bank, PO) passed because the fraud was in the supporting documentation, not in the payment metadata.
- A genuinely independent releaser who reviewed the service receipt could have detected fabrication (depending on its sophistication). The four-eyes principle was designed for exactly this scenario.
- An additional MG-4 manager review was not present for this case (no same-user flag, no emergency).

**What remains exposed**:
- The fundamental problem is that formal four-eyes compliance (different user IDs) does not guarantee substantive independence when the same pair works together daily at the same workstation.
- If the organisational design intentionally creates a dedicated two-person cell (no design documents found), then the cell's quality controls (rotation, cross-checking, workload monitoring) become the relevant compensating controls — and these are absent.

**Under a truly independent second releaser** (randomly assigned, different workstation, no repeated pairing):
- The releaser would have had no established relationship with u12 and no incentive to rubber-stamp.
- The fabricated receipt would have faced genuine scrutiny from a person with no stake in the payment's approval.
- The probability of the fraud succeeding would be materially lower, though not zero (a sufficiently convincing fabrication might still pass).

### AP-208 (Critical — EUR 900,000, Control Cascade Failure)

**Most plausible loss mechanism**: u72 prepared and released a EUR 900,000 payment to a vendor (active only 8 months) whose bank account had changed three days earlier. AV-2 was unavailable, so the bank-change flag was never raised. The manager ratified after settlement, and the audit occurred four days later. If the bank change was fraudulent, the funds are likely irrecoverable.

**Which control breaks the causal chain**:
- AV-2 **would have** broken the chain: the bank-change-within-seven-days check would have flagged or blocked the release. But AV-2 was down.
- A pre-settlement manager review **could have** broken the chain: the manager could have independently verified the bank account. But the manager ratified after settlement.
- The RA-7 audit **detected** the issue but four days after release and after settlement — corrective capacity was zero.

**What remains exposed**:
- The entire payment chain was exposed: no automated validation, no pre-settlement human review, late audit. The only "control" was the emergency token, which merely permitted the same-user handling.
- The AV-2 outage created a single point of failure that cascaded through the entire compensating package because no manual fallback was enforced.

**Under a truly independent second releaser**:
- The releaser would have been a different human who would have seen the payment details, including the vendor name and bank account. Even without AV-2, a releaser reviewing a EUR 900,000 payment to a relatively new vendor might have questioned the bank details.
- However, without AV-2's bank-change flag, the releaser would need to manually compare the bank account against historical records — a less reliable check. The independent releaser provides **partial** mitigation, not full protection, in the absence of AV-2.
- The key improvement: the independent releaser introduces a mandatory human checkpoint that cannot be bypassed by the preparer alone, even during a system outage. This is the architectural resilience that the same-user approach lacks.

### AP-201 (Low — Convenience Same-User, Well-Compensated)

**Most plausible loss mechanism**: u17 makes an error (wrong vendor, wrong amount) on a low-value office supply payment and releases it without challenge because no second person is involved.

**Which control breaks the causal chain**:
- AV-2 passed (no duplicate, no sanctions issue, amount within limit, PO match) — so the most common error types were already screened.
- m04 reviewed at T+24 minutes, before settlement (at T+2 hours) — this is a genuine interception point. m04 is independent of u17.
- RA-7 audit at T+25 hours is marginal for the recall window but still provides a detection point.

**What remains exposed**:
- The 24-minute window between release and m04's review, and the ~2-hour window before settlement, during which the payment could have been redirected or the error compounded.
- The risk that m04's review was cursory (no documented evidence of review quality).

**Under a truly independent second releaser**: The error would be caught at the release step itself — before the payment enters the settlement queue. The window of exposure shrinks to near zero for internal errors. For this low-risk case, the incremental benefit is small in practice but meaningful in principle: the control architecture would be robust by default rather than robust only when compensating controls happen to function.

### AP-206 (Medium — Ambiguous Token, Strong Manager Review)

**Most plausible loss mechanism**: During a production outage, u52 prepares and releases a payment with an ambiguous emergency token (created 2 minutes after prepare). If the token was not active before prepare, ED-1 condition 1 fails, and the same-user handling is unjustified.

**Which control breaks the causal chain**:
- m11 approved at T+4 minutes, **before release** at T+8 minutes. This is a fully preventive MG-4 action by an independent manager. Regardless of the token ambiguity, the pre-release approval means a genuine second human reviewed and authorised the payment before it was released.
- AV-2 passed (automated checks clean).
- Audit at T+19 hours is within the recall window.

**What remains exposed**:
- The ambiguity of the token creates a governance/documentation gap: even if the payment was properly controlled, the emergency pathway's eligibility cannot be verified. This matters for auditability and policy enforcement.
- If the token was not active before prepare, a precedent is set that ED-1 conditions can be retroactively satisfied.

**Under a truly independent second releaser**: The token issue becomes irrelevant — a different human would have released the payment regardless of emergency status. The m11 pre-release approval already provides equivalent protective value to a second releaser; the main difference is the formal authorisation pathway (ED-1 vs. nominal FEP-1).

## 6. Evidence and Monitoring Recommendations

### Monitoring Rules

| Metric | Definition | Alert Threshold | Investigation Threshold | Rationale |
|--------|-----------|-----------------|------------------------|-----------|
| **Same-user rate** | % of completed payments where `Prepare_Payment.org:resource == Release_Payment.org:resource` | > 5% per month | > 10% per month or any month-over-month doubling | Detects whether same-user handling is becoming routine rather than exceptional. |
| **Override rate** | % of AV-2 warnings overridden, by operator | Any single operator > 3 overrides/month | Any override on a payment > EUR 100,000 | AP-202 shows that overrides can defeat the entire AV-2 layer. Track who overrides and on what. |
| **Override credential mismatch** | Override performed by a different resource than the AV-2 warning was directed to | Any occurrence | Any occurrence | Detects credential sharing (as in AP-202). This is a strong indicator of control failure. |
| **Late manager approval** | Manager approval/ratification timestamp > Bank_Settlement timestamp | Any occurrence | Any occurrence | Once settlement has occurred, the manager review loses all corrective capacity. Every instance should be investigated. |
| **Audit-before-recall-window** | Audit timestamp > (Release_Payment timestamp + 24 h) for same-user payments | > 20% of same-user payments | Any same-user payment > EUR 50,000 with audit after recall window | RA-7's corrective value collapses after 24 h. Late audits for high-value payments are high-risk. |
| **Repeated resource pairs** | Same (preparer, releaser) pair appearing in > N completed payments per 30-day rolling window | > 10 payments/month | > 20 payments/month or any pair with  1 defect | Detects potential dedicated cells or collusive patterns (cf. AP-204/AP-209). |
| **Shared workstation** | Preparer and releaser share the same IP address, MAC address, or terminal ID | Any occurrence | Any occurrence combined with repeated pairing | Shared workstations undermine the independence assumption. Not proof of misconduct but a necessary investigation trigger. |
| **Bank-change proximity** | Payment to vendor with bank-account change within 7 days, **especially when AV-2 was unavailable** | Any payment > EUR 50,000 | Any payment where AV-2 was down AND bank change within 7 days (cf. AP-208) | This is the highest-risk combination: the automated check that would have flagged the change was absent. |
| **AV-2 service outage** | Any period where AV-2 is unavailable during payment-processing hours | Immediate alert | Any release during outage | AP-208 demonstrates that an AV-2 outage can cascade into total control failure. During an outage, manual-checklist completion should be mandatory and verified. |
| **Emergency token activation after prepare** | Emergency token timestamp > Prepare_Payment timestamp for the same case | Any occurrence | Any occurrence (cf. AP-206) | ED-1 condition 1 requires the token to be active **before** prepare. A post-hoc token undermines the emergency pathway's integrity. |

### Alert vs. Proof of Misconduct

Every metric above is an **evidence flag**, not a compliance verdict or misconduct finding. Specifically:

- A **repeated resource pair** may reflect an intentional payment cell (good organisational design) or a collusive arrangement (bad). Investigation requires reviewing organisational design documents, rotation policies, and the defect rate for the pair.
- A **shared workstation** may reflect hot-desking, shift work, or a small office — not necessarily credential sharing. Investigation requires comparing workstation logs with HR records.
- A **late manager approval** may reflect a system delay, a timezone error, or a genuine control failure. Investigation requires comparing the approval evidence (what the manager reviewed) against the payment details.
- An **override** may be legitimate (manager reviewed and accepted the risk) or illegitimate (preparer used borrowed credentials). Investigation requires access logs and the manager's documented justification.

The monitoring system should produce a **risk-weighted composite score** per case, combining multiple flags, rather than treating any single flag as dispositive. The scoring should escalate to a human compliance reviewer for contextual assessment.

### PM4Py Version Notes

1. **`filter_four_eyes_principle` return type**: In PM4Py  2.7, the function returns a pandas DataFrame directly. In some older versions it may return an `EventLog` object; the code handles this with the `to_dataframe()` fallback.
2. **`@` prefix on case IDs**: Some PM4Py versions (roughly 2.5–2.6) prepend `@` to case identifiers during `format_dataframe`. The code strips this with `.str.lstrip("@")`.
3. **Activity-key parameter**: The function signature may accept the two activity names as positional arguments or as keyword arguments (`activity1`, `activity2`). The positional form used here is the most portable.
4. **SYSTEM resource**: SYSTEM-performed activities (e.g., `Automated_Validate`) are not filtered out before the four-eyes check, but this is harmless because SYSTEM does not perform `Prepare_Payment` or `Release_Payment`. No SYSTEM-vs-human false positives will occur.
5. **`Audit_Review` activity**: The code identifies audit timing by searching for this exact activity name. If the production system uses a different name, the filter string must be adjusted.
