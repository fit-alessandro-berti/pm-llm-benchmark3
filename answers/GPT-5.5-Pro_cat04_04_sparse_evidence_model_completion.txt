# 2. Shared Assumptions

All three models treat the given traces as complete case traces from **Register Order** to **Archive Case**. The models encode visible activity completions, not starts, durations, or resource assignments. A directly-follows relation is therefore interpreted as an observed completion-order relation only.

All models assume:

* **Register Order** is first and **Archive Case** is last.
* **Approve Configuration** must precede **Release Production**, and **Release Production** must precede **Archive Case**.
* **Credit Check** and **Engineering Review** are both required before **Approve Configuration**.
* **Expedite Review**, when present, occurs at most once, after both principal checks, and before **Approve Configuration**.
* **Supplier Confirmation**, when present, must occur before **Approve Configuration**.
* Activity counts support plausibility but are not encoded as probabilities.
* No rework loop is modeled, because no repeated activity appears in the evidence and D6 explicitly limits X to at most once.
* The no-S path represents two different latent explanations: a legitimately stocked-component case and a case where Supplier Confirmation was required but not logged. This is a deliberate abstraction caused by the absent external/stocked attribute and the integration problem.
* Optionality is represented with XOR branches and silent transitions. This does not mean the business rule is intrinsically optional for every order; it means the log lacks the attributes needed to condition the branch properly.

# 3. Conservative Candidate

**Inductive-bias statement.**
The conservative model is a high-precision, low-generalization model. It accepts exactly the seven observed visible variants and refuses to infer concurrency, hidden case types, or unseen expedite/supplier combinations from sparse evidence. It is useful as an audit baseline but is likely too brittle for operational monitoring.

**Compact formal expression.**

```text
model_conservative =
XOR(
  ->(R,C,E,S,A,L,Z),
  ->(R,E,C,S,A,L,Z),
  ->(R,C,E,A,L,Z),
  ->(R,E,C,A,L,Z),
  ->(R,C,S,E,A,L,Z),
  ->(R,C,E,S,X,A,L,Z),
  ->(R,E,C,X,S,A,L,Z)
)
```

This is an XOR enumeration. Duplicate visible labels such as **Credit Check** and **Engineering Review** occur in multiple branches. PM4Py can represent this, but the resulting Petri net contains duplicate labeled transitions, which can complicate diagnostics and scale poorly as the number of variants grows.

**Self-contained PM4Py code.**

```python
import pm4py

model_conservative = pm4py.parse_process_tree("""
X(
  ->('Register Order','Credit Check','Engineering Review','Supplier Confirmation','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Supplier Confirmation','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Engineering Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Supplier Confirmation','Engineering Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Engineering Review','Supplier Confirmation','Expedite Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Expedite Review','Supplier Confirmation','Approve Configuration','Release Production','Archive Case')
)
""")
```

**Behavior deliberately excluded.**

* Any unobserved C/E/S/X interleaving, even if domain-plausible.
* `Register Order, Credit Check, Engineering Review, Expedite Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case`.
* `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case`.
* Supplier Confirmation before both principal checks.
* Expedite Review before both principal checks.
* Approval before either Credit Check or Engineering Review.
* Release Production before Approve Configuration.
* Repeated Credit Check, Engineering Review, Supplier Confirmation, or Expedite Review.

**Known underfitting risks.**

* It underfits if C and E are truly parallel and future completion orders produce unseen interleavings.
* It underfits S6 because S6 permits X before or after S, while only two X placements are observed.
* It underfits missing Supplier Confirmation events: a missing S event in a new completion order would be rejected.
* It treats a 30-case sample as if it defines the whole language.
* It does not generalize over stocked versus external components because the conditioning attribute is absent.
* It is structurally simple to explain but not scalable: each new variant requires another XOR branch.

# 4. Balanced Candidate

**Inductive-bias statement.**
The balanced model generalizes where the evidence and domain rules jointly support it, but it avoids making the process completely free. It treats C and E as unordered completions after R, makes S optional because stocked cases and missing data are both plausible, requires S to occur after at least one principal check when present, and constrains X after both C and E while leaving X unordered with S.

**Compact formal expression.**

```text
model_balanced =
PO(
  R < M < A < L < Z
)

M =
XOR(
  PO(C || E, C < X?, E < X?),
  PO(C || E, C < S, C < X?, E < X?),
  PO(C || E, E < S, C < X?, E < X?)
)

X? = XOR(tau, X)
```

Interpretation:

* `C || E` means no order is imposed between C and E.
* If S is present, it is modeled as starting after either C or E has enough information.
* X is optional but, when present, must follow both C and E.
* S and X have no ordering relation with each other, so X-before-S and S-before-X are both possible.
* The whole middle block precedes A, so C, E, optional S, and optional X all complete before approval.

**Self-contained PM4Py POWL code.**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

def _t(label):
    try:
        return Transition(label=label)
    except TypeError:
        return Transition(label)

def _tau():
    return SilentTransition()

def _xor(*children):
    try:
        return OperatorPOWL(operator=Operator.XOR, children=list(children))
    except TypeError:
        return OperatorPOWL(Operator.XOR, list(children))

def _po(children, edges):
    try:
        po = StrictPartialOrder(nodes=list(children))
    except TypeError:
        po = StrictPartialOrder(list(children))
    for source, target in edges:
        po.order.add_edge(source, target)
    return po

def _balanced_middle_no_supplier():
    c = _t("Credit Check")
    e = _t("Engineering Review")
    x_opt = _xor(_tau(), _t("Expedite Review"))
    return _po(
        [c, e, x_opt],
        [(c, x_opt), (e, x_opt)]
    )

def _balanced_middle_supplier_after_credit():
    c = _t("Credit Check")
    e = _t("Engineering Review")
    s = _t("Supplier Confirmation")
    x_opt = _xor(_tau(), _t("Expedite Review"))
    return _po(
        [c, e, s, x_opt],
        [(c, s), (c, x_opt), (e, x_opt)]
    )

def _balanced_middle_supplier_after_engineering():
    c = _t("Credit Check")
    e = _t("Engineering Review")
    s = _t("Supplier Confirmation")
    x_opt = _xor(_tau(), _t("Expedite Review"))
    return _po(
        [c, e, s, x_opt],
        [(e, s), (c, x_opt), (e, x_opt)]
    )

middle_balanced = _xor(
    _balanced_middle_no_supplier(),
    _balanced_middle_supplier_after_credit(),
    _balanced_middle_supplier_after_engineering(),
)

r = _t("Register Order")
a = _t("Approve Configuration")
l = _t("Release Production")
z = _t("Archive Case")

model_balanced = _po(
    [r, middle_balanced, a, l, z],
    [(r, middle_balanced), (middle_balanced, a), (a, l), (l, z)]
)
```

**How sequence, concurrency, and partial order are decided.**

For **Register Order → middle block → Approve Configuration → Release Production → Archive Case**, I use sequence-like partial-order edges because D1, D2, D3, D4, the start/end sets, and the invariant A→L→Z tail strongly support those constraints.

For **Credit Check** and **Engineering Review**, I do not impose C before E or E before C. The DFG shows both completion orders, S2 says they normally run in parallel, and D7/S7 warn that completion order does not identify start precedence. Therefore, I encode a partial order with no C/E edge. This admits both orders but does not claim proven overlap.

For **Supplier Confirmation**, I reject the too-strict rule “after both C and E” because V5 shows C,S,E and D5 says S may begin after either principal check. I also reject fully unconstrained S in the balanced model because D5 still says S begins after either C or E, not before both. Since “after either” is a disjunctive dependency, I encode it with XOR branches: S-after-C or S-after-E, plus a no-S branch.

For **Expedite Review**, I use D6/S6 as the main rule: optional, at most once, after both C and E, before approval. Because S6 explicitly allows X before or after S, I add no S/X order.

**Behavior deliberately excluded.**

* Supplier Confirmation as the first post-registration activity.
* Approval before both C and E.
* Approval before S when S is present.
* Expedite Review before either C or E is complete.
* Expedite Review after approval.
* More than one Expedite Review.
* Release Production before Approve Configuration.
* Archive Case before Release Production.
* Any cancellation/rejection path not present in the activity set.

**Known underfitting risks.**

* If S can legitimately begin immediately after R based on order metadata, the balanced model underfits.
* If Supplier Confirmation can repeat for multiple external components, the at-most-once abstraction underfits.
* If there are hidden cancellation, rejection, or rework paths, they are excluded.
* If the Finance manager’s strict C-before-E rule is correct and E-before-C traces are logging artifacts, the model overgeneralizes C/E ordering rather than underfitting; however, it would still be structurally mis-specified.
* The no-S branch hides two distinct realities: stocked component and missing event. That is not a clean business model.

# 5. Permissive Candidate

**Inductive-bias statement.**
The permissive model admits broad but still bounded behavior. It preserves high-confidence compliance constraints—R first, A before L before Z, C and E before A, X after both C and E—but treats Supplier Confirmation as optional and not causally ordered with the principal checks. This is useful for exploration, anomaly triage, and sensitivity analysis, but it has a higher precision risk.

**Compact formal expression.**

```text
model_permissive =
PO(
  R < M < A < L < Z
)

M =
PO(
  C,
  E,
  S?,
  X?,
  C < X?,
  E < X?
)

S? = XOR(tau, S)
X? = XOR(tau, X)
```

Interpretation:

* C and E are required and unordered.
* S is optional and can occur anywhere inside the middle block before approval.
* X is optional but must occur after both C and E.
* S and X are unordered.
* Approval still waits for the entire middle block.

This relaxes D5. The boundary is intentional: because D5 is low-to-medium confidence and lifecycle timestamps are missing, the permissive model allows early S as a sensitivity case. It still forbids behavior that violates stronger rules: missing C/E before approval, X before both checks, release before approval, archive before release, repeated X, and post-approval S.

**Self-contained PM4Py POWL code.**


**Behavior deliberately excluded.**

* Approval before C or E.
* Release Production before Approve Configuration.
* Archive Case before Release Production.
* Expedite Review before both C and E.
* Expedite Review after approval.
* More than one Expedite Review.
* Supplier Confirmation after approval.
* Repeated Supplier Confirmation.
* Any activity outside the supplied activity set.

**Known underfitting risks.**

* It still underfits if multiple supplier confirmations are needed for multiple external components.
* It underfits if the real process has rework from approval back to checks.
* It underfits if expedite review can be reopened or repeated.
* It underfits if there are rejection, cancellation, or manual-hold outcomes not listed.
* It does not encode probabilities or case attributes, so it cannot distinguish rare-but-valid behavior from likely noise.

# 8. Validation Code

The code below is intentionally self-contained. It reconstructs the 30-case log, defines all three models, converts them to Petri nets, runs available PM4Py diagnostics and quality metrics, performs sampled playout, and checks a small manual trace suite. Sampled playout is not a proof of language inclusion or exclusion.

```python
import pprint
import pm4py

from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


# ---------------------------------------------------------------------
# Activity labels
# ---------------------------------------------------------------------

R = "Register Order"
C = "Credit Check"
E = "Engineering Review"
S = "Supplier Confirmation"
X = "Expedite Review"
A = "Approve Configuration"
L = "Release Production"
Z = "Archive Case"


# ---------------------------------------------------------------------
# 1. Reconstruct the 30-case event log
# ---------------------------------------------------------------------

variants = [
    (12, [R, C, E, S, A, L, Z]),
    (7,  [R, E, C, S, A, L, Z]),
    (4,  [R, C, E, A, L, Z]),
    (3,  [R, E, C, A, L, Z]),
    (2,  [R, C, S, E, A, L, Z]),
    (1,  [R, C, E, S, X, A, L, Z]),
    (1,  [R, E, C, X, S, A, L, Z]),
]

trace_strings = []
for count, trace in variants:
    trace_strings.extend([",".join(trace)] * count)

log = pm4py.parse_event_log_string(trace_strings)

print("Number of traces:", len(log))
print("Discovered DFG:")
pprint.pp(pm4py.discover_dfg(log))


# ---------------------------------------------------------------------
# 2. Candidate model definitions
# ---------------------------------------------------------------------

# Conservative ProcessTree: exact XOR over observed variants.
model_conservative = pm4py.parse_process_tree("""
X(
  ->('Register Order','Credit Check','Engineering Review','Supplier Confirmation','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Supplier Confirmation','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Engineering Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Supplier Confirmation','Engineering Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Credit Check','Engineering Review','Supplier Confirmation','Expedite Review','Approve Configuration','Release Production','Archive Case'),
  ->('Register Order','Engineering Review','Credit Check','Expedite Review','Supplier Confirmation','Approve Configuration','Release Production','Archive Case')
)
""")


# POWL construction helpers. The try/except blocks tolerate small PM4Py
# constructor-signature differences across versions.
def t(label):
    try:
        return Transition(label=label)
    except TypeError:
        return Transition(label)

def tau():
    return SilentTransition()

def xor(*children):
    try:
        return OperatorPOWL(operator=Operator.XOR, children=list(children))
    except TypeError:
        return OperatorPOWL(Operator.XOR, list(children))

def po(children, edges):
    try:
        order = StrictPartialOrder(nodes=list(children))
    except TypeError:
        order = StrictPartialOrder(list(children))
    for source, target in edges:
        order.order.add_edge(source, target)
    return order


def balanced_middle_no_supplier():
    c = t(C)
    e = t(E)
    x_opt = xor(tau(), t(X))
    return po([c, e, x_opt], [(c, x_opt), (e, x_opt)])


def balanced_middle_supplier_after_credit():
    c = t(C)
    e = t(E)
    s = t(S)
    x_opt = xor(tau(), t(X))
    return po([c, e, s, x_opt], [(c, s), (c, x_opt), (e, x_opt)])


def balanced_middle_supplier_after_engineering():
    c = t(C)
    e = t(E)
    s = t(S)
    x_opt = xor(tau(), t(X))
    return po([c, e, s, x_opt], [(e, s), (c, x_opt), (e, x_opt)])


middle_balanced = xor(
    balanced_middle_no_supplier(),
    balanced_middle_supplier_after_credit(),
    balanced_middle_supplier_after_engineering(),
)

r = t(R)
a = t(A)
l = t(L)
z = t(Z)

model_balanced = po(
    [r, middle_balanced, a, l, z],
    [(r, middle_balanced), (middle_balanced, a), (a, l), (l, z)]
)


# Permissive POWL.
c = t(C)
e = t(E)
s_opt = xor(tau(), t(S))
x_opt = xor(tau(), t(X))

middle_permissive = po(
    [c, e, s_opt, x_opt],
    [(c, x_opt), (e, x_opt)]
)

r = t(R)
a = t(A)
l = t(L)
z = t(Z)

model_permissive = po(
    [r, middle_permissive, a, l, z],
    [(r, middle_permissive), (middle_permissive, a), (a, l), (l, z)]
)


models = {
    "conservative": model_conservative,
    "balanced": model_balanced,
    "permissive": model_permissive,
}


# ---------------------------------------------------------------------
# 3. Convert to accepting Petri nets and run soundness/quality metrics
# ---------------------------------------------------------------------

def safe_call(description, func):
    try:
        return func()
    except Exception as exc:
        return {"error": f"{type(exc).__name__}: {exc}"}


petri_models = {}

for name, model in models.items():
    print("\n" + "=" * 80)
    print("MODEL:", name)

    net, im, fm = pm4py.convert_to_petri_net(model)
    petri_models[name] = (net, im, fm)

    soundness = safe_call(
        "soundness",
        lambda: pm4py.check_soundness(net, im, fm, print_diagnostics=True)
    )

    fitness = safe_call(
        "fitness_alignments",
        lambda: pm4py.fitness_alignments(log, net, im, fm)
    )

    precision = safe_call(
        "precision_alignments",
        lambda: pm4py.precision_alignments(log, net, im, fm)
    )

    generalization = safe_call(
        "generalization_tbr",
        lambda: pm4py.generalization_tbr(log, net, im, fm)
    )

    simplicity = safe_call(
        "simplicity_petri_net",
        lambda: pm4py.simplicity_petri_net(net, im, fm)
    )

    print("Soundness:")
    pprint.pp(soundness)
    print("Fitness:")
    pprint.pp(fitness)
    print("Precision:")
    pprint.pp(precision)
    print("Generalization:")
    pprint.pp(generalization)
    print("Simplicity:")
    pprint.pp(simplicity)


# ---------------------------------------------------------------------
# 4. Sampled playout
# ---------------------------------------------------------------------

def traces_from_event_log(event_log, max_traces=20):
    traces = []
    for trace in event_log:
        traces.append(tuple(event["concept:name"] for event in trace))
        if len(traces) >= max_traces:
            break
    return traces


def sampled_playout(model, net, im, fm, no_traces=50):
    attempts = [
        lambda: pm4py.play_out(
            model,
            parameters={"no_traces": no_traces, "max_trace_length": 10}
        ),
        lambda: pm4py.play_out(model, no_traces=no_traces),
        lambda: pm4py.play_out(
            net,
            im,
            fm,
            parameters={"no_traces": no_traces, "max_trace_length": 10}
        ),
    ]
    last_error = None
    for attempt in attempts:
        try:
            return attempt()
        except Exception as exc:
            last_error = exc
    raise last_error


for name, model in models.items():
    print("\n" + "=" * 80)
    print("SAMPLED PLAYOUT:", name)
    net, im, fm = petri_models[name]
    playout_log = safe_call(
        "play_out",
        lambda model=model, net=net, im=im, fm=fm: sampled_playout(model, net, im, fm)
    )
    if isinstance(playout_log, dict) and "error" in playout_log:
        pprint.pp(playout_log)
    else:
        unique_sampled = sorted(set(traces_from_event_log(playout_log, max_traces=100)))
        for tr in unique_sampled[:20]:
            print(tr)

print(
    "\nNote: sampled playout is useful for inspection but does not prove "
    "full language inclusion or exclusion, especially for models with "
    "concurrency, choices, loops, or silent transitions."
)


# ---------------------------------------------------------------------
# 5. Manual positive/negative trace suite
# ---------------------------------------------------------------------

def parse_single_trace(trace):
    return pm4py.parse_event_log_string([",".join(trace)])


def alignment_score_dict(single_log, net, im, fm):
    return pm4py.fitness_alignments(single_log, net, im, fm)


def is_perfectly_fitting(trace, net, im, fm, tolerance=1e-9):
    single_log = parse_single_trace(trace)
    result = alignment_score_dict(single_log, net, im, fm)

    # PM4Py versions expose different key names.
    candidate_keys = [
        "log_fitness",
        "average_trace_fitness",
        "averageFitness",
        "fitness",
    ]

    for key in candidate_keys:
        if isinstance(result, dict) and key in result:
            try:
                return float(result[key]) >= 1.0 - tolerance
            except Exception:
                pass

    # Some versions expose percentage of fitting traces.
    percent_keys = [
        "percentage_of_fitting_traces",
        "percFitTraces",
    ]
    for key in percent_keys:
        if isinstance(result, dict) and key in result:
            try:
                value = float(result[key])
                return value >= 100.0 - tolerance or value >= 1.0 - tolerance
            except Exception:
                pass

    raise RuntimeError(f"Could not interpret alignment fitness result: {result}")


suite = [
    (
        "observed_v1",

        {"conservative": True, "balanced": True, "permissive": True},

    ),
    (
        "bad_missing_credit",
        [R, E, S, A, L, Z],

    ),
    (
        "bad_expedite_too_early",
        [R, X, C, E, A, L, Z],

print("\n" + "=" * 80)
print("MANUAL TRACE SUITE")

for case_id, trace, expected_by_model in suite:
    print("\nTrace:", case_id, "=>", trace)
    for model_name, expected in expected_by_model.items():
        net, im, fm = petri_models[model_name]
        actual = safe_call(
```

Limitations of this validation setup:

* Alignment-based fitness can check whether a trace fits a Petri net, but it does not by itself explain why a trace is semantically valid or invalid.
* Sampled playout does not prove complete language inclusion.
* Precision, generalization, and simplicity scores are model/log-dependent diagnostics, not truth indicators.
* Because the candidate models contain duplicate visible labels in some branches, diagnostics may need manual interpretation.

# 9. Recommendation and Data-Collection Plan

I recommend **model_balanced** for immediate use. It fits the observed evidence, respects the strongest domain rules, handles the most important uncertainty around C/E ordering, and does not overreact to the Finance manager’s unsupported strict sequence claim. It is also more suitable than the conservative model for live monitoring because it will not flag every unseen but domain-plausible interleaving as a deviation.

I recommend **model_permissive** for sensitivity analysis. It is useful for asking: “How many deviations disappear if Supplier Confirmation can happen at any pre-approval point?” If that substantially changes conformance results, the next investigation should focus on the supplier process and missing lifecycle data.

The conservative model should be retained as an audit baseline, not as the primary operational model.

Concrete data-collection plan:

1. **Collect lifecycle timestamps, not only completion timestamps.**
   For Credit Check, Engineering Review, Supplier Confirmation, and Expedite Review, collect at least `start_time`, `complete_time`, `resource`, and `source_system_event_id`. This distinguishes true concurrency from sequential variants and ingestion-order artifacts.

2. **Export the missing case attributes.**
   Add `component_type`, `external_component_required`, `stocked_component_flag`, `supplier_confirmation_required`, `supplier_id`, `number_of_external_components`, and `configuration_complexity`.

3. **Collect rule-trigger attributes for Expedite Review.**
   Add `expedite_trigger`, `trigger_time`, `trigger_source`, `approved_by`, and `reason_code`. This tests whether X really requires both C and E or whether some early expedite review exists but was absent from the sample.

4. **Record data-quality indicators.**
   Add `source_system`, `integration_status`, `event_expected_but_missing`, `backfill_flag`, and `ingestion_timestamp`. This separates true no-S cases from missing Supplier Confirmation events.

5. **Target the most informative future traces.**
   The following observations would sharply distinguish the hypotheses:

   * C starts, then E starts before C completes: strong evidence for actual overlap.
   * E starts only after C completes across many cases: supports S1’s strict sequence.
   * S starts after C completes but before E completes: supports balanced S-after-either.
   * S starts after E completes but before C completes: supports the symmetric S-after-either branch.
   * S starts before both C and E: supports permissive early-S behavior and weakens D5.
   * External-component case with no S and no integration error: challenges S3.
   * Stocked-component case with no S: supports S4.
   * External-component case where S is expected but missing from the log: quantifies S5.
   * X before both C and E: would challenge D6/S6 and require compliance escalation.
   * X after both C/E but before S and X after S: confirms S6’s no-order claim between X and S.

6. **Use a future holdout log.**
   Fit none of the models to the holdout. Score all three on alignment fitness, precision, deviations by rule category, and analyst-labeled false positives. The balanced model should remain the default only if it reduces false positives without allowing compliance-relevant violations.

# 10. Uncertainty Statement

My confidence in the **R first and Z last** decision is very high, around **0.95–0.98**, because D1, the start/end sets, and all 30 traces agree.

My confidence in **A before L before Z** is very high, around **0.95–0.99**, because D2 and all 30 traces support the invariant tail.

My confidence that **C and E are both required before A** is high but not absolute, around **0.85–0.90**. D3 supports it, and all observed traces contain both C and E before A. The caveat is that the sample is small and no exceptional cancellation or emergency approval paths are described.

My confidence in **not enforcing C before E** is moderate-to-high, around **0.75–0.85**. The log has 19 C-first cases and 11 E-first cases, and S2/S7 make the Finance manager’s strict claim uncertain. However, without lifecycle timestamps, I cannot distinguish true concurrency from two sequential variants or logging artifacts.

My confidence in modeling **Supplier Confirmation as optional/no-S** is moderate, around **0.65–0.75**. Seven of 30 traces lack S, which is more than the expected 5–10% missing-event rate alone would explain, so stocked components are plausible. But the absent external/stocked attribute prevents clean separation of true optionality from missing data.

My confidence in the balanced rule **S after either C or E, but not before both** is only moderate, around **0.55–0.65**. It is supported by D5 and V5, but D5 is low-to-medium confidence and only completion timestamps are available. This is the main reason to keep the permissive model for sensitivity analysis.

My confidence in **X after both C and E, before A, at most once** is medium-to-high, around **0.80–0.90**. It is based more on D6/S6 than on frequency, because X appears only twice.

The most material alternative interpretation is that the Finance manager is right and the 11 E-before-C traces are caused by logging or ingestion artifacts. If lifecycle data confirmed that Engineering Review never starts before Credit Check finishes, I would replace the balanced C/E partial order with a strict C→E sequence and treat E-first completions as data-quality deviations. A second material alternative is that Supplier Confirmation can begin immediately after registration for some supplier-known configurations; if confirmed, the permissive model or a conditioned variant of it would become more appropriate than the current balanced model.
