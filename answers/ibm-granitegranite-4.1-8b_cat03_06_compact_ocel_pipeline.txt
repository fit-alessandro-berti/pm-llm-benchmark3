## 1. Modeling assumptions
- **Object types and capitalization**: Orders (O100, O200), Items (I1, I2, I3), Packages (P1, P2), Deliveries (D1, D2), Invoice (V1), Payment (M1, M2). All identifiers are capitalized per OCEL convention.
- **E2O qualifier vocabulary**:  
  - `contains` – used for Order  Item relationships.  
  - `packs` – used for Package  Item relationships.  
  - `carries` – used for Delivery  Package relationships.  
  - `bills` – used for Invoice  Order relationships.  
  - `settles` – used for Payment  Invoice relationships.  
- **O2O direction conventions**: Relations are treated as directed from the source object to the target object, e.g., `Order  Item` for `contains`.
- **Logistics and financial events relation**: Events are directly linked to the objects they affect (e.g., `Create Order` directly relates to `Order O100`). This avoids an extra propagation step and keeps the model sourcesystem faithful. Propagated relations could be added later for analytical reuse but would risk conflating source facts with derived insights.
- **Preventing analytical relation propagation confusion**: All sourcesystem events carry explicit `activity` and `timestamp`. Analytical relations (e.g., derived “Payment settles Invoice”) are added as distinct E2O rows with qualifiers, ensuring they are distinguishable from the original operational E2O rows.
- **PM4Py version assumption**: The code uses `pm4py.v2` APIs (`ocel_flattening`, `discover_...`). If a different PM4Py version is installed, replace `pm4py` calls with the equivalent functions from that version (e.g., `pm4py_v1` namespace). The core OCEL construction logic remains unchanged.

*Especially consequential events*: `Reserve Stock` (E6) and `Record Payment` (E12, E13) are pivotal for convergence because they trigger shared resource allocation and settlement logic.

## 4. Expected flattened behavior
- **Order** – Trace: `Create Order  Add Item (I1)  Add Item (I2)  Issue Invoice  Record Payment (M1)  Record Payment (M2)  Close Order`. Shared events (e.g., `Reserve Stock`) appear as copies for each Order, preserving context. Lifecycle aspects (creation  closure) are retained.
- **Package** – Trace: `Pack Package (P1)  Dispatch Package (D1)  Confirm Delivery (D1)`; `Pack Package (P2)  Dispatch Package (D2)  Confirm Delivery (D2)`. No lifecycle closure events; only packaging and delivery steps are present.
- **Delivery** – Trace: `Dispatch Package (D1)  Confirm Delivery (D1)`; `Dispatch Package (D2)  Confirm Delivery (D2)`. Similar to Package flattening, delivery steps are captured.
- **Invoice** – Trace: `Issue Invoice  Record Payment (M1)  Record Payment (M2)`. No creation of the Order itself appears; only billing and payment settlement events are directly attached.
- **Payment** – Flattened trace would consist of isolated `Record Payment (M1)` and `Record Payment (M2)` events, lacking temporal context with the Order lifecycle, making interpretation weak (e.g., cannot see which item(s) funded each payment).

## 5. Expected objectcentric structures
- **OCDFG**: Shows directed edges between all objectcentric events preserving business flow (`O100`  `Add Item I1`  `Pack Package P1`  `Dispatch Delivery D1`  `Confirm Delivery D1`  `Issue Invoice V1`  `Record Payment M1`  `Record Payment M2`  `Close Order O100`). The same pattern mirrors for `O200`. Highlights convergent paths (e.g., both Orders feed into the same Invoice V1).
- **OTG**: Nodes are object types (Order, Item, Package, Delivery, Invoice, Payment). Edges reflect the most frequent relationships (e.g., `Order  contains  Item`, `Package  packs  Item`, `Delivery  carries  Package`, `Invoice  bills  Order`, `Payment  settles  Invoice`). Shows global connectivity and potential bottlenecks (Invoice as a central hub).
- **ET–OT**: Associates each event with the object types it involves, enabling analysis of event distribution across types (e.g., how many events per Order vs. per Invoice).
- **Objectcentric Petri net**: Places places for each object state (e.g., `OrderCreated`, `ItemAdded`, `ReadyToShip`, `Paid`, `Closed`). Transitions correspond to activities (Create Order, Add Item, Pack, Dispatch, Confirm, Pay, Close). Provides a formal model for verifying invariants (e.g., an Order cannot be closed until all payments are settled).
- **Objectinteractions summary**: Quantifies cooccurrences, such as “Orders and Invoices interact 2 times” and “Packages and Deliveries interact 2 times”, useful for spotting unexpected coupling.

## 6. Modeling alternatives
1. **Sourceminimal relations** – Only directly observed E2O links (e.g., `Create Order`  `O100`, `Add Item`  `I1`), omitting inferred relations like `settles`. This keeps the model faithful to source logs but may hide analytical insights such as settlement dependencies.
2. **Full operational involvement** – Explicitly map every operational substep (e.g., `Reserve Stock` as a shared E2O between both Orders) and duplicate events for each Order that participates, providing maximum detail for process mining but inflating event counts.
3. **O2Opropagated analytical relations** – After constructing the base O2O, add derived relations computed from the log (e.g., “Payment settles Invoice” inferred from cooccurrence patterns). These are stored as separate qualifier rows, allowing separate analytical queries without altering the original source data.

Each alternative changes the granularity of discoverable patterns: sourceminimal yields leaner DFGs; full involvement yields richer, more complex nets; propagated analytic relations enable higherlevel abstraction at the cost of added abstraction layers.

## 7. Failure modes
1. **Relation inflation** – Adding unnecessary E2O rows (e.g., linking every item to every order) distorts event frequencies and inflates DFG size.
2. **Missing direct E2O links** – Forgetting to create `contains` relations leads to disconnected object traces, breaking flattening.
3. **Treat O2O propagation as observation** – Using derived relations as if they were source events may cause mistaken causal inferences (e.g., assuming a payment caused invoice issuance).
4. **Duplicate shared events after flattening** – Flattening may duplicate `Reserve Stock` for both Orders, leading to ambiguous activity frequencies.
5. **Ambiguous payment allocation** – If payment events lack a clear link to specific invoice items, downstream analysis (e.g., reimbursment) becomes inaccurate.
6. **Overly short Payment traces** – Isolating `Record Payment` from the surrounding process can strip essential context (e.g., which invoice is being settled).
7. **Constructor/API version mismatch** – Using an OCEL constructor for PM4Py v1 while the code targets v2 results in attribute errors (e.g., missing `events` key).
8. **False total order for sametime events** – Although timestamps are unique here, any future model with concurrent events could misorder them, breaking temporal semantics in DFG discovery.
