# 1. Executive Verdict

The net **is** a workflow net in the structural sense: there is a single source place (`source`, in-degree 0), a single sink place (`sink`, out-degree 0), and every node lies on some path from `source` to `sink` (verified below). It should **not** be expected to be sound. The principal defect is an **asymmetric join**: `t_join_normal` is a proper two-input AND-join (`p_analysis_done` + `p_review_done`), but `t_join_waived` is a single-input pass-through that only consumes `p_waived` and never synchronizes with the analysis branch. Business consequence: when the waiver route is chosen, the case can be authorized **before** (or entirely without regard to) analysis completion, and the analysis-branch token becomes permanently stranded once authorization occurs — a case can reach `sink` while a token still lingers in `p_analysis`/`p_analysis_done`, violating both the stated authorization precondition and proper completion.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `t_split` | AND-split into analysis + review branches | Correctly implemented: produces one token in `p_analysis` and one in `p_review` from one token in `p_ready` | None — this part is correct |
| `t_standard_review` (`p_review`…`p_review_done`) | One XOR alternative for review | Correctly consumes `p_review`, produces `p_review_done`; feeds the proper AND-join `t_join_normal` | None in isolation |
| `t_waive_review` (`p_review`…`p_waived`) | Other XOR alternative for review | Correctly consumes `p_review`, produces `p_waived`; but `p_waived` feeds a join that is **not** an AND-join | Waiver path silently skips synchronization |
| `t_join_normal` | AND-join of analysis + standard review | Correctly requires both `p_analysis_done` and `p_review_done` | None — correct pattern |
| `t_join_waived` | *Should* be AND-join of analysis + waiver | Only consumes `p_waived`; has no arc from `p_analysis_done` | Authorization becomes possible without analysis; `p_analysis`/`p_analysis_done` token orphaned |
| `im`/`fm` (`source`…`sink`) | Single case token in, single completion token out | Structurally fine (unique source/sink) | Behaviorally, `fm` may be “reached” with extra tokens elsewhere still present — i.e., a marking with `sink=1` is reachable that is *not* `fm` (dead, but improper) |
| Source-to-sink coverage | Every place/transition should lie on a directed path sourcesink | All 9 places and 8 transitions do lie on such a path (e.g., `p_analysis_done``t_join_normal``p_decision``t_authorize``sink`, and `p_analysis_done` is *also* structurally reachable to sink only via the normal join, not via the waived join) | Satisfies the workflow-net *syntactic* test, masking the deeper *semantic* defect — a good illustration that WF-net-ness  soundness |

# 3. Marking-Based Counterexample

**Counterexample A — authorization occurs before analysis (business-rule violation).**

Firing sequence: `t_register, t_split, t_waive_review, t_join_waived, t_authorize, t_analyze`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---|---|---|---|---|
| 0 | — (im) | `source:1` | `t_register` | start |
| 1 | `t_register` | `p_ready:1` | `t_split` | |
| 2 | `t_split` | `p_analysis:1, p_review:1` | `t_analyze`, `t_standard_review`, `t_waive_review` | both parallel-branch tokens created |
| 3 | `t_waive_review` | `p_analysis:1, p_waived:1` | `t_analyze`, `t_join_waived` | waiver route chosen; analysis token untouched |
| 4 | `t_join_waived` | `p_analysis:1, p_decision:1` | `t_analyze`, `t_authorize` | **join fires with no dependency on analysis** |
| 5 | `t_authorize` | `p_analysis:1, sink:1` | `t_analyze` | `t_authorize` fired **before** `t_analyze` — violates "authorization only after analysis and review are both complete" |
| 6 | `t_analyze` | `p_analysis_done:1, sink:1` | *(none)* | dead marking; `sink` holds a token but marking  `fm` |

A token exists in `sink` from step 5 onward, but the **exact** final marking `fm = {sink:1}` is never reached: from step 5 the marking is `{p_analysis:1, sink:1}` and from step 6 it is `{p_analysis_done:1, sink:1}`. No transition can ever consume `p_analysis_done` at that point (`t_join_normal` also needs `p_review_done`, which will never be produced because `p_review` was already consumed by `t_waive_review`), so the leftover token is permanent — the net is stuck in an improper "completed-looking" state.

**Counterexample B — leftover token even with "correct" temporal order (soundness violation, independent of the ordering issue).**

Firing sequence: `t_register, t_split, t_analyze, t_waive_review, t_join_waived, t_authorize`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---|---|---|---|---|
| 0 | — (im) | `source:1` | `t_register` | |
| 1 | `t_register` | `p_ready:1` | `t_split` | |
| 2 | `t_split` | `p_analysis:1, p_review:1` | `t_analyze`, `t_standard_review`, `t_waive_review` | |
| 3 | `t_analyze` | `p_analysis_done:1, p_review:1` | `t_standard_review`, `t_waive_review` | analysis done *first*, respecting intended order |
| 4 | `t_waive_review` | `p_analysis_done:1, p_waived:1` | `t_join_waived` | |
| 5 | `t_join_waived` | `p_analysis_done:1, p_decision:1` | `t_authorize` | join fires while ignoring `p_analysis_done` |
| 6 | `t_authorize` | `p_analysis_done:1, sink:1` | *(none — dead marking)* | `sink` marked, but extra token remains: `fm` not reached and never will be |

This shows the defect is not merely a race condition that could be "fixed" by convention/logging discipline — even in the temporally well-behaved order, the missing arc causes a permanently dangling token and a dead marking distinct from `fm`. This is a genuine soundness violation (violates "option to complete": from the marking after step 3 or 4, no firing sequence reaches `fm` exactly once the waiver branch is taken), not just an AND/XOR labeling mismatch.

# 4. Minimal-Repair Alternatives

**Edit-cost model** (stated explicitly): cost(place add/remove) = 3, cost(transition add/remove) = 3, cost(arc add/remove) = 1. Rationale: adding/removing places or transitions changes the net's semantic vocabulary and typically forces re-verification of every path through them; arcs are cheaper, purely relational edits.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---|---|---|---|
| **R1 — Symmetric AND-join (add missing sync arc)** | Add one arc: `p_analysis_done  t_join_waived`. No removals. | 1 arc  **cost 1** | Fully preserves stated intent: analysis mandatory on every path; authorization only after analysis **and** whichever review outcome are both complete. | `t_join_waived` now requires both `p_analysis_done` and `p_waived`. Waiver path becomes a true parallel-AND join, symmetric to `t_join_normal`. Order of `t_analyze` vs `t_waive_review` no longer matters — join waits for both regardless of interleaving. | Negligible: two transitions (`t_join_normal`, `t_join_waived`) now compete for the single `p_analysis_done` token, but since exactly one of `p_review_done`/`p_waived` can ever hold a token (XOR upstream), only one join is ever actually enabled — no new conflict/deadlock introduced. |
| **R2 — Unify into a single synchronization point (merge review outcome)** | Remove: arc `p_waivedt_join_waived`, arc `t_join_waivedp_decision`, transition `t_join_waived`, arc `standard_reviewp_review_done`, arc `waive_reviewp_waived`, arc `p_review_donet_join_normal` (5 arcs, and note `p_review_done`, `p_waived` become unused and can be dropped: 2 places). Add: place `p_review_outcome`; arcs `t_standard_reviewp_review_outcome`, `t_waive_reviewp_review_outcome`, `p_review_outcomet_join_normal`. | 5 arcs + 2 places + 1 transition removed (cost 5+6+3=14), 1 place + 3 arcs added (cost 3+3=6)  **cost  20** | Preserves "analysis mandatory + both branches synchronized before authorize," but *merges* the two review outcomes structurally into one place before the join. | A single AND-join transition (`t_join_normal`) now handles both routes; no duplicate join logic can drift out of sync again. Distinguishability of waiver vs. standard review is preserved at the *event/label* level (the two transitions remain distinct in the log) but not at the *place* level. | Architecturally cleaner, but higher edit cost and a larger regression surface (touches both branches, not just the broken one); a case-attribute or downstream query that inspects "did token pass through `p_waived` vs `p_review_done`" structurally still works (those places aren't touched pre-merge), but any logic keyed on `p_decision`'s *provenance* place is now uniform. |
| **R3 — Explicit policy change: analysis optional under waiver** | Add place `p_analysis_or_skip`; add transition `t_skip_analysis` with arcs `p_analysist_skip_analysis`, `t_skip_analysisp_analysis_or_skip`; reroute `t_analyze`'s output from `p_analysis_done` to `p_analysis_or_skip`; remove `p_analysis_done`; rewire both joins to consume `p_analysis_or_skip` instead. | 1 place + 1 transition added (cost 6), 2 arcs added for skip path + 2 arcs rewired on joins + 1 arc rewired on `t_analyze` output (5 arcs, cost 5), 1 place removed (cost 3)  **cost  14**, *and* a policy change | **Does NOT preserve stated intent** ("analysis is always mandatory") — this is a deliberate business-rule change: under waiver, analysis becomes optional/skippable. | Two ways to satisfy the join precondition: real analysis or explicit skip. Waiver case can complete without ever running `t_analyze`. | Must be explicitly approved by the business owner; risk of silent policy drift if this is deployed under the impression it's a "bug fix" rather than a scope change; audit/compliance risk if analysis was regulatorily mandatory. |

**Minimality justification.** Under the stated cost model, **R1 is minimal** (cost 1) and is the unique cheapest repair that preserves business intent exactly — it fixes the identified defect with the smallest possible structural change (one arc), mirroring the existing, already-correct `t_join_normal` pattern, so no new design idiom is introduced. R2 is a legitimate, behaviorally similar (intent-preserving) alternative but costs an order of magnitude more because it eliminates duplicate structure; it is not "tied" with R1 — it is strictly more expensive but offers a maintainability argument that a pure cost metric doesn't capture (this trade-off is discussed in §7, not hidden). R3 is excluded as a default because it silently changes what "mandatory" means; it is offered only as an explicit, clearly labeled policy alternative, not a bug fix.

# 6. Diagnostic and Reachability Code

```python
import pm4py

def is_enabled(net, marking, transition_name):
    """Check enabledness explicitly rather than silently moving tokens."""
    t = next((tr for tr in net.transitions if tr.name == transition_name), None)
    if t is None:
        raise ValueError(f"Transition {transition_name} not found in net")
    for arc in t.in_arcs:
        if marking.get(arc.source, 0) < arc.weight:
            return False, t
    return True, t

def fire(net, marking, transition_name):
    """Fire a transition by name if (and only if) it is enabled."""
    enabled, t = is_enabled(net, marking, transition_name)
    if not enabled:
        raise RuntimeError(f"Transition {transition_name} is NOT enabled in marking {marking}")
    new_marking = Marking(marking)
    for arc in t.in_arcs:
        new_marking[arc.source] -= arc.weight
        if new_marking[arc.source] == 0:
            del new_marking[arc.source]
    for arc in t.out_arcs:
        new_marking[arc.target] = new_marking.get(arc.target, 0) + arc.weight
    print(f"Fired {transition_name:20s} -> {dict(new_marking)}")
    return new_marking

def run_diagnostics(net, im, fm, label):
    print(f"\n=== {label} ===")
    is_wfnet = pm4py.check_is_workflow_net(net)
    print("is workflow net:", is_wfnet)
    soundness = pm4py.check_soundness(net, im, fm, print_diagnostics=True)
    print("soundness result:", soundness)
    enabled = pm4py.get_enabled_transitions(net, im)
    print("enabled at im:", [t.name for t in enabled])
    rg = pm4py.convert_to_reachability_graph(net, im, fm)
    print("reachability graph built, #states:", len(rg.states), "#edges:", len(rg.transitions))
    return soundness, rg

# --- Diagnostics on the ORIGINAL (defective) net ---
run_diagnostics(net, im, fm, "ORIGINAL net")

print("\n--- Replaying Counterexample A on the ORIGINAL net ---")
m = Marking(im)
for step in ["t_register", "t_split", "t_waive_review", "t_join_waived", "t_authorize", "t_analyze"]:
    m = fire(net, m, step)
print("Final marking reached:", dict(m), " == fm?", m == fm)

# --- Diagnostics on the REPAIRED net ---
run_diagnostics(repaired_net, repaired_im, repaired_fm, "REPAIRED net (R1)")

print("\n--- Replaying the same intended sequence on the REPAIRED net ---")
m = Marking(repaired_im)
m = fire(repaired_net, m, "t_register")
m = fire(repaired_net, m, "t_split")
m = fire(repaired_net, m, "t_waive_review")
try:
    m = fire(repaired_net, m, "t_join_waived")  # should NOT be enabled yet
except RuntimeError as e:
    print("Expected block:", e)
m = fire(repaired_net, m, "t_analyze")
m = fire(repaired_net, m, "t_join_waived")      # now enabled
m = fire(repaired_net, m, "t_authorize")
print("Final marking reached:", dict(m), " == fm?", m == repaired_fm)
```

**Expected qualitative difference:** On the original net, `check_soundness` should report a violation related to proper completion / option to complete (a reachable dead marking distinct from `fm`, and/or a marking where `sink` is populated while other places retain tokens). `check_is_workflow_net` should return `True` for *both* nets (the defect is behavioral, not structural). On the repaired net, `check_soundness` should report no such violation, and the replay of Counterexample A's transition order should now explicitly show `t_join_waived` blocked until `t_analyze` has fired, terminating in `dict(m) == repaired_fm`. No specific state-space cardinalities are asserted here since none were computed by hand.

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of waiver vs. standard review:** preserved under both R1 and R2 at the event-label level (`t_standard_review` vs. `t_waive_review` remain distinct transitions with distinct labels), so process mining/conformance on the event log can still separate the two routes. Under R2, the *place* that funnels into the join is shared (`p_review_outcome`), so any downstream logic that inspected place identity rather than the firing transition would lose that distinction — this is a real, if narrow, risk.
- **Silent transitions and duplicate behavior:** `t_split`, `t_join_normal`, `t_join_waived` are unlabeled (silent/`None` label) in all variants. R1 does not add any new silent transition, so no new ambiguity is introduced in the visible-behavior projection. R3 (not selected) adds a new silent transition (`t_skip_analysis`) whose presence would be invisible in the event log, which is precisely the kind of change that can defeat "detect mandatory-step bypass" auditing described below — a strong argument against deploying R3 silently.
- **Soundness is necessary, not sufficient:** passing `check_soundness` only proves the net has no deadlocks/dangling tokens and can always complete; it does **not** verify domain semantics such as "authorization never precedes analysis in real time" beyond what the net structure encodes, nor does it check data/resource constraints, timing, or four-eyes-principle-style business rules that aren't expressible purely in control-flow. A net can be sound yet still authorize before some *externally required* condition if that condition isn't modeled as a place/token at all.
- **Regression trace suite (minimum):**
  - Positive: `register  split  analyze  standard_review  join_normal  authorize` (both orders of `analyze`/`standard_review`).
  - Positive: `register  split  waive_review  analyze  join_waived  authorize` and the reverse interleaving `analyze` before `waive_review`.
  - Negative (must be rejected/blocked): `register  split  waive_review  join_waived  authorize` **without** `analyze` ever firing — this should now be structurally impossible (never enabled) in the repaired net; test by attempting to fire `t_join_waived` right after `t_waive_review` and asserting `is_enabled` returns `False`.
  - Negative: any attempt to fire `t_authorize` when `p_decision` is unmarked.
- **Detecting an accidental bypass of mandatory analysis:** replay every waiver-route case in the event log and assert that `Perform Analysis` appears before `Authorize Case` in the case's trace (a simple LTL/temporal check: `eventually(Perform Analysis) before Authorize Case`), and additionally re-run the structural check "is `t_join_waived` (or its successor in a repaired model) dependent on a place only reachable through `t_analyze`?" after every net change — this second, structural check is exactly what would have caught the original bug before deployment.

# 8. Final Recommendation

**Deploy R1** (add the single missing arc `p_analysis_done  t_join_waived`). It has the lowest edit cost, requires no change to visible labels, requires no change to the stated business policy, and directly mirrors the already-correct `t_join_normal` pattern — minimizing both review effort and the chance of introducing a new defect. It resolves both counterexamples: it removes the possibility of `t_authorize` firing before `t_analyze`, and it eliminates the permanently dangling token, restoring proper completion.

**Fallback: R2** (unify the two joins behind a shared `p_review_outcome` place) if the organization anticipates adding further review alternatives (e.g., a third "escalated review" route) in the near future, since a single shared join scales better and prevents the same asymmetric-arc mistake from recurring per new branch. It costs more to implement now and touches more of the net, but amortizes better across future variants. R3 (making analysis optional under waiver) is explicitly **not recommended** as either primary or fallback, since it silently contradicts the stated "analysis is always mandatory" requirement; it should only be considered after an explicit, documented business-policy decision, not as a technical fix.
