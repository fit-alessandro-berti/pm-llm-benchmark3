## 1. Temporal Data Semantics

- State is reconstructed by sorting events per case by `time:timestamp`, then `event_index`.
- For each case, the current value of `amount`, `risk_level`, `jurisdiction`, `customer_type`, and `exemption_id` is the latest non-null value carried forward from preceding events.
- A blank cell means “no update at this event”; it does not set the attribute to null.
- Final case attributes are not copied backward. The state at `Release_Funds` is computed only from events at or before that release event.
- Equal-timestamp events are ordered by `event_index`. In TX-311, `Enhanced_Review` is `event_index 3` and the jurisdiction change to DE is `event_index 4`, so the jurisdiction changed after the review.
- Event time is the timestamp on the event. Effective time is normally the event timestamp unless evidence gives a different effective time. Record time is when an event was recorded in a system. Evidence time is when an approval/signature was actually created.
- A material data change is rule-specific: for R1 it includes jurisdiction changes and R4-material amount increases; for R2 it includes risk/customer-type changes to HIGH or PEP; for R3 it is the sanctions-list update; for R4 it is an amount increase over 20 percent after a relevant review.
- Missing values are not defaulted to low-risk values. If a decisive trigger cannot be established or excluded, the case is classified `INDETERMINATE` unless other evidence resolves it.
- Temporal relations use strict `before/after`: `X before Y` iff `time(X) < time(Y)`, or `time(X) = time(Y)` and `event_index(X) < event_index(Y)`.

## 4. Ambiguities and Alternative Readings

- **TX-302**: If the recorded exemption event at 11:00 were treated as the approval time, then EX-77 would not be valid at release at 09:40 and the case would be `NONCOMPLIANT`. The better reading uses the qualified signature timestamp of 09:05, which is before release, and treats the 11:00 record as a late database insertion.

- **TX-305**: The amount is unknown at release. If the later settlement amount of 150,000 were accepted as conclusive for the release amount, then R1 would likely be triggered and the case would require a valid post-amount-change `Enhanced_Review`; since the Enhanced_Review document has no amount, the case would likely be `NONCOMPLIANT`. If independent evidence showed the release amount was below 100,000, R1 would not trigger and the case could be `COMPLIANT`. Because neither is established, `INDETERMINATE` is correct.

- **TX-306**: The main interpretive risk is whether the 220k230k amount update after `Enhanced_Review` is a “material data change” for R1 even though it is below 20 percent. If every amount update were treated as material, TX-306 would fail R1. The better reading is that R4 defines material amount changes: only increases above 20 percent invalidate for amount-dependent obligations.

- **TX-310**: If an independent witness or other reliable evidence established Head_Compliance approval at 08:45, then EX-88 would be valid and the case would be `JUSTIFIED_EXCEPTION`. On the evidence given, the approval is not proven at release because the qualified signing certificate was created after release and the only oral-approval witness is the requester.

- **TX-311**: If same-timestamp events were treated as simultaneous or if final case state were copied backward, one could mischaracterize the Enhanced_Review as already occurring under the DE jurisdiction. The event-time reading is clear: `event_index 3` precedes `event_index 4`, so jurisdiction changed to DE after the Enhanced_Review. At release, jurisdiction is DE, so R1 is not triggered.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage**  
   A control-flow model using final case attributes can incorrectly copy a later value backward. Example: TX-301’s final amount is 125,000, but the earlier `Standard_Review` occurred when amount was 80,000.

2. **Post-hoc exemptions**  
   A control-flow check may see an exemption logged after release and treat it as valid. TX-310 shows why this fails: EX-88’s qualified signature was created after release, so the exemption was not proven at release.

3. **Material changes after review**  
   Control-flow conformance can show that a review occurred, but not whether a later amount increase invalidated it. TX-309 has an `Enhanced_Review`, but the subsequent amount increase over 20 percent invalidates it for R1.

4. **Conditional activation**  
   R1 depends on the runtime state: jurisdiction not DE and amount at least 100,000. A trace may contain no `Enhanced_Review` and still be compliant if the amount is below threshold, or may require one if the amount crosses the threshold. Control-flow alone cannot evaluate this.

5. **Missing data**  
   TX-305 has unknown amount at release. A control-flow-only checker may either skip the R1 threshold check or falsely assume low risk. It cannot distinguish `INDETERMINATE` from `TRIGGERED` or `NOT_TRIGGERED`.

6. **Same-timestamp ordering**  
   TX-311 has `Enhanced_Review` and `Update_Jurisdiction` with the same timestamp. Only `event_index` resolves that jurisdiction changed after review. Control-flow-only models that ignore event index lose this ordering.

7. **Review type and content distinctions**  
   Some rules require `Enhanced_Review` specifically, not `Standard_Review`; some require a `Compliance_Approve` that actually followed an Enhanced_Review. Control-flow-only conformance can confuse these activities.

## 7. Recommended Logging and Control Improvements

- **Immutable release payloads**  
  Capture a signed, immutable payload at `Release_Funds`: amount, jurisdiction, risk, customer type, exemption id, rule version, and the decision timestamp.

- **Separate timestamps**  
  Add `effective_time`, `record_time`, `approval_time`, and `signature_time` in addition to `event_time`. This prevents backdated fields from being mistaken for timely approvals.

- **Structured exemption scope**  
  Store exemption scope as structured data: allowed jurisdictions, customer types, amount ceiling, waiver rule, effective/expiry times, and evidence reference. Avoid free-text scope only.

- **Change provenance**  
  For every update event, log old value, new value, source system, user, and reason. Examples: amount changes, jurisdiction changes, risk reclassification, customer type changes, sanctions-list updates.

- **Rule version and decision trace**  
  Log the active rule version and which rules were evaluated at release, with their outcomes. This avoids ambiguity about whether a case was judged under current or historical rules.

- **Stable event ordering**  
  Ensure every event has a monotonic sequence number that is meaningful across all source systems, so same-timestamp ordering is not dependent on private CSV order.

- **Explicit missing-data markers**  
  Distinguish “attribute not updated” from “attribute is unavailable” and “attribute is unknown at release.” This supports determinate `INDETERMINATE` classification instead of silent defaults.
