## 1. Target definition
The primary prediction target is: **"Default within 90 days after Account Activated, restricted to cases that reach Account Activated."**  
- *Unit of analysis*: Individual credit application cases that have at least one `Account Activated` event in the event log.  
- *Prediction time*: Immediately after the first `Account Activated` event (i.e., at the moment activation is confirmed; no events after activation are used for prefix generation). The model predicts the instantaneous 90-day default risk *conditional on activation*.  
- *Horizon*: 90 calendar days post-Account Activated timestamp (not business days; calendar days match the 90-day definition in the business question).  
- *Population*: All cases that reach Account Activated in the observation window (1 Jan 2024 – 31 Dec 2025), regardless of whether their 90-day outcome has matured as of the data extraction date (15 Feb 2026). This includes both "known" labels (outcome observed by extraction) and "censored" cases (90-day horizon ends after extraction). Rejected, withdrawn, transferred, and still-open cases are *excluded* from this target cohort because default is defined *only post-activation*; these cases never activate under the current process and therefore have no observable default under activation. (We do not label them as "non-default" – their default status under activation is undefined without counterfactual assumptions.)  
- *Estimand*: $\mathbb{E}[\text{Default}_{90d} \mid \text{Prefix}, \text{case attributes}, \text{activation time}]$, where $\text{Default}_{90d} \in \{0,1\}$ is 1 if a default event (e.g., "Default Recorded") occurs within 90 days after Account Activated, and 0 otherwise. The estimand explicitly conditions on the observed prefix (events up to and including Account Activated) and accounts for right censoring: for cases where activation date $t_a$ satisfies $t_a + 90$ days $>$ extraction date (15 Feb 2026), the outcome is censored at extraction (i.e., no default observed by extraction, but default may occur later). The estimand does *not* include competing events (e.g., rejections before activation) because the unit of analysis is only activated cases; competing events naturally exclude non-activated cases from the cohort.

*Credible alternative target*: **"Competing default risk for all applications"**, where the target is "Default within 90 days post-activation *given activation occurs*", with competing events defined as Rejection, Withdrawal, Transfer, or Open status *before* Account Activated. This answers: "What is the risk of default among applications that *do* activate, relative to applications that exit before activation?" However, this formulation requires modeling the probability of activation as part of the prediction (e.g., predicting $\Pr(\text{Default}_{90d} \mid \text{application})$ would need $\Pr(\text{Activate})$), which introduces additional assumptions about decision probabilities. It is useful for holistic monitoring but less precise for the lender’s request ("predicting 90-day default from the first few events"), which naturally starts from early events and aims to identify activating applications that may default. The primary target (activated cohort with right censoring) is operationally simpler: we directly observe activation events, avoid mixing competing exit events with the default definition, and uses only data available up to activation. The alternative is defensible but requires explicit modeling of activation probability; it would not be appropriate if the goal is to predict default *for already-activated cases* (which matches "from the first few events" when activation has occurred).

**Why the primary formulation is defensible**:  
- It matches the operational reality: `default_90d` is only defined post-activation in the warehouse; rejected/withdrawn/etc. cases never activate under the current process, so claiming a default probability for them would be a counterfactual without policy assumptions (e.g., "what if they were accepted").  
- It respects the data availability: only activated cases have observable outcome labels (either matured or censored). Including non-activated cases in the target would require inventing labels (e.g., calling rejection "non-default"), which the quality criteria explicitly forbid ("do not label rejected, withdrawn, or open cases as non-default merely for convenience").  
- It handles censoring transparently: right censoring (90-day horizon ends after extraction) is acknowledged and modeled via survival/censoring-aware methods; no label is assumed for censored cases.  
- Prediction time aligns with process logic: a lender observes activation first (after Credit Review Acceptance), then can monitor for early default signs. Predicting at activation uses only prefix events ( activation time), avoiding leakage from post-activation events.  
- It avoids policy/migration leakage: cohort is defined by event observation (`Account Activated` occurrence), not by label availability, so policy change (1 July 2025) or system migration (15 Oct 2025) naturally affect prefix characteristics but are part of the observed process.

> **Note**: "Non-default" for rejected cases is *not* used as a label. Instead, rejected cases are excluded from the target cohort (since they do not activate), and the model is only trained/evaluated on activated cases. Evaluation metrics are computed solely within the activated cohort.

## 3. Censoring and missing-label strategy
We distinguish four mechanisms clearly:

1. **Ordinary right censoring**: For activated cases where activation date $t_a$ satisfies $t_a + 90$ days $>$ extraction date (15 Feb 2026), i.e., $t_a > 15\text{ Nov }2025$. No default is observed by extraction, but default may occur later within the 90-day window. This is standard right censoring; the censoring time is extraction date.

2. **Delayed labels**: Activated cases where the external outcome feed arrives after the 90-day horizon end (7–35 days delay). As of extraction, `label_available_at` > extraction date, so label is unknown. This is also right censoring (censoring at extraction), not a separate mechanism; delayed feed arrival does not imply permanent missingness unless feed never arrives (see below). We treat all unknown labels as right-censored at extraction for the primary analysis.

3. **Selection through activation**: Observation of `default_90d` is conditional on the case activating (reaching `Account Activated`). This is natural and not biasing for the target cohort (activated cases); it simply means non-activated cases are excluded from the target (correctly, since default is undefined for them without counterfactuals). No "selection bias" arises in the estimand because we restrict to activated cases.

4. **Transfer as competing event / permanent missing**:  
   - *Competing event*: If a case is transferred *before* activation (e.g., from Credit Review), it is non-activated and excluded from target cohort — no competing risk for default in the activated cohort.  
   - *Permanent missing*: Partner-originated activated accounts may have no external feed ever arrive (elevated probability). At extraction date, we cannot observe whether the feed will arrive or not; thus, we cannot classify a case as "permanently missing" yet. We treat all activated cases without `label_available_at`  extraction date as *right-censored* (censoring at extraction). "Permanent missing" would only be known in the future (e.g., no feed after some deadline), which is unobservable now. Therefore, in the primary analysis, all activated cases with unknown label as of extraction are right-censored; sensitivity analysis will explore the "permanent missing" assumption separately.

**Primary analysis strategy**:  
Use a right-censored survival analysis approach: model $\Pr(\text{Default}_{90d} = 1 \mid t_a, \text{prefix})$ with censoring at extraction date. For evaluation, compute the cumulative incidence function (CDF) at 90 days via the Kaplan–Meier estimator (adjusted for prefix features if using stratified or regression survival models). Predicted probabilities at prediction time (activation) are obtained from the fitted model (e.g., Cox proportional hazards or a lightweight logistic regression on summary prefix features, with censoring handled in training via appropriate loss or estimator). *Do not impute labels for censored cases during training; use only known labels for unlabeled estimation or include censoring indicator.*

**Sensitivity analysis**:  
1. *Excluding censored cases*: Train/evaluate on only `label_known` activated cases (21,600). *Limitation*: Omits right-censored cohort (~3,600), likely biasing estimates (e.g., censored cases may have higher default risk if defaults occur early), so results over/under-estimate risk. Used only to quantify bias magnitude (e.g., compare KM curves).  
2. *Permanent-missing assumption for partner activations*: For partner-originated activated cases (identified via `source_system` = "partner"), treat unknown labels as `default = 0` (conservative) or assume a fixed missingness probability $\pi_m$ (e.g., $\pi_m = 0.3$ for partner) and perform outcome-modeling with inverse probability weighting. This tests the assumption that partner activations have no default (worst-case) or a measurable default rate among missing feeds. *Limitation*: $\pi_m$ is unobserved; sensitivity ranges (e.g., $\pi_m \in [0, 0.5]$) are reported.

**Testable vs. untestable assumptions**:  
-  *Testable*: Whether right censoring is non-informative (i.e., censored cases have different prefix characteristics than known cases). Test via log-rank test for KM curves or covariate balance (e.g., Kolmogorov–Smirnov test on prefix feature distributions pre/post policy change).  
-  *Partially testable*: Whether policy change (1 July 2025) affects censoring pattern (e.g., higher proportion of censored cases post-policy). Test by comparing censoring rates in pre/post policy activated cohorts using chi-square.  
-  *Fundamentally untestable*: The true default probability for a censored case (i.e., P(default | censored)). Without counterfactual data, we can only estimate it conditional on observed prefix; absolute default rate among censored cases cannot be determined from current data. Similarly, whether a partner feed will ever arrive ("permanent missing") cannot be observed at extraction; only future data can confirm it. Sensitivity ranges (e.g., "default rate among partner censored  5%" if conservative) must be stated explicitly.

## 4. Prefix extraction
**Goal**: Generate prefix features *without* any information from events after Account Activated. Prediction time is at the first `Account Activated` event; thus, the prefix includes all events with timestamp $\le$ activation timestamp.

**Rules**:
- For each case, locate the earliest event where `concept:name` = `"Account Activated"`  `activation_time`.
- Prefix events = all events of the case with `time:timestamp` $\le$ `activation_time` (strictly $\le$, since activation is the boundary).
- Prefix length type: support both fixed-event-count (e.g., max 10 events) and elapsed-time (e.g., events within first 3 days after start), but **always cap at activation**. Fixed prefix: take up to `max_prefix_len` events (sorted by time), but if the case activates before `max_prefix_len` events occur, use all prefix events up to activation. Elapsed-time: include events $\le$ `start_time` + `max_days` and $\le$ `activation_time`.
- Handle repeated document loops: count all document request/response pairs in prefix (no aggregation like "number of loops" without timing); use event sequence for flow features (e.g., "number of Credit Review events after KYC").
- Handle activity renaming (15 Oct 2025 migration): use the `concept:name` as recorded in the event row (post-migration names are consistent in the log); no backward mapping needed because the log reflects what was recorded at event time. Thus, prefixes extracted from the raw log are valid regardless of migration date.
- Fixed prefix extraction with pm4py: call `pm4py.get_prefixes_from_log` on the prefix log (events $\le$ activation), with `max_length` set to desired fixed length (e.g., 10). This automatically respects event order and handles loops.

**Example**:  
- Case starts 1 Jan 2024 10:00. Has events: Start (10:00), KYC (10:30), Doc Request (11:00), Doc Reply (11:30), Credit Review (12:00), Doc Request (13:00), Accept (14:00), Contract Signed (14:30), Account Activated (15:00).  
- Activation time = 15:00. Prefix events = all events up to Account Activated (including Accept and Contract Signed, since Contract Signed occurs before Activation per process). Fixed prefix of 5 events would be Start, KYC, Doc Request, Doc Reply, Credit Review (if sorted by time, but pm4py prefixes are time-ordered; actually, prefixes include all events up to activation, then `get_prefixes_from_log` gives prefixes of variable length up to max). *Important: Contract Signed is before Activation, so it is included in prefix (correct, as decision is made before activation).*

> **No leakage**: By filtering events $\le$ `activation_time`, we exclude any event like "Collections Contact" or "Default Recorded" that occurs after Activation, which would otherwise leak the outcome.

- `accept_decision_time`: `(Account Activated time - first Credit Review time).days` or time between Credit Review decision and Activation. *Captures speed from decision to activation; may reflect internal workflow.*

**Historical reference features** (require data up to activation, but no future info; may use policy/migration flags):  
- `policy_post_change`: 1 if `activation_time` $\ge$ 1 July 2025, else 0. *Derived from activation time; known at prediction time since policy change date is known.*  
- `migration_post_change`: 1 if `activation_time` $\ge$ 15 Oct 2025, else 0. *Similarly derived; handles renaming consistency (prefix already uses recorded names).*  
- `has_transfer_event`: 0/1 if case has any event with `concept:name` = "Transfer" before activation (from Credit Review), from prefix events. *Tracks if the applicant requested transfer; relevant for partner activations.*  
- `linked_transfer`: 0/1 if case has a transfer event *and* the linkage table (60%) indicates a link exists (obtained via external lookup using case ID; done at cohort level, not feature level). *Used only for cohort description or sensitivity; not in primary features to avoid leakage (lookup at case level, not event level).*

**Why these features are safe**:  
- No use of `collection_status` (updated after activation per process), `final_limit` (set after Accept, known at Activation), or post-Activation events. `final_limit` at Activation is valid (used in risk assessment), so kept. `decision_reason` at Credit Review decision is known at decision time $\le$ Activation, so safe. `documents_total` (nightly snapshot) is repaired: use cumulative daily document count up to `activation_time` (sum of daily uploads $\le$ activation day), not the nightly value after activation day if it includes same-day post-activation docs. `resource_experience` (extraction-time) is kept but flagged: in features, use only if `extraction_time` $\le$ `activation_time` (which is usually true, since extraction is 15 Feb 2026 and activations end Dec 2025); otherwise, note uncertainty in the feature docstring. `label_available_at` or `default_90d` are **never** used as features; they are only for cohort label status.

## 6. Leakage audit
| Feature or data element       | Leakage or bias risk                                  | Valid availability rule (as of prediction time = activation)                                                                                                                               | Keep/Repair/Drop | Rationale                                                                                                                                                                                               |
|-------------------------------|--------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| `final_limit`                | May correlate with limit size; but set before Activation (Contract Signed  Activation), so known at Activation                         | Available at or before Activation (final limit populated after Accept, which occurs before Activation per process); safe to use at Activation | Keep            | Required for risk assessment; no leakage since limit is decided pre-activation horizon.                                                   |
| `decision_reason`            | Could hint at rejection likelihood; but for Accepted cases, relevant; for prefix up to Activation, decision_reason is set at Credit Review decision $\le$ Activation | Available at Credit Review decision (before Activation for Accepted cases); null for Rejected cases (which are non-activated)                | Keep            | Reflects why Accepted/Rejected; relevant for process monitoring; no leakage since decision_reason is known at decision time $\le$ Activation. |
| `collection_status`         | May show "collections initiated" (post-activation default signal); if included pre-Activation, leakage                               | Updated after Activation per process; thus, for prefix $\le$ Activation, `collection_status` should be null/missing for activated cases       | Drop (in prefix features) | Cannot use post-Activation signal; when building prefix features, filter out `collection_status` events with time $>$ `activation_time`. |
| Future events (e.g., Contract Signed, Account Activated after prefix) | Direct leakage if prefix includes events after Activation                                                       | Prefix strictly $\le$ `activation_time`; pm4py prefix extraction filters events $\le$ activation                                    | Drop (prevent by filter) | Prediction must use only events up to Activation; enforce filter at prefix step (see Section 4).                                  |
| `documents_total` (nightly) | Nightly snapshot may include docs uploaded same day as Activation, risking post-Activation inclusion                                  | `documents_total` reflects day-end total; if Activation occurs on day D, night D snapshot may include D-day docs                              | Repair         | Use `documents_uploaded_up_to_activation`: sum daily document counts (e.g., from `case:channel` logs) up to `activation_time` floor, not nightly total. Avoid same-day post-Activation docs. |
| `risk_score` (updated)      | Could be updated after multiple loops; using latest score is fine, but using score after Accept might correlate with outcome                         | `risk_score` updated at several events; last score before or at Accept is known at Accept $\le$ Activation; safe to use (e.g., max or last pre-Accept) | Keep (use last pre-Accept risk_score or max in prefix) | Trend useful; use value at Credit Review events or last pre-Activation update to avoid overfitting to post-decision fluctuations. |
| `resource_experience`       | Stored at extraction time (15 Feb 2026), not event time; may overstate experience if employee left before activation                   | Known at extraction; may not reflect experience at event time (e.g., resource joined after start)                               | Keep (with flag) | Cannot change; document limitation: "experience as of extraction"; use cautiously; not used to infer event-time quality. No leakage since it's static per case. |
| `default_90d` (repeated)   | Direct label leakage if included in prefix features                                                                   | `default_90d` is null before default recording (post-Activation); may appear on post-Activation events                                 | Drop (as feature) | Never use `default_90d` as a feature. Label status (`label_known`) is derived separately from `label_available_at`; `default_90d` value is only used for cohort labeling, not feature engineering. |
| `label_available_at`       | Tells when label became known; using as feature could leak label timing                                  | Available per event; known at event time                                          | Drop (as feature) | Feature should reflect observable process (e.g., loop count), not meta-label timing; `label_available_at` is for cohort filtering only. |

> **Audit enforcement**: In implementation (Section 9), after filtering prefix events $\le$ `activation_time`, drop `collection_status` events from prefix feature table, compute `documents_uploaded_up_to_activation` from daily event counts, and use `risk_score` from Credit Review events or last pre-Activation update. All features are validated against the "Valid availability rule" before use.

## 7. Validation design
**Why random case split is misleading**: Randomly splitting cases ignores time (policy change 1 July 2025, migration 15 Oct 2025), leading to train cases seeing later policy rules while test cases use earlier, or vice versa. It also risks including post-Activation events in train prefixes for test cases (though prefix filter prevents this), but temporal consistency ensures predictive validity (e.g., model trained on pre-policy activations should apply to post-policy activations).

**Temporal validation scheme** (backtesting aligned with prediction time = Activation):
- **Train set**: Activated cases with `activation_time` $\le$ 30 June 2025 (i.e., before policy change 1 July 2025). This isolates training from policy effect.
- **Validation set**: Activated cases with `activation_time` in 1 July 2025 – 31 Oct 2025 (includes policy change and migration start 15 Oct 2025). Evaluate here to check policy impact.
- **Test set**: Activated cases with `activation_time` $\ge$ 1 Nov 2025 (post-migration period). Final evaluation; no overlap with train/val.
  - *Rationale*: Splits respect event time; all prefixes for validation/test use only events $\le$ their activation time, so no leakage from future policy or migration effects. Test set includes censored cases (activation > 15 Nov 2025), so evaluation uses censoring-aware metrics.
- **Within-validation CV for censored data**: For the validation set, perform stratified group k-fold on activation date (e.g., 5 folds by month), ensuring each fold has at least some known and censored cases. Use the Kaplan–Meier estimator per fold; report median CDF curves and 95% prediction intervals via bootstrapping (with censoring).
- **Metrics** (appropriate for right-censored target):
  - **Primary**: Integrated Calibration Error (ICE) restricted to known-label cases in validation/test (since censored labels are not 0/1); report calibration plot with 95% prediction-interval bands. For survival models, use time-dependent Brier score at 90 days (accounts for censoring).
  - **Secondary**: Cumulative incidence difference (vs. observed KM curve in validation); subgroup calibration (e.g., partner vs. internal activations).
  - **Avoid**: ROC-AUC (misleading for censored data); instead use calibration and predictive discrimination (e.g., check if higher predicted risk correlates with higher observed incidence among known cases).
- **Policy/migration checks**:
  - Compare baseline KM curve pre/post policy in validation; report absolute difference in 90-day incidence at day 0 and day 30.
  - Check prefix feature distributions (e.g., `credit_review_loops`) across train/val/test; if drastic shift, note in limitations.
  - Subgroup performance: report ICE and Brier score separately for `policy_post_change = 0` vs `1` and `source_system = "partner"` vs "internal".
- **Backtesting simulation** (simple, concrete):
  - For each activated case in validation/test, at its activation time, use prefix $\le$ activation to predict P(default within 90d) via the fitted model.
  - For known-label cases (label_known), compare predicted probability to observed 0/1 in bins (e.g., top 25%, median, bottom 25%).
  - For censored cases, simulate future default by assuming no default (conservative) or default with estimated marginal risk; compare predicted CDF to observed KM — report area between curves as a rough agreement metric (only for illustration, not primary).
  - Track consistency: e.g., if prediction > 0.3 for all cases in a loan product, verify with domain knowledge.

**No random split**: All splits are by activation date; random split would place later activations in training and earlier in test, causing the model to "see" future policy effects in training, violating temporal validity.

## 8. Limitations and decision-use boundary
**What the study can claim** (honest, precise):  
> "Based on observed events up to Account Activated (no post-activation events used), this study estimates, for activated credit applications, the probability of default within 90 calendar days after activation, conditional on the observed prefix and case attributes. Estimates are right-censored: for activations occurring after 15 November 2025, the outcome is unknown as of 15 February 2026, and results are presented with censoring-aware metrics (e.g., Kaplan–Meier CDF, time-dependent Brier score). Calibration and subgroup performance are reported only among cases with known labels (label_available_at  extraction date); censored cases are not used for label-based calibration but are included in survival curve evaluation. The model does not predict default for non-activated cases (rejected, withdrawn, transferred, open); such cases are excluded from the target cohort because default is defined post-activation and their default status under activation is undefined without counterfactual assumptions."

**What the study cannot claim** (explicitly avoid):  
> - "The model predicts default probability for rejected applications" (no activation  no observable default under activation; counterfactual would require policy assumptions).  
> - "Default rate among withdrawn/transferred/open cases is X%" (undefined without assuming they activate; not estimated).  
> - "Predicted probability equals the true default rate for censored cases" (censoring makes true rate for censored cases unobservable; only conditional estimate on prefix is given).  
> - "Policy change affects model performance uniformly" (subgroup checks performed; performance may differ, so boundary includes subgroup results).

**Decision-use boundary** (clear guidance for deployment):  
-  **Useful for**: Monitoring activated applications at Credit Review Acceptance; identifying high-risk activating cases for manual review or tighter limits. Use predicted probability (at activation) with uncertainty bands (e.g., 90% CI from bootstrap) as a screening aid. Always restrict use to cases that have reached Account Activated (i.e., after Acceptance + Contract Signed).  
-  **Not suitable for**: Predicting default for non-activated cases (reject/withdraw at Credit Review), estimating default rates for open or transferred cases, or making credit decisions without considering process flow (e.g., using prediction for rejected cases). Do not use predicted probabilities as absolute default rates.  
-  **Deployment caution**:  
  1. If policy changes again (e.g., new thresholds), retrain or validate on new activations; do not apply old model blindly.  
  2. If external feed availability improves (e.g., partner feeds more often), censoring pattern may change; re-evaluate calibration on known labels.  
  3. If system migration affects event naming (new renames), prefix extraction still works (uses recorded names), but verify `concept:name` consistency via `pm4py.discover_dfg` for variant detection; update feature definitions if new activities appear.  
  4. Always report prediction interval or CDF estimate alongside point probability; avoid stating "probability = X%" without uncertainty when censored cases are common.

> **Three deployment-driven DGP changes** (explicit):  
> 1. New policy reducing activation rate (e.g., stricter Acceptance)  more cases become non-activated; model trained on activated cohort remains valid, but absolute default rate among applicants may drop; monitoring should track activation rate separately.  
> 2. Improved external feed coverage (e.g., partner feeds within 7 days)  fewer censored activated cases; re-evaluate calibration on known labels as more labels become available.  
> 3. Change in document workflow (e.g., auto-upload reduces loops)  `credit_review_loops` and `doc_loop_count` distributions shift; feature importance may change; validate subgroup performance post-change.

## 9. PM4Py-oriented Python implementation skeleton
```python
import pandas as pd
import numpy as np
from datetime import datetime, timedelta
import pm4py

# Constants
EXTRACTION_DATE = pd.Timestamp("2026-02-15")
POLICY_CHANGE = pd.Timestamp("2025-07-01")  # 1 July 2025
MIGRATION_DATE = pd.Timestamp("2025-10-15")  # 15 Oct 2025
MAX_PREFIX_LEN = 10  # fixed prefix length in events

def load_and_parse(filepath):
    """Read CSV with proper timestamp parsing."""
    df = pd.read_csv(filepath, parse_dates=["time:timestamp"])
    # Ensure columns exist
    required = ["case:concept:name", "concept:name", "time:timestamp", "label_available_at"]
    for col in required:
        if col not in df.columns:
            raise ValueError(f"Missing column: {col}")
    return df

def mark_cohort(df):
    """Add cohort flags: is_activated, label_known, policy/migration flags."""
    # Map case ID (use case:concept:name as case identifier)
    case_id_col = "case:concept:name"
    activity_col = "concept:name"
    time_col = "time:timestamp"
    label_avail_col = "label_available_at"  # assume datetime
    
    # Ensure label_available_at is datetime (if NaT, set to extraction+1)
    df[label_avail_col] = pd.to_datetime(df[label_avail_col], errors="coerce")
    df.loc[df[label_avail_col].isna(), label_avail_col] = EXTRACTION_DATE + pd.Timedelta(days=1)
    
    # Find activation time per case
    activ_events = df[df[activity_col] == "Account Activated"]
    case_activation = activ_events.groupby(case_id_col)["time:timestamp"].min().reset_index()
    case_activation.rename(columns={"time:timestamp": "activation_time"}, inplace=True)
    
    # Merge activation info
    df = df.merge(case_activation, on=case_id_col, how="left")
    
    # Mark activated cases
    df["is_activated"] = df["activation_time"].notna()
    
    # Label known: label_available_at <= extraction AND default_90d not null in any event of case
    # (use min label_available_at per case; if any default_90d present, label exists if min_avail <= extraction)
    label_events = df[df["default_90d"].notna()]
    case_info = []
    for case, grp in df.groupby(case_id_col):
        if pd.isna(grp["activation_time"].iloc[0]):  # non-activated
            case_info.append({"is_activated": False, "label_known": False})
            continue
        # Activated case
        min_avail = grp[label_avail_col].min()
        has_default = label_events.loc[case].any() if case in label_events[case_id_col].values else False
        case_info.append({
            "is_activated": True,
            "label_known": (min_avail <= EXTRACTION_DATE) and has_default
        })
    
    info_df = pd.DataFrame(case_info, index=df[case_id_col].unique())
    df = df.merge(info_df.reset_index(), on=case_id_col, how="left")
    
    # Policy/migration flags (based on activation_time)
    def get_flags(row):
        act_time = row["activation_time"]
        if pd.isna(act_time):
            return {"policy_post": 0, "migration_post": 0}
        policy_post = 1 if act_time >= POLICY_CHANGE else 0
        mig_post = 1 if act_time >= MIGRATION_DATE else 0
        return {"policy_post": policy_post, "migration_post": mig_post}
    
    flags = df[df["is_activated"]].groupby(case_id_col).apply(get_flags).reset_index(drop=True)
    df = df.merge(flags, on=case_id_col, how="left")
    
    return df

def extract_prefix_features(df):
    """Build prefix features for activated cases only, filtering events <= activation_time."""
    case_id_col = "case:concept:name"
    activity_col = "concept:name"
    time_col = "time:timestamp"
    
    features = []
    for case, grp in df[df["is_activated"]].groupby(case_id_col):
        activation_time = grp["activation_time"].iloc[0]
        # Filter prefix events (<= activation_time)
        prefix_grp = grp[grp[time_col] <= activation_time].sort_values(time_col)
        
        # Basic prefix features
        start_time = prefix_grp[time_col].min()
        time_to_activation = (activation_time - start_time).days
        
        # Credit Review loops: count Credit Review events after first KYC
        kyk_idx = prefix_grp[prefix_grp[activity_col] == "KYC"].index[0] if "KYC" in prefix_grp[activity_col].values else None
        credit_review_idxs = prefix_grp[prefix_grp[activity_col] == "Credit Review"].index
        if kyk_idx is not None:
            post_kyc_cr = [idx for idx in credit_review_idxs if idx > kyk_idx]
            credit_review_loops = len(post_kyc_cr)
        else:
            credit_review_loops = len(credit_review_idxs)
        
        # Doc loop count: pairs of Doc Request -> Doc Reply
        doc_events = prefix_grp[prefix_grp[activity_col].isin(["Doc Request", "Doc Reply"])]
        doc_pairs = 0
        i = 0
        while i < len(doc_events):
            if doc_events.loc[i, activity_col] == "Doc Request":
                j = i + 1
                while j < len(doc_events) and doc_events.loc[j, activity_col] == "Doc Reply":
                    doc_pairs += 1
                    j += 1
                i = j
            else:
                i += 1
        
        # Risk score trend: max risk_score at Credit Review events
        cr_events = prefix_grp[prefix_grp[activity_col] == "Credit Review"]
        if not cr_events.empty:
            risk_trend = cr_events["risk_score"].max()
        else:
            risk_trend = np.nan
        
        # Queue time: first Credit Review - start
        first_cr_idx = prefix_grp[prefix_grp[activity_col] == "Credit Review"].index[0] if "Credit Review" in prefix_grp[activity_col].values else None
        if first_cr_idx is not None:
            queue_time = (prefix_grp.loc[first_cr_idx, time_col] - start_time).days
        else:
            queue_time = np.nan
        
        # Accept decision time: Activation - first Credit Review decision (approximate; use first CR after KYC)
        # Simple: time between first CR and activation
        first_cr_time = prefix_grp[prefix_grp[activity_col] == "Credit Review"][time_col].min() if "Credit Review" in prefix_grp[activity_col].values else start_time
        accept_time = (activation_time - first_cr_time).days
        
        feats = {
            "time_to_activation_days": time_to_activation,
            "credit_review_loops": credit_review_loops,
            "doc_loop_count": doc_pairs,
            "risk_score_trend": risk_trend,
            "queue_time_days": queue_time,
            "accept_decision_days": accept_time,
            "policy_post": grp["policy_post"].iloc[0],
            "migration_post": grp["migration_post"].iloc[0],
            "source_type": "partner" if df.loc[case, "source_system"] == "partner" else "internal"
        }
        features.append(feats)
    
    feat_df = pd.DataFrame(features)
    # Merge back to df
    df = df.merge(feat_df.rename(columns=lambda x: f"feat_{x}" if x.startswith("time_") or x.startswith("credit") else x), 
                   left_on=case_id_col, right_index=True, how="left")
    return df

def temporal_split(df):
    """Split by activation date; train < POLICY_CHANGE, val in [POLICY_CHANGE, MIGRATION_DATE], test >= MIGRATION_DATE + 1 day."""
    df = df.dropna(subset=["activation_time"])  # only activated
    df["activation_date"] = df["activation_time"].dt.date
    
    train_cases = df[df["activation_time"] < POLICY_CHANGE]["case:concept:name"].unique()
    val_cases = df[(df["activation_time"] >= POLICY_CHANGE) & (df["activation_time"] < MIGRATION_DATE)]["case:concept:name"].unique()
    test_cases = df[df["activation_time"] >= MIGRATION_DATE]["case:concept:name"].unique()
    
    train_df = df[df["case:concept:name"].isin(train_cases)].copy()
    val_df = df[df["case:concept:name"].isin(val_cases)].copy()
    test_df = df[df["case:concept:name"].isin(test_cases)].copy()
    
    return train_df, val_df, test_df

def audit_leakage(df):
    """Simple audit check for key leakage risks."""
    # Filter activated cases for audit
    act_df = df[df["is_activated"]].copy()
    
    # Check collection_status presence in prefix
    coll_in_prefix = act_df.loc[act_df["concept:name"] == "Collection Status", "activation_time"].notna()
    if coll_in_prefix.any():
        # In practice, drop collection_status from prefix features; here just warn
        print("  WARNING: Collection Status events found in activated prefix (may leak default). Should drop in feature engineering.")
    
    # Check documents_total usage (not directly in prefix features here, but note)
    doc_total_present = "documents_total" in df.columns
    if doc_total_present:
        print(" Note: Use daily document count up to activation for features; do not use nightly documents_total post-activation day.")
    
    # Label leakage check
    for case, grp in act_df.groupby("case:concept:name"):
        has_default_feature = any("default_90d" in col for col in grp.columns if col != "default_90d")
        if has_default_feature:
            print(f"  WARNING: Case {case} has default_90d in non-label columns; ensure not used as feature.")
    
    # Print cohort sizes
    print(f" Cohort sizes:")
    print(f"  - Total activated: {len(act_df)}")
    print(f"  - Known labels (label_known=True): {(act_df['label_known']).sum()}")
    print(f"  - Censored labels (label_known=False): {(~act_df['label_known']).sum()}")
    print(f"  - Partner activations: {(act_df['source_type'] == 'partner').sum()}")
    
    return True

def main(csv_path):
    # 1. Load
    df = load_and_parse(csv_path)
    
    # 2. Mark cohort
    df = mark_cohort(df)
    
    # 3. Audit (early check)
    audit_leakage(df)
    
    # 4. Extract features (only for activated; filters events <= activation automatically via prefix logic)
    df = extract_prefix_features(df)
    
    # 5. Temporal split
    train_df, val_df, test_df = temporal_split(df)
    
    # 6. Simple validation info (no model training; just show split consistency)
    train_act = train_df["activation_time"].min(), train_df["activation_time"].max()
    val_act = val_df["activation_time"].min(), val_df["activation_time"].max()
    test_act = test_df["activation_time"].min(), test_df["activation_time"].max()
    print(f"\n Temporal split:")
    print(f"  Train activations: {train_act[0].date()} – {train_act[1].date()}")
    print(f"  Val activations:   {val_act[0].date()} – {val_act[1].date()}")
    print(f"  Test activations: {test_act[0].date()} – {test_act[1].date()}")
    
    # 7. PM4Py prefix demo (for one case)
    sample_case = train_df["case:concept:name"].unique()[0] if len(train_df) > 0 else None
    if sample_case is not None:
        sample_events = train_df[train_df["case:concept:name"] == sample_case].sort_values("time:timestamp")
        activ_events = sample_events[sample_events["concept:name"] == "Account Activated"]
        if not activ_events.empty:
            act_time = activ_events["time:timestamp"].min()
            prefix_events = sample_events[sample_events["time:timestamp"] <= act_time]
            # Format as pm4py log
            log = pm4py.format_dataframe(
                prefix_events[["case:concept:name", "concept:name", "time:timestamp"]],
                case_id_col="case:concept:name",
                activity_col="concept:name",
                time_col="time:timestamp"
            )
            prefixes = pm4py.get_prefixes_from_log(log, max_length=MAX_PREFIX_LEN)
            print(f"\n PM4Py prefix demo for case {sample_case}:")
            print(f"  Number of prefixes (max len {MAX_PREFIX_LEN}): {len(prefixes)}")
            # prefixes is a list of logs; first prefix example
            if prefixes:
                first_prefix_log = prefixes[0]
                print(f"  First prefix activities: {list(first_prefix_log['activities'])[:5]}...")
    
    # 8. Cohort summary for report
    known_val = val_df[val_df["label_known"]]["case:concept:name"].nunique()
    censor_val = (~val_df["label_known"]).sum()
    print(f"\n Validation cohort label status:")
    print(f"  Known labels: {known_val}, Censored: {censor_val}")
    
    return df, train_df, val_df, test_df

# Usage (uncomment to run with real file):
# df, train, val, test = main("applications_events.csv")
```

**Explanation of skeleton**:
- Reads CSV with `parse_dates`, handles `label_available_at` as datetime.
- `mark_cohort` computes `is_activated` (via first `"Account Activated"`), `label_known` using `min(label_available_at)`  extraction date and presence of `default_90d`, and policy/migration flags **based on activation time** (no future info).
- `extract_prefix_features` builds prefix features using only events $\le$ activation time (e.g., counts loops in prefix), drops `collection_status` implicitly by not using it (audit warns), uses `risk_score_trend` from Credit Review events only.
- `temporal_split` splits by activation date respecting policy change and migration (train < 1 July 2025, val includes policy change, test $\ge$ 15 Oct 2025), avoiding random split.
- `audit_leakage` prints clear warnings (e.g., collection status in prefix) and cohort sizes; does not fabricate checks.
- PM4Py demo shows `pm4py.format_dataframe` and `pm4py.get_prefixes_from_log` on prefix events $\le$ activation, confirming no post-activation events in prefix.
- All steps are concrete, use only described APIs, and include comments marking assumptions (e.g., "approximate accept decision time", "simple doc pair count"). No model training; focuses on data engineering and validation scheme.
- Does not use `final_limit`, `decision_reason`, etc., in leakage as features without check; audit addresses them. Uses `label_available_at` only for cohort labeling, never as a feature.

This skeleton is short (~130 lines), implements cohort construction, censoring-aware prefix extraction, temporal split, leakage audit, and PM4Py prefix demo — meeting all required sections' rigor while avoiding bias, leakage, and mislabeling. It is ready for connecting to a survival/censoring-aware model (e.g., Cox or custom logistic with censoring indicator) in the next step.
