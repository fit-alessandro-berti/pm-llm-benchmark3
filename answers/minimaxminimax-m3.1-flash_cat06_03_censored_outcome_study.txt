## 1. Target definition

Let \(A_i\) indicate that application \(i\) reaches **Account Activated**, and let \(R_i\) indicate that it reaches the first completed **Credit Review**.

For activated applications only, define

\[
D_{90,i}=\mathbf 1\{\text{a default occurs in }[A_i,A_i+90\text{ days}]\}.
\]

A value \(D_{90,i}=0\) is assigned only when the activated account has complete 90-day follow-up and an observed non-default outcome. For rejected, withdrawn, transferred without linked re-entry, and open applications, \(D_{90}\) is **undefined**, not zero.

- **Prediction time:** \(t_i\), the timestamp of the first completed Credit Review. All predictors must be known at or before \(t_i\). Fixed-event and elapsed-time prediction times are analyzed separately as specified below.
- **Horizon:** 90 days beginning at activation, not 90 days beginning at application or at prediction.
- **Unit of analysis:** The canonical application. If a transfer is linked to a later platform case, all linked events are combined under one root application ID.
- **Primary population:** Applications started during the observation window that reach \(t_i\), are observed to activate under the factual activation policy, and have a matured, observable 90-day outcome.
- **Estimand:** The application-level conditional risk

\[
\theta(x)=P(D_{90}=1\mid A=1,R=1,X_{\le t_i}=x),
\]

or its marginal analogue \(P(D_{90}=1\mid A=1,R=1)\). This is a factual, activation-conditional predictive estimand under the observed policy, not a causal effect of activation.

This formulation is preferable to “default for every application” because activation creates the exposure period in which default is defined. The 21,600 labeled accounts are the relevant population for the default model; they are not a random sample of all 48,000 applications.

For an operational system that must score every application, the defensible design is two-stage:

1. A pathway model estimates \(P(A=1,\text{pathway}\mid X)\) using all applications.
2. The default model estimates \(P(D_{90}=1\mid A=1,X)\).

The product \(P(A=1\mid X)P(D_{90}=1\mid A=1,X)\) is a **joint probability of activation followed by default under the observed policy**, not the probability that an arbitrary application defaults.

Credible alternatives answer different questions:

- A **multi-state model** can represent pre-activation states and transitions to rejection, withdrawal, transfer, activation, activation without default, and 90-day default. It is appropriate for disposition management across all applications but does not reduce to one honest “default for all” probability.
- A **time-to-default model after activation**, with day-90 administrative censoring and informative censoring for missing feeds, preserves timing information.
- A target such as \(P(D_{90}=1\mid do(\text{activate}))\) or the default risk that would follow a different approval policy is a counterfactual estimand and is not identified by these data.

## 2. Cohort construction

The reporting unit is the root application after applying known transfer links. The cohort-flow table below uses the reported snapshot classification and accounts for all 48,000 starts.

| Flow at the cutoff | Count | Status in the primary study | Treatment |
|---|---:|---|---|
| Activated; label observed: 2,700 default, 18,900 non-default | 21,600 | Labeled primary outcomes | Eligible for the conditional default model when the required prefix exists |
| Activated; 90-day outcome or feed not yet usable | 3,600 | Not mature, delayed, or feed-missing | Right-censored/delayed/unknown; never converted to non-default |
| Rejected | 9,100 | Competing terminal outcome | Default target undefined |
| Withdrawn | 5,700 | Competing terminal outcome | Default target undefined |
| Transferred | 2,900 | Competing event or missing follow-up | Follow known links; unresolved transfers are not negatives |
| Still open | 5,100 | Administrative right censoring for time to activation | Not in the activated default denominator |
| **Total** | **48,000** |  |  |

The aggregate of 3,600 does not disclose how many are still inside the 90-day horizon, inside the additional 7–35 day feed window, or overdue for the expected feed. The implementation must split this bucket using activation time, `label_available_at`, and the cutoff. A feed-overdue case must be treated as selectively missing rather than as an ordinary right-censored non-default.

**As-of rules**

- Use only records whose `data_extract_time` is no later than the analysis cutoff.
- Event features use events with timestamps in 1 January 2024–31 December 2025 and no later than the cutoff.
- Outcome metadata arriving after 31 December 2025 but no later than the cutoff may be used to ascertain historical labels. Such metadata must not enter event features.
- Apply transfer links known at the cutoff. Later events from a linked platform are included only if their event timestamps are still before the relevant prediction time.
- Canonicalize activity names using a versioned migration dictionary before splitting or feature extraction.
- Remove exact duplicate events using a frozen rule, such as root application, canonical activity, event timestamp, and source system. Audit near-duplicates separately.
- Preserve application start time before constructing any temporal split.

**Primary inclusion and exclusion**

- Include in the default model: a root application with a valid pre-decision prefix, an observed activation, a matured outcome, and an observed label.
- Exclude from the default model, but retain in the cohort flow: applications without an activation, activations without mature labels, unresolved transfers, and applications with no usable prediction landmark.
- These exclusions are not negative examples. A separate all-application pathway model should use them.

A random split of the 21,600 labeled accounts would be inappropriate because it mixes policy regimes and does not recreate the deployment distribution.

## 3. Censoring and missing-label strategy

| Mechanism | Interpretation | Primary handling | Testability |
|---|---|---|---|
| Ordinary right censoring | An open application has not yet activated by the cutoff; in a post-activation survival analysis, a non-default has not defaulted by day 90 | Censored at the cutoff or day 90; excluded from the observed binary label denominator, never coded zero | Timing is directly observable; independence of censoring is not |
| Delayed label | The 90-day horizon has passed, but the external feed is still within its expected 7–35 day arrival period | Administrative delayed-label censoring; wait for `label_available_at` | Arrival timing and maturity are directly testable |
| Selection through activation | Outcome exposure begins only after activation | Define the primary estimand conditionally on activation; do not impute zero for non-activated cases | The selection mechanism can be described, but counterfactual defaults without activation are not observable |
| Rejection or withdrawal | The application leaves before activation | Competing event for time to activation; undefined target for the binary default outcome | Observable, but the unobserved counterfactual is not |
| Transfer | The application leaves the observed process, possibly reappearing under another ID | Follow known links. For unresolved transfers, censor at transfer for time to activation and treat the activation outcome as selectively unobserved | Linkage and timing are observable; missing-link outcome is not |
| Feed overdue after maturity | The account should be ascertainable but no outcome feed has arrived | Presumed missing/MNAR outcome; not a non-default | Missingness covariates are partially testable; the no-outcome truth is not |

**Primary analysis**

Use the observed labeled activation cohort, with the following qualifications:

1. Restrict the default denominator to activated applications whose 90-day horizon and required feed ascertainment date have passed by the analysis cutoff.
2. Fit a regularized logistic model and a boosted-tree benchmark using only pre-prediction features.
3. If there are matured activations with missing labels, estimate a cross-fitted label-observation propensity model

   \[
   e(X)=P(\text{label observed}\mid X,\text{matured activation}),
   \]

   using pre-activation variables, source system, channel, region, and known historical variables. Use stabilized inverse-probability weights \(1/e(X)\), with weight truncation and effective-sample-size reporting. A complete-case result remains a sensitivity analysis.
4. The primary target conditions on activation, so non-activated applications do not enter this model and do not require activation weights. If the intended claim is generalized to all applications reaching the review landmark, a separate activation/pathway model or an activation-probability weighted analysis is required.
5. Recalibrate only on the temporal validation block. Do not recalibrate using the locked test block.

**Sensitivity analyses**

- **MNAR/pattern-mixture analysis:** Assume missing activated cases have a default probability \(\delta_m\) varying by source, channel, or region; refit under several plausible \(\delta_m\) values. Also report the extreme all-non-default and all-default bounds.
- **Competing-outcome analysis:** Model rejection, withdrawal, transfer, activation, and subsequent 90-day default as competing transitions using all applications.
- **Survival analysis:** Use time from activation to default, with left truncation at activation, day-90 censoring for non-defaults, and inverse-probability-of-censoring weights for feed absence. This should be implemented with an appropriate survival package, not a fabricated PM4Py function.
- **Activation-selection sensitivity:** Restrict start dates to those with sufficient follow-up or use inverse-probability-of-activation weights based on the landmark covariates. This addresses administrative selection into observed activations, but cannot recover counterfactual outcomes for applications never activated.

Timing-based assumptions are directly testable. Missing-at-random assumptions are only partially testable through covariate comparisons between observed and missing labels. Whether partner missingness is independent of unobserved credit quality, and what would happen to rejected or withdrawn applications under another policy, are fundamentally untestable from these data.

## 4. Prefix extraction

The primary operational landmark is the first completed Credit Review. The normal path—Application Started, Identity/KYC Check, Credit Review—provides approximately three early events. Only events at or before the landmark are eligible.

**Canonical event construction**

1. Parse timestamps with a stated timezone policy.
2. Apply the frozen activity-renaming map, including the October migration aliases.
3. Link transfers to root applications where possible.
4. Sort by application, event timestamp, and a deterministic tie-breaker.
5. Remove exact duplicates and record the number removed.
6. Reject prefixes containing Accept, Reject, Withdrawal, Transfer, Activation, Collections, or Default events.

The activity map must come from the migration data dictionary or changelog, not from outcome frequencies or a model fitted on the full test period.

**Fixed-event-count prefixes**

Freeze a candidate \(K=3\) before examining test performance. PM4Py’s `get_prefixes_from_log(log, length=3)` can produce the exact three-event prefixes after canonicalization and deduplication.

- The prediction time is the third event’s timestamp.
- Require that the prefix ends no later than the first Credit Review for the primary decision-focused analysis.
- Exact-\(K\) cases with fewer than three events are reported separately. A capped-prefix sensitivity analysis can use all available events through the landmark, with `event_count` and explicit missingness indicators; it must not be mixed silently with exact-\(K\) results.
- Repeated document requests consume event positions in a fixed-count prefix. Therefore also report loop counts and a separate elapsed-time analysis.

**Elapsed-time prefixes**

For a pre-registered elapsed horizon \(\tau\), such as 24 or 72 hours after Application Started:

- Use the exact event timestamp, not calendar-day membership.
- Include only events with timestamp \(\le t_i+\tau\).
- Select \(\tau\) using training/validation data only.
- Analyze this as a different prediction time and population, not as an interchangeable encoding of the first-review landmark.

A later pre-decision landmark, such as immediately before the final credit decision, can be used as an additional operational variant. It naturally exposes document/rework features that are unavailable at the first review, but it changes the deployment time and therefore must be reported separately.

## 5. Process-aware features

| Feature family | Examples | Valid construction |
|---|---|---|
| Static case attributes | Requested amount, channel, region, originating source, application month | Use values known at application start. If these fields can change, take their first event-time values |
| Prefix control flow | Activities observed, ordered activity sequence, number of distinct activities, transition counts, visited states, prefix-local DFG behavior | Derive from the prefix only. A global DFG must not be learned on future or test traces |
| Timing | Time since application start, inter-event delays, review duration, business-hour delay, time of day, weekend indicator | Use exact timestamps at or before the prediction point |
| Resource and queue | Reviewing resource/team, resource at the current event, concurrent workload, number of open applications in the same queue | Event assignments must be timestamped. Queue measures require a historical snapshot reconstructed at the prediction time |
| Rework | Number of document requests, repeated Credit Reviews, return transitions, time since last document event | Available only at a later prefix. At the first-review landmark these variables are structurally absent, not zero unless “no rework so far” is explicitly encoded |
| Calendar and policy | Day of week, month, days since policy change, migration-period indicator | Known at prediction time, but should be used for monitoring or recalibration rather than treated as a causal correction |
| Historical reference data | Resource experience reconstructed from prior events, rolling workload, historical channel/region default rates, prior-review performance | Compute only from information available before the prediction time and from the training fold; historical label aggregates must be fold-safe |

The extraction-time resource experience field should not be used directly. A replacement can be reconstructed from the number, complexity, and outcomes of that resource’s prior completed applications before the current prediction time.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated after the final credit decision; encodes later underwriting information | Only values assigned at or before \(t_i\) would be valid | Drop for the primary pre-decision model | It is unavailable at the first-review landmark and is policy-informed |
| `decision_reason` | Available at or after Accept/Reject and may directly encode the credit decision | Use only in a post-decision target that explicitly permits it | Drop | It is future information for a pre-decision prediction and a strong policy proxy |
| `collection_status` | Updated after activation and may directly reveal default | Never use as a predictor of the default label | Drop | Direct target leakage |
| Future events | Contract Signed, Activation, Collections Contact, and Default Recorded reveal the pathway or outcome | `event_timestamp <= prediction_time` | Filter and drop later events | All training and validation extraction must use the same as-of rule |
| `documents_total` | Nightly snapshot can include uploads later on the prediction day | Count document-upload events with exact timestamps at or before \(t_i\) | Repair, or drop if exact upload times are unavailable | Calendar-day snapshots leak same-day future activity |
| Updated `risk_score` | A final/backfilled value may incorporate later reviews or decisions | Take the latest event-time value whose timestamp is at or before \(t_i\); derive changes only from prior values | Repair and keep | The latest prefix value is valid; the last row’s value is not |
| Extraction-time resource experience | Includes experience accrued after the prediction point | Reconstruct prior activity/experience through an as-of event table | Repair, otherwise drop | Otherwise it leaks worker tenure and future workload |
| `default_90d` | The outcome itself | Join only after cohort and feature construction | Target only | Direct leakage |
| `label_available_at` | Encodes feed timing and potentially partner/source behavior | Use to determine whether a label was known at the analysis cutoff | Audit and cohort construction only; drop from predictors | It is not available to the lender at prediction time |
| `data_extract_time` | Reveals snapshot mechanics and may differ from event time | Use for snapshot inclusion checks only | Filter only | Not a behavioral predictor |
| `org:resource` | Resource identity may proxy policy, team, or socioeconomic context | Use the resource recorded on the event at or before \(t_i\) | Keep with subgroup audit | It is event-time available, but may introduce fairness and policy-shift concerns |
| `source_system` | Partner origin strongly predicts missing outcome feeds | Use the source known at the event | Keep, but audit calibration and missingness | It is operationally known and useful for monitoring feed quality |
| `case:requested_amount`, `case:channel`, `case:region` | Usually static, but could be backfilled or changed | Use values known at application start and verify stability | Keep after verification | Low leakage risk if genuinely static |
| Activity names | Migration aliases can create spurious new categories and break categorical encoders | Apply the same frozen canonical map in every fold | Repair | Prevents migration artifacts from appearing predictive |

## 7. Validation design

A locked temporal backtest should use application start time—not row order or event time alone—for splitting.

| Block | Application start dates | Purpose |
|---|---|---|
| Development/training | 1 January 2024–31 March 2025 | Fit preprocessing, encoders, DFG vocabulary, resource histories, and model parameters |
| Validation | 1 April–30 June 2025 | Select prefix length, elapsed horizon, hyperparameters, threshold, and calibration |
| Locked test | 1 July–14 October 2025 | Post-policy-change, largely pre-migration temporal test |
| Shift stress | 15 October–31 December 2025 | Migration and late-cohort stress; default metrics may be unavailable because labels have not matured |

Additional rolling-origin folds should reproduce deployment: for each fold, fit only on prior start dates and use records whose labels were available by that fold’s analysis date. All preprocessing and historical aggregates must be refit within the fold. If the snapshot has overwritten historical attribute values, a genuine historical backtest requires a bitemporal/versioned table; the current snapshot alone cannot reconstruct what was known at earlier dates.

**Policy and migration handling**

- Report pre- and post-1 July performance separately. A policy-period indicator does not repair a changed conditional outcome relationship.
- Compare a model trained only on pre-policy data with a rolling post-policy refit, but keep the locked test evaluation unbiased.
- Validate the migration alias map and duplicate rate before extracting features.
- Treat the October–December cohort as a distribution-shift stress test. Do not report a 90-day default metric until outcomes mature; instead monitor activation, label maturity, missing-feed rates, prefix completeness, and calibration among cases already labeled.
- For each evaluation block, report both the 90-day-matured set and the stricter horizon-plus-feed-matured set. An activation after approximately 17 October 2025 has a matured 90-day horizon by the cutoff, while full 35-day feed ascertainment requires activation by approximately 13 October 2025.

**Metrics**

For the conditional binary target, report:

- AUROC and area under the precision-recall curve, with the historical activated prevalence of 2,700/21,600 = 12.5% as the AUPRC reference.
- Brier score and log loss.
- Calibration intercept, calibration slope, reliability plots, and expected calibration error.
- Sensitivity, specificity, PPV, and NPV at a threshold fixed on validation data.
- Weighted metrics using the label-observation model, alongside unweighted complete-case metrics.
- Effective sample size and weight distributions.
- Time-block or application-level bootstrap confidence intervals.

Report subgroup results, with sample sizes and uncertainty, by source/partner, channel, region, amount band, reviewing resource or team, activation cohort, policy period, and label-observation status. Migration-era estimates should be shown separately once labels mature.

A random case split can look reasonable under an IID assumption but is misleading here because it mixes pre/post-policy and pre/post-migration regimes, hides temporal calibration drift, and evaluates interpolation rather than deployment under policy and macroeconomic change. An event-level random split would be substantially worse because it directly exposes future events.

## 8. Limitations and decision-use boundary

The study can claim:

- Predictive association between early, as-of application information and 90-day default **conditional on activation and the factual policy period**.
- Identification of applications likely to default after activation under the observed pathway.
- Temporal calibration and subgroup behavior where mature labels are available.

It cannot claim:

- A default probability for every application.
- That rejected, withdrawn, transferred, or open applications were non-defaults.
- The effect of rejecting or approving an application.
- Prevention of defaults caused by using the model.
- Recovery of defaults for partner cases with missing feeds.
- Invariance across the July policy change or the October migration.
- Fairness or causal validity merely because protected or proxy variables are excluded.

The activation mechanism is a major selection mechanism: credit officers and automated rules decide who becomes exposed, and unobserved factors may affect both activation and later default. The partner feed mechanism is another selection mechanism because partner-originated accounts are more likely to have unobserved outcomes. Conditioning on activation avoids mislabeling the unactivated population but does not make the resulting score causal.

Deployment can change the data-generating process in at least four ways:

1. If credit officers use the score, approval and activation rates change, altering the composition of the activated population.
2. If collections intervention is triggered by the score, defaults and subsequent labels become affected by treatment rather than merely predicted.
3. Market conditions, policy thresholds, partner integrations, and feed-delivery practices can change both prevalence and missingness.
4. Logging and migration changes can alter event coverage, activity names, duplicate rates, and the measured prefixes even when credit behavior is unchanged.

The operational recommendation is therefore shadow deployment first, with monitoring of activation rate, feed completeness, calibration, policy-period drift, and subgroup error. A pre-activation score must always be labelled “risk conditional on activation.” It should not be used as a causal approve/reject rule without a separate policy-impact design.

## 9. PM4Py-oriented Python implementation skeleton

The code below assumes that `default_90d` is encoded as 0/1 and that the linkage adapter can provide a transitively resolved `new_case -> root_case` mapping. `MIGRATION_MAP` must be populated from the migration changelog before production use. Label metadata is extracted before the event-window filter so a late feed attached to an old event can be used for outcomes without entering the event feature log.

```python
import numpy as np
import pandas as pd
import pm4py
from pathlib import Path

CSV = Path("applications_events.csv")
LINKAGE_CSV = Path("case_links.csv")  # optional adapter: new_case, root_case
CUTOFF = pd.Timestamp("2026-02-15")
OBS_START = pd.Timestamp("2024-01-01")
OBS_END = pd.Timestamp("2025-12-31")
PREFIX_K = 3
FEED_MAX_DAYS = 35

# Frozen semantic map; populate migration aliases from the changelog, not outcomes.
BASE_ACTIVITY = {
    "application started": "Application Started", "identity/kyc check": "Identity/KYC Check",
    "credit review": "Credit Review", "accepted": "Accepted", "rejected": "Rejected",
    "withdrawn": "Withdrawn", "transferred": "Transferred",
    "account activated": "Account Activated",
}
MIGRATION_MAP = {}  # normalized old activity -> canonical activity

def canonical_activity(x):
    k = str(x).strip().casefold()
    return MIGRATION_MAP.get(k, BASE_ACTIVITY.get(k, str(x).strip()))

raw = pd.read_csv(CSV)
for c in ["time:timestamp", "label_available_at", "data_extract_time"]:
    raw[c] = pd.to_datetime(raw[c], errors="coerce", utc=True).dt.tz_localize(None)
raw = raw.loc[raw["data_extract_time"].notna() &
              raw["data_extract_time"].le(CUTOFF)].copy()
raw["_y"] = pd.to_numeric(raw["default_90d"], errors="coerce")
raw["canonical_activity"] = raw["concept:name"].map(canonical_activity)

roots = {}
if LINKAGE_CSV.exists():
    lk = pd.read_csv(LINKAGE_CSV)
    roots = dict(zip(lk["new_case"].astype(str), lk["root_case"].astype(str)))
raw["app_id"] = raw["case:concept:name"].astype(str).map(lambda z: roots.get(z, z))

events = raw.loc[raw["time:timestamp"].between(OBS_START, OBS_END)].copy()
labels = raw.loc[raw["_y"].notna() &
                 (raw["label_available_at"].isna() |
                  raw["label_available_at"].le(CUTOFF))].copy()
events = events.sort_values(
    ["app_id", "time:timestamp", "canonical_activity"], kind="mergesort")
events = events.drop_duplicates(
    ["app_id", "canonical_activity", "time:timestamp", "source_system"])
print(f"Removed {len(raw) - len(events)} duplicate event rows")

SAFE = ["case:concept:name", "concept:name", "time:timestamp", "org:resource",
        "case:channel", "case:region", "case:requested_amount", "risk_score",
        "source_system"]
safe = events[SAFE + ["app_id"]].copy()
safe["case:concept:name"] = safe["app_id"]
safe["concept:name"] = events["canonical_activity"]
log = pm4py.format_dataframe(
    safe, case_id="case:concept:name", activity_key="concept:name",
    timestamp_key="time:timestamp")

label_info = {}
for aid, g in labels.groupby("app_id", sort=False):
    ys = g["_y"].dropna().unique()
    y = float(ys[0]) if len(ys) == 1 else np.nan
    av = g.loc[g["_y"].notna(), "label_available_at"].min()
    label_info[aid] = (y, av, len(ys) > 1)

rows = []
for aid, g in events.groupby("app_id", sort=False):
    def ft(a):
        return g.loc[g["canonical_activity"].eq(a), "time:timestamp"].min()
    start = ft("Application Started")
    act = ft("Account Activated")
    review = ft("Credit Review")
    ends = [(ft(a), s) for a, s in
            [("Rejected", "rejected"), ("Withdrawn", "withdrawn"),
             ("Transferred", "transferred")] if pd.notna(ft(a))]
    terminal = min(ends, key=lambda z: z[0]) if ends else (pd.NaT, "open")
    y, av, conflict = label_info.get(aid, (np.nan, pd.NaT, False))
    if pd.notna(act) and pd.notna(av) and av < act:
        y, conflict = np.nan, True
    if pd.notna(act):
        if pd.notna(y):
            status, censor = "labeled", ""
        elif act + pd.Timedelta(days=90) > CUTOFF:
            status, censor = "not_mature", "administrative_horizon"
        elif act + pd.Timedelta(days=90 + FEED_MAX_DAYS) > CUTOFF:
            status, censor = "delayed_label", "administrative_feed"
        else:
            status, censor = "missing_feed", "informative_missing_feed"
        terminal = (act, "activated")
    elif ends:
        status, censor = terminal[1], f"competing_{terminal[1]}"
    else:
        status, censor = "open", "ordinary_right_censoring"
    rows.append({
        "app_id": aid, "start": start, "activation": act, "review": review,
        "terminal_time": terminal[0], "status": status, "censor": censor,
        "y": y, "label_available_at": av, "label_conflict": conflict,
        "path_conflict": bool(pd.notna(act) and any(t < act for t, _ in ends))})
cases = pd.DataFrame(rows)

def temporal_split(t):
    if t < pd.Timestamp("2025-04-01"):
        return "train"
    if t < pd.Timestamp("2025-07-01"):
        return "validation"
    if t < pd.Timestamp("2025-10-15"):
        return "test_post_policy"
    return "stress_migration"

cases["split"] = cases["start"].map(temporal_split)
print(cases["status"].value_counts().to_string())
print(cases.groupby(["split", "status"]).size().to_string())

# Training-fold process audit only; a full-data DFG must not become a feature.
train_ids = set(cases.loc[cases["split"].eq("train"), "app_id"])
train_log = pm4py.format_dataframe(
    safe.loc[safe["app_id"].isin(train_ids)].copy(),
    case_id="case:concept:name", activity_key="concept:name",
    timestamp_key="time:timestamp")
dfg = pm4py.discover_dfg(train_log)

def evv(e, key, default=None):
    try:
        return e[key]
    except (KeyError, TypeError):
        return default

lookup = cases.set_index("app_id").to_dict("index")
prefixes = pm4py.get_prefixes_from_log(log, length=PREFIX_K)
prows = []
for p in prefixes:
    evs = list(p)
    if len(evs) != PREFIX_K:
        continue
    evs.sort(key=lambda e: e["time:timestamp"])
    aid = evv(evs[0], "case:concept:name")
    end = max(evv(e, "time:timestamp") for e in evs)
    review = lookup[aid]["review"]
    if pd.isna(review) or end > review:
        continue
    acts = [evv(e, "concept:name") for e in evs]
    bad = {"Accepted", "Rejected", "Withdrawn", "Transferred", "Account Activated",
           "Collections Contact", "Default Recorded"}
    if bad.intersection(acts):
        continue
    risks = []
    for e in evs:
        v = pd.to_numeric(evv(e, "risk_score", np.nan), errors="coerce")
        if pd.notna(v):
            risks.append(float(v))
    resource = np.nan
    for e in reversed(evs):
        v = evv(e, "org:resource")
        if v is not None:
            resource = v
            break
    prows.append({
        "app_id": aid, "split": lookup[aid]["split"], "prefix_time": end,
        "prefix_activities": "|".join(acts),
        "activity_count": len(set(acts)),
        "review_repeats": max(0, acts.count("Credit Review") - 1),
        "document_loops": sum("document" in str(a).casefold() for a in acts),
        "elapsed_hours": (end - lookup[aid]["start"]).total_seconds() / 3600,
        "risk_score_latest": risks[-1] if risks else np.nan,
        "risk_score_delta": risks[-1] - risks[0] if risks else np.nan,
        "last_resource": resource,
        "case:channel": evv(evs[0], "case:channel"),
        "case:region": evv(evs[0], "case:region"),
        "case:requested_amount": evv(evs[0], "case:requested_amount"),
        "source_system": evv(evs[0], "source_system")})
prefix_df = pd.DataFrame(prows)

model = prefix_df.merge(
    cases[["app_id", "status", "y"]], on="app_id", how="left",
    validate="many_to_one")
model = model.loc[model["status"].eq("labeled") & model["y"].notna()].copy()
feature_cols = [
    "prefix_activities", "activity_count", "review_repeats", "document_loops",
    "elapsed_hours", "risk_score_latest", "risk_score_delta", "last_resource",
    "case:channel", "case:region", "case:requested_amount", "source_system"]
forbidden = {"final_limit", "decision_reason", "collection_status", "default_90d",
             "label_available_at", "documents_total", "future_events"}
overlap = forbidden.intersection(feature_cols).union(
    forbidden.intersection(model.columns))
assert not overlap, overlap
assert model["prefix_time"].le(model["app_id"].map(lookup["review"])).all()
audit = {
    "forbidden_overlap": overlap, "model_rows": len(model),
    "prefix_rows": len(prefix_df), "cohort_rows": len(cases),
    "post_review_prefixes": int((prefix_df["prefix_time"] >
                                  prefix_df["app_id"].map(lookup["review"])).sum())}
print(audit)
print(model.groupby("split").size().to_string())

# Elapsed-time variant: select safe rows with timestamp <= start + tau (e.g. 72h).
# Survival/competing-risk models would be fitted outside PM4Py with left truncation,
# day-90 censoring and IPCW; PM4Py has no survival-modeling API used here.
# The all-application alternative models rejection/withdrawal/transfer as transitions.
```
