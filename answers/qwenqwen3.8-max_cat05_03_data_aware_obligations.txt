## 1. Temporal Data Semantics

The log is treated as an **event-time state machine**, not as a table whose final row describes the whole case.

### State reconstruction

1. **Order events within each case by**  
   `(time:timestamp, event_index)` ascending.  
   `event_index` is the authoritative tie-breaker for equal timestamps.

2. **Blank attribute cells are not null assignments.**  
   A blank means “no update at this event.” Therefore, attribute values are reconstructed by **forward-filling only from prior events within the same case**.

3. **Release state is the state immediately before or at the Release_Funds event.**  
   For a Release_Funds event `r`, the value of an attribute is the value set by the latest preceding update event `u` such that `u` is before `r`, or at the same timestamp but with a lower `event_index`.

4. **Final case values are not copied backward.**  
   A later settlement amount, later jurisdiction, later risk level, or later exemption record does not establish the value that governed an earlier Release_Funds event unless separate evidence explicitly establishes that earlier effective time.

5. **Same-timestamp ordering has concrete consequences.**  
   In TX-311, the Enhanced_Review at `event_index 3` precedes the Update_Jurisdiction to DE at `event_index 4`, even though both occur at `2026-04-06T16:20:00Z`. Therefore, the review occurred while the jurisdiction was still US, but the release occurred after the jurisdiction had become DE.

### Material changes

For these rules, a material change is a change that can affect an obligation:

- `Update_Amount` with an increase of more than 20 percent from the last known amount;
- `Risk_Reclassify`;
- `Update_Jurisdiction`;
- `Update_Customer_Type`;
- for sanctions, `Sanctions_List_Update` is material for R3.

A **decrease** in amount is not, by itself, an invalidating material change under R4. An amount increase from an unknown prior amount is not safely classifiable under R4/R6.

### Time semantics

Four time concepts are separated:

| Time type | Meaning | Example |
|---|---|---|
| Event time | When the event occurred in the process, given by `time:timestamp` and `event_index`. | Release_Funds at 09:40. |
| Effective time | When a legal or policy condition becomes effective. | EX-77 effective from 09:00. |
| Record time | When data was written to a system of record. | EX-77 database insert at 11:00. |
| Evidence time | When evidence proves that a fact existed. | Qualified signature timestamp for EX-77 at 09:05. |

A late record can be evidence of an earlier effective approval, but a backdated display alone is not conclusive. Conversely, a record inserted after release is not automatically invalid if reliable evidence establishes earlier effectiveness and approval.

### Formal pseudo-logic

Let `ord(e) = (timestamp(e), event_index(e))`.

Define:

```text
e1  e2    iff ord(e1) < ord(e2)
e1  e2    iff ord(e1)  ord(e2)
```

State:

```text
value(C, A, V, E) :-
    event(E, C),
    update(U, C, A, V),
    U  E,
    not exists U2:
        update(U2, C, A, _),
        U  U2,
        U2  E.

unknown(C, A, E) :-
    not exists V: value(C, A, V, E).
```

Material amount increase:

```text
material_amount_increase(U, C) :-
    Update_Amount(U, C),
    old_amount(U, C, Old),
    new_amount(U, C, New),
    known(Old),
    known(New),
    New > 1.2 * Old.

material_change(M, C) :-
    material_amount_increase(M, C)
    or Risk_Reclassify(M, C)
    or Update_Jurisdiction(M, C)
    or Update_Customer_Type(M, C).
```

R1:

```text
R1_obligation(C, R) :-
    Release_Funds(R, C),
    value(C, jurisdiction, J, R),
    J != 'DE',
    value(C, amount, A, R),
    A >= 100000.

R1_satisfied_by_review(C, R) :-
    Enhanced_Review(H, C),
    H  R,
    not exists M:
        material_change(M, C),
        M  R,
        H  M.

R1_violation(C, R) :-
    R1_obligation(C, R),
    not valid_exemption(C, _, R),
    not R1_satisfied_by_review(C, R).
```

Thus, if there is a material change before release, the Enhanced_Review must be strictly after that material change. If the material change is at the same timestamp, `event_index` determines whether the review is after it.

R2:

```text
R2_obligation(C, R) :-
    Release_Funds(R, C),
    (
        value(C, risk_level, 'HIGH', R)
        or value(C, customer_type, 'PEP', R)
    ).

R2_satisfied(C, R) :-
    Enhanced_Review(H, C),
    Compliance_Approve(A, C),
    H  A,
    A  R,
    not exists T:
        r2_trigger_change(T, C),
        T  R,
        H  T.

R2_violation(C, R) :-
    R2_obligation(C, R),
    not R2_satisfied(C, R).
```

Here `r2_trigger_change` means a change that made the case HIGH risk or PEP. This captures the idea that the Compliance_Approve must follow a relevant Enhanced_Review.

R3:

```text
R3_obligation(C, R) :-

R3_violation(C, R) :-

        Sanctions_Screen(S2, C),
        L  S2,
        S2  R.
```

```text
R4_invalidating_increase(C, R) :-

        material_amount_increase(U, C),
        V  U,
```

```text
valid_exemption(C, X, R) :-
    claimed_at_release(R, X),
    approved_by(X, Head_Compliance),
    effective_from(X)  ord(R),
    ord(R)  expires(X),
    scope_jurisdiction(X) = value(C, jurisdiction, R),
```

A displayed backdated field alone does not satisfy `evidence_approval_before`. A qualified signature before release, or other reliable independent evidence, may satisfy it. A late database record may be consistent with earlier approval but is not sufficient alone.

```text
evaluate_at_event(C, R) :-
```

## 4. Ambiguities and Alternative Readings

### TX-305 — INDETERMINATE

TX-305 is indeterminate because the release-time amount is unknown. The jurisdiction is CA, which is not DE, so if the amount were at least EUR 100,000, R1 would trigger. If the amount were below EUR 100,000, R1 would not trigger.

Evidence that would change the result:

- **Immutable release payload showing amount < 100,000**: R1 would not trigger; likely COMPLIANT, subject to other rules.
- **Immutable release payload showing amount  100,000**: R1 would trigger. Because an Enhanced_Review occurred before release and no material change occurred after it, the case could become COMPLIANT if the review is accepted as covering the amount.
- **Evidence that the Enhanced_Review was invalid because it did not assess the amount**: If amount is  100,000 and the review must cover material data, the case could become NONCOMPLIANT.
- **Settlement evidence conclusively establishing release-time amount**: The settlement amount of 150,000 is reliable at settlement time, but the note says it “may equal release amount” and there is no immutable release payload. If independent evidence established that the settlement amount was the release amount effective at release, the amount could be resolved.

Without such evidence, R6 prevents defaulting the missing amount to a low-risk value.

### TX-310 — INDETERMINATE

TX-310 has a clear R1 trigger: foreign jurisdiction AE and amount 200,000. It has no Enhanced_Review. The only possible cure is exemption EX-88.

The exemption evidence is conflicting:

- displayed approval time is 08:50;
- displayed effective time is 08:00;
- release occurred at 10:00;
- the qualified signing certificate was created at 10:30, after release;
- the only witness to oral approval is the transaction requester;
- the database record was inserted at 11:00.

Alternative readings:

- **Strict documentary/signature interpretation**: If a valid exemption requires reliable written or signed approval before release, the post-release certificate creation defeats the exemption. The interested witness is insufficient. Result: NONCOMPLIANT.
- **Oral approval accepted**: If Head_Compliance oral approval at 08:45 is legally sufficient and the witness is accepted despite interest, EX-88 could be valid at release. Result: JUSTIFIED_EXCEPTION.
- **Certificate creation as administrative lag**: If independent evidence showed that the 10:30 certificate creation was merely a technical signing step for an approval already granted and documented before release, the exemption could be accepted. Result: JUSTIFIED_EXCEPTION.
- **Backdating concern**: If the certificate creation time is treated as evidence that the displayed 08:50 approval is unreliable, the exemption cannot be established. Result: NONCOMPLIANT.

Because the evidence is contradictory and the policy explicitly warns that backdated fields alone are not conclusive, the safest classification is INDETERMINATE pending evidential weighting.

### TX-302 — JUSTIFIED_EXCEPTION, but robust under alternative readings

TX-302 relies on EX-77. The exemption record was inserted at 11:00, after release, but the qualified signature timestamp is 09:05, before release, and the outage explanation is strong.

Alternative readings:

- **If record time controls**: If one incorrectly treats the 11:00 database insert as the only effective time, the exemption would appear late. However, TX-302 still has an Enhanced_Review at 09:20 before release and no material change after it. Therefore, R1 would still be satisfied by review, and the case would likely be COMPLIANT rather than justified by exemption.
- **If outage evidence is rejected**: If the qualified signature and outage documentation were rejected, the exemption would fail. Again, the existing Enhanced_Review would still satisfy R1 because there was no later material change.
- **If there had been a material change after 09:20**: Then exemption validity would have been decisive. With strong signature evidence, JUSTIFIED_EXCEPTION is appropriate.

Thus, the classification as JUSTIFIED_EXCEPTION reflects the valid exemption, but the operational compliance result is robust because the Enhanced_Review also exists.

### TX-311 — COMPLIANT under stated event-time semantics, but sensitive to ordering and materiality interpretation

TX-311 depends on same-timestamp ordering.

Given facts:

- amount increased from 90,000 to 115,000 at 16:10;
- Enhanced_Review occurred at 16:20, `event_index 3`;
- Update_Jurisdiction to DE occurred at 16:20, `event_index 4`;
- Release_Funds occurred at 16:30.

Under R7, the review precedes the jurisdiction update. At release, jurisdiction is DE, so R1 is not triggered.

Alternative readings:

- **Ignore event_index**: If same-timestamp events are treated as unordered, it is unclear whether the review occurred before or after the jurisdiction change. The case could become INDETERMINATE.
- **Treat jurisdiction change to DE as requiring re-review**: If any jurisdiction change after review, even a change that removes the foreign trigger, is treated as requiring a new Enhanced_Review, then TX-311 would become NONCOMPLIANT because the review occurred before the DE update.
- **Fix obligation at the moment amount exceeded threshold**: If R1 were interpreted as triggering when the amount became  100,000 while jurisdiction was US, the Enhanced_Review at 16:20 still occurred after that amount increase. The case remains compliant unless one also requires review after every later attribute change, including the DE update.
- **Copy final DE backward**: If one incorrectly treats the final jurisdiction as having applied at the time of the Enhanced_Review, the review would appear unnecessary. This would not change the release outcome but would distort the audit trail.

The stated event-index semantics resolve the case as COMPLIANT.

### Additional borderline interpretations

Two other cases are especially sensitive to threshold and materiality interpretation:

- **TX-306**: If every amount change, regardless of size, were treated as material under R1, the 220,000  230,000 increase after Enhanced_Review would require a new review. Under R4, however, only increases over 20 percent invalidate amount-dependent reviews, so TX-306 is COMPLIANT.
- **TX-308**: If decreases were treated as material changes requiring re-review, the decrease from 140,000 to 100,000 would invalidate the earlier Enhanced_Review. R4 explicitly says a decrease does not by itself invalidate a review, so TX-308 is COMPLIANT.

```python
print(trace_df.to_string(index=False))
```

The code deliberately produces coarse flags such as `PASS_COARSE`, `NONCOMPLIANT_COARSE`, and `REVIEW_REQUIRED`. It does not hard-code the final narrative classifications. Cases requiring evidential weighting, especially TX-305 and TX-310, are routed to review.

## 6. Why Control-Flow-Only Conformance Is Insufficient

Control-flow conformance checks whether activities appear in an allowed order. That is useful, but it cannot faithfully evaluate these rules because the obligations are conditional on time-varying data.

### 1. Final-state leakage

A control-flow checker often sees the final case attributes and implicitly applies them to all earlier events. That is wrong.

Example: TX-311 ends with jurisdiction DE. If final DE is copied backward, one might conclude the case was always domestic. But the Enhanced_Review at the same timestamp occurred before the jurisdiction update by `event_index`. The audit requires knowing the state at each event, not the final state.

### 2. Post-hoc exemptions

A control-flow model may see `Record_Exemption` in the trace and treat it as valid. But the timing of approval, effectiveness, record creation, and signature creation matters.

Example: TX-302 has a late database record but strong signature evidence before release. TX-310 has a late record and a certificate created after release. A sequence check cannot distinguish reliable late evidence from unreliable backdating.

### 3. Material changes after review

A trace can contain `Enhanced_Review` before `Release_Funds`, yet still be noncompliant if a material amount increase occurred after the review.

Example: TX-309 has an Enhanced_Review before release, but a later amount increase exceeding 20 percent invalidates that review for amount-dependent obligations. Control-flow conformance would usually mark the sequence as fitting.

### 4. Conditional activation

The need for Enhanced_Review or Compliance_Approve depends on data values: jurisdiction, amount threshold, risk level, customer type, sanctions-list status.

The same control-flow trace, for example `Create_Transaction  Release_Funds`, may be compliant for a low-value DE retail case and noncompliant for a foreign high-value PEP case. Control-flow conformance cannot represent these conditional activations without data-aware rules.

### 5. Missing data

If amount, risk, jurisdiction, or customer type is missing, a control-flow checker may silently assume the case is low risk or may ignore the missing attribute.

Example: TX-305 has an Enhanced_Review before release, so a control-flow check may pass. But the release amount is unknown. R6 forbids defaulting the missing amount to a low-risk value. The correct result is INDETERMINATE, not PASS.

### 6. Same-timestamp ordering

Many process-mining representations treat events with the same timestamp as unordered or break ties arbitrarily. Here, `event_index` is decisive.

Example: TX-311’s Enhanced_Review and Update_Jurisdiction share a timestamp. `event_index` establishes that the review occurred before the jurisdiction became DE. Ignoring this can change the reconstructed state and the compliance conclusion.

## 7. Recommended Logging and Control Improvements

To make future assessments more determinate, the event log and supporting systems should capture the following.

### 1. Immutable release payloads

Each `Release_Funds` event should include an immutable snapshot of all decision-relevant attributes:

- amount;
- currency;
- jurisdiction;
- risk_level;
- customer_type;
- PEP status;
- sanctions-screening status;
- exemptions relied upon;
- rule version used;
- reviewer/approver identifiers;
- payload hash.

This would resolve cases like TX-305, where the release amount is missing.

### 2. Separate effective time, record time, signature time, and event time

Every update and exemption should carry:

- `event_time`: when the action occurred;
- `effective_from`: when the value or exemption became effective;
- `effective_to`: when it ceased to be effective;
- `recorded_at`: when the database row was written;
- `signed_at`: when a qualified signature was created;
- `evidence_uri`: link to underlying evidence.

This would distinguish TX-302’s valid late record from TX-310’s contested backdated exemption.

### 3. Stable event ordering

Use a monotonic case-level sequence number or hybrid logical clock in addition to timestamps. Do not rely on wall-clock timestamps alone.

Recommended fields:

- `case_event_sequence`;
- `event_index` within timestamp;
- `source_system_clock`;
- `ordering_authority`.

This would remove ambiguity in same-timestamp cases like TX-311.

### 4. Attribute change provenance

Every attribute update should log:

- old value;
- new value;
- reason code;
- actor;
- source system;
- effective time;
- record time;
- supporting document identifier.

For amount changes, include percentage change or a materiality flag computed against the last reviewed amount.

### 5. Explicit exemption scope and lifecycle

Exemptions should be logged as first-class objects with:

- exemption ID;
- approver;
- approval workflow ID;
- effective_from;
- expires_at;
- jurisdictions;
- customer types;
- amount limits;
- currency;
- rules waived;
- signature hash;
- revocation time;
- linked cases or transactions.

A release should reference the exemption version relied upon, not merely an exemption ID.

### 6. Rule versioning and decision logs

Each release should record the policy version and rule engine decision:

- rule set version;
- rules evaluated;
- inputs used;
- outputs;
- violations;
- exemptions applied;
- indeterminate fields;
- override reason, if any.

This would make compliance decisions reproducible and auditable.

### 7. Sanctions-list versioning

Sanctions screening should record:

- list vendor;
- list version;
- list effective time;
- screening time;
- screened jurisdiction;
- screened entity identifiers;
- result;
- reviewer.

A `Sanctions_List_Update` event should include the list version and effective time, so R3 can be evaluated precisely.

### 8. Blocking or explicit escalation for missing decisive data

If amount, jurisdiction, risk, or customer type is missing at release, the system should either:

- block release;
- require documented emergency approval;
- route to manual compliance review;
- record a data-quality exception with owner and expiry.

This prevents silent release with unknown triggers, as in TX-305.

### 9. Review packets bound to state hashes

Each `Standard_Review`, `Enhanced_Review`, and `Compliance_Approve` should reference the exact state reviewed:

- payload hash;
- attribute values;
- rule version;
- material changes considered;
- reviewer attestation.

This would prevent arguments that a review occurred but did not cover the relevant amount, risk, jurisdiction, or PEP status.
