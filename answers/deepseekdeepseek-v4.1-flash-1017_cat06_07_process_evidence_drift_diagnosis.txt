import pandas as pd
import pm4py

def monthly_process_evidence(csv_path, case_col='case_id', act_col='activity', ts_col='timestamp'):
    raw = pd.read_csv(csv_path)
    raw[ts_col] = pd.to_datetime(raw[ts_col], errors='coerce', utc=True)
    raw = raw.dropna(subset=[case_col, act_col, ts_col]).copy()

    # Normalize pre-format because old/new labels must be one activity.
    raw[act_col] = raw[act_col].replace({
        'Diagnostic Assessment Completed':'Initial Diagnosis Completed',
        'DIAGNOSTIC_ASSESSMENT_COMPLETED':'Initial Diagnosis Completed'
    })

    # Duplicate strategy: exact event duplicates, then adjacent same-activity duplicates within 1s.
    if 'event_id' in raw.columns:
        raw = raw.drop_duplicates('event_id')
    raw = raw.sort_values([case_col, ts_col, act_col])
    raw = raw.drop_duplicates(subset=[case_col, act_col, ts_col])
    prev = raw.groupby(case_col)[[ts_col, act_col]].shift(1)
    adj_dup = (raw[act_col].eq(prev[act_col]) &
               (raw[ts_col] - prev[ts_col]).dt.total_seconds().abs().le(1))
    raw = raw.loc[~adj_dup].copy()

    # pm4py formatting: standardized columns case:concept:name/concept:name/time:timestamp
    df = pm4py.format_dataframe(raw, case_id=case_col, activity_key=act_col, timestamp_key=ts_col)
    log = pm4py.convert_to_event_log(df)

    # Interpretations:
    # event-calendar cohort = events occurring in month (process/DFG view).
    # case-start cohort = cases whose first event in month (predictive label view).
    starts = df.groupby('case:concept:name')['time:timestamp'].min()
    df['_case_start_month'] = df['case:concept:name'].map(starts).dt.to_period('M').astype(str)

    rows = []
    months = sorted(df['time:timestamp'].dt.to_period('M').astype(str).unique())
    for m in months:
        t0 = pd.Timestamp(m + '-01', tz='UTC')
        t1 = t0 + pd.offsets.MonthBegin(1)
        # Event-calendar log via PM4Py time filter.
        ev_log = pm4py.filter_time_range(log, t0, t1, mode='events')
        # Case-start log: all events for cases starting in m.
        ids = df.loc[df['_case_start_month'] == m, 'case:concept:name'].dropna().unique().tolist()
        cs_log = pm4py.filter_event_attribute_values(log, 'case:concept:name', ids, level='case')

        for cohort, sublog in [('event_calendar', ev_log), ('case_start', cs_log)]:
            if len(sublog) == 0:
                continue
            dfg, start_act, end_act = pm4py.discover_dfg(sublog)
            perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(sublog)
            variants = pm4py.get_variants(sublog)
            temporal = pm4py.extract_temporal_features_dataframe(sublog)

            top_edges = sorted(dfg.items(), key=lambda kv: kv[1], reverse=True)[:5]
            order_edge = perf_dfg.get(('Order Part', 'Part Received'))
            remote_edge = perf_dfg.get(('Initial Diagnosis Completed', 'Remote Fix'))
            var_rows = sorted(variants.items(), key=lambda kv: kv[1], reverse=True)[:5]
            total_variants = sum(variants.values()) if variants else 1
            unknown_share = sum(v for k, v in variants.items()
                                if any('UNKNOWN_ACTIVITY' in a for a in k)) / total_variants

            rows.append({
                'month': m,
                'cohort': cohort,
                'n_cases': sublog.shape[0] if hasattr(sublog, 'shape') else len(sublog),
                'n_events': len(sublog),
                'unknown_variant_share': unknown_share,
                'top_variants': var_rows,
                'top_dfg_edges': top_edges,
                'perf_edge_order_part_to_received': order_edge,
                'perf_edge_diag_to_remote_fix': remote_edge,
                'temporal_feature_columns': list(temporal.columns),
            })
    return pd.DataFrame(rows)

**October: dominated by label delay/censoring and outcome-API backlog.** Label maturity collapses to 55%, median label delay rises to 52 days, and the backlog disproportionately affects longer resolution paths. The observed breach rate of 0.16 is almost certainly not comparable to September’s 0.31; it likely reflects selection toward short/resolved paths rather than true improvement. The ongoing process/population issues may still be real, but October’s predictive metrics and observed breach rate cannot be used as direct evidence without backfill or censor-aware analysis.

## 3. Diagnostic tests

- **Label-maturity curves and fixed-vintage backtesting.** For each case-start cohort, evaluate only labels matured by fixed vintages such as 30, 45, 60, and 90 days, and plot breach/AUROC/Brier/ECE versus vintage. Expect under label-censoring: October’s observed breach and poor metrics will move substantially as labels mature, particularly for V3/Partner Z; expected under true performance change: high breach and poor within-stratum discrimination persist at complete maturity. If mature fixed-vintage results eliminate October’s anomaly but preserve Aug–Sep V3 degradation, censoring explains October while process/concept issues remain for Aug–Sep.

- **Recomputation after activity-label normalization and duplicate cleaning.** Rebuild April–May prefixes after mapping `Diagnostic Assessment Completed` to `Initial Diagnosis Completed`, deduplicate by event ID and case/time/activity adjacency, backfill cached pre-diagnosis features, and recompute all derived features. Expect under pipeline failure: April/May unknown share, missingness, calibration, and AUROC return toward baseline without a new model. Expect under genuine drift/concept change: residual April/May miscalibration or discrimination remains after clean recomputation.

- **Calibration and discrimination stratified by variant, source, and month.** Compute AUROC, Brier, ECE, calibration intercept/slope, and reliability curves by V1/V2/V3, Partner Z/non-Z, and month. Expect under process/mix/population shift: overall metrics degrade, but within-stratum performance is more stable or correctable by reweighting/intercept recalibration. Expect under concept drift: within-stratum calibration/discrimination degrades, especially for V3/Partner Z, with month-by-variant or month-by-source interactions. Expect under label delay: poor metrics concentrate in immature strata and improve at fixed vintages.

- **Comparison of process variants and DFG/performance-DFG edges.** Monitor variant frequencies and edge durations such as `Order Part -> Part Received`, `Initial Diagnosis Completed -> Remote Fix`, dispatch, repair, and closure. Expect under process drift: V3 share and order-part delay rise with V3 breach, while V1/V2 remain stable; June shows V2 mix shift with lower observed breach. Expect under pure concept drift: breach risk changes even for the same path and similar edge durations. Expect under pipeline failure: April shows spurious `UNKNOWN_ACTIVITY`, unmapped variants, duplicates, or distorted DFGs that disappear after normalization. If edge durations explain V3 breach in a conditional model and no month interaction remains, favor process drift over concept drift.

- **Tests of whether the outcome relationship conditional on the same path changed.** Fit or audit a model with month interactions on path/variant, order-part delay, queue, source, rural distance, device age, and other stable features. Compare `month × V3`, `month × PartnerZ`, and `month × order-part delay` effects. Expect under concept drift: interactions remain and same-path risk predictions are wrong even after adding process covariates. Expect under process/covariate/population shift: month effects become small or disappear after conditioning/reweighting. Expect under label censoring: effects change with maturity vintage and are strongest in incomplete cohorts.

- **Population reweighting or transport-style checks for Partner Z.** Reweight Partner Z to non-Z or baseline distributions of variant, geography, device age, queue, and process durations, or evaluate on common-support regions. Expect under population/covariate shift and missing features: the Partner Z disparity shrinks after reweighting or after adding rural/device features. Expect under concept drift or model unfairness: residual calibration/discrimination disparity remains within matched strata. Expect under label delay: disparity attenuates when using mature labels and maturity-adjusted outcomes.

- **Feature missingness and lineage audits.** Trace each feature back to source events and mapping version; audit duplicate rates, unknown activity share, missing queue, timestamp ordering, cached feature recomputation, and case-prefix construction. Expect under pipeline failure: errors correlate with April migration, duplicates, missing queue, and stale cached features, and clean rebuild fixes them. Expect under real drift: missingness is low after repair and performance issues persist with clean features. This test should precede and gate any retraining decision.

## 4. Recalibration-versus-retraining decision

**Immediate containment.** Freeze automatic retraining decisions. Version-lock the activity mapping and feature lineage. Separate “model performance” from “label maturity,” “pipeline health,” and “process/population change.” Treat October as uninterpretable for outcome metrics until the outcome API backlog is fixed and labels mature. Do not recalibrate April before pipeline repair; do not recalibrate around October censoring.

**Short-term recalibration.** Allow intercept/slope or variant/source-specific calibration only after data-quality gates are green and labels are sufficiently mature. June is a plausible recalibration case: labels are mature, the main change is V2 routing mix, and within-variant breach rates are broadly stable. A global or variant-stratified recalbration may correct June’s overprediction. August–September should not be handled by calibration alone until supplier/process and Partner Z features are added and label maturity is resolved, because calibration could mask a real V3 process shift or missing population covariates. April/May should be repaired and recomputed before any calibration.

**Feature repair.** Prioritize repairing the diagnosis label mapping, duplicate handling, cached pre-diagnosis features, queue features, and lineage. Add process/performance evidence features such as order-part waiting time, supplier/part status, dispatch delay, remote-fix eligibility, and variant path. Add population features for Partner Z: source/partner, rural distance, device age, and common-support indicators. Recompute features historically before training.

**Full retraining.** Full retraining is justified only after: clean feature lineage; mature fixed-vintage labels; stable conditional comparisons; and persistent within-stratum performance loss after recalibration/feature repair. Use Jan–Mar as clean baseline. April–May are unsafe until mapping/dedup/backfill/recompute is complete; afterward they may be usable for robustness but not as ordinary baseline. June–July are conditionally safe after lineage checks and maturity confirmation, but should include routing/supplier features. August is conditionally unsafe until labels are fully mature and supplier/process features are included. September is unsafe for training until Partner Z labels mature and population/process features are added. October is unsafe for training or evaluation except as a censored cohort for maturity analysis.

**Segment-specific model.** A global model plus segment-specific calibration is the safest first step. A separate V3 or Partner Z model is justified only if diagnostics show persistent month/source/variant interactions, poor calibration/discrimination within matched strata, and sufficient common support and mature labels. The likely best design is a hybrid: global model with variant/source/process features and interactions, plus variant-specific thresholds or calibration, with separate V3/Partner Z evaluation. Do not build a separate October model or a Partner Z model using immature labels.

## 5. Monitoring architecture

- **Predictive-performance monitor:** AUROC/PR-AUC, recall at operating threshold, Brier, log loss, and score distributions by month, variant, and source. Require minimum matured-label coverage before alarming.
- **Calibration monitor:** ECE, calibration intercept/slope, reliability curves, and expected-vs-observed breach by variant/source. Separate global and segment views.
- **Label-maturity monitor:** maturity curves, median delay, percentage unresolved, vintage backtests, and outcome-API backlog status. This monitor should be a first-class alarm, not a model-performance alarm.
- **Data-quality monitor:** unknown activity share, renamed-label mapping coverage, duplicate rate, missing queue, schema/version changes, feature freshness, and cache/backfill status.
- **Process-variant monitor:** V1/V2/V3 shares, unmapped variants, routing-policy versions, and path-frequency changes.
- **Performance-DFG monitor:** edge duration quantiles for `Order Part -> Part Received`, `Initial Diagnosis Completed -> Remote Fix`, dispatch, repair, close, plus supplier on-time performance.
- **Population monitor:** Partner/source share, rural distance, device age, queue distribution, covariate shift metrics, common support, and reweighted performance.
- **Intervention/deployment monitor:** model version, threshold changes, routing policies, supplier incidents, API outages, and feature-pipeline deployments.

Alert dependency logic: if a label-maturity or outcome-API alarm is active, performance/calibration drops are tagged as “censored/immature,” and automatic retraining is blocked until fixed-vintage mature results are available. If a data-quality or lineage alarm is active, retraining is blocked and feature repair is triggered. Process/population alarms trigger stratified investigation and possible recalibration/feature work, not automatic retraining. Full retraining is allowed only when mature-label performance deteriorates persistently, data-quality is green, and stratified conditional tests support a real model need.

```python
import pandas as pd
import pm4py

def monthly_process_evidence(csv_path):
    raw = pd.read_csv(csv_path)
    raw['timestamp'] = pd.to_datetime(raw['timestamp'], errors='coerce', utc=True)
    raw = raw.dropna(subset=['case_id', 'activity', 'timestamp']).copy()

    # Normalize renamed diagnosis labels BEFORE PM4Py formatting/feature extraction.
    raw['activity'] = raw['activity'].replace({
        'Diagnostic Assessment Completed': 'Initial Diagnosis Completed',
        'DIAGNOSTIC_ASSESSMENT_COMPLETED': 'Initial Diagnosis Completed'
    })

    # Duplicate strategy: exact event-id dedup where available, exact event dedup,
    # then adjacent same-activity events within 1 second in the same case.
    if 'event_id' in raw.columns:
        raw = raw.drop_duplicates(subset=['event_id'])
    raw = raw.sort_values(['case_id', 'timestamp', 'activity'])
    raw = raw.drop_duplicates(subset=['case_id', 'activity', 'timestamp'])
    prev = raw.groupby('case_id')[['timestamp', 'activity']].shift(1)
    adj_dup = (
        raw['activity'].eq(prev['activity']) &
        (raw['timestamp'] - prev['timestamp']).dt.total_seconds().abs().le(1)
    )
    raw = raw.loc[~adj_dup].copy()

    df = pm4py.format_dataframe(
        raw, case_id='case_id', activity_key='activity', timestamp_key='timestamp'
    )
    log = pm4py.convert_to_event_log(df)

    # Event-calendar cohort: events occurring in a month; process/DFG interpretation.
    # Case-start cohort: all events for cases whose first event starts in that month;
    # predictive/label interpretation.
    starts = df.groupby('case:concept:name')['time:timestamp'].min()
    df['_case_start_month'] = df['case:concept:name'].map(starts).dt.to_period('M').astype(str)

    rows = []
    months = sorted(df['time:timestamp'].dt.to_period('M').astype(str).unique())
    for m in months:
        t0 = pd.Timestamp(f'{m}-01', tz='UTC')
        t1 = t0 + pd.offsets.MonthBegin(1)

        event_log = pm4py.filter_time_range(log, t0, t1, mode='events')
        case_ids = df.loc[df['_case_start_month'] == m, 'case:concept:name'].dropna().unique().tolist()
        case_start_log = pm4py.filter_event_attribute_values(
            log, 'case:concept:name', case_ids, level='case'
        )

        for cohort_name, sublog in [('event_calendar', event_log), ('case_start', case_start_log)]:
            if len(sublog) == 0:
                continue

            dfg, start_act, end_act = pm4py.discover_dfg(sublog)
            perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(sublog)
            variants = pm4py.get_variants(sublog)
            temporal = pm4py.extract_temporal_features_dataframe(sublog)

            total_variants = sum(variants.values()) if variants else 1
            unknown_share = sum(
                v for k, v in variants.items()
                if any('UNKNOWN_ACTIVITY' in a for a in k)
            ) / total_variants

            rows.append({
                'month': m,
                'cohort': cohort_name,
                'n_cases': len(sublog),
                'n_events': sum(len(trace) for trace in sublog),
                'unknown_variant_share': unknown_share,
                'top_variants': sorted(variants.items(), key=lambda kv: kv[1], reverse=True)[:5],
                'top_dfg_edges': sorted(dfg.items(), key=lambda kv: kv[1], reverse=True)[:5],
                'order_part_to_received': perf_dfg.get(('Order Part', 'Part Received')),
                'diag_to_remote_fix': perf_dfg.get(('Initial Diagnosis Completed', 'Remote Fix')),
                'temporal_feature_columns': list(temporal.columns),
            })

    return pd.DataFrame(rows)
```

## 6. Risks of acting on the wrong diagnosis

1. **Retraining on immature labels.** Training on September/October before outcomes mature would teach the model from censored, selected cases, especially longer V3/Partner Z paths. Mitigation: require fixed-vintage maturity thresholds, censor-aware evaluation, and a hard training block while label-delay alarms are active.

2. **Calibrating around a pipeline bug.** Recalibrating April/May could absorb wrong prefixes, duplicate events, unknown activities, and stale cached features into calibration parameters. Mitigation: gate recalibration on data-quality and lineage health; normalize labels, deduplicate, backfill, and recompute before evaluating or recalibrating.

3. **Ignoring genuine supplier-driven process or concept change.** Treating Aug–Sep as only label delay or population shift could understate the V3/parts failure and leave high-risk parts-dependent cases underpredicted. Mitigation: monitor performance-DFG edges and supplier metrics, add order-part delay/supplier features, and test variant-specific conditional calibration; retain V3-specific alarms even when overall breach looks ambiguous.

4. **Overreacting to June’s routing change as concept drift.** June’s overall breach falls because V2 usage rises; retraining globally for “worse” performance could be unnecessary or harmful. Mitigation: stratify by variant and reweight to a fixed mix; use intercept/variant calibration if within-stratum relationships are stable; retrain only if within-variant conditional performance degrades.

5. **Misattributing Partner Z’s population shift to unfair model behavior, or vice versa.** Blaming the model without stratified evidence can miss missing rural/device covariates and common-support issues; ignoring genuine disparities can harm Partner Z. Mitigation: evaluate calibration/discrimination by source after maturity, reweight/transport over common support, add rural/device features, and require residual within-stratum disparity before concluding model unfairness or concept drift.

6. **Treating October’s observed breach as real improvement or deterioration.** October is heavily censored, and the API backlog affects longer paths. Mitigation: mark October uninterpretable for outcome comparison, use fixed-vintage backtests after backfill, and report censored-cohort metrics separately from mature-cohort metrics.
