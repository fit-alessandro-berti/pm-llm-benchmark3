## 2. Process-model consistency checks

A concrete validation suite should include the following checks.

- **Prefix-time availability.** For every feature, store `feature_as_of_ts` and the timestamps of all source events. Assert `feature_as_of_ts <= t0` and that every source event timestamp is  `t0`. Use point-in-time joins. Reject any feature whose extraction date or source event is after `t0`.

- **Activity-order feasibility.** Build a normative DFG/footprint from the process model. Check every observed trace against it. Flag impossible edges such as `Claim Closed -> Damage Assessment Completed`. Use alignment-based conformance to distinguish true deviations from noise. A frequent DFG edge is not automatically a normative rule; high frequency may reflect data-quality problems or non-normative variants.

- **Same-timestamp ambiguity.** When events share a timestamp, require a reliable sequence index. If the index is missing, mark the trace as ambiguous and exclude it from training/explanation or apply explicit tie-breaking rules. Test sensitivity by reordering tied events.

- **Complete-trace information detection.** For each feature, inspect the lineage graph to ensure it uses only prefix events. Recompute features with a prefix-only filter and compare with full-trace values; large differences indicate leakage.

- **Activity status at `t0`.** Classify each activity as observed, enabled, future-possible, or impossible at `t0`. At `t0` after `Coverage Check Completed`:
  - Observed: `Claim Registered`, `Coverage Check Completed`.
  - Future-possible: `Damage Assessment Completed`, `Documents Requested`, `Documents Received`, `Documents Validated`, `Fraud Investigation Opened`, `Settlement Decision Recorded`, `Claim Closed`.
  - Impossible at `t0`: `Appeal` (requires prior Partial/Deny), second `Settlement Decision Recorded` (requires appeal), `Claim Closed` before final decision.
  Explanations must not treat future-possible activities as observed.

- **Repeated Settlement Decision semantics.** Allow a second `Settlement Decision Recorded` only if it is preceded by an `Appeal` and the first decision was `Partial` or `Deny`. Otherwise flag the duplicate. Validate that `Appeal` occurs only after `Partial` or `Deny`. Use declarative rules for precedence, response, and existence constraints.

These checks have limitations: DFG frequency is not normative truth; alignment checks require a correct normative model; declarative rules may be incomplete; same-timestamp tie-breaking may not reflect true order.

## 5. Recommendations for explanation validation

Prioritized plan:

1. **Immediate leakage removal, P0.** Remove all critical leakage features from the `t0` model: `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, future sequence patterns, and the impossible `Claim Closed -> Damage Assessment Completed` pattern. Freeze current explanations; do not use them for decisions.

2. **Point-in-time feature-store design, P1.** Build a feature store with event-time joins, immutable snapshots, and explicit `feature_as_of_ts` and `source_event_ts` metadata. Store lineage so every feature can be traced to events  `t0`.

3. **Historical feature timestamps, P1.** Replace extraction-date joins with event-date joins. Repair mutable/late features: `final_handler_team`  `handler_team_at_t0`; `same_day_document_count_snapshot`  documents  `t0`; `prior_claim_count_before_t0`  `claim_created_at < t0`; `risk_score_current`  `risk_score_at_t0`; `last_resource_role`  `role_at_t0`; employee experience  `experience_at_t0`.

4. **Prefix-only recomputation, P1.** Recompute all features using only events  `t0`. Compare prefix-only values with full-trace values; large differences indicate leakage. Recompute all case explanations after repair.

5. **Process-conformance tests, P2.** Implement the validation suite from Section 2: prefix-time availability, activity-order feasibility, same-timestamp ambiguity, complete-trace detection, activity status at `t0`, and repeated Settlement Decision rules. Use DFG, alignment, footprint, and declarative checks; treat frequent DFG edges as data-quality signals, not normative rules.

6. **Calibration and retraining after feature removal, P2.** Recalibrate or retrain the model after removing leaked features. Assess performance drop, calibration, and whether remaining features still provide useful early signal.

7. **Explanation stability, P3.** Test SHAP-like and sequence explanations across folds, bootstrap samples, and perturbations. Decompose base-value aggregates into named feature contributions. Remove or flag unstable explanations.

8. **Proxy and fairness analysis, P3.** For `claimant_region`, `claimant_channel`, and repaired `prior_claim_count_before_t0`, run disparate-impact, bias, and robustness tests. Document proxy relationships and consider aggregation or removal if fairness risk is unacceptable.

9. **Monitoring for schema and process drift, P4.** Monitor feature distributions, event-order conformance, same-timestamp ambiguity rates, calendar/policy effects, and data-quality metrics. Alert on leakage patterns, impossible edges, and distribution shifts.
