```
def aalen_johansen_cif(time, cause, horizon=72):
    # time: float, cause: int 0 censored, >0 event code
    times = np.unique(time[(time <= horizon) & (cause>0)])
    # include horizon if no event? Need estimate at horizon.
    all_times = sorted(set(list(times)+[horizon]))
    S=1.0
    cif = {c:0.0 for c in np.unique(cause[cause>0])}
    for t in all_times:
        at_risk = (time >= t) # includes censored at t
        Y = at_risk.sum()
        if Y == 0: break
        for c in causes:
            d = ((time == t) & (cause == c)).sum()
            if d>0:
                cif[c] += S * d / Y
        # update S after events at t: S *= (1 - total_events/Y)
        d_all = ((time == t) & (cause > 0)).sum()
        if d_all>0:
            S *= (1 - d_all / Y)
        # remove those with time <= t? at_risk next uses time >= next t; if next >t, those with time==t not at risk. Good.
    return cif, S
```

```
def aj_cif_at_horizon(time, cause, horizon=H):
    time=np.asarray(time,float); cause=np.asarray(cause,int)
    causes = sorted(set(cause[cause>0]))
    cif = {c:0.0 for c in causes}
    S=1.0
    event_times = sorted(set(time[(cause>0) & (time <= horizon)]).union({horizon}))
    for t in event_times:
       risk = time >= t
       Y = risk.sum()
       if Y == 0: break
       d_all = ((time == t) & (cause > 0)).sum()
       for c in causes:
          d = ((time == t) & (cause == c)).sum()
          if d:
             cif[c] += S * d / Y
       if d_all:
          S *= (1 - d_all / Y)
    return cif, S
```

```
def aj_cif_at_horizon(time, cause, horizon=H):
    time = np.asarray(time, dtype=float)
    cause = np.asarray(cause, dtype=int)
    causes = sorted(set(cause[cause > 0]))
    cif = {c: 0.0 for c in causes}
    S = 1.0
    event_times = sorted(set(time[(cause > 0) & (time <= horizon)]).union({horizon}))
    for t in event_times:
        risk = time >= t
        Y = int(risk.sum())
        if Y == 0:
            break
        d_all = int(((time == t) & (cause > 0)).sum())
        for c in causes:
            d = int(((time == t) & (cause == c)).sum())
            if d > 0:
                cif[c] += S * d / Y
        if d_all > 0:
            S *= (1.0 - d_all / Y)
    return cif, S
```

```
def aj_cif_at_horizon(time, cause, horizon=H):
    time = np.asarray(time, dtype=float)
    cause = np.asarray(cause, dtype=int)
    causes = sorted(set(cause[cause > 0]))
    cif = {int(c): 0.0 for c in causes}
    S = 1.0
    event_times = sorted(set(time[(cause > 0) & (time <= horizon)]).union({horizon}))
    for t in event_times:
        risk = time >= t
        Y = int(risk.sum())
        if Y == 0:
            break
        at_t = np.isclose(time, t)
        d_all = int((at_t & (cause > 0)).sum())
        for c in causes:
            d = int((at_t & (cause == c)).sum())
            if d > 0:
                cif[c] += S * d / Y
        if d_all > 0:
            S *= (1.0 - d_all / Y)
    return cif, S
```

# 1. SLA estimands and time definitions

**Time origin.** The survival clock starts at `Submit`, defined as time 0 for every case. The supplied `duration_or_age_h` is the elapsed time from `Submit` to either:

- the observed internal terminal event for rows with `observed_status` in `{resolved, withdrawn, rejected, transferred}`; or
- the observation cutoff for rows with `observed_status = open`.

**Horizon.** The SLA horizon is ` = 72` hours.

**Observed process times and censoring.** For an open case, the time of its last observed event can be derived from the supplied fields as:

`last_event_time_h = duration_or_age_h - last_event_gap_h`.

For example, `S10` is open at age 47 with `last_event_gap_h = 19`, and its prefix ends in `Escalate`, so the last recorded event, `Escalate`, occurred at 28 hours. This is derived from supplied data, not invented. Exact timestamps for intermediate activities such as `Screen`, `Review`, or `Escalate` are generally not supplied, so many process features are interval-censored or only usable at landmarks/cutoff.

**Assumptions.** These are labeled assumptions needed to define estimands:

- **A1.** `priority` and `cohort` are fixed at `Submit`. This is plausible for case management, but not explicitly guaranteed by the prompt.
- **A2.** `Withdraw` and `Reject` preclude any future internal `Resolve`.
- **A3, primary transfer assumption.** `Transfer` ends internal observation. For internal SLA success, it is treated as an internal terminal competing event, not as resolution.
- **A4.** The extract is administratively censored at the cutoff. Open cases are not known to have failed or succeeded beyond their observed age unless their age is already above 72 hours.

Let:

- `T_R` = time of internal `Resolve`, if it occurs;
- `T_W` = time of `Withdraw`;
- `T_J` = time of `Reject`;
- `T_X` = time of `Transfer`;
- `T_any = min(T_R, T_W, T_J, T_X)` = time of first internal terminal disposition;
- `C` = cutoff age for open cases.

The following estimands are useful and not interchangeable.

**Estimand E1: probability of internal resolution by 72 hours.**

`CIF_R(72) = P(T_R  72)`.

This is the cumulative incidence of `Resolve` by 72 hours, treating `Withdraw`, `Reject`, and, under the primary assumption, `Transfer` as competing events. It matches the operational SLA success definition: a case is successful only if it reaches `Resolve` by 72 hours.

**Estimand E2: probability of not being internally resolved by 72 hours.**

`B(72) = P(no internal Resolve by 72)`.

Under E1 with all non-resolution terminal outcomes counted as non-success, `B(72) = 1 - CIF_R(72)`. A more explicit competing-risk encoding is a cause-specific event `NoResolve` at 72 hours for cases known not to have resolved by 72, with `Resolve` as a competing event before 72 and open cases below 72 right-censored. This matches SLA breach reporting, alerting, and customer-facing “late or unresolved” metrics.

**Estimand E3: probability of still having no internal terminal disposition at 72 hours.**

`N(72) = P(T_any > 72)`.

This is the cumulative incidence of “no internal terminal disposition” at 72 hours, or equivalently `1 - CIF_any_terminal(72)`. It matches backlog, aging, capacity, and operational-stall decisions. A case transferred at 96 hours, such as `S32`, contributes as “no internal terminal disposition at 72” because the internal transfer occurred after 72.

**Estimand E4: cumulative incidence of delayed internal resolution after 72 hours.**

`D(72) = P(T_R > 72 and T_R < )`.

This is the unconditional probability of eventual internal resolution after the SLA horizon. It is not directly observable without longer follow-up, because `` is not observed. A practical proxy is the cumulative incidence of `Resolve` over the observed follow-up window minus `CIF_R(72)`. This matches “late resolution” workload and remediation analysis. A conditional version, `P(T_R > 72 | T_R < )`, is tempting but requires modeling eventual resolution and is biased if estimated only from completed resolved cases.

**Estimand E5: cause-specific risk under competing outcomes.**

Cause-specific hazards such as:

`h_R(t) = lim_{dt0} P(t  T_R < t+dt | T_any  t)/dt`

are useful for understanding drivers of resolution, transfer, withdrawal, or rejection. They are not the same as absolute SLA risk. For SLA decisions, cumulative incidence functions are usually more interpretable.

# 2. Event and censoring encoding

The key distinction is:

- **Right censoring** means the case is still under observation and the event time is unknown beyond the observed time. Open cases below 72 hours are genuinely right-censored for a 72-hour horizon.
- **Competing events** are outcomes that prevent the event of interest from occurring, such as `Withdraw` or `Reject` preventing internal `Resolve`.
- **Already-observed breaches** are cases known not to have resolved by 72 hours because their observed age is already above 72, or because they had a non-resolution terminal event before 72. They should not be treated as ordinary unknown censoring for the no-resolve-by-72 estimand.

Cause-code conventions used below:

- E1, `Resolve by 72`: cause 1 = `Resolve`, cause 2 = `Withdraw`, cause 3 = `Reject`, cause 4 = `Transfer`, cause 0 = censored.
- E2, `No internal Resolve by 72`: cause 1 = `NoResolve`, cause 2 = `Resolve` competing, cause 0 = censored.
- E3, `No internal terminal by 72`: cause 1 = `NoTerminal`, cause 2 = `Terminal`, cause 0 = censored.

| Observed status | E1 encoding | E2 encoding | E3 encoding | Censoring/competing-risk rule | Sensitivity alternatives |
|---|---|---|---|---|---|
| `resolved`  72, e.g. `S01` | event cause 1 at duration | competing cause 2 at duration | competing terminal cause 2 at duration | success; not censored | none needed for primary SLA |
| `resolved` > 72, e.g. `S03` | censored at 72 with no event by 72 | failure cause 1 at 72 | failure cause 1 at 72 because terminal occurred after 72 | already observed non-success by horizon; censored for longer resolution time | delayed-resolution CIF; interval-censored resolution time |
| `withdrawn`  72, e.g. `S06` | competing cause 2 at duration | failure cause 1 at duration or 72 | competing terminal cause 2 at duration | not ordinary censoring if internal resolution is impossible after withdrawal | censor if estimand is “resolution if not withdrawn”; unrealistic for SLA |
| `withdrawn` > 72, none observed | censored at 72 | failure cause 1 at 72 | failure cause 1 at 72 | already no terminal by 72 | same as withdrawn  72 |
| `rejected`  72, e.g. `S05` | competing cause 3 at duration | failure cause 1 at duration or 72 | competing terminal cause 2 at duration | not ordinary censoring if internal resolution is impossible after rejection | censor if studying resolution among non-rejected cases |
| `rejected` > 72, none observed | censored at 72 | failure cause 1 at 72 | failure cause 1 at 72 | already no terminal by 72 | same as rejected  72 |
| `transferred`  72, e.g. `S08` | primary: competing cause 4 at duration | primary: failure cause 1 at duration or 72 | primary: competing terminal cause 2 at duration | transfer stops internal observation; not automatically non-informative censoring | see three transfer assumptions below |
| `transferred` > 72, e.g. `S32` | censored at 72 for `Resolve by 72`; transfer occurred after horizon | failure cause 1 at 72 for internal no-resolve | failure cause 1 at 72 because no internal terminal occurred by 72 | already no internal terminal by 72; external outcome unknown | see three transfer assumptions below |
| `open` < 72, e.g. `S15` | censored at age | censored at age | censored at age | genuine right censoring for the 72-hour horizon | worst-case breach, best-case success, informative-censoring adjustment |
| `open`  72, e.g. `S09` | censored at 72 with no event by 72 for E1 | failure cause 1 at 72 | failure cause 1 at 72 | already observed breach for no-resolve and no-terminal; censored for longer follow-up | informative censoring due long `last_event_gap_h` |

**Three plausible transfer treatments.**

1. **Transfer as internal terminal competing event.** This is the primary assumption for internal SLA. A transferred case has not internally resolved and internal observation stops. It contributes to `NoResolve` and, if before 72, to terminal disposition; if after 72, it contributes to `NoTerminal` at 72.

2. **Transfer as right-censoring at transfer time.** This treats the external outcome as unknown and assumes censoring is non-informative. This can be useful if the business question is “what would happen if transferred cases could still resolve externally?” But it is dangerous because all three transfers are high-priority escalated cases: `S08`, `S21`, and `S32` are all `P1`, and all have `Escalate` in the prefix. Censoring them may remove the highest-risk cases.

3. **Transfer as early success or as not terminal, depending on the SLA definition.** If the SLA is about reaching any disposition, early transfer before 72 may be treated as success for `NoResolve`, but still terminal for `NoTerminal`. If the SLA is strictly about internal `Resolve`, this assumption is not operationally valid. If transfer is treated as “not internal terminal,” then `S08` and `S21` would contribute as no internal terminal at 72, which may be appropriate only if the organization considers transfer an ongoing case rather than an internal disposition.

# 3. Why naive completed-case analysis is biased

A completed-case analysis that uses only resolved cases is biased for several distinct reasons.

**Survivor bias.** If we compute SLA breach only among resolved cases, we use the 13 resolved cases and count resolved after 72: `S03` at 76, `S13` at 110, `S20` at 74, and `S28` at 88. That gives a crude delayed-resolution rate of 4/13  31%. But the population SLA question is not “among cases that eventually resolved, how many were late?” It is “what fraction of submitted cases were not internally resolved by 72?” Many cases never internally resolve by the cutoff: open cases `S09`, `S11`, `S25`, and `S26` are already beyond 72 without resolution; withdrawn/rejected cases `S05`, `S06`, `S12`, `S14`, `S22`, `S23`, and `S30` are non-resolutions; transferred cases `S08`, `S21`, and `S32` are not internal resolutions. Ignoring them understates SLA failure.

**Informative censoring from transfers.** All transfers are `P1` and escalated: `S08`, `S21`, and `S32`. If transfers are censored as if they were random, the high-risk `P1` population is partially removed. This can make `P1` look better than it is. `S32` is especially important: it is `P1`, open until at least 96 hours, then transferred. For no-terminal-by-72, it is a known breach at 72; for resolution-by-72, it is known not internally resolved by 72; for external resolution, it is unknown. Treating it as ordinary censoring without sensitivity analysis hides a process failure.

**Informative censoring from long event gaps.** Open cases with large `last_event_gap_h` are likely stalled. Examples:

- `S26`: `P3`, open at 104 h, last event gap 72 h.
- `S11`: `P1`, open at 81 h, last event gap 55 h.
- `S25`: `P1`, open at 79 h, last event gap 48 h.
- `S09`: `P3`, open at 92 h, last event gap 31 h.
- `S10`: `P2`, open at 47 h, last event gap 19 h.

Censoring these at cutoff assumes their unobserved future resolution hazard is like cases that are not censored. That is implausible when the last event gap is large.

**Competing risks.** `Withdraw` and `Reject` are not censoring for internal resolution if they prevent future internal `Resolve`. For example, `S05`, `S14`, and `S23` are rejected; `S06`, `S12`, `S22`, and `S30` are withdrawn. If these are treated as censored, Kaplan-Meier resolution curves will be upward biased because cases that removed themselves from resolution risk are assumed to have the same future resolution probability as cases still under observation.

**Cohort imbalance and non-random rollout.** Cohort B has more `P1` cases than Cohort A: 5 versus 3. Cohort B also contains two of the three transfers, `S21` and `S32`, and a very long-gap open case, `S26`. Cohort B also has more `AutoCheck`-before-`Screen` paths, such as `S16`, `S19`, `S22`, `S27`, `S28`, `S31`, and `S32`, but not all B cases follow that path: `S20`, `S23`, `S26`, and `S30` do not contain `AutoCheck`. Because rollout was not randomized and compliance was incomplete, comparing cohorts on completed resolved cases confounds policy effect, priority mix, and selection.

**Open below versus above 72.** Open cases below 72, such as `S15` at 35 h with gap 2 and `S31` at 23 h with gap 3, are genuinely unknown at the 72-hour horizon. Open cases above 72, such as `S09` at 92 h and `S26` at 104 h, are already known not to have resolved by 72 and, if still open, are already known to have no internal terminal disposition by 72. A naive analysis that treats all open rows identically as censored at cutoff misclassifies already-observed breaches.

A concrete completed-case distortion: among known outcomes excluding open cases below 72, the primary no-resolve-by-72 rate is 18 failures out of 27 known cases, about 66.7%. Among resolved cases only, the late-resolution rate is 4 out of 13, about 30.8%. These answer different questions, and the second one omits many cases that were not successful by the SLA.

# 4. Statistical analysis plan

The primary analysis should be a competing-risks cumulative-incidence analysis, not a simple Kaplan-Meier analysis of resolved cases.

| Method | What it estimates | Fit for this problem | Main caveats |
|---|---|---|---|
| Kaplan-Meier for `Resolve` | Survival to `Resolve` treating all non-resolved terminal outcomes as censoring | Useful only as a flawed comparator | Biased upward when `Withdraw`, `Reject`, or `Transfer` preclude internal resolution |
| Kaplan-Meier for any internal terminal event | Probability of no internal terminal disposition by 72 | Reasonable for E3 if terminal events are correctly defined | Does not distinguish `Resolve`, `Withdraw`, `Reject`, `Transfer`; transfer treatment still matters |
| Aalen-Johansen cumulative incidence | Cause-specific CIF for `Resolve`, `Withdraw`, `Reject`, `Transfer`, or `NoTerminal` | Best primary method for SLA reporting at 72 hours | Small sample; estimates are sensitive to censoring assumptions |
| Cause-specific hazards | Hazard of one event while other events are treated as censoring | Useful for etiology and process drivers | Does not directly give absolute SLA risk; requires AJ or multi-state model to convert to CIF |
| Subdistribution hazards, Fine-Gray | Covariate effects on cumulative incidence of a cause | Useful for secondary modeling of SLA breach risk | Small sample, competing-risk modeling complexity, interpretation requires care |
| Restricted mean time to resolution or no terminal disposition | Average event-free time up to 72 or another horizon | Useful for backlog and capacity summaries | Less directly tied to a binary SLA threshold; still depends on censoring assumptions |
| Landmarking | Dynamic risk using covariates known by a landmark time | Essential for process-aware features such as `Escalate`, `Review`, `Rework`, and stage | Requires exact or bounded event times; data here are sparse |
| Multi-state model | Transitions among `Submit`, `Screen`, `AutoCheck`, `Review`, `Escalate`, `Rework`, and terminal states | Conceptually best for process-aware SLA risk | Too data-rich for only 32 cases; many transitions have very few observations |

**Recommended primary approach.** Use nonparametric Aalen-Johansen cumulative incidence functions for:

1. `CIF_Resolve(72)` under primary transfer-as-competing-event;
2. `CIF_NoResolve(72)`, equivalent to SLA breach for internal resolution;
3. `CIF_NoTerminal(72)`, for backlog and stalled cases.

This is the best primary choice because the operational question is absolute risk by a fixed horizon, and the data contain competing terminal outcomes. It also retains open cases by censoring them at their observed age.

**Recommended secondary approach.** Use landmarked cause-specific or subdistribution models for process-aware risk factors. For example, at landmarks 24 h and 48 h, define time-varying covariates:

- current stage at landmark;
- number of `Review` events by landmark;
- whether `Escalate` occurred by landmark;
- whether `Rework` occurred by landmark;
- time since last event at landmark;
- whether `AutoCheck` occurred by landmark.

Because exact intermediate event times are missing, these should be implemented with interval-censored or conservative landmark rules, not by assuming the full prefix occurred by time 0.

**Tertiary/research approach.** A multi-state model would be ideal if more data were available. With 32 cases, it should be used descriptively or for simulation, not for strong inference.

**Uncertainty.** Given the small sample, point estimates should be accompanied by bootstrap confidence intervals or exact binomial intervals for binary horizon estimates. The code below implements point estimates and sensitivity comparisons; extending it to bootstrap is straightforward.

# 6. Sensitivity analysis

At least four sensitivity dimensions matter: transfer treatment, withdrawal/rejection treatment, open-case censoring, and cohort/priority confounding.

**Sensitivity 1: transfer as internal terminal competing event.** This is the primary assumption. Transferred cases are not internally resolved and are internal terminal outcomes. Under this assumption, all three transfers contribute to no-resolve-by-72. `S08` and `S21` also contribute to terminal disposition before 72; `S32` contributes to no-terminal-at-72 because it transferred after 72.

**Sensitivity 2: transfer as right-censoring.** If `S08`, `S21`, and `S32` are censored, the estimated probability of internal resolution by 72 increases, and the estimated no-resolve probability decreases. This can reverse qualitative conclusions about `P1`. Under the primary known-case view, `P1` has 5 failures out of 7 known cases, about 71%. If transfers are censored, the known `P1` set becomes `S04`, `S18`, `S11`, `S25`, and possibly `S29` depending on open handling; the `P1` risk estimate becomes much more uncertain and may appear lower. Because all transfers are `P1`, this assumption is not neutral.

**Sensitivity 3: withdrawal and rejection as competing events versus censoring.** Treating `Withdraw` and `Reject` as censoring raises the estimated resolution probability. This is especially important for `P3`, where rejections are common: `S05`, `S14`, and `S23`. If rejections are censored, `P3` may look more likely to resolve than it is under the SLA definition. Conversely, if withdrawals are treated as competing events, `P2` and `P3` risk profiles change because withdrawals remove cases from future resolution risk.

**Sensitivity 4: open cases below 72.** Open cases below 72 are genuinely unknown. Bounds are useful:

- Known-case primary no-resolve rate: 18 failures / 27 known cases  66.7%.
- Worst-case bound if all five open cases below 72 eventually breach: 23 / 32  71.9%.
- Best-case bound if all five open cases below 72 would resolve by 72: 18 / 32  56.3%.

These bounds are not survival estimates, but they show that the qualitative conclusion “SLA breach risk is high” is robust: even the best-case bound is above 50%.

**Sensitivity 5: cohort-policy effects.** Cohort B differs from Cohort A in priority mix, transfer frequency, and path pattern. A completed-case comparison of resolved durations is confounded. If transfer is treated as success, Cohort B may look better because `S21` becomes success while `S32` remains after-horizon. If transfer is treated as censoring, Cohort B’s high-risk `P1` transfers are removed. If `AutoCheck` exposure is modeled as a time-varying process feature rather than a cohort baseline, apparent cohort effects may shrink because `AutoCheck` is only partially compliant and occurs after start.

**Conclusions that could reverse.**

- “`P1` has the highest breach risk” could reverse if transfers are censored, because all transfers are `P1`.
- “Cohort B is worse” could reverse if early transfers are treated as successes or if open cases below 72 are optimistically imputed.
- “`P3` has the worst resolution risk” could attenuate if rejections and withdrawals are treated as censoring.
- “`AutoCheck` improves SLA performance” could be misleading if `AutoCheck` is used as a baseline covariate; it is a post-start process event and may be correlated with priority, cohort, and escalation policy.

# 7. Operational interpretation

Survival outputs should be translated into decisions by estimand, not by a single “risk score.”

**SLA compliance dashboard.** Use `CIF_Resolve(72)` as the primary success metric and `CIF_NoResolve(72)` as the primary breach metric. Report confidence intervals and state the transfer assumption. If transfer is not internal resolution, do not hide transfers as censored cases.

**Backlog and capacity alerts.** Use `CIF_NoTerminal(72)` and restricted mean open time. Cases like `S26`, `S11`, and `S25` are operationally important because they are open beyond 72 with large last-event gaps. Alerts should be based on features known at alert time, such as current stage, time since last event, and escalation status by the alert time.

**Workload triage.** For a 48-hour landmark, cases that are still in `Review` or `Escalate` with high predicted no-resolve-by-72 probability should receive attention. For example, `S10` is escalated by 28 hours and still open at 47 hours; `S25` is escalated by 31 hours and open at 79 hours; `S26` has been inactive for 72 hours at cutoff. These are process-aware signals, but they are not causal statements that escalation or inactivity caused the breach.

**Transfer governance.** Because transfer outcomes are externally unknown, create a feedback loop: request external resolution status for `S08`, `S21`, and `S32`-like cases. Until then, report transfer under at least two views: internal SLA view and external-uncertainty view.

**Policy evaluation.** Cohort B cannot be interpreted causally from this extract. Assignment was not randomized, rollout compliance was incomplete, and priority mix differs. Use survival estimates as descriptive monitoring, not as proof that the automated-screening or escalation policy changed outcomes.

**Calibration.** If a risk model is built, check calibration at 72 hours by priority and cohort:

- predicted vs observed `CIF_Resolve(72)`;
- predicted vs observed `CIF_NoTerminal(72)`;
- Brier score or calibration slope/intercept;
- group-specific observed known-case rates and bounds.

With only 32 cases, calibration checks are fragile and should be reported as monitoring diagnostics, not validated model performance.

**Fairness.** Check whether risk scores or alerts differ by priority and cohort. `P1` should not be penalized or favored because of transfer coding. Cohort B should not be flagged as higher risk solely because it contains more `P1` cases or more transfers. If fairness is a concern, report both risk estimates and outcome definitions: a model that treats transfer as success may systematically advantage cohorts or priorities with more transfers.

**Do not present risk scores as causal effects.** A high predicted breach probability means “this case resembles cases that did not resolve by 72,” not “escalation caused delay” or “AutoCheck caused success.” Causal conclusions require a better identification design, such as randomized rollout, regression discontinuity around policy dates, or detailed assignment mechanisms.

```python
# 2. Aalen-Johansen cumulative-incidence helper.
# No external survival library is assumed. If lifelines or scikit-survival were
# available, this helper could be replaced by AalenJohansenFitter or similar.
# The fallback is the manual implementation below.
# -----------------------------------------------------------------------------
def aj_cif_at_horizon(time, cause, horizon=H):
    """
    time: observed time, capped or encoded relative to horizon.
    cause: 0 = censored; >0 = event cause code.
    Returns dict cause -> CIF at horizon and overall survival at horizon.
    """
    time = np.asarray(time, dtype=float)
    cause = np.asarray(cause, dtype=int)

    causes = sorted(set(cause[cause > 0]))
    cif = {int(c): 0.0 for c in causes}
    S = 1.0

    # Include horizon so we can evaluate at 72 even if no event occurs at 72.
    event_times = sorted(set(time[(cause > 0) & (time <= horizon)]).union({horizon}))

    for t in event_times:
        risk = time >= t
        Y = int(risk.sum())
        if Y == 0:
            break

        at_t = np.isclose(time, t)
        d_all = int((at_t & (cause > 0)).sum())

        for c in causes:
            d = int((at_t & (cause == c)).sum())
            if d > 0:
                cif[c] += S * d / Y

        if d_all > 0:
            S *= (1.0 - d_all / Y)

    return cif, S

def encode_cif_resolve(df_in, transfer_scenario="transfer_event", wr_scenario="event"):
    rows = []

    for r in df_in.itertuples(index=False):
        status = r.observed_status
        dur = float(r.duration_or_age_h)

        if status == "resolved":
            if dur <= H:
                rows.append((dur, 1))       # Resolve event by horizon
            else:
                rows.append((H, 0))         # Known no Resolve by 72; censored at horizon

        elif status == "withdrawn":
            if wr_scenario == "censor":
                rows.append((min(dur, H), 0))
            else:
                rows.append((min(dur, H), 2))

        elif status == "rejected":
            if wr_scenario == "censor":
                rows.append((min(dur, H), 0))
            else:
                rows.append((min(dur, H), 3))

        elif status == "transferred":
            if transfer_scenario == "transfer_event":
                if dur <= H:
                    rows.append((dur, 4))   # Transfer competing event before horizon
                else:
                    rows.append((H, 0))     # Transfer after horizon; no event by 72

            elif transfer_scenario == "transfer_censor":
                rows.append((min(dur, H), 0))

            elif transfer_scenario == "transfer_success_early":
                if dur <= H:
                    rows.append((dur, 1))   # Sensitivity: transfer treated as resolution
                else:
                    rows.append((H, 0))

            else:
                rows.append((min(dur, H), 4))

        elif status == "open":
            if dur >= H:
                rows.append((H, 0))         # Known no Resolve by 72; censored at horizon
            else:
                rows.append((dur, 0))       # Genuine right censoring before horizon

        else:
            rows.append((min(dur, H), 0))

    return pd.DataFrame(rows, columns=["time", "cause"])
```

# 9. Limitations and additional data

The strongest limitation is sample size: 32 cases are enough to define estimands and illustrate sensitivity, but not enough for stable multi-state or multivariable survival models. All estimates should be treated as descriptive and uncertainty-aware.

**Highest-priority missing data.**

1. **Exact event timestamps for every activity.** Without them, time-varying features such as `Escalate`, `Review`, `AutoCheck`, and `Rework` are interval-censored or only known at cutoff. This prevents clean landmarking, immortal-time avoidance, and stage-specific hazard estimation.

2. **External outcomes after transfer.** `S08`, `S21`, and `S32` are unobserved after transfer. We need external resolution time, external disposition, and whether transfer should count as SLA success. Without this, transfer must be handled through sensitivity analysis, not a single assumption.

3. **Cutoff and submission dates.** Cohort B began after a policy change, but exact rollout dates and case submission dates are not supplied. Without dates, we cannot separate calendar effects, workload seasonality, and policy effects.

4. **Assignment mechanism and policy compliance.** Cohort assignment was not randomized, and rollout compliance was incomplete. We need the assignment rule, actual policy exposure, and whether `AutoCheck` was attempted, skipped, or failed.

5. **Time-varying workload and queue states.** Cases with long gaps, such as `S26`, `S11`, and `S25`, may be stalled due to staffing, backlog, or external dependencies. Without workload data, inactivity gaps cannot be interpreted causally.

6. **Reason codes for withdrawal, rejection, escalation, and transfer.** `Withdraw` and `Reject` may be customer-driven, policy-driven, or quality-driven. Their competing-risk meaning depends on why they occur.

7. **Priority changes over time.** If `priority` can change after `Submit`, treating it as baseline is invalid. We need priority history.

8. **SLA definition details.** Is the 72-hour clock paused for customer response, external transfer, rework, or holidays? The current analysis assumes a continuous elapsed-time clock from `Submit` to internal terminal event.

**Additional analyses needed for stronger inference.**

- Bootstrap or exact confidence intervals for Aalen-Johansen CIFs.
- Interval-censored survival models if intermediate event times are bounded.
- Multi-state hidden Markov or continuous-time Markov models if event timestamps are supplied.
- Causal sensitivity analysis for cohort policy change, using rollout timing, compliance, and assignment mechanism.
- External outcome follow-up for transferred cases.
- Fairness monitoring by priority, cohort, and process path, with explicit outcome definitions.
