# 1. Assumptions and Interpretation

1. **Low-Risk vs. High-Risk Choice Representation**: Per Narrative Rule 11, data attributes (such as risk levels) are not recorded as event labels. Instead, the risk classification is represented as an exclusive control-flow choice (`Operator.XOR`) enabled immediately after `Analyze Root Cause`. The low-risk alternative activates a single activity: `Supervisor Review`. The high-risk alternative activates a concurrent sub-process containing both `Quality Review` and `Regulatory Review`, which may execute in parallel and complete in either order.
2. **Optional Supplier Consultation Representation**: Per Narrative Rule 6, `Consult Supplier` is an optional activity that occurs at most once per case and can only start after `Analyze Root Cause`. In both formalisms, this optionality is modeled as an exclusive choice (`Operator.XOR`) between `Consult Supplier` and a silent step ($\tau$ / `SilentTransition` / unlabelled node). If selected, `Consult Supplier` executes visibly; if unselected, the silent bypass fires without producing an event log entry.
3. **Abstraction of Trial Inspection Outcomes**: Inspection results ("pass" or "fail") are not explicit event labels. Per Narrative Rule 8, a trial cycle consists of `Execute Trial` followed by `Inspect Trial`. A failed inspection leads to `Adjust Parameters` followed by another trial cycle. A passing inspection directly concludes the trial cycle without performing `Adjust Parameters`. This repeat-until logic is abstracted using a loop construct (`Operator.LOOP`), where the body (do-child) is the sequence `Execute Trial` $\rightarrow$ `Inspect Trial` and the redo-child is `Adjust Parameters`. The final `Inspect Trial` in any trace is therefore implicitly the passing inspection, and `Adjust Parameters` can never follow a passing inspection.
4. **Duplicate Visible Labels Policy**: Duplicate visible activity labels are strictly forbidden in our canonical models. Introducing duplicate labels in block-structured trees to approximate interleavings creates severe non-determinism during alignment computation and token replay, leads to NP-hard conformance checking, obscures true business bottlenecks, and impairs automated process discovery. Every visible activity appears exactly once.
5. **Process-Tree Approximation Policy**: Because the narrative specifies non-block-structured dependencies—where `Execute Trial` synchronizes `Plan Verification` (from containment) and `Design Corrective Action` (from root cause), while `Approval Route` and `Consult Supplier` branch from root cause but only synchronize at `Release Material`—an exact process tree without duplicate labels is topologically impossible. We adopt an explicit **conservative under-approximation policy**. All preparation, planning, design, approval, and supplier consultation activities are grouped into a parallel block preceding the trial loop. This strictly enforces all safety, planning, and authorization prerequisites before trial execution, but over-constrains the process by precluding the intended operational concurrency between approvals/consultations and trial cycles.
6. **Interpretation of "May Overlap"**: "May overlap" is interpreted as **true concurrency** (the absence of causal ordering constraints). Concurrent activities may execute in parallel in physical time (with non-zero duration) or interleave in arbitrary relative order in completion-time event logs, provided their respective upstream causal prerequisites have been satisfied.

# 3. PM4Py Process-Tree Model

### 1. Compact Process-Tree Expression

```text
->( 'Register Deviation', +( ->( 'Contain Material', 'Plan Verification' ), ->( 'Analyze Root Cause', +( 'Design Corrective Action', X( 'Supervisor Review', +( 'Quality Review', 'Regulatory Review' ) ), X( 'Consult Supplier', tau ) ) ) ), *( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' ), 'Release Material', 'Archive Case' )
```

### 2. Self-Contained Python Code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Root node: Sequential execution across the lifecycle stages
tree = ProcessTree(operator=Operator.SEQUENCE)

# Stage 1: Case Registration
c_reg = ProcessTree(label="Register Deviation", parent=tree)

# Stage 2: Investigation, Planning, Approvals, and Consultation (Under-Approximation Block)
c_prep = ProcessTree(operator=Operator.PARALLEL, parent=tree)

# Stream 2.1: Material Containment and Verification Planning
c_cont_stream = ProcessTree(operator=Operator.SEQUENCE, parent=c_prep)
c_cont = ProcessTree(label="Contain Material", parent=c_cont_stream)
c_plan = ProcessTree(label="Plan Verification", parent=c_cont_stream)
c_cont_stream.children.extend([c_cont, c_plan])

# Stream 2.2: Root Cause Analysis, Corrective Action Design, Governance, and Supplier Consultation
c_rc_stream = ProcessTree(operator=Operator.SEQUENCE, parent=c_prep)
c_rc = ProcessTree(label="Analyze Root Cause", parent=c_rc_stream)

c_rc_par = ProcessTree(operator=Operator.PARALLEL, parent=c_rc_stream)
c_des = ProcessTree(label="Design Corrective Action", parent=c_rc_par)

# Approval Route: Low-Risk (Supervisor) vs High-Risk (Quality || Regulatory)
c_app_xor = ProcessTree(operator=Operator.XOR, parent=c_rc_par)
c_app_low = ProcessTree(label="Supervisor Review", parent=c_app_xor)
c_app_high = ProcessTree(operator=Operator.PARALLEL, parent=c_app_xor)
c_qual = ProcessTree(label="Quality Review", parent=c_app_high)
c_regu = ProcessTree(label="Regulatory Review", parent=c_app_high)
c_app_high.children.extend([c_qual, c_regu])
c_app_xor.children.extend([c_app_low, c_app_high])

# Optional Supplier Consultation: Consult Supplier vs. Silent Step (tau)
c_sup_xor = ProcessTree(operator=Operator.XOR, parent=c_rc_par)
c_sup_act = ProcessTree(label="Consult Supplier", parent=c_sup_xor)
c_sup_skip = ProcessTree(label=None, parent=c_sup_xor)
c_sup_xor.children.extend([c_sup_act, c_sup_skip])

c_rc_par.children.extend([c_des, c_app_xor, c_sup_xor])
c_rc_stream.children.extend([c_rc, c_rc_par])

c_prep.children.extend([c_cont_stream, c_rc_stream])

# Stage 3: Trial Execution and Parameter Adjustment Loop
c_trial_loop = ProcessTree(operator=Operator.LOOP, parent=tree)
c_trial_do = ProcessTree(operator=Operator.SEQUENCE, parent=c_trial_loop)
c_exec = ProcessTree(label="Execute Trial", parent=c_trial_do)
c_insp = ProcessTree(label="Inspect Trial", parent=c_trial_do)
c_trial_do.children.extend([c_exec, c_insp])

c_adj = ProcessTree(label="Adjust Parameters", parent=c_trial_loop)
c_trial_loop.children.extend([c_trial_do, c_adj])

# Stage 4: Material Release
c_rel = ProcessTree(label="Release Material", parent=tree)

# Stage 5: Case Closure
c_arch = ProcessTree(label="Archive Case", parent=tree)

# Connect all stages to the root sequence
tree.children.extend([c_reg, c_prep, c_trial_loop, c_rel, c_arch])
```

### 3. Representational Loss and Approximation Analysis

The process-tree formalism enforces strict Single-Entry-Single-Exit (SESE) block modularity. In this manufacturing deviation process, the dependency structure forms an overlapping, non-block-structured network: `Execute Trial` depends on an intermediate milestone joining `Plan Verification` (from the containment stream) and `Design Corrective Action` (from the root-cause stream), whereas `Approval Route` and `Consult Supplier` branch from `Analyze Root Cause` but only join at `Release Material`. In our conservative under-approximation tree, the entire preparation phase (`c_prep`) is synchronized before entering `Trial Loop` (`c_trial_loop`). Consequently, the process tree cannot represent the intended concurrency between approvals/supplier consultation and the trial cycle: it artificially forces `Supervisor Review`, `Quality Review`, `Regulatory Review`, and `Consult Supplier` to finish completely before `Execute Trial` can begin. Traces exhibiting the legitimate business practice of running trials while administrative approvals or supplier discussions are pending are strictly excluded by the tree.

# 4. PM4Py POWL Model

### 1. Compact POWL Description

```text
PO=(
  nodes={
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    X( 'Supervisor Review', PO=(nodes={Quality Review, Regulatory Review}, order={}) ),
    X( 'Consult Supplier', tau ),
    *( PO=(nodes={Execute Trial, Inspect Trial}, order={Execute Trial-->Inspect Trial}), 'Adjust Parameters' ),
    Release Material,
    Archive Case
  },
  order={
    Register Deviation --> Contain Material,
    Register Deviation --> Analyze Root Cause,
    Contain Material --> Plan Verification,
    Analyze Root Cause --> Design Corrective Action,
    Analyze Root Cause --> X( 'Supervisor Review', PO=(nodes={Quality Review, Regulatory Review}, order={}) ),
    Analyze Root Cause --> X( 'Consult Supplier', tau ),
    Plan Verification --> *( PO=(nodes={Execute Trial, Inspect Trial}, order={Execute Trial-->Inspect Trial}), 'Adjust Parameters' ),
    Design Corrective Action --> *( PO=(nodes={Execute Trial, Inspect Trial}, order={Execute Trial-->Inspect Trial}), 'Adjust Parameters' ),
    *( PO=(nodes={Execute Trial, Inspect Trial}, order={Execute Trial-->Inspect Trial}), 'Adjust Parameters' ) --> Release Material,
    X( 'Supervisor Review', PO=(nodes={Quality Review, Regulatory Review}, order={}) ) --> Release Material,
    X( 'Consult Supplier', tau ) --> Release Material,
    Release Material --> Archive Case
  }
)
```

### 2. Self-Contained Python Code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
    Operator,
)

# Atomic visible activities
t_reg = Transition(label="Register Deviation")
t_cont = Transition(label="Contain Material")
t_root = Transition(label="Analyze Root Cause")
t_plan = Transition(label="Plan Verification")
t_des = Transition(label="Design Corrective Action")
t_rel = Transition(label="Release Material")
t_arch = Transition(label="Archive Case")

# Approval Submodel: XOR between Low-Risk (Supervisor) and High-Risk (Quality || Regulatory)
t_sup = Transition(label="Supervisor Review")
t_qual = Transition(label="Quality Review")
t_regu = Transition(label="Regulatory Review")
high_risk = StrictPartialOrder(nodes=[t_qual, t_regu])  # Unconnected nodes = true concurrency
approval = OperatorPOWL(operator=Operator.XOR, children=[t_sup, high_risk])

# Optional Supplier Consultation Submodel: Consult Supplier XOR SilentTransition
t_supp = Transition(label="Consult Supplier")
tau_supp = SilentTransition()
opt_supp = OperatorPOWL(operator=Operator.XOR, children=[t_supp, tau_supp])

# Trial Loop Submodel: LOOP(do: Execute -> Inspect, redo: Adjust Parameters)
t_exec = Transition(label="Execute Trial")
t_insp = Transition(label="Inspect Trial")
trial_seq = StrictPartialOrder(nodes=[t_exec, t_insp])
trial_seq.order.add_edge(t_exec, t_insp)

t_adj = Transition(label="Adjust Parameters")
trial_loop = OperatorPOWL(operator=Operator.LOOP, children=[trial_seq, t_adj])

# Root Partial Order containing top-level nodes
powl_nodes = [
    t_reg, t_cont, t_root, t_plan, t_des,
    approval, opt_supp, trial_loop,
    t_rel, t_arch
]
powl = StrictPartialOrder(nodes=powl_nodes)

# Enforce upstream causal dependencies
powl.order.add_edge(t_reg, t_cont)          # Registration precedes containment
powl.order.add_edge(t_reg, t_root)          # Registration precedes root-cause analysis
powl.order.add_edge(t_cont, t_plan)         # Containment precedes verification planning
powl.order.add_edge(t_root, t_des)          # Root cause precedes corrective-action design
powl.order.add_edge(t_root, approval)       # Root cause precedes risk approval path
powl.order.add_edge(t_root, opt_supp)       # Root cause precedes optional supplier consult

# Cross-branch synchronization gating trial execution
powl.order.add_edge(t_plan, trial_loop)     # Verification plan required before trial
powl.order.add_edge(t_des, trial_loop)      # Corrective design required before trial

# Multi-stream synchronization gating material release
powl.order.add_edge(trial_loop, t_rel)      # Passing trial inspection required before release
powl.order.add_edge(approval, t_rel)        # Approval completion required before release
powl.order.add_edge(opt_supp, t_rel)        # Supplier consult completion (or skip) before release

# Case closure
powl.order.add_edge(t_rel, t_arch)          # Release precedes archiving
```

### 3. Rationale for Concurrently Unconnected Nodes

In the POWL model, any two nodes without a directed path between them are concurrent:
1. `Contain Material` and `{Analyze Root Cause, Design Corrective Action, approval, opt_supp}`: Physical lot segregation and warehouse quarantine proceed independently of engineering root-cause investigations, governance assessments, and supplier outreach (Rule 2).
2. `Plan Verification` and `{Analyze Root Cause, Design Corrective Action, approval, opt_supp}`: Test protocol formulation depends solely on material containment (Rule 3) and can proceed in parallel with defect root-cause analysis, corrective action design, and approval workflows.
3. `approval` and `trial_loop`: Rule 7 explicitly states that the selected approval route does not have to be complete before the trial starts and may overlap the trial cycle. Hence, there is intentionally no ordering edge between `approval` and `trial_loop`.
4. `opt_supp` and `{Design Corrective Action, Plan Verification, approval, trial_loop}`: Rule 6 explicitly states that supplier consultation may overlap corrective-action design, verification planning, approvals, and trial work. Hence, `opt_supp` has no directed edges to or from these nodes.
5. `Quality Review` and `Regulatory Review` (within `high_risk`): Rule 5 explicitly states that high-risk reviews may occur concurrently and in either completion order.

# 7. Preferred Representation and Validation Plan

### Preferred Representation

The **POWL (Partially Ordered Workflow Language)** model is selected as the canonical representation.

**Defense**:
1. **Structural and Semantic Fidelity**: The manufacturing process contains a classic milestone synchronization pattern (Join 1: Plan + Design $\rightarrow$ Trial; Join 2: Trial + Approval + Supplier $\rightarrow$ Release) that is inherently non-well-nested. POWL represents partial orders natively as directed acyclic graphs over structured operators, capturing this milestone synchronization exactly.
2. **Zero Representational Loss**: Unlike the Process Tree—which must choose between conservative over-constraint (delaying trials until approvals finish) or permissive over-approximation (admitting illegal execution orders)—POWL achieves 100% precision and 100% recall against the business narrative.
3. **Traceability and Conformance Precision**: By avoiding label duplication, POWL maintains an injective 1-to-1 mapping between business events and model transitions, ensuring deterministic replay and optimal alignment computation during conformance checking.

### Limitations of the Validation Plan

1. **State Space Truncation of Unbounded Loops**: The `*(trial_do, Adjust Parameters)` construct allows an unbounded number of trial retries. Sampled playout and state-space traversals only explore finite depths (typically $\le 3$ loop iterations), meaning potential concurrency anomalies at extreme loop depths are not formally proven by sampling alone (requiring structural place-invariant inductive proofs).
2. **Instantaneous Completion Abstraction**: Event-log replay abstracts real-world duration into discrete points in time. While interleaving semantics prove the independence of tasks, they do not validate physical resource contention (e.g. machine availability during overlapping trials and parameter adjustments).
3. **Data-Agnostic Control Flow**: The validation plan evaluates purely control-flow traces. It does not evaluate data guards (such as verifying that a deviation classified as high-risk in SAP/ERP actually traversed the Quality/Regulatory path, or that parameter adjustments remained within calibrated engineering tolerances).

# 8. Final Self-Critique

1. **Semantic Loss of Data-to-Control Dependencies**: The workflow narrative states that the risk route depends on risk evaluation, supplier consultation depends on case data, and trial repeat depends on inspection failure. In our control-flow models, these decisions are modeled as non-deterministic choices (`Operator.XOR` and `Operator.LOOP`). Consequently, the model cannot prevent semantic inconsistencies where a severe high-risk defect takes the low-risk supervisor path, or where a trial is needlessly repeated despite an inspection passing in the physical lot data. A fully faithful implementation requires data-aware extensions (such as Data-Aware Petri Nets or DMN decision tables).
2. **Lack of Mid-Loop Cancellation and Long-Running Scope**: In physical production, if `Inspect Trial` fails repeatedly or if `Consult Supplier` reveals that the material defect is fundamentally uncorrectable, the deviation case is typically scrapped or cancelled. In our POWL model, `Release Material` and `Archive Case` are mandatory terminal sinks: every initiated branch (including the supplier consultation and approval route) must terminate successfully, and the trial loop can only exit via a passing inspection. The model lacks an exceptional abort/scrap boundary.
3. **Petri Net State Explosion during Alignment Computation**: While POWL expresses partial-order milestones cleanly, converting nested POWL models with partial orders and silent bypasses into accepting Petri nets introduces multiple silent transitions ($\tau$) and internal control places. During conformance checking on noisy event logs, these silent transitions can substantially increase the state space for $A^*$ alignment heuristics, resulting in higher memory overhead during conformance analysis compared to flat workflow nets.
