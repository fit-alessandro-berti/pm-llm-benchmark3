## 1. Decision rule  
Deployable, stage- and evidence-aware rule (no reliance on raw `p_now` alone). Used at alert generation and for slot evaluation.

- **Eligibility by stage**: Only cases at **Triage** or **Diagnosis Started** (before `Diagnosis Complete`) are eligible for swarm intervention. Cases at `Diagnosis Complete` (e.g., I-03) are automatically ineligible.  
- **Alert persistence & repeated alerts**:  
  - First alert: always eligible for swarm consideration (subject to tier scoring below).  
  - 2nd alert: a swarm request is **suppressed** unless a **materially new event** has occurred since the last alert. A materially new event = observable change in case data since last alert (e.g., new diagnostic log upload, symptom update reported by customer or agent; *not* subjective reprioritization).  
  - Example: I-05 (third alert, "no new event since previous alert")  suppressed; I-07 (third alert, "new customer log uploaded")  eligible if still at Triage/Diagnosis Started. No automatic retry after suppression; re-evaluation occurs only when a new event is reported or stage changes (but stage change to `Diagnosis Complete` makes ineligible).  
  - "No new event" is determined by checking `Data-quality note` and alert history; if unclear (e.g., imputed data like I-06), default to *suppressed* until explicit new event is logged.  
- **Tier scoring (deployable verbal logic, no hidden math)**:  
  1. **Tier 1 (highest priority for slot use)**: Cases at Triage/Diagnosis Started with **TO SLA  4 hours** *and* (first alert **or** new event since last alert).  
  2. **Tier 2 (medium priority; slot used only if Tier 1 fills)**: Cases at Triage/Diagnosis Started with TO SLA 4–8 hours and (first alert **or** new event); or Triage cases with TO SLA >8 hours but very high value (€60k) where ARR midpoint 0.20.  
  3. **Tier 3 (do not intervene now)**: Cases with 2nd alert and no new event since last alert (e.g., I-05, I-09); or Diagnosis Started cases with TO SLA >8 hours and ARR midpoint <0.15.  
  - *Segment-aware ARR use in scoring*: When estimating "plausible direct benefit" for tier assignment, use:  
    - **Public Sector**: midpoint of supplied ARR range.  
    - **Strategic Enterprise**: midpoint  0.02 (accounts for recent overprediction; e.g., 0.15  0.02 = 0.13).  
    - **SME**: midpoint + 0.02 (accounts for underprediction; e.g., 0.26 + 0.02 = 0.28).  
    - **Non-Native-Language Support (NLLS)**: midpoint only; flag as "uncertainty-high" in rationale (no adjustment, but require TO SLA 4h or new event to reach Tier 1).  
    - *Why adjust?* Calibration uncertainty is known per segment; adjustment is conservative and documented. Do **not** adjust `p_now` or claim certainty; instead, use adjusted ARR midpoint only for tier tiering and verbal rationale (e.g., "based on typical over/under-prediction, we expect the true benefit to be around this midpoint ±~0.03").  
  - *False-alarm burden consideration*: Tier 2 automatically excludes cases where false-alarm burden >€1,000 and value <€20,000 (e.g., I-08 has high burden €5k but high value 100k  still Tier 2 if first alert; I-05 has low burden €100 but repeated no-new  Tier 3). This is a simple filter to avoid low-certainty high-burden requests.  
  - *Urgency inclusion*: TO SLA 4h overrides value alone for Tier 1 (e.g., I-07 with TO 1.5h gets Tier 1 even if value 5k).  
  - **Rule in practice**: At alert or when reviewing slots, check stage  if Diagnosis Complete, skip; check alert history  if 2nd alert, verify "new event logged?" (yes  proceed to tier; no  mark suppressed, do not allow swarm request); compute adjusted ARR midpoint per segment; assign Tier 1/2/3 per above; use tier to decide "Intervene / Wait / Do not intervene" (Intervene = Tier 1 if slot available; Wait = Tier 2 if Tier 1 slots exhausted; Do not intervene = Tier 3). No numeric threshold on `p_now`; stage, TO SLA, new-event status, and tier drive the decision.

> *Rationale clarity for operators*: "If it’s the first alert or a new log/symptom was uploaded since the last alert, and the case hasn’t passed Diagnosis Started, check TO SLA. If TO 4h  Tier 1 (use slot if free). If TO 4–8h  Tier 2 (use only if no Tier 1 slots left). If it’s a repeat alert (2nd or later) and no new log/symptom was added since the last alert  Tier 3 (do not request a swarm now; wait for a new log or the case moves to Diagnosis Complete). For Strategic Enterprise, subtract ~2% from the ARR midpoint when judging; for SME, add ~2%; Public and NLLS use the midpoint as given. Always check the stage first – no swarms after Diagnosis Complete."

## 4. Repeated alerts and temporal policy

- **Suppression rule (when alert generated 2nd time)**:  
  - If **no materially new event** (see definition below) has occurred since the last alert  **suppress swarm request** for this alert. Operator/system logs "alert on hold" with reminder: "Review for swarm if new log/symptom uploaded; no swarm request allowed now."  
  - If **a materially new event** has occurred since last alert  **do not suppress**; proceed to tier scoring (Tier 1/2 as per Section 1).  
  - *Materially new event definition (operational, concrete)*: Any observable change in case data since last alert that could affect diagnosis, e.g.,  
    - New diagnostic log upload (e.g., I-07’s customer log),  
    - New symptom report or customer clarification from support agent,  
    - Fix of imputed field (e.g., live queue feature restored),  
    - *Not*: subjective reprioritization, model re-evaluation, or time elapsed alone.  
    - For NLLS cases, require explicit log entry or agent confirmation of new info (e.g., "log uploaded" noted); do not infer from `p_now` change alone.  
  - *How suppression is enforced*: Alert UI shows "Suppressed – wait for new event" when 2nd alert and no new event logged. No button to request swarm for this alert. When a new event is logged (e.g., agent enters "customer log uploaded"), system automatically re-evaluates tier (uses current stage and alert history) and shows "Swarm request possible" if eligible.

- **Cool-down / wait period**: No fixed time cool-down (e.g., 30 mins). Instead, rely on *new event check*: only un-suppress when new event is logged. This avoids waiting unnecessarily (e.g., I-05 could wait hours for no new event).

- **Escalation**:  
  - If a suppressed alert (e.g., I-05) receives a new event (e.g., new log), immediately allow swarm request via tier scoring.  
  - If a Tier 2 case (e.g., I-01) has no Tier 1 slots and value €30k with TO 6h, operator may request slot after Tier 1 fills (per reserve policy); but Tier 3 cases (no new event) never escalate to swarm request without new event.

- **Re-entry**: A case can receive a swarm only if still at Triage/Diagnosis Started **and** a new event has occurred since last alert (or it is the first alert). After `Diagnosis Complete`, no swarm (stage rule), even if new event occurs later. No swarm retries on same case without new event.

- **I-05 vs I-07 comparison**:  
  - I-05: third alert, "no new event since previous alert", false-alarm burden €100.  **Suppress** swarm request for this alert. Operator monitors p but does not request swarm. If later a new log/symptom appears, re-evaluate; otherwise, wait until natural progression (but unlikely to need swarm post-Diagnosis Complete).  
  - I-07: third alert, "new customer log uploaded".  **No suppression**; new log = materially new event. Proceed to tier scoring (Tier 1). Swarm request is reasonable because the log may resolve uncertainty; false-alarm burden low (€50), TO urgent (1.5h), so likely intervene if slot available.

- **Operational check**: At each model refresh (every 30 mins), system scans case logs for "new event" markers (e.g., "log uploaded", "symptom added" in case notes). If found for a suppressed case, auto-notify Tier team with "Swarm possible" flag. No automated swarm scheduling; only operator-triggered after flag.

## 5. Fairness and feedback-loop risks (with concrete safeguards)

- **Value-based prioritization starving lower-value cases**: Risk: High-value cases (e.g., I-08 100k) might consistently get slots if urgency low (TO 8h), while low-value urgent cases (e.g., I-07 5k) compete. Safeguard: **Cap Tier 1 slots at 2 per time window** (e.g., current 4 slots total; max 2 for TO 4h Tier 1 cases, max 1 for Tier 2 cases with value <€30k). If both caps fill, Tier 2 high-value cases (€60k) get the remaining slot(s), but Tier 1 urgent <€20k always has priority for first 2 slots. This ensures at least 2 urgent slots available even if high-value cases appear. *Monitor*: Weekly count of Tier 1 vs Tier 2 slot uses by value band; if >70% of slots go to value >€50k for 2 weeks, adjust cap (e.g., increase Tier 1 cap to 3).

- **Uncertainty for NLLS cases**: Risk: NLLS ARR estimates (e.g., I-09) may be noisy; frequent swarms on NLLS could lead to wasted slots or over-prioritization. Safeguard: **For NLLS cases, require two senior specialists (not one) for the swarm**, and **limit swarms to 1 per NLLS case per week** unless a materially new event occurs. Additionally, when scoring NLLS cases, use "midpoint  0.02" for benefit estimate (conservative), i.e., assume true ARR  midpoint. *Monitor*: Monthly NLLS swarm rate vs predicted need (from tier scores); if >1 swarm/week per NLLS case, review new-event threshold or add language-support checklist.

- **Differential calibration across segments**: Risk: SME underprediction (model says p=0.42 but true p0.5) and Strat overprediction (p=0.66 but true p0.6) could lead to systematic over/under-allocation to segments. Safeguard: **Automatically apply segment-aware adjustment in tier scoring** (as in Section 1: Public = midpoint; Strat = midpoint  0.02; SME = midpoint + 0.02; NLLS = midpoint). **Weekly calibration check**: Compare predicted breach rate (mean `p_now` for cases closed that day) vs actual breach rate (SLA missed) for each segment. If |predicted  actual| >0.05 for any segment for 2 consecutive weeks, re-estimate segment adjustment (e.g., adjust Strat offset from 0.02 to 0.015). Report calibration drift in daily ops dashboard; no policy change until drift observed.

- **Feedback loop: swarms changing future training labels**: Risk: Swarm intervention (e.g., finding missing info) could make future `Diagnosis Complete` label more accurate or biased toward "resolved", inflating future `p_now` predictions and creating a loop where swarms are always needed. Safeguard: **Model retraining uses only data before swarm intervention** for the case. Specifically, for `Diagnosis Complete` label (used in prediction target), do not include swarm findings (e.g., "swarm discovered missing log") in training features or label derivation. Use original diagnosis path data (without swarm-added info) for retraining. If swarm corrects an error (e.g., missing log), record it in case notes but **do not use it to update the model’s `p` prediction for similar cases** during training. *Monitor*: After each retraining (monthly), compare prediction accuracy (breach hit rate) for cases that received a swarm vs no swarm; if swarm-case accuracy improves >0.1 over baseline, investigate label leakage. Stop using swarm-related notes in training features if leakage detected.

- **Spillover harms systematically falling on untreated groups**: Risk: Repeated slot use on certain queue segments (e.g., Public Sector) could increase untreated cases' breach risk due to congestion. Safeguard: **Track and report spillover impact weekly**. For each swarm slot used, log the 6 untreated diagnosis-stage cases in the queue at swarm time (from queue system). After SLA decisions (closed), check which untreated cases missed SLA. Compute simple difference: untreated breach rate post-slot vs baseline (average breach rate for same segment over previous 2 weeks). If average breach rate >0.02 for untreated groups in >2 of 4 weeks, **pause new swarm allocations for that segment for 1 day** and review queue size at swarm times. Also, **randomize slot allocation among Tier 1 cases when 2 Tier 1 cases exist** (e.g., if only I-06 and I-07 are Tier 1, flip a fair coin to choose which gets first slot). This avoids consistently targeting the same queue subset. *Monitor*: Weekly untreated breach rate by segment (with vs without recent slots); alert if untreated breach rate increases >10% after 2 slots in 24h for same segment.

*All safeguards are concrete, operational, and low-overhead:*  
- Caps and limits are simple counts (e.g., max 2 Tier 1 slots).  
- Weekly checks use existing data (queue logs, closed case SLA status).  
- No new tools; use current case notes and queue system to log "new event" and untreated cases.  
- Randomization for small Tier 1 queues uses existing operator action (choose which Tier 1 case gets slot).

## 6. Monitoring and recalibration plan

- **Operational monitoring (daily, by ops team)**:  
  - Track queue stage: % of cases at Triage vs Diagnosis Started vs Diagnosis Complete (goal: <10% Diagnosis Complete before expected SLA deadline).  
  - Track alert status: # suppressed alerts vs # un-suppressed; % of suppressed alerts that receive new event within 2h.  
  - Log swarm usage: slots used, time of swarm, queue size at swarm time (6 untreated cases listed), reported delay (e.g., "swarm took 45min, other work delayed ~15min" from specialist notes).  
  - Verify new-event logging: % of "new log/symptom" entries in case notes that trigger auto-re-evaluation (target >90% accuracy; if <80%, investigate UI prompt clarity).

- **Predictive monitoring (weekly, by data/ML team)**:  
  - **Calibration check**: For each segment (Public, Strat, SME, NLLS), compute actual breach rate = (# SLA-missed cases closed that week) / (# cases closed that week). Compare to predicted breach rate = mean `p_now` for closed cases that week. Report |predicted  actual|; if >0.05 for any segment for 2 consecutive weeks, re-estimate segment adjustment (e.g., Strat offset from 0.02 to new value via simple linear fit on last 5 weeks of closed cases).  
  - **ARR estimate accuracy**: For cases where swarm was used (last 2 weeks), after resolution, record if breach occurred (yes/no). Compare to predicted ARR (midpoint used in tier scoring). Calculate average difference between actual breach reduction (e.g., if p_before=0.6, p_after=0.4  reduction 0.2) and predicted ARR. If |avg diff| >0.03 for any segment for 3 consecutive weeks, widen ARR range uncertainty (e.g., use midpoint ±0.05 instead of midpoint ±0.03 in scoring) and flag NLLS cases for extra review.

- **Causal-effect monitoring (weekly, by ops/ML)**:  
  - For each swarm slot, from queue log, identify the 6 untreated diagnosis-stage cases present at swarm time. After their closure (within 24h), check if they missed SLA. Compute untreated breach rate with vs without recent swarms:  
    - Baseline rate = untreated cases closed in same segment over prior 2 weeks with 1 swarm in last 24h.  
    - Post-slot rate = untreated cases closed within 24h after a swarm slot.  
  - Report breach rate = post-slot rate  baseline rate. If >0.02 for any segment in >2 of 4 weeks, **pause new swarm allocations for that segment for 1 day** (reserves any free slot).  
  - Target: breach rate 0.01 for all segments weekly.

- **Capacity monitoring (daily/weekly)**:  
  - Track actual delay from swarms: specialists report "other work delay" (e.g., "delayed 12–18 mins" in notes). Average delay per slot; compare to model estimate (8–20 mins). If avg delay >18 mins for >50% of slots, investigate queue congestion (e.g., too many Diagnosis Started cases); adjust reserve slot policy (e.g., reduce reserve if avg delay <15 mins).  
  - Track slot utilization: % of 4 daily slots used. Target 60–80% (leaving reserve + flexibility); if >90% consistently, review tier caps.

- **Fairness monitoring (weekly, by ops lead)**:  
  - Report by segment and "received swarm" vs "untreated":  
    - Breach rate (SLA miss) for swarm-received cases vs baseline.  
    - Breach rate for untreated diagnosis-stage cases (from causal-effect monitor).  
    - % of low-value cases (value <€20k) receiving Tier 1 slots.  
  - If untreated breach rate >baseline +0.05 or low-value Tier 1 >50% of slots for 2 weeks, review caps (e.g., increase Tier 2 cap). If NLLS swarm rate >1/week per case for 2 weeks, tighten new-event logging (add checklist).

- **Recalibration & policy change decisions (trigger-based, no fixed schedule)**:  
  - **Change segment adjustment (e.g., Strat offset)**: If weekly calibration check shows |predicted  actual| >0.05 for 2 consecutive weeks. Recalibrate offset via last 5 weeks of closed-case data (simple mean difference). Update adjustment in rule within 1 day.  
  - **Widen ARR uncertainty**: If weekly ARR accuracy check shows |avg predicted ARR  actual breach reduction| >0.03 for 3 consecutive weeks. Switch scoring to use midpoint ±0.05 (instead of midpoint ±~0.03) for all segments; monitor for 1 week; revert if accuracy improves.  
  - **Adjust spillover model or caps**: If causal-effect monitor shows breach rate >0.02 for any segment in >2 of 4 weeks. Pause new swarms for that segment for 1 day; review queue size at swarm times (e.g., if >8 diagnosis-stage cases, limit swarms to 1 per 2 slots). Re-enable after 1 day if breach 0.01 in next week.  
  - **Cap review**: If weekly fairness report shows low-value Tier 1 >50% of slots for 2 weeks, temporarily increase Tier 1 cap to 3 (max 3 out of 4 slots) and Tier 2 cap to 1. If untreated breach rate consistently <baseline for 2 weeks, reduce reserve slot to 0 (if no regulatory incident expected); but always keep 1 reserve if regulatory incident possibility >20% (per management preference).  
  - **Decision log**: Every policy change (adjustment, cap, pause) is logged with: trigger (e.g., "calibration drift >0.05 for Strat"), date, action, rationale, and monitoring metric. Reviewed in biweekly ops sync.

*Why this works:*  
- Monitoring uses existing operational data (queue logs, case notes, closed SLA status); no new tools.  
- Triggers are concrete (e.g., |calibration error| >0.05 for 2 weeks), avoiding ad-hoc changes.  
- Safeguards in Section 5 are directly monitored (e.g., new-event logging accuracy, untreated breach rate).  
- Reserve slot policy is respected (keep 1 free until regulatory incident occurs); reserve is not rigid ("rather than absolute rule").  
- Uncertainty is explicit in monitoring (use ranges, weekly checks, no precision claims).  
- Feedback loops are prevented by excluding swarm findings from model training labels.
