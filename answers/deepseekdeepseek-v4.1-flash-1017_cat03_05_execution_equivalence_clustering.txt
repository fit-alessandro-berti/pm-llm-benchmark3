def canon_sig(execution, lead_type="Order", use_partial_order=False):
    events = sorted(execution.events, key=lambda e:(e.timestamp, e.id))
    # lead order from Create Order event or given execution.lead
    mapping = {}
    counters = defaultdict(int)
    def token(oid, otype):
        if oid in mapping: return mapping[oid]
        ext = str(oid).startswith("EXT")
        if otype == lead_type and oid == execution.lead_order:
            t = (otype, "LEAD", 0, False)
        else:
            k = counters[(otype, ext)]
            counters[(otype, ext)] += 1
            t = (otype, "EXT" if ext else "LOCAL", k, ext)
        mapping[oid] = t
        return t
    def ev_sig(ev):
        by_type = defaultdict(list)
        for otype, oid in ev.omap: # incidence pairs
            by_type[otype].append(token(oid, otype))
        # Keep multiset; sort tokens for determinism.
        return (ev.activity, tuple(sorted((t, tuple(sorted(v))) for t,v in by_type.items())))
    if use_partial_order:
        buckets = []
        for ts, grp in groupby(events, key=lambda e:e.timestamp):
            buckets.append(tuple(sorted(ev_sig(e) for e in grp)))
        event_part = tuple(buckets)
    else:
        event_part = tuple(ev_sig(e) for e in events)
    o2o = []
    for src, rel, tgt in execution.o2o_relations: # includes qualifier rel, e.g. packs, removed_before_dispatch
        o2o.append((token(src.id, src.type), rel, token(tgt.id, tgt.type)))
    o2o_part = tuple(sorted(o2o))
    return (event_part, o2o_part)

## 1. Equivalence design space

**1. Activity-sequence equivalence (`E_act`).**  
Operational definition: project each execution to the ordered list of activity labels of events involving the lead `Order`; preserve repetitions and order, ignore all object identifiers, object types, E2O incidence, O2O relations, qualifiers, and timestamps except for ordering. For same-time events, use either a stable total order by activity label/event id, or a partial-order variant where same-time events are an unordered multiset within each timestamp bucket. Invariants: activity labels, repetition, and order. Discarded: object-centric information. It is reflexive, symmetric, and transitive because it is equality of sequences/partial-order signatures.

**2. Typed structural equivalence under identifier renaming (`E_T`).**  
Operational definition: two executions are equivalent if there exists a bijection on locally named objects, separately per object type and respecting `EXT` external flags, such that the sequence of events is identical up to renamed object tokens and such that the qualified O2O relation set is identical. Each event preserves activity label, occurrence order, repeated events, and the multiset of object tokens per type participating in that event. O2O edges preserve source type, target type, direction, and qualifier such as `removed_before_dispatch` or `partially_settles`. Invariants: typed E2O incidence, object multiplicities, externality, O2O topology and qualifiers, event order. Discarded: raw local identifiers, exact timestamps beyond order, attribute values, and amounts. It is an equivalence relation because it is definable as equality of a canonical typed signature. For concurrency, use timestamp buckets and compare multisets of event signatures within each bucket; if only a supplied total order exists, use that order.

**3. Business-semantic equivalence (`E_B`).**  
Operational definition: equality of a canonical business signature for the lead `Order`. The signature preserves activity labels, repeated activities, per-event object-type multiplicities, external-object flags and co-reference patterns among external objects, qualified O2O motifs, and whether logistics/finance are shared across orders. It abstracts away raw identifiers and exact timestamps. It is still an equivalence relation because it is equality of a canonical signature. Concurrency is handled by a partial-order bucket representation when timestamps support it. Invariants: single vs split package, single vs split delivery, payment multiplicity, cross-order logistics sharing, cross-order invoice sharing, replacement/removal qualifiers, return/repack motifs. Discarded: raw IDs, exact timing, attribute values, and event-instance identity.

## 2. Canonical signatures

Preferred relation: `E_B`. The following Python-like pseudocode canonicalizes local identifiers by first occurrence per `(object_type, external_flag)`, treats the lead order as `LEAD`, preserves per-event incidence, and includes qualified O2O edges.

```python
from collections import defaultdict

def canonical_signature(execution, lead_order, lead_type="Order", partial_order=False):
    # execution.events: list of {activity, timestamp, id, omap: [(type, oid), ...]}
    events = sorted(execution.events, key=lambda e: (e.timestamp, e.id))
    mapping = {}
    counters = defaultdict(int)

    def token(oid, otype):
        if oid in mapping:
            return mapping[oid]
        ext = str(oid).startswith("EXT")
        if otype == lead_type and oid == lead_order:
            tok = (otype, "LEAD", 0, False)
        else:
            k = counters[(otype, ext)]
            counters[(otype, ext)] += 1
            tok = (otype, "EXT" if ext else "LOCAL", k, ext)
        mapping[oid] = tok
        return tok

    def event_signature(ev):
        by_type = defaultdict(list)
        for otype, oid in ev.omap:
            by_type[otype].append(token(oid, otype))
        packed = tuple(sorted(
            (otype, tuple(sorted(tokens)))
            for otype, tokens in by_type.items()
        ))
        return (ev.activity, packed)

    if partial_order:
        buckets = []
        i = 0
        while i < len(events):
            j = i
            while j < len(events) and events[j].timestamp == events[i].timestamp:
                j += 1
            buckets.append(tuple(sorted(event_signature(e) for e in events[i:j])))
            i = j
        event_part = tuple(buckets)
    else:
        event_part = tuple(event_signature(e) for e in events)

    o2o_part = tuple(sorted(
        (token(src, stype), rel, token(tgt, ttype))
        for stype, src, rel, ttype, tgt in execution.o2o_relations
    ))
    return (event_part, o2o_part)
```

Two executions are in the same preferred business-semantic cluster iff their canonical signatures are equal. If O2O qualifiers are unavailable, replace `rel` with `"plain"`; if externality is intentionally ignored, set `ext=False` for every object.

## 5. Borderline cases

**X1 vs X2.** `E_act` and `E_T` both merge them: the activity order is identical, and object identifiers can be bijected per type. A raw-identifier exact clusterer, including `pm4py.cluster_equivalent_ocel` without canonicalization, may split them because `O1/I11/P11/...` differ from `O2/I22/P21/...`. Business semantics strongly agree they are the same. A defensive exact structural definition that treats identifier order or literal IDs as meaningful would over-split.

**X1 vs X5.** They are `E_act`-equivalent because the activity labels are the same. `E_T` and `E_B` separate them because the pack/dispatch events include `EXT-OA` and `EXT-IA`, and the O2O set says `EXT-OA` contains `EXT-IA`. An externality-blind business analysis would merge them with S1, but logistics compliance or cost allocation should not.

**X1 vs X6.** Again `E_act` merges them. `E_T` and `E_B` separate them because invoice and payment are shared with `EXT-OB`. If the analysis focuses only on physical fulfillment, a coarse logistics equivalence could merge X6 with X1. Financial monitoring, revenue recognition, or payment reconciliation should preserve the shared invoice.

**X1 vs X7.** Their activity labels are identical, but X7 has `removed_before_dispatch` and names `I72` in the dispatch event. `E_T` separates them because qualifiers and E2O incidence differ. If one ignores all O2O qualifiers and treats item incidence at dispatch as incidental, X7 can collapse into S1. That is defensible for simple volume reporting but poor for substitution/compliance analysis.

**X3 vs X4.** Both are “multi-package” executions. X3 is split packing with consolidated delivery; X4 is split packing, split delivery, and partial settlement. `E_act` separates them because X4 has additional dispatch and payment events. A coarse “multi-package” equivalence could merge them; a multiplicity-preserving business equivalence should not, because delivery and payment semantics differ.

**X4 vs X8.** Both contain repeated pack/dispatch activity and could be seen as “multi-shipment” by a flattened process. X8 adds return, inspection, repack, and a replacement relation. `E_act` separates them, and `E_B` separates them more sharply by lifecycle motif. If one collapses all repeated dispatch events and ignores return qualifiers, X4 and X8 may look closer, but that destroys reverse-logistics meaning.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` groups objects of a chosen type by their exact object-centric context in the OCEL. In practical terms, its key preserves object types, event activities, E2O incidence, connected object context, and usually exact object/event identities unless canonicalized. It does not magically understand business qualifiers such as `removed_before_dispatch`, especially if they are stored outside standard OCEL E2O incidence. Therefore raw local IDs can make exact clusters too fine: X1 and X2 are isomorphic but may be split because all object IDs differ. External suffixes can also over-split X5/X6 unless `EXT` is treated as an equality-preserving flag rather than a literal name.

Post-processing should replace object IDs with canonical tokens per type and external flag, include any qualified O2O relations supplied separately, then aggregate PM4Py clusters by canonical business signature. Exact equivalence is preferable for audit, debugging, traceability, and detecting duplicate/identity anomalies. Coarser business clustering is preferable for segmentation and management reporting. The `max_objs` parameter and large connected executions matter because cross-order sharing can create large components; truncation may drop external context and merge business-distinct executions or produce unstable cluster boundaries.

```python
import pm4py
from collections import defaultdict

lead_type = "Order"
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=lead_type,
    max_objs=1000
)

def normalize_pm_result(result):
    # PM4Py versions return either object->cluster mappings or cluster groups.
    if isinstance(result, dict):
        inv = defaultdict(list)
        for object_id, cluster_id in result.items():
            inv[cluster_id].append(object_id)
        return list(inv.values())
    return list(result)

business = defaultdict(list)
for group in normalize_pm_result(raw_clusters):
    # group is a set of lead Order objects considered equivalent by exact PM4Py
    subexecution = extract_subexecution_around_orders(
        ocel, group, lead_type=lead_type
    )
    for lead_order in group:
        sig = canonical_signature(
            subexecution,
            lead_order=lead_order,
            lead_type=lead_type,
            partial_order=True
        )
        business[sig].append(lead_order)

business_clusters = list(business.values())
```

## 7. Robustness analysis

If all O2O qualifiers are ignored, X7 loses the `removed_before_dispatch` marker; it remains different from X1 only because the dispatch event explicitly mentions `I72`. If that item incidence is also treated as noise, X7 merges into S1. X4 loses partial/complete settlement distinctions but remains distinct through two deliveries and two payments.

If external objects are ignored, X5 and X6 both collapse toward S1: their pack/dispatch or invoice/payment events retain the lead order and the same local object counts as the baseline. This is exactly why externality-blind clustering is often too coarse for compliance and cost allocation.

If repeated same-label events are collapsed, X3’s two pack events may compress toward a baseline-like single packing step, especially if package multiplicity is not preserved. X4’s two payments may be counted once, weakening partial-settlement semantics. X8’s second pack/dispatch may be conflated with the first, but the `Return Item` and `Inspect Return` activities still prevent full collapse with X4 or X1.

If Pack and Dispatch are treated as a partial order rather than a total order, X4 becomes two independent chains, roughly “pack P41 before D41” and “pack P42 before D42.” This better represents operational concurrency and may make X4 look structurally closer to a multi-shipment abstraction. X8 remains exceptional because return/inspection creates a causal break before the second pack.

If payment multiplicity is represented by an amount attribute rather than by event count, X4’s two payments may be modeled as one settlement with a larger amount. It may then merge with S1 or S2 depending on delivery multiplicity. This is reasonable for finance analytics but poor for compliance that requires payment-history reconstruction.

## 8. Limitations and recommendation

For **compliance monitoring**, use strict `E_B` or `E_T` with external flags, package/delivery multiplicities, qualified O2O relations, return motifs, and payment multiplicity. Compliance needs to see cross-order sharing, substitutions, and rework; activity labels alone hide too much.

For **operational segmentation**, use preferred `E_B` but allow labels such as “standard,” “split shipment,” “cross-order logistics,” “shared finance,” and “return/replacement.” This gives interpretable segments while preserving business-critical object-centric distinctions.

For **root-cause analysis**, use a finer `E_T` or canonicalized exact equivalence with actual timestamps and traceable IDs retained. Root-cause work often needs to know the specific item, package, delivery, invoice, or payment involved, so over-coarse clustering is harmful.

For **descriptive reporting**, use coarse `E_B` clusters or even activity-sequence summaries for dashboards, with the option to drill down to strict structural clusters. No single equivalence is best for all four purposes: compliance wants detail, segmentation wants stable business labels, root-cause wants identity and timing, and reporting wants aggregation. The preferred semantic clustering in Section 3 is therefore a middle ground, not a universal answer.
