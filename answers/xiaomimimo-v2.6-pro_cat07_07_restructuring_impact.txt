# 4. Risks invisible in average cycle time

Average cycle time is a **mixture distribution over segments with shifting weights**. It is stable or improving in all three plausible scenarios in the first 6–8 weeks, and it is *least* sensitive to exactly the things that determine whether this restructuring succeeds. At minimum eight risks hide behind it.

**1. Tail latency.** Median and mean are dominated by the mass of simple cases handled by local intake plus `Bot_Intake`/`Bot_Eligibility`, which this restructuring barely touches (92/100 unchanged at 0.3 h). Pooling concentrates all the tail-generating work into two hubs. The median can improve while **P99 doubles**, because a single M/M/3 queue at  = 0.95 has a waiting time 2.3× today's average *and* a far heavier tail than three separate M/M/1 queues. With complexity-weighted, heavy-tailed service times (there is a `case_complexity` column precisely because service is heterogeneous), realised P99 will be worse than any M/M/c estimate. Only p90/p99 per segment reveals this.

**2. High-complexity cases.** The routing rule "all high-complexity cases go to Technical Shared Service" is a **regressive** rule with respect to complexity: it systematically removes the fast path from the class of cases that most needs one, and it sends them to the queue with the highest utilisation. High-complexity cases are also the class where local knowledge currently prevents rework (the `local_expertise_flag` column exists because this effect is real and measurable). Management's table does not segment by `case_complexity` at all — the 4.0 h TSS wait is an average over a mix that will move adversely.

**3. Loss of local knowledge (a hidden substitution, not a deletion).** Today, 36 referrals/100 happen *because* local techs filter demand. Removing them does not remove the need; it removes the filter. The forecast is referral leakage of 5–15 per 100, which is 25–60 additional specialist-hours per 100 cases of **new** demand created by the restructuring itself. This is invisible in any cycle-time average because it shows up as *more cases entering the slow path* — a composition effect, not a performance effect. It is visible in DFG arc weights (`Local Technical AssessmentSpecialist Review`) and in `get_variants` (new variants appear that contain `Specialist Review` where previously only local activities occurred).

**4. Fairness across customer segments.** Average cycle time can improve while the language/regational-accommodation `customer_segment` deteriorates on every dimension: more handovers (TSS is not local), more rework (regional conventions unknown to the hub), longer cycle time, lower CSAT. Team-level fairness can improve (East catches up) while segment-level fairness worsens, because team and segment are different partitions of the same log. Nothing in a single average distinguishes these.

**5. Fairness across teams can improve by levelling down.** Convergence of North 6.8 d and East 8.6 d toward 7.5 d is arithmetically indistinguishable from East improving to 6.8 d and North degrading to 8.2 d. The maxmin gap metric rewards both. A welfare judgement requires reading the *levels* per team, not the spread.

**6. Learning and skill formation.** Skill atrophy has no cycle-time signature for 6–12 months. Routing all hard cases to the hub means local staff stop seeing hard cases: activity entropy per local resource falls, `discover_organizational_roles` shows role collapse, and `discover_activity_based_resource_similarity` shows resources becoming more similar (homogenisation) — which looks like "standardisation" in a dashboard and is actually the depletion of the internal labour market and of the successor pipeline for the very hub being created. The organisation buys 12 months of queue efficiency and pays with its bench.

**7. Accountability and ownership diffusion.** The projected approval fallout rate rises from 7.1 % to 12.2 % **inside management's own table**, and the plan removes a supervisor. When a shared queue returns a case for rework, the defect was created by one team and the fix is performed by another (the `Rework` activity's `team` differs from the defective activity's `team`). Average cycle time records the extra loop; it does not record that **no one is answerable for it**. Measurable via rework-ownership mismatch (L13) and via the disappearance of informative `handover_reason` values.

**8. Exception handling and non-happy-path variants.** Standardisation compresses the happy path and pushes variance into exception variants (`Rework` twice, ad-hoc arcs, cross-team cover). Average cycle time over all cases is dominated by the happy path. `get_variants` will show **variant count rising while top-10 variant share falls** — the process is becoming *less* standard in its tail even as its head is streamlined. The current 6/100 cross-team handovers with 18 % rework are the visible tip; if local teams are thinned, this class returns at higher volume.

**9. Resilience asymmetry (a ninth risk).** Pooling genuinely improves resilience where it replaces single points of failure (E_Tech at 82 % is one person's absence away from a stop). But removing one supervisor creates a new, *more* concentrated single point of failure in the shared approval queue, and centralising hard Quality Check into the same queue adds a second dependency to it. Average cycle time measured over a quarter with no absences will show none of this. Only an event study around absence episodes (G10) reveals it.
