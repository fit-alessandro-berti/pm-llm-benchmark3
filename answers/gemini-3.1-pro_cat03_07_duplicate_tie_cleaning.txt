## 1. Duplicate-handling decision tree

The following decision tree determines the cleaning action for candidate event pairs/groups sharing similar timestamps and object sets:

1.  **Are the source systems and source event keys identical?**
    *   Yes: Exact technical duplicate (e.g., replay or retry during extraction). -> **Drop** (retain one canonical instance).
    *   No: Proceed to 2.
2.  **Are the harmonized activity labels identical?**
    *   Yes: Proceed to 3.
    *   No: Proceed to 6.
3.  **Do the events refer to exactly the same set of objects across all object types?**
    *   Yes: Proceed to 4.
    *   No: Concurrent same-label events involving different objects (e.g., distinct picks for different items, distinct partial payments for different payment objects). -> **Retain both unchanged** (e.g., e03 vs e05; e13 vs e14).
4.  **Is there external reconciliation evidence that these represent the same physical event?**
    *   Yes: Same physical event observed by multiple systems (e.g., scanner vs. WMS). -> **Merge attributes and relations** (keep authoritative attributes, union E2O links if safe).
    *   No: Proceed to 5.
5.  **Is one event generated by a downstream system as a summary/status update based on the other?**
    *   Yes: Summary event derived from a detailed event (e.g., WMS pack vs. ERP pack summary). -> **Retain both with refined labels or qualifiers** (e.g., "Pack Package (Detailed)" vs "Pack Package (Summary)").
    *   No: Unresolved candidate (same activity, same objects, no clear evidence). -> **Quarantine for review**.
6.  **Are the pre-harmonization source activities semantically distinct despite mapping to the same harmonized label?**
    *   Yes: Harmonization collision (e.g., "accepted by carrier" vs "released from warehouse" both mapped to "Dispatch Package"). -> **Retain both with refined labels or qualifiers** (revert to or append original source activity semantics).
    *   No: Unresolved candidate. -> **Quarantine for review**.

## 3. Timestamp-tie ordering rules

Transforming partial orders (timestamp ties) into a total order requires a deterministic policy to ensure reproducibility, while prioritizing semantic correctness.

**Policy Hierarchy:**

1.  **Domain Constraints (Semantic):** Explicit domain knowledge overrides all. (e.g., e12 must precede e13; e08 (release) precedes e09 (accept) precedes e10 (handover)).
2.  **Within-Source Sequence (Semantic):** If events share a source and timestamp, use `source_seq` to order them. This reflects the source system's internal transaction order.
3.  **Lifecycle Constraints on Shared Objects (Semantic):** Logical progression of object states (e.g., Create -> Validate; Pick -> Pack -> Dispatch).
4.  **Source-Specific Semantics (Semantic):** Authoritative systems often lead downstream summary systems. Detailed WMS events logically precede the corresponding ERP summary events they trigger (e.g., e06 before e07).
5.  **Stable Fallback Order (Deterministic):** If semantics cannot break the tie, use a stable hash of (timestamp, activity, source, source_event_key) or simply alphabetical sorting on `source_event_key` or `eid` to ensure determinism across runs.

**Why adding microseconds first is flawed:**
Adding synthetic microseconds mechanically (e.g., randomly or by ingestion time) before applying semantic rules encodes a false physical order. Downstream algorithms will treat this synthetic order as ground truth. If ingestion time (`ingested_at`) dictates the microsecond delta, a delayed message from an upstream system will incorrectly appear to have occurred after a downstream summary event, creating false loops or constraint violations in the process model.

**Intended Orders:**

*   **e03–e07 at 10:00 (Post-cleaning e03 merged with e04):**
    *   `e03(WMS, Pick I1)` and `e05(SCANNER, Pick I2)`: Concurrent. Domain constraints don't dictate order. Use fallback (e.g., `eid` alphabetical): **e03 -> e05**.
    *   `e06(WMS, Pack Detail)`: Lifecycle constraint (Pick before Pack). Follows e03/e05.
    *   `e07(ERP, Pack Summary)`: Source semantics (ERP summary lags WMS detail). Follows e06.
    *   *Result:* e03 -> e05 -> e06 -> e07 (or e05 -> e03 -> e06 -> e07).

*   **e08–e10 at 10:15:**
    *   Domain constraints (Fact 4, Fact 5) dictate the physical sequence despite the timestamp tie.
    *   *Result:* e08 (Release) -> e09 (Accept) -> e10 (Handover).

*   **e11–e16 at 12:00 (Post-cleaning e11 merged with e16):**
    *   `e11(ERP/Billing, Invoice)`: Lifecycle (Invoice precedes payment processing).
    *   `e12(PSP, Auth M1)`: Lifecycle (Auth before Capture).
    *   `e13(PSP, Capture M1)` and `e14(PSP, Capture M2)`: Concurrent distinct captures. Domain constraints (Fact 7) puts e12 before e13. Use fallback for e13 vs e14: **e13 -> e14**.
    *   `e15(ERP, Payment Summary)`: Source semantics (Summary lags detailed captures).
    *   *Result:* e11 -> e12 -> e13 -> e14 -> e15 (or e11 -> e12 -> e14 -> e13 -> e15).

## 4. Conservative cleaning pipeline

The conservative pipeline focuses on minimum change, preserving as much original data and semantic distinction as possible.

**Steps:**
1.  **Backup Originals:** Copy original timestamps, activities, and sources to new metadata columns (`original_timestamp`, etc.).
2.  **Targeted Deduplication:** Apply verified-pair merging *only* to pairs with strong external evidence (Fact 1: e03/e04, Fact 6: e11/e16). Maintain provenance by recording source EIDs.
3.  **Label Refinement:** Refine harmonized labels that obscure semantic differences. Rename e08 to "Release from Warehouse", e09 to "Accept by Carrier". Qualify summary events: e07 to "Pack Package (ERP Summary)", e15 to "Capture Payment (ERP Summary)".
4.  **Deterministic Ordering:** Apply the hierarchical sorting rules defined in Section 3 to establish a total order column (`sort_index` or similar), without altering the original timestamp.
5.  **Index-based Timedelta:** (Optional, only if strictly required by PM4Py tools that cannot use custom sort columns). Add minimal, deterministic microsecond increments based *strictly* on the derived `sort_index`, not ingestion time.

**Expected retained event count:**
Start: 17 events.
Merge e03/e04: -1 event.
Merge e11/e16: -1 event.
End: 15 events.
Abstraction levels (e06/e07) and distinct partial transactions (e13/e14) are safely preserved.

## 5. Aggressive alternatives

**Scenario A: Evidence-Based Semantic Merging (Moderate)**
This scenario assumes that downstream analysis requires a simplified, single-level process view, preferring to collapse summary/detail pairs into single logical events if they refer to the same transition.

*   *Actions:* In addition to conservative steps, merge abstraction-level pairs. Merge e06 (WMS detail) with e07 (ERP summary) into a single "Pack Package" event. Merge e13/e14 (PSP detail) with e15 (ERP summary) - *wait, this is problematic due to Fact 8 (missing Payment object in e15) and distinct M1/M2 objects in e13/e14.*
*   *Expected count:* ~14 events (depending on how abstraction pairs are handled).
*   *Semantic damage:* Loss of visibility into system latency (WMS to ERP delay). Risk of corrupting object relations if merging e15 (which lacks Payment objects) with e13/e14 (which have specific Payment objects).

**Scenario B: Mechanically Aggressive PM4Py Merging (High Risk)**
This scenario blindly applies generic duplicate detection algorithms based on timestamp and shared objects.

*   *Actions:* Use `pm4py.ocel_drop_duplicates` or `pm4py.ocel_merge_duplicates` aggressively, defining duplicates as events with the same timestamp, activity, and at least one common object (`have_common_object=True`).
*   *Expected count:* <10 events.
*   *Semantic damage:* Massive.
    *   e03, e04, e05 share timestamp, activity ("Pick Item"), and objects (O1, P1). They will be merged/dropped, losing the distinct pick of I2.
    *   e13, e14, e15 share timestamp, activity ("Capture Payment"), and objects (O1, V1). They will be merged/dropped. **Why `have_common_object=True` fails here:** While e13 and e14 represent distinct payment objects (M1, M2), they both relate to Order O1 and Invoice V1. An aggressive merge based on *any* shared object will see O1/V1, conclude they are duplicates, and erroneously collapse two distinct partial payments into one, corrupting the financial reality of the process.

## 8. Audit trail and reversibility

To ensure transparency and allow reconstruction of the raw data, the pipeline must output a separate provenance table (or append structured metadata columns to the event log).

**Provenance Schema:**
*   `canonical_eid`: The ID retained in the cleaned log (e.g., e03).
*   `source_eids`: List of IDs merged into this canonical event (e.g., `["e03", "e04"]`).
*   `merge_rule`: The logic applied (e.g., "Verified Pair Fact 1", "Refined Label Fact 3").
*   `reviewer`: Script version or human analyst name (e.g., "Pipeline_v2.1").
*   `original_activity`: JSON array of original activities (e.g., `{"e03": "Pick Item", "e04": "Pick Item"}`).
*   `refined_activity`: The new label (e.g., "Pick Item").
*   `original_timestamps`: JSON array mapping EID to original time.
*   `adjusted_timestamp`: The synthetic microsecond-adjusted time, if applied.
*   `retained_attributes`: JSON describing which source provided which attribute payload.
*   `discarded_conflicts`: Record of conflicting attributes that were dropped.
*   `confidence`: "High", "Medium", "Review".
*   `reason`: Text description (e.g., "WMS and Scanner reconciliation").

**Reconstruction:**
An analyst can reconstruct the raw view by joining the cleaned log with the provenance table. By exploding the `source_eids` array, they can generate rows for the original events. The `original_activity` and `original_timestamps` JSON payloads provide the raw values needed to overwrite the refined fields, effectively reversing the cleaning pipeline.

## 9. Failure modes and safeguards

Implementing duplicate cleaning on complex OCELs is prone to severe semantic errors.

1.  **Collapsing distinct partial payments:** Merging e13 and e14 because they share an Order and Invoice, ignoring the distinct Payment objects (M1, M2), thus destroying financial accuracy. *Safeguard: Explicit checks for object set equality across ALL types before merging.*
2.  **Converting abstraction-level updates into false rework:** Leaving e06 and e07 as "Pack Package". PM4Py will detect a cycle (`Pack -> Pack`), inflating rework metrics. *Safeguard: Label refinement based on source system semantics.*
3.  **Ordering by ingestion time:** Using `ingested_at` to break timestamp ties will reorder business events based on network latency or batch processing schedules, violating domain constraints. *Safeguard: Strict adherence to semantic ordering rules; ignore ingestion time for business logic.*
4.  **Treating shared objects as proof of duplication:** Assuming any two events with the same timestamp, activity, and at least one shared object are duplicates (the `have_common_object=True` trap). *Safeguard: Do not use library default merges without understanding their object-intersection logic.*
5.  **Unioning incompatible E2O relations:** Merging events and blindly unioning their object relations. If e15 (no payment object) is poorly merged with e13 (M1), e15's scope is falsely expanded. *Safeguard: Only union relations on verified identical physical events.*
6.  **Changing durations through synthetic microseconds:** Adding random or large synthetic microsecond increments can alter performance measurements, especially in high-frequency automated processes. *Safeguard: Keep timedelta increments minimally small (e.g., 1 microsecond) and strictly deterministic.*
7.  **Losing source-authoritative attributes:** Merging e03 and e04 but keeping the scanner payload, losing the WMS-enriched location data. *Safeguard: Define attribute retention policies (e.g., "WMS payload > Scanner payload").*
8.  **Applying duplicate functions to the whole OCEL without inspecting candidate groups:** Running a generic `drop_duplicates` command. It will blindly execute logic across unrelated processes. *Safeguard: Always pre-group candidates by time/label and evaluate specific rules (like the decision tree) before altering the data.*
