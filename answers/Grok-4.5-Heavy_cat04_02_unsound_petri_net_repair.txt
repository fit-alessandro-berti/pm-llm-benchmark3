# 1. Executive Verdict

The net is a workflow net (unique source and sink; every node lies on a source-to-sink path). It should not be expected to be sound. The principal defect is that `t_join_waived` is unary (only consumes from `p_waived`), so the waiver route never synchronizes with the analysis branch. Consequently a case can reach a marking containing a token in `sink` while a residual token remains in the analysis branch (`p_analysis` or `p_analysis_done`). Authorization is therefore possible without analysis, violating the mandatory-analysis rule, and the exact final marking `fm` is never reached on the waiver path.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source` / `t_register` / `p_ready` | Case entry | Correct unique source path | None |
| `t_split` | Parallel launch of analysis + review | Produces tokens in both `p_analysis` and `p_review` | Correct AND-split |
| Analysis branch (`p_analysis` → `t_analyze` → `p_analysis_done`) | Mandatory parallel work | Token produced and later available only to `t_join_normal` | Leftover token when waiver route is taken |
| Standard-review branch (`p_review` → `t_standard_review` → `p_review_done`) | One alternative of the XOR | Correctly feeds binary `t_join_normal` | None on this route |
| Waiver branch (`p_review` → `t_waive_review` → `p_waived`) | Other alternative of the XOR | Token reaches unary `t_join_waived` | Bypass of analysis |
| `t_join_normal` | AND-join of analysis + standard review | Binary; correctly requires both inputs | Works only for standard path |
| `t_join_waived` | Intended AND-join of analysis + waiver | Unary (only `p_waived`); no arc from `p_analysis_done` | Authorization without analysis; residual tokens |
| `p_decision` / `t_authorize` / `sink` | Final authorization and exit | Unique sink; reachable from both joins | Token in sink does not imply exact `fm` |
| Initial/final markings | `{source:1}` → `{sink:1}` | Correct WF-net markings | Residual tokens prevent exact `fm` on waiver |
| Source-to-sink paths | Every node must be covered | All places and transitions lie on at least one path | Passes WF-net check; fails soundness |

# 3. Marking-Based Counterexample

Legal firing sequence that exposes the defect (waiver route, analysis never required):

`t_register` → `t_split` → `t_waive_review` → `t_join_waived` → `t_authorize`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---|---|---|---|---|
| 0 | — | `{source:1}` | `t_register` | Initial marking `im` |
| 1 | `t_register` | `{p_ready:1}` | `t_split` | Case registered |
| 2 | `t_split` | `{p_analysis:1, p_review:1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | Parallel tokens created |
| 3 | `t_waive_review` | `{p_analysis:1, p_waived:1}` | `t_analyze`, `t_join_waived` | Waiver taken; analysis token still present |
| 4 | `t_join_waived` | `{p_analysis:1, p_decision:1}` | `t_analyze`, `t_authorize` | Unary join succeeds without analysis |
| 5 | `t_authorize` | `{p_analysis:1, sink:1}` | `t_analyze` | Token exists in sink, yet marking ≠ `fm` |
| 6 (optional) | `t_analyze` | `{p_analysis_done:1, sink:1}` | (none) | Leftover cannot be consumed: `t_join_normal` needs `p_review_done` which is absent |

A second counter-example (analysis performed before the unary join) ends with `{p_analysis_done:1, sink:1}`; the same residual-token deadlock occurs. In both cases `t_authorize` fires while the analysis branch still holds a token, and the exact final marking `fm` is never obtained.

# 4. Minimal-Repair Alternatives

Edit-cost model: each added or removed place, transition or arc counts as 1 (absolute elementary edits).

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---|---|---|---|
| R1 (add analysis synchronization to waiver join) | Add single arc `p_analysis_done` → `t_join_waived` | 1 | Full: analysis mandatory on both review routes; parallel start; distinguishable labeled reviews; exact `fm` reachable | Both joins become binary AND-joins; the review XOR still selects which join may fire | `p_analysis_done` now has two outgoing arcs (harmless; exclusivity is enforced by the review token) |
| R2 (consolidate both review outcomes into one join) | Remove arcs `t_waive_review`→`p_waived`, `p_waived`→`t_join_waived`, `t_join_waived`→`p_decision`; add arc `t_waive_review`→`p_review_done`; remove place `p_waived` and transition `t_join_waived` | 6 | Full: analysis still mandatory (via the single remaining join); parallel start; reviews still distinguished by visible labels | Single binary join only; structural distinction between waiver and standard disappears | Slightly less modular if future waiver-specific post-processing is required |

Both repairs retain mandatory analysis on the waiver path. R1 is strictly cheaper under the chosen cost model; the two repairs are behaviorally and structurally distinct (two joins versus one). No cheaper distinct repair that preserves the full intent exists.

def fire_named(net, marking, t_name):
    """Fire a named transition after checking enabledness; raise on failure."""
    t = next((tr for tr in net.transitions if tr.name == t_name), None)
    if t is None:
        raise ValueError(f"Transition {t_name} not found")
    enabled = pm4py.get_enabled_transitions(net, marking)
    if t not in enabled:
        raise ValueError(f"{t_name} not enabled under marking { {p.name: marking[p] for p in marking} }")
    return PetriNetSemantics.fire(net, t, marking)

# Demonstrate the original counter-example
print("\n--- Original counter-example sequence ---")
m = im.copy()
for name in ["t_register", "t_split", "t_waive_review", "t_join_waived", "t_authorize"]:
    m = fire_named(net, m, name)
    print(name, "->", {p.name: m[p] for p in m if m[p] > 0})

# Same sequence on repaired net must fail at the unary-join attempt
print("\n--- Same sequence on repaired net (must block) ---")

    m = fire_named(repaired_net, m, name)

Expected qualitative difference: the original is reported as a workflow net yet fails soundness (uncovered places under s-components, residual tokens, option-to-complete violation). The repaired net remains a workflow net and passes soundness; the counter-example sequence is rejected at `t_join_waived` because the analysis token is still required.

# 7. Repair Trade-Offs and Residual Risks

- Waiver and standard review remain distinguishable after R1 by both structure (different joins) and visible labels; after R2 they are distinguished only by labels.
- R1 introduces no new silent transitions; the existing silent joins stay silent. No duplicate visible behavior is created.
- Soundness guarantees proper completion and absence of residual tokens, but does not by itself prove that every positive business trace (analysis always present) and every negative trace (authorization without analysis) are respected; the marking argument is still required.
- Regression test set should include: (a) standard-review path with analysis, (b) waiver path with analysis, (c) any attempt to authorize after only a waiver (must be blocked), (d) attempts to fire joins with only one input token.
- Accidental bypass of mandatory analysis is detected by checking that both `t_join_normal` and `t_join_waived` have `p_analysis_done` among their input places, or by asserting that every complete run of the reachability graph contains the transition `t_analyze`.

# 8. Final Recommendation

Deploy R1 (add the single arc from `p_analysis_done` to `t_join_waived`). It is the unique cost-1 repair that fully restores the stated business intent: analysis remains mandatory on every path, both review alternatives stay distinguishable, and the net becomes sound. The structural change is minimal and local, preserving the original two-join modular design. Use R2 (consolidation to a single join) only as a fallback if a later maintenance decision prefers fewer silent transitions or a simpler place set; the higher edit cost and loss of structural distinction between the two review outcomes make it second-best for the current requirements.
