## 1. Modeling assumptions

- Object types are capitalized exactly as `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`.
- The E2O qualifier vocabulary is role-based and source-oriented: `order_subject`, `container_order`, `added_item`, `demand_order`, `reserved_item`, `package_subject`, `packed_item`, `fulfilled_order`, `delivery_subject`, `dispatched_package`, `dispatched_for_order`, `confirmed_package`, `confirmed_for_order`, `invoice_subject`, `billed_order`, `payment_subject`, and `settles_invoice`.
- O2O direction always uses `ocel:oid -> ocel:oid_2` as source to target. The conventions are `Order -> Item` with `contains`, `Package -> Item` with `packs`, `Delivery -> Package` with `carries`, `Invoice -> Order` with `bills`, and `Payment -> Invoice` with `partially_settles` or `completes_settlement`.
- I use a balanced direct-relation policy. Logistics events are related directly to the package or delivery they operate on and to directly implicated orders; item links are kept direct only where the event explicitly manipulates items (`Add Item`, `Reserve Stock`, `Pack Package`). Financial events are direct to `Invoice` and `Payment`; `Issue Invoice` is also direct to both billed orders, but `Record Payment` is not linked directly to orders because the narrative does not allocate M1 or M2 across O100 and O200.
- Analytical propagation is kept separate from source facts. The `relations` table contains only asserted event-object links, while any later O2O-based propagation should be treated as derived analysis and, if materialized, should use a separate namespace such as `derived:*` qualifiers rather than being mixed into source E2O rows.
- The code assumes a PM4Py variant where `from pm4py.objects.ocel.obj import OCEL` works and `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available. If a local version wants extra optional tables, the adjustment should be isolated at constructor time by passing empty optional structures, without changing the four core DataFrames or their semantics.

## 3. Data-model audit

| Object type | Objects |
|---|---|
| `Order` | `O100`, `O200` |
| `Item` | `I1`, `I2`, `I3` |
| `Package` | `P1`, `P2` |
| `Delivery` | `D1`, `D2` |
| `Invoice` | `V1` |
| `Payment` | `M1`, `M2` |

| O2O qualifier | Cardinality | Rows |
|---|---:|---|
| `contains` | 3 | `O100->I1`, `O100->I2`, `O200->I3` |
| `packs` | 3 | `P1->I1`, `P1->I3`, `P2->I2` |
| `carries` | 2 | `D1->P1`, `D2->P2` |
| `bills` | 2 | `V1->O100`, `V1->O200` |
| `partially_settles` | 1 | `M1->V1` |
| `completes_settlement` | 1 | `M2->V1` |

| Activity | Event count | Object types touched in E2O |
|---|---:|---|
| `Create Order` | 2 | `Order` |
| `Add Item` | 3 | `Order`, `Item` |
| `Reserve Stock` | 1 | `Order`, `Item` |
| `Pack Package` | 2 | `Order`, `Item`, `Package` |
| `Dispatch Package` | 2 | `Order`, `Package`, `Delivery` |
| `Issue Invoice` | 1 | `Order`, `Invoice` |
| `Record Payment` | 2 | `Payment`, `Invoice` |
| `Confirm Delivery` | 2 | `Order`, `Package`, `Delivery` |
| `Close Order` | 2 | `Order` |

The most consequential relation sets are `e07` and `e11`. Event `e07` (`Pack Package` for `P1`) is the key logistics convergence point because one package binds `I1`, `I3`, `O100`, and `O200`. Event `e11` (`Issue Invoice` for `V1`) is the key financial convergence point because one invoice binds both orders and becomes the single settlement target of `M1` and `M2`.

## 4. Expected flattened behavior

- `Order`: the `O100` trace should look roughly like `Create Order -> Add Item -> Add Item -> Reserve Stock -> Pack Package -> Pack Package -> Dispatch Package -> Dispatch Package -> Issue Invoice -> Confirm Delivery -> Confirm Delivery -> Close Order`, while `O200` should look roughly like `Create Order -> Add Item -> Reserve Stock -> Pack Package -> Dispatch Package -> Issue Invoice -> Confirm Delivery -> Close Order`. Shared events copied into both traces are the joint `Reserve Stock`, the `P1` packing event, the `P1/D1` dispatch, the shared invoice issuance, and the `D1` confirmation. Omitted aspects are the invoice settlement sequence and the fact that `P1` is one shared package rather than two separate pack-dispatch-confirm chains. Likely DFG edges include `Create Order -> Add Item`, `Add Item -> Reserve Stock`, `Reserve Stock -> Pack Package`, `Pack Package -> Dispatch Package`, `Dispatch Package -> Issue Invoice`, `Issue Invoice -> Confirm Delivery`, and `Confirm Delivery -> Close Order`, plus same-activity edges such as `Pack Package -> Pack Package` and `Dispatch Package -> Dispatch Package` in `O100`. The main misleading interpretation is that duplicated shared events can make it look as if each order independently executed identical pack and delivery work, even though `P1` and `D1` are shared physical entities.
- `Package`: `P1` and `P2` should each flatten to a compact `Pack Package -> Dispatch Package -> Confirm Delivery` trace. There are no copied shared events between package cases because each event is attached to only one package object. Omitted aspects are order creation, item addition, stock reservation, invoicing, payments, and order closure. The dominant DFG edges should simply be `Pack Package -> Dispatch Package` and `Dispatch Package -> Confirm Delivery`. The misleading interpretation is that `P1` can look like a normal single-case package, even though it is the precise point where two orders converge.
- `Delivery`: `D1` and `D2` should each flatten to `Dispatch Package -> Confirm Delivery`. There are again no copied shared events across delivery cases. Omitted aspects are all upstream order and item preparation, plus the entire financial lifecycle. The DFG is likely a single edge `Dispatch Package -> Confirm Delivery`. The misleading interpretation is that `D1` appears to be a routine delivery case, hiding that its carried package `P1` bundles `O100` and `O200`.
- `Invoice`: `V1` should flatten to one short financial trace, approximately `Issue Invoice -> Record Payment -> Record Payment`. There are no copied shared events at the invoice level because there is only one invoice object. Omitted aspects are the whole logistics lifecycle and the order closures. Likely DFG edges are `Issue Invoice -> Record Payment` and `Record Payment -> Record Payment`. The main misleading interpretation is that a two-step payment chain can appear as a self-looping generic payment activity, while the per-order allocation of `M1` versus `M2` remains intentionally unresolved.

Flattening on `Payment` would be particularly weak because `M1` and `M2` each have only one directly related event: their own `Record Payment`. That yields one-event traces, trivial DFGs, and almost no skeleton structure. Making payment traces longer by force-linking invoice issuance or orders to payment objects would improve apparent discoverability only by blending derived context into observed facts.

## 5. Expected object-centric structures

- `OC-DFG`: the object-centric directly-follows view should expose multiple intertwined lifecycles instead of one compromised flattened one. On the logistics side, `P1` is the important convergence object: `Pack Package`, `Dispatch Package`, and `Confirm Delivery` on `P1/D1` are shared across `O100` and `O200`, while `O100` alone continues through `P2/D2`. On the financial side, `V1` is the convergence object: both `O100` and `O200` meet at `Issue Invoice`, and then `M1` and `M2` both follow as payments on that same invoice. The graph should therefore reveal both convergence (`P1`, `V1`) and divergence (`P2`, `D2`, the extra branch of `O100`).
- `OTG`: the object-type graph should highlight the backbone `Order-Item-Package-Delivery` and `Order-Invoice-Payment`. Because `M1` and `M2` are intentionally attached through `V1` rather than directly to `O100` or `O200`, the finance side should look invoice-centric rather than order-centric. `P1` instantiates the strongest logistics cross-type coupling, and `V1` instantiates the strongest finance coupling.
- `ET-OT`: the event-type to object-type graph should make type participation explicit. `Pack Package` is the richest event type because it touches `Order`, `Item`, and `Package`; `Dispatch Package` and `Confirm Delivery` bridge `Order`, `Package`, and `Delivery`; `Issue Invoice` bridges `Order` and `Invoice`; and `Record Payment` bridges `Payment` and `Invoice` only. This view is where a reviewer should immediately see that payment allocation to individual orders is deliberately not asserted.
- `Object-centric Petri net`: no single net is uniquely forced by the story, but a reasonable discovered model should show separate local lifecycles that synchronize at a few transitions. One synchronization should center on `Pack Package`, where `P1` joins material from `O100` and `O200`; another should center on `Issue Invoice`, where `V1` jointly references both orders. The payment part should show repeated `Record Payment` behavior on `V1` with two one-shot payment objects `M1` and `M2`. The `Order` component should also show that `O100` has an extra fulfillment branch (`P2`, `D2`) before closure, whereas `O200` can close after the `P1/D1` branch and the shared invoice lifecycle have progressed.
- `Object-interactions summary`: this summary should surface `P1` as a cross-order logistics hub and `V1` as the finance hub. `P1` should interact with `I1`, `I3`, `O100`, `O200`, and `D1`. `V1` should interact with `O100`, `O200`, `M1`, and `M2`. `O100` should show the broadest neighborhood because it participates in both `P1/D1` and `P2/D2`, while `O200` should have the smaller neighborhood centered on `I3`, `P1`, `D1`, and `V1`.

## 6. Modeling alternatives

| Policy | Core idea | How discovery changes |
|---|---|---|
| `Source-minimal relations` | Keep only the immediate operational subject(s), for example `Dispatch Package` linked to `Delivery` and `Package` but not to `Order`, and `Record Payment` linked to `Payment` and `Invoice` only. | Flattened `Order` traces become much shorter and cleaner, but cross-order logistics convergence becomes harder to see from order-centric views. The OCEL remains faithful, yet the order DFG under-expresses fulfillment progress. |
| `Balanced direct involvement` | The policy used above: logistics events link to directly implicated orders, but item links stop after packing and payments stay invoice-centric. | `Order` flattening is rich enough to show that `O100` and `O200` share `P1/D1`, while finance still preserves the ambiguity of partial settlement. This gives a good compromise between discoverability and overstatement. |
| `Full operational involvement` | Direct-link all obviously impacted business objects, including direct `Record Payment -> Order` links for both billed orders and possibly item links on delivery events. | Discovery becomes denser. `Order` traces gain payment steps and more logistics detail, but flattening copies more shared events and risks making each order look like it individually “owns” all shared operational work. DFGs become easier to read but less conservative semantically. |
| `O2O-propagated analytical relations` | Start from a sparse source model, then generate a second derived E2O layer through `contains`, `packs`, `carries`, and `bills`, clearly marked with derived qualifiers. | This can produce very informative flattened traces, including invoice/payment visibility on orders and item/package visibility on deliveries, but only if the derived layer is kept separate. If merged into observed E2O, the discovered models stop distinguishing fact from inference. |

## 7. Failure modes

| Failure mode | What goes wrong here |
|---|---|
| `Relation inflation` | If every downstream event is directly related to every reachable order, item, package, and invoice, flattenings become dominated by copied context rather than observed execution, and the discovered models overstate coupling. |
| `Missing direct E2O links` | If `e07`, `e09`, `e11`, or `e13` are not linked directly to `O100` and `O200` where intended, the order-centric perspective hides the narrative’s explicit shared behavior. |
| `Treating O2O propagation as observation` | Deriving `Payment -> Order` or `Delivery -> Item` relations through `V1` or `P1/P2` is analytically useful, but if those rows are stored as if directly observed, the provenance of the link is lost. |
| `Duplicate shared events after flattening` | Shared events such as the `P1` pack or the shared invoice appear in more than one order trace. If a reviewer forgets that flattening duplicates multi-object events by case, they can overcount work. |
| `Ambiguous payment allocation` | Linking `M1` and `M2` directly to `O100` and `O200` would imply a per-order settlement assignment that the story never provides. |
| `Overly short Payment traces` | If payments stay conservatively modeled, payment flattening becomes trivial. That is not a bug, but it can mislead analysts who expect every object type to support rich control-flow discovery. |
| `Constructor/API version mismatch` | Some PM4Py releases differ in OCEL constructor signature or visualization helper names. If this is “fixed” by changing the data model instead of isolating the API adaptation, semantic errors creep in. |
| `False total order for same-time events` | This example has no timestamp ties, but real data often does. A flattening or DFG can suggest a strict sequence that is only an artifact of row order when timestamps coincide. |
| `Reversed O2O direction` | If `V1 -> O100` is accidentally stored as `O100 -> V1`, or `D1 -> P1` as `P1 -> D1`, type-level graphs and propagation logic invert the business semantics. |
| `Broken integrity in repeated activity/timestamp columns` | If `relations` do not repeat the exact event activity and timestamp from `events`, PM4Py checks and later joins can produce inconsistent object-centric behavior even when IDs look correct. |

## 8. Final semantic checks

1. `events` should contain exactly 17 unique `ocel:eid` values, and `objects` should contain exactly 12 unique `ocel:oid` values across the six object types.
2. The `o2o` table should show that `P1` packs `I1` and `I3`, proving that one package crosses the order boundary between `O100` and `O200`.
3. The `o2o` table should show `V1 -> O100` and `V1 -> O200` with qualifier `bills`, and `M1 -> V1` plus `M2 -> V1` with settlement qualifiers, proving one invoice and two payments.
4. The relation set of `e06` should be exactly `O100`, `O200`, `I1`, and `I3`, with no package, delivery, invoice, or payment rows.
5. The relation set of `e07` should include `P1`, `I1`, `I3`, `O100`, and `O200`, making it the central shared packing event.
6. The relation set of `e11` should include `V1`, `O100`, and `O200`, while the relation sets of `e12` and `e15` should include only the payment object (`M1` or `M2`) and `V1`, not orders.
7. `O100` should participate in both logistics branches: `P1/D1` and `P2/D2`, whereas `O200` should participate only in the `P1/D1` branch before closure.
8. Every row in `relations` should carry the same `ocel:activity` and `ocel:timestamp` as its referenced event in `events`, and there should be no duplicate E2O rows.
