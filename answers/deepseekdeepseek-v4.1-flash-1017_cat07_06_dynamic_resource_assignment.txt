# 1. Objectives and constraints

**Objectives.** Assign the current queue to balance, rather than optimize only, the following goals:

1. **SLA and throughput:** reduce waiting and avoid breaches for urgent/high-priority cases.
2. **Quality and compliance:** ensure Security and Final Approval rules are respected.
3. **Continuity:** preserve case ownership where handover cost and complexity are high.
4. **Workload fairness:** avoid overloading already-loaded and high-overtime-risk resources.
5. **Skill development:** provide supervised training where SLA risk is acceptable.
6. **Resilience:** avoid making scarce specialists, especially Security and Approval, single points of failure.
7. **Explainability/auditability:** every assignment should have a recorded reason and be reconstructable from the event log.

**Hard/safety/compliance constraints**

- Skill score `0` means **not allowed**.
- **Security Review:** must be skill 3, or skill 1–2 only under explicit supervision by `R7_Gita` or `R8_Hugo`.
- **Final Approval:** finalization requires skill 2–3. Skill 1 may prepare only under a qualified final approver.
- **High-priority cases** (`urgent`, `high`) must not be assigned to skill below 2 unless a named qualified supervisor is assigned.
- Maximum **4 new primary assignments** per resource in this batch. Supervision is tracked separately but still monitored for capacity.
- **Quality Check batching** only for normal/low priority with SLA remaining >24h.
- Do **not** add routine work to `overtime risk = high` resources unless SLA risk is urgent and no safer qualified alternative exists; any exception must be recorded.
- High-complexity/high-handover cases should normally keep the current owner unless the owner has skill 0/1 and no supervision is feasible.
- No assignment may violate explicit resource authorization rules even if a queue note says “training candidate.”

**Soft preference trade-offs**

- Prefer current owner when handover cost/complexity is high.
- Prefer higher skill for urgent/complex/regulated work, but avoid specialist bottlenecks.
- Prefer lower current workload, lower overtime risk, and fair rotation.
- Prefer training assignments for documented training priorities when SLA slack is sufficient.
- Accept a controlled handover when keeping the current owner would overload a high-overtime resource or preserve a poor skill fit.

# 2. Assignment policy

**Policy name:** SLA-aware continuity-balanced supervised assignment.

**Core idea:** First filter by hard eligibility and compliance. Then score each eligible resource or supervised pair using urgency, skill match, continuity/handover cost, workload/overtime fairness, training value, and specialist-bottleneck risk. Use deterministic tie-breakers and record the main reason.

**Pseudocode**

```text
Inputs:
  queue C = {C001...C016}
  resources R with skill score, open cases, hours remaining, overtime risk, training priority
  current owner, reassignment count, complexity, handover cost band, SLA remaining, priority
  policy weights and capacity limits

For each case c:
  eligible = []
  For each resource r:
    if skill(c.required_skill, r) == 0: reject
    if r already has 4 new primary assignments: reject
    if r overtime_risk == high and c is not urgent and no explicit exception approved:
        penalize heavily / normally reject
    if c.required_skill == Security:
        if skill(c,r) == 3: eligible as primary
        elif skill(c,r) in {1,2} and supervisor in {R7,R8} available:
            eligible as supervised pair
        else: reject
    if c.required_skill == Final Approval:
        if skill(c,r) >= 2: eligible as primary
        elif skill(c,r) == 1 and qualified final approver available:
            eligible as supervised preparation pair
        else: reject
    if c.priority in {urgent, high} and skill(c,r) < 2:
        require named qualified supervisor; otherwise reject
    if c.required_skill == Quality and batch requested:
        require c.priority in {normal, low} and SLA_remaining > 24h
    if estimated service workload > capacity slack and no safe deferral:
        reject or mark high risk

  For each eligible resource/pair r:
    U = priority_weight(c.priority) * urgency(c.SLA_remaining)
        # urgency high for urgent/low remaining; lower for normal/low with long SLA
    S = skill_match = skill(c,r)/3
        # bonus if specialist needed: high complexity or Security/Approval
    H = continuity_score =
        + current_owner_bonus if r == c.current_owner
        - handover_band_penalty(high=2, medium=1, low=0.3) * c.case_complexity
        - reassignment_penalty * c.reassignment_count
    W = workload_fairness =
        - normalized_open_cases(r)
        - batch_assignment_count(r)/4
        - overtime_penalty(r)  # high very negative, medium mild, low zero
    T = training_score =
        + training_bonus if c.priority in {normal,low}
          and c.required_skill == training_priority(r)
          and skill(c,r) in {1,2}
          and supervision available if needed
          and SLA slack is acceptable
    B = resilience_score =
        - specialist_scarcity_penalty if r is a scarce Security/Approval specialist
          and the case is not urgent
        + cross_training_bonus where safe and not bottlenecking critical skills
    Score(r,c) = wU*U + wS*S + wH*H + wW*W + wT*T + wB*B

  Choose argmax Score(r,c). If supervised pair is chosen, record primary and supervisor.
  Tie-breakers:
    1. higher urgency/SLA risk
    2. lower handover cost
    3. lower current open cases and lower batch count
    4. documented training value if SLA slack
    5. deterministic rotation/resource ID to reduce bias

  If no eligible resource:
    escalate to team lead; choose least-risk compliant option with mandatory supervisor.
    Record deviation reason, approved exception, and re-evaluation time.

After draft assignment:
  Check max 4 primary assignments/resource.
  Check training share among normal/low assignments >= 20% where SLA risk acceptable.
  Check high-overtime resources have no avoidable new work.
  Check specialized bottlenecks: Security/Approval queue and supervisor load.
  Re-balance using lower-priority cases first if a hard capacity or supervision limit is breached.
```

**Exception handling.** If an urgent case has no compliant free specialist, prefer “specialist supervision + immediate takeover” over an unlogged rule violation. If a high-overtime resource must receive work, record the urgent SLA reason, the alternatives considered, and a recovery action such as reassigning a low-priority case later.

# 5. Explanation to workers

These assignments are based on a few transparent priorities. First, safety and compliance rules come before speed: Security Reviews need qualified security staff or explicit supervision, and Final Approvals must be finalized by someone authorized. Second, urgent and high-priority cases with short SLA times are protected, but we do not solve urgency by giving work to people who are already overloaded or to trainees without support.

We also try to keep cases with their current owner where changing hands would cost time or risk losing context, especially for complex cases or cases that have already been reassigned several times. Where the current owner is overloaded, we move routine work to someone with capacity and suitable skills. This is not a performance penalty for anyone; it is a way to keep the queue stable and avoid burnout.

Training assignments are real work but are paired with a qualified supervisor and checkpoints. For example, diagnosis training cases are assigned with specialist review. Some cases that look like training opportunities are not used for training because the skill matrix says the person is not authorized for that activity, even if a note mentions them. That is a compliance gap to fix through the proper authorization process, not by informally bypassing the rules.

Quality checks with normal/low priority and enough SLA time may be batched to reduce switching. If your workload changes, or if an urgent case needs immediate attention, the plan will be rechecked. Please raise capacity or safety concerns early so the team lead can adjust the assignment rather than letting an SLA or quality problem build up.

        return 0.0
    band = {"high": 2.0, "medium": 1.0, "low": 0.3}[handover_band[case]]
    return band * complexity[case] + 0.15 * reassign_count[case]

def is_eligible(case, resource, supervisor=None):
    s = skills.loc[resource, required_skill[case]]
    if s == 0:
        return False
    if required_skill[case] == "Security":
        if s == 3:
            return True
        return supervisor in ["R7_Gita", "R8_Hugo"]
    if required_skill[case] == "Final Approval":
        if s < 2:
            return supervisor is not None  # preparation only; finalizer separate
    if priority[case] in ["urgent", "high"] and s < 2:
        return supervisor is not None
    return True

def score(case, resource, supervisor=None, new_assignments=None):
    s = skills.loc[resource, required_skill[case]]
    U = urgency_score(case)
    S = s / 3.0
    H = (2.0 if resource == current_owner[case] else 0.0) - handover_penalty(case, resource)
    W = -(new_assignments.get(resource, 0) / 4.0)
    if overtime_risk[resource] == "high":
        W -= 1.5
    elif overtime_risk[resource] == "medium":
        W -= 0.5
    T = 0.0
    if priority[case] in ["normal", "low"] and required_skill[case] == training_priority.get(resource):
        if sla_remaining[case] > 6 and s in [1, 2]:
            T += 0.8
    B = 0.0
    if required_skill[case] in ["Security", "Final Approval"] and resource in ["R7_Gita", "R8_Hugo", "R6_Farid"]:
        B -= 0.4  # reserve scarce specialists unless urgent/complex
    # Weights are policy parameters, audited and tuned with historical data.
    return 3.0*U + 2.0*S + 1.5*H + 1.2*W + 0.8*T + 0.5*B
