## 2. Process-model consistency checks

A concrete validation suite should implement the following checks before explanations are served:

1.  **Prefix-Time Availability Check:**
    *   *Mechanism:* For every feature, store a `valid_after_event` metadata tag. At inference, assert `valid_after_event <= t0`.
    *   *Role:* Prevents leakage of features calculated post-prediction.
    *   *Limitation:* Does not catch mutable features without timestamps.

2.  **Activity-Order Feasibility (Footprint & Prefix Checks):**
    *   *Mechanism:* Compare the set of events in the explanation (e.g., sequence patterns) against the process footprint restricted to the prefix ending at `t0`.
    *   *Role:* Flags patterns like `Appeal -> Settlement` or `Claim Closed -> DA` as impossible.
    *   *Limitation:* A frequent edge in a DFG is not a rule; checks must use the declarative model, not just observed frequencies.

3.  **Same-Timestamp Ambiguity Resolution:**
    *   *Mechanism:* Detect events with identical timestamps in the log. Require a reliable sequence index. If missing, mark the trace as ambiguous and exclude from pattern mining or assign low confidence.
    *   *Role:* Prevents artifacts like `Claim Closed -> DA` caused by ingestion ordering errors.
    *   *Limitation:* Does not fix the root cause; requires upstream data quality improvements.

4.  **Complete-Trace Information Flagging:**
    *   *Mechanism:* Audit feature definitions. Any feature aggregating over the full trace (e.g., `total_...`, `variant_id`, `last_...`) must be flagged as `full_trace_only`.
    *   *Role:* Ensures explanations only use prefix information.
    *   *Limitation:* Requires rigorous feature cataloging.

5.  **Enabled/Impossible Activity Classification:**
    *   *Mechanism:* At `t0` (after `Coverage Check Completed`), the enabled activities are `Damage Assessment Completed` or `Documents Requested`. Any explanation referencing `Appeal`, `Settlement Decision`, `Claim Closed`, or `Fraud Investigation` as having *already occurred* is invalid.
    *   *Role:* Distinguishes between future possibilities and past facts.
    *   *Limitation:* Parallel activities (Fraud) require careful handling; if Fraud can open before `t0`, it must be in the prefix.

6.  **Repeated Settlement Decision Legitimacy:**
    *   *Mechanism:* Validate that a second `Settlement Decision Recorded` is preceded by an `Appeal` and a `Partial`/`Deny` decision.
    *   *Role:* Ensures semantic correctness of traces involving appeals.
    *   *Limitation:* Does not affect `t0` predictions, as appeals are impossible then.

## 5. Recommendations for explanation validation

1.  **Feature-Store Design:**
    *   Implement a feature store that enforces `valid_after_event` metadata. Features must be versioned with calculation timestamps.
    *   Reject any feature request that does not have a timestamp or valid-after tag.

2.  **Historical Feature Timestamps:**
    *   Store timestamps for all mutable features (e.g., `risk_score`, `handler_team`).
    *   Ensure `risk_score` is computed at event time, not extraction time.

3.  **Prefix-Only Recomputation:**
    *   Audit all SQL and feature pipelines. Replace `<= extraction_date` with `< t0`.
    *   Replace aggregate features (e.g., `total_...`) with prefix-aggregates (e.g., `count_in_prefix`).
    *   Replace `last_` features with `at_t0` or `initial_` features.

4.  **Process-Conformance Tests:**
    *   Run automated tests on explanation outputs:
        *   *Leakage Test:* Assert no feature references events after `t0`.
        *   *Feasibility Test:* Assert no sequence pattern contains events impossible in the prefix.
        *   *Timestamp Test:* Assert no pattern implies order for same-timestamp events without sequence index.
    *   Integrate these tests into CI/CD for model updates.

5.  **Calibration After Feature Removal:**
    *   Retrain models after removing leaked features.
    *   Monitor performance degradation. If performance drops significantly, investigate whether leaked features were capturing valid signals (e.g., `appeal_seen` might correlate with `risk_score` available at `t0`). Replace with valid proxies.

6.  **Explanation Stability:**
    *   Monitor SHAP/feature importance stability across time.
    *   Flag sudden shifts in importance for `calendar_week` or `queue_length` as potential drift or data quality issues.

7.  **Proxy/Fairness Analysis:**
    *   Conduct regular fairness audits on `claimant_region` and `claimant_channel`.
    *   Document proxy relationships. Ensure explanations for region do not imply causality.
    *   Provide alternative explanations for sensitive features (e.g., "Region correlates with network coverage; check repair partner SLAs").

8.  **Monitoring for Schema/Process Drift:**
    *   Monitor for changes in process variants (e.g., new evidence cycle steps).
    *   Alert if `queue_length` distribution shifts significantly, indicating capacity issues.
    *   Track `elapsed_since_registration` distribution to detect early processing bottlenecks.
