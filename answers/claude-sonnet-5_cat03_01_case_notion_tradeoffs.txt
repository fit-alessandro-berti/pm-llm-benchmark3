## 1. Analytical assumptions

**Case notion.** A "case notion" is the object type chosen to serve as the row-grouping key when the OCEL is flattened into a traditional event log (one trace per object instance of that type). Choosing a case notion is a projection decision, not a discovery of ground truth: it determines which events get merged, split, or repeated.

**Convergence.** I define convergence as: an event is related (in the E2O table) to *two or more* objects of the chosen case-notion type. When this happens, the event is copied verbatim into each of those objects' traces. Example: e13 (`Pack Package`) relates to O2 *and* O3, so flattening on Order copies e13 into both O2's and O3's traces.

**Divergence.** I define divergence as: a single object of the chosen case-notion type is related, across time, to *multiple* objects of some other type in a way that produces multiple instances of the same activity inside one trace, without a clear "which one corresponds to which" ordering. Example: O1's trace (flattened on Order) contains two `Pack Package` events (e11 for I11/P1, e12 for I12/P2) that are actually independent parallel branches, not sequential rework.

**Copied shared events: evidence, duplication, or both.** I treat them as **both**, depending on the metric. They are *evidence* that a real-world sharing/consolidation relationship exists (V2 truly bills two orders; D2 truly carries two packages). They are *duplication* the moment they are used for frequency-based metrics (activity counts, DFG edge weights, throughput) computed per flattened trace, because the same physical event is then counted once per related object, inflating totals and violating independence assumptions for any statistics computed "per order."

**Permitted transformations.** I allow, but always flag explicitly:
- **O2O relation propagation** (e.g., deriving that P3 "belongs to" {O2,O3} via `packs``contains`, or that D2 "belongs to" {O1,O2,O3} via `carries``packs``contains`) as an *analytical enrichment*, never as a silent substitute for the E2O table.
- Building **OC-DFGs, OTGs, ET-OT graphs, and object-interaction summaries** as the correct tools for questions that a single flattening cannot answer without distortion.
- Deduplicating frequency counts by underlying event id (rather than by flattened-log row) as a correction technique, not as evidence that duplication "didn't happen."

## 3. Concrete distortion analysis

1. **Cross-order package P3 (Order flattening).** e13 (`Pack Package`, O2+O3) is duplicated into both O2's and O3's traces. An Order-level DFG edge `Add ItemPack Package` is counted twice for one physical packing action. *Harmful* for volume/capacity metrics (overcounts throughput by up to 2x for O2/O3).

2. **Cross-order package P4 (Item flattening).** e14 relates to I32 and I41; it duplicates into both items' cases, as do e17 and e27. A naive count of real `Pack Package` operations (4: e11–e14) becomes 6 item-linked instances. *Context-dependent*: informative for item traceability, harmful for "how many packing operations occurred."

3. **Consolidated delivery D2 (Order vs. Delivery flattening contradiction).** Order-flattening triplicates e16/e24 into O1, O2, O3. A performance comparison "average DispatchConfirm time per order" then treats one physical shipment as three independent observations — pseudo-replication. Delivery-flattening avoids this (D2 is one clean case) but then cannot show *which* orders were affected. *Harmful* if statistical independence is assumed in the Order view.

4. **Consolidated invoice V2 (Order flattening).** e19 (`Issue Invoice`) is duplicated into O2 and O3, so Order-level `Issue Invoice` frequency = 2 for one invoice document, while Invoice-flattening (correctly) shows it once. *Harmful* only if the two counts are compared without acknowledging they measure different things ("invoices issued" vs "orders billed").

5. **Partial payment for V2 (Order flattening).** Both e22 (M2, partial) and e25 (M3, completion) are duplicated into O2's and O3's traces, producing an order-level pattern "Record PaymentRecord Payment" that appears only for O2/O3, not O1/O4. This risks the interpretive trap of concluding "O2/O3 customers are slow/partial payers," when the instalment split is a property of the *shared invoice V2*, unrelated to either order's individual behaviour. *Harmful* if used for customer-risk scoring.

6. **Near-singleton lifecycle: Payment.** Flattening on Payment gives 4 traces of length 1 (M1:e21, M2:e22, M3:e25, M4:e26), all activity `Record Payment`. `discover_dfg` returns no edges. This is not evidence of "no process variability" but an artifact of choosing an object whose only relation is to one activity type. *Harmful* if reported as "no payment process."

7. **Timing interleaving hidden by narrow flattenings.** Only the Order- or Invoice-level view shows that for O2/O3 the sequence is Pack(e13, 10:12)Dispatch(e16, 11:05)Invoice(e19, 12:05)Partial Payment(e22, 12:40)**Confirm Delivery(e24, 16:00)**Completion Payment(e25, next day 09:00)Close(e29/e30, 11:05). The completion payment occurs *after* delivery confirmation while the partial payment occurs *before* it. Delivery-only or Package-only flattenings cannot show this at all (no Invoice/Payment nodes exist there). *Informative* — this interleaving is a genuine business pattern, but only discoverable outside the narrow flattenings.

8. **Item view false process ending.** The last item-linked events are e15/e16/e17 (Dispatch) and e23/e24/e27 (Confirm Delivery); `Close Order` (e28–e31) never references any item. An Item-flattened lifecycle model would therefore define process completion at `Confirm Delivery`, hiding the fact that true closure (e.g., O2/O3 closed at e29/e30, 11:05 Feb-4) also requires the completion payment (e25, 09:00 Feb-4). *Harmful* for SLA definitions built solely on the Item view.

## 4. Traditional versus object-centric analysis portfolio

I would still build several flattened logs, each for a narrow, well-scoped purpose:

- **Order-flattened log** — safe for: order cycle time (CreateClose), presence/absence of each activity per order, coarse SLA reporting — *provided* frequency-based KPIs are deduplicated by underlying event id before aggregation.
- **Invoice-flattened log** — safe for: instalment counts, days-to-full-settlement (V2: e19e25  20h55m across 2 instalments vs V1: e18e21  30 min vs V3: e20e26  21h20m in one instalment).
- **Delivery-flattened log** — safe for: dispatch-to-confirm duration benchmarking (3 clean data points, D1/D2/D3), acknowledging n=3 is too small for statistical generalisation.
- **Package-flattened log** — safe for: pack-to-dispatch and dispatch-to-confirm timing at packaging-operation granularity, distinguishing single-order (P1,P2) from cross-order (P3,P4) packages if tagged via O2O propagation.
- **Item- and Payment-flattened logs** — not recommended as primary artefacts; useful only as attribute-lookup tables (which package held item X; what amount/date each payment carries).

Questions that require object-centric tools rather than any single flattening:

- "Which object types actually interact within `Pack Package` and `Dispatch`?"  **ET-OT graph** (shows Pack Package touches Order, Item, Package; Dispatch additionally touches Delivery).
- "How many orders does a typical delivery serve, and does that correlate with delay?"  **object-interaction summary** / **OTG** between Order and Delivery (via Package), since this cardinality is exactly what single-type flattening hides or duplicates.
- "Is the apparent 2x invoice-issuing frequency for O2/O3 a workload fact or an artifact?"  **OC-DFG with unique-object vs total-object frequency counting**, which will show `Issue Invoice` as 1 event but 2 billed objects — resolving distortion #4 directly.
- "Which case notion best captures the whole fulfilment?"  **equivalent-execution clustering** across candidate flattenings, comparing variant sets.

**Reconciliation rule:** whenever an Order-level count and an Invoice/Delivery/Package-level count disagree (e.g., "2 invoices issued" vs "1 invoice issued"), the discrepancy is resolved not by picking a winner but by reporting both alongside the object-interaction summary that explains the cardinality (V2 bills {O2,O3}). Contradictions between flattened views are treated as diagnostic signals of convergence/divergence, not as errors to eliminate.

## 5. Lead-object decision

**Position B — primary lead object (Order) plus explicit secondary lifecycles (Invoice, Delivery/Package).**

**Decision criteria:** (i) activity coverage — does the type touch all 8 activities; (ii) business relevance — is it the commercial unit stakeholders reason about; (iii) duplication cost — how much convergence-driven inflation results; (iv) lifecycle length — is the object's own trace long enough to be meaningful.

**Strongest supporting evidence:** Order is the only object type touching all 8 activities (e01–e31), giving it unmatched coverage; every other type is missing at least half the process (Item misses Create/Invoice/Payment/Close; Package/Delivery/Invoice/Payment are 2–3 activity near-singletons).

**Strongest counterargument:** Order itself suffers real convergence (9 of 31 events shared, ~35% duplication inflation) and divergence (O1's parallel P1/P2 packing), meaning even the "best" lead object systematically distorts frequency-based KPIs and introduces pseudo-replication for shared resources (D2, V2). No single object type is duplication-free *and* end-to-end.

**Residual risk:** analysts who consume only the Order-flattened DFG without correcting for duplication will overstate invoicing/payment/dispatch volume for O2, O3, O4 relative to O1 by up to 3x on shared events (e16, e24), and may misattribute instalment behaviour (M2/M3) to individual order risk profiles rather than to the shared invoice V2.

**Conditions to change this decision:** if the analytical goal is narrowly logistics-focused (shipment SLA benchmarking), switch the primary lead to Delivery or Package; if the goal is financial reconciliation/AR, switch to Invoice. If more objects with genuine multi-order/multi-package fan-out are added at scale (making Order convergence dominate the log), I would move toward Position C (reject a single lead) and require OC-DFG as the primary artifact with all flattenings as secondary lenses.

## 6. PM4Py analysis outline

```python
import pandas as pd
import pm4py

# --- basic inspection --------------------------------------------------
print(ocel)

activity_counts = ocel.events["ocel:activity"].value_counts()
print("Activity frequencies:\n", activity_counts)

otype_counts = ocel.objects["ocel:type"].value_counts()
print("Object-type frequencies:\n", otype_counts)

# --- flattenings for each candidate lead object -------------------------
lead_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flat_logs = {}
for ot in lead_types:
    flat_logs[ot] = pm4py.ocel_flattening(ocel, ot)

# per-lead-type DFG and log skeleton
dfgs = {}
skeletons = {}
for ot, log in flat_logs.items():
    dfgs[ot] = pm4py.discover_dfg(log)
    skeletons[ot] = pm4py.discover_log_skeleton(log)
    print(f"--- {ot} flattened: {len(log)} events, "
          f"{log['case:concept:name'].nunique()} cases ---")

# --- object-centric artifacts (avoid single-type distortion) ------------
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
obj_interactions = pm4py.ocel_objects_interactions_summary(ocel)

# example: inspect duplication-corrected frequency vs naive Order frequency
order_flat = flat_logs["Order"]
naive_issue_invoice_count = (order_flat["concept:name"] == "Issue Invoice").sum()
unique_issue_invoice_events = ocel.events.loc[
    ocel.events["ocel:activity"] == "Issue Invoice", "ocel:eid"
].nunique()
print("Naive per-order 'Issue Invoice' count:", naive_issue_invoice_count)
print("Unique underlying 'Issue Invoice' events:", unique_issue_invoice_events)

# clustering only justified under Position B (Order as primary + secondary lifecycles)
equivalent_clusters = pm4py.cluster_equivalent_ocel(
    ocel, object_type="Order"
)
print("Equivalent-execution clusters (Order-led):", equivalent_clusters)
```

## 7. Sensitivity and validation plan

1. **Down-weight/remove copied shared events.** Recompute Order-level activity frequencies and DFG edge weights after deduplicating by `ocel:eid` for e13, e14, e16, e17, e19, e22, e24, e25, e27, and compare against the naive per-case counts (e.g., naive `Issue Invoice` = 4 events across O1–O4 traces vs 3 unique underlying events e18/e19/e20).

2. **Direct E2O vs propagated O2O relations.** Re-flatten Package and Delivery after explicitly propagating Order identity through `contains``packs``carries` (e.g., attach {O2,O3} to P3, {O1,O2,O3} to D2) and compare the resulting OC-DFG/ET-OT graphs to the non-propagated versions to quantify how much order-context is recoverable versus genuinely lost.

3. **Lead-object substitution.** Rerun the full analysis with Delivery, then Invoice, as the case notion instead of Order; compare resulting variant counts and mean cycle times (e.g., Delivery gives 3 trivial 2-event variants vs Order's richer but duplicated variants) to test whether conclusions about "process performance" are stable across the choice.

4. **Event- vs unique-object vs total-object frequency in the OC-DFG.** For edges touching e16/e24 (D2, 3 orders) and e13/e19/e22/e25 (V2, 2 orders + 2 payments), compare `discover_ocdfg` frequency annotations computed as (a) number of events, (b) number of unique related objects, (c) total object references, to confirm which metric drives the apparent 2–3x inflation identified in Section 3, and document which metric is appropriate for which stakeholder question (finance vs logistics vs customer service).
