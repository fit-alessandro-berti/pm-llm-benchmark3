## 1. Analytical assumptions

- **Case notion.** A "case" is the set of events whose E2O relations directly reference a chosen object instance, treated as that object's lifecycle. The case identifier is the object id, the trace is the chronologically ordered activity sequence over that object, and case-level metrics (throughput, frequency, variants) are computed within that trace population.

- **Convergence.** Convergence occurs when multiple higher-level business units are funneled into a single lower-level object instance (e.g., O2 and O3 both feed into P3; O1, O2, and O3 all ride D2). In a flattening this manifests as multiple cases sharing a single downstream event, which under naive flattening produces *copies* of that event rather than a true merge.

- **Divergence.** Divergence occurs when one higher-level unit is split across multiple lower-level objects (e.g., O1 splits into P1 and P2; O3 splits into P3 and P4). In a flattening this scatters one case's events across sibling traces that the analyst must reconcile by E2O set intersection or timestamp alignment.

- **Copied shared events.** I treat each copy simultaneously as **evidence** (the activity genuinely co-occurs with each referenced object — e16 truly does involve O1, O2, and O3) **and as duplication** (the activity executed once in calendar time, so counting its repetitions over-states throughput). Both interpretations must be visible in any reporting.

- **Permitted analytical transformations.** I will (a) consider direct E2O flattening, and (b) consider an explicit *propagated* variant in which O2O links (e.g., O1I11P1D1) are used to enrich an object's related-object set, but only as a sensitivity check. I will not silently propagate relations in the primary matrix.

## 3. Concrete distortion analysis

The DFG edge "Pack Package  Dispatch" then has a frequency 3× its true calendar count, biasing any performance or variant ranking toward "Order with multi-order dispatch". This is informative (the convergence is real) but numerically inflated; treat as evidence+duplication.

2. **Triplicated confirmation of D2 (Order flattening).** e24 is a near-copy of e16, again in three order cases. Combined with e16, the "Dispatch  Confirm Delivery" edge for the O1, O2, O3 trio is over-counted by a factor of three relative to ground truth. The effect is harmful for cycle-time estimation but informative for cross-order consolidation analysis.

3. **Cross-order packing of P3 (Package and Order flattening).** e13 directly references O2 and O3. In Order flattening it shows up in both cases; in Package flattening it appears once but its case (P3) has no direct knowledge of which order each item belongs to without O2O propagation. If propagation is silently enabled, the analyst overstates the cross-order signature; if disabled, P3 looks like a single-order pack. Both are traps — explicit propagation is the only honest path.

4. **Cross-order packing of P4 (Package and Order flattening).** e14 relates to O3 and O4. Same structural trap as P3, but compounded by the **next-day delivery**: P4 is dispatched on 2026-02-03 11:15 (e17) but confirmed on 2026-02-04 10:00 (e27). 5. **Consolidated delivery D2 (Delivery flattening).** D2 has only two events (e16, e24). Its entire "lifecycle" is dispatch and confirm — no creation, no closure. Treating D2 as a case yields a trace of length 2 that nevertheless encodes the most strategically important consolidation point in the process. ## 4. Traditional versus object-centric analysis portfolio

- **Order flattening (kept as one of several).** Safe for: order-level conformance against a happy-path lifecycle (CreateAddPackDispatchConfirmPayClose); order throughput and abandonment. Unsafe for: cross-order consolidation, partial payments, shipment-level efficiency.
- **Item flattening (kept).** Safe for: SKU-level physical flow, exception detection per item (e.g., I32 vs I31 split delivery). Unsafe for: anything financial.
- **Package flattening (kept).** Safe for: warehouse consolidation (P3/P4 signatures), pack efficiency. Unsafe for: financial close and order-level closure.
- **Delivery flattening (kept only with caveats).** Safe for: trip-level routing patterns and on-time performance. Unsafe for: anything requiring pre-shipment context — pair with ET-OT.
- **Invoice flattening (kept — high value).** Safe for: payment compliance, partial-payment detection (V2 is unique), dunning logic. Unsafe for: physical flow.
- **Payment flattening (discarded as primary; useful only as a sanity check).** Safe for: payment timing dashboards. Unsafe for: any sequential analysis.

Questions that require OC-DFG or OTG: cross-order consolidation patterns (e13, e14, e16, e24), the V2 partial-payment pathway, the divergence of O1/O3 into multi-package fulfillment. Use `pm4py.discover_otg` and `pm4py.discover_etot` to make these explicit. Use `pm4py.objects_interactions_summary` to rank (Order, Package) and (Order, Delivery) as the dominant interaction pairs.

## 5. Lead-object decision

**Position B — use a primary lead object plus explicitly secondary lifecycles.**

- **Decision criteria.** (i) Coverage of all six activity classes (Create, Add, Pack, Dispatch, Issue, Pay, Confirm, Close); (ii) ability to expose convergence *and* divergence without silent duplication; (iii) ability to support end-to-end throughput from order creation to closure; (iv) ability to remain non-degenerate for at least 80% of cases.
- **Strongest supporting evidence.** Order is the only object type whose flattened traces contain all activity classes and whose lifecycles are non-singleton for all four instances (O1–O4). The financial branch (e18e21e28 for O1; e19e22e25e29/e30 for O2/O3; e20e26e31 for O4) and the physical branch (AddPackDispatchConfirm) both terminate in Close events (e28–e31) that reference the order directly. Order is therefore the most defensible *primary* lifecycle for end-to-end analysis.
- **Strongest counterargument.** Order flattening systematically over-counts cross-order events: e13, e14, e16, e17, e19, e22, e24, e25, e27 are each duplicated at least twice. e16 and e24 are triplicated. This biases DFG frequency statistics and creates phantom "multi-order dispatch" variants. A naïve analyst who leads on Order will reach wrong conclusions about the *frequency* of consolidated events even if the *set* of events is correct.
- **Residual risk.** The V2 partial-payment pattern is materially under-represented in Order flattening — both payment events appear in two order cases, producing the illusion of two separate partial-payment cycles rather than one partial-then-complete cycle. This cannot be reconciled without secondary Invoice analysis.
- **Conditions to change to Position C.** If the analytical goal is dominated by cross-order consolidation (e.g., "how often do we ship multiple orders together?") or by financial compliance (partial payments, consolidated billing), then Order is no longer a sufficient lead and a full object-centric posture becomes necessary. If a fifth order were added with zero shared events, Order would also become more attractive as a single lead; here the share rate (3 of 4 orders participate in cross-order packages and deliveries) is high enough to disqualify Option A.

## 7. Sensitivity and validation plan

1. **Copied-event down-weighting.** For the Order flattening, recompute DFG frequencies with weights of 1/k where k is the number of distinct Order objects referenced by the event (e.g., e16 contributes 1/3 to each of O1, O2, O3). Compare with the unweighted DFG; if the top-3 edges change substantially (e.g., DispatchConfirm loses its inflated rank), the bias is real and should be reported.

2. **Direct vs propagated E2O.** Build a variant OCEL where each event's object set is enriched by walking O2O links once (e.g., e05 inherits I11P1, V1, D1, M1 through containment/packing/carrying/billing/settling). Re-run `discover_ocdfg` and `discover_etot`. The propagation variant makes convergence "inherited" rather than "directly observed"; the diff between the two variants is a quantitative measure of how much the original OCEL understates convergence.

3. **Lead-object swap.** Re-run the full pipeline (flattening  DFG  skeleton  OC-DFG comparison) with Invoice as the lead object instead of Order. The Invoice flattening uniquely surfaces the V2 partial-payment variant; the diff in discovered variants between Order and Invoice leads is a direct quantification of what each lead hides about the other.

4. **Frequency metric basis.** For each event, compute three counts: (a) raw calendar frequency (1 for all events); (b) case frequency under Order flattening (1–3 depending on shared references); (c) total object references (sum over E2O tuples). Plot or tabulate the ratio (b)/(a) and (c)/(a). Events with ratio  2 (e13, e14, e16, e17, e19, e22, e24, e25, e27) are flagged as convergence points. This produces an explicit convergence map and validates the qualitative claims in §3.

5. **Lifecycle completeness audit.** For each object instance, verify that its flattened trace contains at least one event from each business phase (Create, Add, Pack, Dispatch, Issue, Pay, Confirm, Close) where applicable. D1, D2, D3 will fail at Create/Close; M1–M4 will fail everywhere except Pay. Document the failure modes as evidence against Payment and Delivery as lead candidates.

6. **Temporal gap check on P4/D3.** Compute the pack-to-confirm interval for P4 (e14 10:20  e27 next-day 10:00 = 23h40m) and compare against P1, P2, P3 (all  6h). The outlier is informative about next-day delivery routing and validates the §3 trap #4.

7. **Variants under different flattenings.** Enumerate trace variants in `log_order`, `log_invoice`, `log_package`, `log_delivery`. The Invoice flattening should yield exactly three variants (V1, V2, V3), with V2's variant being the only one containing two Record Payment events. The Order flattening should yield four variants (one per order) but with overlapping event subsequences that look like additional variants in a naive directly-follows analysis.
