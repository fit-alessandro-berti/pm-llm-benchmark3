## 1.2 Conflicts found in the statements

1. **R5 against R6 (direct conflict).**
   - R5 says the opinion must precede activation "under all circumstances".
   - R6 allows activation before the opinion under an emergency.
   - The emergency condition (joint authorization outside the log) cannot be seen in the log.
2. **R6 is undecidable from the event log.** The log has no `emergency` attribute and no authorization record.
3. **R12 against R6 (soft overlap).**
   - An emergency activation with a legitimately late opinion will often trigger the EscalationOpinion temporal warning.
   - R6's 24-hour window is measured from activation, while the R12 band is measured from escalation.
   - The two are not contradictory, but they must be reported as separate findings.
4. **R10 against R11.** `Verify Bank Account` must be allowed twice (re-verification), while `Release First Payment` stays at most once.
5. **R3 against R11.** R3 says "before any final outcome". If clarifications could occur after activation, the `nonsuccession(Activate Vendor, Receive Clarification)` approximation would be wrong.
6. **R2 against T8.** T8 has an approval, an activation, a rejection and a close. The backbone says "Close follows either rejection or payment", so T8 is internally contradictory.
7. **R2 and R8 overlap.** R8 repeats part of R2 and is phrased as "should".

| Option | Rule | Advantage | Compliance risk |

| **A. Legal supremacy (strict)** | R6 is not honoured. | **B. **Implemented choice: A as the default profile (`STRICT`).** B is provided as a separately named profile (`EMERGENCY_EXCEPTION`). It is never applied silently: the `policy_profile` parameter must be set explicitly per run. The procedural tree deliberately permits both orderings, because it is the union of the two policies. The choice between them is made only in DECLARE (by including or removing one rule) and in the layer-7 check.

**Risk of choosing A.** Emergency cases will be reported as violations. The risk is false positives and pressure to bypass the system, not false acceptance. If governance later selects B, the `nonsuccession(Activate Vendor, Obtain Legal Opinion)` rule must be removed **together with** enabling the 24 h and authorization check. Removing it alone makes R4 toothless as a timing control.

# 3. Procedural Backbone

## 3.1 Compact formal description

Notation: `` sequence, `` parallel, `×` exclusive choice, `(do, redo)` loop, `` silent step.

```
( Receive Onboarding Request,
   ( Capture Master Data, Run Sanctions Screening, Verify Bank Account ),
   ( , ( Request Clarification, Receive Clarification ) ),
   Classify Risk,
   ( ×( , ( Sanctions Escalation, Obtain Legal Opinion ) ),
      ×( Reject Vendor,
         ( ×( Manager Approval,
               ( Enhanced Due Diligence, Compliance Approval ) ),
            Activate Vendor, Release First Payment ) ) ),
   Close Onboarding )
```

## 3.2 PM4Py code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def _leaf(label=None):                      # label=None -> silent tau
    return ProcessTree(label=label)

def _node(operator, *children):
    n = ProcessTree(operator=operator)
    for c in children:
        c.parent = n
        n.children.append(c)
    return n

SEQ, XOR, AND, LOOP = (Operator.SEQUENCE, Operator.XOR,
                       Operator.PARALLEL, Operator.LOOP)

checks = _node(AND,
               _leaf("Capture Master Data"),
               _leaf("Run Sanctions Screening"),
               _leaf("Verify Bank Account"))

# zero or more clarification cycles: do = tau, redo = Request -> Receive
clarification_loop = _node(LOOP, _leaf(),
                           _node(SEQ, _leaf("Request Clarification"),
                                      _leaf("Receive Clarification")))

# optional legal sub-flow, concurrent with the outcome branch
legal_optional = _node(XOR, _leaf(),
                       _node(SEQ, _leaf("Sanctions Escalation"),
                                  _leaf("Obtain Legal Opinion")))

low_route  = _leaf("Manager Approval")
high_route = _node(SEQ, _leaf("Enhanced Due Diligence"), _leaf("Compliance Approval"))

accepted = _node(SEQ,
                 _node(XOR, low_route, high_route),
                 _leaf("Activate Vendor"),
                 _leaf("Release First Payment"))

outcome = _node(XOR, _leaf("Reject Vendor"), accepted)

procedural_model = _node(SEQ,
                         _leaf("Receive Onboarding Request"),
                         checks,
                         clarification_loop,
                         _leaf("Classify Risk"),
                         _node(AND, legal_optional, outcome),
                         _leaf("Close Onboarding"))

# Derived artefact for alignments / token replay:
# net, im, fm = pm4py.convert_to_petri_net(procedural_model)
```

## 3.3 Explanation

- **Concurrency.**
  - The three checks are fully concurrent. T1–T3 show three different orders, and all are accepted.
  - `Classify Risk` follows the AND-join, which gives "requires all three".
  - The legal sub-flow is in an AND with the outcome branch. This is the approximation: the block-structured tree cannot express "Escalation after screening, Opinion before or after activation but before Close" any more tightly.
  - As a result the tree accepts both T6 (opinion after activation) and T7 (opinion before activation). It is deliberately neutral between R5 and R6, and the policy layers decide.
  - Side effects of this concurrency: an escalation could be placed after activation, or after rejection. DECLARE `STRICT` catches the harmful variants. The tree does not.
  - The tree forces the opinion to occur before `Close Onboarding`.
- **Choices.** The outcome is a single XOR between Reject and accepted. Accepted has the low route (Manager Approval) or the high route (EDD then Compliance Approval). Activation and first payment follow the chosen approval. Because the choice sits inside one XOR, R1, R2 and R8 hold structurally. The tree does not check that the route matches the risk class, which is an attribute (A10).
- **Clarification loop.** The loop is placed between the AND-join of the checks and `Classify Risk`. It allows any number of Request/Receive cycles, and each cycle is closed before the next begins. This enforces R3's "before the next request" and "before any final outcome" structurally. T5 does not replay because the loop's redo part requires a `Receive Clarification` after each `Request Clarification`.
- **Terminal outcomes.** `Close Onboarding` follows the AND-join. It comes after rejection or after the first payment, and only there.
- **Post-activation behaviour: deliberately excluded.**
  - `Change Bank Details` and `Suspend Vendor` are not in the tree. R11 would need a second `Verify Bank Account` and a `Release First Payment` whose position depends on the change, which is hard to express without inventing policy (for example, whether payment may follow suspension).
  - A trace containing them is reported by the tree as "outside backbone". R11 is enforced in DECLARE and layer 7, not in the tree.
  - An extension would add `×(, (Change Bank Details, (Suspend Vendor, Verify Bank Account)))` after `Activate Vendor`, plus a way to order Release after the re-verification.

| Template | Key | Semantics and direction | Requirement |
|---|---|---|---|
| init | Receive Onboarding Request | Every trace starts with it. | Backbone 1 |
| exactly_one | Receive, Classify Risk, Close | Each occurs exactly once. | A11 |
| existence | Capture, Screening, Verify | Each occurs at least once. | Backbone 2 |
| response | (Sanctions Escalation, Obtain Legal Opinion) | Every Escalation is eventually followed by an Opinion. An Opinion without Escalation is allowed by this rule alone. | R4 |
| response | (Change Bank Details, Suspend Vendor) | Every Change is eventually followed by a Suspend. Unconditional, so conservative. | R11 |
| altresponse | (Request, Receive Clarification) | Every Request is followed by a Receive, with no other Request in between. | R3 |
| precedence | (Run Sanctions Screening, Sanctions Escalation) | An Escalation needs an earlier Screening. Screening without Escalation is fine. | R7 |
| precedence | (Sanctions Escalation, Obtain Legal Opinion) | An Opinion needs an earlier Escalation (A4). With the response rule it forms a succession. | A4 |
| precedence | (Activate Vendor, Release First Payment) | A payment requires an earlier activation. Activation without payment is allowed (for example after suspension). | Backbone 5 |
| precedence | (EDD, Compliance Approval) | A Compliance Approval needs an earlier EDD. | Backbone 4 |
| precedence | (Classify Risk, Reject Vendor) | A rejection needs an earlier classification. | Backbone 4 |
| altprecedence | (Request, Receive Clarification) | Every Receive has a matching earlier Request and no other Receive in between. Together with altresponse this is an alternating succession. | R3 |
| noncoexistence | (Reject, Activate) | The two never both occur, in any order. | R1 |
| noncoexistence | (Reject, Manager) and (Reject, Compliance) | A rejected case has no approval. | R2 |
| noncoexistence | (Manager, Compliance) | Not both approvals. | R2, R8 |
| noncoexistence | (Manager, EDD) | Manager Approval and EDD never co-occur. | R8 |
| nonsuccession | (Activate Vendor, Obtain Legal Opinion) | After an activation there is never an Opinion, at any distance. With R4 and A4 this means "the opinion precedes activation". | R5 |
| nonsuccession | (Activate, Receive Clarification) and (Reject, Receive Clarification) | No clarification response after a final outcome. With altresponse this closes every request before the outcome. | R3 |

**Template distinctions used in the design.**

- **Response against precedence.**
  - `response(A,B)` constrains what follows A.
  - `precedence(A,B)` constrains what comes before B.
  - Escalation and Opinion use both. Using only one of them changes the meaning.
- **Alternate response against chain response.**
  - `altresponse` only forbids a second Request before the Receive. Other events may lie in between.
  - `chainresponse` would require the Receive to be the very next event. That is too strong, because other activities are allowed between a request and its response (for example the legal sub-flow, or concurrency in an extension), so it is not used.
- **Noncoexistence against nonsuccession.**
  - `noncoexistence(Reject, Activate)` forbids both orders.
  - `nonsuccession(Reject, Activate)` would forbid only "Reject then Activate". It would miss T8, where Activate comes first.
  - `nonsuccession` is used only where order matters: Opinion after Activate, and Receive Clarification after an outcome.
  - `nonchainsuccession` (only the immediate successor is forbidden) is not used, because it is too weak for R5.
- **Not encoded.**
  - R10's "at most once" (`absence2` is not in the allowed list).
  - "An approval exists if Activate occurs".
  - R11's "Verify between Change and Release".
  - R6's emergency condition.
  - These are placed in the Log Skeleton, the tree and layer 7.

**Orientation.** I assume PM4Py's convention: `always_before (a, b)` means "if a occurs, b occurred before it". `always_after (a, b)` means "if a occurs, b occurs after it". Verify this on a toy log for your PM4Py version. `equivalence` and `never_together` are symmetric, so orientation does not matter. `activ_freq` lists every activity, because PM4Py versions differ in how they treat unlisted activities.

**Overlap and disagreement with the other layers.**

- **Overlap with DECLARE.** R1, R2 and R8 (`never_together`), R3 and R4 (`equivalence`, `always_after`), and R7 (`always_before`) are repeated. The Log Skeleton is weaker on R3: it only checks counts and eventual follow-up, not alternation or closure before the outcome.
- **Overlap with the tree.**
  - The always-before pairs restate the backbone order.
  - A few pairs are deliberately omitted because they become wrong under the post-activation extension. An example is `always_after(Verify Bank Account, Classify Risk)`, which fails when a re-verification follows the change.
- **Disagreement with the tree.**
  - `Verify Bank Account` allows `{1, 2}`, but the tree only allows 1.
  - `Change Bank Details` and `Suspend Vendor` are legal here but outside the tree.
  - The tree accepts unbounded clarification cycles, while the skeleton cuts off at 5. A sixth cycle is a skeleton violation and not a tree or DECLARE violation.
- **R10 is authoritative here.** DECLARE has no at-most-once template in the allowed list.
- **R5 and R6 are not expressed.** The Log Skeleton has no conditional ordering, so T6 passes this layer. That is a blind spot, not agreement.
- **`directly_follows` is empty.** With the concurrent checks, the optional legal sub-flow and the post-activation extension, almost no pair is always adjacent. For example, `Release First Payment` is not always directly followed by `Close Onboarding`, because an emergency opinion can land in between. `Request Clarification  Receive Clarification` is adjacent in the tree, but R3 does not require adjacency, so encoding it would over-constrain.

# 6. Temporal Profile

```python
H = 3600  # seconds per hour
zeta = 2.0

temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * H, 24 * H),  # (172800, 86400)
    ("Sanctions Escalation", "Obtain Legal Opinion"):   (12 * H, 6 * H),   # (43200, 21600)
    ("Activate Vendor", "Release First Payment"):       (72 * H, 36 * H),  # (259200, 129600)
}
# pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)
```

Flag rule: `|  | > ·`.

| Pair | Acceptance window ( ± 2) |
|---|---|
| Request  Receive Clarification | 0 h – 96 h |
| Escalation  Opinion | 0 h – 24 h |
| Activate  Release | 0 h – 144 h |

The lower bounds are negative and therefore unreachable. In practice only "too slow" flags occur.

**Why warnings and not control-flow violations.**
- R12 says the expectations are "normative enough to flag but not automatically reject".
- The profile measures elapsed time between eventually-follows pairs. It has no notion of whether the control flow is legal.
- A late opinion (T7) is a risk signal, not a breach of order. Promoting it to a failure would mix soft statistical deviation with hard policy.
- The orchestrator therefore maps every temporal deviation to `warning`, and never overrides a pass or fail from another layer.
- Emergency activations (R6) will often flag here, because up to 24 h after activation can exceed 24 h after escalation. This is expected and is reported as a separate finding.

def build_df(tests):
    rows = []
    for cid, s in tests.items():
        for tok in s.split(", "):
            act, hr, res = re.fullmatch(r"(.+)@([\d.]+)\[(.+)\]", tok).groups()
            rows.append({CASE: cid, ACT: act, RES: res,

# ---------- R9: segregation of duties ----------
def check_sod(df, left, right):
    if RES not in df.columns:
        return {c: "not evaluated" for c in df[CASE].unique()}
    df = df.assign(**{RES: df[RES].astype("string").str.strip().str.casefold()})
    out = {}
    for cid, g in df.groupby(CASE):
        L, Rt = g[g[ACT].isin(left)], g[g[ACT].isin(right)]
        if L.empty or Rt.empty:
            out[cid] = "pass"                                  # rule not triggered
        elif set(L[RES].dropna()) & set(Rt[RES].dropna()):
            out[cid] = "fail"                                  # definite equality
        elif L[RES].isna().any() or Rt[RES].isna().any():
            out[cid] = "not evaluated"                         # unknown identity
        else:
            out[cid] = "pass"
    return out

def check_R11(df):

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement across layers.**
  - R1, R2, R3, R4, R7 and R8 are each enforced by up to three layers.
  - One defect (T5, T8) therefore produces several alerts.
  - The orchestrator must group findings by requirement ID and layer, and display one root cause with supporting layers. Otherwise counts and dashboards overstate the problems.
  - Redundancy is also useful: it is how a blind layer (for example the Log Skeleton on T6) gets cross-checked.
- **Inconsistency under loops and post-activation changes.**
  - `Verify Bank Account` must allow 1–2 occurrences (R11), but the tree allows one. The layers disagree.
  - A constraint such as `always_after(Verify Bank Account, Classify Risk)` would fail on a legitimate re-verification, and was omitted for that reason.
  - Temporal-profile pairs are eventually-follows pairs, so a second clarification cycle creates cross-cycle pairs (RequestReceive) that can give spurious warnings.
  - `nonsuccession(Activate, Receive Clarification)` assumes no clarification after activation. A clarification triggered by a bank-detail change would clash with it.
  - The Log Skeleton's cap of 5 clarification cycles is arbitrary, unlike the unbounded tree.
  - R9's "applicable approval" compared with a re-verification performed after approval is ambiguous. The implementation conservatively compares all Verify events.
  - R5 is also ambiguous when an escalation occurs after activation. DECLARE `STRICT` is stricter than the literal reading.
- **Vacuity in declarative rules.**
  - `response(Sanctions Escalation, …)`, `nonsuccession(Activate, Obtain Legal Opinion)`, `precedence(…)` and the R8 pairs are all satisfied in traces where their activation condition never occurs.
  - T3 "passes" R4, R5, R7 and R9 without evidence.
  - The PM4Py conformance output does not distinguish vacuous from non-vacuous satisfaction.
  - Anchor rules (`existence`, `exactly_one`, `init`) limit vacuity for the backbone, and the verdict explanations should state when rules were not triggered.
- **Missing case attributes.**
  - Without `org:resource`, R9 is `not evaluated`, never `pass`.
  - Without `emergency:*` attributes, R6 cannot be verified.
  - Without `risk_class`, the low-/high-route match is invisible.
  - Without a `policy_profile`, the user must choose A or B explicitly.
  - Resource identity (aliases, shared accounts, role against person) is also unmodelled.
- **Timestamp-only limitations.**
  - Ties and clock skew between source systems can invert an "opinion before activation" verdict.
  - The 24 h window is wall-clock and does not account for business hours or time zones.
  - Only completion timestamps are present, so waiting time and working time are conflated.
  - The R6 clock uses the activation timestamp, which may differ from the moment the decision was made.
  - A missing event (an unanswered clarification) produces no temporal signal at all.
- **Risk of treating support/confidence as normative truth.**
  - In the authored model, `support = 1.0` and `confidence = 1.0` are declarations of intent and not measurements.
  - If the same structure were discovered from a log, the values would describe how often behaviour occurred, including non-compliant behaviour.
  - A rule with high discovered confidence can encode a common violation.
  - A rule with lower confidence can still be mandatory.
  - The PM4Py conformance checker does not use these values to weight violations. Treat them as metadata only.
- **Other blind spots.**
  - R6 cannot be decided from the log in any profile.
  - Escalation could occur before `Classify Risk`, but the tree forbids that placement (A4).
  - R5's conflict with R6 is a governance question that no formalism can settle.

# 10. Deployment Recommendation

**Canonical procedural representation.**
- Use the block-structured process tree in section 3.
- Convert it to a Petri net only for alignment diagnostics.
- The tree describes the intended flow and is deliberately permissive where policy differs (legal sub-flow timing).
- It is the canonical description for discovery comparison, simulation and explanation. It is not the authority on policy.

**Authoritative policy layers.**
- DECLARE is authoritative for the control-flow policy rules (R1, R3, R4, R5, R7, R8, R11a), with the strict profile as default.
- Layer 7 is authoritative for R2 (count), R6, R9 and R11b.
- The Log Skeleton is authoritative for R10 only. It is otherwise a cross-check.
- The temporal profile is authoritative for R12, as warnings.

**Order of checks.**
1. Schema and attribute completeness. Which attributes exist? Flag `not evaluated` early rather than defaulting to pass.
2. Log Skeleton (cheap, catches cardinality and exclusion errors, including R10).
3. DECLARE with the declared policy profile.
4. Resource/data layer (R2, R5/R6 profile logic, R9, R11b, risk route).
5. Procedural alignments. They are expensive, so run them last for diagnosis: they locate the deviation and explain it, and they never override a policy verdict.
6. Temporal profile on cases without control-flow failure. Its pair statistics are only meaningful for well-formed cases.

**Surfacing contradictory findings.**
- Do not average or majority-vote. Show a per-requirement table: requirement ID, layer, status, earliest decisive event, and whether that layer is authoritative for the requirement.
- Mark disagreements explicitly. Example for T6: "Log Skeleton pass, DECLARE fail: the Log Skeleton cannot express conditional ordering".
- Classify findings by severity: hard failure (R1–R5, R7–R11), `policy-dependent` (R5/R6, missing evidence) and `warning` (R12).
- Report `policy-dependent` with its prerequisite ("supply joint authorization and an opinion within 24 h"), and never as pass.
- Record the active profile (`STRICT` or `EMERGENCY_EXCEPTION`) in every report, so an audit can tell which policy was applied.
- Escalate the R5/R6 conflict to the business owner for a documented decision. The longer-term fix is to log emergency authorization as explicit attributes at the source (option C).
