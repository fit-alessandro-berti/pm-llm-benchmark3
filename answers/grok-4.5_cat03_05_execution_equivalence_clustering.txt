## 1. Equivalence design space

### 1.1 Activity-sequence equivalence
**Definition.** Two executions are equivalent iff the ordered sequences of activity labels are identical. Object identifiers, types, multiplicities, E2O incidence, and O2O relations are ignored.

**Invariants preserved.** Total order of activity names.

**Information discarded.** All object structure, sharing, qualifiers, and cardinalities.

**Properties.** Reflexive, symmetric, transitive (equality on strings/lists).

**Concurrency.** Same-time events would be ordered by a fixed tie-break (e.g., activity name sort) before comparison; true partial orders are linearized.

### 1.2 Typed structural equivalence under identifier renaming
**Definition.** Executions \(E, E'\) are equivalent iff there exists a type-preserving bijection \(\rho\) on object identifiers (local IDs freely renamed; `EXT-*` flags must map to `EXT-*`) such that:
- the sequences of (activity, multiset of (type, renamed-id) pairs) coincide;
- O2O incidence edges coincide after \(\rho\), ignoring qualifier labels unless they alter incidence.

**Invariants preserved.** Activity order; object types; per-event E2O multiplicities; local vs external distinction; connectivity of the O2O graph.

**Information discarded.** Concrete local IDs; Add-Item ordering of sibling items when only IDs differ; soft qualifier text that does not change edge presence.

**Properties.** Reflexive, symmetric, transitive (isomorphism).

**Concurrency.** Linearization as in 1.1, or optionally compare canonical partial orders of events under object-lifecycle causality; here we use the given total order.

### 1.3 Business-semantic equivalence
**Definition.** Equivalence on a canonical business signature built from:
- logistics motif: single-pack / split-pack-consolidated-delivery / split-pack-split-delivery / shared-pack-with-external / return-repack / substitution-before-dispatch;
- finance motif: single-settle / multi-payment / shared-invoice-with-external;
- isolation: whether any E2O/O2O touches `EXT-*`;
- lifecycle extras: return/inspect/repack; replacement/removal qualifiers;
- multiplicities of Package, Delivery, Payment relative to Items and Invoice.

Two executions are equivalent when these motif vectors match after local ID renaming. Exact activity-string identity is not required if the motif is the same (e.g., item add order).

**Invariants preserved.** Business pattern of fulfillment, settlement, and isolation/sharing.

**Information discarded.** Local IDs; immaterial event interleavings that do not change motif (e.g., which item ID was added first); absolute timestamps.

**Properties.** Reflexive, symmetric, transitive by construction on finite discrete signatures.

**Concurrency.** Pack/Dispatch pairs may be treated as a partial order when assessing split vs consolidated logistics; payment order is ignored if only multiplicity matters.

### 1.4 (Optional) Qualified-relation equivalence
Finer than 1.2: same as typed structural equivalence but O2O qualifier labels (`partially_settles`, `removed_before_dispatch`, `replaces`) are part of the isomorphism key. Used only to separate X7 from the baseline when structure alone looks similar.

## 2. Canonical signatures

Preferred relation: **business-semantic equivalence** (1.3).

```python
def canonical_signature(exec):
    # 1. Rename local objects per type by first-appearance order: T1, T2, ...
    #    Keep EXT-* as EXT and record foreign types touched.
    objs = rename_locals_preserve_ext(exec)

    # 2. Multisets of object counts by type (Order always 1 as lead)
    mult = counts_by_type(objs)  # e.g. Item:2, Package:1, Delivery:1, ...

    # 3. Logistics motif
    packs = events(exec, "Pack Package")
    disps = events(exec, "Dispatch")
    rets  = events(exec, "Return Item") + events(exec, "Inspect Return")
    if rets:
        log_motif = "RETURN_REPACK"
    elif has_qualifier(exec, "removed_before_dispatch") or has_qualifier(exec, "replaces") \
         and "Item" in dispatch_e2o_types(disps):
        log_motif = "SUBSTITUTION_BEFORE_DISPATCH"
    elif any_ext_on(packs) or any_ext_on(disps):
        log_motif = "SHARED_PACKAGE_CROSS_ORDER"
    elif len(packs) == 1 and len(disps) == 1:
        log_motif = "SINGLE_PACK_SINGLE_DELIVERY"
    elif len(packs) > 1 and len(disps) == 1:
        log_motif = "SPLIT_PACK_CONSOLIDATED_DELIVERY"
    elif len(packs) > 1 and len(disps) > 1:
        log_motif = "SPLIT_PACK_SPLIT_DELIVERY"
    else:
        log_motif = "OTHER_LOGISTICS"

    # 4. Finance motif
    inv = events(exec, "Issue Invoice")
    pay = events(exec, "Record Payment")
    if any_ext_on(inv) or any_ext_on(pay):
        fin_motif = "SHARED_INVOICE_CROSS_ORDER"
    elif len(pay) > 1 or has_qualifier(exec, "partially_settles"):
        fin_motif = "MULTI_PAYMENT"
    else:
        fin_motif = "SINGLE_PAYMENT"

    # 5. Isolation flag
    isolated = not touches_ext(exec)

    # 6. Activity skeleton (optional secondary key): labels only, sorted concurrent ties
    skeleton = tuple(e.activity for e in exec.events)

    return {
        "mult": mult,
        "logistics": log_motif,
        "finance": fin_motif,
        "isolated": isolated,
        # skeleton not required for cluster id but kept for audit
        "skeleton": skeleton,
    }

def cluster_id(sig):
    return (sig["logistics"], sig["finance"], sig["isolated"],
            sig["mult"].get("Package"), sig["mult"].get("Delivery"),
            sig["mult"].get("Payment"), sig["mult"].get("Item"))
```

This is invariant to local renaming, preserves types, multiplicities, externality, E2O-derived motifs, O2O qualifiers that encode substitution/partial settlement, and repeated activities via counts.

## 4. Cluster interpretations

### SEM-BASE (X1, X2)
**Signature.** Single pack, single delivery, single invoice, single payment; isolated; 2 items.  
**Behavior.** Standard e-commerce fulfillment: all lines packed together, one shipment, full settlement.  
**Risks/opportunities.** Baseline KPI denominator; low exception cost; good automation candidate.  
**Poor flattening.** Case-level “happy path” flattening works; still loses item-pack binding if used for pick-accuracy.  
**Stability.** Stable under ID repair and Add-Item reordering.

### SEM-SPLIT-CONSOL (X3)
**Signature.** Multiple packs, one consolidated delivery; single payment; isolated.  
**Behavior.** Warehouse splits into packages (size/zone) but carrier consolidates.  
**Risks/opportunities.** Extra pack labor; shipping cost optimization opportunity; packing-error risk higher than BASE.  
**Poor flattening.** Unique-event or last-package flattening hides dual pack; delivery-level case id looks like BASE.  
**Stability.** Stable; borderline only if a second Dispatch is missing in data (would look like incomplete split-split).

### SEM-SPLIT-SPLIT-MPAY (X4)
**Signature.** Split packs, split deliveries, multi-payment / partial settlement; isolated.  
**Behavior.** Staged fulfillment (backorder or multi-warehouse) with installment or partial payments.  
**Risks/opportunities.** Promise-date risk; revenue recognition complexity; customer-communication load.  
**Poor flattening.** Order-level single path collapses two deliveries and two payments into one trace with duplicate labels, losing partial-settle semantics.  
**Stability.** Stable if payment qualifiers or payment count retained; fragile if payments denormalized to one attribute.

### SEM-SHARED-PACK (X5)
**Signature.** Pack/Dispatch involve EXT order/item; invoice local only.  
**Behavior.** Cross-order logistics consolidation (same customer, multi-order ship-together).  
**Risks/opportunities.** Cost saving; allocation ambiguity if loss/damage; KPI double-counting if each order claims full delivery.  
**Poor flattening.** Order-centric flat logs duplicate the shared package event or drop EXT context  false BASE.  
**Stability.** Depends on preserving EXT flags; if EXT stripped, collapses to BASE (undesirable).

### SEM-SHARED-INV (X6)
**Signature.** Local logistics like BASE; invoice/payment shared with EXT order.  
**Behavior.** Combined billing (framework contract, household account).  
**Risks/opportunities.** Settlement allocation disputes; dunning must be account-level; credit risk shared.  
**Poor flattening.** Payment-level cases mix two orders; order-level cases invent full payment each.  
**Stability.** Needs EXT on finance objects; qualifier “no order-level allocation” is material.

### SEM-SUBST (X7)
**Signature.** Substitution/removal before dispatch; Dispatch may reference Item; otherwise BASE-like.  
**Behavior.** Line replacement or drop (stock-out, customer change) after pack start.  
**Risks/opportunities.** Inventory accuracy; customer consent; invoice must match final shipped set.  
**Poor flattening.** Activity-only view equals BASE and hides lost-sales / substitution rate.  
**Stability.** Requires O2O qualifiers or Dispatch E2O Item; if qualifiers dropped, wrongly merges with BASE.

### SEM-RETURN (X8)
**Signature.** Return + inspect + repack + second dispatch; then invoice/pay.  
**Behavior.** Post-shipment return of a line and reship (repair, exchange, or wrong-item correction).  
**Risks/opportunities.** Reverse-logistics cost; refund timing vs final invoice; NPS impact.  
**Poor flattening.** Order trace becomes long with repeated Pack/Dispatch; without object binding, cannot see which item looped.  
**Stability.** Stable if Return/Inspect retained; if returns stored in another system, under-detected.

## 5. Borderline cases

**X1 vs X2.**  
Activity-sequence: equal (same labels). Typed-structural: equal under rename (item add order is not structural once IDs are -renamed). Business-semantic: equal.  
Disagreement only if a definition treats event order of distinct Add Item IDs as ordered by ID string — that would be over-fine and is rejected here. Borderline is empty under well-formed renaming.

**X1 vs X5.**  
Activity-sequence: equal  same cluster. Typed-structural: unequal (EXT objects, pack multiplicity of items includes foreign item). Business-semantic: unequal (shared logistics).  
Defensible merge: “lead-order local projection” ignoring EXT for customer-journey reporting. Defensible split: cost allocation and warehouse batching analytics. Equivalences disagree exactly on whether isolation is part of the key.

**X1 vs X6.**  
Activity-sequence: equal. Typed-structural: unequal (Invoice E2O includes EXT-OB). Business-semantic: unequal (shared finance).  
Merge defense: fulfillment-quality monitoring cares only about logistics. Split defense: treasury and credit. Same tension as X5 but on the finance subgraph.

**X1 vs X7.**  
Activity-sequence (labels only): equal. Typed-structural: nearly equal; differs if Dispatch’s Item E2O and removal edge are required to match. Business-semantic / qualified-relation: unequal.  
Merge defense: “shipped and paid once” operational twin. Split defense: compliance and substitution KPIs. This is the sharpest label-vs-semantics border.

**X3 vs X4.**  
All three relations separate them: extra Dispatch, extra Payment, different O2O (one vs two deliveries; partial settle).  
A coarser “any split-pack” business relation could merge logistics and ignore finance  one cluster; a finance-first relation merges neither with BASE but still splits X3/X4. Disagreement arises when “split fulfillment” is defined without delivery cardinality or payment multiplicity.

**X4 vs X8.**  
Both have two packs and two deliveries, so a crude multiplicity signature may collide. Activity-sequence: different (Return/Inspect present only in X8). Typed-structural: different (return edges; P82 replaces P81 for I82; payment count). Business-semantic: different motifs (staged outbound vs return-repack).  
Defensible false merge: counting only Package/Delivery cardinalities without lifecycle motifs. Correct split uses activity alphabet + replace/return qualifiers.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the PM4Py key preserves.**  
`cluster_equivalent_ocel` builds an equivalence key from the object-centric structure around each lead object: ordered events with activity names and the typed object participation patterns (including how many objects of each type touch each event), up to renaming within the connected component. It is essentially exact typed structural equivalence for the extracted sub-OCEL of each lead instance, not a business-motif abstraction.

**Why raw identifiers make clusters too fine.**  
If renaming is incomplete, or external IDs and discovery order differ, two BASE executions land in different buckets. Even with renaming, presence/absence of EXT partners, qualifier-bearing edges, and slight E2O differences (Dispatch with/without Item) each explode the partition — often one execution per cluster on real logs.

**Canonicalization / post-process.**  
Map each PM4Py cluster to the business signature of §2; merge clusters that share `(logistics, finance, isolated, multiplicities)`. Optionally strip or normalize EXT nodes before clustering for “local fulfillment” views, and run a second pass that re-attaches sharing flags.

**When exact equivalence is preferable.**  
Compliance replay, audit sampling, and regression tests of a mining pipeline want exact structure: any divergence is a defect. Coarser business clustering is better for segmentation, capacity planning, and dashboards.

**`max_objs` and large connected executions.**  
Shared packages/invoices (X5, X6) enlarge the connected component. High `max_objs` keeps full sharing context but slows clustering and can weld many orders into one key; low `max_objs` truncates EXT context and falsely aligns X5/X6 with BASE. Prefer explicit EXT flagging over blind truncation.

```python
import pm4py
from collections import defaultdict

LEAD = "Order"

# 1) Exact structural clusters from PM4Py
clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD,
    # max_objs=...  # tune if components explode
)

# 2) Build lead-object -> execution view (assumes helper to project)
#    exec_of[order_id] -> ordered events + o2o for that lead

def business_key(order_id):
    ex = project_lead_execution(ocel, order_id)  # user helper
    sig = canonical_signature(ex)                # from section 2
    return (
        sig["logistics"],
        sig["finance"],
        sig["isolated"],
        tuple(sorted(sig["mult"].items())),
    )

# 3) Post-aggregate PM4Py clusters by business key
exact_to_orders = defaultdict(list)
for cid, sub_ocel in clusters.items():
    # collect lead ids present in this exact cluster
    leads = [oid for oid, ot in zip(sub_ocel.objects[ocel.object_id_column],
                                    sub_ocel.objects[ocel.object_type_column])
             if ot == LEAD]
    for oid in leads:
        exact_to_orders[cid].append(oid)

semantic_clusters = defaultdict(list)
for cid, orders in exact_to_orders.items():
    # all orders in an exact cluster share structure; key any one
    bk = business_key(orders[0])
    semantic_clusters[bk].extend(orders)

# 4) Optional: report both granularities
for bk, orders in semantic_clusters.items():
    print(bk, len(orders), orders[:5])
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.**  
X7 collapses into SEM-BASE (and TS-BASE if Dispatch Item E2O is also ignored). X4 may lose `partially_settles` but still separates via payment multiplicity. Return replace edges in X8 weaken but Return activities remain. **Assignments change:** SEM-SUBST  SEM-BASE.

**Ignore external objects.**  
X5  BASE logistics; X6  BASE finance. Shared-pack/inv clusters disappear. **Assignments change:** X5,X6 merge into SEM-BASE — harmful for cost and credit analytics.

**Collapse repeated same-label events.**  
X3 still has one Dispatch so may look closer to BASE if Pack count is collapsed; X4’s two Dispatch/two Payment collapse toward a single path; X8’s double Pack/Dispatch collapses toward a shorter return-less shape if Return is kept as the only discriminator. **Risk:** X3/X4 under-separated unless multiplicities are stored outside the activity stream.

**Pack and Dispatch as partial order.**  
Interleaving in X4 (PackDispatchPackDispatch) vs batch Packs then Dispatch (X3) remains distinct by delivery cardinality. Within X1/X2, no effect. If an execution packed two packages in either order before one dispatch, partial order would still yield SPLIT-CONSOL. **Borderline:** concurrent pack of shared EXT items would not create false splits.

**Payment multiplicity as amount attribute (optional).**  
X4 could be rewritten as one Record Payment with amount=full; then finance motif becomes SINGLE_PAYMENT and X4 moves nearer a pure SPLIT-SPLIT logistics cluster. Semantic partition still keeps X4 off BASE via two deliveries. **Lesson:** encoding money as structure vs attribute moves borders between finance subclusters.

## 8. Limitations and recommendation

| Purpose | Recommended equivalence | Rationale |
|---------|-------------------------|-----------|
| Compliance monitoring | Typed structural (+ qualifiers) | Must detect substitution, partial settle, and sharing exactly as recorded |
| Operational segmentation | Business-semantic motifs (§2) | Actionable cohorts (baseline, split-ship, return, cross-order) without ID noise |
| Root-cause analysis | Qualified-relation / fine structural | Need edges and EXT context to explain defects and allocation errors |
| Descriptive reporting | Activity-sequence or coarse semantic (merge BASE+minor variants) | Stable volumes; executives rarely need EXT topology |

**Why no single notion wins.**  
Activity-sequence over-merges X5/X6/X7 with X1 and under-serves object-centric insight. Exact typed isomorphism over-splits on harmless renaming and on every sharing variant, flooding dashboards. Pure business motifs can hide compliance-relevant qualifier differences (X7) if implemented carelessly. Purposes differ in cost of false merge vs false split: compliance pays for false merges; reporting pays for false splits.

**Limitations of this study.**  
Eight hand-built executions; no timestamps/concurrency beyond notes; amounts and customer IDs absent; EXT topology is star-shaped only; intentionally no gold clustering. Borderline X7 depends on qualifier availability in real OCELs — often missing. Recommendations should be re-tuned when event vocabularies differ (e.g., “Ship” vs “Dispatch”).

**Final stance.**  
Use **business-semantic equivalence** as the default preferred clustering for understanding X1–X8: merge only X1–X2; keep X3–X8 separate with explicit motifs for split logistics, multi-payment, cross-order pack, cross-order invoice, substitution, and return-repack. Retain typed-structural and activity-sequence views as diagnostic layers, not as the sole “object-centric” answer.
