## 1. Model scope and state variables

**Digital-twin boundary.**  
Model the permit process from portal submission through final decision. Include:

- Municipal activities and queues.
- Applicant-driven document response and applicant no-shows.
- Third-party/public-notice timers.
- Inspector travel and geographic batching.
- Resource calendars, holidays, council-meeting weeks, and part-time pools.
- Cross-case links among architect, district/neighborhood, and inspection bundles.
- Policy interventions and demand Stress scenarios.

Out of scope: downstream construction inspection, court litigation, detailed GIS routing beyond district travel factors, and HR scheduling not represented in the supplied calendars.

**Level of detail.**  
Use an activity-level discrete-event simulation. Each application is an individual case with its own attributes and route. Human resources are modeled as pooled capacity with skills and calendars. System steps have effectively unlimited capacity. External timers are modeled explicitly rather than as municipal work.

**Core entities and state variables.**

| Entity | Important state |
|---|---|
| Case/application | `case_id`, `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `arrival_ts`, current activity/status, route flags, rework counts, review results, SLA class, linked cases, bundle id, latent objection state |
| Applicant/third party | Response-time state for missing documents, appeal state, no-show probability, pre-submission effort under D1 |
| Resource | `resource_id`, pool/skill, FTE, calendar, speed factor, current assignment, overtime/urgent availability |
| Queue | Activity-specific waiting line, priority rule, aging thresholds, district/bundle constraints |
| Calendar | Working windows by pool, holidays, council weeks, non-permit reservations, field-visit days |
| Dependency graph | Edges between cases sharing architect, district/neighborhood, objection cluster, or inspection bundle |
| Global state | Simulation clock, demand-intensity schedule, active policy set, WIP/backlog, bottleneck statistics |

**Queues and dispatch logic.**

- Separate queues for clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, and schedulers.
- Most queues start FIFO, with aging priority and special handling for urgent/exempt cases where documented.
- Two planners handle only Simple renovation cases; this constraint must be represented.
- Fire reviewers work Tuesday-Thursday only.
- Environmental reviewers have only 60% effective permit capacity because 40% is reserved elsewhere.
- Inspectors work Tuesday-Friday, with district travel times and possible geographic batching.
- Legal officers are unavailable during council-meeting weeks except urgent cases.

**Cross-case dependencies.**

- **Architect dependency:** top architects submit bursts; related applications may share missing-document propensity and review issues.
- **Neighborhood dependency:** latent objection clusters by district/time affect public-notice duration for multiple related cases.
- **Inspection bundling:** cases in the same district/time window can be grouped; this reduces travel per inspection but increases waiting while the bundle forms.
- **Join dependency:** Decision drafting starts only after all applicable Planning, Fire, Environmental, Public-notice, and Inspection results are available.
- **Shared-resource coupling:** all cases compete for the same constrained resource pools and calendars.

## 2. Parameter-estimation plan

**Log/model handling with PM4Py.**

- Load the full event log with `pd.read_csv`, not `pm4py.read_csv`.
- Format with `pm4py.format_dataframe(..., case_id_key="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")`.
- Convert to an event log using `pm4py.convert_to_event_log`.
- Compute variants with `pm4py.get_variants` or `pm4py.discover_variants`, depending on PM4Py version.
- Discover control-flow DFG and performance DFG using `pm4py.discover_dfg` and `pm4py.discover_performance_dfg`.
- Parse the supplied process tree with `pm4py.parse_process_tree` if the version supports it; otherwise treat the string as a structural reference.
- Use the process tree as a scaffold, not as the sole executable model: it omits data-dependent routing, resource calendars, joins, rework reasons, objections, and cross-case batching.

**Arrivals.**

- Extract one arrival timestamp per case: minimum `time:timestamp` for `Submit application`.
- Estimate a marked non-homogeneous arrival process:
  - Monthly multiplier: March-May and September-November  1.7× January-February.
  - Weekday effect: Monday portal submissions  2.2× Wednesday.
  - Case-type/district/attribute marks from observed frequencies.
- Model large architects using a burst/cluster process: top 20 architects account for 31% of cases and often submit multiple related cases within a week.
- Estimate average arrival rate for sanity checks, but do not use a single stationary interarrival mean as the generator.

**Service and waiting times.**

- If explicit start/end timestamps exist:
  - Service = end - start.
  - Waiting = start - previous activity completion for the same case.
- For completion-only timestamps:
  - Do not silently equate inter-event time with service time.
  - Treat service/waiting split as partially latent.
  - Use calendar-aware inference: remove non-working time, use HR calendars, resource identities where available, and empirical summaries as priors.
- Fit activity-specific distributions conditioned on case type, district, and resource pool where data volume permits.
- Use empirical, lognormal, Weibull, gamma, or mixture distributions; preserve p50, p90, and heavy tails.
- Public notice is not ordinary service time: model it as fixed minimum 14 days plus a latent objection component with heavy tail up to roughly 60 days.
- Applicant response after missing documents is a separate external distribution with median around 5 days and heavy tail.

**Branching probabilities.**

- Estimate route probabilities from DFG/variant frequencies and case attributes:
  - Fire required if `requires_fire=yes` or area above a latent/imputed threshold.
  - Environmental required if `requires_environment=yes` or district sensitive; sensitivity data incomplete, so use priors/scenarios.
  - Public notice for Complex variance and some New residential cases.
  - Legal check frequency by case type and conflict/rework signals.
- Use conditional models such as logistic regression, decision trees, or empirical conditional tables rather than one global probability.

**Rework.**

- Estimate rework loop probabilities from repeated activities and variants:
  - Completeness rework from repeated Completeness check / missing-document loops.
  - Planning rework from repeated Planning review or downstream return.
  - Inspection rework from repeated inspection-related activities.
  - Legal rework/appeal from repeated Legal check or final-state changes.
- Rework reasons are unreliable text; represent them as latent causes with scenario ranges.
- Model rework as activity-specific loops with additional service, waiting, and sometimes applicant delay.

**Resources and calendars.**

- Use HR calendars as primary source; validate against observed completion patterns.
- Convert FTE to capacity via working windows and reservations.
- Assign skill sets: clerk, planner_simple, planner_all, fire, environmental, scheduler, inspector, legal, system.
- Estimate resource speed factors only if enough cases per resource are observed; otherwise keep homogeneous within pool.

**Dependencies.**

- Estimate architect burst tendency from grouped submissions by `architect_id` and week.
- Estimate objection clusters indirectly from long public-notice durations by district/time; do not label them as observed objection events.
- Estimate inspection-bundle opportunity from district, inspection date, and inspector assignment patterns.
- Use random effects or hierarchical estimates for district and architect heterogeneity.

## 3. Assumptions

- **Arrivals**
  - Portal submissions follow a non-stationary marked point process with monthly, weekday, and architect-burst effects.
  - The provided 18-month pattern repeats approximately annually unless a stress scenario changes it.
  - Removed emergency cases are either negligible for capacity planning or represented by a small unobserved-priority class in sensitivity analysis.

- **Service times**
  - Activity service times depend mainly on activity, case type, district, and resource pool.
  - Completion-only timestamps imply uncertainty in the service/waiting split; estimates are calibrated to medians and p90s, not treated as exact.
  - System activities are capacity-unconstrained.
  - Inspection service includes on-site work plus district-specific travel; travel may be reduced by batching.

- **Routing**
  - Routing uses observed flags where available and imputed latent attributes where not.
  - Fire/environment/public-notice triggers are probabilistic when the log lacks area, sensitivity, or objection data.
  - D2 skips site inspection only for Simple renovation, value < EUR 50,000, and no prior violations.
  - D5 starts a legal pre-check early but may require repeat work if inputs are incomplete.

- **Resources/calendars**
  - HR calendars are accurate enough for simulation and override purely log-inferred availability.
  - Resource pools are interchangeable within skill constraints, with no hidden additional overtime unless modeled as an intervention.
  - Environmental reviewers have 40% effective capacity removed for non-permit duties.
  - Legal officers do no ordinary work during council-meeting weeks; urgent exceptions are modeled separately.

- **Rework**
  - Rework probabilities are conditional on activity and case attributes but not perfectly observed.
  - Multiple rework loops are possible, with diminishing but nonzero probabilities.
  - Appeals are more likely for Complex variance cases and interact with council calendars.

- **Applicant/third-party response**
  - Applicant document response is separate from municipal service and is heavy-tailed.
  - Applicants may miss inspection appointments; no-shows create additional scheduling and travel cost.
  - D1 shifts some effort before formal submission and reduces, but does not eliminate, missing-document loops.

- **Cross-case dependencies**
  - Cases sharing architect/district have correlated attributes and errors.
  - Objections are latent neighborhood-level events that can affect several public-notice cases.
  - Inspection batching creates a trade-off: lower travel per visit but higher waiting before the first visit.

- **Non-stationary demand**
  - No steady-state assumption is valid.
  - Simulations use absolute calendar time, including seasonal peaks, weekdays, holidays, and council weeks.

- **Missing data**
  - Missing start timestamps, objection events, rework reasons, area thresholds, environmental sensitivity, violations, and rare emergency cases are modeled with explicit uncertainty.
  - Results should be reported as distributions over plausible parameter settings, not point estimates.

## 5. Warm-up, replications, and uncertainty treatment

**Warm-up.**

- Use calendar-aligned warm-up because demand is seasonal and non-stationary.
- Suggested design: simulate at least 6 months of warm-up before collecting statistics, with pre-simulated aged cases and open backlog.
- For seasonal conclusions, collect at least 24 months of post-warm-up output, preferably two full annual cycles.
- Do not discard only the first few cases; discard time based on the calendar and WIP stabilization.

**Run length.**

- Calibration baseline: 18 months, matching historical data.
- Intervention comparison: 24-36 months of observation after warm-up.
- Stress scenarios: minimum 12 months, including at least one seasonal peak.

**Replications.**

- Use 100-300 replications per experiment as a starting point; increase until confidence intervals for p90 and SLA compliance stabilize.
- Use common random numbers across interventions: same arrival stream, architect burst draws, and latent objection draws where policy does not intentionally change them.
- Use separate random-number streams for arrivals, service times, applicant response, rework, objections, and resource speed factors.

**Confidence/credible intervals.**

- Report 95% confidence intervals for means using replication-level statistics.
- For medians, p90, and SLA compliance, use bootstrap or batch-means intervals across replications.
- If parameters are estimated Bayesian-style, propagate posterior draws and report credible intervals that combine parameter and simulation uncertainty.
- Report paired differences versus baseline, not only absolute scenario values.

**Heavy-tailed durations.**

- Preserve heavy tails in applicant response, public notice, legal check, and Complex variance cases.
- Use sufficiently long runs and replications; p90 is more Monte-Carlo-sensitive than the median.
- Do not truncate long durations merely to reduce variance. Truncation is acceptable only if it reflects an actual policy or observed administrative rule.
- Report p50, p75, p90, p95, and maximum/WIP tail indicators separately.

**Sensitivity analysis.**

- One-at-a-time: arrival rate ±20%/±30%, service times ±20%, rework ±50%, applicant-response p90 ±50%, objection probability ±50%.
- Scenario ensembles: favorable, central, adverse.
- Global sensitivity: Morris screening or Sobol indices if the calibrated simulator is stable enough.
- Robustness criterion: an intervention should improve median and tail metrics in most plausible parameter sets, not only in the central calibration.

---

## 6. Validation strategy

**Face validation.**

- Walk through the event sequence with permit clerks, planners, inspectors, legal officers, and IT staff.
- Confirm that resource calendars, public-notice rules, rework loops, and proposed interventions match operational language.
- Review simulated traces for implausible behavior, such as legal checks before required inputs or inspections during non-field days.

**Event-log replay validation.**

- Replay historical arrivals and known case attributes.
- For clean paths, compare simulated activity sequences to the observed DFG and variant frequencies.
- Compare predicted timing distributions to observed completion timestamps.
- Use PM4Py conformance/alignment checks between simulated event logs and the supplied process tree as a structural sanity check.
- Do not expect exact replay where start timestamps, objections, rework reasons, and dependencies are missing.

**Distributional validation.**

- Compare simulated versus observed:
  - Variant-group shares.
  - DFG edge frequencies.
  - Case-type mix.
  - Monthly and weekday arrival counts.
  - Median and p90 cycle time by variant group and case type.
  - Missing-document loop frequency.
  - Public-notice duration distribution, treating objection events as latent.
- Acceptance ranges should be set with stakeholders, e.g. major variant shares within a few percentage points and medians/p90s within roughly 10-30%, depending on data quality.

**Resource-utilization validation.**

- Compare simulated activity counts and busy time with log-derived workload and HR expectations.
- Validate that fire reviewers are used only Tuesday-Thursday, inspectors Tuesday-Friday, and legal officers are idle during ordinary council-meeting weeks.
- Check that planner_simple cases are not assigned to planners without the appropriate skill.
- Verify environmental effective capacity is reduced by non-permit reservations.

**Bottleneck validation.**

- Compare simulated waiting-before-activity rankings with empirical summaries.
- Expected bottlenecks in the baseline include Planning review, Public notice, Inspection scheduling/Site inspection, Legal check, and applicant response.
- If the simulator removes a bottleneck that stakeholders know exists, recalibrate queue priorities, calendars, or service assumptions.
- For each intervention, check whether the bottleneck shifts plausibly rather than disappearing unrealistically.

**Out-of-sample validation.**

- Calibrate on an initial period, e.g. first 12-15 months, and validate on the final 3-6 months.
- Validate especially on peak months, because those stress resource calendars.
- Cross-validate by district and case type where sample sizes permit.
- Use historical intervention-free periods only; proposed policies cannot be validated directly until implemented, so their results remain model-based forecasts.

## 7. Decision criteria

**Primary decision rule.**  
Select interventions or portfolios that materially improve primary outcomes versus baseline, pass all guardrails, and remain robust under stress and parameter uncertainty. Do not claim exact optimality; present a ranked set of validated options with trade-offs.

| Metric | Definition | Decision guide / threshold range |
|---|---|---|
| Median cycle time | p50 submission-to-decision, overall and by case type | Prefer 5-10% reduction for broad policies; 15% for targeted variants |
| Tail cycle time | p90/p95 by case type and variant | Prefer 10-20% p90 reduction; Complex variance tail should not worsen |
| SLA compliance | Share meeting agreed deadlines | Illustrative targets: Simple 20d, New residential 60d, Commercial 90d, Complex 180d; thresholds to be confirmed by municipality |
| Rework rate | Share of cases with completeness/planning/inspection/legal/appeal loops | D1 should reduce missing-doc loops materially; no intervention should increase total rework by more than a small tolerated amount unless offset by major cycle-time gain |
| Resource utilization | Busy capacity / available capacity by pool | Healthy range roughly 60-85%; sustained >90% for human pools indicates fragility; very low utilization indicates wasted capacity |
| Backlog/WIP | Open cases by activity and age at month end | Month-end backlog should not grow systematically; peak WIP increase >10% versus baseline needs justification |
| Aging-case count | Cases above 20/30/45 days by activity | D6 should reduce old-case count without large median deterioration |
| Fairness | p50/p90 by district and architect class; large vs small architects; Gini/Theil of waiting time | Worst/best district p90 ratio ideally 1.25; no policy should systematically advantage top architects at the expense of small applicants |
| Inspection travel | Travel hours per inspection and number of site visits per inspector-day | D3/D4 should reduce travel hours or inspection queue without excessive bundle waiting |
| Applicant effort | Pre-submission time, appointment burden, no-show cost | D1/D7 must show whether public-service gains justify applicant burden |
| Cost | Staffing, IT, process-change, and applicant cost | Use cost per day saved and cost per SLA gain; compare D4 seasonal cost against benefits |
| Robustness | Performance across demand/service/rework/objection uncertainty | Benefit should persist in 80% of sampled scenarios; no guardrail failures in central and adverse cases |

**Policy-specific guardrails.**

- D2: must not increase safety/quality risk or hidden rework; requires expert review of low-risk classification.
- D3: bundle waiting must not erase travel savings for non-peak periods.
- D5/D8: early/triaged reviews must not increase legal or environmental rework.
- D9: public-notice early warning must not be treated as eliminating objections.
- D10: combined policy should be preferred only if it improves both median and tail outcomes without creating a new bottleneck.

def lognorm_from_median_p90(median: float, p90: float, rng: np.random.Generator):
    """Sample lognormal service time from median and p90."""
    z90 = 1.2815515655446004
    mu = np.log(median)
    sigma = (np.log(p90) - np.log(median)) / z90
    return float(rng.lognormal(mean=mu, sigma=sigma))

class ArrivalGenerator:
    """
    Non-stationary marked arrival process.
    Includes month multipliers, weekday effects, case-type marks, and architect
    burst generation.
    """

    def __init__(
        self,
        case_attributes: pd.DataFrame,
        params: Dict[str, Any],
    ):
        self.case_attributes = case_attributes
        self.params = params

    def _intensity_multiplier(self, ts: pd.Timestamp, interventions: set) -> float:
        month = ts.month
        weekday = ts.day_name()

        multiplier = self.params["month_multiplier"].get(month, 1.0)
        multiplier *= self.params["weekday_multiplier"].get(weekday, 1.0)

        if "D7" in interventions:
            # D7 reduces Monday spike depending on adoption/compliance level.
            multiplier *= self.params.get("d7_monday_factor", 0.7) if weekday == "Monday" else 1.0

        return multiplier

    def generate(
        self,
        start: pd.Timestamp,
        end: pd.Timestamp,
        rng: np.random.Generator,
        interventions: set,
    ) -> List[CaseState]:
        # Thinning algorithm for a non-homogeneous Poisson process.
        max_rate_per_day = self.params["max_arrivals_per_day"]
        t = start
        cases: List[CaseState] = []

        while t < end:
            t += timedelta(days=rng.exponential(1.0 / max_rate_per_day))
            if t >= end:
                break

            accept_prob = min(1.0, self._intensity_multiplier(t, interventions))
            if rng.random() > accept_prob:
                continue

            # Sample marks from empirical case attributes.
            row = self.case_attributes.sample(
                n=1,
                random_state=int(rng.integers(0, 2**31 - 1)),
            ).iloc[0]

            cases.append(
                CaseState(
                    case_id=f"SIM_{len(cases)+1:06d}",
                    case_type=row["case_type"],
                    district=row["district"],
                    architect_id=row["architect_id"],
                    arrival_ts=t,
                    application_value=float(row["application_value"]),
                    requires_fire=as_bool(row["requires_fire"]),
                    requires_environment=as_bool(row["requires_environment"]),
                    requires_public_notice=as_bool(row["requires_public_notice"]),
                    latent_objection=None,  # set by CrossDependencyModel
                )
            )

        return cases

    for scenario_name, interventions in configs.items():
        for seed in seeds:
            engine = SimulationEngine(
                arrival_generator=ArrivalGenerator(case_attributes, arrival_params),
                dependencies=CrossDependencyModel(dependency_params),
                router=Router(router_params),
                resources=ResourceManager(resources=[], params={}),
            )
            result = engine.run(interventions, seed, start, end)
            result["scenario"] = scenario_name
            rows.append(result)

    return pd.DataFrame(rows)
