```python
import pandas as pd
import pm4py

def extract_monthly_process_evidence(csv_path,
                                     case_id='case_id',
                                     timestamp='timestamp',
                                     activity='activity'):
    """
    Read field_service_events.csv, normalize renamed diagnosis labels,
    handle duplicates, and produce auditable monthly summaries:
    - variant distribution
    - DFG & performanceDFG edges
    - labelmaturity proxies
    - cohort splits (eventcalendar vs casestart)
    Returns a dict of DataFrames/tables, no model fitting.
    """
    # 1. Read raw events
    df = pd.read_csv(csv_path)

    # 2. Normalize renamed diagnosis activity label
    df['activity_norm'] = df[activity].replace({
        'Initial Diagnosis Completed': 'Diagnostic Assessment Completed',
        'Diagnostic Assessment Completed': 'Diagnostic Assessment Completed'
    })
    # Flag UNKNOWN_ACTIVITY for audit (kept in output but excluded from core features)
    df['is_unknown'] = df['activity_norm'].isna()

    # 3. Duplicatehandling strategy
    #    - Sort by timestamp to keep earliest event per case.
    #    - Apply stricter cleaning for dates after 20 Apr 2026 (new source).
    #    In this sketch we keep first per case; production would split by source.
    df = df.sort_values(timestamp).drop_duplicates(subset=[case_id], keep='first')

    # 4. Format for PM4Py
    df_pm4py = pm4py.format_dataframe(df,
                                       case_id=case_id,
                                       activity='activity_norm',
                                       timestamp=timestamp)

    # 5. Filter to study window (April 2026 – October 2026)
    df_pm4py = pm4py.filter_time_range(df_pm4py,
                                        start_timestamp='2026-04-01',
                                        end_timestamp='2026-10-31')

    # 6. Discover DFG (controlflow perspective)
    dfg = pm4py.discover_dfg(df_pm4py)

    # 7. Discover performanceDFG using a proxy performance key.
    #    Here we compute median resolution time per edge from the raw dataframe;
    #    in production the 'performance_key' would map to the breachlabel timestamp.
    #    We extract it via temporal features (see step 10) and pass as a column.
    #    For this sketch we just discover the DFG structure.
    perf_dfg = pm4py.discover_performance_dfg(df_pm4py,
                                               case_id=case_id,
                                               activity='activity_norm',
                                               timestamp=timestamp,
                                               performance_key='breach_time')  # placeholder

    # 8. Get variants (fullwindow approximation)
    variants = pm4py.get_variants(df_pm4py)

    # 9. Extract temporal features (caselevel) – creates eventcalendar cohort
    temporal = pm4py.extract_temporal_features_dataframe(df_pm4py, case_id=case_id)

    # 10. Create eventcalendar cohort (each row = an event, time measured from case start)
    #    and casestart cohort (each row = a case, features: leadtime, total cycle time, etc.)
    #    Interpretation difference:
    #      - Eventcalendar: useful for DFG edgetime analysis, respects activity ordering.
    #      - Casestart: useful for monthly aggregation, survivalstyle backtesting.
    #    Here we just tag both; downstream code can filter accordingly.
    temporal['cohort_type'] = 'case_start'  # will be overwritten per analysis need

    # 11. Build monthly summaries (auditable, no model fitting)
    #    - Case start month
    temporal['case_start_month'] = pd.to_datetime(
        temporal['case_start_timestamp']).dt.to_period('M')

    monthly = (temporal
               .groupby('case_start_month')
               .agg(
                   case_count=('case_id', 'count'),
                   unknown_share=('is_unknown', 'mean'),
               )
               .reset_index())

    # 12. Variant shares per month (simple countbased; pm4py.get_variants gives fullwindow list)
    #    In practice, compute permonth variant distribution by filtering df_pm4py per month slice.
    variant_summary = []
    for m in monthly['case_start_month'].astype(str):
        month_df = pm4py.filter_time_range(df_pm4py,
                                            start_timestamp=m + '-01',
                                            end_timestamp=m + '-31')
        var_counts = pm4py.get_variants(month_df)
        total = sum(v.count() for v in var_counts.values()) if hasattr(var_counts, 'values') else len(var_counts)
        shares = {str(v): c / total for v, c in var_counts.items()} if total else {}
        variant_summary.append({'month': m, 'variant_shares': shares})

    # 13. Return auditable package
    return {
        'raw': df,
        'normalized': df[['case_id', timestamp, 'activity_norm', 'is_unknown']],
        'dfg': dfg,
        'perf_dfg': perf_dfg,
        'variants': variants,
        'temporal': temporal,
        'monthly_summaries': monthly.to_dict(orient='records'),
        'variant_shares_by_month': variant_summary
    }
```

## 6. Risks of acting on the wrong diagnosis

| Failure mode | Why it’s dangerous | Mitigation |
|---|---|---|
| **Retraining on immature labels** | The model may overfit to censored breach observations (e.g., Oct’s 55% maturity). This degrades AUROC/ECE on future mature cohorts and masks true drift, leading to a feedback loop of unnecessary retraining cycles. | Enforce a **labelmaturity gate** (>=90% labels mature by 90days) before any retraining pipeline stage. Use fixedvintage backtesting to confirm discrimination on fully mature cohorts only. |
| **Calibrating around a pipeline bug** (e.g., April’s misaligned diagnosis prefixes) | Adjusting predicted risks to match a distorted observed breach rate propagates the bug into the new model. Calibration may “smooth over” the underlying feature misalignment, giving false confidence and hiding the need for featurerepair. | **Audit feature lineage** and activitylabel normalization **before** any calibration step. Recompute all diagnosisaligned features with the corrected labels; only then apply isotonic/Platt recalibration. Document the pipeline health score as a prerequisite. |
| **Ignoring genuine supplierdriven concept drift** (e.g., V3 breach rising from 0.30 to 0.64 due to parts delays) | The model’s diagnosistobreach relationship genuinely changes; a static model becomes increasingly miscalibrated and predictive power erodes. If unaddressed, service levels deteriorate and breach costs spiral. | **Monitor DFG edge times** (OrderReceived) and variantspecific breach rates. When V3 breach sustains above 0.60 *and* median OrderReceived exceeds 60h for two consecutive months, trigger a **conceptdrift investigation** (retrain or augment features) rather than assuming model decay. |
| **Attributing Partner Z’s population shift to unfair model behavior without stratified evidence** | Jumping to bias conclusions may trigger unnecessary model restrictions, regulatory scrutiny, or missed opportunities to add relevant features (rural distance, device age). It also risks ignoring the real operational impact of the new partner. | Perform **population reweighting** and **variantspecific calibration** first. If breach rates for Partner Z normalize after weighting and feature augmentation, the shift is a distribution issue, not a modelfairness failure. Document assumptions, include rural/device features where permissible, and evaluate fairness metrics **conditional** on variant/path, not globally. |

*Each failure mode pairs a concrete symptom with a concrete guardrail, ensuring that remediation actions are proportionate to the diagnosed cause.*
