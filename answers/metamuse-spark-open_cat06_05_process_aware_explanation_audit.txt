## 2. Process-model consistency checks

We implement a prefix-aware validation suite before any SHAP/sequence explanation is shown. The normative model is encoded as a Petri net / BPMN + declarative constraints; DFG is used only for discovery, not as ground truth.

**1. Prefix-time availability audit (feature timestamp vs t0):**
For each case reconstruct `t0 = timestamp(first Coverage Check Completed)`. Every feature must carry `feature_timestamp` / `valid_period`. Check `feature_timestamp <= t0` (or `event_ts <= t0` for event-derived features). Fail if derived from warehouse tables populated at closure (`total_case_duration_hours`, `final_handler_team`, `last_resource_role`) or from daily snapshots (`same_day_document_count_snapshot`) where `snapshot_ts > t0` or `document_upload_ts > t0`. Same for `prior_claim_count` SQL predicate audit: compare logic `claim_created_at < t0` vs `<= extraction_date`.

**2. Complete-trace detector:**
Flag any feature whose computation window = full trace if `window_end > t0`: `full_trace_variant_id`, `appeal_seen_anywhere`, `num_document_requests_total`, `total_case_duration_hours`. Compute alternative `prefix_variant_id` and `count_up_to_t0` to contrast.

**3. Activity-state classification at t0 (enabled / future-possible / impossible):**
Replay prefix `REG -> COV` on normative Petri net to get marking. At t0:
- **Past:** `Claim Registered`, `Coverage Check Completed` (observed).
- **Enabled:** next steps per model: `Damage Assessment Completed` (fast-track) OR `Documents Requested` OR `Fraud Investigation Opened` (if trigger). These are permissible immediate successors.
- **Future-possible but not enabled:** `Documents Validated`, `Settlement Decision Recorded`, `Appeal`, `Claim Closed`. Explaining t0 with them = leakage.
- **Impossible:** `Claim Closed -> Damage Assessment Completed` (Closed only as final place), `Damage Assessment` *after* `Closed`. This requires conformance, not frequency.
Limitation: model must correctly capture parallel Fraud Investigation and loop; otherwise enabled set is approximate.

**4. Activity-order feasibility & repetition semantics:**
Declarative check: `Settlement Decision Recorded` may occur 1× normally, 2× **only if** `Appeal` occurs between two decisions. Check pattern `DEC -> APP -> DEC` via trace alignment. Any `DEC` without preceding `APP` as second occurrence = violation. Check footprint matrix inferred from model: `Closed` never followed by anything. Compare against learned DFG: a frequent DFG edge `Closed -> Damage Assessment` does **not** make it normative; DFG shows observation, normative model shows allowance.

**5. Same-timestamp ambiguity check:**
Select events where `|ts_i - ts_j| = 0` and `sequence_index IS NULL`. Flag ordering unreliable. For `Claim Closed` and `Damage Assessment Completed` with identical ts, do not infer pattern direction; require ingestion sequence index or causal event-id ordering. Conformance should consider them unordered, not a strict sequence.

**6. Alignment / conformance test:**
Run alignment-based conformance of full trace against normative net (cost-based A*). Fitness should penalise impossible edges (`Closed -> Assessment`). Use it to quarantine noisy traces before pattern mining. Footprint analysis can support but is sensitive to infrequent behavior.

**7. Mutable-feature lineage test:**
Simulate time travel: recompute feature as of `t0 - 1day`, `t0`, `extraction_date`; flag drift if value changes. Applies to `risk_score_current`, `employee_experience`, `final_handler_team`, `claimant_region` (if mutable).

Limitations: DFG frequency  norm; alignment needs accurate normative model; declarative constraints need careful scoping for parallel fraud; all replay assumes correct `t0` isolation (first `Coverage Check`, not any later re-check).

## 3. Alternative feature interpretations

**A. Defensible predictive signal – may be used for t0 prediction, with association-only claim**
*Examples:* `initial_damage_complexity` (frozen pre-t0), `elapsed_since_registration_at_t0` (past timestamps), `claimant_channel = Broker`, `initial_reserve_at_t0` *after proof*.
*What may be claimed:* “Cases with High complexity at registration show higher historical breach rate; useful for triage.”
*What may **not** be claimed:* Causality (“raising complexity causes breach”) or direct actionability (“change channel to reduce breach”). Monitor for shift.

**B. Process-state or congestion signal – valid but contextual**
*Examples:* `queue_length_at_t0` (snapshot validated ±5m), `elapsed_since_registration_at_t0` (slack).
*What may be claimed:* “At t0 the system was congested; congestion is associated with elevated risk.” Good for operational routing/prioritization.
*What may not be claimed:* That reducing queue by 1 deterministically reduces breach by X without intervention trial; queue may proxy for complexity mix.

**C. Proxy requiring fairness/robustness review – available but must not be presented naïvely as “delay driver”**
*Examples:* `claimant_region`, `claimant_channel`, implicitly `initial_damage_complexity` when correlated with demographics.
*What may be claimed:* Predictive association conditional on oversight.
*What may not be claimed:* Causal attribute of region/person. Must: test demographic parity / equal opportunity, run counterfactual stability, consider excluding from decision-facing narratives, document proxy pathways (repair network, language). SHAP rank does not justify operational action on protected-correlated attribute.

**D. Drift/calendar proxy – available but confounded by non-stationary policy**
*Examples:* `calendar_week` (=52, holiday/policy-change weeks).
*What may be claimed:* “Breach rates varied by week in training period.”
*What may not be claimed:* “Week 52 operationally causes delay” or transferability. Must decompose into `policy_version`, `holiday_opening_hours`, `staffing_level_at_t0`; validate on out-of-time folds; monitor schema/process drift.

**E. Unusable until lineage is repaired – do not use for prediction or explanation now**
*Examples:* `final_handler_team`, `last_resource_role = SIU`, `risk_score_current`, `prior_claim_count_before_t0` (buggy), `same_day_document_count_snapshot`, `employee_experience as-of extraction`, `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`.
*What may be claimed:* Nothing with current values. They are not evidence of early knowledge.
*What may not be claimed:* Any t0 predictive or causal role. After repair: e.g., `prior_claim_count_at_t0` with predicate `< t0` becomes defensible (B); `risk_score_at_t0` versioned becomes defensible but still needs fairness review; `assigned_team_at_t0` with history becomes process-state.

## 5. Recommendations for explanation validation

**P0 – Immediate block (stop leakage)**
- Denylist at training & explanation: `total_case_duration_hours`, `appeal_seen_anywhere`, `final_decision`, `num_document_requests_total`, `full_trace_variant_id`, `last_resource_role`, `Claim Closed -> Damage Assessment` pattern and any feature with `feature_ts > t0`. Fail CI if explainer references them at t0.
- Retrain model **only on prefix-filtered dataset** recomputed as of t0; recalibrate probabilities after feature removal; report new AUC/PR, not old SHAP ranks.

**P1 – Feature-store with historical correctness (2-4 weeks)**
- Mandate `feature_timestamp`, `valid_from/to` for every feature. Require `AS OF` join (`feature_ts <= event_ts`). Implement bitemporal store for `handler_team`, `risk_score`, `employee_experience`, `reserve`, `region` if mutable.
- Fix bugs: `prior_claim_count` predicate `< t0`; `same_day_document_count`  event-time filter; snapshots must carry `snapshot_ts` and tolerance window; warehouse closure fields not exposed to t0 models.
- Add unit tests: time-travel consistency check (value at t0 == value recomputed from logs).

**P2 – Prefix-only recomputation & conformance suite**
- Recompute all aggregations/counts/variants **per prefix** (up to t0) for training, not full trace.
- Implement validation suite §2: prefix availability audit, alignment fitness gate, same-timestamp quarantine, declarative repetition check for double `Settlement Decision` only after `Appeal`.
- DFG is diagnostic only; normative Petri net is gate.

**P3 – Calibration & explanation stability after removal**
- Recalibrate (Platt/isotonic) on out-of-time holdout after leakage removal; expected breach rate will drop.
- Test explanation stability: SHAP Jaccard under bootstrap, prefix perturbation, and 5-minute timestamp jitter; suppress unstable explanations.
- Require model to show confidence + base rate.

**P4 – Proxy, fairness & actionability governance**
- For surviving proxies (`region`, `channel`, `complexity`, `calendar_week`): run fairness metrics, counterfactual parity, and “explainable for decision vs monitoring” tiering. Customer-facing actions cannot be justified by region alone.
- Enforce claim language lint: prohibit “causes”, “driver”, “determines” for SHAP; replace with “associated with higher historical breach rate”.
- Drift/calendar features go through policy-flag decomposition and out-of-time OOT validation.

**P5 – Monitoring for schema & process drift**
- Monitor feature PSI, queue distribution, variant mix, fraud-trigger rate, policy-change flag. Alert on new activity, timestamp granularity change, missing `sequence_index`.
- Quarterly audit: random cases traced end-to-end comparing explainer’s claimed drivers vs event log replay. Track calibration drift for 10-day breach target.
- Version model + feature definitions + normative process model together; any process change requires re-validation of enabled/future-possible classification.
