## 1. Conformance semantics

To interpret deviations correctly, we must distinguish between normative violations and modeling limitations. A **forbidden behavior** occurs when an observed relation contradicts a closed-world constraint (e.g., N3, T6, E10). These are hard violations unless proven to be data artifacts. **Missing mandatory behavior** implies an expected relation is absent within the defined scope (e.g., N1, T1). However, mandatory status applies to the business logic, not necessarily the specific abstraction (e.g., "directly-follows" vs. "eventually").

**Unexpected but unregulated behavior** refers to observations falling outside the norm’s coverage (e.g., N6, T4). Under an open-world assumption, these are compliant by default. **Typical-pattern absence** occurs when a "typical" relation is missing (e.g., N5). Since exceptions are legitimate, absence here is not a violation but a deviation from the mean. **Likely data-quality error** involves structural anomalies that contradict system design (e.g., E10 Sensor Heartbeat on Invoice). **Abstraction mismatch** arises when the normative model assumes a granularity (directly-follows) that the data log does not capture (e.g., unrecorded review events between Create and Validate). **Insufficient evidence** applies when the log lacks the necessary attributes to determine compliance (e.g., unlabelled unapplied cash).

The **closed-world assumption** applies strictly to forbidden relations and mandatory columns within the stated scope; if a forbidden relation exists, it is a violation. The **open-world assumption** governs typical and unspecified relations; absence does not imply noncompliance. This distinction prevents penalizing legitimate process variations or incomplete event logging as process failures.

## 3. Detailed reasoning by model family

### OC-DFG
Object-Centric Directly-Follows Graphs establish the sequence of events relative to object lifecycles. This model family can establish whether a process flow adheres to mandatory paths (N1, N4) or forbidden paths (N3). However, it cannot establish *causality* or *intent*, only temporal adjacency. A critical limitation is the abstraction of time; a "directly-follows" relation assumes no intervening events were recorded. For N1 (Create -> Validate), 2 Orders lack this link. The norm expects validation, but the DFG shows a gap. If an unrecorded "Review" event occurred, the DFG abstraction is too strict for the business reality. Thus, the deviation is an abstraction mismatch, not a compliance failure. Conversely, N3 (Cancel -> Dispatch) is a forbidden path. Since this relation exists in the DFG, it represents a true process failure regardless of abstraction, as the sequence itself is prohibited.

### OTG
Object Type Graphs establish structural relationships between object types. This family can establish whether objects interact as required (T1, T2) or forbidden (T6). It cannot establish the *quality* of the interaction, only its existence. For T6 (Order cobirth Payment), the observation of 1 case is a structural violation. In this system, financial objects cannot be born simultaneously with orders. This suggests a bug in the event generation logic. For T3 (Invoice -> Payment), the status is typical. The observation of 18 missing links (4 Write Off, 14 None) is compliant because the norm allows exceptions. However, the OTG cannot distinguish between "Open Credit Terms" and "Forgotten Payment" without external data.

### ET–OT
Event-Object Type graphs bind specific event types to object types. This family establishes whether the correct objects are involved in specific actions (E1–E8). It is highly sensitive to data quality. E10 (Sensor Heartbeat -> Invoice) is a forbidden link. The context suggests a reused numeric identifier caused a join error. While technically a forbidden relation, the root cause is data quality, not business logic. Similarly, E6 (Dispatch Package -> Delivery) is mandatory. Two missing links are noted, but context indicates a carrier reference exists. This implies the object model for "Delivery" might be optional in the logging schema, or the event attribute was not mapped to an object ID. This is an abstraction or data-quality issue, not a process violation.

The danger of interpreting an "eventually expected" rule as a "directly-follows" rule is significant. N1 states orders *should eventually* enter validation. The DFG captures *directly-follows*. If an Order is created, then reviewed, then validated, the DFG shows Create -> Review -> Validate. If Review is unrecorded, DFG shows Create -> Validate. If Create -> Validate is missing entirely, it could mean validation never happened (violation) or validation happened much later with other events in between (abstraction mismatch). The norm must specify the time window or allow intermediate events to avoid false positives.
