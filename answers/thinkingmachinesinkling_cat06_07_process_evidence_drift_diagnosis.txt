import pandas as pd
import pm4py

# Load and format
df = pd.read_csv("field_service_events.csv")
df = pm4py.format_dataframe(df, case_id="case_id", activity_col="activity", timestamp_col="timestamp")

df["activity"] = df["activity"].replace(label_fix)

# Duplicate-handling strategy: exact duplicates on core dimensions

# Monthly audit windows (event-calendar vs case-start cohorts)
months = pd.date_range("2026-01-01", "2026-10-01", freq="MS")
records = []

for s in months:
    e = s + pd.DateOffset(months=1)
    
    # Cohort 1: Event-calendar (all events in window) -> pipeline/process health
    ev_log = pm4py.filter_time_range(df, s, e, mode="events")
    
    # Cohort 2: Case-start (Case Created in window) -> outcome maturity tracking
    created = pm4py.filter_time_range(
        pm4py.filter_dataframe(ev_log, {"activity": ["Case Created"]}),
        s, e, mode="events"
    )
    case_ids = created["case_id"].unique()
    case_log = df[df["case_id"].isin(case_ids)].copy()
    
    # Normalize again for safety on subset (idempotent)
    case_log["activity"] = case_log["activity"].replace(label_fix)
    
    # Process discovery on event-calendar cohort
    dfg = pm4py.discover_dfg(ev_log)
    perf_dfg = pm4py.discover_performance_dfg(ev_log)

    variants = pm4py.get_variants(case_log)

    # Auditable summaries (no predictions)
    unknown_share = float((ev_log["activity"] == "UNKNOWN_ACTIVITY").mean()) if len(ev_log) > 0 else 0.0
    missing_proxy = float(feat_audit.isnull().sum().sum()) / max(feat_audit.size, 1) if not feat_audit.empty else None
    
    # Performance evidence: direct edge statistics for parts path
    part_events = ev_log[ev_log["activity"].isin(["Order Part", "Part Received"])]
    
    records.append({
        "month_start": s,
        "event_calendar_events": len(ev_log),
        "case_start_cases": len(case_ids),
        "unknown_activity_share": round(unknown_share, 4),
        "missing_feature_proxy": round(missing_proxy, 4) if missing_proxy is not None else None,
        "variant_count": len(variants),
        "part_edge_events": len(part_events),
        "dfg_edges": len(dfg),
        "perf_dfg_edges": len(perf_dfg),
        # Note: median durations computed separately from perf_dfg for auditability
    })

audit_df = pd.DataFrame(records)
# Interpretations:
# - event_calendar: captures process-state and pipeline-quality in the calendar month
# - case_start: tracks resolution-path maturity by cohort start date

- **Expected under independent partner effect/unfairness:** Even after reweighting and conditioning on variant, supplier status, and geographic/device features, Z cases show significantly different outcomes or the model systematically underpredicts/overpredicts for them—indicating missing features or a partner-specific concept shift requiring a segment-specific layer.

**G. Feature missingness and lineage audit**
- **Method:** Audit feature-store lineage for “number of events before diagnosis” in Apr–May. Measure missingness rates by source, variant, and partner. Verify duplicate-removal logs and mapping-patch coverage.
- **Expected under pipeline bug:** Missingness is concentrated in Apr (14%) and in specific derived features; lineage traces to the old label mapping; after normalization/dedup, missingness collapses to baseline (<2%).
- **Expected under systematic collection change:** Missingness correlates strongly and permanently with Partner Z onboarding or a new source system across all months, not just Apr.

## 4. Recalibration-versus-retraining decision

**Immediate containment (now – Nov 2026)**
- Halt all automated model updates, redeployments, or global recalibration that use October (and partially September) cohorts.
- Suppress predictive-performance alarms for Oct because maturity is 55%. Route alerts to label-maturity monitoring only.
- Activate manual triage/expedited parts tracking for V3 and Partner Z cases, since process evidence (part delivery >150h) and immature predictions both indicate elevated real risk.

**Short-term recalibration (Nov – Dec 2026)**
- Apply **segment-specific calibration**, not global. For V1/V2, use isotonic or Platt scaling on mature cohorts (Jan–Aug, corrected pipeline). For V3, calibrate separately using mature Jul–Aug data, acknowledging that the feature space is incomplete.
- Do **not** calibrate using October observed labels. If a quick operational adjustment is needed, raise decision thresholds for V3/Partner Z based on process-performance alarms (part delay >100h), not on immature outcome rates.

**Feature repair (Dec 2026 – Jan 2027)**
- Complete backfill/recomputation of the “events before diagnosis” feature for all April cases after full dedup and label normalization.
- Add supplier-performance features: median `Order Part  Part Received` duration per supplier/region, supplier-failure flag.
- Add population features: partner/source indicator (`Partner Z`), rural travel distance proxy, device age.
- Clean duplicates retroactively across the entire source, not only post-20 Apr.

**Full retraining (Feb 2027 or later, once cohorts mature)**
- **Safe months for training:** Jan–Mar (clean baseline); Jun (mature, correct pipeline, policy flag included); Jul–Aug (mature, severe but real supplier dynamics—must be included to learn the new V3 reality, but only with new supplier/performance features added).
- **Unsafe months:** Apr (pipeline-corrupted features—exclude unless fully recomputed and audited); May (residual backfill—include only after feature audit); Sep (82% maturity—use for evaluation with maturity adjustment, not primary training); Oct (55% maturity—exclude entirely from training).
- **Architecture:** A global backbone is insufficient because V1, V2, and V3 now operate under different dynamics, and Partner Z introduces an unmodeled feature region. Use a **variant-aware hierarchical model** (shared representation with variant-specific heads) plus a **partner/calibration layer**. If data volume supports it (~5,000 cases/month, ~2,000 V3 in peak months), separate models per variant with a meta-learner are justified. At minimum, include strong interaction terms (`variant × part_delay`, `partner × variant`) and per-segment calibration.

## 5. Monitoring architecture

**Monitor taxonomy and alert dependencies**
- **Predictive Performance Monitor:** Monthly AUROC, Brier, ECE on mature cohorts only (>90% maturity, >45 days old). Stratified by variant and partner.
- **Calibration Monitor:** Reliability diagrams and ECE per decile, per variant/source. Triggers if segment ECE >0.05 for two consecutive mature months.
- **Label-Maturity Monitor:** Cohort maturity % by start-week; median/90th-percentile label delay; slope of maturity curve. **Dependency:** If maturity <90% or median delay >45d, suppress Predictive Performance and Retraining alarms; emit maturity-only reports.
- **Data-Quality Monitor:** Unknown-activity share; missing-feature rate by derived feature; duplicate rate; schema-mapping consistency (counts of old vs new diagnosis labels); feature-lineage version. **Dependency:** If unknown-activity >1% or missing-feature >5%, suppress Calibration Monitor and Retraining Trigger; route to pipeline audit.
- **Process-Variant Monitor:** Monthly variant distribution (% V1/V2/V3/unmapped); emergence of new unmapped paths. Alert on >5pp shift in V3 or >2% unmapped.
- **Performance-DFG Monitor:** Median and 95th-percentile durations for `Order Part  Part Received` and `Initial Diagnosis Completed  Remote Fix`. Alert if part-receipt median exceeds 60h (baseline ~30h) or remote-fix exceeds 6h.
- **Population Monitor:** Partner/source share; feature-distribution drift (PSI or Wasserstein) for distance/device-age once added. Alert if new source exceeds 10% or feature PSI >0.2.
- **Intervention/Deployment Monitor:** Model version; feature-pipeline version; mapping-patch version; routing-policy flag (`remote_routing_policy`); supplier-status flag (`supplier_degraded`); partner-onboarding flag (`partner_z_active`). All flags must be logged before evaluation.

**Retraining trigger conditions (all must be true)**
1. Data-Quality Monitor: OK (unknown <1%, missing <5%, duplicates controlled).
2. Label-Maturity Monitor: Cohort maturity >95% and median delay stable.
3. Predictive Monitor: Sustained degradation (>2 consecutive mature months) in AUROC or ECE in at least one major segment.
4. Performance-DFG Monitor: Stable or updated (if supplier flag is active, new features must be present in pipeline).
If any of conditions 1 or 2 fail, retraining is blocked regardless of predictive degradation.

**Python sketch: monthly process-evidence extraction**

```python
import pandas as pd
import pm4py

# Load raw event log and format for PM4Py
df = pd.read_csv("field_service_events.csv")
df = pm4py.format_dataframe(df, case_id="case_id", activity_col="activity", timestamp_col="timestamp")

# 1. Normalize renamed diagnosis labels BEFORE feature extraction
label_fix = {"Diagnostic Assessment Completed": "Initial Diagnosis Completed"}
df["activity"] = df["activity"].replace(label_fix)

# 2. Duplicate-handling strategy: drop exact duplicates on core dimensions
# In production, extend with source-system sequence IDs
df = df.drop_duplicates(subset=["case_id", "activity", "timestamp", "resource"])

# 3. Define monthly audit windows
months = pd.date_range("2026-01-01", "2026-10-01", freq="MS")
audit_records = []

for s in months:
    e = s + pd.DateOffset(months=1)
    
    # Cohort A: Event-calendar (all events in calendar window) -> pipeline/process health
    ev_log = pm4py.filter_time_range(df, s, e, mode="events")
    
    # Cohort B: Case-start (Case Created in window) -> outcome maturity tracking
    created_events = pm4py.filter_time_range(
        pm4py.filter_dataframe(ev_log, {"activity": ["Case Created"]}),
        s, e, mode="events"
    )
    started_ids = created_events["case_id"].unique()
    case_log = df[df["case_id"].isin(started_ids)].copy()
    # Idempotent normalization for subset
    case_log["activity"] = case_log["activity"].replace(label_fix)
    
    # 4. Process discovery on event-calendar cohort
    dfg = pm4py.discover_dfg(ev_log)
    perf_dfg = pm4py.discover_performance_dfg(ev_log)
    
    # 5. Variant analysis on case-start cohort
    variants = pm4py.get_variants(case_log)
    
    # 6. Temporal feature audit (prefix extraction up to diagnosis) — not model fitting
    try:
        feat_audit = pm4py.extract_temporal_features_dataframe(case_log)
    except Exception:
        feat_audit = pd.DataFrame()
    
    # Auditable summaries (no predictions fitted)
    unknown_share = float((ev_log["activity"] == "UNKNOWN_ACTIVITY").mean()) if len(ev_log) > 0 else 0.0
    missing_proxy = float(feat_audit.isnull().sum().sum()) / max(feat_audit.size, 1) if not feat_audit.empty else None
    
    # Direct process-performance evidence: part-edge event counts (median computed separately)
    part_events = ev_log[ev_log["activity"].isin(["Order Part", "Part Received"])]
    
    audit_records.append({
        "month_start": s.strftime("%Y-%m"),
        "cohort": "event_calendar",
        "event_count": len(ev_log),
        "unknown_activity_share": round(unknown_share, 4),
        "dfg_edge_count": len(dfg),
        "perf_dfg_edge_count": len(perf_dfg),
        "part_edge_events": len(part_events),
    })
    audit_records.append({
        "month_start": s.strftime("%Y-%m"),
        "cohort": "case_start",
        "case_count": len(started_ids),
        "variant_count": len(variants),
        "missing_feature_proxy": round(missing_proxy, 4) if missing_proxy is not None else None,
    })

audit_df = pd.DataFrame(audit_records)

# Interpretation notes:
# - event_calendar captures pipeline-label health and process-state in the calendar month.
# - case_start tracks resolution-path maturity by cohort start date, essential for
#   comparing observed breach rates at consistent maturity levels.
# - No PM4Py drift detector is used; all outputs are auditable process summaries.
```

## 6. Risks of acting on the wrong diagnosis

**Failure mode 1: Retraining on immature October (and partial September) labels.**
If the team treats October’s 0.16 observed breach rate as “real improvement” and retrains or calibrates downward, the model will learn that V3/Partner Z cases with long part delays are low-risk—directly opposite to reality. Once October labels mature (likely toward ~0.30–0.35), the “retrained” model will be severely miscalibrated.
- **Mitigation:** Enforce a maturity gate (>95% for training, >90% for evaluation). Use fixed-vintage backtesting. Block retraining triggers when label-delay alarms are active.

**Failure mode 2: Calibrating around the April pipeline bug.**
If the team applies global recalibration or feature scaling to “fix” the April AUROC drop without auditing the feature pipeline, they will encode corrupted “number of events before diagnosis” values and `UNKNOWN_ACTIVITY` artifacts into the calibration layer. When the pipeline is repaired, the calibrated model will be systematically wrong.
- **Mitigation:** Data-quality alarms must suppress calibration actions. Require feature-lineage audit and full recomputation of derived features before any model adjustment in Apr/May.

**Failure mode 3: Ignoring genuine supplier-driven concept drift in V3.**
If the team attributes all Aug–Sep degradation to “label delay” or “partner shift” and applies only a global threshold shift, they will miss that the conditional relationship within V3 has broken: the same part-order event now predicts breach far more strongly because delivery times have tripled. A global fix will undercorrect V3 and overcorrect V1/V2.
- **Mitigation:** Require stratified evaluation by variant. Monitor performance-DFG durations. Add supplier/performance features and deploy variant-specific heads or calibration layers.

**Failure mode 4: Attributing Partner Z’s outcomes to unfair model behavior without stratified evidence.**
If the team sees Partner Z’s 0.45 observed rate and immediately applies fairness constraints or penalizes predictions for rural cases, they may miss that the difference is largely mediated by variant mix (more V3) and unmeasured supplier/performance conditions. Applying fairness adjustments before adding distance/device-age features and conditioning on variant could force incorrect predictions and mask real operational issues (e.g., parts delivery to rural areas).
- **Mitigation:** Conduct transport/reweighting checks first. Add missing geographic and device-age features. Evaluate fairness only after conditioning on variant, supplier status, and available covariates. Separate “population shift” alarms from “predictive degradation” alarms.

**Failure mode 5: Applying homogeneous remediation across all months (treating Apr–Oct as one failure).**
A single global retraining on “all recent data” would mix pipeline-corrupted April features, immature October labels, policy-altered June mix, and supplier-altered Aug dynamics. The resulting model would be an average of incompatible regimes and perform poorly in all of them.
- **Mitigation:** Maintain the timeline segmentation (pipeline, policy, supplier, partner, maturity). Use intervention/deployment flags in the feature store so the model can be evaluated and updated regime-by-regime. Retrain on clean, mature, feature-complete cohorts only.
