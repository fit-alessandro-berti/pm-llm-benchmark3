## 1. Temporal Data Semantics

**State Reconstruction:**
- For each case, reconstruct state by processing events in chronological order (timestamp  event_index).
- Blank attribute cells mean "no update at this event" – retain the last known value.
- Unknown values (e.g., missing amount) are explicitly tracked as `UNKNOWN` rather than defaulted.

**Timestamp Handling:**
- Events with identical timestamps are ordered by `event_index`.
- Attribute updates are effective at their event timestamp unless evidence (e.g., notes) specifies otherwise.

**Material Changes:**
- A "material change" is any update to `amount`, `risk_level`, `jurisdiction`, or `customer_type` after the latest review.
- For R4, an amount increase >20% invalidates prior reviews; decreases do not.

**Temporal Distinctions:**
- **Event time:** When the event occurred (timestamp).
- **Effective time:** When an attribute update or exemption becomes valid (may differ from event time).
- **Record time:** When the event was logged (assumed to be timestamp unless noted).
- **Evidence time:** When evidence (e.g., exemption approval) was created or observed.

**Final Attributes:**
- Final case attributes are irrelevant unless they reflect the state at the time of an earlier event.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|------|-----------------------------|----------------------------------|---------------------|---------------------|-----------|------------------------|-----------------|
| R1   | Release_Funds where jurisdiction  DE and amount  100,000 | Enhanced_Review after latest material change | Enhanced_Review  Release_Funds | State at Release_Funds | Valid exemption (R5) | INDETERMINATE if amount unknown | Exemption approval timestamp, scope match |
| R2   | Release_Funds where risk_level = HIGH or customer_type = PEP | Enhanced_Review and Compliance_Approve | Enhanced_Review  Compliance_Approve  Release_Funds | State at Release_Funds | None | INDETERMINATE if risk/customer_type unknown | None |
| R3   | Release_Funds where jurisdiction added to sanctions list after latest Sanctions_Screen | Sanctions_Screen after list update | Sanctions_Screen  Release_Funds | State at Release_Funds and list update | None | INDETERMINATE if jurisdiction unknown | Sanctions list update timestamp |
| R4   | Release_Funds where amount increased >20% after latest review | New review (Standard/Enhanced) | Review  Release_Funds | State at review and Release_Funds | None | INDETERMINATE if prior amount unknown | Amount at review and release |
| R5   | Exemption validity | Head_Compliance approval | Approval  obligation trigger | State at obligation trigger | None | INDETERMINATE if scope unclear | Approval timestamp, scope, expiration |
| R6   | Missing data | None | N/A | N/A | None | INDETERMINATE | None |
| R7   | Same-timestamp events | Tie-breaker: event_index | N/A | State at event | None | N/A | Event_index |

**Formal Pseudo-Logic:**
```
R1(case, release_event):
  state = state_at(release_event)
  IF state.jurisdiction  "DE" AND state.amount  100000:
    latest_change = max(timestamp of material changes before release_event)
    enhanced_review = any(Enhanced_Review after latest_change and before release_event)
    IF NOT enhanced_review AND NOT valid_exemption(case, release_event, "R1"):
      NONCOMPLIANT

R2(case, release_event):
  state = state_at(release_event)
  IF state.risk_level = "HIGH" OR state.customer_type = "PEP":
    enhanced_review = any(Enhanced_Review before release_event)
    compliance_approve = any(Compliance_Approve after enhanced_review and before release_event)
    IF NOT (enhanced_review AND compliance_approve):
      NONCOMPLIANT

R3(case, release_event):
  state = state_at(release_event)
  latest_screen = max(timestamp of Sanctions_Screen before release_event)
  list_updates = any(Sanctions_List_Update after latest_screen and before release_event)
  IF list_updates AND NOT any(Sanctions_Screen after list_updates and before release_event):
    NONCOMPLIANT

R4(case, release_event):
  state = state_at(release_event)
  latest_review = max(timestamp of Standard_Review or Enhanced_Review before release_event)
  IF latest_review:
    review_amount = amount_at(latest_review)
    IF review_amount  UNKNOWN AND state.amount > review_amount * 1.2:
      IF NOT any(Standard_Review or Enhanced_Review after latest_review and before release_event):
        NONCOMPLIANT

R5(exemption, case, release_event, rule):
  state = state_at(release_event)
  IF exemption.approved_by = "Head_Compliance" AND
     exemption.effective_from  release_event.timestamp AND
     exemption.expires  release_event.timestamp AND
     exemption.jurisdiction = state.jurisdiction AND
     exemption.customer_type = state.customer_type AND
     exemption.amount_scope  state.amount AND
     evidence_supports_approval(exemption):
    RETURN True
  RETURN False

R6(case, release_event):
  state = state_at(release_event)
  IF state.amount = UNKNOWN OR state.risk_level = UNKNOWN OR
     state.jurisdiction = UNKNOWN OR state.customer_type = UNKNOWN:
    RETURN INDETERMINATE
  RETURN DETERMINATE

R7(event1, event2):
  IF event1.timestamp = event2.timestamp:
    RETURN event1.event_index < event2.event_index
```

## 4. Ambiguities and Alternative Readings

**TX-302:**
- Alternative: If the exemption approval timestamp (09:05) is considered too late, the case would be NONCOMPLIANT. However, the qualified signature and outage documentation support the effective time of 09:00.

**TX-305:**
- Alternative 1: If the settlement amount (150k) is assumed to equal the release amount, R1 is triggered and not satisfied (no Enhanced_Review). Classification: NONCOMPLIANT.
- Alternative 2: If the release amount is assumed to be <100k, no rules are triggered. Classification: COMPLIANT.
- Evidence needed: Immutable release payload with amount.

**TX-310:**
- Alternative: If the witness testimony of oral approval at 08:45 is accepted, EX-88 would be valid. Classification: JUSTIFIED_EXCEPTION.
- Evidence needed: Corroborating evidence (e.g., call logs) for the oral approval.

**TX-311:**
- Alternative: If the jurisdiction update to DE is considered effective before the Enhanced_Review (despite event_index ordering), R1 would not be triggered. However, the note states the update occurred "after review by event_index," so the current classification stands.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-State Leakage:**
   Control-flow checks assume the final state of a case applies to all events. For example, TX-301's final amount (125k) would incorrectly trigger R1 at the Standard_Review (which used 80k).

2. **Post-Hoc Exemptions:**
   Exemptions recorded after release (e.g., TX-302's EX-77) cannot be evaluated by control-flow, which only sees the sequence of events, not their effective times.

3. **Material Changes After Review:**
   A control-flow check would miss that TX-309's amount increased >20% after the Enhanced_Review, invalidating it for R1.

4. **Conditional Activation:**
   Rules like R1 and R2 are triggered by data conditions (e.g., amount 100k), not just event sequences. Control-flow cannot express "if amount > X then require Y."

5. **Missing Data:**
   Control-flow assumes all data is present. TX-305's missing release amount would be silently ignored, leading to false compliance.

6. **Same-Timestamp Ordering:**
   TX-311's jurisdiction update and Enhanced_Review occur at the same timestamp. Control-flow cannot resolve the order without `event_index`.

## 7. Recommended Logging and Control Improvements

1. **Immutable Release Payloads:**
   Include a cryptographic hash of the release payload (amount, jurisdiction, etc.) at the time of Release_Funds to prevent retroactive changes.

2. **Effective/Record/Signature Timestamps:**
   Log:
   - `effective_timestamp`: When an attribute update or exemption becomes valid.
   - `record_timestamp`: When the event was logged.
   - `signature_timestamp`: When evidence (e.g., exemption approval) was signed.

3. **Rule Versioning:**
   Include a `rule_version` field in events to track which policy version applied at the time.

4. **Exemption Scope Clarity:**
   Explicitly log the scope of exemptions (jurisdiction, customer_type, amount range, waived rules) in the exemption event.

5. **Change Provenance:**
   For material changes (e.g., Update_Amount), log the reason and source (e.g., "customer request via API").

6. **Stable Event Ordering:**
   Replace `event_index` with a globally unique, monotonically increasing sequence ID to avoid timestamp ties.

7. **Data Quality Flags:**
   Add columns like `amount_source` (e.g., "customer_input", "system_calculated") to assess reliability.

8. **Review Scope:**
   Log whether a review (Standard/Enhanced) covered specific attributes (e.g., `review_scope: ["amount", "risk"]`).

9. **Sanctions List Version:**
   Include the version of the sanctions list used in Sanctions_Screen events.

10. **Audit Trail for Exemptions:**
    Log all exemption approvals (including oral approvals) with timestamps and approver identity.
