## 1. Target definition

### The Flaw in the Business Request
The lender requests an early warning model “predicting 90-day default from the first few events of every credit application.” Taken literally, this request is ill-posed. Credit default is a contractual delinquency state (e.g., 90+ days past due) that can occur **only if** an account has been approved, contracted, and activated. An applicant who is rejected at credit review, who withdraws during document collection, or who is transferred to a specialist platform is never exposed to credit risk. 

Informally labeling rejected, withdrawn, or open applications as “non-default” (0) simply because no default occurred is a catastrophic design error. It creates severe **label contamination and negative class bias**: applications rejected specifically because they posed unacceptable credit risk would be coded as "safe" (non-defaulters). A machine learning model trained on such labels would learn that high-risk applicant behaviors (e.g., poor credit bureau scores, erratic KYC verification, excessive requested amounts) correlate with non-default, inducing severe adverse selection upon deployment.

### Primary Target Formulation: Multi-State Competing-Risks / Decomposed Funnel Target
To remain statistically defensible and operationally actionable, the primary target is formulated as a **cause-specific cumulative incidence / multi-state transition target** across the entire intake population of applications.

From the point of prediction at early event prefix $k$ (with information set $\mathcal{H}_k$), the application progresses through a multi-state process toward one of five mutually exclusive absorbing or terminal states $J$:
1. $J = 1$: **Activated & Defaulted within 90 days** ($\text{Def}_{90d}$)
2. $J = 2$: **Activated & Performing for $\ge 90$ days** ($\text{Perf}_{90d}$)
3. $J = 3$: **Rejected and closed**
4. $J = 4$: **Withdrawn by applicant**
5. $J = 5$: **Transferred to partner / external platform**

The operational early warning estimand is the **Cause-Specific Cumulative Incidence Function (CIF)** of 90-day default under the prevailing operational policy:
$$\pi_{\text{default}}(90\text{d} \mid \mathcal{H}_k) = \mathbb{P}(J = 1 \mid \mathcal{H}_k)$$

This decomposes directly into a process funnel component and a conditional credit risk component:
$$\mathbb{P}(J = 1 \mid \mathcal{H}_k) = \underbrace{\mathbb{P}(\text{Activated} \mid \mathcal{H}_k)}_{\text{Funnel Survival / Selection Probability}} \times \underbrace{\mathbb{P}(\text{Default}_{90d} = 1 \mid \text{Activated} = 1, \mathcal{H}_k)}_{\text{Conditional Credit Default Risk}}$$

- **Unit of Analysis**: An individual credit application prefix observed up to event $k$ (or elapsed time $\Delta t$).
- **Target Population**: All initiated credit applications ($N = 48,000$) within the intake window (1 January 2024 through 31 December 2025).
- **Prediction Time ($t_{\text{pred}}$)**: The timestamp of the $k$-th event (e.g., fixed prefix length $k=3$, corresponding to initial Credit Review entry) or an elapsed calendar cutoff (e.g., $\Delta t = 24$ hours from `Application Started`).
- **Outcome Horizon**: Exactly 90 calendar days post `Account Activated` ($[t_{\text{activation}}, t_{\text{activation}} + 90\text{d}]$), with an additional 35-day administrative buffer ($t_{\text{activation}} + 125\text{d}$) to account for external label feed latency.
- **Primary Estimand**: The cause-specific cumulative incidence $\mathbb{P}(J = 1 \mid \mathcal{H}_k)$ and the conditional credit risk $\mathbb{P}(\text{Default}_{90d} = 1 \mid \text{Activated} = 1, \mathcal{H}_k)$.

### Credible Alternative Target Formulations
1. **Conditional Default among Activated Accounts ($P(D_{90d} = 1 \mid A=1, \mathcal{H}_k)$)**:
   - *Question Answered*: "Among applicants who clear underwriting, sign contracts, and activate accounts, what is their default probability?"
   - *Why it differs*: It restricts the population from $N=48,000$ to $N=25,200$ activated accounts. It answers a post-selection portfolio monitoring question, but it cannot inform early triage of raw incoming applications because it conditions on a future post-baseline event ($A=1$), inducing collider stratification bias.
2. **Policy-Specific Counterfactual Default Target ($Y(1)$)**:
   - *Question Answered*: "What would be the 90-day default probability of this applicant if the lender intervened to unconditionally grant credit and activate the account?" ($E[Y(1) \mid \mathcal{H}_k]$).
   - *Why it differs*: This requires estimating potential outcomes under an intervention. It requires three strong, fundamentally untestable assumptions:
     - *Conditional Exchangeability / Ignorability*: $(Y(1), Y(0)) \perp\!\!\! A \mid \mathcal{H}_k$ (no unmeasured confounding between the underwriting decision $A$ and default risk $Y$, ruling out unobserved underwriter discretion).
     - *Positivity*: $0 < \mathbb{P}(A=1 \mid \mathcal{H}_k = x) < 1$ for all observable profiles $x$.
     - *Consistency / SUTVA*: An applicant's default outcome under activation does not depend on the activation status of others or the operational mechanism of activation.
3. **Continuous Time-to-Default Post-Activation with Right-Censoring**:
   - *Question Answered*: "What is the hazard rate $\lambda(t)$ and survival function $S(t)$ of an activated account across continuous time $t \in [0, \infty)$?"
   - *Why it differs*: It avoids the arbitrary discretization at 90 days and naturally accommodates staggered follow-up and delayed external feeds using survival analysis.

### Justification of Primary Selection
The multi-state / decomposed CIF formulation is both **operationally and statistically defensible**:
- *Operationally*: It provides underwriters with a two-dimensional risk signal: whether the applicant is likely to complete onboarding (avoiding wasted manual review on withdrawals and rejections), and whether, if activated, the applicant represents toxic credit risk.
- *Statistically*: It defines targets exclusively on observable physical events, avoids imputing unobserved counterfactuals as pseudo-labels, prevents collider bias, and explicitly represents dropouts, rejections, and transfers as competing risks.

## 2. Cohort construction

### Rules and Timeline Boundaries
- **Observation Window**: Case start timestamp `time:timestamp` $\in [\text{2024-01-01 00:00:00}, \text{2025-12-31 23:59:59}]$.
- **Data Extraction Cutoff Date ($t_{\text{extract}}$)**: 15 February 2026.
- **Inclusion Criteria**: All application traces initiated within the observation window with at least one recorded event.
- **Exclusion Criteria**: Corrupted records lacking a valid `case:concept:name` or unresolvable multi-platform sync anomalies.
- **Label Maturation Rule**: An activated account is defined as *mature* as of $t_{\text{extract}}$ if and only if:
  $$t_{\text{activation}} + 90\text{ days (horizon)} + 35\text{ days (maximum feed delay)} \le t_{\text{extract}}$$

## 3. Censoring and missing-label strategy

### Distinguishing the Five Missingness and Censoring Mechanisms
1. **Ordinary Right Censoring**:
   - *Mechanism*: Activated accounts whose 90-day post-activation window extends beyond the study cutoff or who experience an administrative cut before 90 days without defaulting.
   - *Statistical Property*: Conditional on activation date, this is administrative, non-informative right-censoring: $T_i^* = \min(T_i, C_i), \Delta_i = \mathbb{I}(T_i \le C_i)$.
2. **Delayed Labels (External Feed Latency)**:
   - *Mechanism*: External credit bureau / default feeds arrive 7 to 35 days after the 90-day horizon has elapsed.
   - *Risk*: A case activated 100 days prior to extraction has passed the 90-day mark, but if its feed takes 30 days to arrive, the default flag remains `NULL` on 15 February 2026.
   - *Statistical Property*: Informative latency lag. Evaluating accounts before $90 + 35 = 125$ days post-activation produces artificial false negatives.
3. **Selection through Activation**:
   - *Mechanism*: 17,700 applications (9,100 rejected, 5,700 withdrawn, 2,900 transferred) never activate.
   - *Statistical Property*: This is **structural non-exposure**, not right-censoring. The target $Y$ is undefined or unobservable. Conditioning on $A=1$ induces collider bias if unmeasured factors affect both approval and repayment.
4. **Transfer as a Competing Event / Missing Follow-up**:
   - *Mechanism*: 2,900 applications transferred to partner platforms; 60% (~1,740) are linkable, 40% (~1,160) are lost.
   - *Statistical Property*: Selection into transfer is non-random (specialist platforms typically handle subprime or complex applicants). Treating transfers as independent right-censoring violates non-informative censoring assumptions.
5. **Permanently Missing Outcome Feeds**:
   - *Mechanism*: Partner-originated activated accounts suffer from an elevated rate of permanently missing feeds.
   - *Statistical Property*: Missing Not at Random (MNAR) or Missing at Random (MAR) conditional on channel. If partner-originated loans carry higher baseline default rates, dropping unlinked or unfeeded cases creates survivorship bias.

### Primary Analysis Strategy
The primary analysis couples:
1. **Cause-Specific Cox Models or Fine-Gray Subdistribution Hazard Models**: Used across all 48,000 applications to estimate the cumulative incidence of the competing outcomes $\{J=1, \dots, J=5\}$, handling still-open applications as right-censored at their elapsed process time.
2. **Inverse Probability of Censoring Weighting (IPCW) + Inverse Probability of Selection Weighting (IPSW)**: For the conditional default model among activated accounts:
   - Time-to-default post-activation $T_{\text{def}}$ is modeled using IPCW, where weights $w_i^C(t) = 1 / \hat{G}(t \mid X_i)$ account for delayed feed arrival and immature follow-up.
   - To correct for selection through activation, each activated case receives an IPSW weight $w_i^A = 1 / \hat{e}(X_k)$, where $\hat{e}(X_k) = \mathbb{P}(A=1 \mid X_k)$ is the estimated propensity of activation given prefix features.

### Sensitivity Analyses
1. **Non-parametric Manski Worst-Case Bounds**:
   Compute the extreme bounds of portfolio default probability by imputing:
   - *Lower Bound*: All unobserved, rejected, withdrawn, and missing-feed cases had $D_{90d} = 0$.
   - *Upper Bound*: All unobserved, rejected, and missing-feed cases had $D_{90d} = 1$.
   This establishes the mathematical envelope of default risk free from unverifiable assumptions.
2. **Pattern-Mixture Model for Missing Partner Feeds**:
   Specify a sensitivity parameter $\delta \in [1.0, 3.0]$ representing the odds ratio of default among partner accounts with permanently missing feeds relative to observed partner accounts:
   $$\text{logit}(\mathbb{P}(D=1 \mid \text{Missing Feed}, X)) = \text{logit}(\mathbb{P}(D=1 \mid \text{Observed Feed}, X)) + \log(\delta)$$
   Assess whether model coefficients and risk rankings remain stable as $\delta$ varies.
3. **Transfer Linkage Validation**:
   Compare the 1,740 linked transfers against the 1,160 unlinked transfers on early prefix covariates ($X_k$). Evaluate whether treating linked transfers as an external validation set alters cumulative incidence estimates.

### Formal Classification of Assumptions

| Assumption | Category | Statistical Justification & Verification Method |
| :--- | :--- | :--- |
| **Feed Latency Distribution** | **Testable** | The empirical distribution of feed arrival delay ($\tau_{\text{feed}} \in [7, 35]$ days) can be directly computed for historical matured cases via `label_available_at - (t_activation + 90d)`. |
| **Transfer Linkage Balance** | **Testable** | Difference in means and Kolmogorov-Smirnov tests on prefix features (requested amount, initial score) between the 60% linked and 40% unlinked transfer cases. |
| **Channel-Specific Feed Missingness** | **Testable** | Logistic regression of missing feed indicator on `case:channel` and `source_system` verifies whether missingness is explained by observable channel metadata. |
| **Positivity of Activation ($0 < P(A=1 \mid X_k) < 1$)** | **Partially Testable** | Inspect the empirical overlap of propensity score distributions $\hat{e}(X_k)$ across activated vs rejected cohorts; lack of common support in extreme credit score ranges indicates positivity violations. |
| **Proportional Hazards / Subdistribution Hazards** | **Partially Testable** | Grambsch-Therneau tests on Schoenfeld residuals evaluate whether hazard ratios remain constant over the 90-day post-activation window. |
| **Missing at Random (MAR) within Channel Strata** | **Partially Testable** | Testable across observed covariate subsets, but impossible to confirm whether unobserved factors drive missingness within partner channels. |
| **Counterfactual Default Risk of Rejected Applicants ($Y(1) \mid A=0$)** | **Fundamentally Untestable** | Unobserved by definition. Rejected applicants never receive credit from the lender; their repayment performance under credit exposure cannot be observed or verified from these data. |
| **Unconfoundedness of Activation ($Y(1) \perp A \mid X_k$)** | **Fundamentally Untestable** | Underwriters utilize human judgment, discretionary phone notes, and unmodeled documents. If any unobserved factor influences both the approval decision and default, exchangeability fails. |

## 4. Prefix extraction

### Generation Rules and Temporal Point-in-Time Constraint
All feature representations and state variables must be strictly evaluated **as of** $t_{\text{pred}}$, the timestamp of the last event in the prefix. Any event with $t > t_{\text{pred}}$ is blinded.

Prefixes are generated under two complementary operational paradigms:
1. **Fixed Event-Count Prefixes ($k = 1, 2, 3, \dots$)**:
   - $k=1$: Evaluated at `Application Started` (intake demographics, channel, initial requested amount).
   - $k=2$: Evaluated at `Identity/KYC Check` (automated identity verification outcomes).
   - $k=3$: Evaluated at initial `Credit Review` entry (first underwriter queue assignment, initial credit score).
   - $k=4, 5$: Evaluated after first document request or subsequent underwriter pass.
2. **Elapsed-Time Prefixes ($\Delta t \in \{2\text{ hours}, 24\text{ hours}, 72\text{ hours}, 7\text{ days}\}$)**:
   - Slices the event trace at $t_{\text{pred}} = t_{\text{start}} + \Delta t$.
   - *Operational Rationale*: Event counts can be distorted by process velocity (e.g., an automated channel executes 3 events in 10 seconds, while a manual branch channel executes 3 events over 4 days). Elapsed-time prefixes provide standardized operational decision gates.

### Handling Edge Cases and Process Complexities
- **Short Cases (Early Terminal Transitions)**:
  - An application may reach a terminal state before prefix length $k$ or elapsed time $\Delta t$ (e.g., instant KYC auto-rejection at $k=2$, or immediate applicant withdrawal at 30 minutes).
  - *Rule*: **Never drop short cases.** Dropping them introduces survivorship / immortal time bias. Instead, short cases are retained in the cohort. For fixed-$k$ representations, short cases are marked with an absorbing state flag (`is_early_terminal = True`), and their feature vectors are zero-padded or filled with absorbing-state tokens (`TERMINAL_REJECTED`, `TERMINAL_WITHDRAWN`).
- **Repeated Document Loops (Rework Cycles)**:
  - The process allows: `Credit Review` $\rightarrow$ `Document Requested` $\rightarrow$ `Document Uploaded` $\rightarrow$ `Credit Review`.
  - *Rule*: Prefixes must capture dynamic loop counters up to $t_{\text{pred}}$ (e.g., number of document requests so far, cumulative waiting time). Crucially, any document requested or uploaded after $t_{\text{pred}}$ is strictly excluded.
- **Activity Renaming and System Migration (15 October 2025)**:
  - On 15 October 2025, system migration renamed several activities and created occasional duplicate events.
  - *Canonical Vocabulary Mapping*: A bi-temporal dictionary maps legacy activity strings to a unified canonical ontology (e.g., `{'KYC_Check_v1': 'Identity/KYC Check', 'KYC_Passed': 'Identity/KYC Check', 'Doc_Req_Legacy': 'Document Requested'}`).
  - *Deduplication Filter*: Idempotent events sharing the same `case:concept:name`, canonical `concept:name`, and `org:resource` occurring within a micro-window of $\Delta \tau \le 5$ seconds are collapsed into a single event before prefix slicing.

## 5. Process-aware features

Features available at $t_{\text{pred}}$ are categorized into a structured taxonomy distinguishing their information provenance and availability rules.

### Feature Taxonomy

```
+----------------------------------------------------------------------------------------------------+
|                                    PROCESS-AWARE FEATURE TAXONOMY                                  |
+-----------------------------------+----------------------------------+-----------------------------+
| 1. Static Case Attributes         | 2. Dynamic Prefix Features       | 3. Historical / Queue State |
| (Known at application start)      | (Derived strictly [t_start, t_p])| (Reference data < t_pred)   |
+-----------------------------------+----------------------------------+-----------------------------+
| - case:channel                    | - Prefix trace sequence (n-gram) | - Credit Review queue depth |
| - case:region                     | - DFG transition frequencies     | - Resource active workload  |
| - log(case:requested_amount)      | - Rework loop count (doc reqs)   | - Rolling 30d resource speed|
| - Initial bureau risk_score       | - Elapsed time (t_pred - t_start)| - Macroeconomic index       |
| - Cyclical hour/day-of-week       | - Customer wait vs service time  | - Policy epoch indicator    |
+-----------------------------------+----------------------------------+-----------------------------+
```

1. **Static Case Attributes (Point-in-Time at Intake)**:
   - `case:channel`: Origination channel (`Online`, `Branch`, `Partner`, `Broker`).
   - `case:region`: Geographic underwriting territory.
   - `case:requested_amount`: Log-transformed loan amount requested by applicant.
   - `initial_risk_score`: External bureau credit score recorded at `Application Started`.
2. **Dynamic Control-Flow & Prefix Sequence Features**:
   - `prefix_variant_id`: Encoded string of observed canonical activities up to $k$.
   - `dfg_edge_count`: Occurrence count of specific Directly-Follows transitions observed in the prefix (e.g., `Identity/KYC Check` $\rightarrow$ `Credit Review`).
   - `kyc_fast_tracked`: Binary flag indicating whether KYC completed automatically without manual intervention.
3. **Timing and Velocity Features**:
   - `total_elapsed_seconds`: $t_{\text{pred}} - t_{\text{start}}$.
   - `service_time_seconds`: Total active duration spent inside institutional handling activities.
   - `waiting_time_seconds`: Inactive time elapsed between event completions and subsequent event initiations.
   - `event_velocity`: Number of events executed per hour ($\text{count}(k) / \Delta t$).
4. **Rework and Friction Indicators**:
   - `document_request_cycles`: Count of `Document Requested` events within the prefix.
   - `ping_pong_count`: Number of handoffs between distinct `org:resource` entities within the prefix.
5. **Resource and Operational Queue Features (Point-in-Time State)**:
   - `current_resource_id`: The masked identifier of `org:resource` handling event $k$.
   - `queue_depth_at_pred`: Number of concurrent open applications awaiting review in the `Credit Review` state across the entire system at timestamp $t_{\text{pred}}$.
   - `resource_instantaneous_workload`: Number of active cases assigned to `org:resource` in the trailing 4 hours prior to $t_{\text{pred}}$.
   - `resource_historical_velocity`: Rolling 30-day median processing speed of `org:resource` on historical cases completed prior to $t_{\text{pred}}$.
6. **Cohort, Calendar, and Policy Context**:
   - `sin_hour`, `cos_hour`: Cyclical encoding of time-of-day of application start.
   - `is_post_july_2025_policy`: Binary indicator $\mathbb{I}(t_{\text{start}} \ge \text{2025-07-01})$, capturing the credit-policy threshold change.
   - `is_post_oct_2025_migration`: Binary indicator $\mathbb{I}(t_{\text{start}} \ge \text{2025-10-15})$, capturing the IT system migration.

## 7. Validation design

### Why Random Splitting is Invalid
A standard random train/validation/test split (e.g., `pm4py.split_train_test` or random K-fold CV) is invalid for this setting:
1. **Temporal Arrow Violation**: Random splits allow future cases (e.g., late 2025) to predict past cases (early 2024), leaking macroeconomic trends and operational changes.
2. **Policy Regime Contamination**: On 1 July 2025, credit-policy thresholds changed. Random splitting mixes pre- and post-policy cases across folds, forcing the model to learn an unweighted average of two contradictory underwriting regimes.
3. **System Migration Leakage**: The 15 October 2025 migration introduced renamed activities and duplicate artifacts. Random splitting leaks migration-specific schemas into training folds.
4. **Label Latency and Survivorship Bias**: Matured accounts require 90 days + up to 35 days feed delay ($125$ days). A random split would evaluate recently activated cases that appear non-default solely because their outcome feed has not arrived.

### Chronological Out-of-Time Backtesting Scheme
To evaluate real-world generalization, we establish a strict **multi-period temporal split** anchored on application start time:

```
[===================== Observation Window (48,000 cases) =====================] [Feed Delay] [Extract]
2024-01-01                   2025-01-01             2025-07-01   2025-10-01   2025-12-31    2026-02-15
|-----------------------------|----------------------|------------|------------|--------------|--------->
       TRAINING SPLIT             VALIDATION SPLIT       TEST SPLIT   MONITORING / IMMATURE
     (In-Regime Baseline)       (Pre-Policy Tuning)    (Policy Shift) (Migration & Censored)
         (12 Months)                 (6 Months)          (3 Months)     (3 Months)
```

1. **Split 1: Training Cohort (In-Regime Baseline)**:
   - *Intake Dates*: 1 January 2024 – 31 December 2024.
   - *Regime*: Old credit policy, legacy IT system, fully matured labels (all $> 400$ days prior to extraction).
   - *Purpose*: Base model training for process features, DFG discovery, and initial propensity estimation.
2. **Split 2: In-Regime Validation Cohort (Tuning & Calibration)**:
   - *Intake Dates*: 1 January 2025 – 30 June 2025.
   - *Regime*: Old credit policy, legacy IT system, fully matured labels ($>220$ days prior to extraction).
   - *Purpose*: Hyperparameter tuning, feature selection, probability threshold optimization, and probability calibration.
3. **Split 3: Out-of-Time Test Cohort (Credit Policy Shift)**:
   - *Intake Dates*: 1 July 2025 – 30 September 2025.
   - *Regime*: **New credit policy thresholds**; legacy IT system. Fully matured by 15 February 2026 ($30\text{ Sep } + 125\text{d} = 2\text{ Feb } 2026 \le 15\text{ Feb } 2026$).
   - *Purpose*: Evaluates model resilience to underwriting policy shifts and threshold changes.
4. **Split 4: Out-of-Time Monitoring Cohort (Migration & Immature Labels)**:
   - *Intake Dates*: 1 October 2025 – 31 December 2025.
   - *Regime*: **Post-migration IT schema** (15 Oct 2025); contains the 3,600 immature / delayed-feed activated accounts and 5,100 open cases.
   - *Purpose*: Evaluates data-pipeline resilience to schema renaming, event deduplication, and tests right-censored survival models.

### Calibration, Subgroup Auditing, and Distribution Shift
- **Probability Calibration**: Credit risk models require accurate probabilities for expected loss calculation. Models are calibrated using isotonic regression or Platt scaling fit strictly on Split 2 and evaluated out-of-time on Split 3 using the **Brier Score** and **Expected Calibration Error (ECE)** across deciles.
- **Subgroup Auditing**: Performance must be disaggregated across:
  - *Channel*: Direct Online vs. Branch vs. Partner-originated (auditing partner-feed missingness).
  - *Region*: Geographic credit stability.
  - *Requested Amount Tiers*: Small vs. jumbo credit requests.
  - *Policy Era*: Pre-July 2025 vs. Post-July 2025.
- **Distribution Shift & Drift Monitoring**:
  - *Population Stability Index (PSI)* and *Wasserstein Distance* computed on prefix features and predicted risk scores across splits ($PSI > 0.25$ triggers model alert).
  - *Process Drift*: Transition frequency matrices of the DFG monitored across the 15 October 2025 migration boundary to detect structural process anomalies.
- **Evaluation Metrics**:
  - *For Multi-State / CIF*: Cause-specific concordance index (Harrell's C-index) and Cause-Specific Brier Score at 90 days.
  - *For Conditional Survival*: Time-dependent AUC with Inverse Probability of Censoring Weighting ($\text{AUC}_{\text{IPCW}}(t)$) and Integrated Brier Score (IBS) over $t \in [0, 90]$.

## 8. Limitations and decision-use boundary

### What the Study Can and Cannot Claim
1. **Predictive Association vs. Causal Default Risk**:
   - The model discovers statistical associations between early prefix patterns and default outcomes under the **historical operational and underwriting policy**.
   - It **does not** measure intrinsic applicant creditworthiness in a counterfactual vacuum. A high predicted default risk reflects the probability of default *given that the application survived historical underwriting*.
2. **The "Lender's Curse" and Selection Effects**:
   - The model observes default outcomes exclusively for applicants accepted and activated ($A=1$).
   - It **cannot claim** to know what the default rate would have been among rejected (9,100) or withdrawn (5,700) applicants.
   - If an underwriter rejected an applicant based on subtle, unrecorded qualitative information (e.g., inconsistent phone interview responses) despite clean prefix bureau scores, a model trained naively on activated cases will view those clean prefix scores as safe. Deploying such a model to autonomously approve credit creates catastrophic adverse selection.
3. **Decision-Use Boundary**:
   - *Valid Use*: Operational early warning, workload prioritization, flagging high-risk applications for enhanced underwriting review, and identifying applicants likely to abandon the process.
   - *Invalid Use*: Autonomous credit decline/approval engine or setting credit policy limits without counterfactual verification.

### Three Ways Deployment Alters the Data-Generating Process (Performative Feedback)
1. **Underwriter Intervention Feedback Loops (Performative Prediction)**:
   - If early warning alerts are displayed to underwriters, they will scrutinize flagged applications more aggressively, demand additional documentation, or reject them outright.
   - As a result, these high-risk applicants will never activate ($A=0$), preventing any default from occurring.
   - In subsequent retraining cycles, the training pipeline will observe zero defaults for cases with these prefix profiles, causing the model to falsely conclude that the risk factor has disappeared.
2. **Applicant and Broker Strategic Adaptation (Goodhart's / Campbell's Law)**:
   - If loan brokers or applicants realize that specific early prefix behaviors (e.g., rapid document upload turnaround, specific stated loan amounts, or channel selection) trigger scrutiny or automated fast-tracking, they will alter their submission behavior to mimic low-risk traces.
   - This behavioral shift erodes the statistical association between process features and default risk over time.
3. **Operational Bottlenecks and Dropout Funnel Distortion**:
   - Routing flagged cases into secondary review queues increases customer waiting time.
   - Creditworthy applicants with outside options will withdraw ($J=4$) to seek loans from faster competitors, while desperate, high-risk applicants will remain in queue.
   - This selectively alters the competing-risk composition of the funnel, degrading the underlying quality of the activating cohort.

import pandas as pd

MATURATION_BUFFER = pd.Timedelta(days=125)

    is_rejected = any("Reject" in act for act in activities)
    is_withdrawn = any("Withdraw" in act for act in activities)
    is_transferred = any("Transfer" in act for act in activities)
    
    cohort_status = "open"
    ground_truth_default = np.nan
    
    if is_activated:
        act_row = group[group["concept:name"] == "Account Activated"].iloc[0]
        act_time = act_row["time:timestamp"]
        # Audit label maturity against feed delay
        if act_time + MATURATION_BUFFER <= CUTOFF_DATE:
            cohort_status = "activated_mature"
            labels = group["default_90d"].dropna()
            ground_truth_default = labels.iloc[0] if len(labels) > 0 else np.nan

    elif is_rejected:
        cohort_status = "rejected"               # Competing risk / selective non-exposure
    elif is_withdrawn:
        cohort_status = "withdrawn"              # Competing risk / applicant dropout
    elif is_transferred:
        cohort_status = "transferred"            # Competing risk / loss to follow-up
        
    case_records.append({
        "case:concept:name": case_id,
        "case_start_time": start_time,
        "cohort_status": cohort_status,
        "default_90d": ground_truth_default
    })

case_cohort_df = pd.DataFrame(case_records)

# 3. Strict Temporal Splitting by Application Start Time
# Note: pm4py.split_train_test exists as a random split baseline, but random splitting
# is invalid here due to the 2025-07-01 policy change, 2025-10-15 migration, and feed latency.
TRAIN_CUTOFF = pd.Timestamp("2025-01-01", tz="UTC")
VAL_CUTOFF   = pd.Timestamp("2025-07-01", tz="UTC")  # Pre-policy change boundary
TEST_CUTOFF  = pd.Timestamp("2025-10-01", tz="UTC")  # Pre-migration & matured boundary

def assign_split(t):
    if t < TRAIN_CUTOFF:
        return "train"
    elif t < VAL_CUTOFF:
        return "validation"
    elif t < TEST_CUTOFF:
        return "test_policy_shift"
    return "monitoring_immature"

case_cohort_df["split"] = case_cohort_df["case_start_time"].apply(assign_split)

# 4. Point-in-Time Prefix Generation & Leakage Firewall

prefixes_df = pm4py.get_prefixes_from_log(log_df, length=PREFIX_LENGTH, case_id_key="case:concept:name")

# Identify the exact prediction timestamp t_pred for each case
t_pred_per_case = prefixes_df.groupby("case:concept:name")["time:timestamp"].max().rename("t_pred")
prefixes_df = prefixes_df.merge(t_pred_per_case, on="case:concept:name", how="left")

# Leakage Audit & Firewall: Drop post-prefix fields and enforce temporal boundaries
LEAKAGE_COLUMNS = [
    "final_limit", "decision_reason", "collection_status",
    "default_90d", "label_available_at", "data_extract_time"
]
feature_events = prefixes_df.drop(columns=[c for c in LEAKAGE_COLUMNS if c in prefixes_df.columns])

assert (prefixes_df["time:timestamp"] <= prefixes_df["t_pred"]).all(), "Lookahead event leakage detected!"
for col in LEAKAGE_COLUMNS:

train_cids = set(case_cohort_df[case_cohort_df["split"] == "train"]["case:concept:name"])

features["elapsed_seconds"] = (features["t_pred"] - features["t_start"]).dt.total_seconds()
