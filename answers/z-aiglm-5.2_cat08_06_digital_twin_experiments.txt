# Simulation-Based Digital Twin for a Municipal Building-Permit Process

## 1. Model scope and state variables

### Boundary and level of detail
The digital twin models the end-to-end permit lifecycle from portal submission to permit issuance or rejection. It is a discrete-event simulation (DES) at the case-activity level, not a continuous or purely analytical queueing model. Each case is a simulation entity that moves through activities; resources are modeled as pools with calendars; cross-case dependencies are explicitly represented so that the twin is not an independent-case simulator.

The twin excludes case activities outside the municipal boundary (e.g., the applicant’s internal drafting effort) except where they produce observable delays, such as missing-document response time and public-notice objection periods.

### Primary entities
- **Case**: a permit application with type, district, architect_id, application_value, and attribute flags `requires_fire`, `requires_environment`, `requires_public_notice`.
- **Case family**: a set of cases sharing the same `architect_id` and district within a short submission window; used for inspection bundling and correlated arrival bursts.
- **Resource pool**: clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, and system tasks.
- **Task instance**: an activity to be executed by a resource, with routing, rework flags, and dependency pointers.

### State variables
- `case_id`, `case_type`, `district`, `architect_id`, `application_value`, `arrival_time`, `current_state`, `pending_parallel_reviews`, `rework_count`, `violation_history`, `bundle_id`.
- `resource_pool`: number of FTEs, current assignments, scheduled availability, and calendar interruptions.
- `queue_state`: per-activity FIFO/priority queues, including aging-case priority.
- `calendar_state`: working hours, holidays, council-meeting weeks, field-visit days.
- `inspection_bundle`: open bundles per district with a maximum bundle size and maximum waiting time before release.
- `objection_proxy_state`: latent variable representing whether objections occur; not directly observed but inferred from public-notice duration tail.
- `backlog`: count of cases waiting for each resource pool.
- `sla_clock`: elapsed time per case against type-specific target durations.

### Resources, queues, calendars
- Clerks: 5 FTE, Monday-Friday 08:00-16:00; one clerk dedicated to portal support on Mondays.
- Planners: 8 FTE, 09:00-17:00; two restricted to Simple renovation.
- Fire reviewers: 2 FTE equivalent, Tuesday-Thursday only.
- Environmental reviewers: 3 FTE, Monday-Friday, 40% reserved for non-permit duties.
- Inspectors: 4 FTE, Tuesday-Friday field visits; district-dependent travel.
- Legal officers: 2 FTE, blocked during council-meeting weeks except urgent cases.
- System tasks: effectively unlimited.
- Queues are activity-specific. Planning and Legal check use aging-aware priority under D6. Inspection scheduling uses district batching under D3 and D10.

### Cross-case dependencies
- **Arrival correlation**: large architects submit bursts within the same week.
- **Resource contention**: cases compete for the same scarce pools (fire, environmental, legal, inspectors).
- **Inspection bundling**: same architect + same district within a batching window may be grouped.
- **Public-notice coupling**: neighborhood objections may affect several related cases, although the objection event itself is missing from the log.

## 2. Parameter-estimation plan

### PM4Py log/model handling
PM4Py is used for event-log loading, formatting, variant discovery, direct-following graph (DFG) discovery, performance DFG discovery, and process-tree parsing. It is not used as the simulation engine; the simulation engine is a separate module that consumes PM4Py-derived parameters.

### Arrival estimation
- Estimate baseline daily arrival rate from first-event timestamps per case.
- Fit a non-homogeneous Poisson process (NHPP) with multipliers for month-of-year and day-of-week.
- Model Monday multiplier (2.2x Wednesday) and seasonal multiplier (1.7x in March-May and September-November).
- Model architect bursts by sampling a fraction of arrivals (top 20 architect_ids, 31% of volume) as batched submissions within a short window, using an empirical inter-arrival distribution within bursts.

### Service-time estimation
- For activities with both start and end timestamps, estimate service-time distributions directly via PM4Py performance DFG and case-level elapsed times.
- For activities with only completion timestamps, the observed inter-event time is a convolution of waiting time and service time. We do **not** collapse these into a single “processing time” without acknowledging the limitation. Instead, we decompose using resource calendars and queueing assumptions: assume the resource works on one case at a time and infer service time from the distribution of completion gaps conditional on resource availability; waiting time is the residual.
- Fit parametric or empirical distributions per activity and case type. Use lognormal or gamma families for most activities; use a mixture or Pareto tail for heavy-tailed applicant responses and public-notice durations.

### Waiting-time estimation
- Do not estimate waiting time as an independent random variable. Waiting is endogenous: it emerges from resource contention and calendars in the simulation.
- Use empirical waiting summaries only for validation targets, not as direct inputs, except where waiting is applicant-driven (e.g., Receive missing documents, Public-notice period).

### Branching probabilities
- Estimate branching probabilities from variant frequencies and routing summaries using PM4Py variants.
- Override estimates with known deterministic rules:
  - Fire-safety review when `requires_fire=yes` or building area exceeds threshold.
  - Environmental review when `requires_environment=yes` or district is environmentally sensitive.
  - Public-notice period for Complex variance and qualifying New residential cases.

### Rework estimation
- Rework is modeled as a return to an earlier activity (Planning review, Inspection, Legal check, or Decision drafting after appeal).
- Estimate rework probabilities per case type and per preceding activity from repeated activity occurrences in variants.
- Since rework reasons are unstructured and not reliably coded, rework is modeled as a stochastic loop with a fitted probability, not as a reason-conditioned transition.

### Resource calendars
- Use the HR-reconstructed calendars as structural constraints, not as fitted distributions.
- Model holiday and council-meeting interruptions as blocked intervals for Legal check and Public-notice period.
- Model environmental reviewers with a 40% capacity reduction.

### Cross-case dependencies
- Estimate inspection travel-time parameters per district from site inspection timing, acknowledging that travel is not separately logged; use p90 service time as an upper bound proxy for travel-heavy inspections.
- Estimate bundling benefit as a reduction in per-case travel when multiple same-district cases share a visit.
- Estimate public-notice objection frequency indirectly: because objection events are missing, use the bimodal/hyper-tailed public-notice duration as a proxy and explicitly model a latent objection indicator. Do not claim objection events are observed.

### Missing data handling
- Missing start timestamps: use calendar-aware decomposition as above; report sensitivity to the decomposition assumption.
- Missing objection events: model latent objections; do not treat extended public-notice durations as deterministic.
- Incomplete environmental sensitivity and building area: use a probabilistic trigger with the available flags plus a residual probability for unobserved triggers.
- Flattened log: cross-case dependencies are reconstructed from architect_id and district co-occurrence, not from explicit family IDs.

## 3. Assumptions

### Arrivals
- Arrivals follow a day-of-week and season-modulated NHPP.
- Monday bursts are real demand effects, not just portal logging artifacts.
- Architect bursts are modeled as correlated arrivals, not as independent Poisson draws.

### Service times
- Service times are resource- and activity-specific and are independent of waiting time once a case begins processing.
- Activities without start timestamps are modeled with a latent start inferred from resource calendars.
- Heavy-tailed activities (Environmental review, Receive missing documents, Public-notice period) use distributions with explicit tail parameters.

### Routing
- Deterministic rules take precedence over fitted probabilities when attribute flags are present.
- When flags are missing or unreliable, a residual routing probability is applied.
- Decision drafting waits for all applicable parallel reviews and the public-notice period to complete.

### Resources/calendars
- Resources are non-preemptive except where explicitly modeled (e.g., urgent legal cases during council weeks).
- The 40% environmental reservation is modeled as a capacity reduction, not as a separate queue.
- System tasks have effectively unlimited capacity and zero queueing.

### Rework
- Rework loops return to the designated earlier activity and re-enter the queue.
- Rework probability is conditioned on case type and preceding activity, not on unobserved reason text.
- Each rework pass may have a different service-time distribution (rework is often longer).

### Applicant/third-party response
- Applicant response times are modeled separately from municipal service times.
- Third-party objection durations are latent and affect public-notice period; they are not observed events.

### Cross-case dependencies
- Inspection bundling is optional and controlled by policy (D3/D10).
- Architect-level arrival correlation is modeled; architect-level resource assignment is not.
- Neighborhood objection correlation is approximated by district-level latent objection shocks, not case-pairwise links.

### Non-stationary demand
- Seasonal and weekly patterns observed in the log persist into the simulation horizon.
- No long-term trend growth is assumed unless explicitly added as a stress scenario.

### Missing data
- Missing start timestamps do not bias the service/waiting decomposition beyond the modeled sensitivity range.
- Missing objection events are represented as latent variables, not as censored observations of a known event.
- HR calendars are accurate for normal weeks; holiday and council-week interruptions are treated as known blocks.

## 5. Warm-up, replications, and uncertainty treatment

### Warm-up
- Warm-up length is determined by the time to reach steady-state backlog. Because demand is non-stationary, steady-state is seasonal rather than constant; we use Welch’s method on weekly backlog to choose a warm-up of at least one full seasonal cycle, approximately 12 months.
- Warm-up data are discarded before computing performance metrics.

### Run length and replications
- Simulation horizon: 24 months after warm-up to cover two annual cycles.
- Replications: 50 per scenario for primary metrics; 200 for tail-sensitive metrics (p90, SLA compliance).
- Random seeds: use common random numbers across paired scenarios; report seed ranges for reproducibility.

### Confidence intervals
- Report 95% confidence intervals for mean metrics using replication means.
- For tail metrics, report empirical percentiles with bootstrap intervals rather than normal approximations.

### Heavy-tailed durations
- Fit heavy-tailed distributions (e.g., lognormal, Pareto tail) for Receive missing documents, Public-notice period, and Environmental review.
- Use a mixture model for public-notice duration: a fixed minimum plus an objection-driven tail component.
- Sensitivity analysis on tail parameters: vary tail index and objection probability.

### Sensitivity analysis
- One-at-a-time sensitivity on: missing-doc reduction effectiveness (D1), no-inspection threshold (D2), batch size and max wait (D3), extra inspector FTE (D4), triage accuracy (D8), objection early-warning effect (D9).
- Global sensitivity via a small fractional factorial design across the most uncertain parameters.

### Uncertainty from missing data
- Propagate service/waiting decomposition uncertainty as a parameter range.
- Propagate latent objection probability as a prior with credible intervals.
- Do not report point estimates as exact; report interval estimates and robustness across assumptions.

## 6. Validation strategy

### Face validation
- Review the process model, routing rules, and calendars with domain experts.
- Confirm that rework loops, parallel reviews, and public-notice periods behave as described.

### Event-log replay validation
- Replay the historical event log through the process model using PM4Py alignment/conformance where feasible.
- Check that the discovered DFG and performance DFG are consistent with the simulation’s activity ordering and parallelism.

### Distributional validation
- Compare simulated activity-level waiting and service-time distributions to empirical summaries (median, p90).
- Use two-sample tests (e.g., Kolmogorov-Smirnov) on per-case cycle times, with multiple-comparison awareness.

### Resource-utilization validation
- Compare simulated resource utilization per pool to HR-derived expectations.
- Flag pools where simulated utilization diverges significantly from operational reality.

### Bottleneck validation
- Identify historical bottlenecks from performance DFG and queue summaries.
- Confirm the simulation reproduces the same primary bottlenecks (Planning, Legal, Environmental, Inspection).

### Out-of-sample validation
- Split the 18-month log into training (first 12 months) and holdout (last 6 months).
- Estimate parameters on training data; validate arrival patterns, cycle-time distributions, and SLA compliance on holdout data.
- Report out-of-sample error for median and p90 cycle time per case type.

### Cross-case dependency validation
- Validate inspection bundling behavior against same-district, same-week co-occurrence patterns.
- Validate architect burst arrival patterns against empirical burst statistics.

## 7. Decision criteria

### Primary metrics
- **Median cycle time** per case type.
- **p90 cycle time** per case type, reflecting tail risk.
- **SLA compliance rate** by case type (e.g., Simple  30d, New residential  90d, Commercial  120d, Complex variance  180d). Thresholds are illustrative and should be confirmed with the municipality.

### Fairness metrics
- Cycle-time disparity across districts (especially D3 and D5).
- Cycle-time disparity across architects (small vs large).
- Disproportionate impact on any case type.

### Resource and backlog metrics
- Average and peak utilization per resource pool.
- Backlog size and age distribution per pool.
- Overtime or capacity-expansion cost proxy for temporary resources.

### Rework and quality metrics
- Rework loop frequency per case type.
- Estimated inspection-skip risk for D2/D10 (proxy via historical violation rates where available).
- Environmental triage misclassification risk for D8.

### Robustness metrics
- Performance under stress scenarios S1-S4.
- Standard deviation of cycle time across replications.
- Sensitivity of conclusions to heavy-tail and missing-data assumptions.

### Selection rule
- Prefer interventions that improve median and p90 cycle time with non-overlapping confidence intervals versus baseline.
- Reject interventions that materially worsen fairness or resource utilization above sustainable thresholds (e.g., sustained utilization > 85%).
- For combined policies, require that the improvement exceeds the best single intervention by a meaningful margin and remains robust under at least two stress scenarios.
- Do not claim optimality; report interventions as Pareto-improving candidates under stated assumptions.

def load_and_format_log(path: str) -> pd.DataFrame:
    """Load CSV and format with PM4Py conventions."""
    df = pd.read_csv(path)
    # Preserve case attributes that PM4Py format_dataframe will carry if present
    df = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",

def analyze_log(df: pd.DataFrame) -> Dict[str, Any]:
    """Compute variants, DFG, performance DFG, and arrival stats."""
    variants = pm4py.get_variants(df)
    dfg, sa, ea = pm4py.discover_dfg(df)
    perf_dfg, perf_sa, perf_ea = pm4py.discover_performance_dfg(df)

    # Case arrival average (cases per day)
    arrivals = df.groupby("case:concept:name")["time:timestamp"].min()
    arrivals = arrivals.sort_values()
    if len(arrivals) > 1:
        inter_arrival = arrivals.diff().dropna().dt.total_seconds() / 86400.0
        arrival_rate_per_day = 1.0 / inter_arrival.mean() if inter_arrival.mean() > 0 else 0.0
    else:
        arrival_rate_per_day = 0.0

    return {
        "variants": variants,
        "dfg": dfg,
        "start_activities": sa,
        "end_activities": ea,
        "perf_dfg": perf_dfg,
        "perf_start_activities": perf_sa,
        "perf_end_activities": perf_ea,
        "arrival_rate_per_day": arrival_rate_per_day,
        "arrivals": arrivals,
    }


def compute_duration_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Add inter-event duration per case.
    NOTE: Because many activities have only completion timestamps, the
    'inter_event_duration' is a convolution of waiting and service time.
    The simulation engine must decompose these using resource calendars;
    do not treat this column as pure service time.
    """
    df = df.copy()
    df = df.sort_values(["case:concept:name", "time:timestamp"])
    df["prev_timestamp"] = df.groupby("case:concept:name")["time:timestamp"].shift(1)
    df["inter_event_duration_s"] = (
        (df["time:timestamp"] - df["prev_timestamp"]).dt.total_seconds()
    )
    df["inter_event_duration_h"] = df["inter_event_duration_s"] / 3600.0
    df["inter_event_duration_d"] = df["inter_event_duration_s"] / 86400.0
    return df
