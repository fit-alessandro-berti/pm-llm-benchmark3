# 5. PM4Py role-discovery and similarity code

```python
import pandas as pd
import pm4py

# 1. Load and format event log dataframe
df = pd.read_csv("order_to_resolution_log.csv")
df = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource"
)

# 2. Discover organizational roles using PM4Py
roles = pm4py.discover_organizational_roles(df)
print("Discovered Organizational Roles:", roles)

# 3. Discover activity-based resource similarity
similarity_matrix = pm4py.discover_activity_based_resource_similarity(df)
print("Activity-Based Resource Similarity Matrix:")
print(similarity_matrix)

# 4. Compute handover-of-work and working-together networks
handover_net = pm4py.discover_handover_of_work_network(df)
working_together_net = pm4py.discover_working_together_network(df)
print("Handover of Work Network nodes/edges:", len(handover_net.get("nodes", [])))
print("Working Together Network nodes/edges:", len(working_together_net.get("nodes", [])))

# 5. Enrich role-discovery output with case complexity and substitution indicators
# Merge case complexity back into event log for analysis per resource
complexity_df = df[["case:concept:name", "case_complexity", "temporary_substitution"]].drop_duplicates()
enriched_df = pd.merge(df, complexity_df, on="case:concept:name", how="left")

# Aggregate workload profiles by resource, including median complexity
resource_profile = enriched_df.groupby("org:resource").agg(
    total_events=("concept:name", "count"),
    unique_cases=("case:concept:name", "nunique"),
    temp_subs_touched=("temporary_substitution", lambda x: (x.notnull() & (x != "none")).sum())
).reset_index()

print("Enriched Resource Profile Summary:")
print(resource_profile.head(15))

# 6. Guardrail against naive frequency clustering:
# Check if resources with similar activity frequencies have disparate complexity profiles
complexity_summary = enriched_df.groupby(["org:resource", "case_complexity"]).size().unstack(fill_value=0)
print("Case Complexity Distribution per Resource:")
print(complexity_summary)
```

# 6. Operational interpretation

- **Staffing & Capacity Planning:** Management should not rely on raw event counts or simple activity-frequency clustering to size teams. For instance, treating Giorgio (Front Office) as a substitute for Fatima (Commercial) creates hidden inefficiencies, as evidenced by the doubling of pricing duration during substitution episodes. Staffing models must account for domain certifications and case complexity distributions.
- **Training & Risk Control:** The high reopen rate (17 cases) originating from temporary agents (Kai and Lina) indicates that onboarding must enforce strict validation training. Furthermore, Mateo's filtering of security reviews during Weeks 7–8 created critical delays (>2 days), showing that routing power should not be delegated without formal security governance protocols.
- **Resilience:** Cross-functional roles like Mateo provide vital agility during unexpected absences (e.g., Hana's audit workshop), but relying on informal bridging without clear decision authority leads to rework (13 out of 21 preliminary approvals rejected). Formalizing delegation paths will mitigate these operational risks.

### Cautions for Change Management:
1. **Misinterpreting Shadow Substitutions as Proficiency:** Just because a resource (e.g., Giorgio or Mateo) stepped in during an absence does not mean they can absorb that role permanently without sacrificing speed or quality (as seen in duration spikes and rework rates).
2. **Ignoring Complexity Boundaries:** Assigning high-complexity or critical cases to resources mined into a generalist cluster based solely on activity names will degrade resolution times and customer satisfaction. Role definitions must be bounded by case complexity metrics and risk profiles, not just process traces.
