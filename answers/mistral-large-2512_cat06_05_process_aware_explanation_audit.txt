## 2. Process-model consistency checks

**Validation Suite Design:**
1. **Prefix-Time Availability Check**
   - *Method*: For each feature, verify that its value can be computed using only events with timestamps  `t0`.
   - *Tool*: SQL query with `WHERE event_timestamp <= t0` or process mining tool with prefix filtering.
   - *Limitation*: Does not catch features derived from future events but stored with incorrect timestamps (e.g., `same_day_document_count_snapshot`).

2. **Activity-Order Feasibility Check**
   - *Method*: Use a declarative process model (e.g., Declare constraints) to flag impossible activity sequences.
     - Example: `Claim Closed` cannot precede `Damage Assessment Completed`.
   - *Tool*: PM4Py or ProM with Declare miner.
   - *Limitation*: False positives if normative process allows rare exceptions (e.g., parallel fraud investigation).

3. **Same-Timestamp Ambiguity Check**
   - *Method*: For events with identical timestamps, verify if a reliable sequence index exists. If not, flag as ambiguous.
   - *Tool*: SQL query to count events with `event_timestamp = t0` and missing `sequence_index`.
   - *Limitation*: May overlook cases where sequence index is present but unreliable.

4. **Complete-Trace Feature Check**
   - *Method*: For each feature, check if its definition references events after `t0` (e.g., `appeal_seen_anywhere`).
   - *Tool*: Static analysis of feature SQL or process mining tool with trace slicing.
   - *Limitation*: May miss features that *appear* prefix-based but use future data (e.g., `final_handler_team`).

5. **Enabled/Impossible/Future-Possible Check**
   - *Method*: At `t0`, classify activities as:
     - *Enabled*: Can occur next (e.g., `Damage Assessment Completed` in fast track).
     - *Impossible*: Cannot occur next (e.g., `Appeal` before `Settlement Decision`).
     - *Future-Possible*: May occur later (e.g., `Fraud Investigation Opened`).
   - *Tool*: Alignments or prefix automata (e.g., using PM4Py).
   - *Limitation*: Requires normative process model; may not handle parallel paths well.

6. **Repeated Settlement Decision Check**
   - *Method*: Verify that `Settlement Decision Recorded` appears twice only if an `Appeal` occurs between them.
   - *Tool*: SQL query to count `Settlement Decision` events per case and check for intervening `Appeal`.
   - *Limitation*: May not catch cases where `Appeal` is mislabeled.
