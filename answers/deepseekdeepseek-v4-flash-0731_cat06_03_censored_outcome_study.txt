## 1. Target definition

**Primary target.**  
For every application that is still under review at the prediction landmark, define a multi-state outcome:

- `AD` = the case is eventually Account Activated and a default is recorded within 90 days after Activation;
- `AN` = the case is Account Activated and does **not** default within 90 days after Activation;
- `REJ` = Rejected before Activation;
- `WD` = Withdrawn before Activation;
- `TR` = Transferred before Activation;
- `OPEN`/`CENS` = still open, or activated but the 90-day outcome is not yet known at the data-extraction cutoff.

The primary estimand is the cumulative incidence probability of `AD`, conditional on the event history available at the prediction landmark:

\[
p_{AD} = P(\text{activated and default within 90 days after activation} \mid \mathcal{H}_{\tau})
\]

where \(\mathcal{H}_{\tau}\) is the prefix of events available at prediction time \(\tau\). The model should ideally output a vector of state probabilities, not only a binary “default vs non-default.” In particular, `REJ`, `WD`, and `TR` are competing terminal states, not “non-default” labels.

**Prediction time.**  
Default is defined after activation, and activation is an intermediate event. We therefore set the prediction landmark at the end of the first \(k\) events after Application Started, defaulting to \(k=3\). For sensitivity, we also consider an elapsed-time landmark, e.g., 72 hours after Application Started.

**Unit of analysis.**  
One credit application.

**Population.**  
All 48,000 applications started between 1 January 2024 and 31 December 2025 and present in the event file.

**Horizon.**  
The default event is observed within 90 days after Account Activated. Because activation may occur after the prediction landmark, the target is a time-to-event / multi-state target, not a simple binary outcome at a fixed calendar horizon. For evaluation, we use an administrative horizon \(H\) from application start, e.g., 12 or 18 months, and handle cases not followed to \(H\) as censored.

**Alternative target.**  
A credible alternative is the conditional default target:

\[
P(\text{default within 90 days after activation} \mid \text{Accounts Activated}, \mathcal{H}_{\tau})
\]

This answers a different question: “If this application is activated under the current policy, how likely is it to default?” It is useful for post-acceptance credit-risk segmentation, but it is not a prediction for all applications because rejected, withdrawn, transferred, and still-open cases have no defined activation outcome.

| Activated, default within 90 days, label mature | 2,700 | `default_90d = 1` | `AD` |
| Activated, 90-day outcome not yet mature / delayed feed / permanently missing feed | 3,600 | omitted | censored or `activated_missing_label` |
| Rejected | 9,100 | omitted | competing terminal state `REJ` |
| Withdrawn | 5,700 | omitted | competing terminal state `WD` |
| Transferred | 2,900 | omitted | competing terminal state `TR` on the original application; linked-platform follow-up is a sensitivity |
| Still open at extraction | 5,100 | omitted | right-censored at data extraction |
| **Total** | **48,000** | | |

**Inclusion rules.**
- Include all applications whose earliest `Application Started` event is between 1 January 2024 and 31 December 2025.
- For the fixed-count landmark, include only cases that have at least \(k\) events and whose \(k\)-th event occurs before any decision/activation event (`Accepted`, `Rejected`, `Withdrawn`, `Transferred`, `Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`).
- Cases with fewer than \(k\) events, or whose terminal event occurs before the landmark, are not scorable in the fixed-count primary analysis. They are included in the elapsed-time sensitivity.

**Exclusion rules.**
- Do not exclude rejected, withdrawn, or transferred cases from the multi-state target.
- Do not merge transferred cases into the original application unless explicitly defining a partner-platform outcome in a sensitivity analysis.
- Do not use any event after the prediction landmark for feature construction.

**As-of rules.**
- A feature is available only if its value is knowable at the prediction time.
- `label_available_at` is used only to decide whether the outcome is known, never as a feature.
- Nightly snapshot features such as `documents_total` are only valid if their snapshot time is strictly before the prediction time.

## 3. Censoring and missing-label strategy

We distinguish five mechanisms.

1. **Ordinary right censoring**  
   Applications still open at 15 February 2026, or activated accounts whose 90-day default window has not yet elapsed, are right-censored.

2. **Delayed labels**  
   The external feed arrives 7–35 days after the 90-day horizon. An activated account whose `default_90d` is not yet present at the extraction cutoff is censored, even if the 90-day window has elapsed.

3. **Selection through activation**  
   Default is observable only after activation. In the primary multi-state target, activation is an intermediate state, not a missingness mechanism. In the conditional-default alternative, the activated cohort is a selected population; inference is then conditional on activation, and application to never-activated cases is a counterfactual claim.

4. **Transfer as a competing event or missing follow-up**  
   In the primary analysis, transfer before activation is a competing terminal event for the original application. Linked transfer outcomes are not merged into the original target because the partner platform may have different policies and data semantics.

5. **Permanently missing outcome feeds**  
   Partner-originated activated accounts can have permanently missing outcomes. If the missing feed is related to default risk, treating it as independent censoring can bias estimates.

**Primary analysis strategy.**  
Use a multi-state model with cause-specific hazards for transitions:

- Application Start / Review  Activation;
- Application Start / Review  Rejected;
- Application Start / Review  Withdrawn;
- Application Start / Review  Transferred;
- Activated  Default within 90 days;
- Activated  No default after 90 days.

These hazard models are combined with an Aalen–Johansen estimator to obtain the cumulative incidence of `AD`. Right-censoring is handled at the event time level. Activated cases without a mature label are censored at the later of activation + 90 days or their expected feed-lag date, but no later than the extraction cutoff.

**Sensitivity analyses.**
1. **Inverse probability of missing-label weighting** among activated accounts: estimate the probability that the outcome feed is observed, and weight complete-label activated cases by the inverse of that probability. This assumes missingness is explainable by observed features and prior events.
2. **Tipping-point analysis**: impute the missing default rate over a plausible range and examine how \(p_{AD}\) changes.
3. **Elapsed-time landmark**: use a 72-hour elapsed prefix instead of a fixed event-count prefix, so short cases are not excluded.
4. **Linked-transfer sensitivity**: when the linkage table is available and the partner outcome is defined in the same way, rerun the analysis with transfer outcomes as a separate state.

**Testable / partially testable / untestable.**
- Testable: whether missing feed rates differ by region, channel, source system, or prefix features.
- Partially testable: whether censoring is independent of the event process, using comparisons between early and late cohorts.
- Fundamentally untestable: nonignorable missingness; counterfactual default of rejected applications under an altered acceptance policy.

## 4. Prefix extraction

**Fixed event-count prefixes.**  
The primary landmark uses the first \(k\) events per case. We apply a canonical activity mapping and then truncate each case at its \(k\)-th event. The prediction time is the timestamp of the \(k\)-th event. All later events are removed before feature construction.

**Elapsed-time prefixes.**  
For sensitivity, define a cutoff

\[
\text{cutoff}_i = \text{Application Started}_i + 72 \text{ hours}
\]

and keep all events with `time:timestamp <= cutoff_i`. This naturally includes short cases and repeated document loops.

**Handling short cases.**  
In the fixed-count primary, cases with fewer than \(k\) events before a decision/terminal event are not assigned a valid early-warning landmark. They are not silently dropped from the study; they are included in the elapsed-time sensitivity. In the multi-state model, they may still contribute to the cohort-flow and censoring description.

**Repeated document loops.**  
Loops are not collapsed. In fixed-count prefixes, each loop event consumes one prefix position. Loop counts and rework indicators are extracted as features. The directly-follows graph should be computed on prefix data only, not full traces.

**Activity renaming and duplicate events.**  
A mapping table canonicalizes activity names before and after the 15 October 2025 migration. Exact duplicate event rows are removed using case, activity, timestamp, resource, and source system. A migration-period flag is added as a feature so the model can account for data-generating changes.

## 5. Process-aware features

Feature categories are separated by availability.

**Static case attributes.**
- `case:channel`
- `case:region`
- `case:requested_amount`
- `source_system`
- Application start time, day-of-week, month, policy-period indicator (pre/post 1 July 2025), migration-period indicator.

**Prefix-derived features.**
- Number of events in prefix.
- Distinct activities in prefix.
- Presence and count of document requests.
- Count of returns from document request to Credit Review.
- Rework indicator: Credit Review appearing after Request Documents.
- First and last activity in prefix.
- Variant identifier or variant frequency from the prefix log.
- Elapsed time since Application Started.
- Inter-event durations within the prefix.
- Latest `risk_score` available before the prediction time, and its change from the first available value.

**Resource / queue features.**
- `org:resource` identifiers for KYC and Credit Review events.
- Number of distinct resources seen in the prefix.
- Resource load computed from historical events before the prediction time, e.g., number of cases handled by that resource in the previous 7 days.

**Historical reference features.**
These are computed only from training cases whose events occurred before the current prediction time:
- Average duration from KYC to Credit Review.
- Frequency of document-request rework.
- Region/channel historical default rates among activated cases.
- Directly-follows transition probabilities.

Features such as `final_limit`, `decision_reason`, and `collection_status` are not available at the early prediction landmark and are excluded.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Contains the final credit decision and approved limit; unavailable before decision | Only available after the final credit decision | **Drop** | Early warning must be before the final decision |
| `decision_reason` | Reveals Accept/Reject and possibly the reason | Populated at or after Accept/Reject | **Drop** | Would directly leak the terminal/selection outcome |
| `collection_status` | Updated after activation and may directly reveal default | Only after activation | **Drop** | This is part of the outcome or a post-outcome process, not a predictor |
| Future events | Contract Signed, Account Activated, Collections Contact, Default Recorded can occur after the prediction time | Only events with timestamp <= prediction time may enter the prefix | **Repair by truncation** | Prefix extraction and feature construction must remove future rows |
| `documents_total` | Nightly snapshot can include documents uploaded later on the same calendar day than the nominal prediction time | Use snapshot time < prediction time; if only daily snapshot is available, shift its valid time to the start of the next day or previous day | **Repair / drop if no snapshot time** | Otherwise same-day documents leak information after the prediction moment |
| Updated `risk_score` | Later updates may incorporate information not available at prediction time | Keep only the latest value with `time:timestamp <= prediction time` | **Keep after truncation** | The last valid risk score is legitimate |
| Resource experience | Stored as experience at extraction time, not event time | Use experience as of the event time if an HR table exists | **Repair or drop** | Extraction-time experience is future information |
| `default_90d` | This is the label | Only used for target construction; not for feature extraction | **Drop as feature** | Outcome leakage |
| `label_available_at` | Label maturity time | Only used to define whether target is known | **Drop as feature** | Outcome timing is not a predictor |
| `source_system` | Known at start, but partner-originated cases may have missing feed | Available at event time | **Keep** | Useful for missingness modeling |

## 7. Validation design

A random case split is misleading here because:

- cases starting later have less mature labels;
- the 1 July 2025 policy change alters selection and outcome relationships;
- the 15 October 2025 migration changes event names and creates duplicates;
- random splits can put future cases into training and past cases into validation, violating temporal causality.

**Temporal validation scheme.**

1. Sort all applications by `start_time`.
2. Use an expanding-window or rolling-origin design:
   - **Train**: applications started before the validation month;
   - **Validation**: applications started in the current validation month;
   - **Holdout/test**: a final period used only once, e.g., the last 6 months with mature labels or the latest censored cohort evaluated only with survival metrics.
3. For each validation month, fit on all earlier data and score only cases whose prediction landmark occurs in that month.
4. Evaluate the cumulative incidence of `AD` at a fixed administrative horizon \(H\), e.g., 12 months from application start, using IPCW to handle cases not followed to \(H\).

**Policy change.**  
Include a policy-period indicator and interactions in the model. Evaluate pre-policy and post-policy subgroups separately. If the post-policy labels are not mature, report interim metrics after maturity is reached.

**System migration.**  
Apply the canonical activity mapping before training. Validate separately for pre-migration and post-migration cases. Remove exact duplicate events and check whether event-name distributions changed.

**Label maturity.**  
For binary metrics, do not use cases whose `label_available_at` is after the extraction cutoff as known outcomes. Use survival/competing-risk metrics instead:

- IPCW time-dependent Brier score for cumulative incidence of `AD`;
- Cause-specific AUC;
- Calibration slope and reliability curves for predicted cumulative incidence;
- Subgroup performance by region, channel, requested amount band, and policy period.

**Distribution shift.**  
Compare feature distributions between train and validation/test cohorts using standardized mean differences or Kolmogorov–Smirnov statistics. Large shifts should trigger a warning that the model needs recalibration before deployment.

## 8. Limitations and decision-use boundary

This study can claim:

- predictive association between early prefix features and the probability that an application eventually activates and defaults within 90 days under the historical process;
- a fair comparison of models under explicit censoring, missing-feed, and competing-event assumptions.

This study cannot claim:

- that rejected or withdrawn applications “would not have defaulted” if activated;
- a counterfactual default-risk estimate for cases whose activation status was changed by policy;
- unbiased causal estimates of the effect of an intervention on default.

**Selection effects.**  
Activation policy selects which applications enter the default-at-risk set. If the lender changes approval policy, the joint distribution of activation and default changes. The conditional default model among activated accounts will not automatically generalize to a different activated population.

**Missing feed risks.**  
Partner-originated activated accounts have a higher chance of permanently missing outcome feeds. If missingness is related to default risk, primary estimates may be biased.

**Deployment can change the data-generating process.**  
At least three ways:

1. If the model is used for early intervention, collections and customer behavior will change, and defaults may decrease.
2. If lenders use the score to reject or withdraw applications, the activated population changes and the observed default rate changes.
3. If applicants learn that the model exists, application composition and self-selection may change.
4. If policy thresholds or partner-transfer rules change in response to the model, the transition probabilities to `REJ`, `WD`, and `TR` also change.
