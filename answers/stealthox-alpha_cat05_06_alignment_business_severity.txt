## 1. Materiality Framework

**Principle:** Raw alignment cost measures edit distance under a uniform cost function (every visible move = 1). It is a *searchlight*, not a *scale*. Business severity is assessed on a separate axis using the following dimensions:

| Dimension | Question it answers | Weight guidance |
|---|---|---|
| **Control objective** | Which control/policy was defeated? Breaches of preventive authorization controls (P2, P3) outrank record-keeping defects (P4 evidence, labels). | Highest |
| **Amount / exposure** | How much money was or could have been moved? EUR 480,000 unevidenced  EUR 800 noise. | High |
| **Reversibility** | Funds paid are irreversible; a missed log line can be backfilled; a notification can be re-sent. Irreversible + unauthorized = top tier. | High |
| **Timing** | Pay-before-approve, bank change 1h before payment, notification inside/outside 24h. Proximity of red-flag events to money movement amplifies risk. | High |
| **Customer / regulatory harm** | Was the claimant treated correctly? Would an auditor/regulator view the control as operating? | Medium |
| **Recurrence / systemicity** | One-off vs. 74 retries/month or 4 data-blind auto-approvals. Systemic issues compound and mask each other. | Medium |
| **Evidence reliability** | Signed external report > immutable log > mutable CRM text field > verbal assertion. Lower reliability  higher residual risk at same "fact pattern." | Medium |
| **Model scope legitimacy** | Traces outside the agreed model scope (P6 dispute) are not deviations at all, even at maximal cost. | Gate |

**Severity anchors (1–5):**
1. **Negligible** – harmless technical noise or fitting artifacts; no business meaning.
2. **Minor** – record-keeping/evidence-hygiene gaps; substantive controls demonstrably operated.
3. **Moderate** – real policy breach with bounded exposure and no fraud indicators.
4. **Major** – control bypass with active fraud indicators, or systemic unauthorized approvals.
5. **Critical** – irreversible severe control failure (pay-before-approve) or large unevidenced exposure on maximum-risk profiles.

**Confidence is a separate axis:** it expresses how reliable our *interpretation* is given evidence quality (stable IDs, immutable logs, corroboration), not how bad the outcome is. A case can be Severity 5 / Medium confidence (CL-602: we know evidence is absent, we don't know whether the screen ran) or Severity 1 / High confidence (CL-601). Action logic follows the matrix: **High-Sev/High-Conf  contain now; High-Sev/Low-Conf  investigate first, fast; Low-Sev/High-frequency  engineer out in bulk.**

**Deviation taxonomy used throughout (mutually exclusive primary class):**
process-model mismatch · event-label mismatch · missing evidence · actual operational deviation · data-aware policy failure · harmless technical noise.

## 4. Causal Hypotheses and Evidence Tests

A missing log event is **never proof** an activity did not occur; each block below separates what the log shows from what the world may have done.

**1. CL-602 — absent Fraud Screen on €480k.**
- H1 *Skipped deliberately* under time pressure (operational deviation). H2 *Performed informally/verbally*, never recorded (procedural workaround). H3 *Ran in a separate fraud system* not integrated with the core log (logging gap).
- Discriminating evidence: fraud-system and screening-queue queries by case ID and timestamp window; approver's workstation session logs; whether peer high-risk cases the same day have screens (if *only* this one lacks it  H1/H2; if a systematic subset lacks it  H3).

**2. CL-604 — payment at 10:03, approval recorded 10:20.**
- H1 *Genuine bypass*: payment initiated before approval to hit a cut-off. H2 *Verbal approval given earlier, recorded later* (recording lag). H3 *Clock/timezone skew* between bank rail and core system. H4 *Batch settlement fired early*.
- Discriminating evidence: NTP/timezone reconciliation of both systems; payment-initiation request timestamp at the gateway vs. bank acceptance; approval workstation audit trail (was the approval form opened before 10:03?); whether other same-day payments show the same lag signature.

**3. CL-610 (and the 4-case pattern) — auto-approve despite P1/P2.**
- H1 *Rule misconfiguration*: bank-change recency condition absent from the approval rule. H2 *Stale data feed*: bank-change timestamp not propagated within the hour. H3 *Override misuse* by an operator.
- Discriminating evidence: rule-engine config version history; end-to-end lineage/latency measurement of the bank-change attribute; override logs; recompute the 4 cases against the current rule set (if all pass today  config/feed fixed itself or was patched; if they still pass  the condition never existed  H1).

**4. CL-606 (+9 cases) — missing core Assess Loss with external report.**
- H1 *By design*: high-value claims are assessed externally and the model was never updated. H2 *Assessor failed to sync*. H3 *Interface failure dropped events*.
- Discriminating evidence: Do all 9 have signed reports ( systematic channel, H1) or only some ( H2/H3)? Interface error/retry queues for the period; correlation of gaps with a specific adjuster or deployment date.

**5. CL-608 — notification evidenced only by a mutable CRM field.**
- H1 *Message sent; link design is the only defect.* H2 *Message never sent*; field filled aspirationally or later. H3 *Sent but linked to the wrong case.*
- Discriminating evidence: portal server-side delivery logs keyed by recipient and timestamp; CRM field version/audit history (when was the text written, by whom, has it changed?); claimant-side confirmation. Server logs trump the mutable field in evidentiary weight.

**6. CL-607 / CL-612 — denial and withdrawal "deviations."**
- H1 *Scope mismatch only*: model is fine; these traces belong to a different process. H2 *Genuine model incompleteness*: business intends denials/withdrawals in scope (P6). H3 *Routing defect*: deniable claims wrongly entering the payable pipeline.
- Discriminating evidence: signed scope statement vs. intake design docs; volume share of cost  4 traces that are denials/withdrawals; upstream filtering rules (were denied leads ever supposed to reach this system?).

**7. CL-611 — `Assess Damage` vs `Assess Loss`.**
- H1 *Deliberate rename with poor change management* (mapping applied after go-live). H2 *Free-text data-entry inconsistency* by users. H3 *Two distinct activities conflated* (unlikely given identical position and downstream flow).
- Discriminating evidence: mapping-table version history and deployment notes; time-series of label usage (does `Assess Damage` appear only before/after a release date?  H1; scattered throughout  H2); procedure documents referencing each term.

## 6. Why Alignment Cost Is Not Business Risk

Raw cost is the minimum edit distance between log and model **under one chosen cost function**. Five-plus supplied cases show every way that decouples from business risk:

1. **Uniform cost-function design flattens criticality.** Every visible move costs 1, so a missing UI autosave (CL-601) prices identically to a missing Fraud Screen on a €480,000 HIGH-risk claim with a day-old bank change (CL-602, cost 1). Business-wise these differ by orders of magnitude; edit-distance-wise they are twins. In this very sample the script in Section 7 computes a Spearman rank correlation between raw cost and assessed severity of approximately **0.12** — i.e., no monotone relationship, if anything a slight inverse one.

2. **Scope effects dominate the cost tail.** The most expensive alignments (cost 4) are CL-607 and CL-612 — a correctly denied claim and a rightful withdrawal. The model simply has no branch for them (P6), so perfect business conduct generates maximal distance. "Denied and withdrawn cases account for most alignments with raw cost  4": the top of the cost distribution is substantially *noise of scope*, not deviance.

3. **Hidden moves are fitting — and zero cost proves nothing.** CL-605's `T(tau)` is a silent routing transition that fits by construction; it is structural plumbing, not evidence of virtue or vice. Its converse is decisive: CL-609 and CL-610 are **fully synchronous, cost 0**, and both breach P1 (CL-610 also leaves P2 unmet one hour after a beneficiary bank change). Control-flow alignment is blind to data conditions; a zero-cost trace can be a live fraud vector.

4. **Irreversibility and fictional repairs.** CL-604 costs 3, yet the bank accepted payment 17 minutes before approval. The alignment "repairs" this by inserting a second, compliant `M(Pay Claim)` that never occurred — edit distance minimizes symbols, not money. You cannot un-pay. A cheap repair over an irreversible event is the definition of cost understating risk (P3 exists precisely because of this).

5. **Missing-but-external evidence.** CL-606 (cost 1) flags an assessment that a licensed adjuster demonstrably signed; CL-608 (cost 1) flags a notification probably delivered via secure portal within 24 hours. In both, the log gap reflects system-of-record boundaries, not skipped duties — though CL-608's mutable CRM link and the 2 unstable document IDs inside the CL-606 pattern degrade *confidence*, which cost cannot express at all.

6. **Duplicated telemetry and recurrence multiplication.** CL-601 costs 3 for UI chatter; CL-603 costs 1 for a transport retry — and the same retry pattern recurs **74 times a month**, contributing ~74 units of phantom deviation that bury genuine signals. Individually trivial, collectively corrosive: recurrence, not unit cost, drives monitoring harm.

7. **Label granularity.** CL-611 costs 2 because the core said `Assess Damage` where the model says `Assess Loss` — a synonym with a governance problem, not a behavioral one.

Finally, alternative optimal alignments may exist for any trace; the supplied alignments are treated as authoritative diagnostics here, but their costs remain properties of the *chosen cost function and model*, not of the business outcome. **Use cost to find where to look; use the materiality framework to decide what it means.**

## 7. PM4Py Reproduction and Aggregation Code

```python
# =====================================================================
# Section 7 - PM4Py reproduction + business-risk aggregation
# Technical alignment costs produced here are DIAGNOSTIC ONLY and are
# kept in columns strictly separate from the business-severity
# assessment, which remains a narrative judgment (Sections 1-6).
# No external files are read.
# =====================================================================
from datetime import datetime, timedelta
import pandas as pd

# ---------------------------------------------------------------------
# Constants: normative process tree and the 12 case traces (activities)
# ---------------------------------------------------------------------
TREE_STRING = ("-> ( 'Register Claim', 'Validate Coverage', 'Assess Loss', "
               "X ( -> ( 'Fraud Screen', 'Manual Approve' ), 'Auto Approve' ), "
               "'Pay Claim', 'Notify Claimant' )")

TRACES = {
    "CL-601": ["Register Claim", "Validate Coverage", "Open Workbench", "Assess Loss",
               "Autosave", "Auto Approve", "Pay Claim", "Notify Claimant", "Close Workbench"],
    "CL-602": ["Register Claim", "Validate Coverage", "Assess Loss",
               "Manual Approve", "Pay Claim", "Notify Claimant"],
    "CL-603": ["Register Claim", "Validate Coverage", "Assess Loss", "Auto Approve",
               "Pay Claim", "Notify Claimant", "Notify Claimant"],          # retry duplicate
    "CL-604": ["Register Claim", "Validate Coverage", "Assess Loss", "Pay Claim",
               "Manual Approve", "Notify Claimant"],                        # pay BEFORE approve
    "CL-605": ["Register Claim", "Validate Coverage", "Assess Loss",
               "Auto Approve", "Pay Claim", "Notify Claimant"],
    "CL-606": ["Register Claim", "Validate Coverage", "Fraud Screen",
               "Manual Approve", "Pay Claim", "Notify Claimant"],
    "CL-607": ["Register Claim", "Validate Coverage", "Deny Claim", "Notify Claimant"],
    "CL-608": ["Register Claim", "Validate Coverage", "Assess Loss", "Fraud Screen",
               "Manual Approve", "Pay Claim"],
    "CL-609": ["Register Claim", "Validate Coverage", "Assess Loss",
               "Auto Approve", "Pay Claim", "Notify Claimant"],
    "CL-610": ["Register Claim", "Validate Coverage", "Assess Loss",
               "Auto Approve", "Pay Claim", "Notify Claimant"],
    "CL-611": ["Register Claim", "Validate Coverage", "Assess Damage", "Fraud Screen",
               "Manual Approve", "Pay Claim", "Notify Claimant"],
    "CL-612": ["Register Claim", "Validate Coverage", "Assess Loss", "Withdraw Claim"],
}

BASE = datetime(2024, 5, 2, 8, 0, 0)

def build_string_log() -> str:
    """case_id,activity,ISO-timestamp lines, one case per calendar day."""
    lines = []
    for i, (case, acts) in enumerate(TRACES.items()):
        t0 = BASE + timedelta(days=i)
        for j, act in enumerate(acts):
            ts = (t0 + timedelta(minutes=7 * j)).strftime("%Y-%m-%d %H:%M:%S")
            lines.append(f"{case},{act},{ts}")
    return "\n".join(lines)

# ---------------------------------------------------------------------
# Steps 1-5: parse tree -> Petri net -> log -> alignments  (if pm4py present)
# ---------------------------------------------------------------------
try:
    import pm4py
    pm4py_ok = True
except Exception as e:                                   # pragma: no cover
    pm4py_ok = False
    print(f"[warn] pm4py unavailable ({e}); live alignment skipped, "
          f"aggregation below still executes.")

if pm4py_ok:
    # (1) parse the supplied process-tree string
    tree = pm4py.parse_process_tree(TREE_STRING)
    # (2) convert to an accepting Petri net
    net, im, fm = pm4py.convert_to_petri_net(tree)
    print(f"Parsed tree OK. Petri net: {len(net.places)} places, "
          f"{len(net.transitions)} transitions, {len(net.arcs)} arcs.")

    # (3) small event log via parse_event_log_string (pandas-df fallback allowed)
    string_log = build_string_log()
    log = None
    try:
        log = pm4py.parse_event_log_string(
            string_log, sep=",",
            activity_key="concept:name",
            case_id_key="case:concept:name",
            timestamp_key="time:timestamp")
    except Exception:
        rows = [ln.split(",") for ln in string_log.split("\n")]
        df_log = pd.DataFrame(rows, columns=["case:concept:name",
                                             "concept:name", "time:timestamp"])
        df_log["time:timestamp"] = pd.to_datetime(df_log["time:timestamp"])
        try:
            log = pm4py.convert_to_event_log(df_log)
        except Exception:
            log = df_log                                  # pm4py accepts DataFrames

    # (4) conformance alignments
    diagnostics = pm4py.conformance_diagnostics_alignments(log, net, im, fm)

    # (5) REQUIRED CAVEAT about optimality/formatting differences
    print("""
[NOTE] PM4Py's A* optimizer may return a DIFFERENT but equally optimal
alignment than the supplied authoritative notation (move ordering,
silent-move placement, and cost scaling can vary across pm4py versions
and log encodings). The supplied alignments in the task remain the
authoritative diagnostic inputs; the values below are a reproducibility
cross-check only and never override Sections 1-6.
""")
    for case_id, diag in zip(TRACES.keys(), diagnostics):
        cost = diag.get("cost", "?") if isinstance(diag, dict) else "?"
        fit = diag.get("fitness", "?") if isinstance(diag, dict) else "?"
        print(f"  {case_id}: pm4py cost={cost}, fitness={fit}")

# ---------------------------------------------------------------------
# Step 6: dataframe of the SUPPLIED (authoritative) move summaries
# ---------------------------------------------------------------------
SUPPLIED_MOVES = {
    "CL-601": [("S","Register Claim"),("S","Validate Coverage"),("L","Open Workbench"),
               ("S","Assess Loss"),("L","Autosave"),("S","Auto Approve"),
               ("S","Pay Claim"),("S","Notify Claimant"),("L","Close Workbench")],
```
