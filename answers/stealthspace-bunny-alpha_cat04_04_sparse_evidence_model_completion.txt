**DFG consistency audit.** The supplied DFG is not the exact frequency DFG of the listed strings. The following direct-edge counts disagree:

- Register Order  Engineering Review: **12**, not 11.
- Credit Check  Supplier Confirmation: **15**, not 9.
- Engineering Review  Approve Configuration: **7**, not 6.
- Credit Check  Approve Configuration: **7**, not 3.
- Supplier Confirmation  Approve Configuration: **24**, not 20.
- Expedite Review  Approve Configuration: **2**, not 1.

The other listed edges agree. In particular, direct RC and RE counts sum to \(19+12=31\), although there are 30 traces. The discrepancy is not evidence for unlisted cases; its cause is unknown. The models below therefore encode the explicit trace strings, and the validation code reports the disagreement rather than silently correcting or reproducing it.

**Why two DFG directions do not prove concurrency.** CE has count 17 and EC has count 11. Those counts could arise from a strictly sequential system that executes C first in some cases and E first in others. A DFG aggregates across cases; it does not establish that the two activities overlapped within any case. Conversely, a process-model compiler may infer a partial order from aggregated counts, but that is a modeling choice—not evidence of actual parallelism. Here, D7 and S7 expressly prohibit making that inference without lifecycle timing data.

# 2. Shared Assumptions

1. **Single-case, single-occurrence abstraction.** Each case contains R, C, E, A, P, and Z exactly once. S and X occur zero or one time. The models do not represent retries, repeated approvals, or repeated engineering reviews.

2. **Completion semantics.** An event represents a completed activity. A modeled dependency says that the next observable event cannot occur until the required model tokens have been consumed. It is not a verified start-time constraint.

3. **Log-order semantics.** Observed event order is used to describe accepting traces. POWL non-precedence permits multiple event linearizations; it does not assert that the underlying activities were simultaneously executing.

4. **Supplier Confirmation abstraction.** A missing S event can represent either a legitimate stocked-component skip or an integration-related missing event. There is insufficient information to distinguish these cases. The models represent this with a zero-or-one choice, not an explicit business predicate. This abstraction conflates missingness with true optionality.

5. **Requiredness remains unresolved.** S3 and S4 imply a potential attribute-dependent requirement: S for external components, possibly no S for stocked components. Because the attribute is absent, all three models use the same conservative log-level abstraction rather than inventing attribute guards.

6. **Expedite Review abstraction.** X is optional and occurs at most once. It follows the C/E join and precedes A. Its order relative to S is unconstrained in the generalized models.

7. **Common terminal sequence.** A, P, and Z occur once, in that order. The models prioritize the domain rules and unanimous observed suffix over hypothetical exceptions.

8. **Model scope.** The three candidates are alternative process hypotheses for one-order, one-pass cases. They are not statistical models of duration, capacity, resource behavior, or missing-event mechanisms.

# 3. Conservative Candidate

**Inductive bias.** This model treats the seven distinct observed completion strings as the entire single-pass behavior, factoring their common prefix choices and terminal sequence. It introduces no unobserved interleaving or newly optional combination. It therefore does not interpret S2 as concurrency, D5 as an early-start permission, or S6 as permitting X without an S event. The result is faithful to the recorded strings, but its apparent conservatism is only observational: an absent S event remains causally ambiguous, and a DFG edge does not become a causal law merely because it is frequent.

Let R, C, E, S, X, A, P, and Z abbreviate the eight activity names. With \(\oplus\) denoting exclusive initial choice and juxtaposition denoting required observable order:

```text
U0 = {
  C E,
  E C,
  C E S,
  C S E,
  E C S,
  E S C,
  C E S X,
  E C X S
}

M_conservative = R  u · A · P · Z,  for u  U0
```

Its bounded, single-occurrence visible-trace language contains exactly the seven distinct observed strings.

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def build_conservative():
    tail = (
        "Approve Configuration",
        "Release Production",
        "Archive Case",
    )

    # Prefixes of the seven distinct observed variants.
    prefixes = [
        ("Credit Check", "Engineering Review"),
        ("Engineering Review", "Credit Check"),
        ("Credit Check", "Engineering Review", "Supplier Confirmation"),
        ("Credit Check", "Supplier Confirmation", "Engineering Review"),
        ("Engineering Review", "Credit Check", "Supplier Confirmation"),
        ("Engineering Review", "Supplier Confirmation", "Credit Check"),
        (
            "Credit Check",
            "Engineering Review",
            "Supplier Confirmation",
            "Expedite Review",
        ),
        (
            "Engineering Review",
            "Credit Check",
            "Expedite Review",
            "Supplier Confirmation",
        ),
    ]

    branches = []
    for prefix in prefixes:
        labels = ("Register Order",) + prefix + tail
        branches.append(
            ProcessTree(
                operator=Operator.SEQUENCE,
                children=[ProcessTree(name=name) for name in labels],
            )
        )

    return ProcessTree(operator=Operator.XOR, children=branches)


model_conservative = build_conservative()
```

**Behavior deliberately excluded**

- Any additional prefix permutation not listed in `U0`.
- C and E in an unobserved relative order.
- X without an S event.
- S occurring between R and the first principal check.
- S or X occurring more than once.
- Any ordering other than A  P  Z.
- Missing mandatory-case labels or a new terminal activity.

**Known underfitting risks**

- It rejects every legitimate but unobserved interleaving.
- It cannot represent partial-order observations without enumerating all accepted linearizations.
- It treats the two X-bearing strings as the only possible X contexts.
- It conflates skip and missingness for S, despite not being able to establish either mechanism.
- It cannot express a C/E overlap hypothesis or later support for S2.
- It has limited scalability: exact enumeration grows factorially with unconstrained activities. Factoring common prefixes helps authoring but does not remove the underlying enumeration burden.
- Future identical strings can be deduplicated for language membership without changing the model, but their multiplicities must be retained for frequencies or likelihoods. Repeated labels within a branch are not interchangeable: for example, CC needs separate leaf instances or a structured partial-order representation. A XOR of a large trace set should be deduplicated by trace string, not by set of labels.

# 4. Balanced Candidate

**Inductive bias.** This is a representative—not uniquely most probable—generalization. It requires observable C before E because that order occurs in 17 of 28 two-check cases and is asserted by S1, but it does not treat that choice as a verified start-time law. Both checks form a join before A, after which S and X are independently optional and unordered; S6 explicitly supports the two observed S/X orders. This partial order admits early S between C and E and X without an S event without invoking D5 as a general requirement. Rejecting E-before-C and S-before-E is a deliberate robustness tradeoff against S2, D5, and the substantial minority of observations; S2 and D7 prevent treating those rejected alternatives as impossible.

```text
M_balanced = R  (C ; E)  (S  X)  A  P  Z
```

Here, `;` requires observable C-before-E order, while \(\parallel\) means no precedence. S and X each have a zero-or-one choice. The source construction yields eight distinct single-occurrence traces: six observed strings and two unobserved strings.

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def build_balanced():
    r, c, e, s, x, a, p, z = [
        Transition(name)
        for name in (
            "Register Order",
            "Credit Check",
            "Engineering Review",
            "Supplier Confirmation",
            "Expedite Review",
            "Approve Configuration",
            "Release Production",
            "Archive Case",
        )
    ]

    # Observable precedence, not a verified start-time constraint.
    checks = StrictPartialOrder([c, e])
    checks.order.add_edge(c, e)

    # No precedence between S and X. Compiled POWL permits either to be skipped.
    optional_reviews = StrictPartialOrder([s, x])

    pre_approval = StrictPartialOrder([r, checks, optional_reviews])
    pre_approval.order.add_edge(r, checks)
    pre_approval.order.add_edge(checks, optional_reviews)

    tail = StrictPartialOrder([a, p, z])
    tail.order.add_edge(a, p)
    tail.order.add_edge(p, z)

    model = StrictPartialOrder([pre_approval, tail])
    model.order.add_edge(pre_approval, tail)
    return model


model_balanced = build_balanced()
```

**Behavior deliberately excluded**

- E appearing before C in the observable trace.
- S occurring after C but before E.
- S or X after A.
- X before both C and E.
- A second occurrence of S or X.
- P before A, Z before P, or a non-Z terminal event.

**Known underfitting risks**

- Its strict C-before-E proxy can exclude genuinely overlapping checks whose E event is logged first.
- Its S-after-both-checks proxy can exclude legitimate D5 early starts.
- It admits X without S without observed confirmation of that business combination.
- It still cannot distinguish stocked skipping from S logging failure.
- It assumes no retries, even though future process behavior may contain them.
- A precise, high-fitness model against these 30 cases does not establish concurrency or a causal mechanism.

# 5. Permissive Candidate

**Inductive bias.** This model minimizes precedence assumptions about the principal checks: C and E have no direct order, while both must complete before approval. S becomes enabled after the first check completes, implementing D5 as a permissive dependency. X remains gated by the join of C and E, as required by D6 and S6. S and X are otherwise unordered. This admits the reported parallel-check interpretation and the S-before-E observation, but neither is proven. The broadening is bounded by mandatory completion requirements rather than by a requirement that every possible label order be accepted.

```text
M_permissive = R  (C  E)  (S  X)  A  P  Z
```

Here, \(\parallel\) means no direct observable precedence. The C/E join still precedes the optional reviews, and every optional-review event still precedes A.

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def build_permissive():
    r, c, e, s, x, a, p, z = [
        Transition(name)
        for name in (
            "Register Order",
            "Credit Check",
            "Engineering Review",
            "Supplier Confirmation",
            "Expedite Review",
            "Approve Configuration",
            "Release Production",
            "Archive Case",
        )
    ]

    # No precedence between the two principal checks.
    checks = StrictPartialOrder([c, e])

    # S becomes enabled after either check; X waits for both.
    optional_reviews = StrictPartialOrder([s, x])

    pre_approval = StrictPartialOrder([r, checks, optional_reviews])
    pre_approval.order.add_edge(r, checks)
    pre_approval.order.add_edge(checks, optional_reviews)

    tail = StrictPartialOrder([a, p, z])
    tail.order.add_edge(a, p)
    tail.order.add_edge(p, z)

    model = StrictPartialOrder([pre_approval, tail])
    model.order.add_edge(pre_approval, tail)
    return model


model_permissive = build_permissive()
```

**Behavior deliberately excluded**

- S before either principal check completes.
- X before both principal checks complete.
- S or X after A.
- A second occurrence of X.
- A, P, or Z occurring more than once or in a different terminal order.
- Any unlabeled substitute for a mandatory activity.

Those exclusions are the boundary between reasonable generalization and clearly unsupported behavior. By contrast, the model deliberately permits E-before-C, S-before-E, and an S/X order different from the single observed X/S order. These are reasonable only relative to S2, D5, and S6; they are not entailed by the trace evidence.

**Known underfitting and misuse risks**

- It can become a catch-all that hides an incorrect process rule.
- It conflicts with S1 if that statement is an authoritative contractual constraint.
- It interprets D5 as a mandatory minimum prerequisite, although D5 says S *may* start early.
- It accepts cases that would be undesirable if every external component truly requires S.
- It still treats missing and skipped S events as indistinguishable.
- The partial order describes observable choices, not verified physical parallelism.

# 7. Comparative Model Matrix

“High fitness” here means compatibility with the observed strings, not evidence that the model identifies the real causal process.

Under the single-occurrence source constructions, the complete visible-trace languages have **7, 8, and 13 traces**, respectively. These cardinalities are not fitness measurements. The validation code recomputes them by bounded reachability rather than by sampling.

# 8. Validation Code

The following is standalone and rebuilds the candidates rather than relying on previous code cells.

Important limitations:

- The source models have no unbounded retry loops. The reachability routine can therefore enumerate their complete visible-trace languages if its caps are not reached.
- It is not a general decision procedure for infinite process languages.
- PM4Py metrics are version- and configuration-dependent. In particular, the TBR generalization result has changed representation across releases, so the code reports available numeric fields rather than inventing a scalar.
- `precision_alignments` measures the alignment-based precision objective; it need not equal empirical trace-language precision. Membership of the manually defined negative traces is checked separately.
- Native playout is a sample check only. Exactness comes from the bounded state-space search for these finite candidates, not from playout.

    return flat

def build_powl(strict_checks):
    r, c, e, s, x, a, p, z = [
        Transition(name)
        for name in (
            "Register Order",
            "Credit Check",
            "Engineering Review",
            "Supplier Confirmation",
            "Expedite Review",
            "Approve Configuration",
            "Release Production",
            "Archive Case",
        )
    ]

    checks = StrictPartialOrder([c, e])
    if strict_checks:
        checks.order.add_edge(c, e)

    optional_reviews = StrictPartialOrder([s, x])

    pre_approval = StrictPartialOrder([r, checks, optional_reviews])
    pre_approval.order.add_edge(r, checks)

    tail = StrictPartialOrder([a, p, z])
    tail.order.add_edge(a, p)
    tail.order.add_edge(p, z)

    model.order.add_edge(pre_approval, tail)

def marking_from_counts(net, counts):
    marking = Marking()
    for place, count in counts.items():
        marking[place.name] = count
    return marking


def marking_key(marking):
    return tuple(sorted(
        (place, count)
        for place, count in marking.items()
        if count != 0
    ))


def transition_label(transition):
    # PM4Py transitions compiled from SilentTransition have is_silent=True.
    if getattr(transition, "is_silent", False):
        return None
    return transition.name


def enabled_transitions(net, marking):
    result = []
    for transition in net.transitions:
        required_ok = all(
            marking.get(arc.place.name, 0) >= arc.weight
            for arc in net.in_arcs.get(transition, [])
        )
        if required_ok:
            result.append(transition)
    return result


def fire_transition(net, marking, transition):
    result = Marking()

    for place, count in marking.items():
        result[place] = count

    for arc in net.in_arcs.get(transition, []):
        result[arc.place.name] -= arc.weight

    for arc in net.out_arcs.get(transition, []):
        result[arc.place.name] = result.get(arc.place.name, 0) + arc.weight

    return result


def is_workflow_net(net, initial_marking, final_marking):
    sources = set(initial_marking)
    sinks = set(final_marking)

    return (
        len(sources) == 1
        and len(sinks) == 1
        and sources.issubset(sinks)
        and sources.isdisjoint(sinks)
        and set(net.places).issubset(sources | sinks)
    )


def bounded_audit(net, im, fm, max_states=100_000, max_traces=10_000):
    """
    Exact state exploration if the finite-state caps are not reached.

    This is intentionally not advertised as a general algorithm for
    arbitrary nets with unbounded token creation.
    """
    initial = marking_from_counts(net, im)
    final_key = marking_key(marking_from_counts(net, fm))

    queue = deque([(initial, ())])
    seen = {marking_key(initial)}
    accepted = set()

    while queue:
        marking, visible_trace = queue.popleft()
        current_key = marking_key(marking)

        if current_key == final_key:
            accepted.add(visible_trace)
            if len(accepted) > max_traces:
                raise RuntimeError("Trace enumeration cap reached.")
            continue

        enabled = enabled_transitions(net, marking)
        if not enabled:
            continue

        for transition in enabled:
            next_marking = fire_transition(net, marking, transition)
            next_key = marking_key(next_marking)

            if len(seen) >= max_states and next_key not in seen:
                raise RuntimeError("Marking enumeration cap reached.")

            if next_key not in seen:
                seen.add(next_key)
                label = transition_label(transition)
                next_trace = (
                    visible_trace
                    if label is None
                    else visible_trace + (label,)
                )
                queue.append((next_marking, next_trace))

    # Reverse reachability from the final marking.
    reverse_predecessors = {}
    for transition in net.transitions:
        target = marking_from_counts(net, {
            arc.place.name: arc.weight
            for arc in net.out_arcs.get(transition, [])
        })
        for source in net.in_arcs.get(transition, []):
            reverse_predecessors.setdefault(
                source.place.name, set()
            ).add(transition.name)

    can_reach_final = {final_key}
    reverse_queue = deque([final_key])
    while reverse_queue:
        state = reverse_queue.popleft()
        for place, count in state:
            if count != 1:
                continue
            for transition_name in reverse_predecessors.get(place, set()):
                transition = net.transitions[transition_name]
                arcs = net.out_arcs.get(transition, [])
                if len(arcs) != 1:
                    # This reverse search helper is not needed for the
                    # one-token source models; do not silently generalize it.
                    continue
                consumed = arcs[0]
                predecessor = dict(state)
                predecessor[consumed.place.name] = 0
                # An enabling predecessor must supply this one token.
                predecessor[consumed.place.name] = 1
                predecessor_key = tuple(sorted(predecessor.items()))
                if predecessor_key not in can_reach_final:
                    can_reach_final.add(predecessor_key)
                    reverse_queue.append(predecessor_key)

    # Use forward co-reachability, which is simpler and exact for these nets.
    from_final = {final_key}
    stack = [initial]
    while stack:
        marking = stack.pop()
        key = marking_key(marking)
        if key in from_final:
            continue
        from_final.add(key)
        for transition in enabled_transitions(net, marking):
            stack.append(fire_transition(net, marking, transition))

    return {
        "workflow_structure": is_workflow_net(net, im, fm),
        "all_reachable_markings_live": all(
            state in from_final for state in seen
        ),
        "all_reachable_markings_can_reach_final": all(
            state in can_reach_final for state in seen
        ),
        "marking_count": len(seen),
        "traces": tuple(sorted(accepted)),
    }


def available_score(function):
    try:
        result = function()
    except (
        AttributeError,
        NotImplementedError,
        TypeError,
        PM4PyException,
    ) as error:
        print("Metric unavailable:", type(error).__name__, str(error))
        return None, None

    value = result
    if isinstance(value, (tuple, list)) and value:
        value = value[0]

    if isinstance(value, Real) and not isinstance(value, bool):
        return float(value), result

    return None, result


def average_benedikt_fields(result):
    if isinstance(result, Real) and not isinstance(result, bool):
        return float(result)

    if result is None:
        return None

    values = []
    try:
        for trace in result:
            for event in trace:
                if hasattr(event, "get"):
                    value = event.get("benedikt")
                else:
                    value = getattr(event, "benedikt", None)

                if isinstance(value, Real) and not isinstance(value, bool):
                    values.append(float(value))
    except TypeError:
        return None

    return sum(values) / len(values) if values else None

# 9. Recommendation and Data-Collection Plan

**Immediate recommendation: `model_balanced`.** It offers a meaningful reduction in trace-order overfitting while retaining D1, D2, D3, D4, and D6. Its uncertainty is explicit: it fixes C before E, leaves S and X unordered, and represents S absence as skip-or-missing. It should be deployed as a **provisional operational hypothesis**, not as proof of actual concurrency or a compliance certification.

**Sensitivity model: `model_permissive`.** Run it alongside the balanced model to identify operational cases affected by E-first observations, S-before-E behavior, and other C/E/S orderings. The difference between them is a useful risk envelope. The conservative model should also remain available as an audit baseline for detecting unexplained deviations.

**Immediate data-quality action**

1. Reconcile the supplied DFG against a new DFG generated from the same 30 source traces.
2. Preserve duplicate cases and case identifiers; seven distinct strings must not be mistaken for seven cases.
3. Flag S-free cases as **“absence unresolved: stocked or missing”**, not automatically as stocked.
4. Obtain the upstream integration audit for the two Expedite Review cases and other S-bearing cases to determine whether event loss is possible.
5. Report balanced-versus-permissive disagreements rather than choosing a winner from the existing 30 cases.

**Concrete collection plan**

Instrument a prospective pilot of 100 completed cases, or all cases over a fixed eight-week window if that yields fewer than 100. Stratify the pilot by:

- C/E completion order.
- Whether S starts after C, after E, or after both.
- S present, explicitly skipped, or recovered from upstream records.
- X present and its order relative to S.
- External versus stocked component status.

For each case, collect:

- Stable order ID and component/order line ID.
- `external_component` or `stocked_component`.
- Whether Supplier Confirmation is required, attempted, completed, or explicitly skipped.
- Skip reason and approval authority.
- S integration event ID, delivery status, and error/retry status.
- X trigger/decision reason.
- Activity instance ID and activity version.
- Actual start, end, and completion timestamps with timezone and clock source.
- Ingestion timestamp and ingestion index as separate fields.
- Previous/next lifecycle timestamps, including queuing and waiting states.
- Retry and cancellation indicators.

Do not infer a start constraint from completion events. S1 specifically requires the C-end and E-start timestamps, while S2 requires start timestamps for both checks to test overlap.

**Maximally informative future cases**

1. **External component with a confirmed S obligation and event:** distinguishes S3 from S4 and tests whether mandatory S is merely absent from the log.
2. **Stocked component with an explicit skip record:** provides a true zero-S observation rather than an ambiguous one.
3. **E starts before C finishes, and C finishes first:** distinguishes true overlap from E-first sequencing.
4. **C starts before E but E finishes first, with both start times retained:** a decisive ordering/overlap counterexample to any strict completion-order assumption.
5. **C completes, S starts and completes, E completes, X runs, then A:** specifically tests D5 and distinguishes early S from the observed CSE variant.
6. **Both checks complete, X occurs without an S obligation, and the reason is recorded:** tests whether X is independently optional or merely accompanies S.
7. **X before S and S before X, each with both checks already complete:** tests the S6 generalization.
8. **A case with a true S integration failure:** separates process optionality from telemetry loss.
9. **Any legitimate repeated C, E, or A activity instance:** tests the common single-occurrence assumption.

These cases should be selected from legitimate process outcomes or carefully governed exploratory cases, not by manufacturing noncompliant orders. For each hypothesis comparison, report counts by actual start/finish relations and requiredness attributes, rather than only an aggregate fitness score.

# 10. Uncertainty Statement

| Major decision | Calibrated confidence | Reason |
|---|---|---|
| R is intended to start and Z to end. | High | D1 plus unanimous observed endpoints. |
| A precedes P and Z in this single-pass scope. | High for the observed scope | D2 and all 30 traces; future exceptions are not established. |
| Both C and E complete before A. | Medium-high | D3 and unanimous observed behavior. |
| S is genuinely optional, rather than sometimes unlogged. | Low | S3/S4 and S5 cannot be resolved without the component attribute and integration evidence. |
| Conservative enumeration is the best observational description. | High | It exactly represents the seven distinct trace strings. |
| C should precede E in future completions. | Low-medium | Supported by 17/28 two-check orders and S1, but contradicted by 11/28 and unverifiable at the start-time level. |
| C and E genuinely overlap. | Low-medium | S2 supports it, but D7 and S7 prevent identifying it from the logs. |
| S may normally start after either check. | Low-medium | D5 says it may; only two traces show S before E, and start timestamps are absent. |
| X is independently optional and unordered relative to S. | Medium | D6 and S6 support the structure, but only two X cases exist and both contain S. |
| Single occurrence of every other activity is a general rule. | Medium-low for the observed cases; low for future cases | All listed traces are single-pass, but no explicit retry rule was collected. |
| The supplied DFG is internally consistent with the source traces. | Very low | Six direct-edge counts disagree with an independent reconstruction. |

A plausible alternative interpretation would materially change the recommendation: the checks may genuinely overlap, while Supplier Confirmation still requires **both** checks. That hypothesis is neither the balanced nor the permissive candidate—it would use a concurrent C/E join followed by the same S/X region as the balanced model. Reliable start/finish timestamps showing repeated overlap, together with more S-after-one-check cases, would favor replacing the balanced C/E precedence with that alternative rather than adopting all of the permissive assumptions.

Accordingly, the present recommendation is conditional: **balanced for immediate use, permissive for sensitivity, conservative for audit comparison, and additional lifecycle evidence before claiming a uniquely causal model.**
