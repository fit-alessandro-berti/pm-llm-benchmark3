## 1. Temporal Data Semantics

Amounts are read as EUR. The log has no currency attribute, and every threshold in the rules is stated in EUR. `XZ` is a fictional jurisdiction and is still a real control value for sanctions.

**Total order.** Within a case, event `e1` is strictly earlier than `e2` (`e1 ≺ e2`) when `time(e1) < time(e2)`, or the timestamps are equal and `event_index(e1) < event_index(e2)`. `e1 ≼ e2` includes identity. Obligation checks at `Release_Funds` use this order, not arrival order and not a sort on timestamp alone.

**Blanks.** A blank attribute cell is “no update,” not a write of null. It leaves the previous value in force. A value becomes unknown only when no earlier event in that case has set it.

**State at an event.** For each of `amount`, `risk_level`, `jurisdiction`, and `customer_type`, the value at event `e` is the non-blank value on the latest event `e' ≼ e` that wrote that attribute. Reconstruction is a forward fold. Final case attributes, later settlements, and later database inserts are invisible at earlier events.

**Four clocks.**
- **Event time** is the timestamp of the log row. An attribute update is effective then, unless separate evidence gives another effective time.
- **Effective time** is when the business fact became true (exemption `effective_from`, the moment a jurisdiction entered the sanctions list, the moment a signature made an approval exist).
- **Record time** is when a system row was inserted. `Record_Exemption` at 11:00 is record time. It can lag effective time, as with the documented outage on EX-77.
- **Evidence time** is when proof was created: qualified signature time, or creation time of the signing certificate. A displayed or backdated effective time is a claim. It becomes operative only when evidence time supports that the approval already existed at the obligation trigger.

**Material change.** Relative to the latest earlier `Standard_Review` or `Enhanced_Review` `r`, a later amount `a` is a material amount increase when both amounts are known and `a > 1.2 × amount-at-r` (equivalently `a × 5 > amount-at-r × 6`). That increase invalidates `r` for amount-dependent obligations (R1). A decrease does not. An increase of 20 percent or less does not. An increase from an unknown amount is not classifiable. A jurisdiction change is material to a still-live R1 obligation. A move to `HIGH` or `PEP` is material to R2. A sanctions-list addition is material to R3.

**Snapshot used for release.** R1 and R2 are decided on the state of the release event after its own non-blank updates and after every `≺`-earlier event. They are not decided on the state at `Create_Transaction` and not on the state after `Settlement_Confirmed`. The initial create establishes state; it is not itself a post-review invalidation.

**Same timestamp.** On TX-311, `Enhanced_Review` is event_index 3 and `Update_Jurisdiction` to `DE` is event_index 4, both at 16:20. The review’s snapshot is still `US` / 115,000. The release snapshot is `DE` / 115,000. The tie-break changes which state the review saw. It does not change the release-time jurisdiction, which is `DE` either way, because both rows precede release.

**Pseudo-logic.** `ρ` is the release event. `val(a, e)` is the forward state of attribute `a` at `e`, or `⊥`.

```
e1 ≺ e2  ⇔  time(e1) < time(e2)
         ∨ (time(e1) = time(e2) ∧ event_index(e1) < event_index(e2))

Invalidated(r, ρ) ⇔
    r is the ≺-latest Standard_Review or Enhanced_Review with r ≺ ρ
    ∧ val(amount, r) ≠ ⊥ ∧ val(amount, ρ) ≠ ⊥
    ∧ val(amount, ρ) × 5 > val(amount, r) × 6

Unclassifiable(r, ρ) ⇔
    r ≺ ρ ∧ (val(amount, r) = ⊥ ∨ val(amount, ρ) = ⊥)
    ∧ an amount-dependent obligation is otherwise live

Trig1(ρ) ⇔ val(jur,ρ) ∉ {⊥, DE} ∧ val(amount,ρ) ≠ ⊥ ∧ val(amount,ρ) ≥ 100000
Off1(ρ)  ⇔ val(jur,ρ) = DE ∨ (val(amount,ρ) ≠ ⊥ ∧ val(amount,ρ) < 100000)
Indet1(ρ) ⇔ ¬Off1(ρ) ∧ (val(jur,ρ) = ⊥ ∨ val(amount,ρ) = ⊥)

er ≔ ≺-latest Enhanced_Review with er ≺ ρ
Stale1(er, ρ) ⇔
    Invalidated(er, ρ)
    ∨ (Trig1(ρ) ∧ ∃ jurisdiction-changing m: er ≺ m ≺ ρ)

Rev1(ρ) ⇔ er exists ∧ ¬Stale1(er, ρ) ∧ ¬Unclassifiable(er, ρ)

Trig2(ρ) ⇔ val(risk,ρ) = HIGH ∨ val(customer,ρ) = PEP
Indet2(ρ) ⇔ ¬Trig2(ρ) ∧ (val(risk,ρ) = ⊥ ∨ val(customer,ρ) = ⊥)
t* ≔ latest event ≺ ρ that established a trigger value still true at ρ
Rev2(ρ) ⇔ ∃ er, ca:
    t* ≺ er ≺ ca ≺ ρ
    ∧ er is Enhanced_Review
    ∧ ca is Compliance_Approve of that enhanced review
A Compliance_Approve of a standard packet does not witness er.

u ≔ ≺-latest Sanctions_List_Update ≺ ρ adding val(jur, ρ)
s ≔ ≺-latest Sanctions_Screen ≺ ρ
Trig3(ρ) ⇔ u exists ∧ (s does not exist ∨ s ≺ u)
Sat3(ρ)  ⇔ ∃ s2 Sanctions_Screen: u ≺ s2 ≺ ρ

ValidEx(rule, ρ) ⇔ the release references x, or x was recorded earlier, and all of:
    x.approved_by = Head_Compliance
    x.effective_from ≤ time(ρ) and time(ρ) is before x is expired
    x.jurisdiction, x.customer_type, and x.amount_max match val(·, ρ)
    x.waives rule
    qualified_signature_time(x) ≤ time(ρ)
    certificate_created(x) ≤ time(ρ)
Displayed approval/effective fields do not satisfy the last two atoms.
An interested requester’s oral statement does not satisfy them.
record_time(x) > time(ρ) is compatible with ValidEx when the two evidence atoms hold.

Outcome for rule Ri:
    Off          if Off_i
    INDETERMINATE if Indet_i, or Unclassifiable and Ri is amount-dependent,
                   or the only candidate exception is display-backdated and uncorroborated
    SATISFIED    if Trig_i ∧ the review/screen ordering holds
    JUSTIFIED_EXCEPTION if Trig_i ∧ the ordering fails ∧ ValidEx(Ri, ρ)
    VIOLATION    if Trig_i ∧ the ordering fails ∧ ValidEx is false on the evidence

Case class:
    NONCOMPLIANT          if any VIOLATION
    INDETERMINATE         if no VIOLATION and any INDETERMINATE
    JUSTIFIED_EXCEPTION   if no violation or indeterminacy, and some live rule is saved only by ValidEx
    COMPLIANT             if every live rule is SATISFIED and the rest are Off
```

R4 is a defeater of the review atom inside R1, not a second duty to perform a named activity when R1 is off. R6 and R7 are constraints on the atoms above: `⊥` is not coerced, and every “before” is `≺`.

## 4. Ambiguities and Alternative Readings

**TX-305 (indeterminate).** The R1 trigger is open because CA is not DE and the amount at release was never written. Two later facts would close it. An immutable release payload with amount &lt; 100,000 would make R1 off; R2 and R3 are already off, so the case would be COMPLIANT. A payload with amount ≥ 100,000 would turn R1 on. The existing enhanced review still has a gap: the review document contains no amount, and R4 says an increase from an unknown amount is not classifiable. With a known high release amount and still no amount on the review, the case would move to NONCOMPLIANT unless the payload showed the reviewed amount was already the release amount and the review had actually assessed it. The settlement amount of 150,000 does none of this work. It is a value on 7 April. Copying it onto the 6 April release is final-state leakage. Using it only as a suspicion correctly leaves the case INDETERMINATE.

**TX-302.** Primary result is COMPLIANT because the enhanced review ran after the 180,000 / GB / CORPORATE / MEDIUM state existed and nothing material changed afterward. The independent alternative is also favorable: if the review were set aside, EX-77 would still be `ValidEx` for R1. Signature time 09:05 is evidence time, release is 09:40, and the 11:00 insert is explained record lag. That alternative classification is JUSTIFIED_EXCEPTION. What would make the case NONCOMPLIANT is evidence that the qualified signature was not verifiable or that the review was not an enhanced review. The log and the register do not say that. EX-77 waives R1 only; it would not have cured an R2 or R3 breach had one existed. MEDIUM and CORPORATE do not trigger R2.

**TX-310.** Primary result is NONCOMPLIANT. R1 is plainly on (AE, 200,000). A standard review is not an enhanced review. R5’s evidence atom fails: certificate creation at 10:30 is after release at 10:00, so the displayed 08:50 time is backdated, and a requester’s statement that oral approval happened at 08:45 does not corroborate Head_Compliance approval. The late insert therefore does not play the role it plays for EX-77, where a pre-release signature plus a documented outage explains the lag. Confidence is medium because the residue is testimonial. An independent witness, or a qualified signature whose time is ≤ 10:00, with the same scope, would make EX-88 valid and move the case to JUSTIFIED_EXCEPTION. Treating the requester’s oral claim as a live factual dispute that cannot be weighed would move the case to INDETERMINATE. The reading adopted here is the one R5 states: a displayed backdate alone is not conclusive, and this record’s independent certificate time contradicts the display.

**TX-311.** At release the jurisdiction is DE, so R1 is off, and the amount path 90,000 → 115,000 happened before the enhanced review, so there is no post-review material increase. The same-timestamp fact still matters. Index 3 precedes index 4, so the review observed US / 115,000, which was an R1-live state, and only the next index turned the jurisdiction to DE. Under a release-time reading the classification stays COMPLIANT even if the two 16:20 rows were swapped, because both still precede release and the release snapshot would remain DE. Under a continuous reading (the duty must have been met while it was live), the actual index order is what shows the enhanced review occurred during the US / 115,000 interval. Swapping the indexes would put the jurisdiction change first and would leave that interval without an enhanced review. Timestamp-only processing cannot see the difference. A further reading that any jurisdiction change after a review keeps R1 alive would be a different rule: at release the foreign limb is false.

**TX-306 (alternative).** The adopted reading is that “material” for R4, and for the R1 phrase “latest material data change,” is an increase of more than 20 percent, a jurisdiction change while R1 stays live, or a new HIGH/PEP episode for R2. On that reading +4.545% after approval changes nothing, and both R1 and R2 are satisfied. A stricter reading, under which any post-review amount write is material and demands a new enhanced review and a new approval, would make TX-306 NONCOMPLIANT. That stricter reading is set aside because R4 draws the 20 percent line and expressly withholds invalidation from non-qualifying increases.

**TX-308 (alternative).** The decrease 140,000 → 100,000 leaves the enhanced review in force, and 100,000 still meets “at least 100,000,” so R1 is on and satisfied. A symmetric rule that any amount edit after review invalidates it would make TX-308 NONCOMPLIANT. R4 blocks that symmetry. A reading that “at least 100,000” means “strictly greater than 100,000” would turn R1 off and would also be COMPLIANT, by a different route. The threshold text includes equality.

**TX-307 (alternative).** The adopted reading is that R2 requires an enhanced review, and approval of a standard packet does not supply one. The semantic note on standard packets matches that reading. The case would become COMPLIANT only under a reading that `Compliance_Approve` alone, or `Standard_Review` plus approval, discharges a PEP trigger. That reading erases the difference the log is careful to draw between the two review types. DE and 70,000 keep R1 off on any natural reading; they do not soften R2.

**TX-301 and TX-309 (boundary check).** Both are NONCOMPLIANT even before exemption analysis, because no exemption id appears. TX-301 would remain NONCOMPLIANT if the +56.25% increase were ignored, because R1 demands an enhanced review and the case never has one. R4 is an additional defeater of the standard review, not the sole reason. TX-309 is the converse pattern: an enhanced review exists and precedes release, and it is still insufficient because 118,000 → 145,000 (+22.88%) is after that review. Comparing the release amount with the original 95,000 would also exceed 20 percent, but the rule’s baseline is the latest review, which saw 118,000. Either baseline invalidates the review that release actually relies on.

ATTRS = ["amount", "risk_level", "jurisdiction", "customer_type"]
CASE = "case:concept:name"
ACT = "concept:name"
TIME = "time:timestamp"


def more_than_20(new, old):
    """True when new > 1.2 * old, using integers so the 20% line is exact."""
    if pd.isna(new) or pd.isna(old):
        return False
    return int(new) * 5 > int(old) * 6


def parse_log(csv_text: str) -> pd.DataFrame:
    raw = pd.read_csv(io.StringIO(csv_text), dtype=str)
    raw["event_index"] = pd.to_numeric(raw["event_index"], errors="raise").astype(int)
    formatted = pm4py.format_dataframe(
        raw,
        case_id=CASE,
        activity_key=ACT,
        timestamp_key=TIME,
    )
    # format_dataframe orders by case and timestamp only. Re-impose event_index.
    formatted = formatted.sort_values(
        [CASE, TIME, "event_index"], kind="mergesort"
    ).reset_index(drop=True)
    formatted["amount"] = pd.to_numeric(formatted["amount"], errors="coerce")
    for col in ["risk_level", "jurisdiction", "customer_type", "exemption_id", "note"]:
        formatted[col] = formatted[col].replace({"": pd.NA})
    return formatted


def forward_fill_attributes(df: pd.DataFrame) -> pd.DataFrame:
    out = df.copy()
    out[ATTRS] = out.groupby(CASE, sort=False)[ATTRS].ffill()
    return out

def evidence_support(ex: pd.Series, release_ts: pd.Timestamp) -> str:
    """R5 evidence atom. Displayed times and a requester's oral claim do not suffice."""
    sig = ex["qualified_signature_time"]
    cert = ex["certificate_created"]
    if pd.notna(sig) and pd.notna(cert) and sig <= release_ts and cert <= release_ts:
        return "SUPPORTED"
    if pd.notna(cert) and cert > release_ts:
        return "CONTRADICTED"
    if pd.notna(ex["displayed_approval"]):
        return "DISPLAY_ONLY"
    return "UNSUPPORTED"


def evaluate_exemption(ex: pd.Series, state: dict, release_ts: pd.Timestamp, rule: str):
    if ex is None:
        return "NONE", False
    support = evidence_support(ex, release_ts)
    scope_ok = (
        state["jurisdiction"] == ex["scope_jurisdiction"]
        and state["customer_type"] == ex["scope_customer_type"]
        and pd.notna(state["amount"])
        and int(state["amount"]) <= int(ex["amount_max"])
        and rule in str(ex["waives"]).split(",")
        and ex["approved_by"] == "Head_Compliance"
        and pd.notna(ex["effective_from"])
        and ex["effective_from"] <= release_ts
        and pd.notna(ex["expires"])
        and release_ts <= ex["expires"]
    )
    if not scope_ok:
        return support, False
    if support == "SUPPORTED":
        return support, True
    return support, False


def classify_case(r1: str, r2: str, r3: str) -> str:
    vals = [r1, r2, r3]
    if any(v == "VIOLATION" for v in vals):
        return "NONCOMPLIANT"
    if any(v == "INDETERMINATE" for v in vals):
        return "INDETERMINATE"
    if any(v == "REVIEW_REQUIRED" for v in vals):
        return "REVIEW_REQUIRED"
    if any(v == "JUSTIFIED_EXCEPTION" for v in vals):
        return "JUSTIFIED_EXCEPTION"
    return "COMPLIANT"


def replay_case(g: pd.DataFrame, register: pd.DataFrame) -> dict:
    g = g.sort_values([TIME, "event_index"], kind="mergesort")
    state = {a: pd.NA for a in ATTRS}
    last = {
        "Standard_Review": None,
        "Enhanced_Review": None,
        "Compliance_Approve": None,
        "Sanctions_Screen": None,
        "Sanctions_List_Update": None,
    }
    amount_at = {"Standard_Review": pd.NA, "Enhanced_Review": pd.NA}
    jur_at_enhanced = pd.NA
    review_key = None
    amount_at_latest_review = pd.NA
    latest_review_name = None
    high_since = None
    pep_since = None
    list_adds = []
    jur_change_keys = []
    release = None
    approve_note = pd.NA
    material_increase_keys = []

    for rec in g.itertuples(index=False):
        ts = getattr(rec, TIME)
        idx = int(getattr(rec, "event_index"))
        key = (ts, idx)
        act = getattr(rec, ACT)
        old = dict(state)
        for attr in ATTRS:
            val = getattr(rec, attr)
            if pd.notna(val):
                state[attr] = val
        if pd.notna(old["amount"]) and pd.notna(state["amount"]) and more_than_20(state["amount"], old["amount"]):
            material_increase_keys.append(key)
        if pd.notna(old["jurisdiction"]) and pd.notna(state["jurisdiction"]) and state["jurisdiction"] != old["jurisdiction"]:
            jur_change_keys.append(key)
        if state["risk_level"] == "HIGH" and old["risk_level"] != "HIGH":
            high_since = key
        if state["customer_type"] == "PEP" and old["customer_type"] != "PEP":
            pep_since = key
        if act in ("Standard_Review", "Enhanced_Review"):
            last[act] = key
            amount_at[act] = state["amount"]
            if review_key is None or key > review_key:
                review_key = key
                amount_at_latest_review = state["amount"]
                latest_review_name = act
            if act == "Enhanced_Review":
                jur_at_enhanced = state["jurisdiction"]
        elif act == "Compliance_Approve":
            last[act] = key
            approve_note = getattr(rec, "note")
        elif act == "Sanctions_Screen":
            last[act] = key
        elif act == "Sanctions_List_Update":
            last[act] = key
            list_adds.append((key, state["jurisdiction"]))
        elif act == "Release_Funds":
            release = {
                "key": key,
                "ts": ts,
                "state": dict(state),
                "exemption_id": getattr(rec, "exemption_id"),
            }

    if release is None:
        return {"case": g[CASE].iloc[0], "coarse_label": "INDETERMINATE", "note": "no release"}

    st = release["state"]
    rel_key = release["key"]
    amt, jur = st["amount"], st["jurisdiction"]
    risk, cust = st["risk_level"], st["customer_type"]

    # R4 against the latest standard or enhanced review.
    if review_key is None:
        r4 = "NO_PRIOR_REVIEW"
        ratio = pd.NA
    elif pd.isna(amount_at_latest_review) or pd.isna(amt):
        r4 = "NOT_CLASSIFIABLE"
        ratio = pd.NA
    else:
        ratio = float(amt) / float(amount_at_latest_review)
        r4 = "INVALIDATES" if more_than_20(amt, amount_at_latest_review) else "DOES_NOT_INVALIDATE"

    post_review_jur_change = any(review_key is not None and review_key < k < rel_key for k in jur_change_keys)
    # Jurisdiction changes are assessed for R1 only when an enhanced review is the candidate.
    post_er_jur_change = any(
        last["Enhanced_Review"] is not None and last["Enhanced_Review"] < k < rel_key for k in jur_change_keys
    )

    ex = None
    ex_id = release["exemption_id"]
    if pd.notna(ex_id):
        hit = register.loc[register["exemption_id"] == ex_id]
        ex = None if hit.empty else hit.iloc[0]
    support, ex_valid = evaluate_exemption(ex, st, release["ts"], "R1")

    # R1
    domestic = pd.notna(jur) and jur == "DE"
    below = pd.notna(amt) and int(amt) < 100000
    if domestic or below:
        r1 = "NOT_TRIGGERED"
    elif pd.isna(jur) or pd.isna(amt):
        r1 = "INDETERMINATE"
    else:
        er = last["Enhanced_Review"]
        if er is None or not (er < rel_key):
            review_ok = False
            unclass = False
        elif pd.isna(amount_at["Enhanced_Review"]):
            review_ok = False
            unclass = True
        elif more_than_20(amt, amount_at["Enhanced_Review"]) or post_er_jur_change:
            review_ok = False
            unclass = False
        else:
            review_ok = True
            unclass = False
        if review_ok:
            r1 = "SATISFIED"
        elif unclass:
            r1 = "INDETERMINATE"
        elif ex_valid:
            r1 = "JUSTIFIED_EXCEPTION"
        elif support == "DISPLAY_ONLY":
            r1 = "REVIEW_REQUIRED"
        else:
            r1 = "VIOLATION"

    # R2. Amount invalidation does not erase a HIGH/PEP review whose triggers are unchanged.
    if risk == "HIGH" or cust == "PEP":
        need = [k for k, flag in ((high_since, risk == "HIGH"), (pep_since, cust == "PEP")) if flag and k is not None]
        t_star = max(need) if need else None
        er = last["Enhanced_Review"]
        ca = last["Compliance_Approve"]
        standard_packet = isinstance(approve_note, str) and "standard" in approve_note.lower()
        if er is not None and ca is not None and t_star is not None and t_star < er < ca < rel_key and not standard_packet:
            r2 = "SATISFIED"
        elif pd.isna(risk) or pd.isna(cust):
            r2 = "INDETERMINATE"
        else:
            r2 = "VIOLATION"
    elif pd.isna(risk) or pd.isna(cust):
        r2 = "INDETERMINATE"
    else:
        r2 = "NOT_TRIGGERED"

    # R3
    matching_adds = [k for k, added in list_adds if added == jur and k < rel_key]
    if pd.isna(jur):
        r3 = "INDETERMINATE" if list_adds else "NOT_TRIGGERED"
    elif not matching_adds:
        r3 = "NOT_TRIGGERED"
    else:
        u = max(matching_adds)
        screen = last["Sanctions_Screen"]
        later_screen = screen is not None and u < screen < rel_key
        if screen is not None and u < screen:
            r3 = "NOT_TRIGGERED"
        elif later_screen:
            r3 = "SATISFIED"
        else:
            r3 = "VIOLATION"

    label = classify_case(r1, r2, r3)
    return {
        "case": g[CASE].iloc[0],
        "release_time": release["ts"],
        "amount_at_release": amt,
        "risk_at_release": risk,
        "jurisdiction_at_release": jur,
        "customer_at_release": cust,
        "amount_unknown": bool(pd.isna(amt)),
        "risk_unknown": bool(pd.isna(risk)),
        "jurisdiction_unknown": bool(pd.isna(jur)),
        "customer_unknown": bool(pd.isna(cust)),
        "last_standard_review": None if last["Standard_Review"] is None else last["Standard_Review"][0],
        "last_enhanced_review": None if last["Enhanced_Review"] is None else last["Enhanced_Review"][0],
        "enhanced_review_index": None if last["Enhanced_Review"] is None else last["Enhanced_Review"][1],
        "jurisdiction_at_enhanced_review": jur_at_enhanced,
        "amount_at_enhanced_review": amount_at["Enhanced_Review"],
        "last_compliance_approve": None if last["Compliance_Approve"] is None else last["Compliance_Approve"][0],
        "approve_note": approve_note,
        "last_sanctions_screen": None if last["Sanctions_Screen"] is None else last["Sanctions_Screen"][0],
        "last_sanctions_list_update": None if last["Sanctions_List_Update"] is None else last["Sanctions_List_Update"][0],
        "latest_review": latest_review_name,
        "amount_at_latest_review": amount_at_latest_review,
        "post_review_amount_ratio": ratio,
        "r4_effect": r4,
        "post_review_jurisdiction_change": post_review_jur_change,
        "material_increase_count": len(material_increase_keys),
        "exemption_id": ex_id if pd.notna(ex_id) else pd.NA,
        "exemption_evidence": support,
        "exemption_valid_for_r1": ex_valid,
        "exemption_signature_time": None if ex is None else ex["qualified_signature_time"],
        "exemption_certificate_created": None if ex is None else ex["certificate_created"],
        "exemption_record_time": None if ex is None else ex["record_time"],
        "r1_flag": r1,
        "r2_flag": r2,
        "r3_flag": r3,
        "coarse_label": label,
    }


def declare_precedence(case_df: pd.DataFrame, earlier: str, later: str) -> bool:
    """DECLARE precedence(earlier, later): if later occurs, some earlier occurs ≺ it.

    Vacuous truth when later never occurs. This ignores data conditions on purpose.
    """
    g = case_df.sort_values([TIME, "event_index"], kind="mergesort")
    later_hits = g.loc[g[ACT] == later, ["event_index", TIME]]
    if later_hits.empty:
        return True
    first_later = later_hits.iloc[0]
    earlier_hits = g.loc[g[ACT] == earlier]
    if earlier_hits.empty:
        return False
    for rec in earlier_hits.itertuples(index=False):
        if (getattr(rec, TIME), int(getattr(rec, "event_index"))) < (
            first_later[TIME],
            int(first_later["event_index"]),
        ):
            return True
    return False

Control-flow precedence cannot stand in for the flags above. `precedence(Enhanced_Review, Release_Funds)` is false for TX-304, which is a sanctions miss rather than a missing enhanced review, and true for TX-309 and TX-305, which are a stale review and an unknown amount. ## 6. Why Control-Flow-Only Conformance Is Insufficient

A DECLARE or trace-alignment model sees activity names and, at best, their order. These obligations turn on the state at one event, compared with the state at an earlier event, plus evidence that is not an activity.

1. **Final-state leakage.** TX-305 ends at 150,000. That figure is not the amount at release; the release row never contained an amount. TX-301’s final 125,000 was not the amount at the standard review. TX-311’s final jurisdiction `DE` was not the jurisdiction at the enhanced review. A case attribute joined from the last event paints every earlier activity with the end state.

2. **Post-hoc exemptions and split clocks.** TX-302 and TX-310 both reference an exemption at release and both insert the database row at 11:00, after release. Requiring `Record_Exemption ≺ Release_Funds` condemns TX-302, whose qualified signature at 09:05 already supported the approval. Treating “exemption recorded eventually” as enough absolves TX-310, whose certificate was created at 10:30. Record time, effective time, and evidence time are different relations. The trace has only one timestamp per row.

3. **Material change after a review that still precedes release.** TX-309 contains `Enhanced_Review` and then `Release_Funds`, so precedence holds, but 118,000 → 145,000 (+22.88%) invalidated that review. The mirror images are easy false alarms: TX-308’s decrease and TX-306’s +4.545% increase sit between review and release and do not invalidate anything. A single “no update after review” constraint cannot express the 20 percent asymmetry.

4. **Conditional activation.** R1, R2, and R3 do not share a guard. `precedence(Enhanced_Review, Release_Funds)` fails TX-304, whose live duty is a second sanctions screen after XZ was listed, and whose 60,000 amount never triggers R1. The same constraint passes TX-303, which has the enhanced review and lacks `Compliance_Approve` after a move to HIGH. TX-307 fails the enhanced-review precedence and is in fact noncompliant, but the reason is PEP after a customer-type update, not a foreign high-value amount. One global ordering rule mixes true hits with both false hits and false passes.

5. **Missing data.** TX-305’s trace contains create, enhanced review, and release. Existence and precedence are satisfied. The amount cell is empty on every event up to release. Conformance has no `⊥`, so an implementation that drops incomplete traces, or that fills 0, silently converts an indeterminate R1 question into a pass or a fail.

6. **Same-timestamp ordering.** TX-311’s enhanced review and the change to DE share 16:20. The control-flow word is only the multiset or the sequence of names; `event_index` is outside the alphabet. A timestamp sort that is not stable, or a log converter that keeps one event per timestamp, attributes the review to the wrong jurisdiction. Under a continuous reading of R1 that swap changes the result.

7. **Activity labels hide the object that was approved.** `Standard_Review` is a different act from `Enhanced_Review`. TX-301, TX-307, and TX-310 all contain a review activity and still fail R1 or R2. TX-307 also contains `Compliance_Approve`, which is the label R2 asks for, while the note says the packet was the standard review. Equality of activity names is not equality of the attested state.

8. **Exemption scope is not a trace arc.** Even a perfect “exemption then release” pattern would not check Head_Compliance, jurisdiction, customer type, amount cap, expiry, the rule waived, or signature time. EX-77 and EX-88 are both R1-only and both amount-capped. The facts that separate them sit in a register, not in the sequence of activity names.

## 7. Recommended Logging and Control Improvements

Log a decision so that a later auditor can rebuild the snapshot without inference.

- **Immutable release payload.** On `Release_Funds`, store amount, currency, risk, jurisdiction, customer type, sanctions-list version, exemption ids relied on, rule ids evaluated, and a hash of the review pack. Reject a release whose payload omits amount or currency. Do not let settlement rewrite that payload.
- **Three timestamps on every state change and every exemption.** `effective_time`, `record_time`, and `evidence_time` (qualified signature time and certificate serial). A late insert is valid only when `evidence_time` is at or before the decision and the lag reason is a structured code, such as `outage`, rather than free text.
- **Rule version.** Store the policy version and the threshold (100,000 EUR, 20 percent, which roles may approve) on the release event, so a later policy edit does not rewrite history.
- **Structured exemption scope.** Fields for jurisdiction, customer type, amount minimum and maximum, currency, rules waived, `effective_from`, `expires`, approver role, and signature reference. Match them to the release payload in the control, not in a spreadsheet note.
- **Change provenance.** Each update writes old value, new value, actor, source system, and reason. “Blank means unchanged” should be an explicit `unchanged` marker, distinct from `unknown` and from a deliberate clear.
- **Stable order.** Persist a monotonic per-case sequence as the authoritative order. Keep timestamp and `event_index` immutable. Forbid two business events from sharing a sequence number. If two facts must share a timestamp, the sequence still says which state each event saw.
- **Review attestation.** `Enhanced_Review` and `Compliance_Approve` should name the amount, risk, jurisdiction, customer type, and sanctions-list version the actor attested, plus `packet_type = enhanced|standard`. An approval of a standard packet then cannot be read as the successor of an enhanced review.
- **Sanctions pairing.** Screens store the list version they ran against. List updates store the jurisdiction added or removed and the effective time. The release control requires the screen version to be at least the latest version effective before release.
- **Unknown is a blocking status.** If amount, risk, jurisdiction, or customer type is unknown at release, the control result is `INDETERMINATE` and release stops, rather than a default to LOW, DE, or zero.
