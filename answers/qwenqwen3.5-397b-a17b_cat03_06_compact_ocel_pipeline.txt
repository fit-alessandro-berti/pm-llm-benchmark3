## 4. Expected flattened behavior

*   **Order:**
    *   *Trace Shape:* `Create Order`  `Add Item`  `Reserve Stock`  `Issue Invoice`  `Close Order`.
    *   *Shared Events:* `Reserve Stock` and `Issue Invoice` will appear in both O100 and O200 traces.
    *   *Omitted Aspects:* `Pack Package` and `Dispatch Package` will likely be **omitted** because my E2O modeling linked these events to `Package`/`Delivery`/`Item`, not directly to `Order`. This demonstrates the trade-off: the Order log is clean but operationally incomplete without O2O traversal.
    *   *DFG Edges:* Linear flow mostly, with `Reserve Stock` potentially looping or parallel depending on discovery noise.
    *   *Misleading Interpretation:* One might assume Orders are fulfilled without packing/shipping steps.

*   **Package:**
    *   *Trace Shape:* `Pack Package`  `Dispatch Package`.
    *   *Copied Events:* None (Packages are distinct).
    *   *Omitted:* Stock reservation (linked to Items/Orders), Invoice/Payment.
    *   *DFG:* Simple linear sequence.

*   **Delivery:**
    *   *Trace Shape:* `Dispatch Package`  `Confirm Delivery`.
    *   *Omitted:* Packing (preceding event linked to Package).
    *   *DFG:* Simple linear sequence.

*   **Invoice:**
    *   *Trace Shape:* `Issue Invoice`  `Record Payment` (x2).
    *   *Shared Events:* `Issue Invoice` is the start. `Record Payment` links to Invoice.
    *   *DFG:* `Issue Invoice`  `Record Payment`. Since there are two payments (M1, M2) for V1, the flattened log for V1 will have two events of the same activity type. This might look like a loop or parallel activity in a DFG depending on timestamp handling.

*   **Payment Flattening Weakness:**
    Flattening on `Payment` yields traces of length 1 (just `Record Payment`). Payments (M1, M2) do not have a lifecycle in this model (no "Initiate Payment", "Validate Payment"). They are instantaneous settlement events. A DFG on Payment objects would show no edges (start  end immediately), providing zero process insight.

## 5. Expected object-centric structures

*   **OC-DFG:** Will reveal the cross-object flow. We expect to see edges from `Add Item` (Order/Item) to `Reserve Stock` (Order/Item), then to `Pack Package` (Package/Item). Crucially, it will show the divergence at `Pack Package` (P1 vs P2) and the convergence at `Issue Invoice` (V1 collecting O100/O200).
*   **OTG (Object Type Graph):** Will show the schema: `Order`  `Item`  `Package`  `Delivery`. Also `Invoice`  `Order` and `Payment`  `Invoice`. This validates the structural relationships independent of time.
*   **ET–OT (Event Type to Object Type):** A matrix showing which activities touch which types. E.g., `Dispatch Package` touches `Package` and `Delivery` but not `Order`. This highlights the "blind spots" of single-object flattening.
*   **Object-Centric Petri Net:** Will likely show places representing object states (e.g., "Item Reserved", "Package Packed"). Transitions will be activities. Because P1 combines I1 and I3 (from different Orders), the net will show a **synchronization transition** at `Pack Package` or `Reserve Stock` where tokens from O100 and O200 paths meet.
*   **Object-Interactions Summary:** Will quantify how many events are shared.
    *   `Reserve Stock`: Shared by 4 objects (O100, O200, I1, I3). High interaction score.
    *   `Issue Invoice`: Shared by 3 objects (V1, O100, O200).
    *   `Add Item`: Shared by 2 objects.
    *   This summary identifies `Reserve Stock` and `Issue Invoice` as the primary coupling points in the system.

## 6. Modeling alternatives

1.  **Source-Minimal Relations:**
    *   *Policy:* Only link the primary object explicitly named in the event sentence (e.g., "Dispatch P1" links only to P1).
    *   *Impact:* Flattened Order logs would be extremely sparse (no logistics events). OC-DFG would rely entirely on O2O traversal to connect logistics to Orders, potentially weakening edge confidence in discovery algorithms that weight E2O heavily.
2.  **Full Operational Involvement:**
    *   *Policy:* Link every object that is operationally affected (e.g., "Dispatch P1" links to P1, D1, *and* O100, O200 because P1 contains their items).
    *   *Impact:* Flattened Order logs become complete (include Dispatch). However, it inflates the E2O table and blurs the line between direct system recording and derived knowledge. It might create artificial concurrency in the OC-DFG.
3.  **O2O-Propagated Analytical Relations:**
    *   *Policy:* Do not store downstream relations in E2O. Instead, rely on a preprocessing step that expands E2O based on O2O paths before discovery.
    *   *Impact:* Keeps the raw OCEL clean (faithful to source). Allows analysts to toggle "propagation depth" during analysis. Requires more complex pipeline logic outside the standard OCEL constructor.

## 7. Failure modes

1.  **Relation Inflation:** Copying event attributes into `relations` for every object link creates a wide table. If an event touches 100 items, the event data is duplicated 100 times, increasing memory usage significantly.
2.  **Missing Direct E2O Links:** If `Dispatch Package` is not linked to `Delivery` in E2O, the Delivery object type will have no events, making `ocel_flattening` on Delivery return an empty log.
3.  **Treating O2O Propagation as Observation:** Assuming that because O100 `contains` I1, an event on I1 is *observed* on O100. This confuses structural hierarchy with temporal occurrence, potentially distorting performance analysis (e.g., Order start time vs Item start time).
4.  **Duplicate Shared Events after Flattening:** If an event touches two Orders (e.g., `Reserve Stock`), and we flatten on Order, the event appears in both traces. If we merge these traces later without care, we might double-count throughput times.
5.  **Ambiguous Payment Allocation:** M1 and M2 settle V1. V1 bills O100 and O200. The data does not specify which Payment covers which Order. Analytics might incorrectly attribute M1 fully to O100.
6.  **Overly Short Payment Traces:** As noted, Payment objects only have one event. Discovery algorithms expecting a "start" and "end" activity might fail or produce trivial nets for this object type.
7.  **Constructor/API Version Mismatch:** The `OCEL` class constructor signature varies between PM4Py versions (e.g., `OCEL2` vs `OCEL`). Hardcoding this might break in production if the library updates.
8.  **False Total Order for Same-Time Events:** Although this dataset has unique timestamps, if two events shared a timestamp, standard sorting might impose an arbitrary order, creating false causality in the DFG.
