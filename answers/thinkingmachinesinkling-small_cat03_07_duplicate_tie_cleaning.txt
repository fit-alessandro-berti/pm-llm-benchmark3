 NO (different activity or timestamp, but grouped by common objects)

## 3. Timestamp-tie ordering rules

### Rule taxonomy

| Rule | Type | Basis |
|---|---|---|
| **R1. Domain precedence** (e.g., `Validate` after `Create`; `Authorize` before `Capture`; `Accept` before `Handover`; `Pick` before `Pack`) | **Semantic** | Lifecycle / business logic |
| **R2. Object-state lifecycle** (same `O1`: `Create`  `Validate`  `Pick`  `Pack`  `Dispatch`  `Invoice`  `Capture`  `Confirm`) | **Semantic** | Object-centric lifecycle constraints |
| **R3. Within-source sequence** (`source_seq` within same `source`) | **Deterministic / weakly semantic** | Source-local ordering; used only when R1/R2 silent and sources agree |
| **R4. Source-specific semantics** (WMS physical detail before ERP message summary; scanner scan before WMS enrichment) | **Semantic** | Source role and message flow |
| **R5. Related-object dependency** (capture of `M1` requires `V1`; pick of `I1` requires order open) | **Semantic** | Cross-object relations |
| **R6. Ingestion time (`ingested_at`)** | **Technical only; never primary business order** | Technical artifact; may indicate latency, not causality |
| **R7. Stable fallback** (ascending `eid` or original key) | **Deterministic** | Guarantees total order without inventing causality |

### The microsecond trap

Adding synthetic microseconds (e.g., `+1ms` to `e09` to make it after `e08`, or `+0.001s` to `e05` to make it after `e03`) **before** applying R1–R5 **encodes a false causality**. It turns an arbitrary concurrency into an apparent sequentiality, which corrupts concurrency analysis, parallel DFG discovery, and performance statistics (e.g., false “wait time” or false “duration”). The correct procedure is:

1. Build a **partial order** using R1–R5.
2. For elements incomparable under that partial order, apply R3/R7 to obtain a **deterministic total order** for computation only.
3. Preserve the **original timestamp** unchanged; use a separate `adjusted_order_key` or `sequence_index` for sorting, never overwrite the business timestamp.

### Intended orders (admissible alternatives noted)

**10:00 cluster (`e03`–`e07`)**
- Partial order: `{e03/e04}` (merged canonical pick `I1`) and `e05` (pick `I2`) are concurrent; both precede `e06` (physical pack); `e06` precedes `e07` (ERP summary) by R4.
- Admissible total orders:
  1. `e03/04` (canonical), `e05`, `e06`, `e07`
  2. `e05`, `e03/04`, `e06`, `e07`
  (Only requirement: picks before pack; physical before summary; picks concurrent.)

**10:15 cluster (`e08`–`e10`)**
- Partial order: `e08`  `e09`  `e10` (release  accept  handover; R1/R2).
- Total order is forced by semantics: `e08`, `e09`, `e10`. No ambiguity.

**12:00 cluster (`e11`–`e16`) after duplicate handling**
- After merging `e11/e16`  single invoice event (`e11_merged`), and retaining `e12` (`Authorize M1`), `e13` (`Capture M1`), `e14` (`Capture M2`), `e15` (ERP summary).
- Partial order: `e11_merged`  `e12`  `e13`; `e13` and `e14` concurrent (different payments, both after invoice/auth); `e15` after both `e13` and `e14` (summary of messages).
- Admissible: `e11_merged`, `e12`, `e13`, `e14`, `e15`.

## 4. Conservative cleaning pipeline

**Goal:** Minimum change; preserve abstraction; delete nothing unless strongly proven.

**Steps:**

1. **Ingest and archive** `ocel_raw`; create `ocel_work = deepcopy(ocel_raw)`.
2. **Preserve metadata**: ensure `original_timestamp`, `original_activity`, `source`, `source_event_key`, `source_seq`, `payload_hash`, and `ingested_at` exist; never overwrite.
3. **Candidate group detection**: group by (`timestamp`, `activity`) and inspect `related objects` overlap; identify groups with reconciliation notes.
4. **Verified-pair merge only**:
   - Merge `e03`/`e04` (reconciliation confirmed).
   - Merge `e11`/`e16` (same `V1`, complementary authority).
   Use a custom merge function (see §6) that unions relations and tags attributes by source.
5. **Label refinement**: add `refined_activity` column; for `e07` append ` [ERP Summary]`; for `e09` append ` [Carrier Accept]`; for `e15` append ` [ERP Summary]`; for `e10` keep `Handover` distinct.
6. **Retention of concurrency**: keep `e05` (distinct `I2`), `e14` (`M2`), `e06` (detailed pack), `e08`/`e09`/`e10` all separate.
7. **Partial-order assignment**:
   - Apply R1 (domain), R2 (lifecycle), R4 (source semantics).
   - Derive `partial_order_key` (integer ranks with gaps for concurrency).
8. **Deterministic total-order**:
   - `ocel_sort_by_additional_column` on `partial_order_key`, then `source_seq`, then stable `eid`.
   - Never use `ingested_at`.
9. **Index-based delta** (post-order):
   - `ocel_add_index_based_timedelta` only after sorting; compute inter-event durations from the sorted sequence, but do not alter `timestamp`.
10. **Referential integrity check**: verify all E2O links point to objects in the object table and event IDs exist.

**Expected retained event count:** **15** (from 17). Two verified pairs merge (2), zero unproven drops, zero false merges of concurrent picks or distinct payments.

## 5. Aggressive alternatives

### Scenario A — Evidence-based semantic merging

**Rules:** Merge verified physical duplicates (`e03/e04`, `e11/e16`). Additionally, merge abstraction pairs where the detailed and summary describe the same business transition without new object types (`e06/e07` into one event with combined payload; `e13/e15` merge only if `M1` relation preserved in union). Refine `e08/e09` into a single logistics milestone because they share all objects and are sequential phases of one “dispatch” step (but retain `e10` separate).

**Expected count:** ~13 (merge `e03/e04`, `e11/e16`, `e06/e07`; possibly `e08/e09`).

**Likely semantic damage:** Merging `e06/e07` loses the distinction between physical pack completion and ERP message latency; merging `e08/e09` hides the warehouse-to-carrier handoff interval, which is critical for logistics performance. If `e13/e15` merged incorrectly, summary lag disappears.

### Scenario B — Mechanically aggressive PM4Py merging

**Rule:** Apply `pm4py.ocel_merge_duplicates` with `have_common_object=True`, `same_activity=True`, and `timestamp_key="timestamp"` globally, without inspecting candidate groups.

**Expected count:** ~8–9 (potential collapse of: `e03/e04/e05`; `e06/e07`; `e08/e09/e10`; `e11/e16`; `e12/e13/e15`; `e13/e14` at risk).

**Most likely damage:** Catastrophic loss of concurrency and partial-payment tracking.

**Why `have_common_object=True` is not sufficient to protect `e13` and `e14`:**
- `e13` relates to `O1`, `V1`, `M1`; `e14` relates to `O1`, `V1`, `M2`.
- They share `O1` and `V1` (order and invoice), which is natural because both payments settle the same invoice.
- However, they are **different business events** because they involve different `Payment` objects (`M1` vs `M2`). A common-object check that ignores object-type specificity and relation cardinalities will merge them, destroying evidence of partial payment and misrepresenting the payment lifecycle as a single capture. The safeguard is to require **identical related-object sets at the fine-grained instance level** (or verified reconciliation) before merging.

## 8. Audit trail and reversibility

### Provenance schema per canonical event

| Field | Purpose |
|---|---|
| `canonical_eid` | Stable ID in cleaned log |
| `source_event_ids` | List of original `eid`s (e.g., `["e03","e04"]`) |
| `merge_rule_version` | Version tag (`v1.0-verified-pair`, `v2.0-abstraction-retention`) |
| `reviewer_or_rule` | Automated rule ID or human reviewer code |
| `original_activity` | Label from primary source |
| `refined_activity` | Post-cleaning label / qualifier |
| `original_timestamp_utc` | Unchanged business timestamp |
| `adjusted_timestamp_utc` | Only if a deterministic shift is applied (should be null for conservative) |
| `attributes_source_map` | JSON: `{"WMS": {"location":"A1"}, "SCANNER": {"key":"S-901"}}` |
| `relations_source_map` | JSON listing which source contributed which E2O tuples |
| `discarded_conflicts` | List of fields dropped / overridden (e.g., `payload_hash_scanner` if not used) |
| `confidence_score` | `high` / `medium` / `low` / `quarantine` |
| `reason_text` | Human-readable justification |

### Reconstructing the raw view

An analyst reconstructs by:
1. Selecting `canonical_eid` from cleaned log.
2. Looking up `source_event_ids` in the provenance table.
3. Retrieving original rows from `ocel_raw` (archived separately, never overwritten) using `source_event_key` and `original_timestamp`.
4. Applying `attributes_source_map` to see which source provided which fields.
5. Checking `discarded_conflicts` to see if any assertion was overridden.
Because `original_timestamp` is never overwritten and `source_event_key` is preserved, the raw record is fully recoverable without reverse-engineering.

## 9. Failure modes and safeguards

| # | Failure mode | Example / Manifestation | Safeguard |
|---|---|---|---|
| 1 | **Collapsing distinct partial payments** | Merging `e13` (`M1`) and `e14` (`M2`) because they share `O1`/`V1`; losing `M2` | Require identical related-object instance sets (`M1` vs `M2`); never merge if `Payment` objects differ |
| 2 | **Converting abstraction-level updates into false rework** | Merging `e07` (ERP summary) with `e06` (WMS detail) creates loop `Pack  Pack` | Preserve abstraction levels; add qualifiers rather than merge |
| 3 | **Ordering by ingestion time** | `e09` ingested at 10:15:20 after `e08` at 10:15:01; false sequence implied | Use domain lifecycle (R1/R2); tag `ingested_at` as technical |
| 4 | **Treating shared objects as proof of duplication** | `e13`/`e14` share `O1,V1`; `e03`/`e05` share `O1,P1`; merger collapses them | Inspect object-type cardinality; disjoint sub-objects mean concurrency |
| 5 | **Unioning incompatible E2O relations** | Merging `e11`/`e16` and accidentally dropping `V1` attributes from billing | Union relations explicitly; tag source of each relation |
| 6 | **Changing durations through synthetic microseconds** | Adding 1ms to `e09` to make it “after” `e08`; inventing transfer latency | Apply partial order first; only use deterministic tie-break for incomparable pairs; keep original timestamps |
| 7 | **Losing source-authoritative attributes** | Taking WMS payload and overwriting ERP invoice fields | Implement `source_authority` map; merge with tag rather than overwrite |
| 8 | **Applying duplicate functions globally without candidate inspection** | Running `pm4py.ocel_merge_duplicates` on full OCEL; merges picks of `I1` and `I2`; collapses logistics chain | Mandatory `pre_check_candidates`; restrict library calls to verified groups only |
| 9 | **Quarantining unresolved candidates then ignoring them** | Leaving `e08/e09` unclassified but forcing total order | Quarantine must block merge/drop; only deterministic ordering allowed |
| 10 | **Falsely assuming same timestamp = same instant** | `e03/e05` at 10:00 are concurrent picks; microsecond insertion makes them sequential | Preserve concurrency in partial order; use object-level constraints only |

**Constraints satisfied:** `e05` and `e14` are never dropped; ingestion time is never primary order; original timestamps preserved; deterministic total order never presented as physical truth; multiple pipelines (conservative, evidence, mechanical) compared; no blanket merge of equal-activity events.

The pipeline is designed for conservative preservation first, with explicit escalation paths to evidence-based and mechanical alternatives only when provenance is documented and risks are explicitly accepted.
