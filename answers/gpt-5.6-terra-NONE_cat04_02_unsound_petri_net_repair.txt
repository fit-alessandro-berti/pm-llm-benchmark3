# 1. Executive Verdict

The model is structurally a workflow net: it has one source place, one sink place, and every node is on at least one directed source-to-sink path. It should not be expected to be sound, however. The principal defect is that `t_join_waived` consumes only the waiver token and creates `p_decision`, without requiring the mandatory analysis token in `p_analysis_done`. Consequently, authorization can occur before analysis is performed. If analysis is later performed, its token remains stranded in `p_analysis_done`, so a marking containing a sink token is reachable but the exact final marking `fm = [sink:1]` is not. The business consequence is unauthorized completion of waived cases before mandatory analysis, plus improper completion/dead-token behavior.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source -> t_register -> p_ready` | Start and registration of a case | Correct sequential entry into the process | No issue by itself |
| `t_split` | AND-split: create analysis and review work in parallel | Consumes one token from `p_ready` and creates one token in each of `p_analysis` and `p_review` | Correctly enables concurrent/interleaved analysis and review choice |
| Analysis branch: `p_analysis -> t_analyze -> p_analysis_done` | Mandatory analysis | Produces a token that is required by `t_join_normal`, but not by `t_join_waived` | Waived cases can bypass analysis; a later analysis token can become stranded |
| Standard-review branch: `p_review -> t_standard_review -> p_review_done` | One allowed review outcome | Competes with `t_waive_review` for the single token in `p_review`; therefore only one review outcome can occur | Correct XOR choice between standard review and waiver |
| Waiver branch: `p_review -> t_waive_review -> p_waived` | Alternative review outcome, formally recorded | Produces `p_waived`, but that token alone enables `t_join_waived` | Waiver alone permits decision and authorization |
| `t_join_normal` | AND-join requiring analysis and standard review | Correctly requires tokens from both `p_analysis_done` and `p_review_done` before producing `p_decision` | Standard-review route respects mandatory analysis |
| `t_join_waived` | Intended AND-join requiring analysis and waiver | Has only one input, `p_waived`; it is not a synchronization | Decision and authorization may occur without analysis |
| `p_decision -> t_authorize -> sink` | Authorization and proper completion | Authorization consumes one decision token and produces one sink token | A sink token may be reached while another token remains elsewhere |
| Initial marking `im = [source:1]` | Unique case start | Correctly initializes the source place | Appropriate workflow-net initial marking |
| Final marking `fm = [sink:1]` | Proper completion with no residual work | Exact final marking requires only one sink token and no other tokens | Waiver-after-bypass route reaches a sink token but not `fm` if analysis is later fired |
| Source/sink reachability | Workflow-net structural requirement | Every place and transition lies on at least one directed source-to-sink graph path | Structural connectivity does not guarantee behavioral soundness |

The review alternatives are mutually exclusive because both consume the same token in `p_review`. The defect is not the XOR choice itself; it is the missing analysis input to the waiver synchronization.

# 3. Marking-Based Counterexample

A legal firing sequence exposing the defect is:

```text
t_register, t_split, t_waive_review, t_join_waived, t_authorize, t_analyze
```

Here, `t_authorize` fires before `t_analyze`, violating the requirement that analysis be complete before authorization.

Notation below uses place names with positive token counts only.

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `[source:1]` | `{t_register}` | Initial marking `im` |
| 1 | `t_register` | `[p_ready:1]` | `{t_split}` | Case registration completed |
| 2 | `t_split` | `[p_analysis:1, p_review:1]` | `{t_analyze, t_standard_review, t_waive_review}` | One token has been created in each parallel branch |
| 3 | `t_waive_review` | `[p_analysis:1, p_waived:1]` | `{t_analyze, t_join_waived}` | Waiver outcome is recorded; analysis is still unfinished |
| 4 | `t_join_waived` | `[p_analysis:1, p_decision:1]` | `{t_analyze, t_authorize}` | Defect: waiver alone enabled the waiver “join”; no analysis token was required |
| 5 | `t_authorize` | `[p_analysis:1, sink:1]` | `{t_analyze}` | Authorization occurs before analysis. A token exists in `sink`, but this is not exact final marking `fm`, because `p_analysis` still contains a token |
| 6 | `t_analyze` | `[p_analysis_done:1, sink:1]` | `{}` | The analysis token has moved to `p_analysis_done`, but neither join is enabled: `t_join_normal` lacks `p_review_done`; `t_join_waived` requires `p_waived`, already consumed |

At step 5, a token exists in the sink, but the exact final marking is not reached:

```text
current marking = [p_analysis:1, sink:1]
fm              = [sink:1]
```

After step 6, the leftover token in `p_analysis_done` cannot be consumed. `t_join_normal` additionally requires a token in `p_review_done`, but the review token was consumed by `t_waive_review`, so standard review cannot subsequently be performed. `t_join_waived` cannot consume `p_analysis_done` at all and its waiver token has already been consumed. The net is therefore deadlocked outside `fm`.

A second relevant sequence shows that the waiver path can appear to complete correctly if analysis happened first:

```text
t_register, t_split, t_analyze, t_waive_review, t_join_waived, t_authorize
```

This sequence reaches exactly `[sink:1]`. That does not repair the model: the existence of a correct interleaving does not eliminate the illegal interleaving where authorization precedes analysis.

# 4. Minimal-Repair Alternatives

Edit-cost model:

- add one arc: cost 1;
- remove one arc: cost 1;
- add/remove one place: cost 1;
- add/remove one transition: cost 1;
- changing a label or transition identifier is not counted unless needed for a policy change;
- arc weights are unchanged and assumed to be one.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| A. Add analysis as an input to the waiver join | Add arc `p_analysis_done -> t_join_waived` | 1 | Analysis remains mandatory; waiver remains a distinct review outcome; authorization requires analysis plus waiver | Waiver route becomes a true two-input synchronization, parallel to the standard route | Two silent joins lead to the same `p_decision`; operational users may not directly see which silent join fired, though visible review labels remain distinguishable |
| B. Rewire waiver result into the normal join | Remove arc `p_waived -> t_join_waived`; remove arc `t_join_waived -> p_decision`; add arc `p_waived -> t_join_normal` | 3 | Analysis remains mandatory; exactly one review outcome is required; authorization follows analysis plus either review outcome | `t_join_waived` becomes disconnected and must either be removed as a fourth edit or tolerated only if structural validation is not required; the practical clean variant also removes `t_join_waived` | If the unused transition is not removed, the net no longer satisfies normal workflow-net connectivity expectations; with removal, review outcome is still visible but both outcomes share one join |
| C. Explicit policy change: analysis optional for waived cases | Remove arc `p_analysis_done -> t_join_normal`; remove arc `p_analysis_done -> t_join_waived`; add direct arc `p_analysis -> t_join_normal` only if analysis completion is not required on standard route is not appropriate; therefore a clean policy redesign requires separate routing, e.g. remove `t_split` analysis output and add conditional decision structure | More than 1 | Only preserves a changed policy: standard review may still require analysis, while waiver may authorize without it | Mandatory analysis is deliberately abandoned for waived cases | High governance/compliance risk; this is not consistent with the stated business intent |

Repair A is the selected implementation below. It is behaviorally minimal under the stated intent: one additional prerequisite arc makes `t_join_waived` require both `p_analysis_done` and `p_waived`.

Repair B is structurally distinct because it replaces the two-join design with one shared synchronization point. Its clean form is not tied with Repair A: after rewiring, `t_join_waived` has no meaningful source-to-sink participation and should be removed to preserve workflow-net structure, increasing the cost. If preserving the original structure and all nodes is required, Repair A is strictly cheaper.

There is no zero-edit repair that enforces mandatory analysis on the waiver route: in the original net, the sequence through `t_join_waived` and `t_authorize` is enabled without consuming or requiring any analysis-related token.

# 6. Diagnostic and Reachability Code

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking

def marking_as_dict(marking):
    return {
        place.name: count
        for place, count in marking.items()
        if count > 0
    }

def enabled_transition_names(process_net, marking):
    return sorted(
        transition.name
        for transition in pm4py.get_enabled_transitions(process_net, marking)
    )

def get_transition_by_name(process_net, transition_name):
    for transition in process_net.transitions:
        if transition.name == transition_name:
            return transition
    raise KeyError(f"Transition not found: {transition_name}")

def fire_named_transition(process_net, marking, transition_name):
    transition = get_transition_by_name(process_net, transition_name)
    enabled = pm4py.get_enabled_transitions(process_net, marking)

    if transition not in enabled:
        raise RuntimeError(
            f"{transition_name} is not enabled; "
            f"enabled transitions are {enabled_transition_names(process_net, marking)}"
        )

    next_marking = Marking(marking)

    for arc in transition.in_arcs:
        next_marking[arc.source] -= arc.weight
        if next_marking[arc.source] == 0:
            del next_marking[arc.source]

    for arc in transition.out_arcs:
        next_marking[arc.target] = next_marking.get(arc.target, 0) + arc.weight

    print(
        f"fired={transition_name}; "
        f"marking={marking_as_dict(next_marking)}; "
        f"enabled={enabled_transition_names(process_net, next_marking)}"
    )
    return next_marking

for model_name, process_net, initial_marking, final_marking in [
    ("original", net, im, fm),
    ("repaired", repaired_net, repaired_im, repaired_fm),
]:
    print(f"\n=== {model_name.upper()} ===")
    print("workflow net:", pm4py.check_is_workflow_net(process_net))
    print("soundness:")
    print(pm4py.check_soundness(
        process_net,
        initial_marking,
        final_marking,
        print_diagnostics=True
    ))
    print(
        "enabled at initial marking:",
        enabled_transition_names(process_net, initial_marking)
    )

    reachability_graph = pm4py.convert_to_reachability_graph(
        process_net,
        initial_marking,
        final_marking
    )
    print("reachability graph constructed:", reachability_graph is not None)

print("\n=== ORIGINAL WAIVER COUNTEREXAMPLE ===")
m = Marking(im)
print(
    f"initial marking={marking_as_dict(m)}; "
    f"enabled={enabled_transition_names(net, m)}"
)
for transition_name in [
    "t_register",
    "t_split",
    "t_waive_review",
    "t_join_waived",
    "t_authorize",
    "t_analyze",
]:
    m = fire_named_transition(net, m, transition_name)

print("\n=== REPAIRED WAIVER ROUTE ===")
m = Marking(repaired_im)
print(
    f"initial marking={marking_as_dict(m)}; "
    f"enabled={enabled_transition_names(repaired_net, m)}"
)
for transition_name in [
    "t_register",
    "t_split",
    "t_waive_review",
]:
    m = fire_named_transition(repaired_net, m, transition_name)

print(
    "At this point t_join_waived is intentionally disabled until "
    "t_analyze produces p_analysis_done."
)
m = fire_named_transition(repaired_net, m, "t_analyze")
m = fire_named_transition(repaired_net, m, "t_join_waived")
m = fire_named_transition(repaired_net, m, "t_authorize")
```

Qualitatively, both models should satisfy the structural workflow-net check. The original model’s soundness diagnostic should reveal behavioral improper-completion/dead-marking concerns caused by the waiver bypass. The repaired model should remove the waiver-before-analysis path and should allow both review alternatives to complete exactly at `[sink:1]`. The reachability graph for the repaired model should no longer contain a reachable marking with `sink` plus an unfinished or stranded analysis token.

# 7. Repair Trade-Offs and Residual Risks

The selected repair preserves visible distinction between the review alternatives:

- `t_standard_review` remains labeled **Perform Standard Review**.
- `t_waive_review` remains labeled **Record Review Waiver**.

Both alternatives still lead through silent routing transitions, but that is normal Petri-net control-flow modeling. The two silent joins do create structurally similar behavior: both produce `p_decision`. This is not duplicate business behavior because the preceding visible review outcome differs. For audit purposes, event logging should retain the visible waiver or standard-review event and should not rely on silent transition identities.

Soundness is necessary but not sufficient evidence of business alignment. A sound model could still implement the wrong policy, for example by making analysis optional after waiver, by allowing the wrong actor to record a waiver, or by allowing waiver without an appropriate approval rule. Soundness establishes behavioral completion properties, not semantic compliance with all governance requirements.

Regression tests should include these positive traces:

```text
Register Case,
Perform Analysis,
Perform Standard Review,
Authorize Case
```

and

```text
Register Case,
Record Review Waiver,
Perform Analysis,
Authorize Case
```

with either valid interleaving of analysis and the selected review outcome.

Negative traces should include:

```text
Register Case,
Record Review Waiver,
Authorize Case
```

and

```text
Register Case,
Perform Standard Review,
Authorize Case
```

Both must be rejected because analysis is not complete. Also test that both review outcomes cannot occur in the same case, and that authorization cannot occur twice.

An accidental bypass of mandatory analysis can be detected through reachability analysis or model-checking assertions: for every reachable marking enabling `t_authorize`, require that the token enabling authorization can only have been produced by a join consuming an analysis-completion token. Practically, inspect that every directed route to `p_decision` includes a synchronization requiring `p_analysis_done`, and include the negative waiver-without-analysis trace in automated conformance tests.

# 8. Final Recommendation

Deploy Repair A: add `p_analysis_done -> t_join_waived`.

It is the smallest intent-preserving repair under the stated edit-cost model: one arc addition. It directly fixes the missing synchronization condition without changing visible activities, review choice semantics, auditability of waiver versus standard review, or the existing standard-review path. Both successful outcomes then require completed analysis and exactly one selected review outcome before authorization. It also retains a clear conceptual structure: two mutually exclusive review outcomes, each synchronized with mandatory analysis.

Use Repair B, a shared join for standard review and waiver, as a fallback if the organization prefers a simpler control-flow structure with one decision synchronization. That alternative is reasonable but needs careful cleanup of `t_join_waived` to preserve workflow-net structure, making it more invasive. It also makes both review outcomes converge earlier, which may be less convenient when separate downstream audit or policy controls are later added.

Do not adopt an optional-analysis waiver policy unless governance explicitly approves that business-rule change.
