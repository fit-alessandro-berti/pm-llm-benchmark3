Warm-up: transient analysis — the system has long delays (public notice 14-60d), so warm-up should be at least 2-3× the p90 of case duration for the slowest case type, or use initial-state initialization (pre-load backlog from steady-state search). Recommended: 
- Run length: 18 months (to match log) or 24 months with a 6-month warm-up; or use "warm-up until stationarity diagnostics stabilize" (e.g., moving-average of queue lengths over 4-week windows stabilizes).
- Since demand is periodic (seasonal), warm-up should be an integer number of seasonal cycles (1 full year) so that the seasonal phase matches; alternatively start the simulation on Jan 1 with a pre-loaded backlog sampled from the previous-year stationary cycle.
- Replications:  30 (prefer 50-100 for tail metrics); seeds: independent random streams (arrival, routing, service, applicant response, objection, resource) using SeedSequence spawning per stream per replication for common random numbers (CRN) across interventions — critical for paired comparisons.
- CI: nonparametric bootstrap or t-based CI on replication-level metric means; paired t-test/CI for differences vs baseline using CRN; report95% CI. For quantiles (p90, p95) use bootstrap across replications or across cases with cluster bootstrap by replication.
- Bayesian option: hierarchical model for metric by intervention; report posterior difference with P(better) and ROPE.
- Heavy tails: fit lognormal/Weibull/Pareto to exceedances (POT); use empirical resampling with tail extrapolation; truncate at a defensible maximum (e.g., statutory max,99.9th percentile) and report the effect of truncation; do not use normal; validate via Q-Q plots and KS/AD tests; consider L-moments.
- Sensitivity: Morris/Sobol screening on ~30 parameters; one-at-a-time for calendars; scenario analysis; probability of model/parameter uncertainty via sampling parameters from their posterior (parameter uncertainty propagated into outcome intervals = "uncertainty in outcomes" separate from "stochastic variability").

Two sources of uncertainty: (i) process stochasticity (aleatory)  replication variance; (ii) parameter uncertainty (epistemic)  sample parameters from bootstrap/posterior per replication (nested: outer loop over parameter draws, inner loop over replications). Report both.

Validation strategy:
1. Face validation with process owners (clerks, planners, inspectors, legal) — walk-through of queue behavior, check that the "inspectors busy in D3/D5" behavior matches field experience.
2. Event-log replay / backward validation: simulate with the historical input (same arrival times replayed, same case attributes, same calendars)  compare resulting traces to actual traces: distribution of case sojourn (KS/AD, quantile-quantile), variant proportions (chi-square / total variation distance), per-activity waiting (median, p90), rework rates, cycle time per case type, number of inspections per case, outcome (permit/reject) rates.
3. Distributional validation: per-activity service/waiting, per-case duration by variant group, throughput per month, WIP/queue length over time (need proxies — the log only gives waiting before activity; can approximate queue length via Little's law from waiting time and throughput).
4. Resource utilization: compare with HR/overtime data, leave records, known utilization (env 40% non-permit duties, fire Tue-Thu). Use inferred utilization = sum of service times / capacity.
5. Bottleneck validation: check that simulated bottlenecks match known ones (planning queue in peak, legal queue around council weeks, inspection waiting8d).
6. Out-of-sample: calibrate on months 1-12, validate on months 13-18 (or rolling origin: calibrate on Jan-2025..Jun-2025, validate Jul-2025..Dec-2025). Also hold out one case type / one district.
7. Cross-validation of routing: compare simulated branching proportions vs observed; conformance of simulated logs to the discovered model (token replay fitness/alignments should be comparable to real log fitness).
8. Only after validation passes with pre-agreed thresholds do we run intervention experiments; and we report "validated for this domain of operation" — interventions that push the system outside the calibrated operating range (e.g., 2× demand) carry extrapolation risk  flag it.

Decision criteria: define metrics with thresholds/ranges.

Metrics:
- Median and p90/p95 case cycle time by case type; overall.
- SLA compliance by case type (e.g., simple  15d, new residential  45d, commercial  75d, complex  150d — define as provisional targets to be agreed, based on the variant table's medians/p90).
- Rework rate (fraction of cases with 1 rework loop) and rework-induced delay days.
- Throughput and backlog (WIP at month18), oldest-case age.
- Resource utilization per pool: target range 65-85%; flag >90% (unstable) or <40% (waste). Fire reviewers Tue-Thu at high utilization is fragile.
- Fairness: per-district (D1..D5) median/p90 differences  some tolerance (e.g., max/min ratio  1.15 after adjusting for case mix — use case-mix-standardized rates); per-architect: Gini or maxmin of standardized cycle time; no district worse by >10% vs baseline.
- Equity of outcome: reject rates by district/architect (avoid introducing bias, e.g., D2 skipping inspections must not shift risk to low-value applicants: check post-implementation defect/violation proxy — but we can't measure violations in the log  flag as out-of-model; require a monitoring plan).
- Robustness: performance under stress scenarios; rank stability across parameter draws (e.g., intervention is preferred in 80% of parameter draws and 70% of stress scenarios).
- Cost: staffing cost, temporary inspector cost, system build cost, applicant effort (for D1/D7)  cost per day of cycle-time reduction; net-benefit with monetized applicant time (state assumption: EUR/hour applicant time).
- Decision rule: Pareto frontier on (cycle time, cost, fairness, robustness); dominance requirement: no metric worsens beyond tolerance (non-inferiority margins), at least one improves with CI excluding zero.
- Multi-criteria: weighted score with weights elicited from stakeholders; report sensitivity to weights.

Robustness: rank correlation (Kendall's tau) of intervention ranking across scenarios; minimax regret.

    df = df.sort_values([...]).copy()

# Simulation-Based Digital Twin for the Building-Permit Process

> **Framing note.** This design treats the twin as a *calibrated, validated decision-support model*, not as a replay engine and not as an optimiser. Every intervention is evaluated as a **paired counterfactual against a validated baseline under shared random numbers**, with two distinct uncertainty intervals (stochastic variability and parameter uncertainty), and with explicit statements about what the event log **cannot** identify (objection events, building area, environmental sensitivity, start timestamps, rework reasons).

|---|---|
| **Start of scope** | Portal acceptance of `Submit application` (first timestamp of a case) |
| **End of scope** | Terminal event `Issue permit` / `Reject application`; **first** appeal is inside scope as a rework loop; litigation/court appeal is out of scope |
| **Geographic/organisational scope** | Permit office resources: 5 clerks, 8 planners, fire pool (2 FTE-equivalent), environmental pool (3 FTE at 60% permit availability), 4 inspectors, 2 legal officers, system/portal (infinite capacity) |
| **Time model** | Discrete-event simulation, clock in `pandas.Timestamp`, service durations in minutes |
| **Horizon** | 30 simulated months: months 1–12 burn-in (discarded), months 13–30 = 18-month measurement window aligned to the calendar phase of the historical log |
| **Level of detail** | Activity-level DES with **role-level pools but individual resource instances** (needed because fire = Tue–Thu only, legal = blackout weeks, 2 planners are Simple-only) |

**Explicitly out of scope (and why):** pre-submission applicant preparation (modelled only as a *behavioural response* to D1/D7), post-permit construction, deeper legal appeals, consultant internal lead times (lumped into environmental-review hold time), and the rare emergency decisions that were **removed** from the log (either declared out of scope, or re-introduced as a separate exogenous flow with a bounded rate — never silently re-inserted).

### 1.2 Entities

- **Case** (permit application) with attributes: `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `prior_violations`, latent covariates (building area, district sensitivity) drawn from an imputation distribution.
- **ActivityInstance** (start, finish, resource, activity, sojourn).
- **Resource / ResourcePool** (capacity, calendar, skill set, queue discipline, utilisation counters).
- **ReviewResult** (fire/env/planning/legal/inspection outcomes) — needed for the AND-join.
- **NoticePeriod** (statutory window in **calendar** days).
- **ObjectionEpisode** (**latent**; keyed by district × overlapping notice window; flagged `objection:latent = True` in output so it is never mistaken for observed data).
- **InspectionBatch** (district bundle produced by D3).
- **ArchitectCampaign** (burst of submissions from a top-20 architect).
- **AppealEpisode**.

### 1.3 State variables

| Level | State variables |
|---|---|
| **Case** | phase/activity; `arrival_time`; pending review set (AND-join precondition); rework counters per loop (completeness / inspection / legal / appeal); elapsed age; eligibility flags for D2; current queue membership; status  {queued, in-service, holding, finished, abandoned} |
| **Resource** | free/busy count; current case; calendar position (next open slot); remaining capacity today; skill set; accumulated busy minutes / capacity minutes; leave/blackout flag |
| **Queue (per activity)** | queue length; discipline (FIFO default, aging priority for D6, batch formation for D3, triage class for D8); head-of-line waiting time; batch composition |
| **Cross-case / system** | WIP per activity; district backlog; active notice periods per district; active objection episodes per district; open inspection requests per district (for bundling); active architect campaigns; aging-case list; monthly throughput; oldest open case age |
| **Economy of time** | two clocks: **business clock** (municipal resources, `Calendar`) and **calendar clock** (public notice, applicant response, statutory deadlines) |

### 1.4 Queues, disciplines and calendars

| Pool | Capacity | Calendar | Queue discipline |
|---|---|---|---|
| Clerks | 5 FTE | Mon–Fri 08:00–16:00; 1 dedicated to portal support on Monday | FIFO; Monday surge creates the observed 1.5 d median wait |
| Planners | 8 FTE (2 restricted to Simple renovation) | Mon–Fri 09:00–17:00 | FIFO  **aging priority (D6)** as an experiment factor; skill-restricted sub-queues for Simple-only planners |
| Fire reviewers | 2 FTE-equivalent | **Tue–Thu only** | FIFO; single pooled queue (creates cross-type coupling) |
| Environmental | 3 FTE × 60% permit duty = 1.8 permit FTE | Mon–Fri | FIFO  **triage classes (D8)** |
| Inspectors | 4 FTE (+1 temp in D4, peak months only) | Field work **Tue–Fri**, district travel | FIFO  **batch queue (D3)** with window/max-batch-size rules |
| Legal | 2 FTE | Mon–Fri, **blackout during council-meeting weeks** except urgent | FIFO with an "urgent" pre-emptive-priority lane (non-preemptive within a case) |
| System / portal |  | 24/7 | No queue |
| Applicant / third parties | exogenous | Calendar days (test business-day variant) | N/A — modelled as a **response-time distribution**, not a queue |

**Critical modelling distinction (not collapsed):** each activity is decomposed into
1. **queue wait** (endogenous — emerges from capacity vs demand),
2. **touch/resource-occupancy time** (exogenous — schedulable, consumes capacity),
3. **internal hold** (e.g., waiting for a consultant report while "inside" environmental review — consumes *no* capacity but blocks the case).

Only (1)+(2)+(3) summed are observable where start timestamps are missing. See the capacity audit in §2.6 — the supplied summaries are *not* capacity-consistent, which is direct evidence that the reported "service time" is **touch time + internal hold**, not resource occupancy.

### 1.5 Cross-case dependencies (explicitly modelled)

| # | Mechanism | Implementation |
|---|---|---|
| K1 | **Shared resources** (implicit coupling) | Singletons: one planner pool instance, one fire queue, etc. Cases are *never* simulated independently. |
| K2 | **Architect bursts** | `ArchitectCampaign`: top-20 architects (31% of volume) generate over-dispersed same-week clusters of `k` submissions  correlated arrival shocks to the clerk/planner queues. |
| K3 | **Neighbourhood objections** | `ObjectionEpisode(district, window)`: while an episode is active, all open notice periods in that district with overlapping windows receive a **shared** extension multiplier  correlated, district-level duration shocks. Latent by construction. |
| K4 | **Inspection bundling (D3)** | `InspectionBundler`: open requests in one district within a `W`-day window form a batch of size  `B`; travel cost shared (largest saving in D3/D5), but the **first** case in the batch waits for the batch to fill. |
| K5 | **Aging reservation (D6)** | A shared reserved planner-day diverts capacity from fresh cases  couples new and old cases. |
| K6 | **Announcement effects** | Policy rollout in month `m` changes both routing (D2/D8) *and* arrivals (elasticity to applicant friction, D1/D7). |

**Consequence for statistics:** the replication unit is the **whole system run**, not the case. Cases within a replication are dependent  case-level IID confidence intervals are invalid. We report CIs over replications (or cluster-bootstrap by replication) and log the realised dependency graph (edges from K2–K5) to report an effective sample size next to the nominal case count.

## 2. Parameter-estimation plan

### 2.1 PM4Py usage map (log & model handling only)

| Purpose | PM4Py call | Notes |
|---|---|---|

| Attribute & start/end activity profiles | `pm4py.get_event_attribute_values(log, "case_type")`, `pm4py.get_start_activities(log)`, `pm4py.get_end_activities(log)` | Case-mix, district shares, variant mix validation. |

| DFG | `pm4py.discover_dfg(log)`  `(dfg, start_activities, end_activities)` | Frequency DFG. |
| Performance DFG | `pm4py.algo.discovery.dfg.algorithm.apply(log, variant=pm4py.algo.discovery.dfg.Algorithm.DFG_PERFORMANCE)`; **fallback** manual edge-median from consecutive events | Manual fallback matters because missing start timestamps make edge sojourn = waiting + service of the successor. |
| Given process model | `pm4py.parse_process_tree(tree_str)`, `pm4py.view_process_tree(tree)` | See §8 for the operator-set problem. |
| Data-driven reference model | `pm4py.discover_process_tree_inductive(log)` / `pm4py.discover_petri_net_inductive(log)` | Used to locate rework loops and missing activities. |
| Conformance | `pm4py.algo.conformance.tokenreplay.algorithm.apply(log, net)`, `pm4py.algo.conformance.alignments.petri_net.algorithm.apply(log, net, im, fm)`, `pm4py.algo.evaluation.replay_fitness/precision/generalization.algorithm.apply(...)` | Diagnose where the simplified tree *disagrees* with reality. |
| Filtering / slicing | `pm4py.filtering.filter_event_attribute_values(...)` | Per case type, per district, per architect. |

**What PM4Py must *not* be used for in this twin:** PM4Py's playout (`pm4py.algo.simulation.playout`) generates traces from a model but honours **no resource calendars, no queueing, no non-stationary arrivals and no cross-case dependencies** — it is a *conformance reference*, not the twin. PM4Py must not be used to infer missing start timestamps, to reconstruct objection events, or to invent rework reasons.

### 2.2 Arrivals (non-stationary)

1. Take first timestamps per case; produce daily counts `N_d`.
2. Fit a **negative-binomial GLM** (log link, overdispersion needed for architect bursts and Monday spikes):
   `log E[N_d] = 0 + month-dummies + weekday-dummies + trend·t + campaign-indicator_d`.
3. Set Jan–Feb as the seasonal reference (index = 1.0). Verify the reported 1.7× for Mar–May and Sep–Nov; **estimate Jun–Aug and Dec, which the summary leaves unspecified** (data gap  point estimate + wide CI).
4. Back-of-envelope consistency check (to be replaced by the MLE): with Jan–Feb = `a`, Mar–May & Sep–Nov = `1.7a`, and Jun–Aug/Dec assumed `1.15a`, `16.8a = 31,200`  `a  1,857 cases/month  60 cases/day`, peak  `3,157/month  102/day`. If the fitted value differs materially, the assumed index for the unspecified months is wrong — re-solve.
5. **Weekday profile:** only the Monday/Wednesday ratio (2.2) is given. Estimate the full 7-vector from first timestamps; if only the ratio survives, place a **Dirichlet prior** on the remaining days and propagate the uncertainty rather than inventing a profile.
6. **Architect campaigns:** for the top-20 `architect_id`s, count submissions per ISO week  fit a **hurdle/negative-binomial** for campaign size `k` and a day-of-week-biased campaign start; remaining architects  independent NHPP.
7. **Change-point detection** (rolling ² or PELT on daily counts) to find historical regime shifts; expose a `policy_breakpoints` hook so the twin can inject a mid-run regime change (S5).
8. Validate: one-step-ahead forecast of monthly counts; MAPE on held-out months.

### 2.3 Service / touch / hold times

1. Where start timestamps exist: `service = completion  start`, `waiting = start  previous completion`.
2. Where starts are missing: **the split is not identifiable from the log.** Strategy:
   - Fit the distribution on instrumented activities of the same *kind* (desk review, field work, clerical) and partially pool hierarchically across activities (activity-level random effect).
   - Constrain by the **capacity balance** (§2.6): the reconstructed occupancy must be feasible given the calendar.
   - Constrain by the **observed sojourn**: `E[queue] + E[occupancy] + E[hold]  observed sojourn` at the observed load; solve for occupancy, then validate the implied queue length against the reported median waiting.
3. Where only median/p90 are available (the supplied table), reconstruct a lognormal exactly:
   ` = ln(median)`, ` = ln(p90/median)/1.28155`.

   | Activity | median | p90 |  (log) |  (log minutes) | mean (min) |
   |---|---|---|---|---|---|
   | Completeness check | 25 min | 90 min | 1.000 | 3.219 |  61 |
   | Planning review | 3.5 h | 14 h | 1.082 | 5.347 |  377 |
   | Site inspection | 1 h | 3 h + travel | 1.082 (D3/D5 shift  up by travel) | 4.094 |  144 |
   | Fire-safety review | 2.5 h | 9 h | 1.000 | 5.011 |  247 |
   | Legal check | 3 h | 16 h | 1.058 | 5.704 |  344 |

4. Stratify by `case_type`, `district` (travel), and architect where cell sizes allow; use partial pooling elsewhere.
5. **Public notice is not a service-time distribution**: it is `14` statutory **calendar** days + a latent objection extension. Fit a **two-component mixture** on observed durations (component 1: mass at 14–17 d; component 2: right-shifted lognormal)  `P(objection)` = component-2 weight, extension = component-2 location/scale. Report with a bootstrap CI and label it **inferred**, never observed.
6. Heavy tails (site inspection travel, applicant response): fit lognormal/Weibull by MLE, check the tail with a mean-excess/Hill diagnostic; if a Pareto-like tail with ` < 3` appears, use POT/GPD extrapolation for p99 and **report quantiles rather than means** as primary.

### 2.4 Waiting times

Waiting is **not an independent input** for municipal activities — it is an *output* of the queueing model. It enters the plan in three ways:

1. **As a calibration target:** simulated median/p90 waiting before each activity must match the supplied table within tolerance (§6).
2. **As an exogenous distribution** for applicant/third-party response (`Receive missing documents`: median 5 d, heavy-tailed; p90 not supplied  data request; until then, empirical resampling with tail extrapolation and a wide CI).
3. **As a decomposition constraint** where starts are missing (see §2.3).

The limitation is stated openly: for activities with only completion timestamps we can validate **sojourn**, and we can validate **waiting** only indirectly (via the capacity balance and via Little's law `L = W` on inferred queue lengths).

### 2.5 Routing, rework and dependencies

- **Routing predicates** for fire/environment/public notice are encoded as rules with an *uncertainty envelope*, because two predictors are missing (building area, district sensitivity):
  `P(requires_fire | case_type, application_value, district)` and `P(requires_env | case_type, district, observed flag)` fitted from observed flags; the "unknown" bucket is run under best/worst-case bounds.
- **Join semantics:** `Decision drafting` requires an AND-join over the *applicable* subset {planning, fire, environmental, public notice, inspection}. This is a **partial-order constraint**, not expressible in the simplified tree  encoded directly in the engine.
- **Outcome routing:** `P(reject | case_type, district, rework_count, appeal)` from the log; where counts are small, hierarchical shrinkage toward the overall rate.
- **Rework:** count loop back-edges per case with token replay/alignments on the discovered model; estimate `P(1 iteration)` at completeness / inspection / legal / appeal and the iteration-count distribution (geometric-like) with a cap = observed max + 1; sensitivity over the cap. Rework *reasons* are unstructured  **do not condition on reason**; treat as an unobserved type. (Free-text clustering is a stated future refinement, not a current input.)
- **Dependencies:**
  - K2 from §2.2(6).
  - K3 (objection coupling): test the correlation of public-notice durations for cases with **overlapping notice windows in the same district** (Spearman with block bootstrap). Positive correlation  shared episode; estimate a coupling strength with a wide CI and label it latent.
  - K4 (batching gain): compare `Site inspection` occupancy+travel by district and by whether other inspections occurred the same day in that district (a batching proxy)  estimate travel saving `(district)` and the batch-wait penalty.
  - K5 is a design parameter, not an estimated one.
- **Flattened-log limitation:** no case-to-case relation exists in the log, so cross-case edges are **re-derived** from `(architect_id, district, overlapping time windows)`. This is explicitly stated as a reconstruction, not an observation.

### 2.6 Pre-calibration capacity audit (identifiability gate — do this first)

Before any calibration, check feasibility: `_a = _c _c · p_{c,a} · E[S_a] / capacity_hours_a`.

Illustrative (monthly cases  1,733; target   0.70–0.85):

| Activity | Available h/month | Demand if reported service times are true occupancy | Implied  | Verdict |
|---|---|---|---|---|
| Planning review | 8 × 8 h × 21 d  **1,344** | 1,733 × 6.3 h  10,900 | ** 8.1** | Infeasible |
| Fire-safety review | 2 × 3 d/wk × 8 h  **208** | ~433 × 4.1 h  1,775 | ** 8.5** | Infeasible |
| Environmental review | 3 × 60% × 8 h × 21 d  **302** | ~260 × 8.0 h  2,080 | ** 6.9** | Infeasible |

**Conclusion:** the "median service time" column cannot be resource-occupancy as supplied. Either (a) a large share of cases is auto/desk-approved at the relevant step, (b) the reported duration includes internal holds (consultant reports, applicant/site access) or hidden queueing, or (c) the calendar is understated (overtime/batching). Resolution order: re-split occupancy from instrumented activities  allow a desk-approved sub-path  only then adjust calendars. **If the audit cannot be closed, the model is not identifiable and no intervention ranking should be published.** This is a hard gate, reported in the deliverable.

### 2.7 Calendars

Reconstructed from HR, then **validated against the log**: compute the share of each activity's start/completion falling outside the reconstructed window per pool (e.g., fire reviews on Monday, legal checks during council weeks). A high "calendar violation rate" means either the calendar or the timestamps (data-entry time vs actual time) are wrong  reconcile before use. Holidays and council-meeting blackout weeks are an explicit date table for the historical period; for forward runs they recur with a small probability of a one-week extension.

### 2.8 Estimation stages and calibration

- **Stage 1 — directly estimable** (arrivals, instrumented service times, branching, calendars): point estimate + bootstrap CI.
- **Stage 2 — partially identified** (occupancy/hold split for uninstrumented activities, queue discipline, batching gain, objection coupling, latent covariates, D1/D7 elasticities): bounded ranges from the capacity audit, expert elicitation, and **history matching** — choose values minimising a weighted Mahalanobis distance between ~20 simulated and observed summary statistics (case-mix medians/p90s, variant shares, per-activity median/p90 sojourn, monthly throughput, rework rate, outcome rates, utilisation proxies), retaining all parameter sets inside a pre-declared acceptance region ( an ensemble, not a single "best" vector).
- **Stage 3 — parameter ensemble**: bootstrap draws (Stage 1) × accepted Stage-2 sets  `K  50–100` parameter vectors propagated into the experiments (§5).

## 3. Assumptions

### 3.1 Arrivals
- **A1** Arrivals are a piecewise-stationary non-homogeneous process: `(t) = base × seasonal(month) × weekday(dow) × trend(t)`, with architect campaigns added on top. *Basis:* explicit seasonality and Monday/Wednesday ratio in the summary. *Test:* NB deviance + held-out MAPE; alternative structural model (Hawkes self-exciting on architect submissions) in the sensitivity set.
- **A2** Jan–Feb is the seasonal reference; Jun–Aug/Dec indices are **estimated**, not assumed (summary gap).
- **A3** Case mix (45/28/17/10) is constant in the baseline but is allowed to drift in stress tests (S5), because mix and volume usually move together.
- **A4** Case attributes (`requires_*`, district, architect, value) are sampled jointly (not independently) — cross-tabulated from the log.

### 3.2 Service times
- **A5** Reported durations = touch + internal hold + (partly) hidden queue; resource occupancy is smaller and is recovered via the capacity audit. *Test:*  feasibility + sojourn match.
- **A6** Lognormal for desk reviews and clerical work; district-shifted lognormal for inspections (travel); deterministic statutory component for public notice; empirical/GPD for applicant response. *Test:* Q–Q, AD test, tail index; family swapped in sensitivity.
- **A7** Service is independent of queue length (no speed-up/slow-down under load). *Test:* compare observed service vs queue length; if a relationship exists, add a load-dependent multiplier.
- **A8** No learning or fatigue curve in the baseline; D4's temporary inspector has a 4-week ramp from 70% to 100% productivity.

### 3.3 Routing
- **A9** Fire/env/notice decisions follow the documented rules **plus** missing covariates with bounded imputation (best/worst case), never point-imputed as if observed.
- **A10** `Decision drafting` waits for all *applicable* results (AND-join over a case-specific pending set).
- **A11** Review order is a partial order; concurrency is allowed but joins are enforced. The simplified process tree cannot express this (see §8) and is used for *conformance diagnostics*, not as the execution semantics.
- **A12** Rejection concentrates after planning/legal conflict; `P(reject)` estimated hierarchically.

### 3.4 Resources / calendars
- **A13** Calendars as supplied, with holidays and council blackout weeks as explicit dates; blackout extension in stress tests.
- **A14** Individual resources within a pool (needed for Tue–Thu fire, 2 Simple-only planners); no cross-pool substitution (fire  planner) except a declared, low-probability emergency lane.
- **A15** Non-preemptive scheduling; a case in service keeps its resource to completion (plus calendar interruptions handled by freezing the resource at the window boundary, not by aborting).
- **A16** Environmental pool = 3 FTE × 60% permit duty = **1.8 permit FTE**, modelled as a reduced-capacity calendar rather than as extra waiting.

### 3.5 Rework
- **A17** Rework is a generic loop with case-type-dependent probability and iteration count; **reasons are unobserved** and never synthesised into the output log as if coded.
- **A18** Loop cap = observed max + 1; beyond the cap the case is routed to appeal/abandonment. Sensitivity on the cap because the tail is cap-sensitive.
- **A19** Rework re-uses the same service distribution (no "faster second pass"), unless the log supports a ratio — test both.

### 3.6 Applicant / third-party response
- **A20** Exogenous, heavy-tailed, in **calendar days**; modelled separately from municipal service time (explicit requirement).
- **A21** D1 and D7 change applicant behaviour: elasticity of submission volume to friction  {0.3, 0, +0.1} — **not assumed to be zero**, because a pre-submission checker and appointment slots both add effort.
- **A22** D1 has imperfect accuracy: sensitivity/specificity  {0.80/0.95, 0.90/0.90, 0.95/0.85}. False "complete" verdicts create a **new** rework path that does not exist in the baseline — this must be modelled, otherwise D1 is flattered.
- **A23** Applicant response may be business-day-bounded or calendar-bounded; both variants are run (the log does not settle it).

### 3.7 Cross-case dependencies
- **A24** Architect campaigns are the dominant non-resource coupling; K2–K5 all implemented as shared singleton state (§1.5).
- **A25** Objection episodes are **latent**: correlated duration extension by district × overlapping window; no objection events are ever written to the simulated log as observed facts.
- **A26** Batching reduces travel by `(district)` (largest in D3/D5) and adds a batch-fill wait; `W  {3, 5}` business days, batch size  `B  {3, 5}`.
- **A27** Case-level dependence means IID-per-case inference is invalid (see §5).

### 3.8 Non-stationary demand
- **A28** Seasonality recurs annually; interventions are evaluated over a full seasonal cycle so a policy is not credited for luck about *when* it starts.
- **A29** Demand and routing can change **within** a run (policy announcement, mix shift) via `policy_breakpoints`.
- **A30** Interventions that change applicant friction also change arrivals (A21) — interventions are never evaluated with arrivals frozen unless explicitly labelled "ceteris paribus".

### 3.9 Missing data
- **A31** Missing starts  interval-censored sojourn, split resolved by the capacity audit + partial pooling; **no single imputed value is treated as truth** — imputations are drawn inside the parameter ensemble.
- **A32** Objections  latent mixture, with CI; **never** fabricated as events.
- **A33** Unstructured rework reasons  coarsened to "rework occurred / loop index".
- **A34** Removed emergency cases  declared out of scope (or a bounded exogenous flow); their absence biases tail estimates downward, which is stated when interpreting p90/p95.
- **A35** HR-derived calendars  validated against log activity hours; discrepancies reported.
- **A36** Flattened log  cross-case links reconstructed from attributes/time windows; dependency strength is an estimate with a wide CI.

## 5. Warm-up, replications, and uncertainty treatment

### 5.1 Warm-up
Because demand is **periodic**, a naive "run until queues look flat" is wrong — a flat 8-week window can hide a seasonal phase. Procedure:

1. **Seasonal-periodic initialisation:** run the *same calendar year* repeatedly until the state at 1 January converges (max | queue length| < 5% between successive years, and slope of the last 8 weekly WIP means has a CI containing 0). Use the converged 1 January state as the initial state (backfilled backlog, cases already in flight with their remaining service).
2. Alternatively (primary): **12-month burn-in discarded**, then an **18-month measurement window** aligned to the log's calendar phase. Total run = 30 months.
3. Warm-up adequacy diagnostics: weekly WIP, queue length per activity, oldest open case age, and monthly throughput — all four must satisfy the stability criterion above.
4. Any intervention that changes volume (D1, D7) is warmed up **with the intervention on**, so the burn-in reflects the new regime.

### 5.2 Run length and replications
- **Run length:** 18-month measurement window (to match the log), plus a secondary full-seasonal-year report so interventions are not credited for timing luck.
- **Replications:** pilot of 10 to estimate variance  `n = (1.96 · s / )²` for the desired half-width ``; then **50** for Phase 1–2 (min 30), **100** for tail metrics (p95) and the top-2 candidates, **200** for the final recommendation if the CI still straddles the decision threshold.
- **Replication = whole system run.** Cases inside a run are dependent (K1–K6)  **no case-level IID CIs**; report cluster bootstrap by replication and an effective sample size.

### 5.3 Seeds and common random numbers
- Master seed  `np.random.SeedSequence(master, spawn_key=(crc32(experiment), rep, crc32(stream)))`.
- **Separate streams:** `arrival`, `attributes`, `routing`, `service`, `applicant`, `objection`, `batch`, `calendar`, `intervention`.
- CRN: the *same* stream keys are reused across baseline and intervention so differences are paired.
- **Counter-based/keyed draws to keep CRN valid when an intervention removes draws:** service times are drawn from `rng(master, case_id, activity, draw_index)` — identical for the same case-activity in *any* experiment. If D2 removes an inspection, other cases' draws are unaffected (naïve stream consumption would desynchronise the whole stream and destroy the pairing).

### 5.4 Confidence / credible intervals
- Primary: 95% **t-interval across replications** for replication-level metrics (mean, median, p90, SLA rate, utilisation, rework rate, backlog).
- For **differences vs baseline**: paired interval on the CRN differences (much tighter than unpaired).
- For **quantiles**: compute the quantile per replication, then a t-interval across replications; cross-check with a cluster bootstrap (resample replications, then cases within a replication).
- Bayesian variant: Bayesian bootstrap or a hierarchical model `metric ~ intervention + (1|replication) + (1|parameter-draw)`  posterior of each difference, `P(intervention better)`, and a ROPE (region of practical equivalence, e.g. ±2% cycle time).
- **Multiplicity:** 10+ interventions × many metrics  apply Benjamini–Hochberg FDR on the superiority tests, and use non-inferiority gates (§7) first; report simultaneous CIs for the headline metrics.

### 5.5 Two distinct uncertainty sources
| Source | Treatment |
|---|---|
| **Aleatory** (process randomness) | Variance across replications within one parameter draw |
| **Epistemic** (parameter uncertainty) | Outer loop over `K` parameter draws; variance across draws |
| **Total** | Nested variance decomposition (ANOVA): report `% aleatory / % epistemic` for each headline metric; the decision interval uses the **total** |

### 5.6 Sensitivity analysis
1. **Morris screening** (r = 20 trajectories) over ~25 uncertain parameters  identify the top 5–8.
2. **Sobol' or one-at-a-time tornado** on the top parameters (occupancy/hold split, objection coupling, elasticities, batching gain, fire calendar, legal blackout length, tail truncation).
3. **Structural sensitivity:** arrivals (NHPP vs NB-day-count vs Hawkes), service family (lognormal vs empirical bootstrap vs Weibull), queue discipline (FIFO vs SRPT-like), objection model (mixture vs censored lognormal).
4. Report rank stability of interventions across all structural variants.

### 5.7 Heavy-tailed durations
- Report **median and quantiles as primary**; means only with a warning (the mean of a near-Pareto tail is unstable).
- Fit the tail explicitly (mean-excess / Hill); if ` < 3`, use GPD for p99 and state the extrapolation.
- **Truncation:** simulate with truncation at p99.9 *and* at the statutory/practical maximum; report both. Never silently truncate — truncation systematically flatters the very metrics (p90/p95) that decide.
- Increase replications rather than trimming data; provide winsorised means as a secondary metric only.

## 6. Validation strategy

All acceptance thresholds below are **pre-declared before running any intervention** (otherwise validation becomes adjustable after seeing results).

| # | Validation layer | Method | Acceptance threshold |
|---|---|---|---|
| V1 | **Face validation** | Walk-through with 1 clerk, 2 planners, 1 inspector, 1 legal officer: inspect simulated queue behaviour in peak weeks, Monday backlog, council-week legal queues, D3/D5 travel. | Domain experts must rate simulated behaviour as "recognisable" and must not identify a *structural* error (wrong order, impossible calendar). Documented objection log. |
| V2 | **Event-log replay (backward validation)** | Replay the **historical arrivals and case attributes** (same arrival timestamps, same attributes, same calendars) through the twin; compare generated traces to the real log. | median cycle time per case type ±10%; p90 ±15%; variant-share total-variation distance  0.05; monthly throughput ±5%; per-activity median sojourn ±20% or ±1 d; rework rate ±3 pp; outcome (issue/reject) ±3 pp |
| V3 | **Distributional validation** | Q–Q plots + KS/AD for service, sojourn, waiting, per-variant duration, monthly throughput; compare p50/p75/p90/p95. | KS p > 0.05 on per-activity sojourn after multiplicity correction, *or* quantile deviations within V2 tolerances |
| V4 | **Resource-utilisation validation** | Compare simulated busy/capacity per pool against: HR leave data, overtime records, the 40% env non-permit duty, fire Tue–Thu, and the §2.6 capacity audit. Cross-check with Little's law (`L = W`) on inferred queue lengths. |   [0.65, 0.85] where plausible;  > 1.0 anywhere  reject the parameter set (never accept an infeasible model) |
| V5 | **Bottleneck validation** | Identify the simulated binding constraint each month; compare to known bottlenecks (planning queue in peaks, legal around council weeks, inspection wait  8 d, env  8 d). | Same *rank order* of activities by waiting time as observed; the simulated top-2 bottlenecks must appear in the observed top-3 |
| V6 | **Routing/conformance validation** | Feed the simulated log back through PM4Py: `discover_dfg`, `discover_variants`, token replay / alignments against both the discovered model and the given tree. Compare simulated vs real fitness. | Simulated-vs-real token-replay fitness differs by  0.03; branching proportions within ±2 pp |
| V7 | **Out-of-sample (temporal)** | Calibrate on months 1–12, validate on months 13–18; plus rolling-origin (calibrate H1, validate H2) and a hold-out district (D5) and hold-out case type (Complex variance). | V2 tolerances met on the held-out period/district/type |
| V8 | **Dependency validation** | Compare simulated vs observed duration correlation between same-architect/same-district overlapping cases and between overlapping notice windows. | Sign and rough magnitude match; if observed correlation  0, set the coupling strength to ~0 rather than imposing dependence |
| V9 | **Calendar validation** | Share of simulated activity times outside reconstructed windows vs share in the real log. | Violation rate within 1 pp of the observed rate |

**Gates:** interventions are run only after V1–V7 pass. If a proposed intervention pushes the system outside the calibrated envelope (e.g., S4's 2.2× demand), results are labelled **extrapolation** and carry an additional warning band. Validation is repeated after any recalibration.

## 7. Decision criteria

> SLA values are **provisional and must be signed off before Phase 1** (no moving goalposts after results are seen).

### 7.1 Metrics and thresholds

| # | Metric | Definition | Threshold / target | Role |
|---|---|---|---|---|
| M1 | Median cycle time, per case type | case-mix-specific median (arrival  terminal) | non-inferior: upper 95% CI of difference vs B0  **+2%**; superiority:  **10%** | Gate + primary |
| M2 | p90 / p95 cycle time | per case type and overall | non-inferior  **+5%**; superiority  **15%** | Primary (tail is the citizen-visible pain) |
| M3 | SLA compliance by case type | `% cases  SLA_t` (provisional: Simple 21 d, New residential 60 d, Commercial 100 d, Complex 200 d) | non-inferior  **3 pp**; superiority  **+5 pp** | Primary |
| M4 | Rework | % cases with  1 loop; rework-induced delay days | D1-type interventions:  **20%** relative; others:  +2 pp | Primary |
| M5 | Resource utilisation | busy/capacity per pool | must stay in **[0.65, 0.85]**; never > **0.90** (fire: never > 0.85 given Tue–Thu) | Gate |
| M6 | Backlog / WIP | WIP at end of peak month; oldest open case age |  B0 (peak WIP); oldest case  B0 | Primary |
| M7 | Throughput | decisions/month |  B0 in every month | Gate |
| M8 | **Fairness across districts** | case-mix-**standardised** p90 per district (`_t w_t·p90_{d,t}`, `w_t` = overall type share) | max/min  **1.15**; change vs B0 within **±10% for every district** (no district may be left worse) | Gate |
| M9 | **Fairness across architects** | standardised p90 for top-20 vs rest; share of cases breaching SLA by architect size quartile | difference  **5 pp**; no quartile worse by > 3 pp vs B0 | Gate |
| M10 | Outcome equity | reject rate by district/architect (standardised) | change within **±3 pp**; investigate any district with > 5 pp shift | Gate (D2/D8 especially) |
| M11 | Cost | build cost + staffing/temp cost + applicant effort (€/h, assumption stated) | incremental € per calendar-day saved  stakeholder WTP; report the **cost–benefit frontier** | Preference |
| M12 | **Robustness** | % of parameter draws where the option is best or within ROPE of best; worst-case regret across S1–S5 |  **80%** of draws; regret  **10%** of the best option in every stress scenario; no worst-place finish | Gate |
| M13 | Rank stability | Kendall's  of the ranking across structural sensitivity variants |  0.7 | Preference |
| M14 | Identification status | is the intervention's key parameter identifiable from available data? | D9 (and parts of D2/D8): **no**  range + data-collection requirement, no point recommendation | Gate |

### 7.2 Decision rule (applied in order)
1. **Validation gate** — baseline must have passed §6.
2. **Non-inferiority gate** — for M1, M2, M3, M5, M7, M8, M9, M10, the 95% CI must exclude degradation beyond the margins above. Fail  rejected regardless of gains elsewhere.
3. **Superiority test** — at least one primary metric (M2, M3, M4 or M6) improves with a 95% CI excluding 0 (FDR-controlled) **and** exceeds the practical threshold (15% p90 or 5 pp SLA).
4. **Robustness gate** — M12/M13.
5. **Cost-effectiveness** — among survivors, present the Pareto frontier over (cycle time, tail, cost, fairness, robustness); elicit weights from stakeholders and report weight-sensitivity (an option that wins only under one narrow weight vector is reported as such).
6. **Identification gate** — D9 and any option whose effect depends on unobserved data are recommended only as a *monitored pilot with a defined data-collection plan*, with the twin reporting a decision-relevant **range**, not a point estimate.

### 7.3 What will *not* be claimed
- No claim of **optimal** intervention: we report "preferred among the tested set, under the calibrated model and the tested scenario envelope, with intervals".
- No ranking published before calibration/validation gates are met (§2.6, §6).
- Enforcement/defect consequences of D2 and misrouting consequences of D8 are **outside the model**; adoption requires a monitored pilot with post-permit violation tracking.
- All recommendations carry a **re-calibration trigger**: monitor live KPIs for 3 months; if observed p90/SLA falls outside the model's 95% prediction band for two consecutive months, update the parameter posterior and re-run the shortlist.

def load_log_dataframe(csv_text: str = PERMIT_LOG_CSV) -> pd.DataFrame:
    """PM4Py has no `pm4py.read_csv` -> build the frame with pandas, then format."""
    df = pd.read_csv(io.StringIO(csv_text))
    df[TIMESTAMP] = pd.to_datetime(df[TIMESTAMP], errors="coerce")
    for c in [CASE_ID, ACTIVITY, "org:resource", "case_type", "district", "architect_id"]:
        df[c] = df[c].astype(str)
    df["application_value"] = pd.to_numeric(df["application_value"], errors="coerce")
    for c in ["requires_fire", "requires_environment", "requires_public_notice"]:
        df[c] = df[c].map({"yes": True, "no": False})
    return df.sort_values([CASE_ID, TIMESTAMP], kind="mergesort").reset_index(drop=True)


def to_event_log(df: pd.DataFrame):
    """Format with PM4Py conventions; return an EventLog (type varies by version)."""
    formatted = pm4py.format_dataframe(
        df.copy(), case_id=CASE_ID, activity_key=ACTIVITY, timestamp_key=TIMESTAMP
    )
    if isinstance(formatted, pd.DataFrame):          # older/newer versions differ
        return pm4py.convert_to_event_log(formatted)
    return formatted


def compute_variants(log_or_df) -> pd.DataFrame:
    """Variant share table (PM4Py first, manual groupby as fallback)."""
    try:
        v = pm4py.discover_variants(log_or_df)
    except Exception:
        df = (log_or_df if isinstance(log_or_df, pd.DataFrame)
              else pm4py.convert_to_dataframe(log_or_df))
        seq = (df.sort_values([CASE_ID, TIMESTAMP])
                 .groupby(CASE_ID)[ACTIVITY].agg(">".join))
        v = seq.value_counts().to_dict()
    rows = [{"variant": ">".join(k) if isinstance(k, (tuple, list)) else str(k),
             "count": int(c)} for k, c in v.items()]
    out = pd.DataFrame(rows)
    out["share"] = out["count"] / out["count"].sum()
    return out.sort_values("count", ascending=False).reset_index(drop=True)


def compute_dfg(log) -> Tuple[dict, set, set]:
    """Frequency DFG: PM4Py returns (dfg, start_activities, end_activities)."""
    res = pm4py.discover_dfg(log)
    if isinstance(res, tuple) and len(res) == 3:
        return res
    return res, set(), set()


def _edge_frame(df: pd.DataFrame) -> pd.DataFrame:
    """Consecutive-event edges; 'd' is the EDGE sojourn of the successor activity
    (= its waiting + its service/hold when start timestamps are absent)."""
    df = df.sort_values([CASE_ID, TIMESTAMP], kind="mergesort")
    g = df.groupby(CASE_ID, sort=False)
    succ = g.shift(-1)
    e = pd.DataFrame({
        "a": df[ACTIVITY].to_numpy(),
        "b": succ[ACTIVITY].to_numpy(),
        "d_min": (succ[TIMESTAMP] - df[TIMESTAMP]).dt.total_seconds().to_numpy() / 60.0,
    }).dropna(subset=["b"])
    return e


def compute_performance_dfg(log, df: Optional[pd.DataFrame] = None) -> dict:
    """Median edge duration; PM4Py variant first, deterministic manual fallback."""
    try:
        return pm4py.algo.discovery.dfg.algorithm.apply(
            log, variant=pm4py.algo.discovery.dfg.Algorithm.DFG_PERFORMANCE
        )
    except Exception:
        if df is None:
            raise
        e = _edge_frame(df)
        return e.groupby(["a", "b"])["d_min"].median().to_dict()


def compute_frequency_dfg_from_df(df: pd.DataFrame) -> dict:
    e = _edge_frame(df)
    return e.groupby(["a", "b"]).size().to_dict()


def add_service_waiting_columns(df: pd.DataFrame,
                                start_col: str = "start:timestamp") -> pd.DataFrame:
    """Waiting / service split. With only completion timestamps the split is NOT
    identifiable: we return sojourn and flag the rows as censored instead of
    inventing a service time."""
    df = df.sort_values([CASE_ID, TIMESTAMP], kind="mergesort").copy()
    prev = df.groupby(CASE_ID, sort=False)[TIMESTAMP].shift(1)
    df["prev_completion"] = prev
    df["sojourn_days"] = (df[TIMESTAMP] - prev).dt.total_seconds() / 86400.0
    if start_col in df.columns:
        st = pd.to_datetime(df[start_col])
        df["service_days"] = (df[TIMESTAMP] - st).dt.total_seconds() / 86400.0
        df["waiting_days"] = (st - prev).dt.total_seconds() / 86400.0
        df["split_censored"] = False
    else:
        df["service_days"] = np.nan
        df["waiting_days"] = np.nan
        df["split_censored"] = True     # documented data gap, not a zero
    return df


def compute_arrival_stats(df: pd.DataFrame) -> Dict[str, object]:
    first = df.groupby(CASE_ID)[TIMESTAMP].min().sort_values()
    gaps = first.diff().dt.total_seconds().dropna() / 86400.0
    span = max((first.max() - first.min()).days, 1)
    by_month = first.groupby(first.dt.to_period("M")).size()
    by_dow = first.groupby(first.dt.dayofweek).size()
    dim = pd.Series({p: p.days_in_month for p in by_month.index}, dtype=float)
    seasonal = (by_month / dim)
    seasonal = seasonal / seasonal.mean()          # month-length corrected index
    return {
        "n_cases": int(first.size),
        "span_days": span,
        "mean_interarrival_days": float(gaps.mean()) if len(gaps) else np.nan,
        "rate_per_day": float(first.size / span),
        "seasonal_index_by_month": seasonal.round(3).to_dict(),
        "cases_by_dow": by_dow.to_dict(),
        "monday_vs_wednesday": float(by_dow.get(0, 0) / max(by_dow.get(2, 1), 1)),
        "architect_top20_share": float(
            df.groupby(CASE_ID)["architect_id"].first()
              .isin(_top20(df)).mean()),
    }


def _top20(df: pd.DataFrame, n: int = 20) -> set:
    per_case = df.groupby(CASE_ID)["architect_id"].first()
    return set(per_case.value_counts().head(n).index)


# --- process tree ------------------------------------------------------------ #

# As supplied by the process-mining team. LIMITATIONS (documented, not hidden):
#  * 'X(a,b)' and '+(...)' are not PM4Py's operator set (PM4Py: '->' sequence,
#    '+' exclusive choice, '*' loop, '&' parallel, 'tau' silent). If parse fails
#    we fall back to TREE_PM4PY below.
#  * If '+' is read as exclusive choice, the review block allows *skipping*
#    Planning review and X('Issue permit','Reject application') is not a choice.
#  * The tree cannot express: the AND-join before 'Decision drafting', statutory
#    minimum/extended public-notice durations, rework *reasons*, appeals, or any
#    cross-case dependency. Timing/queueing are out of scope for a process tree.
#  * The log shows the completeness loop via 'Receive missing documents' -> second
#    'Completeness check' WITHOUT a 'Completeness rework' event: the loop-back
#    label in the tree does not appear in the log -> expect non-perfect fitness.
TREE_AS_GIVEN = (
    "->( 'Submit application',"
    " *( ->( 'Completeness check',"
    "        X( tau, ->('Request missing documents','Receive missing documents') ) ),"
    "    'Completeness rework' ),"
    " +( 'Planning review', X(tau,'Fire-safety review'), X(tau,'Environmental review') ),"
    " X(tau,'Public-notice period'),"
    " *( ->('Inspection scheduling','Site inspection'), 'Inspection rework' ),"
    " 'Decision drafting',"
    " X(tau,'Legal check'),"
    " X('Issue permit','Reject application') )"
)

# Normalised to PM4Py's operator set: X(a,b) -> +(a,b); the review block becomes
# '&' so Planning always runs and fire/env are independent options; the terminal
# choice becomes a proper exclusive choice.
TREE_PM4PY = (
    "->( 'Submit application',"
    " *( ->( 'Completeness check',"
    "        +( tau, ->('Request missing documents','Receive missing documents') ) ),"
    "    'Completeness rework' ),"
    " &( 'Planning review', +(tau,'Fire-safety review'), +(tau,'Environmental review') ),"
    " +( tau, 'Public-notice period' ),"
    " *( ->('Inspection scheduling','Site inspection'), 'Inspection rework' ),"
    " 'Decision drafting',"
    " +( tau, 'Legal check' ),"
    " +('Issue permit','Reject application') )"
)


def parse_process_tree_safe(tree_str: str = TREE_AS_GIVEN,
                            fallback_str: str = TREE_PM4PY):
    for s in (tree_str, fallback_str):
        try:
            tree = pm4py.parse_process_tree(s)
        except Exception as exc:
            warnings.warn(f"pm4py.parse_process_tree rejected this string: {exc}")
            continue
        ops = {n.operator for n in tree.subtree if n.operator is not None}
        if not {"->", "+", "*"}.issubset(ops):
            warnings.warn(f"unexpected operator set {ops}: control-flow semantics "
                          "may differ from the intent; verify with the DFG below.")
        return tree
    raise RuntimeError("no parseable process tree")


def discover_and_evaluate_model(log) -> Dict[str, object]:
    """Reference model + conformance diagnostics (Layer A only)."""
    net, im, fm = pm4py.discover_petri_net_inductive(log)
    out: Dict[str, object] = {"inductive_net": (net, im, fm)}

    tree = parse_process_tree_safe()
    out["process_tree"] = tree
    try:                                   # version-dependent converter
        g_net, g_im, g_fm = pm4py.convert_to_petri_net(tree)
    except Exception:
        g_net = g_im = g_fm = None

    try:                                   # token-based replay fitness
        tr = pm4py.algo.conformance.tokenreplay.algorithm.apply(log, net)
        out["fit_rate_inductive"] = float(np.mean([bool(t.get("trace_is_fit", False))
                                                   for t in tr]))
        if g_net is not None:
            trg = pm4py.algo.conformance.tokenreplay.algorithm.apply(log, g_net)
            out["fit_rate_given_tree"] = float(np.mean([bool(t.get("trace_is_fit", False))
                                                        for t in trg]))
    except Exception as exc:               # never fatal for the twin
        warnings.warn(f"token replay unavailable: {exc}")

    try:
        al = pm4py.algo.conformance.alignments.petri_net.algorithm.apply(log, net, im, fm)
        out["mean_alignment_fitness"] = float(np.mean(
            [a.get("fitness", np.nan) for a in al]))
    except Exception as exc:
        warnings.warn(f"alignments unavailable: {exc}")
    return out


def log_summary(df: pd.DataFrame) -> Dict[str, object]:
    log = to_event_log(df)
    dfg, starts, ends = compute_dfg(log)
    return {
        "variants": compute_variants(log),
        "dfg": dfg, "start_activities": starts, "end_activities": ends,
        "performance_dfg": compute_performance_dfg(log, df),
        "frequency_dfg": compute_frequency_dfg_from_df(df),
        "arrivals": compute_arrival_stats(df),
        "service_waiting": add_service_waiting_columns(df),
        "case_attributes": {k: pm4py.get_event_attribute_values(log, k)
                            for k in ("case_type", "district")},
    }

class ParameterEstimator:
    """Log -> ModelParameters. Stage 1 = point estimate; Stage 2 = bounded ranges
    resolved by the capacity audit + history matching (never a silent point fix)."""

    def __init__(self, df: pd.DataFrame):
        self.df = add_service_waiting_columns(df)
        self.log = to_event_log(df)

    def estimate(self) -> ModelParameters:
        return ModelParameters(
            arrivals=self._arrivals(),
            service=self._service(),          # occupancy vs internal-hold split
            routing=self._routing(),
            rework=self._rework(),
            dependencies=self._dependencies(),
            resources=self._resources(),
            applicant_response={"Receive missing documents": (1.6, 0.7)},  # lognormal days
        )

    def _arrivals(self) -> ArrivalParams:
        s = compute_arrival_stats(self.df)
        p = ArrivalParams(base_rate_per_day=s["rate_per_day"])
        # TODO: NB-GLM on daily counts -> seasonal_index / weekday_index + CI
        #       (the weekday vector above is a placeholder: only Mon/Wed = 2.2 is known)
        p.seasonal_index = {int(k[5:7]): v for k, v in s["seasonal_index_by_month"].items()}
        return p

    def _service(self) -> ServiceParams:
        """Reconstruct lognormal occupancy from median/p90 where starts are absent,
        then re-solve occupancy so that the capacity audit (rho in [0.65,0.85]) holds."""
        spec = {  # (median_min, p90_min) from the empirical summary
            "Completeness check": (25, 90), "Request missing documents": (10, 25),
            "Planning review": (210, 840), "Fire-safety review": (150, 540),
            "Environmental review": (240, 1080), "Inspection scheduling": (20, 60),
            "Site inspection": (60, 180), "Decision drafting": (120, 480),
            "Legal check": (180, 960), "Issue permit": (5, 20),
            "Reject application": (30, 120),
        }
        occ, hold = {}, {}
        for a, (md, p90) in spec.items():
            mu, sigma = math.log(md), math.log(p90 / md) / 1.28155
            occ[a] = (mu, sigma)
        # TODO: replace occ[a] by start-completion fits where starts exist, then
        #       move the residual (reported - occupancy) into internal_hold[a].
        return ServiceParams(occupancy=occ, internal_hold=hold,
                             travel_extra_by_district={"D3": 45.0, "D5": 55.0})

    def _routing(self) -> RoutingParams:
        # cross-tabs / logistic models on the log; missing covariates -> bounds
        return RoutingParams(
            p_fire={"Simple renovation": 0.05, "New residential": 0.55,
                    "Commercial": 0.70, "Complex variance": 0.60},
            p_environment={"Simple renovation": 0.02, "New residential": 0.15,
                           "Commercial": 0.55, "Complex variance": 0.45},
            p_public_notice={"Simple renovation": 0.02, "New residential": 0.45,
                             "Commercial": 0.35, "Complex variance": 1.0},
            p_reject={"Simple renovation": 0.04, "New residential": 0.08,
                      "Commercial": 0.12, "Complex variance": 0.18},
            p_request_missing_docs={"Simple renovation": 0.25, "New residential": 0.40,
                                    "Commercial": 0.45, "Complex variance": 0.50})

    def _rework(self) -> ReworkParams:
        return ReworkParams()      # TODO: loop back-edge counts from alignments

    def _dependencies(self) -> DependencyParams:
        return DependencyParams()  # TODO: duration-correlation test + batching proxy

    def _resources(self) -> List[ResourceSpec]:
        return [
            ResourceSpec("clerks", 5, [(d, 8.0, 16.0) for d in range(5)],
                         ["Completeness check", "Request missing documents"]),
            ResourceSpec("planners", 8, [(d, 9.0, 17.0) for d in range(5)],
                         ["Planning review", "Decision drafting"]),
            ResourceSpec("fire", 2, [(d, 8.0, 16.0) for d in (1, 2, 3)],  # Tue-Thu
                         ["Fire-safety review"]),
            ResourceSpec("environment", 3, [(d, 9.0, 17.0) for d in range(5)],
                         ["Environmental review"], busy_fraction=0.6),
            ResourceSpec("inspectors", 4, [(d, 8.0, 17.0) for d in (1, 2, 3, 4)],
                         ["Inspection scheduling", "Site inspection"]),
            ResourceSpec("legal", 2, [(d, 9.0, 17.0) for d in range(5)],
                         ["Legal check"]),
            ResourceSpec("system", 10 ** 6, [(d, 0.0, 24.0) for d in range(7)],
                         ["Submit application", "Receive missing documents",
                          "Public-notice period", "Issue permit",
                          "Reject application"]),
        ]

class Calendar:
    """Business clock for one pool. Public notice & applicant response use the
    separate *calendar-day* clock and therefore bypass this class."""

    def __init__(self, windows: Sequence[Tuple[int, float, float]],
                 holidays: Sequence[str] = (), blackout: Sequence[str] = ()):
        self.windows = list(windows)
        self.holidays = set(pd.to_datetime(list(holidays)).date())
        self.blackout = set(pd.to_datetime(list(blackout)).date())

    def _intervals(self, day) -> List[Tuple[pd.Timestamp, pd.Timestamp]]:
        d = pd.Timestamp(day)
        if day in self.holidays or day in self.blackout:
            return []
        out = [(d + pd.Timedelta(hours=s), d + pd.Timedelta(hours=e))
               for (dow, s, e) in self.windows if dow == d.dayofweek]
        return sorted(out)

    def is_open(self, ts: pd.Timestamp) -> bool:
        return any(a <= ts < b for a, b in self._intervals(ts.date()))

    def next_open(self, ts: pd.Timestamp) -> pd.Timestamp:
        day, ts = ts.normalize(), ts
        for _ in range(400):
            for a, b in self._intervals(day.date()):
                if ts <= a:
                    return a
                if a <= ts < b:
                    return ts
            day = day + pd.Timedelta(days=1)
            ts = day
        raise RuntimeError("calendar never opens")

    def add_minutes(self, ts: pd.Timestamp, minutes: float) -> pd.Timestamp:
        rem, ts, guard = float(minutes), self.next_open(ts), 0
        while rem > 1e-9:
            guard += 1
            if guard > 100_000:
                raise RuntimeError("calendar advance failed")
            iv = self._intervals(ts.date())
            cur = next(((a, b) for a, b in iv if a <= ts < b), None)
            if cur is None:
                ts = self.next_open(ts)
                continue
            a, b = cur
            avail = (b - ts).total_seconds() / 60.0
            if rem <= avail:
                return ts + pd.Timedelta(minutes=rem)
            rem -= avail
            ts = self.next_open(b + pd.Timedelta(seconds=1))
        return ts


class ResourcePool:
    """One *singleton* per role: this is what makes cases compete (K1)."""

    def __init__(self, spec: ResourceSpec, discipline: str = "FIFO"):
        self.spec, self.discipline = spec, discipline
        self.calendar = Calendar(spec.windows, spec.holidays, spec.blackout)
        self.capacity = spec.capacity
        self.free = spec.capacity
        self.queue: deque = deque()
        self.util_busy_min = 0.0
        self.util_cap_min = 0.0

    def admit(self, case, activity: str, priority: float = 0.0) -> None:
        if self.discipline == "AGING":          # D6: aging-first priority
            self.queue.append((priority, activity, case))
            self.queue = deque(sorted(self.queue, key=lambda x: -x[0]))
        else:
            self.queue.append((priority, activity, case))

    def try_dispatch(self, now) -> List[Tuple[str, str, object]]:
        out = []
        while self.free > 0 and self.queue:
            _, activity, case = self.queue.popleft()
            self.free -= 1
            out.append((activity, case, now))
        return out

    def release(self, minutes: float) -> None:
        self.free += 1
        self.util_busy_min += minutes

class ArrivalGenerator:
    """Piecewise NHPP by (month, weekday) + over-dispersed architect campaigns."""

    def __init__(self, p: ArrivalParams, iv: InterventionSpec, st: StressScenario):
        self.p, self.iv, self.st = p, iv, st

    def _lambda(self, day: pd.Timestamp) -> float:
        wd = day.dayofweek
        wk = (self.iv.weekday_target or self.p.weekday_index).get(wd, 1.0)
        return (self.p.base_rate_per_day
                * self.p.seasonal_index.get(day.month, 1.0)
                * self.st.arrival_mult * self.st.peak_mult
                * wk
                * (self.p.trend_per_year ** ((day.year - 2026) ))
                * (1.0 + self.iv.submission_elasticity * self._friction()))

    def _friction(self) -> float:
        return float(self.iv.d1) * 0.5 + float(self.iv.d7) * 0.5

    def generate(self, t0, t1, rng) -> List[Tuple[pd.Timestamp, object]]:
        from sklearn...  # NOT needed: attributes sampled from the cross-tab
        rows, day = [], t0.normalize()
        while day <= t1:
            n = int(rng.poisson(self._lambda(day)))
            if n:
                ts = day + pd.to_timedelta(rng.random(n) * 24 * 60, unit="m")
                rows += [(pd.Timestamp(x), None) for x in sorted(ts)]
            day += pd.Timedelta(days=1)
        rows += self._campaigns(t0, t1, rng)     # K2: top-20 architect bursts
        return sorted(rows, key=lambda r: r[0])

    def _campaigns(self, t0, t1, rng) -> list:
        """TODO: hurdle-NB campaign size k, campaign start day, architect mark
        sampled from the top-20 cross-tab; volume scaled by campaign_share."""
        return []


class ServiceSampler:
    def __init__(self, p: ServiceParams):
        self.p = p

    def occupancy_minutes(self, activity: str, attrs, district: str, rng) -> float:
        mu, sg = self.p.occupancy[activity]
        extra = self.p.travel_extra_by_district.get(district, 0.0) \
            if activity == "Site inspection" else 0.0
        return float(rng.lognormal(mu, sg)) + extra

    def hold_minutes(self, activity: str, rng) -> float:      # consumes no capacity
        if activity not in self.p.internal_hold:
            return 0.0
        mu, sg = self.p.internal_hold[activity]
        return float(rng.lognormal(mu, sg))


class Router:
    def __init__(self, rp: RoutingParams, rw: ReworkParams, iv: InterventionSpec):
        self.rp, self.rw, self.iv = rp, rw, iv

    def required_reviews(self, attrs, rng) -> set:
        out = set()
        if rng.random() < self.rp.p_fire.get(attrs.case_type, 0.0):
            out.add("Fire-safety review")
        env = rng.random() < self.rp.p_environment.get(attrs.case_type, 0.0)
        if self.iv.d8:                                   # triage: false negatives!
            env = env and (not self.iv.triage_strict or
                           attrs.district in {"D5"} or attrs.application_value > 250_000)
        if env:
            out.add("Environmental review")
        if rng.random() < self.rp.p_public_notice.get(attrs.case_type, 0.0):
            out.add("Public-notice period")
        return out

    def eligible_d2(self, attrs) -> bool:
        return (self.iv.d2 and attrs.case_type == "Simple renovation"
                and attrs.application_value < 50_000 and not attrs.prior_violations)

    def next_after(self, activity: str, case, ctx, now, rng):
        """XOR resolution + rework probabilities. Returns next activity or None.
        TODO: AND-join check before 'Decision drafting' over case.pending_reviews;
              latent objection extension before 'Public-notice period' completes;
              D5 legal pre-check (parallel, with wasted-work probability)."""
        return None

class PermitSimulator:
    """One full-system replication. All pools/calendars/context are singletons."""

    def __init__(self, params: ModelParameters, intervention: InterventionSpec,
                 stress: StressScenario, master_seed: int, rep: int, draw: int):
        self.p, self.iv, self.st = params, intervention, stress
        self.pools = {s.name: ResourcePool(s) for s in params.resources}
        self.pools_by_activity = {a: self.pools[s.name]
                                  for s in params.resources for a in s.activities}
        self.ctx = SharedContext(params, intervention)
        self.router = Router(params.routing, params.rework, intervention)
        self.service = ServiceSampler(params.service)
        self.arrivals = ArrivalGenerator(params.arrivals, intervention, stress)
        self.seed, self.rep, self.draw = master_seed, rep, draw
        self._seq, self.events, self.traces = 0, [], []

    # counter-based RNG: identical (case, activity, index) => identical draw in ANY
    # experiment, so CRN survives interventions that add/remove draws.
    def _rng(self, *key) -> np.random.Generator:
        spawn = tuple(zlib.crc32(str(k).encode()) for k in key) + (self.draw,)
        return np.random.default_rng(np.random.SeedSequence(self.seed, spawn_key=spawn))

    def _now_seq(self):
        self._seq += 1
        return self._seq

    def _priority(self, case, now) -> float:
        if self.iv.d6 and not np.isnan(self.iv.aging_threshold_days):
            age = (now - case.arrival).days
            return float(age >= self.iv.aging_threshold_days)   # aging gate
        return 0.0

    def _try_schedule(self, case, activity, now, events):
        pool = self.pools_by_activity.get(activity)
        if pool is None:
            heapq.heappush(events, (now, self._now_seq(), "complete",
                                    (case, activity, now, now)))
            return
        pool.admit(case, activity, priority=self._priority(case, now))
        for a, c, t in pool.try_dispatch(now):
            start = pool.calendar.next_open(t)
            dur = self.service.occupancy_minutes(
                a, c.attrs, c.attrs.district, self._rng(c.case_id, a, 0))
            fin = pool.calendar.add_minutes(start, dur)
            heapq.heappush(events, (fin, self._now_seq(), "complete",
                                    (c, a, start, fin)))

    def _on_arrive(self, now, case, events):
        self.ctx.register_architect(case)
        case.pending_reviews = self.router.required_reviews(
            case.attrs, self._rng(case.case_id, "routing"))
        self._try_schedule(case, "Submit application", now, events)

    def _on_complete(self, now, case, activity, start, events):
        pool = self.pools_by_activity.get(activity)
        if pool is not None:
            pool.release((now - start).total_seconds() / 60.0)
        case.trace.append({CASE_ID: case.case_id, ACTIVITY: activity,
                           TIMESTAMP: now, "org:resource": getattr(
                               pool.spec, "name", "system") if pool else "system",
                           **case.attrs.__dict__})
        # TODO hooks: latent objection extension (K3); batch formation (K4/D3);
        #             AND-join before 'Decision drafting'; appeal rework loop.
        nxt = self.router.next_after(activity, case, self.ctx, now,
                                     self._rng(case.case_id, activity, 1))
        if nxt is None:
            case.finished_at = now
        else:
            self._try_schedule(case, nxt, now, events)

    def run(self, t0: pd.Timestamp, t1: pd.Timestamp) -> pd.DataFrame:
        import heapq
        events: list = []
        for i, (t, attrs) in enumerate(self.arrivals.generate(t0, t1,
                self._rng("arrival"))):
            if attrs is None:
                attrs = self._sample_attrs(self._rng("attributes", i))
            case = Case(f"C{i:06d}", attrs, t)
            heapq.heappush(events, (t, self._now_seq(), "arrive", case))
        while events:
            now, _, kind, payload = heapq.heappop(events)
            if kind == "arrive":
                self._on_arrive(now, payload, events)
            elif kind == "complete":
                case, act, start, _ = payload
                self._on_complete(now, case, act, start, events)
            # TODO: 'applicant_response', 'notice_end', 'batch_depart',
            #       'policy_change' (S5 mid-run regime change)
        return pd.DataFrame(self.traces)

    def _sample_attrs(self, rng):
        raise NotImplementedError("sample jointly from the case-type cross-tab")

SLA_DAYS = {"Simple renovation": 21, "New residential": 60,
            "Commercial": 100, "Complex variance": 200}   # provisional, sign off!


def compute_metrics(case_frame: pd.DataFrame, pools: Dict[str, ResourcePool]) -> dict:
    """case_frame: one row per case with arrival, finish, case_type, district,
    architect quartile, rework count."""
    m = {}
    m["median_days"] = float(case_frame["cycle_days"].median())
    m["p90_days"] = float(case_frame["cycle_days"].quantile(0.90))
    for ct, g in case_frame.groupby("case_type"):
        m[f"median_{ct}"] = float(g["cycle_days"].median())
        sla = SLA_DAYS[ct]
        m[f"sla_{ct}"] = float((g["cycle_days"] <= sla).mean())
    m["rework_rate"] = float((case_frame["rework_count"] > 0).mean())
    m["peak_wip"] = float(case_frame["wip_peak"])
    for name, p in pools.items():                     # gate: 0.65-0.85, never >0.90
        cap = max(p.util_cap_min, 1.0)
        m[f"util_{name}"] = p.util_busy_min / cap
    # M8 case-mix-standardised district p90 (direct standardisation)
    w = case_frame["case_type"].value_counts(normalize=True).to_dict()
    std = {}
    for d, g in case_frame.groupby("district"):
        std[d] = sum(wt * g[g.case_type == ct]["cycle_days"].quantile(0.90)
                     for ct, wt in w.items() if (g.case_type == ct).any())
    m["district_std_p90_max_min"] = (max(std.values()) / max(min(std.values()), 1e-9))
    m["reject_rate"] = float((case_frame["outcome"] == "Reject application").mean())
    return m


def ci(values: Sequence[float], alpha: float = 0.05):
    v = np.asarray(values, dtype=float)
    n = len(v)
    m = float(v.mean())
    if n < 2:
        return m, np.nan, np.nan
    se = float(v.std(ddof=1)) / math.sqrt(n)
    t = float(sps.t.ppf(1 - alpha / 2, n - 1))
    return m, m - t * se, m + t * se


def paired_ci(baseline: Sequence[float], alternative: Sequence[float],
              alpha: float = 0.05):
    """CRN-paired difference interval (the primary comparison in this design)."""
    b, a = np.asarray(baseline, float), np.asarray(alternative, float)
    assert b.size == a.size, "CRN pairing broken"
    return ci(a - b, alpha)


class ExperimentRunner:
    def __init__(self, params_ensemble: List[ModelParameters], n_reps: int,
                 master_seed: int = 20260101,
                 burn_in_months: int = 12, measure_months: int = 18):
        self.ensemble, self.n_reps, self.seed = params_ensemble, n_reps, master_seed
        self.t0 = pd.Timestamp("2026-01-01")
        self.burn = burn_in_months
        self.measure = measure_months

    def run_one(self, exp: Experiment, rep: int) -> dict:
        params = self.ensemble[exp.param_draw % len(self.ensemble)]
        sim = PermitSimulator(params, exp.intervention, exp.stress,
                              master_seed=self.seed, rep=rep, draw=exp.param_draw)
        sim.run(self.t0, self.t0 + pd.DateOffset(
            months=self.burn + self.measure))       # burn-in discarded in metrics
        # TODO: aggregate sim.traces -> case_frame -> compute_metrics
        return {"experiment": exp.name, "rep": rep, "param_draw": exp.param_draw}

    def run_all(self, exps: List[Experiment]) -> pd.DataFrame:
        rows = []
        for exp in exps:
            for rep in range(self.n_reps):           # CRN: same seeds as B0
                rows.append(self.run_one(exp, rep))
        return pd.DataFrame(rows)

    @staticmethod
    def summarise(results: pd.DataFrame) -> pd.DataFrame:
        out = []
        metrics = [c for c in results.columns
                   if c not in {"experiment", "rep", "param_draw"}]
        for name, g in results.groupby("experiment"):
            row = {"experiment": name, "n_reps": len(g)}
            for m in metrics:
                mu, lo, hi = ci(g[m].values)
                row[f"{m}_mean"], row[f"{m}_lo"], row[f"{m}_hi"] = mu, lo, hi
            out.append(row)
        return pd.DataFrame(out)

**Design notes on the skeleton**

1. **PM4Py is isolated in Layer A.** The engine consumes only `pandas` columns; simulated traces are re-formatted with `pm4py.format_dataframe` and pushed back through `log_summary()` / `discover_and_evaluate_model()` for the replay and distributional validation loops (V2, V6).
2. **No `pm4py.read_csv`** — the log excerpt is loaded with `pandas.read_csv(io.StringIO(...))` and then normalised by `pm4py.format_dataframe`.
3. **The process-tree string is treated honestly**: we try `pm4py.parse_process_tree(TREE_AS_GIVEN)`, warn on operator-set mismatch, and fall back to a PM4Py-normalised tree, while documenting what *no* process tree can express (the AND-join before `Decision drafting`, statutory notice durations, rework reasons, appeals, cross-case dependencies) — those live in `Router`, `SharedContext` and the event loop, not in the tree.
4. **Waiting and service are never collapsed**: `add_service_waiting_columns` marks the split as `split_censored = True` when start timestamps are absent, and `ServiceParams` separates *occupancy* (consumes capacity) from *internal hold* (does not) so that the §2.6 capacity audit can be enforced.
5. **Dependencies are singleton state** (`SharedContext`, `ResourcePool`, `InspectionBundler`), and `PermitSimulator._rng` is counter-based so common random numbers survive interventions that add or remove random draws.
6. **`objection_episodes` are latent**: `active_objection_mult()` models a *duration* effect only and explicitly refuses to emit an observed-looking objection event.
