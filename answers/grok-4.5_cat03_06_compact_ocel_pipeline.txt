## 1. Modeling assumptions

- **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment` (singular, PascalCase). Object IDs: `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, `M2`.
- **E2O qualifier vocabulary:** `creates`, `adds`, `reserves`, `packs`, `dispatches`, `issues`, `records`, `confirms`, `closes`, plus involvement qualifiers `involves_order`, `involves_item`, `bills_order` where an event operationally touches extra objects. Qualifiers are stable verb-like roles, not free text.
- **O2O direction conventions:** directed edges from “container / owner / upstream” to “contained / target / downstream”:
  - `Order contains Item`
  - `Package packs Item`
  - `Delivery carries Package`
  - `Invoice bills Order`
  - `Payment partially_settles Invoice` (M1), `Payment completes_settlement Invoice` (M2)
- **Logistics and financial events vs Orders/Items:** Downstream logistics (`Pack`, `Dispatch`, `Confirm Delivery`) and finance (`Issue Invoice`, `Record Payment`) **do** get direct E2O links to the Orders they operationally involve (and Pack/Reserve also to Items), because the narrative states shared operational involvement (e.g. P1 combines two orders; V1 bills both). Items are linked on create/add/reserve/pack; not on pure delivery confirm or payment.
- **Preventing propagation confusion:** Only **explicit narrative facts** appear in `relations` and `o2o`. No derived “Order–Delivery” or “Item–Invoice” O2O rows. Analytical reachability is left to PM4Py graph algorithms, not pre-materialized as if it were source-system fact.
- **PM4Py assumption:** `from pm4py.objects.ocel.obj import OCEL` with `OCEL(events=..., objects=..., relations=..., o2o=...)`. Attribute columns use the `ocel:` prefix. If a newer API expects `parameters` or different column names, isolate the constructor line; data semantics stay unchanged.

**Trade-off (direct vs propagated):** Direct E2O to Orders/Items on shared events improves flattened Order views and OC-DFG convergence/divergence at the cost of denser relations. Pure source-minimal E2O (only the primary object) keeps relations sparse but forces analysts to join O2O for any cross-order insight—easy to confuse graph expansion with observed events. This model uses **rich direct operational E2O** for stated involvement, and **O2O only for structural business relationships**.

## 3. Data-model audit

**Objects by type**

| Object type | Objects |
|-------------|---------|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

**O2O qualifiers and cardinality**

| Qualifier | Directed pairs | Cardinality pattern |
|-----------|----------------|---------------------|
| `contains` | O100I1, O100I2, O200I3 | 2 Orders  3 Items (1–2 items/order) |
| `packs` | P1I1, P1I3, P2I2 | P1 is many-item cross-order; P2 single |
| `carries` | D1P1, D2P2 | 1:1 Delivery–Package |
| `bills` | V1O100, V1O200 | 1 Invoice  2 Orders |
| `partially_settles` | M1V1 | first partial payment |
| `completes_settlement` | M2V1 | second payment completing V1 |

**Activities and object types touched (E2O)**

| Activity | Object types in relations |
|----------|---------------------------|
| Create Order | Order |
| Add Item | Item, Order |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery, Order |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery, Package, Order |
| Close Order | Order |

**Consequential event for convergence/divergence:** **e07 (`Pack Package` on P1)** — and closely **e06 (`Reserve Stock`)** — bind I1 (O100) and I3 (O200) into one operational step. They are the primary **convergence** points of two order lines into shared logistics. **e11 (`Issue Invoice` V1)** is the financial convergence of both orders. **e09/e13** propagate that divergence/convergence through delivery D1. These relation sets drive multi-object concurrency in OC views and **event copying** when flattening on Order.

## 4. Expected flattened behavior

### Order (O100, O200)
- **Trace shape (approx.):**
  - **O100:** Create Order  Add Item  Add Item  Reserve Stock  Pack Package (P1)  Pack Package (P2)  Dispatch (D1)  Dispatch (D2)  Issue Invoice  Confirm D1  Confirm D2  Close Order  
  - **O200:** Create Order  Add Item  Reserve Stock  Pack Package (P1)  Dispatch (D1)  Issue Invoice  Confirm D1  Close Order  
  - Neither Order sees payment events (payments linked only to Payment/Invoice).
- **Copied shared events:** e06, e07, e09, e11, e13 appear in **both** order traces (same `ocel:eid` conceptually duplicated into two cases).
- **Omitted lifecycle:** payment partial/complete settlement; pure payment objects; item-level identity after flatten is only via activity labels.
- **Likely DFG edges:** CreateAdd, AddReserve, ReservePack, PackPack (O100 only), PackDispatch, DispatchIssue Invoice, IssueConfirm, ConfirmClose; also DispatchDispatch and ConfirmConfirm on O100.
- **Misleading interpretations:** Shared Reserve/Pack/Invoice look like duplicated work per order; frequencies double-count convergent events; O100 appears to “do” two full delivery subflows while O200 does one—correct for involvement, easy to misread as duplicate warehouse effort.

### Package (P1, P2)
- **Trace shape:** Pack  Dispatch  Confirm Delivery (short logistics spine).
- **Copied shared events:** none between P1 and P2 (disjoint); Orders not in these traces unless also related (they are related on pack/dispatch/confirm via Order E2O, but flattening is on Package only  Order objects drop out).
- **Omitted:** order creation, items add, invoice, payments, close.
- **Likely DFG:** Pack  Dispatch  Confirm (linear, high fitness).
- **Misleading:** Loses that P1 is cross-order; looks identical in shape to P2 despite different commercial fan-in.

### Delivery (D1, D2)
- **Trace shape:** Dispatch Package  Confirm Delivery.
- **Copied shared events:** none between D1/D2.
- **Omitted:** everything before dispatch and all finance/order close.
- **Likely DFG:** single edge Dispatch  Confirm.
- **Misleading:** ultra-short traces; no visibility that D1 serves two orders.

### Invoice (V1)
- **Trace shape (single case):** Issue Invoice  Record Payment  Record Payment  
  (M1 then M2; amounts remain event attributes if preserved by flattening).
- **Copied shared events:** N/A (one invoice object).
- **Omitted:** entire logistics and per-order create/close; which payment completed settlement is only visible if qualifier/O2O or amount attributes survive (often only activity names remain).
- **Likely DFG:** Issue  Record Payment  Record Payment (self-loop or sequential repeat on Record Payment).
- **Misleading:** looks like a tiny A/R subprocess disconnected from fulfillment; both orders’ billable reality collapses to one case without order identifiers in the control-flow.

### Why flattening on Payment is particularly weak
Each payment object (M1, M2) participates in essentially **one** event (`Record Payment`), yielding **length-1 traces**, no DFG edges of interest, and **no path** to orders or deliveries. Settlement semantics live in **O2O** (`partially_settles` / `completes_settlement`) and the shared Invoice, which flattening on Payment throws away. Ambiguous allocation of the 100+150 split across O100/O200 cannot appear in a payment-centric case notion at all.

## 5. Expected object-centric structures

- **OC-DFG:** Per-type DFGs plus inter-type coupling. Order type shows create/add/reserve/pack/dispatch/invoice/confirm/close with concurrency between O100 and O200. Package/Delivery show short chains. **P1** appears on paths fed by items from **both O100 and O200**. **V1** sits on a financial lane receiving both orders then two **Record Payment** steps (**M1**, **M2**). Divergence: one order  two packages (O100P1,P2); convergence: two orders  P1 and  V1.

- **OTG (object type graph):** Edges among Order–Item, Package–Item, Delivery–Package, Invoice–Order, Payment–Invoice reflecting O2O (and possibly co-occurrence). Expect a hub at Order and Invoice; Payment only touches Invoice; Delivery only via Package—not a direct Order–Delivery type edge unless the implementation infers interaction from joint events (our O2O does not add Order–Delivery).

- **ET–OT graph:** Activities linked to types they touch—e.g. `Reserve Stock`–Item, `Reserve Stock`–Order; `Pack Package`–Package/Item/Order; `Record Payment`–Payment/Invoice; `Issue Invoice`–Invoice/Order. Makes visible that **Reserve/Pack/Issue** are multi-type events, while **Close Order** is Order-only.

- **Object-centric Petri net:** Multiple object-type token colors. Do **not** treat the net as a single unique true model: discovery heuristics may place silent interfaces differently around shared **e06/e07/e11**. Informally: Order places fork into item handling; **P1** consumes/synchronizes tokens related to I1 and I3 (hence O100 & O200); **V1** synchronizes billing of both orders; payment transitions refine **V1**’s settlement without consuming order tokens directly; close transitions sink order tokens after logistics/finance side conditions depending on the miner.

- **Object-interactions summary:** High interaction scores for **O100–O200** via shared events (reserve, pack P1, dispatch D1, invoice V1, confirm D1); **P1** interacting with I1, I3 and both orders; **V1** with O100, O200, **M1**, **M2**; **O100** alone with P2/D2/I2. **M1/M2** interact with V1, not directly with orders—matching partial payments settling one invoice for two orders.

## 6. Modeling alternatives

1. **Source-minimal E2O**  
   Only the “primary” object per event (e.g. Pack  P1 only; Reserve  I1 & I3 only; Dispatch  D1 or P1 only; Issue  V1 only).  
   **Effect:** Flattened Order traces shrink to create/add/close (plus whatever still links orders). OC-DFG loses direct Order edges through warehouse/finance; convergence of O100/O200 must be recovered via O2O+reasoning. Cleaner “system of record” fidelity; weaker out-of-the-box process maps on Order.

2. **Full operational involvement (this pipeline)**  
   Every event that the narrative says is shared or order-relevant gets direct Order (and often Item) E2O.  
   **Effect:** Rich Order flattenings and clear OC-DFG convergence at P1/V1; risk of **relation inflation** and double-counted frequencies after flatten. Still no fabricated Order–Payment E2O.

3. **O2O-propagated analytical relations**  
   Materialize E2O for every object reachable by O2O walk (e.g. Confirm Delivery D1 also linked to I1, I3, O100, O200, even V1).  
   **Effect:** Flattened logs become very long and homogeneous; DFGs over-connect; discovery cannot distinguish **observed** participation from **inferred** ancestry. Dangerous if stored in `relations` without a qualifier namespace such as `analytic_propagated:*`. Better done at query time.

4. **(Bonus) Finance-linked orders on payments**  
   Also E2O-link e12/e15 to O100 and O200.  
   **Effect:** Order traces include payments; better end-to-end Order DFG, but invents allocation of M1/M2 to both orders equally—**ambiguous payment allocation** becomes a hidden modeling claim.

## 7. Failure modes

1. **Relation inflation:** Too many E2O qualifiers/objects per event  dense OC graphs, flattened frequency distortion, slower discovery.
2. **Missing direct E2O links:** Minimal relations  empty or trivial Order DFGs for logistics; false conclusion that orders never pack/ship.
3. **Treating O2O propagation as observation:** Writing hop-expanded pairs into `relations` or `o2o` as if the WMS/ERP emitted them  irreversible semantic pollution.
4. **Duplicate shared events after flattening:** e06/e07/e11 counted once per order case  inflated activity counts and misleading parallelism metrics.
5. **Ambiguous payment allocation:** Linking M1/M2 to orders without a business allocation rule  false per-order cash DFGs; amounts 100 and 150 cannot be split across O100/O200 from the narrative.
6. **Overly short Payment traces:** Flatten-on-Payment yields single-event cases  useless DFG/skeleton, apparent “no process.”
7. **Constructor/API version mismatch:** Some PM4Py versions use different import paths, `ocel:type` vs `ocel:object_type`, or omit `o2o` in the constructor  runtime failure if the whole pipeline is rewritten instead of isolating the constructor.
8. **False total order for same-time events:** Equal timestamps force arbitrary order in sequential miners; this dataset has distinct timestamps, but merging clocks or batch loads could reintroduce the issue.
9. **Qualifier inconsistency:** Mixing `packs` as E2O and O2O without documenting level  wrong joins when filtering by qualifier.
10. **Omitting repeated activity/timestamp on relations:** Breaks OCEL consistency checks and some PM4Py flatteners that trust relation-local timestamps.
11. **Modeling amount as an object:** Creates pseudo object types and spurious interactions; forbidden here—amounts stay on events.
12. **Assuming a unique OC Petri net meaning:** Different miners/parameters yield different silent transitions around **P1** and **V1** synchronization; over-interpreting one net as “the” process is a methodological failure.
