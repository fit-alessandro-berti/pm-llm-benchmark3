## 1. Control-Objective Decomposition

FEP-1 is not only "two different usernames touched two steps." Its control objective decomposes into several threat scenarios:

| Objective / threat scenario | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|
| Prevent one person from unilaterally initiating and authorizing a payment | Partial preventer only. It reduces some error/fraud paths but does not add an independent human decision. Warning mode is weaker because it can be overridden. | Strong preventive control when the manager is genuinely independent and acts before release or at least before irrevocable settlement. Weak if rubber-stamped or conflicted. | Detective only. It does not stop the original unilateral act unless still within recall/recovery window. | Conditional package for emergency cases. It does not erase the objective; it tries to replace strict step separation with a stronger package of preconditions plus independent approval and rapid review. |
| Block structured payment defects such as duplicate invoice, sanctions hit, recent bank change, operator-limit breach, and basic PO mismatch | Strong preventive control for exactly these covered checks if it blocks, weaker if it only warns and the warning is overridden. | Can prevent if the manager actually reviews the warning, bank details, invoice, and support. Otherwise weak. | Can detect after the fact, but often too late to avoid transfer. | Depends on AV-2 being fully operational and clean. ED-1 inherits AV-2's strengths and gaps. |
| Verify the business basis: goods/services received, support is genuine, and the payment is commercially reasonable | Gap. AV-2 explicitly does not establish receipt, authenticity of a service record, or commercial reasonableness. | Potentially strong if the manager substantively reviews receipt/service evidence and reasonableness. Weak if only formal sign-off. | Can detect fabricated support later, but usually after exposure. | Only as strong as the underlying MG-4 review and audit; ED-1 does not create new substantive receipt validation by itself. |
| Resist collusion, conflict of interest, or credential misuse by the apparent second actor | Gap. System validation does not prove who controlled the account or whether two humans were independent. | Strong only if the manager is independent, uses their own credential, and has no unresolved conflict. Weak if the approver is a direct supervisor under pressure, shares credentials, or acts with the same workstation/session pattern. | Can detect patterns later, especially repeated pairs or suspicious timing, but is not a front-line anti-collusion barrier. | Partial only. ED-1 requires an independent manager, but if independence evidence is weak, the package is weak. |
| Limit emergency-process abuse and convenience bypasses | Gap by itself. AV-2 can reduce transaction risk but cannot justify why one user handled both core steps. | Helps if the manager challenges the necessity of the emergency. | Can detect after the fact whether the exception was abused. | Main governance wrapper for justified exceptions: pre-existing token, low amount, established vendor, no recent bank change, clean AV-2, independent approval before settlement, and rapid audit. |
| Preserve recoverability once a bad payment path has started | Preventive only if it blocks before release. Otherwise limited. | Stronger when before release. If after release but before settlement, it is hybrid: detective as to the already-issued release, preventive as to irrevocable completion if the settlement can still be stopped. | Main detective/corrective control. It is partly corrective only while recall/recovery remains realistic. | Requires rapid audit, so ED-1 explicitly tries to keep a corrective path alive. |
| Handle control outages and degraded operation safely | If unavailable, it creates a major gap for bank-change and ownership risk. | Can only compensate if the manager obtains equivalent evidence manually and before settlement. | Late audit rarely compensates for an outage on a high-risk payment. | ED-1 is not satisfied if AV-2 was not fully operational and passed cleanly; outage cases are therefore outside its intended safe harbor. |

The main implication is that a case can violate nominal step separation without fully failing the objective, and a case can satisfy nominal separation while still failing the objective if independence or substantive review collapses.

## 2. Equivalence and Sufficiency Test

I would assess compensating controls with the following structured test.

1. Completion gate
   - If no payment was completed because release was blocked or canceled, classify as `LOSS_PREVENTED_BEFORE_COMPLETION`.
   - If funds could still have left or did leave, continue with the rest of the test.

2. Independence gate
   - Ask whether there was a genuinely independent human checkpoint.
   - Distinct usernames are not enough if there is shared credential use, a direct supervisory conflict, a shared workstation/session pattern that undermines separation, or evidence of a tightly coupled pair with no real challenge function.

3. Timing gate
   - Best: independent review before `Release_Payment`.
   - Next best: after release but before irrevocable settlement, if there is real authority and time to stop settlement.
   - Much weaker: after settlement, because that is mostly detective and often not recoverable.

4. Coverage gate
   - Match the control package to the actual risk in the case.
   - AV-2 is strong for duplicate, sanctions, bank-change, limit, and PO-match issues.
   - AV-2 does not cover receipt authenticity, service reality, commercial reasonableness, collusion, or credential control.
   - A compensating package cannot be "equivalent" if it misses the dominant hazard in the case.

5. Overrideability and outage gate
   - Hard blocks are materially stronger than warnings.
   - A warning overridden by the same operator, or by misuse of another person's credential, is close to ineffective for independence purposes.
   - Service unavailability is a major degradation unless replaced by credible manual evidence and strong independent approval.

6. Recoverability gate
   - RA-7 is only partly corrective while settlement or bank recall is still realistically available.
   - Audit after the recall window may still support accountability, but it does not compensate much for transaction loss prevention.

7. Evidence-quality gate
   - Rely on timestamps, documented review artifacts, explicit settlement times, signed support, token timing, and credential provenance.
   - Where evidence is materially ambiguous, downgrade from `OBJECTIVE_MET` to `OBJECTIVE_PARTIALLY_MET` or `INDETERMINATE`.

8. Collusion-resistance gate
   - True equivalence requires some resistance to collusion or at least some evidence that the second actor can and does challenge the first.
   - Repeated fixed pairs, shared workstations, and fabricated supporting evidence can defeat nominal four-eyes even when two accounts appear in the log.

Using those gates:

| Sufficiency level | Practical test |
|---|---|
| Fully equivalent | Independent human review is real, timely, and sufficiently informed; dominant transaction risks are covered; warnings were not self-overridden; recovery is not the sole safeguard; evidence is reliable; collusion resistance is credible. |
| Partially equivalent | The package materially reduces risk, but one important dimension is weaker: for example post-release manager action, incomplete evidence, narrow AV-2 coverage, borderline audit timing, or unresolved independence concerns. This is where "technically nonconforming but tolerable" often sits. |
| Merely mitigating | Some controls exist, but they mainly soften the loss if things go wrong rather than replacing the separation objective. Common examples are late ratification, late audit, warning overrides, or AV-2 coverage that misses the actual hazard. |
| Ineffective | No real independent checkpoint before irrevocable transfer, major risk factors are uncovered, overrides/outages nullify key protections, or evidence is too weak to rely on. |

"Same expected loss" is not the only valid standard because control equivalence is also about ex ante deterrence, governance legitimacy, evidentiary defensibility, tail-risk containment, and robustness to correlated failure. Two packages can have similar average loss in small samples while being very different in reversibility, collusion resistance, auditability, or exposure to catastrophic outliers.

For the case labels, I would interpret:

| Label | Meaning |
|---|---|
| `OBJECTIVE_MET` | The package is strong enough, for this case, to treat the control objective as satisfied even if nominal FEP-1 was not followed exactly. |
| `OBJECTIVE_PARTIALLY_MET` | Risk was materially reduced, but the package was not fully equivalent or the evidence is too weak for a clean pass. |
| `OBJECTIVE_FAILED` | The package did not compensate sufficiently for the control objective. |
| `LOSS_PREVENTED_BEFORE_COMPLETION` | Preventive control stopped completion before funds left. |
| `INDETERMINATE` | Evidence gaps are too material to conclude met or failed with confidence. |

## 4. Preventive-Detective-Corrective Comparison

| Control state | Primary role | Preventive value | Detective value | Corrective value | Main limitations |
|---|---|---|---|---|---|
| AV-2 full pass | Preventive | Strong for duplicate, sanctions, bank-change, amount-limit, and basic PO-match defects | Limited | None by itself | Does not prove receipt, service reality, commercial reasonableness, or actor independence |
| AV-2 warning with override | Mixed, but weakened | Only partial; once overridden, the effective barrier may be low | High as an audit trail that a known risk was surfaced | None by itself | Very sensitive to who overrides and whether override authority is independent |
| AV-2 hard block | Preventive | Very strong for the covered defect class | Some logging value | Not needed if block holds | Narrow coverage: only the blocked rule family |
| MG-4 before release | Preventive | Strong if independent and substantive | Some | Little need if it stops bad releases | Weak if rubber-stamped or if manager lacks real expertise |
| MG-4 after release but before settlement | Hybrid | Preventive against irrevocable completion if the manager can still stop settlement | Detective as to the fact that release already happened or same-user handling already occurred | Some, while the bank transfer is still interruptible | Much weaker if settlement is fast or hold power is informal only |
| MG-4 after settlement | Detective | Little or none | Moderate to strong for accountability | Usually weak, because recall may already be uncertain | Too late for many fraud/diversion scenarios |
| RA-7 within one business day and inside recall window | Detective with partial corrective effect | None | Strong | Moderate, because bad transfers may still be recalled or frozen | Relies on someone noticing the defect; cannot replace missing pre-release judgment |
| RA-7 after recall window | Detective | None | Moderate | Low | Useful for lessons and accountability, weak for loss prevention |
| ED-1 package fully satisfied | Composite emergency substitute | Can be near-equivalent for narrow emergency cases | Strong because it layers audit and documented exception use | Moderate via rapid audit and pre-settlement approval | Only valid inside its conditions; not a general excuse for same-user handling |

My semantic choice for manager action after `Release_Payment` but before `Bank_Settlement` is "hybrid, leaning preventive for completed-payment risk." The reason is that FEP-1's business purpose is to prevent an erroneous or fraudulent transfer from becoming effective, not merely to police log ordering. Once release has happened, the workflow deviation already exists, so the manager's action is detective relative to the release event. But if settlement is the point of practical irreversibility and the manager can still stop it, that same action remains preventive relative to the completed-loss event. In AP-201 and AP-207, I therefore treat it as meaningful risk reduction, but not as strong as pre-release approval.

| AP-204 | Consulting payment supported by fabricated service evidence, possibly enabled by collusion or a non-independent pair | No effective chain break for the dominant hazard; AV-2 does not validate service authenticity | Fake receipt risk, collusion risk, and false reassurance from nominal dual control remain | An actually independent second releaser with obligation to inspect evidence would likely have demanded better receiving proof or rejected the release |

The key residual-risk pattern is this:

- AV-2 is powerful against structured data defects but weak against fabricated business justification.
- MG-4 is powerful only when independent, timely, and substantive.
- RA-7 helps most when the defect is still recoverable.
- ED-1 can be strong, but only for narrow emergency cases and only when its conditions are evidenced, not merely asserted.

## 6. Evidence and Monitoring Recommendations

Evidence collection:

- Preserve a per-case UTC timeline linking prepare, validation result, override actor, manager action, settlement, and audit completion.
- Require evidence artifacts for MG-4 review: invoice, bank details, receipt/service confirmation, and explicit manager attestation that these were reviewed.
- Record whether manager action before settlement had real stop authority or was merely administrative ratification.
- Log credential provenance for overrides and approvals. "Credential assigned to manager X" is not enough; the actual actor/session evidence matters.
- Capture workstation, session, and device identifiers for prepare and release so shared-endpoint patterns can be investigated.
- Preserve vendor-master history, especially bank-account changes, effective timestamps, and who made them.
- For outage handling, record whether AV-2 was unavailable, what manual substitute evidence was obtained, who authorized degraded operation, and why release was still allowed.
- For emergency use, retain token issuance time, issuer, justification, and source-system latency evidence if timestamps are disputed.

Monitoring rules:

- Same-user rate: monitor the share of completed payments where `Prepare_Payment` and `Release_Payment` are by the same human. Outside ED-1-like cases, the expected rate should be near zero. Alert on any increase, then segment by amount, vendor age, bank-change recency, and outage status.
- Override rate: monitor AV-2 warning overrides overall and specifically for bank-change and operator-limit warnings. Any self-override or use of another person's credential should be a high-priority incident, not a routine exception.
- Late manager approval: alert on manager actions after release, and escalate sharply when they occur after settlement. Before-settlement ratification is not automatically bad, but it should be exceptional and evidenced.
- Audit-before-recall-window: track whether emergency or same-user releases are audited within one business day and also inside the practical recall window. Those are related but not identical metrics; both should be visible.
- Repeated resource pairs: monitor pair concentration for `Prepare_Payment` and `Release_Payment`. Repeated pairing above peer baseline is an alert for reduced independence, not proof of collusion.
- Shared workstations: alert when the prepare/release pair repeatedly uses the same workstation or overlapping session context. Again, this is a risk signal, not proof.
- Bank-change proximity: alert on releases within seven days of a vendor bank change, especially if the vendor is new, AV-2 warned, or AV-2 was unavailable.
- Control outages: treat `Validation_Service_Unavailable` on any high-value or recent-bank-change payment as a major control event requiring immediate review.
- Manager independence: alert when the manager is the preparer's direct supervisor, appears in repeated fixed-pair networks, or approves through suspect credential patterns.

Alert versus proof:

- A high same-user rate, repeated pair, shared workstation, or direct reporting line is an alerting fact pattern. It does not alone prove misconduct.
- Fabricated support, credential misuse, unexplained overrides of serious warnings, or a payment routed to a suspect account are much closer to proof of control failure.
- Monitoring should therefore drive escalation and evidence collection, not automatic accusations.

def first_value(grp, activity, column="org:resource"):
    rows = grp.loc[grp["concept:name"] == activity, column]
    return rows.iloc[0] if not rows.empty else pd.NA


def first_ts(grp, activities):
    if isinstance(activities, str):
        activities = [activities]
    rows = grp.loc[grp["concept:name"].isin(activities), "time:timestamp"]
    return rows.min() if not rows.empty else pd.NaT


case_rows = []
for case_id, grp in df.groupby("case:concept:name"):
    prepare_ts = first_ts(grp, "Prepare_Payment")
    release_ts = first_ts(grp, "Release_Payment")
    settlement_ts = first_ts(grp, "Bank_Settlement")

def manager_timing(row):
    if pd.isna(row["manager_ts"]):
        return "NO_MANAGER_EVENT"
    if pd.notna(row["release_ts"]) and row["manager_ts"] <= row["release_ts"]:
        return "PRE_RELEASE"
    if pd.notna(row["settlement_ts"]):
        if row["manager_ts"] <= row["settlement_ts"]:
            return "POST_RELEASE_PRE_SETTLEMENT"
        return "POST_SETTLEMENT"
    if pd.notna(row["release_ts"]):
        return "POST_RELEASE_SETTLEMENT_UNKNOWN"
    return "TIMING_UNCLEAR"


def audit_timing(row):
    if pd.isna(row["audit_ts"]):
        return "NO_AUDIT"
    if pd.isna(row["release_ts"]):
        return "AUDIT_WITHOUT_RELEASE"
    within_1bd = row["audit_ts"] <= row["release_ts"] + pd.offsets.BDay(1)
    recall_anchor = (
        row["settlement_ts"] if pd.notna(row["settlement_ts"]) else row["release_ts"]
    )
    within_24h = row["audit_ts"] <= recall_anchor + pd.Timedelta(hours=24)
    return f"WITHIN_1BD={within_1bd};WITHIN_24H_OF_ANCHOR={within_24h}"


def av_coverage(row):
    mapping = {
        "full_pass_no_override": "FULL_PASS",
        "warning_overridden": "WARNING_OVERRIDDEN",
        "hard_block": "BLOCKED",
        "service_unavailable": "UNAVAILABLE",
    }
    return mapping.get(row["av_fact_status"], str(row["av_fact_status"]).upper())


case_events["manager_timing_flag"] = case_events.apply(manager_timing, axis=1)
case_events["audit_timing_flag"] = case_events.apply(audit_timing, axis=1)
case_events["av_coverage_flag"] = case_events.apply(av_coverage, axis=1)

cols = [

PM4Py caveat: the exact behavior of `filter_four_eyes_principle` can vary by version and return type. In PM4Py versions where `keep_violations=False` is the default, the bare call returns conforming rather than violating cases, so `keep_violations=True` is the safer explicit way to obtain the violating completed-payment set. Also, the code above emits only evidence flags and timing classifications; it does not and should not pretend to compute the final compliance verdict automatically.
