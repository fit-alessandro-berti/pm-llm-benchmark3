# Process Model Discovery for Custom Production Orders

## 1. Evidence Ledger

| Evidence ID | What it supports | What it does not prove | Reliability | Modeling implication |
|-------------|------------------|------------------------|-------------|----------------------|
| Variants | Observed execution sequences | Causality, concurrency, or true optionality | High (observed) | Basis for all models, but doesn't prove order constraints |
| D1 | Start/end activities | Nothing about internal flow | High | All models must start with Register Order and end with Archive Case |
| D2 | Approve Configuration  Release Production | Nothing about prerequisites | High | Strict sequence in all models |
| D3 | Both Credit Check and Engineering Review before Approve Configuration | Order between them or concurrency | Medium-high | Both must complete before approval, but order/parallelism uncertain |
| D4 | Supplier Confirmation before Approve Configuration when present | Whether it's always required | Medium | Must precede approval when present |
| D5 | Supplier Confirmation can start after either Credit Check or Engineering Review | Doesn't prove it can start after both | Medium | Allows flexible ordering in balanced/permissive models |
| D6 | Expedite Review is optional, after both checks, before approval | Exact position relative to Supplier Confirmation | Medium | Optional activity with specific prerequisites |
| D7 | Uncertainty about Credit Check/Engineering Review relationship | Doesn't prove any specific relationship | Low | Models must explicitly represent this uncertainty |
| S1 | Credit Check before Engineering Review | Doesn't account for parallel execution | Medium (stakeholder) | Conservative model should respect this |
| S2 | Parallel execution possible | Doesn't prove it's always parallel | Medium (stakeholder) | Balanced/permissive models should allow concurrency |
| S3 | Supplier Confirmation mandatory for external components | Doesn't prove it's always required | Medium (stakeholder) | Models must handle optional Supplier Confirmation |
| S4 | Supplier Confirmation skipped for stocked components | Doesn't quantify how often | Medium (stakeholder) | Models must allow skipping |
| S5 | Missing Supplier Confirmation events (5-10%) | Doesn't prove they're always missing | Low (data quality) | Models must handle missing data |
| S6 | Expedite Review constraints | Doesn't specify exact position | Medium (stakeholder) | Models must respect prerequisites |
| S7 | Only completion timestamps available | Doesn't prove actual start times | Low (data quality) | Models can't rely on start times |

**Why DFG directions don't prove concurrency:**
The direct-follows graph shows both "Credit Check  Engineering Review" and "Engineering Review  Credit Check" edges, but this doesn't prove true concurrency. It could result from:
1. Sequential execution in different orders
2. Parallel execution with logging artifacts
3. Overlapping execution with one finishing first
4. Different process variants with different orders
Without start timestamps or lifecycle data, we cannot distinguish these cases.

## 2. Shared Assumptions

1. **Event semantics**: Only completion timestamps are available, so we model activities as atomic events occurring at their completion time.

2. **Missing Supplier Confirmation events**:
   - Some are legitimately skipped (stocked components)
   - Some are missing due to data quality issues (5-10%)
   - Models must handle both cases through optional paths

3. **Absent external/stocked attribute**:
   - Cannot distinguish between legitimate skips and missing data
   - Models must treat Supplier Confirmation as optional without knowing the reason

4. **Optionality representation**:
   - Optional activities are modeled with XOR splits where one path skips the activity
   - Silent transitions represent skips where appropriate

5. **Expedite Review**:
   - Always optional
   - Requires both Credit Check and Engineering Review to be complete
   - Must occur before Approve Configuration

6. **Start/end activities**:
   - All traces start with Register Order
   - All traces end with Archive Case

7. **Approvals**:
   - Approve Configuration must occur before Release Production
   - Both Credit Check and Engineering Review must complete before Approve Configuration

## 3. Conservative Candidate

**Inductive-bias statement**:
The conservative model prioritizes strict adherence to observed variants and high-confidence rules. It avoids making assumptions about concurrency or parallelism where evidence is ambiguous, instead using explicit XOR choices to represent all observed orderings. This model minimizes false positives (admitting unobserved behavior) at the cost of potentially underfitting the true process.

**Behavior deliberately excluded**:
1. Any interleaving of Credit Check and Engineering Review (treated as strictly sequential in observed order)
2. Supplier Confirmation occurring after Approve Configuration
3. Expedite Review occurring before both Credit Check and Engineering Review are complete
4. Multiple occurrences of any activity (except through explicit loops which we don't model)
5. Any unobserved ordering of activities (e.g., Credit Check after Supplier Confirmation when Engineering Review comes first)

**Known underfitting risks**:
1. Cannot represent true parallelism between Credit Check and Engineering Review
2. Forces explicit choice between all observed orderings, even when they might be equivalent
3. Doesn't generalize to unobserved but plausible orderings
4. Duplicate activity labels in different branches make the model harder to maintain
5. Scalability issues with many variants (exponential growth in XOR branches)

## 4. Balanced Candidate

**Inductive-bias statement**:
The balanced model seeks the most plausible generalization of the observed behavior while explicitly managing uncertainty. It uses domain knowledge to distinguish between true optionality and missing data, and makes reasonable assumptions about concurrency where evidence is ambiguous. This model balances fitness with generalization, avoiding both overfitting to observed variants and over-permissiveness.

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

# Balanced model as POWL
# Create transitions
register = Transition("Register Order")
credit = Transition("Credit Check")
engineering = Transition("Engineering Review")
supplier = Transition("Supplier Confirmation")
expedite = Transition("Expedite Review")
approve = Transition("Approve Configuration")
release = Transition("Release Production")
archive = Transition("Archive Case")
tau = SilentTransition()

# Partial order for Credit Check and Engineering Review (can be in any order or parallel)
checks_order = StrictPartialOrder()
checks_order.order.add_edge(register, credit)
checks_order.order.add_edge(register, engineering)
# No edge between credit and engineering - they can be in any order or parallel

# Partial order for Supplier Confirmation (can start after either check)
supplier_order = StrictPartialOrder()
supplier_order.order.add_edge(credit, supplier)
supplier_order.order.add_edge(engineering, supplier)
# Optional - can be skipped
supplier_order.optional = True

# Partial order for Expedite Review (requires both checks, optional)
expedite_order = StrictPartialOrder()
expedite_order.order.add_edge(credit, expedite)
expedite_order.order.add_edge(engineering, expedite)
expedite_order.order.add_edge(expedite, approve)
expedite_order.optional = True

# Approval sequence
approval_order = StrictPartialOrder()
approval_order.order.add_edge(credit, approve)
approval_order.order.add_edge(engineering, approve)
approval_order.order.add_edge(supplier, approve)  # When present
approval_order.order.add_edge(expedite, approve)  # When present

# Final sequence
final_order = StrictPartialOrder()
final_order.order.add_edge(approve, release)
final_order.order.add_edge(release, archive)

# Combine all partial orders
model_balanced = OperatorPOWL(
    operator="and",
    children=[
        checks_order,
        supplier_order,
        expedite_order,
        approval_order,
        final_order
    ]
)
```

**Decision rationale for key relationships**:

1. **Credit Check and Engineering Review**:
   - *Evidence*: Both orders observed, stakeholder S2 claims parallel execution is normal
   - *Decision*: Model as concurrent (no order constraint) in balanced model
   - *Alternative*: Could model as XOR between sequences, but this would underfit
   - *Justification*: Stakeholder S2's statement about parallel execution is more credible than S1's strict sequence, and the DFG shows both orders

2. **Supplier Confirmation**:
   - *Evidence*: Can start after either check (D5), but must precede approval (D4)
   - *Decision*: Partial order allowing start after either check, but must complete before approval
   - *Alternative*: Could require both checks to complete first, but D5 suggests this isn't necessary
   - *Justification*: D5 explicitly states it can start after either, and we see cases where it follows one but not both

3. **Expedite Review**:
   - *Evidence*: Requires both checks (D6), optional, before approval (D6)
   - *Decision*: Partial order requiring both checks, optional, before approval
   - *Alternative*: Could allow it before Supplier Confirmation, but S6 says it can be before or after
   - *Justification*: D6 is clear about prerequisites, and S6 confirms flexibility in position

4. **Optionality**:
   - *Supplier Confirmation*: Modeled as optional (can be skipped) due to S3/S4 and missing data (S5)
   - *Expedite Review*: Modeled as optional due to D6 and only appearing in 2/30 cases

**Behavior deliberately excluded**:
1. Supplier Confirmation after Approve Configuration
2. Expedite Review before both Credit Check and Engineering Review are complete
3. Approve Configuration before both Credit Check and Engineering Review are complete
4. Multiple occurrences of any activity
5. Any activity between Release Production and Archive Case

**Known underfitting risks**:
1. May still be too restrictive about the exact timing of Supplier Confirmation relative to checks
2. Doesn't capture that some Supplier Confirmation skips are legitimate while others are missing data
3. May not perfectly represent all possible interleavings of parallel activities

## 5. Permissive Candidate

**Inductive-bias statement**:
The permissive model admits all reasonable behavior consistent with the broad domain rules, even if not observed in the sample. It makes minimal assumptions about ordering constraints, only enforcing those with high-confidence evidence. This model prioritizes recall over precision, serving as an upper bound on possible process behavior.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Permissive model as ProcessTree
model_permissive = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[
        ProcessTree(label="Register Order"),
        ProcessTree(
            operator=Operator.PARALLEL,
            children=[
                # Credit Check and Engineering Review can be in any order or parallel
                ProcessTree(label="Credit Check"),
                ProcessTree(label="Engineering Review"),
                # Supplier Confirmation can start after either check, optional
                ProcessTree(
                    operator=Operator.XOR,
                    children=[
                        ProcessTree(
                            operator=Operator.SEQUENCE,
                            children=[
                                ProcessTree(
                                    operator=Operator.LOOP,
                                    children=[
                                        ProcessTree(operator=Operator.XOR, children=[
                                            ProcessTree(label="Credit Check"),
                                            ProcessTree(label="Engineering Review")
                                        ]),
                                        ProcessTree(label="Supplier Confirmation")
                                    ],
                                    label="0"
                                ),
                                # Can have multiple Supplier Confirmations? No, but this allows flexibility
                            ]
                        ),
                        ProcessTree()  # Skip
                    ]
                ),
                # Expedite Review is optional, requires both checks
                ProcessTree(
                    operator=Operator.XOR,
                    children=[
                        ProcessTree(
                            operator=Operator.SEQUENCE,
                            children=[
                                ProcessTree(
                                    operator=Operator.PARALLEL,
                                    children=[
                                        ProcessTree(label="Credit Check"),
                                        ProcessTree(label="Engineering Review")
                                    ]
                                ),
                                ProcessTree(label="Expedite Review")
                            ]
                        ),
                        ProcessTree()  # Skip
                    ]
                )
            ]
        ),
        ProcessTree(
            operator=Operator.SEQUENCE,
            children=[
                # Approve Configuration requires all previous to be complete
                ProcessTree(label="Approve Configuration"),
                ProcessTree(label="Release Production"),
                ProcessTree(label="Archive Case")
            ]
        )
    ]
)
```

**Boundary between "reasonable generalization" and forbidden behavior**:
*Allowed*:
1. Any interleaving of Credit Check and Engineering Review
2. Supplier Confirmation starting after either check (or both)
3. Multiple Supplier Confirmations (though likely not realistic)
4. Expedite Review at any point after both checks are complete
5. Any ordering of activities that doesn't violate high-confidence rules

*Forbidden*:
1. Activities before Register Order or after Archive Case
2. Approve Configuration before both Credit Check and Engineering Review are complete
3. Release Production before Approve Configuration
4. Expedite Review before both checks are complete
5. Multiple Register Order or Archive Case activities

**Behavior deliberately excluded**:
1. Activities outside the defined start/end boundaries
2. Violations of high-confidence rules (D1, D2)
3. Activities that would make the process unsound (e.g., deadlocks)
4. Clearly impossible orderings (e.g., Archive Case before Register Order)

**Known overfitting risks**:
1. May admit unrealistic behavior (e.g., multiple Supplier Confirmations)
2. Doesn't enforce that Supplier Confirmation must complete before approval
3. Allows too much flexibility in activity ordering that may not reflect reality
4. The parallel block with XORs inside may create unintended behavior

```python
def check_trace(model, trace, expected_positive=True):
    net, im, fm = convert_to_petri(model)
    trace_log = pm4py.parse_event_log_string(f"case_id,{','.join(trace)}")
    fitness = eval_factory.apply(trace_log, net, im, fm, variant=eval_factory.Variants.ALIGNMENT_BASED)
    is_positive = fitness["average_trace_fitness"] > 0.99
    return is_positive == expected_positive

print("\nPositive trace validation:")
for i, trace in enumerate(positive_traces):
    print(f"Trace {i+1}: {check_trace(model_conservative, trace)} (conservative), "
          f"{check_trace(model_balanced, trace)} (balanced), "
          f"{check_trace(model_permissive, trace)} (permissive)")

print("\nNegative trace validation:")
for i, trace in enumerate(negative_traces):
    print(f"Trace {i+1}: {not check_trace(model_conservative, trace, False)} (conservative), "
          f"{not check_trace(model_balanced, trace, False)} (balanced), "
          f"{not check_trace(model_permissive, trace, False)} (permissive)")
```

**Limitations**:
1. Sampled playout doesn't prove language inclusion for infinite languages

## 10. Uncertainty Statement

**Calibrated confidence assessments**:

1. **Credit Check and Engineering Review relationship**:
   - *Confidence*: 60% that they can be truly concurrent, 30% that they're sequential in either order, 10% other
   - *Alternative interpretation*: If S1's statement is strictly true (Credit Check before Engineering Review), the balanced model would need adjustment
   - *Impact*: Would require changing the parallel block to a sequence in the balanced model

2. **Supplier Confirmation optionality**:
   - *Confidence*: 70% that it's legitimately optional for some cases, 20% that it's always required but sometimes missing, 10% other
   - *Alternative interpretation*: If S3 is strictly true (always required for external components) and we could identify external components, we might model it as mandatory with a data quality exception
   - *Impact*: Would require adding a data quality exception path in the models

3. **Expedite Review position**:
   - *Confidence*: 80% that it can occur before or after Supplier Confirmation, 15% that it must occur after, 5% other
   - *Alternative interpretation*: If S6 is interpreted strictly to mean only after Supplier Confirmation, the models would need adjustment
   - *Impact*: Would require changing the partial order in the balanced model

4. **Missing data rate**:
   - *Confidence*: 70% that 5-10% of Supplier Confirmation events are missing, 20% that it's higher, 10% that it's lower
   - *Alternative interpretation*: If the missing data rate is actually 20-30%, we might need to adjust how we model optionality
   - *Impact*: Would require more emphasis on data quality paths in the models

**Plausible alternative interpretation that would change recommendations**:
If we take the finance manager's statement (S1) as an absolute rule ("Credit Check must finish before Engineering Review starts") rather than a preference or typical case, we would need to:
1. Adjust the balanced model to enforce Credit Check before Engineering Review
2. Re-evaluate the permissive model to remove parallel execution
3. Potentially recommend the conservative model as the primary model since it already respects this ordering

This would significantly change our recommendation because:
- The balanced model's parallel block would become invalid
- The permissive model's flexibility would be reduced
- The conservative model would better match this stricter interpretation

The key uncertainty is whether S1 represents an absolute business rule or just a typical execution pattern. Additional data collection about the actual timing of these activities would be crucial to resolve this.
