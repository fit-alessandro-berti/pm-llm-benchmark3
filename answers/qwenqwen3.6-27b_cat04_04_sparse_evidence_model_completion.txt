| D1 | Register Order is start; Archive Case is end. | Intermediate control flow. | High | Fixed start/end nodes in all models. |
| D2 | Release Production requires Approve Configuration. | Other dependencies. | High | Strict sequence: Approve  Release  Archive. |
| D3 | CC and ER must precede Approve Configuration. | Order between CC and ER. | Medium-High | Both must complete before Approve. No constraint on their mutual order. |
| D4 | SC (if required) precedes Approve Configuration. | Whether SC is truly optional or missing. | Medium | Model SC as optional/conditional; place before Approve. |
| D5 | SC may start after CC or ER. | Exact trigger condition. | Medium | SC not strictly dependent on both checks; partial order acceptable. |
| D6 | Expedite Review is optional, max once, requires CC & ER, precedes Approve. | Placement relative to SC. | Medium | Optional branch after CC & ER, before Approve. |
| D7 | Timestamps are completion-only; no concurrency signal. | Execution overlap or true parallelism. | High | Models must explicitly choose between sequence, XOR, or partial order; cannot claim concurrency from logs. |
| S1 (Finance) | CC finishes before ER starts. | Engineering workflow reality. | Medium (conflicting) | Conservative model may enforce CCER sequence. |
| S2 (Engineering) | CC & ER run in parallel; log order is arbitrary. | Finance compliance view. | Medium (conflicting) | Balanced/Permissive models should allow CC/ER concurrency or flexible order. |
| S3 (Procurement) | SC mandatory for external components. | Component type distribution. | Medium | SC cannot be modeled as universally mandatory without component attribute. |
| S4 (Production) | Stocked components skip SC. | Frequency of stocked vs external. | Medium | Explains SC absence in 7 traces; supports optionality. |
| S5 (Data Eng) | External/stocked attribute missing; 5–10% SC events may be missing. | True optionality rate. | High (data quality warning) | Models must treat SC optionality as a proxy for missing data + true skips. |
| S6 (Compliance) | Expedite only after CC & ER; before/after SC; before Approve. | Exact interleaving frequency. | Medium | Constrains Expedite placement; allows SC/Expedite swap. |
| S7 (Logging) | Only completion timestamps; same-timestamp ordered by ingestion index. | Causal or concurrent execution. | High | DFG bidirectionality is an artifact; models must not infer concurrency from order. |

# 2. Shared Assumptions

- **Completion Semantics:** All models treat log entries as completion events. Start times are unknown. Observed order reflects completion sequence, not necessarily execution order.
- **Missing Supplier Confirmation:** Treated as optional in control flow due to S4 (stocked components) and S5 (integration loss). Models do not assume hidden mandatory steps; optionality is a deliberate abstraction over missing data.
- **Absent External/Stocked Attribute:** Cannot condition branching on component type. Optionality gates are used as proxies.
- **Optionality Representation:** ProcessTree uses `Optional (O)` or `XOR` operators. POWL uses optional transitions with no incoming/outgoing constraints beyond domain rules.
- **Fixed Backbone:** `Register Order  [Core Checks]  [SC/Expedite]  Approve Configuration  Release Production  Archive Case` is invariant across all candidates per D1, D2, D3.
- **Expedite Review:** Modeled as at-most-once optional activity constrained by D6/S6.

# 3. Conservative Candidate

**Inductive Bias Statement:**  
The conservative model prioritizes compliance safety and observed frequencies. It assumes the Finance stakeholder (S1) is correct: Credit Check must complete before Engineering Review begins. It treats unobserved interleavings as invalid, models Supplier Confirmation and Expedite Review as strictly optional sequential steps after the checks, and rejects any behavior not explicitly supported by high-confidence rules or the majority variant. This minimizes precision risk but accepts higher underfitting risk if parallel execution is true.

**Compact Formal Expression:**  
`Register Order  Credit Check  Engineering Review  (Supplier Confirmation?)  (Expedite Review?)  Approve Configuration  Release Production  Archive Case`

**PM4Py ProcessTree Code:**
```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator, Leaf

# Build conservative tree programmatically
cc = Leaf("Credit Check")
er = Leaf("Engineering Review")
sc = ProcessTree(Operator.OPTIONAL, [Leaf("Supplier Confirmation")])
exp = ProcessTree(Operator.OPTIONAL, [Leaf("Expedite Review")])
approve = Leaf("Approve Configuration")
release = Leaf("Release Production")
archive = Leaf("Archive Case")
register = Leaf("Register Order")

# Sequence: Register -> CC -> ER -> (SC?) -> (Expedite?) -> Approve -> Release -> Archive
model_conservative = ProcessTree(Operator.SEQUENCE, [
    register, cc, er, sc, exp, approve, release, archive
])
```

**Deliberately Excluded Behavior:**
- Engineering Review before Credit Check
- Concurrent execution of CC and ER
- Expedite Review before both CC and ER complete
- Supplier Confirmation after Approve Configuration
- Any interleaving of SC and Expedite Review not strictly sequential

**Known Underfitting Risks:**
- Rejects valid parallel CC/ER executions (violates S2/D7)
- May flag compliant parallel traces as deviations
- Treats missing SC events as true optionality, potentially masking data loss (S5)
- Over-constrains Expedite Review placement relative to SC

# 4. Balanced Candidate

**Inductive Bias Statement:**  
The balanced model acknowledges the S1/S2 conflict and D7's timestamp limitation by modeling Credit Check and Engineering Review as a partial order (concurrent or interleaved). It respects D3/D4/D6/S6 by placing SC and Expedite Review after the checks but allows flexible interleaving between them. Optionality covers both stocked components and missing data. This model trades slight precision risk for robust generalization and explicit uncertainty management.

**Compact Formal Expression:**  
`Register Order  {CC, ER} (partial order)  {SC?, Expedite?} (partial order, both < Approve)  Approve Configuration  Release Production  Archive Case`  
Constraints: `CC < Approve`, `ER < Approve`, `SC < Approve`, `Expedite < Approve`, `CC < Expedite`, `ER < Expedite`. No order between CC & ER. No order between SC & Expedite.

**POWL Code:**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

# Define activities
act_register = Transition("Register Order")
act_cc = Transition("Credit Check")
act_er = Transition("Engineering Review")
act_sc = Transition("Supplier Confirmation")
act_exp = Transition("Expedite Review")
act_approve = Transition("Approve Configuration")
act_release = Transition("Release Production")
act_archive = Transition("Archive Case")

# Partial order constraints
po = StrictPartialOrder()
po.order.add_edge(act_register, act_cc)
po.order.add_edge(act_register, act_er)
po.order.add_edge(act_cc, act_approve)
po.order.add_edge(act_er, act_approve)
po.order.add_edge(act_sc, act_approve)
po.order.add_edge(act_exp, act_approve)
po.order.add_edge(act_cc, act_exp)
po.order.add_edge(act_er, act_exp)
# Fixed backbone
po.order.add_edge(act_approve, act_release)
po.order.add_edge(act_release, act_archive)

# Optional transitions (SC and Expedite have no mandatory predecessors besides checks)
# In POWL, optionality is implicit via lack of strict path constraints, but we mark them explicitly
optional_transitions = {act_sc, act_exp}

model_balanced = OperatorPOWL(
    po,
    start_activities={act_register},
    end_activities={act_archive},
    optional_transitions=optional_transitions
)
```

**Decision Rationale (Sequence vs Concurrency vs Partial Order):**  
- `CC` & `ER`: DFG shows both orders. S1 says sequence, S2 says parallel. D7 says timestamps can't prove concurrency. Partial order captures both hypotheses without committing.
- `SC`: D4/D5 say it must precede Approve and can start after either check. Modeled as optional partial order node before Approve.
- `Expedite`: D6/S6 require CC & ER completion, allow before/after SC, must precede Approve. Constrained by edges to CC/ER and Approve, but no edge to SC.
- This avoids false concurrency claims while admitting plausible interleavings.

**Deliberately Excluded Behavior:**
- Expedite Review before CC or ER
- SC or Expedite after Approve Configuration
- Release Production before Approve Configuration
- Missing Register Order or Archive Case

**Known Underfitting Risks:**
- May admit rare SC/Expedite interleavings not seen in logs
- Partial order does not enforce max-once for Expedite (relies on compliance monitoring)
- Optionality may over-approximate true stocked-component frequency

# 5. Permissive Candidate

**Inductive Bias Statement:**  
The permissive model maximizes generalization within domain rules. It assumes full concurrency between CC and ER, treats SC and Expedite as fully optional and freely interleavable after the checks, and only enforces hard constraints (D1, D2, D3, D6). It accepts that unobserved combinations are likely valid given missing attributes (S5) and logging limitations (S7). This model prioritizes fitness and exploration over precision.

**Compact Formal Expression:**  
`Register Order  (CC || ER)  (SC? || Expedite?)  Approve Configuration  Release Production  Archive Case`  
All middle activities are optional and concurrent after checks, constrained only by `CC < Approve`, `ER < Approve`, `SC < Approve`, `Expedite < Approve`, `CC < Expedite`, `ER < Expedite`.

**PM4Py ProcessTree Code:**
```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator, Leaf

# Parallel block for checks
cc = Leaf("Credit Check")
er = Leaf("Engineering Review")
checks_parallel = ProcessTree(Operator.AND, [cc, er])

# Optional blocks
sc_opt = ProcessTree(Operator.OPTIONAL, [Leaf("Supplier Confirmation")])
exp_opt = ProcessTree(Operator.OPTIONAL, [Leaf("Expedite Review")])

# Fixed backbone
register = Leaf("Register Order")
approve = Leaf("Approve Configuration")
release = Leaf("Release Production")
archive = Leaf("Archive Case")

# Permissive structure: Register -> (CC || ER) -> (SC? || Expedite?) -> Approve -> Release -> Archive
model_permissive = ProcessTree(Operator.SEQUENCE, [
    register,
    checks_parallel,
    ProcessTree(Operator.OR, [sc_opt, exp_opt]), # OR allows any combination including both
    approve,
    release,
    archive
])
```

**Deliberately Excluded Behavior:**
- Expedite Review before CC or ER completion
- Any activity after Approve Configuration except Release/Archive
- Missing Register Order or Archive Case
- SC or Expedite after Release Production

**Known Underfitting Risks:**  
Low. The model is designed to underfit minimally. Primary risk is overfitting (admitting undesirable traces).

# 9. Recommendation and Data-Collection Plan

**Recommendation:**  
- **Immediate Use:** `model_balanced` (POWL). It explicitly manages the S1/S2 conflict via partial order, respects all medium/high-confidence rules, and tolerates missing SC data without over-constraining or over-approximating. It offers the best trade-off for compliance monitoring and operational flexibility.
- **Sensitivity Analysis:** `model_conservative` (ProcessTree). Use to test precision bounds and audit strict compliance scenarios. Compare deviation reports against balanced model to quantify false positives from parallel execution.

**Data-Collection Plan:**  
1. **Lifecycle Timestamps:** Capture `start_time` and `end_time` for CC, ER, SC, and Expedite. This resolves D7/S7 and distinguishes concurrency from sequence.
2. **Component Attribute:** Export `external_stocked_flag` from ERP/PLM. Eliminates S5 ambiguity and allows conditional branching instead of optionality.
3. **Integration Health Logs:** Add event-level success/failure flags for SC integration. Quantifies missing data rate (S5).
4. **Maximally Informative Traces:**  
   - Traces with explicit `start_time` overlap between CC and ER (>50% overlap = concurrency).  
   - Traces with `external_stocked_flag = stocked` and missing SC (validates S4).  
   - Traces with `external_stocked_flag = external` and missing SC (validates S5 data loss).  
   - Traces where Expedite Review occurs before SC (validates S6 flexibility).

# 10. Uncertainty Statement

**Calibrated Confidence Assessment:**  
- **CC/ER Order:** 55% concurrent/interleaved (S2, D7, DFG bidirectionality), 35% sequential CCER (S1, conservative variant dominance), 10% unknown/overlapping.  
- **SC Optionality:** 65% true optionality (stocked components, S4), 35% missing data artifact (S5). Models treat it as optional; if missingness >40%, SC is likely mandatory for external, requiring conditional modeling.  
- **Expedite Placement:** 70% before SC, 20% after SC, 10% concurrent. S6 permits both; logs show mixed order.  
- **Backbone (RegisterApproveReleaseArchive):** 95%+ confidence. High consistency across all variants and rules.

**Plausible Alternative Interpretation:**  
If Finance compliance (S1) is strictly enforced by system design and Engineering's claim (S2) reflects informal workarounds not captured in logs, then `model_conservative` becomes the ground truth. Conversely, if the 5–10% SC missing rate (S5) is actually >30% due to deeper integration failures, then SC is effectively mandatory for 90% of cases, and all models underfit by treating it as optional. Collecting `external_stocked_flag` and start timestamps would immediately collapse this uncertainty space, shifting recommendation toward a conditional ProcessTree with explicit concurrency gates. Until then, the balanced partial-order model remains the most defensible hypothesis.
