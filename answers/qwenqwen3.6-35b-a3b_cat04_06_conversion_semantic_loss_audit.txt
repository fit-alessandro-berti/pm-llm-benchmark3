    operator=Operator.XOR,
    children=[legal_review, skip_legal],

trial_body = StrictPartialOrder(nodes=[configure_trial, inspect_trial])
trial_body.order.add_edge(configure_trial, inspect_trial)

correct_defect = Transition(label="Correct Defect")
verification_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, correct_defect],
)

release_change = Transition(label="Release Change")
archive_change = Transition(label="Archive Change")

    nodes=[
        register,
        assess_risk,
        prepare_evidence,
        optional_legal,
        verification_loop,
        release_change,
        archive_change,
    ]
)

source_powl.order.add_edge(register, assess_risk)
source_powl.order.add_edge(register, prepare_evidence)
source_powl.order.add_edge(assess_risk, optional_legal)
source_powl.order.add_edge(assess_risk, verification_loop)

**Discussion of Key Points:**
- **True concurrency vs. arbitrary interleaving:** Petri nets natively model concurrent enabled transitions. BPMN does not; converters typically flatten concurrency into parallel gateways or sequence flows, making the model *approximated*. Stakeholders may misread interleaving as strict ordering.
- **Lack of edge between Optional Legal and Verification:** The source explicitly leaves these branches unordered. Petri nets preserve this via independent tokens. BPMN visualization often forces a topological sort, creating an illusion of sequence.
- **Silent optional behavior:** `skip_legal` is a -transition. In Petri nets, it's an invisible arc. BPMN converters often omit it or render it as an invisible task, which can confuse routing analysis if not explicitly documented.
- **Binary-loop semantics:** The loop requires at least one iteration. Petri nets enforce this via the control flow structure. BPMN loop markers are purely visual; the actual iteration count is structural, not semantic in the BPMN schema.
- **Join before Release Change:** `release_change` synchronizes two branches. Petri nets use a place to merge tokens. BPMN uses a parallel gateway. The conversion is *approximated* because BPMN gateways can be misinterpreted as exclusive or inclusive without explicit documentation.
- **Activity-label uniqueness:** All labels are unique, preventing token ambiguity. Round-trip BPMNPetri may collapse identical labels if present, but here labels remain distinct.
- **Initial and final markings:** Preserved across conversions. BPMN start/end events map cleanly to `im`/`fm`.
- **Gateway or routing-node ambiguity in BPMN visualization:** Parallel gateways may be drawn sequentially due to layout algorithms. Exclusive gateways may appear where silent routing exists. Visual layout  behavioral semantics.

# 6. Visual-Semantics Review

BPMN rendering frequently misleads stakeholders due to layout artifacts and gateway symbolism:
- **Parallel Gateways:** Converters often draw parallel gateways as sequential sequence flows due to graph layout heuristics. A stakeholder may read `Assess Risk  Prepare Evidence` as ordered, violating INV-02.
- **Exclusive Gateways:** The XOR for `optional_legal` may be rendered as a standard decision diamond. Without explicit "skip" labeling, it appears mandatory rather than optional.
- **Loop Visualization:** BPMN loop markers are decorative. The strict partial order inside the loop (`Configure Trial  Inspect Trial`) may be flattened into a single task or drawn with confusing internal routing.
- **Silent Routing Nodes:** `skip_legal` and internal Petri places often become invisible or appear as unlabeled circles. Stakeholders cannot verify optionality or concurrency without inspecting the underlying net.
- **Apparent Ordering:** Top-down graph layout imposes a false temporal sequence on concurrent branches. `Legal Review` and `Verification Loop` may be stacked vertically, suggesting strict ordering.

**Proposed Annotations/Documentation:**
- Add explicit concurrency markers (e.g., `||`) in BPMN task descriptions.
- Label silent transitions as `[] Skip Legal` to preserve optionality semantics.
- Include a "Control Flow Semantics" note stating: "Parallel gateways indicate true concurrency, not sequence. Loop executes 1 times. Release Change requires completion of both upstream branches."
- Provide side-by-side Petri net visualization for technical validation.

# 7. Rejection Criteria

A conversion result should be **rejected or quarantined** if any of the following occur:
1. **Unsoundness Detected:** `pm4py.check_soundness` reports deadlocks, unreachable final marking, or improper completion.
2. **Loss of Required Interleaving:** Round-trip Petri net enforces strict sequential ordering where the source specifies concurrency (e.g., `Assess Risk` before `Prepare Evidence`).
3. **Premature Release:** Bounded trace validation admits a trace where `Release Change` occurs before `Verify Loop` completes.
4. **Collapse of Optional Behavior:** XOR branch becomes mandatory (both paths required) or impossible (neither path reachable) in the converted net.
5. **Failed Exact-Final-Marking Test:** Round-trip BPMNPetri net cannot reach the exact `fm` marking defined by the source.
6. **Silent Infinite Cycling:** Bounded exploration detects unbounded -transitions or silent loops that prevent termination, violating the finite trace assumption.
7. **Conversion Exception Suppression:** Exceptions from `convert_to_process_tree` or null returns are caught but silently ignored without logging or fallback validation.

# 8. Canonical Representation Recommendation

- **Authoritative Canonical Model:** **Accepting Petri Net**. Petri nets provide mathematically rigorous semantics for concurrency, silent transitions, loops, and synchronization. They are executable, analyzable, and immune to layout ambiguity.
- **Visualization Model:** **BPMN**. Used exclusively for stakeholder communication, documentation, and UI rendering. It is derivative and must never be edited directly if it feeds back into the canonical store.
- **Derivative Artifacts:** BPMN diagrams, Process Trees (if generated), and visual exports. These are approximations or layout-dependent representations.
- **Required Validation Evidence for Derivatives:** 
  - Soundness proof (`check_soundness` passes).
  - Footprint equivalence or bounded trace coverage report.
  - Round-trip marking equality verification.
  - Explicit annotation of concurrency vs. sequence.
- **Process Tree Intermediate:** **Not allowed** for authoritative storage or critical path analysis. The source model's true concurrency and non-block-structured synchronization inherently violate process tree constraints. Conversion attempts should be logged and discarded, not forced.
- **Avoiding Round-Trip Drift:** 
  - Store only the canonical Petri net (or POWL) in version control.
  - Generate BPMN/Tree on-demand from the canonical source.
  - Implement automated regression tests that compare footprints and soundness on every export.
  - Prohibit manual edits to BPMN that alter control flow; restrict edits to styling, annotations, and layout.

# 9. Residual Uncertainty

Even if all validation tests pass, the following claims **cannot** be established:
1. **Runtime Performance & Throughput:** Structural models do not capture timing, resource contention, or execution speed. A sound model may still bottleneck under load due to unmodeled constraints.
2. **Semantic Label Correctness:** The model verifies control flow, not business meaning. `Legal Review` could semantically mismatch actual regulatory requirements without affecting structural validity.
3. **Compliance with External Audits:** The model encodes internal process logic. External compliance (e.g., data retention, audit trail completeness, regulatory approvals) requires constraints outside the control-flow graph, which are not validated by footprint or soundness checks.
4. **Behavioral Equivalence in Infinite State Spaces:** Bounded exploration and footprint matching cannot guarantee equivalence under unbounded loop expansions or edge-case concurrency interleavings beyond the defined limits.
