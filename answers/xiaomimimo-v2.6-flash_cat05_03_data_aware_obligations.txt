## 1. Temporal Data Semantics

**State reconstruction (event-time).** For each case I build a *strict total order* on events using the key `ord(e) = (time:timestamp, event_index)`. State at event `e` is the forward-fill of every attribute from the last event `e'  e` in that case whose cell for that attribute is non-blank. Forward-fill runs **only** over earlier rows (sort  `groupby(case).ffill()`), so future values can never leak backwards; the final case row is never projected onto earlier events.

**Blanks.** A blank cell means *“no update at this event.”* It is **not** `null`, `0`, `LOW`, `DE`, or “cleared.” Therefore TX-302’s blank `risk_level` at `Release_Funds` still yields `MEDIUM`, TX-303’s blank risk still yields `HIGH`, TX-305’s blank `amount` at creation is `` (unknown), not `0`, and TX-305’s `150000` at `Settlement_Confirmed` (04-07 08:00) is a **future** value that must not be copied to the 04-06 11:30 release.

**Equal timestamps.** `event_index` breaks ties. TX-311 has `Enhanced_Review` (idx 3) and `Update_Jurisdiction  DE` (idx 4) at `16:20:00Z`; the correct order is review first, jurisdiction change second. Consequence: the review covered the `US / 115000` state, while the state governing the release is `DE / 115000`. Had idx 4 been ordered first, the review would have covered a `DE` case — the obligation outcome at release is unchanged (R1 is excluded by `DE` either way), but the *evidentiary content* of the review changes. Any checker that orders on timestamp alone (most conformance tools) silently loses this distinction.

**Material change.** A change is *material* if it alters a trigger condition (jurisdiction for R1/R3, risk/customer type for R2) or if the amount **increases by more than 20 %** relative to the value at the preceding review (R4). Decreases are explicitly *not* material (R4). An amount transition with an unknown operand is *unclassifiable*. The case-creation event is the baseline floor for “after the latest material data change” when no material change has occurred.

**Final attributes.** The last row of a case is a *description of the case after all events*, not a governing value. `TX-305` ends with `150000`, `TX-311` ends with `DE`; neither may be applied to earlier events. Conversely, a value that is only *recorded* later (e.g. `Record_Exemption` at 11:00) is not automatically effective earlier.

**Five distinct times.**

| Time | Meaning | Examples in this log |
|---|---|---|
| **Event time** | when the activity occurred | `Enhanced_Review` TX-302 @ 09:20 |
| **Effective time** | when a value/authorisation is operative | attribute updates at their own event ts (unless stated); exemption `effective_from` 09:00 / `expires` 18:00 |
| **Record time** | when the row was persisted | `Record_Exemption` inserts @ 11:00 (post-outage) |
| **Evidence/attestation time** | when the proof artifact was created | EX-77 signature 09:05; EX-88 certificate created 10:30; witness statement |
| **Decision time** | when the obligation is evaluated | `Release_Funds` — the snapshot used for R1–R4 |

Obligations are evaluated at **decision time** using **event-time state**, tested against **effective times**, and accepted only if **evidence time  decision time**. Record time is never substituted for evidence time (R5), and evidence time after decision time cannot retroactively create compliance.

## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).**
- *Amount  100 000 at release, proven* (immutable release payload, bank advice quoting the release message, customer order file): R1 triggers. Outcome then depends on a second judgment — whether an `Enhanced_Review` whose document **carries no amount** can be shown to cover an amount-dependent obligation. Adequate  **COMPLIANT**; inadequate  **NONCOMPLIANT**.
- *Amount < 100 000 proven*: R1 not triggered (jurisdiction CA  DE does not matter); R2/R3/R4 idle  **COMPLIANT**.
- *Evidence of an unlogged amount change 11:00–11:30* (feed outage): if > 20 % increase, R4 invalidates the ER  **NONCOMPLIANT**.
- *Accepting settlement 150000 as the release amount*: forbidden under the stated facts (“no immutable release payload”); only a hash-linked release artifact would make back-projection legitimate.
- *Counter-reading*: since the ER occurs after the only pre-release state event, R1’s *outcome* would be invariant — but that invariance itself rests on assuming no hidden change occurred during the outage, which R6 forbids assuming. Hence INDETERMINATE rather than COMPLIANT.

**TX-310 (NONCOMPLIANT; alternative INDETERMINATE).**
- Independent approval evidence  10:00 (qualified timestamp, approver mailbox/workflow log, unconflicted second witness)  exemption effective  **JUSTIFIED_EXCEPTION** (EX-88 waives R1 only; R2/R3/R4 idle).
- A reviewer treating the conflicting artifacts (backdated 08:50 vs certificate 10:30 vs witness 08:45) as genuinely unresolved  **INDETERMINATE** instead of NONCOMPLIANT.
- Scope breach (amount > 250 000, non-AE, non-CORPORATE)  exemption invalid *regardless* of evidence  firmly NONCOMPLIANT.
- Presence of any `Enhanced_Review` before 10:00  **COMPLIANT** without needing the exemption at all.

**TX-302 (COMPLIANT — robust to both readings).**
- If the release’s cited exemption were treated as the *operative* basis (rather than the ER), the label becomes **JUSTIFIED_EXCEPTION** instead of COMPLIANT — **no change in deviation status**, because EX-77 independently satisfies all five R5 conditions.
- If only the 11:00 `Record_Exemption` row existed (no qualified 09:05 signature), R5 would fail — but the ER at 09:20 still satisfies R1, so the case stays compliant. This dual-path structure is what makes TX-302 reading-insensitive.
- Only a reading that *disqualifies the ER itself* (e.g. requiring the review to postdate the exemption record, or holding the 09:20 review incomplete) would reduce the case to a single point of failure — and even then EX-77 saves it.

**TX-311 (COMPLIANT under the rules as written; reading-sensitive).**
- Correct reading (R7): trigger decided at `Release_Funds`, where jurisdiction = `DE`  R1 **not triggered**  COMPLIANT.
- Alternative: an evaluator who decides the trigger from the **review-time** snapshot (`US`, 115000  100000) would trigger R1 and then find the jurisdiction change at idx 4 *after* the ER  **NONCOMPLIANT**. This is exactly the “copy state across events” error R7 forbids.
- Alternative: ignoring `event_index` leaves the review’s covered state ambiguous (US vs DE). Obligations still resolve to COMPLIANT, but if policy required the review to evidence the *governing* jurisdiction, the case could be pushed to **INDETERMINATE**.
- Counterfactual: a release ordered between idx 3 and idx 4 (state still `US`) would trigger R1 with no material-change-compliant review  **NONCOMPLIANT**.

**TX-306 (COMPLIANT, reading-sensitive).**
- *Primary*: “material data change” inherits R4’s 20 % threshold and dimension changes  +4.55 % is immaterial  ER remains after the last material change  COMPLIANT.
- *Strict*: any `Update_Amount` resets the R1 clock  the 12:30 update postdates the ER  **NONCOMPLIANT**.
- *Stricter still*: requiring R2’s ER to postdate every state update  also violated. The rules do not state this, so it is a policy choice, not a textual consequence.

**TX-308 (COMPLIANT — two boundary/materiality readings).**
- *Inclusive* threshold (` 100000`): R1 triggers and is satisfied by the ER  COMPLIANT. *Exclusive* (`> 100000`): R1 not triggered  also no deviation. Outcome is stable here, but the trigger flag itself flips (matters for reporting/sampling).
- *Contrary reading*: treating a decrease as material  ER 14:20  change 14:25  **NONCOMPLIANT**; this directly contradicts R4, so it is rejected.

**TX-303 / TX-307 (other interpretation levers).**
- TX-303: only an `Approve`/`Sign_Off` activity *aliased* to `Compliance_Approve`, or an approval logged under a different case, would cure the deviation — an event-taxonomy/mapping question, not a data question. ## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** Attribute-based tools commonly bind the *case-level* (final) value to every event. That would back-project `TX-305  150000` onto the 11:30 release (manufacturing an R1 trigger from a settlement that had not happened) and `TX-311  DE` onto the review at 16:20 idx 3 (hiding that the review covered `US`). Only forward-filled event-time state is correct.
2. **Post-hoc exemptions.** A `Record_Exemption` activity at 11:00 makes the trace look like “release preceded by an exemption.” Control flow cannot distinguish record time from evidence time: EX-77 (signature 09:05, outage-documented insert) is valid; EX-88 (certificate created 10:30, conflicted witness, backdated PDF) is not. Same shape, opposite outcomes — only R5’s evidence prong separates them.
3. **Material changes after review.** In `TX-309` an `Enhanced_Review` *does* precede `Release_Funds`, so the precedence template passes, yet a +22.88 % increase at 15:28 (after the review, before release) invalidated it. Control flow sees an event, not the review’s *currency* relative to the state at release.
4. **Conditional activation.** R1–R3 fire only under data predicates (`jur  DE  amt  100000`; `risk = HIGH  type = PEP`; “jurisdiction added after the latest screen”). DECLARE/DFG templates are unconditional: `TX-301` (triggers R1, violated), `TX-308` (triggers R1, satisfied) and `TX-303` (does not trigger R1) are indistinguishable to a pure precedence checker.
5. **Missing data.** A missing `amount` is not a violation and not a pass — it is an unknown (R6). Conformance engines treat absent attributes as “don’t care” and silently report success (`TX-305` would show `Enhanced_Review  Release_Funds` = satisfied), whereas the correct answer is INDETERMINATE. Defaulting to `0`/`LOW` (a common ffill bug) would wrongly *trigger* R1 on TX-305.
6. **Same-timestamp ordering.** `TX-311` has two events at `16:20:00Z`. Tools that sort on timestamp only (or use arrival order) can place the jurisdiction change before the review, changing what the review covered; `event_index` is the only stable discriminator. This also affects strictness: `allow_exact_matches=True` would let an event “at” the release instant satisfy “before release.”
7. **Activity-name substitutability and granularity.** `TX-301`/`TX-310`/`TX-307` pass any generic “a review/approval occurred before release” template because `Standard_Review` and a `Compliance_Approve` on a *standard packet* exist — the rules require specifically an `Enhanced_Review`, and R2 additionally requires `ER  CA`. Control flow sees “some node existed,” not “the right node with the right content and the right ordering.”
8. **Presence  validity, and absence  violation of the right rule.** A present but ineffective artefact (`EX-88`), a present but stale artefact (`Sanctions_Screen` at 08:10 in `TX-304`, superseded by the 08:30 list update), and a rule that was never triggered (`TX-311`) all collapse to the same control-flow signal. Conformance also cannot express *invalidation* (R4) or *unknown* (R6) at all — these are not events.

## 7. Recommended Logging and Control Improvements

**Immutable release payload.** Emit `Release_Funds` with a signed, hash-chained payload snapshot: `amount`, `currency`, `jurisdiction`, `risk_level`, `customer_type`, `sanctions_list_version`, `rule_set_version`, `evaluated_obligations[]`, plus the `state_snapshot_id` it was derived from. This single artefact would have resolved `TX-305` (unknown release amount), `TX-301` (amount at release), and `TX-311` (governing jurisdiction) definitively.

**Three/four timestamps on every authorisation artefact.** `effective_from` / `effective_to` (when it operates), `recorded_at` (DB insert), `signed_at` / `attested_at` (evidence creation), and `event_time` (activity occurrence) — stored as separate columns, never a single “approval date.” Add `evidence_artifact_id` with a trusted timestamp authority reference and signer role (`approved_by`, `approver_role`), plus the outage/ticket ID whenever `recorded_at  signed_at`. This makes R5 mechanical: `evidence_time  decision_time`.

**Exemption scope as structured, machine-checkable data.** `waives = [R1, …]`, `scope_jurisdiction`, `scope_customer_type`, `scope_amount_min/max`, `currency`, `rule_version`, `expiry`, `counterparty`. The register row should be joinable on the release payload so “matching” is a query, not an argument (`TX-302`/`TX-310`).

**Review events must record what they covered.** Each `Standard_Review`/`Enhanced_Review` should carry `state_snapshot_id`, `covered_aspects = {amount, risk, jurisdiction, customer_type}`, `input_amount`, and `review_type_code`. This separates `Enhanced_Review` from `Standard_Review` in data (not just by name) and answers whether a review lacking an amount can discharge an amount-dependent obligation (`TX-305`), and whether a `Compliance_Approve` packet was enhanced or standard (`TX-307`).

**Attribute-change provenance.** Every change event should log `attribute`, `previous_value`, `new_value`, `source_system`, `actor`, `reason_code`, `materiality_flag` (and, for amount, `delta_pct`), and `supersedes_event_id`. An explicit `UNKNOWN`/`value_unavailable` marker (with cause, e.g. feed outage ticket) must be loggable as a *value* so that unknowns are positive facts rather than blanks (`TX-305`).

**Sanctions screening tied to list versions.** `Sanctions_List_Update` should emit `list_version_id`, `jurisdictions_added/removed`, `effective_at`; `Sanctions_Screen` should echo the `list_version_id` it used and its `screening_profile`. R3 then becomes: `screen.list_version_id == current_list_version_id` — no inference from timestamps (`TX-304`).

**Stable, monotonic event ordering.** Persist a per-case monotonic sequence number (and, ideally, a global LSN) written by the source system *in addition to* the timestamp, exposed as `event_index`; forbid clock-only ordering, record `clock_source`/`timezone`, and reject or explicitly flag duplicate `(case, timestamp, index)` triples. Conformance tooling must consume this key rather than sorting on timestamps.

**Rule-engine decision records.** Emit an `Obligation_Evaluated` event per (case, rule, decision point): `rule_id`, `rule_version`, `triggered` (TRUE/FALSE/UNKNOWN), `state_snapshot_id`, `evidence_refs[]`, `outcome` (SATISFIED/VIOLATED/INDETERMINATE), `evaluated_at`, `evaluator`. That turns retroactive interpretation into a reviewable artifact and creates an audit trail for `REVIEW_REQUIRED` cases.

**Conformance architecture.** Keep control-flow conformance for shape anomalies, but add a data-aware layer (declarative rules with data conditions, DCR graphs with variables, or a rules engine over event-time state) that: (i) forward-fills only; (ii) breaks ties on `event_index`; (iii) models invalidation (R4), exemption validity (R5) and unknowns (R6) explicitly; and (iv) reports `INDETERMINATE` as a first-class outcome instead of forcing a binary verdict.
