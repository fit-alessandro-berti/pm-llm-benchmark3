## 1. Equivalence design space

Let an execution be represented as `X = (E, O, <=, act, type, ext, I_eo, I_oo, Q)` where `E` is the ordered event set, `O` the object set, `act(e)` the activity label, `type(o)` the object type, `ext(o)` whether `o` is external, `I_eo` the event-object incidences, `I_oo` the unqualified object-object links, and `Q` the qualified O2O facts.

`R1: activity-sequence equivalence`
- Definition: `X ~A Y` iff the ordered activity-label sequences are identical: `alpha(X) = <act(e1), ..., act(en)> = alpha(Y)`.
- Preserves: trace length, exact activity order, repeated activities.
- Discards: all object identities, object types, multiplicities, local/external status, E2O incidence, O2O links, qualifiers.
- Properties: reflexive, symmetric, and transitive because it is equality of sequences.
- Concurrency: if two events are truly simultaneous, I would compare timestamp buckets of activity multisets rather than force an arbitrary order; if a total order is required, I would use a deterministic tie-breaker such as event id.

`R2: typed-structural equivalence under identifier renaming`
- Definition: `X ~T Y` iff there is an order-preserving isomorphism between the two typed event-object hypergraphs after renaming local identifiers. The isomorphism must preserve activity labels, event order, object types, local versus external status, E2O incidence, and unqualified O2O edges. It may rename local ids, but it may not turn a local object into an external one or change types. I treat O2O qualifiers as ignored at this level.
- Preserves: exact event order, exact typed E2O structure, exact typed O2O topology, multiplicities of objects per type, external-object participation.
- Discards: raw local identifiers, lexical order of ids, qualifier semantics such as `removed_before_dispatch` or `partially_settles`.
- Properties: reflexive, symmetric, and transitive because typed hypergraph isomorphism is an equivalence relation.
- Concurrency: replace total-order preservation by partial-order preservation, or compare timestamp buckets with canonical sorting inside each bucket.

`R3: preferred business-semantic equivalence`
- Definition: `X ~S Y` iff their canonical semantic signatures are equal: `sig_sem(X) = sig_sem(Y)`. My preferred signature keeps the exact activity-label sequence, counts of local objects by type, a boolean saying whether the focal execution is coupled to any external object at all, and motif tags derived from multiplicities and qualifiers. The motif tags are `fragmented_fulfillment`, `staged_payment`, `substitution`, and `return_repack`.
- Preserves: control-flow shape, repeated activities, local object multiplicities, whether the execution is isolated versus cross-order-coupled, and exception motifs carried by qualifiers or by distinctive subtraces.
- Discards: raw ids, exact external partner ids, the exact domain in which external sharing occurs, and fine package-item identity detail if it does not change the business motif.
- Properties: reflexive, symmetric, and transitive because it is equality of a deterministic canonical signature.
- Concurrency: build the activity component as timestamp buckets, with events inside a bucket represented by a multiset or lexicographically sorted canonical event tokens.

`R4: focal-order projection equivalence`
- Definition: first drop all external objects and all edges or qualifiers that only matter because those external objects exist; then apply `R2` to the projected execution.
- Preserves: the internally visible flow of the lead order.
- Discards: cross-order entanglement in logistics or finance.
- Properties: reflexive, symmetric, and transitive.
- Concurrency: handled as in `R2`.

`R4` is useful for analysis, but I would not use it as the main business relation because it hides exactly the kind of coordination risk that makes X5 and X6 interesting.

## 2. Canonical signatures

For `R3`, I use the following canonical signature. It is invariant to local identifier renaming because it never uses local ids directly.

```python
from collections import Counter

def is_external(obj_id: str) -> bool:
    return obj_id.startswith("EXT")

def bucketize(events):
    # If timestamps are available, group equal timestamps.
    # In this benchmark the given order is already the event order,
    # so each event is its own bucket.
    return [[ev] for ev in events]

def has_activity_subsequence(events, labels):
    seq = [ev.activity for ev in events]
    j = 0
    for a in seq:
        if a == labels[j]:
            j += 1
            if j == len(labels):
                return True
    return False

def motif_tags(execution):
    tags = set()

    local_counts = Counter()
    for obj in execution.objects:
        if not is_external(obj.id):
            local_counts[obj.type] += 1

    qualifiers = set()
    for rel in execution.o2o_relations:
        if rel.qualifier is not None:
            qualifiers.add(rel.qualifier)

    if local_counts["Package"] > 1 or local_counts["Delivery"] > 1:
        tags.add("fragmented_fulfillment")

    if local_counts["Payment"] > 1 or "partially_settles" in qualifiers:
        tags.add("staged_payment")

    if "removed_before_dispatch" in qualifiers or "replaces" in qualifiers:
        tags.add("substitution")

    if has_activity_subsequence(
        execution.events,
        ["Return Item", "Inspect Return", "Pack Package", "Dispatch"]
    ):
        tags.add("return_repack")

    return tuple(sorted(tags))

def semantic_signature(execution):
    activity_buckets = []
    for bucket in bucketize(execution.events):
        activity_buckets.append(tuple(ev.activity for ev in bucket))

    local_counts = Counter()
    shared_external = False

    for obj in execution.objects:
        if is_external(obj.id):
            shared_external = True
        else:
            local_counts[obj.type] += 1

    for ev in execution.events:
        for obj in ev.objects:
            if is_external(obj.id):
                shared_external = True

    for rel in execution.o2o_relations:
        if is_external(rel.src_id) or is_external(rel.dst_id):
            shared_external = True

    count_vector = tuple(sorted(local_counts.items()))

    return (
        tuple(activity_buckets),   # exact activity order, bucketed for ties
        count_vector,              # local object multiplicities only
        shared_external,           # cross-order coupling yes/no
        motif_tags(execution),     # business exception motifs
    )
```

This signature intentionally merges X5 and X6, because both are baseline local order flows with cross-order coupling, and I treat the presence of entanglement as business-relevant but the logistics-versus-finance location of that entanglement as secondary. If that distinction matters, replace `shared_external` by two flags such as `shared_logistics` and `shared_finance`.

## 4. Cluster interpretations

`S1: isolated standard order-to-cash`
- Signature: one local order, two local items, one package, one delivery, one invoice, one payment, no external objects, no qualifiers.
- Business behavior: clean self-contained fulfillment and settlement.
- Risks or opportunities: low coordination overhead; useful as a control cluster for SLA and conformance baselines.
- Poorly represented by: delivery-centric or package-centric flattening, because those views drop the invoice-payment closure; order flattening is actually fine here.
- Stability under repair: very stable. Renaming ids, reordering the two `Add Item` object ids, or repairing harmless attribute noise does not move it.

`S2: fragmented forward fulfillment`
- Signature: multiple packages but no reverse flow, no external sharing, one consolidated commercial closure.
- Business behavior: warehouse work is split, but outbound shipping remains effectively consolidated.
- Risks or opportunities: consolidation delay, packing coordination, and packaging cost tradeoffs; opportunity for transport optimization.
- Poorly represented by: package-centric flattening, because it turns one coordinated order into two apparently independent package cases.
- Stability under repair: stable under identifier repair, but not stable if data repair merges the two packages into one or drops one pack relation.

`S3: staged fulfillment with staged settlement`
- Signature: multiple packages, multiple deliveries, one invoice, multiple payments, no external sharing.
- Business behavior: the order is fulfilled in legs and financially settled in parts.
- Risks or opportunities: reconciliation across shipment status and payment status, customer-communication complexity, and backorder/installment support opportunities.
- Poorly represented by: any single-object flattening. Package-centric views miss the shared invoice; invoice-centric views miss that fulfillment happened in multiple delivery legs.
- Stability under repair: moderately stable. If the two payments are merged into one full payment, the execution can collapse toward `S2`.

`S4: cross-order-entangled execution`
- Signature: locally it looks like the happy path, but at least one external object participates somewhere in the focal execution.
- Business behavior: the order is not operationally isolated. In X5 the coupling is logistical; in X6 it is financial.
- Risks or opportunities: allocation ambiguity, reconciliation effort, auditability issues, and shared-shipment or shared-billing efficiencies.
- Poorly represented by: order-centric flattening, because it either duplicates shared objects across orders or hides the fact that the focal order was not isolated.
- Stability under repair: sensitive to repairs on external links. If external references are treated as noise and removed, the cluster collapses to `S1`.

`S5: pre-dispatch substitution`
- Signature: happy-path control flow plus a substitution motif from qualified relations.
- Business behavior: an initially packed item was removed or replaced before final dispatch.
- Risks or opportunities: hidden pick-pack exceptions, product substitution governance, and customer-service implications; opportunity to study substitution policy quality.
- Poorly represented by: ordinary order flattening without qualified O2O semantics, because it can look indistinguishable from `S1`.
- Stability under repair: fragile. If the qualifier or replacement relation is lost, the execution is easily misclassified as the happy path.

`S6: return, inspect, repack, redispatch`
- Signature: first dispatch, then reverse-logistics events, then a new package and new dispatch.
- Business behavior: a returned item re-enters the process and is resent after inspection.
- Risks or opportunities: extra logistics cost, damage or quality signals, and rework-cycle analysis opportunities.
- Poorly represented by: package-centric flattening, because P81 and P82 appear as separate cases and the replacement relation between them is obscured.
- Stability under repair: fairly stable as long as the return and second dispatch remain visible; if reverse-flow events are collapsed away, it can be mistaken for a forward-only cluster.

## 5. Borderline cases

1. `X1` versus `X2`
   Under literal event-string equivalence they differ, because every object id changes and the two `Add Item` events mention different item ids in different lexical order. Under `R2` and `R3` they are equivalent, because local identifiers are intentionally renamed away and nothing business-relevant changes.

2. `X1` versus `X5`
   Under `R1` they are equivalent, because the activity labels are identical. Under `R4` they are also equivalent, because projecting away the external order and item leaves the same focal-order flow. Under `R2` and `R3` they differ, because X5 is not isolated: package and delivery are shared with another order.

3. `X1` versus `X6`
   Again, `R1` says equivalent because the visible activity sequence is the same. A focal-order projection that ignores cross-order finance can also merge them. `R2` and `R3` separate them, because invoice and payment are shared across orders, which changes accountability and settlement semantics even though the logistics part is unchanged.

4. `X1` versus `X7`
   `R1` merges them because both follow the same activity-label sequence. `R2` can already separate them if E2O incidence is preserved, because X7's dispatch event explicitly touches an item. `R3` definitely separates them, because the `removed_before_dispatch` and replacement semantics mark a fulfillment exception rather than a clean happy path.

5. `X3` versus `X4`
   A coarse business relation that only asks whether fulfillment is fragmented could merge them: both use more than one package and remain forward-only. My `R3` does not merge them, because X4 adds staged deliveries and staged payment, which materially changes customer experience and reconciliation work. `R1` and `R2` also separate them.

6. `X4` versus `X8`
   A very coarse logistics abstraction might group them as "orders with two outbound legs." My preferred relation keeps them apart. X4 is monotone forward fragmentation; X8 is a reverse-loop exception with return, inspection, repack, and redispatch. Those are operationally different phenomena even if both end up with two dispatches.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is closer to my `R2` than to my preferred `R3`, but it is even more exact in some places and less expressive in others.

- Exact information preserved by the PM4Py key: PM4Py first splits the log into one sub-OCEL per lead object using the lead object plus its ancestors and descendants in the object-interaction graph. It then renames objects canonically by object type and lifecycle timing. The final cluster key is a tuple of event descriptions and object descriptions. With timestamps disabled, each event description is essentially `(activity, related_object_1, ..., related_object_k)` in sorted event order, and each object description is `(renamed_object_id, object_type)` in sorted object-id order. So it preserves exact activity order, exact per-event related-object lists after canonical renaming, and exact object inventory by type.
- Information PM4Py does not preserve in that key: the default key used here does not include timestamps, event attributes, object attributes, object changes, or the O2O table with its qualifiers. That is why X7's substitution semantics are not fully captured unless they also surface through E2O incidence.
- Why raw object identifiers can make exact clusters too fine: without canonical renaming, X1 and X2 would split immediately even though they are the same execution up to renaming. PM4Py reduces that problem by renaming objects, but exact clustering is still "too fine" whenever one wants to ignore distinctions such as where an external coupling occurs or whether two structurally different traces belong to the same business motif.
- How I would canonicalize or post-process returned clusters: keep PM4Py's exact clusters as the first pass, then compute a second-pass canonical semantic signature per returned cluster member. In that second pass, replace renamed ids by local type counts, collapse external participation to a business flag such as `shared_external`, reintroduce O2O qualifiers from the original sub-OCEL, and derive motif tags such as `staged_payment`, `substitution`, and `return_repack`. Then merge exact clusters whose semantic signatures match.
- When exact equivalence is preferable: exact equivalence is better for regression testing an OCEL extraction pipeline, strict conformance debugging, benchmarking deterministic variant discovery, and any investigation where X5 versus X6 or X3 versus X4 must remain distinct. A coarser business clustering is preferable when the goal is managerial summarization, variant compression, or exception typology rather than exact replay identity.
