## 1. Analytical assumptions

**Case notion:** I interpret case notion as a projection rule: choose one object type C, and for each object o of type C create a case whose trace is the time-ordered list of all events e where (e,o) is in the direct E2O relation. No inference via O2O. This is the standard OCEL 2.0 flattening.

**Convergence:** Many cases converge on one event. Formally, if an event e is directly related to n>1 objects of the chosen case type, flattening copies e into n traces. Example: e16 `Dispatch` is related to O1,O2,O3, so Order-flattening creates three copies of e16. Frequency is inflated while interaction evidence is retained.

**Divergence:** One case diverges over many related objects. If a case object o is related to multiple distinct objects that each generate an event of the same activity, that activity repeats inside o's trace. This creates self-loops and apparent rework that is really parallelism / batching. Example: O1 contains I11,I12, so Order-flattening puts both e11 and e12 `Pack Package` in O1's trace.

**Copied shared events as both evidence and duplication:** I treat a copy as evidence that the business interaction truly touched that case, and simultaneously as duplication if used for counting. e24 `Confirm Delivery` truly confirms delivery for O1,O2,O3 via P2,P3,D2. Deleting copies would hide consolidation; counting copies as independent occurrences would triple-count one confirmation. Analysis must therefore keep two ledgers: occurrence ledger (31 unique events) and case-ledger (e.g., 42 rows after Order-flattening).

**Analytical transformations permitted:**
- Default: no silent O2O propagation. I use only direct E2O as stated. I do not assume e13 `Pack Package P3` belongs to O2 because P3 packs I21; I use it only because e13 explicitly lists O2,O3.
- Permitted as explicit, labelled variants for sensitivity: (a) O2O-propagated enrichment, e.g., link e11 to O1 via P1-packs-I11-contains-O1 even if O1 were missing; (b) down-weighting or de-duplication of convergent events for frequency/performance; (c) object-centric views that need no flattening. Any propagation must be declared and its delta versus direct-E2O reported, not silently merged.

## 3. Concrete distortion analysis

**1. O1 split creates false Pack rework — Order flattening, divergence.**
O1 trace contains e11 `Pack P1` then e12 `Pack P2`. Order-DFG gains edge Pack Package -> Pack Package with frequency 1, plus Add Item -> Add Item e05->e06. An analyst reading variants sees O1 as rework/long variant vs O2 (single pack e13). In reality O1 was split by design across P1,P2, not reworked. Effect is harmful if labelled rework; informative if labelled split. Must annotate as divergence, not loop.

**2. Cross-order package P3 double-counts packing — Order flattening, convergence.**
e13 `Pack P3` lists O2,O3,I21,I31. Order view copies e13 to O2 and O3. Pack Package frequency becomes 5 rows (e11,e12,e13x2,e14x2? actually e14 also double) instead of 4 executions. DFG edge Add Item -> Pack Package inflated. O2 and O3 appear to each have independent packing at 10:12, hiding that there was one joint packing operation for I21+I31. Harmful for resource/cost counting; informative for order-progress tracking. Requires unique-object counting to reconcile.

**3. Cross-order package P4 merges unrelated orders — Order and Item flattening, convergence.**
e14 `Pack P4` packs I32(O3)+I41(O4). Order-flattening copies to O3,O4; Item-flattening copies to I32,I41. In Order-DFG, O3 shows e13->e14 Pack->Pack and O4 shows Create->Add->Pack, obscuring that P4's delay affects two orders simultaneously. If e14 is late, both O3 and O4 appear late independently, inviting double root-cause tickets. Context-dependent: duplication correctly signals blast radius, but harmful if summed as two delays.

**4. Consolidated delivery D2 triples Dispatch/Confirm — Order flattening, convergence.**
e16 `Dispatch D2` carries P2+P3 and lists O1,O2,O3; e24 `Confirm D2` similarly lists O1,O2,O3. Copies create 3x Dispatch and 3x Confirm Delivery rows from 2 executions. Order-DFG shows Dispatch->Issue Invoice or Dispatch->Confirm edges with inflated support, and variant table shows three orders sharing identical 11:05 and 16:00 timestamps. Naive performance analysis reports average D2 confirmation time three times, overweighting D2 vs D1 (e15,e23) and D3 (e17,e27). Harmful for volume/KPI; informative as evidence D2 is consolidation point. Package flattening mirrors this: e16,e24 copied to P2,P3.

**5. Consolidated invoice V2 doubles finance events — Order flattening, convergence.**
e19 `Issue V2` bills O2+O3; e22 and e25 `Record V2/M2/M3` list O2,O3. Order copies double Issue Invoice (1->2) and Record Payment for V2 (2->4 rows). Order-DFG suggests each of O2,O3 was invoiced and paid twice, while truth is one invoice V2 paid in two instalments. Frequency-based DFG thickness misleads audit. Harmful if counting receivables; informative to show O2 and O3 financial fates are coupled — O3 Close e30 cannot be understood without M3 e25 which also blocks O2 Close e29.

**6. Partial payments look like rework loop — Invoice flattening, divergence + Order propagation.**
V2 trace e19->e22(M2 partially_settles)->e25(M3 completes_settlement) yields DFG edge Record Payment -> Record Payment. In Invoice view this is correct instalment behaviour, not rework. In Order view, both O2 and O3 contain e22->...->e25, so loop appears twice. If analyst applies generic rework detector, V2 flagged as non-conforming. Also performance gap e22 12:40 -> e25 next day 09:00 (~20h20) appears as payment delay; in Order view it blocks both e29 and e30 Close Order, but counting twice overstates cash-at-risk. Context-dependent: loop is informative for credit policy, harmful as defect.

**7. Near-singleton Payment lifecycle collapses analysis — Payment flattening, truncation.**
M1 appears only in e21, M2 only e22, M3 only e25, M4 only e26. Flattened log has four cases of length 1, DFG with zero edges, no variants, log skeleton vacuous (no always-follows). Any directly-follows or performance view is empty, tempting claim of instant process. It hides that M2 without M3 leaves V2 unsettled and O2/O3 unclosable until next day, and that M4 e26 precedes e27 Confirm and e31 Close. Harmful if used for lead time; useful only to enumerate cash events. Demonstrates why shortest lifecycle must never be lead.

**8. Near-singleton Delivery lifecycle hides causality — Delivery flattening, truncation.**
D1:e15->e23, D2:e16->e24, D3:e17->e27. DFG is single edge Dispatch->Confirm Delivery (freq 3). Looks clean and comparable, but D3's ~22h45 span vs D1 3h appears as carrier slowness. In full OCEL, D3's span includes overnight gap and coupling to finance: V2 settlement e25 and V3 settlement e26 occur before e27, and O3/O4 closure e30/e31 after. Delivery view cannot explain why D3 waited; Item/Package views show P4 packed at 10:20 but dispatched 11:15 and confirmed next day. Truncation is harmful for root-cause, informative for pure SLA reporting if explicitly scoped to last-mile only.

**9. Item and Package flattenings erase finance coupling — Item/Package flattening, loss.**
I21 trace e07->e13->e16->e24 ends at Confirm, with no hint that O2 needs V2/M2/M3 and Close e29 next day. P3 trace e13->e16->e24 similarly ends 16:00 Day 1, hiding 20h payment wait to e25. An Item-centric DFG suggests fulfilment complete at Confirm Delivery, while Order-centric shows Close Order a day later. If KPIs built on Item/Package, on-time delivery overstates on-time order closure for O2,O3,O4. This is harmful for end-to-end OTIF; informative if question is strictly warehouse throughput. Shows why any single-type DFG needs OTG/ET-OT to recover cross-type dependencies.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs to still create, with safe questions:**
- **Order-flattened (primary, qualified):** Safe for order lead-time distribution Create e01-e04 to Close e28-e31, and for per-order variant listing if annotated for divergence/convergence. Safe to answer: which orders experienced split (O1 e11+e12) vs consolidation (O3 e13+e14, e16+e17). Unsafe for counting packs/dispatches/invoices/payments or for resource performance without de-duplication.
- **Item-flattened:** Safe for unit flow time Add->Confirm per I11,I12,I21,I31,I32,I41 and for comparing split vs joint packing. Unsafe for finance or closure compliance.
- **Package-flattened:** Safe for packing-station workload: 4 packs, of which P3 (I21+I31) and P4 (I32+I41) are cross-order. Safe to answer pack-to-dispatch lag per package. Unsafe for order OTIF.
- **Invoice-flattened (V2-focused):** Safe for audit: V1 single-settle M1, V2 two-instalment M2+M3, V3 single-settle M4. Safe to answer days-sales-outstanding per invoice. Unsafe for logistics causality.
- **Delivery-flattened:** Safe only for last-mile SLA Dispatch->Confirm per D1,D2,D3. Unsafe for anything else.
- **Payment-flattened:** Do not create as process log. Use only as event table. Its DFG/skeleton are degenerate by construction.

**Questions requiring object-centric artefacts:**
- How do P3, P4, D2, V2 couple orders? Requires OC-DFG (per-type edges preserve single execution + interaction), OTG (object-type relations Order-Item-Package-Delivery-Invoice-Payment), ET-OT graph (which event touches which types, e.g., e16 touches Order+Item+Package+Delivery), object interaction summary (counts of O2O: P3 packs 2 items from 2 orders; D2 carries 2 packages; V2 bills 2 orders).
- Is e13->e16->e24 a shared path or parallel paths? Requires equivalent-execution clustering / object-interaction view to see I21 and I31 co-executed, not duplicated.
- True frequency vs case-frequency: Requires OC-DFG's three counts (events, unique objects, total objects) — e.g., e16 is 1 event, 3 Order objects, 8 total objects.

**Reconciling contradictory findings:**
Keep occurrence ledger as ground truth. When Order-DFG says 5 packs and Package-OCDFG says 4 pack events, report both with rule: flattened frequency = sum over cases, OC frequency = unique events. When Order view shows Pack->Pack rework for O1,O3 and Item view shows linear flow, prefer Item view for rework verdict and annotate Order loop as divergence artefact. When Delivery view shows D2 normal and Order view shows O2,O3 delayed to next-day close, explain via finance coupling e25 blocking e29,e30. Never overwrite OC finding with flattened finding; use flattened only for case-scoped SLA after documenting copy handling.

## 5. Lead-object decision

**Position chosen: B. Use a primary lead object plus explicitly secondary lifecycles.**

**Decision criteria:** (1) End-to-end coverage from creation to closure; (2) Distortion manageability (can convergence/divergence be labelled and corrected?); (3) Preservation of mandated business facts (splits, consolidations, instalments); (4) Stakeholder intelligibility without hiding coupling.

**Strongest supporting evidence:** Only Order spans e01 Create to e28-e31 Close. O1 trace e01,e05,e06,e11,e12,e15,e16,e18,e21,e23,e24,e28 captures split across P1,P2 and dual Dispatch/Confirm via D1+D2 — no other type sees both creation and cash/closure. O3 trace captures full complexity: two Adds e08,e09, two Packs e13(P3 cross O2/O3)+e14(P4 cross O3/O4), two Dispatches e16(D2)+e17(D3), V2 instalments e22+e25, two Confirms e24+e27 to Close e30. Item/Package/Delivery/Invoice/Payment lifecycles all truncate before closure (Items end at Confirm, Packages at Confirm, Deliveries 2 events, Invoices miss logistics, Payments singletons). If end-to-end OTIF or order-closure compliance is the goal, Order must be backbone.

**Strongest counterargument:** Order-flattening most distorts shared executions: e16/e24 triple-counted across O1,O2,O3, e13/e14/e19/e22/e25 double-counted, plus divergence self-loops. A naive Order-DFG overstates volume by 35% (31->42) and fabricates rework. Package or Item views are cleaner for logistics and Invoice view is cleaner for audit. Elevating Order risks institutionalizing double-counting if secondary views are ignored.

**Residual risk:** Even with qualifications, performance averaging over Order cases triple-weights D2's 4h55 and double-weights P3/P4/V2 timings. Finance risk double-counted for O2+O3. Mitigation requires reporting unique-event metrics alongside case metrics and labelling e13,e14,e16,e17,e19,e22,e24,e25,e27 as shared.

**Conditions to change decision:** Switch to C (reject single lead) if audience uses flattened frequencies for resourcing/billing without correction — then no primary is safe and only OC-DFG/OTG should govern. Switch primary to Package+Delivery if question narrows to warehouse/last-mile efficiency where Order finance wait is out of scope and Item/Package linearity is more truthful. Switch primary to Invoice if question narrows to audit/collections where V2+M2+M3 is the process.

In short: Order as primary for end-to-end story, Item/Package/Invoice/Delivery as mandatory secondaries for truth-checking; never Payment as lead.

print(ocel)

flat_invoice = pm4py.ocel_flattening(ocel, object_type="Invoice")

# Store lengths to quantify duplication vs truncation: 31 events -> ? rows
order_rows, item_rows = len(flat_order), len(flat_item)

# --- Traditional DFG + skeleton per flattening (to expose distortion, not to declare truth) ---
dfg_order, start_order, end_order = pm4py.discover_dfg(flat_order)

skel_order = pm4py.discover_log_skeleton(flat_order)      # will show Pack->Pack, Dispatch->Dispatch artefacts for O1,O3
skel_invoice = pm4py.discover_log_skeleton(flat_invoice)  # will show Record->Record for V2 e22->e25
# skel_payment degenerate (singletons M1-M4): assert emptiness rather than plot
skel_payment = pm4py.discover_log_skeleton(flat_payment)

# --- Object-centric artefacts (ground truth ledger) ---
ocdfg = pm4py.discover_ocdfg(ocel)  # per-type edges; compare event vs unique-object vs total-object counts for e13,e16,e24,e22
otg = pm4py.discover_otg(ocel)      # O2O: O-contains-I, P-packs-I, D-carries-P, V-bills-O, M-settles-V
etot = pm4py.discover_etot(ocel)    # ET-OT: e16 touches Order+Item+Package+Delivery; e19 touches Order+Invoice
interactions = pm4py.ocel_objects_interactions_summary(ocel)  # quantifies P3:2 items/2 orders, D2:2 packages/3 orders, V2:2 orders/2 payments

print(f"clusters: {len(clusters)}, order_rows={order_rows}, item_rows={item_rows}")
print(f"dfg_order edges incl. Pack->Pack: {[(k,v) for k,v in dfg_order.items() if k[0]=='Pack Package' and k[1]=='Pack Package']}")
print(f"interactions summary:\n{interactions}")
# Do NOT resolve by visual inspection: assert numeric reconciliation
assert sum(dfg_order.values()) != sum(ocdfg['event_frequency'].values())  # flattened vs unique-event counts must differ due to e13,e16,e24 copies

## 7. Sensitivity and validation plan

**1. Remove / down-weight copied shared events.** Recompute Order-DFG and KPIs three ways: (a) full copy (baseline 42 rows), (b) deduplicated occurrence ledger (31 unique events, shared events e13,e14,e16,e17,e19,e22,e24,e25,e27 counted once), (c) fractional weighting (e16/e24 weight 1/3 per Order, e13/e14 weight 1/2). Expect Pack/ Dispatch/ Confirm frequencies to drop 30-50% and Pack->Pack edge to persist (divergence, not convergence) while Dispatch volume collapses. If lead-time conclusions flip between (a) and (b), report occurrence-based result as primary and case-based as blast-radius view.

**2. Direct E2O vs explicitly propagated-relation variant.** Build propagated log where e.g., e11 inherits O1 via P1-packs-I11 plus O1-contains-I11, and e15 inherits similarly, then diff trace sets versus direct-E2O traces used above. In this dataset propagation should add little (events already richly linked), but test removal of explicit O-links to simulate sparse logging: if propagation creates extra O2O-derived copies (e.g., inferring O2 into e14 via nothing — should not), flag over-propagation. Any metric that changes only under propagation is marked as inference-dependent, not evidence.

**3. Change the lead object and compare verdicts.** Re-run end-to-end questions under Order, Item, Package, Invoice leads: (i) variant count, (ii) mean Create-to-Confirm vs Create-to-Close, (iii) rework rate. Expect Item/Package to report zero rework and shorter lead times (ending e23/e24/e27) versus Order reporting Pack->Pack loops and next-day closes e29-e31 due to M3 e25 blocking. Document contradiction as truncation vs divergence artefact, not disagreement. If stakeholder prefers Package lead for warehouse KPI, require separate Invoice-lead view for V2 instalments to avoid claiming completion at Confirm.

**4. Compare OC-DFG frequency metrics: events vs unique objects vs total objects.** For edges touching shared executions (e.g., Pack Package -> Dispatch for P3/D2, Issue Invoice -> Record Payment for V2), extract all three OC-DFG counts. Expect event=1 for e13,e16,e19 but total-objects 4-8 and unique Order objects 2-3. Validate that Order-flattened DFG thickness tracks total-objects, not events. Use unique-object count for capacity planning (how many packages/deliveries/invoices ran) and total-object count for impact analysis (how many orders/items affected). Any finding that holds on only one metric (e.g., D2 dominant only on total-objects) must be qualified accordingly, preventing frequency inflation from masquerading as bottleneck.
