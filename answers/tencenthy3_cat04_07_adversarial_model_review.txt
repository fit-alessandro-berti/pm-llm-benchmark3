# 1. Review Scope and Assumptions

We distinguish four possible use cases for the discovered models:

1. **Exploratory descriptive mining / brainstorming** – the model is used to roughly visualise what happened and support hypothesis generation.
2. **Conformance enforcement / compliance monitoring** – the model is used to automatically accept or reject cases or flag violations.

The acceptable trade-off between fitness, precision, generalization, and simplicity changes sharply across these uses:

- For **exploration**, high fitness and simplicity matter; low precision is tolerable because the goal is recall of observed behaviour, not rejection of invalid behaviour.
- For **enforcement**, precision against a curated negative suite and correct mandatory-order constraints dominate; a drop in holdout fitness caused by rejecting *valid* unseen combinations is a defect, not a virtue.
- For **simulation**, optional branches and attribute conditions must be realistic; missing `external/internal` and `affected-check` attributes make any current model unsafe for reliable simulation.
- For **communication**, comprehensibility is critical, but not at the cost of hiding skipped mandatory controls.

We assume the governance board must decide whether either original model may be deployed for enforcement or only for exploration, and whether a new model is needed. We treat the behaviour probes B1–B8 as policy test cases, not as a complete ground truth. We assume the reported metrics are non-reproducible as given because seeds, alignment costs, and preprocessing were omitted.

# 3. Adversarial Review of Model S

**Strongest case for Model S**
Model S is compact, fast, and easy to explain. Its `tau` branches tolerate missing events, which is realistic given incomplete logs. It correctly fixes `Register Dossier` first and `Release Order` last, and it enforces exactly one approval via `X('Manager Approval','Auto Approval')`. For pure exploration it recovers the skeleton of the process and is far more comprehensible than Model C.

**Strongest case against Model S**
The model makes Credit Check, Technical Review, Supplier Review, and Expedite Review all optional and fully concurrent. It therefore admits traces that skip mandatory controls and misorders Expedite Review. It also omits `Correct Dossier` entirely, so it cannot represent P6.

**Five or more concrete undesirable behaviours admitted by Model S**

1. `Register Dossier, Manager Approval, Release Order` — skips both mandatory checks (violates P2). Admitted because all four `X(activity,tau)` choices can take `tau`.
2. `Register Dossier, Expedite Review, Manager Approval, Release Order` — does Expedite before any mandatory check (violates P4). Admitted by parallel block.
3. `Register Dossier, Supplier Review, Auto Approval, Release Order` — Supplier only, no checks (misapplies P3 and violates P2). Admitted.
4. `Register Dossier, Credit Check, Manager Approval, Release Order` — skips Technical Review (violates P2). Admitted.
5. `Register Dossier, Expedite Review, Credit Check, Technical Review, Auto Approval, Release Order` — B4, Expedite before checks (violates P4). Admitted.
6. `Register Dossier, Supplier Review, Expedite Review, Manager Approval, Release Order` — neither mandatory check performed (violates P2). Admitted.

**Intentional noise tolerance vs accidental semantic flaw**
The `tau` options are a legitimate noise-tolerant device for missing events. The accidental flaw is the use of a **parallel block of independent optional choices** rather than a structure that makes Credit Check and Technical Review mandatory and ordered before approval. The `X(Manager,Auto)` node is correct; the missing `Correct Dossier` node is a separate gap.

# 4. Adversarial Review of Model C

**Strongest case for Model C**
Model C explicitly enumerates observed compliant variants. It always includes both mandatory checks before approval, respects alternate check order, includes Supplier and Expedite branches, and contains one correction variant. Its training precision is high and it rejects clearly forbidden traces such as B3, B4, and B8. As a catalogue of historical variants it is audit-friendly.

**Strongest case against Model C**
- **Branch enumeration:** every new valid combination requires a new exclusive branch; the model cannot express `Supplier + Auto` or `Technical,Credit + Auto` though B2 and B5 are plausible.
- **Duplicate labels:** 33 duplicate labels complicate ownership and impact analysis (F3).
- **Unseen combinations:** holdout fitness 0.744 shows it rejects legitimate new cases (F2, F4).
- **Correction handling:** only variant 7 repeats *both* checks after `Correct Dossier`; P6 requires only affected checks, and partial rechecks (B6) are rejected.
- **Memorisation risk:** high precision may be an artefact of positive-only evaluation (F5) and of enumerating training traces rather than capturing rules.
- **Maintainability:** any process change needs branch edits; the model is not attribute-aware despite P3’s dependency on an external/internal attribute.
- **Holdout degradation:** without stratified splits and negative tests, the drop may reflect valid novelty rather than error, but either way the model is too brittle for enforcement.

Model C therefore performs well as a *historical variant list* but poorly as a forward-looking compliance model.

# 5. Behavior-Probe Matrix

Acceptance is reasoned from the formal expressions. Model S uses a sequence of `Register`, a parallel block of four `X(activity,tau)` choices, then `X(Manager,Auto)`, then `Release`. Model C is an exclusive choice of eight fixed traces.

| Probe | Model S accepts? | Model C accepts? | Policy assessment | Consequence for review |
|---|---|---|---|---|
| B1: Reg, Credit, Tech, Manager, Release | Yes | Yes | valid | Both pass; baseline OK. |
| B2: Reg, Tech, Credit, Auto, Release | Yes | No (no Auto+Tech,Credit branch) | valid | C too strict; S correct here. |
| B3: Reg, Manager, Release | Yes (all tau) | No | forbidden | S fails P2; C correct. |
| B4: Reg, Expedite, Credit, Tech, Manager, Release | Yes (parallel) | No | forbidden | S fails P4; C correct. |
| B5: Reg, Tech, Credit, Supplier, Expedite, Auto, Release | Yes | No (no Auto+Supplier+Expedite) | plausible valid | C rejects valid urgent/external case; S accepts. |
| B6: Reg, Credit, Tech, Correct, Tech, Manager, Release | No (Correct not in S) | No (only full both-recheck branch) | policy-dependent valid | Neither supports partial recheck; both fail P6. |
| B7: Reg, Credit, Tech, Supplier, Manager, Release | Yes | Yes | valid external | Both acceptable. |
| B8: Reg, Credit, Tech, Credit, Manager, Release | No (no repetition in S) | No | suspicious/forbidden | Both correctly reject; but S also cannot represent legitimate correction. |

Uncertainty: if `+` were interpreted as inclusive rather than parallel choice, S would be even more restrictive, but standard process-tree semantics treat `+` as parallel; under that standard interpretation the table holds. Model C acceptance is exact because it is an exclusive choice of fully specified sequences.

# 6. Likely Metric Pathologies

Discussed pathologies:

- **Train/holdout leakage or split sensitivity** – no seeds or preprocessing published; holdout numbers may not be stable.
- **Missing-event bias** – logs lack `external/internal` and `affected-check`; both models are evaluated on incomplete data.
- **Positive-log-only precision** – precision computed only on observed traces (F5); no curated negatives, so false-accept rate unknown.
- **Duplicated-label effects** – 33 duplicate labels in C distort simplicity, diagnostics, and ownership.
- **Silent-transition effects** – S’s `tau` choices hide skipped mandatory activities, inflating fitness.
- **Alignment-cost sensitivity** – undocumented cost settings can make missing mandatory steps cheap to align.
- **Fitness rewarded by optionalizing mandatory behaviour** – S’s high fitness is partly a control-flow defect.
- **Generalization rewarded by excessive permissiveness** – S’s TBR 0.907 is not evidence of valid generality.
- **Stakeholder-score methodology** – informal 1–5 score lacks protocol.
- **Runtime confounding by model size** – C’s slower runtime is partly due to branch explosion, not inherent complexity.

**Ranked by likely decision impact**

1. Positive-log-only precision / no negative suite – makes precision uninformative for enforcement.
2. Fitness rewarded by optionalizing mandatory behaviour (S) and holdout rejection of valid unseen behaviour (C) – core control-flow correctness.
3. Missing-attribute bias (`external/internal`, `affected-check`) – invalidates Supplier and correction semantics.
4. Silent-transition effects masking skipped mandatory checks in S.
5. Duplicated-label effects harming maintainability and diagnostics in C.
6. Train/holdout leakage / split sensitivity – undermines trust in reported holdout fitness.
7. Generalization metric misinterpretation (TBR rewards permissiveness).
8. Alignment-cost sensitivity – undocumented costs can hide misalignments.
9. Stakeholder-score methodology – informal and non-comparable.
10. Runtime confounding by model size – real but secondary to correctness.

# 7. Third Alternative

We propose `model_third`: a POWL backbone that encodes mandatory checks, an explicit correction loop, optional but attribute-flagged Supplier Review, ordered Expedite Review, and exactly-one approval.

## 1. Compact formal description

- `Register Dossier` (once, first)
- Mandatory parallel checks: `Credit Check`  `Technical Review` (both required, any order)
- Zero-or-more correction blocks: each block is `Correct Dossier` followed by a choice of repeating `Credit Check` only, `Technical Review` only, or both (no repeated check without `Correct`)
- Optional `Supplier Review` (modelled optional because the `external/internal` attribute is missing; post-hoc policy check required)
- Optional `Expedite Review`, constrained to occur after the mandatory checks and before approval
- Exactly one of `Manager Approval` / `Auto Approval`
- `Release Order` last

## 2. PM4Py code assigning `model_third`

```python
from pm4py.objects.powl.obj import Transition, SilentTransition, OperatorPOWL, StrictPartialOrder

def optional(label):
    # exclusive choice between the activity and a silent skip
    return OperatorPOWL(OperatorPOWL.CHOICE, [Transition(label=label), SilentTransition()])

# initial mandatory checks in parallel
credit = Transition(label='Credit Check')
tech = Transition(label='Technical Review')
initial_checks = StrictPartialOrder([credit, tech])  # no edge => concurrent, both mandatory

# recheck choice after a correction (at least one affected check)
re_credit = Transition(label='Credit Check')
re_tech = Transition(label='Technical Review')
only_c = re_credit
only_t = re_tech
both = StrictPartialOrder([re_credit, re_tech])
recheck_choice = OperatorPOWL(OperatorPOWL.CHOICE, [only_c, only_t, both])

corr = Transition(label='Correct Dossier')
corr_block = StrictPartialOrder([corr, recheck_choice])
# LOOP with silent body allows zero or more corrections without forcing extra full checks
correction_loop = OperatorPOWL(OperatorPOWL.LOOP, [SilentTransition(), corr_block])

reg = Transition(label='Register Dossier')
sup_opt = optional('Supplier Review')
exp_opt = optional('Expedite Review')
appr = OperatorPOWL(OperatorPOWL.CHOICE, [Transition(label='Manager Approval'),
                                          Transition(label='Auto Approval')])
rel = Transition(label='Release Order')

model_third = StrictPartialOrder([reg, initial_checks, correction_loop,
                                  sup_opt, exp_opt, appr, rel])
model_third.order.add_edge(reg, initial_checks)
model_third.order.add_edge(initial_checks, correction_loop)
model_third.order.add_edge(correction_loop, sup_opt)
model_third.order.add_edge(correction_loop, exp_opt)
model_third.order.add_edge(sup_opt, appr)
model_third.order.add_edge(exp_opt, appr)
model_third.order.add_edge(correction_loop, appr)
model_third.order.add_edge(appr, rel)
```

## 3. Declarative dictionaries / external checks

```python
policy_rules = {
    "supplier_requires_external": True,
    "expedite_after_both_checks": True,
    "exactly_one_approval": True,
    "no_check_repeat_without_correction": True
}

def post_hoc_policy_check(trace, attrs):
    """Returns (passed, flags). attrs may lack external/internal and affected_check."""
    flags = []
    acts = [e["concept:name"] for e in trace]
    if attrs.get("external") is True and "Supplier Review" not in acts:
        flags.append("MISSING_SUPPLIER_FOR_EXTERNAL")
    if "Expedite Review" in acts:
        if not (("Credit Check" in acts) and ("Technical Review" in acts)
                and acts.index("Expedite Review") > max(acts.index("Credit Check"),
                                                        acts.index("Technical Review"))):
            flags.append("EXPEDITE_ORDER_VIOLATION")
    # duplicate check without correction
    for a in ["Credit Check", "Technical Review"]:
        idx = [i for i, x in enumerate(acts) if x == a]
        if len(idx) > 1:
            if not any(acts[i] == "Correct Dossier" for i in range(idx[0], idx[1])):
                flags.append("SUSPICIOUS_REPEAT_" + a)
    return (len(flags) == 0, flags)
```

## 4. Explicit semantics

- **Mandatory checks:** `initial_checks` is a non-optional partial order; both must occur before `correction_loop` and approval.
- **Optional Supplier Review:** modelled as optional because the external attribute is missing; `post_hoc_policy_check` enforces it when the attribute is present.
- **Expedite Review ordering:** edge `correction_loop  exp_opt` ensures that if Expedite occurs it follows both mandatory checks; it remains optional and may occur before or after Supplier.
- **Exactly-one approval:** `OperatorPOWL.CHOICE` between Manager and Auto.
- **Correction/recheck:** the loop body is silent; the redo block is `Correct Dossier` followed by a recheck choice, guaranteeing P7 and partially supporting P6.

## 5. Limitations caused by missing attributes

Without `external/internal`, Supplier Review cannot be made mandatory for externals and optional for internals; it is conservatively optional with a warning. Without `affected-check`, the recheck choice allows one or both checks rather than restricting to the truly affected check; this is safer than C’s forced both-repeat but still imprecise.
