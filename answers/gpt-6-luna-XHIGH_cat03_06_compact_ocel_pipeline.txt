## 1. Modeling assumptions

The object types are capitalized exactly as follows: Order, Item, Package, Delivery, Invoice, and Payment. The object IDs are O100/O200, I1/I2/I3, P1/P2, D1/D2, V1, and M1/M2.

E2O qualifiers describe each event’s role for the linked object. The vocabulary used below is created_order, order, added_item, order_context, reserved_item, packed_package, packed_item, related_order, dispatched_package, delivery, issued_invoice, billed_order, payment, settled_invoice, confirmed_delivery, and closed_order. They are role labels, not lifecycle statuses.

Each O2O row is directed from ocel:oid to ocel:oid_2: Order → Item uses contains; Package → Item uses packs; Delivery → Package uses carries; Invoice → Order uses bills; Payment → Invoice uses partially_settles. The supplied facts call both payments partial, so neither is marked as completing settlement. No invoice total or per-order payment allocation is inferred.

The E2O policy is source-faithful with explicit shared operational context. Reserve Stock directly touches both Orders and both reserved Items. Pack P1 directly touches P1, I1, I3, O100, and O200 because the description explicitly says the event relates to both Orders. Pack P2 touches P2 and I2; its Order context can be reached through the O2O graph. Dispatch events touch their Package and Delivery, delivery confirmations touch their Delivery, invoice issuance touches V1 and both billed Orders, and payment records touch the Payment and V1. These logistics and financial E2O links do not propagate Orders or Items through O2O paths.

Keeping those distinctions preserves the difference between a source event’s recorded participants and an analytical relation inferred by graph traversal. If propagated links are later useful, derive them into a separately labeled analysis view or use a separately labeled relation qualifier; do not silently add them to this base relations table.

The code assumes the stated OCEL(events=..., objects=..., relations=..., o2o=...) constructor and the listed PM4Py convenience APIs are available. Some PM4Py releases differ in constructor or discovery return signatures. If needed, adapt the isolated OCEL(...) line (or unpack a discovery result according to that release) while retaining the same four DataFrames and their semantics.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

# One row per event. Payment amounts are event attributes, not objects.
event_rows = [
    ("e01", "Create Order",     "2026-04-06 08:00:00", "O100", None),
    ("e02", "Add Item",         "2026-04-06 08:05:00", "O100", None),
    ("e03", "Add Item",         "2026-04-06 08:06:00", "O100", None),
    ("e04", "Create Order",     "2026-04-06 08:10:00", "O200", None),
    ("e05", "Add Item",         "2026-04-06 08:12:00", "O200", None),
    ("e06", "Reserve Stock",    "2026-04-06 08:30:00", None,  None),
    ("e07", "Pack Package",     "2026-04-06 09:00:00", None,  None),
    ("e08", "Pack Package",     "2026-04-06 09:05:00", None,  None),
    ("e09", "Dispatch Package", "2026-04-06 10:00:00", None,  None),
    ("e10", "Dispatch Package", "2026-04-06 10:15:00", None,  None),
    ("e11", "Issue Invoice",    "2026-04-06 11:00:00", None,  None),
    ("e12", "Record Payment",   "2026-04-06 11:30:00", None,  100),
    ("e13", "Confirm Delivery", "2026-04-06 13:00:00", None,  None),
    ("e14", "Confirm Delivery", "2026-04-07 09:00:00", None,  None),
    ("e15", "Record Payment",   "2026-04-07 10:00:00", None,  150),
    ("e16", "Close Order",      "2026-04-07 10:30:00", "O200", None),
    ("e17", "Close Order",      "2026-04-07 10:35:00", "O100", None),
]
events = pd.DataFrame(
    event_rows,
    columns=[
        "ocel:eid", "ocel:activity", "ocel:timestamp",
        "primary_order", "payment_amount",
    ],
)
events["ocel:timestamp"] = pd.to_datetime(events["ocel:timestamp"], utc=True)

objects = pd.DataFrame(
    [
        ("O100", "Order"), ("O200", "Order"),
        ("I1", "Item"), ("I2", "Item"), ("I3", "Item"),
        ("P1", "Package"), ("P2", "Package"),
        ("D1", "Delivery"), ("D2", "Delivery"),
        ("V1", "Invoice"),
        ("M1", "Payment"), ("M2", "Payment"),
    ],
    columns=["ocel:oid", "ocel:type"],
)

# E2O specifications: (event ID, object ID, role qualifier).
e2o_specs = [
    ("e01", "O100", "created_order"),
    ("e02", "O100", "order"), ("e02", "I1", "added_item"),
    ("e03", "O100", "order"), ("e03", "I2", "added_item"),
    ("e04", "O200", "created_order"),
    ("e05", "O200", "order"), ("e05", "I3", "added_item"),
    ("e06", "O100", "order_context"), ("e06", "O200", "order_context"),
    ("e06", "I1", "reserved_item"), ("e06", "I3", "reserved_item"),
    ("e07", "P1", "packed_package"),
    ("e07", "I1", "packed_item"), ("e07", "I3", "packed_item"),
    ("e07", "O100", "related_order"), ("e07", "O200", "related_order"),
    ("e08", "P2", "packed_package"), ("e08", "I2", "packed_item"),
    ("e09", "P1", "dispatched_package"), ("e09", "D1", "delivery"),
    ("e10", "P2", "dispatched_package"), ("e10", "D2", "delivery"),
    ("e11", "V1", "issued_invoice"),
    ("e11", "O100", "billed_order"), ("e11", "O200", "billed_order"),
    ("e12", "M1", "payment"), ("e12", "V1", "settled_invoice"),
    ("e13", "D1", "confirmed_delivery"),
    ("e14", "D2", "confirmed_delivery"),
    ("e15", "M2", "payment"), ("e15", "V1", "settled_invoice"),
    ("e16", "O200", "closed_order"),
    ("e17", "O100", "closed_order"),
]

event_by_id = events.set_index("ocel:eid")
type_by_oid = objects.set_index("ocel:oid")["ocel:type"]
relation_rows = []
for eid, oid, qualifier in e2o_specs:
    event = event_by_id.loc[eid]
    relation_rows.append(
        {
            "ocel:eid": eid,
            "ocel:activity": event["ocel:activity"],
            "ocel:timestamp": event["ocel:timestamp"],
            "ocel:oid": oid,
            "ocel:type": type_by_oid.loc[oid],
            "ocel:qualifier": qualifier,
        }
    )
relations = pd.DataFrame(
    relation_rows,
    columns=[
        "ocel:eid", "ocel:activity", "ocel:timestamp",
        "ocel:oid", "ocel:type", "ocel:qualifier",
    ],
)

# Directed O2O rows: source ID, target ID, relationship qualifier.
o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"), ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"), ("P1", "I3", "packs"),
        ("P2", "I2", "packs"),
        ("D1", "P1", "carries"), ("D2", "P2", "carries"),
        ("V1", "O100", "bills"), ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"),
        ("M2", "V1", "partially_settles"),
    ],
    columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"],
)

# Referential-integrity and consistency checks.
event_ids = set(events["ocel:eid"])
object_ids = set(objects["ocel:oid"])
assert events["ocel:eid"].is_unique
assert objects["ocel:oid"].is_unique
assert not relations["ocel:eid"].isna().any()
assert set(relations["ocel:eid"]).issubset(event_ids)
assert not relations["ocel:oid"].isna().any()
assert set(relations["ocel:oid"]).issubset(object_ids)
assert set(o2o["ocel:oid"]).issubset(object_ids)
assert set(o2o["ocel:oid_2"]).issubset(object_ids)
assert not relations.duplicated().any()
assert not relations.duplicated(
    subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]
).any()
assert not o2o.duplicated().any()
assert relations["ocel:activity"].equals(
    relations["ocel:eid"].map(event_by_id["ocel:activity"])
)
assert relations["ocel:timestamp"].equals(
    relations["ocel:eid"].map(event_by_id["ocel:timestamp"])
)
assert str(events["ocel:timestamp"].dtype).endswith(", UTC]")
assert relations["ocel:type"].equals(relations["ocel:oid"].map(type_by_oid))

# The constructor line is the only point that may need adapting to a
# PM4Py release with a different OCEL constructor signature.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)
print("\nActivity frequencies:\n", events["ocel:activity"].value_counts().sort_index())
print("\nObject-type frequencies:\n", objects["ocel:type"].value_counts().sort_index())
print("\nObject types from PM4Py:\n", pm4py.ocel_get_object_types(ocel))
print(
    "\nActivities per object type:\n",
    pm4py.ocel_object_type_activities(ocel),
)

# Flatten each selected type independently; preserve the outputs by type.
flatten_types = ["Order", "Package", "Delivery", "Invoice"]
flat_logs = {}
dfgs = {}
log_skeletons = {}
for object_type in flatten_types:
    flat_logs[object_type] = pm4py.ocel_flattening(ocel, object_type)
    dfgs[object_type] = pm4py.discover_dfg(flat_logs[object_type])
    log_skeletons[object_type] = pm4py.discover_log_skeleton(
        flat_logs[object_type]
    )

# Object-centric discovery outputs.
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn, ocpn_diagnostics = pm4py.discover_oc_petri_net(ocel)
object_interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Optional visualizations, when the installed PM4Py visualization extras
# and the corresponding API signatures are available:
# pm4py.view_ocdfg(ocdfg)
# pm4py.view_ocpn(ocpn, ocpn_diagnostics)
```

## 3. Data-model audit

Object inventory:

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

O2O qualifier counts and direction:

| Qualifier | Direction | Rows / cardinality |
|---|---|---:|
| contains | Order → Item | 3: O100→I1, O100→I2, O200→I3 |
| packs | Package → Item | 3: P1→I1, P1→I3, P2→I2 |
| carries | Delivery → Package | 2: D1→P1, D2→P2 |
| bills | Invoice → Order | 2: V1→O100, V1→O200 |
| partially_settles | Payment → Invoice | 2: M1→V1, M2→V1 |

Activity-to-object-type audit, based on direct E2O links:

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Package, Item, Order (Order is present on the P1 event) |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

Reserve Stock (e06) is especially consequential: one event is jointly related to O100, O200, I1, and I3, so it represents shared operational work and will appear in both direct Order projections. Pack P1 (e07) also explicitly relates both Orders and combines their Items. Invoice issuance (e11) is a convergence point because V1 bills both Orders.

## 4. Expected flattened behavior

Flattening uses direct E2O event participation for the selected object type. O2O links provide context but do not, by themselves, add events to a flattened trace.

- **Order:** O100 is approximately Create Order → Add Item(I1) → Add Item(I2) → Reserve Stock → Pack Package(P1) → Issue Invoice(V1) → Close Order. O200 is approximately Create Order → Add Item(I3) → Reserve Stock → Pack Package(P1) → Issue Invoice(V1) → Close Order. Reserve Stock, Pack P1, and Issue Invoice are copied into both order traces because each event directly relates to both Orders. The traces omit dispatch, delivery confirmation, and payment events. Likely aggregate DFG edges include Create Order→Add Item, Add Item→Add Item, Add Item→Reserve Stock, Reserve Stock→Pack Package, Pack Package→Issue Invoice, and Issue Invoice→Close Order. The flattening can make shared work look like two independent executions and can make it seem that each Order individually owns all of the shared reservation, package, and invoice activity.

- **Package:** P1 is approximately Pack Package → Dispatch Package; P2 has the same two-activity shape. P1’s pack event mentions both Items and both Orders, but it occurs once in the P1 trace. Likely DFG edge: Pack Package→Dispatch Package. Package traces omit order creation/closure, invoice/payment activity, and delivery confirmation. They can suggest that packages have a self-contained lifecycle and conceal that P1 combines Items from two Orders.

- **Delivery:** D1 is approximately Dispatch Package → Confirm Delivery; D2 has the same shape. Each event is directly related to its Delivery and is not shared across D1 and D2, so neither trace duplicates an event from the other. Likely DFG edge: Dispatch Package→Confirm Delivery. These traces omit package contents, Orders, invoice, and payments, and can make delivery performance appear unrelated to the mixed-order contents of P1.

- **Invoice:** V1 is approximately Issue Invoice → Record Payment(M1) → Record Payment(M2). The issue event and each payment event occur once in this invoice trace. The issue event is shared across O100 and O200 in Order flattening, but it is not duplicated within the single V1 trace. Likely DFG edges are Issue Invoice→Record Payment and Record Payment→Record Payment. This view shows two recorded payments against one invoice, but does not establish an invoice total, whether it is fully paid, or how either payment is allocated between the billed Orders.

Flattening on Payment is particularly weak: M1 and M2 each have only one directly related event, Record Payment. Each trace would therefore be a one-event trace, with no payment creation, authorization, or lifecycle sequence. The O2O link to V1 does not pull the invoice’s other events or the billed Orders into a Payment trace.

## 5. Expected object-centric structures

- **OC-DFG:** The graph should summarize activity directly-follows behavior while retaining object-type context and shared participation information. It can expose the Order path from creation and item addition through Reserve Stock, Pack Package, invoice issuance, and closure, alongside Package dispatch and Delivery confirmation paths. The shared e06 Reserve Stock and e07 Pack P1 participation should remain visible as joint work involving O100 and O200; e11 Issue Invoice is another shared Order event. V1 then links the invoice issuance and both payment records at the Invoice type level. Exact graph labels and aggregation details depend on the PM4Py version and discovery options.

- **OTG:** The object-type graph should reflect the directed O2O schema: Order→Item, Package→Item, Delivery→Package, Invoice→Order, and Payment→Invoice. Its paths make the convergence and divergence inspectable. P1 packs I1 and I3, which belong to O100 and O200 respectively, so the two order/item lineages converge at P1 (and D1 carries P1). V1 bills both O100 and O200, while M1 and M2 each point to V1. These are relationship paths, not additional event observations.

- **ET–OT graph:** This graph should connect event/activity types to the object types that participate in them. For example, Reserve Stock connects to Order and Item; Pack Package connects to Package and Item, and also Order because e07 directly links O100/O200; Dispatch Package connects to Package and Delivery; Issue Invoice connects to Invoice and Order; Record Payment connects to Payment and Invoice. Such a view helps check which activities span object types and highlights e06, e07, and e11 as cross-object events.

- **Object-centric Petri net:** The discovered net can represent activity behavior and synchronization across object types, including shared reservation/packing and the Invoice/Payment path. It may expose that V1 joins the billing of O100 and O200 and that P1 handles Items from both Orders. The mined net is one model inferred under a particular algorithm and parameterization; it does not have a uniquely determined interpretation, and it should not be read as proof of a single mandatory execution order beyond the recorded events.

- **Object-interactions summary:** An interaction summary should highlight object pairs co-participating in events. O100 and O200 interact directly through Reserve Stock, Pack P1, and Issue Invoice. I1 and I3 co-occur in Reserve Stock and Pack P1; P1 co-occurs with those Items in its pack event. M1 and V1 co-occur in the first payment event, and M2 and V1 co-occur in the second. Depending on the summary’s exact definition, O2O-connected pairs such as an Order and its Item may also be represented separately from event co-participation. Keep those two evidence sources distinct when interpreting the result.

## 6. Modeling alternatives

1. **Source-minimal E2O:** Link each event only to the objects explicitly named as participants, with shared Orders included where the description says so. This is the policy used here. It keeps operational observations conservative; downstream Order flattening omits direct order context for dispatch and delivery, even though that context is reachable through package/item relationships.

2. **Full operational involvement:** Add direct E2O links for all objects considered operationally involved. For example, Dispatch P1 could link to O100, O200, I1, and I3, and Confirm Delivery D1 could link to those objects as well as D1. This makes Order and Item projections more complete for end-to-end operational analysis, but increases shared-event copying and can make inferred lineage look like a source-system observation unless the policy is clearly labeled.

3. **O2O-propagated analytical relations:** Keep the base E2O relations source-faithful, then create a separate derived view that traverses O2O paths (for example, from P1 through I1/I3 to O100/O200). This can support Order-level logistics and end-to-end DFG analysis without rewriting the source facts. It can also multiply links across many-to-many paths, so the derived rows need provenance and must not be mistaken for observed participants.

4. **Object-anchor or item-centric operational policy:** Relate stock reservation primarily to I1 and I3, and package/dispatch events to the relevant Package, Items, and Delivery, while retaining Orders only where explicitly present. This emphasizes inventory and fulfillment behavior. Order-level flattening becomes sparser, but the business story is unchanged because Order ownership remains expressible through Order→Item O2O links.

5. **Financial propagation policy:** Relate Record Payment directly to V1 and the Orders billed by V1 for a finance-focused projection, while retaining M1/M2 as direct payment participants. This makes payment activity visible in both Order traces, but the data gives no allocation of 100 or 150 units to a particular Order. Such links express invoice-level analytical context, not per-order payment allocation.

## 7. Failure modes

1. **Relation inflation:** Propagating every Package, Delivery, Invoice, and Payment event to every reachable Order and Item can create large numbers of repeated E2O rows and distort activity frequencies in flattened logs.

2. **Missing direct shared-event links:** Omitting O100/O200 from Reserve Stock or from the explicitly shared Pack P1 event hides the stated joint operational work and changes the Order projections.

3. **Treating O2O propagation as observation:** A path such as Delivery→Package→Item→Order is lineage context. It does not prove that a delivery event’s source record explicitly named that Order or Item.

4. **Duplicate shared events after flattening:** Reserve Stock, Pack P1, and Issue Invoice appear in both Order traces. Summing flattened event counts as if each row were a distinct source event double-counts them.

5. **Ambiguous payment allocation:** M1 and M2 both settle V1, which bills two Orders. The narrative does not say how the 100 and 150 units divide between O100 and O200, nor does it state the invoice total or that the balance reaches zero.

6. **Overly short Payment traces:** With only one directly related Record Payment event per Payment object, Payment flattening cannot reveal a meaningful lifecycle or settlement sequence.

7. **Constructor or API version mismatch:** PM4Py releases can change import locations, constructor arguments, discovery return shapes, or visualization signatures. Adapting the isolated constructor/API call is preferable to changing the table semantics to fit a different version.

8. **False total-order interpretation:** Timestamp sorting gives an observed chronology, not proof that every adjacent event causally depends on the previous one. This example has no timestamp ties, but in tied data an arbitrary row order can create spurious DFG edges; even with distinct timestamps, a DFG edge is not itself a causal claim.

9. **Wrong O2O direction or qualifier:** Reversing carries, bills, or partially_settles can obscure which object owns the relationship. Ambiguous qualifiers also make the object graph hard to audit.

10. **Inconsistent E2O attributes or IDs:** A relation row with an unknown event/object, or with an activity/timestamp copied incorrectly, breaks referential integrity and can produce silent or misleading discovery results.

11. **Omitting objects or events to simplify the model:** Leaving out M2, D2, or I3 would remove stated business facts and alter the observed convergence/divergence patterns.

12. **Inventing completion or causality:** Labeling M2 as completing settlement, adding an invoice amount, or claiming one Order’s payment is settled before the other would exceed the supplied facts.

## 8. Final semantic checks

A reviewer can inspect the generated tables and verify at least these statements:

1. events has 17 unique IDs, e01–e17, and every timestamp is timezone-aware UTC.
2. objects has exactly 12 unique IDs: two Orders, three Items, two Packages, two Deliveries, one Invoice, and two Payments.
3. O100 contains I1 and I2; O200 contains I3; P1 packs I1 and I3; P2 packs I2.
4. D1 carries P1 and D2 carries P2; V1 bills both O100 and O200.
5. M1 and M2 each have a Record Payment event against V1, with amounts 100 and 150 stored on those event rows, and no amount object exists.
6. Reserve Stock e06 is directly related to O100, O200, I1, and I3.
7. Pack Package e07 is directly related to P1, I1, I3, O100, and O200; e08 is related to P2 and I2.
8. Issue Invoice e11 is directly related to V1, O100, and O200; the payment events are related to M1/V1 and M2/V1.
9. Each relations row repeats the activity and UTC timestamp for its event in events, and every referenced event/object exists.
10. The relation tables contain no duplicate rows, and dispatch/confirmation events are not silently propagated to Orders or Items in the base E2O data.
