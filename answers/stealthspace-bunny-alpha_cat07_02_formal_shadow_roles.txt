# 1. Proposed role structure

The structure below is an **operating-role hypothesis**, not a claim about formal HR reporting lines. A resource’s activities, certifications, home team, case complexity, and substitution history support the assignments; however, the log does not explicitly record final decision rights. In particular, participation in an approval activity must not automatically be interpreted as authority to give final approval.

Two qualifications matter:

- The complexity figures describe **case exposure**, not necessarily exclusive case ownership. A case can touch several resources.
- “Core” means regularly owned work, not necessarily the most frequent work. Rare security interventions and approvals can be organizationally more critical than high-volume registration.

# 2. Core versus peripheral activities

Core activities are recurring responsibilities that define a role’s operating contribution. Peripheral activities are shared, occasional, delegated, or secondary work. Neither core status nor high frequency establishes authority.

### Front-office service delivery — R01_Amira and R02_Ben

- **Core:** Validation, standard response, and closure are high-frequency activities. The standard-path fragments make this the most likely human case-owning role.
- **Peripheral:** The smaller diagnosis, configuration, and implementation counts suggest triage, simple adjustments, or escalation support rather than unrestricted technical ownership.
- **Complexity:** Amira handles more medium/high cases than Ben, so both belong in the same craft role, but case allocation should reflect experience.
- **Substitution and authority:** These agents are not shown substituting for pricing or security specialists and do not perform A9 in this window. They should not automatically receive commercial or supervisory authority simply because they close requests.

### Technical diagnosis, configuration, and implementation — R03_Chen and R04_Dina

- **Core:** Diagnosis, configuration, and implementation have high and nearly equal counts for both resources.
- **Peripheral:** Their registration, standard-response, security, quality, and closure activities indicate support and handoffs around the technical core.
- **Complexity:** Similarity of 0.94 supports a shared craft role, but it does not justify equal allocation of critical or security-adjacent work. Chen’s higher critical and security exposure may reflect expertise, assignment policy, or both.
- **Authority:** Technical execution should be distinguished from permission to approve exceptions, release security-sensitive changes, or close an escalated case.

- **Complexity:** Erik has the highest median complexity in the resource table. Treating A6 as peripheral because it has fewer events would be especially misleading.

# 5. PM4Py role-discovery and similarity code

The following is illustrative Python for a PM4Py-style normalized dataframe. It assumes the supplied event attributes are present and uses `caseid`, `activity`, `timestamp`, and `resource` after `format_dataframe`.

The role-discovery API returns **groups of resource names**, not an authoritative organizational chart or membership probabilities. The code therefore:

1. Tries several candidate numbers of roles.
2. Keeps selected memberships separate from validated authority metadata.
3. Counts case exposure once per resource–case pair.
4. Joins complexity and temporary-substitution indicators without counting repeated events as extra cases.
5. Treats networks and similarity as explanatory evidence, not reporting relationships.

```python
import pandas as pd
import networkx as nx
import pm4py

# ------------------------------------------------------------
# 1. Load and format the event log
# ------------------------------------------------------------

RAW_CASE = "case:concept:name"
RAW_ACTIVITY = "concept:name"
RAW_TIME = "time:timestamp"
RAW_RESOURCE = "org:resource"
RAW_COMPLEXITY = "case_complexity"
RAW_TEMP = "temporary_substitution"

required = {
    RAW_CASE, RAW_ACTIVITY, RAW_TIME, RAW_RESOURCE,
    RAW_COMPLEXITY, RAW_TEMP
}

raw = pd.read_csv(
    "service_events.csv",
    dtype={RAW_CASE: str, RAW_ACTIVITY: str, RAW_RESOURCE: str}
)

missing = required - set(raw.columns)
if missing:
    raise ValueError(f"Missing columns: {sorted(missing)}")

raw[RAW_TIME] = pd.to_datetime(raw[RAW_TIME], utc=True)
raw = raw.sort_values(
    [RAW_CASE, RAW_TIME, RAW_RESOURCE], kind="stable"
).reset_index(drop=True)

# Normalize the identifier, activity, timestamp, and resource columns.
# Original attributes are retained by format_dataframe.
df = pm4py.format_dataframe(
    raw,
    case_id=RAW_CASE,
    activity_id=RAW_ACTIVITY,
    timestamp_key=RAW_TIME,
    resource_key=RAW_RESOURCE
)

# Keys produced by format_dataframe in this PM4Py-style schema.
CASE = "caseid"
ACTIVITY = "activity"
TIME = "timestamp"
RESOURCE = "resource"

df = df.sort_values(
    [CASE, TIME], kind="stable"
).reset_index(drop=True)

# ------------------------------------------------------------
# 2. Validate and attach case-level context
# ------------------------------------------------------------

# This example assumes case_complexity is constant within a case.
# If it changes over time, its timestamp semantics must be resolved first.
complexity_variants = raw.groupby(RAW_CASE)[RAW_COMPLEXITY].nunique(
    dropna=False
)
if (complexity_variants > 1).any():
    raise ValueError(
        "case_complexity changes within a case; define its temporal meaning "
        "before joining it as a case-level attribute."
    )

if raw[RAW_COMPLEXITY].isna().any():
    raise ValueError("Resolve missing case_complexity values first.")

case_complexity = raw.groupby(RAW_CASE)[RAW_COMPLEXITY].first()
df[RAW_COMPLEXITY] = df[CASE].map(case_complexity)

# Explicitly normalize temporary_substitution to actual booleans.
temp_text = raw[RAW_TEMP].astype("string").str.strip().str.lower()
if not temp_text.isin(["true", "false"]).all():
    raise ValueError(
        "Normalize temporary_substitution to true/false before this example."
    )
df[RAW_TEMP] = temp_text.eq("true")

# A case-level flag is useful for slicing, but does NOT mean every
# event in that case was performed by a temporary substitute.
df["case_any_substitution"] = (
    df.groupby(CASE)[RAW_TEMP].transform("any")
)

# If available, separately load absence episodes with:
# absent_resource, covering_resource, start_time, end_time, reason.
# Do not infer the absent person from the covering resource's job title.

# ------------------------------------------------------------
# 3. Discover candidate organizational roles at several k
# ------------------------------------------------------------

K_VALUES = (4, 5, 6, 7)       # Illustrative sensitivity values
SELECTED_K = 5               # Not an assertion that five is correct

role_candidate_rows = []

for k in K_VALUES:
    groups = pm4py.discover_organizational_roles(
        df,
        num_roles=k
    )

    for role_id, members in enumerate(groups):
        for resource in sorted(members):
            role_candidate_rows.append({
                "candidate_k": k,
                "role_id": role_id,
                "resource": resource
            })

role_candidates = pd.DataFrame(role_candidate_rows)

selected_roles = role_candidates.loc[
    role_candidates["candidate_k"].eq(SELECTED_K),
    ["role_id", "resource"]
].copy()

# Check membership stability across k before interpreting roles.
# Stability means comparative co-membership across candidate partitions.
# It is not a measure of authority or statistical confidence.
membership_by_k = role_candidates.pivot(
    index="resource",
    columns="candidate_k",
    values="role_id"
)
print(membership_by_k)

# ------------------------------------------------------------
# 4. Inspect activity-profile similarity
# ------------------------------------------------------------

activity_similarity_records = (
    pm4py.discover_activity_based_resource_similarity(
        df,
        method="cosine",
        resource_key=RESOURCE
    )
)

activity_similarity = pd.DataFrame.from_records(
    activity_similarity_records,
    columns=["resource_1", "resource_2", "similarity"]
)

print(activity_similarity.sort_values(
    "similarity", ascending=False
))

# The exact scores depend on the representation and preprocessing.
# To reproduce the question's normalized-count cosine calculation,
# use the same L1 row normalization and activity count definition.
#
# Also repeat similarity analysis within complexity, product, and
# customer-segment slices. A high overall score can hide very
# different high/critical exposure.

# ------------------------------------------------------------
# 5. Build handover and working-together networks
# ------------------------------------------------------------

handover_graph = pm4py.discover_handover_of_work_network(
    df,
    resource_key=RESOURCE
)

together_graph = pm4py.discover_working_together_network(
    df,
    resource_key=RESOURCE
)

def edges_to_frame(graph, network_name):
    edges = nx.to_pandas_edgelist(graph)
    if edges.empty:
        return pd.DataFrame(
            columns=["resource", "target_resource", "weight", "network"]
        )

    return (
        edges.rename(columns={
            "source": "resource",
            "target": "target_resource"
        })
        .assign(network=network_name)
    )

handover_edges = edges_to_frame(handover_graph, "handover")
together_edges = edges_to_frame(together_graph, "working_together")

# Handover direction means work routing within cases, not reporting.
# Working-together edges mean co-occurrence, not necessarily joint
# execution, communication, or agreement.

# ------------------------------------------------------------
# 6. Create case/resource exposure data
# ------------------------------------------------------------

# IMPORTANT:
# Do not aggregate raw event rows into caseloads. A ten-event case
# must not count as ten cases. Temporary flags are resolved to the
# case first so that True/False event rows cannot duplicate exposure.

resource_case = (
    df[[
        CASE,
        RESOURCE,
        RAW_COMPLEXITY,
        "case_any_substitution"
    ]]
    .drop_duplicates()
)

resource_profile = (
    resource_case.groupby(RESOURCE)
    .agg(
        touched_cases=(CASE, "nunique"),
        temporary_case_touches=("case_any_substitution", "sum")
    )
)

# Support either categorical complexity or a numeric case score.
if pd.api.types.is_numeric_dtype(resource_case[RAW_COMPLEXITY]):
    resource_profile["median_case_complexity"] = (
        resource_case.groupby(RESOURCE)[RAW_COMPLEXITY].median()
    )
else:
    complexity_counts = pd.crosstab(
        resource_case[RESOURCE],
        resource_case[RAW_COMPLEXITY]
    )

    allowed_levels = {"Low", "Medium", "High", "Critical"}
    unexpected = set(complexity_counts.columns) - allowed_levels
    if unexpected:
        raise ValueError(
            f"Unexpected complexity levels: {sorted(unexpected)}"
        )

    resource_profile = resource_profile.join(complexity_counts)

    high = resource_profile.get(
        "High", pd.Series(0, index=resource_profile.index)
    )
    critical = resource_profile.get(
        "Critical", pd.Series(0, index=resource_profile.index)
    )

    resource_profile["high_or_critical_touch_share"] = (
        (high + critical) / resource_profile["touched_cases"]
    )

# ------------------------------------------------------------
# 7. Enrich candidate memberships with complexity/substitution data
# ------------------------------------------------------------

# Import a separately validated roster if available.
# roster = pd.read_csv("validated_resource_roster.csv")
# It should contain resource, home_role, certifications,
# approval_rights, and backup_eligible—not values inferred from counts.

role_resource = selected_roles.merge(
    resource_profile.reset_index(),
    on=RESOURCE,
    how="left",
    validate="one_to_one"
)

# Add activity counts only as a descriptive comparison.
# They should not determine membership or authority.
activity_counts = (
    pd.crosstab(df[RESOURCE], df[ACTIVITY])
    .reset_index()
    .rename(columns={RESOURCE: "resource"})
)

role_resource = role_resource.merge(
    activity_counts,
    on="resource",
    how="left",
    validate="one_to_one"
)

role_resource["authority_status"] = (
    "Unverified: inspect sign-off, delegation, certification, "
    "and outcome evidence"
)

role_summary = (
    role_resource.groupby("role_id")
    .agg(
        members=(RESOURCE, lambda s: ", ".join(sorted(s))),
        member_count=(RESOURCE, "nunique"),
        # These are member-case exposures, not unique organization cases.
        member_case_exposures=("touched_cases", "sum"),
        temporary_case_exposures=(
            "temporary_case_touches", "sum"
        )
    )
)

role_summary["authority_status"] = (
    "Not established by role mining or event frequency"
)

print(role_resource.sort_values("role_id"))
print(role_summary)
print(handover_edges.sort_values("weight", ascending=False))
print(together_edges.sort_values("weight", ascending=False))

# ------------------------------------------------------------
# 8. Recommended robustness checks, not automatic conclusions
# ------------------------------------------------------------
```

A useful evidence hierarchy is:

1. **Assignment and outcome evidence:** who was accountable, who executed, and what happened.
2. **Context:** complexity, product, customer segment, and whether a referral was necessary.
3. **Behavioral similarity:** similar activities and networks.
4. **Frequency:** useful for workload, but weakest as evidence of authority or competence.

# 6. Operational interpretation

## Staffing

- **Front office:** Use event volume, simple-case demand, and service-time measures for capacity planning, but distinguish bot intake from human workload. The temporary pool can support predictable low-complexity demand; it should not be treated as a permanent source of critical-case expertise.
- **Technical team:** Preserve Chen and Dina as a shared technical capability while using complexity- and complexity-adjusted outcomes to assign critical work. A gradual critical-case development plan is more defensible than assuming the more experienced resource should automatically receive every difficult case.
- **Security:** Protect sufficient specialist capacity and avoid filling the role with routine work merely to increase utilization. The two critical waits during referral filtering warrant investigation of triage quality, queue delay, and specialist availability.
- **Quality:** Staff for both review throughput and knowledge stewardship. Verify whether quality work is concentrated by activity, shift, or case type rather than assuming Ivan and Julia are interchangeable.
- **Automation:** Do not translate Nora’s event count into human staffing demand. Instead, budget for automation monitoring, exception handling, and human fallback capacity.

## Training and competence

- Introduce an explicit **entitlement-note quality standard** for temporary and permanent front-office staff. Bot prechecks do not necessarily capture the explanatory information needed for later diagnosis or rework.
- Pair technical analysts on security-adjacent and critical cases to develop redundant expertise, while retaining clear ownership of the final technical decision.
- Give Giorgio broader commercial experience through a formal development path, but validate pricing and negotiation authorization independently of successful absence coverage.
- Train Mateo in escalation thresholds, security-referral criteria, and the distinction between preparing and authorizing a decision.
- Establish formal backup arrangements for security review and supervisor approval. Delegation should be time-bounded and auditable; it should not be inferred from a few event counts.

## Risk control

- Use reopen rates, incomplete validation notes, security-related delays, and quality-check outcomes as risk indicators—not just event volume.
- Introduce stronger pre-close sampling for low-complexity temporary work while investigating whether the 17 reopens reflect training, workflow design, missing context, or broader process issues.
- Record both the actor and the final approver for A7, A9, and security-sensitive implementation events. This would eliminate much of the ambiguity between preparation, review, and authorization.
- Treat critical security queues and approval queues as distinct controls. A reduction in false referrals is beneficial only if critical-case delay does not become unacceptable.
- Feed recurring validation and escalation failures into the knowledge-base process so that quality work also prevents recurrence.

## Resilience and shadow-role governance

Use a validated skill matrix rather than a mined role label to select substitutes. Each critical boundary should have:

- a primary owner and formally authorized backup;
- documented minimum case complexity for independent work;
- training and periodic reassessment;
- clear provisional-versus-final decision markers;
- an escalation route when the primary or backup is unavailable.

Giorgio’s commercial shadow work can be valuable continuity and cross-skilling. Mateo’s brokerage can make escalation efficient. Erik’s rare interventions can prevent high-risk changes from receiving routine treatment. The governance objective is to make these contributions explicit and reviewable, not to force everyone into a single permanent cluster or to discourage secondary responsibilities.

## Cautions before changing staffing

1. **Activity clusters are not formal authority.** A9 participation can include preparation, as demonstrated by Mateo’s preliminary decisions. Decision metadata, delegation rules, and outcome audits are needed before changing approval authority.
2. **Frequency does not measure competence or capacity.** Nora dominates event volume through automation; Kai and Lina have high activity but low-complexity assignments. Conversely, Erik and Hana have lower volumes but much higher risk exposure.
3. **Similar profiles hide different risk.** Chen/Dina and Ivan/Julia have high similarity but different case portfolios. Hana/Mateo and Erik/Mateo also show why coordination, approval, and specialist work should not be merged merely because they occur in escalated cases.
4. **Observational evidence does not establish causation.** The security filtering episode coincides with both fewer false escalations and two critical delays; it does not prove that either outcome was caused solely by Mateo’s decisions.
5. **Temporary performance is not permanent certification.** The temporary closure episode warrants remediation and controlled permissions, but not an inference about the employees’ long-term potential or a permanent transfer of specialist responsibilities.
