## 2. Rawversusnormalized interpretation  

The raw fitness (0.92–0.55) reflects poor alignment between the observed event log and the historical normative model before migration, primarily because `Validate Eligibility` was renamed to `Eligibility Screen` and `Open Case` was duplicated or omitted in many traces. Mapping these labels and eliminating duplicated `Open Case` events restores alignment—mapped fitness approaches the premigration values (0.88–0.92). This shows that much of the early fitness drop was **provenance/semantic logging drift** rather than genuine behavior change.  

Duplicated technical events inflate the path count for `Open Case  Register` and cause phantom transitions in the DFG, obscuring true controlflow. Missing resource identifiers (5% of cases) further fragment trace completion, yet they are concentrated in migrated activities, suggesting a systemic datacapture issue rather than random noise.  

Even after correction, performance metrics (median cycle time, rework rates) deteriorate postMay, indicating **real behavioral drift** (supplier disruption, staffing cuts) and **casemix drift** (more complex, highervolume cases). The postJuly priority rule’s impact on queue waiting and senior assessment usage cannot be explained solely by logging; servicetime decomposition shows a large queueing component that grew alongside the new assessment ordering, underscoring genuine process adaptation rather than mere label artifacts.  

Thus, while label mapping recovers conformance, it does **not** guarantee unchanged business logic; it merely aligns observed events to the expected vocabulary. Subsequent performance degradation signals genuine changes in resource utilization, service flow, and case characteristics that persisted beyond the migration artifact.

## 6. Segmentation plan  

| segment level | variables | purpose | minimum support rule | comparisons enabled | risk of conditioning bias |
|---------------|-----------|---------|----------------------|---------------------|---------------------------|
| **Process** | `activity`, `case_id`, `timestamp` | Core event flow (RegisterEligibilityCollectAssessDecision) |  5 cases per segment | Controlflow, variant detection | Minimal – reflects true process |
| **Supplier** | `supplier_id`, `case_id` | Isolate SupplierZ behavior, incomplete bundles |  30 cases per month | Rework, cycletime vs supplier | Supplier bias if dataset unbalanced |
| **Complexity** | `complexity_flag`, `case_id` | Separate high vs standardcomplexity cases |  20 highcomplexity cases per month | Performance vs complexity | May miss lowcomplexity edge cases |
| **Staffing** | `staff_id`, `case_id` (derived from assessor assignment) | Capture redistribution effects |  10 cases per staffing cluster | Queue waiting vs staff count | Staffing attribution uncertainty |
| **Priority** | `priority_flag`, `case_id` | Identify highpriority cases routed to Senior Assessment |  15 prioritized cases per month | Senior vs standard assessment usage | Priority flag may be inconsistently applied |
| **Seasonality** | `month`, `case_id` | Capture renewal season effects |  50 cases per month | Volume, complexity, cycletime trends | Seasonal bias if other annual cycles exist |

**Primary monitoring population**: **Processlevel segment** (all cases). It provides the broadest view of drift while still allowing refined subgroup comparisons (supplier, complexity, etc.). Keeping the primary population at the full event log avoids underrepresentation of subtle but organizationwide drifts, especially given the migration and staffing impacts that affect all cases.

**Handling seasonality & multiple testing**:  
- Apply **seasonal decomposition** to all timeseries before comparison, removing the seasonal component.  
- Use **Bonferroni correction** or **false discovery rate** across the ten monitors to control familywise error.  
- For monitors intrinsically seasonal (e.g., case mix), flag only **aberrant deviations** beyond 1.5× the seasonal amplitude.

# Part B: Reusable PM4Py functions for eventlevel analysis
import pm4py
from pm4py.objects.log.importer.xes import factory as xes_importer
import pandas as pd

def prepare_event_log(df):
    """Format DataFrame to PM4Py-compatible format."""
    # Ensure columns: event, case_id, timestamp
    required = ['case_id', 'event', 'timestamp']
    assert all(col in df.columns for col in required), "Missing required columns"
    return df[required].copy()

def slice_time_window(log, start, end):
    """Filter log to a specific time window."""
    return log[(log['timestamp'] >= start) & (log['timestamp'] <= end)]

def discover_dfg(log):
    """Discover a business process DFG."""
    return pm4py.discover_dfg(log, parameters={"variant": "alpha-miner"})

def get_variants(log):
    """Extract variants (sorted activity sequences)."""
    return pm4py.get_variants(log, parameters={"type": "sequence"})

def discover_temporal_profile(log):
    """Obtain temporal profile (frequency of transitions over time)."""
    return pm4py.discover_temporal_profile(log, parameters={"granularity": "hour"})

def apply_label_mapping(log, mapping):
    """Map activity names according to a provided dictionary without overwriting original log."""
    log_mapped = log.copy()
    log_mapped['event'] = log['event'].map(mapping)
    return log_mapped

# Example reusable skeleton (not executed here)
def event_log_analysis(raw_df, mapping=None):
    log = prepare_event_log(raw_df)
    # Mapping step (optional)
    if mapping is not None:
        log = apply_label_mapping(log, mapping)
    # Slice a window (e.g., July 2026)
    july_log = slice_time_window(log, '2026-07-01', '2026-07-31')
    dfg = discover_dfg(july_log)
    variants = get_variants(july_log)
    temporal_profile = discover_temporal_profile(july_log)
    return dfg, variants, temporal_profile

## 9. Provisional attribution  

The March system migration primarily explains the abrupt rawfitness collapse (evidence strength85) via logging/semantic drift—duplicate `Open Case` events and missing resource identifiers disrupted trace completeness. However, the fitness partially recovers after mapping, indicating that **label inconsistencies, not process behavior**, drove most of the observed disparity.  

Supplier disruption in early May introduces a **population/casemix drift** (evidence strength80) because SupplierZ’s incomplete bundles increased rework and rawfitness loss; the spike in fastvariant and rework percentages aligns with this mechanism. Staffing cuts on June15 generate a **controlflow/behavioral drift** (evidence strength78) reflected by a sharp rise in queue waiting and cycletime, corroborated by the seniorassessment surge.  

The priority rule enacted July1 instigates a **behavioral drift** (evidence strength75) that reorders highcomplexity cases, increasing seniorassessment usage and altering temporal profiles without changing the underlying activity set.  

Seasonal renewal beginning October1 manifests as a **recurring/seasonal drift** (evidence strength90), raising highcomplexity share and overall volume, explaining the sustained increase in cycle time despite staffing mitigation efforts.  

Interaction among mechanisms is evident: the priority rule’s effect on queueing is observable **only after** staffing reductions, suggesting mediation (staffing  queue  priority impact). Supplierinduced rework persists **even after** recovery (September), hinting at **confounding** where prior incomplete data left lingering backlog effects.  

**Strongest conclusions**:  
- The March migration is chiefly a **logging drift**.  
- Supplier disruption is a **population/casemix drift** with real rework consequences.  
- Staffing cuts produce a **controlflow/behavioral drift** amplified by the priority rule.  
- Seasonal renewal is a **recurring drift** on top of the preceding mechanisms.  

**Plausible but less certain**: The exact proportion of queueing attributable to staffing vs priority rule cannot be cleanly separated without finergrained staffing attribution; a structural equation model would improve clarity.  

If additional data (e.g., assessor assignment logs) were available, it would sharpen the staffingqueue linkage and allow tighter quantification of the interaction effects, potentially revising the relative weight of each mechanism.  

## 10. Monitoring decision rules  

1. **IF raw_model_fitness falls below 0.88 for two consecutive months, THEN investigate label mapping completeness and duplicate `Open Case` events, BECAUSE a sudden drop is typical of logging drift postmigration.**  
2. **IF duplicate_open_case_pct > 4% for any month, THEN trigger a dataquality audit of the `Open Case` creation module, BECAUSE persistent duplicates indicate ongoing provenance issues.**  
3. **IF missing_resource_pct > 6% for a month, THEN flag all traces with incomplete resource IDs for reingestion, BECAUSE missing identifiers often accompany migration artifacts.**  
4. **IF rework_variant_pct rises > 5% above its 3month moving average, THEN flag the SupplierZ cohort for supplierlevel investigation, BECAUSE rework spikes align with incomplete bundles.**  
5. **IF median waiting time before Assess increases > 1hour relative to the 3month trend, THEN examine staffing levels and redistribution plan, BECAUSE queueing reflects controlflow/behavioral strain.**  
6. **IF senior_assessment_rate (AssessSeniorAssessment) exceeds 20% of total Assess events, THEN review the priority rule implementation for possible overprioritization, BECAUSE high senior usage signals behavioral drift from priority changes.**  
7. **IF high_complexity_pct > 40% for October–December each year, THEN treat as expected seasonal renewal, but if it exceeds 45% for two successive years, THEN flag potential underlying process deterioration, BECAUSE extreme seasonal spikes may signal interaction with staffing or supplier issues.**  

These rules balance early detection of artifactdriven drift (logging) with substantive behavioral and performance changes (staffing, supplier, priority), while explicitly accounting for seasonality and allowing for nuanced followup diagnostics.
