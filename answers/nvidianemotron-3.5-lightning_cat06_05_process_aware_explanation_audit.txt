## 2. Processmodel consistency checks  

A concrete validation suite should be built around five complementary test families. Each test can be automated (e.g., via Python/pandas, ProM, or custom scripts) and executed after any featureengineering or explanationgeneration change.

| Test | What it checks | Typical method | Limitations |
|------|----------------|----------------|-------------|
| **Prefixtime availability** | Guarantees that every feature value used in an explanation is present in the event log **at or before** t (the moment after the first `Coverage Check Completed`). | Load the event log up to t, then leftjoin the feature table. Flag any value that requires an event occurring **after** the t cutoff (e.g., `total_case_duration_hours`, `appeal_seen_anywhere`). | Requires a reliable t definition; if t varies per claim the test must be percase. |
| **Activityorder feasibility (DFG / prefix constraints)** | Verifies that the ordered sequence of activities in an explanation respects the normative process model (e.g., `Damage Assessment Completed` cannot precede `Coverage Check Completed`). | Build a DirectlyFollows Graph (DFG) from the full log; for each explanation, walk the prefix up to t and confirm that the next claimed activity is a reachable successor. Use “prefixconstrained” DFG to allow only states reachable from the current state. | DFG reflects observed behaviour, not strict business rules; rare but legitimate deviations may be flagged falsepositively. |
| **Sametimestamp ambiguity resolution** | Detects pairs or groups of events that share an ingestion timestamp but have an undefined execution order, which can corrupt “first/last” derivations. | Query the log for events with identical `timestamp` and no `sequence_index`; report them. In the validation suite, treat such groups as “unknown order” and either (a) require a deterministic tiebreaker (e.g., event type priority) or (b) exclude features that depend on the ordering. | If the source system never provides a reliable index, the only safe action is to mark the affected features as “unusable until timestamp disambiguation”. |
| **Completetrace vs. prefixonly feature provenance** | Flags any feature that is calculated from the **full case trace** (events after t) versus those that use only information available up to t. | For each top12 feature, trace its SQL or ETL definition. Mark as “completetrace” if any reference to events after the prediction cutoff exists (e.g., `num_document_requests_total`, `full_trace_variant_id`). | Some features may be “conditionally” completetrace (e.g., only if a certain subprocess has finished). Those need a secondary “conditional” check. |
| **Explanationactivity feasibility (enabled / impossible / futurepossible at t)** | For every local feature mentioned in a case explanation, classifies whether the underlying activity (e.g., “appeal”, “final decision”) is (i) **enabled** (already happened before t), (ii) **impossible** (cannot happen given the process state at t), or (iii) **futurepossible** (may happen later). | Map each activity to the process model states reachable from the prefix at t. If the activity’s required preceding event is absent  *impossible*; if present  *enabled*; otherwise  *futurepossible*. | This check is binary; nuanced states (e.g., “appeal started but not decided”) may need a threevalued logic or a probabilistic flag. |
| **Repeated `Settlement Decision Recorded` legitimacy after appeal** | Confirms that two `Settlement Decision Recorded` events are only semantically valid when the first is `Partial` or `Deny` and an `Appeal` has been recorded in between. | Parse the log for `Settlement Decision Recorded` events; verify that a second occurrence is preceded by an `Appeal` event and that the first decision was not `Approve` or `Withdrawn`. Flag any illegitimate doubledecision as a modelling error. | The rule relies on correct `Appeal` event tags; mislabeled appeals will cause false legitimacy judgments. |

**How to use the suite**

1. **Run prefixtime availability first** – any feature flagged here is immediately removed or repaired before proceeding.  
2. **Run activityorder feasibility** – ensures that any remaining feature respects the temporal ordering of the claim lifecycle.  
3. **Check sametimestamp groups** – resolve or discard features that depend on ordering of cotimed events.  
4. **Classify feature provenance** – keep only prefixonly features; reengineer or drop completetrace ones.  
5. **Classify explanation activities** – if an explanation claims an “impossible” activity, it must be removed or reframed as a “futurepossible” disclaimer.  
6. **Validate repeated settlement decisions** – prevents spurious “breachrisk” signals that arise from modelling the appealreconsideration loop incorrectly.  

A frequent DFG edge is **not** a normative rule; it merely reflects observed flow. Consequently, the validation suite should **augment** DFG checks with the explicit process steps listed in the normative process description, not replace them.

## 3. Alternative feature interpretations  

| Class | Features that fall here | What may be claimed | What must NOT be claimed |
|-------|------------------------|---------------------|--------------------------|
| **Defensible predictive signal** | `queue_length_at_t0`, `initial_damage_complexity`, `elapsed_since_registration_at_t0`, `initial_reserve` (if set at registration), `claimant_channel` (with fairness note) | • “Higher queue length at t is associated with a higher predicted breach probability.” <br>• “Claims with high initial damage complexity have higher risk.” <br>• “Longer elapsed registration time (up to t) slightly reduces risk.” | • Causal statements such as “queue length *causes* breach.” <br>• Claims that the feature can be *acted upon* before t (e.g., “reduce queue length to avoid breach”). |
| **Processstate or congestion signal** | `queue_length_at_t0` (also listed above), `elapsed_since_registration_at_t0` (age as a proxy for “how far we are in the process”) | • “Current congestion level is a reliable indicator of imminent delay.” | • That congestion is the *root cause* of breach; other concurrent factors may dominate. |
| **Proxy requiring fairness / robustness review** | `claimant_region`, `claimant_channel`, `calendar_week`, `same_day_document_count_snapshot` (if not fully timestamprestricted) | • “RegionR4 shows a statistically higher breach rate, warranting a fairness audit.” <br>• “Calendar week52 aligns with a known policy change; model performance should be monitored during that week.” | • “RegionR4 *causes* longer settlement times.” <br>• Using the proxy to *optimise* operations without a biasmitigation plan. |
| **Drift / calendar proxy** | `calendar_week` (also in proxy class) | • “Model predictions shift in week52; this may reflect operational drift rather than claimintrinsic factors.” | • “Week52 is inherently ‘bad’ for all claims.” |
| **Unusable until lineage is repaired** | `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `num_document_requests_total`, `full_trace_variant_id`, `prior_claim_count_before_t0`, `same_day_document_count_snapshot` (if not restricted), `risk_score_current`, `last_resource_role` | • *None* until the ETL/sourcing defect is fixed. | • Any predictive or causal claim based on the raw, unrepaired value. |

**Key takeaway:**  
- **Predictive validity** only requires that the feature be *available* at t and *processconsistent* (i.e., not a future outcome).  
- **Causal or actionable interpretation** is never justified solely by SHAP importance; it must be backed by a mechanistic model or experimental evidence.  
- **Fairness/sensitivity** must be explicitly flagged for any feature that correlates with protected attributes (region, channel, etc.), even if the feature is otherwise legitimate.  
- **Lineage defects** (SQL bugs, missing timestamps, nightly refreshes) render a feature *unusable* for explanation until the datapipeline is corrected; the audit should mandate a remediation ticket, not a blanket exclusion.

## 5. Recommendations for explanation validation (prioritized plan)

| # | Recommendation | Why it matters | Suggested implementation |
|---|----------------|----------------|------------------------|
| **1** | **Featurestore design with eventtime stamps** – store every derived feature together with the timestamp of the last source event it depends on. | Guarantees that a feature can be queried “as of t” and instantly flagged if it needs later data. | Add a `feature_timestamp` column to the feature table; ETL jobs must populate it from the originating event’s `event_time`. |
| **2** | **Historical feature timestamps** – keep a timeindexed snapshot of every mutable attribute (e.g., `risk_score_current`, `final_handler_team`, `queue_length`). | Enables “prefixonly” recomputation and resolves the mutablelineage problem. | Use a changedatacapture (CDC) pipeline or periodic pointintime dumps; version the feature values per claim. |
| **3** | **Prefixonly recomputation routine** – a scheduled job that, for each claim, extracts all SHAPrelevant features **as they exist at the moment right after the first `Coverage Check Completed`**. | Guarantees that explanations never implicitly use future outcomes. | Define a cutoff view (`log_up_to_t0`) and materialise the feature set there; compare against the fulltrace version to surface drift. |
| **4** | **Processconformance tests** (prefixDFG, activityorder, sametimestamp checks) integrated into the CI pipeline. | Catches leakage and ordering bugs before they reach modelexplanation code. | Automate the five test families from Section2; fail the build if any “critical” finding appears. |
| **5** | **Calibration after feature removal** – recalibrate model probabilities (or SHAP values) after each set of leaked features is pruned. | Prevents systematic over or underconfidence that can arise when highimportance leakage is removed. | After each remediation cycle, run a holdout set evaluation; adjust calibration ( Platt scaling, isotonic) as needed. |
| **6** | **Explanation stability monitoring** – track SHAP contribution rankings over sliding windows (e.g., weekly). | Detects when the model starts relying on newlyadded or drifted features. | Plot rank trajectories; trigger a review if a feature enters the top5 that was previously absent or severity changes. |
| **7** | **Proxy / fairness analysis** – formal audit for any feature that correlates with region, channel, or calendar week. | Meets ethical and regulatory obligations; avoids hidden bias in operational decisions. | Use demographic parity, equalized odds checks on the subset of claims where the feature is active; document findings and mitigation steps. |
| **8** | **Monitoring for schema or process drift** – alert when the normative process (e.g., addition of a new evidence cycle, change in fraudinvestigation trigger) deviates from the stored model assumptions. | The claimprocessing landscape evolves; stale explanations become misleading. | Subscribe to changemanagement tickets; automatically run the validation suite (Section2) whenever a processchange ticket is merged. |

**Implementation roadmap (highlevel)**  

1. **Month1** – Add `feature_timestamp` to the data warehouse; run a oneoff audit of the top12 features to tag each as “timestamped” or “missing”.  
2. **Month2** – Build the prefixonly recomputation job; validate against a sample of 200 claims that manually trace the process up to t.  
3. **Month3** – Deploy the validationsuite CI checks; fix the identified lineage defects (`prior_claim_count_before_t0`, `same_day_document_count_snapshot`, sametimestamp pairs).  
4. **Month4** – Conduct fairness audits on `claimant_region`, `claimant_channel`, `calendar_week`; document remediation or deprovisioning decisions.  
5. **Month5** – Recalibrate the model after each remediation cycle; record calibration metrics.  
6. **Ongoing** – Weekly monitoring of SHAPrank stability; monthly driftalert review; quarterly fullprocessconformance audit.  

Following this plan will ensure that every explanation reported to underwriters, investigators, or regulators is **temporally consistent**, **processaware**, and **free of hidden leakage**, while still preserving the legitimate predictive signals that the model has learned from the available data up to the prediction moment.
