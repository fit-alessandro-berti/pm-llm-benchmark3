# OCEL 2.0 Retail Order Process: Complete Construction and Analysis

## 1. Modeling Assumptions

### Object Types and Capitalization
- **Order**: O100, O200  
- **Item**: I1, I2, I3  
- **Package**: P1, P2  
- **Delivery**: D1, D2  
- **Invoice**: V1  
- **Payment**: M1, M2  

All capitalized as shown; types stored as singular nouns (e.g., "Order", "Item").

### E2O Qualifier Vocabulary
- **source**: Order/Item is the originating document or entity for the event.  
- **affects**: Event modifies the state of an object but is not definitionally owned by it (e.g., a dispatch affects a Package).  
- **references**: Event logically concerns an object without direct operational change (e.g., a reserve-stock event references Items).  
- **billable_on**: Invoice relates to Orders that contain billable items.  
- **settled_by**: Invoice relates to Payments that settle it.  

### O2O Direction Conventions
- **Order  contains  Item**: indicates Orders house Items.  
- **Package  packs  Item**: indicates Packages contain Items.  
- **Delivery  carries  Package**: indicates Deliveries transport Packages.  
- **Invoice  bills  Order**: Invoice issued against Orders.  
- **Payment  partially_settles  Invoice** or **completes_settlement  Invoice**: hierarchical payment settlement.  

### Logistics and Financial Events' Relation to Orders and Items
**Policy: Direct source + operational propagation**

- **Creation and lifecycle events** (Create Order, Add Item, Pack, Dispatch, Deliver, Issue Invoice, Close Order) are directly related to their primary objects via "source" or "affects" qualifiers.  
- **Shared operational events** (Reserve Stock, Pack P1, Dispatch D1) are related to *all* Orders and Items involved, using the "references" qualifier.  
- **Payment events** are related to the Invoice they settle, not directly to Orders, to avoid double-counting; analytical queries can follow O2O chains if needed.  

**Trade-off**: Direct source relations anchor each event to at least one primary object; propagated relations (e.g., Pack P1  O100, O200 via Item membership) make shared events visible in per-Order flattening but can inflate trace length. We include both to support flexible analysis; code comments note where propagation occurs.

### Preventing Analytical Propagation Confusion
- Relations table includes a **derivation** column (informational, not mandatory) marking whether a relation is "source" or "propagated".  
- Comments in code clarify when O2O chains are traversed for analysis vs. when E2O relations are read directly.  
- Flattened logs are validated to show which events appear multiple times due to propagation.

### PM4Py Version Assumption
Code assumes PM4Py  2.7.9 with `pm4py.ocel_*` and `pm4py.discover_*` (OC-DFG, OTG, ETOT, OC Petri net) functions. If version differs:
- Replace `OCEL(...)` with `ocel_object_from_df(...)` or check `pm4py.__version__`.  
- Replace `discover_ocdfg`, `discover_otg`, `discover_etot`, `discover_oc_petri_net` with fallbacks or custom implementations.  
- All data-frame construction is PM4Py-agnostic.

relations_data.append(("E003", "Add Item", datetime(2026, 4, 6, 8, 6, tzinfo=tz), "I2", "Item", "source", "source"))

relations_data.append(("E004", "Create Order", datetime(2026, 4, 6, 8, 10, tzinfo=tz), "O200", "Order", "source", "source"))

relations_data.append(("E005", "Add Item", datetime(2026, 4, 6, 8, 12, tzinfo=tz), "I3", "Item", "source", "source"))

relations_data.append(("E006", "Reserve Stock", datetime(2026, 4, 6, 8, 30, tzinfo=tz), "I1", "Item", "references", "source"))

# E007: Pack Package P1 with I1 and I3 (shared event)

relations_data.append(("E007", "Pack Package", datetime(2026, 4, 6, 9, 0, tzinfo=tz), "P1", "Package", "source", "source"))

relations_data.append(("E007", "Pack Package", datetime(2026, 4, 6, 9, 0, tzinfo=tz), "I3", "Item", "references", "source"))

relations_data.append(("E008", "Pack Package", datetime(2026, 4, 6, 9, 5, tzinfo=tz), "P2", "Package", "source", "source"))

relations_data.append(("E009", "Dispatch Package", datetime(2026, 4, 6, 10, 0, tzinfo=tz), "O100", "Order", "affects", "propagated"))
relations_data.append(("E009", "Dispatch Package", datetime(2026, 4, 6, 10, 0, tzinfo=tz), "O200", "Order", "affects", "propagated"))

relations_data.append(("E010", "Dispatch Package", datetime(2026, 4, 6, 10, 15, tzinfo=tz), "O100", "Order", "affects", "propagated"))

relations_data.append(("E011", "Issue Invoice", datetime(2026, 4, 6, 11, 0, tzinfo=tz), "V1", "Invoice", "source", "source"))

relations_data.append(("E013", "Confirm Delivery", datetime(2026, 4, 6, 13, 0, tzinfo=tz), "D1", "Delivery", "source", "source"))
relations_data.append(("E013", "Confirm Delivery", datetime(2026, 4, 6, 13, 0, tzinfo=tz), "P1", "Package", "affects", "propagated"))
relations_data.append(("E013", "Confirm Delivery", datetime(2026, 4, 6, 13, 0, tzinfo=tz), "O100", "Order", "affects", "propagated"))
relations_data.append(("E013", "Confirm Delivery", datetime(2026, 4, 6, 13, 0, tzinfo=tz), "O200", "Order", "affects", "propagated"))

relations_data.append(("E014", "Confirm Delivery", datetime(2026, 4, 7, 9, 0, tzinfo=tz), "D2", "Delivery", "source", "source"))

relations_data.append(("E015", "Record Payment", datetime(2026, 4, 7, 10, 0, tzinfo=tz), "M2", "Payment", "source", "source"))

assert len(orphan_oids_o2o) == 0, f"Orphan object IDs in o2o: {orphan_oids_o2o}"

# Check activity/timestamp consistency
for idx, row in relations.iterrows():
    event_row = events[events["ocel:eid"] == row["ocel:eid"]].iloc[0]
    assert row["ocel:activity"] == event_row["ocel:activity"], \
        f"Activity mismatch for {row['ocel:eid']}: {row['ocel:activity']} vs {event_row['ocel:activity']}"

        f"Timestamp mismatch for {row['ocel:eid']}"
print(f" Activity/timestamp consistency in relations")

# Check no duplicate relation rows
relation_cols = ["ocel:eid", "ocel:oid", "ocel:qualifier"]

## 4. Expected Flattened Behavior

### Order Flattening

**Approximate Trace Shape:**  
`Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Dispatch Package  Confirm Delivery  Issue Invoice  Record Payment  Record Payment  Close Order`

**Example for O100:**
- E001, E002, E003, E006 (shared), E007 (shared), E008, E009 (shared?), E010, E011 (shared), E012, E015, E017

**Copied Shared Events:**
- E006 (Reserve Stock) appears in both O100 and O200 traces.
- E007 (Pack P1) appears in both traces.
- E009 (Dispatch D1) and E013 (Confirm D1) propagated to both Orders.
- E011 (Issue Invoice) appears in both traces.

**Omitted Lifecycle Aspects:**
- Payment details (amounts) not in flattened event attributes (depends on PM4Py version).
- Package internal state not visible; only Pack and Dispatch events matter.
- O2O relationships not preserved in flat trace; analyst must refer to original o2o table.

**Likely DFG Edges (per Order):**
- Create Order  Add Item  Add Item  Reserve Stock  Pack Package (likely two packing events for O100: E007, E008)
- Dispatch Package  Confirm Delivery  Issue Invoice
- Issue Invoice  Record Payment  Record Payment
- Record Payment  Close Order

**Misleading Interpretations:**
1. **Double-counting of shared events:** E006, E007 appear twice, suggesting Orders are more independent than they are.
2. **Overly sequential traces:** Parallel packing (P1 and P2) and dispatch (D1 and D2) may appear serial if timestamp ordering is tight.
3. **Payment merging:** Both M1 and M2 appear as two distinct Record Payment events in O100 trace; unclear which payment settles O100 vs. O200.
4. **Missing item-to-package mapping:** Flattening by Order loses visibility of which items went into which package.

### Package Flattening

**Approximate Trace Shape:**  
`Pack Package  Dispatch Package  Confirm Delivery`

**Example for P1:**
- E007, E009, E013

**Copied Shared Events:**
- P1 is packed once (E007), dispatched in D1 (E009), confirmed in D1 (E013). No true sharing from Package perspective.
- P2 is packed once (E008), dispatched in D2 (E010), confirmed in D2 (E014). Similarly isolated.

**Omitted Lifecycle Aspects:**
- Item packing sequence lost; PM4Py flattening does not reconstruct which items were added to the package.
- Order ownership of items not preserved; only the Package itself is visible.

**Likely DFG Edges:**
- Pack Package  Dispatch Package  Confirm Delivery (linear)

**Misleading Interpretations:**
1. **Over-simplification:** Package flattening is too short (3 events max) to reveal meaningful patterns.
2. **Missing multi-item aggregation:** P1 contains two items from two Orders, but the flattened trace shows no branching.

### Delivery Flattening

**Approximate Trace Shape:**  
`Dispatch Package  Confirm Delivery`

**Example for D1:**
- E009, E013

**Copied Shared Events:**
- D1 dispatches P1 (E009), then confirms (E013). No shared events.
- D2 dispatches P2 (E010), then confirms (E014). No shared events.

**Omitted Lifecycle Aspects:**
- Package contents (Items, Orders) are not visible.
- Dispatch and confirmation are atomic from Delivery's view; no intermediate states.

**Likely DFG Edges:**
- Dispatch Package  Confirm Delivery (linear)

**Misleading Interpretations:**
1. **Minimal trace:** Only two activity types per Delivery. No discrimination of process anomalies.
2. **Delivery delays hidden:** Delivery D2 is confirmed one day after dispatch, but flattening does not flag this as exceptional.

---

### Invoice Flattening

**Approximate Trace Shape:**  
`Issue Invoice  Record Payment  Record Payment  (implicitly settled)`

**Example for V1:**
- E011, E012, E015

**Copied Shared Events:**
- None; V1 is a single object.

**Omitted Lifecycle Aspects:**
- Order itemization not captured.
- Payment amounts are in events but may not propagate to flattened log depending on PM4Py version.
- Settlement status (partially vs. completed) only inferred from qualifier interpretation, not explicit in trace.

**Likely DFG Edges:**
- Issue Invoice  Record Payment  Record Payment (linear)

**Misleading Interpretations:**
1. **Ambiguous payment sequence:** Two Record Payment events appear with no indication that M1 is partial and M2 is final.
2. **No invoice-order link:** Invoice flattening does not reveal that V1 bills O100 and O200; analyst must cross-reference o2o.

---

### Why Flattening on Payment is Weak

**Payment objects (M1, M2) are ephemeral:**
- Each Payment appears in only two events: creation (Record Payment) and settlement reference (Record Payment again, same event).
- Payment traces would be trivial: `Record Payment` (single-event traces).
- No lifecycle: Payments do not precede or follow other activities; they are purely financial records attached to Invoices.
- **Result:** Payment flattening yields zero DFG edges and one-node DFG per Payment. No process discovery is possible.

## 6. Modeling Alternatives

### Alternative A: Source-Minimal Relations

**Policy:** E2O relations only for directly owned/created objects; no propagation.

**Implication:**
- E006 (Reserve Stock) relates only to I1, I3; not to O100, O200.
- E007 (Pack P1) relates only to P1; Item relations omitted unless they are the *source* of the event.
- E009 (Dispatch D1) relates to D1 only; Orders not mentioned.
- E011 (Issue Invoice) relates to V1 only; Orders omitted unless modeled as "subject" of billing.

**Discovery Impact:**
- **OC-DFG**: Sparser, fewer convergence edges. Reserve Stock and Issue Invoice appear isolated.
- **Flattening by Order**: Traces are shorter but fragmented; missing intermediate logistics events. E006, E007 do not appear in O100 trace at all.
- **Analysis Use Case**: Better for isolating true source-system ownership; less suitable for end-to-end process mining.

**Trade-off:** Simpler model, less inflation, but loses visibility of shared operations.

---

### Alternative B: Full Operational Involvement

**Policy:** E2O relations for all objects operationally touched by the event, with no distinction between source and derived.

**Implication:**
- E006 (Reserve Stock) relates to I1, I3, O100, O200, P1, P2 (all objects downstream of these Items).
- E007 (Pack P1) relates to P1, I1, I3, O100, O200 (full causal closure).
- E009 (Dispatch D1) relates to D1, P1, I1, I3, O100, O200 (full closure).
- E011 (Issue Invoice) relates to V1, O100, O200, I1, I2, I3 (via billing Orders that contain these Items).

**Discovery Impact:**
- **OC-DFG**: Denser, more edges, but harder to interpret (noise).
- **Flattening by Order**: Traces include all upstream and downstream events, creating strong coupling. O100 and O200 traces become nearly identical.
- **Analysis Use Case**: Suitable for detecting all operational interdependencies; risk of over-fitting.

**Trade-off:** Comprehensive but noisy; can obscure causal structure.

---

### Alternative C: O2O-Propagated Analytical Relations

**Policy:** E2O relations contain only source links; propagation is *computed on-the-fly* by following O2O edges.

**Implication:**
- E006 (Reserve Stock) relates to I1, I3 only (source).
- Analytical queries follow I1 contains O100, I3 contains O200 to infer that E006 affects O100 and O200.
- E007 (Pack P1) relates to P1, I1, I3 (source).
- Queries follow P1 packs I1 (in O100), P1 packs I3 (in O200) to derive O100, O200 involvement.

**Discovery Impact:**
- **Relations table** is smaller, cleaner.
- **OC-DFG discovery**: Must resolve O2O chains during analysis; algorithm overhead increases.
- **Flattening by Order**: Requires pre-processing to inject propagated E2O links; can produce same traces as Alternative B if propagation is applied.
- **Analysis Use Case**: Separates analytical artifacts from facts; audit trail clear.

**Trade-off:** Cleaner data, higher algorithmic cost; requires post-processing for flattening.

---

## 7. Failure Modes

### 1. **Relation Inflation**
**Symptom:** E2O relations grow to O(|Events| × |Objects|).  
**Cause:** Propagating every event to all reachable objects via O2O chains.  
**Example:** If E006 is propagated to O100, O200, I1, I3, P1, P2, D1, D2, V1, (8 relations for 1 event), then 17 events × ~8 relations/event = 136 relations (our actual: 57, mostly source+minimal propagation).  
**Mitigation:** Document derivation column; apply propagation only to high-value shared events.

---

### 2. **Missing Direct E2O Links**
**Symptom:** OC-DFG is fragmented; some activity-activity edges vanish.  
**Cause:** Under-modeling propagation. Example: E009 (Dispatch D1) not linked to O100/O200 means flattening by Order misses the dispatch event.  
**Example:** If E006, E007, E009, E013 are omitted from O100 relations, O100 traces become: Create  Add  Add  Issue Invoice  Pay  Pay  Close (missing logistics).  
**Mitigation:** Ensure shared operational events include propagated E2O links. Use O2O chains to validate coverage.

---

### 3. **Treating O2O Propagation as Observation**
**Symptom:** Analyst assumes O2O edges reflect actual data flow, conflating model assumptions with facts.  
**Cause:** No clear separation between "source" (S) and "propagated" (P) relations.  
**Example:** If derivation column is omitted, one cannot distinguish whether E006  O100 is a fact (source) or inference (propagated via Item containment). Confusion in audit.  
**Mitigation:** Include derivation metadata; document assumptions in prose.

---

### 4. **Duplicate Shared Events After Flattening**
**Symptom:** E006 (Reserve Stock) appears twice in O100 and O200 flattened logs, inflating trace length and DFG frequency.  
**Cause:** Shared events are correctly in both Order relations; flattening does not deduplicate.  
**Example:** 
- O100 flattening: Create O100  Add I1  Add I2  **Reserve Stock**  Pack P1  Pack P2  Dispatch P1  Dispatch P2  Confirm D1  Confirm D2  Issue Invoice  Record Payment (M1)  Record Payment (M2)  Close O100. 
- O200 flattening: Create O200  Add I3  **Reserve Stock**  Pack P1  Dispatch P1  Confirm D1  Issue Invoice  Record Payment (M1)  Record Payment (M2)  Close O200.  
- Both traces include E006, E007, E009, E013, E011, E012, E015.
- DFG for Order: `Reserve Stock  Pack Package` has frequency 2 (once per Order), not 1.  
**Mitigation:** Document this in expected behavior; use object-type-specific DFG analysis (e.g., DFG per object type).

---

### 5. **Ambiguous Payment Allocation**
**Symptom:** After flattening by Order, each Order trace includes both M1 (100) and M2 (150), but no indication of how much each Order pays.  
**Cause:** Payments settle Invoice (not Orders directly). O2O does not specify Order-to-Payment mapping.  
**Example:** Invoice V1 (for O100 + O200) receives M1=100 and M2=150. O100 flattening includes both; should O100 be attributed 100, 50+50, 75+75, or 0 of the amounts?  
**Mitigation:** Model a "Payment Allocation" object or O2O relation, or extend events with allocation percentages. Accept ambiguity and document in reports.

---

### 6. **Overly Short Payment Traces**
**Symptom:** Payment flattening yields single-event traces or trivial DFGs.  
**Cause:** Payments are stateless financial records; no lifecycle precedes or follows them.  
**Example:** M1 and M2 traces are each `Record Payment` (E012) and `Record Payment` (E015), respectively. DFG is empty. Log skeleton is trivial.  
**Mitigation:** Do not flatten by Payment. Payment is a secondary entity; keep it in the O2O dimension only.

---

### 7. **Constructor/API Version Mismatch**
**Symptom:** `OCEL(...)` constructor fails; PM4Py function names differ (e.g., `discover_ocdfg` not found).  
**Cause:** PM4Py version < 2.7.9 or API refactoring.  
**Example:** PM4Py 2.7.0 uses `ocel_objects_interactions_summary(...)` but 2.6.x does not.  
**Mitigation:** Version check and fallback; use try-except blocks around discovery calls.

---

### 8. **False Total Order for Same-Time Events**
**Symptom:** Two events with identical timestamps are arbitrarily ordered by PM4Py's flattening, leading to inconsistent DFG construction.  
**Cause:** Flattening algorithm imposes a total order on events; tie-breaking is not documented.  
**Example (Hypothetical):** If E002 and E003 both have timestamp 2026-04-06 08:05 (e.g., "Add Item I1" and "Add Item I2" happen simultaneously), flattening may produce O100 trace:
- Variant 1: Add I1  Add I2  ...  
- Variant 2: Add I2  Add I1  ...  
- DFG may record both edges, inflating complexity.  
**Mitigation (in current model):** All timestamps are distinct (08:00, 08:05, 08:06, ..., 10:35). Future models with genuine concurrency should include event IDs as tie-breakers.

---

### 9. **O2O Cycles (Unintended)**
**Symptom:** Cyclic O2O relations cause infinite loops in transitive closure queries.  
**Cause:** Modeling error; e.g., Order contains Item, Item contains Order (nonsensical).  
**Example:** In current model, o2o is acyclic (Order  Item  Package  Delivery, Invoice  Order, Payment  Invoice). No cycles detected.  
**Mitigation:** Validate o2o for cycles before analysis. Use topological sort or cycle-detection library.

---

### 10. **Event Attributes Lost in Flattening**
**Symptom:** Payment amounts (100, 150) not visible in flattened logs; DFG shows only activity names, not amount aggregates.  
**Cause:** PM4Py's flattening may drop non-standard event attributes, or require explicit inclusion in parameters.  
**Example:** events table includes "amount" column; flattened logs may not preserve it.  
**Mitigation:** Explicitly map event attributes to flattened log columns; validate with `flattened[obj_type].columns` after flattening.
