# 1. Delay-decomposition definitions

**Notation.** For case `c` and branch `i  {A,B,C}`, define wall-clock timestamps: `a_c` (arrival), `f_c` (fork_release), `s(i,c)`/`e(i,c)` (branch start/end), `g_c`/`h_c` (final start/end). All durations in minutes.

**Latent fork-join quantity (not directly logged):**

```
join_ready(c) = J(c) = max over i of e(i,c)
```

**Primary components (non-additive across branches):**

| Symbol | Formula | Meaning |
|---|---|---|
| `U_c` (upstream_elapsed) | `f_c  a_c` | entry  permission to start |
| `Q_ic` (branch queue) | `s(i,c)  f_c` | own queue after permission |
| `P_ic` (branch service) | `e(i,c)  s(i,c)` | active work |
| `Y_ic` (sync wait) | `J(c)  e(i,c)` | idle wait after finishing (0 for the last completer) |
| `W_c` (stage_elapsed) | `J(c)  f_c = max_i (Q_ic + P_ic)` | fork-join stage span |
| `_c` (downstream_queue) | `g_c  J(c)` | wait before F |
| `_c` (final_service) | `h_c  g_c` | Release Decision work |
| `T_c` (total_flow_time) | `h_c  a_c` | end-to-end |

**Exact, non-double-counted decomposition.** Because the three branches run concurrently,

```
T_c  =  U_c  +  W_c  +  _c  +  _c
     =  U_c  +  (Q_(i*,c) + P_(i*,c))  +  _c  +  _c ,    i*_c = argmax_i (e(i,c))
```

Only the **critical branch's** queue and service enter the additive identity; the other branches run *inside* its span. Ties at the max: pick the lexicographic minimum `{A<B<C}` and flag the tie (none occur in the raw data; ties appear only after counterfactual CF2).

**Why summing all branch synchronization waits double counts.** Two arguments:

1. *Algebraic:* for **every** branch, `Q_ic + P_ic + Y_ic = (sf) + (es) + (Je) = J  f = W_c`, identically. Hence `_i (Q+P+Y)_ic = 3 · W_c` — a literal triple count of the stage span. The true stage span is obtained by `max`, not `sum`.
2. *Wall-clock intuition:* between the earliest completion and `join_ready`, several finished branches idle **simultaneously in the same calendar interval**. The case experiences that idle span once, not once per waiting branch.

Numerical preview (verified per case below and in §6): e.g. F01 — A: 0+50+0 = 50, B: 5+40+5 = 50, C: 10+18+22 = 50; each branch "explains" the whole 50-min stage; naïvely summing all three gives 150 min against a real stage of 50 min. The same collapse-by-max applies to queue and service: `max_i(Q+P) = 50  123 = _i(Q+P)` for F01.

# 5. Recommended redesigns and risks

### RD1 — Stress-test (B) dispatch redesign: reserve-and-pull with a queue cap, paired with a conditional A fast-track
- **Mechanism (recommendation):** cap `B_queue` at 10 min via protected B slots per 15-min release wave and pull-triggered starts (targets CF2's 92.5 min). Add a *conditional* A fast-track triggered when B is projected to finish early, shaving the A floor only where it would bind (recovers part of the 22.5 min CF2 truncation without wasting A effort elsewhere).
- **Throughput:** station service rates unchanged, so long-run throughput stays pinned by the final station (6 jobs/h capacity vs 4 jobs/h demand, O/E); gains are flow-time and WIP-related, not capacity-related.
- **Flow-time tail:** modeled worst case 130  ~100–115; spread narrows sharply because both tail cases are B-driven.
- **Resource utilization:** B rig busy-time unchanged (service unchanged) but queue inventory drops; A fast-track consumes small extra A capacity episodically — verify A has slack (A utilizations are not directly observable, §7).
- **Possible new bottlenecks:** A becomes the systematic second binder (already visible post-CF2); afterwards C's rare 25–35 min queue spikes (F04/F08) and the final station dominate. Monitor all three simultaneously.
- **Synchronization effects:** earlier, tighter `join_ready` reduces accumulation of others' sync waits (especially C's 30-min average idling); the AND-join slack collapses when sojourns converge — beneficial for WIP but it *moves* attention downstream.
- **Pilot/measure first:** shadow-run the slot schedule for ~2 weeks on a subset; track `B_queue` percentiles, join slack (`J ` second-largest end), A-start punctuality, and re-estimate this decomposition; use a switch-back design to separate seasonality.

### RD2 — Final-station smoothing: earliest-ready assignment across F1/F2 (replacing fixed rotation) + validated "short-decision" lane
- **Mechanism (recommendation):** assign each case to whichever of F1/F2 is free at `join_ready` instead of the observed strict alternation; institute an accelerated standard decision path for routine releases, escalating only anomalies. Targets CF3's 176 min without a third resource.
- **Throughput:** capacity addition unnecessary at 66% utilization (O/E); the redesign converts existing idle pockets into absorption capacity during join clusters (10:00–10:55, 11:15–12:10).
- **Flow-time tail:** removes 8–20 min per case, *including* cases where branch work cannot help (F04, F08, F11 under CF2) — the only lever benefiting all 12.
- **Resource utilization:** balances F1/F2 (observed unequal idle: F1 had two long idle pockets while later running back-to-back); smoother, lower-variance duty cycles.
- **Possible new bottlenecks:** uncovers true branch constraints underneath (expect A next); if the wait is actually policy-based, the capacity fix silently fails — detect this in the pilot, not production.
- **Synchronization effects:** none upstream of `join_ready` (acts strictly after it), which is why RD1+RD2 savings are locally additive (268.5 min combined, §4).
