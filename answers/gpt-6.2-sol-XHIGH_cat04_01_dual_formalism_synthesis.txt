# 1. Assumptions and Interpretation

1. The language consists of finite, completed cases. Each visible event records activity completion. A precedence edge requires the predecessor to finish before the successor starts. The witness traces show the resulting completion order, with any timestamp ties assumed to be resolved consistently with causality.
2. After Analyze Root Cause, an exclusive choice selects the approval route. The low-risk branch contains Supervisor Review. The high-risk branch requires both Quality Review and Regulatory Review, with either completion order. The model abstracts away the case data that determine the branch.
3. The supplier branch is an exclusive choice between one Consult Supplier and a silent skip. A consultation can happen only after Analyze Root Cause, and the chosen branch must finish before release. Selection is abstracted from case data, so omission is interpreted as taking the skip.
4. The final Inspect Trial in a completed trace stands for a pass. Each earlier Inspect Trial stands for a failure and is followed in the trial subtrace by Adjust Parameters and another trial. The pass and fail decisions are implicit in the loop exit and redo. A run that keeps failing can continue indefinitely, with finite prefixes that do not yet complete a case.
5. An unordered pair is eligible for actual overlap when its prerequisites permit it. At the trace level, concurrency appears as freedom to interleave completions. Either completion order is compatible with overlap or serial execution. The models impose no resource constraints.
6. Each visible label has a single leaf in each model. Repeated trial labels arise from revisiting loop leaves.
7. The process tree uses a conservative under-approximation. It joins the two initial activities before opening the planning, design, approval, and supplier work. It preserves parallelism between the initial activities and keeps approvals and consultation independent of trial progress after that join.

|---|---|---|---|---|

| D02 | Contain Material | Analyze Root Cause | Unordered | The two streams may overlap and finish in either order. |
| D03 | Contain Material | Plan Verification | Precedence | Verification planning uses completed containment. |
| D04 | Analyze Root Cause | Design Corrective Action | Precedence | The design uses the completed analysis. |
| D05 | Analyze Root Cause | Approval route | Precedence into exclusive choice | Choose Supervisor Review for low risk or the two-review route for high risk. |
| D06 | Quality Review | Regulatory Review | Unordered, both mandatory in high-risk branch | Both reviews must finish, in either order. |
| D07 | Analyze Root Cause | Supplier branch | Precedence into optional choice | The branch is either one consultation or a silent skip. |
| D08 | Plan Verification, Design Corrective Action | Trial loop | AND join | Both work products are required before the first Execute Trial. |

# 3. PM4Py Process-Tree Model

The operators are sequence (`SEQ`), parallel (`AND`), exclusive choice (`XOR`), and a binary do/redo loop (`LOOP`). The operator `AND` admits all order-preserving interleavings of its branches. The leaf `τ` is silent.

```text
SEQ(
  Register Deviation,
  AND(Contain Material, Analyze Root Cause),
  AND(
    SEQ(
      AND(Plan Verification, Design Corrective Action),
      LOOP(SEQ(Execute Trial, Inspect Trial), Adjust Parameters)
    ),
    XOR(Supervisor Review, AND(Quality Review, Regulatory Review)),
    XOR(Consult Supplier, τ)
  ),
  Release Material,
  Archive Case
)
```

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree


def activity(label):
    return ProcessTree(label=label)


def block(operator, *children):
    parent = ProcessTree(operator=operator, children=[])
    for child in children:
        parent.children.append(child)
        child.parent = parent
    return parent


initial_work = block(
    Operator.PARALLEL, activity("Contain Material"), activity("Analyze Root Cause")
)
trial_preparation = block(
    Operator.PARALLEL, activity("Plan Verification"), activity("Design Corrective Action")
)
trial = block(
    Operator.LOOP,
    block(Operator.SEQUENCE, activity("Execute Trial"), activity("Inspect Trial")),
    activity("Adjust Parameters"),
)
approval = block(
    Operator.XOR,
    activity("Supervisor Review"),
    block(Operator.PARALLEL, activity("Quality Review"), activity("Regulatory Review")),
)
supplier = block(Operator.XOR, activity("Consult Supplier"), ProcessTree())

tree = block(
    Operator.SEQUENCE,
    activity("Register Deviation"),
    initial_work,
    block(
        Operator.PARALLEL,
        block(Operator.SEQUENCE, trial_preparation, trial),
        approval,
        supplier,
    ),
    activity("Release Material"),
    activity("Archive Case"),
)
```

In addition to the intended prerequisites, the initial join forces Analyze Root Cause before Plan Verification and Contain Material before Design Corrective Action, every executed review, and Consult Supplier when taken. This excludes traces where planning completes before analysis or where design, a review, or a consultation completes before containment. It also excludes schedules where an affected activity starts before its added prerequisite finishes, even if its completion order matches the tree. The tree's completion language is exactly the intended language restricted by those added completion-order relations. The initial activities can still overlap, planning and design can still overlap, and either approval route and the optional consultation can still run alongside preparation and the trial loop after the join. The tree preserves the trial entry requirements, the do/redo behavior, and the release join.

The join follows from the concurrency priorities of this single-occurrence design. To see the obstruction, fix a route and a supplier choice, and unfold the loop to a fixed iteration count. The resulting visible precedence order of a sequence/parallel tree is series-parallel. Write `C` for containment, `A` for analysis, `E` for the first trial execution, and `V` for a review that is required in the chosen route. The intended relations on these four occurrences are exactly `C < E`, `A < E`, and `A < V`. This is the four-element N order, which cannot be induced by a sequence/parallel composition. Keeping `C` unordered with `A` and `V` unordered with `E` requires `C < V`, since `V < C` would force `V < E`. The argument also applies to a selected consultation in place of `V`. Once `C < V` is added, the four-element orders on `{C, A, Plan Verification, V}` and `{C, A, Design Corrective Action, V}` again induce N unless further edges are added. Keeping the review unordered with both work products and preserving the initial parallelism forces `A < Plan Verification` and `C < Design Corrective Action`. Reversing either added edge would order the two initial activities by transitivity. Different concurrency priorities or duplicated branches would change the trade-off.

# 4. PM4Py POWL Model

`PO` denotes a strict partial order on the listed sibling nodes. The arrows below show its cover edges. The code stores their full transitive relation.

```text
Approval = XOR(Supervisor Review, PO(Quality Review, Regulatory Review))
Supplier = XOR(Consult Supplier, τ)
Trial = LOOP(PO(Execute Trial → Inspect Trial), Adjust Parameters)

Outer PO cover edges
  Register Deviation → Contain Material, Analyze Root Cause
  Contain Material → Plan Verification
  Analyze Root Cause → Design Corrective Action, Approval, Supplier
  Plan Verification, Design Corrective Action → Trial
  Trial, Approval, Supplier → Release Material
  Release Material → Archive Case
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")
release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")
high_risk = StrictPartialOrder(nodes=[quality, regulatory])
approval = OperatorPOWL(
    Operator.XOR, [Transition(label="Supervisor Review"), high_risk]
)
supplier = OperatorPOWL(
    Operator.XOR, [Transition(label="Consult Supplier"), SilentTransition()]
)

execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
trial_body = StrictPartialOrder(nodes=[execute, inspect])
trial_body.order.add_edge(execute, inspect)
trial = OperatorPOWL(
    Operator.LOOP, [trial_body, Transition(label="Adjust Parameters")]
)

work = [contain, analyze, plan, design, approval, supplier, trial]
powl = StrictPartialOrder(nodes=[register, *work, release, archive])

for source_node, target_node in [
    (contain, plan),
    (analyze, design),
    (analyze, approval),
    (analyze, supplier),
    (plan, trial),
    (design, trial),
    (contain, trial),  # Implied via plan.
    (analyze, trial),  # Implied via design.
]:
    powl.order.add_edge(source_node, target_node)

for node in work:
    powl.order.add_edge(register, node)
    powl.order.add_edge(node, release)
    powl.order.add_edge(node, archive)

powl.order.add_edge(register, release)
powl.order.add_edge(register, archive)
powl.order.add_edge(release, archive)
```

The following are all incomparable pairs of outer work nodes, grouped by the first node in the pair.

- **Containment** is unordered with analysis, design, approvals, and the supplier branch. These belong to the analysis stream and can progress while containment is underway.
- **Analysis** is also unordered with planning, which needs only containment.
- **Planning** is also unordered with design, approvals, and the supplier branch. Those analysis-driven obligations can progress independently of verification planning.
- **Design** is also unordered with approvals and the supplier branch. All are enabled by analysis and use no work product from one another.
- **Approvals** are also unordered with the supplier branch and the trial. They may finish before, during, or after trial work.
- **The supplier branch** is also unordered with the trial. When consulted, the supplier can finish before, during, or after trial work.

Within the high-risk route, Quality Review and Regulatory Review are unordered because neither needs the other's output. The XOR alternatives and the do/redo components have their order and activation rules defined by their operators. For any POWL execution, its selected branches and loop count satisfy the intended visible precedence. Conversely, an intended trace fixes the branch selections and iteration count and is an interleaving of those components respecting the POWL edges. This gives equality of the finite completed trace languages under the assumptions above.

# 5. Behavioral Witnesses

Each row gives a complete candidate trace in completion order. The initial work uses `R` for Register Deviation, `C` for Contain Material, `A` for Analyze Root Cause, `P` for Plan Verification, and `D` for Design Corrective Action. The approvals and consultation use `V` for Supervisor Review, `Q` for Quality Review, `G` for Regulatory Review, and `S` for Consult Supplier. The trial and closing activities use `E` for Execute Trial, `I` for Inspect Trial, `J` for Adjust Parameters, `M` for Release Material, and `Z` for Archive Case.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|---|---|---|---|---|---|
| T1 | R C A P D V E I M Z | Allowed | Accepted | Accepted | Low risk. Supervisor Review finishes before the trial and the supplier branch is skipped. |
| T2 | R A C D P G E I Q M Z | Allowed | Accepted | Accepted | High risk. Regulatory Review finishes first, and Quality Review completes after the passing inspection and before release. |
| T3 | R C A D P E V I S M Z | Allowed | Accepted | Accepted | Low risk with consultation. Approval completes during the trial cycle and supplier consultation completes last before release. |
| T4 | R A C P D E I J V E I M Z | Allowed | Accepted | Accepted | The first inspection fails. Parameters are adjusted, approval completes, and the second trial passes. |
| T5 | R A D V S C P E I M Z | Allowed | Rejected | Accepted | Design, approval, and consultation can finish before containment. The tree first rejects `D` because its initial join still waits for `C`. |
| T6 | R A C D E P I V M Z | Forbidden | Rejected | Rejected | The first `E` violates the trial-entry join. Design has finished but verification planning has yet to complete. |
| T7 | R C A P D Q E I M G Z | Forbidden | Rejected | Rejected | At `M`, Quality Review has committed the case to the high-risk route and Regulatory Review is still outstanding. |
| T8 | R C A P D V E I E I M Z | Forbidden | Rejected | Rejected | The second `E` is the earliest illegal event. After the first `I`, a repeat requires `J` first. |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial streams | Containment and analysis proceed independently after registration. | Parallel branches share an exit join. | Unordered nodes following registration. | Both preserve the initial pair's freedom. The tree adds a downstream barrier. | Either task may finish first in both models. POWL enables each stream to hand off its own work when its prerequisite finishes, even while the other stream remains active. |
| Planning and design prerequisites | Planning needs containment. Design needs analysis. | Both need containment and analysis. | Separate edges connect each work product to its own prerequisite. | Tree overconstrains each by one prerequisite. POWL is exact. | Legitimate early planning or design can be flagged in tree-based conformance checking. |
| Risk route | Exactly one route, with both high-risk reviews unordered. | XOR with a parallel high-risk branch, enabled after the initial join. | Same choice, with an unordered high-risk branch enabled after analysis. | The tree adds containment as an approval prerequisite. Route membership is exact in both. | Reviews that finish while containment is underway can appear nonconforming in the tree. |
| Approval and trial overlap | Trial waits for planning and design. Approval can finish independently of the trial. | Approval is parallel with the preparation and trial sequence after the initial join. | Trial and approval are incomparable. | Both preserve trial entry and the freedom to interleave approval with trial. | Trial can proceed even with a review outstanding, and release waits for that review. |
| Optional consultation | Skip or consult once after analysis, independently of the other work, with completion before release if taken. | XOR with a silent skip after the initial join. | XOR with a silent skip after analysis, incomparable with preparation and trial. | The tree adds containment to the eligibility condition. Optionality and completion at release are exact in both. | Early legitimate supplier work can be flagged by the tree. Case data are needed to audit when consultation was required. |
| Repeat until pass | Perform at least one execute/inspect cycle. Adjustment occurs only between cycles. | Binary loop with execute/inspect as the body and adjustment as redo. | Same loop with an internal execute-to-inspect edge. | Both are exact for the abstract visible cycle. | Missing adjustments and unfinished retries violate conformance. Actual inspection outcomes require case data. |
| Release synchronization | Release follows the pass, chosen reviews, and any selected consultation. Archive follows release. | Parallel join before release, then sequence to archive. | Edges from the three obligations to release and from release to archive. | Both enforce the same release obligations. | Premature release and archiving are rejected. |
| Duplicate-label risk | Labels identify activity types. Repeated trial labels mark new iterations of the same activities. | One visible leaf per label. Loop leaves can fire again. | One visible transition node per label. Loop nodes can fire again. | Neither adds ambiguity by duplicating a visible label in the source model. | Conformance diagnostics can attribute a label to one source node. Lifecycle outcomes and iteration attribution still depend on trace context. |

# 7. Preferred Representation and Validation Plan

Use the POWL model as the canonical representation. The edges express exactly which work products enable a trial, which obligations enable release, and where the case can progress independently. The tree is a conservative block-structured view whose initial join must be accounted for when interpreting deviations.

1. **Convert each model to an accepting Petri net.** Use `net, im, fm = pm4py.convert_to_petri_net(model)` on each model where supported. For POWL, the dedicated `pm4py.objects.conversion.powl.converter.apply(powl)` is an alternative when the generic dispatcher lacks POWL support. Retain both markings and the PM4Py version.
2. **Check soundness.** Call `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on each converted net. Check option to complete, proper completion, and absence of dead transitions. For small finite nets, verify these properties directly by exploring all reachable markings, working backward from the final marking, and recording which transitions fire. Having an option to complete is compatible with runs that keep choosing redo.
3. **Explore bounded complete playout.** From each initial marking, enumerate enabled firings up to a bound of two Execute Trial events. Keep distinct states by marking and visible prefix so silent paths can be explored without repeatedly expanding the same state. Collect projected traces that reach the exact final marking. For an independent oracle, expand one and two iterations for each risk and supplier choice, then enumerate the linear extensions from Section 2. Require equality with the oracle for POWL and with the oracle filtered by the extra relations in Section 3 for the tree. Increase the iteration bound or sample longer cases to exercise additional retries.
4. **Test positive and negative traces.** For each row in Section 5, require an accepting firing sequence with the exact visible projection when acceptance is expected. For rejection, explore all reachable markings matching the prefix, with silent closure before and after each visible event. Require that no matching path reaches the final marking after consuming the whole trace and allowing a silent suffix. Also mutate valid cases to attempt an early release with consultation still outstanding, mix the risk routes, and release immediately after an adjustment.
5. **Check silent routing and label identity.** Verify one visible leaf per activity label in each source model and inspect the converted nets for unintended visible duplicates. Exercise both branches of the supplier choice and check that the skip emits no event. Confirm that silent firings alone cannot complete the case and cannot bypass required approvals, the first trial cycle, or the retry after an adjustment.
6. **Scope the conclusions.** Bounded playout and trace tests can expose counterexamples, with coverage limited by the bound or sample. Workflow-net soundness cannot establish equivalence to the narrative. Completion traces cannot establish physical overlap or validate the case data behind approvals, consultation, and inspection outcomes.

With PM4Py 2.7.23.4, both models converted and passed the soundness check. Exhaustive marking exploration independently confirmed soundness over 91 reachable tree-net markings and 114 POWL-net markings. Each net had one transition per visible label. With up to two trial iterations, the tree produced 4,588 distinct completed traces and POWL produced 7,896. Both sets matched their respective oracles, and all eight witness verdicts and earliest rejection points matched.

# 8. Final Self-Critique

1. The tree deliberately excludes work that starts as soon as its own prerequisite finishes while the other initial stream is unfinished. Some affected schedules still produce accepted traces because completions can occur in an order consistent with the added join.
2. Inferring a pass from the final inspection makes the model unable to detect a release after a recorded inspection that actually failed. The same projection loses evidence of whether the chosen route or supplier skip agreed with the case data.
3. The witnesses and bounded checks exercise short retries. The unbounded claim depends on the do/redo semantics and the correspondence between the intended dependencies and the model.
