# 1. Model scope and state variables

The digital twin should be a **calendar-aware, resource-constrained, discrete-event simulation** of the building-permit process from `Submit application` to either `Issue permit` or `Reject application`. It should not be a pure trace replay or an independent-case Monte Carlo model, because the source process explicitly includes non-stationary arrivals, shared resource queues, rework loops, related applications from the same architect, district-based inspection batching, and missing objection events that affect public-notice duration. 

**Boundary.** The operational boundary includes:

* Formal permit processing after portal submission.
* Municipal activities: completeness check, planning review, fire-safety review, environmental review, inspection scheduling, site inspection, decision drafting, legal check, issuing, and rejection.
* Applicant and third-party delays: missing-document response, applicant readiness for inspection, consultant reports, public objections.
* Policy interventions D1-D10, including interventions that occur before formal submission, such as the pre-submission document checker.
* Calendar disruptions, especially public holidays and council-meeting weeks affecting legal and public-notice stages.

The twin should exclude post-permit construction activity and long-term compliance monitoring, except where needed as an input to the proposed no-inspection rule, because the policy requires “no prior violations,” which is not fully represented in the provided event-log excerpt. 

**Level of detail.** The model should be activity-level rather than only variant-level. Variant groups are useful for calibration, but the simulation must represent queues, calendars, parallel reviews, synchronization before decision drafting, and rework. The process tree gives the nominal control-flow skeleton, while the simulation adds stochastic timing, resources, priorities, dependencies, and latent events.

**Main entities.**

| Entity                         | Purpose in the simulation                                                                                                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PermitCase`                   | One building-permit application. Holds case type, district, architect, value, routing flags, current activity, timestamps, rework counters, public-notice status, inspection status, and terminal outcome.              |
| `Architect`                    | Generates correlated arrival bursts. Top architects should be modeled separately because the top 20 architects submit 31% of cases and often submit related cases in the same week.                                     |
| `District`                     | Affects inspection travel time, environmental sensitivity, objection likelihood, and batching opportunities. Districts D3 and D5 require special travel-time parameters.                                                |
| `InspectionBundle`             | Temporary group of cases from compatible districts or same architect/district. Bundling can reduce travel time but delays the first case in the bundle.                                                                 |
| `NeighborhoodObjectionCluster` | Latent object for related public-notice cases. Objections are not fully captured, so the simulation should model them as hidden events inferred from extended public-notice durations, not as directly observed events. |
| `ResourcePool`                 | Clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, system resources, and temporary resources under interventions.                                                                   |
| `Calendar`                     | Working-time and interruption model for each resource pool, including weekday availability, part-time calendars, holidays, and council-meeting weeks.                                                                   |
| `PolicyScenario`               | Encodes baseline and interventions D1-D10, including policy parameters and take-up assumptions.                                                                                                                         |

**Case state variables.**

Each case should maintain at least:

* `case_id`
* `case_type`: Simple renovation, New residential, Commercial, Complex variance
* `district`
* `architect_id`
* `application_value`
* `requires_fire`
* `requires_environment`
* `requires_public_notice`
* latent or external fields: `building_area`, `environmental_sensitivity`, `prior_violations`, `objection_risk`, `applicant_response_type`
* current enabled activities
* completed activities
* required review set: planning, fire, environmental, public notice, inspection, legal
* join state before decision drafting
* queue entry time per activity
* activity start and completion time where available or simulated
* accumulated waiting time by queue
* accumulated municipal service time
* applicant/third-party delay time
* rework counts: completeness rework, planning rework, inspection rework, legal rework, appeal-related rework
* terminal outcome: issued, rejected, still open
* SLA clock and aging category

**Resource pools and calendars.**

The resource model should represent the provided calendars explicitly:

| Pool                    | Calendar and capacity behavior                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Clerks                  | 5 FTE, Monday-Friday 08:00-16:00; on Mondays one clerk is dedicated to portal support, so effective completeness-check capacity is lower during Monday spikes. |
| Planners                | 8 FTE, Monday-Friday 09:00-17:00; two planners only handle Simple renovation.                                                                                  |
| Fire reviewers          | 2 FTE equivalent, Tuesday-Thursday only.                                                                                                                       |
| Environmental reviewers | 3 FTE, Monday-Friday, but only 60% of time available for permit work because 40% is reserved for non-permit duties.                                            |
| Inspectors              | 4 FTE, field visits Tuesday-Friday; district-dependent travel time and bundling are central.                                                                   |
| Legal officers          | 2 FTE; no work during council-meeting weeks except urgent cases.                                                                                               |
| System                  | Unlimited capacity for portal and mostly automated tasks.                                                                                                      |
| Applicant / third party | Not a municipal resource. Response times are separate stochastic delays.                                                                                       |

These calendars are not optional. They are part of the causal mechanism that generates queues and tail durations. 

**Queues.**

The twin should include separate queues for:

* completeness checks
* missing-document requests
* planning review
* fire-safety review
* environmental review
* inspection scheduling
* site inspection trips
* decision drafting
* legal check
* rejection preparation
* issue permit automation

Queue discipline should be scenario-dependent. Baseline can use first-come-first-served within activity and priority class, but D6 introduces an aging-case planner reserve, D3 changes inspection scheduling, and D7 changes arrival smoothing.

**Cross-case dependencies.**

The digital twin should explicitly model four dependency types:

1. **Arrival correlation:** top architects create weekly bursts, so arrivals are not independent Poisson cases.
2. **Resource coupling:** all cases compete for shared clerks, planners, reviewers, inspectors, and legal officers.
3. **Inspection batching:** cases from the same district, nearby districts, or same architect/district can be grouped. This reduces travel time but can increase waiting for early cases.
4. **Public-notice coupling:** neighborhood objections can affect several related cases. Because objections are missing from the log, they should be modeled as latent cluster-level events inferred from public-notice duration, not as observed facts.

# 2. Parameter-estimation plan

**1. Prepare and audit the event log.**

Start by loading the log with pandas, sorting by `case:concept:name` and `time:timestamp`, and formatting it with `pm4py.format_dataframe`. Use PM4Py for process-mining diagnostics: variants, directly-follows graph, performance directly-follows graph, case-arrival average, and possibly conformance diagnostics against the process tree or a translated Petri net. PM4Py should not be treated as the simulation engine; it provides log/model handling and calibration evidence. The required code conventions are explicitly stated in the prompt. 

**2. Estimate arrivals.**

The arrival process should be a **marked, non-homogeneous, overdispersed arrival model**.

Estimate:

* monthly seasonality: March-May and September-November have 1.7x the January-February arrival rate
* weekday effect: Monday submissions are 2.2x Wednesday submissions
* time-of-day distribution of portal submissions
* case-type mix: 45% Simple renovation, 28% New residential, 17% Commercial, 10% Complex variance
* district distribution by case type
* architect distribution, with the top 20 architects modeled as burst-generating actors

A reasonable structure is:

```text
daily_cases ~ NegativeBinomial(mean = base_rate × month_factor × weekday_factor,
                               dispersion = estimated_from_daily_counts)
```

Then assign case marks using conditional distributions:

```text
case_type | month, architect_type
district | case_type, architect_id
application_value | case_type, district
requires_fire / requires_environment / requires_public_notice | case_type, district, value, latent attributes
```

For large architects, use a clustered arrival process: a top architect has a weekly burst indicator, and if active, submits several related cases in the same architect-district-time cluster.

**3. Estimate service times separately from waiting times.**

Do not estimate total inter-event time and call it “service time.” The source states that many resources record only completion timestamps, so the waiting/service split is partly inferred. 

Use three timing layers:

| Timing layer           | Meaning                                                 | Estimation approach                                                                                                                           |
| ---------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Municipal service time | Active work by municipal staff                          | Use start-complete pairs where available; otherwise use empirical service summaries as priors and calibrate against resource utilization.     |
| Queue waiting time     | Delay before resource starts work                       | Generated endogenously by the simulation from arrivals, calendars, capacity, and queue rules. Calibrate to observed median waiting summaries. |
| External response time | Applicant, consultant, public, or calendar-driven delay | Estimate separately for missing documents, consultant reports, public objections, no-shows, and public-notice extensions.                     |

Fit activity-specific distributions, preferably stratified by case type and district where sample size allows:

| Activity                  | Suggested distribution family                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------ |
| Completeness check        | Gamma or lognormal, short service with Monday queue effects generated by arrivals.               |
| Request missing documents | Short gamma/lognormal service.                                                                   |
| Receive missing documents | Heavy-tailed applicant-response distribution; mixture or lognormal/Pareto tail.                  |
| Planning review           | Lognormal/gamma with covariates: case type, district, value, resource.                           |
| Fire-safety review        | Calendar-constrained service with Tuesday-Thursday availability.                                 |
| Environmental review      | Mixture distribution, because consultant reports and project attributes create high variability. |
| Public-notice period      | Deterministic 14-day minimum plus latent objection extension.                                    |
| Inspection scheduling     | Short service; waiting affected by batching policy.                                              |
| Site inspection           | Service plus district-specific travel time and no-show risk.                                     |
| Decision drafting         | Service after synchronization of all required review results.                                    |
| Legal check               | Calendar-constrained service with council-meeting interruption effects.                          |

The empirical timing table gives activity medians, p90 service times, median waiting, and key distribution issues; these should be calibration targets, not simply hard-coded constants. 

**4. Estimate routing and branching probabilities.**

Estimate path choices using the event log and the provided routing rules:

* Missing-document loop probability by case type, architect, district, and application value.
* Fire review probability from `requires_fire=yes`, plus a latent probability for cases requiring fire review because of a building-area threshold not fully available in the log.
* Environmental review probability from `requires_environment=yes`, plus a latent district-sensitivity component.
* Public-notice probability for Complex variance and some New residential cases.
* Legal-check probability by case type, value, complexity, public notice, and conflict indicators.
* Rejection probability by case type and prior path, especially after legal/planning conflicts.
* Appeal/rework probability for complex and rejected cases where observed.

Use the process tree as the normative structure, but allow rare variants and exceptions because the event-log summary includes “Other rare variants” with mixed exceptions.

**5. Estimate rework.**

Rework must be activity-specific, not a generic delay multiplier.

Estimate:

* completeness rework from repeated `Completeness check` after `Request missing documents` and `Receive missing documents`
* planning rework from repeated planning-related activity or returns to applicant
* inspection rework from repeated `Inspection scheduling` / `Site inspection`
* legal rework from legal check followed by additional drafting/planning/legal activity
* appeal-related rework where post-decision or appeal indicators exist

Because rework reasons are unstructured and not reliably coded, use observed loop counts as the primary quantitative basis and keep reason-specific models as sensitivity scenarios. 

**6. Estimate calendars and capacities.**

Use HR calendars as the authoritative base because resource calendars were reconstructed from HR data, not purely from event logs. Then validate them against observed event timestamps and workload volumes. Estimate effective capacity, absences, non-permit duties, and interruptions.

Important calibration checks:

* Monday clerk capacity after assigning one clerk to portal support.
* Fire-review queue behavior under Tuesday-Thursday-only availability.
* Environmental-review utilization after subtracting 40% non-permit time.
* Inspector trip capacity under Tuesday-Friday field visits.
* Legal throughput during and around council-meeting weeks.

**7. Estimate cross-case dependencies.**

Use the flattened case log carefully because it underrepresents dependencies between related applications. 

Estimate dependencies as follows:

| Dependency                       | Estimation method                                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Architect bursts                 | Weekly counts per `architect_id`; fit top-20 architects separately from the rest.                                     |
| Related applications             | Same architect, same district, and close submission dates form candidate related-case clusters.                       |
| Inspection batching              | Compare inspection wait and travel-time proxies by district, date, inspector, and scheduling proximity.               |
| Public-notice objection clusters | Infer from extended public-notice durations, same district/neighborhood proxy, and same time window. Treat as latent. |
| Shared-resource queue spillovers | Calibrate using resource-specific workload, waiting-time distributions, and utilization.                              |

**8. Calibrate the full model.**

Calibration targets should include:

* variant shares
* median and p90 duration by variant group
* waiting-time medians before each activity
* activity service medians and p90s
* case-arrival average and day/month seasonality
* resource utilization by pool
* queue-length and aging profiles
* district D3/D5 inspection delays
* long tails for Complex variance, public notice, and inspection rework variants

Use parameter search, approximate Bayesian calibration, or simulation-based optimization. The output should be a calibrated range of plausible models, not one falsely precise model.

# 3. Assumptions

**Arrivals.**

* Arrivals are not stationary.
* Formal submissions follow a non-homogeneous, overdispersed daily process with month, weekday, and time-of-day effects.
* Case type, district, architect, and value are sampled as correlated marks, not independently.
* Top architects are modeled with burst behavior; smaller architects use a lower-intensity background process.
* D7 changes the arrival pattern by smoothing architect-facing appointment slots, but does not eliminate total demand unless a take-up or dropout parameter is explicitly introduced.

**Service times.**

* Human activity service times are positive random variables fitted by activity, with stratification by case type and district where data supports it.
* System tasks have effectively unlimited capacity and short service times.
* The public-notice period is not ordinary service time; it is a statutory minimum duration plus possible latent objection extension.
* Site inspection time is the sum of inspection service time, travel time, and possible no-show or rescheduling effects.
* Because start timestamps are often missing, service-time estimates are partly inferred and should be treated as uncertain.

**Routing.**

* The process tree defines the nominal control flow.
* Fire review is required when `requires_fire=yes` or when an unobserved building-area threshold applies.
* Environmental review is required when `requires_environment=yes` or when a latent environmental-sensitivity condition applies.
* Public notice is required for Complex variance and some New residential cases.
* Decision drafting cannot start until all applicable review, public-notice, and inspection obligations are complete.
* Legal check is optional in the process tree, but its probability depends on case type, conflict risk, complexity, and policy setting.
* Rejection and issuing are terminal alternatives unless appeal/rework is explicitly modeled as a post-decision loop.

**Resources/calendars.**

* Clerks, planners, fire reviewers, environmental reviewers, inspectors, and legal officers work according to the provided calendars.
* Environmental reviewers devote only 60% of nominal capacity to permit work.
* Legal officers have no ordinary work during council-meeting weeks except urgent cases.
* Inspector capacity depends not only on FTE count but also on district travel and visit grouping.
* Temporary inspector capacity under D4 applies only in peak months.
* Resource calendars are taken from HR data, then validated against event-log timing.

**Rework.**

* Rework probabilities vary by activity and case type.
* Completeness rework is strongly tied to missing documents.
* Inspection rework is tied to applicant readiness, district travel, and no-shows.
* Complex variance cases have higher rework and appeal probability.
* Rework reasons are not reliably coded, so reason-specific effects should be sensitivity-tested rather than treated as known.

**Applicant/third-party response.**

* Applicant missing-document response is external to municipal capacity and is heavy-tailed.
* Consultant reports affect environmental review variability.
* Public objections are latent third-party events, inferred from long public-notice durations.
* Applicant readiness affects inspection timing and rework/no-show risk.
* D1 may reduce formal missing-document loops but may increase effort before formal submission.

**Cross-case dependencies.**

* Same architect and district within a short submission window indicates a candidate related-case cluster.
* Inspection batching can reduce travel time while increasing waiting for the earliest cases in the batch.
* Neighborhood objections may affect several related cases in the same district or area.
* Shared queues create spillovers: improving one case type can worsen another if it consumes scarce staff.

**Non-stationary demand.**

* Seasonal peaks are explicitly represented.
* Monday bursts are explicitly represented.
* Calendar interruptions such as holidays and council meetings are represented as time-varying capacity and delay factors.
* Experiments use common random numbers so that interventions face the same arrival scenarios where appropriate.

**Missing data.**

* Missing start timestamps mean observed inter-event times are not clean service times.
* Missing objection events are represented by a latent process calibrated to public-notice duration, not by pretending objections are observed.
* Incomplete environmental-sensitivity and building-area data are represented as latent or externally supplied covariates.
* Removed emergency decisions are excluded from baseline calibration unless a separate emergency module is added.
* Flattened case logs understate cross-case dependencies, so dependency parameters must be validated with domain experts and sensitivity analysis.

# 5. Warm-up, replications, and uncertainty treatment

**Warm-up.**

Because the process has strong seasonality, a simple steady-state warm-up is not enough. Use one of two approaches:

1. **Observed-WIP initialization**, preferred if open-case snapshots exist. Initialize the simulation with the real backlog distribution by case type, activity, age, district, and architect.
2. **Calendar-preserving synthetic warm-up**, if WIP snapshots are unavailable. Simulate at least 6-12 months before the evaluation window, using the same seasonal calendar, then discard the warm-up outputs but keep the resulting WIP.

For a January-start evaluation, a useful warm-up is the previous September-December or a full prior synthetic year, because September-November is a peak period.

**Run length.**

Use at least one full calendar year for policy evaluation, and preferably two years, so that the model includes:

* March-May peak
* September-November peak
* Monday submission spikes
* council-meeting weeks
* holidays
* long public-notice and Complex variance tails

For validation against the 18-month historical log, use rolling windows: train on one period, validate on a later period, then reverse or roll forward where possible.

**Replications and random seeds.**

Use common random numbers across policies:

```text
seed 1001 baseline, D1, D2, ..., D10
seed 1002 baseline, D1, D2, ..., D10
...
```

This makes paired differences more stable. Start with 100 replications for screening, then increase to 300-500 for final policy comparisons, especially for tail metrics such as p90/p95 duration and long public-notice cases.

**Uncertainty intervals.**

Report:

* paired confidence intervals for policy-vs-baseline differences
* bootstrap intervals for median, p90, and SLA compliance
* credible intervals if using Bayesian parameter calibration
* separate first-order stochastic uncertainty from second-order parameter uncertainty

Do not report a single “optimal” policy without calibration and validation.

**Heavy-tailed durations.**

Applicant response, objections, consultant reports, Complex variance cases, and inspection rework have long tails. Handle them with:

* quantile metrics rather than only means
* mixture distributions for public notice and applicant response
* p90 and p95 reporting by case type
* capped and uncapped sensitivity runs
* tail-specific validation against variant p90 durations
* robust comparisons such as median difference and probability of improvement

**Sensitivity analysis.**

Prioritize sensitivity on uncertain or biased parameters:

| Parameter                                    | Why it matters                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------ |
| Objection probability and extension duration | Objections are missing and public-notice tails are important.            |
| Missing-document loop reduction under D1     | Directly affects D1 and D10.                                             |
| Eligibility and risk under D2                | No-inspection rule depends on prior-violation data not shown in the log. |
| Inspection travel-time reduction under D3    | Determines whether batching helps or merely delays first cases.          |
| Temporary inspector productivity under D4    | New resource may have onboarding or routing limitations.                 |
| Legal pre-check rework/waste under D5        | Could help late-stage delay or overload legal officers.                  |
| Environmental triage accuracy under D8       | Misclassification may create fairness and compliance risks.              |
| Arrival burst intensity                      | Determines whether D7 and clerk-capacity changes matter.                 |
| Start-time inference assumptions             | Affects service-time calibration and utilization estimates.              |

# 6. Validation strategy

**Face validation.**

Conduct structured validation sessions with clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, and policy managers. Ask them to review:

* routing logic
* calendar assumptions
* queue priorities
* legal/council interruption rules
* inspection batching behavior
* causes of rework
* interpretation of public-notice extensions
* expected intervention side effects

The goal is not only to confirm averages but to confirm mechanisms.

**Event-log replay validation.**

Use observed arrivals and case attributes as exogenous inputs, then simulate the baseline process with current policy. Compare simulated outputs to the historical log:

* variant frequencies
* activity occurrence rates
* loop counts
* terminal outcome shares
* median and p90 case durations
* activity waiting medians
* district-specific inspection delays
* case-type-specific tails

The replay should not force exact historical timestamps; it should reproduce distributions and queue behavior under the observed demand pattern.

**Distributional validation.**

Compare full distributions, not only means:

| Distribution                                | Validation target                                  |
| ------------------------------------------- | -------------------------------------------------- |
| Total case duration by case type            | Match median, p75, p90, and p95.                   |
| Duration by variant group                   | Match the provided variant median and p90 values.  |
| Waiting before activity                     | Match empirical waiting summaries.                 |
| Service time by activity                    | Match median and p90 service-time summaries.       |
| Public-notice duration                      | Match 14-day minimum mass and long objection tail. |
| Inspection waiting/travel proxy by district | D3 and D5 should be slower.                        |
| Arrival process                             | Match monthly and weekday arrival patterns.        |

Use visual checks such as ECDFs, QQ plots, and calendar heatmaps, plus quantitative summaries. Formal tests are secondary because with 31,200 cases, small deviations will be statistically significant even if operationally unimportant.

**Resource-utilization validation.**

Validate simulated utilization against HR capacity and observed throughput:

* clerk utilization around Monday spikes
* planner utilization by simple-only planners versus general planners
* fire-review utilization under Tuesday-Thursday calendar
* environmental-review utilization after reserving 40% non-permit time
* inspector utilization including travel and district batching
* legal utilization around council-meeting weeks

Because start timestamps are missing for many activities, utilization cannot be validated purely from completion events. Use HR calendars, staff interviews, and workload estimates.

**Bottleneck validation.**

Check whether the model reproduces known bottleneck signatures:

* completeness queues spike after Monday submissions
* applicant response dominates Simple-with-missing-docs variants
* environmental and legal queues interact for Commercial cases
* Complex variance has a long tail due to public notice, appeal/rework, and council calendar
* inspection rework variants are sensitive to inspector availability and applicant readiness
* D3/D5 show longer inspection-related delays

**Out-of-sample validation.**

Split the 18-month log into calibration and validation windows, for example:

* months 1-12 for calibration, months 13-18 for validation
* rolling 6-month windows
* peak-season validation separately from non-peak validation

A model that matches only average months but fails in March-May or September-November should not be accepted for policy comparison.

**Cross-case dependency validation.**

Validate dependency mechanisms using cluster-level summaries:

* weekly submissions by top architects
* number of same-architect/same-district clusters
* inspection grouping frequency and waiting penalty
* public-notice long-duration clustering by district/time
* backlog spillovers after top-architect bursts

If the flattened log cannot validate these directly, mark the dependency parameters as uncertain and include them in sensitivity analysis.

# 7. Decision criteria

The municipality should select interventions using a **multi-criteria decision rule**, not only average cycle-time reduction. A policy is attractive only if it improves speed, tails, fairness, and robustness without creating unacceptable compliance or workload risk.

| Criterion                    | Metric                                                                                       | Suggested decision threshold or interpretation                                                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Median duration              | Median calendar days from `Submit application` to terminal outcome, by case type and overall | Prefer policies reducing median by at least 5-10% without worsening any major case type by more than 3-5%.                                                            |
| Tail duration                | p90 and p95 duration by case type and district                                               | Strong preference for policies reducing p90 by at least 10-15%, especially for Commercial, Complex variance, and inspection rework variants.                          |
| SLA compliance               | Share completed within the municipality’s formal SLA, by case type                           | Because the prompt does not provide a formal SLA, use existing municipal targets if available; otherwise compare relative improvement and avoid subgroup degradation. |
| Backlog                      | Average and p90 WIP; cases older than 30, 60, 120, and 180 days                              | Reject policies that reduce medians while increasing aged backlog.                                                                                                    |
| Fairness across districts    | p90 duration and SLA compliance by district, especially D3 and D5                            | No district should lose more than 2-3 percentage points of SLA compliance unless explicitly justified.                                                                |
| Fairness across architects   | Outcomes for top-20 architects versus smaller architects                                     | D7 appointment slots must not concentrate benefits only among large architects.                                                                                       |
| Resource utilization         | Utilization by pool, overtime, idle time, queue starvation                                   | Sustainable target range roughly 70-85%; sustained >90% for specialist pools signals fragility.                                                                       |
| Rework                       | Completeness rework rate, inspection rework rate, legal rework rate                          | Prefer policies reducing rework; reject those that hide rework upstream or shift it to appeals.                                                                       |
| Applicant/third-party burden | Pre-submission effort, missing-document response, no-show risk                               | D1 should be assessed on total applicant burden, not only formal municipal cycle time.                                                                                |
| Compliance and safety        | Incorrect no-inspection eligibility, legal-precheck errors, environmental triage errors      | D2 and D8 require explicit risk tolerance; operational speed cannot dominate statutory controls.                                                                      |
| Robustness                   | Probability policy beats baseline under S1-S5 stress scenarios                               | Prefer policies that improve baseline and remain non-harmful in at least most stress scenarios.                                                                       |
| Spillovers                   | Effect on non-target case types and downstream queues                                        | Reject policies that improve Simple renovation while substantially worsening Commercial or Complex variance tails.                                                    |
| Cost-effectiveness           | Staff cost, temporary inspector cost, system cost per day saved or SLA breach avoided        | D4 should be justified by peak-month benefit; D10 should be checked for interaction effects.                                                                          |

A practical selection rule:

```text
Shortlist interventions that:
1. reduce overall p90 duration by at least 10%;
2. improve or preserve SLA compliance for every case type;
3. do not worsen D3/D5 p90 duration;
4. keep specialist utilization below sustained overload;
5. remain beneficial under at least three stress scenarios;
6. have no unresolved compliance risk.
```

Under that rule, D10 may be promising because it combines document-quality improvement, low-risk inspection removal, batching, and peak inspection capacity. But it should not be declared optimal until calibrated and validated, because it may simply move the bottleneck from inspections to planning, environmental review, decision drafting, or legal check.

def add_elapsed_columns(
    df: pd.DataFrame,
    start_timestamp_col: Optional[str] = None,
    completion_timestamp_col: str = "time:timestamp",
) -> pd.DataFrame:
    """
    Add timing columns.

    The excerpt provides completion timestamps only. Therefore:
    - elapsed_since_prev_completion is observable;
    - true service_time and true waiting_before_activity are not identifiable;
    - if a start timestamp column exists in the full log, use it to split waiting/service.
    """
    out = df.sort_values(
        ["case:concept:name", completion_timestamp_col]
    ).copy()

    group = out.groupby("case:concept:name", sort=False)

    out["prev_activity"] = group["concept:name"].shift(1)
    out["prev_completion_timestamp"] = group[completion_timestamp_col].shift(1)

    out["elapsed_since_prev_completion"] = (
        out[completion_timestamp_col] - out["prev_completion_timestamp"]
    )

    out["elapsed_since_prev_completion_hours"] = (
        out["elapsed_since_prev_completion"].dt.total_seconds() / 3600.0
    )

    if start_timestamp_col is not None and start_timestamp_col in out.columns:
        out[start_timestamp_col] = pd.to_datetime(out[start_timestamp_col])

        out["observed_service_time"] = (
            out[completion_timestamp_col] - out[start_timestamp_col]
        )
        out["observed_service_time_hours"] = (
            out["observed_service_time"].dt.total_seconds() / 3600.0
        )

        out["observed_wait_before_activity"] = (
            out[start_timestamp_col] - out["prev_completion_timestamp"]
        )
        out["observed_wait_before_activity_hours"] = (
            out["observed_wait_before_activity"].dt.total_seconds() / 3600.0
        )
    else:
        # Explicitly mark these as unavailable, rather than pretending that
        # inter-event time is service time.
        out["observed_service_time_hours"] = np.nan
        out["observed_wait_before_activity_hours"] = np.nan

    return out

    name: str
    working_days: Tuple[int, ...]  # Monday=0, Sunday=6
    start_hour: float
    end_hour: float
    unavailable_weeks: set[int] = field(default_factory=set)

class ArrivalGenerator:
    """
    Non-stationary marked arrival generator.

    A calibrated version would use:
    - month factors;
    - weekday factors;
    - case-type mix;
    - architect burst model;
    - district and value distributions.
    """

    def __init__(self, rng: np.random.Generator, scenario: Scenario):
        self.rng = rng
        self.scenario = scenario

        self.case_mix = {
            "Simple renovation": 0.45,
            "New residential": 0.28,
            "Commercial": 0.17,
            "Complex variance": 0.10,
        }

    def month_factor(self, timestamp: pd.Timestamp) -> float:
        if timestamp.month in {3, 4, 5, 9, 10, 11}:
            return self.scenario.peak_arrival_multiplier
        return 1.0

    def weekday_factor(self, timestamp: pd.Timestamp) -> float:
        # Monday=0, Wednesday=2.
        if timestamp.weekday() == 0:
            return self.scenario.monday_multiplier
        if timestamp.weekday() == 2:
            return 1.0
        return 1.2

    def sample_case_type(self) -> str:
        labels = list(self.case_mix.keys())
        probs = np.array(list(self.case_mix.values()), dtype=float)
        probs = probs / probs.sum()
        return str(self.rng.choice(labels, p=probs))

    def generate_daily_arrivals(
        self,
        date: pd.Timestamp,
        base_daily_rate: float,
    ) -> List[PermitCase]:
        rate = (
            base_daily_rate
            * self.month_factor(date)
            * self.weekday_factor(date)
        )

        if self.scenario.architect_appointment_slots:
            # Smooth Monday bursts, preserving total demand in this skeleton.
            if date.weekday() == 0:
                rate *= 1.0 - self.scenario.monday_burst_reduction

        # Negative-binomial-like overdispersion could replace Poisson here.
        n = self.rng.poisson(rate)

        cases: List[PermitCase] = []
        for i in range(n):
            case_type = self.sample_case_type()

            district = str(self.rng.choice(["D1", "D2", "D3", "D4", "D5"]))
            architect_id = str(self.rng.choice(["A02", "A17", "A99", "OTHER"]))

            if case_type == "Simple renovation":
                value = float(self.rng.lognormal(mean=10.3, sigma=0.4))
            else:
                value = float(self.rng.lognormal(mean=13.0, sigma=0.8))

            requires_fire = case_type in {"New residential", "Commercial"}
            requires_environment = case_type in {"Commercial"}
            requires_public_notice = case_type in {
                "Complex variance",
                "New residential",
            }

            cases.append(
                PermitCase(
                    case_id=f"SYN-{date.strftime('%Y%m%d')}-{i:04d}",
                    case_type=case_type,
                    district=district,
                    architect_id=architect_id,
                    application_value=value,
                    requires_fire=requires_fire,
                    requires_environment=requires_environment,
                    requires_public_notice=requires_public_notice,
                )
            )

        return cases


class RoutingPolicy:
    """Activity-enabling rules, including interventions."""

    def __init__(self, scenario: Scenario, rng: np.random.Generator):
        self.scenario = scenario
        self.rng = rng

    def needs_inspection(self, case: PermitCase) -> bool:
        if (
            self.scenario.no_inspection_for_low_risk_simple
            and case.case_type == "Simple renovation"
            and case.application_value < self.scenario.low_risk_value_threshold
            and case.prior_violations is False
        ):
            return False
        return True

    def needs_legal_check(self, case: PermitCase) -> bool:
        if case.case_type in {"Commercial", "Complex variance"}:
            return True
        if case.requires_public_notice:
            return True
        return bool(self.rng.random() < 0.15)

    def missing_document_loop_occurs(self, case: PermitCase) -> bool:
        base_prob = {
            "Simple renovation": 0.25,
            "New residential": 0.35,
            "Commercial": 0.40,
            "Complex variance": 0.50,
        }[case.case_type]

        if self.scenario.pre_submission_checker:
            base_prob *= 1.0 - self.scenario.missing_doc_loop_reduction

        return bool(self.rng.random() < base_prob)

    def public_objection_occurs(self, case: PermitCase) -> bool:
        if not case.requires_public_notice:
            return False

        base_prob = {
            "Simple renovation": 0.02,
            "New residential": 0.15,
            "Commercial": 0.20,
            "Complex variance": 0.35,
        }[case.case_type]

        prob = min(1.0, base_prob * self.scenario.objection_multiplier)

        if self.scenario.objection_early_warning:
            # Early warning should reduce duration or severity, not necessarily
            # make the objection event disappear.
            pass

        return bool(self.rng.random() < prob)


class ServiceTimeSampler:
    """
    Placeholder service-time sampler.

    A calibrated version would fit distributions to the full event log and
    empirical summaries, stratified by case type, activity, district, and
    resource where enough data is available.
    """

    def __init__(self, rng: np.random.Generator):
        self.rng = rng

    def hours(self, activity: str, case: PermitCase) -> float:
        # Median-ish placeholders based on the supplied summaries.
        medians = {
            "Completeness check": 25.0 / 60.0,
            "Request missing documents": 10.0 / 60.0,
            "Planning review": 3.5,
            "Fire-safety review": 2.5,
            "Environmental review": 4.0,
            "Inspection scheduling": 20.0 / 60.0,
            "Site inspection": 1.0,
            "Decision drafting": 2.0,
            "Legal check": 3.0,
            "Issue permit": 5.0 / 60.0,
            "Reject application": 0.5,
        }
        median = medians.get(activity, 1.0)

        # Simple lognormal placeholder. Calibration should replace this.
        sigma = 0.6
        mu = math.log(max(median, 0.01))
        value = float(self.rng.lognormal(mean=mu, sigma=sigma))

        if activity == "Site inspection" and case.district in {"D3", "D5"}:
            value += 0.5  # placeholder district travel penalty

        return value

class PermitDigitalTwinSimulator:
    """
    Placeholder discrete-event simulator.

    A production implementation could use SimPy/salabim/custom event calendar.
    This skeleton only shows the separation of:
    - arrival generation;
    - routing;
    - service-time sampling;
    - resource calendars;
    - experiment execution.
    """

    def __init__(
        self,
        scenario: Scenario,
        seed: int,
        start_date: str,
        end_date: str,
        base_daily_rate: float,
    ):
        self.scenario = scenario
        self.rng = np.random.default_rng(seed)
        self.start_date = pd.Timestamp(start_date)
        self.end_date = pd.Timestamp(end_date)
        self.base_daily_rate = base_daily_rate

        self.arrivals = ArrivalGenerator(self.rng, scenario)
        self.routing = RoutingPolicy(scenario, self.rng)
        self.service_times = ServiceTimeSampler(self.rng)
        self.resources = CalendarFactory.build(scenario)

    def run(self) -> SimulationResult:
        synthetic_records: List[Dict[str, Any]] = []

        for date in pd.date_range(self.start_date, self.end_date, freq="D"):
            new_cases = self.arrivals.generate_daily_arrivals(
                date=date,
                base_daily_rate=self.base_daily_rate,
            )

            for case in new_cases:
                # This is only a placeholder path simulation. A real DES would:
                # - enqueue each enabled activity;
                # - seize resources according to calendars;
                # - schedule activity completion events;
                # - synchronize parallel branches before Decision drafting;
                # - maintain WIP and backlog;
                # - apply batching and cross-case effects.
                case.timestamps["Submit application"] = date

                activities = ["Submit application", "Completeness check"]

                if self.routing.missing_document_loop_occurs(case):
                    activities.extend(
                        [
                            "Request missing documents",
                            "Receive missing documents",
                            "Completeness check",
                        ]
                    )

                activities.append("Planning review")

                if case.requires_fire:
                    activities.append("Fire-safety review")
                if case.requires_environment:
                    activities.append("Environmental review")
                if case.requires_public_notice:
                    activities.append("Public-notice period")

                if self.routing.needs_inspection(case):
                    activities.extend(["Inspection scheduling", "Site inspection"])

                activities.append("Decision drafting")

                if self.routing.needs_legal_check(case):
                    activities.append("Legal check")

                activities.append("Issue permit")

                t = pd.Timestamp(date)
                for activity in activities:
                    service_hours = self.service_times.hours(activity, case)

                    # Placeholder elapsed-time logic. Real engine should use
                    # queues and calendars, not simple accumulation.
                    if activity == "Receive missing documents":
                        elapsed_hours = float(self.rng.lognormal(np.log(5 * 24), 0.8))
                    elif activity == "Public-notice period":
                        objection = self.routing.public_objection_occurs(case)
                        if objection:
                            elapsed_hours = 60 * 24
                            if self.scenario.objection_early_warning:
                                elapsed_hours *= 0.75
                        else:
                            elapsed_hours = 14 * 24
                    else:
                        elapsed_hours = service_hours

                    t = t + pd.Timedelta(hours=elapsed_hours)

                    synthetic_records.append(
                        {
                            "case:concept:name": case.case_id,
                            "concept:name": activity,
                            "time:timestamp": t,
                            "case_type": case.case_type,
                            "district": case.district,
                            "architect_id": case.architect_id,
                            "application_value": case.application_value,
                            "scenario": self.scenario.name,
                        }
                    )

        completed = pd.DataFrame(synthetic_records)

        resource_summary = pd.DataFrame(
            [
                {
                    "resource_pool": name,
                    "effective_capacity": pool.effective_capacity,
                    "calendar": pool.calendar.name,
                }
                for name, pool in self.resources.items()
            ]
        )

        queue_summary = pd.DataFrame(
            columns=[

            ]
        )

        return SimulationResult(
            scenario_name=self.scenario.name,
            completed_cases=completed,
            resource_summary=resource_summary,
            queue_summary=queue_summary,
        )

def summarize_case_durations(simulated_log: pd.DataFrame) -> pd.DataFrame:
    if simulated_log.empty:
        return pd.DataFrame()

    case_times = (
        simulated_log.groupby(["scenario", "case:concept:name"])
        .agg(
            start=("time:timestamp", "min"),
            end=("time:timestamp", "max"),
            case_type=("case_type", "first"),
            district=("district", "first"),
            architect_id=("architect_id", "first"),
        )
        .reset_index()
    )
    case_times["duration_days"] = (
        case_times["end"] - case_times["start"]
    ).dt.total_seconds() / (24 * 3600)

    summary = (
        case_times.groupby(["scenario", "case_type"])
        .agg(
            n_cases=("case:concept:name", "nunique"),
            median_days=("duration_days", "median"),
            p90_days=("duration_days", lambda s: s.quantile(0.90)),
            p95_days=("duration_days", lambda s: s.quantile(0.95)),
        )
        .reset_index()
    )

    return summary


def run_experiment_matrix(
    seeds: Iterable[int],
    start_date: str = "2026-01-01",
    end_date: str = "2026-12-31",
    base_daily_rate: float = 50.0,
) -> pd.DataFrame:
    all_summaries: List[pd.DataFrame] = []

    for scenario in build_scenarios():
        for seed in seeds:
            sim = PermitDigitalTwinSimulator(
                scenario=scenario,
                seed=seed,
                start_date=start_date,
                end_date=end_date,
                base_daily_rate=base_daily_rate,
            )
            result = sim.run()
            summary = summarize_case_durations(result.completed_cases)
            summary["seed"] = seed
            all_summaries.append(summary)

    return pd.concat(all_summaries, ignore_index=True)
