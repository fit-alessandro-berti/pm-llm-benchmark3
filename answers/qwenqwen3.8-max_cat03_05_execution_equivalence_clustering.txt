## 1. Equivalence design space

I treat each execution as a typed temporal event-object graph centered on a lead `Order`: events are nodes, objects are typed nodes, event-to-object incidence is explicit, object identifiers are local unless marked `EXT`, and O2O notes are additional labeled object-object edges or qualifiers. Different equivalence notions are obtained by choosing which graph features are quotiented away.

### 1.1 Activity-sequence equivalence

**Definition.** Project an execution to the ordered list of activity labels:
`trace(X) = (a1, a2, ..., an)`. Two executions are activity-sequence equivalent iff these label sequences are identical. If events have the same timestamp, I either sort same-time events by activity label for reproducibility or, preferably, treat each timestamp block as a multiset and compare multisets.

**Preserved invariants.** Activity labels, repetition of activities, and the chosen total or block-wise order of activities.

**Discarded information.** All object types, object identifiers, multiplicities, E2O incidence, external-object flags, O2O qualifiers, and business semantics.

**Equivalence properties.** Reflexive, symmetric, transitive.

**Concurrency.** Same-time events are equivalent under permutation if the relation is defined over timestamp blocks. If a total order is imposed by tie-breaking, concurrency is artificially serialized; this should be documented.

### 1.2 Typed structural equivalence under identifier renaming

**Definition.** Represent an execution as a labeled temporal bipartite graph with event nodes, object nodes, event-object incidence edges, and precedence edges between events. Two executions are typed-structurally equivalent iff there is an isomorphism preserving:

- event activity labels;
- event order or the chosen partial order;
- object types;
- external/local flag;
- event-object incidence;
- repeated events.

Raw local identifiers are renamed away. External identifiers are also canonicalized, but their `EXT` status is preserved.

**Preserved invariants.** Object-centric shape: how many objects of each type participate, which events touch them, whether they are external, and the temporal ordering of events.

**Discarded information.** Raw identifiers and usually O2O business qualifiers, unless a qualified variant is used.

**Equivalence properties.** Reflexive, symmetric, transitive because graph isomorphism is an equivalence relation.

**Concurrency.** If events are concurrent, replace total precedence edges with a partial order. Isomorphism then preserves only causal or observed precedence, not arbitrary interleavings.

### 1.3 Business-semantic equivalence

**Definition.** Define a canonical business motif from selected object-centric features. For the preferred clustering below, I use:

- `split_pkg`: more than one local `Package` or more than one `Pack Package` event.
- `ext_log`: an external object participates in logistics activities, especially `Pack Package` or `Dispatch`.
- `ext_fin`: an external object participates in financial activities, especially `Issue Invoice` or `Record Payment`.
- `replacement`: O2O qualifiers or event-object evidence indicating removal/substitution before dispatch, e.g. `removed_before_dispatch`.
- `return_repack`: return-related activities or qualifiers, e.g. `Return Item`, `Inspect Return`, repack replacement.

The motif is chosen deterministically with priority:
`replacement` > `return_repack` > `ext_log` > `ext_fin` > `split_pkg` > `standard`.

Two executions are business-semantically equivalent iff their canonical motif signatures are equal.

**Preserved invariants.** Business-critical deviations: split fulfillment, cross-order logistics sharing, cross-order financial sharing, replacement, return/repack.

**Discarded information.** Exact local identifiers, exact Add Item order, some count differences such as whether a split fulfillment has one or two deliveries/payments, and some timestamp-level interleaving.

**Equivalence properties.** Reflexive, symmetric, transitive because it is equality of a canonical signature.

**Concurrency.** The motif predicates are existence-based and therefore robust to concurrent permutations. If pre/post-dispatch distinction matters, use O2O qualifiers or causal partial order rather than raw timestamps.

### 1.4 Optional fourth relation: qualified lifecycle equivalence

A useful finer relation is typed structural equivalence plus O2O qualifiers and event-role qualifiers. It preserves predicates such as `partial_settles`, `completes_settlement`, `removed_before_dispatch`, and `replaces`. This is important for compliance and root-cause analysis, but it can produce very small clusters.

## 2. Canonical signatures

The preferred signature canonicalizes local identifiers, preserves external flags, event-object incidence, repeated activities, and selected O2O qualifiers, then abstracts to a business motif. In production, the renaming step should use a typed temporal-graph canonicalization such as Weisfeiler-Lehman hashing or a graph-isomorphism library. The exhaustive version below makes the invariance explicit.

```python
from collections import Counter

LOGISTICS_ACT = {"Pack Package", "Dispatch"}
FINANCIAL_ACT = {"Issue Invoice", "Record Payment"}
REPLACEMENT_QUALS = {"removed_before_dispatch", "replaces_item", "replacement"}
RETURN_QUALS = {"repack_replaces", "return_inspected"}
RETURN_ACTS = {"Return Item", "Inspect Return"}

def is_ext(obj_id):
    return str(obj_id).startswith("EXT")

def all_type_external_preserving_bijections(objects):
    # objects: set of (obj_id, obj_type, is_external)
    # Return all bijections that map:
    #   local  -> local
    #   EXT    -> EXT
    #   type T -> type T
    # For small examples this is feasible; for real logs use WL/BLISS.
    ...

def rename_events(events, mapping):
    renamed = []
    for e in events:
        renamed.append({
            "act": e["act"],
            "objects": {
                typ: sorted(mapping[oid] for oid in ids)
                for typ, ids in e["objects"].items()
            }
        })
    return renamed

def rename_o2o(o2o, mapping):
    return sorted((mapping[s], p, mapping[o]) for s, p, o in o2o)

def count_local_objects(events):
    c = Counter()
    for e in events:
        for typ, ids in e["objects"].items():
            for oid in ids:
                if not is_ext(oid):
                    c[typ] += 1
    # Count distinct canonical objects, not incidences, in a full implementation.
    return c

def motif_signature(events, o2o):
    labels = [e["act"] for e in events]
    counts = count_local_objects(events)

    ext_log = any(
        e["act"] in LOGISTICS_ACT and any(is_ext(oid) for ids in e["objects"].values() for oid in ids)
        for e in events
    )
    ext_fin = any(
        e["act"] in FINANCIAL_ACT and any(is_ext(oid) for ids in e["objects"].values() for oid in ids)
        for e in events
    )

    quals = {p for _, p, _ in o2o}
    replacement = bool(quals & REPLACEMENT_QUALS)
    ret_repack = bool(labels and (set(labels) & RETURN_ACTS)) or bool(quals & RETURN_QUALS)

    split_pkg = counts.get("Package", 0) > 1 or labels.count("Pack Package") > 1

    if replacement:
        motif = "REPLACEMENT"
    elif ret_repack:
        motif = "RETURN_REPACK"
    elif ext_log:
        motif = "EXT_LOGISTICS"
    elif ext_fin:
        motif = "EXT_FINANCIAL"
    elif split_pkg:
        motif = "SPLIT_FULFILLMENT"
    else:
        motif = "STANDARD_ISOLATED"

    return f"{motif}|pkg_split={split_pkg}|ext_log={ext_log}|ext_fin={ext_fin}"

def preferred_signature(events, o2o):
    best = None
    objects = collect_objects_with_type_and_external_flag(events)
    for mapping in all_type_external_preserving_bijections(objects):
        ev = rename_events(events, mapping)
        oo = rename_o2o(o2o, mapping)
        sig = motif_signature(ev, oo)
        if best is None or sig < best:
            best = sig
    return best
```

The signature is invariant under local identifier renaming because all admissible type- and externality-preserving renamings are considered and the lexicographically smallest motif is returned.

## 4. Cluster interpretations

### SEM-STD: standard isolated order-to-cash

**Signature.** `STANDARD_ISOLATED|pkg_split=False|ext_log=False|ext_fin=False`

**Business behavior.** A lead order is created, items are added, one package is packed and dispatched, one invoice is issued, and one payment settles it. X1 and X2 differ only in local identifiers and the order in which indistinguishable Add Item events appear.

**Risks/opportunities.** Low operational complexity. Suitable for straight-through processing and automation. Main opportunity is maintaining a clean order-to-cash baseline.

**Poor flattening.** A pure activity-trace flattening is acceptable for high-level reporting but hides object coverage: it cannot show that both items are contained in the same package or that one payment settles one invoice.

**Stability.** Very stable under identifier renaming, timestamp jitter, and Add Item permutation. It remains stable if a missing `Create Order` is repaired, provided no exception or external object is introduced.

### SEM-SPLIT: split fulfillment family

**Signature.** `SPLIT_FULFILLMENT|pkg_split=True|ext_log=False|ext_fin=False`

**Business behavior.** The order requires more than one package. X3 splits packages but consolidates delivery and settlement. X4 splits packages and deliveries, and also uses two payment events for partial and completing settlement. The preferred semantic cluster groups them because the core business motif is “fulfillment cannot be completed in one package.”

**Risks/opportunities.** Risks include split shipments, inconsistent customer communication, higher logistics cost, and partial-payment reconciliation. Opportunities include pack optimization and shipment consolidation.

**Poor flattening.** A case table with one row per order hides package-delivery-payment linkage. An activity trace that collapses repeated `Pack Package` or `Record Payment` events would incorrectly make X3 or X4 look like a standard order.

**Stability.** Stable as long as multiple packages are real. If duplicate Pack events are incorrectly merged during data repair, X3 may collapse into standard. If X4’s second payment is treated as an amount attribute, the financial subtype is lost, but the split-fulfillment motif remains.

### SEM-EXT-LOG: cross-order logistics consolidation

**Signature.** `EXT_LOGISTICS|pkg_split=False|ext_log=True|ext_fin=False`

**Business behavior.** X5’s local order is billed locally, but its logistics execution is not isolated: the package and dispatch involve an external order and external item. This represents co-packing or consolidated shipment across orders.

**Risks/opportunities.** Risks include dependency on another order’s availability, cost allocation, delivery SLA ambiguity, and limited visibility into the external object’s lifecycle. The opportunity is logistics consolidation and reduced shipping cost.

**Poor flattening.** Flattening to local objects only, or dropping `EXT` objects, makes X5 indistinguishable from X1. That hides the cross-order dependency.

**Stability.** Stable if external flags are preserved. If external objects are ignored, reclassified as local, or removed during repair, the execution collapses into the standard cluster.

### SEM-EXT-FIN: cross-order shared billing/settlement

**Signature.** `EXT_FINANCIAL|pkg_split=False|ext_log=False|ext_fin=True`

**Business behavior.** X6 has local logistics, but the invoice and payment are shared with an external order. The financial execution is consolidated, while fulfillment remains isolated.

**Risks/opportunities.** Risks include revenue allocation, tax treatment, dunning responsibility, and unclear settlement attribution. The opportunity is consolidated billing for related orders or customers.

**Poor flattening.** A traditional relational flattening that assigns each invoice to exactly one order will either drop the external order or arbitrarily choose one. A payment flattening that stores only total amount hides the absence of order-level allocation.

**Stability.** Stable if external financial participation is preserved. If `EXT-OB` is ignored, X6 becomes structurally and semantically indistinguishable from X1.

### SEM-REPLACE: pre-dispatch replacement/substitution

**Signature.** `REPLACEMENT|pkg_split=False|ext_log=False|ext_fin=False`

**Business behavior.** X7 looks like a standard order at the activity-label level, but O2O qualifiers show that one item was removed or substituted before dispatch. The package initially contains both items, but dispatch is qualified by replacement/removal.

**Risks/opportunities.** Risks include inventory mismatch, incorrect billing, customer dissatisfaction, and compliance issues if substitution is not authorized. The opportunity is resilient fulfillment through substitution.

**Poor flattening.** Activity-only flattening is especially poor: X7 appears identical to X1. Object flattening without O2O qualifiers may also fail, unless it preserves the anomalous item participation in the Dispatch event.

**Stability.** Less stable if O2O qualifiers are dropped. If repair adds explicit removal or substitution events, the cluster remains meaningful if those events or qualifiers are retained.

### SEM-RETURN: return, inspection, repack, redispatch

**Signature.** `RETURN_REPACK|pkg_split=True|ext_log=False|ext_fin=False`

**Business behavior.** X8 contains a reverse-logistics loop: an item is returned from the first delivery, inspected, repacked into a new package, and dispatched again. Invoice and payment occur after the final fulfillment state.

**Risks/opportunities.** Risks include return fraud, inventory disposition errors, delayed settlement, and additional transport cost. Opportunities include refurbishment, restocking, and customer retention.

**Poor flattening.** Flattening to one delivery per order hides the second dispatch. Treating the return as a separate order breaks the link to the original order. Activity-only traces lose the object-level connection between returned item, original delivery, and repack.

**Stability.** Stable if return and repack events are preserved. Adding a missing `Create Order` would not change the cluster. Removing the second dispatch as a supposed duplicate would destroy the motif.

## 5. Borderline cases

### X1 versus X2

Activity-sequence and typed-structural equivalence agree: they are equivalent. A raw exact equivalence that treats local identifiers as meaningful would separate them. Another possible but unsupported business rule, such as “first-added item has priority,” could also separate them; without such a rule, the item-identifier order should be ignored.

### X1 versus X5

Activity-sequence equivalence says X1 and X5 are equivalent because both have the same labels. Typed-structural and preferred semantic equivalence disagree because X5 contains external objects in logistics events. If externality is ignored, X5 looks like a standard order; if cross-order logistics dependency matters, it is a different business behavior.

### X1 versus X6

Again, activity labels are identical. Typed-structural equivalence separates X6 because external objects appear in invoice and payment events. Business-semantic equivalence separates it because shared financial execution creates allocation and reconciliation semantics absent from X1.

### X1 versus X7

Activity-sequence equivalence collapses them. Typed-structural equivalence already separates them if the Dispatch event’s item participation is preserved. Qualified or business-semantic equivalence separates them strongly because of `removed_before_dispatch`. If qualifiers and item-level dispatch details are ignored, X7 can be falsely normalized into the standard cluster.

### X3 versus X4

Activity-sequence and typed-structural equivalence separate them: X3 has two Pack events before one Dispatch and one payment; X4 interleaves Pack/Dispatch and has two payments. The preferred business-semantic equivalence groups them as split fulfillment because both require multiple packages. A compliance-oriented financial equivalence would separate them because X4 has partial settlement.

### X4 versus X8

Both have repeated Pack and Dispatch events, so a very coarse multiplicity-based equivalence could group them as “multi-package/multi-dispatch.” Activity-sequence and semantic equivalence separate them because X8 contains return and inspection activities and a repack motif. If return events are ignored or modeled as a separate order, X8 may be incorrectly flattened into a split-delivery case.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py key structure used by `pm4py.cluster_equivalent_ocel` should be understood as an exact structural fingerprint of each lead-object execution. It preserves the observed event sequence around the lead object, the activity labels, and the related object identifiers/types participating in those events. If object-object relations or qualifiers are included in the OCEL extraction, they contribute to the key as supplied, but they are not semantically interpreted. The key is therefore closer to typed exact equivalence than to business equivalence.

Raw object identifiers make exact clusters too fine because every new order, item, package, invoice, or payment can create a new fingerprint. X1 and X2 are business-identical, but an exact key containing raw IDs may place them in different clusters. Similarly, local identifier permutations in repeated Add Item events can create artificial distinctions.

To canonicalize, first normalize identifiers by type and external flag, then compute a motif signature. Exact PM4Py clusters can then be merged into business clusters. Exact equivalence is preferable when debugging data quality, detecting duplicate executions, performing legal audit, or checking conformance where exact object identity and exact event-object incidence matter. Coarser business clustering is preferable for operational reporting and segmentation.

`max_objs` matters because large events or highly connected cross-order executions can make key construction expensive or can truncate object participation. If `max_objs` drops an external object from a Pack or Invoice event, X5 or X6 could be incorrectly merged with X1. For large connected executions, use blocking by time or lead object, canonicalize external references separately, and avoid unbounded graph canonicalization.


## 7. Robustness analysis

**Ignore all O2O qualifiers.** X7 is the most affected. Without `removed_before_dispatch`, it may collapse into the standard cluster unless the Dispatch event’s item participation is still used. X4 loses partial-settlement nuance but remains a split-fulfillment case under the preferred motif. X8 remains a return cluster because return activities are still present.

**Ignore external objects.** X5 and X6 collapse toward X1. Typed-structural clusters become much coarser, and business risk is hidden. This perturbation is dangerous for logistics cost allocation and financial reconciliation.

**Collapse repeated same-label events.** This is destructive. X3’s two Pack events may become one, making it look standard at the activity level. X4’s second Dispatch or second Record Payment may disappear, hiding split delivery or partial settlement. X8’s second Pack/Dispatch may be treated as duplicate, destroying the repack motif. Repeated activities are often business signal, not noise.

**Treat Pack and Dispatch order as partial order.** If only causal dependencies are preserved, X3 and X4 remain distinct as long as object incidence is preserved: X3 has two packages entering one delivery, while X4 has two package-delivery pairs. If the partial order is made too permissive and object incidence is ignored, X3 and X4 may merge incorrectly.

**Treat payment multiplicity as amount attribute.** X4’s two payments become one payment with amount or settlement-status attributes. Activity and typed-structural clusters become coarser. The preferred semantic cluster remains split fulfillment, but financial compliance loses the explicit partial-settlement event. If partial settlement is regulatory or audit-relevant, payment events should remain structural.

## 8. Limitations and recommendation

No single equivalence notion is best for all tasks.

**Compliance monitoring.** Use qualified typed-structural equivalence: preserve event-object incidence, external flags, payment events, and O2O qualifiers. Compliance needs to detect shared invoices, partial settlements, and unauthorized substitutions.

**Operational segmentation.** Use the preferred business-semantic motif equivalence. It gives actionable groups such as standard, split fulfillment, external logistics, external financial, replacement, and return.

**Root-cause analysis.** Use fine-grained typed or qualified lifecycle equivalence. Root cause often depends on exact temporal ordering, object participation, and qualifiers such as `removed_before_dispatch` or `repack_replaces`.

**Descriptive reporting.** Use activity-sequence equivalence or a coarse business motif. These are easier to communicate but should not be used for audit or diagnosis.

The main limitation of the preferred semantic clustering is that it intentionally abstracts from some count differences, such as X4’s split deliveries and payments. That abstraction is useful for segmentation but inappropriate when the exact financial or delivery pattern is the analytic target. Therefore, equivalence level should be chosen by question, not by data alone.
