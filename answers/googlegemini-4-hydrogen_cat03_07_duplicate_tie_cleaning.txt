## 1. Duplicate-handling decision tree

In multi-system Object-Centric Event Logs (OCELs), identical `(timestamp, activity)` pairs arise from fundamentally different mechanisms. Deduplicating purely on surface columns destroys legitimate concurrency and distinct business transitions. The following decision tree classifies candidate event pairs or groups $(e_a, e_b)$ sharing a harmonized `activity` (or a causal/reconciliation link) within a bounded time window $\Delta t$:

```text
Candidate group G = {e_a, e_b, ...} (same timestamp or within t, same or linked activity)

 [1] Identical payload_hash AND identical (source, source_event_key) AND identical E2O object set?
    YES  Exact technical duplicate (re-ingestion / at-least-once delivery)
                DECISION: DROP redundant copy; keep first canonical row and log drop in audit trail.

 NO  Compare objects, source semantics, and reconciliation evidence:
    
     [2] Same physical/business transition confirmed by reconciliation key or authoritative cross-system ID
           (same core objects; differing payloads/enrichments or differing system-specific attributes)?
        YES  Same physical event observed by multiple systems
                    DECISION: MERGE attributes (by source-authority precedence) and relations (verified union);
                       record all source_event_keys in provenance.
    
     [3] One event is an aggregate/summary status generated downstream from the other(s),
           possibly lacking fine-grained objects (e.g., ERP summary lacking Item or Payment)?
        YES  Summary event derived from a detailed event
            Conservative / multi-granularity analysis required?
               DECISION: RETAIN BOTH WITH REFINED LABELS OR QUALIFIERS
                  (e.g., append "[ERP Summary]" and set abstraction_level="summary").
            Single-granularity 1:1 business-transition view required AND summary maps 1:1 to one detail event?
                DECISION: MERGE summary attributes into detailed event (do NOT merge if 1:N across objects).
    
     [4] Harmonized label masks distinct source meanings across systems (e.g., warehouse release vs. carrier acceptance)?
        YES  Harmonization collision between semantically distinct source activities
                    DECISION: RETAIN BOTH WITH REFINED LABELS OR QUALIFIERS
                       (restore source-faithful activity names; keep original harmonized label in provenance).
    
     [5] Disjoint differentiating objects of a discriminating type (e.g., distinct Item I1 vs I2, Payment M1 vs M2),
           even if higher-level context objects (Order O1, Package P1, Invoice V1) are shared?
        YES  Concurrent same-label events involving different objects
                    DECISION: RETAIN BOTH UNCHANGED (preserve distinct eids and E2O links).
    
     [6] Ambiguous object overlap, conflicting timestamps, or missing reconciliation proof?
         YES  Unresolved candidate
                     DECISION: QUARANTINE FOR REVIEW (retain both in working log with review_flag=True;
                        do not merge until domain stewardship resolves).
```

This structure enforces a core principle: **absence of proof of duplication is not proof of duplication**. Only branches `[1]` and `[2]` (plus narrow 1:1 cases of `[3]` under evidence-based merging) reduce event counts.

## 3. Timestamp-tie ordering rules

### Partial-order-to-total-order policy

When multiple events share the same `original_timestamp`, ordering must proceed strictly from **semantic rules** down to **deterministic tie-breakers**, never confusing the two:

1. **Tier 1 — Domain & causal constraints (Semantic):** Physical or business prerequisites across activities (e.g., `Pick Item` precedes `Pack Package`; warehouse release precedes carrier acceptance; detailed source transaction precedes downstream ERP summary message).
2. **Tier 2 — Lifecycle constraints on shared objects (Semantic):** Intra-object state transitions on a shared object (e.g., for `M1`, `Authorize Payment` must precede `Capture Payment`; for `V1`, `Issue Invoice` precedes invoice balance update).
3. **Tier 3 — Within-source sequence (`source_seq`) (Semantic within single source):** Valid **only** when comparing two events emitted by the *same* `source` system (e.g., `CARRIER` `seq 1 < seq 2`; `PSP` `seq 400 < 401 < 402`). Never compare `source_seq` across systems (`WMS 110` vs `ERP 30` is meaningless).
4. **Tier 4 — Source-specific semantics (Semantic / Architectural):** Known producer-consumer relationships between systems (e.g., `WMS` operational event precedes `ERP` status summary triggered by that message; `PSP` payment execution precedes `ERP` payment balance posting).
5. **Tier 5 — Ingestion time (`ingested_at`) (Non-semantic / Diagnostic only):** **Excluded** from primary ordering because asynchronous queues and batch delays invert business order (Fact 9). May only break ties between genuinely concurrent events as an arbitrary deterministic key if explicitly documented—never overriding Tiers 1–4.
6. **Tier 6 — Stable deterministic fallback (Merely deterministic):** Canonical lexicographical order on `(activity, discriminating_object_id, eid)` so repeated pipeline runs yield identical total orders without claiming physical precedence.

### Why premature microseconds encode a false story

If an engineer runs `ocel_add_index_based_timedelta` *before* resolving Tiers 1–4, PM4Py assigns synthetic microseconds according to raw row order or ingestion order. Because `e07` or `e15` could appear before `e06` or `e13`—or `e10` before `e09`—those synthetic microseconds become indistinguishable from true sub-second measurements in downstream discovery. Process miners then infer impossible directly-follows edges (e.g., `Capture Payment -> Authorize Payment` or `Handover to Carrier -> Accept Package at Carrier`), turning an arbitrary serialization order into a permanent structural claim.

### Intended orders for timestamp-tie groups

* **`e03–e07` at `10:00:00` (after merging `e03+e04 -> e03`):**
  * *Semantic partial order:* $\{e03, e05\} \prec e06 \prec e07$ (picking items `I1`, `I2` precedes packing `P1`; WMS detail `e06` precedes ERP message-derived summary `e07`). `e03` (`Pick I1`) and `e05` (`Pick I2`) are **concurrent** (`e03 \parallel e05`); cross-system `source_seq` (100 vs 552) is non-comparable.
  * *Admissible orders:* `e03 -> e05 -> e06 -> e07` or `e05 -> e03 -> e06 -> e07` (Conservative); `e03 -> e05 -> e06` or `e05 -> e03 -> e06` (Evidence-merge where `e07` is collapsed into `e06`).
  * *Deterministic total order (Conservative):* **`e03 -> e05 -> e06 -> e07`** (Tier 6 fallback `e03 < e05`).

* **`e08–e10` at `10:15:00`:**
  * *Semantic partial order:* $e08 \prec e09 \prec e10$. Tier 1/4 requires warehouse release (`e08`) before carrier acceptance (`e09`); Tier 3 (`CARRIER` `source_seq` 1 < 2) and Fact 5 require `e09` before `e10`.
  * *Unique admissible & total order:* **`e08 -> e09 -> e10`**.

* **`e11–e16` at `12:00:00` (after merging `e11+e16 -> e11`):**
  * *Semantic partial order:* $e11 \prec e15$, $e12 \prec e13$ (lifecycle on `M1`), $\{e13, e14\} \prec e15$ (Fact 8/Tier 4: ERP summary follows payment messages), and within `PSP` Tier 3 gives $e12\,(400) \prec e13\,(401) \prec e14\,(402)$. Note that `M1` capture (`e13`) and `M2` capture (`e14`) are business-wise independent partial payments ordered here by PSP emission sequence, while `e11` (`Issue Invoice`) precedes payment settlement by billing convention (or runs concurrently with `e12` if pre-authorization occurs at checkout).
  * *Admissible orders:* `e11 -> e12 -> e13 -> e14 -> e15` (and `e12 -> e11 -> ...` only if checkout pre-auth precedes invoicing).
  * *Deterministic total order:* **`e11 -> e12 -> e13 -> e14 -> e15`**.

## 4. Conservative cleaning pipeline

The conservative pipeline minimizes semantic alteration and preserves multi-granularity observability:

1. **Snapshot & metadata preservation:** Deep-copy `ocel_raw`; copy `ocel:timestamp` into `original_timestamp` and `ocel:activity` into `original_activity`, retaining `source`, `source_event_key`, `source_seq`, `ingested_at`, and `payload_hash`.
2. **Verified-pair attribute & relation merging:** Merge only pairs backed by explicit cross-system identity proof:
   * `e03 + e04 -> e03` (same physical scan; preserve WMS `location` and append SCANNER provenance).
   * `e11 + e16 -> e11` (same invoice `V1`; merge ERP and BILLING authoritative attributes).
3. **Harmonization collision & abstraction refinement:**
   * Relabel `e08`  `Release Package from Warehouse` and `e09`  `Accept Package at Carrier`.
   * Relabel summary events `e07`  `Pack Package (ERP Summary)` and `e15`  `Reconcile Invoice Payment (ERP Summary)`, tagging `abstraction_level="summary"` so abstraction transitions are not mistaken for rework loops.
4. **Exact-duplicate hygiene pass:** Run `pm4py.ocel_drop_duplicates` *after* steps 2–3 to remove only true identical clones (0 additional drops here).
5. **Deterministic partial-to-total ordering:** Compute a `sort_rank` column encoding Tiers 1–6 (keeping `e03 || e05` and `e13 || e14` flagged `is_concurrent_tie=True`), sort with `pm4py.ocel_sort_by_additional_column`, and apply `pm4py.ocel_add_index_based_timedelta` solely to materialize a deterministic working timestamp while `original_timestamp` remains untouched.

## 5. Aggressive alternatives

### Alternative 1: Evidence-based semantic merging

This pipeline applies everything in the conservative pipeline plus **1:1 derived-summary collapse** where domain evidence confirms a summary adds no distinct business transition:
* Collapses `e07` (`Pack Package` ERP summary) into `e06` (`Pack Package` WMS detail), preserving `ER-150` in provenance and keeping `e06`'s `{O1, I1, I2, P1}` relations.

(An optional stricter variant drops/archives `e15` as a derived reporting view, yielding 13 events / 35 E2O.)

* **Retained event count (primary):** **14 events**, **37 E2O relations**.
* **Most likely semantic damage:** Loses visibility into ERP posting latency (the 55-second delay between WMS pack and ERP status synchronization) inside the main control-flow graph, and hides ERP synchronization failures unless queried from the provenance/audit log.

### Alternative 2: Mechanically aggressive PM4Py merging

This pipeline applies `pm4py.ocel_merge_duplicates(ocel, have_common_object=True)` directly to `ocel_raw` without pre-splitting harmonization collisions or guarding discriminating object types:
* `e03 + e04 + e05` (`10:00:00`, `Pick Item`) collapse into **1 event** because all three share `O1` and `P1`, creating a false single batch pick `{O1, I1, I2, P1}` and erasing `e05`.
* `e06 + e07` (`10:00:00`, `Pack Package`) collapse into **1 event** (`{O1, I1, I2, P1}`).
* `e08 + e09` (`10:15:00`, `Dispatch Package`) collapse into **1 event** (`{O1, P1, D1}`), erasing the warehouse-to-carrier boundary.
* `e11 + e16` (`12:00:00`, `Issue Invoice`) collapse into **1 event** (`{O1, V1}`).
* `e13 + e14 + e15` (`12:00:00`, `Capture Payment`) collapse into **1 event** (`{O1, V1, M1, M2}`) because all three share `O1` and `V1`.

* **Retained event count:** **10 events**, **28 E2O relations**.
* **Most likely semantic damage:** Catastrophic data distortion—distinct partial payments `M1` and `M2` collapse into one capture event, distinct item picks `I1` and `I2` merge, and distinct custody activities (`e08`/`e09`) disappear.

### Why `have_common_object=True` fails to protect `e13` and `e14`

In PM4Py, `have_common_object=True` only requires that two same-activity, same-timestamp events share *at least one* object of *any* type (`O1` or `V1`) to be merged. Because `e13` relates to `{O1, V1, M1}` and `e14` relates to `{O1, V1, M2}`, their intersection `{O1, V1}` is non-empty. The parameter is blind to **disjointness on the discriminating entity type (`Payment`)**: two captures on the same Order and Invoice are distinct precisely because `M1 != M2`. The exact same flaw merges `e03` (`I1`) and `e05` (`I2`) via shared `{O1, P1}`. Protecting such events requires either per-type exclusivity rules (e.g., *do not merge if events hold distinct objects of type `Item` or `Payment`*) or verifying duplicate candidates prior to calling PM4Py utilities.

def _init_provenance_columns(ocel):
    """Add non-destructive provenance columns without mutating ocel_raw."""
    ev = ocel.events.copy()
    ev["original_timestamp"] = ev[ocel.event_timestamp]
    ev["original_activity"] = ev[ocel.event_activity]
    ev["abstraction_level"] = "atomic"
    ev["merged_source_eids"] = ev[ocel.event_id_column].apply(lambda x: json.dumps([x]))
    ev["merged_source_keys"] = ev.apply(
        lambda r: json.dumps([f"{r['source']}:{r['source_event_key']}"]), axis=1
    )
    ev["merge_rule"] = "none"
    ev["is_concurrent_tie"] = False
    ocel.events = ev
    return ocel


def inspect_duplicate_candidates(ocel):
    """Pre-check candidate groups by (timestamp, activity) and object overlap."""
    ev = ocel.events
    rel = ocel.relations
    obj_sets = rel.groupby(ocel.event_id_column)[ocel.object_id_column].apply(set).to_dict()
    obj_by_type = (
        rel.groupby([ocel.event_id_column, ocel.object_type_column])[ocel.object_id_column]
        .apply(set)
        .to_dict()
    )

    groups = ev.groupby([ocel.event_timestamp, ocel.event_activity])
    diagnostics = []
    for (ts, act), grp in groups:
        if len(grp) < 2:
            continue
        eids = grp[ocel.event_id_column].tolist()
        sets = [obj_sets.get(eid, set()) for eid in eids]
        shared = set.intersection(*sets) if sets else set()
        # Check whether any discriminating object type (Item, Payment) has disjoint values
        disjoint_discriminating = False
        for otype in ("Item", "Payment"):
            type_sets = [obj_by_type.get((eid, otype), set()) for eid in eids]
            non_empty = [s for s in type_sets if s]
            if len(non_empty) >= 2 and len(set.intersection(*non_empty)) == 0:
                disjoint_discriminating = True
        diagnostics.append(
            {
                "timestamp": ts,
                "activity": act,
                "eids": eids,
                "sources": grp["source"].tolist(),
                "shared_objects": sorted(shared),
                "identical_objects": all(s == sets[0] for s in sets),
                "disjoint_item_or_payment": disjoint_discriminating,
            }
        )
    return pd.DataFrame(diagnostics)


def merge_verified_pairs(ocel, merge_specs, audit_log):
    """
    Merge verified duplicate pairs while preserving attributes, relations, and audit trail.
    merge_specs: list of dicts with keys:
      'canonical_eid', 'drop_eids', 'rule', 'reason', 'confidence', 'extra_attrs'
    """
    ev = ocel.events.copy()
    rel = ocel.relations.copy()
    eid_col = ocel.event_id_column
    act_col = ocel.event_activity
    ts_col = ocel.event_timestamp

    for spec in merge_specs:
        c_eid = spec["canonical_eid"]
        d_eids = spec["drop_eids"]
        all_eids = [c_eid] + d_eids
        subset = ev[ev[eid_col].isin(all_eids)]
        if len(subset) < 2:
            continue

        c_idx = ev.index[ev[eid_col] == c_eid][0]
        # Combine provenance arrays
        merged_eids = []
        merged_keys = []
        retained_attrs = {}
        for _, row in subset.iterrows():
            merged_eids.extend(json.loads(row["merged_source_eids"]))
            merged_keys.extend(json.loads(row["merged_source_keys"]))
            retained_attrs[row[eid_col]] = {
                "source": row["source"],
                "source_event_key": row["source_event_key"],
                "payload_hash": row["payload_hash"],
            }

        ev.at[c_idx, "merged_source_eids"] = json.dumps(merged_eids)
        ev.at[c_idx, "merged_source_keys"] = json.dumps(merged_keys)
        ev.at[c_idx, "merge_rule"] = spec["rule"]
        for k, v in spec.get("extra_attrs", {}).items():
            ev.at[c_idx, k] = v

        # Verified relation union: repoint dropped eids to canonical eid, keeping canonical act/ts
        c_act = ev.at[c_idx, act_col]
        c_ts = ev.at[c_idx, ts_col]
        rel.loc[rel[eid_col].isin(d_eids), eid_col] = c_eid
        rel.loc[rel[eid_col] == c_eid, act_col] = c_act
        rel.loc[rel[eid_col] == c_eid, ts_col] = c_ts

        # Drop redundant event rows and duplicate E2O links
        ev = ev[~ev[eid_col].isin(d_eids)].copy()
        dedup_cols = [eid_col, ocel.object_id_column]
        if hasattr(ocel, "qualifier") and ocel.qualifier in rel.columns:
            dedup_cols.append(ocel.qualifier)
        rel = rel.drop_duplicates(subset=dedup_cols, keep="first").copy()

        audit_log.append(
            {
                "canonical_eid": c_eid,
                "source_eids": merged_eids,
                "merge_rule": spec["rule"],
                "rule_version": "v1.0",
                "original_activities": subset["original_activity"].tolist(),
                "refined_activity": c_act,
                "original_timestamps": subset["original_timestamp"].astype(str).tolist(),
                "attributes_retained": retained_attrs,
                "discarded_conflicts": spec.get("discarded_conflicts", {}),
                "confidence": spec["confidence"],
                "reason": spec["reason"],
            }
        )

    ocel.events = ev.reset_index(drop=True)
    ocel.relations = rel.reset_index(drop=True)
    return ocel


def apply_semantic_relabeling(ocel, relabel_map):
    """Update activity labels and abstraction levels in both events and relations."""
    ev = ocel.events.copy()
    rel = ocel.relations.copy()
    for eid, (new_act, abs_level) in relabel_map.items():
        mask_ev = ev[ocel.event_id_column] == eid
        if mask_ev.any():
            ev.loc[mask_ev, ocel.event_activity] = new_act
            ev.loc[mask_ev, "abstraction_level"] = abs_level
            rel.loc[rel[ocel.event_id_column] == eid, ocel.event_activity] = new_act
    ocel.events = ev
    ocel.relations = rel
    return ocel


def assign_partial_order_rank(ocel):
    """
    Encode semantic Tiers 1-4 and deterministic Tier 6 fallback into sort_rank.
    Do NOT use ingested_at as primary order.
    """
    ev = ocel.events.copy()
    # Explicit semantic partial-order rank per canonical eid within tied timestamps
    semantic_tier_rank = {
        "e03": 10, "e05": 11, "e06": 20, "e07": 30,  # 10:00 ties (e03 || e05)
        "e08": 10, "e09": 20, "e10": 30,             # 10:15 ties (strict semantic order)
        "e11": 10, "e12": 20, "e13": 30, "e14": 31, "e15": 40,  # 12:00 ties
    }
    concurrent_ties = {"e03", "e05", "e13", "e14"}
    ev["sort_rank"] = ev[ocel.event_id_column].map(semantic_tier_rank).fillna(0).astype(int)
    ev["is_concurrent_tie"] = ev[ocel.event_id_column].isin(concurrent_ties)
    ocel.events = ev
    return ocel


def validate_ocel_integrity(ocel, name):
    """Check referential integrity between events, relations, and objects."""
    ev_ids = set(ocel.events[ocel.event_id_column])
    obj_ids = set(ocel.objects[ocel.object_id_column])
    rel_eids = set(ocel.relations[ocel.event_id_column])
    rel_oids = set(ocel.relations[ocel.object_id_column])

    assert ocel.events[ocel.event_id_column].is_unique, f"{name}: duplicate eids!"
    assert rel_eids.issubset(ev_ids), f"{name}: orphan eids in relations!"
    assert rel_oids.issubset(obj_ids), f"{name}: orphan oids in relations!"
    assert ocel.events["original_timestamp"].notna().all(), f"{name}: missing original_timestamp!"

    # Ensure events and relations agree on activity and timestamp
    merged = ocel.relations.merge(
        ocel.events[[ocel.event_id_column, ocel.event_activity, ocel.event_timestamp]],
        on=ocel.event_id_column,
        suffixes=("_rel", "_ev"),
    )
    assert (merged[f"{ocel.event_activity}_rel"] == merged[f"{ocel.event_activity}_ev"]).all(), (
        f"{name}: activity mismatch between events and relations!"
    )
    assert (merged[f"{ocel.event_timestamp}_rel"] == merged[f"{ocel.event_timestamp}_ev"]).all(), (
        f"{name}: timestamp mismatch between events and relations!"
    )
    print(f"[{name}] OK -> events: {len(ocel.events)}, relations: {len(ocel.relations)}")

### Concrete edges, weights, and patterns whose interpretation changes

1. **`Pick Item -> Pick Item` on `I1` (`e03 -> e04`):** Raw exhibits a false item-level rework loop; Conservative, Evidence-merge, and Aggressive remove it, though Aggressive also swallows `e05` (`I2`).
2. **`Pack Package -> Pack Package` on `O1`/`P1` (`e06 -> e07`):** Raw interprets this as packing rework; Conservative reinterprets it as `Pack Package -> Pack Package (ERP Summary)` (cross-system synchronization); Evidence-merge collapses it into one transition.
3. **`Dispatch Package -> Dispatch Package` (`e08 -> e09`):** Raw interprets this as double dispatch; Conservative and Evidence-merge split it into `Release Package from Warehouse -> Accept Package at Carrier`; Aggressive erases the carrier acceptance step completely.
4. **`Issue Invoice -> Issue Invoice` (`e11 -> e16`):** Raw shows duplicate invoicing on `V1`; all three cleaned variants resolve it to a single `Issue Invoice` event.
5. **`Capture Payment -> Capture Payment` (`e13 -> e14 -> e15`):** Raw shows three captures on `O1`/`V1`; Conservative and Evidence-merge distinguish two partial captures (`M1`, `M2`) followed by `Reconcile Invoice Payment (ERP Summary)`; Aggressive merges all three into one event.
6. **`Authorize Payment -> Capture Payment` (`e12 -> e13` vs. `M2`):** In Raw, Conservative, and Evidence-merge, `M1` has `Authorize -> Capture` while `M2` has standalone `Capture` (`e14`); in Aggressive, `M2` is falsely attached to `e13`'s merged node, creating an apparent multi-payment batch capture.
7. **OTG (Object Type Graph) relation `Order`–`Payment` & `Item`–`Package`:** OTG edges remain structurally present across all datasets, **but** in Aggressive merging, `(Capture Payment, Payment)` co-occurs with both `M1` and `M2` on a single event (making `M1` and `M2` appear co-captured in one transaction rather than independent partial payments), and `(Pick Item, Item)` co-occurs with `I1` and `I2` simultaneously.
8. **ET–OT weight `(Dispatch Package, Delivery)`:** Drops from 2 in Raw to 0 (split into 1+1 across `Release` and `Accept`) in Conservative/Evidence-merge, and 1 in Aggressive.

## 8. Audit trail and reversibility

Every merge, relabel, drop, or timestamp adjustment must write to an immutable **Event Provenance & Reversibility Log** (`ocel_audit_log`) paired with an **E2O Relation Delta Log**:

| Field | Type | Description / Example |
|---|---|---|
| `canonical_eid` | string | Surviving event ID (`e03`, `e11`, `e08`) |
| `source_eids` | array[string] | All contributing raw IDs (`["e03", "e04"]`) |
| `merge_rule` | string | Rule identifier (`verified_cross_system_scan`, `harmonization_relabel`) |
| `rule_version` | string | Semantic version & steward (`v1.0 / data-steward-ops`) |
| `original_activities` | array[string] | Raw harmonized labels before refinement (`["Dispatch Package"]`) |
| `refined_activity` | string | Cleaned label (`Release Package from Warehouse`) |
| `original_timestamps` | array[datetime] | Exact UTC timestamps prior to timedelta tie-breaking |
| `adjusted_timestamp` | datetime | Microsecond-shifted timestamp in cleaned OCEL |
| `attributes_retained` | json | Per-source attribute snapshot (`e11` ERP fields, `e16` BILLING fields, `payload_hash`es) |
| `discarded_conflicts` | json | Non-selected values when sources disagreed (e.g., redundant `payload_hash`) |
| `confidence` | enum | `High`, `Medium`, `Low` |
| `reason` | string | Human-readable justification referencing reconciliation evidence |
| `e2o_delta` | json | Original `(eid, oid, qualifier)` tuples prior to union/repointing |

### Reconstructing the raw view

An analyst reconstructs `ocel_raw` deterministically without retaining two full OCEL copies by:
1. Reading every event row in the cleaned OCEL and expanding `source_eids` from `ocel_audit_log` back into one row per original `eid`.
2. Restoring `original_timestamp` and `original_activity` for each expanded `eid`, and rehydrating source-specific columns (`source`, `source_event_key`, `source_seq`, `ingested_at`, `payload_hash`) from `attributes_retained` and `discarded_conflicts`.
3. Replacing repointed E2O rows in `ocel.relations` using the `e2o_delta` snapshot (restoring original `eid -> oid` mappings, e.g., separating `e06`'s `{O1,I1,I2,P1}` from `e07`'s `{O1,P1}` in Evidence-merge, or restoring `e04` and `e16` rows).

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments (`e13`/`e14`):** Using `(timestamp, activity)` plus `have_common_object=True` merges `e13` and `e14` via shared `O1` and `V1`. *Safeguard:* Enforce object-type disjointness checks—never merge events holding distinct non-empty sets of discriminating entities (`Payment`, `Item`).
2. **Converting abstraction-level updates into false rework (`e06`/`e07`, `e13`/`e15`):** Leaving ERP summaries with the same activity label as operational events creates spurious self-loops in flattened DFGs. *Safeguard:* Tag `abstraction_level="summary"` and qualify labels (`(ERP Summary)`) or collapse only verified 1:1 summaries.
3. **Ordering by ingestion time (`ingested_at`):** Sorting ties by `ingested_at` lets network/batch latency dictate process flow (e.g., ordering `e07` or `e15` ahead of late-arriving operational events if queues skew). *Safeguard:* Explicitly exclude `ingested_at` from Tiers 1–4; use domain, lifecycle, and within-source `source_seq` first.
4. **Treating shared objects as proof of duplication (`e03`/`e05`, `e08`/`e09`):** Assuming shared `{O1, P1}` or `{O1, P1, D1}` implies one event conflates concurrent picks and cross-system custody transitions. *Safeguard:* Require positive cross-system reconciliation proof or identical payload semantics before merging.
5. **Unioning incompatible E2O relations (`e15` with `e13` or `e14`):** Repointing `e15` onto `e13` falsely binds an invoice-wide balance update exclusively to `M1` (or merges `M1` and `M2`). *Safeguard:* Never collapse a `1:N` aggregate summary event into a single granular child event.
6. **Changing durations through synthetic microseconds:** Applying `ocel_add_index_based_timedelta` before semantic sorting or overwriting `original_timestamp` distorts cycle-time analytics and invents precedence among concurrent picks (`e03`/`e05`). *Safeguard:* Always preserve `original_timestamp`, flag `is_concurrent_tie`, and apply timedelta shifts only as the final serialization step.
7. **Losing source-authoritative attributes (`e03`/`e04`, `e11`/`e16`):** Calling `ocel_drop_duplicates` blindly drops `e04` or `e16`, discarding scanner keys or billing-authoritative invoice attributes. *Safeguard:* Implement a field-level authority merge (`merge_verified_pairs`) before any drop pass.
8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups:** Running `ocel_merge_duplicates` globally bypasses harmonization collisions like `e08`/`e09`. *Safeguard:* Mandate `inspect_duplicate_candidates` pre-check reports and human/rule sign-off per candidate pattern.
9. **Comparing `source_seq` across heterogeneous systems:** Treating `ERP seq 30 < WMS seq 110` as business order invents impossible causality (`e07` before `e06`). *Safeguard:* Restrict `source_seq` comparisons strictly to pairs sharing the exact same `source`.
10. **Desynchronizing `ocel.events` and `ocel.relations`:** Filtering or relabeling `ocel.events` without updating `ocel.relations` leaves orphan `eid`s or stale activity names in PM4Py OC-DFGs. *Safeguard:* Run `validate_ocel_integrity` after every pipeline stage.
