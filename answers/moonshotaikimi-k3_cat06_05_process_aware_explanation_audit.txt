## 2. Process-model consistency checks

A concrete validation suite should combine temporal gates, conformance checking, and explanation-semantics tests.

**1. Prefix-time availability tests**

- Define exactly one `t0` per case as immediately after the first `Coverage Check Completed`, using both event timestamp and reliable sequence index.
- Specify the cutoff convention: the coverage event itself is included; other same-timestamp events are included only if a reliable sequence proves they occurred no later than coverage. Otherwise they are excluded or marked ambiguous.
- For every feature, record:
  - maximum source event time;
  - source sequence position;
  - feature valid-from time;
  - extraction or refresh time;
  - transformation and code version.
- Use event-time joins such as `source_time <= t0`, not `extraction_date`, `CURRENT_DATE`, or unbounded case aggregates.
- Run a future-perturbation canary: append synthetic appeals, document requests, settlement events, closure events, or future claims after `t0`. The `t0` feature vector and prediction must remain byte-for-byte unchanged.
- Separately mutate post-`t0` handler, risk score, employee experience, and document uploads. Any prediction change identifies leakage.
- Future information may be used to construct the training label, but the label pipeline must be physically separate from the feature pipeline.

**2. Activity-order feasibility and prefix conformance**

Represent the normative process with explicit branching and parallelism rather than a single total order:

- Registration precedes the first coverage check.
- After coverage, either the fast-track damage path or one or more document cycles is allowed.
- Damage assessment precedes settlement.
- Fraud investigation can follow a trigger and run concurrently with evidence collection or assessment.
- Appeal is enabled only after Partial or Deny.
- A second settlement event is allowed after appeal.
- Closure follows a final decision or withdrawal.

Use prefix replay or alignment against this model to identify deviations. Alignment is useful for locating missing, inserted, or misordered activities, but it does not itself establish feature availability and may select an arbitrary repair when timestamps tie.

Use footprints or directly-follows constraints for local ordering checks, while recognizing that pairwise footprints can mishandle concurrent fraud investigation. Declarative constraints can express rules such as “appeal requires a preceding Partial or Deny” and “closure requires a final state,” but should distinguish hard normative constraints from rare legitimate exceptions.

A mined DFG is descriptive. A frequent DFG edge is not automatically a normative rule, and a rare edge is not automatically invalid.

**3. Same-timestamp ambiguity tests**

- Never sort equal-timestamp events arbitrarily by activity name or ingestion order.
- If a sequence index is present, test that it is unique and monotonic within a case.
- If it is absent, retain the events as a tie set and evaluate all admissible topological orders.
- A sequence-pattern indicator should be:
  - `true` only if the order is reliably established;
  - `false` if a reliable order disproves it;
  - `unknown` if the result depends on an unresolved tie.
- The `Claim Closed` and `Damage Assessment Completed` tie in Case Z must be marked ambiguous and sent for data-quality investigation. It cannot support a positive `Closed -> Damage` explanation.
- Run sensitivity tests using all plausible orderings and report whether predictions or explanations change.
- Validate timestamp precision, time zones, clock synchronization, and batch ingestion ordering.

**4. Complete-trace feature detection**

- Perform static lineage checks for closure tables, full-case window functions, `last_*` fields, `total_*` fields, `anywhere` indicators, extraction-date joins, and suffix pattern extraction.
- Perform dynamic checks that record the actual rows used to calculate each feature.
- Require every sequence feature to name its prefix endpoint. A pattern absent from the prefix cannot be true merely because it occurs later in the completed trace.
- Maintain separate prefix-pattern and completed-trace-pattern namespaces so they cannot be accidentally joined.

**5. Enabled, future-possible, and impossible explanation checks**

Replay the observed prefix to a process state and classify every activity mentioned by an explanation:

- **Observed/current:** Claim Registered and the first Coverage Check Completed.
- **Enabled at `t0`:** Damage Assessment for the fast track or Documents Requested for the evidence path; fraud opening may also be enabled if its trigger condition is satisfied.
- **Future-possible but not currently enabled:** Appeal, a later settlement decision, and closure. They may become reachable but have not occurred.
- **Impossible as an observed relation:** Closure before the required assessment and final decision, including the asserted `Claim Closed -> Damage Assessment Completed` ordering.

An explanation may say that current complexity is statistically associated with later evidence cycles. It may not say that document rework, appeal, settlement, or closure has occurred when those events are absent from the prefix.

Temporal and process validity are independent: an appeal timestamped before its required decision might pass a cutoff but fail process conformance, while `Appeal -> Settlement Decision Recorded` is process-valid but fails the current cutoff.

**6. Repeated settlement-decision semantics**

The conformance model should retain decision instance IDs, outcomes, and appeal links:

- `Partial -> Appeal -> Settlement Decision Recorded` is legitimate.
- `Deny -> Appeal -> Settlement Decision Recorded` is legitimate.
- A second `Settlement Decision Recorded` should not be rejected merely because the activity label repeats.
- A repeated settlement without an intervening qualifying appeal should be treated as a duplicate, retry, or semantic exception until explained.
- Appeal after Approve, appeal before any decision, or closure before a final state should trigger a conformance incident.
- Closure should follow a final decision or withdrawal, not merely any settlement event.

## 3. Alternative feature interpretations

Predictive validity, causality, actionability, and fairness are different standards:

- **Predictive validity:** the feature was available at `t0` and provides stable, calibrated out-of-time information.
- **Causal interpretation:** requires evidence about an intervention, such as a suitable natural experiment or controlled change. Temporal ordering and SHAP importance alone are insufficient.
- **Operational actionability:** requires a controllable pre-decision lever, evidence that changing it improves outcomes, and consideration of cost and side effects.
- **Fairness:** a feature can be predictive but still create unlawful or unacceptable disparate treatment or impact. Removing every proxy is not automatically necessary, but retention requires review and monitoring.

| Class | Surviving or repairable signals | What may be claimed | What may not be claimed |
|---|---|---|---|
| Defensible predictive signal | `initial_damage_complexity`; `elapsed_since_registration_at_t0`; timestamp-validated `initial_reserve_at_t0`; legitimately observed prefix patterns | “This registration-time or prefix-time attribute was associated with breach risk in out-of-time data.” | Do not claim causation or carry over SHAP values from the contaminated model. Subjective fields such as complexity still need quality and bias checks. |
| Process-state or congestion signal | `queue_length_at_t0`; prefix age; observed prefix state; point-in-time document count; current team or resource role; investigation already active at `t0` | “This describes congestion or process state at prediction time and is associated with risk.” Queue length may be a candidate for operational triage. | Do not claim that adding staff, changing queue length, or assigning a team will reduce breaches without intervention evidence. Current state is not necessarily controllable for an individual claim. |
| Proxy requiring fairness/robustness review | `claimant_region`; `claimant_channel`; repaired prior-claim history; initial reserve; potentially subjective complexity scores | “The model uses a statistical association. We monitor calibration, errors, stability, and subgroup impact.” Region may partly represent legitimate repair-network capacity and partly sensitive socioeconomic context. | Do not say a region, channel, or claimant history inherently causes delay. Do not use the explanation to penalize claimants without legal and fairness review. Decompose into explicit operational factors where possible. |
| Drift/calendar proxy | `calendar_week`; explicit holiday period; known policy regime; scheduled capacity calendar | “This is temporal context associated with historical outcomes, conditional on the period in which the model was trained.” Scheduled future holidays known at `t0` can be legitimate exogenous information. | Do not claim an intrinsic causal effect of week 52 or assume the relationship survives policy changes. Require out-of-time validation and drift monitoring. |
| Unusable until lineage is repaired | Current implementations of total duration, appeal-anywhere, final team, total document requests, full variant, prior-count SQL, same-day snapshot, mutable risk score, last resource role, final decision, employee experience, and suffix sequence patterns | No `t0` predictive or causal claim is defensible from the current implementation. Some have valid replacements, such as prefix document count, team at `t0`, strict prior count, historical risk score, and current role. | Do not “SHAP away” the leakage, average it with valid features, or rely on a 65% coincidental match. Full-trace appeal, closure, final decision, and total duration have no meaningful current-case analogue at this `t0`. |

The legitimate explanation strategy is therefore not to delete every correlated variable. It is to retain temporally valid signals under appropriate governance, repair mutable aggregates with historical timestamps, and prohibit causal or claimant-blaming language.

## 5. Recommendations for explanation validation

1. **Immediately contain leaked explanations.** Quarantine closure-derived, complete-trace, and extraction-date features from serving and reason-code generation. Mark existing scores as unaudited or fall back to a model using only validated prefix features. Audit all features, not only the top 12.

2. **Redesign the feature store around prediction time.** Use immutable, versioned, preferably bitemporal records containing event time, ingestion time, valid-from/valid-to time, sequence index, feature timestamp, entity ID, source, and transformation version. Online and offline features must share the same point-in-time implementation.

3. **Materialize prefix-only training data.** Reconstruct every historical case as of the first coverage check. Replace full-trace aggregates with prefix aggregates and rebuild handler team, risk score, reserve, employee experience, resource role, and document counts as of `t0`. Store the exact `t0` feature vector for reproducibility.

4. **Add temporal tripwires.** Statically reject feature SQL containing extraction-date joins, unbounded windows, closure tables, `last_*` fields, or full-trace pattern sources unless explicitly approved. Dynamically test suffix invariance by adding or modifying post-`t0` events and requiring no change to the `t0` vector.

5. **Put process-conformance tests in CI.** Replay prefixes against the normative model, test branching and fraud concurrency, preserve same-timestamp ambiguity, and validate appeal and repeated-decision semantics. Classify findings as conformant, ambiguous, repairable exception, or hard violation. Use mined DFGs for drift discovery, not as proof of normative rules.

6. **Retrain and recalibrate after feature removal.** Use out-of-time validation and, where appropriate, claimant-group separation. Expect apparent performance to fall when leakage is removed; report the honest performance. Recalibrate probabilities after retraining and assess calibration over time and relevant subgroups.

7. **Regenerate explanations on the repaired model.** Recompute global and local importance rather than reusing old SHAP values. Test explanation stability under bootstrap resampling, model seeds, correlated-feature grouping, and plausible same-timestamp orderings. Explanation templates should say “associated with” unless causal evidence exists.

8. **Perform proxy and fairness analysis.** Review region, channel, prior-claim history, reserve, and subjective complexity measures. Measure approval-time errors, calibration, and explanation disparity across protected and intersectional groups. Consider replacing proxies with explicit operational variables, but do not assume automatic deletion is the only valid mitigation.

9. **Monitor schema and process drift.** Alert on new or renamed activities, missing sequence indexes, increased same-timestamp rates, changing settlement-event semantics, feature freshness, future-data joins, DFG or conformance changes, holiday and policy shifts, population changes, and calibration deterioration.

10. **Govern explanation release.** Require a model card listing the prediction-time contract, allowed feature classes, known proxies, process assumptions, calibration results, fairness review, and prohibited causal wording. Periodically replay historical cases to verify that stored explanations remain reproducible.
