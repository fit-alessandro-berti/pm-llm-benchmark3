**Why bidirectional DFG edges do not prove concurrency:** observing both `("Credit Check","Engineering Review")` and `("Engineering Review","Credit Check")` in a DFG only shows that both orderings appear in the *recorded* total order. With completion-only timestamps (S7) and potential overlap (D7/S2), the earlier completion can appear first even if the other started earlier; with ties, ingestion index can arbitrarily order simultaneous completions; and with population heterogeneity, different cases can legitimately follow different sequences. Therefore, “both directions” supports **uncertainty/variability**, not a definitive AND-parallelism claim.

# 2. Shared Assumptions

- **Lifecycle semantics**: each recorded activity is a *completion* event; the log’s total order is by completion timestamp, with tie-breaking by ingestion index (S7). None of the models treats the observed order as start-order or as proof of non-overlap (D7).
- **Single-occurrence assumption (within one case)**: each labeled activity occurs at most once per case (supported by all 30 traces). None of the candidates includes explicit rework loops because none were observed.
- **`Supplier Confirmation` absence is ambiguous**: missing `SC` in a trace can mean (i) stocked components legitimately skipping `SC` (S4), and/or (ii) an integration miss (S5). In control-flow, all candidates represent this as a **single optionality abstraction** `SC?` (implemented as an XOR between `SC` and a silent transition), and explicitly acknowledge that this conflates “true skip” and “missing data.”
- **Conditional requirement cannot be encoded without the missing attribute**: because external/stocked is absent (S5), none of the candidates can condition `SC` on that attribute directly; the optional `SC?` stands in for this unknown guard.
- **Expedite semantics**: `EX` is optional, occurs at most once, must be after both checks and before approval (D6/S6). Relative order with `SC` is left flexible whenever possible (S6; V6/V7).
- **Backbone**: all candidates enforce `Register Order` as start and `Archive Case` as end (D1), and `Approve Configuration → Release Production → Archive Case` (D2 + full support in variants).

# 3. Conservative Candidate

**Inductive bias (one paragraph):** This candidate intentionally **overfits** the 30 observed cases by admitting only the seven observed control-flow variants (factored by a shared prefix/suffix). It prioritizes **precision** and “no hallucinated behavior” over generalization, treating absence of evidence as evidence of absence. It is robust to stakeholder conflict (S1 vs S2) by refusing to generalize beyond what was logged, but it is fragile to missing-data and future drift (S5) because any new interleaving is rejected.

**Compact formal expression:**  
Let \(\sigma_1,\dots,\sigma_7\) be the seven observed middle fragments:
- \(\sigma_1 = \langle CC, ER, SC\rangle\)
- \(\sigma_2 = \langle ER, CC, SC\rangle\)
- \(\sigma_3 = \langle CC, ER\rangle\)
- \(\sigma_4 = \langle ER, CC\rangle\)
- \(\sigma_5 = \langle CC, SC, ER\rangle\)
- \(\sigma_6 = \langle CC, ER, SC, EX\rangle\)
- \(\sigma_7 = \langle ER, CC, EX, SC\rangle\)

Then:
\[
\text{model\_conservative} \;=\; \rightarrow(RO,\; X(\sigma_1,\dots,\sigma_7),\; AC,\; RP,\; AR)
\]

**PM4Py code (`ProcessTree`)**:

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(lbl: str) -> ProcessTree:
    return ProcessTree(label=lbl)

def seq(*lbls: str) -> ProcessTree:
    return ProcessTree(operator=Operator.SEQUENCE, children=[leaf(l) for l in lbls])

def xor(*children: ProcessTree) -> ProcessTree:
    return ProcessTree(operator=Operator.XOR, children=list(children))

middle = xor(
    seq("Credit Check", "Engineering Review", "Supplier Confirmation"),
    seq("Engineering Review", "Credit Check", "Supplier Confirmation"),
    seq("Credit Check", "Engineering Review"),
    seq("Engineering Review", "Credit Check"),
    seq("Credit Check", "Supplier Confirmation", "Engineering Review"),
    seq("Credit Check", "Engineering Review", "Supplier Confirmation", "Expedite Review"),
    seq("Engineering Review", "Credit Check", "Expedite Review", "Supplier Confirmation"),
)

model_conservative = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[
        leaf("Register Order"),
        middle,
        leaf("Approve Configuration"),
        leaf("Release Production"),
        leaf("Archive Case"),
    ],
)
```

**Behavior deliberately excluded (examples):**

- Any trace not exactly equal to one of the seven observed variants (e.g., `RO, CC, ER, EX, AC, RP, AR`).
- Any alternative interleaving of `SC` (e.g., `RO, ER, SC, CC, AC, RP, AR`) even if arguably consistent with D5.
- Any placement of `EX` other than the two observed placements (e.g., `... SC, EX ...` is allowed only as in V6; `... EX ...` only as in V7).
- Any rework (repeating `CC`, `ER`, `SC`, or `EX`) and any omission of `AC`, `RP`, or `AR`.

**Known underfitting risks:**

- **Missing-data sensitivity**: if an `SC` event is missing (S5) in a case that otherwise follows V1/V2/V6/V7, the trace may map to a pattern not enumerated and will be rejected.
- **Interleaving drift**: a new but reasonable order (e.g., `RO, ER, CC, SC, EX, AC, RP, AR`) is rejected despite being consistent with D6/S6.
- **Scalability/duplicate-label issue**: XOR-enumeration grows linearly with the number of variants; repeated activity labels appear in many branches, making the tree large and reducing explainability as the log grows (even though it is “precise” on the observed sample).

# 4. Balanced Candidate

**Inductive bias (one paragraph):** This candidate aims for a **plausible, evidence-aligned generalization** that remains explicit about uncertainty. It enforces the high-confidence backbone (D1–D2) and the medium-to-high precedence constraints (`CC` and `ER` before approval, D3) while avoiding a hard commitment between S1 and S2 by modeling the two checks in an **unordered partial order** (admitting both observed orders without claiming true concurrency). It represents `SC` as optional to handle both stocked cases (S4) and missing `SC` events (S5), but restricts early `SC` to occur only after `CC` because that is the only “early SC” pattern actually observed (V5) and keeps precision reasonable.

**Compact formal expression (partial order with optional nodes):**

Let \(SC? = X(\tau, SC)\) and \(EX? = X(\tau, EX)\). Define a strict partial order over nodes
\(\{RO, CC, ER, SC?, EX?, AC, RP, AR\}\) with precedence constraints:

- \(RO \prec CC,\; RO \prec ER\)
- \(CC \prec SC?\)  (balanced commitment guided by V5 and absence of `SC→CC` evidence)
- \(CC \prec EX?,\; ER \prec EX?\)
- \(CC \prec AC,\; ER \prec AC,\; SC? \prec AC,\; EX? \prec AC\)
- \(AC \prec RP \prec AR\)
- No constraint between \(CC\) and \(ER\); no constraint between \(SC?\) and \(EX?\)

**Exactly how sequence vs concurrency vs partial order is chosen (CC/ER/SC/EX):**

- **`Credit Check` vs `Engineering Review`**: bidirectional adjacency (E-DFG) + conflicting stakeholders (S1 vs S2) + completion-only ordering (S7) ⇒ choose **partial order** (no edge), which admits `CC→ER` and `ER→CC` without asserting either strict sequence or true parallelism.
- **`Supplier Confirmation`**: V5 shows `SC` can complete between the checks, but only in the pattern `CC→SC→ER` (never `ER→SC→CC`, and never `SC` before `CC`). Combined with D5 (low-to-medium) and S5 (missing `SC`) ⇒ model `SC` as **optional**, and (in the balanced bias) require it to be **enabled after `CC`** while still allowing it to occur before `ER`.
- **`Expedite Review`**: D6/S6 (medium to high) and both observed expedite traces show `EX` after both checks and before approval ⇒ encode `EX` as **optional but requiring both checks**, and leave `EX` unordered with `SC` (supported by V6 vs V7 and S6).

**PM4Py code (`POWL` with `StrictPartialOrder`)**:

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

ro = Transition("Register Order")
cc = Transition("Credit Check")
er = Transition("Engineering Review")
sc = Transition("Supplier Confirmation")
ex = Transition("Expedite Review")
ac = Transition("Approve Configuration")
rp = Transition("Release Production")
ar = Transition("Archive Case")

sc_opt = OperatorPOWL(Operator.XOR, [SilentTransition(), sc])   # SC? (stocked or missing)
ex_opt = OperatorPOWL(Operator.XOR, [SilentTransition(), ex])   # EX?

po = StrictPartialOrder([ro, cc, er, sc_opt, ex_opt, ac, rp, ar])

po.order.add_edge(ro, cc)
po.order.add_edge(ro, er)

po.order.add_edge(cc, sc_opt)   # balanced commitment: SC enabled after CC

po.order.add_edge(cc, ex_opt)
po.order.add_edge(er, ex_opt)   # EX requires both checks

po.order.add_edge(cc, ac)
po.order.add_edge(er, ac)       # both checks before approval
po.order.add_edge(sc_opt, ac)   # if SC happens, it is before approval
po.order.add_edge(ex_opt, ac)   # if EX happens, it is before approval

po.order.add_edge(ac, rp)
po.order.add_edge(rp, ar)

model_balanced = po
```

**Behavior deliberately excluded (examples):**

- `SC` completing before `CC` (e.g., `RO, ER, SC, CC, AC, RP, AR`) even though D5 says “after either” (this is excluded to keep precision aligned with observed V5).
- `EX` occurring before completion of both checks (e.g., `RO, CC, EX, ER, ...`), per D6/S6.
- `SC` or `EX` after `AC`, and any `RP` without prior `AC` (D2).

**Known underfitting risks:**

- If reality allows `ER→SC→CC` (supplier work triggered by engineering output before credit completion), this model will reject those traces.
- If `SC` can legitimately complete immediately after `RO` (procurement starts from order registration), this model underfits by forcing `CC` first.
- If there is unobserved rework (repeat checks, repeat supplier confirmation), the model underfits by having no loops.

# 5. Permissive Candidate

**Inductive bias (one paragraph):** This candidate maximizes **reasonable generalization** under sparse evidence, aiming to support exploration and “what-if” analysis. It keeps only the most defensible hard constraints (D1–D3 and D6, plus the observed backbone) and relaxes uncertain enablement assumptions: `SC` may complete at any time after registration and before approval (capturing both “started early” and “logged late but still pre-approval”), and it may interleave arbitrarily with the two checks. This greatly increases language coverage but increases precision risk by admitting plausible-yet-unobserved interleavings.

**Boundary: what remains forbidden vs what becomes allowed**

- **Still forbidden (hard constraints kept)**:
  - Any trace not starting with `RO` or not ending with `AR` (D1).
  - `RP` without `AC` and any `AC` after `RP` (D2).
  - `AC` before either `CC` or `ER` (D3).
  - `EX` before completion of both `CC` and `ER`, or `EX` after `AC` (D6/S6).
  - `SC` after `AC` when it appears (D4, applied as “if present, it must be pre-approval”).
- **Allowed generalization**:
  - Any ordering/overlap between `CC` and `ER` (S1 vs S2 uncertainty).
  - Any ordering between `SC` and the checks, as long as `SC` (if present) is after `RO` and before `AC`.
  - `EX` may occur before or after `SC` (S6; V6/V7).

**Compact formal expression (more permissive partial order):**

Let \(SC? = X(\tau, SC)\) and \(EX? = X(\tau, EX)\). Strict partial order over
\(\{RO, CC, ER, SC?, EX?, AC, RP, AR\}\) with constraints:

- \(RO \prec CC,\; RO \prec ER,\; RO \prec SC?\)
- \(CC \prec EX?,\; ER \prec EX?\)
- \(CC \prec AC,\; ER \prec AC,\; SC? \prec AC,\; EX? \prec AC\)
- \(AC \prec RP \prec AR\)
- No other ordering constraints (so `SC?` can occur before/between/after the checks; `SC?` and `EX?` remain unordered)

**PM4Py code (`POWL` with `StrictPartialOrder`)**:

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

ro = Transition("Register Order")
cc = Transition("Credit Check")
er = Transition("Engineering Review")
ac = Transition("Approve Configuration")
rp = Transition("Release Production")
ar = Transition("Archive Case")

sc_opt = OperatorPOWL(Operator.XOR, [SilentTransition(), Transition("Supplier Confirmation")])  # SC?
ex_opt = OperatorPOWL(Operator.XOR, [SilentTransition(), Transition("Expedite Review")])       # EX?

po = StrictPartialOrder([ro, cc, er, sc_opt, ex_opt, ac, rp, ar])

# after registration, the checks and (optional) supplier work may start in any order
po.order.add_edge(ro, cc)
po.order.add_edge(ro, er)
po.order.add_edge(ro, sc_opt)

# expedite requires both checks
po.order.add_edge(cc, ex_opt)
po.order.add_edge(er, ex_opt)

# approval waits for the checks and any chosen optional steps
po.order.add_edge(cc, ac)
po.order.add_edge(er, ac)
po.order.add_edge(sc_opt, ac)
po.order.add_edge(ex_opt, ac)

po.order.add_edge(ac, rp)
po.order.add_edge(rp, ar)

model_permissive = po
```

**Behavior deliberately excluded (examples):**

- `RO, CC, ER, AC, EX, RP, AR` (expedite after approval) — violates D6/S6.
- `RO, SC, AC, CC, ER, RP, AR` (approval before checks) — violates D3.
- Any trace that releases without approval — violates D2.

**Known underfitting risks:**

- If the real process enforces strict `CC→ER` (S1) or strict `ER→CC`, this model underfits compliance intent by being too permissive (i.e., it cannot “explain” violations as violations).
- If `SC` is actually mandatory for almost all cases and missingness is rare, the model underfits by treating `SC` as optional rather than “mandatory but sometimes missing.”
- If rework/loops exist in reality (repeat `SC`, repeat reviews), the model underfits by not modeling those cycles.

# 8. Validation Code

The code below evaluates soundness and standard conformance metrics on the finite observed log. **Limitation:** none of the available APIs can exhaustively compare infinite languages (especially for permissive partial orders). Sampled/bounded playout can *suggest* plausible admitted behavior, but it does **not** prove language inclusion or exclusion.

```python
import pm4py

from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition


# --- 1) Reconstruct the 30-case log ---
trace_strs = []
trace_strs += [
    "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"
] * 12
trace_strs += [
    "Register Order, Engineering Review, Credit Check, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"
] * 7
trace_strs += [
    "Register Order, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case"
] * 4
trace_strs += [
    "Register Order, Engineering Review, Credit Check, Approve Configuration, Release Production, Archive Case"
] * 3
trace_strs += [
    "Register Order, Credit Check, Supplier Confirmation, Engineering Review, Approve Configuration, Release Production, Archive Case"
] * 2
trace_strs += [
    "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Expedite Review, Approve Configuration, Release Production, Archive Case"
] * 1
trace_strs += [
    "Register Order, Engineering Review, Credit Check, Expedite Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"
] * 1

log = pm4py.parse_event_log_string(trace_strs, sep=", ", return_legacy_log_object=True)


# --- Helpers for ProcessTree construction ---
def leaf(lbl: str) -> ProcessTree:
    return ProcessTree(label=lbl)


def seq(*lbls: str) -> ProcessTree:
    return ProcessTree(operator=Operator.SEQUENCE, children=[leaf(l) for l in lbls])


def xor(*children: ProcessTree) -> ProcessTree:
    return ProcessTree(operator=Operator.XOR, children=list(children))


# --- 2) Define the three candidates ---
# Conservative (ProcessTree enumeration)
middle = xor(
    seq("Credit Check", "Engineering Review", "Supplier Confirmation"),
    seq("Engineering Review", "Credit Check", "Supplier Confirmation"),

# 9. Recommendation and Data-Collection Plan

**Recommendation (immediate use):** use **`model_balanced`** for day-to-day analysis (conformance checks, operational reporting, and risk discussions). It is the best compromise under S1/S2 conflict and S5 missingness: it enforces the backbone constraints, admits all observed variants, handles absent `SC` explicitly, and avoids claiming concurrency from completion-order artifacts.

**Recommendation (sensitivity analysis):** use **`model_permissive`** as a deliberately broader hypothesis space for exploration (simulation, scenario testing, and to bound precision risk). Compare conformance/precision deltas between balanced vs permissive to quantify how much your conclusions depend on uncertain ordering assumptions.

**Concrete data-collection plan to resolve ambiguities (what to collect, and why):**

- **Add lifecycle timestamps (`start` + `complete`) for `Credit Check` and `Engineering Review`**:
  - Purpose: distinguish strict precedence (S1) from overlap/parallelism (S2), and avoid inferring concurrency from completion order (D7/S7).
  - Minimal: capture `time:start` and `time:complete` (or duration) per activity.
- **Export the missing case attribute(s)**:
  - `component_sourcing = {stocked, external}` or equivalent; ideally at component level and aggregated to “SC required?”
  - Purpose: separate true optionality (S4) from missing events (S5) and decide whether `SC` should be mandatory under certain conditions (S3).
- **Instrument `Supplier Confirmation` integration health**:
  - Add correlation IDs between procurement system and event log; capture delivery acknowledgements; compute missingness rates by supplier/component.
  - Purpose: validate S5 and assess whether missing `SC` is random or systematic (which impacts model choice and compliance conclusions).
- **Add an explicit `expedite_flag` / `expedite_reason` and enforce it in logging**:
  - Purpose: confirm D6/S6 and identify whether `EX` is tied to `SC` in practice (not stated but operationally possible).
- **Collect “decision-ready” attributes at approval**:
  - e.g., `credit_score_band`, `engineering_complexity`, `external_component_count`, `supplier_risk`, `config_version`.
  - Purpose: support data-aware constraints (e.g., when `SC` is required) and reduce spurious optionality.
- **Maximally informative future traces (what to look for / sample intentionally)**:
  - Cases where `SC` completes before `CC` (tests permissive vs balanced).
  - Cases where `EX` happens with no `SC` but external components present (tests whether `EX` depends on `SC` in reality).
  - Cases with overlapping `CC` and `ER` intervals (tests S1 vs S2 directly).
  - Cases with `SC` present but logged late (tests whether post-hoc logging affects ordering).

# 10. Uncertainty Statement

- **Backbone (`RO` start; `AC→RP→AR`; `RP` requires `AC`)**: **high confidence** (D1–D2; unanimous in all 30 traces).
- **`CC` vs `ER` ordering (strict sequence vs overlap/parallel)**: **low confidence**. Evidence is genuinely conflicting (S1 vs S2), and completion-only timestamps (S7) make the observed total order compatible with both sequential and overlapping executions (D7).
- **Is `Supplier Confirmation` truly optional vs missing?**: **medium confidence** that a *mixture* exists. V3/V4 show missing `SC` in 7/30 cases, but S5 says 5–10% may be missing and the key conditioning attribute is absent; therefore absence cannot be interpreted as pure optionality.
- **Enablement of `SC` (after `CC`, after `ER`, or after either)**: **low-to-medium confidence**. V5 supports “after one check but before the other,” but it only shows `CC→SC→ER` (not `ER→SC→CC`). Balanced’s `CC≺SC` is a precision-leaning commitment; permissive relaxes it.
- **`EX` constraints (after both checks; before approval; relative order with `SC`)**: **medium-to-high confidence** for the check-dependency and pre-approval placement (D6/S6, supported by V6/V7), **medium confidence** that `EX` can occur before or after `SC` (explicit in S6; observed both ways).

**Material alternative interpretation that would change the recommendation:** if S1 is correct as a strict control (Credit Check must finish before Engineering Review starts) and is broadly enforced, then the best operational model would replace the partial-order between `CC` and `ER` with a strict sequence `CC→ER` and treat any `ER→CC` ordering as nonconformance or logging error. Under that interpretation, `model_balanced` would be too permissive and a stricter “compliance-first” candidate (not the current permissive one) would become preferable.
