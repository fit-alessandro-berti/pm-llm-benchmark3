Now section 1: definitions and formulas.

Let c  {1..12} case, i  {A,B,C}. Let t(c, X) be timestamp of event X for case c. Define:

upstream(c) = t(c, fork_release) - t(c, arrival).

queue_i(c) = t(c, i_start) - t(c, fork_release) [0].

service_i(c) = t(c, i_end) - t(c, i_start) [0].

branch_completion_offset_i(c) = queue_i(c) + service_i(c) = t(c, i_end) - t(c, fork_release).

join_ready(c) = max_{i{A,B,C}} t(c, i_end) = t(c, fork_release) + max_i (queue_i+service_i). (This equals latest branch completion.)

sync_wait_i(c) = join_ready(c) - t(c, i_end) = max_j(queue_j+service_j) - (queue_i+service_i) 0.

fork_join_stage(c) = join_ready(c) - t(c, fork_release) = max_i(queue_i+service_i).

downstream_queue(c) = t(c, final_start) - join_ready(c) [0 if rule holds].

final_service(c) = t(c, final_end) - t(c, final_start).

total_flow(c) = t(c, final_end) - t(c, arrival) = upstream + fork_join_stage + downstream_queue + final_service. (Equation 1)

Alternative additive branch decomposition for analysis (non-additive to total): For each branch i, its wall-clock footprint = queue_i + service_i + sync_wait_i = fork_join_stage (since padded to join_ready). Thus for any branch, queue_i + service_i + sync_wait_i = fork_join_stage. Wait is that true? Let's check: queue+service = offset_i, sync_wait_i = T - offset_i, sum = T = fork_join_stage. Yes! For each branch individually, the sum of its queue, service, and sync wait equals the stage time (because from fork_release to join_ready, the branch either works (queue+service) or waits (sync) ). So branch-specific sync wait is not an extra additive component on top of queue+service+stage; it is the complement within the stage. If one tried to compute total flow as upstream + _i(queue_i+service_i+sync_wait_i) + downstream + final, they'd get upstream + 3*fork_join_stage + ... which triple counts the stage (or double counts if only summing sync separately?). More precisely, because each branch's timeline is padded to the same join_ready, adding sync_wait_i across branches counts the same calendar interval during which multiple branches are simultaneously waiting. For the overlapping period after the second-last branch finishes until join_ready, both earlier-finishing branches are waiting, so that calendar interval appears in two sync_wait terms. Thus summing all branches' sync_wait_i double counts (or overcounts) the synchronization interval relative to the single case-level gap max_i sync_wait_i = T - min_i(offset_i). To avoid double counting, total flow must use the stage time once, not the sum of branch pads. Or if one wants branch-attributable delays, use only max_i sync_wait_i (the case-level synchronization span) and note that _i sync_wait_i = fork_join_stage*3 - _i offset_i, which is larger. # 1. Delay-decomposition definitions

Let case index be \(c\in\{1,\dots,12\}\) and branch index \(i\in\{A,B,C\}\).  
Let \(t_{c,\text{arr}}\) be `arrival`, \(t_{c,\text{fork}}\) be `fork_release`, \(t_{c,i}^{\text{start}}\) and \(t_{c,i}^{\text{end}}\) the branch start/end timestamps, \(t_{c,F}^{\text{start}}\) and \(t_{c,F}^{\text{end}}\) the final activity timestamps.

**Component formulas (all durations in minutes):**

- Upstream elapsed:  
  \(U_c = t_{c,\text{fork}} - t_{c,\text{arr}}\)

- Branch queue waiting:  
  \(q_{c,i} = t_{c,i}^{\text{start}} - t_{c,\text{fork}}\)

- Branch active service:  
  \(s_{c,i} = t_{c,i}^{\text{end}} - t_{c,i}^{\text{start}}\)

- Branch completion offset from fork:  
  \(o_{c,i} = q_{c,i} + s_{c,i} = t_{c,i}^{\text{end}} - t_{c,\text{fork}}\)

- Join-ready time (latest branch completion):  
  \(J_c = \max_i t_{c,i}^{\text{end}} = t_{c,\text{fork}} + \max_i o_{c,i}\)

- Elapsed fork-join stage time (wall-clock parallel stage):  
  \(S_c = J_c - t_{c,\text{fork}} = \max_i o_{c,i}\)

- Branch-specific synchronization waiting:  
  \(w_{c,i} = J_c - t_{c,i}^{\text{end}} = \max_j o_{c,j} - o_{c,i}\)

- Downstream queueing before final:  
  \(D_c = t_{c,F}^{\text{start}} - J_c\)

- Final service:  
  \(F_c = t_{c,F}^{\text{end}} - t_{c,F}^{\text{start}}\)

- Total case flow time:  
  \(T_c = t_{c,F}^{\text{end}} - t_{c,\text{arr}} = U_c + S_c + D_c + F_c\)

**Why summing all branch synchronization waits double counts:**

For a case, suppose branch completion offsets are ordered \(o_1 \le o_2 \le o_3 = S_c\). Then:

\[
\sum_i w_{c,i} = (S_c-o_1)+(S_c-o_2)+0 = (o_2-o_1) + 2(S_c-o_2)
\]

The true case-level synchronization span (first completion to join-ready) is:

\[
S_c - o_1 = (o_2-o_1) + (S_c-o_2)
\]

The interval \((S_c-o_2)\) is the period when both the first and second finishers are waiting simultaneously. Summing \(w_{c,i}\) counts that calendar interval twice. Moreover, because \(q_{c,i}+s_{c,i}+w_{c,i}=S_c\) for every branch individually, adding all three branches’ queue, service, and sync terms would give \(3S_c\), and adding the separate stage term \(S_c\) on top would overcount the fork-join stage by a factor of four. Therefore, the additive total-flow identity uses \(S_c\) exactly once; \(q_{c,i}, s_{c,i}, w_{c,i}\) are branch-level diagnostics and must not be summed into \(T_c\).

# 5. PM4Py interval-event DataFrame (one row per branch/final activity)
rows = []
for _, r in df.iterrows():
    for act, s, e in [('A', r['A_start'], r['A_end']),

                      ('C', r['C_start'], r['C_end']),

                     'concept:name': act,
                     'start_timestamp': s,
                     'time:timestamp': e})

idf = pm4py.format_dataframe(idf, case_id='case:concept:name',
                             activity_key='concept:name',
                             timestamp_key='time:timestamp',
                             start_timestamp_key='start_timestamp')
log = pm4py.convert_to_event_log(idf)

# 6. Relevant PM4Py performance call
print("PM4Py service times (branch/final):")
for act in ['A','B','C','F']:
    print(act, pm4py.get_service_time(log, act))

# NOTE: join_ready, branch sync waits, and fork-join stage are custom pandas
# calculations using max() across branch end times. Standard directly-follows
# performance (e.g. discover_performance_dfg) recovers edges between activity
# completions/starts but does NOT itself recover synchronization waiting of
# early-finishing branches or the max-based join_ready gap.

print("\nCase-level decomposition:")
cols = ['case','upstream_elapsed','A_queue','A_service','B_queue','B_service',

        'final_service','total_flow_time']

print(df[['case','sav_cf1','sav_cf2','sav_cf3']].to_string(index=False))

# 7. Limits of inference

- **Causality:** The timestamps show *that* queues exist (e.g., positive `B_queue`, `C_queue`), but not *why*. Queue delays could reflect limited machines, analyst scheduling, batching, priority rules, or data-handoff lags. No causal claim is warranted from this data alone.
- **Branch resource capacity:** We observe one start and one end per branch per case, but not how many parallel resources serve each branch, their occupancy, or whether branches share resources. Thus utilization of A/B/C stations cannot be measured.
- **Work preemption:** Only start and complete events are given. We cannot detect whether an activity was paused, resumed, or interrupted; we assume continuous execution because no contrary evidence exists.
- **Downstream queue vs release policy:** `final_start - join_ready` is labeled downstream queueing only under the model assumption. The consistently low final-station utilization suggests the gap may instead be a fixed handoff latency, approval delay, or deliberate release policy. Treating it as pure congestion would overstate the benefit of adding final-station capacity.
- **Synchronization waiting from standard logs:** Directly-follows or DFG-based performance metrics would not by themselves expose the early-finishing branches’ wait until `join_ready`; that quantity requires the custom max-based logic above.
- **Arrival process:** Arrivals are evenly spaced every 15 minutes (except the first 10-minute gap), which may indicate scheduled release rather than organic demand; we cannot infer arrival variability or its driver.
- **Quality/rework:** No data on rejections, repeats, or post-final loops; total flow time is a single-pass observation for these 12 cases only.
