## 1. Equivalence design space

We define three distinct equivalence relations. Each relation represents a different "resolution" of process behavior, trading structural detail for pattern generalization.

### 1. Activity-Sequence Equivalence (ASE)
*   **Definition:** Two executions are equivalent if their projections onto the sequence of Activity labels are strictly identical. 
*   **Invariants Preserved:** The exact number of events, their chronological order, and activity labels.
*   **Information Discarded:** All object identifiers, object types, E2O incidence (e.g., whether an item was involved in a dispatch), O2O topology, external objects, and O2O qualifiers.
*   **Properties:** Reflexive, symmetric, and transitive. It forms a standard equivalence relation.
*   **Concurrency:** Assumes a strict total order as presented in the event logs. If concurrency existed, a stable topological sort (e.g., alphabetically breaking ties) would be required to ensure transitivity.

### 2. Typed Structural Isomorphism (TSI)
*   **Definition:** Two executions are equivalent if there exists a bijection between their local object identifiers that preserves: (1) the sequence of events, (2) the activity label of each event, (3) the object type and E2O incidence of every object, (4) O2O links including their specific qualifiers, and (5) external object identifiers (`EXT-`).
*   **Invariants Preserved:** Full E2O and O2O graph topology, object types, exact multiplicities, O2O qualifiers (e.g., `partially_settles`), and cross-order boundaries.
*   **Information Discarded:** Meaningless variations in local identifiers (e.g., renaming `O1` to `O2`).
*   **Properties:** Reflexive, symmetric, and transitive.
*   **Concurrency:** Relies on a linear extension. If events were partially ordered, graph isomorphism of the causality graph would replace sequence bijection.

### 3. Business-Semantic Equivalence (BSE) — *Preferred*
*   **Definition:** Two executions are equivalent if their canonical Business-Semantic Signatures match. This relation abstracts local IDs into generic typed placeholders based on order of appearance, but strictly preserves event order, E2O multiplicities, and O2O qualifiers. It captures "what happened to the order" from a data-integrity and logistics perspective.
*   **Invariants Preserved:** Lifecycle sequence, object type multiplicities per event, O2O relationships, exception qualifiers, and external dependencies.
*   **Information Discarded:** Specific local identifiers.
*   **Properties:** Reflexive, symmetric, and transitive.
*   **Concurrency:** Handled via stable topological sorting prior to signature generation. 

## 2. Canonical signatures

For BSE (our preferred equivalence), we construct a canonical signature consisting of two parts: a sequence of localized event footprints and a sorted list of O2O relationships. 

The algorithm operates as follows:
1.  Iterate through the execution chronologically.
2.  Map each new local object ID to a canonical placeholder (e.g., `O1` -> `Order_1`, `I11` -> `Item_1`, `I12` -> `Item_2`).
3.  Preserve `EXT-` identifiers exactly as they appear, mapping them to standard prefixes if needed (e.g., `EXT-OA` remains `EXT-OA`).
4.  For each event, record the Activity and a dictionary of `{ObjectType: Count}` for the involved objects.
5.  Record all O2O relations as tuples of `(Source_Type, Target_Type, Qualifier)`. If no qualifier exists, use `None`.

```python
def get_bse_signature(execution):
    id_map = {}
    type_counters = {}
    canonical_events = []
    canonical_o2o = []
    
    # Helper to map raw IDs to canonical local IDs or preserve EXT
    def map_id(obj_id):
        if obj_id.startswith("EXT-"):
            return obj_id
        if obj_id not in id_map:
            # Extract type from ID prefix (e.g., "O1" -> "Order", "I11" -> "Item")
            obj_type = "".join([c for c in obj_id if not c.isdigit()]) 
            # Note: A robust parser would use the explicitly stated ObjectType in the trace.
            # Assuming ObjectType is provided in the trace definition:
            pass 
        return id_map.get(obj_id)

    # This is a simplified representation assuming parsed objects:
    for event in execution:
        activity = event['activity']
        incidence = {}
        for obj_type, obj_ids in event['objects'].items():
            for oid in obj_ids:
                if oid not in id_map and not oid.startswith("EXT-"):
                    type_counters[obj_type] = type_counters.get(obj_type, 0) + 1
                    id_map[oid] = f"{obj_type}_{type_counters[obj_type]}"
                
                canonical_id = map_id(oid)
                incidence[obj_type] = incidence.get(obj_type, 0) + 1
        
        canonical_events.append((activity, str(sorted(incidence.items()))))
        
    # Assuming O2O links are parsed from the execution context
    for o2o in execution.get('o2o_links', []):
        canonical_o2o.append((o2o['source_type'], o2o['target_type'], o2o.get('qualifier', None)))
        
    return tuple(canonical_events), tuple(sorted(canonical_o2o))
```

*   **BSE_3 (Split Shipment, Consolidated Delivery):** Multiple packages grouped into one truck/shipment.
    *   *Risks/Opportunities:* Risk of partial availability delaying the consolidated shipment. Opportunity for warehouse picking optimization.
    *   *Flattening:* Poorly represented by flat event logs, which lose the 2:1 Package-to-Delivery mapping.
    *   *Stability:* Stable.
*   **BSE_4 (Split Fulfillment & Fragmented Payment):** Logistics and financials are both decoupled. 
    *   *Risks/Opportunities:* High operational complexity. Risk of reconciliation errors due to partial settlement (`partially_settles` qualifier).
    *   *Flattening:* Extremely poor representation. Flattening creates a Cartesian explosion of packages, deliveries, and payments.
    *   *Stability:* Stable, though strictly sensitive to payment split counts.
*   **BSE_5 & BSE_6 (Cross-Order Dependencies):** One order relies on another order's logistics (X5) or financials (X6).
    *   *Risks/Opportunities:* Risk of cascading delays. Opportunity for consolidated invoicing/shipping cost reduction.
    *   *Flattening:* Traditional flattening isolates the order, completely erasing the external dependency.
    *   *Stability:* Stable, provided external objects are correctly logged.
*   **BSE_7 (Item Replacement):** An item was modified or substituted before dispatch.
    *   *Risks/Opportunities:* Inventory tracking risk if the `removed_before_dispatch` qualifier is lost. Potential root cause for customer complaints if wrong item shipped.
    *   *Flattening:* Looks identical to BSE_1 in traditional flattening, hiding the exception entirely.
    *   *Stability:* Stable if O2O qualifiers are preserved.
*   **BSE_8 (Return & Re-dispatch):** A full return lifecycle.
    *   *Risks/Opportunities:* High cost of reverse logistics. Opportunity to analyze root cause of returns via the `Inspect` event.
    *   *Flattening:* Poor. The cycle (Dispatch -> Return -> Inspect -> Pack -> Dispatch) is flattened into a confusing sequence of repeated activity names.
    *   *Stability:* Stable.

## 5. Borderline cases

1.  **X1 versus X2:** 
    *   *ASE / TSI / BSE:* All group them together. Identifiers are renamed. A raw-string equivalence without canonicalization would incorrectly split them.
2.  **X1 versus X5:** 
    *   *ASE:* Groups them (Activity labels are identical).
    *   *TSI / BSE:* Splits them. The prompt dictates that external identifiers (`EXT-OA`, `EXT-IA`) encode externality. BSE preserves this boundary, distinguishing a self-contained order from a co-shipped one.
3.  **X1 versus X6:** 
    *   *ASE:* Groups them. 
    *   *TSI / BSE:* Splits them. Even though the logistics sequence is strictly identical to X1, the Invoice and Payment involve `EXT-OB`. Flattening ignores this, but BSE preserves the shared financial boundary.
4.  **X1 versus X7:**
    *   *ASE:* Groups them. The activity trace is strictly identical (`Create, Add, Add, Pack, Dispatch, Issue, Record`).
    *   *TSI / BSE:* Splits them. X7's Dispatch event includes `Item:I72` directly in its E2O incidence, and carries an O2O qualifier `removed_before_dispatch`. A strictly label-based view misses this operational exception; the structural view catches it.
5.  **X3 versus X4:**
    *   *ASE:* Splits them (Sequence order differs: `Pack, Pack, Dispatch` vs `Pack, Dispatch, Pack, Dispatch`).
    *   *TSI / BSE:* Splits them. X4 has interleaved Pack/Dispatch cycles and two Payment events with partial settlement qualifiers. 
    *   *Alternative:* A coarser "Lifecycle Motif" equivalence would merge them into a "Multi-Package" cluster, ignoring multiplicity, but BSE strictly preserves it.
6.  **X4 versus X8:**
    *   *ASE:* Splits them. X8 has `Return Item` and `Inspect Return` activities.
    *   *TSI / BSE:* Splits them. X8 represents a deviation loop (a lifecycle motif of returns), while X4 represents forward-only fragmentation. Both are complex, but their business risks (partial availability vs. customer returns) are fundamentally different.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The `pm4py.cluster_equivalent_ocel` function clusters executions by exact equivalence. By default, it uses the raw object identifiers as part of the equivalence key. Therefore, it preserves **exactly** the E2O incidence, the O2O relationships, the activity sequences, and the exact string values of the object IDs.

*   **Why raw IDs make clusters too fine:** Without pre-processing, PM4Py will treat X1 (`O1`) and X2 (`O2`) as entirely different variants. In real-world logs, database sequence IDs ruin pattern discovery. 
*   **Canonicalization:** To make PM4Py return structurally meaningful clusters (equivalent to TSI or BSE), we must pre-process the OCEL to rename local objects based on their order of appearance per object type.
*   **Exact vs Coarse:** Exact equivalence (via PM4Py) is strictly best for compliance monitoring and root-cause analysis where a specific missing object (like an `EXT-OB` link) changes the legal liability of a process. Coarse equivalence is better for descriptive reporting.
*   **Practical use limits:** If an execution has a massive connected component (e.g., a wholesale order with 500 items), canonicalization is straightforward, but exact equivalence ensures we don't accidentally group a 500-item order with a 2-item order just because their lifecycle "shape" looks similar.

**Python Outline:**
```python
import pm4py
from copy import deepcopy

def canonicalize_ocel(ocel):
    """Renames local objects based on order of appearance, preserving EXT objects."""
    c_ocel = deepcopy(ocel)
    id_map = {}
    type_counters = {}
    
    # Assuming ocel.events and ocel.objects are accessible dataframes
    # Iterate over events chronologically to assign canonical IDs
    for idx, row in c_ocel.relations.sort_values('event_timestamp').iterrows():
        raw_id = row['object_id']
        obj_type = row['object_type']
        
        if raw_id.startswith("EXT-"):
            continue
            
        if raw_id not in id_map:
            type_counters[obj_type] = type_counters.get(obj_type, 0) + 1
            id_map[raw_id] = f"{obj_type}_{type_counters[obj_type]}"
            
    # Apply mapping to the entire OCEL object tables and relation tables
    c_ocel.relations['object_id'] = c_ocel.relations['object_id'].map(lambda x: id_map.get(x, x))
    # (Repeat for objects, object_changes, etc.)
    
    return c_ocel

def get_bse_clusters(ocel):
    # 1. Canonicalize to ignore meaningless identifier variance
    c_ocel = canonicalize_ocel(ocel)
    
    # 2. Use PM4Py to find exact structural variants on the normalized data
    exact_clusters = pm4py.cluster_equivalent_ocel(c_ocel)
    
    # 3. (Optional) Post-process: Merge clusters that only differ by 
    # repeated counts if implementing Lifecycle Motif Equivalence.
    return exact_clusters
```

## 7. Robustness analysis

1.  **Ignore all O2O qualifiers:** 
    *   *Impact:* X1 and X7 would merge into a single cluster, as the `removed_before_dispatch` qualifier distinguishing them would be lost. X4's `partially_settles` would become standard `settles`, though the multiplicity (2 payments) would still separate it from X1.
2.  **Ignore external objects (`EXT-`):** 
    *   *Impact:* X5 and X6 would lose their external boundaries. X5 would merge with X1 (or X3/X4 if multiplicities differ, but X5's logistics matches X1). X6's Invoice would look standard. X1, X5, and X6 might merge if only activity labels and local E2O are considered.
3.  **Collapse repeated same-label events:** 
    *   *Impact:* X3's `Pack, Pack` becomes `Pack`. X4's interleaved sequence collapses. X3 and X4 would likely merge into a single "Multi-Package" motif cluster, as the structural difference between consolidated and split dispatches is washed out by collapsing the sequence.
4.  **Treat Pack/Dispatch as a partial order:** 
    *   *Impact:* X4's interleaved Pack/Dispatch (`P1->D1->P2->D2`) could be interpreted as two parallel independent sub-traces (`P1->D1 || P2->D2`). This reinforces its separation from X3, where `P1` and `P2` strictly precede `D1`.
5.  **Treat payment multiplicity as an amount attribute:** 
    *   *Impact:* X4's two `Record Payment` events would become a single `Record Payment` event with an attribute `amount = [partial, remaining]`. X4's activity sequence would become identical to X3. They would merge under ASE, but BSE (if it captures attributes) might still separate them based on attribute variance.

## 8. Limitations and recommendation

No single equivalence notion is universally optimal. 

*   **Compliance monitoring:** Requires **Typed Structural Isomorphism (TSI)**. Compliance rules frequently depend on specific structural requirements (e.g., "an invoice must not bill external orders unless authorized"). Exact topological matching ensures no unauthorized object sharing goes unnoticed.
*   **Operational segmentation:** Requires **Business-Semantic Equivalence (BSE)**. Segmenting customers by "how their orders are fulfilled" (e.g., split shipment vs. consolidated) necessitates grouping by shape and multiplicity without being distracted by raw IDs.
*   **Root-cause analysis:** Requires **TSI**. When investigating why a specific order failed, analysts must see the exact structural deviations (e.g., X7's removed item or X8's return loop) without them being generalized away.
*   **Descriptive reporting:** Requires **Lifecycle Motif Equivalence (LME)** or coarse BSE. Dashboards reporting on "Return Rates" or "Partial Payment Frequencies" benefit from aggressively collapsing repetitive structures (like treating X3 and X4 simply as "Split Shipments").

**Conclusion:** 
For general-purpose object-centric process mining, **Business-Semantic Equivalence (BSE)** strikes the best balance. It correctly ignores meaningless identifiers (unlike raw PM4Py output) while retaining critical structural nuances like external dependencies and lifecycle exceptions (unlike Activity-Sequence Equivalence). However, any robust analytical platform should allow users to fluidly slide between TSI (for root-cause drilling) and coarse motif grouping (for executive reporting).
