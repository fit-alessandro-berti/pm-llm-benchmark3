## 2. Equivalence and Sufficiency Test

A compensating-control package is evaluated against a multi-dimensional sufficiency matrix rather than a binary pass/fail:

| Dimension | Fully Equivalent | Partially Equivalent | Merely Mitigating | Ineffective |
|---|---|---|---|---|
| **Timing** | Pre-release or pre-settlement | Post-release but pre-settlement | Post-settlement | Beyond recall window |
| **Independence** | No reporting/COI overlap; distinct workstation | Independent but shared infrastructure | Direct supervisor or unresolved COI | Same user or compromised credential |
| **Coverage** | Covers data validity, commercial reasonableness, & bank ownership | Covers data validity only | Covers only automated checks | Bypassed or unavailable |
| **Overrideability** | No override or override requires dual independent sign-off | Override allowed with documented justification | Override by preparer or without review | Override without logging or audit trail |
| **Recoverability** | Funds recallable or blocked | Recall possible but time-constrained | Recall unlikely | Irrevocable settlement |
| **Evidence Quality** | Signed, timestamped, granular review artifacts | Partial documentation | Warning logs only | Missing/unsigned manual checks |
| **Collusion Resistance** | Separated roles, rotated pairs, distinct systems | Separated roles but static pairing | Same workstation or repeated pair | Shared credentials or coordinated override |

**Why “same expected loss” is not the only standard:** Expected loss (probability × impact) is an actuarial risk metric, not a compliance benchmark. Control objectives are governance requirements focused on design effectiveness, independence, and assurance. A control may lower expected loss by reducing impact (e.g., post-settlement audit) while failing the objective because it doesn’t prevent the threat, lacks independence, or violates timing thresholds. Compliance standards also require demonstrable process integrity, auditability, and segregation of duties, which probabilistic loss models cannot capture.

## 4. Preventive–Detective–Corrective Comparison

| Control | Primary Type | Timing Dependency | Preventive Capacity | Detective Capacity | Corrective Capacity | Semantic Note |
|---|---|---|---|---|---|---|
| **AV-2** | Preventive | Before Release_Payment | High (blocks/warns on data anomalies) | Medium (logs warnings/overrides) | None | Acts at process boundary; cannot validate commercial intent |
| **MG-4** | Hybrid | Pre-release > Pre-settlement > Post-settlement | High if pre-release; Medium if pre-settlement | High if post-release; Low if post-settlement | Medium if pre-settlement (can trigger bank hold/recall) | **Manager action after Release_Payment but before Bank_Settlement is hybrid:** detective regarding internal process execution (payment already released), but preventive regarding financial loss (can still initiate recall/hold before irrevocable settlement). |
| **RA-7** | Detective/Corrective | Post-settlement | None | High (pattern analysis, receipt validation) | High if <24h; Low if >24h | Corrective capacity is time-bound to bank recall windows |
| **ED-1** | Framework/Permission | Pre-Prepare to Post-Audit | None (enables single-operator) | None | None | Mandates compensating controls; not a control itself |

## 6. Evidence and Monitoring Recommendations

| Metric | Threshold / Rule | Alert vs. Proof Distinction |
|---|---|---|
| **Same-user rate** | Track % of payments where Prepare=Release. Alert if >5% or any non-ED-1 same-user. | Alert indicates process deviation; proof requires emergency token validation & compensating control verification. |
| **Override rate** | Track AV-2 warning overrides. Alert if >2% or any override by preparer. | Alert signals risk elevation; proof requires override justification logs & independent review evidence. |
| **Late manager approval** | Delta between Release_Payment and Manager_Approve/Ratify. Alert if >0 (post-release) or >4h pre-release. | Alert flags timing gap; proof of deficiency requires review artifact analysis (rubber-stamp vs substantive). |
| **Audit-before-recall-window** | Audit_Review timestamp vs Bank_Settlement. Alert if audit >24h post-settlement. | Alert indicates lost corrective capacity; proof of control failure requires settlement timestamp verification. |
| **Repeated resource pairs** | Track Prepare/Release combinations. Alert if same pair >3 payments/month. | Alert suggests collusion risk or dedicated cell; proof requires organizational design review & independence verification. |
| **Shared workstations** | Log IP/MAC/session overlap. Alert if concurrent or sequential same-session for distinct users. | Alert indicates infrastructure compromise; proof requires session logs & credential audit trails. |
| **Bank-change proximity** | Track bank updates within 7d of payment. Alert if any payment proceeds without enhanced review. | Alert flags data validity risk; proof of failure requires bank-ownership verification records. |
| **Control outages** | Track AV-2 downtime. Alert if any payment processed during outage. | Alert indicates preventive gap; proof of risk realization requires manual checklist & manager review evidence. |

**Monitoring Principle:** Alerts trigger investigation workflows; they do not constitute proof of misconduct. Proof requires corroborating evidence (receipt validation, credential logs, interview records, bank confirmation). Monitoring should focus on control design effectiveness, timing compliance, and independence verification, not just activity counting.
