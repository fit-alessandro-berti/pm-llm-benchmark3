def compute_performance_dfg_fallback(log: pd.DataFrame) -> Dict[Tuple[str, str], Dict[str, float]]:
    work = log.sort_values(["case:concept:name", "time:timestamp"]).copy()
    work["prev_activity"] = work.groupby("case:concept:name")["concept:name"].shift(1)
    work["prev_time"] = work.groupby("case:concept:name")["time:timestamp"].shift(1)
    edges = work.dropna(subset=["prev_activity"])
    perf: Dict[Tuple[str, str], Dict[str, float]] = {}

            "median_days": float(days.median()) if len(g) else float("nan"),

# 1. Model scope and state variables

**Boundary.** The digital twin simulates the municipal building-permit process from applicant submission through permit issuance or rejection. It includes portal/system events, municipal review activities, applicant and third-party response delays, inspection scheduling, site inspection, legal check, public notice, and rework/appeal loops. It excludes construction execution, payments, post-permit inspections, and detailed GIS/permitting-system internals unless they affect process timing.

**Level of detail.** The model is a discrete-event simulation at the activity-resource-calendar level. Cases are represented individually with attributes such as `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, and `requires_public_notice`. Resources, calendars, queues, batching, and cross-case dependencies are explicitly modeled.

**Entities.**
- **Case:** a permit application with state, attributes, timestamps, rework counters, bundle ID, latent objection risk, and SLA clock.
- **Activity instance:** an event such as `Planning review`, `Site inspection`, or `Receive missing documents`.
- **Resource:** clerk, planner, fire reviewer, environmental reviewer, inspector, legal officer, or system.
- **Architect:** a cross-case entity that can generate bursts and related applications.
- **District:** a geographic and policy-relevant entity affecting travel time, environmental sensitivity, objections, and fairness.
- **Inspection bundle:** a temporary grouping of related cases for inspector routing.
- **Objection:** a latent event affecting public-notice duration; not directly observed in the log.
- **Policy:** a configuration flag or parameter set for interventions D1-D10.

**Core state variables.**
- Case state: current activity, status, submission time, last-event time, rework counts, priority, bundle membership, objection risk, and applicable policy flags.
- Resource state: availability time, skill set, working calendar, current location/travel state, capacity, and utilization.
- Queue state: pending cases by activity, resource type, district, priority, and aging.
- Calendar state: holidays, council-meeting weeks, peak months, part-time schedules, reserved time, and inspector field days.
- Environment state: arrival intensity, objection hazard, missing-document hazard, applicant-response distribution, and no-show probability.
- Policy state: enabled interventions and their parameter values.
- Performance state: backlog, open cases, waiting times, rework counts, SLA breaches, and district/architect fairness measures.

**Resources and queues.** Queues are modeled separately for clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, applicant responses, and system tasks. Queues are not merely delays; they depend on resource capacity, calendars, priority rules, batching, and policy changes.

**Calendars.** The model includes working hours, holidays, council-meeting weeks, part-time fire-reviewer availability, environmental reviewers’ reserved non-permit time, inspector field days, and Monday portal-support staffing.

**Cross-case dependencies.** The model includes architect bursts, related applications from the same architect and district, neighborhood objection clusters, inspector geographic batching, shared resource pools, aging-based planner reservations, and policy interactions that affect multiple cases simultaneously.

# 2. Parameter-estimation plan

PM4Py is used for log handling, control-flow discovery, variant analysis, DFG/performance DFG extraction, and conformance validation. It is not used as the simulation engine. The simulation engine consumes estimated parameters and policy logic.

**Log and model handling with PM4Py.**
- Use `pm4py.format_dataframe` with `case:concept:name`, `concept:name`, and `time:timestamp`.
- Use `pm4py.get_variant_statistics` to estimate observed variant shares and durations.
- Use `pm4py.discover_dfg` and `pm4py.discover_performance_dfg` to estimate transition frequencies and inter-event-time proxies.
- Use `pm4py.discover_process_tree_inductive` or `pm4py.parse_process_tree` for model inspection, but treat the simplified tree as a control-flow skeleton, not an executable policy model.
- Use PM4Py alignment/conformance functions for validation, not for generating future cases.

**Arrival estimation.**
- Estimate first-event arrival times per case.
- Fit a non-stationary arrival process, such as a time-varying Poisson or negative-binomial process, with factors for:
  - month/season,
  - weekday,
  - Monday portal spike,
  - architect burst behavior,
  - case-type mix.
- Estimate `(t)` as a baseline rate multiplied by seasonal and weekday factors.
- For architect bursts, model top architects separately using weekly case counts or a Markov-modulated arrival process.
- For D7, modify the arrival distribution by shifting some Monday submissions into appointment slots.

**Service-time estimation.**
- If start and completion timestamps exist, compute service time as `completion - start`.
- If only completion timestamps exist, use inter-event times as waiting/service proxies and calibrate simulated service times to match empirical summaries.
- Fit distributions by activity, case type, district, and resource type.
- Use lognormal, gamma, or Weibull distributions for human activities.
- Use deterministic plus random extension for public notice: 14-day minimum plus objection delay.
- Use separate distributions for applicant-driven activities such as `Receive missing documents`.
- Use empirical quantiles where sample size is adequate; use parametric fits for sparse activities.

**Waiting-time estimation.**
- Prefer start timestamps when available.
- When missing, use PM4Py performance DFG inter-event times as proxies.
- Calibrate simulated queues so that median and p90 waiting times match observed proxies for key activities: completeness check, planning review, environmental review, inspection scheduling, legal check, and decision drafting.
- Explicitly report that proxy waiting includes residual service time and calendar gaps when start timestamps are missing.

**Branching and routing estimation.**
- Estimate conditional probabilities for:
  - fire-safety review,
  - environmental review,
  - public notice,
  - legal check,
  - reject vs. issue,
  - rework loops.
- Use logistic regression or decision trees with attributes such as `case_type`, `district`, `application_value`, `requires_fire`, `requires_environment`, and `requires_public_notice`.
- For missing building area and environmental sensitivity, estimate district-level priors or latent-class probabilities and test sensitivity.
- Use the process tree for structural control flow, but use a simulation router for guards, policy changes, and cross-case dependencies.

**Rework estimation.**
- Identify rework from repeated activities and variants:
  - completeness rework,
  - inspection rework,
  - legal rework,
  - appeal/rework in complex cases.
- Estimate rework probability by case type and attributes.
- Estimate additional duration for each rework loop.
- Since rework reasons are unstructured, use latent rework types and sensitivity analysis rather than assuming reliable cause coding.

**Resource-calendar estimation.**
- Use HR calendars for nominal availability.
- Infer actual busy periods from completion timestamps.
- Estimate council-meeting effects on legal check and public notice.
- Estimate inspector travel time by district and batching effect.
- Estimate environmental reviewer availability after 40% reserved time.
- Estimate fire reviewer availability given Tuesday-Thursday-only work.

**Cross-case dependency estimation.**
- Estimate architect co-submission patterns using `architect_id`, submission week, and district.
- Estimate objection risk from unusually long public-notice durations, treating objections as latent.
- Estimate inspection batching effects from completion timestamps, district, and inspector patterns.
- Validate dependencies with domain experts because the flattened log may underrepresent related cases.

# 3. Assumptions

**Arrivals.**
- Arrivals are non-stationary and driven by month, weekday, case type, and architect behavior.
- Portal submissions can occur outside working hours, but municipal processing waits until the next working window.
- Architect bursts are modeled as correlated arrivals, not independent cases.
- D7 changes the arrival distribution but not total demand unless explicitly specified.

**Service times.**
- Municipal service times are stochastic and conditionally independent given case attributes, resource type, and policy.
- Service times may be heavy-tailed, especially for environmental review, legal check, and complex cases.
- System activities have near-zero service time and unlimited capacity.
- Fixed public-notice minimum is 14 days; objections extend duration.

**Routing.**
- Routing depends on case attributes, latent thresholds, and policy flags.
- Fire review is triggered by `requires_fire` or estimated area threshold.
- Environmental review is triggered by `requires_environment` or estimated district sensitivity.
- Public notice is required for Complex variance and some New residential cases.
- Decision drafting waits for all applicable review, inspection, and public-notice results.
- The simplified process tree does not encode all guards; simulation routing logic supplements it.

**Resources and calendars.**
- Resource capacities are known from HR data but may not match actual event-log utilization.
- Clerks, planners, fire reviewers, environmental reviewers, inspectors, and legal officers have distinct calendars.
- Legal officers are unavailable during council-meeting weeks except urgent cases.
- Environmental reviewers have 40% reserved time.
- Inspectors work Tuesday-Friday and have district-dependent travel time.
- Batching reduces travel time but can increase waiting for the first case in a bundle.

**Rework.**
- Rework is modeled as probabilistic loops with additional duration.
- Rework reasons are latent because unstructured text is unreliable.
- Appeals are treated as a rework or exception path, not as a separate post-permit process.
- Rework rates may change under interventions, especially D1, D2, and D9.

**Applicant and third-party response.**
- Applicant response is modeled separately from municipal service time.
- `Receive missing documents` is applicant-driven and heavy-tailed.
- Consultant reports and third-party inputs can extend environmental review.
- Applicant readiness affects inspection no-shows and rework.

**Cross-case dependencies.**
- Same-architect cases are correlated in arrival and may be related in content.
- Neighborhood objections are latent and may affect multiple cases in the same district or area.
- Inspection bundles create waiting dependencies between cases.
- Shared resource pools create congestion externalities across case types and districts.

**Non-stationary demand.**
- March-May and September-November have elevated arrival rates.
- Monday submissions are high; Wednesday submissions are low.
- Large architects create weekly bursts.
- Stress scenarios amplify these patterns.

**Missing data.**
- Start timestamps are missing for many activities; waiting/service split is inferred.
- Objection events are missing; public-notice duration is used as a proxy.
- Building area and environmental sensitivity are incomplete.
- Emergency decisions are removed, potentially truncating rare tails.
- Rework reasons are not reliably coded.
- Cross-case dependencies may be underrepresented in the flattened log.

# 5. Warm-up, replications, and uncertainty treatment

**Warm-up.** Because demand is non-stationary, the model is not treated as a stationary steady-state system. Use a 30-day burn-in to fill initial queues and stabilize resource availability, or initialize the backlog from a replay of the historical period. Do not discard peak months; analyze results by month and by season.

**Run length.** Use a 24-month horizon with two annual seasonal cycles for policy comparison. For quick screening, use 12 months with common random numbers. For tail and robustness analysis, use 24 months.

**Replications.**
- Baseline and individual policies: 100 paired replications.
- Combined policies: 100 paired replications.
- Stress scenarios: 50 paired replications.
- Sensitivity analysis: 30 replications per perturbed parameter set.

**Random seeds and common random numbers.** Use separate RNG streams for arrivals, service times, routing, rework, objections, applicant response, inspector no-shows, and resource absences. Use the same underlying random draws across policy scenarios where possible so differences are attributable to interventions rather than random noise. When a policy changes the arrival process, use shared uniforms or inverse-CDF streams to preserve comparability.

**Confidence intervals.**
- For mean and median metrics, use paired bootstrap confidence intervals over replications.
- For p90, p95, and p99, use percentile bootstrap and report uncertainty explicitly.
- For SLA compliance, use Wilson or bootstrap confidence intervals.
- For paired policy differences, report 95% confidence intervals for the difference.

**Parameter uncertainty.**
- Use bootstrap resampling of empirical service and response distributions.
- For parametric fits, propagate parameter uncertainty using bootstrap or Bayesian posterior samples.
- For latent objection probabilities and missing thresholds, use high/low scenario bounds.

**Sensitivity analysis.**
- One-at-a-time sensitivity for key parameters: arrival peak, Monday spike, missing-doc rate, objection rate, applicant response tail, inspector travel time, no-show rate, legal council weeks, and environmental variability.
- Global sensitivity for combined policies using a fractional factorial or Sobol design on the most influential parameters.
- Report which interventions are robust and which are sensitive to assumptions.

**Heavy-tailed durations.**
- Use lognormal, gamma, Weibull, or mixture distributions rather than normal distributions.
- For applicant response and public-notice objections, use a mixture with a heavy tail.
- Report p90, p95, p99, and tail ratios, not only medians.
- If tail parameters are uncertain, run low-tail, base-tail, and high-tail scenarios.
- Do not rely on trimmed means for decision-making if SLA compliance depends on the tail.

# 6. Validation strategy

**Face validation.** Review the model with permit clerks, planners, inspectors, legal officers, environmental reviewers, and process owners. Validate activity names, routing logic, rework paths, calendars, batching rules, and policy interpretations.

**Event-log replay validation.** Use PM4Py conformance checking and alignment to verify that the simulated process can reproduce observed control-flow patterns. Check that the model does not generate impossible paths and that replayed historical cases match observed variants within acceptable precision and fitness.

**Distributional validation.** Compare simulated and observed distributions for:
- case duration by case type and district,
- activity waiting-time proxies,
- service-time proxies where start timestamps exist,
- variant shares,
- rework frequencies,
- public-notice durations,
- arrival counts by month and weekday,
- architect burst patterns.
Use quantile comparisons, KS or Anderson-Darling tests, and visual QQ plots. Do not overfit rare variants.

**Resource-utilization validation.** Compare simulated resource utilization with inferred utilization from completion timestamps. Because start timestamps are missing, treat this as approximate validation and test sensitivity to the waiting/service split.

**Bottleneck validation.** Compare simulated bottlenecks with performance DFG and empirical waiting summaries. Expected bottlenecks include Monday clerk queues, planning review, environmental review, inspection scheduling, public notice with objections, and legal check during council weeks.

**Out-of-sample validation.** Train parameters on the first 12 months and validate on the remaining 6 months. Additionally, validate peak-month behavior separately. Use leave-one-district-out or leave-one-case-type-out checks where sample size permits.

**Validation of missing-data assumptions.** Since objections are not observed, validate the latent objection model by checking whether simulated public-notice duration distributions match observed short and long tails. Validate missing start timestamps by comparing simulated inter-event-time proxies with observed performance DFG edges.

# 7. Decision criteria

The simulation is used to compare robustness and trade-offs, not to prove exact optimality. Select interventions that are Pareto-satisfactory or show acceptable trade-offs across metrics.

| Criterion | Metric | Target or decision rule |
|---|---|---|
| Median duration | Median case duration by case type | Improve or preserve; no more than 5% degradation for target case type |
| Tail duration | p90 and p95 case duration by case type | p90 reduction >= 10% for target case type; p95 reduction >= 15% for high-risk variants |
| SLA compliance | Share of cases within SLA by case type | Simple p90 <= 24 days; New residential p90 <= 75-95 days; Commercial p90 <= 110-130 days; Complex p90 <= 220-260 days, with improvement over baseline |
| Fairness | District p90 spread and architect burst effects | No district p90 worse than baseline by > 5 days; no architect-burst group worse than baseline by > 10% |
| Resource utilization | Average and peak utilization by resource pool | Planners 65-85%; inspectors 60-90% peak; legal <= 75% outside council weeks; no sustained > 95% for more than two weeks |
| Rework | Completeness, inspection, legal, and appeal rework rates | Completeness rework <= 20%; inspection rework <= 8%; appeal/rework <= 5%; no increase > 2 percentage points without offsetting benefit |
| Backlog | Open cases older than 60 or 90 days | Cases > 60 days <= 2% of active backlog; cases > 90 days <= 1% |
| Robustness | Performance under S1-S3 stress scenarios | p90 degradation under stress <= 20% relative to baseline stress; policy remains beneficial in at least two of three stress scenarios |
| Risk | Quality, legal, or environmental risk proxies | No-inspection and triage policies require explicit risk bounds; no unacceptable increase in rework, objections, or post-permit complaints |
| Feasibility | Implementation effort and cost | Temporary inspector cost acceptable; early-warning and triage require data availability; combined policy must not create unmanageable operational complexity |

A policy should be selected only if it improves the primary objective, does not violate fairness or utilization guardrails, and remains robust under stress scenarios.

def parse_process_model(tree_string: str, log: pd.DataFrame) -> Tuple[Any, str]:
    """
    Try to parse the simplified process tree string. If PM4Py cannot parse it,
    fall back to an inductive process tree from the log.
    """
    clean_tree = " ".join(tree_string.split())

    try:
        tree = pm4py.parse_process_tree(clean_tree)
        note = "Parsed simplified process-tree string."
    except Exception as exc:
        note = (
            f"pm4py.parse_process_tree failed ({exc}). "
            "Using inductive process tree as fallback. "
            "The simplified string is only a control-flow sketch and may not "
            "encode guards, policies, or cross-case dependencies."
        )
        try:
            tree = pm4py.discover_process_tree_inductive(log)
        except Exception as exc2:
            tree = None
            note += f" Inductive fallback failed ({exc2})."

    return tree, note

def compute_performance_dfg_fallback(log: pd.DataFrame) -> Dict[Tuple[str, str], Dict[str, float]]:
    """
    Fallback performance DFG if the installed PM4Py version does not provide
    discover_performance_dfg or returns an incompatible object.
    """
    work = log.sort_values(["case:concept:name", "time:timestamp"]).copy()
    work["prev_activity"] = work.groupby("case:concept:name")["concept:name"].shift(1)
    work["prev_time"] = work.groupby("case:concept:name")["time:timestamp"].shift(1)

    edges = work.dropna(subset=["prev_activity"])
    perf: Dict[Tuple[str, str], Dict[str, float]] = {}

    for (a, b), g in edges.groupby(["prev_activity", "concept:name"]):
        days = (g["time:timestamp"] - g["prev_time"]).dt.total_seconds() / 86400.0
        perf[(str(a), str(b))] = {
            "frequency": float(len(g)),
            "median_days": float(days.median()) if len(g) else float("nan"),
            "p90_days": float(days.quantile(0.9)) if len(g) else float("nan"),
        }

    return perf


def compute_pm4py_statistics(log: pd.DataFrame) -> Dict[str, Any]:
    """
    Compute PM4Py-based control-flow and performance summaries.
    """
    variants = pm4py.get_variant_statistics(log)

    # DFG: frequencies only.
    dfg, start_activities, end_activities = pm4py.discover_dfg(log)

    # Performance DFG: inter-event-time summaries.
    try:
        perf = pm4py.discover_performance_dfg(log)
        if isinstance(perf, tuple):
            perf_dfg = perf[0]
        else:
            perf_dfg = perf
    except Exception:
        perf_dfg = compute_performance_dfg_fallback(log)

    return {
        "variants": variants,
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": perf_dfg,
    }


def compute_arrival_profile(log: pd.DataFrame) -> Dict[str, Any]:
    """
    Estimate case arrival average and simple non-stationary patterns.
    """
    first_events = (
        log.groupby("case:concept:name")["time:timestamp"]
        .min()
        .sort_values()
    )

    inter_days = first_events.diff().dt.total_seconds() / 86400.0
    mean_interarrival_days = float(inter_days.mean()) if not inter_days.empty else float("nan")

    arrival_rate_per_day = (
        1.0 / mean_interarrival_days
        if mean_interarrival_days == mean_interarrival_days and mean_interarrival_days > 0
        else float("nan")
    )

    by_month = first_events.dt.to_period("M").value_counts().sort_index()
    by_weekday = (
        first_events.dt.day_name()
        .value_counts()
        .reindex(
            [
                "Monday",
                "Tuesday",
                "Wednesday",
                "Thursday",
                "Friday",
                "Saturday",
                "Sunday",
            ]
        )
        .fillna(0)
    )

    return {
        "n_cases": int(first_events.size),
        "mean_interarrival_days": mean_interarrival_days,
        "arrival_rate_per_day": arrival_rate_per_day,
        "arrivals_by_month": by_month,
        "arrivals_by_weekday": by_weekday,
    }


def add_service_waiting_columns(log: pd.DataFrame) -> pd.DataFrame:
    """
    Add service/waiting columns when possible.

    Important limitation:
    - If start timestamps are missing, waiting_time_hours is only a proxy for
      inter-event time and conflates waiting, previous service, and calendar gaps.
    """
    work = log.sort_values(["case:concept:name", "time:timestamp"]).copy()
    work["prev_end"] = work.groupby("case:concept:name")["time:timestamp"].shift(1)

    if "time:timestamp_start" in work.columns and work["time:timestamp_start"].notna().any():
        work["service_time_hours"] = (
            (work["time:timestamp"] - work["time:timestamp_start"]).dt.total_seconds() / 3600.0
        )
        work["waiting_time_hours"] = (
            (work["time:timestamp_start"] - work["prev_end"]).dt.total_seconds() / 3600.0
        )
    else:
        # No reliable service/wait split.
        work["service_time_hours"] = np.nan
        work["waiting_time_hours"] = (
            (work["time:timestamp"] - work["prev_end"]).dt.total_seconds() / 3600.0
        )
        work["waiting_time_hours"] = work["waiting_time_hours"].clip(lower=0)

    return work


def compute_activity_summary(log: pd.DataFrame) -> pd.DataFrame:
    """
    Summarize activity-level event counts and proxy waiting times.
    """
    work = add_service_waiting_columns(log)

    summary = (
        work.groupby("concept:name")
        .agg(
            events=("concept:name", "size"),
            cases=("case:concept:name", "nunique"),
            median_waiting_proxy_hours=("waiting_time_hours", "median"),
            p90_waiting_proxy_hours=("waiting_time_hours", lambda s: s.quantile(0.9)),
            median_service_hours=("service_time_hours", "median"),
        )
        .reset_index()
    )

    return summary

class WorkingCalendar:
    """
    Placeholder calendar object.

    In a full model, this would encode:
    - holidays,
    - council-meeting weeks,
    - resource-specific working windows,
    - part-time schedules,
    - reserved time,
    - peak months.
    """

    def __init__(
        self,
        holidays: Iterable[pd.Timestamp],
        council_weeks: Iterable[Tuple[pd.Timestamp, pd.Timestamp]],
        resource_windows: Dict[str, List[Tuple[int, int, int]]],
    ):
        self.holidays = {pd.Timestamp(h).normalize() for h in holidays}
        self.council_weeks = [
            (pd.Timestamp(s).normalize(), pd.Timestamp(e).normalize())
            for s, e in council_weeks
        ]
        self.resource_windows = resource_windows

    def is_working(self, ts: pd.Timestamp, resource_type: str) -> bool:
        ts = ts.normalize()

        if ts in self.holidays:
            return False

        if resource_type == "legal":
            if any(start <= ts <= end for start, end in self.council_weeks):
                return False

        windows = self.resource_windows.get(resource_type, [])
        if windows:
            return any(ts.weekday() == day for day, _, _ in windows)

        # Default: Monday-Friday.
        return ts.weekday() < 5

    def next_working_time(self, ts: pd.Timestamp, resource_type: str) -> pd.Timestamp:
        candidate = ts
        for _ in range(10000):
            if self.is_working(candidate, resource_type):
                return candidate
            candidate += pd.Timedelta(hours=1)
        return ts


class ResourcePool:
    """
    Placeholder resource pool.

    A full implementation would model:
    - skill routing,
    - capacity changes,
    - part-time availability,
    - travel time,
    - inspector batching,
    - urgent-case exceptions.
    """

    def __init__(
        self,
        resource_type: str,
        capacity: int,
        calendar: WorkingCalendar,
        working_hours_per_day: float = 7.0,
    ):
        self.resource_type = resource_type
        self.capacity = capacity
        self.calendar = calendar
        self.working_hours_per_day = working_hours_per_day
        self.resources = [
            Resource(
                resource_id=f"{resource_type}_{i}",
                resource_type=resource_type,
                skills=[resource_type],
                location="D1",
                available_at=pd.Timestamp("2026-01-01"),
            )
            for i in range(capacity)
        ]

    def available(self, ts: pd.Timestamp) -> List[Resource]:
        return [
            r
            for r in self.resources
            if r.available_at <= ts and self.calendar.is_working(ts, self.resource_type)
        ]

    def acquire(
        self,
        case_id: str,
        activity: str,
        ts: pd.Timestamp,
        duration_hours: float,
    ) -> Optional[Tuple[str, pd.Timestamp, pd.Timestamp]]:
        avail = self.available(ts)
        if not avail:
            return None

        resource = min(avail, key=lambda r: r.available_at)
        start = max(ts, resource.available_at)
        start = self.calendar.next_working_time(start, self.resource_type)

        # Simplified: does not yet account for non-working interruptions.
        end = start + pd.Timedelta(hours=duration_hours)
        resource.available_at = end

        return resource.resource_id, start, end


@dataclass(order=True)
class QueueItem:
    priority: float
    case_id: str = field(compare=False)
    activity: str = field(compare=False)
    requested_at: pd.Timestamp = field(compare=False)


class PriorityQueue:
    def __init__(self, name: str):
        self.name = name
        self.items: List[QueueItem] = []

    def push(self, case_id: str, activity: str, now: pd.Timestamp, priority: float) -> None:
        heapq.heappush(
            self.items,
            QueueItem(priority=priority, case_id=case_id, activity=activity, requested_at=now),
        )

    def pop(self) -> Optional[QueueItem]:
        if not self.items:
            return None
        return heapq.heappop(self.items)

    def __len__(self) -> int:
        return len(self.items)

    df_raw, log = load_and_format_log()

    pm_stats = compute_pm4py_statistics(log)
    arrival_profile = compute_arrival_profile(log)
    log_with_durations = add_service_waiting_columns(log)
    activity_summary = compute_activity_summary(log)

    print("Process-tree note:", tree_note)
    print("Variants:", pm_stats["variants"])
    print("DFG edges:", list(pm_stats["dfg"].items())[:10])
    print("Performance DFG edges:", list(pm_stats["performance_dfg"].items())[:10])
    print("Arrival profile:", {k: v for k, v in arrival_profile.items() if k != "arrivals_by_month" and k != "arrivals_by_weekday"})
    print("Mean interarrival days:", arrival_profile["mean_interarrival_days"])
    print("Arrival rate per day:", arrival_profile["arrival_rate_per_day"])
    print("Activity summary:")
    print(activity_summary)

    # If start timestamps are missing, make the limitation explicit.

        print(
            "Warning: start timestamps are missing. "

    # Prepare calibration artifacts for the simulation engine.
    log_stats = {

        "activity_summary": activity_summary,
