What the PM4Py key preserves (as I understand): object type + set of activities an object participates in ("object footprint"); then event key = multiset of the footprints of objects linked to the event; events with equal keys form clusters; the returned clusters are *event* clusters within a single Ocel, and the Ocel is returned with cluster labels attached. It preserves: types, incidence, event multiplicity (as clusters of events), and it ignores: identifier values, timestamps, event order, quantities/amounts, O2O qualifiers and O2O relations (unless the objects' activity footprints already encode them indirectly), external-vs-local distinction (a shared object simply appears in two orders' events — hmm, but with E2O, an external order's object has a footprint spanning both orders' events, so externality is partially visible as a wide footprint; but the "EXT" flag per se is not preserved — it's visible only as an object with a large footprint). Why raw identifiers make exact clusters too fine: if you key on the raw (activity, tuple(sorted(object_ids))), then every distinct order has distinct ids  every event gets a unique key  no clustering at all; and renaming the same process across orders yields different keys; also the key doesn't generalize across executions unless you map to canonical group ids, which requires the two-level (object-class then event-class) construction. PM4Py's two-level scheme solves this. But note: if the data has "noise" (e.g., an extra object type participating), the object footprint changes and the event cluster differs  over-fragmentation.

1. Recompute canonical keys with a controlled vocabulary (strip prefixes, unify type synonyms, map multi-item events to counts).

def archetype_facets(ex):
    lead = ex.lead
    items_local = {o for o,t in ex.otype.items() if t=="Item" and ex.owner.get(o)==lead}
    packs = [e for e in ex.events if e.label=="Pack" and lead in e.objects]
    p1 = first_attempt_packs(ex, packs)
    covered = set().union(*[set(e.objects) & items_local for e in p1]) if p1 else set()
    packaging_scope = ("order" if len(p1)>=1 and covered==items_local
                       else "line" if len(p1)>=2 else "mixed")
    # delivery scope over first attempt
    dl = [e for e in ex.events if e.label=="Dispatch" and lead in e.objects]
    d1 = [d for d in dl if any(after(ex,p,d) for p in p1)]   # dispatch of first attempt
    pkgs1 = set().union(*[set(e.objects) for e in p1])
    carried = {d: set(d.objects) & pkgs1 for d in d1}
    delivery_scope = ("order" if len(d1)==1 and len(carried[d1[0]])==len(pkgs1)
                      else "package" if all(len(v)==1 for v in carried.values())
                      else "mixed")
    # billing / settlement
    inv = [e for e in ex.events if e.label=="Issue"]
    billing_scope = "cross_order" if any(ex.owner.get(o) not in (None,lead) for e in inv for o in e.objects if ex.otype[o]=="Order") else "order"
    pay = [e for e in ex.events if e.label=="Record"]
    settlement_scope = "shared_unallocated" if any(e for e in pay if any(ex.owner.get(o) not in (None,lead) and ex.otype[o]=="Order" for o in e.objects)) else "order"
    # isolation: phases in which a foreign order participates
    iso = set()
    for e in ex.events:
        if any(ex.owner.get(o) not in (None, lead) and ex.otype[o]=="Order" for o in e.objects):
            iso.add(PHASE.get(e.label,"other"))
    # motifs
    motifs = set()
    for (s, st, t, tt, act, q) in ex.o2o:
        if q in QUAL_MOTIF: motifs.add(QUAL_MOTIF[q])
    for e in ex.events:

    shipped_items = set().union(*[set(e.objects)&items_local for e in d1]) if d1 else set()
    if packed_items - shipped_items: motifs.add("line_removal")
    return (tuple(sorted(iso)), packaging_scope, delivery_scope, billing_scope,
            settlement_scope, tuple(sorted(motifs)))

# Object-Centric Equivalence Design for Eight Order Executions

## 1. Equivalence design space

**Base model.** An execution is $X=(O,E,\lambda,\alpha,q)$: objects $O$ with a type and an owning Order; events $E$ with an activity label, a timestamp and an incidence to objects; $\alpha$ the happens-before relation derived from timestamps (equal timestamps yield *no* edge); $q$ the O2O relations carrying qualifiers. The lead object type is `Order`; an object is **external** iff its owning Order is not the lead Order. Everything below is defined relative to the lead Order, never to a raw identifier.

**R1 — Activity-sequence equivalence.**
*Definition.* Build the label-labelled DAG $D_X$ (nodes = events, node label = activity, edges = $\alpha$) and compare up to label-preserving isomorphism. For the totally ordered logs given here this reduces to equality of the label sequence.
*Preserves:* the activity multiset and coarse activity causality. *Discards:* all objects, types, multiplicities, externality, qualifiers, timestamps.
*Properties.* Reflexive, symmetric, transitive (isomorphism on finite structures is an equivalence). *Concurrency.* Ties simply produce no edge, so two same-label events with identical predecessors/successors are interchangeable — this is exactly why X1 and X2 coincide.

**R2 — Typed structural equivalence under identifier renaming (E2O only).**
*Definition.* $\phi(o)=(\mathrm{type}(o),\mathrm{ext}(o),\mathrm{acts}(o))$, where $\mathrm{acts}(o)$ is the set of activity labels of events containing $o$; $\psi(e)=(\mathrm{label}(e),\{\!\{\phi(o):o\in e\}\!\})$ retaining instance counts; $\mathrm{Key}(X)=\{\!\{\psi(e)\}\!\}$ (order-insensitive multiset). $X\equiv_2 Y \iff \mathrm{Key}(X)=\mathrm{Key}(Y)$. This is a 1WL-style canonicalisation: sound, and complete for isomorphism on this dataset.
*Preserves:* types, eventobject incidence, object counts per event, event multiplicity, externality flags. *Discards:* identifiers, order/timestamps, O2O relations and qualifiers, amounts and quantities.
*Properties.* Reflexive, symmetric, transitive (equality of canonical keys). *Concurrency.* Irrelevant — incidence only; the ordered variant uses a canonical topological sort with deterministic tie-break.

**R3 — Business-semantic equivalence (archetype level).** *(preferred)*
*Definition.* Extract a facet vector $\Phi(X)$ and compare it:
1. *Isolation* — phases in which a non-lead Order participates (`fulfilment`, `billing`).
2. *Packaging scope* — `order` (one package binds all order lines) / `line` (lines split across packages) / `mixed`.
3. *Delivery scope* — `order` (one delivery carries all first-attempt packages) / `package` (one delivery per package).
4. *Billing scope* — `order` / `cross_order`.
5. *Settlement scope* — `order` / `shared_unallocated`.
6. *Archetype motifs* — normalised O2O qualifier motifs: `line_removal`, `substitution`, `repack`, `package_replacement`, `return`, `inspection`.

$X\equiv_3 Y \iff \Phi(X)=\Phi(Y)$. The organising principle: **the archetype records which entities are bound together in one business transaction and which capability is exercised; it deliberately ignores how many records realise that binding.** Settlement-schedule motifs (`instalment`, `settlement_complete`) and record counts are pushed into a *variant* vector $V(X)$, so instalment payment is a variant of an order-scoped obligation, not a different obligation.

*Preserves:* binding scope, cross-order coupling, exception motifs, settlement scope. *Discards:* identifiers, timestamps, counts of packages/deliveries/payments, delivery batching, instalment count.
*Properties.* Reflexive, symmetric, transitive ($\Phi$ is a deterministic function of $X$). *Concurrency.* Facets use reachability in $\alpha$, not timestamps; motifs that cannot be established under a partial order are recorded as `indeterminate` rather than guessed, and no event is invented.

**R4 — Strict facet equivalence (audit level).** $X\equiv_4 Y \iff (\Phi(X),V(X))=(\Phi(Y),V(Y))$. It adds package/delivery/invoice/payment counts, batching mode and settlement motifs; on this dataset it reproduces R2's partition. Note R1, R2, R3 are not nested in general (R2 is order-insensitive, so it may merge differently-ordered sequences that R1 separates).

## 2. Canonical signatures

The scheme below is rename-invariant (signatures never contain identifiers), deterministic (all sets sorted), and distinguishes three layers: a structural key, an archetype key $\Phi$, and a variant key $V$.

```python
# ---- canonical signature machinery -------------------------------------------
from collections import Counter, defaultdict

PHASE = {"Create":"order", "Add":"line", "Pack":"fulfilment", "Dispatch":"fulfilment",
         "Issue":"billing", "Record":"billing", "Return":"exception", "Inspect":"exception"}

# motif vocabulary keyed by (source_type, target_type, qualifier)
MOTIF = {("Item","Item","replaces"):"substitution",
         ("Package","Item","removed_before_dispatch"):"line_removal",
         ("Package","Item","repack"):"repack",
         ("Package","Package","replaces"):"package_replacement",
         ("Payment","Invoice","partially_settles"):"instalment",
         ("Payment","Invoice","completes_settlement"):"settlement_complete"}
ACT_MOTIF = {"Return":"return", "Inspect":"inspection"}
ARCHETYPE_MOTIFS = {"substitution","line_removal","repack","package_replacement",
                    "return","inspection"}          # part of Phi
VARIANT_MOTIFS   = {"instalment","settlement_complete"}   # part of V only

def canon(x): return repr(x)

def object_signature(otype, external, acts):
    return (otype, bool(external), tuple(sorted(acts)))

def event_signature(label, obj_sigs):
    return (label, tuple(sorted(obj_sigs)))          # multiplicity preserved

def structural_key(ex, ordered=False):
    acts = defaultdict(set)
    for e in ex.events:
        for o in e.objects: acts[o].add(e.label)
    osig = {o: object_signature(ex.otype[o], ex.owner[o] != ex.lead, acts[o]) for o in acts}
    esig = {e.eid: event_signature(e.label, [osig[o] for o in e.objects]) for e in ex.events}
    if ordered:   # canonical topological order, ties broken by signature
        return tuple(canon(esig[e.eid]) for e in ex.sorted_events())
    return tuple(sorted(canon(k) for k, _ in Counter(esig.values()).items()))

def archetype_facets(ex):
    lead = ex.lead
    items = {o for o,t in ex.otype.items() if t=="Item" and ex.owner.get(o)==lead}
    packs = [e for e in ex.events if e.label=="Pack" and lead in e.objects]
    p1 = [p for p in packs if not ex.after_return(p)]            # first attempt only
    covered = set().union(*[set(e.objects) & items for e in p1]) if p1 else set()
    packaging = "order" if (len(p1)==1 and covered==items) else ("line" if len(p1)>=2 else "mixed")
    pkgs1 = set().union(*[set(e.objects) for e in p1]) if p1 else set()
    dl = [d for d in ex.events if d.label=="Dispatch" and lead in d.objects]
    d1 = [d for d in dl if set(d.objects) & pkgs1]
    carried = [set(d.objects) & pkgs1 for d in d1]
    delivery = ("order" if len(d1)==1 and len(carried[0])==len(pkgs1)
                else "package" if all(len(c)==1 for c in carried) else "mixed")
    def foreign_orders(e): return [o for o in e.objects
                                  if ex.otype.get(o)=="Order" and ex.owner.get(o)!=lead]
    inv = [e for e in ex.events if e.label=="Issue" and lead in e.objects]
    pay = [e for e in ex.events if e.label=="Record" and lead in e.objects]
    billing = "cross_order" if any(foreign_orders(e) for e in inv) else "order"
    settle = ("shared_unallocated" if any(foreign_orders(e) for e in pay) else "order")
    iso = {PHASE.get(e.label,"other") for e in ex.events if foreign_orders(e)}
    motifs = set()
    for (s, st, t, tt, act, q) in ex.o2o:
        m = MOTIF.get((st, tt, q))
        if m: motifs.add(m)
    for e in ex.events:
        if e.label in ACT_MOTIF: motifs.add(ACT_MOTIF[e.label])
    shipped = set().union(*[set(d.objects) & items for d in d1]) if d1 else set()
    if (covered - shipped): motifs.add("line_removal")     # qualifier-free fallback
    return (tuple(sorted(iso)), packaging, delivery, billing, settle,
            tuple(sorted(motifs & ARCHETYPE_MOTIFS)))

def variant_key(ex):
    counts = Counter(e.label for e in ex.events)
    vmot = sorted(m for m in motif_set(ex) if m in VARIANT_MOTIFS)
    return (counts["Pack"], counts["Dispatch"], counts["Issue"], counts["Record"],
            tuple(vmot))
```

Keys: $\Phi$ (archetype, R3), $(\Phi,V)$ (strict, R4), and `structural_key` (R2). Because every component is a sorted tuple of type/flag/label strings, two executions can be compared by plain equality, and the whole scheme is reproducible from an OCEL table plus a qualifier table.

## 4. Cluster interpretations

**F1 — Self-contained order-to-cash (X1, X2).** Signature: one package binding all lines, one delivery, one invoice binding only the lead Order, one payment, no externality, no motifs. Business: the textbook single-order fulfilment and cash collection; nothing is shared with another order. Risk: it is the majority class, so any dashboard built on F1 hides the exception rate (three of eight traces here are not F1 yet look identical in a log). Opportunity: the reference segment for SLA benchmarking and regression detection. Poorly represented by label-only flattening (it absorbs X5, X6, X7) and by any "one order = one package = one invoice = one payment" four-box flattening that treats shared objects as ordinary. Stability: high — invariant to renaming, event order and identifier churn; breaks only if source systems merge Invoice and Payment or drop empty relations.

**F2 — Split fulfilment with order-level billing (X3, X4).** Signature: packaging scope `line`, billing scope `order`, no externality, no motifs. Business: fulfilment granularity falls below order granularity — the same commercial obligation is physically decomposed into packages and delivery waves; X3 is the consolidated variant (one delivery, one payment), X4 the fragmented variant (delivery per package, instalment settlement). Risks: partial deliveries and missed consolidated delivery SLAs; revenue recognition and dunning complexity where settlement is instalment. Opportunity: line-level packing enables carrier/zone optimisation and partial shipment; consolidation cuts cost. Poorly represented by bag-of-activities flattening (which merges F2 into F1) and by counting "packages per order" without binding (which cannot tell consolidation from fragmentation). Stability: medium — robust to renaming and ordering, but sensitive to how consolidation is recorded (one Dispatch with two packages versus two Dispatches) and to whether instalments are modelled as events or amounts.

**F3 — Cross-order consolidated fulfilment (X5).** Signature: isolation `{fulfilment}`, otherwise order-scoped. Business: a package and delivery that mix a foreign order's line with the lead order's lines (consolidated shipping, gift shipment, drop-ship). Risks: revenue attribution, mis-packing attribution, freight charged to the wrong order, and the invoice (O5 only) no longer matching the physical consignment. Opportunity: shipping-cost reduction and carrier consolidation campaigns. Poorly represented by any flattening that projects to the lead Order's own objects — the entire phenomenon disappears; an E2O-only projection shows exactly X1's event counts. Stability: stable provided externality flags survive; it collapses into F1 the moment external objects are stripped.

**F4 — Cross-order consolidated billing (X6).** Signature: billing scope `cross_order`, settlement `shared_unallocated`, isolation `{billing}`, logistics untouched. Business: consolidated invoicing (e.g. periodic or marketplace billing) where one invoice and one payment cover several orders without allocation. Risks: order-level margin, tax and revenue cannot be computed from the trace; cash attribution and dispute handling break. Opportunity: lower billing cost, B2B credit terms. Poorly represented by flattening "order  activities", which reproduces F1 exactly; and by financial flattening assuming invoiceorder is 1:1. Stability: depends entirely on whether the invoice's multi-order binding is retained; if the billing system stores allocations elsewhere, the trace is unidentifiable.

**F5 — Line substitution / removal before dispatch (X7).** Signature: archetype motifs `{line_removal, substitution}`; the dispatched line set is a strict subset of the packed line set. Business: a line was cancelled or substituted after packing but before dispatch; the shipment and the invoice no longer describe the same goods. Risks: mis-shipment, unauthorised substitution, revenue-versus-shipped-item mismatch, inventory that was picked and returned. Opportunity: substitution capture and approval-workflow metrics. Poorly represented by label-only flattening (indistinguishable from F1) and by any flattening that keeps only the final item list. Stability: moderate — the *partition* survives loss of qualifiers (the shippedpacked signal is E2O-derivable), but a data-repair policy that overwrites the package contents instead of qualifying them erases the evidence and merges F5 into F1.

**F6 — Return and repack (X8).** Signature: archetype motifs `{return, inspection, repack, package_replacement}`; one line traverses two deliveries. Business: reverse flow followed by re-fulfilment or re-packing for reshipment. Risks: revenue reversal, double counting of the line in two packages, duplicated freight, and a second wave that bypasses the original approval. Opportunity: return-rate analytics and reship SLA. Poorly represented by order-level activity flattening (the line's double traversal is invisible) and by feature vectors over counts only, where X8 and X4 look alike (2 packages, 2 deliveries) although one is a forward split and the other a reverse flow. Stability: stable while the return event and replacement qualifier persist; unstable if returns are re-keyed as fresh orders, which would re-label it as F1.

## 5. Borderline cases

**X1 vs X2.** R1 and R2 both equate them: the two Add Item events differ only by local identifier and are mutually exchangeable (under a partial order they are unordered, so isomorphism can swap them). A third, defensible definition *does* separate them — a *behavioural* relation requiring "the line added first is the line packed first" or "identifier order encodes customer request order". Such a relation is usually an artefact of log-generation order rather than business meaning, and it is exactly the kind of difference the brief warns against treating as meaningful.

**X1 vs X5.** R1 cannot see the difference (identical label sequence). R2 and R3 separate it because the foreign Order and foreign line change the pack/dispatch binding and the isolation set. A defensible competing view projects the trace to the lead Order's own scope ("what happened in *my* order?"), under which X5 is an ordinary order — legitimate for per-order operational analytics, but it renders consolidated shipping invisible and destroys freight-cost attribution. The third position (keep them in one family, record the shared scope as a variant flag) is what many ERP order-centres actually implement.

**X1 vs X6.** R1 equates them; R2/R3 separate them (one invoice binds two Orders; payment is unallocated). A defensible disagreement: if the analytical question is purely logistics, X6 is F1 and the shared invoice is a billing-side attribute; if the question is "is this order financially self-contained?", X6 must be separated, because order-level revenue, tax and margin are simply not derivable from the trace.

**X1 vs X7.** R1 equates them (same labels). R2 separates them because the substitute line appears in Dispatch and the two lines have different footprints {Add,Pack} vs {Add,Pack,Dispatch}; R3 separates them via `line_removal`/`substitution` and the shippedpacked test. The genuinely dangerous case is a *repaired* log in which the cancelled line is overwritten out of the Pack event: then X7 becomes E2O-identical to X1 and only the qualifier distinguishes it. Two defensible definitions (E2O-only vs qualifier-aware) then disagree completely.

**X3 vs X4.** This is the pivotal modelling decision of the whole study. R1 and R2 separate them (different label sequences; different event multiplicity and delivery–package incidence). R3 merges them into F2 on the principle that both exercise the same capability — fulfilment decomposed below order granularity under a single order-scoped commercial obligation — and treat consolidated dispatch and instalment settlement as execution variants. The strict relation R4 (+V) splits them back into F2a={X3} and F2b={X4}. Merge if you are asking "which fulfilment capabilities does this process have?"; split if you are asking "does delivery align with package, and is cash collected in one event?" I recommend merging for segmentation and retaining the variant vector so the split is recoverable.

**X4 vs X8.** Both have two packages, two deliveries and two "waves". R1/R2 separate them on counts and labels; R3 separates them on motifs (X8 carries return/repack/package_replacement) and on lineage (X4's waves carry *different* lines; X8's second wave carries a line already delivered once). A defensible merge exists for capacity-planning segmentation — "two-wave fulfilment of one order" — but it is dangerous: a coarse feature vector over counts alone would merge a forward commercial split with a reverse flow carrying revenue-reversal and duplicate-freight risk.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the PM4Py key preserves.** In the releases I know, `pm4py.cluster_equivalent_ocel(ocel)` works in two stages. First it computes an *object footprint* per object — object type together with the set of activities in which that object occurs — and partitions objects into classes by that footprint. Second it forms an *event key* from the multiset of footprints of the objects linked to that event, and groups events with identical keys. It therefore preserves: object types, the eventobject incidence structure, per-event object counts, and event multiplicity (as clusters of events). It discards: identifier values, timestamps and event order, amounts and quantities, and — critically — the O2O relation with its qualifiers. Externality is not represented as a flag; a shared object merely shows up as an object with a wide footprint. The returned clusters are **event-level** classes, labelled with local indices, so they are not directly comparable across OCs. (Check the exact signature and returned fields in your installed version; some releases accept extra keyword arguments.)

**Why raw identifiers make exact clusters too fine.** Keying on `(activity, tuple(sorted(object_ids)))` makes every event unique — in every order — so clustering degenerates to identity. Renaming a process across two executions then yields different keys even though the processes are identical. PM4Py's two-level construction fixes this by replacing identifiers with footprints; the remaining over-fragmentation risk comes from *noise* (an extra object type touching an event, a stray activity), which changes a footprint and splits a class.

**Post-processing.** (i) Recompute a canonical, execution-comparable key yourself (never rely on per-OCel cluster indices): object footprint  event key  multiset of event keys per lead Order. (ii) Enrich with the O2O relation, which PM4Py's Ocel exposes as `ocel.qualifiers` (source/target ids and types, activity, qualifier) even though the clustering key ignores it: use it for replacement, removal, repack and partial-settlement motifs, and for detecting externality (an Order object that appears in events whose lead is another Order). (iii) Aggregate event-level clusters to Order level and then to a business-family label using the facet extractor. (iv) Report cluster sizes and the singleton rate; a partition of seven clusters over eight traces is a diagnostic, not a segmentation.

**When exact equivalence is preferable.** Compliance and audit evidence, exception queues, "no order may be dispatched against an invoice that covers another order" style controls, regression tests on curated traces, and small data-quality samples where any deviation must be surfaced.

**`max_objs` and large connected executions.** Where Ocel construction caps the number of objects linked per event (surfaced as `max_objs` in some releases), the footprint is computed on the retained subset: two structurally different events can collapse into one class (false merges) and cross-order links can be dropped (lost externality), so clusters become artefacts of the cap. Independently, executions with hundreds of objects per event (bulk invoices, consolidated packing) produce near-identical footprints and therefore giant equivalence classes, plus memory and runtime pressure; and the qualifier graph becomes the only reliable carrier of cross-order semantics. Remedies: raise or disable the cap for the phases you care about, aggregate objects by type before signature computation, and read externality and motifs from `ocel.qualifiers` rather than from E2O counts.

```python
import pm4py
from collections import Counter, defaultdict

LEAD_TYPE = "Order"

def ocel_parts(ocel):
    ev = {r.event_id: r.activity for r in ocel.events.itertuples()}
    obj_type, obj_acts = {}, defaultdict(set)
    for r in ocel.objects.itertuples():
        obj_type[r.object_id] = r.object_type
        obj_acts[r.object_id].add(r.activity)
    ev_objs = defaultdict(list)
    for r in ocel.related.itertuples():
        ev_objs[r.event_id].append(r.object_id)
    return ev, obj_type, dict(obj_acts), ev_objs

def canonical_exec_keys(ocel):
    """rename-invariant, cross-execution comparable key per lead Order"""
    ev, obj_type, obj_acts, ev_objs = ocel_parts(ocel)
    osig = {o: (obj_type[o], tuple(sorted(obj_acts[o]))) for o in obj_type}
    esig = {e: (ev[e], tuple(sorted(osig[o] for o in ev_objs[e]))) for e in ev}
    keys = defaultdict(list)
    for e, parts in esig.items():
        for o in ev_objs[e]:
            if obj_type.get(o) == LEAD_TYPE:
                keys[o].append(parts)
    return {lead: tuple(sorted(Counter(v).items())) for lead, v in keys.items()}

def semantic_family(ocel, lead, obj_type=None):
    """facet extraction from E2O + ocel.qualifiers (externality, scope, motifs)"""
    ev, obj_type, obj_acts, ev_objs = ocel_parts(ocel)
    q = ocel.qualifiers
    foreign = lambda e: [o for o in ev_objs[e]
                         if obj_type.get(o) == LEAD_TYPE and o != lead]
    iso = {ev[e] for e in ev if foreign(e)}
    motifs = {r.qualifier for r in q.itertuples()
              if r.source_id == lead or r.target_id == lead}
    billing = "cross_order" if any(foreign(e) for e in ev if ev[e] == "Issue") else "order"
    settle  = "shared_unallocated" if any(foreign(e) for e in ev if ev[e]=="Record") else "order"
    return (tuple(sorted(iso)), billing, settle, tuple(sorted(motifs)))

def cluster_orders(ocels):
    """ocels: {order_id: Ocel}  ->  family labels + structural keys"""
    out = {}
    for lead, ocel in ocels.items():
        try:
            ocel, event_clusters = pm4py.cluster_equivalent_ocel(ocel)   # event level
        except Exception as exc:                                        # API drift
            event_clusters = []
        key = canonical_exec_keys(ocel).get(lead)
        fam = semantic_family(ocel, lead)
        out[lead] = {"structural": key, "family": fam,
                     "pm4py_event_clusters": [len(c) for c in event_clusters]}
    families = defaultdict(list)
    for lead, d in out.items():
        families[d["family"]].append(lead)
    return out, dict(families)
```

Note the deliberate ordering: PM4Py's clustering supplies the *structure*, the custom step supplies the *semantics* (externality, scope, motifs), and the aggregation step supplies the *unit of analysis* (the lead Order).

## 7. Robustness analysis

**Ignore all O2O qualifiers.** R2 is untouched (it is E2O-only). R3's partition is unchanged, but the motif vocabulary degrades: X7 keeps `line_removal` only through the E2O fallback (shipped  packed) and loses `substitution`; X8 keeps the activity-derived `return`/`inspection` but loses `repack`/`package_replacement`; X4 loses the instalment marker — which is a variant, so F2 is unaffected. The partition is stable, the *labels* are not.

**Ignore external objects.** This is the pivotal perturbation. R2 collapses {X5} and {X6} into the baseline cluster, giving {X1,X2,X5,X6} · {X3} · {X4} · {X7} · {X8}; R3 collapses them further into F1, giving {X1,X2,X5,X6} · {X3,X4} · {X7} · {X8}. R1 is unchanged (it never saw objects). Conclusion: externality handling is the single most consequential modelling decision in this study.

**Collapse repeated same-label events (bag instead of multiset).** R1 degenerates: all of X1–X7 share the bag {Create, Add, Pack, Dispatch, Issue, Record}, leaving only X8 apart. R2 partially collapses: X4's two Pack events, two Dispatch events and two Payment events all carry identical signatures, so X4's key becomes X1's key and X4 merges into the baseline — but X3 does *not*, because its Dispatch carries two packages while X1's carries one (class-instance counts survive the collapse). R3 is almost fully protected: packaging, delivery and billing scope are computed from binding, not from event counts, so F1…F6 all survive.

**Treat Pack/Dispatch as a partial order.** R1, defined on the label-labelled DAG, yields the same partition here (X4's two parallel packdispatch chains differ from X3's converging packs). R2 and R3 are order-insensitive except for motif detection; the real exposure is X8, whose `repack`/`package_replacement` motifs require returnpackdispatch reachability. Under genuine concurrency those motifs become `indeterminate`, moving X8 into a separate "concurrent-motif" cluster — a case where the partition changes for principled, not accidental, reasons.

**Treat payment multiplicity as an amount attribute.** X4's two payments become one payment event carrying an amount or an instalment sequence. R2's key changes (fewer Record events) and X4 stays separate from X3 only because of the Dispatch multiplicity; R3's $\Phi$ is unaffected, and only the variant entry `instalment×2` is replaced by an amount value. F2 remains {X3, X4}. If instead instalments are stored as invoice amounts, the semantic relation loses the instalment distinction entirely — a reminder that amounts are not a substitute for structure unless the question is monetary.

**Bonus: type-blind object signatures.** Dropping object types lets X5's foreign Order share the Package footprint and X6's foreign Order share the Invoice footprint; event signatures then change shape (e.g. "two invoice-class objects on Issue") and the partition may survive for the wrong reason. Never do this: type is the cheapest defence against accidental merges.

## 8. Limitations and recommendation

**Compliance monitoring  R4 (strict facets + qualifiers), with R2 as a cross-check.** Auditors need the evidence preserved: cross-order invoices, instalment settlement, removed lines, returns. Coarsening to F2 or F1 would hide X4's instalments and X6's shared billing, which are exactly the control points. Use the fine partition here, but require qualifier-backed reasons and expect singleton clusters — the purpose is exception detection, not segmentation.

**Operational segmentation  R3 (archetype families).** Segments should track capabilities: line-level fulfilment (F2), consolidated shipping (F3), consolidated billing (F4), substitution (F5), returns (F6). R3 is stable under renaming, event reordering, batch collapsing and payment-modelling changes — exactly the perturbations that make R2 brittle — so it is the right layer for longitudinal tracking and for capacity planning.

**Root-cause analysis  motif-level equivalence, embedded in R2.** Failure analysis needs the *pattern* (line removal before dispatch, returnrepack, partial delivery), not the whole trace. Extracting the archetype motif set and clustering on motifs exposes recurring causal motifs that the R1 label families hide and that R2 over-fragments.

**Descriptive reporting  R1 for volumes, R3 for composition, never R2 alone.** Label-based counts are cheap and stable for throughput dashboards, but must be published alongside the family split, otherwise "standard order-to-cash" is inflated by X5, X6 and X7. R2's seven clusters over eight traces are analytically vacuous as reporting segments.

**Why no single notion wins.** Each relation answers a different question: R1 asks *which steps happened*, R2 asks *whether two traces are the same shape*, R3 asks *which business capability and binding scope is exercised*, R4 asks *what exactly happened*. The coarsest erases the risk signals (X5, X6, X7 all vanish into F1's label family); the finest produces near-singletons that no segment can act on, and it is unstable under nuisance variation (batch collapsing alone merges X4 into the baseline). **Recommendation:** maintain the hierarchy R1  R4 with R3 as the business-facing middle layer, publish family and variant keys side by side, and treat every change of family membership as a reviewable event — so that aggregation (reporting) and refinement (audit) are both one click away without re-deriving semantics. The remaining honest limitation is that the boundary between F2 and F2a/F2b is a judgement, not a fact; it should be recorded as an explicit modelling choice, with the variant vector retained so either reading can be reconstructed.
