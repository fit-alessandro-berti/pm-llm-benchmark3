# 5. Pilot design

## Pilot scope

Use a phased, risk-controlled pilot rather than full rollout.

Recommended pilot:

1. Start with the Technical Shared Service only.
   - Centralize technical specialist review for East first.
   - Keep Legal/Risk shared queue largely unchanged during the initial pilot because Legal/Risk are already near capacity.
   - Do not remove local supervisor accountability immediately; introduce shared approval only for a limited set of medium/high-value East cases.

2. Preserve local informal triage.
   - Keep a local technical liaison or “local expertise” role in East during the pilot.
   - The liaison can provide early informal advice and prevent unnecessary central referrals.

3. Limit routing changes.
   - Route high-complexity East cases to the Technical Shared Service.
   - Keep simple eligibility and intake local.
   - Use explicit priority and regional accommodation flags.

## Comparison group

Use a stepped-wedge or matched-control design.

Preferred option:

- East receives the pilot.
- North and South remain in the current model as comparison teams.
- Within East, if operationally feasible, randomly assign a subset of medium-complexity cases to remain local to create an internal control.

Alternative if randomization is not possible:

- Match East pilot cases to similar pre-change East cases and concurrent North/South cases using:
  - `case_complexity`
  - `required_specialty`
  - `customer_segment`
  - `priority`
  - `location`
  - case value or product type

| Phase | Duration | Purpose |
|---|---:|---|
| Baseline measurement | 8–12 weeks before change | Establish stable handover, waiting, rework, SLA, and fairness baselines. |
| Pilot stabilization | 2–4 weeks after go-live | Exclude unstable transition period from formal evaluation. |
| Pilot evaluation | 8–12 weeks after stabilization | Compare pilot against controls and baseline. |
| Extension decision | 2–4 weeks | Decide whether to expand, modify, pause, or roll back. |

Total recommended pilot duration: approximately 4–6 months, including baseline and evaluation.

## Segmentation

All metrics should be segmented by:

- `team`: North, South, East
- `case_complexity`: low, medium, high
- `required_specialty`: technical, legal, risk, security, none
- `customer_segment`: for example retail, SME, enterprise, vulnerable, public sector
- `priority`
- `location` or language/region attributes
- `local_expertise_flag`
- presence or absence of rework
- supervisor/approval path: local vs shared approval

## Guardrail metrics

| Guardrail | Metric | Trigger for concern |
|---|---|---|
| Central queue delay | Median and p90 wait after handover to Technical Shared Service | Median >5h or p90 >18h for two consecutive weeks. |
| High-complexity tail | p90 cycle time for high-complexity cases | p90 increases >15–20% versus baseline/control. |
| Rework after specialist advice | Rework rate within X events after TSS return | Increases >2–3 percentage points versus baseline. |
| SLA protection | SLA miss rate by team and segment | Increases >1–2 percentage points overall or >3 points in any vulnerable segment. |
| Fairness gap | Difference in p90 cycle time between segments | Gap widens materially versus baseline. |
| Role clarity | Reassignment_count, distinct resources per case, vague handover_reason | Sustained increase or staff survey score below threshold. |
| Local expertise retention | Share of cases with local expertise involvement | Falls below agreed minimum for complex/regional cases. |
| Legal/Risk saturation | Legal/Risk median wait and queue WIP | Median wait >10.5h or p90 worsens materially. |
| Customer experience | Local customer satisfaction or complaint rate | Decline in pilot team or affected segments. |

## Staff feedback collection

Collect qualitative and quantitative feedback weekly or biweekly:

- Case ownership clarity survey.
- Ease of getting specialist advice.
- Perceived fairness across teams and customer segments.
- Quality of central specialist advice.
- Whether local staff feel they are losing technical skill.
- Whether regional/language conventions are being preserved.
- Notes on missing case context in central queue.
- Interviews with local caseworkers, central specialists, supervisors, and Quality Check staff.

## Rollback or adjustment triggers

Immediate pause or rollback if:

- Technical Shared Service p90 wait exceeds 36 hours for two consecutive weeks.
- High-complexity p90 cycle time worsens by more than 25%.
- SLA miss rate rises by more than 3 percentage points in any major team or segment.
- Rework after central specialist advice rises by more than 3–4 percentage points.
- Legal/Risk queue becomes saturated and urgent cases are delayed.
- Staff report severe loss of ownership or customer harm.

Adjust before rollback if:

- Waits rise but can be addressed by capacity, routing rules, or local liaison support.
- Rework rises only in a specific specialty or segment.
- Shared approval ambiguity can be fixed with named accountable approver.
- East improves but North/South would need different capacity assumptions.

# 6. Recommendation

Recommendation: **modify and pilot first; do not fully roll out immediately.**

The restructuring has plausible benefits:

- East may benefit because E_Tech is already overloaded.
- Centralization may improve standardization of specialist decisions.
- Shared queues may reduce dependence on individual local specialists.
- Routing rules may reduce misrouting and cross-team ad hoc transfers.

However, the risks are substantial:

- Legal/Risk specialists are already near capacity.
- Central technical review may become a hidden bottleneck.
- North/South may lose valuable local expertise.
- Shared approval may reduce accountability.
- Average cycle time may improve while high-complexity, regional, or vulnerable-segment cases worsen.
- Learning effects may reduce long-term resilience.

The proposal should be modified before piloting:

1. Do not assume that higher specialist utilization automatically means better performance.
   - Utilization must be evaluated together with waiting time, rework, SLA misses, and tail latency.

2. Keep a local technical liaison or local expertise role during the pilot.
   - This preserves informal triage and regional knowledge.

3. Add capacity or demand controls before expanding Legal/Risk centralization.
   - Legal/Risk are already near saturation.

4. Define explicit ownership for shared approvals.
   - Each case should have a named local owner and a named shared-service approver or escalation path.

5. Monitor fairness explicitly.
   - Do not judge success only by overall median cycle time.

Management should not infer from early averages that the change is successful if:

- Median cycle time improves but p90/p99 worsens.
- Simple cases become faster while high-complexity cases wait longer.
- Specialist utilization rises but queue waiting also rises.
- East improves but North/South complex or regional cases deteriorate.
- Handover counts fall but waiting time replaces visible handovers.
- Rework remains stable only because quality issues are discovered later.
- Staff report loss of ownership even if timestamps look acceptable.

Proceed to a controlled pilot only with guardrails, segmented measurement, and explicit rollback thresholds. Full rollout should require evidence that the pilot improves not only average cycle time but also tail performance, rework, fairness, role clarity, and resilience.

case_start = (
    df.groupby("case:concept:name")["time:timestamp"]
    .min()
    .rename("case_start")
)

df = df.merge(case_start, on="case:concept:name", how="left")

df["period"] = df["case_start"].apply(
    lambda ts: "pre" if ts < CHANGE_DATE else "post"
)

# ------------------------------------------------------------
# 3. Derive handover transitions and waiting after handover
# ------------------------------------------------------------

df = df.sort_values(["case:concept:name", "time:timestamp"])

gb = df.groupby("case:concept:name")

df["prev_activity"] = gb["concept:name"].shift(1)
df["prev_resource"] = gb["org:resource"].shift(1)
df["prev_time"] = gb["time:timestamp"].shift(1)

df["handover"] = (
    df["prev_resource"].notna()
    & (df["prev_resource"] != df["org:resource"])
)

df["wait_after_handover_h"] = (
    (df["time:timestamp"] - df["prev_time"])
    .dt.total_seconds() / 3600
)

# Optional: map resources to organizational groups
def resource_group(resource):
    if pd.isna(resource):
        return "unknown"

    resource = str(resource)

    if resource.startswith(("Bot_Intake",)):
        return "Bot_Intake"

    if resource.startswith(("N_Intake", "S_Intake", "E_Intake")):
        return "local intake"

    if resource.startswith(("N_Case", "S_Case", "E_Case")):
        return "local caseworker"

    if resource in {"N_Tech", "S_Tech", "E_Tech"}:
        return "embedded tech specialist"

    if resource == "Technical Shared Service":
        return "Technical Shared Service"

    if resource in {"Specialist_Legal", "Legal Review"}:
        return "Legal shared queue"

    if resource in {"Specialist_Risk", "Risk Review"}:
        return "Risk shared queue"

    if resource in {"Specialist Review", "Security Review"}:
        return "Specialist Review shared queue"

    if resource.startswith(("N_Supervisor", "S_Supervisor", "E_Supervisor")):
        return "local supervisor"

    if resource == "Shared Approval Queue":
        return "shared approval queue"

    return resource

df["resource_group"] = df["org:resource"].map(resource_group)

# Need to recompute prev_resource_group after mapping
df["prev_resource_group"] = gb["resource_group"].shift(1)

# Example: convert handover network to edge table
def network_to_edge_table(network, metric_name):
    rows = []

    for key, value in network.items():
        # PM4Py network outputs may vary by version.
        # Common shape is {(source, target): weight}
        if isinstance(key, tuple) and len(key) == 2:
            source, target = key
            rows.append(
                {
                    "source": source,
                    "target": target,
                    metric_name: value,
                }
            )

    return pd.DataFrame(rows)
