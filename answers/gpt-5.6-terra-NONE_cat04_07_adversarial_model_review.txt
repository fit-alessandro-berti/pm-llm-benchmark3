# 1. Review Scope and Assumptions

This review distinguishes four use cases that require different error tolerances:

1. **Exploration and descriptive discovery**  
   A model may tolerate noisy, incomplete, or unusual traces to help analysts find patterns. High fitness and broad coverage can be useful, but the model must be labeled explicitly as exploratory and must not be used to approve or reject cases.

2. **Conformance enforcement and compliance monitoring**  
   The model must reliably prohibit known violations: missing mandatory checks, approval before required checks, invalid rework, and duplicate checks without correction. Here, false acceptance is often more serious than false rejection. Precision must be assessed against curated negative behavior, not only positive event-log traces.

3. **Simulation and operational planning**  
   The model should represent legitimate routing alternatives and attribute-dependent decisions, including external sourcing and correction scope. Overly enumerated models are brittle; overly permissive models create implausible simulations.

4. **Stakeholder communication and process ownership**  
   The model must expose policy decisions clearly: what is mandatory, what is optional, which attributes determine routing, and what correction permits. A hidden or inferred rule should not be treated as an auditable business rule.

The fitness/precision trade-off therefore depends on use:

- For **exploration**, lower precision may be tolerable if the model is clearly marked as permissive and supported by trace-level diagnostics.
- For **enforcement**, low precision is unacceptable when it means accepting forbidden behavior such as B3, B4, or B8.
- For **simulation**, generalization matters, but only for policy-plausible combinations; unconstrained optionality is not legitimate generalization.
- For **communication**, compactness and semantic transparency matter more than maximizing any single metric.

Neither original model is suitable as the sole policy model. Model S is useful only as a deliberately permissive exploratory baseline. Model C is a historical-variant recognizer rather than a maintainable policy representation.

# 3. Adversarial Review of Model S

## Strongest case for Model S

Model S has legitimate strengths as an exploratory artifact:

- It preserves the broad start/end framing: `Register Dossier` first and `Release Order` last.
- It represents the four reviews as potentially concurrent or reorderable through `+(...)`, which can be useful for diagnosing observed variation and missing events.
- Its high training and holdout fitness, high token-based generalization, high structural simplicity, low runtime, and high informal comprehension make it attractive as a first-pass descriptive model.
- Its permissiveness may partially protect against incomplete logs, especially if Supplier Review events are missing in some external cases.
- It avoids Model C’s variant explosion and duplicate-label burden.

These benefits are real for exploration. They do not make it a compliance or operational-routing model.

## Strongest case against Model S

Model S accidentally changes mandatory business rules into optional behavior. The parallel block is composed of XOR-like optional leaves `X(activity, tau)`, so every review can be skipped. It also fails to impose required precedence between mandatory checks, Expedite Review, approval, and Supplier Review. The resulting model accepts traces that stakeholders explicitly identify as forbidden.

The central flaw is not merely “noise tolerance.” A model can tolerate missing events through explicit uncertainty handling, conformance classifications, or alternate data-quality paths. Model S instead encodes substantive policy violations as normal model behavior.

## Concrete undesirable or policy-ambiguous admitted behaviors

Assuming standard process-tree semantics:

1. **Missing both mandatory checks**
   ```text
   Register Dossier, Manager Approval, Release Order
   ```
   This is B3 and is forbidden. Model S accepts it because all reviews are optional.

2. **Expedite before mandatory checks**
   ```text
   Register Dossier, Expedite Review, Credit Check, Technical Review,
   Manager Approval, Release Order
   ```
   This is B4 and is forbidden. Model S accepts it because the parallel block imposes no ordering among selected activities.

3. **Approval without any review**
   ```text
   Register Dossier, Auto Approval, Release Order
   ```
   Forbidden for the same reason as B3.

4. **Only one mandatory check**
   ```text
   Register Dossier, Credit Check, Manager Approval, Release Order
   ```
   Forbidden because Technical Review is mandatory before approval.

5. **Expedite without mandatory checks**
   ```text
   Register Dossier, Expedite Review, Auto Approval, Release Order
   ```
   Forbidden: Expedite Review must follow both mandatory checks.

6. **Supplier Review before mandatory checks**
   ```text
   Register Dossier, Supplier Review, Credit Check, Technical Review,
   Manager Approval, Release Order
   ```
   Policy-ambiguous at best. P3 requires Supplier Review for external orders, but the stated policy does not explicitly permit it before the mandatory checks. Model S makes it freely reorderable.

7. **Supplier Review absent for an external order**
   ```text
   Register Dossier, Credit Check, Technical Review,
   Manager Approval, Release Order
   ```
   This trace is valid for internal cases, but invalid for external cases. Model S cannot distinguish them because it has no external/internal condition.

8. **No rework activity at all**
   ```text
   Register Dossier, Credit Check, Technical Review,
   Manager Approval, Release Order
   ```
   This is valid for an internal case, but the issue is that Model S has no `Correct Dossier` activity and no rework semantics. It cannot represent legitimate correction-driven repetitions.

9. **Repeated check without correction**
   ```text
   Register Dossier, Credit Check, Technical Review, Credit Check,
   Manager Approval, Release Order
   ```
   Model S does not naturally support arbitrary duplicate activity occurrences because the leaves are not loops. However, alignments may still score such traces with low-cost deviations depending on costs. It therefore neither explicitly detects nor transparently explains the P7 anomaly.

10. **Correction trace cannot be represented**
   ```text
   Register Dossier, Credit Check, Technical Review, Correct Dossier,
   Technical Review, Manager Approval, Release Order
   ```
   B6 cannot be accepted as modeled behavior because `Correct Dossier` is absent. Any apparent conformance would arise only through alignment deviations, not through an explicit correction policy.

## Intentional noise tolerance versus accidental semantic flaws

| Issue | Intentional noise tolerance? | Accidental semantic flaw? |
|---|---:|---:|
| Allowing rare but plausible combinations of known reviews | Potentially | Not necessarily |
| Tolerating missing Supplier Review events in imperfect logs | Potentially, if labeled as data-quality uncertainty | Not if it silently turns external review into optional policy behavior |
| Skipping Credit Check | No | Yes |
| Skipping Technical Review | No | Yes |
| Expedite before mandatory checks | No | Yes |
| Approval before mandatory checks | No | Yes |
| Missing correction/recheck behavior | No | Yes; the model lacks a required business concept |
| No external/internal routing distinction | Not inherently | Yes for enforcement, because P3 is attribute-conditioned |

# 4. Adversarial Review of Model C

## Strongest case for Model C

Model C makes a serious attempt to encode observed process variants explicitly:

- It preserves `Register Dossier` first and `Release Order` last.
- It requires both Credit Check and Technical Review in every listed branch.
- It includes both observed mandatory-check orders in several branches.
- It includes Supplier Review in some variants.
- It includes an Expedite Review variant.
- It includes a correction-related variant.
- It includes Auto Approval in one branch and Manager Approval in others.
- Its high training precision is consistent with tightly bounded observed behavior.

For a narrowly defined historical replay task—such as identifying whether a trace exactly resembles one of a small set of known frequent variants—Model C can be useful. It may also be useful as a candidate-variant catalogue for discussion.

## Strongest case against Model C

Model C is branch enumeration masquerading as policy. It expresses a finite sample of historical traces, not a stable set of business rules. It is brittle because every legitimate combination must be enumerated in advance, and it duplicates the same business activities across many branches.

### Branch enumeration

The model enumerates a handful of trace sequences. This creates combinatorial fragility. For example, it includes:

```text
Credit Check, Technical Review, Supplier Review, Expedite Review,
Manager Approval
```

but not:

```text
Technical Review, Credit Check, Supplier Review, Expedite Review,
Auto Approval
```

even though B5 is plausible under stated policy.

The absence is not a policy decision. It is an artifact of historical variant selection.

### Duplicate labels

The same label, such as `Credit Check`, appears as a separate leaf transition in many branches. The model therefore has multiple structurally distinct occurrences representing one business responsibility. This creates problems for:

- ownership assignment;
- change impact analysis;
- performance analysis by activity;
- conformance diagnostics;
- activity-level controls;
- traceability from a rule to a unique model element.

The reported duplicate-label count of 33 is plausible given the branching, but its definition must be documented before it is used as a formal metric.

### Unseen combinations

F4 is directly predicted by Model C’s construction: cases combining Supplier Review, Auto Approval, and alternate check order are absent from training and rejected. Yet these may be legitimate combinations of independently allowed policy features.

A policy model should separate independent choices:

- check order;
- external sourcing;
- expedite need;
- approval mechanism;
- correction scope.

Model C instead binds these choices into monolithic branches.

### Correction handling

Model C includes only:

```text
Credit Check, Technical Review, Correct Dossier,
Credit Check, Technical Review
```

It cannot express:

- correction affecting Credit Check only;
- correction affecting Technical Review only;
- correction affecting both checks after either initial check order;
- correction occurring in an external or expedited case;
- multiple corrections, despite P6 allowing repetition.

Thus it does not transparently represent the actual decision: which checks were affected.

### Holdout degradation

The drop from training fitness 0.973 to holdout fitness 0.744 is material. It is consistent with overfitting to observed variants, split-sensitive variant coverage, or both. The score does not prove holdout cases are compliant, but F4 indicates that at least some holdout failures are plausible legitimate combinations rather than obvious violations.

### Maintainability

Every new approved combination requires adding another branch, which may require duplicating several activity labels. The number of variants grows roughly as combinations of:

- two check orders;
- Supplier Review present/absent;
- Expedite present/absent;
- two approvals;
- several correction scopes;
- multiple correction cycles.

This is not maintainable and invites omission errors.

### Is high precision memorization?

Possibly. Alignment precision of 0.941 on the training log is impressive only if the model is also evaluated against valid-but-unobserved behavior and invalid behavior. Here, the model directly enumerates frequent variants, so high training precision may largely reflect memorization of those variants. It does not demonstrate that the model distinguishes policy-valid from merely observed behavior.

# 5. Behavior-Probe Matrix

Assumptions: `->` is sequence, `X` is exclusive choice, `+` is parallel composition, and `tau` is a silent activity. Under standard process-tree semantics, activities in `+` may interleave in arbitrary order, while each chosen leaf occurs once. No loops are present in either supplied expression.

| Probe | Model S accepts? | Model C accepts? | Policy assessment | Consequence for review |
|---|---|---|---|---|
| B1: Register, Credit, Technical, Manager, Release | Yes | Yes | Valid | Both cover the basic internal/manual path. |
| B2: Register, Technical, Credit, Auto, Release | Yes | No | Valid | C wrongly rejects a stated valid combination because Auto Approval is only enumerated after Credit then Technical. |
| B3: Register, Manager, Release | Yes | No | Forbidden | S has a critical false acceptance. C correctly rejects this trace. |
| B4: Register, Expedite, Credit, Technical, Manager, Release | Yes | No | Forbidden | S has a critical ordering failure. C correctly rejects this trace. |
| B5: Register, Technical, Credit, Supplier, Expedite, Auto, Release | Yes | No | Plausible valid external/urgent case | S happens to cover it, but without enforcing why; C rejects plausible valid behavior due to enumeration. |
| B6: Register, Credit, Technical, Correct, Technical, Manager, Release | No as model behavior; only alignable with deviations | No | Policy-dependent: valid only if correction affected Technical Review alone | Neither model transparently represents single-check rework. S lacks Correct Dossier; C only allows both checks after correction. |
| B7: Register, Credit, Technical, Supplier, Manager, Release | Yes | Yes | Valid external case | Both accept, but S cannot enforce Supplier Review for external cases and C cannot generalize all valid external combinations. |
| B8: Register, Credit, Technical, Credit, Manager, Release | No as exact model behavior; may align with deviations | No | Suspicious/forbidden without correction | Both reject exact trace language, but neither provides a clear P7 anomaly explanation through explicit rework semantics. |

For B6 and B8, “accepts” refers to membership in the model language, not merely whether an alignment algorithm can produce a finite-cost alignment by inserting, deleting, or relabeling moves. Alignment conformance can be nonzero even when a trace is not accepted by the model; costs and move classifications must be inspected.

# 6. Likely Metric Pathologies

The following are ranked by likely decision impact.

| Rank | Pathology | Why it matters |
|---:|---|---|
| 1 | Fitness rewarded by optionalizing mandatory behavior | Model S’s high fitness is directly inflated by allowing missing mandatory checks and invalid ordering. This can create false compliance confidence. |
| 2 | Positive-log-only precision | C’s high precision may reflect closeness to observed traces rather than discrimination against known invalid behavior. Without negatives, precision cannot establish enforcement quality. |
| 3 | Missing-event bias | Missing Supplier Review events can make a correct external-control model look less fit, while a permissive model looks artificially robust. Missing events should be modeled as data-quality uncertainty, not policy optionality. |
| 4 | Train/holdout leakage or split sensitivity | Without case IDs, dates, seeds, preprocessing, and split code, the holdout comparison is not reproducible. A random split may distribute near-identical variants across train and test. |
| 5 | Alignment-cost sensitivity | Alignment fitness and diagnostics depend on costs for synchronous moves, log moves, model moves, and silent transitions. Different settings could materially change rankings. |
| 6 | Generalization rewarded by excessive permissiveness | Token-based generalization can reward S for enabling broad behavior, including prohibited behavior. High “generalization” is not equivalent to valid flexibility. |
| 7 | Duplicated-label effects | In C, repeated labels across branches complicate transition identity and may affect diagnostics, precision, performance attribution, and maintenance estimates. |
| 8 | Silent-transition effects | Model S explicitly uses `tau` alternatives. Silent transitions can permit routing that is not visible in logs and can affect precision, alignment paths, and reachability. |
| 9 | Runtime confounding by model size | C’s runtime likely reflects its larger branch-expanded state space, but hardware, trace complexity, cache effects, and timeout behavior are missing. |
| 10 | Stakeholder-score methodology | Informal scores are vulnerable to presentation bias and may reward visual simplicity while hiding semantic danger. |
| 11 | Metric definition ambiguity | “Duplicate-label count” is undocumented; “generalization” and “simplicity” variants must be versioned and parameterized. |

Additional details:

- **Train/holdout leakage or split sensitivity:** Cases from the same customer, supplier, batch, or correction episode may appear in both train and holdout. Temporal drift matters: if Auto Approval or external sourcing rules changed over time, random splitting masks it.
- **Missing-event bias:** Supplier Review is especially problematic because its requiredness depends on an unlogged attribute. The observed absence of Supplier Review is not proof that it did not occur.
- **Duplicated-label effects:** C can map an observed `Credit Check` to multiple branch-specific transitions. This makes an alignment less interpretable: the same business event may be “explained” by structurally different copies.
- **Silent-transition effects:** S uses silent alternatives for every review. These are not neutral; each silent branch encodes the possibility of skipping a review.
- **Alignment-cost sensitivity:** If missing model moves are cheap, S’s missing mandatory checks are almost unpenalized; if log moves are cheap, duplicate events may appear less severe than policy intends.
- **Stakeholder comprehension:** A valid protocol would use representative roles, scenario questions, independent scoring, success/error measures, and documented materials—not only a preference rating.
- **Runtime confounding:** Median runtime ignores p95/p99 latency. A model that is fast on ordinary cases but times out on correction-heavy cases may be unsuitable despite a good median.

# 7. Third Alternative

## Strategy

Use a **block-structured procedural backbone plus explicit data-conditioned policy checks**.

The procedural backbone expresses universal sequencing and bounded routing:

- Register first.
- Credit Check and Technical Review are both mandatory, in either order.
- Supplier Review is represented as an optional observed activity in the control-flow backbone because the external/internal attribute is absent.
- Expedite Review is optional but can occur only after both mandatory checks.
- Exactly one approval occurs.
- Release Order is last.
- Correction cycles are represented explicitly, but the procedural model alone does not decide which rechecks are required.

External sourcing and correction scope are enforced by post-hoc, attribute-aware policy checks. This avoids both failures of the original models:

- It does **not** make Credit Check or Technical Review optional.
- It does **not** enumerate every combination of order, supplier, expedite, approval, and rework.

## 1. Compact formal description

Let:

- \(R\) = Register Dossier
- \(C\) = Credit Check
- \(T\) = Technical Review
- \(S\) = Supplier Review
- \(E\) = Expedite Review
- \(D\) = Correct Dossier
- \(M\) = Manager Approval
- \(A\) = Auto Approval
- \(L\) = Release Order

Main backbone language:

```text
R ;
(C || T) ;
[ S ] ;
[ E ] ;
[ D ; RecheckCycle ]* ;
(M XOR A) ;
L
```

with semantic constraints:

1. `C` and `T` each occur at least once before approval.
2. `E`, if present, occurs after the first completion of both `C` and `T`, and before approval.
3. `S`, if present, occurs before approval; its requiredness is determined by `external_internal`.
4. Exactly one of `M` and `A` occurs.
5. Every repeated `C` or `T` must be causally associated with a preceding `D`.
6. A `D` has an `affected_checks` value in `{Credit, Technical, Both}`:
   - Credit: require one subsequent `C` before approval;
   - Technical: require one subsequent `T` before approval;
   - Both: require subsequent `C` and `T`, in either order, before approval.
7. If `affected_checks` is absent, classify the case as **indeterminate / data-quality exception**, not automatically compliant.
8. If `external_internal = external`, require `S`; if missing, classify as **policy violation or telemetry-missing**, depending on evidence from the source system.

The recheck semantics are intentionally enforced outside the simple backbone because the required branch depends on data not present in the discovery log.

## 2. Self-contained PM4Py code assigning the main model to `model_third`

The following code constructs a compact POWL-style backbone. It intentionally does not encode Supplier Review requiredness or correction scope as unconditional control-flow choices; those are checked by the policy function below.

```python
import pm4py

from pm4py.objects.powl.obj import (
    Transition,
    SilentTransition,
    OperatorPOWL,
    StrictPartialOrder,
)

# Activity nodes
register = Transition("Register Dossier")
credit = Transition("Credit Check")
technical = Transition("Technical Review")
supplier = Transition("Supplier Review")
expedite = Transition("Expedite Review")
correct = Transition("Correct Dossier")
manager = Transition("Manager Approval")
auto = Transition("Auto Approval")
release = Transition("Release Order")

# Standard POWL operators. Exact enum names can vary by PM4Py release;
# inspect your installed version if needed.
from pm4py.objects.powl.obj import Operator

# Mandatory checks may complete in either order.
mandatory_checks = OperatorPOWL(
    Operator.PARALLEL,
    [credit, technical]
)

# Optional observed steps. Optionality here means "may occur in a case",
# not "requiredness is waived when the governing attribute says required".
optional_supplier = OperatorPOWL(
    Operator.XOR,
    [supplier, SilentTransition()]
)

optional_expedite = OperatorPOWL(
    Operator.XOR,
    [expedite, SilentTransition()]
)

# A correction may repeat. The exact recheck scope is validated externally.
# The loop body permits a correction followed by one-or-more observed rechecks.
# Post-hoc checks prohibit unsupported repetitions and enforce affected_checks.
recheck_choice = OperatorPOWL(
    Operator.XOR,
    [
        credit,
        technical,
        OperatorPOWL(Operator.PARALLEL, [credit, technical]),
    ]
)

correction_cycle = OperatorPOWL(
    Operator.SEQUENCE,
    [correct, recheck_choice]
)

optional_corrections = OperatorPOWL(
    Operator.LOOP,
    [correction_cycle, SilentTransition()]
)

approval = OperatorPOWL(
    Operator.XOR,
    [manager, auto]
)

# Strict partial order supplies the universal precedence backbone.
model_third = StrictPartialOrder(
    [
        register,
        mandatory_checks,
        optional_supplier,
        optional_expedite,
        optional_corrections,
        approval,
        release,
    ]
)

model_third.order.add_edge(register, mandatory_checks)
model_third.order.add_edge(mandatory_checks, optional_supplier)
model_third.order.add_edge(mandatory_checks, optional_expedite)

# Supplier and Expedite may occur in either order after mandatory checks.
model_third.order.add_edge(optional_supplier, approval)
model_third.order.add_edge(optional_expedite, approval)

# Corrections/rechecks occur after initial checks and before approval.
model_third.order.add_edge(mandatory_checks, optional_corrections)
model_third.order.add_edge(optional_corrections, approval)

model_third.order.add_edge(approval, release)

# Conversion for Petri-net-based diagnostics, if supported in the installed PM4Py version.
net, im, fm = pm4py.convert_to_petri_net(model_third)
```

Implementation note: POWL APIs and operator enum names differ across PM4Py versions. The code should be version-pinned and tested in the target environment. If the installed release does not support direct POWL-to-Petri conversion for this object structure, retain the POWL as the governance artifact and implement the equivalent Petri net or process tree for metrics, with an equivalence test suite.

## 3. Declarative dictionaries and external checks

```python
POLICY = {
    "register_activity": "Register Dossier",
    "release_activity": "Release Order",
    "mandatory_checks": {"Credit Check", "Technical Review"},
    "supplier_activity": "Supplier Review",
    "expedite_activity": "Expedite Review",
    "correction_activity": "Correct Dossier",
    "approval_activities": {"Manager Approval", "Auto Approval"},
    "external_attribute": "external_internal",
    "affected_checks_attribute": "affected_checks",
}

VALID_AFFECTED_CHECKS = {
    "credit": {"Credit Check"},
    "technical": {"Technical Review"},
    "both": {"Credit Check", "Technical Review"},
}
```

Illustrative trace-level policy checker:

```python
def policy_check_case(events, case_attributes):
    """
    events: ordered list of activity names
    case_attributes: dict containing, where available:
        external_internal in {"external", "internal"}
        affected_checks: either a scalar for one correction or a list aligned
                         to Correct Dossier occurrences:
                         {"credit", "technical", "both"}
    Returns a list of findings. An empty list means no detected violation,
    not proof that missing attributes were valid.
    """
    findings = []

    R = POLICY["register_activity"]
    L = POLICY["release_activity"]
    C = "Credit Check"
    T = "Technical Review"
    S = POLICY["supplier_activity"]
    E = POLICY["expedite_activity"]
    D = POLICY["correction_activity"]
    approvals = POLICY["approval_activities"]

    if not events:
        return ["empty trace"]

    if events[0] != R:
        findings.append("P1 violation: Register Dossier is not first")

    if events[-1] != L:
        findings.append("P1 violation: Release Order is not last")

    approval_positions = [i for i, x in enumerate(events) if x in approvals]
    if len(approval_positions) != 1:
        findings.append("P5 violation: exactly one approval is required")
        return findings

    approval_pos = approval_positions[0]

    # No release before approval and no relevant execution after release.
    if approval_pos > len(events) - 2:
        findings.append("approval must occur before Release Order")

    prefix = events[:approval_pos]

    # Initial mandatory checks must occur before approval.
    if C not in prefix or T not in prefix:
        findings.append("P2 violation: both mandatory checks required before approval")

    # Expedite requires initial mandatory checks before it.
    for i, x in enumerate(events):
        if x == E:
            if i >= approval_pos:
                findings.append("P4 violation: Expedite Review after approval")
            prior = set(events[:i])
            if C not in prior or T not in prior:
                findings.append("P4 violation: Expedite Review before both mandatory checks")

    # Supplier requirement conditioned on source attribute.
    source_type = case_attributes.get(POLICY["external_attribute"])
    if source_type == "external" and S not in prefix:
        findings.append("P3 violation: external order missing Supplier Review")
    elif source_type is None:
        findings.append("P3 indeterminate: external/internal attribute missing")

    # Repeated mandatory checks must follow a correction.
    seen_initial = {C: 0, T: 0}
    correction_indices = [i for i, x in enumerate(events) if x == D]

    for i, x in enumerate(events):
        if x not in {C, T}:
            continue
        seen_initial[x] += 1
        if seen_initial[x] > 1:
            if not any(d < i for d in correction_indices):
                findings.append(
                    f"P7 violation: repeated {x} without preceding Correct Dossier"
                )

    # Correction scope validation: assumes affected_checks list is aligned
    # to Correct Dossier occurrences. If unavailable, do not silently approve.
    scopes = case_attributes.get(POLICY["affected_checks_attribute"])
    if correction_indices:
        if scopes is None:
            findings.append(
                "P6 indeterminate: correction exists but affected_checks is missing"
            )
        else:
            if isinstance(scopes, str):
                scopes = [scopes]

            if len(scopes) != len(correction_indices):
                findings.append(
                    "P6 indeterminate: affected_checks count does not match corrections"
                )
            else:
                for j, d_pos in enumerate(correction_indices):
                    scope = scopes[j]
                    required = VALID_AFFECTED_CHECKS.get(scope)
                    if required is None:
                        findings.append(f"P6 invalid affected_checks value: {scope}")
                        continue

                    next_boundary = (
                        correction_indices[j + 1]
                        if j + 1 < len(correction_indices)
                        else approval_pos
                    )
                    segment = set(events[d_pos + 1:next_boundary])

                    if not required.issubset(segment):
                        findings.append(
                            f"P6 violation: correction {j + 1} requires recheck(s) "
                            f"{sorted(required)} before approval"
                        )

                    # A strict policy can additionally flag unrequired rechecks.
                    unexpected = (segment & {C, T}) - required
                    if unexpected:
                        findings.append(
                            f"P6 review: correction {j + 1} contains unrequired "
                            f"recheck(s) {sorted(unexpected)}"
                        )

    return findings
```

## 4. Explicit semantics

| Requirement | Third-alternative semantics |
|---|---|
| Mandatory checks | Credit Check and Technical Review are mandatory before approval. Their relative order is unconstrained. They are never modeled as optional. |
| Supplier Review | Appears as an optional control-flow event only because external/internal is unavailable in the discovery log. In enforcement, it is mandatory when `external_internal = external`; absent attribute produces indeterminate status, not automatic compliance. |
| Expedite Review | Optional. If it occurs, it must occur after both initial mandatory checks and before approval. It may occur before or after Supplier Review. |
| Exactly-one approval | XOR between Manager Approval and Auto Approval. Exactly one must occur before Release Order. |
| Correction/recheck behavior | Every correction has an `affected_checks` scope: Credit, Technical, or Both. Only those checks must repeat after that correction and before approval. Repeated mandatory checks without a preceding correction are violations. Missing scope is indeterminate and requires data remediation or manual review. |
| Multiple corrections | Permitted as repeated correction cycles, but each correction must have its own scope and corresponding rechecks. |
| Missing events | Treated as a data-quality or conformance issue; not silently converted into policy optionality. |

## 5. Limitations caused by missing attributes

The model cannot fully enforce P3 or P6 from the discovery log alone.

- Without **external/internal**, Supplier Review absence is ambiguous: it may mean internal order, missing telemetry, or noncompliance.
- Without **affected-check**, a correction followed by only Technical Review could be valid, invalid, or incompletely logged.
- The correct response is not to make Supplier Review and rechecks universally optional. The correct response is to:
  1. add the attributes to future event capture;
  2. reconstruct them from ERP/procurement and dossier-change systems where possible;
  3. classify historical cases with missing attributes as indeterminate;
  4. avoid using those indeterminate cases as clean evidence for discovery or enforcement calibration.

# 9. Validation Experiments

The validation program should treat the model as a governed decision artifact, not merely as a discovery output.

## 9.1 Reproducible data preparation and splits

Publish:

- source extraction query or API specification;
- preprocessing code;
- activity mapping;
- lifecycle handling;
- timestamp ordering rules;
- case identifier;
- handling of duplicate events;
- missing-event assumptions;
- excluded cases and reasons;
- PM4Py version, Python version, operating system, and dependency lockfile;
- random seeds;
- exact train/validation/holdout case IDs or stable hashed identifiers.

Use more than one split:

1. **Seeded random case split** for comparability.
2. **Temporal holdout** to detect drift.
3. **Attribute-stratified holdout** by external/internal, approval type, supplier presence, expedite presence, correction count, and source system.
4. **Group split** by customer, supplier, product family, or dossier template where leakage is plausible.

Example split skeleton:

## 9.2 Curated positive and negative suites

Build a policy-labeled suite independent of the discovery log.

### Positive suite

Include:

- B1, B2, B5 where external, B6 under each valid correction scope, B7 where external;
- both check orders;
- Supplier before/after Expedite;
- Manager and Auto approvals;
- one and multiple correction cycles;
- external and internal cases.

### Negative suite

Include:

- B3 and B4;
- missing Credit or Technical;
- Expedite before either mandatory check;
- Supplier omitted for known external cases;
- both approvals;
- no approval;
- repeated Credit or Technical without correction;
- correction with missing required recheck;
- correction followed by the wrong recheck;
- release before approval;
- events after Release Order.

The suite should distinguish:

- **forbidden**;
- **valid**;
- **indeterminate because required attributes are missing**;
- **data-quality anomaly**.

A compliance model should not receive credit for treating indeterminate cases as cleanly valid.

## 9.3 Missing-event and duplicate-event perturbation tests

Starting with known-valid traces:

- delete Supplier Review;
- delete Credit Check;
- delete Technical Review;
- delete Expedite Review;
- duplicate Credit Check with and without Correct Dossier;
- duplicate Technical Review with and without Correct Dossier;
- reorder timestamp-tied events;
- insert unrelated logging artifacts if such artifacts are realistic.

Expected results:

- Missing Supplier for an external case should become violation or indeterminate, not silently valid.
- Missing mandatory checks should be violations.
- Duplicate checks without correction should be violations.
- Missing optional Expedite should remain valid.
- Missing correction scope should become indeterminate.

## 9.4 Unseen-combination tests

Systematically test the Cartesian combinations that policy permits rather than only combinations observed in training:

- Credit/Technical order: 2;
- Supplier: absent/present where compatible with internal/external;
- Expedite: absent/present;
- approval: manager/auto;
- correction scope: none/credit/technical/both;
- correction count: 0/1/2.

Not all combinations are meaningful, but the test design should explicitly state which are valid, invalid, or attribute-dependent. This exposes Model C-style enumeration failure.

## 9.5 Alignment-cost sensitivity

Run alignments under documented alternatives:

- equal model/log move costs;
- higher cost for missing mandatory checks;
- high cost for approval/release violations;
- separate costs for optional activities;
- silent-transition costs where configurable;
- an explicitly documented default PM4Py configuration.

Report whether the ranking of models and the classification of B1–B8 change. A model whose apparent performance changes drastically under defensible costs is not stable enough for enforcement.

## 9.6 Soundness and reachability checks

For every converted Petri net:

- check soundness;
- inspect dead transitions;
- verify completion can be reached;
- verify no improper completion;
- inspect reachable markings where feasible;
- test that forbidden approval-before-check paths are unreachable;
- test that valid check-order combinations are reachable.

Example:

```python
import pm4py

net, im, fm = pm4py.convert_to_petri_net(model_third)

pm4py.check_soundness(
    net,
    im,
    fm,
    print_diagnostics=True,
)
```

Soundness is necessary but not sufficient. A sound net can still encode a bad policy.

## 9.8 Stakeholder comprehension protocol

Replace the informal score with a documented task-based study.

Participants should include:

- process owners;
- compliance officers;
- operations users;
- IT architects;
- analysts.

For each blinded model representation:

1. Ask participants to determine whether B1–B8 are accepted, forbidden, or attribute-dependent.
2. Ask them to explain why.
3. Measure correctness, completion time, confidence, and disagreement.
4. Ask change-impact questions: “How would you add Auto Approval for external expedited cases?”
5. Record whether participants identify mandatory checks and correction scope correctly.

Report sample size, role distribution, model rendering, training provided, scoring rubric, and inter-rater agreement.

## 9.9 Decision rule

Reject a candidate for compliance deployment despite good aggregate metrics if any of the following applies:

- it accepts a curated forbidden trace involving missing mandatory checks, approval before mandatory checks, or Expedite before checks;
- it cannot distinguish valid from forbidden rework under available attributes and does not classify ambiguity explicitly;
- it fails soundness or has reachable prohibited states;
- its results are not reproducible from published code, data lineage, and parameters;
- it materially degrades on attribute-stratified or temporal holdout without an explained policy or data-quality cause;
- it is too complex for named owners to maintain safely;
- its apparent precision is supported only by positive-log evaluation and has not passed the negative suite.

# 10. Governance Recommendation

## Exploration

- **Model S may be retained only as an exploratory visualization baseline.**
- It must be labeled: “Permissive discovery model; not a policy or conformance model.”
- It must not be used to determine compliance, automate routing, approve release, or infer that skipped checks are acceptable.
- Its value is in showing possible observed interleavings and highlighting potential missing-event patterns.

## Compliance and enforcement

- **Neither Model S nor Model C should be deployed as the compliance model.**
- Model S must be rejected because it accepts direct policy violations, including B3 and B4.
- Model C must be rejected because its branch enumeration is incomplete, brittle, and unable to represent policy-permitted unseen combinations such as B2 and B5. Its high training precision is insufficient evidence of policy correctness.

## Treatment of Model C

Model C may be archived as a historical-variant catalogue or used for forensic comparison against frequent past paths. It should not be maintained as the normative process model. Its branch-expanded representation should be retired from active policy governance once equivalent historical reporting is preserved.

## Conditions for third-alternative deployment

The third alternative may proceed from design to controlled pilot only when it meets all of the following:

1. **Data remediation plan:** external/internal and affected-check attributes are added to the event schema or reliably joined from authoritative systems.
2. **Policy ownership:** named business owners approve the semantics of Supplier Review and correction scopes.
3. **Negative-suite success:** it rejects all critical forbidden traces and correctly classifies attribute-dependent traces.
4. **Reachability evidence:** soundness and reachability tests demonstrate that prohibited approval paths are unreachable.
5. **Reproducibility:** code, seeds, preprocessing, metrics, costs, model version, and split case IDs are published internally.
6. **Holdout robustness:** it performs acceptably across temporal and attribute-stratified holdouts, with deviations reviewed at trace level.
7. **Operational design:** indeterminate cases caused by missing attributes have a defined manual-review workflow rather than silent auto-approval.
8. **Usability evidence:** stakeholders can correctly interpret mandatory checks, correction scope, and escalation paths in a documented comprehension study.

# 11. Dissenting View

The recommendation may be overly cautious and may understate the operational value of Model C. In a regulated environment, it can be rational to treat unobserved behavior as noncompliant until formally approved. Model C does exactly that: it provides a small, explicit set of historically frequent execution paths, has high training precision, and rejects obvious violations such as missing mandatory checks and Expedite Review before the checks. Its lower holdout fitness could be a feature rather than a defect if the holdout includes undocumented workarounds, missing Supplier Review events, or policy drift. Replacing it with a hybrid procedural-plus-declarative design may introduce a new governance burden: separate code, data attributes, policy dictionaries, and exception classifications can be harder to audit than a finite list of visible paths. The third model also depends on attributes that are currently absent, so it may defer rather than solve the immediate control problem. Meanwhile, Model S offers a transparent, high-coverage map of observed behavior and may be sufficient if enforcement remains manual.

I would change the recommendation if a curated, business-approved trace suite showed that Model C correctly accepts all valid combinations expected in production, rejects all critical negative traces, remains stable on temporal and attribute-stratified holdout, and can be maintained through a controlled variant-governance process without label ambiguity. I would also reconsider if source-system evidence showed that the missing attributes cannot be captured or reconstructed at acceptable cost.
