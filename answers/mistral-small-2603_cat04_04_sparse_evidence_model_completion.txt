# 2. Shared Assumptions

All three models share the following assumptions:

- **Event completion semantics:** Only completion timestamps are available. Activities with the same timestamp are ordered by ingestion index (S7). This means we cannot distinguish true concurrency from interleaved execution or overlapping execution with same completion timestamp.
- **Missing Supplier Confirmation events:** 5–10% of Supplier Confirmation events may be missing (S5). We model this as optional occurrence rather than mandatory, to avoid overfitting to observed variants.
- **Absent external/stocked attribute:** The attribute distinguishing external and stocked components is not available (S4). Thus, we cannot condition Supplier Confirmation on component type.
- **Optionality representation:** Optionality is modeled explicitly (e.g., via silent transitions, optional subtrees, or partial orders) rather than inferred from missing events.
- **Expedite Review:** Modeled as optional, occurring at most once, requiring both Credit Check and Engineering Review, and preceding Approve Configuration (D6, S6).
- **Dependencies:** All dependencies (e.g., Approve Configuration requires Credit Check and Engineering Review) are enforced as mandatory prerequisites, but not necessarily in a specific order unless supported by evidence.
- **Start/end constraints:** Register Order is the only start activity, and Archive Case is the only end activity (D1).
- **Silent transitions:** Used to model optionality and missing data where appropriate.

# 3. Conservative Candidate

**Inductive-bias statement:**
The conservative model prioritizes not admitting any behavior not explicitly supported by the observed variants or high-confidence rules (D1, D2). It avoids inferring concurrency, optionality, or missing data where evidence is ambiguous. It models Supplier Confirmation as mandatory only when observed, and Expedite Review as optional only when observed. It enforces strict ordering where supported by variants or high-confidence rules, and uses XOR splits to enumerate observed alternatives. This model is likely to underfit, as it will reject many plausible but unobserved behaviors.

# 4. Balanced Candidate

**Inductive-bias statement:**
The balanced model generalizes from the observed variants while explicitly managing uncertainty. It models Credit Check and Engineering Review as partially ordered (allowing concurrency or interleaving), Supplier Confirmation as optional (to account for stocked components and missing events), and Expedite Review as optional but constrained. It uses a combination of sequence, concurrency, and optional subtrees to capture the most plausible generalization. The model prioritizes medium-confidence rules (D3–D6, S2, S6) over low-confidence or disputed rules (S1).

**Decision criteria for sequence vs. concurrency vs. partial order:**
- **Credit Check and Engineering Review:** Modeled as a partial order (concurrent or interleaved) due to bidirectional DFG edges, Engineering lead’s statement (S2), and lack of evidence for strict sequence (S1 is disputed).
- **Supplier Confirmation:** Modeled as optional and can occur after either Credit Check or Engineering Review, due to medium-confidence rules (D5, S3, S4) and observed variants.
- **Expedite Review:** Modeled as optional, requiring both Credit Check and Engineering Review, and preceding Approve Configuration, due to medium-confidence rules (D6, S6).
- **Approve Configuration:** Requires both Credit Check and Engineering Review (D3), but order is not enforced.

**Formal expression:**
```
POWL(
    PartialOrder(
        Register Order  Credit Check,
        Register Order  Engineering Review,
        Credit Check  Approve Configuration,
        Engineering Review  Approve Configuration,
        Credit Check  Supplier Confirmation,
        Engineering Review  Supplier Confirmation,
        Supplier Confirmation  Approve Configuration,
        Credit Check  Expedite Review,
        Engineering Review  Expedite Review,
        Expedite Review  Approve Configuration,

    ),
    Operators:
        - Credit Check and Engineering Review are concurrent (no order enforced between them)
        - Supplier Confirmation is optional (can be skipped)
        - Expedite Review is optional (can be skipped)
)
```

from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition
from pm4py.objects.process_tree.obj import Operator

def create_model_balanced():
    # Create activities
    register = Transition("Register Order")
    credit = Transition("Credit Check")
    eng = Transition("Engineering Review")
    supplier = Transition("Supplier Confirmation")
    expedite = Transition("Expedite Review")
    approve = Transition("Approve Configuration")
    release = Transition("Release Production")
    archive = Transition("Archive Case")

    # Create partial order
    partial_order = StrictPartialOrder()
    partial_order.add_edge(register, credit)
    partial_order.add_edge(register, eng)
    partial_order.add_edge(credit, approve)
    partial_order.add_edge(eng, approve)
    partial_order.add_edge(credit, supplier)
    partial_order.add_edge(eng, supplier)
    partial_order.add_edge(supplier, approve)
    partial_order.add_edge(credit, expedite)
    partial_order.add_edge(eng, expedite)
    partial_order.add_edge(expedite, approve)
    partial_order.add_edge(approve, release)
    partial_order.add_edge(release, archive)

    # Create POWL model
    model = OperatorPOWL(partial_order=partial_order)

    # Add silent transitions for optionality
    silent_supplier = SilentTransition()
    silent_expedite = SilentTransition()

    # Supplier Confirmation is optional
    model.partial_order.add_edge(credit, silent_supplier)
    model.partial_order.add_edge(eng, silent_supplier)
    model.partial_order.add_edge(silent_supplier, approve)

    # Expedite Review is optional
    model.partial_order.add_edge(credit, silent_expedite)
    model.partial_order.add_edge(eng, silent_expedite)
    model.partial_order.add_edge(silent_expedite, approve)

    return model

model_balanced = create_model_balanced()

**Known underfitting risks:**
- The model may still underfit true concurrency between Supplier Confirmation and Approve Configuration preparation, as it enforces a strict order.
- It may not capture all possible interleavings of Credit Check and Engineering Review, as the partial order only enforces direct dependencies.

# 5. Permissive Candidate

**Inductive-bias statement:**
The permissive model admits all reasonable behaviors consistent with the broad domain rules, even if not observed. It models Credit Check and Engineering Review as fully concurrent (true concurrency), Supplier Confirmation as fully optional (can be skipped or occur in any order relative to Credit Check and Engineering Review), and Expedite Review as optional but constrained. It uses a combination of concurrency, optionality, and silent transitions to maximize generalization potential. The model prioritizes low-to-medium confidence rules (D4–D6, S3, S4, S6) and allows for missing data (S5) to be modeled as true optionality.

**Boundary between reasonable generalization and forbidden behavior:**
- **Reasonable generalization:** Any interleaving or concurrency of Credit Check and Engineering Review; Supplier Confirmation occurring before, between, or after Credit Check and Engineering Review; Expedite Review occurring after both Credit Check and Engineering Review and before Approve Configuration.
- **Forbidden behavior:** Any occurrence of Expedite Review without both Credit Check and Engineering Review completed; any occurrence of Supplier Confirmation after Approve Configuration; any occurrence of Release Production without Approve Configuration; any start activity other than Register Order or end activity other than Archive Case.

**Formal expression:**
```

        Register Order  Credit Check,
        Register Order  Engineering Review,
        Credit Check  Approve Configuration,
        Engineering Review  Approve Configuration,
        Credit Check  Supplier Confirmation,
        Engineering Review  Supplier Confirmation,
        Supplier Confirmation  Approve Configuration,
        Credit Check  Expedite Review,
        Engineering Review  Expedite Review,
        Expedite Review  Approve Configuration,
        Approve Configuration  Release Production,
        Release Production  Archive Case
    ),
    Operators:
        - Credit Check and Engineering Review are fully concurrent (no order enforced)
        - Supplier Confirmation is fully optional and can occur in any order relative to Credit Check and Engineering Review
        - Expedite Review is optional and can occur in any order relative to Supplier Confirmation, as long as it follows Credit Check and Engineering Review
)
```

def create_model_permissive():
    # Create activities
    register = Transition("Register Order")
    credit = Transition("Credit Check")
    eng = Transition("Engineering Review")
    supplier = Transition("Supplier Confirmation")
    expedite = Transition("Expedite Review")
    approve = Transition("Approve Configuration")
    release = Transition("Release Production")
    archive = Transition("Archive Case")

    # Create partial order
    partial_order = StrictPartialOrder()
    partial_order.add_edge(register, credit)
    partial_order.add_edge(register, eng)
    partial_order.add_edge(credit, approve)
    partial_order.add_edge(eng, approve)
    partial_order.add_edge(credit, supplier)
    partial_order.add_edge(eng, supplier)
    partial_order.add_edge(supplier, approve)
    partial_order.add_edge(credit, expedite)
    partial_order.add_edge(eng, expedite)
    partial_order.add_edge(expedite, approve)
    partial_order.add_edge(approve, release)
    partial_order.add_edge(release, archive)

    # Add edges to allow Supplier Confirmation to occur in any order relative to Credit Check and Engineering Review
    # (already covered by direct edges, but we add reverse edges to allow full concurrency)
    partial_order.add_edge(supplier, credit)
    partial_order.add_edge(supplier, eng)

    # Add edges to allow Expedite Review to occur in any order relative to Supplier Confirmation
    partial_order.add_edge(expedite, supplier)
    partial_order.add_edge(supplier, expedite)

    # Create POWL model
    model = OperatorPOWL(partial_order=partial_order)

    # Add silent transitions for full optionality
    silent_supplier = SilentTransition()
    silent_expedite = SilentTransition()

    # Supplier Confirmation is fully optional
    model.partial_order.add_edge(credit, silent_supplier)
    model.partial_order.add_edge(eng, silent_supplier)
    model.partial_order.add_edge(silent_supplier, approve)

    # Expedite Review is fully optional
    model.partial_order.add_edge(credit, silent_expedite)
    model.partial_order.add_edge(eng, silent_expedite)
    model.partial_order.add_edge(silent_expedite, approve)

    return model

model_permissive = create_model_permissive()

- Any occurrence of Supplier Confirmation after Approve Configuration.
- Any occurrence of Release Production without Approve Configuration.

# 9. Recommendation and Data-Collection Plan

**Recommendation:**
- **Immediate use:** `model_balanced` is recommended for immediate use. It balances fitness, precision, and generalization, and is robust to missing Supplier Confirmation events. It aligns with medium-to-high confidence rules and stakeholder statements, while avoiding overfitting to observed variants.
- **Sensitivity analysis:** `model_permissive` is recommended for sensitivity analysis. It will help identify which behaviors are most sensitive to assumptions about concurrency and optionality, and can guide future data collection.

**Data-collection plan:**

- Traces with true concurrency between Credit Check and Engineering Review (same start timestamp, different completion timestamps).

- Traces with Credit Check and Engineering Review occurring in different orders.
