# 1. Assumptions and Interpretation
1. Low-risk versus high-risk is represented as an exclusivechoice (XOR) between  
   • “Supervisor Review” (low) and  
   • the parallel pair “Quality Review”  “Regulatory Review” (high).  
   Because PM4Py POWL offers an explicit XOR operator while the process-tree has to remain block-structured, the process-tree realises the choice through a normal XOR; the POWL model adds no partial-order edges between the alternative branches so that only one of them can be taken in any concrete trace.
2. “Consult Supplier” is modelled as an XOR(optional) =    “Consult Supplier”.  
   The activity may occur at most once and only if the optional branch is chosen.
3. A passing inspection is abstracted by leaving the loop via  after an “Inspect Trial”.  
   The redo branch (“Adjust Parameters”) can only be reached directly after an inspection, guaranteeing that no Adjust Parameters follows a passing inspection.
4. Duplicate visible labels are **not** used.  Every real activity name occurs exactly once in every model.
5. Approximation policy for the process tree: conservative under-approximation.  
   The tree sacrifices the intended overlap between the approval route and the trial cycle; everything else is modelled exactly.
6. “May overlap” is interpreted as “no precedence edge exists” – i.e. true concurrency, not merely interleaving.

# 3. PM4Py Process-Tree Model

````python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# handy shortcut
def act(name):
    return ProcessTree(label=name)

tau = ProcessTree(None)

# Loop for the trial cycle  (Execute -> Inspect) ^ (Adjust)*
trial_body = ProcessTree(Operator.SEQUENCE, children=[act("Execute Trial"),
                                                      act("Inspect Trial")])
trial_redo = act("Adjust Parameters")
trial_exit = tau
trial_loop = ProcessTree(Operator.LOOP, children=[trial_body, trial_redo, trial_exit])

# Risk-route XOR
low_risk = act("Supervisor Review")
high_parallel = ProcessTree(Operator.PARALLEL, children=[act("Quality Review"),
                                                         act("Regulatory Review")])
risk_xor = ProcessTree(Operator.XOR, children=[low_risk, high_parallel])

# Optional supplier consultation
supplier_opt = ProcessTree(Operator.XOR, children=[tau, act("Consult Supplier")])

# Branch that stems from Analyse Root Cause
after_analyse = ProcessTree(Operator.PARALLEL, children=[
        act("Design Corrective Action"),
        risk_xor,
        supplier_opt
])

# Two early work-streams executed in parallel
early_parallel = ProcessTree(Operator.PARALLEL, children=[
        ProcessTree(Operator.SEQUENCE, children=[act("Contain Material"),
                                                 act("Plan Verification")]),
        ProcessTree(Operator.SEQUENCE, children=[act("Analyze Root Cause"),
                                                 after_analyse])
])

# Full tree
tree = ProcessTree(Operator.SEQUENCE, children=[
        act("Register Deviation"),
        early_parallel,
        trial_loop,
        act("Release Material"),
        act("Archive Case")
])
````

Paragraph – unavoidable approximations  
• Approvals and supplier consultation are located inside the branch that is completed before the trial loop starts.  Consequently “Quality/Regulatory Review” or “Supervisor Review” cannot overlap with “Execute Trial”, which under-approximates the intended behaviour (Req. 7).  
• “Consult Supplier” may not start until after “Design Corrective Action” in the tree, although the narrative allows it to start immediately after “Analyze Root Cause”.  
All other requirements are represented exactly.

# 4. PM4Py POWL Model

````python
from pm4py.objects.powl.obj import StrictPartialOrder, Transition, SilentTransition

# Visible transitions
reg      = Transition("Register Deviation")
contain  = Transition("Contain Material")
analyse  = Transition("Analyze Root Cause")
plan     = Transition("Plan Verification")
design   = Transition("Design Corrective Action")
sup      = Transition("Supervisor Review")
qual     = Transition("Quality Review")
regul    = Transition("Regulatory Review")
supp_inv = Transition("Consult Supplier")
exe      = Transition("Execute Trial")
insp     = Transition("Inspect Trial")
adj      = Transition("Adjust Parameters")
rel      = Transition("Release Material")
arc      = Transition("Archive Case")

tau      = SilentTransition()          # loop-exit

# Flat partial-order backbone
nodes = [reg, contain, analyse, plan, design,
         sup, qual, regul, supp_inv,
         exe, insp, adj, rel, arc, tau]
powl = StrictPartialOrder(nodes)

# Core precedence relations
powl.add_edge(reg,      contain)
powl.add_edge(reg,      analyse)

powl.add_edge(contain,  plan)

powl.add_edge(analyse,  design)
powl.add_edge(analyse,  sup)
powl.add_edge(analyse,  qual)
powl.add_edge(analyse,  regul)
powl.add_edge(analyse,  supp_inv)

powl.add_edge(plan,     exe)
powl.add_edge(design,   exe)

powl.add_edge(exe,      insp)
powl.add_edge(insp,     adj)        # taken when inspection fails
powl.add_edge(adj,      exe)        # start new trial iteration

# Release synchronisation
for a in [insp, sup, qual, regul, supp_inv]:
    powl.add_edge(a, rel)
powl.add_edge(rel, arc)
````

Explanation of concurrency  
Any pair of nodes without an edge is intentionally left concurrent, allowing overlap.  For instance, “Quality Review” and “Execute Trial” have no direct or transitive edge, therefore they may interleave arbitrarily; this fulfils Req. 7.  Likewise “Consult Supplier” is only ordered after “Analyze Root Cause” and before “Release Material”; it can overlap everything else.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Over/Under-constraint | Business consequence |
|-------------|-------------------|--------------|------|-----------------------|-----------------------|
| Dual early work-streams | True concurrency | exact | exact | — | Shortens lead time |
| Containment  Plan | strict order | exact | edge present | — | Safety first |
| Analyse  Design | strict order | exact | edge present | — | Corrective design based on facts |
| Risk route XOR | XOR; high=both reviews | exact | over-approx (all three could occur) | POWL under-spec | Extra reviews waste effort |
| Approval  Trial overlap | allowed | **not allowed** | exact | Tree over-constraint | Longer cycle time in tree analysis |
| Optional supplier | 1, may overlap | allowed but later than earliest | exact | Tree under-spec (late start) | Misses early supplier input in tree |
| Repeat-until-pass | loop (Adjust before next Execute) | exact | exact | — | Quality preserved |
| Release join | waits for pass, approvals, supplier | exact inside tree, exact in POWL | exact | — | Legal compliance |
| No duplicate labels | enforced | enforced | enforced | — | Log replay unambiguous |

# 7. Preferred Representation and Validation Plan
Preferred: POWL.  It captures the critical cross-branch dependencies directly and keeps all intended interleavings; the process-tree had to give up the approval/trial overlap.

Validation plan:
1. Convert both models to accepting Petri nets with `pm4py.convert_to_petri_net`.
2. Run PM4Py soundness checker (`check_soundness`) and inspect any deadlocks or livelocks.
3. Perform bounded playout (500 traces length  30) from the POWL net; verify that at least one trace matches each of T1–T4 and none matches T5–T8.
4. Replay T1–T8 against the nets with conformance checking; expect deviations exactly as stated in §5.
5. Specifically inspect silent transitions: use token-based replay and ensure that every silent transition in the trial loop is consumed at least once in sampled traces.
6. Check for accidental duplicate labels by asserting `len(set(label)) == number_of_visible_transitions`.
Limitations: the soundness checker ignores data conditions, so low/high/supplier choices cannot be fully validated; bounded playout may miss rare corner traces; replay verdicts depend on alignment quality.

# 8. Final Self-Critique
1. Semantic weakness: the POWL model does not enforce the XOR between low and high risk – it merely permits both routes to be taken, relying on data outside the control-flow.  
2. The process-tree under-approximates the crucial overlap between approvals and the trial cycle, which may mislead performance analysts.  
3. The sample code assumes that the simple `StrictPartialOrder` object is accepted as a complete POWL model; if a wrapper operator were mandatory in a newer PM4Py version, minor adjustments would be needed.
