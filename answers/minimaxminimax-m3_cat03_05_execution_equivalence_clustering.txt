## 1. Equivalence design space

I define four relations, three of which are required. All are defined relative to the lead object type `Order`. An execution is the multiset of events that touch at least one `Order` object, restricted to those events and their directly attached objects.

### 1.1 Activity-sequence equivalence (_AS)

Two executions $X, Y$ are activity-sequence equivalent, written $X \approx_{AS} Y$, iff their timestamp-ordered sequences of activity labels are identical as ordered multisets. The relation discards object types, identifiers, O2O relations, qualifiers, and externality.

- **Preserves:** activity label, total order, label multiplicity.
- **Discards:** object type, identifiers, E2O/O2O, qualifiers, external flags.
- **Reflexive / symmetric / transitive:** yes — it is exact string-multiset equality over an alphabet.
- **Concurrency:** events with equal timestamps are sorted by `(activity, set of attached object types)`; ties are broken lexicographically.

X1, X2, X5, X6, X7 all reduce to `[Create Order, Add Item, Add Item, Pack Package, Dispatch, Issue Invoice, Record Payment]`, so they collapse into one _AS cluster even though their business meanings differ.

### 1.2 Typed structural equivalence under identifier renaming (_TS)

Two executions are typed-structural equivalent, $X \approx_{TS} Y$, iff there exists a bijection on local identifiers that maps every event of $X$ to an event of $Y$ with identical activity label, identical internal-object-type multiset, and identical O2O relation multiset, while preserving event order. External flags are encoded as a separate `EXT` marker per attached type but their specific identity is stripped.

- **Preserves:** activity, E2O multiplicity by type, O2O multiplicity by (parent_type, child_type, qualifier), total event order.
- **Discards:** raw identifier values, attribute values, specific external-object identity.
- **Reflexive / symmetric / transitive:** yes — equality of canonical event tuples is an equivalence relation.
- **Concurrency:** same tie-break as 1.1; the canonical form is a tuple of sorted per-event fingerprints, so ordering becomes deterministic.

This is the finest relation among those I define that still treats identifiers as pure noise. It separates X1 from X2 only via identifier renaming; X3, X4, X5, X6, X7, X8 each acquire distinct canonical signatures.

### 1.3 Business-semantic equivalence (_BS)

Two executions are business-semantically equivalent, $X \approx_{BS} Y$, iff they share the same **lifecycle motif**, defined as the conjunction of (a) the _TS canonical signature, (b) the external-flag multiset per activity, (c) the O2O qualifier multiset (e.g. `partial_settlement`, `replaces`, `removed_before_dispatch`, `returns_from`), and (d) the shape of `PackDispatch` pairing treated as a partial order over package lifecycles.

- **Preserves:** everything in 1.2 plus externality, qualifiers, and lifecycle pairing shape.
- **Discards:** identifiers, timestamps, attributes, monetary amounts, customer identifiers.
- **Reflexive / symmetric / transitive:** yes — two executions either share a finite tuple-of-tuples signature or they do not.
- **Concurrency:** Pack/Dispatch pairs are matched via shared `Package` object across the signature, not by timestamp; simultaneous events are equivalent to any consistent interleaving.

_BS is the relation I treat as preferred. It produces a partition where the clean baseline, the split-logistics motif, the cross-order motif, and the exception motif each become one cluster.

## 2. Canonical signatures

The signature is a tuple of per-event fingerprints. Each fingerprint is `(activity, internal_type_multiset, external_type_set, qualifier_tuple)`, sorted by timestamp and then by `(activity, fingerprint)` for tie-breaking. The Python outline assumes an `OCEL`-like event log with attributes `event.activity`, `event.objects` (dict `type  [id]`), and `event.qualifiers` (dict `relation  qualifier`).

```python
def canonical_signature(execution, lead_type="Order"):
    events = sorted(
        [e for e in execution.events
         if any(o.startswith("O") or o == lead_type
                for o in e.objects.get(lead_type, []))],
        key=lambda e: (e.timestamp, e.activity)
    )
    parts = []
    for e in events:
        int_types = {}      # type -> count of non-EXT ids
        ext_types = set()   # set of types with EXT ids
        for t, ids in e.objects.items():
            for oid in ids:
                if oid.startswith("EXT"):
                    ext_types.add(t)
                else:
                    int_types[t] = int_types.get(t, 0) + 1
        quals = tuple(sorted(
            (rel, q) for rel, q in getattr(e, "qualifiers", {}).items()
        ))
        parts.append((
            e.activity,
            tuple(sorted(int_types.items())),
            tuple(sorted(ext_types)),
            quals
        ))
    return tuple(parts)
```

## 4. Cluster interpretations

**C-CleanBaseline (X1, X2).** Signature: one Order  two Items  one Package  one Delivery  one Invoice  one Payment; no external objects, no qualifiers. Business behavior: a textbook straight-through order with one consolidated physical shipment and one financial settlement. Operational risk: low; opportunity: this is the canonical template to benchmark deviation. Flattening concern: a naive label-only flattening overstates homogeneity and would absorb X5–X7, masking cross-order risk. Stable under identifier renaming, attribute removal, and reasonable timestamp jitter.

**C-LogisticsSplit (X3, X4).** Signature: two Items, two Packages, one or two Deliveries, one Invoice, one or two Payments. Business behavior: physical fulfillment splits while the invoice remains a single customer-facing artifact. X3 merges both packages onto one delivery; X4 ships them separately and pays in two installments. Operational risk: reconciliation complexity, partial-payment aging, and route failure on the second leg. Opportunity: enables partial fulfillment and incremental revenue recognition. Flattening concern: collapsing X3 and X4 into "split logistics" loses the partial-payment pattern, which is critical for cash-flow analysis. Stability: the cluster holds under renaming and timestamp jitter; it collapses to `C-CleanBaseline` only if all qualifiers and multiplicities are dropped, which is unsafe.

**C-CrossOrder (X5, X6).** Signature: at least one event references an `EXT` Order, with the externality attached either to logistics (X5: shared `Package` and `Delivery`) or to finance (X6: shared `Invoice` and `Payment`). Business behavior: two orders co-execute on one physical or financial resource. Risk: revenue misallocation, audit-trail gaps, SLA ambiguity; opportunity: cross-sell bundling, cost amortization. Flattening concern: dropping `EXT` flags merges this cluster into `C-CleanBaseline`, which silently hides a material operational pattern. Stability: stable under renaming; brittle under external-flag suppression.

**C-ExceptionLifecycle (X7, X8).** Signature: lifecycle deviates from a single straight path. X7 substitutes one Item before dispatch (`removed_before_dispatch`); X8 returns one Item, inspects it, and repacks it into a new Package. Risk: incorrect revenue recognition if the original Invoice is not amended, inventory drift, customer-experience breakage. Opportunity: process mining of returns and substitutions reveals product-quality signals. Flattening concern: label-only flattening absorbs X7 into `C-CleanBaseline` and X8 into `C-LogisticsSplit`, erasing the exception. Stability: stable under renaming, but X7 can be lost if qualifiers are ignored.

## 5. Borderline cases

**X1 vs X2.** Under all three relations they coincide: labels are identical (_AS), the canonical fingerprint after renaming is identical (_TS), and both lack externality and qualifiers (_BS). A defensible coarser definition (e.g. _AS only) agrees with the finer ones; this pair is the easiest case.

**X1 vs X5.** Under _AS they coincide (the EXT flag does not appear in the label). Under _TS and _BS they differ because X5's `Pack Package` and `Dispatch` carry `EXT` markers on Order and Item. The disagreement is informative: a label-only monitoring tool would treat cross-order logistics as a normal single-package case, which is exactly the kind of mistake business-semantic equivalence is designed to prevent.

**X1 vs X6.** Same shape as X1 vs X5, but the externality lives on `Issue Invoice` and `Record Payment` instead of on logistics. _AS lumps them; _TS and _BS separate them. The pair highlights that finance-side sharing is invisible at the label level and is only recoverable through O2O topology.

**X1 vs X7.** Under _AS identical. Under _TS they differ because `Dispatch` carries the qualifier `removed_before_dispatch` on Item. Under _BS they differ because the lifecycle motif is "single-package with mid-flight substitution." A definition that ignores qualifiers would silently merge X7 into the clean baseline; this is the canonical example of why the O2O qualifier layer matters.

**X3 vs X4.** Under _AS clearly distinct (interleaved Pack/Dispatch vs two Pack then one Dispatch). Under _TS also distinct (Dispatch multiplicity and Record Payment multiplicity differ). Under _BS they both belong to `C-LogisticsSplit` because their defining motif is "split packaging with a single Order," and the partial-payment qualifier is treated as a within-cluster variant rather than a cluster-level separator. The two definitions legitimately disagree on whether partial payment is a within-cluster dimension or a between-cluster boundary.

**X4 vs X8.** Under _AS and _TS distinct (X8 introduces `Return Item` and `Inspect Return` activities and a second package lifecycle). Under _BS they belong to different clusters because the motifs differ: X4 is "split-and-partial-pay," X8 is "return-and-repack." They share a higher-level logistics motif (multiple packages per Order), so _LG would merge them — a useful demonstration that a coarser relation can be misleading for finance and compliance work.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` clusters objects by exact equality of the multiset of events they participate in, including the full set of attached object identifiers. It therefore preserves activity labels, E2O incidence, and O2O relations with raw identifiers intact. This is the strongest structural notion PM4Py exposes natively.

Raw identifiers make this partition too fine: X1 and X2 would be in different clusters despite identical behavior, X3 and X4 would also separate even at the business level we care about, and any `EXT` flag would never be normalised. To obtain a coarser, semantically meaningful partition, I canonicalize each object's event history by replacing identifiers with `(type, position-in-event)` tokens, then aggregate by the canonical signature of Section 2, then optionally merge clusters that share a chosen motif dictionary.

Exact equivalence is preferable when the question is "did two orders literally execute on the same resource at the same time?" — for example, in audit or forensic checks. Business-semantic equivalence is preferable when the question is "are these orders operationally comparable?" In OCELs with very large connected executions, `max_objs` trimming is necessary because the equivalence test otherwise blows up; canonicalization also helps because it short-circuits on a tuple hash.

```python
import pm4py
from collections import defaultdict

ocel = pm4py.read_ocel("path/to/ocel.ocz")
exact = pm4py.cluster_equivalent_ocel(ocel)   # dict: cluster_id -> [obj_ids]

def canonical_history(obj_id, ocel):
    sig = []
    for ev in sorted(ocel.objects[obj_id]["events"]):
        objs = ocel.events[ev]["objects"]
        int_t = tuple(sorted(
            (ocel.objects[oid]["type"], 1)
            for oid in objs if not oid.startswith("EXT")
        ))
        ext_t = tuple(sorted({
            ocel.objects[oid]["type"] for oid in objs
            if oid.startswith("EXT")
        }))
        quals = tuple(sorted(ocel.events[ev].get("qualifiers", {}).items()))
        sig.append((ev, int_t, ext_t, quals))
    return tuple(sig)

canon_clusters = defaultdict(list)
for cid, members in exact.items():
    for oid in members:
        canon_clusters[canonical_history(oid, ocel)].append(oid)

# Optional: further merge by motif
MOTIF = {("C-CleanBaseline",), ("C-LogisticsSplit",),
         ("C-CrossOrder",), ("C-ExceptionLifecycle",)}
final = defaultdict(list)
for sig, members in canon_clusters.items():
    motif = classify_motif(sig)         # business rule from Section 1.3
    final[motif].extend(members)
```

The classification step `classify_motif` implements the rules in Section 1.3 and is the only place where domain semantics enters the pipeline.

## 7. Robustness analysis

**Perturbation A: ignore all O2O qualifiers.** X7 merges into `C-CleanBaseline` (the `removed_before_dispatch` qualifier is gone), and X4 loses its partial-payment distinction within `C-LogisticsSplit`. Business risk: silent loss of substitution and partial-settlement signals.

**Perturbation B: ignore external objects.** X5 and X6 collapse into `C-CleanBaseline`. This is the most dangerous perturbation for compliance work because cross-order revenue allocation and SLA breach attribution vanish.

**Perturbation C: collapse repeated same-label events.** Under pure bag semantics, X4's `[Pack, Dispatch, Pack, Dispatch, Payment, Payment]` becomes `{Pack×2, Dispatch×2, Payment×2}` and X3 becomes `{Pack×2, Dispatch×1, Payment×1}`. The two still separate, but partial-order information between paired events is lost, so a "Pack then Dispatch then Pack then Dispatch" order cannot be distinguished from any interleaving.

**Perturbation D: treat Pack/Dispatch as a partial order.** Pairs of `Pack Package` and `Dispatch` that share a `Package` form a happens-before edge. Under partial-order semantics, X3 and X4 can both be described as "two packages packed and dispatched before invoice and payment." Whether they merge depends on whether `Record Payment` multiplicity is part of the order. If yes, they remain distinct; if no, they merge into a single "two-package execution" cluster, equivalent to _LG.

**Perturbation E (optional): payment multiplicity as an amount attribute.** X4's two `Record Payment` events collapse into one event whose `Payment` set has size two, or whose amount attribute equals their sum. This change preserves financial semantics but erases the timing of the partial settlement, which matters for cash-flow analytics. Recommended only when the analysis question is "how much was paid," not "when."

## 8. Limitations and recommendation

No single equivalence serves all four purposes.

- **Compliance monitoring** benefits from _TS or _BS, never _AS. The qualifier layer (`removed_before_dispatch`, `partial_settlement`, shared `EXT` objects) is exactly what auditors and regulators look for; flattening it is unsafe.
- **Operational segmentation** benefits from _BS with the external-flag and qualifier layers retained. A segmentation that mixes cross-order cases with clean baselines produces misleading dashboards.
- **Root-cause analysis** benefits from the finest non-redundant relation, which is _BS extended with timestamps and attributes. The exception cluster (X7, X8) is precisely where RCA pays off, and _AS would erase the trace.
- **Descriptive reporting** is the only purpose for which _AS or _LG is acceptable, because high-level KPIs rarely need qualifier detail.

The right working default is _BS with the canonical-signature pipeline of Section 2: it is reproducible, robust to identifier noise, sensitive to externality and qualifiers, and stable under reasonable data-repair choices. Finer relations (_TS) should be reserved for forensic work; coarser relations (_AS, _LG) should be reserved for descriptive dashboards and only after the business-semantic partition has been validated.
