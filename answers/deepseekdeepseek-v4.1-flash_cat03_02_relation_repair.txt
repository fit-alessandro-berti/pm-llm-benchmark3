## 1. Consistency rules and evidence model

**Hard invariants**
- Every E2O relation must reference an existing event ID and object ID; every O2O relation must reference existing object IDs.
- Duplicate identical E2O/O2O triples are not allowed.
- Qualifier direction is fixed: `DEL-X carries PK-7`, not `PK-7 carries DEL-X`.
- Basic lifecycle order is hard where event timestamps and object creation imply it: an Item cannot be packed before Add Item, a Package cannot be dispatched before Pack Item, an Invoice cannot be paid before Issue Invoice.
- Event/object IDs, activity names, and object types are not invented.

**Strong defaults**
- `Create Order` relates to exactly one Order.
- `Add Item` relates to one Order and one Item.
- `Pack Item` normally relates to one Item and one Package, with scanner-outage exceptions.
- `Dispatch Package` normally relates one Package to one Delivery, with bulk-dispatch exceptions.
- `Issue Invoice` relates one Invoice to one or more Orders.
- `Record Payment` relates one Payment and normally one Invoice; unapplied cash is possible.
- Existing O2O structure should be consistent with E2O events when both are present.

**Weak heuristics**
- Identifier similarity is useful but not proof: `PK8-2` suggests `PK-8`; `N-421?` suggests `DEL-Y`; `N-42*` is too broad.
- Temporal order supports PackDispatchConfirm and InvoicePayment.
- Amount and customer matching are corroborative, not decisive. `INV-44` total 230 equals 130+100, but fees/discounts can also explain totals.
- Route matching supports NORTH packages/deliveries.
- Attribute hints such as `order_hint=ORD-A` support item-order relations.

**Evidence against repairs**
- Arithmetic equality alone does not prove invoice or payment linkage.
- A wildcard carrier reference matching multiple deliveries is weak evidence for a unique delivery edge.
- Adding an O2O edge solely because an E2O edge was inferred is circular; it cannot then be counted as independent confirmation.
- A package containing items from different orders is plausible only if consolidation is otherwise supported.
- Scanner outages make item-only `Pack Item` rows possible, so ev08 need not force a package relation.

I combine evidence by preferring minimum additions that satisfy strong defaults, then downweighting amount-only and wildcard-identifier inferences. Existing O2O edges are treated as corroborating only when they are not derived from the same proposed E2O edge.

## 5. Lifecycle and cardinality audit

**Order.** ORD-A has a full lifecycle: create, add items, pack, dispatch via PK-7/PK-8, confirm delivery to order, invoice, and payments. ORD-B under Bundle A gets create, add item, pack via PK-8, dispatch via DEL-Y, invoice, and payment, but no explicit `Confirm Delivery` E2O edge. That leaves ORD-B less confirmed, not fully orphaned. Under Bundle B, ORD-B stops after Add Item, so it is an incomplete/orphan order.

**Item.** IT-A1 is packed in PK-7 and carried by DEL-X. IT-A2 is packed in PK-8 and carried by DEL-Y. IT-B1 under Bundle A is packed in PK-8 and carried by DEL-Y; under Bundle B it is an orphan after Add Item. Bundle A creates a mixed-order package because PK-8 packs both IT-A2 and IT-B1.

**Package.** PK-7 remains a normal package. PK-8 under Bundle A becomes one-to-many to items: it packs IT-A2 and IT-B1, then is carried by DEL-Y. Under Bundle B, PK-8 packs only IT-A2. No package is dispatched before being packed in either bundle.

**Delivery.** DEL-X carries PK-7 and is supported by ev09 E2O evidence. DEL-Y under A/B carries PK-8, supported by ev10 E2O evidence. ev11 remains unresolved, so no delivery is explicitly confirmed by the event. DEL-Y is therefore dispatched but not confirmed in A/B.

**Invoice.** INV-44 under Bundle A bills ORD-A and ORD-B and is settled by PAY-1 and PAY-2. This is a one-to-many invoice-to-order relation and a many-to-one payment-to-invoice relation. Under Bundle B, INV-44 bills only ORD-A and is partially settled by PAY-1.

**Payment.** PAY-1 settles INV-44 and is corroborated by ev13. PAY-2 under Bundle A settles INV-44, creating a multiple-payment invoice. Under Bundle B, PAY-2 is an orphan/unapplied payment.

**Independent evidence and circularity.** Existing `DEL-X carries PK-7`, `PK-7 packs IT-A1`, and `PAY-1 settles INV-44` are independently supported because their E2O events mention both endpoints. The added O2O edges are not independent: `PK-8 packs IT-B1` follows from `ev08  PK-8`; `DEL-Y carries PK-8` follows from `ev10  DEL-Y`; `INV-44 bills ORD-B` follows from `ev12  ORD-B`; `PAY-2 settles INV-44` follows from `ev14  INV-44`. Treating those O2O edges as separate confirmation would be circular.

## 8. Over-repair warnings

1. Forcing `ev08  PK-8` and `PK-8 packs IT-B1` creates a mixed-order package; if false, package, order, and delivery flattenings will falsely show ORD-B goods traveling with ORD-A goods.
2. Adding `INV-44 bills ORD-B` solely because 230 equals 130+100 may create a false multi-order invoice, inflating Order–Invoice interactions and merging ORD-B into an invoice lifecycle it never had.
3. Adding `PAY-2 settles INV-44` based on arithmetic can erase unapplied-cash behavior, making an incomplete payment record look fully settled.
4. Assigning ev11 uniquely to DEL-X or DEL-Y from `N-42*` creates a false delivery confirmation edge; assigning it to both creates a false bulk-confirmation pattern.
5. Adding `ev11  ORD-B` because of the shared customer C17 falsely marks ORD-B as delivery-confirmed and can make ORD-A and ORD-B look like equivalent executions.
6. Treating an inferred O2O edge as independent confirmation of the E2O edge that produced it is circular and overstates confidence in mixed packages, multi-order invoices, and payment settlement.
7. Completing every object lifecycle—especially ORD-B, IT-B1, and PAY-2—would hide genuine scanner outages, missing events, or unapplied cash, reducing the log’s ability to model exceptions.
