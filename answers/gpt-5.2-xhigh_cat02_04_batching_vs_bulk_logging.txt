# 3. Consequences for performance analysis

Below, “waiting time” refers to \(W_q = start - queue\_arrival\), “service time” to \(S = complete - start\), and “sojourn” to \(C = complete - queue\_arrival\). These are only meaningful if `start/complete` reflect execution, not UI group actions or bulk submissions.

## G1 (Apply label / RBT-7)

- **If interpreted literally (4 parallel jobs, each 3 minutes)**:
  - **Service time bias**: per-case \(S\) looks correct (3 min) but double-counts machine effort (4×3 min) over a 3-minute wall-clock window.
  - **Utilization bias**: can imply >100% utilization unless the cell is modeled as capacity 4 (multi-capacity server).
  - **Waiting bias**: earlier arrivals (08:54) appear to wait longer than later ones; this can be *real* (waiting to fill a 4-slot fixture) or an artifact of when the upstream system emits `queue_arrival`.
  - **Throughput bias**: throughput is correctly “4 outputs at 09:03”, but capacity inference is wrong if treated as single-capacity serial.
  - **Conformance bias**: can introduce apparent high parallelism; a model might learn that “Apply label” happens simultaneously for multiple cases, which is only meaningful if batch/cycle semantics are represented.
- **Most defensible correction**: treat as a **single cycle** with **batch size 4** (multi-item fixture) and allocate machine time per cycle, not per item, or use batch-aware costing (e.g., divide cycle time by batch size when estimating per-item effort).

## G2 (Surface inspection / T-B)

- **Signature suggests “group start”**, not true per-item start.
- **Waiting time bias**:
  - Using `start=10:00` for all cases **underestimates waiting** for later-inspected items (they likely started after earlier completions), even though it looks like they started simultaneously.
- **Service time bias**:
  - Later-completing cases get **inflated service times** (e.g., 27 minutes) because their intervals wrongly include time spent inspecting other items.
- **Utilization bias**:
  - Interval overlap makes one resource appear to run many jobs concurrently; utilization can exceed 1 unless the log is reinterpreted.
- **Throughput/bottleneck**:
  - Completes are staggered, so throughput may look reasonable, but bottleneck analysis that uses service times will falsely identify inspection as “long”.
- **Conformance**:
  - Discovery may infer parallel branches or concurrency where the real behavior is “one worker sequentially inspects within a group.”
- **Correction**: keep completes (and recorded_at) as event-specific, but treat per-case starts as **unknown** within \([group\_start, case\_complete]\) or reconstruct sequential starts (e.g., start\_i ≈ complete\_{i-1}) as a *modeling assumption* for queueing metrics.

## G3 (Release review / T-C)

- **Likely bulk completion/submission timestamp**.
- **Waiting time bias**: start timestamps vary and may still approximate “pickup” time; waiting can be somewhat usable if `start` is real.
- **Service time bias**:
  - If `complete=11:30` is submission time, then \(S\) is **overstated** for earlier-started cases (their “service” includes time spent reviewing other cases and/or idle time before submission).
- **Utilization & WIP bias**:
  - Inflated \(S\) increases estimated utilization and apparent WIP; the activity looks like a long, overlapping batch.
- **Throughput bias**:
  - Artificial completion synchronization produces a “throughput spike” at 11:30 and can distort SLA/lead-time distributions.
- **Conformance bias**:
  - Identical completes can create false synchronization constraints or hide true ordering among cases.
- **Correction**: treat completion as **right-censored** (true completion \(\le\) submission time), or model two events: “review finished” and “form submitted” (currently conflated).

## G4 (Pack item / T-D)

- **Clean serial pattern** with high-resolution timestamps.
- **Waiting time**: increasing waits are consistent with a queue formed by arrivals slightly earlier than starts.
- **Service time**: stable 4-minute service is plausible; recorded_at seconds after completion supports genuine execution timestamps.
- **Utilization**: near-continuous work implies high utilization; bottleneck detection is likely reliable here.
- **Conformance**: ordering is clear (no ties); good candidate cluster for performance conclusions.
- **Caveat**: PM4Py may label this “sequential batching,” but physically it can simply be normal FIFO single-server processing with little idle, not a deliberate batch policy.

## G5 (Root-cause analysis / analyst_pool)

- **If resource IDs are trusted as unique workers**:
  - Overlap implies heavy multitasking or concurrent processing by one person, producing **implausible utilization** (>1) and ambiguous service interpretation.
- **If `analyst_pool` is a shared account (supported by context)**:
  - Overlap mostly indicates **parallel analysts**, not multitasking; the correct model is a **resource pool with capacity up to 3**.
- **Waiting time**: start times can still be a useful “pickup” proxy, but must be interpreted relative to pool capacity.
- **Bottlenecks**: treating the pool as one server can falsely indicate a bottleneck (because overlap inflates “busy time”); treating as a capacity-k pool can flip the conclusion.
- **Conformance**: resource-based rules (“same resource cannot overlap”) become invalid; conformance checks must be identity-aware.

## G6 (Close ticket / T-F) — why this pattern is so dangerous

- **Key mechanism**: bulk form submission overwrites both `start` and `complete` with the same “submission/closing session” time (17:00), decoupled from actual work.
- **Inflated waiting + near-zero service** (explicitly):
  - Waiting \(W_q = start - queue\_arrival\) becomes **hours** because `start` is pushed to 17:00.
  - Service \(S = complete - start\) becomes **0** because `complete == start`.
  - Result: the data simultaneously implies “tickets waited forever” *and* “closing takes no time,” which can make the close step look non-bottleneck in service-time terms while appearing as the dominant delay in waiting-time terms.
- **Utilization bias**: summed service time is ~0, so T-F appears idle even while the system shows huge queues.
- **Throughput bias**: a large number of tickets “complete” at exactly 17:00, producing artificial throughput spikes and end-of-shift effects.
- **Conformance bias**: temporal ordering between cases collapses; many events become ties, potentially breaking ordering-based checks.
- **Correction**: exclude from execution-time performance analysis or replace with interval-censored estimates; at minimum, split into “work performed” vs “bulk closure logged.”

## G7 (Manual measure / T-G)

- **Timestamp coarsening dominates** (15-minute precision with undocumented rounding).
- **Waiting time bias**:
  - Negative waits can occur (arrivals after rounded-down start), which is a strong red flag for clock/rounding mismatch rather than true negative waiting.
- **Service time bias**:
  - Service times become quantized (here, exactly 15 minutes for all), flattening variability and misleading utilization/bottleneck analysis.
- **Throughput bias**:
  - Many cases share identical completion windows; throughput appears in bursts at quarter-hour boundaries.
- **Conformance bias**:
  - Many ties create ambiguous ordering; discovered models can overstate concurrency.
- **Correction**: treat start/complete as intervals of width at least 15 minutes (interval-censored) and avoid fine-grained queueing inference.

## G8 (Repair triage / T-H)

- **Queue accumulation after capacity loss** is consistent with a long initial wait then a dense serial “recovery run.”
- **Waiting time bias**:
  - If the safety-check truly blocked triage, then the initial waiting is real but attributable to downtime; queue analysis should attribute delay to **capacity unavailability**, not slow service.
  - If clocks differ materially, some of the apparent wait could be an offset artifact.
- **Service time**: stable 7-minute services with 1-second precision look credible.
- **Utilization/bottleneck**:
  - A naive model might mark T-H as a bottleneck due to long waits; a downtime-aware model would separate “blocked” vs “busy.”
- **Conformance**:
  - Clear serial order; good for within-run ordering, but causal linkage to safety-check needs clock reconciliation.

    return pd.Series(
        {
            "overlap_rate": float(np.mean(overlaps)),
            "adjacency_rate": float(np.mean(adjacency)),

# 5. Robustness and alternative explanations

## Resource identity: trusted IDs vs shared accounts

- **If resource IDs are trusted as “one worker = one ID”**:
  - **G5** becomes strong evidence of **true concurrent work/multitasking** (overlaps on one resource), inflating utilization and invalidating single-server assumptions.
  - **G1** strongly supports **physical multi-capacity concurrency** (one cell processing multiple items simultaneously).
- **If resource IDs are treated as possibly shared/pooled**:
  - **G5** shifts to a **capacity-pool** explanation; overlap no longer implies multitasking, and utilization must be computed against pool size (unknown, up to 3).
  - Any resource-based conformance rule (“no overlap per resource”) becomes unreliable unless identities are disambiguated.

## Timestamp semantics: exact points vs interval-censoring by stated precision

- **Exact-timestamp assumption** (treat the recorded times as true execution times):
  - PM4Py’s categories line up mechanically: G1/G6/G7 “Simultaneous”, G2 “Batching on Start”, G3 “Batching on End”, G4/G8 “Sequential batching”, G5 “Concurrent batching”.
  - Negative waits (G7) become impossible anomalies, suggesting data-quality failure.
- **Interval-censored assumption** (each timestamp represents an interval of width ≈ `precision`):
  - Many “equalities” become non-informative ties. For **1-minute** precision (G2/G3/G5/G6) and **15-minute** precision (G7), it is easy for distinct true times to collapse to the same recorded minute/quarter-hour.
  - Sequential adjacency (G4/G8) is robust because it appears with **1-second** precision and repeated exact boundaries across a chain; but if precision were coarse, adjacency could be accidental.

## Same temporal pattern, multiple physical explanations (at least three)

- **Identical start and end across many cases** (G1, G6, G7):
  - Could mean a *true simultaneous batch* (multi-capacity machine cycle), *bulk logging* (end-of-shift form), or *timestamp coarsening/rounding* (legacy MES).
- **Identical start with staggered end** (G2):
  - Could mean *start batching/common setup*, or coarse start timestamp assignment (e.g., “top of hour”), or true parallel processing with one shared start event (requires capacity evidence).
- **Staggered start with identical end** (G3):
  - Could mean *bulk submission* (form submitted after finishing), *hard deadline*, or *coarsening* where ends round to the same minute.
- **Overlaps on one resource** (G5):
  - Could mean *multitasking*, *shared-account artifact*, or misinterpreted lifecycle semantics where “start” reflects assignment time and “complete” reflects reporting time.
- **Large arrival-to-first-start gap then dense serial completion** (G8):
  - Could mean *capacity loss/downtime*, *prioritization/other work*, or *clock skew* between upstream arrivals and local execution times.

# 6. Data-collection redesign

Prioritized changes to disambiguate operational batches from logging batches and to support valid queueing/performance inference:

1. **Separate execution vs submission timestamps (highest priority)**:
   - Record `work_started_at`, `work_completed_at` (execution), and independently `form_submitted_at` / `db_inserted_at` (`recorded_at`).
   - Never overwrite execution timestamps with submission times; store both.
2. **Resource/badge identity (eliminate shared-account ambiguity)**:
   - Persist operator/badge ID alongside login ID; for pool accounts, log the *actual* person and workstation.
   - If shared logins are unavoidable, encode **pool capacity** explicitly (e.g., `resource_pool=analyst_pool`, `member_id=...`).
3. **Batch/group identifiers and capacity metadata**:
   - Add `batch_id`/`group_id` when a UI supports “begin group” or when a machine cycle processes multiple items.
   - Record workstation/cell capacity (e.g., “fixture_slots=4”), and attach items to the cycle ID.
4. **Pause/resume and blocking events**:
   - Capture `pause`, `resume`, `blocked_by_safety`, `downtime_start/end` events so “queue accumulation after capacity loss” can be modeled rather than inferred.
5. **Clock alignment and provenance**:
   - NTP-sync all devices; store `clock_offset_estimate` or “server time vs device time”.
   - Keep timezone and monotonic sequence; log the source clock used for each timestamp.
6. **Precision metadata as executable rules**:
   - Store not just “precision=15 min”, but the **rounding function** (floor/ceil/nearest) and whether it applies to start vs complete.
   - Prefer raw timestamps plus a “display rounding” layer rather than rounding at capture time.
7. **Queue semantics instrumentation**:
   - Distinguish “arrived to queue”, “eligible for processing”, “picked up”, and “started work” to avoid mixing upstream arrivals with local readiness.

# 7. Final adjudication

- **High-confidence interpretations (usable with minimal caveats)**:
  - **G4**: reliable serial execution (good for waiting/service/utilization/bottleneck inference).
  - **G1**: high-confidence **simultaneous batch/cycle** pattern, but per-item service accounting needs batch-aware correction (multi-capacity cycle allocation).
  - **G2**: high-confidence that `start` is a **group-start artifact**; per-item starts are not directly observed.
  - **G6**: high-confidence **bulk logging** (execution timing not represented).
  - **G7**: high-confidence **timestamp coarsening** dominates (fine-grained inference not valid).
- **Clusters that should be excluded or interval-censored for queue analysis**:
  - **Exclude or treat as logging-only**: **G6** (inflated waits + near-zero service is structural).
  - **Interval-censor / reconstruct**: **G2** and **G3** (group-start and group-end/submission semantics).
  - **Interval-censor**: **G7** (15-minute rounding; negative waits indicate coarse/biased timestamps).
  - **Model as pool / identity-uncertain**: **G5** (do not use single-resource constraints; utilization depends on unknown pool size).
- **Require operational validation before performance conclusions**:
  - **G3**: confirm whether 11:30 is submission time vs a real deadline; if submission, split events.
  - **G5**: confirm actual analyst concurrency and whether start/complete are assignment/reporting times.
  - **G8**: validate safety-check linkage and quantify clock offsets between systems; if confirmed, treat delays as downtime-driven backlog rather than slow service.
