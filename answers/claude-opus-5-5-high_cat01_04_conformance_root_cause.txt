## 3. Causal-abductive explanation

```text

H_report_metric_definition   -> measured_fitness
H_incident_detection         -> business_outcomes
H_appeal_censoring           -> business_outcomes
```

Measured fitness is generated by the *recorded* log compared with the *normative model*, so it can fall because behavior changed, because the recording changed, or because the model became stale. The June collapse fits the recording path. The UI release changed `recorded_labels` but not `true_process`. The gateway inserted `Queue Routed`. The ETL change made the order of `Decision` and `Notify` a by-product of ingestion batching. Each mechanism alone costs one or two moves per trace. Because they coincided and hit almost every case, fitness collapsed abruptly and uniformly, which is the signature of instrumentation. Behavioral drift is usually gradual and uneven across reviewers. In August the policy changed `true_process` while `normative_model` lagged, so compliant sign-offs were scored as deviations.

The staged repairs remove most of the collapse but leave a residue that no documented change explains. That residue consists of enhanced reviews without a recorded check, overrides that only lead into standard review, unrouted cases that all went to standard review, and early notifications confined to routed standard cases. It lies exactly where `reviewer_behavior` or silent capture loss would act.

Unchanged outcomes do not prove data error. A skipped compliance check usually yields the same decision. Thirty bypasses would move approval by less than one point. August-September appeals are right-censored. Incident detection is incomplete and may rely on the same log. Nor do stable outcomes rule out noncompliance: they measure customer-visible results, not control execution. Outcomes are weakly informative in both directions, so the discriminating evidence has to come from provenance checks, stratification and audits.

## 6. PM4Py reproduction and model-comparison code

def tree_to_net(tree_string):
    tree = pm4py.parse_process_tree(tree_string)
    net, im, fm = pm4py.convert_to_petri_net(tree)
    return tree, net, im, fm

def expand_variants(variant_counts):
    traces = []
    for trace, count in variant_counts.items():
        traces.extend([trace] * count)
    return pm4py.parse_event_log_string(traces)

# 3. Transparent, logged normalisation pipeline

LABEL_MAP = {"Risk Screen": "Classify"}   # justified by 40-case UI audit + release notes
TECHNICAL_EVENTS = {"Queue Routed"}       # gateway event from 2026-06-03, no business meaning


def normalise(df, map_labels=True, drop_technical=True):
    out = df.copy()
    steps = []
    if map_labels:
        n = int(out[ACT].isin(LABEL_MAP.keys()).sum())
        out[ACT] = out[ACT].replace(LABEL_MAP)
        steps.append(f"relabelled {n} events via {LABEL_MAP}")
    if drop_technical:
        mask = out[ACT].isin(TECHNICAL_EVENTS)
        steps.append(f"removed {int(mask.sum())} technical events {sorted(TECHNICAL_EVENTS)}")
        out = out[~mask]
    return out.reset_index(drop=True), steps


def swap_reversed_notify(variant_counts, share_repaired):
    """Sensitivity stand-in for source-sequence ordering, which the aggregates do
    not contain. share_repaired=1.0 assumes every Notify->Decision is an ingestion
    artefact (upper bound); 11/70 uses only the screenshot-confirmed share
    (lower bound). Replace with a real sort on the source sequence number."""
    out = Counter()
    for trace, count in variant_counts.items():
        if "Notify,Decision" in trace:
            k = round(count * share_repaired)
            out[trace.replace("Notify,Decision", "Decision,Notify")] += k
            out[trace] += count - k
        else:
            out[trace] += count
    return dict(out)

def dfg_table(df, top=12):
    dfg, start, end = pm4py.discover_dfg(df)
    rows = sorted(dfg.items(), key=lambda kv: -kv[1])[:top]
    return pd.DataFrame([(a, b, c) for (a, b), c in rows], columns=["from", "to", "count"])


def alignment_diagnostics(df, net, im, fm):
    aligned = pm4py.conformance_diagnostics_alignments(df, net, im, fm)
    log_moves, model_moves = Counter(), Counter()
    fitting = 0
    for res in aligned:
        if res["cost"] < 10000:     # visible deviations cost 10000 each; tau moves cost 1
            fitting += 1
        for log_lbl, model_lbl in res["alignment"]:
            if log_lbl != ">>" and model_lbl == ">>":
                log_moves[log_lbl] += 1
            elif log_lbl == ">>" and model_lbl not in (">>", None):
                model_moves[model_lbl] += 1
    fit = pm4py.fitness_alignments(df, net, im, fm)
    return {
        "perfectly_fitting_%": round(100.0 * fitting / len(aligned), 1),
        "log_fitness": round(fit["log_fitness"], 3),
        "avg_trace_fitness": round(fit["averageFitness"], 3),
        "top_log_moves": log_moves.most_common(4),
        "top_model_moves": model_moves.most_common(4),
    }


def report(title, df, net, im, fm, with_precision=False):
    diag = alignment_diagnostics(df, net, im, fm)
    if with_precision:
        diag["precision_alignments"] = round(pm4py.precision_alignments(df, net, im, fm), 3)
    print(f"\n--- {title} ---")
    for k, v in diag.items():
        print(f"  {k}: {v}")
    return diag

              f"(reported {reported_epc[p]}){flag}")

    print("\n=== Frequency DFGs (raw, recorded order) ===")
    for p, df in logs.items():

    print("\n=== Raw vs staged normalisation against the normative model ===")
    results = {}
    for p, df in logs.items():
        results[(p, "raw")] = report(f"{p} raw", df, net, im, fm)
        if p == "Apr-May":
            continue
        mapped, s1 = normalise(df, map_labels=True, drop_technical=False)
        print(f"  pipeline: {s1}")
        results[(p, "label")] = report(f"{p} label map only", mapped, net, im, fm)
        clean, s2 = normalise(df, map_labels=True, drop_technical=True)
        print(f"  pipeline: {s2}")
        results[(p, "label+tech")] = report(f"{p} label map + technical-event removal", clean, net, im, fm)

    aug, _ = normalise(expand_variants(swap_reversed_notify(VARIANTS["Aug-Sep"], 1.0)))

## 7. Provisional conclusion

**Primary explanation of the measured collapse (confidence about 80%).** The fall from roughly 93% to 32% fitting is predominantly a measurement failure, not a behavioral one. Three documented instrumentation changes added deviations to nearly every trace at once: the `Classify` to `Risk Screen` relabel, the new `Queue Routed` gateway event, and the use of ingestion time for `Decision`/`Notify`. Their staged repair restores June–July fitting to 89%. The later August–September drop is mainly model obsolescence: the tree was never updated for mandatory `Supervisor Sign-off`, so compliant behavior is scored as deviation. The aggregate numbers themselves are not reliable, since the variant tables cannot reproduce several reported values.

**Residual compliance concern (about 50% confidence that a real problem exists in at least some cases).** 55 enhanced reviews have no recorded compliance check: there were none before June, and they make up 11–15% of enhanced cases since. No repair removes them. Every irregular path ends in standard review: unrouted cases, legacy-label cases, overrides and early notifications. The EUR 50k sign-off rule has never been checked, because the value attribute was dropped. These may be capture losses, but they sit exactly where real bypasses would hide.

**Immediate actions.**
- *IT:* freeze and version the extraction. Restore source timestamps and document where the sequence number comes from. Publish an event dictionary. Explain the missing `Request Info` events, the missing resources and the Aug 12 override-logging change.
- *Process owners:* formally approve the label mapping. Issue a versioned model with a data-aware sign-off constraint. Explain the direction of `Manual Override` and the 90 unrouted cases.
- *Compliance:* audit all 55 no-check cases, and all high-value cases without sign-off, against systems of record. Keep the audit blind to hypothesis. Record the incomplete incident detection as a control finding in its own right.

**What must not be claimed yet:**
- that employees became noncompliant;
- that the process is compliant;
- that the 55 cases are bypasses, or that they are logging gaps;
- that all reversed notifications are artifacts (only 11 of 70 are confirmed);
- that 86–89% fitness under a candidate model demonstrates adherence to the EUR 50k policy;
- that stable appeal rates prove there was no harm.

## 8. Model-governance recommendation

1. **Model versioning:** Every normative model is versioned, with an effective date range and a link to the policy clause that motivates each construct. Conformance jobs must select the model version by case date, and any policy change (such as the EUR 50k sign-off) triggers a mandatory model-impact review before its effective date, not afterwards.
2. **Event-semantic contracts:** Each business activity has a contract. It states the canonical label, its semantic definition, the source screen or field, the owner and the allowed aliases. UI or schema releases that touch a contracted element must declare a mapping. The mapping is approved by the process owner and must be supported by evidence that the outputs are equivalent, not just by release notes.
3. **Technical-event policy:** New system-generated events (such as `Queue Routed`) must be registered with a type flag (technical or business), a coverage specification and their payload semantics before they reach the analysis log. Technical events are excluded from control-flow conformance by rule, and their payloads are kept for routing checks rather than silently deleted.
4. **Timestamp provenance:** Every event carries both its source-execution timestamp and its ingestion timestamp, a source sequence number with documented generation semantics, and a provenance tag. Conformance and performance metrics may only order events by validated source time or sequence. ETL changes to any time field require a regression test on ordering-sensitive relations such as `Decision` before `Notify`.
5. **Data-aware constraints:** Obligations conditioned on case data (value thresholds, risk class, authorizations) are encoded as data-aware rules or guards, alongside the control-flow model. Reports must stratify by the conditioning attributes. Any model extension must pass a precision and normative-content review, so that optionality is never added merely to recover fitness.
6. **Post-release validation:** After any UI, gateway, ETL or policy release, run a validation window with fixed checks. These cover weekly DFG and variant step-change detection, the appearance or disappearance of activities, per-activity completeness (including resources), a random provenance audit of at least 30 cases, and a comparison of conformance under the old and new pipelines. Conformance declines are reported as incidents only after this validation separates artifacts from behavior.
