## 1. Control-Objective Decomposition

FEP-1 ("preparer ≠ releaser") is a mechanism, not an objective. The underlying objectives / threat scenarios, and what each control can do about them:

**O1 — Unilateral fraud: one insider redirects funds to an account they control.**
- AV-2: partially prevents (bank-change-in-7-days check, ownership check, sanctions, operator limit) but is overrideable and explicitly cannot establish who controls a compromised account.
- MG-4: prevents if performed before release or settlement by a genuinely independent L3+ manager who reviews bank details; fails if the manager is conflicted or rubber-stamps.
- RA-7: detects; corrects only inside the ~24 h recall window.
- ED-1: does not itself act; it restricts when the single-operator path may be used (amount, vendor age, no recent bank change), shrinking the attack surface.

**O2 — Unintentional error: wrong amount, duplicate invoice, wrong payee.**
- AV-2: strong preventive coverage (duplicate check, PO match, limits) — this is its home ground.
- MG-4: preventive/detective backstop if substantive.
- RA-7: detective; corrective only inside recall.
- ED-1: neutral (does not address it directly; condition 5 imports AV-2).

**O3 — Payment for goods/services never received (fabricated receipt).**
- AV-2: fails by design ("does not establish that goods/services were received").
- MG-4: only control that can prevent it, and only if the manager actually reviews the supporting receipt.
- RA-7: detects (as in AP-204) but usually after recovery is uncertain.
- ED-1: neutral; four-eyes itself only helps if the second person exercises independent judgment.

**O4 — Collusion between two or more actors (including preparer–releaser pairs).**
- FEP-1 itself fails: distinct user IDs are no defense.
- AV-2: fails ("does not detect collusion").
- MG-4: helps only if the manager is outside the colluding set and substantive.
- RA-7: the main defense — pattern detection over time (repeated pairs, shared workstations).
- ED-1: irrelevant.

**O5 — Compromised credential / account takeover (one person acting under two identities, or stolen override credentials).**
- FEP-1: defeated if one actor holds two credentials (cf. u23 using m09's override credential).
- AV-2: fails ("cannot establish who controlled a compromised account").
- MG-4: partial — an out-of-band human approval raises the attacker's cost.
- RA-7: detective; also the forensic mechanism afterwards.
- ED-1: neutral.

**O6 — Vendor-master manipulation / bank-account-change fraud (classic BEC profile).**
- AV-2: strong preventive check (bank change within 7 days) — but only when operational and not overridden.
- MG-4: detective/preventive if the manager verifies bank details against an independent source.
- RA-7: corrective only inside the recall window; after settlement, largely evidentiary.
- ED-1: condition 4 (no bank change in 7 days) is a hard gate for the emergency path.

**O7 — Override and exception abuse (using warnings-override or the emergency path as a loophole).**
- AV-2: is itself the exposed surface (manager-override of warnings).
- MG-4: must be independent of whoever overrode; otherwise the override collapses independence entirely.
- RA-7: detects override-rate anomalies and post-hoc token creation.
- ED-1: condition 1 (token active *before* Prepare_Payment) exists precisely to prevent retroactive justification.

No single control covers all objectives: AV-2 covers O2/O6 well, nothing covers O3 except substantive MG-4, nothing covers O4 except RA-7 pattern analysis. Sufficiency therefore depends on which threat is live in the specific case.

## 2. Equivalence and Sufficiency Test

A compensating package for a nominal FEP-1 breach is evaluated on seven dimensions:

1. **Timing**: does an independent check occur before the point of irrevocability (bank settlement)? A pre-release check is strongest; a post-release/pre-settlement check retains corrective capacity; a post-settlement check is evidence only.
2. **Independence**: is the second human free of hierarchy conflicts (e.g., not rating the operator's performance), not the preparer/releaser, and not sharing credentials or workstations with them?
3. **Coverage**: does the package address the threat that is actually live in this case (recent bank change → O6; no receipt confirmation → O3), not just some threat?
4. **Overrideability**: can the controlled party neutralize the control (warning overrides, unsigned checklists, post-hoc tokens)?
5. **Recoverability**: if the package only detects, does detection land inside the ~24 h recall window?
6. **Evidence quality**: is there contemporaneous proof the control was substantive (documented review of invoice, bank details, receipt) rather than a log entry?
7. **Collusion resistance**: how many independent parties must fail or conspire for a loss to complete?

**Grading:**
- **Fully equivalent**: an independent, substantive, non-overridden human check occurred before settlement AND automated coverage matched the live risks AND detection would still have been inside the recall window. The package blocks every loss path FEP-1 would have blocked, with comparable collusion resistance (≥2 independent parties must fail).
- **Partially equivalent**: the main loss paths were blocked before irrevocability, but at least one dimension is degraded (e.g., procedural gate broken, one uncovered threat of low likelihood, timing tight).
- **Merely mitigating**: only detective value after irrevocability, or preventive value that misses the live threat; loss would likely complete, but would be found.
- **Ineffective**: no independent check before irrevocability, controls overridden/unavailable, conflicted approvers, detection after the recall window.

**Why "same expected loss" is not the only standard.** (a) Expected loss ignores tail risk: a package that equalizes the mean can leave a EUR 900k unrecoverable tail (AP-208). (b) It ignores incentive and deterrence effects: predictable pre-commitment (token before prepare, non-overrideable blocks) deters attempts; expected-loss math on observed cases misses attempts never made. (c) It ignores evidence and accountability: regulators and courts require demonstrable control operation, not statistical equivalence. (d) It is outcome-biased when estimated ex post — AP-208 had zero realized loss and terrible controls; AP-205 had a stopped attempt and good controls. Sufficiency must be judged on the information available at decision time. (e) Independence is a value in itself: a package that channels all trust into one overridable system changes the failure mode from "two humans must collude" to "one credential must leak."

## 4. Preventive–Detective–Corrective Comparison

| Control | Primary class | Timing anchor | Overrideable? | Corrective capacity | Coverage limits | Collusion resistance |
|---|---|---|---|---|---|---|
| AV-2 | Preventive (block) / preventive-advisory (warning) | Before release | Yes — warnings by authorized manager (abused in AP-202); also fails open when unavailable (AP-208) | None once release occurs | No receipt verification, no collusion or account-takeover detection | Low: one leaked override credential defeats it |
| MG-4 (before release) | Preventive | Before release | Only by skipping/rubber-stamping | Full: nothing has left | Depends entirely on substantive review and independence | Moderate: attacker must recruit or deceive the manager |
| MG-4 (after release, before settlement) | Hybrid — see below | Before irrevocability | Same | High: recall/stop still possible | Same | Moderate |
| MG-4 (after settlement) | Detective only | After irrevocability | — | ~None (exceptional legal recovery) | Same | Low practical value against completed fraud |
| RA-7 (≤24 h) | Detective, partly corrective | Inside recall window | No | Partial: recall usually possible | Sampling/attention limits; depends on audit quality | Good against patterns (pairs, overrides) over time |
| RA-7 (>24 h) | Detective / evidentiary | After recall window | No | Marginal | Same | Same, but losses stand |
| ED-1 | Not a control — a gating meta-rule | Before Prepare (token) | Defeated by post-hoc tokens (AP-206 question, AP-208) | None itself; it sequences the other controls | Only as good as enforcement of its seven conditions | N/A |

**Semantics for a manager action after Release_Payment but before Bank_Settlement (AP-201, AP-207):** it is *detective with respect to the release event* — the internal control breach has already occurred and is on the record — but *preventive with respect to the loss event*, because settlement is the point of irrevocability and the manager can still stop or recall the transfer. I adopt loss-anchored semantics and call it a **hybrid (detective–corrective)** control: FEP-1's stated purpose is to prevent an erroneous or fraudulent *transfer*, and for internal-control purposes the transfer is consummated at settlement, not at the release keystroke. Consequence of this choice: pre-settlement ratification earns substantial (not full) credit — full credit only when it is demonstrably substantive and time remains to act (AP-207: 80 minutes; AP-201: 90 minutes). Post-settlement ratification (AP-202, AP-208) earns essentially none against loss.

## 5. Counterfactual and Residual-Risk Analysis

Probability language is qualitative; any number is illustrative only.

**AP-202.** Loss mechanism (realized): insider or insider-adjacent fraud — new vendor with a bank account changed two hours before payment, linked to an employee's relative; the single actor prepared, overrode the warning with a credential not his own, and released. Which control could have broken the chain: AV-2's warning *did* fire — the chain broke at the override; a non-overrideable block on (new vendor AND bank change <7 d AND amount > operator limit) would very likely have stopped it, as would any independent pre-settlement human check. What remains exposed even after fixes: credential-sharing between u23 and m09, and m09's conflicted position. Under a truly independent second releaser: loss becomes unlikely unless the releaser colludes or rubber-stamps — the second releaser would confront the same warning and would need to co-own the override. Likelihood of loss drops from near-certain (given an attacker in the preparer seat) to low.

**AP-204.** Loss mechanism (realized): fabricated service receipt monetized through a formally compliant two-person flow — either collusion or one person effectively controlling both sessions on the shared workstation. Which control breaks the chain: none that was deployed; AV-2 cannot see receipt fraud, and the "independent" releaser wasn't. What would: goods-receipt confirmation from a third party, physical/logical session separation, or substantive MG-4 for consulting payments above a threshold. Remaining exposure: the other 36 joint payments; the pair remains active (AP-209). A truly independent second releaser changes little *if* the fraud is receipt fabrication by the preparer alone (the releaser rarely verifies delivery) — moderate reduction at best; the real fix is receipt verification, not more eyes on the same paper.

**AP-208.** Loss mechanism (counterfactual): BEC/vendor-impersonation — young vendor, bank account changed three days earlier, EUR 900k, and *no functioning ownership check at release time*. Every element of the classic pattern was present; legitimacy was luck. Which control would break the chain: AV-2's bank-change and ownership checks (unavailable), a signed manual fallback (unsigned), or MG-4 before settlement (came a day late). What remains exposed: the entire amount, unrecoverably, in the counterfactual. A truly independent second releaser helps moderately — a diligent one would demand ownership evidence before releasing 900k to a changed account; a hurried one under outage pressure might not. The stronger fix is a hard rule: no release above the operator limit during an AV-2 outage without a signed checklist and pre-release MG-4.

**AP-201.** Loss mechanism (counterfactual): keying error or petty self-dealing by u17. AV-2 breaks the error chain (duplicate, limit, PO match); m04's pre-settlement ratification breaks anything AV-2 missed except receipt fraud — and a fabricated receipt for EUR 1,800 in office supplies is a low-yield, high-detection crime given 100%-style audit attention. Remaining exposure: trivial in money terms; the real residual is normative — tolerated convenience violations erode the token discipline that AP-208 shows matters. An independent second releaser would reduce an already-small risk marginally; the cheaper equivalent is enforcing the token requirement.

**AP-206.** Loss mechanism (counterfactual): a rushed outage payment to a wrong or manipulated payee. The chain was broken *before release* by m11's substantive approval plus a full AV-2 pass — the strongest possible placement. Remaining exposure: not this payment, but the precedent: if tokens can appear two minutes after Prepare_Payment, ED-1's precommitment gate is decorative, and a future attacker can manufacture "emergencies" retroactively. An independent second releaser would add little here (the manager already was the second pair of eyes pre-release); fixing token issuance latency/logging adds more.

**AP-209.** Loss mechanism (hypothetical): same as AP-204 — pair-mediated receipt fraud. No control deployed distinguishes this case from AP-204 except audit outcome ("no defect found"), which is weak evidence given the audit missed nothing because there may have been nothing, or found nothing because receipt fraud is hard to see. A truly independent second releaser — specifically, breaking the fixed u12/u13 pairing via rotation — is exactly the intervention with the highest value here: it converts a static two-party trust assumption into a randomized one, sharply raising collusion cost. Residual after rotation: low.

**AP-205.** For completeness: the loss mechanism (duplicate payment) was severed by AV-2's hard block — the ideal outcome. Residual: the same-user *attempt* pattern; if u44's attempts recur, that is a probing signal, not noise.

## 6. Evidence and Monitoring Recommendations

**Evidence to collect routinely (contemporaneous, tamper-evident):**
- Token issuance logs with issuer identity, request time, and stated reason, reconciled against outage/incident tickets (resolves AP-206-type ambiguity).
- Override records: credential used, its owner, session origin (IP/workstation), and the specific warning overridden (would have exposed AP-202 in minutes).
- Manager review artifacts: which documents (invoice, bank detail, receipt) were opened/attested, not just an approval timestamp — distinguishes substantive MG-4 from rubber stamps.
- Workstation/session telemetry binding user IDs to physical or virtual endpoints (AP-204/AP-209).
- Signed manual fallback checklists during any AV-2 outage, filed before release.
- Bank-ownership evidence (confirmed callback, penny-test) retained per payment where a bank change occurred within 30 days.

**Monitoring rules (alert thresholds are illustrative starting points, to be calibrated):**
1. **Same-user rate**: share of completed payments with preparer = releaser, per operator and per unit, weekly. Alert on any same-user completion *without* an active pre-Prepare token, and on operators exceeding ~2 per month.
2. **Override rate**: overrides per operator and per manager credential; alert on any override executed under a credential whose owner is not the session user, and on managers whose override approvals exceed peer baseline.
3. **Late manager approval**: distribution of (manager action − release) and (manager action − settlement); alert whenever manager action follows settlement on any nominal-violation or emergency case.
4. **Audit-before-recall-window**: fraction of same-user/emergency payments audited within 24 h of release; alert when a case scheduled for 100% next-day audit slips past the recall window (AP-202: 8 days; AP-208: 4 days).
5. **Repeated resource pairs**: rolling 30-day count of identical (preparer, releaser) pairs; alert above a percentile threshold (u12/u13 at 37/30 days is an extreme outlier) and force pair rotation pending review.
6. **Shared workstations**: alert when preparer and releaser of the same case share an endpoint or overlapping session, ever.
7. **Bank-change proximity**: alert on any payment within 7 days of a bank-account change, escalating (hard hold) when combined with vendor age < 1 year or amount above the operator limit.
8. **Control outages**: alert on any release during an AV-2 outage; hard-block releases above the operator limit during outages absent a signed checklist plus pre-release MG-4.

**Alert versus proof.** An alert is a statistical or rule-based anomaly that raises the prior of a control problem and triggers proportionate investigation; it is not a finding of misconduct. The u12/u13 pairing may be a sanctioned two-person cell (the missing design docs cut both ways); a late token may be a logging artifact (AP-206); a high override rate may reflect a badly tuned AV-2. Treating alerts as verdicts produces unfair accusations and teaches staff to game the metrics. Proof requires corroborated evidence — forensic session data, document provenance, financial tracing — evaluated by someone independent of the monitored population. Conversely, absence of alerts is not proof of health: AP-204 was formally clean until the audit read the receipt.

for col in ("token_time", "settlement_time"):

       .groupby("case:concept:name")

# 6) Preliminary evidence flags (True / False / None=unknown)
# ---------------------------------------------------------------
def flags(r):
    tok_ok = (None if (r.token_active and pd.isna(r.token_time))
              else bool(r.token_active and pd.notna(r.token_time)
                        and r.token_time < r.prepare_time))
    settle = r.settlement_time
    mgr_pre_settle = (None if pd.isna(r.manager_time) or pd.isna(settle)
                      else bool(r.manager_time < settle))
    audit_recall = (None if pd.isna(r.audit_time) or pd.isna(r.release_time)
                    else bool(r.audit_time <= r.release_time + pd.Timedelta(hours=24)))
    audit_1bd = (None if pd.isna(r.audit_time) or pd.isna(r.release_time)
                 else bool(r.audit_time <= r.release_time + pd.offsets.BusinessDay(1)))
    ed1 = {
        "ed1_1_token_before_prepare": tok_ok,
        "ed1_2_amount_lt_100k": bool(r.amount_eur < 100_000),
        "ed1_3_vendor_ge_180d": bool(r.vendor_days >= 180),
        "ed1_4_no_bank_change_7d": bool(pd.isna(r.bank_change_days) or r.bank_change_days > 7),
        "ed1_5_av_pass_no_override": bool(r.av_result == "pass" and not r.override_used),
        "ed1_6_indep_mgr_before_settlement": (None if mgr_pre_settle is None
                                              else bool(mgr_pre_settle and r.manager_independent is True)),
        "ed1_7_audit_within_1bd": audit_1bd,
    }
    vals = list(ed1.values())
    ed1_all = False if any(v is False for v in vals) else (None if any(v is None for v in vals) else True)
    return pd.Series({
        "av_result": r.av_result,
        "override_used": bool(r.override_used),
        "bank_change_within_7d": bool(pd.notna(r.bank_change_days) and r.bank_change_days <= 7),
        "audit_within_recall_24h": audit_recall,
        **ed1,
        "ed1_all_conditions": ed1_all,
    })

**PM4Py behavior I cannot guarantee across versions.** (1) The retention semantics of `pm4py.filter_four_eyes_principle` differ across releases: some document it as returning the *violating* cases (same resource performs both activities), while the underlying LTL checker historically exposed a `positive` parameter and, depending on version, the top-level wrapper instead retains the cases *satisfying* four-eyes (distinct resources) — e.g., under pm4py 2.7.x this call retains AP-204 and AP-209, the two distinct-user completed payments, not the six same-user cases. Some releases also return an `EventLog` object rather than a DataFrame. The code therefore wraps the call in `try/except`, prints whatever the installed version retains with an explicit semantics warning, and treats the plain-pandas preparer-vs-releaser comparison as authoritative: the nominal violators are AP-201, AP-202, AP-203, AP-206, AP-207 and AP-208, and the two lists must be complementary over completed payments — any other divergence indicates a version quirk to investigate. (2) `pm4py.format_dataframe` may emit deprecation warnings or add index columns in newer releases; this does not affect the logic since the pandas checks operate on the raw frame. (3) Cases with no `Release_Payment` (AP-205) are invisible to the four-eyes filter by construction, which is exactly why step 4 identifies blocked attempts separately. (4) The one-business-day audit check uses `pd.offsets.BusinessDay`, which ignores local holidays; for the given May 2026 weekday timestamps this is immaterial.

Finally, the note the task itself requires: these code outputs are evidence for judgment. The flags mark where controls fired, when, and by whom; whether a package was *sufficient* (Sections 2–3) additionally depends on independence in substance, review quality, and case-specific threat profiles, which no rule table decides on its own.
