# 1. Delay-decomposition definitions

The process models a fork-join structure where `arrival` initiates the flow, `fork_release` permits parallel work, branches A, B, and C execute in parallel, and `final_start` initiates the resource-constrained station.

**Formulas:**
For a case $c$ and branch $i \in \{A, B, C\}$:

1.  **Upstream Elapsed:** $T_{upstream}^{(c)} = \text{fork\_release}^{(c)} - \text{arrival}^{(c)}$
2.  **Branch Queue:** $Q_{i}^{(c)} = \text{start}_{i}^{(c)} - \text{fork\_release}^{(c)}$ (Assuming $\text{start} \ge \text{fork\_release}$)
3.  **Branch Service:** $S_{i}^{(c)} = \text{end}_{i}^{(c)} - \text{start}_{i}^{(c)}$
4.  **Join Ready:** $T_{join}^{(c)} = \max(\text{end}_{A}^{(c)}, \text{end}_{B}^{(c)}, \text{end}_{C}^{(c)})$
5.  **Branch Sync Wait:** $W_{i}^{(c)} = \max(0, T_{join}^{(c)} - \text{end}_{i}^{(c)})$
6.  **Downstream Queue:** $Q_{down}^{(c)} = \text{final\_start}^{(c)} - T_{join}^{(c)}$
7.  **Final Service:** $S_{final}^{(c)} = \text{final\_end}^{(c)} - \text{final\_start}^{(c)}$
8.  **Total Flow Time:** $T_{total}^{(c)} = \text{final\_end}^{(c)} - \text{arrival}^{(c)}$

**Double Counting Explanation:**
Summing all branch synchronization waits ($\sum_{i} W_{i}^{(c)}$) would attribute the synchronization delay to every branch. Since $T_{join}^{(c)}$ is defined as the *latest* completion, the critical branch has $W_{critical}^{(c)} = 0$. Non-critical branches have $W_{non-critical}^{(c)} > 0$.
If one sums these waits to reconstruct the "elapsed time" of the join stage, one assumes the process waited for *all* branches sequentially or adds their idle times to the timeline. This inflates the perceived duration of the join stage because the actual process idle time is zero (the join starts exactly when the last branch finishes). The sum counts the time interval $[T_{join}^{(c)}, T_{join}^{(c)}]$ multiple times (once for each non-critical branch) rather than representing a single sequential extension. Thus, summing them double counts the synchronization interval relative to the critical path logic.

# 5. Recommended redesigns and risks

**Recommendation 1: Optimize Branch B Queueing (Resource Scheduling)**
*   **Action:** Increase resource availability for Branch B (Machine Stress Test) or prioritize B release.
*   **Throughput:** Increases system throughput by reducing variance in `join_ready`.
*   **Flow-Time Tail:** Reduces the tail significantly (see Counterfactual 2). F07 and F12 are high-flow-time cases driven by B queue.
*   **Risks:** If B is accelerated, it might become critical in fewer cases, but A or C might become critical. However, since B's mean service is shorter than A's, B is less likely to dominate the join time if queueing is removed.
*   **Pilot:** Measure B queue times specifically. Implement a "pre-release" buffer for B tasks to ensure `B_start` $\approx$ `fork_release`.

**Recommendation 2: Final Station Capacity Expansion**
*   **Action:** Add resources to F (Release Decision) or parallelize F1/F2.
*   **Throughput:** No change in `join_ready` time, but increases `final_end`.
*   **Flow-Time Tail:** Reduces `total_flow_time` for 6 cases where downstream queue exists.
*   **Risks:** May mask upstream inefficiencies. If A, B, or C are slow, F capacity does not help.
*   **Pilot:** Monitor `final_start` vs `join_ready`. If gap persists, capacity is not the bottleneck.

**Recommendation 3: Stabilize Branch A (Standardize Service)**
*   **Action:** Standardize Laboratory Assay protocols to ensure 50m consistency.
*   **Throughput:** A is a constant 50m. Reducing it to 40m risks making B (37.5m + queue) the bottleneck.
*   **Flow-Time Tail:** Relatively low impact compared to B queueing.
*   **Risks:** Over-optimizing A may shift the bottleneck to B or C without reducing total time.

# 7. Limits of inference

The provided timestamps and process definition allow for a robust decomposition of time, but several causal and structural inferences remain uncertain:

1.  **Causality vs. Correlation:** The decomposition identifies *where* time is spent (e.g., B queueing), but does not prove *why* B queues (e.g., resource scarcity, upstream delay).
2.  **Resource Capacity:** The data shows `final_resource` (F1/F2) but does not specify the capacity of each resource (e.g., is F1 a single machine or a pool?). If F1 is a pool, the queueing dynamics differ from a single server.
3.  **Work Preemption:** The data assumes tasks run to completion once started. If tasks can be paused and resumed (preemptive scheduling), the `service` time would include wait time, inflating the metric.
4.  **Release Policy:** The `downstream_queue` might not be due to congestion but due to a batch-release policy (e.g., F only processes cases in groups). This would mean increasing F capacity does not reduce the queue, only the batch size.
5.  **Synchronization Granularity:** The `join_ready` is a single timestamp. It does not capture if the join activity itself takes time to coordinate (e.g., waiting for all reports). The model assumes instantaneous join logic upon max completion.
6.  **Hidden Dependencies:** The data assumes independence between branches (A, B, C). If a technical failure in A delays B (e.g., shared lab equipment), the independence assumption is violated.

These limitations suggest that while the decomposition identifies performance characteristics, it requires operational context to validate the root causes of the delays identified.
