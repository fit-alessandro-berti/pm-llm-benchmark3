## 1. Modeling assumptions

- **Object types:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Capitalization is used consistently in all tables and PM4Py calls.
- **E2O qualifier vocabulary:** source-observed qualifiers use the `observed:` prefix, such as `observed:created_order`, `observed:packed_item`, and `observed:settled_invoice`. Analytically propagated context uses `derived_context:order`, `derived_context:item`, or `derived_context:package`.
- **O2O directions:**
  - `Order  Item`: `contains`
  - `Package  Item`: `packs`
  - `Delivery  Package`: `carries`
  - `Invoice  Order`: `bills`
  - `Payment  Invoice`: `partial_settles` or `completes_settlement`
  
  Reverse rows are not duplicated; analyses requiring reverse navigation should traverse these edges in reverse.
- **Downstream E2O richness:** logistics events are enriched with direct E2O rows for affected Orders and Items. Such rows are marked as analytically derived. Invoice issuance is directly related to both Orders because that fact is explicit. Payment events are related only to their Payment and Invoice objects because allocating either payment to an individual Order or Item is not supported by the narrative.
- **Source versus propagation:** every relation has a `relation_origin` column, and its qualifier is also prefixed with either `observed:` or `derived_context:`. A source-minimal OCEL can therefore be obtained by filtering `relation_origin == "observed"` without guessing which relations were propagated.
- **PM4Py version assumption:** the code assumes a recent PM4Py version exposing the requested top-level discovery functions and the constructor `OCEL(events=..., objects=..., relations=..., o2o=...)`. The constructor is isolated on one line. For a version with a different constructor signature, only that adapter line should change; the four DataFrames and their semantics should remain unchanged.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL


# ---------------------------------------------------------------------------
# Events
# ---------------------------------------------------------------------------

event_rows = [
    ("e01", "Create Order",     "2026-04-06 08:00:00+00:00", None,  None),
    ("e02", "Add Item",         "2026-04-06 08:05:00+00:00", None,  None),
    ("e03", "Add Item",         "2026-04-06 08:06:00+00:00", None,  None),
    ("e04", "Create Order",     "2026-04-06 08:10:00+00:00", None,  None),
    ("e05", "Add Item",         "2026-04-06 08:12:00+00:00", None,  None),
    ("e06", "Reserve Stock",    "2026-04-06 08:30:00+00:00", None,  None),
    ("e07", "Pack Package",     "2026-04-06 09:00:00+00:00", None,  None),
    ("e08", "Pack Package",     "2026-04-06 09:05:00+00:00", None,  None),
    ("e09", "Dispatch Package", "2026-04-06 10:00:00+00:00", None,  None),
    ("e10", "Dispatch Package", "2026-04-06 10:15:00+00:00", None,  None),
    ("e11", "Issue Invoice",    "2026-04-06 11:00:00+00:00", None,  None),
    ("e12", "Record Payment",   "2026-04-06 11:30:00+00:00", 100.0, "monetary_unit"),
    ("e13", "Confirm Delivery", "2026-04-06 13:00:00+00:00", None,  None),
    ("e14", "Confirm Delivery", "2026-04-07 09:00:00+00:00", None,  None),
    ("e15", "Record Payment",   "2026-04-07 10:00:00+00:00", 150.0, "monetary_unit"),
    ("e16", "Close Order",      "2026-04-07 10:30:00+00:00", None,  None),
    ("e17", "Close Order",      "2026-04-07 10:35:00+00:00", None,  None),
]

events = pd.DataFrame(
    event_rows,
    columns=[
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "amount",
        "amount_unit",
    ],
)
events["ocel:timestamp"] = pd.to_datetime(events["ocel:timestamp"], utc=True)
events["amount"] = pd.to_numeric(events["amount"], errors="coerce")


# ---------------------------------------------------------------------------
# Objects
# ---------------------------------------------------------------------------

objects = pd.DataFrame(
    [
        ("O100", "Order"),
        ("O200", "Order"),
        ("I1",   "Item"),
        ("I2",   "Item"),
        ("I3",   "Item"),
        ("P1",   "Package"),
        ("P2",   "Package"),
        ("D1",   "Delivery"),
        ("D2",   "Delivery"),
        ("V1",   "Invoice"),
        ("M1",   "Payment"),
        ("M2",   "Payment"),
    ],
    columns=["ocel:oid", "ocel:type"],
)


# ---------------------------------------------------------------------------
# Event-to-object relations
#
# "observed" means explicitly stated operational/source involvement.
# "analytically_propagated" means context derived through the stated
# Order/Item/Package/Delivery relationships.
# ---------------------------------------------------------------------------

event_lookup = events.set_index("ocel:eid")
relation_rows = []


def relate(eid, oid, qualifier, relation_origin="observed"):
    """Add an E2O relation while copying authoritative event data."""
    event = event_lookup.loc[eid]
    relation_rows.append(
        {
            "ocel:eid": eid,
            "ocel:activity": event["ocel:activity"],
            "ocel:timestamp": event["ocel:timestamp"],
            "ocel:oid": oid,
            "ocel:type": objects.loc[
                objects["ocel:oid"].eq(oid), "ocel:type"
            ].iloc[0],
            "ocel:qualifier": qualifier,
            "relation_origin": relation_origin,
        }
    )


# e01-e05: order creation and item addition
relate("e01", "O100", "observed:created_order")

relate("e02", "O100", "observed:order")
relate("e02", "I1",   "observed:added_item")

relate("e03", "O100", "observed:order")
relate("e03", "I2",   "observed:added_item")

relate("e04", "O200", "observed:created_order")

relate("e05", "O200", "observed:order")
relate("e05", "I3",   "observed:added_item")

# e06: explicitly shared reservation
relate("e06", "I1",   "observed:reserved_item")
relate("e06", "I3",   "observed:reserved_item")
relate("e06", "O100", "observed:participating_order")
relate("e06", "O200", "observed:participating_order")

# e07: P1 is explicitly packed with I1/I3 and relates to both orders
relate("e07", "P1",   "observed:packed_package")
relate("e07", "I1",   "observed:packed_item")
relate("e07", "I3",   "observed:packed_item")
relate("e07", "O100", "observed:participating_order")
relate("e07", "O200", "observed:participating_order")

# e08: source mentions P2 and I2; O100 is analytically propagated context
relate("e08", "P2",   "observed:packed_package")
relate("e08", "I2",   "observed:packed_item")
relate(
    "e08", "O100", "derived_context:order",
    relation_origin="analytically_propagated"
)

# e09-e10: dispatch source relations plus propagated item/order context
relate("e09", "P1", "observed:dispatched_package")
relate("e09", "D1", "observed:delivery")
for oid in ["I1", "I3"]:
    relate(
        "e09", oid, "derived_context:item",
        relation_origin="analytically_propagated"
    )
for oid in ["O100", "O200"]:
    relate(
        "e09", oid, "derived_context:order",
        relation_origin="analytically_propagated"
    )

relate("e10", "P2", "observed:dispatched_package")
relate("e10", "D2", "observed:delivery")
relate(
    "e10", "I2", "derived_context:item",
    relation_origin="analytically_propagated"
)
relate(
    "e10", "O100", "derived_context:order",
    relation_origin="analytically_propagated"
)

# e11: one invoice explicitly bills both orders
relate("e11", "V1",   "observed:issued_invoice")
relate("e11", "O100", "observed:billed_order")
relate("e11", "O200", "observed:billed_order")

# e12: first payment
relate("e12", "M1", "observed:recorded_payment")
relate("e12", "V1", "observed:settled_invoice")

# e13-e14: confirmation source relation plus propagated logistics context
relate("e13", "D1", "observed:confirmed_delivery")
relate(
    "e13", "P1", "derived_context:package",
    relation_origin="analytically_propagated"
)
for oid in ["I1", "I3"]:
    relate(
        "e13", oid, "derived_context:item",
        relation_origin="analytically_propagated"
    )
for oid in ["O100", "O200"]:
    relate(
        "e13", oid, "derived_context:order",
        relation_origin="analytically_propagated"
    )

relate("e14", "D2", "observed:confirmed_delivery")
relate(
    "e14", "P2", "derived_context:package",
    relation_origin="analytically_propagated"
)
relate(
    "e14", "I2", "derived_context:item",
    relation_origin="analytically_propagated"
)
relate(
    "e14", "O100", "derived_context:order",
    relation_origin="analytically_propagated"
)

# e15: second payment
relate("e15", "M2", "observed:recorded_payment")
relate("e15", "V1", "observed:settled_invoice")

# e16-e17: closures
relate("e16", "O200", "observed:closed_order")
relate("e17", "O100", "observed:closed_order")

relations = pd.DataFrame(
    relation_rows,
    columns=[
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "ocel:oid",
        "ocel:type",
        "ocel:qualifier",
        "relation_origin",
    ],
)
relations["ocel:timestamp"] = pd.to_datetime(
    relations["ocel:timestamp"], utc=True
)


# ---------------------------------------------------------------------------
# Object-to-object relations
# ---------------------------------------------------------------------------

o2o = pd.DataFrame(
    [
        # Order -> Item
        ("O100", "I1",   "contains"),
        ("O100", "I2",   "contains"),
        ("O200", "I3",   "contains"),

        # Package -> Item
        ("P1",   "I1",   "packs"),
        ("P1",   "I3",   "packs"),
        ("P2",   "I2",   "packs"),

        # Delivery -> Package
        ("D1",   "P1",   "carries"),
        ("D2",   "P2",   "carries"),

        # Invoice -> Order
        ("V1",   "O100", "bills"),
        ("V1",   "O200", "bills"),

        # Payment -> Invoice
        ("M1",   "V1",   "partial_settles"),
        ("M2",   "V1",   "completes_settlement"),
    ],
    columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"],
)


# ---------------------------------------------------------------------------
# Referential-integrity and consistency validations
# ---------------------------------------------------------------------------

event_ids = set(events["ocel:eid"])
object_ids = set(objects["ocel:oid"])

assert len(events) == 17
assert len(objects) == 12

assert events["ocel:eid"].is_unique, "Event IDs must be unique."
assert objects["ocel:oid"].is_unique, "Object IDs must be globally unique."

assert set(relations["ocel:eid"]).issubset(event_ids), \
    "Relations contain orphan event IDs."
assert event_ids == set(relations["ocel:eid"]), \
    "Every event should have at least one E2O relation."

assert set(relations["ocel:oid"]).issubset(object_ids), \
    "Relations contain orphan object IDs."
assert (
    set(o2o["ocel:oid"]) | set(o2o["ocel:oid_2"])
).issubset(object_ids), "O2O contains orphan object IDs."

assert events["ocel:timestamp"].dt.tz is not None
assert relations["ocel:timestamp"].dt.tz is not None

event_relation_check = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
    on="ocel:eid",
    how="left",
    suffixes=("_rel", "_event"),
    validate="many_to_one",
)
assert event_relation_check["ocel:activity_rel"].eq(
    event_relation_check["ocel:activity_event"]
).all(), "Relation activities do not match their events."
assert event_relation_check["ocel:timestamp_rel"].eq(
    event_relation_check["ocel:timestamp_event"]
).all(), "Relation timestamps do not match their events."

relation_type_check = relations.merge(
    objects,
    on="ocel:oid",
    how="left",
    suffixes=("_rel", "_object"),
    validate="many_to_one",
)
assert relation_type_check["ocel:type_rel"].eq(
    relation_type_check["ocel:type_object"]
).all(), "Relation object types do not match the object table."

assert not relations.duplicated().any(), \
    "Duplicate relation rows are not allowed."
assert not relations.duplicated(
    subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]
).any(), "Duplicate event-object-qualifier relations are not allowed."
assert not o2o.duplicated().any(), "Duplicate O2O rows are not allowed."
assert not o2o["ocel:oid"].eq(o2o["ocel:oid_2"]).any(), \
    "Self-referential O2O rows are not expected here."

assert relations.loc[
    relations["relation_origin"].eq("observed"), "ocel:qualifier"
].str.startswith("observed:").all()
assert relations.loc[
    relations["relation_origin"].eq("analytically_propagated"),
    "ocel:qualifier"
].str.startswith("derived_context:").all()


# ---------------------------------------------------------------------------
# OCEL construction
# This is the only constructor line that may need a version-specific adapter.
# ---------------------------------------------------------------------------

ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)


# ---------------------------------------------------------------------------
# Basic inspection
# ---------------------------------------------------------------------------

print(ocel)

print("\nEvent-table activity frequencies:")
print(events["ocel:activity"].value_counts().sort_index())

print("\nObject-table type frequencies:")
print(objects["ocel:type"].value_counts().sort_index())

object_types_from_api = pm4py.ocel_get_object_types(ocel)
print("\nObject types returned by pm4py.ocel_get_object_types:")
print(object_types_from_api)

activities_per_object_type = pm4py.ocel_object_type_activities(ocel)
print("\nActivities per object type:")
print(activities_per_object_type)


# ---------------------------------------------------------------------------
# Traditional projections derived from the one OCEL
# ---------------------------------------------------------------------------

flattened_logs = {}
dfgs = {}
log_skeletons = {}

for object_type in ["Order", "Package", "Delivery", "Invoice", "Payment"]:
    flat_log = pm4py.ocel_flattening(ocel, object_type)
    flattened_logs[object_type] = flat_log
    dfgs[object_type] = pm4py.discover_dfg(flat_log)
    log_skeletons[object_type] = pm4py.discover_log_skeleton(flat_log)


# ---------------------------------------------------------------------------
# Object-centric discoveries
# ---------------------------------------------------------------------------

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
oc_petri_net = pm4py.discover_oc_petri_net(ocel)
interactions_summary = pm4py.ocel_objects_interactions_summary(ocel)

# Optional local visualizations; these may require Graphviz/viewer support.
# pm4py.view_ocdfg(ocdfg, format="svg")
# pm4py.view_ocpn(oc_petri_net, format="svg")
```

## 3. Data-model audit

**Objects**

| Object type | Objects | Count |
|---|---|---:|
| Order | O100, O200 | 2 |
| Item | I1, I2, I3 | 3 |
| Package | P1, P2 | 2 |
| Delivery | D1, D2 | 2 |
| Invoice | V1 | 1 |
| Payment | M1, M2 | 2 |

**O2O relations**

| Direction | Qualifier | Cardinality |
|---|---|---:|
| Order  Item | `contains` | 3 |
| Package  Item | `packs` | 3 |
| Delivery  Package | `carries` | 2 |
| Invoice  Order | `bills` | 2 |
| Payment  Invoice | `partial_settles` | 1 |
| Payment  Invoice | `completes_settlement` | 1 |

**Activity-to-object-type incidence**

| Activity | Object types touched | Origin notes |
|---|---|---|
| Create Order | Order | Observed |
| Add Item | Order, Item | Observed |
| Reserve Stock | Order, Item | Explicitly shared/observed |
| Pack Package | Order, Item, Package | O100 on P2 is propagated; P1 order links are explicit |
| Dispatch Package | Order, Item, Package, Delivery | Package/Delivery observed; Order/Item propagated |
| Issue Invoice | Order, Invoice | Observed |
| Record Payment | Invoice, Payment | Observed; no Order allocation |
| Confirm Delivery | Order, Item, Package, Delivery | Delivery observed; other context propagated |
| Close Order | Order | Observed |

The most consequential observed relation set is **e07**, which joins P1, I1, I3, O100, and O200 in one event. It exposes both convergence—two Orders and two Items into one Package—and later divergence into two Order lifecycles. The propagated e09 and e13 relations deliberately carry that bridge into dispatch and delivery confirmation.

The other major convergence point is **e11**: one Invoice V1 is issued for both O100 and O200. Events e12 and e15 then form a one-Invoice-to-many-Payments pattern through M1 and M2.

## 4. Expected flattened behavior

**Order flattening**

- **Approximate traces**
  - O100: Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Dispatch Package  Dispatch Package  Issue Invoice  Confirm Delivery  Confirm Delivery  Close Order.
  - O200: Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order.
- **Copied shared events:** e06, e07, e09, e11, and e13 occur in both Order traces. The e09 and e13 copies arise from explicitly tagged analytical propagation.
- **Omitted aspects:** payment events are absent because M1 and M2 were not allocated directly to either Order. Payment completion before closure therefore is not visible in the Order projection.
- **Likely DFG edges:** Create Order  Add Item, Add Item  Reserve Stock, Reserve Stock  Pack Package, Pack Package  Dispatch Package, Dispatch Package  Issue Invoice, Issue Invoice  Confirm Delivery, and Confirm Delivery  Close Order. O100 additionally creates self-edges such as Pack Package  Pack Package, Dispatch Package  Dispatch Package, and Confirm Delivery  Confirm Delivery.
- **Misleading interpretation:** the projection serializes P1 and P2 work inside O100 and hides that P1 is simultaneously serving O200. Counts of shared activities are duplicated across Order cases. It may also appear that Orders close without payment because payment events are deliberately omitted.

**Package flattening**

- **Approximate traces**
  - P1: Pack Package  Dispatch Package  Confirm Delivery.
  - P2: Pack Package  Dispatch Package  Confirm Delivery.
- **Copied shared events:** no event is related to both P1 and P2, so there is no within-view copying across Package cases.
- **Omitted aspects:** order creation, item addition, reservation, invoicing, payment, and closure are absent.
- **Likely DFG edges:** Pack Package  Dispatch Package and Dispatch Package  Confirm Delivery. The log skeleton will likely treat this sequence as strict because both observed Package traces have the same shape.
- **Misleading interpretation:** P1 and P2 appear behaviorally identical, even though P1 combines I1 and I3 from two different Orders while P2 contains only I2 from O100.

**Delivery flattening**

- **Approximate traces**
  - D1: Dispatch Package  Confirm Delivery.
  - D2: Dispatch Package  Confirm Delivery.
- **Copied shared events:** none between D1 and D2.
- **Omitted aspects:** packing, Package composition, Orders, Items, invoice settlement, and closure are omitted.
- **Likely DFG edge:** Dispatch Package  Confirm Delivery.
- **Misleading interpretation:** the projection supports transit-time analysis but hides that D1 carries P1, which consolidates items from O100 and O200. With only two traces, any log-skeleton rule will be based on very little evidence.

**Invoice flattening**

- **Approximate trace**
  - V1: Issue Invoice  Record Payment  Record Payment.
- **Copied shared events:** there is only one Invoice case, so e11 is not copied within this view, despite being related to two Orders.
- **Omitted aspects:** Order creation, logistics, delivery confirmation, and Order closure are not part of the V1 trace.
- **Likely DFG edges:** Issue Invoice  Record Payment and Record Payment  Record Payment.
- **Misleading interpretation:** one trace can make two installments look like a universally mandatory payment pattern. The amounts 100 and 150 remain event attributes, but this view cannot allocate them between O100 and O200.

**Why Payment flattening is weak**

M1 and M2 each have only one directly related event: Record Payment. Thus both Payment traces are single-event traces, yielding no meaningful DFG edges and almost no lifecycle constraints. O2O links to V1 do not automatically make Issue Invoice or the other payment part of each Payment trace. Furthermore, the distinction between `partial_settles` and `completes_settlement` is an O2O qualifier, not a different event activity.

## 5. Expected object-centric structures

- **OC-DFG:** It should retain activity flow by object type without selecting one universal case notion. P1 exposes the convergence of I1 from O100 and I3 from O200 at Pack Package. V1 similarly converges O100 and O200 at Issue Invoice, after which M1 and M2 interact with the same Invoice through two Record Payment events. Since payments are not directly allocated to Orders, the Order-specific DFG component should not contain Record Payment.

- **OTG:** The canonical type-level relationships should include Order–Item, Item–Package, Package–Delivery, Order–Invoice, and Invoice–Payment. The enriched relations also support Order–Package, Order–Delivery, Item–Delivery, and related contextual edges. Depending on whether the implementation represents same-type interactions, shared events involving O100 and O200 or I1 and I3 may also induce same-type links.

- **ET–OT graph:** Expected activity/type incidences include Pack Package with Order, Item, and Package; Dispatch Package and Confirm Delivery with Order, Item, Package, and Delivery; Issue Invoice with Order and Invoice; and Record Payment with Invoice and Payment. This graph makes the modeling policy especially visible because analytically propagated relations enlarge the set of types associated with logistics activities.

- **Object-centric Petri net:** The discovered model should contain synchronized behavior around Reserve Stock, Pack Package, Issue Invoice, and Record Payment. P1 creates a multi-object synchronization involving O100, O200, I1, and I3. V1 synchronizes with O100 and O200 when issued and later with M1 and M2 during settlement. The exact places, silent transitions, and synchronization structure are discovery-algorithm outcomes; this small OCEL does not determine one unique object-centric Petri-net interpretation.

- **Object-interactions summary:** Event co-occurrence should show P1 interacting with I1, I3, O100, and O200, and D1 interacting with P1 and its propagated context. V1 interacts with O100 and O200 at e11, with M1 at e12, and with M2 at e15. M1 and M2 do not directly co-occur; they are connected indirectly through V1. O100 and O200 repeatedly interact at the shared reservation, P1 packaging, propagated P1 logistics, and invoice issuance.

## 6. Modeling alternatives

1. **Source-minimal relations**
   - Keep only explicitly mentioned event participants. Dispatch events would relate only to a Package and Delivery; confirmation events only to a Delivery. P2 packing would not relate directly to O100.
   - Order traces would omit most downstream logistics. OTG and ET–OT results would be sparser, but source provenance would be strongest.

2. **Full operational involvement**
   - Relate every downstream logistics and financial event to every reachable Order and Item. For example, both payment events could be linked to O100 and O200 through V1.
   - Order traces would include both Record Payment events, and object-centric models would show stronger Order–Payment synchronization. However, each payment amount could be double-counted when flattened by Order, and the relations could wrongly suggest a known allocation.

3. **O2O-propagated analytical relations**
   - Store only source-minimal E2O relations in the canonical OCEL and derive contextual E2O rows on demand by traversing O2O paths.
   - Discovery results can match the rich model when propagation is materialized before discovery, while the source layer remains clean. The propagation depth and allowed qualifier paths must be documented because PM4Py flattening does not generally infer arbitrary O2O transitive participation automatically.

4. **Lifecycle-owner policy**
   - Relate events only to the object whose lifecycle state changes and to indispensable transaction objects. For example, Dispatch Package could be attached primarily to P1/P2 and Confirm Delivery primarily to D1/D2.
   - This yields clean per-type lifecycles but weakens cross-object synchronization and makes Order-centric downstream behavior depend almost entirely on O2O navigation.

All four policies can describe the same business facts; they differ in what is asserted as direct event participation and therefore in what discovery algorithms can observe.

## 7. Failure modes

1. **Relation inflation:** propagating every event through every reachable O2O path can create very dense relation sets, inflated activity counts in flattened logs, and spurious type interactions.

2. **Missing direct E2O links:** PM4Py flattening generally follows direct E2O relations, not arbitrary O2O paths. A source-minimal model may therefore omit operationally relevant events from Order, Item, or Package projections.

3. **Treating propagation as observation:** without `relation_origin` or qualifier prefixes, analysts may believe that a source system explicitly recorded O100 on a delivery confirmation when that relationship was derived through D1  P1  I1  O100.

4. **Duplicate shared events after flattening:** e06, e07, e09, e11, and e13 are copied into both Order cases. Summing flattened event counts as though they were unique business occurrences would overcount work.

5. **Ambiguous payment allocation:** V1 bills two Orders, but the narrative does not say how the amounts 100 and 150 are allocated. Directly attaching both amounts to both Orders would imply unsupported allocation and potentially double-count 500 monetary units instead of 250.

6. **Overly short Payment traces:** each Payment has one Record Payment event. Payment flattening cannot reveal invoice issuance, installment ordering, or settlement completion unless additional E2O relations or lifecycle events are modeled.

7. **Constructor/API version mismatch:** older PM4Py versions may use another OCEL constructor signature, import location, visualization name, or discovery return format. An adapter should change only the isolated API call, not object IDs, qualifiers, directions, or relations.

8. **False total order for same-time events:** sorting timestamp ties by row position or event ID invents precedence. This example has no ties, but a generalized pipeline must not interpret an arbitrary tie-break as causal order.

9. **Activity/timestamp drift in relations:** manually repeating activity and timestamp values can introduce inconsistencies between `events` and `relations`. The merge-based validation guards against this.

10. **Orphans or type drift:** a misspelled object ID or a relation declaring P1 as a Delivery would compromise referential integrity and type-specific discovery.

11. **O2O direction reversal:** storing Item  Package with qualifier `packs`, or Invoice  Payment with `partial_settles`, would invert the intended grammar and confuse directional traversals.

12. **Overfitting from tiny samples:** the Package and Delivery logs each contain only two traces, and the Invoice log only one. DFGs are descriptive, while log-skeleton constraints may look much stronger than the available evidence warrants.

## 8. Final semantic checks

A reviewer can manually verify that:

1. The event table contains exactly 17 unique event IDs and all timestamps are UTC-aware.
2. The object table contains exactly O100, O200, I1, I2, I3, P1, P2, D1, D2, V1, M1, and M2.
3. O100 has `contains` links to I1 and I2, while O200 has a `contains` link to I3.
4. P1 has `packs` links to I1 and I3, proving that it combines Items from different Orders; P2 packs only I2.
5. D1 carries P1 and D2 carries P2.
6. V1 bills both O100 and O200.
