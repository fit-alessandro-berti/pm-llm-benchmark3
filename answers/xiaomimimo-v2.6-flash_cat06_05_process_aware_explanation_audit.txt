## 2. Process-model consistency checks

I propose a suite ("PTEX") of nine checks, run as CI gates on every feature-store registration and on every explanation pack. Each check states its pass criterion and, importantly, its limitation.

**T1 — Prefix-replay ground-truth diff (lineage).**
Build `prefix_snapshot(t0, case)` by replaying the raw event log with `event_time  t0` under a documented tie-break rule, and separately build each business feature (queue table, document store, assignment table) with its own as-of join. Diff `f_joined` against `f_replay` for every feature used at `t0`.
*Pass:* zero unexplained mismatches.
*Catches:* `final_handler_team`, `prior_claim_count`, `same_day_document_count`, `risk_score_current`, `employee_experience`.
*Limitation:* the replay is only as good as log completeness and the tie-break; features sourced from systems absent from the event log (queue table) need their own as-of reconstruction, and a wrong-but-consistent source will not be caught.

**T2 — Feature-store admission contract (static).**
Every feature definition must carry `available_at_expression`, `as_of_column`, `event_time`, `source_query_hash`, `prefix_monotone  {true,false}`, `reads_full_trace  {true,false}`. CI rejects training jobs where metadata is missing or `reads_full_trace = true`.
*Catches:* all complete-trace features at authoring time, before they reach a leaderboard.
*Limitation:* metadata can be *declared* incorrectly — hence T1 as the empirical counterpart. Static checks catch intent; replay catches reality.

**T3 — Prefix-suffix independence test (leakage detector).**
Truncate each trace at increasing prefix lengths `k`; recompute every feature. Classify: *value changes under truncation and not declared `prefix_monotone`*  leakage; *importance collapses as `k  t0`*  future-dependent.
*Catches:* `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, `last_resource_role`.
*Limitation:* some features legitimately grow (`elapsed_since_registration_at_t0`), so equality is the wrong criterion for monotone features — this is why the `prefix_monotone` declaration exists.

**T4 — Activity-order feasibility: DFG × declarative constraints.**
Two artefacts with deliberately different roles:
- **DFG (mined)** — empirical directly-follows graph. Used to detect *implausible explanations* (a pattern the log never shows) and to detect *implausible logs* (a DFG edge that violates a norm). A DFG edge is **evidence, not a rule**; an observed `Claim Closed  Damage Assessment` may be an artifact of missing timestamps, and a genuinely waived norm will still be absent from the DFG.
- **Declarative constraints (normative)** — precedence/response/existence with co-binding parameters, e.g. `[Damage Assessment]*  [Settlement Decision]`; `Appeal` only if immediately preceded by a decision whose outcome  {Partial, Deny}; `[Appeal]  [Settlement Decision]` (response); `[Settlement Decision*]  [Claim Closed]` only after a *final* decision; `Documents Received` after `Documents Requested` with a second request permitted only after `Documents Validated`; `Fraud Investigation` after a trigger with no precedence over assessment.
Every emitted pattern gets a three-way verdict: **enabled at `t0` / future-possible at `t0` / impossible**. Only "enabled at `t0`" or "prefix history" may appear in a `t0` explanation.
*Result:* S1 `Claim Closed  Damage Assessment` = impossible; S2 `Appeal  Decision` = future-possible (edge legal, information not); S4 `Coverage Check  Fraud` = enabled (information not); S5 = future-possible.
*Limitation:* Declare constraints are brittle to label granularity — the coarse `Settlement Decision Recorded` hides outcome, so `Appeal` cannot be co-bound without an outcome attribute; waivers/overrides produce false violations; alignment checking itself is ambiguous when several alignments tie on cost, and same-timestamp events generate multiple valid alignments, so alignment "fitness" must be reported as a *range*, not a scalar.

**T5 — Same-timestamp ambiguity gate.**
Compute `p0 = P(t = 0  sequence_index missing)` for adjacent pairs, overall and per activity pair. If `p0` exceeds a threshold for any pair used by an ordering-dependent feature or pattern, quarantine that explainer. Additionally, for each ordered pair, count *both* observed orderings; if both occur, the edge is non-discriminative and must be dropped regardless of normativity.
*Tie-break ladder:* source-system sequence index  transaction/audit id  ingestion log offset  declare unorderable. Do **not** fall back to name/alphabetical ordering.
*Limitation:* a sequence index generated by batch ingestion can itself be wrong; verify against an independent source for at least a sample.

**T6 — Enabled-set (token-game) admissibility check for local explanations.**
Compute the process-model state after `Coverage Check Completed`. Enabled: `Damage Assessment Completed`, `Documents Requested`, `Fraud Investigation Opened` (if a trigger flag exists). Future-reachable but not enabled: `Documents Received/Validated`, `Settlement Decision Recorded`, `Appeal`, `Claim Closed`, a second `Settlement Decision`, `Claim Closed  Damage Assessment`.
**Admissibility rule:** a local explanation may reference (i) events in the prefix history, (ii) features derived only from the prefix, (iii) state descriptors of *enabled* activities. Anything referencing future-reachable or impossible activities  fail, with the offending feature named.
*Applied here:* this single test fails X (`appeal_seen_anywhere`, `final_decision`), Y (`full_trace_variant_id`), Z (pattern, `last_resource_role`).
*Limitation:* the enabled set comes from an idealised model; real processes contain waivers. Record deviations as warnings for the process owner rather than hard-failing, or the suite loses credibility.

**T7 — Repeated-decision semantics tests.**
Synthetic fixtures: (a) `DEC(partial)  APPEAL  DEC(approve)` must yield `num_settlement_decisions = 2`, `num_appeals = 1`, a distinct variant (`…DEC-APP-DEC…`), and must **not** be flagged as a violation; (b) two `Settlement Decision` events **without** an intervening appeal must be flagged as an out-of-model path (mislabelling or a genuine exception); (c) dedup/join logic must not collapse the second decision; (d) the label counter must not be used as a `t0` feature (at `t0` it is necessarily 0).
*Purpose:* distinguishes "repeated coarse label after appeal = legitimate" from "repeated label without appeal = defect", which is exactly the distinction S1/S2 demand.
*Limitation:* requires an outcome attribute on decisions to co-bind `Appeal`; without it, (a) and (b) are indistinguishable.

**T8 — Explanation stability and sanity.**
Bootstrap refits; Spearman rank correlation of feature importances across resamples and across rolling time windows; per-case sign stability of the top-5 drivers; additivity check (SHAP values sum to model output **against a prefix-only background**); monotonicity sanity (more elapsed time  less slack  monotone effect; queue length direction plausible); detection of base-value jumps after feature removal.
*Catches:* the contaminated bases shown for X/Y/Z; unstable `calendar_week`.
*Limitation:* SHAP distributes credit arbitrarily among correlated features — importance shifts after a removal are **not** evidence of improvement, they may simply be credit migrating to a substitute. Use grouped/conditional SHAP and report group-level, not feature-level, importance when correlation is high.

**T9 — Fairness/proxy gate.**
For each sensitive or sensitive-correlated feature: proxy strength (AUC when randomized vs. removed), group-level mean |SHAP| disparity across region/language/channel, subgroup calibration (ECE per group), and downstream impact if the score is used to allocate handling effort.
*Limitation:* fairness criteria conflict; choose per use-case and document. A feature can pass predictive validation and still fail this gate.

## 3. Alternative feature interpretations

### The four standards (these are not interchangeable)

| Standard | What it requires | What it does **not** permit |
|---|---|---|
| **Predictive validity** | Available at `t0`, stable/auditable lineage, out-of-time lift, calibrated. Correlation with sensitive attributes is *acceptable here*. | Being re-labelled as a cause or a lever. |
| **Causal interpretation** | Identification (RCT, IV, diff-in-diff, explicit do-calculus assumptions) plus sensitivity analysis. **None of the current features satisfies this.** | Any use of "causes", "determines", "driver" driven by SHAP rank alone. |
| **Operational actionability** | (a) the variable is *modifiable by the operations team*, (b) a causal effect is established, (c) effect size is material, (d) no gaming/displacement or feedback harm. | Treating queue length as a proven lever without a study; treating region, complexity, channel or calendar week as levers at all. |
| **Fairness review** | Group impact, proxy strength, subgroup calibration, and review of how the score is *used*. | Deleting a proxy by reflex — or keeping it silently. |

### Class A — Defensible predictive signal (keep; association only)

| Feature | May claim | May **not** claim |
|---|---|---|
| `initial_damage_complexity` | "High complexity, recorded at registration, is associated with longer handling in this data." | That complexity *causes* breach, or that changing the score would change outcomes. It is a claim attribute, not a lever. |
| `elapsed_since_registration_at_t0` | "1.2 h of the 10-day budget consumed; most slack remains." | That already-old claims are intrinsically harder — the dominant effect is definitional slack, and separating the two needs a study. |
| `initial_reserve` (once frozen-at-registration is proven) | "Larger reserves are associated with longer handling." | That reserve drives delay; it is an assessor judgement partly endogenous with complexity. |
| `prefix_variant_id` (replacement for `full_trace_variant_id`) | "The observed prefix is `REG-COV`, the standard entry path." | Any statement about the path *beyond* `t0`. Expect near-zero importance — that is correct, not a bug. |
| `prior_claim_count_before_t0` (after SQL repair) | "Higher prior claim frequency is associated with slightly higher risk." | Causal or complexity language; it is also Class C. |

### Class B — Process-state / congestion signal (keep; the most operationally meaningful class)

| Feature | May claim | May **not** claim |
|---|---|---|
| `queue_length_at_t0` | "Claims arriving into a queue of 18 items in this data settle later than those arriving into a queue of 4." | "Congestion increases risk" as an **actionable** reason. Reducing the queue may well help, but that requires a causal evaluation (randomised dispatch, natural experiment, IV) — this is the strongest actionability *candidate* in the pack, not a proven lever. |
| `documents_in_hand_at_t0`, `open_request_at_t0` (prefix replacements for `num_document_requests_total` and the S3 pattern) | "Paperwork already present at `t0` is associated with fewer evidence cycles and lower risk." | Any count of *future* rework. |
| `fraud_investigation_open_at_t0` / `fraud_trigger_flag_at_t0` (replacement for S4) | "An open fraud flag at `t0` is associated with longer handling, as expected given parallel investigation." | "Fraud investigation causes breach" — parallel work may extend elapsed time without being wasteful; and the flag is Class C for fairness. |
| `handler_team_at_t0`, `current_resource_role_at_t0` (replacements for `final_handler_team`, `last_resource_role`) | "Claims assigned to team X at `t0` in this data settle later." | "The final team determines delay" — this is the clearest reverse-causality error in the pack: delay causes reassignment, not the converse. ### Class C — Proxy requiring fairness/robustness review (keep *only* after review; never as a "driver")

- **`claimant_region`** — available and predictive, but correlated with repair-network coverage, language, channel and socioeconomic characteristics. *Do not delete reflexively.* Instead: (i) measure proxy strength and group-level attribution disparity; (ii) test substitution with the **operational mediators** (distance to network garage, language-support availability) — these are less sensitive, often more actionable, and may absorb the effect; (iii) if retained, the explanation must say "associated with", must never say "region is a delay driver", and region must never be used to *deprioritise* claims.
- **`claimant_channel`** — same treatment; check product-mix confounding first.
- **`risk_score_current`** (after as-of repair) — audit component attribution; composite scores routinely embed region and behaviour terms, laundering proxies through a single number.
- **`initial_reserve`** — correlates with regional repair costs; review alongside region.
- **`prior_claim_count_before_t0`** — repeat-claimant frequency is a socioeconomic proxy.
- **Fraud trigger/flag** — sensitive; high false-positive disparity risk across language and region groups.

### Class D — Drift / calendar proxy (keep with regime versioning; extrapolation forbidden)

- **`calendar_week`** — available at `t0`, but confounded with a policy change, a holiday period and possibly a target-definition change. *May claim:* "In weeks with holiday coverage during this policy regime, breach rates were higher." *May not claim:* "certain weeks are operationally worse" as a general fact, or any prediction across a regime boundary without re-validation. Recommend encoding `policy_regime` + `holiday_coverage_flag` rather than raw week numbers.

## 5. Recommendations for explanation validation

### P0 — Stop the bleeding (immediate)
1. **Freeze the current explanation pack.** Do not ship the global SHAP table or the pattern list to operations or claimants. Re-label them "offline process-mining findings" if they are to be kept at all.
2. **Feature-store admission contract.** Every feature must carry `available_at`, `event_time`, `as_of_rule`, `source_query_hash`, `prefix_monotone`, `reads_full_trace`. Training jobs fail CI if metadata is missing or `reads_full_trace = true`.
3. **Prefix-replay harness as ground truth.** Build `prefix_snapshot(t0)` by replaying the log with `event_time  t0` plus a documented tie-break, and automatically diff every joined feature against it. This single test catches 5 of the defects found here.
4. **Fix the known SQL lineage defects now:** `prior_claim_count` window  `< t0`; document count  `event_time  t0`; handler team  assignment as-of `t0`; employee experience  as-of event time; risk score  as-of `t0`. Add a query-lint rule banning `<= extraction_date` in model features.

### P1 — Rebuild and re-verify (weeks)
5. **Rebuild the feature set**, not the explanation text: permanently inadmissible (`total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, `last_resource_role`) are removed; their prefix analogues are added where non-constant (`prefix_variant_id`, `documents_in_hand_at_t0`, `handler_team_at_t0`, `current_resource_role_at_t0`, `fraud_open_at_t0`, `policy_regime`).
6. **Recalibrate after feature removal.** Expect a material performance drop and report it honestly. Gate on reliability diagram, Brier, ECE and out-of-time AUC — **and check subgroup calibration by region/channel/week**, because removing a feature can leave global calibration intact while worsening it for a segment.
7. **Process-conformance suite in CI** (T1–T7): declarative constraint check on every emitted pattern; enabled-set admissibility check on every local explanation; t=0 ambiguity gate; prefix-suffix independence test; repeated-decision semantics fixtures.
8. **Explanation validation** (T8): prefix-only background for the SHAP base; additivity check; bootstrap rank-stability of feature importance; per-case driver sign stability; monotonicity sanity for slack and queue; automatic warning when a top driver is flagged proxy or drift. Publish the *post-repair* ranking — do not hand-edit the existing one, since removing a feature redistributes credit to correlated substitutes.

### P2 — Fairness, causality and actionability governance
9. **Proxy/fairness analysis** for `claimant_region`, `claimant_channel`, `initial_reserve`, `risk_score`, `prior_claim_count`, fraud flags: proxy strength (AUC when randomized), group-level attribution disparity, subgroup calibration, and downstream impact. Decide *retain-with-review* / *substitute* (region  network coverage + language support) / *remove*, and document the rationale. The default must not be reflexive deletion — nor silent retention.
10. **Four-tier evidence label on every explanation:** (a) availability at `t0` (with `available_at` shown), (b) evidence type — prefix observation / congestion state / conformance-derived, (c) causal status — *none*, observational, unless a study is attached, (d) actionability — is it a lever, and what study would be needed. Ban "causes", "determines", "driver" absent an identified causal effect; this alone would have invalidated ranks 2, 3, 9 and all five pattern narratives.
11. **Feedback-loop / impact review before deployment.** If the score is used to prioritise handling, high-score claims may be expedited (suppressing the very breaches we predict) or deprioritised (harming claimants, and disproportionately in proxy-protected groups). Run a pre-deployment impact assessment and monitor for performative drift.

### P3 — Continuous monitoring
12. **Schema/lineage drift:** column-level lineage diff per release, completeness of availability metadata, alert on any change to a feature's `available_at` semantics or SQL template version.
13. **Process drift:** rolling DFG and variant drift (edges appearing/disappearing), t=0 rate, missing-sequence-index rate, violations against the declarative constraint set, appearance of new activities or decision types, and explicit detection of operating-policy changes (which must trigger a `policy_regime` bump and out-of-time revalidation).
14. **Concept and target drift:** PSI on score and key features, calibration by week and segment, breach-rate base-rate shifts, and — critically — **target-definition changes** across policy regimes, since a changed 10-day definition would silently invalidate the label.
15. **Explanation drift:** rolling rank correlation of feature importance, per-case driver sign flips, alert when a feature enters or leaves the top-k unexpectedly or when a proxy's importance grows.
16. **Separate the two artefacts permanently:** an *offline process-mining report* (full-trace patterns allowed, explicitly labelled as post-hoc, no `t0` claims) and a *decision-time explanation* (prefix-only, with an attached auto-generated admissibility report listing each feature's `available_at`, evidence type, causal status and fairness status).
