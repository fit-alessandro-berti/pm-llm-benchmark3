## 1. Duplicate-handling decision tree

The tree is evaluated per candidate group (same `activity` + same second-resolution `timestamp`). No step automatically drops or merges; every terminal explicitly states the OCEL operation.

```
START: Candidate group (activity + timestamp equality)

1. Exact technical duplicate?
   Same source, same source_event_key, same payload_hash & timestamp & activity (+ same E2O objects)
    YES: Proven re-ingestion. Terminal A: DROP duplicate, keep earliest ingested as canonical.
    NO  2

2. Same physical business event observed by multiple sources? [Verified only]
   Criterion: external reconciliation OR same source_seq causality + same physical object instances 
             e.g. e03/e04 reconciliation report, complementary payloads (WMS location enrichment).
             Requires positive evidence, not just same label+time.
    YES, evidence strong: Terminal B: MERGE attributes and relations into canonical eid, keep loser as alternate source.
    NO  3

3. Summary / derived status update from detailed event? [Abstraction level]
   Criterion: different source lineage (WMSERP message ER-150, PSPERP ER-201), 
             less granular payload h-pack-summary vs h-pack-detail, no new object state change,
             source generation rule documented.
    YES: Terminal C: RETAIN BOTH with refined labels/qualifiers (e.g. Pack Package [WMS-detail] vs Pack Package [ERP-status]).
           Never merge across abstraction levels in conservative mode. Merge only in evidence-based variant with attribute provenance.
    NO  4

4. Harmonization collision? [Semantic distinct source activities mapped to one label]
   Criterion: original_activity / payload semantics differ despite harmonized label.
             e08 W-79 'released from warehouse' vs e09 C-400 'accepted by carrier' both  Dispatch Package.
    YES: Terminal D: RETAIN BOTH with refined labels (Release from Warehouse, Accept by Carrier) + restore original_activity.
           Counts as semantic fix, not deduplication.
    NO  5

5. Concurrent same-label events on different object instances?
   Criterion: Same activity+timestamp but disjoint mandatory object instances (e03 I1 vs e05 I2, e13 M1 vs e14 M2).
             Distinct payload_hash and different source_seq within same source.
    YES: Terminal E: RETAIN BOTH UNCHANGED (or with micro-order only). Same time is legitimate concurrency.
           Require object-disjointness test before considering duplicate.
    NO  6

6. Unresolved candidate (same objects, no evidence, no lineage, no semantic difference)
     Terminal F: QUARANTINE FOR REVIEW. Retain both, add qualifier [to_review], add deterministic order, log in audit table.
       Do NOT drop/merge.
```

Terminal summary:

* **A - drop:** only exact technical duplicates.
* **B - merge attributes and relations:** verified same physical event.
* **C/D - retain both with refined labels:** summary/derived and harmonization collision. Preserves semantics.
* **E - retain both unchanged:** concurrency.
* **F - quarantine:** insufficient evidence.

Conservative principle: Default to **E / C / D / F**. Only A and B with strong evidence cause row reduction.

## 3. Timestamp-tie ordering rules

### Policy: Semantic ordering before deterministic tie-breaking

We distinguish **semantic rules** (evidence about business order) from **deterministic rules** (arbitrary but reproducible total order for analysis tools).

**Semantic (must precede any synthetic time shift):**
1. **Domain constraints:** e.g., Release  Accept  Handover; Pack requires Picks completed. Source fact 10: Carrier handover after acceptance.
2. **Within-source sequence:** `source_seq` is authoritative within one system for business causal order when domain confirms (e09 seq1 < e10 seq2; e12 seq400 < e13 seq401 < e14 seq402). Not comparable across sources.
3. **Lifecycle constraints on shared objects:** Object-type lifecycles: Order CreatedValidated; Item PickedPacked; Payment AuthorizedCaptured. e12 Authorize M1 must precede e13 Capture M1.
4. **Source-specific semantics / derivation:** Detailed event precedes its derived status summary (WMS W-77/W-78 before ERP ER-150 that was generated *from* WMS message). Even if timestamps equal, causal direction is known.

**Deterministic (only to produce total order for flattening, sorting):**
5. **Source precedence for remaining ties:** Fixed ranking e.g. WMS > SCANNER > CARRIER > ERP > BILLING > PSP for display only; logged as non-semantic.
6. **Ingestion time:** `ingested_at` is *technical*, never primary. Used only as weak tie-breaker within same source if domain silent, with warning.
7. **Stable fallback:** `eid` lexicographic / canonical index. Guarantees reproducibility.

Deterministic rules must be marked `is_semantic=false` in audit so analysts know not to interpret order as true physical order.

### Why adding microseconds *first* encodes a false story

If you call `ocel_add_index_based_timedelta` before resolving semantic order, the arbitrary row order (often ingestion or file order) becomes baked into `event_timestamp` at microsecond resolution. Downstream miners then *measure* durations like `Dispatch 0.001s  Dispatch 0.002s` and DFG discovery counts precedence evidence that never existed. Duration, performance, and apparent “rework within 2 microseconds” become artifacts of code, not business. Original second-precision timestamp must be preserved as `original_timestamp`; synthetic `adjusted_timestamp` is added **after** the semantic partial order is fixed and documented as deterministic, not factual. Otherwise you turn legitimate concurrency into a strict sequence and falsely prove order where there was tie/knowledge gap.

## 4. Conservative cleaning pipeline

**Principle:** Minimum-change, preserve-meaning, fix labels.

1. **Preserve:** Copy `event_timestamp  original_timestamp`, `activity  original_activity`, keep `source`, `source_event_key`, `payload_hash`, `ingested_at`.
2. **Verified merges only:** Merge e03+e04 into canonical e03; merge e11+e16 into canonical e11 via custom verified-pair function (attribute authority map). No other row removal.
3. **Refine without deleting:** Rename harmonization collisions: e08`Dispatch Package [WMS-release]`, e09`Dispatch Package [Carrier-accept]`, e10`Handover to Carrier` refined, e06/e07 qualified, e15 qualified `Capture Payment [ERP-summary]`. Keeps 1:1 event count but fixes semantics.
4. **Deterministic ordering without deleting concurrency:** Define `order_key` using semantic rank, then `ocel_sort_by_additional_column`, then `ocel_add_index_based_timedelta` (1ms steps) to create `adjusted_timestamp` while `original_timestamp` unchanged. Concurrency is remembered via `is_concurrent_group` flag and same `semantic_rank`.
5. **Store provenance:** Audit table per §8.

**Retained event count:** Raw 17  **15 events** (2 verified merges). E2O relation count drops by at most 1 duplicate edge (if e03/e04 relations identical). No object-instance loss. Order-flattened DFG retains all legitimate edges; only Pick rework artifact removed. This is the baseline for evaluation; any further reduction must justify semantic cost.

## 5. Aggressive alternatives

### 5A. Evidence-based semantic merging

*Merge abstraction levels where lineage is documented, but keep distinct objects separate.*

* **Actions:** Same as conservative *plus* merge e06/e07 into single `Pack Package` canonical e06 (WMS authoritative, ERP `is_derived` annotation), and optionally attach e15 summary attributes to payment captures (e13e15 for M1, e14 independent). e08/e09 still split (not merged – semantics differ). Verified pairs + derivation merges.
* **Retained:** 17  **14 events** (e03/e04, e11/e16, e06/e07).
* **Most likely semantic damage:** Loses abstraction-level distinction. Analysts can no longer measure WMS execution lag vs ERP posting lag (10:00:05 vs 10:01:00), and ET-OT weight for ERP `Pack Package` disappears. Performance analysis underestimates system latency. If e15 attached, ERP modeling deficit (no M1 link) is hidden.

Still safe for e13/e14: kept separate.

### 5B. Mechanically aggressive PM4Py merging

*Apply PM4Py duplicate functions globally on activity+timestamp groups.*

Example: `pm4py.ocel_drop_duplicates(ocel, have_common_object=True)` or `ocel_merge_duplicates` without inspecting candidate groups; `have_common_object=False` would be even more aggressive.

* **Actions:** Group by `activity`+`timestamp` (second). Within each group keep one event, drop/merge rest if they share any object. No distinction of object instances, abstraction, or harmonization.
* **Retained:** 17  **10–11 events.** Typical collapse:
  * Pick group e03/e04/e05 (31) **drops e05** – violates constraint.
  * Pack group e06/e07 (21)
  * Dispatch group e08/e09 (21) – erases harmonization collision.
  * Invoice group e11/e16 (21)
  * Capture group e13/e14/e15 (31) – collapses distinct payments.
* **Semantic damage:** 
  * Collapsing distinct partial payments (m1 vs m2) into one capture – financial audit fails, Payment-flattened DFG loses parallel branches.
  * Converting abstraction-level status updates into false rework elimination – hides system lag, creates false instantaneous Pack.
  * Unioning incompatible E2O relations: merged Capture would spuriously link M1+M2+I/V into one event, inventing `Captures 2 payments at once` pattern and corrupting OT weights.
  * Item-flattened DFG loses `Pick I2` node.

**Why `have_common_object=True` does not protect e13/e14:** The check asks “do events share *any* object?” e13{O1,V1,M1}, e14{O1,V1,M2}. They share O1 and V1 (Order and Invoice) even though they differ on the distinguishing object Payment. The library sees common O1/V1 and treats them as duplicates of the same Capture at same time. It has no notion that Payment is the *qualifying* object for this activity. Protection requires `object-disjointness on the activity’s mandatory object type` (here Payment), not existence of any common object. Without that, partial payments are merged.

```python
verified_pairs_cons = [("e03","e04"), ("e11","e16")]
authority_map = {"e11": {"amount":"ERP", "tax_breakdown":"BILLING"}}
ocel_cons, audit_verified_cons = merge_verified_pairs(ocel_cons, verified_pairs_cons, {}, authority_map)

# 1c) Refine harmonized/abstraction labels without dropping
refine = {
    "e08": "Dispatch Package [WMS-release]",
    "e09": "Dispatch Package [Carrier-accept]",
    "e06": "Pack Package [WMS-execution]",
    "e07": "Pack Package [ERP-status]",
    "e15": "Capture Payment [ERP-summary]"
}
ocel_cons.events.loc[ocel_cons.events["eid"].isin(refine.keys()), "activity"] = \
    ocel_cons.events.loc[ocel_cons.events["eid"].isin(refine.keys()), "eid"].map(refine)

# 1d) Provenance columns for ordering
ocel_cons.events["original_timestamp_preserved"] = ocel_cons.events["original_timestamp"]
# semantic rank: domain + source_seq based (manual for demo, in production derive from rules)
semantic_rank_map = {
    "e01":0,"e02":1,
    "e03":2,"e05":2, # concurrent picks same rank
    "e06":3,"e07":4,
    "e08":5,"e09":6,"e10":7,
    "e11":8,"e12":8,"e13":9,"e14":9,"e15":10,"e17":11
}
ocel_cons.events["semantic_rank"] = ocel_cons.events["eid"].map(semantic_rank_map)
# add source_seq as secondary for deterministic within-source order
ocel_cons.events["order_key"] = ocel_cons.events["semantic_rank"]*1000 + ocel_cons.events["source_seq"].fillna(0)

# 1e) Deterministic ordering: sort then add timedelta ONLY AFTER order is set
ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, "order_key")
# keeps original_timestamp intact, creates adjusted_timestamp with 1ms steps
ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons, delta=pd.Timedelta("1ms"), 
                                                 timestamp_column="event_timestamp",
                                                 original_timestamp_column="original_timestamp")
# flag semantic vs deterministic
ocel_cons.events["is_semantic_order"] = ocel_cons.events["eid"].isin(["e08","e09","e10","e12","e13"])

# validate
assert set(ocel_cons.relations["ocel:eid"]).issubset(set(ocel_cons.events["eid"]))
print(f"Conservative: {len(ocel_raw.events)} -> {len(ocel_cons.events)} events")

# ========== SCENARIO 2: Evidence-based semantic merge (aggressive but reasoned) ==========
ocel_ev = copy.deepcopy(ocel_cons) # start from conservative
# additionally merge e06/e07 pack levels
ocel_ev, audit_pack = merge_verified_pairs(ocel_ev, [("e06","e07")], {}, None)
# annotate e15 as derived summary linked to payments rather than separate event (keep but flag)
ocel_ev.events.loc[ocel_ev.events["eid"]=="e15", "is_derived_summary"] = True
print(f"Evidence-based: {len(ocel_ev.events)} events")

# ========== SCENARIO 3: Mechanically aggressive library merge (DEMONSTRATION ONLY - WARNING) ==========
# WARNING: This globally collapses distinct objects and harmonization collisions. Do NOT use for reporting.
ocel_agg = copy.deepcopy(ocel_raw)
ocel_agg.events["original_timestamp"] = ocel_agg.events["event_timestamp"]
# Example of dangerous blanket call: groups by activity+timestamp, keeps one if any common object
# This WILL incorrectly drop e05 and collapse e13/e14.
ocel_agg_dropped = pm4py.ocel_drop_duplicates(ocel_agg, have_common_object=True)  # JUSTIFIED SCENARIO DEMO with check above
# Separate aggressive merge (different function) on copy
ocel_agg2 = copy.deepcopy(ocel_raw)
ocel_agg_merged = pm4py.ocel_merge_duplicates(ocel_agg2, have_common_object=True)  # WARNING: unions E2O incorrectly
# Both need re-sorting afterwards, but damage already done
ocel_agg_merged = pm4py.ocel_sort_by_additional_column(ocel_agg_merged, "ingested_at") # WRONG primary order - for contrast
ocel_agg_merged = pm4py.ocel_add_index_based_timedelta(ocel_agg_merged, delta=pd.Timedelta("1ms"))

# Final validation for all scenarios
for name, ocel in [("raw",ocel_raw),("cons",ocel_cons),("ev",ocel_ev),("agg",ocel_agg_merged)]:
    assert "original_timestamp" in ocel.events.columns, f"{name} lost original_timestamp"
    print(name, len(ocel.events), len(ocel.relations))
```

Key implementation invariants: deep copies for independence, original timestamp/activity preserved, pre-check before any library deduplication, `drop_duplicates` used only once in justified inspected context, `merge_duplicates` shown separately with warning, `sort` before `add_index_based_timedelta`, custom verified-pair helper defined, referential integrity validated, raw never mutated.

1. **`Pick Item  Pick Item` (Order-flattened):** Raw 2 edges (one artifact duplicate e03e04, one true concurrency e03/e05). Conservative keeps 1 concurrent edge, Aggressive removes entirely (0) – hides concurrency.
2. **`Pick Item  Pack Package` (Item-flattened):** Raw shows two Pick nodes  two Pack edges. Aggressive shows 1 Pick  1 Pack – suggests 1 item packed.
3. **`Pack Package  Pack Package` (Order-flattened):** Raw/Conservative show WMSERP status loop (rework-like). Evidence-based/Aggressive remove it – changes rework measurement from 1 to 0.
4. **`Dispatch Package  Dispatch Package`  `Handover to Carrier` (Package/Delivery OTG):** Raw has e08e09 artificial self-loop. Conservative refines to `Release  Accept  Handover` (3-step). Aggressive collapses to `Dispatch  Handover` (2-step) – loses carrier acceptance boundary.

6. **`Issue Invoice  Capture Payment` / `Capture Payment  Capture Payment` (Order-flattened):** Raw shows InvoiceAuthorizeCaptureCapture (M1M2ERP summary). Conservative shows Invoice(AuthorizeCapture M1  Capture M2)  Summary. 7. *(bonus)* **`Capture Payment  Confirm Delivery` (OC-DFG):** Raw performance duration 21h includes ERP summary lag correctly. Evidence-based shortens duration by 60s–12h; Aggressive collapses and shows clean 21h but via wrong event object mix.

Lifecycle/performance impact: Conservative keeps second-resolution ties flagged, so performance dashboards show 0-duration for tie clusters with warning. Adding synthetic milliseconds after semantic ordering allows DFG visualization without distorting measured lead time (21h Order-to-Delivery). Aggressive merges underestimate resource hand-over time and overestimate process straight-through.

**Reconstruction of raw view:**

1. Audit `source_event_ids` allows expanding each canonical back to original rows: `events_raw = explode(audit.source_event_ids)` joined to preserved `original_timestamp`, `original_activity`, `source`, `payload_hash`.
2. `adjusted_timestamp` is ignored; `original_timestamp` restores.
3. Refined labels map back via `original_activity`.
4. E2O: for merged events with identical relations, de-duplicate expansion reproduces raw; for unioned relations, audit stores `e2o_before` to split. Even aggressive merges remain reversible if audit logged, but information loss (distinct Payment merge) is documented as `discarded_conflicts: M2 object link`.
5. Provide `revert_to_raw(ocel_clean, audit_log)` function that deep-copies clean OCEL and reinserts dropped events from audit, restoring 17-event raw state bit-identical for replay.

No analyst is forced to trust synthetic microseconds – `original_timestamp` column remains queryable.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments (e13/e14):** Sharing O1/V1 triggers `have_common_object=True` but M1M2. Safeguard: require equality on *activity-specific mandatory object type* (Payment for Capture) and check `payload_hash` / `source_seq` distinctness; quarantine if M-object differs.
2. **Converting abstraction-level updates into false rework or false duplication (e06/e07, e13/e15, e15):** ERP summaries look like duplicate Pack/Capture. Safeguard: trace lineage (`ER-150 generated from WMS message`, `ER-201 after PSP messages`); keep both with `[detail]`/`[summary]` qualifiers; never merge across `is_derived` boundary in conservative mode.
3. **Ordering by ingestion time as business order:** `ingested_at` 10:00:01 vs 10:00:03 vs 12:01:00 reflects system lag, not physical order. Safeguard: use domain/source_seq first; mark ingest as `is_semantic=false` and log warning; never sort by ingest before semantic ranks.
4. **Treating shared objects as proof of duplication:** O1,P1,D1 shared by e08/e09/e10 and O1,V1 shared by invoice/payments does not imply same event. Safeguard: pre-check object *instance* disjointness (I1 vs I2, M1 vs M2) and harmonization metadata before dropping.
5. **Unioning incompatible E2O relations in `ocel_merge_duplicates`:** Merged Capture would link O1,V1,M1,M2 together, creating impossible “one capture pays two invoices with two methods” event. Safeguard: validate E2O cardinality per activity (e.g., Capture must have 1 Payment); reject merges that increase cardinality beyond allowed; prefer quarantine.
6. **Changing durations through synthetic microseconds:** Adding 1ms before fixing semantic order makes PickPack look 1ms and DispatchAccept 1ms, corrupting performance. Safeguard: preserve `original_timestamp`, add timedelta only after semantic partial order, document as deterministic, exclude synthetic delta from KPI calculations.
7. **Losing source-authoritative attributes (e11/e16 invoice, e03/e04 location):** Last-write-wins overwrite (BILLING overwrites ERP tax vs amount) silently drops authoritative data. Safeguard: attribute authority map, merge both values into `attribute_provenance` dict, log `discarded_conflicts`.
8. **Applying duplicate functions to whole OCEL without inspecting candidate groups:** Blanket `drop_duplicates` on 17 events collapses legitimate concurrency (e05, e14) and harmonization collisions. Safeguard: always run candidate-group pre-check (activity+timestamp groupby + E2O overlap review), apply verified-pair helper only to high-confidence pairs.
9. **(Bonus) Erasing original timestamp / claiming total order proves truth:** Overwrites UTC second and asserts deterministic order is real. Safeguard: `original_timestamp` immutable column, `adjusted_timestamp` separate, and disclaimer in every report: deterministic order does not prove physical order beyond stated semantic constraints.
