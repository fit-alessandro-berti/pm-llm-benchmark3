## 1. Equivalence design space

Let an execution be an ordered object-centric trace: events have activity labels, timestamps or log order, typed object references, and optional O2O qualifiers. The lead object type is `Order`.

### 1.1 Activity-sequence equivalence

**Definition.** Project every event to its activity label and keep the timestamp/log order. Two executions are equivalent iff their activity-label sequences are identical.

**Invariants preserved.** Activity labels, repetition of activities, and total order of labels.

**Information discarded.** Object types, object identifiers, object multiplicities, event-object incidence, external-object flags, O2O qualifiers, package/delivery/payment structure, and all business relations.

**Equivalence properties.** Reflexive, symmetric, transitive because equality of sequences is an equivalence relation.

**Concurrency.** If two events have the same timestamp, I would canonicalize them by sorting activity labels lexicographically within the timestamp. If true concurrency is modeled as a partial order, this relation becomes label-poset equivalence, but for the given total sequences the simpler sequence version is sufficient.

### 1.2 Typed structural equivalence under identifier renaming

**Definition.** Two executions are equivalent iff there exists a bijection between their local object identifiers that preserves object type and external/local status, and a bijection between events preserving activity label, event order, and typed event-object incidence. Operationally, canonicalize local object IDs by first appearance within each type, keep `EXT` flags, sort object references inside each event, and compare the resulting normalized event trace.

**Invariants preserved.** Activity labels, event order, object types, object multiplicities, event-object incidence, repeated activities, and whether an object is external.

**Information discarded.** Raw local identifier names. In the basic version, I discard O2O qualifiers and business interpretation of amounts unless they are explicitly encoded as structural relations.

**Equivalence properties.** Reflexive, symmetric, transitive because it is isomorphism of typed ordered event-object structures.

**Concurrency.** Same-time events are sorted by their canonical event key. If a partial order is supplied, equivalence requires labeled poset isomorphism: event labels, typed object incidence, and precedence constraints must match.

### 1.3 Business-semantic equivalence

**Definition.** Two executions are equivalent iff they have the same canonical business-motif signature. The signature preserves selected business invariants: lead-order isolation, external sharing in logistics or finance, package/item/delivery multiplicities, invoice/payment patterns, settlement qualifiers, replacement/return motifs, and repeated business-relevant activities. It intentionally ignores raw identifiers and may ignore ordering of independent events such as two `Add Item` events.

**Invariants preserved.** Object-type multiplicities, external-object flags by business domain, E2O incidence for business-relevant objects, O2O qualifiers such as `partial_settles`, `removed_before_dispatch`, or `replaces`, and lifecycle motifs such as split fulfillment, cross-order consolidation, replacement, and return/repack.

**Information discarded.** Raw identifiers, incidental ordering of independent events, and non-business attributes unless explicitly included.

**Equivalence properties.** If defined as equality of a deterministic signature, it is reflexive, symmetric, and transitive. If defined by heuristic similarity, transitivity can fail; therefore I prefer exact signature equality.

**Concurrency.** Independent events can be represented as a multiset or sorted canonical block. Causally dependent events, such as `Pack Package` before the corresponding `Dispatch`, remain ordered.

### 1.4 Optional fourth relation: lead-local projection equivalence

For diagnostics, one can define a lead-local projection that removes all `EXT` objects and qualifiers, then applies typed structural equivalence. This is useful because it shows how much of the difference between executions is caused solely by cross-order sharing.

## 2. Canonical signatures

The preferred semantic signature canonicalizes local identifiers, preserves external flags, event order, E2O incidence, O2O qualifiers, and repeated activities.

```python
from collections import defaultdict

LOGISTICS = {"Pack Package", "Dispatch", "Return Item", "Inspect Return"}
FINANCIAL = {"Issue Invoice", "Record Payment"}

def is_ext(oid: str) -> bool:
    return oid.startswith("EXT")

class Canonicalizer:
    def __init__(self):
        self.local_index = {}
        self.ext_index = {}
        self.objects = set()

    def map(self, otype: str, oid: str) -> str:
        if is_ext(oid):
            key = (otype, oid)
            if key not in self.ext_index:
                self.ext_index[key] = len(self.ext_index)
            cid = f"{otype}:EXT{self.ext_index[key]}"
        else:
            key = (otype, oid)
            if key not in self.local_index:
                same_type = [k for k in self.local_index if k[0] == otype]
                self.local_index[key] = len(same_type)
            cid = f"{otype}:{self.local_index[key]}"
        self.objects.add((otype, cid))
        return cid

    def object_counts(self):
        counts = defaultdict(int)
        for otype, cid in self.objects:
            counts[(otype, "EXT" in cid)] += 1
        return tuple(sorted(counts.items()))

def normalize_events(events, canon, partial_order=False):
    normalized = []
    for e in events:
        pairs = []
        for otype, oids in e["objects"].items():
            for oid in oids:
                pairs.append((otype, canon.map(otype, oid)))
        pairs.sort()
        normalized.append((e.get("time"), e["activity"], tuple(pairs)))

    if partial_order:
        # Same-time events become sorted concurrent blocks.
        by_time = defaultdict(list)
        for t, act, objs in normalized:
            by_time[t].append((act, objs))
        return tuple(
            ("concurrent", tuple(sorted(block)))
            for _, block in sorted(by_time.items())
        )

    # Total order: preserve given order, but canonicalize same-time ties.
    return tuple((act, objs) for _, act, objs in sorted(normalized))

def normalize_qualifiers(o2o_qualifiers, canon):
    out = []
    for s_type, s_id, rel, o_type, o_id in o2o_qualifiers:
        out.append((
            s_type,
            canon.map(s_type, s_id),
            rel,
            o_type,
            canon.map(o_type, o_id),
        ))
    return tuple(sorted(out))

def external_roles(trace):
    log_ext = set()
    fin_ext = set()
    for act, objs in trace:
        for otype, cid in objs:
            if "EXT" in cid:
                if act in LOGISTICS:
                    log_ext.add((otype, cid))
                if act in FINANCIAL:
                    fin_ext.add((otype, cid))
    return tuple(sorted(log_ext)), tuple(sorted(fin_ext))

def motif_features(trace, quals, canon):
    packs = [objs for act, objs in trace if act == "Pack Package"]
    dispatches = [objs for act, objs in trace if act == "Dispatch"]
    payments = [cid for otype, cid in canon.objects if otype == "Payment"]
    invoices = [cid for otype, cid in canon.objects if otype == "Invoice"]

    return (
        len(packs),
        len(dispatches),
        len(invoices),
        len(payments),
        any(rel == "partial_settles" for _, _, rel, _, _ in quals),
        any(rel == "removed_before_dispatch" for _, _, rel, _, _ in quals),
        any(rel == "replaces" for _, _, rel, _, _ in quals),
        any(act == "Return Item" for act, _ in trace),
        any(act == "Inspect Return" for act, _ in trace),
    )

def preferred_signature(events, o2o_qualifiers, lead_type="Order", partial_order=False):
    canon = Canonicalizer()
    trace = normalize_events(events, canon, partial_order=partial_order)
    quals = normalize_qualifiers(o2o_qualifiers, canon)
    log_ext, fin_ext = external_roles(trace)
    motif = motif_features(trace, quals, canon)

    return (
        lead_type,
        trace,
        canon.object_counts(),
        log_ext,
        fin_ext,
        quals,
        motif,
    )
```

## 4. Cluster interpretations

### S-BASELINE-ISOLATED: X1, X2

**Signature.** `isolated; 1 order, 2 items, 1 package, 1 delivery, 1 invoice, 1 payment; no qualifiers`.

**Business behavior.** A normal single-order, single-package, single-delivery, single-invoice, single-payment execution. X2 differs only in local identifier names and item-addition identifier order.

**Risks/opportunities.** Low operational risk. Suitable for straight-through automation and standard cycle-time monitoring.

**Poor flattening.** Flattening to one case per item would duplicate order, invoice, and payment events and make a simple order appear fragmented.

**Stability.** Very stable under reasonable repairs. Renaming identifiers or swapping independent `Add Item` events does not change the cluster.

### S-SPLIT-PACK-CONSOLIDATED: X3

**Signature.** `2 packs; 1 dispatch; 1 delivery; 1 invoice; 1 payment`.

**Business behavior.** Items are packed separately but shipped together. This may reflect warehouse constraints while preserving consolidated customer delivery.

**Risks/opportunities.** Risk of missing one package during consolidation. Opportunity to optimize packing without increasing delivery cost.

**Poor flattening.** Order-level flattening hides the two-package structure; delivery-level flattening hides that packing was split.

**Stability.** Stable if package objects are preserved. It becomes unstable only under aggressive simplification that collapses repeated `Pack Package` events.

### S-SPLIT-DELIVER-PARTIAL: X4

**Signature.** `2 packs; 2 dispatches; 2 deliveries; 1 invoice; 2 payments; partial_settles/completes_settlement`.

**Business behavior.** The order is fulfilled in separate shipment legs and financially settled in stages. This is a split-delivery, partial-payment pattern.

**Risks/opportunities.** Risks include payment allocation errors, revenue-recognition ambiguity, and customer confusion. Opportunities include faster partial fulfillment.

**Poor flattening.** Order-centric flattening hides multiple deliveries; invoice-centric flattening hides the physical fulfillment split.

**Stability.** Stable if payment events or payment qualifiers are retained. If payment multiplicity is converted to an amount attribute, the financial motif changes, but the delivery split remains.

### S-CROSS-ORDER-LOGISTICS: X5

**Signature.** `external Order and Item in Pack/Dispatch; local invoice/payment`.

**Business behavior.** Logistics is consolidated across orders. The package contains an item or order reference from another execution, while billing remains local.

**Risks/opportunities.** Risks include unclear ownership, cost allocation, customs/export issues, and traceability gaps. Opportunity is shipping consolidation.

**Poor flattening.** Order-only flattening either hides the external dependency or duplicates the shared package across orders.

**Stability.** Stable when external flags are preserved. If external objects are ignored, this cluster collapses into the baseline cluster, which is semantically dangerous.

### S-CROSS-ORDER-FINANCE: X6

**Signature.** `local logistics; external Order in Issue Invoice/Record Payment`.

**Business behavior.** Logistics is isolated, but invoicing/payment is consolidated across orders.

**Risks/opportunities.** Risks include incorrect revenue allocation, tax issues, dunning errors, and privacy leakage across orders. Opportunity is consolidated billing.

**Poor flattening.** Order-centric flattening hides that the invoice is shared; invoice-centric flattening loses delivery context.

**Stability.** Stable when external financial objects are preserved. If external objects are removed, it falsely becomes baseline.

### S-PRE-DISPATCH-REPLACEMENT: X7

**Signature.** `pack two items; dispatch with one item; removed_before_dispatch/replacement qualifier`.

**Business behavior.** An item was substituted or removed before dispatch. The activity labels look baseline-like, but the object graph reveals an exception.

**Risks/opportunities.** Risks include inventory mismatch, billing for unavailable items, and customer dissatisfaction. Opportunity is automated replacement handling.

**Poor flattening.** Activity-sequence flattening completely hides the removal. Package-centric flattening may show the package but not the item-level substitution.

**Stability.** Stable if event-object incidence and qualifiers are kept. If qualifiers and the extra `Item` in `Dispatch` are ignored, it can be misclassified as baseline.

### S-POST-DISPATCH-RETURN-REPACK: X8

**Signature.** `dispatch; return; inspect; second pack; second dispatch; replaces`.

**Business behavior.** A post-delivery return triggers inspection and repack/redelivery. This is a reverse-logistics motif.

**Risks/opportunities.** Risks include double shipment, incorrect refund/replacement decisions, and inventory quality errors. Opportunity is structured return recovery.

**Poor flattening.** Order-level flattening hides the reverse loop; package-level flattening treats the two packages as independent rather than replacement-related.

**Stability.** Stable if return and replacement relations are preserved. Collapsing repeated `Pack Package`/`Dispatch` events weakens the repack semantics, although `Return Item` still signals an exception.

## 5. Borderline cases

### X1 versus X2

Under activity-sequence and typed structural equivalence, X1 and X2 are equivalent: the identifier names and item-ID order are not meaningful. Under raw exact identifier equivalence, they differ. A business-semantic view also merges them because no external sharing, qualifier, or multiplicity differs.

### X1 versus X5

Activity-sequence equivalence merges X1 and X5 because the labels are identical. Typed structural equivalence with external flags separates them because X5 includes external `Order` and `Item` references in logistics events. Business-semantic equivalence also separates them because cross-order logistics consolidation is a meaningful compliance and cost-allocation issue. A lead-local projection ignoring `EXT` objects would merge them, but that projection discards an important business fact.

### X1 versus X6

Again, activity-sequence equivalence merges X1 and X6. Typed structural equivalence separates them because `Issue Invoice` and `Record Payment` include an external order. Business-semantic equivalence separates them because shared invoicing changes financial accountability. If one ignores external financial objects, X6 becomes indistinguishable from baseline, which is undesirable for finance compliance.

### X1 versus X7

At activity-label level, X7 resembles X1. Typed structural equivalence separates them because X7’s `Dispatch` event includes an item and because O2O qualifiers indicate removal/replacement. Business-semantic equivalence separates them because replacement is an exception motif. If one ignores item-level incidence in dispatch and ignores qualifiers, X7 would be incorrectly merged with baseline.

### X3 versus X4

Both involve split packing. A coarse “split-package” equivalence could group them. However, typed structural equivalence and the preferred business-semantic equivalence separate them because X3 consolidates delivery and has one payment, while X4 has split deliveries and partial payment. The disagreement is between a logistics-packing view and a full fulfillment-to-settlement view.

### X4 versus X8

Both contain repeated packing/dispatch structure. A coarse multi-leg fulfillment equivalence could group them. However, X4 is forward logistics with partial payment, while X8 contains return, inspection, and replacement/repack. Typed structural and business-semantic equivalence separate them because the causal motif and financial pattern differ.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py exact OCEL clustering key preserves the raw object-centric incidence structure. For each event, it effectively keeps the activity and the sorted tuple of typed object references, usually as `(object_type, object_id)` pairs. For executions centered on a lead object type such as `Order`, it keeps the ordered collection of such event keys associated with the lead object. Thus it preserves activity labels, raw object identifiers, object types, event-object incidence, and event order. It does not normalize local identifiers, infer business roles, or interpret O2O qualifiers unless those qualifiers are explicitly stored as attributes.

Raw identifiers make exact clusters too fine because every order instance has unique IDs. X1 and X2 would likely fall into different exact clusters even though they are structurally isomorphic. Similarly, any incidental identifier change creates a new cluster.

To obtain meaningful clusters, I would canonicalize each returned cluster: rename local IDs by first appearance, preserve external flags, sort object references, normalize qualifiers, and compute the preferred semantic signature. Then I would merge exact PM4Py clusters with identical semantic signatures.

Exact equivalence is preferable for conformance checking, debugging, legal audit trails, and detecting unexpected object sharing. Coarser business clustering is preferable for operational reporting and segmentation.

`max_objs` and large connected executions matter because shared packages, invoices, or external orders can connect many lead objects. Exact clustering may become memory-intensive or produce giant components. If `max_objs` truncates object references, clusters may change silently. For large logs, one should project to the lead object, canonicalize identifiers, and possibly cluster by semantic motifs rather than raw exact keys.

```python
import pm4py
from collections import defaultdict

LEAD_OBJECT_TYPE = "Order"

def canonical_pm4py_cluster(cluster, lead_type=LEAD_OBJECT_TYPE):
    events = []
    qualifiers = []

    # Assume cluster exposes events and object qualifiers in an OCEL-like form.
    for ev in sorted(cluster.events, key=lambda e: (e.timestamp, e.id)):
        obj_map = defaultdict(list)
        for obj in ev.omap:
            obj_map[obj.type].append(obj.id)
        events.append({
            "time": ev.timestamp,
            "activity": ev.activity,
            "objects": dict(obj_map),
        })

    # If O2O qualifiers are stored as object attributes or relations:
    for rel in getattr(cluster, "o2o_qualifiers", []):
        qualifiers.append((
            rel.source_type,
            rel.source_id,
            rel.qualifier,
            rel.target_type,
            rel.target_id,
        ))

    return preferred_signature(events, qualifiers, lead_type=lead_type)

exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    lead_object_type=LEAD_OBJECT_TYPE,
    max_objs=10_000,
)

semantic_groups = defaultdict(list)

for cluster_key, cluster in exact_clusters.items():
    sig = canonical_pm4py_cluster(cluster)
    semantic_groups[sig].append(cluster_key)

for sig, members in semantic_groups.items():
    print("Semantic signature:", sig)
    print("Merged exact PM4Py clusters:", members)
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** X4 still has two payments, but the distinction between partial and completing settlement is weakened. X7 may still be separated if the extra `Item` in `Dispatch` is preserved, but the explicit replacement explanation is lost. X8 still has return/inspection events, but the fact that the second package replaces the first becomes implicit. Preferred clusters remain mostly stable, but their business interpretation becomes less precise.

**Ignore external objects.** X5 and X6 move toward X1/X2 under both typed structural and business-semantic clustering if the projection removes `EXT` references. This is a high-risk simplification because cross-order logistics and cross-order finance are compliance-relevant.

**Collapse repeated same-label events.** If all repeated activities are collapsed, X3 and X4 can become activity-equivalent to X1. Typed structural clustering also loses package/payment multiplicity. This hides split fulfillment and partial payment. X8 remains exceptional because of `Return Item` and `Inspect Return`, but the repack loop is weakened.

**Treat Pack/Dispatch order as partial order.** If only causal dependencies are preserved, different total interleavings of independent pack/dispatch legs can become equivalent. X4 may become equivalent to other parallel two-leg fulfillments, but it remains distinct from X3 because delivery count differs. X1 remains baseline. X8 remains distinct because return/inspection creates a post-delivery dependency.

**Treat payment multiplicity as an amount attribute.** X4’s two payment events may become one payment object with partial and completed amount attributes. If amount semantics are preserved, business-semantic clustering can still identify partial settlement. If amount attributes are ignored, X4’s financial distinctness is reduced, although its split-delivery structure remains.

## 8. Limitations and recommendation

**Compliance monitoring.** Use strict qualified typed-structural equivalence: canonical identifier renaming plus external flags and O2O qualifiers. Compliance needs sensitivity to shared invoices, cross-order logistics, replacements, and partial settlements.

**Operational segmentation.** Use the preferred business-semantic equivalence. It groups executions by meaningful operational motifs such as baseline, split fulfillment, cross-order consolidation, replacement, and return/repack.

**Root-cause analysis.** Use typed structural equivalence under identifier renaming, then drill into qualifiers. Structural canonicalization shows where object graphs differ without being distracted by raw IDs; qualifiers then explain why they differ.

**Descriptive reporting.** Use activity-sequence equivalence or activity labels augmented with simple object counts. It is easiest to communicate but should not be used when object-level structure matters.

No single equivalence notion is best for all purposes. Compliance requires fine-grained structural and qualifier sensitivity. Operational segmentation needs abstraction from identifiers and incidental order. Root-cause analysis needs diagnostic precision without identifier noise. Descriptive reporting needs simplicity. The right equivalence level depends on the decision being supported.
