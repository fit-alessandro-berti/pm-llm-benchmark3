# 1. Model scope and state variables

## Boundary and level of detail
The digital twin covers the municipal building-permit process from portal submission through completeness, reviews, public notice, inspection, decision, legal check, and issue/reject. It also includes applicant/third-party response delays, rework, objections, resource calendars, and cross-case dependencies. It excludes broader zoning policy, political decision-making, and portal implementation details except where an intervention directly changes portal behavior.

Use a hybrid discrete-event/agent-based simulation at activity-level granularity:
- Municipal activities are resource-constrained tasks with queues.
- Applicant/third-party activities are external delays, not municipal service times.
- Inspections are scheduled in district-aware batches.
- Public notice is a fixed minimum plus a latent objection process.
- Architect/neighborhood dependencies are represented by shared groups.

## Entities
- Case: building-permit application.
- Applicant/architect: external actor, can submit bursts and related cases.
- Resource: clerk, planner, fire reviewer, environmental reviewer, inspector, legal officer, system.
- District: geography affecting travel, environmental sensitivity, and inspection batching.
- Objection group: latent neighborhood/public-notice relationship among cases.
- Inspection batch: cases grouped geographically or by architect/district.
- Policy scenario: intervention configuration.

## Case state variables
- `case_id`, `case_type`, `district`, `architect_id`, `application_value`
- `requires_fire`, `requires_environment`, `requires_public_notice`
- `submitted_at`, `ready_times`, `completed_activities`, `current_stage`
- `rework_count`, `rework_history`, `objection_flag`, `objection_duration`
- `inspection_batch_id`, `related_case_ids`, `decision`, `decision_time`
- `sla_due`, `priority`, `aging_days`, `prior_violations`

## Resource state variables
- `resource_id`, `role`, `skills`, `capacity`, `calendar`
- `available_intervals`, `current_task`, `queue`, `utilization`
- `non_permit_duty_fraction` for environmental reviewers
- `travel_time_by_district` for inspectors
- `council_week_flag` for legal officers

## Queues
- Per-activity/resource-pool queues, e.g. completeness, planning, fire, environmental, inspection scheduling, legal.
- Priority rules: FIFO by default; aging override for D6; case-type/risk priority for triage policies; district batching for inspections.
- Inspection queue supports batching: wait for batch, then travel savings, but first case may wait longer.

## Calendars
- Clerks: Mon-Fri 08:00-16:00; Monday portal support.
- Planners: Mon-Fri 09:00-17:00; two only for Simple renovation.
- Fire reviewers: Tue-Thu only.
- Environmental reviewers: Mon-Fri, 40% reserved for non-permit duties.
- Inspectors: Tue-Fri field visits; travel depends on district; batching possible.
- Legal: no work during council meeting weeks except urgent cases.
- System tasks: effectively unlimited.
- Holidays, peak months, and council weeks are explicit calendar interruptions.

## Cross-case dependencies
- Architect bursts: top architects submit multiple related applications in the same week.
- Related cases: same architect/district may share documents, review context, or inspection trips.
- Inspection batching: same district can be grouped, reducing travel but increasing waiting for the first case.
- Objection spillover: a public objection may affect related cases in the same neighborhood, district, or architect portfolio.
- Resource contention: shared planners, legal officers, inspectors, and reviewers create indirect dependencies.
- Decision drafting waits for all applicable reviews, public notice, and inspection results.

# 2. Parameter-estimation plan

## PM4Py-based log and model handling
Use PM4Py for event-log formatting, variant discovery, DFG/performance DFG, and process-tree parsing. The simplified process tree string is only a structural guide: it omits data conditions, calendars, resources, rework reasons, and cross-case dependencies. PM4Py can parse it if syntactically valid, but the simulation engine must implement the real routing logic.

## Arrivals
- Extract first event per case as arrival timestamp.
- Estimate non-stationary intensity using piecewise rates, month effects, weekday effects, and peak-month multipliers.
- Monday factor: estimate from observed weekday submission counts; apply as day-of-week multiplier.
- Case mix: multinomial by month and district, using historical case-type shares.
- Architect bursts: model top-architect weekly counts with empirical distributions, negative binomial, or Hawkes-like self-excitation.
- Related-case lag: estimate inter-submission times within architect/district/week groups.
- District mix: empirical conditional on case type and month.

## Service times
- Where start and complete timestamps exist, compute service time directly.
- Where start timestamps are missing, use completion-only data with censoring/EM or calibrate service distributions against known medians/p90s.
- Fit activity-specific distributions: lognormal, gamma, Weibull, or empirical bootstrap.
- Do not collapse waiting into service. Waiting is queue time from ready time to start.
- For applicant-driven activities such as `Receive missing documents`, model separately as external delay, e.g. lognormal or heavy-tailed mixture.

## Waiting times
- Define waiting as `start_time - ready_time`, where ready time is max completion of prerequisites.
- If start missing, infer waiting from queue simulation calibration and empirical waiting summaries.
- Calibrate queue discipline and resource capacity until simulated waiting quantiles match observed medians/p90s.

## Branching and routing
- Estimate conditional probabilities by case type, district, value, flags, and architect.
- Fire: `requires_fire=yes` or building-area threshold; threshold is partially latent, so use sensitivity bounds.
- Environmental: `requires_environment=yes` or environmentally sensitive district; sensitivity data incomplete.
- Public notice: Complex variance always; some New residential; estimate by case type/district/value.
- Legal: estimate from observed path, case type, value, and conflict indicators.
- Use decision trees, logistic regression, or Bayesian networks if data are sufficient; otherwise use expert priors and scenario ranges.

## Rework
- Estimate loop probabilities after Planning, Inspection, Legal, and appeal.
- If reasons are unstructured, use topic modeling only after validation; otherwise treat rework reasons as latent and vary in sensitivity analysis.
- Model loop count and additional delay distributions by variant and case type.

## Resource calendars
- Reconstruct from HR calendars plus event-log utilization.
- Estimate availability windows, holidays, council weeks, part-time fire reviewers, and environmental non-permit duty.
- Calibrate capacity so simulated utilization is plausible relative to observed workload.
- Inspector travel: use district-level empirical distributions or priors if GPS/travel data unavailable.

## Cross-case dependencies
- Architect groups: link cases by `architect_id` and submission week.
- Inspection batches: estimate batch sizes and travel savings from same-district inspection dates.
- Objections: objection events are missing, so do not treat public-notice duration as observed objections. Instead model a latent objection hazard whose duration proxy matches observed public-notice p90/tail.
- Neighborhood spillover: if address/parcel data unavailable, use district plus overlapping notice windows as a proxy and test sensitivity.

## Non-stationary demand
- Use time-varying arrival rates, peak-month multipliers, weekday factors, and architect burst intensities.
- Include policy-change effects as scenario switches, not as historical calibration unless historical policy changed.

## Missing data
- Missing start timestamps: impute or bound waiting/service splits.
- Missing objections: latent variable with priors and sensitivity.
- Missing rework reasons: latent categories with uncertainty.
- Removed emergency decisions: treat as out-of-scope but note censoring.
- Flattened dependencies: reconstruct architect/district groups and test dependency strength.

# 3. Assumptions

## Arrivals
- Non-stationary Poisson or NHPP with month, weekday, and peak multipliers.
- Monday submissions are elevated and can be smoothed by D7.
- Architect bursts are correlated within architect and week.
- Case-type mix varies by month/district but is calibrated from history.

## Service times
- Municipal service times are activity- and resource-dependent.
- Service time is independent of waiting time, except for fatigue/queue effects if modeled.
- System tasks are near-instant.
- Heavy tails are possible, especially environmental, legal, inspection, and applicant response.

## Routing
- Fire, environmental, public notice, legal, and inspection requirements follow observable flags plus latent thresholds.
- Decision drafting waits for all applicable prerequisites.
- Rare emergency paths are excluded or modeled separately.

## Resources/calendars
- HR calendars are approximately correct.
- Fire reviewers work only Tue-Thu.
- Environmental reviewers have 40% non-permit duties.
- Inspectors travel by district and can batch.
- Legal capacity drops during council weeks.
- System capacity is unlimited.

## Rework
- Rework loops occur after Planning, Inspection, Legal, and appeal.
- Rework probabilities depend on case type, district, value, and resource.
- Rework reasons are latent unless reliably coded.

## Applicant/third-party response
- Applicant response time is external, heavy-tailed, and not constrained by municipal calendars.
- Missing-document delay dominates Simple-with-missing-docs variants.
- Objection duration is not equivalent to objection incidence; it is a proxy.

## Cross-case dependencies
- Same architect cases may be correlated in submission and review.
- Same-district inspections can be batched.
- Objections can spill over to related cases.
- Resource contention couples cases indirectly.

## Non-stationary demand
- Seasonality repeats approximately across years, but policy and external shocks can change it.
- Peak months have 1.7x baseline arrival rate; stress scenarios can increase this.
- Interventions may change arrival behavior, e.g. D7 smooths Monday peaks.

## Missing data
- Missing start timestamps create uncertainty in waiting/service split.
- Missing objection events create uncertainty in public-notice tail.
- Missing rework reasons create uncertainty in rework routing.
- Flattened dependencies underrepresent architect and neighborhood coupling.
- Validation must distinguish observed, inferred, and assumed parameters.

# 4. Experiment matrix

Design baseline and interventions with common random numbers. Use pilot replications first, then final replications. Stress scenarios are run for all promising interventions.

| ID | Type / intervention | Factors and levels | Mechanism in twin | Expected trade-offs |
|---|---|---|---|---|
| Baseline | Current policy | Historical arrival, routing, calendars | Calibrated to 18-month log | Reference for all metrics |
| D1 | Pre-submission document checker | Checker coverage 0/50/80%; missing-doc reduction 20/40/60%; applicant pre-effort +0/1/3d | Lower missing-doc loop probability; shift effort before submission | Fewer completeness loops and rework; may delay submission and not help Complex cases |

# 5. Warm-up, replications, and uncertainty treatment

## Warm-up
Because demand is non-stationary, there is no true steady state. Use a 12-month initialization period covering all seasons to populate queues, backlog, and resource state. Discard the first 12 months of output. Start measurement at January after warm-up.

## Run length
- Main experiments: 36-60 simulated months after warm-up.
- Rare Complex variance and tail metrics: extend to 60-84 months or use importance sampling.
- Policy comparisons should cover at least two full annual cycles.

## Replications
- Pilot: 30 replications per scenario.
- Final: 200 replications for main comparisons; 500 for p95/p99 and rare-case metrics.
- Use common random numbers across interventions to reduce variance.
- Maintain separate random streams for arrivals, case attributes, service times, routing, rework, objections, resources, and dependencies.

## Uncertainty treatment
- Report medians, p90, p95, p99, SLA compliance, utilization, backlog, and fairness metrics.
- Use percentile bootstrap confidence intervals over replications.
- For Bayesian calibration, report posterior predictive credible intervals.
- Use batch means for throughput and utilization if autocorrelation exists.
- Do not claim exact optimality from uncalibrated simulation.

## Sensitivity analysis
- One-at-a-time sensitivity on key parameters: peak multiplier, service p90, missing-doc probability, objection probability, travel savings, dependency strength, resource availability, eligibility thresholds.
- Global sensitivity: Morris screening, then Sobol indices for important parameters.
- Stress scenarios S1-S5 are mandatory.

## Heavy-tailed durations
- Use empirical bootstrap, lognormal, gamma, Weibull, or phase-type distributions.
- Applicant response: heavy-tailed lognormal or Pareto-like with sensitivity.
- Public notice: mixture of fixed minimum plus latent objection hazard.
- Track p95/p99/CVaR; avoid relying only on means.

# 6. Validation strategy

## Face validation
Review activities, roles, calendars, routing rules, and dependencies with process owners. Confirm that D1-D10 mechanisms match intended policy.

## Event-log replay validation
Replay historical cases with actual arrivals and, where possible, actual resource calendars. Compare simulated activity sequences, variants, and timestamps against observed traces. Use PM4Py conformance checking when a valid process model is available.

## Distributional validation
Compare simulated vs observed distributions for:
- Case duration by case type
- Activity service times
- Waiting times before activities
- Rework loop counts
- Public-notice duration
- Inspection delay
Use KS, Anderson-Darling, quantile plots, and median/p90 comparisons.

## Resource-utilization validation
Compare utilization, overtime, queue lengths, and backlog by resource role. Check that inspectors, planners, legal, fire, and environmental reviewers have plausible workloads.

## Bottleneck validation
Identify bottlenecks in the log and in simulation. Compare waiting-time contributions by activity. The simulation should reproduce major bottlenecks, e.g. inspection, legal, public notice, environmental review.

## Out-of-sample validation
Hold out the last 6 months, one district, or one case type. Calibrate on the rest and test prediction. Use temporal validation and cross-validation by district/architect group.

## Cross-case dependency validation
If data permit, compare related-case lags, inspection batch sizes, and objection spillover. If not, validate through expert review and sensitivity analysis.

## Missing-data validation
Test how imputation and latent objection/rework assumptions affect conclusions. Report whether decisions are robust to plausible missing-data mechanisms.

# 7. Decision criteria

Define metrics and thresholds before running final experiments. Thresholds are calibrated to baseline and may be adjusted after validation.

| Metric | Definition | Target / threshold range |
|---|---|---|
| Median cycle time | Median case duration by case type | >=10% reduction for Simple/New residential; no worsening for others |
| Tail cycle time | p90/p95/p99 by case type | >=15% reduction in bottleneck case types; no p95 increase >5% |
| SLA compliance | % cases within target by case type | Simple <=30d, New residential <=90d, Commercial <=120d, Complex <=180d; target +10 percentage points or >=85/80/70/60% |
| Backlog | Cases waiting/overdue | Reduce overdue >20%; peak backlog not worse than baseline |
| Fairness: districts | D3/D5 vs D1/D2 p90 gap | <=10% gap or no group p95 worsens >10% |
| Fairness: architects | Top-20 vs others p90 gap | <=15% gap |
| Resource utilization | Human resource busy fraction | 65-85% normal; <90% peak; overtime <10% |
| Rework | Missing-doc loop, inspection rework, legal rework | Reduce missing-doc loop >=20%; no increase in legal rework |
| Robustness | Worst stress scenario p95 | No worse than baseline +10%; low regret across S1-S5 |
| Cost | Overtime, temporary inspector, applicant effort | Cost per case within budget; D4/D10 must justify cost |
| Equity/safety | D2 missed violations, D8 missed environmental risk | No material increase in safety risk; conservative bounds |

Selection should use a Pareto frontier across cycle time, tail risk, SLA, fairness, utilization, cost, and robustness. Choose an intervention only if its uncertainty interval shows meaningful improvement and it does not violate fairness/safety constraints. Prefer robust combined policies if interactions are non-negative, but do not claim exact optimality.

def load_and_format_log() -> pd.DataFrame:
    """Load the illustrative CSV with pandas, then format for PM4Py."""

def add_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Add timing columns.
    With only one timestamp per activity, service and waiting cannot be fully separated.
    The columns below are inter-event proxies. If lifecycle start/complete exists, fill service/waiting.
    """
    df = df.sort_values([CASE, TS]).copy()
    df["inter_event_sec"] = df.groupby(CASE)[TS].diff().dt.total_seconds()
    df["time_to_next_sec"] = (
        df.groupby(CASE)[TS].shift(-1).sub(df[TS]).dt.total_seconds()
    )
    df["service_sec"] = np.nan
    df["waiting_sec"] = np.nan

    if "lifecycle:transition" in df.columns:
        for (case_id, activity), grp in df.groupby([CASE, ACT]):
            starts = grp[
                grp["lifecycle:transition"].str.lower().isin(["start", "schedule"])
            ]
            completes = grp[
                grp["lifecycle:transition"].str.lower().isin(["complete", "end"])
            ]
            if not starts.empty and not completes.empty:
                start_t = starts[TS].min()
                comp_candidates = completes[completes[TS] >= start_t][TS]
                if not comp_candidates.empty:
                    comp_t = comp_candidates.min()
                    service = (comp_t - start_t).total_seconds()
                    prev = df[(df[CASE] == case_id) & (df[TS] < start_t)][TS].max()
                    mask = (df[CASE] == case_id) & (df[ACT] == activity)
                    df.loc[mask, "service_sec"] = service
                    if pd.notna(prev):
                        df.loc[mask, "waiting_sec"] = (start_t - prev).total_seconds()
    return df


def pm4py_analysis(df: pd.DataFrame) -> Dict:
    """PM4Py-based log/model handling: variants, DFG, performance DFG, arrivals."""
    log = pm4py.convert_to_event_log(df)

    try:
        variants = pm4py.get_variants(log)
    except AttributeError:
        from pm4py.statistics.variants.log import get as variants_get
        variants = variants_get.get_variants(log)

    variant_counts = {v: len(instances) for v, instances in variants.items()}

    dfg, start_activities, end_activities = pm4py.discover_dfg(log)

    try:
        perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(log)
    except Exception as e:
        perf_dfg, perf_start, perf_end = None, None, None
        print(f"Performance DFG unavailable: {e}")

    first_events = df.groupby(CASE)[TS].min().sort_values()
    interarrival_days = first_events.diff().dt.total_seconds().div(86400).dropna()
    mean_interarrival_days = interarrival_days.mean()
    mean_arrival_rate_per_day = (
        1.0 / mean_interarrival_days if mean_interarrival_days > 0 else None
    )

    return {
        "variant_counts": variant_counts,
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": perf_dfg,
        "mean_interarrival_days": mean_interarrival_days,
        "mean_arrival_rate_per_day": mean_arrival_rate_per_day,
    }


def parse_simplified_tree():
    """
    Parse the simplified process tree. This is structural only.
    Data-dependent routing, resources, calendars, and dependencies are not executable here.
    """
    try:
        tree = pm4py.parse_process_tree(PROCESS_TREE_STR)
        net, im, fm = pm4py.convert_to_petri_net(tree)
        return tree, net, im, fm
    except Exception as e:
        print("Simplified tree is not a complete executable model:", e)
        return None, None, None, None
