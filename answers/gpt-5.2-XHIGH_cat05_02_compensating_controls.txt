## 1. Control-Objective Decomposition

FEP-1 (“Prepare_Payment” and “Release_Payment” performed by different humans) is a *means* to several risk objectives, not an end in itself. Decomposed threat scenarios (at least five) and how AV-2, MG-4, RA-7, ED-1 contribute:

| Objective / threat scenario (what can go wrong) | Why FEP-1 helps (baseline) | AV-2 (automated validation) | MG-4 (independent manager) | RA-7 (audit + recall) | ED-1 (emergency permission w/ conditions) |
|---|---|---|---|---|---|
| 1) **Single-operator fraud** (self-dealing, fake vendor, steering funds) | Forces a second human decision, adding deterrence and a second “stop” point | Helps only for covered checks (sanctions, duplicates, bank ownership, recent bank changes, limit, PO match). Does **not** assess receipt/commercial reasonableness or collusion | Strong if truly independent and *actually reviews* invoice, bank details, receipt/service evidence; weak if rubber-stamped or conflicted | Detective; only partly corrective *if* within recall window and action is taken | Allows same-user execution only if additional guardrails create an equivalent second check before irreversibility |
| 2) **Single-operator error** (wrong amount, duplicate invoice, wrong bank detail) | Second person can catch typos and mismatches before money leaves | **Strong** for duplicate detection, limit checks, basic PO match, some bank checks; warnings/overrides reduce strength | Can catch context/reasonableness mistakes and missing documentation | Detects after-the-fact; correction depends on timing vs recall window | Narrows emergency scope to low-ish risk cases (amount/vendor age/no recent bank change) and adds pre-settlement manager review + timely audit |
| 3) **Bank diversion via recent account change** (authorized/unauthorized change, “social engineering”, invoice redirection) | Second person should question sudden bank changes and verify ownership | **Direct coverage**: flags recent bank-account change and checks ownership *if operational*; can be overridden; outage removes it | Can verify change authorization and require independent confirmation; strength depends on diligence | Often too late for prevention; may only document/attribute | Explicitly forbids recent bank change; requires AV-2 pass without override; requires manager approval before settlement |
| 4) **Limit/override abuse & credential compromise** (operator uses someone else’s approval, bypasses warnings) | Segregation reduces “one credential = full payment path” | Operator-limit check helps; but override paths can become an attack surface | Effective only if manager approval uses *manager’s own* authentication and is independent; supervisor conflicts reduce resistance | Can detect anomalies like override usage, shared credentials, repeated patterns; correction may be impossible after settlement | Requires manager approval (and AV pass without override); token and audit create traceability expectations—if logs show misuse, ED-1 is not satisfied |
| 5) **Collusion / pseudo-independence** (two-person cell rubber-stamps; shared workstation; repeated pairs) | Assumes independence; if independence is fake, four-eyes degrades to “two signatures, one mind” | Does not address collusion; can be gamed by two actors | Adds hierarchy and typically broader independence—*if* no conflict and review is substantive | Detects patterns (repeated pairs, unusual throughput), but is still after-the-fact | ED-1 adds a manager to the path; still not collusion-proof (operator+manager collusion remains possible) |
| 6) **Inadequate evidence of receipt / legitimacy** (fake service receipt; no receiving confirmation) | Second person should demand support and sanity-check | AV-2 explicitly does **not** establish goods/services received | Can and should require receipt/service evidence and reasonableness | May detect later; correction depends on recovery options | ED-1 does not remove the need for legitimacy evidence; it requires manager review and timely audit to keep “receipt” scrutiny in emergencies |
| 7) **Timeliness / recoverability objective** (detect early enough to stop/recall) | Two-person check tends to catch issues earlier | Can block before release (best), or warn (weaker) | If before release/settlement can prevent; if after release but before settlement can still stop settlement if authority exists | Explicitly oriented to 1-business-day audit; becomes partly corrective within ~24h recall window | Requires RA-7 within 1 business day and manager approval before settlement, making timeliness part of the emergency substitute |

Key implication: *A “control occurred” is not equal to “control was sufficient.”* Sufficiency depends on timing, independence, and coverage against the specific threat scenario.

## 2. Equivalence and Sufficiency Test

### 2.1 Structured test (dimensions)

Define the “harmful outcome” as **irrevocable bank settlement** (or the point after which recovery is uncertain). Then evaluate the compensating package along these dimensions:

- **Timing / irreversibility**
  - **Strong**: independent check *before* `Release_Payment` (pre-authorization).
  - **Medium**: independent check after `Release_Payment` but *before* bank settlement **and** with authority to cancel/stop settlement (pre-loss).
  - **Weak**: check after settlement; purely detective.
- **Independence**
  - Different human actors; no shared/service accounts; no undisclosed conflict (e.g., direct supervisor rating the operator).
  - Independence is undermined by repeated exclusive pairing, shared workstations/sessions, or credential sharing.
- **Coverage vs FEP-1’s purpose**
  - Must address at least: payee/bank legitimacy (especially recent changes), amount/limit, duplicate, supporting evidence/receipt, and basic reasonableness.
  - AV-2 coverage is **bounded** to its checks; a “clean pass” is evidence only for those checks.
- **Overrideability & credential integrity**
  - Warnings that can be overridden are weaker; overrides must be attributable to an authorized, independent approver.
  - Any sign of “borrowed credentials” collapses the independence story.
- **Recoverability / correction**
  - Can the organization cancel before settlement? Can the bank recall within ~24h? Is RA-7 completed within that window?
  - After the recall window, “audit” is mainly accountability, not correction.
- **Evidence quality**
  - Logs should show: who approved, when, and (ideally) what was reviewed; emergency token activation time; override rationale; bank-change evidence; workstation/session identity if relevant.
- **Collusion resistance**
  - Requires more than “two different usernames”: rotation, workload separation, and monitoring to avoid “two-person capture.”

### 2.2 Classification mapping (equivalence → control-objective result)

Use this as a decision rule (conceptual, not mechanical):

- **Fully equivalent** → `OBJECTIVE_MET`
  - Independence is credible; a meaningful independent check occurs before irreversibility; AV-2 is operational and passed without override (where required); audit is timely enough to support recall; ED-1 conditions are satisfied when same-user execution is used.
- **Partially equivalent** → `OBJECTIVE_PARTIALLY_MET`
  - Significant mitigation exists (e.g., AV-2 pass + independent manager before settlement), but one major dimension is weaker/uncertain (e.g., manager approval after release, token timing ambiguity, repeated-pair independence concerns, audit slightly late).
- **Merely mitigating (detects but doesn’t prevent)** → tends toward `OBJECTIVE_PARTIALLY_MET` or `OBJECTIVE_FAILED` depending on residual exposure
  - E.g., only retrospective audit after settlement, or overridden warnings without strong independent approval.
- **Ineffective** → `OBJECTIVE_FAILED`
  - Same-user with weak/late/compromised compensations; outages; overrides; conflicted approval; audit outside recovery window; or evidence that the “second person” was not functionally independent.
- **Prevented before completion** → `LOSS_PREVENTED_BEFORE_COMPLETION`
  - Preventive control blocks the release so funds do not leave.
- **Evidence insufficient to decide** → `INDETERMINATE`
  - Critical facts missing (e.g., whether manager ratification could stop settlement; whether token timestamp is real vs log delay; whether approval was substantive).

### 2.3 Why “same expected loss” is not the only standard

Even if two designs had similar *expected* monetary loss, FEP-1-type objectives also encode:

- **Tail-risk reduction** (rare but catastrophic frauds dominate impact).
- **Deterrence and accountability** (the act of needing an independent human changes behavior; audit-after-the-fact does not).
- **Regulatory / governance expectations** (segregation is often required as a *control principle*).
- **Attribution and incident response quality** (credential sharing and rubber-stamping destroy forensic value).
- **Non-monetary harms** (sanctions violations, reputational damage, legal exposure) that are not well captured by “expected loss.”

## 4. Preventive–Detective–Corrective Comparison

### 4.1 Control comparison table

| Control | Preventive | Detective | Corrective | Typical effective timing | Independence requirement | Overrideability / fragility | Main gaps |
|---|---:|---:|---:|---|---|---|---|
| **AV-2** (Automated validation) | High when it **blocks**; medium when it **warns** | Medium (warnings create signals) | Low (doesn’t itself recover funds) | Before release | Independent of humans (system), but depends on system integrity and configuration | Warnings can be overridden; outages eliminate coverage; limited to implemented checks | No receipt/legitimacy, no collusion detection, no commercial reasonableness, cannot prove who controlled compromised account |
| **MG-4** (Manager approval/ratify) | High if before release; medium if after release but before settlement (depends on cancel authority) | Medium if after release (detects improper release) | Medium if it can stop settlement/trigger recall promptly | Best before release; acceptable before settlement if action can still stop funds | Critical: manager must be independent (no conflict) and not preparer/releaser; review must be substantive | Rubber-stamping; conflicts of interest; “approval” via shared credential collapses independence | Can miss technical bank-ownership checks without AV; can be bypassed if not required; may be too late if after settlement |
| **RA-7** (Audit + recall) | Low | High (for anomalies found in audit) | Medium only within recall window and if process can halt/recall quickly | Within 1 business day; ideally <24h from release/settlement | Auditor independence expected | Effectiveness collapses after recall window; depends on audit scope/triage | Cannot reliably recover after 24h; cannot prevent immediate loss; may only document harm |
| **ED-1** (Emergency permission with conditions) | N/A as a single control; **gates** same-user behavior by requiring a stronger package | N/A | N/A | Must be established before prepare; conditions must hold end-to-end | Requires independent manager and audit in addition to AV-2 | Fails if token timing is wrong, AV is unavailable/overridden, amount too high, bank changed recently, or approvals are late | Not collusion-proof; cannot replace goods-receipt control; relies on accurate logging and real necessity |

### 4.2 Semantics of “manager action after release but before settlement”

There are two reasonable semantics, depending on what you define as the “act to be prevented”:

- **Preventive relative to the harmful outcome (bank settlement)**: if the manager has *real authority and time* to cancel/stop settlement, their post-release/pre-settlement action can prevent the money leaving, so it is preventive of loss.
- **Detective relative to internal authorization quality (release step)**: the manager is necessarily detecting that a release already occurred (including any policy breach), and then correcting by stopping settlement.

In this answer, I treat it as a **hybrid**: *detective of an improper release, potentially corrective/preventive of loss* when it occurs before settlement and the organization can actually halt/recall in time.

## 5. Counterfactual and Residual-Risk Analysis

For each case below: plausible loss mechanism, what (if anything) breaks the causal chain, what remains exposed, and how a truly independent second releaser would change things.

### AP-202 (OBJECTIVE_FAILED)

- **Plausible loss mechanism**: new vendor + recent bank change + AV warning + override using a supervisor credential → payment diverted to related party.
- **Chain-break control (actual)**: none effective; AV warned but was overridden; MG-4 was late and conflicted; RA-7 was late.
- **What remains exposed**: full diversion risk, credential compromise risk, governance failure (override path).
- **If truly independent second releaser existed**: would add a hard stop point that likely requires verifying bank change authorization/ownership and vendor onboarding; would reduce the feasibility of single-operator rapid execution and credential misuse. ### AP-203 (OBJECTIVE_MET)

### AP-207 (OBJECTIVE_MET)

- **Plausible loss mechanism**: emergency use could be exploited for wrong payee/bank detail; risk is concentrated in the time between release and manager review.

## 6. Evidence and Monitoring Recommendations

### 6.1 Evidence to collect (so “independence” and “timing” are provable)

- **Settlement events for all cases**: log `Bank_Settlement` (or “sent to bank”) consistently; missing settlement timestamps make “before/after” judgments fragile.
- **Emergency token telemetry**: token activation time, requester, reason code, and linkage to the case; detect tokens created *after* prepare.
- **Manager approval artifacts**: who approved (strong authentication), when, and a minimal attestation of what was reviewed (invoice, bank details, receipt/service report).
- **Override provenance**: explicit “override by manager” events with the actual manager identity; block usage of another person’s credential (MFA, device binding).
- **Workstation/session identifiers**: device ID, session ID, IP, and short-horizon co-login patterns to detect shared workstations that undermine independence.
- **Bank change evidence**: reference to approved vendor master-data change request and independent verification (call-back, supplier confirmation) for recent bank changes.

### 6.2 Monitoring rules (alerts, not proof)

Track and alert on combinations that concentrate risk; treat an alert as triage, not a misconduct verdict:

- **Same-user rate**: percent of completed payments where preparer=releaser.
  - Segment by **ED-1 eligibility** (amount <100k, vendor age ≥180d, no recent bank change, AV pass without override, manager before settlement, audit ≤1 business day).
  - Alert on any same-user completion **without** full ED-1 evidence.
- **Override rate**: count and rate of `Override_Warning`, especially when the warning relates to **bank change** or **operator limit**.
  - Critical alert: override performed with a credential assigned to someone else, or override without an independent manager event near in time.
- **Late manager approval**: manager approval/ratify after settlement (always high concern) or materially after release (exposure window).
- **Audit-before-recall-window**: percent of audits initiated within ~24h; alert when RA-7 exceeds the recall window on any high-risk pattern (new vendor, bank change, high amount, AV outage).
- **Repeated resource pairs**: detect (Prepare, Release) pairs that recur unusually (e.g., u12/u13) and correlate with anomalies; alert on “exclusive pairs” and lack of rotation.
- **Shared workstation indicators**: multiple distinct users executing prepare/release from the same workstation/session within short windows; alert as a “pseudo-independence” risk.
- **Bank-change proximity**: any payment where bank change occurred within 7 days (or tighter windows like 24–72h) should trigger heightened scrutiny; couple with “new vendor” and “AV warning/override.”
- **Control outages**: `Validation_Service_Unavailable` should automatically require enhanced compensations (e.g., mandatory independent manager pre-release + signed checklist + independent bank verification). Alert on any release during outage.

### 6.3 Distinguish alerts from proof

- **An alert is not proof of fraud**: repeated pairs and shared workstations can arise from staffing models; overrides can be legitimate; emergency tokens can be delayed in logging.
- **But alerts are evidence of elevated residual risk**: they justify targeted review of supporting documents, access logs, and credential provenance.

PM4Py behavior I cannot guarantee across versions:

- `pm4py.filter_four_eyes_principle(...)` has varied in some ecosystems between returning **cases that satisfy** the four-eyes principle vs **cases that violate** it (and how it behaves if one of the two activities is missing or occurs multiple times). The code above cross-checks against a direct pandas computation and prints an interpretation note.
- `pm4py.format_dataframe(...)` and `pm4py.convert_to_event_log(...)` signatures can vary (e.g., optional `start_timestamp_key`), and trace attribute keys for case identifiers can differ (`"concept:name"` vs `"case:concept:name"`). The code includes a conservative extractor.
