## 1. Equivalence design space

All relations below compare executions centred on one lead `Order`. Local identifiers are never meaningful in themselves; `EXT-*` is meaningful because it signals sharing with another centred execution.

**1.1 Activity-sequence equivalence, $E_{act}$**

*Definition:* $X\sim Y$ iff their timestamp-ordered activity-label sequences are identical, including repetitions.

*Preserves:* activity order, repetition count, presence of extra steps such as `Return Item`. *Discards:* all object types, multiplicities, E2O/O2O incidence, sharing, qualifiers, and which object recurs.

*Equivalence properties:* reflexive, symmetric, transitive, because it is equality of a sequence.

*Concurrency:* Strictly, timestamp ties make “the sequence” ill-defined. I therefore treat equal-timestamp events as an unordered block, giving a sequence of activity multisets; alternatively, two linear extensions are equivalent when tied events share no object. Merely sorting tied labels alphabetically is reproducible but semantically arbitrary.

This relation is useful as a baseline, not as an object-centric clustering.

**1.2 Typed structural equivalence under renaming, $E_{type}$**

*Definition:* $X\sim Y$ iff there is a bijection between their local objects preserving object type and `EXT` status, and an order-preserving bijection between events preserving activity labels, such that every event has the same multiset of related objects by type, the same objects recur across the same events, and unqualified typed O2O adjacency and cardinalities agree.

*Preserves:* per-event typed multiplicities; object recurrence; split versus consolidated packing/dispatch; numbers of payments; external sharing location structurally; extra E2O links, e.g. an `Item` on `Dispatch`. *Discards:* local names, concrete identity, qualifier meaning such as `replaces`, `removed_before_dispatch`, `partially_settles`, amounts, and business interpretation.

*Equivalence properties:* reflexive, symmetric, transitive: typed graph isomorphism is an equivalence relation.

*Concurrency:* Events are compared as a partial order, not only a list. Precedence is retained when events share an object or have distinct timestamps; independent simultaneous events may be permuted. The two `Add Item` events in X1/X2 are structurally interchangeable.

**1.3 Business-semantic equivalence, $E_{sem}$ — preferred**

*Definition:* $X\sim Y$ iff their canonical semantic signatures (Section 2) are equal. The signature starts from $E_{type}$ and adds: lead-order isolation versus `EXT` sharing by process area; O2O qualifiers; lifecycle motifs such as single/consolidated/split fulfilment, partial payment, replacement/removal, and return–inspect–repack; and causal order among events linked through the same Package, Delivery, Invoice, Item, or Order.

*Preserves:* everything in $E_{type}$, plus whether sharing is logistical or financial, whether settlement is partial or complete at motif level, whether an item was removed/replaced, and whether fulfilment is interrupted by a return loop. *Discards:* local identifiers, exact item identities beyond their relational role, ordering of independent `Add Item` events, timestamps except for causal/partial order, and unprovided attributes such as amounts or reasons.

*Equivalence properties:* reflexive, symmetric, transitive, because equality of a deterministic canonical signature is used. A threshold-based “similarity” would not generally be transitive and is not used here.

*Concurrency:* Independent events, e.g. adding distinct items before packing, commute. Events sharing a Package/Delivery/Invoice retain order: `Pack` before its `Dispatch`, first `Dispatch` before `Return`, `Return` before repacking.

**1.4 Optional coarse motif equivalence, $E_{motif}$**

Collapse every multiplicity $>1$ to `many`, ignore whether multiplicity occurs at Pack, Dispatch, or Payment, and retain only stage order, loops, and sharing area. This can group split-fulfilment variants for capacity planning, but it is too coarse for compliance. It is also an equivalence if defined by canonical motif equality.

## 2. Canonical signatures

Preferred relation: $E_{sem}$. Objects are coloured initially by `(object_type, is_EXT, is_lead_Order)`. Events are coloured by activity. Iterative colour refinement incorporates, for each object, the multiset of incident event colours and qualified O2O neighbours; for each event, the multiset of incident object colours by role/type. If colours remain ambiguous—two otherwise identical Items—choose the lexicographically smallest encoding over colour-preserving bijections. This handles X1 versus X2 without treating identifier order as meaning.

```python
def canonical_signature(execution, lead_type="Order"):
    events = execution.events_sorted_by_time()
    objects = execution.objects()

    # Initial colours ignore local IDs, preserve semantics.
    obj_colour = {o: (o.type, o.is_external, o.type == lead_type)
                  for o in objects}
    evt_colour = {e: e.activity for e in events}

    # Refine until stable: incidence + multiplicity + qualifiers.
    while True:
        new_obj = {}
        for o in objects:
            incident = sorted((evt_colour[e], count_role(e, o))
                              for e in events if o in e.objects)
            o2o = sorted((q, obj_colour[n]) for q, n in o2o_edges(o))
            new_obj[o] = hash((obj_colour[o], incident, o2o))
        new_evt = {}
        for e in events:
            incidence = sorted((obj_colour[o], role(e, o))
                               for o in e.objects)
            new_evt[e] = hash((evt_colour[e], incidence))
        if stable(new_obj, new_evt): break
        obj_colour, evt_colour = relabel(new_obj), relabel(new_evt)

    # Canonical naming: try colour-preserving permutations if needed;
    # choose lexicographically minimal encoding. Small executions: brute force.
    best = None
    for naming in colour_preserving_namings(objects, obj_colour):
        causal_edges = [(naming[e], naming[f])
                        for e, f in causal_precedences(events)
                        # distinct timestamps or shared typed object chain
                        ]
        encoded_events = []
        for e in events_in_partial_order(events, causal_edges):
            by_type = multiset((o.type, o.is_external, naming[o])
                               for o in e.objects)
            encoded_events.append((e.activity, by_type))
        qualifiers = sorted((q, naming[a], naming[b])
                            for q, a, b in execution.o2o_qualified_edges)
        motifs = extract_motifs(encoded_events, qualifiers)
        # motifs: pack_cardinality, dispatch_cardinality, ext_area,
        # payment_count/partial, replacement?, return_loop?
        sig = (tuple(encoded_events), tuple(causal_edges),
               tuple(qualifiers), motifs)
        best = sig if best is None else min(best, sig)
    return best
```

The signature is reproducible: sorting is by type, externality, refined colour, activity, and qualifier—not by raw identifier, except as a deterministic final tie-breaker after renaming-invariance has been established.

## 3. Cluster assignments

Cluster key: `A`=activity, `T`=typed-structural, `S`=preferred semantic. Signatures are abbreviated: `Cr`=Create Order, `Ad`=Add Item, `Pk`=Pack, `Di`=Dispatch, `In`=Issue Invoice, `Pa`=Record Payment; superscripts give relevant typed counts; `EXT-L`=external logistics sharing, `EXT-F`=external financial sharing.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature | Main reason |
|---|---|---|---|---|---|
| X1 | A1 | T1 | S1: Isolated single-package | `Cr[O1] Ad[O1,I1]×2 Pk[O1,I2,P1] Di[O1,P1,D1] In[O1,V1] Pa[O1,V1,M1]` | Baseline; one package, one delivery, one invoice/payment, no EXT, no qualifier anomaly |
| X2 | A1 | T1 | S1: Isolated single-package | Same as X1 after renaming | Item identifiers and Add order are renamings/permutations of independent events |
| X3 | A2 | T2 | S2: Split-pack, consolidated delivery | `Pk×2 each[I1,P1]; Di[O1,P2,D1]; Pa×1` | Two packages but one shared delivery; settlement remains single |
| X4 | A3 | T3 | S3: Split delivery, instalment settlement | `Pk-Di; Pk-Di; In; Pa×2(partialcomplete)` | Fulfilment and payment are both fragmented, interleaved packing/dispatch |
| X5 | A1 | T4 | S4: Cross-order shared logistics | A1 labels; `Pk[O2 incl EXT-O, I3 incl EXT-I, P1] Di[O2,P1,D1]; In/Pa local` | Activity labels hide shared package/delivery with another order |
| X6 | A1 | T5 | S5: Cross-order shared finance | A1 labels; logistics local; `In[O2,V1] Pa[O2,V1,M1]` with EXT Order | Package is private, invoice/payment are jointly shared and unallocated |

| X8 | A4 | T7 | S7: Return–inspect–repack loop | `…Di[P1,D1] Return[I1,D1] Inspect[I1] Pk[I1,P2] Di[P2,D2] In Pa` | Extra reverse-logistics loop and replacement package/delivery |

$E_{act}$ has four clusters; $E_{type}$ and $E_{sem}$ each separate all but X1/X2 here. That is not a claim that the finest partition is generally best; in this dataset each non-baseline execution carries a distinct structural or semantic deviation.

## 5. Borderline cases

**X1 versus X2.** $E_{act}$, $E_{type}$, and $E_{sem}$ all merge them. Only an identifier-sensitive exact method separates them. The reversed Add order is either an irrelevant permutation of independent events or, under a strict total-order encoding that also encodes identifiers, a false difference. Defensible disagreement arises if timestamps were exact and picking order mattered operationally; with the supplied data, merging is correct.

**X1 versus X5.** $E_{act}$ merges them: identical labels. $E_{type}$ and $E_{sem}$ separate them because Pack/Dispatch involve two Orders and three Items, with `EXT` sharing. A logistics-blind financial audit could defensibly merge them; a fulfilment or chain-of-custody analysis must not.

**X1 versus X6.** Again $E_{act}$ merges. $E_{type}$ separates on Invoice/Payment multiplicity; $E_{sem}$ separates more specifically as shared finance rather than shared logistics. If an analyst canonicalises away non-lead Orders, they merge—but that discards allocation risk, so the coarser choice must be explicit.

**X1 versus X7.** $E_{act}$ merges. A purely activity-plus-cardinality method that ignores the extra Item at Dispatch and all qualifiers also merges. $E_{type}$ separates because Dispatch incidence differs; $E_{sem}$ separates even under a repair that normalises that incidence, provided `replaces`/`removed_before_dispatch` is retained. This is the clearest case where labels overstate normality.

**X3 versus X4.** Coarse motif equivalence can merge them as “split fulfilment with two packages.” $E_{act}$, $E_{type}$, and $E_{sem}$ separate them: X3 consolidates both packages into one delivery and pays once; X4 has two deliveries, interleaved Pack/Dispatch, and two-stage settlement. For warehouse capacity the merge may be useful; for carrier cost or collections it is misleading.

**X4 versus X8.** Both involve two Packages, two Deliveries, and repeated Pack/Dispatch, so a multiplicity-only signature may place them close or together. Semantically they differ: X4 is forward split shipment plus partial payment; X8 is a post-dispatch return, inspection, repack, and redispatch with a single final payment. Activity order and the return motif must separate them.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

In PM4Py, `pm4py.cluster_equivalent_ocel(ocel, ...)` partitions an object-centric log into sub-logs whose executions are treated as exactly equivalent under the library’s internal key. Conceptually—and implementations/versions should be checked—the key preserves much more than an activity string: the ordered event/activity structure together with the typed object graph incident to those events, i.e. which object instances participate in which events and how objects are connected through events. That is close to exact typed isomorphism *before* canonical renaming, and in practice raw identifiers can leak into equality through object identity, event/object ordering, timestamps, or connected-component extraction.

Raw identifiers make exact clusters too fine: X1 and X2 are the same process under renaming, yet an ID-sensitive key can put every execution in its own cluster, especially when object IDs are globally unique by construction. Exact clustering then measures naming, not behaviour. Post-processing should therefore: (i) take each returned cluster/sub-log; (ii) extract executions centred on lead objects of type `Order`; (iii) compute the Section-2 canonical signature; (iv) aggregate exact clusters by that signature; and (v) report both levels, because merging exact clusters is a modelling decision.

Exact equivalence is preferable for regression testing, deduplication, audit replay, conformance where object identity and exact incidence matter, and detecting unintended log changes. Coarser semantic clustering is preferable for segmentation and reporting.

`max_objs` (where exposed) and related size limits matter practically: executions sharing Packages, Invoices, or Deliveries can form large connected components spanning many Orders. A cap can truncate external context, split a shared execution, or make results dependent on traversal order; uncapped extraction can be expensive and produce mega-clusters. I would run exact clustering with a documented cap, flag truncated executions, and never silently treat a truncated X5/X6 as isolated.

```python
import pm4py
from collections import defaultdict

# Assume `ocel` is a pm4py OCEL object.
exact_clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=100)

semantic_groups = defaultdict(list)
audit_rows = []

for exact_id, sub_ocel in enumerate(exact_clusters):
    # Lead-centred extraction: one execution per Order object.
    for order_id in object_ids_of_type(sub_ocel, "Order"):
        execution = extract_execution_centred_on(
            sub_ocel, lead_object=order_id, lead_type="Order",
            include_external_context=True)

        sig = canonical_signature(execution, lead_type="Order")  # Section 2
        semantic_groups[sig].append((exact_id, order_id))
        audit_rows.append({
            "exact_cluster": exact_id,
            "lead_order": order_id,          # retained for audit only
            "semantic_signature": sig,
            "n_events": len(execution.events),
            "truncated": execution.was_truncated,
        })

# Aggregation step: many exact clusters -> fewer semantic clusters.
for sig, members in sorted(semantic_groups.items(), key=lambda kv: str(kv[0])):
    print(len(members), sig, members[:5])
```

## 7. Robustness analysis

| Perturbation | Effect on assignments | Interpretation |
|---|---|---|
| Ignore all O2O qualifiers | X7 remains separate under my $E_{type}$ because Dispatch carries an Item, but its *meaning* becomes “dispatch with explicit item reference,” not replacement. If Dispatch incidence is also normalised, X7 collapses into S1. X4 loses `partially_settles`, though two Payments still signal instalments. X8 loses `replaces` for P82 but keeps the return loop. | Qualifiers are decisive mainly for X7; elsewhere they refine rather than create clusters. |
| Ignore external objects | X5’s Pack/Dispatch reduce toward one Order/two local Items plus an unexplained extra Item if EXT Item is dropped inconsistently; with consistent dropping, X5S1. X6S1. X1/X2 unchanged. | This is the most dangerous repair: it manufactures isolation and destroys S4/S5, precisely where risk concentrates. |
| Collapse repeated same-label events | X1/X2 lose the second Add; X3 loses split packing; X4 loses second Pack/Dispatch/Payment; X8’s two Pack/Dispatch collapse, making the return loop look like a simple exception or even baseline with extra Return/Inspect. | Repetition encodes multiplicity and fragmentation; collapsing is only defensible for a very coarse motif view. |
| Treat Pack/Dispatch order as partial order | X1–X3, X5–X7 unchanged materially. X4 remains distinct because each Pack precedes its own Dispatch through a shared Package, and it still has two Deliveries/Payments. X8 remains distinct because Return depends on D81 and repack depends on Return/Inspect. No new merges under causal partial order; a careless “bag of Pack/Dispatch” would over-merge. | Partial order removes false sequencing sensitivity without erasing object-mediated causality. |
| Payment multiplicity as amount attribute | If two payments become one `amount_total` plus `n_payments=2` retained as an attribute, X4 may stay separate only if the attribute is in the signature. If structure alone is kept and payments are aggregated to one event, X4 moves closer to X3-like split fulfilment and could merge under $E_{motif}$. | Amounts can be more informative than counts, but replacing structure with a total hides partial-settlement behaviour. |

Overall, S1/S2/S7 are comparatively robust; S6 is qualifier-fragile; S4/S5 are external-context-fragile; S3 is payment-representation-fragile.

## 8. Limitations and recommendation

No single equivalence is best because the purposes punish different errors. Fine partitions preserve evidence but fragment samples; coarse partitions support statistics but can hide exactly the exception that matters.

| Purpose | Recommended level | Rationale |
|---|---|---|
| Compliance monitoring | $E_{type}$ plus qualifiers and EXT context—close to $E_{sem}$, with exact PM4Py clusters retained for audit | Missing a shared invoice, removed item, or partial settlement is a false negative with legal/financial consequence. Identifier-renaming invariance is still needed so that renaming does not create fake violations. |
| Operational segmentation | Preferred $E_{sem}$, possibly relaxed to $E_{motif}$ for high-volume reporting | Segments should correspond to distinct handling: consolidated, split-pack, split-delivery, shared logistics/finance, replacement, returns. These have different costs, owners, and interventions. |
| Root-cause analysis | Start at $E_{sem}$, then drill into exact clusters and individual executions | Coarse clusters give comparable cohorts; exact subclusters reveal whether a “return cluster” is driven by one carrier, item, or data-quality artefact. Beginning with exact IDs would drown the signal. |
| Descriptive reporting | $E_{act}$ supplemented by semantic exception rates | Executives need stable headline flows, but reporting only labels would claim X1/X5/X6/X7 are identical. Report the baseline flow and the share deviating by sharing, split, replacement, payment, or return motif. |

Limitations: the dataset supplies no timestamps beyond order, amounts, timestamps durations, object attributes, reasons, or allocation proportions for shared invoices/packages. I therefore cannot distinguish intentional substitution from error in X7, efficient co-packing from contamination in X5, or joint billing fairness in X6. Canonical graph naming can be expensive for very large connected executions, and colour refinement needs a backtracking fallback for symmetric objects. Finally, semantic motifs involve analyst judgement: they must be versioned, documented, and sensitivity-tested under Section 7 perturbations rather than presented as discovered truth.
