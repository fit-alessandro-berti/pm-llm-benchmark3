## 3. Causal-abductive explanation

```text
[UI_release (May 31)] --------> [recorded_labels ("Risk Screen")] ---\
[ETL_change (Jun 15)] ---------> [recorded_order (Invert Dec/Not)] ----+--> [alignment_moves (Log/Model Inconsistencies)] --> [measured_fitness (32% -> 89%)]
[Gateway_release (Jun 3)] ----> [recorded_events ("Queue Routed")] --/                                                               ^
                                                                                                                                     |
[policy_change (Aug 1)] ------> [true_process (Adds Sign-off)] -------> [normative_model (Obsolete/Missing Sign-off)] -------------/
                                        |
[reviewer_behavior] --------------------+--> [true_process (55 Bypasses / Overrides)] ---> [business_outcomes (Stable but Masked Risk)]
```

The measured drop in conformance from 93% to 32% is a multi-causal composite artifact dominated by technical logging and data engineering mutations, overlaid with real operational drift. First, software UI release 4.2 renamed `Classify` to `Risk Screen`, causing immediate label-mismatch alignment moves. Second, the June 3 gateway deployment introduced a purely technical logging artifact (`Queue Routed`). Third, the June 15 ETL change substituted warehouse ingestion timestamps for event occurrence timestamps, artificially inverting `Decision` and `Notify`. Reversing these three data pipeline issues restores conformance to 89%.

However, data extraction errors do not account for all variance. On August 1, a legitimate policy change introduced `Supervisor Sign-off` for high-value claims (> EUR 50k), rendering the normative control-flow tree obsolete. Furthermore, a persistent residual fraction of traces exhibits potential employee noncompliance (55 cases skipping `Compliance Check` after `Enhanced Review`, plus manual overrides). 

Unchanged business outcomes (stable appeal rates ~3.7%, cycle time ~26.5h) neither prove data hygiene nor rule out noncompliance. Aggregate KPIs mask localized risks: an unperformed compliance check on a fraudulent claim will not alter aggregate approval rates if the overall volume dominates, nor will it drive immediate customer appeals if noncompliant approvals favor the applicant.

## 6. PM4Py reproduction and model-comparison code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.conversion.process_tree import converter as pt_converter
from pm4py.algo.conformance.alignments.petri_net import algorithm as alignments
from pm4py.algo.evaluation.fitness import algorithm as fitness_evaluator
from pm4py.algo.evaluation.precision import algorithm as precision_evaluator
import pandas as pd

# 1. Encode normative process tree
# Tree: -> ( Receive, Classify, X( * ( Standard Review, Request Info ), -> ( Enhanced Review, Compliance Check ) ), Decision, Notify )
receive = ProcessTree(label="Receive")
classify = ProcessTree(label="Classify")

# Loop: Standard Review, Request Info
std_review = ProcessTree(label="Standard Review")
req_info = ProcessTree(label="Request Info")
loop_branch = ProcessTree(operator=Operator.LOOP, children=[std_review, req_info])

# Sequence: Enhanced Review -> Compliance Check
enh_review = ProcessTree(label="Enhanced Review")
comp_check = ProcessTree(label="Compliance Check")
seq_enh = ProcessTree(operator=Operator.SEQUENCE, children=[enh_review, comp_check])

# XOR Choice
xor_choice = ProcessTree(operator=Operator.XOR, children=[loop_branch, seq_enh])

decision = ProcessTree(label="Decision")
notify = ProcessTree(label="Notify")

normative_tree = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[receive, classify, xor_choice, decision, notify]
)

# 2. Convert to Petri net
net_norm, im_norm, fm_norm = pt_converter.apply(normative_tree)

# 3. Define Trace Variants for periods
apr_may_variants = {
    ("Receive", "Classify", "Standard Review", "Decision", "Notify"): 380,
    ("Receive", "Classify", "Enhanced Review", "Compliance Check", "Decision", "Notify"): 180,
    ("Receive", "Classify", "Standard Review", "Request Info", "Standard Review", "Decision", "Notify"): 40
}

june_july_variants = {
    ("Receive", "Risk Screen", "Queue Routed", "Standard Review", "Decision", "Notify"): 270,
    ("Receive", "Risk Screen", "Queue Routed", "Enhanced Review", "Compliance Check", "Decision", "Notify"): 145,
    ("Receive", "Risk Screen", "Queue Routed", "Standard Review", "Notify", "Decision"): 70,
    ("Receive", "Risk Screen", "Standard Review", "Decision", "Notify"): 90,
    ("Receive", "Classify", "Queue Routed", "Standard Review", "Decision", "Notify"): 30,
    ("Receive", "Risk Screen", "Queue Routed", "Enhanced Review", "Decision", "Notify"): 25,
    ("Receive", "Risk Screen", "Queue Routed", "Manual Override", "Standard Review", "Decision", "Notify"): 20
}

aug_sep_variants = {
    ("Receive", "Risk Screen", "Queue Routed", "Standard Review", "Decision", "Notify"): 210,
    ("Receive", "Risk Screen", "Queue Routed", "Enhanced Review", "Compliance Check", "Supervisor Sign-off", "Decision", "Notify"): 150,
    ("Receive", "Risk Screen", "Queue Routed", "Enhanced Review", "Compliance Check", "Decision", "Notify"): 90,
    ("Receive", "Risk Screen", "Queue Routed", "Standard Review", "Supervisor Sign-off", "Decision", "Notify"): 60,
    ("Receive", "Risk Screen", "Queue Routed", "Standard Review", "Notify", "Decision"): 45,
    ("Receive", "Risk Screen", "Queue Routed", "Enhanced Review", "Decision", "Notify"): 30,
    ("Receive", "Risk Screen", "Queue Routed", "Manual Override", "Standard Review", "Decision", "Notify"): 35
}

def variants_to_log(variant_dict):
    rows = []
    case_id = 0
    for trace, count in variant_dict.items():
        for _ in range(count):
            case_str = f"case_{case_id}"
            for idx, act in enumerate(trace):
                rows.append({
                    "case:concept:name": case_str,
                    "concept:name": act,
                    "time:timestamp": pd.Timestamp("2026-06-01") + pd.Timedelta(minutes=idx)
                })
            case_id += 1
    df = pd.DataFrame(rows)
    return pm4py.format_dataframe(df, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")

log_apr_may = variants_to_log(apr_may_variants)
log_jun_jul_raw = variants_to_log(june_july_variants)
log_aug_sep_raw = variants_to_log(aug_sep_variants)

# 4 & 5. Discover DFG and Fitness on Apr-May
dfg_apr_may = pm4py.discover_dfg(log_apr_may)
fit_apr_may = fitness_evaluator.apply(log_apr_may, net_norm, im_norm, fm_norm)
print(f"Apr-May Raw Fitness: {fit_apr_may['log_fitness']:.4f}")

# 6 & 7. Normalization pipeline on Jun-Jul
# Mapping Risk Screen -> Classify, removing Queue Routed, re-ordering Decision/Notify
def normalize_log(df_in, map_label=True, remove_queue=True, fix_order=True):
    df = df_in.copy()
    if map_label:
        df["concept:name"] = df["concept:name"].replace({"Risk Screen": "Classify"})
    if remove_queue:
        df = df[df["concept:name"] != "Queue Routed"].copy()
    if fix_order:
        # Swap Notify -> Decision to Decision -> Notify within traces
        cases = []
        for case_id, group in df.groupby("case:concept:name"):
            acts = list(group["concept:name"])
            for i in range(len(acts)-1):
                if acts[i] == "Notify" and acts[i+1] == "Decision":
                    acts[i], acts[i+1] = "Decision", "Notify"
            g_new = group.copy()
            g_new["concept:name"] = acts
            cases.append(g_new)
        df = pd.concat(cases, ignore_index=True)
    return pm4py.format_dataframe(df, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")

log_jun_jul_norm = normalize_log(log_jun_jul_raw, map_label=True, remove_queue=True, fix_order=True)
fit_jun_jul_raw = fitness_evaluator.apply(log_jun_jul_raw, net_norm, im_norm, fm_norm)
fit_jun_jul_norm = fitness_evaluator.apply(log_jun_jul_norm, net_norm, im_norm, fm_norm)

print(f"Jun-Jul Raw Fitness: {fit_jun_jul_raw['log_fitness']:.4f}")
print(f"Jun-Jul Normalized Fitness: {fit_jun_jul_norm['log_fitness']:.4f}")

# 8. Candidate model for Aug-Sep (optional Supervisor Sign-off)
sup_signoff = ProcessTree(label="Supervisor Sign-off")
tau = ProcessTree() # silent / optional choice
opt_signoff = ProcessTree(operator=Operator.XOR, children=[sup_signoff, tau])

candidate_tree = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[receive, classify, xor_choice, opt_signoff, decision, notify]
)
net_cand, im_cand, fm_cand = pt_converter.apply(candidate_tree)

log_aug_sep_norm = normalize_log(log_aug_sep_raw, map_label=True, remove_queue=True, fix_order=True)

fit_aug_sep_normative = fitness_evaluator.apply(log_aug_sep_norm, net_norm, im_norm, fm_norm)
fit_aug_sep_candidate = fitness_evaluator.apply(log_aug_sep_norm, net_cand, im_cand, fm_cand)

prec_aug_sep_normative = precision_evaluator.apply(log_aug_sep_norm, net_norm, im_norm, fm_norm)
prec_aug_sep_candidate = precision_evaluator.apply(log_aug_sep_norm, net_cand, im_cand, fm_cand)

print(f"Aug-Sep Normative Model Fitness: {fit_aug_sep_normative['log_fitness']:.4f}, Precision: {prec_aug_sep_normative:.4f}")
print(f"Aug-Sep Candidate Model Fitness: {fit_aug_sep_candidate['log_fitness']:.4f}, Precision: {prec_aug_sep_candidate:.4f}")

# 9. Print Caveats
print("\n--- GOVERNANCE & MODELING CAVEATS ---")
print("1. Control-Flow Limitation: The candidate process tree treats 'Supervisor Sign-off' as optional")
print("   for ALL cases purely in control-flow. It cannot enforce the business rule requirement (> EUR 50,000).")
print("2. Overgeneralization Risk: The relaxed model allows low-value claims (< EUR 50k) to undergo or skip")
print("   sign-off without triggering conformance violations, reducing precision and masking policy misuse.")
print("3. Data-Aware Conformance Needed: Full validation requires a Data-Aware Petri Net (DPN) or DPDFG")
print("   evaluating the expression: IF claim_amount > 50000 THEN mandatory(Supervisor Sign-off).")
```

## 7. Provisional conclusion

### Primary Explanation for Conformance Collapse
The measured collapse in process conformance—dropping sharply from 93% in May to 32% in June/July—is primarily driven by a compound series of uncoordinated IT release artifacts and extraction failures, rather than systemic operational breakdown. Specifically:
1. **Interface Label Shift**: UI Release 4.2 renamed the `Classify` step to `Risk Screen`, rendering all incoming activity logs structurally non-conformant against the static normative process tree.
2. **Technical Logging Noise**: The event gateway release on June 3 introduced non-functional `Queue Routed` system events directly into the main case traces.
3. **ETL Sequence Inversion**: The June 15 ETL pipeline update switched timestamps to warehouse ingestion times, corrupting the temporal ordering of `Decision` and `Notify`.

Applying technical remediation (label mapping, gateway filtering, and sequence re-ordering) restores measured conformance from 32% to 89%.

### Assessment of Remaining Compliance Risk
Despite data extraction defects accounting for the majority of the fitness loss, **a genuine operational compliance risk persists**. Specifically, across the June–September logs, 55 recorded traces exhibit an `Enhanced Review` followed immediately by `Decision`, bypassing the mandatory `Compliance Check`. Furthermore, the appearance of `Manual Override` activities (55 cases total) indicates potential reviewer workarounds that circumvent standard control gates. The stable business outcomes (appeal rates ~3.7%, cycle time ~26.5h) do not disprove these violations, as non-compliant approvals naturally avoid customer appeals.

### Confidence Levels
- **Data Pipeline Defect Causality**: **95% Confidence** (Validated via manual audits, ETL code commit records, and alignment recovery).
- **Residual Operational Noncompliance Risk**: **80% Confidence** (Confirmed in trace variants, pending physical verification of case files).

### Immediate Actions
1. **IT / Data Engineering**: Update the ETL pipeline to re-map `Risk Screen` -> `Classify`, exclude pure gateway queue events from process mining views, and restore transaction-sequence-based event ordering.
2. **Process Owners**: Submit a formal change request to update the normative model to version 2.0, incorporating data-aware conditional rules for `Supervisor Sign-off` on claims exceeding EUR 50,000.
3. **Compliance**: Initiate a targeted manual audit of the 55 cases showing bypassed compliance checks and investigate the specific user roles executing `Manual Override`.

### What Must NOT Be Claimed Yet
- **Do not claim that reviewers are broadly non-compliant** or blameworthy for the initial drop from 93% to 32%.
- **Do not claim that the process is fully compliant** simply because business KPIs (appeal rates and cycle times) remained steady.
- **Do not claim that the extended process model is final** until data-aware attributes (`claim_amount`) are formally linked to the conformance checking engine.

## 8. Model-governance recommendation

1. **Synchronized Model-Release Versioning**: No software UI modification or business policy update affecting process activity names or control flows may be deployed to production without a concurrent versioned update to the process mining normative model repository.
2. **Interface Semantic Contracts**: Establish binding API/logging contracts between front-end UI teams and data engineering. UI display label changes (e.g., `Classify` to `Risk Screen`) must preserve underlying database semantic event keys.
3. **Strict Separation of Technical Events**: Pure middleware, queue routing, and system orchestration events must be logged into a dedicated infrastructure log table and explicitly excluded from business-level event logs used for regulatory compliance monitoring.
4. **Timestamp and Sequence Provenance Mandate**: Process mining pipelines must strictly utilize immutable source-system transactional timestamps and monotonically increasing sequence numbers rather than database warehouse ingestion times for event ordering.
5. **Data-Aware Conformance Engine Integration**: Transition regulatory conformance checking from pure control-flow process trees to Data-Aware Petri Nets (DPNs) that evaluate decision rules (e.g., mandatory `Supervisor Sign-off` conditional upon `claim_amount > EUR 50,000`).
6. **Mandatory Post-Release Conformance Validation**: Require automated post-release process mining regression testing within 7 days of any software update or policy deployment to detect logging corruptions or unintended operational drift immediately.
