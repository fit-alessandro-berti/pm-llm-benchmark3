Both DFG directions for the same pair do **not** prove concurrency. A DFG edge means that, in at least one observed case, one completion event was recorded before another completion event. # 2. Shared Assumptions

- **Completion-event semantics:** Activity labels are interpreted as completed activities. When a model says `Credit Check` precedes `Engineering Review`, this means the logged completion of `Credit Check` precedes the logged completion of `Engineering Review` unless otherwise stated.
- **No causal/concurrency proof:** No model claims that completion order proves true sequence, concurrency, overlap, or enabling. A partial order in a model means “the model does not constrain the relative order of these visible completions.”
- **Start and end:** `Register Order` is always first and `Archive Case` is always last, per D1 and all traces.
- **Mandatory tail:** `Approve Configuration  Release Production  Archive Case` is mandatory and ordered, per D2 and all traces.
- **Principal checks:** `Credit Check` and `Engineering Review` must both be completed before `Approve Configuration`, per D3, but their relative order is uncertain.
- **Supplier Confirmation absence:** A trace without `Supplier Confirmation` is treated as either a genuine skip or a missing exported event. The models do **not** distinguish these because the external/stocked attribute and missing-event flag are absent.
- **Optionality abstraction:** Optional activities are modeled with XOR branches containing either the activity or a silent skip. For Supplier Confirmation, this is an abstraction over two mechanisms: legitimate skip and data loss.
- **Expedite Review:** Modeled as optional, at most once, after both principal checks and before approval, per D6/S6.
- **No repeated activities:** None of the listed activities is assumed to repeat in a single case.
- **Frequency treatment:** Trace counts inform plausibility but are not encoded as probabilities or weights in the PM4Py models.

# 3. Conservative Candidate

**Inductive bias.** The conservative model treats the observed variants as the only defensible language. It prioritizes not admitting any completion-order behavior that has not been seen, and it gives priority to high-confidence rules plus the exact empirical variants. This is an intentionally low-generalization, low-risk hypothesis: it is useful as a replay/conformance baseline, but it confuses “not observed” with “impossible.” It also ignores frequency except through branch inclusion, so a 12-case variant and a 1-case variant receive the same structural status.

**Compact formal expression.** Let `RO=Register Order`, `CC=Credit Check`, `ER=Engineering Review`, `SC=Supplier Confirmation`, `EX=Expedite Review`, `AP=Approve Configuration`, `RP=Release Production`, `AR=Archive Case`.

`model_conservative = XOR(V1, V2, V3, V4, V5, V6, V7)` with:

- `V1 = RO  CC  ER  SC  AP  RP  AR`
- `V2 = RO  ER  CC  SC  AP  RP  AR`
- `V3 = RO  CC  ER  AP  RP  AR`
- `V4 = RO  ER  CC  AP  RP  AR`
- `V5 = RO  CC  SC  ER  AP  RP  AR`
- `V6 = RO  CC  ER  SC  EX  AP  RP  AR`
- `V7 = RO  ER  CC  EX  SC  AP  RP  AR`

**Self-contained PM4Py code.**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def pt_leaf(label):
    return ProcessTree(label=label)

def pt_seq(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def pt_xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

observed_variants = [
    ("Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
     "Approve Configuration", "Release Production", "Archive Case"),
    ("Register Order", "Engineering Review", "Credit Check", "Supplier Confirmation",
     "Approve Configuration", "Release Production", "Archive Case"),
    ("Register Order", "Credit Check", "Engineering Review",
     "Approve Configuration", "Release Production", "Archive Case"),
    ("Register Order", "Engineering Review", "Credit Check",
     "Approve Configuration", "Release Production", "Archive Case"),
    ("Register Order", "Credit Check", "Supplier Confirmation", "Engineering Review",
     "Approve Configuration", "Release Production", "Archive Case"),
    ("Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
     "Expedite Review", "Approve Configuration", "Release Production", "Archive Case"),

     "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case"),

    pt_seq(*[pt_leaf(a) for a in variant])
    for variant in observed_variants

```

**Behavior deliberately excluded.**

- `RO, ER, SC, CC, AP, RP, AR`: SC directly after ER is unobserved.
- `RO, CC, ER, EX, AP, RP, AR`: Expedite without SC is unobserved.
- `RO, ER, SC, CC, EX, SC, AP, RP, AR`: repeated or newly ordered SC behavior is excluded.
- Any case where `AP`, `RP`, or `AR` is skipped or reordered.
- Any case where `EX` appears before CC and ER.
- Any unobserved interleaving of CC, ER, SC, and EX.

**Known underfitting risks.**

- Misses legitimate unseen completion interleavings if S2 is correct.
- Treats the 5–10% possible missing SC events as evidence for true optionality only in the exact observed positions.
- Cannot generalize to external/stocked conditionality because that attribute is absent.
- Overfits low-count variants, including the two single-case Expedite traces.
- Duplicate labels across XOR branches, especially the shared `Register Order` prefix, can make conformance diagnostics ambiguous and can cause state-space growth as the number of variants increases.
- Scalability is linear in the number of enumerated variants before conversion, but the converted state space may grow substantially because many branches share labels.

# 4. Balanced Candidate

**Inductive bias.** The balanced model generalizes beyond the seven observed variants but only along dimensions supported by multiple pieces of evidence. It treats CC and ER as flexibly ordered because both DFG directions and S2 support completion-order flexibility, while still requiring both before approval per D3. It treats SC as optional because stocked cases and missing-export effects are both plausible, and when SC is present it allows SC to depend on either CC or ER alone, reflecting D5 without making D5 absolute. It treats EX as optional but tightly constrained: after both principal checks, before approval, and unordered relative to SC.

**Compact formal expression.**

`model_balanced = RO  XOR(P_CC, P_ER, P_noSC)  AP  RP  AR`

Where each `P_*` is a partial order over CC, ER, optional SC, and optional EX:

- `P_CC`: `CC  EX`, `ER  EX`, `CC  SC`; no order between CC and ER; no order between SC and EX.
- `P_ER`: `CC  EX`, `ER  EX`, `ER  SC`; no order between CC and ER; no order between SC and EX.
- `P_noSC`: `CC  EX`, `ER  EX`; no order between CC and ER; SC silently skipped.

Here `EX` is itself an XOR between the visible `Expedite Review` and a silent skip.

**Self-contained PM4Py code.**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def build_balanced_check_region(sc_prereq):
    # sc_prereq is "CC", "ER", or None.
    cc = Transition("Credit Check")
    er = Transition("Engineering Review")

    # Optional expedite: choosing SilentTransition means no visible Expedite event.
    ex_choice = OperatorPOWL(
        Operator.XOR,
        [Transition("Expedite Review"), SilentTransition()]
    )

    nodes = [cc, er, ex_choice]

    if sc_prereq in ("CC", "ER"):
        sc = Transition("Supplier Confirmation")
        nodes.append(sc)

    po = StrictPartialOrder(nodes=nodes)

    # D6/S6: Expedite requires both principal checks and precedes approval.
    po.order.add_edge(cc, ex_choice)
    po.order.add_edge(er, ex_choice)

    # D5 as a branch-specific soft dependency: SC may follow either CC or ER.
    if sc_prereq == "CC":
        po.order.add_edge(cc, sc)
    elif sc_prereq == "ER":
        po.order.add_edge(er, sc)

    return po

balanced_region = OperatorPOWL(
    Operator.XOR,
    [
        build_balanced_check_region("CC"),
        build_balanced_check_region("ER"),
        build_balanced_check_region(None),
    ]
)

model_balanced = OperatorPOWL(
    Operator.SEQUENCE,
    [
        Transition("Register Order"),
        balanced_region,
        Transition("Approve Configuration"),
        Transition("Release Production"),
        Transition("Archive Case"),
    ]
)
```

**How sequence, concurrency, and partial order were decided.**

- **RO, AP, RP, AR:** sequence. All 30 traces and D1/D2 support this.
- **CC vs ER:** partial order with no edge between them. Both completion directions occur, S2 says order is variable, and D7 says completion order does not reveal true concurrency. This is a modeling choice of “no enforced visible order,” not a claim of real parallel execution.
- **SC:** optional XOR. S3/S4 conflict, and the external/stocked attribute is absent; S5 says some missing SC events may be export loss. When SC is present, the model uses two partial-order branches, `CC  SC` and `ER  SC`, to encode D5 while allowing both observed “SC after CC only” and “SC after ER only” possibilities.
- **EX:** optional XOR inside a partial order. Edges `CC  EX` and `ER  EX` encode D6/S6. There is deliberately no edge between SC and EX, because V7 and S6 allow EX before SC, while V6 allows EX after SC.
- **SC vs EX:** unordered. Evidence supports both `SC  EX` and `EX  SC`; no stronger rule is defensible.

**Behavior deliberately excluded.**

- Expedite before either CC or ER.
- More than one Expedite Review.
- Supplier Confirmation after approval.
- Supplier Confirmation before both CC and ER.
- Any trace missing CC, ER, AP, RP, or AR.
- Any reordering of AP, RP, AR.

**Known underfitting risks.**

- Still rejects SC before both principal checks, even though permissive interpretation of D5 might allow it.
- Does not condition SC on external/stocked status because the attribute is unavailable.
- Does not model probabilities or frequencies; rare and common completions are structurally similar.
- Treats missing SC and true skip using the same silent branch.
- Does not represent actual parallel start/overlap semantics, only completion-order flexibility.

# 5. Permissive Candidate

**Inductive bias.** The permissive model treats D5 as a weak tendency rather than a hard prerequisite. It admits any reasonable completion order in which SC occurs at most once before approval, EX occurs at most once after both principal checks and before approval, and the mandatory start/check/approval/release/archive backbone is respected. This is useful for sensitivity analysis and exploration, especially if integration loss or unobserved routing is larger than expected, but it has a higher risk of admitting behavior that compliance would reject.

**Compact formal expression.**

`model_permissive = RO  P_broad  AP  RP  AR`

Where `P_broad` contains:

- `CC`, `ER` unordered.
- Optional `SC` anywhere before AP.
- Optional `EX` with `CC  EX` and `ER  EX`.
- No order constraint between `SC` and `EX`.

**Self-contained PM4Py code.**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def build_permissive_check_region():
    cc = Transition("Credit Check")
    er = Transition("Engineering Review")

    sc_choice = OperatorPOWL(
        Operator.XOR,
        [Transition("Supplier Confirmation"), SilentTransition()]
    )

    ex_choice = OperatorPOWL(
        Operator.XOR,
        [Transition("Expedite Review"), SilentTransition()]
    )

    nodes = [cc, er, sc_choice, ex_choice]
    po = StrictPartialOrder(nodes=nodes)

    # D6/S6: Expedite requires both principal checks.
    po.order.add_edge(cc, ex_choice)
    po.order.add_edge(er, ex_choice)

    # D5 is not enforced as a hard prerequisite here:
    # SC may occur before, between, or after the principal checks,
    # provided the whole partial order finishes before approval.
    return po

permissive_region = build_permissive_check_region()

model_permissive = OperatorPOWL(
    Operator.SEQUENCE,
    [
        Transition("Register Order"),
        permissive_region,
        Transition("Approve Configuration"),
        Transition("Release Production"),
        Transition("Archive Case"),
    ]
)
```

**Boundary between reasonable generalization and forbidden behavior.**

Reasonable but unobserved generalizations admitted here include SC before CC/ER, SC between CC and ER, EX before or after SC, and flexible CC/ER completion order. These are treated as possible because D5 is low-to-medium confidence, SC absence may be data loss, and completion timestamps are ambiguous.

Forbidden behavior remains:

- Missing `Register Order`, `Approve Configuration`, `Release Production`, or `Archive Case`.
- Reordering `AP  RP  AR`.
- Missing CC or ER.
- EX before both CC and ER.
- More than one EX.
- More than one SC.
- SC after approval.
- Any activity before registration or after archive.

**Behavior deliberately excluded.**

- `RO, EX, CC, ER, AP, RP, AR`: EX before principal checks.
- `RO, CC, AP, RP, AR`: missing ER.
- `RO, CC, ER, RP, AR`: release without approval.
- `RO, CC, ER, EX, EX, AP, RP, AR`: duplicated Expedite Review.
- `RO, CC, ER, AP, SC, RP, AR`: SC after approval.

**Known underfitting risks.**

- Underfits D5 if “after either CC or ER” is actually mandatory.
- Does not distinguish external cases requiring SC from stocked cases skipping SC.
- Does not encode missing-event probability or data-source quality.
- Does not model conditional dependencies based on credit result, engineering outcome, due date, or expedite reason.
- Because it is broad, it may underfit compliance constraints that are not represented as hard edges.

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| Expected fitness on the 30 observed cases | Perfect by construction | Expected perfect; all observed variants are included | Expected perfect; all observed variants are included |
| Expected precision risk | Lowest; only observed completions admitted | Moderate; admits selected unobserved but plausible interleavings | High; admits broad unobserved orders, especially SC before checks |
| Generalization potential | Very low | Moderate and evidence-guided | High |
| Structural simplicity | Structurally simple idea, but seven explicit XOR branches with repeated prefixes | Moderate; three partial-order branches plus optional EX | High structural simplicity, but broad behavior |
| Explainability | Easy to explain as “only what was observed”; harder to defend as process truth | Best compromise: each edge/branch maps to a rule or conflict | Easy to explain as broad constraints, but weak on disputed D5 |
| Robustness to missing Supplier Confirmation events | Low; skip positions are frozen to observed variants | Moderate-high; skip is a first-class branch, but still cannot identify missing cases | High-ish; broad SC placement absorbs uncertainty but may hide data-quality issues |
| Handling of unseen interleavings | None | Many plausible CC/ER/SC/EX interleavings | Broadest, including SC before checks |
| Suitability for compliance versus exploration | Strict replay/compliance baseline only | Best for immediate compliance-aware use with uncertainty | Sensitivity analysis, stress testing, exploration |

def pt_leaf(label):
    return ProcessTree(label=label)

def pt_seq(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def pt_xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

def normalize_metric_value(x):
    if isinstance(x, dict):
        for key in ("log_fitness", "fitness", "precision", "value", "score"):
            if key in x and isinstance(x[key], (int, float)):
                return x[key]

        return numeric[0] if numeric else x
    return x

def safe_metric(fn, *args, **kwargs):
    try:
        return normalize_metric_value(fn(*args, **kwargs))
    except Exception as e:
        return "unavailable: {}: {}".format(type(e).__name__, e)

# 4. Bounded token playout directly on the converted Petri nets

def build_net_index(net):
    place_by_id = {id(p): p for p in net.places}
    transitions = sorted(
        net.transitions,
        key=lambda t: (str(getattr(t, "name", "")), str(getattr(t, "label", "")), id(t))
    )

    arcs_in = {id(t): [] for t in transitions}
    arcs_out = {id(t): [] for t in transitions}

    for a in net.arcs:
        w = getattr(a, "weight", 1)
        if w is None:
            w = 1
        w = int(w)

        if id(a.target) in arcs_in and id(a.source) in place_by_id:
            arcs_in[id(a.target)].append((id(a.source), w))

        if id(a.source) in arcs_out and id(a.target) in place_by_id:
            arcs_out[id(a.source)].append((id(a.target), w))

    return {
        "place_by_id": place_by_id,
        "transitions": transitions,
        "arcs_in": arcs_in,
        "arcs_out": arcs_out,
    }

def mkey_from_marking(marking):
    return tuple(sorted((id(p), int(c)) for p, c in marking.items() if c))

def marking_from_mkey(mkey, place_by_id):
    return {place_by_id[pid]: cnt for pid, cnt in mkey}

def visible_label(t):
    lab = getattr(t, "label", None)
    if lab is None or lab == "":
        return None
    return str(lab)

def is_enabled(mkey, tid, idx):
    marking = dict(mkey)
    return all(marking.get(pid, 0) >= w for pid, w in idx["arcs_in"][tid])

def fire(mkey, tid, idx):
    marking = dict(mkey)

    for pid, w in idx["arcs_in"][tid]:
        marking[pid] -= w
        if marking[pid] == 0:
            del marking[pid]

    for pid, w in idx["arcs_out"][tid]:
        marking[pid] = marking.get(pid, 0) + w

    return tuple(sorted(marking.items()))

def bounded_playout(net, im, fm, max_events=10, max_traces=500, max_states=100000):
    idx = build_net_index(net)
    start = mkey_from_marking(im)
    final = mkey_from_marking(fm)

    q = deque([(start, ())])
    seen = set()
    traces = []
    hit_bound = False

    while q and len(traces) < max_traces and len(seen) < max_states:
        mkey, trace = q.popleft()
        state = (mkey, trace)
        if state in seen:
            continue
        seen.add(state)

        if mkey == final:
            if trace not in traces:
                traces.append(trace)
            continue

        if len(trace) >= max_events:
            hit_bound = True
            continue

        for t in idx["transitions"]:
            tid = id(t)
            if not is_enabled(mkey, tid, idx):
                continue

            lab = visible_label(t)
            new_mkey = fire(mkey, tid, idx)
            new_trace = trace + ((lab,) if lab is not None else ())

            if len(new_trace) <= max_events:
                q.append((new_mkey, new_trace))

            if len(q) + len(seen) >= max_states:
                hit_bound = True
                break

    return traces, (hit_bound or len(traces) >= max_traces or len(seen) >= max_states)

playout_summary = {}
for name, (net, im, fm) in pnets.items():
    traces, hit_bound = bounded_playout(net, im, fm)
    playout_summary[name] = {
        "bounded_trace_count": len(traces),
        "hit_bound": hit_bound,
        "examples": traces[:3],
    }

for name, summary in playout_summary.items():

def accepts_trace(net, im, fm, trace, max_states=100000):
    idx = build_net_index(net)
    start = mkey_from_marking(im)
    final = mkey_from_marking(fm)
    target = tuple(trace)

    stack = [(start, 0)]
    seen = set()

    while stack and len(seen) < max_states:
        mkey, pos = stack.pop()
        state = (mkey, pos)
        if state in seen:
            continue
        seen.add(state)

        if mkey == final:
            if pos == len(target):
                return True
            continue

        if pos >= len(target):
            continue

        for t in idx["transitions"]:
            tid = id(t)
            if not is_enabled(mkey, tid, idx):
                continue

            lab = visible_label(t)
            if lab is not None and lab != target[pos]:
                continue

            new_mkey = fire(mkey, tid, idx)
            new_pos = pos + 1 if lab is not None else pos
            stack.append((new_mkey, new_pos))

    return False

# 9. Recommendation and Data-Collection Plan

**Recommendation.** Use `model_balanced` for immediate operational use. It fits all observed variants, respects high- and medium-confidence rules, admits the most defensible unseen interleavings, and does not overextend SC to arbitrary positions. Use `model_permissive` for sensitivity analysis, especially to test how conclusions change if D5 is wrong, SC integration loss is substantial, or unobserved SC-before-checks cases are possible. Keep `model_conservative` as a replay regression baseline, not as the main process truth.

**Concrete data-collection plan.**

- Collect lifecycle timestamps, not only completions: start and complete for `Credit Check`, `Engineering Review`, `Supplier Confirmation`, and `Expedite Review`; ideally also for approval-related steps if timing exists.
- Collect case attributes: external/stocked indicator, component category, supplier ID, stock availability flag, required-supplier-confirmation flag, order priority, due date, expedite reason, configuration complexity, credit-result code, engineering-result code.
- Collect data-quality fields: source system for SC events, integration-status flag, export batch ID, event ingestion time, ingestion index, and a definitive marker for “SC not required” versus “SC required but event missing.”
- Analyze overlap: compare CC and ER start/complete intervals to distinguish strict sequence from true overlap. Completion-order alternation alone is insufficient.
- Analyze SC prerequisites: among cases with SC, test whether SC starts after CC completion, ER completion, both, or neither. This directly tests D5.
- Analyze SC absence: join exported logs with procurement/source-system records to estimate whether missing SC is due to stocked components, integration failure, or both.
- Analyze Expedite: collect reason and authorization data, and test whether Expedite cases differ systematically in priority, delay risk, or credit/engineering outcomes.

**Maximally informative future traces.**

- `RO, CC, SC, ER, EX, AP, RP, AR`: distinguishes SC-after-CC-only from SC-after-both.
- `RO, ER, SC, CC, EX, AP, RP, AR`: tests the balanced ER-only SC branch.
- `RO, SC, CC, ER, AP, RP, AR`: tests whether D5 should be relaxed toward the permissive model.
- `RO, CC, ER, EX, AP, RP, AR`: tests whether Expedite can occur when SC is absent or missing.
- `RO, CC, ER, SC, EX, AP, RP, AR` versus `RO, CC, ER, EX, SC, AP, RP, AR`: helps separate SC/EX ordering.
- Paired start/complete timestamps for `RO, CC, ER, ...`: distinguishes sequence from concurrency even when the visible completion order is the same.

# 10. Uncertainty Statement

- **RO start and AR end:** high confidence, approximately 0.95. Supported by D1 and all 30 traces.
- **APRPAR:** high confidence, approximately 0.95. Supported by D2 and all 30 traces.
- **CC and ER before AP:** medium-high confidence, approximately 0.8. Supported by D3 and all traces, but not by start/end lifecycle data.
- **No fixed CC/ER completion order:** medium confidence, approximately 0.65. Supported by V2/V4 and DFG reverse edges; weakened by S1 and D7.
- **True CC/ER concurrency:** low-to-medium confidence, approximately 0.4–0.55. S2 supports it, but completion timestamps cannot prove it.
- **SC optionality:** medium confidence, approximately 0.6. Supported by S3/S4 conflict and observed absent SC; weakened by S5 missing-event possibility.
- **SC after either CC or ER:** low-to-medium confidence, approximately 0.4–0.55. Supported by D5 and V5, but not enough to make it a hard rule.
- **EX optional and after both checks before AP:** medium confidence, approximately 0.7. Supported by D6/S6 and both Expedite variants, but only two cases exist.
- **EX at most once:** medium-to-high confidence, approximately 0.75, mostly from D6/S6 rather than frequency evidence.
- **SC missing-event rate of 5–10%:** low-to-medium confidence, approximately 0.3–0.5, because it comes from a stakeholder/data-quality statement but cannot be verified from the exported log.

A plausible alternative interpretation that would materially change the recommendation is that Finance’s S1 is correct: `Credit Check` must finish before `Engineering Review` starts, and the reverse logged orders are caused by logging or timestamp problems. In that case, the balanced and permissive no-order treatment of CC/ER would be wrong, and a stricter CC-before-ER model would be preferable. Another material alternative is that nearly all absent SC events are integration losses rather than true skips; then SC should be modeled as mandatory-with-missing-data rather than optional, which would also change the recommendation.
