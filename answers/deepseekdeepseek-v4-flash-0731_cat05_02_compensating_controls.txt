## 1. Control-Objective Decomposition

| Objective / threat scenario | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|
| A single human both initiates and authorizes a payment. | Detects data anomalies, but does not substitute for human independence. | Can prevent if independent approval is before release or before settlement. | Detects same-user or abnormal approval afterwards. | Permits same-user only under strict preconditions; if conditions fail, it does not authorize the violation. |
| Payee or bank account is wrong, changed, or not owned by expected vendor. | Checks bank-account ownership and changes in prior 7 days; strong only if fully operational and not overridden. | Can detect if manager checks bank details and invoices. | Detects after the fact; high value only if still recallable. | Requires no bank-account change in prior 7 days and AV-2 fully operational. |
| Duplicate, fake, or non-received goods/services are paid. | Blocks duplicate invoice and basic PO mismatch, but does not prove receipt or commercial reasonableness. | Can prevent only if manager inspects supporting evidence. | Can uncover fabricated receipts, but usually after money is gone. | Does not itself establish receipt; ED-1 still relies on AV-2 and manager/audit. |
| Override or approval is abused by a conflicted or non-independent manager. | Warning/override is a risk; AV-2 cannot judge manager conflicts. | Strongest only if manager is independent and actually reviews evidence. | Can reveal late approvals, overrides, and manager relationships. | Requires independent MG-4 before settlement; does not remove conflict risk by itself. |
| Preparer and releaser collude, share credentials, or use shared workstations. | Cannot detect collusion. | Reduces risk if manager is independent and outside the pair. | Can detect repeated pairs and audit findings, but late. | Not designed to prevent collusion beyond requiring manager/audit. |
| Emergency exception is used as convenience rather than necessity. | Not relevant to emergency justification. | Can question emergency basis before settlement. | Can confirm/refute token timing and urgency later. | Strict preconditions: token before Prepare, < EUR 100k, vendor tenure, no bank change, AV-2 pass, MG-4, RA-7. |

## 2. Equivalence and Sufficiency Test

A package is **fully equivalent** when it satisfies the control objective, not merely the form:

- **Timing**: key controls occur before irrevocable bank settlement; ideally before release.
- **Independence**: approving/reviewing manager is level L3+, unrelated to preparer/releaser, and not in a conflict relationship.
- **Coverage**: AV-2 checks run fully without override; manual checks are signed and reliable.
- **Overrideability**: warnings/overrides cannot be self-issued by the same person needing approval.
- **Recoverability**: audit and manager action occur within the recall window when bank settlement is not yet final.
- **Evidence quality**: timestamps, token activation, signed checklists, workstation/session logs, organizational design documents exist.
- **Collusion resistance**: no repeated pair, shared workstation, or unexplained relationship undermines the two-person assumption.

Classifications:

- **Fully equivalent**: all critical requirements met, including ED-1 conditions when same user is used, or distinct users with no unresolved independence gap.
- **Partially equivalent**: risk is materially reduced, but a key control is late, incomplete, conflicted, overridden, or evidence is missing.
- **Merely mitigating**: controls are mostly after-the-fact, cannot prevent an irreversible transfer, or rely on the same compromised/conflicted decision path.
- **Ineffective**: material failures combine with high exposure and no reliable detection/correction.

“Same expected loss” is not the only standard because the objective is also about **resilience, auditability, and deterrence**. A single good outcome does not make a control process sufficient; the process must work before the risk is realized, not only after a favorable result.

## 4. Preventive–Detective–Corrective Comparison

| Control | Primary mode | Prevents? | Detects? | Corrects? | Key limitation |
|---|---|---|---|---|---|
| AV-2 full pass | Preventive gate before Release | Can block duplicate, sanctions, bank-account change, limit, basic PO mismatch | Emits warnings | Not by itself | Does not confirm receipt, commercial reasonableness, or collusion |
| AV-2 warning + override | Prevention weakened | Only if override is blocked; if overridden, not preventive | Logs override | No | Override credential must not belong to preparer/releaser; otherwise ineffective |
| MG-4 before Release | Preventive | Yes, stops release/authorization | Not needed | Not needed | Requires independence and actual review |
| MG-4 after Release but before Bank_Settlement | Hybrid | Prevents final irrevocable settlement | Detects issue after release | Yes, can stop/recall before settlement | Weaker than pre-release approval because payment instruction has already left the system |
| MG-4 after Bank_Settlement | Detective/ratification | No | Yes | Usually weak | Bank settlement is treated as irrevocable for internal-control purposes |
| RA-7 within 24h / recall window | Detective, partly corrective | No | Yes | Yes, if bank recall still available | Requires immediate action; after 24h recovery is uncertain |
| RA-7 after recall window | Detective only | No | Yes | Rare/exceptional | Cannot reliably recover funds |
| ED-1 | Conditional permission | Allows same-user only under strict conditions | Backed by AV-2, MG-4, RA-7 | Depends on timing of manager/audit | If any condition fails, same-user is not authorized |

A manager action **after Release_Payment but before Bank_Settlement** should be treated as **hybrid**: it is detective with respect to the release, but preventive with respect to the final irrevocable settlement. It is weaker than approval before release because the bank instruction has already been sent; however, it still provides a practical opportunity to stop the payment before funds are transferred.

## 6. Evidence and Monitoring Recommendations

- **Same-user rate**: Monitor all completed payments where Prepare and Release resources match. Alert when a same-user case lacks a valid ED-1 token before Prepare. An alert is not proof of fraud; it is a review trigger.
- **Override rate**: Track AV-2 warnings, overrides, and the owner of the override credential. High override rates by one preparer/manager pair require review.
- **Late manager approval**: Compare manager event time with Release_Payment and Bank_Settlement. Approval after Release but before settlement is a weaker, hybrid control; approval after settlement is detective only.
- **Audit-before-recall-window**: For ED-1 and all high-risk cases, audit must complete within 24 hours of release. Audit after 24 hours should be flagged as reduced corrective capacity.
- **Repeated resource pairs**: Count case co-occurrence of preparer/releaser pairs. Repeated pairs are not proof of collusion, but they require evidence that they form a legitimate, documented payment cell.
- **Shared workstations**: Collect workstation/session logs and active-login information. Flag when two users on a payment have overlapping sessions or use the same terminal; this weakens non-repudiation.
- **Bank-change proximity**: Flag every payment where vendor bank account changed within 7 days. Require enhanced manager review and bank-ownership validation. Flag is not a fraud conclusion.
- **Control outages**: Track Validation_Service_Unavailable, manual checklist completion, and all releases made during AV-2 outage. Block or require independent pre-settlement manager approval for any release during an outage, especially above ED-1 thresholds.
