## 1. Interaction-graph description

Use a typed graph with object nodes and event nodes. Keep stable object-to-object relations separate from time-stamped event participation. A batch cure is one event with several participants. Its incidence edges preserve which jobs shared the *same* cure, machine and rack. The compact edge list below uses braces for multiple targets and “respectively” for one-to-one matches.

| Source | Relation or event role | Target |
|---|---|---|
| J1 … J6 | requires | C1 … C6, respectively |
| L7, L8 | contains | {C2, C5}, {C1, C3}, respectively |
| B1, B2 | batches | {J1, J2, J3}, {J4, J5}, respectively |
| S1, S2, S3 | consolidates | {J1, J4}, {J2, J3}, {J5, J6}, respectively |
| Batch Cure, 12:05 | batch / machine / tool / jobs / components | B1 / OVEN-1 / RACK-7 / {J1, J2, J3} / {C1, C2, C3} |
| Machine Process, 11:45 | job / component / machine / tool | J4 / C4 / CNC-2 / FIX-A |
| Quarantine Lot, 10:20 and Release Lot, 13:50 | lot / affected components / associated jobs in integrated evidence | L7 / {C2, C5} / {J2, J5} |

The membership edges and listed event participants are supplied observations at the stated level of integration. The source Job extraction omits both lot events because it uses direct Job links. The path J2–C2–L7–C5–J5 reconstructs common exposure through component membership. J2’s recorded override changes how that exposure applies. L8 membership alone establishes no hold.

Three higher-order motifs explain the coupling. First, multiple Job–Component pairs join at a Batch requiring a Machine and Tool together. Second, different jobs successively claim a Tool needed at a Machine. J3’s acquire and release are observed, continuous possession between them is inferred, and an exclusive claim that blocked J4 is a hypothesis. Third, Batch–Job–Shipment memberships cross-cut each other. S1 reunites a B1 job with a B2 job, so J1 can finish curing and still depend on J4. S3 connects B2 to J6, for which no batch is listed. A projected job–job edge means shared participation or membership. Inferring who delayed whom also requires timing, eligibility and policy.

## 4. What flattening misses

| Viewpoint | Visible | Hidden or duplicated, and resulting misleading conclusion |
|---|---|---|
| Job | Routes, rework, individual intervals and, where linked, dispatch | A job projection can repeat B1’s one cure across three traces and S1’s departure across two. The supplied 1.1 h median Pack → Dispatch conceals J1’s 355 min. Similar total durations do not imply independent progress. |
| Machine | Uses, releases, cycles and utilization | A CNC trace omits a fixture held elsewhere. A gap between machine events can include processing, off-shift time or genuine idle time. Reading a long gap as spare *usable* capacity, or as a queue, gives the wrong diagnosis. |
| Batch | Load/cure/unload per run and a common launch | Early-ready members can wait before the first batch activity. A normal Load → Cure interval can coexist with J1 waiting most of the morning. Batch membership alone misses S1’s cross-batch dependency. |
| Tool | Acquisitions, releases, cleaning and recalibration where recorded | A tool trace can omit denied requests and the identities of jobs ready elsewhere. A long Acquire → Release interval for FIX-A measures possession under a pairing assumption. It does not measure J4’s wait throughout J3’s hold. |
| ComponentLot | L7 quarantine and release, with component membership available by join | A lot trace misses job-specific demand and the scope of exceptions. Treating Quarantine → Release as every member’s material delay would incorrectly stall J2 until 13:50. |
| Shipment | One create/load/dispatch path per shipment | Packed jobs can wait before shipment creation or loading. A 0.3 h median Load → Dispatch says little about the oldest packed member. Projecting the departure onto each job loses the identity of the partner that packed last. |

Machines can sit idle while jobs wait for a *combination* of eligible material, batch partners and a qualified tool. Waiting can also occur after production. Interaction counts do not weight duration or queue size. Two Batch–Machine interactions cover both cures, while 15 Job–Tool interactions include uses or releases and omit some waiting. The two directional lot/job counts can describe the same relations.

## 6. Intervention portfolio and spillovers

Assign pilots by interacting batch, tool shift, lot or shipment lane. Jobs sharing those objects can affect each other’s outcomes. Match comparison periods on product mix, eligible demand and operating calendar, and follow all exposed jobs through dispatch.

## 7. PM4Py analysis outline

```python
import pandas as pd
import pm4py

interactions = pm4py.ocel_objects_interactions_summary(ocel)
object_graph = pm4py.discover_objects_graph(ocel, "object_interaction")
type_graph = pm4py.discover_otg(ocel)
event_type_object_type = pm4py.discover_etot(ocel)
ocdfg = pm4py.discover_ocdfg(ocel)

# On the same typed activity edge, compare distinct event-ID pairs with
# distinct objects traversing it. A shared pair may serve several objects,
# and one object may traverse an activity edge repeatedly.
edges = ocdfg["edges"]
rows = []
for obj_type, by_edge in edges["event_couples"].items():
    for (source, target), couples in by_edge.items():
        objects = edges["unique_objects"][obj_type][(source, target)]
        rows.append((obj_type, source, target, len(couples), len(objects)))
edge_counts = pd.DataFrame(rows, columns=[
    "object_type", "source", "target", "event_pairs", "distinct_objects"
])
print(edge_counts[edge_counts["event_pairs"] != edge_counts["distinct_objects"]])

# Retain event identity to distinguish physical cures from job participations.
relations = ocel.relations
event_id, object_id = ocel.event_id_column, ocel.object_id_column
job_cures = relations.loc[
    relations[ocel.event_activity].eq("Batch Cure")
    & relations[ocel.object_type_column].eq("Job"), [event_id, object_id]
].drop_duplicates()
print(job_cures.groupby(event_id)[object_id].nunique().rename("jobs_in_cure"))

performance = {}
for obj_type in ("Job", "Machine", "Batch", "Tool", "ComponentLot", "Shipment"):
    flat = pm4py.ocel_flattening(ocel, obj_type)
    if len(flat):
        performance[obj_type] = pm4py.discover_performance_dfg(flat)
job_features = pm4py.extract_ocel_features(ocel, "Job")

# Match reported member readiness to actual starts on the batch key.
# Times are offsets from midnight on the common observation day.
members = pd.DataFrame([
    ("B1", "J1", "08:10:00"), ("B1", "J2", "08:25:00"),
    ("B1", "J3", "11:55:00"), ("B2", "J4", "13:10:00"),
    ("B2", "J5", "14:40:00"),
], columns=["batch", "job", "ready"])
starts = {"B1": "12:05:00", "B2": "14:50:00"}
members["ready"] = pd.to_timedelta(members["ready"])
members["start"] = pd.to_timedelta(members["batch"].map(starts))
last_ready = members.groupby("batch")["ready"].transform("max")
members["lead_to_last_ready"] = last_ready - members["ready"]
members["post_readiness_lag"] = members["start"] - last_ready
print(members)
```

Run the projections on both source-linked and enriched OCELs using the same physical event IDs. A change in Job edges with unchanged lot history measures extraction sensitivity. For tool attribution, intersect a ready job’s pending request with tool unavailability and machine feasibility. Treat projections and lifecycle features as descriptions until those conditions are checked.

## 8. Falsification and additional data

The following observations would weaken the first-ranked explanation that waiting for batch partners materially controls launch times.

1. Readiness audits place J1 or J2 near noon, eliminating most of the claimed early-ready interval.
2. Dispatch records show the 12:05 and 14:50 slots were fixed before membership was chosen and earlier slots could never be used.
3. Oven state histories show an incompatible cycle occupied OVEN-1 throughout B1’s apparent early opportunity.
4. Rack certification, staffing or recipe records put independent hard gates at the observed launches even when every member was ready early.
5. Event-level membership histories show the alleged last member routinely joins after launch or was assigned retrospectively.
6. Across comparable runs with verified free equipment, moving the final member’s readiness earlier leaves launch time unchanged, including when all members are ready well ahead of schedule.
7. Matched single-job or permitted partial loads incur similarly long waits despite removing the partner requirement.

Discriminating data would include (1) actual readiness transitions, prerequisites and timestamp provenance by job and operation, (2) batch membership revisions, minimum-load rules and planned versus actual launch, (3) tool requests, grants, denied requests, release, serial number and qualified alternatives, (4) machine occupation intervals, setup, maintenance and crew availability, (5) time-effective lot dispositions, component demand times and signed override scope, (6) calibration and rack-cleaning start, completion and return-to-service times, (7) member-level pack/load times, carrier cutoffs, available departures and split permissions, and (8) stable source event IDs, clock offsets and direct versus derived relation qualifiers. Together these distinguish an observed joint wait from an earlier start that operations could actually have executed.
