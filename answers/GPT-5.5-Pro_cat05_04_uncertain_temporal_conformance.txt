## 1. Normalization Assumptions

I use the supplied source data as authoritative and do not replace uncertain timestamps with exact midpoints except in the explicitly marked PM4Py comparison in section 5. 

For each source, I first apply display-resolution uncertainty, then clock-offset correction. With `clock_offset = recorded_clock - true_clock`, if the offset is `[a,b]`, the true time is:

`[displayed_clock_min - b, displayed_clock_max - a]`.

Resolution semantics used:

| Source type                                   | Display interval before clock correction |
| --------------------------------------------- | ---------------------------------------- |
| HUB exact second                              | displayed second ±0.5 s                  |
| OPS-BER / VENDOR-NY / LEGACY-BER floor minute | `[HH:MM:00, HH:MM:59.999]`               |
| SENSOR nearest 10 s                           | displayed time ±5 s                      |
| MOBILE-LON nearest minute                     | `[HH:MM-30s, HH:MM+29.999s]`             |

Time-zone conversion is done using the local zone stated for the source: CEST/BST/EDT where applicable. For T-405, the ambiguous Berlin local hour on 2025-10-26 is represented as DST fold alternatives first; then ingestion order is applied. That eliminates all but: `Alert_Received` in the first fold, `Investigation_Start` and `Containment_Complete` in the second fold.

For durations, I enforce the process-order interpretation for activity pairs such as `Alert_Received → Investigation_Start`. If two event intervals overlap, the minimum feasible duration is `0`, not a negative number. This matters for T-407 and T-409. The maximum duration is always latest feasible second event minus earliest feasible first event.

For T-404, `Investigation_Start` is inferred from `Investigation_Complete - investigation duration`, retaining the full signed duration range `[18,25]` minutes and HUB uncertainty.

For T-406, my main interpretation treats the mobile entry delay as uncertainty about the actual occurrence time: the user may have recorded the start up to 5 minutes late, so the true `Investigation_Start` may be up to 5 minutes earlier than the corrected mobile record. If the delay is treated as record-only, not occurrence-time uncertainty, T-406 becomes materially less risky for `Investigation_Start → Containment_Complete`.

For T-407, `Alert_Sent` is not identical to `Alert_Received`. I classify receipt-based rules conditionally: using delivery latency `[0,20]` minutes and the plausible but unlogged causal assumption that receipt was not after investigation start. Without that semantic assumption, T-407 `Alert_Received` tests are indeterminate for enforcement.

Section 3 uses zero SLA tolerance and temporal-profile `ζ=2` as the base setting. Section 4 varies SLA tolerance and `ζ`.

Then T-406 S2 becomes `1948.5–2611.5 s`, a certain pass even at zero SLA tolerance, and TP Investigation→Containment becomes a certain pass even at ζ=1.

import pandas as pd
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from itertools import product
from zoneinfo import ZoneInfo

UTC = timezone.utc

@dataclass(frozen=True)
class Interval:
    start: datetime
    end: datetime
    note: str = ""

    def __post_init__(self):
        if self.start > self.end:
            raise ValueError(f"Invalid interval: {self.start} > {self.end}")

    @property
    def midpoint(self) -> datetime:
        return self.start + (self.end - self.start) / 2


def parse_naive(value: str) -> datetime:
    return datetime.strptime(
        value,
        "%Y-%m-%d %H:%M:%S" if len(value) > 16 else "%Y-%m-%d %H:%M",
    )


def true_from_clock_interval(clock_start_utc, clock_end_utc,
                             offset_low_s, offset_high_s, note="") -> Interval:
    # clock_offset = recorded_clock - true_clock, so true = recorded - offset
    return Interval(
        clock_start_utc - timedelta(seconds=offset_high_s),
        clock_end_utc - timedelta(seconds=offset_low_s),
        note,
    )

        t - timedelta(seconds=0.5),
        t + timedelta(seconds=0.5),
        -1,
        1,
        "HUB second +/-0.5s; offset [-1,+1]s",
    )]

                       offset_high_s: float, fold: int = 0, note: str = "") -> Interval:

    end_naive = start_naive + timedelta(seconds=59, milliseconds=999)

    # Build aware datetimes from the naive local endpoints so the DST fold is preserved.
    clock_start = start_naive.replace(
        tzinfo=ZoneInfo(tz_name), fold=fold
    ).astimezone(UTC)
    clock_end = end_naive.replace(
        tzinfo=ZoneInfo(tz_name), fold=fold
    ).astimezone(UTC)

    return true_from_clock_interval(
        clock_start,
        clock_end,
        offset_low_s,
        offset_high_s,
        note,
    )

    clock_end = (base + timedelta(seconds=29, milliseconds=999)).astimezone(UTC)

def ordered_feasible(*ivs: Interval) -> bool:
    # Existence of a nondecreasing selection t1 <= t2 <= ... across intervals.
    current = ivs[0].start
    if current > ivs[0].end:
        return False

    for iv in ivs[1:]:
        current = max(current, iv.start)
        if current > iv.end:
            return False

    return True


def merge_numeric(ints: list[tuple[float, float]]) -> list[tuple[float, float]]:
    if not ints:
        return []

    ints = sorted(ints)
    merged = [list(ints[0])]

    for lo, hi in ints[1:]:
        if lo <= merged[-1][1] + 1e-9:
            merged[-1][1] = max(merged[-1][1], hi)
        else:
            merged.append([lo, hi])

    return [tuple(x) for x in merged]


def duration_intervals(start_ivs: list[Interval],
                       end_ivs: list[Interval],
                       enforce_order=True) -> list[tuple[float, float]]:
    out = []

    for x in start_ivs:
        for y in end_ivs:
            if not enforce_order:
                out.append((
                    (y.start - x.end).total_seconds(),
                    (y.end - x.start).total_seconds(),
                ))
                continue

            if x.start > y.end:
                continue

            overlaps = y.start <= x.end and x.start <= y.end
            lo = 0.0 if overlaps else (y.start - x.end).total_seconds()
            hi = (y.end - x.start).total_seconds()
            out.append((lo, hi))

    return merge_numeric(out)


def classify_max(ints: list[tuple[float, float]], limit_s: float) -> str:
    if not ints:

    if all(hi <= limit_s for lo, hi in ints):
        return "CERTAIN_PASS"
    if all(lo > limit_s for lo, hi in ints):
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

        return "CERTAIN_PASS"
    if all(hi < low_s or lo > high_s for lo, hi in ints):
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

## 7. Governance Recommendation

Store event occurrence timestamps in UTC while retaining the raw displayed timestamp, source time zone, source system, display resolution, rounding semantics, and original offset telemetry. UTC storage alone is not enough; the raw record is needed for audit reconstruction.

Record clock-offset telemetry at event level or at least at a fine-grained interval around each event. Daily NTP diagnostics are weaker than per-hour or per-event diagnostics, and T-409 shows how missing offset telemetry can turn a legal SLA check into a possible violation.

Persist explicit timestamp-resolution metadata: exact second, floor-to-minute, nearest-minute, nearest-10-seconds, manual entry, and any measurement uncertainty. Rounding should never be silently interpreted as an exact timestamp.

Require source systems to distinguish lifecycle semantics: start event, completion event, user-entered observation, system-ingestion time, sent time, received time, and acknowledgment time. T-407 demonstrates why `Alert_Sent` must not be reused as `Alert_Received` without a documented proxy rule.

For DST-sensitive local systems, store the DST fold or store UTC at source. If local timestamps are unavoidable, preserve the local offset such as `+02:00` or `+01:00` in the event record. T-405 is recoverable only because ingestion order constrains the fold alternatives.

Add causal identifiers for cross-system messages: alert ID, delivery acknowledgment ID, investigation work-record ID, containment ID, and close ID. Message correlation should link sent, delivered, acknowledged, and acted-upon events.

Create a mobile-entry policy: manual timestamps should distinguish actual occurrence time, user entry time, device clock time, server receipt time, and allowed backdating. The policy should specify whether entry delay shifts legal occurrence time or only record provenance.

For enforcement, define an interval-overlap policy before cases are adjudicated. A conservative legal policy could require `CERTAIN_VIOLATION` before sanction. An operational early-warning policy can act on `POSSIBLE_VIOLATION`, but should label it as uncertainty-driven and should not treat it as proven noncompliance.

For temporal-profile conformance, keep it separate from SLA enforcement. A case can legally pass but statistically deviate, or legally fail while remaining near a broad profile band. Temporal-profile deviations should trigger process review, not automatic SLA penalties, unless governance explicitly says otherwise.
