## 1. Normalization Assumptions

**A1 – Interval construction (resolution first, then clock correction).** A displayed value R is first widened to the set of source-clock readings that could have produced it, `[R + r_lo, R + r_hi]`. Then `true = reading − offset` with `offset ∈ [a, b]`, so

`true ∈ [R + r_lo − b, R + r_hi − a]`.

A positive offset means the source clock was fast, so the true time is earlier than recorded. Net windows around the displayed value (already converted to UTC):

| System | Reading window from display semantics | Offset [a, b] | True-time window relative to displayed value |
|---|---|---|---|
| HUB | ±0.5 s (measurement uncertainty, treated as the resolution step) | [−1, +1] s | [R − 1.5 s, R + 1.5 s] |
| OPS-BER | floor to minute: [R, R + 60 s) | [−90, +120] s | [R − 120 s, R + 150 s) |
| SENSOR | nearest 10 s: [R − 5 s, R + 5 s) | [−5, +5] s | [R − 10 s, R + 10 s) |
| VENDOR-NY | floor to minute | [−180, +180] s | [R − 180 s, R + 240 s) |
| LEGACY-BER | floor to minute | [−60, +60] s | [R − 60 s, R + 120 s) |
| MOBILE-LON | nearest minute: [R − 30 s, R + 30 s) | [−300, +300] s | [R − 330 s, R + 330 s), before entry delay |

**A2 – Bounds are sets, not distributions.** No probability is attached to any position inside an interval. Flooring makes upper ends half-open ("59.999"). For classification I use the closed supremum, which is conservative and differs by at most 1 ms; no finding depends on it.

**A3 – Independence of errors (primary) versus common-mode offset (sensitivity).** Duration bounds are `[B_lo − A_hi, B_hi − A_lo]`, which assumes the two events' errors are independent. That is the widest defensible reading. If two events from the same clock shared one offset (HUB–HUB pairs, the three LEGACY-BER events of T-405), the offset would cancel and the intervals would shrink. This does not change any classification (checked for T-405 S1, which becomes (840, 960) s, and for T-408 IS→CC at zeta 2, which becomes [3299, 3301] s). It is not assumed, because drift between events is not excluded by the metadata.

**A4 – Time zones.** CEST = UTC+02:00, EDT = UTC−04:00, BST = UTC+01:00, CET = UTC+01:00. The wall time is converted to UTC with IANA rules and then widened; no interval other than T-405 is near a transition.

**A5 – DST fold (T-405).** On 2025-10-26 Europe/Berlin switches at 01:00:00Z (03:00 CEST becomes 02:00 CET). Each 02:xx value has two candidates: fold A = CEST (first pass, 00:xxZ) and fold B = CET (second pass, 01:xxZ). Both are kept as disjoint alternatives. The ingestion sequence (Alert before Start before Containment) is then treated as true-time order, which prunes combinations but does not remove the ±clock and flooring uncertainty of the survivors. This is an assumption: ingestion order is not automatically occurrence order. Here it agrees with the process logic, which adds support.

**A6 – Inferred start (T-404).** `Investigation_Start = Investigation_Complete − d`, `d ∈ [18, 25] min` inclusive, with d read as elapsed wall-clock time between start and completion. The HUB uncertainty of the completion event and the full duration range are both retained. If d were net working time excluding pauses, the start could be earlier still; that would only add passing S1 outcomes and more S2 exposure.

**A7 – Missing receipt (T-407).** `Alert_Sent` is not `Alert_Received`. I build a surrogate `Alert_Received = Alert_Sent + latency`, `latency ∈ [0, 20] min`, which also assumes the alert was delivered at all. The plausible but unlogged causal constraint "receipt not after investigation start" is applied in the primary analysis and dropped in a sensitivity check. Results that rest on this surrogate are marked inference-conditional.

**A8 – Mobile entry delay (T-406).** Two steps are kept separate.
- Step 1, record time: the displayed 13:14 BST with rounding and clock bound gives the true instant the timestamp represents, [12:08:30Z, 12:19:30Z).
- Step 2, occurrence time. Primary assumption: the timestamp was captured when the user made the entry, up to 5 minutes after the investigation actually started. The delay therefore shifts my estimate of occurrence earlier by [0, 300] s and never later, giving [12:03:30Z, 12:19:30Z).
- Alternative: the delay only describes when the record was created and the user typed the correct start time, so the occurrence interval equals the record interval. This choice is material for S2 and is reported both ways.

**A9 – Weak offset estimate (T-409).** The ±12 min "engineering estimate" is not a verified bound. I compute the pair under two candidate bounds: weak [−720, +720] s and the usual NTP bound [−90, +120] s (not validated for that hour). A pair touching this timestamp is INDETERMINATE when the two candidates disagree. When they agree, I report the common class and state which offset would break it. The process order "start not before alert receipt" is used only to clip negative durations.

**A10 – Rule semantics.** "No later than" is inclusive: `duration ≤ limit` passes. Temporal-profile bands are inclusive, `[avg − zeta·std, avg + zeta·std]`, matching PM4Py, which flags only strict exceedance. Baseline for Section 3 is SLA tolerance 0 and zeta = 2; other settings are in Section 4.

**A11 – Coupling.** S1 and S2 share Investigation_Start: a later start hurts S1 and helps S2. Each row is classified on its own, and joint impossibility is noted where it matters (T-404).

**A12 – Scales.** Severity for SLA rows is the worst feasible overshoot: None (no feasible overshoot), Low (≤ 2 min), Medium (2–5 min), High (> 5 min or a certain breach), Critical (certain breach over 1 h). Profile rows are statistical only: None, Low (max |z| ≤ 3), Medium (max |z| > 3 or certain deviation). Confidence is my confidence that the label is correct given evidence quality.

    "T-405": [(AR, IS), (IS, CC)],
    "T-407": [(AR, IS)],
    "T-409": [(AR, IS)],

# ---------------------------------------------------------------- 2. normalization
def sec(x):
    return timedelta(seconds=float(x))


def utc_candidates(recorded, tzname):
    """Wall time -> UTC instants. Two instants are returned inside a DST fold."""
    naive = datetime.fromisoformat(recorded)
    tz = ZoneInfo(tzname)
    return sorted({naive.replace(tzinfo=tz, fold=f).astimezone(UTC) for f in (0, 1)})


def event_intervals(row, cfg):
    """List of alternative true-time UTC intervals (lo, hi) for one logged event."""
    src, extra = SOURCES[row.system], row.extra
    r_lo, r_hi = src["res"]
    o_lo, o_hi = src["off"]
    if "offset_scenarios" in extra:
        o_lo, o_hi = extra["offset_scenarios"][cfg["weak_offset"]]
    out = []
    for inst in utc_candidates(row.recorded, src["tz"]):
        lo = inst + sec(r_lo) - sec(o_hi)      # resolution first, then true = clock - offset
        hi = inst + sec(r_hi) - sec(o_lo)
        if "entry_delay" in extra and cfg["entry_delay_shifts_occurrence"]:
            lo -= sec(extra["entry_delay"][1])  # occurrence may precede the entry
        out.append((pd.Timestamp(lo), pd.Timestamp(hi)))
    return out


def case_scenarios(cfg):
    """case -> list of scenarios; a scenario maps activity -> (lo, hi) in UTC."""
    result = {}
    for case, grp in events.groupby("case_id", sort=True):
        alts = {r.activity: event_intervals(r, cfg) for r in grp.itertuples()}
        if case in DERIVED:
            target, anchor, (d_lo, d_hi) = DERIVED[case]
            alts[target] = [(lo + sec(d_lo), hi + sec(d_hi)) for lo, hi in alts[anchor]]
        acts, scenarios = list(alts), []
        for combo in product(*(alts[a] for a in acts)):
            sc, ok = dict(zip(acts, combo)), True
            for _ in range(3):                              # propagate order constraints
                for a, b in ORDER.get(case, []) if cfg["use_order"] else []:
                    (alo, ahi), (blo, bhi) = sc[a], sc[b]
                    sc[a], sc[b] = (alo, min(ahi, bhi)), (max(blo, alo), bhi)
                    ok &= sc[a][0] <= sc[a][1] and sc[b][0] <= sc[b][1]
            if ok:
                scenarios.append(sc)
        result[case] = scenarios
    return result


# ---------------------------------------------------------------- 3. durations + classes
def merge(ivs):
    out = []
    for lo, hi in sorted(ivs):
        if out and lo <= out[-1][1]:
            out[-1] = (out[-1][0], max(out[-1][1], hi))
        else:
            out.append((lo, hi))
    return out


def durations(scenarios, case, a, b, cfg):
    """Union of feasible duration intervals (s) for b - a; None if not testable."""
    ivs = []
    for sc in scenarios:
        if a not in sc or b not in sc:
            return None
        lo = (sc[b][0] - sc[a][1]).total_seconds()
        hi = (sc[b][1] - sc[a][0]).total_seconds()
        if cfg["use_order"] and (a, b) in ORDER.get(case, []):
            lo = max(lo, 0.0)
        ivs.append((lo, hi))
    return merge(ivs) if ivs else None


def classify(ivs, acc_lo, acc_hi):
    if not ivs:
        return "INDETERMINATE"
    if all(acc_lo <= lo and hi <= acc_hi for lo, hi in ivs):
        return "CERTAIN_PASS"
    if all(hi < acc_lo or lo > acc_hi for lo, hi in ivs):
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"


def checks():
    for name, (a, b, limit) in SLA.items():
        for tol in TOLERANCES_S:
            yield f"{name}+{tol // 60}min", a, b, float("-inf"), limit + tol
    for (a, b), (avg, std) in TEMPORAL_PROFILE.items():
        for z in ZETAS:
            yield f"TP {a}->{b} z={z}", a, b, avg - z * std, avg + z * std


def analyse(cfg):
    scen, rows = case_scenarios(cfg), []
    alt_cfg = dict(cfg, weak_offset="nominal" if cfg["weak_offset"] == "weak" else "weak")
    alt_scen = case_scenarios(alt_cfg)
    for case in scen:
        for label, a, b, lo, hi in checks():
            d = durations(scen[case], case, a, b, cfg)
            cls = classify(d, lo, hi)
            if d and {(case, a), (case, b)} & WEAK:
                other = classify(durations(alt_scen[case], case, a, b, alt_cfg), lo, hi)
                if other != cls:                # verdict depends on an unverified bound
                    cls = f"INDETERMINATE ({cfg['weak_offset']}:{cls} / {alt_cfg['weak_offset']}:{other})"
            rows.append(dict(case_id=case, check=label, durations_s=d, accept=(lo, hi), interval_class=cls))
    return scen, pd.DataFrame(rows)

def pm4py_midpoint_deviations(log, zeta):
    """Version-sensitive part, isolated. Assumption (PM4Py 2.7.x): the result is a list
    with one entry per case, in the order of first appearance of the case id in the
    dataframe; each entry is a list of tuples (act_a, act_b, duration_s, n_std).

    out = pm4py.conformance_temporal_profile(log, TEMPORAL_PROFILE, zeta=zeta)

    return {(cid, d[0], d[1]): (float(d[2]), float(d[3])) for cid, devs in zip(case_ids, out) for d in devs}

Notes on the code:
- **Execution.** I ran it with PM4Py 2.7.23.4, pandas 3.0.5 and Python 3.12. It reads no external file, and its interval output is the source of the numbers in Sections 2 to 4.
- **Interval logic is not PM4Py.** Normalization, fold alternatives, duration intervals and the four-way classification are plain pandas and standard-library code. PM4Py receives only the midpoint log and evaluates one point per event; it has no notion of timestamp uncertainty.
- **Version assumptions, isolated in `pm4py_midpoint_deviations`.** The function assumes the return value is a list with one entry per case, ordered as the case ids appear in the formatted dataframe, each entry holding `(activity_a, activity_b, duration_s, n_std)` tuples. It raises if the shape differs. Some versions also accept `return_diagnostics_dataframe=True`; I did not rely on its column names.
- **Case-id pitfall.** With default settings this PM4Py version parsed the case id "T-401" as a date inside `format_dataframe`. The explicit `timest_format` and the assertion guard against that.
- **Code rule for T-409.** The code labels a pair INDETERMINATE only when the weak and nominal bounds disagree. Where they agree it prints the common class; Section 3 marks those as conditional.

Midpoint results from that run (secondary comparison only):
- **Zeta 1 flags:** T-401 Alert→Start (855 s); T-402 Alert→Start (1095 s) and Alert→Containment (3720 s); T-403 Alert→Start (930 s) and Alert→Containment (3450 s); T-404 Alert→Start (810 s); T-405 Alert→Start (900 s); T-408 Start→Containment (3300 s), Alert→Containment (3900 s) and Containment→Close (138300 s).
- **Zeta 2 flags:** T-402 Alert→Start and T-408 Containment→Close. **Zeta 3 flags:** none.
- **Agreement.** Every certain interval verdict matches the midpoint verdict; that is expected, since a midpoint lies inside its interval.
- **False crispness.** 26 of 87 pair-and-zeta verdicts look definite at the midpoint while the interval class is POSSIBLE_VIOLATION or INDETERMINATE. Examples:
  - T-402 Alert→Start at zeta 2 is flagged, although a pass is still feasible.

  - T-408 Start→Containment at zeta 2 is exactly 3300 s at the midpoint and is not flagged; the interval result is possible.
  - T-405 Alert→Start is exactly 900 s at the midpoint, so a point-based S1 verdict would flip on one millisecond.

## 6. Evidential Sufficiency

Thresholds below are derived from the intervals; "o" is the clock offset (positive means the clock was fast).

| Finding | Evidence type needed | Minimum evidence that makes it certain |
|---|---|---|
| T-401 S1 (possible) | Stronger synchronization, then resolution | Seconds alone can never settle it under the current offset bound. An event-level offset for OPS-BER at 10:14 is required: o ≥ +1.5 s gives CERTAIN_PASS, o < −61.5 s gives CERTAIN_VIOLATION. In between, the unfloored seconds are also needed |
| T-402 S2 (possible) | Stronger synchronization (one-sided) | Proof that OPS-BER was not more than 58.5 s fast at 11:18 gives CERTAIN_PASS. A certain breach is unreachable within the stated bound |
| T-402 Alert→Start at zeta 2 and 3 (possible) | Stronger synchronization | For zeta 2, proof that o < +118.5 s gives a certain deviation. For zeta 3, an event-level offset plus unfloored seconds |
| T-403 S1 and profile pairs (possible) | Stronger synchronization or missing activity evidence | Vendor offset at the event: o ≤ −61.5 s gives CERTAIN_PASS, o > +1.5 s gives CERTAIN_VIOLATION, otherwise seconds are also needed. Cheaper: a HUB-side receipt record for the alert, which replaces the vendor clock with ±1.5 s |
| T-404 S1 (possible) | Missing activity evidence or duration evidence | A logged Investigation_Start in HUB. Otherwise a duration bound: d ≥ 20 min 3 s gives CERTAIN_PASS, d < 19 min 57 s gives CERTAIN_VIOLATION. Semantic confirmation that d is elapsed time is also needed |
| T-404 S2 (possible) | Duration evidence | d ≤ 24 min 57 s gives CERTAIN_PASS. A duration in [20:03, 24:57] clears S1 and S2 together |
| T-405 S1 (possible) | Semantic (fold), resolution, synchronization | A logged fold or UTC offset, to replace the ordering inference. Unfloored seconds for both events, since flooring alone spans the limit. Evidence that the LEGACY-BER offset did not drift between the two events |
| T-406 S1 (possible) | Stronger synchronization (one-sided) | Proof that the phone clock was not slow by more than 28.5 s gives CERTAIN_PASS under either delay semantics, for example a HUB receipt time for the mobile submission |
| T-406 S2 (possible) | Semantic evidence, or synchronization | Confirmation that the entered time is the occurrence time (record-only delay) gives CERTAIN_PASS. Alternatively, proof that the phone was not fast by more than 88.5 s. An offset within [−28.5, +88.5] s clears S1 and S2 together |
| T-407 S1 and Alert→Start (possible, inference-conditional) | Missing activity evidence, plus semantic evidence | A receipt acknowledgment timestamp. Failing that, latency evidence: ≥ 123 s gives CERTAIN_PASS, < 117 s gives CERTAIN_VIOLATION. Also a ruling on whether the SLA clock starts at send or at receipt, and proof of delivery |
| T-408 Start→Containment at zeta 2 (possible) | Semantic evidence and synchronization | A ruling on whether the band edge is inclusive, plus sub-second timestamps with a shared offset. Immaterial in practice because S2 is a certain breach |
| T-409 S1 (indeterminate) | Stronger synchronization | NTP diagnostics for the 18:00 hour. Any proof that the clock was not slow by more than 9 min 58.5 s gives CERTAIN_PASS. Confirmation of the nominal bound also settles the profile pairs |
| T-409 Alert→Start and Start→Containment profile (indeterminate or conditional) | Stronger synchronization | Same diagnostics; under the nominal bound the zeta 1 result is a certain "too fast" deviation for Alert→Start and a pass for Start→Containment |
| S3 and Containment→Close for T-402 to T-407 and T-409 (indeterminate) | Missing activity evidence | A Close_Incident event, or an authoritative extraction time with confirmation that the case is still open. The 36-hour deadlines are about 2026-06-02T22:02Z (T-402), 2026-06-02T20:58Z (T-403), 2026-06-02T22:55Z (T-404), 2025-10-27T13:41Z to 13:44Z (T-405), 2026-06-03T00:52Z (T-406), 2026-06-03T02:55Z (T-407) and 2026-06-03T04:35Z (T-409) |

Remaining possible profile findings (T-401, T-404, T-405, T-406 Alert→Start and the zeta 1 rows) are resolved by the same evidence as the corresponding S1 or S2 row.

## 7. Governance Recommendation

**Timestamps**
- Store every event as a UTC instant with the UTC offset applied, and keep the raw source string, source zone and source system alongside it. Never overwrite the raw value.
- Do not truncate at ingestion. Minute flooring alone makes T-401, T-402, T-405 and T-406 undecidable; require at least second resolution from operational systems.
- Store resolution metadata per source and per event: unit, and whether the value was floored, rounded or exact.
- Store both event time and ingestion time, and never substitute one for the other.

**Clocks**
- Record source offset telemetry per event or per short window (NTP or PTP offset and its error bound), with retention matched to the audit period.
- Treat a gap in diagnostics, as in T-409, as a data-quality incident. A fallback "engineering estimate" should be labelled as unverified and must not feed enforcement.
- Counter-stamp external and mobile events with a HUB receipt time. This gives a cheap one-sided bound that would have settled T-403 and T-406.

**Time zones and DST**
- Record the UTC offset or the fold flag for every local timestamp. Legacy systems that cannot do so should log in UTC.
- Until fixed, flag every event in a fold hour as ambiguous and carry both candidates forward, as done for T-405.

**Lifecycle semantics**
- Log start and complete as separate events with an explicit lifecycle attribute. Do not reconstruct starts from durations except as flagged, inferred evidence (T-404).
- Define the SLA anchor precisely. Alert_Sent and Alert_Received are different events; require a receipt acknowledgment (T-407).
- For user-entered times, capture two fields: when the activity occurred according to the user, and when the entry was made by the device (T-406).

**Provenance and causality**
- Carry causal identifiers: alert id, message id, correlation id and a per-source sequence number, so ordering does not depend on ingestion order.
- Mark each event as logged, inferred or user-asserted, and record who signed any work record used as evidence.
- Version the temporal profile and state the zeta in use; keep it separate from the SLA limits.

**Enforcement policy**
- Enforce only on CERTAIN_VIOLATION under documented bounds. Here that is T-402 S1, T-408 S2 and T-408 S3.
- Interval overlap alone (POSSIBLE_VIOLATION) is not sufficient for a penalty. It should trigger an evidence request with a deadline, using the items in Section 6, and a review.
- INDETERMINATE is a data-quality finding against the source owner, not a compliance verdict in either direction. It must not be reported as a pass.
- Fix the tolerance in advance. Section 4 shows that a 2-minute grace clears three possible findings and a 5-minute grace clears all but T-402 S1, so choosing the tolerance after seeing the data would decide the outcome.
- Keep midpoint-based PM4Py results for monitoring and trend dashboards only, labelled as lossy. Use temporal-profile deviations as triggers for investigation, never as SLA evidence.
- If calibrated offset distributions become available, a probabilistic threshold could be added later; the current evidence supports only bounds.
