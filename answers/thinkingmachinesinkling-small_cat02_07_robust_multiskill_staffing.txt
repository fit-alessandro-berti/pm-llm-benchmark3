# 3. Candidate policies

All policies use transparent dispatch rules that operators can audit.

### Policy 1 — Strict specialization with fixed queues
- **Eligibility / assignment:** Resources are permanently assigned to families:
  - Ada, Ben, Deepa: Intake, Mechanical, Validation.
  - Chen, Emil, Deepa: Electrical, Software, Validation.
  - Farah: emergency overflow only (all skills, 08–12).
- **Queues:** One queue per skill/family; P1 jumps to front of its family queue.
- **Preemption:** P1 can preempt P2/P3 diagnostic work if the resource is the designated family resource for that skill.
- **Parallel ME/ES:** Allowed only if both branches can be assigned to distinct eligible resources at the same time; else sequential.
- **Handover/minimization:** Cross-team cases (ME/ES) must hand over unless Deepa or Farah is used for both families; setup avoided because resources do not switch families between cases (fixed assignment).
- **Overflow:** None hard-coded; if queue exceeds 3 cases, call supervisor (modeled as forced use of Farah).

### Policy 2 — Full pooling to any qualified resource
- **Eligibility:** Any resource with non-None multiplier for the activity.
- **Priority score / dispatch:** At each decision point:
  1. Filter eligible resources with available next slot  current time + setup.
  2. Compute expected completion = max(resource_available, case_ready) + service*time + 7 min (handover if resource changed from previous activity) + 5 min (if cross-team and different resource).
  3. Choose the resource minimizing that expected completion; tie-break to lowest multiplier (fastest).
- **Reservation:** None.
- **Preemption:** Enabled; if P1 arrives and best resource busy with P2/P3 diagnostic, interrupt; restart penalty added.
- **Parallel ME/ES:** If two eligible resources are available and case priority is not P1 (to save coordination delay for P1), start both branches; else sequential.
- **Setup:** Applied explicitly when resource’s previous case used a different skill family.

### Policy 3 — Hybrid reserve + controlled cross-skill overflow (recommended primary)
- **Reservation thresholds:**
  - P1 cases reserve Ada (Intake/Val), Deepa (Intake/Mech/Elec/Val), and Chen/Emil (diagnostic) when available.
  - P1 diagnostic work is done sequentially on a cross-skilled resource (Deepa/Emil if qualified) to eliminate the 8 min coordination delay and minimize handover/setup.
- **P2/P3 dispatch:** Use general pool; if queue length > 2 or estimated wait > 15 min, overflow to reserved resource if it is idle.
- **Parallel/sequential:**
  - P1 ME/ES  sequential on single cross-skilled resource (no 8 min coord, no handover if same resource across intake/diag/val when possible).
  - P2/P3 ME/ES  parallel if two qualified resources idle; else sequential.
- **Preemption:** P1 can preempt P2/P3 only from non-reserved resources (to protect reserve); at most once per case.
- **Setup/handover:** Retain case on same resource across consecutive activities when eligible (e.g., Deepa does Intake  Mechanical  Validation); only add 7 min if a different resource is required.

3. `pm4py.discover_handover_of_work_network`: measure handover burden per policy; Policy 3 should show fewer cross-team edges.
4. `discover_dfg` / `discover_bpmn`: detect bottleneck migration (e.g., from Mechanical to Validation under U1).
5. Filter variants for ME/ES: compare path lengths of parallel vs sequential branches; if coherent with policy, confirm compliance.

**Drift detection:** If mean `actual_service_time` / `planned_service_time` > 1.15 for two weeks, revise mean estimates (U4 may have permanently shifted operating conditions).

# 9. Limits and validation plan

**What cannot be concluded from expected arrivals and ranges alone:**
- Correlation between case types and priorities (e.g., are ME cases more likely P1?).
- Actual service-time distributions (ranges may be truncated or bimodal).
- Dynamic behavior of preemption (when exactly does P1 arrive relative to remaining time?).
- Interaction of parallel branches with shared resource contention.
- Human factors (fatigue, error rates) that affect multipliers.

**Pilot / backtest design:**
1. **A/B pilot (4 weeks):** Run Policy 3 (Hybrid) on one shift and Policy 1 (Strict) on another, protecting P1 by always reserving Ada + Deepa. Measure P1 cycle time with control chart.
2. **Backtest with historical event log:** If available, replay arrivals; compare predicted vs actual handover counts from PM4Py `discover_handover_of_work_network`.
3. **Safety rule:** If P1 SLA over any 3-day rolling window falls below 85%, immediately revert to full reserve mode (Policy 3 with tightened thresholds) and disable P2/P3 overflow until recovery.
4. **Distinction test:** Use Mann-Whitney U on P1 cycle times between policies; require p < 0.05 and effect size > 0.3 for adoption.

**Validation metrics for rollout:**
- P1 attainment  88% (with 90% target).
- Max utilization spread < 15%.
- Handover events per case < 2.5 average.
- No increase in Validation stage mean delay > 10% over baseline.

If the pilot shows that setup time (5 min) dominates under Policy 2, the hybrid reserve is confirmed as the operational equilibrium.
