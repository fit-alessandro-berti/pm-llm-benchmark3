# Uncertainty-Aware Predictive Process Monitoring Study for Early Default Warning

## 1. Target definition

**Primary target formulation:**
*Default within 90 days after activation among applications that reach activation*, with prediction time at the first Credit Review event.

- **Prediction target:** Binary indicator `default_90d` (1 if default occurs within 90 days of Account Activated, 0 otherwise)
- **Prediction time:** First occurrence of "Credit Review" event
- **Horizon:** 90 days from Account Activated (not from prediction time)
- **Unit of analysis:** Individual credit application case
- **Population:** All applications that reach the first Credit Review event and are eventually activated
- **Estimand:** Risk of default conditional on reaching activation, given information available at first Credit Review

**Rationale:** This formulation is operationally defensible because:
1. It matches the business question's focus on activated accounts (the only ones exposed to credit risk)
2. It avoids counterfactual assumptions about what would happen to rejected/withdrawn cases if they were activated
3. It maintains clear temporal separation between prediction time and outcome observation
4. It aligns with the available labeled data (only activated accounts have observed outcomes)

**Alternative target formulation:**
*Competing risks model for all applications* with states: {Rejected, Withdrawn, Transferred, Activated (non-default), Activated (default)}.

- **Prediction target:** Probability of each terminal state at prediction time
- **Prediction time:** First Credit Review event
- **Horizon:** Until case termination (rejection, withdrawal, transfer, or activation)
- **Population:** All applications reaching first Credit Review

**Why it answers a different question:**
1. It provides a complete view of application outcomes rather than just default risk
2. It requires stronger assumptions about the relationship between rejection/withdrawal and default risk
3. It's more complex to implement and communicate to business stakeholders
4. It doesn't directly answer the lender's question about default risk among activated accounts

## 2. Cohort construction

**Inclusion rules:**
- All applications started between 1 Jan 2024 and 31 Dec 2025
- Must have at least one "Credit Review" event (prediction point)
- For primary analysis: must eventually reach "Account Activated" (regardless of label maturity)

**Exclusion rules:**
- Cases with no events after "Application Started" (data quality)
- Cases with corrupted timestamps (e.g., future dates)
- Cases from partner-originated transfers with no linkage (missing outcome risk)

**As-of rules:**
- Label maturity cutoff: 15 Feb 2026 (data extraction date)
- 90-day outcome window must be complete by cutoff (Account Activated  15 Nov 2025)
- Delayed outcome feed window: +35 days (Account Activated  11 Oct 2025 for guaranteed label availability)

**Cohort flow table:**

| Category | Count | Status | Notes |
|----------|-------|--------|-------|
| Applications started | 48,000 | | |
| No Credit Review event | 3,600 | Excluded | Data quality |
| Reached first Credit Review | 44,400 | | |
| - Rejected | 9,100 | Competing outcome | |
| - Withdrawn | 5,700 | Competing outcome | |
| - Transferred | 2,900 | Competing outcome (60% linked) | 1,740 linked, 1,160 unlinked |
| - Still open at cutoff | 5,100 | Censored | |
| - Activated (mature outcome) | 21,600 | Labeled | 18,900 non-default, 2,700 default |
| - Activated (immature outcome) | 3,600 | Censored | Outcome not yet mature |

**Primary analysis cohort:** 21,600 labeled activated cases + 3,600 censored activated cases = 25,200 cases

## 3. Censoring and missing-label strategy

**Censoring types:**
1. **Ordinary right censoring:** Activated cases with Account Activated > 11 Oct 2025 (insufficient time for 90-day window + 35-day feed delay)
2. **Delayed labels:** Activated cases with Account Activated between 11 Oct-15 Nov 2025 (90-day window complete but feed may be delayed)
3. **Selection through activation:** Rejected/withdrawn/transferred cases (never exposed to credit risk)
4. **Transfer as competing event:** Transferred cases with no linkage (outcome missing not at random)
5. **Permanently missing feeds:** Partner-originated cases (elevated missingness risk)

**Primary analysis strategy:**
- Treat immature activated cases (3,600) as right-censored at prediction time
- Use survival analysis (Cox proportional hazards or random survival forests) to model time-to-default from activation
- For binary classification, use only mature cases (21,600) with inverse probability of censoring weighting (IPCW) to account for selection bias

**Sensitivity analyses:**
1. **Complete case analysis:** Train only on mature cases (21,600) without weighting
2. **Multiple imputation:** Impute outcomes for immature cases based on observed patterns
3. **Competing risks model:** Include rejected/withdrawn/transferred as separate states
4. **Policy-period analysis:** Separate models for pre/post 1 July 2025 policy change

**Assumption testability:**
- **Testable:** Proportional hazards assumption (Schoenfeld residuals), censoring independence (log-rank test)
- **Partially testable:** Missing at random for delayed labels (sensitivity analysis), transfer linkage bias (comparison of linked vs unlinked)
- **Untestable:** Counterfactual default risk for rejected cases, missingness mechanism for permanently missing feeds

## 4. Prefix extraction

**Prefix generation rules:**
1. **Fixed event-count prefixes:** First 3, 5, and 7 events after "Application Started"
2. **Elapsed-time prefixes:** 1 day, 3 days, and 7 days after "Application Started"
3. **Process-aware prefixes:** First Credit Review event (prediction point)

**Handling special cases:**
- **Short cases:** Include cases with fewer events than prefix length (pad with missing values)
- **Repeated document loops:** Treat as distinct events (no aggregation)
- **Activity renaming:** Map renamed activities to consistent names (pre/post 15 Oct 2025)
- **Duplicate events:** Remove exact duplicates (same case, activity, timestamp)

**Implementation approach:**
1. For each case, identify prediction point (first Credit Review)
2. Extract all events up to and including prediction point
3. For fixed-length prefixes, take first N events (N=3,5,7)
4. For time-based prefixes, take all events within T days (T=1,3,7)
5. Ensure no future events (after prediction point) are included in prefixes

## 5. Process-aware features

**Static case attributes (available at prediction time):**
- `case:channel`
- `case:region`
- `case:requested_amount`
- Initial `risk_score` (from first event)

**Prefix-derived features:**
- **Control-flow:**
  - Sequence of activities (variants)
  - Number of document requests
  - Number of Credit Review loops
  - Presence of specific activities (e.g., "Request Documents")
  - Directly-follows graph features (e.g., transition probabilities)

- **Timing:**
  - Total prefix duration
  - Time between Application Started and first Credit Review
  - Time between last two events
  - Average time between events
  - Time since last event (at prediction point)

- **Resource/queue:**
  - Number of distinct resources involved
  - Resource experience (at extraction time - use with caution)
  - Number of cases in queue at prediction time (requires historical reference)

- **Rework:**
  - Number of repeated activities
  - Number of document request loops
  - Number of Credit Review loops

- **Cohort/calendar:**
  - Application start month/quarter
  - Policy period (pre/post 1 July 2025)
  - System version (pre/post 15 Oct 2025)

**Historical reference features:**
- Average processing time for similar cases (same channel, region)
- Default rate for similar cases (same channel, region, requested amount band)
- Current queue length (requires separate queue data)

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|-------------------------|----------------------|-------------------------|------------------|-----------|
| `final_limit` | Contains post-decision information | Only available after Accept/Reject | Drop | Not available at prediction time |
| `decision_reason` | Contains post-decision information | Only available after Accept/Reject | Drop | Not available at prediction time |
| `collection_status` | Contains post-activation information | Only available after Account Activated | Drop | Reveals default status |
| Future events | Events after prediction point | Only events up to prediction point | Drop | Lookahead bias |
| `documents_total` | May include same-day uploads after prediction time | Use snapshot from previous day | Repair | Potential same-day leakage |
| Updated `risk_score` | May be updated after prediction point | Use value at prediction point | Repair | Later updates not available |
| Resource experience | Recorded at extraction time | Use experience at event time (if available) | Repair | Temporal mismatch |
| `default_90d` | Target variable | Only available after 90-day window | Keep | Properly delayed |
| `label_available_at` | Reveals label timing | Not used as feature | Drop | Potential leakage |
| `source_system` | May reveal post-migration cases | Available at all times | Keep | Static attribute |
| `data_extract_time` | Reveals case maturity | Not used as feature | Drop | Potential leakage |

## 7. Validation design

**Temporal validation scheme:**
1. **Split by application start time:**
   - Train: 1 Jan 2024 - 31 Dec 2024 (12 months)
   - Validation: 1 Jan 2025 - 30 Jun 2025 (6 months, pre-policy change)
   - Test: 1 Jul 2025 - 31 Dec 2025 (6 months, post-policy change)

2. **Label maturity handling:**
   - For each split, apply the same 15 Feb 2026 cutoff
   - Only include cases with mature outcomes in validation/test sets
   - Use censored cases in training for survival analysis

3. **System migration handling:**
   - Ensure test set contains only post-migration cases (after 15 Oct 2025)
   - Map activity names consistently across periods

**Evaluation metrics:**
1. **Primary metrics (binary classification):**
   - AUC-ROC (accounts for class imbalance)
   - Precision-Recall curve (focus on default class)
   - Brier score (calibration)
   - Expected calibration error

2. **Survival analysis metrics:**
   - Concordance index (time-dependent AUC)
   - Brier score for survival models
   - Integrated Brier score

3. **Subgroup analysis:**
   - Performance by channel, region, requested amount band
   - Performance by policy period (pre/post 1 Jul 2025)
   - Performance by system version (pre/post 15 Oct 2025)

4. **Distribution shift tests:**
   - Population stability index (PSI) for key features
   - Kolmogorov-Smirnov tests for feature distributions
   - Performance degradation between validation and test sets

**Why random split is misleading:**
1. Temporal dependencies: Cases from the same time period share unobserved factors
2. Policy changes: Random split would mix pre/post policy cases
3. System changes: Random split would mix pre/post migration cases
4. Label maturity: Random split could include immature cases in test set
5. Concept drift: Default risk may change over time due to external factors

## 8. Limitations and decision-use boundary

**What the study can claim:**
1. Predictive association between early process features and default risk among activated accounts
2. Relative risk ranking of applications at first Credit Review
3. Identification of high-risk process patterns (e.g., frequent document requests)
4. Performance metrics under the observed activation policy

**What the study cannot claim:**
1. Counterfactual default risk for rejected/withdrawn cases (no observed outcomes)
2. Causal effect of process changes on default risk (observational data only)
3. Absolute default probabilities without activation selection bias
4. Performance under different activation policies

**Ways deployment could change the data-generating process:**
1. **Feedback loops:** Model-informed decisions may change applicant behavior (e.g., more withdrawals)
2. **Policy changes:** Lender may adjust activation criteria based on model predictions
3. **Process changes:** Lender may modify the application process in response to findings
4. **Adversarial behavior:** Applicants or intermediaries may game the system
5. **Distribution shift:** Economic conditions may change default risk independently of process features

**Decision-use boundary:**
- The model should be used as a decision support tool, not an automated decision-maker
- Predictions should be interpreted as relative risk scores, not absolute probabilities
- The model is only valid for applications following the observed process patterns
- Regular monitoring of model performance and feature distributions is required
- The model should not be used to evaluate counterfactual scenarios (e.g., "what if we activated all applications?")

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py
from datetime import datetime, timedelta
from typing import Tuple, Dict, List
import numpy as np
from sklearn.model_selection import train_test_split

# Configuration
DATA_PATH = "applications_events.csv"
CUTOFF_DATE = datetime(2026, 2, 15)  # Data extraction date
POLICY_CHANGE_DATE = datetime(2025, 7, 1)
MIGRATION_DATE = datetime(2025, 10, 15)
MIN_HORIZON = timedelta(days=90 + 35)  # 90-day window + 35-day feed delay

def load_and_preprocess_data() -> pd.DataFrame:
    """Load and preprocess the event log."""
    df = pd.read_csv(DATA_PATH)
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])
    df = df.sort_values(["case:concept:name", "time:timestamp"])

    # Map renamed activities (post-migration)
    activity_map = {
        "Old_KYC_Check": "Identity/KYC Check",
        "New_Credit_Review": "Credit Review"
    }
    df["concept:name"] = df["concept:name"].replace(activity_map)

    # Remove exact duplicates (same case, activity, timestamp)
    df = df.drop_duplicates(
        subset=["case:concept:name", "concept:name", "time:timestamp"],
        keep="first"
    )

    return df

def identify_prediction_points(df: pd.DataFrame) -> pd.DataFrame:
    """Identify the first Credit Review event for each case."""
    credit_reviews = df[df["concept:name"] == "Credit Review"]
    first_reviews = credit_reviews.groupby("case:concept:name").first().reset_index()
    first_reviews = first_reviews[["case:concept:name", "time:timestamp"]]
    first_reviews = first_reviews.rename(columns={
        "time:timestamp": "prediction_time"
    })
    return first_reviews

def determine_case_outcomes(df: pd.DataFrame, first_reviews: pd.DataFrame) -> pd.DataFrame:
    """Determine case outcomes and label maturity."""
    # Get case start and end times
    case_info = df.groupby("case:concept:name").agg(
        start_time=("time:timestamp", "min"),
        end_time=("time:timestamp", "max"),
        last_activity=("concept:name", "last"),
        has_activated=("concept:name", lambda x: "Account Activated" in x.values),
        has_default=("default_90d", lambda x: x.notna().any() and x.max() == 1),
        label_available_at=("label_available_at", "max")
    ).reset_index()

    # Merge with prediction points
    case_info = case_info.merge(first_reviews, on="case:concept:name", how="left")

    # Determine outcome status
    case_info["outcome_status"] = "unknown"
    case_info.loc[case_info["last_activity"] == "Rejected", "outcome_status"] = "rejected"
    case_info.loc[case_info["last_activity"] == "Withdrawn", "outcome_status"] = "withdrawn"
    case_info.loc[case_info["last_activity"] == "Transferred", "outcome_status"] = "transferred"
    case_info.loc[case_info["has_activated"] & case_info["has_default"], "outcome_status"] = "default"
    case_info.loc[case_info["has_activated"] & ~case_info["has_default"], "outcome_status"] = "non_default"
    case_info.loc[case_info["end_time"] == CUTOFF_DATE, "outcome_status"] = "still_open"

    # Determine label maturity
    case_info["label_mature"] = (
        case_info["has_activated"] &
        (case_info["end_time"] + MIN_HORIZON <= CUTOFF_DATE) &
        (case_info["label_available_at"] <= CUTOFF_DATE)
    )

    # For primary analysis: only activated cases
    case_info["primary_analysis_cohort"] = case_info["has_activated"]

    return case_info

def create_temporal_splits(case_info: pd.DataFrame) -> Dict[str, pd.DataFrame]:
    """Create temporal train/validation/test splits."""
    # Split by case start time
    train_cases = case_info[
        case_info["start_time"] < datetime(2025, 1, 1)
    ]["case:concept:name"]

    val_cases = case_info[
        (case_info["start_time"] >= datetime(2025, 1, 1)) &
        (case_info["start_time"] < datetime(2025, 7, 1))
    ]["case:concept:name"]

    test_cases = case_info[
        case_info["start_time"] >= datetime(2025, 7, 1)
    ]["case:concept:name"]

    # For primary analysis: only activated cases with mature labels in val/test
    val_cases = val_cases[
        case_info.loc[val_cases.index, "label_mature"] &
        case_info.loc[val_cases.index, "primary_analysis_cohort"]
    ]

    test_cases = test_cases[
        case_info.loc[test_cases.index, "label_mature"] &
        case_info.loc[test_cases.index, "primary_analysis_cohort"]
    ]

    return {
        "train": train_cases,
        "validation": val_cases,
        "test": test_cases
    }

def extract_prefixes(df: pd.DataFrame, case_info: pd.DataFrame, splits: Dict[str, pd.DataFrame]) -> Dict[str, pd.DataFrame]:
    """Extract prefixes for each split."""
    # Convert to PM4Py event log
    event_log = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp"
    )

    prefix_logs = {}

    for split_name, case_ids in splits.items():
        # Filter cases for this split
        split_log = pm4py.filter_event_attribute_values(
            event_log,
            "case:concept:name",
            case_ids.tolist()
        )

        # Extract prefixes up to prediction point
        prefix_log = pm4py.get_prefixes_from_log(
            split_log,
            activity_key="concept:name",
            timestamp_key="time:timestamp",
            case_id_key="case:concept:name",
            max_events=7  # Fixed-length prefix
        )

        # For time-based prefixes, we would use a different approach
        # Here we demonstrate fixed-length prefixes

        # Convert back to DataFrame
        prefix_df = pm4py.convert_to_dataframe(prefix_log)

        # Add case-level information
        prefix_df = prefix_df.merge(
            case_info[["case:concept:name", "outcome_status", "label_mature", "prediction_time"]],
            on="case:concept:name",
            how="left"
        )

        # Ensure no events after prediction time are included
        prefix_df = prefix_df[
            prefix_df["time:timestamp"] <= prefix_df["prediction_time"]
        ]

        prefix_logs[split_name] = prefix_df

    return prefix_logs

def create_features(prefix_dfs: Dict[str, pd.DataFrame]) -> Dict[str, pd.DataFrame]:
    """Create process-aware features from prefixes."""
    feature_dfs = {}

    for split_name, prefix_df in prefix_dfs.items():
        # Basic case attributes
        features = prefix_df.groupby("case:concept:name").first()[[
            "case:channel", "case:region", "case:requested_amount", "risk_score"
        ]].reset_index()

        # Control-flow features
        variants = pm4py.get_variants_sorted(
            pm4py.convert_to_event_log(prefix_df)
        )
        variant_counts = pd.DataFrame([
            {"case:concept:name": case, "variant": ";".join([x["concept:name"] for x in variant])}
            for case, variant in variants.items()
        ])
        features = features.merge(variant_counts, on="case:concept:name", how="left")

        # Timing features
        temporal_features = pm4py.extract_temporal_features_dataframe(
            prefix_df,
            case_id="case:concept:name",
            activity_key="concept:name",
            timestamp_key="time:timestamp"
        )
        features = features.merge(temporal_features, on="case:concept:name", how="left")

        # Rework features
        dfg = pm4py.discover_dfg(
            pm4py.convert_to_event_log(prefix_df)
        )
        # Add DFG-based features (example: number of document requests)
        doc_requests = prefix_df[
            prefix_df["concept:name"] == "Request Documents"
        ].groupby("case:concept:name").size().reset_index(name="num_doc_requests")
        features = features.merge(doc_requests, on="case:concept:name", how="left")
        features["num_doc_requests"] = features["num_doc_requests"].fillna(0)

        # Add outcome for labeled cases
        features = features.merge(
            prefix_df.groupby("case:concept:name")["outcome_status"].first().reset_index(),
            on="case:concept:name",
            how="left"
        )

        # Add policy period
        features["policy_period"] = features["case:concept:name"].map(
            lambda x: "post" if case_info.loc[x, "start_time"] >= POLICY_CHANGE_DATE else "pre"
        )

        feature_dfs[split_name] = features

    return feature_dfs

def leakage_audit(feature_dfs: Dict[str, pd.DataFrame]) -> pd.DataFrame:
    """Perform leakage audit on features."""
    audit_results = []

    for split_name, features in feature_dfs.items():
        # Check for post-prediction features
        post_pred_features = [
            "final_limit", "decision_reason", "collection_status"
        ]

        for feature in post_pred_features:
            if feature in features.columns:
                audit_results.append({
                    "split": split_name,
                    "feature": feature,
                    "risk": "Post-prediction information",
                    "action": "Drop",
                    "present": True
                })
            else:
                audit_results.append({
                    "split": split_name,
                    "feature": feature,
                    "risk": "Post-prediction information",
                    "action": "Drop",
                    "present": False
                })

        # Check for same-day document leakage
        if "documents_total" in features.columns:
            audit_results.append({
                "split": split_name,
                "feature": "documents_total",
                "risk": "Potential same-day leakage",
                "action": "Repair (use previous day snapshot)",
                "present": True
            })

        # Check for updated risk score
        if features["risk_score"].nunique() > 1:
            audit_results.append({
                "split": split_name,
                "feature": "risk_score",
                "risk": "May be updated after prediction point",
                "action": "Repair (use value at prediction point)",
                "present": True
            })

    return pd.DataFrame(audit_results)

def main():
    # Load and preprocess data
    print("Loading and preprocessing data...")
    df = load_and_preprocess_data()

    # Identify prediction points
    print("Identifying prediction points...")
    first_reviews = identify_prediction_points(df)

    # Determine case outcomes
    print("Determining case outcomes...")
    case_info = determine_case_outcomes(df, first_reviews)

    # Print cohort statistics
    print("\nCohort statistics:")
    print(case_info["outcome_status"].value_counts())
    print("\nPrimary analysis cohort (activated cases):")
    print(case_info[case_info["primary_analysis_cohort"]]["outcome_status"].value_counts())
    print("\nMature labels in primary cohort:")
    print(case_info[case_info["primary_analysis_cohort"]]["label_mature"].value_counts())

    # Create temporal splits
    print("\nCreating temporal splits...")
    splits = create_temporal_splits(case_info)

    # Extract prefixes
    print("Extracting prefixes...")
    prefix_dfs = extract_prefixes(df, case_info, splits)

    # Create features
    print("Creating features...")
    feature_dfs = create_features(prefix_dfs)

    # Leakage audit
    print("\nPerforming leakage audit...")
    audit_df = leakage_audit(feature_dfs)
    print(audit_df[audit_df["present"]])

    # Here you would typically:
    # 1. Apply the leakage audit recommendations
    # 2. Encode categorical features
    # 3. Handle missing values
    # 4. Train survival or classification models
    # 5. Evaluate on validation/test sets

    print("\nPipeline complete. Ready for modeling.")

if __name__ == "__main__":
    main()
```
