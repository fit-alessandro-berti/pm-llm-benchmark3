def validate_exemption(ex, trigger_ts, snap, rule='R1'):
    reasons = []
    if ex is None: return None, ['NO_EXEMPTION']
    if ex['approved_by'] != 'Head_Compliance': reasons.append('NOT_APPROVED_BY_HEAD_COMPLIANCE')
    if ex['effective_from'] > trigger_ts: reasons.append('EFFECTIVE_AFTER_TRIGGER')
    if ex['expires'] <= trigger_ts: reasons.append('EXPIRED_AT_TRIGGER')
    scope_j = ex['scope_jurisdiction']; 
    if snap['jurisdiction'] != scope_j: reasons.append('JURISDICTION_SCOPE_MISMATCH')
    if snap['customer_type'] != ex['scope_customer_type']: reasons.append('CUSTOMER_TYPE_SCOPE_MISMATCH')
    if snap['amount'] is None: reasons.append('AMOUNT_UNKNOWN_SCOPE_UNVERIFIABLE')
    elif snap['amount'] > ex['scope_amount_max']: reasons.append('AMOUNT_SCOPE_MISMATCH')
    if rule not in ex['waived_rules']: reasons.append('RULE_NOT_WAIVED')
    # evidence: approval existed at trigger time
    ev = None
    if ex.get('signature_valid') and ex.get('certificate_created') and parse_ts(ex['certificate_created']) <= trigger_ts:
        ev = 'QUALIFIED_SIGNATURE_BEFORE_TRIGGER'
    elif ex.get('witness_independent') and ex.get('displayed_approval') and parse_ts(ex['displayed_approval']) <= trigger_ts:
        ev = 'INDEPENDENT_WITNESS_CORROBORATION'
    else:
        reasons.append('NO_EVIDENCE_OF_TIMELY_APPROVAL')
    return ev, reasons

def validate_exemption(ex, trigger_ts, snap):

    if ex is None:

# TransactionReview Conformance Assessment (EventTime, RuleBased)

---

## 1. Temporal Data Semantics

**State reconstruction.** The log is a set of *attributecarrying events*, not a set of case rows. For each case I replay the events in the total order `key(e) = (time(e), event_index(e))` (lexicographic; `event_index` breaks ties) and maintain a mutable state vector `S = (amount, risk_level, jurisdiction, customer_type)`. An event *updates* `S[c]` only for attributes whose cell is nonblank. This is a forwardonly fold: the state "at" an event `e` contains only updates from events `f` with `key(f)  key(e)`. No value is ever read from an event after `e`; the final case state is **never** projected backward.

**Blanks.** An empty cell in `amount / risk_level / jurisdiction / customer_type / exemption_id` means *"this event carried no information about this attribute"*, i.e. "no update at this event" — not "the value is null". A blank therefore does **not** overwrite a previously known value and does **not** create an unknown value. An unknown value exists only when no event at or before the point of interest ever supplied that attribute (e.g. TX305's amount at release).

**Material change.** Materiality is derived from R4, not from the fact that *some* update occurred:
* amount increase **> 20 %**  material (`AMOUNT_INCREASE_GT20`);
* amount increase  20 %  **immaterial** (R4 threshold);
* amount decrease  **immaterial** ("a decrease does not by itself invalidate a review");
* risk / jurisdiction / customertype change  material (they are triggeractivating attributes);
* reemission of the same value  `NO_CHANGE`, immaterial.

**Four different times.**
* **Event time** – when the business fact happened (the timestamp column); it drives all rule evaluation.
* **Effective time** – when an attribute update becomes operative. Per instruction, the event timestamp *is* the effective time unless a record explicitly establishes otherwise (e.g. an exemption's displayed `effective_from`). A displayed backdated field is a *claim* about effective time, not proof.
* **Record time** – when the system wrote the row (e.g. `Record_Exemption` at 11:00). Record time is *never* the trigger time; it can only corroborate that an earlier approval existed.
* **Evidence time** – when the *proof* was created/observed (signed certificate creation time, witness statement time, immutable release payload time). Evidence time decides admissibility and credibility of an exemption claim (R5).

**Same timestamp.** TX311 has `Enhanced_Review` (event_index 3) and `Update_Jurisdiction` (event_index 4) at `16:20`. The review therefore **did not see** the DE reclassification; the DE value is operative only for events with `event_index  4`. TX309 and TX301 have single events per timestamp, so ordering is unambiguous there.

**Limits.** Conformance is computed only over the events present. Where evidence needed for a decision is missing (amount at release in TX305, executable proof of approval in TX310), the case is reported as indeterminate/contested rather than defaulted (R6). Formally: a case is COMPLIANT only when every *triggered* obligation has a satisfied or validly waived discharge; it is NONCOMPLIANT only when a trigger is provable *and* the discharge is provably absent/invalid; otherwise INDETERMINATE.

## 4. Ambiguities and Alternative Readings

**TX302 — late exemption record vs. timely approval.**
*Reading A (adopted).* EX77 is valid: a qualified digital signature created 09:05 with a valid hash is evidence that approval existed at 09:05, i.e. before the 09:40 trigger. The 11:00 row is a *recordtime* artefact of an outage; R5 explicitly allows a late record as evidence of earlier approval, and here the instrument itself (signature, hash) proves timeliness. Result: **COMPLIANT**, and even without the waiver the outcome is COMPLIANT because `Enhanced_Review` 09:20 independently discharges R1.
*Reading B.* If one insists that the batch job was the only authorised approval channel, the waiver was unusable at 09:40 — but R1 is still satisfied by the Enhanced_Review, so the classification is unchanged.
*What would change the result.* Evidence that the 09:05 signature was applied to a different document or that the signed instruction covered a *different* transaction/amount band; then EX77 would fail R5's scope limb and R1 would rest solely on the ER (still compliant). Alternatively, a finding that the ER 09:20 covered only a partial scope  the classification would become **JUSTIFIED_EXCEPTION** (still not a breach).

**TX305 — unknown amount at release.**
*Reading A (adopted).* The amount at release is . R1's trigger cannot be established **or excluded**, so R6 requires INDETERMINATE. The corroborating `Settlement_Confirmed` amount (150 000, 20260407 08:00) is reliable *at settlement time* and is *evidence time*, i.e. after the release; it is admissible as corroboration but not as the releasetime amount, and the note says only that it "may equal" the release amount.
*Reading B (strong, and arguably the betterfounded engineering answer).* The conclusion is **branchinvariant**: if the released amount was < 100 000, R1 never triggers; if it was  100 000, R1 is triggered but `Enhanced_Review` 11:15 exists after the only data change (11:00 create) and before release, so R1 is satisfied. R2 never triggers (MEDIUM, CORPORATE), R3/R4 have no trigger. Hence COMPLIANT regardless of the missing value — i.e. the defect is an **auditability** defect, not a compliance defect.
*Reading C.* If the amount learned at settlement (150 000) is treated as a discovered **material amount change** whose discovery postdates the release, then the review's baseline is unknown and R4 cannot be applied (increase from  is not classifiable)  INDETERMINATE with a possible latent R1 failure.
*What would change the result.* An immutable release payload (or bank debit advice timestamped 11:30) establishing the released amount: 150 kplus  defensible **COMPLIANT** (via the 11:15 ER) and a documentation finding; a value below 100 k  clean **COMPLIANT**. A finding that the ER document was scoped to a **maximum** amount below the released amount (or that the operational policy required a Compliance_Approve for any CA foreign high value)  **NONCOMPLIANT**.

**TX310 — backdated exemption, contested evidence.**
*Reading A (adopted).* R5 imposes the burden on the party asserting the exemption. The only candidate proof of approval at 08:45/08:50 is (i) a displayed field on a PDF whose signing certificate was created at 10:30 — after the release — and (ii) oral evidence from the transaction requester himself. A backdated display alone is not conclusive, and an interestedparty witness is not corroboration; meanwhile the certificate timeline (created 10:30, inserted 11:00) positively suggests the artefact did not exist at 10:00. The waiver is denied and the underlying R1 duty is undischarged (only a Standard_Review exists)  **NONCOMPLIANT**.
*Reading B.* If the signingcertificate timestamp is treated as a *certificate issuance* artefact rather than the moment of the approval act, and if the witness's 08:45 oral approval is credited (some policies accept documented oral approvals by the Head_Compliance, later formalised), then EX88 was in force (effective 08:00, unexpired at 12:00, scope matches 200 000) and the case becomes **JUSTIFIED_EXCEPTION**.
*Reading C (intermediate).* Treat it as INDETERMINATE because the evidence is internally contradictory (PDF 08:50 vs. certificate 10:30 vs. witness 08:45).
*What would change the result.* A Head_Compliance attestation or a contemporaneous approval log entry timestamped  10:00 that is independent of the requester  JUSTIFIED_EXCEPTION. Certificate metadata showing creation at 08:47 with a valid hash and a valid signature (not merely an issuerside timestamp)  JUSTIFIED_EXCEPTION. Confirmation that the requester’s testimony is the sole basis  NONCOMPLIANT stands; note the case is also aggravated by the fact that the *release message itself* already referenced EX88 at 10:00, before the record existed, which invites scrutiny of control ordering.

**TX311 — sametimestamp ordering and a jurisdiction that changed after the review.**
*Reading A (adopted).* With `event_index` 3 < 4, the jurisdiction became DE **after** the Enhanced_Review. At release (16:30) the jurisdiction is DE, so R1's foreign limb is false and R1 is not triggered; R2 is not triggered (LOW / CORPORATE); the +27.8 % amount change at 16:10 precedes the 16:20 ER, so R4 does not invalidate it  COMPLIANT. Note that the order is not merely cosmetic: had the update come first, the ER would have reviewed a DE transaction and never had to exist under R1; as it stands the transaction was reviewed on the *more* conservative (US, 115 k) state, which is why the case is clean.
*Reading B.* If the 16:20 DE change were shown to be **retroactively effective** (e.g. an effectivedated correction stating the transaction was always DE), the ER would have been performed against a state that never existed and would be a documentation defect, though not a breach.
*Reading C.* If the log's `event_index` were unreliable (a sourcesystem reordering), the state could be reversed, and one would need the ingestion sequence, perevent offsets and server timestamps to order the pair. The outcome is robust here (both orders are compliant) but the *control path* differs, which matters for audit narratives.

**TX306 — materiality threshold vs. "any change".** *Adopted:* only a >20 % increase is material, so the 12:30 +4.55 % update does not disturb the 12:15 ER and the case is COMPLIANT. *Alternative:* if "latest material data change" in R1 were read as "latest **any** change to any triggerrelevant attribute", then the 12:30 update would postdate the ER and R1 would be violated (NONCOMPLIANT). This alternative is rejected because R4 supplies the only materiality definition in the policy and explicitly excludes decreases and small increases; but it shows that R1 and R4 need an explicit crossreference (see §7).

**TX307 — can an approval over a standard packet cure a missing enhanced review?** *Adopted:* no — the release was of a PEP customer and no Enhanced_Review exists, and the Compliance_Approve explicitly "approved standard review packet". *Alternative (requires defending a different interpretation):* if the policy treated a properly approved standard packet as an equivalent evidenced review for nonhighrisk PEPs (i.e. R2's "relevant Enhanced_Review" being read as "the review that was actually performed and approved"), the case could be defended as a controlequivalence argument. That reading conflicts with the stated semantic fact that a Standard_Review is not an Enhanced_Review and with "a Compliance_Approve that reviewed only a standard packet does not cure the absence of Enhanced_Review unless you defend a different interpretation" — it is therefore recorded as a defensiblebutrejected position, and is the single most likely place for a reviewer to disagree.

**TX303 / TX301 / TX309 — potential unlogged evidence.** For TX303 (no Compliance_Approve recorded) and TX309 (no post15:28 ER), the log may simply be incomplete. If an outofband, timestamped approval or review is produced (with evidence time before release), the classification flips to COMPLIANT. The assessment stands on the log as recorded.

**TX308 — threshold boundary.** "At least EUR 100 000" is read inclusively, so R1 is triggered (and satisfied). If the threshold were strictly greater than 100 000, R1 would not trigger and the case would be trivially compliant — same classification, different audit narrative.

# ---------------------------------------------------------------------
# 1) Parse the log (io.StringIO), keep event_index, parse UTC timestamps
# ---------------------------------------------------------------------
def load_log():
    df = pd.read_csv(io.StringIO(CSV_TEXT), dtype=str, keep_default_na=False)
    df['event_index'] = df['event_index'].astype('int64')
    try:
        df['ts'] = pd.to_datetime(df['time:timestamp'], utc=True, format='ISO8601')
    except Exception:
        df['ts'] = pd.to_datetime(df['time:timestamp'], utc=True)
    df = df.sort_values(['case:concept:name', 'ts', 'event_index'],
                        kind='mergesort').reset_index(drop=True)
    return df


# ---------------------------------------------------------------------
# 2) PM4Py: convert to a PM4Py event log (needed for the control-flow view)
# ---------------------------------------------------------------------
try:
    import pm4py
    HAVE_PM4PY = True
except Exception:                                   # pragma: no cover
    HAVE_PM4PY = False


def to_pm4py_log(df):
    """Format the frame into a PM4Py EventLog; fall back to manual Event construction."""
    pdf = df.copy()
    pdf['time:timestamp'] = pdf['ts'].dt.tz_convert('UTC').dt.tz_localize(None)
    if HAVE_PM4PY:
        try:
            log = pm4py.format_dataframe(pdf,
                                         case_id='case:concept:name',
                                         activity_key='concept:name',
                                         timestamp_key='time:timestamp')
            return log
        except Exception as exc:
            print('[pm4py] format_dataframe unavailable (%s); using manual EventLog' % exc)
    from pm4py.objects.log.log import Event, EventLog
    log = EventLog()
    for _, r in pdf.iterrows():
        e = Event()
        e['case_id'] = r['case:concept:name']
        e['activity'] = r['concept:name']
        e['time:timestamp'] = r['time:timestamp'].to_pydatetime()
        e['event_index'] = int(r['event_index'])
        e['org:resource'] = r['org:resource']
        log.add(e)
    return log

# 3) Forward-only attribute propagation (pandas ffill) + cross-check
# ---------------------------------------------------------------------
def forward_fill_state(df):
    """Blank cell == 'no update at this event'. ffill only propagates PAST values."""
    d = df.sort_values(['case:concept:name', 'ts', 'event_index'],
                        kind='mergesort').copy()
    for c in ('risk_level', 'jurisdiction', 'customer_type'):
        d['state_' + c] = d[c].replace('', np.nan)          # blank -> no information
    d['state_amount'] = pd.to_numeric(d['amount'].replace('', np.nan), errors='coerce')
    g = d.groupby('case:concept:name', sort=False)
    for c in ('state_risk_level', 'state_jurisdiction', 'state_customer_type', 'state_amount'):
        d[c] = g[c].ffill()                                 # forward only, never backward
    return d


# ---------------------------------------------------------------------
# 4/5) Event-time DFA: replay events, track state + last relevant events
# ---------------------------------------------------------------------
def build_dfa(df):
    timelines = {}
    for cid, g in df.groupby('case:concept:name', sort=True):
        g = g.sort_values(['ts', 'event_index'], kind='mergesort')
        state = {'amount': None, 'risk_level': None, 'jurisdiction': None, 'customer_type': None}
        seq, idx = [], -1
        for _, r in g.iterrows():
            idx += 1
            changes = []
            for c in ATTRIBUTES:
                v = r[c]
                v = v.strip() if isinstance(v, str) else v
                if v == '' or v is None or (isinstance(v, float) and np.isnan(v)):
                    continue                              # blank == no update at this event
                old = state[c]
                if c == 'amount':
                    new = float(v)
                    if old is None or old == 0:
                        pct, kind = None, 'AMOUNT_UNKNOWN_BASE'
                    else:
                        pct = (new - old) / old
                        if pct > MATERIAL_INCREASE:
                            kind = 'AMOUNT_INCREASE_GT20'   # material (R4)
                        elif pct > 0:
                            kind = 'AMOUNT_INCREASE_LE20'    # immaterial
                        elif pct < 0:
                            kind = 'AMOUNT_DECREASE'         # immaterial (R4)
                        else:
                            kind = 'AMOUNT_UNCHANGED'
                    state[c] = new
                else:
                    new, pct = v, None
                    kind = ('ATTR_' + c.upper()) if old != new else 'NO_CHANGE'
                    state[c] = new
                changes.append(dict(attr=c, old=old, new=new, pct=pct, kind=kind))
            exid = r['exemption_id']
            exid = exid.strip() if isinstance(exid, str) else exid
            seq.append(dict(idx=idx, key=(r['ts'], int(r['event_index'])), ts=r['ts'],
                            event_index=int(r['event_index']), activity=r['concept:name'],
                            org=r['org:resource'], note=r['note'], changes=changes,
                            snap=dict(state),
                            amt_old=next((c['old'] for c in changes if c['attr'] == 'amount'), None),
                            amt_new=next((c['new'] for c in changes if c['attr'] == 'amount'), None),
                            exemption_id=(exid or None)))
        # pointers: last occurrence of each control event, and last material change
        er = sr = ca = screen = lu = mat = None
        for e in seq:
            a = e['activity']
            if a == 'Enhanced_Review':
                er = e['idx']
            elif a == 'Standard_Review':
                sr = e['idx']
            elif a == 'Compliance_Approve':
                ca = e['idx']
            elif a == 'Sanctions_Screen':
                screen = e['idx']
            elif a == 'Sanctions_List_Update':
                lu = e['idx']
            if any(c['kind'] in MATERIAL_KINDS for c in e['changes']):
                mat = e['idx']
            e.update(er_idx=er, sr_idx=sr, ca_idx=ca, screen_idx=screen,
                     list_idx=lu, material_idx=mat)
        timelines[cid] = seq
    return timelines


def r4_check(seq, rev_idx):
    """Was the review invalidated by a >20% increase after it (R4)?"""
    if rev_idx is None:
        return ('N/A', None)
    base = seq[rev_idx]['snap'].get('amount')
    if base is None:
        return ('UNKNOWN_BASE', None)          # increase from unknown base: not classifiable
    worst = None
    for e in seq[rev_idx + 1:]:
        if e['amt_old'] is not None and e['amt_new'] is not None and base:
            pct = (e['amt_new'] - base) / base
            worst = pct if worst is None else max(worst, pct)
    if worst is not None and worst > MATERIAL_INCREASE:
        return ('INVALIDATED', worst)
    return ('VALID', worst)


# ---------------------------------------------------------------------
# 6) Exemption validity per R5 (scope + validity window + evidence time)
# ---------------------------------------------------------------------
def validate_exemption(ex, trigger_ts, snap, duty='R1'):
    reasons, evidence = [], []
    if ex is None:
        return False, ['NO_EXEMPTION_RECORD'], None
    if ex['approved_by'] != 'Head_Compliance':
        reasons.append('NOT_APPROVED_BY_HEAD_COMPLIANCE')
    if pd.Timestamp(ex['effective_from']) > trigger_ts:
        reasons.append('EFFECTIVE_FROM_AFTER_TRIGGER')
    if pd.Timestamp(ex['expires']) <= trigger_ts:
        reasons.append('EXPIRED_AT_TRIGGER')
    if snap.get('jurisdiction') != ex['scope_jurisdiction']:
        reasons.append('JURISDICTION_SCOPE_MISMATCH')
    if snap.get('customer_type') != ex['scope_customer_type']:
        reasons.append('CUSTOMER_TYPE_SCOPE_MISMATCH')
    if snap.get('amount') is None:
        reasons.append('AMOUNT_UNKNOWN_SCOPE_UNVERIFIABLE')
    elif snap['amount'] > ex['scope_amount_max']:
        reasons.append('AMOUNT_SCOPE_MISMATCH')
    if duty not in ex['waives_rules'].split('|'):
        reasons.append('RULE_NOT_WAIVED')
    # ---- evidence-time test: was approval demonstrably in existence at the trigger?
    if ex['signature_valid'] and pd.Timestamp(ex['certificate_created']) <= trigger_ts:
        evidence.append('QUALIFIED_SIGNATURE_EVIDENCE_TIME=%s' % ex['certificate_created'])
    elif ex['independent_witness'] and pd.Timestamp(ex['displayed_approval']) <= trigger_ts:
        evidence.append('INDEPENDENT_WITNESS_EVIDENCE_TIME=%s' % ex['displayed_approval'])
    else:
        reasons.append('NO_VERIFIABLE_EVIDENCE_OF_APPROVAL_AT_TRIGGER')
    if pd.Timestamp(ex['record_insert_ts']) > trigger_ts:
        evidence.append('RECORD_TIME_LATER_THAN_TRIGGER(record-artifact only)')
    return (len(reasons) == 0), reasons, ('; '.join(evidence) or None)


# ---------------------------------------------------------------------
# 6/7) Rule evaluation at each Release_Funds + case-level diagnostics
# ---------------------------------------------------------------------
def evaluate_case(cid, seq, reg_by_id):
    rel = [e for e in seq if e['activity'] == 'Release_Funds']
    if not rel:
        return None
    rel = rel[0]
    ridx, ts, snap = rel['idx'], rel['ts'], rel['snap']
    amt, risk = snap['amount'], snap['risk_level']
    jur, ctype = snap['jurisdiction'], snap['customer_type']
    er_i, sr_i, ca_i = rel['er_idx'], rel['sr_idx'], rel['ca_idx']
    sc_i, lu_i, mat_i = rel['screen_idx'], rel['list_idx'], rel['material_idx']

    # exemption referenced anywhere in the case (release messages may carry it)
    exid = next((e['exemption_id'] for e in seq if e['exemption_id']), None)
    ex = reg_by_id.get(exid)
    ex_valid, ex_reasons, ex_ev = validate_exemption(ex, ts, snap)

    # ---- R1
    if jur is None or amt is None:
        r1_trig, r1_status = 'UNKNOWN', 'INDETERMINATE'
    elif jur != 'DE' and amt >= HIGH_VALUE:
        r1_trig = 'YES'
        er_ok = er_i is not None and er_i < ridx and (mat_i is None or er_i > mat_i)
        if ex_valid:
            r1_status = 'WAIVED_BY_EXEMPTION'
        elif er_ok:
            r1_status = 'SATISFIED_BY_ENHANCED_REVIEW'
        else:
            r1_status = 'VIOLATION'
    else:
        r1_trig, r1_status = 'NO', 'NOT_APPLICABLE'

    # ---- R2
    if risk == 'HIGH' or ctype == 'PEP':
        r2_trig = 'YES'
        er_ok = er_i is not None and er_i < ridx
        ca_ok = ca_i is not None and er_i is not None and er_i < ca_i < ridx
        r2_status = 'SATISFIED' if (er_ok and ca_ok) else 'VIOLATION'
    elif risk is None or ctype is None:
        r2_trig, r2_status = 'UNKNOWN', 'INDETERMINATE'
    else:
        r2_trig, r2_status = 'NO', 'NOT_APPLICABLE'

    # ---- R3
    if jur is None:
        r3_trig, r3_status = 'UNKNOWN', 'INDETERMINATE'
    elif lu_i is not None and (sc_i is None or lu_i > sc_i):
        list_jur = next((c['new'] for c in seq[lu_i]['changes'] if c['attr'] == 'jurisdiction'), None)
        if list_jur == jur:
            r3_trig = 'YES'
            fresh = sc_i is not None and sc_i > lu_i and sc_i < ridx
            r3_status = 'SATISFIED' if fresh else 'VIOLATION'
        else:
            r3_trig, r3_status = 'NO', 'NOT_APPLICABLE'
    else:
        r3_trig, r3_status = 'NO', 'NOT_APPLICABLE'

    r4_er, r4_er_pct = r4_check(seq, er_i)
    r4_sr, r4_sr_pct = r4_check(seq, sr_i)

    unknown = [n for n, v in (('AMOUNT', amt), ('RISK', risk),
                              ('JURISDICTION', jur), ('CUSTOMER_TYPE', ctype)) if v is None]
    breaches, uncertainties = [], []
    if r1_status == 'VIOLATION':
        breaches.append('R1')
    if r2_status == 'VIOLATION':
        breaches.append('R2')
    if r3_status == 'VIOLATION':
        breaches.append('R3')
    if r4_er == 'INVALIDATED':
        breaches.append('R4_ER_INVALIDATED')
    for s, tag in ((r1_status, 'R1'), (r2_status, 'R2'), (r3_status, 'R3')):
        if s == 'INDETERMINATE':
            uncertainties.append('%s_TRIGGER_UNKNOWN' % tag)
    if unknown:
        uncertainties.append('UNKNOWN_AT_RELEASE:' + ','.join(unknown))
    if r4_er == 'UNKNOWN_BASE':
        uncertainties.append('R4_BASELINE_UNKNOWN')
    if exid and not ex_valid:
        uncertainties.append('EXEMPTION_CLAIM_REJECTED:' + ';'.join(ex_reasons))

    parts = []
    if breaches:
        parts.append('BREACH:' + ','.join(breaches))
    if uncertainties:
        parts.append('REVIEW_REQUIRED')
    label = ' + '.join(parts) if parts else 'PASS'

    def ts_of(i):
        return None if i is None else seq[i]['ts'].isoformat()

    return dict(case=cid,
                release_ts=ts.isoformat(),
                amount_at_release=amt, risk_at_release=risk,
                jurisdiction_at_release=jur, customer_type_at_release=ctype,
                unknown_flags='|'.join(unknown) or None,
                r1_trigger=r1_trig, r1_status=r1_status,
                r2_trigger=r2_trig, r2_status=r2_status,
                r3_trigger=r3_trig, r3_status=r3_status,
                last_enhanced_review_ts=ts_of(er_i),
                last_standard_review_ts=ts_of(sr_i),
                last_compliance_approve_ts=ts_of(ca_i),
                last_sanctions_screen_ts=ts_of(sc_i),
                last_sanctions_list_update_ts=ts_of(lu_i),
                last_material_change_ts=ts_of(mat_i),
                r4_enhanced_review=r4_er, r4_enhanced_review_max_increase=r4_er_pct,
                r4_standard_review=r4_sr, r4_standard_review_max_increase=r4_sr_pct,
                exemption_id=exid,
                exemption_valid_at_trigger=(None if ex is None else ex_valid),
                exemption_reasons=';'.join(ex_reasons) or None,
                exemption_evidence=ex_ev,
                auto_label=label,
                breaches=','.join(breaches) or None,
                uncertainties=';'.join(uncertainties) or None)

**Why this code cannot and should not produce the narrative verdicts directly.**
* It evaluates *rule obligations* (R1–R4) over reconstructed state, and joins the exemption register with an explicit **evidencetime** test (`certificate_created  trigger`), so TX302’s late insert is accepted on signature evidence while TX310’s backdated display is rejected.
* It **refuses to default** unknown values: `REVIEW_REQUIRED` is emitted for TX305 (amount  at release, R1 trigger unestablished, R4 baseline unknown) and for TX310 (contested exemption evidence), because those require human evidential judgement.
* The `cf_vs_data_divergent` column exposes the controlflow failure modes in this very log: CF sees a `Compliance_Approve` in TX307 and would “pass” it, whereas the dataaware check shows the approval covered only a *standard* packet (R2 breach); CF sees an `Enhanced_Review` in TX309 and would “pass” it, whereas the amountincrease invalidates it (R1 + R4); CF flags TX304 for the wrong reason (missing enhanced review) while the actual breach (R3, rescreening after the list update) is invisible to it; and CF flags TX302/TX305/TX308 for missing `Compliance_Approve` even though R2 never triggers there (conditional activation + false positives). A DECLARE/response check would additionally produce false positives (TX308 has a legitimate amount *decrease*; TX306 a legitimate *small* increase), because controlflow templates cannot express “only if amount  100 000 and the risk is HIGH”, nor “a review is invalidated by a data change”.
* The code deliberately does **not** implement “a release requires an enhanced review” as a fixed template; the obligation’s activation, its discharge and its invalidation all depend on attributes that are only knowable at the trigger’s event time.

## 6. Why ControlFlowOnly Conformance Is Insufficient

1. **Finalstate leakage.** A conformance model over the whole case (or over `case`level attribute columns, as in a denormalised extract) evaluates R1 with the *final* jurisdiction/amount/risk. TX311 is the clean illustration: at release the jurisdiction is DE (so R1 is not triggered), while at creation it was US — copying the final state backward to the review would misstate what was reviewed and, conversely, copying the *initial* state forward would manufacture a breach. The correct object is a state *per event*, folded forward only.
2. **Posthoc and backdated exemptions.** R5 is fundamentally an *evidencetime* test. TX302 (insert 11:00, signature 09:05) and TX310 (displayed 08:50, certificate created 10:30) are structurally identical rows: the release message already cites an exemption id that the database does not yet contain. A controlflow trace sees “Standard_Review  Release_Funds” plus an exemption tag and cannot distinguish a legitimate outagedelayed record from an unbacked claim; only a separate, materiality and timeaware exemption validation can.
3. **Material changes after review.** The obligation is not “an enhanced review occurred” but “an enhanced review occurred **after** the latest material change, and was not invalidated by a later change”. TX301 (+56.25 %, SR only), TX309 (+24.2 % then +22.9 %, ER invalidated) and, contrastingly, TX306 (+4.55 %, immaterial) and TX308 (decrease) are indistinguishable at the activitysequence level — the same trace shape, opposite outcomes. Sequence conformance has no vocabulary for value deltas.
4. **Conditional activation.** R1 fires only for nonDE and  100 k; R2 only for HIGH/PEP; R3 only after a list update naming the current jurisdiction. A `never(Release_Funds, Enhanced_Review)`style template would demand enhanced reviews for TX304 (60 k, never required) and TX307style DE retail transfers, and would not demand them where they matter; a `response` template would flag TX302/TX305/TX308 for a missing `Compliance_Approve` that policy never required. Both are false positives, and the second failure mode is silent.
5. **Missing / unknown data.** R6 forbids defaulting. TX305 has no amount at release, no amount in the review document and no amount in the release message; the only number (150 000) appears at settlement time, the next day. A controlflow model would simply see “enhanced review  release” and, if it also spurred a `Compliance_Approve` template, conclude compliance with a confidence it cannot justify. Unknown inputs must generate an explicit *indeterminate* state, which the formal model must be able to represent.
6. **Sametimestamp ordering.** TX311 places an `Enhanced_Review` and a jurisdiction change at the same timestamp; `event_index` 3 < 4 means the review did **not** see DE and therefore was performed against the stricter US/115 000 state. Controlflow tools that rely on the declared timestamp alone either order the pair arbitrarily or flag a tie. A tie is a *semantic* event (an update that lands microseconds after a control and thus escapes it), and it must be resolved by a stable, logged ordering key with a stated consequence.
7. **Scope of the approving artefact.** TX307’s `Compliance_Approve` explicitly "approved standard review packet". Activity presence is satisfied; the *substance* required by R2 (an enhanced review) is not. Conformance over activity names cannot distinguish a review of the right object at the right depth from a nominally identical event on a different packet.
8. **Currency of the sanction list.** R3 is about the *version* of the list (the screen must postdate the list update), not the presence of a screening. TX304 contains a `Sanctions_Screen` before the update — activity presence satisfied, the legal purpose defeated. A `response(Sanctions_Screen, Release_Funds)` template would pass TX304.
9. **Review/approval pairing and ordering.** R2 requires `Compliance_Approve` *after* the *relevant* `Enhanced_Review`. A “both present” check passes an approval that precedes the review; a “never” check on reversed pairs needs a comparability notion the trace does not carry.
10. **Sanctionlist and jurisdiction update attribution.** The `Sanctions_List_Update` row carries a jurisdiction attribute that is a *screen input*, not a case attribute change. Naive attribute folds that treat every nonblank cell as a case attribute update corrupt the state (they would mark TX304 as a material change and misdate the jurisdiction); event semantics must distinguish payload fields from state mutations — a distinction PM4Py’s CSV importer cannot make for you.

## 7. Recommended Logging and Control Improvements

**Event & ordering**
1. **Immutable release payload.** Every `Release_Funds` must carry a signed, hashsealed payload with the *authoritative* amount, currency, jurisdiction, customer type, risk level, and the exemption id relied upon — as actually released, not as later reconstructed. This alone would convert TX305 from INDETERMINATE to decidable.
2. **Stable, total ordering keys.** Persist `event_id` (UUID), `source_sequence` (monotonic per producer), `server_received_at` (record time) and a `effective_at` (business/effective time) distinct from `occurred_at` (event time). Require the producer to guarantee `source_sequence` uniqueness and emit it; use `(occurred_at, source_sequence)` as the canonical total order and document the tiebreak consequence in the rulebook (as §1 does here). Never rely on ingestion order.
3. **Attributechange provenance.** Record `previous_value`, `new_value`, `changed_by`, `change_reason`, `source_of_truth` and `authorised_at` for every update event; distinguish *state mutations* from *payload/reference fields* (e.g. `Sanctions_List_Update.jurisdiction` must be flagged `reference_only`) so replays cannot corrupt state.
4. **Missingvalue semantics.** Define two distinct tokens in the schema — `value_unchanged` and `value_unknown` — so “no update” is never conflated with “null”. Add a `data_quality` field and a feedhealth register so amounts that could not be retrieved are *known unknowns* with timestamps.

**Time & evidence**
5. **Four clocks on every row:** `occurred_at`, `effective_at`, `recorded_at`, `evidence_at` (when the supporting artefact came into existence). Reviews, approvals, screenings and exemption records must all carry an `evidence_at` derived from a verifiable artefact (certificate creation time, log entry, ledger commit).
6. **Signaturefirst exemption issuance.** Issue exemptions by signing first and recording second: the register should store the *signature timestamp* and the *certificate creation timestamp* separately, and the release message should be able to reference an exemption id that is already durable (or fail closed). Record the outage/retry mechanism in the issuance path so late reconciliation is expected and harmless.
7. **A nonrepudiable approval journal.** Witness attestations should be captured from the approver directly, with identity, independence flag, device/session id and a timestamp from an independent time source; disallow requestersourced attestations from satisfying R5.

**Rule & exemption semantics**
8. **Rule versioning.** Bind each review, approval and screening event to `rule_version` and a `policy_snapshot_id` (including thresholds), so “which duty applied at the time” is answerable; TX301style changes to the >20 % threshold would otherwise be unresolvable.
9. **Materialchange definition in the log.** Have the system compute and attach `pct_change_vs_last_review`, `material_change` (bool, with the configured threshold) and `last_review_id` to each update event; reviewers then apply R4 as recorded rather than rederiving it, and `$case_id`level review lineage (`reviewed_amount`, `reviewed_jurisdiction`, `reviewed_risk`) makes foreign highvalue and PEP reasoning auditable.
10. **Exemption scope and claims.** Model scope as (jurisdiction, customer_type, amount range, currency) with `applies_to_rule_ids`, `approved_by`, `approval_evidence_id`, `effective_from`, `expires_at`, `max_uses`, and `per_transaction` binding. A release referencing an exemption should store the exception id *and* the snapshot it relied on; the system must refuse to release when a cited exemption is not yet durable, rather than accepting an id that will appear later (as in TX302/TX310).
11. **Review–approval linkage.** Require `Compliance_Approve` to reference the exact `review_id` and `packet_type` it approved, and require `Enhanced_Review` artefacts to state the reviewed amount/jurisdiction, so R2 pairing and R4 invalidation can be checked mechanically rather than from freetext notes.
12. **Screening list versions.** Record `list_version` and `list_published_at` on every `Sanctions_Screen` and every `Sanctions_List_Update`; R3 then reduces to a version comparison, and TX304 would have been caught in the workflow (stale version flagged), not in the audit.
13. **Reconciliation and alerting.** Automate a “noreleasewithoutdischarge” prerelease check (with an explicit INDETERMINATE outcome that blocks or routes to a second line) and reconcile settlement records against release payloads; the TX305 gap shows that release/settlement amounts should be reconciled automatically rather than discovered a day later.
