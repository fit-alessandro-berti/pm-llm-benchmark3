## 6. Revised Normative Architecture

To resolve the conflict between rigid models and dynamic operations, a layered architecture is required.

1.  **Core Control Flow (POWL):** Represents the standard "Happy Path" and defined exceptions (Pilot, Emergency) as structural variants.
2.  **Data-Aware Eligibility Rules (Pandas/SQL):** Enforces risk levels, spend caps, dates, and supplier attributes. These rules gate the structural variants.
3.  **Resource & Conflict Rules (IAM/Graph):** Enforces SoD, CoI, and alias resolution. Independent of control flow.
4.  **Policy Overlay Governance:** A versioned table linking Case IDs to specific Policy Versions (CS-9, PD-3, FD-7). No case is judged without a linked policy version.
5.  **Scope Definitions:** Explicit inclusion/exclusion criteria for Reactivations, Rejections, and Pre-screens.

**Governance Mechanism:**
*   **Pilots/Emergencies:** Must be registered in the Policy Overlay with strict `start_time` and `end_time`. System automatically rejects eligibility after `end_time`.
*   **Model Updates:** `Request_More_Info` loops must be added to POWL only after Process Owner sign-off (N5).
*   **Data Integrity:** CRM links must be immutable UUIDs. Mutable text fields are flagged as `DATA_QUALITY_INDETERMINATE`.

    # in the standard route, but we will use Policy Overlay to enforce timing constraints 
    # (e.g. Quality before Activate vs after) that POWL cannot strictly enforce alone.
    checks_parallel = OperatorPOWL(operator=Operator.PARALLEL, children=[sanctions, quality])
    
    # --- Sub-Process: Approval Routes ---
    # Standard: Manual Approval -> Activate
    std_approval_seq = StrictPartialOrder(nodes=[manual_approval, activate])
    std_approval_seq.order.add_edge(manual_approval, activate)
    
    # Pilot/Emergency: Auto Approve -> Activate (or Provisional Activate)
    # We model Auto_Approve as an alternative to Manual_Approval
    auto_approval_seq = StrictPartialOrder(nodes=[auto_approval, activate])
    auto_approval_seq.order.add_edge(auto_approval, activate)
    
    # Combine Approval Routes (XOR)
    approval_routes = OperatorPOWL(operator=Operator.XOR, children=[std_approval_seq, auto_approval_seq])
    
    # --- Main Control Flow Construction ---
    # We build the main StrictPartialOrder M1
    M1 = StrictPartialOrder(nodes=[
        register, 
        loop_body, # The loop block occurs after register, before checks/decision
        checks_parallel, 
        approval_routes, 
        reject, 
        notify, 
        close
    ])
    
    # Edges
    # 1. Register -> Info Loop (Optional/Repeatable)
    # In POWL, optional loops are tricky. We approximate by allowing path to skip or enter.
    # For this model, we enforce Loop -> Checks sequence for simplicity of graph, 
    # acknowledging data rules enforce the 'optional' nature.
    M1.order.add_edge(register, loop_body)
    M1.order.add_edge(loop_body, checks_parallel)
    
    # 2. Checks -> Decision Point (Implicit in structure)
    # We connect checks to the approval routes and reject branch
    # Since approval_routes is an OperatorPOWL, we connect checks to it.
    M1.order.add_edge(checks_parallel, approval_routes)
    
    # 3. Reject Branch (XOR with Approval)
    # The approval_routes XOR already handles the split between Approval and Reject?
    # No, approval_routes was defined as [std_approval, auto_approval]. 
    # We need to include Reject in the main decision XOR.
    # Let's the decision logic to be clearer.
    
    # Re-defining Decision for clarity in M1 edges
    # Remove previous approval_routes addition to M1 nodes to avoid duplication confusion
    # Instead, we create a Decision Operator containing [Standard_Approval, Auto_Approval, Reject]
    
    # Clear M1 to rebuild cleanly
    M1 = StrictPartialOrder(nodes=[register, loop_body, sanctions, quality, manual_approval, auto_approval, activate, reject, notify, close])
    
    # Sequence: Register -> Loop
    M1.order.add_edge(register, loop_body)
    
    # Sequence: Loop -> Sanctions & Quality (Parallel)
    M1.order.add_edge(loop_body, sanctions)
    M1.order.add_edge(loop_body, quality)
    
    # Sequence: Sanctions & Quality -> Decision (Manual, Auto, Reject)
    # Since POWL StrictPartialOrder expects edges between nodes, and we need an XOR split.
    # We introduce an OperatorPOWL node for the Decision.
    decision_op = OperatorPOWL(operator=Operator.XOR, children=[manual_approval, auto_approval, reject])
    M1.nodes.add(decision_op)
    
    M1.order.add_edge(sanctions, decision_op)
    M1.order.add_edge(quality, decision_op)
    
    # Sequence: Approval -> Activate
    # The XOR children are manual_approval, auto_approval, reject.
    # We need Activate to follow manual_approval OR auto_approval.
    # POWL structure limitation: We model Activate as following the Decision Operator,
    # but logically it only follows approval branches. 
    # To be precise in POWL:
    # Branch 1: Manual -> Activate
    # Branch 2: Auto -> Activate
    # Branch 3: Reject -> (No Activate)
    
    # Simplified Defensible Approximation for POWL:
    # Decision XOR leads to Activate OR Close(Reject). 
    # But Reject leads to Notify->Close. Approval leads to Activate->Notify->Close.
    # We will model Activate as following the Decision, with the understanding that 
    # Data Rules prevent Activate if Reject was chosen.
    
    activate_node = Activate # Reuse transition
    M1.order.add_edge(decision_op, activate) # Approximation: Activate follows decision
    M1.order.add_edge(decision_op, notify) # Reject path goes to Notify
    
    # To strictly separate Reject vs Activate:
    # We need two XOR branches. 
    # Branch A: (Manual XOR Auto) -> Activate
    # Branch B: Reject
    # Then Merge -> Notify
    
    # Let's implement the Strict Separation for correctness.
    M1 = StrictPartialOrder(nodes=[register, loop_body, sanctions, quality, manual_approval, auto_approval, activate, reject, notify, close])
    
    # 1. Register -> Loop
    M1.order.add_edge(register, loop_body)
    # 2. Loop -> Checks (Parallel)
    M1.order.add_edge(loop_body, sanctions)
    M1.order.add_edge(loop_body, quality)
    
    # 3. Checks -> Decision XOR
    # Decision Children: [Approved_Path, Reject_Path]
    approved_path_seq = StrictPartialOrder(nodes=[manual_approval, auto_approval, activate])
    # XOR for approval type
    approval_type_xor = OperatorPOWL(operator=Operator.XOR, children=[manual_approval, auto_approval])
    # Connect Approval Type to Activate
    # In StrictPartialOrder, we add edges. 
    # We will treat approval_type_xor as a node that precedes Activate.
    M1.nodes.add(approval_type_xor)
    M1.order.add_edge(sanctions, approval_type_xor)
    M1.order.add_edge(quality, approval_type_xor)
    M1.order.add_edge(approval_type_xor, activate)
    
    # Reject Path
    M1.order.add_edge(sanctions, reject)
    M1.order.add_edge(quality, reject)
    # Constraint: Reject and Activate are mutually exclusive. 
    # POWL Partial Order doesn't enforce XOR easily without OperatorPOWL wrapper.
    # We wrap the [Activate, Reject] choice in an OperatorPOWL.
    
    final_decision = OperatorPOWL(operator=Operator.XOR, children=[activate, reject])
    M1.nodes.add(final_decision)
    
    # Connect Checks to Final Decision
    M1.order.add_edge(sanctions, final_decision)
    M1.order.add_edge(quality, final_decision)
    
    # 4. Post-Decision -> Notify -> Close
    M1.order.add_edge(final_decision, notify)
    M1.order.add_edge(notify, close)
    
    return M1
