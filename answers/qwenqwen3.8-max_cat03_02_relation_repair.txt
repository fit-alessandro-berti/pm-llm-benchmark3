## 1. Consistency rules and evidence model

I treat the observed OCEL fragment as partially correct but incomplete. The repair strategy is therefore abductive: propose relations that make the fragment more coherent, while retaining explicit uncertainty where the evidence is ambiguous.

### Hard invariants

| Rule | Classification | Use |
|---|---|---|
| Do not invent new events or objects. | Hard invariant | Repairs may only connect existing `ev*`, `ORD*`, `IT*`, `PK*`, `DEL*`, `INV*`, and `PAY*` records. |
| Referential integrity. | Hard invariant | Every proposed E2O relation must refer to an existing event and object; every O2O relation must refer to two existing objects. |
| O2O directionality matters. | Hard invariant | `DEL-X carries PK-7` is not equivalent to `PK-7 carries DEL-X`. Proposed O2O edges must use the semantically plausible direction. |
| Observed relations are not deleted merely because they are incomplete. | Hard invariant | The repair adds or withholds relations; it does not remove observed relations unless there is a direct contradiction, and none is decisive here. |

### Strong defaults

| Rule | Classification | Use |
|---|---|---|
| `Create Order` normally relates to exactly one Order. | Strong default | `ev01` and `ev02` already look complete. |
| `Add Item` normally relates to one Order and one Item. | Strong default | `ev03`–`ev05` already look complete. |
| `Pack Item` normally relates to one Item and one Package. | Strong default | `ev08` is suspicious because it has only `IT-B1`. The scanner reference `PK8-2` suggests `PK-8`, but a scanner outage remains possible. |
| `Dispatch Package` normally relates to one Package and one Delivery. | Strong default | `ev10` is suspicious because it has only `PK-8`. The carrier reference `N-421?` suggests `DEL-Y`, but the question mark lowers confidence. |
| `Confirm Delivery` may relate to one or more Deliveries, or only to an Order/Customer if carrier data is lost. | Strong default | `ev11` should not automatically be forced onto one Delivery. |
| `Issue Invoice` relates to one Invoice and one or more Orders. | Strong default | `ev12` may legitimately cover more than one Order, but the observed relation only contains `ORD-A`. |
| `Record Payment` relates to one Payment and normally one Invoice. | Strong default | `ev14` may be missing an Invoice, but unapplied cash is also possible. |

### Weak heuristics

| Evidence type | Classification | Use |
|---|---|---|
| Identifier similarity: `PK8-*`, `N-420`, `N-421`, `N-42*`, `B-771`, `B-772`. | Weak heuristic | Useful but not decisive. For example, `N-42*` can match both `N-420` and `N-421`. |
| Timestamp proximity and lifecycle order. | Weak heuristic | Packing precedes dispatch; dispatch precedes delivery confirmation; invoice precedes payment. The observed timestamps are broadly consistent. |
| Customer and route alignment. | Weak heuristic | `C17` and `NORTH` make several connections plausible, but they do not prove them. |
| Amount matching. | Weak heuristic | `130 + 100 = 230` is evidence for a consolidated invoice or related payments, but it is not proof. Fees, taxes, discounts, partial payments, or unapplied cash are possible. |
| Existing O2O structure. | Weak-to-strong evidence | Observed O2O edges such as `DEL-X carries PK-7` support corresponding event relations, but inferred O2O edges must not be treated as independent if they are derived from the same assumed E2O edge. |

### Evidence against a repair

The following count as evidence against a proposed repair:

- violating expected activity cardinality, such as assigning one `Create Order` event to two Orders;
- connecting objects with incompatible identifiers, such as linking `ev10` strongly to `DEL-X` despite `N-421?`;
- using amount equality as the only justification for invoice or payment relations;
- creating a complete lifecycle solely to remove orphans;
- treating an inferred O2O edge as independent confirmation of the E2O edge from which it was inferred.

### Evidence combination model

I use hard invariants as filters. A candidate that violates them is rejected. Strong lifecycle defaults generate plausible missing links. Weak heuristics then raise or lower confidence. Identifier similarity is most useful when it is local and specific, such as `scanner_ref=PK8-2` pointing to `PK-8`. It is less useful when it is partial, such as `N-42*`. Amount and customer evidence is only used as corroboration, never as sole proof. Existing O2O edges can corroborate E2O additions when they were observed independently, but O2O edges invented from an E2O assumption are marked as derivative and given lower confidence.

## 3. Alternative repair bundles

### Bundle A: conservative / minimum-change repair

Bundle A is the selected repair in the JSON section. It repairs only the physical-execution gaps where identifier evidence is relatively local, and it leaves billing and delivery-confirmation ambiguity visible.

**How Bundle A handles the required ambiguities:**

- **ev08 and PK-8:**  
  Bundle A adds `ev08 -> PK-8` as a provisional E2O relation because `scanner_ref=PK8-2` is close to `PK-8` and follows `ev07` with `scanner_ref=PK8-1`. It also adds `PK-8 packs IT-B1` as a lower-confidence O2O relation. However, both are provisional because the observed row lacks a Package and a scanner outage is possible.

- **ev10 and DEL-X/DEL-Y:**  
  Bundle A adds `ev10 -> DEL-Y` provisionally because `external_ref=N-421?` matches `DEL-Y.carrier_ref=N-421`. It also adds `DEL-Y carries PK-8` provisionally. It rejects `ev10 -> DEL-X` because the identifier evidence points away from `DEL-X`, and `DEL-X` is already dispatched in `ev09`.

- **ev11 and the delivery objects:**  
  Bundle A leaves `ev11` unresolved with respect to Deliveries. The event may refer to `DEL-X`, `DEL-Y`, both, or only to an Order because the portal lost the carrier identifier. The wildcard `N-42*` is not decisive.

- **INV-44 and ORD-B:**  
  Bundle A does not add `INV-44 bills ORD-B` or `ev12 -> ORD-B`. The amount pattern is suggestive but not strong enough for a conservative repair.

- **PAY-2 and INV-44:**  
  Bundle A does not add `ev14 -> INV-44` or `PAY-2 settles INV-44`. `PAY-2` remains an unapplied or unresolved payment.

**Lifecycle coherence under Bundle A:**  
Bundle A yields a coherent but incomplete physical lifecycle. `ORD-A` and `ORD-B` are created and receive items. `IT-A1` is packed in `PK-7`; `IT-A2` is packed in `PK-8`; `IT-B1` is probably packed in `PK-8`. `PK-7` is dispatched with `DEL-X`; `PK-8` is probably dispatched with `DEL-Y`. Delivery confirmation, consolidated invoicing, and second payment application remain open. This is intentionally less complete but more cautious.

### Bundle B: consolidated billing and bulk confirmation interpretation

Bundle B is a plausible alternative that accepts more repair risk in exchange for a more complete business lifecycle. It assumes that the customer’s two orders were handled together for invoicing and payment, and that the delivery confirmation may have been a bulk or customer-portal acknowledgment.

**How Bundle B handles the required ambiguities:**

- **ev08 and PK-8:**  
  Bundle B accepts the same provisional repair as Bundle A: `ev08 -> PK-8` and `PK-8 packs IT-B1`. This makes `PK-8` a mixed-order package, which is unusual but plausible in warehouse operations.

- **ev10 and DEL-X/DEL-Y:**  
  Bundle B also accepts `ev10 -> DEL-Y` and `DEL-Y carries PK-8`. It rejects `ev10 -> DEL-X` for the same identifier-mismatch reason.

- **ev11 and the delivery objects:**  
  Bundle B does not assign `ev11` uniquely to one Delivery. Instead, it adds both `ev11 -> DEL-X` and `ev11 -> DEL-Y` as provisional relations, interpreting `external_ref=N-42*` as a bulk or partially masked carrier reference. This is still uncertain, but it avoids privileging one matching prefix when both are compatible.

- **INV-44 and ORD-B:**  
  Bundle B adds `INV-44 bills ORD-B` and `ev12 -> ORD-B`. The rationale is that the invoice total 230 aligns with the combined declared values of `ORD-A` and `ORD-B`, and the same customer is involved. This is treated as plausible, not proven.

- **PAY-2 and INV-44:**  
  Bundle B adds `ev14 -> INV-44` and `PAY-2 settles INV-44`. The two payments together match the invoice total, but this is again only amount evidence and should remain provisional.

**Lifecycle coherence under Bundle B:**  
Bundle B produces a much more complete lifecycle. Both Orders are created, items are added, packed, dispatched, and probably delivered. The Invoice covers both Orders, and both Payments settle it. The risk is that Bundle B may convert a data-quality problem into an apparently clean end-to-end process. If the invoice actually covered only `ORD-A` with extra charges, or if `PAY-2` is unapplied cash, Bundle B will hide that anomaly.

## 5. Lifecycle and cardinality audit

This audit assumes the selected conservative repair, Bundle A.

### Order objects

The selected repair preserves plausible Order lifecycles for both `ORD-A` and `ORD-B`, although they remain incomplete.

- `ORD-A` is created in `ev01`, receives `IT-A1` and `IT-A2`, is referenced in `ev11`, is billed by `INV-44` in `ev12`, and is indirectly connected to packing and dispatch through its items.
- `ORD-B` is created in `ev02`, receives `IT-B1`, and is indirectly connected to packing and dispatch if the provisional `PK-8` repair is accepted. It remains uninvoiced and unpaid in Bundle A.

There is no suspicious one-to-many relation at the Order level. Each `Create Order` event relates to one Order, and each `Add Item` event relates to one Order and one Item. The main uncertainty is whether `ORD-B` should later be linked to `INV-44`.

### Item objects

The Item lifecycles are mostly coherent.

- `IT-A1` is contained by `ORD-A`, packed in `PK-7`, and dispatched through `DEL-X`.
- `IT-A2` is contained by `ORD-A`, packed in `PK-8`, and dispatched through `DEL-Y` if the provisional dispatch repair is accepted.
- `IT-B1` is contained by `ORD-B` and provisionally packed in `PK-8`.

The suspicious point is that `PK-8` would contain items from two different Orders: `IT-A2` from `ORD-A` and `IT-B1` from `ORD-B`. This is not impossible, but it is a operational anomaly worth flagging. The repair does not resolve whether this reflects real mixed packing, repacking, or a scanner error.

### Package objects

`PK-7` has a clean lifecycle: it packs `IT-A1`, is dispatched in `ev09`, and is carried by `DEL-X`. Its only missing part is delivery confirmation, which Bundle A leaves unresolved.

`PK-8` becomes more complex under Bundle A. It already packs `IT-A2`, is dispatched in `ev10`, and provisionally packs `IT-B1` and is carried by `DEL-Y`. This creates a plausible but uncertain package lifecycle. The relation is supported by event identifier similarity, but the O2O edge is derivative from the E2O addition and should not be treated as independent confirmation.

### Delivery objects

`DEL-X` is observed in `ev09` and carries `PK-7`. Bundle A does not link it to `ev11`, so its confirmation remains unresolved. This is acceptable because `Confirm Delivery` may refer only to an Order or customer portal context.

`DEL-Y` is introduced into the dispatch lifecycle by `ev10 -> DEL-Y` and `DEL-Y carries PK-8`. It remains unconfirmed. This orphan-like confirmation gap is preserved deliberately.

### Invoice objects

`INV-44` is issued in `ev12` and observed to bill `ORD-A`. It is settled by `PAY-1` in `ev13`. Bundle A leaves the invoice total of 230 unresolved with respect to `ORD-B`. This creates a suspicious but not impossible situation: the invoice may include fees, taxes, discounts, or another order, but the data does not determine which.

### Payment objects

`PAY-1` has a coherent lifecycle: it is recorded in `ev13` and settles `INV-44`. `PAY-2` remains orphan-like with respect to Invoice. Bundle A treats this as unresolved rather than forcing `PAY-2` onto `INV-44`. This preserves the possibility of unapplied cash, a missing invoice, or a payment directed to another object not present in the extract.

### Independent support and circularity

Some relations are independently supported by E2O and O2O evidence. For example, `ev09 -> DEL-X` and `DEL-X carries PK-7` support each other, and both were observed. Similarly, `ev13 -> INV-44` and `PAY-1 settles INV-44` are mutually consistent.

However, the selected repair contains derivative inference:

- `PK-8 packs IT-B1` is largely inferred from `ev08 -> PK-8`.
- `DEL-Y carries PK-8` is largely inferred from `ev10 -> DEL-Y`.

Therefore, these O2O edges must not be treated as independent confirmation of the corresponding E2O edges. Doing so would be circular: first assume the event relation, then infer the object relation, then claim the object relation proves the event relation. Bundle A therefore assigns lower confidence to the O2O additions than to the direct identifier-based E2O candidates.

## 6. Downstream process-mining effects

### Unrepaired log

In the unrepaired log, several object lifecycles stop abruptly:

- `IT-B1` stops after `Pack Item` because `ev08` has no Package.
- `PK-8` has `Pack Item` and `Dispatch Package`, but no Delivery.
- `DEL-Y` has no events.
- `PAY-2` has no Invoice.
- `ev11` is an Order-centric confirmation with no Delivery.

This preserves anomalies but weakens object-centric discovery.

### Effect on the OC-DFG

Under the unrepaired log, the object-centric DFG may show:

- For `PK-8`: `Pack Item` to `Dispatch Package`, because `ev07` and `ev10` both reference `PK-8`.
- For `IT-B1`: `Add Item` to `Pack Item`, but no continuation to dispatch.
- For `DEL-Y`: no lifecycle.

Under Bundle A:

- `PK-8` gains `ev08` as an additional `Pack Item` event. This may introduce `Pack Item -> Pack Item` behavior for `PK-8`, or at least multiple incoming packing edges, depending on the OC-DFG implementation.
- `IT-B1` may now continue indirectly to `Dispatch Package` if the discovery or flattening propagates through O2O relations.
- `DEL-Y` gains a `Dispatch Package` event.
- No `Confirm Delivery` edge is added to Deliveries, so the confirmation gap remains visible.

Under Bundle B:

- `DEL-X` and `DEL-Y` may both receive `Confirm Delivery` edges.
- `INV-44` becomes connected to both Orders.
- `PAY-2` becomes connected to `INV-44`, creating a second `Record Payment` relation for the same Invoice.
- The OC-DFG will look more complete but may overstate process integration.

### Effect on the OTG

The OTG describes object-type relationships.

Unrepaired OTG contains observed object-type links such as:

- `Order` to `Item`;
- `Package` to `Item`;
- `Delivery` to `Package`;
- `Invoice` to `Order`;
- `Payment` to `Invoice`.

Bundle A adds or strengthens:

- `Package` to `Item` through `PK-8 packs IT-B1`;
- `Delivery` to `Package` through `DEL-Y carries PK-8`.

Bundle B additionally adds:

- `Invoice` to `Order` through `INV-44 bills ORD-B`;
- `Payment` to `Invoice` through `PAY-2 settles INV-44`.

These additions change the apparent object-type topology, especially by making `Invoice` and `Payment` part of a two-order, two-payment structure.

### Effect on the ET–OT graph

The ET–OT graph connects event types to object types.

Unrepaired:

- `Pack Item` is linked to `Item` and, through observed rows, to `Package` for `ev06` and `ev07` only.
- `Dispatch Package` is linked to `Delivery` only through `ev09`.
- `Confirm Delivery` is linked to `Order`, not `Delivery`.
- `Record Payment` is linked to `Invoice` only for `ev13`, not `ev14`.

Bundle A:

- `Pack Item -> Package` becomes stronger because `ev08` now references `PK-8`.
- `Dispatch Package -> Delivery` becomes stronger because `ev10` references `DEL-Y`.
- `Confirm Delivery -> Delivery` still does not appear.
- `Record Payment -> Invoice` still does not appear for `ev14`.

Bundle B:

- `Confirm Delivery -> Delivery` appears or strengthens.
- `Issue Invoice -> Order` gains additional support for `ORD-B`.
- `Record Payment -> Invoice` becomes supported by both `ev13` and `ev14`.

### Effect on flattenings

Flattening behavior can depend on whether the flattening implementation propagates through O2O relations. With that caveat:

- **Order flattening:**  
  Unrepaired, `ORD-B` may stop after item addition. Bundle A may connect `ORD-B` indirectly to packing and dispatch if O2O propagation is used, but not to invoice or payment. Bundle B may make both Orders appear to share an invoice and payment lifecycle.

- **Package flattening:**  
  Bundle A adds another packing event to `PK-8` and connects `PK-8` to `DEL-Y`. This can create a more complete Package case but may also introduce apparent rework or multiple packing steps.

- **Delivery flattening:**  
  Unrepaired, `DEL-Y` has no events. Bundle A gives `DEL-Y` a dispatch event. Bundle B gives both Deliveries confirmation events.

- **Invoice flattening:**  
  Bundle A leaves `INV-44` linked to `ORD-A`, `ev12`, and `PAY-1`. Bundle B makes `INV-44` a consolidated invoice with two Orders and two Payments.

- **Payment flattening:**  
  Bundle A leaves `PAY-2` as an isolated payment case. Bundle B connects `PAY-2` to `INV-44`, removing the orphan but possibly hiding unapplied cash.

### Activity frequencies

Event-based activity frequencies do not change because no events are added. However, object-centric frequencies can change:

- `Pack Item` becomes associated with more Package objects under Bundle A.
- `Dispatch Package` becomes associated with more Delivery objects under Bundle A.
- `Confirm Delivery` becomes associated with Delivery objects only under Bundle B.
- `Issue Invoice` becomes associated with two Orders under Bundle B.
- `Record Payment` becomes associated with Invoice in both payment events under Bundle B.

Thus, unique-object counts and total object-event relations change even though the event log’s raw activity counts do not.

### Equivalent-execution clustering around Order

In the unrepaired log, `ORD-A` and `ORD-B` are unlikely to cluster together: `ORD-A` has confirmation, invoice, and payment traces, while `ORD-B` stops early.

Under Bundle A, they remain distinct because `ORD-B` is still not invoiced or paid.

Under Bundle B, the two Orders become much more similar: both are created, packed, dispatched, confirmed, invoiced, and paid. This may produce a stronger equivalent-execution cluster around customer `C17`. That may be correct, but it may also be an artifact of over-repair.

## 8. Over-repair warnings

An aggressive repair could create false process behavior in at least the following ways.

1. **Forcing `ev11` onto `DEL-X` only.**  
   The wildcard `N-42*` matches both `N-420` and `N-421`. Assigning the confirmation uniquely to `DEL-X` would create a false confirmed delivery, hide portal ambiguity, and make `DEL-X` look complete while `DEL-Y` remains artificially orphaned.

2. **Forcing `ev11` onto `DEL-Y` only.**  
   This is equally risky. `ev11` observes `ORD-A`, not `ORD-B`, and `DEL-Y` is only connected through provisional repairs. A unique assignment would overstate confidence in the dispatch interpretation.

3. **Adding `INV-44 bills ORD-B` solely because amounts sum to 230.**  
   Arithmetic alignment is evidence, not proof. The invoice could include fees, taxes, discounts, or another missing order. If the relation is added too aggressively, Order and Invoice flattenings will falsely show consolidated billing.

4. **Adding `PAY-2 settles INV-44` solely because payments sum to the invoice total.**  
   This can hide unapplied cash or a missing invoice. It would also make payment reconciliation appear healthier than the source data supports.

5. **Assuming `ev08` must belong to `PK-8` without allowing scanner outage.**  
   The scanner reference is suggestive, but the observed row is item-only. If the pack event was an exception, adding `PK-8` creates a false cross-order package and distorts package throughput, packing rework, and dispatch analysis.

6. **Completing every lifecycle just to remove orphans.**  
   Orphan objects such as `PAY-2` or `DEL-Y` may be meaningful signals of missing data, exceptional process behavior, or unresolved reconciliation. Repairing them away can turn a data-quality problem into a misleadingly clean process model.
