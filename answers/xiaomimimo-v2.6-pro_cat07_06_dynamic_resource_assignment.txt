# 1. Objectives and constraints

## 1.1 What the policy is trying to achieve

The policy is a **multiobjective, constrained decision rule**, not a singlenumber optimiser. Six objectives are pursued simultaneously and are deliberately allowed to conflict, so that every assignment can be explained as an explicit tradeoff.

| # | Objective | Operational definition (what we measure) | Why it matters |
|---|---|---|---|
| O1 | **Shortterm throughput** | Cases started/completed per shift; total added waiting + service time for the batch | Revenue and queue burndown |
| O2 | **Skill development** | Share of assignments that advance a *documented* training priority; skills upgraded per quarter | Future capacity and bench strength |
| O3 | **Workload fairness** | Open cases + new assignments per person; Gini of load; overtime exposure | Wellbeing, absence risk, perceived justice |
| O4 | **Continuity of case ownership** | Share of cases keeping `current_owner`; mean `reassignment_count` | Historical evidence: >2 reassignments  1.8× rework, 1.4× appeals |
| O5 | **SLA risk control** | Predicted slack per case at assignment time; SLA miss rate | Customer commitments, penalties |
| O6 | **Resilience** | "Bus factor" per activity; reserved capacity in thin skills; graceful degradation if one person is absent | A service that only runs when two specific people are in the building is not a service |

## 1.2 Hard constraints — safety and compliance (never traded away)

These are **filters**, applied before any scoring. A candidate resource that violates one is simply not on the list. There is no weighting that can buy an exception.

| ID | Hard constraint | Type |
|---|---|---|
| **H1** | Skill score for the required skill must be  1 (0 = not allowed  structurally ineligible) | Competence / safety |
| **H2** | Highpriority cases (priority  {high, urgent}) must go to skill  2, **or** to skill 1 under a *named* supervisor | Quality / customer risk |
| **H3** | **Security Review** is performed by skill 3, or by skill 1–2 under explicit supervision by R7_Gita or R8_Hugo. Skill 0 may observe/assist only and must not perform or sign | Compliance (Risk) |
| **H4** | **Final Approval** is finalised by skill 2–3. Skill 1 may *prepare* only and must not finalise. Skill 0 may not touch it | Compliance (segregation of duties) |
| **H5** | Continuity is mandatorypreferred for high complexity (`case_complexity  0.70`) **and** `handover_cost_band = high`, unless the owner has skill 0–1 **and** no supervision is feasible | Historical evidence (+2.7 h waiting per handover) |
| **H6** | No resource may receive more than **4** assignments in one decision batch | Fairness / singleabsence blast radius |
| **H7** | No new work to a resource with `overtime_risk = high`, unless the case is urgent **and** no compliant alternative exists (written justification required) | Wellbeing / duty of care |
| **H8** | Quality Check may be batched only if priority  {normal, low} **and** `sla_deadline  now > 24 h` | Batching safety |
| **H9** | Estimated completion must be earlier than `sla_deadline` minus a safety margin (margin = 15 % of SLA, min 30 min) | Feasibility filter |
| **H10** | **Reassignment guard:** if `reassignment_count  2` **and** `handover_cost_band  {medium, high}` **and** SLA slack > 8 h, the owner is not changed | Keeps cases out of the 1.8× rework band |

## 1.3 Soft constraints — preference tradeoffs (weighted, and deliberately in tension)

| ID | Preference | Tension with |
|---|---|---|
| S1 | Best skill match (specialist > competent > trainee) | S3 fairness, S4 continuity, O6 resilience (specialist monopoly) |
| S2 | SLA slack maximisation | S1 (specialists are busy), S5 development (trainees are slow) |
| S3 | Load equalisation and overtime protection | S1, S2 |
| S4 | Case ownership continuity | S1 (fresh eyes), S3 (relieving overloaded owners) |
| S5 | Training that matches a **documented** training priority | S2 (trainees cost ~3.3 h extra service time), H7 |
| S6 | Resilience: keep  25 % reserve capacity in thin skills (Security, Approval) | S1, O1 |
| S7 | Batching / setup economy (Quality) | S4 continuity |

**Explicit statement of nonuniqueness.** There is no single optimum. Three different defensible answers exist for C001 alone (specialistowned, ownercontinued with specialist cosign, or full handover), and each is preferred under a different weighting of O1–O6. The policy below therefore (a) fixes the hard rules first, (b) makes the soft weights explicit and adjustable, and (c) records, per assignment, which objective was traded away.

---

# 2. Assignment policy

## 2.1 Design principle: *rules first, scores second, plain language always*

Workers must be able to answer "why me?" in one sentence. A purely numeric optimiser cannot do that. The policy is therefore **lexicographic** (a hardrule gate) followed by a **transparent additive scorecard** with fixed, published weights. Every result carries a machinereadable `assignment_reason` code *and* a human sentence.

## 2.2 Pseudocode

```text

DYNAMIC, EXPLAINABLE RESOURCE ASSIGNMENT (DERA) — batch version

INPUT : queue Q = {(case c, next activity a_c, required_skill s_c,
                    priority p_c, sla_remaining t_c, complexity x_c,
                    owner o_c, reassign_n n_c, handover_band h_c)}
        resource table R = {skill[r,·], open_cases[r], hours_left[r],
                            overtime_risk[r], training_priority[r], team[r]}
OUTPUT: assignment list, each with (resource | supervised pair),
        reason code, reason sentence, trade-off note, risk flag

CONSTANTS (published to staff):
  W = {SLA:0.30, SKILL:0.20, CONT:0.20, FAIR:0.5*0.30=0.15,
       DEV:0.10, RESIL:0.05}          # sums to 1.00
  DEV_WEIGHT_RELAXED = 0.20            # used when there is SLA slack
  SUPERVISOR_POOL(s) = {R7_Gita,R8_Hugo} for s = security
                       {skill[r,s]  2 and skill[r,s] > skill[worker,s]} otherwise
  BOTTLENECK_SKILLS  = {security, approval}      # from §6 role/bottleneck audit
  RESERVE_FRACTION   = 0.25                      # of hours_left for those skills


STEP 0 — CASE ORDERING (what we decide first)

for each c in Q:
    urgency(c) = 0.5 * {urgent:1.0, high:0.75, normal:0.40, low:0.15}[p_c]
               + 0.5 * (1 - min(1, t_c / 48h))
sort Q by urgency DESC, then t_c ASC          # "tightest clock first"


STEP 1 — HARD ELIGIBILITY FILTER (H1–H5, H8)

for each c, for each r in R:
    E(r,c) = TRUE
    if skill[r, s_c] == 0:                    E = FALSE  # H1 not allowed
    if p_c in {high, urgent} and skill[r,s_c] < 2:
        if no named supervisor available:     E = FALSE  # H2
        else: mark pair(r, supervisor)
    if s_c == security:                                            # H3
        if skill[r,security] == 3: ok (r may perform and sign)
        elif skill[r,security] in {1,2} and supervised_by  {R7,R8}:
             ok (r performs under explicit supervision)
        elif skill[r,security] == 0: r may OBSERVE/ASSIST ONLY
             -> activity performed & signed by a skill-3 resource
        else: E = FALSE
    if a_c == "Final Approval":                                       # H4
        if skill[r,approval] >= 2: r may FINALISE
        elif skill[r,approval] == 1: r may PREPARE only (never finalise)
        else: E = FALSE
    if x_c >= 0.70 and h_c == "high":                                 # H5
        if r != o_c and skill[o_c,s_c] >= 2:                 E = FALSE  # keep owner
        if r != o_c and skill[o_c,s_c] <= 1 and supervisor exists:
                                                     E = FALSE  # keep owner + supervise
    if a_c == "Quality Check" and batched(c) and
       not (p_c in {normal,low} and t_c > 24h):              E = FALSE  # H8

    # H10 reassignment guard (soft-hard hybrid)
    if n_c >= 2 and h_c in {medium,high} and t_c > 8h and r != o_c:
        E = FALSE   unless override code REASSIGN_LOOPBREAK recorded


STEP 2 — SLA URGENCY / FEASIBILITY SCORING   (0-100)

handover_penalty(c,r) = {none:0, low:0.5h, medium:1.0h, high:2.7h}[h_c or "none"]
                        + 0.5h if x_c >= 0.70 and r != o_c
effort(r,c)   = base_touch[a_c] * (1.5 if skill[r,s_c] == 1 else 1.0)
                + 0.25h if supervised/supervising
slack(c,r)    = t_c - effort(r,c) - handover_penalty(c,r) - safety_margin(c)

SLA_fit =  100  if slack >= 4h
           80   if 2h <= slack < 4h
           50   if 0.5h <= slack < 2h
           25   if 0 <= slack < 0.5h
        HARD FAIL (H9) if slack < 0


STEP 3 — SKILL-MATCH SCORING                    (0-100)

SKILL_fit = {3:100, 2:70, 1:35}[skill[r,s_c]]           # 0 already excluded
SKILL_fit += 10 if supervised pair is used and skill[supervisor,s_c] == 3
complexity gate: if x_c >= 0.70 and skill[r,s_c] == 1 -> SKILL_fit = 0 (blocked)
                 unless a skill-3 co-performer is named (then score = 100 for the pair)


STEP 4 — CONTINUITY / HANDOVER-COST SCORING     (0-100)

CONT_fit = 100 if r == o_c else 0
CONT_fit -= 15 * n_c                      # troubled-case drift penalty (owner route)
CONT_fit -= {none:0, low:10, medium:35, high:70}[h_c]   # handover route
CONT_fit -= 25 if x_c >= 0.70 and r != o_c
CONT_fit = max(0, CONT_fit)


STEP 5 — WORKLOAD / OVERTIME FAIRNESS SCORING   (0-100)

load(r)      = (open_cases[r] + already_assigned_in_batch[r]) / max_r(open_cases)
headroom(r)  = 1 - min(1, committed_hours[r] / hours_left[r])
ot_penalty   = {low:0, medium:15, high:40}[overtime_risk[r]]
FAIR_fit     = 60*(1 - load(r)) + 40*headroom(r) - ot_penalty
H6 gate      : already_assigned_in_batch[r] >= 4  -> HARD FAIL
H7 gate      : overtime_risk[r] == high and p_c != urgent -> HARD FAIL
               overtime_risk[r] == urgent and alternatives exist -> HARD FAIL
               (exception only with written code OT_OVERRIDE)


STEP 6 — TRAINING / DEVELOPMENT SCORING         (0-100)

DEV_fit = 0
if p_c in {normal, low} and slack(c,r) >= 4h:
    if s_c == training_priority[r]:
        if skill[r,s_c] == 1 and supervisor named : DEV_fit = 100   # "gold" training
        if skill[r,s_c] == 0 and shadow role only  : DEV_fit = 60   # exposure only
    elif skill[r,s_c] == 1 and supervisor named    : DEV_fit = 40   # generalist breadth
DEV_fit is scaled by (1 - urgency(c))  # when the clock is tight we do not train
Quota (rule 3): at the end of the batch,
    training_share = #normal/low assignments with DEV_fit>0 AND documented priority
                     / #normal/low assignments
    if training_share < 0.20 and SLA_risk_ok: re-run the batch with
        DEV weight raised 0.10 -> 0.20 for the lowest-urgency normal/low cases.


STEP 7 — RESILIENCE / BOTTLENECK AVOIDANCE      (0-100)

RESIL_fit = 50
if skill in BOTTLENECK_SKILLS and skill[r,s] == 3:
    reserve_after = hours_left[r] - committed_hours[r] - effort(r,c)
    if reserve_after < RESERVE_FRACTION * hours_left[r]: RESIL_fit -= 40
    if this case is urgent and r is the only uncommitted thin-skill resource: +20
if this assignment reduces concentration (e.g. moves work off a >10-case owner):
    RESIL_fit += 25
if this assignment creates cross-training into a skill with bus factor  2: +25
if already_assigned_in_batch[r] == 3: RESIL_fit -= 15   # avoid the cap cliff


STEP 8 — TOTAL, TIE-BREAK, EXCEPTIONS

w = W, but if urgency(c) < 0.5: w.DEV = 0.20, w.CONT = 0.15, w.FAIR = 0.10
    if urgency(c) > 0.8:      w.SLA = 0.40, w.DEV = 0.05, w.CONT = 0.15
score(r,c) =  w[k] * k_fit(r,c)          # all k_fit normalised to 0-100

choose r* = argmax score(r,c) over eligible r
TIE-BREAK (fixed, published order):
    1. larger skill margin above the minimum required
    2. r == current_owner
    3. lower (open_cases + assigned_in_batch)
    4. larger hours_left
    5. lower overtime_risk  (low < medium < high)
    6. named supervisor already on the case (cheaper coordination)
    7. lowest resource id  (determinism only)

EXCEPTION / OVERRIDE PROTOCOL
  if no eligible r:
      relax in this fixed order, one step at a time:
          (a) drop DEV requirement   (b) drop FAIR balance (allow H7 override)
          (c) drop CONTINUITY          NEVER relax H1-H4, H6, H9
      record override code, approver, compensating control (e.g. 100 % review)
  if H10 blocks all sensible options and urgency(c) > 0.8:
      allow REASSIGN_LOOPBREAK with a mandatory structured handover document
  emit for every case:
      (resource | supervised pair, reason_code, reason_sentence,
       trade_off_note, training_flag, risk_to_monitor)
      -> written into the event-log columns org:resource, assignment_reason,
         reassignment_count, workload_snapshot, handover_cost_band
```

## 2.3 Why these weights

* **SLA 0.30** — the deadline is the only objective with an external, contractual consequence; it must dominate but not monopolise.
* **Skill 0.20 + Continuity 0.20** — deliberately equal. The historical evidence cuts both ways (+2.7 h per highcomplexity handover vs +3.3 h per weakskill retention), so neither may systematically win.
* **Fairness 0.15** — high enough that "the same three people always get the work" cannot emerge, low enough that it cannot push a case past its deadline.
* **Development 0.10 (0.20 when there is slack)** — this is the "dynamic" element in plain language: *when the clock allows, we invest in people; when it does not, we protect the deadline.* It is visible and staff can see it operating.
* **Resilience 0.05** — small per case, but it acts through the **reserve rule** and the **busfactor bonus**, which are multiplicative in effect.
