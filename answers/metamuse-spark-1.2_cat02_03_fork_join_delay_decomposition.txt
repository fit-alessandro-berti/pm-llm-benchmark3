# 1. Delay-decomposition definitions

For case $c\in\{F01..F12\}$ and branch $i\in\{A,B,C\}$ let:

* `arrival[c]`, `fork_release[c]` logged times
* `i_start[c]`, `i_end[c]` logged branch complete events
* `final_start[c]`, `final_end[c]` logged

Define per case:

```
upstream_elapsed[c] = fork_release[c] - arrival[c]

i_queue[c]        = i_start[c] - fork_release[c]    >=0 by assumption
i_service[c]      = i_end[c] - i_start[c]
i_completion[c]   = i_queue[c] + i_service[c] = i_end[c] - fork_release[c]

join_ready[c]     = max_{i in {A,B,C}} i_end[c]       // not logged, implied by AND-join
critical_branch[c]= argmax_i i_end[c]                 // tie -> set of branches
critical_completion[c] = join_ready[c] - fork_release[c] = max_i i_completion[c]

i_sync_wait[c]    = join_ready[c] - i_end[c]          // 0 for critical branch(es)
fork_join_elapsed[c] = join_ready[c] - fork_release[c]

downstream_queue[c] = final_start[c] - join_ready[c]  // downstream queueing IF model holds
final_service[c]    = final_end[c] - final_start[c]
total_flow_time[c]  = final_end[c] - arrival[c]
```

**No-double-counting identity:**

```
total_flow_time[c] = upstream_elapsed[c] + fork_join_elapsed[c] + downstream_queue[c] + final_service[c]
```

and

```
fork_join_elapsed[c] = i_completion[c] + i_sync_wait[c]   for any i
                     = max_i i_completion[c]
```

If we summed synchronization waits across branches we would count the same elapsed
interval multiple times:

```
_i i_sync_wait[c] = _i (join_ready - i_end) = 3*join_ready - _i i_end
```

Elapsed fork-join time is **not** `_i i_sync_wait` nor `_i i_completion`. Only one branch is critical at a time.
The non-critical branches wait *in parallel* during the interval
`[i_end , join_ready]`; overlapping waits do not add sequentially.
The correct aggregation is `max`, not `sum`. Summing all `i_sync_wait` would count the period from the first finishing branch to `join_ready` up to 3 times and would exceed elapsed time. Example F01: `A_sync=0, B_sync=5, C_sync=22` sum=27 but `fork_join_elapsed=50`; `C_sync=22` overlaps entirely with `A` still running. Only `max completion = 50` is elapsed.

**Assumptions needed** (labelled):

* **A1 - Fork permissive:** `fork_release` is earliest start allowed; `i_queue >=0`.
* **A2 - AND-join:** `join_ready = max i_end`. No early release.
* **A3 - Final queue attribution:** `final_start - join_ready` is interpreted as downstream queue. If final station has a release policy or calendar not captured, this over-attributes.
* **A4 - Clock accuracy:** 1-minute resolution; ties within 1 min treated as simultaneous.

**Influence ranking - reasoned:**

2. **A - secondary / conditional.** Largest service but *zero queue* and zero variance, so its influence is capped. It sets a floor of 50 min fork-join time. It is never more than 25 min ahead of B, and B overtakes it in 8 cases. Reducing A alone rarely helps (see counterfactual).

3. **C - least influential on average but explains two outliers.** Mean completion lowest (30.6), mean sync longest (30.4) meaning it usually waits. However queue spikes (35 in F04, 25 in F08) plus a 30-min service outlier in F08 make it critical in 16.7% of cases. Without queue variability C would never be critical.

**Do not equate service with influence:** A service 50 > B 37.5 but B queue+service 56.7 > A. Frequency and tail contribution, not mean service, determine flow. C illustrates opposite: small service but large queue can sporadically dominate.

Tie handling: No exact minute ties in original data. Deterministic rule used: `argmax` returns first max in order A,B,C if equal; reporting as set `{A,B}`. In counterfactuals F06 and F02 become ties (A=B) and noted.

# 4. Counterfactual redesign analysis

Three counterfactuals evaluated under **A5**: `downstream_queue` preserved (final_start shifts with join_ready) unless resource contention explicitly modelled; this isolates branch effects. For exact numbers see Python section. Table shows per-case join change and total flow saving.

### CF1: Reduce A service by 20% (50  40 min, -10 min)

*Method:* `A_end' = A_start+40`, `join' = max(A_end',B_end,C_end)`, saving = `join-join'`.

| case | old join | new join | saving | benefit? |
|---|---|---|---|---|
| F01 |09:00|08:55|5|yes, B becomes critical |
| F02-10 |09:25-11:20|unchanged|0|no - B or C remains critical |
| F11 |11:30|11:20|10|yes, now tie A=B |
| F12 |12:10|unchanged|0|no |
| **Aggregate** | | **mean saving 1.25 min**, max 10, 10/12 zero benefit |

**Direct benefits:** Only when A is critical (F01,F11). Else zero because `B_completion` (or `C_completion`) already exceeds `A_completion-10`. Example F06: even with 10 min faster A, `B_completion=65 >40` so no gain.

**Zero-benefit cases:** 83% of cases masked by B/C dominance.

**Secondary effects:** Lower A service frees lab capacity (not measured) but does not reduce synchronization waits for A much (A sync already low). Could reduce upstream queue if A resource shared, not observable. Risk: investing in assay acceleration yields <2% flow reduction overall despite 20% service cut. Downstream queue unchanged, so tail (130) still 130 unless B improved.

**Direct benefits:** Large when B is critical (6 of 8 B-critical cases save 5-15). When B not critical, saving zero. F05,F06,F10 illustrate *critical-path switch*: B improvement makes A the new bottleneck, capping gain. Halving B queue does not eliminate B queue (still 5-15 min); full elimination would add ~9.6 min extra.

**Secondary effects:** Reduces fork_join variance: range shrinks 50-75  50-~55 for most cases; tail flow 130115 in F07. Reduces synchronization waits for A (A_sync falls). In 4 cases resource idle gaps >saving, so no masking.

**Comparison to CF1:** Despite smaller absolute service cut (avg B queue cut 9.6 vs A service cut 10), CF2 yields ~6× larger mean flow reduction because it attacks the frequent critical branch.

### CF3: Add final-station capacity / eliminate downstream queueing

*Interpretation:* Downstream queue 8-20 min (mean 14.7) suggests final stage is not instantaneous. With 2 resources, observed waits persist even when alternate resource is idle, indicating either assignment affinity (F1 vs F2 routes) or release policy, not pure FCFS contention.

**Ideal:** `final_start' = join_ready` (zero downstream wait). Saving = `downstream_queue`.

Aggregate: mean 14.7, all 12 benefit, total 176 min saved, more than CF1+CF2 combined. Tail: F07 130115, F12 125115.

**50% reduction:** mean 7.3, all benefit proportionally.

**Direct benefits:** Immediate flow reduction for every case, no zero-benefit case because downstream is after join irrespective of critical branch. Also reduces `total_flow` variance due to final-stage contention.

**Masking interaction:** Does *not* reduce `fork_join_elapsed` (still 50-75). If branch times later improve, final capacity ensures those improvements pass through to flow. Without final capacity, earlier CF2 savings could be partially absorbed as longer downstream wait if final resources busy. Example: F03 new join 09:35 with CF2, but F1 resource next free after F01 is 09:28, so still free — no masking. F06 new join 10:15, but F2 next free after F04 is 10:30, so if we moved F06 15 min earlier, it would have to wait until 10:30 anyway for its F2 server, masking 0-? Need resource-specific modeling.

**Secondary effects / risks:** Adding third server or pooling F1/F2 (flexible assignment) eliminates affinity idle. Utilization currently: each server busy 6*20=120 min over window 09:08-12:40 (212 min)  ~57% each. Third server drops to ~38% but cuts tail waits. Risk: if downstream waits are policy (e.g., batch release), adding capacity does nothing; must verify cause. Also, faster final stage may expose upstream fork delay as new bottleneck.

Even perfect final capacity does not shorten fork-join; combined CF2+CF3 would yield ~22 min mean reduction vs CF1+CF3 ~16 min.

# 5. Recommended redesigns and risks

### Recommendation 1: Targeted B-queue reduction (Machine Stress Test) + work-leveling before pooling A capacity

**What:** Halve B queueing (e.g., add buffer capacity, priority rule, or second stress-test slot during 09:25-11:25 peak). Pilot: instrument B resource utilization, confirm B queue correlates with arrivals burst (F05-F07, F12 show 25-30 min waits). Do not yet accelerate A assay.

**Throughput/flow:** Mean fork-join 6153, mean total flow 115107.5, tail 130118 (with downstream unchanged). Reduces synchronization waiting for A (A_sync 11~6) because gaps shrink.

**Tail:** Most effective at trimming right tail where B queue 25-30 creates 65-75 min fork-join. 50% cut brings 7560.

**Utilization:** B server utilization likely high (queue implies bottleneck). Adding capacity increases utilization headroom; A lab currently 0 queue suggests spare capacity but constant 50-min service indicates possible batch or fixed protocol — spare.

**New bottlenecks / synchronization:** After CF2, A becomes critical in 5/12 vs 2/12 originally. Further B improvements beyond 50% will hit A floor (50 min). Diminishing returns. Need to monitor that C spikes (F04,F08) still create isolated 57-min fork-join; C will become relatively more frequent as second-most critical.

**What to pilot/measure first:**
* Log B resource identity and queue length (not just time). Measure `B_start - fork_release` distribution by hour.
* Test 1 week with expedited B queue (e.g., reserve slot for cases where `B_completion` predicted > `A_completion`). Measure per-case `join_ready`, `critical_branch` switch, and whether downstream idle increases.
* A/B test: ensure A assay not starved.

**Risk if wrong:** If B queue is not capacity but sequencing (e.g., B requires A output?), then reducing queue does not help and may cause rework. Verify causal independence of branches.

### Recommendation 2: Pool final stage (F1/F2 flexible) and eliminate assignment-affinity wait, before adding third server

**What:** Change final dispatch from fixed affinity (odd FF1, evenF2) to pooled first-available. Observed downstream waits 15-20 even when alternate server idle 10-30 min suggests affinity causes avoidable wait. Pilot: allow any case to go to first free F resource. Separately, test small batch-release reduction (e.g., 5-min polling  continuous).

**Throughput/flow:** Mean downstream 14.7~4-6 (empirical pooled simulation shows mean ~5). Total flow mean 115~105, tail improves without touching branches. Combined with R1, mean  ~98.

**Tail:** Downstream tail 20~8. However fork-join tail 75 remains if B not fixed.

**Utilization:** Two servers pooled at 57% each keep utilization ~57% combined, but wait collapses because idle server can cover burst. Adding third server only if pooled still shows >10 min waits at peak (11:30-12:10 burst where F09,F10,F11 all within 35 min). Currently pooled 2 servers can handle arrival every ~15 min with service 20  utilization 66%, steady-state queue not zero but lower. Third server would drop utilization to 44% and make service essentially immediate, at cost of idle.

**Synchronization effects:** Shorter downstream does not affect `join_ready` but makes flow more sensitive to branch variance — branch improvements now directly visible to customer.

**New bottlenecks:** Final stage ceases to mask branch delays; variability of fork-join becomes the dominant flow variance. May need to revisit B queue afterwards.

**What to pilot/measure first:**
* Reconstruct resource availability timeline per F1/F2, simulate pooled `final_start_pooled = max(join_ready, min(next_free_F1, next_free_F2))` vs actual. Quantify pooled saving per case (see Python).
* Log reason for downstream wait: resource busy vs policy. If `final_start - join_ready` occurs while both F idle (e.g., F01 8 min wait while both idle at 09:00), then policy, not capacity, is cause — pooling won't help; need policy change.
* Pilot one day with pooled assignment, measure `downstream_queue` distribution and whether upstream still controls.

**Order:** Recommend R1 first if data confirms B is capacity-limited, because it attacks the dominant fork-join driver. R2 in parallel as low-cost dispatch change; if pooled simulation shows >8 min mean saving, it justifies before capital expenditure. Do not accelerate A until B queue <10 min average, because A investments are masked.

    # simplified: track two servers pooled

# 7. Limits of inference

**What timestamps alone cannot identify:**

* **Causality / why waits occur:** `B_queue` measured as `B_start - fork_release` lumps together resource busyness, operator unavailability, batching, priority, and possibly data-entry delay. Without resource logs for A/B/C, we cannot attribute queue to capacity vs policy. Similarly, A queue zero may mean dedicated or pooled lab, but we cannot infer capacity.

* **Branch resource capacity and parallelism:** Number of parallel servers for A/B/C, preemptions, or multitasking not logged. A constant 50-min service suggests a fixed protocol or single server with no contention, but could also be paced. B/C queue variation implies contention but not its level.

* **Work preemption / overlap:** Complete-event data alone cannot detect if work was paused, split, or overlapped. Service = end-start may include idle within task.

* **Whether final-station waiting is truly a queue:** `downstream_queue = final_start - join_ready` assumes cases can start F immediately at `join_ready` if a server is free. Observed waits persist even when alternate F server appears idle (e.g., F01 8 min wait, both F1/F2 idle at 09:00), suggesting waits may be release policy, inspection interval, or transfer time rather than FCFS queue. Without resource-busy intervals or queue-length snapshots we cannot distinguish.

* **Fork-release semantics:** `fork_release` may itself contain upstream queue hidden before it, or may be delayed by preparation step not parallelized. Arrival to fork includes unknown upstream work.

* **Assignment and routing:** Final resource affinity (F1 vs F2) is logged but its rule unknown; pooled vs dedicated counterfactuals depend on this.

* **External confounders:** Calendar effects (breaks, shifts) and case priority could explain spikes like F04 C queue 35. No data to rule out.

* **Synchronization vs downstream entanglement:** If `join_ready` definition is wrong (e.g., F could start before slowest branch finishes in some cases), then `downstream_queue` is mis-measured and `sync waits` are artefacts.

* **Generalizability:** 12 cases over one morning cannot support inference about steady-state throughput, long-run utilization, or statistical significance. Tail estimates (max 75) have wide uncertainty.

* **PM4Py limits:** Standard `discover_performance_dfg` and `get_service_time` compute directly-follows sojourn and service per activity, not fork-join max. Synchronization waits and critical-path switches must be custom calculations as shown; relying solely on DFG would double-count or miss parallel overlaps.

Any redesign should therefore pilot with direct resource measurements (B tester busy time, final station idle time, queue-length traces) before capital investment.
