# 7. Third Alternative

**Strategy:** A **Hybrid Procedural-Declarative Model**.
- **Procedural Backbone (POWL):** Enforces P1, P2, P4, P5, P7 structurally.
- **Declarative/Data Constraints:** Enforces P3 (External) and P6 (Affected Check) via post-hoc data checks, as attributes are missing from the control-flow log.
- **Rework Logic:** Uses a `LOOP` operator to allow `Correct Dossier` to trigger re-execution of checks, satisfying P6 broadly while P7 is enforced by the loop structure (cannot repeat check without passing through `Correct Dossier` node in the loop back-edge).

**Formal Description:**
`Sequence( Register, Loop( Sequence( Parallel(Credit, Tech), Optional(Supplier), Optional(Expedite) ), Correct_Dossier ), XOR(Manager, Auto), Release )`
*Note: Supplier and Expedite are inside the loop body so that if a Correction occurs, the conditions (P3, P4) are re-evaluated upon re-entry.*

**PM4Py Code:**

```python
import pm4py
from pm4py.objects.powl.model import POWLModel
from pm4py.objects.powl.operator import OperatorPOWL
from pm4py.objects.powl.transition import Transition, SilentTransition

def build_third_model():
    # Atomic Activities
    t_register = Transition("Register Dossier")
    t_credit = Transition("Credit Check")
    t_tech = Transition("Technical Review")
    t_supplier = Transition("Supplier Review")
    t_expedite = Transition("Expedite Review")
    t_manager = Transition("Manager Approval")
    t_auto = Transition("Auto Approval")
    t_release = Transition("Release Order")
    t_correct = Transition("Correct Dossier")
    
    # Silent Transitions for Optionality
    tau_supplier = SilentTransition()
    tau_expedite = SilentTransition()
    
    # P2: Mandatory Checks (Parallel)
    # Credit and Tech must both occur, order doesn't matter
    mandatory_checks = OperatorPOWL(OperatorPOWL.PARALLEL, [t_credit, t_tech])
    
    # P3: Optional Supplier (XOR with Silent)
    # Structurally optional, data constraint required for enforcement
    supplier_block = OperatorPOWL(OperatorPOWL.XOR, [t_supplier, tau_supplier])
    
    # P4: Optional Expedite (XOR with Silent)
    # Structurally optional, must follow checks (ensured by Sequence)
    expedite_block = OperatorPOWL(OperatorPOWL.XOR, [t_expedite, tau_expedite])
    
    # P6/P7: Reworkable Phase
    # Sequence: Checks -> (Opt Supplier) -> (Opt Expedite)
    # Loop: If Correct Dossier happens, go back to start of Checks
    check_phase_body = OperatorPOWL(OperatorPOWL.SEQUENCE, [
        mandatory_checks,
        supplier_block,
        expedite_block
    ])
    
    reworkable_phase = OperatorPOWL(OperatorPOWL.LOOP, [check_phase_body, t_correct])
    
    # P5: Exactly One Approval
    approval_block = OperatorPOWL(OperatorPOWL.XOR, [t_manager, t_auto])
    
    # P1: Full Flow
    model_tree = OperatorPOWL(OperatorPOWL.SEQUENCE, [
        t_register,
        reworkable_phase,
        approval_block,
        t_release
    ])
    
    return POWLModel(model_tree)

model_third = build_third_model()
```

**Semantics & Limitations:**
1.  **Mandatory Checks:** Enforced by `PARALLEL` without `tau`. Cannot skip.
2.  **Supplier/Expedite:** Modeled as optional (`XOR` with `tau`) because the "External" attribute is missing. **Constraint:** A post-hoc data check must verify: `IF Order_Type == 'External' THEN Supplier Review EXISTS`.
3.  **Expedite Ordering:** Enforced by `SEQUENCE` (after `mandatory_checks`).
4.  **Approval:** `XOR` ensures exactly one.
5.  **Correction:** The `LOOP` operator allows `Correct Dossier` to repeat the `check_phase_body`. This satisfies P7 (Check -> Check is impossible without passing `Correct Dossier` in the loop back-edge).
6.  **Limitation:** The model allows *all* checks to repeat on correction, not just "affected" ones (P6), because the "affected" attribute is missing. This is a safe over-approximation (allows valid behavior) but requires data auditing to ensure efficiency.

# 9. Validation Experiments

To validate `model_third` and retire S/C, the following evaluation program is required:

1.  **Reproducible Splits:** Publish random seed (e.g., `seed=42`) and preprocessing code (filtering, abstraction) to ensure 80/20 split is replicable.
2.  **Attribute-Stratified Holdout:** Split holdout set by `Order_Type` (Internal/External) to ensure P3 logic holds across strata.
3.  **Curated Negative Trace Suite:** Generate synthetic traces violating P2, P4, P7. Measure **False Positive Rate** (valid traces rejected) and **False Negative Rate** (invalid traces accepted).
4.  **Perturbation Tests:** Randomly remove 5% of events (missing event bias) and duplicate 5% (noise). Measure fitness stability.
5.  **Unseen-Combination Tests:** Inject valid traces combining `Supplier + Auto + Expedite` (B5) into holdout. Measure fitness.
6.  **Alignment-Cost Sensitivity:** Vary alignment move costs (model move vs. log move). Ensure P2 violations are penalized heavily.
7.  **Soundness Checks:** `pm4py.check_soundness` to ensure no deadlocks.
8.  **Stakeholder Comprehension:** Structured survey (N=10) with tasks (e.g., "Can I skip Credit Check?"). Score accuracy, not just satisfaction.
9.  **Decision Rule:** Reject model if **Holdout Fitness < 0.90** OR **Negative Suite Precision < 0.95**.

# 10. Governance Recommendation

1.  **Model S (Retire for Compliance):** May be used for **Exploration** only (high-level bottleneck analysis). It must **not** be used for compliance or automated enforcement due to semantic violations (P2, P4).
2.  **Model C (Retire):** Unmaintainable and overfitted. The duplicate labels and enumeration strategy create unacceptable IT and audit risk (F3, F2).
3.  **Third Alternative (Candidate for Deployment):** Recommended for **Compliance** and **Operational Monitoring**, conditional on:
    - Passing the Negative Suite Precision test (>0.95).
    - Stakeholder validation of the "Correction Loop" semantics (confirming broad rework is acceptable given missing attributes).
    - Implementation of the post-hoc data constraints for P3 (External Supplier) since the control-flow model cannot enforce it alone.

# 11. Dissenting View

The Third Alternative imposes a rigid "Happy Path" structure on a process that stakeholders describe as having "unresolved detail" and missing attributes. By enforcing a strict `Loop` for corrections, we risk blocking legitimate emergency overrides where a Manager might approve a dossier after a phone-call correction that isn't logged as `Correct Dossier`. The model assumes the event log is a complete truth, but F4 suggests missing `Supplier Review` events are already common. Enforcing structural constraints on incomplete data will generate a high volume of false positives, causing "alert fatigue" where compliance teams ignore genuine violations because the system cries wolf on every missing attribute. I would recommend retaining Model S for monitoring and only using the Third Alternative for post-mortem audit, not real-time blocking.

**Evidence to Change Decision:**
I would change my recommendation if an analysis of the last 6 months of "rejected" cases showed that >10% of valid orders were forced through artificial `Correct Dossier` events just to satisfy the system, or if emergency bypass traces (valid but violating the loop) were formally documented and approved by Risk Management.
