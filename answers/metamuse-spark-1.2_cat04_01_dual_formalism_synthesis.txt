# 1. Assumptions and Interpretation

1.  **Low-risk / high-risk choice:** Not a data condition. Modeled as `XOR(Supervisor Review, PAR(Quality Review, Regulatory Review))`. Choice is made after `Analyze Root Cause` by control-flow branching. Silent data dependency is not encoded; replay fitness assumes oracle chooses correct branch.
2.  **Optional supplier consultation:** Modeled as `XOR(Consult Supplier, tau)` where `tau` is a silent skip. At most once, zero or one occurrence. Decision is non-deterministic in control-flow (data not represented). If present, its position is constrained by partial order edges.
3.  **Passing inspection abstraction:** `Inspect Trial` outcome is not an event label. Abstracted as `LOOP( SEQ(Execute Trial, Inspect Trial), Adjust Parameters)`. One loop iteration = one trial cycle. Loop exit means the last `Inspect Trial` passed; loop redo `Adjust Parameters` means previous inspection failed. `Adjust Parameters` never follows the passing inspection by construction. No `fail/pass` labels exist.
4.  **Duplicate visible labels:** Prohibited in the canonical models presented. Duplication (`DCA` in two branches, `PV` in two branches) would allow faithful non-block-structured synchronization but destroys label uniqueness, breaks conformance counting, mining and frequency analysis. Discussed as `duplication-based approximation` alternative and rejected.
5.  **Process-tree approximation policy:** **Conservative under-approximation** is primary, with local over-approximation inside the `LOOP`. The tree *excludes* some intended concurrent interleavings rather than admitting unsafe orderings such as `Plan Verification` before `Contain Material`, `Design Corrective Action` before `Analyze Root Cause`, or `Execute Trial` before its two prerequisites. Consequence: fitness < 1.0 on intended log, precision = 1.0 w.r.t unsafe dependencies. A permissive over-approximation is discussed but not chosen.
6.  **"May overlap" interpretation:** Interpreted as **absence of order constraint = true concurrency** permitted by `PARALLEL` / partial-order incomparability. No requirement for simultaneous execution, only that any interleaving of completions is allowed and recorded as a total order. In POWL this is partial-order incomparability; in the process tree this is `Operator.PARALLEL`.

# 3. PM4Py Process-Tree Model

### Compact expression

```text
SEQ(
  Register Deviation,
  PAR(
    SEQ(Contain Material, Plan Verification),
    SEQ(Analyze Root Cause, Design Corrective Action)
  ),
  PAR(
    XOR(Supervisor Review, PAR(Quality Review, Regulatory Review)),
    LOOP(SEQ(Execute Trial, Inspect Trial), Adjust Parameters),
    XOR(Consult Supplier, tau)
  ),
  Release Material,
  Archive Case
)

// pm4py parse syntax (equivalent):
// ->('Register Deviation', ^(->('Contain Material','Plan Verification'),->('Analyze Root Cause','Design Corrective Action')), ^(X('Supervisor Review',^('Quality Review','Regulatory Review')), *(->('Execute Trial','Inspect Trial'),'Adjust Parameters'), X('Consult Supplier',tau)), 'Release Material','Archive Case')
```

Mapping to narrative: `->` = `SEQUENCE`, `^` = `PARALLEL`, `X` = `XOR`, `*` = `LOOP` (do, redo). First `PAR` enforces CM->PV and ARC->DCA concurrently. Second `PAR` allows approvals, trial loop and optional CS to overlap. Outer `SEQ` enforces RD first and RM->AC last.

### Self-contained Python code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def tau():
    # silent leaf: label is None
    return ProcessTree(label=None)

# leaves
rd = leaf("Register Deviation")
cm = leaf("Contain Material")
pv = leaf("Plan Verification")
arc = leaf("Analyze Root Cause")
dca = leaf("Design Corrective Action")
sr = leaf("Supervisor Review")
qr = leaf("Quality Review")
rr = leaf("Regulatory Review")
cs = leaf("Consult Supplier")
et = leaf("Execute Trial")
it = leaf("Inspect Trial")
ap = leaf("Adjust Parameters")
rm = leaf("Release Material")
ac = leaf("Archive Case")

# SEQ(CM,PV)
seq_cm_pv = ProcessTree(operator=Operator.SEQUENCE)
seq_cm_pv.children = [cm, pv]
cm.parent = seq_cm_pv
pv.parent = seq_cm_pv

# SEQ(ARC,DCA)
seq_arc_dca = ProcessTree(operator=Operator.SEQUENCE)
seq_arc_dca.children = [arc, dca]
arc.parent = seq_arc_dca
dca.parent = seq_arc_dca

# PAR( SEQ(CM,PV), SEQ(ARC,DCA) )
par_initial = ProcessTree(operator=Operator.PARALLEL)
par_initial.children = [seq_cm_pv, seq_arc_dca]
seq_cm_pv.parent = par_initial
seq_arc_dca.parent = par_initial

# XOR(SR, PAR(QR,RR))
par_qr_rr = ProcessTree(operator=Operator.PARALLEL)
par_qr_rr.children = [qr, rr]
qr.parent = par_qr_rr
rr.parent = par_qr_rr

xor_approval = ProcessTree(operator=Operator.XOR)
xor_approval.children = [sr, par_qr_rr]
sr.parent = xor_approval
par_qr_rr.parent = xor_approval

# SEQ(ET,IT)
seq_et_it = ProcessTree(operator=Operator.SEQUENCE)
seq_et_it.children = [et, it]
et.parent = seq_et_it
it.parent = seq_et_it

# LOOP(SEQ(ET,IT), AP)
loop_trial = ProcessTree(operator=Operator.LOOP)
loop_trial.children = [seq_et_it, ap]
seq_et_it.parent = loop_trial
ap.parent = loop_trial

# XOR(CS, tau)
xor_cs = ProcessTree(operator=Operator.XOR)
silent = tau()
xor_cs.children = [cs, silent]
cs.parent = xor_cs
silent.parent = xor_cs

# PAR( approval, loop, optional CS )
par_second = ProcessTree(operator=Operator.PARALLEL)
par_second.children = [xor_approval, loop_trial, xor_cs]
xor_approval.parent = par_second
loop_trial.parent = par_second
xor_cs.parent = par_second

# ROOT SEQ(RD, par_initial, par_second, RM, AC)
tree = ProcessTree(operator=Operator.SEQUENCE)
tree.children = [rd, par_initial, par_second, rm, ac]
rd.parent = tree
par_initial.parent = tree
par_second.parent = tree
rm.parent = tree
ac.parent = tree
```

The variable `tree` is the final `ProcessTree`. Using `pm4py.parse_process_tree(...)` with the string above yields an equivalent tree; the string maps `->` to `SEQUENCE`, `^` to `PARALLEL`, `X` to `XOR`, `*` to `LOOP`.

### Approximation and loss

Every requirement that cannot be represented exactly:

*   **Cross-branch AND-join before ET exactly:** Intended `ET` waits for `PV` *and* `DCA` only. Tree waits for `PAR(SEQ(CM,PV), SEQ(ARC,DCA))` to complete entirely before `par_second`, so `DCA` and `PV` are correctly synchronized, but the structure forces them to be the *only* prerequisites in that phase and forces a barrier.
*   **Early start of approvals after ARC:** Intended approvals may start immediately after `ARC` and overlap `PV` and `DCA`. Tree delays all approvals until *after* both `PV` and `DCA` (barrier between the two `PAR`s). This is over-constraint / under-approximation – traces where `Quality Review` starts before `Plan Verification` completes are excluded.
*   **Early/overlapping Consult Supplier:** Intended `CS` may start after `ARC` and overlap `PV`, `DCA`, approvals and trial. Tree places `XOR(CS,tau)` in `par_second`, therefore `CS` cannot start until after `PV` and `DCA`. Excludes intended interleavings where `CS` overlaps design/planning.
*   **DCA concurrent with approvals:** Intended `DCA` and approvals are concurrent after `ARC`. Tree sequences `DCA` before approvals (`DCA` in first `PAR`, approvals in second `PAR`). Adds `DCA -> approval` order not required.
*   **Intra-loop concurrency:** Tree admits any interleaving inside `par_second` between approvals, `CS` and the *entire* loop as a block, but still block-structures approvals vs trial. It cannot express that a single approval activity occurs *between* `ET` and `IT` of the same iteration vs between iterations differently – only coarse `PAR`.
*   No duplicate labels are used, therefore faithful non-block synchronization would require duplication; we sacrifice concurrency to preserve label uniqueness.

# 4. PM4Py POWL Model

### Compact description

```text
POWL = StrictPartialOrder(
  nodes = {
    RD, CM, ARC, PV, DCA,
    APPROVAL = XOR(SR, PAR(QR,RR)),
    CS_OPT = XOR(CS, tau),
    TRIAL = LOOP(SEQ(ET,IT), AP),
    RM, AC
  },
  order = {
    RD -> CM, RD -> ARC,
    CM -> PV,
    ARC -> DCA,
    ARC -> APPROVAL,
    ARC -> CS_OPT,
    PV -> TRIAL,
    DCA -> TRIAL,
    APPROVAL -> RM,
    TRIAL -> RM,
    CS_OPT -> RM,
    RM -> AC
  }
)
PAR(QR,RR) has no edge between QR and RR.
LOOP semantics: do SEQ(ET,IT), redo AP.
```

### Self-contained Python code

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# transitions (visible)
RD = Transition(label="Register Deviation")
CM = Transition(label="Contain Material")
ARC = Transition(label="Analyze Root Cause")
PV = Transition(label="Plan Verification")
DCA = Transition(label="Design Corrective Action")
SR = Transition(label="Supervisor Review")
QR = Transition(label="Quality Review")
RR = Transition(label="Regulatory Review")
CS = Transition(label="Consult Supplier")
ET = Transition(label="Execute Trial")
IT = Transition(label="Inspect Trial")
AP = Transition(label="Adjust Parameters")
RM = Transition(label="Release Material")
AC = Transition(label="Archive Case")

# --- submodels ---
# high-risk PAR(QR,RR)
high = StrictPartialOrder(nodes=[QR, RR])
# no edge between QR and RR => concurrent

# approval choice: XOR(SR, high)
approval = OperatorPOWL(operator=Operator.XOR, children=[SR, high])

# optional CS: XOR(CS, tau)
cs_opt = OperatorPOWL(operator=Operator.XOR, children=[CS, SilentTransition()])

# trial cycle SEQ(ET,IT)
seq_et_it = StrictPartialOrder(nodes=[ET, IT])
seq_et_it.order.add_edge(ET, IT)

# LOOP(SEQ(ET,IT), AP)
trial = OperatorPOWL(operator=Operator.LOOP, children=[seq_et_it, AP])

# --- root partial order ---
powl = StrictPartialOrder(nodes=[RD, CM, ARC, PV, DCA, approval, cs_opt, trial, RM, AC])

# required precedence edges
powl.order.add_edge(RD, CM)
powl.order.add_edge(RD, ARC)
powl.order.add_edge(CM, PV)
powl.order.add_edge(ARC, DCA)
powl.order.add_edge(ARC, approval)
powl.order.add_edge(ARC, cs_opt)
powl.order.add_edge(PV, trial)
powl.order.add_edge(DCA, trial)
powl.order.add_edge(approval, RM)
powl.order.add_edge(trial, RM)
powl.order.add_edge(cs_opt, RM)
powl.order.add_edge(RM, AC)
```

All dependencies from §2 are added with `order.add_edge`. Variable `powl` is the final POWL model.

### Why unconnected nodes may remain concurrent

Any pair without a (transitive) edge is intentionally concurrent:

*   `CM` vs `ARC` – no edge between them (both only after `RD`)  containment and root-cause may overlap.
*   `PV` vs `DCA` and `PV` vs `approval` – `PV` depends only on `CM`, `DCA`/`approval` only on `ARC`  verification planning may overlap design and approvals.
*   `PV` vs `CS` (via `cs_opt`) – only `ARC -> cs_opt`, no `PV -> cs_opt` / `cs_opt -> PV`  supplier consultation may overlap planning.
*   `approval` vs `trial` – no edge between them  approvals may overlap trial cycles (ET/IT/AP), as required.
*   `cs_opt` vs `approval` and `cs_opt` vs `trial` – no edge  `CS` may overlap approvals and trial.
*   `QR` vs `RR` inside `high` – no edge  high-risk reviews concurrent in either order.
*   `CM` vs `DCA`/`approval`/`trial` etc. – only indirect via `RD`, otherwise concurrent where intended.

StrictPartialOrder transitively closes edges, so no hidden order is introduced.

# 7. Preferred Representation and Validation Plan

**Canonical choice: POWL.**

Defence: POWL with `StrictPartialOrder` is the only representation that can express the non-block-structured cross-branch dependencies (CM->PV, ARC->DCA, PV+DCA->ET, ARC->approval/CS, approval/trial/CS ->RM) without duplication or barrier introduction. The process tree is necessarily approximating and under-approximates valid concurrency, lowering fitness on intended logs while staying sound. POWL is strictly more faithful, retains label uniqueness, directly models `may overlap` as incomparability, and preserves independent progress before synchronizing release. For a compliance-critical deviation process where early approvals/supplier involvement and trial overlapping matter for lead time, the POWL’s exactness is business-critical.

### Concrete validation plan

1.  **Conversion to accepting Petri net where supported**
    ```python
    net, im, fm = pm4py.convert_to_petri_net(powl)  # POWL -> Petri net
    net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)
    ```
    Inspect that conversion succeeds; inspect net structure for silent transitions (`tau` for CS skip, LOOP back-edges). Document that conversion is not proof of fidelity – it preserves language but may introduce silent steps.

2.  **Soundness checking**
    ```python
    pm4py.check_soundness(net, im, fm, print_diagnostics=True)
    ```
    Verify workflow soundness (no deadlocks, proper completion) for both nets. Unsoundness would indicate modeling error (e.g., missing RM->AC edge).

3.  **Bounded / sampled playout**
    ```python
    log_powl = pm4py.play_out(powl, parameters={"num_traces": 200})
    log_tree = pm4py.play_out(tree, parameters={"num_traces": 200})
    ```
    Sample traces, check that RD is always first, AC last, CM before PV, ARC before DCA, ET-IT pattern holds, AP always between IT and ET, RM before AC.

4.  **Explicit positive and negative trace tests**
    ```python
    from pm4py.objects.log.obj import Trace, EventLog
    # replay with alignments or footprint checks; example positive T1, negative F1
    def make_trace(acts): ...
    # pm4py.conformance_diagnostics_alignments(log, net, im, fm)
    ```
    Test five allowed witnesses against both models (expect alignments cost 0 for POWL, cost >0 for T3 on tree) and three forbidden witnesses (expect alignment cost >0 / non-fitting for both).

5.  **Silent behavior / duplicated-label check**
    ```python
    # count skips of CS, loop iterations
    # ensure no transition label appears twice in net
    labels = [t.label for t in net.transitions if t.label]
    assert len(labels) == len(set(labels)), "duplicate visible label"
    # distinguish silent tau steps vs skipped CS vs loop redo
    ```
    Replay log containing `CS` vs empty `CS` to confirm `XOR(CS,tau)` does not create livelock and that `LOOP` silent redo is not confused with `RM`. For duplication-based alternative, count token-based replay inflation.

6.  **Limitations**
    *   Playout is sampled, not exhaustive – state space of concurrent approvals + optional CS + loop is infinite; bounded exploration misses rare interleavings.
    *   Conversion to Petri net may normalize partial-order concurrency into interleaving diamonds, obscuring true concurrency vs interleaving.
    *   Alignments penalize model moves vs log moves equally – cannot quantify *how* much the tree under-approximates without enumerating all partial-order linearizations.
    *   Silent transitions introduced for `tau` and LOOP create invisible behavior that alignments can exploit to hide violations if costs not tuned.
    *   No data perspective – low/high risk and inspection outcome abstracted as non-deterministic choice, so fitness checks cannot validate that choice logic matches business rules.

# 8. Final Self-Critique

1.  **Semantic weakness – tree barrier hides true trade-off:** The chosen process tree is presented as conservative under-approximation, but its `PAR(initial) -> PAR(approval, trial, CS)` barrier also *permits* interleavings that are arguably not intended inside `par_second` (e.g., `CS` could be considered concurrent with `RM` start if net interleaving semantics are interleaving-based). The critique of permissiveness vs conservativeness is not quantified with language inclusion metrics.

2.  **Semantic weakness – LOOP abstraction conflates instance correlation:** Both models use `LOOP(SEQ(ET,IT), AP)` which loses the correlation that an `Adjust Parameters` belongs to the *preceding* failed `Inspect Trial` and that a passing `IT` enables `RM`. POWL enforces order but does not forbid a trace where an `AP` occurs without a preceding `IT` failure being observable – this is inherent to control-flow-only abstraction but is a residual semantic gap.

3.  **Syntactic / tooling weakness – API fragility:** `StrictPartialOrder` constructor signature and `OperatorPOWL` LOOP arity differ across pm4py versions (some require `children` as list of `StrictPartialOrder` vs `Transition`). The provided code assumes `Operator.LOOP` with two children and `SilentTransition()` availability; in older releases `SilentTransition` must be imported differently or `tau` modeled via empty `StrictPartialOrder`. Execution may need minor adaptation, and the compact POWL string is not directly parsable by `pm4py.parse_powl_model_string` without quoting adjustments.
