## 1. Temporal Data Semantics

**Reconstruction of state:** State is reconstructed per case as an event-sourced time series. Sort by `time:timestamp` then `event_index`. Start from `Create_Transaction` values. For each subsequent event in order, update only non-blank cells for `amount, risk_level, jurisdiction, customer_type`. Blank = no update, not NULL assignment. The current value at event `e` is the last non-blank value at or before `e` in that order.

**Blanks:** CSV blanks are preserved as unknown/no-change markers, then forward-filled within case (`ffill` after sorting, no `bfill`, no cross-case fill). Unknown remains unknown until first explicit value.

**Equal timestamps:** `event_index` is the tie-breaker. Logical order = `(timestamp, event_index)`. Consequence: two events at the same UTC instant have a defined before/after. In TX-311, `Enhanced_Review` (index 3) precedes `Update_Jurisdiction` (index 4) at `16:20:00Z`. Review therefore saw `US`, release saw `DE`.

**Material changes:** Any explicit update to `amount, risk_level, jurisdiction, customer_type`, plus `Sanctions_List_Update`, is a candidate material change. For amount-dependent obligations, R4 narrows materiality: only an increase >20% since the latest `Standard_Review/Enhanced_Review` invalidates that review. Decreases do not invalidate. Increase from unknown is not computable and blocks R4 evaluation. Jurisdiction/risk/customer-type changes are material for R1/R2/R3 trigger evaluation and for R1's "after the latest material data change" clause.

**Final attributes:** Final case state is not projected backward. Each obligation is evaluated on the latest known value at the relevant event time (R7). E.g., settlement amount on T+1 does not prove release amount; DE at release does not prove DE at review.

**Four times distinguished:**
- `event time`: `time:timestamp` + `event_index` when something is claimed to have happened.
- `effective time`: when a value or exemption legally takes effect (e.g., `effective_from`, list-addition time). Defaults to event time unless evidence establishes another time.
- `record time`: when evidence was written to a system (e.g., `Record_Exemption` DB insert at 11:00).
- `evidence time`: when cryptographic / independent proof of existence was created (e.g., qualified signature timestamp, certificate validity, witness statement time). A late `record time` with strong `evidence time` (TX-302 outage + valid 09:05 signature) can prove earlier `effective time`. A displayed field with invalid `evidence time` (TX-310 certificate created after release) cannot.

## 4. Ambiguities and Alternative Readings

**TX-302 (late record vs timely approval):** Result changes if evidence quality is downgraded. If qualified signature were invalid or outage undocumented, `Record_Exemption 11:00` after `Release 09:40` would be post-hoc. Under strict `record_time  release` view, classification would become NONCOMPLIANT (R1 needs Enhanced — but here Enhanced exists, so still COMPLIANT) or, in a variant without Enhanced, INDETERMINATE/NONCOMPLIANT. What saves TX-302 is redundancy: Enhanced alone satisfies R1, so exemption is defense-in-depth. If policy required exemption pre-registration regardless, or if Enhanced were deemed stale, EX-77's strong evidence_time would still justify JUSTIFIED_EXCEPTION. Lesson: distinguish redundant vs sole-basis exemptions.

**TX-305 (unknown amount):** Would become COMPLIANT if an immutable release payload or review document proved amount at release and review (e.g., if review stated 80k and release proved 85k, increase 20% and Enhanced covers R1 if 100k, or R1 not triggered if <100k). Would become NONCOMPLIANT if release payload proved amount 100k with >20% increase from any proven review amount, or if amount 100k with no valid Enhanced after change. Settlement 150k alone cannot decide because no linkage proves `release_amount == settlement_amount` (fees, FX, partial settlement possible). Additional evidence needed: release message schema, amount feed audit, reviewer attestation of amount seen.

**TX-310 (contradictory exemption evidence):** Strict evidentiary reading  NONCOMPLIANT: reject interested-witness oral claim, treat cert creation 10:30 as proof approval did not exist at 10:00, backdated PDF display insufficient per R5. Lenient reading  JUSTIFIED_EXCEPTION: accept oral approval 08:45 as effective, treat late certificate as mere formalization, scope/effective/expiry otherwise match. Current evidence supports neither conclusively  INDETERMINATE is correct. What would change it: qualified signature with `evidence_time 08:50` and independent log, Head_Compliance calendar/email, or system approval workflow entry; conversely, CA audit showing no approval record before 10:30 would push to NONCOMPLIANT. Also note EX-88 waives R1 only, so even if valid it would not help an R2 case — not relevant here but limits scope.

**TX-311 (same-timestamp ordering + jurisdiction shopping):** If `event_index` is ignored, order of Enhanced vs jurisdiction change at 16:20 is ambiguous; a checker using only timestamp would either falsely conclude Enhanced saw DE (over-crediting review coverage) or flag indeterminate ordering. With `event_index 3<4`, Enhanced saw US/115k, release saw DE. Under R7 (snapshot at release)  COMPLIANT because DE exempts R1. Alternative interpretation — continuous monitoring or anti-evasion rule — would flag: jurisdiction change to exempting DE immediately before release without re-screening/re-review is suspicious and could require new review or proof of genuine relocation. Would change to INDETERMINATE (need effective-time proof of jurisdiction, beneficial-owner residence, change provenance) or NONCOMPLIANT under a rule version that freezes R1 trigger at review time or requires review after last jurisdiction change regardless of exempt direction. Also, if DE evidence is weak (typo, interim), trigger remains US/115k and Enhanced 16:20 satisfies  still COMPLIANT, but for different reason.

**Two other cases with alternative readings:**
- **TX-306:** If "material data change" in R1 were read as *any* amount change (not R4-filtered), Enhanced 12:15 before 12:30 change would fail "after latest material change" and verdict would flip to NONCOMPLIANT pending re-review. The R4 >20% test is what keeps it COMPLIANT. Needs explicit rule-versioning.
- **TX-308:** If threshold were read as `>100000` (exclusive) instead of ``, release at exactly 100k would not trigger R1  COMPLIANT trivially without needing R4 decrease analysis. If decrease magnitude were large (e.g., structuring to evade), a conduct rule could still flag despite R4. Clarify inclusive threshold in rule version.

    if s.empty: return pd.NaT

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage:** Standard miners / conformance that use end-of-case attributes copy settlement amount (TX-305: 150k on T+1) or final jurisdiction (TX-311: DE) backward, inventing a trigger or erasing one. Event-time snapshots are required.
2. **Post-hoc exemptions:** Control-flow sees `Record_Exemption` after `Release` as a trace-order violation or ignores it. It cannot distinguish TX-302 (late record + timely qualified signature + outage = valid) from TX-310 (late record + post-dated certificate + interested witness = unproven). Needs record vs effective vs evidence time.
3. **Material changes after review:** `Precedence(Enhanced,Release)` passes TX-301-variant, TX-309, and TX-306 identically, yet R4 invalidates the first two (>20%: 56% and 22.9%) and excuses the third (4.35%). Percentages on data values are invisible to activity order.
4. **Conditional activation:** R1/R2 fire only on data predicates (`jurisdiction!=DE AND amount>=100k`; `risk==HIGH OR cust==PEP`). Pure DECLARE would demand Enhanced/Approval on every release, failing compliant low-value/DE cases and passing high-value cases with wrong review type (StandardEnhanced in TX-301/TX-307/TX-310).
5. **Missing data:** Control-flow is two-valued (present/absent). R6 requires three-valued logic: TX-305 (unknown release amount) and TX-310 (unknown approval existence) must be INDETERMINATE, not defaulted to compliant or violated. Unknown flags must propagate.
6. **Same-timestamp ordering:** Without `event_index`, TX-311's `Enhanced` and `Update_Jurisdiction` at `16:20:00Z` are simultaneous. Order determines what the reviewer saw (US vs DE). Most logs sort stably but arbitrarily; conformance must use explicit tie-breaker and state the consequence.
7. **Approval semantics beyond order:** `Response(Enhanced,Compliance_Approve)` passes TX-307, yet the approval covered only a standard packet, which per policy does not cure missing Enhanced. Content and scope of the approval matter, not just occurrence.

## 7. Recommended Logging and Control Improvements

- **Immutable release payloads:** Emit `Release_Funds` with mandatory `amount, currency, jurisdiction, risk_level, customer_type, rule_version` frozen at release, hashed and signed. Prevents TX-305 settlement-projection and proves threshold evaluation. Reject release messages omitting amount.
- **Separate effective / record / signature timestamps:** Every attribute update and exemption carries `effective_time`, `record_time`, `actor`, plus qualified `signature_time` and certificate reference. Late inserts (TX-302/TX-310) must link to original signed approval; displays of `effective_from` without signature are warnings.
- **Rule version on each event:** Log `policy_version` (e.g., threshold 100k inclusive, R4 20%, DE carve-out) at review and release to resolve inclusive-threshold and any-vs->20% disputes (TX-306/TX-308).
- **Exemption scope as structured data:** `jurisdiction_set, customer_type_set, max_amount, waived_rules [R1], effective_from, expiry, approver_role+ID` enforced at release time by the workflow engine, not by free-text note. Block release referencing expired/out-of-scope/post-dated exemption pending Head_Compliance countersignature.
- **Change provenance and reason:** `Update_*` events must carry `old_value, new_value, source_system, reason_code, supporting_doc_id`. Amount feed outages (TX-305) must block or escalate high-value releases; jurisdiction changes to exempt values immediately before release (TX-311) must trigger re-screening hold and enhanced due-diligence.
- **Stable ordering keys:** Require monotonic `event_index` or `seq_no` per case plus `ingest_time`; never rely on timestamp alone. Visualize and check `(timestamp, event_index)` in every audit.
- **Review content linkage:** `Enhanced_Review`, `Standard_Review`, `Compliance_Approve`, `Sanctions_Screen` must reference `reviewed_snapshot_hash` (amount/jurisdiction/risk seen), `packet_type`, and `screen_list_version`. Approval must state which packet was approved; standard-packet approvals must not satisfy R2.
- **Sanctions list versioning:** `Sanctions_List_Update` must carry `list_version, added_jurisdictions[], effective_time`; `Sanctions_Screen` must carry `list_version_checked`. Enable automatic R3 re-screen tasks when `list_version` advances before release.
- **Unknown-value handling by design:** Make amount/risk/jurisdiction non-nullable at release; allow explicit `UNKNOWN` with mandatory `fallback_review` path that forces Enhanced + dual approval and marks case for human close-out, rather than silent defaulting.
