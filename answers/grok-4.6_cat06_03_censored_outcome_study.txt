## 1. Target definition

**Primary target (selected, activation-conditional 90-day default).**  
Let a case be one credit application (`case:concept:name`). Let \(T_{\text{act}}\) be the timestamp of the first `Account Activated` event, and let \(D\) be the calendar time of the first default event after activation (from the outcome feed, not from in-process collections text). Define

\[
Y =
\begin{cases}
1 & \text{if } T_{\text{act}} \text{ exists and } D \le T_{\text{act}}+90\text{d}, \\
0 & \text{if } T_{\text{act}} \text{ exists, } D > T_{\text{act}}+90\text{d},\ \text{and the feed has matured}, \\
\text{undefined} & \text{if the case is never activated}, \\
\text{censored} & \text{if activated but } 90\text{d (plus feed delay) has not matured as of the study cutoff}.
\end{cases}
\]

- **Prediction time.** A prefix as-of time \(\tau\), chosen *before* Accept / Reject / Transfer / Withdrawal / Contract Signed / Account Activated. Two operational clocks are used in parallel: (i) event-count prefixes of length \(k\in\{2,3,4\}\) after `Application Started`; (ii) elapsed-time prefixes at \(t\in\{24\text{h}, 72\text{h}, 7\text{d}\}\) after case start. If a competing terminal arrives before \(\tau\), that case is not scored for the primary target (the decision has already been made).
- **Horizon.** 90 days after *activation*, not 90 days after application start. The warehouse definition is post-activation default; mixing the two clocks would change the estimand.
- **Unit of analysis.** One application; one row per \((case, k)\) or \((case, t)\) prefix. Repeated prefixes from the same case are clustered in inference.
- **Population.** Applications started in the observation window that, under the *observed* credit policy, reach `Account Activated`. Rejected, withdrawn, transferred-without-activation, and still-open cases are **not** members of the labeled primary population.
- **Estimand.** The selected-sample predictive functional
  \[
  \pi(x_\tau) = \Pr(Y=1 \mid X_\tau=x_\tau,\ \text{activated},\ \text{label identifiable}),
  \]
  where \(X_\tau\) is information available at \(\tau\). This is **not** \(\Pr(\text{default}\mid\text{every application})\) and **not** a counterfactual “had we activated this rejected file.”

This is operationally defensible because the lender’s legal/accounting default is defined only after money is extended, the warehouse already stores that label, and an early-warning score used *at underwriting* is a statement about risk *if the file is booked*. It is statistically defensible because \(Y\) is actually generated for activated accounts (subject to delay and censoring). It is *not* convenient complete-case mining of the 21,600-row export: immature activations remain censored, and non-activated cases are not coded \(Y=0\).

**Alternative A — multi-state / competing outcomes on all 48,000 applications.**  
Absorbing states: Rejected; Withdrawn; Transferred; Activated-and-defaulted-by-90d; Activated-and-survived-90d; plus a censored state for still-open or immature labels. The identifiable quantities are cause-specific hazards and cumulative incidence functions, especially \(\Pr(\text{Activated and }Y=1\mid X_\tau)\). This answers a *portfolio-flow* question (“how many early prefixes become booked defaults?”), not an underwriting question (“if we book this file, will it default?”). Treating Rejected as non-default is a degenerate and biased special case of this model and is rejected.

**Alternative B — policy-specific counterfactual default.**  
\(\Pr(Y^{\text{activate}}=1\mid X_\tau)\) under a hypothetical policy that activates the file. This is what the informal request (“default for every application”) actually needs, and it is **not identified** from these data without unconfoundedness, an instrument, or an explicit policy model. The 1 July 2025 threshold change is a candidate design feature for a sensitivity analysis, not a license to impute zeros.

## 2. Cohort construction

**As-of rule.** All inclusion, terminal-state, and label-maturity decisions are made with a configurable study cutoff \(C\) (default: `data_extract_time` = 15 February 2026). An event or attribute is visible only if its timestamp is \(\le \min(\tau, C)\). A 90-day label is *identifiable* only if `label_available_at` \(\le C\), or, if that field is missing, only if \(T_{\text{act}}+90\text{d}+\Delta_{\text{feed}} \le C\) with a conservative \(\Delta_{\text{feed}}=35\) days (125-day booking-to-identifiable window). Partner-originated activations with a permanently empty feed are *not* recoded as non-default.

**Inclusion.**
- Case start (`Application Started`) in [1 Jan 2024, 31 Dec 2025].
- At least one event at or before the chosen \(\tau\) (otherwise no prefix exists).
- For the *primary labeled analysis*: `Account Activated` \(\le C\), and either a matured \(Y\in\{0,1\}\) or explicit right-censoring.

**Exclusion (from the primary labeled set, not from the process census).**
- Rejected, withdrawn, or transferred-without-linked-activation: default is undefined under the observed policy.
- Still-open at \(C\): no activation, so no primary label.
- Prefixes that already contain Accept / Reject / Transfer / Withdrawal / Contract Signed / Account Activated / Collections Contact / Default Recorded: prediction time has been violated.
- Duplicate events created by the 15 Oct 2025 migration after activity-name harmonization (keep first by timestamp, `source_system`, activity).
- Cases whose only “label” is a business recode of reject/withdraw as non-default.

**Transfer rule.** If the linkage table maps the case to a later activation on a partner platform, follow-up is used *only* for the linked 60% and is flagged `followup_linked=1`. The unlinked 40% are a competing exit with missing follow-up, not \(Y=0\).

**Cohort-flow table (all 48,000 starts; extraction 15 Feb 2026).**

| Step | N | Analytic role |
|---|---:|---|
| Applications started 1 Jan 2024–31 Dec 2025 | 48,000 | Source population / competing-risk census |
| Still open at extraction (no Accept/Reject/Withdraw/Transfer/Activate) | 5,100 | Decision-time administrative censoring; \(Y\) undefined |
| Reached a pre-activation terminal or activation | 42,900 | — |
| Rejected and closed | 9,100 | Competing terminal; default **undefined**; do not label 0 |
| Withdrawn by applicant | 5,700 | Competing terminal; default **undefined**; do not label 0 |
| Transferred to partner/specialist | 2,900 | Competing exit; ~1,740 linkable, ~1,160 selectively unobserved follow-up |
| Account activated (exposed to 90-day default risk) | 25,200 | Primary risk set |
| Activated, 90-day outcome or delayed feed not identifiable | 3,600 | Ordinary right censoring and/or delayed labels |
| Activated, label identifiable (current ML export) | 21,600 | Complete primary labels |
| — of which non-default | 18,900 | Survived 90d after activation |
| — of which default | 2,700 | Event (\(12.5\%\) of mature activations; \(5.6\%\) of all starts) |

The 21,600-row export is a **selected, matured subset**, not the study population. Any metric computed only on those rows is an activation-conditional, maturity-conditional association.

## 3. Censoring and missing-label strategy

Distinguish five mechanisms; they are not interchangeable.

1. **Ordinary right censoring.** Activated, clock still inside the 90-day window at \(C\), or the case is still open and has not been activated. The default *process* is defined for activations; it is not defined for still-open files.
2. **Delayed labels.** The feed arrives 7–35 days after the 90-day point. A case with \(T_{\text{act}}+90\text{d} \le C < \) `label_available_at` is not a non-default; it is a delayed complete observation. Using `default_90d` whenever it is non-missing without checking `label_available_at` leaks post-cutoff information and preferentially observes faster feeds.
3. **Selection through activation.** Rejects, withdrawals, and many transfers are never exposed. This is not censoring of a well-defined default time; it is a different potential outcome. Coding them as \(Y=0\) answers a different, policy-entangled question and will make the model look well-calibrated to “no default” while learning the accept/reject policy.
4. **Transfer.** A competing operational exit. For 60% a linkage table restores follow-up (possibly under a new case id); for 40% follow-up is missing. Linked vs unlinked can differ by region, amount, and `source_system`.
5. **Permanently missing partner outcome feeds.** Elevated among partner-originated activations. This is closer to missing-not-at-random outcome observation than to administrative censoring.

**Primary analysis strategy.**  
Fit the primary model only on the **activated risk set** (25,200), using a 90-day binary endpoint when identifiable and a right-censored survival / binary-with-censoring likelihood otherwise (e.g. discrete-time hazard or a survival model with time origin \(T_{\text{act}}\)). Prefix features \(X_\tau\) are computed strictly before activation. Non-activated cases enter only a **separate activation / competing-exit model** (multinomial or cause-specific hazards for {Activate, Reject, Withdraw, Transfer, Open-at-\(C\)}). Reported underwriting scores are \(\hat\pi(x_\tau)=\widehat\Pr(Y=1\mid X_\tau,\text{activated})\). Reported portfolio early-warning volumes are \(\hat\Pr(\text{Activate}\mid X_\tau)\times\hat\pi(x_\tau)\), never \(\hat\pi\) applied to rejects as if they were booked.

Delayed labels: a case contributes as censored until `label_available_at` \(\le C\); after that it contributes a complete 90-day binary. Conservative analyses require 125 days of potential follow-up before a \(Y=0\) is accepted.

**Sensitivity analyses.**
- Complete-case logit on the 21,600 mature labels only (documents the bias from dropping the 3,600).
- Inverse-probability-of-activation weights using the competing-exit model; compare weighted vs unweighted \(\hat\pi\).
- Inverse-probability-of-maturity / of-feed-arrival weights among activations, with `source_system`, partner flag, region, and activation month.
- Transfer: (i) treat all transfers as competing exits; (ii) include linked follow-up only; (iii) Manski-style bounds that assign unlinked and missing-feed activations to \(\{0,1\}\).
- Policy-threshold design: re-estimate \(\hat\pi\) separately before/after 1 July 2025 and, as an explicitly weaker analysis, use the threshold shift as a selection shock for Alternative B.
- Recode-rejects-as-zero (the requested informal target) as a *negative control*: it should look “better” and is treated as a biased comparator, not a candidate production target.

**Assumptions.**
- Independent censoring of the 90-day clock given \(X_\tau\), activation month, and `source_system`: **partially testable** (censoring hazard vs risk score, channel, partner flag; calendar bunching of the 3,600).
- Delayed-feed MAR given those covariates and `label_available_at` patterns: **partially testable**.
- No unmeasured selection into activation (needed to transport \(\hat\pi\) to rejected files, or for IPW to recover a population default risk): **fundamentally untestable**. The July 2025 policy change is a limited, testable *shift* in selection, not a proof of unconfoundedness.
- Linked transfers are exchangeable with unlinked given observables: **partially testable** on covariates, not on outcomes for the unlinked 40%.
- Permanently missing partner feeds are MAR: **largely untestable** without an external collections audit; bound it.

## 4. Prefix extraction

Work from the event log after timestamp parsing, not from the wide warehouse snapshot.

**No-future filter.** For each case and each \(\tau\), keep events with `time:timestamp` \(\le \tau\) and \(\le C\). Drop every attribute that is documented as post-decision or post-activation (`final_limit`, `decision_reason`, `collection_status`, any `default_90d` / `label_available_at` used as a feature). `risk_score` is the last value on a retained event, not the case-level last value.

**Fixed event-count prefixes.** After activity-name harmonization and deduplication, take the first \(k\) events. Implement with `pm4py.get_prefixes_from_log` on the *harmonized, pre-terminal* log, then discard any prefix whose last event is already a terminal or post-decision activity. If the raw case has fewer than \(k\) events:
- if it terminated (Reject / Withdraw / Transfer) before \(k\), it contributes to the competing-exit model at the last available length and is out of the primary default model;
- if it is still open and short, it is a short-prefix observation, flagged `prefix_truncated=1`, and is not padded with fictional activities.

**Elapsed-time prefixes.** \(\tau = T_{\text{start}}+t\). Keep events in \((T_{\text{start}},\tau]\). Same terminal and column filters. A nightly `documents_total` snapshot is **not** an elapsed-time prefix: include a document only if its own upload event timestamp is \(\le\tau\) (same-calendar-day later uploads are future).

**Document loops.** Repeated `request documents` \(\to\) `Credit Review` cycles that occur *at or before* \(\tau\) are valid control-flow and rework features (counts, time in loop, whether the last review is waiting on documents). Loops after \(\tau\) are invisible.

**Activity renaming and duplicates (15 Oct 2025).** Maintain an explicit many-to-one map from post-migration names to a canonical vocabulary (`Application Started`, `Identity/KYC Check`, `Credit Review`, `Documents Requested`, `Accepted`, `Rejected`, `Withdrawn`, `Transferred`, `Contract Signed`, `Account Activated`, plus collections/default events that must never appear in prefixes). Apply the map *before* prefixing so \(k\) is comparable across eras. After mapping, drop exact duplicates on `(case, canonical activity, timestamp, org:resource)` retaining one row. Unmapped rare names stay as `UNMAPPED:*` and are monitored, not silently folded into `Credit Review`.

**Short cases and early terminals.** The early-warning system is defined only while the file is still live. Do not generate a \(k=4\) prefix for a three-event reject by carrying the reject into the prefix; that trains the model on the decision itself.

## 5. Process-aware features

All features below must be computable from \(\{e : e.\text{time}\le\tau\}\) plus *historical* reference data known at \(\tau\).

**Static case attributes (frozen at start).** `case:channel`, `case:region`, `case:requested_amount`, start month/dow, `source_system` at first event, pre/post 1 July 2025 policy regime of the *start* date (a cohort tag, not a future policy).

**Prefix-derived control-flow.** Canonical activity counts; occurrence of first `Credit Review`; number of `Documents Requested` \(\to\) `Credit Review` rework cycles; position of last activity; whether KYC is complete; variant ID computed on the prefix only (`pm4py.get_variants` on the prefix log, not the full log); optional small-DFG node/edge indicators from a DFG *fit on training prefixes* (`pm4py.discover_dfg`).

**Timing.** Elapsed time from start to \(\tau\); sojourn in KYC and in Credit Review; time since last event; intra-loop duration. Service vs waiting decomposition is allowed only if computed on the prefix (`pm4py.insert_case_service_waiting_time` on the filtered frame), and waiting is interpreted as time between that case’s own events, not as a claim about the true queue unless a historical queue feature is added.

**Resource / queue (as-of \(\tau\)).** Number of distinct `org:resource` in the prefix; last resource; last resource’s *historical* experience (see leakage table); cases by the same resource that are open at \(\tau\) (requires a point-in-time scan of *other* cases’ events \(\le\tau\)); arrival intensity in the same region/channel over the previous 7 days as of \(\tau\).

**Rework.** Document-request count, consecutive review repeats, oscillating KYC/review flags.

**Cohort / calendar.** Policy era; post-migration flag if \(\tau\) is after 15 Oct 2025; month-of-year; days to extraction (for diagnosis only, **not** a production feature).

**Updated numeric attributes.** Last `risk_score` at or before \(\tau\); number of risk-score updates in the prefix; requested amount (static). Never `final_limit`.

**Features that need historical reference data (not the case row alone).** Resource tenure as-of event time (HR snapshot or first-seen date in a *prior* period); queue length and arrival rates; training-only DFG/variant encoders; policy-threshold tables by date. Extraction-time employee experience is forbidden.

`pm4py.extract_temporal_features_dataframe` may be used on the **prefix frame only**, as a convenience for sojourn/waiting summaries, with the same no-future filter.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Post-decision; encodes Accept and exposure size | Populated only after final credit decision, after \(\tau\) | Drop | Not known at early-warning time; almost a proxy for activation |
| `decision_reason` | Direct view of Accept/Reject and policy text | At or after Accept/Reject | Drop | Target-adjacent and post-prefix |
| `collection_status` | Often reveals default or delinquency path | Updated after activation | Drop | Outcome leakage |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded, later reviews) | Direct path-to-label and post-\(\tau\) control flow | Event timestamp \(\le\tau\) | Drop from feature log; use only to build labels/censoring | Prefix extraction must filter the log, not just “not use the column” |
| `documents_total` (nightly snapshot) | Same-day later uploads after nominal \(\tau\) | Use document *events* with timestamp \(\le\tau\), not the nightly total | Repair | Snapshot is not an as-of feature |
| Updated `risk_score` | Last-in-case score can be post-review or post-decision | Last score on events \(\le\tau\) | Repair | Keep the as-of score; drop later revisions |
| Resource experience at extraction | Future promotions/tenure; survivors stay employed | Experience as of event time from a dated snapshot or first-seen proxy | Repair or drop | Extraction-time tenure is not a prefix attribute |
| `default_90d` as a feature | Is the label | Never a covariate | Drop | Direct leakage |
| `label_available_at` as a feature | Encodes that a mature outcome exists and when the feed arrived; correlated with default and partner missingness | Use only to define identifiability of \(Y\), after split cutoffs | Drop as feature | Selection-into-label leakage |
| `data_extract_time` / time-to-extract | Almost a function of late 2025 starts (immature labels) | Study metadata only | Drop as feature | Teaches the model the extraction artifact |
| Full-log variants / DFG / waiting times | Paths that include Accept→Activate→Default | Fit/apply only on prefix logs | Repair | Process discovery on complete traces leaks terminals |
| `pm4py.split_train_test` random split | Mixes policy eras and lets later operational practice inform earlier cases | Temporal split by start time (Section 7) | Drop as primary splitter | Convenience baseline only |
| Treating reject/withdraw/open as \(Y=0\) | Changes the estimand; learns the policy | Do not recode | Drop that coding | Default is undefined without activation |
| Transfer linkage used as if complete | 40% missing follow-up; linked 60% not a random sample | Flag linkage; bound or model missingness | Repair | Selective observation |
| Partner missing feed as \(Y=0\) | MNAR outcome | Censor or bound | Repair | Permanently missing \(\ne\) survived |
| Policy regime after 1 Jul 2025 applied to earlier starts | Future policy does not apply to earlier files | Regime from start date or from \(\tau\), never from extraction | Repair | Calendar feature must be as-of |

## 7. Validation design

**Why a random case split is misleading.** Cases started in 2024 and late 2025 share a random fold, so the model is trained on post-policy, post-migration behavior and tested on pre-policy files (and vice versa). Long-running cases place late events and matured labels next to early prefixes from the same operational era. Random splits also hide that the 3,600 immature activations are almost all recent: complete-case metrics on a random fold over-represent early bookings and under-represent current policy. Temporal order is part of the data-generating process.

**Primary split (by `Application Started` date, not by activation date and not by label).** After requiring that a training label be identifiable by the *training cutoff* (not by the global extract):

| Fold | Case start | Role | Label rule |
|---|---|---|---|
| Train | 1 Jan 2024 – 31 Mar 2025 | Fit | Identifiable by 31 Aug 2025 (125-day buffer after a late-March activation window) |
| Validation | 1 Apr 2025 – 30 Jun 2025 | Tune, calibrate | Identifiable by 30 Nov 2025 |
| Test-A (policy shift) | 1 Jul 2025 – 14 Oct 2025 | First backtest | Identifiable by 15 Feb 2026 extract |
| Test-B (migration + immaturity) | 15 Oct 2025 – 31 Dec 2025 | Stress / partial labels | Report complete-case *and* censored metrics; many \(Y\) not identifiable |

Walk-forward monthly backtests inside 2025 with the same identifiability rule. Never use `pm4py.split_train_test` except as a published “invalid comparator.”

**Policy change and migration.** Fit with a start-era indicator and interactions (risk score × post-July, channel × post-July). Report Test-A vs train as the policy-shift evaluation. Harmonize activities before scoring Test-B; also run an un-harmonized diagnostic to measure rename breakage. Do not pool pre/post July for the headline number without showing both.

**Label maturity.** A test case without identifiable \(Y\) is not scored on binary AUC; it enters time-dependent / censored metrics. Do not wait until the global extract to label the training fold (that uses future feed arrivals).

**Calibration and shift.** Reliability plots and ECE/Brier on mature activations, by fold, channel, region, amount decile, partner vs direct, pre/post policy, pre/post migration. Population Stability Index on \(X_\tau\) and on \(\hat\pi\). Activation rate and default rate among activations, by fold — if activation falls after July 2025, \(\hat\pi\) can stay calibrated *inside* activations while portfolio default counts move.

**Metrics (matched to the target).**
- Primary (activation-conditional): AUPRC and average precision (12.5% base rate), AUROC as secondary, Brier, ECE, calibration slope/intercept, recall at fixed review capacity.
- With censoring: time-dependent AUC at 90d, integrated Brier, observed vs predicted default among cases with full 125-day potential follow-up.
- Competing-exit companion: log-loss / Brier for \(\Pr(\text{Activate}\mid X_\tau)\) and cumulative incidence of Activate-and-default.
- Subgroups as above; cluster-robust or case-blocked bootstrap because multiple \(k\) prefixes share a case.
- Do not optimize AUROC on the 21,600 export as the study success criterion.

## 8. Limitations and decision-use boundary

**The study can claim.** Among applications that the *observed* policy activates, early prefixes contain associations with 90-day post-activation default; those associations can be temporally validated across a known policy break and a known migration; competing-exit models can forecast booking volumes times conditional default; missing-feed and transfer uncertainty can be bounded.

**The study cannot claim.** That a rejected, withdrawn, or open file “would not have defaulted”; that \(\hat\pi\) is a counterfactual default probability under a more lenient policy; that partner-originated booked accounts with no feed survived; that resource “skill” is causal; that the model is stable under its own deployment.

**Three layers that must stay separate.**
- *Predictive association* on selected, matured activations: what the primary model estimates.
- *Selection effects*: who is activated is a function of KYC, risk score, documents, channel, and the July 2025 thresholds — the same signals that predict default.
- *Counterfactual default risk* if a reject had been booked: not identified here.

**At least three deployment feedback loops.**
1. Underwriters (or a rules engine) start using \(\hat\pi\) in the accept/limit decision → the activation set changes → the selected-sample relationship between \(X_\tau\) and \(Y\) shifts (performativity).
2. A further policy or limit-table change, like 1 July 2025, alters both \(P(\text{Activate}\mid X)\) and \(P(Y\mid X,\text{Activate})\).
3. Collections and reporting respond to scored “high risk” bookings (earlier contact, different `collection_status` paths, faster or slower default feeds), which changes observed \(Y\) and missingness.

**Decision-use boundary.** Use \(\hat\pi\) only as an *underwriting* early-warning input *conditional on intending to activate*, with a separate activation model or human policy, calibrated inside eras, and with rejects left unlabeled. Do not auto-decline on \(\hat\pi\) as if it were P(default) for every start. Do not put the score into collections treatment if that treatment defines the label. Re-validate after any threshold change and after any activity-taxonomy change.

import numpy as np
import pm4py
from datetime import timedelta

HORIZON = timedelta(days=90)
POLICY_ON = pd.Timestamp("2025-07-01")
MIGRATE_ON = pd.Timestamp("2025-10-15")
TERMINALS = {"Accepted", "Rejected", "Withdrawn", "Transferred",
             "Contract Signed", "Account Activated"}

              "default_90d", "label_available_at", "data_extract_time"]

NAME_MAP = {"ID Check": "Identity/KYC Check", "KYC": "Identity/KYC Check",
            "Credit Review v2": "Credit Review", "Docs Requested": "Documents Requested"}

df = pd.read_csv("applications_events.csv", parse_dates=[
    "time:timestamp", "label_available_at", "data_extract_time"])
df["concept:name"] = df["concept:name"].replace(NAME_MAP)
df = df.sort_values(["case:concept:name", "time:timestamp"])
df = df.drop_duplicates(["case:concept:name", "concept:name",
                         "time:timestamp", "org:resource"])
df = pm4py.format_dataframe(
    df, case_id="case:concept:name", activity_key="concept:name",
    timestamp_key="time:timestamp")

def case_status(g, cutoff=EXTRACT):
    g = g[g["time:timestamp"] <= cutoff]
    acts, t0 = set(g["concept:name"]), g["time:timestamp"].min()
    t_act = g.loc[g["concept:name"].eq("Account Activated"), "time:timestamp"].min()
    lab = g["default_90d"].dropna()
    avail = g["label_available_at"].dropna()
    y, mature = np.nan, False
    if pd.notna(t_act):
        # Identifiable non-default requires horizon + feed delay, not a missing feed.
        mature = (bool(len(avail)) and avail.iloc[-1] <= cutoff) or (
            t_act + HORIZON + FEED_BUFFER <= cutoff and len(lab) > 0)
        if mature and len(lab):
            y = float(lab.iloc[-1])
    terminal = next((a for a in ["Rejected", "Withdrawn", "Transferred",
                                 "Account Activated"] if a in acts), "OPEN")
    return pd.Series(dict(start=t0, t_act=t_act, terminal=terminal, y=y,
                          mature=mature, era=np.where(t0 < POLICY_ON, "pre", "post"),
                          migrated=t0 >= MIGRATE_ON))

cases = df.groupby("case:concept:name", sort=False).apply(case_status).reset_index()
# Cohort census — must sum to 48,000 when run on the described extract.
cohort = {
    "started": len(cases),
    "rejected": int((cases.terminal == "Rejected").sum()),
    "withdrawn": int((cases.terminal == "Withdrawn").sum()),
    "transferred": int((cases.terminal == "Transferred").sum()),
    "open": int((cases.terminal == "OPEN").sum()),
    "activated_immature": int(((cases.terminal == "Account Activated") & ~cases.mature).sum()),
    "activated_y0": int((cases.y == 0).sum()),
    "activated_y1": int((cases.y == 1).sum()),
}

def temporal_split(start):
    if start <= pd.Timestamp("2025-03-31"):
        return "train"
    if start <= pd.Timestamp("2025-06-30"):
        return "val"
    if start < MIGRATE_ON:
        return "test_policy"
    return "test_migrate"

cases["split"] = cases["start"].map(temporal_split)
# Convenience only — do not use for reported metrics:
# _train, _test = pm4py.split_train_test(pm4py.convert_to_event_log(df), 0.8)

K = 3
live = df[~df["concept:name"].isin(LEAKY_EVENTS)]
log = pm4py.convert_to_event_log(live)
pref_log = pm4py.get_prefixes_from_log(log, K)
pref = pm4py.convert_to_dataframe(pref_log)
pref = pref.merge(cases[["case:concept:name", "start", "t_act", "terminal",
                         "y", "mature", "era", "split"]], on="case:concept:name")
# Elapsed-time prefixes (parallel clock): events with timestamp <= start + t.
# t_h = pd.Timedelta("72h"); time_pref = df.merge(cases[["case:concept:name","start"]])
# time_pref = time_pref[time_pref["time:timestamp"] <= time_pref["start"] + t_h]

# Prefix as-of: last risk_score on retained events; never post-prefix columns.
assert not set(LEAKY_COLS) & set(pref.columns) or True
feat_cols = [c for c in pref.columns if c not in LEAKY_COLS]
