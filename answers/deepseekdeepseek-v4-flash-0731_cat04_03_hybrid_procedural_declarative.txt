# 1. Policy Interpretation and Conflict Resolution

Material assumptions:

- `Receive Onboarding Request` and `Close Onboarding` occur exactly once per case.
- `Activate Vendor` marks an accepted case; `Reject Vendor` marks a rejected case.
- `Classify Risk` is not a final outcome; `Activate Vendor` and `Reject Vendor` are the final business outcomes for R3.
- In R9, “the applicable approval” means `Manager Approval` for the low-risk route and `Compliance Approval` for the high-risk route.
- `org:resource` is the resource attribute; if it is missing, resource checks are incomplete and require manual review.
- R11 is interpreted as: if `Change Bank Details` occurs after activation and before the single `Release First Payment`, then `Suspend Vendor` must follow and another `Verify Bank Account` must occur before that release.

R5/R6 conflict resolutions:

1. **Strict R5 resolution**: `Obtain Legal Opinion` must precede `Activate Vendor` whenever `Sanctions Escalation` occurred. R6 emergency activations are treated as external exceptions that must be audited outside the event log. We adopt this resolution in the implemented model.
2. **R6-friendly resolution**: emergency activation before legal opinion is allowed only if a separate, externally maintained authorization list includes the case; the opinion must still arrive within 24 hours. The event log cannot verify this because it has no emergency or authorization attribute.
3. **Attribute-based compromise**: add an explicit `Emergency Authorization` event/attribute when R6 is used; without it, R5 is enforced.

Compliance risk of choosing strict R5: legitimate emergency activations will be reported as conformance violations, even if they were jointly authorized outside the system. This is intentional in our chosen design; the audit team must maintain a separate exception register.

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}

zeta = 2.0
```

Temporal deviations are warnings because R12 explicitly says these expectations are “normative enough to flag but not automatically reject.” A long legal opinion or a delayed first payment may still be valid operationally; temporal profile conformance should not make a case non-fitting by itself.

# 7. Resource- and Data-Aware Checks

```python
from datetime import timedelta

def get_resource(ev):
    return ev.get("org:resource")

def get_time(ev):
    return ev.get("time:timestamp")

def check_r9(log):
    issues = []
    for case in log:
        case_id = case.attributes.get("concept:name")
        by_act = {ev["concept:name"]: ev for ev in case}

        vba = by_act.get("Verify Bank Account")
        manager = by_act.get("Manager Approval")
        compliance = by_act.get("Compliance Approval")
        cmd = by_act.get("Capture Master Data")
        activate = by_act.get("Activate Vendor")

        # Verify Bank Account must differ from the applicable approval.
        for approval in (manager, compliance):
            if approval is not None:
                if vba is None:
                    issues.append(("incomplete", case_id, "Verify Bank Account missing"))
                elif get_resource(vba) is None or get_resource(approval) is None:
                    issues.append(("incomplete", case_id, "resource attribute missing"))
                elif get_resource(vba) == get_resource(approval):
                    issues.append(("fail", case_id,
                                   f"Verify Bank Account and {approval['concept:name']} have same resource"))

        # Capture Master Data must differ from Activate Vendor.
        if cmd is not None and activate is not None:
            if get_resource(cmd) is None or get_resource(activate) is None:
                issues.append(("incomplete", case_id, "resource attribute missing"))
            elif get_resource(cmd) == get_resource(activate):
                issues.append(("fail", case_id,
                               "Capture Master Data and Activate Vendor have same resource"))

    return issues

def check_r5_r6(log, authorized_emergency_case_ids=None):
    """
    Strict R5 is the default.
    If an emergency authorization list is supplied, R6 can be evaluated only for cases
    in that list; otherwise emergency activation is a violation.
    """
    if authorized_emergency_case_ids is None:
        authorized_emergency_case_ids = set()

    issues = []
    for case in log:
        case_id = case.attributes.get("concept:name")
        times = {}
        for ev in case:
            times[ev["concept:name"]] = get_time(ev)

        if "Sanctions Escalation" not in times or "Activate Vendor" not in times:
            continue
        if "Obtain Legal Opinion" not in times:
            issues.append(("fail", case_id, "Sanctions Escalation without Obtain Legal Opinion"))
            continue

        if times["Activate Vendor"] >= times["Obtain Legal Opinion"]:
            continue  # opinion precedes activation: strict R5 satisfied

        if case_id not in authorized_emergency_case_ids:
            issues.append(("fail", case_id,
                           "Activate Vendor before Obtain Legal Opinion without external emergency authorization"))
        else:
            if times["Obtain Legal Opinion"] - times["Activate Vendor"] > timedelta(hours=24):
                issues.append(("fail", case_id, "Emergency legal opinion exceeded 24 hours"))

    return issues
```

If `org:resource` or `time:timestamp` is missing, the check returns `incomplete` rather than pass; the case must be manually reviewed. The event log does not contain an emergency attribute or joint authorization, so `check_r5_r6` requires an external authorization list under an R6-friendly policy.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement across layers**: many constraints appear both in the process tree and DECLARE, e.g. R1, R7, R8. This is intended to provide defense-in-depth, but it can make one small model change silently alter another layer’s meaning.
- **Loops and post-activation changes**: the clarification loop and post-activation bank-details loop interact with R10. Because `Release First Payment` is at most once, `Change Bank Details` after release cannot have a “later release”; the process tree therefore only allows it before release. If operations need changes after release, R10 must be revisited.
- **Vacuity in declarative rules**: rules such as `precedence(("Obtain Legal Opinion", "Activate Vendor"))` are vacuous when `Obtain Legal Opinion` does not occur. This is why `response(Sanctions Escalation, Obtain Legal Opinion)` is also needed; one rule alone is insufficient.
- **Missing case attributes**: resource, timestamp, and emergency authorization attributes are not guaranteed. Missing resource attributes make four-eyes checks impossible; missing timestamps make temporal checks impossible.
- **Timestamp-only limitations**: temporal profiles detect only elapsed time, not causal order. They cannot know why an activity was late or whether delay was due to an emergency exception.
- **Support/confidence metadata**: the values `1.0` and `0.99` are manually declared normative settings, not discovered statistical support. They should not be read as “99% of historical traces complied”; otherwise conformance output becomes misleading.

# 10. Deployment Recommendation

- **Canonical procedural representation**: use the ProcessTree in Section 3 as the normative control-flow skeleton.
- **Authoritative policy layer**: use DECLARE for hard event-level constraints, log skeleton for occurrence-count constraints, and the resource/data layer for segregation-of-duties and external emergency authorization. Temporal profile should be advisory.
- **Recommended conformance order**:
  1. Check procedural fitness with `pm4py.conformance_process_tree` or equivalent.
  2. Run DECLARE conformance with `pm4py.conformance_declare`.
  3. Run log-skeleton conformance with `pm4py.conformance_log_skeleton`.
  4. Run resource and data-aware checks from Section 7.
  5. Run temporal profile conformance with `zeta = 2.0`, reporting warnings only.
- **Surfacing findings**: show grouped, per-case violations with the layer that detected them. Distinguish hard violations from temporal warnings. Mark cases with missing resource/timestamp attributes or potential R6 emergency authorizations as “needs manual review” rather than silently passing them.
