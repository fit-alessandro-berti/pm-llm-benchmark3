from collections import defaultdict

def is_external(obj_id): return str(obj_id).startswith("EXT")

def event_signature(ev):
    objs = tuple(sorted((t, is_external(i)) for t,i in ev["objects"]))
    return (ev["activity"], objs)

def object_profile(objects):
    uniq = set((t, i) for t,i in objects)
    cnt = defaultdict(int)
    for t,i in uniq: cnt[(t,is_external(i))]+=1
    return tuple(sorted((t,e,n) for (t,e),n in cnt.items()))

def o2o_profile(edges):
    return tuple(sorted((e["src_type"], e["src_ext"], e["qualifier"], e["tgt_type"], e["tgt_ext"], e.get("context_type","")) for e in edges))

def motif_profile(events, o2o_edges):
    acts = [e["activity"] for e in events]
    ext_order_log = any(e["activity"] in {"Pack Package","Dispatch"} and any(t=="Order" and is_external(i) for t,i in e["objects"]) for e in events)
    ext_order_fin = any(e["activity"] in {"Issue Invoice","Record Payment"} and any(t=="Order" and is_external(i) for t,i in e["objects"]) for e in events)
    quals = {e["qualifier"] for e in o2o_edges}
    return tuple(sorted([
       ("pack_count", acts.count("Pack Package")),
       ("dispatch_count", acts.count("Dispatch")),
       ("payment_count", acts.count("Record Payment")),
       ("return_count", acts.count("Return Item")),
       ("split_package", acts.count("Pack Package") > 1),
       ("consolidated_delivery", acts.count("Dispatch")==1 and acts.count("Pack Package")>1),
       ("split_delivery", acts.count("Dispatch")>1),
       ("cross_order_logistics", ext_order_log),
       ("cross_order_financial", ext_order_fin),
       ("replacement_or_removal", bool({"replaces","removed_before_dispatch"} & quals)),
       ("partial_payment", bool({"partially_settles","completes_settlement"} & quals)),
       ("return_repack", acts.count("Return Item")>0 and acts.count("Pack Package")>1)
    ]))

def canonical_signature(events, objects, o2o_edges):
    layers = defaultdict(list)
    for ev in events: layers[ev["timestamp"]].append(event_signature(ev))
    event_seq = tuple(tuple(sorted(v)) for _,v in sorted(layers.items()))
    return (event_seq, object_profile(objects), o2o_profile(o2o_edges), motif_profile(events, o2o_edges))

## 1. Equivalence design space

I treat an execution as an object-centric graph with:

- events: activity label, timestamp, and event-to-object incidences;
- objects: object type and local/external flag, where identifiers beginning with `EXT` are external;
- O2O relations: qualified links such as `packs`, `carries`, `bills`, `settles`, `replaces`, `removed_before_dispatch`, `partially_settles`, and `completes_settlement`;
- a lead object type: `Order`.

Local identifiers are not semantic unless they encode externality or a supplied qualifier.

### 1.1 Activity-sequence equivalence

**Definition.** Two executions are equivalent if their sequences of activity labels are identical. Operationally, map each event to its activity name and compare the resulting sequence. If timestamps can tie, compare a sequence of multisets of activity labels grouped by timestamp, not an arbitrary total order.

**Invariants preserved.** Activity names, activity order, and repeated activities.

**Information discarded.** All object information: object types, multiplicities, external objects, E2O incidence, O2O qualifiers, amounts, and lifecycle semantics.

**Equivalence properties.** Reflexive, symmetric, and transitive because it is equality of a canonical label sequence.

**Concurrency handling.** Same-timestamp events are treated as unordered within their timestamp layer. If the input has no timestamps, the listed order is treated as total.

### 1.2 Local typed structural equivalence under identifier renaming

**Definition.** Two executions are equivalent if there exists a bijection between their local objects of the same type such that:

1. the activity sequence is identical;
2. for each event, the multiset of local object types participating in that event is identical;
3. local object multiplicities by type are identical.

This is a local-view typed isomorphism. It ignores `EXT` flags and O2O qualifiers.

**Invariants preserved.** Event order, local object types, local object multiplicities, repeated activities, and local E2O incidence by type.

**Information discarded.** External objects, O2O qualifiers, local identifiers, amounts, and business meaning attached to qualified relations.

**Equivalence properties.** Reflexive, symmetric, and transitive because it is equality of a canonical local typed signature.

**Concurrency handling.** Same-timestamp events are compared as multisets of event signatures. Each event signature is `(activity, sorted multiset of local object types)`.

### 1.3 Business-semantic equivalence

**Definition.** Two executions are equivalent if their canonical business graphs are equal. The graph preserves:

- event order or timestamp layers;
- activity labels;
- local and external object types;
- object multiplicities;
- E2O incidence by object type and external flag;
- O2O qualified edges;
- derived lifecycle motifs such as split packages, consolidated delivery, cross-order sharing, replacement/removal, return/repack, and partial payment.

This is the preferred equivalence used below.

**Invariants preserved.** Business-relevant structure: shared external objects, package splitting, delivery consolidation or splitting, payment multiplicity and settlement qualifiers, item replacement/removal, and reverse-logistics motifs.

**Information discarded.** Local identifiers, exact timestamps when only order matters, non-semantic attribute values, and object identities not encoded by type, externality, or qualifiers.

**Equivalence properties.** Reflexive, symmetric, and transitive because it is equality of a deterministic canonical signature.

**Concurrency handling.** Same-timestamp events form an antichain. Within each timestamp layer, event signatures are sorted lexicographically before inclusion in the canonical signature.

### 1.4 Optional fourth relation: external-aware typed structural equivalence

A useful intermediate relation is local typed structural equivalence plus preservation of external object flags, but without O2O qualifiers. It separates X5 and X6 from X1 because external objects participate in different events, but it does not yet interpret qualified relations such as replacement or partial settlement.

## 2. Canonical signatures

The following Python-like scheme produces the signature used for business-semantic equivalence. It is invariant to local identifier renaming because identifiers are replaced by `(object_type, external_flag)`.

```python
from collections import defaultdict

def is_external(obj_id: str) -> bool:
    return str(obj_id).startswith("EXT")

def event_signature(event):
    # event: {"activity": str, "timestamp": str, "objects": [(type, id), ...]}
    objs = tuple(sorted(
        (obj_type, is_external(obj_id))
        for obj_type, obj_id in event["objects"]
    ))
    return (event["activity"], objs)

def object_profile(objects):
    # objects: [(type, id), ...], may contain duplicates across events
    unique = set((obj_type, obj_id) for obj_type, obj_id in objects)
    counts = defaultdict(int)
    for obj_type, obj_id in unique:
        counts[(obj_type, is_external(obj_id))] += 1
    return tuple(sorted(
        (obj_type, ext_flag, count)
        for (obj_type, ext_flag), count in counts.items()
    ))

def o2o_profile(edges):
    # edge: {"src_type", "src_ext", "qualifier", "tgt_type", "tgt_ext", "context_type"}
    return tuple(sorted(
        (
            e["src_type"],
            e["src_ext"],
            e["qualifier"],
            e["tgt_type"],
            e["tgt_ext"],
            e.get("context_type", ""),
        )
        for e in edges
    ))

def motif_profile(events, edges):
    activities = [e["activity"] for e in events]

    ext_order_logistics = any(
        e["activity"] in {"Pack Package", "Dispatch"}
        and any(
            obj_type == "Order" and is_external(obj_id)
            for obj_type, obj_id in e["objects"]
        )
        for e in events
    )

    ext_order_financial = any(
        e["activity"] in {"Issue Invoice", "Record Payment"}
        and any(
            obj_type == "Order" and is_external(obj_id)
            for obj_type, obj_id in e["objects"]
        )
        for e in events
    )

    qualifiers = {e["qualifier"] for e in edges}

    return tuple(sorted([
        ("pack_count", activities.count("Pack Package")),
        ("dispatch_count", activities.count("Dispatch")),
        ("payment_count", activities.count("Record Payment")),
        ("return_count", activities.count("Return Item")),
        ("split_package", activities.count("Pack Package") > 1),
        ("consolidated_delivery",
         activities.count("Dispatch") == 1 and activities.count("Pack Package") > 1),
        ("split_delivery", activities.count("Dispatch") > 1),
        ("cross_order_logistics", ext_order_logistics),
        ("cross_order_financial", ext_order_financial),
        ("replacement_or_removal",
         bool({"replaces", "removed_before_dispatch"} & qualifiers)),
        ("partial_payment",
         bool({"partially_settles", "completes_settlement"} & qualifiers)),
        ("return_repack",
         activities.count("Return Item") > 0 and activities.count("Pack Package") > 1),
    ]))

def canonical_signature(events, objects, o2o_edges):
    layers = defaultdict(list)
    for event in events:
        layers[event["timestamp"]].append(event_signature(event))

    # Same-timestamp events are unordered.
    event_seq = tuple(
        tuple(sorted(event_sigs))
        for _, event_sigs in sorted(layers.items())
    )

    return (
        event_seq,
        object_profile(objects),
        o2o_profile(o2o_edges),
        motif_profile(events, o2o_edges),
    )
```

Two executions are business-semantically equivalent exactly when this tuple is equal.

## 4. Cluster interpretations

### `SEM_STANDARD`

**Signature.** One order, two items, one package, one delivery, one invoice, one payment; no external objects; no special qualifiers.

**Business behavior.** Normal direct fulfillment: the order is packed once, dispatched once, invoiced once, and paid once.

**Risks or opportunities.** Low operational risk. Useful as a baseline for detecting deviations.

**Poor flattening.** Activity-only flattening cannot distinguish X1 from X5, X6, or X7. Order-case flattening may also hide item/package multiplicities if object counts are not preserved.

**Stability.** Stable under identifier repair. Not stable if external flags or O2O qualifiers are missing, because X5–X7 may falsely enter this cluster.

### `SEM_SPLIT_PACK_CONSOLIDATED`

**Signature.** Two Pack events, one Dispatch event, two Packages, one Delivery; each package packs one item; delivery carries both packages.

**Business behavior.** Inventory or packaging constraints force split packing, but shipment is consolidated.

**Risks or opportunities.** Risk of partial package loss or mismatched package tracking. Opportunity to optimize warehouse packing while preserving one customer delivery.

**Poor flattening.** If only the Dispatch event is retained, package splitting disappears. If Pack events are collapsed, object-level fulfillment detail is lost.

**Stability.** Stable if package counts and `carries` relations are preserved. Fragile if pack events are merged during data repair.

### `SEM_SPLIT_PACK_SPLIT_DELIVERY_PARTIAL`

**Signature.** Two Pack events, two Dispatch events, two Payment events; two Packages and two Deliveries; payments partially and completely settle one invoice.

**Business behavior.** The order is fulfilled asynchronously, and settlement is also asynchronous or installment-based.

**Risks or opportunities.** Higher risk of reconciliation errors, credit exposure, and delivery tracking complexity. Opportunity to detect multi-shipment and multi-payment behavior.

**Poor flattening.** Payment as a single amount attribute loses the two-payment structure. Delivery consolidation assumptions lose split shipments.

**Stability.** Stable if payment multiplicity and settlement qualifiers are preserved. Less stable if amounts are repaired into one payment record.

### `SEM_CROSS_ORDER_LOGISTICS_SHARING`

**Signature.** Locally standard order, items, package, delivery, invoice, and payment, but Pack and Dispatch include an external Order and external Item.

**Business behavior.** This order shares a physical shipment with another order. The invoice is still local to this order.

**Risks or opportunities.** Risk: delivery attribution, customer communication, and reverse logistics become cross-order. Opportunity: shipping-cost optimization.

**Poor flattening.** A local Order-centric trace looks identical to X1. External participation is invisible unless `EXT` objects are preserved.

**Stability.** Stable only if external object flags are retained. If external objects are removed as noise, this cluster collapses into `SEM_STANDARD`.

### `SEM_CROSS_ORDER_FINANCIAL_SHARING`

**Signature.** Locally standard logistics, but Issue Invoice and Record Payment include an external Order.

**Business behavior.** This order shares an invoice or payment with another order. Logistics remain local.

**Risks or opportunities.** Risk: billing allocation, dunning, refunds, and credit checks may be ambiguous. Opportunity: consolidated billing efficiency.

**Poor flattening.** A local financial trace looks standard. External Order participation is lost if only local objects are retained.

**Stability.** Stable if external flags and, ideally, allocation semantics are preserved. Without allocation, payment settlement is structurally present but financially ambiguous.

### `SEM_ITEM_REPLACEMENT_REMOVAL`

**Signature.** Standard activity sequence and counts, but Dispatch includes an Item object and O2O edges encode `replaces` and `removed_before_dispatch`.

**Business behavior.** One item was substituted or removed before dispatch, while the order-level invoice and payment remain standard.

**Risks or opportunities.** Risk: fulfillment accuracy, customer dissatisfaction, inventory mismatch, and auditability. Opportunity: detect substitutions and monitor item-level fulfillment deviations.

**Poor flattening.** Activity-only flattening makes this look exactly like X1. Even typed local flattening may miss it if the extra Item in Dispatch is treated as noise.

**Stability.** Stable if O2O qualifiers are maintained. If qualifiers are stripped, it may collapse toward `SEM_STANDARD`, depending on whether the Dispatch Item incidence is preserved.

### `SEM_RETURN_REPACK`

**Signature.** Return and Inspect activities after initial dispatch; second Pack and Dispatch; Package replaces Package for an Item; one invoice and one payment.

**Business behavior.** An item was returned, inspected, repacked, and reshipped.

**Risks or opportunities.** Risk: reverse-logistics cost, duplicate package tracking, and delivery-status confusion. Opportunity: service recovery and return-rate monitoring.

**Poor flattening.** Case-centric flattening may show extra events but not object-level replacement. Package identity is essential.

**Stability.** Stable if Return/Inspect events and package replacement qualifiers are preserved. If returns are collapsed into an event attribute, the object-centric reverse-logistics motif is lost.

## 5. Borderline cases

### X1 versus X2

Under activity-sequence, local typed structural, and business-semantic equivalence, X1 and X2 are equivalent. They differ only in local identifiers and the order of two identical `Add Item` events. A defensible disagreement arises only if raw identifiers or first-seen item order are treated as meaningful. That is usually wrong unless identifiers encode business identity.

### X1 versus X5

Activity-sequence equivalence groups them together. Local typed structural equivalence also groups them together because the local event-object pattern is standard. Business-semantic equivalence separates them because X5 includes external Order and Item objects in logistics events. The disagreement is between a local process view and an enterprise object view.

### X1 versus X6

This is similar to X1 versus X5, but the external object appears in financial events. Activity-only and local typed structural views treat X6 as standard. Business-semantic view separates it because invoice and payment are shared with another order. The disagreement matters for finance compliance.

### X1 versus X7

Activity-sequence equivalence groups them together. Local typed structural equivalence separates them if the extra `Item` in Dispatch is preserved. Business-semantic equivalence separates them because O2O qualifiers encode replacement and removal. A coarser view that ignores both qualifiers and non-lead event objects would incorrectly merge X7 with X1.

### X3 versus X4

Both involve split packages, but X3 consolidates delivery and has one payment, while X4 splits delivery and has two payments with partial settlement. Activity-sequence and typed structural equivalence separate them. A coarse business cluster such as “multi-package fulfillment” could group them, but that would lose delivery and settlement risk differences.

### X4 versus X8

Both have two packages and two deliveries. X4 is forward split fulfillment with partial payment. X8 is reverse logistics with return, inspection, and repack. Activity-sequence and typed structural equivalence separate them. A multiplicity-only view that sees only Package=2 and Delivery=2 might cluster them, but lifecycle motifs should prevent that.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py’s `cluster_equivalent_ocel` clusters OCEL executions using a key derived from the event and event-object tables. In practice, it preserves identifier-level event sequence and E2O incidence: activity names, event order, and the object identifiers or typed object references participating in each event. It does not preserve O2O qualifiers, external lifecycle semantics, or business motifs unless those are encoded in the OCEL itself.

Raw object identifiers make exact clusters too fine. X1 and X2 have different local IDs, so an identifier-level key may split them even though their typed structure is identical. Conversely, `max_objs` can make clusters too coarse if it truncates or omits objects beyond a limit. Large connected executions can also explode key size or force object omission, causing semantically different executions to merge or semantically identical ones to split.

For compliance or operational segmentation, post-process PM4Py clusters with a canonical signature that removes local identifiers, preserves external flags, and adds O2O qualifiers or derived motifs.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# Restrict to Order-centered executions if PM4Py exposes a lead filter.
lead_ocel = pm4py.filter_ocel_lead_object_type(ocel, LEAD_TYPE)

# Raw PM4Py equivalence clusters.
raw_clusters = pm4py.cluster_equivalent_ocel(lead_ocel, max_objs=5)

def is_ext(obj_id):
    return str(obj_id).startswith("EXT")

def ocel_fragment_to_inputs(frag):
    events = []
    for ev in frag["events"]:
        objs = [
            (rel["object_type"], rel["object_id"])
            for rel in frag["event_object"]
            if rel["event_id"] == ev["event_id"]
        ]
        events.append({
            "timestamp": ev["timestamp"],
            "activity": ev["activity"],
            "objects": objs,
        })

    objects = [
        (o["object_type"], o["object_id"])
        for o in frag["objects"]
    ]

    # O2O qualifiers are not standard in basic OCEL tables, but may be supplied
    # by a domain-specific enrichment step.
    o2o_edges = frag.get("o2o_edges", [])

    return events, objects, o2o_edges

def canonical_semantic_signature(frag):
    events, objects, o2o_edges = ocel_fragment_to_inputs(frag)

    layers = defaultdict(list)
    for ev in events:
        objs = tuple(sorted(
            (t, is_ext(i)) for t, i in ev["objects"]
        ))
        layers[ev["timestamp"]].append((ev["activity"], objs))

    event_seq = tuple(
        tuple(sorted(v)) for _, v in sorted(layers.items())
    )

    unique = set((t, i) for t, i in objects)
    counts = defaultdict(int)
    for t, i in unique:
        counts[(t, is_ext(i))] += 1
    obj_profile = tuple(sorted(
        (t, e, n) for (t, e), n in counts.items()
    ))

    o2o_sig = tuple(sorted(
        (
            e["src_type"],
            e["src_ext"],
            e["qualifier"],
            e["tgt_type"],
            e["tgt_ext"],
            e.get("context_type", ""),
        )
        for e in o2o_edges
    ))

    # Reuse motif_profile from Section 2, adapted to the event_seq and o2o_sig.
    motifs = motif_profile_from_signature(event_seq, o2o_sig)

    return (event_seq, obj_profile, o2o_sig, motifs)

semantic_groups = defaultdict(list)

for cluster in raw_clusters:
    for frag in cluster:
        semantic_groups[canonical_semantic_signature(frag)].append(frag)
```

Exact equivalence is preferable when auditing raw event ingestion, debugging OCEL construction, or proving that two logs are byte-for-byte equivalent. Coarser business clustering is preferable for monitoring, segmentation, and root-cause analysis because it ignores arbitrary identifiers and exposes meaningful object relationships.

## 7. Robustness analysis

### Ignore all O2O qualifiers

If qualifiers are removed but event incidence remains, X7 still differs from X1 because Dispatch includes an Item. If that extra Item is also treated as noise, X7 collapses into `SEM_STANDARD`. X4 loses the distinction between partial and completed settlement, but payment multiplicity may still keep it separate. X8 loses the package-replacement motif, but Return/Inspect activities and two packages/deliveries still keep it distinct.

### Ignore external objects

X5 and X6 collapse into `SEM_STANDARD`. This is dangerous for compliance because cross-order logistics and cross-order finance disappear. X1 and X2 remain stable.

### Collapse repeated same-label events

If repeated `Add Item`, `Pack Package`, `Dispatch`, or `Record Payment` events are collapsed into one activity occurrence and object counts are not preserved, X3, X4, and X8 may merge with X1. If object counts are preserved, split-package and split-delivery motifs survive, but repeated-event structure is lost.

### Treat Pack and Dispatch order as partial order

X1, X2, and X3 are unaffected. X4’s interleaving of Pack and Dispatch may become less important, but its two independent package-delivery chains remain. X8 remains distinct because Return and Inspect create a causal reverse-logistics chain. Partial-order canonicalization prevents false splits caused only by arbitrary same-time event ordering.

### Treat payment multiplicity as an amount attribute

X4’s two payments may become one payment record with an amount. The partial-payment motif is lost. If split delivery remains, X4 still differs from X3. If delivery splitting is also abstracted, X4 may merge toward standard fulfillment, which would hide settlement risk.

## 8. Limitations and recommendation

| Purpose | Recommended equivalence | Reason |
|---|---|---|
| Compliance monitoring | Business-semantic equivalence with external flags and O2O qualifiers | Detects cross-order sharing, replacement/removal, partial settlement, and reverse logistics |
| Operational segmentation | Business-semantic equivalence | Produces actionable categories such as standard, split fulfillment, shared logistics, shared finance, and returns |
| Root-cause analysis | Typed structural plus external-aware and qualified structure | Preserves event order, object incidence, and deviations that explain failures |
| Descriptive reporting | Activity-sequence or coarse business clusters | Keeps reports simple and stable for audiences that do not need object-level detail |

No single equivalence notion is best for all four purposes. Compliance needs semantic risk distinctions. Operations needs stable business categories. Root-cause analysis needs structural detail. Reporting needs simplicity. The finest partition is not automatically the best partition; it is useful only when the extra distinctions are semantically meaningful.
