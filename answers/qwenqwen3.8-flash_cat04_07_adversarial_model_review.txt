def evaluate_trace(trace, attrs=None):
    violations = []
    warnings = []
    if not trace:
        return ['empty_trace'], warnings
    for a in trace:
        if a not in KNOWN:
            warnings.append(f'unknown_activity:{a}')
    if trace.count(R) != 1:
        violations.append('register_not_exactly_once')
    if trace.count(REL) != 1:
        violations.append('release_not_exactly_once')
    if trace[0] != R:
        violations.append('register_not_first')
    if trace[-1] != REL:
        violations.append('release_not_last')
    approvals = [a for a in trace if a in APPROVAL]
    if len(approvals) != 1:
        violations.append('approval_not_exactly_one')
    app_pos = trace.index(approvals[0]) if approvals else len(trace)
    before = trace[:app_pos]
    if C not in before or T not in before:
        violations.append('mandatory_checks_missing_before_approval')
    if any(a in MANDATORY for a in trace[app_pos + 1:]):
        violations.append('mandatory_after_approval')
    if any(a in {D, S, E} for a in trace[app_pos + 1:]):
        violations.append('process_activity_after_approval')
    if trace.count(S) > 1:
        violations.append('supplier_multiple_occurrences')
    if trace.count(E) > 1:
        violations.append('expedite_multiple_occurrences')
    if S in trace:
        s_pos = trace.index(S)
        if C not in trace[:s_pos] or T not in trace[:s_pos]:
            warnings.append('supplier_before_mandatory_checks')
    if E in trace:
        e_pos = trace.index(E)
        if C not in trace[:e_pos] or T not in trace[:e_pos]:
            violations.append('expedite_before_mandatory_checks')
        if any(a in MANDATORY for a in trace[e_pos + 1:app_pos]):
            violations.append('mandatory_recheck_after_expedite')
    if D in trace:
        d_pos = trace.index(D)
        if C not in trace[:d_pos] or T not in trace[:d_pos]:
            violations.append('correct_before_initial_mandatory_checks')
    if attrs is not None:
        ext = attrs.get('external_order')
        if ext is True and S not in trace:
            violations.append('supplier_missing_for_external_order')
        elif ext is False and S in trace:
            warnings.append('supplier_present_on_internal_order')
        elif ext is None:
            warnings.append('external_order_unknown')
    else:
        warnings.append('external_internal_attribute_missing')
    last_mandatory_pos = {C: None, T: None}
    last_correct_pos = None
    for i, a in enumerate(trace):
        if a == D:
            last_correct_pos = i
        if a in MANDATORY:
            if last_mandatory_pos[a] is not None:
                if last_correct_pos is None or last_correct_pos < last_mandatory_pos[a]:
                    violations.append('repeated_mandatory_without_preceding_correct_dossier')
            last_mandatory_pos[a] = i
    for i, a in enumerate(trace):
        if a == D:
            next_boundary = app_pos
            for j in range(i + 1, app_pos):
                if trace[j] == D:
                    next_boundary = j
                    break
            if not any(trace[j] in MANDATORY for j in range(i + 1, next_boundary)):
                warnings.append('correct_dossier_without_mandatory_recheck')
    if D in trace and any(a in MANDATORY for a in trace[trace.index(D) + 1:app_pos]):
        warnings.append('correction_recheck_affected_attribute_missing')
    return violations, warnings

# 1. Review Scope and Assumptions

This review is for a model-governance board, not for a leaderboard. The reported metrics are evidence about how the models behaved on one undisclosed log preparation, not ground truth about the process. I do not average the metrics into a single score. The central question is not whether Model S or Model C has the larger aggregate number, but whether either can be trusted for the intended use.

I distinguish four uses:

- **Exploration**: discover possible variants, understand noise, and generate hypotheses. Fitness and coverage matter; precision can be low if the model is clearly labeled non-enforcing.
- **Conformance enforcement**: decide whether a trace is compliant. Negative controls and hard policy violations matter more than average fitness. A model that admits forbidden behavior is unsafe even with high holdout fitness.
- **Simulation**: require soundness, reachability, and behavior that is neither too permissive nor too brittle. Over-enumerated models can simulate only frequent past paths and miss legitimate future behavior.
- **Stakeholder communication**: require transparency, maintainability, and traceable policy semantics. A model that business users cannot understand is unlikely to survive change control.

Assumptions used throughout:

1. PM4Py process-tree semantics are assumed to be:
   - `->` sequence,
   - `X` exclusive choice,
   - `+` parallel composition,
   - `*` loop with body and exit,
   - `tau` silent transition.
2. The reported split, preprocessing, alignment costs, and held-out cases are not reproducible from the evidence supplied. Therefore, apparent differences may be metric artifacts rather than semantic differences.
3. The log lacks the external/internal order attribute and the affected-check attribute. These are not minor metadata gaps; they are policy-critical.
4. “Missing Supplier Review” cannot be automatically interpreted as “internal order,” and “missing Correct Dossier” cannot be automatically interpreted as “suspicious repeated check.” These require data-quality and policy checks, not silent optionalization.

# 3. Adversarial Review of Model S

## Strongest case for Model S

Model S is attractive because it is simple, fast, understandable, and highly fitful on both training and holdout observed cases. Its high holdout fitness and token-based generalization suggest that it covers the observed positive variants well. Its low runtime makes it practical for large logs. For discovery and data-quality triage, a permissive model can be useful: it does not immediately reject noisy or incomplete traces, and it can help analysts see which variants are frequent.

If the intended use is explicitly exploratory, and if the model is labeled as non-enforcing, Model S has a legitimate role.

## Strongest case against Model S

Model S is unacceptable for conformance enforcement because it does not encode the core policy constraints. It treats Credit Check and Technical Review as optional activities, allows them to be skipped, and allows Expedite Review to occur before them. It does not represent Correct Dossier at all. It also cannot express that Supplier Review is conditional on external sourcing. Its “robustness to missing events” is therefore not a virtue in a compliance context: it conflates missing data with permitted behavior.

## Concrete behaviors admitted by Model S that are undesirable or policy-ambiguous

Under the assumed PM4Py semantics, the parallel block after Register contains four optional branches. This allows any subset of Credit Check, Technical Review, Supplier Review, and Expedite Review in any order before approval.

1. **Skips both mandatory checks**  
   `Register Dossier, Manager Approval, Release Order`  
   This is B3 and is forbidden by P2. Model S accepts it because all optional branches can choose `tau`.

2. **Skips Technical Review**  
   `Register Dossier, Credit Check, Manager Approval, Release Order`  
   This violates P2. Model S accepts it because Technical Review is optional.

3. **Skips Credit Check**  
   `Register Dossier, Technical Review, Auto Approval, Release Order`  
   This violates P2. Model S accepts it because Credit Check is optional.

4. **Places Expedite Review before mandatory checks**  
   `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   This is B4 and violates P4. Model S accepts it because the parallel block imposes no precedence between Expedite Review and the mandatory checks.

5. **Admits Supplier Review without mandatory checks**  
   `Register Dossier, Supplier Review, Auto Approval, Release Order`  
   This violates P2 and is policy-ambiguous for P3 because external/internal status is unknown. Model S accepts it.

6. **Admits Supplier Review before mandatory checks**  
   `Register Dossier, Supplier Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   The mandatory checks eventually occur, but the ordering of Supplier Review relative to them is not controlled. Depending on business policy, this may be invalid or merely ambiguous. Model S accepts it.

7. **Admits Supplier Review on potentially internal orders**  
   `Register Dossier, Credit Check, Technical Review, Supplier Review, Auto Approval, Release Order`  
   If Supplier Review is only meaningful for externally sourced orders, this trace is policy-ambiguous without the external attribute. Model S accepts it unconditionally.

## Intentional noise tolerance versus accidental semantic flaws

Some permissiveness is intentional: Supplier Review and Expedite Review are optional or conditional, and logs can miss events. But Model S’s optionalization of Credit Check and Technical Review is not a defensible noise-tolerance choice; it is an accidental semantic flaw. P2 makes those checks mandatory before approval. Likewise, allowing Expedite Review before mandatory checks is not noise tolerance; it violates P4.

Model S also rejects B8, `Register Dossier, Credit Check, Technical Review, Credit Check, Manager Approval, Release Order`, but this is not evidence that it detects P7. It rejects B8 because it cannot repeat any activity at all. That same limitation makes it reject legitimate corrected repeats such as B6.

# 4. Adversarial Review of Model C

## Strongest case for Model C

Model C is the more conservative and more precise of the two on the training log. It prevents the most dangerous Model S failures: it does not allow Credit Check or Technical Review to be skipped, it does not allow Expedite Review before mandatory checks, and it does not allow multiple approvals. It also includes one correction variant and several frequent internal/external/Manager variants. For a narrow audit use—“does this trace match a known compliant variant?”—Model C can be useful as a regression suite of known behavior.

## Strongest case against Model C

Model C is brittle, overfit, and difficult to maintain. It enumerates observed variants as exclusive choices rather than encoding policy constraints. Its holdout fitness collapse from 0.973 training to 0.744 holdout is not merely “unseen behavior is noncompliant”; it is evidence that the model rejects legitimate combinations of already known activities, such as alternate check order with Auto Approval, Supplier Review with Auto Approval, Expedite Review before Supplier Review, and partial correction rechecks.

## Branch enumeration and maintainability

Model C is an exclusive choice over eight full traces. To add a new valid combination, the team must add another complete trace. This causes combinatorial explosion. For example, if Supplier Review, Expedite Review, Auto Approval, alternate check order, and partial corrections are all legitimate, the number of enumerated variants grows rapidly. This is exactly the maintainability problem raised by F2 and F3.

## Duplicate labels

The reported duplicate-label count of 33 is consistent with the same activity labels appearing in many branches. Duplicate labels can make impact analysis difficult because a change to Credit Check may require updating many branches. They can also make alignment and precision metrics harder to interpret because the same label may map to multiple structural positions. The definition is undocumented, so the number itself is not decisive, but the qualitative concern is credible.

## Unseen combinations and holdout degradation

F4 states that holdout cases combine Supplier Review, Auto Approval, and alternate check order in ways absent from training. Model C explicitly rejects such combinations:

- B2: `Register Dossier, Technical Review, Credit Check, Auto Approval, Release Order` is valid under P2 and P5, but Model C rejects it.
- B5: `Register Dossier, Technical Review, Credit Check, Supplier Review, Expedite Review, Auto Approval, Release Order` is plausible valid external/urgent behavior, but Model C rejects it.
- B6: `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order` is policy-dependent but potentially valid, and Model C rejects it because its only correction trace repeats both checks.

The low holdout fitness is therefore not proof that the holdout cases are invalid. It is at least partly evidence that Model C does not represent the policy space.

## Correction handling

Model C includes only one correction variant:

`Register Dossier, Credit Check, Technical Review, Correct Dossier, Credit Check, Technical Review, Manager Approval, Release Order`

This does not represent the process owner’s requirement in F6: a correction may require repeating only Credit Check, only Technical Review, or both. Model C cannot represent that decision transparently. It also does not represent repeated corrections.

## Is high precision an artifact?

Yes, likely. Precision on a positive log measures how much model behavior is supported by observed log behavior. A model that enumerates observed positive traces can score high precision while having poor recall for valid behavior. Without a curated negative suite, high precision does not prove policy correctness. It may simply prove memorization of frequent variants.

# 7. Third Alternative

## Strategy

I propose a **block-structured procedural backbone plus explicit uncertainty and post-hoc policy checks**. The control-flow model enforces the structural constraints that can be safely inferred from P1, P2, P4, P5, P6, and P7. Data-dependent and ambiguous constraints are handled by declarative checks, not by silently making mandatory activities optional.

The deployed conformance object is not only `model_third`; it is the pair:

```python
(model_third, evaluate_trace)
```

## Compact formal description

Let:

- `R` = Register Dossier
- `C` = Credit Check
- `T` = Technical Review
- `S` = Supplier Review
- `E` = Expedite Review
- `D` = Correct Dossier
- `M` = Manager Approval
- `A` = Auto Approval
- `Rel` = Release Order
- `` = silent transition

Control-flow backbone:

```text
R ; (C T | T C) ; ( (D ( | C | T | C T | T C)) | S | E )* ; (M | A) ; Rel
```

This backbone means:

1. Register first.
2. Credit Check and Technical Review both occur before approval, in either order.
3. After the initial mandatory checks, any number of post-check episodes may occur:
   - a correction episode: `Correct Dossier` followed by zero or one recheck episode,
   - Supplier Review,
   - Expedite Review.
4. Exactly one approval occurs.
5. Release last.

The post-hoc checks then enforce or flag:

- Supplier Review conditional on external/internal order,
- Expedite Review precedence relative to mandatory checks and late rechecks,
- repeated mandatory checks without a preceding Correct Dossier,
- cardinality of Supplier Review and Expedite Review if the business requires at most one,
- correction/recheck uncertainty due to missing affected-check attributes.

## Declarative dictionaries and external checks

The following checks are intentionally simple and readable. They are not a replacement for a full DECLARE engine, but they make the policy logic explicit.

```python
POLICY_CHECKS = {
    "hard": [
        "register_not_first",
        "release_not_last",
        "approval_not_exactly_one",
        "mandatory_checks_missing_before_approval",
        "expedite_before_mandatory_checks",
        "mandatory_recheck_after_expedite",
        "repeated_mandatory_without_preceding_correct_dossier",
        "correct_before_initial_mandatory_checks",
        "supplier_missing_for_external_order",
        "supplier_multiple_occurrences",
        "expedite_multiple_occurrences",
    ],
    "warnings": [
        "external_internal_attribute_missing",
        "external_order_unknown",
        "supplier_present_on_internal_order",
        "supplier_before_mandatory_checks",
        "correct_dossier_without_mandatory_recheck",
        "correction_recheck_affected_attribute_missing",
        "unknown_activity",
    ],
}


def evaluate_trace(trace, attrs=None):
    violations = []
    warnings = []

    if not trace:
        return ["empty_trace"], warnings

    for a in trace:
        if a not in KNOWN:
            warnings.append(f"unknown_activity:{a}")

    if trace.count(R) != 1:
        violations.append("register_not_exactly_once")
    if trace.count(REL) != 1:
        violations.append("release_not_exactly_once")
    if trace[0] != R:
        violations.append("register_not_first")
    if trace[-1] != REL:
        violations.append("release_not_last")

    approvals = [a for a in trace if a in APPROVAL]
    if len(approvals) != 1:
        violations.append("approval_not_exactly_one")

    app_pos = trace.index(approvals[0]) if approvals else len(trace)
    before_approval = trace[:app_pos]

    if C not in before_approval or T not in before_approval:
        violations.append("mandatory_checks_missing_before_approval")

    if any(a in MANDATORY for a in trace[app_pos + 1:]):
        violations.append("mandatory_after_approval")

    if any(a in {D, S, E} for a in trace[app_pos + 1:]):
        violations.append("process_activity_after_approval")

    if trace.count(S) > 1:
        violations.append("supplier_multiple_occurrences")
    if trace.count(E) > 1:
        violations.append("expedite_multiple_occurrences")

    if S in trace:
        s_pos = trace.index(S)
        if C not in trace[:s_pos] or T not in trace[:s_pos]:
            warnings.append("supplier_before_mandatory_checks")

    if E in trace:
        e_pos = trace.index(E)
        if C not in trace[:e_pos] or T not in trace[:e_pos]:
            violations.append("expedite_before_mandatory_checks")
        if any(a in MANDATORY for a in trace[e_pos + 1:app_pos]):
            violations.append("mandatory_recheck_after_expedite")

    if D in trace:
        d_pos = trace.index(D)
        if C not in trace[:d_pos] or T not in trace[:d_pos]:
            violations.append("correct_before_initial_mandatory_checks")

    if attrs is not None:
        ext = attrs.get("external_order")
        if ext is True and S not in trace:
            violations.append("supplier_missing_for_external_order")
        elif ext is False and S in trace:
            warnings.append("supplier_present_on_internal_order")
        elif ext is None:
            warnings.append("external_order_unknown")
    else:
        warnings.append("external_internal_attribute_missing")

    last_mandatory_pos = {C: None, T: None}
    last_correct_pos = None

    for i, a in enumerate(trace):
        if a == D:
            last_correct_pos = i
        if a in MANDATORY:
            if last_mandatory_pos[a] is not None:
                if last_correct_pos is None or last_correct_pos < last_mandatory_pos[a]:
                    violations.append(
                        "repeated_mandatory_without_preceding_correct_dossier"
                    )
            last_mandatory_pos[a] = i

    for i, a in enumerate(trace):
        if a == D:
            next_boundary = app_pos
            for j in range(i + 1, app_pos):
                if trace[j] == D:
                    next_boundary = j
                    break
            if not any(trace[j] in MANDATORY for j in range(i + 1, next_boundary)):
                warnings.append("correct_dossier_without_mandatory_recheck")

    if D in trace and any(a in MANDATORY for a in trace[trace.index(D) + 1:app_pos]):
        warnings.append("correction_recheck_affected_attribute_missing")

    return violations, warnings
```

## Explicit semantics

### Mandatory checks

Credit Check and Technical Review are mandatory before approval. The backbone requires both before the approval block. They may occur in either order. Rechecks are allowed only inside a correction episode.

### Optional Supplier Review

Supplier Review is optional in the control-flow backbone because the external/internal attribute is missing. This is not the same as treating it as universally permitted. The post-hoc check requires Supplier Review when `external_order=True`, warns when `external_order=False`, and warns when the attribute is missing.

### Expedite Review ordering

Expedite Review occurs after the initial mandatory checks because the loop begins after the mandatory block. Supplier Review and Expedite Review may occur in either order. A strict post-hoc check rejects a mandatory recheck after Expedite Review before approval. If the business only requires Expedite Review after the first occurrence of both mandatory checks, that check can be changed from violation to warning.

### Exactly-one approval

The approval block is `X('Manager Approval', 'Auto Approval')`, so exactly one approval is required. The post-hoc check independently verifies count.

### Correction and recheck behavior

Correct Dossier may occur zero or more times after the initial mandatory checks. Each correction episode may be followed by:

- no recheck,
- Credit Check only,
- Technical Review only,
- Credit Check then Technical Review,
- Technical Review then Credit Check.

A repeated mandatory check without a preceding Correct Dossier is flagged. Because the affected-check attribute is missing, any correction recheck produces a warning rather than being automatically deemed compliant.

## Limitations caused by missing attributes

1. **Missing external/internal attribute**  
   Supplier Review cannot be fully enforced. The model treats it as optional in control flow and uses post-hoc conditional checks. If the attribute remains unavailable, automatic compliance decisions involving Supplier Review should be quarantined for human review.

2. **Missing affected-check attribute**  
   The model cannot know whether a correction affected Credit Check, Technical Review, both, or neither. It allows any subset of rechecks after Correct Dossier and flags uncertainty. This is safer than Model S, which cannot represent correction at all, and more general than Model C, which only represents one correction variant.

3. **Missing Correct Dossier events**  
   If Correct Dossier is not logged, a legitimate recheck may be flagged as a repeated mandatory check without correction. This is a data-quality limitation, not a modeling defect.

4. **Duplicate labels**  
   Credit Check and Technical Review appear both in the initial mandatory block and in correction rechecks. This is semantically necessary but can affect alignment ambiguity and simplicity metrics.

5. **Contiguous recheck episodes**  
   The backbone models a correction recheck as contiguous. If logs show Supplier Review or Expedite Review between two rechecks of the same correction episode, the backbone may reject a legitimate trace. This can be addressed with a POWL or event-level attributes.

6. **Cardinality of optional reviews**  
   The backbone’s loop can admit multiple Supplier Review or Expedite Review events. The post-hoc checks treat duplicates as violations under a conservative interpretation. If the business allows multiple reviews, the check should become a warning or be removed.

## Reproducible case splits and published preprocessing

```python
import random
from collections import defaultdict
import pm4py

SEED = 20240515
random.seed(SEED)

def preprocess(log, known_activities):
    """
    Publish this function exactly.
    Required steps:
    1. Keep only known activities.
    2. Sort cases by case ID and timestamp.
    3. Document any filtered cases and why.
    """
    log = log[log["concept:name"].isin(known_activities)].copy()
    log = log.sort_values(["case:concept:name", "time:timestamp"])
    return log

def get_case_traces(log):
    return [
        (cid, list(g["concept:name"]))
        for cid, g in log.groupby("case:concept:name", sort=True)
    ]

def safe_pos(trace, activity):
    return trace.index(activity) if activity in trace else -1

def trace_signature(trace):
    """
    Surrogate stratification while external_order is missing.
    Later, add external_order, affected_checks, and order_type if available.
    """
    order = None
    if C in trace and T in trace:
        order = "CT" if safe_pos(trace, C) < safe_pos(trace, T) else "TC"

    return (
        S in trace,
        E in trace,
        D in trace,
        M in trace,
        A in trace,
        order,
    )

def stratified_case_split(case_traces, train_frac=0.8):
    random.seed(SEED)
    buckets = defaultdict(list)

    for cid, trace in case_traces:
        buckets[trace_signature(trace)].append(cid)

    train_ids = []
    holdout_ids = []

    for key, ids in buckets.items():
        ids = sorted(ids)
        random.shuffle(ids)

        if len(ids) == 1:
            # Rare strata: force into holdout to test generalization.
            holdout_ids.extend(ids)
        else:
            cut = int(round(train_frac * len(ids)))
            cut = max(1, min(cut, len(ids) - 1))
            train_ids.extend(ids[:cut])
            holdout_ids.extend(ids[cut:])

    return train_ids, holdout_ids
```

def remove_event(trace, event):
    return [a for a in trace if a != event]

def duplicate_event(trace, event):
    out = []
    duplicated = False
    for a in trace:
        out.append(a)
        if a == event and not duplicated:
            out.append(event)
            duplicated = True
    return out

def perturbation_suite(case_traces):
    perturbations = []

## Stakeholder comprehension protocol

Replace the informal 1–5 score with a documented protocol:

1. Recruit at least three stakeholder groups: compliance, operations, IT/data.
2. Use the same model view for all participants.
3. Ask forced-choice tasks:

## Decision rule for rejection despite good aggregate metrics

```python
def enforcement_ready(metrics, negative_results, probe_results, stakeholder_results):
    if not metrics["soundness"]:
        return False, "Model is not sound."

    if any(r["model_accepts"] and not r["policy_violations"] for r in negative_results):
        return False, "Model accepts a hard negative without policy violation."

    forbidden_probes = ["B3", "B4", "B8"]
    for probe in forbidden_probes:
        if probe_results[probe]["accepted"]:
            return False, f"Model accepts forbidden probe {probe}."

    valid_probes = ["B1", "B2", "B5", "B7"]
    for probe in valid_probes:
        if not probe_results[probe]["accepted"]:
            return False, f"Model rejects valid probe {probe}."

    if metrics["holdout_fitness"] < 0.95:
        return False, "Holdout fitness below board threshold."

    if stakeholder_results["median_comprehension"] < 3.0:
        return False, "Stakeholder comprehension below threshold."

    return True, "Ready for enforcement pilot."
```

The board must set numeric thresholds explicitly. Aggregate fitness cannot override a hard negative.

# 10. Governance Recommendation

## Exploration

Model S may be used for exploration only under a clear warning label: “non-enforcing, noise-tolerant, may admit forbidden behavior.” It is useful for discovering variants, checking holdout coverage, and triaging missing events. It should not be used to certify compliance.

## Conformance enforcement

Neither Model S nor Model C should be used as the sole conformance model.

- Model S is unsafe because it can skip mandatory checks and misorder Expedite Review.
- Model C is too brittle and rejects known valid behaviors. It may be useful as a **known-variant regression suite**, not as a policy model.

## Retirement status

- **Model S**: do not retire, but quarantine from compliance. Use as exploratory skeleton only.
- **Model C**: retire as the sole conformance model. Retain as an archive of frequent observed variants, with duplicate-label and maintainability warnings.
- **Third alternative**: candidate for enforcement after validation and data enrichment.

## Conditions before deploying the third alternative

The third alternative must meet all of the following before automatic enforcement:

1. Pass soundness and reachability checks.
2. Reject all hard negative probes, including B3, B4, and B8.
3. Accept valid probes, including B1, B2, B5, B6 when policy-dependent, B7, and the adversarial traces A1–A3 under the agreed policy.
4. Report holdout fitness, precision, generalization, simplicity, and runtime separately.
5. Pass alignment-cost sensitivity analysis; no metric may depend on free `tau` moves.
6. Use attribute-stratified holdout tests. If external/internal data is absent, Supplier-related decisions must remain warnings or manual review.
7. Implement or document the post-hoc checks, including version control for `evaluate_trace`.
8. Obtain business sign-off on ambiguous choices:
   - Is Supplier Review forbidden on internal orders or merely optional?
   - Must Expedite Review follow all mandatory rechecks, or only the initial mandatory checks?
   - Are multiple Supplier or Expedite Reviews allowed?
   - Is a Correct Dossier without recheck allowed?
9. Stakeholder comprehension must be measured with a documented protocol, not an informal score.
10. If missing attributes cannot be remediated, the third model may be used for triage and review queueing, not for automatic noncompliance decisions.

# 11. Dissenting View

The recommendation is too cautious and over-engineered. Model S’s low precision is not a defect for discovery; it is the feature that allowed holdout fitness and generalization to remain high while the process was still poorly understood. The board’s real problem is missing attributes and noisy event logs, not a lack of a sophisticated hybrid. Adding a loop, silent transitions, and post-hoc checks creates a second, hidden model that is harder to audit than either submission. It admits interleavings and duplicate optional reviews that the business has not approved, then asks custom code to decide policy. That shifts responsibility from a transparent Petri net to Python functions with their own bugs. Model C, despite poor holdout fitness, is the only artifact that actually encodes known compliant behavior and can be used today as a regression suite. The correct governance action is to collect the missing external/internal and affected-check attributes, then rerun inductive discovery on a cleaned log. If the new log still supports Model S’s holdout fitness, the process owner should accept S for exploration and C for known-variant enforcement, rather than inventing a third model whose validation burden is larger than its value.

Additional evidence that would change my decision:

1. **Published reproducible artifacts**: seeds, preprocessing code, alignment costs, and held-out case IDs showing that C’s holdout collapse is caused by genuinely invalid behavior rather than split sensitivity.
2. **A curated negative suite**: evidence that Model S admits a material number of forbidden traces and that Model C rejects them without also rejecting known valid variants.
3. **Business sign-off on unseen behavior**: if stakeholders explicitly require that unseen behavior be treated as noncompliant until approved, then C’s conservatism may be acceptable for enforcement.
4. **Attribute enrichment**: if external/internal and affected-check attributes are added to the event log, a simpler attribute-conditioned model may replace the hybrid backbone plus post-hoc checks.
5. **Stakeholder protocol results**: if a formal comprehension study shows that Model C is understandable to compliance owners and that Model S’s simplicity hides dangerous omissions, the governance choice could shift toward C as a controlled variant catalog.
6. **Production constraints**: if the third model’s post-hoc checks cannot be maintained, versioned, or audited, then a narrower use of C for known variants plus S for exploration may be operationally safer than a hybrid system.
