# 2. Shared Assumptions

All three models share the following assumptions:

1. **Event-completion semantics.** Every trace records only the completion order of activities. No activity start timestamps, durations, or resource assignments are available. Consequently, "A precedes B in a trace" means A completed before B completed, not that A causally enabled B or that they did not overlap.

2. **Missing Supplier Confirmation events.** S5 indicates 5–10% of Supplier Confirmation events may be missing due to an integration problem. The 7 traces without Supplier Confirmation (V3: 4, V4: 3) cannot be confidently classified as "genuinely no Supplier" vs. "Supplier occurred but was not logged." We abstract this by modeling Supplier Confirmation as optional (XOR with skip) in the balanced and permissive models. This conflates two distinct phenomena: (a) true optionality for stocked components (S4) and (b) data missingness (S5). We disclose this abstraction explicitly.

3. **Absent external/stocked attribute.** The attribute that would distinguish external (Supplier required, S3) from stocked (Supplier not required, S4) components was not exported. Without it, we cannot condition Supplier's optionality on case type. All models therefore treat Supplier optionality uniformly.

4. **Optionality representation.** Optional activities are represented as XOR(activity, silent transition). When the silent branch is chosen, the activity is absent from the trace. This is a control-flow abstraction for missingness and genuine optionality alike.

5. **Fixed prefix and suffix.** Register Order is the sole start activity (D1, 30/30 traces). Approve Configuration  Release Production  Archive Case is the invariant suffix (D2, 30/30 traces). All models enforce this.

6. **At-most-once semantics for Expedite.** D6 states Expedite occurs at most once. XOR(Expedite, skip) inherently enforces zero or one occurrence. No model allows repeated Expedite.

7. **Label identity.** Activity labels are treated as types, not tokens. Multiple occurrences of the same label in a model (e.g., in the conservative XOR) refer to the same activity class, not distinct subprocesses.

# 3. Conservative Candidate

**Inductive-bias statement.** The conservative model admits exactly the seven observed trace variants and nothing else. It treats each variant as a distinct sequential path and selects among them with a seven-way XOR. This minimizes false positives (high precision) at the cost of zero generalization: any future trace that deviates by even one activity or ordering will be classified as non-conforming. The model overfits to the observed sample and cannot distinguish noise from structural variation. Duplicate labels across XOR branches are semantically correct but create a scalability problem: with *n* variants, the tree grows linearly, and adding or merging variants requires manual tree surgery. Automated discovery would produce a more compact representation, but we sacrifice compactness for maximal precision.

**Formal expression.**

```
SEQ(Register, XOR(
  SEQ(Credit Check, Engineering Review, Supplier Confirmation),
  SEQ(Engineering Review, Credit Check, Supplier Confirmation),
  SEQ(Credit Check, Engineering Review),
  SEQ(Engineering Review, Credit Check),
  SEQ(Credit Check, Supplier Confirmation, Engineering Review),
  SEQ(Credit Check, Engineering Review, Supplier Confirmation, Expedite Review),
  SEQ(Engineering Review, Credit Check, Expedite Review, Supplier Confirmation)
), SEQ(Approve, Release, Archive))
```

**PM4Py code.**

```python
import pm4py

conservative_tree_str = (
    "->(Register Order, X("
    "->(Credit Check, Engineering Review, Supplier Confirmation), "
    "->(Engineering Review, Credit Check, Supplier Confirmation), "
    "->(Credit Check, Engineering Review), "
    "->(Engineering Review, Credit Check), "
    "->(Credit Check, Supplier Confirmation, Engineering Review), "
    "->(Credit Check, Engineering Review, Supplier Confirmation, Expedite Review), "
    "->(Engineering Review, Credit Check, Expedite Review, Supplier Confirmation)"
    "), ->(Approve Configuration, Release Production, Archive Case))"
)

model_conservative = pm4py.parse_process_tree(conservative_tree_str)
```

**Behavior deliberately excluded.**
- Expedite Review without Supplier Confirmation (e.g., CC, ER, Expedite, Approve, …).
- Supplier Confirmation without Credit Check preceding it (e.g., ER, Supplier, CC, …).
- Any interleaving of Supplier and Expedite not matching V6 or V7 exactly.
- Multiple occurrences of any activity.
- Any activity between Approve and Release, or between Release and Archive.
- Traces not starting with Register or not ending with Archive.

**Known underfitting risks.**
- A trace with CC, ER, Expedite, Approve (Expedite present, Supplier absent) is a plausible future case (stocked components with expedite) but is rejected.
- If S5 is correct, some V3/V4 traces truly had Supplier; the model treats them as a separate variant, embedding data quality issues into the control-flow structure.
- The model cannot represent the domain rule D5 (Supplier may begin after either check) as a generalization; it only captures the specific observed instantiation.
- Adding a single new variant in production requires modifying the tree structure.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model generalizes from the seven observed variants by recognizing the recurring structural pattern: two principal checks (Credit Check, Engineering Review) that appear in both orders, an optional Supplier Confirmation that follows Credit Check but need not wait for Engineering Review (V5, D5), an optional Expedite Review that requires both checks (D6, S6), and a fixed approval-release-archive suffix. The model uses a strict partial order (POWL) to express these precedence constraints without imposing unnecessary total orderings. Credit Check and Engineering Review are modeled as concurrent (no edge between them) because both orderings appear with substantial frequency and S2 supports parallel execution; however, we acknowledge D7 that this is an inductive hypothesis, not a proven fact. Supplier Confirmation is constrained to follow Credit Check (all 23 Supplier-containing traces show CC before Supplier) but not Engineering Review, matching V5. Expedite Review is constrained to follow both checks, per D6/S6. Supplier and Expedite have no relative ordering constraint, matching V6 and V7. The model is a middle ground: it admits all observed traces plus reasonable unobserved combinations (e.g., Expedite without Supplier) while excluding traces that violate medium-to-high confidence domain rules.

**How sequence, concurrency, and partial order are decided.**

| Pair | Decision | Rationale |
|---|---|---|
| CC  ER | **Concurrent** (no edge) | Both orderings appear with substantial counts (17 and 11). S2 states they normally run in parallel. D7 warns this is not proven, but a sequential-choice model would be a separate defensible alternative. |
| CC  Supplier | **Sequence edge** (CC precedes Supplier) | All 23 Supplier-containing traces show CC before Supplier. V5 shows Supplier can precede ER, so the constraint is only on CC. D5 supports "after either," but evidence consistently shows CC first. |
| ER  Supplier | **No edge** | V5 demonstrates Supplier can finish before ER. D5 says Supplier need not wait for both. |
| {CC, ER}  Expedite | **Both edges** | D6 (medium confidence) and S6 explicitly state Expedite requires both checks. V6 and V7 both show Expedite after both. |
| Supplier  Expedite | **No edge** | V6 shows Supplier before Expedite; V7 shows Expedite before Supplier. S6 explicitly allows either order. |
| All  Approve | **Edges from CC, ER, Supplier-opt, Expedite-opt** | D2, D3, D4 collectively require all prerequisites before Approve. Optional activities use XOR-with-skip; when skipped, the XOR block completes immediately, satisfying the edge. |
| Approve  Release  Archive | **Sequence** | D1, D2, 30/30 traces. |

**Formal expression.**

POWL strict partial order (children shown with edges):
```
Children: {CC, ER, XOR(Supplier, ), XOR(Expedite, ), Approve}
Edges:
  CC  XOR(Supplier, )
  CC  XOR(Expedite, )
  ER  XOR(Expedite, )
  CC  Approve
  ER  Approve
  XOR(Supplier, )  Approve
  XOR(Expedite, )  Approve
Wrapped in: SEQ(Register, PartialOrder, Release, Archive)
```

**PM4Py code.**

```python

    SilentTransition,

po_balanced.order.add_edge(er, expedite_opt)
po_balanced.order.add_edge(cc, approve)
po_balanced.order.add_edge(er, approve)
po_balanced.order.add_edge(supplier_opt, approve)
po_balanced.order.add_edge(expedite_opt, approve)

model_balanced = OperatorPOWL(

    [
        Transition("Register Order"),
        po_balanced,
```

- Supplier Confirmation before Credit Check (no evidence; all 23 traces show CC first).
- Expedite Review before both checks complete (violates D6, S6).
- Expedite Review after Approve (violates D6).
- Multiple occurrences of Supplier or Expedite (XOR enforces at-most-once).
- Any activity between Approve and Release, or Release and Archive.
- Supplier Confirmation after Approve Configuration.

**Known underfitting risks.**
- If D5's "after either" interpretation is correct, Supplier after only Engineering Review (without Credit Check first) should be valid, but this model excludes it.
- If some V3/V4 traces are genuinely external components with missing Supplier events, the model's optionality abstraction may admit non-conforming cases as conforming (reducing precision).
- The concurrency assumption for CC and ER (no edge) is based on inductive reasoning from completion orders and S2; if S1 is correct (CC must precede ER), the model over-generalizes.
- The partial order does not express "Supplier requires at least one check"—it only requires Credit Check specifically, which is evidence-driven but may be too narrow.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model prioritizes coverage of all behavior consistent with the broad domain rules (D1–D6, S3–S6) over precision. It relaxes the balanced model's constraint that Credit Check must precede Supplier Confirmation, instead allowing Supplier to occur at any point after Register but before Approve. This follows D5's literal wording ("may begin after either Credit Check or Engineering Review") and acknowledges that the consistent CC-before-Supplier pattern in the data may be a sampling artifact rather than a structural requirement. Expedite Review remains constrained to follow both checks (D6, high-stakes compliance rule). The model uses a POWL strict partial order with fewer edges than the balanced model, yielding a larger language. The boundary between "reasonable generalization" and "forbidden" is defined by the medium-to-high confidence domain rules: any behavior that violates D1 (start/end), D2 (Release requires Approve), D3 (both checks before Approve), or D6 (Expedite after both checks) is forbidden. Behavior that is unobserved but not prohibited by these rules is admitted.

**Boundary definition.**

| Admitted (reasonable generalization) | Forbidden |
|---|---|
| Supplier before or concurrent with either check (D5) | Expedite before both checks complete (D6) |
| Expedite without Supplier (stocked + expedite) | Any activity after Archive (D1) |
| Any interleaving of CC and ER (D7, S2) | Release before Approve (D2) |
| Supplier and Expedite in either order (S6) | Multiple Expedite occurrences (D6) |
| No Supplier and no Expedite (stocked, non-expedited) | Approve before either check (D3) |
| Supplier after only ER (D5, unobserved) | Missing Register (D1) |

**Formal expression.**

```
Children: {CC, ER, XOR(Supplier, ), XOR(Expedite, ), Approve}
Edges:
  CC  XOR(Expedite, )
  ER  XOR(Expedite, )
  CC  Approve
  ER  Approve
  XOR(Supplier, )  Approve
  XOR(Expedite, )  Approve
  (NO edge from CC or ER to Supplier)
Wrapped in: SEQ(Register, PartialOrder, Release, Archive)
```

```python
    po.order.add_edge(cc, exp_opt)
    po.order.add_edge(er, exp_opt)
    po.order.add_edge(cc, appr)
    po.order.add_edge(er, appr)
    po.order.add_edge(sup_opt, appr)
    po.order.add_edge(exp_opt, appr)

    return OperatorPOWL(
        Operator.SEQUENCE,
        [
            Transition("Register Order"),
            po,
            Transition("Release Production"),
            Transition("Archive Case"),
        ],
    )

    po.order.add_edge(er, exp_opt)

    po.order.add_edge(er, appr)
    po.order.add_edge(sup_opt, appr)
    po.order.add_edge(exp_opt, appr)

    return OperatorPOWL(
        Operator.SEQUENCE,
        [
            Transition("Register Order"),
            po,
            Transition("Release Production"),
            Transition("Archive Case"),
        ],
    )
```

# 9. Recommendation and Data-Collection Plan

## Recommendation

**For immediate operational use: the balanced candidate (`model_balanced`).**

Rationale: It admits all 30 observed traces, generalizes to plausible unobserved combinations (e.g., Expedite without Supplier for stocked components), and enforces the medium-to-high-confidence domain rules (D2, D3, D6). Its partial-order structure explicitly represents the uncertainty about Credit Check and Engineering Review ordering without committing to a false sequential constraint. It is robust to the known Supplier Confirmation missingness (S5) because Supplier is optional. It excludes behavior that violates well-supported constraints (e.g., Expedite before both checks).

**For sensitivity analysis: the permissive candidate (`model_permissive`).**

Rationale: It tests the impact of relaxing the Credit Check  Supplier Confirmation constraint, which is the most debatable edge in the balanced model. If the permissive model admits many additional conforming traces in production without quality issues, the balanced model's CCSupplier edge may be unnecessarily restrictive. If the permissive model's broader language captures implausible behavior (e.g., Supplier before any check), the balanced model's constraint is validated.

The conservative model is **not recommended** for operational use: it overfits, cannot absorb missing-data traces, and provides no generalization.

## Data-Collection Plan

### Primary data gaps to resolve

| Gap | Current uncertainty | Data to collect | Distinguishing power |
|---|---|---|---|
| Start vs. completion timestamps | Cannot distinguish concurrency from sequential-choice for CC and ER (D7, S7) | Export activity **start** timestamps in addition to completion timestamps | If CC start and ER start overlap in the same case  concurrency confirmed. If CC always starts after ER completes (or vice versa)  sequential. |
| External vs. stocked component attribute | Cannot distinguish true Supplier optionality (S4) from missingness (S5) | Export the `component_type` (external/stocked) attribute per case | If all external-component cases have Supplier and all stocked cases lack it  Supplier is conditionally mandatory, not optional. |
| Supplier Confirmation event completeness | 5–10% events may be missing (S5) | Fix integration; add an audit flag for Supplier events sourced from the procurement system vs. inferred | If fixed integration shows Supplier in cases previously classified as V3/V4  those variants are artifacts. |
| Expedite Review trigger condition | Only 2 traces; trigger unknown | Export `expedite_requested` boolean and `expedite_reason` per case | Determines whether Expedite is a parallel independent option or conditioned on Supplier timing. |

### Maximally informative future traces

To distinguish the competing hypotheses, the following **unobserved but possible** trace types would be maximally informative:

1. **Register, Engineering Review, Supplier Confirmation, Credit Check, Approve, Release, Archive** — Supplier after ER only (no CC first). If observed, the balanced model's CCSupplier edge is too restrictive; the permissive model is validated. If never observed despite sufficient volume, the balanced model is correct.

2. **Register, Credit Check, Engineering Review, Expedite Review, Approve, Release, Archive** — Expedite without Supplier. If observed, confirms stocked components can have expedite requests; validates the balanced model's independent optionality. If never observed, Expedite may require Supplier, and the models should add an edge.

3. **Register, Credit Check, Expedite Review, Engineering Review, Approve, Release, Archive** — Expedite before Engineering Review completes. If observed, D6 is wrong or more nuanced. If never observed, D6 is validated.

4. **Register, Credit Check, Engineering Review, Approve, Release, Archive** with a confirmed external component type — Supplier absent on an external-component case. If observed with confirmed external type, S5's missingness estimate is higher than 5–10%. If never observed, V3/V4 are stocked-component cases and Supplier optionality is genuine.

5. **Start timestamps showing CC and ER overlapping** — Directly confirms concurrency (S2) vs. sequential (S1). Even 5–10 cases with overlapping start timestamps would strongly support the parallel hypothesis.

### Recommended collection protocol

- Collect start and end timestamps for all activities for a minimum of 100 new cases.
- Export `component_type`, `supplier_system_source`, and `expedite_requested` as case-level attributes.
- After 100 cases, re-evaluate all three models using the same validation code with the expanded log.

# 10. Uncertainty Statement

## Calibrated confidence assessment for major modeling decisions

| Decision | Confidence | Rationale | Alternative interpretation |
|---|---|---|---|
| Register is sole start; Archive is sole end | **High (95%)** | D1 (high confidence), 30/30 traces | A pre-registration or post-archive step could exist but was not logged |
| Approve  Release  Archive is a fixed sequence | **High (95%)** | D2 (high), 30/30 traces, invariant ordering | A rejection/revision path between Approve and Release could exist but was not observed |
| Credit Check and Engineering Review are concurrent (no edge) | **Medium (55%)** | Both orderings appear (17/11), S2 supports parallel, but D7 warns completion order  concurrency; S1 contradicts | They could be two sequential variants selected by a hidden condition (e.g., order type). If so, a choice (XOR) between CCER and ERCC is more accurate than parallel. |
| Credit Check must precede Supplier Confirmation | **Medium-high (75%)** | All 23 Supplier-containing traces show CC first; V5 shows Supplier before ER | D5 says "after either," so Supplier-after-ER-only is rule-consistent but unobserved. Could be sampling bias. |
| Supplier Confirmation is optional | **Medium (60%)** | S3 (mandatory for external) + S4 (stocked skip) + S5 (5–10% missing) | If all cases are external, Supplier is mandatory and V3/V4 are missing-data artifacts. The optionality abstraction conflates three distinct phenomena. |
| Expedite Review requires both checks (D6) | **Medium-high (75%)** | D6, S6 explicitly state this; both observed Expedite traces comply | Compliance rules may be aspirational; real-world traces might violate D6. Low sample (2 traces) limits empirical validation. |
| Expedite and Supplier have no relative ordering | **Medium (65%)** | V6 (Supplier before Expedite) and V7 (Expedite before Supplier) both observed; S6 explicitly allows either | A hidden condition (e.g., Expedite only when Supplier is delayed) could create a dependency not captured. |
| The conservative model's XOR enumeration is complete | **Low (30%)** | Only 30 traces, 7 variants; new variants likely in production | With more data, additional variants (e.g., Expedite without Supplier) will appear, making the conservative model non-conforming. |

## Plausible alternative interpretation that would materially change the recommendation

**Alternative: Credit Check and Engineering Review are not concurrent but follow two sequential process paths selected by a hidden attribute (e.g., order complexity).**

Under this interpretation, some cases always do CCER (perhaps standard orders) and others always do ERCC (perhaps engineering-heavy orders). The two DFG directions arise from two disjoint sequential variants, not from concurrency within a single case. This would mean:

- The balanced and permissive models' partial order (no edge between CC and ER) is **too permissive**: it admits traces like CCERSupplierApprove and ERCCSupplierApprove as valid for the same case, when in reality each case follows exactly one sequential path.
- The correct model would be an XOR between `SEQ(CC, ER, ...)` and `SEQ(ER, CC, ...)`, with Supplier and Expedite constraints applied within each branch.
- The conservative model would be closer to correct than the balanced model for the check-ordering dimension, though it would still need to handle Supplier/Expedite optionality.
- The recommendation would shift toward a **hybrid model**: XOR over the two check orderings, with optional Supplier and Expedite as partial-order constraints within each branch.

This alternative cannot be ruled out without **start timestamps** (to check overlap) or the **hidden attribute** (to check for a splitting condition). The data-collection plan in Section 9 directly addresses this ambiguity. Until such data is available, the balanced model remains the best operational choice, but the concurrency assumption should be treated as a **working hypothesis with moderate confidence**, not an established fact.
