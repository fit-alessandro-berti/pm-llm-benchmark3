## 1. Equivalence design space

Three equivalence relations are defined. All are reflexive, symmetric, and transitive by construction. Concurrency is not assumed (events are given in total timestamp order); if timestamps were equal, the equivalence would require consistent partial-order reasoning (e.g., Pack must precede Dispatch for fulfillment consistency). Only the observable event sequence, object-type roles, O2O notes, and qualifiers mentioned in notes are used—no inferred internal state. Local identifiers (e.g., O1, I11) are ignored for equivalence that respects renaming; EXT-prefixed identifiers denote external objects and are treated consistently (EXT- prefixes are preserved, but internal names like OA/OB/IA are renamed per execution).

1. **Activity-sequence equivalence**  
   *Definition (operational):* Two executions are equivalent if, after normalizing all local object identifiers as follows, the event sequences match label-by-label:  
   - Map every Order ID to `Order` (single canonical Order symbol per execution), every Item ID to `I1`, `I2`, ... in insertion order (first Add Item  `I1`, second  `I2`, etc.), every Package ID to `P1`, `P2`, ..., every Delivery ID to `D1`, `D1`, ..., every Invoice ID to `V`, and every Payment ID to `M`. EXT-prefixed IDs (e.g., `EXT-OA`, `EXT-IA`, `EXT-OB`) are mapped to `E-Order`, `E-Item`, `E-Obj` respectively (e.g., `EXT-OA`  `E-Order`, `EXT-IA`  `E-Item`, `EXT-OB`  `E-Obj`); the `E-` prefix is retained to distinguish external from local. Normalize item IDs strictly by the order of `Add Item` events (first added item = `I1`, etc.). Do **not** reorder events; compare sequences position-wise. For example, X1 becomes: `(Create Order), (Add Item Order;I1), (Add Item Order;I2), (Pack Package Order;I1,I2), (Dispatch Delivery Order;Package), (Issue Invoice Order;V), (Record Payment Invoice;M)`. X2 (with items added I22 then I21) becomes `(Create Order), (Add Item Order;I2), (Add Item Order;I1), ...` — sequence differs at Add positions, so **not** equivalent to X1 under this strict normalization. Qualifiers (e.g., `removed_before_dispatch`) and O2O notes are **not** included in the sequence comparison; only event labels and normalized type references.  
   *Invariants preserved:* Event order; relative ordering of logistics vs financial activities (e.g., Pack before Dispatch); normalized role symbols reflect type.  
   *Information discarded:* Original local ID names (O1 vs O2), item ID permutation within Add events (if order matters), O2O qualifiers, external object internal names (OA/OB/IA), payment amounts.  
   *Symmetry/transitivity:* Yes—normalization is per-execution and deterministic; if A matches B's normalized sequence and B matches C's, A matches C's.

2. **Typed structural equivalence under identifier renaming**  
   *Definition (operational):* Two executions are equivalent if there exists a bijective mapping  of object IDs such that:  
   -  preserves object types (Order  Order, Item  Item, Package  Package, Delivery  Delivery, Invoice  Invoice, Payment  Payment; EXT-prefixed IDs map to EXT-prefixed IDs of the same kind, e.g., `EXT-OA`  `EXT-OA'`),  
   -  is consistent within each execution (local IDs map to local IDs of the same type; external IDs map among external IDs),  
   - the object-centric topology (undirected edges: Order–Item, Item–Package, Package–Delivery, Order–Package, Order–Invoice, Invoice–Payment) is isomorphic under  (ignoring edge direction for topology; direction is implied by event order but topology equivalence checks connectivity only),  
   - event dependencies implied by minimal feasibility are respected (e.g., Pack must occur after all Add Item for its items; Dispatch after Pack; Issue Invoice after Pack; Record Payment after Issue Invoice). Dependencies are checked via event sequence in normalized form but not enforced during topology isomorphism—only that the graph structure matches. Qualifiers (e.g., `removed_before_dispatch`) are **not** part of the structural graph; they are discarded.  
   *Invariants preserved:* Number of objects per type per Order (e.g., one Order, two Items), topology connectivity (e.g., Order connected to Items via Packages), presence/absence of multiple Packages or Deliveries per Order logistics.  
   *Information discarded:* Exact ID names (e.g., O1 vs O2), item addition order (since topology only cares about Item–Package links), qualifiers, external object internal suffixes (OA/OB), event order beyond feasibility (e.g., can have Pack1, Pack2 vs Pack2, Pack1 if topology same), EXT-flag value (only the `EXT-` prefix is preserved; internal name like OA is renamed).  
   *Symmetry/transitivity:* Yes—graph isomorphism is symmetric and transitive under renaming.

3. **Business-semantic equivalence using multiplicities, shared external objects, O2O qualifiers, or lifecycle motifs**  
   *Definition (operational):* Two executions are equivalent if all of the following semantic conditions hold (checked using only event sequence, O2O notes, and qualifiers; no inference beyond provided text):  
   - **Delivery intent:** Exactly one `Dispatch` activity mentioning the lead Order (i.e., one `Dispatch{Order:Ox; Package:…; Delivery:D}` event)  *single delivery intent*; more than one `Dispatch` mentioning the Order  *split delivery intent*. (A `Dispatch` event that lists multiple Packages for the Order is still counted as one Dispatch; e.g., X3's `Dispatch{Order:O3; Package:P31,P32; Delivery:D31}` is single delivery.)  
   - **Invoice scope:** `Issue Invoice` activity references only the Order (`Invoice{Order:Ox; Invoice:V}`)  *order-only invoice*; references both Order and an `EXT-Ob` (`Invoice{Order:Ox,EXT-Ob; Invoice:V}`)  *shared invoice*. (External invoice sharing is explicit in X6; X5 bills only Order even with external Package, so invoice scope is order-only for X5.)  
   - **Payment pattern:** Exactly one `Record Payment` activity for the Invoice  *single payment*; two `Record Payment` activities for the same Invoice where O2O notes mention `partially_settles` and `completes_settlement` (e.g., X4)  *partial payment pattern*. (Only qualifier phrases from O2O notes are used; no amount attributes.)  
   - **Modification type:**  
     - `normal` if no O2O note mentions a qualifier like `removed_before_dispatch` *and* no `Return Item` event occurs;  
     - `replacement` if O2O note mentions `removed_before_dispatch` (X7);  
     - `return` if `Return Item` and `Inspect Return` events occur (X8);  
     (Only these explicit terms from O2O notes define modification type. X1–X4 (except X4's payment), X5–X7 (except X7's qualifier), X8's return are covered.)  
   - **External involvement:**  
     - `logistics` if any `Pack` activity includes an `EXT-IA` (external Item) or `EXT-OA` (external Order container) in its arguments;  
     - `invoice` if any `Issue Invoice` includes `EXT-Ob`;  
     (Both can be true simultaneously in principle, but not in examples; flags are independent booleans.)  
   *Invariants preserved:* Business intent derived from explicit O2O phrasing (`bills only Ox`, `partially_settles`, `replaces`, `returns`), minimal feasibility (Pack before Dispatch), invoice scope consistency (invoice scope cannot be shared without explicit EXT-Ob).  
   *Information discarded:* Local ID names, item addition order (unless qualifier/return applies), exact timing of events beyond relative order implied by sequence, payment amounts, internal external names (OA/OB/IA beyond `EXT-` prefix), minor wording variations not matching qualifier phrases.  
   *Symmetry/transitivity:* Yes—conditions are binary/boolean checks or single-count checks based on observable events/O2O notes; no ambiguity.

*Fourth relation (optional, used internally for signature):* **Delivery-logistics consistency** — defined as "the number of Dispatch events for the Order equals 1 if all Packages are dispatched together (i.e., one Dispatch lists all Packages), and >1 if Dispatches are per-Package (i.e., Dispatch occurs before subsequent Packages are created)." This is equivalent to the Delivery intent criterion above and is used directly in the canonical signature (no extra relation defined separately).

All definitions are operational, reproducible (no ambiguity), and ignore irrelevant details (e.g., local ID order for Adds without qualifier). Borderline cases are handled by strict use of explicit O2O phrases (`removed_before_dispatch`, `partially_settles`, `returns`); no inference (e.g., X3's two Packs with one Dispatch  single delivery intent because Dispatch lists both Packages).

## 2. Canonical signatures

For the preferred equivalence relation (Business-semantic), a concise, identifier-renaming-invariant canonical signature is defined as a 7-element tuple:  
`(delivery_single, invoice_scope, payment_partial, has_replacement, has_return, external_logistics, external_invoice)` where:  
- `delivery_single` = `True` if exactly one `Dispatch` activity mentions the lead Order (regardless of number of Packages), `False` otherwise.  
- `invoice_scope` = `"order"` if `Issue Invoice` args contain only the Order (no `EXT-*`), `"shared"` if contains `EXT-Ob`.  
- `payment_partial` = `True` if there are exactly two `Record Payment` activities for the same Invoice *and* O2O notes for that execution mention `partially_settles` and `completes_settlement` (only for X4; others have one payment), `False` otherwise. *(Note: only check qualifier phrases; do not inspect amounts.)*  
- `has_replacement` = `True` if O2O note mentions `removed_before_dispatch` (only X7), `False` otherwise.  
- `has_return` = `True` if `Return Item` and `Inspect Return` events exist (only X8), `False` otherwise. *(Return implies inspection in X8; check both events.)*  
- `external_logistics` = `True` if any `Pack` args include `EXT-IA` or `EXT-OA` (e.g., X5), `False` otherwise.  
- `external_invoice` = `True` if any `Issue Invoice` args include `EXT-Ob` (e.g., X6), `False` otherwise.  

Signature computation is deterministic and requires only event list and O2O notes (no internal assumptions). Python-like pseudocode:

```python
def compute_semantic_signature(events, o2o_notes):
    # Extract Order ID from first Create event (e.g., "Create Order{Order:O1}")
    # For simplicity, assume one Order per execution; find all events mentioning Order
    order_events = [ev for ev in events if "Order:" in str(ev)]
    dispatch_events = [ev for ev in events if "Dispatch" in str(ev) and any("Order:" in str(arg) for arg in ev.args)]
    
    delivery_single = (len(dispatch_events) == 1)
    
    invoice_event = next(ev for ev in events if "Issue Invoice" in str(ev))
    invoice_args = set(str(arg) for arg in invoice_event.args)
    invoice_scope = "shared" if any(arg.startswith("EXT-") for arg in invoice_args) else "order"
    
    # Find Invoice ID from invoice_event, count Record Payment for it
    invoice_id = None
    for arg in invoice_event.args:
        if "Invoice:" in str(arg):
            invoice_id = arg.split(":")[-1]  # e.g., "V11"
            break
    payment_events = [ev for ev in events if "Record Payment" in str(ev)]
    payment_for_invoice = [ev for ev in payment_events if invoice_id in str(ev)]
    payment_partial = (len(payment_for_invoice) == 2 and 
                       "partially_settles" in o2o_notes and "completes_settlement" in o2o_notes)
    
    has_replacement = ("removed_before_dispatch" in o2o_notes)
    has_return = ("Return Item" in str(events) and "Inspect Return" in str(events))
    
    pack_events = [ev for ev in events if "Pack" in str(ev)]
    external_logistics = any(str(arg).startswith("EXT-") for ev in pack_events for arg in ev.args)
    
    invoice_event_str = str(invoice_event)
    external_invoice = any(str(arg).startswith("EXT-") for arg in invoice_event.args)
    
    return (
        delivery_single,  # bool
        invoice_scope,   # "order" or "shared"
        payment_partial, # bool
        has_replacement, # bool
        has_return,      # bool
        external_logistics, # bool
        external_invoice  # bool
    )
```

*Notes on implementation:*  
- `o2o_notes` is a simple string or set containing phrases like "removed_before_dispatch", "partially_settles", "completes_settlement", etc., extracted from the O2O section.  
- `has_return` checks for both `Return Item` and `Inspect Return` event labels (exact match), as in X8.  
- `payment_partial` is `True` only if *both* qualifier phrases appear in O2O notes for that execution (X4); for others, it is `False` even if two payments exist without qualifiers (not present in examples).  
- Signature ignores ID names; uses only roles and O2O note phrases.  
- Reproducible: same input  same tuple.

  (1 Dispatch; Invoice only Order; 1 Payment; no qualifier/return; no external)

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` performs exact structural equivalence on OCEL (Object-Centric Event Logs) by comparing object keys that include raw object identifiers. By default, it preserves raw IDs (e.g., `Order:O1`, `Package:P11`), so two executions with different local IDs (X1 vs X2) would be considered different unless IDs are renamed consistently within the cluster. However, `pm4py`'s key structure typically includes event type and object IDs, so `Create Order{Order:O1}` vs `Create Order{Order:O2}` would not match under default keys, leading to finer clusters (e.g., X1 and X2 separate) if IDs are not canonicalized.

- **What `pm4py` preserves:** Exact object ID values (e.g., `O1`, `P11`) in keys; event sequence order; object-type incidence (which objects appear in which events). It does **not** by default incorporate O2O qualifiers (e.g., `removed_before_dispatch`) or business phrases (e.g., `partially_settles`), since those are metadata outside the OCEL core.

- **Why raw IDs make clusters too fine:** Raw IDs (O1 vs O2, P11 vs P21) are execution-specific and renameable. Thus `pm4py.cluster_equivalent_ocel` with default keys would cluster each execution separately or only group X1=X2 if IDs are renamed beforehand, but without renaming, X1 and X2 would differ due to ID mismatch. However, business semantic equivalence considers ID renaming natural (X1 and X2 are logically same), so exact ID equivalence is overly strict for operational segmentation.

- **Canonicalization/post-processing outline (Python):**

              if "Payment:" in str(arg):
                  pay_id = arg.split(":")[-1]
                  payment_ids.append(pay_id)
              if arg.startswith("EXT-"):
                  parts = arg.split("-", 1)
                  if len(parts) == 2:
                      ext_type = parts[1][:2]  # "OA", "IA", "OB"
                      if ext_type in ["OA", "OB"]:

                      elif ext_type == "IA":

      # Extract O2O note phrases

              if phrase.startswith(("removed_before_dispatch", "partially_settles", "completes_settlement", "bills only", "bills O and")):
                  o2o_phrases.add(phrase.lower())
      
      # Return a lightweight signature dict for semantic clustering
      return {

          "invoice_scope": "shared" if any("EXT-" in str(arg) for arg in ocel.events[0].arguments) else "order",  # crude, refine with Issue Invoice check
          "payment_partial": len([e for e in ocel.events if "Record Payment" in str(e)]) == 2 and "partially" in str(ocel.notes),
          "has_replacement": "removed_before_dispatch" in str(ocel.notes),
          "has_return": "Return Item" in str(ocel.events) and "Inspect Return" in str(ocel.events),
          "external_logistics": bool(ext_item_ids),
          "external_invoice": bool(any("EXT-OB" in str(arg) for arg in ocel.events[0].arguments)),
          "o2o_phrases": frozenset(o2o_phrases)

## 8. Limitations and recommendation

- **No single equivalence notion is best for all purposes:**  
  - *Compliance monitoring:* Use **activity-sequence equivalence** (or pm4py exact structural with canonical ID renaming). Detects event-order violations (e.g., Dispatch before Pack), which are regulatory risks. Fine clusters ensure no false negatives.  
  - *Operational segmentation:* Use **business-semantic equivalence** (preferred clusters). Groups orders by fulfillment pattern (e.g., SemA for single-delivery, SemF for return), enabling targeted process improvements (e.g., warehouse packing efficiency for SemA, return-inspection workflow for SemF). Avoids alert fatigue from ID-based splits.  
  - *Root-cause analysis:* Use **typed structural equivalence** under renaming. Identifies topology bugs (e.g., Pack after Dispatch, missing Package-Item link), useful for debugging execution flows. Structural isomorphism highlights graph inconsistencies.  
  - *Descriptive reporting:* Use **business-semantic equivalence**. KPIs like "% orders with single delivery" (SemA+SemC+SemD), "% with return" (SemF), "% with invoice sharing" (SemD) are clear to stakeholders; avoids technical ID details.

- **Limitations:**  
  - Semantic equivalence relies on explicit O2O phrase matching (`removed_before_dispatch`, etc.). If qualifiers are vague (e.g., "item may be swapped"), signature may misclassify; requires precise phrase documentation.  
  - External flags (`EXT-*`) are detected by prefix only; internal names (OA/OB/IA) are not analyzed (correct per constraints), but if external object lifecycle differs (e.g., shared vs dedicated), prefix alone may not capture nuance (but EXT- prefix indicates externality, which is sufficient for logistics risk).  
  - Activity-sequence equivalence is strict on Add item order; if business cares about Add order (e.g., inventory availability), Activity-sequence should allow order significance (adjust normalization), but current definition treats it irrelevant. This is valid per examples (no such rule stated).  
  - Payment partial relies on qualifier phrases; without phrases, two payments could be partial in practice but not detected (e.g., amount < invoice total). For financial monitoring, add amount check in reporting layer; semantic clusters can include a "payment-check" filter for finance views.

- **Recommendation:**  
  > For practical use with these executions, adopt **business-semantic equivalence** as the default clustering for operational and reporting purposes (e.g., dashboard clusters SemA, SemB, ..., SemF), and use **activity-sequence equivalence** with ID canonicalization for compliance audits. For pm4py integration, first canonicalize object IDs (map to roles O/I/P/etc.), then apply `pm4py.cluster_equivalent_ocel` for exact structural checks on flagged clusters (e.g., if SemB cluster has Draft events), and finally merge clusters by semantic signature for segmentation. This balances precision (compliance), usability (clear clusters), and safety (no over-clustering due to IDs).

*Rationale:* Business-semantic clusters directly reflect customer-facing intent (delivery single/split, return handling, invoice scope), enabling actionable insights with minimal noise. Activity-sequence provides strict event-order validation for compliance. Post-processing with canonicalization ensures pm4py results are reusable without ID drift. No single method suffices all goals; the recommendation uses the appropriate level per purpose, as confirmed by perturbation robustness and borderline case analysis.
