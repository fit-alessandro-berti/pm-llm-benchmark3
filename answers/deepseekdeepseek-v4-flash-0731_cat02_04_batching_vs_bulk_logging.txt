| G8 | Waiting from arrival to first start at 15:38 is real only if clocks are aligned; clock skew can bias the reported wait by minutes. | Contiguous 7-minute intervals are plausible service times, but minute-rounded timestamps add ±1 minute uncertainty. | The safety hold creates an idle period followed by saturation; if the hold is not modeled as capacity loss, T-H falsely becomes the bottleneck. |

G6-like data is important because the same one-line record can be read in two contradictory ways. Using `queue_arrival`  `start` treats 17:00 as the end of waiting and therefore creates very large waiting times. Using `start`  `complete` treats 17:00 as both the start and finish of service and therefore creates near-zero service times. If a ticket was actually worked on at 15:00 and closed at 15:05, then inserted at 17:01, the true waiting is `15:00 - queue_arrival` and the true service is `15:05 - 15:00`. The log instead reports `17:00 - queue_arrival` as waiting and `17:00 - 17:00` as service. Thus waiting is inflated by exactly the unrecorded service-plus-reporting latency, and service is deflated to zero. The only safe choice is to treat 17:00 as a censoring point, not as an execution timestamp.

def pair_overlap_rate(g):
    n = len(g)
    if n < 2:
        return 0.0
    starts = g["start_dt"].values
    ends = g["complete_dt"].values
    overlaps = 0
    for i in range(n):
        for j in range(i + 1, n):
            if starts[i] < ends[j] and starts[j] < ends[i]:
                overlaps += 1
    return overlaps / (n * (n - 1) / 2)

    return adj

# 5. Robustness and alternative explanations

If resource IDs are trusted as unique workers, G5 changes from a shared-account artifact to apparent multitasking by one analyst. The temporal pattern is the same, but the physical interpretation is completely different: one person juggling four analyses versus three people sharing a login. The same ambiguity affects G7 if multiple technicians could share `T-G`, and it would affect G2 if the “single begin group” screen context were removed. For G1, resource identity as a machine is more reliable, but it still does not tell us whether all four fixture slots were active simultaneously.

If timestamps are treated as exact, PM4Py will confidently detect overlapping batches in G2, G3, and G7, and a zero-duration batch in G6. If timestamps are interval-censored by their stated precision, those detections become much weaker. A 1-minute granularity means that “10:00” could represent a range of possible true starts; the four G2 starts could have been ordered within that minute. A 15-minute granularity in G7 means that “14:00” and “14:15” give almost no information about real start/end order. Exact timestamps are therefore only safe for G4, G8, and partly G1; all other clusters need sensitivity analysis or bounds.

Several clusters illustrate the same temporal pattern supporting multiple physical explanations:

1. **G1 and G7**: Both show identical starts and identical completions. G1 is best explained as a physical four-item fixture batch; G7 is best explained as coarse rounding. The pattern alone cannot distinguish “simultaneous work” from “same rounded logging time.”
2. **G2**: All starts equal with staggered completions could be a begin-group batching convenience, or it could be 1-minute timestamp coarsening hiding ordered starts. The UI context resolves it, but not the raw timestamps.
3. **G3**: All completions equal with staggered starts could be a bulk form submission, or genuine concurrent reviews finalized at the same time. The source’s form behavior is needed to choose.
4. **G8**: A long gap before contiguous service could be queue accumulation during a safety check, an unmodeled idle period, or clock skew between the safety system and the repair queue.

# 6. Data-collection redesign

A prioritized redesign should address the following.

1. **Execution timestamps**: Emit timestamps at actual state transitions, not at form submission or database insertion. Store `event_type` as `start`, `complete`, `pause`, or `resume`. Never derive both start and complete from the same database write.
2. **Recording timestamps**: Keep `recorded_at` as a separate insertion timestamp. It is useful for diagnosing batching artifacts, but it should never be used as the execution time.
3. **Source clocks**: Synchronize all systems to a common time source. Record clock offsets for legacy systems. If clock skew is unavoidable, store the offset with each event so waiting and service intervals can be adjusted.
4. **Resource/badge identity**: Replace shared logins with unique badge or session identifiers for human tasks. For shared pools, retain a session ID and a user ID per session. For machines, store asset ID and operator, if relevant.
5. **Group/batch identifiers**: Add `work_order_id`, `fixture_id`, `lot_id`, `folder_id`, and `submission_batch_id`. This directly separates operational batching from reporting batching.
6. **Workstation capacity**: Record the number of slots per fixture, number of inspectors, and capacity of each workstation. If capacity is greater than one, log slot-level start/complete events when possible.
7. **Pause/resume events**: Record interruptions such as safety holds, breaks, failures, and end-of-shift as separate state events with reason codes. Do not let a pause look like service time or waiting time.
8. **Timestamp precision metadata**: Preserve raw timestamp values, declared precision, actual accuracy, rounding rule, and timezone. Avoid exporting HH:MM-format strings that hide seconds.

# 7. Final adjudication

High confidence can be placed in the qualitative interpretation of most clusters, but not all of them support quantitative process-mining.

- **G1**: High confidence in a capacity-supported simultaneous batch. Use it only with a capacity-aware model.
- **G2**: High confidence in start batching via the begin-group UI. Waiting and service times need correction before use.
- **G4**: High confidence in sequential processing. It is the most queue-analysis-friendly cluster, though seconds should be restored if possible.
- **G7**: High confidence in timestamp coarsening. It should be excluded from point-estimate waiting/service calculations.
- **G8**: High confidence in queue accumulation after a safety-related capacity loss, but exact waiting times require clock reconciliation.

Clusters that should be excluded or interval-censored in queue analysis include:

- **G3**: use starts if trusted, but interval-censor completions; do not compute service times from the bulk submission time.
- **G5**: exclude from resource-level utilization and bottleneck detection until badge-level identity is available.
- **G6**: exclude from both waiting and service-time analysis; treat 17:00 as a censoring boundary, not as actual execution time.
- **G7**: exclude from point estimates entirely because of 15-minute rounding.

Operational validation is required before drawing final performance conclusions for:

- **G1**: raw PLC seconds and fixture-slot mapping;
- **G3**: per-review form submission timestamps;
- **G5**: session/badge identity;
- **G8**: clock offsets among the safety system, queue system, and scanner.
