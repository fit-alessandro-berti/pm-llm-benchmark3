## 1. Temporal Data Semantics

I reconstruct each case as an ordered event stream by `(time:timestamp, event_index)`. Blank attribute cells are treated as “no update at this event”; they never clear a prior value and never mean `null`. A nonblank attribute value becomes effective at that event’s timestamp, and for equal timestamps the lower `event_index` is applied first. For a `Release_Funds` event, the state snapshot includes all prior events and any same-timestamp events with lower `event_index`; it excludes later events and same-timestamp events with higher `event_index`.

I distinguish:

- **Event time**: when the business event occurred.
- **Effective time**: when an attribute value becomes operative; default is the event timestamp unless evidence establishes another effective time.
- **Record time**: when a database row or document was inserted/created.
- **Evidence time**: when approval/signature/independent evidence indicates that a fact existed or was approved.

Final case attributes are never copied backward. A late database record can be evidence of earlier approval, but record time alone is not decisive; approval evidence and effective timing control exemption validity. Material amount changes are evaluated against the amount known at the latest `Standard_Review` or `Enhanced_Review`: a later increase of more than 20% invalidates that review for amount-dependent obligations; a decrease does not by itself invalidate. If the amount at review or the later amount is unknown, R4 is not safely classifiable without other evidence. Missing decisive amount, risk, jurisdiction, or customer type is classified as `INDETERMINATE` unless other evidence resolves it. TX-311 specifically uses `event_index` ordering: the `Enhanced_Review` at index 3 occurs before the jurisdiction update to `DE` at index 4, but the release snapshot has jurisdiction `DE`.

### Formal pseudo-logic

Let `e  r` mean `(t_e < t_r) OR (t_e = t_r AND i_e < i_r)`, where `i` is `event_index`. Let `Snap(e)` be the attribute state after applying all nonblank updates from events `e'` with `e'  e`, then applying `e`’s own nonblank updates. Let `PostAmt(m)` be the amount after an `Update_Amount` event `m`.

```text
R1(r):
  Release_Funds(r)
   known(Snap(r).amount)
   Snap(r).amount >= 100000
   known(Snap(r).jurisdiction)
   Snap(r).jurisdiction != "DE"
   not ValidExemption(r, "R1", Snap(r))
   exists e (
       Enhanced_Review(e)
        e  r
        ERValidForR1(e, r)
    ).

ERValidForR1(e, r):
  known(Snap(e).amount)
   forall m (
       Update_Amount(m)
        e  m  r
        known(PostAmt(m))
          PostAmt(m) <= 1.2 * Snap(e).amount
    ).
If any required amount is unknown, R1/ER validity is INDETERMINATE.

R2(r):
  Release_Funds(r)
   (Snap(r).risk_level = "HIGH"  Snap(r).customer_type = "PEP")
   exists e1, e2 (
       Enhanced_Review(e1)
        Compliance_Approve(e2)
        e1  e2
        e2  r
    ).
If risk/customer type is unknown and trigger cannot be excluded, INDETERMINATE.

R3(r):
  Release_Funds(r)
   exists u (
       Sanctions_List_Update(u)
        u  r
        jur(u) = Snap(r).jurisdiction
        u is after the latest Sanctions_Screen before u
    )
   exists s2 (
       Sanctions_Screen(s2)
        u  s2
        s2  r
    ).
If jurisdiction unknown, INDETERMINATE.

R4(v, m):
  Review(v)  {Standard_Review, Enhanced_Review}
   Update_Amount(m)
   v  m
   known(Snap(v).amount)
   known(PostAmt(m))
   PostAmt(m) > 1.2 * Snap(v).amount
   Invalidates(v, m) for amount-dependent obligations.
If either amount is unknown, R4 status is INDETERMINATE for that pair.
Decrease or increase 20% does not invalidate by itself.

R5(r, rule, scope):
  ValidExemption(r, rule, scope) :-
    Exemption(x)
     approved_by(x) = "Head_Compliance"
     effective_from(x) <= t_r
     t_r <= expires(x)
     scopeMatch(x, scope)
     EvidenceApprovalExistedBy(x, t_r)
     rule  waives(x).

RecordTime(x) > t_r does not by itself invalidate prior approval evidence,
but a displayed backdated field alone is not conclusive.

R6:
  If a decisive predicate for R1–R5 depends on an unknown value
  and cannot be established or excluded  INDETERMINATE.

R7:
  Snap(r) uses only events e'  r and r's own nonblank updates.
  Final case state is never copied backward to earlier events.
```

## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).** If an immutable release payload or independent contemporaneous evidence proves the release amount was below EUR 100,000, R1 would not trigger and the case would likely be compliant. If the release amount is proven to be at least EUR 100,000, the ER at 11:15 may or may not satisfy R1: the review document has no amount, so a strict reading says the ER did not review the high-value amount and R1 is not satisfied. If one accepts the ER as a generic enhanced review despite the missing amount and no later material change, the case could become compliant. The later settlement amount of 150,000 is reliable at settlement time but does not by itself establish the immutable release amount; without a release payload, the release-time amount remains indeterminate.

**TX-310 (INDETERMINATE).** If independent evidence establishes that Head_Compliance actually approved EX-88 at 08:45 or otherwise before the 10:00 release, EX-88 could be valid and would waive R1, producing `JUSTIFIED_EXCEPTION`. Independent corroboration could include a contemporaneous approval log, a call record, an independent witness, or a qualified signature timestamp before release. If that evidence is absent or rejected, EX-88 is not valid at release and the case is `NONCOMPLIANT` because there is no `Enhanced_Review` and the only review is a `Standard_Review`. The 10:30 certificate creation after release and the requester’s interested witness statement weigh strongly against timely approval.

**TX-302.** The result depends on accepting the late database record as evidence of earlier approval. The qualified digital signature and hash timestamp 09:05, plus the documented outage, strongly support approval before the 09:40 release. If a conservative policy requires the database record itself to exist before release, or requires approval before the displayed `effective_from` 09:00, EX-77 could be rejected and TX-302 would become `NONCOMPLIANT` for R1. Under R5 as written, late record time is not fatal when other evidence supports earlier approval.

**TX-308.** The case is compliant because R4 says a decrease does not by itself invalidate a review. If an alternative reading treated any amount change after review as requiring a new ER, then the 14:25 decrease from 140k to 100k would invalidate the 14:20 ER and TX-308 would become `NONCOMPLIANT`. If the amount at release were interpreted as 99,999 rather than exactly 100,000, R1 would not trigger because “at least EUR 100,000” includes exactly 100,000.

**TX-309.** The ER at 15:25 reviewed 118k; the later 15:28 update to 145k is a 22.9% increase and invalidates the ER for R1. If the 15:28 increase were treated as covered by the ER because it was expected or within some tolerance, the case could become compliant. If the 15:25 ER were considered to review a projected amount rather than the then-current 118k, evidence would be needed. Without such evidence, the material-change invalidation is clear.

**TX-311.** At release, jurisdiction is `DE`, so R1 is not triggered. The same-timestamp ordering means the ER at index 3 occurred while jurisdiction was still `US`, and the jurisdiction update to `DE` occurred at index 4. If the jurisdiction update were considered ineffective at release, release jurisdiction would be `US`; R1 would trigger, but the 16:20 ER is after the 16:10 amount update and before release, so R1 would likely still be satisfied. If R1 were incorrectly evaluated at ER time rather than release time, the state would differ, but the final classification remains compliant on these facts.

            if er_time is not None and er_time < t:
                if pd.isna(er_amt):
                    r1_er_valid = "UNKNOWN"
                else:
                    amount_updates = g[
                        (g["concept:name"] == "Update_Amount")
                        & (g["time:timestamp"] > er_time)
                        & (g["time:timestamp"] < t)
                    ]
                    invalid = False
                    unknown = False

                    for _, ar in amount_updates.iterrows():
                        new_amt = ar["amount"]
                        if pd.isna(er_amt) or pd.isna(new_amt):
                            unknown = True
                        elif new_amt > er_amt * 1.2:
                            invalid = True

                    if unknown:
                        r1_er_valid = "UNKNOWN"
                    elif invalid:
                        r1_er_valid = False
                    else:
                        r1_er_valid = True
            else:
                r1_er_valid = False if r1_trigger is True else None

            ex_status = valid_exemption(ex_id, t, amt, risk, jur, cust, "R1")

            if r1_trigger is True:
                if ex_status == "VALID":
                    r1_satisfied = True
                elif ex_status == "REVIEW_REQUIRED":
                    r1_satisfied = "REVIEW_REQUIRED"
                elif r1_er_valid == "UNKNOWN":
                    r1_satisfied = "INDETERMINATE"
                else:
                    r1_satisfied = bool(r1_er_valid is True)
            elif r1_trigger == "UNKNOWN":
                r1_satisfied = "INDETERMINATE"
            else:
                r1_satisfied = "NOT_TRIGGERED"

            # R2 trigger and satisfaction.
            if risk == "HIGH" or cust == "PEP":
                r2_trigger = True
            elif pd.isna(risk) or pd.isna(cust):
                r2_trigger = "UNKNOWN"
            else:
                r2_trigger = False

            er_before = er_time if er_time is not None and er_time < t else None
            comp_before = last_compliance if last_compliance is not None and last_compliance < t else None

            if r2_trigger is True:
                if er_before is None or comp_before is None:
                    r2_satisfied = False
                elif comp_before > er_before:
                    r2_satisfied = True
                else:
                    r2_satisfied = False
            elif r2_trigger == "UNKNOWN":
                r2_satisfied = "INDETERMINATE"
            else:
                r2_satisfied = "NOT_TRIGGERED"

            # R3 trigger and satisfaction.
            r3_trigger = False
            r3_satisfied = "NOT_TRIGGERED"

            if pd.isna(jur):
                r3_trigger = "UNKNOWN"
                r3_satisfied = "INDETERMINATE"
            else:
                list_updates = g[
                    (g["concept:name"] == "Sanctions_List_Update")
                    & (g["time:timestamp"] < t)
                ]

                for _, lu in list_updates.iterrows():
                    lu_jur = lu["jurisdiction"] if not is_blank(lu["jurisdiction"]) else None
                    if lu_jur == jur:
                        screens = g[
                            (g["concept:name"] == "Sanctions_Screen")
                            & (g["time:timestamp"] < t)
                        ]
                        latest_screen_time = screens["time:timestamp"].max() if not screens.empty else pd.NaT

                        if pd.isna(latest_screen_time) or lu["time:timestamp"] > latest_screen_time:
                            r3_trigger = True
                            post_screens = screens[screens["time:timestamp"] > lu["time:timestamp"]]
                            r3_satisfied = not post_screens.empty
                        break

            unknown_flags = []
            if pd.isna(amt):
                unknown_flags.append("amount_unknown")
            if pd.isna(risk):
                unknown_flags.append("risk_unknown")
            if pd.isna(jur):
                unknown_flags.append("jurisdiction_unknown")
            if pd.isna(cust):
                unknown_flags.append("customer_type_unknown")

            if (
                r1_satisfied in ["INDETERMINATE", "REVIEW_REQUIRED"]
                or r2_satisfied == "INDETERMINATE"
                or r3_satisfied == "INDETERMINATE"
            ):
                cls = "REVIEW_REQUIRED"
            elif r1_satisfied is False or r2_satisfied is False or r3_satisfied is False:
                cls = "NONCOMPLIANT_HINT"
            elif ex_status == "VALID" and r1_trigger is True:
                cls = "JUSTIFIED_EXCEPTION_HINT"
            elif (
                r1_satisfied in [True, "NOT_TRIGGERED"]
                and r2_satisfied in [True, "NOT_TRIGGERED"]
                and r3_satisfied in [True, "NOT_TRIGGERED"]
            ):
                cls = "COMPLIANT_HINT"
            else:
                cls = "REVIEW_REQUIRED"

            results.append({
                "case": case,
                "release_time": t,
                "event_index": idx,
                "amount": amt,
                "risk_level": risk,
                "jurisdiction": jur,
                "customer_type": cust,
                "exemption_id": ex_id,
                "r1_trigger": r1_trigger,
                "r1_exemption_status": ex_status,
                "latest_er_time": er_time,
                "latest_er_amount": er_amt,
                "r1_er_valid": r1_er_valid,
                "r1_satisfied": r1_satisfied,
                "r2_trigger": r2_trigger,
                "latest_compliance_time": comp_before,
                "r2_satisfied": r2_satisfied,
                "r3_trigger": r3_trigger,
                "r3_satisfied": r3_satisfied,
                "material_changes": material_changes.copy(),
                "unknown_flags": ",".join(unknown_flags),
                "classification_hint": cls,
            })

diag = pd.DataFrame(results).sort_values("case").reset_index(drop=True)

pd.set_option("display.max_columns", None)
pd.set_option("display.width", 250)
print("Case-level diagnostics:")
print(diag[[
    "case", "release_time", "amount", "risk_level", "jurisdiction", "customer_type",
    "r1_trigger", "r1_exemption_status", "latest_er_time", "r1_er_valid", "r1_satisfied",
    "r2_trigger", "latest_compliance_time", "r2_satisfied",
    "r3_trigger", "r3_satisfied", "classification_hint", "unknown_flags"
]])

# Optional: coarse control-flow variant check.

    variants = pm4py.get_variants(df_pm)
    print("\nControl-flow variants (activity order only; not data-aware):")
    for variant, freq in variants.items():
        print(freq, variant)
except Exception as exc:

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** Using the final case amount, risk, jurisdiction, or customer type to judge an earlier release can wrongly apply future changes backward. TX-311’s jurisdiction changes to `DE` after the ER; R1 must be evaluated using the release-time snapshot, not the final state alone.

2. **Post-hoc exemptions.** A control-flow trace might see `Record_Exemption` after `Release_Funds` and flag a deviation, even when strong evidence shows timely approval. TX-302 is the opposite: the late record is after release, but the qualified signature supports earlier approval. Control-flow alone cannot distinguish record time from approval evidence time.

3. **Material changes after review.** TX-301 and TX-309 contain the expected activities, but amount increases after review invalidate the review for amount-dependent obligations. Pure activity conformance cannot compute “>20% increase after latest review.”

4. **Conditional activation.** R1 activates only for non-`DE` jurisdiction and amount 100,000; R2 only for `HIGH` risk or `PEP`; R3 only after a sanctions-list update for the current jurisdiction. Control-flow conformance does not evaluate these data-dependent conditions.

5. **Missing data.** TX-305 has an unknown amount at release. A control-flow trace may see `Enhanced_Review` before `Release_Funds` and look compliant, but R6 requires an indeterminate classification when the decisive amount cannot be established or excluded.

6. **Same-timestamp ordering.** TX-311 has an ER and a jurisdiction update at the same timestamp. `event_index` changes the state at and after the ER. Control-flow-only tools often ignore or poorly represent same-timestamp order unless the log is explicitly sorted and causality-safe.

7. **Exemption scope and evidence.** TX-310’s EX-88 is within displayed scope but has contradictory approval evidence. Control-flow can see a release referencing an exemption, but cannot assess whether the approver was authorized, whether the certificate was created after release, or whether a witness is independent.

8. **Review type substitution.** TX-301 has a `Standard_Review`, and TX-307 has `Compliance_Approve` of a standard packet. Neither is an `Enhanced_Review`. Control-flow conformance may treat review-like activities as equivalent unless the model distinguishes semantic review types and packet scope.

9. **Sanctions-list update timing.** TX-304 requires comparing the jurisdiction in the list update to the release state and checking for a screen after the update. Activity order alone cannot evaluate list version, jurisdiction match, or whether the screen occurred after the relevant list update.

## 7. Recommended Logging and Control Improvements

- Write an **immutable release payload** for every `Release_Funds` event containing amount, currency, risk level, jurisdiction, customer type, rule version, exemption ID if claimed, and the exact timestamp used for release.
- Record separate **event time, effective time, record time, and evidence time** for attribute changes and exemptions. For approvals, log qualified signature/certificate time, approval time, and database insertion time.
- Add **stable event ordering**: case ID plus monotonically increasing sequence number, `event_index`, source-system transaction ID, and hash chaining or append-only audit trail.
- Log **exemption scope** explicitly: jurisdiction, customer type, amount minimum/maximum, waived rules, effective-from, expiry, approver identity, approval evidence type, and approval evidence timestamp.
- For oral or exceptional approvals, require **independent corroboration** and record the corroborating source; do not rely solely on a transaction requester’s witness statement.
- Record **change provenance** for every attribute update: previous value, new value, source system, actor, reason, effective time, record time, and whether the value was verified.
- Store **material-change calculations** at review and release time: review ID, amount at review, current amount, percentage change, threshold result, and whether the review is invalidated.
- Use explicit **unknown-value markers** rather than blank cells or silent defaults, with reason codes such as `amount_feed_unavailable`, `review_document_missing_amount`, or `release_payload_omitted`.
- Version and snapshot **sanctions lists** with effective timestamps; log which list version each sanctions screen used and which jurisdiction was added or removed.
- Record **rule version and policy evaluation timestamp** with each decision so later policy changes do not retroactively alter old decisions.
- Implement **data-aware conformance/replay checks** in addition to control-flow conformance: replay event-time state, evaluate preconditions at each obligation trigger, and emit `REVIEW_REQUIRED` when evidence is contradictory or missing.
- Preserve the full activity and data history for `Standard_Review`, `Enhanced_Review`, and `Compliance_Approve`, including which packet and which attributes were reviewed, to prevent review-type substitution.
