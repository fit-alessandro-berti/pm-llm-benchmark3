## 1. Equivalence design space

**Activity-sequence equivalence.** Project each Order execution to its timestamp-ordered list of activity labels, retaining repeated labels. Two executions are equivalent when these lists match exactly. This preserves activity names, order, and repetition; it discards object types and identities, event-to-object links, multiplicities of participating objects, external sharing, and O2O relations. Exact list equality is reflexive, symmetric, and transitive. Same-time events need a fixed tie-break rule; alternatively, represent them as unordered groups and compare those groups.

**Typed structural equivalence.** Represent each execution as an attributed event-object graph: event nodes carry activity labels and order; object nodes carry type and external/local status; E2O edges record participation; O2O edges record relations. Two executions are equivalent if there is a type- and attribute-preserving graph isomorphism that maps the lead Order to the lead Order and preserves the event order. This preserves typed multiplicities, incidence, and any included qualifiers, while discarding local identifiers. Isomorphism is reflexive, symmetric, and transitive. For concurrent or same-time events, preserve a partial order or unordered event group instead of imposing an arbitrary order.

**Business-semantic equivalence.** Project the graph to a declared set of business motifs, then compare those projections. For this answer, the projection preserves package and delivery counts and links, external sharing by object type, payment-event multiplicity, replacement/removal, and return/inspection/repack motifs. It ignores local identifiers and incidental event interleavings that do not change those motifs. Equality of a fixed canonical projection is reflexive, symmetric, and transitive. Same-time or concurrent events are represented as unordered unless their causal order is part of a motif. Changing the projection changes the relation, so the projection must be stated with the results.

## 2. Canonical signatures

For the preferred relation, canonicalize the execution graph under local identifier renaming, then emit a projection containing the chosen motifs. One reproducible method is to enumerate all type-preserving renamings of local objects, serialize each graph, and choose the lexicographically smallest serialization. For larger executions, use a graph-isomorphism canonical-labeling library instead of enumerating permutations.

```python
def preferred_signature(execution):
    # execution contains events, objects, E2O edges, O2O edges,
    # timestamps/order, and relation qualifiers.
    graph = make_graph(
        lead_type="Order",
        preserve_event_labels=True,
        preserve_repeated_events=True,
        preserve_object_types=True,
        preserve_external_flags=True,
        preserve_e2o=True,
        preserve_o2o_qualifiers=True,
        preserve_event_order=True,
    )

    # Local IDs are renamed; external status and type remain.
    canonical_graph = canonical_label(
        graph,
        rename_local_ids=True,
        retain_external_identity=False,
    )

    return serialize_projection(
        canonical_graph,
        fields=[
            "package_item_membership",
            "package_delivery_membership",
            "delivery_count",
            "external_sharing_by_type",
            "payment_event_count",
            "replacement_or_removal",
            "return_inspect_repack_motifs",
        ],
    )
```

## 4. Cluster interpretations

- **S1 — Isolated single-package execution.** Signature: one package, one delivery, one invoice, one payment, no external sharing or exception motif. This is ordinary fulfillment and settlement. It offers a useful baseline; the main risk is treating X2’s identifier or item ordering as meaningful. A case-level event log can flatten it adequately. The cluster is stable under local renaming and reasonable item-order repairs.

- **S2 — Split packages, consolidated delivery.** Signature: two packages travel on one delivery. This can support packaging flexibility and consolidate transport, but creates a dependency on correct package-to-delivery links. A single delivery-level flattened trace may obscure separate package handling. The cluster is stable unless package or delivery links are missing or duplicated.

- **S3 — Split deliveries and staged payment.** Signature: two package-delivery legs and two payment events, with partial then completing settlement. This provides fulfillment flexibility but raises reconciliation and installment-tracking risks. Flattening to one case row or one payment total loses leg and payment multiplicity. The cluster is stable if the two payment events and their completion semantics are retained; it is less stable if those distinctions are repaired away.

- **S4 — Cross-order logistics sharing.** Signature: a package used by the lead Order also includes an external Order’s item. This may reflect consolidation opportunities, but creates allocation, ownership, and traceability risks. Order-centric flattening can make the package look private to the lead Order. The cluster depends on correct external references and is unstable if those references are absent or misclassified.

- **S5 — Cross-order financial sharing.** Signature: an invoice bills the lead and an external Order, with payment lacking order-level allocation. Consolidated billing may be intentional, but creates allocation and audit risks. Order-level flattened logs can misstate who was billed or settled. The cluster is unstable if external invoice links or allocation details are repaired or added.

- **S6 — Replacement/removal.** Signature: replacement or removal is recorded for an item initially packed, with a related dispatch. This can represent legitimate substitution, but creates inventory and customer-communication risks if the removed item is still counted as shipped. A simple activity sequence or unqualified event log represents it poorly. The cluster’s stability depends on retaining the qualified relation.

- **S7 — Return and repack.** Signature: initial dispatch, return, inspection, repack, and second dispatch for the returned item. This is a recovery flow that supports quality control, but adds handling cost and can complicate delivery and inventory status. Flattening to a final shipment or a single package per item hides the earlier dispatch and return. It is stable if return and repack events are reliably captured.

## 5. Borderline cases

**X1 versus X2.** Identifier-renaming typed equivalence and business-semantic equivalence group them. Raw-identifier exact equivalence may separate them; the activity sequences match. The reversed item-ID order is immaterial when Add Item events are treated as indistinguishable.

**X1 versus X5.** Activity-sequence equivalence groups them. A typed or semantic relation preserving external objects and cross-order package membership separates them. If external objects are omitted from the execution scope, a local-only relation may group them.

**X1 versus X6.** Activity-sequence equivalence groups them. Typed structure or a financial semantic projection separates them because the invoice bills an external Order and payment lacks order-level allocation. A projection that ignores external financial links could group them.

**X1 versus X7.** Activity-sequence equivalence groups them. A qualified-relation semantic projection separates them because one item was removed or substituted. A relation that ignores qualifiers and direct item participation at Dispatch could group them.

**X3 versus X4.** Both have two packages, so packing-strategy equivalence can group them. A delivery-topology or full lifecycle relation separates one consolidated delivery from two separate deliveries; payment multiplicity also differs.

**X4 versus X8.** A coarse exception-heavy or multi-delivery category can group them. A lifecycle-motif relation separates two forward deliveries with staged payment from a return, inspection, and repack sequence.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py function clusters executions using an exact key for the extracted lead-object executions. Depending on PM4Py version and OCEL conversion, the key may preserve activity order, event/object participation, object types, multiplicity, and raw object identifiers. Whether O2O relations and qualifiers participate should be checked for the installed version rather than assumed.

Raw identifiers can make exact clusters too fine: X1 and X2 differ in their local IDs despite matching after renaming. A useful workflow is to get exact clusters, canonicalize each member by typed graph structure, then aggregate members with equal canonical signatures. Keep external flags in the canonicalization when cross-order sharing matters.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD_TYPE,
    max_objs=10000,
)

semantic_clusters = defaultdict(list)

for exact_key, members in exact_clusters.items():
    for member in members:
        lead_id, execution_ocel = materialize_member(
            ocel, member, lead_type=LEAD_TYPE
        )
        graph = to_execution_graph(
            execution_ocel,
            lead_type=LEAD_TYPE,
            lead_id=lead_id,
            preserve_o2o=True,
            preserve_qualifiers=True,
            mark_external=True,
        )
        signature = preferred_signature(graph)  # Identifier-invariant
        semantic_clusters[signature].append(lead_id)
```

Exact equivalence is useful for duplicate detection, audit replay, or checking extraction consistency. Business clustering is better suited to operational segmentation. `max_objs` can limit large connected executions; shared packages or invoices may connect many Orders. A low cap can exclude or truncate the very shared cases of interest, while a high cap can increase memory and runtime. Report cap-affected cases explicitly.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** X7 loses its explicit removal/replacement distinction and may merge with X1 if the semantic projection does not preserve its item-level Dispatch difference. X4 loses partial/completing settlement labels but retains two payment events. X8 remains distinct through return and inspection activities.
- **Ignore external objects:** X5 may merge with X1 after removing external package participation; X6 may also merge after dropping the external invoice Order. Both sharing motifs disappear.
- **Collapse repeated same-label events:** X4’s repeated Pack, Dispatch, and payment events may be reduced to single labels, masking its multiplicities. X8 can lose evidence of repacking and redispatch, though Return and Inspect still distinguish it.
- **Treat Pack and Dispatch order as a partial order:** Independent package branches can be reordered without changing the cluster, provided each package is packed before its dispatch. X4 remains distinct from X3 because their delivery topology differs.
- **Treat payment multiplicity as an amount attribute:** X4 remains distinct only if installment count or staged-settlement status is retained. Aggregating payments to a total can erase the distinction between staged and single settlement.

## 8. Limitations and recommendation

These clusters depend on relation completeness. Missing qualifiers can hide replacement; incomplete external links can make shared execution appear isolated; duplicate events can inflate multiplicities. The examples omit amounts, quantities, cancellations, actors, and durations, so signatures should be interpreted as patterns in recorded data rather than complete business truth.

For **compliance monitoring**, use typed structural equivalence or a rule-refined semantic relation that preserves external sharing, qualifiers, payment multiplicity, and lifecycle order. For **operational segmentation**, use the preferred semantic relation to ignore harmless renaming while retaining actionable motifs. For **root-cause analysis**, start with semantic clusters and drill into exact structures and timing. For **descriptive reporting**, use concern-specific projections for logistics, finance, and returns. No single relation serves all purposes equally; a layered hierarchy preserves detail while supporting interpretable summaries.
