## 1. Target definition

The primary target is the probability of default within 90 days after activation, among applications that are eventually activated, using information available at a fixed early prediction time: 72 hours after application start. The unit is an application, deduplicated across known transfer links where possible. The estimand is predictive association in the activated population under the historical activation process, not default risk for every applicant or under a changed policy.

This conditions on a future event—activation—so it is suitable for retrospective risk prediction among accounts that activate, but it cannot directly serve as an unbiased early decision rule for every application. At prediction time, activation is unknown. A separate all-application multi-state target could predict eventual rejection, withdrawal, transfer, activation, or remaining open by a stated time, then predict default after activation among activated cases. That answers a process-outcome question rather than assigning “non-default” to rejected or withdrawn cases. A policy-specific counterfactual default target for all applicants would require assumptions about what would happen if each applicant were activated, which these data cannot establish.

## 2. Cohort construction

Use all 48,000 applications as the starting cohort. Define outcomes and availability at the extraction date, 15 February 2026, and apply label maturity only when the outcome feed is available and the 90-day horizon plus the feed-lag allowance has elapsed. For model training, use activated cases with a known mature outcome. Retain all other cases in the cohort accounting, but do not code them as non-default.

| Group | Count | Cohort treatment |
|---|---:|---|
| Mature activated, labeled | 21,600 | Include in primary binary outcome analysis |
| Activated, outcome/feed not mature | 3,600 | Not yet mature; exclude from binary training labels, retain for follow-up |
| Rejected | 9,100 | Competing process outcome; no default label |
| Withdrawn | 5,700 | Competing process outcome; no default label |
| Transferred | 2,900 | Competing event or missing follow-up; linkage incomplete |
| Still open | 5,100 | Censored at extraction; no default label |
| **Total** | **48,000** | |

The counts imply 25,200 activated cases in total. The primary outcome cohort consists only of the 21,600 with matured labels. This table treats the supplied categories as mutually exclusive; implementation should verify that against case-level event history and resolve overlaps before modeling.

Include cases started in the observation window with a valid application identifier and a prediction point that can be formed. Exclude duplicate event records only under a documented migration-aware deduplication rule, preserving an audit trail. Do not exclude a case merely because it was rejected, withdrawn, transferred, or open. A case without a complete 72-hour observation window at the extraction cutoff cannot contribute a 72-hour prefix at that cutoff.

## 3. Censoring and missing-label strategy

Ordinary right censoring applies to cases that have not reached a process outcome or the default horizon by extraction. Delayed labels are a separate availability issue: the 90-day outcome may have elapsed while its feed is still pending. Maturity should require both elapsed horizon and a received outcome, with the stated 35-day maximum lag used for conservative completeness checks.

Activation is a selection mechanism: default is defined only for activated accounts, and activation depends on the application process and policy. The activated-cohort model estimates risk in that selected population. Transfer can be a competing process event when no linked continuation is observed; with linkage, follow the case across identifiers. Because linkage exists for only 60%, report transfer follow-up separately and do not assume unlinked transfers are ordinary censoring. Permanently missing partner feeds are missing outcomes, potentially informative, rather than known non-defaults.

Primary analysis: train a binary model only on mature activated cases, with temporal validation and calibration in comparable activated cohorts. Report the selected population and use inverse probability of censoring/observation weighting only as a sensitivity analysis, conditional on measured predictors of activation and feed availability. Sensitivity analyses should include worst/best-case outcome bounds for missing feeds and transfers, and comparisons of linked versus unlinked transfer cases.

Observable assumptions include timestamp ordering, feed delay distributions among observed labels, and measured covariate differences by maturity or feed status. Conditional independence of missing labels or censoring can be partially probed using observed predictors but not proven. The counterfactual default outcomes of never-activated applications and outcomes permanently missing in a systematically different partner population are fundamentally untestable from these data.

## 4. Prefix extraction

Generate one 72-hour elapsed-time prefix per application, using events timestamped no later than start plus 72 hours. For a fixed event-count analysis, create prefixes after the first 1, 2, and 3 events, excluding the prediction event itself from later information. Short cases should remain represented with their available shorter prefix and an explicit prefix-length or “not yet reached” indicator; do not silently drop them. The risk set at each prediction point must be based on information then available.

Document requests and returns to Credit Review are repeated process behavior, not duplicates. Preserve them and derive loop counts and time between rework cycles. Map known migration-era activity aliases to canonical names using a versioned mapping; flag ambiguous records and inspect duplicate-event patterns before deduplicating. Do not treat all repeated same-activity events as duplicates.

## 5. Process-aware features

Static attributes available at application start include channel, region, and requested amount, subject to validation of when each was recorded. Prefix-derived features can include observed activities and variants, prefix length, elapsed time, time since last event, waiting intervals, current activity, document-request count, returns to Credit Review, and transition counts. Queue features may include time in queue or workload at the time, if historically timestamped data exists. Calendar features should include application start date, weekday, and policy period, with migration period separately represented.

Historical reference features could include resource experience at event time, prior resource workload, and process norms computed from training data only. Experience captured at extraction must not be backfilled as though it were experience at event time. Aggregates and process models must be fit using training history and made available only from past data to avoid temporal leakage.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated after final decision | Only if decision preceded the stated prediction time, which it ordinarily will not | Drop | Decision consequence leaks future process information |
| `decision_reason` | Populated at/after Accept/Reject | Only if recorded by prediction time | Drop for early prefix | Encodes decision and outcome selection |
| `collection_status` | Updated after activation and may reveal default | Never use for pre-activation prediction | Drop | Direct outcome leakage |
| Future events | Contract, activation, collections, default occur after prediction | Filter strictly to timestamps at or before prediction time | Drop from prefix | Direct look-ahead |
| `documents_total` | Nightly snapshot may include later same-day uploads | Use timestamped document events no later than prediction time | Repair | Snapshot timing is ambiguous |
| `risk_score` | Updated at several events | Select latest value recorded by prediction time; retain update time/version | Repair | Later score updates can leak decisions or outcomes |
| Resource experience | Measured at extraction, not event time | Reconstruct experience using history available by event time | Repair or drop | Current value leaks future tenure |
| `default_90d` | Repeated when known; label may arrive later | Use only as outcome after maturity; never as feature | Drop from predictors | Target leakage |
| `label_available_at` | Captures feed timing and observation process | Use to define label maturity and censoring, not as a predictor | Restrict to audit | Can encode future observability |

## 7. Validation design

Use rolling temporal backtests by application start time, with outcomes evaluated only after the 90-day horizon and feed-delay window have matured. For example, train on earlier periods, validate on a later pre-policy period, then test on post-1 July 2025 cases once their outcomes are mature. Report performance separately before and after the policy change; avoid pooling across threshold regimes without period-specific calibration. The October migration requires an additional data-quality and performance slice, with canonical activity mapping fixed using documented rules.

A cutoff-based split should ensure every training label was available by the simulated training cutoff. Prefix features must also be reconstructed as of their prediction times. Evaluate discrimination and calibration among mature activated accounts using AUROC, AUPRC, Brier score, calibration plots, and threshold-specific recall/precision. For analyses incorporating censoring, use time-dependent metrics such as IPCW Brier score or cumulative/dynamic AUC, stating their censoring assumptions. Report subgroup results by channel, region, policy period, transfer/linkage status, and source system, with uncertainty intervals.

A random case split can mix policy regimes, migration artifacts, and near-duplicate transferred cases across sets. It can also let later labels or process patterns inform training while evaluating on earlier cases, yielding optimistic estimates.

## 8. Limitations and decision-use boundary

The study can estimate predictive association among activated accounts with observed, mature feeds under the historical process. It cannot identify the default risk of rejected or withdrawn applicants, nor the risk those applicants would have had if activated. It cannot claim that a score causes lower default or transports unchanged to a different activation policy.

Deployment could change who is activated, how applicants respond to document requests, and which cases receive staff attention or partner transfer. Those changes alter selection, process timing, and outcome observability. Use the model as decision support for a clearly specified activated-account monitoring workflow; separately validate any use before activation and monitor calibration, missing-feed rates, and subgroup performance.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py

CSV = "applications_events.csv"
EXTRACT = pd.Timestamp("2026-02-15", tz="UTC")
PRED_HOURS = 72
POLICY = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION = pd.Timestamp("2025-10-15", tz="UTC")
FEED_LAG_DAYS = 35

df = pd.read_csv(CSV, parse_dates=["time:timestamp",
                                  "label_available_at",
                                  "data_extract_time"])
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)
df["label_available_at"] = pd.to_datetime(df["label_available_at"], utc=True)
df["case:concept:name"] = df["case:concept:name"].astype(str)

# Versioned migration aliases; retain original name for audit.
df["activity_raw"] = df["concept:name"]
aliases = {"ID Verification": "Identity/KYC Check",
           "KYC Check": "Identity/KYC Check",
           "Credit Review Old": "Credit Review"}
df["concept:name"] = df["concept:name"].replace(aliases)
df = df.sort_values(["case:concept:name", "time:timestamp"])
dup_key = ["case:concept:name", "concept:name", "time:timestamp"]
df["duplicate_candidate"] = df.duplicated(dup_key, keep="first")
df = df.loc[~df["duplicate_candidate"]].copy()

# PM4Py case/activity/timestamp formatting.
df = pm4py.format_dataframe(df, case_id="case:concept:name",
                            activity_key="concept:name",
                            timestamp_key="time:timestamp")

def case_table(events, cutoff):
    obs = events[events["time:timestamp"] <= cutoff].copy()
    obs = obs.sort_values(["case:concept:name", "time:timestamp"])
    start = obs.groupby("case:concept:name")["time:timestamp"].min()
    activation = (obs[obs["concept:name"] == "Account Activated"]
                  .groupby("case:concept:name")["time:timestamp"].min())
    term_names = {"Rejected", "Withdrawn", "Transferred"}
    terms = obs[obs["concept:name"].isin(term_names)]
    terminal = terms.groupby("case:concept:name").first()["concept:name"]
    labels = obs.groupby("case:concept:name").agg(
        y=("default_90d", "last"),
        available=("label_available_at", "max"))
    out = pd.concat([start.rename("start"), activation.rename("activation"),
                     terminal.rename("terminal"), labels], axis=1).reset_index()
    out["horizon_due"] = out["activation"] + pd.Timedelta(days=90)
    out["mature_by_cutoff"] = (
        out["activation"].notna() &
        (out["horizon_due"] + pd.Timedelta(days=FEED_LAG_DAYS) <= cutoff) &
        out["available"].notna() & (out["available"] <= cutoff) & out["y"].notna())
    out["policy_period"] = out["start"] >= POLICY
    out["migration_period"] = out["start"] >= MIGRATION
    return out

cases = case_table(df, EXTRACT)
# Compare to expected snapshot totals; investigate overlaps/missing cases.
assert cases["case:concept:name"].nunique() <= 48000
print(cases["mature_by_cutoff"].value_counts(dropna=False))

def elapsed_prefix(events, hours=PRED_HOURS):
    starts = events.groupby("case:concept:name")["time:timestamp"].transform("min")
    return events.loc[events["time:timestamp"] <=
                      starts + pd.Timedelta(hours=hours)].copy()

prefix72 = elapsed_prefix(df)
# Fixed event-count prefixes for process inspection; length counts included events.
elog = pm4py.convert_to_event_log(df)
prefix3 = pm4py.get_prefixes_from_log(elog, length=3)

# Build prediction-time-safe case features.
prefix72 = prefix72.sort_values(["case:concept:name", "time:timestamp"])
prefix72["is_doc_request"] = prefix72["concept:name"].eq("Request Documents")
features = prefix72.groupby("case:concept:name").agg(
    prefix_len=("concept:name", "size"),
    last_event=("concept:name", "last"),
    doc_requests=("is_doc_request", "sum"),
    last_risk=("risk_score", "last"),
    last_event_time=("time:timestamp", "max"))
features["risk_updated_at"] = prefix72.groupby("case:concept:name")[
    "time:timestamp"].max()

# Explicitly remove target/post-outcome fields from feature source.
for col in ["final_limit", "decision_reason", "collection_status",
            "default_90d", "label_available_at", "documents_total"]:
    if col in prefix72:
        prefix72 = prefix72.drop(columns=col)

# Split by start time; require labels to have matured by each training cutoff.
cases = cases.sort_values("start")
train = cases[cases["start"] < "2025-04-01"]
valid = cases[cases["start"].between("2025-04-01", "2025-06-30")]
test = cases[cases["start"] >= "2025-07-01"]
train_ids = set(train.loc[train["mature_by_cutoff"], "case:concept:name"])
valid_ids = set(valid["case:concept:name"])
test_ids = set(test["case:concept:name"])
train_log = df[df["case:concept:name"].isin(train_ids)]
pm_train = pm4py.convert_to_event_log(train_log)
# Process discovery on training history only; never use test variants to fit features.
```
