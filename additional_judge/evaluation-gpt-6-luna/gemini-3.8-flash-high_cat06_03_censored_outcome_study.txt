## 1. Target definition

The proposal recognizes that default is not observed for every application and selects eventual activation as its primary population. That is a defensible direction, but the target, prediction time, and estimand are not fully pinned down. A stronger definition would predict default within 90 days after activation, conditional on eventual activation, using only information available at a specified early prefix time. The estimand would be predictive risk among activated cases with comparable observed prefixes; it would not estimate what would happen if every applicant were activated.

A credible alternative is a multi-state target for all applications, such as the probability of reaching activation, rejection, withdrawal, or transfer by a fixed time, followed by default risk after activation. This answers an operational funnel question and does not assign a default outcome to rejected or withdrawn cases. A policy-specific counterfactual for all applicants would require stronger, untestable assumptions about activation and outcomes under policies that were not applied.

## 2. Cohort construction

The response describes some statuses and maturity rules, but its cohort flow does not account for all 48,000 applications. It also does not explain precedence when statuses conflict or whether counts are mutually exclusive. The supplied code makes maturity depend on activation date plus 125 days, but then treats mature cases with missing labels as “activated_mature,” without resolving those missing outcomes.

For an activated-only analysis, inclusion should require a valid application start, an unambiguous activation, a prediction prefix available before the outcome, and a mature, verified label. Exclude or separately audit duplicate and conflicting events, unresolved transfers, and missing mature labels. ## 3. Censoring and missing-label strategy

The response notes delayed feeds, activation selection, transfer, and immature cases, but does not cleanly distinguish delayed labels from ordinary right censoring or propose a well-specified primary estimator.

Use a fixed-horizon binary model only for activated accounts whose 90-day horizon and feed-latency window have elapsed, with label availability verified. Keep immature outcomes pending rather than treating them as non-default. For event-time analysis, censor at last reliable follow-up and use a survival or competing-risk method; delayed labels are an observation process that may require inverse-probability-of-observation weighting or a sensitivity analysis.

Activation selection means estimates apply to the activated population under historical policy. Transfer is a competing process outcome when it ends the original application, but may also cause loss to follow-up if the account reappears elsewhere. The 60% linkage table permits linkage sensitivity checks; partner feeds missing permanently may be informative. Compare complete cases with weighting under an explicit missing-at-random model and bounds or scenarios for missing-not-at-random outcomes. Checkable assumptions include observed maturity dates, label rates by time and source, and covariate overlap; missingness conditional on unobserved outcomes and counterfactual outcomes for unactivated applicants are not testable from these data.

## 4. Prefix extraction

Use a point-in-time event table ordered by timestamp with deterministic tie handling and a declared prediction boundary. Fixed event-count prefixes should be generated at specified k values, such as k=3, only when the case has at least k eligible events. Elapsed-time prefixes should include events with timestamps at or before a landmark from application start, such as 1, 3, or 7 days; cases with no event by a landmark need an explicit “no event yet” representation or a clearly stated exclusion.

The proposed code uses PM4Py prefix extraction at length 3 but does not demonstrate that the selected prefix ends at Credit Review or that tied events are ordered safely. Repeated document loops should be retained as process behavior, with counts and time since last request, while capping or summarizing extreme loops if needed. Create a versioned activity mapping for the migration effective 15 October 2025, preserve raw labels for audit, and check duplicate events before prefix generation. The supplied assertion checks timestamps only after prefixes are generated; it does not itself prove point-in-time feature correctness.

## 5. Process-aware features

Useful features include prefix event count, elapsed time, current activity, direct-following transition counts, number of document request/return loops, time since last event, and whether the case has reached Credit Review. Static channel, region, and requested amount are usable only if their values were known at prediction time. `risk_score` must be selected as the latest value timestamped no later than prediction, not simply the last value in an arbitrarily ordered group. Exclude `final_limit`, `decision_reason`, post-activation collections fields, default labels, label availability, extraction time, and future same-day `documents_total`. Resource experience at extraction is not point-in-time safe.

The answer identifies several leakage fields, but its feature aggregation uses `first` and `last` without establishing event order or field availability. It also fails to discuss same-day snapshots or extraction-time resource experience, despite these being explicit risks.

## 6. Leakage and validation design

Use application-level grouping so linked identifiers do not cross folds where linkage is known. Fit mappings, imputers, scalers, feature selection, and process discovery on training data only. Split chronologically, report performance before and after the 1 July 2025 policy change, and separately assess the 15 October 2025 migration. Test periods must be mature enough for labels; later cases can be monitoring-only until outcomes mature.

The proposed date split is directionally sensible but flawed: its training rule assigns only cases before 1 January 2025 to train, and the shown splits do not clearly provide a representative pre-policy validation period. The test ending 1 October avoids the migration but does not evaluate post-migration performance. A temporal test across the policy shift and a separate post-migration evaluation should be planned when mature labels exist.

## 7. Uncertainty and calibration

Report discrimination and calibration with uncertainty intervals, not a single benchmark score. For binary outcomes, include Brier score, log loss, calibration plots, calibration intercept/slope, and decision-threshold metrics with bootstrap intervals clustered by application or linked entity. Report subgroup results by policy era, channel, region, and source, with sample sizes and label coverage. For survival or competing risks, use time-dependent calibration and appropriate cumulative-incidence metrics.

The response mentions cohort and split reporting, but gives little concrete uncertainty or calibration plan. It should distinguish uncertainty from sampling variability, label incompleteness, and selection into activation.

## 8. PM4Py-oriented implementation skeleton

The skeleton has useful elements: timestamp parsing, PM4Py formatting, funnel auditing, temporal splitting, prefix extraction, and an explicit leakage column list. However, it is not reliable as written. It infers terminal status from activity-name substrings without precedence, uses `.iloc[0]` for activation without sorting, and assumes activity names are stable despite the migration. It labels all mature activated cases as mature even when the outcome is missing. `pm4py.get_prefixes_from_log` may not be available in the installed PM4Py version, and the code does not show event ordering or point-in-time retrieval for changing fields. Its DFG is trained on prefixes, but no actual model, censoring estimator, or calibration procedure is implemented. The claimed competing-risk encoding also treats default and “performing” as possible event types without specifying a valid time origin and mutually exclusive event definition.

A sound skeleton should normalize and deduplicate events, sort deterministically, build one case-level state record with explicit precedence and audit flags, calculate label maturity and availability separately, extract only events/values available by prediction time, and assert that feature timestamps and source availability precede that time. It should then fit the selected activated-population model only on verified mature labels, retain censored or unresolved cases for appropriate survival analyses, and report flow and validation metrics.

## 9. Limitations and decision recommendation

The proposed design correctly rejects the idea that rejected applicants are non-defaults and recognizes activation selection. Its core conclusion should be that the available export supports prediction among historically activated accounts, not an unconditional “90-day default for every application” score. The workflow needs a complete, reconciled cohort flow; explicit target and prediction-time semantics; robust handling of missing mature labels and transfer linkage; corrected point-in-time feature construction; and a validation plan that evaluates both policy and migration changes before deployment.
