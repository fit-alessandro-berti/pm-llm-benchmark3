## 1. Duplicate-handling decision tree

1. **Exact technical duplicate?** Same source and source event key, or byte-for-byte equivalent event record and relations.
   - Yes: keep one canonical event, **drop** the redundant row, and retain its ID and provenance in the audit record.
   - No: continue.

2. **Same physical event observed by multiple systems?** Supported by an explicit reconciliation record or a strong business identifier, with compatible time and object context.
   - Yes: **merge attributes and relations** under source-authority rules, retaining every source value and ID.
   - No or uncertain: continue.

3. **Summary event derived from a detailed event?**
   - If it records a distinct acknowledgement, status update, or abstraction-level transition: **retain both with refined labels or qualifiers**.
   - If evidence establishes it is only a duplicate observation and no distinct transition: **merge attributes and relations**.
   - If the distinction is unresolved: **quarantine for review**.

4. **Harmonization collision between semantically distinct source activities?**
   - Yes: **retain both with refined labels or qualifiers** that reflect their source-specific meanings.
   - If the source meaning cannot be established: **quarantine for review**.

5. **Concurrent same-label events involving different objects?**
   - Yes: **retain both unchanged** when the distinct object identity is meaningful; refine labels only if needed to disambiguate the event type.
   - No: continue.

6. **Unresolved candidate?**
   - **Quarantine for review**; do not automatically drop or merge it.

## 3. Timestamp-tie ordering rules

Build a partial order from explicit business constraints first, then obtain a deterministic topological order. Keep the original timestamp unchanged.

- **Domain constraints — semantic:** use known facts such as e12 before e13 for M1 and carrier acceptance before handover (e09 before e10).
- **Within-source sequence — semantic only within its source:** use `source_seq` to order events from the same source when it does not conflict with a stronger business constraint. Never compare sequence numbers across sources.
- **Lifecycle constraints on shared objects — semantic but conditional:** apply only where object type and business meaning establish a lifecycle dependency. Shared objects alone do not establish order.
- **Source-specific semantics — semantic:** distinguish warehouse release from carrier acceptance; do not infer event equivalence from a harmonized label.
- **Ingestion time — diagnostic only:** do not use it to establish business order.
- **Stable fallback order — deterministic only:** break remaining ties by a documented stable key, such as `(timestamp, source priority, source, source_seq, eid)`, subject to the semantic constraints above.

Adding microseconds before establishing semantic order can turn an arbitrary tie-break into an apparent business fact and can distort durations and performance measures. Prefer a separate order key for analysis. If a tool requires adjusted timestamps, preserve the original timestamp and mark adjusted values as synthetic.

**Intended orders:**

- **e03–e07 at 10:00:** e03/e04 represent one physical scan and may be canonicalized together. Keep e05 as the distinct I2 pick. Keep e06 and e07 separate. The facts do not establish a total order among these events. Represent the scan and e05 as concurrent with packing unless stronger source or lifecycle evidence exists; use the stable fallback order only to serialize them for a tool.
- **e08–e10 at 10:15:** e08 (warehouse release) precedes e09 (carrier acceptance), which precedes e10 (handover). These are distinct events.
- **e11–e16 at 12:00:** after merging e11/e16, place the canonical invoice issuance before payment activity only if a domain rule establishes it; the prompt does not explicitly establish that order at tied timestamps. e12 precedes e13 for M1. e14 concerns M2 and may be concurrent with the M1 capture. e15 remains a separate summary, with no specified total order relative to the captures. Use stable fallback ordering for unresolved ties.

## 4. Conservative cleaning pipeline

Start from an immutable raw OCEL and a deep copy. Preserve original IDs, source keys, sources, labels, timestamps, and relations. Use exact technical deduplication only for records proven to be identical. Apply the reconciliation-supported custom merge for e03/e04 and the invoice-identity-supported custom merge for e11/e16, recording source-specific values and relation origins. Retain e06/e07, e08/e09, e13/e14, and e15 as separate events; refine harmonized labels where the source meaning is known.

Validate event and object references after each change. Store a deterministic order key separately from business timestamps, and use it to serialize ties where a downstream analysis requires a total order. This leaves legitimate concurrency represented in the underlying event data.

Expected count: **15 events** from 17, assuming e03/e04 and e11/e16 each become one canonical event.

## 5. Aggressive alternatives

**Evidence-based semantic merge:** in addition to the conservative merges, merge e06/e07 if review establishes they are observations of the same transition and the summary adds no distinct state change. Expected count: **14**. Likely damage: loss of ERP acknowledgement or propagation timing and source-specific abstraction.

**Aggressive library merge:** run PM4Py’s common-object merge over the event log after inspecting candidate groups. On this dataset, an unguarded common-object merge could reduce the count to **10**, depending on library grouping behavior. It may collapse e05 with e03/e04, e14 with e13, e08 with e09, and other events sharing objects, while discarding distinctions in relations and event meaning. This count is illustrative; verify it against the installed PM4Py version and the actual OCEL schema.

`have_common_object=True` is not sufficient protection for e13/e14: both share O1 and V1, but each refers to a different Payment object, M1 versus M2. A safe merge rule must check event identity and relevant object identity, not merely any shared object.

## 6. PM4Py-oriented Python implementation

The example assumes the OCEL follows PM4Py’s usual event, object, and event-to-object tables. Adapt table and column names to the installed version. The custom merge helper is specified to retain all source records in an audit sidecar; the canonical OCEL event keeps the chosen canonical event ID.

```python
import copy
import pandas as pd
import pm4py

# Never mutate the raw input.
ocel_base = copy.deepcopy(ocel_raw)

events = ocel_base.events
required = {
    "eid", "timestamp", "activity", "source", "source_event_key",
    "source_seq", "ingested_at", "payload_hash",
}
missing = required - set(events.columns)
if missing:
    raise ValueError(f"Missing expected event columns: {sorted(missing)}")

# Preserve original values before changing labels, times, or IDs.
for col, original_col in [
    ("timestamp", "original_timestamp"),
    ("activity", "original_activity"),
    ("source", "original_source"),
    ("source_event_key", "original_source_event_key"),
]:
    if original_col not in events.columns:
        events[original_col] = events[col]

# Candidate pre-check: this reports candidates; it does not declare duplicates.
print(
    events.groupby(["timestamp", "activity"], dropna=False)
          .agg(eids=("eid", list), sources=("source", list),
               keys=("source_event_key", list),
               object_candidates=("eid", "size"))
          .query("object_candidates > 1")
)

# For a real deployment, load reconciliation evidence and an authority matrix.
# The pair list below is supported by the facts in this prompt.
verified_pairs = [
    ("e03", "e04", "same_physical_scan"),
    ("e11", "e16", "same_invoice_issuance"),
]

def merge_verified_pairs(ocel, pairs, *, authority, audit):
    """Merge only explicitly verified eid pairs.

    Keep the first eid as canonical. For each attribute, preserve both source
    values in audit and select the value prescribed by `authority`. Union
    compatible E2O relations, recording their source eids. Refuse conflicting
    object types or incompatible identifiers; do not guess.
    """
    result = copy.deepcopy(ocel)
    ev = result.events
    e2o = result.relations
    for keep_eid, drop_eid, rule in pairs:
        rows = ev.set_index("eid", drop=False)
        if keep_eid not in rows.index or drop_eid not in rows.index:
            raise KeyError((keep_eid, drop_eid))
        keep = rows.loc[keep_eid]
        drop = rows.loc[drop_eid]
        if isinstance(keep, pd.DataFrame) or isinstance(drop, pd.DataFrame):
            raise ValueError("Expected unique event IDs")

        # Store all source values before applying any authority decision.
        audit.append({
            "canonical_eid": keep_eid, "merged_eid": drop_eid,
            "rule": rule, "keep_values": keep.to_dict(),
            "merged_values": drop.to_dict(),
        })

        for col in ev.columns:
            if col in {"eid", "timestamp", "activity"}:
                continue
            preferred_source = authority.get(rule, {}).get(col)
            if preferred_source and drop.get("source") == preferred_source:
                ev.loc[ev["eid"] == keep_eid, col] = drop[col]

        # Preserve all compatible relations and their origins in the audit.
        pair_rel = e2o[e2o["event_id"].isin([keep_eid, drop_eid])].copy()
        audit[-1]["relations"] = pair_rel.to_dict("records")
        # Relations are unioned by event/object/type; retain relation metadata
        # in the audit sidecar before removing duplicate rows.
        pair_rel["event_id"] = keep_eid
        non_pair = e2o[~e2o["event_id"].isin([keep_eid, drop_eid])]
        result.relations = pd.concat(
            [non_pair, pair_rel], ignore_index=True
        ).drop_duplicates(
            subset=["event_id", "object_id", "qualifier"]
            if "qualifier" in pair_rel.columns
            else ["event_id", "object_id"]
        )

        result.events = result.events[result.events["eid"] != drop_eid].copy()
        ev = result.events
        e2o = result.relations
    return result

audit_cons = []
authority = {
    "same_physical_scan": {"location": "WMS"},
    "same_invoice_issuance": {},
}
ocel_cons = merge_verified_pairs(
    copy.deepcopy(ocel_base), verified_pairs,
    authority=authority, audit=audit_cons
)

# Exact technical duplicates only; use PM4Py's drop function on a justified
# scenario. Review its grouping behavior for the installed PM4Py version first.
ocel_exact = copy.deepcopy(ocel_base)
ocel_exact = pm4py.ocel_drop_duplicates(ocel_exact)

# Refine source-specific meanings while retaining originals.
def refine_labels(ocel):
    out = copy.deepcopy(ocel)
    label_map = {
        "e07": "Pack Package (ERP summary)",
        "e09": "Carrier Accept",
        "e15": "Payment Summary",
    }
    out.events.loc[out.events["eid"].isin(label_map), "activity"] = (
        out.events["eid"].map(label_map)
    )
    return out

ocel_cons = refine_labels(ocel_cons)

def validate_referential_integrity(ocel):
    event_ids = set(ocel.events["eid"])
    object_ids = set(ocel.objects["object_id"])
    rel = ocel.relations
    assert set(rel["event_id"]).issubset(event_ids)
    assert set(rel["object_id"]).issubset(object_ids)
    assert ocel.events["eid"].is_unique

validate_referential_integrity(ocel_cons)
validate_referential_integrity(ocel_exact)

# Deterministic serialization: constraints should be incorporated into a
# topological sorter in production. This fallback key is not a business order.
def add_stable_order_key(ocel):
    out = copy.deepcopy(ocel)
    priority = {
        "ERP": 1, "WMS": 2, "CARRIER": 3, "PSP": 4,
        "BILLING": 5, "SCANNER": 6,
    }
    out.events["_order_key"] = list(zip(
        pd.to_datetime(out.events["original_timestamp"], utc=True),
        out.events["source"].map(priority).fillna(99),
        out.events["source"].astype(str),
        pd.to_numeric(out.events["source_seq"], errors="coerce")
          .fillna(-1).astype(int),
        out.events["eid"].astype(str),
    ))
    return pm4py.ocel_sort_by_additional_column(out, "_order_key")

ocel_cons = add_stable_order_key(ocel_cons)

# Apply only after the semantic partial order has been established and
# serialized. Keep original_timestamp for all measurement and audit work.
ocel_cons = pm4py.ocel_add_index_based_timedelta(
    ocel_cons, "timestamp", "derived_index_timedelta"
)
validate_referential_integrity(ocel_cons)

# Separate aggressive scenario. Warning: common-object grouping can collapse
# unrelated events, including captures for M1 and M2.
ocel_aggressive = copy.deepcopy(ocel_base)
print(
    "WARNING: common-object merging may erase distinct event meanings and "
    "Payment identities; inspect results and validate against source evidence."
)
ocel_aggressive = pm4py.ocel_merge_duplicates(
    ocel_aggressive, have_common_object=True
)
validate_referential_integrity(ocel_aggressive)
```

## 7. Sensitivity analysis

The relation totals below assume the listed object links are the complete raw event-to-object relations. PM4Py merge behavior and the chosen relation-union policy can change these counts, so compute them from the actual OCEL after each operation.

- **Raw — 17 events, 44 relations.** Order-flattened views contain repeated Pick, Pack, Dispatch, Issue Invoice, and Capture labels. Object-flattened views distinguish the I1 and I2 picks and the M1 and M2 captures. Tied timestamps create apparent immediate repeats and zero-second durations.
- **Conservative — 15 events, approximately 39 relations under the stated relation policy.** The two verified cross-system pairs are canonicalized. The separate picks, captures, pack events, warehouse release, carrier acceptance, handover, and payment summary remain. Source-level and object-level views retain the distinctions needed for analysis.
- **Evidence-based merge — 14 events if e06/e07 are additionally merged.** Pack-level event counts and source propagation visibility decrease. The WMS-to-ERP acknowledgement or latency may disappear.
- **Aggressive library merge — potentially 10 events under the prompt’s illustrative assumption.** Common-object merging can collapse distinct picks, captures, and logistics events. Payment-flattened and lifecycle views may falsely combine M1/M2 or warehouse/carrier transitions.

Patterns whose interpretation changes include duplicate I1 scans versus the separate I2 pick; detailed pack versus ERP summary; warehouse release versus carrier acceptance; invoice issuance observations; M1 and M2 captures; and payment captures versus the invoice-level balance summary.

## 9. Failure modes and safeguards

| Failure mode | Safeguard |
|---|---|
| Collapsing distinct partial payments e13/e14 | Require payment identity or explicit reconciliation evidence; inspect Payment-object views |
| Treating a derived summary as a duplicate | Preserve summary events unless evidence establishes they add no distinct transition |
| Ordering by ingestion time | Use ingestion time only for late-arrival diagnostics |
| Comparing source sequence numbers across systems | Apply `source_seq` only within a single source |
| Treating shared objects as proof of duplication | Use shared objects only to propose candidates; require business identity evidence |
| Unioning incompatible relations | Validate object types and retain relation provenance; do not invent a Payment relation for e15 |
| Changing durations with synthetic microseconds | Preserve original timestamps and measure from them |
| Applying library duplicate functions without inspection | Pre-check groups, review function semantics, then validate results |
| Losing original source authority during merge | Retain all source values and record the authority rule and conflicts |
