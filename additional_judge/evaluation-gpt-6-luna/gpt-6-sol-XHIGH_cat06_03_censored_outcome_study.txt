## 1. Target definition

The primary target is the 90-day default outcome among accounts that are activated, with time measured from Account Activated. The unit is an activated account, and a prediction would be made at a prespecified pre-activation landmark, such as after the first three events or at a fixed elapsed time from Application Started. The target is the observed default risk in the population activated under the historical policy, conditional on features available at that landmark and eventual activation.

This is operationally measurable for mature activated accounts, but it does not estimate default risk for every application. Activation is a selective downstream event, and landmarking on cases that eventually activate can itself induce selection. A credible alternative is a multi-state target for all applications, predicting activation, rejection, withdrawal, transfer, remaining open, and post-activation default over a fixed window. That answers a process-outcome question rather than assigning a default label to applications that never activated. A policy-specific counterfactual default target for all applicants would answer a different question and would require stronger causal assumptions and data.

## 2. Cohort construction

Use the 48,000 application IDs as the denominator. Include an application in an activated-account outcome analysis only if it has an activation event and the 90-day horizon and feed delay have matured by the cutoff. Do not treat rejected, withdrawn, or still-open cases as non-default. Treat those outcomes as competing states for an all-application analysis. A transfer with no reliable linkage is a competing outcome for the source application and potentially incomplete follow-up for the linked account.

Apply the extraction cutoff of 15 February 2026 to event and label availability. Establish the terminal state using the first valid terminal event and reconcile cases with conflicting or out-of-order terminal events. The prompt’s snapshot counts should be treated as a starting reconciliation, not as proof that each case belongs to exactly one category. The CSV only states an event observation window through 31 December 2025, so cases open then cannot be assumed still open on 15 February without refreshed status data.

## 3. Censoring and missing-label strategy

Ordinary right censoring applies when an application has not reached a defined outcome by the observation cutoff. Delayed labels apply when the 90-day horizon has elapsed but the external feed has not arrived; a missing label is not a negative label. Selection through activation means the observed default target is conditional on a policy-driven event. Transfers can be competing exits from the originating process and can also create missing follow-up when the account reappears elsewhere. Permanently missing partner feeds are informative missingness risks.

The primary analysis should estimate outcomes among activated accounts with mature labels under the historical policy, while separately describing label maturity and follow-up by channel, partner, policy period, and other observed subgroups. For a multi-state analysis, model transitions and censoring explicitly; use inverse-probability-of-censoring or observation weights only where the relevant predictors and positivity assumptions are plausible. Sensitivity analyses should include complete-case versus weighted estimates and bounds or scenarios for missing partner outcomes. Test label-arrival rates and observed covariate balance where possible; the missingness mechanism for permanently absent outcomes and counterfactual outcomes for nonactivated cases are fundamentally untestable from this export.

## 4. Prefix extraction

Generate fixed event-count prefixes, such as the first one, two, and three events, retaining only cases with enough events for the requested prefix. Report how many short cases are excluded at each prefix length; do not pad them with future events. Also generate elapsed-time landmarks, such as a fixed number of hours or days after Application Started, using only events whose event time and record availability are at or before the landmark. Keep short or inactive traces represented with an explicit “no event by landmark” state where appropriate.

Count document-request loops and Credit Review repetitions from the observed prefix. Normalize activity names with a reviewed, versioned migration map before prefix construction, preserve original names for audit, and investigate possible duplicate events. Deduplicate only with a reliable event identifier or documented migration rule; timestamp ties alone are not enough evidence of duplicates.

## 5. Process-aware features

Static attributes available at the landmark include channel, region, and requested amount, subject to validation that they were known then. Prefix features can include activity sequence, last activity, event count, time since start, inter-event times, time in current activity, repeated reviews, document-request loops, and transitions observed so far. Resource and queue features should use the event-time assignment and historically available workload or experience data, not extraction-time values.

Calendar features can include start or landmark date, weekday, policy period, and migration period. Historical reference features such as resource workload, typical queue delays, or transition rates must be computed using training-period data available before the prediction time. The code skeleton includes only a subset of these features and does not implement queue or historical reference features.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final decision | Available before landmark with event-time proof | Drop | Downstream decision information |
| `decision_reason` | Appears at or after Accept/Reject | Known by landmark and decision has occurred | Drop for early warning | Likely encodes decision/outcome |
| `collection_status` | Updated after activation; can reveal default | Pre-landmark availability and no post-activation update | Drop | Direct post-outcome leakage risk |
| Future events | Include contract, activation, collections, and default | Event and record availability at or before landmark | Drop future rows | Prevents future process information entering features |
| `documents_total` | Nightly snapshot can contain later same-day uploads | Timestamped document state strictly at or before landmark | Repair or drop | Calendar-day equality does not establish ordering |
| Updated `risk_score` | Can change at later events | Use only the last value recorded by the landmark | Repair | Later score versions leak later review information |
| Resource experience | Stored at extraction, not event time | Reconstruct event-time experience from history | Repair or drop | Extraction-time experience is temporally invalid |
| `label_available_at` | Reflects outcome-feed arrival and maturity | Use for outcome eligibility/censoring, never as predictor | Drop from features | Can encode label observation and future information |
| `default_90d` | Repeated on events when known | Outcome table only, after maturity checks | Drop from features | Direct target leakage |

## 7. Validation design

Use chronological case-start splits, with training on earlier cases, validation on a later period, and a final test period that reflects a realistic deployment cutoff. Apply a maturity embargo: score only landmarks whose target window and maximum expected feed delay have elapsed by the evaluation cutoff, or use an explicit censoring-aware method. Report performance before and after the 1 July 2025 policy change separately, and treat the 15 October 2025 migration period as a distinct data-quality regime until activity mapping and duplicate handling are validated.

Assess calibration as well as discrimination, and report subgroup results by channel, region, source system, partner status, and policy era, including label maturity and missing-feed rates. Monitor feature and transition drift. A random case split can mix policy regimes, migration artifacts, and label-maturity patterns across partitions, overstating performance on a future deployment period.

For mature binary outcomes, report calibration, Brier score, and discrimination metrics such as ROC AUC and precision-recall AUC, with uncertainty intervals. If using a censoring-aware time-to-event or multi-state model, use appropriate time-dependent discrimination and calibration measures and account for competing events rather than treating them as ordinary negatives.

## 8. Limitations and decision-use boundary

The study can estimate predictive associations for activated accounts under the historical activation policy, subject to selection and outcome-feed limitations. It cannot identify how rejected, withdrawn, or open applicants would have performed if activated, nor infer that they are non-defaults. A counterfactual default-risk claim requires an intervention definition, adequate overlap, measured confounders, and assumptions that cannot be validated from these data alone.

Deployment could change the data-generating process if staff act on scores and alter approval or document-request decisions; if applicants change behavior in response to faster or slower decisions; or if a new approval threshold changes which accounts activate and therefore which outcomes are observed. Partner routing, migration practices, and collection strategies could also change label capture or outcome prevalence. The score should not be used to claim causal effects or all-applicant default risk without a design and data that support those claims.

## 9. PM4Py-oriented Python implementation skeleton

The skeleton keeps the outcome table separate from the feature table. It assumes the supplied snapshot contains all application IDs and that timestamped records can be compared with the stated as-of cutoff. A production build needs a source sequence/event ID, record-availability timestamps for backfills, and refreshed January–February process status.

~~~python
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
CUTOFF = pd.Timestamp("2026-02-15 23:59:59", tz="UTC")
EVENT_END = pd.Timestamp("2025-12-31 23:59:59", tz="UTC")
WINDOW, OUTCOME, LAG = (pd.Timedelta(days=d) for d in (180, 90, 35))
K = 3
EXITS = {"Rejected", "Withdrawn", "Transferred"}
# Supply a reviewed, versioned migration map; empty here because names are unspecified.
RENAMES = {}

raw = pd.read_csv("applications_events.csv", dtype={CASE: "string"})
for col in (TS, "label_available_at", "data_extract_time"):
    raw[col] = pd.to_datetime(raw[col], utc=True, errors="coerce")
raw["risk_score"] = pd.to_numeric(raw["risk_score"], errors="coerce")
raw["default_90d"] = pd.to_numeric(raw["default_90d"], errors="coerce")
observed_rows = raw.loc[
    raw["data_extract_time"].le(CUTOFF)
    & raw[TS].between(pd.Timestamp("2024-01-01", tz="UTC"), EVENT_END)
].copy()
observed_rows[ACT] = observed_rows[ACT].replace(RENAMES)
observed_rows = observed_rows.sort_values([CASE, TS], kind="stable")
assert observed_rows[CASE].notna().all()
# Exact timestamp ties and migration duplicates need event IDs before deduplication.
tie_count = observed_rows.duplicated([CASE, TS], keep=False).sum()
print("same-case timestamp ties to audit:", tie_count)

starts = observed_rows.groupby(CASE, sort=False)[TS].min()
case = pd.DataFrame(index=starts.index)
case["start_at"] = starts
first_activity = observed_rows.groupby(CASE, sort=False)[ACT].first()
print("cases without first Application Started:",
      int(first_activity.ne("Application Started").sum()))
activated = observed_rows.loc[observed_rows[ACT].eq("Account Activated")]
case["activation_at"] = activated.groupby(CASE)[TS].min()
terminal = observed_rows.loc[observed_rows[ACT].isin(EXITS)]
terminal = terminal.drop_duplicates(CASE, keep="first").set_index(CASE)
case["terminal_at"] = terminal[TS]
case["terminal_type"] = terminal[ACT]
bad_order = case["terminal_at"].notna() & case["activation_at"].notna()
print("cases with both activation and terminal exit to reconcile:",
      int(bad_order.sum()))

known = observed_rows.loc[
    observed_rows["default_90d"].isin([0, 1])
    & observed_rows["label_available_at"].le(CUTOFF)
].copy()
assert known.groupby(CASE)["default_90d"].nunique().le(1).all()
known = known.sort_values("label_available_at").drop_duplicates(CASE, keep="last")
known = known.set_index(CASE)
case["label"] = known["default_90d"]
case["label_at"] = known["label_available_at"]
case["label_ok"] = (
    case["activation_at"].notna()
    & case["label"].isin([0, 1])
    & case["label_at"].ge(case["activation_at"])
    & (case["activation_at"] + OUTCOME).le(CUTOFF)
)
case["feed_overdue"] = (
    case["activation_at"].notna()
    & ~case["label_ok"]
    & (case["activation_at"] + OUTCOME + LAG).le(CUTOFF)
)
case["snapshot_group"] = np.select(
    [
        case["activation_at"].notna() & case["label_ok"] & case["label"].eq(0),
        case["activation_at"].notna() & case["label_ok"] & case["label"].eq(1),
        case["activation_at"].notna(),
        case["terminal_type"].eq("Rejected"),
        case["terminal_type"].eq("Withdrawn"),
        case["terminal_type"].eq("Transferred"),
    ],
    [
        "activated_nondefault", "activated_default", "activated_unresolved",
        "rejected", "withdrawn", "transferred",
    ],
    default="open",
)
print("snapshot cohort counts:")
print(case["snapshot_group"].value_counts(dropna=False))
print("feed-overdue activated:", int(case["feed_overdue"].sum()))
print("total unique applications:", len(case))

# Explicit allowlist: no outcome, post-decision, collection, or nightly fields.
safe_cols = [
    CASE, ACT, TS, "org:resource", "case:channel", "case:region",
    "case:requested_amount", "risk_score", "source_system",
]
safe = observed_rows[safe_cols].copy()
safe = pm4py.format_dataframe(
    safe, case_id=CASE, activity_key=ACT, timestamp_key=TS
)
safe = safe.sort_values([CASE, TS], kind="stable")
shortened = pm4py.get_prefixes_from_log(safe, length=K, case_id_key=CASE)
shortened = shortened.sort_values([CASE, TS], kind="stable")
sizes = shortened.groupby(CASE).size()
prefix = shortened.loc[shortened[CASE].isin(sizes.index[sizes.eq(K)])].copy()
# For the all-case baseline, rerun with K=1; never pad short traces.
group = prefix.groupby(CASE, sort=False)

def last_observed(series):
    values = series.dropna()
    return values.iloc[-1] if len(values) else np.nan

X = pd.DataFrame(index=group.size().index)
X["prefix_at"] = group[TS].max()
X["activities"] = group[ACT].agg(tuple)
X["last_activity"] = group[ACT].last()
X["document_requests"] = group[ACT].apply(
    lambda s: int(s.eq("Documents Requested").sum())
)
X["review_repeats"] = group[ACT].apply(
    lambda s: max(0, int(s.eq("Credit Review").sum()) - 1)
)
X["elapsed_hours"] = (group[TS].max() - group[TS].min()).dt.total_seconds() / 3600
X["risk_score_asof"] = group["risk_score"].apply(last_observed)
for col in ("case:channel", "case:region", "case:requested_amount",
            "org:resource", "source_system"):
    X[col] = group[col].apply(last_observed)
X["policy_after_2025_07_01"] = X["prefix_at"].ge(
    pd.Timestamp("2025-07-01", tz="UTC")
).astype(int)

# Retain only preactivation, preexit landmarks; outcomes remain in Y.
a = case["activation_at"].reindex(X.index)
e = case["terminal_at"].reindex(X.index)
active_at_landmark = (a.isna() | a.gt(X["prefix_at"])) & (
    e.isna() | e.gt(X["prefix_at"])
)
X = X.loc[active_at_landmark].copy()
t = X["prefix_at"]
a, e = a.reindex(X.index), e.reindex(X.index)
term_kind = case["terminal_type"].reindex(X.index)
a_in = a.ge(t) & a.le(t + WINDOW) & (e.isna() | a.lt(e))
e_in = e.ge(t) & e.le(t + WINDOW) & (a.isna() | e.lt(a))
label_ok = case["label_ok"].reindex(X.index).fillna(False)
label = case["label"].reindex(X.index)
Y = pd.DataFrame(index=X.index)
Y["state"] = np.where(
    (t + WINDOW).le(EVENT_END), "no_activation_by_180d", "right_censored"
)
Y.loc[e_in, "state"] = term_kind.loc[e_in].str.lower()
Y.loc[a_in & ~label_ok, "state"] = np.where(
    (a.loc[a_in & ~label_ok] + OUTCOME + LAG).le(CUTOFF),
    "feed_missing", "label_pending"
)
Y.loc[a_in & label_ok & label.eq(0), "state"] = "activated_nondefault"
Y.loc[a_in & label_ok & label.eq(1), "state"] = "activated_default"
Y["split"] = np.select(
    [
        case["start_at"].reindex(X.index).lt(pd.Timestamp("2024-10-01", tz="UTC")),
        case["start_at"].reindex(X.index).lt(pd.Timestamp("2025-01-01", tz="UTC")),
        case["start_at"].reindex(X.index).le(pd.Timestamp("2025-04-15", tz="UTC")),
    ], ["train", "validation", "test"], default="shadow"
)
Y["full_window_observable"] = (
    (t + WINDOW).le(EVENT_END)
    & (t + WINDOW + OUTCOME + LAG).le(CUTOFF)
)
for forbidden in ("final_limit", "decision_reason", "collection_status",
                  "documents_total", "default_90d", "label_available_at"):
    assert forbidden not in X.columns
assert X["prefix_at"].le(EVENT_END).all()
print("landmark outcome and split counts:")
print(pd.crosstab(Y["split"], Y["state"]))
~~~
