## 1. Equivalence design space

Let a lead execution be the events and object relations associated with one `Order`.

**Activity-sequence equivalence (ASE).** Two executions are equivalent when their ordered activity-label lists match exactly. This preserves activity names, repetition, and total event order. It discards object types, multiplicities, identifiers, relations, qualifiers, and attributes. Equality of lists is reflexive, symmetric, and transitive. For concurrent events, either use a deterministic timestamp-plus-tie-break order or define equivalence over partial orders; those choices can produce different clusters.

**Typed structural equivalence (TSE).** Two executions are equivalent when there is a bijection between their local events and objects that preserves activity labels, object types, event order, E2O incidence, O2O edges, and qualifiers. External-object flags are preserved, but identifier strings are ignored. This preserves the typed event/object graph and its order; it discards the literal local identifiers and attributes not included in the graph. Isomorphism is reflexive, symmetric, and transitive. For simultaneous events, require an isomorphism preserving a partial order rather than a chosen total order.

**Business-semantic equivalence (BSE).** Equivalence depends on a declared business projection. For the preferred projection here, retain order-level counts and motifs for deliveries, packages, payments, external sharing, qualified substitutions or removals, returns, and repacks. Ignore local identifiers and package-to-item wiring when it does not change those motifs. This preserves the declared operational and risk flags while discarding details outside the projection. Equality of a fixed canonical projection is reflexive, symmetric, and transitive. Concurrent events are represented using their partial-order motif; timestamp order is retained only where it changes a lifecycle motif.

## 2. Canonical signatures

The preferred relation is BSE. Build a per-order projection, then compare its canonical tuple. A reproducible implementation should derive counts and flags from the event and relation tables rather than hand-assign cluster labels.

```python
def bse_signature(lead, events, e2o, o2o, object_type, is_external):
    # events are for this lead, in timestamp order; e2o maps event to objects
    activities = [e.activity for e in events]
    packages = distinct_objects(e2o, events, "Package")
    deliveries = distinct_objects(e2o, events, "Delivery")
    payments = distinct_objects(e2o, events, "Payment")

    return (
        count(activities, "Dispatch"),
        len(packages),
        len(deliveries),
        len(payments),
        any(is_external(o) for o in incident_objects(events, e2o)),
        has_qualified_relation(o2o, "replaces"),
        has_qualified_relation(o2o, "removed_before_dispatch"),
        count(activities, "Return Item"),
        count(activities, "Inspect Return"),
        count(activities, "Pack Package"),
        count(activities, "Dispatch"),
        # Include repeated activity counts; omit local identifier strings.
    )
```

This projection must be specified consistently: for example, a return-and-repack flag should require the relevant return, inspection, and subsequent pack/dispatch motif. If exact typed structure is desired instead, canonicalize the typed event/object graph by trying identifier-renaming permutations or a graph-isomorphism routine, retaining event order, incidence, external flags, and qualifiers.

## 4. Cluster interpretations

- **S1 — Baseline fulfillment and settlement.** One package, one delivery, one payment, with no flagged sharing or repair. This is ordinary closed fulfillment. The opportunity is a simple reference path; risks are mainly hidden if a flat event log loses object links. Traditional order-level activity flattening represents it adequately for sequence reporting. Stable under reasonable identifier repairs.

- **S2 — Consolidated delivery.** Multiple packages travel in one delivery. This can reduce delivery overhead, but creates a coordination point where one delivery exception affects multiple packages. A single order-level trace can hide package multiplicity. Stable if package and delivery records are reliable.

- **S3 — Staged shipment and settlement.** The order has multiple deliveries and multiple payments. This may reflect split availability or staged fulfillment, with added reconciliation and customer-service complexity. A flattened trace hides which payments correspond to which delivery. Stability depends on whether two payment records truly represent partial settlement rather than a data duplication.

- **S4 — Cross-order logistics sharing.** An external order/item participates in the package lifecycle. Sharing can improve packing efficiency but risks allocation, ownership, and traceability errors. Order-only flattening poorly represents the shared object. Stable only when external ownership is trustworthy.

- **S5 — Cross-order financial sharing.** An invoice bills multiple orders, and the payment lacks order-level allocation. This may be legitimate consolidated billing, but complicates receivables, refunds, and order-level profitability. A flattened order trace obscures invoice scope. Stability depends on accurate invoice-to-order links.

- **S6 — Substitution or removal before dispatch.** A package initially includes an item later marked removed, while another item replaces it. This can represent acceptable substitution or an operational exception, but it needs clear audit and customer-consent data. A plain activity sequence hides the qualified relation. Stability depends on qualifier correctness and whether the dispatch incidence reflects the final contents.

- **S7 — Return and repack.** An item is returned, inspected, repacked, and dispatched again. This may be a successful recovery, but introduces quality, inventory, and duplicate-shipment risks. A flattened order sequence poorly captures which item and package were involved. Stable if return and replacement links are complete.

## 5. Borderline cases

- **X1 versus X2:** ASE agrees because the activity labels and order match. TSE also agrees after identifier renaming; a raw-ID graph comparison would disagree.
- **X1 versus X5:** ASE agrees, but TSE and BSE disagree because X5 includes external logistics objects. A projection that drops external objects would merge them.
- **X1 versus X6:** ASE agrees, while TSE and BSE preserve the external invoice sharing. If invoice scope is absent from the chosen projection, BSE could merge them.
- **X1 versus X7:** ASE agrees. TSE distinguishes the qualified removal and differing dispatch incidence; a coarser BSE that ignores qualifiers and item-level dispatch links may merge them.
- **X3 versus X4:** Both have two packages, so a package-count-only projection can group them. ASE and TSE distinguish one consolidated delivery from two deliveries; BSE does too when it retains delivery count.
- **X4 versus X8:** Both have multiple package/dispatch activity and more than one delivery, but X8 includes a return, inspection, and repack lifecycle. A coarse shipment-count BSE might merge them; ASE and TSE distinguish their event sequences and relations.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py function groups equivalent OCEL executions according to its exact key structure and object bound. The key preserves whichever event, object, and relation fields the installed implementation includes; inspect that version’s implementation before relying on a specific set of fields. If literal object identifiers participate, otherwise isomorphic executions such as X1 and X2 can be separated.

Canonicalize or post-process returned clusters by constructing a per-lead signature that removes local identifier strings while retaining the fields required for the selected equivalence. Exact equivalence is preferable for audits, regression checks, or investigations where any structural difference matters. `max_objs` can exclude large connected executions from comparison; shared-object components may also grow beyond a practical bound.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** X7 loses the qualified removal signal but still has an item in the dispatch event, so it may remain distinct under a projection retaining that incidence. X8 remains distinct through its return and repack events. If those motifs are inferred only from qualifiers, the clusters become less stable.
- **Ignore external objects:** X5 and X6 can collapse into the baseline if their external incidences are discarded. This removes the main distinction between local and shared logistics or finance.
- **Collapse repeated same-label events:** X3’s two pack events and X4’s repeated pack/dispatch/payment events lose multiplicity information. X4 can approach X1 under ASE; X8 remains distinguishable if return and inspection labels are retained.
- **Treat Pack and Dispatch as partially ordered:** A partial order that preserves each package’s pack-before-dispatch relation still distinguishes consolidated and split delivery patterns. If all pack and dispatch events are treated as an unordered bag, the timing and linkage evidence weakens.
- **Treat payment multiplicity as an amount attribute:** X4 could resemble one-payment executions if two records are replaced by a single partial amount. Preserving amount and settlement state can retain the distinction; without them, the cluster is sensitive to data representation.

## 8. Limitations and recommendation

The preferred partition reflects a deliberate business projection. Dropping package counts, external flags, qualifiers, or payment multiplicity changes its clusters. External-object ownership and relation qualifiers also depend on source-data quality.

Use a qualifier- and sharing-aware projection for compliance monitoring, shipment-aware signatures for operational segmentation, and typed structural equivalence for root-cause analysis. A coarser business projection can support descriptive reporting, but it should retain flags for exceptions that matter to the reporting purpose.
