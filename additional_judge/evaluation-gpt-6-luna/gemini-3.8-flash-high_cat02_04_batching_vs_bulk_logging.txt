# 3. Consequences for performance analysis

Waiting below means queue arrival to the recorded start; service time means recorded complete minus start. Those quantities are only meaningful when the fields represent execution. With distorted timestamps, a direction of bias can be stated only conditionally.

- **G1:** Recorded arrival-to-start waits are 6, 5, 4, and 2 minutes. The three-minute interval is a per-item elapsed window, not proof that four workers or four independent servers were occupied. Treating the cell as capacity one can inflate inferred utilization and make the cell look like an implausible 400% loaded server. Treating each item as a separate three-minute serial service would overstate total occupied time and can create a false bottleneck. If the items truly occupy one four-place fixture concurrently, item service is three minutes while cell busy time is about three minutes for the batch. Conformance should allow a four-item batch or shared execution interval rather than flagging simultaneous events as impossible.

- **G2:** Arrival-to-start waits based on 10:00 range from 18 to 6 minutes, and recorded services range from 8 to 27 minutes. If 10:00 is a group setup time, those waits may be useful as waits to group start, but not necessarily waits to each item’s execution. If inspection is serial, the common start can understate later items’ waits and distort service durations; if inspectors multitask, the long intervals may include pauses and overstate active labor. A single-resource utilization estimate based on four overlapping intervals can exceed 100% (the intervals sum to 60 item-minutes across a 27-minute span), so it is not a valid single-worker utilization measure. Queue accumulation and bottleneck detection depend on the actual inspection mode. Conformance should distinguish group start from item execution.

- **G3:** Arrival-to-recorded-start waits are 22, 18, 12, and 5 minutes; recorded services are 28, 20, 13, and 6 minutes. If 11:30 is folder submission rather than each review’s execution end, the computed services are inflated for earlier-finishing reviews, while individual waits to completion are not represented. If the reviews genuinely overlapped, the intervals may instead represent elapsed case handling, not continuous labor. Resource utilization from overlapping intervals is unreliable without active-time and identity data. A common end can mask per-case completion and make the wrong activity appear to be the bottleneck. Conformance may falsely accept a bulk approval as item-level completion or falsely reject staggered completion as inconsistent.

- **G4:** Arrival-to-start waits are 7, 10, 13, 16, and 19 minutes; each recorded service is four minutes, and each next start coincides with the prior completion. This supports a serial server with growing queue delay. Summing service intervals gives 20 minutes over a 20-minute span, consistent with a continuously occupied single resource over this fragment, though the excerpt alone cannot establish a long-run utilization rate. Queue wait increases by three minutes per item because arrivals continue faster than the four-minute service rhythm. Bottleneck detection will identify this station if the pattern persists. Conformance should preserve the observed FIFO sequence and sequential service.

- **G5:** Arrival-to-start waits by case are 15, 15, 16, and 15 minutes; recorded services are 25, 15, 20, and 10 minutes. Their intervals overlap substantially. If one person performed all work serially but the timestamps mark case-open/case-close periods, service time and resource busy time are overstated; if multiple analysts worked in parallel, treating `analyst_pool` as one worker can overstate utilization and falsely flag a capacity violation. If the shared account represents different workers, per-person utilization and conformance cannot be derived. Rounding both endpoints to quarter-hour boundaries can move true starts earlier or later within the rounding intervals and create false service-time equality. Consequently, point utilization and throughput rates can be biased in either direction, and bottleneck rankings based on these intervals are unstable. # 4. Robustness and uncertainty

A timestamp-tolerance sweep can show whether PM4Py-style temporal pattern labels depend on exact equality or survive modest timing uncertainty. It cannot establish physical batching, active work, clock accuracy, worker identity, or causal downtime. For each cluster, report how equality, adjacency, and overlap labels change across tolerances (for example, 0, 1, 2, 5, and 15 minutes), alongside the raw intervals and source precision. G1’s one-second equality is stronger than minute-level equality, but the fixture capacity is what makes a physical batch plausible. G7’s documented 15-minute precision dominates any fine-grained tolerance result. G8’s cross-system downtime comparison requires clock synchronization evidence.

A defensible analysis should keep observed fields separate from inferred execution semantics, label assumptions, and avoid substituting `recorded_at` for `complete`. Use point estimates only where source semantics and precision support them. For uncertain timestamps, report intervals or sensitivity ranges; for absent execution times, mark measures unavailable. Do not use PM4Py temporal-pattern labels as proof of a batch mechanism.

# 5. Python evaluation design

The evidence supports a tolerance-sensitivity analysis of temporal patterns, not a definitive physical batch classifier. Use the supplied data as embedded input, retain source and precision fields, and produce raw per-cluster interval summaries plus labels at multiple tolerances. Any inferred label should be named as a temporal pattern and kept separate from the adjudicated operational hypothesis.

```python
import pandas as pd

# Embed the prompt rows in a list of dictionaries:
# rows = [{"cluster": ..., "case": ..., "activity": ..., "resource": ...,
#          "queue_arrival": ..., "start": ..., "complete": ...,
#          "recorded_at": ..., "source": ..., "precision": ...,
#          "sequence_no": ...}, ...]
df = pd.DataFrame(rows)

for col in ["queue_arrival", "start", "complete", "recorded_at"]:
    df[col] = pd.to_datetime("2026-05-26 " + df[col].astype(str))

df["service_min"] = (df["complete"] - df["start"]).dt.total_seconds() / 60
df["queue_wait_min"] = (df["start"] - df["queue_arrival"]).dt.total_seconds() / 60
df["recording_lag_sec"] = (df["recorded_at"] - df["complete"]).dt.total_seconds()

# Treat these as descriptive point calculations until timestamp semantics are validated.
# Pairwise overlap duration is measured from lifecycle intervals, not active labor.
def overlap_minutes(a_start, a_end, b_start, b_end):
    return max(0.0, (min(a_end, b_end) - max(a_start, b_start)).total_seconds() / 60)

def temporal_summary(g, tolerance_min):
    g = g.sort_values(["start", "sequence_no"]).copy()
    starts = g["start"].tolist()
    ends = g["complete"].tolist()

    start_equal = (max(starts) - min(starts)).total_seconds() <= tolerance_min * 60
    end_equal = (max(ends) - min(ends)).total_seconds() <= tolerance_min * 60

    adjacent = False
    for i in range(len(g) - 1):
        gap = (starts[i + 1] - ends[i]).total_seconds() / 60
        if abs(gap) <= tolerance_min:
            adjacent = True

    overlap_pairs = 0
    for i in range(len(g)):
        for j in range(i + 1, len(g)):
            if overlap_minutes(starts[i], ends[i], starts[j], ends[j]) > tolerance_min:
                overlap_pairs += 1

    return pd.Series({
        "n": len(g),
        "start_equal": start_equal,
        "end_equal": end_equal,
        "adjacent_pair_exists": adjacent,
        "overlap_pairs_gt_tolerance": overlap_pairs,
        "mean_service_min_point": g["service_min"].mean(),
        "mean_wait_min_point": g["queue_wait_min"].mean(),
        "max_recording_lag_sec": g["recording_lag_sec"].max(),
        "source": ",".join(sorted(g["source"].astype(str).unique())),
        "precision": ",".join(sorted(g["precision"].astype(str).unique())),
    })

for tol in [0, 1, 2, 5, 15]:
    result = df.groupby("cluster", group_keys=False).apply(
        lambda g: temporal_summary(g, tol), include_groups=False
    )
    print(f"\nTolerance = {tol} minutes")
    print(result)
```

The code reports whether any adjacent pair exists, not whether the entire cluster forms one sequential chain; that distinction should be retained in interpretation. Its overlap count is based on the recorded lifecycle intervals and should not be described as concurrent labor. The point service and waiting summaries deliberately remain labeled as unvalidated. To assess uncertainty more rigorously, replace point timestamps with intervals derived from documented precision and the actual rounding rule once known; the prompt does not specify enough to calculate exact interval bounds for G7.

# 6. Operational redesign

1. **Capture execution separately from setup and submission.** Log item-level physical start and completion timestamps. Where work begins as a group, record setup or group-start events separately from each item’s execution.
2. **Keep event time and receipt time.** Store the client or device execution timestamp and server `recorded_at`; flag substantial differences for review rather than treating receipt time as completion.
3. **Synchronize system clocks.** Use a common time source across scanners, PLCs, tablets, MES, and safety systems so downtime can be compared with work events.
4. **Record accountable identity.** Capture a unique operator ID as well as station or machine ID. For shared stations, preserve both identities.
5. **Add explicit batch fields.** Record batch ID, type, size, and item position so physical batches, group starts, sequential runs, and administrative bulk entries can be distinguished.
6. **Represent capacity.** Store workstation capacity and model utilization against that capacity where appropriate; do not assume every resource is a single server.
7. **Log pauses and unavailability.** Capture downtime start, end, resource, and reason so queue accumulation can be separated from active service.
8. **Preserve timestamp uncertainty.** Store documented precision and, where available, rounding rules. Use interval-aware analysis when timestamps are quantized or uncertain.
