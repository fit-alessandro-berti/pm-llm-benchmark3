1. Duplicate-handling decision tree

```text
Candidate pair/group
├─ Same source event key and identical business content?
│  ├─ Yes → exact technical duplicate: drop redundant copy; log its ID and provenance.
│  └─ No
├─ Evidence confirms the same physical event across systems?
│  ├─ Yes → merge attributes and relations; retain all source provenance and conflicts.
│  └─ No
├─ Is one event a summary derived from a detailed event?
│  ├─ Confirmed same transition and analysis permits loss of abstraction level
│  │  → merge attributes and relations, preserving the summary/detailed roles.
│  ├─ They convey distinct analytical meaning → retain both with refined labels or qualifiers.
│  └─ Unresolved → quarantine for review.
├─ Did harmonization map semantically distinct source activities to one label?
│  └─ Yes → retain both with refined labels or qualifiers.
├─ Same label and time, but different object identity?
│  └─ Yes → retain both unchanged.
└─ Evidence remains insufficient → quarantine for review.
```

3. Timestamp-tie ordering rules

Construct a partial order first, then choose a deterministic linear extension:

1. **Domain constraints (semantic):** enforce known causal facts, such as e12 before e13 and carrier acceptance e09 before handover e10.
2. **Within-source sequence (semantic where documented):** use `source_seq` only for events from the same source. Never compare sequence values across systems.
3. **Lifecycle constraints on shared objects (semantic):** apply only well-supported lifecycle rules, such as create before validate. Do not infer an order merely because two events share a timestamp and object.
4. **Source-specific semantics (semantic):** preserve distinctions such as warehouse release before carrier acceptance when supported by the source definitions.
5. **Ingestion time (not semantic):** retain for audit, but do not use as a business-time ordering rule.
6. **Stable fallback (deterministic only):** for remaining incomparable events, sort by stable source name, source event key, then eid.

Use a topological sort over the semantic constraints, with the stable fallback to choose among currently available events. Adding microseconds before resolving semantic order turns a tie into an apparent causal sequence and can imply durations or precedence that the source data does not support.

Admissible orders:

- **e03–e07 at 10:00:** e03/e04 represent one scan after merge; e05 is the distinct I2 pick. The picks precede e06’s pack under the lifecycle rule. e07 is a summary update, so it may follow the detailed pack if the derivation is accepted; otherwise e06 and e07 remain unordered. The stable fallback orders incomparable records reproducibly.
- **e08–e10 at 10:15:** e08 (warehouse release) → e09 (carrier acceptance) → e10 (handover), based on source semantics and the known acceptance-before-handover fact.
- **e11–e16 at 12:00:** merge e11/e16 into one invoice event. Keep e12 before e13 for M1. e14 remains a distinct capture for M2; no ordering against e13 is established. e15 remains a summary with no Payment relation; do not assign it to M1 or M2. Stable fallback orders remaining ties.

4. Conservative cleaning pipeline

Take a frozen copy of the raw log and preserve original IDs, labels, timestamps, sources, and source event keys. Remove exact technical duplicates only when identity and business content support that decision. Merge the confirmed scan pair e03/e04 and invoice pair e11/e16 with field-level provenance. Keep e06/e07, e08/e09, e09/e10, and e13/e14/e15 distinct; refine harmonized labels with source-specific qualifiers where justified. Build the semantic partial order, then apply a stable deterministic tie-break. Store any ordering timestamp separately from the original timestamp.

Expected event count: **15**, assuming no unlisted exact technical duplicates.

5. Aggressive alternatives

- **Evidence-based semantic merge:** merge e03/e04 and e11/e16; additionally merge e06/e07 and, if an explicit derivation link becomes available, e15 into its payment event. With only the current data, e15 cannot safely be assigned to M1 or M2; an analysis scenario that assigns it to one must state that assumption. Merging e06/e07 loses the distinction between a detailed transaction and a summary. Expected count with only the defensible first two merges: **15**. An additional e06/e07 merge gives **14**; assigning e15 to one capture gives **13**.
- **Mechanically aggressive PM4Py merge:** merge events with a common object under broad rules. This can collapse e13 and e14 even though they represent payments M1 and M2, and may collapse semantically distinct dispatch or packing observations. Expected count is data- and library-dependent; it should be measured, not assumed to be 10. The likely damage is loss of payment identity, source authority, abstraction level, and lifecycle distinctions.

`have_common_object=True` is insufficient: e13 and e14 share O1 and V1, but have different Payment objects. A safe merge rule must inspect object type and identity, not just the existence of any shared object.

6. PM4Py-oriented Python implementation

```python
import copy
import pandas as pd
import pm4py

def prepare(raw):
    log = copy.deepcopy(raw)
    ev = log.events
    for col in ("timestamp", "activity", "source", "source_event_key"):
        if col not in ev.columns:
            raise ValueError(f"Missing required column: {col}")
    ev["original_timestamp"] = ev["timestamp"]
    ev["original_activity"] = ev["activity"]
    # These source fields remain attached to each event through scenario work.
    return log

def pre_check_candidate_groups(log):
    ev = log.events
    # Report same-time, same-label candidates for human/rule review.
    cols = ["timestamp", "activity"]
    groups = []
    for key, frame in ev.groupby(cols, dropna=False):
        if len(frame) > 1:
            groups.append({
                "key": key,
                "eids": frame.index.tolist(),
                "sources": frame["source"].tolist(),
                "objects": frame.get("related_objects", pd.Series(index=frame.index)).tolist(),
            })
    return groups

def validate_referential_integrity(log):
    ev = log.events
    obj = log.objects
    e2o = log.relations
    event_ids = set(ev.index)
    object_ids = set(obj.index)
    if not set(e2o["ocel:eid"]).issubset(event_ids):
        raise ValueError("Relation references missing event")
    if not set(e2o["ocel:oid"]).issubset(object_ids):
        raise ValueError("Relation references missing object")

def apply_verified_pair_merge(log, pairs):
    """Merge specified eids into the first eid; union relations and preserve conflicts."""
    ev = log.events
    rel = log.relations
    for canonical, duplicates, rule in pairs:
        ids = [canonical, *duplicates]
        rows = ev.loc[ids]
        if rows["timestamp"].nunique(dropna=False) != 1:
            raise ValueError(f"{rule}: timestamps differ; review before merging")
        # Preserve every source row in an audit column. Never silently overwrite.
        ev.at[canonical, "merged_source_records"] = rows.to_dict("records")
        ev.at[canonical, "merge_rule"] = rule
        # Keep canonical attributes; store noncanonical values as provenance.
        for col in ev.columns:
            vals = rows[col].dropna().unique().tolist()
            if len(vals) > 1:
                ev.at[canonical, f"conflict:{col}"] = vals
        # Union event-object relations, retaining other relation columns.
        subset = rel[rel["ocel:eid"].isin(ids)].copy()
        subset["ocel:eid"] = canonical
        rel = pd.concat([rel[~rel["ocel:eid"].isin(ids)], subset],
                        ignore_index=True).drop_duplicates()
        ev = ev.drop(index=duplicates)
    log.events = ev
    log.relations = rel
    return log

def refine_labels(log):
    ev = log.events
    refinements = {
        "e08": "Release from Warehouse",
        "e09": "Carrier Acceptance",
        "e10": "Handover to Carrier",
    }
    for eid, label in refinements.items():
        if eid in ev.index:
            ev.at[eid, "activity"] = label
    return log

def establish_order(log):
    ev = log.events.copy()
    # Deterministic fallback columns; semantic precedence constraints should be
    # applied by a topological sort before this stable fallback sort.
    ev["_source"] = ev["source"].fillna("").astype(str)
    ev["_key"] = ev["source_event_key"].fillna("").astype(str)
    ev["_eid"] = ev.index.astype(str)
    ev = ev.sort_values(
        ["timestamp", "_source", "_key", "_eid"], kind="mergesort")
    ev["deterministic_order"] = range(len(ev))
    log.events = ev.drop(columns=["_source", "_key", "_eid"])
    return log

def add_index_timedelta(log):
    # Called only after semantic order and deterministic fallback are established.
    return pm4py.ocel_add_index_based_timedelta(
        log, "deterministic_order", "deterministic_ts")

# Independent scenario copies.
ocel_conservative = prepare(ocel_raw)
ocel_evidence = prepare(ocel_raw)
ocel_aggressive = prepare(ocel_raw)

print("Conservative pre-check:", pre_check_candidate_groups(ocel_conservative))
verified = [
    ("e03", ["e04"], "verified_same_physical_scan"),
    ("e11", ["e16"], "verified_same_invoice_issuance"),
]
ocel_conservative = apply_verified_pair_merge(ocel_conservative, verified)
ocel_conservative = refine_labels(ocel_conservative)
ocel_conservative = establish_order(ocel_conservative)
ocel_conservative = add_index_timedelta(ocel_conservative)
validate_referential_integrity(ocel_conservative)

# Evidence-based scenario is separate; add a summary merge only when a specific
# derivation relationship is established and documented.
ocel_evidence = apply_verified_pair_merge(ocel_evidence, verified)
ocel_evidence = refine_labels(ocel_evidence)
ocel_evidence = establish_order(ocel_evidence)
ocel_evidence = add_index_timedelta(ocel_evidence)
validate_referential_integrity(ocel_evidence)

# Library scenarios are isolated and explicitly experimental.
print("Aggressive pre-check:", pre_check_candidate_groups(ocel_aggressive))
print("WARNING: common-object merging can collapse distinct Payment objects M1/M2.")
ocel_aggressive = pm4py.ocel_merge_duplicates(
    ocel_aggressive, have_common_object=True)
ocel_aggressive = pm4py.ocel_sort_by_additional_column(
    ocel_aggressive, column="source_seq")
ocel_aggressive = pm4py.ocel_drop_duplicates(ocel_aggressive)
validate_referential_integrity(ocel_aggressive)
```

7. Sensitivity analysis

| Dataset | Expected events | Expected E2O effect | Order/process effects |
|---|---:|---|---|
| Raw | 17 | All original links retained | Includes repeated observations and harmonized collisions |
| Conservative | 15 | Deduplicate e03/e04 and e11/e16 links | Retains two distinct picks, both packing observations, both dispatch stages, and both payments |
| Evidence-based merge | 14–15, depending on whether e06/e07 is merged | Fewer links if summary/detail relations are unioned | May hide abstraction-level distinctions; e15 remains separate absent an explicit payment link |
| Aggressive library merge | Measure from output; likely fewer than conservative | Potentially removes distinct payment and logistics links | Can erase M2, collapse release and acceptance, and create false event order |

Key changed interpretations:

- Pick counts fall by one when e03/e04 merge; e05 must remain to preserve the I2 pick.
- Packing counts fall only if e06/e07 are merged, losing the detail/summary distinction.
- Dispatch analysis changes when e08/e09 receive refined labels rather than one harmonized label.
- Invoice issuance becomes one event after the supported e11/e16 merge, while both systems’ attribute contributions remain auditable.
- Payment analysis must retain M1 and M2 as separate captures. A common-object merge can erase this distinction.
- Synthetic tie-break timestamps are ordering aids only; performance durations should use original business timestamps.

8. Audit trail and reversibility

Keep a provenance record for each modified event with canonical eid, all source eids, merge rule, reviewer or rule version, original and refined activity, original and adjusted timestamps, attribute-to-source mapping, conflicts, confidence, and reason. Preserve a frozen raw OCEL so the original events and relations can be restored directly. A compact audit record alone is not a substitute for retaining the original event rows and relation rows.

9. Failure modes and safeguards

1. **Collapsing partial payments:** require payment-object identity checks; preserve e13 and e14.
2. **Merging summary and detail:** retain abstraction roles unless a supported derivation and analysis decision justify merging.
3. **Ordering by ingestion time:** exclude `ingested_at` from business precedence.
4. **Treating shared objects as proof of duplication:** require event-level evidence and inspect typed object identities.
5. **Unioning incompatible relations:** retain source-specific relation provenance and qualifiers.
6. **Adding synthetic timestamps too early:** establish the semantic partial order first; preserve original timestamps.
7. **Losing source-authoritative attributes:** merge with field-level source attribution and conflict records.
8. **Applying duplicate functions globally:** inspect candidate groups and protect known-distinct pairs before library operations.
9. **Comparing `source_seq` across systems:** use it only within its source.
10. **Losing reversibility:** keep a frozen raw log and complete event/relation provenance for every modification.
