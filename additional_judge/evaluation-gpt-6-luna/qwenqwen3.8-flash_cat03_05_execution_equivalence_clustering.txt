## 1. Equivalence design space

Represent an execution as ordered events, typed objects, event-to-object (E2O) incidences, and qualified object-to-object (O2O) relations, centered on an `Order`. Local identifiers are arbitrary; `EXT` marks an object whose lifecycle belongs to another order.

1. **Activity-sequence equivalence (`A`)**: Two executions are equivalent if their timestamp-ordered lists of activity labels match, including repetitions. This preserves activity names, order, and counts, but discards object types, multiplicities, incidences, externality, and O2O relations. Equality of these lists is reflexive, symmetric, and transitive. Events at the same timestamp are treated as an unordered multiset of labels; otherwise, the supplied timestamp order is used.

2. **Local typed structural equivalence (`T`)**: Two executions are equivalent if their events can be matched in order with the same labels and the same multisets of *local* object types on each event. Equivalently, there is a type-preserving renaming of local objects that preserves E2O incidence. This preserves local object multiplicities, event order, and repeated activities, but discards external objects and O2O qualifiers. It is reflexive, symmetric, and transitive. Tied-time events are compared as an unordered multiset of event signatures within each timestamp layer.

3. **Business-semantic equivalence (`S`)**, the preferred relation: Two executions are equivalent if their canonical signatures in Section 2 match. This preserves object types and counts, external-object flags, event order, E2O incidence, qualified O2O relations, and the listed lifecycle motifs. It discards local identifiers and exact timestamp values. Equality of canonical signatures is reflexive, symmetric, and transitive. Events sharing a timestamp form an unordered layer; timestamp layers remain ordered.

A useful intermediate variant, **external-aware typed equivalence**, is `T` with external objects and their E2O incidences retained, but O2O qualifiers ignored. It separates cross-order sharing from isolated local executions without distinguishing replacement or return semantics.

## 2. Canonical signatures

For `S`, build event signatures from the activity and the multiset of participating `(type, external_flag)` pairs. Count each distinct object once in the object profile. Include all supplied O2O edges using endpoint types, endpoint external flags, qualifier, and any context type. Add motif counts or flags for split packages, split deliveries, cross-order logistics or finance, replacement/removal, partial settlement, and return/repack.

```python
from collections import defaultdict

def external(object_id):
    return str(object_id).startswith("EXT")

def event_sig(event):
    # event["objects"] is a list of (object_type, object_id)
    incidence = tuple(sorted((typ, external(oid))
                             for typ, oid in event["objects"]))
    return event["activity"], incidence

def object_profile(objects):
    # objects contains unique (object_type, object_id) pairs
    counts = defaultdict(int)
    for typ, oid in set(objects):
        counts[(typ, external(oid))] += 1
    return tuple(sorted((typ, is_ext, n)
                        for (typ, is_ext), n in counts.items()))

def canonical_signature(events, objects, o2o_edges):
    layers = defaultdict(list)
    for event in events:
        layers[event["timestamp"]].append(event_sig(event))
    event_order = tuple(tuple(sorted(signatures))
                        for _, signatures in sorted(layers.items()))

    relations = tuple(sorted(
        (edge["source_type"], edge["source_external"],
         edge["qualifier"], edge["target_type"],
         edge["target_external"], edge.get("context_type", ""))
        for edge in o2o_edges
    ))

    activities = [event["activity"] for event in events]
    qualifiers = {edge["qualifier"] for edge in o2o_edges}
    motifs = (
        ("pack_count", activities.count("Pack Package")),
        ("dispatch_count", activities.count("Dispatch")),
        ("payment_count", activities.count("Record Payment")),
        ("return_repack", "Return Item" in activities
                          and activities.count("Pack Package") > 1),
        ("replacement_or_removal",
         bool({"replaces", "removed_before_dispatch"} & qualifiers)),
        ("partial_settlement",
         bool({"partially_settles", "completes_settlement"} & qualifiers)),
    )
    return event_order, object_profile(objects), relations, motifs
```

The event signatures preserve E2O multiplicity on each event. Object profiles count distinct objects rather than their repeated appearances in events. The O2O input includes the supplied standard relations as well as qualified relations.

## 3. Cluster assignments

For `T`, external objects are omitted; for `S`, they and qualified relations are retained.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature | Main reason |
|---|---|---|---|---|---|
| X1 | A-single | T-standard | S-standard | 1 package, 1 delivery, 1 payment; no external objects | Baseline fulfillment |
| X2 | A-single | T-standard | S-standard | Same signature as X1 after local renaming | Identifier and item-add order differences are immaterial |
| X3 | A-two-pack | T-two-pack | S-consolidated | 2 packs, 1 dispatch, 2 packages, 1 delivery | Split packing with consolidated delivery |
| X4 | A-split-delivery | T-split-payment | S-split-partial | 2 packs, 2 dispatches, 2 payments; partial/completion qualifiers | Split fulfillment and staged settlement |
| X5 | A-single | T-standard | S-shared-logistics | External Order and Item participate in Pack/Dispatch | Logistics are shared across orders |
| X6 | A-single | T-standard | S-shared-finance | External Order participates in Invoice/Payment | Financial execution is shared |
| X7 | A-single | T-dispatch-item | S-replacement | Dispatch includes Item; replacement/removal qualifiers | Item substitution or removal before dispatch |
| X8 | A-return | T-return-repack | S-return-repack | Return and inspection; second pack/dispatch; package replacement | Reverse logistics and repacking |

## 4. Cluster interpretations

- **S-standard** — Signature: one order, two local items, one package, one delivery, one invoice, and one payment, with no external objects. This is ordinary single-package fulfillment. It offers a useful baseline; its main risk is that a flattened order trace can make X5, X6, or X7 look identical if it omits external participation or qualified relations. It is stable under local identifier repair, but not if external flags or qualifiers are lost.

- **S-consolidated** — Signature: two packages carried by one delivery. This can reflect warehouse or inventory constraints while keeping transport consolidated. It creates package-level tracking and partial-receipt risks, but may reduce shipping cost. A flattening that records only one dispatch per order can hide the two-package structure. It is stable if package counts and package-to-delivery relations are repaired consistently.

- **S-split-partial** — Signature: two packages, two deliveries, and two payments, with partial and completion settlement qualifiers. Fulfillment and settlement proceed in stages. This supports delivery-level monitoring but raises reconciliation, tracking, and credit-exposure risks. A flattening that stores only a final payment amount loses the staged settlement; one that aggregates dispatches loses the delivery split. The cluster is less stable if repairs collapse the two payments into an amount.

- **S-shared-logistics** — Signature: external Order and Item objects participate in Pack/Dispatch, while the invoice bills only the local order. This is cross-order logistics sharing, potentially enabling consolidated shipping. It complicates shipment attribution, customer communications, and returns. A local order-centric flattening represents it poorly because the external participants disappear. The distinction is stable only while external flags and incidences are retained.

- **S-shared-finance** — Signature: an external Order participates in Invoice/Payment, with no order-level allocation. This is shared financial execution. It may simplify billing but creates allocation, refund, and audit risks. A local finance trace can look like the standard case if it drops external participation. The distinction depends on preserving the external order and any available allocation information.

- **S-replacement** — Signature: Dispatch includes an Item and qualified relations record replacement/removal. The activity sequence resembles the baseline, but the item set was changed before dispatch. This can be a service recovery opportunity and a source of fulfillment, inventory, or customer-billing errors. Activity-only flattening represents it poorly. It is stable only if the qualifier and the relevant E2O incidence survive repair.

- **S-return-repack** — Signature: Return Item and Inspect Return occur before a second pack/dispatch, with a package replacement relation for the returned item. This is reverse logistics followed by reshipment. It creates return tracking and duplicate-shipment risks, while enabling service recovery. A simple order trace may show the events but miss which package and delivery belong to the returned item. It is stable when return events and package relations are preserved.

## 5. Borderline cases

- **X1 versus X2:** Activity-sequence, local typed structural, and preferred semantic equivalence all group them. A raw-identifier comparison can separate them, but that treats arbitrary local IDs as meaningful. The different order of the two `Add Item` events also does not matter under activity-sequence equivalence because the labels match.

- **X1 versus X5:** Activity-sequence and local typed structural equivalence group them: after omitting external objects, their local event structure matches. Business-semantic or external-aware typed equivalence separates them because another order’s item and order participate in logistics.

- **X1 versus X6:** Activity-sequence and local typed structural equivalence again group them. Business-semantic equivalence separates them because the external order shares the invoice/payment execution. Ignoring external participation would hide that financial distinction.

- **X1 versus X7:** Activity-sequence equivalence groups them. Local typed structural equivalence separates them because Dispatch has an Item incidence in X7. A coarser relation that ignores event-object incidence would group them; qualified business-semantic equivalence separates them through the replacement and removal relations.

- **X3 versus X4:** A coarse business category such as “multi-package fulfillment” can group them. Activity-sequence and typed structural equivalence separate them, as does the preferred relation: X3 has one consolidated delivery, while X4 has two deliveries and staged payments.

- **X4 versus X8:** A multiplicity-only view can group them because both have two packages and two deliveries. Activity-sequence, typed structural, and preferred semantic equivalence separate them: X4 is forward split fulfillment with partial settlement; X8 includes a return, inspection, and repack.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py key should be treated as an exact structural key for the execution representation used by the function: event labels and ordering together with the participating object references/types represented in the OCEL event-object data. If raw identifiers enter that key, X1 and X2 can be separated despite their isomorphic structures. O2O qualifiers and business meanings are not guaranteed to be represented by that key; externality is only visible if encoded in the input representation.

Canonicalize or aggregate the returned clusters by a second signature that replaces local IDs with type and external flags, retains E2O incidence, and adds qualified O2O relations or derived motifs. Exact clusters are useful for checking ingestion and exact structural repetition. A coarser semantic grouping is more useful for segmentation and monitoring. `max_objs` limits practical key construction: a low limit can omit distinctions among large executions, while large connected executions can make exact comparison costly.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"
lead_ocel = pm4py.filter_ocel_lead_object_type(ocel, LEAD_TYPE)
raw_clusters = pm4py.cluster_equivalent_ocel(lead_ocel, max_objs=5)

def canonical_fragment(fragment):
    # Expected fragment fields: events, event_object, objects, optional o2o_edges.
    events = sorted(fragment["events"],
                    key=lambda e: (e["timestamp"], e["event_id"]))
    layers = defaultdict(list)
    for event in events:
        incidence = [
            (rel["object_type"], rel["object_id"])
            for rel in fragment["event_object"]
            if rel["event_id"] == event["event_id"]
        ]
        layers[event["timestamp"]].append((
            event["activity"],
            tuple(sorted((typ, str(oid).startswith("EXT"))
                         for typ, oid in incidence))
        ))
    event_order = tuple(tuple(sorted(v))
                        for _, v in sorted(layers.items()))

    counts = defaultdict(int)
    for typ, oid in set((o["object_type"], o["object_id"])
                        for o in fragment["objects"]):
        counts[(typ, str(oid).startswith("EXT"))] += 1
    object_profile = tuple(sorted((typ, ext, n)
                                  for (typ, ext), n in counts.items()))

    # O2O qualifiers may come from a domain-specific enrichment.
    o2o = tuple(sorted(
        (e["source_type"], e["source_external"], e["qualifier"],
         e["target_type"], e["target_external"], e.get("context_type", ""))
        for e in fragment.get("o2o_edges", [])
    ))
    return event_order, object_profile, o2o

semantic_groups = defaultdict(list)
for cluster in raw_clusters:
    for fragment in cluster:
        semantic_groups[canonical_fragment(fragment)].append(fragment)
```

The fragment field names and return shape should be adapted to the installed PM4Py version and OCEL representation; the important step is the identifier-invariant post-processing keyed by typed incidence and qualified relations.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** X4 loses the distinction between partial and completion settlement, though two payment events remain. X8 loses the package-replacement relation, but Return/Inspect and repeated packing still distinguish it. X7 remains distinct if Dispatch’s Item incidence is retained; it can collapse toward X1 if that incidence is also discarded.
- **Ignore external objects:** X5 and X6 collapse into the local standard pattern, losing the cross-order logistics and finance distinctions. X1 and X2 are unchanged.
- **Collapse repeated same-label events:** If repeated events are collapsed and object counts are discarded, X3, X4, and X8 can move toward simpler activity patterns; X4 also loses payment multiplicity. If object counts and incidences remain, their package and delivery structures still distinguish them.
- **Treat Pack/Dispatch order as partial:** X4 can be represented as two package-dispatch chains whose interleaving is immaterial. This merges alternate total orderings of those chains, but does not make X4 equivalent to X3, which has one delivery. X8 remains distinct because its return and inspection form a separate lifecycle stage.
- **Represent payment multiplicity as amount:** X4’s two payment events may become one aggregate payment, removing the partial-settlement motif. Its two deliveries still distinguish it from X3 unless delivery structure is also abstracted.

## 8. Limitations and recommendation

| Purpose | Recommended equivalence | Reason |
|---|---|---|
| Compliance monitoring | Qualified business-semantic equivalence | Retains cross-order sharing, replacement/removal, and settlement distinctions |
| Operational segmentation | Business-semantic equivalence | Gives actionable groups such as standard, split, shared, and return flows |
| Root-cause analysis | Typed structural equivalence enriched with external flags and O2O qualifiers | Retains event-object structure needed to locate the deviation |
| Descriptive reporting | Activity sequence or a coarser business grouping | Keeps summaries readable while preserving the distinctions important to the audience |

No one relation serves all four purposes: compliance requires risk-relevant semantics, segmentation needs actionable categories, root-cause analysis needs structural detail, and reporting benefits from simpler groupings.
