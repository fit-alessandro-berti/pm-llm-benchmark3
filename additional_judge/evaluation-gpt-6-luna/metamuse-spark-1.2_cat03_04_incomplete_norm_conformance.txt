## 1. Conformance semantics

- **Forbidden behavior:** A relation explicitly marked forbidden is a violation when the observed relation is genuine and its stated scope applies.
- **Missing mandatory behavior:** A required relation is absent for an in-scope case. Counts alone may show a gap, but case level data and scope determine whether it is a true violation.
- **Unexpected but unregulated behavior:** A relation absent from the norm, or marked unspecified, is not a violation. It may still warrant review.
- **Typical-pattern absence:** Missing a typical relation is a departure from a common pattern, not a violation; legitimate exceptions are explicitly allowed.
- **Likely data-quality error:** Evidence suggests an observed relation or missing link may result from incorrect extraction, joins, or representation. Treat the apparent conformance result as provisional until checked.
- **Abstraction mismatch:** The summary’s model relation may be stricter or less expressive than the business rule—for example, directly-follows when the norm says “eventually.”
- **Insufficient evidence:** Available counts do not establish scope, sequence, or cause well enough to classify a case conclusively.

The norm is closed-world for explicitly forbidden relations and mandatory columns within their stated scope. Elsewhere it is open-world: an unlisted or unspecified relation is not prohibited simply because the norm does not mention it.

## 3. Detailed reasoning by model family

### OC-DFG

An OC-DFG summary shows directly-follows relations within an object’s event sequence, with counts. It can identify observed paths and apparent gaps in those paths. It cannot, from aggregate counts alone, establish an individual case’s complete sequence, whether the object is in scope, or why a path is absent.

N1 says every newly created **standard** Order should **eventually** enter validation. The 98/100 directly-follows count is only an approximation: an intervening review event could make the directly-follows edge absent while the Order still satisfies the eventual rule. The two cases need full traces and scope information before being called violations. This is a key abstraction risk: “eventually” must not be silently converted into “immediately next.”

N2 is typical, so 83 Validate -> Close relations do not make the remainder nonconforming. N2 explicitly allows intermediate events, and the 72 Validate -> Issue Invoice paths fit that open description. N3 is forbidden, so the two Cancel -> Dispatch cases merit investigation if the event and object links are correct. N4 is mandatory only for externally shipped packages; 198/200 is a gap count, but scope and event capture still matter. N5 is typical: the 92/110 payment paths, four write-offs, and 14 invoices without observed successors do not by themselves establish violations. N6 leaves Reopen -> Close unspecified, so its single occurrence is not a violation.

### OTG

An OTG records relations between object types, such as an Order interacting with an Item or being born together with a Payment. It can show that a type-level relation exists and its weight. It generally cannot show whether that relation was valid for a particular event, whether it violates a sequence rule, or whether a missing edge is a true business omission.

The Order–Item and Package–Delivery interactions appear at the expected weights, although those totals do not prove every required event-level link. The Invoice–Payment edge is typical, not mandatory for every Invoice. The Order–Customer and Order–RiskCase edges are unspecified; their presence is not noncompliance. The single Order–Payment cobirth is different: T6 explicitly forbids it, so it is a potential violation requiring verification of event and object birth semantics. The seven Package–Delivery codeaths are not addressed by the norm and should not be treated as violations.

### ET–OT

ET–OT relates event types to object types. It can identify missing or extra participation by event type, and the stated mandatory or forbidden statuses give these observations clear meaning. It cannot, from aggregate counts alone, explain an exception or validate a questionable link.

The Add Item counts show two fewer Order links than Item links, a likely gap against E2; event-level inspection is needed to identify which events and why. The two Dispatch Package events without Delivery relations appear to miss E6 and T2, but carrier references may expose a representation mismatch. Record Payment has complete Payment links under E7, while one event lacks the Invoice link required by E8 unless it was explicitly typed as unapplied cash. Finance’s general statement that unapplied cash is possible does not itself meet the norm’s explicit labeling condition.

Manual Compliance Review–RiskCase is unspecified under E9, and the additional Customer links are also unregulated by this norm. Sensor Heartbeat–Invoice is explicitly forbidden under E10, but the suspected reused-ID join makes it a likely data-quality error pending verification.

## 4. Mandatory, forbidden, typical, and unregulated behavior

**Mandatory**

- N1: newly created standard Orders must eventually enter validation. The two missing direct-follow edges change classification only if full traces show no later validation or the Orders are in scope; direct-follow absence alone is inconclusive.
- N4: externally shipped Packages must have Pack -> Dispatch. The two gaps are in scope only if those Packages were externally shipped and observation is complete.
- T1 and E2: Add Item requires an Order interaction/participation. Two events lack the required Order link.
- T2 and E6: Dispatch Package requires a Delivery interaction/participation. Two events lack the Delivery link unless the norm’s object-participation requirement is satisfied by the carrier reference.
- E1, E3, E4, E5, E7, E8: required event-object participation. The observed gaps are two Add Item–Order links and one unlabeled Record Payment–Invoice link. E8’s exception applies only if the event is explicitly typed as unapplied cash.

**Forbidden**

- N3: Cancel Order -> Dispatch Package for the same Order. Two observed cases are violations if linkage and sequence are correct.
- T6: Order–Payment object cobirth. One observed edge is a potential violation if it represents a genuine shared business event.
- E10: Sensor Heartbeat–Invoice. One observed edge is forbidden if genuine; the suspected reused-ID join makes a data-quality explanation likely.

**Typical**

- N2: Validate Order -> Close Order. Its absence in some cases is not a violation; intermediate events are allowed.
- N5: Issue Invoice -> Record Payment. The 18 invoices without that edge are not automatically violations. Four write-offs and 14 invoices with no observed successor need context such as payment terms and observation window.
- T3: Invoice–Payment interaction. Its absence can be legitimate, including unapplied cash.

**Unregulated**

- Create Order -> Manual Compliance Review for three Orders; whether these count against N1 depends on Order scope and eventual validation.
- Validate Order -> Issue Invoice for 72 Orders.

- Order–Customer and Order–RiskCase OTG relations.

## 5. PM4Py conformance code sketch

```python
import pm4py

# Discover the observed model-family summaries.
obs_ocdfg = pm4py.discover_ocdfg(ocel)
obs_otg = pm4py.discover_otg(ocel)
obs_etot = pm4py.discover_etot(ocel)

# Norm dictionaries/tuples are assumed to encode the supplied statuses and scopes.
# These comparisons flag structural differences only; they do not decide scope,
# exceptions, data quality, or whether "eventually" was incorrectly modeled as
# directly-follows.
def flatten(value):
    if isinstance(value, dict):
        return {
            key: flatten(item)
            for key, item in value.items()
        }
    if isinstance(value, (set, list, tuple)):
        return {flatten(item) for item in value}
    return value

def structural_difference(observed, normative):
    observed_items = flatten(observed)
    normative_items = flatten(normative)
    return {
        "observed": observed_items,
        "normative": normative_items,
        "observed_only": observed_items - normative_items
            if isinstance(observed_items, set) and isinstance(normative_items, set)
            else None,
        "normative_only": normative_items - observed_items
            if isinstance(observed_items, set) and isinstance(normative_items, set)
            else None,
    }

ocdfg_diff = structural_difference(obs_ocdfg, norm_ocdfg)
otg_diff = structural_difference(obs_otg, norm_otg)
etot_diff = structural_difference(obs_etot, norm_etot)

print("OC-DFG structural comparison:", ocdfg_diff)
print("OTG structural comparison:", otg_diff)
print("ET-OT structural comparison:", etot_diff)
```
