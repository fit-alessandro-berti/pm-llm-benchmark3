## 1. Target definition

The primary target is the observed-policy probability of default within 90 days after Account Activated, conditional on eventual activation and on information available at an early prediction point. The unit is an application/account; the target population is applications that are eventually activated and have an ascertainable 90-day outcome under the observed process. The estimand is therefore conditional on selection into activation. It does not define a default outcome for applications that are never activated.

Set prediction time at the third observed event, or at 14 days after Application Started if fewer than three events have occurred by then, whichever comes first. Use only events and attributes available by that time. Exclude cases already terminal or activated before that point from this pre-decision prediction task; report their counts. The horizon begins at activation, not prediction time, so the model’s intended use is to estimate post-activation risk from an early application prefix for cases that later activate. Because activation is not known at prediction time, pair this with a separately validated activation-probability estimate if the score is shown for all active applications.

A credible alternative is a multi-state target for all applications: transition to activation, rejection, withdrawal, or transfer, followed by default within 90 days after activation. That answers a process-outcome question under the observed policy. It still does not assign counterfactual default outcomes to rejected or withdrawn applications.

## 2. Cohort construction

Use an as-of cutoff of 15 February 2026 for the snapshot, and require both a completed 90-day post-activation horizon and an observed label before treating a case as a binary training example. Since feed delay is 7–35 days, a conservative maturity date is activation plus 125 days; the recorded `label_available_at` must also be on or before cutoff. The label export’s 21,600 cases are treated as matured only after verifying those conditions.

| Cohort status | Count | Treatment |
|---|---:|---|
| Activated, matured, default | 2,700 | Labeled event |
| Activated, matured, non-default | 18,900 | Labeled non-event |
| Activated, not yet mature or feed not yet available | 3,600 | Right-censored or delayed label; not a negative |
| Rejected | 9,100 | Competing process outcome; no observed default target |
| Withdrawn | 5,700 | Competing process outcome; no observed default target |
| Transferred | 2,900 | Competing outcome or incomplete follow-up; investigate linkage |
| Still open at extraction | 5,100 | Censored in process follow-up |
| **Total** | **48,000** | |

For the conditional default model, include activated accounts with matured labels and a valid prefix at the specified prediction time. Exclude non-activated outcomes from the binary target; retain them in the cohort accounting and in a separate activation/competing-outcome analysis. Cases that activate or terminate before the prediction point are outside this early-prefix landmark population and should be counted explicitly. Reconcile case IDs and category precedence so the flow table remains mutually exclusive.

## 3. Censoring and missing-label strategy

- **Ordinary right censoring:** An account whose 90-day horizon has not elapsed by cutoff has incomplete outcome follow-up. Do not call it non-default. Use a survival or cumulative-incidence analysis where follow-up time and event status are available.
- **Delayed labels:** A completed horizon with no feed yet is not necessarily censoring at 90 days. Track horizon completion separately from feed arrival and use `label_available_at` to define when a label could have been used in training.
- **Selection through activation:** Default is observed only after activation, so the matured activated sample estimates risk among selected accounts. Model activation separately; inverse-probability weighting can be a sensitivity analysis only if relevant selection drivers are observed and positivity holds. Neither weighting nor imputation makes the result a counterfactual default estimate without stronger assumptions.
- **Transfer:** Treat transfer as a competing process outcome when no subsequent activation is observed in the target platform. For linked cases, continue follow-up under a defined cross-platform case identity. For unlinked cases, distinguish lost follow-up from an observed competing event. With only 60% linkage, neither interpretation is fully identified.
- **Permanently missing feeds:** Estimate missingness by source, partner, time, and observed prefix. Use inverse-probability-of-observation weighting and sensitivity bounds or scenarios for partner outcomes. Missing-at-random conditional on observed fields is an assumption, not a fact.

The primary analysis is the matured, labeled activated cohort with temporal evaluation, accompanied by a survival/cumulative-incidence analysis using all eligible activated accounts with known follow-up. Sensitivities should include a longer maturity lag, inverse-probability weighting for label observation, alternative transfer handling, and best/worst plausible outcomes for permanently missing feeds.

Label arrival and observed censoring can be measured. Conditional independence of censoring or feed missingness is only partially assessable. Counterfactual outcomes for never-activated cases and missing partner outcomes are fundamentally untestable from this export alone.

## 4. Prefix extraction

Generate prefixes at the third event and at elapsed-time landmarks such as 7 and 14 days after start. For each landmark, retain only events timestamped at or before it and attributes known by that time. If a case has fewer events, use the elapsed-time prefix, including a zero-event prefix where appropriate; report short-prefix coverage separately. Do not wait for a later event to create a feature for an earlier landmark.

Represent repeated document requests and returns as ordered loops, with counts and elapsed time between iterations. Canonicalize renamed activities using a documented migration mapping, retain original names for audit, and deduplicate only verified migration duplicates. Preserve timestamps and distinguish genuine repeated events from duplicates.

## 5. Process-aware features

**Static case attributes:** requested amount, region, and channel, provided they are known at the prediction time. Source system and policy period may be used to characterize cohorts or drift.

**Prefix-derived features:** current activity, activity counts and transitions, time since start and between events, number and duration of document loops, current queue or resource, distinct resources involved, resource handoffs, and risk-score values and changes observed within the prefix. Capture short-prefix length explicitly.

**Historical-reference features:** resource experience reconstructed as of event time, queue workload, and historical transition or duration rates. Compute these from prior data only, within each temporal training fold. Do not use outcome rates calculated using future cases.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Set after final credit decision | Exclude before decision; use only if a later prediction landmark explicitly permits it | Drop for primary landmark | Reveals a downstream decision |
| `decision_reason` | Populated at or after Accept/Reject | Available only after the decision event | Drop | Reveals terminal process outcome |
| `collection_status` | Updated after activation and may reveal default | Never use for the early application prefix | Drop | Direct post-outcome leakage |
| Future events | Contract, activation, collections, and default events reveal later process state | Include events only through the landmark timestamp | Drop beyond landmark | Prevents future-path leakage |
| `documents_total` | Nightly value can include later same-day uploads | Use event-level uploads through landmark, or a lagged snapshot known by then | Repair or drop | Same-day snapshot is not reliably as-of |
| Updated `risk_score` | Later updates may follow documents or decisions | Use only values timestamped and available by landmark; define tie handling | Repair | A valid feature only when its version is as-of |
| Resource experience | Stored at extraction, not event time | Reconstruct from historical employment data as of event time | Repair or drop | Extraction-time value leaks future experience |
| `label_available_at` and `default_90d` | Label and label-arrival timing reveal outcome or ascertainment | Use for target construction and maturity only | Drop from features | Outcome metadata is not a predictor |
| `data_extract_time` | Snapshot metadata can encode collection timing | Use as cutoff metadata only | Drop from features | Not available as a case-level predictor at scoring |

## 7. Validation design

Use temporal splits by application start time, with label maturity determined separately at each simulated training cutoff:

| Split | Start dates | Role |
|---|---|---|
| Train | 1 Jan 2024–30 Jun 2025 | Pre-policy training |
| Validation | 1 Jul 2025–14 Oct 2025 | Post-policy, pre-migration validation |
| Test | 15 Oct 2025–31 Dec 2025 | Post-migration test |

For each simulated deployment date, train only on labels that would have arrived by that date. The late test period will have incomplete label maturity at the extraction date; report its eligible counts and do not infer performance for immature cases. Add rolling-origin backtests around both 1 July and 15 October to separate policy and migration effects. Compare migration-era results under canonicalized and raw activity names.

Evaluate discrimination with PR-AUC and ROC-AUC, and calibration with Brier score, calibration slope/intercept, and reliability plots on matured activated cases. For survival or competing-risk analyses, use time-dependent discrimination and calibration or cumulative-incidence scoring with censoring handled by the estimator. Report event counts, censoring, and maturity alongside every metric. Assess calibration and performance by policy period, migration period, region, channel, partner/source, activation, and transfer linkage. Monitor activation and competing-outcome rates, prefix distributions, missingness, and calibration over time.

A random case split mixes policy and migration regimes, can place near-contemporaneous cases in both train and test, and ignores when labels became available. It can therefore overstate performance for a future deployment.

## 8. Limitations and decision-use boundary

The study can estimate predictive association among activated cases with observed outcomes under the historical process. It cannot claim that rejected, withdrawn, or transferred applicants would have defaulted or not defaulted if activated. The conditional model describes a selected population; it is not a population-wide or causal estimate. A policy-specific counterfactual default risk would require explicit intervention definitions and strong assumptions about selection, positivity, and unmeasured drivers.

Deployment can change the data-generating process in at least three ways:

1. Using risk scores to alter approval or activation changes which cases enter the observed default cohort.
2. Triggering extra documents or manual review changes process paths, timing, and withdrawal rates.
3. Partner routing, policy thresholds, system migration, or feed practices can change transfer rates, activity distributions, and label missingness.

Use the score for monitored decision support within the validated population and policy context. Revalidate after process or policy changes; do not present it as counterfactual default risk for non-activated applications.

## 9. PM4Py-oriented Python implementation skeleton

```python
import numpy as np
import pandas as pd
import pm4py

AS_OF = pd.Timestamp("2026-02-15")
HORIZON_DAYS, MAX_FEED_LAG_DAYS = 90, 35
N_PREFIX, MAX_PREFIX_DAYS = 3, 14
ACTIVITY_MAP = {
    "Credit Review (new)": "Credit Review",
    "Request Documents": "Documents Requested",
    "Account activated": "Account Activated",
}
TERMINAL = {"Rejected", "Withdrawn", "Transferred"}
FORBIDDEN = {
    "final_limit", "decision_reason", "collection_status",
    "documents_total", "default_90d", "label_available_at",
    "data_extract_time",
}

def load_events(path="applications_events.csv"):
    d = pd.read_csv(path, parse_dates=["time:timestamp", "label_available_at",
                                       "data_extract_time"])
    d["activity_original"] = d["concept:name"]
    d["concept:name"] = d["concept:name"].replace(ACTIVITY_MAP)
    # Validate duplicate signatures before removing migration duplicates.
    d = d.drop_duplicates(["case:concept:name", "concept:name",
                           "time:timestamp", "org:resource"])
    return d.sort_values(["case:concept:name", "time:timestamp"])

def first_time(g, activity):
    x = g.loc[g["concept:name"].eq(activity), "time:timestamp"]
    return x.min() if len(x) else pd.NaT

def make_case_table(d):
    out = []
    for cid, g in d.groupby("case:concept:name", sort=False):
        start = g["time:timestamp"].min()
        activation = first_time(g, "Account Activated")
        term_rows = g[g["concept:name"].isin(TERMINAL)].sort_values("time:timestamp")
        term = term_rows.iloc[0] if len(term_rows) else None
        available = g["label_available_at"].dropna()
        label_at = available.min() if len(available) else pd.NaT
        labels = g["default_90d"].dropna() if "default_90d" in g else pd.Series(dtype=float)
        y = labels.iloc[-1] if len(labels) else np.nan
        mature_by_horizon = pd.notna(activation) and (
            activation + pd.Timedelta(days=HORIZON_DAYS + MAX_FEED_LAG_DAYS) <= AS_OF
        )
        observed_label = mature_by_horizon and pd.notna(label_at) and label_at <= AS_OF and pd.notna(y)
        if term is not None:
            status = str(term["concept:name"]).lower()
        elif pd.notna(activation):
            status = "labeled_default" if observed_label and y == 1 else (
                "labeled_nondefault" if observed_label and y == 0 else "activated_immature"
            )
        else:
            status = "open"
        out.append({
            "case:concept:name": cid, "start_time": start,
            "activation_time": activation,
            "terminal_time": term["time:timestamp"] if term is not None else pd.NaT,
            "terminal_type": term["concept:name"] if term is not None else None,
            "label_available_at": label_at, "default_90d": y,
            "label_matured": bool(observed_label), "status": status,
        })
    return pd.DataFrame(out)

def temporal_split(cases):
    c = cases.copy()
    c["split"] = np.select(
        [c.start_time < "2025-07-01", c.start_time < "2025-10-15"],
        ["train", "validation"], default="test"
    )
    return c

def make_prefix_table(d, cases):
    # Landmark is the earlier of Nth event, 14 days, and any prior terminal/activation.
    limits = []
    for cid, g in d.groupby("case:concept:name", sort=False):
        g = g.sort_values("time:timestamp")
        start = g["time:timestamp"].min()
        candidates = [start + pd.Timedelta(days=MAX_PREFIX_DAYS)]
        if len(g) >= N_PREFIX:
            candidates.append(g["time:timestamp"].iloc[N_PREFIX - 1])
        limits.append((cid, min(candidates)))
    lm = pd.DataFrame(limits, columns=["case:concept:name", "landmark"])
    x = d.merge(lm, on="case:concept:name")
    x = x[x["time:timestamp"] <= x["landmark"]].copy()
    # Remove post-prefix target and decision fields before building features.
    x = x.drop(columns=[c for c in FORBIDDEN if c in x.columns])
    log = pm4py.format_dataframe(
        x, case_id="case:concept:name", activity_key="concept:name",
        timestamp_key="time:timestamp"
    )
    prefixes = pm4py.get_prefixes_from_log(
        log, prefix_length=N_PREFIX, case_id_key="case:concept:name",
        activity_key="concept:name", timestamp_key="time:timestamp"
    )
    # DFG/variants describe observed prefix structure; they are not target encodings.
    dfg = pm4py.discover_dfg(
        log, case_id_key="case:concept:name", activity_key="concept:name",
        timestamp_key="time:timestamp"
    )
    variants = pm4py.get_variants(
        log, case_id_key="case:concept:name", activity_key="concept:name"
    )
    rows = []
    for cid, g in x.groupby("case:concept:name", sort=False):
        g = g.sort_values("time:timestamp")
        acts = g["concept:name"].tolist()
        rows.append({
            "case:concept:name": cid,
            "event_count": len(g),
            "elapsed_seconds": (g["time:timestamp"].max() -
                                g["time:timestamp"].min()).total_seconds(),
            "current_activity": acts[-1],
            "document_requests": acts.count("Documents Requested"),
            "resource_count": g["org:resource"].nunique(),
            "risk_score_asof": g["risk_score"].dropna().iloc[-1]
                if g["risk_score"].notna().any() else np.nan,
        })
    f = pd.DataFrame(rows).merge(cases, on="case:concept:name", how="left")
    assert not (set(f.columns) & FORBIDDEN)
    return f, prefixes, dfg, variants

def main():
    events = load_events()
    cases = temporal_split(make_case_table(events))
    features, prefixes, dfg, variants = make_prefix_table(events, cases)
    print(cases["status"].value_counts(dropna=False))
    print(cases.groupby("split")["status"].value_counts())
    print("Feature leakage columns:", set(features.columns) & FORBIDDEN)
    # Confirm the supplied snapshot totals after case-ID reconciliation.
    assert len(cases) == 48000
    # Later connect a survival or competing-risk estimator using follow-up time,
    # event type, and censoring indicators; PM4Py does not supply that estimator.

if __name__ == "__main__":
    main()
```
